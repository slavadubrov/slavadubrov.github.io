LLM Fine-Tuning Guide: LoRA, QLoRA, Unsloth, Axolotl

Viacheslav Dubrov

2026-01-04 · Updated 2026-09-12 · 22 min · Model Engineering

This guide is for Python engineers deciding whether and how to fine-tune a large language model. You will learn when to choose fine-tuning over prompting or retrieval and how to choose between methods such as LoRA and QLoRA. The guide also explains how to prepare data, evaluate the trained model, and plan its deployment.

The examples explain configurations and checks. They are not a verified end-to-end training recipe; the practical section separates the companion repository commands from a proposed training configuration.

For a shorter comparison of those options, see Fine-Tuning vs RAG vs Prompting.

Should you fine-tune at all?

Before you spend GPU hours, decide whether fine-tuning is the right tool for the problem in front of you.

Byte says

If valid JSON is the only missing behavior, test constrained decoding on the original weights first. A training run is a long way to discover a missing brace.

Fine-tuning changes behavior encoded in weights. Retrieval supplies evidence at inference time, so it is the better starting point for facts that change or need citations. New documents become available only after ingestion and indexing; check that freshness against your requirement.

Clear prompts and examples are cheaper to iterate on than a new training run. They may already solve a style or instruction-following problem. Fine-tuning can reduce repeated prompt tokens, but serving latency depends on the model, output length, hardware, and implementation; a weight update is not itself a speedup.

For syntax, libraries such as xgrammar and outlines mask invalid next tokens under a supported schema or grammar. A successfully completed constrained generation belongs to that language. Handle truncation and other incomplete generations separately, and validate the result before using it. The constraint cannot make a customer ID true or a tool choice appropriate. Measure its latency on your backend rather than assuming a fixed overhead.

Make the business case measurable

Fine-tuning may reduce recurring prompt tokens or let a smaller model meet the target, but neither saving is automatic. Calculate the break-even point with your own traffic and pricing:

[ \text{break-even requests} = \frac{\text{training + evaluation + deployment cost}} {\text{baseline cost/request} - \text{tuned cost/request}} ]

If the denominator is small, negative, or based on an unproven quality assumption, the project does not yet have an economic case.

[!TIP] The hybrid setup A common architecture is a task-adapted smaller model plus retrieval for changing facts. Treat the larger prompted model as the baseline and keep the smaller model only if it meets the same task-specific quality and safety thresholds.

Types of fine-tuning

There are three main shapes fine-tuning can take. They differ in what kind of data they need and what they teach the model.

1. Continued pre-training (self-supervised)

You train the base model on more raw text, using the next token in each sequence as the training target. That is self-supervised learning: the text supplies its own targets, just as in the original pre-training run.

When to use it:

  • The domain has vocabulary the base model never saw (medical, legal, internal codebases).
  • You have piles of domain text but no labeled (input, output) pairs.
  • The base model fumbles domain-specific terminology.

Example: training on millions of clinical notes so the model picks up medical abbreviations, drug names, and clinical workflows.

2. Supervised fine-tuning (SFT)

SFT trains on labeled (input, output) pairs. You show the model the exact output you want for each input.

When to use it:

  • You have a specific task with a clean input/output format.
  • You have quality labeled data, even in small amounts.
  • You need predictable behavior on a known shape of input.

Example: training on (SQL query description, SQL code) pairs for text-to-SQL. This fixed calendar interval assumes signup_date is stored in UTC:

{
    "input": "Get users who signed up in August 2026 (UTC)",
    "output": "SELECT * FROM users WHERE signup_date >= '2026-08-01' AND signup_date < '2026-09-01'"
}

3. Instruction tuning

Instruction tuning is a special case of SFT designed to make models follow a wide variety of natural-language instructions. The training data is (instruction, response) pairs across many different tasks.

When to use it:

  • You want a general-purpose assistant (like ChatGPT or Claude).
  • The model needs to handle varied, open-ended requests.
  • You’re building a chat interface.

Example: training on thousands of diverse instructions like “Summarize this article,” “Write a poem about X,” “Explain Y in simple terms.”

[!NOTE] What people actually do SFT and instruction tuning use the same next-token objective; the distinction is the breadth and construction of the dataset. Continued pre-training is a separate experiment and should be followed by tests for both domain gains and general-capability regression.

The 7-stage fine-tuning pipeline

Fine-tuning is a pipeline, not a single command. Each stage has its own failure modes, and skipping one usually shows up as a bad model later.

Each stage builds on the previous one:

  1. Data preparation — Define the unit of evaluation, split the data, then clean and format it
  2. Model selection — Choose the right base model and load weights
  3. Training setup — Configure hardware, hyperparameters, and optimization strategy
  4. Fine-tuning — Run SFT, DPO, or ORPO training
  5. Evaluation — Benchmark performance and validate quality
  6. Deployment — Export and serve your model
  7. Monitoring — Track performance, maintain, and iterate

[!WARNING] Data is the foundation Training reproduces systematic flaws in the examples. Inspect labels, leakage, coverage, and policy compliance before spending time on optimizer sweeps.

Stage 1: Data preparation

Many fine-tuning projects fail here, not in training. Modern data prep is more than running a regex over CSVs.

Five transformations after the source split

Assign source groups to train or evaluation before transforming rows. A support ticket and every rewrite of that ticket keep the same partition. Cluster known near-duplicates before assigning groups, then check again across partitions after cleaning. Freeze the evaluation set; augment only training data.

List the errors your examples should teach the model to correct, then define each row’s required fields and labels. Choose processing tools for those steps; DataTrove and Distilabel can help with larger datasets.

1. Ingestion and filtering

  • Action: remove broken UTF-8 and off-task content. Label refusals by policy: retain correct refusals as training targets and evaluation cases; exclude only invalid or off-task refusals.
  • Tools: Trafilatura for extraction and fastText’s language-identification models for language ID; the distributed lid.176 models recognize 176 languages.

2. Sensitive-data policy

  • Action: decide what the model is allowed to learn, then redact, tokenize, or exclude personal and confidential fields as required.
  • Tools: Microsoft Presidio or scrubadub.
  • Why: a detector is only one control; provenance, consent, retention, access, and deletion requirements still apply.

3. Deduplication (MinHash LSH)

  • Action: remove near-duplicates to reduce repetition and leakage risk; this does not prevent memorization.
  • Tools: DataTrove handles terabyte-scale processing well.

4. Synthetic augmentation, if needed

  • Action: use a suitable teacher model to rewrite training examples into instruction-response pairs, retaining their source IDs. Do not augment the held-out partition.
  • Tools: Distilabel.
  • Validation: sample teacher outputs, check them against the same rubric as human labels, and report results separately for synthetic and human-written examples. Such an evaluation subset is called a slice; other useful slices include language and task type.

5. Formatting

  • Action: convert to a standard format (Alpaca or ShareGPT).

Data format examples

Alpaca format (instruction-following):

{
    "instruction": "Summarize the following text.",
    "input": "The text to be summarized...",
    "output": "This is the summary."
}

ShareGPT-style storage (conversational):

{
    "conversations": [
        { "from": "user", "value": "Hello, who are you?" },
        { "from": "assistant", "value": "I am a helpful AI assistant." }
    ]
}

What actually matters

  • Coverage before volume. Add examples that represent distinct failure modes, not repetitions of the easy majority case.
  • Cleanliness. Drop irrelevant text, normalize whitespace, keep formatting consistent.
  • Balance. Preserve important rare cases and report performance per slice.
  • Separation. Split by source, user, document, or time when random row splits would leak near-duplicates.
  • Provenance. Record the source, license or permission, transformation history, and deletion path for every dataset version.

Stage 2: Model selection and hardware

The base model and its minimum GPU memory requirement determine what you can train.

Start with the smallest base model that already clears the non-negotiable baseline checks. Confirm:

  • license and redistribution terms for the intended product;
  • language, domain, tool-use, and safety behavior before adaptation;
  • tokenizer and chat-template compatibility with the dataset;
  • maximum context and truncation behavior needed by real examples;
  • support in both the training framework and target serving engine.

Fine-tuning is an adaptation step, not a repair for an unsuitable base. If the model fails capabilities the dataset does not cover, choose another base before running more epochs.

Size the run, not the marketing tier

There is no durable “model size → GPU” table. Peak memory changes with weight precision, optimizer, trainable parameter count, sequence length, micro-batch size, activation checkpointing, attention implementation, and framework overhead. Start with a memory estimate, then run a short maximum-length smoke test on the exact stack.

Memory componentFull fine-tuningLoRAQLoRA
Base weightsTraining precisionFrozen, usually BF16/FP16Frozen, typically 4-bit NF4
GradientsAll trainable weightsAdapter weightsAdapter weights
Optimizer statesAll trainable weightsAdapter weightsAdapter weights
ActivationsDepends on batch and sequence length in every methodSame dependencySame dependency

The original QLoRA paper fit a 65B LLaMA model on one 48 GB GPU in its specific setup. That result is a useful bound, not a promise that every current 70B architecture, context length, kernel, or trainer will fit the same device.

Memory math

For a model with PPP parameters, weights alone require approximately 2P2P2P bytes in BF16/FP16 or 0.5P0.5P0.5P bytes at four bits, before quantization metadata and runtime buffers. Full Adam-style training adds gradients, optimizer states, and often higher-precision master weights. LoRA avoids most trainable-state memory; QLoRA additionally reduces the frozen base-weight footprint. Activations can still dominate at long sequence lengths.

Use this workflow:

  1. Choose the longest sequence and micro-batch you must support.
  2. Estimate weights and trainable state, leaving headroom for activations and kernels.
  3. Run one forward/backward step at maximum length.
  4. Record peak allocated and reserved memory.
  5. Only then scale batch size, rank, sequence length, or GPU count.

Stage 3: Training setup and methods

From stored rows to training targets

ShareGPT is a dataset shape; ChatML is one serialization convention. Convert from/value to the roles and fields the trainer accepts, then use the selected model’s chat template. Do not substitute ChatML tokens just because the data is conversational.

For the greeting row above, the normalized messages are:

messages = [
    {"role": "user", "content": "Hello, who are you?"},
    {"role": "assistant", "content": "I am a helpful AI assistant."},
]
# Inspection step after loading the selected model's tokenizer:
rendered = tokenizer.apply_chat_template(
    messages, tokenize=False, add_generation_prompt=False,
)
print(rendered)

Inspect the actual serialized row before training: role delimiters, end-of-turn tokens, and tool schemas must match inference. For a tool-use row, preserve tool definitions, assistant tool calls, and tool results as distinct fields. Check that truncation does not remove the supervised response or cut a tool argument in half.

Loss masking chooses which tokens the model is rewarded for predicting. In full-sequence training, user, system, tool, and assistant text can all contribute. In assistant-only training, those context tokens remain visible to attention but their labels are ignored (commonly -100); only the assistant spans contribute. For this greeting, the answer should be a target and the user’s question should not, if assistant-only behavior is the intent.

TRL’s SFT documentation supports assistant_only_loss=True for conversational datasets whose templates expose generation spans. A template without those spans cannot supply that mask. Prompt/completion datasets have a separate completion_only_loss option. Before enabling either, inspect one tokenized batch and decode the tokens with non-ignored labels. Then repeat with a tool conversation and a maximum-length example. The illustrative training configuration below deliberately uses full-sequence loss; assistant-only training requires this additional template and mask check.

Choose a sequence length from the data distribution and run the maximum-length memory check from Stage 2. Packing places several shorter examples into one training sequence. Start without it so row boundaries are easy to inspect. Benchmark packing only after the serialized rows and labels are correct.

Full fine-tuning vs PEFT

Full fine-tuning (FFT) updates every weight, so gradients and optimizer state scale with the whole model. The peak cannot be inferred from parameter count alone, but it is far above the memory needed to load the weights for inference.

Parameter-efficient fine-tuning (PEFT) trains only a small subset of parameters and freezes the rest. The math gets a lot friendlier.

LoRA: the starting point

LoRA (Low-Rank Adaptation) freezes a pre-trained matrix and represents its learned update with two smaller matrices. The original paper motivates this with the hypothesis that useful adaptation updates have low intrinsic rank.

DoRA: weight-decomposed LoRA

DoRA (Weight-Decomposed Low-Rank Adaptation) separates the magnitude of each weight vector from its direction. The DoRA paper applies a LoRA update to the directional component while learning the magnitude separately.

How it works:

Instead of treating weights as a single entity, DoRA breaks pre-trained weights into two components:

  1. Magnitude — a trainable value per weight vector.
  2. Direction — a normalized vector updated through low-rank matrices.

In compact column-wise notation:

W′=mV+BA∥V+BA∥cW' = m \frac{V + BA}{\lVert V + BA \rVert_c}W′=m∥V+BA∥c​V+BA​

where:

  • m = magnitude (trainable)
  • V=W0V = W_0V=W0​ = the frozen initial matrix; normalize after adding BABABA
  • BABABA = the learned low-rank directional update
  • ∥⋅∥c\lVert \cdot \rVert_c∥⋅∥c​ = column-wise normalization

What you get for that extra structure:

  • More degrees of freedom than standard LoRA because magnitude can change independently.
  • Better results than LoRA in several configurations reported by the proposing paper.
  • Extra parameters and computation, so the gain should be verified on your task and serving path.

Adapter merging for multi-task learning

Separate adapters let one frozen base support several tasks. You can route requests to an adapter, serve multiple adapters from one engine when supported, or create an offline merged candidate. Merging can introduce interference, so evaluate the merged artifact rather than assuming the source adapters compose cleanly.

Common merging methods:

  1. Concatenation — combine adapter parameters and grow the effective rank. Fast and simple.
  2. Linear combination — weighted sum of adapters. Gives you knobs.
  3. SVD — matrix decomposition for merging. More flexible, but slower.

Example: one adapter for summarization, another for translation, merged into a single multi-task model.

Stage 4: Fine-tuning and preference alignment

SFT learns demonstrations. Preference optimization instead learns from comparisons such as “chosen response A is better than rejected response B”. Use it only when pairwise preference is the right label for the error; factual correctness and policy compliance often need stronger evaluators than a global preference.

PPO-based RLHF

RLHF means reinforcement learning from human feedback. The policy is the language model that generates responses; a reward model scores those responses using preferences learned from human comparisons. A PPO-based recipe has three stages:

  1. SFT — learn the task.
  2. Reward model — train on human preferences (chosen vs rejected).
  3. PPO (Proximal Policy Optimization) — generate responses and update the language model to increase their reward scores.

The operational cost comes from the moving parts:

  • Complicated to implement and maintain.
  • Expensive — you train multiple models.
  • Sampling from the model being trained requires checks for unstable updates and responses that exploit the reward model without satisfying the task.

DPO

DPO (Direct Preference Optimization) drops the separate reward model and reinforcement-learning loop. It favors chosen responses while discouraging large changes from a fixed starting model, called the reference model. The DPO paper derives this objective by limiting how far response probabilities can move from that reference; the mathematical limit is a KL-divergence constraint.

A preference pair contains the same prompt and two candidate responses. This abbreviated row shows its fields; real labels need complete responses and a reason to prefer one:

{
    "prompt": "Explain quantum computing",
    "chosen": "Quantum computing uses qubits...",   # Preferred response
    "rejected": "Well, it's complicated..."        # Non-preferred response
}

What changes operationally:

  • Simpler code path (no separate reward model, no RL loop).
  • Training on saved preference pairs rather than generating new responses for reward scoring during each update.
  • A fixed reference model, or its saved log probabilities for the training responses, in the standard formulation.

DPO is easier to prototype than a full PPO pipeline, but it is not an automatic quality upgrade. Results depend on the starting policy, pair quality, loss settings, length effects, and evaluation protocol. Compare it with an SFT checkpoint on the same held-out preference and task suites.

ORPO

ORPO (Odds-Ratio Preference Optimization) combines the SFT negative-log-likelihood loss with an odds-ratio penalty on rejected responses. It removes the separate reference model and can combine task learning and preference optimization in one run.

How it works: ORPO uses a combined loss that does two things at once:

  1. Maximizes the likelihood of the chosen response (learning the task).
  2. Penalizes the rejected response with an odds-ratio term (learning preferences).

Hyperparameters worth knowing (TRL 1.12.0 API):

# API shown in TRL 1.12.0 documentation
from trl.experimental.orpo import ORPOConfig

config = ORPOConfig(
    learning_rate=8e-6,  # Very low, as recommended by the ORPO paper
    beta=0.1,            # Controls strength of preference penalty
    # ... other params
)
  • Learning rate: the paper used low rates in its experiments; tune against your model, batch, and data rather than copying one value as a rule.
  • Beta: controls the preference term relative to the SFT term.

The trade-off:

  • One training stage instead of two.
  • No reward model.
  • No reference-model forward pass.
  • A coupled run: if task learning or preference behavior regresses, there is no intermediate SFT checkpoint from the same pipeline to inspect.

Choose through the data and evaluation design:

  • Use DPO when you already have a satisfactory SFT checkpoint and want a simpler offline preference experiment.
  • Test ORPO when a reference-free, single-stage objective fits your data and operational constraints.
  • Use PPO-based RLHF when online sampling against an explicit learned reward is part of the requirement and you can monitor reward exploitation.

None is a default across tasks. Keep an SFT-only baseline and report both task metrics and preference metrics.

Fine-tuning frameworks

Frameworks overlap and change quickly. Pick by the execution path you must support, pin versions, and keep the training configuration portable enough to reproduce outside a notebook.

Unsloth — speed and memory efficiency

Unsloth integrates with Hugging Face trl and transformers and provides optimized kernels, checkpointing, and quantized fine-tuning paths for supported models.

  • Custom Triton GPU kernels for attention, RoPE, and cross-entropy that skip PyTorch overhead.
  • Memory-efficient backprop that recomputes activations during the backward pass instead of holding them in memory.
  • Fused operations that collapse multiple steps (layer norm + linear, and similar) into single GPU calls.
  • 4-bit quantization integrated directly into the QLoRA path with optimized dequantization.

[!IMPORTANT] Import order matters Follow the import order in the Unsloth example for the version you pin. Unsloth applies patches during import, so importing it before trl and transformers avoids missing optimizations or version-specific errors.

# Correct order
from unsloth import FastLanguageModel  # Must be first!
from trl import SFTTrainer
from transformers import TrainingArguments

# Avoid this order with Unsloth's patched path
from trl import SFTTrainer
from unsloth import FastLanguageModel

Best for: single-GPU training, prototyping, Colab notebooks, anyone watching the GPU bill.

Published speed and memory numbers vary by model, sequence length, batch, precision, and hardware. Benchmark tokens per second and peak memory on your own run instead of treating a headline ratio as a framework property.

Practical demo: fine-tuning with Unsloth

Companion configuration

The companion’s config.py selects the model, dataset, and LoRA settings:

# Model & Dataset
MODEL_NAME = "nvidia/Llama-3.1-Nemotron-Nano-4B-v1.1"  # 4B params, 128K context
DATASET_NAME = "glaiveai/glaive-function-calling-v2"   # 113K examples

# LoRA Configuration
LORA_R = 16        # Adapter capacity; tune against held-out results
LORA_ALPHA = 32    # Update scaling; alpha/r is the classic LoRA scale
MAX_SEQ_LENGTH = 4096

# Candidate modules for this Llama-family model
LORA_TARGET_MODULES = [
    "q_proj", "k_proj", "v_proj", "o_proj",
    "gate_proj", "up_proj", "down_proj",
]

[!NOTE] The alpha-to-rank ratio alpha/r scales the classic LoRA update. alpha = 2r is a common starting heuristic in some tool documentation, not a stability guarantee. Sweep rank, alpha, learning rate, and target modules only after the data and baseline are fixed.

Proposed TRL training configuration

This is a schematic configuration, not code shipped by the companion. Supply train_dataset and eval_dataset as Hugging Face datasets with messages and, for tool examples, tools columns. Produce them from a versioned source/group split as described in Stage 1. Pin compatible Unsloth, TRL, Transformers, and model revisions; the API shape follows TRL 1.12.0.

)

# Prerequisite: supply the prepared datasets described above.

# Train with the current TRL configuration surface.
trainer = SFTTrainer(
    model=model,
    processing_class=tokenizer,
    train_dataset=train_dataset,
    eval_dataset=eval_dataset,
    args=SFTConfig(
        output_dir="outputs/proposed-nemotron-run",
        max_length=4096,
        packing=False,
        assistant_only_loss=False,  # Full-sequence targets; inspect before changing
        eval_strategy="epoch",
        per_device_train_batch_size=2,
        gradient_accumulation_steps=4,
        learning_rate=2e-4,
        num_train_epochs=3,
        bf16=True,  # Requires BF16-capable hardware
    ),
)
trainer.train()
trainer.save_model("outputs/proposed-nemotron-adapter")
tokenizer.save_pretrained("outputs/proposed-nemotron-adapter")

Stage 5: Evaluation

Byte says

If the same support ticket appears in training and evaluation, a higher score can reward recall of that ticket. Split by ticket before making rows or rewrites.

Fix the test cases, scoring rules, and passing thresholds before the first run. At minimum, compare the tuned checkpoint with the exact untuned base under the same prompt, decoding settings, and tool environment. Report aggregate quality only after checking the failure slices the project was meant to improve.

Track four groups:

  1. Target task: exact match, execution success, human rubric, or another outcome tied to the use case.
  2. Regression: general abilities and previously supported task slices that adaptation could damage.
  3. Safety and policy: refusals, data leakage, prompt injection, or domain-specific constraints.
  4. Operations: latency, throughput, memory, artifact size, and cost at the intended serving configuration.

Automated benchmarks

Use lm-evaluation-harness to check relevant standardized tasks alongside your product tests. This command requires a merged Hugging Face checkpoint. Its example path is the legacy companion’s merged output from Stage 6; it does not load the adapter saved by the proposed configuration above. Substitute the merged checkpoint you intend to evaluate:

lm_eval --model hf \
    --model_args pretrained=./outputs/unsloth-nemotron-function-calling-merged \
    --tasks hellaswag,arc_easy,mmlu \
    --batch_size 8

LLM-as-judge

For subjective quality, a larger model can assist with scoring, but calibrate it against human-reviewed examples and keep the candidate identity hidden:

judge_prompt = """
Rate this response from 1-5 on:
- Relevance
- Accuracy
- Formatting

Response: {model_output}
Expected: {ground_truth}
"""

Domain-specific evaluation

Hold out real examples by source, user, document, or time so near-duplicates cannot leak across the split. For function calling, validate the full trajectory: tool selection, arguments, execution result, recovery, and final response. Report confidence intervals or paired win/loss counts when the sample is small, and inspect every regression in a critical slice.

Stage 6: Deployment and output formats

Choose the artifact based on the serving engine and rollback plan, not only file size. These CLI examples refer to the legacy companion, not the proposed TRL excerpt. Its default adapter directory is outputs/unsloth-nemotron-function-calling, with -merged and -gguf directories for exports. Each CLI invocation trains again; it is not an export-only command. For a real release, export the selected evaluated checkpoint rather than comparing artifacts from separate retraining runs.

1. LoRA adapter

uv run finetune  # Default adapter directory shown below
  • Size: proportional to targeted modules, rank, layers, and dtype; often far smaller than the base.
  • Best for: development, versioned task adapters, and engines that support LoRA directly.
  • Bonus: you can swap adapters without re-downloading the base model.

2. Merged model

uv run finetune --merge  # Creates a standalone full model
  • Size: approximately the full base checkpoint at the chosen output precision.
  • Best for: engines or distribution paths that do not support the adapter separately.
  • Trade-off: larger artifact and slower rollout; simpler single-model loading.

3. GGUF format

uv run finetune --gguf q4_k_m  # File size and name depend on the exporter
  • Size: model-dependent; roughly four-bit weights plus metadata for Q4 variants.
  • Best for: CPU inference, Ollama, llama.cpp, edge deployment.
  • Options: q4_k_m (smaller), q5_k_m (more weight fidelity), q8_0 (larger and higher fidelity). Measure the task impact after conversion.

Stage 7: Serving and monitoring

With vLLM

This serving sketch assumes the proposed adapter has passed task evaluation and was trained with a Llama 3.1-compatible tool template. Save that exact reviewed template as serving-chat-template.jinja. The legacy ChatML-formatted adapter is not established as compatible with this parser/template pair. Verify one complete tool trajectory before exposing the endpoint.

# Serve the base and expose a PEFT adapter as a model name. This parser and
# template pair is for a Llama 3.1-compatible function-calling adapter.
vllm serve nvidia/Llama-3.1-Nemotron-Nano-4B-v1.1 \
    --enable-lora \
    --lora-modules function-calling=./outputs/proposed-nemotron-adapter \
    --enable-auto-tool-choice \
    --tool-call-parser llama3_json \
    --chat-template ./serving-chat-template.jinja \
    --host 0.0.0.0 \
    --port 8000 \
    --max-model-len 4096

This deliberately minimal flight schema tests argument generation through the OpenAI-compatible API. It asks for a proposed book_flight call with a destination; it does not execute a booking. Inspect response.choices[0].message.tool_calls for the function name and JSON arguments. For this input, the intended result is book_flight with {"destination": "Tokyo"}. Because tool choice is automatic, also check whether the model returned a call at all:

from openai import OpenAI

client = OpenAI(base_url="http://localhost:8000/v1", api_key="dummy")
response = client.chat.completions.create(
    model="function-calling",
    messages=[{"role": "user", "content": "Book a flight to Tokyo"}],
    tools=[
        {
            "type": "function",
            "function": {
                "name": "book_flight",
                "description": "Book a flight to a city.",
                "strict": True,
                "parameters": {
                    "type": "object",
                    "properties": {
                        "destination": {"type": "string"},
                    },
                    "required": ["destination"],
                    "additionalProperties": False,
                },
            },
        }
    ],
    tool_choice="auto",
)

vLLM’s tool-calling guide requires auto tool choice and a parser matched to the model. Supply a compatible chat template if the tokenizer configuration lacks one. With tool_choice="auto", constrained arguments also require strict: true on at least one function and a strict-compatible parameters schema. The server’s strict-tool-calling setting must be enabled (the documented default). Without that opt-in, vLLM extracts calls from raw text, so the arguments may be malformed or violate the schema.

With Ollama (local)

Inspect the actual -gguf export directory and substitute the emitted filename for MODEL_FILE.gguf below; Unsloth versions can name files differently. A GGUF file alone does not establish correct chat/tool formatting in Ollama or llama.cpp. Match the trained template and test the imported artifact.

# Create Modelfile
echo 'FROM ./outputs/unsloth-nemotron-function-calling-gguf/MODEL_FILE.gguf' > Modelfile

# Import to Ollama
ollama create my-function-model -f Modelfile

# Run
ollama run my-function-model

With llama.cpp (CPU)

Using the same GGUF export and filename substitution, this command checks a plain-text response. It does not test a complete tool call:

./llama-cli -m ./outputs/unsloth-nemotron-function-calling-gguf/MODEL_FILE.gguf \
    -p "What's the weather in Tokyo?" \
    --ctx-size 4096

Monitor the released model

The lifecycle does not stop at a healthy training loss. Record the base-model revision, tokenizer and chat template, adapter hash, dataset version, training configuration, and evaluation report as one release unit. In production, monitor task success, invalid outputs, policy failures, latency, and input drift by the same slices used offline. Keep the previous artifact loadable and define a rollback threshold before launch.

Your next test

Before a full run, inspect one serialized conversation and its loss targets, then complete a maximum-length forward/backward step. Save that configuration with the dataset split and baseline report. If a tool schema is missing, preserve it in the training row. If an answer is truncated, adjust the sequence length and formatting so the full answer survives. Resolve those problems before adding epochs.
