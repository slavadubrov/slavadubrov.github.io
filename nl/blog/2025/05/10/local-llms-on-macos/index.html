Lokale LLM’s op macOS: Ollama, LM Studio, llama.cpp, MLX en Apple Silicon

Veel alledaagse prompts hebben geen externe API nodig. Apple Silicon kan bruikbare taalmodellen lokaal uitvoeren omdat de CPU en GPU één gecentraliseerde geheugenvoorraad delen, hoewel het modelbestand slechts een deel van dit geheugenbudget vormt.

De belangrijkste keuze in deze gids is het hulpmiddel rondom het model. Ollama, LM Studio, llama.cpp en MLX-LM overlappen elkaar, maar ze bieden verschillende niveaus van controle: een beheerde lokale dienst, desktoponderzoek, directe uitvoering van GGUF-bestanden, of Apple-gebaseerd Python. Kies eerst op basis van de kwaliteit van het resultaat voor het model, en kies vervolgens het hulpmiddel dat past bij het gewenste interface en de benodigde artefacten.

Kort samengevat: Gebruik Ollama voor een beheerde lokale dienst, LM Studio voor het visualiseren van modellen op de desktop en hun lokale APIs, llama.cpp voor directe controle over de uitvoering van GGUF-bestanden, en MLX-LM voor experimenten met Apple-gebaseerd Python. Geen enkel hulpmiddel is altijd het snelst. Test de exacte modelversie, quantisatie, contextgrootte en werklast in combinatie met het beschikbare geheugen.

Begin met een geheugenbegrenzing

De ruwe grootte van gequantiseerde gewichten is slechts het eerste element:

peak memory ≈ model weights
            + KV cache
            + runtime workspace
            + multimodal components
            + application and OS memory

De contextlengte, type van het cachegeheugen, aantal gelijktijdige verzoeken en de modelarchitectuur beïnvloeden het eindresultaat. Zelfs een standaard vierbit-model van 7 of 8 miljard parameters kan op een Mac met 8 GB geheugen onhandig werken, omdat het besturingssysteem niet al het beschikbare geheugen aan de applicatie kan toekennen.

Gebruik tijdens het testen Activity Monitor of de eigen metrics van de applicatie. Houd voldoende ruimte over om geheugenproblemen en swappen te voorkomen; een model dat wel wordt geladen maar het systeem dwingt tot continu swappen, is niet geschikt voor interactief gebruik.

Onthoud ook dat lokale inferentie verschilt van offline werking. Prompts kunnen op de machine blijven terwijl de applicatie nog steeds verbinding maakt met het netwerk voor het downloaden van modellen, updates of optionele functies. Laad eerst de artefacten naar de machine, sluit daarna het netwerk af en controleer het workflow als offline werking vereist is.

Ollama: beheerde lokale dienst

Ollama beheert het downloaden van modellen, templates, het levenscyclusproces en een localhost-API. Het is nuttig wanneer de applicatiecode moet reageren op een stabiele lokale dienst in plaats van op eigen inferentiefuncties.

ollama pull <model>
ollama run <model>

curl http://localhost:11434/api/chat \
    -H 'Content-Type: application/json' \
    -d '{
      "model": "<model>",
      "messages": [{"role": "user", "content": "Explain unified memory."}],
      "stream": false
    }'

Controleer het modelmanifest en de contextconfiguratie in plaats van te veronderstellen dat een korte bibliotheeknaam een onveranderlijk checkpoint aangeeft. Noteer of pin het exacte artefact voor evaluaties.

Ollama offert enige lage niveau zichtbaarheid op voor gemak in het levenscyclusbeheer. Gebruik llama.cpp of een andere runtime wanneer je rechtstreeks controle wilt uitoefenen op een GGUF-bestand, chattemplate, cacheinstellingen of nieuwe backendfuncties.

LM Studio: desktoponderzoek en lokale APIs

LM Studio is handig wanneer modelontdekking, configuratie van laadprocessen, inspectie van chats en gelijktijdige menselijke evaluaties onderdeel moeten zijn van één desktopworkflow. De server ondersteunt native SDK’s en compatibiliteitsendpunten.

Het huidige gebruik van het Python SDK ziet er als volgt uit:

import lmstudio as lms


with lms.Client() as client:
    model = client.llm.model("<downloaded-model-key>")
    response = model.respond("Write one sentence about local inference.")
    print(response)

Start de lokale API via de Developer-tab of met:

lms server start

LM Studio kan draaien op localhost of een lokale netwerk en ondersteunt API-tokens. Houd het op loopback tenzij remote toegang expliciet gewenst is; netwerkbinding zorgt ervoor dat een privé desktopmodel verandert in een dienst die authenticatie, firewallbeleid en veilige toolconfiguratie vereist.

llama.cpp: directe GGUF-executie

llama.cpp is de referentieoptie wanneer het artefact in GGUF-formaat is en je de runtimegrenzen rechtstreeks wilt zien. Het ondersteunt Apple Metal naast CPU en andere hardwarebackends.

brew install llama.cpp

# Download through the Hugging Face integration and select a quantization.
llama-cli -hf <publisher>/<gguf-repository>:Q4_K_M

# Or start an OpenAI-compatible local server.
llama-server -hf <publisher>/<gguf-repository>:Q4_K_M

De huidige -hf-route in het repository kan, indien beschikbaar, een overeenkomstige multimodale projector downloaden. Modelondersteuning, templates en CLI-functies veranderen snel; pin dus een bekende build en bewaar de startopdracht samen met de evaluatieregistratie.

Kies voor llama.cpp wanneer directe controle het doel is, niet omdat “lage niveau” automatisch sneller betekent. Een beheerde tool kan goede standaardinstellingen bieden; directe opties kunnen juist de prestaties verslechteren.

MLX-LM: Apple-native Python-werk

MLX-LM is gebaseerd op Apple’s MLX-arrayframework. Het ondersteunt generatie, chat, conversie, kwantisatie en parameter-efficiënt fine-tuning voor compatibele modellen.

uv add mlx-lm
uv run mlx_lm.generate \
    --model mlx-community/<compatible-model> \
    --prompt "Explain Metal acceleration in one paragraph."

Python geeft het model en de tokenizer rechtstreeks weer:

from mlx_lm import generate, load


model, tokenizer = load("mlx-community/<compatible-model>")
messages = [{"role": "user", "content": "Give one local-LLM benchmark rule."}]
prompt = tokenizer.apply_chat_template(
    messages,
    tokenize=False,
    add_generation_prompt=True,
)
print(generate(model, tokenizer, prompt=prompt, max_tokens=80))

De HTTP-server van MLX-LM is gedocumenteerd als een ontwikkelingsserver met basisbeveiligingscontroles, geen productiedienst. Gebruik hem voor lokale experimenten of plaatst een geverifieerde applicatieinterface ervoor.

Controlelijst voor veiligheid en privacy

  1. Koppel API’s aan loopback, tenzij netwerktoegang vereist is.
  2. Voeg authenticatie toe voordat het netwerk wordt geexposeerd.
  3. Behandel modelbestanden als artefacten van derden; noteer bron, versie, licentie en hash.
  4. Vermijd het uitvoeren van onbeoordeeld, aangepast modelcode.
  5. Controleer of optionele functies voor documenten, hulpmiddelen, updates of analyses netwerkoproepen maken.
  6. Ga er niet van uit dat lokaal genereren de opgehaalde documenten, logs of bijwerkingen van hulpmiddelen veilig maakt.

Conclusie

De beste keuze is niet “het beste Mac LLM-hulpprogramma”. Het gaat om de kleinste combinatie van componenten die voldoet aan de controlebehoeften van je werkflow. Ollama beheert een dienst, LM Studio beheert het desktoponderzoek, llama.cpp maakt GGUF-executie mogelijk, en MLX-LM biedt Apple-natieve Python-functionaliteiten.

Geef elke kandidaat dezelfde taak, context en geheugenlimiet. Het resultaat zal betrouwbaarder zijn dan anekdotes over hardware of statische sterrenratings – en gemakkelijk te herzien wanneer de hulpmiddelen veranderen.
