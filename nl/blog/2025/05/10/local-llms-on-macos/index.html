Lokale LLMs op macOS: Ollama, LM Studio, MLX, llama.cpp

Viacheslav Dubrov

2025-05-10 · Bijgewerkt 2026-08-10 · 6 min · Modelengineering · Ontwikkelaarstools

Automatische vertaling Dit artikel is automatisch vertaald vanuit de oorspronkelijke Engelse versie.

Veel alledaagse prompts hebben geen remote API nodig. Apple Silicon kan bruikbare taalmodellen lokaal draaien omdat de CPU en GPU één unified memory pool delen. Het modelbestand is echter slechts een deel van het geheug budget.

Deze handleiding is bedoeld voor engineers die een lokale LLM-workflow op een Apple Silicon Mac kiezen. Aan het einde kun je een tool selecteren en een eerlijke, memory-aware benchmark uitvoeren voor je beoogde workload.

De belangrijkste keuze in deze handleiding is de tool rond het model. Ollama, LM Studio, llama.cpp en MLX-LM overlappen qua mogelijkheden, maar bieden verschillende niveaus van controle: een managed local service, desktopverkenning, directe GGUF-executie of Apple-native Python. Kies eerst het model op basis van task quality en kies daarna de tool op basis van de interface en het artifact dat je nodig hebt.

TL;DR. Gebruik Ollama voor een managed local service, LM Studio voor desktopverkenning van modellen en de lokale APIs, llama.cpp voor directe controle over GGUF-executie en MLX-LM voor Apple-native Python-experimenten. Geen van deze tools is universeel het snelst. Benchmark het exacte model, de quantization, de context en de workload, met voldoende geheugenruimte.

Begin met een memory envelope

De ruwe grootte van quantized weights is slechts de eerste term:

peak memory ≈ model weights
            + KV cache
            + runtime workspace
            + multimodal components
            + application and OS memory

Context length, cache dtype, parallel requests en modelarchitectuur veranderen het resultaat. Een nominaal vier-bit 7B- of 8B-model kan op een Mac met 8 GB nog steeds problematisch zijn, omdat het besturingssysteem niet al het geïnstalleerde geheugen aan de runtime kan geven.

Gebruik Activity Monitor of de eigen metrics van de runtime tijdens het testen. Apple bepaalt memory pressure aan de hand van vrij geheugen, swap rate, wired memory en cached files. Houd voldoende headroom aan om langdurige swap te voorkomen; een model dat wel laadt maar het systeem in memory pressure duwt, is geen goede interactieve fit.

Maak ook onderscheid tussen lokale inference en offline operation. Prompts kunnen op de machine blijven terwijl de applicatie nog steeds het netwerk gebruikt voor modeldownloads, updates of optionele features. Ollama documenteert lokale execution, modeldownloads en optionele cloudfeatures afzonderlijk in zijn FAQ. Behandel offline operation als een workflowvereiste die je per applicatie moet verifiëren: download artifacts vooraf, verbreek de netwerkverbinding en test de volledige workflow.

Ollama: managed local service

Ollama beheert modeldownloads, templates, de process lifecycle en een localhost API. Het is nuttig wanneer application code zich op een stabiele lokale service moet richten in plaats van zelf inference-flags te beheren.

MODEL=llama3.2
ollama pull "$MODEL"
ollama run "$MODEL" "Explain unified memory."

curl http://localhost:11434/api/chat \
    -H 'Content-Type: application/json' \
    -d '{
      "model": "'"$MODEL"'",
      "messages": [{"role": "user", "content": "Explain unified memory."}],
      "stream": false
    }'

Inspecteer het modelmanifest en de contextconfiguratie in plaats van aan te nemen dat een korte librarynaam een immutable checkpoint identificeert. Pin of registreer het exacte artifact voor evals.

Ollama ruilt een deel van de low-level visibility in voor gemak rond de lifecycle. Stap over op llama.cpp of een andere runtime wanneer je directe controle nodig hebt over een GGUF-file, chat template, cache setting of nieuwe backendfeature.

LM Studio: desktopverkenning en lokale APIs

LM Studio is nuttig wanneer model discovery, load configuration, chat inspection en side-by-side human evaluation in één workflow thuishoren. Het biedt inmiddels native Python- en TypeScript-SDKs, OpenAI-compatible endpoints, structured output, tool use en een headless daemon, en is dus niet langer alleen een desktop-GUI.

De huidige Python SDK maakt verbinding met een model dat je al hebt gedownload:

import lmstudio as lms

MODEL_KEY = "ibm/granite-4-micro"

with lms.Client() as client:
    model = client.llm.model(MODEL_KEY)
    response = model.respond("Write one sentence about local inference.")
    print(response)

Start de lokale API vanuit het tabblad Developer of met:

lms server start

LM Studio kan op localhost of een lokaal netwerk serven en ondersteunt API-tokens in zijn API authentication settings. Houd de service op loopback tenzij remote access bewust is ingeschakeld. Als je de service op een LAN exposeert, vereist dan de gedocumenteerde API-tokenoptie, pas een host-firewallregel toe en controleer de toegang tot tools en integraties.

llama.cpp: directe GGUF-executie

llama.cpp is de referentieroute wanneer het artifact GGUF is en je de runtime boundary direct wilt zien. Het ondersteunt Apple Metal naast CPU- en andere hardware-backends.

brew install llama.cpp

# Download through the Hugging Face integration and select a quantization.
MODEL_REPO=ggml-org/gemma-3-1b-it-GGUF
QUANT=Q4_K_M
llama-cli -hf "$MODEL_REPO:$QUANT"

# Or start an OpenAI-compatible local server.
llama-server -hf "$MODEL_REPO:$QUANT"

Het huidige -hf-pad van de repository kan, indien beschikbaar, een bijpassende multimodal projector downloaden. Modelondersteuning, templates en CLI-flags veranderen snel. Pin daarom een bekende build en bewaar de launch command bij het evaluation record.

Kies llama.cpp wanneer directe controle het doel is, niet omdat “lower-level” automatisch sneller betekent. Een managed tool kan goede defaults kiezen; directe flags kunnen de performance ook verslechteren.

MLX-LM: Apple-native Python-ontwikkeling

MLX-LM bouwt voort op Apple’s MLX array framework. Het ondersteunt generation, chat, conversie, quantization en parameter-efficient fine-tuning voor compatibele modellen.

MODEL=mlx-community/Llama-3.2-3B-Instruct-4bit
uv add mlx-lm
uv run mlx_lm.generate \
    --model "$MODEL" \
    --prompt "Explain Metal acceleration in one paragraph."

Python geeft direct toegang tot het model en de tokenizer:

from mlx_lm import generate, load

MODEL = "mlx-community/Llama-3.2-3B-Instruct-4bit"

model, tokenizer = load(MODEL)
messages = [{"role": "user", "content": "Give one local-LLM benchmark rule."}]
prompt = tokenizer.apply_chat_template(
    messages,
    tokenize=False,
    add_generation_prompt=True,
)
print(generate(model, tokenizer, prompt=prompt, max_tokens=80))

De HTTP-server van MLX-LM wordt gedocumenteerd als een development server met basic security checks, niet als een production service. Gebruik deze voor lokale experimenten of plaats er een gecontroleerde application boundary voor.

Een eerlijke benchmark kost minder tijd dan een slechte download

Test dezelfde checkpoint family en, waar de formats dat toestaan, vergelijkbare quantization. Gebruik een kleine promptset met:

  • één korte interactieve prompt
  • één lange prompt dicht bij de beoogde context
  • structured output of tool calls als de applicatie die nodig heeft
  • een representatieve generation length
  • één herhaald request om cold load van warm inference te onderscheiden

Vergelijk niet het 4-bit-model van de ene tool met het full-precision-model van een andere tool en schrijf het verschil vervolgens toe aan de runtime.

Checklist voor security en privacy

  1. Bind APIs aan loopback tenzij network access vereist is.
  2. Als LAN access vereist is, gebruik dan een host-firewall en óf de gedocumenteerde authentication van de tool óf een geauthenticeerde reverse proxy vóór de service. Ondersteuning voor API-tokens is tool-specifiek: LM Studio documenteert API-tokens, terwijl de gedocumenteerde exposure path van Ollama host binding en proxying gebruikt.
  3. Behandel modelfiles als third-party artifacts; registreer source, revision, license en hash.
  4. Voer geen niet-gecontroleerde custom model code uit.
  5. Controleer of optionele document-, tool-, update- of analyticsfeatures network calls uitvoeren.
  6. Ga er niet van uit dat lokale generation retrieved documents, logs of tool side effects veilig maakt.

Belangrijkste conclusies

  1. Kies eerst de workflow boundary: managed service, desktop- en headless development, directe GGUF-control of Apple-native Python.
  2. Zowel Ollama als LM Studio bieden lokale APIs. Vergelijk lifecycle control, SDKs, structured output, tools en runtime visibility.
  3. Model weights vormen slechts een deel van het geheugbudget. Houd rekening met KV cache, workspace, multimodal components, de applicatie en de headroom die macOS nodig heeft.
  4. Lokale inference is niet automatisch offline of privé. Verifieer network calls, binding, authentication, artifacts, logs en tool side effects.
  5. Benchmark dezelfde task, checkpoint family, context en vergelijkbare quantization voordat je een resultaat aan de runtime toeschrijft.
