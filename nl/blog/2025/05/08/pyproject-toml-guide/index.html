pyproject.toml Gids: Python-pakketbouw, afhankelijkheden en configuratie van hulpprogramma’s

Oudere Python-projecten verspreiden de configuratie vaak over setup.py, setup.cfg, requirements-bestanden, MANIFEST.in en aparte bestanden voor ontwikkelingstools. pyproject.toml biedt een centrale plek voor al deze elementen, hoewel het geen vervanging is voor alle projectbestanden of ervoor zorgt dat elke sectie onderdeel wordt van één standaard.

Deze gids neemt je mee door het bestand, van de bouwconfiguratie tot de projectmetadata en de instellingen van de hulpprogramma’s. Om het begrijpelijk te houden, is het handig om vier verantwoordelijke gebieden te onderscheiden: wat het project bouwt, wat het project publiceert, wat bijdragers lokaal nodig hebben, en wat individuele tools configureren.

Kort samengevat: Gebruik [build-system] voor de backend die een distributie bouwt, [project] voor gepubliceerde metadata en runtime-afhankelijkheden, [dependency-groups] voor ongepubliceerde ontwikkelomgevingen, en [tool.*] alleen wanneer de documentatie van dat hulpprogramma dat vereist. Een afhankelijkheidsverklaring is geen lockfile.

Eén bestand, vier verantwoordelijken

Drie pakketbouwstandaarden hebben de kernstructuur vastgesteld:

  • PEP 518 definieert de vereisten voor het bouwsysteem.
  • PEP 621 definieert de projectmetadata.
  • PEP 735 definieert ongepubliceerde groepen van afhankelijkheden.

Auteurs van hulpprogramma’s kunnen ook een eigen namespace onder [tool] definiëren. Dit gebied is conventioneel, maar niet universeel: elk hulpprogramma bepaalt zelf zijn eigen sleutels en gedrag.

Hier is een kleine geïmpakte bibliotheek:

[build-system]
requires = ["hatchling>=1.26"]
build-backend = "hatchling.build"

[project]
name = "weather-client"
version = "0.1.0"
description = "A small weather API client"
readme = "README.md"
requires-python = ">=3.11"
dependencies = [
  "httpx>=0.27",
]

[project.optional-dependencies]
cli = ["rich>=13"]

[project.scripts]
weather = "weather_client.cli:main"

[dependency-groups]
test = ["pytest>=8", "pytest-cov>=5"]
lint = ["ruff>=0.12"]

[tool.pytest.ini_options]
testpaths = ["tests"]

[tool.ruff]
line-length = 100
target-version = "py311"

Elke lijst met afhankelijkheden beantwoordt een andere vraag. Deze onderscheiding vormt het hart van het bestand.

[build-system]: hoe bronmateriaal een distributie wordt

Een bouwfrontend zoals python -m build, pip of uv roept een bouwbackend op. De backend bepaalt hoe de bronboom wordt omgezet in een sdist of wheel en welke bestanden daarin terechtkomen.

[build-system]
requires = ["hatchling>=1.26"]
build-backend = "hatchling.build"

requires bevat de afhankelijkheden die nodig zijn om de backend uit te voeren in zijn geïsoleerde bouwomgeving. Dit is niet dezelfde lijst met runtime-afhankelijkheden als voor je pakket.

Declareer een bouwsysteem wanneer het project een distributie genereert of zijn eigen code als pakket moet installeren. Ook niet-pakketprojecten kunnen nog steeds pyproject.toml gebruiken; PEP 735 staat zelfs toe dat een bestand alleen maar groepen van afhankelijkheden bevat. Omgevingsbeheerders behandelen projecten zonder bouwsysteem op verschillende manieren, dus kies dit bewust.

Kies de backend op basis van de bouwvereisten:

  • behoefte aan een pure-Python-opbouw en bestandsselectie
  • gebruik van gecompileerde extensies of externe bouwsystemen
  • vereisten voor dynamische versies of gegenereerde bestanden
  • gewenst editable-install-gedrag
  • volwassenheid van de backend in het release-pipeline

Kopieer de huidige aanbevolen tabel van de backend uit diens documentatie. Voeg wheel niet uit gewoonte toe aan de bouwvereisten; de backend geeft zelf aan wat hij nodig heeft.

[project]: wat metadata-consumenten ontvangen

De [project]-tabel beschrijft de distributie: de naam, versie, Python-compatibiliteit, runtime-afhankelijkheden, entry points en andere indexmetadata.

[project]
name = "weather-client"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = ["httpx>=0.27"]

De afhankelijkheidsspecificaties vormen beperkingen voor een resolver, en geen momentopname van één omgeving. Ze worden onderdeel van de metadata in wheel- en sdist-bestanden, zodat downstream-installers ze kunnen combineren met vereisten uit andere pakketten.

Extras vormen een publieke installatieinterface

[project.optional-dependencies] definieert de extras die gebruikers kunnen aanvragen:

[project.optional-dependencies]
cli = ["rich>=13"]
postgres = ["psycopg[binary]>=3.2"]

Een gebruiker kan weather-client[cli] installeren. Omdat de namen en vereisten van extras gepubliceerd zijn, moeten ze worden beschouwd als productfuncties. Gebruik geen extra met de naam dev enkel om alle hulpprogramma’s voor bijdragers op te slaan.

Entrypunten verbinden geïnstalleerde commando’s met Python

[project.scripts]
weather = "weather_client.cli:main"

Na installatie van de distributie exposeert de omgeving weather, dat weather_client.cli:main importeert en oproept. Test het commando vanuit een gebouwde wheel, en niet alleen vanuit de wortelpath van het repository; de wheel is wat gebruikers daadwerkelijk ontvangen.

[dependency-groups]: lokale, ongepubliceerde omgevingen

PEP 735 beschrijft afhankelijkheidsgroepen voor ontwikkelomgevingen of omgevingen zonder pakketstructuur, zonder deze te publiceren als pakketmetadata.

[dependency-groups]
test = ["pytest>=8", "pytest-cov>=5"]
lint = ["ruff>=0.12"]
dev = [
  { include-group = "test" },
  { include-group = "lint" },
]

Dit vormt de juiste grens voor tests, linters, documentatiegeneratoren en soortgelijke hulpprogramma’s voor bijdragers. Het is ook nuttig voor applicaties of notebooks die geen distributie genereren.

Afhankelijkheidsgroepen zijn gestandaardiseerde gegevens, maar de installatieinterfaces verschillen nog steeds. Controleer hoe de gekozen omgevingsbeheerder ze installeert, lockt en oplost. PEP 735 definieert geen universele command-line-interface.

[tool.*]: configuratie eigendom van één hulpprogramma

Tool-tabellen delen geen schema:

[tool.pytest.ini_options]
addopts = "-ra"
testpaths = ["tests"]

[tool.ruff]
line-length = 100

Gebruik een [tool.*]-tabel alleen als het hulpprogramma dit specificeert. Sommige instellingen moeten nog steeds in hun eigen bestanden blijven, omdat een ander ecosysteem ze nodig heeft, het bestand een andere vorm vereist, of de configuratie op zich duidelijker is. pyproject.toml fungeert als coördinatiepunt, maar is geen verplichting om alles te centraliseren.

Verklaringen, lockbestanden en vereistenbestanden lossen verschillende problemen op

De meest voorkomende oorzaak van verwarring is het beschouwen van elk afhankelijkheidsartefact als een concurrentiebron van waarheid.

ArtefactPrimair doelTypische inhoud
[project.dependencies]Gepubliceerd runtijdcontractDirecte vereisten en compatibele bereiken
[project.optional-dependencies]Gepubliceerde opt-in functiesExtras gericht op gebruikers
[dependency-groups]Ongepubliceerde lokale omgevingenTest-, lint-, documentatie- of applicatiegroepen
LockfileEen opgeloste omgeving reproducerenPrecise versies, bronnen en resolutiemetadata
requirements.txtPip-compatibele installatie-invoerVereisten plus pip-specifieke opties, beperkingen, URLs of hashes

Een bibliotheek publiceert doorgaans compatibele beperkingen en tests voor een specifiek bereik. Een applicatie bewaart meestal het lockfile van de omgevingsbeheerder. Precieze versienummers moeten worden opgenomen in het geïmplementeerde deploy-artefact, en niet zomaar in de publieke metadata van de bibliotheek.

Houd een requirementsbestand aan wanneer integraties de formaten of functies van pip vereisen. Als een door uv beheerd project er eentje nodig heeft, exporteer deze dan uit het lockfile in plaats van twee afzonderlijke dependentiemengsels bij te houden:

uv export --format requirements.txt --output-file requirements.txt

De export vormt een afgeleide compatibiliteitsuitvoer. Het lockfile blijft de bron voor dat werkproces.

Een migratie die het gedrag behoudt

Begin niet met het verwijderen van setup.py of requirements.txt. Classificeer eerst wat elke bestaande bestand doet.

  1. Maak een inventaris van de buildlogica, metadata, runtime-eisen, extra’s, ontwikkelaarsomgevingen, hulinstellingen, pakketgegevens en entry points.
  2. Kies een backend die de huidige bestandsinclusie, gecompileerde artefacten en editabele installaties kan reproduceren.
  3. Verplaats statische, gepubliceerde metadata naar [project]; houd echt dynamische velden expliciet.
  4. Zet alleen requirements voor bijdragers naar [dependency-groups], en niet naar publieke extra’s.
  5. Plaats hulinstellingen alleen wanneer het hulpprogramma equivalente semantiek ondersteunt.
  6. Bouw zowel een sdist als een wheel, controleer hun inhoud en installeer de wheel in een schone omgeving.
  7. Voer de entry points, tests, importcontroles en de daadwerkelijke deploy-path uit.
  8. Verwijder de oude configuratie pas nadat de artefacten en het gedrag overeenkomen.

MANIFEST.in kan nog steeds nodig zijn bij sommige setups van setuptools, en een klein setup.py kan nog geldig zijn voor programmatische buildgedragingen. Modernisering betekent een verschuiving in eigendom, geen wedstrijd om bestanden te verwijderen.

Een huidige uv-workflow

uv onderscheidt applicaties van bibliotheken bij het maken van een project:

# Non-library application template
uv init weather-app

# Packaged library with a src layout and build system
uv init --lib weather-client

uv init genereert de projectbestanden. De eerste projectoperatie, zoals uv run, uv sync of uv lock, maakt indien nodig het lockfile en het persistente .venv aan.

cd weather-client
uv add httpx
uv add --group test pytest pytest-cov
uv run pytest
uv build

uv plaatst momenteel lokale ontwikkelingsvereisten in gestandaardiseerde dependentiegroepen. De ingebouwde uv_build backend is een optie voor pure-Python-projecten; gecompileerde extensies hebben een geschikte alternatief nodig, zoals maturin of scikit-build-core.

Conclusie

pyproject.toml wordt duidelijk wanneer elke tabel één doelgroep heeft. Build-isolatie valt onder [build-system]. Gepubliceerd gedrag behoort tot [project]. Ontwikkelaarsomgevingen zijn voorbehouden aan [dependency-groups]. Hulpprogramma-switches vallen onder het hulpprogramma dat ze definiërt.

Zodra deze grenzen stabiel zijn, wordt het gemakkelijker om bestanden te beoordelen – en migraties vermijden dat package-metadata verward wordt met de geïmplementeerde omgeving van één machine.
