Handleiding voor pyproject.toml: packaging, dependencies en tools

Viacheslav Dubrov

2025-05-08 · Bijgewerkt 2026-07-15 · 5 min · Ontwikkelaarstools

Automatische vertaling Dit artikel is automatisch vertaald vanuit de oorspronkelijke Engelse versie.

Oudere Python-projecten verspreiden configuratie vaak over setup.py, setup.cfg, requirements-bestanden, MANIFEST.in en afzonderlijke bestanden voor development-tools. pyproject.toml biedt deze verantwoordelijkheden een gemeenschappelijke plek, maar vervangt niet elk projectbestand en maakt niet elke sectie onderdeel van één standaard.

Deze handleiding doorloopt het bestand van buildconfiguratie tot projectmetadata en toolinstellingen. Vier eigenaars houden de secties gescheiden: wat het project bouwt, wat het project publiceert, wat contributors lokaal nodig hebben en welke configuratie afzonderlijke tools gebruiken.

TL;DR. Gebruik [build-system] voor de backend die een distributie bouwt, [project] voor gepubliceerde metadata en runtime requirements, [dependency-groups] voor niet-gepubliceerde development environments en [tool.*] alleen wanneer de documentatie van die tool dat voorschrijft. Een dependency-declaratie is geen lockfile.

Eén bestand, vier eigenaars

Drie packaging-standaarden vormen de kernstructuur:

  • PEP 518 definieert build-system requirements.
  • PEP 621 definieert projectmetadata.
  • PEP 735 definieert niet-gepubliceerde dependency groups.

Toolauteurs kunnen ook een namespace onder [tool] claimen. Er is niets gestandaardiseerd aan wat daar staat: elke tool definieert zijn eigen keys en gedrag.

Hier is een kleine packaged library:

[build-system]
requires = ["hatchling>=1.26"]
build-backend = "hatchling.build"

[project]
name = "weather-client"
version = "0.1.0"
description = "A small weather API client"
readme = "README.md"
requires-python = ">=3.11"
dependencies = [
  "httpx>=0.27",
]

[project.optional-dependencies]
cli = ["rich>=13"]

[project.scripts]
weather = "weather_client.cli:main"

[dependency-groups]
test = ["pytest>=8", "pytest-cov>=5"]
lint = ["ruff>=0.12"]

[tool.pytest.ini_options]
testpaths = ["tests"]

[tool.ruff]
line-length = 100
target-version = "py311"

Elke dependency-lijst beantwoordt een andere vraag.

[build-system]: hoe source een distributie wordt

Een build frontend zoals python -m build, pip of uv roept een build backend aan. De backend bepaalt hoe de source tree wordt omgezet in een sdist of wheel en welke bestanden in die artifacts terechtkomen.

[build-system]
requires = ["hatchling>=1.26"]
build-backend = "hatchling.build"

requires bevat dependencies die nodig zijn om de backend in zijn geïsoleerde build environment uit te voeren. Dit is niet de runtime dependency-lijst van je package.

Declareer een build system wanneer het project een distributie produceert of zijn eigen code als package moet installeren. Een non-package project kan nog steeds pyproject.toml gebruiken; PEP 735 staat zelfs een bestand toe dat alleen dependency groups bevat. Environment managers verschillen in hoe ze omgaan met een project zonder build system, dus maak deze keuze bewust.

Kies de backend op basis van de build requirements:

  • pure-Python layout en behoeften rond file selection
  • compiled extensions of externe buildsystems
  • vereisten voor dynamic versioning of gegenereerde bestanden
  • gedrag van editable installs
  • volwassenheid van de backend in de release pipeline

Neem de actuele aanbevolen table van de backend over uit de documentatie. Voeg niet uit gewoonte wheel toe aan build requirements; de backend declareert wat hij nodig heeft.

[project]: metadata die consumers ontvangen

De [project]-table beschrijft de distributie: de naam, versie, Python-compatibiliteit, runtime dependencies, entry points en andere indexmetadata.

[project]
name = "weather-client"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = ["httpx>=0.27"]

De dependency specifiers zijn constraints voor een resolver, geen snapshot van één environment. Ze worden onderdeel van de metadata van wheel en sdist, zodat downstream installers ze kunnen combineren met requirements van andere packages.

Extras zijn een publieke installation interface

[project.optional-dependencies] definieert extras die consumers kunnen opvragen:

[project.optional-dependencies]
cli = ["rich>=13"]
postgres = ["psycopg[binary]>=3.2"]

Een consumer kan weather-client[cli] installeren. Omdat extra-namen en requirements worden gepubliceerd, moet je ze behandelen als product capabilities. Gebruik geen extra met de naam dev alleen om alle contributor-tools in onder te brengen.

Entry points koppelen geïnstalleerde commands aan Python

[project.scripts]
weather = "weather_client.cli:main"

Nadat de distributie is geïnstalleerd, stelt de environment weather beschikbaar, die weather_client.cli:main importeert en aanroept. Test de command vanuit een gebouwde wheel, niet alleen vanuit de repository root; de wheel is wat users ontvangen.

[dependency-groups]: lokale, niet-gepubliceerde environments

Byte says

Ik hield jarenlang elk hulpprogramma voor bijdragers in een dev-extra. Het installeerde prima, dus ik keek nooit verder. De extra stond al die tijd in de metadata van de gepubliceerde wheel, en iedereen kon hem opvragen.

PEP 735 dependency groups beschrijven development- of non-package environments zonder ze als package metadata te publiceren.

[dependency-groups]
test = ["pytest>=8", "pytest-cov>=5"]
lint = ["ruff>=0.12"]
dev = [
  { include-group = "test" },
  { include-group = "lint" },
]

Dit is de juiste grens voor tests, linters, documentation builders en vergelijkbare contributor-tools. Het is ook nuttig voor applications of notebooks die geen distributie bouwen.

Dependency groups zijn gestandaardiseerde data, maar installerinterfaces verschillen nog steeds. Controleer hoe de gekozen environment manager ze installeert, lockt en resolved. PEP 735 definieert geen universele command-line interface.

[tool.*]: configuratie die eigendom is van één tool

Tooltables delen geen schema:

[tool.pytest.ini_options]
addopts = "-ra"
testpaths = ["tests"]

[tool.ruff]
line-length = 100

Gebruik een [tool.*]-table alleen als de tool dit documenteert. Sommige instellingen horen nog steeds in eigen bestanden, omdat een ander ecosysteem ze consumeert, het bestand een ander format nodig heeft of de configuratie op zichzelf duidelijker is. pyproject.toml is een coördinatiepunt. Het vereist niet dat elke instelling wordt gecentraliseerd.

Declaraties, locks en requirements-bestanden lossen verschillende problemen op

Een veelvoorkomende bron van verwarring is dat elke dependency-artifact wordt behandeld als een concurrerende source of truth.

ArtifactPrimair doelTypische inhoud
[project.dependencies]Gepubliceerd runtime-contractDirecte requirements en compatibele ranges
[project.optional-dependencies]Gepubliceerde opt-in capabilitiesConsumergerichte extras
[dependency-groups]Niet-gepubliceerde lokale environmentsTest-, lint-, docs- of application groups
LockfileEen resolved environment reproducerenExacte versies, sources en resolution metadata
requirements.txtpip-compatibele installation inputRequirements plus pip-specifieke opties, constraints, URLs of hashes

Een library publiceert doorgaans compatibele constraints en test tegen een range. Een application commit meestal de lockfile van de environment manager. Exacte pins horen in het resolved deployment-artifact, niet zonder meer in de publieke metadata van een library.

Houd een requirements-bestand aan wanneer een integratie pip’s format of features vereist. Als een uv-managed project er één nodig heeft, exporteer het dan vanuit de lock in plaats van twee onafhankelijke dependency-sets te onderhouden:

uv export --format requirements.txt --output-file requirements.txt

De export is afgeleide compatibiliteitsoutput. De lock blijft de resolved source voor die workflow.

Een migratie die gedrag behoudt

Begin niet met het verwijderen van setup.py of requirements.txt. Classificeer eerst wat elk bestaand bestand doet.

  1. Breng buildlogica, metadata, runtime requirements, extras, developer environments, toolinstellingen, package data en entry points in kaart.
  2. Selecteer een backend die de huidige file inclusion, compiled artifacts en editable installs kan reproduceren.
  3. Verplaats statische gepubliceerde metadata naar [project]; houd echt dynamische velden expliciet.
  4. Verplaats uitsluitend voor contributors bedoelde requirements naar [dependency-groups], niet naar publieke extras.
  5. Verplaats toolinstellingen alleen wanneer de tool equivalente semantics ondersteunt.
  6. Bouw zowel een sdist als een wheel, inspecteer hun inhoud en installeer de wheel in een schone environment.
  7. Voer entry points, tests, import checks en het daadwerkelijke deployment-pad uit.
  8. Verwijder oude configuratie pas nadat de artifacts en het gedrag overeenkomen.

MANIFEST.in kan bij sommige setuptools-layouts nog steeds nodig zijn, en een kleine setup.py kan geldig blijven voor programmatic buildgedrag. Modernisering verplaatst eigenaarschap tussen bestanden. Bestanden verwijderen is niet het doel.

Een actuele uv-workflow

uv maakt bij het aanmaken van een project onderscheid tussen applications en libraries:

# Non-library application template
uv init weather-app

# Packaged library with a src layout and build system
uv init --lib weather-client

uv init maakt projectbestanden aan. De eerste projectoperatie, zoals uv run, uv sync of uv lock, maakt indien nodig de lockfile en persistente .venv aan.

cd weather-client
uv add httpx
uv add --group test pytest pytest-cov
uv run pytest
uv build

uv plaatst lokale development requirements momenteel in gestandaardiseerde dependency groups. De native uv_build-backend is één optie voor pure-Python-projecten; voor compiled extensions is een geschikt alternatief nodig, zoals maturin of scikit-build-core. Zie uv’s projectconfiguratiedocumentatie voor de actuele backendinstellingen.

Conclusie

pyproject.toml is duidelijk wanneer elke table één doelgroep heeft. Build isolation hoort in [build-system] en gepubliceerd gedrag in [project]. Contributor-environments horen in [dependency-groups]. Tool switches horen bij de tool die ze definieert.

Zodra deze grenzen stabiel zijn, wordt het bestand eenvoudiger te reviewen en verwarren migraties package metadata niet langer met de resolved environment van één machine.
