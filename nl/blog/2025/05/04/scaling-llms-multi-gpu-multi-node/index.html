LLMs schalen met multi-GPU- en multi-node-parallelisme

Viacheslav Dubrov

2025-05-04 · Bijgewerkt 2026-07-15 · 9 min · Modelengineering · AI-infrastructuur

Automatische vertaling Dit artikel is automatisch vertaald vanuit de oorspronkelijke Engelse versie.

Workloads met grote modellen gaan om verschillende redenen verder dan één GPU. Een training job kan zonder geheugen komen te zitten door de optimizer state. Een andere kan tegen de geheugengrens aanlopen door activations over lange sequences. Een model dat past, haalt mogelijk nog steeds de throughput-doelstelling niet. Elk probleem vereist een andere partitionering en een ander communication pattern.

Dit is een praktische rondleiding door de belangrijkste parallelismestrategieën en de onderliggende beperkingen, gebaseerd op de Ultra-Scale Playbook van Hugging Face. Het doel is te laten zien wat elke split oplevert, welke data wordt uitgewisseld en wanneer combinaties noodzakelijk worden.

TL;DR. Replicated data parallelism levert training throughput op wanneer één replica past. Fully sharded data parallelism partitioneert model state, maar voegt parameter all-gathers en gradient reduce-scatters toe. Tensor-, pipeline-, context- en expert-parallelisme splitsen respectievelijk layer math, depth, sequence en mixture-of-experts (MoE)-layers. Combineer ze pas nadat je hebt vastgesteld welke memory- of communication constraint bepalend is.

Deze guide gaat ervan uit dat je vertrouwd bent met backpropagation, Transformer-layers en een standaard PyTorch training loop.

Begin met twee memory budgets

Training en inference hebben niet dezelfde footprint.

training peak ≈ parameters
              + gradients
              + optimizer state
              + saved activations
              + temporary buffers
              + communication buffers
              + allocator headroom

inference peak ≈ resident weights
               + key/value (KV) cache
               + runtime workspace
               + communication buffers
               + allocator headroom

Een model met 70 miljard parameters heeft alleen voor BF16 weights al een decimale ondergrens van 140 GB. Dat zegt weinig over training, waarbij gradients, optimizer state, master weights en activations de meeste memory kunnen gebruiken. Ook voor serving is dit geen volledige sizing: daar zijn cache policy, sequence length, batch concurrency en quantization bepalend.

Profile de exacte architecture, precision, sequence length, micro-batch, optimizer, checkpointing policy en runtime. Leg peak allocated en reserved memory, tokens per second, tijd in kernels en tijd die zichtbaar is in collectives vast.

Replicated data parallelism: throughput zonder extra capacity

Replicated data parallelism, meestal distributed data parallel genoemd, houdt op elke rank een volledige training replica bij. De DistributedDataParallel-documentatie van PyTorch beschrijft dit replica-and-gradient-synchronization-model. Elke rank verwerkt een andere micro-batch en gradients worden vóór de optimizer step gesynchroniseerd.

Gebruik dit wanneer de volledige training state met voldoende headroom past en de global batch kan groeien of gradient accumulation kan worden aangepast. De belangrijkste voordelen zijn eenvoudige semantics en een volwassen implementatie die backward computation overlapt met bucketed gradient reduction.

Meer ranks kunnen nadelig zijn wanneer de local batch te klein wordt. Dat geldt ook wanneer het netwerk de all-reduce niet kan verbergen of input delivery stalls veroorzaakt. De gewenste optimization batch schaalt mogelijk niet mee.

Fully sharded data parallelism: state memory inruilen voor collectives

Fully sharded data parallelism slaat parameter-, gradient- en optimizer-shards op over een groep. Het ZeRO-paper beschrijft dit state-sharding pattern en PyTorch’s FSDP2 API implementeert het. De parameters van een layer worden voor de computation geall-gathered en kunnen daarna opnieuw worden geshard. Gradients worden met reduce-scatter teruggestuurd naar de owners.

De huidige PyTorch-documentatie maakt onderscheid tussen de fully_shard API in fully sharded data parallelism version 2 (FSDP2) en de oudere FullyShardedDataParallel wrapper. FSDP2 groepeert communication op basis van de modules waarop fully_shard wordt toegepast en adviseert bottom-up application, zodat communication en computation van layer groups kunnen overlappen.

from torch.distributed.fsdp import fully_shard

# Apply bottom-up: each block becomes a communication group.
for block in model.transformer.blocks:
    fully_shard(block)

# Shard remaining root parameters such as embeddings and output projection.
fully_shard(model)

# Construct the optimizer after parameters have become sharded distributed tensors (DTensors).
optimizer = AdamW(model.parameters(), lr=learning_rate)

Dit is een structurele schets, geen complete launcher. Device meshes, mixed precision, checkpointing, initialization, optimizer state en distributed checkpoints moeten aansluiten op de training stack.

Sharding is aantrekkelijk wanneer model state de bepalende constraint is en layer computation voldoende collective traffic kan verbergen. Het kan een slechte trade-off zijn voor kleine modellen, trage links, kleine layers of layouts waarbij de shard group een verkeerde topology boundary overschrijdt.

Tensor parallelism: layer math partitioneren

Tensor parallelism partitioneert linear algebra binnen een layer. Voorbeelden zijn column-parallel en row-parallel projections. De parallelism guide van NVIDIA documenteert deze layer-level split. Partial results vereisen collectives binnen Transformer-blocks, waardoor latency en bandwidth herhaaldelijk belangrijk zijn tijdens de forward- en backward-pass.

Gebruik dit wanneer een layer of de bijbehorende activations niet past, of wanneer de matmuls groot genoeg zijn om partitioned kernels sneller te laten zijn dan één rank. Map de tensor-parallel group naar het snelste beschikbare communication domain en meet vervolgens. Een hoge tensor-parallel degree kan elke lokale matrix zo klein maken dat de kernel efficiency daalt terwijl de collective overhead toeneemt.

Sequence parallelism wordt vaak gecombineerd met tensor parallelism om replicatie van bepaalde activation work te voorkomen. Het verschilt van context parallelism over de volledige input sequence van het model.

Pipeline parallelism: depth partitioneren en tijd schedulen

Pipeline parallelism plaatst verschillende layer groups op verschillende stages en verstuurt activations ertussen. Micro-batches houden stages gelijktijdig aan het werk. Het GPipe-paper gebruikt deze schedule voor zeer grote neural networks.

Het vermindert de model state per stage en kan, vergeleken met per-layer tensor collectives, de hoeveelheid communication over een tragere boundary verkleinen. De kosten zijn bubbles, activation transfers, stage imbalance, complexere scheduling en moeilijker recovery en checkpointing.

Voor een eenvoudige, gebalanceerde GPipe-style schedule met p stages en m micro-batches is de forward bubble fraction idealiter ongeveer:

(p - 1) / (m + p - 1)

Echte schedules kunnen one-forward/one-backward, interleaving of zero-bubble-varianten gebruiken, en ongelijke layer costs kunnen de formule domineren. Kies stage boundaries op basis van gemeten tijd en memory, niet op basis van gelijke aantallen layers.

Context parallelism: activations over lange sequences partitioneren

Context parallelism distribueert de sequence dimension. De context-parallelism-documentatie van NVIDIA beschrijft de sequence split en de key/value exchange die voor attention nodig is. Elke rank bezit een sequence shard, terwijl attention de informatie uitwisselt die nodig is om full-context semantics te behouden. Implementaties kunnen point-to-point rings, all-gather, all-to-all of hiërarchische combinaties gebruiken.

Het vermindert activation memory voor training met lange context, maar repliceert weights over de context group en introduceert attention communication. Het voordeel hangt af van het attention type, causal masking, sequence length, recomputation en de manier waarop context groups worden gecombineerd met tensor- en data-parallel groups.

Selecteer dit niet op basis van een universele grens van 8K, 32K of 100K. Profile activation memory en attention communication voor de daadwerkelijke architecture.

Expert parallelism: alleen voor een MoE-architecture

Expert parallelism distribueert experts in mixture-of-experts-layers. De parallelism guide van NVIDIA documenteert deze expert placement en de combinatie ervan met andere parallelismedimensies. De router stuurt token representations naar geselecteerde experts en combineert hun resultaten. Alleen geselecteerde experts rekenen voor elke token, maar de totale expert weights moeten nog steeds worden opgeslagen en over de serving placement worden verdeeld.

Expert parallelism is geen optimization switch voor een dense model. Het maakt deel uit van een MoE-architecture. Belangrijke aandachtspunten zijn load balance, capacity limits, token all-to-all, dropped of padded tokens, auxiliary losses en failure skew. Track tokens per expert, routing entropy, capacity overflow, communication time en quality per route.

Stel een layout samen op basis van de topology

Grote training systems combineren meerdere dimensies. De totale world size volgt doorgaans het product van de groepsgroottes voor data-parallel (DP), tensor-parallel (TP), pipeline-parallel (PP) en context-parallel (CP). De parallelism guide van NVIDIA toont dit product:

world size = DP × TP × PP × CP

Expert parallelism kan dimensies anders delen of daarin worden opgenomen. Controleer daarom de ondersteunde mesh van het framework in plaats van blind te vermenigvuldigen.

Bouw de layout in deze volgorde op:

  1. Teken de communication domains: GPU-to-GPU-links, switches, non-uniform memory access (NUMA)-boundaries, node fabric, oversubscription en storage path.
  2. Plaats frequente latency-sensitive collectives, meestal TP, in het snelste geschikte domain.
  3. Kies FSDP- of replicated DP-groups op basis van resterende capacity en bandwidth.
  4. Voeg PP toe wanneer depth placement of cross-domain traffic voordeel oplevert; balanceer gemeten stage time en memory.
  5. Voeg CP alleen toe voor de sequence constraint en expert parallelism (EP) alleen voor de expert topology van het model.
  6. Controleer de deelbaarheid van heads, hidden dimensions, layers, experts, batch en sequence voor de beoogde mesh.
  7. Benchmark verschillende geldige meshes. Topology-aware heuristics leveren kandidaten, geen winnaars.

Twee clusters met hetzelfde aantal GPUs kunnen verschillende layouts prefereren, omdat link bandwidth, switch hierarchy, CPU attachment en network contention verschillen.

Training en serving vereisen afzonderlijke beslissingen

Inference gebruikt doorgaans geen gradients of optimizer state. FSDP-style training layouts kunnen daarom niet automatisch worden overgenomen.

Stel voor serving de volgende vragen:

  • Past één replica met weights, KV cache, workspace en de beoogde concurrency?
  • Levert throughput meer op met meerdere onafhankelijke replicas of met sharding van één replica?
  • Vermindert TP de weight- en cache pressure per rank voldoende om de communication per layer terug te verdienen?
  • Wordt PP efficiënt ondersteund voor het model en de request scheduler?
  • Hoe belasten prefill en decode computation, memory bandwidth en interconnect op verschillende manieren?
  • Wat gebeurt er met tail latency wanneer requests verschillende prompt- en output lengths hebben?

Benchmark de volledige server met de scheduler, quantization, context distribution, batching policy en traffic shape. Training tokens per second kunnen serving time to first token of inter-token latency niet voorspellen.

Meet een scaling-layout eerlijk

Leg voor elke kandidaat het volgende vast:

  • model, code, runtime, kernels en topology identity
  • global en local batch, sequence distribution en token count
  • peak memory per categorie, waar beschikbaar
  • useful tokens per second en model floating-point operation (FLOP) utilization, wanneer consistent berekend
  • blootgestelde tijd in all-reduce-, all-gather-, reduce-scatter-, all-to-all- en point-to-point-operaties
  • input stalls, checkpoint time, restart behavior en straggler distribution
  • training loss of serving-output parity ten opzichte van de baseline

Vergelijk weak en strong scaling bewust. Strong scaling houdt het totale werk constant terwijl het aantal ranks toeneemt. Weak scaling houdt het werk per rank constant, waardoor het totale werk met het aantal ranks groeit. Een percentage met het label “scaling efficiency” is betekenisloos zonder die denominator en baseline.

Conclusie

Parallelism is een mapping van een gemeten bottleneck naar een tensor dimension en een communication pattern. Replication, sharding, layer partitioning, staging, sequence partitioning en expert routing verlichten elk een andere constraint en veroorzaken elk een andere failure mode.

Breng de workload in kaart, teken de topology, genereer geldige meshes en profile ze. De winnende layout is de layout die met voldoende headroom past en voor de workload die je daadwerkelijk draait zo weinig mogelijk communication blootstelt.
