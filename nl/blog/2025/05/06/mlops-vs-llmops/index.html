MLOps versus LLMOps: infrastructuur voor foundation models

Viacheslav Dubrov

2025-05-06 · Bijgewerkt 2026-07-15 · 7 min · AI-infrastructuur

Automatische vertaling Dit artikel is automatisch vertaald vanuit de oorspronkelijke Engelse versie.

Foundation models hebben verschillende aannames achter klassieke MLOps veranderd. Teams passen vaak een pretrained model aan of roepen het aan, in plaats van elk model vanaf nul te trainen. Gegenereerde antwoorden en tool-acties vereisen bovendien evaluatie die verder gaat dan één vaste prediction metric.

De discipline van MLOps blijft van toepassing. Wat is veranderd, is de operationele eenheid: het gedrag van een language-modelapplicatie kan naast model weights ook afhangen van prompts, decoding, retrieval, tool contracts, permissions, routing en policy. In dit artikel wordt uitgelegd wat bruikbaar is gebleven en wat LLM-systemen daaraan hebben toegevoegd.

Dit artikel is bedoeld voor ML-, platform- en AI application engineers die conventionele MLOps al begrijpen.

Na het lezen kun je het volledige release manifest voor een foundation-modelapplicatie identificeren. Je kunt ook bepalen welke control je als eerste moet toevoegen wanneer er een failure optreedt.

TL;DR. Behoud MLOps-lineage, automatisering, staged delivery, monitoring en rollback. Breid het release manifest uit met provider of weights, prompts, schemas, retrieval state, tools, routing en policy. Promoot dat manifest via gelaagde evaluaties en gebruik vervolgens privacybewuste traces om production failures om te zetten in nieuwe tests.

Wat MLOps al heeft opgelost

MLOps heeft controls gevestigd die niet verouderd raken wanneer het model tekst genereert:

  • lineage van data, code, configuratie en model naar een release
  • reproduceerbare training- of build-pipelines
  • offline validation vóór promotion
  • registries en immutable artifact identity
  • staged rollout, service-level objectives, rollback en incident response
  • infrastructure telemetry en capacity planning
  • access control, retention en audit policy voor data

Foundation models nemen deze behoeften niet weg. Ze maken de oude term “model version” alleen te beperkt.

De release-eenheid werd een system manifest

Voor een conventionele prediction service is de meeste behavioral change doorgaans terug te voeren op code, feature logic en model identity. Voor een foundation-modelsysteem moet je ten minste het volgende vastleggen:

application code revision
model provider + model/revision + serving configuration
system and task prompts
response schema + decoding parameters
retrieval corpus snapshot + parser + chunker + embedding model + index
tool definitions + implementation revisions + permission policy
routing, fallback, caching, and budget policy
safety and business-rule revisions
evaluation dataset + scorer revisions

De exacte lijst hangt af van het systeem. De invariant is dat één manifest elk onafhankelijk wijzigend component moet identificeren dat user-visible behavior kan veranderen.

De model alias van een provider is niet noodzakelijk een immutable artifact. Een self-hosted checkpoint hash is preciezer, maar ook runtime-, quantization-, template- en parallelism-configuratie horen in het release record thuis.

Vijf failure surfaces zijn uitgebreid

Het verschil tussen MLOps en LLMOps wordt duidelijker in failure analysis dan in lijsten met tools.

1. Model en serving

Hosted models brengen provider availability, quotas, regional processing, alias changes en pay-per-token economics met zich mee. Self-hosted models voegen weight supply chains, GPU-capaciteit, batching, cache policy, quantization en distributed serving toe.

Beide hebben controls nodig voor latency, errors, throughput, saturation en cost. Geen van beide deploymentmodi maakt quality evaluation overbodig.

2. Prompt, schema en orchestration

Een prompt is code-achtige configuratie, maar de prompttekst alleen definieert het gedrag niet. Message ordering, tool descriptions, response schema, decoding, retries, truncation en de omringende code zijn allemaal van belang.

Versioneer de assembled request en orchestration policy. Test structured outputs met parsers en business invariants, in plaats van “valid JSON” als task success te accepteren.

3. Retrieval en context

Retrieval voegt een onafhankelijk data product toe tussen de source of truth en het model:

De pipeline moet source revision, parser- en chunker-versies, embedding identity, index build, access-control metadata en deletion state behouden. Evalueer retrieval vóór generation. Controleer of het systeem het juiste bewijs heeft gevonden, of authorization filtering correct werkte en of het antwoord het aangeleverde bewijs correct gebruikte.

Een vector index vervangt geen feature store of warehouse. Een vector index handelt similarity retrieval af. Structured point-in-time features en analytical facts hebben andere consistency- en queryvereisten.

4. Tools en acties

Wanneer een model APIs kan aanroepen, kunnen quality failures side effects worden. De operationele boundary omvat nu ook tool authentication, least privilege, argument validation, timeouts, idempotency, approval policy en postcondition checks.

Trace welke tool werd aangeboden, geselecteerd, aangeroepen, afgewezen, opnieuw geprobeerd en gecommit. Een vloeiend final answer bewijst niet dat het action path correct was.

5. Safety, security en policy

Content filters zijn één control, geen complete guardrail layer. Tot de bedreigingen behoren ook prompt injection, cross-tenant retrieval, secret disclosure, excessive agency, untrusted model- of node-code en onveilige tool arguments.

Druk deterministische business rules waar mogelijk buiten het model uit. Definieer residual risks, test adversarial cases en wijs een owner aan voor policy changes. NIST’s Generative AI Profile is een nuttige risk inventory, maar geen kant-en-klare acceptance test.

Evaluatie wordt een release gate

Free-form output maakt één geaggregeerd accuracy number onvoldoende. Dat betekent niet dat quality onmeetbaar is.

Bouw een evaluation stack met verschillende soorten evidence:

  1. Deterministische checks: schema validity, aanwezige citations, toegestane tools, argument constraints, policy rules, latency en budget.
  2. Component metrics: retrieval recall en ranking, tool-selection accuracy, tool-argument correctness en route selection.
  3. End-to-end tasks: representatieve inputs met expliciete success criteria en slice labels.
  4. Model-based scoring: rubric-driven judgments die zijn gecalibreerd tegen expert labels en worden gemonitord op judge drift.
  5. Human review: ambigue, consequential, nieuwe of gesamplede cases waarbij automatisering niet authoritative is.
  6. Adversarial tests: injection-, data-boundary-, abuse-, refusal- en side-effect-cases die aan het threat model zijn gekoppeld.

Sla resultaten per example op, niet alleen gemiddelden. Een release kan het gemiddelde verbeteren en tegelijk regressies veroorzaken voor één taal, tenant, documenttype of action class.

Ik promoveerde een release omdat het gemiddelde steeg. Het documenttype van één tenant was slechter geworden, en het gemiddelde was groot genoeg om dat verlies op te slokken.

De deployment gate vergelijkt een candidate manifest met de huidige release op dezelfde versioned suite. Thresholds moeten quality, safety, latency en cost gezamenlijk afdekken. Een goedkopere route die de taak niet goed uitvoert, is geen optimization.

Traces verbinden production met evaluatie

Infrastructure metrics kunnen laten zien dat een model call traag is. Ze laten niet zien dat retrieval een niet-geautoriseerd document heeft teruggegeven of dat een tool met het verkeerde account is aangeroepen. MLflow’s tracing documentation beschrijft traces die de intermediate steps en metadata vastleggen die nodig zijn om dit path te inspecteren.

Leg een trace vast over het volledige decision path:

  • release-manifest identity en request correlation
  • model- en provider-calls, latency, usage en finish state
  • retrieval query, document identifiers, scores en filtering decisions
  • prompt/template revision zonder gevoelige content indiscriminately op te slaan
  • tool offers, arguments, approvals, results en side-effect identifiers
  • policy decisions, retries, fallbacks en final outcome

Tracing creëert een nieuw data-governance-oppervlak. Pas minimization, redaction, tenant isolation, encryption, sampling, retention en access review toe voordat je volledige prompts of documenten verzamelt. OpenTelemetry’s GenAI semantic conventions kunnen helpen bij interoperability, maar zijn nog in ontwikkeling. Pin de convention- of schema-versie, instrumentation en collector-versies.

De improvement loop is:

production trace → triaged failure → labeled regression case
                 → candidate change → offline comparison
                 → staged release → monitored outcome

User feedback kan onderzoek prioriteren, maar een thumbs-up is geen ground truth. Bewaar de omliggende trace en verkrijg expert labels voor consequential cases.

De serving gateway is een policy boundary

Een gateway kan application clients loskoppelen van providers of self-hosted engines. Verantwoordelijkheden die je daar kunt onderbrengen zijn onder meer:

  • authentication, tenant budgets, quotas en rate limits
  • stabiele request- en response-contracten
  • route selection op basis van capability, region, latency of geëvalueerde quality
  • bounded retries, circuit breakers en expliciete fallback semantics
  • cache partitioning en sensitive-data policy
  • usage attribution en propagation van het release manifest

Fallback is evenzeer een behavioral change als een reliability mechanism. Als een kleiner model, alternate provider of reduced context de task quality verandert, evalueer en traceer die branch dan als een afzonderlijke route.

Plaats niet elke orchestration decision in de gateway. Houd domain rules dicht bij de applicatie en maak ownership zichtbaar.

Fine-tuning is één intervention, niet de maturity ladder

Kies de intervention op basis van de geobserveerde failure:

FailureEerste component om te inspecteren
Ontbrekende actuele of private feitenretrieval en source synchronization
Verkeerd format of ongeldige argumentsschema, constrained output, validation
Inconsistent task behaviorprompt, examples, model choice, daarna adaptation data
Excess latency of costroute, context, cache, batching, quantization
Niet-geautoriseerde of onveilige actiontool permissions en deterministische policy
Domain behavior die niet uit context kan worden hersteldfine-tuning of een ander specialized model

LoRA en andere parameter-efficient methods verminderen het aantal trainable parameters. Ze nemen dataset governance, base-model licensing, evaluation, serving compatibility of rollback requirements niet weg.

Een praktische adoptiesequentie

  1. Definieer de user task, harm boundaries, service objectives en cost envelope.
  2. Maak het release manifest voordat je een prompt registry, vector database of gateway product introduceert.
  3. Bouw een kleine, geslicede evaluation set en deterministische component tests.
  4. Instrumenteer één end-to-end trace met privacy controls en stabiele release identities.
  5. Promoot via shadow, canary of limited traffic met een expliciete rollback trigger.
  6. Zet reviewed production failures om in regression cases en herhaal.

Voeg alleen infrastructuur toe wanneer die een benoemde control beheert of een gemeten bottleneck wegneemt. “LLMOps platform” is geen architectuurvereiste.

Conclusie

LLMOps is MLOps toegepast op een grotere behavioral unit. Het model blijft belangrijk, maar prompts, retrieved evidence, tool permissions, routing en policy kunnen de uitkomst veranderen zonder de weights te wijzigen.

Version die volledige unit, evalueer deze vóór release, traceer haar met privacy boundaries en rollback haar als één systeem.
