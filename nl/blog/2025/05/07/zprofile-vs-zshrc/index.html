Zsh-startupbestanden: .zprofile versus .zshrc op macOS en Linux

Viacheslav Dubrov

2025-05-07 · Bijgewerkt 2026-07-15 · 4 min · Ontwikkelaarstools

Automatische vertaling Dit artikel is automatisch vertaald vanuit de oorspronkelijke Engelse versie.

Als je terminal traag aanvoelt of een environment variable wel in de ene terminal verschijnt maar niet in de andere, ligt de oorzaak vaak bij de startup mode van Zsh. De twee bestanden waar de meeste mensen naar grijpen zijn ~/.zprofile en ~/.zshrc, maar op basis van de bestandsnaam alleen kun je niet bepalen waar een regel thuishoort.

Zsh kiest startup files op basis van twee onafhankelijke eigenschappen: of de shell een login shell is en of deze interactive is. Terminalapplicaties op macOS en Linux kunnen verschillende combinaties kiezen. Inspecteer daarom de actieve shell in plaats van ervan uit te gaan dat het besturingssysteem dit voor je bepaalt.

TL;DR. Plaats initialisatie voor de login-session in .zprofile en interactive gedrag in .zshrc. Houd .zshenv stil en minimaal. Verplaats interactive version-manager hooks niet naar .zprofile en source niet het volledige profile vanuit .zshrc; inspecteer de door de tool gegenereerde code en volg de actuele Zsh-instructies.

Zsh evalueert twee onafhankelijke flags

Een shell kan zijn:

  • login en interactive, zoals Apple Terminal het standaard login shell van het account normaal gesproken start
  • non-login en interactive, zoals een geneste zsh of veel Linux-terminalconfiguraties deze start
  • login en non-interactive, zoals zsh -lc 'command'
  • non-login en non-interactive, zoals zsh -c 'command'

Terminalapplicaties, IDE’s, remote sessions, multiplexers en expliciete shell flags kunnen verschillende modes kiezen. Het besturingssysteem alleen bepaalt het resultaat dus niet.

Vraag het de actieve shell in plaats van te gokken:

print -r -- "interactive=$options[interactive] login=$options[login]"

De daadwerkelijke startup-volgorde

Zsh leest globale bestanden en daarna het bijbehorende user file. Met de standaardopties van RCS is de volgorde van de user files:

  1. $ZDOTDIR/.zshenv bij elke Zsh-invocatie
  2. $ZDOTDIR/.zprofile als de shell een login shell is
  3. $ZDOTDIR/.zshrc als de shell interactive is
  4. $ZDOTDIR/.zlogin als de shell een login shell is
  5. $ZDOTDIR/.zlogout wanneer een login shell normaal afsluit

Als ZDOTDIR niet is ingesteld, gebruikt Zsh $HOME. De locaties van system-wide files zijn afhankelijk van de installatie; de gebruikelijke defaults zijn /etc/zshenv, /etc/zprofile, /etc/zshrc, /etc/zlogin en /etc/zlogout.

.zprofile wordt eenmaal per login-shell process uitgevoerd, niet eenmaal per login op de computer. Als elk nieuw terminaltabblad een login shell start, leest elk tabblad het bestand.

Houd .zshenv saai

Elke non-interactive zsh -c leest .zshenv. Een echo, package-manager call of dure subprocess kan daar command output beschadigen en scripts vertragen. De meeste gebruikers hebben weinig tot niets in dit bestand nodig.

Een geëxporteerde variable in .zprofile wordt geërfd door child processes van die login shell. Deze wordt niet automatisch geïnjecteerd in losstaande GUI-applicaties, services of shells waarvan de parent het bestand nooit heeft gelezen.

Gebruik .zprofile voor login-only setup

Een klein profile kan geëxporteerde defaults en een idempotent path instellen:

# ~/.zprofile
export EDITOR=nvim
export VISUAL=nvim

# Zsh ties the path array to the PATH scalar.
typeset -U path PATH
path=("$HOME/.local/bin" $path)
export PATH

typeset -U verwijdert dubbele array entries. Dit maakt herhaald sourcen veiliger, hoewel startup files nog steeds onnodig werk moeten vermijden.

Gebruik .zshrc voor interactive state

# ~/.zshrc
setopt auto_cd hist_ignore_all_dups share_history

autoload -Uz compinit
compinit

alias ll='ls -lah'
bindkey -e

Aliases, completion widgets, key maps, prompts en directory-change hooks horen bij de interactive shell die ze gebruikt.

Version managers overschrijden de eenvoudige bestandsgrens

Het advies “zet version managers in .zprofile omdat ze traag zijn” is onbetrouwbaar. Een version manager kan verschillende soorten code genereren:

  • een statische path- of root-variable
  • een command-shim path die child processes nodig hebben
  • completion definitions
  • shell functions die de huidige shell wijzigen
  • directory-change hooks voor automatisch wisselen van versions

De interactive onderdelen moeten in elke interactive shell aanwezig zijn, inclusief een geneste zsh die vanuit een editor wordt gestart. De actuele fnm-documentatie plaatst deze hook daarom in .zshrc:

eval "$(fnm env --use-on-cd --shell zsh)"

De actuele pyenv-documentatie plaatst volledige interactive initialisatie eveneens in .zshrc:

export PYENV_ROOT="$HOME/.pyenv"
[[ -d $PYENV_ROOT/bin ]] && path=("$PYENV_ROOT/bin" $path)
eval "$(pyenv init - zsh)"

Pyenv documenteert een beperktere pyenv init --path-mode voor het instellen van de shim-path, maar volledige pyenv init installeert ook completion en shell functions. Inspecteer de actuele documentatie en gegenereerde output van een tool voordat je deze opsplitst.

Als startup traag is, meet dit dan voordat je code verplaatst naar een mode waarin deze niet meer werkt.

Source niet het volledige profile vanuit .zshrc

Een veelgebruikte cross-platform workaround is:

# Avoid this blanket coupling.
source ~/.zprofile

Daarmee worden login-only actions actions per interactive shell en kunnen agent startup, keychain access, output of path mutations zich herhalen.

Als zowel login als non-login interactive shells een kleine set statische exports nodig hebben, extraheer dan een idempotent fragment en source dat bewust:

# ~/.config/zsh/environment.zsh
typeset -U path PATH
path=("$HOME/.local/bin" $path)
export PATH EDITOR=nvim VISUAL=nvim
# ~/.zprofile
source "$HOME/.config/zsh/environment.zsh"
# ~/.zshrc
if [[ ! -o login ]]; then
  source "$HOME/.config/zsh/environment.zsh"
fi

# Interactive-only configuration follows.

Dit patroon houdt shared data gescheiden van login side effects. Een andere geldige keuze is om de terminal of session manager consistent te configureren in plaats van beide modes te ondersteunen.

Diagnoseer de shell die traag is of state mist

Reproduceer elke mode rechtstreeks:

zsh -lic 'print "login interactive"'
zsh -ic  'print "non-login interactive"'
zsh -lc  'print "login non-interactive"'
zsh -c   'print "non-login non-interactive"'

Meet de mode die gebruikers daadwerkelijk starten:

time zsh -lic exit
time zsh -ic exit

Trace file- en line-execution wanneer niet duidelijk is waar de source vandaan komt:

PS4='%N:%i> ' zsh -xlic exit

Voer de trace uit in een schoon testaccount of inspecteer deze voordat je hem deelt: startup commands kunnen tokens en andere gevoelige waarden uitbreiden.

Controleer bij een ontbrekend executable zowel de mode als het path:

print -r -- "interactive=$options[interactive] login=$options[login]"

Conclusie

Het relevante onderscheid is niet “environment versus aliases”. Het gaat om login-only state versus interactive state, plus de kleine hoeveelheid die daadwerkelijk elk Zsh-process moet beïnvloeden.

Controleer de shell flags, houd startup files stil en plaats elke gegenereerde hook waar alle vereiste features beschikbaar zijn. Zo blijft de configuratie portable tussen terminalapplicaties, zonder te doen alsof macOS en Linux elk één vaste launch mode hebben.
