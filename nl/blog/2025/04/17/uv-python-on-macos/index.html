uv op macOS: Beheer van Python-versies, projecten en hulpmiddelen

Ik ben overgestapt op uv voor mijn Python-workflow, omdat dit hulpmiddel de voormalige tool-switching tussen pip, virtuele omgevingen, pip-tools, pipx en projectbeheerders heeft vervangen. Nu volstaat één uitvoerbaar bestand voor het grootste deel van deze taken.

De workflows verschillen echter nog steeds. Een project, een inline-metadata-script, eenmalige CLI’s en geïnstalleerde CLI’s hebben elk hun eigen omgeving en levenscyclus. Deze gids laat de door mij gebruikte commando’s en de grenzen daartussen zien.

Snelle start

# Install uv with Homebrew
brew install uv

# Start a project
uv init example-app
cd example-app
uv add httpx
uv run python main.py

# Run an isolated CLI without installing it permanently
uvx ruff check .

# Run a script that declares PEP 723 dependencies
uv run fetch.py

TL;DR. Binnen projecten gebruik ik uv add, uv lock, uv sync en uv run; voor zelfstandige scripts maak ik gebruik van PEP 723-metadata; uvx wordt gebruikt voor eenmalige hulpmiddelen; en uv tool install voor commando’s die op PATH moeten blijven staan. In CI controleert --locked of de projectmetadata overeenkomt met uv.lock; --frozen vertrouwt op de bestaande lock zonder de versheid te controleren.

Installeer uv met één owner

Homebrew is een handige manier om uv op macOS te installeren:

brew install uv
uv --version

Als Homebrew uv al heeft geïnstalleerd, dient het dit te upgraden:

brew upgrade uv

uv self update is bedoeld voor de standaardinstallatiemethode van uv en wordt uitgeschakeld bij installaties via package-managers. Laat geen twee installatieprogramma’s concurreren om hetzelfde uitvoerbaar bestand.

Handige identiteitscommando’s:

command -v uv
uv python dir
uv tool dir
uv cache dir

Gemanageerde Python-installaties, permanente hulpmiddelen en tijdelijke cache-entries hebben aparte mappen. De cache kan worden verwijderd en opnieuw aangemaakt; hij vormt geen bron van waarheid.

Projecten: declaraties, resolutie en omgeving

Een uv-project bevat normaal gesproken drie verschillende artefacten:

  • pyproject.toml declareert de projectmetadata en directe vereisten.
  • uv.lock slaat de cross-platform resolutie van uv op.
  • .venv is de lokaal geïnstalleerde omgeving en dient tijdelijk te zijn.

Maak een applicatie aan en voeg runtime- en testvereisten toe:

uv init forecast-app
cd forecast-app

uv add httpx
uv add --group test pytest
uv run python main.py
uv run --group test pytest

De huidige uv-applicatietemplates genereren main.py, pyproject.toml, README.md en .python-version. Ze definiëren standaard geen build-systeem. Gebruik uv init --lib voor een gepakte bibliotheek met een src-layout en een build-backend.

uv run controleert het project, updateert de lock indien nodig, synchroniseert de vereiste afhankelijkheden en voert het commando uit. De eerste projectoperatie maakt indien nodig .venv en uv.lock aan; uv init zelf genereert alleen de projectbestanden.

Commit de invoer, niet de omgeving

Commit pyproject.toml, uv.lock, de broncode en een bewuste .python-version. Negeer .venv en de caches van uv.

De lock legt een resolutie vast voor alle ondersteunde markers en platforms; dit zorgt er niet voor dat native wheels identiek zijn op macOS, Linux, Intel en Apple Silicon. Test elke distributieplatform.

Lockversheid bepalen: --locked is niet --frozen

Als standaard kunnen projectcommando’s uv.lock bijwerken wanneer de declaraties veranderen.

Gebruik --locked om te vereisen dat de lock up-to-date is met de projectmetadata:

uv lock --check
uv sync --locked
uv run --locked pytest

Wanneer pyproject.toml en uv.lock niet overeenkomen, falen deze commando’s in plaats van een nieuwe lock te genereren. Dit vormt meestal de gewenste CI-gate.

Gebruik --frozen alleen wanneer je expliciet wilt dat uv de bestaande lock gebruikt zonder te controleren of deze nog actueel is:

uv sync --frozen

Dit kan nuttig zijn in een gecontroleerde buildfase waarin de lock al is geverifieerd, maar het is geen detector voor verouderde locks. uv sync werkt standaard exact en verwijdert ongewenste pakketten; uv run maakt standaard gebruik van een onnauwkeurige synchronisatie, tenzij --exact wordt opgevraagd.

Gemanageerde Python: een versieniveauverzoek, geen universele binary

uv kan Python-distributies downloaden en beheren:

uv python install 3.12 3.13
uv python list --only-installed
uv python pin 3.12

De gemanageerde CPython-builds van uv komen van het python-build-standalone-project. uv kan ook systeminterpreters, Homebrew, pyenv, Conda en andere interpreters detecteren.

.python-version is een versieniveauverzoek dat door uv en andere compatibele tools wordt gedetecteerd. requires-python in pyproject.toml vormt het compatibiliteitscontract van het project. Houd beide bewust in stand:

[project]
requires-python = ">=3.12,<3.14"

Het pinnen van 3.12 garandeert niet dat er voor altijd dezelfde patch-build of hetzelfde artefact op elk besturingssysteem beschikbaar is. Vraag alleen om een exacte patch wanneer dit daadwerkelijk nodig is, en zorg ervoor dat de CI expliciet de interpretator selecteert en rapporteert.

Gebruik een andere Python-manager wanneer een project een distributie of buildconfiguratie nodig heeft die uv niet levert. uv kan die interpretator nog steeds gebruiken via --python of via normale detectiemethoden.

Kiezen tussen uv run, uvx en geïnstalleerde hulpmiddelen

Projectgerelateerde hulpmiddelen: uv run

Als pytest, mypy, een codegenerator of een ander hulpmiddel het project moet importeren of diens gelockte plugins moet gebruiken, declareer het dan in een afhankelijkheidsgroep:

uv add --group lint ruff
uv run --group lint ruff check .

Het uitvoeren van dit hulpmiddel via uvx zal het isoleren van het project en kan ertoe leiden dat de benodigde geïnstalleerde pakketten of plugins niet zichtbaar zijn.

Ad-hoc hulpmiddelen: uvx

uvx is een alias voor uv tool run. Het creëert een geïsoleerde omgeving die wordt opgeslagen in de tijdelijke uv-cache:

uvx ruff@0.12.0 check .
uvx --from jupyterlab jupyter lab
uvx --with mkdocs-material mkdocs --help

Pin de versie van het hulpmiddel in de CI of in de documentatie. Bij een eerste, ongeversioneerde oproep wordt een actuele release geselecteerd, terwijl latere oproepen de cachestatus kunnen hergebruiken.

Permanente uitvoerbare bestanden: uv tool install

Installeer een hulpmiddel wanneer scripts buiten jouw controle zijn commando’s van dit hulpmiddel op PATH nodig hebben, of wanneer het machinemanifest dit expliciet beheert:

uv tool install 'ruff==0.12.0'
uv tool list
uv tool upgrade ruff
uv tool uninstall ruff

Permanente hulpmiddelen maken nog steeds gebruik van geïsoleerde omgevingen. Mutateer deze omgevingen niet handmatig met pip.

Scripts: één bestand als release-eenheid maken

PEP 723 definieert metadata voor inline-scripts. Een compatibele runner kan de commentblokken lezen en een geïsoleerde omgeving opbouwen.

# /// script
# requires-python = ">=3.12"
# dependencies = [
#   "httpx>=0.27,<1",
# ]
# ///
import httpx


response = httpx.get("https://example.com", timeout=10)
response.raise_for_status()
print(response.status_code)

Voer metadata uit en bewerk deze met uv:

uv run fetch.py
uv add --script fetch.py rich
uv remove --script fetch.py rich

Een gewone python fetch.py negeert de commentaarmetadata. Daarom heeft het script afhankelijkheid van een compatibele runner, ook al blijft de Python-syntaxis geldig.

Voor een script dat later een specifieke oplossing moet reproduceren, moet er een bijbehorend lock worden aangemaakt:

uv lock --script fetch.py
uv run --script fetch.py

Dit schrijft fetch.py.lock op. Een exclude-newer-tijdstempel kan de mogelijke distributiedata beperken, maar is zwakker dan een exact vastgelegde oplossing en garandeert niet dat het artefact beschikbaar blijft.

Gebruik liever een project wanneer meerdere bestanden dezelfde afhankelijkheden delen, de code als pakket geïmporteerd kan worden, tests toegang hebben tot de projectstatus, of meerdere scripts samen verplaatst moeten worden.

Vereistenbestanden: compatibiliteit, geen fouten

Een requirements.txt-bestand kan losse invoerwaarden, exacte waarden, hashes, beperkingen, indices, URLs of een gecompileerde omgeving bevatten. De reproduceerbaarheid hangt af van de manier waarop het wordt gegenereerd en gebruikt; alleen de bestandsnaam zegt niets over de inhoud.

Gebruik de pip-compatibele interface van uv zonder migratie:

uv venv
uv pip sync requirements.txt
uv run python app.py

uv pip sync zorgt ervoor dat de omgeving overeenkomt met het bestand, terwijl uv pip install -r additief werkt.

Voor een eigen applicatie kan een gestage migratie nuttig zijn:

uv init --bare
uv add -r requirements.in
uv add --group test -r requirements-test.in
uv lock
uv sync --locked

Voer eerst het volledige test- en deployproces uit voordat oude bestanden worden verwijderd. Als een downstream-systeem nog steeds de pip-formaat verwacht, kan dit worden afgeleid uit het geverifieerde uv lock:

uv export --format requirements.txt \
  --output-file requirements.txt

Houd uv.lock en een handmatig bewerkte export niet als twee concurrerende oplossingen bij.

Cache, indices en grenzen van de leveringsketen

De uv-cache verbetert herhaalde installaties, maar is nog steeds tijdelijk:

uv cache prune
uv cache clean

Gebruik prune voor routinematige schoonmaakwerkzaamheden. clean verwijdert alle cache-entries en zorgt ervoor dat er opnieuw gedownload en gebouwd wordt.

Een lockfile verbetert de reproduceerbaarheid; het maakt de afhankelijkheden echter niet betrouwbaar. Controleer de bronnen van pakketten, de indexconfiguratie, Git-revisies, build-backend’s, licenties en credentials. Houd geauthenticeerde indexconfiguraties buiten de gecommitteerde bestanden, tenzij het repository alleen niet-vertrouwelijke referenties naar een goedgekeurd authenticatiemechanisme bevat.

Voor native pakketten moet de deployarchitectuur worden vastgelegd en de beschikbaarheid van testwheels worden gecontroleerd. Anders kan een resolver terugvallen op een bronbuild die compilers en systeembibliotheken vereist die afwezig zijn in CI of in productieomgevingen.

Een compacte operationele controlelijst

Voor elk project:

  1. Definieer requires-python en directe afhankelijkheden in pyproject.toml.
  2. Scheid gepubliceerde extra’s van lokale afhankelijkheidsgroepen.
  3. Commit uv.lock; negeer .venv en de cachestatus.
  4. Voer projectgerelateerde hulpprogramma’s uit binnen de projectomgeving.
  5. Gebruik uv lock --check of --locked in CI.
  6. Test elke doelbesturingssysteem- en architectuurcombinatie die door de lock wordt ondersteund.
  7. Exporteer alleen compatibiliteitsformaten voor genoemde downstream-consumenten.
  8. Beoordeel de broncode- en credentialbeleid apart van de resolutie.

UV is het meest nuttig wanneer deze eigendomsgrenzen zichtbaar blijven. Eén binary kan ze allemaal beheren zonder ze te combineren tot één enkele omgeving. Deze combinatie – minder tools, zonder te doen alsof elke workflow hetzelfde is – is de reden dat ik het nog steeds als mijn standaard Python-projecttool op macOS gebruik.
