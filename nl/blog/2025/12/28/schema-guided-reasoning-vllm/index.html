Schema-Guided Reasoning: vLLM, XGrammar en Pydantic

Viacheslav Dubrov

2025-12-28 · Bijgewerkt 2026-09-12 · 13 min · AI-agenten · Modelengineering

Dit artikel is bedoeld voor Python-engineers die modeloutput nodig hebben die downstream-code kan valideren. Je leert hoe je een Pydantic-schema definieert, structured output opvraagt bij vLLM en application checks toevoegt voor betekenis en beleid.

Pydantic beschrijft de responsevelden, vLLM serveert het model en XGrammar beperkt welke tokens het model kan genereren. Deze beperking heet constrained decoding. Ze is alleen van toepassing op de schemafeatures die door de decoding-backend worden ondersteund, hier XGrammar. Een tokenlimiet kan nog steeds een onvolledig JSON-prefix opleveren. Daarom moet application code de completion controleren en het resultaat valideren.

Wat is Schema-Guided Reasoning?

Schema-Guided Reasoning is een techniek die Rinat Abdullin in juli 2025 beschreef. In plaats van het model tekst vrij te laten aanvullen — wat inconsistent of ambigu kan zijn — geef je het een strikt template dat definieert:

  • welke stappen de response moet representeren
  • in welke volgorde die stappen bedoeld zijn, zodat een reviewer het pad van data naar beslissing kan inspecteren
  • waarop het model zijn aandacht moet richten

Zie het als een checklist van outputs die je kunt inspecteren, niet als bewijs van de interne reasoning van het model. De decoder controleert de outputstructuur; application code bepaalt wanneer elke fase wordt uitgevoerd en of een resultaat mag worden gebruikt.

Wat het schema controleert

Het voorbeeld gaat over een korting om een klant te behouden die mogelijk vertrekt. Churn probability schat de kans op vertrek; cart value is het totaalbedrag vóór de korting. Margin is de brutowinst als fractie van dat totaal: een winkelmandje van $200 met een margin van 0.20 heeft $40 brutowinst. Kortingen gebruiken percentagepunten, dus een voorstel van 15 betekent 15%.

Een pricing model kan geldige JSON retourneren en toch een korting van 25% voorstellen terwijl de margin slechts 20% bedraagt. Het schema legt het voorstel vast; application code moet controleren of de korting is toegestaan.

Velden zoals churn_analysis, margin_math en max_discount_percent maken de bedoelde intermediate outputs expliciet. Een schema beperkt de geretourneerde vorm. Het maakt op zichzelf niet dat het ene veld afhankelijk is van het andere en bewijst evenmin dat de beslissing correct is.

Dat levert het volgende op:

  • vergelijkbare outputstructuur bij herhaalde runs
  • vastgelegde intermediate outputs die reviewers kunnen inspecteren
  • intermediate fields die je tegen een testdataset kunt beoordelen
  • een hypothese om met kleinere models te testen: het beperken van het format kan helpen, maar task accuracy moet nog steeds worden geëvalueerd
  • Abdullin schrijft dat een accuracy-boost van 5–10% in de door hem geobserveerde gevallen “not uncommon” is; dit is een practitioner-observatie, geen benchmarkresultaat, dus meet dit op je eigen workload

Prompt guidance en decoder constraints

Prompt guidance en constrained decoding kunnen worden gecombineerd. Deze vergelijking laat zien waar elk mechanisme het aangevraagde format controleert.

Prompt engineering: het format opvragen

Deze prompt vraagt het model om het kortingsvoorstel als JSON te formatteren:

Please analyze the customer data and output your response as valid JSON
with the following structure: {"discount": <number>, "reason": <string>}
Be careful with the formatting!

Je hoopt dat het begrip van het model van “output JSON” sterker is dan zijn neiging om conversationeel te reageren. Een modelupdate, een wijziging van de temperature of een ander few-shot-example kan je parser breken.

Chain of Thought: bruikbare reasoning trace, hetzelfde structuurprobleem

Een chain-of-thought (CoT)-prompt vraagt om intermediate analysis. De response kan er als volgt uitzien:

Let's think step by step:
1. First, I'll analyze the customer's churn risk...
2. Then I'll calculate the margin...
3. Therefore, I recommend a 15% discount.

CoT kan task accuracy verbeteren wanneer de prompt, het model, de task en de evaluatie dit ondersteunen, maar het resultaat blijft prose die moeilijk betrouwbaar te parsen is. Mogelijk heb je een tweede LLM-call nodig om structured data te extraheren.

SGR: structured chain of thought

SGR kan intermediate fields beschikbaar maken voor inspectie en evaluatie. Of dit task accuracy verbetert, hangt af van het model, de prompt, de task en de manier waarop die velden worden gebruikt; het schema formaliseert alleen hun vorm:

class PricingLogic(BaseModel):
    # 1. Recorded analysis
    churn_analysis: str = Field(..., description="Analyze churn_probability")
    financial_analysis: str = Field(..., description="Analyze cart_value and margin")

    # 2. Proposed calculation, checked by application code
    margin_math: str = Field(..., description="Calculate: 'Cart $X * Y% = $Z'")

    # 3. Proposed decision, not bounded by the analysis fields
    max_discount_percent: float = Field(..., description="Max allowed discount")

    # 4. Final Output
    customer_message: str

Het schema beschrijft deze velden in die volgorde. Eén objectschema creëert geen afzonderlijke validation step tussen de velden. Gebruik aparte calls of application checks wanneer latere beslissingen afhankelijk moeten zijn van eerdere resultaten.

SGR-patronen

Byte zegt

Door analysis fields vóór een beslissing te plaatsen, wordt de response eenvoudiger te inspecteren. Een veld met de naam margin_math is nog steeds een string, geen calculator.

SGR heeft drie core patterns die je kunt combineren tot grotere workflows.

1. Cascade: sequential reasoning steps

Cascade representeert een reasoning order in één structured response. Hier legt een documentclassifier een summary, een topic-match score en een voorgestelde categorie vast. Er wordt geen afzonderlijke check uitgevoerd tussen deze velden.

from pydantic import BaseModel
from typing import Literal, Annotated
from annotated_types import Ge, Le

class DocumentEvaluation(BaseModel):
    """Record a document summary, score, and proposed category."""

    # Step 1: Record a summary
    brief_document_summary: str

    # Step 2: Rate (bounded integer)
    rate_topic_match: Annotated[int, Ge(1), Le(10)]

    # Step 3: Decide (constrained choices)
    final_recommendation: Literal["relevant", "irrelevant", "review"]

Voorbeelden van toepassingen: documentclassificatie en triage van supporttickets.

Het model krijgt de opdracht om brief_document_summary, rate_topic_match en final_recommendation in die volgorde te retourneren. Als de volgorde een beleidsvereiste is, handhaaf je die met afzonderlijke calls of deterministische application logic.

2. Routing: een semantic switch statement

Routing vraagt het model om één pad uit een reeks opties te selecteren, geïmplementeerd met Union-types. Deze router kiest tussen het ophalen van klantdata voor een pricing request en het retourneren van een algemeen antwoord.

from pydantic import BaseModel
from typing import Literal, Union

class FeatureLookup(BaseModel):
    """Route to database lookup."""
    rationale: str
    tool_name: Literal["fetch_user_features"] = "fetch_user_features"
    user_id: str

class GeneralResponse(BaseModel):
    """Standard response for non-pricing queries."""
    tool_name: Literal["respond"] = "respond"
    content: str

class RouterSchema(BaseModel):
    """The model must pick exactly ONE branch."""
    action: Union[FeatureLookup, GeneralResponse]

Goede toepassingen: intent classification, tool selection, support triage en multi-agent dispatch.

De branch-specifieke Literal-values helpen validation om de union members van elkaar te onderscheiden. Ze maken routing niet correct. Valideer het resultaat en dispatch het in application code. Configureer en test voor een expliciete Pydantic discriminator een discriminated union.

3. Cycle: herhaalde reasoning met lists

Cycle beschrijft meerdere items, met bounds voor het aantal. Dit voorbeeld voor risk assessment vraagt om twee tot vier factors, elk met een explanation en severity.

from pydantic import BaseModel
from typing import List, Literal, Annotated
from annotated_types import MinLen, MaxLen

class RiskFactor(BaseModel):
    explanation: str
    severity: Literal["low", "medium", "high"]

class RiskAssessment(BaseModel):
    """Generate 2-4 risk factors."""
    factors: Annotated[List[RiskFactor], MinLen(2), MaxLen(4)]

Goede toepassingen: risk assessment, issue extraction, parallel tool calls en multi-step planning.

De list bounds beschrijven een variabele batch van 2–4 items. Een ondersteunde decoder kan die lengte beperken; application validation controleert dit opnieuw. In combinatie met Routing kan de list voorgestelde tool calls beschrijven. Application code moet deze autoriseren en dispatchen.

SGR laten werken: constrained decoding

De bovenstaande patronen zijn slechts Pydantic-schema’s. Constrained decoding kan de ondersteunde constraints afdwingen die in hun JSON Schema worden geëxporteerd. Arbitraire Python-validators worden geen decoder constraints; ze worden na generation nog steeds door Pydantic uitgevoerd.

Constrained decoding wijzigt de token generation step. In plaats van het model vrij uit zijn vocabulary te laten samplen, past de engine een grammar mask toe dat tokens blokkeert die het schema zouden schenden. Dit gebeurt in de inference engine, niet in je application code.

[!TIP] SGR vereist geen “reasoning models” zoals o1 of DeepSeek-R1. Instruction-tuned models kunnen eveneens schema-constrained responses produceren. Vergelijk de task accuracy voor de specifieke models die je wilt serven.

Waarom hier vLLM en XGrammar gebruiken?

De structured-output API van vLLM accepteert JSON Schema via een OpenAI-compatible client. Daardoor kan het voorbeeld vertrouwde request plumbing behouden en tegelijk de decoding-backend op de server configureren. Schema-subsets, error handling en modelgedrag moeten nog steeds worden getest wanneer je van provider wisselt.

XGrammar levert de grammar compiler en token-mask machinery. Het technical overview beschrijft de onderstaande CPU/GPU-splitsing; de benchmarkresultaten gelden voor de geteste workloads, niet voor elke deployment.

Hoe XGrammar schema’s afdwingt

Waar de masking plaatsvindt

Logits zijn de ongenormaliseerde scores van het model voor mogelijke volgende tokens. XGrammar wijzigt die scores na de forward pass van het model en vóór sampling. Het verandert het model zelf niet. Het filtert welke tokens kunnen worden geselecteerd.

Een standaard inference loop ziet er als volgt uit:

1. Input tokens → GPU Forward Pass → Logits (one unnormalized score per vocabulary token)
2. Logits → Sampling (temperature, top-p, etc.) → Next Token
3. Repeat until done

XGrammar zit tussen stap 1 en 2:

1. Input tokens → GPU Forward Pass → Raw Logits
2. Raw Logits → XGrammar Logits Processor → Masked Logits
3. Masked Logits → Sampling → Next Token (continues the grammar-valid prefix)
4. Repeat until done

Het diagram toont hoe de modelscores en het grammar mask samenkomen voordat een token wordt geselecteerd. Elk geaccepteerd token werkt ook de grammar state voor de volgende stap bij.

Het model berekent nog steeds de volledige probability distribution op de GPU. XGrammar’s GrammarMatcher genereert het bitmask op de CPU; daarna verplaatst de serving engine dat bitmask naar het device van de logits en past het daar in place toe vóór sampling. Voor GPU-logits gebruikt XGrammar een GPU-kernel voor die toepassing. Ongeldige tokens krijgen logits met de waarde -∞, waardoor hun probability na softmax exact 0 is.

Twee fasen

XGrammar splitst het werk op in compile-time en runtime. Dit ontwerp beperkt herhaald grammarwerk.

Fase 1: grammar compilation, één keer per schema

Dit fragment bouwt een grammar voor het schema met de tokenizer van het model. Het gecompileerde resultaat kan worden hergebruikt bij het genereren van responses met dat schema.

# This happens once per schema
tokenizer_info = xgr.TokenizerInfo.from_huggingface(tokenizer)
grammar_compiler = xgr.GrammarCompiler(tokenizer_info)
compiled_grammar = grammar_compiler.compile_json_schema(schema_json)

Tijdens compilation doet XGrammar het volgende:

  1. Converteert het JSON Schema naar een Context-Free Grammar.
  2. Bouwt een Pushdown Automaton (PDA), een state machine met een stack die geneste structuren zoals {"a": {"b": {"c": ...}}} kan verwerken.
  3. Berekent vooraf welke tokens op elke grammarpositie geldig zijn. Het resultaat is de “adaptive token mask cache”.
  4. Categoriseert tokens als “context-independent” (cacheable) of “context-dependent” (moeten tijdens runtime worden gecontroleerd tegen de stack state).

[!NOTE] De XGrammar-paper rapporteert dat in zijn metingen ongeveer 99% van de tokens context-independent was (paper). Beschouw dit als benchmark-specifiek, niet als een universele ratio.

Fase 2: runtime mask generation, bij elk token

Bij elke generation step:

  1. De GrammarMatcher houdt de huidige positie in de grammar bij.
  2. Het zoekt het vooraf berekende mask op voor context-independent tokens.
  3. Het voert de PDA uit om de resterende context-dependent tokens te controleren.
  4. Het combineert deze tot een finaal bitmask, verplaatst dit naar het device van de logits en past het daar toe.

Waarom Pushdown Automata en geen regex?

Vanwege nesting. Een regular expression (een finite state machine) kan structuren zoals deze niet betrouwbaar matchen:

{ "user": { "profile": { "settings": { "theme": "dark" } } } }

Het moeilijke deel zijn de sluitende accolades }}}: je moet onthouden hoeveel accolades je hebt geopend. Een Pushdown Automaton heeft hiervoor een stack, zodat het willekeurige nesting depth kan verwerken. Daarom kan XGrammar ook Union-types, geneste objects en recursive schemas afdwingen, waar regex-based approaches tekortschieten.

Een concreet voorbeeld: een float field genereren

Wanneer het model "max_discount_percent": genereert, weet XGrammar uit het schema dat daarna een float komt. De geldige token set hangt af van de parser state en tokenizer. Aan het begin van het getal kan het mask een digit of minteken toelaten; na een digit kan het continuations toelaten zoals nog een digit, een decimaalpunt of een exponent marker.

  • Een quote, {, [, true, false of null kan dit getal niet beginnen, dus het mask blokkeert hun tokens in die state.
  • De forward pass kan een hoge probability hebben toegekend aan het token voor "fifteen". Omdat dat token dit numeric field niet kan vervolgen, verwijdert het mask het en moet het model een geldige numeric continuation kiezen.

Wat de overhead beïnvloedt

Drie redenen:

  1. Mask generation en transfer. XGrammar genereert masks op de CPU en de serving engine verplaatst ze naar het device van de logits voor in-place application. De mate van overlap hangt af van de serving implementation en workload.
  2. Caching. Het meeste validity work gebeurt tijdens compilation. Runtime bestaat grotendeels uit cache lookups.
  3. C++-implementation. Het hot path is C++, niet Python, en het mask wordt in place op de logits toegepast.

De aangehaalde benchmarks rapporteren lage overhead voor hun geteste grammars, tokenizers, hardware en workloads. Die resultaten vormen geen algemene garantie voor latency of throughput.

Een algemene request kan direct een response retourneren. Een pricing request heeft customer data en een model proposal nodig, gevolgd door een application policy check voordat de korting mag worden gerapporteerd.

Stap 1: definieer de schema’s

RouterSchema staat twee alternatives toe: customer data opvragen met FeatureLookup of tekst retourneren met GeneralResponse. Na het ophalen van de data gebruikt een afzonderlijke call PricingLogic om de analysis en proposed discount vast te leggen. Door deze responses gescheiden te houden, kan de application de data ophalen voordat zij om een proposal vraagt.

# sgr/models/schemas.py
from pydantic import BaseModel, Field
from typing import Literal, Union

# --- Phase 1: Routing (Union for branching) ---
class FeatureLookup(BaseModel):
    """Route to DB lookup if pricing context is needed."""
    rationale: str
    tool_name: Literal["fetch_user_features"] = "fetch_user_features"
    user_id: str

class GeneralResponse(BaseModel):
    """Standard response for non-pricing queries."""
    tool_name: Literal["respond"] = "respond"
    content: str

class RouterSchema(BaseModel):
    action: Union[FeatureLookup, GeneralResponse]

# --- Phase 2: Pricing Logic (Cascade for sequential reasoning) ---
class PricingLogic(BaseModel):
    """
    Structured response for dynamic pricing. The fields record an intended analysis→decision flow.
    """
    # 1. Data Analysis (Reflection)
    churn_analysis: str = Field(...,
        description="Analyze churn_probability (High > 0.7).")
    financial_analysis: str = Field(...,
        description="Analyze cart_value and profit_margin.")

    # 2. Recorded calculation; application code recomputes policy
    margin_math: str = Field(...,
        description="Calculate absolute profit: 'Cart $200 * 0.20 Margin = $40'.")

    # 3. Model-proposed decision; application code approves it.
    max_discount_percent: float = Field(...,
        description="Proposed discount percentage. Application code enforces policy.")

Stap 2: vraag een structured response op en valideer die

De client exporteert het Pydantic-model als JSON Schema, voegt dit toe aan een bestaand system message voor prompt guidance en verstuurt het als een structured-output constraint. XGrammar wordt op de server geconfigureerd; de client levert het schema voor elke request.

completed_content weigert incomplete, refused of lege responses voordat Pydantic de JSON en de velden valideert. Token-limit stops worden geweigerd, zelfs als de geretourneerde tekst toevallig parsebaar is. Deze errors worden doorgegeven aan de caller, die een error response of retry policy moet leveren; via deze paden wordt geen offer goedgekeurd.

# sgr/utils/llm_client.py
import json
from typing import TypeVar

from openai import OpenAI
from pydantic import BaseModel

T = TypeVar("T", bound=BaseModel)

def completed_content(completion) -> str:
    """Reject incomplete, refused, or empty results before JSON validation."""
    if not completion.choices:
        raise ValueError("No completion returned")
    choice = completion.choices[0]
    if choice.finish_reason != "stop" or getattr(choice.message, "refusal", None):
        raise ValueError("Completion was not successful")
    content = choice.message.content
    if not isinstance(content, str) or not content.strip():
        raise ValueError("Completion has no content")
    return content

class LLMClient:
    """Wrapper for vLLM with XGrammar-enforced structured generation."""

    def __init__(self, base_url: str = "http://localhost:8000/v1"):
        # Local vLLM commonly has no authentication. EMPTY is not authentication.
        self.client = OpenAI(base_url=base_url, api_key="EMPTY")
        self.model = self._get_available_model()

    def _get_available_model(self) -> str:
        """Auto-detect the model running on vLLM server."""
        models = self.client.models.list()
        if not models.data:
            raise RuntimeError("vLLM reported no available models")
        return models.data[0].id

    def run_sgr(self, messages: list[dict], schema_class: type[T]) -> T:
        """Run inference with Schema-Guided Response constraints.

        Uses vLLM structured outputs to constrain the JSON shape at generation time.
        """
        schema_dict = schema_class.model_json_schema()

        # Enhance system message with schema for model guidance
        enhanced_messages = messages.copy()
        if enhanced_messages and enhanced_messages[0]["role"] == "system":
            schema_json = json.dumps(schema_dict, indent=2)
            enhanced_messages[0] = {
                "role": "system",
                "content": (
                    enhanced_messages[0]["content"]
                    + f"\n\nRespond with JSON matching this schema:\n{schema_json}"
                ),
            }

        # vLLM v0.12+ structured outputs. Configure the backend on the server.
        completion = self.client.chat.completions.create(
            model=self.model,
            messages=enhanced_messages,
            temperature=0.1,  # Reduces sampling variation; it is not deterministic.
            extra_body={"structured_outputs": {"json": schema_dict}},
        )

        return schema_class.model_validate_json(completed_content(completion))

[!NOTE] In de huidige vLLM vraagt structured_outputs: {"json": schema_dict} om JSON die met het schema overeenkomt. Configureer indien nodig de structured-output-backend met de --structured-outputs-config.backend-option van de server. Dit is software enforcement in de inference server, geen hardware enforcement.

Stap 3: orkestreer de agent

De application routeert de request, haalt data op voor de geauthenticeerde caller, vraagt om een proposal, controleert dit en retourneert het resultaat. De feature store gebruikt de geauthenticeerde user_id, nooit de ID die het model voorstelt. De prompt ontvangt ook user_ltv, de geschatte customer lifetime value; deze estimate geeft het model context, maar stelt de discount limit niet vast.

Het demonstration policy wijst voorgestelde percentages buiten 0–20 af en rondt daarna af naar beneden op honderdsten van een percentagepunt. Een final discount die meer kost dan de brutowinst van het cart wordt afgewezen. approve_discount controleert vóór de berekening dat de inputs finite zijn, de cart value positief is en de margin een fractie tussen 0 en 1 is.

# sgr/agent.py
from decimal import Decimal, ROUND_DOWN

from .models.schemas import PricingLogic, RouterSchema
from .prompts.routing import build_routing_prompt
from .prompts.pricing import build_pricing_context_prompt, ASSISTANT_FETCH_MESSAGE
from .store.hybrid_store import HybridFeatureStore
from .utils.llm_client import LLMClient

def approve_discount(offer: PricingLogic, context: dict) -> Decimal:
    """Enforce the pricing policy independently of the model's explanation."""
    cart_value = Decimal(str(context["current_cart_value"]))
    margin = Decimal(str(context["cart_profit_margin"]))
    proposed = Decimal(str(offer.max_discount_percent))

    if not all(value.is_finite() for value in (cart_value, margin, proposed)):
        raise ValueError("Pricing values must be finite")
    if cart_value <= 0 or not Decimal("0") <= margin <= Decimal("1"):
        raise ValueError("Invalid pricing context")

    if not Decimal("0") <= proposed <= Decimal("20"):
        raise ValueError("Proposed discount violates pricing policy")
    # Policy rounds down to hundredths of a percentage point before approval.
    approved = proposed.quantize(Decimal("0.01"), rounding=ROUND_DOWN)
    gross_profit = cart_value * margin
    discount_cost = cart_value * approved / Decimal("100")
    policy_cap = min(margin * Decimal("100"), Decimal("20"))
    if not Decimal("0") <= approved <= policy_cap or discount_cost > gross_profit:
        raise ValueError("Proposed discount violates pricing policy")

    return approved

def pricing_agent(user_query: str, user_id: str) -> str:
    """Integrate routing, context, and pricing; user_id is caller-authenticated."""

    llm = LLMClient()
    feature_store = HybridFeatureStore()

    # Build conversation history
    history = [
        {"role": "system", "content": build_routing_prompt(user_id)},
        {"role": "user", "content": user_query},
    ]

    # --- Phase 1: Routing (Uses RouterSchema) ---
    print(f"🤖 Processing: '{user_query}' for {user_id}")
    decision = llm.run_sgr(history, RouterSchema)
    print(f"📍 Routing decision: {decision.action.tool_name}")

    if decision.action.tool_name == "respond":
        return decision.action.content

    # --- Phase 2: Context Retrieval ---
    if decision.action.tool_name == "fetch_user_features":
        print(f"🔍 Fetching features for {user_id}...")
        context = feature_store.get_user_context(user_id)

        if not context:
            return "Error: User profile not found."

        print(f"   [Data] LTV: ${context.get('user_ltv')} | "
              f"Margin: {context.get('cart_profit_margin', 0) * 100}%")

        # Inject context into conversation
        history.append({"role": "assistant", "content": ASSISTANT_FETCH_MESSAGE})
        history.append({
            "role": "user",
            "content": build_pricing_context_prompt(
                churn_prob=context.get("churn_probability", 0.5),
                cart_val=context.get("current_cart_value", 100),
                margin=context.get("cart_profit_margin", 0.2),
                user_ltv=context.get("user_ltv", 0),
            ),
        })

        # --- Phase 3: model proposal, then deterministic policy enforcement ---
        print("🧠 Proposing Offer (Schema Enforced)...")
        offer = llm.run_sgr(history, PricingLogic)
        try:
            approved_discount = approve_discount(offer, context)
        except ValueError:
            return "No discount approved: the proposal failed the pricing policy."

        # Audit log: reasoning is inspectable; pricing is application-enforced.
        print(f"   [Audit] Math: {offer.margin_math}")
        print(f"   [Audit] Approved Discount: {approved_discount}%")

        return (
            f"Illustrative approved discount: {approved_discount}%. "
            "No coupon has been issued."
        )

    return "I'm sorry, I couldn't process your request."

if __name__ == "__main__":
    response = pricing_agent("I want a discount or I'm leaving!", "user_102")
    print(f"\n💬 Final Reply: {response}")

Een proposal van 15% op een cart van $200 met 20% margin retourneert 15.00 vanuit de policy function. De application rapporteert dat percentage zonder te doen alsof zij een coupon uitgeeft. Een boundary test gebruikt een margin van 0.12346, oftewel 12.346%. Een 12.346-proposal wordt naar beneden afgerond op 12.34 voordat de final value wordt gecontroleerd. Afronden naar 12.35 na approval zou de margin overschrijden.

Checks vóór een live integration

Byte zegt

Een proposal kan geldige JSON bevatten en toch een korting bevatten die groter is dan de margin. De policy function controleert het getal, ook als de explanation overtuigend klinkt.

Schema design

  1. Orden fields volgens de bedoelde reasoning flow. Beschouw die volgorde als documentatie, tenzij afzonderlijke calls of application checks haar afdwingen.
  2. Schrijf beschrijvende Field-descriptions. Ze sturen de aandacht van het model net zo sterk als de field name.
  3. Beperk met Literal en Annotated. Gebruik Literal["a", "b"] voor enums en Annotated[int, Ge(1), Le(10)] voor bounds.
  4. Houd schemas focused. Gebruik één schema per reasoning phase en composeer daarna met meerdere calls.

vLLM-configuratie

  1. Gebruik een lage temperature (0.1–0.3) om sampling variation te beperken. Zet voor repeatable tests het model en de serving configuration vast, gebruik de deterministic mode van de server als die beschikbaar is en verifieer het resultaat.
  2. Leg de task en schema fields uit in de prompt, zoals de client hierboven doet. Prompt guidance en decoder constraints hebben complementaire rollen.
  3. Meet token usage tegen dezelfde prompt, hetzelfde model, hetzelfde schema en dezelfde task. SGR kan meer of minder tokens genereren dan een free-form CoT-response.

Production considerations

  1. Versioneer je schemas op dezelfde manier als je APIs.
  2. Ook met SGR moeten network- en servererrors graceful worden afgehandeld.
  3. Leg de proposal en policy decision afzonderlijk vast voor debugging, met inachtneming van je regels voor dataretentie en redactie.
  4. Bereken prices, limits, permissions en andere semantic rules opnieuw in application code voordat je ze gebruikt; test boundary values die het schema alleen niet kan afwijzen.

De volgende test

Begin met de discount limit en een incomplete completion. De offline check dekt beide gevallen, maar kan niet bepalen of een model een echte klant correct routeert of de margin accuraat uitlegt. Houd voor een live evaluation het model, de prompts, het schema en de serving settings constant. Tel incomplete results, schema failures, routing mistakes en policy rejections afzonderlijk voordat je cost of task accuracy vergelijkt.
