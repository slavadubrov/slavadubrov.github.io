LoRAX Serving Guide: LoRA-adapters op Kubernetes op schaal

Eén base model en veel LoRA-adapters creëren een ongebruikelijk servingprobleem. De base weights worden gedeeld, maar voor elk request kan een andere set adapter weights nodig zijn. Een conventioneel ontwerp met één deployment per variant verspilt GPU-geheugen wanneer de meeste varianten inactief zijn.

LoRAX adresseert die long tail. Het laadt adapters on demand, batcht requests voor verschillende adapters en verplaatst adapter weights tussen GPU- en CPU-geheugen. De aantrekkelijke headline luidt: “duizenden fine-tuned models op één GPU.” De technische vraag is specifieker: gegeven je actieve adapterset, arrival pattern en latencydoelstelling, levert exchange scheduling voldoende voordeel op om een extra serving runtime te rechtvaardigen?

Deze guide is bedoeld voor inference- en platform engineers die veel LoRA-varianten vanuit één base model moeten serven. Je leert hoe je de gedocumenteerde APIs test, de working set dimensioneert en de starter Helm-chart omzet in een expliciet productieplan.

Samenvatting. Kies LoRAX wanneer veel compatibele LoRA-adapters één base model delen en traffic schaars of long-tailed is. De capaciteit hangt af van de actieve working set, niet van de catalogusgrootte. Pin de runtime, authenticatie en allowlist adapter-ID’s, voeg duurzame artifact caching en probes toe, routeer voor cache-locality en benchmark cold en warm paths afzonderlijk.

Het servingprobleem is de working set

LoRA bevriest een base model en leert low-rank updates voor geselecteerde weight matrices. De resulterende adapter is doorgaans veel kleiner dan een volledig checkpoint, maar de grootte hangt nog steeds af van rank, target modules, het aantal lagen en dtype. Vaste claims zoals “elke adapter is 100 MB” zijn slechte input voor capacity planning.

Maak voor serving onderscheid tussen drie grootheden:

  • Catalogusgrootte: elke adapter die een platform uit storage kan resolven
  • Actieve working set: adapters die binnen het cache-retention window requests ontvangen
  • Concurrent set: adapters die op hetzelfde moment in batches vertegenwoordigd zijn

Een catalogus kan duizenden adapters bevatten zonder dat duizenden adapters in VRAM passen. Wat telt, is hoe vaak de actieve set verandert, hoe groot die adapters zijn en of requests voor verschillende adapters nuttige batches kunnen delen.

LoRAX combineert vier mechanismen:

  1. Het base model blijft resident voor alle compatibele adapters.
  2. Een request noemt een adapter die vanuit Hugging Face, Predibase of een filesystem kan worden geresolved.
  3. Adapter exchange scheduling prefetcht en offloadt weights tussen GPU- en CPU-geheugen.
  4. Heterogeneous continuous batching groepeert requests voor verschillende adapters.

De LoRAX-projectrapporten dat heterogeneous batching throughput en latency in zijn benchmarks vrijwel constant houdt naarmate het aantal concurrerende adapters groeit. Beschouw dit vendorresultaat als een hypothese voor jouw workload. Promptlengte, outputlengte, rank, target modules, batch occupancy, cache churn en GPU-generatie kunnen het resultaat veranderen.

De herstelde chart hieronder is afkomstig uit Predibase’s LoRAX launch report van november 2023. Predibase benchmarkte Llama 2 7B met queries verdeeld over 1 tot 128 adapters op één NVIDIA A10G. Deze chart toont de kostenvergelijking voor 1 tot 32 adapters bij het verwerken van één miljoen tokens, gelijkmatig verdeeld over de adapters.

Wanneer LoRAX een plausibele keuze is

LoRAX verdient een benchmark wanneer aan al deze voorwaarden wordt voldaan:

  • adapters zijn getraind tegen hetzelfde ondersteunde base model en dezelfde tokenizer contract
  • traffic omvat veel adapters, met een betekenisvolle long tail
  • een cold adapter on demand laden heeft de voorkeur boven er een deployment voor reserveren
  • tenant- of task-routing bestaat al aan de application boundary
  • het team kan een gespecialiseerde inference runtime en het cachegedrag daarvan beheren

Typische gevallen zijn tenant-specifieke assistants, veel domainvarianten en online experiments die één base checkpoint delen.

LoRAX past minder goed wanneer enkele adapters het grootste deel van de traffic verwerken of wanneer de models geen base delen. De fit is ook minder sterk wanneer harde latencydoelstellingen geen cold loads verdragen of wanneer het platform niet veilig kan bepalen welke artifacts de server laadt. Een standaard vLLM- of TGI-deployment met een vaste adapterset kan in die gevallen eenvoudiger zijn.

Gebruik Kubernetes niet alleen omdat de catalogus groot is. Bewijs eerst de runtime- en adaptercompatibiliteit op één GPU.

Probeer lokaal één base en twee adapters

De LoRAX README beveelt de prebuilt container aan. Gebruik in een echte omgeving een immutable image digest. main wordt hier alleen getoond omdat dit de gedocumenteerde quick-start tag van de repository is. Deze voorbeelden zijn illustratief en niet lokaal geverifieerd in deze checkout. Controleer ze aan de hand van de image- en dependencyversies die je implementeert.

mkdir -p data

docker run --rm --gpus all --shm-size 1g \
    -p 8080:80 \
    -v "$PWD/data:/data" \
    ghcr.io/predibase/lorax:main \
    --model-id mistralai/Mistral-7B-Instruct-v0.1

De gedocumenteerde minimumvereisten zijn Linux, Docker, een NVIDIA GPU van Ampere of nieuwer en drivers die compatibel zijn met CUDA 11.8. Modellicenties en gated repositories kunnen ook een Hugging Face-token vereisen.

Start met het base model:

curl http://127.0.0.1:8080/generate \
    -H 'Content-Type: application/json' \
    -d '{
      "inputs": "[INST] Give one reason to measure cold-adapter latency. [/INST]",
      "parameters": {"max_new_tokens": 64}
    }'

Stuur vervolgens een compatibele adapter:

curl http://127.0.0.1:8080/generate \
    -H 'Content-Type: application/json' \
    -d '{
      "inputs": "[INST] Solve: Natalia sold 48 clips in April and half as many in May. What is the total? [/INST]",
      "parameters": {
        "max_new_tokens": 64,
        "adapter_id": "vineetsharma/qlora-adapter-Mistral-7B-Instruct-v0.1-gsm8k"
      }
    }'

Het eerste request kan de adapter downloaden en laden. Latere requests kunnen gebruikmaken van gecachte artifacts en residente weights. Leg beide paths vast. Eén warm request zegt weinig over long-tailgedrag.

Gebruik een OpenAI-compatible client

LoRAX biedt een OpenAI-compatible chat-endpoint. Het veld model identificeert de adapter:

from openai import OpenAI


client = OpenAI(
    api_key="EMPTY",
    base_url="http://127.0.0.1:8080/v1",
)

response = client.chat.completions.create(
    model="alignment-handbook/zephyr-7b-dpo-lora",
    messages=[
        {"role": "user", "content": "Explain cache locality in two sentences."},
    ],
    max_tokens=100,
)

print(response.choices[0].message.content)

De server vereist standaard geen API key. Dat is handig voor localhost, maar onveilig voor een configuratie die aan het Internet wordt blootgesteld. Plaats authentication, tenant authorization, quotas en adapter allowlisting ervoor.

Definieer een compatibility gate

Controleer minimaal het volgende voordat een adapter in de catalogus wordt opgenomen:

  • gedeclareerd base model en revision
  • compatibiliteit van tokenizer en chat template
  • LoRA-rank en target modules die door de runtime worden ondersteund
  • artifactformaat en tensorshapes
  • licentie, provenance en integrity digest
  • een kleine suite met behavioral en regression tests

Wijs incompatibele artifacts af tijdens registration, niet bij het eerste request van een gebruiker.

Begrijp residency voordat je implementeert

Het base model gebruikt het grootste vaste aandeel van het GPU-geheugen. Adapter weights, KV cache, batch workspace en runtime kernels concurreren om de resterende ruimte. CPU-RAM kan offloaded adapters bevatten, terwijl /data gedownloade artifacts opslaat.

Dit zijn geen onderling uitwisselbare tiers. Een disk- of Hub-artifact moet worden gelezen en gematerialiseerd voordat het een CPU- of GPU-resident adapter wordt. Meet de transities afzonderlijk:

PadWat het omvatTe registreren metric
GPU-hitAdapter is al residentqueuetijd en time to first token
CPU-hitTransfer of rematerialization naar GPUadapter-load delay en end-to-end latency
Artifact-hitLezen uit lokale /data cacheread/load delay en cachebytes

Capacity planning moet de echte adapter-popularity distribution replayen. Uniform random adapter-ID’s creëren een ander cacheprobleem dan een Zipf-achtige tenant-workload.

Patch de lacunes expliciet

Het huidige chart-template hard-codeert emptyDir-volumes en gewone environmentwaarden. Een geharde deployment heeft daarom een reviewed chart fork, post-render patch of manifestlaag op hoger niveau nodig om het volgende toe te voegen:

  • een PersistentVolumeClaim of node-local artifact cache gemount op /data
  • een Secret reference voor Hub-credentials
  • een startup probe vóór een agressieve liveness probe
  • pod disruption policy en topology spread voor meerdere replicas
  • NetworkPolicy, beperkingen voor service accounts en een authenticated gateway
  • pinning van image digests en integrity checks voor artifacts

Plaats een Hub-token niet rechtstreeks in een gecommitte values file. Twee replicas bieden alleen nuttige high availability als beide het base model kunnen laden. De router moet bovendien voorkomen dat elke cold adapter naar beide pods wordt gestuurd.

Routeer voor cache-locality

Round-robin balancing kan elke replica in een cold cache veranderen. Een nuttige router koppelt een toegestane adapter-ID via hash of een andere stabiele regel aan één replica. Houd een failoverpad aan voor momenten waarop die replica niet beschikbaar is.

De routing key moet afkomstig zijn uit geauthenticeerde application state, niet uit een willekeurige publieke URL-parameter. Anders kan een caller remote downloads afdwingen, caches laten churnen of private adapternamen onderzoeken.

LoRAX of vLLM?

De huidige vLLM-documentatie beschrijft LoRA-modules die bij startup worden gedeclareerd en dynamic loading via endpoints of resolver plugins. De documentatie waarschuwt dat het runtime updaten van adapters securityrisico’s heeft en buiten een geïsoleerde, vertrouwde omgeving niet in productie moet worden gebruikt.

De nuttige vergelijking is operationeel, niet numeriek:

VraagLoRAXvLLM
Hoe worden long-tail adapters ontdekt?Adapter-ID kan requests naar Hugging Face-, Predibase- of filesystem-artifacts resolvenStatische modules, dynamic management endpoints of resolver plugins
Hoe wordt residency beheerd?Expliciete adapter exchange scheduling tussen GPU en CPUGeconfigureerde actieve en CPU LoRA-limieten plus resolvergedrag
Wat is de requestinterface?TGI-stijl /generate, Python client en OpenAI-compatible chatOpenAI-compatible serving en native Python APIs
Wat moet de keuze bepalen?Cold/warm latency, cache churn, throughput van heterogeneous batches en operational fitDezelfde workload replay en operationele criteria

Vermijd regels zoals “LoRAX voor 1.000 adapters, vLLM voor tien.” Alleen de catalogusgrootte bepaalt de performance niet. Benchmark beide met dezelfde base, adapters, prompts, ranks, arrival trace en hardware.

Een production acceptance test

Voer voordat je de catalogus uitbreidt een replay uit met:

  1. Een vaste hot set om warm throughput en latency vast te stellen.
  2. Een long-tailverdeling om CPU- en artifact-cachehits te meten.
  3. Een burst van nog niet eerder gebruikte maar toegestane adapters.
  4. Pod replacement om base- en adapter recovery te meten.
  5. Eén onbeschikbare of corrupte adapter om isolation en fallback te verifiëren.
  6. Concurrent tenants om authentication, quotas en metric labels te verifiëren.

Volg deze metrics:

  • request rate
  • queuetijd
  • time to first token
  • inter-token latency
  • totale latency
  • adapter-loadtijd
  • cache-hitklasse
  • GPU-geheugen
  • CPU-geheugen
  • gedownloade bytes
  • failures per reden

Zet adapter-ID’s niet in unbounded metric labels. Koppel ze aan gecontroleerde dimensies of sampled traces.

Definieer acceptance thresholds vóór de test. Stel een maximale error rate voor de cold path en een warm P99-doel vast. Stel ook een cache-hitdoel vast voor de waargenomen popularity distribution en een recovery-time objective na podverlies.

Conclusie

LoRAX verandert veel compatibele fine-tunes van een fleet met kopieën van het base model in een adapter-placementprobleem. Dat kan een sterk ontwerp zijn voor long-tailworkloads, maar het maakt kosten of latency niet per definitie vlak. De actieve working set, exchange path, batchmix en storage layer bepalen nog steeds het resultaat.

Bewijs die mechanismen eerst op één GPU. Neem daarna Kubernetes serieus: pin artifacts, behoud de cache, bescherm credentials, autoriseer adapters, routeer voor locality en meet elke residency path. Als LoRAX onder dezelfde replay beter presteert dan een actuele vLLM-configuratie, is de deploymentbeslissing met bewijs onderbouwd.
