AI agent runtime voor langdurige taken: sessions en checkpoints

Viacheslav Dubrov

2026-05-26 · Bijgewerkt 2026-08-01 · 40 min · AI-agenten

Automatische vertaling Dit artikel is automatisch vertaald vanuit de oorspronkelijke Engelse versie.

In de vorige vier posts ging het over wat er binnen één turn gebeurt: reasoning loops kiezen de volgende actie, memory levert de state die die turn leest, tool use bepaalt welke acties de agent kan uitvoeren, en security bepaalt welke daarvan mogen worden uitgevoerd. Dit artikel behandelt de laag onder alle vier: de runtime die een run tijdens lange sessions en na process failures actief houdt.

Een agent-run kan uren duren, terwijl het worker process op elk moment kan herstarten. Het model kiest nog steeds de volgende actie, maar de runtime moet state behouden, de uitvoering aansturen en herstellen van een failure midden in een tool call. Deze post definieert de runtime boundary. Deel 6 behandelt vervolgens het onderdeel daarin dat beslissingen neemt — de harness. Daar worden memory, tool contracts en permission checks niet langer als drie afzonderlijke onderwerpen behandeld, maar als één programma.

TL;DR

Een langlopende agent heeft vijf expliciet geplaatste componenten nodig: een durable session log, de harness die de loop aanstuurt, een sandbox, een checkpoint store en een trace. Een queue plus worker plus PostgreSQL checkpointer is voor de meeste teams de juiste default. Als je niet kunt aangeven welke component eigenaar is van elk van de vijf, is de agent nog een prototype.

Wat is een AI-agent-runtime?

Een AI-agent-runtime is de infrastructuurlaag die een agent die tools gebruikt actief, geïsoleerd, observeerbaar en hervatbaar houdt nadat de model call is beëindigd. De runtime beheert session state, tool execution, checkpoints, secrets, traces, cost limits en deployment shape. Het model kiest de volgende actie; de runtime bepaalt waar die actie wordt uitgevoerd, hoe die wordt vastgelegd en hoe de run na een failure wordt hervat. De harness bepaalt of de actie is toegestaan. De harness is geen storage layer; het is het programma dat op deze componenten steunt en staat daarom in de onderstaande tabel, omdat ook die component een plek moet krijgen.

Vier van die vijf — session, sandbox, checkpoint, trace — slaan state op of beperken de execution. De harness is degene die beslist; daar komen alle beslissingen over memory, tool-contracten en permissions samen. In dit artikel behandelen we die als één box en beschrijven we waarop die steunt. Part 6 opent de box en deelt dezelfde vijf opnieuw in: één component die beslist en vier waarop die draait.

Lange runs doorbreken aannames over stateless processes

Byte says

Ik bewaarde het runlog in het geheugen van de worker en dat werkte wekenlang. Daarna verving een reguliere deploy de worker midden in de taak. De volledige runhistorie verdween ermee.

Een stateless chat-endpoint kan request-state in één process bijhouden en die na de response weggooien. Een lange agent-run doorkruist worker-restarts, deploys, context-resets en approval-pauses. Het worker-process kan daardoor niet langer de source of truth zijn.

Het OpenAI Codex-team rapporteert in de harness engineering write-up hoe lang deze runs worden:

“We regularly see single Codex runs work on a single task for upwards of six hours (often while the humans are sleeping).”

Het engineeringteam van Anthropic beschrijft het bijbehorende state-probleem in Effective harnesses for long-running agents:

“The core challenge of long-running agents is that they must work in discrete sessions, and each new session begins with no memory of what came before.”

Beide observaties impliceren hetzelfde runtime-design: persist state buiten de worker en maak workers vervangbaar.

De session moet buiten het worker-process leven. Een durable store registreert model calls, tool results en approvals, zodat een andere worker na een crash kan hervatten op het laatste veilige punt. Checkpoints laten de runtime ook een nieuwe model session starten wanneer het context window vol raakt, zonder de volledige history opnieuw af te spelen. In Anthropics formulering worden harness-instances disposable en restartable; durable state leeft elders.

Vijf primitives om te definiëren voordat je shipt

Anthropics Scaling Managed Agents biedt een bruikbare vocabulary voor vijf runtime-verantwoordelijkheden. De harness stuurt de agent vooruit, terwijl de session registreert wat die heeft gedaan en de sandbox commands uitvoert. De checkpoint geeft de volgende worker een resume point; de trace bewaart evidence voor latere debugging. Een implementatie kan components samenvoegen, maar de verantwoordelijkheden en failure boundaries moeten nog steeds benoemd worden.

Session. Een append-only log van alles wat er is gebeurd: model calls, tool calls, results, errors en approvals.

Het woord is overloaded, dus baken drie spans af die session worden genoemd. Een thread is de conversatie van een gebruiker over meerdere dagen. Dit is de langst levende van de drie, en LangGraph houdt die bij met een thread_id.

Een model session is de kortste: één ononderbroken periode van model context. Compaction — de stap die het window samenvat zodat het werk kan doorgaan — verlengt een model session in plaats van die te beëindigen. Een restart of een bewust gekozen fresh start beëindigt die. Part 6 gebruikt “model session” in die betekenis.

In dit artikel betekent “session” de durable log van één run. Die staat tussen de andere twee in: meerdere model sessions schrijven naar één log, en één thread bouwt meerdere logs op. Recovery is wake(sessionId) → getSession(id) → resume from last event.

In LangGraph maakt herstel gebruik van een thread_id plus een Postgres checkpointer (zie LangGraph persistence). De OpenAI Agents SDK levert tien ingebouwde session backends, waaronder SQLiteSession, RedisSession, SQLAlchemySession, MongoDBSession en EncryptedSession (zie de Sessions docs).

Harness. De orchestration loop en het enige primitive hier dat beslissingen neemt. De harness bouwt de prompt op uit het geheugen, roept het model aan, controleert de voorgestelde tool call aan de hand van de permission rules, dispatcht wat is toegestaan, schrijft resultaten terug naar de session, past retry rules toe en bepaalt of de taak is voltooid. Elk van deze stappen bevat een aanname over wat het model niet zelfstandig kan doen. Anthropic benadrukt dat rechtstreeks — het wordt geciteerd in het onderstaande gedeelte over failure modes, dat grotendeels gaat over wat er gebeurt wanneer die aannames verouderd raken.

Het Codex-team van OpenAI noemt dit harness engineering: software schrijven vereist nog steeds engineering-inspanning, maar een groter deel daarvan gaat nu naar de scaffolding dan naar de code zelf. LangGraph’s CompiledStateGraph, LangChain’s Deep Agents en het create_deep_agent-entrypoint daarvan, en Claude Code zelf zijn in deze betekenis allemaal harnesses.

Sandbox. De geïsoleerde execution environment waarin commands daadwerkelijk worden uitgevoerd. De pagina over sandbox concepts van de OpenAI Agents SDK trekt de grens helder:

“De outer runtime beheert nog steeds approvals, tracing, handoffs en resume bookkeeping. De sandbox session beheert commands, file changes en environment isolation.”

Met “outer runtime” wordt daar de harness samen met de state stores bedoeld. In de terminologie van deze serie zijn approvals en handoffs harness-beslissingen (Part 4 en Part 6); tracing en resume bookkeeping zijn de session- en checkpoint-primitives.

Sandboxes verschillen in hun levensduur en in wat ze tussen runs onthouden. De eenvoudigste vorm is fresh ephemeral: start er één voor een enkele taak, vernietig hem wanneer de taak eindigt en betaal bij elke run de cold-start-kosten.

Persistent paused-sandboxes bewaren het filesystem en een memory snapshot tussen runs. De volgende resume kan daardoor een volledige boot vermijden. Snapshot or fork maakt een copy-on-write-image van een voorbereide parent, zodat veel taken geïnstalleerde dependencies en warm caches delen zonder hun writable state te delen.

Per-worktree-sandboxes geven elke taak een eigen workspace en observability stack. Afzonderlijke logs, metrics en traces maken het mogelijk één run te debuggen zonder dat de state ervan naar een andere run lekt. De provider table verderop in dit artikel vergelijkt cold-start- en persistence-gedrag.

Checkpoint. Resumable state.

LangGraph’s PostgresSaver schrijft bij elke super-stepgrens een Checkpoint. Een super-step is één ronde van de graph: één node of een batch die parallel is uitgevoerd. Writes per task gaan naar checkpoint_writes, zodat succesvolle node-outputs niet opnieuw worden berekend wanneer een sibling faalt.

Een checkpoint is een gewone dict (v, id, ts, channel_values, channel_versions, versions_seen, updated_channels). LangGraph serialiseert deze met zijn op msgpack gebaseerde JsonPlusSerializer in plaats van JSON. datetime, set, Decimal en dataclasses kunnen allemaal round-trip worden geserialiseerd. Het format staat beschreven op de PyPI-pagina van langgraph-checkpoint-postgres en in de LangGraph checkpoints reference.

StateSnapshot is de afzonderlijke, uitgebreidere view die graph.get_state() boven op een checkpoint opbouwt. Dat is het object waarvan de .values later de debug bundle dumpt.

Trace. De replay- en debuglaag. Elke model call, tool call en sub-agentstap wordt een span met timing, inputs, outputs, tokenaantallen en kosten. Wanneer een run van zes uur mislukt, lees je de trace om te achterhalen wat er misging. De terminaloutput van de run is dan allang verdwenen. De GenAI semantic conventions van OpenTelemetry standaardiseren de attribuutnamen: welk model, welke provider, hoeveel tokens, welke conversatie en welke workflow. Naar een OTLP-compatibele bestemming die deze conventies ondersteunt, kan dezelfde instrumentation de trace exporteren naar systemen zoals Tempo, Jaeger, Honeycomb of LangSmith, al kunnen backend adapters of destinationspecifieke configuratie nog steeds nodig zijn.

Policy en secrets doorkruisen de primitives

Twee grenzen doorkruisen alle vijf primitives. Ze vormen de runtimeversie van het security-argument uit Part 4. De permission decision zelf hoort bij de harness; hieronder staat waar de machinery die deze beslissing afdwingt en van input voorziet fysiek is ondergebracht.

Permission enforcement

De permission ladder uit Part 4 moet ergens worden uitgevoerd. De check wordt vóór elke tool call uitgevoerd en bepaalt of die wordt toegestaan. In production zijn twee patronen gebruikelijk. Deep Agents laat elke subagent declareren welke file paths deze mag lezen of schrijven, waarna de middleware alles buiten die declaratie blokkeert. Anthropic Managed Agents routeert elke tool call via een Model Context Protocol (MCP) proxy, zodat de proxy de permissions afdwingt in plaats van de agentcode. Wanneer voor een gevoelige call human approval nodig is, pauzeren LangGraph’s interrupt() en de approval hook van Deep Agents de graph totdat iemand toestemming geeft.

Secret broker

Het model mag geen long-lived secrets zien, en de sandbox meestal ook niet. Het patroon van Managed Agents is het patroon om over te nemen:

“Voor Git gebruiken we de access token van elke repository om de repo tijdens de initialisatie van de sandbox te clonen en deze aan de lokale git remote te koppelen. Git push en pull werken vanuit de sandbox zonder dat de agent de token ooit zelf verwerkt. Voor custom tools ondersteunen we MCP en slaan we OAuth-tokens op in een secure vault. Claude roept MCP-tools aan via een dedicated proxy; deze proxy ontvangt een token die aan de sessie is gekoppeld. … De harness krijgt nooit kennis van credentials.”

In de market-analyst-agent-referentiestack — een kleine LangGraph-agent die marktdata ophaalt en een analistenrapport schrijft, opgebouwd in deze serie — beheert de MCP-sidecar de API-sleutels van de data-provider en stelt deze alleen het tool-oppervlak beschikbaar aan de LangGraph-worker. In het lokale compose-bestand lezen beide containers dezelfde .env; dat is een development-shortcut en niet het aanbevolen patroon. In productie komt de omgeving van de sidecar uit een secret store — Docker secrets of HashiCorp Vault — waar de worker geen toegang toe heeft. De worker roept de tool vervolgens aan zonder ooit de credential erachter te bezitten.

Controleer de plaatsing

Een praktische sanity check is om elk component op te schrijven en te bepalen welke van de vijf primitives het implementeert. Postgres kan bijvoorbeeld session management en checkpointing verzorgen. De worker-container is de harness. Een service zoals Daytona, Modal of E2B levert de sandbox, terwijl Tempo of LangSmith de trace opslaat.

Bekijk vervolgens gekoppelde failures. Als twee primitives in hetzelfde proces draaien, legt één crash beide stil. Als ze een credential delen, kan één leak beide boundaries overschrijden. Veelvoorkomende voorbeelden zijn een worker die ook de trace-durability beheert, of een sidecar-token dat ook toegang geeft tot de checkpoint-database.

Failure modes van een production AI-agent-runtime

De runtime beheert retries, herstelt eerder werk, isoleert workspaces en handhaaft budgetten. Naarmate runs zich over meerdere workers en context windows uitstrekken, verschuiven de failures naar state, dubbele side effects, sandbox-drift en budgetoverschrijdingen.

De failures vallen in vier groepen:

  • Failures in de outputkwaliteit: de agent verklaart het werk voltooid voordat het daadwerkelijk klaar is, vergeet wat hij heeft gedaan na een reset van het context window, of vertrouwt op zijn eigen self-evaluation en levert kapotte output op.
  • Failures in kostenbeheersing: de agent blijft steken in een retry-loop of verbruikt het token- of tool-call-budget zonder iets bruikbaars te produceren.
  • State- en crashfailures: workspaces driften doordat de ene run bestanden aanpast die door een andere run worden beheerd, tool calls worden meer dan één keer uitgevoerd doordat retries ze opnieuw afspelen, of werk gaat verloren wanneer een worker tussen twee events uitvalt.
  • Failures door het context window: het model vat samen en stopt voortijdig omdat het denkt dat de ruimte opraakt, ook wanneer het window nog voldoende headroom heeft.

De tabel koppelt elke failure aan een mitigation, de basis voor de aanbeveling en de runtime-hook die deze afdwingt. Modelspecifiek gedrag kan veranderen; beschouw observaties over vendors daarom als aanleiding om de aanname opnieuw te testen, niet als permanente regels.

Twee ideeën liggen aan de basis van de meeste rijen. Anthropic over harness-staleness in Harness design for long-running application development:

“Every component in a harness encodes an assumption about what the model can’t do on its own, and those assumptions are worth stress testing, both because they may be incorrect, and because they can quickly go stale as models improve.”

Vercel over het verwante probleem van te veel tools die te veel aannames vastleggen, in We removed 80% of our agent’s tools:

“We deleted most of it and stripped the agent down to a single tool: execute arbitrary bash commands. We call this a file system agent.”

Het citaat beschrijft de bash-core; de agent die Vercel uitbracht behield twee tools, ExecuteCommand en ExecuteSQL, tegenover vijftien daarvoor. Part 3 behandelt het volledige voor-en-na-overzicht. Hun gerapporteerde resultaat over vijf representatieve queries: success ging van 4/5 naar 5/5, en het slechtste geval daalde van 724 s / 100 steps / 145,463 tokens (failed) naar 141 s / 19 steps / 67,483 tokens (succeeded). Die rij met het slechtste geval is de opvallende; gemiddeld over de vijf queries bedroeg de tokenbesparing 37%. De les is niet: “verwijder je tools.” Het punt is dat elke primitive in je runtime, inclusief het tool surface, een halfwaardetijd heeft. Test de aanname opnieuw wanneer het model verandert.

Cognition zag dezelfde bewegende target bij de session length met Sonnet 4.5. In Rebuilding Devin for Claude Sonnet 4.5 beschrijven ze een model dat proactief SUMMARY.md / CHANGELOG.md wegschrijft zodra het merkt dat de context uitgeput raakt, maar onderschat hoeveel tokens het nog over heeft. Hun oplossing was om de context van 1M tokens in te schakelen en het gebruik te begrenzen op 200k, zodat het model blijft denken dat het nog headroom heeft. Dat was een beta flag toen ze het artikel schreven.

De current context-window documentation van Anthropic vermeldt Sonnet 4.5 volgens de stand van augustus 2026 nog steeds met 200k. Het venster van 1M wordt standaard geleverd, zonder beta header, op Opus 4.6 en later en Sonnet 4.6 en later. De cap is het deel om in de gaten te houden. Die bestaat alleen omdat Sonnet 4.5 zijn resterende context verkeerd inschat; zodra een model dat niet meer doet, is de cap geen fix meer maar een kunstmatig plafond. Sinds Cognition dat artikel schreef, zijn er meer dan één modelgeneratie verstreken; controleer de cijfers opnieuw aan de hand van de actuele modellijst voordat je dit verder toepast.

Het harness-team van OpenAI heeft de versie in één regel: “Humans steer. Agents execute.” Wanneer iets faalt, is de nuttige vraag welke capability ontbreekt en hoe je die capability zowel legible als enforceable maakt voor de agent.

De gezonde run-lifecycle

Een goed verlopende run is saai. Het is een keten van kleine, herstelbare stappen, waarbij elke stap het resultaat naar durable storage schrijft voordat de volgende begint.

Elk resultaat schrijven voordat de volgende stap begint, beperkt de schade bij een crash. Bij een failure gaat alleen de step die op dat moment wordt uitgevoerd verloren, waarna de volgende worker verdergaat vanaf de laatst voltooide step in plaats van het volledige request opnieuw te starten.

  1. Start vanuit een nieuwe sessie of hervat een bestaande sessie. Bij hervatten mount je de workspace vanuit de laatst bekende toestand, lees je eventuele progress files die de vorige poging heeft achtergelaten (PROGRESS.md, feature-list.json) en laad je het laatste checkpoint uit de database. Hier geeft de harness de agent alles wat de vorige worker in het geheugen had voordat die uitviel.
  2. Plan voordat er tool calls worden uitgevoerd. Leg vast hoe ‘klaar’ eruitziet, hoeveel de run mag besteden, welke tools de agent mag aanroepen en waardoor de run vroegtijdig moet stoppen. Deze planwaarden worden runtime checks; zonder die waarden heeft de uitvoering niets om tegenwicht te bieden.
  3. Voer één tool call per keer uit. De permission check van de harness bepaalt of de call wordt toegestaan, waarna de harness deze dispatcht, het resultaat vastlegt en één event in de session log schrijft. Eén stap, één event. Een crash tussen events is herstelbaar, omdat de log — niet het geheugen van de worker — de source of truth is.
  4. Maak checkpoints op super-step boundaries, of na elk event in een eenvoudigere harness. Persist de graph state, de workspace diff en verwijzingen naar geproduceerde artifacts. Dit checkpoint wordt bij de volgende resume door stap 1 gelezen. Ontbreekt het checkpoint of is het verouderd, dan valt recovery terug op het vanaf nul replayen van de volledige session log, wat veel trager is.
  5. Evalueer de artifacts wanneer de agent denkt dat het werk klaar is: tests, een evaluator in een fresh context, schema validation en browser checks. Als de check slaagt, eindigt de run succesvol. Als de check faalt, wordt de run hervat vanaf het laatste schone checkpoint, met de foutmelding toegevoegd aan de context, en probeert de agent het opnieuw.

Geen enkele stap in die lijst vereist dat de agent tussen runs iets onthoudt. De state staat in de sessie en het checkpoint, en de agent leest die bij elke resume opnieuw in.

Elke tool met side effects heeft een idempotency key nodig die is afgeleid van het session ID en tool-call ID en vóór het uitvoeren van de side effect wordt opgeslagen. send_email(session_id, tool_call_id, message_hash). create_pr(session_id, tool_call_id, branch_name). charge_customer(session_id, tool_call_id, invoice_id). At-least-once execution is de default in queues en workflow engines, dus duplicaten zullen voorkomen. Als een tool bij herhaling echte schade kan veroorzaken en je deze niet op basis van een key kunt dedupliceren, is de tool nog niet klaar voor agents.

Evaluation moet ook evidence buiten de producerende context omvatten. Een evaluator in een fresh context vermindert shared-context bias, terwijl tests, lints, browser checks en schema validation deterministische evidence leveren. De check kan pass, fail of needs_human retourneren. Voor code agents kan de reviewer een andere model session zijn met read-only tools. Voor data- en report agents combineer je deterministische validation met een reviewer model wanneer er nog menselijk of modelmatig oordeel nodig is.

Elf deployment patterns voor AI agents en wat de keuze ertussen bepaalt

Zodra de vijf primitives zijn benoemd, is de vraag welke deployment shape ze uitvoert. Met ‘shape’ bedoel ik een arrangement van die primitives: waar de harness draait, waar state wordt gepersist en welk type sandbox het werk uitvoert. Een shape is een wiring-beslissing, geen vendor-keuze. De onderstaande chart laat zien bij welke run length elke shape goed werkt. In de tekst erna wordt uiteengezet wat de keuze ertussen bepaalt.

Als je maar één van de elf leest, lees dan shape 2: queue + worker + checkpoint DB. Dit is de standaard die ik de meeste teams aanbeveel, de shape die door de reference repo wordt gebruikt en het skelet waarop de meeste andere shapes variëren: queue → worker → durable state, waarbij de sandbox source, harness owner of state engine wordt verwisseld. Als je shape 2 eerst leest, kun je de rest sneller scannen.

De grafiek vergelijkt shapes op basis van run-lengte. De matrix hieronder vergelijkt ze op basis van ownership: waar elk van de vijf primitives fysiek draait. Groene cellen geven aan dat de shape de primitive levert, grijze cellen dat je deze zelf moet aansluiten en rode cellen dat de shape die primitive helemaal niet kan hosten.

1. SDK in een app server (synchronous, request scoped)

De oorspronkelijke shape. De agent SDK draait in een request handler. Goed voor taken van minder dan 30 seconden, demo’s en interne tools. Ongeschikt voor alles waarvan een HTTP-client de verbinding kan verbreken. De HTTP-timeout van Cloud Run loopt maximaal 60 minuten, en elke panic in de web-tier beëindigt de run. De SDK is de harness, het webproces fungeert ook als sandbox en state staat meestal in process memory, tenzij je deze expliciet elders opslaat. Gebruik dit niet voor werk dat meerdere uren duurt.

2. Queue + worker + checkpoint DB

De standaard die ik de meeste teams aanbeveel en de production shape die wordt gebruikt in market-analyst-agent: een Python-worker met een PostgreSQL-checkpointer, Redis Streams (of RabbitMQ) voor de inbound queue en een MCP-sidecar voor tools. Goed voor runs van 10 minuten tot meerdere uren met idempotente stappen. De local runner kan de queue omzeilen voor synchronous development, maar de queue maakt deel uit van de production shape zodra je async submission en backpressure nodig hebt.

De app accepteert een request, maakt een session row aan, pusht een job en retourneert een run ID. De worker haalt de job op, voert de harness uit, schrijft checkpoints, streamt status en slaat artifacts op terwijl de run vordert. Postgres blijft beschikbaar, workers zijn cattle en queue depth levert backpressure. Spot/Preemptible compute werkt zolang de checkpointer het schrijven naar disk afrondt voordat deze success rapporteert.

In deze shape is de worker de harness. De container en per-thread workspace vormen een execution boundary, maar untrusted code heeft nog steeds een hardened sandbox of VM nodig. Postgres beheert session- en checkpoint-state. Traces lopen via OpenTelemetry naar de observability stack die je gebruikt.

3. Durable workflow engine (Temporal-style)

Agent orchestration code draait binnen een Temporal Workflow; model calls en tool calls draaien als Activities. De Workflow-state leeft in een event-history log die wordt ondersteund door Cassandra, MySQL of Postgres, zodat state ook na deploys betrouwbaar kan worden gereplayd. De Temporal × OpenAI Agents SDK integration, sinds maart 2026 algemeen beschikbaar, levert een OpenAIAgentsPlugin en een activity_as_tool-helper. De agentic sandboxes write-up beschrijft hoe je een draaiende agent halverwege een gesprek naar een andere sandbox provider forked. Inactieve Workflows verbruiken geen compute. De beperkingen zijn reëel: realtime agents worden niet ondersteund, streaming is nog steeds als experimental gemarkeerd, en LocalShellTool en ComputerTool zijn uitgeschakeld omdat ze niet passen bij een distributed model.

Gebruik deze vorm wanneer de run echte wachtpunten heeft: human approvals, external callbacks, lange sleeps, retries met business rules en deploy windows. Een human approval wordt een durable sleep die geen compute verbruikt, in plaats van een polling loop die dat wel doet.

De Workflow-code is de harness. De sandbox bevindt zich meestal buiten Temporal en wordt aangeroepen vanuit Activities. Session- en checkpoint-state worden samengebracht in Temporal’s event-history log, terwijl trace-zichtbaarheid afkomstig is van Temporal UI plus OpenTelemetry spans op elke Activity.

4. Sandbox provider per session

Een nieuwere vorm. Elke agent-run krijgt een eigen microVM of container van een sandbox-as-a-service provider. De harness bevindt zich ergens durable; de sandbox is de disposable execution environment.

De provider beheert de sandbox en niets anders. Harness, sessie, checkpoint en trace blijven aan jouw kant, doorgaans aangesloten volgens de queue + worker-vorm uit #2.

5. Anthropic Managed Agents (gehoste harness)

Anthropic lanceerde Managed Agents op 8 april 2026 als public beta, achter de managed-agents-2026-04-01-betaheader. De service biedt een gehoste session, harness, sandbox en vault-backed MCP proxy. Met wake(sessionId) kan de harness op een nieuwe worker worden geïnitialiseerd zonder durable session state te verliezen.

Anthropic brengt Managed Agents in rekening tegen standaard token rates plus $0.08 per session-hour. De facturatie gebeurt op millisecondeniveau en geldt alleen zolang de session-status “running” is; idle time is gratis. Een runaway retry loop voegt daardoor session-hour-kosten toe boven op de tokenkosten.

Lees de caveats. De korting van de Batch API is niet van toepassing (“Sessions are stateful and interactive. There is no batch mode.”). Managed Agents is niet beschikbaar via AWS Bedrock of Google Vertex AI. Binnen de beta vallen MCP tunnels en het “dreaming” van agents onder een aanvullende research preview waarvoor je toegang moet aanvragen; multi-agent coordination en rubric-graded self-evaluation zijn gedocumenteerde onderdelen van de beta. Lock-in is groot: je ruilt de vrijheid van de harness in voor het niet zelf draaien van de loop.

Anthropic host alle vijf primitives: session, harness, sandbox, checkpoint en trace. Je draagt de runtime over en ontvangt de outputs.

6. LangChain Deep Agents Deploy (managed open harness)

deepagents deploy verpakt een deepagents.toml in een LangSmith Deployment met durable execution, memory, multi-tenancy, human-in-the-loop, observability, sandboxed code execution en scheduled runs. Cloud-, hybrid- en self-hosted deployment modes worden ondersteund. Sandbox providers (LangSmith Sandboxes, Daytona, Modal, Runloop of custom) kunnen via één config value worden gewisseld. State staat in een virtual filesystem met pluggable backends; memory is gescoped naar de user, de assistant of beide. Lock-in is lager dan bij Managed Agents: de harness heeft een MIT-licentie, instructions gebruiken de open AGENTS.md-standard en agents zijn beschikbaar via MCP, het A2A-protocol (Agent2Agent) en Agent Protocol. Zie LangChain’s runtime-behind-production-deep-agents-write-up.

Alle vijf primitives worden standaard gehost, maar elk onderdeel kan via config worden gewisseld. De sandbox zit achter één config value. Session en checkpoint staan op een virtual filesystem met pluggable backends. Trace gaat naar LangSmith.

7. Google Cloud Run service of job

Cloud Run heeft twee verschillende runtime modes; welke het beste past, hangt af van hoe de agent wordt aangeroepen. Services zijn HTTP-bound en schalen terug naar nul tussen requests; de harness draait als request handler die terugkeert wanneer de run klaar is. Jobs draaien tot voltooiing zonder HTTP entrypoint; de harness draait als een one-shot worker die afsluit zodra de task is voltooid. Beide kunnen de harness hosten, maar geen van beide bewaart state tussen runs. Sessions en checkpoints moeten in Postgres, Spanner of een vergelijkbare external store staan.

De harde limieten verschillen sterk. Timeout voor requests naar Cloud Run-services: standaard 300 s, maximaal 3.600 s (60 min). WebSockets hebben dezelfde timeout. Cloud Run Jobs: standaard 10 min per task, maximaal 168 uur (7 dagen); voor tasks die GPU’s gebruiken is het maximum 1 uur. Services schalen naar nul, tenzij je always-on CPU inschakelt; jobs hebben geen HTTP en schalen niet automatisch.

Gebruik een service voor synchrone runs tot 60 minuten. Gebruik een job voor langer durend one-shot- of async-werk. Cloud Run Jobs kunnen een task dagenlang actief houden, maar bieden geen durable replay over deploys, versie-updates of worker-vervanging heen. Gebruik Cloud Run niet voor workloads langer dan 7 dagen.

Cloud Run host de harness. Session- en checkpoint-state staan in Postgres, Spanner of een andere external store, en traces kunnen via Cloud Logging en OpenTelemetry worden verwerkt. De service container is een execution environment; voeg een aparte sandbox toe wanneer de agent untrusted code uitvoert.

8. AWS Lambda (waarom dit de verkeerde tool is)

De maximale function-timeout van Lambda is hard begrensd op 900 s (15 minuten). Als API Gateway vóór de function staat, hangt de integration limit af van het API-type. HTTP API’s staan 30 seconden toe; REST integrations hebben standaard een limiet van 29 seconden, terwijl Regional en private REST API’s een langere timeout kunnen configureren. Geen van deze routes maakt van Lambda een worker voor processen van meerdere uren. Een langlopende harness heeft nog steeds external state en re-invocation nodig, waardoor opnieuw de vorm van een queue + worker ontstaat. Gebruik Lambda voor begrensde tool calls, zoals het ophalen van bestanden of uploads naar S3, aangeroepen door een langer draaiende orchestrator. Plaats de orchestrator daar niet.

Op zijn hoogst kan Lambda één tool call binnen de limiet van 15 minuten uitvoeren. De harness, session, checkpoint, sandbox en trace moeten ergens anders worden ondergebracht.

9. AWS ECS / Fargate task per run

Fargate documenteert geen harde limiet voor de runtime van een task, in tegenstelling tot Lambda. Fargate-throttlingquota staan een launch burst van 100 toe, met een refill van 20 per seconde; on-demand- en Spot-budgetten zijn afzonderlijk. ECS-servicequota beperken services met AWS Cloud Map discovery tot 1.000 tasks per service en EC2-backed clusters tot 5.000 container instances.

Fargate vereist de modus awsvpc, waardoor elke task een network interface en private IP krijgt. Deze architectuur past bij data access binnen een VPC. Fargate Spot brengt interruption risk met zich mee, en durability blijft jouw verantwoordelijkheid omdat het platform geen replay in de stijl van Temporal biedt.

Fargate host de harness en geeft elke run een eigen task. Daardoor worden workspaces en task credentials van elkaar gescheiden, maar op zichzelf is dit geen volledige sandbox voor hostile code. Session, checkpoint en trace gaan naar external services zoals RDS of DynamoDB, aangevuld met CloudWatch/X-Ray.

10. Kubernetes Job of namespace per sessie

Goed als je Kubernetes al beheert en per sessie een sandbox met clusterbrede controls wilt. Minder geschikt als je sub-second startup nodig hebt, omdat het ophalen van de container image en het initialiseren van de pod bij een cold start te lang duurt. Het patroon bestaat uit één Job per agent-run, met activeDeadlineSeconds, een PersistentVolumeClaim voor de workspace en een sidecar voor de MCP-server. Crash recovery moet je zelf bouwen. Kubernetes alleen inzetten om agents te hosten brengt veel configuratie-overhead en operationele belasting met zich mee. Het is alleen de moeite waard als je K8s al om andere redenen gebruikt.

Kubernetes host de harness en de execution environment per run, meestal als één Job en soms met een dedicated namespace. Sterke isolatie hangt nog steeds af van de runtime class, network policy, pod security en de onderliggende container- of VM-boundary. Session- en checkpoint-state staan in een externe database of op een PersistentVolumeClaim.

11. Lokale Docker Compose (alleen voor development)

De referentie voor de volgende sectie. Het doel van deze vorm is dat die de production topology één-op-één weerspiegelt (dezelfde primitives, dezelfde network shape) terwijl alles op één machine draait. Wat niet wordt weerspiegeld, is de isolatie: één gedeelde workspace-mount, één Postgres, geen geharde sandbox en geen afzonderlijke failure domains tussen de worker en de state. Ship niets dat hierop lijkt.

Compose weerspiegelt shape #2 op één host. Postgres bevat de session- en checkpoint-state en de worker-container is de harness. De gedeelde workspace-mount is handig voor development, maar isoleert untrusted runs niet. De optionele OpenTelemetry-stack legt traces vast.

Referentiestack: Docker Compose

De reference topology, gebruikt in slavadubrov/market-analyst-agent, bestaat uit een LangGraph-worker, een Postgres-checkpointer, Qdrant voor retrieval, een MCP-sidecar, een Redis-queue voor async production-like runs en een optionele Prometheus / Grafana / Loki / Tempo / OTel observability-stack. In local compose is Redis alleen optioneel omdat de synchronous runner de worker rechtstreeks kan aanroepen. docker compose up brengt de core topology lokaal omhoog; de MCP-sidecar en de observability-stack zijn opt-in profiles (--profile mcp, --profile observability).

Het enige onderdeel dat het waard is om inline te tonen, is de canonical LangGraph-wiring. Dit is een illustratief fragment, geen repository-runnable voorbeeld. Om het uit te voeren heb je langgraph, langgraph-checkpoint-postgres en psycopg[binary,pool] nodig, een bereikbare PostgreSQL-database met rechten om de checkpointer-tabellen aan te maken, POSTGRES_PASSWORD en een eerder gebouwde StateGraph in builder; zie LangGraph’s Postgres checkpointer setup.

import os
from urllib.parse import quote

from langgraph.checkpoint.postgres import PostgresSaver

password = quote(os.environ["POSTGRES_PASSWORD"], safe="")
DB_URI = f"postgresql://agent:{password}@postgres:5432/agent"
# `builder` is your StateGraph, already built
session_id = "session-123"
with PostgresSaver.from_conn_string(DB_URI) as checkpointer:
    checkpointer.setup()  # creates tables on first run
    graph = builder.compile(checkpointer=checkpointer)
    result = graph.invoke(
        {"messages": [{"role": "user", "content": "Continue the task"}]},
        {"configurable": {"thread_id": session_id}},
    )

Observability die de run overleeft

Korte request handlers zijn eenvoudig te debuggen: als er iets misgaat, lees je de response en de live log. Long-running agents hebben die luxe niet. Tegen de tijd dat een run van zes uur faalt, vond de interessante gebeurtenis vijf uur geleden plaats, is de live terminaloutput verdwenen en is de worker die de output produceerde vervangen. Niemand gaat de run uit het geheugen reconstrueren. Je debugt dus aan de hand van duurzame artifacts die zijn weggeschreven terwijl de run nog actief was.

Byte says

Ik probeerde mijn eerste lange run vanuit de terminal te debuggen. De interessante gebeurtenis had uren eerder plaatsgevonden en was uit de buffer gescrolld.

Production stacks omvatten doorgaans vier soorten artifacts, verdeeld over twee groepen. Twee daarvan lees je na afloop van de run, voor postmortems en replay: een queryable event log van elke stap en OpenTelemetry-traces van waar tijd en tokens naartoe gingen. Twee andere lees je tijdens de run. De eerste is een live tail van wat de agent in de workspace produceert. De andere is een observability stack per worktree, die de agent zelf kan queryen terwijl hij nog aan het werk is.

Structured event log (lezen na de run)

Elke model call, tool call, result, error en approval wordt naar durable storage geschreven, gekoppeld aan een session ID en timestamp. Zodra de run eindigt, query je deze gegevens zoals een normale databasetabel. Addy Osmani legt de lat duidelijk in Long-running Agents: “If you can’t reconstruct what the agent did in the last 24 hours from durable storage, what you have is a long-running shell script that happens to call an LLM, not a long-running agent.”

OpenTelemetry GenAI traces (lezen na de run)

Dezelfde stapsgewijze data wordt als spans geëmitteerd met behulp van de standaardattributen uit de gen_ai.* semantic conventions: modelnaam, provider, aantallen input- en outputtokens, conversation ID en workflownaam. De conventions hebben nog steeds de stabiliteitsstatus Development.

In 2026 zijn ze uit de belangrijkste semantic-conventions-repository van OpenTelemetry verplaatst naar hun eigen GenAI semantic conventions repo. Je kunt de attribuutnamen gebruiken voor instrumentation, maar pin de revision die je hebt gevalideerd in plaats van een versienummer uit de main repo. Provider-specifieke velden staan in subnamespaces (anthropic.*, openai.*), gekoppeld aan gen_ai.provider.name. De reden om de standaard te gebruiken is portability: op OTLP-compatible destinations die deze conventions ondersteunen, hoef je bij het wisselen van backend mogelijk geen nieuwe instrumentation toe te voegen. Backend adapters of destination-specific configuration kunnen echter nog steeds nodig zijn.

Tool-call timeline plus workspace-diffs (lezen tijdens de run)

De snelste manier om te weten wat een agent op dit moment doet, is een tail te maken van wat hij in de workspace produceert, niet door in een session log te greppen. De quick-start van Anthropic voor Harness Primitives for Long-Running Claude Agents levert hiervoor een two-pane watch loop: watch -n 5 'git log --oneline -8' toont de meest recente commits die de agent heeft gemaakt en watch -n 5 'find screenshots -name "*.png" | tail -5' toont de meest recente screenshots die hij heeft genomen. Twee terminal panes die elke vijf seconden worden vernieuwd, volstaan om te zien of een run echte voortgang boekt of blijft ronddraaien.

Ephemeral stack per worktree (door de agent zelf gelezen tijdens de run)

Volgens OpenAI’s harness-post: “Logs, metrics en traces worden via een lokale observability stack aan Codex beschikbaar gesteld; die stack is ephemeral voor elke worktree.” Elke agent-worktree krijgt een eigen kortlevende Loki + Prometheus + Tempo, uitsluitend binnen die run. De agent bevraagt deze stack tijdens zijn werk. Daardoor kan een prompt als “geen enkele span in deze vier user journeys duurt langer dan twee seconden” iets worden wat de agent rechtstreeks kan verifiëren, in plaats van iets waarover hij moet gokken.

(De fresh-context evaluator uit de tabel met failure modes leest deze artifacts om te bepalen of de taak “done” is. Deze evaluator hoort bij evaluation, niet bij observability; zie § healthy run lifecycle. Hij is afhankelijk van elk hierboven beschreven oppervlak.)

Een minimale self-hosted observability stack

Voor iets als market-analyst-agent:

  1. OpenTelemetry Collector met de GenAI Normalizer Processor (contrib, alpha) voor ondersteunde GenAI-attributen. Gebruik de generieke Attributes- of Transform-processors om gen_ai.*-velden te filteren of te herschrijven.
  2. Tempo (of Jaeger) voor traces, gesleuteld op gen_ai.conversation.id / thread_id.
  3. Loki voor gestructureerde event-logvermeldingen.
  4. Prometheus voor gen_ai.client.token.usage, gen_ai.client.operation.duration en gen_ai.client.operation.time_to_first_chunk — de gen_ai.server.*-metrics komen van de modelserver, dus je krijgt ze alleen als je de weights zelf host (zie de GenAI metrics conventions).
  5. Grafana-dashboards, gesleuteld op gen_ai.agent.name en gen_ai.request.model.

Hosted alternatieven (kies er één, niet drie):

  • LangSmith: native LangGraph-integratie; tevens het deployment target voor Deep Agents Deploy.
  • Braintrust: de beste fit als eval-first regression suites prioriteit hebben.
  • Arize Phoenix: OSS, native voor OTLP (het OpenTelemetry-wireprotocol), en combineert goed met instrumentation via OpenInference.
  • OpenAI’s tracing dashboard: automatisch wanneer je de OpenAI Agents SDK of de Temporal-integratie daarvan gebruikt.
  • Anthropic’s Claude-tracing: voor sessions die binnen Managed Agents draaien.

Instrumenteer de LangGraph-node

Dit is een illustratief fragment en wordt overgeslagen door de example runner van de repository. Het veronderstelt dat de LangGraph-node al een actieve OpenTelemetry span, de huidige thread_id en een provider-response-object usage met input_tokens en output_tokens heeft; tracerconfiguratie, exportconfiguratie en provider-specifieke usage mapping vallen buiten dit fragment.

span.set_attribute("gen_ai.operation.name", "chat")
span.set_attribute("gen_ai.provider.name", "anthropic")
span.set_attribute("gen_ai.request.model", "<your-model-id>")
span.set_attribute("gen_ai.response.model", "<your-model-id>")

span.set_attribute("gen_ai.workflow.name", "research_then_write")

span.set_attribute("gen_ai.usage.output_tokens", usage.output_tokens)

Het debug-bundlepatroon

Wanneer een run faalt, moet de worker een /workspaces/${THREAD_ID}/_debug/ wegschrijven met daarin de artifacts waar je in een postmortem om zou vragen:

  • session.jsonl: volledige event-logdump van de PostgresSaver (checkpointer.list({"configurable": {"thread_id": ...}})).
  • last_state.json: StateSnapshot.values van de laatste succesvolle super-step.
  • trace.json: door OTLP geëxporteerde spans voor de run.
  • tool_calls.csv: (ts, tool, input_hash, latency_ms, status, error).
  • workspace.tar.zst: de workspace-directory plus git diff tegen de initializer-commit.
  • screenshots/*.png: wat de agent zag.
  • PROGRESS.md, feature-list.json en alle andere door de agent aangemaakte progress-bestanden.
  • env.txt: image tags, modelversie, harness-commit-SHA.

Deze bundle bevat voldoende bewijs voor een mens of reviewer-agent om de fout te reconstrueren. “De agent liep vast” is vaag. Een illustratief rapport is concreet: sessie s_123 besteedde 71 procent van zijn tokens aan het herhalen van drie commands nadat npm install was mislukt.

De juiste vorm kiezen: een beslisgids

De meeste bovenstaande vergelijkingen komen neer op een handvol beslissingen.

Begin met de runtime

Gebruik de runtime als eerste filter:

  • Korter dan 30 seconden, idempotent: request-lifecycle-SDK in een app-server.
  • 30 seconden tot 60 minuten: queue + worker + checkpoint-database.
  • 60 minuten tot 24 uur: dezelfde queue + worker, of een Cloud Run Job voor one-shot work. Gebruik een durable workflow engine als je ook versioning en replay nodig hebt.
  • Langer dan 24 uur, deploys moeten worden overleefd: durable workflow engine (Temporal-stijl). Cloud Run Jobs kunnen langlopende workloads uitvoeren tot aan hun task-limiet, maar bieden geen replay-semantics.
  • Multi-day reinforcement-learning-trainingsloops: K8s Job + volume + Temporal.

Controleer na deze grove filter de side effects, recovery, replay, isolation, datalocatie en het team dat het systeem gaat beheren.

Platformfit per use case

De matrix is compact, en geen enkele groene cel bepaalt op zichzelf de architectuur; meestal zijn het de gele cellen — waarin een platform iets alleen onder een voorwaarde ondersteunt — die de doorslag geven. Brede workloaddekking is nuttig, maar laat data residency, replay-semantics, afhankelijkheid van de provider, operationele volwassenheid en de kosten van het later verplaatsen van state niet zien.

Deep Agents Deploy is de enige kolom in de matrix zonder rode of gele cel: korte synchrone runs, multi-hour batchverwerking, sandbox forking, GPU-workloads en de laagste lock-in komen allemaal groen uit. Daardoor is het een kandidaat wanneer één platform elke workload moet bedienen. Die breedte gaat gepaard met minder production track record dan een queue + worker + Postgres-stack. Beschouw de groene cellen als capability claims die je moet valideren en vergelijk vervolgens de operationele beperkingen die de matrix niet kan weergeven.

Anthropic Managed Agents past volledig bij je workload, of helemaal niet. Het product heeft twee harde beperkingen: het is hosted-only en Claude-only. Als je workload aan beide voorwaarden voldoet — Claude is al het model dat je wilt gebruiken en je beheert liever niet zelf een harness — dan past Managed Agents goed. Een interne coding agent die in bursts van twee tot zes uur draait, is de vorm die hier het beste bij past; bovendien neemt het een groot deel van het platformwerk uit handen van je team. Als een van beide voorwaarden niet geldt omdat je een non-Claude-model of self-hosted compliance nodig hebt, past Managed Agents niet. Geen enkele configuratiewijziging verandert dat.

Hosted harness versus owned harness

Het onderscheid gaat hier over wie de harness beheert, niet over wie de code ervan heeft geschreven. Hosted betekent dat de vendor de harness-loop in diens infrastructuur draait en jij een API aanroept. Owned betekent dat jij de loop op je eigen infrastructuur draait, ook als de harness-code zelf van een vendor afkomstig is.

LangChain komt aan beide kanten van deze scheidslijn voor, wat vaak tot verwarring leidt. Ze leveren LangGraph, een MIT-gelicentieerde library die je zelf host (owned), en Deep Agents Deploy, een managed product dat standaard in cloud mode een Deep Agents-harness op LangSmith Deployment draait (hosted). Hetzelfde bedrijf, twee verschillende operational models. Je kiest wie de loop draait, niet wiens logo op de library staat. (Deep Agents Deploy heeft ook een self-hosted mode voor teams die de ergonomics van de harness willen zonder de cloudcomponent; die mode valt onder owned.)

Kies een hosted harness wanneer de model support, data boundary, recovery behavior en extension points al aansluiten op je behoeften. Kies een owned harness wanneer die constraints requirements zijn waarvan je verwacht dat ze veranderen. Migratie tussen beide verandert state, observability en execution boundaries. Test daarom het exit path voordat production data ervan afhankelijk wordt.

Hosted sandbox versus een owned execution environment

Kies een hosted sandbox wanneer de isolation-, pause/resume- of fork-semantics van de provider aansluiten op je threat model en startup budget. Docker of Fargate kan geschikt zijn voor vertrouwde interne workloads die VPC-toegang of strikte data residency nodig hebben, maar een standaardcontainer is geen voldoende boundary voor hostile code. Part 4 behandelt in dat geval de verschillende isolation-opties.

State stores: Git, DB en object storage naast elkaar

Long-running agents gebruiken meestal drie state stores tegelijk, omdat elke store een ander artifact beheert.

Git slaat workspace state op: de code, documenten en progress files die de agent wijzigt. Elke commit geeft de harness een stabiel recovery point en de volgende sessie een compacte history.

De checkpoint database slaat graph state op: wat is besloten, welke nodes zijn uitgevoerd, welke resultaten zijn teruggekomen en wat hierna moet worden uitgevoerd. De artifact store bevat grote finale outputs, zoals PDF’s, Parquet-bestanden en screenshots. Die artifacts horen niet in Git of de checkpoint database.

Wanneer je git als state gebruikt

Gebruik git wanneer de workload code-shaped is (multi-file edits, refactors, app generation) of voldoende document-shaped is dat file history ertoe doet. Het pattern is eenvoudig: maak een run branch aan, maak een initializer commit en commit daarna op betekenisvolle boundaries: na de setup, na elke feature, nadat de tests slagen en na de laatste cleanup. Sla de laatste workspace commit SHA op naast de checkpoint row. Bij een resume checkt de volgende worker de branch uit, leest git log --oneline -8, inspecteert git status en de laatste diff en leest vervolgens PROGRESS.md of het handoff-bestand dat de vorige sessie heeft geschreven.

Daarmee wordt git een recovery surface voor het artifact dat wordt bewerkt, niet een vervanging voor de checkpoint-database. Git kan twee vragen beantwoorden: wat is er veranderd en welke versie heeft de tests doorstaan? Het kan de harness niet vertellen welke graph node vervolgens moet worden uitgevoerd, welke tool call op goedkeuring wacht of welke retry de idempotency key al heeft gebruikt. Anthropic’s harness gebruikt initializer commits plus per-feature commits als bron van waarheid voor workspace recovery; het model leest git log --oneline -8 om de state te herstellen. Sla git over wanneer het work product uit één conversational answer bestaat. De overhead weegt dan niet op tegen de voordelen.

Wanneer DB-checkpointing gebruiken

Gebruik PostgresSaver-style checkpointing wanneer de agent een graph structure heeft met meerdere nodes waarvan de intermediate state van belang is (planner → researcher → writer → verifier). De reference repo gebruikt dit precies om die reden. Plaats geen terabyte-scale workspace artifacts in de checkpoint; die horen in object storage.

Wanneer een artifact store gebruiken (S3 / GCS)

Gebruik object storage wanneer:

  • de output groter is dan wat de checkpoint-database zou moeten bevatten;
  • downstream consumers een URL-addressable artifact nodig hebben zonder via de agent te gaan; of
  • het deliverable en de run state verschillende retention windows hebben.

Je kunt bijvoorbeeld de session log na 30 dagen verwijderen, maar het final report jarenlang bewaren. Structureer de keys op basis van (thread_id, checkpoint_id, artifact_name), zodat de run die het artifact heeft geproduceerd reconstrueerbaar blijft.

Wanneer human approval gates toevoegen

Voeg gates toe wanneer de tool call destructief en onomkeerbaar is (DB writes, money movement, external comms versturen), wanneer de tool call buiten de blast radius van de agent treedt (production deploys, customer-facing publishes) of wanneer toezichthouders review vereisen. LangGraph’s interrupt() en de approval middleware van Deep Agents bieden beide ingebouwde ondersteuning voor deze gates. Deel 4 behandelde waarom deze gates een permission concern zijn en geen prompt concern.

Een praktische production checklist

Beantwoord voordat een long-running agent wordt uitgerold deze vragen in concrete infrastructuurtermen.

  1. Welke store beheert session events en checkpoints?
  2. Wat gebeurt er als de worker halverwege een tool call uitvalt?
  3. Kan één run de workspace van een andere run corrupt maken?
  4. Voor welke acties is goedkeuring vereist?
  5. Kunnen het model of de sandbox raw credentials lezen?
  6. Welke tool calls kunnen veilig opnieuw worden uitgevoerd?
  7. Waar wordt de per-run cost cap afgedwongen?
  8. Welke fresh-context evaluator bepaalt dat de run “done” is?
  9. Waar staan final outputs nadat de sandbox is verdwenen?
  10. Kunnen we morgen een failed run verklaren zonder die opnieuw uit te voeren?

Als het antwoord op een van deze vragen is: “de prompt zegt dat de agent voorzichtig moet zijn”, dan is het systeem nog niet deployed. Het is nog steeds een demo.

De volgende laag is de harness loop

Deze runtime kan een run actief en recoverable houden, maar durability bewijst niet dat het werk correct is. Deel 6, Harness Engineering for AI Agents, opent de harness primitive uit de bovenstaande tabel: hoe een trace je laat zien met welke van meerdere failures je daadwerkelijk te maken hebt, waar retry- en stopregels staan, wat een handoff moet behouden en hoe een externe acceptance check bepaalt dat een run done is. Dit is ook het laatste artikel in de serie.
