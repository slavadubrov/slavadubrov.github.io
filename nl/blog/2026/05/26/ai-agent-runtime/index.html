Langdurige AI-agent-runtime in 2026: sessies, sandboxes, checkpoints en harnesses

Deel 5 van de serie ‘Engineering the Agentic Stack’

De vorige vier artikelen gingen over het interne ontwerp van een agent: reasoning loops, memory, tool use en security. Dit artikel behandelt de runtime die ervoor zorgt dat deze componenten blijven functioneren tijdens lange sessies en bij procesfouten.

Een agentrun kan uren duren, terwijl het worker-proces op elk moment opnieuw gestart kan worden. Het model kiest nog steeds de volgende actie, maar de runtime moet de staat behouden, de uitvoering beheren en herstellen na een fout tijdens een toolaanroep. In dit artikel wordt de grens van de runtime gedefinieerd. Deel 6 zal zich richten op de harness daarin: de feedback-, retry-, handoff- en acceptatielogica die bepaalt of de agent doorwerkt of stopt.

Wat is een AI-agent-runtime?

Een AI-agent-runtime is de infrastructuurlaag die zorgt voor een toolgebruikende agent die actief blijft, geïsoleerd is, waarneembaar is en kan worden hervat nadat de modelaanroep is afgerond. Hij beheert de sessiestaat, de uitvoering van tools, checkpoints, beleidscontroles, geheime gegevens, trace-gegevens, kostenlimieten en de deploy-vorm. Het model kiest de volgende actie; de runtime beslist waar die actie wordt uitgevoerd, of deze is toegestaan, hoe deze wordt geregistreerd en hoe de run na een fout wordt hervat.

Lange runs breken de aannames over stateless processen

Een stateless chat-endpoint kan de requeststate in één proces bewaren en deze na het versturen van een response verwijderen. Een lange agentrun omvat herstarts van workers, deployments, context-resetten en goedkeuringspauzes. Het worker-proces kan dan niet langer de bron van waarheid zijn.

Het OpenAI Codex-team rapporteert de duur van runs in hun harness-engineering-artikel:

“We zien regelmatig dat enkele Codex-runs voor één taak langer dan zes uur werken (vaak terwijl de mensen slapen).”

Het engineeringteam van Anthropic beschrijft het bijbehorende staatprobleem in Effective harnesses for long-running agents:

“De kernuitdaging van langdurig draaiende agents is dat ze moeten werken in discrete sessies, waarbij elke nieuwe sessie begint zonder enige herinnering aan wat er eerder is gebeurd.”

Beide observaties duiden op hetzelfde ontwerp voor de uitvoeromgeving: de staat moet buiten de worker worden opgeslagen zodat workers vervangbaar zijn.

De sessie moet zich buiten het worker-proces bevinden. Een duurzame opslagplaats registreert modelaanroepen, resultaten van tools en goedkeuringen, zodat een andere worker na een crash kan worden hervat op het laatste veilige punt. Checkpoints maken het bovendien mogelijk om bij voldoening van het contextvenster een nieuwe modelsessie te starten, zonder de volledige geschiedenis opnieuw af te spelen. Volgens de formulering van Anthropic worden harness‑instances wegwerpprecies en opnieuw te starten; de duurzame staat bevindt zich elders.

Het model beslist wat er vervolgens moet gebeuren. De uitvoeromgeving bepaalt of deze actie is toegestaan, waar deze wordt uitgevoerd, hoe deze wordt geregistreerd en hoe de uitvoering na een crash wordt hervat. De rest van dit artikel gaat over die uitvoeromgeving.

De vijf runtime‑primitieven die elke langlopende AI‑agent nodig heeft

In Anthropics artikel Scaling Managed Agents wordt een nuttig vocabulaire aangeboden voor de vijf verantwoordelijkheden van de uitvoeromgeving. De harness stuurt de agent aan, terwijl de sessie vastlegt wat deze heeft gedaan en de sandbox commando’s uitvoert. Checkpoints bieden de volgende worker een hervatingspunt; traces bewaren bewijsmateriaal voor latere debugging. Een implementatie kan componenten combineren, maar de verantwoordelijkheden en foutgrenzen hebben nog steeds benamingen nodig.

Sessie. Een alleen‑toevoegende log van alles wat is gebeurd: modelaanroepen, toolaanroepen, resultaten, fouten, goedkeuringen. Herstel vindt plaats via wake(sessionId) → getSession(id) → resume from last event. In LangGraph is dit een thread_id gecombineerd met een Postgres checkpointer (zie LangGraph persistence). Het OpenAI Agents SDK bevat tien ingebouwde sessie‑backends, waaronder SQLiteSession, RedisSession, SQLAlchemySession, MongoDBSession en EncryptedSession (zie de Sessions docs).

Harness. De orchestratie‑lus. Hij roept het model aan, parseert toolaanroepen, voert ze uit, schrijft de resultaten terug naar de sessie en past herhalingsregels toe. Anthropic stelt dit recht voor zijn raap:

“Elk component in een harness drukt een aannames uit over wat het model niet zelfstandig kan doen.”

Het Codex‑team van OpenAI noemt deze discipline harness engineering: het schrijven van software vereist nog steeds discipline, maar nu gaat meer aandacht naar de infrastructuur dan naar de code zelf. LangGraphs CompiledStateGraph, Deep Agents’ create_deep_agent en Claude Code zelf vallen in deze zin ook onder harnesses.

Sandbox. De geïsoleerde uitvoeromgeving waarin commando’s daadwerkelijk worden uitgevoerd. Op de pagina sandbox concepts van het OpenAI Agents SDK wordt dit duidelijk omschreven:

“De externe uitvoeromgeving is nog steeds verantwoordelijk voor goedkeuringen, tracing, overdrachten en het bijhouden van hervatingsgegevens. De sandbox‑sessie is verantwoordelijk voor commando’s, bestandswijzigingen en isolatie van de omgeving.”

Sandboxes verschillen in hun levensduur en in wat ze tussen uitvoeringen onthouden. De eenvoudigste vorm is fresh ephemeral: er wordt één sandbox gestart voor één taak, deze wordt vernietigd zodra de taak is afgerond, en er wordt bij elke uitvoering de kosten voor een cold‑start betaald.

Persistent paused sandboxes bewaren het bestandssysteem en een geheugen‑snapshot tussen uitvoeringen. Hierdoor kan een hervatting zonder volledige opstart plaatsvinden. Snapshot or fork maakt een copy‑on‑write‑afbeelding af van een voorbereide ouder‑instance, zodat meerdere taken dezelfde geïnstalleerde afhankelijkheden en opgewarmde caches delen, zonder hun schrijfbare staat te delen.

Per-worktree-sandboxen bieden elke taak zijn eigen werkruimte en observabiliteitsstack. Afzonderlijke logs, metrics en traces maken het mogelijk om één uitvoering te debuggen zonder dat de toestand van die uitvoering invloed heeft op andere uitvoeringen. De tabel met providers verderop in dit artikel vergelijkt het gedrag bij een koude start en bij persistente data.

Checkpoint. Herstartbare toestandsopslag. LangGraph’s PostgresSaver schrijft op elk grenspunt van een super-stap een StateSnapshot, terwijl er per taak ook gegevens worden opgeslagen in checkpoint_writes. Hierdoor worden succesvolle uitvoerresultaten van knopen niet opnieuw berekend wanneer een verwante knoop faalt. De snapshot is een JSON-serialiseerbaar dict (v, ts, id, channel_values, channel_versions, versions_seen, pending_sends), zoals beschreven op de langgraph-checkpoint-postgres PyPI-pagina en in de LangGraph checkpoints reference.

Trace. Het hulpmiddel voor herbeziening en debugging. Elke modelaanroep, toolaanroep en sub-agent-stap wordt vertegenwoordigd door een span met informatie over tijdsduur, invoer, uitvoer, tokenaantallen en kosten. Wanneer een zes uur durende uitvoering mislukt, is de trace essentieel om vast te stellen wat er mis is gegaan; de terminaluitvoer van de uitvoering is dan al lang verdwenen. OpenTelemetry’s GenAI semantic conventions standaardiseren de namen van de attributen (welk model, welke provider, hoeveel tokens, welk gesprek, welk workflow), zodat dezelfde trace netjes wordt weergegeven in Tempo, Jaeger, Honeycomb of LangSmith zonder dat opnieuw instrumentatie nodig is.

Policy en geheime gegevens vormen aparte runtime-grenzen

Er zijn twee grenzen die alle vijf de primitives doorkruisen en die het gemakkelijker maken om ze als afzonderlijke aspecten te beschouwen. Dit zijn de runtime-versies van het beveiligingsargument uit Deel 4.

Policy engine

Voor elke toolaanroep wordt eerst een toestemmingsschepping uitgevoerd om te bepalen of de aanroep wordt goedgekeurd. In productieomgevingen komen twee veelgebruikte patronen voor. Bij Deep Agents kan elke subagent aangeven welke bestandspaden hij mag lezen of schrijven, waarna het middleware alles buiten deze lijst blokkeert. Anthropic Managed Agents stuurt elke toolaanroep via een MCP-proxy, zodat de proxy de toestemmingen controleert in plaats van de agentcode zelf. Wanneer een gevoelige aanroep menselijke goedkeuring vereist, zorgen LangGraph’s interrupt() en de approval-hook van Deep Agents ervoor dat de uitvoering wordt opgeschort totdat iemand toestemming geeft.

Secret broker

Het model moet geen langlevende geheime gegevens kunnen zien, en dat geldt meestal ook voor sandboxen. Het Managed Agents-patroon is hierbij het meest geschikt:

“Voor Git gebruiken we de access-token van elk repository om het repo tijdens de initialisatie van de sandbox te klonen en deze te koppelen aan de lokale git remote. Git push en pull werken van binnenuit de sandbox, zonder dat de agent zelf ooit met de token omgaat. Voor aangepaste tools ondersteunen we MCP en slaan we OAuth-tokens op in een veilige kluis. Claude roept MCP-tools op via een speciale proxy; deze proxy neemt een token op dat gekoppeld is aan de sessie. … De harness krijgt nooit kennis van enige credentials.”

In de referentiestack van market-analyst-agent) leest de MCP sidecar OAuth-tokens op uit een Docker-secret (in productie HashiCorp Vault), en geeft alleen het benodigde interface-element door aan de LangGraph-worker. De worker ziet nooit de tokens zelf. git push werkt daarin correct, terwijl cat ~/.ssh/id_rsa dat niet doet.

Een praktische controlemethode is om elke component op te sommen en aan te geven voor welk van de vijf primitieven deze dient. Postgres kan verantwoordelijk zijn voor het beheren van sessies en checkpoints. De worker-container fungeert als samenstellend element. Diensten zoals Daytona, Modal of E2B bieden de sandbox, terwijl Tempo of LangSmith de trace-gegevens opslaan.

Vervolgens moeten gekoppelde fouten worden onderzocht. Als twee primitieven zich in dezelfde procesinstans bevinden, zorgt één crash ervoor dat beide uitvallen. Wanneer ze dezelfde credentials delen, kan één lek tot problemen in beide leiden. Voorbeelden hiervan zijn een worker die ook verantwoordelijk is voor de duurzaamheid van traces, of een sidecar-token dat ook toegang geeft tot de checkpoint-database.

Foutmodi tijdens de uitvoering van productie-AI-agenten

De runtime beheert herproberingen, herstelt eerder uitgevoerde werkzaamheden, isolateert werkruimtes en handhaaft budgetbeperkingen. De vijf genoemde primitieven bepalen het levenscyclus van een uitvoering, terwijl beleidsregels en secret-brokerage hierover heen werken. Naarmate uitvoeringen zich over meerdere workers en context-windows verspreiden, verschuiven de fouten richting problemen met toestandsbeheer, dubbele bijwerkingen, drift in de sandbox en onvoldoende budgettoepassing.

De fouten vallen uiteen in vier categorieën:

  • Fouten met betrekking tot kwaliteit van het output: de agent verklaart dat de taak voltooid is voordat dit daadwerkelijk het geval is, vergeet wat hij eerder heeft gedaan bij een reset van de context-window, of vertrouwt op zijn eigen evaluatie en levert gebroken output af.
  • Fouten bij kostenbeheer: de agent raakt vast in een herprobeeringslus, of verbruikt het token- of tool-call-budget zonder iets bruikbaars te produceren.
  • Fouten met betrekking tot toestand en crashes: werkruimtes gaan scheef omdat één uitvoering bestanden aanraakt die eigendom zijn van een andere uitvoering, toolcalls worden meerdere keren uitgevoerd door herproberingen, of er wordt geen werk opgeslagen wanneer een worker tussen gebeurtenissen crasht.
  • Fouten met betrekking tot de context-window: het model vat samen en stopt vroegtijdig omdat het denkt dat de beschikbare ruimte op is, zelfs wanneer er nog voldoende ruimte over is.

De tabel koppelt elke fout aan een mitigatiemaatregel, de runtime-hook die deze toepast, en de grondslag voor de aanbeveling. Het gedrag kan per model verschillen; beschouw observaties van leveranciers dan ook als aanleiding om aannames opnieuw te testen in plaats van ze als definitieve regels te zien.

Er komen twee concepten steeds terug in elke rij. Anthropic, met betrekking tot het probleem van verouderde componenten in Harness design for long-running application development:

“Elke component in een harness vertegenwoordigt een aannames over wat het model niet op eigen kracht kan doen, en deze aannames verdienen een strenge test, zowel omdat ze onjuist kunnen zijn als omdat ze snel verouderen naarmate de modellen verbeteren.”

Vercel, met betrekking tot het vergelijkbare probleem van te veel tools die te veel aannames bevatten, in We removed 80% of our agent’s tools:

“We hebben het grootste deel ervan verwijderd en de agent teruggebracht tot één enkele tool: het uitvoeren van willekeurige bash-commando’s. Wij noemen dit een file system agent.”

Volgens Vercel steeg het succespercentage bij een representatieve query van 80% naar 100%, terwijl de slechtste case daalde van 724 seconden per 100 stappen en 145.463 tokens (mislukt) naar 141 seconden per 19 stappen en 67.483 tokens (geslaagd). De les is niet dat je je tools moet verwijderen, maar dat elke primitief in je runtime – inclusief de beschikbare tools – een bepaalde levensduur heeft. Test de aannames opnieuw wanneer het model verandert.

Cognition ondervond hetzelfde probleem met betrekking tot de sessielengte bij Sonnet 4.5. In Rebuilding Devin for Claude Sonnet 4.5 beschrijven ze een model dat proactief SUMMARY.md / CHANGELOG.md genereert zodra het merkt dat de context op is, maar dat het onderschat hoeveel tokens er nog over zijn. Hun oplossing is om de beta-versie met 1 miljoen tokens te gebruiken en de gebruikssom te beperken tot 200.000 tokens, zodat het model nog steeds denkt dat er ruimte is. Ook deze maatregel zal uiteindelijk nutteloos worden.

Het team van OpenAI formuleert deze discipline in één zin: “Mensen sturen, agents uitvoeren.” Wanneer er iets misgaat, gaat het niet om “het nog eens proberen”, maar om “welke capaciteit ontbreekt en hoe kunnen we die zodanig maken dat de agent hem kan begrijpen en naleven?”

Het gezonde levenscyclus van een uitvoering

Een goed functionerende uitvoering is saai: het bestaat uit een reeks kleine, herstelbare stappen, waarbij elke stap zijn resultaat eerst op duurzame opslag zet voordat de volgende stap begint.

Dit mechanisme beschermt tegen schade door crashes. Bij een fout gaat alleen de huidige stap verloren, en de volgende worker vervangt deze direct door de vorige voltooide stap, in plaats van de hele aanvraag opnieuw te starten.

  1. Start opnieuw, hetzij vanuit een nieuwe sessie, hetzij vanuit een hervatte sessie. Bij hervatting wordt het werkgebied gemounted uit zijn laatst bekende staat, worden eventuele voortgangsbestanden die bij een eerdere poging zijn achtergebleven (PROGRESS.md, feature-list.json) gelezen, en wordt het laatste checkpoint uit de database geladen. Hieroverdraagt het harness aan de agent alles wat de vorige worker in zijn geheugen had voordat deze stopte.

  2. Plan eerst voordat er toolaanroepen worden uitgevoerd. Noteer hoe ‘afgerond’ eruitziet, hoeveel tijd de uitvoering mag gebruiken, welke tools de agent mag oproepen, en wat de uitvoering moet stoppen als deze te vroeg moet eindigen. Deze planningswaarden vormen de runtime-checks; zonder ze heeft de uitvoering geen richtlijnen om zich aan te houden.

  3. Voer één toolaanroep per keer uit. De policy-laag beslist of de aanroep is toegestaan. Het harness voert hem uit, slaat het resultaat op en schrijft één event op in het sessielog. Eén stap, één event. Een crash tussen events is herstelbaar, omdat het log – en niet de geheugeninformatie van de worker – de bron van waarheid is.

  4. Maak checkpoints op grenzen van super-stappen, of na elk event in een eenvoudiger harness. Sla de grafische staat, de verschillen in het werkgebied en referenties naar alle gegenereerde artefacten op. Dit checkpoint wordt door stap 1 gelezen bij het volgende hervatten. Als het checkpoint ontbreekt of verouderd is, verloopt het herstel trager, omdat dan het hele sessielog opnieuw moet worden afgespeeld.

  5. Evalueer tegen de artefacten wanneer de agent denkt dat de taak is afgerond: tests, een reviewer met een schone context, schemavalidatie en browserchecks. Als de controle slaagt, eindigt de uitvoering succesvol. Mislukt dit, wordt de uitvoering hervat vanaf het laatste geldige checkpoint, waarbij het foutbericht aan de context wordt toegevoegd, en wordt opnieuw geprobeerd.

Er is geen enkele stap in deze lijst waarbij de agent iets tussen uitvoeringen moet onthouden. De staat bevindt zich in de sessie en het checkpoint, en de agent laadt deze opnieuw in bij elk hervatten.

Tools met bijwerkingen hebben idempotentie nodig. Elke tool met bijwerkingen vereist een idempotentie-sleutel die is afgeleid van de sessie-ID en de toolaanroep-ID, en die al wordt opgeslagen voordat de bijwerking optreedt. send_email(session_id, tool_call_id, message_hash). create_pr(session_id, tool_call_id, branch_name). charge_customer(session_id, tool_call_id, invoice_id). Minstens één keer uitvoeren is de standaard in queues en workflow-engineën. Als herhalen van een toolaanroep echte schade kan veroorzaken, is de tool nog niet geschikt voor gebruik door agents.

Evaluatie moet bewijsmateriaal bevatten dat buiten de oorspronkelijke context valt. Een nieuwe evaluator verminderd bias door gedeelde context, terwijl tests, lints, browserchecks en schemavalidatie deterministisch bewijs leveren. De controle kan pass, fail of needs_human teruggeven. Voor code-agents kan de reviewer een andere modelsessie zijn met alleen-leestools. Voor data- en rapport-agents moet deterministische validatie worden gecombineerd met een reviewer-model waarbij nog steeds oordeel nodig is.

Elf deploypatronen voor AI-agents en wat de keuze bepaalt

Zodra de vijf primitieven zijn genoemd, blijft de vraag over welke deployvorm ze zal gebruiken. Met ‘vorm’ bedoel ik de manier waarop deze primitieven zijn gerangschikt: waar het harness zich bevindt, waar de staat wordt opgeslagen, en in wat voor soort sandbox het werk wordt uitgevoerd. Het gaat hierbij niet alleen om een keuze van één leverancier. De onderstaande grafiek toont waar elke vorm zich bevindt op de as van de uitvoeringsduur. De tekst daarna legt uit wat de keuze tussen deze vormen bepaalt.

Als je maar één van de elf configuraties gaat lezen, kies dan voor vorm 2: queue + worker + checkpoint DB. Dit is de standaard die ik aanbeveel voor de meeste teams, de configuratie die wordt gebruikt in het referentierepo, en de basis waarop de overige vormen zijn gebaseerd: queue → worker → duurzame staat, met eventueel een andere sandbox, eigenaar van de harness of state engine. Door eerst vorm 2 te bestuderen, ga je sneller door de overige vormen heen.

De grafiek vergelijkt de verschillende vormen op basis van hun uitvoeringsduur. De matrix hieronder vergelijkt ze op basis van eigendom: waar elke van de vijf primitieven fysiek wordt opgeslagen. Groene cellen geven aan dat de vorm zelf de primitief levert; grijs betekent dat je deze zelf moet integreren.

1. SDK binnen een app-server (synchronisch, request-gebonden)

De oorspronkelijke configuratie. Het agent-SDK draait binnen een request-handler. Geschikt voor taken die minder dan 30 seconden duren, demos en interne hulpprogramma’s. Niet geschikt voor situaties waarin een HTTP-client kan worden afgebroken. De HTTP-tijdslimiet van Cloud Run bedraagt maximaal 60 minuten, en elke paniek in het webproces beëindigt de uitvoering. Het SDK fungeert als harness, het webproces dient tevens als sandbox, en de staat bevindt zich meestal in het procesgeheugen, tenzij je deze expliciet ergens anders plaatst. Gebruik deze configuratie niet voor werkzaamheden die meerdere uren duren.

2. Queue + worker + checkpoint DB

De standaard die ik aanbeveel voor de meeste teams, en de productieconfiguratie die wordt gebruikt in market-analyst-agent: een Python-worker met een PostgreSQL-checkpointer, Redis Streams (of RabbitMQ) voor de invoerqueue, en een MCP-sidecar voor hulpprogramma’s. Geschikt voor uitvoeringen van 10 minuten tot meerdere uren met idempotente stappen. De lokale runner kan de queue omzeilen voor synchroneuze ontwikkeling, maar zodra je async-inzendingen en backpressure nodig hebt, maakt de queue deel uit van de productieconfiguratie.

De app accepteert een verzoek, maakt een sessierow aan, stuurt een taak door en geeft een run-ID terug. De worker haalt de taak op, voert de harness uit, slaat checkpoints op, stuurt statusmeldingen door en slaat artefacten op terwijl dit gebeurt. Postgres blijft intact, workers zijn ‘cattle’, en de diepte van de queue zorgt voor backpressure. Spot/Preemptible computing werkt zolang de checkpointer klaar is met schrijven naar het schijf voordat hij succes meldt.

In deze configuratie is de worker de harness. Zijn container en per-thread workspace vormen een uitvoeringsgrens, maar onbetrouwbare code heeft nog steeds een versterkte sandbox of VM nodig. Postgres beheert de sessie- en checkpointstaten. Trace-gegevens gaan via OpenTelemetry naar de observabiliteitssuite die je gebruikt.

3. Duurzame workflow-engine (Temporal-stijl)

Het agent-orkestreercode draait binnen een Temporal Workflow; model- en hulpprogrammaaanroepen worden uitgevoerd als Activities. De workflowstaat wordt opgeslagen in een event-history-log ondersteund door Cassandra, MySQL of Postgres, zodat de staat na elke deploy correct kan worden hersteld. De public-preview Temporal × OpenAI Agents SDK integratie bevat een OpenAIAgentsPlugin en een activity_as_tool helper, en de agentic sandboxes write-up beschrijft hoe je een lopende agent tussendoor kunt overzetten naar een andere sandbox-provider. Idle workflows verbruiken geen rekenkracht. Er zijn echter beperkingen: streaming- en spraakagenten worden in de huidige integratie niet ondersteund, en LocalShellTool en ComputerTool zijn uitgeschakeld omdat ze niet passen binnen een gedistribueerd model.

Gebruik deze vorm wanneer een run daadwerkelijke wachtpunten kent: menselijke goedkeuringen, externe callback‑aanroepen, lange slaapperioden, herproberingen onder invloed van bedrijfsregels, of deploy‑tijfen. Een menselijke goedkeuring resulteert in een duurzame slaaptoestand die geen rekenkracht verbruikt, in tegenstelling tot een polling‑lus die dat wel doet.

De Workflow‑code vormt het ‘harness’. De sandbox bevindt zich meestal buiten Temporal en wordt aangeroepen vanuit Activities. De sessie‑ en checkpoint‑staten worden opgenomen in Temporal’s event‑history‑log, terwijl de trace‑zichtbaarheid wordt geboden door de Temporal UI in combinatie met OpenTelemetry spans voor elke Activity.

5. Anthropic Managed Agents (gehoste harness)

Anthropic lanceerde Managed Agents op 8 april 2026 in een publieke beta-versie, onder het managed-agents-2026-04-01 beta-label. De dienst biedt een gehosteerde sessie, harness, sandbox en een MCP-proxy ondersteund door een vault. wake(sessionId) maakt het mogelijk om de harness op een nieuwe worker te initialiseren zonder dat de permanente sessiestatus verloren gaat.

Claude rekent voor Managed Agents de standaard tokenprijzen op, plus $0,08 per sessie-uur. Facturatie vindt plaats op millisecondenniveau en is alleen van toepassing zolang de sessiestatus “running” is; tijdens idle-tijd wordt geen kosten in rekening gebracht. Een oncontroleerbare retry-loop leidt dus tot extra kosten voor sessie-uur naast de tokenkosten.

Lees de beperkingen goed. De kortingsregeling voor de Batch API is niet van toepassing (“Sessies zijn stateful en interactief; er is geen batchmodus”). Managed Agents is niet beschikbaar via AWS Bedrock of Google Vertex AI. Multi-agentcoördinatie en zelfevaluatie bevinden zich nog in de research-preview-fase. De lock-in is hoog: je geeft de vrijheid van de harness op in ruil voor het niet zelf hoeven uitvoeren van de loop.

Anthropic host alle vijf de primitieven: sessie, harness, sandbox, checkpoint en trace. Jij zorgt voor de uitvoeromgeving en ontvangt de resultaten.

6. LangChain Deep Agents Deploy (gebeheerde open harness)

deepagents deploy pakketten een deepagents.toml samen tot een LangSmith Deployment met duurzame uitvoering, geheugenbeheer, multi-tenancy, menselijke begeleiding, observabiliteit, geïsoleerde codeuitvoering en geplande uitvoeringen. Er zijn cloud-, hybride- en zelfgehosteerde implementatiemogelijkheden. Sandboxproviders (LangSmith Sandboxes, Daytona, Modal, Runloop of zelfgemaakt) kunnen eenvoudig worden gewisseld via één configuratiewaarde. De staat wordt opgeslagen in een virtueel bestandsysteem met plugbare backends; het geheugen is toegewezen aan de gebruiker, de assistent of beide. De lock-in is lager dan bij Managed Agents: de harness valt onder de MIT-licentie, de instructies maken gebruik van de open AGENTS.md standaard, en de agents zijn bereikbaar via MCP, A2A en Agent Protocol. Zie LangChain’s artikel runtime-behind-production-deep-agents.

Alle vijf de primitieven worden standaard gehost, maar elk kan worden aangepast via configuratie. De sandbox wordt bepaald door één configuratiewaarde. Sessie en checkpoint worden opgeslagen in een virtueel bestandsysteem met plugbare backends. Trace-gegevens gaan naar LangSmith.

7. Google Cloud Run-service of -job

Cloud Run kent twee verschillende uitvoermodi, waarvan de keuze afhangt van hoe de agent wordt opgeroepen. Services zijn gebonden aan HTTP en schalen terug tot nul tussen verzoeken; de harness werkt als een verzoekverwerker die stopt zodra de uitvoering voltooid is. Jobs worden tot het einde uitgevoerd zonder HTTP-entrypoint; de harness fungeert dan als eenmalige worker die ophoudt zodra de taak klaar is. Beide kunnen de harness herbergen, maar geen van beide bewaart staat tussen uitvoeringen. Sessions en checkpoints moeten worden opgeslagen in Postgres, Spanner of een soortgelijke externe opslag.

De harde limieten verschillen sterk tussen deze twee opties. Cloud Run-serviceverzoeksTimeout: standaard 300 s, maximaal 3.600 s (60 minuten). WebSockets hebben dezelfde timeout. Cloud Run-jobs: standaard 10 minuten per taak, maximaal 168 uur (7 dagen); voor taken met GPU’s geldt een limiet van 1 uur. Services schalen terug tot nul tenzij je ‘always-on CPU’ inschakelt; jobs hebben geen HTTP en schalen niet automatisch.

Gebruik een service voor synchrone uitvoeringen tot 60 minuten. Gebruik een job voor langere, eenmalige of asynchrone taken. Cloud Run Jobs kunnen een taak dagenlang actief houden, maar ze bieden geen duurzame mogelijkheid om resultaten na deployments, versienummers of vervanging van workers te herhalen. Boven de 7 dagen moet Cloud Run worden vermeden.

Cloud Run herbergt de harness. Session- en checkpointstaten worden opgeslagen in Postgres, Spanner of een andere externe opslag, en traces kunnen via Cloud Logging en OpenTelemetry worden verwerkt. Het servicecontainer vormt het uitvoeromgeving; voeg een aparte sandbox toe wanneer de agent onbetrouwbare code uitvoert.

8. AWS Lambda (waarom dit het verkeerde hulpmiddel is)

Lambda’s maximale functietimout bedraagt 900 s (15 minuten), en dat is vastgesteld. Als API Gateway de functie voorafgaat, hangt de integratielimiet af van het API-type. HTTP-API’s staan 30 seconden toe; REST-integraties hebben standaard 29 seconden, terwijl regionale en private REST-API’s een langere timout kunnen configureren. Geen van deze opties maakt van Lambda een worker die urenlang kan draaien. Een langlopende harness heeft nog steeds externe staat en opnieuw oproepen nodig, waardoor de queue + worker-structuur weer ontstaat. Gebruik Lambda voor beperkte toolcalls, zoals het ophalen van bestanden of het uploaden naar S3, die worden opgeroepen door een langduriger orchestrator. Plaats de orchestrator er niet zelf.

In het beste geval kan Lambda één toolcall onderbrengen binnen zijn limiet van 15 minuten. De harness, sessions, checkpoints, sandbox en traces moeten allemaal ergens anders worden opgeslagen.

9. AWS ECS / Fargate-taak per uitvoering

In tegenstelling tot Lambda geeft Fargate geen harde limiet aan voor de uitvoeringstijd van taken. Fargate-throttlingquotas stellen een lanceersnelheid van 100 taakseconden vast, met een herladen snelheid van 20 per seconde, inclusief aparte budgetten voor on-demand en spot. ECS-servicequotas beperken services die AWS Cloud Map gebruiken tot 1.000 taken per service, en clusters gebaseerd op EC2 tot 5.000 containerinstances.

Fargate vereist awsvpc-modus, zodat elke taak een netwerkinterface en een privé-IP krijgt. Deze configuratie is geschikt voor interne VPC-data-toegang. Fargate Spot brengt risico’s op onderbrekingen met zich mee, en de duurzaamheid blijft jouw verantwoordelijkheid omdat de platform geen Temporal-achtige herhaling mogelijk maakt.

Fargate beherst de infrastructuur en zorgt ervoor dat elke uitvoering zijn eigen taak krijgt toegewezen. Hierdoor worden werkruimtes en accountgegevens van taken gescheiden, maar het vormt op zichzelf geen volledige sandbox tegen gevaarlijke code. Session-, checkpoint- en trace-gegevens worden opgeslagen bij externe diensten zoals RDS of DynamoDB, samen met CloudWatch/X-Ray.

10. Kubernetes Job of namespace per sessie

Uitstekend wanneer je al Kubernetes gebruikt en een sandbox per sessie wilt combineren met clusterwijde controle. Minder geschikt wanneer een subsecondenstart vereist is, omdat het laden van de containerimage en het initialiseren van de pod tijdens een koude start te lang duurt. Het gebruikelijke patroon bestaat uit één Job per agentuitvoering, inclusief activeDeadlineSeconds, een PersistentVolumeClaim voor de werkruimte, en een sidecar voor de MCP-server. Het herstel bij crashes moet zelf worden ontworpen. Het gebruik van Kubernetes alleen om agents te hosten brengt hoge kosten met zich mee qua configuratie en operationele last. Het is alleen rendabel als je K8s al om andere redenen gebruikt.

Kubernetes beheert zowel de infrastructuur als de uitvoeromgeving per run, meestal via één Job en soms in combinatie met een aparte namespace. Sterke isolatie hangt nog steeds af van de runtime-klasse, netwerkbeleid, podbeveiliging en de grenzen van de onderliggende container of VM. Session- en checkpoint-gegevens worden opgeslagen in een externe database of op een PersistentVolumeClaim.

11. Lokale Docker Compose (alleen voor ontwikkeling)

Referentie voor het volgende gedeelte. Het voordeel van deze opzet is dat deze de productietopologie one-to-one weerspiegelt (zelfde componenten,zelfde netwerkstructuur), maar dan op één machine. Lees de lijst met “niet producties veilig” aan het einde van het volgende gedeelte voordat je iets dergelijks in productie zet.

Compose weerspiegelt structuur #2 op één host. Postgres bewaart de session- en checkpoint-gegevens, terwijl de worker-container de infrastructuur draait. Het delen van de werkruimte is handig voor ontwikkeling, maar zorgt niet voor isolatie van onbetrouwbare uitvoeringen. De optionele OpenTelemetry-stack registreert trace-gegevens.

Referentiestack: Docker Compose

De referentietopologie, gebruikt in slavadubrov/market-analyst-agent, bestaat uit een LangGraph-worker, een Postgres-checkpointer, Qdrant voor zoekopdrachten, een MCP-sidecar, een Redis-queue voor asynchrone, productielike uitvoeringen, en optioneel een Prometheus / Grafana / Loki / Tempo / OTel observabiliteitsstack. Bij lokale Docker Compose is Redis optioneel, omdat de synchrone runner rechtstreeks naar de worker kan apellen. docker compose up zorgt ervoor dat de hele topologie lokaal wordt opgestart.

Het enige onderdeel dat expliciet getoond kan worden, is de standaardconfiguratie van LangGraph. Dit is het kleinste concrete voorbeeld van het checkpoint-principe:

Observabiliteit die na de uitvoering blijft bestaan

Korte requesthandlers zijn gemakkelijk te debuggen: wanneer er iets misgaat, kun je de respons en de live-logs bekijken. Lange lopende agents hebben die mogelijkheid niet. Tegen de tijd dat een zes uur durende uitvoering faalt, heeft het relevante incident zich al vijf uur eerder voorgedaan, zijn de live-terminaloutput en de worker die het heeft gegenereerd verdwenen. Niemand zal de uitvoering op basis van geheugen reconstrueren. Daarom wordt geadviseerd om te debuggen op basis van permanente artefacten die tijdens de uitvoering zijn gemaakt.

Productiestacks omvatten doorgaans vier soorten artefacten, gegroepeerd in twee categorieën. Twee daarvan worden gelezen na de uitvoering, voor postmortems en herhaling: een querybaar gebeurtenislog van elke stap, en OpenTelemetry-traces die aangeven waar tijd en tokens naartoe gaan. De andere twee worden gelezen tijdens de uitvoering, zodat men het proces in real time kan volgen: een live weergave van wat de agent in het werkgebied genereert, en een observabiliteitssysteem per worktree dat de agent zelf kan raadplegen terwijl deze nog draait.

Gestructureerd gebeurtenislog (gelezen na de uitvoering)

Elke modelaanroep, hulpprogrammaanroep, resultaat, fout en goedkeuring wordt opgeslagen in duurzame opslag, gecodeerd met een sessie-ID en tijdstempel. Zodra de uitvoering is afgerond, kan men dit loggen als een gewone database-tabel. Addy Osmani stelt duidelijk de standaard vast in Long-running Agents: “Als je niet kunt reconstrueren wat de agent de afgelopen 24 uur heeft gedaan uit de duurzame opslag, dan heb je te maken met een langlopend shellscript dat toevallig een LLM aanroept, en niet met een echte langlopende agent.”

OpenTelemetry GenAI-traces (gelezen na de uitvoering)

Hetzelfde soort stapsgewijs data, maar uitgezonden als spans met behulp van de standaardattributen uit de gen_ai.* semantische conventies: modelnaam, provider, aantal invoer- en uitvoertokens, gespreks-ID, workflow-naam (ontwikkelingsstatus per v1.36.0). Provider-specifieke velden bevinden zich in subnamenruimtes (anthropic.*, openai.*), gecodeerd via gen_ai.provider.name. De reden om de standaard te gebruiken, is portabiliteit: dezelfde trace wordt netjes weergegeven in Tempo, Jaeger, Honeycomb of LangSmith, zonder dat de code opnieuw moet worden geïnstrumenteerd bij elke backend-wisseling.

Tijdslijn van hulpprogrammaanroepen plus verschillen in het werkgebied (gelezen tijdens de uitvoering)

De snelste manier om te weten wat een agent op dit moment doet, is door te kijken naar wat deze genereert in het werkgebied, in plaats van door door een sessie-log te zoeken. Anthropic’s Harness Primitives for Long-Running Claude Agents bevat twee hooks voor dit doel: watch -n 5 'git log --oneline -8' toont de meest recente commits die de agent heeft gemaakt, en watch -n 5 'find screenshots -name "*.png" | tail -5' laat de nieuwste screenshots zien. Twee terminalvensters die elke vijf seconden worden bijgewerkt, zijn voldoende om vast te stellen of er daadwerkelijk vooruitgang wordt geboekt of dat de agent alleen maar loopt te draaien.

Tijdelijke observabiliteitssysteem per worktree (gelezen door de agent zelf, tijdens de uitvoering)

Volgens OpenAI’s harness post: “Logs, metrics en traces worden via een lokaal observabiliteitssysteem dat tijdelijk is voor elke worktree, beschikbaar gesteld aan Codex.” Elke agent-worktree krijgt zijn eigen kortstondige Loki + Prometheus + Tempo-installatie, beperkt tot die specifieke uitvoering. De agent raadpleegt dit systeem tijdens het werken. Hierdoor kan een opdracht als “geen span in deze vier gebruikersjourneys mag langer duren dan twee seconden” direct worden gecontroleerd door de agent, in plaats van dat deze hierover moet gissen.

(Het fresh-context evaluator uit de tabel met fallemodi leest deze artefacten om te bepalen of de uitvoering “afgerond” is. Het valt onder evaluatie, niet onder observabiliteit; zie § healthy run lifecycle. Het is afhankelijk van al de bovenstaande componenten.)

Een minimale zelfgehoste observabiliteitssysteem

Voor zoiets als market-analyst-agent:

  1. OpenTelemetry Collector met de GenAI-processor en een attribuutfilter op gen_ai.*.
  2. Tempo (of Jaeger) voor traces, gecodeerd via gen_ai.conversation.id / thread_id.
  3. Loki voor gestructureerde eventlog-entries.
  4. Prometheus voor gen_ai.client.token.usage, gen_ai.client.operation.duration en gen_ai.server.time_to_first_token (zie de GenAI-metriekconventies).
  5. Grafana-dashboards die worden gecodeerd op basis van gen_ai.agent.name en gen_ai.request.model.

Gehosteerde alternatieven (kies er één, niet drie):

  • LangSmith: native integratie met LangGraph; tevens het deploy-doel voor Deep Agents Deploy.
  • Braintrust: de beste keuze wanneer regressietests waarbij eerst evaluatie plaatsvindt prioriteit hebben.
  • Arize Phoenix: OSS, OTLP-native, en combineerbaar met de instrumentatie van OpenInference.
  • De tracing-dashboard van OpenAI: automatisch wanneer je het OpenAI Agents SDK of de Temporal-integratie gebruikt.
  • De tracing van Anthropic’s Claude: voor sessies die binnen Managed Agents draaien.

Het debug-bundle-patroon

Wanneer een run mislukt, moet de worker /workspaces/${THREAD_ID}/_debug/ achterlaten dat de artefacten bevat die je bij een postmortem nodig hebt:

  • session.jsonl: volledige eventlog-dump van PostgresSaver (checkpointer.list({"thread_id": ...})).
  • last_state.json: StateSnapshot.values uit de laatste succesvolle super-step.
  • trace.json: OTLP-geëxporteerde spans voor de run.
  • tool_calls.csv: (ts, tool, input_hash, latency_ms, status, error).
  • workspace.tar.zst: de workspace-directory samen met git diff ten opzichte van de initializer-commit.
  • screenshots/*.png: wat de agent heeft waargenomen.
  • PROGRESS.md, feature-list.json en alle andere door de agent gegenereerde progressiefailen.
  • env.txt: image-tags, modelversie en SHA van de harness-commit.

Dit bundle levert mensen of review-agenten voldoende bewijs om de fout te reconstrueren. “De agent zat vast” is vaag; een gedetailleerd rapport is concreet: de sessie s_123 gebruikte 71 procent van haar tokens om drie commando’s te herhalen nadat npm install faalde.

Het juiste formaat kiezen: een beslisgids

De meeste vergelijkingen hierboven komen neer op een paar belangrijke beslissingen.

Begin met de duur van de run

Gebruik de duur van de run als eerste filter:

  • Minder dan 30 seconden, idempotent: request-lifecycle SDK in een appserver.
  • 30 s tot 60 minuten, geen crashherstel nodig: queue + worker + checkpoint-DB.
  • 60 minuten tot 24 uur: dezelfde queue + worker, of een Cloud Run Job voor éénmalig werk. Gebruik een duurzame workflow-engine als je ook versienummering en replay nodig hebt.
  • Langer dan 24 uur, moet bestand zijn tegen deploys: duurzame workflow-engine (Temporal-stijl). Cloud Run Jobs kunnen langdurig werk opslaan tot aan hun taalimiet, maar ze bieden geen replay-semantiek.
  • Meerdedaagse RL-trainingssessies: K8s Job + volume + Temporal.

Na deze grove filtering moet je kijken naar bijwerkingen, herstelmogelijkheden, replay, isolatie, opslaglocatie van gegevens en het team dat het systeem zal beheren.

Platformaanpassing per gebruiksscenario

De matrix is dichtbevolkt omdat geen enkele groene cel alleen al de architectuur bepaalt. Een brede dekking van werklasten is nuttig, maar geeft geen inzicht in gegevensresidentie, replay-semantiek, afhankelijkheid van providers, operationele volwassenheid of de kosten van het later verplaatsen van staat.

Deep Agents Deploy omvat elk type werklast dat in de matrix wordt genoteerd, waardoor het een geschikte optie is wanneer één platform zowel korte uitvoeringen, meerdere uren durende taken, code-agents, onderzoek-agents als geplande jobs moet ondersteunen. Deze breedte komt echter met een korter productieverleden vergeleken met een stack van queue + worker + Postgres. Beschouw de groene cellen als beweringen over mogelijkheden die geverifieerd moeten worden, en vergelijk ze vervolgens met de operationele beperkingen die de matrix niet kan weergeven.

Anthropic Managed Agents past ofwel volledig bij je werklast, of helemaal niet. Het product kent drie strikte beperkingen: het is uitsluitend gehost, uitsluitend gebaseerd op Claude, en elke sessie duurt minder dan 24 uur. Als je werklast aan al deze voorwaarden voldoet – bijvoorbeeld een interne coderingsagent die in bursts van 2 tot 6 uur draait en waarbij je zelf geen harness wilt beheren – dan is Managed Agents een uitstekende keuze, aangezien dit een groot deel van het platformwerk van je team wegneemt. Als één van de beperkingen niet wordt nageleefd, bijvoorbeeld omdat je een niet-Claude-model, zelfgehoste compatibiliteit of 48-uurs uitvoeringen nodig hebt, past Managed Agents niet; hoeveel configuratiewijzigingen ook worden aangebracht.

Het is raadzaam de prijsmodellering al vóór het maken van een beslissing uit te voeren, en niet erna. Gehostte harness versus eigen harness

De verschillen hier zijn operationeel, en hebben niets te maken met wie de harness-code heeft geschreven. Gehost betekent dat de leverancier de harness-loop op zijn infrastructuur uitvoert en jij een API-aanroep doet. Eigen betekent dat jij de loop op je eigen infrastructuur draait, zelfs als de harness-code zelf afkomstig is van een leverancier.

LangChain komt aan beide kanten van deze scheidslijn voor, wat mensen vaak in de war brengt. Ze leveren LangGraph, een onder MIT-licentie vallende bibliotheek die je zelf kunt hosten (eigen), en Deep Agents Deploy, een beheerd product dat een Deep Agents harness op LangSmith Deployment in zijn standaard cloudmodus uitvoert (gehost). Hetzelfde bedrijf, twee verschillende operationele modellen. Jij kiest het model, niet de leverancier. (Deep Agents Deploy beschikt ook over een zelfgehoste modus voor teams die de gebruikersvriendelijkheid van de harness willen zonder de cloudcomponent; die modus valt onder de categorie ‘eigen’.)

Kies voor een gehostte harness wanneer de ondersteuning voor modellen, de gegevensgrenzen, het herstelgedrag en de uitbreidingspunten al passen. Kies voor een eigen harness wanneer deze beperkingen juist kenmerken zijn die je van plan bent te wijzigen. Migratie tussen de twee verandert de staat, de observabiliteit en de uitvoeringsgrenzen; test dus eerst de overgangsmogelijkheden voordat productiedata daarvan afhankelijk wordt.

Gehosteerde sandbox versus eigen uitvoeromgeving

Kies voor een gehosteerde sandbox wanneer de isolatie, pauze/hervatting of fork-semantiek van de provider overeenkomt met het dreigingsmodel en de beschikbare startbudgetten. Docker of Fargate zijn geschikt voor betrouwbare interne werklasten die toegang tot een VPC of strikte gegevensresidentie nodig hebben, maar een standaardcontainer vormt geen voldoende beveiligingsbarrière tegen kwaadaardig code. Voeg gVisor, Kata, een microVM of een andere versterkte runtime toe wanneer de agent onbetrouwbare pakketten installeert of gegenereerde programma’s uitvoert.

State-opslag: Git, DB en objectopslag naast elkaar

Langlopende agents gebruiken meestal tegelijkertijd drie state-opslagen, omdat elke opslag een ander type artefact bevat.

Git slaat de staat van het werkgebied op: de code, documenten en voortgangsbestanden die door de agent worden gewijzigd. Elke commit biedt het beheersysteem een stabiele herstelpunt en zorgt voor een compacte historie in de volgende sessie.

De checkpoint-database slaat de grafische staat op: wat is besloten, welke knopen zijn uitgevoerd, welke resultaten zijn teruggegeven en wat vervolgens moet worden uitgevoerd. De artefactopslag bevat grote eindresultaten zoals PDF’s, Parquet-bestanden en screenshotten. Deze artefacten horen niet in Git of de checkpoint-database.

Wanneer git als state moet worden gebruikt

Gebruik git wanneer de werklast bestaat uit code (meerdere bestandswijzigingen, refactorings, applicatiegeneratie) of voldoende uit documenten zodat de bestandshistorie belangrijk is. Het patroon is eenvoudig: maak een run-branch aan, voer een initializer-commit uit en commit vervolgens op zinvolle momenten: na de configuratie, na elk feature, nadat de tests zijn geslaagd en na de finale opruiming. Bewaar de SHA van de meest recente workspace-commit naast de checkpoint-regel. Bij hervatting haalt de volgende worker de branch op, leest git log --oneline -8, controleert git status en het meest recente diff, en leest vervolgens PROGRESS.md of het overdrachtsbestand dat de vorige sessie heeft gemaakt.

Hierdoor fungeert git als herstelpunt voor het artefact dat wordt bewerkt, maar vervangt het de checkpoint-database niet. Git kan twee vragen beantwoorden: wat is veranderd en welke versie heeft de tests doorstaan. Het kan het beheersysteem echter niet vertellen welke grafische knoop vervolgens moet worden uitgevoerd, welke toolaanroep nog goedgekeurd moet worden of welke retry al zijn idempotentie-sleutel heeft gebruikt. Anthropic’s beheersysteem maakt gebruik van initializer-commits plus per-feature-commits als bron van waarheid voor het herstellen van het werkgebied; het model leest git log --oneline -8 om de staat te herstellen. Sla git over wanneer het eindproduct slechts één conversatieantwoord is – de extra overhead is dan niet gerechtvaardigd.

Wanneer DB-checkpointing moet worden gebruikt

Gebruik PostgresSaver-stijl checkpointing wanneer de agent een grafische structuur heeft met meerdere knopen waarvan de tussentijdse staat belangrijk is (planner → onderzoeker → schrijver → verifier). Het referentierepo gebruikt dit om precies deze reden. Plaats geen terabyte-grote workspace-artefacten in de checkpoint; die gaan naar objectopslag.

Wanneer een artefactopslag (S3 / GCS) moet worden gebruikt

Gebruik objectopslag wanneer:

  • het resultaat groter is dan de checkpoint-database kan bevatten;
  • downstream-consumenten een via URL bereikbaar artefact nodig hebben zonder via de agent te moeten gaan; of
  • het eindproduct en de run-state verschillende retentietijden hebben.

Bijvoorbeeld: je kunt de sessielog na 30 dagen verwijderen, maar het eindrapport jarenlang bewaren. Gebruik (thread_id, checkpoint_id, artifact_name) om de indeling te keyen, zodat de oorspronkelijke run nog steeds kan worden gereconstrueerd.

Wanneer menselijke goedkeuring vereist is

Voeg goedkeuringsmechanismen toe wanneer een tool‑aanroep destructief en onomkeerbaar is (bijv. schrijven in een database, geldtransacties, verzenden van externe berichten), wanneer de aanroep buiten het actieradiusgebied van de agent valt (productie‑deployments, publicaties voor klanten), of wanneer toezichthouders een review eisen. Zowel LangGraph’s interrupt() als de goedkeuringsmiddleware van Deep Agents bieden ingebouwde ondersteuning voor dergelijke mechanismen. In Deel 4 wordt uitgelegd waarom deze mechanismen een vraagstuk van toestemming zijn, en niet van prompts.

Een praktische controlelijst voor productie

Vooraleer een langlopende agent in productie gaat, beantwoord deze vragen in termen van de concrete infrastructuur.

  1. Welke store beheert de sessie‑evenementen en checkpoints?
  2. Wat gebeurt er als de worker halverwege een tool‑aanroep crasht?
  3. Kan één run de werkruimte van een andere run corrumperen?
  4. Welke acties vereisen goedkeuring?
  5. Kan het model of de sandbox ruwe credentials lezen?
  6. Welke tool‑aanroepen mogen veilig worden herhaald?
  7. Waar wordt de kostenlimiet per run gehandhaafd?
  8. Welke controle op een frisse context bepaalt of een run klaar is?
  9. Waar worden de uiteindelijke outputbestanden opgeslagen nadat de sandbox is afgesloten?
  10. Kunnen we morgen een mislukte run uitleggen zonder hem opnieuw te laten lopen?

Als het antwoord op één van deze vragen is “de prompt instrueert de agent om voorzichtig te zijn”, is het systeem nog niet in productie gebracht; het blijft een demo.

De volgende laag is de harness‑loop

Deze runtime kan ervoor zorgen dat een run actief blijft en herstelbaar is, maar duurzaamheid bewijst niet dat het werk correct is. In Deel 6, Harness Engineering for AI Agents, wordt de cyclus rondom het model besproken: hoe een trace wordt omgezet in een testgeval, waar de regels voor herhalen en stoppen zich bevinden, wat moet worden behouden bij een overdracht, en hoe een externe acceptatiecontrole bepaalt of een run voltooid is.
