AI Agent Evaluation in productie: van traces naar testsuites

Een chatbot geeft je één antwoord om te beoordelen. Een agent geeft je een hele beslisboom: plannen, tool calls, retries en het moment waarop de agent besluit dat hij klaar is.

Dat verschil vereist een andere evaluatiemethode. Een final answer kan correct lijken, terwijl de agent een vereiste tool heeft overgeslagen, een call 17 keer heeft herhaald, een resultaat verkeerd heeft geïnterpreteerd of een pad heeft gevolgd dat production policy verbiedt. Answer-only grading verbergt deze fouten.

TL;DR: Agent evals hebben drie lagen nodig: outcome metrics, trajectory metrics en component metrics. Bouw rond deze loop: trace -> label -> cluster -> dedupe -> versioned dataset -> CI gate -> online monitoring. Gebruik deterministische checks voor tool order, arguments, loops en invariants. Gebruik LLM judges alleen wanneer de check interpretatie vereist, structureer die judges met Schema-Guided Reasoning (SGR) en kalibreer ze tegen human labels voordat je erop vertrouwt.

Waarom agent evals anders zijn

Traditionele LLM evals scoren meestal één input-output-paar: relevance, faithfulness, correctness, safety en soms style. Agents voegen planning, tool calls, retries en termination checks toe, waarbij elke stap een nieuwe plek is waar iets kan misgaan.

Neem een refund agent. Het transcript kan goed eindigen terwijl de trace onjuist is:

lookup_order -> issue_refund -> final_answer

De output eval slaagt. Een trajectory eval moet falen, omdat verify_identity nooit is uitgevoerd vóór issue_refund. Voor tool-using agents zijn answer-only evals smoke tests: ze detecteren totale uitval, maar missen vrijwel alles daaronder.

Er is een tweede probleem: fouten stapelen zich op. Als een workflow 20 vereiste stappen heeft, elke stap onafhankelijk slaagt en elke stap dezelfde betrouwbaarheid van 95% heeft, komt de end-to-end success rate uit op ongeveer 36%:

0.9520≈0.360.95^{20} \approx 0.360.9520≈0.36

De agent kan dus solide lijken in geïsoleerde checks en toch de meeste volledige runs laten mislukken. De oorzaak zit meestal ergens in het midden. Die vinden vereist visibility op componentniveau, niet nog een blik op het antwoord.

Twee onderzoeksteams hebben dit gekwantificeerd.

tau-bench geeft een agent airline- en retail-customer-servicetaken. De agent praat met een gesimuleerde gebruiker, roept APIs aan en moet domain policy volgen. Na het gesprek controleert de grader of de database de geannoteerde goal state heeft bereikt. Een plausibel transcript met de verkeerde rows faalt alsnog.

Onder die grading slaagde zelfs GPT-4o voor minder dan de helft van de taken. Het paper introduceerde ook pass^k: voer dezelfde taak k keer uit en tel de taak alleen als pass wanneer de agent slaagt in alle k runs.

Retailscores die voor één poging acceptabel leken, zakten onder 25% bij k = 8. Bij meer dan driekwart van de taken faalde dezelfde agent minstens één keer wanneer hij acht keer met dezelfde taak werd geconfronteerd. Een eval met één run kan die inconsistentie niet blootleggen.

MAST onderzoekt waarom agents falen. De auteurs annoteerden meer dan 1.600 execution traces van 7 populaire multi-agent frameworks en ordenden de failures in 14 terugkerende modes. De taxonomy omvat vage role definitions (system design), een agent die negeert wat een andere agent heeft gerapporteerd (inter-agent misalignment) en succes verklaren zonder het resultaat te controleren (no verification). Deze failures impliceren prompts, orchestration logic en ontbrekende checks in de harness. Een sterker base model kan geen verification step uitvoeren die nooit is gebouwd. Het evaluatiedoel moet daarom ook de harness rond het model omvatten.

De adoption gap

De State of Agent Engineering-survey van LangChain (1.340 respondenten, afgenomen eind 2025) suggereert dat veel teams al over het ruwe materiaal voor betere evals beschikken: 89% rapporteerde enige vorm van observability, terwijl 52,4% offline evals uitvoerde en 37,3% online evals.

Volgens dezelfde survey heeft 57,3% van de respondenten al agents in productie. Op de vraag wat production blokkeert, noemde 32% quality en 20% latency. Dit is een vendor survey onder de eigen respondenten, geen census van agentteams, maar de resultaten laten wel een nuttige kloof zien tussen trace collection en systematische evaluatie.

Teams blijven daardoor in een ongemakkelijke tussenfase: ze kunnen achteraf een slechte run inspecteren en vervolgens toch exact dezelfde failure nog twee keer shippen.

Elke gediagnosticeerde production failure moet een trace, een label, een dataset row en een scorer achterlaten. Een failure die zich herhaalbaar voordoet, hoort in de regression suite.

Kies metrics op basis van de failure mode

De juiste metric hangt af van de failure mode, niet van het framework. De nuttige indeling heeft drie scopes:

  1. Outcome evals beantwoorden de vraag of de taak is geslaagd.
  2. Trajectory evals beantwoorden de vraag of het pad geldig, efficiënt en policy-compliant was.
  3. Component evals beantwoorden de vraag welke tool, retriever, sub-agent of decision step is stukgelopen.

Elke scope kan offline draaien op vaste, replayable cases vóór release of online op sampled production traces na de response. De guardrails-sectie hieronder behandelt dit onderscheid in detail. Offline evals kunnen goldens vereisen: opgeslagen cases die een input koppelen aan de outcome, tool invariants en arguments die een correcte run moet produceren. Online evals moeten de voorkeur geven aan invariants, distributions en async checks die buiten het request path blijven.

Tool-call correctness

Tool correctness vergelijkt de aangeroepen tools met de verwachte tools. Kies bewust hoe strikt je wilt zijn:

  • Exact match: de sequence moet exact overeenkomen. Gebruik dit wanneer order policy is, bijvoorbeeld lookup_order -> verify_identity -> issue_refund.
  • In-order match: required tools moeten in de juiste relatieve order voorkomen, maar extra harmless calls zijn toegestaan.
  • Any-order match: required tools moeten voorkomen, maar de order mag variëren.

Een kleine lokale scorer is voldoende om te beginnen:

from collections import Counter


def tool_correctness(called: list[str], expected: list[str], mode: str = "in_order") -> float:
    if not expected:
        return 1.0
    if mode == "exact":
        return float(called == expected)
    if mode == "any_order":
        matched = sum((Counter(called) & Counter(expected)).values())
        return matched / len(expected)

    rows = [[0] * (len(expected) + 1) for _ in range(len(called) + 1)]
    for i, tool in enumerate(called):
        for j, wanted in enumerate(expected):
            if tool == wanted:
                rows[i + 1][j + 1] = rows[i][j] + 1
            else:
                rows[i + 1][j + 1] = max(rows[i][j + 1], rows[i + 1][j])
    return rows[-1][-1] / len(expected)


called = ["lookup_order", "check_refund_policy", "issue_refund"]
expected = ["lookup_order", "verify_identity", "issue_refund"]

print(round(tool_correctness(called, expected, "exact"), 3))     # 0.0
print(round(tool_correctness(called, expected, "in_order"), 3))  # 0.667

De score in_order is longest-common-subsequence recall: welk deel van de vereiste sequence in de juiste order behouden bleef. Let op wat deze score negeert. Junk calls verlagen de score niet. Een agent kan hier dus 1.0 scoren terwijl hij twee keer zoveel calls doet als nodig. Wanneer extra calls geld kosten of state muteren, track dan ook precision (gematchte required calls gedeeld door het totale aantal calls) en interpreteer beide samen. Recall detecteert de ontbrekende stap; precision detecteert het rondzwerven.

DeepEval’s Tool Correctness metric biedt dezelfde instellingen via should_consider_ordering en should_exact_match.

Argument correctness

De juiste tool aanroepen met verkeerde arguments is vaak erger dan de verkeerde tool aanroepen, omdat de trace er normaal uitziet.

Valideer voor eenvoudige cases JSON Schema en exacte values. Sla voor semantic cases de verwachte arguments op en beoordeel de deltas:

{
    "trace_id": "tr_2417",
    "input": "Reschedule order A-100 for next Friday.",
    "expected_tools": ["lookup_order", "reschedule_delivery"],
    "expected_arguments": {
        "reschedule_delivery": {
            "order_id": "A-100",
            "date": "2026-06-19"
        }
    }
}

Een tool-name metric kan 2026-06-17 niet detecteren wanneer de policy 2026-06-19 vereist. De dataset moet ook arguments opslaan.

De bijbehorende score is parameter-match: het percentage verwachte (tool, key, value)-triples dat de agent correct heeft ingevuld.

def argument_correctness(called_args: dict, expected_args: dict) -> float:
    total = matched = 0
    for tool, params in expected_args.items():
        for key, want in params.items():
            total += 1
            if called_args.get(tool, {}).get(key) == want:
                matched += 1
    return matched / total if total else 1.0

Exacte equality is geschikt voor IDs, enums en dates die al naar één format zijn genormaliseerd. Ze is ongeschikt voor vrije tekst, floats en dates in het format dat het model heeft geproduceerd, waarbij == een correct antwoord als fout markeert. Beoordeel die fields volgens hun eigen regels: een normalized string match, een date parse of een numeric tolerance. De metric blijft hetzelfde; de comparator per field verandert.

Efficiency, loops en dead ends

Een agent die de taak afrondt na vijf redundante tool calls laat nog steeds een planningprobleem zien en kost meer om te draaien.

Begin met deze goedkope signalen:

  • Redundant-call rate: identieke tool calls met identieke arguments die meer dan twee keer worden herhaald.
  • Trace shape anomalies: plotselinge pieken in depth, tool-call count, token count, latency of cost.
  • Path convergence: hoe dicht de run bij het kortste bekende geldige pad voor de taak komt.
  • Termination correctness: of de agent te vroeg stopte, na succes bleef doorwerken of succes verklaarde zonder de vereiste state change.
  • Plan adherence: als de agent vóór het handelen een plan schrijft, controleer dan of de trace dat plan volgt. Een goed plan dat wordt genegeerd en een slecht plan dat perfect wordt gevolgd, falen beide, maar om tegenovergestelde redenen. Het verschil tussen plan en trace vertelt je welke van de twee het is.

Voer deze checks waar mogelijk vóór een judge uit. Een loop detector bestaat uit enkele regels over de trace. Daarvoor is geen model nodig.

Task completion en outcome grading

End-to-end luidt de vraag: “heeft de gebruiker gekregen waar hij om vroeg?”

Twee patronen werken het best:

  • Referenceless task-completion judging: haal het doel uit de input en beoordeel of de trace plus final answer dit doel heeft bereikt. Dit werkt online, omdat production traffic zelden golden outputs heeft.
  • Environment-state grading: vergelijk de finale database rows, files, tickets, bookings of records met een geannoteerde goal state. Dit is robuuster dan transcript matching, omdat agents geldige paden kunnen vinden die je niet vooraf hebt uitgeschreven.

De tweede optie is beter wanneer je die kunt bouwen. De final state is het contract. Het transcript is alleen bewijs.

Twee kanttekeningen houden dit eerlijk. Een 2025 audit van agentic benchmarks liet zien dat tau-bench sommige taken uitsluitend op basis van de database state grade. Bij taken waarvan de geannoteerde outcome geen state change en geen specifieke tekst vereist, slaagt een agent die niets doet daardoor alsnog: 38% op de airline split en 6,0% op retail, bij elke k. En Anthropic rapporteerde een Opus 4.5-run die een tau2-bench-bookingtaak “faalde” door een policy loophole te vinden die voor de gebruiker feitelijk de betere uitkomst was. State grading is beter dan transcript matching, maar de goal state blijft een annotation en annotations bevatten bugs. Audit ook de cases die te gemakkelijk slagen, niet alleen de cases die falen.

Component evals

Outcome- en trajectory metrics laten zien dat een run is gefaald en ongeveer waar dat gebeurde. Component evals scoren één span: was de retrieved chunk relevant, gaf de sub-agent het schema terug dat de caller verwachtte, kon de eigen response van de tool worden geparsed? Koppel de score aan de span in plaats van aan de run, zodat “welke tool is deze week verslechterd?” een query wordt in plaats van een rerun.

Drie checks dekken het grootste deel:

  • Per-span scoring: voer de metric uit die bij het type span past. Retrieval spans krijgen recall en precision tegen de geannoteerde chunk, sub-agent spans krijgen schema validation plus hun eigen tool-correctness score, en tool spans krijgen error rate en latency.
  • Tool-result interpretation: geef de agent een correct maar lastig tool output (een lege list, een partial match of een stale timestamp) en controleer wat hij daarna doet. Een tool kan correct zijn terwijl de agent het resultaat verkeerd leest; die failure wordt pas twee stappen later zichtbaar.
  • Failure attribution: de zichtbare failure ligt meestal downstream van de werkelijke oorzaak. Wijs de failure toe aan de vroegste span waarvan de output al verkeerd was, niet aan de stap die de error veroorzaakte.

Hier komt ook de compounding math uit het begin van pas. Als 20 stappen er afzonderlijk goed uitzien en de run toch meestal faalt, laten per-span pass rates zien welke stap daadwerkelijk op 95% draait en welke op 70%.

De trace-to-eval flywheel

Mine production failures voordat je extra eval cases bedenkt.

De loop:

  1. Leg de volledige trace vast.
  2. Label wat er is misgegaan.
  3. Groepeer vergelijkbare failures.
  4. Behoud één representatieve golden per cluster.
  5. Versioneer de dataset.
  6. Draai die in CI.
  7. Blijf sampled production traces online scoren.

De bijbehorende repository trace2evals implementeert de volledige loop voor een faulty support agent. De repository legt OpenTelemetry GenAI spans vast, detecteert failures met deterministische regels, dedupliceert cases tot een versioned golden dataset en draait elke golden opnieuw in CI. De default backend vervangt het model door deterministische regels die de beslissingen van de buggy agent opnieuw uitvoeren, zodat make demo de volledige loop offline reproduceert zonder API key. Stel een API key in en dezelfde commands sturen een real model aan.

Mine failures met error analysis

Hamel Husain en Shreya Shankar beschrijven een error-analysis workflow voor precies deze stap; Hamels field guide loopt er stap voor stap doorheen. De eerste twee stappen ontlenen hun namen aan kwalitatief onderzoek, maar de methode is eenvoudig: lees traces, maak notities en benoem de patronen.

  1. Open coding: lees 30 tot 50 echte traces en schrijf vrijvormige notities over wat er misging.
  2. Axial coding: cluster die notities in 5 of 6 benoemde failure categories.
  3. Label alles aan de hand van de taxonomy.
  4. Bouw metrics voor de grootste buckets.

Begin niet met labels als reasoning_issue of tool_problem. Die zijn te vaag om te testen. Gebruik labels als missing_identity_verification, date_argument_mismatch, retried_same_tool_after_429 of stopped_before_database_update. Een label met deze mate van specificiteit vertelt je precies wat de regression test moet assert-en.

Deduplicate voordat je cases promoveert

De trace-mining loop heeft een valkuil: voor altijd elke bad trace toevoegen. Zo ontstaat een dataset die groot, duur en smal is. De suite slaagt dan op near-duplicates uit maart, terwijl de nieuwe vorm van dezelfde bug in juni wordt gemist.

Groepeer eerst. Promoveer één representatieve golden per cluster. Sla de gerelateerde trace IDs op in metadata, zodat een reviewer het production evidence later kan inspecteren.

Als een failure cluster na een fix terugkeert, heeft de regression case niet voldoende gegeneraliseerd. Cluster opnieuw en verbreed de golden in plaats van 15 point examples toe te voegen.

Versioneer de dataset

Versioneer datasets op dezelfde manier als prompts en code. Wanneer er iets betekenisvol verandert (model, prompt, tool schema, judge prompt of app behavior), wil je dezelfde dataset version vóór en na de wijziging uitvoeren.

De CI gate moet het volgende pinnen:

  • dataset version
  • app version
  • prompt version
  • judge model
  • judge prompt
  • evaluator code version

Als een van deze onderdelen verandert, wordt je before/after comparison onduidelijk. Een goldens-v3.json-file in git is op kleine schaal prima. Tool-native snapshots in Langfuse, Phoenix, Braintrust of LangSmith zijn nuttig zodra de dataset collaborative wordt.

Gate CI

Een falende metric moet een falende build opleveren, anders is de eval suite slechts een dashboard waar niemand naar kijkt.

De test moet de huidige agent opnieuw draaien met de golden input. Hij moet niet alleen de oude failed trace replayen (schets; de runnable versie staat in de companion repository):

@pytest.mark.parametrize("golden", GOLDENS, ids=[item["id"] for item in GOLDENS])
def test_agent_regression(golden: dict) -> None:
    answer, fresh_trace = run_agent_and_capture_trace(golden["input"])

    refired = set(flag_failures(fresh_trace)) & set(golden["failure_modes"])
    assert not refired, f"failure mode regressed: {sorted(refired)}"

    assert tool_correctness(
        called=[call["name"] for call in fresh_trace["tool_calls"]],
        expected=golden["expected_tools"],
        mode=golden.get("tool_match", "in_order"),
    ) >= golden.get("tool_threshold", 1.0)

Dit onderscheid is gemakkelijk verkeerd te implementeren. De taak van de dataset is om te detecteren dat de volgende agent version een oude failure opnieuw maakt, niet om de failure zelf te archiveren.

Kalibreer de judge voordat je erop vertrouwt

LLM-as-judge is nuttig. Je kunt jezelf er ook gemakkelijk mee voor de gek houden.

G-Eval vraagt een judge om vóór het scoren expliciete rubric-stappen te schrijven. Vervolgens telt de judge elk rating level op, gewogen met de token probability (score=∑ip(si) si\text{score} = \sum_i p(s_i)\,s_iscore=∑i​p(si​)si​). Dit protocol kwam beter overeen met human ratings dan de oudere automatische metrics die het verving.

Voor de probability-weighted step zijn judge logprobs nodig, die sommige hosted models niet beschikbaar maken. Het bredere resultaat ondersteunt nog steeds een expliciet rubric path boven een kale score.

MT-Bench liet zien dat GPT-4 ongeveer even vaak instemde met human preferences als mensen onderling. Dat resultaat hielp om LLM judging mainstream te maken. Later onderzoek bracht position-, length- en self-preference-biases aan het licht. Judge scores kunnen ook verschuiven wanneer de prompt of model version verandert.

JudgeBench bouwde response pairs waarin één antwoord objectief fout is op het gebied van verifiable knowledge, reasoning, math en code. Met een standaard judge prompt scoorde GPT-4o 50,9%, nauwelijks boven een coin flip. Claude 3.5 Sonnet, de beste geteste non-reasoning judge, kwam uit op 64,3%, terwijl o3-mini met high reasoning effort 80,9% bereikte. Confident maar foute antwoorden blijven moeilijk voor een judge die niet reasoned voordat hij grade.

Behandel de judge als een measurement instrument: kalibreer hem tegen human labels voordat hij iets grade, en controleer hem opnieuw wanneer het judge model of de prompt verandert.

Wanneer een judge nodig is, maak de verdict structured. Schema-Guided Reasoning (SGR) definieert het reasoning path van de judge als een Pydantic-schema. Structured Outputs of constrained decoding vereist vervolgens fields zoals evidence, passed_criteria, failed_criteria, failure_mode en score.

Plaats evidence fields vóór de score. De judge past dan bij elke run en voor elk compatible model dezelfde vooraf gedefinieerde rubric stages in dezelfde field order toe. Een reviewer kan benoemde fields inspecteren in plaats van een paragraaf te parsen. CI kan een stabiel JSON-object diffen, terwijl de calibration set zichtbaar maakt met welke rubric stage het human label niet overeenkwam.

Een structured verdict kan ook de cost curve veranderen. Behandel een goedkoper model als candidate, niet als automatische replacement. Draai het over dezelfde human-labeled calibration set. Vergelijk agreement, false-pass rate en false-fail rate met de grotere judge. Gebruik het goedkopere model alleen voor routine cases als het de thresholds van je applicatie haalt. Houd de grotere judge voor disagreements, high-risk cases of calibration runs.

Standaardchecklist voor judge hygiene:

  1. Geef waar mogelijk de voorkeur aan binary pass/fail. Schalen met vijf punten nodigen uit tot schijnprecisie.
  2. Label 30 tot 50 trajectories met de hand voordat je de definitieve rubric schrijft.
  3. Meet judge-human agreement met Cohens kappa (agreement gecorrigeerd voor toeval; een judge die altijd “pass” zegt, scoort daardoor bijna nul) of met eenvoudige TPR/TNR.
  4. Decompose coarse criteria. “Heeft de agent identity geverifieerd vóór de refund tool call?” is beter dan “Was de trajectory goed?”
  5. Emit de verdict via een SGR-schema met evidence, failed criteria, failure mode en score.
  6. Gebruik waar mogelijk een judge uit een andere model family dan de generator.
  7. Randomize pairwise order en neem het gemiddelde van beide richtingen.
  8. Penalize unsupported length in de rubric. Een langer antwoord is geen beter antwoord.
  9. Pin het judge model, de prompt, de dataset, het schema en de app version.
  10. Recalibreer na wijzigingen aan model, prompt, tool, policy of schema.

Gebruik voor high-stakes scores een kleine jury in plaats van één grote judge. PoLL testte een panel van kleinere judges uit disjuncte model families en poolde hun verdicts. Over zes datasets kwam het panel beter overeen met human judgments dan één GPT-4 judge. Het vermeed ook de self-preference bias van één judge en kostte meer dan zeven keer minder. Houd human review voor beslissingen die money, access, safety of compliance beïnvloeden.

Als een judge op jouw taak met een kappa van 0,55 overeenkomt met humans, gebruik hem dan niet om deploys te blokkeren. Gebruik hem om review queues te sorteren. Ligt de score rond 0,75 en zijn de failure costs matig, dan is een CI gate veel beter te verdedigen.

Guardrails blokkeren inline; online evals observeren achteraf

Mensen halen deze twee door elkaar omdat beide scores produceren. Het verschil zit in de plaatsing: inline in het request path, vóór release of na de response.

Guardrails draaien inline. Ze zijn snel en zichtbaar voor de gebruiker. Een guardrail kan een tool call blokkeren, PII redigeren, prompt injection afwijzen of vóór het verlaten van je systeem een retry afdwingen. Een false positive is een production bug. Een false negative is stiller en erger: schema-, range- en policy checks zijn echt deterministisch, maar injection- en PII-detectie zijn classifiers. Beschouw misses daar dus als te verwachten en laat een async eval monitoren wat erdoorheen komt.

Offline evals draaien vóór release. Ze zijn reproducible. Ze gaten prompts, models, tools, retrievers en policies tegen een vaste dataset.

Online evals draaien na de response, meestal op sampled traffic. Ze kunnen langzamere LLM judges gebruiken omdat ze niet in het latency path zitten. Hun taak is drift detecteren, nieuwe failure clusters vinden en de volgende offline dataset voeden.

Een verkeerde plaatsing doet in beide gevallen pijn:

  • Een judge in het request path voegt latency en een nieuwe bron van flakiness toe.
  • Een guardrail die tot async scoring wordt gedegradeerd, laat policy violations gebruikers bereiken.

Score voor systemen met een hoge load een kleine sample met een sterkere judge en een bredere sample met goedkopere classifiers. Alarmeer op clusters en confidence bounds, niet op één noisy point estimate.

De trade-off-notities beschrijven waar kosten vandaan komen, niet wat de tools zijn. Pricing pages veranderen en vendors tellen verschillende zaken: traces, observations, spans, scores, users, retention of processed data. Controleer live pricing opnieuw voordat je je vastlegt.

Korte beslisregels:

  • Heb je self-hosted tracing met OTel portability nodig: begin met Phoenix of Langfuse.
  • Heb je een code-first CI gate nodig: begin met DeepEval.
  • Ben je al committed aan LangGraph: LangSmith is handig.
  • Wil je managed PR regression review: Braintrust is moeilijk te verslaan.
  • Domineren security- en red-team cases: Promptfoo is de gerichte tool.
  • Gaat het om safety research of controlled benchmark work: Inspect AI past beter.

Tool choice is secundair. Als production failures geen test cases worden, betaal je vooral voor trace storage.

Praktische rollout-checklist

Bouw eerst de evidence pipeline voordat je de metric stack uitbreidt. Begin met bepalen waar de voorbeelden vandaan komen.

  1. Verzamel eerst historische runs. Bestaat de agent al, haal dan traces, support tickets, bug reports, thumbs-down sessions, manual QA transcripts en dogfooding notes op voordat je de implementation wijzigt. Bestaat de agent nog niet, log dan vanaf dag één elke prototype- en manual test run.

  2. Instrumenteer de trace shape. Leg messages, tool calls, arguments, tool outputs, errors, token counts, latency, cost, user feedback, app version, prompt version, model version, tool schema version en de final environment state vast. Gebruik OpenTelemetry GenAI conventions of OpenInference-style spans als je portability wilt. Gebruik Langfuse, LangSmith, Phoenix of Braintrust als je direct een trace UI en dataset workflow wilt.

  3. Maak seed cases van echte failures. Lees de traces voordat je ze met een model samenvat. Sla voor elke bruikbare failure de input, source trace ID, expected state, expected tool invariants, failure mode, severity en reviewer note op. Langfuse kan dataset items koppelen aan production traces; LangSmith kan datasets maken van traced runs. Bewaar de source link zodat de case auditable blijft.

  4. Genereer cold-start cases als er geen history is. Vraag een LLM om tasks te draften op basis van product requirements, policies, tool schemas, state machines en support macros. Dek happy paths en failures af, zoals verkeerde permissions, ontbrekende identity checks, stale tool results, ambigue dates, retries na rate limits en tegenstrijdige tool output.

  5. Vertrouw synthetic cases pas na human review. Synthetic examples zijn nuttig voor coverage, niet voor truth. Markeer ze met source: synthetic en vereis dat een reviewer de expected outcome goedkeurt. Draai waar mogelijk een known-good reference path en gebruik verschillende model families om de case te genereren en het resultaat te judgen.

  6. Bouw een kleine balanced dataset. Neem successes, failures, refusals, boundary cases, long-turn cases, policy-sensitive cases en valid alternate paths op. Maak de golden niet tot “het exacte oude transcript”. De golden moet de required outcome, toegestane invariants en failure mode coderen.

  7. Voeg eerst deterministische checks toe. Required tool order wanneer order policy is, required arguments, schema validation, final-state diffs, loop limits, token- en latency ceilings en task-specific invariants moeten vóór elke judge draaien.

  8. Voeg één SGR-shaped judge toe. Gebruik die alleen voor het deel dat interpretatie vereist. Kalibreer hem tegen human labels. Als hij op de calibration set geen goede en slechte voorbeelden van elkaar kan onderscheiden, verbeter dan eerst de rubric voordat je hem aan CI koppelt.

  9. Verbind de loop. Draai de kleine offline suite in CI, draai de grotere suite vóór release, score sampled production traffic online en promoveer terugkerende online failure clusters naar de offline dataset.

Je eerste eval suite zal op saaie manieren verkeerd zijn. Ship hem toch. Een suite die je elke dag draait, is gemakkelijker te verbeteren dan een perfect design document dat nooit een bad PR blokkeert.
