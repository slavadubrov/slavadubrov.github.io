Deel I — Hardware foundations

De concepten hier — arithmetic intensity, de GPU memory hierarchy en de hardwaretermen — komen overal elders in deze guide terug.

1. Memory-bound versus compute-bound en het roofline model

Het startpunt voor LLM-performance is arithmetic intensity: hoeveel nuttige berekeningen voert de GPU uit voor elke byte data die hij uit memory laadt? Die verhouding bepaalt of een operatie compute-bound is (wachten op de processor) of memory-bound (wachten tot data is geladen).

Elke GPU heeft een drempel voor “critical intensity” waarbij de compute-capability precies in balans is met de memory bandwidth. Voor een NVIDIA H100 SXM in sparse TF32-modus (NVIDIA H100 specifications):

989 TFLOPS3.35 TB/s≈295 FLOPs/byte\frac{989 \text{ TFLOPS}}{3.35 \text{ TB/s}} \approx 295 \text{ FLOPs/byte}3.35 TB/s989 TFLOPS​≈295 FLOPs/byte

Batch-one decode en long of voldoende gebatchte prefill bevinden zich doorgaans aan tegenovergestelde kanten van deze drempel:

  • Decode is memory-bound. Tokens één voor één genereren betekent dat de multi-gigabyte weight matrix uit memory moet worden geladen om ermee te vermenigvuldigen voor één nieuwe token. In een vereenvoudigde 16-bit, batch-one-analyse heeft de operatie ongeveer 1 FLOP/byte, bijna 300x onder de H100-roofline-drempel. Dat verschil verklaart waarom decode in dit regime de peak compute throughput niet kan benaderen.
  • Long of voldoende gebatchte prefill is vaak compute-bound. Bij het verwerken van veel prompt tokens worden weights hergebruikt in grote matrixmultiplications, waardoor arithmetic intensity boven de roofline-drempel kan komen. Korte prompts en kleine batches kunnen daarentegen worden beperkt door memory traffic of kernel-launch-overhead.

Om decode te versnellen, werk je dus aan memory bandwidth: verklein de weights met quantization, verlaag de KV-memory-overhead met GQA en PagedAttention en verhoog de intensity met batching. Voor long of goed gebatchte prefills kunnen snellere matrixberekeningen en compute met lagere precision helpen; profileer workloads met korte prefill afzonderlijk.

2. GPU memory hierarchy

Een GPU heeft vier memorylagen, gerangschikt als een piramide: grote maar trage main memory (HBM) onderaan en kleine maar zeer snelle registers bovenaan. Data door deze hierarchy verplaatsen is een belangrijke performancebeperking.

Van snel naar langzaam op een H100:

  1. Registers zijn de snelste memory en zijn direct gekoppeld aan processing threads. Voor Hopper’s WGMMA kan matrix A uit registers of shared memory komen, terwijl matrix B uit shared memory komt.
  2. SRAM (shared memory) is snelle on-chip working memory die lokaal is voor elke SM.
  3. L2 cache is een gedeelde laag van 50 MB. Die kan data serveren die over SMs heen wordt hergebruikt, zonder een nieuwe HBM-fetch.
  4. HBM3 is de main memory van 80 GB waarin model weights en de KV cache staan, met ~3.35 TB/s bandwidth.

FlashAttention en kernel fusion verlagen HBM-traffic door intermediate work on-chip te houden of te combineren. PagedAttention richt zich op een ander probleem: het mapt logische KV-blocks naar niet-contigue fysieke GPU-memory-blocks, waardoor fragmentation afneemt en block sharing mogelijk wordt.

3. GPU hardware glossary

De onderstaande termen komen in de rest van deze guide terug.

HBM (High Bandwidth Memory) stackt DRAM dies die via through-silicon vias (TSVs) zijn verbonden naast de GPU die. Generaties zijn onder meer HBM2e (A100, 2 TB/s), HBM3 (H100, 3.35 TB/s) en HBM3e (H200/B200, 4.8–8 TB/s). HBM-bandwidth is een directe beperking voor TPOT in memory-bound decode-regimes.

GDDR (Graphics DDR) is traditionele graphics memory voor consumer- en workstation-GPUs zoals de RTX 4090 en L40S. De bandwidth is lager dan bij HBM, maar de kosten per GB zijn lager. GDDR6X op de RTX 4090 levert ongeveer 1 TB/s, tegenover 3.35 TB/s HBM3-bandwidth op de H100.

Een SM (Streaming Multiprocessor) is het basisblok voor compute in een NVIDIA GPU. Elke SM bevat CUDA cores, Tensor Cores, shared memory en een warp scheduler. De H100 heeft 132 SMs; de A100 heeft er 108.

Tensor Cores zijn gespecialiseerde matrix-multiply-accumulate-units binnen elke SM. Ze versnellen de mixed-precision matmuls die het grootste deel van transformer-compute vormen. H100 SXM Tensor Cores leveren 494.5 dense of 989 sparse TF32 TFLOPS; vermeld bij vergelijking altijd de precision- en sparsity-modus.

CUDA Cores zijn general-purpose floating-point- en integer-units. Ze verwerken element-wise operations, activation functions en ander werk dat niet uit matrixoperaties bestaat terwijl Tensor Cores ondersteunde matrixoperaties uitvoeren.

Een warp is een groep van 32 threads die lockstep op een SM uitvoeren en daarmee NVIDIA’s kleinste scheduling unit vormen. Warp specialization wijst verschillende warps toe aan data movement en compute, zodat de taken kunnen overlappen.

NVLink is NVIDIA’s high-speed GPU-to-GPU-interconnect binnen een node. NVLink 4.0 op de H100 levert 900 GB/s bidirectional bandwidth; NVLink 5.0 op de B200 bereikt 1.8 TB/s. Deze bandwidth is belangrijk voor tensor parallelism, omdat GPUs bij elke transformerlaag partial results uitwisselen.

InfiniBand is een high-speed network fabric voor communicatie tussen nodes. InfiniBand-adapters uit de ConnectX-klasse leveren de inter-node fabric voor pipeline-parallel of distributed-training-traffic; de bandwidth hangt af van de adapter en portconfiguratie.

RDMA (Remote Direct Memory Access) laat een device memory op een andere machine benaderen zonder de datapath via een CPU te routeren. GPUDirect RDMA ondersteunt directe GPU-to-GPU-transfers tussen nodes, waaronder KV-cache-transfers in disaggregated serving.

NVMe (Non-Volatile Memory Express) is de SSD-interface voor KV-cache-offloading en ZeRO-Infinity-parameter-offloading wanneer GPU- en CPU-memory ontoereikend zijn. Sequential bandwidth hangt af van drive en workload en blijft ver onder HBM-bandwidth.

TFLOPS en PFLOPS zijn respectievelijk triljoenen en biljarden floating-point operations per seconde. Eén TFLOPS is 101210^{12}1012 FLOPS. De H100 haalt 989 sparse TF32 tensor TFLOPS, terwijl FlashAttention-3 ongeveer 1.2 PFLOPS in FP8 rapporteert; deze waarden gebruiken verschillende formats en mogen niet alsof het één metric is met elkaar worden vergeleken.

Deel II — Inference fundamentals

Inference is het deel van het system dat gebruikers daadwerkelijk ervaren. Latency, de KV cache, het two-phase execution model, attention en quantization bepalen samen hoe snel, goedkoop en betrouwbaar je kunt serven.

4. Latency: TTFT, TPOT en percentielen

Time to First Token (TTFT) is de end-to-end delay van het indienen van een request tot de eerste output token. Dit omvat queueing, tokenization, scheduling, prompt prefill, de eerste decode-step en network delivery. Langere prompts verhogen doorgaans het prefill-component, maar elk van deze stages kan dominant worden. Targets zijn productspecifiek; MLPerf Inference v5.0 gebruikt een P99 TTFT-limiet van ≤\leq≤ 450 ms voor het interactieve Llama 2 70B-scenario.

Time Per Output Token (TPOT) is het gemiddelde interval tussen opeenvolgende tokens na de eerste token. Dit correspondeert met de decode-fase. Batch-one of low-intensity decode is doorgaans memory-bandwidth-bound, terwijl voldoende grote batches compute-bound kunnen worden:

TPOT=E2E Latency−TTFTOutput Tokens−1\text{TPOT} = \frac{\text{E2E Latency} - \text{TTFT}}{\text{Output Tokens} - 1}TPOT=Output Tokens−1E2E Latency−TTFT​

Deze definitie vereist minstens twee output tokens; TPOT is niet gedefinieerd voor een response van één token.

De gemiddelde stille leessnelheid van volwassen Engelstalige lezers is ongeveer 238 woorden per minuut voor non-fictie (Brysbaert, 2019). Streaming-targets moeten nog steeds uit producttests komen; MLPerf gebruikt een P99 TPOT-limiet van ≤\leq≤ 40 ms voor zijn interactieve scenario.

P50 versus P99 latency is belangrijk omdat de mediaan de tail verbergt. Een system met een goede P50 en slechte P99 kan problemen hebben met batching, preemption, queueing of workload-skew; traces zijn nodig om ze van elkaar te onderscheiden.

5. Throughput: tokens per seconde en de latency trade-off

Throughput wordt gemeten in output tokens per second over concurrent requests. Requests per second is op zichzelf een zwakkere metric, omdat een response van 10 tokens en een response van 1.000 tokens zeer verschillende kosten hebben. Gepubliceerde benchmarkcijfers variëren met model, precision, hardware, prompt- en outputlengte, concurrency en SLO. Vergelijk vLLM, SGLang en TensorRT-LLM met één harness in plaats van hun headline results te combineren.

De trade-off: bij lage concurrency krijgt elk request uitstekende latency, maar wordt de GPU onderbenut. Een grotere batch size verhoogt throughput bijna lineair tot compute verzadigd raakt; daarna loopt latency sterk op. Goodput, de rate van requests per second die aan je SLO-targets voldoen, verbindt raw throughput met wat gebruikers werkelijk ervaren.

6. KV cache: de bottleneck achter de meeste andere bottlenecks

Tijdens autoregressive generation attendt elke nieuwe token op elke eerdere token. De KV cache bewaart de Key- en Value-projections van elke token in elke laag om O(n2)O(n^2)O(n2) recomputation te vermijden. Zonder deze cache zou het genereren van token nnn vereisen dat het model opnieuw over alle n−1n-1n−1 eerdere tokens wordt uitgevoerd.

De KV cache kan de dominante variabele memory pressure worden bij lange sequence lengths of hoge concurrency, omdat hij lineair groeit met sequence length, batch size en layer count:

KVcache=2×L×hkv×dh×s×B×bytesKVcache = 2 \times L \times h_{kv} \times d_h \times s \times B \times \text{bytes}KVcache=2×L×hkv​×dh​×s×B×bytes

waarbij:

  • LLL = aantal layers
  • hkvh_{kv}hkv​ = aantal KV heads
  • dhd_hdh​ = head dimension
  • sss = sequence length
  • BBB = batch size
  • bytes\text{bytes}bytes = bytes per cached element, bepaald door de KV-cache-precision

Concrete voorbeelden met FP16 en batch size 1: Llama 3.1 8B gebruikt bij 8.192 tokens ~1.0 GB KV cache; bij 128K tokens 16 GB. Llama 3.1 70B heeft bij 128K tokens ~40 GB nodig voor één sequence, de helft van de VRAM van een H100. Bij hoge concurrency of long context kan de KV cache groter worden dan de memory voor model weights; het resultaat hangt af van sequence length, active batch size, KV precision en het aantal KV heads. Naive implementations verspillen 60–80% van de gealloceerde KV memory aan fragmentation. Dat is het probleem waarvoor PagedAttention is ontworpen.

De belangrijkste optimizations zijn GQA (minder KV heads), KV-cache-quantization (FP8/INT8), PagedAttention (block-based allocation met <4% waste) en offloading van de KV cache naar CPU of NVMe.

7. Prefill versus decode: twee fasen, twee bottlenecks

De prefill phase verwerkt de input prompt in parallel en vult de KV cache. Long of voldoende gebatchte prefills worden vaak compute-bound, omdat ze grote matrixmultiplications gebruiken; korte prefills kunnen beperkt blijven door memory traffic of kernel-launch-overhead. Prefill draagt bij aan time to first token (TTFT), naast queueing, tokenization, scheduling, de eerste decode-step en network delivery. De decode phase genereert één token per keer. Elke step leest model weights en de KV cache uit HBM, waardoor batch-one decode memory-bandwidth-bound is en de belangrijkste driver van time per output token (TPOT).

Chunked prefill splitst de prompt op in chunks met vaste grootte in plaats van alles in één keer te verwerken. Een scheduler kan deze chunks interleaven met decode-work, zodat één lange prompt een iteration niet monopoliseert. Sarathi-Serve rapporteert betere throughput-latency-trade-offs in de geteste workloads, maar de winst hangt af van model, hardware, request-length distribution, chunk size en comparison baseline. Extra scheduling en kleinere kernels kunnen TTFT voor het nieuwe request verhogen.

Disaggregated serving plaatst prefill en decode in afzonderlijke GPU-pools, zodat elke pool een andere bottleneck kan targeten. Splitwise en DistServe beschrijven dit pattern. De pools transporteren KV-cache-data via een snelle interconnect zoals RDMA, waardoor communication cost onderdeel wordt van het design.

8. GQA en MQA: de KV cache verkleinen

Standard Multi-Head Attention (MHA) geeft elke query head een eigen K- en V-head. Multi-Query Attention (MQA) deelt één KV head over alle query heads; dit is een extreme reductie. Grouped-Query Attention (GQA) is de praktische middenweg: groepen query heads delen één KV head.

Llama 3 70B gebruikt 64 query heads maar slechts 8 KV heads: een 8x reductie van de KV cache tegenover dezelfde architecture met één KV head per query head. Llama 3.1 405B gebruikt 128 query heads en 8 KV heads, een 16x reductie volgens dezelfde berekening (Meta, 2024). Ainslie et al. rapporteren GQA-quality die in hun geteste models dicht bij MHA ligt en MQA-snelheid benadert. Een kleinere KV cache kan grotere batches ondersteunen, maar de gerealiseerde latency- en throughput-winst hangt nog steeds af van kernel en workload.

9. Quantization: bits inruilen voor speed en memory

Quantization verlaagt de precision van model weights en/of activations. De belangrijkste trade-offs:

AWQ (Activation-Aware Weight Quantization) identificeert salient weight channels op basis van activation magnitudes en past per-channel scaling toe om deze te beschermen. De calibration-behoefte hangt af van model en configuratie; in één OPT-6.7B INT3-g128-vergelijking gebruikte AWQ 16 calibration sequences en GPTQ 192. Rapporteer in een reproduceerbare setup zowel het aantal sequences als de sequence length. GPTQ gebruikt approximate second-order information voor layer-wise quantization. bitsandbytes kan quantization uitvoeren tijdens het laden van het model, zonder afzonderlijke preprocessing-pass; het NF4-format vormt de basis voor QLoRA fine-tuning. FP8 op Hopper-class hardware halveert de weight memory ten opzichte van FP16/BF16, maar quality en speed hangen nog steeds af van model, calibration en kernel.

De serving-kernel kan even belangrijk zijn als het quantization-algorithm. Section 10 geeft een begrensd Marlin-resultaat en legt uit waarom de winst afhangt van de servingconfiguratie.

Deel III — Inference optimizations

Elke softwaretechniek hier richt zich op een specifieke bottleneck: FlashAttention benut de SRAM-HBM-gap, PagedAttention verwijdert KV-cache-fragmentation en continuous batching houdt de GPU bezig.

10. CUDA kernels en kernel fusion

Een CUDA kernel is een functie voor de GPU die parallel over duizenden threads draait. Wanneer de CPU een kernel aanroept, verdeelt de GPU het werk over zijn SMs: elke SM draait meerdere warps van 32 threads en elke thread verwerkt een deel van de data. Elke operatie in LLM inference, van matrixmultiplication tot token sampling, is uiteindelijk een kernel launch. Eén forward pass door een 70B-model triggert honderden tot duizenden kernel launches; het verschil tussen een naive kernel en een geoptimaliseerde kernel kan bepalen of je system zijn latency-SLO haalt.

De belangrijkste kernelcategorieën in LLM serving:

  • GEMM kernels voor matrixmultiplication, die zowel prefill- als decode-compute domineren.
  • Attention kernels zoals FlashAttention, die berekeningen tilen zodat ze in SRAM blijven in plaats van naar HBM te spillen.
  • Fused kernels die meerdere operations combineren (zoals add + layer norm of QKV projection) in één launch om intermediate HBM round-trips over te slaan.
  • Sampling kernels die logits via top-k-, top-p- of temperature-sampling omzetten naar token IDs.

Kernelkwaliteit kan bepalen of compressed weights daadwerkelijk een speedup opleveren. Het Marlin-paper rapporteert tot 2.8x end-to-end speedup tegenover zijn FP16-baseline voor geteste weight-only INT4 vLLM-configuraties. Dat resultaat is specifiek voor de models, GPUs, batch sizes en serving setup van het paper en is dus geen universele INT4-winst.

Triton verlaagt de drempel voor het schrijven van custom kernels door GPU-programming via Python aan te bieden in plaats van raw CUDA C++. Daardoor komt kernel-level optimization binnen bereik van ML engineers en niet alleen GPU-specialisten. De meeste optimizations verderop in dit deel (FlashAttention, fused kernels, PagedAttention) zijn betere kernels of slimmere manieren om kernel launches te orchestreren.

Kernel fusion combineert sequentiële operations in één GPU kernel en slaat intermediate HBM writes over. Veelvoorkomende fusions zijn QKV projection, attention plus softmax, add plus RMSNorm (FlashNorm) en SwiGLU activation (DeepFusionKernel). Triton maakt deze kernels via Python toegankelijk. De exacte winst in launch count en utilization hangt af van model graph, compiler, GPU en serving framework; profileer daarom de deployed stack in plaats van uit te gaan van een universeel percentage.

11. FlashAttention: attention tilen zodat het in SRAM past

Standard attention materialiseert de volledige N×NN \times NN×N attention matrix in HBM, wat O(N2)O(N^2)O(N2) memory kost en veel memory traffic veroorzaakt. Het idee achter FlashAttention is om deze matrix helemaal niet te materialiseren. Q-, K- en V-matrices worden getiled in blocks die in SRAM passen; partial attention wordt per tile berekend en de resultaten worden samengevoegd met een online softmax (waarbij de running max en sum incrementeel over blocks worden bijgehouden). Memory daalt van O(N2)O(N^2)O(N2) naar O(N)O(N)O(N) en HBM-reads dalen met een orde van grootte.

Elke versie richt zich op de bottleneck van de betreffende GPU-generatie:

  • FlashAttention v1 (A100, 2022) bewees dat het tiling- plus online-softmax-idee werkt. Het paper rapporteerde een speedup van 2–4x ten opzichte van standard attention, maar slechts 25–40% GPU-utilization omdat kernel scheduling veel SMs idle liet.
  • FlashAttention v2 (A100, 2023) herwerkte de parallelism door over de sequence dimension te splitsen in plaats van over batch en heads. Het bereikte 50–73% utilization op A100, ongeveer 2x sneller dan v1.
  • FlashAttention v3 (H100 Hopper, 2024) voegde warp specialization toe (afzonderlijke warps voor data movement versus math) en GEMM-softmax-pipelining om memory loads en compute te overlappen. Het paper rapporteert tot 740 TFLOPS/s in FP16 (75% utilization) en bijna 1.2 PFLOPS/s in FP8 op H100. NeurIPS 2024 spotlight.
  • FlashAttention v4 (B200 Blackwell, 2026) adresseert een nieuwe bottleneck: op Blackwell schaalt de throughput van Tensor Cores zo snel dat non-matmul-operations (softmax exponentials, rescaling) de limiter worden. FA4 emuleert de exponential in software met polynomial approximations op FMA-units, gebruikt conditional rescaling om overhead te verlagen en slaat intermediates op in Blackwells dedicated tensor memory (TMEM) in plaats van registers. Het paper rapporteert ongeveer 1.6 PFLOPS op B200 in BF16, 1.3x sneller dan cuDNN 9.13 en 2.7x sneller dan Triton in zijn tests.

12. FlashDecoding: de decode-bottleneck paralleliseren

Standard FlashAttention houdt de GPU bezig door het werk over batch size en query length te verdelen. Tijdens decode genereert het model precies één token per keer (query length = 1). Als de batch size maal het aantal attention heads kleiner is dan het totale aantal SMs van de GPU (108 op een A100), blijft het grootste deel van de GPU idle terwijl enkele units sequentieel door de token history werken.

FlashDecoding lost dit op door een nieuwe parallelization dimension toe te voegen: de KV sequence length zelf. De KV cache wordt in kleinere chunks opgeknipt en over alle anders idle GPU-processors verdeeld om parallel te evalueren; daarna worden de partial computations samengevoegd met een log-sum-exp-reduction.

In Stanfords batch-one CodeLlama-34B-benchmark, met sequence lengths van 512 tot 64K tokens, bereikte FlashDecoding tot 8x end-to-end speedup tegenover de geteste baselines en bleef attention latency tot 64K vrijwel constant. Het resultaat is gebonden aan die hardware en benchmark en vormt geen algemene decode-garantie.

13. Continuous batching versus static batching

Static batching wacht tot elke sequence in een batch klaar is voordat de volgende batch start. Korte sequences verspillen daardoor GPU-cycles doordat ze idle blijven nadat ze end-of-sequence bereiken. Continuous batching (geïntroduceerd door het Orca-paper, OSDI 2022) werkt op iteration-level granularity: bij elke decode-step worden voltooide sequences verwijderd en nieuwe toegevoegd.

In Anyscales OPT-13B-benchmark bereikte geoptimaliseerde static batching 4x de naive baseline, continuous batching 8x en vLLM met continuous batching plus PagedAttention 23x (Anyscale, 2023). Continuous batching verhoogt ook de druk op KV allocation en wordt daarom vaak gecombineerd met paged memory management.

14. PagedAttention: virtual memory voor de KV cache

vLLM’s PagedAttention past het OS-idee van virtual memory toe op KV-cache-management. De KV cache wordt gesplitst in blocks met vaste grootte (typisch 16 tokens), blocks worden on demand gealloceerd naarmate tokens worden gegenereerd en logische (sequentiële) posities worden via block tables gemapt naar fysieke (verspreide) memorylocaties. Meerdere requests die een prefix delen (system prompts, beam search) kunnen naar dezelfde fysieke blocks verwijzen.

Eerdere systems verspilden 60–80% van de KV-cache-memory aan fragmentation en pre-allocation. PagedAttention verlaagt dit tot <4%, waardoor throughput 2–4x kan stijgen bij dezelfde latency en tot 24x ten opzichte van HuggingFace Transformers (vLLM Blog, 2023).

15. Speculative decoding: meerdere tokens per forward pass

Bij speculative decoding genereert een klein draft model KKK candidate tokens; vervolgens scoort het grote target model alle KKK posities in één forward pass. De decoder accepteert draft tokens van links naar rechts met probabilities die uit de target- en draft-distributions worden afgeleid. Na de eerste rejection samplet hij een correctie uit de residual target distribution en worden de resterende draft tokens weggegooid. Deze aangepaste rejection-sampling-stap behoudt de outputdistribution van het target model binnen de numerieke grenzen van de hardware; exact token matching alleen doet dat niet.

De winst is het meest aannemelijk bij kleine serving-batches en korte draft lengths, wanneer het scoren van de draft wordt gedomineerd door weight-, KV-cache- of communication-traffic in plaats van door de extra token compute. Het oorspronkelijke speculative-sampling-paper rapporteerde 2–2.5x decoding speedup voor zijn geteste 70B Chinchilla-setup; EAGLE-3 rapporteerde in zijn tests tot 6.5x. Varianten zijn Medusa (extra prediction heads, zonder apart model), prompt lookup decoding (n-gram matching tegen de input zonder afzonderlijke draft-model-forward-pass) en EAGLE (feature-level extrapolation).

Bij hoge batch sizes kan extra draft- en verification-work de winst tenietdoen. Speculative decoding is het meest veelbelovend wanneer de serving-batch klein genoeg is en draft acceptance hoog; benchmark de volledige serving loop in plaats van alleen de verification-kernel.

16. Prefix caching en KV-cache-hergebruik

In plaats van de KV cache weg te gooien wanneer een request klaar is, houdt prefix caching deze beschikbaar voor hergebruik bij nieuwe requests met dezelfde prefix tokens. Dat vermindert redundant prefill-werk voor system prompts, few-shot examples, RAG context en conversation history uit multi-turn gesprekken.

vLLM’s Automatic Prefix Caching hasht KV blocks en gebruikt een globale hash table voor lookup. SGLangs RadixAttention onderhoudt een radix tree van gecachte KV tensors met token-level granularity. Beide zijn afhankelijk van herhaalde, token-identieke prefixes. Rapporteer daarom naast latency of throughput ook de hit rate.

17. Streaming in de praktijk

Streaming stuurt tokens naar de client zodra ze zijn gegenereerd, in plaats van te wachten op de volledige response. Veel serving frameworks bieden dit via Server-Sent Events: de client opent een langdurige HTTP-connection en de server pusht elke token of token batch als een data: event. TTFT bepaalt wanneer de gebruiker voor het eerst output ziet; TPOT helpt bepalen hoe vloeiend dat aanvoelt. Stel de target vast via producttests en het gekozen interaction model.

Aan clientzijde vereist streaming keuzes rond buffering. Token voor token renderen kan visuele jitter veroorzaken, vooral bij markdown of code blocks die meerdere tokens context nodig hebben om correct te formatteren. Veelvoorkomende patterns zijn word-level buffering (tokens verzamelen tot een whitespace boundary), line-level buffering (wachten op een newline voordat je rendert) en adaptive buffering (proza direct renderen, code blocks bufferen). In de OpenAI Chat Completions API voegt stream_options: {"include_usage": true} een laatste usage-chunk toe vóór het data: [DONE]-message. OpenAI-compatible servers kunnen hiervan afwijken; verifieer daarom de geselecteerde implementatie.

Chunked prefill is één manier om te voorkomen dat lange prefills de token delivery voor concurrent users blokkeren. Decode-priority scheduling kan in-flight requests beschermen, terwijl disaggregated serving prefill en decode isoleert in afzonderlijke GPU-pools.

Multi-Head Attention laat elke token informatie wegen van de tokens die zichtbaar zijn onder de attention mask. 19. Decoder-only models voor general-purpose generation

De oorspronkelijke Transformer (2017) had zowel een encoder als een decoder. Sindsdien splitste het veld zich op in drie architectural families, waarvan er één de default voor generative AI werd.

Encoder-only models (BERT, RoBERTa) gebruiken bidirectional attention: elke token attendt in beide richtingen op elke andere token. Dat levert rijke representations voor understanding-tasks (classification, NER, semantic similarity), maar ze kunnen text niet autoregressively genereren. Encoder-only models zijn nog steeds gebruikelijk als backbone voor embedding models, rerankers en lightweight classifiers (bijvoorbeeld de BERT-based routers in RouteLLM).

Encoder-decoder models (T5, BART, de oorspronkelijke Transformer) scheiden understanding van generation. De encoder verwerkt de volledige input met bidirectional attention, waarna de decoder output autoregressively genereert terwijl hij via cross-attention op de representations van de encoder let. Dit bood een natuurlijk voordeel voor sequence-to-sequence-tasks zoals translation, waarbij input en output verschillende sequences zijn. Googles T5 liet zien dat elke NLP-task als text-to-text kan worden geformuleerd; encoder-decoder models worden nog steeds gebruikt voor gespecialiseerde systems (Whisper voor speech recognition, FLAN-T5 voor instruction following).

Decoder-only models (GPT, Llama, Mistral, Gemini) gebruiken causal (unidirectional) attention: elke token attendt alleen op eerdere tokens. Ze zijn gebruikelijk voor general-purpose text generation omdat één causal language-model objective schaalt over unpaired text, terwijl inference instructions, few-shot demonstrations en de query behandelt als tokens in één prefix. De herhaalde decoder block vermijdt bovendien een afzonderlijke encoder stack en cross-attention path. Encoder-decoder models blijven nuttig wanneer een task baat heeft bij afzonderlijke encoding van de input en generation tegen die representation, waaronder translation en speech recognition.

20. Mixture of experts

MoE vervangt de dense FFN in elke transformerlaag door meerdere kleinere expert FFNs plus een lightweight gating router. De router berekent voor elke expert een score (typisch een softmax over learned linear projections) en selecteert de top-kkk experts per token. Alleen de geactiveerde experts rekenen, zodat een model enorme totale capacity kan hebben terwijl de cost per token laag blijft. Dit is sparse conditional computation: total parameters bepalen wat het model kan representeren, active parameters bepalen wat het kost om het uit te voeren.

21. Tokenization: BPE, SentencePiece en tiktoken

LLMs zien geen text. Ze zien sequences van integer token IDs. Een tokenizer splitst raw text in tokens (subword pieces) en mapt elk token naar een ID. De keuze van tokenizer beïnvloedt model quality, inference speed en multilingual fairness.

Byte Pair Encoding (BPE) is het gangbare algorithm. Het voegt iteratief de meest frequente aangrenzende paren in de training corpus samen. Een vereenvoudigd voorbeeld:

  1. Start met een character-level vocabulary: [l, o, w, e, r, _]
  2. Het meest frequente paar is (l, o) → merge tot lo → vocabulary: [l, o, w, e, r, _, lo]
  3. Het volgende meest frequente paar is (lo, w) → merge tot low → vocabulary voegt low toe
  4. Ga door tot de vocabulary de target size bereikt (bijvoorbeeld 128K tokens)

Veelvoorkomende woorden zoals “the” worden single tokens, terwijl zeldzame woorden zoals “defenestration” worden opgesplitst in subword pieces zoals ["def", "en", "est", "ration"]. De trade-off is vocabulary size versus sequence length.

Drie tokenizer-implementations dekken het grootste deel van production use:

  • SentencePiece traint direct op raw Unicode text zonder language-specific pre-tokenizer. Het bewaart whitespace met het ▁ meta-symbol en kan optioneel terugvallen op UTF-8 byte tokens. Het ondersteunt zowel BPE- als unigram-models en wordt gebruikt door Llama 1/2, T5 en Mistral.
  • tiktoken is OpenAI’s Rust-based tokenizer met byte-level BPE. In de gepubliceerde GPT-2-benchmark draaide deze 3–6x sneller dan de geteste GPT2TokenizerFast-configuratie. Llama 3 stapte over van SentencePiece naar tiktokens algorithm.
  • Hugging Face Tokenizers is een veelgebruikte Rust-based library die BPE, WordPiece en Unigram ondersteunt.

Fertility meet hoeveel tokens een tokenizer produceert per woord of andere gekozen text unit. Dit varieert met de exacte tokenizer, language, script, normalization, domain en sample. Meet dit op representative traffic in plaats van te extrapoleren vanuit één tokenizer of language.

Training is waar capabilities worden opgebouwd. Dit deel behandelt pretraining, efficiënte fine-tuning (LoRA, mixed precision), scaling laws en alignment methods.

23. Pretraining, fine-tuning en alignment

Pretraining is self-supervised next-token prediction op een grote corpus. De compute kan vele ordes van grootte omvatten; Llama 3 405B gebruikte bijvoorbeeld 3.8×10253.8 \times 10^{25}3.8×1025 FLOPs. Supervised fine-tuning (SFT) past het pretrained model aan op task-specific labeled data. RLHF / RLAIF gebruikt preference data om gedrag te sturen: een conventionele RLHF-pipeline verzamelt comparisons, traint een reward model en optimaliseert vervolgens de policy. RLAIF vervangt sommige human judgments door AI-generated feedback.

Compute hangt af van model size, sequence length, data volume, optimizer en method. PPO houdt ook meer model state bij dan SFT, omdat een typische setup policy-, reference-, reward- en critic-models bevat. Ik behandelde het volledige fine-tuning decision framework in LLM Fine-Tuning Guide.

24. LoRA en QLoRA: parameter-efficient fine-tuning

LoRA bevriest de pretrained weights en injecteert trainable low-rank matrices AAA (r×kr \times kr×k) en BBB (d×rd \times rd×r), zodat de updated weight W0+BAW_0 + BAW0​+BA wordt. Het LoRA-paper reduceerde GPT-3 175B in zijn setup tot ongeveer 18 miljoen trainable parameters. Rank is een tuning parameter, geen regel voor task complexity; selecteer rank met een quality- en memory-sweep. LoRA adapters kunnen na training in de base weights worden gemerged om inference zonder afzonderlijke adapter path mogelijk te maken.

QLoRA laadt het base model in 4-bit NF4-quantization en traint LoRA adapters in BF16. NormalFloat4 plaatst meer quantization levels rond nul, waar de weight density het grootst is. Het paper fine-tunede een 65B-model op één 48 GB GPU en rapporteerde resultaten dicht bij zijn 16-bit baselines. De runtime- en memory-trade-offs zijn specifiek voor de geteste stack.

26. Gradient checkpointing

Elke layer van de forward pass produceert een intermediate output die een activation wordt genoemd:

Input→[Layer 1]→activation1→[Layer 2]→activation2→[Layer 3]→output\text{Input} \rightarrow [\text{Layer 1}] \rightarrow \text{activation}_1 \rightarrow [\text{Layer 2}] \rightarrow \text{activation}_2 \rightarrow [\text{Layer 3}] \rightarrow \text{output}Input→[Layer 1]→activation1​→[Layer 2]→activation2​→[Layer 3]→output

Normaal moeten alle activations in memory blijven, omdat backpropagation ze nodig heeft om gradients te berekenen. Bij een deep transformer kunnen opgeslagen activations meer memory innemen dan de model weights zelf.

Gradient checkpointing ruilt compute in voor memory door de meeste activations weg te gooien en ze tijdens backprop on the fly opnieuw te berekenen. De standaardstrategie (Chen et al., 2016) verdeelt een network van nnn layers in n\sqrt{n}n​ gelijkmatig verdeelde segments en bewaart alleen de boundary activation van elk segment. Deze opgeslagen boundaries zijn de “checkpoints”. Alle intermediate activations binnen een segment worden onmiddellijk verwijderd.

Wanneer de backward pass een layer binnen een segment bereikt, worden de activations vanaf het dichtstbijzijnde checkpoint opnieuw berekend. Bij de gelijkmatig gesegmenteerde strategie daalt de opgeslagen activation memory van O(n)O(n)O(n) naar O(n)O(\sqrt{n})O(n​). De werkelijke memory savings en recomputation overhead hangen af van model, checkpoint boundaries, sequence length, framework en implementation; meet beide daarom op de target training run. Schakel dit in HuggingFace in met gradient_checkpointing=True.

27. DeepSpeed ZeRO stages

Bij standard data parallelism bevat elke GPU een complete kopie van model weights, gradients en optimizer states. Voor Adam kost elke parameter 2 bytes voor de FP16 weight + 4 bytes voor de FP32 master weight + 4 bytes voor momentum + 4 bytes voor variance + 2 bytes voor de gradient: 16 bytes per parameter. Een model met 7.5B parameters vereist ~120 GB per GPU, waarbij elke GPU hetzelfde opslaat. Op 64 GPUs zijn dat 64 identieke kopieën van 120 GB. Veel verspilde memory.

DeepSpeed ZeRO (Zero Redundancy Optimizer) verwijdert deze duplicatie door deze componenten over GPUs te sharden in plaats van ze te repliceren:

  • Stage 1 — partitioneer optimizer states. Elke GPU bewaart slechts 1/N van de optimizer states (de FP32 master weights plus Adams first en second moments, 12 bytes/param). Wanneer een GPU een weight moet updaten, update hij alleen zijn slice en broadcast hij het resultaat. Onder de onderstaande aannames daalt memory van ~120 GB naar ~41.3 GB per GPU.
  • Stage 2 — partitioneer ook gradients. Gradients worden niet langer naar elke GPU all-reduced (2 bytes/param). Elke GPU ontvangt via reduce-scatter alleen de gradient slice die hij nodig heeft. Onder dezelfde aannames daalt memory naar ~28.1 GB per GPU.
  • Stage 3 — partitioneer ook de model weights. Elke GPU bevat slechts 1/N van de FP16 weights. Vóór elke forward- of backward-pass van een layer roept de GPU all-gather aan om tijdelijk de volledige layer weights uit alle andere GPUs te reconstrueren; vervolgens rekent hij en verwijdert hij de verzamelde weights. Onder dezelfde aannames daalt memory naar ~15.0 GB per GPU.

Daardoor kan training van models met triljoenen parameters op beperkte GPU-clusters mogelijk worden. Storage offload voegt PCIe- en storage-transfer-cost toe; het gemeten effect hangt af van drive, PCIe-topology, partitioning, prefetch, transfer overlap en workload. Gebruik dit om aan capacity requirements te voldoen, niet op basis van een vaste veronderstelde slowdown; profileer de target-configuratie.

28. FSDP: PyTorch-native sharding

Fully Sharded Data Parallel (FSDP) is PyTorchs ingebouwde antwoord op DeepSpeed ZeRO-3. Het shardt parameters, gradients en optimizer states over GPUs volgens hetzelfde basisidee. De mechanics per layer vormen een eenvoudige loop:

  1. All-gather de volledige parameters van alle GPUs (reconstrueer tijdelijk de complete layer).
  2. Compute de forward- of backward-pass voor die layer.
  3. Free de verzamelde parameters onmiddellijk. Elke GPU houdt alleen zijn eigen shard.
  4. Reduce-scatter gradients zodat elke GPU alleen zijn toegewezen gradient slice ontvangt.

30. RLHF, DPO, GRPO en het alignment-landschap

Alignment stuurt een pretrained model naar gewenste instructions, preferences en safety policies. Het garandeert op zichzelf geen truthfulness of safe behavior. De onderstaande methods ruilen implementation complexity, data requirements, exploration en training stability tegen elkaar af.

De klassieke RLHF-pipeline: SFT → human preference pairs verzamelen → een reward model op die pairs trainen → de policy fine-tunen met PPO (Proximal Policy Optimization). PPO houdt 4 model copies tegelijk in memory (policy, reference, critic/value model, reward model) en is gevoelig voor hyperparameters. Het is ook vatbaar voor reward hacking, waarbij het model eigenaardigheden van het reward model uitbuit — bijvoorbeeld verbose, zelfverzekerd klinkende antwoorden — in plaats van quality werkelijk te verbeteren.

DPO (Direct Preference Optimization) slaat het learned reward model en de online RL-loop over door direct een loss op preference pairs te optimaliseren. Dat vereenvoudigt de training pipeline. Standard DPO is offline: het traint op een fixed dataset en exploret geen nieuwe responses tijdens de update loop. Of die beperking relevant is, hangt af van task en data coverage.

GRPO (Group Relative Policy Optimization, DeepSeek) verwijdert PPOs learned critic door meerdere completions per prompt te genereren en group-relative rewards als baseline te gebruiken. Dit verlaagt de model-state burden ten opzichte van een typische PPO-setup. In tegenstelling tot DPO is GRPO on-policy: het model genereert tijdens training fresh responses. DeepSeek-R1 combineert GRPO met RLVR (reinforcement learning from verifiable rewards), met checks zoals math answers, code compilation en unit tests. Deze rewards zijn makkelijker te auditen dan een learned preference score, maar incomplete tests en proxy objectives kunnen nog steeds worden geëxploiteerd.

31. Distillation: knowledge tussen models comprimeren

Knowledge distillation draagt capabilities over van een grote teacher naar een kleinere student. Logit-based distillation traint de student om de outputdistribution van de teacher te matchen. Data-based distillation laat de teacher examples genereren waarop de student fine-tunet. Data-based methods zijn gangbaar voor LLMs omdat ze over architectures heen kunnen werken en met API-only teachers, maar hun waarde wordt begrensd door teacher quality, data coverage, filtering en generation cost.

DeepSeek-R1 stelde een mixture van ongeveer 800.000 examples samen — circa 600.000 reasoning-related samples en 200.000 non-reasoning samples — en gebruikte deze om Qwen2.5- en Llama 3-models van 1.5B tot 70B parameters te distillen. In de evaluation van het paper:

  • DeepSeek-R1-Distill-Qwen-32B scoort 72.6% op AIME 2024 en 94.3% op MATH-500, hoger dan de in het paper gerapporteerde cijfers voor OpenAI o1-mini.
  • DeepSeek-R1-Distill-Qwen-7B scoort 55.5% op AIME 2024, hoger dan het resultaat van QwQ-32B-Preview uit het paper, ondanks het kleinere model.

In de small-model-experiments van DeepSeek-R1 presteerde distillation beter dan direct GRPO op de geteste base models. Dat ondersteunt distillation voor deze setup; het bewijst geen universele ranking tussen distillation en RL.

LLM-generated training data wordt gebruikt in verschillende terugkerende patterns:

  • Self-Instruct bootstrap vanuit een kleine seed set van door mensen geschreven instructions: de LLM genereert nieuwe instructions, inputs en outputs, die worden gefilterd en aan de pool worden toegevoegd. Het Alpaca-project gebruikte 52.000 examples die uit 175 seeds werden gegenereerd. Stanford rapporteerde data generation onder 500andfine−tuningunder500 and fine-tuning under 500andfine−tuningunder100, waarmee de initiële reproduction cost onder $600 lag; de GPT-3.5 comparison was een beperkte projectevaluation en geen brede equivalentie.
  • Evol-Instruct (WizardLM) neemt bestaande instructions en evolueert deze iteratief langs complexity axes (constraints toevoegen, reasoning verdiepen, problems concreter maken) om steeds moeilijkere training examples te produceren.
  • Microsofts Phi-4 (14B) gebruikte synthetic data voor een groot deel van de pretraining, waaronder generation, critique, self-revision en instruction reversal. Het technical report vergelijkt de resulterende STEM- en coding-performance met grotere models op de geselecteerde benchmarks.

Het relevante risico is model collapse: wanneer models recursief worden getraind op synthetic data uit vorige generaties, verdwijnen de tails van de oorspronkelijke distribution geleidelijk. Het model overschat common patterns en verliest zeldzame maar belangrijke variaties (Shumailov et al., 2024). Een afzonderlijke Ahrefs classifier study samplede in april 2025 één nieuw gedetecteerde Engelstalige pagina per domein uit 900.000 pagina’s en classificeerde 74.2% als tekst met enige AI-generation. Die vendor study is geen census van het web. Mitigation begint met het combineren van synthetic en real data, filtering en lineage tracking, zodat recursive generation meetbaar wordt.

Deel VI — Scaling and deployment

Opschalen van één GPU naar een cluster betekent werk over devices verdelen. Dit deel behandelt parallelism-strategieën, serving frameworks, GPU-selectie en routing.

33. Vier vormen van parallelism

Tensor Parallelism (TP) splitst afzonderlijke weight matrices over GPUs en communiceert doorgaans na elke layer. Snelle intra-node links zoals NVLink maken dit vooral binnen één node praktisch. Meer shards verlagen memory en compute per device, maar verhogen communication; kies de degree met een latency benchmark.

Pipeline Parallelism (PP) splitst layers sequentieel over GPUs en geeft activations tussen stages door. Het communication pattern kan over nodes werken, maar pipeline bubbles en ongelijke stage times verlagen utilization. Grote deployments combineren vaak TP binnen een node met PP over nodes.

Data Parallelism (DP) repliceert het serving model zodat elke replica onafhankelijke requests afhandelt zonder per-request cross-replica communication. Dit is efficiënt wanneer het model past en traffic kan worden gebalanceerd. In training wordt DP vaak gecombineerd met ZeRO of FSDP om state te sharden.

Expert Parallelism (EP) distribueert MoE experts over GPUs met all-to-all communication voor token routing. De performance hangt af van token balance, expert placement en interconnect-topology; all-to-all-traffic kan de dominante bottleneck worden.

Een startheuristiek voor parallelism:

  • Model past op één GPU: begin met onafhankelijke replicas en meet DP-scaling.
  • Model past binnen één node: test TP binnen de node en replicate daarna de groep als traffic dat vereist.
  • Model overspant nodes: test een combinatie van TP en PP tegen de interconnect en latency target.
  • Mixture of experts: voeg EP alleen toe wanneer expert placement dit vereist.

34. Serving frameworks vergeleken

vLLM biedt paged KV allocation, continuous batching, een OpenAI-compatible API en verschillende parallelism-modes. Model- en hardware-support veranderen frequent; verifieer het target model daarom tegen de actuele compatibility matrix.

SGLang combineert RadixAttention voor prefix reuse, een custom scheduler en structured generation. De gepubliceerde throughput gains hangen af van workload en configuratie; vergelijk SGLang met vLLM en TensorRT-LLM met identieke prompts, outputs, hardware en SLOs.

TensorRT-LLM richt zich met CUDA graph fusion en kernel optimization op lage latency voor single requests, met native FP8/FP4-support. De gepubliceerde cijfers zijn hardware- en model-specifiek. De trade-off is een steilere learning curve en een NVIDIA-specific deployment surface.

TGI integreert met het Hugging Face-ecosystem en ondersteunt verschillende hardware backends. Controleer de actuele maintenance- en feature-status van de repository voordat je het voor een nieuwe deployment kiest.

Ollama legt de nadruk op een eenvoudige lokale model workflow. Gebruik het voor development convenience; benchmark een andere serving stack wanneer hoge concurrency of expliciete SLO-control belangrijk is.

llama.cpp is een portable C/C++ runtime met ARM-, x86-, Metal-, CUDA-, ROCm- en Vulkan-paden. GGUF ondersteunt verschillende quantization levels. Performance varieert sterk met model, quantization, context en backend; gebruik daarom de local benchmark tool voor de target machine.

36. Model cascading en routing

Model routing kiest per query welke LLM deze afhandelt, op basis van voorspelde complexity of capability. RouteLLM (LMSYS/UC Berkeley, ICLR 2025) rapporteert een 85% cost reduction op zijn MT-Bench-setup met behoud van 95% van zijn GPT-4-quality-baseline. Of routing loont, hangt af van actuele prices, de traffic mix, router errors en de quality floor.

Routers variëren van lightweight classifiers tot LLM-based judges. Cascading is de sequentiële variant: een query start bij een goedkoper model en escaleert wanneer een scoring function het antwoord afwijst. FrugalGPT rapporteert tot 98% lagere cost of tot 4% hogere accuracy in zijn geëvalueerde model pool. Een production cascade vereist calibrated escalation criteria en monitoring voor queries die het goedkope model onterecht accepteert.

Deel VII — Applications

Application-level patterns die raw model capabilities omzetten in bruikbare systems. Embeddings voeden retrieval, RAG groundt responses in external knowledge, agents orchestreren multi-step workflows en prompt engineering brengt dit samen.

37. Embedding models versus generative models

Embedding models encoden text in fixed-dimensional vectors die semantic meaning vastleggen. In tegenstelling tot generative models die token sequences produceren, geven ze voor de input één dense vector terug, vaak met enkele honderden tot enkele duizenden dimensions. Hun backbones bestaan uit bidirectional encoder-only transformers en decoder-derived models die voor representation learning zijn aangepast. Een pooling layer reduceert per-token representations vaak tot één vector via mean pooling, een special classification token of een model-specific last-token method. Contrastive fine-tuning duwt semantically similar texts naar elkaar toe en dissimilar texts uit elkaar.

Huidige embedding systems dekken verschillende deployment needs. Qwen3-Embedding-8B ondersteunt configureerbare output dimensions en veel languages. Gemini Embedding 2 accepteert text, images, video, audio en documents. pplx-embed-v1-4B onderzoekt lower-precision dense embeddings. OpenAI text-embedding-3-large ondersteunt verkorte embeddings via zijn dimensions parameter. Dit zijn examples, geen ranking: evalueer language, modality, task, dimension en serving cost op één retrieval set.

Matryoshka Representation Learning (MRL, Kusupati et al., NeurIPS 2022) maakt embedding dimensions flexibel. MRL, genoemd naar Russische matroesjka-poppen, structureert een embedding zo dat de eerste mmm dimensions even informatief zijn als een onafhankelijk getraind mmm-dimensional model. Tijdens training aggregeert MRL losses over een gekozen O(log⁡d)O(\log d)O(logd)-set van prefix dimensions, meestal consistente halveringen; het 2048-dimensional example van het paper gebruikt {8,16,…,1024,2048}\{8, 16, \ldots, 1024, 2048\}{8,16,…,1024,2048}. De aggregated loss zorgt ervoor dat de voorste dimensions coarse semantic information dragen, terwijl latere dimensions fijnere details toevoegen.

Na training kan een MRL-embedding worden afgekapt tot een ondersteunde prefix dimension. OpenAI rapporteert dat text-embedding-3-large met 256 dimensions beter presteert dan text-embedding-ada-002 met 1.536 dimensions op de aangehaalde MTEB-comparison. Dat levert een 6x-reductie in raw vector storage op; search latency en database cost hangen ook af van index, metadata, filtering en hardware.

Het embedding model is één belangrijke component in een RAG pipeline, naast parsing, chunking, search, reranking en generation. Als relevante evidence niet wordt retrieved, kan een sterkere generator deze niet betrouwbaar reconstrueren.

38. RAG architecture in production

Retrieval-Augmented Generation voorziet een LLM tijdens query time van retrieved documents. Het kan actuele of private evidence bieden die niet in de model weights aanwezig is, maar retrieval garandeert niet dat het antwoord deze evidence correct gebruikt. Een production RAG system is een multi-stage pipeline waarvan de stages afzonderlijk moeten worden geëvalueerd.

De ingestion pipeline draait offline. Raw documents (PDFs, HTML, Markdown, databases) worden eerst geparsed naar clean text. Dat is lastiger dan het klinkt: alleen PDF parsing kan al tables, headers en formatting verliezen. De text wordt vervolgens opgesplitst in chunks, die afzonderlijk worden geëmbed en geïndexeerd.

Chunking beïnvloedt zowel retrieval recall als de context die voor de generator beschikbaar is. Geschikte sizes hangen af van document structure, query granularity, embedder limits en reranker limits. Veelgebruikte approaches zijn fixed-size with overlap, recursive splitting langs document boundaries en semantic chunking op basis van embedding similarity. Vergelijk ze met page- of section-level relevance labels in plaats van universeel één token range te kiezen.

Elke chunk wordt vervolgens geëmbed met een model zoals die in Section 37 en opgeslagen in een vector database (Pinecone, Weaviate, Qdrant, pgvector enzovoort).

De retrieval pipeline draait tijdens query time. Begin met een meetbare baseline en voeg stages alleen toe wanneer error analysis laat zien dat ze een echte miss adresseren:

  • Hybrid search combineert dense vector retrieval met sparse retrieval zoals BM25, vaak samengevoegd via Reciprocal Rank Fusion (RRF). Dense search verwerkt semantic paraphrases; sparse search vangt exacte identifiers, error codes en acronyms. Vendor benchmarks rapporteren gains ten opzichte van vector-only baselines, maar de omvang hangt af van corpus en relevance labels.
  • Reranking stuurt retrieved candidates door een model dat query en document gezamenlijk scoort. Dit kan fine-grained relevance verbeteren ten koste van een extra model call. Candidate count, retained count en latency moeten samen worden getuned. Ik behandelde de volledige multi-stage pipeline in Building a Modern Search Ranking Stack.
  • Query transformation herschrijft de query van de gebruiker vóór retrieval om recall te verbeteren. HyDE (Hypothetical Document Embeddings) laat de LLM een hypothetical answer genereren, die vervolgens wordt geëmbed en voor retrieval wordt gebruikt. Multi-query expansion genereert meerdere formuleringen van dezelfde question. Step-back prompting stelt eerst een algemenere vraag om bredere context op te halen.

De gangbare failure modes:

  • Retrieval failure — het correcte document bestaat, maar wordt niet retrieved. Test chunking, query transformation, hybrid search en metadata filtering tegen de miss.
  • Context poisoning — irrelevante retrieved chunks misleiden de LLM. Test reranking, context filters en kleinere retained sets.
  • Lost-in-the-middle — in de geteste settings voor multi-document question answering en key-value retrieval vonden Liu et al. dat answer performance doorgaans het hoogst was wanneer relevante informatie aan het begin of einde van de input stond en lager wanneer deze in het midden stond.

GraphRAG (Microsoft, 2024) breidt vector retrieval uit met een extracted entity- en relationship graph. Het richt zich op corpus-level en relationship-heavy questions die flat chunk retrieval kan missen. De trade-off is extra extraction-, indexing-, storage- en evaluation-work.

Practitioner guides publiceren latency ranges voor embedding, search, reranking en generation, maar die cijfers variëren per region, corpus, hardware en model. Meet elke stage in traces en evalueer de quality change voordat je de extra latency accepteert.

39. Agent architectures en tool calling

LLM agents gebruiken models om tool calls te selecteren en te sequencen rond een evoluerende state. Drie nuttige orchestration patterns zijn:

  • ReAct — interleavet action selection met observations. Het kan na elk tool result aanpassen, maar een groeiende history verhoogt token- en latency-cost.
  • ReWOO — plant tool calls met placeholders, voert onafhankelijk werk parallel uit en synthetiseert daarna. Het paper rapporteert token savings ten opzichte van ReAct, maar het fixed plan heeft een expliciet recovery path nodig wanneer een tool faalt.
  • Planner-executor — scheidt planning van execution en kan na failure een re-planning policy toevoegen. Dit maakt model specialization mogelijk, maar voegt orchestration state en een extra decision boundary toe.

Meet deze curves met de werkelijke tool descriptions en failure distribution. Frameworks zoals LangGraph kunnen state en recovery paths expliciet maken, maar nemen de evaluation burden niet weg.

40. Prompt engineering voor production

Prompting in production is een evaluation problem: verander één onderdeel van prompt of context en meet vervolgens task quality en failure modes. De onderstaande techniques zijn gebruikelijke startpunten, geen universele volgorde.

Few-shot examples zijn vaak effectief om output format te sturen. Begin met 3–5 examples die empty inputs, ambiguous queries en multi-part answers afdekken en meet het resultaat op een held-out set. Examples moeten de echte input distribution bestrijken en niet alleen de happy path. Meer examples verbruiken context en garanderen geen verdere gains.

Chain-of-thought (CoT) prompting vraagt een model om intermediate reasoning vóór het antwoord te tonen. Kojima et al. rapporteerden gains van het suffix “Let’s think step by step” op hun geteste reasoning tasks, maar het effect varieert per model en nieuwere reasoning APIs exposen mogelijk geen hidden traces. Kies voor production bij voorkeur voor een inspectable task decomposition of een concise rationale wanneer die voor de evaluator nuttig is. Self-consistency (Wang et al., 2023) samplet meerdere reasoning paths en aggregeert de answers, waarbij extra inference cost wordt ingeruild voor robustness op geschikte tasks.

Structured output met expliciete JSON schemas (Section 39) verwijdert veel parsing failures. Constrained decoding engines zoals xgrammar kunnen de ondersteunde grammar tijdens generation afdwingen; factual accuracy en semantic validity vereisen nog steeds evaluation en unsupported schema features moeten mogelijk afzonderlijk worden afgehandeld.

Prompt chaining splitst een task op in gerichte stages, bijvoorbeeld classify intent → retrieve context → generate response → validate output. Dit kan failures lokaliseren, verschillende models per stage mogelijk maken en cacheable intermediate state blootleggen. Het voegt ook interfaces en latency toe; vergelijk het daarom met een single-call baseline.

Temperature verandert de sampling distribution. Lage waarden zijn een redelijk startpunt voor classification of extraction; hogere waarden kunnen diversity voor ideation verhogen. Exact gedrag verschilt per model API en werkt samen met top_p, top_k en provider defaults. Sweep de ondersteunde settings voor de task in plaats van één range te kopiëren.

System- versus user-message separation houdt persistent policy gescheiden van per-request content. Chat templates en instruction tuning geven deze rollen een verschillende priority, maar maken van een system message geen enforcement boundary. Plaats stabiel gedrag in de system message, houd untrusted data in user- of tool-content en enforce hard constraints zoals PII removal ook buiten het model.

Context engineering breidt prompt work uit naar het samenstellen van retrieved documents, tool results, conversation history en examples. Liu et al. vonden een lost-in-the-middle-effect in de long-context models die zij testten; position moet daarom onderdeel zijn van de evaluation en niet als irrelevant worden aangenomen. Ik behandelde de bredere workflow in Context Engineering for AI Agents.

41. Rate limiting voor requests met variabele cost

Traditionele rate limiting op requests per second gaat uit van ongeveer gelijke cost per request. LLMs doorbreken die aanname. Een classificatieprompt van 10 tokens en documentanalyse van 100K tokens gebruiken hetzelfde API-endpoint, maar verschillen vier ordes van grootte in cost. Rate limiting op RPS laat dure requests ongecontroleerd door of verstikt goedkope requests onnodig.

Production systems hebben token-based rate limiting nodig over meerdere dimensions. OpenAI documenteert request- en tokenlimits per usage tier. Anthropic splitst limits voor input tokens en output tokens. Exacte quotas en algorithms kunnen veranderen; behandel provider documentation als source of truth. Het architectural point is dat je requests en tokens onafhankelijk moet budgetteren.

Het praktische implementation pattern is een multi-dimensional limit hierarchy (user → application → organization → global), met priority tiers voor premium access. Op requestniveau is token budget reservation de relevante technique: schat total tokens (input + max_tokens) bij admission, trek ze af van de bucket en pas dit bij completion aan op basis van actual usage. Zo voorkomt je dat een burst van requests met lange generation capacity uitput voordat ze output beginnen te produceren.

Voor self-hosted deployments is het equivalent provisioned throughput: dedicated GPU capacity reserveren voor target token rates. Voor vLLM-deployments betekent dit admission control configureren rond active decode slots en KV-cache-pressure, niet alleen rond request count. Zoals Section 5 uitlegt, hebben throughput en admission beide token-aware limits nodig.

42. Failure modes om tegen te ontwerpen

LLM serving voegt failure modes toe die samenhangen met variabele sequence length, KV memory en long-running decode work. Ontwerp en load-test de defenses voordat production traffic ervan afhankelijk is.

Out-of-Memory (OOM) is een veelvoorkomende failure. Een 70B FP16-model heeft ongeveer 140 GB nodig voor weights alleen, en de KV cache voor één Llama 3.1 70B-sequence met 128K context kan onder de aannames in Section 6 ongeveer 40 GB toevoegen. Het verschil tussen “past in memory” en “OOM under load” is kleiner dan het lijkt, omdat een batch van requests met long context meer KV memory kan gebruiken dan verwacht. Prevention combineert een gemeten memory reserve met quantization en paged KV allocation. Voor workloads met hoge KV pressure kan LMCache KV data offloaden naar CPU memory of disk; gebruik de gepubliceerde results als startpunt en benchmark de lokale memory hierarchy.

Preemption treedt op wanneer KV-cache-pressure de scheduler dwingt work te evicten of te recomputen. De exacte strategy hangt af van serving version en configuration. Vanuit gebruikersperspectief is het symptoom hogere end-to-end latency zonder duidelijke application error. Monitor preemption counts en correleer deze met KV use, queue depth en request lengths.

Tail latency kan pieken wanneer grote prefills decode work vertragen. Chunked prefill (Section 7) en length-aware scheduling richten zich op deze interference. Het Learning-to-Rank-scheduler-paper en CascadeInfer rapporteren improvements ten opzichte van hun baselines onder hun geëvalueerde workloads, maar het exacte resultaat hangt af van request-length distribution en scheduler configuration.

Cascading failures kunnen beginnen wanneer trage requests de queue laten groeien, upstream clients time-outs krijgen en retries extra load toevoegen. Defenses zijn onder meer admission control, per-tenant concurrency limits, output caps, retry budgets en gateway circuit breakers. Disaggregated prefill- en decode-pools kunnen helpen wanneer load tests persistent phase interference aantonen.

43. LLM systems monitoren

LLM monitoring verschilt op enkele fundamentele punten van traditionele API monitoring. Elk request heeft variabele cost, twee afzonderlijke phases met verschillende bottlenecks en een memory footprint die afhangt van zowel input length als generation length. Standard metrics zoals request latency en error rate missen het grootste deel van wat belangrijk is.

Goodput is het aantal requests per second dat aan alle gedefinieerde SLO-thresholds voldoet, zoals TTFT, TPOT en total latency. Dit is een nuttige gecombineerde metric omdat raw throughput er gezond uit kan zien terwijl latency-SLOs falen: een system dat 100 requests per second verwerkt maar bij 40% de thresholds mist, heeft een goodput van 60 requests per second. Optimaliseren voor goodput houdt de performance distribution zichtbaar in plaats van alleen het gemiddelde te rapporteren.

vLLM exposeert een Prometheus-endpoint op /metrics met running en waiting requests, KV-cache-use, generation-length distributions en prefix-cache-statistics. Metric names kunnen tussen releases veranderen; bind dashboards aan de deployed version. Een typische stack gebruikt Prometheus voor metrics, Grafana voor visualization en OpenTelemetry-compatible traces over application- en serving-components heen.

Nuttige alert patterns zijn onder meer. Leid thresholds af uit load tests in plaats van deze examples ongewijzigd te kopiëren:

  • Preemption count spikes — de runtime swapt of recomputet work, wat latency toevoegt zonder application error.
  • KV-cache-utilization nadert de geteste preemption region — voeg capacity toe of shed load voordat evictions cascaderen.
  • Queue depth blijft persistent boven de geteste batch envelope — admission control moet requests gaan rejecten of deprioriteren.
  • TTFT stijgt terwijl TPOT vlak blijft — deze divergence wijst eerst op queueing, admission, network of prefill pressure en niet op decode throughput. Gebruik traces en queue metrics om ze te onderscheiden.

44. Cost optimization: een compounding strategy

Provider prices en input-to-output price ratios veranderen. Haal actuele rates op vóór een purchasing decision; model tier en output length kunnen de rekening domineren nog voordat infrastructure optimizations worden toegepast.

Verschillende approaches kunnen worden gestapeld, maar pas nadat je hebt gemeten welke op de workload van toepassing zijn:

  1. Quantization van FP16 naar INT4 verlaagt de weight memory met 75%. Of dit de bill verlaagt, hangt af van kernel speed, batch size en hardware utilization (Section 9).
  2. Model routing stuurt eligible traffic naar goedkopere models. Meet de false-accept-rate van de router en de end-to-end quality voordat je het aandeel dat door het goedkopere model wordt afgehandeld verhoogt (Section 36).
  3. Prompt caching vermindert repeated-prefix-work. Provider discounts en rate-limit treatment veranderen in de tijd; combineer daarom de measured hit rate met de actuele terms (Section 16).
  4. Batch APIs kunnen non-real-time work zoals evaluations, synthetic-data generation en bulk classification goedkoper maken. Controleer actuele prijzen en completion windows.
  5. Self-hosting kan winnen bij sustained utilization, maar er is geen universeel break-evenpunt in token volume. Neem naast GPU rental ook engineering, orchestration, observability, capacity slack en on-call costs mee.

Het vermenigvuldigen van de illustrative factors levert theoretisch een grote reductie op, maar de inputs zijn niet onafhankelijk: quantization verandert throughput, routing verandert de quality mix en caching en batching zijn alleen op eligible traffic van toepassing. Bouw de estimate op uit measured traffic shares en valideer deze tegen de invoice.

45. Capacity planning en autoscaling

Capacity planning voor LLM serving moet rekening houden met variabele request cost, long-running decode work en sequence-dependent memory. Afhankelijk van de workload kunnen KV memory, memory bandwidth, compute of de interconnect de limiterende resource zijn.

De theoretische memory ceiling voor concurrent requests volgt uit het KV-cache-budget:

max concurrent sequences=GPU memory−model weights−overheadper-sequence KV cache size\text{max concurrent sequences} = \frac{\text{GPU memory} - \text{model weights} - \text{overhead}}{\text{per-sequence KV cache size}}max concurrent sequences=per-sequence KV cache sizeGPU memory−model weights−overhead​

Stel voor capacity arithmetic dat de runtime een KV-budget van 40 GiB exposeert voor Llama 3.1 70B met een FP16 KV cache. Elke sequence van 4K gebruikt ongeveer 1.25 GiB en elke sequence van 128K ongeveer 40 GiB. Dat budget past dus maximaal ongeveer 32 sequences van 4K of één sequence van 128K, vóór allocator-, runtime-, workload-variance- en SLO-overhead. Daarom sturen GPU selection en KV cache optimization direct het capacity plan.

De capacity formula voor fleet sizing:

required GPUs=peak tokens/s×safety-factor multiplierper-GPU tokens/s at target SLO\text{required GPUs} = \frac{\text{peak tokens/s} \times \text{safety-factor multiplier}}{\text{per-GPU tokens/s at target SLO}}required GPUs=per-GPU tokens/s at target SLOpeak tokens/s×safety-factor multiplier​

Zet beide rates om naar dezelfde time unit voordat je deelt. Het relevante detail is “at target SLO”. Een safety-factor-multiplier zoals 1.3 reserveert 30% headroom; kies deze op basis van gemeten burstiness, failures en recovery time. Peak token throughput en SLO-compliant throughput kunnen sterk verschillen naarmate concurrency stijgt. Benchmark met de echte prompt- en output-length distribution bij de vereiste TTFT- en TPOT-thresholds, in plaats van een theoretical maximum te gebruiken.

GPU utilization is onvoldoende als enige autoscaling-signal, omdat deze zowel tijdens gezonde processing als tijdens overload hoog kan blijven. Combineer haar met queue depth, KV-cache utilization en goodput degradation. Tune thresholds met load tests; waarden zoals 80% KV utilization zijn startpunten, geen universele limits. Deze metrics worden geïntroduceerd in Section 43.

Scale-to-zero kan passen bij development- en staging-environments met lange idle periods. Serverless inference platforms en Kubernetes-based autoscalers zoals KEDA kunnen idle capacity verwijderen, maar de savings en cold-start time hangen af van model size, image- en weight-caching en infrastructure. Meet startup time voordat je dezelfde policy gebruikt voor latency-sensitive production traffic.

Het onderling verbonden system

KV-cache-demand beperkt de haalbare batch size naast weight memory, runtime-overhead en request lengths. Grotere batches kunnen arithmetic intensity verhogen, hoewel workload shape nog steeds bepaalt of decode memory-bound blijft. Continuous batching verbetert utilization maar verhoogt KV-allocation churn; PagedAttention reduceert fragmentation en pre-allocation-waste door sequences met variabele length.

Aan de trainingskant kan lifecycle cost het trainen van een kleiner model op meer tokens bevoordelen, zoals Llama 3 8B illustreert. GRPO reduceert de critic-state burden van PPO. In de geteste small-model-setup van DeepSeek-R1 presteerde distillation beter dan direct RL. Dit zijn design options om te evalueren, geen single training recipe.

Routing, caching, quantization en right-sized hardware versterken elkaar alleen wanneer elke optimization tegen dezelfde quality- en latency-target wordt gemeten.

Belangrijkste principes

  1. LLM inference heeft twee afzonderlijke phases. In gangbare serving-regimes neigt prefill naar compute en decode naar memory bandwidth; workload shape kan deze grens verschuiven.
  2. De KV cache is vaak een centrale constraint. De omvang beïnvloedt batch capacity en memory pressure. GQA, paged allocation en KV quantization richten zich op verschillende delen van die constraint.
  3. De GPU memory hierarchy verklaart veel optimizations. FlashAttention en kernel fusion reduceren dure data movement zonder de functie van het model te wijzigen.
  4. Continuous batching en PagedAttention werken samen. Eén gepubliceerde comparison rapporteert 23x throughput ten opzichte van zijn naive baseline; meet de winst in je eigen serving stack.
  5. Chinchilla-optimal is niet inference-optimal. Llama 3 8B werd bijvoorbeeld getraind met ongeveer 1.875 tokens per parameter om meer training compute in te ruilen voor goedkopere inference.
  6. GRPO en distillation hebben de alignment-toolkit veranderd. DeepSeek-R1 rapporteerde sterkere small-model-results met distillation dan met zijn direct-RL-experiments.
  7. Cost optimization compount alleen over eligible traffic. Model quantization, routing, caching en batch APIs vereisen afzonderlijke coverage- en quality-metingen voordat de savings mogen worden vermenigvuldigd.
  8. Serving hardware moet bij de bottleneck passen. Decode-heavy workloads profiteren vaak van HBM capacity en bandwidth; prefill-heavy workloads leggen meer gewicht op compute.
