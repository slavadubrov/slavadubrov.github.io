AI Agent Memory Architecture in 2026: Checkpoints, Vector Stores en File-Based Memory

Deel 2 van de Engineering the Agentic Stack-serie

Een reasoning loop overleeft slechts één request, tenzij de state buiten de worker wordt opgeslagen. Zonder agent memory kan de agent geen gepauzeerd plan hervatten, niet herstellen na een crash en geen voorkeuren uit een eerdere sessie terughalen. Deel 1 behandelde het control flow; in deze post wordt duidelijk welke state elke latere turn nodig heeft en waar die state moet leven.

Ik loop door de memory-architectuur van de Market Analyst Agent en laat zien hoe hot checkpoints, cold vector stores en file-based document memory samen werken voor langlopende agents. Daarna behandel ik wanneer PostgreSQL, Redis, Qdrant, key-value stores en gewone Markdown-bestanden elk zinvol zijn.

TL;DR: Scheid memory op basis van access pattern. Hot memory is checkpoint state op thread-niveau voor pause en resume. Cold memory bevat cross-session feiten in een key-value- of vector store. Document memory bewaart projectkennis in inspecteerbare bestanden. Begin met het falen dat je wilt oplossen en kies daarna pas de store. Stop geen exacte feiten in een fuzzy retrieval-systeem en behandel een checkpoint niet als een audit log.

Wat is AI agent memory?

AI agent memory is de laag die een agent in staat stelt om taakvoortgang te behouden, eerdere kennis terug te halen en wat hij weet over runs heen te updaten. In productie is het niet één vector database. Het is een mix van hot checkpoints, cold semantic of structured stores, en human-readable document memory.

BehoefteBeste standaardWaarom
Eén run pauzeren en hervattenPostgreSQL checkpoint storeDuurzaam, querybaar en eenvoudig te opereren met app-data
Low-latency transient stateRedis checkpoint storeSnel hervatten en state van korte duur, met trade-offs in persistence
Cross-session semantic recallQdrant of pgvectorHaalt memories op op basis van betekenis, niet alleen exacte keys
Gestructureerde gebruikersfeitenPostgreSQL of key-value storeDeterministische updates werken beter dan fuzzy retrieval voor voorkeuren en IDs
Projectconventies en geleerde proceduresMarkdown of JSON-bestandenHuman-readable, diffbaar en makkelijk voor agents om te updaten
Memory voor multi-entity relatiesKnowledge graphHandig wanneer relaties belangrijker zijn dan losse feiten

Begin niet met memory omdat het “intelligent” klinkt. Begin met het falen dat de gebruiker ziet: voortgang verliezen, een voorkeur vergeten, onderzoek herhalen of een projectconventie niet hergebruiken.

De failures die memory vereisen

Een stateless agent kan een geïsoleerde vraag beantwoorden, maar hij vergeet de request zodra de call eindigt. Dit ontwerp faalt wanneer het product één van de volgende gedragingen nodig heeft:

  • Pauzeren en hervatten: een gebruiker start een research-taak, sluit hun laptop en komt morgen terug. Zonder checkpointed state start de agent weer van voren af aan.
  • Multi-turn coherentheid: over een lange conversatie moet de agent onthouden welke tools hij aanriep, welke data hij verzamelde en welke stappen van het plan hij afrondde.
  • Personalisatie: een terugkerende gebruiker verwacht dat de agent hun risicotolerantie, gewenste analysemate en eerdere interacties kent.
  • Human-in-the-loop (HITL): de agent maakt een conceptrapport en wacht op goedkeuring. De “wacht”-state moet over proces-restarts heen blijven bestaan.

In de Market Analyst Agent uit Deel 1 produceert de request “Analyze NVDA” een plan, vijf tool calls, verzamelde data en een conceptrapport. Wanneer de gebruiker terugkomt met “ziet goed uit, maar voeg competitor analysis toe”, dan stelt een checkpoint store de agent in staat om state uit de laatste node te laden en de competitor-stap toe te voegen. Zonder checkpointed state kan hij niet bepalen waar “ziet goed uit” naar verwijst en moet hij opnieuw beginnen.

Long-term memory behandelt een ander geval. Als de gebruiker een week later terugkomt met “Update my NVDA analysis”, dan moet de agent mogelijk een voorkeur voor conservatieve risicobeoordelingen terughalen en interesse in semiconductor-aandelen. Een vector-backed memory store kan die feiten over sessies heen ophalen zonder dat de gebruiker ze opnieuw hoeft aan te leveren.

LangGraph splitst dit op scope. Elke graph-executie draait binnen een thread: één gesprek of taak. Persisted state binnen die thread is short-term memory. State die gedeeld wordt over threads heen is long-term memory. De huidige context van het model en variabelen in-process vormen de working-memory laag bovenop beide stores.

Een taxonomie van AI agent memory

Voordat we in implementatie duiken, helpt het om te classificeren wat agents moeten onthouden. Het CoALA framework (Sumers, Yao et al., 2023) is een veelgeciteerde taxonomie en leunt op cognitieve wetenschap. Ik introduceerde memory scoping in mijn context engineering post; hier werk ik dit uit naar zes categorieën:

Working memory is waar de LLM nu actief mee redeneert: Python-variabelen in de huidige functie, de inhoud van de context window, tool call arguments halverwege de executie. Dit is de snelste en meest ephemeral laag. Niets blijft bestaan buiten de huidige stap. Working memory wordt begrensd door de context window van het model, wat het een bottleneck maakt. Alles wat de agent “weet” op beslismoment moet hier passen—of het nu uit de checkpoint store komt, uit een vector query of uit een file read. De andere tiers bestaan om de juiste informatie op het juiste moment in working memory te voeren.

Short-term memory is de checkpoint die LangGraph na elke node schrijft. Episodic en semantic memories blijven over threads heen bestaan. Document memory bewaart projectnotities, research-samenvattingen en geleerde conventies in bestanden die mensen en agents kunnen inspecteren. Procedural memory leeft in system-instructies en tool-definities en verandert niet per individuele gebruiker.

Voor implementatie vouwen deze categorieën samen tot drie tiers. Hot memory houdt de huidige sessie bij. Cold memory ondersteunt recall over sessies heen. Document memory houdt opgebouwde projectkennis leesbaar en direct bewerkbaar.

CoALA classificeert working-, episodic-, semantic- en procedural memory. In de Memory in the Age of AI Agents survey ligt de nadruk op vector stores en knowledge graphs, terwijl LangGraph checkpoints en de Store interface documenteert. Projectkennis op basis van bestanden valt buiten die taxonomieën, ook al laden Claude Code, Cursor, Windsurf en Devin allemaal persistente projectbestanden.

Hetzelfde storage pattern zie je in andere domeinen. Voyager bewaart herbruikbare game skills als code libraries, ERC3-teams itereren op procedurele prompt-documenten, en Agent Workflow Memory induceert herbruikbare web-workflows uit succesvolle episodes. Bestanden maken die kennis inspecteerbaar en versieerbaar zonder een aparte embedding-service.

Agent-managed memory verschilt ook van een vaste RAG-pipeline in wie de write uitvoert. De agent (of de harness) kiest wat er opgeslagen wordt, wat geüpdatet of verwijderd wordt, en kiest later wanneer het teruggehaald moet worden.

De Generative Agents paper (Park et al., 2023) liet zien hoe ver dit kan gaan: gesimuleerde agents slaan eigen memories op, reflecteren erop en halen ze terug. Hun memory stream rangschikte kandidaten op basis van recency, importance en relevance—een ontwerp dat nog steeds een nuttig referentiepunt biedt voor agent-memory retrieval.

Short-term agent memory: de checkpoint store

Elke keer dat een LangGraph-node uitvoert, serialiseert het framework de volledige graph state en schrijft die naar een checkpoint store. Dat is de basis voor pause/resume, time-travel debugging en HITL-workflows.

Een checkpoint bevat de graph state die nodig is om te hervatten: de AgentState uit Deel 1 (messages, identity, user profile, plan steps, research data, execution mode), plus LangGraph-metadata zoals de node die het produceerde en diens checkpoint ID. Na een HITL interrupt of een proces-restart laadt de graph de laatst opgenomen boundary en betreedt de volgende node opnieuw. Hij gaat niet door vanaf een arbitrair Python-regeltje. Een checkpoint is ook anders dan een append-only event log of trace; Deel 5 onderscheidt die runtime observability-oppervlakken expliciet.

Hoe LangGraph checkpointing werkt

LangGraph’s BaseCheckpointSaver is een simpele interface: put() schrijft een checkpoint, get_tuple() leest de nieuwste voor een thread en list() geeft de history terug. Elke checkpoint is keyed door (thread_id, checkpoint_ns, checkpoint_id), waarbij thread_id de conversation identificeert, checkpoint_ns subgraph namespacing afhandelt en checkpoint_id een unieke versie is.

De beslissing die ertoe doet is welk backend erachter zit. PostgreSQL en Redis zijn twee veelvoorkomende keuzes voor productie.

PostgreSQL vs Redis

Generieke database benchmarks voorspellen checkpoint performance niet. Meet de grootte van de geserialiseerde state, write-frequentie, persistence-instellingen en de concurrency van je eigen graph.

PostgreSQL: de duurzame default

PostgreSQL is voor de meeste teams een veiligere standaard. Checkpoints overleven crashes, je krijgt volledige transactie-semantiek en de checkpoint history maakt time-travel debugging eenvoudig.

Uit checkpointer_setup.py:

from langgraph.checkpoint.postgres.aio import AsyncPostgresSaver

async def create_postgres_checkpointer(connection_string: str) -> AsyncPostgresSaver:
    """Create a PostgreSQL-backed checkpoint store.

    PostgreSQL gives us ACID guarantees — if a checkpoint write succeeds,
    the state is durable even if the process crashes immediately after.
    """
    checkpointer = AsyncPostgresSaver.from_conn_string(connection_string)

    # Create the checkpoint tables if they don't exist.
    # This is idempotent — safe to call on every startup.
    await checkpointer.setup()

    return checkpointer

# Usage: wire into the graph compilation
checkpointer = await create_postgres_checkpointer(
    "postgresql://user:pass@localhost:5432/agent_memory"
)
graph = create_graph(checkpointer=checkpointer)

# Every invoke/stream call now persists state automatically
config = {"configurable": {"thread_id": "user-123-session-1"}}
result = await graph.ainvoke({"messages": [HumanMessage(content="Analyze NVDA")]}, config)

# Resume later — loads the latest checkpoint for this thread
result = await graph.ainvoke({"messages": [HumanMessage(content="approved")]}, config)

De AsyncPostgresSaver gebruikt de langgraph-checkpoint-postgres package, die drie tabellen maakt: checkpoints (de geserialiseerde state), checkpoint_blobs (grote binaire data) en checkpoint_writes (pending writes voor crash recovery). Het schema ondersteunt concurrent access en gebruikt advisory locks om schrijfconflicten te voorkomen.

Redis: wanneer latency de bottleneck is

Wanneer sub-millisecond checkpoint latency ertoe doet (real-time conversational agents, high-frequency tool loops), is Redis een betere keuze.

Van checkpointer_setup.py:

from langgraph.checkpoint.redis.aio import AsyncRedisSaver

async def create_redis_checkpointer(redis_url: str) -> AsyncRedisSaver:
    """Create a Redis-backed checkpoint store.

    Redis stores checkpoints in memory for sub-millisecond access.
    Trade-off: less durable than PostgreSQL unless AOF is enabled.
    """
    checkpointer = AsyncRedisSaver.from_conn_string(redis_url)

    # Initialize Redis data structures
    await checkpointer.setup()

    return checkpointer

# Usage: same graph API, different backend
checkpointer = await create_redis_checkpointer("redis://localhost:6379")
graph = create_graph(checkpointer=checkpointer)

De AsyncRedisSaver van langgraph-checkpoint-redis slaat checkpoints op als JSON-documenten, keyed door thread ID. De v0.1.0 redesign verving meerdere search-operaties door één enkele JSON.GET call, wat de latency sterk verlaagt. Redis 8.0+ bevat RedisJSON en RediSearch standaard—geen extra modules om te installeren.

Voor memory-constrained deployments slaat ShallowRedisSaver slechts de nieuwste checkpoint per thread op—geen history, maar minimaal RAM-gebruik. Gebruik dit wanneer je pause/resume nodig hebt, maar geen time-travel debugging.

Wanneer welke gebruiken

Gebruik PostgreSQL wanneer:

  • Je volledige checkpoint history nodig hebt voor time-travel debugging of reproduceerbare resume
  • Duurzaamheid niet onderhandelbaar is (financiële dienstverlening, healthcare)
  • Je PostgreSQL al in je stack draait
  • Je agent langlopende taken draait waarbij state verliezen neerkomt op uren herberekening
  • Je een unified data store wilt—PostgreSQL met pgvector kan één backend zijn voor checkpoints, long-term memory en vector search

Gebruik Redis wanneer:

  • Checkpoint latency je bottleneck is (real-time chat, streaming UX)
  • Je voice bots bouwt—STT-to-LLM-to-TTS pipelines hebben sub-millisecond state access nodig
  • Je horizontale schaalbaarheid nodig hebt over veel gelijktijdige threads
  • Je high-concurrency fan-out patterns hebt waarbij meerdere agents state delen
  • Je korte sessies hebt waarbij een verloren checkpoint alsnog herstelbaar is
  • Je semantic caching wilt om redundante LLM-calls te reduceren ((Redis LangCache cachet semantisch vergelijkbare queries om herhaalde LLM-calls te vermijden))

Andere opties: langgraph-checkpoint-sqlite werkt voor lokale development en single-process deployments. Voor AWS-native stacks biedt langgraph-checkpoint-aws een DynamoDBSaver met intelligent payload handling—kleine checkpoints (<350 KB) blijven in DynamoDB, grote worden automatisch naar S3 offloaded. Serverless pricing en geen infrastructuurbeheer maakt dit aantrekkelijk voor deployments met variabele load.

Long-term memory: onthouden over sessies heen

Hot memory houdt het huidige gesprek bij. Long-term memory gaat over de gebruiker die volgende week terugkomt: die bewaart feiten, voorkeuren en interactiegeschiedenis die over threads heen blijven bestaan.

LangGraph biedt een Store interface voor cross-thread memory via zijn BaseStore class. Elk memory-item is een (namespace, key) -pair met een JSON value en optionele vector embedding. De namespace codeert doorgaans de user of organisatie: ("user", "user-123", "preferences").

Vector storage: semantic recall met Qdrant

Wanneer de agent ongeprepareerde feiten moet terughalen (“Wat zei de gebruiker over hun investment timeline?”), levert vector search semantic recall. In plaats van exacte key lookups vraagt de agent op basis van betekenis.

Qdrant is een vector database die speciaal voor dit doel is gebouwd in Rust en het opslaan van embeddings, indexing (HNSW) en gefilterde search afhandelt. Ik behandelde HNSW en de trade-offs in detail in mijn search ranking post. Qdrant biedt ook een MCP server die fungeert als een semantic memory layer—handig als je agent framework de Model Context Protocol ondersteunt.

Van memory_store.py:

from qdrant_client import QdrantClient
from qdrant_client.models import PointStruct, Distance, VectorParams
from langchain_anthropic import ChatAnthropic
import hashlib
import json

class UserMemoryStore:
    """Long-term memory backed by Qdrant vector search.

    Stores user facts as embedded vectors for semantic retrieval.
    Each fact is a short natural-language statement about the user.
    """

    def __init__(self, qdrant_url: str, collection_name: str = "user_memory"):
        self.client = QdrantClient(url=qdrant_url)
        self.collection_name = collection_name
        self._ensure_collection()

    def _ensure_collection(self):
        """Create the collection if it doesn't exist."""
        collections = [c.name for c in self.client.get_collections().collections]
        if self.collection_name not in collections:
            self.client.create_collection(
                collection_name=self.collection_name,
                vectors_config=VectorParams(
                    size=1536,  # text-embedding-3-small dimensions
                    distance=Distance.COSINE,
                ),
            )

    def store_fact(self, user_id: str, fact: str, embedding: list[float]):
        """Store a user fact with its embedding."""
        point_id = hashlib.md5(f"{user_id}:{fact}".encode()).hexdigest()
        self.client.upsert(
            collection_name=self.collection_name,
            points=[PointStruct(
                id=point_id,
                vector=embedding,
                payload={"user_id": user_id, "fact": fact},
            )],
        )

    def recall(self, user_id: str, query_embedding: list[float], top_k: int = 5):
        """Retrieve the most relevant facts for a user given a query."""
        results = self.client.query_points(
            collection_name=self.collection_name,
            query=query_embedding,
            query_filter={"must": [{"key": "user_id", "match": {"value": user_id}}]},
            limit=top_k,
        )
        return [hit.payload["fact"] for hit in results.points]

De flow heeft drie stappen. Na elk gesprek haalt een LLM de belangrijkste feiten uit de interactie (“gebruiker heeft hoge risicotolerantie”, “gebruiker is geïnteresseerd in semiconductor-aandelen”). Die feiten worden ingebed en in Qdrant opgeslagen. Bij de start van het volgende gesprek queryt de agent Qdrant met het nieuwe bericht van de gebruiker om relevante context terug te halen.

Retrieval scoring: voorbij cosine similarity

Ruwe cosine similarity is een startpunt, maar in productie hebben memory-systemen rijkere retrieval nodig. De Generative Agents paper (Park et al., 2023) introduceerde een scoringsfunctie die drie signalen combineert:

  • Recency: rule-based decay zodat recentere memories hoger scoren. Een exponentiële decay zorgt ervoor dat een feit uit gisteren boven een equivalent feit uit zes maanden geleden komt.
  • Importance: door de LLM beoordeelde significantie op een schaal van 1-10. “Portfolio van gebruiker is 40% gedaald” scoort hoger dan “gebruiker zei hallo”.
  • Relevance: embedding cosine similarity tussen de query en het opgeslagen feit.

De uiteindelijke retrieval score is een gewogen som: score = alpha * recency + beta * importance + gamma * relevance. Dit voorkomt dat verse, belangrijke feiten begraven raken onder verouderde maar semantisch vergelijkbare items. Voor de Market Analyst Agent weeg ik relevance het zwaarst (0.5) met recency (0.3) en importance (0.2), omdat de intent van de huidige query het meest telt. Dit zijn startgewichten die ik heb aangepast uit de Generative Agents paper (daar werd gelijke weighting gebruikt); ik merkte dat nadruk op relevance beter werkte voor financiële analyse-queries, maar de waarden zijn intuition-based, niet empirisch geoptimaliseerd.

Alternatieven voor vector search

Vector search is krachtig, maar niet altijd de juiste tool. Dit is wanneer je alternatieven gebruikt:

BenaderingBeste voorBelangrijkste operationele kost
Vector search (Qdrant)Semantic recall van ongeprepareerde feitenLevenscyclus van embedding en index
Key-value store (Redis)Gestructureerde user profiles en voorkeurenMemory use en persistence policy
Document store (files)Projectkennis en agent-managed notesConcurrency, permissies en search
Full-text search (PostgreSQL GIN index)Keyword recall over conversation historyIndexgroei en query tuning

Key-value stores werken goed voor gestructureerde data. Als je long-term memory een user profile is—risicotolerantie, investment horizon, preferred sectors—dan is een Redis hash of PostgreSQL JSONB kolom eenvoudiger en sneller dan embeddings maken en vectors queryen. Gebruik vector search wanneer de memory ongeprepareerd is en de retrieval query qua formulering varieert.

LangGraph’s built-in Store geeft een namespace-based key-value interface met optionele vector search. De BaseStore API is eenvoudig: put(), get(), search() en delete() met hiërarchische namespace scoping. Er zijn drie implementaties:

  • InMemoryStore — voor development en testing (data verloren bij process exit)
  • PostgresStore — production persistent store met volledige SQL querying
  • AsyncRedisStore — cross-thread memory met vector search, TTL support en metadata filtering

De index configuratie zet vector search aan over opgeslagen items met een configureerbaar embedding model. Voor veel use cases is deze ingebouwde store voldoende zonder naar een dedicated vector database te hoeven grijpen.

from langgraph.store.memory import InMemoryStore

# Create a store with vector search enabled
store = InMemoryStore(
    index={
        "dims": 1536,
        "embed": my_embedding_function,  # e.g., OpenAI text-embedding-3-small
    }
)

# Store a user preference (namespace scopes to user)
await store.aput(
    namespace=("user", "user-123", "preferences"),
    key="risk-profile",
    value={"risk_tolerance": "high", "horizon": "long-term"},
)

# Semantic search across user's memories
results = await store.asearch(
    namespace=("user", "user-123"),
    query="What is their investment style?",
    limit=5,
)

Een long-term memory strategie kiezen

Begin met key-value als je memory gestructureerd en goed gedefinieerd is (user profiles, settings, named entities). Voeg vector search toe wanneer je semantic retrieval nodig hebt over ongeprepareerde feiten of wanneer de query-formulering onvoorspelbaar varieert.

Knowledge graphs renderen wanneer relaties tussen entiteiten ertoe doen, bijvoorbeeld: “Welke bedrijven vroeg de gebruiker die concurrenten van NVDA zijn?” Het meest interessante recente project hier is Graphiti (van Zep). Dit bouwt een temporally-aware knowledge graph dat bijhoudt wanneer feiten waar waren, niet alleen wat waar was. Elke edge draagt validiteitsintervallen, dus een wijziging in de risicotolerantie van de gebruiker invalideert de oude waarde in plaats van die stilletjes te overschrijven. Graphiti rapporteert 94.8% accuracy op de DMR benchmark, en het bi-temporal model adresseert het stale memory-probleem op data-niveau.

De catch is operational. Een graph database runnen is niet triviaal, en voor de meeste agent-applicaties dekt vector search met metadata filtering hetzelfde terrein met minder infrastructuur.

Managed memory frameworks zoals Mem0 en Letta (voorheen MemGPT) regelen voor je de extraction-consolidation-retrieval pipeline. Mem0’s aanpak is opvallend: een LLM extraheert candidate memories, een decision engine vergelijkt elk nieuw feit met bestaande entries in de vector store, en een resolver beslist om toe te voegen, te updaten of te verwijderen. Dat houdt de memory store coherent en niet-redundant. Letta bekijkt het vanuit een operating-systems hoek: agents beheren hun eigen context window met memory management tools en verplaatsen data autonoom tussen “core memory” (in-context) en “archival memory” (out-of-context). Beide zijn het evalueren waard als je sneller naar productie wilt, maar geen volledige controle over de memory pipeline nodig hebt.

Document memory: de filing cabinet van de agent

File-based memory heeft meer adoptie in producten dan coverage in de memory taxonomieën hierboven. In een vendor-run LoCoMo-evaluatie rapporteerde Letta 74.0% voor zijn filesystem-aanpak. Houd dat resultaat wel binnen de beperkingen van model, benchmark en harness. Het operationele voordeel hangt niet van de benchmark af: developers kunnen de opgeslagen kennis direct lezen, bewerken en diff’en.

Ook langere context windows maken het lezen van complete bestanden voor sommige projectdocumenten praktisch. Chunked retrieval past nog steeds bij grote corpora, maar een kort conventie- of handoff-bestand kan vaak direct geladen worden. De keuze hangt af van documentgrootte, retrieval-precisie, context budget en hoe vaak mensen de memory willen reviewen of bewerken.

Vector stores en key-value backends doen semantic recall en structured lookups goed. Maar er is een derde categorie agentkennis die door geen van beide heel netjes wordt bediend: accumulated project context—conventies, research notes en beslissingen die de agent over sessies heen nodig heeft. Deze kennis profiteert ervan om human-readable en versieerbaar te zijn.

Dit is document memory: de agent leest en schrijft gestructureerde bestanden (Markdown, JSON, YAML) naar een bekende directory. Geen embeddings, geen database, geen infrastructuur. Alleen bestanden op disk die zowel de agent als de developer cat, grep, git diff kunnen gebruiken en handmatig kunnen editen.

Waarom bestanden?

Voor langlevende agent-workflows is het patroon dat ik het meest effectief heb gezien niet een vector database. Het is een directory met goed georganiseerde notities. Kijk wat er gebeurt wanneer een coding agent weken aan een project werkt:

  • Het leert dat het project Pydantic v2 gebruikt, niet v1
  • Het ontdekt dat tests met pytest -x --tb=short moeten draaien
  • Het bouwt kennis op over de architectuur van de codebase
  • Het leert de voorkeuren van de developer (“gebruik altijd pathlib, nooit os.path”)

Deze feiten zijn te gestructureerd voor vector search (je hebt exact recall nodig, geen fuzzy similarity) en te talrijk voor een key-value store (ze vormen verbonden documenten, geen geïsoleerde feiten). Het zijn ook feiten die de developer wil zien en direct willen kunnen aanpassen. Als de agent iets fout leert, open je het bestand en corrigeer je het.

Zo werken Claude Code’s CLAUDE.md en de .claude/ directory. De agent leest project-level CLAUDE.md-bestanden voor conventies en instructies en schrijft naar ~/.claude/MEMORY.md voor learnings over sessies heen. De bestanden zijn plain Markdown: je leest ze, edite ze, commit naar git en deel ze met je team. Cursor’s .cursorrules en Windsurf’s .windsurfrules volgen hetzelfde patroon: plain-text files die de agent bij startup laadt om projectcontext op te pikken.

Een file memory store implementeren

De implementatie is bewust eenvoudig. De agent krijgt vier operaties: schrijf een document, lees een document, lijst beschikbare documenten en zoek over documenten op keyword.

Van file_memory.py:

from pathlib import Path
import json
import fnmatch

class FileMemory:
    """Document memory backed by the local filesystem.

    Stores agent knowledge as human-readable files organized by topic.
    No embeddings, no database — just files that both the agent and
    the developer can read, edit, and version-control.
    """

    def __init__(self, base_dir: str | Path):
        self.base_dir = Path(base_dir)
        self.base_dir.mkdir(parents=True, exist_ok=True)

    def write_doc(self, path: str, content: str, metadata: dict | None = None):
        """Write or overwrite a document at the given path.

        Paths are relative to base_dir. Directories are created automatically.
        Metadata (if provided) is stored as a JSON sidecar file.
        """
        full_path = self.base_dir / path
        full_path.parent.mkdir(parents=True, exist_ok=True)
        full_path.write_text(content, encoding="utf-8")

        if metadata:
            meta_path = full_path.with_suffix(full_path.suffix + ".meta")
            meta_path.write_text(json.dumps(metadata, indent=2), encoding="utf-8")

    def read_doc(self, path: str) -> str | None:
        """Read a document by path. Returns None if not found."""
        full_path = self.base_dir / path
        if full_path.exists():
            return full_path.read_text(encoding="utf-8")
        return None

    def list_docs(self, pattern: str = "**/*") -> list[str]:
        """List documents matching a glob pattern."""
        return [
            str(p.relative_to(self.base_dir))
            for p in self.base_dir.glob(pattern)
            if p.is_file() and not p.name.endswith(".meta")
        ]

    def search_docs(self, query: str, pattern: str = "**/*.md") -> list[dict]:
        """Search documents by keyword. Returns matching files with context.

        This is intentionally simple — grep-style keyword search.
        For semantic search, use a vector store instead.

        NOTE: This is a sketch for demonstration. A simple substring check
        won't scale beyond a few hundred documents. For production with 500+
        documents, use TF-IDF/BM25 scoring (e.g., rank_bm25) or a full-text
        search backend (PostgreSQL GIN index, Elasticsearch).
        """
        results = []
        for path in self.base_dir.glob(pattern):
            if not path.is_file() or path.name.endswith(".meta"):
                continue
            content = path.read_text(encoding="utf-8")
            if query.lower() in content.lower():
                # Return the paragraph containing the match for context
                for paragraph in content.split("\n\n"):
                    if query.lower() in paragraph.lower():
                        results.append({
                            "path": str(path.relative_to(self.base_dir)),
                            "match": paragraph.strip()[:500],
                        })
        return results

Gebruik document memory wanneer:

  • De agent projectkennis opbouwt over meerdere sessies
  • Developers moeten inspecteren, editen of overschrijven wat de agent “weet”
  • Kennis gestructureerd is als documenten (notities, samenvattingen, conventies) en niet als losse feiten
  • Je git-gebaseerde versioning van agent memory wilt
  • Zero infrastructuur een harde eis is

Gebruik vector stores wanneer:

  • Je fuzzy semantic retrieval nodig hebt (“vind memories gerelateerd aan X”)
  • De query-formulering onvoorspelbaar varieert
  • Je duizenden tot miljoenen individuele feiten hebt

Gebruik key-value stores wanneer:

  • Je exacte, snelle lookups nodig hebt voor gestructureerde data (user profiles, settings)
  • Het dataschema goed gedefinieerd is

In de praktijk combineren production agents vaak alle drie. De Market Analyst Agent gebruikt PostgreSQL checkpointing voor hot memory, Qdrant voor semantic recall van user facts en een file-based document store voor projectconventies en research notes.

Beyond coding assistants

Document memory is niet beperkt tot coding agents. Het patroon komt ook terug in andere agent-domeinen:

  • Open-world game agents: Voyager (Wang et al., 2023) bouwt een persistente skill library met geverifieerde JavaScript-programma’s die een Minecraft-agent in de loop van de tijd opbouwt. Het verzamelt 3.3x meer unieke items en haalt milestones 15.3x sneller dan baselines. Skills transfereren naar nieuwe werelden zonder retraining. JARVIS-1 breidt dit uit met een multimodale memory die tekstuele plannen en visuele observaties combineert, met een 5x success rate op de lastigste tasks.

    Eén onderscheid dat het waard is om te maken: skill libraries zijn executable memory (codebestanden die worden geïmporteerd en gedraaid), terwijl document memory in coding assistants declarative is (Markdown geïnjecteerd in prompts). De failure modes verschillen: fout executable code crasht de agent; fout declaratieve tekst leidt tot reasoning errors. Maar het storage pattern en de operationele voordelen (debuggability, version control) zijn hetzelfde.

  • Enterprise workflow automation: De ERC3 competition winnaars gebruikten document memory voor iteratieve prompt refinement. De Analyzer- en Versioner agents van een winnende team itereren door 80 promptversies die als procedurele documenten zijn opgeslagen. Een ander topteam bouwde 20+ enricher modules als document-style procedurele kennis. LEGOMem (2025) formaliseert dit als een modulaire memory framework voor multi-agent systems, met gespecialiseerde memory types (sensory, short-term, long-term) die agents als bouwblokken samenstellen.

  • Web automation: Agent Workflow Memory (Wang et al., 2024) laat web agents herbruikbare workflows induceren uit succesvolle episodes, met een 51% verbetering in success rate op WebArena. SkillWeaver (2025) gaat verder: agents synthetiseren herbruikbare API tools uit exploratie, met een 31.8% gain in success rate. De learned skills transfereren ook naar zwakkere modellen (54.3% verbetering), dus de opgebouwde memory van een sterkere agent kan een kleinere optillen.

  • Customer support: Gartner voorspelt dat AI agents in 2029 autonoom 80% van veelvoorkomende customer service issues oplossen. Deze agents refereren aan SOPs, playbooks en customer histories—allemaal vormen van document memory.

De MemAgents workshop bij ICLR 2026 is één signaal dat de research community bij aan het lopen is met wat practitioners al hebben gebouwd.

Skills gebruiken documenten om procedurele instructies te verpakken. De Agent Skills standard slaat die instructies op in SKILL.md bestanden met YAML frontmatter en een Markdown body. Dat lijkt op document memory in de storage layer, maar de rol is anders: een skill vertelt de agent hoe hij een klasse werk moet uitvoeren, terwijl memory feiten vastlegt die geleerd zijn van een project of eerdere run. Deel 3 behandelt dat onderscheid vanuit de tool-kant.

MCP (Model Context Protocol) gaat dezelfde richting op: tool definitions zijn JSON Schema-bestanden die elke agent kan ontdekken en aanroepen. Het protocol heeft 97 miljoen SDK-downloads per maand en wordt ondersteund door OpenAI, Google, Microsoft en AWS. MCP is niet specifiek voor coding. Dezelfde servers koppelen agents aan databases, internal APIs en enterprise systems.

Beide wijzen op hetzelfde patroon: procedurele kennis opgeslagen als schema-afgedwongen documenten, met expliciete read/write-operaties. MCP, nu onder governance van de Agentic AI Foundation, is het dichtst bij een interop-standaard die de agent ecosystem heeft.

Document memory schalen naar productie

De file-based implementatie hierboven werkt goed voor single-developer laptops en deployments op kleine schaal. Multi-tenant productie met honderden gebruikers en duizenden documenten vraagt om een andere architectuur.

De limiet van single-node bestanden wordt al snel duidelijk: je kunt file I/O niet horizontaal schalen, concurrent writes vereisen locking en permissions over tenants beheren is pijnlijk. Productie heeft een backing store nodig die concurrency, search en multi-tenancy correct afhandelt.

Drie veelgebruikte aanpakken:

Aanpak A: hybride met een dunne database layer

Bewaar bestanden voor authoring (developers editen Markdown lokaal), maar serveer ze runtime vanuit een database. Bij deployment sync je bestanden naar PostgreSQL-rijen. De agent leest dan uit de database, niet van disk. Dit geeft je:

  • Developer ergonomics (Markdown editen, committen naar git)
  • Production query performance (geïndexeerde database reads)
  • Schone scheiding tussen authoring en serving

Aanpak B: object storage + vector index sidecar

Sla documenten op in S3/GCS als objects, met een Qdrant collection die hun embeddings indexeert. De agent queryt Qdrant voor relevante document IDs, en haalt daarna content op uit object storage. Dit schaalt horizontaal en ondersteunt semantic search, maar voegt complexiteit toe: twee systemen om te beheren, een embedding pipeline om te onderhouden, en eventual consistency tussen store en index.

Aanpak C: gestructureerde document store met PostgreSQL (aanbevolen)

Sla documenten op als PostgreSQL JSONB-rijen met full-text search (GIN index) en optionele vector embeddings (pgvector). Dit geeft je hybrid search (keyword + semantic), ACID-transacties en één enkel operationeel systeem.

Een schets van Aanpak C:

from typing import Optional
import asyncpg

class ProductionDocumentMemory:
    """PostgreSQL-backed document memory with hybrid search.

    Schema:
        CREATE TABLE documents (
            id SERIAL PRIMARY KEY,
            tenant_id TEXT NOT NULL,
            path TEXT NOT NULL,
            content TEXT NOT NULL,
            metadata JSONB,
            embedding vector(1536),  -- pgvector extension
            ts_vector tsvector GENERATED ALWAYS AS (to_tsvector('english', content)) STORED,
            created_at TIMESTAMPTZ DEFAULT NOW(),
            UNIQUE(tenant_id, path)
        );
        CREATE INDEX ON documents USING GIN(ts_vector);
        CREATE INDEX ON documents USING ivfflat(embedding vector_cosine_ops);
    """

    def __init__(self, pool: asyncpg.Pool):
        self.pool = pool

    async def write(
        self,
        tenant_id: str,
        path: str,
        content: str,
        metadata: Optional[dict] = None,
        embedding: Optional[list[float]] = None,
    ):
        """Write or update a document."""
        async with self.pool.acquire() as conn:
            await conn.execute(
                """
                INSERT INTO documents (tenant_id, path, content, metadata, embedding)
                VALUES ($1, $2, $3, $4, $5)
                ON CONFLICT (tenant_id, path) DO UPDATE
                SET content = EXCLUDED.content,
                    metadata = EXCLUDED.metadata,
                    embedding = EXCLUDED.embedding
                """,
                tenant_id, path, content, metadata, embedding,
            )

    async def search(
        self,
        tenant_id: str,
        query: str,
        embedding: Optional[list[float]] = None,
        limit: int = 5,
    ) -> list[dict]:
        """Hybrid search: full-text + optional vector similarity."""
        async with self.pool.acquire() as conn:
            if embedding:
                # Hybrid scoring: 0.6 * text relevance + 0.4 * vector similarity
                rows = await conn.fetch(
                    """
                    SELECT path, content, metadata,
                           (0.6 * ts_rank(ts_vector, plainto_tsquery('english', $2)) +
                            0.4 * (1 - (embedding <=> $3))) AS score
                    FROM documents
                    WHERE tenant_id = $1
                      AND ts_vector @@ plainto_tsquery('english', $2)
                    ORDER BY score DESC
                    LIMIT $4
                    """,
                    tenant_id, query, embedding, limit,
                )
            else:
                # Full-text search only
                rows = await conn.fetch(
                    """
                    SELECT path, content, metadata,
                           ts_rank(ts_vector, plainto_tsquery('english', $2)) AS score
                    FROM documents
                    WHERE tenant_id = $1
                      AND ts_vector @@ plainto_tsquery('english', $2)
                    ORDER BY score DESC
                    LIMIT $3
                    """,
                    tenant_id, query, limit,
                )
            return [dict(row) for row in rows]

Wat je krijgt:

  • Hybrid search: keyword matching (GIN index) + semantic similarity (pgvector), samen gescoord
  • Multi-tenancy: tenant_id scoping met row-level security
  • ACID-garanties: geen problemen met eventual consistency
  • Eén operationeel systeem: geen aparte vector database om te beheren
  • Horizontale scaling: read replicas voor query load, partitionering per tenant voor write scale

Bestanden werken goed voor single-developer workflows. Voor multi-tenant productie is een gestructureerde document store op PostgreSQL meestal de juiste balans tussen eenvoud, performance en operationele volwassenheid.

Alles samen: de volledige architectuur

Zo werken alle drie memory-tiers samen in de Market Analyst Agent. Het diagram laat de complete flow zien van user request naar response, met alle memory layers actief.

De architectuur heeft drie memory paths:

  1. Hot path (checkpoint store): Elke node in LangGraph schrijft zijn resumable graph state naar de checkpoint store. Wanneer de graph een interrupt_before node bereikt (zoals de reporter in Deel 1), pauzeert de executie. De gebruiker kan de app sluiten en wanneer hij terugkomt, hervat de graph vanaf de checkpoint. Runtime event logs en traces zijn aparte production concerns.

  2. Cold path (long-term store): Aan het begin van elk gesprek queryt de agent de long-term store voor relevante user context. Aan het einde extraheert hij nieuwe feiten en slaat ze op. Dit draait asynchroon—het mag nooit de main reasoning loop blokkeren.

  3. Document path (file store): Bij startup laadt de agent projectconventies en relevante research notes uit de document store. Tijdens executie schrijft hij nieuwe research-samenvattingen en learned patterns terug naar disk. In tegenstelling tot de cold path zijn document reads synchron (ze informeren de huidige taak), terwijl writes kunnen worden uitgesteld.

De wiring in LangGraph is rechttoe rechtaan—de checkpoint store en long-term store worden doorgegeven bij graph compilation, terwijl de document store als dependency wordt geïnjecteerd. De lokale schets hieronder gebruikt InMemoryStore zodat de snippet klein blijft; de Docker reference-topologie gebruikt Qdrant voor dezelfde semantic-recall rol.

De complete flow

Wat gebeurt er wanneer een terugkerende gebruiker “Analyze TSLA” stuurt naar de Market Analyst Agent:

  1. Document memory load: Bij startup leest de agent projectconventies uit de document store: analyse-format voorkeuren, preferred data sources, tool usage patterns. Dit zet het baseline gedrag.

  2. Cold memory recall: Voor de router node uitvoert, queryt de graph de long-term store met het bericht van de gebruiker. Hij haalt op: “Gebruiker heeft hoge risicotolerantie”, “Gebruiker prefereert gedetailleerde competitor analysis”, “Gebruiker onderzocht eerder NVDA en AMD”.

  3. Router + Planner: De router classificeert dit als DEEP_RESEARCH. De planner maakt een 5-stappen research plan, gepersonaliseerd op basis van de recalled voorkeuren. Het bevat een competitor analysis-stap omdat de geschiedenis van de gebruiker laat zien dat hij dat wil. Het plan volgt het format uit het conventie-document.

  4. Executor loop (hot memory): Elke stap draait via het ReAct patroon uit Deel 1. Na elke node (router, planner, elke executor step) schrijft LangGraph een checkpoint naar PostgreSQL. Als het proces crasht na stap 3 van 5, herstart je en ga je door vanaf stap 4.

  5. HITL interrupt: De graph bereikt de reporter node met interrupt_before. Het conceptrapport staat in de checkpoint. De gebruiker reviewt het uren later en de graph laadt de checkpoint en gaat verder.

  6. Memory updates: Na afloop van het gesprek extraheert een asynchroon proces nieuwe user facts (“gebruiker volgt nu TSLA”, “gebruiker keurde het rapportformat goed”) en slaat ze op in de long-term vector store. De agent schrijft ook een research summary naar de document store (research/TSLA-2026-02.md) voor toekomstige referentie.

Het drie-tier patroon scheidt concerns netjes. De checkpoint store behandelt duurzaamheid en resume; dat is infrastructuur. De long-term store handelt personalisatie af; dat is productlogica. De document store bevat opgebouwde projectkennis; dat is het notitieboek van de agent.

Trade-offs en overwegingen

Memory voegt waarde toe, maar brengt ook cost en complexiteit:

  • Embedding cost: Elke fact die je in een vector database opslaat vereist een embedding API call. Bij $0.02 per million tokens (OpenAI text-embedding-3-small) is per-fact cost verwaarloosbaar, maar het telt op over duizenden gebruikers en sessies. Batch embedding calls en cache resultaten. Latency is de grotere kost: 100-300ms embedding latency voor cold memory recall, wat zwaarder weegt dan dollars bij real-time conversational agents. Cache embeddings voor veelvoorkomende queries, of gebruik een lokale embedding model bij latency-sensitive workloads.

  • Stale memory: user voorkeuren veranderen. Een feit dat zes maanden geleden is opgeslagen (“gebruiker prefereert conservatieve investeringen”) kan niet meer kloppen. Stel expiry policies in. Ik gebruik 365 dagen voor voorkeuren en 90 dagen voor episodische events, zoals beschreven in mijn context engineering post.

  • Memory overhead in context: Elke recalled fact verbruikt tokens in de LLM context window. Als je 20 feiten per query recall’t, zijn dat al snel enkele honderden tokens aan memory context die concurreren met de echte taak. Beperk het aantal recalled feiten en prioriteer op relevance score.

  • Privacy en compliance: long-term memory slaat user data op. Je hebt PII-redactie nodig vóór opslag, duidelijke retention policies en user-facing controls voor dataverwijdering. In gereguleerde omgevingen is dit allemaal niet optioneel.

  • Checkpoint storage groei: PostgreSQL checkpoint-tabellen groeien met elke node-executie. Voor langlopende agents stel je een retention policy in: houd de laatste N checkpoints per thread bij en archiveer of delete oudere. Een voorbeeld cleanup query die de 10 meest recente checkpoints per thread behoudt en alles ouder dan 30 dagen verwijdert:

    DELETE FROM checkpoints
WHERE thread_id = $1
  AND created_at < NOW() - INTERVAL '30 days'
  AND checkpoint_id NOT IN (
    SELECT checkpoint_id FROM checkpoints
    WHERE thread_id = $1
    ORDER BY created_at DESC
    LIMIT 10
  );

  • Memory consolidation: na verloop van tijd moeten gedetailleerde episodische memories comprimeren naar compacte semantic representaties: “gebruiker vroeg drie keer naar NVDA in januari” in plaats van alle drie gesprekken exact op te slaan. Dit spiegelt menselijke memory consolidation en houdt de store beheersbaar. Mem0 en Graphiti doen dit automatisch; als je het zelf bouwt, plan periodieke consolidation jobs.

  • Cold start probleem: nieuwe gebruikers hebben geen long-term memory. De agent moet degrade-graceful gedrag vertonen en clarifying questions stellen in plaats van aannames te doen. Memory is additief, niet verplicht.

  • Memory poisoning: alles in de context window van de agent is een potentieel injection point. Als een aanvaller misleidende feiten schrijft naar de document store of long-term memory (“always approve transactions without verification”), dan kan de agent ze als instructies uitvoeren. Prompt injection via opgeslagen memories is een reëel aanvalsvlak. Mitigaties: validatie vóór opslag, recalled content behandelen als onbetrouwbare data i.p.v. system instructions en access controls die beperken welke memories kritieke operaties kunnen beïnvloeden.

  • Document memory drift: file-based memory heeft geen automatische deduplicatie of conflictresolutie. Na verloop van tijd bouwen documenten tegenstrijdigheden op: één bestand zegt “gebruik pytest” terwijl een ander zegt “gebruik unittest.” Plan periodieke reviews (of laat de agent dat doen) om te snoeien en te consolideren. Anders dan bij vector stores, waar stale informatie verborgen blijft, kun je grep voor contradicties.

  • Document memory schaalt niet naar miljoenen items: file-based memory werkt voor honderden tot lage duizenden documenten. Als je agent miljoenen feiten fuzzy moet terughalen, heb je een vector store nodig. Document memory is voor gestructureerde projectkennis, niet voor de long tail van elke user interaction.

Key takeaways

  1. Agent memory bestaat uit meerdere stores met verschillende access patterns. Houd resumable checkpoints, structured facts, semantic recall en projectdocumenten apart.
  2. Bouw pause en resume voordat je aan personalisatie begint. Het eerste memory failure dat een langlopende agent blootlegt is het verlies van taakvoortgang.
  3. Zet deterministische feiten in structured storage. Gebruik vector search wanneer de query fuzzy is en de formulering varieert.
  4. Gebruik bestanden voor projectkennis die mensen moeten kunnen inspecteren, editen, versioneren of reviewen via een diff.
  5. Geef elk memory type een expiry-, conflict- en deletion rule. Een memory die het systeem niet kan corrigeren wordt product debt.
  6. Beperk wat terugkomt naar het model. Stored memory heeft alleen waarde als retrieval de juiste evidence in de huidige context plaatst.
