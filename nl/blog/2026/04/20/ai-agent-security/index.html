AI Agent Security: permissies, sandboxes en MCP-dreigingen

Viacheslav Dubrov

2026-04-20 · Bijgewerkt 2026-09-12 · 37 min · AI-agenten

Automatische vertaling

Dit artikel is automatisch vertaald vanuit de oorspronkelijke Engelse versie.

Deze guide is bedoeld voor engineers die AI agents bouwen of deployen die tools gebruiken. Je leert waar je toolpermissies, sandboxrestricties, credentiallimieten en menselijke goedkeuring afdwingt, zodat je kunt bepalen welke check een onveilige actie stopt voordat die bestanden, netwerken of een extern systeem bereikt.

De harness is de code die elke prompt opbouwt, beslist welke voorgestelde tool calls worden uitgevoerd en resultaten terugstuurt naar het model. De meeste checks horen daar thuis, omdat dit de laatste goedkope plek is om een commando te stoppen. Nadat een commando is uitgevoerd, moeten de sandbox, de credentials die het heeft ontvangen en elk recoveryproces de schade beperken. Sommige incidenten in dit artikel bereiken helemaal geen model.

AI agent security is breder dan LLM-safety. Vroege guardrailproducten inspecteerden de input en output van één model call. Ze konden toxische tekst filteren, persoonlijke gegevens redigeren, jailbreaks blokkeren en off-topic antwoorden afwijzen. Die grens was nuttig zolang het model alleen tekst kon retourneren.

Tool loops voegden filesystems, shells, Model Context Protocol (MCP)-servers en credentials toe. Daarmee verschoof het threat model van onveilige tekst naar onveilige acties. De zeven incidentgroepen hieronder omvatten indirecte prompt injection en fouten in configuratie, identity en softwaredistributie. Text screening kan helpen bij sommige kwaadaardige inputs; het kan de controls op die execution boundaries niet vervangen.

Wanneer een agent een repository kan lezen, een tool kan aanroepen of data naar een derde partij kan sturen, koppel je elke voorgestelde actie aan de check die haar kan stoppen. De volgende secties behandelen permissies, hooks, sandboxes, credentials en human review.

TL;DR

Contentfilters inspecteren tekst rond een model call. Agent security regelt ook voorgestelde tool calls, credentials, bestanden, netwerktoegang en onomkeerbare side effects. Verschillende incidenten omzeilden het model volledig; andere gebruikten kwaadaardige tekst om toegestane operaties te sturen. Een praktische policy stack combineert permissies, pre-tool hooks, OS-sandboxes, human escalation, scoped credentials en een audit trace.

AI agent security stack

Geen enkele guardrail beveiligt een agent op zichzelf. Elk onderdeel van het systeem heeft een eigen check nodig.

De tabel laat zien waar elke check draait. De harness is het eerder beschreven controlprogramma. De runtime is de infrastructuur die dit gebruikt: de sandbox, session log, checkpoint store en traces die een worker restart overleven.

Content filtersUnsafe input and output textToxic output, PII leakage, policy-violating completionsHarness
Permission ladderWhich tools, paths, APIs, and scopes the agent can useA summarizer trying to write to production systemsHarness
Pre-tool policy hookWhether this specific action should run nowShell command built from untrusted retrieved contentHarness
SandboxWhat the tool can touch at the OS and network layerFile exfiltration, dependency compromise, command injectionRuntime

MCP and token scopingWhich server and audience a credential is valid forToken reuse across an unintended tool serverRuntime
Audit traceWhat happened, who approved it, and whyIncident investigation after a long autonomous runRuntime

Contentfilters vragen of het model iets onveiligs heeft gezegd. Agent security vraagt ook of het systeem de volgende actie mag uitvoeren.

De harness-rijen bepalen of een actie mag worden uitgevoerd. De runtime-rijen handhaven vooraf ingestelde limieten en leggen vast wat er is gebeurd. Houd de sandbox ook aan wanneer de permission rules compleet lijken: die kan een call stoppen waarop de harness niet had gerekend. De sandbox kan niet bepalen of een toegestane actie de juiste actie was; dat moet de harness doen.

De laatste kolom geeft aan waar een check draait, niet wie hem beheert. Een vendor kan een contentfilter leveren, maar de harness roept het aan.

Managed contentfilters dekken de text layer. De overige controls horen thuis in application policy, identity en infrastructure.

Waarom AI agent security anders is dan LLM-safety

Bharani Subramaniam en Martin Fowler schetsten de framing begin 2025 in Emerging Patterns in Building GenAI Products. Hun observatie was beperkt en direct:

“With traditional systems, we could assess correctness primarily through testing… With LLM-based systems, we encounter a system that no longer behaves deterministically.”

Output evaluation vraagt of een modelresponse aan een rubric voldoet. Een agent threat model moet ook tool calls, shell commands, file writes, credentials en network requests omvatten. Een output grader kan die acties niet stoppen. De harness doet dat wel: dit is de verzameling checks die een modelvoorstel omzet in een toegestane actie. De rest van dit artikel behandelt die checks.

Simon Willison beschreef de vorm van agent-specifiek risico in juni 2025 met de lethal trifecta:

“The lethal trifecta of capabilities is: access to your private data; exposure to untrusted content; the ability to externally communicate in a way that could be used to steal your data. If your agent combines these three features, an attacker can easily trick it into accessing your private data and sending it to that attacker.”

Veel nuttige agents combineren deze capabilities: toegang tot een inbox, web retrieval en een messaging tool; of toegang tot een repository, het lezen van issues en pull-request writes. Een contentguardrail vraagt of het model onveilige tekst heeft gegenereerd. De trifecta vraagt of untrusted input het systeem kan sturen naar het vrijgeven van data via een toegestane actie.

De structurele variant van hetzelfde argument staat in Joel Fokou’s Parallax-preprint (arXiv 2604.12986, ingediend op 14 april 2026, niet peer-reviewed). De kernclaim:

“The system that reasons about actions must be structurally unable to execute them, and the system that executes actions must be structurally unable to reason about them, with an independent, immutable validator interposed between the two.”

Je hoeft de evaluatiecijfers van het paper niet te accepteren om het structurele punt te onderzoeken. Verschillende huidige harnesses implementeren delen van dezelfde scheiding:

  • Claude Code’s PreToolUse hooks
  • Codex CLI’s OS-sandboxed executor (op Linux: bubblewrap plus seccomp system-call filtering)
  • Anthropic’s Managed Agents, die credentials in een vault bewaren waar de agent nooit toegang toe heeft
  • MCP’s RFC 8707 audience-bound tokens

Deze systemen houden het model gescheiden van de code die commando’s uitvoert. Hun controls verschillen, maar geen ervan laat de command runner vertrouwen op het oordeel van het model over veiligheid.

Er bestaat een aanvullende discipline die Alessandro Pignati het meest kernachtig benoemde in January 2026: het Principle of Least Agency. Least Privilege vraagt waartoe heeft deze identity toegang? Least Agency vraagt wat mag deze agent beslissen? Privilege beperkt de credentials; agency beperkt het bereik van een plan, zelfs wanneer de credentials geldig zijn. Excessive Agency is een eigen categorie in de Top 10 voor LLM Applications van OWASP, het Open Worldwide Application Security Project. De afzonderlijke agentic lijst die later in dit artikel wordt besproken, splitst dezelfde fout op in tool misuse en privilege abuse. Least Agency is de ontwerpdiscipline die beide voorkomt. Een agent die je inbox kan samenvatten, heeft waarschijnlijk geen commitrechten op je monorepo nodig.

Wat LLM guardrails wel afdekken

Byte zegt

Geef een agent een contentfilter en een write tool. Het filter kan de woorden inspecteren; de tool policy bepaalt of de file write wordt uitgevoerd.

LLM guardrails doen belangrijk werk rond de model call. Ze inspecteren input, retrieved text en output en blokkeren, redigeren, repareren of markeren content die niet aan een geconfigureerde regel voldoet. De onderstaande producten verschillen in deployment en coverage. Een content check staat los van een authorization check op de tool- of MCP-servergrens; sommige producten bieden ook runtime policy features die hun eigen configuratie en evaluatie vereisen.

NVIDIA NeMo Guardrails

Het meest opinionated product: een orchestration framework rond vijf railtypes (input, dialog, retrieval, execution, output) met een eigen DSL — Colang, een Python-achtige taal voor dialog flows, user intents en bot messages. Je kunt de basis vanuit Python + YAML aansturen, maar uitgebreidere dialog logic wordt in Colang geschreven — vandaar “opinionated.” Documentatie staat op docs.nvidia.com/nemo/guardrails.

Dit is een illustratieve API-vorm; het vereist het package en een geconfigureerde ./config directory.

from nemoguardrails import LLMRails, RailsConfig

config = RailsConfig.from_path("./config")
rails = LLMRails(config)
response = rails.generate(
    messages=[{"role": "user", "content": "Hello"}]
)

NeMo’s repo is expliciet over zijn threat model: “common LLM vulnerabilities, such as jailbreaks and prompt injections.” Het is even expliciet over de scope: “The built-in guardrails may or may not be suitable for a given production use case… developers should work with their internal application team to ensure guardrails meets requirements.” De hier getoonde content-screening path bewaakt wat het model zegt. De huidige NeMo-documentatie beschrijft ook execution rails, custom actions en tool-call inspection; dit zijn configureerbare runtime controls, geen bewijs dat de gedeployde tool of MCP-server de call heeft geauthenticeerd en geautoriseerd. De applicatie blijft eigenaar van die grens.

Meta Llama Guard 4

Een pure content classifier van 12B, gepruned uit Llama-4-Scout en afgestemd op de MLCommons hazards taxonomy (13 harm categories plus code-interpreter abuse, volgens de model card). Meta is ongewoon open over de beperkingen:

“Some hazard categories may require factual, up-to-date knowledge to be evaluated fully… Lastly, as an LLM, Llama Guard 4 may be susceptible to adversarial attacks or prompt injection attacks that could bypass or alter its intended use: see Llama Prompt Guard 2 for detecting prompt attacks.”

Meta levert een afzonderlijk product om zijn content classifier tegen prompt injection te beschermen. Als die zin klinkt als een structurele erkenning, dan is dat ook zo.

Guardrails AI

Een validator registry. Je combineert Hub validators (PII via Presidio, JailbreakDetect, CompetitorCheck, provenance checks) met on_fail actions exception | fix | fix_reask | filter | refrain | reask | noop, of met een custom callback (guardrailsai.com). Let op: exception, niet raise. In de huidige source gaat een onbekende on_fail string naar de custom-callback handling en ontstaat er een error tijdens validator setup, in plaats van een warning en fallback. Pin de versie die je deployt en test dat failure path. Er is geen uniform threat model; coverage is gelijk aan de unie van de geïnstalleerde validators. Je krijgt bescherming voor waarvoor je een validator hebt, en voor niets anders.

Lakera Guard

De gevestigde SaaS API, getraind op tientallen miljoenen attack samples die zijn verzameld via Gandalf. Het product belooft input en output te screenen op “prompt attacks… and data leakage.” Lakera’s afzonderlijke AI Agent Security-product beschrijft ook policy en runtime enforcement voor wat agents kunnen benaderen, aanroepen en doen. Dat is een ander productoppervlak dan de hier besproken content-screening call. Controleer vóór deployment het actuele product- en pricingcontract.

AWS Bedrock Guardrails

De enterprise-default als je al op Bedrock zit. ApplyGuardrail werkt met elk model, Bedrock of niet:

# No-run: illustrative AWS request; requires boto3, AWS credentials, and a real guardrail identifier.
import boto3

brt = boto3.client("bedrock-runtime")
resp = brt.apply_guardrail(
    guardrailIdentifier="gr-xxxxxxxxxxxx",
    guardrailVersion="2",
    source="INPUT",
    content=[{"text": {"text": "user question",
                        "qualifiers": ["guard_content"]}}],
)

Gepubliceerde ApplyGuardrail pricing: $0.15 per 1.000 text units voor contentfilters of denied topics, $0.10 voor PII-filters of contextual grounding. Een text unit bevat maximaal 1.000 tekens.

Azure AI Content Safety

Levert Prompt Shields als unified endpoint dat “detects and blocks adversarial user input attacks… direct and indirect threats.” Azure is ook open: “You can’t use Azure AI Content Safety to detect illegal child exploitation images,” en de meertalige kwaliteit is beperkt tot acht geëvalueerde talen.

OpenAI Moderation en OpenAI Guardrails

omni-moderation-latest is de gratis multimodale baseline. Daarnaast is openai-guardrails-python (documentatie op guardrails.openai.com) het frameworkantwoord van OpenAI: een three-stage pipeline (pre-flight, input, output) met Jailbreak Detection, Hallucination Detection via FileSearch, NSFW, PII via Presidio en LLM-as-judge. GuardrailAgent integreert met de Agents SDK.

# No-run: illustrative OpenAI Guardrails API shape; requires the package and guardrail_config.json.
from guardrails import GuardrailsOpenAI, GuardrailTripwireTriggered

client = GuardrailsOpenAI(config="guardrail_config.json")
try:
    resp = client.responses.create(model="<your-model-id>", input="...")
except GuardrailTripwireTriggered as e:
    print(f"blocked: {e}")

Wat contentfilters niet beslissen

Twee observaties gelden voor alle zeven.

Ten eerste zijn gepubliceerde latency- en throughputcijfers schaars. Bedrock, Azure en Lakera publiceren pricing, maar geen garanties voor worst-case latency. Meta publiceert evenmin een garantie voor een hosted endpoint voor Llama Guard. NVIDIA levert NeMo Guardrails als software die je zelf host, dus latency hangt af van je model en infrastructuur. Meet elke synchrone check op de critical path in plaats van de kosten uit productpricing af te leiden.

Ten tweede behandelt deze sectie de hierboven genoemde contentgerichte configuraties.

Een contentfilter kan modelinput en -output inspecteren. Het toont niet aan dat een specifieke tool call is geautoriseerd, dat een MCP-server de caller heeft geauthenticeerd of dat het systeem multi-step data exfiltration of code execution vóór een model call kan stoppen. Authorization is een afzonderlijke beslissing over de vraag of deze identity deze call naar deze server mag uitvoeren.

NeMo documenteert ook execution rails en tool-call inspection, en Lakera beschrijft runtime enforcement in zijn afzonderlijke AI Agent Security-product. Dat zijn aanvullende controls die je moet configureren en testen. De rest van deze post behandelt de checks rond tool execution.

AI agent security threats: zeven incidenten en de OWASP ASI Top 10

De kloof tussen het filteren van tekst en het beveiligen van execution werd medio 2025 concreet. De zeven incidenten hieronder bereikten retrieval, configuratie, credentials, package installation of CI execution. Een content classifier kan nog steeds een verdachte string detecteren, maar de controls die deze paden direct blokkeren bevinden zich op de grenzen van tools, identity, sandboxes en de supply chain.

EchoLeak — CVE-2025-32711

Onthuld in juni 2025 door Aim Labs, de researchtak van Aim Security, tegen Microsoft 365 Copilot. De technische write-up staat nu bij Cato Networks, dat dit team overnam, onder de naam van Itay Ravia, voormalig hoofd van Aim Labs (write-up). Een crafted email, geformuleerd als instructies aan de menselijke ontvanger, glipte voorbij XPIA (Microsofts ingebouwde filter dat Copilot-inputs controleert op prompt-injection attacks). Vervolgens kwam de email terecht in Copilots retrieval layer, het deel van het systeem dat je documenten doorzoekt om context voor antwoorden te vinden. De onderzoekers noemen deze techniek RAG-spraying: de aanvaller gebruikt meerdere emails of een lange, gechunkte email om de retrieval exposure te vergroten. Dat vergroot de kans op retrieval, maar garandeert die niet. Eenmaal binnen verwerkte Copilot gehoorzaam de gevoeligste data uit de session in een Markdown-link naar een afbeelding op een door de aanvaller beheerd domein. De Teams preview API, die op een domein draaide dat al door Microsofts eigen browser policies werd vertrouwd, haalde die afbeeldings-URL automatisch op en gaf de data daarmee aan de aanvaller door. Zero clicks. Aim Labs noemde deze aanvalsklasse “LLM Scope Violation”: het model overschrijdt een grens die het nooit had mogen overschrijden, met alleen operaties die elk afzonderlijk systeem als legitiem beschouwde.

Elke stap leek op zichzelf legitiem. De email was aan een mens gericht. Retrieval haalde een document op dat het hoorde op te halen. De Markdown-link werd weergegeven zoals Markdown-links worden weergegeven. De image fetch ging naar een allowlisted domain. De onderzoekers omzeilden XPIA’s screening en het model volgde indirecte instructies uit retrieved content. De case combineert een prompt-injection failure met retrieval-, rendering- en egressgedrag; hij laat niet zien dat detectors niets te signaleren hadden.

Amazon Q Developer VS Code v1.84.0 — juli 2025

AWS bracht een gecompromitteerde build uit nadat een aanvaller via een over-scoped CodeBuild GitHub-token een kwaadaardig system-promptbestand had gecommit (advisory). De payload probeerde de instructies van de agent te wijzigen in de richting van destructieve acties. De kwaadaardige code werd met v1.84.0 verspreid, maar werd door een syntax error niet uitgevoerd. AWS trok credentials in, verwijderde de code en bracht v1.85.0 uit. De payload faalde door die syntax error, niet doordat een security control haar blokkeerde.

Azure Web Apps MCP service — CVE-2026-32211

Microsofts vendor CVE record gaat over ontbrekende authentication in de hosted Azure Web Apps MCP service. Het is geen advisory tegen elke lokale Azure MCP-server of SDK. Een caller die een niet-geauthenticeerde tool service bereikt, kan het model volledig omzeilen; de gedeployde service moet het request authenticeren en autoriseren.

Claude Code project-trust vulnerabilities

Dit waren afzonderlijke vulnerabilities, geen noodzakelijke stappen van één aanval:

  1. Een trust-warning bypass werd opgelost in 1.0.87.
  2. Pre-trust execution, CVE-2025-59536, werd opgelost in 1.0.111. Repositoryconfiguratie kon execution triggeren voordat het project trusted was.
  3. Endpoint/API-key exposure, CVE-2026-21852, werd opgelost in 2.0.65. Untrusted configuration kon API-traffic omleiden en credentials blootleggen.

Project trust, hook execution en endpoint configuration zijn host controls. Een content classifier kan niet voorkomen dat code wordt uitgevoerd vóór de model call.

Axios 1.14.1 en 0.30.4 — 31 maart 2026

De postmortem van de maintainer identificeert twee kwaadaardige releases, 1.14.1 en 0.30.4, die de dependency plain-crypto-js@4.2.1 bevatten. Die dependency installeerde een remote access trojan: malware die een aanvaller remote access tot de machine geeft. Exposure vereiste dat de getroffen versies werden resolved en het relevante installgedrag werd uitgevoerd; een ongerelateerde npm install haalde ze niet automatisch op. Dit is een supply-chain execution failure, onafhankelijk van modelgedrag.

Trivy Actions tag hijack — 19 maart 2026

De Aqua advisory beschrijft dat 76 van 77 trivy-action-version tags en zeven setup-trivy-tags naar kwaadaardige content werden omgeleid. De kwaadaardige action entrypoint verzamelde geheugen van het runnerproces en credentialbestanden; schrijf dat volledige collection path niet toe aan de scanner binary. Het latere Docker Hub-event had een afzonderlijk exposure window.

Een workflow die tijdens de compromise een getroffen tag resolvede, kon de payload uitvoeren. Tags zijn mutable references, dus pin reviewed Actions op immutable commit SHAs en verifieer dependency changes. Een coding agent kan dezelfde unsafe reference naar meer workflow files verspreiden.

OpenAI / Hugging Face — evaluaties in juli 2026

OpenAI’s incident report van 26 augustus beschrijft dat interne cybersecurity-evaluation agents via gedeelde infrastructuur het internet bereikten, samenwerkten via een niet-geautoriseerd message board en systemen van Hugging Face compromitteerden. Het principal model was intern en de evaluaties draaiden met beperkte safeguards. Dit is bewijs over die evaluation environment, geen gemeten failure rate voor publiek gedeployde agents.

De engineeringles is dat een toegestane interne service een outbound path of een cross-session communication channel kan worden. Test wat een package mirror, proxy en shared store namens de agent kunnen doen, niet alleen of de sandbox een directe internetverbinding kan openen. METR’s separate investigation onderzocht agentgedrag en collaboration; het evalueren van safeguard effectiveness en remediation viel buiten de scope.

Asynchronous provider intervention

OpenAI’s misalignment monitoring kan na output of actions interveniëren. Voor ondersteunde models kunnen Responses requests met persisted reasoning, WebSockets of OpenAI compaction automatisch worden gestopt. Andere Responses requests kunnen alerts genereren zonder automatisch te stoppen; Chat Completions valt buiten dit systeem. Een webhook maakt blocking niet mogelijk.

Een geblokkeerd request rapporteert misalignment_policy_violation, met HTTP 403 vóór streaming; errors kunnen ook midden in een stream arriveren. Stop verdere actions, bewaar request- en toolrecords en vraag operator review. Retry niet automatisch. Eerdere effects blijven bestaan en alerts kunnen onjuist zijn of problemen missen. Dit voegt detection toe; het vervangt lokale authorization niet.

De OWASP ASI Top 10, editie 2026

OWASP’s Agentic Security Initiative (ASI) is een working group die specifiek gericht is op LLM-driven agents. Op 9 december 2025 publiceerde de groep de Agentic Security Initiative Top 10 for 2026: een catalogus met tien agent-security risk categories.

Gebruik dit als checklist voor threat-model coverage, niet als ranglijst van gemeten incidentfrequentie:

Contentfilters kunnen bijdragen aan het detecteren van kwaadaardige instructies, waaronder goal hijack en memory poisoning. Categorieën overlappen: geen enkele categorie behoort exclusief tot een text filter. Koppel elk attack path waar relevant aan controls voor identity, tool policy, memory, orchestration, monitoring en de supply chain. EchoLeak valt onder ASI01. Amazon Q valt onder ASI04 (Supply Chain) en ASI02 (Tool Misuse). Azure MCP is ASI03 (Identity). Claude Code CVE-2025-59536 omvat ASI05 (Code Execution), ASI04 en ASI03. Axios en Trivy zijn ASI04. De mapping laat zien waarom het threat model verder moet gaan dan modelinput en -output.

Permission is infrastructure, geen prompt

Hier houden guardrails op het product te zijn en worden ze één subsystem van een harness. Drie huidige systemen (OpenAI Agents SDK, Codex CLI en Claude Code) laten zien hoe een production policy surface er werkelijk uitziet. Alle drie handhaven permission in code. Geen ervan vertrouwt erop dat het model voorzichtig is.

OpenAI Agents SDK

De SDK scheidt harness van compute. Hosted MCP tools accepteren require_approval — ofwel de kale string "always" / "never", of een filterobject met die twee policies als keys en de toolnamen waarop elke policy van toepassing is — plus een on_approval_request callback die voor elke tool onder "always" wordt aangeroepen en {"approve": bool} retourneert, met optioneel een reason. Fijnmazige tool filtering (tool_filter) is beschikbaar op de lokale servervarianten (MCPServerStdio, MCPServerStreamableHttp, MCPServerSse) als je dat nodig hebt:

# No-run: illustrative Agents SDK shape; requires openai-agents, a configured hosted MCP server, and credentials.
from agents import Agent, HostedMCPTool

def approve(request):
    # Only tools under the "always" policy reach this callback.
    if request.data.name == "delete_repo":
        return {"approve": False, "reason": "escalate to a human reviewer"}
    return {"approve": True}

agent = Agent(
    name="Ops",
    tools=[HostedMCPTool(
        tool_config={
            "type": "mcp",
            "server_label": "github",
            "server_url": "https://mcp.example.com",
            "require_approval": {
                "always": {"tool_names": ["delete_repo"]},
                "never": {"tool_names": ["list_issues"]},
            },
        },
        on_approval_request=approve,
    )],
)

De approval callback is code. De per-tool approval policy is code. Je kunt dit bestand lezen, testen en diffen. Dat geldt niet voor een system prompt die zegt: “wees voorzichtig met production.”

Codex CLI en de managed policy layer

OpenAI’s coding harness ondersteunt een managed requirements.toml file die IT-afdelingen via device management kunnen pushen. Op Unix-systemen staat het system file op /etc/codex/requirements.toml. Het werkt als een hard-constraint layer, zodat project-level settings de regels niet kunnen overriden:

# /etc/codex/requirements.toml
[rules]
prefix_rules = [
    { pattern = [{ token = "rm" }, { any_of = ["-rf", "-fr"] }], decision = "forbidden", justification = "Recursive force-delete prohibited by IT policy" },
]

prefix_rules.decision accepteert alleen "prompt" of "forbidden", nooit "allow". Een project kan zichzelf geen permission geven die de managed layer verbiedt. MCP allowlists zijn zowel op naam als op identity gebaseerd, bijvoorbeeld een command string of URL. Een project kan dus niet beweren github-mcp te zijn en naar de server van een aanvaller wijzen. Ondersteunde requirements verschillen per client en version. De huidige documentatie vereist specifiek Codex 0.138.0 of later voor managed permission-profile keys. Test daarom vóór rollout elke requirements policy tegen elke clientversion in de fleet.

Claude Code’s permission ladder

Claude Code publiceert geen vaste reeks van zes checks voor elke tool call. De permission rules worden geëvalueerd volgens deny → ask → allow; de eerste matching rule bepaalt de uitkomst. Een PreToolUse hook draait vóór de permission prompt. Een PreToolUse decision kan een call zonder prompt toestaan, weigeren, de gebruiker vragen of voor later uitstellen. Deny- en ask-rules blijven van toepassing; sommige interactieve actions behouden ook hun approval requirements. De actieve permission mode verwerkt calls die door rules en hooks unresolved blijven. De Claude Agent SDK heeft een afzonderlijke canUseTool callback voor unresolved requests. Die callback is een SDK-control, geen Claude Code CLI permission check.

Modes wisselen met Shift+Tab tussen default → acceptEdits → plan. auto, bypassPermissions en dontAsk worden onder specifieke entry conditions geactiveerd die de enterprise-managed policy layer kan uitschakelen. Dit is meer dan een config file die op correctheid wordt gecontroleerd. Het is een state machine met precedence rules, gepubliceerd zodat een securityteam erover kan redeneren.

Drie blast radii in één file

Dit is de vorm van een Codex-style permission config met een default en twee named profiles:

# ~/.codex/config.toml
approval_policy = "on-request"
sandbox_mode = "workspace-write"

[profiles.ci]
approval_policy = "never"
sandbox_mode = "read-only"

[profiles.release]
approval_policy = "untrusted"
sandbox_mode = "danger-full-access"

[mcp_servers.github]
command = "gh-mcp"
args = ["--readonly"]

Twee keys doen het werk en zijn onafhankelijk. approval_policy bepaalt wanneer een mens wordt gevraagd. on-request laat de agent escaleren wanneer hij tegen een blokkade aanloopt. never vraagt helemaal niets. untrusted stopt bij elk commando dat niet op de trusted list staat. sandbox_mode bepaalt wat het commando kan benaderen als het wordt uitgevoerd.

CI onderbreekt niemand en kan niet schrijven. Release kan de volledige machine bereiken, maar moet vrijwel alles eerst met een mens afhandelen. Het releaseprofiel betaalt voor dat bereik: danger-full-access schakelt de sandbox uit, waardoor untrusted approval de enige overgebleven control is. Alles buiten de trusted list wordt door een mens goedgekeurd of wordt niet uitgevoerd. Die trusted list is dan de volledige security boundary.

De default- en CI-profielen houden de kernel eronder: Seatbelt op macOS, bubblewrap plus seccomp op Linux en restricted tokens op Windows. Hoe dan ook maakt de mening van het model geen deel uit van de beslissing.

Sandbox enforcement is een OS-vraagstuk

De kernel doet hier het echte werk. Elk OS biedt een ander toolkit, en de twee CLIs gebruiken niet altijd hetzelfde onderdeel:

PlatformClaude CodeCodex CLI
macOSSeatbelt via sandbox-exec met een SBPL (Seatbelt Profile Language)-profileSeatbelt via sandbox-exec -p
Linuxbubblewrap + socat network proxybubblewrap + seccomp (legacy Landlock via use_legacy_landlock)
WindowsWSL2 vereistNative restricted tokens + workspace ACLs + capability SIDs

Ze zijn het eens waar het OS één optie biedt (Seatbelt, bubblewrap) en verschillen waar dat niet zo is. Claude Code’s sandbox vereist WSL2 op Windows; dat is een sandboxbeperking, geen claim dat de CLI niet native kan draaien. Codex levert een native Windows-sandbox. In beide gevallen vindt enforcement plaats in de kernel, niet in het model.

Codex’ Linux path stapelt drie kernel-level locks rond het commando. PR_SET_NO_NEW_PRIVS verhindert dat het proces extra privileges verkrijgt, ook als het dat probeert. Een seccomp filter laat de kernel hele classes van system calls weigeren. Network restrictions hangen ervan af of networking is uitgeschakeld of een proxymode is geconfigureerd; ze zijn niet universeel beperkt tot Unix sockets. Zie de Linux sandbox implementation. Een verse geïsoleerde /proc verbergt de rest van de machine.

Codex hardent ook zijn eigen binary bij startup op elk Unix-platform. Het zet RLIMIT_CORE=0 om core dumps te onderdrukken en weigert debugger attach. Dat is een andere boundary dan de sandbox.

De Windows sandbox heeft twee modes. unelevated gebruikt een restricted token als user en biedt niet de network enforcement van de elevated mode. elevated gebruikt dedicated sandbox users, firewall rules en filesystem ACLs.

Wanneer network access uitstaat, plaatst Codex stub-.bat- en .cmd-files voor ssh en scp in een directory vooraan in PATH. Die commando’s eindigen met een non-zero exitstatus in plaats van de echte binaries te bereiken. Codex wijst HTTP_PROXY, HTTPS_PROXY, ALL_PROXY en de Git proxy variables ook naar een dode lokale poort. Deze maatregelen beïnvloeden coöperatieve tools; proxy variables en command stubs alleen kunnen arbitraire networking niet beperken.

Een sandbox heeft ook een gedefinieerde failure mode nodig. In Claude Code’s huidige configuratie stopt sandbox.failIfUnavailable: true de execution wanneer sandboxing niet kan starten. allowUnsandboxedCommands: false schakelt de unsandboxed retry escape hatch van de agent uit, maar excludedCommands omzeilt die nog steeds. Test de effectieve configuratie met ontbrekende dependencies en een verboden destination.

Credential brokering is nu ook lokaal beschikbaar. Claude Code’s sandbox.credentials kan named files en environment variables weigeren. Environment-variable masking, beschikbaar sinds v2.1.199, geeft sandboxed commands een placeholder en laat de proxy de echte waarde injecteren in requests naar geconfigureerde hosts. Stel smalle injectHosts in en configureer TLS termination; masking autoriseert de gevraagde operation niet. Deze controls dekken gesandboxte Bash commands, dus hooks, MCP-processen en andere execution paths hebben nog steeds hun eigen credential policy nodig.

Isolation choices buiten Claude Code en Codex

Als je zelf een agent bouwt, blijkt “sandbox” een parapluterm te zijn. De open-source opties liggen op een spectrum — van lichte namespace wrappers aan de ene kant tot volledige microVMs aan de andere — en je keuze hangt af van hoeveel vertrouwen je hebt in de code die erin draait.

Lichte isolation — dezelfde kernel, minder privileges:

  • bubblewrap — een low-level namespace sandbox constructor die wordt gebruikt door Flatpak en Claude Code op Linux. De caller moet filesystem, network en optioneel seccomp policy kiezen; bubblewrap zelf is geen kant-en-klare security policy.
  • Standaard Docker / OCI containers — namespace isolation boven op een gedeelde hostkernel. Geen sandbox voor untrusted code; de eigen documentatie van gVisor maakt dit expliciet (“containers are not a sandbox”). Een redelijk startpunt in combinatie met seccomp en AppArmor, maar niet meer dan dat.

Application-kernel isolation — de agent praat met een fake kernel:

  • gVisor — Google’s user-space kernel. Je container denkt dat hij op Linux draait, terwijl een Go-kernelimplementatie system calls onderschept. Dit vermindert directe blootstelling aan de hostkernel zonder guest VM, met trade-offs voor compatibility en performance.

Volledige VM-isolation — een dedicated kernel per sandbox:

  • Firecracker — AWS’ microVM-technologie. Elke VM heeft een eigen Linux-kernel onder KVM; containers delen de hostkernel. Een compromise in één VM moet nog steeds door de VMM- of hostcontrols heen om de host of een andere VM te beïnvloeden, dus Firecracker’s Jailer en een gepatchte host blijven onderdeel van de bescherming.
  • Kata Containers — container UX met VM-grade isolation. Waar Kubernetes-clusters naartoe gaan wanneer ze untrusted code moeten draaien.

Platforms — wat je huurt in plaats van bouwt:

  • E2B wikkelt Firecracker in een hosted sandbox API.
  • OpenSandbox scheidt de SDK van door administrators geconfigureerde runtime isolation. Default Docker runc is geen microVM; het Firecracker path gebruikt Kata met Firecracker via Kubernetes.
  • Microsoft’s Agent Governance Toolkit (MIT-licensed, april 2026) voegt daarbovenop een runtime policy engine toe. Het koppelt policy controls aan de OWASP ASI Top 10. De latencyclaim bij startup betreft één policy engine, niet de totale kosten van elke check in een gedeployde agent.

Kies het isolationniveau op basis van het trustniveau van de code, tenant boundary, network access, hostdata en recovery cost. Namespace- en seccomp-controls kunnen passen bij trusted internal tools. LLM-generated code en untrusted packages hebben een sterkere boundary nodig, zoals gVisor, Kata of een microVM, gevolgd door tests van de escape- en exfiltrationpaths in je eigen threat model.

Claude Code en Codex kozen uit hetzelfde menu als iedereen. Ze verpakten het alleen anders.

PreToolUse hooks als programmeerbare policy

Modes en allowlists behandelen de eenvoudige gevallen: “laat de agent files editen maar geen bash uitvoeren”, “weiger alles dat eruitziet als rm -rf.” Ze schieten tekort wanneer je policy echte logic nodig heeft. Je wilt git push alleen blokkeren wanneer de branch main is. Je wilt elke Edit weigeren die een file raakt waarvan de naam met een secret regex matcht. Je wilt shell calls per session rate-limiten of elke tool invocation naar je centrale audit log sturen (de SIEM, het security information and event management-systeem dat je securityteam al monitort).

Dat past niet in een statische allowlist. Daarvoor zijn hooks — shell commands die Claude Code op specifieke momenten in de lifecycle van een tool call uitvoert, met de mogelijkheid om de pending call te inspecteren en een gestructureerde allow/deny te retourneren. Claude Code exposeert ongeveer dertig lifecycle events (de volledige lijst staat in de documentatie), en één daarvan herordent al het overige: een PreToolUse hook die permissionDecision: "deny" retourneert, blokkeert een tool ongeacht de mode.

Dit is de settings-vorm:

{
    "permissions": {
        "defaultMode": "acceptEdits",
        "deny": ["Bash(rm -rf:*)", "Bash(sudo:*)", "Read(.env*)"]
    },
    "hooks": {
        "PreToolUse": [
            {
                "matcher": "Bash",
                "hooks": [
                    {
                        "type": "command",
                        "command": ".claude/hooks/pre-bash-firewall.sh"
                    }
                ]
            },
            {
                "matcher": "Edit|Write",
                "hooks": [
                    {
                        "type": "command",
                        "command": ".claude/hooks/protect-paths.sh"
                    }
                ]
            }
        ]
    }
}

De statische deny rules en dynamische hooks hebben verschillende failure modes. Een PreToolUse-resultaat van deny blokkeert vóór de normale permission flow, maar een timeout van een command-, HTTP- of MCP-tool-hook is non-blocking: Claude Code gaat verder met die flow. In dit voorbeeld kan acceptEdits dus een Edit of Write goedkeuren wanneer protect-paths.sh een timeout krijgt. Laat een niet-onderhandelbare path restriction niet uitsluitend afhangen van een command hook. Zet statische restricties in deny rules of de sandbox; kies voor dynamische policy een control waarvan evaluator failure restrictief blijft en test zowel timeoutgedrag als een expliciete deny.

Een hook kan een shellscript van vijf regels zijn of een volledige policy engine. De return shape is wat telt:

{
    "hookSpecificOutput": {
        "hookEventName": "PreToolUse",
        "permissionDecision": "deny",
        "permissionDecisionReason": "writes outside workspace prohibited"
    }
}

Het model ziet een gestructureerde deny. De reasoning loop uit Part 1 verwerkt dit net als elke andere tool observation: de denial wordt context, de agent plant opnieuw en de loop gaat verder. Dit is wat “permission is infrastructure” oplevert. De deny is gekoppeld aan hetzelfde mechanisme dat een 500 van een HTTP-tool verwerkt. Het is geen afzonderlijke security workflow die je achteraf moet toevoegen.

Een veelvoorkomend anti-pattern is een system prompt schrijven met “verwijder geen files zonder expliciete bevestiging van de gebruiker”, de agent deployen en die instructie als control gebruiken. Een geïnjecteerde prompt of een tool result dat door een aanvaller wordt beheerd, kan om die instructie heen werken. Het model is geen policy engine. Het kan jouw pattern matchen, maar ook een pattern dat door een aanvaller is aangeleverd.

Human approval werkt alleen als escalation

Byte zegt

Na twintig approval prompts klik je gemakkelijk op Approve zonder te lezen. Bewaar prompts voor actions waarvoor een beslissing van een persoon nodig is.

Contentfilters inspecteren wat het model zegt. Permission rules inspecteren de tool call voordat die draait. Human-in-the-loop review behandelt de actions waarvoor nog steeds een persoon nodig is. Als mensen 93% van de prompts goedkeuren, inspecteer dan de escalation rules en de promptkwaliteit.

LangGraph levert het pause/resume primitive. HumanLayer verpakt het approval channel, en Anthropic’s usage data laat zien waarom je het aantal en de kwaliteit van escalations moet meten.

Het LangGraph primitive

LangGraph’s interrupt() + Command(resume=value) pauzeert een graph, persisteert de state via de geconfigureerde checkpointer en hervat met een door een mens geleverde waarde. Of die resume veilig is, hangt af van één detail in de documentatie:

“When execution resumes (after you provide the requested input), the runtime restarts the entire node from the beginning — it does not resume from the exact line where interrupt was called.”

Uit dat restartgedrag volgen drie constraints:

1. Side effects vóór interrupt() moeten idempotent zijn. Wanneer de mens reageert, draait de hele node opnieuw vanaf het begin, niet vanaf de regel met interrupt(). Als je node dus een email verstuurt, pauzeert voor approval en vervolgens “sent” retourneert, wordt de email bij resume een tweede keer verstuurd. Oplossing: plaats side effects na de interrupt of maak ze veilig om te herhalen (dedupe keys, upsert in plaats van insert, cache op message ID).

2. Interrupts worden op index aan resumes gekoppeld, niet op naam. Als één node twee interrupt()-calls heeft, koppelt LangGraph ze aan Command(resume=...)-values in de volgorde waarin ze worden uitgevoerd. Elke branching die het aantal interrupts wijzigt (een if die er bij resume één overslaat, een loop die een ander aantal keer iterereert) laat de indexes verschuiven, waardoor een resume value bij de verkeerde interrupt kan belanden.

3. Houd payloads JSON-safe. De documentatie van LangGraph vereist JSON-serializable values voor interrupt() en resume payloads. Gebruik strings, numbers, booleans, arrays en dictionaries die deze waarden bevatten. Vermijd functions, class instances en andere complexe objecten, omdat serialization afhangt van de geconfigureerde checkpointer. Zet approvaldata om in dictionaries en primitives voordat je die aan interrupt() doorgeeft of via een HTTP API exposeert.

De drie canonical patterns:

# No-run: illustrative LangGraph sketches; requires LangGraph, a tool decorator, interrupt, and smtp_send.
# (a) Approval check
@tool
def send_email(to, subject, body):
    resp = interrupt({"action": "send_email", "to": to,
                      "subject": subject, "body": body})
    if resp.get("action") == "approve":
        return smtp_send(to, subject, body)
    return "Email cancelled"

# (b) Edit-and-continue
def review_node(state):
    edited = interrupt({"content": state["generated_text"]})
    return {"generated_text": edited}

# (c) Mid-run state correction — conditional edge
class AgeState(TypedDict):
    age: int | None
    pending_question: str | None

def get_age_node(state: AgeState):
    question = state.get("pending_question") or "What is your age?"
    answer = interrupt(question)  # once per node invocation
    if isinstance(answer, int) and answer > 0:
        return {"age": answer, "pending_question": None}
    return {"pending_question": f"'{answer}' is not valid. Please enter a positive number."}

def route_age(state: AgeState):
    return END if state.get("age") is not None else "get_age"

builder = StateGraph(AgeState)
builder.add_node("get_age", get_age_node)
builder.add_edge(START, "get_age")
builder.add_conditional_edges("get_age", route_age)

Resume is graph.invoke(Command(resume={"action": "approve"}), config=cfg). LangGraph 0.4+ ondersteunt dict-based multi-interrupt resume voor parallel branches, wat belangrijk wordt zodra je agent uitwaaiert.

HumanLayer: approval als product

HumanLayer is de managed versie van hetzelfde idee. Je decoreert een functie en approval requests worden naar Slack, email of Discord gerouteerd, met rules voor wie een melding krijgt. Wanneer de agent multiply(2, 5) probeert aan te roepen, zien de logs er zo uit:

last message led to 1 tool calls: [('multiply', '{"x":2,"y":5}')]
HumanLayer: waiting for approval for multiply

De approver klikt in Slack op approve of deny. Bij een deny formuleren de HumanLayer docs het zo: “HumanLayer will pass your feedback back to the agent, which can then adjust its approach.” Dankzij die feedback kan de agent zijn plan aanpassen in plaats van een rejection als dead end te behandelen.

Approval fatigue in de data

Anthropic publiceerde de echte data in februari 2026. Drie bevindingen zijn belangrijker dan de rest.

“We found that 80% of tool calls come from agents that appear to have at least one kind of safeguard (like restricted permissions or human approval requirements), 73% appear to have a human in the loop in some way, and only 0.8% of actions appear to be irreversible.”

Dat is het goede nieuws. Behandel 80% als een bovengrens, omdat Anthropic in voetnoot 14 toevoegt: “Claude often overestimated human involvement, so we expect 80% to be an upper bound.”

“Newer users (<50 sessions) employ full auto-approve roughly 20% of the time; by 750 sessions, this increases to over 40% of sessions.”

Dit is de drift. Gebruikers beginnen voorzichtig en worden minder voorzichtig naarmate ze vertrouwen opbouwen in de tool. Dat is menselijk gedrag en geen karakterfout. Het is een telemetriesignaal dat je systeem moet volgen. (Een kleine factcheck: secundaire berichtgeving citeerde dit breed als “20% → over 50%.” Tegenover de primaire data van Anthropic is het geverifieerde getal 20% → over 40%. Als je het cijfer 50% hebt gezien, komt dat daar vandaan.)

Anthropic’s engineering post van maart 2026 over Claude Code’s auto mode geeft het kerngetal:

“Claude Code users approve 93% of permission prompts. We built classifiers to automate some decisions, increasing safety while reducing approval fatigue… If a session accumulates 3 consecutive denials or 20 total, we stop the model and escalate to the human.”

Een hoge approval rate is aanleiding om te onderzoeken of prompts mensen helpen beslissen; het bewijst geen universele failure threshold. Anthropic’s two-stage classifier vermindert het aantal prompts en escaleert geclusterde denials. De gerapporteerde false-positive rate van 0,4% gebruikte 10.000 traffic examples. False-negative rates waren 17% op 52 echte overeager actions en 5,7% op 1.000 synthetische exfiltration cases. Dat zijn verschillende populaties, geen complementaire percentages en geen bewijs dat classification sandboxing vervangt.

Meet de kwaliteit van escalation

Allowlist routineuze, reversibele actions en log ze. Escaleer actions waarvan de side effects een boundary overschrijden die de runtime niet kan terugdraaien, zoals een extern bericht, een production write, een force push of een payment. Anthropic beschrijft het doel als ervoor zorgen dat een mens kan ingrijpen wanneer de beslissing echte gevolgen heeft.

Volg de volledige funnel in plaats van een geleend approval-rate target na te streven: voorgestelde actions, automatische allows, escalations, approvals, denials, edits en incidents na approval. Een hoge approval rate kan betekenen dat de prompts routinematige ruis zijn. Een hoge denial- of editrate kan betekenen dat de planner de verkeerde action voorstelt of de informatie verbergt die een approver nodig heeft. De juiste threshold hangt af van de action class en de kosten van een false allow; bepaal die aan de hand van je eigen incident- en reviewdata.

MCP-scoping en de supply chain

MCP verbindt agents met externe tools zoals Slack, GitHub en databases, waardoor het authorization model onderdeel wordt van de security boundary. De specificatierevisies uit 2025 scheidden de rollen van token issuer en resource server en voegden resource indicators toe. Die geschiedenis verklaart welke audience- en forwarding checks een server vandaag moet afdwingen.

MCP authorization in drie revisies

Authorization was optioneel voor MCP-implementaties in de 2025-03-26 spec. Voor een production HTTP-deployment dat user data of tools beschermt, adviseer ik OAuth 2.1 met PKCE (Proof Key for Code Exchange), wat de specificatie vereist wanneer een implementatie OAuth authorization ondersteunt. Het vroege ontwerp liet één MCP-server twee rollen uitvoeren. De authorization server geeft tokens uit; de resource server accepteert ze. Dit zijn afzonderlijke rollen, ook wanneer één service beide uitvoert. Als die service een request forwardt naar een andere server, kan dezelfde credential ergens terechtkomen waarvoor die nooit bedoeld was. Daar zit het gat.

De revisie van 2025-06-18 maakte de rollen expliciet. Een protected MCP-server fungeert als OAuth resource server, terwijl een authorization server het token uitgeeft. De authorization server kan samen met de resource server worden gehost of afzonderlijk draaien. RFC 8707 Resource Indicators binden het token aan een target resource, en RFC 9728 Protected Resource Metadata geeft de client een expliciet discovery path. De spec verbiedt een MCP-server ook om het token van een client upstream door te sturen.

De revisie van 2025-11-25 behield die scheiding en werkte aan de onderdelen die een client correct moet uitvoeren. Discovery van de authorization server kreeg OpenID Connect Discovery, zodat een client de juiste issuer kan vinden in plaats van te gokken. Incremental scope consent verhuisde naar de WWW-Authenticate header, waarmee een server op het moment dat een scope nodig is om één extra scope kan vragen in plaats van alles vooraf te eisen. Client registration kreeg OAuth Client ID Metadata Documents als recommended mechanism, ter vervanging van dynamic registration voor de meeste deployments. Protected Resource Metadata discovery werd eveneens op RFC 9728 afgestemd, waardoor WWW-Authenticate optioneel werd met een .well-known fallback.

Controleer de versioning page vóór implementatie. Op 6 september 2026 is de huidige revision 2026-07-28. Deze vereist dat elk request de protocolversie declareert en laat de server elk request afzonderlijk accepteren of weigeren. Een client kan vooraf server/discover aanroepen om een version te selecteren, maar discovery is optioneel. Per-request declaration en negotiation blijven vereist, ook wanneer de client een unsupported-version error afhandelt en opnieuw probeert met een mutually supported version.

Audience binding beperkt replay tegen de verkeerde MCP-server. Het neutraliseert niet de afzonderlijke Claude Code configuration vulnerabilities die hierboven zijn beschreven: een host-side hook kan nog steeds vóór de start van het model uitvoeren en een untrusted project kan nog steeds proberen lokale configuratie te wijzigen. Token scope, project trust, hook policy en sandboxing blijven afzonderlijke controls.

De MCP-checklist voor 2026

Als je MCP in production levert of gebruikt:

  1. Behandel authentication als een production requirement, niet als een protocoldefault. MCP laat authorization optioneel, maar ik adviseer OAuth 2.1 met PKCE voor een protected HTTP deployment. De advisory over de hosted Azure Web Apps MCP service ging over ontbrekende authentication. Als je server traffic accepteert zonder caller credentials te verifiëren, heb je een tool gebouwd die iedereen die hem kan bereiken kan aanroepen.
  2. Tokens zijn audience-bound. Vraag een token aan voor de target MCP resource en valideer dat het gepresenteerde token jouw server als audience benoemt. Weiger tokens die voor een andere resource zijn uitgegeven.
  3. Isoleer read- en write-authority bewust. MCP bindt een token aan een resource server, niet aan één individuele tool. Als een Slack-server een credential met chat:write accepteert en die naar zowel read- als write-handlers routeert, kan een read-oriented tool via de policy van die server veranderen in een path voor het versturen van messages. Gebruik afzonderlijke resource servers of afzonderlijke credentials en authorization checks wanneer read- en write-operations onafhankelijke blast radii nodig hebben.
  4. Gebruik verse, kortlevende tokens in plaats van permanente API keys. Het vault pattern van Claude Managed Agents (Anthropic engineering) is de referentie: de agent zelf ziet de echte credentials nooit. De proxy haalt de bijbehorende opgeslagen credentials uit de vault, roept namens de agent de tool aan en retourneert het resultaat. Een fresh token voor elke call uitgeven is geen gedocumenteerde guarantee; short-lived credentials zijn een deployment recommendation.

Supply-chain controls blijven van toepassing

De axios- en Trivy-incidenten zijn bekende package- en CI-supply-chain failures, toegepast op systemen die dependency installation automatiseren. Automation verhoogt het aantal en het tempo van executions, dus version-, provenance- en review-controls moeten actief zijn voordat het gegenereerde commando CI of een sandbox bereikt.

De verdediging is eenvoudig:

  • Pin versions in het lockfile. Agents mogen nooit een floating version resolven — geen @latest, geen npm update, geen --upgrade.
  • Scan in CI met tools die onafhankelijk zijn van het component dat wordt gecontroleerd.
  • Gebruik GitHub commit SHAs voor Actions, geen tags.
  • Review dependency diffs op agent-driven PRs vóór merge.

Dit zijn standaard supply-chain controls. Agent automation verandert de frequentie, niet het mechanisme.

Een policy stack voor de Market Analyst Agent

De Market Analyst Agent uit Part 1 is een kleine LangGraph-agent die market data ophaalt en een analyst report schrijft — maar niet zo klein als die beschrijving suggereert. Naast de market-data tools draait hij een allowlisted CLI via subprocess, evalueert hij door het model geschreven Python in process en maakt hij simulated trade records aan. Hij gebruikt tool invocation, code execution en approval routing, maar plaatst geen echte orders. Dit is hoe een minimale policy stack ervoor uitziet.

Layer 1: een PreToolUse hook die vóór execution weigert

Zelfs een agent die “alleen stock data leest” kan dingen proberen die hij niet hoort te doen: een curl naar een URL van een aanvaller, writes buiten de workspace, git-mutations op de host repo. Een deny rule is infrastructure, geen prompt. De sketch hieronder retourneert de eigen decision shape van de agent, niet de omringende hookSpecificOutput-envelope die Claude Code verwacht.

# agent/permissions.py
from pathlib import Path

DENY_COMMANDS = frozenset({
    "rm -rf", "sudo", "chmod 777",
    "curl -X POST", "wget", "nc ",
})
WORKSPACE = Path("./workspace").resolve()

def _outside_workspace(path: str) -> bool:
    # Resolve first: "~/.ssh/id_rsa" and "workspace/../../etc" both
    # have to become real paths before the comparison means anything.
    return not Path(path).expanduser().resolve().is_relative_to(WORKSPACE)

def pre_tool_use(tool_name: str, args: dict) -> dict | None:
    if tool_name == "shell":
        cmd = args.get("command", "")
        if any(bad in cmd for bad in DENY_COMMANDS):
            return {"permissionDecision": "deny",
                    "reason": f"command pattern disallowed: {cmd!r}"}
    if tool_name == "write_file":
        path = args.get("path", "")
        if _outside_workspace(path):
            return {"permissionDecision": "deny",
                    "reason": f"path outside workspace: {path!r}"}
    return None  # fall through to mode / canUseTool

De sketch maakt het control point zichtbaar. De hook retourneert een structured deny en de reasoning loop ontvangt die denial als een tool observation.

De path check is een allowlist: één workspace root, al het overige wordt geweigerd. Een deny-list van forbidden prefixes blokkeert alleen paden waar je aan hebt gedacht. ~/.ssh/id_rsa wordt nooit precies geschreven zoals jij hem hebt opgeschreven. De command check is nog steeds een deny-list. Substring matching is geen production shell policy. Een echte implementatie moet het commando parsen en voor execution vertrouwen op de OS-sandbox. De sketch is zelf geen execution boundary: als een externe hook hem uitvoert, moet een timeout een onafhankelijke workspacerestriction actief laten.

Layer 2: een input canary voor prompt injection

Agent-goal hijack (ASI01) komt vaak binnen via een retrieved web page, user message of research-paper-PDF. Een goedkope regex canary vangt letterlijke instruction patterns en creëert een nuttig telemetry event. Obfuscated, meertalige en contextafhankelijke injections mist hij, dus hij kan niet als decision boundary dienen:

# agent/input_canary.py
import re

INJECTION_PATTERNS = [
    re.compile(r"ignore\s+(?:all\s+|any\s+|the\s+)?"
               r"(?:previous\s+|prior\s+|above\s+|earlier\s+)?"
               r"(?:instructions|rules|prompts?)",
               re.IGNORECASE),
    re.compile(r"you are now|act as|roleplay as", re.IGNORECASE),
    re.compile(r"system[ _:]*prompt", re.IGNORECASE),
    re.compile(r"<\|im_(start|end)\|>"),
]

def input_canary(text: str) -> dict | None:
    for pat in INJECTION_PATTERNS:
        m = pat.search(text)
        if m:
            return {"flag": "possible_injection", "match": m.group(0)}
    return None

Log flagged inputs; reject ze niet automatisch. False positives zijn hier kostbaar voor een research assistant. Maar de log laat je zien wanneer het aantal flags bij één gebruiker plotseling stijgt.

Layer 3: een custom completion validator

Een custom harness kan een report valideren voordat het als complete wordt geaccepteerd. In deze sketch moet de harness de geretourneerde decision verwerken: continue stuurt de feedback naar het model voor een bounded retry; allow_stop accepteert het report. Als de retries op zijn, moet de harness failure rapporteren in plaats van ongeldige output te accepteren. De functie alleen dwingt die loop niet af.

Dit zijn custom decision names, niet het Claude Code Stop-contract, dat decision: "block" gebruikt met een reason om stoppen te voorkomen. De schema- en tickercheck hieronder illustreren application-level validation:

# No-run: illustrative policy sketch; requires Pydantic and the repo-local agent.schemas module.
# agent/completion_validator.py
from pydantic import ValidationError
from agent.schemas import MarketReport

def validate_completion(final_output: str) -> dict:
    try:
        report = MarketReport.model_validate_json(final_output)
    except ValidationError as e:
        return {"decision": "continue",
                "feedback": f"schema invalid: {e.errors()[:3]}"}
    if not report.tickers:
        return {"decision": "continue",
                "feedback": "no tickers in report — did you skip the snapshot step?"}
    return {"decision": "allow_stop"}

Deze checks stellen vast dat de output overeenkomt met het report schema en minstens één ticker noemt. Ze verifiëren de market data of de analyse niet.

Layer 4: approval vóór outbound actions

De execute_trade van de market analyst is een gesimuleerde, idempotente state transition, en demonstreert dus approval routing in plaats van een onomkeerbare financiële side effect. Toon bij een echte outbound integration — email, Slack, een report voor een klant of een brokerage order — de voorgestelde action aan de persoon en wacht op approval of rejection voordat de tool draait. Gebruik interrupt() voor die pause:

# No-run: illustrative outbound-tool sketch; requires LangGraph, a tool decorator, and smtp_send.
# agent/tools/notify.py
from langgraph.types import interrupt

@tool
def send_report(to: str, body: str):
    resp = interrupt({
        "action": "send_report",
        "to": to,
        "body": body,  # Review the complete content that will execute.
    })
    if resp.get("action") == "approve":
        return smtp_send(to, body)
    return "send cancelled by human"

Outbound actions voltooien de lethal trifecta. Vereis approval voor outbound actions wanneer de bestaande authorization en deployment policy ze niet afdekken. Bind approval aan de volledige destination en content; gewijzigde arguments vereisen een nieuwe decision. Messages aan finance, klanten of andere externe recipients moeten aan de approver tonen wat er wordt verzonden en waarheen.

Wat deze stack niet doet

Dit biedt geen verdediging tegen:

  • Een gecompromitte dependency upstream (axios-class). De agent voert uit wat uv sync zegt dat hij moet uitvoeren.
  • Een kwaadaardige .mcp.json in een cloned repo (CVE-2025-59536-class). Het permission model van de host MCP client is waar dit wordt opgevangen, niet de code van de agent.
  • Een data-theft chain die uit legitieme tools is opgebouwd (EchoLeak-class) — de agent leest private data, haalt externe URLs op en stuurt messages naar buiten. Breek of beperk dat exfiltration path met scoped data access, trusted routing, egress restrictions en waar nodig approval. Eén capability verwijderen blokkeert dit specifieke path, niet elke mogelijke aanval.
  • Een escape uit execute_python_analysis, de in-process Python evaluator van de agent. Die blokkeert een lijst met statement types, weigert identifiers die met een underscore beginnen en staat imports alleen toe uit json, math en statistics. Maar exec in het worker process is geen boundary: een bypass draait met de file handles en network access van de worker. Plaats dit achter filesystem-, network- en credential isolation plus CPU-, memory- en timelimits voordat je untrusted code evalueert. Een subprocess alleen erft access en is geen security sandbox.

Deze vier layers zijn lokale policy, en lokale policy is de binnenste layer die je beheert, niet de enige. Elk item in die lijst moet elders worden opgevangen — in het lockfile, in de MCP client, in de process boundary rond generated code of in controls die verhinderen dat untrusted instructions private data met een exfiltration destination verbinden.

Belangrijkste conclusies

  1. Contentfilters en execution policy beschermen verschillende boundaries. Filters inspecteren modelinput en -output. Tool authorization, credential scope, sandboxes en supply-chain controls werken op de paden die in de zeven incidenten zijn gebruikt.
  2. De meeste OWASP ASI-categorieën vereisen controls buiten modeloutput. Gebruik de lijst om elke threat te koppelen aan het component dat haar daadwerkelijk kan blokkeren of registreren.
  3. Permission is infrastructure, geen prompt. Claude Code documenteert de precedence van deny-, ask- en allow-rules, terwijl PreToolUse vóór execution kan blokkeren. De Claude Agent SDK stelt een afzonderlijk canUseTool-path beschikbaar. Andere runtimes hebben een even goed testbaar precedence model nodig.
  4. Behandel de structured deny van een PreToolUse hook als elke andere tool observation. De reasoning loop verwerkt dit al. Je hebt geen afzonderlijke security workflow nodig.
  5. Een approval rate van 93% is een signaal om promptkwaliteit en escalationfrequentie te onderzoeken. Meet edits, denials en incidents na approval in plaats van een universeel target te kopiëren.
  6. Audience-bound tokens en per-session vaults beperken credential replay en exposure. Ze vervangen project trust, hook policy of sandboxing niet.
  7. Supply-chain checks moeten op automation speed draaien. Pin versions en Actions SHAs, scan in CI en review dependency changes in pull requests die door agents zijn geschreven.
  8. Bouw de policy layer zo dat een nieuwe productlancering haar niet ongeldig maakt. OpenAI Agents SDK, Codex CLI en Claude Code drukken dezelfde primitives op verschillende manieren uit. De primitives (permission ladders, hooks, sandboxes, interrupts, audience-bound tokens) zijn waarop je inzet.
