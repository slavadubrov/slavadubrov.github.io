Harness engineering voor AI agents: de loop rond het model ontwerpen

Deel 6 van de serie Engineering the Agentic Stack

De reasoning loop van een agent kiest de volgende actie. De harness levert context aan, valideert en autoriseert voorgestelde tool calls, dispatcht geaccepteerde calls naar de runtime, legt de resultaten vast en beslist of de taak voltooid is.

Models stellen edits voor en kunnen taken als voltooid markeren, terwijl de harness permissies afdwingt en de acceptance checks interpreteert die bepalen of de loop mag stoppen. Deel 5 behandelde de runtime die het proces in leven houdt. Dit artikel richt zich op de control code binnen die runtime: hoe je meet of elke toevoeging helpt en hoe je de resulterende controls vindbaar houdt terwijl de harness verandert.

Na de eerste expliciete acceptance check is elke extra retry, handoff of evaluator een hypothese over een geobserveerde failure. Zo’n component verdient pas een plek wanneer een gecontroleerde vergelijking laat zien dat hij helpt.

Om dat control path concreet te maken, gebruik ik een kleine fictieve store-repository. De coding-taak is om de drempel voor een automatische korting van 10% te verlagen van $100 naar $75 in src/checkout.py. De repository heeft twee verplichte checks:

  • pytest tests/test_checkout.py verifieert de kortingsberekening.
  • pnpm playwright test tests/checkout_discount.spec.ts voegt een item van $80 toe in een lokale testwinkel en controleert of de checkout-pagina een korting van $8 toont.

Het voorbeeld is een didactische fixture, geen echte applicatie of benchmark. Elke poging start vanaf dezelfde commit en dezelfde seeded testdata. De harness mag de wijziging alleen accepteren wanneer beide commands slagen en de trace die resultaten koppelt aan de geteste commit.

Latere secties schakelen bewust over naar twee andere voorbeelden. Een staging-order API laat zien waarom state-changing calls replay protection nodig hebben, terwijl een payment-adapter-migratie laat zien wat een nieuwe model session nodig heeft om onvoltooid werk te hervatten. De companion lab verderop staat opnieuw los hiervan: het is uitvoerbaar, maar bevat generieke gesimuleerde taken in plaats van deze store-repository.

TL;DR: Begin met één model, een paar smalle tools en een expliciete acceptance check. Voeg retries toe nadat traces tijdelijke call-failures laten zien. Voeg een progress handoff toe wanneer hervatte sessions werk herhalen. Als je een van beide wijzigingen test, houd dan de modelversie, taken, grader en het totale budget gelijk. Verwijder de component als hij het gemeten resultaat niet verbetert.

Waar de harness eigenaar van is

OpenAI’s Codex loop walkthrough beschrijft de basiscirkel. De harness stelt een prompt samen, vraagt het model om de volgende actie, stuurt een geaccepteerde tool call naar de runtime, voegt het resultaat toe en vraagt opnieuw totdat de harness het resultaat accepteert of de controle teruggeeft aan de gebruiker.

Volg de discount-wijziging van voorstel tot acceptatie

Voor de hierboven gedefinieerde discount-taak stelt het model voor om calculate_discount in src/checkout.py te wijzigen. Er gebeuren meerdere dingen voordat die edit als voortgang telt:

  1. De context builder levert de taak, repository-instructies, relevante bestanden, eerdere tool results en het huidige plan aan.
  2. Het model stelt een edit_file call voor met een pad en vervangende tekst.
  3. De tool boundary (de harness-code tussen voorstel en uitvoering) valideert de argumenten, controleert het pad tegen de toegestane scope en vraagt om approval als de operatie dat nodig heeft.
  4. De runtime past de edit toe in de sandbox en geeft een structured output terug.
  5. De harness draait pytest tests/test_checkout.py, gevolgd door pnpm playwright test tests/checkout_discount.spec.ts, en leest van beide de exit codes. De browser test controleert de zichtbare korting van $8 op de seeded cart van $80.
  6. De harness beslist wat de resultaten betekenen. Een gefaalde check wordt nieuwe context voor de volgende modelturn, en een geslaagde run maakt de taak een completion candidate.
  7. Een geslaagd resultaat wordt pas completion evidence nadat de harness de command, exit code en geteste artifact-versie in de trace heeft vastgelegd.

Bij stap 2 is er nog geen bestand gewijzigd. De harness kan ../../secrets.env afwijzen, approval vereisen voor een destructieve command, of een run stoppen die zijn budget heeft uitgeput. Nadat de tests hebben gedraaid, leest de harness zelf hun exit codes. Het model kan zijn eigen edit niet als geslaagd markeren.

De trace moet het voorgestelde pad en de vervangende tekst tonen, de permission decision, de bestanden die zijn gewijzigd, de geteste commit en beide command-results. Een definitief bericht done zonder die records bewijst niet dat deze wijziging de verplichte checks heeft gehaald.

Tool contracts scheiden voorstel van permissie

De discount-taak heeft alleen file edits en test-commands nodig. Een state-changing API heeft een andere failure mode, dus voor deze sectie wisselen we van voorbeeld. Stel dat de agent create_test_order kan aanroepen tegen een staging order-service terwijl hij testdata opzet. Deze tool is geen onderdeel van de acceptance checks van de discount-taak. Hij is hier nuttig omdat een timeout kan verhullen of de service een order heeft aangemaakt.

De tool boundary heeft meer nodig dan een natural-language description. Voor create_test_order heeft de harness een contract nodig met:

  • gevalideerde argumenten, zodat malformed input vóór uitvoering wordt afgewezen
  • een structured output zoals { "order_id": "123", "created": true }, zodat latere checks geen free-form tekst hoeven te parsen
  • een effect category die vastlegt of de call alleen informatie ophaalt of een bestand, database-record of externe service wijzigt. Ook legt die vast of het veilig is de call te herhalen. Dit label vertelt de harness of een automatische retry werk kan dupliceren: hij kan get_order_status retryn wanneer de service die lookup als read-only definieert, maar hij mag create_test_order niet blind retryn omdat de eerste call de order al kan hebben aangemaakt
  • een timeout- en retry policy, zodat een verloren response geen onbeperkte reeks calls triggert
  • een permission rule die aangeeft welke approval vereist is. Het lezen van orderstatus mag automatisch draaien, terwijl het aanmaken van een order bevestiging kan vereisen

De natural-language description is tekst die aan het model wordt getoond. Die kan bijvoorbeeld zeggen: “Create a test order for checkout verification.” Die zin helpt het model beslissen wanneer het create_test_order moet voorstellen. Hij autoriseert de call niet. In dit voorbeeld valideert de MCP-client van de harness de argumenten, past zijn eigen regels toe en controleert server trust, approval requirements en retry safety voordat iets wordt gedispatcht.

Een MCP-server publiceert tool descriptions en optionele behavior annotations naar de client. Een defecte of kwaadaardige server zou een state-changing tool als onschadelijk kunnen beschrijven. Als de client die claim automatisch zou accepteren, zou hij create_test_order zonder approval kunnen uitvoeren of retryn en een duplicaat aanmaken, dus de MCP-specificatie vereist dat clients tool annotations als onbetrouwbaar behandelen tenzij de server zelf trusted is.

De specificatie schrijft geen universele trust setting voor. De client heeft daarom een expliciete trust policy nodig voor zijn deployment; een server kan zijn eigen annotations niet zelf betrouwbaar maken. Dat beleid beslist welke metadata permission- of retry-beslissingen mag beïnvloeden en welke annotations alleen adviserend blijven.

Een state-changing call retryn heeft replay protection nodig

Een lastiger retry-probleem ontstaat wanneer create_test_order de order aanmaakt maar de HTTP-response verloren gaat. De harness ziet een timeout en kan niet vaststellen of de server de request heeft voltooid. Het herhalen van de call kan een tweede order aanmaken.

Een statuslookup kan worden geretryd wanneer de service die als read-only definieert. Een create-call heeft bescherming nodig zoals een idempotency key: de client voegt een unieke request identifier toe, en de service retourneert het eerste resultaat in plaats van nog een order aan te maken wanneer hij die identifier opnieuw ziet. Zonder deze bescherming moet de harness controleren of de order bestaat of om een menselijke beslissing vragen voordat er een nieuwe poging volgt. AWS documenteert dit patroon in zijn idempotent API guidance.

Acceptatie heeft onafhankelijk bewijs nodig

Een succesvolle response van create_test_order bewijst alleen dat de tool data heeft teruggegeven. Het bewijst niet dat een coding-taak zijn tests heeft gehaald. Als een latere browser test afhangt van de staged order, moet de harness het response-schema valideren en die test nog steeds draaien voordat hij de codewijziging accepteert.

Sommige criteria zijn niet te reduceren tot een exit code. Voor een afzonderlijke visual-design-taak kan een nieuwe evaluator een gerenderde pagina of diagram vergelijken met een geschreven rubric. Teams moeten die evaluator toetsen aan menselijke reviews voordat ze hem gebruiken als completion gate.

Een payment-adapter-migratie heeft een handoff nodig

We wisselen opnieuw van taak, maar blijven in de fictieve store-repository. De agent moet checkout nu migreren van payment adapter v1 naar v2. Het werk beslaat de checkout-handler, payment client, configuratie en tests, dus het kan langer duren dan één model session.

Voordat de eerste session zijn contextlimiet bereikt, heeft hij meerdere bestanden aangepast, een lokale payment sandbox gestart en tests/payment_migration.spec.ts falend achtergelaten. Die browser acceptance test voltooit één betaling via adapter v2 en verifieert de vastgelegde provider-ID. Een conversation summary kan de volgende model session oriënteren, maar kan de sandbox niet herstarten of bewijzen welke bestanden op dit moment gewijzigd zijn.

Compaction vervangt oudere messages door een kortere samenvatting zodat de huidige session kan doorgaan. Een progress handoff legt vast wat de volgende session nodig heeft: de huidige branch, gewijzigde bestanden, de laatste test-command en output, en de volgende onopgeloste stap. Als de oude conversatie verouderde aannames bevat, kan de harness een nieuwe model session starten met die handoff en de huidige workspace. Het vervangen van een gecrashte worker en het herstellen van zijn processen is een aparte runtime-recoverytaak.

Een kleine documentatie-edit heeft mogelijk geen van deze mechanismen nodig. De payment-migratie heeft een handoff nodig zodra werk over meerdere sessions loopt, omdat de volgende model session zowel de workspace als de taakstatus moet reconstrueren.

Anthropic’s experimenten met long-running coding agents gebruikten git-history en een progress file tussen sessions, terwijl zijn latere rapport over harness-design compaction scheidt van een fresh-context handoff en de extra orchestration, tokengebruik en wall time rapporteert die handoffs vereisen.

Meet één wijziging tegelijk

Een ablation meet of een harness-component het verwachte effect veroorzaakt door die component te wijzigen of te verwijderen terwijl de rest van het experiment gelijk blijft. Bijvoorbeeld: helpt editor linting dit model op deze tasksuite?

Gebruik het volgende protocol:

  1. Bevries de modelversie, task-instances, omgeving, grader en prompts buiten de te testen component.
  2. Geef beide varianten hetzelfde totale budget voor tokens, tijd en dollars.
  3. Kies het aantal trials of de stopregel voordat je de vergelijking uitvoert.
  4. Draai dezelfde task-instances in beide varianten. Omdat modeloutputs variëren, herhaal je elke taak meerdere keren.
  5. Rapporteer het gemiddelde samen met de spreiding of het confidence interval.
  6. Tel elke gestarte trial mee, inclusief timeouts, policy-stops, harness-crashes en evaluator-failures.

Alleen de success rate kan een dure component verhullen. Volg minimaal het aantal kapotte taken dat als voltooid is geaccepteerd, kosten en wall time per voltooide taak, tool errors, dubbele orders, reviewminuten en manual permission overrides. Kies de metric die de echte kosten van het product draagt. Een stijging van twee procentpunten in voltooide taken is een slechte trade-off als die de reviewqueue verdubbelt.

Een paired experiment voor payment-migratie maakt de progress handoff meetbaar. Elk control/treatment-paar start vanaf dezelfde repository-commit en seeded checkpoint, met hetzelfde model, dezelfde taak, grader en hetzelfde totale budget. De handoff is de enige schakelaar. De primaire metric telt dubbele tool actions na hervatting: een action is dubbel wanneer operatie en artifact overeenkomen met een stap die de vorige session al had voltooid.

Houd de harness editbaar nadat hij zijn plek heeft verdiend

Ablation houdt een harness klein, maar de code ervan kan het model waarvoor hij is getuned alsnog overleven. Een verzoek als “mask secrets in elk capture path” benoemt een behavior, geen bestand. In een productie-harness kan dat behavior execution stages en gedeelde state overspannen. Een mens of coding agent moet elke implementatielocatie kunnen vinden voordat hij die veilig kan wijzigen.

Een preprint uit 2026 van Wang et al., het Harness Handbook, noemt deze stap behavior localization. Het handbook bouwt een behavior-centric map van de harness-codebase. Static analysis extraheert een program graph zonder model-calls, waarna een LLM de onderdelen ordent in execution stages.

De maintainer of coding agent begint met een system overview, opent de relevante execution stage en daalt af naar source-grounded entries voor een functie of bestand. Een register-view legt vast waar gedeelde state tussen stages wordt geschreven en gelezen. Deze hiërarchie houdt het overzicht klein en bewaart tegelijk een pad naar de broncode.

Versheid is een aparte regel. Elke locator moet resolven tegen de live repository. Het handbook sluit verouderde entries uit in plaats van te gokken, en elke non-empty diff resynchroniseert de entries die hij beïnvloedt.

Het diagram comprimeert de modificatieloop: een request dat alleen behavior benoemt daalt af door de niveaus van het handbook, elke kandidaat-locator wordt geverifieerd tegen de live repository voordat het plan wordt geschreven, en elke toegepaste diff resynchroniseert de map.

De Handbook-evaluatie volgt het protocol waar dit artikel voor pleit. Op twee open-source harnesses (Terminus-2, zes Python-bestanden, en de Codex-monorepo, 2.267 Rust-bestanden) verkende een read-only planner op basis van DeepSeek-V4-Pro de repository direct of via het handbook. Requests, repository, tool permissions en decoding waren in beide armen identiek. Drie judges (GPT-5.5, Opus 4.8, DeepSeek-V4-Pro) scoorden elk edit-plan op localization, scope control en reasoning:

Probeer de methode in de companion lab

Elke task-fixture declareert een moeilijkheidsgraad plus vier booleaanse voorwaarden: een flaky tool, verloren voortgang, een gemiste implementation gap en ambigue completion. Het configuratieschema van de lab controleert alle vijf componentvelden. Dit uitvoerbare fragment toont dezelfde guard voor één geldig progress-handoff-paar:

from dataclasses import dataclass, fields


@dataclass(frozen=True)
class Config:
    progress_handoff: bool = False
    evaluator: bool = False
    retry_policy: bool = False
    fail_closed_acceptance: bool = False
    context_reset: bool = False


def changed_components(control: Config, treatment: Config) -> tuple[str, ...]:
    return tuple(
        field.name
        for field in fields(control)
        if getattr(control, field.name) != getattr(treatment, field.name)
    )


control = Config(progress_handoff=False, evaluator=True, retry_policy=True)
treatment = Config(progress_handoff=True, evaluator=True, retry_policy=True)
assert changed_components(control, treatment) == ("progress_handoff",)

Begin met één loop en één acceptance check

Ik zou een coding-agent-harness beginnen met één capabel model, repository-instructies, een paar smalle tools, een sandbox en één expliciete acceptance test. Ik zou tool calls, resultaten, kosten en die laatste test in één trace vastleggen zodat de eerste nuttige failures zichtbaar zijn zonder ze te reconstrueren uit terminal-logs en chattranscripten. Dit is een voorgestelde baseline, geen bewijs uit een deployed systeem.

Voeg daarna alleen toe wat een trace rechtvaardigt. Leg vast wie elke component onderhoudt, hoeveel tokens of seconden hij toevoegt en welke regression test zijn verwijdering na een modelupgrade zou rechtvaardigen.

Zes maanden later moet iemand die progress_handoff=True ziet, de gefaalde traces kunnen vinden die hem rechtvaardigden en de regression-cases die hem daar nog steeds houden. De traces verklaren waarom de component bestaat; een actuele behavior map verklaart waar je hem moet aanpassen.
