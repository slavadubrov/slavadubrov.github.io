Harness engineering voor AI agents: control loops ontwerpen

Viacheslav Dubrov

2026-07-22 · Bijgewerkt 2026-09-12 · 26 min · AI-agenten

Automatische vertaling

Dit artikel is automatisch vertaald vanuit de oorspronkelijke Engelse versie.

Harness engineering is het ontwerpen van de control code rond de reasoning loop van een agent. Voor engineers die coding agents bouwen of reviewen, legt dit artikel uit hoe je voltooiing verifieert, veilig retryt, voortgang tussen sessies bewaart en optionele controls vergelijkt met een vaste baseline.

Een agent kan zijn beurt beëindigen terwijl het werk nog niet af is. Voor een coding agent zijn het gewijzigde artifact en de vereiste testresultaten het bruikbare bewijs. Een final message met de tekst “done” bewijst geen van beide.

De harness levert context, valideert en autoriseert tool calls, registreert resultaten en beslist of het bewijs voldoende is om het werk te accepteren. De runtime houdt de uitvoering en state daaronder actief. De store-voorbeelden hieronder zijn fictief; het bijbehorende lab is een deterministische simulatie, geen meting van een live agent.

TL;DR

Accepteer een coding task niet omdat het model zegt dat die klaar

is. Vereis het gewijzigde artifact en de vereiste testresultaten. Voeg alleen een retry, handoff of evaluator toe wanneer een gecontroleerde vergelijking aantoont dat dit het resultaat verbetert.

De eenvoudigste acceptance check is makkelijk te schrijven voor een kleine research agent zoals die waarmee deze serie is begonnen — een LangGraph agent die marktdata ophaalt en een analistenrapport schrijft. Een hook buiten het model valideert het rapport tegen een schema en controleert of het daadwerkelijk stock tickers bevat; een malformed report houdt de run open. Twaalf regels gewone code zijn genoeg, en het model mag zijn eigen output niet als well-formed verklaren. De repo gebruikt een zachtere check: een evaluator met fresh context stemt, waarna een human het resultaat reviewt. (Part 4 schetst de deterministische versie.)

Wat dit voorbeeld niet kan laten zien, is het interessante deel: wat er gebeurt wanneer het bewijs ambigu is, wanneer een retry iemand dubbel kan laten betalen of wanneer het werk langer duurt dan de sessie waarin het is gestart. Daarvoor is een task nodig met een scherpere pass/fail-grens dan een research report heeft. De research agent blijft het voorbeeld voor de acceptance check; een kleine fictieve store-repository wordt toegevoegd voor de retry- en handoff-cases. De coding task is om de drempel voor een automatische korting van 10% te verlagen van $100 naar $75 in src/checkout.py. De repository heeft twee vereiste checks:

  • pytest tests/test_checkout.py controleert de discount calculation.
  • pnpm playwright test tests/checkout_discount.spec.ts voegt een item van $80 toe in een lokale test store en controleert of de checkoutpagina een korting van $8 toont.

Het voorbeeld is een teaching fixture, geen echte applicatie of benchmark. Elke poging start vanaf dezelfde commit en met dezelfde seeded test data. De harness mag de wijziging alleen accepteren wanneer beide commands slagen en een durable acceptance record beide resultaten koppelt aan een clean committed candidate of aan een digest van de volledige geteste snapshot, inclusief relevante untracked files.

Het diagram volgt de discount change van voorstel tot bewijs. De harness levert de task en files, controleert de voorgestelde edit_file-arguments en permissions, en dispatcht de geaccepteerde call. Nadat de runtime de edit toepast, voert de harness de benoemde unit- en browser acceptance tests uit. Een gefaald command gaat als bewijs terug naar het model voor een volgende turn; twee geslaagde commands maken de wijziging eligible voor acceptance.

Wat de harness beheert

OpenAI’s Codex loop walkthrough beschrijft de basiscyclus. De harness stelt een prompt samen, vraagt het model om de volgende actie, stuurt een geaccepteerde tool call naar de runtime en voegt het resultaat toe. Daarna vraagt de harness het opnieuw. Dit herhaalt zich totdat de harness het resultaat accepteert of de control teruggeeft aan de user.

Implementaties kunnen verschillende verantwoordelijkheden in één process samenvoegen. De failure boundaries blijven echter verschillend:

TermTaakVoorbeeld voor een coding agent
ModelStelt tekst, een tool call of een final answer voorStelt een edit voor in src/checkout.py
Reasoning loopKiest de volgende stap uit de beschikbare contextInspect, edit, test, opnieuw inspecteren
HarnessLevert context, valideert voorstellen, autoriseert ze, dispatcht geaccepteerde calls, registreert resultaten en controleert voltooiingStaat edits onder src/ toe en vereist beide benoemde tests
RuntimeVoert geaccepteerde calls uit en houdt state buiten het worker process actiefSession log, sandbox, checkpoint store, trace backend

De runtime-row omvat vier zaken: session, sandbox, checkpoint en trace. Alle vier bewaren state of beperken de uitvoering. Het model stelt de actie voor en de reasoning loop kiest de volgende stap. De harness beslist of een voorgestelde call mag worden uitgevoerd en of het bewijs voldoende is om te stoppen. Daarom krijgt de harness een eigen artikel. Part 5 telt de harness samen met die vier als een van de vijf primitives die je vóór shipping moet plaatsen; dit artikel splitst hem weer uit.

Wanneer een failure optreedt, diagnosticeer dan de boundary die moet reageren. Een slecht plan kan betere instructies of betere model reasoning vereisen. Als edit_file een path buiten src/ target, moet de harness die afwijzen. Een sandbox process dat sterft voordat de edit wordt uitgevoerd, hoort bij de runtime, die de worker moet herstarten of de crash moet melden.

Waar de eerdere delen terechtkomen

De harness-row hierboven doet het meeste werk in die tabel, en daar komen Parts 2, 3 en 4 uiteindelijk terecht. Elk deel beslist één ding over een enkele turn:

Het diagram brengt verantwoordelijkheden in de serie in kaart. De rijen groeperen het model, de harness en de runtime; ze tonen niet de execution order. Context en tools informeren het voorstel, permission checks gaan aan de uitvoering vooraf en completion checks gebruiken het resulterende bewijs.

Parts 3 en 4 delen step 3, en precies die overlap is het argument om ze als één program te behandelen. Dezelfde laag harness code die een malformed argument afwijst, wijst ook een call af die wel is toegestaan maar nog niet is goedgekeurd. Als validation en authorization in afzonderlijke services draaien, bewaar dan de gevalideerde arguments over die boundary heen, zodat de authorization decision betrekking heeft op de call die werkelijk wordt uitgevoerd.

De splitsing blijft belangrijk voor debugging: een edit van het verkeerde bestand is een Part 4 path rule, geen Part 2 retrieval-probleem. Een sectie tegen het einde van dit artikel zet dat om in een routing table.

OpenAI’s eigen harness-engineering-case study beschrijft een bootable application instance voor elke worktree. Het team verbond ook browser automation met de agent environment en maakte logs, metrics en traces beschikbaar.

Een task zoals “geen span in deze vier kritieke user journeys is langer dan twee seconden” werd testbaar omdat de agent de applicatie kon uitvoeren en dezelfde signals kon opvragen die een engineer zou inspecteren. De case study is productspecifiek. Wat overdraagbaar is, is de voorwaarde achter het resultaat: de applicatie en haar performance-signalen moesten binnen de agent environment beschikbaar zijn.

Lopopolo, de auteur van die case study, onderhoudt een field guide for harness engineering. Die benoemt de twee levers die dit artikel gebruikt: houd het model en de coding agent als black box constant en engineer de context en tools eromheen. Zijn framing verklaart ook waarom zoveel van de harness uit gewone code bestaat.

De quality bar, procedures, exception history en authority relationships van een organisatie vallen buiten wat een general-purpose model kan weten. De harness maakt ze zichtbaar als repository instructions, permission rules en acceptance checks. Elke geaccepteerde run kan zijn lessons terugvoeren naar die artifacts, in plaats van erop te vertrouwen dat de volgende sessie ze opnieuw ontdekt.

Volg de discount change van voorstel tot acceptance

Byte zegt

Ik heb nog steeds beide testresultaten voor deze discount change nodig, ook als het model zegt dat die klaar is.

Voor de hierboven gedefinieerde discount task stelt het model voor om calculate_discount in src/checkout.py te wijzigen. Voordat die edit als progress geldt, gebeuren verschillende dingen:

  1. De context builder levert de task, repository instructions, relevante files, eerdere tool results en het huidige plan.
  2. Het model stelt een edit_file call voor met een path en replacement text.
  3. De tool boundary (de harness code tussen proposal en execution) valideert de arguments, controleert het path tegen de toegestane scope en vraagt om approval als de operatie dat vereist.
  4. De runtime past de edit toe in de sandbox en retourneert een structured result.
  5. De harness voert pytest tests/test_checkout.py uit, gevolgd door pnpm playwright test tests/checkout_discount.spec.ts, en leest beide exit codes. De browser test controleert de zichtbare korting van $8 op de seeded cart van $80.
  6. De harness beslist wat de resultaten betekenen. Een gefaalde check wordt nieuwe context voor de volgende model turn; een geslaagde run maakt de task een completion candidate.
  7. Een geslaagd resultaat wordt pas completion evidence nadat de harness het command, de exit code, de geteste snapshot, de grader en de environment versions durable heeft geregistreerd; een trace kan naar dat record verwijzen.

Na step 2 is er nog geen file gewijzigd. De harness kan ../../secrets.env afwijzen, approval vereisen voor een destructive command of een run stoppen die zijn budget heeft opgebruikt. Dat is het laatste goedkope moment dat je krijgt. Nadat de tests zijn uitgevoerd, leest de harness zelf hun exit codes. Het model kan zijn eigen edit niet als geslaagd markeren.

Het acceptance record moet de geteste snapshot, beide commands en resultaten, en de grader- en environment versions identificeren; traces kunnen naar dat record verwijzen. Houd vereiste tests buiten de writable scope van de agent, of keur wijzigingen onafhankelijk goed voordat je ze gradeert. Elke latere file edit maakt het resultaat ongeldig. Deze checks implementeren de stable-environment- en bypass-resistant-grader-principes uit Anthropic’s evaluation guidance. Een laatste done-message zonder deze records bewijst niet dat deze wijziging de vereiste checks heeft doorstaan.

Bepaal waar elke rule wordt afgedwongen

De vereiste dat tests/checkout_discount.spec.ts slaagt, hoort in deterministische code, niet in de prompt. De harness dispatcht het Playwright command naar de runtime, leest de exit code en weigert de run te beëindigen zolang de test faalt. Een prompt kan het model eraan herinneren de test uit te voeren. Hij kan het model niet verhinderen succes te verklaren zonder bewijs.

Tool contracts scheiden voorstel en permission

De discount task heeft alleen file edits en test commands nodig. Een state-changing API heeft een ander failure mode, dus voor deze sectie wisselen we van voorbeeld. Stel dat de agent create_test_order kan aanroepen tegen een staging order service bij het aanmaken van test data. Deze tool is geen acceptance check van de discount task. Hij is hier nuttig omdat een timeout kan verbergen of de service een order heeft aangemaakt.

De tool boundary heeft meer nodig dan een beschrijving in natural language. Er is een expliciet tool contract nodig. Part 3 pleitte daarvoor vanuit het perspectief van het model: duidelijke actions, compacte feedback, recoverable errors. De harness heeft hetzelfde contract om een andere reden nodig. Zij moet zonder het model te vragen beslissen of een call mag worden uitgevoerd en of een gefaalde call mag worden herhaald. Voor create_test_order betekent dat een contract met:

  • gevalideerde arguments, zodat malformed input vóór execution wordt afgewezen
  • een structured result zoals { "order_id": "123", "created": true }, zodat latere checks geen free-form text hoeven te parsen
  • een effect category die registreert of de call alleen informatie ophaalt of een file, database record of external service wijzigt. De category registreert ook of herhaling van de call veilig is. Dit label vertelt de harness of een automatic retry werk kan dupliceren. De harness kan get_order_status retryen wanneer de service die lookup als read-only definieert. Zij mag create_test_order niet blind retryen, omdat de eerste call de order al kan hebben aangemaakt
  • een timeout- en retry policy, zodat een verloren response geen onbeperkte reeks calls veroorzaakt
  • een permission rule die zegt welke approval nodig is. De orderstatus lezen kan automatisch gebeuren, terwijl het aanmaken van een order confirmation kan vereisen

De beschrijving in natural language is tekst die aan het model wordt getoond. Die kan zeggen: “Create a test order for checkout verification.” Die zin helpt het model bepalen wanneer het create_test_order moet voorstellen. Hij autoriseert de call niet. In dit voorbeeld valideert de Model Context Protocol (MCP)-client van de harness de arguments, past zijn eigen rules toe en controleert server trust, approval requirements en retry safety voordat iets wordt gedispatcht. Daarmee worden de permission rules en pre-tool checks uit Part 4 gecombineerd, met één extra vraag: of een call die al is gefaald opnieuw mag worden verstuurd.

Een MCP server publiceert tool descriptions en optionele behavior annotations naar de client. Een faulty of malicious server kan een state-changing tool als harmless beschrijven. Een client die die claim automatisch accepteert, kan create_test_order zonder approval uitvoeren of retryen en zo een duplicate aanmaken. De MCP-specificatie vereist daarom dat clients tool annotations als untrusted behandelen, tenzij de server zelf trusted is.

De specificatie schrijft geen universele trust setting voor. Je hebt daarom een expliciet trust policy nodig voor je deployment; een server kan zijn eigen annotations niet trustworthy maken. Die policy beslist welke metadata permission- of retry-decisions mag beïnvloeden en welke annotations alleen advisory blijven.

Een state-changing call retryen vereist replay protection

Part 5 vereist een durable operation identity voor side effects die bij een retry kunnen dupliceren. De harness beslist wanneer die key deze rol moet vervullen. create_test_order maakt de order aan, maar de HTTP response gaat verloren. De harness ziet een timeout en kan niet weten of de server het request heeft voltooid. De call herhalen kan een tweede order aanmaken.

Persist een application-owned operation ID vóór dispatch en bind die aan de approved arguments. Hergebruik deze ID bij het herstellen van dezelfde bedoelde order, ook als het model een nieuwe tool-call ID genereert; bewaar model IDs afzonderlijk voor correlation. Reconcile gewijzigde payloads of verlopen provider-deduplication windows in plaats van blind opnieuw te verzenden. Stripe’s contract staat bijvoorbeeld toe keys pas na ten minste 24 uur te verwijderen.

Een status lookup kan worden geretryd wanneer de service die als read-only definieert. Een creation call heeft de key nodig: de client koppelt een uniek request identifier en de service retourneert het eerste resultaat in plaats van een nieuwe order te creëren wanneer dezelfde identifier opnieuw wordt gezien. Zonder deze bescherming moet de harness controleren of de order bestaat of een human decision vragen voordat een nieuwe poging wordt gedaan. AWS documenteert dit patroon in zijn idempotent API guidance.

Acceptance vereist onafhankelijk bewijs

Een succesvolle create_test_order response bewijst alleen dat de tool data heeft geretourneerd. Zij bewijst niet dat een coding task de tests heeft doorstaan. Als een latere browser test afhankelijk is van de staged order, moet de harness het response schema valideren en die test nog steeds uitvoeren voordat de code change wordt geaccepteerd.

Sommige criteria kunnen niet worden gereduceerd tot een exit code. Voor een afzonderlijke visual-design task kan een evaluator met fresh context een rendered page of diagram vergelijken met een geschreven rubric — “fresh context” betekent een tweede model session die start zonder history van de run en de geproduceerde artifacts leest in plaats van het transcript. Vergelijk die evaluator met human reviews voordat je het resultaat laat beslissen of de task compleet is.

Een payment-adapter migration heeft een handoff nodig

Wissel opnieuw van task, maar blijf in de fictieve store-repository. De agent moet checkout nu migreren van payment adapter v1 naar v2. Het werk omvat de checkout handler, payment client, configuration en tests, en kan daardoor langer duren dan één model session — één ononderbroken reeks model context die eindigt door een restart of een bewuste fresh start, in plaats van te worden meegenomen.

Voordat de eerste session zijn context limit bereikt, heeft die meerdere files gewijzigd, een lokale payment sandbox gestart en tests/payment_migration.spec.ts gefaald achtergelaten. Die browser acceptance test voltooit één payment via adapter v2 en controleert de geregistreerde provider ID. Een conversation summary kan de volgende model session oriënteren, maar kan de sandbox niet herstarten of bewijzen welke files momenteel gewijzigd zijn.

De volgende session moet drie dingen herstellen:

Wat moet worden hersteldWat het omvatHoe het kan falen
Conversation historyMessages, tool calls en returned resultsOude details verdringen de huidige task
Working environmentFiles, payment sandbox en browser-test stateHet transcript zegt dat een service draait nadat die is gestopt
Task progressPlan, voltooide checks, pending approval, next actionDe volgende session herhaalt afgerond werk

Compaction vervangt oudere messages door een kortere summary, zodat de huidige session kan doorgaan. Een progress handoff legt vast wat de volgende session nodig heeft: de huidige branch, gewijzigde files, het laatste test command en de output, en de volgende onopgeloste stap.

Een handoff file is document memory voor de volgende model session. Een checkpoint kan het plan, voltooide steps, resultaten en resterende werk al bewaren. Voeg een handoff toe wanneer die details in de volgende context ontbreken of onbruikbaar zijn, en verifieer files en draaiende services tegen de live environment.

Als de oude conversation stale assumptions bevat, kan de harness een fresh model session starten met die handoff en de huidige workspace. Een gecrashte worker vervangen en zijn processes herstellen is een afzonderlijke runtime recovery job.

Een kleine documentation edit heeft mogelijk geen van deze mechanismen nodig. De payment migration heeft een handoff nodig als de opgeslagen state geen bruikbare task progress bevat, omdat de volgende model session zowel de workspace als de task status moet reconstrueren.

Anthropic’s experiments met long-running coding agents gebruikten git history en een progress file tussen sessions. Anthropic’s latere harness-design report maakt onderscheid tussen compaction en een fresh-context handoff en rapporteert dat handoffs orchestration, token use en wall time toevoegen, zonder cijfers te publiceren die een van die overheads aan de handoff zelf toeschrijven.

Gebruik traces om drie failures te onderscheiden

De volgende drie rijen zijn illustratieve trace sketches, geen gemeten runs of output uit het companion lab. Elke rij toont een andere failure en dus een andere harness response.

Een failure die transient lijkt, maakt niet elke call veilig om te retryen. De eerste rij is een read-only lookup. De tweede rij is een state-changing request, dus de idempotency key en de server-side status bepalen of een nieuwe creation attempt is toegestaan. De derde rij is helemaal geen tool failure; de harness heeft het bewijs dat nodig is om de discount change te accepteren nog niet verzameld.

Een chat transcript registreert wat het model zag. Het kan niet bewijzen of de order service een request heeft committed voordat de response verdween. Een trace kan dat bewijs alleen leveren als hij het relevante server result of de status lookup bevat; een client-side timeout alleen laat de uitkomst onopgelost. De durable operation- en acceptance records moeten de client call, approval decision, operation identity, server result of status lookup, tested snapshot en acceptance-test result aan elkaar koppelen. Traces kunnen die links zichtbaar maken voor debugging zonder de recovery ledger te worden. Die velden vertellen de harness welke van de drie paden actief is.

Voor optionele hulp zoals planning aids, summaries en extra evaluators moet je de failure benoemen en meten of het component zijn kosten terugverdient. Authorization, isolation, privacy requirements en mandatory acceptance checks blijven van kracht, ook als gewone tasks zonder deze componenten slagen. Test die constraints met adversarial cases en expliciete invariants; een kleine success benchmark kan niet rechtvaardigen dat je ze verwijdert.

Meet één wijziging per keer

Een ablation meet of een harness-component het verwachte effect veroorzaakt door dat component te wijzigen of te verwijderen terwijl de rest van het experiment gelijk blijft. Helpt editor linting dit model bijvoorbeeld op deze task suite?

Gebruik het volgende protocol:

  1. Freeze de modelversie, task instances, environment, grader en prompts buiten het component dat wordt getest.
  2. Geef beide varianten hetzelfde totale token-, tijd- en dollarbudget.
  3. Kies het aantal trials of de stopping rule voordat je de vergelijking uitvoert.
  4. Voer dezelfde task instances in beide varianten uit. Omdat model outputs variëren, herhaal je elke task meerdere keren.
  5. Rapporteer het gemiddelde samen met de spreiding of confidence interval.
  6. Tel elke gestarte trial mee, inclusief timeouts, policy stops, harness crashes en evaluator failures.

Success rate alleen kan een duur component verbergen. Meet minimaal broken tasks die als complete zijn geaccepteerd, cost en wall time per completed task, tool errors, duplicate orders, review minutes en manual permission overrides. Kies de metric die voor je product de werkelijke kosten draagt. Een stijging van twee punten in completed tasks is een slechte trade als je review queue verdubbelt.

Voor de fictieve payment migration zou een paired experiment de optionele progress handoff meetbaar maken. Elk control/treatment-paar start vanaf dezelfde repository commit en seeded checkpoint, met hetzelfde model, task, grader en totale budget. De handoff is de enige switch. De primary metric telt duplicate tool actions na resume: een action is duplicate wanneer de operation en artifact overeenkomen met een stap die de vorige session al had voltooid.

Het SWE-agent paper fixeert GPT-4 Turbo op de 300-task SWE-bench Lite-split en rapporteert 18,0% resolved met de volledige interface, tegenover 11,0% voor een shell-only agent met een worked demonstration en 7,3% voor dezelfde agent zonder demonstration. Het headlineverschil van 10,7 punten in het paper wordt gemeten tegenover die baseline van 7,3%; Part 3 werkt dezelfde drie cijfers uit vanuit het perspectief van interface design. Het paper wijzigde ook afzonderlijke interface features:

Deze cijfers horen bij dat model, die benchmark en de cap van $4 per task. De drie rijen onder de reference zijn de nuttige one-feature tests: in elke test werd één interface feature gewijzigd terwijl het model en de evaluation setup gelijk bleven.

LangChain publiceerde een bredere fixed-model comparison voor deepagents-cli. Daarin stijgt Terminal-Bench 2.0 van 52,8% naar 66,5% met gpt-5.2-codex fixed, terwijl het team de system prompt, tools en middleware wijzigde. De post bundelt meerdere wijzigingen en vermeldt geen confidence interval, fixed-total-budget comparison of per-change ablation table. Dat resultaat kan niet identificeren welke wijziging hielp. De modelnamen in deze sectie zijn de modellen die elk onderzoek destijds fixeerde; het protocol, niet de modellijst, is overdraagbaar.

Een nieuwere vergelijking laat zien waarom de API configuration bij de frozen baseline hoort. In zijn July 29, 2026 ARC-AGI-3 report rapporteert OpenAI dat GPT-5.6 Sol’s public-set score steeg van 13,3% naar 38,3% toen de harness reasoning behield en compaction gebruikte in plaats van reasoning te verwijderen en history af te kappen. De metric is Relative Human Action Efficiency, niet het percentage solved tasks. Dit is een vendor-reported, bundled comparison; hij isoleert de twee settings niet en stelt geen production effect size vast. Leg bij een upgrade de API, reasoning retention, compaction policy en budgets vast naast de model ID. Anders kan een schijnbare model regression een ontbrekende capability in de adapter zijn.

Neem provider intervention op in de failure suite. Een misalignment_policy_violation moet ook na streamed output een stop-and-review path bereiken; dit is geen transient retry case. Part 4 behandelt de API-dependent scope ervan. Test dat de harness dispatch stopt en reeds voltooide effects registreert.

Anthropic’s long-running application report is een kwalitatieve, productspecifieke case study en geen controlled benchmark. De applicatie is RetroForge, een 2D retro game maker; in Sprint 3 controleerde de harness evaluator 27 criteria voor de level editor. Het werk begon op eerdere Opus-modellen en toen Opus 4.6 verscheen, verwijderde het team harness-components één voor één om te zien welke door het nieuwere model overbodig waren geworden. Het report stelt dat evaluator calls overhead werden op tasks die Opus 4.6 betrouwbaar zelfstandig kon voltooien, maar nabij de grens van het model nog steeds hielpen. Het voorbeeld is een reden om oude scaffolding opnieuw te valideren wanneer het model verandert; het schat geen algemene effect size.

Houd de harness bewerkbaar nadat die zijn plaats heeft verdiend

Ablation houdt een harness klein, maar de code kan het model waarvoor die is afgesteld nog overleven. Een request zoals “mask secrets in every capture path” benoemt gedrag, geen file. In een production harness kan dat gedrag zich uitstrekken over execution stages en shared state. Voordat je het veilig kunt wijzigen, moet je elke implementation site vinden — en de coding agent waaraan je het werk delegeert moet dat ook doen.

Een preprint van Wang et al. uit 2026 introduceert het Harness Handbook, een research-stage approach om die code te vinden. Het paper noemt deze search behavior localization. Het handbook bouwt een behavior-centric map van de harness codebase. Static analysis, waarvoor geen model calls nodig zijn, extraheert een program graph, waarna een LLM de units in execution stages ordent.

De maintainer of coding agent begint met een system overview, opent de relevante execution stage en daalt af naar source-grounded entries voor een function of file. Een state register legt vast waar shared state tussen stages wordt geschreven en gelezen. Deze hierarchy houdt het overzicht klein en behoudt tegelijk een path naar de source.

Freshness is een afzonderlijke rule. De map is een navigation aid; live source bepaalt het behavior. Elke locator moet tegen de live repository resolven. Het handbook bevriest stale entries in plaats van te gokken, en elke non-empty diff resynchroniseert de entries die daardoor worden geraakt.

Het diagram comprimeert de modification loop: een behavior-only request daalt door de levels van het handbook, elke kandidaat-locator wordt tegen de live repository geverifieerd voordat het plan wordt geschreven en elke toegepaste diff resynchroniseert de map.

De Handbook evaluation vergelijkt matched arms op 30 requests per repository. Zij toont geen gelijke totale budgets, herhaalde stochastic trials of uncertainty estimates aan, en de gerapporteerde vergelijkingen sluiten missing outputs en planner errors uit. Zij illustreert daarom een deel van het bovenstaande protocol, niet het geheel. Er worden twee open-source harnesses behandeld: Terminus-2 (zes Python files) en de Codex monorepo (2.267 Rust files). In beide gevallen verkende een read-only planner powered by DeepSeek-V4-Pro de repository direct of via het handbook. Requests, repository, tool permissions en decoding waren in beide arms identiek. Drie judges (GPT-5.5, Opus 4.8, DeepSeek-V4-Pro) scoorden elk edit plan op localization, scope control en reasoning — merk op dat één judge hetzelfde model is als het model dat de plans produceerde. Een win betekent dat de quality score van de ene arm op een schaal van 0–100 minstens drie punten hoger was dan die van de andere; anders was die judge–request comparison een tie. De gerapporteerde rate is wins gedeeld door het aantal valid judge–request comparisons:

HarnessBaseline win rateHandbook-assisted win ratePlanner tokens
Terminus-2 (6 files)26.7%45.6%−8.6%
Codex monorepo (2,267 files)28.3%38.3%−12.7%

De handbook-assisted planner won in beide repositories vaker en gebruikte minder planner tokens. De voorwaarden blijven aan dat resultaat verbonden: drie LLM judges scoorden edit plans die door één planner model voor twee harnesses waren geproduceerd. Het onderzoek evalueerde plans, geen uitgevoerde diffs of production defect rates.

Probeer de methode in het companion lab

Het harness-demo project op commit 517353f3 is een kleine, deterministische oefening met 12 generieke synthetic tasks rond code changes zoals fix-parser-edge-case, split-large-module en wire-browser-test. Het implementeert de fictieve store-repository niet.

Elke task fixture declareert een difficulty plus vier boolean conditions: een flaky tool, lost progress, een gemiste implementation gap en ambiguous completion. De simulator leidt een vijfde condition af voor difficult tasks die ook een progress file nodig hebben: zonder context_reset bewaart compaction stale assumptions. Een deterministische grader markeert een task alleen als passed wanneer de geselecteerde configuration elke toepasselijke condition afhandelt. Er draait geen model of external service.

De commands beantwoorden verschillende vragen:

  • make check voert Ruff en zeven unit tests uit, inclusief de validator die elke ablation pair afwijst waarin meer dan één component wijzigt.
  • make run print een cumulative teaching matrix en daarna vijf geldige leave-one-component-out comparisons.
  • make failures benoemt voor elke gefaalde task de niet-afgehandelde condition. De volledige harness moet eindigen met all synthetic tasks pass.

Installeer eerst Git, make en uv. Clone het lab en selecteer de pinned revision; voer de commands daarna uit vanuit de repository root:

git clone https://github.com/slavadubrov/harness-demo.git
cd harness-demo
git checkout 517353f3a47541d66099983170fe90812b6ef23b
make check
make run
make failures

Het causale deel van make run ziet er zo uit:

component                 control  treatment  delta
retry_policy              8/12     12/12       +4
progress_handoff          7/12     12/12       +5
evaluator                 8/12     12/12       +4
fail_closed_acceptance    7/12     12/12       +5

Voor elke rij is de control de volledige configuration met één component verwijderd; de treatment herstelt alleen dat component. De eerdere cumulative matrix is nuttig voor oriëntatie, maar sommige aangrenzende rijen voegen meerdere components tegelijk toe en kunnen daarom geen oorzaak identificeren.

Het lab valideert elke gedeclareerde pair voordat die wordt uitgevoerd. De regression tests bevatten ook bewust een invalid pair die retry policy en evaluator tegelijk wijzigt; de validator wijst die af.

Het lab vergelijkt alle vijf component fields bij het valideren van een pair. Dit uitvoerbare fragment toont dezelfde guard op één geldige progress-handoff-pair:

from dataclasses import dataclass, fields

@dataclass(frozen=True)
class Config:
    progress_handoff: bool = False
    evaluator: bool = False
    retry_policy: bool = False
    fail_closed_acceptance: bool = False
    context_reset: bool = False

def changed_components(control: Config, treatment: Config) -> tuple[str, ...]:
    return tuple(
        field.name
        for field in fields(control)
        if getattr(control, field.name) != getattr(treatment, field.name)
    )

control = Config(progress_handoff=False, evaluator=True, retry_policy=True)
treatment = Config(progress_handoff=True, evaluator=True, retry_policy=True)
assert changed_components(control, treatment) == ("progress_handoff",)

Welke layer moet je openen wanneer een run fout gaat

De serie bewoog vanuit de reasoning loop naar buiten. Begin met de eerste failure die je ziet en onderzoek daarna het component dat verantwoordelijk is voor die taak. Een run kan meer dan één component omvatten:

Wat de run deedWaar de fix thuishoortDeel
Koos een slechte volgende stap terwijl de juiste informatie al beschikbaar wasReasoning loop of het model1
Herhaalde werk of verloor een beslissing die een uur eerder was genomenContext assembly en handoffs2
Kon de benodigde action niet uitdrukken of las een returned result verkeerdTool contract3
Deed iets waartoe het nooit in staat had mogen zijnPermission rules4
Verloor alles toen een worker midden in een call stierfSession, checkpoint, sandbox5
Verklaarde werk als geslaagd dat niet af wasAcceptance checks en traces6

Vier rijen wijzen naar harness code, terwijl rij 5 naar de runtime wijst. Instructions kunnen gedrag beïnvloeden, maar ze vervangen geen permission check, durable checkpoint of acceptance test.

Begin met één loop en één acceptance check

Ik zou een coding-agent harness starten met één capabel model, repository instructions, enkele narrow tools, een sandbox en één expliciete acceptance test. Ik zou tool calls, results, costs en die final test in één trace registreren, zodat de eerste bruikbare failures zichtbaar zijn zonder ze uit terminal logs en chat transcripts te moeten reconstrueren. Dit is een proposed baseline, geen bewijs uit een deployed system.

Voeg vanaf daar alleen toe wat een trace rechtvaardigt. Registreer wie elk component onderhoudt, hoeveel tokens of seconden het toevoegt en welke regression test het verwijderen ervan na een model upgrade zou rechtvaardigen.

Zes maanden later zou iemand die progress_handoff=True ziet, de gefaalde traces moeten kunnen vinden die het component rechtvaardigden, samen met de regression cases die het nog steeds behouden. De traces verklaren waarom het component bestaat; een actuele behavior map verklaart waar je eraan kunt werken.

Als je via een search hier bent gekomen, hebben de vijf voorgaande artikelen een systeem rond een reasoning loop opgebouwd:

  1. De loop kiest de volgende stap.
  2. Memory levert context en een echte Postgres checkpoint store bewaart die.
  3. Tool contracts definiëren actions en de result shapes die latere checks kunnen lezen.
  4. Security voegt de deny hook en stop-hook validator toe. Beide blijven in het voorbeeld schetsmatig, maar markeren de control points.
  5. De runtime houdt het process actief over sessions en failures heen.

De serie voegde ook een optioneel MCP server surface en een evaluator node toe die het draft report controleert voordat een human het ziet. Een proxy die de worker via credentials routeert, blijft een voorgestelde extension. Dit zijn gewone stukken code rond een model call. De router is om dezelfde reden harness code: hij kiest het reasoning pattern voordat de reasoning loop start.

Houd voor het volgende optionele assistance component de gefaalde trace, de acceptance rule en de comparison met dat component disabled bij elkaar. Laat het weg als je het voordeel niet kunt identificeren. Vereiste security- en acceptance constraints zijn niet afhankelijk van die vergelijking.
