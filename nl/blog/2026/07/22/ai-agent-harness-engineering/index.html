Harness engineering voor AI agents: control loops ontwerpen

Deel 6 van de serie Engineering the Agentic Stack

De reasoning loop van een agent kiest de volgende actie. Zijn harness levert context, valideert voorgestelde tool calls, autoriseert ze, dispatcht wat wordt geaccepteerd, legt de resultaten vast en bepaalt of de taak voltooid is.

Voor de eerste drie van die taken bestaat al een artikel. Memory levert de context, tool use definieert wat kan worden voorgesteld en security bepaalt wat wordt uitgevoerd. Ze verschenen als afzonderlijke posts omdat het afzonderlijke engineeringproblemen zijn. De keuze tussen Qdrant en pgvector heeft niets te maken met het schrijven van een PreToolUse deny rule.

Ze delen ook een specifiek moment: de kloof tussen het moment waarop het model een actie benoemt en het moment waarop de machine die uitvoert. Elk onderdeel beantwoordt een vraag over die kloof, en de harness is de code die de kloof lang genoeg openhoudt om alle drie de vragen te kunnen stellen.

Dit artikel behandelt wat na die drie onderdelen overblijft: bepalen of het afgeronde werk daadwerkelijk afgerond is, en aantonen dat elke control in de loop oplevert wat die kost. Deel 5 behandelde de runtime die het proces daaronder actief houdt.

Dit artikel is bedoeld voor engineers die coding-agent harnesses bouwen of reviewen en daarbij tool calls moeten autoriseren, voortgang moeten behouden en voltooiing moeten aantonen.

Aan het einde moet je elke control kunnen plaatsen, acceptance evidence onafhankelijk kunnen houden van het model dat de actie voorstelt, retries voor side effects kunnen beveiligen en één component tegelijk kunnen meten.

TL;DR: Begin met één model, enkele smalle tools en een expliciete acceptance check. Voeg retries toe nadat traces transient call failures laten zien. Voeg een progress handoff toe wanneer hervatte sessions werk herhalen. Houd bij het testen van beide de modelversie, taken, grader en het totale budget gelijk. Verwijder de component wanneer die het gemeten resultaat niet verbetert.

Na de eerste expliciete acceptance check is elke extra retry, handoff of evaluator een hypothese over een geobserveerde failure. De component verdient alleen een plaats wanneer een gecontroleerde vergelijking aantoont dat die helpt.

Wat de harness beheert

OpenAI’s Codex loop walkthrough beschrijft de basiscyclus. De harness stelt een prompt samen, vraagt het model om de volgende actie, stuurt een geaccepteerde tool call naar de runtime en voegt het resultaat toe. Daarna vraagt de harness het opnieuw. Dit wordt herhaald totdat de harness het resultaat accepteert of de control teruggeeft aan de gebruiker.

Implementaties kunnen verschillende verantwoordelijkheden in één proces combineren. De failure boundaries blijven echter verschillend:

De runtime-row omvat vier zaken: session, sandbox, checkpoint en trace. Alle vier slaan state op of begrenzen de uitvoering. Het model stelt de actie voor en de reasoning loop kiest de volgende stap. De harness beslist of een voorgestelde call mag worden uitgevoerd en of de evidence voldoende is om af te ronden. Daarom krijgt de harness een eigen artikel. Deel 5 telt de harness samen met die vier andere onderdelen als een van de vijf primitives die je vóór shipping moet plaatsen; dit artikel haalt de harness er weer afzonderlijk uit.

Wanneer een failure optreedt, diagnoseer je de boundary die erop moet reageren. Een slecht plan kan betere instructies of betere model reasoning vereisen. Als edit_file een path buiten src/ target, moet de harness die call weigeren. Een sandboxproces dat stopt voordat de edit wordt uitgevoerd, hoort bij de runtime; die moet de worker herstarten of de crash rapporteren.

Volg de discount change van voorstel tot acceptatie

Voor de hierboven gedefinieerde discount task stelt het model voor om calculate_discount in src/checkout.py te wijzigen. Voordat die edit als progress telt, gebeuren er verschillende dingen:

  1. De context builder levert de taak, repository instructions, relevante bestanden, eerdere tool results en het huidige plan.
  2. Het model stelt een edit_file call voor met een path en replacement text.
  3. De tool boundary (de harness-code tussen proposal en execution) valideert de arguments, controleert het path tegen de toegestane scope en vraagt om approval wanneer de operatie dat vereist.
  4. De runtime past de edit toe in de sandbox en retourneert een structured result.
  5. De harness voert pytest tests/test_checkout.py uit, gevolgd door pnpm playwright test tests/checkout_discount.spec.ts, en leest beide exit codes. De browser test controleert de zichtbare korting van $8 op de seeded cart van $80.
  6. De harness bepaalt wat de resultaten betekenen. Een gefaalde check wordt nieuwe context voor de volgende model turn; een geslaagde run maakt de taak eligible for completion.
  7. Een geslaagd resultaat wordt pas completion evidence wanneer de harness het command, de exit code en de versie van het geteste artifact in de trace heeft vastgelegd.

Na stap 2 is er nog geen bestand gewijzigd. De harness kan ../../secrets.env weigeren, approval vereisen voor een destructive command of een run stoppen die zijn budget heeft uitgeput. Dat is het laatste goedkope moment dat je krijgt. Nadat de tests zijn uitgevoerd, leest de harness zelf hun exit codes. Het model kan zijn eigen edit niet als geslaagd markeren.

De trace moet het voorgestelde path en de replacement text tonen, de permission decision, de gewijzigde bestanden, de geteste commit en de resultaten van beide commands. Een finale done-message zonder die records bewijst niet dat deze wijziging de vereiste checks heeft doorstaan.

Tool contracts scheiden voorstel en permission

De discount task heeft alleen file edits en test commands nodig. Een state-changing API heeft een ander failure mode, dus voor deze sectie wisselen we van voorbeeld. Stel dat de agent create_test_order kan aanroepen tegen een staging order service tijdens het aanmaken van test data. Deze tool is geen acceptance check van de discount task. Het voorbeeld is hier nuttig omdat een timeout kan verhullen of de service een order heeft aangemaakt.

De tool boundary heeft meer nodig dan een beschrijving in natuurlijke taal. Er is een expliciet tool contract nodig. Deel 3 bepleitte dat vanuit het perspectief van het model: duidelijke acties, compacte feedback en recoverable errors. De harness heeft om een andere reden hetzelfde contract nodig. De harness moet zonder het model te vragen kunnen beslissen of een call mag worden uitgevoerd en of een gefaalde call mag worden herhaald. Voor create_test_order betekent dat een contract met:

  • gevalideerde arguments, zodat malformed input vóór execution wordt afgewezen
  • een structured result zoals { "order_id": "123", "created": true }, zodat latere checks geen free-form text hoeven te parsen
  • een effect category die vastlegt of de call alleen informatie ophaalt of een bestand, database record of external service wijzigt. De category legt ook vast of het veilig is de call te herhalen. Dit label vertelt de harness of een automatic retry werk kan dupliceren. De harness kan get_order_status opnieuw proberen wanneer de service die lookup als read-only definieert. De harness mag create_test_order niet blind opnieuw proberen, omdat de eerste call de order al kan hebben aangemaakt
  • een timeout- en retry policy, zodat een verloren response geen onbeperkte reeks calls triggert
  • een permission rule die aangeeft welke approval nodig is. Het lezen van order status mag automatisch gebeuren, terwijl het aanmaken van een order confirmation kan vereisen

De beschrijving in natuurlijke taal is tekst die aan het model wordt getoond. Die kan luiden: “Create a test order for checkout verification.” Die zin helpt het model bepalen wanneer het create_test_order moet voorstellen. De zin autoriseert de call niet. In dit voorbeeld valideert de Model Context Protocol (MCP)-client van de harness de arguments, past hij zijn eigen regels toe en controleert hij server trust, approval requirements en retry safety voordat er iets wordt gedispatched. Dat is de ordered deny/ask/hook/allow ladder uit Deel 4, met één extra vraag: of een call die al is gefaald opnieuw mag worden verstuurd.

Een MCP-server publiceert tool descriptions en optionele behavior annotations naar de client. Een defecte of malicious server kan een state-changing tool als harmless beschrijven. Een client die die claim automatisch accepteert, kan create_test_order zonder approval uitvoeren of retryen en een duplicate creëren. De MCP-specificatie vereist daarom dat clients tool annotations als untrusted behandelen, tenzij de server zelf trusted is.

De specificatie schrijft geen universele trust setting voor. Je hebt daarom een expliciet trust policy nodig voor je deployment; een server kan zijn eigen annotations niet trustworthy maken. Die policy bepaalt welke metadata invloed mag hebben op permission- of retry-decisions en welke annotations alleen advisory blijven.

Voor het retryen van een state-changing call is replay protection nodig

Deel 5 plaatst een idempotency key op elke tool call met side effects. De harness bepaalt wanneer die key het verschil moet maken. create_test_order maakt de order aan, maar de HTTP-response gaat verloren. De harness ziet een timeout en kan niet bepalen of de server de request heeft voltooid. De call opnieuw uitvoeren kan een tweede order creëren.

Een status lookup kan worden geretryd wanneer de service die als read-only definieert. Een creation call heeft de key nodig: de client voegt een unieke request identifier toe en de service retourneert het eerste resultaat in plaats van opnieuw een order aan te maken wanneer die identifier opnieuw wordt gezien. Zonder deze bescherming moet de harness controleren of de order bestaat of om een human decision vragen voordat er een nieuwe poging wordt gedaan. AWS documenteert dit patroon in zijn idempotent API guidance.

Acceptance vereist onafhankelijke evidence

Een succesvolle response van create_test_order toont alleen aan dat de tool data heeft geretourneerd. Het bewijst niet dat een coding task de tests heeft doorstaan. Als een latere browser test afhankelijk is van de staged order, moet de harness het response schema valideren en die test alsnog uitvoeren voordat de codewijziging wordt geaccepteerd.

Sommige criteria kunnen niet tot een exit code worden gereduceerd. Voor een afzonderlijke visual-design task kan een fresh-context evaluator een gerenderde pagina of diagram vergelijken met een geschreven rubric — “fresh-context” betekent hier een tweede model session die zonder history van de run start en de geproduceerde artifacts leest in plaats van het transcript. Vergelijk die evaluator met human reviews voordat je hem completion laat gaten.

Een payment-adaptermigratie vereist een handoff

Wissel opnieuw van taak, maar blijf in de fictieve store-repository. De agent moet checkout nu migreren van payment adapter v1 naar v2. Het werk omvat de checkout handler, payment client, configuration en tests en kan daardoor langer duren dan één model session — één doorlopende periode van model context, beëindigd door een restart of een bewuste fresh start in plaats van voortgezet.

Voordat de eerste session de limiet van zijn context bereikt, heeft die meerdere bestanden gewijzigd, een lokale payment sandbox gestart en tests/payment_migration.spec.ts failing achtergelaten. Die browser acceptance test voert één payment uit via adapter v2 en verifieert de geregistreerde provider ID. Een conversation summary kan de volgende model session oriënteren, maar kan de sandbox niet herstarten en niet bewijzen welke bestanden momenteel gewijzigd zijn.

De volgende session moet drie zaken herstellen:

Compaction vervangt oudere messages door een kortere summary, zodat de huidige session kan doorgaan. Een progress handoff legt vast wat de volgende session nodig heeft: de huidige branch, gewijzigde bestanden, het laatste test command en de output daarvan, plus de volgende onopgeloste stap.

Een handoff-file is document memory, geschreven voor één lezer — de volgende model session — en is een ander artifact dan de checkpoint die de runtime herstelt. De checkpoint beantwoordt waar de execution is gestopt. De handoff beantwoordt wat het werk betekent en wat nog rest. Herstel een checkpoint zonder handoff en de volgende session krijgt een resumable process, maar geen idee welke van de vier aangeraakte gebieden — handler, client, configuration, tests — al is afgerond. Dat veroorzaakt duplicate work.

Als de oude conversation stale assumptions bevat, kan de harness een nieuwe model session starten met die handoff en de huidige workspace. Het vervangen van een gecrashte worker en het herstellen van diens processen is een afzonderlijke runtime-recoverytaak.

Een kleine documentation edit heeft mogelijk geen van deze mechanismen nodig. De payment migration heeft een handoff nodig zodra het werk sessions overschrijdt, omdat de volgende model session zowel de workspace als de task status moet reconstrueren.

Anthropic’s experimenten met long-running coding agents gebruikten git history en een progress file tussen sessions. Anthropic’s latere harness-design report scheidt compaction van een fresh-context handoff en rapporteert dat handoffs orchestration, token use en wall time toevoegen, zonder cijfers te publiceren die een van die overheads specifiek aan de handoff toeschrijven.

Meet één wijziging tegelijk

Een ablation meet of een harness-component het verwachte effect veroorzaakt door die component te wijzigen of te verwijderen terwijl de rest van het experiment gelijk blijft. Helpt editor linting bijvoorbeeld dit model op deze task suite?

Gebruik het volgende protocol:

  1. Freeze de modelversie, task instances, environment, grader en prompts buiten de component die wordt getest.
  2. Geef beide varianten hetzelfde totale token-, tijd- en dollarbudget.
  3. Kies het aantal trials of de stopping rule voordat je de vergelijking uitvoert.
  4. Voer in beide varianten dezelfde task instances uit. Omdat model outputs variëren, herhaal je elke taak meerdere keren.
  5. Rapporteer het gemiddelde samen met de spreiding of confidence interval.
  6. Tel elke gestarte trial mee, inclusief timeouts, policy stops, harness crashes en evaluator failures.

Alleen success rate kan een dure component verhullen. Houd minimaal bij: broken tasks die als complete worden geaccepteerd, cost en wall time per completed task, tool errors, duplicate orders, review minutes en manual permission overrides. Kies de metric die de echte cost voor je product draagt. Een stijging van twee procentpunten in completed tasks is een slechte trade als daardoor je review queue verdubbelt.

Een paired payment-migration experiment maakt de progress handoff meetbaar. Elk control/treatment-paar start vanaf dezelfde repository commit en seeded checkpoint, met hetzelfde model, dezelfde taak, grader en hetzelfde totale budget. De handoff is de enige switch. De primary metric telt duplicate tool actions na resume: een action is duplicate wanneer de operation en het artifact overeenkomen met een stap die de vorige session al had voltooid.

Houd de harness bewerkbaar nadat die haar plaats heeft verdiend

Ablation houdt een harness klein, maar de code kan het model overleven waarvoor die is getuned. Een verzoek zoals “mask secrets in every capture path” benoemt gedrag, geen bestand. In een production harness kan dat gedrag zich over execution stages en shared state uitstrekken. Voordat je het veilig kunt wijzigen, moet je elke implementation site vinden — en hetzelfde geldt voor de coding agent waaraan je dit delegeert.

Een preprint uit 2026 van Wang et al., het Harness Handbook, noemt deze zoektocht behavior localization. Het handbook bouwt een behavior-centric map van de harness codebase. Static analysis, waarvoor geen model calls nodig zijn, extraheert een program graph. Vervolgens organiseert een LLM de units daarvan in execution stages.

De maintainer of coding agent begint met een system overview, opent de relevante execution stage en daalt af naar source-grounded entries voor een function of file. Een state register legt vast waar shared state tussen stages wordt geschreven en gelezen. Deze hiërarchie houdt het overzicht klein en behoudt tegelijk een path naar de source.

Freshness is een afzonderlijke regel. Elke locator moet resolven tegen de live repository. Het handbook bevriest stale entries in plaats van te gokken, en elke non-empty diff synchroniseert de entries die daardoor worden geraakt opnieuw.

Het diagram comprimeert de modification loop: een behavior-only request daalt door de niveaus van het handbook, elke kandidaat-locator wordt tegen de live repository geverifieerd voordat het plan wordt geschreven en elke toegepaste diff synchroniseert de map opnieuw.

De Handbook evaluation volgt het protocol waarvoor dit artikel pleit. De evaluatie omvat twee open-source harnesses: Terminus-2 (zes Python-bestanden) en de Codex-monorepo (2.267 Rust-bestanden). In beide gevallen verkende een read-only planner, aangedreven door DeepSeek-V4-Pro, de repository rechtstreeks of routeerde via het handbook. Requests, repository, tool permissions en decoding waren in beide arms identiek. Drie judges (GPT-5.5, Opus 4.8, DeepSeek-V4-Pro) scoorden elk edit plan op localization, scope control en reasoning — let op: één judge is hetzelfde model dat de plans produceerde:

HarnessBaseline win rateHandbook-assistedPlanner tokens
Terminus-2 (6 files)26.7%45.6%−8.6%
Codex monorepo (2,267 files)28.3%38.3%−12.7%

De handbook-assisted planner won in beide repositories vaker en gebruikte minder planner tokens. De voorwaarden blijven aan dat resultaat verbonden: drie LLM judges scoorden edit plans die door één planner model op twee harnesses waren geproduceerd. De studie evalueerde plans, geen uitgevoerde diffs of production defect rates.

Probeer de methode in het companion lab

Het harness-demo project op commit 517353f3 is een kleine, deterministische oefening met 12 generieke synthetic tasks die code changes behandelen zoals fix-parser-edge-case, split-large-module en wire-browser-test. Het implementeert de fictieve store-repository niet.

Elke task fixture definieert een difficulty en vier boolean conditions: een flaky tool, lost progress, een gemiste implementation gap en ambiguous completion. De simulator leidt een vijfde condition af voor moeilijke tasks die ook een progress file nodig hebben: zonder context_reset behoudt compaction stale assumptions. Een deterministic grader markeert een task alleen als passed wanneer de geselecteerde configuratie elke toepasselijke condition afhandelt. Er draait geen model of external service.

De commands beantwoorden verschillende vragen:

  • make check voert Ruff en zeven unit tests uit, waaronder de validator die elk ablation pair afwijst dat meer dan één component wijzigt.
  • make run print een cumulative teaching matrix en vervolgens vijf geldige leave-one-component-out comparisons.
  • make failures benoemt de unhandled condition voor elke gefaalde task. De volledige harness moet eindigen met all synthetic tasks pass.

make run
make failures

De causal section van make run ziet er als volgt uit:

Voor elke row is de control de volledige configuratie met één component verwijderd; de treatment herstelt alleen die component. De eerdere cumulative matrix is nuttig ter oriëntatie, maar sommige aangrenzende rows voegen meerdere componenten tegelijk toe en kunnen daarom geen oorzaak identificeren.

Het lab valideert elk gedeclareerd pair voordat het wordt uitgevoerd. De regression tests bevatten ook een opzettelijk ongeldig pair dat tegelijk de retry policy en evaluator wijzigt; de validator wijst dat af.

Het lab vergelijkt alle vijf component fields wanneer het een pair valideert. Dit runnable excerpt toont dezelfde guard voor één geldig progress-handoff-pair:

from dataclasses import dataclass, fields


@dataclass(frozen=True)
class Config:
    progress_handoff: bool = False
    evaluator: bool = False
    retry_policy: bool = False
    fail_closed_acceptance: bool = False
    context_reset: bool = False


def changed_components(control: Config, treatment: Config) -> tuple[str, ...]:
    return tuple(
        field.name
        for field in fields(control)
        if getattr(control, field.name) != getattr(treatment, field.name)
    )


control = Config(progress_handoff=False, evaluator=True, retry_policy=True)
treatment = Config(progress_handoff=True, evaluator=True, retry_policy=True)
assert changed_components(control, treatment) == ("progress_handoff",)

Welke layer open je wanneer een run misgaat?

De serie liep van inner naar outer, en hier betaalt die volgorde zich uit. Een failing agent run heeft meestal één owner:

Wat de run deedWaar de fix thuishoortDeel
Koos een slechte volgende stap terwijl de juiste informatie al beschikbaar wasReasoning loop of model1
Herhaalde werk of verloor een beslissing die een uur eerder was genomenContext assembly en handoffs2
Kon de benodigde actie niet uitdrukken of las een returned result verkeerdTool contract3
Deed iets waartoe hij nooit in staat had mogen zijnPermission rules4
Verloor alles toen een worker midden in een call stierfSession, checkpoint, sandbox5
Verklaarde werk als geslaagd terwijl het niet af wasAcceptance checks en traces6

Vier van deze zes rows zijn harness-code. Row 5 is de runtime eronder en row 1 is de enige die een prompt nog kan beïnvloeden.

Begin met één loop en één acceptance check

Ik zou een coding-agent harness starten met één capable model, repository instructions, enkele smalle tools, een sandbox en één expliciete acceptance test. Ik zou tool calls, results, costs en die final test in één trace vastleggen, zodat de eerste nuttige failures zichtbaar zijn zonder ze te moeten reconstrueren uit terminal logs en chat transcripts. Dit is een voorgestelde baseline, geen evidence uit een deployed system.

Voeg daarna alleen toe wat een trace rechtvaardigt. Leg vast wie elke component onderhoudt, hoeveel tokens of seconden die toevoegt en welke regression test het verwijderen ervan na een model upgrade zou rechtvaardigen.

Zes maanden later moet iemand die progress_handoff=True ziet, de failed traces kunnen vinden die de component rechtvaardigden en de regression cases die hem nog steeds op zijn plaats houden. De traces verklaren waarom de component bestaat; een actuele behavior map verklaart waar je die moet aanpassen.

Als je via een search hier bent beland, hebben de vijf voorafgaande artikelen een systeem rond een reasoning loop opgebouwd:

  1. De loop kiest de volgende stap.
  2. Memory levert context en een echte Postgres checkpoint store bewaart die.
  3. Tool contracts definiëren acties en de result shapes die latere checks kunnen lezen.
  4. Security voegt de deny hook en stop-hook validator toe. Beide blijven in het voorbeeld schetsmatig, maar markeren de control points.
  5. De runtime houdt het proces actief over sessions en failures heen.

De serie voegde ook een MCP sidecar toe om te tonen waar tokens van data providers thuishoren en een evaluator node die het draft report controleert voordat een human het ziet. Dat zijn gewone stukken code rond een model call. De router is om dezelfde reden harness-code: die kiest het reasoning pattern voordat de reasoning loop start.

Je volgende stap is het instrumenteren van één kleine loop. Leg tool calls, results, costs en één expliciete acceptance test vast. Voeg één control pas toe nadat een trace de failure toont die de control moet aanpakken. Vergelijk die met een fixed control en verwijder hem wanneer het gemeten voordeel verdwijnt.
