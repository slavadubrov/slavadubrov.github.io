AI-systemen meta-engineeren: van traces naar beter geheugen

Viacheslav Dubrov

2026-09-12 · Bijgewerkt 2026-09-12 · 23 min · AI-agenten

Automatische vertaling

Dit artikel is automatisch vertaald vanuit de oorspronkelijke Engelse versie.

Dit artikel opent Meta-Engineering AI Systems, een zesdelige gids voor closed-loop AI engineering: agents inzetten om failures te onderzoeken, wijzigingen te testen en de resultaten te gebruiken om AI-systemen te verbeteren.

Het gedrag van een AI-applicatie hangt van meer af dan alleen het model. Prompts, opgehaalde informatie, opgeslagen memory, tools en application code beïnvloeden allemaal wat er gebeurt. Wanneer een antwoord fout is, kunnen meerdere wijzigingen plausibel lijken. Het engineeringprobleem is bepalen welke wijziging helpt, wat die kost en wat die nog meer breekt.

Ik gebruik meta-engineering hier voor het ontwerpen van het verbeterproces zelf: welk bewijs de agent ziet, wat die mag wijzigen, hoe we voorstellen testen en wie beslist of we ze overnemen. Closed-loop beschrijft hoe dat proces leert van zijn experimenten. Elk resultaat beïnvloedt wat we daarna proberen of gebruiken, ook wanneer een voorgestelde wijziging faalt.

We kunnen dat werk in stappen automatiseren. Een persoon kan de exacte wijzigingen specificeren die getest moeten worden, een set toegestane alternatieven voor een zoekalgoritme definiëren of het volgende voorstel delegeren aan een LLM agent. De runner test elke candidate en bewaart bewijs voor de volgende beslissing. Deze serie richt zich op het integreren van agents in dat proces, terwijl execution, evaluation en adoption onder expliciete controle blijven.

De vraag die door alle zes delen loopt, is hoeveel van dit werk we aan een agent kunnen delegeren terwijl het bewijs en de beslissing om een wijziging over te nemen betrouwbaar blijven. We beginnen met het in kaart brengen van het volledige systeem en bouwen daarna een kleine werkende versie rond agent memory.

Wat de loop sluit

Er zijn twee verschillende loops om in het oog te houden. Binnen een agent-applicatie kiest de runtime loop een actie, roept een tool aan, observeert het resultaat en gaat verder met de huidige taak van de gebruiker. De improvement loop werkt over meerdere versies van die applicatie heen. Die onderzoekt gedrag uit voltooide runs en test wijzigingen die latere runs moeten verbeteren.

De improvement loop begint met evidence: een onjuist antwoord, een ongewenste state change, excessive cost of een andere observeerbare failure. Een trace legt de stappen achter die uitkomst vast. De proposer kiest een candidate, een specifieke versie van een wijziging. Een runner voert de candidate uit op gedefinieerde taken en een evaluator controleert het resulterende gedrag tegen de requirements. In het live experiment van dit artikel is een LLM agent de proposer:

Evaluation levert input voor een beslissing; evaluation autoriseert zichzelf niet. Iemand moet beslissen of het gemeten voordeel het overnemen van de wijziging rechtvaardigt, inclusief de gevolgen voor cost, permissions en ander vereist gedrag. In deze serie beginnen we met een human reviewer. De proposer kan een wijziging voorstellen, maar kan de checks niet herschrijven, zijn eigen budget niet verhogen en zichzelf geen approval geven.

Er zijn twee return paths. De experiment history voedt latere voorstellen, ook wanneer een candidate wordt afgewezen. Als een candidate wordt goedgekeurd en overgenomen, levert het gedrag ervan nieuwe evidence uit gebruik. Het is belangrijk dat een wijziging reversible blijft wanneer die evidence het oorspronkelijke experiment tegenspreekt. Een score registreren is slechts één stap; de loop is gesloten wanneer de evidence beïnvloedt wat we daarna proberen of gebruiken.

Wat wordt verbeterd, is de target. Dat kan een memory policy, retrieval pipeline, tool-selection code of het programma zijn dat de context van een model samenstelt. Model training is een andere mogelijke intervention. De loop kan werken met vaste model weights: de agent kan het omringende programma verbeteren zonder een model te trainen. Deze eerste demo bevat de outer LLM agent al. Latere delen versterken de evaluator en testen of agentic search zijn cost waard is ten opzichte van eenvoudigere methoden.

Kies hoeveel van de search je delegeert

Stel dat je al weet wat je wilt proberen: twee models vergelijken in een extraction step of memory thresholds testen van 0.6, 0.7 en 0.8. Je kunt die keuzes zelf aanleveren en execution, scoring en reporting automatiseren. Na het lezen van de resultaten kies je het volgende experiment. De feedback loop werkt ook al heeft het systeem de candidates niet zelf bedacht.

Ik gebruik vier werkmodi om die verdeling zichtbaar te maken. De figuur toont één manier om steeds meer experiment design te delegeren: begin met exacte modelkeuzes, laat het systeem settings en goedgekeurde componenten doorzoeken of vraag een agent om failures te onderzoeken en het volgende experiment te kiezen. De mens specificeert minder van elke poging, maar stelt nog steeds de regels voor de search vast.

De modenames beschrijven praktische arrangementen voor deze serie, geen industriestandaard voor autonomy levels. Wat mag veranderen en wie de wijziging kiest, zijn afzonderlijke beslissingen. Optuna’s search-space examples combineren modelkeuze met parameter ranges. Scikit-learn’s pipeline search vergelijkt alternatieve componenten via gewone grid search. Een component vervangen maakt het proces dus op zichzelf niet agentic. De breedtes in de figuur illustreren de werkverdeling in deze voorbeelden; het zijn geen gemeten aandelen van control of effort.

Agent-led investigation beschrijft hoe de volgende poging wordt gekozen. De agent leest failures en eerdere resultaten, stelt een wijziging voor en past zich na de test aan. Dit volgt het onderscheid in Anthropic’s workflow and agent patterns: een vooraf gedefinieerd proces kan execution automatiseren, terwijl een agent zijn volgende stappen stuurt op basis van feedback. Hybride methoden zijn ook mogelijk: DSPy’s MIPROv2 gebruikt een model om instructions voor te stellen en Bayesian optimization om combinaties daarvan te doorzoeken. Een vaste model comparison heeft geen LLM proposer nodig; de resultaten komen in de feedback loop terecht wanneer ze het volgende experiment of de volgende system version sturen.

Proposal, execution en adoption permissions blijven gescheiden. Een agent kan vóór elke run een wijziging opstellen ter goedkeuring of toegestane wijzigingen unattended testen terwijl een persoon de adoption beoordeelt. Ook een goedgekeurde componentenlijst heeft compatibele implementaties nodig; permission om een adapter te selecteren omvat niet de permission om er een te schrijven. In elke modus blijft de agent binnen de toegestane wijzigingen, vaste checks en het budget en kan die zichzelf geen deployment approval geven. Meer werk delegeren laat ook ruimte voor supervision: Anthropic’s study of deployed agents beschrijft hoe gebruikers verschuiven van het goedkeuren van individuele acties naar monitoring en intervention.

Alle modi kunnen dezelfde experiment ledger gebruiken: een record van elke geprobeerd wijziging. Bewaar de candidate en diens parent, de exacte wijziging en wie die heeft aangeleverd, de test- en environment-versies, het resultaat, de cost en eventuele failure of rejection. Met die history kan een mens het volgende voorstel aan een agent geven—or dat weer overnemen—zonder de evidence te verliezen. Scores uit verschillende testversies moeten nog steeds van elkaar worden onderscheiden.

Deze demo combineert configuration search met agent-led investigation. We definiëren vijf settings, de tests, het budget en de selection rule. De agent kiest values en de volgende hypothesis op basis van feedback; Python voert de tests automatisch uit. Human release review blijft afzonderlijk. De repository accepteert ook een candidate JSON die door een persoon via lab evaluate wordt aangeleverd. Model sweeps, component adapters en door agents geschreven code zijn bredere designopties voor latere delen, geen geïmplementeerde modi van deze memory-demo.

Waarom dit nu onderzoeken

Het feedbackprincipe is bekende engineering. Het recente werk dat mij interesseert, plaatst coding agents in het investigation- en experimentproces. Het geeft ons concrete implementaties om te onderzoeken, in plaats van ons te vragen aan te nemen dat autonomous improvement zal werken.

Karpathy’s autoresearch specificeert een compact experiment: wijzig een training program, voer dat uit onder een vaste training-time budget, inspecteer het validation result en registreer of de poging is behouden, verworpen of gecrasht. De instructions scheiden het bewerkbare training file van de vaste evaluation code. Die scheiding maakt het voorgestelde werk en het succescriterium inspecteerbaar.

Meta-Harness, een preprint uit maart 2026, onderzoekt een andere target: de code die bepaalt welke informatie een LLM-applicatie opslaat, ophaalt en aan zijn model presenteert. De proposer kan via een filesystem de source, scores en execution traces van eerdere candidates inspecteren. Experiment history wordt working material voor de volgende investigation.

Deze projecten motiveren de engineeringvraag van de serie: wat moet het omringende systeem doen zodra een agent investigations kan uitvoeren en wijzigingen kan voorstellen, zodat die experimenten nuttig worden? Meer attempts bewijzen op zichzelf geen betere beslissingen. Een zwakke evaluator kan een schadelijke wijziging belonen en een searchproces kan die zwakte herhaaldelijk uitbuiten. We testen de waarde van agentic proposals tegen eenvoudigere alternatieven, in plaats van een voordeel aan te nemen.

Geef de outer agent een kleine, inspecteerbare target

Stel je een assistant voor die de accountgegevens van Ada onthoudt. Op 1 januari leert die dat ze in Berlijn woont. Op 3 januari leert die over een verhuizing naar Parijs die op 10 januari ingaat. Wanneer op 5 januari naar haar stad wordt gevraagd, antwoordt die Parijs.

De memory bevat beide facts. De retrieval rule geeft de voorkeur aan de meest recent ontvangen fact zonder te controleren wanneer die geldig wordt. Dat is een concrete failure die een improvement agent kan onderzoeken.

De target is bewust alleen een memory tool, geen complete assistant. De tool ontvangt voorbereide facts, slaat ze op of weigert ze en haalt een value op voor een vraag. De writer, date handling, retrieval en answer selection zijn gewone Python. Conversation extraction en natural-language answer generation laten we buiten dit experiment, zodat we kunnen vaststellen wat een regelwijziging precies heeft gedaan.

De LLM bevindt zich in de outer loop van het Python-experiment. De agent ontvangt testresultaten, beslist welke settings moeten veranderen en krijgt het volgende resultaat terug. De geregistreerde campaigns gebruiken een echt model om die wijzigingen te kiezen.

Door deze verdeling kunnen we de engineeringloop testen zonder een tweede bron van modelgedrag in de memory tool te introduceren. In een grotere applicatie zouden beide loops models kunnen gebruiken. Hier is één LLM voldoende om het improvementproces agentic te maken. Een andere LLM kan dezelfde proposer-rol invullen; diens proposals moeten hetzelfde schema volgen en dezelfde checks doorstaan.

Begrijp één test voordat je de score leest

Een scenario is één compleet testverhaal. Een event is één actie die naar de memory tool wordt gestuurd: write, query of delete. Het scenario met de toekomstige verhuizing heeft vier events:

  1. Sla city = Berlin op, geldig vanaf 1 januari.
  2. Sla city = Paris op, ontvangen op 3 januari maar geldig vanaf 10 januari.
  3. Vraag op 5 januari naar de stad. Verwacht Berlijn.
  4. Vraag op 12 januari naar de stad. Verwacht Parijs.

De inputs zijn al structured. Het Parijs-fact identificeert bijvoorbeeld de owner (north workspace, user ada), subject (account), property (city), value (Paris) en effective date. De strings Berlijn en Parijs komen uit de testdata, niet uit een model dat memories uit conversation genereert.

Confidence is een supplied score die wordt gebruikt om te beslissen of een voorgesteld fact moet worden opgeslagen. De writer vergelijkt die met min_confidence. Een voorstel van delivery = courier met score 0.4 wordt bij de baseline threshold van 0.7 verworpen, maar bij een threshold van 0.2 opgeslagen. De test author levert de score aan; het is geen gemeten probability dat het voorstel correct is. We evalueren hoe de storage rule met die scores omgaat, niet of een model ze betrouwbaar kan schatten.

Elk scenario begint met een lege Python list met memory records. Geaccepteerde updates sluiten de validity period van de vorige value af en voegen een nieuw record toe. Na de twee city writes beschrijven de records het volgende:

ValueReceivedValid fromValid until
BerlinJanuary 1January 1January 10, excluded
ParisJanuary 3January 10No end date

De answer function retourneert het eerste retrieved record dat overeenkomt met de requested property. De evaluator vergelijkt die value met het expected answer. Een compleet scenario slaagt alleen als elk antwoord correct is en elke toepasselijke data-rule check slaagt. Deletion, owner isolation en prohibited writes hebben naast answer quality expliciete checks.

De tests leveren owner IDs direct aan; deze demo heeft geen authentication system. Een echte service moet die IDs uit de authenticated request halen. Een input die expliciet als instruction is gelabeld afwijzen, toont ook niet aan dat instructions in gewone tekst worden gedetecteerd.

Geef memory ook een schema

De facts hebben hun eigen regels nodig. Ik gebruik Schema-Guided Agent Memory (SGAM) voor het pattern waarin schemas de opgeslagen state en diens lifecycle beheersen. Hier demonstreren we een klein deel daarvan: typed facts, ownership, source references, validity intervals en deletion. Het latere SGR-schema bepaalt wat de outer agent mag voorstellen; dit memory-schema bepaalt wat de tool mag opslaan.

Het Parijs-record na de tweede write bevat:

{
    "tenant": "north",
    "user": "ada",
    "entity": "account",
    "key": "city",
    "value": "Paris",
    "confidence": 0.95,
    "source": "user",
    "valid_from": "2026-01-10",
    "schema_version": 1,
    "memory_type": "fact",
    "id": "m002",
    "source_event_id": "future-move:event-2",
    "observed_at": "2026-01-03",
    "valid_to": null,
    "supersedes_memory_id": "m001"
}

source_event_id verwijst naar het event dat Parijs heeft aangeleverd. supersedes_memory_id koppelt Parijs aan het Berlijn-record, m001. schema_version: 1 identificeert het recordformat; het betekent niet dat het programma oude data automatisch kan migreren.

MemoryRecord en Memory.write() handhaven dat format. Ontbrekende source references, ongeldige dates en malformed fields worden afgewezen voordat de stored history verandert. Een closed interval moet eindigen na het begin. Berlijn kan eindigen op 10 januari terwijl Parijs die dag begint; geen van beide records heeft een empty interval.

Stel dat de volgende write zegt Rome, eveneens geldig vanaf 10 januari. De writer wijst dat conflict af en laat Parijs ongewijzigd. Een tweede Parijs-fact voor dezelfde datum hergebruikt het record eenvoudig. Een update met een eerdere effective date wordt eveneens afgewezen: deze kleine writer reconstrueert geen late-arriving history. Dit zijn vaste policies die de outer agent niet kan wijzigen. De deduplicate setting bepaalt hoeveel herhaalde confirmations met een latere effective date worden toegestaan.

De baseline negeert bij het lezen nog steeds bewust subject- en date-filters. De tool slaat geldige records op, maar kan de verkeerde kiezen. Dat is de fault die we de agent geven om te repareren. Owner isolation geldt voor elke configuration en deletion verwijdert alle versions van de requested property binnen het subject van die owner.

Dit is een in-memory demonstration van die SGAM-regels. Er is geen durable database, retention service of migration system. Afzonderlijke writer regression tests controleren rejected writes en interval boundaries; het zijn geen extra scenarios in de score van de 20-story campaign.

Laat de agent een wijziging kiezen

Een campaign is één poging om de oorspronkelijke configuration te verbeteren, die begint met verse agent history. Een iteration is één call waarin de agent een wijziging voorstelt of besluit te stoppen. De volgende iteration ontvangt feedback uit eerdere iterations.

De campaign begint door alleen de baseline uit te voeren. Die slaagt voor 13 van 20 scenarios. Daarna geven we de agent:

  • de huidige settings en hun betekenissen;
  • de measurements van de baseline;
  • traces van failing scenarios, rejected writes en duplicate confirmations;
  • de wijzigingen die de agent mag voorstellen;
  • eerdere proposals en hun resultaten, wanneer die er zijn.

De eerste request bevat geen kant-en-klare improved configurations. De repository bevat ook vier handmatig voorbereide configurations om memory-mechanics uit te leggen, maar de live agent begint niet met die answers.

De agent kan vijf settings in de bestaande tool wijzigen:

SettingWat een wijziging doet
min_confidenceWijzigt de minimale supplied score die nodig is om een fact op te slaan.
filter_entityBeperkt retrieval tot het requested subject, zoals home in plaats van work.
time_awareBeperkt retrieval tot facts die geldig zijn op de requested date.
deduplicateHergebruikt een identiek actief fact in plaats van een nieuwe confirmation op te slaan.
top_kStelt vast hoeveel records worden geselecteerd voordat de answer context wordt gepackt.

Een proposal mag maximaal twee settings wijzigen. Numerieke values hebben bounds: confidence van 0 tot 1 en top_k van 1 tot 8. Het contract registreert de toegestane configuration changes van de tool; het agent schema en de validator voegen de proposal rules toe.

De agent heeft in dit proces geen shell- of filesystem-tools. De agent kan Python, expected answers, owner isolation, deletion behavior, het memory schema, conflict handling, scoring, budgets of release authority niet bewerken. De output is data die Python kan accepteren of afwijzen. Dit is een klein configuration experiment, geen sandbox voor willekeurige code die door een agent wordt geschreven.

Maak van elk voorstel een SGR decision record

Ik gebruik Schema-Guided Reasoning om de decision inspecteerbaar te maken. Elke model response heeft dezelfde fields:

FieldWat de lezer moet kunnen inspecteren
observationsWelk supplied scenario en event ondersteunen de proposed change?
hypothesisWelke rule lijkt het probleem te veroorzaken?
predicted_effectWat zou moeten verbeteren wanneer we de change testen?
actionStelt de agent een change voor of stopt die?
patchWelke permitted settings moeten veranderen?

De OpenAI Responses request gebruikt een strict JSON Schema dat uit Pydantic models is gegenereerd. Objects wijzen extra fields af en elk patch field is required maar kan null zijn, wat betekent: “laat deze setting ongewijzigd.” Structured Outputs beperkt de response shape. Python controleert nog steeds of references bestaan, values zijn toegestaan en de proposed configuration niet al is getest.

Het schema bewijst de hypothesis niet en maakt de interne reasoning van het model niet zichtbaar. Dit zijn beknopte decision records die we aan de evidence kunnen toetsen.

In de eerste geregistreerde iteration identificeerde de agent cross-subject retrieval en facts die buiten hun validity interval werden geretourneerd. De werkelijke response stelde deze patch voor:

{
    "min_confidence": null,
    "filter_entity": true,
    "time_aware": true,
    "deduplicate": null,
    "top_k": null
}

Deze twee settings werden door het model gekozen. De runner leverde de parent ID aan en kende de candidate ID toe; het model kon de wijziging niet omleiden naar een willekeurige parent of file.

Volg de wijziging door Python

Zowel de baseline als de nieuwe configuration slaan dezelfde records voor Berlijn en Parijs op. De voorgestelde wijziging beïnvloedt welke records retrieval mag overwegen.

In Memory.query() activeren deze switches twee filters:

if self.config.filter_entity:
    eligible = [r for r in eligible if r["entity"] == event["entity"]]
if self.config.time_aware:
    eligible = [r for r in eligible if valid_at(r, event["as_of"])]

De validity check include’t de startdatum en sluit de einddatum uit:

def valid_at(item: dict, at: str) -> bool:
    return item["valid_from"] <= at and (
        item["valid_to"] is None or at < item["valid_to"]
    )

De dates gebruiken YYYY-MM-DD, dus hun string order komt overeen met hun calendar order. Voor de vraag van 5 januari wordt Parijs uitgesloten omdat het pas op 10 januari geldig wordt. Berlijn blijft beschikbaar. Voor de vraag van 12 januari is Parijs geldig en is Berlijn historical.

Python voert de proposed configuration uit op alle 20 stories. Deze eerste wijziging verbetert de success van 13/20 naar 19/20, waarbij alle geïmplementeerde hard checks slagen. De wijziging verandert twee filters tegelijk, dus de gain over de volledige suite meet hun gecombineerde effect. De city trace laat zien wat de date filter in dit specifieke geval deed.

De runner selecteert deze configuration als parent voor het volgende experiment. Die selection is geen deployment. Het model krijgt in de volgende request het gemeten resultaat, de geselecteerde settings en de resterende evidence terug.

De selection rule ligt vast: alle hard checks moeten slagen, betere complete-scenario success heeft de voorkeur en bij gelijke success heeft een kleiner aantal opgeslagen records de voorkeur. Een slechter resultaat laat de vorige parent staan. De tests oefenen dat rejection path ook uit met een scripted regressing proposal; dat was geen gemeten quality regression in deze drie live campaigns.

De response voldeed aan het JSON Schema, maar de reference identificeerde geen supplied event, dus Python wees die af vóór evaluation. De controller retourneert de rejected response en specifieke validation error als feedback; offline tests controleren dat gedrag. De drie hieronder gerapporteerde campaigns hadden geen validation failures.

Herhaal de search campaign, niet de deterministische test

Dezelfde memory configuration en inputs produceren dezelfde antwoorden. Die evaluation herhalen voegt geen evidence over answer quality toe. De runner controleert een nieuwe configuration één keer en hergebruikt geverifieerde parent results voor comparisons.

De outer agent kan verschillende proposals kiezen, dus we voerden drie onafhankelijke campaigns uit. Elke campaign begon op dezelfde 13/20-baseline, kreeg een verse history en had maximaal vier modelbeslissingen. Geen enkele campaign ontving de discoveries van een vorige campaign.

Alle drie campaigns kozen dezelfde sequence: beide retrieval filters activeren, confirmations dedupliceren, de confidence threshold verlagen naar 0.6 en vervolgens stoppen.

Er waren 12 model calls: negen proposals die Python evalueerde, gevolgd door drie stop decisions. Elke campaign voerde de baseline plus drie nieuwe configurations uit op 20 stories: 80 memory-tool executions per campaign. De 20 stories bleven de hele tijd gelijk.

Alle drie selecteerden dezelfde uiteindelijke settings. Dit is een kleine observatie van één model, prompt, target en publieke test suite. Het schat niet hoe betrouwbaar de optimizer onbekende systems zal verbeteren. Een sterkere comparison hoort later in de serie thuis: herhaalde campaigns met matched budgets, concurrerende proposalmethoden en tests die de proposer niet kan inspecteren.

Lees quality en cost op het juiste niveau

Het experiment heeft twee verschillende costs. Het uitvoeren van de memory tool gebruikt lokale CPU-tijd en maakt geen model calls. Het uitvoeren van de outer proposer gebruikt input- en output-tokens. Een provider-cost field van nul in een memory-evaluation report beschrijft alleen de inner tool; het is niet de cost van de campaign.

Voor de recorded study op 11 september 2026 gebruikten we GPT-5.6 Luna (gpt-5.6-luna), reasoning effort low, het opgeslagen SGR-schema en de bijbehorende instructions en maximaal 4.096 output-tokens per call. Het programma schakelde automatische SDK retries uit en stelde een request timeout van 60 seconden in. Exacte requests, geretourneerde model IDs, usage en call durations worden bewaard.

De token-based cost estimate voor de 12 model calls is USD 0.039177, tegenover een geconfigureerd budget van USD 0.50. De berekening gebruikt de gepubliceerde model rates, bevat de cache-write surcharge die in usage werd gerapporteerd en negeert cache-read discounts. Het is een conservatieve schatting op basis van recorded usage, geen invoice. Hardware en development time vallen buiten dat bedrag.

Vóór elke call reserveert de runner een upper estimate op basis van begrensde input size en het maximum aantal output-tokens. Als het resterende budget die reservation niet kan dekken, stopt de runner. Failed of interrupted calls blijven in het record; wanneer usage niet beschikbaar is, wordt het gereserveerde bedrag behouden en niet als nul behandeld.

Voor answer quality betekent 20/20 dat elk answer en elke toepasselijke hard check slaagde op deze 20 voorbereide stories. Het betekent geen production-ready memory. Alle stories zijn publieke development cases; geselecteerde traces en suite feedback zijn beschikbaar voor de proposer. Ze behandelen updates, historical questions, uncertainty, duplicates, distractors, owner separation, deletion en disallowed writes. De labels search, evaluation en adversarial organiseren de oorspronkelijke suite; ze maken geen van deze cases tot een hidden test set.

Deze kleine suite put inspiratie uit LongMemEval, MemoryAgentBench, VehicleMemBench en GateMem. De inputs en scoring zijn hier van onszelf; de resultaten reproduceren die benchmarks niet.

Je kunt ook vier handmatig voorbereide configurations in de repository vergelijken. Ze illustreren waarom meer facts accepteren answers kan verslechteren en hoe storage kan verbeteren zonder hogere answer quality. Ze tonen ook de human-specified kant van dezelfde experimentmachinery: de author levert de candidates aan en Python evalueert ze. Het zijn nuttige teaching comparisons, geen evidence dat agentic search beter is dan een competente human of een andere searchmethode.

Voer een verse agent campaign uit

Om de agent nieuwe proposals te laten kiezen, clone je de companion en download je de recorded evidence:

git clone --branch v0.2.2 --depth 1 https://github.com/slavadubrov/meta-engineering-ai-lab.git
cd meta-engineering-ai-lab
uv sync --frozen
uv run --frozen python scripts/fetch_evidence.py
uv run --frozen python -m lab verify artifacts/agent-study-03 --source

De download controleert SHA-256 en herstelt de volledige recordings onder artifacts/. Er worden geen model calls gemaakt. Als je de evidence al hebt gedownload, sla je die stap over en voer je de verification command uit.

Sla een OPENAI_API_KEY op in een lokaal .env.local-bestand. De repository negeert dat bestand. Voer daarna uit:

uv run --frozen --env-file .env.local python -m lab campaign \
  --live --campaigns 3 --iterations 4 --budget-usd 0.50 \
  --output artifacts/my-agent-study

--live schakelt provider calls expliciet in. Een key in de environment zorgt er niet voor dat de offline memory commands of de browser een live agent worden. --campaigns 3 creëert drie onafhankelijke agent histories; --iterations 4 beperkt het aantal decisions binnen elke history. Gebruik voor elke study een nieuwe output directory: bestaande evidence wordt nooit overschreven.

Open artifacts/my-agent-study/report.md voor de campaign outcomes en links naar elke request, response en Python evaluation. Vergelijk de voorgestelde wijzigingen met de hierboven geregistreerde campaign: de agent kan anders kiezen, ook al zijn de memory tests deterministisch.

De README brengt de code en commands in kaart. Het frozen campaign report en de archive checksum en example index stellen een lezer in staat de evidence van dit artikel direct te inspecteren.

Houd experiment history gescheiden van user memory

De memory tool slaat Ada’s stad en taal op. De experiment history slaat op wat de agent zag, de voorgestelde patch, eventuele rejection, de resulterende measurements en welke configuration de volgende parent werd. Deze stores dienen verschillende doelen.

Elke iteration bewaart de exacte request met instructions en schema, de provider response, usage en timing, de validation outcome en elke voltooide evaluation. Failed proposals blijven zichtbaar. File hashes koppelen de opgeslagen evidence aan de implementatie en inputs die voor het experiment zijn gebruikt.

Dit zijn synthetische facts, dus het publieke record kan volledige states bewaren. Echte traces hebben een afzonderlijk retention policy nodig: een fact uit de memory tool verwijderen wist eerdere copies uit experiment logs of backups niet. De deletion test van de demo controleert de records van de tool en latere reads, niet het wissen uit elke mogelijke store.

Wat het volgende artikel moet uitdagen

We hebben nu een agent in de improvement loop. Die stelt een wijziging voor, ontvangt een gemeten resultaat, kiest de volgende wijziging en kan besluiten te stoppen. Ongeldige proposals volgen een afzonderlijk rejection path en blijven in het record. De authority is beperkt tot configuration; testing en release review blijven afzonderlijke verantwoordelijkheden.

Het volgende risico is de evaluator zelf. Als success het bewaren van elk fact beloont, kan de agent leren om guesses te bewaren. Als een suite alleen naar de huidige stad vraagt, kan die een wijziging missen die nuttige history vernietigt. Een krachtigere proposer kan zwakke metingen efficiënter uitbuiten.

Deel 2, Maak het scorebaar voordat je het autonomous maakt, vraagt hoe we die metingen kunnen testen voordat we de proposer meer vrijheid geven. De 20/20 van de eerste campaign is het startpunt voor die investigation.
