Meta-engineering van AI-systemen: van traces naar betere memory

Viacheslav Dubrov

2026-09-12 · Bijgewerkt 2026-09-14 · 24 min · AI-agenten

Automatische vertaling

Dit artikel is automatisch vertaald vanuit de oorspronkelijke Engelse versie.

Dit artikel is bedoeld voor engineers die agents bouwen die failures onderzoeken, wijzigingen testen en de resultaten gebruiken om AI-systemen te verbeteren. Het is het eerste deel van Meta-Engineering AI Systems, een gids in zes delen over closed-loop AI engineering. In dit eerste deel bouw je rond een kleine memory tool een door een LLM aangestuurd improvement process en inspecteer je het bewijsmateriaal achter elke voorgestelde wijziging.

Het gedrag van een AI-applicatie hangt van meer af dan alleen het model. Prompts, opgehaalde informatie, opgeslagen memory, tools en application code beïnvloeden allemaal wat er gebeurt. Als een antwoord onjuist is, kunnen meerdere wijzigingen plausibel lijken. De engineeringopgave is bepalen welke wijziging helpt, wat die kost en wat die verder kapotmaakt.

Ik gebruik meta-engineering hier voor het ontwerpen van het improvement process zelf: welk bewijsmateriaal de agent ziet, wat die mag wijzigen, hoe we diens voorstellen testen en wie beslist of we een wijziging overnemen. Closed-loop beschrijft hoe dat proces leert van zijn experimenten. Elk resultaat bepaalt wat we daarna proberen of gebruiken, ook wanneer een voorgestelde wijziging faalt.

De centrale vraag in alle zes delen is hoeveel van dit werk we aan een agent kunnen delegeren en tegelijk het bewijsmateriaal en de beslissing om een wijziging over te nemen betrouwbaar kunnen houden. Om dat proces te ontwerpen, moeten we eerst onderscheid maken tussen wat we kunnen wijzigen en hoe we bepalen of een wijziging heeft geholpen.

Waar meta-engineering op optimaliseert

Prompt engineering wijzigt de instructies. Context engineering wijzigt welke informatie het model ontvangt. Loop engineering wijzigt hoe een agent handelt, resultaten observeert, retries uitvoert en stopt. Graph engineering wijzigt hoe stappen of agents met elkaar verbonden zijn en hoe werk wordt gerouteerd. Dit zijn overlappende ontwerpkeuzes binnen een AI-systeem.

Meta-engineering organiseert de experimenten die alle vier optimaliseren. Promptformulering, context assembly, loopconfiguratie en graphstructuur worden parameters die gecontroleerde experimenten kunnen variëren en meten. We beoordelen een wijziging op basis van de resultaten van het volledige systeem, inclusief kwaliteit, kosten en het vereiste gedrag. Graphstructuur blijft de moeite waard om te verbeteren; het experimentproces vertelt ons of een specifieke wijziging aan de graph helpt. Deze serie behandelt dat proces voor agent-systemen. Memory is het eerste uitgewerkte voorbeeld.

Wat de loop sluit

Het experimentproces in het diagram is de improvement loop. Die werkt over verschillende versies van een applicatie, onderzoekt voltooide runs en test wijzigingen die bedoeld zijn om latere runs te verbeteren. Binnen de applicatie kiest de runtime loop een actie, roept die een tool aan, observeert het resultaat en gaat verder met de huidige taak van de gebruiker. Loop engineering wijzigt dat runtimegedrag; meta-engineering test of de wijziging de resultaten van het systeem verbetert.

De improvement loop begint met bewijs: een onjuist antwoord, een ongewenste state change, buitensporige kosten of een andere waarneembare fout. Een trace legt de stappen achter die uitkomst vast. De proposer kiest een candidate, een specifieke versie van een wijziging. Een runner voert de candidate uit op gedefinieerde taken, en een evaluator controleert het resulterende gedrag aan de hand van de requirements. In het live experiment van dit artikel is een LLM-agent de proposer:

Evaluatie levert input voor een beslissing, maar autoriseert zichzelf niet. Iemand moet beslissen of het gemeten voordeel opweegt tegen het invoeren van de wijziging, inclusief de effecten op kosten, permissies en ander vereist gedrag. In deze serie beginnen we met een human reviewer. De proposer kan een wijziging voorstellen, maar kan de checks niet herschrijven, zijn eigen budget niet verhogen en zichzelf geen goedkeuring geven.

Er zijn twee return paths. De experimentgeschiedenis voedt latere voorstellen, ook wanneer een candidate wordt afgewezen. Als een candidate wordt goedgekeurd en overgenomen, levert het gedrag ervan nieuwe evidence uit het gebruik. Het is belangrijk dat een wijziging reversibel blijft wanneer die evidence in tegenspraak is met het oorspronkelijke experiment. Een score registreren is slechts één stap; de loop is rond wanneer de evidence verandert wat we vervolgens proberen of gebruiken.

Wat wordt verbeterd, is de target. Dat kan een memory policy, een retrieval pipeline, tool-selection code of het programma zijn dat de context van een model samenstelt. Model training is een andere mogelijke interventie. De loop kan werken met vaste modelgewichten: de agent kan het omringende programma verbeteren zonder een model te trainen. Deze eerste demo bevat de outer LLM-agent al. In latere delen versterken we de evaluator en testen we of agentic search de kosten waard is in vergelijking met eenvoudigere methoden.

Kies hoeveel van de search je wilt delegeren

Bepalen wat je wilt wijzigen staat los van bepalen wie het experiment ontwerpt. Elk van de vier bovenstaande ontwerpgebieden kan human-specified changes, automated search of agent-led investigation omvatten.

Stel dat je al weet wat je wilt proberen: vergelijk twee modellen in een extraction step of test de memory thresholds van 0.6, 0.7 en 0.8. Je kunt die keuzes zelf aanleveren en execution, scoring en reporting automatiseren. Na het lezen van de resultaten kies je het volgende experiment. De feedback loop werkt ook wanneer het systeem de candidates niet zelf heeft bedacht.

Ik gebruik vier working modes om die verdeling zichtbaar te maken. De figuur toont één manier om steeds meer van het experimentontwerp te delegeren: begin met exacte modelkeuzes, laat het systeem settings en goedgekeurde componenten doorzoeken, of vraag een agent om failures te onderzoeken en het volgende experiment te kiezen. De human specificeert minder van elke poging, maar bepaalt nog steeds de regels voor de search.

De modustypen beschrijven praktische opstellingen voor deze serie, niet een industriestandaard voor autonomieniveaus. Optuna’s voorbeelden van search spaces combineren modelkeuze met parameterbereiken. Scikit-learn’s pipeline search vergelijkt alternatieve componenten via een gewone grid search. Een component vervangen maakt het proces dus op zichzelf niet agentischer. De breedtes in de figuur illustreren de taakverdeling in deze voorbeelden; het zijn geen gemeten aandelen van controle of inspanning.

Agent-led investigation beschrijft hoe de volgende poging wordt gekozen. De agent leest failures en eerdere resultaten, stelt een wijziging voor en past zich na de test aan. Dit sluit aan bij het onderscheid in Anthropic’s workflow- en agentpatronen: een vooraf gedefinieerd proces kan de uitvoering automatiseren, terwijl een agent zijn volgende stappen op basis van feedback bepaalt. Hybride methoden zijn ook mogelijk: DSPy’s MIPROv2 gebruikt een model om instructies voor te stellen en Bayesian optimization om combinaties daarvan te doorzoeken. Voor een vaste modelvergelijking is geen LLM-proposer nodig; de resultaten komen in de feedbackloop terecht wanneer ze richting geven aan het volgende experiment of de volgende systeemversie.

Rechten voor voorstellen, uitvoering en adoptie blijven gescheiden. Een agent kan vóór elke run een wijziging ter goedkeuring opstellen, of toegestane wijzigingen unattended testen terwijl een persoon de adoptie beoordeelt. Een goedgekeurde lijst met componenten vereist nog steeds compatibele implementaties; toestemming om een adapter te selecteren omvat niet de toestemming om er een te schrijven. In elke modus blijft de agent binnen de toegestane wijzigingen, vaste checks en het budget, en kan hij zichzelf geen goedkeuring voor deployment geven. Meer werk delegeren laat bovendien ruimte voor toezicht: Anthropic’s onderzoek naar gedeployde agents beschrijft hoe gebruikers verschuiven van het goedkeuren van afzonderlijke acties naar monitoren en interveniëren.

Alle modi kunnen dezelfde experiment ledger gebruiken: een registratie van elke uitgeprobeerde wijziging. Leg de kandidaat en zijn parent vast, de exacte wijziging en wie die heeft aangeleverd, de versies van de tests en de omgeving, het resultaat, de kosten en eventuele failure of afwijzing. Dankzij die historie kan een mens het volgende voorstel aan een agent overdragen — of het weer overnemen — zonder het bewijsmateriaal kwijt te raken. Scores uit verschillende testversies moeten nog steeds van elkaar worden onderscheiden.

Deze demo combineert configuration search met agent-led investigation. We definiëren vijf instellingen, de tests, het budget en de selectieregel. De agent kiest waarden en de volgende hypothese op basis van feedback; Python voert de tests automatisch uit. Human release review blijft hiervan gescheiden. De repository accepteert ook een candidate JSON supplied by a person via lab evaluate. Model sweeps, component adapters en door agents geschreven code zijn bredere ontwerpopties voor latere onderdelen, geen geïmplementeerde modi van deze memory demo.

Waarom dit nu onderzoeken

Het feedbackprincipe is bekende engineeringpraktijk. Het recente werk dat mij interesseert, plaatst coding agents in het onderzoek- en experimenteerproces. Het geeft ons concrete implementaties om te onderzoeken, in plaats van ons te vragen aan te nemen dat autonome verbetering zal werken.

Karpathy’s autoresearch specificeert een compact experiment: pas een trainingsprogramma aan, voer het uit binnen een vast tijdsbudget, inspecteer het validatieresultaat en leg vast of de poging is behouden, verworpen of gecrasht. De instructies scheiden het bewerkbare trainingsbestand van de vaste evaluatiecode. Door die scheiding zijn het voorgestelde werk en het succescriterium inspecteerbaar.

Meta-Harness, een preprint uit maart 2026, richt zich op iets anders: de code die bepaalt welke informatie een LLM-applicatie opslaat, ophaalt en aan zijn model presenteert. De proposer kan via een filesystem de broncode, scores en execution traces van eerdere kandidaten inspecteren. De experimentgeschiedenis wordt zo werkmateriaal voor het volgende onderzoek.

Toegevoegd op 14 september 2026: De survey van Yi Duan en coauteurs, The Last AI Built by Humans: Toward Genuine Recursive Self-Improvement, is op 10 september ingediend, twee dagen vóór de publicatiedatum van dit artikel. De discussie over recursive meta-improvement beschrijft een systeem dat een improvement mechanism herziet en die herziening behoudt om latere rondes aan te sturen. Ik zie dit als verwant aan het bredere doel van deze serie: zowel agents die systemen verbeteren als het proces dat zij daarvoor gebruiken engineeren. Het levert ons ook een aanvullende onderzoeksvraag op: kan het systeem blijvende, geteste verbeteringen aanbrengen in dat proces zelf?

Voor deze serie is het praktisch gezien het belangrijkst om elk experiment betrouwbaar te maken. Meer pogingen leiden op zichzelf niet tot betere beslissingen. Een zwakke evaluator kan een schadelijke wijziging belonen, waarna een search process die zwakte herhaaldelijk kan uitbuiten. We zullen de waarde van agentic proposals toetsen aan eenvoudigere alternatieven, in plaats van zonder meer van een voordeel uit te gaan.

Geef de outer agent een klein, inspecteerbaar target

Stel je een assistant voor die de accountgegevens van Ada onthoudt. Op 1 januari leert hij dat ze in Berlijn woont. Op 3 januari leert hij dat ze gaat verhuizen naar Parijs, met ingang van 10 januari. Wanneer hem op 5 januari naar haar stad wordt gevraagd, antwoordt hij Parijs.

De memory bevat beide feiten. De retrieval rule geeft voorrang aan het feit dat het meest recent is ontvangen, zonder te controleren wanneer het geldig wordt. Dat is een concrete failure die een improvement agent kan onderzoeken.

Het target is bewust alleen een memory-tool, geen complete assistant. Hij ontvangt voorbereide feiten, slaat ze op of verwerpt ze, en haalt een waarde op voor een vraag. De writer, date handling, retrieval en answer selection zijn gewone Python. Conversation extraction en natural-language answer generation laten we buiten dit experiment, zodat we kunnen vaststellen wat een regelwijziging daadwerkelijk heeft gedaan.

De LLM zit in de outer loop van het Python-experiment. De agent ontvangt testresultaten, beslist welke settings moeten worden gewijzigd en krijgt vervolgens het volgende resultaat terug. De vastgelegde campaigns gebruiken een echt model om die wijzigingen te kiezen.

Met deze opsplitsing kunnen we de engineering loop testen zonder een tweede bron van modelgedrag in de memory tool te introduceren. In een grotere applicatie zouden beide loops modellen kunnen gebruiken. Hier volstaat één LLM om het verbeterproces agentic te maken. Een andere LLM kan dezelfde proposer-rol vervullen; de voorstellen moeten hetzelfde schema volgen en dezelfde checks doorstaan.

Begrijp één test voordat je de score leest

Een scenario is één volledig testverhaal. Een event is één actie die naar de memory tool wordt gestuurd: schrijven, query’en of verwijderen. Het scenario voor een toekomstige wijziging bevat vier events:

  1. Sla city = Berlin op, geldig vanaf 1 januari.
  2. Sla city = Paris op, ontvangen op 3 januari maar geldig vanaf 10 januari.
  3. Vraag op 5 januari naar de stad. Verwacht Berlijn.
  4. Vraag op 12 januari naar de stad. Verwacht Parijs.

De inputs zijn al gestructureerd. Het feit over Parijs identificeert bijvoorbeeld de owner (north workspace, user ada), het subject (account), de property (city), de value (Paris) en de effective date. De strings Berlin en Paris komen uit de testdata, niet uit een model dat memories uit een conversatie genereert.

Confidence is een meegeleverde score die bepaalt of een voorgesteld feit moet worden opgeslagen. De writer vergelijkt deze met min_confidence. Een voorstel van delivery = courier met score 0.4 wordt afgewezen bij de baselinedrempel van 0.7, maar opgeslagen bij een drempel van 0.2. De auteur van de test levert de score aan; het is geen gemeten waarschijnlijkheid dat het voorstel correct is. We evalueren hoe de storage rule met deze scores omgaat, niet of een model ze betrouwbaar kan inschatten.

Elk scenario start met een lege Python-list met memory records. Geaccepteerde updates sluiten de validity period van de vorige value af en voegen een nieuw record toe. Na de twee city writes beschrijven de records het volgende:

ValueReceivedValid fromValid until
BerlinJanuary 1January 1January 10, excluded
ParisJanuary 3January 10No end date

De answer function retourneert het eerste opgehaalde record dat overeenkomt met de opgevraagde property. De evaluator vergelijkt die value met het verwachte antwoord. Een volledig scenario slaagt alleen als elk antwoord correct is en elke toepasselijke data-rule-check slaagt. Deletion, owner isolation en prohibited writes hebben naast answer quality expliciete checks.

De tests leveren owner-ID’s rechtstreeks aan; deze demo heeft geen authentication system. Een echte service moet deze ID’s uit het geauthenticeerde request halen. Het expliciet afwijzen van een input die als instruction is gelabeld, toont bovendien niet aan dat instructions die in gewone tekst verborgen zitten worden gedetecteerd.

Geef memory ook een schema

De feiten hebben hun eigen regels nodig. Ik gebruik Schema-Guided Agent Memory (SGAM) voor het patroon waarin schema’s de opgeslagen state en de lifecycle ervan aansturen. Hier demonstreren we een klein deel daarvan: typed facts, ownership, source references, validity intervals en deletion. Het latere SGR-schema bepaalt wat de outer agent mag voorstellen; dit memory-schema bepaalt wat de tool mag opslaan.

Het Paris-record na de tweede write bevat:

{
    "tenant": "north",
    "user": "ada",
    "entity": "account",
    "key": "city",
    "value": "Paris",
    "confidence": 0.95,
    "source": "user",
    "valid_from": "2026-01-10",
    "schema_version": 1,
    "memory_type": "fact",
    "id": "m002",
    "source_event_id": "future-move:event-2",
    "observed_at": "2026-01-03",
    "valid_to": null,
    "supersedes_memory_id": "m001"
}

source_event_id verwijst naar het event dat Paris heeft aangeleverd. supersedes_memory_id koppelt Paris aan het Berlin-record, m001. schema_version: 1 identificeert het recordformat; dit betekent niet dat het programma oude data automatisch kan migreren.

MemoryRecord en Memory.write() dwingen dat format af. Ontbrekende source references, ongeldige datums en verkeerd gevormde velden worden afgewezen voordat de opgeslagen history verandert. Een gesloten interval moet eindigen na het begin ervan. Berlin kan eindigen op 10 januari terwijl Paris die dag begint; geen van beide records heeft een leeg interval.

Stel dat de volgende write zegt: Rome, eveneens geldig vanaf 10 januari. De writer wijst dat conflict af en laat Paris ongewijzigd. Een tweede Paris-fact voor dezelfde datum gebruikt simpelweg opnieuw hetzelfde record. Een update met een eerdere ingangsdatum wordt ook afgewezen: deze kleine writer reconstrueert geen history die te laat binnenkomt. Dit zijn vaste policies die de outer agent niet kan wijzigen. De deduplicate-instelling bepaalt hoe herhaalde confirmations met een latere ingangsdatum worden afgehandeld.

De baseline negeert bij het lezen nog steeds bewust subject- en date-filters. Hij slaat geldige records op, maar kan de verkeerde kiezen. Dat is de fout die we de agent laten herstellen. Owner isolation geldt voor elke configuratie, en deletion verwijdert alle versies van de aangevraagde property binnen het subject van die owner.

Dit is een in-memory demonstratie van die SGAM-regels. Er is geen durable database, retention service of migratiesysteem. Afzonderlijke writer-regressiontests controleren afgewezen writes en intervalgrenzen; ze zijn geen extra scenario’s in de score van de 20-story campaign.

Laat de agent een wijziging kiezen

Een campaign is één poging om de oorspronkelijke configuratie te verbeteren, met een nieuwe agent-history. Een iteration is één call waarin de agent een wijziging voorstelt of besluit te stoppen. De volgende iteration ontvangt feedback uit eerdere iterations.

De campaign begint door alleen de baseline uit te voeren. Die slaagt voor 13 van de 20 scenario’s. Vervolgens geven we de agent:

  • de huidige settings en hun betekenis;
  • de metingen van de baseline;
  • traces van falende scenario’s, afgewezen writes en duplicate confirmations;
  • de wijzigingen die hij mag voorstellen;
  • eerdere voorstellen en de resultaten daarvan, voor zover die er zijn.

Het eerste verzoek bevat geen kant-en-klare verbeterde configuraties. De repository bevat ook vier handmatig voorbereide configuraties om de memory-mechanics uit te leggen, maar de live agent begint niet met die antwoorden.

De agent kan vijf settings in de bestaande tool wijzigen:

InstellingWat het wijzigen ervan doet
min_confidenceWijzigt de minimaal vereiste aangeleverde score om een feit op te slaan.
filter_entityBeperkt retrieval tot het aangevraagde onderwerp, zoals thuis in plaats van werk.
time_awareBeperkt retrieval tot feiten die geldig zijn op de aangevraagde datum.
deduplicateHergebruikt een identiek actief feit in plaats van nog een bevestiging op te slaan.
top_kBepaalt hoeveel records worden geselecteerd voordat de answer context wordt samengesteld.

Een voorstel mag maximaal twee instellingen wijzigen. Numerieke waarden hebben grenzen: confidence van 0 tot 1, en top_k van 1 tot 8. Het contract legt de configuratiewijzigingen vast die de tool mag uitvoeren; het agent-schema en de validator voegen de voorstelregels toe.

De agent heeft in dit proces geen shell- of filesystem-tools. De agent kan geen Python, verwachte antwoorden, owner isolation, deletion behavior, memory schema, conflict handling, scoring, budgets of release authority wijzigen. De output is data die Python kan accepteren of afwijzen. Dit is een klein configuratie-experiment, geen sandbox voor willekeurige code die door een agent wordt geschreven.

Maak van elk voorstel een SGR-beslissingsrecord

Ik gebruik Schema-Guided Reasoning om de beslissing inspecteerbaar te maken. Elke modelrespons heeft dezelfde velden:

VeldWat de lezer moet kunnen inspecteren
observationsWelk aangeleverd scenario en welke gebeurtenis ondersteunen de voorgestelde wijziging?
hypothesisWelke regel lijkt het probleem te veroorzaken?
predicted_effectWat moet verbeteren wanneer we de wijziging testen?
actionStelt de agent een wijziging voor of stopt hij?
patchWelke toegestane instellingen moeten worden gewijzigd?

Het OpenAI Responses-request gebruikt een strikt JSON Schema dat uit Pydantic-modellen wordt gegenereerd. Objecten wijzen extra velden af, en elk patchveld is verplicht maar mag null zijn, wat betekent: “laat deze instelling ongewijzigd.” Structured Outputs beperkt de vorm van de response. Python controleert nog steeds of verwijzingen bestaan, waarden zijn toegestaan en de voorgestelde configuratie nog niet is getest.

Het schema bewijst de hypothese niet en maakt de interne redenering van het model niet zichtbaar. Dit zijn beknopte beslissingsrecords die we aan de hand van bewijs kunnen controleren.

In de eerste vastgelegde iteratie identificeerde de agent retrieval over verschillende onderwerpen heen en feiten die buiten hun geldigheidsinterval werden geretourneerd. De daadwerkelijke response bevatte dit voorstel:

{
    "min_confidence": null,
    "filter_entity": true,
    "time_aware": true,
    "deduplicate": null,
    "top_k": null
}

Het model koos deze twee instellingen. De runner leverde de parent-ID aan en kende de candidate-ID toe; het model kon de wijziging niet omleiden naar een willekeurige parent of een willekeurig bestand.

Volg de wijziging door Python

Zowel de baseline als de nieuwe configuratie slaan dezelfde records voor Berlijn en Parijs op. De voorgestelde wijziging bepaalt welke records retrieval mag meenemen.

In Memory.query() activeren deze switches twee filters:

if self.config.filter_entity:
    eligible = [r for r in eligible if r["entity"] == event["entity"]]
if self.config.time_aware:
    eligible = [r for r in eligible if valid_at(r, event["as_of"])]

De validity check neemt de startdatum mee en sluit de einddatum uit:

def valid_at(item: dict, at: str) -> bool:
    return item["valid_from"] <= at and (
        item["valid_to"] is None or at < item["valid_to"]
    )

De datums gebruiken YYYY-MM-DD, waardoor hun stringvolgorde overeenkomt met hun kalender volgorde. Voor de vraag van 5 januari wordt Parijs uitgesloten, omdat het pas op 10 januari geldig wordt. Berlijn blijft beschikbaar. Voor de vraag van 12 januari is Parijs geldig en is Berlijn historische informatie.

Python voert de voorgestelde configuratie uit op alle 20 stories. Deze eerste wijziging verhoogt de success rate van 13/20 naar 19/20, waarbij alle geïmplementeerde hard checks slagen. Er worden twee filters tegelijk gewijzigd, dus de winst over de volledige suite meet hun gecombineerde effect. De city trace laat zien wat de date filter in dit specifieke geval heeft gedaan.

De runner selecteert deze configuratie als parent voor het volgende experiment. Die selectie betekent niet dat de configuratie wordt gedeployed. Het model krijgt het gemeten resultaat, de geselecteerde instellingen en de resterende evidence terug in het volgende request.

De volgende beslissing moet het resultaat gebruiken

Hier is de volledige eerste campaign. Elke rij bevat een echte model response, geen vooraf geschreven stap uit een demonstration script:

De tweede response verwees naar het scenario met duplicate confirmations. Dat story schrijft language = German drie keer. Deduplication bewaart één record in plaats van drie, terwijl het antwoord behouden blijft. Over de volledige suite daalde het gemiddelde aantal opgeslagen records van 1.70 naar 1.60, terwijl de success rate 19/20 bleef.

Het derde voorstel richtte zich op een andere failure. Een nuttige language preference had een supplied confidence van 0.6, onder de huidige 0.7-threshold. Door de threshold te verlagen naar 0.6 werd deze preference toegelaten, terwijl het onzekere courier-voorstel met score 0.4 nog steeds werd afgewezen. De success rate bereikte 20/20; het gemiddelde aantal opgeslagen records werd 1.65, omdat memory nu het extra nuttige fact behield.

Bij de vierde aanroep besloot de agent te stoppen: op basis van het aangeleverde bewijs had hij geen verdere onderbouwde wijziging voor te stellen. Dat is een modelbeslissing en geen bewijs dat de configuratie globaal optimaal is.

Het volgende request bevat de huidige resultaten en eerdere beslissingen. Nadat de agent had gezien dat zijn retrieval-fix hielp, ging hij verder met storage en write admission. De runner leverde die volgende patches of een vooraf geschreven reeks stappen niet aan.

De selectieregel staat vast: alle hard checks moeten slagen, een hoger succespercentage voor het complete scenario heeft de voorkeur en bij gelijk succes worden minder opgeslagen records verkozen. Een slechter resultaat laat de vorige parent intact. De tests oefenen dat rejectiepad ook uit met een scripted proposal die regressie veroorzaakt; dit was geen gemeten kwaliteitsregressie in deze drie live-campagnes.

Een afzonderlijke development run bevat een echte validation rejection: de agent verwees naar agent-01, een candidate ID, alsof het een scenario was. Het antwoord voldeed aan het JSON-schema, maar de referentie identificeerde geen aangeleverd event, waardoor Python het antwoord vóór de evaluatie afwees. De controller geeft het afgewezen antwoord en de specifieke validatiefout als feedback terug; offline tests controleren dat gedrag. De drie hieronder gerapporteerde campagnes hadden geen validation failures.

Herhaal de search campaign, niet de deterministische test

Dezelfde memory-configuratie en inputs leveren dezelfde antwoorden op. Het herhalen van die evaluatie levert geen extra bewijs over de antwoordkwaliteit op. De runner controleert een nieuwe configuratie één keer en gebruikt geverifieerde parent-resultaten opnieuw voor vergelijkingen.

De outer agent kan verschillende proposals kiezen, dus we hebben drie onafhankelijke campagnes uitgevoerd. Elke campagne begon bij dezelfde baseline van 13/20, kreeg een verse history en had maximaal vier modelbeslissingen. Geen enkele campagne kreeg de ontdekkingen van de vorige campagne.

Alle drie de campagnes kozen dezelfde sequence: beide retrieval-filters inschakelen, confirmations dedupliceren, de confidence threshold verlagen naar 0.6 en vervolgens stoppen.

Er waren 12 model calls: negen proposals die door Python werden geëvalueerd, gevolgd door drie stopbeslissingen. Elke campagne voerde de baseline plus drie nieuwe configuraties uit op 20 stories: 80 memory-tool-executions per campagne. De 20 stories bleven gedurende de hele campagne gelijk.

Alle drie selecteerden dezelfde final settings. Dit is een kleine observatie van één model, één prompt, één target en één publieke testsuite. Het schat niet hoe betrouwbaar de optimizer onbekende systemen zal verbeteren. Een sterkere vergelijking hoort later in de serie thuis: herhaalde campagnes met gematchte budgets, concurrerende proposal-methoden en tests die de proposer niet kan inspecteren.

Lees kwaliteit en kosten op het juiste niveau

Het experiment heeft twee verschillende kostenposten. Het uitvoeren van de memory tool gebruikt lokale CPU-tijd en doet geen modelaanroepen. Het uitvoeren van de outer proposer gebruikt input- en outputtokens. Een provider-cost-veld met waarde nul in een memory evaluation report beschrijft alleen de inner tool; het zijn niet de kosten van de campagne.

Voor de vastgelegde studie van 11 september 2026 gebruikten we GPT-5.6 Luna (gpt-5.6-luna), reasoning effort low, het opgeslagen SGR-schema en de opgeslagen instructies, en maximaal 4.096 outputtokens per aanroep. Het programma schakelde automatische SDK-retries uit en stelde een request timeout van 60 seconden in. Exacte requests, geretourneerde model-ID’s, usage en call durations worden bewaard.

De geschatte tokenkosten voor de 12 modelaanroepen bedragen USD 0.039177, tegenover een geconfigureerd budget van USD 0.50. De berekening gebruikt de gepubliceerde modeltarieven, bevat de in usage gerapporteerde cache-write-toeslag en negeert cache-read-kortingen. Het is een conservatieve schatting op basis van vastgelegde usage, geen factuur. Hardware en developmenttijd vallen buiten dit bedrag.

Vóór elke aanroep reserveert de runner een bovengrens op basis van de begrensde inputgrootte en het maximale aantal outputtokens. Als het resterende budget die reservering niet kan dekken, stopt de runner. Mislukte of onderbroken aanroepen blijven in het record; wanneer usage niet beschikbaar is, blijft het gereserveerde bedrag behouden in plaats van als nul te worden behandeld.

Voor answer quality betekent 20/20 dat elk antwoord en elke toepasselijke harde check voor deze 20 voorbereide stories is geslaagd. Het betekent niet dat de memory production-ready is. Alle stories zijn openbare developmentcases; geselecteerde traces en feedback uit de suite zijn beschikbaar voor de proposer. Ze behandelen updates, historische vragen, onzekerheid, duplicaten, distractors, scheiding van owners, verwijdering en niet-toegestane writes. De labels search, evaluation en adversarial structureren de oorspronkelijke suite; ze maken geen van deze cases tot een hidden test set.

Deze kleine suite is geïnspireerd door ideeën uit LongMemEval, MemoryAgentBench, VehicleMemBench en GateMem. De inputs en scoring hier zijn van onszelf; de resultaten reproduceren die benchmarks niet.

Je kunt ook vier handmatig voorbereide configuraties in de repository vergelijken. Ze illustreren waarom het accepteren van meer feiten antwoorden kan verslechteren en hoe storage kan verbeteren zonder hogere answer quality. Ze tonen ook de door mensen gespecificeerde kant van dezelfde experimentmachinerie: de auteur levert de candidates aan en Python evalueert ze. Het zijn nuttige vergelijkingen voor uitleg, geen bewijs dat agentic search beter presteert dan een competente mens of een andere searchmethode.

Start een nieuwe agent-campagne

Als je de agent nieuwe proposals wilt laten kiezen, clone dan de companion en download het vastgelegde bewijs:

git clone --branch v0.2.2 --depth 1 https://github.com/slavadubrov/meta-engineering-ai-lab.git
cd meta-engineering-ai-lab
uv sync --frozen
uv run --frozen python scripts/fetch_evidence.py
uv run --frozen python -m lab verify artifacts/agent-study-03 --source

De download controleert de SHA-256 en herstelt de volledige recordings onder artifacts/. Er worden geen modelaanroepen gedaan. Als je het bewijs al hebt gedownload, sla die stap dan over en voer het verificatiecommando uit.

Sla een OPENAI_API_KEY op in een lokaal .env.local-bestand. De repository negeert dat bestand. Voer daarna het volgende uit:

uv run --frozen --env-file .env.local python -m lab campaign \
  --live --campaigns 3 --iterations 4 --budget-usd 0.50 \
  --output artifacts/my-agent-study

--live schakelt provider calls expliciet in. Een key in de environment maakt de offline memory commands of de browser niet tot een live agent. --campaigns 3 maakt drie onafhankelijke agent histories aan; --iterations 4 beperkt de beslissingen binnen elke history. Gebruik voor elke studie een nieuwe outputdirectory: bestaande evidence wordt nooit overschreven.

Open artifacts/my-agent-study/report.md voor de campaign outcomes en links naar elk request, elke response en elke Python-evaluatie. Vergelijk de voorgestelde wijzigingen met de hierboven vastgelegde campaign: de agent kan andere keuzes maken, ook al zijn de memory tests deterministisch.

De README brengt de code en commands in kaart. Met het bevroren campaign report en de archive checksum en example index kan een lezer de evidence voor dit artikel rechtstreeks inspecteren.

Houd experiment history gescheiden van user memory

De memory tool slaat Ada’s city en language op. De experiment history slaat op wat de agent zag, de voorgestelde patch, eventuele afwijzing, de resulterende metingen en welke configuration de volgende parent werd. Deze stores dienen verschillende doelen.

Elke iteration bewaart het exacte request met instructions en schema, de provider response, usage en timing, het validation outcome en elke voltooide evaluation. Failed proposals blijven zichtbaar. File hashes koppelen de opgeslagen evidence aan de implementation en inputs die voor het experiment zijn gebruikt.

Dit zijn synthetic facts, dus het publieke record kan volledige states bewaren. Voor echte traces is een afzonderlijk retention policy nodig: het verwijderen van een fact uit de memory tool wist eerdere copies in experiment logs of backups niet. De deletion test van de demo controleert de records en latere reads van de tool, niet het wissen uit elke mogelijke store.

Wat het volgende artikel moet uitdagen

We hebben nu een agent in de improvement loop. De agent stelt een wijziging voor, ontvangt een gemeten resultaat, kiest de volgende wijziging en kan besluiten te stoppen. Invalid proposals volgen een afzonderlijk rejection path en blijven in het record staan. Memory gaf ons een klein target voor dit eerste experiment. De scheiding tussen proposal, evaluation en adoption geldt ook wanneer we andere onderdelen van een agent system wijzigen.

Het volgende risico is de evaluator zelf. Als succes wordt beloond wanneer elk fact behouden blijft, kan de agent leren om guesses te bewaren. Als een suite alleen naar de huidige city vraagt, kan die een wijziging missen die nuttige history vernietigt. Een capabelere proposer kan zwakke metingen efficiënter uitbuiten.

Part 2, Make It Scorable Before You Make It Autonomous, onderzoekt hoe we die metingen kunnen testen voordat we de proposer meer vrijheid geven. De 20/20 van de eerste campaign is het startpunt voor dat onderzoek.
