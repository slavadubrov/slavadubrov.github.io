Redeneringslopen van AI-agenten in 2026: ReAct versus ReWOO versus Plan-and-Execute

Deel 1 van de serie ‘Engineering the Agentic Stack’

Een redeneringsloop van een agent bepaalt hoe een systeem plannen maakt, tools aanroept, resultaten leest en beslist wanneer het moet stoppen. Deze controlestroom heeft invloed op de kosten, vertragingen en mogelijkheden tot herstel wanneer een tool onverwachte output retourneert.

In dit artikel worden de drie belangrijkste patronen voor redeneringslopen van AI-agenten in 2026 vergeleken: ReAct, ReWOO en Plan-and-Execute. Het voorbeeld dat wordt gebruikt, is een Market Analyst Agent die ik in LangGraph heb gebouwd; de volledige code is te vinden op GitHub.

Dit is het eerste deel van deze serie. In latere delen worden onder andere het staatssysteem waaruit de loop weer wordt hervat, de beschikbare tools, de beleidsregels rondom deze oproepen, de runtime die een uitvoering in stand houdt, en de controles die bepalen of het werk daadwerkelijk voltooid is, behandeld.

Kort samengevat: ReAct is flexibel maar kostbaar, ReWOO is snel wanneer het werkproces voorspelbaar is, en Plan-and-Execute is geschikt voor meerdere stappen tellende analyses. Een productiegebruikte AI-agent kan per verzoek overschakelen tussen verschillende redeneringslopen, door gebruik te maken van gedeelde staat en gecacheerde LangGraph-nodes, zodat elke taak de loop krijgt die past bij zijn structuur.

De loop bepaalt kosten, vertragingen en herstelmogelijkheden

Een bruikbare agent heeft meer nodig dan alleen een goede prompt. Zijn controlegrafiek moet redenering, tools en geheugen met elkaar verbinden, terwijl fouten worden afgehandeld.

De redeneringsloop bepaalt wanneer het model plannen maakt, een tool aanroept, het resultaat leest en stopt. Een slechte keuze leidt tot onnodige oproepen aan het model en verhoogde vertragingen. Bovendien kan dit ertoe leiden dat de agent niet kan herstellen van onverwachte output van een tool.

Drie patronen voor redenering bij AI-agenten

ReAct: denken, handelen, observeren, herhalen

ReAct (Yao et al., 2022) is het oorspronkelijke patroon voor interactieve agenten. Het werkt volgens een lus:

  1. Denken: de agent genereert een “gedachte” om het doel te analyseren en de volgende stap te plannen.
  2. Handelen: op basis van deze gedachte wordt een tool aangeroepen.
  3. Observeren: de agent leest het resultaat, waardoor zijn begrip voor de volgende denkronde wordt bijgewerkt.

Voordelen:

  • Door gebruik te maken van echte observaties worden verzinsels verminderd.
  • De agent kan op het moment zelf zijn strategie aanpassen op basis van wat hij zojuist heeft gezien.
  • Het historisch verslag van tool-oproepen en observaties biedt een duidelijke traceerbaarheid van de uitvoering.

Nadelen:

  • Het historische materiaal blijft zich opstapelen en wordt bij elke stap opnieuw verwerkt, waardoor vertragingen en kosten toenemen naarmate de lus langer wordt.
  • Het is inefficiënt wanneer tool-oproepen van tevoren hadden kunnen worden gepland, een situatie waar ReWOO juist optimaal is.
  • Zonder stopconditie of limiet op het aantal stappen zal de lus oneindig doorgaan.

Het meest geschikt voor: exploratieve taken, debugging, en situaties waarin je de volgende stap niet kunt voorspellen.

ReWOO: alles van tevoren plannen

ReWOO (Reasoning WithOut Observation) is een efficiënter alternatief voor ReAct. Het trucje zit hem in het scheiden van redenering en uitvoering van tools: in plaats van na elke actie te stoppen om te observeren, plant ReWOO de hele reeks tool-oproepen in één keer.

  1. Plan: één oproep aan de LLM genereert het volledige plan voor de tooloproepen, waarbij variabele placeholders (#E1, #E2)) worden gebruikt voor nog niet beschikbare uitvoerresultaten.
  2. Worker: een niet-LLM executor voert de geplande tools achtereenvolgens of parallel uit en vult de placeholders in.
  3. Solver: een laatste oproep aan de LLM gebruikt de verzamelde observaties om het antwoord op te stellen.

Voordelen:

  • Minder herhaalde modeloproepen dan bij ReAct wanneer het initiële plan geldig blijft.
  • Lagere vertraging; er hoeft geen geschiedenis opnieuw ingediend te worden bij elke stap.
  • De planner kan zelf gefine-tuned worden, zonder dat er een live omgeving nodig is.

Nadelen:

  • Gevoelig wanneer tools zich abnormaal gedragen; het plan gaat ervan uit dat alles correct werkt.
  • Vereist voorspelbare werkflows.
  • Zonder expliciete fallback-logica blijft een foutief plan doorlopen.

Ideaal voor: snelle snapshots, statuscontroles, dashboards. Alles waarbij de tools zich voorspelbaar gedragen.

Plan-and-Execute: een hybride

Plan-and-Execute bevindt zich tussen deze twee benaderingen in. Het artikel beschrijft een eenvoudige indeling die door de meeste moderne agents wordt gebruikt:

  1. Planningfase: eerst wordt er een plan gemaakt dat de taak opsplitst in kleinere sub-taken.
  2. Uitvoerfase: vervolgens worden deze sub-taken uitgevoerd.

Het oorspronkelijke artikel richtte zich op zero-shot prompting. Moderne frameworks zoals LangGraph hebben dit uitgewerkt tot een volledig orchestratiepatroon met sequentiële uitvoering en keuze van een model per stap (een krachtig redeneringsmodel voor planning, een goedkopper model voor uitvoering).

Voordelen:

  • Hiërarchisch redeneren dat overeenkomt met de manier waarop een menselijke expert een project opdeelt.
  • Herplanning is mogelijk; je kunt pauzeren en opnieuw evalueren als het resultaat van een stap onverwacht is.
  • Specialisatie van modellen: de planner kan duur zijn, terwijl de executor goedkoop kan zijn.
  • Begrensde complexiteit, met een duidelijke controlepunt na elke stap.

Nadelen:

  • Hogere vertraging dan bij ReWOO omdat de stappen sequentieel worden uitgevoerd.
  • Meer staat die beheerd moet worden.
  • Overbodig voor one-shot queries.

Ideaal voor: complexe meestapsanalyses, onderzoekstaakken, alles wat aan het einde synthese vereist.

Patroon 1: Implementatie van Plan-and-Execute

Plan-and-Execute is geschikt voor taken die multi-stappige synthese vereisen. Het belangrijkste is om planning en uitvoering gescheiden te houden: een krachtig model voor het initiële plan, gevolgd door een ReAct-cyclus om elke stap uit te voeren met ruimte om te reageren op de resultaten van de tools.

Hoe dit overeenkomt met het patroon:

  1. Eén initiële planningsfase. Één LLM-oproep genereert het volledige plan als een lijst met stapbeschrijvingen.
  2. Output gestuurd door een schema, waardoor het plan vóór uitvoering wordt gevalideerd.
  3. Nog geen tooluitvoering. De planner beslist alleen wat er moet gebeuren, niet hoe.
  4. Menselijke leesbare stappen. Elke stap is tekst die door de executor kan worden geïnterpreteerd.
# System prompt guides the LLM to think like a research analyst
# creating a strategic plan, not immediate tool calls
PLANNER_SYSTEM_PROMPT = """You are a senior investment research analyst.
Break down stock analysis requests into 4-6 research steps covering:
1. Current price and basic metrics
2. Recent news and announcements
3. Competitor analysis (if relevant)
4. Financial health assessment
5. Risk factors
6. Investment thesis synthesis

Output as JSON with step_number, description, and tool_hint."""

# Schema-Guided Reasoning: Enforce structure with Pydantic
class PlanOutput(BaseModel):
    """Structured output for the planner."""

    steps: list[PlanStep] = Field(description="Research steps to execute")
    ticker: str = Field(description="The stock ticker being analyzed")

def planner_node(state: AgentState) -> dict:
    """Generate a research plan from the user's request.

    This is Phase 1 of Plan-and-Execute: creating the high-level strategy.
    """

    # Use a powerful model for strategic planning
    llm = ChatAnthropic(model="claude-sonnet-4-5-20250929", temperature=0)

    # Ask for a typed plan and validate it before execution.
    # The API can still fail, so production code also handles that exception.
    structured_llm = llm.with_structured_output(PlanOutput)

    # Context from long-term memory personalizes the plan
    profile_context = f"""
User Profile:
- Risk Tolerance: {state.user_profile.risk_tolerance}
- Investment Horizon: {state.user_profile.investment_horizon}
"""

    # Single LLM call creates the complete plan
    result: PlanOutput = structured_llm.invoke([
        SystemMessage(content=PLANNER_SYSTEM_PROMPT + profile_context),
        HumanMessage(content=f"Create a research plan for: {last_user_message}"),
    ])

    # State update: Store the plan and initialize tracking
    return {
        "plan": result.steps,           # The sequential steps to execute
        "current_step_index": 0,        # Start at step 0
        "research_data": ResearchData(ticker=result.ticker),  # Initialize data container
    }

Die llm.with_structured_output(PlanOutput)-regel vertegenwoordigt Schema-Guided Reasoning (SGR), een onderwerp dat ik al besprak in een eerdere post. Het schema zorgt ervoor dat de applicatie een ongeldig plan kan weigeren voordat LangGraph de gevalideerde velden gebruikt om conditionele randen te genereren.

Patroon 2: ReAct-executie

Zodra het plan beschikbaar is, voert de executor elke stap uit als een afzonderlijke ReAct-lus. Dit is fase 2: elke stap is voldoende klein zodat de Thought-Action-Observation-cyclus gefocust blijft, waardoor de agent kan reageren op wat de tool teruggeeft.

Hoe het ReAct-deel is opgebouwd:

  1. Iteratieve uitvoering. Eén stap tegelijk, met observatiefeedback.
  2. De Thought-Action-Observation-lus loopt binnenin create_react_agent.
  3. Resultaten van eerdere stappen worden gebruikt als context voor het huidige redeneren.
  4. De agent kiest tools op basis van de beschrijving van de stap.
  5. Hij kan halverwege een stap zijn aanpak aanpassen op basis van de output van een tool.
# Tools available for the ReAct agent to choose from
TOOLS = [
    get_stock_snapshot,
    get_price_history,
    search_news,
    search_competitors,
    get_financials,
]

def executor_node(state: AgentState) -> dict:
    """Execute the current step using a ReAct agent.

    This is Phase 2 of Plan-and-Execute: adaptive execution of each planned step.
    Each step runs as a mini ReAct loop until completion.
    """

    # Get the current step from the plan
    current_step = state.plan[state.current_step_index]

    # Build context from what we've learned so far
    # This matters: each step builds on previous observations
    previous_context = ""
    for step in state.plan[:state.current_step_index]:
        if step.result:
            previous_context += f"\nStep {step.step_number}: {step.result}\n"

    # Create a ReAct agent for this step
    # LangGraph's create_react_agent implements the full Thought-Action-Observation loop:
    # 1. Agent generates a "thought" about what tool to call
    # 2. Agent calls the tool ("action")
    # 3. Tool returns result ("observation")
    # 4. Agent decides: call another tool or finish
    react_agent = create_react_agent(
        model=ChatAnthropic(model="claude-sonnet-4-5-20250929"),
        tools=TOOLS,
    )

    # Invoke the ReAct loop for this single step
    # The agent will loop internally until it completes the step
    result = react_agent.invoke({
        "messages": [
            SystemMessage(content=EXECUTOR_SYSTEM_PROMPT),
            HumanMessage(content=f"""Execute Step {current_step.step_number}:
{current_step.description}

Ticker: {state.research_data.ticker}
Previous findings: {previous_context}"""),
        ]
    })

    # Extract the final answer from the ReAct agent's message history
    # The last message contains the synthesis after all tool calls
    updated_plan = list(state.plan)
    updated_plan[state.current_step_index] = PlanStep(
        step_number=current_step.step_number,
        description=current_step.description,
        completed=True,
        result=result["messages"][-1].content,  # Final observation
    )

    # State update: Mark step complete and advance to next
    return {
        "plan": updated_plan,
        "current_step_index": state.current_step_index + 1,
    }

Dit is de kern van het Plan-and-Execute-proces: een krachtig model schrijft het plan, waarna ReAct elke stap met volledige aanpasbaarheid uitvoert.

Patroon 3: ReWOO voor snelle snapshots

Voor snelle rapportages slaat ReWOO het gecombineerde redeneren over en voert de tools parallel uit. De planner genereert van tevoren een gecompileerde script met toolaanroepen, die door de worker wordt uitgevoerd zonder verdere betrokkenheid van een LLM.

De structuur hiervan:

  1. Drie fasen (Planner → Worker → Solver), zonder lussen.
  2. Toolaanroepen verwijzen naar #E1 en #E2 als placeholders voor nog niet beschikbare resultaten.
  3. Tijdens de uitvoering is er geen LLM betrokken; de worker voert alleen tools uit.
  4. Onafhankelijke tools werken parallel.
  5. Aan het einde vindt één syntheseaanroep plaats, waarbij alle gegevens tegelijk worden verwerkt.

Fase 1: ReWOO planner (creëert van tevoren het volledige uitvoeringsnetwerk)

class ReWOOPlanStep(BaseModel):
    """A step in the ReWOO plan with variable placeholders.

    Key difference from Plan-and-Execute's PlanStep:
    - Contains actual tool_name and tool_args (not just description)
    - Uses variable references (#E1) for dependencies
    """
    step_id: str  # e.g., "#E1" - becomes a variable
    description: str
    tool_name: str     # Exact tool to call
    tool_args: dict    # May contain variable refs like {"price": "#E1"}
    depends_on: list[str] = []  # For dependency ordering
    result: str | None = None

class ReWOOPlanOutput(BaseModel):
    """Structured output for ReWOO planner."""
    steps: list[ReWOOPlanStep] = Field(description="Planned tool calls with variables")

def rewoo_planner_node(state: AgentState) -> dict:
    """Generate a complete plan of tool calls upfront.

    This is the key difference from Plan-and-Execute: instead of creating
    human-readable step descriptions, we create EXACT tool calls that
    the worker will execute blindly.
    """

    llm = ChatAnthropic(model="claude-sonnet-4-5-20250929", temperature=0)

    # Schema-Guided Reasoning ensures valid tool call specifications
    structured_llm = llm.with_structured_output(ReWOOPlanOutput)

    ticker = state.research_data.ticker if state.research_data else "UNKNOWN"

    # Single LLM call to plan ALL tool executions
    result: ReWOOPlanOutput = structured_llm.invoke([
        SystemMessage(content=REWOO_PLANNER_PROMPT),
        HumanMessage(content=f"""Create a ReWOO plan for: {query}

Ticker: {ticker}

Output tool calls with:
- step_id: Variable name (#E1, #E2, etc.)
- description: What this accomplishes
- tool_name: Exact tool from the list
- tool_args: Dictionary of arguments
- depends_on: List of step_ids this depends on"""),
    ])

    # State update: Store the complete execution plan
    # Worker will execute this without any LLM involvement
    return {"rewoo_plan": result.steps}

Fase 2: ReWOO worker (voert tools uit zonder LLM-redenering)

def rewoo_worker_node(state: AgentState) -> dict:
    """Execute all planned tools in parallel (no LLM calls).

    This is the key efficiency: Worker is "dumb" - it just runs tools
    according to the plan. No LLM calls = massive token savings.
    """

    results = {}  # Store results keyed by step_id (e.g., "#E1": "$150.23")

    # Execute ALL independent steps in parallel using ThreadPoolExecutor
    # This is where ReWOO gets its speed advantage
    with ThreadPoolExecutor(max_workers=5) as executor:
        futures = {
            executor.submit(execute_tool, step): step
            for step in state.rewoo_plan
            if not step.depends_on  # Only independent tools for parallel batch
        }

        # Collect results as they complete
        for future in as_completed(futures):
            step = futures[future]
            results[step.step_id] = future.result()
            # No LLM reasoning here - just store the raw tool output

    # State update: Store results for the Solver phase
    return {"rewoo_plan": updated_steps}

Fase 3: ReWOO solver (syntetiseert alle resultaten in één LLM-aanroep)

def rewoo_solver_node(state: AgentState) -> dict:
    """Synthesize all tool results into a flash briefing.

    This is the second efficiency gain: Instead of interleaving
    LLM calls with tool execution (like ReAct), we make ONE
    final synthesis call with all gathered data.
    """

    # Build context from ALL tool results at once
    tool_results = []
    for step in state.rewoo_plan:
        if step.result:
            tool_results.append(f"### {step.description}\n{step.result}")

    context = "\n\n".join(tool_results)

    # Single LLM call to synthesize everything
    structured_llm = llm.with_structured_output(FlashBriefingOutput)
    result = structured_llm.invoke([
        SystemMessage(content=REWOO_SOLVER_PROMPT),
        HumanMessage(content=f"Create a flash briefing from this data:\n\n{context}"),
    ])

    return {"draft_report": result}

ReWOO plant van tevoren elke toolaanroep en slaat de afhankelijkheden op in placeholders zoals #E1 en #E2. De executor kan onafhankelijke aanroepen parallel uitvoeren zonder het model te vragen wat vervolgens moet gebeuren. Een laatste modelaanroep combineert de resultaten, waardoor voorspelbare workflows goedkoop blijven.

Wanneer elk patroon het model aanroept

De drie patronen verschillen in wanneer en hoe ze de LLM aanroepen:

Wat er tussen hen verschilt, is wat de planner genereert. Dit bepaalt alles in de volgende stappen.

  1. Plan-and-Execute genereert menselijkeleesbare beschrijvingen van de stappen:

    # Planner output (list of PlanStep objects)
plan = [
    PlanStep(
        step_number=1,
        description="Get current price and key financial metrics",
        tool_hint="get_stock_price"
    ),
    PlanStep(
        step_number=2,
        description="Search for recent news and earnings",
        tool_hint="search_news"
    ),
    # ... more steps
]

    De executor leest elke beschrijving en beslist welke hulpmiddelen moeten worden opgeroepen. Dit is flexibel, maar kost een oproep aan een LLM per stap.

  2. ReAct beschikt niet over een vooraf opgestelde plan. Het maakt gebruik van iteratief redeneren:

    # No planning phase - ReAct works step-by-step with accumulated messages
messages = [
    HumanMessage(content="Execute Step 1: Get current price"),
    AIMessage(content="I'll call get_stock_price"),
    ToolMessage(tool_call_id="1", content="$132.45"),
    AIMessage(content="Now I need metrics..."),
    # ... agent continues until step complete
]

    Meerdere LLM-oproepen per stap passen zich aan aan de waarnemingen en kosten doorgaans meer dan de twee geplande methoden.

  3. ReWOO genereert expliciete, uitvoerbare specificaties voor het oproepen van hulpmiddelen:

    # Planner output (list of ReWOOPlanStep objects)
rewoo_plan = [
    ReWOOPlanStep(
        step_id="#E1",
        tool_name="get_stock_price",
        tool_args={"ticker": "NVDA"}
    ),
    ReWOOPlanStep(
        step_id="#E2",
        tool_name="search_news",
        tool_args={"query": "NVDA earnings", "limit": 5}
    ),
    # ... all tool calls planned upfront
]

    De worker draait zonder tussenkomst van een LLM. Alle modeloproepen vinden plaats binnen de planner en solver, waardoor het aantal modeloproepen voorspelbaar is.

Geheugen- en staatstoevoer:

  • Plan-and-Execute: de staat beweegt zich via plan → current_step_index → research_data.
  • ReAct: de staat wordt opgeslagen in het messages-array (het volledige gespreksverloop).
  • ReWOO: de staat beweegt zich via rewoo_plan, waarbij de result-velden door de worker worden ingevuld.

Samenvatting: het verbinden van het graf

Zo kunnen de drie patronen samenwerken binnen één LangGraph-systeem. Ze delen één AgentState en bevinden zich in één graf. Een router kiest per verzoek het juiste pad, zodat er sprake is van één agent met drie uitvoeringsmodi, in plaats van drie aparte agents.

LangGraph houdt de verbindingen declaratief:

def create_graph(checkpointer=None):
    builder = StateGraph(AgentState)

    # Add nodes
    builder.add_node("router", router_node)
    builder.add_node("planner", planner_node)
    builder.add_node("executor", executor_node)
    builder.add_node("reporter", reporter_node)
    builder.add_node("rewoo_planner", rewoo_planner_node)
    builder.add_node("rewoo_worker", rewoo_worker_node)
    builder.add_node("rewoo_solver", rewoo_solver_node)

    # Define edges
    builder.add_edge(START, "router")
    builder.add_conditional_edges("router", route_after_router, {
        "planner": "planner",
        "rewoo_planner": "rewoo_planner",
    })

    # Deep Research path
    builder.add_edge("planner", "executor")
    builder.add_conditional_edges("executor", route_after_executor, {
        "executor": "executor",  # Loop back for more steps
        "reporter": "reporter",  # Done with plan
    })
    builder.add_edge("reporter", END)

    # Flash Briefing path (ReWOO)
    builder.add_edge("rewoo_planner", "rewoo_worker")
    builder.add_edge("rewoo_worker", "rewoo_solver")
    builder.add_edge("rewoo_solver", END)

    return builder.compile(
        checkpointer=checkpointer,
        interrupt_before=["reporter"],  # HITL pause for approval
    )

Automatische selectie van het patroon met behulp van een router

Om voor elk verzoek het juiste patroon te kiezen, heb ik een router-classifier toegevoegd. Deze gebruikt Schema-Guided Reasoning om een betrouwbare classificatie te garanderen:

class ExecutionMode(str, Enum):
    """Execution mode for the agent."""

    DEEP_RESEARCH = "deep_research"  # Plan-and-Execute + ReAct (thorough)
    FLASH_BRIEFING = "flash_briefing"  # ReWOO (fast, token-efficient)

class RouterOutput(BaseModel):
    """Structured output for the router."""

    mode: ExecutionMode  # DEEP_RESEARCH or FLASH_BRIEFING
    ticker: str
    reasoning: str

ROUTER_SYSTEM_PROMPT = """Classify the user's request:

1. **deep_research**: Complex analysis requiring synthesis
   - Examples: "Analyze strategic risks", "investment thesis"

2. **flash_briefing**: Quick snapshots, simple data retrieval
   - Examples: "quick snapshot", "current price"

Default to deep_research if unclear."""

structured_llm = llm.with_structured_output(RouterOutput)

Met deze oplossing hoeven gebruikers geen modus zelf te kiezen. De router stuurt “current price” automatisch naar ReWOO en “investment thesis” naar Plan-and-Execute.

Belangrijkste conclusies

  1. ReAct biedt de meeste feedbackpunten, maar dit gaat gepaard met herhaalde modeloproepen.
  2. ReWOO vermindert het aantal modeloproepen wanneer de hulpmiddelen betrouwbaar zijn en de afhankelijkheden voorspelbaar.
  3. Plan-and-Execute is geschikt voor complexe analyses die vóór uitvoering kunnen worden opgedeeld, maar toch per stap feedback nodig hebben.
  4. Een router kan per verzoek kiezen tussen de verschillende methoden, zodat gebruikers dit niet zelf hoeven te doen.
  5. De loop heeft opgeslagen staat nodig om een onderbreking of herstart van de worker te overleven. Dit is het onderwerp van Deel 2.

De volledige implementatie, inclusief de router en de gedeelde staat, is te vinden in het Market Analyst Agent repository.
