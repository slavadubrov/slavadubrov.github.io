uv auf macOS: Python-Versionen, Projekte und Tools verwalten

Viacheslav Dubrov

2025-04-17 · Aktualisiert 2026-07-17 · 6 Min. · Entwicklungswerkzeuge

Automatische Übersetzung Dieser Artikel wurde automatisch aus der englischen Originalversion übersetzt.

Ich habe meinen Python-Workflow auf uv umgestellt. Damit entfiel der Wechsel zwischen pip, virtuellen Umgebungen, pip-tools, pipx und Project Managern, den ich zuvor verwendet hatte. Jetzt deckt ein einziges Executable den größten Teil dieser Aufgaben ab.

Die Workflows unterscheiden sich weiterhin. Ein Projekt, ein Script mit Inline-Metadaten, ein einmaliges CLI-Tool und ein installiertes CLI haben jeweils eine eigene Umgebung und einen eigenen Lifecycle. Dieser Leitfaden zeigt die von mir verwendeten Commands und die jeweilige Abgrenzung dahinter.

Dieser Leitfaden richtet sich an Python-Entwickler auf macOS, die ihre pip-, Virtual-Environment-, pip-tools- oder pipx-Workflows durch uv ersetzen. Danach kannst du die passende uv-Umgebung für ein Projekt, ein eigenständiges Script, ein einmaliges Tool oder einen Command auswählen, der auf PATH bleiben muss.

Schnellstart

# Install uv with Homebrew
brew install uv

# Start a project
uv init example-app
cd example-app
uv add httpx
uv run python main.py

# Run an isolated CLI without installing it permanently
uvx ruff check .

TL;DR. Innerhalb von Projekten verwende ich uv add, uv lock, uv sync und uv run. Für eigenständige Scripts verwende ich PEP-723-Metadaten, für einmalige Tools uvx und für Commands, die auf PATH bleiben müssen, uv tool install. In CI überprüft --locked, ob die Projektmetadaten mit uv.lock übereinstimmen. --frozen verlässt sich auf das vorhandene Lockfile, ohne dessen Aktualität zu prüfen.

uv mit einem einzigen Owner installieren

Homebrew ist ein bequemer Installationsweg unter macOS. Die unterstützten Methoden findest du in uv’s Installationsanleitung:

brew install uv
uv --version

Wenn Homebrew uv installiert hat, sollte Homebrew uv auch aktualisieren:

brew upgrade uv

uv self update ist für uv’s Standalone-Installationsmethode vorgesehen und bei Installationen über einen Package Manager deaktiviert. Lass nicht zwei Installer um dasselbe Executable konkurrieren.

Nützliche Commands zur Identitätsprüfung:

command -v uv
uv python dir
uv tool dir
uv cache dir

Verwaltete Python-Installationen, persistente Tools und temporäre Cache-Einträge liegen in separaten Verzeichnissen. Der Cache kann gelöscht und neu aufgebaut werden. Er ist keine Source of Truth.

Projekte: Deklarationen, Auflösung und Umgebung

Ein uv-Projekt besteht normalerweise aus drei Artefakten:

  • pyproject.toml definiert die Projektmetadaten und direkten Requirements.
  • uv.lock speichert uv’s plattformübergreifende Auflösung.
  • .venv ist die lokal installierte Umgebung und sollte problemlos verworfen werden können.

Erstelle eine Application und füge Runtime- und Test-Requirements hinzu:

uv init forecast-app
cd forecast-app

uv add httpx
uv add --group test pytest
uv run python main.py
uv run --group test pytest

Aktuelle uv-Application-Templates erzeugen main.py, pyproject.toml, README.md und .python-version. Standardmäßig definieren sie kein Build-System. Verwende uv init --lib für eine paketierte Library mit einem src-Layout und einem Build-Backend.

uv run prüft das Projekt, aktualisiert das Lockfile bei Bedarf, synchronisiert die erforderlichen Dependencies und führt den Command aus. Dieser Lifecycle wird in uv’s Dokumentation zu Projektstruktur und Synchronisierung beschrieben. Die erste Projektoperation erstellt .venv und uv.lock bei Bedarf. uv init selbst erstellt nur die Projektdateien.

Inputs committen, nicht die Umgebung

Committe pyproject.toml, uv.lock, den Source-Code und ein bewusst festgelegtes .python-version. Ignoriere .venv und uv’s Caches.

Das Lockfile dokumentiert eine Auflösung über unterstützte Marker und Plattformen hinweg. Es sorgt nicht dafür, dass native Wheels unter macOS, Linux, auf Intel und Apple Silicon identisch sind. Teste jede Deployment-Plattform.

Aktualität des Lockfiles: --locked ist nicht --frozen

Standardmäßig dürfen Project Commands uv.lock aktualisieren, wenn sich Deklarationen ändern. Hinweise zu den Flags für Aktualität und Exaktheit findest du in der Dokumentation zu Locking und Synchronisierung von uv.

Verwende --locked, um sicherzustellen, dass das Lockfile mit den Projektmetadaten aktuell ist:

uv lock --check
uv sync --locked
uv run --locked pytest

Wenn pyproject.toml und uv.lock nicht übereinstimmen, schlagen diese Commands fehl, statt ein neues Lockfile aufzulösen. Dieser Fehler ist normalerweise genau der CI-Gate, den du brauchst.

Verwende --frozen nur, wenn uv bewusst das vorhandene Lockfile nutzen soll, ohne zu prüfen, ob es aktuell ist:

uv sync --frozen

Das kann in einer kontrollierten Build-Phase sinnvoll sein, in der das Lockfile bereits validiert wurde. Es ist jedoch kein Detector für veraltete Lockfiles.

Exaktheit ist eine separate Einstellung von Aktualität. uv sync ist standardmäßig exakt und entfernt überflüssige Packages. uv run verwendet standardmäßig eine inexakte Synchronisierung, sofern nicht --exact angefordert wird.

Verwaltetes Python: eine Versionsanforderung, kein universelles Binary

uv kann Python-Distributionen herunterladen und verwalten:

uv python install 3.12 3.13
uv python list --only-installed
uv python pin 3.12

uv’s verwaltete CPython-Builds stammen aus dem Projekt python-build-standalone. uv kann außerdem System-Python, Homebrew, pyenv, Conda und andere Interpreter erkennen. Eine Übersicht der unterstützten Quellen und des Discovery-Verhaltens findest du in der Dokumentation zu Python-Versionen von uv.

.python-version ist eine von uv und anderen kompatiblen Tools erkannte Versionsanforderung. requires-python in pyproject.toml ist der Compatibility Contract des Projekts. Halte beide Angaben bewusst fest:

[project]
requires-python = ">=3.12,<3.14"

Das Pinnen von 3.12 garantiert weder für immer denselben Patch-Build noch dasselbe Artefakt auf jedem Betriebssystem. Fordere eine exakte Patch-Version an, wenn du eine bestimmte Version benötigst, und sorge dafür, dass CI den Interpreter explizit auswählt und ausgibt.

Verwende einen anderen Python Manager, wenn ein Projekt eine Distribution oder Build-Konfiguration benötigt, die uv nicht bereitstellt. uv kann diesen Interpreter trotzdem über --python oder über die normale Discovery verwenden.

Auswahl zwischen uv run, uvx und installierten Tools

An das Projekt gekoppelte Tools: uv run

Wenn pytest, mypy, ein Code Generator oder ein anderes Tool das Projekt importieren oder dessen gelockte Plugins verwenden muss, deklariere es in einer Dependency Group:

uv add --group lint ruff
uv run --group lint ruff check .

Wenn du dieses Tool über uvx ausführst, wird es vom Projekt isoliert. Dadurch kann das benötigte installierte Package oder Plugin möglicherweise nicht gefunden werden.

Ad-hoc-Tools: uvx

uvx ist ein Alias für uv tool run. Es erstellt eine isolierte Umgebung im wegwerfbaren uv-Cache. Die Dokumentation zu uv Tools beschreibt diesen Cache und den Lifecycle persistenter Tools:

uvx ruff@0.12.0 check .
uvx --from jupyterlab jupyter lab
uvx --with mkdocs-material mkdocs --help

Pinnen die Tool-Version in CI oder in der Dokumentation. Der erste Aufruf ohne Versionsangabe wählt ein aktuelles Release; spätere Aufrufe verwenden möglicherweise den vorhandenen Cache-Zustand erneut.

Persistente Executables: uv tool install

Installiere ein Tool, wenn Scripts außerhalb deiner Kontrolle dessen Command auf PATH benötigen oder wenn dein Machine-Setup-Manifest dafür verantwortlich sein soll:

uv tool install ruff
uv tool list
uv tool upgrade ruff
uv tool uninstall ruff

Auch persistente Tools verwenden isolierte Umgebungen. Verändere diese Umgebungen nicht manuell mit pip.

Scripts: Eine Datei als Release-Einheit

PEP 723 definiert Inline-Script-Metadaten. Ein kompatibler Runner kann den Kommentarblock lesen und eine isolierte Umgebung erstellen. Format und Runner-Verhalten werden im uv-Script-Guide und in PEP 723 beschrieben.

# /// script
# requires-python = ">=3.12"
# dependencies = [
#   "httpx>=0.27,<1",
# ]
# ///
import httpx

response = httpx.get("https://example.com", timeout=10)
response.raise_for_status()
print(response.status_code)

Führe das Script aus und bearbeite die Metadaten mit uv:

uv run fetch.py
uv add --script fetch.py rich
uv remove --script fetch.py rich

Normales python fetch.py ignoriert die Kommentar-Metadaten. Das Script benötigt daher einen kompatiblen Runner, obwohl die Python-Syntax weiterhin gültig ist.

Wenn ein Script eine spätere Reproduktion der Auflösung benötigt, erstelle ein benachbartes Lockfile:

uv lock --script fetch.py
uv run --script fetch.py

Dadurch wird fetch.py.lock geschrieben. Ein exclude-newer-Zeitstempel kann die Daten der infrage kommenden Distributionen einschränken. Er ist jedoch schwächer als eine exakt gelockte Auflösung und garantiert nicht, dass ein Artefakt weiterhin verfügbar ist.

Verwende stattdessen ein Projekt, wenn mehrere Dateien Dependencies gemeinsam nutzen, der Code als Package importierbar ist, Tests den Projektzustand benötigen oder mehrere Scripts gemeinsam weiterentwickelt werden müssen.

Requirements-Dateien: Kompatibilität statt Scheitern

Eine requirements.txt-Datei kann lose Inputs, exakte Pins, Hashes, Constraints, Indexes, URLs oder einen vom Resolver erzeugten Requirements-Export enthalten. Ihre Reproduzierbarkeit hängt davon ab, wie sie erzeugt und verwendet wurde. Der Dateiname allein sagt nichts aus.

Verwende die pip-kompatible Schnittstelle von uv, ohne zu migrieren:

uv venv
uv pip sync requirements.txt
uv run python app.py

uv pip sync bringt die Umgebung auf den Stand der Datei. uv pip install -r fügt lediglich hinzu.

Für eine selbst verantwortete Application kann eine schrittweise Migration sinnvoll sein:

uv init --bare
uv add -r requirements.in
uv add --group test -r requirements-test.in
uv lock
uv sync --locked

Führe den vollständigen Test- und Deployment-Pfad aus, bevor du alte Dateien löschst. Wenn ein nachgelagertes System weiterhin das pip-Format erwartet, leite es mit uv’s Export-Command aus dem validierten uv-Lockfile ab:

uv export --format requirements.txt \
  --output-file requirements.txt

Verwalte uv.lock und einen manuell bearbeiteten Export nicht als zwei konkurrierende Auflösungen.

Cache, Indexes und Supply-Chain-Grenzen

Der uv-Cache beschleunigt wiederholte Installationen, bleibt aber wegwerfbar:

uv cache prune
uv cache clean

Bevorzuge prune für die routinemäßige Bereinigung. clean entfernt alle Cache-Einträge und erzwingt bei späteren Aufrufen erneute Downloads und Builds.

Ein Lockfile verbessert die Reproduzierbarkeit. Es macht Dependencies jedoch nicht vertrauenswürdig. Prüfe Package-Quellen, Index-Konfiguration, Git-Revisions, Build-Backends, Lizenzen und Credentials. Halte authentifizierte Index-Konfiguration aus committeten Dateien heraus. Eine Ausnahme ist ein nicht geheimes Verweisziel auf einen freigegebenen Credential-Mechanismus.

Bei nativen Packages solltest du die Deployment-Architektur dokumentieren und die Verfügbarkeit von Wheels testen. Andernfalls kann ein Resolver auf einen Source-Build ausweichen, der Compiler und System-Libraries benötigt, die in CI oder Production fehlen.

Kompakte Betriebs-Checkliste

Für jedes Projekt:

  1. Definiere requires-python und direkte Dependencies in pyproject.toml.
  2. Trenne veröffentlichte Extras von lokalen Dependency Groups.
  3. Committe uv.lock. Ignoriere .venv und den Cache-Zustand.
  4. Führe projektgekoppelte Tools in der Projektumgebung aus.
  5. Verwende uv lock --check oder --locked in CI.
  6. Teste jedes Zielbetriebssystem und jede Zielarchitektur, die im Lockfile repräsentiert sind.
  7. Exportiere Kompatibilitätsformate nur für ausdrücklich benannte nachgelagerte Consumer.
  8. Prüfe Source- und Credential-Richtlinien unabhängig von der Auflösung.

uv ist besonders nützlich, wenn diese Ownership-Grenzen sichtbar bleiben. Ein Binary kann sie alle verwalten, ohne sie in eine einzige Umgebung zu verwandeln. Weniger Tools, während die vier Workflows getrennt bleiben. Deshalb verwende ich uv unter macOS weiterhin als mein standardmäßiges Python-Projekt-Tool.
