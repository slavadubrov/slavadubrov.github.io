uv unter macOS: Verwaltung von Python-Versionen, Projekten und Tools

Ich habe meinen Python-Arbeitsablauf auf uv umgestellt, da es die bisherige Tool-Wechselpraxis zwischen pip, virtuellen Umgebungen, pip-tools, pipx sowie Projektverwaltungswerkzeugen ersetzt. Ein einziger Ausführbarer übernimmt nun den Großteil dieser Aufgaben.

Die Arbeitsabläufe unterscheiden sich jedoch weiterhin. Ein Projekt, ein Skript mit Inline-Metadaten, eine einmalige CLI sowie eine installierte CLI verfügen jeweils über ihre eigene Umgebung und Lebensdauer. Diese Anleitung zeigt die von mir verwendeten Befehle sowie die Grenzen zwischen diesen Bereichen.

Schnellstart

# Install uv with Homebrew
brew install uv

# Start a project
uv init example-app
cd example-app
uv add httpx
uv run python main.py

# Run an isolated CLI without installing it permanently
uvx ruff check .

# Run a script that declares PEP 723 dependencies
uv run fetch.py

Kurzfassung: In Projekten verwende ich uv add, uv lock, uv sync und uv run; für selbstständige Skripte gelten die PEP 723-Metadaten; uvx dient einmaligen Tools, und uv tool install wird für Befehle verwendet, die auf PATH verbleiben müssen. In CI überprüft --locked, ob die Projektmetadaten mit uv.lock übereinstimmen; --frozen vertraut auf das vorhandene Lock-Datei, ohne deren Aktualität zu prüfen.

Installation von uv mit einem einzigen Owner

Homebrew ist ein praktischer Weg zur Installation unter macOS:

brew install uv
uv --version

Falls Homebrew bereits uv installiert hat, sollte es dieses aktualisieren:

brew upgrade uv

uv self update gilt für die eigenständige Installationsmethode von uv und ist bei Installationen über Paketmanager deaktiviert. Es darf nicht zu Konflikten zwischen zwei Installern für denselben Ausführbaren kommen.

Nützliche Identitätsbefehle:

command -v uv
uv python dir
uv tool dir
uv cache dir

Verwaltete Python-Installationen, persistente Tools sowie temporäre Cache-Einträge befinden sich in separaten Verzeichnissen. Der Cache kann gelöscht und neu erstellt werden; er stellt keine Quelle der Wahrheit dar.

Projekte: Deklaration, Auflösung und Umgebung

Ein uv-Projekt enthält in der Regel drei verschiedene Artefakte:

  • pyproject.toml deklariert die Projektmetadaten sowie direkte Abhängigkeiten.
  • uv.lock speichert die plattformunabhängige Auflösung durch uv.
  • .venv ist die lokal installierte Umgebung und sollte temporär sein.

Erstellen Sie eine Anwendung und fügen Sie Laufzeit- sowie Test-Abhängigkeiten hinzu:

uv init forecast-app
cd forecast-app

uv add httpx
uv add --group test pytest
uv run python main.py
uv run --group test pytest

Aktuelle uv-Anwendungsvorlagen erzeugen main.py, pyproject.toml, README.md und .python-version. Standardmäßig wird kein Build-System definiert. Verwenden Sie uv init --lib für eine paketierte Bibliothek mit einer src-Struktur und einem entsprechenden Build-Backend.

uv run prüft das Projekt, aktualisiert das Lock-Datei bei Bedarf, synchronisiert die erforderlichen Abhängigkeiten und führt den Befehl aus. Die erste Projektoperation erstellt bei Bedarf .venv und uv.lock; uv init selbst erzeugt lediglich die Projektdateien.

Commitnen Sie die Eingaben – nicht die Umgebung

Committen Sie pyproject.toml, uv.lock, die Quellcode-Dateien sowie einen bewusst festgelegten .python-version. Ignorieren Sie .venv sowie Uvs Caches.

Das Lock-Datei dokumentiert die Auflösung für unterstützte Plattformen und Marker; es sorgt nicht dafür, dass native Wheels unter macOS, Linux, Intel und Apple Silicon identisch sind. Testen Sie jede Deployment-Plattform.

Frische des Schlosses sichern: --locked entspricht nicht --frozen

Standardmäßig können Projektbefehle uv.lock aktualisieren, sobald sich die Deklarationen ändern.

Verwenden Sie --locked, um zu gewährleisten, dass das Schloss mit den Projektmetadaten übereinstimmt:

uv lock --check
uv sync --locked
uv run --locked pytest

Falls pyproject.toml und uv.lock nicht übereinstimmen, scheitern diese Befehle, anstatt ein neues Schloss zu erstellen. Dies stellt in der Regel die gewünschte CI-Sperre dar.

Verwenden Sie --frozen nur dann, wenn Sie explizit möchten, dass uv das vorhandene Schloss ohne Überprüfung seiner Aktualität verwendet:

uv sync --frozen

Dies kann in einer kontrollierten Build-Phase nützlich sein, in der das Schloss bereits validiert wurde, es handelt sich dabei jedoch nicht um einen Detektor für veraltete Schlösser. uv sync ist standardmäßig präzise und entfernt überflüssige Pakete; uv run verwendet standardmäßig eine unpräzise Synchronisation, es sei denn, --exact wird angefordert.

Verwalteter Python: Eine Versionsanfrage, kein universelles Binärpaket

uv kann Python-Distributionen herunterladen und verwalten:

uv python install 3.12 3.13
uv python list --only-installed
uv python pin 3.12

UVs verwaltete CPython-Builds stammen aus dem python-build-standalone-Projekt. Zudem kann uv System-, Homebrew-, pyenv-, Conda- sowie andere Interpreter erkennen.

.python-version ist eine von uv sowie anderen kompatiblen Tools erkannte Versionsanfrage. requires-python in pyproject.toml stellt den Kompatibilitätsvertrag des Projekts dar. Beides sollte absichtlich beibehalten werden:

[project]
requires-python = ">=3.12,<3.14"

Das Festpinnen von 3.12 garantiert weder dauerhaft denselben Patch-Build noch auf jedem Betriebssystem dasselbe Artefakt. Beantragen Sie einen exakten Patch nur dann, wenn dies tatsächlich erforderlich ist, und lassen Sie die CI explizit den Interpreter auswählen und melden.

Verwenden Sie einen anderen Python-Manager, wenn ein Projekt eine Distribution oder eine Build-Konfiguration benötigt, die uv nicht bereitstellt. UV kann diesen Interpreter weiterhin über --python oder normale Erkennungsmethoden nutzen.

Wahl zwischen uv run, uvx und installierten Tools

Projektgebundene Tools: uv run

Falls pytest, mypy, ein Codegenerator oder ein anderes Tool das Projekt importieren oder seine gesperrten Plugins verwenden muss, deklarieren Sie es in einer Abhängigkeitsgruppe:

uv add --group lint ruff
uv run --group lint ruff check .

Der Ausführung dieses Tools über uvx würde es vom Projekt isolieren und möglicherweise die benötigten installierten Pakete oder Plugins verbergen.

Ad-hoc-Tools: uvx

uvx ist ein Alias für uv tool run. Es erzeugt eine isolierte Umgebung, die im einmaligen uv-Cache gespeichert wird:

uvx ruff@0.12.0 check .
uvx --from jupyterlab jupyter lab
uvx --with mkdocs-material mkdocs --help

Pinnen Sie die Tool-Version in der CI oder in der Dokumentation. Bei einer ersten, unversionierten Aufrufung wird die aktuellste Version ausgewählt, während spätere Aufrufe den Cache-Zustand wiederverwenden können.

Dauerhafte Ausführbare: uv tool install

Installieren Sie ein Tool, wenn Skripte außerhalb Ihrer Kontrolle seinen Befehl auf PATH benötigen oder wenn das Maschinenmanifest es explizit besitzt:

uv tool install 'ruff==0.12.0'
uv tool list
uv tool upgrade ruff
uv tool uninstall ruff

Auch dauerhafte Tools nutzen weiterhin isolierte Umgebungen. Verändern Sie diese Umgebungen nicht manuell mit pip.

Skripte: Einzelnes Dateiformat als Release-Einheit

PEP 723 definiert Metadaten für Inline-Skripte. Ein kompatibler Runner kann den Kommentarblock lesen und eine isolierte Umgebung erstellen.

# /// script
# requires-python = ">=3.12"
# dependencies = [
#   "httpx>=0.27,<1",
# ]
# ///
import httpx


response = httpx.get("https://example.com", timeout=10)
response.raise_for_status()
print(response.status_code)

Metadaten können mit uv ausgeführt und geändert werden:

uv run fetch.py
uv add --script fetch.py rich
uv remove --script fetch.py rich

Reiner python fetch.py ignoriert die Kommentarmetadaten. Daher ist ein kompatibler Runner erforderlich, auch wenn die Python-Syntax weiterhin gültig ist.

Für Skripte, bei denen später eine bestimmte Lösung reproduziert werden muss, sollte ein zugehöriges Lock erstellt werden:

uv lock --script fetch.py
uv run --script fetch.py

Dadurch wird fetch.py.lock geschrieben. Ein exclude-newer-Timestamp kann die möglichen Veröffentlichungsdaten einschränken, ist jedoch schwächer als eine exakt gesperrte Lösung und garantiert nicht, dass das Ergebnis weiterhin verfügbar bleibt.

Verwenden Sie stattdessen ein Projekt, wenn mehrere Dateien gemeinsame Abhängigkeiten haben, der Code als Paket importiert werden soll, Tests den Projektzustand benötigen oder mehrere Skripte gemeinsam verschoben werden müssen.

Anforderungsdateien: Kompatibilität statt Ausfälle

Eine requirements.txt-Datei kann lose Eingaben, präzise Pins, Hashes, Einschränkungen, Indizes, URLs oder eine kompilierte Umgebung enthalten. Ihre Reproduzierbarkeit hängt davon ab, wie sie erstellt und genutzt wird; allein der Dateiname sagt nichts aus.

Nutzen Sie die pip-kompatible Schnittstelle von uv, ohne migrieren zu müssen:

uv venv
uv pip sync requirements.txt
uv run python app.py

uv pip sync stellt sicher, dass die Umgebung der Datei entspricht, während uv pip install -r additive Effekte hat.

Bei einer eigenen Anwendung kann eine schrittweise Migration nützlich sein:

uv init --bare
uv add -r requirements.in
uv add --group test -r requirements-test.in
uv lock
uv sync --locked

Führen Sie vor dem Löschen alter Dateien den vollständigen Test- und Bereitstellungsprozess aus. Falls ein nachgeschaltetes System weiterhin den pip-Format erwartet, ermitteln Sie diesen aus dem validierten uv Lock:

uv export --format requirements.txt \
  --output-file requirements.txt

Bewahren Sie weder uv.lock noch eine manuell bearbeitete Exportversion als zwei konkurrierende Lösungen auf.

Cache, Indizes und Grenzen der Lieferkette

Der uv-Cache verbessert wiederholte Installationen, bleibt aber verwendbar nur für einmalige Zwecke:

uv cache prune
uv cache clean

Für routinemäßige Reinigungen ist prune vorzuziehen. clean löscht alle Cache-Einträge und zwingt zu erneuten Downloads sowie Kompilierungen.

Ein Lockfile erhöht die Wiederholbarkeit, macht die Abhängigkeiten aber nicht automatisch zuverlässig. Überprüfen Sie die Quellen der Pakete, die Index-Konfiguration, Git-Revisionen, Build-Backends, Lizenzen sowie Zugangsdaten. Halten Sie authentifizierte Index-Konfigurationen außerhalb von committenen Dateien, es sei denn, der Repository enthält ausschließlich nicht-sensitive Verweise auf ein genehmigtes Authentifizierungsverfahren.

Für native Pakete sollten die Bereitstellungsarchitektur sowie die Verfügbarkeit der Test-Wheels dokumentiert werden. Andernfalls könnte ein Resolver auf eine Quellkompilation zurückgreifen, die Compiler sowie Systembibliotheken erfordert, die im CI oder in der Produktion fehlen.

Eine kompakte Checkliste für die Arbeit

Für jedes Projekt:

  1. Definieren Sie requires-python sowie direkte Abhängigkeiten in pyproject.toml.
  2. Trennen Sie veröffentlichte Zusatzkomponenten von lokalen Abhängigkeitsgruppen.
  3. Commitpen Sie uv.lock; ignorieren Sie .venv sowie den Cache-Zustand.
  4. Führen Sie projektbezogene Tools innerhalb der Projektumgebung aus.
  5. Verwenden Sie in CI uv lock --check oder --locked.
  6. Testen Sie jede Ziel-OS-Plattform sowie Architektur, die durch den Lock repräsentiert wird.
  7. Exportieren Sie Kompatibilitätsformate nur für benannte Nachfrager.
  8. Überprüfen Sie die Quellcode- und Zugangsdatenpolitik unabhängig von der gewählten Lösung.

uv ist am nützlichsten, wenn diese Eigentumsgrenzen sichtbar bleiben. Ein einzelnes Binär kann sie alle verwalten, ohne daraus eine einzige Umgebung zu machen. Genau diese Kombination – weniger Tools, ohne anzunehmen, jeder Workflow sei identisch – ist der Grund, warum ich es weiterhin als meine Standard-Tool für Python-Projekte unter macOS verwende.
