Zsh-Startdateien: ~/.zprofile gegen ~/.zshrc unter macOS und Linux

Falls Ihre Terminalanwendung langsam reagiert oder eine Umgebungsvariable in einem Terminal vorhanden ist, aber nicht im anderen, liegt die Ursache oft am Startmodus von Zsh. Die beiden am häufigsten genutzten Dateien sind ~/.zprofile und ~/.zshrc, doch allein aus den Dateinamen geht nicht hervor, ob eine bestimmte Zeile dorthin gehört.

Zsh wählt die zu ladenden Startdateien anhand zweier unabhängiger Kriterien aus: ob es sich um eine Login-Shell handelt und ob der Shell-Modus interaktiv ist. Terminalanwendungen unter macOS und Linux können unterschiedliche Kombinationen verwenden, weshalb man die aktuell laufende Shell prüfen sollte, anstatt anzunehmen, dass das Betriebssystem dies automatisch entscheidet.

Kurzfassung: Legen Sie die Initialisierung für Login-Sessions in .zprofile und das interaktive Verhalten in .zshrc ab. Halten Sie .zshenv möglichst leer und minimal. Verschieben Sie keine Hooks für das interaktive Version-Management in .zprofile und importieren Sie auch nicht das gesamte Profil aus .zshrc; prüfen Sie stattdessen den von der jeweiligen Anwendung erzeugten Code sowie die dortigen Anweisungen für Zsh.

Zsh bewertet zwei unabhängige Flags

Eine Shell kann folgende Eigenschaften aufweisen:

  • sowohl Login- als auch interaktiv, wie es bei Apple Terminal üblich ist, da hier normalerweise die Standard-Login-Shell des Benutzers gestartet wird
  • weder Login- noch interaktiv, wie es bei eingebetteten zsh oder vielen Linux-Terminalkonfigurationen der Fall ist
  • sowohl Login- als auch nicht-interaktiv, wie es bei zsh -lc 'command' der Fall ist
  • weder Login- noch nicht-interaktiv, wie es bei zsh -c 'command' der Fall ist

Terminalanwendungen, IDEs, Remote-Sessions, Multiplexer sowie explizite Shell-Flags können unterschiedliche Modi wählen. Das Betriebssystem allein bestimmt den Modus nicht.

Stellen Sie lieber die aktuell laufende Shell zur Frage, anstatt zu raten:

print -r -- "interactive=$options[interactive] login=$options[login]"

Der tatsächliche Startablauf

Zsh liest zunächst die globalen Dateien und anschließend die entsprechenden Benutzerdateien. Bei den standardmäßigen RCS-Einstellungen erfolgt die Lesereihenfolge der Benutzerdateien wie folgt:

  1. $ZDOTDIR/.zshenv bei jeder Aufrufung von Zsh
  2. $ZDOTDIR/.zprofile, falls es sich um eine Login-Shell handelt
  3. $ZDOTDIR/.zshrc, falls der Shell-Modus interaktiv ist
  4. $ZDOTDIR/.zlogin, falls es sich um eine Login-Shell handelt
  5. $ZDOTDIR/.zlogout, wenn eine Login-Shell normal beendet wird

Falls ZDOTDIR nicht gesetzt ist, verwendet Zsh $HOME. Die systemweiten Dateipfade hängen von der Installation ab; die gängigen Standardwerte sind /etc/zshenv, /etc/zprofile, /etc/zshrc, /etc/zlogin und /etc/zlogout.

Diese Reihenfolge dient lediglich als Filter und garantiert keinen vollständigen Lebenszyklus. .zprofile wird einmal pro Login-Shell-Prozess ausgeführt, nicht einmal pro Computer-Login. Wenn jede neue Terminalleiste eine Login-Shell startet, wird diese Datei in jeder Leiste gelesen.

Halten Sie .zshenv unkompliziert

Jeder nicht-interaktive zsh -c liest .zshenv ein. Ein echo, ein Aufruf eines Paketmanagers oder ein aufwendiger Unterprozess dort kann die Befehlsausgabe verfälschen und Skripte verlangsamen. Die meisten Benutzer benötigen in dieser Datei wenig oder gar nichts.

Eine exportierte Variable in .zprofile wird von den Kindprozessen dieser Anmelde-Shell geerbt. Sie wird jedoch nicht automatisch in unverwandte GUI-Anwendungen, Dienste oder Shells injiziert, deren Elternprozess die Datei nie gelesen hat.

Verwenden Sie .zprofile für rein anmeldebezogene Einrichtungen

Ein kleines Profil kann exportierte Standardwerte sowie einen idempotenten Pfad festlegen:

# ~/.zprofile
export EDITOR=nvim
export VISUAL=nvim

# Zsh ties the path array to the PATH scalar.
typeset -U path PATH
path=("$HOME/.local/bin" $path)
export PATH

typeset -U entfernt doppelte Array-Einträge. Dadurch wird das wiederholte Einbinden sicherer, wobei Startdateien dennoch unnötige Arbeiten vermeiden sollten.

Verwenden Sie .zshrc für interaktiven Zustand

# ~/.zshrc
setopt auto_cd hist_ignore_all_dups share_history

autoload -Uz compinit
compinit

alias ll='ls -lah'
bindkey -e

Aliase, Kompletterungs-Widgets, Tastenkarten, Prompts sowie Hooks für Verzeichniswechsel gehören zur interaktiven Shell, die sie verwendet.

Versionierungsmanager überschreiten die einfache Dateigrenze

„Versionierungsmanager in .zprofile platzieren, weil sie langsam sind“, ist kein zuverlässiger Rat. Ein Versionierungsmanager kann verschiedene Arten von Code erzeugen:

  • einen statischen Pfad oder eine Root-Variable
  • einen Pfad für Befehlsshims, der von Kindprozessen benötigt wird
  • Definitionen für Kompletterungen
  • Shell-Funktionen, die die aktuelle Shell verändern
  • Hooks für Verzeichniswechsel zur automatischen Versionswechsel

Die interaktiven Teile müssen in jeder interaktiven Shell vorhanden sein – einschließlich einer in einem Editor gestarteten verschachtelten zsh. Daher weist die aktuelle fnm-Dokumentation diesen Hook in .zshrc aus:

eval "$(fnm env --use-on-cd --shell zsh)"

Auch die aktuelle pyenv-Dokumentation platziert die vollständige interaktive Initialisierung in .zshrc:

export PYENV_ROOT="$HOME/.pyenv"
[[ -d $PYENV_ROOT/bin ]] && path=("$PYENV_ROOT/bin" $path)
eval "$(pyenv init - zsh)"

Pyenv dokumentiert einen enger gefassten pyenv init --path-Modus für die Einrichtung von shim-Pfaden, doch der vollständige pyenv init-Modus installiert zusätzlich Funktionen zur Autocompletion sowie Shell-Funktionen. Prüfen Sie vor der Aufteilung stets die aktuelle Dokumentation sowie die erzeugten Ausgaben eines Tools.

Falls der Startzeitraum langsam ist, messen Sie diesen Wert zunächst, bevor Sie Code in einen Modus verschieben, in dem das Tool nicht mehr funktioniert.

Verwenden Sie nicht das gesamte Profil aus .zshrc

Eine gängige plattformübergreifende Lösung besteht darin:

# Avoid this blanket coupling.
source ~/.zprofile

Dadurch werden Aktionen, die ausschließlich beim Anmelden ausgeführt werden, in Aktionen pro interaktiver Shell umgewandelt, wodurch der Agent neu gestartet, auf den Schlüsselbund zugegriffen, Ausgaben erzeugt oder Pfade geändert werden können.

Falls sowohl interaktive Shells nach Anmeldung als auch solche ohne Anmeldung eine kleine Anzahl statischer Exporte benötigen, extrahieren Sie einen idempotenten Fragment und importieren Sie diesen gezielt:

# ~/.config/zsh/environment.zsh
typeset -U path PATH
path=("$HOME/.local/bin" $path)
export PATH EDITOR=nvim VISUAL=nvim
# ~/.zprofile
source "$HOME/.config/zsh/environment.zsh"
# ~/.zshrc
if [[ ! -o login ]]; then
  source "$HOME/.config/zsh/environment.zsh"
fi

# Interactive-only configuration follows.

Dieses Muster hält gemeinsame Daten getrennt von Effekten, die beim Anmelden auftreten. Eine weitere valide Alternative besteht darin, den Terminal oder Session-Manager einheitlich zu konfigurieren, anstatt beide Modi zu unterstützen.

Diagnostizieren Sie die langsame Shell oder den fehlenden Zustand

Reproduzieren Sie jeden Modus direkt:

zsh -lic 'print "login interactive"'
zsh -ic  'print "non-login interactive"'
zsh -lc  'print "login non-interactive"'
zsh -c   'print "non-login non-interactive"'

Messen Sie außerdem, welchen Modus die Benutzer tatsächlich verwenden:

time zsh -lic exit
time zsh -ic exit

Wenn die Quelle unklar ist, verfolgen Sie die Ausführung von Dateien und Zeilen:

PS4='%N:%i> ' zsh -xlic exit

Führen Sie die Protokollierung in einem sauberen Testkonto aus oder prüfen Sie sie vor dem Teilen – Startbefehle können Tokens sowie andere sensible Werte erweitern.

Bei einem fehlenden Ausführbaren prüfen Sie sowohl den Modus als auch den Pfad:

print -r -- "interactive=$options[interactive] login=$options[login]"
print -l -- $path
whence -va python node uv

Fazit

Die relevante Unterscheidung liegt nicht zwischen „Umgebung“ und „Aliassen“, sondern zwischen Zuständen, die ausschließlich beim Anmelden bestehen, und interaktiven Zuständen, ergänzt durch jene wenigen Elemente, die tatsächlich in jedem Zsh-Prozess wirken müssen.

Stellen Sie sicher, dass die Shell-Flags korrekt sind, halten Sie die Startdateien unauffällig und platzieren Sie jede generierte Hook-Funktion dort, wo alle erforderlichen Funktionen vorhanden sind. Dadurch wird die Konfiguration unabhängig von den jeweiligen Terminal-Anwendungen portabel, ohne vorgeben zu müssen, macOS und Linux hätten jeweils einen festen Startmodus.
