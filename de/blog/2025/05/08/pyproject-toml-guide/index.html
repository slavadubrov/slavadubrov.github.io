pyproject.toml Leitfaden: Python-Paketierung, Abhängigkeiten und Konfiguration von Tools

Ältere Python-Projekte verteilen die Konfiguration oft auf setup.py, setup.cfg, Requirements-Dateien, MANIFEST.in sowie separaten Dateien für Entwicklungswerkzeuge. pyproject.toml bietet einen zentralen Ort für all diese Aspekte, ersetzt jedoch nicht alle Projektdateien oder macht nicht jeden Abschnitt zu einem einheitlichen Standard.

Dieser Leitfaden führt durch die Datei – von der Build-Konfiguration über die Projektmetadaten bis hin zu den Tool-Einstellungen. Um die Übersichtlichkeit zu gewährleisten, werden vier Verantwortungsbereiche unterschieden: Was das Projekt kompiliert, was veröffentlicht wird, was lokale Entwickler benötigen, und welche Tools welche Einstellungen vornehmen.

Kurzfassung: Verwenden Sie [build-system] für den Backend, der eine Distribution erstellt, [project] für veröffentlichte Metadaten sowie Laufzeitabhängigkeiten, [dependency-groups] für unveröffentlichte Entwicklungsumgebungen – und [tool.*] ausschließlich dann, wenn die Dokumentation des jeweiligen Tools dies vorschreibt. Eine Abhängigkeitsdeklaration ist kein Lockfile.

Eine Datei, vier Verantwortungsbereiche

Drei Paketierungsstandards legen die grundlegende Struktur fest:

  • PEP 518 definiert die Anforderungen an das Build-System.
  • PEP 621 definiert die Projektmetadaten.
  • PEP 735 definiert unveröffentlichte Abhängigkeitsgruppen.

Tool-Entwickler können außerdem einen Namespace unter [tool] definieren. Dieser Bereich ist zwar üblich, aber nicht universell geregelt – jedes Tool legt seine eigenen Schlüssel und Verhaltensweisen fest.

Hier ist eine kleine, gepackte Bibliothek:

[build-system]
requires = ["hatchling>=1.26"]
build-backend = "hatchling.build"

[project]
name = "weather-client"
version = "0.1.0"
description = "A small weather API client"
readme = "README.md"
requires-python = ">=3.11"
dependencies = [
  "httpx>=0.27",
]

[project.optional-dependencies]
cli = ["rich>=13"]

[project.scripts]
weather = "weather_client.cli:main"

[dependency-groups]
test = ["pytest>=8", "pytest-cov>=5"]
lint = ["ruff>=0.12"]

[tool.pytest.ini_options]
testpaths = ["tests"]

[tool.ruff]
line-length = 100
target-version = "py311"

Jede Abhängigkeitsliste beantwortet eine andere Frage. Genau diese Unterscheidung bildet das Kernprinzip der Datei.

[build-system]: Wie aus Quellcode eine Distribution entsteht

Ein Build-Frontend wie python -m build, pip oder uv ruft einen Build-Backend auf. Der Backend entscheidet, wie aus dem Quellbaum ein sdist oder wheel entsteht und welche Dateien in diese Artefakte aufgenommen werden.

[build-system]
requires = ["hatchling>=1.26"]
build-backend = "hatchling.build"

requires enthält die zur Ausführung des Backends in seiner isolierten Build-Umgebung erforderlichen Abhängigkeiten. Es handelt sich dabei nicht um die Laufzeitabhängigkeitsliste Ihres Pakets.

Declarieren Sie ein Build-System, wenn das Projekt eine Distribution erzeugt oder seinen eigenen Code als Paket installieren muss. Auch Nicht-Paket-Projekte können weiterhin pyproject.toml nutzen – PEP 735 erlaubt sogar eine Datei, die ausschließlich Abhängigkeitsgruppen enthält. Umgebungsmanager behandeln Projekte ohne Build-System unterschiedlich, daher sollte diese Entscheidung bewusst getroffen werden.

Wählen Sie den Backend entsprechend den Build-Anforderungen aus:

  • Layout und Dateiauswahl für reine Python-Anwendungen
  • Kompilierte Erweiterungen oder externe Build-Systeme
  • Anforderungen an dynamische Versionen oder generierte Dateien
  • Verhalten bei „editable-install“
  • Reifegrad des Backends im Release-Pipeline

Kopieren Sie die aktuell empfohlene Tabelle des Backends aus dessen Dokumentation. Fügen Sie wheel nicht aus Gewohnheit zu den Build-Anforderungen hinzu – der Backend gibt selbst an, was er benötigt.

[project]: Was die Metadatenkonsumenten erhalten

Die [project]-Tabelle beschreibt die Distribution: ihren Namen, die Version, die Kompatibilität mit Python, die Laufzeitabhängigkeiten, die Einstiegspunkte sowie weitere Index-Metadaten.

[project]
name = "weather-client"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = ["httpx>=0.27"]

Die Abhängigkeitsspezifikatoren stellen Einschränkungen für einen Resolver dar und keine Abbildung eines bestimmten Umgebungszustands. Sie werden Teil der Metadaten von Wheel- und sdist-Dateien, sodass nachfolgende Installer sie mit Anforderungen aus anderen Paketen kombinieren können.

Extras bilden eine öffentliche Installations-Schnittstelle

[project.optional-dependencies] definiert die Extras, die Verbraucher anfordern können:

[project.optional-dependencies]
cli = ["rich>=13"]
postgres = ["psycopg[binary]>=3.2"]

Ein Verbraucher kann weather-client[cli] installieren. Da Namen sowie Anforderungen dieser Extras veröffentlicht werden, sollten sie als Produktfunktionen betrachtet werden. Verwenden Sie kein Extra mit dem Namen dev ausschließlich dazu, alle Tools der Mitwirkenden zu speichern.

Eingangspunkte verbinden installierte Befehle mit Python

[project.scripts]
weather = "weather_client.cli:main"

Nach der Installation der Distribution stellt die Umgebung weather bereit, welches wiederum weather_client.cli:main importiert und aufruft. Testen Sie den Befehl anhand einer erstellten Wheel-Datei – nicht nur am Repository-Root –, da die Nutzer letztlich diese Wheel-Datei erhalten.

[dependency-groups]: lokale, unveröffentlichte Umgebungen

PEP 735 beschreibt Abhängigkeitsgruppen für Entwicklungs- oder nicht-paketbasierte Umgebungen, ohne diese als Paketmetadaten zu veröffentlichen.

[dependency-groups]
test = ["pytest>=8", "pytest-cov>=5"]
lint = ["ruff>=0.12"]
dev = [
  { include-group = "test" },
  { include-group = "lint" },
]

Dies bildet die angemessene Grenze für Tests, Linter, Dokumentationsgeneratoren sowie ähnliche Tools der Mitwirkenden. Zudem ist sie nützlich für Anwendungen oder Notebooks, die keine eigene Distribution erstellen. Abhängigkeitsgruppen sind standardisierte Daten, doch die Schnittstellen der Installer variieren weiterhin. Prüfen Sie, wie der gewählte Umgebungsmanager sie installiert, absichert und löst. PEP 735 legt keine universelle Kommandozeilschnittstelle fest.

[tool.*]: Konfigurationen, die einem Tool gehören

Tool-Tabellen teilen kein gemeinsames Schema:

[tool.pytest.ini_options]
addopts = "-ra"
testpaths = ["tests"]

[tool.ruff]
line-length = 100

Verwenden Sie eine [tool.*]-Tabelle nur dann, wenn das Tool dies explizit vorschreibt. Einige Einstellungen sollten weiterhin in eigenen Dateien gespeichert werden, weil ein anderes Ökosystem sie benötigt, die Datei ein anderes Format erfordert oder die Konfiguration in isolierter Form klarer ist. pyproject.toml dient lediglich als Koordinationspunkt und nicht als Vorgabe, alles zentral zu erfassen.

Deklarationen, Lockdateien und Anforderungsdateien lösen unterschiedliche Probleme

Die häufigste Quelle von Verwirrung besteht darin, jedes Abhängigkeitsartefakt als konkurrierende Quelle der Wahrheit zu betrachten.

ArtefaktHaupteinsatzzweckTypische Inhalte
[project.dependencies]Veröffentlichter LaufzeitvertragDirekte Anforderungen sowie kompatible Versionsbereiche
[project.optional-dependencies]Veröffentlichte, optional nutzbare FunktionenFür Verbraucher zugängliche Extras
[dependency-groups]Unveröffentlichte lokale UmgebungenGruppen für Tests, Linting, Dokumentation oder Anwendungen
LockfileWiederherstellung einer gelösten UmgebungGenaue Versionen, Quellen sowie Metadaten zur Lösung
requirements.txtPip-kompatible InstallationsdatenAnforderungen zusammen mit pip-spezifischen Optionen, Einschränkungen, URLs oder Hash-Werten

Eine Bibliothek gibt in der Regel kompatible Einschränkungen sowie Tests für einen bestimmten Bereich bereit. Eine Anwendung speichert üblicherweise das Lockfile des Umgebungsmanagers. Genaue Versionsangaben sollten im finalen Deployment-Artifact enthalten sein und nicht blind in den öffentlichen Metadaten der Bibliothek.

Falls eine Integration die Formatierung oder Funktionen von pip erfordert, sollte ein Anforderungsdatei aufbewahrt werden. Wenn ein mit uv verwaltetes Projekt eine solche Datei benötigt, muss sie aus dem Lockfile exportiert werden, anstatt zwei unabhängige Abhängigkeitsmengen zu pflegen:

uv export --format requirements.txt --output-file requirements.txt

Der Export stellt eine abgeleitete Kompatibilitätsausgabe dar. Das Lockfile bleibt weiterhin die Quelle für diesen Arbeitsablauf.

Eine Migration, die das Verhalten beibehält

Beginnen Sie nicht damit, setup.py oder requirements.txt zu löschen. Zuerst klassifizieren Sie die Funktion jedes bestehenden Files.

  1. Erstellen Sie eine Übersicht über die Build-Logik, Metadaten, Laufzeitanforderungen, Zusatzkomponenten, Entwicklerumgebungen, Tool-Einstellungen, Paketdaten sowie Einstiegspunkte.
  2. Wählen Sie einen Backend, der aktuelle Dateiinklusionen, kompilierte Artefakte sowie editierbare Installationen reproduzieren kann.
  3. Verschieben Sie statische, veröffentlichte Metadaten in [project]; wirklich dynamische Felder sollten explizit bleiben.
  4. Legen Sie Anforderungen, die nur für Mitwirkende bestimmt sind, in [dependency-groups] ab – nicht in öffentliche Zusatzkomponenten.
  5. Fügen Sie Tool-Einstellungen nur dann hinzu, wenn das jeweilige Tool äquivalente Semantiken unterstützt.
  6. Erstellen Sie sowohl einen sdist- als auch einen wheel-Format-Datei, prüfen deren Inhalte und installieren anschließend den wheel in einer sauberen Umgebung.
  7. Rufen Sie die Einstiegspunkte, Tests, Import-Prüfungen sowie den tatsächlichen Deployment-Pfad auf.
  8. Lösen Sie alte Konfigurationen erst dann auf, wenn Artefakte und Verhalten übereinstimmen.

MANIFEST.in kann bei einigen setuptools-basierten Strukturen weiterhin erforderlich sein, und ein kleiner setup.py kann für programmgesteuertes Build-Verhalten weiterhin gültig sein. Modernisierung bedeutet lediglich einen Wechsel des Verantwortungsträgers – keinen Wettbewerb um das Löschen von Dateien.

Ein aktueller uv-Arbeitsablauf

uv unterscheidet bei der Erstellung eines Projekts zwischen Anwendungen und Bibliotheken:

# Non-library application template
uv init weather-app

# Packaged library with a src layout and build system
uv init --lib weather-client

uv init erzeugt die Projektdateien. Die erste Projektoperation, wie z. B. uv run, uv sync oder uv lock, erstellt je nach Bedarf das Lockfile sowie das persistente .venv.

cd weather-client
uv add httpx
uv add --group test pytest pytest-cov
uv run pytest
uv build

Derzeit platziert uv lokale Entwicklungsanforderungen in standardisierten Abhängigkeitsgruppen. Der eingebettete uv_build-Backend ist eine Option für reine Python-Projekte; für kompilierte Erweiterungen sind Alternativen wie maturin oder scikit-build-core erforderlich.

Fazit

pyproject.toml wird klar, wenn jede Tabelle ein eindeutiges Publikum hat. Die Isolation der Builds gehört zu [build-system], das veröffentlichte Verhalten zu [project], die Entwicklerumgebungen zu [dependency-groups]. Tool-weite Änderungen gehören zum jeweiligen Tool, das sie definiert.

Sobald diese Grenzen stabil sind, lässt sich der Code leichter überprüfen – und Migrationsprozesse vermischen nicht mehr die Paketmetadaten mit der gelösten Umgebung eines einzelnen Rechners.
