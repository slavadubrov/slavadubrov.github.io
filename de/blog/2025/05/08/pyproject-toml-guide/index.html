Leitfaden zu pyproject.toml: Packaging, Dependencies und Tools

Viacheslav Dubrov

2025-05-08 · Aktualisiert 2026-07-15 · 5 Min. · Entwicklungswerkzeuge

Automatische Übersetzung Dieser Artikel wurde automatisch aus der englischen Originalversion übersetzt.

Ältere Python-Projekte verteilten ihre Konfiguration oft über setup.py, setup.cfg, Requirements-Dateien, MANIFEST.in und separate Dateien für Development-Tools. pyproject.toml bietet diesen Themen einen gemeinsamen Ort, ersetzt jedoch nicht jede Projektdatei und macht nicht jeden Abschnitt zu einem Bestandteil eines einzigen Standards.

Dieser Leitfaden führt durch die Datei – von der Build-Konfiguration über Projektmetadaten bis zu Tool-Einstellungen. Vier Verantwortliche halten die Abschnitte getrennt: Was baut das Projekt, was veröffentlicht das Projekt, was benötigen Contributors lokal, und welche Konfigurationen verwalten die einzelnen Tools?

TL;DR. Verwende [build-system] für das Backend, das eine Distribution baut, [project] für veröffentlichte Metadaten und Runtime-Dependencies, [dependency-groups] für nicht veröffentlichte Development-Umgebungen und [tool.*] nur dort, wo es die Dokumentation des jeweiligen Tools vorsieht. Eine Dependency-Deklaration ist kein Lockfile.

Eine Datei, vier Verantwortliche

Drei Packaging-Standards haben die Kernstruktur etabliert:

  • PEP 518 definiert die Anforderungen an das Build-System.
  • PEP 621 definiert die Projektmetadaten.
  • PEP 735 definiert nicht veröffentlichte Dependency-Gruppen.

Tool-Autoren können außerdem einen Namespace unter [tool] beanspruchen. Was dort abgelegt wird, ist nicht standardisiert: Jedes Tool definiert seine eigenen Keys und sein eigenes Verhalten.

Hier ist eine kleine gepackte Library:

[build-system]
requires = ["hatchling>=1.26"]
build-backend = "hatchling.build"

[project]
name = "weather-client"
version = "0.1.0"
description = "A small weather API client"
readme = "README.md"
requires-python = ">=3.11"
dependencies = [
  "httpx>=0.27",
]

[project.optional-dependencies]
cli = ["rich>=13"]

[project.scripts]
weather = "weather_client.cli:main"

[dependency-groups]
test = ["pytest>=8", "pytest-cov>=5"]
lint = ["ruff>=0.12"]

[tool.pytest.ini_options]
testpaths = ["tests"]

[tool.ruff]
line-length = 100
target-version = "py311"

Jede Dependency-Liste beantwortet eine andere Frage.

[build-system]: Wie aus Source eine Distribution wird

Ein Build-Frontend wie python -m build, pip oder uv ruft ein Build-Backend auf. Das Backend entscheidet, wie aus dem Source-Tree eine sdist oder ein Wheel entsteht und welche Dateien in diese Artefakte aufgenommen werden.

[build-system]
requires = ["hatchling>=1.26"]
build-backend = "hatchling.build"

requires enthält die Dependencies, die zum Ausführen des Backends in seiner isolierten Build-Umgebung benötigt werden. Es handelt sich nicht um die Runtime-Dependencies deines Packages.

Deklariere ein Build-System, wenn das Projekt eine Distribution erzeugt oder der eigene Code als Package installiert werden muss. Auch ein Non-Package-Projekt kann pyproject.toml verwenden; PEP 735 erlaubt sogar eine Datei, die ausschließlich Dependency-Gruppen enthält. Environment-Manager unterscheiden sich darin, wie sie ein Projekt ohne Build-System behandeln. Triff diese Entscheidung daher bewusst.

Wähle das Backend anhand der Build-Anforderungen:

  • Pure-Python-Layout und Anforderungen an die Dateiauswahl
  • Compiled Extensions oder externe Build-Systeme
  • Anforderungen an dynamische Versionen oder generierte Dateien
  • Verhalten bei Editable Installs
  • Reifegrad des Backends in der Release-Pipeline

Übernimm die aktuell empfohlene Tabelle des Backends aus dessen Dokumentation. Füge wheel nicht aus Gewohnheit zu den Build-Anforderungen hinzu; das Backend definiert selbst, was es benötigt.

[project]: Welche Metadaten Consumers erhalten

Die Tabelle [project] beschreibt die Distribution: ihren Namen, ihre Version, die Python-Kompatibilität, Runtime-Dependencies, Entry-Points und weitere Index-Metadaten.

[project]
name = "weather-client"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = ["httpx>=0.27"]

Die Dependency-Specifier sind Constraints für einen Resolver, kein Snapshot einer einzelnen Umgebung. Sie werden Teil der Metadaten von Wheel und sdist, sodass nachgelagerte Installer sie mit den Requirements anderer Packages kombinieren können.

Extras sind eine öffentliche Installationsschnittstelle

[project.optional-dependencies] definiert Extras, die Consumers anfordern können:

[project.optional-dependencies]
cli = ["rich>=13"]
postgres = ["psycopg[binary]>=3.2"]

Ein Consumer kann weather-client[cli] installieren. Da Extra-Namen und Requirements veröffentlicht werden, solltest du sie als Produktfähigkeiten behandeln. Verwende kein Extra namens dev, nur um darin alle Contributor-Tools abzulegen.

Entry-Points verbinden installierte Commands mit Python

[project.scripts]
weather = "weather_client.cli:main"

Nach der Installation der Distribution stellt die Umgebung weather bereit. Dieser Command importiert weather_client.cli:main und ruft es auf. Teste den Command mit einem gebauten Wheel und nicht nur aus dem Repository-Root; Das Wheel ist das Artefakt, das die Nutzer erhalten.

[dependency-groups]: lokale, nicht veröffentlichte Umgebungen

Byte says

Ich hielt jahrelang jedes Contributor-Tool in einem dev-Extra. Die Installation funktionierte, deshalb sah ich nie nach. Das Extra stand die ganze Zeit in den veröffentlichten Wheel-Metadaten, und jeder konnte es anfordern.

Dependency-Gruppen nach PEP 735 beschreiben Development- oder Non-Package-Umgebungen, ohne sie als Package-Metadaten zu veröffentlichen.

[dependency-groups]
test = ["pytest>=8", "pytest-cov>=5"]
lint = ["ruff>=0.12"]
dev = [
  { include-group = "test" },
  { include-group = "lint" },
]

Dies ist die richtige Grenze für Tests, Linter, Documentation-Builder und ähnliche Contributor-Tools. Es ist außerdem für Applications oder Notebooks nützlich, die keine Distribution bauen.

Dependency-Gruppen sind standardisierte Daten, die Installer-Schnittstellen unterscheiden sich jedoch weiterhin. Prüfe, wie der ausgewählte Environment-Manager sie installiert, lockt und auflöst. PEP 735 definiert keine universelle Command-Line-Schnittstelle.

[tool.*]: Konfiguration im Besitz eines einzelnen Tools

Tool-Tabellen verwenden kein gemeinsames Schema:

[tool.pytest.ini_options]
addopts = "-ra"
testpaths = ["tests"]

[tool.ruff]
line-length = 100

Verwende eine Tabelle [tool.*] nur, wenn das Tool sie dokumentiert. Manche Einstellungen gehören weiterhin in eigene Dateien, weil ein anderes Ökosystem sie konsumiert, die Datei ein anderes Format benötigt oder die Konfiguration dort übersichtlicher ist. pyproject.toml ist ein Koordinationspunkt. Es verlangt nicht, jede Einstellung zu zentralisieren.

Deklarationen, Locks und Requirements-Dateien lösen unterschiedliche Probleme

Eine häufige Ursache für Verwirrung ist, jedes Dependency-Artefakt als konkurrierende Quelle der Wahrheit zu behandeln.

ArtefaktHauptzweckTypische Inhalte
[project.dependencies]Veröffentlichter Runtime-VertragDirekte Requirements und kompatible Bereiche
[project.optional-dependencies]Veröffentlichte Opt-in-FähigkeitenConsumer-facing Extras
[dependency-groups]Nicht veröffentlichte lokale UmgebungenTest-, Lint-, Docs- oder Application-Gruppen
LockfileReproduzierbare aufgelöste UmgebungExakte Versionen, Quellen und Resolution-Metadaten
requirements.txtPip-kompatibler InstallationsinputRequirements plus Pip-spezifische Optionen, Constraints, URLs oder Hashes

Eine Library veröffentlicht normalerweise kompatible Constraints und testet gegen einen Versionsbereich. Eine Application committed üblicherweise das Lockfile des Environment-Managers. Exakte Pins gehören in das aufgelöste Deployment-Artefakt und nicht blind in die öffentlichen Metadaten einer Library.

Behalte eine Requirements-Datei bei, wenn eine Integration das Format oder die Features von pip benötigt. Falls ein uv-managed Project eine solche Datei benötigt, exportiere sie aus dem Lock, statt zwei unabhängige Dependency-Sets zu pflegen:

uv export --format requirements.txt --output-file requirements.txt

Der Export ist abgeleitete Kompatibilitätsausgabe. Das Lock bleibt für diesen Workflow die aufgelöste Quelle.

Eine Migration, die das Verhalten beibehält

Beginne nicht damit, setup.py oder requirements.txt zu löschen. Klassifiziere zuerst, welche Funktion jede bestehende Datei erfüllt.

  1. Erfasse Build-Logik, Metadaten, Runtime-Requirements, Extras, Developer-Umgebungen, Tool-Einstellungen, Package-Daten und Entry-Points.
  2. Wähle ein Backend, das die aktuelle Dateiauswahl, Compiled Artifacts und Editable Installs reproduzieren kann.
  3. Verschiebe statische veröffentlichte Metadaten nach [project]; halte tatsächlich dynamische Felder explizit.
  4. Verschiebe ausschließlich für Contributors bestimmte Requirements nach [dependency-groups] und nicht in öffentliche Extras.
  5. Verschiebe Tool-Einstellungen nur dann, wenn das Tool gleichwertige Semantik unterstützt.
  6. Baue sowohl eine sdist als auch ein Wheel, prüfe deren Inhalte und installiere das Wheel in einer sauberen Umgebung.
  7. Führe Entry-Points, Tests, Import-Checks und den tatsächlichen Deployment-Pfad aus.
  8. Lösche die alte Konfiguration erst, nachdem Artefakte und Verhalten übereinstimmen.

MANIFEST.in kann bei manchen setuptools-Layouts weiterhin erforderlich sein, und ein kleines setup.py kann für programmatisches Build-Verhalten weiterhin sinnvoll sein. Modernisierung verschiebt Verantwortlichkeiten zwischen Dateien. Das Löschen von Dateien ist nicht das Ziel.

Ein aktueller uv-Workflow

uv unterscheidet beim Erstellen eines Projekts zwischen Applications und Libraries:

# Non-library application template
uv init weather-app

# Packaged library with a src layout and build system
uv init --lib weather-client

uv init erstellt Projektdateien. Die erste Projektoperation, etwa uv run, uv sync oder uv lock, erstellt bei Bedarf das Lockfile und ein persistentes .venv.

cd weather-client
uv add httpx
uv add --group test pytest pytest-cov
uv run pytest
uv build

uv legt lokale Development-Requirements derzeit in standardisierten Dependency-Gruppen ab. Sein natives uv_build-Backend ist eine Option für Pure-Python-Projekte; Compiled Extensions benötigen eine geeignete Alternative wie maturin oder scikit-build-core. Aktuelle Backend-Einstellungen findest du in der Dokumentation zur Projektkonfiguration von uv.

Fazit

pyproject.toml ist übersichtlich, wenn jede Tabelle eine Zielgruppe hat. Build-Isolation gehört nach [build-system] und veröffentlichtes Verhalten nach [project]. Contributor-Umgebungen gehören nach [dependency-groups]. Tool-Schalter gehören zu dem Tool, das sie definiert.

Sobald diese Grenzen stabil sind, lässt sich die Datei leichter reviewen, und Migrationen verwechseln Package-Metadaten nicht mehr mit der aufgelösten Umgebung einer einzelnen Maschine.
