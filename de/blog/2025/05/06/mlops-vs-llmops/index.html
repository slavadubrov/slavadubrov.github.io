MLOps vs. LLMOps: Infrastruktur für Foundation Models

Viacheslav Dubrov

2025-05-06 · Aktualisiert 2026-07-15 · 7 Min. · KI-Infrastruktur

Automatische Übersetzung Dieser Artikel wurde automatisch aus der englischen Originalversion übersetzt.

Foundation Models haben mehrere Annahmen verändert, auf denen klassisches MLOps beruht. Teams passen häufig ein pretrained Model an oder rufen es auf, statt jedes Model von Grund auf zu trainieren. Generierte Antworten und Tool-Aktionen erfordern außerdem eine Evaluation, die über eine feste Prediction-Metrik hinausgeht.

Die MLOps-Disziplin bleibt relevant. Verändert hat sich die operative Einheit: Das Verhalten einer Language-Model-Anwendung kann neben Model Weights auch von Prompts, Decoding, Retrieval, Tool Contracts, Berechtigungen, Routing und Policy abhängen. Dieser Artikel erklärt, was weiterhin nützlich ist und was LLM-Systeme zusätzlich erfordern.

Dieser Artikel richtet sich an ML-, Platform- und AI-Application-Engineers, die konventionelles MLOps bereits verstehen.

Nach der Lektüre können Sie das vollständige Release-Manifest für eine Foundation-Model-Anwendung bestimmen. Außerdem können Sie auswählen, welche Kontrolle Sie beim Auftreten eines Fehlers zuerst ergänzen sollten.

TL;DR. Behalten Sie MLOps-Lineage, Automation, gestaffelte Auslieferung, Monitoring und Rollback bei. Erweitern Sie das Release-Manifest um Provider oder Weights, Prompts, Schemas, Retrieval State, Tools, Routing und Policy. Führen Sie dieses Manifest durch mehrere Evaluationsschichten und nutzen Sie anschließend privacy-aware Traces, um Produktionsfehler in neue Tests zu überführen.

Was MLOps bereits gelöst hat

MLOps hat Kontrollen etabliert, die nicht obsolet werden, wenn das Model Text generiert:

  • Lineage von Daten, Code, Konfiguration und Model bis zu einem Release
  • wiederholbare Training- oder Build-Pipelines
  • Offline-Validierung vor der Promotion
  • Registries und unveränderliche Artifact-Identität
  • gestaffelter Rollout, Service-Level Objectives, Rollback und Incident Response
  • Infrastruktur-Telemetrie und Capacity Planning
  • Access Control, Retention und Audit Policy für Daten

Foundation Models beseitigen diese Anforderungen nicht. Sie machen lediglich den alten Begriff „Model-Version“ zu klein.

Die Release-Einheit wurde zu einem System-Manifest

Bei einem konventionellen Prediction Service lässt sich die meiste Verhaltensänderung normalerweise auf Code, Feature Logic und Model-Identität zurückführen. Bei einem Foundation-Model-System sollten Sie mindestens Folgendes erfassen:

application code revision
model provider + model/revision + serving configuration
system and task prompts
response schema + decoding parameters
retrieval corpus snapshot + parser + chunker + embedding model + index
tool definitions + implementation revisions + permission policy
routing, fallback, caching, and budget policy
safety and business-rule revisions
evaluation dataset + scorer revisions

Die genaue Liste hängt vom System ab. Die Invariante ist, dass ein einziges Manifest jede unabhängig veränderbare Komponente identifizieren muss, die das für Nutzer sichtbare Verhalten ändern kann.

Der Model-Alias eines Providers ist nicht notwendigerweise ein unveränderliches Artifact. Ein Hash eines self-hosted Checkpoints ist präziser, aber auch Runtime, Quantization, Template und Parallelism-Konfiguration gehören in den Release-Datensatz.

Fünf erweiterte Failure Surfaces

Der Unterschied zwischen MLOps und LLMOps wird bei der Fehleranalyse deutlicher als in Tool-Listen.

1. Model und Serving

Hosted Models bringen Provider-Verfügbarkeit, Quotas, regionale Verarbeitung, Alias-Änderungen und Pay-per-Token-Ökonomie mit sich. Self-hosted Models bringen zusätzlich Weight Supply Chains, GPU-Kapazität, Batching, Cache Policy, Quantization und Distributed Serving mit sich.

Beide benötigen Kontrollen für Latency, Errors, Throughput, Saturation und Kosten. Keine der beiden Deployment-Varianten macht Quality Evaluation überflüssig.

2. Prompt, Schema und Orchestration

Ein Prompt ist eine codeähnliche Konfiguration, aber der Prompt-Text allein definiert das Verhalten nicht. Message Ordering, Tool Descriptions, Response Schema, Decoding, Retries, Truncation und der umgebende Code sind ebenfalls relevant.

Versionieren Sie den zusammengesetzten Request und die Orchestration Policy. Testen Sie Structured Outputs mit Parsern und Business-Invarianten, statt „valides JSON“ als Task-Erfolg zu akzeptieren.

3. Retrieval und Context

Retrieval fügt zwischen der Source of Truth und dem Model ein unabhängiges Data Product ein:

Die Pipeline muss Source Revision, Parser- und Chunker-Versionen, Embedding-Identität, Index Build, Access-Control-Metadaten und Deletion State bewahren. Evaluieren Sie Retrieval vor der Generation. Prüfen Sie, ob das System die richtigen Belege gefunden hat, ob die Autorisierungsfilterung gegriffen hat und ob die Antwort die bereitgestellten Belege korrekt verwendet hat.

Ein Vector Index ersetzt weder einen Feature Store noch ein Warehouse. Er übernimmt Similarity Retrieval. Strukturierte Point-in-Time-Features und analytische Fakten haben andere Anforderungen an Konsistenz und Abfragen.

4. Tools und Aktionen

Wenn ein Model APIs aufrufen kann, können Qualitätsfehler zu Seiteneffekten werden. Die operative Grenze umfasst nun Tool Authentication, Least Privilege, Argument Validation, Timeouts, Idempotency, Approval Policy und Postcondition Checks.

Tracen Sie, welches Tool angeboten, ausgewählt, aufgerufen, abgelehnt, erneut versucht und committed wurde. Eine flüssige finale Antwort kann nicht beweisen, dass der Aktionspfad korrekt war.

5. Safety, Security und Policy

Content Filter sind nur eine Kontrolle und keine vollständige Guardrail-Schicht. Zu den Bedrohungen gehören auch Prompt Injection, Cross-Tenant Retrieval, Secret Disclosure, Excessive Agency, nicht vertrauenswürdiger Model- oder Node-Code und unsichere Tool-Argumente.

Drücken Sie deterministische Business Rules nach Möglichkeit außerhalb des Models aus. Definieren Sie Residual Risks, testen Sie adversariale Fälle und benennen Sie einen Owner für Policy-Änderungen. NISTs Generative AI Profile ist ein nützliches Risk Inventory, aber kein sofort einsetzbarer Acceptance Test.

Evaluation wird zum Release Gate

Freiform-Output macht eine einzelne aggregierte Accuracy-Zahl unzureichend. Das bedeutet nicht, dass sich Qualität nicht messen lässt.

Bauen Sie einen Evaluations-Stack mit mehreren Evidenztypen auf:

  1. Deterministische Checks: Schema Validity, vorhandene Citations, erlaubte Tools, Argument Constraints, Policy Rules, Latency und Budget.
  2. Component Metrics: Retrieval Recall und Ranking, Tool-Selection Accuracy, Tool-Argument Correctness und Route Selection.
  3. End-to-End-Tasks: repräsentative Inputs mit expliziten Success Criteria und Slice Labels.
  4. Model-Based Scoring: Rubric-basierte Bewertungen, kalibriert gegen Expert Labels und überwacht auf Judge Drift.
  5. Human Review: mehrdeutige, folgenreiche, neuartige oder gesampelte Fälle, in denen Automation nicht maßgeblich ist.
  6. Adversarial Tests: Injection-, Data-Boundary-, Abuse-, Refusal- und Side-Effect-Fälle, die an das Threat Model gebunden sind.

Speichern Sie Ergebnisse pro Beispiel und nicht nur Durchschnittswerte. Ein Release kann den Mittelwert verbessern und gleichzeitig bei einer Sprache, einem Tenant, einem Dokumenttyp oder einer Aktionsklasse regressieren.

Byte says

Ich beförderte ein Release, weil der Durchschnitt stieg. Der Dokumenttyp eines Tenants war schlechter geworden, und der Durchschnitt war groß genug, um den Verlust zu verschlucken.

Das Deployment Gate vergleicht ein Candidate Manifest mit dem aktuellen Release anhand derselben versionierten Suite. Die Thresholds sollten Quality, Safety, Latency und Kosten gemeinsam abdecken. Eine günstigere Route, die die Aufgabe nicht erfüllt, ist keine Optimierung.

Traces verbinden die Produktion mit der Evaluation

Infrastrukturmetriken können zeigen, dass ein Model Call langsam war. Sie zeigen jedoch nicht, dass Retrieval ein nicht autorisiertes Dokument zurückgegeben hat oder dass ein Tool mit dem falschen Account aufgerufen wurde. MLflows Tracing-Dokumentation beschreibt Traces, die Zwischenstände und Metadaten erfassen, die für die Untersuchung dieses Pfads erforderlich sind.

Erfassen Sie einen Trace über den gesamten Entscheidungspfad:

  • Release-Manifest-Identität und Request Correlation
  • Model- und Provider-Calls, Latency, Usage und Finish State
  • Retrieval Query, Dokument-IDs, Scores und Filtering Decisions
  • Prompt-/Template-Revision, ohne sensible Inhalte wahllos zu speichern
  • Tool Offers, Arguments, Approvals, Results und Side-Effect-IDs
  • Policy Decisions, Retries, Fallbacks und finales Ergebnis

Tracing schafft eine neue Data-Governance-Fläche. Wenden Sie vor dem Erfassen vollständiger Prompts oder Dokumente Minimization, Redaction, Tenant Isolation, Encryption, Sampling, Retention und Access Review an. OpenTelemetrys GenAI Semantic Conventions können bei der Interoperabilität helfen, befinden sich jedoch noch in Entwicklung. Fixieren Sie die Version von Convention oder Schema sowie die Versionen von Instrumentation und Collector.

Der Improvement Loop lautet:

production trace → triaged failure → labeled regression case
                 → candidate change → offline comparison
                 → staged release → monitored outcome

Nutzerfeedback kann die Priorisierung von Untersuchungen unterstützen, ist aber keine Ground Truth. Bewahren Sie den umgebenden Trace und holen Sie für folgenreiche Fälle Expert Labels ein.

Das Serving Gateway ist eine Policy Boundary

Ein Gateway kann Application Clients von Providern oder self-hosted Engines entkoppeln. Zu den Aufgaben, die sich dort gut unterbringen lassen, gehören:

  • Authentication, Tenant Budgets, Quotas und Rate Limits
  • stabile Request- und Response-Contracts
  • Route Selection nach Capability, Region, Latency oder evaluierter Quality
  • begrenzte Retries, Circuit Breakers und explizite Fallback-Semantik
  • Cache Partitioning und Sensitive-Data Policy
  • Usage Attribution und Propagation des Release Manifests

Fallback ist ebenso sehr eine Verhaltensänderung wie ein Reliability Mechanism. Wenn ein kleineres Model, ein alternativer Provider oder ein reduzierter Context die Task Quality verändert, evaluieren und tracen Sie diesen Branch als eigene Route.

Verlagern Sie nicht jede Orchestration-Entscheidung in das Gateway. Halten Sie Domain Rules nahe an der Anwendung und machen Sie Zuständigkeiten sichtbar.

Fine-Tuning ist eine Intervention, nicht die Reifeleiter

Wählen Sie die Intervention anhand des beobachteten Fehlers:

FehlerErste zu untersuchende Komponente
Aktuelle oder private Fakten fehlenRetrieval und Source Synchronization
Falsches Format oder ungültige ArgumenteSchema, Constrained Output, Validation
Inkonsistentes Task-VerhaltenPrompt, Beispiele, Model-Wahl, anschließend Adaptation Data
Zu hohe Latency oder KostenRoute, Context, Cache, Batching, Quantization
Nicht autorisierte oder unsichere AktionTool Permissions und deterministische Policy
Domain-Verhalten nicht aus Context ableitbarFine-Tuning oder ein anderes spezialisiertes Model

LoRA und andere Parameter-Efficient-Methoden reduzieren die Anzahl trainierbarer Parameter. Sie beseitigen weder Dataset Governance, Base-Model-Licensing, Evaluation, Serving Compatibility noch Rollback-Anforderungen.

Eine praktische Einführungssequenz

  1. Definieren Sie die User Task, Harm Boundaries, Service Objectives und das Cost Envelope.
  2. Erstellen Sie das Release Manifest, bevor Sie ein Prompt Registry, eine Vector Database oder ein Gateway-Produkt einführen.
  3. Bauen Sie einen kleinen, geslicten Evaluationsdatensatz und deterministische Component Tests auf.
  4. Instrumentieren Sie einen End-to-End-Trace mit Privacy Controls und stabilen Release-Identitäten.
  5. Führen Sie die Promotion über Shadow, Canary oder begrenzten Traffic mit einem expliziten Rollback Trigger durch.
  6. Überführen Sie untersuchte Produktionsfehler in Regression Cases und wiederholen Sie den Prozess.

Fügen Sie Infrastruktur nur hinzu, wenn sie eine benannte Kontrolle übernimmt oder einen gemessenen Bottleneck beseitigt. Eine „LLMOps Platform“ ist keine Architekturanforderung.

Fazit

LLMOps ist MLOps, angewandt auf eine größere Verhaltenseinheit. Das Model bleibt wichtig, aber Prompts, abgerufene Evidenz, Tool Permissions, Routing und Policy können das Ergebnis verändern, ohne dass sich die Weights ändern.

Versionieren Sie diese gesamte Einheit, evaluieren Sie sie vor dem Release, tracen Sie sie mit Privacy Boundaries und rollen Sie sie als ein System zurück.
