Schema-Guided Reasoning: vLLM, XGrammar und Pydantic

Viacheslav Dubrov

2025-12-28 · Aktualisiert 2026-09-12 · 13 Min. · KI-Agenten · Modellentwicklung

Dieser Artikel richtet sich an Python Engineers, die Model-Ausgaben benötigen, die nachgelagerter Code validieren kann. Sie lernen, wie Sie ein Pydantic-Schema definieren, Structured Output von vLLM anfordern und zusätzliche Checks für Bedeutung und Policy in der Anwendung ergänzen.

Pydantic beschreibt die Response-Felder, vLLM stellt das Model bereit und XGrammar schränkt ein, welche Tokens das Model generieren kann. Diese Einschränkung wird Constrained Decoding genannt. Sie gilt nur für die Schema-Features, die vom Decoding-Backend unterstützt werden – hier XGrammar. Ein Token-Limit kann weiterhin ein unvollständiges JSON-Präfix hinterlassen. Daher muss Anwendungscode die Vollständigkeit prüfen und das Ergebnis validieren.

Was ist Schema-Guided Reasoning?

Schema-Guided Reasoning ist eine Technik, die Rinat Abdullin im Juli 2025 beschrieben hat. Statt das Model Text frei vervollständigen zu lassen – was inkonsistent oder mehrdeutig sein kann –, geben Sie ihm ein striktes Template vor, das Folgendes definiert:

  • welche Schritte die Response abbilden soll
  • die vorgesehene Reihenfolge dieser Schritte, damit ein Reviewer den Weg von den Daten zur Entscheidung prüfen kann
  • worauf es seine Attention richten soll

Betrachten Sie dies als Checkliste der zu prüfenden Outputs und nicht als Beweis für das interne Reasoning des Models. Der Decoder prüft die Output-Struktur; Anwendungscode steuert, wann die einzelnen Phasen ausgeführt werden und ob ein Ergebnis verwendet werden darf.

Was das Schema steuert

Das laufende Beispiel schlägt einen Discount vor, um einen möglicherweise abwandernden Kunden zu halten. Die Churn-Wahrscheinlichkeit schätzt diese Abwanderungswahrscheinlichkeit; der Cart-Wert ist der Gesamtbetrag vor dem Discount. Die Margin ist der Bruttogewinn als Anteil dieses Gesamtbetrags: Ein Cart von $200 mit einer Margin von 0.20 hat $40 Bruttogewinn. Discounts werden in Prozentpunkten angegeben; ein Vorschlag von 15 bedeutet daher 15 %.

Ein Pricing-Model kann gültiges JSON zurückgeben und trotzdem einen Discount von 25 % vorschlagen, obwohl die Margin nur 20 % beträgt. Das Schema hält den Vorschlag fest; Anwendungscode muss prüfen, ob der Discount zulässig ist.

Felder wie churn_analysis, margin_math und max_discount_percent machen die vorgesehenen Intermediate Outputs explizit. Ein Schema beschränkt die zurückgegebene Form. Es sorgt nicht automatisch dafür, dass ein Feld von einem anderen abhängt, und beweist nicht, dass die Entscheidung korrekt ist.

Damit erhalten Sie:

  • eine vergleichbare Output-Struktur über wiederholte Runs hinweg
  • aufgezeichnete Intermediate Outputs, die Reviewer prüfen können
  • Intermediate-Felder, die Sie anhand eines Test-Datasets bewerten können
  • eine Hypothese, die Sie mit kleineren Models testen können: Eine Formatbeschränkung kann helfen, die Task-Accuracy muss jedoch weiterhin evaluiert werden
  • Abdullin schreibt, dass ein Accuracy-Boost von 5–10 % in den von ihm beobachteten Fällen „nicht ungewöhnlich“ sei; dies ist eine Practitioner-Beobachtung und kein Benchmark-Ergebnis. Messen Sie den Effekt daher für Ihren eigenen Workload.

Prompt-Guidance und Decoder-Constraints

Prompt-Guidance und Constrained Decoding lassen sich kombinieren. Dieser Vergleich zeigt, an welcher Stelle jeweils das angeforderte Format geprüft wird.

Prompt Engineering: das Format anfordern

Dieser Prompt fordert das Model auf, den Discount-Vorschlag als JSON zu formatieren:

Please analyze the customer data and output your response as valid JSON
with the following structure: {"discount": <number>, "reason": <string>}
Be careful with the formatting!

Sie hoffen darauf, dass das Verständnis des Models für „output JSON“ seine Tendenz zu konversationellen Antworten überwiegt. Ein Model-Update, eine Temperaturänderung oder ein anderes Few-Shot-Beispiel kann Ihren Parser brechen.

Chain-of-Thought: nützlicher Reasoning-Trace, dasselbe Strukturproblem

Ein Chain-of-Thought-(CoT)-Prompt fordert eine Intermediate-Analyse an. Die Response könnte so aussehen:

Let's think step by step:
1. First, I'll analyze the customer's churn risk...
2. Then I'll calculate the margin...
3. Therefore, I recommend a 15% discount.

CoT kann die Task-Accuracy verbessern, wenn Prompt, Model, Task und Evaluation dies unterstützen. Das Ergebnis bleibt jedoch Prosa, die sich nur schwer zuverlässig parsen lässt. Möglicherweise benötigen Sie einen zweiten LLM-Call, nur um strukturierte Daten zu extrahieren.

SGR: strukturierter Chain-of-Thought

SGR kann Intermediate-Felder zur Prüfung und Evaluation verfügbar machen. Ob dies die Task-Accuracy verbessert, hängt vom Model, Prompt, Task und der Verwendung dieser Felder ab; das Schema formalisiert lediglich deren Form:

class PricingLogic(BaseModel):
    # 1. Recorded analysis
    churn_analysis: str = Field(..., description="Analyze churn_probability")
    financial_analysis: str = Field(..., description="Analyze cart_value and margin")

    # 2. Proposed calculation, checked by application code
    margin_math: str = Field(..., description="Calculate: 'Cart $X * Y% = $Z'")

    # 3. Proposed decision, not bounded by the analysis fields
    max_discount_percent: float = Field(..., description="Max allowed discount")

    # 4. Final Output
    customer_message: str

Das Schema beschreibt diese Felder in dieser Reihenfolge. Ein einzelnes Object-Schema erzeugt keinen separaten Validierungsschritt zwischen ihnen. Verwenden Sie separate Calls oder Application Checks, wenn spätere Entscheidungen von früheren Ergebnissen abhängen müssen.

SGR-Patterns

Byte says

Wenn Analysefelder vor einer Entscheidung stehen, lässt sich die Response leichter prüfen. Ein Feld namens margin_math ist weiterhin ein String und kein Taschenrechner.

SGR besitzt drei zentrale Patterns, die sich zu größeren Workflows kombinieren lassen.

1. Cascade: sequenzielle Reasoning-Schritte

Cascade bildet eine Reasoning-Reihenfolge in einer strukturierten Response ab. Hier hält ein Document Classifier eine Zusammenfassung, einen Topic-Match-Score und eine vorgeschlagene Kategorie fest. Zwischen diesen Feldern wird kein separater Check ausgeführt.

from pydantic import BaseModel
from typing import Literal, Annotated
from annotated_types import Ge, Le

class DocumentEvaluation(BaseModel):
    """Record a document summary, score, and proposed category."""

    # Step 1: Record a summary
    brief_document_summary: str

    # Step 2: Rate (bounded integer)
    rate_topic_match: Annotated[int, Ge(1), Le(10)]

    # Step 3: Decide (constrained choices)
    final_recommendation: Literal["relevant", "irrelevant", "review"]

Beispielhafte Anwendungen: Document Classification und Support-Ticket-Triage.

Das Model soll brief_document_summary, rate_topic_match und final_recommendation in dieser Reihenfolge zurückgeben. Wenn die Reihenfolge eine Policy-Anforderung ist, erzwingen Sie sie mit separaten Calls oder deterministischer Application Logic.

2. Routing: ein semantisches Switch-Statement

Routing fordert das Model auf, einen Pfad aus einer Menge von Optionen auszuwählen, implementiert mit Union-Typen. Dieser Router wählt zwischen dem Abruf von Kundendaten für eine Pricing-Anfrage und einer allgemeinen Response.

from pydantic import BaseModel
from typing import Literal, Union

class FeatureLookup(BaseModel):
    """Route to database lookup."""
    rationale: str
    tool_name: Literal["fetch_user_features"] = "fetch_user_features"
    user_id: str

class GeneralResponse(BaseModel):
    """Standard response for non-pricing queries."""
    tool_name: Literal["respond"] = "respond"
    content: str

class RouterSchema(BaseModel):
    """The model must pick exactly ONE branch."""
    action: Union[FeatureLookup, GeneralResponse]

Geeignete Einsatzbereiche: Intent Classification, Tool Selection, Support-Triage und Multi-Agent Dispatch.

Die Branch-spezifischen Literal-Werte helfen der Validierung, die Union-Member zu unterscheiden. Sie machen das Routing nicht korrekt. Validieren Sie das Ergebnis und führen Sie den Dispatch in der Anwendung aus. Für einen expliziten Pydantic-Discriminator konfigurieren und testen Sie eine Discriminated Union.

3. Cycle: wiederholtes Reasoning mit Listen

Cycle beschreibt mehrere Items und begrenzt deren Anzahl. Dieses Beispiel zur Risikoanalyse fordert zwei bis vier Faktoren an, jeweils mit Erklärung und Schweregrad.

from pydantic import BaseModel
from typing import List, Literal, Annotated
from annotated_types import MinLen, MaxLen

class RiskFactor(BaseModel):
    explanation: str
    severity: Literal["low", "medium", "high"]

class RiskAssessment(BaseModel):
    """Generate 2-4 risk factors."""
    factors: Annotated[List[RiskFactor], MinLen(2), MaxLen(4)]

Geeignete Einsatzbereiche: Risikoanalyse, Issue Extraction, parallele Tool Calls und mehrstufige Planung.

Die Listenbegrenzung beschreibt einen variablen Batch aus 2–4 Items. Ein unterstützter Decoder kann diese Länge beschränken; Application Validation prüft sie erneut. In Kombination mit Routing kann die Liste vorgeschlagene Tool Calls beschreiben. Anwendungscode muss diese autorisieren und dispatchen.

SGR funktionsfähig machen: Constrained Decoding

Die oben beschriebenen Patterns sind lediglich Pydantic-Schemas. Constrained Decoding kann die unterstützten Constraints erzwingen, die in ihrem JSON Schema enthalten sind. Beliebige Python-Validatoren werden nicht zu Decoder-Constraints; sie laufen weiterhin nach der Generation in Pydantic.

Constrained Decoding verändert den Schritt der Token-Generation. Statt das Model frei aus seinem Vokabular samplen zu lassen, verwendet die Engine eine Grammar Mask, die Tokens blockiert, die gegen das Schema verstoßen würden. Dies geschieht in der Inference Engine und nicht in Ihrem Anwendungscode.

[!TIP] SGR erfordert keine „Reasoning Models“ wie o1 oder DeepSeek-R1. Instruction-Tuned Models können ebenfalls Schema-constrained Responses erzeugen. Vergleichen Sie die Task-Accuracy für die konkreten Models, die Sie bereitstellen möchten.

Warum hier vLLM und XGrammar verwenden?

Die Structured-Output-API von vLLM akzeptiert JSON Schema über einen OpenAI-kompatiblen Client. Dadurch kann das Beispiel eine vertraute Request-Anbindung beibehalten und gleichzeitig das Decoding-Backend auf dem Server konfigurieren. Schema-Subsets, Error Handling und Model-Verhalten müssen beim Wechsel des Providers weiterhin getestet werden.

XGrammar stellt den Grammar Compiler und die Token-Mask-Mechanik bereit. Die technische Übersicht erklärt die unten beschriebene Aufteilung zwischen CPU und GPU; die dortigen Benchmark-Ergebnisse gelten für die getesteten Workloads und nicht für jedes Deployment.

Wie XGrammar Schemas erzwingt

Wo das Masking stattfindet

Logits sind die unnormalisierten Scores des Models für mögliche nächste Tokens. XGrammar modifiziert diese Scores nach dem Forward Pass des Models und vor dem Sampling. Das Model selbst wird nicht verändert. Gefiltert wird lediglich, welche Tokens ausgewählt werden können.

Ein standardmäßiger Inference Loop sieht so aus:

1. Input tokens → GPU Forward Pass → Logits (one unnormalized score per vocabulary token)
2. Logits → Sampling (temperature, top-p, etc.) → Next Token
3. Repeat until done

XGrammar schaltet sich zwischen Schritt 1 und 2:

1. Input tokens → GPU Forward Pass → Raw Logits
2. Raw Logits → XGrammar Logits Processor → Masked Logits
3. Masked Logits → Sampling → Next Token (continues the grammar-valid prefix)
4. Repeat until done

Das Diagramm zeigt, wie die Scores des Models und die Grammar Mask zusammentreffen, bevor ein Token ausgewählt wird. Jedes akzeptierte Token aktualisiert außerdem den Grammar State für den nächsten Schritt.

Das Model berechnet weiterhin die vollständige Probability Distribution auf der GPU. XGrammars GrammarMatcher erzeugt die Bitmask auf der CPU. Anschließend verschiebt die Serving Engine diese Bitmask auf das Device der Logits und wendet sie vor dem Sampling in place an. Für GPU-Logits verwendet XGrammar dafür einen GPU-Kernel. Bei ungültigen Tokens werden die Logits auf -∞ gesetzt, wodurch ihre Probability nach Softmax exakt 0 ist.

Zwei Phasen

XGrammar teilt die Arbeit in Compile-Time und Runtime auf. Dieses Design reduziert wiederholte Grammar-Arbeit.

Phase 1: Grammar Compilation, einmal pro Schema

Dieser Ausschnitt erstellt mithilfe des Tokenizers des Models eine Grammar für das Schema. Das compilierte Ergebnis kann bei der Generation von Responses mit diesem Schema wiederverwendet werden.

# This happens once per schema
tokenizer_info = xgr.TokenizerInfo.from_huggingface(tokenizer)
grammar_compiler = xgr.GrammarCompiler(tokenizer_info)
compiled_grammar = grammar_compiler.compile_json_schema(schema_json)

Während der Compilation führt XGrammar folgende Schritte aus:

  1. Konvertiert das JSON Schema in eine Context-Free Grammar.
  2. Erstellt einen Pushdown Automaton (PDA), eine State Machine mit Stack, die verschachtelte Strukturen wie {"a": {"b": {"c": ...}}} verarbeiten kann.
  3. Berechnet vorab, welche Tokens an jeder Grammar-Position gültig sind. Das Ergebnis ist der „Adaptive Token Mask Cache“.
  4. Kategorisiert Tokens als „Context-Independent“ (cachebar) oder „Context-Dependent“ (müssen zur Runtime anhand des Stack-States geprüft werden).

[!NOTE] Das XGrammar-Paper berichtet, dass in seinen Messungen etwa 99 % der Tokens Context-Independent waren (Paper). Betrachten Sie diese Zahl als Benchmark-spezifisch und nicht als universelles Verhältnis.

Phase 2: Runtime-Mask-Generation, für jedes Token

Bei jedem Generation-Schritt:

  1. Der GrammarMatcher verfolgt die aktuelle Position in der Grammar.
  2. Er sucht die vorberechnete Mask für Context-Independent Tokens nach.
  3. Er führt den PDA aus, um die verbleibenden Context-Dependent Tokens zu prüfen.
  4. Er kombiniert sie zu einer finalen Bitmask, verschiebt sie auf das Device der Logits und wendet sie dort an.

Warum Pushdown Automata statt Regex?

Wegen der Verschachtelung. Ein regulärer Ausdruck – also eine endliche State Machine – kann Strukturen wie diese nicht zuverlässig matchen:

{ "user": { "profile": { "settings": { "theme": "dark" } } } }

Der schwierige Teil sind die schließenden geschweiften Klammern }}}: Sie müssen sich merken, wie viele öffnende Klammern vorhanden sind. Ein Pushdown Automaton besitzt dafür einen Stack und kann somit beliebige Verschachtelungstiefen verarbeiten. Deshalb kann XGrammar auch Union-Typen, verschachtelte Objekte und rekursive Schemas erzwingen, während Regex-basierte Ansätze hier an ihre Grenzen stoßen.

Ein konkretes Beispiel: ein Float-Feld generieren

Wenn das Model "max_discount_percent": generiert, weiß XGrammar aus dem Schema, dass als Nächstes ein float folgt. Die Menge gültiger Tokens hängt vom Parser-State und Tokenizer ab. Am Anfang der Zahl kann die Mask eine Ziffer oder ein Minuszeichen zulassen; nach einer Ziffer kann sie Fortsetzungen wie eine weitere Ziffer, einen Dezimalpunkt oder einen Exponentenmarker zulassen.

  • Ein Anführungszeichen, {, [, true, false oder null kann diese Zahl nicht beginnen. Die Mask blockiert daher die entsprechenden Tokens in diesem State.
  • Der Forward Pass kann dem Token für "fifteen" eine hohe Probability zugewiesen haben. Da dieses Token das numerische Feld nicht fortsetzen kann, entfernt die Mask es, und das Model muss eine gültige numerische Fortsetzung auswählen.

Was den Overhead beeinflusst

Drei Gründe:

  1. Mask-Generation und Transfer. XGrammar generiert Masks auf der CPU, und die Serving Engine überträgt sie zur Anwendung in place auf das Device der Logits. Wie stark sich diese Vorgänge überlappen, hängt von der Serving-Implementierung und dem Workload ab.
  2. Caching. Der größte Teil der Validity-Arbeit wird zur Compile-Time erledigt. Zur Runtime handelt es sich überwiegend um Cache Lookups.
  3. C++-Implementierung. Der Hot Path ist C++ und nicht Python, und die Mask wird in place auf die Logits angewendet.

Die zitierten Benchmarks berichten für die getesteten Grammars, Tokenizers, Hardware-Konfigurationen und Workloads einen geringen Overhead. Diese Ergebnisse stellen keine allgemeine Garantie für Latency oder Throughput dar.

Schritt 1: Schemas definieren

RouterSchema erlaubt zwei Alternativen: Kundendaten mit FeatureLookup anfordern oder mit GeneralResponse Text zurückgeben. Nach dem Abruf der Daten verwendet ein separater Call PricingLogic, um die Analyse und den vorgeschlagenen Discount festzuhalten. Durch die Trennung dieser Responses kann die Anwendung die Daten abrufen, bevor sie einen Proposal anfordert.

# sgr/models/schemas.py
from pydantic import BaseModel, Field
from typing import Literal, Union

# --- Phase 1: Routing (Union for branching) ---
class FeatureLookup(BaseModel):
    """Route to DB lookup if pricing context is needed."""
    rationale: str
    tool_name: Literal["fetch_user_features"] = "fetch_user_features"
    user_id: str

class GeneralResponse(BaseModel):
    """Standard response for non-pricing queries."""
    tool_name: Literal["respond"] = "respond"
    content: str

class RouterSchema(BaseModel):
    action: Union[FeatureLookup, GeneralResponse]

# --- Phase 2: Pricing Logic (Cascade for sequential reasoning) ---
class PricingLogic(BaseModel):
    """
    Structured response for dynamic pricing. The fields record an intended analysis→decision flow.
    """
    # 1. Data Analysis (Reflection)
    churn_analysis: str = Field(...,
        description="Analyze churn_probability (High > 0.7).")
    financial_analysis: str = Field(...,
        description="Analyze cart_value and profit_margin.")

    # 2. Recorded calculation; application code recomputes policy
    margin_math: str = Field(...,
        description="Calculate absolute profit: 'Cart $200 * 0.20 Margin = $40'.")

    # 3. Model-proposed decision; application code approves it.
    max_discount_percent: float = Field(...,
        description="Proposed discount percentage. Application code enforces policy.")

Schritt 2: Eine strukturierte Response anfordern und validieren

Der Client exportiert das Pydantic-Model als JSON Schema, fügt es einer bestehenden System Message zur Prompt-Guidance hinzu und sendet es als Structured-Output-Constraint. XGrammar ist auf dem Server konfiguriert; der Client liefert das Schema für jede Anfrage.

completed_content weist unvollständige, abgelehnte oder leere Responses zurück, bevor Pydantic das JSON und seine Felder validiert. Token-Limit-Stopps werden ebenfalls zurückgewiesen, selbst wenn der zurückgegebene Text zufällig geparst werden kann. Diese Fehler werden an den Caller weitergegeben, der eine Error-Response oder Retry-Policy bereitstellen muss; auf diesen Pfaden wird kein Angebot genehmigt.

# sgr/utils/llm_client.py
import json
from typing import TypeVar

from openai import OpenAI
from pydantic import BaseModel

T = TypeVar("T", bound=BaseModel)

def completed_content(completion) -> str:
    """Reject incomplete, refused, or empty results before JSON validation."""
    if not completion.choices:
        raise ValueError("No completion returned")
    choice = completion.choices[0]
    if choice.finish_reason != "stop" or getattr(choice.message, "refusal", None):
        raise ValueError("Completion was not successful")
    content = choice.message.content
    if not isinstance(content, str) or not content.strip():
        raise ValueError("Completion has no content")
    return content

class LLMClient:
    """Wrapper for vLLM with XGrammar-enforced structured generation."""

    def __init__(self, base_url: str = "http://localhost:8000/v1"):
        # Local vLLM commonly has no authentication. EMPTY is not authentication.
        self.client = OpenAI(base_url=base_url, api_key="EMPTY")
        self.model = self._get_available_model()

    def _get_available_model(self) -> str:
        """Auto-detect the model running on vLLM server."""
        models = self.client.models.list()
        if not models.data:
            raise RuntimeError("vLLM reported no available models")
        return models.data[0].id

    def run_sgr(self, messages: list[dict], schema_class: type[T]) -> T:
        """Run inference with Schema-Guided Response constraints.

        Uses vLLM structured outputs to constrain the JSON shape at generation time.
        """
        schema_dict = schema_class.model_json_schema()

        # Enhance system message with schema for model guidance
        enhanced_messages = messages.copy()
        if enhanced_messages and enhanced_messages[0]["role"] == "system":
            schema_json = json.dumps(schema_dict, indent=2)
            enhanced_messages[0] = {
                "role": "system",
                "content": (
                    enhanced_messages[0]["content"]
                    + f"\n\nRespond with JSON matching this schema:\n{schema_json}"
                ),
            }

        # vLLM v0.12+ structured outputs. Configure the backend on the server.
        completion = self.client.chat.completions.create(
            model=self.model,
            messages=enhanced_messages,
            temperature=0.1,  # Reduces sampling variation; it is not deterministic.
            extra_body={"structured_outputs": {"json": schema_dict}},
        )

        return schema_class.model_validate_json(completed_content(completion))

[!NOTE] Im aktuellen vLLM fordert structured_outputs: {"json": schema_dict} JSON an, das dem Schema entspricht. Konfigurieren Sie das Structured-Output-Backend bei Bedarf mit der Server-Option --structured-outputs-config.backend. Dies ist Software-Enforcement in der Inference Server und kein Hardware-Enforcement.

Schritt 3: Den Agent orchestrieren

Die Anwendung routet die Anfrage, ruft Daten für den authentifizierten Caller ab, fordert einen Proposal an, prüft ihn und gibt das Ergebnis zurück. Der Feature Store verwendet die authentifizierte user_id und niemals die vom Model vorgeschlagene ID. Der Prompt erhält außerdem user_ltv, den geschätzten Customer Lifetime Value. Diese Schätzung liefert dem Model Context, legt aber das Discount-Limit nicht fest.

Die Demo-Policy lehnt vorgeschlagene Prozentsätze außerhalb von 0–20 ab und rundet anschließend auf Hundertstel eines Prozentpunkts ab. Sie lehnt einen finalen Discount ab, dessen Kosten den Bruttogewinn des Carts übersteigen. approve_discount prüft vor der Berechnung, ob die Inputs endlich sind, der Cart-Wert positiv ist und die Margin zwischen 0 und 1 liegt.

# sgr/agent.py
from decimal import Decimal, ROUND_DOWN

from .models.schemas import PricingLogic, RouterSchema
from .prompts.routing import build_routing_prompt
from .prompts.pricing import build_pricing_context_prompt, ASSISTANT_FETCH_MESSAGE
from .store.hybrid_store import HybridFeatureStore
from .utils.llm_client import LLMClient

def approve_discount(offer: PricingLogic, context: dict) -> Decimal:
    """Enforce the pricing policy independently of the model's explanation."""
    cart_value = Decimal(str(context["current_cart_value"]))
    margin = Decimal(str(context["cart_profit_margin"]))
    proposed = Decimal(str(offer.max_discount_percent))

    if not all(value.is_finite() for value in (cart_value, margin, proposed)):
        raise ValueError("Pricing values must be finite")
    if cart_value <= 0 or not Decimal("0") <= margin <= Decimal("1"):
        raise ValueError("Invalid pricing context")

    if not Decimal("0") <= proposed <= Decimal("20"):
        raise ValueError("Proposed discount violates pricing policy")
    # Policy rounds down to hundredths of a percentage point before approval.
    approved = proposed.quantize(Decimal("0.01"), rounding=ROUND_DOWN)
    gross_profit = cart_value * margin
    discount_cost = cart_value * approved / Decimal("100")
    policy_cap = min(margin * Decimal("100"), Decimal("20"))
    if not Decimal("0") <= approved <= policy_cap or discount_cost > gross_profit:
        raise ValueError("Proposed discount violates pricing policy")

    return approved

def pricing_agent(user_query: str, user_id: str) -> str:
    """Integrate routing, context, and pricing; user_id is caller-authenticated."""

    llm = LLMClient()
    feature_store = HybridFeatureStore()

    # Build conversation history
    history = [
        {"role": "system", "content": build_routing_prompt(user_id)},
        {"role": "user", "content": user_query},
    ]

    # --- Phase 1: Routing (Uses RouterSchema) ---
    print(f"🤖 Processing: '{user_query}' for {user_id}")
    decision = llm.run_sgr(history, RouterSchema)
    print(f"📍 Routing decision: {decision.action.tool_name}")

    if decision.action.tool_name == "respond":
        return decision.action.content

    # --- Phase 2: Context Retrieval ---
    if decision.action.tool_name == "fetch_user_features":
        print(f"🔍 Fetching features for {user_id}...")
        context = feature_store.get_user_context(user_id)

        if not context:
            return "Error: User profile not found."

        print(f"   [Data] LTV: ${context.get('user_ltv')} | "
              f"Margin: {context.get('cart_profit_margin', 0) * 100}%")

        # Inject context into conversation
        history.append({"role": "assistant", "content": ASSISTANT_FETCH_MESSAGE})
        history.append({
            "role": "user",
            "content": build_pricing_context_prompt(
                churn_prob=context.get("churn_probability", 0.5),
                cart_val=context.get("current_cart_value", 100),
                margin=context.get("cart_profit_margin", 0.2),
                user_ltv=context.get("user_ltv", 0),
            ),
        })

        # --- Phase 3: model proposal, then deterministic policy enforcement ---
        print("🧠 Proposing Offer (Schema Enforced)...")
        offer = llm.run_sgr(history, PricingLogic)
        try:
            approved_discount = approve_discount(offer, context)
        except ValueError:
            return "No discount approved: the proposal failed the pricing policy."

        # Audit log: reasoning is inspectable; pricing is application-enforced.
        print(f"   [Audit] Math: {offer.margin_math}")
        print(f"   [Audit] Approved Discount: {approved_discount}%")

        return (
            f"Illustrative approved discount: {approved_discount}%. "
            "No coupon has been issued."
        )

    return "I'm sorry, I couldn't process your request."

if __name__ == "__main__":
    response = pricing_agent("I want a discount or I'm leaving!", "user_102")
    print(f"\n💬 Final Reply: {response}")

Ein Proposal von 15 % bei einem Cart von $200 und einer Margin von 20 % liefert aus der Policy-Funktion 15.00 zurück. Die Anwendung meldet diesen Prozentsatz, ohne vorzugeben, einen Coupon auszustellen. Ein Boundary-Test verwendet eine Margin von 0.12346 bzw. 12,346 %. Ein 12.346-Proposal wird vor der Prüfung des finalen Werts auf 12.34 abgerundet. Ein Runden auf 12.35 nach der Genehmigung würde die Margin überschreiten.

Checks vor einer Live-Integration

Byte says

Ein Proposal kann gültiges JSON und gleichzeitig einen Discount enthalten, der größer als die Margin ist. Die Policy-Funktion prüft die Zahl, selbst wenn die Erklärung überzeugend klingt.

Schema-Design

  1. Ordnen Sie Felder nach dem vorgesehenen Reasoning Flow an. Betrachten Sie diese Reihenfolge als Dokumentation, sofern separate Calls oder Application Checks sie nicht erzwingen.
  2. Schreiben Sie aussagekräftige Field-Beschreibungen. Sie lenken die Attention des Models ebenso stark wie der Feldname.
  3. Beschränken Sie mit Literal und Annotated. Verwenden Sie Literal["a", "b"] für Enums und Annotated[int, Ge(1), Le(10)] für Bounds.
  4. Halten Sie Schemas fokussiert. Verwenden Sie ein Schema pro Reasoning-Phase und kombinieren Sie diese anschließend mit mehreren Calls.

vLLM-Konfiguration

  1. Verwenden Sie eine niedrige Temperatur (0.1–0.3), um Sampling-Variationen zu reduzieren. Für wiederholbare Tests fixieren Sie Model und Serving-Konfiguration, verwenden Sie den deterministischen Modus des Servers, sofern vorhanden, und verifizieren Sie das Ergebnis.
  2. Erklären Sie Task und Schema-Felder im Prompt, wie es der Client oben tut. Prompt-Guidance und Decoder-Constraints ergänzen sich.
  3. Messen Sie den Token-Verbrauch mit demselben Prompt, Model, Schema und derselben Task. SGR kann mehr oder weniger Tokens ausgeben als eine freie CoT-Response.

Überlegungen für die Production

  1. Versionieren Sie Ihre Schemas genauso wie Ihre APIs.
  2. Auch mit SGR müssen Netzwerk- und Serverfehler Graceful Handling erhalten.
  3. Zeichnen Sie Proposal und Policy-Entscheidung separat zum Debugging auf, vorbehaltlich Ihrer Regeln für Data Retention und Redaction.
  4. Berechnen Sie Preise, Limits, Berechtigungen und andere semantische Regeln vor der Verwendung erneut in Application Code. Testen Sie Boundary Values, die das Schema allein nicht ablehnen kann.

Der nächste Test

Beginnen Sie mit dem Discount-Limit und einer unvollständigen Completion. Der Offline-Check deckt beides ab, kann Ihnen jedoch nicht sagen, ob ein Model einen echten Kunden korrekt routet oder die Margin korrekt erklärt. Halten Sie für eine Live-Evaluation Model, Prompts, Schema und Serving-Einstellungen konstant. Zählen Sie unvollständige Ergebnisse, Schema-Fehler, Routing-Fehler und Policy-Rejections getrennt, bevor Sie Kosten oder Task-Accuracy vergleichen.
