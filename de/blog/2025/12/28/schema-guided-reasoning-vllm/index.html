Schema-Guided Reasoning auf vLLM: Strukturierte Outputs mit xgrammar und Pydantic

Das Wiederholen eines LLM-Aufrufs garantiert kein gültiges JSON. Das nächste Beispiel könnte auf dieselbe Weise fehlschlagen, und wiederholte Aufrufe erhöhen Latenz und Kosten.

Schema-Guided Reasoning (SGR) erzwingt ein Schema, während das Modell jeden Token generiert. Sie definieren die erforderlichen Felder mit Pydantic, und die Inferenz-Engine blockiert Tokens, die gegen diese Struktur verstoßen würden. Das Ergebnis ist konstruktionsbedingt syntaktisch gültig, statt durch Wiederholung zu werden.

Kurzfassung. SGR nutzt Constrained Decoding, um die Ausgabe eines LLMs an ein von Ihnen kontrolliertes Pydantic-Schema zu binden. Kombiniert man es mit dem xgrammar-Backend von vLLM, wird das Schema bereits beim Decode durchgesetzt – mit vernachlässigbarem Latenzaufwand.

Was ist Schema-Guided Reasoning?

Schema-Guided Reasoning ist eine Technik, die Rinat Abdullin im Jahr 2024 beschrieben hat. Anstatt das Modell den Text frei vervollständigen zu lassen (was inkonsistent oder mehrdeutig sein kann), gibt man ihm eine strikte Vorlage, die festlegt:

  • welche Schritte es durchlaufen muss, sodass es die Analyse nicht überspringen kann
  • in welcher Reihenfolge diese Schritte ablaufen, damit das Reasoning vom Datensatz bis zur Entscheidung verläuft
  • worauf es seine Aufmerksamkeit richten soll

Stellen Sie sich das als eine kognitive Checkliste vor, der das Modell folgen muss.

Was das Schema steuert

Felder wie churn_analysis, margin_math und max_discount_percent machen die erwarteten Zwischenoutputs explizit. Das Modell muss die erforderliche Struktur füllen, bevor es die endgültige Rabattentscheidung zurückgeben kann.

Das bietet Ihnen:

  • reproduzierbares Reasoning über wiederholte Durchläufe hinweg
  • auditable Outputs, bei denen jeder Schritt überprüfbar ist
  • Zwischenfelder, die Sie anhand eines Test-Datasets bewerten können
  • kleinere Modelle, die praktikabel werden, da das Schema die Struktur bereitstellt, die das Modell sonst lernen müsste
  • eine gemeldete Genauigkeitssteigerung von 5–10 % in Abdullins Produktionsworkloads, die Sie an Ihren eigenen Daten überprüfen sollten

Prompt-Engineering: semantische Überredung

Please analyze the customer data and output your response as valid JSON
with the following structure: {"discount": <number>, "reason": <string>}
Be careful with the formatting!

Sie hoffen, dass das Verständnis des Modells für “auszugebendes JSON” seine Neigung zur Konversation überwiegt. Ein Modell-Update, eine Temperaturänderung oder ein anderes Few-Shot-Beispiel können Ihren Parser jedoch zum Scheitern bringen.

Chain of Thought: besseres Reasoning, gleiches Strukturproblem

Let's think step by step:
1. First, I'll analyze the customer's churn risk...
2. Then I'll calculate the margin...
3. Therefore, I recommend a 15% discount.

CoT verbessert die Accuracy des Reasonings, verschlechtert jedoch die Struktur. Die Ausgabe ist unvorhersehbare Prosa, die sich nur schwer zuverlässig parsen lässt. Meist führt dies dazu, dass Sie einen zweiten LLM-Aufruf durchführen müssen, nur um die strukturierten Daten zu extrahieren.

SGR: strukturierte Chain of Thought

SGR bewahrt die Intuition von CoT, dass Zwischen-Reasoning die Genauigkeit erhöht. Es formalisiert lediglich die einzelnen Schritte:

class PricingLogic(BaseModel):
    # 1. Data Analysis (must complete before decision)
    churn_analysis: str = Field(..., description="Analyze churn_probability")
    financial_analysis: str = Field(..., description="Analyze cart_value and margin")

    # 2. Math Enforcement (explicit calculation)
    margin_math: str = Field(..., description="Calculate: 'Cart $X * Y% = $Z'")

    # 3. Decision Constraint (bounded by prior analysis)
    max_discount_percent: float = Field(..., description="Max allowed discount")

    # 4. Final Output
    offer_code: str
    customer_message: str

Das Modell kann max_discount_percent erst dann ausgeben, wenn churn_analysis, financial_analysis und margin_math gefüllt sind.

SGR-Muster

SGR verfügt über drei Kernmuster, die sich zu größeren Workflows zusammenfügen.

1. Cascade: sequentielle Reasoning-Schritte

Cascade erzwingt eine bestimmte Reasoning-Reihenfolge. Jedes Feld muss abgeschlossen sein, bevor das nächste beginnt.

from pydantic import BaseModel
from typing import Literal, Annotated
from annotated_types import Ge, Le

class CandidateEvaluation(BaseModel):
    """Evaluate a job candidate with enforced reasoning order."""

    # Step 1: Summarize (forces context awareness)
    brief_candidate_summary: str

    # Step 2: Rate (bounded integer)
    rate_skill_match: Annotated[int, Ge(1), Le(10)]

    # Step 3: Decide (constrained choices)
    final_recommendation: Literal["hire", "reject", "hold"]

Gute Anwendungen: Kandidatenbewertung, Dokumentenklassifizierung, Compliance-Analyse, medizinische Diagnose.

Das Modell muss brief_candidate_summary schreiben, bevor es bewerten kann, und bewerten, bevor es empfehlen kann.

2. Routing: eine semantische Switch-Anweisung

Routing verpflichtet das Modell, einen bestimmten Pfad aus einer Reihe von Optionen zu wählen, implementiert mit Union-Typen.

from pydantic import BaseModel
from typing import Literal, Union

class FeatureLookup(BaseModel):
    """Route to database lookup."""
    rationale: str
    tool_name: Literal["fetch_user_features"] = "fetch_user_features"
    user_id: str

class GeneralResponse(BaseModel):
    """Standard response for non-pricing queries."""
    tool_name: Literal["respond"] = "respond"
    content: str

class RouterSchema(BaseModel):
    """The model must pick exactly ONE branch."""
    action: Union[FeatureLookup, GeneralResponse]

Gute Anwendungen: Intent-Klassifizierung, Tool-Auswahl, Support-Triage, Multi-Agent-Dispatch.

Der Literal-Diskriminator (tool_name) veranlasst das Modell, einen einzigen Zweig zu wählen und nur die Felder auszufüllen, die dieser Zweig benötigt.

3. Zyklus: wiederholtes Reasoning mit Listen

Der Zyklus zwingt das Modell, mehrere Elemente zu erzeugen, wobei die Anzahl begrenzt ist.

from pydantic import BaseModel
from typing import List, Literal, Annotated
from annotated_types import MinLen, MaxLen

class RiskFactor(BaseModel):
    explanation: str
    severity: Literal["low", "medium", "high"]

class RiskAssessment(BaseModel):
    """Generate 2-4 risk factors."""
    factors: Annotated[List[RiskFactor], MinLen(2), MaxLen(4)]

Gute Anwendungsfälle: Risikobewertung, Issue-Extraktion, parallele Tool Calls, mehrstufiges Planning.

Die MinLen und MaxLen Grenzen erzwingen mindestens 2 und höchstens 4 Elemente. In Verbindung mit Routing ermöglicht dies die Verteilung eines festbreiten Batches von Tool Calls.

SGR zum Funktionieren bringen: eingeschränkte Dekodierung

Die oben genannten Muster sind lediglich Pydantic-Schemas. Was sie verbindlich macht, ist die eingeschränkte Dekodierung (auch als Structured Output bezeichnet).

Die eingeschränkte Dekodierung modifiziert den Schritt der Token-Generierung. Anstatt dem Modell freie Auswahl aus seinem Vokabular zu ermöglichen, wendet die Engine eine Grammatikmaske an, die Tokens blockiert, die gegen das Schema verstoßen würden. Dies geschieht im Inference-Engine, nicht in Ihrem Anwendungscode.

[!TIPP] SGR erfordert keine „Reasoning-Modelle“ wie o1 oder DeepSeek-R1. Es funktioniert problemlos mit instruktions-abgestimmten Modellen und besonders gut mit Modellen, die aus Reasoning-Modellen abgeleitet wurden.

Warum sich dieser Artikel auf vLLM und xgrammar konzentriert

Einige Gründe:

  • vLLM ist einer der am weitesten verbreiteten Open-Source-LLM-Inference-Engines, sodass das hier Erstellte problemlos portiert werden kann.
  • xgrammar ist in C++ implementiert und verursacht nur eine vernachlässigbare Latenz.
  • Die API von vLLM ist mit OpenAI kompatibel, was die Migration von Cloud-Anbietern kostengünstig hält.
  • xgrammar bewältigt komplexe verschachtelte Schemata, Vereinigungen und rekursive Strukturen.

Wie xgrammar Schemata durchsetzt

Wo die Maskierung stattfindet

xgrammar modifiziert die Ausgabe-Logits nach dem Forward-Pass des Models und vor dem Sampling. Es verändert das Model selbst nicht; es filtert lediglich, welche Tokens ausgewählt werden können.

Ein standardmäßiger Inference-Loop sieht folgendermaßen aus:

1. Input tokens → GPU Forward Pass → Logits (probability scores for all ~128K tokens)
2. Logits → Sampling (temperature, top-p, etc.) → Next Token
3. Repeat until done

xgrammar schiebt sich zwischen Schritt 1 und 2 ein:

1. Input tokens → GPU Forward Pass → Raw Logits
2. Raw Logits → xgrammar Logits Processor → Masked Logits
3. Masked Logits → Sampling → Next Token (guaranteed valid)
4. Repeat until done

Das Model berechnet weiterhin seine vollständige Wahrscheinlichkeitsverteilung auf der GPU. Anschließend läuft xgrammar auf der CPU und wendet eine Bitmaske auf diese Logits an, bevor das Sampling erfolgt. Ungültige Tokens erhalten Logits im Wert von -∞, wodurch ihre Wahrscheinlichkeit nach der Softmax-Funktion exakt Null wird.

Zwei Phasen

xgrammar teilt die Arbeit in Compile-Time und Runtime auf – genau das macht es so schnell.

Phase 1: Grammatik-Kompilierung, einmal pro Schema

# This happens once per schema
tokenizer_info = xgr.TokenizerInfo.from_huggingface(tokenizer)
grammar_compiler = xgr.GrammarCompiler(tokenizer_info)
compiled_grammar = grammar_compiler.compile_json_schema(schema_json)

Während der Kompilierung führt xgrammar folgende Schritte aus:

  1. Konvertiert das JSON-Schema in eine kontextfreie Grammatik.
  2. Erstellt einen Pushdown-Automaten (PDA), also eine State Machine mit einem Stack, um verschachtelte Strukturen wie {"a": {"b": {"c": ...}}} zu handhaben.
  3. Berechnet im Voraus, welche Tokens an jeder Grammatikposition gültig sind. Das Ergebnis ist der „adaptive Token-Masken-Cache“.
  4. Kategorisiert Tokens als „kontextunabhängig“ (cachefähig) oder „kontextabhängig“ (müssen zur Laufzeit gegen den Stack-Zustand geprüft werden).

[!HINWEIS] Etwa 99 % der Tokens erweisen sich als kontextunabhängig und landen im Cache (XGrammar paper). Die meisten Gültigkeitsprüfungen zur Laufzeit sind daher reine Cache-Lookups, weshalb xgrammar so schnell ist.

Phase 2: Laufzeit-Maskengenerierung, für jeden Token

Bei jedem Generierungsschritt:

  1. Der GrammarMatcher verfolgt die aktuelle Position in der Grammatik.
  2. Er sucht im vorgefertigten Cache nach Masken für kontextunabhängige Tokens.
  3. Er führt den PDA aus, um die verbleibenden kontextabhängigen Tokens zu prüfen.
  4. Er kombiniert alles zu einer finalen Bitmaske und wendet sie auf die Logits an.

Warum Pushdown-Automaten und nicht reguläre Ausdrücke?

Wegen der Schachtelung. Ein regulärer Ausdruck (eine endliche Zustandsmaschine) kann Strukturen wie folgende nicht zuverlässig abgleichen:

{ "user": { "profile": { "settings": { "theme": "dark" } } } }

Der schwierige Teil sind die schließenden geschweiften Klammern }}}: Man muss sich merken, wie viele davon geöffnet wurden. Ein Pushdown-Automat verfügt über einen Stack, der dies verfolgt, sodass er eine beliebige Schachtelungstiefe bewältigen kann. Aus diesem Grund kann xgrammar auch Union-Typen, verschachtelte Objekte und rekursive Schemata durchsetzen, wo regex-basierte Ansätze versagen.

Ein konkretes Beispiel: Erzeugung eines Float-Feldes

Wenn das Model "max_discount_percent": generiert, weiß xgrammar anhand des Schemas, dass als Nächstes ein float folgt. Die Maskierung:

  • erlaubt (Wahrscheinlichkeit unverändert): 0, 1, 2, …, 9, ., -
  • blockiert (Wahrscheinlichkeit auf 0 gesetzt): ", {, [, true, false, null sowie den Rest des über 128.000 Wörter umfassenden Vokabulars

Der Vorwärtsdurchlauf könnte dem Wort "fifteen" eine hohe Wahrscheinlichkeit zugeordnet haben. Nach der Maskierung durch xgrammar beträgt die Wahrscheinlichkeit dieses Tokens 0. Das Model muss nun Ziffern ausgeben.

Warum „nahezu kein Overhead“?

Drei Gründe:

  1. Parallele Ausführung. Die Maskenberechnung auf der CPU überschneidet sich mit dem nächsten Vorwärtsdurchlauf auf der GPU. Während die GPU die Logits für Token N+1 berechnet, berechnet die CPU die Maskierung für Token N.
  2. Caching. Der Großteil der Gültigkeitsprüfung erfolgt zur Compile-Zeit. Zur Laufzeit handelt es sich meist nur um Cache-Lookups.
  3. C++-Implementierung. Der Hotpath ist C++, nicht Python, und die Maskierung wird direkt in den Logits angewendet.

In Benchmarks zeigt xgrammar einen vernachlässigbaren Overhead, und die strukturierte Generierung kann gelegentlich schneller sein als die uneingeschränkte Generierung, da das eingeschränkte Vokabular das Sampling günstiger macht.

Schritt 1: Definition der Schemata

# sgr/models/schemas.py
from pydantic import BaseModel, Field
from typing import Literal, Union


# --- Phase 1: Routing (Union for branching) ---
class FeatureLookup(BaseModel):
    """Route to DB lookup if pricing context is needed."""
    rationale: str
    tool_name: Literal["fetch_user_features"] = "fetch_user_features"
    user_id: str


class GeneralResponse(BaseModel):
    """Standard response for non-pricing queries."""
    tool_name: Literal["respond"] = "respond"
    content: str


class RouterSchema(BaseModel):
    action: Union[FeatureLookup, GeneralResponse]


# --- Phase 2: Pricing Logic (Cascade for sequential reasoning) ---
class PricingLogic(BaseModel):
    """
    Strict reasoning topology for dynamic pricing.
    Fields are ordered to enforce the analysis→decision flow.
    """
    # 1. Data Analysis (Reflection)
    churn_analysis: str = Field(...,
        description="Analyze churn_probability (High > 0.7).")
    financial_analysis: str = Field(...,
        description="Analyze cart_value and profit_margin.")

    # 2. Hard Math Enforcement
    margin_math: str = Field(...,
        description="Calculate absolute profit: 'Cart $200 * 0.20 Margin = $40'.")

    # 3. The Decision Constraint
    max_discount_percent: float = Field(...,
        description="Max allowed discount %. NEVER exceed margin.")

    # 4. Final Output
    offer_code: str = Field(..., description="Generated code (e.g. SAVE20).")
    customer_message: str = Field(..., description="The final polite offer text.")

Schritt 2: Ein LLM-Client, der xgrammar aktiviert

# sgr/utils/llm_client.py
from openai import OpenAI
from pydantic import BaseModel
from typing import TypeVar
import json

T = TypeVar("T", bound=BaseModel)


class LLMClient:
    """Wrapper for vLLM with xgrammar-enforced structured generation."""

    def __init__(self, base_url: str = "http://localhost:8000/v1"):
        self.client = OpenAI(base_url=base_url, api_key="EMPTY")
        self.model = self._get_available_model()

    def _get_available_model(self) -> str:
        """Auto-detect the model running on vLLM server."""
        try:
            models = self.client.models.list()
            if models.data:
                return models.data[0].id
        except Exception:
            pass
        return "Qwen/Qwen2.5-7B-Instruct"

    def run_sgr(self, messages: list[dict], schema_class: type[T]) -> T:
        """Run inference with Schema-Guided Response constraints.

        Uses vLLM's guided_json with xgrammar backend to enforce
        strict schema constraints at the token generation level.
        """
        schema_dict = schema_class.model_json_schema()

        # Enhance system message with schema for model guidance
        enhanced_messages = messages.copy()
        if enhanced_messages and enhanced_messages[0]["role"] == "system":
            schema_json = json.dumps(schema_dict, indent=2)
            enhanced_messages[0] = {
                "role": "system",
                "content": (
                    enhanced_messages[0]["content"]
                    + f"\n\nRespond with JSON matching this schema:\n{schema_json}"
                ),
            }

        # vLLM's guided_json with the xgrammar backend
        completion = self.client.chat.completions.create(
            model=self.model,
            messages=enhanced_messages,
            temperature=0.1,  # Low temp for deterministic reasoning
            extra_body={
                "guided_json": schema_dict,  # Pydantic schema as dict
                "guided_decoding_backend": "xgrammar",  # Hardware-enforced
            },
        )

        raw_response = completion.choices[0].message.content
        return schema_class.model_validate_json(raw_response)

[!HINWEIS] guided_json akzeptiert ein JSON-Schema-Dict. Mit guided_decoding_backend: "xgrammar" kann das LLM nur Tokens generieren, die ein gültiges JSON bilden und Ihrem Schema entsprechen.

Schritt 3: Orchestrierung des Agents

# sgr/agent.py
from .models.schemas import PricingLogic, RouterSchema
from .prompts.routing import build_routing_prompt
from .prompts.pricing import build_pricing_context_prompt, ASSISTANT_FETCH_MESSAGE
from .store.hybrid_store import HybridFeatureStore
from .utils.llm_client import LLMClient


def pricing_agent(user_query: str, user_id: str) -> str:
    """Process a pricing query with three-phase SGR workflow."""

    llm = LLMClient()
    feature_store = HybridFeatureStore()

    # Build conversation history
    history = [
        {"role": "system", "content": build_routing_prompt(user_id)},
        {"role": "user", "content": user_query},
    ]

    # --- Phase 1: Routing (Uses RouterSchema) ---
    print(f"🤖 Processing: '{user_query}' for {user_id}")
    decision = llm.run_sgr(history, RouterSchema)
    print(f"📍 Routing decision: {decision.action.tool_name}")

    if decision.action.tool_name == "respond":
        return decision.action.content

    # --- Phase 2: Context Retrieval ---
    if decision.action.tool_name == "fetch_user_features":
        print(f"🔍 Fetching features for {user_id}...")
        context = feature_store.get_user_context(user_id)

        if not context:
            return "Error: User profile not found."

        print(f"   [Data] LTV: ${context.get('user_ltv')} | "
              f"Margin: {context.get('cart_profit_margin', 0) * 100}%")

        # Inject context into conversation
        history.append({"role": "assistant", "content": ASSISTANT_FETCH_MESSAGE})
        history.append({
            "role": "user",
            "content": build_pricing_context_prompt(
                churn_prob=context.get("churn_probability", 0.5),
                cart_val=context.get("current_cart_value", 100),
                margin=context.get("cart_profit_margin", 0.2),
                user_ltv=context.get("user_ltv", 0),
            ),
        })

        # --- Phase 3: SGR Logic Execution (Uses PricingLogic) ---
        print("🧠 Calculating Offer (Schema Enforced)...")
        offer = llm.run_sgr(history, PricingLogic)

        # Audit log — the SGR benefit: explicit reasoning traces
        print(f"   [Audit] Math: {offer.margin_math}")
        print(f"   [Audit] Max Allowed: {offer.max_discount_percent}%")

        return offer.customer_message

    return "I'm sorry, I couldn't process your request."


if __name__ == "__main__":
    response = pricing_agent("I want a discount or I'm leaving!", "user_102")
    print(f"\n💬 Final Reply: {response}")

Schema, vLLM und Produktions-Checkliste

Schema-Design

  1. Felder nach dem Reasoning-Fluss sortieren. Analysefelder stehen vor Entscheidungsfeldern.
  2. Schreiben Sie beschreibende Field-Beschreibungen. Sie lenken die Aufmerksamkeit des Modells ebenso wie der Feldname selbst.
  3. Beschränken Sie mit Literal und Annotated. Verwenden Sie Literal["a", "b"] für Enums und Annotated[int, Ge(1), Le(10)] für Grenzwerte.
  4. Halten Sie die Schemata fokussiert. Ein Schema pro Reasoning-Phase, anschließend durch mehrere Aufrufe zusammenfügen.

vLLM-Konfiguration

  1. Verwenden Sie eine niedrige Temperatur (0,1–0,3) für ein wiederholbareres Reasoning.
  2. Überlassen Sie xgrammar die Strukturierung. Kämpfen Sie nicht mit Formatierungsanweisungen im Prompt dagegen an.
  3. Achten Sie auf die Token-Nutzung. SGR verwendet in der Regel weniger Tokens als CoT, da keine ausführliche Prosa vorhanden ist.

Produktionsüberlegungen

  1. Versionieren Sie Ihre Schemata genauso wie Ihre APIs.
  2. Auch bei SGR müssen Netzwerk- und Serverfehler weiterhin elegant behandelt werden.
  3. Protokollieren Sie rohe SGR-Ausgaben zur Compliance und Fehlersuche.
  4. Testen Sie mit Randfällen, damit das Schema auch an den Grenzen hält.

Fazit

Sie definieren die Reasoning-Topologie in Pydantic, lassen xgrammar sie zum Zeitpunkt der Decodierung durchsetzen, und das Ergebnis ist:

  • syntaktisch gültig von Haus aus, wodurch die Wiederholungs- und Neuparsing-Schleife entfällt
  • auf Feldebene überprüfbar
  • mit kleineren Modellen nutzbar, da diese das Format nicht mehr selbst exakt festlegen müssen
  • kostengünstiger im Betrieb, da Sie weniger Tokens, weniger Wiederholungen und kleinere Modelle verwenden

Die sgr-discount-manager-Demo verbindet jedes Codebeispiel dieses Beitrags mit einem echten vLLM-Server. Klonen Sie sie und beginnen Sie, die Schemata an Ihren eigenen Workflow anzupassen.

Wichtige Erkenntnisse

  1. Schema-Guided Reasoning macht die Reasoning-Topologie explizit, statt zu hoffen, dass das Modell prosaischen Anweisungen folgt.
  2. Constrained Decoding verhindert ungültiges JSON bereits beim Generieren – das ist sauberer, als es später zu validieren und erneut zu versuchen.
  3. Platzieren Sie Analysefelder vor Entscheidungsfeldern, wenn das Schema das Reasoning vor der Ausgabe erzwingen soll.
  4. Verwenden Sie SGR, wenn nachgelagerte Codes von der Struktur abhängen, nicht wenn freie Prosa das Endprodukt ist.
