Leitfaden zur Bereitstellung mit LoRAX: Betrieb mehrerer LoRA-Adapter auf Kubernetes

Ein Basismodell in Kombination mit vielen LoRA-Adaptern stellt ein ungewöhnliches Bereitstellungsproblem dar. Die Basisgewichte werden gemeinsam genutzt, doch jeder Anfrage kann ein anderer Satz an Adaptergewichten benötigt werden. Ein herkömmliches Design, bei dem für jede Variante eine eigene Deployment-Einheit erstellt wird, führt dazu, dass GPU-Speicher verschwendet wird, da die meisten Varianten untätig bleiben.

LoRAX löst dieses Problem im Bereich der sogenannten „Long Tail“. Es lädt Adapter nach Bedarf, gruppiert Anfragen für verschiedene Adapter zusammen und bewegt die Adaptergewichte zwischen GPU- und CPU-Speicher hin und her. Der ansprechende Slogan lautet: „Tausende feinabgestimmter Modelle auf einer einzigen GPU.“ Die technische Frage ist jedoch enger gefasst: Bringt das geplante Austauschschema von Adaptern, das Eintreffen neuer Anfragen sowie das angestrebte Latenzniveau einen ausreichenden Nutzen mit sich, um einen zusätzlichen Agent Runtime zu rechtfertigen?

Dieser Leitfaden beantwortet diese Frage, überprüft die API lokal und wandelt anschließend das Starter-Helm-Chart des Repositoriums in einen konkreten Produktionsplan um.

Kurzfassung: Wählen Sie LoRAX, wenn viele kompatible LoRA-Adapter ein gemeinsames Basismodell teilen und der Datenverkehr spärlich oder langgezogen verteilt ist. Die verfügbare Kapazität hängt vom aktiven Arbeitsset ab – nicht von der Größe des gesamten Katalogs. Festlegen Sie den Agent Runtime, authentifizieren und listen Sie die Adapter-ID‑Werte auf, fügen Sie dauerhafte Caching‑Mechanismen sowie Überwachungsmechanismen hinzu, richten Sie die Routen so ein, dass die Cache‑Lokalität gewährleistet wird, und messen Sie getrennt die Leistung bei kalten und warmen Anfragen.

Das Bereitstellungsproblem liegt im Arbeitsset

LoRA „efriert“ ein Basismodell und lernt niedrig-rangige Aktualisierungen für ausgewählte Gewichtsmatrizen. Der resultierende Adapter ist in der Regel deutlich kleiner als ein vollständiger Checkpoint, seine Größe hängt jedoch weiterhin vom Rang, den Zielmodulen, der Anzahl der Schichten sowie vom Datentyp ab. Feste Angaben wie „jeder Adapter ist 100 MB groß“ liefern ungenaue Informationen zur verfügbaren Kapazität.

Für die Bereitstellung sind drei Größen zu unterscheiden:

  • Kataloggröße: Alle Adapter, die eine Plattform aus dem Speicher auflösen kann
  • Aktives Arbeitsset: Adapter, die innerhalb des Cache‑Retentionszeitraums Anfragen erhalten
  • Konkurrenzset: Adapter, die zum gleichen Zeitpunkt in Batches dargestellt werden

Ein Katalog kann Tausende von Adaptern enthalten, ohne dass diese alle in den VRAM passen. Entscheidend sind vielmehr die Häufigkeit, mit der sich das aktive Set ändert, die Größe dieser Adapter sowie die Möglichkeit, dass Anfragen für unterschiedliche Adapter nützliche Batches teilen können.

LoRAX kombiniert vier Mechanismen:

  1. Das Basismodell bleibt für alle kompatiblen Adapter vorhanden.
  2. Eine Anfrage gibt einen Adapter an, der aus Hugging Face, Predibase oder einem Dateisystem aufgelöst werden kann.
  3. Das Austauschschema für Adapter lädt Gewichte im Voraus und verschiebt sie zwischen GPU- und CPU-Speicher.
  4. Heterogene kontinuierliche Batching‑Verfahren gruppieren Anfragen, die unterschiedliche Adapter betreffen.

Laut den Projektberichten halten heterogene Batching‑Verfahren in den Benchmarks die Throughput‑Werte sowie die Latenz nahezu konstant, auch wenn die Anzahl der gleichzeitig aktiven Adapter zunimmt. Behandeln Sie dies als Hypothese für Ihre eigene Workload. Die Länge der Prompts, die Länge der Ausgaben, der Rang, die Zielmodule, die Auslastung der Batches, die Cache‑Veränderungen sowie die GPU-Generierung können die Ergebnisse beeinflussen.

Wann LoRAX eine sinnvolle Wahl ist

LoRAX lohnt sich, wenn alle folgenden Bedingungen erfüllt sind:

  • Die Adapter wurden unter Verwendung desselben unterstützten Basismodells sowie desselben Tokenizer-Vertrags trainiert
  • Der Datenverkehr umfasst viele Adapter mit einer deutlichen Long Tail
  • Das Nachladen eines kaltstartenden Adapters nach Bedarf ist vorteilhafter als die Bereitstellung eines eigenen Deployments dafür
  • Es existiert bereits eine Routierung von Tenant‑ oder Task‑Anfragen an der Anwendungsgrenze
  • Das Team verfügt über einen spezialisierten Inference Runtime samt entsprechendem Cache‑Verhalten

Typische Anwendungsfälle umfassen tenant-spezifische Assistenten, zahlreiche Domänenvarianten sowie Online-Experimente, die einen gemeinsamen Basis-Checkpoint teilen.

Eine geringere Eignung zeigt sich hingegen dann, wenn nur wenige Adapter den Datenverkehr dominieren, die Modelle keinen gemeinsamen Basis-Code teilen, strenge Latenzziele einen „Cold Start“ nicht zulassen oder die Plattform nicht sicher steuern kann, welche Artefakte der Server lädt. In solchen Fällen kann eine herkömmliche vLLM- oder TGI-Implementierung mit fester Adapterliste einfacher zu handhaben sein.

Verwenden Sie Kubernetes nicht einfach deshalb, weil das Katalogvolumen groß ist. Überprüfen Sie zunächst die Kompatibilität von Agent Runtime und Adaptern auf einer einzigen GPU.

Lokale Überprüfung eines Basis-Modells sowie zweier Adapter

Die LoRAX README empfiehlt den vorgefertigten Container. In einer echten Umgebung sollten unveränderliche Image-Digests verwendet werden; main wird hier lediglich aus Gründen angegeben, dass es sich um die im Repository dokumentierte Quick-Start-Tag handelt.

mkdir -p data

docker run --rm --gpus all --shm-size 1g \
    -p 8080:80 \
    -v "$PWD/data:/data" \
    ghcr.io/predibase/lorax:main \
    --model-id mistralai/Mistral-7B-Instruct-v0.1

Als dokumentierte Mindestanforderungen gelten Linux, Docker, eine NVIDIA-GPU der Ampere-Reihe oder neuer sowie Treiber, die CUDA 11.8 unterstützen. Model-Lizenzen sowie geschützte Repositorien können außerdem einen Hugging Face Token erfordern.

Beginnen Sie mit dem Basis-Modell:

curl http://127.0.0.1:8080/generate \
    -H 'Content-Type: application/json' \
    -d '{
      "inputs": "[INST] Give one reason to measure cold-adapter latency. [/INST]",
      "parameters": {"max_new_tokens": 64}
    }'

Senden Sie anschließend einen kompatiblen Adapter:

curl http://127.0.0.1:8080/generate \
    -H 'Content-Type: application/json' \
    -d '{
      "inputs": "[INST] Solve: Natalia sold 48 clips in April and half as many in May. What is the total? [/INST]",
      "parameters": {
        "max_new_tokens": 64,
        "adapter_id": "vineetsharma/qlora-adapter-Mistral-7B-Instruct-v0.1-gsm8k"
      }
    }'

Der erste Anfragen kann dazu führen, dass der Adapter heruntergeladen und geladen wird; spätere Anfragen können hingegen auf in Cache gespeicherte Artefakte sowie bereits vorliegende Gewichte zurückgreifen. Dokumentieren Sie beide Vorgänge. Ein einzelner „warm“er Anruf sagt wenig über das Verhalten bei selten genutzten Szenarien aus.

Verwendung des aktuellen OpenAI Clients

LoRAX stellt einen mit OpenAI kompatiblen Chat-Endpunkt bereit. Das Feld model identifiziert den jeweiligen Adapter:

from openai import OpenAI


client = OpenAI(
    api_key="EMPTY",
    base_url="http://127.0.0.1:8080/v1",
)

response = client.chat.completions.create(
    model="alignment-handbook/zephyr-7b-dpo-lora",
    messages=[
        {"role": "user", "content": "Explain cache locality in two sentences."},
    ],
    max_tokens=100,
)

print(response.choices[0].message.content)

Standardmäßig benötigt der Server keine API-Key. Dies ist für den lokalen Betrieb praktisch, stellt aber als Internet-zugängliche Konfiguration ein Sicherheitsrisiko dar. Stellen Sie Authentifizierung, Berechtigungsverwaltung nach Tenant-Prinzipien, Quotenregelungen sowie eine Allowlist für Adapter vor diesen Endpunkt.

Definition einer Kompatibilitätsprüfung

Bevor ein Adapter in den Katalog aufgenommen wird, müssen mindestens folgende Aspekte überprüft werden:

  • deklariertes Basis-Modell und dessen Revision
  • Kompatibilität von Tokenizer und Chat-Template
  • vom Agent Runtime unterstützte LoRA-Rank-Werte sowie Zielmodule
  • Format der Artefakte sowie Tensor-Formen
  • Lizenzinformationen, Herkunftsdaten sowie Integritäts-Digests
  • ein kleines Set an Verhaltens- und Regressionstests

Inkompatible Artefakte sollten bereits bei der Registrierung abgelehnt werden, anstatt erst bei der ersten Anfrage eines Benutzers.

Verständnis der Residenz vor der Bereitstellung

Das Basis-Modell verbraucht den größten Teil des fest zugewiesenen GPU-Gedächtnisses. Für den Rest konkurrieren die Adapter-Gewichte, der KV-Cache, der Batch-Workspace sowie die Runtime-Kerne miteinander. Die CPU-RAM kann entlastet werden, indem dort entladebare Adapter gespeichert werden, während /data heruntergeladene Artefakte speichert.

Es handelt sich dabei nicht um austauschbare Ebenen. Ein auf Disk oder im Hub gespeichertes Artefakt muss zuerst gelesen und in den Speicher geladen werden, bevor es zu einem im CPU- oder GPU-Speicher residierenden Adapter wird. Messen Sie die Übergänge getrennt voneinander:

PfadWas enthält er?Zu erfassende Metrik
GPU-HitAdapter ist bereits im Speicher vorhandenWartezeit im Queue sowie Zeit bis zum ersten Token
CPU-HitÜbertragung oder Neuinitialisierung ins GPUVerzögerung beim Laden des Adapters sowie Gesamtlatenz
Artefakt-HitLesevorgang aus dem lokalen /data CacheLese-/Ladeverzögerung sowie Anzahl der Cache-Bytes
Remote-MissHerunterladen, Validierung und LadenDownload-Zeit, Fehlerhäufigkeit sowie Gesamtkaltlatenz

Die Kapazitätsplanung sollte die tatsächliche Verteilung der Popularität der Adapter nachbilden. Einheitlich zufällig generierte Adapter-IDs führen aufgrund einer arbeitsspezifischen Laststruktur, die dem Zipf‑Gesetz ähnelt, zu anderen Problemen im Cache‑Management.

Deployieren Sie den Repository‑Chart sorgfältig

Der Repository enthält charts/lorax, weshalb ein wiederholbarer Ausgangspunkt eine festgepinnte Repository‑Revision sowie ein lokaler Chart darstellt:

git clone https://github.com/predibase/lorax.git
cd lorax
git checkout <reviewed-commit-or-release>

helm dependency update charts/lorax
helm template lorax charts/lorax -f values.production.yaml
helm upgrade --install lorax charts/lorax \
    --namespace inference \
    --create-namespace \
    -f values.production.yaml

Wie am 15. Juli 2026 geprüft, erfordern die Standardeinstellungen des Charts Aufmerksamkeit:

  • Die Image‑Tag ist latest
  • /data ist ein emptyDir, wodurch das Ersetzen von Pods die heruntergeladenen Artefakte löscht
  • Die Liveness- und Readiness‑Probes sind leer
  • Der Hugging Face‑Token wird als reiner Umgebungswert behandelt
  • Standardmäßig wird eine einzige GPU angefordert

Dadurch dient der Chart lediglich als nützliches Gerüst, nicht als Produktivrichtlinie.

Beginnen Sie mit der tatsächlichen Wertstruktur des Charts

Der Chart gruppiert die Laufzeitkonfiguration unter deployment, wobei die Launcher‑Argumente eine Liste von Namens/Wert‑Paaren bilden. Eine minimale Struktur sieht wie folgt aus:

deployment:
    replicas: 1

    image:
        repository: ghcr.io/predibase/lorax
        tag: "<tested-tag>" # Prefer an immutable digest in rendered manifests.

    args:
        - name: "--model-id"
          value: "mistralai/Mistral-7B-Instruct-v0.1"
        - name: "--max-input-length"
          value: "2048"
        - name: "--max-total-tokens"
          value: "3072"
        - name: "--max-batch-total-tokens"
          value: "8192"
        - name: "--max-batch-prefill-tokens"
          value: "4096"

    resources:
        requests:
            nvidia.com/gpu: "1"
        limits:
            nvidia.com/gpu: "1"

    readinessProbe:
        httpGet:
            path: /health
            port: http
        periodSeconds: 5
        failureThreshold: 600

service:
    serviceType: ClusterIP
    port: 80

Die oben genannten Token‑Limitierungen dienen lediglich als Beispielwerte, keine Empfehlungen zur Größenbestimmung. Diese Werte sollten aus repräsentativen Prompts, der erwarteten Konkurrenzlast, der GPU‑Speicherkapazität sowie Load‑Tests abgeleitet werden.

Beheben Sie die Lücken explizit

Das aktuelle Chart‑Template enthält fest codierte emptyDir‑Volumina sowie einfache Umgebungsvariablen. Eine sichere Bereitstellung erfordert daher eine überprüfte Fork des Charts, einen Patch nach der Generierung oder eine höherstufige Manifest‑Schicht, um Folgendes hinzuzufügen:

  • Ein PersistentVolumeClaim oder einen node‑lokalen Artefakt‑Cache, der unter /data montiert wird
  • Eine Referenz auf ein Secret für Hub‑Anmeldedaten
  • Eine Startup‑Probe vor einer aggressiven Liveness‑Probe
  • Eine Pod‑Disruption‑Policy sowie Topologie‑Verteilung für mehrere Replicas
  • NetworkPolicy‑Einschränkungen, Service‑Account‑Restriktionen sowie einen authentifizierten Gateway
  • Image‑Digest‑Pinning sowie Prüfungen auf Integrität der Artefakte

Platzieren Sie keinen Hub‑Token direkt in einer kommitierten Values‑Datei. Nehmen Sie nicht an, dass zwei Replicas eine nützliche Hochverfügbarkeit bieten, solange beide nicht in der Lage sind, das Basismodell zu laden und der Router verhindern kann, dass alle „kalten“ Adapter an beide Pods gesendet werden.

Steuern Sie die Cache‑Lokalität

Ein Round‑Robin‑Ausgleich kann dazu führen, dass jedes Replica zu einem „kalten“ Cache wird. Ein effektiver Router hasht oder weist auf andere Weise einen zulässigen Adapter‑ID einem Replica zu, während gleichzeitig ein Failover‑Pfad bei Unverfügbarkeit dieses Replicas erhalten bleibt.

Der Routing‑Key muss aus authentifiziertem Anwendungsstatus stammen, nicht aus einem willkürlichen öffentlichen URL‑Parameter. Andernfalls kann ein Aufrufer entfernte Downloads erzwingen, Caches überfluten oder private Adapter‑Namensräume abfragen.

LoRAX oder vLLM?

Der aktuelle vLLM kann LoRA‑Module bereitstellen, die beim Start deklariert werden, und kann sie auch dynamisch über Endpunkte oder Resolver‑Plugins laden. Seine eigene Dokumentation warnt jedoch davor, dass das Aktualisieren von Adaptern während der Laufzeit Sicherheitsrisiken birgt und daher außerhalb eines isolierten, vertrauenswürdigen Umfelds nicht in der Produktion eingesetzt werden sollte.

Der aussagekräftige Vergleich betrifft eher die Betriebsaspekte als numerische Kennzahlen:

Wie werden Adapter für den Langzeitbereich entdeckt?Der Adapter-Identifikator kann auf Anfrage Ressourcen von Hugging Face, Predibase oder dem Dateisystem aufrufen.Statische Module, dynamische Verwaltungsendpunkte oder Resolver-Plugins
Wie wird die Residenzverwaltung gesteuert?Explizite Planung des Austauschs von Adaptern zwischen GPU und CPU.Konfigurierte Limits für aktive und CPU-basierte LoRA-Module sowie das Verhalten des Resolvers

Vermeiden Sie Aussagen wie „LoRAX für 1.000 Adapter, vLLM für zehn“. Allein die Größe des Katalogs bestimmt nicht die Leistung. Vergleichen Sie beide Lösungen unter denselben Voraussetzungen – d.h. mit identischer Basis, Adaptern, Prompts, Rangfolgen, Ankunftsprofilen und Hardware.

Produktionsakzeptanztest

Bevor der Katalog erweitert wird, führen Sie einen Replay-Test durch, der folgende Schritte umfasst:

  1. Eine feste Gruppe von Adaptern, um Warmthroughput und -latenz zu ermitteln.
  2. Eine Verteilung aus dem Langzeitbereich, um CPU-Nutzung und Cache-Hits zu messen.
  3. Ein Ansturm an zuvor nicht gesehenen, aber im Allowlist enthaltenen Adaptern.
  4. Ersetzung von Pods, um Wiederherstellungszeiten der Basis- und Adapterfunktionen zu prüfen.
  5. Ein nicht verfügbarer oder beschädigter Adapter, um Isolierung und Fallback-Mechanismen zu überprüfen.
  6. Mehrere gleichzeitige Nutzer, um Authentifizierung, Quoten und Metrik-Etiketten zu validieren.

Überwachen Sie dabei die Anfragenrate, Wartezeiten, Zeit bis zum ersten Token, Latenz zwischen Tokens, Gesamtlatenz, Ladezeit der Adapter, Cache-Hit-Kategorie, GPU- und CPU-Speicherbedarf, heruntergeladene Bytes sowie Fehlerursachen. Vermeiden Sie es, Adapter-IDs in unbegrenzte Metrik-Etiketten aufzunehmen; führen Sie stattdessen eine Zuordnung zu kontrollierten Dimensionen oder ausgewählten Trace-Daten durch.

Definieren Sie vor dem Test klare Akzeptanzkriterien. Beispiele hierfür sind ein maximaler Fehleranteil im Kaltpfad, ein Zielwert für die Warm-P99-Latenz, ein Cache-Hit-Zielwert entsprechend der beobachteten Popularitätsverteilung sowie ein Ziel für die Wiederherstellungszeit nach Pod-Verlust.

Fazit

LoRAX wandelt viele kompatible Feintunings, die ursprünglich als Kopien von Basismodellen dienten, in ein Problem der Platzierung von Adaptern um. Dies kann ein vorteilhafter Ansatz für Workloads mit geringer Nutzung sein, führt jedoch nicht automatisch zu konstanten Kosten oder Latenzen. Die aktive Arbeitsmenge, der Austauschweg, die Mischung der Batchs sowie die Speicherschicht bestimmen weiterhin das Ergebnis.

Prüfen Sie diese Mechanismen zunächst auf einer einzigen GPU. Anschließend gehen Sie bei der Nutzung von Kubernetes sorgfältig vor: Fixieren Sie die Artefakte, schützen Sie den Cache, sichern Sie die Zugangsdaten, autorisieren Sie die Adapter, leiten Sie die Anfragen lokal weiter und messen Sie jeden möglichen Residenzpfad. Wenn LoRAX unter denselben Bedingungen eine bessere Leistung als die aktuelle vLLM-Konfiguration zeigt, gibt es fundierte Gründe für eine Umstellung.
