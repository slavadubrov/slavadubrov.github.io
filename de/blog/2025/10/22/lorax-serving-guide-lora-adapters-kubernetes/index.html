LoRAX Serving Guide: LoRA-Adapter auf Kubernetes im großen Maßstab

Viacheslav Dubrov

2025-10-22 · Aktualisiert 2026-08-16 · 9 Min. · Modellentwicklung · KI-Infrastruktur

Automatische Übersetzung Dieser Artikel wurde automatisch aus der englischen Originalversion übersetzt.

Ein Base Model und viele LoRA-Adapter erzeugen ein ungewöhnliches Serving-Problem. Die Base Weights werden gemeinsam genutzt, aber jede Anfrage kann einen anderen Satz von Adapter Weights benötigen. Ein herkömmliches Design mit jeweils einem Deployment pro Variante verschwendet GPU-Speicher, wenn die meisten Varianten inaktiv sind.

LoRAX adressiert diesen Long Tail. Es lädt Adapter on demand, batcht Anfragen für verschiedene Adapter und verschiebt Adapter Weights zwischen GPU- und CPU-Speicher. Die attraktive Kurzform lautet: „Tausende Fine-Tuned Models auf einer GPU.“ Die eigentliche Engineering-Frage ist enger gefasst: Hilft Exchange Scheduling bei Ihrer aktiven Adapter-Menge, Ihrem Arrival Pattern und Ihrem Latency-Ziel ausreichend, um eine weitere Serving Runtime zu rechtfertigen?

Dieser Guide richtet sich an Inference- und Platform-Engineers, die viele LoRA-Varianten aus einem Base Model bereitstellen müssen. Er zeigt, wie sich die dokumentierten APIs testen, der Working Set dimensionieren und das Starter-Helm-Chart in einen expliziten Production Plan überführen lassen.

Zusammenfassung. Wählen Sie LoRAX, wenn viele kompatible LoRA-Adapter ein Base Model gemeinsam nutzen und der Traffic dünn oder Long-Tailed ist. Die Kapazität hängt vom aktiven Working Set ab, nicht von der Größe des Katalogs. Pinnen Sie die Runtime, authentifizieren und allowlisten Sie Adapter-IDs, ergänzen Sie dauerhaftes Artifact-Caching und Probes, routen Sie cache-bewusst und benchmarken Sie Cold- und Warm-Pfade getrennt.

Das Serving-Problem ist der Working Set

LoRA hält ein Base Model unverändert und lernt Low-Rank-Updates für ausgewählte Weight Matrices. Der resultierende Adapter ist normalerweise deutlich kleiner als ein vollständiger Checkpoint, aber seine Größe hängt weiterhin von Rank, Target Modules, Layer-Anzahl und Dtype ab. Feste Annahmen wie „jeder Adapter ist 100 MB groß“ sind schlechte Inputs für die Kapazitätsplanung.

Für Serving sollten Sie drei Größen unterscheiden:

  • Catalog Size: alle Adapter, die eine Platform aus dem Storage auflösen kann
  • Active Working Set: Adapter, die innerhalb des Cache-Retention-Fensters Anfragen erhalten
  • Concurrent Set: Adapter, die zum selben Zeitpunkt in Batches vertreten sind

Ein Katalog kann Tausende Adapter enthalten, ohne dass Tausende davon in den VRAM passen. Entscheidend ist, wie häufig sich der aktive Set ändert, wie groß diese Adapter sind und ob sich Anfragen für unterschiedliche Adapter in nützlichen Batches gemeinsam verarbeiten lassen.

LoRAX kombiniert vier Mechanismen:

  1. Das Base Model bleibt für alle kompatiblen Adapter resident.
  2. Eine Anfrage benennt einen Adapter, der aus Hugging Face, Predibase oder einem Filesystem aufgelöst werden kann.
  3. Adapter Exchange Scheduling lädt Weights vorab und lagert sie zwischen GPU- und CPU-Speicher aus.
  4. Heterogeneous Continuous Batching gruppiert Anfragen, die auf unterschiedliche Adapter zielen.

Das LoRAX-Projekt berichtet, dass Heterogeneous Batching in seinen Benchmarks Throughput und Latency nahezu konstant hält, wenn die Zahl gleichzeitig verwendeter Adapter steigt. Betrachten Sie dieses Vendor-Ergebnis als Hypothese für Ihren Workload. Prompt-Länge, Output-Länge, Rank, Target Modules, Batch-Auslastung, Cache Churn und GPU-Generation können das Ergebnis verändern.

Das unten wiederhergestellte Diagramm stammt aus Predibase’ LoRAX-Launch-Report vom November 2023. Predibase benchmarkte Llama 2 7B mit Queries, die auf 1 bis 128 Adapter verteilt waren, auf einer NVIDIA A10G. Das Diagramm zeigt den Kostenvergleich für 1 bis 32 Adapter bei der Verarbeitung von einer Million Tokens, gleichmäßig auf die Adapter verteilt.

Archivierter Projektvergleich, reproduziert aus Predibase’ LoRAX-Report von 2023. Die Kosten für LoRAX und dedizierte Deployments basieren auf GPU-Stunden aus diesem Experiment. Auf dem Detaillierungsniveau der Quelle verwendet die GPT-3.5-Turbo-Linie die Kosten pro Token des Fine-Tuned Models.

Interpretieren Sie die flachen orangefarbenen Balken als Ergebnis dieses Benchmark-Designs, nicht als aktuelle Preiszusage. Der Test verarbeitete insgesamt eine Million Tokens und erlaubte verschiedenen Adaptern, sich einen Batch zu teilen. Beim Dedicated Baseline wurde separate gehostete Compute-Kapazität für jedes Model angenommen, daher stiegen die Kosten mit der Model-Anzahl.

Predibase legte folgende Benchmark-Inputs nicht offen:

  • Prompt-to-Output-Token-Mix
  • Request-Längen
  • Batch-Größe
  • Adapter-Rank
  • GPU-Stundenpreis
  • exaktes Utilization Model für dedizierte Deployments
  • exakte historische Input- und Output-Preise von GPT-3.5

Daher enthält der Report nicht genügend Informationen, um die dargestellten Dollarwerte unabhängig zu reproduzieren.

Das Diagramm deckt außerdem keinen Sparse Traffic, keine Cold Downloads, keine aktuellen Cloud-Preise, keine neueren GPUs, keine anderen Base Models und keine Adapter mit anderen Ranks ab. Es spricht für Workload Replay. Dieses kann es jedoch nicht ersetzen.

Wann LoRAX plausibel passt

LoRAX sollte benchmarked werden, wenn alle folgenden Bedingungen erfüllt sind:

  • Die Adapter wurden gegen dasselbe unterstützte Base Model und denselben Tokenizer Contract trainiert.
  • Der Traffic verteilt sich auf viele Adapter und weist einen relevanten Long Tail auf.
  • Das Laden eines Cold Adapters on demand ist dem Reservieren eines Deployments dafür vorzuziehen.
  • Tenant- oder Task-Routing existiert bereits an der Application Boundary.
  • Das Team kann eine spezialisierte Inference Runtime und ihr Cache-Verhalten betreiben.

Typische Fälle sind Tenant-spezifische Assistenten, viele Domain-Varianten und Online-Experimente, die einen Base Checkpoint gemeinsam nutzen.

LoRAX passt schlechter, wenn wenige Adapter den Großteil des Traffics übernehmen oder die Models kein Base Model gemeinsam haben. Ebenfalls schlechter passt es, wenn harte Latency-Ziele keine Cold Loads tolerieren oder die Platform nicht sicher kontrollieren kann, welche Artifacts der Server lädt. Ein standardmäßiges vLLM- oder TGI-Deployment mit einem festen Adapter-Set kann in diesen Fällen einfacher sein.

Verwenden Sie Kubernetes nicht allein deshalb, weil der Katalog groß ist. Beweisen Sie zuerst die Runtime- und Adapter-Kompatibilität auf einer GPU.

Lokal ein Base Model und zwei Adapter testen

Die LoRAX-README empfiehlt ihren vorgefertigten Container. Verwenden Sie in einer realen Umgebung einen unveränderlichen Image Digest. main wird hier nur verwendet, weil dies der dokumentierte Quick-Start-Tag des Repositorys ist. Diese Beispiele dienen der Illustration und wurden in diesem Checkout nicht lokal verifiziert. Prüfen Sie sie anhand der Image- und Dependency-Versionen, die Sie deployen.

mkdir -p data

docker run --rm --gpus all --shm-size 1g \
    -p 8080:80 \
    -v "$PWD/data:/data" \
    ghcr.io/predibase/lorax:main \
    --model-id mistralai/Mistral-7B-Instruct-v0.1

Die dokumentierten Mindestanforderungen sind Linux, Docker, eine NVIDIA-GPU der Ampere-Generation oder neuer und CUDA-11.8-kompatible Treiber. Model-Lizenzen und gated Repositories können außerdem ein Hugging Face Token erfordern.

Starten Sie mit dem Base Model:

curl http://127.0.0.1:8080/generate \
    -H 'Content-Type: application/json' \
    -d '{
      "inputs": "[INST] Give one reason to measure cold-adapter latency. [/INST]",
      "parameters": {"max_new_tokens": 64}
    }'

Senden Sie anschließend einen kompatiblen Adapter:

curl http://127.0.0.1:8080/generate \
    -H 'Content-Type: application/json' \
    -d '{
      "inputs": "[INST] Solve: Natalia sold 48 clips in April and half as many in May. What is the total? [/INST]",
      "parameters": {
        "max_new_tokens": 64,
        "adapter_id": "vineetsharma/qlora-adapter-Mistral-7B-Instruct-v0.1-gsm8k"
      }
    }'

Die erste Anfrage lädt und lädt den Adapter möglicherweise zunächst. Spätere Anfragen können gecachte Artifacts und residente Weights verwenden. Erfassen Sie beide Pfade. Eine einzelne Warm-Anfrage sagt wenig über Long-Tail-Verhalten aus.

Einen OpenAI-kompatiblen Client verwenden

LoRAX stellt einen OpenAI-kompatiblen Chat-Endpunkt bereit. Das Feld model identifiziert den Adapter:

from openai import OpenAI

client = OpenAI(
    api_key="EMPTY",
    base_url="http://127.0.0.1:8080/v1",
)

response = client.chat.completions.create(
    model="alignment-handbook/zephyr-7b-dpo-lora",
    messages=[
        {"role": "user", "content": "Explain cache locality in two sentences."},
    ],
    max_tokens=100,
)

print(response.choices[0].message.content)

Der Server benötigt standardmäßig keinen API Key. Das ist für Localhost praktisch, aber als Konfiguration mit Internet-Exposure unsicher. Schalten Sie Authentication, Tenant Authorization, Quotas und Adapter-Allowlisting davor.

Einen Compatibility Gate definieren

Prüfen Sie mindestens Folgendes, bevor ein Adapter in den Katalog aufgenommen wird:

  • deklariertes Base Model und Revision
  • Kompatibilität von Tokenizer und Chat Template
  • LoRA-Rank und vom Runtime unterstützte Target Modules
  • Artifact-Format und Tensor Shapes
  • Lizenz, Provenance und Integrity Digest
  • eine kleine Suite aus Behavioral- und Regression-Tests

Lehnen Sie inkompatible Artifacts bereits bei der Registrierung ab und nicht erst bei der ersten Anfrage eines Users.

Residency vor dem Deployment verstehen

Das Base Model belegt den größten festen Anteil des GPU-Speichers. Adapter Weights, KV cache, Batch Workspace und Runtime-Kernels konkurrieren um den verbleibenden Speicher. CPU-RAM kann ausgelagerte Adapter aufnehmen, während /data heruntergeladene Artifacts speichert.

Diese Tiers sind nicht austauschbar. Ein Disk- oder Hub-Artifact muss gelesen und materialisiert werden, bevor es zu einem CPU- oder GPU-residenten Adapter wird. Messen Sie die Übergänge getrennt:

PfadEnthaltene VorgängeZu erfassende Metrik
GPU HitAdapter bereits residentQueue Time und Time to First Token
CPU HitTransfer oder Rematerialisierung zur GPUAdapter-Load-Delay und End-to-End-Latency
Artifact HitLesen aus lokalem /data CacheRead-/Load-Delay und Cache-Bytes
Remote MissDownload sowie Validierung und LadenDownload-Zeit, Fehler und vollständige Cold-Latency

Die Kapazitätsplanung sollte die reale Adapter-Popularity-Distribution replayen. Gleichverteilte zufällige Adapter-IDs erzeugen ein anderes Cache-Problem als ein Zipf-artiger Tenant-Workload.

Das Repository-Chart sorgfältig deployen

Das Repository enthält charts/lorax. Daher ist ein gepinnter Repository-Stand zusammen mit einem lokalen Chart der reproduzierbare Ausgangspunkt:

git clone https://github.com/predibase/lorax.git
cd lorax
git checkout <reviewed-commit-or-release>

helm dependency update charts/lorax
helm template lorax charts/lorax -f values.production.yaml
helm upgrade --install lorax charts/lorax \
    --namespace inference \
    --create-namespace \
    -f values.production.yaml

Bei der Prüfung am 15. Juli 2026 zeigten die Chart Values und das Deployment Template Defaults, die Aufmerksamkeit verdienen:

  • Der Image Tag ist latest.
  • /data ist ein emptyDir, daher gehen heruntergeladene Artifacts beim Ersetzen des Pods verloren.
  • Liveness- und Readiness-Probes sind leer.
  • Das Hugging Face Token wird als Literal Environment Value modelliert.
  • Standardmäßig wird eine GPU angefordert.

Das Chart ist nützliches Scaffolding. Es ist keine Production Policy.

Mit der tatsächlichen Value-Struktur des Charts beginnen

Das Chart verschachtelt die Runtime-Konfiguration unter deployment; Launcher-Argumente sind eine Liste aus Name-/Value-Paaren. Ein minimales Overlay sieht so aus:

deployment:
    replicas: 1

    image:
        repository: ghcr.io/predibase/lorax
        tag: "<tested-tag>" # Prefer an immutable digest in rendered manifests.

    args:
        - name: "--model-id"
          value: "mistralai/Mistral-7B-Instruct-v0.1"
        - name: "--max-input-length"
          value: "2048"
        - name: "--max-total-tokens"
          value: "3072"
        - name: "--max-batch-total-tokens"
          value: "8192"
        - name: "--max-batch-prefill-tokens"
          value: "4096"

    resources:
        requests:
            nvidia.com/gpu: "1"
        limits:
            nvidia.com/gpu: "1"

    readinessProbe:
        httpGet:
            path: /health
            port: http
        periodSeconds: 5
        failureThreshold: 600

service:
    serviceType: ClusterIP
    port: 80

Die oben genannten Token-Limits sind beispielhafte Startwerte und keine Sizing-Empfehlungen. Leiten Sie sie aus repräsentativen Prompts, erwarteter Concurrency, GPU-Speicher und Load Tests ab.

Die Lücken explizit schließen

Das aktuelle Chart Template hardcodiert emptyDir Volumes und einfache Environment Values. Ein gehärtetes Deployment benötigt daher einen geprüften Chart Fork, einen Post-Render-Patch oder eine höher liegende Manifest-Schicht, um Folgendes hinzuzufügen:

  • einen PersistentVolumeClaim oder Node-lokalen Artifact Cache, gemountet unter /data
  • eine Secret-Referenz für Hub-Credentials
  • eine Startup Probe vor einer aggressiven Liveness Probe
  • Pod Disruption Policy und Topology Spread für mehrere Replicas
  • NetworkPolicy, Service-Account-Einschränkungen und ein authentifiziertes Gateway
  • Image-Digest-Pinning und Artifact-Integrity-Checks

Legen Sie ein Hub Token niemals direkt in einer versionierten Values-Datei ab. Zwei Replicas bieten nur dann nützliche High Availability, wenn beide das Base Model laden können. Der Router muss außerdem vermeiden, jeden Cold Adapter an beide Pods zu senden.

Für Cache Locality routen

Round-Robin-Balancing kann dazu führen, dass jede Replica zu einem Cold Cache wird. Ein nützlicher Router ordnet eine erlaubte Adapter-ID per Hash oder einer anderen stabilen Regel einer Replica zu. Für den Fall, dass diese Replica nicht verfügbar ist, bleibt ein Failover-Pfad bestehen.

Der Routing Key muss aus authentifiziertem Application State stammen und nicht aus einem beliebigen öffentlichen URL-Parameter. Andernfalls kann ein Caller Remote Downloads erzwingen, Caches in Bewegung versetzen oder private Adapter-Namen ausspähen.

LoRAX oder vLLM?

Die aktuelle vLLM-Dokumentation beschreibt LoRA-Module, die beim Startup deklariert werden, sowie dynamisches Laden über Endpoints oder Resolver Plugins. Sie warnt, dass Runtime Adapter Updating Sicherheitsrisiken birgt und außerhalb einer isolierten, vertrauenswürdigen Umgebung nicht in Production eingesetzt werden sollte.

Der sinnvolle Vergleich ist operativ und nicht numerisch:

FrageLoRAXvLLM
Wie werden Long-Tail-Adapter gefunden?Die Adapter-ID kann Hugging Face-, Predibase- oder Filesystem-Artifacts on request auflösen.Statische Module, dynamische Management-Endpoints oder Resolver Plugins
Wie wird Residency verwaltet?Explizites Adapter Exchange Scheduling zwischen GPU und CPUKonfigurierte Active- und CPU-LoRA-Limits plus Resolver-Verhalten
Welche Request-Schnittstelle gibt es?TGI-artiges /generate, Python Client und OpenAI-kompatibles ChatOpenAI-kompatibles Serving und native Python APIs
Was sollte entscheiden?Cold-/Warm-Latency, Cache Churn, Heterogeneous-Batch-Throughput und Operational FitDerselbe Workload Replay und dieselben operativen Kriterien

Vermeiden Sie Regeln wie „LoRAX für 1.000 Adapter, vLLM für zehn“. Die Catalog Size allein bestimmt die Performance nicht. Benchmarken Sie beide mit demselben Base Model, denselben Adaptern, Prompts, Ranks, Arrival Trace und derselben Hardware.

Ein Production-Acceptance-Test

Führen Sie vor einer Erweiterung des Katalogs ein Replay durch, das Folgendes umfasst:

  1. Ein fester Hot Set zur Ermittlung von Warm-Throughput und -Latency.
  2. Eine Long-Tail-Distribution zur Messung von CPU- und Artifact-Cache-Hits.
  3. Ein Burst bisher unbekannter, aber allowlisteter Adapter.
  4. Pod Replacement zur Messung der Recovery von Base Model und Adaptern.
  5. Ein nicht verfügbarer oder beschädigter Adapter zur Prüfung von Isolation und Fallback.
  6. Gleichzeitige Tenants zur Prüfung von Authentication, Quotas und Metric Labels.

Erfassen Sie diese Metriken:

  • Request Rate
  • Queue Time
  • Time to First Token
  • Inter-Token-Latency
  • Total Latency
  • Adapter Load Time
  • Cache-Hit-Klasse
  • GPU-Speicher
  • CPU-Speicher
  • Download-Bytes
  • Fehler nach Ursache

Nehmen Sie Adapter-IDs nicht in unbounded Metric Labels auf. Ordnen Sie sie kontrollierten Dimensionen oder gesampelten Traces zu.

Definieren Sie die Acceptance Thresholds vor dem Test. Legen Sie eine maximale Error Rate für den Cold Path und ein Warm-P99-Ziel fest. Definieren Sie außerdem ein Cache-Hit-Ziel für die beobachtete Popularity-Distribution sowie ein Recovery-Time-Objective nach einem Pod-Verlust.

Fazit

LoRAX macht aus vielen kompatiblen Fine-Tunes kein Fleet aus Kopien des Base Models, sondern ein Adapter-Placement-Problem. Das kann für Long-Tail-Workloads ein starkes Design sein, macht Kosten oder Latency jedoch nicht per Definition konstant. Der aktive Working Set, der Exchange Path, der Batch-Mix und die Storage-Schicht bestimmen weiterhin das Ergebnis.

Beweisen Sie diese Mechanismen zunächst auf einer GPU. Nehmen Sie Kubernetes anschließend ernst: Pinnen Sie Artifacts, erhalten Sie den Cache, schützen Sie Credentials, autorisieren Sie Adapter, routen Sie für Locality und messen Sie jeden Residency Path. Wenn LoRAX eine aktuelle vLLM-Konfiguration unter demselben Replay schlägt, ist die Deployment-Entscheidung durch Evidenz abgesichert.
