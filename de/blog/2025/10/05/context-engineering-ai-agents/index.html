Context Engineering für AI Agents: Memory und Tools

Viacheslav Dubrov

2025-10-05 · Aktualisiert 2026-08-16 · 15 Min. · KI-Agenten

Automatische Übersetzung Dieser Artikel wurde automatisch aus der englischen Originalversion übersetzt.

Context Engineering ist die Pipeline, die vor jeder Entscheidung auswählt, was ein Model sieht: Instructions, Examples, Knowledge, Memory, Tool Definitions, Observations und Guardrails. Ein Agent handelt nicht auf Basis all dessen, was das System weiß. Er handelt auf Basis der Working Set, die für den nächsten Model Call zusammengestellt wird.

Bei dieser Auswahl beginnen viele Fehler. Eine veraltete Preference wirkt aktuell. Abgerufener Text enthält eine Instruction. Ein langes Tool Result verbirgt die fehlgeschlagene Precondition. Eine Summary erinnert sich an die Entscheidung, verliert aber die Information darüber, welche Datei geändert wurde.

Die praktische Aufgabe besteht darin, für jede Entscheidung die kleinste ausreichende Working Set zusammenzustellen und dabei Scope, Provenance und Permissions zu bewahren. Dieser Artikel beschreibt die Patterns, die ich verwende, sowie die Grenzen, die sie belastbar halten.

Der Artikel richtet sich an Engineers, die AI Agents, Retrieval-Systeme und Anwendungen mit Tool Use entwickeln oder betreiben.

Sie werden in der Lage sein, eine Context Pipeline pro Entscheidung zu entwerfen, ihre Trust Boundaries zu identifizieren und zu evaluieren, ob ihre Working Set die jeweilige Aufgabe unterstützt.

TL;DR. Behandeln Sie Context als typisiertes Runtime-Artefakt mit Provenance. Wählen Sie ihn pro Schritt aus, erzwingen Sie Tenant- und Permission-Scope vor dem Retrieval und trennen Sie vertrauenswürdige Instructions von nicht vertrauenswürdigen Daten. Planen Sie Budgets nach Utility, validieren Sie Actions außerhalb des Models und evaluieren Sie Task Outcomes statt allein die Context Length.

Context ist ein Decision Input, nicht Memory

Das Context Window ist der aktuelle Input des Models einschließlich der generierten Tokens. Es kann Conversation Turns enthalten, ist aber kein dauerhaftes Memory-System. Long-Term Memory, Document Indexes, Datenbanken und Artifact Stores liegen außerhalb des Windows. Eine Context Pipeline entscheidet, was hineinkopiert wird.

Die Window Size ist eine Kapazitätsgrenze, keine Qualitätsgarantie. Lost in the Middle und RULER zeigen, dass Retrieval und Reasoning von Position, Task, Model und Sequence Length abhängen können. Die operative Schlussfolgerung lautet nicht, dass mittlere Tokens immer ignoriert werden. Vielmehr können zusätzliche, relevant wirkende Tokens die Task Performance trotzdem reduzieren.

Das Diagramm zeigt das qualitative Ergebnis der Studie, keine universelle Attention Curve. Liu et al. untersuchten Multi-Document Question Answering und Key-Value Retrieval. Häufig beobachteten sie eine bessere Performance, wenn sich das relevante Item am Anfang oder Ende befand. Größe und Form des Effekts variierten je nach Model, Task und Context Length. Testen Sie die Position als Variable in Ihrem eigenen Eval Set, statt eine feste Middle Penalty anzunehmen.

Das Folgende ist ein illustratives Pydantic Schema und keine getestete Repository-Implementierung. Es validiert ausschließlich Feldtypen und Literal Values. Es autorisiert weder den Tenant, hält total_input_tokens konsistent mit items, persistiert das Manifest noch erzwingt es das Verhalten des Models.

from datetime import datetime
from typing import Literal

from pydantic import BaseModel

class ContextItem(BaseModel):
    item_id: str
    kind: Literal["instruction", "task_state", "evidence", "memory", "tool"]
    source: str
    trust: Literal["trusted", "untrusted"]
    retrieved_at: datetime | None = None
    version: str | None = None
    token_count: int

class ContextManifest(BaseModel):
    request_id: str
    tenant_id: str
    items: list[ContextItem]
    total_input_tokens: int

Das Manifest macht einen Fehler reproduzierbar. Aus „Das Model hat halluziniert“ wird eine testbare Frage: Welche Evidence, welche Version, welcher Permission Scope und welches Tool Schema wurden tatsächlich übergeben?

Der Assembly Lifecycle

Eine zuverlässige Pipeline führt diese Operationen in der folgenden Reihenfolge aus:

  1. Trusted Request Context auflösen. Authentifizieren Sie Actor, Tenant, Locale, Zeit und aktuellen Task State außerhalb des Models.
  2. Die nächste Entscheidung auswählen. Ein Planning-Schritt, eine Evidence Lookup, eine Tool Selection und eine Final Response benötigen unterschiedlichen Context.
  3. Innerhalb des Scopes retrieven. Wenden Sie Authorization- und Tenant-Filter vor dem Semantic Ranking an, nicht erst, nachdem Dokumente in die Candidate Set gelangt sind.
  4. Rangfolge und Budget festlegen. Wählen Sie Items anhand von Utility, Freshness, Authority und Diversity innerhalb eines Input Budgets aus.
  5. Mit Trust Boundaries assemblieren. Halten Sie Policy in Instruction Channels und zitieren Sie abgerufene Inhalte als Daten. Abgerufene Instructions werden nicht zur System Policy.
  6. Ein typisiertes Proposal generieren. Constrained Decoding kann unterstützte Syntax und Shape erzwingen. Es kann Values nicht korrekt machen.
  7. Validieren und ausführen. Application Code prüft Authorization, Business Rules, Tool Arguments und Postconditions.
  8. Provenance und Outcome speichern. Speichern Sie das Manifest, die ausgewählten Source IDs, Referenzen auf Tool Results, das Validation Result und das Task Outcome.

Der Lifecycle gilt pro Entscheidung. Das Wiederverwenden eines großen Contexts für einen gesamten Agent Run erzeugt veraltete Evidence und gibt jedem Schritt Zugriff auf Material, das er nicht benötigt.

Jede Context Source erhält genau eine Aufgabe

Instructions definieren dauerhaftes Verhalten

Instructions legen Role, Policy, Output Contract und Escalation Behavior fest. Halten Sie stabile Inhalte stabil, um Prefix Caching zu verbessern, frieren Sie jedoch keine Values ein, die sich zur Runtime ändern. Ein Refund Threshold gehört in einen Policy Service oder einen versionierten Data Record, nicht dauerhaft in einen Prompt kopiert.

Die Instruction Hierarchy ist eine Control Boundary, kein Security Sandbox. Ein Model kann weiterhin bösartigen Text in einem abgerufenen Dokument befolgen. Begrenzen Sie nicht vertrauenswürdige Inhalte, kennzeichnen Sie sie als Evidence statt als Instruction, beschränken Sie Tools unabhängig davon und testen Sie Prompt-Injection-Fälle.

Übertragen Sie die Role Names eines Providers nicht in eine universelle Hierarchy. Die OpenAI Model Spec definiert Authority Levels für Platform- oder System-, Developer- und User-Instructions. Die Anthropic Messages API verwendet einen Top-Level-Parameter system sowie user- und assistant-Messages. Sie stellt in dieser API keine entsprechende developer-Role bereit. Andere Runtimes treffen andere Entscheidungen. Ordnen Sie Ihre Policy den dokumentierten Channels des Providers zu und erzwingen Sie Permissions und Side Effects anschließend in Application Code.

Task State hält Commitments fest

Conversation Prose ist keine zuverlässige Source of Truth für Multi-Step Work. Halten Sie Objective, aktuelle Phase, abgeschlossene Actions, ausstehende Approvals, Artifact References und Test Status explizit fest. Das Model kann diesen State für die Narration zusammenfassen. Application Code besitzt die kanonische Version.

Examples zeigen Edge Decisions

Few-Shot Examples sind nützlich, wenn sie eine schwierige Boundary klären, nicht wenn sie lediglich das Schema wiederholen. Wählen Sie Examples, die zur aktuellen Entscheidung passen und relevante Edge Cases enthalten. Evaluieren Sie Example Retrieval wie Document Retrieval: Ein oberflächlich ähnliches, aber Policy-inkompatibles Example kann schlechter sein als gar keines.

Knowledge liefert Evidence

Retrieval eignet sich für aktuelle, private oder zitierfähige Fakten. Es gibt kein universell bestes top_k, keine universell beste Chunk Size, Hybrid Weight oder Reranker Cutoff. Tunen Sie den gesamten Pfad anhand von Questions mit bekannter unterstützender Evidence.

Ein nützliches Evidence Item enthält:

  • Source und stabile Document ID
  • Version oder Effective Date
  • Permission Scope
  • zitierter Span und Location
  • Retrieval- und Reranking Scores für das Debugging

Fordern Sie das Model nicht auf, eine URL zu zitieren, die es nie erhalten hat. Loggen Sie keine vollständigen privaten Dokumente allein zum Debuggen der Auswahl.

Memory liefert gescopte Continuity

Memory ist Retrieved Data mit zusätzlichen Lifecycle-Risiken. Als Design Metadata sollten Sie Subject, Provenance, Purpose, die anwendbare Consent- oder Legal-Basis-Entscheidung, Creation Time, Expiry- oder Review Policy sowie den Deletion Path erfassen. Das geltende Datenschutzrecht und Product Counsel bestimmen die Legal Basis eines Products und seiner Daten, nicht diese Checkliste.

Feste Regeln wie „Preferences bleiben 365 Tage erhalten“ sind keine portable Policy. Retention richtet sich nach Product Need, User Expectation und geltendem Recht. Prüfen Sie vor dem Laden eines Memory:

  1. Gehört es zu diesem authentifizierten Subject und Tenant?
  2. Ist sein Purpose für diese Entscheidung relevant?
  3. Ist es aktuell genug für die Verwendung?
  4. Ist seine Source authoritative oder lediglich vom Model inferred?

Behandeln Sie inferred Memories als Hypothesen. Machen Sie aus einer einzelnen Model Response nicht stillschweigend einen dauerhaften User Fact.

Tool Contracts legen Capabilities offen

Tool Descriptions sollten Preconditions, Effects, Authorization Scope, Input Schema, Output Schema, Idempotency und aussagekräftige Failures erklären. Ein Schema-valid Tool Call kann dennoch unauthorized oder unsafe sein.

Ersetzen Sie nach der Execution ein ausführliches Raw Output durch eine typisierte Observation, die das für die Entscheidung relevante Resultat sowie eine Referenz auf das vollständige Artifact bewahrt:

{
    "tool": "check_api_key_status",
    "status": "revoked",
    "checked_at": "2026-07-15T09:30:00Z",
    "account_id": "A-123",
    "artifact_ref": "toolrun://req-42/step-3"
}

Die MCP Specification standardisiert, wie Clients mit Tools, Resources und Prompts interagieren. Sie autorisiert deren Verwendung nicht und macht zurückgegebene Inhalte nicht vertrauenswürdig. Halten Sie Gateway-, Credential- und Policy Checks außerhalb des Models und der Protocol Description.

Laden Sie Details, wenn eine Entscheidung sie benötigt

Progressive Disclosure ist ein Pattern für die Context Assembly: Halten Sie IDs und vertrauenswürdigen Task State verfügbar und laden Sie Details für die aktuelle Entscheidung nach. Es ist keine Zusage, dass ein bestimmtes Token Budget für jedes Model funktioniert.

Der Router muss Authorization und Tenant Scope vor dem Retrieval anwenden. Er sollte Evidence Spans, Memory Records und Tool Schemas zurückgeben, die der aktuellen Entscheidung dienen. Das Model schlägt anschließend eine Action vor. Application Code validiert dieses Proposal vor der Execution. Anthropic verwendet in seiner Tool-Context Guidance dasselbe selektive Prinzip für große Toolsets. Tool Search hält Definitions außerhalb des Context Windows, bis das Model sie anfordert. Messen Sie in Ihrem System, ob der zusätzliche Routing-Schritt Task Success, Latency und Tokens pro erfolgreichem Task verbessert.

Wie Context degradiert

Byte says

Ich gab einem fehlschlagenden Agenten ein größeres Kontextfenster und einen Reranker. Er antwortete weiterhin aus dem überholten Richtliniendokument, nur schneller und überzeugter. Nichts in der Pipeline hatte dieses Dokument außer Kraft gesetzt.

Schlechter Context schlägt nicht nur auf eine Weise fehl. Das folgende Degradation Model mit fünf Patterns ist meine Synthese für das Debugging, beeinflusst durch die oben genannten Long-Context-Evals und die Forschung zu Prompt Injection:

  • Position Loss: Die erforderliche Evidence ist vorhanden, aber das Model verwendet sie aufgrund ihrer Position und der umgebenden Sequence inkonsistent. Long-Context-Evals zeigen, dass der Effekt je nach Model und Task variiert. Es gibt keinen universellen „schlechten mittleren“ Bereich.
  • Poisoning: Ein falsches Memory, ein veraltetes Dokument, eine bösartige Instruction oder eine fehlerhafte Tool Observation gelangt in die Working Set und beeinflusst spätere Entscheidungen.
  • Distraction: Relevante Evidence konkurriert mit Material, das aktuell oder semantisch ähnlich, für den aktuellen Schritt aber unnötig ist.
  • Confusion: Überlappende Instructions, Examples oder Tool Descriptions lassen mehrere plausible Interpretationen des Tasks zu.
  • Clash: Zwei Items, die authoritative wirken, widersprechen sich bei einem Value, einer Policy oder der nächsten Action, und der Assembler legt weder ihre Versions noch ihre Precedence offen.

Diese Failures erfordern unterschiedliche Fixes. Besseres Ranking kann bei Distraction helfen, aber keine veraltete Source reparieren. Delimiters können die Trennung von Daten und Instructions unterstützen, aber kein Tool autorisieren. Ein größeres Context Window kann mehr widersprüchliches Material bewahren, ohne den Konflikt zu lösen.

Wenn ein Run fehlschlägt, untersuchen Sie das Manifest und fragen Sie zunächst, welches Pattern aufgetreten ist, bevor Sie den Prompt ändern oder eine weitere Retrieval Stage hinzufügen.

Budgetierung nach Utility statt nach Component Quotas

Ein Context Budget reserviert zunächst Platz für das Output und weist den verbleibenden Input der aktuellen Entscheidung zu. Gehen Sie vom unterstützten Window des Models aus, ziehen Sie maximales Output und Protocol Overhead ab und packen Sie die Candidates in den verbleibenden Raum.

Bewerten Sie Candidates mit Features, die Ihre Evals herausfordern können:

utility = relevance × authority × freshness × scope_match
          − redundancy_penalty − injection_risk

Betrachten Sie die Formel als Design Prompt. In einer Policy-Antwort kann Authority die Semantic Similarity dominieren. Beim Debugging kann ein aktueller fehlerhafter Log allgemeine Documentation übertreffen.

Auch die Reihenfolge ist relevant. Halten Sie stabile vertrauenswürdige Instructions an erster Stelle, wenn die Cache Semantics des Providers von einem gemeinsamen Prefix profitieren. Platzieren Sie den aktuellen Task und die Entscheidung nahe bei der Evidence, auf die sie sich beziehen. Vermeiden Sie Timestamps oder Request IDs in stabilen Prefixes, wenn sie dort nicht benötigt werden.

Komprimieren ohne State-Verlust

Compression ist verlustbehaftet, sofern das Original nicht adressierbar bleibt. Die Evaluation von Factory Research zu drei Compression-Ansätzen über lang laufende Agent Sessions formuliert das Ziel als Tokens pro Task, nicht Tokens pro Request. Ich leite daraus eine Engineering-Empfehlung ab: Optimieren Sie Tokens pro erfolgreichem Task, nicht Tokens pro Request, unter vergleichbaren Task-Bedingungen – nicht als universelles Gesetz. Factory Research Evaluation

Verwenden Sie getrennte Mechanismen für unterschiedliche Materialien:

  • Conversation: Fassen Sie Decisions, ungelöste Fragen und Commitments zusammen.
  • Tool Observations: Bewahren Sie typisierte Findings und Artifact References. Entfernen Sie Boilerplate und wiederholte Payloads.
  • Retrieved Evidence: Bewahren Sie Source IDs, Supporting Spans und Effective Dates, damit das System sie erneut abrufen kann.
  • Task State: Speichern Sie ihn kanonisch außerhalb der Summary.
  • File- oder Artifact Trail: Führen Sie einen expliziten Index der Reads, Writes, Hashes und Test Results.

Lösen Sie Compaction anhand gemessener Degradation oder eines Budget Thresholds aus, der für Model und Task gewählt wurde. Veröffentlichen Sie keine allgemeine Regel wie „bei 70 % komprimieren“, als würden alle Models am selben Punkt ausfallen.

Evaluieren Sie Compression mit Probes, die eine Fortsetzung erfordern, nicht mit Lexical Overlap:

  • Was ist das aktuelle Objective und die nächste Action?
  • Welche Files oder Records wurden geändert?
  • Welche Decision wurde abgelehnt und warum?
  • Welche Source unterstützt die aktuelle Claim?
  • Welche Approval steht noch aus?

Führen Sie denselben Task mit und ohne Compression aus. Vergleichen Sie Success, Incorrect Actions, Re-Fetches, Latency und die Gesamtzahl der Tokens.

Prompt Caching kann die Kosten wiederholter Prefixes senken, reduziert aber nicht die Anzahl der Tokens im Context Window. Abgeschlossene History komprimieren

Ersetzen Sie alte Conversation Turns durch einen strukturierten Handoff, der Decisions, ungelöste Fragen, geänderte Artifacts und Test State festhält. Halten Sie das ursprüngliche Transcript oder die Artifacts adressierbar, wenn Review oder Recovery dies erfordern.

Ausführliche Observations maskieren

Ein Tool kann seitenweise Logs zurückgeben, obwohl der nächste Schritt nur Status, Error Code und Artifact Reference benötigt. Konvertieren Sie das Raw Result nach der Validation in eine typisierte Observation und halten Sie die vollständige Payload außerhalb des Prompts. Lassen Sie das Model nicht die einzige Failure-Evidence wegzusammenfassen.

Cachebare Prefixes bewahren

Provider und Runtimes können Arbeit wiederverwenden, wenn der Anfang eines Requests stabil bleibt. Halten Sie dauerhafte Instructions und Tool Schemas in einer konsistenten Reihenfolge und verschieben Sie Timestamps, Request IDs, Retrieved Evidence und den aktuellen State in den dynamischen Suffix. Prüfen Sie die Cache Semantics des Providers, bevor Sie Ihre Architektur darauf ausrichten.

Nach Decision partitionieren

Ein Planner, Retriever, Tool Caller und Final-Answer-Schritt benötigen nicht dasselbe Material. Geben Sie jedem Schritt nur die vertrauenswürdigen Instructions, den State, die Evidence und die Tools, die er benötigt. Partitioning reduziert gleichzeitig den Token-Verbrauch und die Capability Exposure; ob notwendige Informationen entfernt wurden, können jedoch nur Task-Level Evals zeigen.

Die Context Supply Chain absichern

Die Prompt-Injection-Forschung betrachtet nicht vertrauenswürdige externe Inhalte als Attack Surface (Paper). Im operativen Model dieses Artikels kann Context Poisoning über Documents, Memories, Tool Results, Skills oder frühere Assistant Messages eintreffen. Text als „untrusted“ zu markieren hilft dem Model, aber Enforcement muss architektonisch erfolgen.

Die folgende Supply-Chain-Checkliste ist meine Engineering-Empfehlung. Sie überführt Protocol- und Threat-Model-Boundaries in Application Controls. Weder die MCP Specification noch das Prompt-Injection-Paper erzwingen diese vollständige Checkliste.

Verwenden Sie diese Boundaries:

  1. Autorisieren Sie vor Retrieval und Tool Execution.
  2. Trennen Sie Daten von Instruction Channels und delimitieren Sie externe Texte.
  3. Erlauben Sie Tools pro Schritt und Actor per Allowlist. Side-Effect-Capabilities sind standardmäßig deaktiviert.
  4. Validieren Sie Resource Identifiers, statt dem Model das Erfinden von Tenant Keys oder File Paths zu überlassen.
  5. Verlangen Sie für Operationen mit hoher Auswirkung eine Confirmation auf Basis der Policy, nicht des Model Confidence.
  6. Scannen und prüfen Sie ausführbare Skills oder Connectors vor der Installation.
  7. Verhindern Sie, dass Secrets und Raw Sensitive Context in Logs und Long-Term Memory gelangen.

Automatisches „Repair“ ist nur für Änderungen angemessen, die die Bedeutung bewahren, etwa das Parsen eines bekannten Date Formats. Fehlende Tool Arguments mit „sinnvollen Defaults“ zu füllen, kann die Operation verändern. Fordern Sie bei unsicherer Bedeutung eine Clarification an oder lehnen Sie ab.

Worked Example: eine API-Key-Supportanfrage

Bei „Warum funktioniert mein API Key nicht?“ ist die nächste Entscheidung das Sammeln diagnostischer Evidence, nicht die Generierung der Final Answer. Der Assembler könnte Folgendes aufnehmen:

  • Trusted Support Policy und Response Contract
  • authentifizierte Account ID und Plan aus dem Application State
  • das aktuelle Ticket Objective und bereits versuchte Actions
  • zwei aktuelle Runbook Spans innerhalb des Product- und Version-Scopes
  • ein gescoptes Memory, dass der Key vor drei Tagen erstellt wurde, einschließlich Provenance
  • check_api_key_status und search_incidents, jedoch keine Tools zum Löschen oder Rotieren des Keys

Das Model schlägt einen Read-Only Status Check vor. Application Code autorisiert den Account, ruft das Tool auf und speichert eine typisierte Observation. Ein zweiter Model Call erhält die relevanten Runbook Spans zusammen mit dieser Observation. Die Final Response zitiert die Runbook Version, gibt den Key niemals aus und bietet Rotation nur als separat autorisierte Action an.

Nicht enthalten bleiben: irrelevante Ticket History, sämtliche Support Examples, Raw Account Dumps, Mutation Tools und Memories anderer Tenants.

Anti-Patterns explizit testen

  • Das Window vollpacken: Alle Retrieved Documents, History, Memories und Tools laden, nur weil noch Capacity vorhanden ist.
  • RAG überall: Semantic Retrieval für Values verwenden, die in eine Datenbank, einen Policy Service oder den authentifizierten Application State gehören.
  • Unbounded Memory: Inferred Facts ohne Scope, Expiry, Correction oder Deletion Semantics behalten.
  • Ein Call für jede Stage: Einen Prompt auffordern, zu retrieven, zu reasonen, zu autorisieren, zu mutieren und zu erklären, ohne beobachtbare Boundaries.
  • Schema gleich Correctness: Gültiges JSON als Beweis behandeln, dass Values, Permissions oder Business Decisions korrekt sind.
  • Keine Component Evals: Nur die Final Prose bewerten und Retrieval-, Context-Selection- oder Tool-Failures übersehen.

Machen Sie aus jedem Anti-Pattern ein Counterexample im Eval Set. Eine Guideline, die von keinem Task oder Trace ausgeübt wird, lässt sich leicht verletzen, ohne dass es auffällt.

Den Assembler evaluieren, nicht nur die Antwort

Erstellen Sie ein festes Task Set mit Evidence Labels, Permission Boundaries, erforderlichen Tool Calls und verbotenen Actions. Messen Sie für jede Änderung an der Context Policy:

DimensionFrage
Task SuccessHat der Agent das User Goal korrekt abgeschlossen?
Evidence RecallEnthielt die Working Set die notwendigen Sources?
Context PrecisionWie viel des enthaltenen Materials war tatsächlich nützlich?
FreshnessWurde die anwendbare Version ausgewählt?
IsolationGelangte ein Cross-Tenant- oder nicht autorisiertes Item in Candidates oder Context?
Action SafetyWaren Arguments, Authorization und Postconditions gültig?
EfficiencyWie hoch waren Latency und die Gesamtzahl der Tokens pro erfolgreichem Task?
RecoverabilityKonnte ein Reviewer die Entscheidung anhand der Provenance rekonstruieren?

Verwenden Sie Ablations, um den kausalen Nutzen zu ermitteln: Entfernen Sie Memory, Reranking, Examples oder Compression jeweils einzeln. Eine Component, die Tokens hinzufügt, ohne den relevanten Slice zu verbessern, sollte nicht standardmäßig geladen werden.

Fazit

Gutes Context Engineering ist selektiv und nachvollziehbar. Es füllt kein großes Window, nur weil Capacity verfügbar ist. Stattdessen konstruiert es eine auf den jeweiligen Schritt zugeschnittene Working Set aus vertrauenswürdigen Instructions, kanonischem Task State, gescopter Evidence, geprüftem Memory und erlaubten Tools.

Der Loop ist kurz: assemblieren, Manifest erstellen, Proposal generieren, validieren, ausführen und evaluieren. Wenn eine Entscheidung fehlschlägt, zeigt dieser Loop, ob Evidence, Freshness, Authority, State oder Policy gefehlt haben. Zugleich liefert er einen Test für die nächste Änderung.
