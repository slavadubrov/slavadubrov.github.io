Domain-Driven Design für AI Agents: Kontexte und Regeln

Agent-Projekte lassen sich nur schwer ändern, wenn Prompts, Code und Geschäftsprozesse unterschiedliche Begriffe verwenden. Die Compliance-Abteilung fordert einen „Policy Check“, während die Implementierung process_data() bereitstellt. Der vage Name verschleiert, welche Regel angewendet wird, wer dafür verantwortlich ist und wo eine Änderung hingehört.

Domain-Driven Design (DDD) stellt diese Geschäftssprache und die Verantwortlichkeiten in den Mittelpunkt. Bei einem Agent kann das Model eine Anfrage interpretieren und einen typisierten Befehl vorschlagen. Ein Application Service stellt anschließend vertrauenswürdigen Kontext bereit, und das Domain Model akzeptiert oder verwirft die Zustandsänderung. Dieser Leitfaden verknüpft die Arbeit an Vokabular und Grenzen mit diesem Ausführungspfad.

Dieser Leitfaden richtet sich an Engineers, die Agents bauen, welche Geschäftsstatus ändern und explizite Verantwortlichkeiten für Domain-Regeln benötigen. Sie lernen, wie sich ein Model-Vorschlag auf einen autorisierten Application Command abbilden lässt und an welcher Stelle der illustrative Ablauf noch eine konkrete Transaktionsimplementierung erfordert.

TL;DR. Verwenden Sie DDD, wenn ein Agent Geschäftsstatus in einer Domain mit bedeutungsvoller Sprache, klaren Verantwortlichkeiten und Regeln ändert. Ein Schema validiert die Struktur eines Model-Vorschlags; die Domain setzt dessen Bedeutung durch. Setzen Sie Agents nicht mit Bounded Contexts gleich, und betrachten Sie generiertes JSON nicht als gültige Geschäftsentscheidung.

Regelverantwortung ist das Problem

Agent-Systeme verteilen eine einzelne Regel häufig über einen System Prompt, eine Tool Description, einen API Handler und eine Datenbank-Constraint. Die Kopien driften auseinander. Ein Refund-Limit wird geändert, ein Prompt bleibt veraltet, und ein syntaktisch gültiger Tool Call erreicht die falsche Policy.

DDD beginnt mit anderen Fragen:

  • Welches Team ist für die Regel verantwortlich?
  • Welche Sprache verwenden Domain-Experten dafür?
  • Innerhalb welcher Grenze hat dieser Begriff genau eine Bedeutung?
  • Welche Zustandsänderungen müssen gemeinsam konsistent bleiben?

Diese Fragen sind hilfreich, wenn ein Workflow wichtig genug ist, um Policies und einen Lifecycle zu besitzen. Ein einfacher schreibgeschützter Chatbot benötigt möglicherweise keine Aggregates, Repositories und Events. Verwenden Sie DDD, um Domain-Komplexität zu beherrschen, nicht um jeden LLM Call damit auszustatten.

Strategisches Design vor dem Code

Eine Ubiquitous Language aufbauen

Eine Ubiquitous Language ist ein Vokabular, das Domain-Experten und Developers innerhalb eines Bounded Contexts gemeinsam verwenden. Wenn der Support-Betrieb RefundRequest, approval limit und settlement sagt, sollten diese Begriffe in Requirements, Code, Tool Contracts und Evals vorkommen.

Das bedeutet mehr, als beschreibende Methodennamen auszuwählen. Begriffe benötigen Definitionen und Beispiele. Bedeutet „approved“, dass ein Manager auf eine Schaltfläche geklickt hat, dass der Payment Processor die Überweisung akzeptiert hat oder beides? Eine in einem Glossar entdeckte Mehrdeutigkeit ist günstiger als eine in einem Agent Trace entdeckte.

Bounded Contexts um Models und Verantwortlichkeiten ziehen

Dasselbe Substantiv kann in unterschiedlichen Kontexten verschiedene Bedeutungen haben. „Product“ kann in Inventory eine Stock-Keeping Unit, in Billing eine bepreiste Position und in Order Management eine Lieferzusage sein.

Fowler beschreibt diese Trennung als Möglichkeit, zu verhindern, dass sich ein Model über jede Bedeutung eines Begriffs erstreckt (Bounded Contexts). Ein Bounded Context ist nicht automatisch ein Microservice, Repository, Agent oder Team, auch wenn diese Grenzen häufig übereinstimmen.

Diese Unterscheidung ist beim Agent-Design wichtig:

  • Ein Context kann intern mehrere Model Calls oder spezialisierte Agents verwenden.
  • Ein Agent, der mehrere Contexts umfasst, benötigt für jeden davon explizite Übersetzungen und Autorität.
  • Orchestration ist eine Angelegenheit der Application; sie hebt Domain-Verantwortlichkeiten nicht auf.

Beginnen Sie mit einer Context Map, bevor Sie einen Agent-Graphen zeichnen. Andernfalls bildet der Graph eher die Verfügbarkeit von Tools als die Geschäftsstruktur ab.

Subdomains klassifizieren

DDD unterscheidet üblicherweise:

  • Core Domain: die Fähigkeit, die einen differenzierten Wert schafft
  • Supporting Subdomain: notwendige, geschäftsspezifische Arbeit, die nicht das Differenzierungsmerkmal ist
  • Generic Subdomain: eine gelöste Fähigkeit wie Identity oder E-Mail-Zustellung

Bei einem Task Assistant kann Task Management die Core Domain, Scheduling eine Supporting Subdomain und Notification Delivery eine Generic Subdomain sein.

Diese Klassifizierung lenkt Investitionen. Sie bedeutet nicht, dass jede Box ein LLM benötigt.

Taktische Patterns definieren die Zustandsgrenze

Entities und Value Objects

Eine Entity besitzt eine Identity und einen Lifecycle. Eine Task bleibt dieselbe Task, auch wenn sich ihre Beschreibung ändert. Ein Value Object wird durch seine Werte definiert und ist normalerweise immutable: eine E-Mail-Adresse, ein Geldbetrag oder ein Zeitfenster.

Aggregates und Invariants

Ein Aggregate ist eine Consistency Boundary in DDD (Evans, Domain-Driven Design Reference). Sein Root stellt die Operationen bereit, die Members ändern können, und schützt Invariants wie:

  • Eine abgeschlossene Task kann nicht erneut abgeschlossen werden.
  • Ein Owner kann nicht für denselben Tag doppelte offene Reminders besitzen.
  • Ein Refund darf den verbleibenden erstattbaren Betrag nicht überschreiten.

Ein Aggregate wird nicht allein dadurch sicher, dass hinter einer add_task()-Methode eine Python-Liste liegt. Externer Code darf keine mutable Referenz erhalten, die diese Methode umgeht. Auch die Persistence benötigt Concurrency Control, da zwei gültige Requests beim gleichzeitigen Speichern ein Invariant verletzen können.

Repositories und Application Services

Ein Repository lädt und speichert Aggregates, ohne Datenbankbelange in die Domain durchsickern zu lassen (Fowler, Repository). Ein Application Service koordiniert einen Use Case: State laden, die Domain-Operation aufrufen, mit einer erwarteten Version speichern und daraus resultierende Events veröffentlichen.

Die Domain sollte kein LLM, keinen HTTP Client und kein ORM aufrufen. Das sind Adapter um den Use Case herum.

Domain Events sind Fakten, kein Message Bus

TaskAdded ist ein in der Vergangenheit liegender Fakt, den die Domain auslöst. Die Application kann ihn zusammen mit dem Aggregate-Update in einem Outbox speichern und nach dem Commit als Integration Event veröffentlichen. Das ist das Transactional-Outbox-Pattern und keine Garantie, die das Event Object selbst bereitstellt (Richardson, Transactional Outbox). Wenn eine Entity direkt an einen Broker sendet, besteht das Risiko, dass ein Event für eine später fehlschlagende Transaktion veröffentlicht wird.

Events können Agents koordinieren, machen die Koordination aber nicht von selbst zuverlässig. Delivery Semantics, Idempotenz, Ordering und versionierte Contracts bleiben Infrastrukturarbeit.

Model-Output als nicht vertrauenswürdigen Vorschlag behandeln

Eine LLM-Integration ähnelt einer Anti-Corruption Layer: Sie übersetzt eine externe, probabilistische Repräsentation in Begriffe, die die Domain versteht. Die Analogie ist sinnvoll, solange Validation und Policy getrennt bleiben.

Die Boundary umfasst vier Schritte:

  1. Constrain und parsen: einen typisierten Output Contract verlangen.
  2. Normalisieren: Dates, Units, Identifiers und Locale mithilfe vertrauenswürdigen Kontexts auflösen.
  3. Autorisieren: entscheiden, ob dieser Actor die Operation anfordern darf.
  4. Ausführen: eine Aggregate-Methode aufrufen, die das Invariant durchsetzt.

Pydantic kann ein fehlendes Feld oder einen ungültigen Enum-Wert über sein Typed-Validation-Model ablehnen (Pydantic documentation). Es kann jedoch nicht entscheiden, ob „morgen“ auf das richtige Datum verweist, ob der User die Task List besitzt oder ob bereits eine ähnliche Task offen ist.

Illustrativer Ablauf: eine Task hinzufügen

Die folgenden Fragmente zeigen einen Request, kein vollständiges Modul. Der Actor ist actor_id, der Zielzustand ist das TaskList des Owners, und der Domain-Side-Effect ist ein TaskAdded Event. Der Tool- oder Model-Adapter stellt AddTaskProposal bereit; der Application Service autorisiert den Actor, ändert das Aggregate und ist für die Persistence Boundary verantwortlich. TaskAdded, TaskAuthorizer und Outbox sind ausgelassene Types. Keine begleitende Implementierung oder kein Test in diesem Repository macht diese Fragmente ausführbar.

1. Den Model-seitigen Vorschlag definieren

Halten Sie den Vorschlag nahe an dem, was das Model ableiten kann. Lassen Sie es keine Database IDs oder vertrauenswürdigen Owner Identifiers erfinden.

from datetime import date
from typing import Literal

from pydantic import BaseModel, Field


class AddTaskProposal(BaseModel):
    description: str = Field(min_length=1, max_length=200)
    due_date: date | None = None
    priority: Literal["low", "normal", "high"] = "normal"

Wenn der User „morgen“ sagt, sollte die Application dem Model ein explizites lokales Datum geben oder den relativen Ausdruck mit einem getesteten Date Parser auflösen. Verwenden Sie niemals die Uhr des Inference Servers als impliziten Business Context.

2. Das Invariant in das Aggregate legen

from dataclasses import dataclass, field
from datetime import date
from uuid import UUID, uuid4


@dataclass(frozen=True)
class Task:
    task_id: UUID
    description: str
    due_date: date | None
    priority: str


@dataclass
class TaskList:
    owner_id: UUID
    version: int
    _tasks: dict[UUID, Task] = field(default_factory=dict)
    _events: list[object] = field(default_factory=list)

    @property
    def tasks(self) -> tuple[Task, ...]:
        return tuple(self._tasks.values())

    def pull_events(self) -> tuple[object, ...]:
        events = tuple(self._events)
        self._events.clear()
        return events

    def add_task(
        self,
        description: str,
        due_date: date | None,
        priority: str,
    ) -> Task:
        normalized = " ".join(description.casefold().split())
        duplicate = any(
            " ".join(task.description.casefold().split()) == normalized
            and task.due_date == due_date
            for task in self._tasks.values()
        )
        if duplicate:
            raise ValueError("A matching task already exists for that date")

        task = Task(uuid4(), description.strip(), due_date, priority)
        self._tasks[task.task_id] = task
        self._events.append(TaskAdded(task.task_id, self.owner_id))
        return task

Das Beispiel lässt die Definition von TaskAdded aus Gründen der Kürze weg. In einem vollständigen Domain-Modul wäre es ein immutable Value Object. Das Aggregate stellt statt seines mutablen Dictionary eine Tuple-Ansicht bereit, sodass Caller nicht an add_task() vorbei Elemente anhängen können.

Die Duplicate Detection ist hier bewusst einfach gehalten. Reale Regeln benötigen möglicherweise Locale-aware Normalization, Recurrence Semantics oder eine Database Uniqueness Constraint als abschließende, race-sichere Absicherung.

3. Den Repository Port definieren

from typing import Protocol
from uuid import UUID


class ConcurrentUpdate(Exception):
    pass


class TaskListRepository(Protocol):
    def get(self, owner_id: UUID) -> TaskList: ...

    def save(self, task_list: TaskList, expected_version: int) -> None: ...

Der Infrastructure Adapter kann Optimistic Concurrency mit einer Version Column implementieren. Der Domain Contract beschreibt, worauf es ankommt, ohne von SQLAlchemy oder einer bestimmten Datenbank abzuhängen.

4. Den Use Case koordinieren

from uuid import UUID


class AddTaskService:
    def __init__(
        self,
        repository: TaskListRepository,
        authorizer: TaskAuthorizer,
        outbox: Outbox,
    ) -> None:
        self.repository = repository
        self.authorizer = authorizer
        self.outbox = outbox

    def execute(
        self,
        actor_id: UUID,
        owner_id: UUID,
        proposal: AddTaskProposal,
    ) -> Task:
        self.authorizer.require_add_permission(actor_id, owner_id)

        task_list = self.repository.get(owner_id)
        expected_version = task_list.version
        task = task_list.add_task(
            description=proposal.description,
            due_date=proposal.due_date,
            priority=proposal.priority,
        )

        # Illustrative only: these two calls are not atomic through these ports.
        self.repository.save(task_list, expected_version)
        self.outbox.add_all(task_list.pull_events())
        return task

Der obige Code implementiert die Transaktion nicht. Repository Save und Outbox Insert müssen über eine konkrete Unit of Work ausgeführt werden, die eine gemeinsame Database Transaction verwendet. Andernfalls kann ein Fehler nach save dazu führen, dass die Task ohne ihr Event gespeichert bleibt. Das Diagramm zeigt diese beabsichtigte Boundary, nicht eine Garantie, die durch die Fragmente bereitgestellt wird.

Das Model ist in diesem Service nicht enthalten. Ein Adapter kann AddTaskProposal von einem LLM beziehen, ein anderer von einem HTTP Form, und Tests können es direkt erstellen. Das Business-Verhalten bleibt identisch.

Tools auf Application Commands abbilden

Agent-Tools sollten Use Cases statt Database Primitives bereitstellen. Bevorzugen Sie:

add_task(description, due_date, priority)
complete_task(task_id)
reschedule_task(task_id, due_date)

gegenüber:

insert_row(table, values)
update_record(table, id, patch)

Das erste Set spricht die Sprache der Domain und bietet der Application einen Ort, um zu autorisieren und Regeln durchzusetzen. Das zweite erlaubt dem Model, beliebige Persistence Mutations zu beschreiben.

Ein Tool Result sollte Fehler unterscheiden, auf die der Agent reagieren kann: ungültiger Vorschlag, nicht autorisierter Actor, Domain Conflict, Concurrent Update und nicht verfügbare Infrastruktur. Reduzieren Sie nicht alle Fehler auf einen String, der zu blinden Retries einlädt.

Die Boundary in Schichten testen

Domain Tests

Testen Sie Aggregates ohne Model, Network oder Database:

  • Doppelte Tasks werden abgelehnt.
  • Gültige Tasks lösen das erwartete Event aus.
  • Exponierte Collections können den internen State nicht verändern.
  • Transition Rules gelten auch bei wiederholten Operationen.

Application Tests

Verwenden Sie Fake Repositories und Authorizers, um Loading, die Reihenfolge der Authorization, Saves mit Expected Version, Outbox-Verhalten und Error Mapping zu überprüfen.

Model-Contract-Evaluations

Evaluieren Sie den probabilistischen Adapter separat:

  • Genauigkeit von Intent- und Field-Extraction
  • Auflösung relativer Dates mit bereitgestelltem Timezone Context
  • Ablehnung oder Rückfrage, wenn erforderliche Informationen fehlen
  • Resistenz gegen Prompt Injection innerhalb eines zitierten Task-Texts
  • Rate von schema-validen, aber semantisch unbrauchbaren Vorschlägen

Ein End-to-End-Test sollte anschließend bestätigen, dass schlechte Vorschläge niemals dieselben Domain-Methoden umgehen können, die von vertrauenswürdigen Interfaces verwendet werden.

Woran man ein funktionierendes Design erkennt

Sie sollten den Model Provider wechseln können, ohne einen Domain Test zu ändern. Eine Policy-Änderung sollte ein einzelnes Aggregate oder einen Domain Service betreffen und nicht mehrere Prompts. Traces sollten Begriffe verwenden, die das verantwortliche Team kennt. Malformed oder nicht autorisierte Vorschläge sollten vor der Persistence fehlschlagen, und ein Concurrent Save sollte fehlschlagen, statt den State stillschweigend zu überschreiben.

DDD macht ein Model nicht deterministisch. Es macht die Autorität, Sprache und Consistency Boundaries des Systems so explizit, dass das Model sie nicht selbst übernehmen muss.
