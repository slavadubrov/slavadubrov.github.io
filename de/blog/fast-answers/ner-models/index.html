Die besten NER-Modelle 2026: spaCy, GLiNER, Transformers, LLMs

Viacheslav Dubrov

2026-06-08 · Aktualisiert 2026-08-17 · 5 Min. · Retrieval- und Sprachsysteme

Automatische Übersetzung Dieser Artikel wurde automatisch aus der englischen Originalversion übersetzt.

Named Entity Recognition (NER) findet und labelt Textspans wie Personen, Unternehmen und Produktcodes. Diese Seite richtet sich an Engineers, die für einen Produktions-Workload einen passenden Extraktionsansatz auswählen. Sie bietet einen Ausgangspunkt, den Sie gegen Ihr Schema, Ihre Dokumente und Ihre betrieblichen Anforderungen testen können.

Verwenden Sie spaCy für stabile Labels und schnelle Pipelines. Wählen Sie GLiNER, wenn sich Labels häufig ändern, einen Bi-Encoder, wenn ein großes Label-Inventar gecachte Embeddings wiederverwenden kann, oder einen Fine-Tuned Transformer Token Classifier, wenn gelabelte Beispiele vorhanden sind. Verwenden Sie LLM-basierte Structured Extraction, wenn Sie einen komplexen Datensatz statt einer einfachen Liste von Spans benötigen.

Letzte Prüfung: 17.08.2026. Auswahlkriterien: Label-Stabilität, Label-Inventar, Span- gegenüber Record-Output, Sprache, überwachte Daten, Latenz, Normalisierung und Review-Kosten.

Auswahl des passenden Ansatzes

Beginnen Sie mit dem Entitätsschema, nicht mit dem Model.

Wenn Labels stabil sind und repräsentative Beispiele vorliegen, fine-tunen Sie einen Token Classifier. Vergleichen Sie ihn auf einem zurückgehaltenen Domain-Testset. Er sagt Token-Labels ohne autoregressive Generation voraus. Latenz und Kosten hängen weiterhin von Model, Hardware, Batch-Größe und Serving-Stack ab.

Wenn sich Labels wöchentlich ändern, verwenden Sie GLiNER oder einen LLM Extractor, während sich die Ontologie stabilisiert. Schreiben Sie für jedes mehrdeutige Label eine kurze Typbeschreibung. Aktuelle Hard-Zero-Shot-NER-Forschung zeigt, dass Beschreibungen die Generalisierung verbessern und verhindern, dass Label Leakage als Zero-Shot-Fähigkeit interpretiert wird. Ziel ist, zunächst das richtige Schema zu bestimmen, bevor Sie Annotation-Budget investieren.

Wenn Sie ein großes Label-Inventar wiederverwenden, evaluieren Sie einen Bi-Encoder, bevor Sie einen gemeinsamen Label-Text-Encoder einsetzen. Das GLiNER-Bi-Encoder-Paper berichtet 61,5 Micro-F1 auf CrossNER. Außerdem wird bei 1.024 Labels unter den H100-Testbedingungen ein bis zu 130-mal höherer Throughput mit vorab berechneten Embeddings berichtet. Diese Ergebnisse zeigen ein Skalierungsverhalten. Sie sind keine Schätzung für einen anderen Produktions-Workload.

Wenn Dokumente mehrere Sprachen umfassen, benchmarken Sie jede Zielsprache und jedes Script. OpenNER 1.0 stellte in seiner Sammlung mit 52 Sprachen fest, dass kein einzelnes Model in allen Sprachen am besten abschneidet. Testen Sie sowohl englische als auch lokalisierte Typbeschreibungen, da der Label-Text Teil des Model-Inputs ist.

Wenn der Output ein strukturierter Record statt Spans ist, verwenden Sie ein LLM mit Structured Outputs oder eine Hybrid-Pipeline. LangExtract ist nützlich, wenn jede Extraktion auf ihre Quellposition zurückgeführt werden muss. NuExtract ist eine Self-Hosted-Option für multimodale Dokumentextraktion. Beide benötigen weiterhin eine Evaluation auf Feldebene für die Zieldokumente.

Viele geschäftliche Extraktionsaufgaben sind keine reine NER. „Finde die Parteien, Verpflichtungen, das Inkrafttreten, die Kündigungsklausel und das anwendbare Recht“ ist Dokumentverständnis mit Entitätsfeldern.

Verwenden Sie für PII ein PII-Framework wie Presidio als Integrations- und Redaction-Layer. Behandeln Sie GLiNER2-PII als Model-Kandidaten, nicht als Compliance-Entscheidung. Messen Sie den Recall für die sensiblen Formate, Sprachen und Dokumente, die das System verarbeiten wird.

Produktions-Pipeline

Eine Produktions-Extraktions-Pipeline ergänzt das Model häufig um weitere Stufen:

  1. Kandidatenextraktion: spaCy, GLiNER, Transformer-Model, LLM, Regeln oder eine Kombination.
  2. Optionale Normalisierung oder Entity Linking: Ordnen Sie Spans kanonischen IDs, Produktcodes, Usern, Unternehmen oder Ontologieeinträgen zu.
  3. Validierung und Review: Verwerfen Sie unmögliche Labels, erzwingen Sie Schema-Constraints, deduplizieren Sie Spans und leiten Sie unsichere Fälle an das Review weiter.

Normalisierung macht extrahierten Text zu nutzbaren Produktdaten. Den Span „Apple“ zu finden, ist nur der erste Schritt. Das System muss weiterhin entscheiden, ob damit das Unternehmen, die Frucht, eine Produktfamilie oder ein Aktien-Ticker gemeint ist, und ihn anschließend einer stabilen ID zuordnen.

Eval-Checkliste

Messen Sie mehr als Entity-Level-F1:

  • Exact-Span-F1
  • Relaxed-Span-F1
  • Label-Confusion-Matrix
  • Umgang mit verschachtelten Entitäten
  • Genauigkeit der Entitätsnormalisierung
  • Sensitivität gegenüber Typbeschreibungen und Label-Sprache
  • Slices nach Sprache, Script und Dokumentformat
  • False Positives nach Label
  • Confidence Calibration
  • Latenz und Kosten pro Dokument
  • Human-Correction-Rate

Halten Sie das Testset von Schema-Design und Threshold-Tuning getrennt. Berichten Sie die Anzahl der Dokumente und Entity Mentions pro Label. Verwenden Sie Confidence-Intervalle auf Dokumentebene, wenn wiederholte Mentions in einem Dokument andernfalls die Sicherheit künstlich erhöhen würden.
