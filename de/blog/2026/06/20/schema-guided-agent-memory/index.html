AI Agent Memory: Schema-Guided State und Provenance

Viacheslav Dubrov

2026-06-20 · Aktualisiert 2026-07-22 · 14 Min. · KI-Agenten

Automatische Übersetzung Dieser Artikel wurde automatisch aus der englischen Originalversion übersetzt.

Lang laufende Agents rufen häufig veraltete Fakten ab, weil gewöhnliche Semantic Memory keine Regel dafür besitzt, welcher Wert aktuell ist.

Wenn ein Benutzer eine Passfrist von 15. Juli auf 30. Juni ändert, kann die Vector Search beide Aussagen abrufen. Eine zustandsbehaftete Memory-Schicht muss festhalten, dass der Wert vom 30. Juni den früheren Wert ersetzt.

Dieser Artikel richtet sich an Engineers, die lang laufende oder mandantenfähige Agents entwickeln, deren Memory separate Runs überdauern und dabei den aktuellen State sowie Tenant-Grenzen berücksichtigen muss.

Am Ende sollten Sie in der Lage sein, einen typisierten Memory Record und einen Write Path zu entwerfen und anschließend Current-State- und Point-in-Time-Reads zu testen, ohne Vector Recall als Source of Truth zu behandeln.

TL;DR

Behandeln Sie persistentes Agent Memory als typisierten Application State. Extrahieren Sie Memory Candidates über eine Structured-Output-Grenze. Speichern Sie Records mit Tenant Scope, Validity Windows, Supersession, Provenance und Schema Versioning und rufen Sie im Read Path nur den kleinsten aktuellen Ausschnitt ab. Reservieren Sie Vector Search für unscharfen Recall. Lesen Sie veränderliche Fakten aus Scoped, Current Records.

Die Context-Window-Falle

Das Context Window ist die Eingabe, die für einen einzelnen Model Call verfügbar ist. Eine Anwendung kann Messages in spätere Calls übernehmen, doch die Application Policy muss entscheiden, welche alten Fakten weiterhin gelten und wer sie sehen darf.

Lang laufende Agents müssen sich Preferences, Task Status, Customer Facts, Tool Decisions, Compliance Notes und frühere Fehler merken. Die einfache Variante besteht darin, Summaries anzuhängen oder alte Notes in einen Vector Store zu schreiben. Das funktioniert, bis sich einer der gespeicherten Fakten ändert.

Nun verfügt der Agent über zwei Passfristen, zwei bevorzugte Formate oder zwei Projektentscheidungen. Semantic Search kann beide abrufen. Eine Summary kann einen davon überschreiben. Ein langer Context kann den veralteten neben dem aktiven Wert enthalten. Diese Designs rufen Text ab, setzen den aktuellen Wert aber nicht durch.

Der Memory Contract muss konkrete Fragen beantworten:

  • Was gilt jetzt?
  • Was galt am 2. Juni?
  • Wer hat es gesagt?
  • Zu welchem Tenant gehört es?
  • Welchen älteren Fakt hat dieser Fakt ersetzt?
  • Kann ich ihn löschen oder ablaufen lassen?

Schema-Guided Agent Memory (SGAM) speichert diese Antworten als Fields und Relations, statt sie implizit in Prose zu belassen.

Was SGAM bedeutet

Drei ähnlich benannte Konzepte definieren den Scope von SGAM.

Schema-Guided Dialogue (SGD) ist das 2019 Google Task-Oriented Dialogue Dataset. Sein Schema beschreibt Service APIs, Intents und Slots, damit ein Dialogue Model den State von Services verfolgen kann, die es noch nicht gesehen hat. Es ist ein nützlicher Präzedenzfall für Schema-Based Tracking, bleibt aber auf Dialogue Services beschränkt.

Schema-Guided Memory (SGM) ist der Research-Begriff, den Mei et al. in According to Me: Long-Term Personalized Referential Memory QA verwenden. Das Paper vergleicht Free-Text-Descriptive Memory (DM) mit Memory Items im Fixed-Schema-Key-Value-Format. Beide Repräsentationen enthalten dieselben Source Information in unterschiedlichen Strukturen.

In diesem Artikel verwende ich Schema-Guided Agent Memory (SGAM) für ein Engineering Pattern, bei dem Schemas Writes, Updates, Retrieval und Deletion steuern. Das Schema definiert den Application State und seinen Lifecycle.

ATM-Bench zeigt, warum die Repräsentation relevant ist. Es verwendet ungefähr vier Jahre persönliche Daten aus Emails, Images und Videos. Die Fragen erfordern persönliche Referenzen, Location, mehrere Evidence Pieces und Updates über die Zeit. Für seinen Hard Split berichtet das Paper, dass SGM im getesteten Setup DM bei Retrieval und Question Answering übertrifft. SGM legt Fields wie Time, Source, Location, Entities und Tags in einer Fixed Representation offen. Ich behandle diese Repräsentation und die berichteten Ergebnisse als die unterstützte Schlussfolgerung; das Paper etabliert keinen direkten Field-Addressing-Mechanismus.

SGM versus DM beantwortet eine Storage-Frage: Soll Memory Free Text bleiben oder Named Fields verwenden? Ein produktiver Agent hat vor dem Storage ein weiteres Problem. Er muss eine unstrukturierte Conversation in ein vorgeschlagenes Memory Update überführen. Schema-Guided Reasoning (SGR) macht diesen beabsichtigten Decision Path prüfbar: Die Response kann Evidence, Subject und Attribute, einen Vergleich mit dem Current State sowie einen Candidate Write enthalten. Die Model Response erzwingt keine Dependencies oder Reihenfolge zwischen diesen Fields. Separate Calls, Validators und Application Policy setzen diese Regeln durch; SGAM wendet die Storage- und Lifecycle-Regeln nach dem Model Call an.

Model Extraction und Memory Ownership trennen

Byte says

Jeder Schreibvorgang meines Extractors war schema-valid. Sowohl die überholte Passfrist als auch ihre Korrektur waren gültig, deshalb blieben beide im Speicher.

Der Memory Write durchläuft drei Schichten. Structured Output (SO) erzwingt die Shape des Candidate Objects. Schema-Guided Reasoning (SGR) macht die beabsichtigten Fields und die Decision Intent des Models in einer strukturierten Response prüfbar. Schema-Guided Agent Memory (SGAM) verwaltet den Candidate nach dem Model Call als persistenten State. Separate Calls, Validators und Application Policy erzwingen Dependencies, Reihenfolge und Lifecycle Rules.

Ein Verdict, eine Route oder ein Plan läuft normalerweise mit dem aktuellen Request ab. Ein anderer Run kann einen Memory Candidate Tage später lesen oder ihn zur Auswahl eines Tool Calls verwenden. Diese längere Lebensdauer erfordert Storage Rules, die SGR nicht bereitstellt.

SGR strukturiert einen Model Call um eine beabsichtigte Reasoning Topology. Bei einem Memory Write könnte die Response Source Evidence, ein normalisiertes Subject und Attribute, einen Vergleich mit dem Current State sowie ein Proposed Update enthalten. Pydantic oder JSON Schema beschreibt diese Fields. Provider-native Structured Output oder ein Guided-Decoding-Runtime wie XGrammar hält die Response in dieser Shape.

Diese Shape macht die vom Model deklarierten Fields und seine Intent prüfbar. Sie kann keine korrekte Schlussfolgerung garantieren und nicht beweisen, dass das Model diese Fields in der richtigen Reihenfolge verwendet hat. Separate Calls, Validators und Application Policy bilden die Enforcement Boundary für Dependencies, Reihenfolge und Lifecycle.

SGAM entscheidet, was geschieht, sobald dieses Object existiert. Soll es gespeichert werden? Ersetzt es einen älteren Fakt? Welcher Tenant darf es sehen? Ist es aktuell oder historisch? Welche Source Episode belegt es?

Im Write Path sieht die Sequenz so aus:

SGR reasoning schema + Structured Output -> candidate write -> SGAM policy and persistence

Dieser Block benötigt Pydantic und ist daher im Beispiel mit no-run markiert, damit Environments, die diese optionale Dependency nicht installieren, dies in den Checks erkennen:

from datetime import datetime
from pydantic import BaseModel, Field

class MemoryDelta(BaseModel):
    tenant_id: str = Field(description="Isolation boundary, e.g. acme")
    subject: str = Field(description="Normalized entity ID, e.g. mira")
    attribute: str = Field(description="Property being updated")
    value: str = Field(description="New value")
    valid_from: datetime
    source_episode_id: str

MemoryDelta hält fest, was das Model extrahiert hat. Der SGAM Write Service entscheidet weiterhin, ob der Candidate abgelehnt, gemerged oder gespeichert wird.

Write und Read Paths haben unterschiedliche Aufgaben

Nur der Write Path mutiert den gespeicherten State. Der Read Path wählt Records für den aktuellen Request aus.

Der Ingestion Flow ist der Write Path:

  1. Erfassen Sie eine Raw Episode aus Messages, Tool Results oder Business Events.
  2. Extrahieren Sie typisierte Candidates über Structured Output.
  3. Validieren Sie das Schema und weisen Sie fehlerhafte Writes zurück.
  4. Lösen Sie Conflicts auf, schließen Sie veraltete Fakten und bewahren Sie die Provenance.
  5. Committen Sie den Record in den SGAM Store.

Der Request Flow ist der Read Path:

  1. Beginnen Sie mit der User Question.
  2. Entscheiden Sie, ob die Frage den Current State oder einen Point-in-Time State benötigt.
  3. Filtern Sie nach Tenant, Memory Type, Subject, Attribute und Validity Window.
  4. Fügen Sie Vector- oder Graph-Expansion nur hinzu, wenn der Exact-State-Lookup nicht ausreicht.
  5. Stellen Sie den kleinsten belegten Context für das Model zusammen.

Lesen Sie das Diagramm von links nach rechts in zwei Lanes. Die obere Lane schreibt Memory, die untere liest es. Beide verwenden denselben Store.

Was in ein Memory Schema gehört

Ein minimaler SGAM Record benötigt mehr als text.

memory_id
subject
attribute
value
memory_type
schema_version
valid_from
valid_to
supersedes_memory_id
source_episode_id
confidence
retention_policy

Mit diesen Fields kann eine neue Passfrist die vorherige schließen, ohne die Historie zu löschen. Dieselbe Tabelle kann Current-State- und Point-in-Time-Queries beantworten und das Ergebnis anschließend bis zu seiner Source Episode zurückverfolgen. schema_version unterstützt Migrations, während retention_policy Löschjobs mitteilt, was sie zusätzlich entfernen müssen.

Verwenden Sie RAG zum Abrufen von Documents und SGAM zur Verwaltung veränderlicher States. Vector Search bleibt für Fuzzy Recall, Clustering und Expansion im System. Der aktuelle Wert von mira.passport_deadline sollte aus einem Scoped Memory Record stammen und nicht aus dem Chunk, der zufällig am höchsten gerankt wurde.

Beispiel für einen veralteten Fakt

Betrachten wir einen synthetischen Trace mit zwei Episodes, dargestellt als DM Baseline und SGAM Ledger:

e1: Mira prefers concise answers. Her passport deadline is 2026-07-15.
e2: Mira corrected the deadline. It is now 2026-06-30.

Eine DM Baseline behält beide Episodes als Free Text, sodass Text Search e1 zurückgeben kann, weil dieser Text die richtigen Words enthält. SGAM extrahiert aus jeder Episode einen typisierten Fakt, der nach Tenant, Subject und Attribute geKeyed ist. Es sollte e2 als Current State zurückgeben und e1 für eine Historical Query behalten.

Der folgende eigenständige SQLite Write Path verwendet ISO-8601-UTC-Strings für Timestamps, konfiguriert sqlite3.Row vor dem Lesen nach Column Name und erstellt einen Partial Unique Index für genau einen offenen Fakt pro Tenant, Subject und Attribute. replace_fact verwaltet eine Transaction; SQLite serialisiert Concurrent Writers, daher sollten Caller die gesamte Transaction nach einem Lock- oder Uniqueness Error erneut ausführen.

import sqlite3
from dataclasses import dataclass

@dataclass(frozen=True)
class MemoryFact:
    tenant_id: str
    subject: str
    attribute: str
    value: str
    valid_from: str
    source_episode_id: str

def open_db() -> sqlite3.Connection:
    db = sqlite3.connect(":memory:")
    db.row_factory = sqlite3.Row
    db.executescript(
        """
        create table memory_facts (
            fact_id integer primary key,
            tenant_id text not null,
            subject text not null,
            attribute text not null,
            value text not null,
            valid_from text not null,
            valid_to text,
            source_episode_id text not null
        );
        create unique index one_open_fact
        on memory_facts (tenant_id, subject, attribute)
        where valid_to is null;
        """
    )
    return db

def close_previous_fact(db: sqlite3.Connection, fact: MemoryFact) -> int | None:
    row = db.execute(
        """
        select fact_id
        from memory_facts
        where tenant_id = ?
          and subject = ?
          and attribute = ?
          and valid_to is null
        limit 1
        """,
        (fact.tenant_id, fact.subject, fact.attribute),
    ).fetchone()
    if not row:
        return None

    db.execute(
        "update memory_facts set valid_to = ? where fact_id = ? and valid_to is null",
        (fact.valid_from, row["fact_id"]),
    )
    return int(row["fact_id"])

def replace_fact(db: sqlite3.Connection, fact: MemoryFact) -> None:
    with db:
        close_previous_fact(db, fact)
        db.execute(
            """
            insert into memory_facts
                (tenant_id, subject, attribute, value, valid_from, source_episode_id)
            values (?, ?, ?, ?, ?, ?)
            """,
            (
                fact.tenant_id,
                fact.subject,
                fact.attribute,
                fact.value,
                fact.valid_from,
                fact.source_episode_id,
            ),
        )

db = open_db()
replace_fact(
    db,
    MemoryFact("acme", "mira", "passport_deadline", "2026-07-15", "2026-06-01T09:00:00Z", "e1"),
)
replace_fact(
    db,
    MemoryFact("acme", "mira", "passport_deadline", "2026-06-30", "2026-06-03T10:00:00Z", "e2"),
)
current = db.execute(
    """
    select value, source_episode_id
    from memory_facts
    where tenant_id = ? and subject = ? and attribute = ? and valid_to is null
    """,
    ("acme", "mira", "passport_deadline"),
).fetchone()
assert (current["value"], current["source_episode_id"]) == ("2026-06-30", "e2")

Wenn e2 eintrifft, setzt die Function valid_to für den aus e1 extrahierten Fakt auf den Timestamp von e2 und fügt anschließend e2 mit einem offenen valid_to ein. Die Row Factory macht row["fact_id"] auf der hier erstellten Default Connection gültig. Der Partial Unique Index ist der Database Guard für genau eine offene Row; ein Multi-Writer Deployment sollte eine Database und Retry Policy wählen, die zum Workload passt. DM besitzt keinen entsprechenden Update Step, sodass der alte Text die Korrektur weiterhin überranken kann.

Current- und Historical-Deadline-Queries gegen beide Repräsentationen liefern unterschiedliche Ergebnisse:

Naive text memory:
  returned episode: e1 -> passport deadline is 2026-07-15

SGAM current state:
  mira.passport_deadline = 2026-06-30
  valid_from=2026-06-03T10:00:00Z, source=e2

SGAM point-in-time state:
  on 2026-06-02, mira.passport_deadline = 2026-07-15

Kombinieren Sie diese Transaction in Production mit Structured Extraction im Write Path. Die Database Transaction aktualisiert die Temporal Validity. Das Model extrahiert einen Candidate Fact, entscheidet aber nicht, welche gespeicherte Row aktuell bleibt.

Graphiti ist eine konkrete Open-Source-Implementierung von relationalem, temporalem Memory. Es verfolgt, wie sich Facts ändern, bewahrt Pointer auf Source Episodes und unterstützt Hybrid Retrieval. LangGraph trennt Thread Checkpoints von Cross-Thread Stores. Mem0 bündelt Memory Operations als Managed Service. Letta verwendet editierbare Context Blocks statt Field-Level-SGAM, behandelt Agent State aber ebenfalls als persistente Daten.

Beginnen Sie mit dem Data Model. Wenn Exact Fact Lookup die wichtigste Operation ist, reicht normalerweise eine Relational Table mit JSON Payloads, Validity Columns, Tenant Indexes und einem Vector Sidecar aus. Fügen Sie einen Graph hinzu, wenn Relationship Traversal Teil des Produkts ist – nicht, weil die Graph-Demo beeindruckend aussieht.

Bauen Sie zuerst den Write Path, nicht den Graph

Byte says

Ich baute zuerst den Graphen. Jede Abfrage des Produkts lautete: „Was ist Xs aktuelles Y?“, und darauf gibt eine Tabelle mit zwei Gültigkeitsspalten die Antwort.

Entscheiden Sie zunächst, was das Produkt speichern darf. Die Entscheidung zwischen Graph und Vector kommt später.

Ein Support Agent könnte Account Tier, Open Cases und dauerhafte Contact Preferences speichern. Er sollte nicht jede frustrierte Nebenbemerkung in Profile State überführen. Ein Coding Agent könnte Repo Conventions und Unresolved Tasks speichern. Er sollte keine private Note für immer behalten, nur weil diese Note einmal abgerufen wurde.

Beginnen Sie mit dem Write Path und behandeln Sie Memory als kleine State Mutation:

  1. Benennen Sie Memory Type, Subject, Tenant Scope und Retention Class.
  2. Extrahieren Sie Candidate Records mit Structured Output.
  3. Validieren Sie den Payload mit Pydantic oder der Schema-Schicht, die Ihr Stack bereits verwendet.
  4. Lösen Sie Conflicts vor dem Insert auf und entscheiden Sie insbesondere, ob der neue Record einen alten superseded.
  5. Bewahren Sie einen Source Pointer auf die Raw Episode, den Tool Result, die File, das Ticket oder die User Confirmation auf, aus dem bzw. der der Record entstanden ist.
  6. Schreiben Sie die Schema Version mit jedem Record, statt sie ausschließlich im Application Code zu hinterlegen.

Der erste SGAM Store kann eine Relational Table mit einer JSON Column und einigen Indexes sein. Ein Graph wird nützlich, wenn das Produkt Relationships wie Customer-to-Account, Account-to-Policy, Task-to-Artifact oder Project-to-Decision traversieren muss.

Hot Path und Background Writes

Eine sofortige Extraction lohnt sich, wenn der nächste Turn vom neuen Memory abhängt. Wenn der User sagt: „Merke dir, dass ich kurze Antworten bevorzuge“, sollte das System keinen Nightly Job benötigen, bevor es sich anders verhält.

Die meisten Turns benötigen keinen Immediate Write. Speichern Sie die Raw Episode mit Tenant-, Session- und Tool-Metadaten und lassen Sie anschließend einen Background Worker Candidates extrahieren. Bei Recurrence-Based Consolidation puffert der Worker schwache Signale und promoted einen Fakt erst, wenn sich ähnliche Evidence wiederholt oder der User ihn bestätigt. Dies führt zu Freshness Lag. Für „User fragt häufig nach CSV-Exports“ ist das akzeptabel, für „Customer hat die Lieferadresse geändert“ riskant.

Halten Sie den Read Path deterministisch. Erzwingen Sie Tenant Scope und Validity zuerst und verwenden Sie Fuzzy Retrieval nur dann, wenn es nützlichen Context hinzufügen kann.

  1. Filtern Sie nach Tenant, Memory Type und Validity Window.
  2. Rufen Sie Exact Structured State vor Semantic Neighbors ab.
  3. Verwenden Sie Vector- oder Graph-Expansion für Supporting Evidence, Related Entities und Examples – nicht als Authority für aktuelle Facts.
  4. Stellen Sie den kleinsten belegten Context zusammen, der die Frage beantworten kann.

Behandeln Sie Schema Migration als Product Change, da sie verändert, was der Agent abrufen, zitieren oder löschen kann. Sie kann außerdem ändern, welche historischen Facts als aktuell gelten. Planen Sie Migration Scripts, Backfills, Dual-Read Windows und Deletion Behavior im selben Release.

Wann sich SGAM-Komplexität lohnt

Verwenden Sie SGAM, wenn sich Facts im Laufe der Zeit ändern können:

  • User Preferences, die aktualisiert oder widerrufen werden können
  • Customer- oder Account-Facts mit Audit-Anforderungen
  • Task State für lang laufende Assistants
  • Coding-Agent-Project-Memory
  • von mehreren Agents geteilter State
  • Compliance Notes, bei denen Provenance relevant ist
  • temporale Fragen wie „Was haben wir vor der Migration angenommen?“

SGAM ist überdimensioniert, wenn Memory kurzlebig, explorativ oder günstig neu berechenbar ist. Wenn der Agent nur einige Turns Continuity benötigt, reichen ein Checkpoint und eine gekürzte Message History aus. Für statisches Document QA genügt möglicherweise RAG. Und wenn die Domain so instabil ist, dass sich das Schema täglich ändert, wird Typed Memory das Team ausbremsen.

Evaluation Checklist

Evaluieren Sie den gesamten Memory Lifecycle ebenso wie die finale Answer. Ein System kann eine plausible Response erzeugen, obwohl es den falschen Fakt gespeichert, einen veralteten abgerufen oder eine Tenant-Grenze überschritten hat.

Ich verwende dieselbe Stage-by-Stage-Aufteilung wie in meinem RAG-Evaluation-Artikel. Messen Sie die Stage, in der ein Fehler auftreten kann, statt die Evaluation auf den generierten Text zu beschränken. Die Trace-Disziplin aus dem Artikel zur Agent-Evaluation gilt ebenfalls, weil ein Memory-Bug häufig bereits in der Run History sichtbar wird, bevor er die Answer erreicht.

Ich würde SGAM mit Replay testen. Speisen Sie eine feste Sequence von Episodes in den Memory Writer ein und prüfen Sie das Ledger nach jedem relevanten Turn. Stellen Sie anschließend Current-State- und Point-in-Time-Fragen an den resultierenden Store.

Benchmarks wie LoCoMo, LongMemEval und ATM-Bench stellen öffentliche Test Cases bereit. Sie ersetzen keine Domain Test Suite. Ein Coding Assistant, ein Customer-Support-Bot und ein Compliance Copilot benötigen unterschiedliche Schemas, Filters, Retention Rules und Failure Tests.

Caveats

SGAM ist meine Bezeichnung für ein Pattern, kein Standard. Bestehende Projekte teilen das Problem unterschiedlich auf. LangGraph Memory und LangMem beschreiben Short-Term- und Long-Term-Stores, Profiles, Collections, Hot-Path-Writes und Background Memory Managers. Zep Graphiti verwendet den Begriff Temporal Context Graph. Letta persistiert editierbare Memory Blocks, während Mem0 eine Managed Memory Layer anbietet. Microsoft GraphRAG, LlamaIndex Property Graphs und Cognee fassen verwandte Teile des Problems als Knowledge Graphs auf.

Ein User Profile, ein Episode Log, ein Document Graph und ein von einem Agent editierbarer Memory Block lösen unterschiedliche Retrieval- und Update-Probleme. Ich reserviere SGAM für persistentes Memory, das den aktuellen Application State repräsentiert und daher Schema, Validity, Provenance, Conflict Handling, Retention und Migration benötigt.

Typed Memory kann weiterhin falsch sein. Ein Schema macht fehlerhafte Writes leichter prüfbar; es macht sie nicht vertrauenswürdig. Sie benötigen weiterhin Source Trust, User Confirmation für sensible Facts, Conflict Policy, Deletion und Monitoring.

Schema Migration verursacht Arbeit. Sobald Memory zum State wird, sind Sie für Versioning, Backfills, alte Records und Deletion Behavior verantwortlich. Wenn Sie diese Arbeit auslassen, werden alte Records die Semantics oder Retention Policy überdauern, durch die sie erstellt wurden.
