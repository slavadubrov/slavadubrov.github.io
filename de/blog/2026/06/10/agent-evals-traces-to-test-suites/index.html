AI-Agent-Evaluation in Production: Von Traces zu Testsuiten

Ein Chatbot liefert Ihnen eine Antwort zur Bewertung. Ein Agent liefert Ihnen einen ganzen Entscheidungsbaum: Pläne, Tool Calls, Retries und den Moment, in dem er entscheidet, dass er fertig ist.

Dieser Unterschied erfordert eine andere Evaluationsmethode. Eine finale Antwort kann korrekt aussehen, obwohl der Agent ein erforderliches Tool übersprungen, einen Call 17-mal wiederholt, ein Ergebnis falsch interpretiert oder einen von der Production-Policy verbotenen Pfad eingeschlagen hat. Answer-only-Grading verschleiert diese Fehler.

TL;DR: Agent Evals benötigen drei Ebenen: Outcome-Metriken, Trajectory-Metriken und Component-Metriken. Bauen Sie den Prozess um diesen Loop herum auf: Trace -> Label -> Cluster -> Dedupe -> versioniertes Dataset -> CI-Gate -> Online-Monitoring. Verwenden Sie deterministische Checks für Tool-Reihenfolge, Argumente, Loops und Invarianten. Setzen Sie LLM Judges nur dort ein, wo der Check Interpretation erfordert, strukturieren Sie diese Judges mit Schema-Guided Reasoning (SGR) und kalibrieren Sie sie anhand von Human Labels, bevor Sie ihnen vertrauen.

Warum sich Agent Evals unterscheiden

Traditionelle LLM Evals bewerten meist ein einzelnes Input-Output-Paar: Relevanz, Faithfulness, Korrektheit, Sicherheit, vielleicht Stil. Agents fügen Planning, Tool Calls, Retries und Termination Checks hinzu, und jeder Schritt ist eine neue Fehlerquelle.

Nehmen wir einen Refund Agent. Das Transkript kann gut enden, während der Trace falsch ist:

lookup_order -> issue_refund -> final_answer

Das Output-Eval ist erfolgreich. Ein Trajectory-Eval sollte fehlschlagen, weil verify_identity nie vor issue_refund ausgeführt wurde. Für Agents mit Tool Use sind Answer-only-Evals Smoke Tests: Sie erkennen einen vollständigen Ausfall und übersehen fast alles andere.

Es gibt ein zweites Problem: Fehler verstärken sich. Wenn ein Workflow 20 erforderliche Schritte umfasst, jeder Schritt unabhängig erfolgreich ist und jeder Schritt dieselbe Zuverlässigkeit von 95 % besitzt, liegt die End-to-End-Erfolgsrate bei ungefähr 36 %:

0.9520≈0.360.95^{20} \approx 0.360.9520≈0.36

Der Agent kann in isolierten Checks also solide wirken und trotzdem die meisten vollständigen Runs nicht bestehen. Der Bruch liegt meist irgendwo in der Mitte. Ihn zu finden erfordert Visibility auf Component-Ebene, nicht einen weiteren Blick auf die Antwort.

Zwei Forschungsteams haben dies quantifiziert.

tau-bench gibt einem Agenten Customer-Service-Aufgaben aus den Bereichen Fluggesellschaften und Einzelhandel. Der Agent kommuniziert mit einem simulierten User, ruft APIs auf und muss die Domain-Policy befolgen. Nach der Konversation prüft der Grader, ob die Datenbank den annotierten Zielzustand erreicht hat. Ein plausibles Transkript mit den falschen Zeilen schlägt trotzdem fehl.

Unter diesem Grading schaffte selbst GPT-4o weniger als die Hälfte der Aufgaben. Das Paper führte außerdem pass^k ein: Dieselbe Aufgabe wird k-mal ausgeführt, und ein Pass zählt nur, wenn der Agent in allen k Runs erfolgreich ist.

Retail-Scores, die bei einem Versuch noch akzeptabel aussahen, fielen bei k = 8 unter 25 %. Bei mehr als drei Vierteln der Aufgaben scheiterte derselbe Agent bei mindestens einem von acht Versuchen mit derselben Aufgabe. Ein Eval mit nur einem Run kann diese Inkonsistenz nicht sichtbar machen.

MAST untersucht, warum Agents scheitern. Die Autoren annotierten mehr als 1.600 Execution Traces aus sieben populären Multi-Agent-Frameworks und ordneten die Fehler 14 wiederkehrenden Modi zu. Die Taxonomie umfasst vage Rollendefinitionen (System Design), dass ein Agent ignoriert, was ein anderer Agent berichtet hat (Inter-Agent Misalignment), sowie das Deklarieren von Erfolg ohne Prüfung des Ergebnisses (No Verification). Diese Fehler betreffen Prompts, Orchestration-Logik und fehlende Checks im Harness. Ein stärkeres Base Model kann keinen Verification-Schritt ausführen, der nie implementiert wurde. Das Evaluationsziel muss daher auch den Harness um das Model herum umfassen.

Die Adoptionslücke

Die Umfrage State of Agent Engineering von LangChain (1.340 Befragte, durchgeführt Ende 2025) deutet darauf hin, dass viele Teams bereits das Rohmaterial für bessere Evals besitzen: 89 % berichteten von irgendeiner Form von Observability, während 52,4 % Offline Evals und 37,3 % Online Evals durchführten.

Dieselbe Umfrage berichtet, dass 57,3 % der Befragten bereits Agents in Production einsetzen. Auf die Frage, was Production blockiert, nannten 32 % die Qualität und 20 % die Latency. Es handelt sich um eine Vendor-Umfrage unter den eigenen Befragten und nicht um eine Vollerhebung aller Agent-Teams. Sie zeigt jedoch eine nützliche Lücke zwischen Trace-Sammlung und systematischer Evaluation.

Teams befinden sich dadurch in einem schwierigen Zwischenzustand: Sie können einen fehlerhaften Run nachträglich untersuchen und anschließend trotzdem denselben Fehler zweimal ausliefern.

Jeder diagnostizierte Production-Fehler sollte einen Trace, ein Label, eine Dataset-Zeile und einen Scorer hinterlassen. Ein reproduzierbarer Fehler gehört in die Regression Suite.

Metriken nach Fehlermodus auswählen

Die richtige Metrik hängt vom Fehlermodus ab, nicht vom Framework. Die sinnvolle Aufteilung umfasst drei Bereiche:

  1. Outcome Evals beantworten, ob die Aufgabe erfolgreich war.
  2. Trajectory Evals beantworten, ob der Pfad gültig, effizient und Policy-konform war.
  3. Component Evals beantworten, welches Tool, welcher Retriever, welcher Sub-Agent oder welcher Entscheidungsschritt ausgefallen ist.

Jeder Bereich kann offline auf festen, reproduzierbaren Fällen vor dem Release oder online auf gesampelten Production Traces nach der Antwort ausgeführt werden. Der Abschnitt zu Guardrails behandelt diese Aufteilung ausführlich. Offline Evals können Goldens erfordern: gespeicherte Fälle, die ein Input mit dem Outcome, den Tool-Invarianten und den Argumenten verbinden, die ein korrekter Run erzeugen muss. Online Evals sollten Invarianten, Verteilungen und asynchrone Checks bevorzugen, die nicht im Request Path liegen.

Beginnen Sie mit deterministischen Metriken. Sie sind kostengünstig, schnell und driften nicht.

Tool-Call-Korrektheit

Tool Correctness vergleicht die aufgerufenen Tools mit den erwarteten Tools. Wählen Sie den Grad der Strenge bewusst:

  • Exact Match: Die Sequenz muss exakt übereinstimmen. Verwenden Sie dies, wenn die Reihenfolge Policy ist, etwa bei lookup_order -> verify_identity -> issue_refund.
  • In-Order Match: Erforderliche Tools müssen in der korrekten relativen Reihenfolge vorkommen, zusätzliche harmlose Calls sind jedoch erlaubt.
  • Any-Order Match: Erforderliche Tools müssen vorkommen, ihre Reihenfolge darf jedoch variieren.

Ein kleiner lokaler Scorer reicht für den Anfang:

from collections import Counter


def tool_correctness(called: list[str], expected: list[str], mode: str = "in_order") -> float:
    if not expected:
        return 1.0
    if mode == "exact":
        return float(called == expected)
    if mode == "any_order":
        matched = sum((Counter(called) & Counter(expected)).values())
        return matched / len(expected)

    rows = [[0] * (len(expected) + 1) for _ in range(len(called) + 1)]
    for i, tool in enumerate(called):
        for j, wanted in enumerate(expected):
            if tool == wanted:
                rows[i + 1][j + 1] = rows[i][j] + 1
            else:
                rows[i + 1][j + 1] = max(rows[i][j + 1], rows[i + 1][j])
    return rows[-1][-1] / len(expected)


called = ["lookup_order", "check_refund_policy", "issue_refund"]
expected = ["lookup_order", "verify_identity", "issue_refund"]

print(round(tool_correctness(called, expected, "exact"), 3))     # 0.0
print(round(tool_correctness(called, expected, "in_order"), 3))  # 0.667

Der Score in_order ist der Recall der Longest Common Subsequence: welcher Anteil der erforderlichen Sequenz in der richtigen Reihenfolge erhalten blieb. Beachten Sie, was er ignoriert. Junk Calls senken den Score nicht. Ein Agent kann hier also 1,0 erreichen und trotzdem doppelt so viele Calls ausführen wie nötig. Wenn zusätzliche Calls Geld kosten oder den State verändern, erfassen Sie zusätzlich die Precision (gematchte erforderliche Calls geteilt durch alle Calls) und betrachten Sie beide Werte gemeinsam. Recall erkennt den fehlenden Schritt, Precision das Wandern.

DeepEvals Tool Correctness-Metrik stellt dieselben Stellschrauben über should_consider_ordering und should_exact_match bereit.

Argument Correctness

Das richtige Tool mit den falschen Argumenten aufzurufen ist häufig schlimmer, als das falsche Tool aufzurufen, weil der Trace normal aussieht.

Für einfache Fälle validieren Sie JSON Schema und exakte Werte. Für semantische Fälle speichern Sie die erwarteten Argumente und bewerten die Abweichungen:

{
    "trace_id": "tr_2417",
    "input": "Reschedule order A-100 for next Friday.",
    "expected_tools": ["lookup_order", "reschedule_delivery"],
    "expected_arguments": {
        "reschedule_delivery": {
            "order_id": "A-100",
            "date": "2026-06-19"
        }
    }
}

Eine Tool-Name-Metrik kann 2026-06-17 nicht erkennen, wenn die Policy 2026-06-19 verlangt. Das Dataset muss daher auch Argumente speichern.

Der zu diesem Dataset gehörende Score ist Parameter Match: der Anteil der erwarteten (tool, key, value)-Tupel, die der Agent korrekt erzeugt hat.

def argument_correctness(called_args: dict, expected_args: dict) -> float:
    total = matched = 0
    for tool, params in expected_args.items():
        for key, want in params.items():
            total += 1
            if called_args.get(tool, {}).get(key) == want:
                matched += 1
    return matched / total if total else 1.0

Exakte Gleichheit ist für IDs, Enums und bereits in ein einheitliches Format normalisierte Datumsangaben richtig. Für Freitext, Floats und Datumsangaben in beliebiger Form ist sie falsch, weil == eine korrekte Antwort als falsch markiert. Bewerten Sie diese Felder nach ihren eigenen Regeln: normalisierter String-Match, Date-Parsing oder numerische Toleranz. Die Metrik bleibt gleich, nur der Comparator pro Feld ändert sich.

Efficiency, Loops und Sackgassen

Ein Agent, der die Aufgabe nach fünf redundanten Tool Calls abschließt, deutet weiterhin auf ein Planning-Problem hin und verursacht höhere Betriebskosten.

Mit diesen kostengünstigen Signalen sollten Sie beginnen:

  • Redundant-Call-Rate: Identische Tool Calls mit identischen Argumenten, die mehr als zweimal wiederholt werden.
  • Trace-Shape-Anomalien: Plötzliche Anstiege bei Tiefe, Tool-Call-Anzahl, Token-Anzahl, Latency oder Cost.
  • Path Convergence: Wie nahe der Run am kürzesten bekannten gültigen Pfad für die Aufgabe liegt.
  • Termination Correctness: Ob der Agent zu früh stoppte, nach dem Erfolg weiterarbeitete oder Erfolg deklarierte, ohne die erforderliche State-Änderung herbeizuführen.
  • Plan Adherence: Wenn der Agent vor dem Handeln einen Plan schreibt, prüfen Sie, ob der Trace diesem Plan folgt. Ein guter, ignorierter Plan und ein schlechter, perfekt befolgter Plan schlagen beide fehl – aus gegensätzlichen Gründen. Die Differenz zwischen Plan und Trace zeigt, welcher Fall vorliegt.

Führen Sie diese Checks nach Möglichkeit vor einem Judge aus. Ein Loop Detector umfasst nur wenige Zeilen über dem Trace und benötigt kein Model.

Task Completion und Outcome Grading

End-to-End lautet die Frage: „Hat der User bekommen, was er verlangt hat?“

Zwei Muster funktionieren am besten:

  • Referenceless Task-Completion Judging: Extrahieren Sie das Ziel aus dem Input und bewerten Sie, ob Trace plus finale Antwort es erreicht haben. Das funktioniert online, weil Production Traffic nur selten Golden Outputs besitzt.
  • Environment-State Grading: Vergleichen Sie die finalen Datenbankzeilen, Dateien, Tickets, Buchungen oder Records mit einem annotierten Zielzustand. Das ist robuster als Transcript Matching, weil Agents gültige Pfade finden können, die Sie nicht vorab aufgeschrieben haben.

Die zweite Option ist besser, wenn Sie sie implementieren können. Der finale State ist der Vertrag. Das Transkript ist lediglich Evidence.

Zwei Einschränkungen sind wichtig. Ein 2025 Audit von Agentic Benchmarks stellte fest, dass tau-bench einige Aufgaben ausschließlich anhand des Database State bewertet. Bei Aufgaben, deren annotiertes Outcome keine State-Änderung und keinen bestimmten Text erfordert, erhält ein Agent, der nichts tut, daher einen Pass: 38 % im Airline-Split und 6,0 % im Retail-Split, bei jedem k. Außerdem berichtete Anthropic von einem Opus-4.5-Run, der eine tau2-bench-Buchungsaufgabe „nicht bestand“, weil er eine Policy-Lücke fand, die für den User tatsächlich das bessere Ergebnis darstellte. State Grading ist Transcript Matching überlegen, aber der Zielzustand bleibt eine Annotation, und Annotationen können Fehler enthalten. Prüfen Sie auch Fälle, die zu leicht bestehen, nicht nur solche, die fehlschlagen.

Component Evals

Outcome- und Trajectory-Metriken zeigen, dass der Run fehlgeschlagen ist, und ungefähr, wo. Component Evals bewerten einen einzelnen Span: War der abgerufene Chunk relevant? Hat der Sub-Agent das von seinem Caller erwartete Schema zurückgegeben? Ließ sich die eigene Antwort des Tools parsen? Hängen Sie den Score am Span statt am Run auf. Dann wird „Welches Tool hat sich diese Woche verschlechtert?“ zu einer Query und nicht zu einem erneuten Run.

Drei Checks decken den Großteil ab:

  • Per-Span-Scoring: Führen Sie die zum Span-Typ passende Metrik aus. Retrieval-Spans erhalten Recall und Precision gegenüber dem annotierten Chunk, Sub-Agent-Spans Schema Validation plus ihren eigenen Tool-Correctness-Score, Tool-Spans Error Rate und Latency.
  • Tool-Result-Interpretation: Geben Sie dem Agenten einen korrekten, aber schwer interpretierbaren Tool Output (eine leere Liste, einen Partial Match, einen veralteten Timestamp) und prüfen Sie, was er als Nächstes tut. Ein Tool kann korrekt sein, während der Agent es falsch liest. Dieser Fehler wird zwei Schritte später sichtbar.
  • Failure Attribution: Der sichtbare Fehler liegt meist downstream vom eigentlichen Fehler. Ordnen Sie ihn dem frühesten Span zu, dessen Output bereits falsch war, und nicht dem Schritt, der den Error ausgelöst hat.

Auch hier zahlt sich die Compounding-Mathematik aus dem Einstieg aus. Wenn 20 Schritte isoliert betrachtet gut aussehen und der Run trotzdem meistens fehlschlägt, zeigen Ihnen die Pass-Raten pro Span, welcher Schritt tatsächlich mit 95 % und welcher mit 70 % läuft.

Das Trace-to-Eval-Flywheel

Analysieren Sie zuerst Production-Fehler, bevor Sie zusätzliche Eval-Fälle brainstormen.

Der Loop:

  1. Erfassen Sie den vollständigen Trace.
  2. Labeln Sie, was fehlgeschlagen ist.
  3. Gruppieren Sie ähnliche Fehler.
  4. Behalten Sie pro Cluster ein repräsentatives Golden.
  5. Versionieren Sie das Dataset.
  6. Führen Sie es in CI aus.
  7. Bewerten Sie weiterhin gesampelte Production Traces online.

Das begleitende Repository trace2evals implementiert den vollständigen Loop für einen fehlerhaften Support Agent. Es erfasst OpenTelemetry-GenAI-Spans, erkennt Fehler mit deterministischen Regeln, dedupliziert Fälle in ein versioniertes Golden Dataset und führt jedes Golden in CI erneut aus. Das Default-Backend ersetzt das Model durch deterministische Regeln, die die Entscheidungen des fehlerhaften Agents nachstellen. Dadurch reproduziert make demo den gesamten Loop offline ohne API Key. Mit gesetztem API Key steuern dieselben Commands ein echtes Model.

Fehler mit Error Analysis finden

Hamel Husain und Shreya Shankar beschreiben für genau diesen Schritt einen Error-Analysis-Workflow; Hamels Field Guide führt ihn praktisch durch. Die ersten beiden Schritte übernehmen ihre Bezeichnungen aus der qualitativen Forschung, die Methode ist jedoch unkompliziert: Traces lesen, Notizen machen, Muster benennen.

  1. Open Coding: Lesen Sie 30 bis 50 echte Traces und notieren Sie frei, was schiefgelaufen ist.
  2. Axial Coding: Clustern Sie diese Notizen in fünf oder sechs benannte Fehlerkategorien.
  3. Alles labeln anhand der Taxonomie.
  4. Metriken erstellen für die größten Kategorien.

Beginnen Sie nicht mit Labels wie reasoning_issue oder tool_problem. Sie sind zu vage zum Testen. Verwenden Sie Labels wie missing_identity_verification, date_argument_mismatch, retried_same_tool_after_429 oder stopped_before_database_update. Ein derart spezifisches Label sagt Ihnen genau, was der Regressionstest prüfen muss.

Vor dem Promotion-Schritt deduplizieren

Der Trace-Mining-Loop hat eine Falle: jeden fehlerhaften Trace für immer hinzuzufügen. Dadurch entsteht ein großes, teures und enges Dataset. Es besteht dann auf Near-Duplicates aus dem März, verpasst aber im Juni die neue Form desselben Bugs.

Gruppieren Sie zuerst. Übernehmen Sie pro Cluster ein repräsentatives Golden. Speichern Sie die zugehörigen Trace-IDs in den Metadaten, damit ein Reviewer die Production-Evidence später untersuchen kann.

Wenn ein Failure Cluster nach einem Fix erneut auftritt, hat der Regression Case nicht generalisiert. Clustern Sie neu und erweitern Sie das Golden, statt 15 punktuelle Beispiele hinzuzufügen.

Das Dataset versionieren

Versionieren Sie Datasets genauso wie Prompts und Code. Wenn sich etwas Wesentliches ändert (Model, Prompt, Tool Schema, Judge Prompt oder App-Verhalten), möchten Sie dieselbe Dataset-Version davor und danach ausführen.

Das CI-Gate sollte Folgendes pinnen:

  • Dataset-Version
  • App-Version
  • Prompt-Version
  • Judge Model
  • Judge Prompt
  • Evaluator-Code-Version

Wenn sich eines davon ändert, wird Ihr Vorher-Nachher-Vergleich unscharf. Eine goldens-v3.json-Datei in Git reicht bei kleinem Umfang aus. Tool-native Snapshots in Langfuse, Phoenix, Braintrust oder LangSmith helfen, sobald das Dataset kollaborativ gepflegt wird.

CI gaten

Eine fehlschlagende Metrik muss zu einem fehlschlagenden Build werden, sonst ist die Eval Suite nur ein Dashboard, das niemand liest.

Der Test sollte den aktuellen Agenten erneut gegen den Golden Input ausführen. Er sollte nicht lediglich den alten fehlgeschlagenen Trace abspielen (Skizze; die ausführbare Version befindet sich im begleitenden Repository):

@pytest.mark.parametrize("golden", GOLDENS, ids=[item["id"] for item in GOLDENS])
def test_agent_regression(golden: dict) -> None:
    answer, fresh_trace = run_agent_and_capture_trace(golden["input"])

    refired = set(flag_failures(fresh_trace)) & set(golden["failure_modes"])
    assert not refired, f"failure mode regressed: {sorted(refired)}"

    assert tool_correctness(
        called=[call["name"] for call in fresh_trace["tool_calls"]],
        expected=golden["expected_tools"],
        mode=golden.get("tool_match", "in_order"),
    ) >= golden.get("tool_threshold", 1.0)

Diese Unterscheidung wird leicht übersehen. Die Aufgabe des Datasets besteht darin, die nächste Version des Agents dabei zu erwischen, wie sie einen alten Fehler wiederholt – nicht darin, den Fehler selbst zu archivieren.

Den Judge kalibrieren, bevor Sie ihm vertrauen

LLM-as-Judge ist hilfreich. Man kann sich damit aber auch leicht selbst täuschen.

G-Eval fordert einen Judge auf, vor dem Scoring explizite Rubric-Schritte zu formulieren. Anschließend summiert er jedes Rating-Level, gewichtet mit seiner Token-Wahrscheinlichkeit (score=∑ip(si) si\text{score} = \sum_i p(s_i)\,s_iscore=∑i​p(si​)si​). Dieses Protokoll stimmte besser mit menschlichen Ratings überein als die älteren automatischen Metriken, die es ersetzte.

Der wahrscheinlichkeitsgewichtete Schritt benötigt Judge-Logprobs, die einige gehostete Models nicht bereitstellen. Das übergeordnete Ergebnis spricht weiterhin für einen expliziten Rubric-Pfad statt eines bloßen Scores.

MT-Bench zeigte, dass GPT-4 ungefähr so häufig mit menschlichen Präferenzen übereinstimmte, wie Menschen untereinander übereinstimmen. Dieses Ergebnis trug dazu bei, LLM Judging zum Mainstream zu machen. Spätere Arbeiten zeigten Bias durch Position, Länge und Self-Preference. Judge Scores können sich außerdem ändern, wenn sich Prompt oder Model-Version ändern.

JudgeBench erstellte Antwortpaare, bei denen eine Antwort in überprüfbarem Wissen, Reasoning, Mathematik oder Code objektiv falsch war. Mit einem einfachen Judge Prompt erreichte GPT-4o 50,9 % – kaum mehr als einen Münzwurf. Claude 3.5 Sonnet, der beste getestete Judge ohne Reasoning, kam auf 64,3 %, während o3-mini bei hohem Reasoning-Aufwand 80,9 % erreichte. Selbstbewusste, aber falsche Antworten bleiben für einen Judge schwierig, der vor dem Grading nicht Reasoning betreibt.

Betrachten Sie den Judge als Messinstrument: Kalibrieren Sie ihn anhand menschlicher Labels, bevor er irgendetwas bewertet, und überprüfen Sie ihn erneut, sobald sich Judge Model oder Prompt ändern.

Wenn ein Judge erforderlich ist, strukturieren Sie das Verdict. Schema-Guided Reasoning (SGR) definiert den Reasoning-Pfad des Judges als Pydantic-Schema. Structured Outputs oder Constrained Decoding erzwingen anschließend Felder wie evidence, passed_criteria, failed_criteria, failure_mode und score.

Platzieren Sie Evidence-Felder vor dem Score. Der Judge wendet dann in jedem Run und über alle kompatiblen Models hinweg dieselben vordefinierten Rubric-Stufen in derselben Feldreihenfolge an. Ein Reviewer kann benannte Felder inspizieren, statt einen Absatz zu parsen. CI kann ein stabiles JSON-Objekt diffen, während das Calibration Set zeigt, bei welcher Rubric-Stufe die Abweichung vom Human Label auftrat.

Ein strukturiertes Verdict kann auch die Kostenkurve verändern. Betrachten Sie ein günstigeres Model als Kandidaten, nicht als automatischen Ersatz. Führen Sie es über dasselbe Human-Labeled Calibration Set aus. Vergleichen Sie Agreement, False-Pass-Rate und False-Fail-Rate mit dem größeren Judge. Verwenden Sie es nur für Routinefälle, wenn es die von Ihrer Anwendung gesetzten Schwellenwerte erfüllt. Behalten Sie den größeren Judge für Disagreements, High-Risk-Fälle oder Calibration Runs.

Checkliste für Judge Hygiene:

  1. Bevorzugen Sie, wo möglich, binäres Pass/Fail. Fünf-Punkte-Skalen suggerieren eine Scheingenauigkeit.
  2. Labeln Sie 30 bis 50 Trajectories von Hand, bevor Sie die finale Rubric schreiben.
  3. Messen Sie die Übereinstimmung zwischen Judge und Menschen mit Cohens Kappa (um Zufallsübereinstimmung korrigierte Übereinstimmung; ein Judge, der immer „Pass“ sagt, liegt nahe null) oder mit einfacher TPR/TNR.
  4. Zerlegen Sie grobe Kriterien. „Hat der Agent vor dem Refund Tool Call die Identität verifiziert?“ ist besser als „War die Trajectory gut?“
  5. Geben Sie das Verdict über ein SGR-Schema mit Evidence, Failed Criteria, Failure Mode und Score aus.
  6. Verwenden Sie nach Möglichkeit einen Judge aus einer anderen Model-Familie als der Generator.
  7. Randomisieren Sie die Reihenfolge bei Paarvergleichen und mitteln Sie beide Richtungen.
  8. Bestrafen Sie nicht belegte Länge in der Rubric. Eine längere Antwort ist nicht automatisch besser.
  9. Pinnen Sie Judge Model, Prompt, Dataset, Schema und App-Version.
  10. Kalibrieren Sie nach Änderungen an Model, Prompt, Tool, Policy oder Schema neu.

Für High-Stakes-Scores sollten Sie statt eines einzelnen großen Judges eine kleine Jury einsetzen. PoLL testete ein Panel kleinerer Judges aus disjunkten Model-Familien und aggregierte deren Verdicts. Über sechs Datasets hinweg stimmte das Panel besser mit menschlichen Bewertungen überein als ein einzelner GPT-4-Judge. Außerdem vermied es den Self-Preference-Bias des einzelnen Judges und kostete mehr als siebenmal weniger. Behalten Sie Human Review für Entscheidungen bei, die Geld, Zugriff, Sicherheit oder Compliance betreffen.

Wenn ein Judge bei Ihrer Aufgabe eine Kappa von 0,55 mit Menschen erreicht, verwenden Sie ihn nicht, um Deployments zu blockieren. Nutzen Sie ihn zum Sortieren von Review Queues. Liegt er bei etwa 0,75 und sind die Fehlerkosten moderat, lässt sich ein CI-Gate deutlich besser verteidigen.

Guardrails blockieren inline, Online Evals beobachten danach

Diese beiden Konzepte werden verwechselt, weil beide Scores erzeugen. Der Unterschied ist die Platzierung: inline im Request Path, vor dem Release oder nach der Antwort.

Guardrails laufen inline. Sie sind schnell und für den User sichtbar. Ein Guardrail kann einen Tool Call blockieren, PII redigieren, Prompt Injection ablehnen oder vor dem Verlassen Ihres Systems einen Retry erzwingen. Ein False Positive ist ein Production Bug. Ein False Negative ist leiser und schlimmer: Schema-, Range- und Policy-Checks sind tatsächlich deterministisch, Injection- und PII-Erkennung sind jedoch Classifier. Behandeln Sie deren Fehlklassifikationen als erwartbar und lassen Sie ein asynchrones Eval beobachten, was sie durchlassen.

Offline Evals laufen vor dem Release. Sie sind reproduzierbar. Sie gaten Prompts, Models, Tools, Retriever und Policies gegen ein fixes Dataset.

Online Evals laufen nach der Antwort, meist auf gesampeltem Traffic. Sie können langsamere LLM Judges verwenden, weil sie nicht im Latency Path liegen. Ihre Aufgabe ist es, Drift zu erkennen, neue Failure Cluster zu finden und das nächste Offline Dataset zu speisen.

Wird die Platzierung falsch gewählt, entstehen in beiden Richtungen Probleme:

  • Ein Judge im Request Path erhöht die Latency und bringt eine neue Flakiness-Quelle hinzu.
  • Ein Guardrail, das auf asynchrones Scoring verschoben wird, lässt Policy-Verstöße die User erreichen.

Für Systeme mit hohem Volumen sollten Sie ein kleines Sample mit einem stärkeren Judge und ein breiteres Sample mit günstigeren Classifiers bewerten. Alarmieren Sie bei Clustern und Confidence Bounds, nicht bei einem einzelnen verrauschten Punktschätzer.

Tooling-Entscheidungen

Kein einzelnes Tool beherrscht den gesamten Loop. Die meisten Production Stacks verwenden zwei Komponenten: einen Trace Store und einen CI-/Eval-Runner.

Die Trade-off-Hinweise beschreiben, wo Kosten entstehen, nicht wie hoch sie sind. Pricing-Seiten ändern sich, und Vendors zählen unterschiedliche Einheiten: Traces, Observations, Spans, Scores, User, Retention oder verarbeitete Daten. Prüfen Sie die aktuellen Preise erneut, bevor Sie sich festlegen.

Entscheidungshilfen:

  • Self-Hosted Tracing mit OTel-Portabilität erforderlich: Starten Sie mit Phoenix oder Langfuse.
  • Code-First-CI-Gate erforderlich: Starten Sie mit DeepEval.
  • Bereits auf LangGraph festgelegt: LangSmith ist komfortabel.
  • Managed PR Regression Review gewünscht: Braintrust ist schwer zu übertreffen.
  • Security- und Red-Team-Fälle dominieren: Promptfoo ist das fokussierte Tool.
  • Safety Research oder kontrollierte Benchmark-Arbeit: Inspect AI passt besser.

Die Tool-Wahl ist zweitrangig. Wenn Production-Fehler nicht zu Testfällen werden, bezahlen Sie hauptsächlich für Trace Storage.

Praktische Rollout-Checkliste

Bauen Sie die Evidence Pipeline auf, bevor Sie den Metrik-Stack erweitern. Entscheiden Sie zunächst, woher die Beispiele kommen.

  1. Sammeln Sie zuerst historische Runs. Wenn der Agent bereits existiert, erfassen Sie Traces, Support-Tickets, Bug Reports, Thumbs-Down-Sessions, manuelle QA-Transkripte und Dogfooding-Notizen, bevor Sie die Implementierung ändern. Wenn der Agent noch nicht existiert, loggen Sie ab dem ersten Tag jeden Prototype- und manuellen Test-Run.

  2. Instrumentieren Sie die Trace-Form. Erfassen Sie Messages, Tool Calls, Argumente, Tool Outputs, Errors, Token Counts, Latency, Cost, User Feedback, App-Version, Prompt-Version, Model-Version, Tool-Schema-Version und den finalen Environment State. Verwenden Sie OpenTelemetry GenAI Conventions oder OpenInference-ähnliche Spans, wenn Sie Portabilität benötigen. Verwenden Sie Langfuse, LangSmith, Phoenix oder Braintrust, wenn Sie sofort eine Trace-UI und einen Dataset-Workflow benötigen.

  3. Machen Sie aus echten Fehlern Seed Cases. Lesen Sie die Traces, bevor Sie sie mit einem Model zusammenfassen. Speichern Sie für jeden nützlichen Fehler den Input, die Source Trace ID, den erwarteten State, die erwarteten Tool-Invarianten, den Failure Mode, die Severity und die Reviewer-Notiz. Langfuse kann Dataset Items mit Production Traces verknüpfen; LangSmith kann Datasets aus getraceten Runs erstellen. Bewahren Sie den Source Link auf, damit der Fall auditierbar bleibt.

  4. Wenn keine Historie existiert, generieren Sie Cold-Start-Fälle. Bitten Sie ein LLM, aus Product Requirements, Policies, Tool Schemas, State Machines und Support-Macros Aufgaben zu erstellen. Decken Sie Happy Paths und Fehler ab, etwa falsche Berechtigungen, fehlende Identity Checks, veraltete Tool Results, mehrdeutige Datumsangaben, Retries nach Rate Limits und widersprüchliche Tool Outputs.

  5. Vertrauen Sie Synthetic Cases erst nach Human Review. Synthetische Beispiele sind für Coverage nützlich, nicht für Truth. Markieren Sie sie mit source: synthetic und verlangen Sie, dass ein Reviewer das erwartete Outcome freigibt. Führen Sie nach Möglichkeit einen bekannten Good Reference Path aus und verwenden Sie unterschiedliche Model-Familien zur Erstellung des Falls und zur Bewertung des Ergebnisses.

  6. Bauen Sie ein kleines, ausgewogenes Dataset. Nehmen Sie Erfolge, Fehler, Refusals, Grenzfälle, Long-Turn-Fälle, Policy-sensitive Fälle und gültige alternative Pfade auf. Machen Sie das Golden nicht zum „exakten alten Transkript“. Das Golden sollte das erforderliche Outcome, zulässige Invarianten und den Failure Mode kodieren.

  7. Fügen Sie zuerst deterministische Checks hinzu. Erforderliche Tool-Reihenfolge, wenn sie Policy ist, erforderliche Argumente, Schema Validation, Final-State-Diffs, Loop-Limits, Token- und Latency-Grenzen sowie aufgabenspezifische Invarianten sollten vor jedem Judge ausgeführt werden.

  8. Fügen Sie einen SGR-förmigen Judge hinzu. Verwenden Sie ihn nur für den Teil, der Interpretation erfordert. Kalibrieren Sie ihn anhand von Human Labels. Wenn er Good und Bad Examples im Calibration Set nicht trennen kann, korrigieren Sie die Rubric, bevor Sie ihn in CI integrieren.

  9. Verbinden Sie den Loop. Führen Sie die kleine Offline Suite in CI aus, die größere Suite vor dem Release, bewerten Sie gesampelten Production Traffic online und übernehmen Sie wiederkehrende Online Failure Cluster in das Offline Dataset.

Ihre erste Eval Suite wird auf langweilige Weise falsch sein. Shippen Sie sie trotzdem. Eine Suite, die Sie täglich ausführen, lässt sich leichter verbessern als ein perfektes Design-Dokument, das niemals einen fehlerhaften PR blockiert.
