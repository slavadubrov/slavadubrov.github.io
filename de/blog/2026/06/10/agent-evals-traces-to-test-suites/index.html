Bewertung von AI Agents in der Produktion: Vom Trace bis zu Test-Suites

Ein Chatbot liefert Ihnen eine einzige Antwort zur Bewertung. Ein Agent hingegen stellt Ihnen einen gesamten Entscheidungsbaum zur Verfügung: Pläne, Tool Calls, Wiederholversuche sowie den Zeitpunkt, an dem er entschied, dass die Arbeit abgeschlossen ist.

Dieser Unterschied erfordert eine andere Bewertungsmethode. Eine Endantwort mag korrekt erscheinen, selbst wenn der Agent ein erforderliches Tool übersprungen hat, einen Call 17 Mal wiederholt hat, ein Ergebnis falsch interpretiert hat oder einen Pfad verfolgt hat, der von den Produktionsrichtlinien verboten wird. Eine rein auf die Antwort ausgerichtete Bewertung verschleiert solche Fehler.

Zusammenfassung: Die Bewertung von Agents benötigt drei Ebenen: Ergebnismetriken, Trajektoriemetriken und Komponentenmetriken. Bauen Sie Ihr Verfahren um folgenden Loop auf: Trace -> Labelierung -> Clustering -> Deduplizierung -> versioniertes Datensatz -> CI-Gate -> Online-Überwachung. Verwenden Sie deterministische Prüfungen für die Reihenfolge der Tools, Argumente, Schleifen und Invarianten. Setzen Sie LLM-Bewerter nur ein, wenn die Prüfung auf Interpretation angewiesen ist, gestalten Sie diese Bewerter mithilfe von Schema-Guided Reasoning (SGR) und kalibrieren Sie sie anhand menschlicher Labels, bevor man ihnen vertraut.

Warum Agent-Bewertungen anders sind

Herkömmliche LLM-Bewertungen bewerten in der Regel nur ein Eingabeausgabepaar: Relevanz, Treue, Korrektheit, Sicherheit – gegebenenfalls auch Stil. Agents hingegen beinhalten Planung, Tool Calls, Wiederholversuche sowie Abschlussprüfungen, wodurch jeder Schritt zu einem potenziellen Versagenspunkt wird.

Nehmen wir einen Refund-Agenten. Der Transkript kann gut enden, während der Trace fehlerhaft ist:

lookup_order -> issue_refund -> final_answer

Die Ausgabe-Bewertung bestätigt Erfolg. Eine Trajektorie-Bewertung sollte hingegen fehlschlagen, da verify_identity zuvor nie ausgeführt wurde issue_refund. Bei Agents, die Tools nutzen, dienen Bewertungen, die nur auf die Antwort achten, lediglich als Schnelltests: Sie erkennen totale Ausfälle, übersehen aber alles Weitere.

Es gibt ein weiteres Problem: Fehler kumulieren sich. Wenn ein Workflow 20 erforderliche Schritte enthält, von denen jeder unabhängig erfolgreich sein muss und jeder denselben Zuverlässigkeitsgrad von 95 % aufweist, liegt die Gesamterfolgsrate bei etwa 36 %:

0.9520≈0.360.95^{20} \approx 0.360.9520≈0.36

Daher kann ein Agent in isolierten Prüfungen solide erscheinen und dennoch bei den meisten vollständigen Ausführungen versagen. Der Fehler liegt in der Regel irgendwo dazwischen, und seine Aufdeckung erfordert eine Sicht auf die Komponentenebene – nicht erneute Betrachtung der Antwort.

Zwei Forscherteams haben Zahlen zu diesem Phänomen ermittelt.

tau-bench stellt Agenten Aufgaben im Bereich Flugzeug- und Einzelhandelskundenservice zur Verfügung. Der Agent kommuniziert mit einem simulierten Benutzer, ruft APIs auf und muss dabei die Branchenrichtlinien befolgen. Nach dem Gespräch prüft der Bewertungsmechanismus, ob die Datenbank den annotierten Zielzustand erreicht hat. Selbst ein plausibles Transkript mit falschen Zeilen führt zum Scheitern.

Nach dieser Bewertungschart schaffte sogar GPT-4o weniger als die Hälfte der Aufgaben. In der Veröffentlichung wurde außerdem pass^k eingeführt: Dasselbe Task wird k Mal ausgeführt, und ein Erfolg wird nur dann gezählt, wenn der Agent in allen k Durchläufen erfolgreich ist.

Die bei einer einzigen Ausführung noch akzeptablen Ergebnisse im Einzelhandel sanken bei k = 8 auf unter 25 %. Derselbe Agent musste dieselbe Aufgabe acht Mal bearbeiten und erzielte dabei meist unterschiedliche Ergebnisse. Eine Bewertung nach nur einem Durchlauf kann diese Inkonsistenzen nicht aufzeigen.

MAST untersucht die Ursachen für das Scheitern von AI Agents. Die Autoren annotierten mehr als 1.600 Ausführungsprotokolle aus sieben gängigen Multi-Agent-Frameworks und ordneten die Fehler in 14 wiederkehrende Muster ein. Zu diesen gehören vage definierte Rollen (Systemdesign), Situationen, in denen ein Agent die Berichte eines anderen ignoriert (Inter-Agent-Misalignment), sowie das Erklären eines Erfolgs ohne Überprüfung des Ergebnisses (keine Verifizierung). Solche Fehler betreffen vor allem Prompts, die Orchestrierungslogik sowie fehlende Kontrollmechanismen im sogenannten Harness. Ein leistungsstärkeres Basismodell kann keine Verifizierungsstufe ausführen, die ursprünglich gar nicht implementiert wurde; daher muss das Bewertungsziel den um das Modell herum liegenden Harness mit einschließen.

Der Adoptionsunterschied

Die Umfrage von LangChain zeigt, dass viele Befragte bereits die Rohdaten für bessere Evaluierungen besitzen: 89 % gaben an, über einige Formen der Observability zu verfügen, während 52,4 % Offline-Evaluierungen durchführten und 37,3 % Online-Evaluierungen.

Auch die Umfrage State of Agent Engineering weist aus, dass 57,3 % der Befragten bereits Agenten in der Produktion einsetzen. Bei der Frage nach den Hindernissen für die Produktion nannten 32 % Qualitätsschwächen und 20 % Latenzprobleme als Gründe. Es handelt sich dabei um eine Umfrage unter den Anbietern selbst, nicht um eine Umfrage aller Agent-Teams, doch sie macht einen relevanten Unterschied zwischen der Datenerfassung und einer systematischen Bewertung deutlich.

Dadurch befinden sich die Teams in einem schwierigen Zwischenzustand: Sie können zwar nachträglich fehlerhafte Ausführungen analysieren, senden aber dennoch denselben Fehler zweimal aus. Jeder diagnostizierte Produktionsfehler sollte ein Ausführungsprotokoll, eine Kennzeichnung, einen Datensatzeintrag sowie einen Bewertungsfaktor hinterlassen. Wiederholte Fehler sollten in das Regressionstest-Set aufgenommen werden.

Metriken nach Fehlermodus auswählen

Die richtige Metrik hängt vom Fehlermodus ab und nicht vom verwendeten Framework. Eine nützliche Einteilung umfasst drei Bereiche:

  1. Ergebnis-basierte Evaluierungen beantworten die Frage, ob die Aufgabe erfolgreich war.
  2. Bahn-basierte Evaluierungen prüfen, ob der genutzte Weg gültig, effizient und mit den Richtlinien vereinbar war.
  3. Komponenten-basierte Evaluierungen identifizieren, welche Tool, Retriever, Unteragent oder Entscheidungsschritt versagt hat.

Jeder dieser Bereiche kann entweder offline anhand fester, wiederaufrufbarer Fälle vor der Veröffentlichung oder online anhand ausgewählter Produktionsprotokolle nach der Antwort durchgeführt werden. Der Abschnitt „Guardrails“ erläutert diese Einteilung im Detail. Offline-Evaluierungen können Goldstandard-Daten erfordern, während Online-Evaluierungen eher auf Invarianten, Verteilungen sowie asynchronen Prüfungen setzen sollten, die außerhalb des Request-Pfads liegen.

Korrektheit der Tool-Aufrufe

Die Korrektheit der Tool-Aufrufe vergleicht die tatsächlich aufgerufenen Tools mit den erwarteten Tools. Wählen Sie die gewünschte Strenge bewusst aus:

  • Exakte Übereinstimmung: Die Sequenz muss genau übereinstimmen. Verwenden Sie dies, wenn die Reihenfolge eine Richtlinie ist, z. B. lookup_order -> verify_identity -> issue_refund.
  • In Ordnung liegende Übereinstimmung: Die notwendigen Tools müssen in der korrekten relativen Reihenfolge erscheinen, zusätzliche unbedenkliche Aufrufe sind jedoch zulässig.
  • Beliebige Reihenfolge: Die notwendigen Tools müssen vorhanden sein, doch die Reihenfolge darf variieren.

Ein kleiner lokaler Bewertungsfunktion reicht bereits zum Start aus:

from collections import Counter


def tool_correctness(called: list[str], expected: list[str], mode: str = "in_order") -> float:
    if not expected:
        return 1.0
    if mode == "exact":
        return float(called == expected)
    if mode == "any_order":
        matched = sum((Counter(called) & Counter(expected)).values())
        return matched / len(expected)

    rows = [[0] * (len(expected) + 1) for _ in range(len(called) + 1)]
    for i, tool in enumerate(called):
        for j, wanted in enumerate(expected):
            if tool == wanted:
                rows[i + 1][j + 1] = rows[i][j] + 1
            else:
                rows[i + 1][j + 1] = max(rows[i][j + 1], rows[i + 1][j])
    return rows[-1][-1] / len(expected)


called = ["lookup_order", "check_refund_policy", "issue_refund"]
expected = ["lookup_order", "verify_identity", "issue_refund"]

print(round(tool_correctness(called, expected, "exact"), 3))     # 0.0
print(round(tool_correctness(called, expected, "in_order"), 3))  # 0.667

Der Wert von in_order gibt den Recall der längsten gemeinsamen Teilfolge an – also den Anteil der erforderlichen Sequenz, der im richtigen Aufbau erhalten blieb. Dabei werden bestimmte Aspekte ignoriert. Unrelevanten Tool-Aufrufen wird dieser Wert nicht verringert, sodass ein AI Agent hier einen Wert von 1,0 erreichen kann, selbst wenn er doppelt so viele Aufrufe vornimmt wie nötig. Wenn zusätzliche Aufrufe Kosten verursachen oder den Zustand des Agents verändern, sollte man den Precision-Wert gleichzeitig betrachten (Anzahl der korrekt abgewickelten Aufrufe geteilt durch die Gesamtanzahl der Aufrufe) und beide Werte zusammen analysieren. Der Recall zeigt auf, welche Schritte fehlen, während der Precision-Wert darauf hinweist, ob der Agent vom Ziel abweicht.

Die Metrik DeepEval’s Tool Correctness metric stellt dieselben Einstellmöglichkeiten über should_consider_ordering und should_exact_match zur Verfügung.

Korrektheit der Argumente

Der Einsatz des falschen Tools mit den richtigen Argumenten ist oft schlimmer als der Einsatz des richtigen Tools, da die Ausführungsprotokolle dann normal erscheinen.

Bei einfachen Fällen sollten JSON-Schemata sowie exakte Werte überprüft werden. Bei semantischen Aufgaben sollten die erwarteten Argumente gespeichert und die Abweichungen bewertet werden:

{
    "trace_id": "tr_2417",
    "input": "Reschedule order A-100 for next Friday.",
    "expected_tools": ["lookup_order", "reschedule_delivery"],
    "expected_arguments": {
        "reschedule_delivery": {
            "order_id": "A-100",
            "date": "2026-06-19"
        }
    }
}

Eine Metrik, die nur den Tool-Name berücksichtigt, kann Fälle wie 2026-06-17 nicht erkennen, in denen die Strategie stattdessen 2026-06-19 erfordert. Daher muss das Dataset auch die Argumente speichern.

Der damit verbundene Wert lautet Parameter-Match – er gibt an, welcher Anteil der erwarteten (tool, key, value)-Tripel vom AI Agent korrekt verarbeitet wurde.

def argument_correctness(called_args: dict, expected_args: dict) -> float:
    total = matched = 0
    for tool, params in expected_args.items():
        for key, want in params.items():
            total += 1
            if called_args.get(tool, {}).get(key) == want:
                matched += 1
    return matched / total if total else 1.0

Genaue Gleichheit ist für IDs, Enums und Datumswerte angemessen. Für Freitexte und Fließkommazahlen hingegen führt sie zu Fehlern, da == eine korrekte Antwort fälschlicherweise als falsch markiert. Solche Felder sollten nach ihren eigenen Kriterien bewertet werden – beispielsweise durch normierte String-Vergleiche, Datumsverarbeitung oder numerische Toleranzen. Die Metrik bleibt dabei unverändert, ändert sich jedoch je nach verwendetem Vergleichsmechanismus pro Feld.

Effizienz, Schleifen und Sackgassen

Ein AI Agent, der eine Aufgabe nach fünf überflüssigen Tool-Aufrufen abschließt, weist dennoch ein Planungsproblem auf und verursacht höhere Laufkosten.

Kostenlose Indikatoren, mit denen man beginnen sollte, sind:

  • Rate redundanter Aufrufe: Identische Tool-Aufrufe mit denselben Argumenten, die mehr als zweimal wiederholt werden.
  • Anomalien in der Struktur der Ausführungsprotokolle: Plötzliche Anstiege bei Tiefe, Anzahl der Tool-Aufrufe, Anzahl der Tokens, Latenz oder Kosten.
  • Konvergenz des Pfades: Wie nah liegt die Ausführung am kürzesten bekannten gültigen Pfad für die Aufgabe?
  • Richtigkeit der Beendigung: Ob der Agent frühzeitig aufhörte, nach einem Erfolg weiterarbeitete oder ohne die erforderliche Zustandsänderung Erfolg meldete.
  • Befolgung des Plans: Falls der Agent vor dem Handeln einen Plan erstellt, sollte geprüft werden, ob die Ausführungsprotokolle diesem Plan folgen. Ein guter Plan, der ignoriert wird, sowie ein schlechter Plan, der perfekt befolgt wird, führen jeweils aus unterschiedlichen Gründen zum Scheitern; der Unterschied zwischen Plan und Protokollen zeigt anschaulich, welches Problem vorliegt.

Solche Überprüfungen sollten immer möglichst vor der Bewertung durch einen Judge durchgeführt werden. Ein Schleifenerkennungswerkzeug benötigt lediglich einige Zeilen Code und basiert nicht auf einem Modell.

Abschluss der Aufgabe und Bewertung des Ergebnisses

Im Endeffekt lautet die Frage: „Hat der Benutzer genau das erhalten, was er angefordert hat?“

Zwei Ansätze sind hier am effektivsten:

  • Bewertung ohne Referenzdaten: Das Ziel wird aus der Eingabe extrahiert, und es wird geprüft, ob die Ausführungsprotokolle zusammen mit der endgültigen Antwort dieses Ziel erreichen. Dies funktioniert auch im Online-Betrieb, da Produktionsdatenströme selten über vordefinierte „goldene“ Ausgaben verfügen.
  • Bewertung des Zustands der Umgebung: Die finalen Datenbankzeilen, Dateien, Tickets, Buchungen oder anderen Aufzeichnungen werden mit einem annotierten Zielzustand verglichen. Diese Methode ist robuster als die Vergleich mit Transkripten, da AI Agents gültige Pfade finden können, die man nicht explizit definiert hat.

Die zweite Option ist vorzuziehen, sofern sie umsetzbar ist. Der endgültige Zustand stellt den Vertrag dar; das Transkript dient lediglich als Beweismittel.

Zwei Aspekte müssen hier berücksichtigt werden, und zwar aus dem Benchmark, der die Bewertung von Zuständen populär gemacht hat. Tau-Bench kann einem Agenten eine Bestehensnote vergeben, selbst wenn dieser bei bestimmten sinnlosen Aufgaben nichts unternimmt, da der Ausgangszustand bereits das Ziel erfüllte. Zudem berichtete Anthropic über einen Lauf von Opus 4.5, bei dem eine Aufgabe im tau2-Bench aufgrund eines Strategie-Lochs „fehlschlug“, obwohl dieses Loch tatsächlich ein besseres Ergebnis für den Benutzer bedeutete. Die Zustandsbewertung ist zwar besser als das Abgleichen von Transkripten, doch der Zielzustand bleibt weiterhin eine Annotation – und Annotationen enthalten Fehler. Prüfen Sie daher insbesondere die Fälle, die zu leicht bestehen, nicht nur diejenigen, die fehlschlagen.

Das Trace-zu-Eval-Flussrad

Erkennen Sie Produktionsfehler, bevor Sie weitere Evaluierungsfallbeispiele erstellen.

Der Ablauf besteht aus folgenden Schritten:

  1. Erfassen Sie den vollständigen Trace.
  2. Kennzeichnen Sie, was fehlgeschlagen ist.
  3. Gruppieren Sie ähnliche Fehlerfälle.
  4. Bewahren Sie pro Cluster einen repräsentativen „Golden Case“ auf.
  5. Versionieren Sie das Datenset.
  6. Führen Sie es in CI aus.
  7. Setzen Sie kontinuierlich die Bewertung von ausgewählten Produktions-Traces fort.

Das begleitende Repository trace2evals implementiert diesen gesamten Ablauf für einen fehlerhaften Support-Agenten. Es erfasst OpenTelemetry GenAI Spans, erkennt Fehler mithilfe deterministischer Regeln, entfernt Duplikate in einem versionierten Golden-Set und führt jeden Golden Case erneut in CI aus. Die standardmäßige Skriptversion erfordert keine API-Schlüssel, sodass make demo den Prozess offline nachvollziehen lässt.

Fehler aufspüren durch Fehleranalyse

Hamel Husain und Shreya Shankar beschreiben einen Workflow zur Fehleranalyse, der genau diesem Schritt dient; Hamels Feldführer erklärt ihn detailliert. Die ersten beiden Schritte leihen ihre Bezeichnungen aus der qualitativen Forschung, doch die Methode ist einfach: Lesen Sie die Traces, machen Sie Notizen und benennen Sie die Muster.

  1. Offene Kodierung: Lesen Sie 30 bis 50 echte Traces und schreiben Sie frei formulierte Notizen dazu, was schiefgelaufen ist.
  2. Axiale Kodierung: Gruppieren Sie diese Notizen in 5 bis 6 benannte Fehlerkategorien.
  3. Kennzeichnen Sie alles gemäß der Taxonomie.
  4. Erstellen Sie Metriken für die größten Gruppen.

Beginnen Sie nicht mit allgemeinen Labels wie reasoning_issue oder tool_problem – sie sind zu vage, um getestet zu werden. Verwenden Sie stattdessen spezifischere Labels wie missing_identity_verification, date_argument_mismatch, retried_same_tool_after_429 oder stopped_before_database_update. Ein solch präzises Label gibt Ihnen exakt an, was im Regressionstest überprüft werden sollte.

Duplikate entfernen, bevor Sie etwas weiterverwenden

Der Trace-Mining-Ablauf birgt eine Falle: Jeder schlechte Trace wird ewig hinzugefügt. Dadurch entsteht ein Datenset, das groß, teuer und eng gefasst ist. Es übernimmt nahezu identische Fälle aus März, während neue Formen desselben Fehlers im Juni übersehen werden.

Gruppieren Sie zunächst die Fälle. Wählen Sie pro Cluster einen repräsentativen Golden Case aus. Speichern Sie die entsprechenden Trace-ID‑Werte in den Metadaten, damit ein Prüfer später die Produktionsbelege einsehen kann.

Falls ein Fehlercluster nach einer Korrektur erneut auftritt, hat die Regression nicht generalisiert. Gruppieren Sie erneut und erweitern Sie stattdessen den Golden Case, anstatt 15 zusätzliche Beispiele hinzuzufügen.

Das Datenset versionieren

Versionieren Sie Datensets genauso wie Prompts und Code. Immer dann, wenn sich etwas Bedeutendes ändert – sei es das Modell, der Prompt, das Tool-Schema, der Judge-Prompt oder das Verhalten der Anwendung – sollten Sie dieselbe Datenset-Version vor und nach der Änderung ausführen.

Die CI-Gate sollte folgende Elemente festlegen:

  • Datenset-Version
  • Anwendungs-Version
  • Prompt-Version
  • Judge-Modell
  • Judge-Prompt
  • Version des Evaluator-Code

Wenn eine dieser Änderungen vorgenommen wird, wird der Vergleich vorher/nachher unklar. Ein goldens-v3.json-Datei in Git ist bei kleinen Datensätzen ausreichend. Tool-eigene Snapshots in Langfuse, Phoenix, Braintrust oder LangSmith sind hingegen nützlich, sobald der Datensatz gemeinsam genutzt wird.

Gate CI

Ein fehlerhafter Metrikwert muss zu einem fehlerhaften Build führen – andernfalls dient das Bewertungssystem lediglich als Dashboard, das niemand liest.

Der Test sollte den aktuellen AI Agent mit dem „goldenen“ Eingabedatenpunkt erneut ausführen, anstatt lediglich die alte, fehlgeschlagene Ausführung abzuspielen:

@pytest.mark.parametrize("golden", GOLDENS, ids=[item["id"] for item in GOLDENS])
def test_agent_regression(golden: dict) -> None:
    answer, fresh_trace = run_agent_and_capture_trace(golden["input"])

    refired = set(flag_failures(fresh_trace)) & set(golden["failure_modes"])
    assert not refired, f"failure mode regressed: {sorted(refired)}"

    assert tool_correctness(
        called=[call["name"] for call in fresh_trace["tool_calls"]],
        expected=golden["expected_tools"],
        mode=golden.get("tool_match", "in_order"),
    ) >= golden.get("tool_threshold", 1.0)

Diese Unterscheidung lässt sich leicht falsch verstehen. Die Aufgabe des Datensatzes besteht darin, zu erkennen, ob eine neue Version des AI Agents denselben alten Fehler wiederholt – nicht darin, den Fehler selbst zu archivieren.

Kalibrieren Sie den Bewertungsmechanismus, bevor Sie ihm vertrauen

LLM-as-judge kann dabei helfen. Allerdings ist es auch einfach, sich selbst zu täuschen.

G-Eval verlangt von dem Bewertungsmechanismus, vor der Bewertung explizite Kriterienschritte festzulegen. Anschließend werden die einzelnen Bewertungsebenen nach ihrer Token-Wahrscheinlichkeit (score=∑ip(si) si\text{score} = \sum_i p(s_i)\,s_iscore=∑i​p(si​)si​) gewichtet und summiert. Dieses Verfahren lieferte bessere Ergebnisse bei der Erfassung menschlicher Bewertungen als die älteren automatischen Metriken, die es ersetzt hat.

Für die wahrscheinlichkeitsbasierte Gewichtung sind die Logprobs des Bewertungsmechanismus erforderlich – diese werden jedoch von einigen gehosteten Modellen nicht bereitgestellt. Dennoch unterstützt das Gesamtergebnis weiterhin einen klaren Kriterienweg gegenüber einer rein numerischen Bewertung.

MT-Bench zeigte, dass GPT-4 etwa genauso oft mit menschlichen Präferenzen übereinstimmte wie Menschen untereinander – was dazu beitrug, dass die Nutzung von LLMs für Bewertungen zum Standard wurde. Spätere Studien identifizierten Bias bezüglich Position, Länge und Selbstpräferenz. Zudem können die Bewertungen des Mechanismus schwanken, wenn sich der Prompt oder die Modellversion ändert.

JudgeBench erstellte Antwortpaare, bei denen eine Antwort aufgrund überprüfbarer Fakten in Bereichen wie Wissen, Reasoning, Mathematik und Code objektiv falsch war. GPT-4o erreichte auf dieser Testbasis 50,9 %, während der stärkste getestete Bewertungsmechanismus etwa 64 % erreichte. Zuverlässige, aber falsche Antworten bleiben weiterhin ein schwieriges Problem für modellbasierte Bewertungsmechanismen.

Betrachten Sie den Bewertungsmechanismus als Messinstrument: Kalibrieren Sie ihn zunächst anhand menschlicher Labels, bevor er etwas bewertet, und überprüfen Sie ihn erneut, sobald sich das Modell oder der Prompt ändert.

Falls ein Bewertungsmechanismus erforderlich ist, sollten die Ergebnisse strukturiert sein. Schema-Guided Reasoning (SGR) definiert den Denkweg des Mechanismus als Pydantic-Schema. Structured Outputs oder Constrained Decoding erfordern anschließend Felder wie evidence, passed_criteria, failed_criteria, failure_mode und score.

Platzieren Sie die Belegfelder vor der Bewertung. Dadurch wendet der Mechanismus bei jeder Ausführung und bei jedem kompatiblen Modell dieselben, im Voraus definierten Kriterienschritte in derselben Reihenfolge an. Ein Prüfer kann so direkt auf die benannten Felder zugreifen, anstatt einen Textabschnitt analysieren zu müssen. CI-Systeme können stabile JSON-Objekte vergleichen, während der Kalibrierungssatz zeigt, in welchem Kriterienschritt es zu Abweichungen vom menschlichen Label kam.

Außerdem kann dies die Kostenstruktur beeinflussen. Betrachten Sie günstigere Modelle zunächst als Kandidaten – nicht als automatische Ersatzlösung. Führen Sie sie auf demselben mit menschlichen Labels versehenen Kalibrierungssatz aus und vergleichen Sie deren Übereinstimmungsrate, False-Pass-Rate sowie False-Fail-Rate mit denen des leistungsstärkeren Bewertungsmechanismus. Verwenden Sie solche Modelle nur für Routinefälle, sofern sie die von Ihrer Anwendung festgelegten Schwellenwerte erfüllen. Für Fälle mit Unstimmigkeiten, Hochrisiko-Situationen oder Kalibrierungsausführungen sollten weiterhin die leistungsstärkeren Mechanismen genutzt werden.

Standard-Checkliste zur Hygiene des Bewertungsmechanismus:

  1. Wo immer möglich sollte ein binäres Ergebnis „Bestanden“/„Nicht bestanden“ bevorzugt werden, da Fünf-Punkte-Skalen künstliche Präzision vortäuschen.
  2. Bevor die endgültige Bewertungskriterienliste erstellt wird, müssen 30 bis 50 Trajektorien manuell beschriftet werden.
  3. Die Übereinstimmung zwischen den Bewertern und menschlichen Referenzwerten wird entweder mit Cohen’s Kappa gemessen – wobei die Übereinstimmung auf Zufallsfaktoren korrigiert wird, sodass ein Bewertender, der stets „Bestanden“ gibt, einen nahe null liegenden Wert erhält – oder direkt über TPR/TNR.
  4. Grobe Kriterien sollten in präzisere Unterkriterien aufgeteilt werden. Statt der allgemeinen Frage „War die Trajektorie gut?“ ist beispielsweise die spezifischere Frage „Hat der Agent die Identität vor dem Aufruf des Rückerstattungstools überprüft?“ aussagekräftiger.
  5. Das Urteil soll über ein SGR-Schema mit Belegen, fehlgeschlagenen Kriterien, Fehlerursachen sowie einem Score ausgesendet werden.
  6. Soweit möglich sollte ein Bewertender aus einer anderen Modellfamilie als der Generierende verwendet werden.
  7. Die Reihenfolge der Paarprüfungen muss zufällisiert werden, und anschließend werden die Ergebnisse in beide Richtungen durchschnittlich.
  8. In den Bewertungskriterien sollte eine zu lange Antwort nicht belohnt werden – längere Antworten bedeuten nicht automatisch bessere Leistungen.
  9. Modell, Prompt, Datensatz, Schema sowie App-Version müssen festgelegt werden.
  10. Nach Änderungen am Modell, Prompt, Tool, Policy oder Schema muss eine Neukalibrierung erfolgen.

Für hochkritische Bewertungen ist es sinnvoller, ein kleines Gremium statt eines einzelnen Bewerters einzusetzen. PoLL hat ein Panel aus kleineren Bewertern unterschiedlicher Modellfamilien getestet und deren Urteile zusammengeführt. Bei sechs verschiedenen Datensätzen erzielte dieses Panel bessere Ergebnisse bei der Nachvollziehung menschlicher Entscheidungen als ein einzelner GPT-4-Bewertender. Zudem wurden die Verzerrungen durch die eigene Präferenz des einzelnen Bewerters vermieden, und die Kosten lagen siebenmal niedriger. Für Entscheidungen, die finanzielle Aspekte, Zugriffsmöglichkeiten, Sicherheit oder Compliance betreffen, sollte weiterhin eine menschliche Überprüfung erfolgen.

Falls ein Bewertender bei Ihrer Aufgabe einen Kappa-Wert von 0,55 gegenüber menschlichen Referenzwerten aufweist, sollte er nicht zur Blockierung von Deploys genutzt werden, sondern lediglich zur Sortierung der Überprüfungsqueues. Liegt der Wert bei etwa 0,75 und die Kosten für Fehlerrückmeldungen sind moderat, lässt sich ein CI-Gate deutlich leichter rechtfertigen.

Guardrails laufen inline, Online-Evaluierungen erfolgen danach

Viele verwechseln diese Ansätze, weil beide Scores liefern. Der Unterschied liegt in der Platzierung: Guardrails laufen inline im Anfragepfad, noch vor der Freigabe oder nach der Antwort.

Guardrails laufen inline. Sie sind schnell, deterministisch und für den Benutzer sichtbar. Ein Guardrail kann einen Tool-Aufruf blockieren, personenbezogene Daten maskieren, Prompt-Injection verhindern oder einen Neversuch erzwingen, bevor die Antwort das System verlässt. Ein falscher Positivfall stellt dabei einen Produktionsfehler dar.

Offline-Evaluierungen finden vor der Freigabe statt. Sie sind reproduzierbar und prüfen Prompts, Modelle, Tools, Retrieval-Systeme sowie Policies anhand eines festgelegten Datensatzes.

Online-Evaluierungen laufen nach der Antwort, in der Regel anhand ausgewählter Traffic-Beispiele. Da sie nicht im Latenzpfad liegen, können hier langsamere LLM-Bewertender eingesetzt werden. Ihre Aufgabe besteht darin, Abweichungen zu erkennen, neue Fehlermuster zu identifizieren und diese in den nächsten Offline-Datensatz einzubringen.

Eine falsche Platzierung hat in jedem Fall negative Auswirkungen:

  • Ein Guardrail im Anfragepfad verursacht zusätzliche Latenz und birgt ein neues Risiko für Instabilität.
  • Ein Guardrail, der nur asynchron bewertet wird, ermöglicht es, dass Policy-Verstöße den Nutzern zugänglich gemacht werden.

In Systemen mit hohem Durchsatz sollten kleine Stichproben mit leistungsfähigeren Bewertern und größere Stichproben mit günstigeren Klassifikatoren bewertet werden. Es sollten Warnungen bei Clusterbildung sowie Konfidenzintervallen ausgelöst werden, anstatt sich auf einen einzelnen störanfälligen Wert zu verlassen.

Preislisten ändern sich, und Anbieter berücksichtigen unterschiedliche Faktoren wie Traces, Beobachtungen, Spannungen, Bewertungswerte, Nutzerzahlen, Retention-Raten oder verarbeitete Daten. Überprüfen Sie vor dem Commit immer die aktuellen Preise.

Entscheidungshilfen:

  • Benötigen Sie tracings mit OTel-Portabilität im Selbsthosting? Beginnen Sie mit Phoenix oder Langfuse.
  • Brauchen Sie ein auf Code ausgerichtetes CI-Kontrollmechanismus? Starten Sie mit DeepEval.
  • Sind Sie bereits auf LangGraph angewiesen? LangSmith ist die praktischste Wahl.
  • Wünschen Sie eine verwaltete Überprüfung von PR-Regressionen? Braintrust ist unschlagbar.
  • Spielen Sicherheit und Red-Team-Anwendungen die Hauptrolle? Promptfoo ist das passende Werkzeug.
  • Arbeiten Sie an Sicherheitsforschung oder kontrollierten Benchmark-Tests? Inspect AI eignet sich besser.

Die Auswahl des Tools ist sekundär. Wenn Produktionsfehler nicht zu Testfällen werden, zahlt man hauptsächlich für den Speicherbedarf der Traces.

Praktische Checkliste für die Einführung

Bauen Sie zunächst den Beweispipeline auf, bevor Sie den Metrik-Stack erweitern. Entscheiden Sie dabei zuerst, woher die Beispiele stammen sollen.

  1. Sammeln Sie zunächst historische Ausführungen. Falls der Agent bereits vorhanden ist, holen Sie Traces, Supportanfragen, Fehlerberichte, negative Bewertungssitzungen, Transkripte manueller QA-Prüfungen sowie Notizen aus internen Tests ein, bevor Sie die Implementierung ändern. Ist der Agent noch nicht vorhanden, protokollieren Sie ab dem ersten Tag jedes Prototyps sowie jede manuelle Testausführung.

  2. Die Trace-Struktur instrumentieren. Erfassen Sie Nachrichten, Tool Calls, Argumente, Tool-Ausgaben, Fehler, Token-Zahlen, Latenzzeiten, Kosten, Nutzerfeedback, App-Version, Prompt-Version, Modell-Version, Tool-Schema-Version sowie den endgültigen Zustand der Umgebung. Verwenden Sie dabei die OpenTelemetry GenAI-Konventionen oder OpenInference-basierte Spans, falls Portabilität gewünscht ist. Für eine sofortige Visualisierung der Traces sowie einen Workflow für Datensätze eignen sich Langfuse, LangSmith, Phoenix oder Braintrust.

  3. Reale Ausfälle in Ausgangsfälle umwandeln. Lesen Sie die Traces vor dem Zusammenfassen mit einem Modell durch. Für jeden nützlichen Ausfall speichern Sie die Eingabe, die Quell-Trace-ID, den erwarteten Zustand, die erwarteten Tool-Invarianten, den Ausfallmodus, die Schweregrade sowie eine Anmerkung des Prüfers. Langfuse kann Datensatzelemente mit Produkt-Traces verknüpfen; LangSmith kann aus getrackten Ausführungen Datensätze erstellen. Bewahren Sie die Quellverknüpfung auf, damit der Fall weiterhin nachvollziehbar bleibt.

  4. Falls keine Historie vorhanden ist, Cold-Start-Fälle generieren. Beauftragen Sie ein LLM damit, Aufgaben auf Basis von Produktanforderungen, Richtlinien, Tool-Schemata, State Machines sowie Support-Makros zu entwerfen. Berücksichtigen Sie dabei sowohl erfolgreiche Abläufe als auch Ausfälle wie fehlende Berechtigungen, fehlende Identitätsprüfungen, veraltete Tool-Ergebnisse, unklare Datumsangaben, Wiederholungsversuche nach Rate-Limits sowie widersprüchliche Tool-Ausgaben.

  5. Synthetische Fälle dürfen erst nach Überprüfung durch einen Menschen verwendet werden. Synthetische Beispiele sind zwar hilfreich zur Abdeckung, liefern aber keine Garantie für Richtigkeit. Markieren Sie sie mit source: synthetic und verlangen Sie von einem Prüfer die Freigabe des erwarteten Ergebnisses. Falls möglich, führen Sie einen bekannten, funktionierenden Referenzweg aus und nutzen Sie unterschiedliche Modellfamilien, um den Fall zu erzeugen und das Ergebnis zu bewerten.

  6. Einen kleinen, ausgewogenen Datensatz erstellen. Enthalten Sie darin Erfolge, Ausfälle, Ablehnungen, Grenzfälle, lange Dialoge, policy-sensible Fälle sowie gültige alternative Abläufe. Es sollte sich nicht um das „exakte alte Transkript“ handeln – der Goldstandard muss vielmehr das erforderliche Ergebnis, zulässige Invarianten sowie den Ausfallmodus kodieren.

  7. Zunächst deterministische Checks hinzufügen. Notwendige Reihenfolgen von Tool-Calls (basierend auf Richtlinien), erforderliche Argumente, Schema-Validierung, Vergleiche des Endzustands, Limits für Schleifen, Obergrenzen für Tokens und Latenz sowie task-spezifische Invarianten müssen vor jedem Bewertungsmechanismus ausgeführt werden.

  8. Einen SGR-förmigen Bewertungsmechanismus hinzufügen. Verwenden Sie ihn ausschließlich für die Teile, die Interpretation erfordern. Kalibrieren Sie ihn anhand menschlicher Labels. Falls er auf dem Kalibrierungssatz gute und schlechte Beispiele nicht unterscheiden kann, korrigieren Sie zunächst die Bewertungskriterien, bevor Sie ihn in den CI-Prozess integrieren.

  9. Den Agent Loop verbinden. Führen Sie das kleine Offline-Testset im CI aus, das größere Testset vor der Veröffentlichung, bewerten Sie ausgewählte Online-Verkehrsmuster und führen Sie wiederkehrende Online-Ausfallmuster zurück in den Offline-Datensatz ein.

Ihr erstes Evaluations-Testset wird auf langweilige Weise fehlerhaft sein – senden Sie es trotzdem raus. Ein Testset, das täglich ausgeführt wird, lässt sich leichter beheben als ein perfektes Designdokument, das niemals einen schlechten Pull Request blockiert.
