TL;DR

Agent-Evals benötigen drei Ebenen: Outcome-Metriken, Trajectory-Metriken und Component-Metriken. Wandeln Sie Traces in ein versioniertes Dataset um, führen Sie es in CI aus und überwachen Sie gesampelte Production-Traces. Verwenden Sie deterministische Checks für Tool-Reihenfolge, Argumente, Loops und Invarianten. Setzen Sie LLM Judges nur dort ein, wo der Check Interpretation erfordert, strukturieren Sie diese Judges mit Schema-Guided Reasoning (SGR) und kalibrieren Sie sie gegen Human Labels, bevor Sie ihnen vertrauen.

Warum sich Agent-Evals unterscheiden

Traditionelle LLM-Evals bewerten meist ein einzelnes Input-Output-Paar: Relevanz, Faithfulness, Korrektheit, Safety und möglicherweise Stil. Agents bringen Planning, Tool Calls, Retries und Termination-Checks hinzu, wobei jeder Schritt eine neue Fehlerquelle darstellt.

Nehmen wir einen Refund-Agent. Das Transkript kann erfolgreich enden, während der Trace falsch ist:

lookup_order -> issue_refund -> final_answer

Der Output-Eval ist erfolgreich. Ein Trajectory-Eval sollte fehlschlagen, weil verify_identity nie vor issue_refund ausgeführt wurde. Bei Tool-using Agents können Answer-only-Evals Fehler in der Content-Qualität erkennen, aber sie können nicht belegen, dass der Agent eine gültige Trajectory durchlaufen oder die erforderlichen Side Effects erzeugt hat.

Es gibt ein zweites Problem: Fehler akkumulieren sich. Wenn ein Workflow 20 erforderliche Schritte umfasst, jeder Schritt unabhängig erfolgreich ist und jeder Schritt dieselbe Reliability von 95 % hat, liegt die End-to-End-Success-Rate bei ungefähr 36 %:

0.9520≈0.360.95^{20} \approx 0.360.9520≈0.36

Der Agent kann in isolierten Checks also solide wirken und trotzdem die meisten vollständigen Runs nicht bestehen. Der Bruch liegt normalerweise irgendwo in der Mitte. Ihn zu finden, erfordert Visibility auf Component-Ebene und nicht noch einen weiteren Blick auf die Antwort.

Zwei Research-Teams haben dies quantifiziert.

tau-bench stellt einem Agent Airline- und Retail-Customer-Service-Aufgaben. Der Agent kommuniziert mit einem simulierten User, ruft APIs auf und muss die Domain-Policy befolgen. Nach der Conversation prüft der Grader, ob die Datenbank den annotierten Goal State erreicht hat. Ein plausibles Transkript mit den falschen Rows schlägt daher trotzdem fehl.

Unter diesem Grading löste GPT-4o nur 35,2 % der Airline-Aufgaben und etwas mehr als 60 % der Retail-Aufgaben. Das Paper führte außerdem pass^k ein: die Wahrscheinlichkeit, dass alle k unabhängigen Trials bestehen, gemittelt über die Tasks.

Retail, der einfachere Split, hatte ein pass^8 von unter 25 %. Für einen zufällig ausgewählten Retail-Task und acht unabhängige Trials lag die Wahrscheinlichkeit, dass alle acht Runs erfolgreich waren, unter 25 %. Ein Eval mit nur einem Run kann diese Consistency nicht messen.

MAST untersucht, warum Agents scheitern. Die Autoren entwickelten aus 150 von Hand annotierten Traces eine Taxonomie mit 14 Failure Modes und wandten sie anschließend auf mehr als 1.600 Traces aus 7 populären Multi-Agent-Frameworks an. Die Taxonomie umfasst vage Role Definitions (System Design), dass ein Agent ignoriert, was ein anderer Agent berichtet hat (Inter-Agent Misalignment), und dass Erfolg erklärt wird, ohne das Ergebnis zu prüfen (No Verification). Diese Fehler weisen auf Prompts, Orchestration-Logik und fehlende Checks im Harness hin. Ein stärkeres Base Model kann keinen Verification-Schritt ausführen, der nie implementiert wurde. Das Evaluationsziel muss daher auch den Harness rund um das Model umfassen.

Die Adoption-Lücke

Die Umfrage State of Agent Engineering von LangChain (1.340 Befragte, durchgeführt Ende 2025) deutet darauf hin, dass viele Teams bereits die Rohdaten für bessere Evals besitzen. Demnach verfügten 89 % über irgendeine Form von Observability, 52,4 % führten Offline-Evals aus und 37,3 % Online-Evals.

Die Umfrage berichtet außerdem, dass 57,3 % der Befragten bereits Agents in Production einsetzen. Auf die Frage, was Production blockiert, nannten 32 % Quality und 20 % Latency. Dies ist eine Vendor-Umfrage unter den eigenen Befragten und keine Vollerhebung aller Agent-Teams. Sie zeigt jedoch eine nützliche Lücke zwischen Trace-Sammlung und systematischer Evaluation.

Teams verbleiben dadurch in einem schwierigen Zwischenzustand: Sie können einen fehlerhaften Run im Nachhinein untersuchen und denselben Fehler anschließend trotzdem zweimal ausliefern.

Jeder diagnostizierte Production-Fehler sollte einen Trace, ein Label, eine Dataset-Zeile und einen Scorer hinterlassen. Ein reproduzierbarer Fehler gehört in die Regression-Suite.

Metriken nach Failure Mode auswählen

Die richtige Metrik hängt vom Failure Mode ab, nicht vom Framework. Die sinnvolle Aufteilung umfasst drei Ebenen:

  1. Outcome-Evals beantworten, ob der Task erfolgreich war.
  2. Trajectory-Evals beantworten, ob der Pfad gültig, effizient und Policy-konform war.
  3. Component-Evals beantworten, welches Tool, welcher Retriever, Sub-Agent oder Decision-Step ausgefallen ist.

Jede Ebene kann offline auf festen, replaybaren Cases vor dem Release oder online auf gesampelten Production-Traces nach der Response ausgeführt werden. Der Abschnitt zu Guardrails behandelt diese Aufteilung ausführlich. Offline-Evals können Goldens erfordern: gespeicherte Cases, die ein Input mit dem Outcome, Tool-Invarianten und den Argumenten verbinden, die ein korrekter Run erzeugen muss. Online-Evals sollten Invarianten, Distributionen und asynchrone Checks bevorzugen, die nicht im Request Path liegen.

Beginnen Sie mit deterministischen Metriken. Für fixe Inputs und Code sind sie reproduzierbar und kostengünstig auszuführen. Ihre Regeln können dennoch veralten, wenn sich Tools oder Policies ändern. Versionieren Sie den Scorer daher gemeinsam mit der Specification, die er prüft.

Tool-Call-Correctness

Tool Correctness vergleicht die aufgerufenen Tools mit den erwarteten Tools. Wählen Sie die Strenge bewusst:

  • Exact Match: Die Sequenz muss exakt übereinstimmen. Verwenden Sie dies, wenn die Reihenfolge Policy ist, zum Beispiel lookup_order -> verify_identity -> issue_refund.
  • In-Order Match: Erforderliche Tools müssen in der richtigen relativen Reihenfolge erscheinen; zusätzliche harmlose Calls sind jedoch erlaubt.
  • Any-Order Match: Die erforderlichen Tools müssen erscheinen, die Reihenfolge darf aber variieren.

Für den Anfang genügt ein kleiner lokaler Scorer:

from collections import Counter

def tool_correctness(called: list[str], expected: list[str], mode: str = "in_order") -> float:
    if mode not in {"exact", "in_order", "any_order"}:
        raise ValueError(f"unknown matching mode: {mode}")
    if mode == "exact":
        return float(called == expected)
    if not expected:
        return 1.0
    if mode == "any_order":
        matched = sum((Counter(called) & Counter(expected)).values())
        return matched / len(expected)

    rows = [[0] * (len(expected) + 1) for _ in range(len(called) + 1)]
    for i, tool in enumerate(called):
        for j, wanted in enumerate(expected):
            if tool == wanted:
                rows[i + 1][j + 1] = rows[i][j] + 1
            else:
                rows[i + 1][j + 1] = max(rows[i][j + 1], rows[i + 1][j])
    return rows[-1][-1] / len(expected)

called = ["lookup_order", "check_refund_policy", "issue_refund"]
expected = ["lookup_order", "verify_identity", "issue_refund"]

print(round(tool_correctness(called, expected, "exact"), 3))     # 0.0
print(round(tool_correctness(called, expected, "in_order"), 3))  # 0.667
assert tool_correctness(["issue_refund"], [], "exact") == 0.0
assert tool_correctness([], [], "exact") == 1.0
assert tool_correctness(["a", "b"], ["a", "a", "b"], "any_order") == 2 / 3
try:
    tool_correctness([], [], "typo")
except ValueError:
    pass
else:
    raise AssertionError("unknown modes must fail")

Der in_order-Score ist der Recall der Longest Common Subsequence: Welcher Anteil der erforderlichen Sequenz in der richtigen Reihenfolge erhalten geblieben ist. Beachten Sie, was er ignoriert. Junk Calls senken den Score nicht. Ein Agent kann hier also 1,0 erreichen und trotzdem doppelt so viele Calls ausführen wie nötig. Wenn zusätzliche Calls Kosten verursachen oder den State mutieren, erfassen Sie zusätzlich die Precision (gematchte Required Calls geteilt durch alle Calls) und interpretieren Sie beide Werte gemeinsam. Recall erkennt den fehlenden Schritt, Precision das Wandering. Weder ein Recall-Score von 1,0 noch eine hohe Precision autorisieren zusätzliche Mutations. Prüfen Sie jeden State-Changing Call auf Permissions, Ressource, Argumente und erforderliche vorherige Verification. Bei einer leeren Expected List bedeutet nur der Exact Mode „keine Calls erlaubt“; die anderen Modes enthalten keine positiven Anforderungen.

DeepEvals Tool-Correctness-Metrik stellt dieselben Stellschrauben über should_consider_ordering und should_exact_match bereit.

Argument Correctness

Das richtige Tool mit falschen Argumenten aufzurufen ist oft schlimmer als das falsche Tool aufzurufen, weil der Trace normal aussieht.

Für einfache Fälle validieren Sie JSON Schema und exakte Werte. Für semantische Fälle speichern Sie erwartete Argumente und bewerten Sie die Deltas:

{
    "trace_id": "tr_2417",
    "input": "Reschedule order A-100 for June 19, 2026.",
    "expected_tools": ["lookup_order", "reschedule_delivery"],
    "expected_arguments": {
        "reschedule_delivery": {
            "order_id": "A-100",
            "date": "2026-06-19"
        }
    }
}

Eine Tool-Name-Metrik kann 2026-06-17 nicht erkennen, wenn die Policy 2026-06-19 verlangt. Das Dataset muss daher auch Argumente speichern.

Für diese Illustration mit einem Call pro Tool ist Parameter Match der Anteil der erwarteten (tool, key, value)-Tripel, die der Agent korrekt geliefert hat. Die folgenden Dictionaries sind nur gültig, wenn jedes relevante Tool höchstens einmal aufgerufen wird. Erzeugen Sie sie nicht, indem Sie frühere Calls mit demselben Namen überschreiben: Dadurch würde ein falscher Refund gefolgt von einem korrekten verborgen. Bei wiederholten Calls müssen Sie Call IDs und Reihenfolge erhalten, den vorgesehenen Invocation matchen und jede Mutation separat validieren.

def argument_correctness(called_args: dict, expected_args: dict) -> float:
    total = matched = 0
    for tool, params in expected_args.items():
        for key, want in params.items():
            total += 1
            if key in called_args.get(tool, {}) and called_args[tool][key] == want:
                matched += 1
    return matched / total if total else 1.0

assert argument_correctness({}, {"reschedule_delivery": {"date": None}}) == 0.0
assert argument_correctness({"reschedule_delivery": {}},
                            {"reschedule_delivery": {"date": None}}) == 0.0
assert argument_correctness({"reschedule_delivery": {"date": None}},
                            {"reschedule_delivery": {"date": None}}) == 1.0

Exakte Gleichheit ist für IDs, Enums und bereits auf ein Format normalisierte Daten richtig. Sie ist falsch für Freitext, Floats und Datumswerte in beliebiger Form, bei denen == eine korrekte Antwort als falsch markiert. Bewerten Sie diese Felder nach ihren jeweiligen Regeln: ein Match normalisierter Strings, ein Date Parse oder eine numerische Toleranz. Die Metrik bleibt dieselbe; der Comparator ändert sich pro Feld.

Efficiency, Loops und Dead Ends

Ein Agent, der den Task erst nach fünf redundanten Tool Calls abschließt, weist weiterhin auf ein Planning-Problem hin und verursacht höhere Kosten.

Mit diesen günstigen Signals sollten Sie beginnen:

  • Redundant-Call-Rate: identische Tool Calls mit identischen Argumenten, die mehr als zweimal wiederholt werden.
  • Trace-Shape-Anomalien: plötzliche Anstiege bei Depth, Tool-Call-Count, Token-Count, Latency oder Cost.
  • Path Convergence: Wie nah der Run am kürzesten bekannten gültigen Pfad für den Task liegt.
  • Termination Correctness: Ob der Agent zu früh gestoppt, nach dem Erfolg weitergearbeitet oder Erfolg erklärt hat, ohne die erforderliche State Change auszuführen.
  • Plan Adherence: Wenn der Agent vor dem Handeln einen Plan schreibt, prüfen Sie, ob der Trace diesem Plan gefolgt ist. Ein guter ignorierter Plan und ein schlecht ausgeführter Plan, dem perfekt gefolgt wurde, schlagen beide fehl – aus entgegengesetzten Gründen. Die Differenz zwischen Plan und Trace zeigt, welcher Fall vorliegt.

Führen Sie diese Checks nach Möglichkeit vor einem Judge aus. Ein Loop Detector umfasst nur wenige Zeilen über dem Trace. Er benötigt kein Model.

Task Completion und Outcome Grading

Beim Outcome Grading lautet die Frage: „Hat der User bekommen, worum er gebeten hat?“

Zwei Patterns funktionieren am besten:

  • Referenceless Task-Completion Judging: Extrahieren Sie das Ziel aus dem Input und bewerten Sie, ob Trace plus finale Antwort es erreicht haben. Dies funktioniert online, weil Production Traffic nur selten Golden Outputs besitzt.
  • Environment-State-Grading: Vergleichen Sie die finalen Datenbank-Rows, Files, Tickets, Bookings oder Records mit einem annotierten Goal State. Das ist robuster als Transcript Matching, weil Agents gültige Pfade finden können, die Sie nicht vorab aufgeschrieben haben.

Die zweite Option ist besser, wenn Sie sie umsetzen können. Der Final State ist der Vertrag. Das Transkript ist nur Evidence.

Zwei Caveats sorgen für eine realistische Bewertung. Ein 2025-Audit von agentic Benchmarks stellte fest, dass tau-bench einige Tasks ausschließlich anhand des Database State bewertet. Bei manchen Tasks erfordert das annotierte Outcome weder eine State Change noch einen bestimmten Text. Ein Agent, der nichts tut, kann dann einen Pass erreichen: 38 % im Airline-Split und 6,0 % im Retail-Split bei jedem k. Anthropic berichtete von einem Opus-4.5-Run, der bei einer Booking-Aufgabe in tau2-bench, dem Nachfolger-Benchmark, „scheiterte“. Der Agent fand eine Policy-Lücke, die tatsächlich das bessere Outcome für den User darstellte. State Grading ist besser als Transcript Matching, aber der Goal State ist weiterhin eine Annotation und Annotationen können Fehler enthalten. Auditen Sie auch Cases, die zu leicht bestehen, nicht nur die fehlgeschlagenen.

Benchmark-Versionen und Environments verändern das Ergebnis

Die oben genannten tau-bench-Zahlen erklären die Reliability bei wiederholten Trials; sie stellen keine aktuelle Model-Leaderboard dar. Das gepflegte tau-bench-Repository präsentiert inzwischen tau3-bench, das Knowledge Retrieval und Full-Duplex-Voice hinzufügt. Der Grading-Fix für v1.0.1 vom Juli 2026 verändert die banking_knowledge-Scores: Ergebnisse früherer Versionen sind für diese Domain nicht vergleichbar. Pinnen Sie Task- und Grader-Revisions ebenso wie das Model und bewerten Sie gespeicherte Trajectories neu, wenn eine Annotation korrigiert wird.

Wählen Sie einen Benchmark, der die bereitgestellte Interface-Form abbildet. Text-only Customer-Service-Tests können Interruption Handling in einem Voice-Agent nicht belegen. Knowledge-Retrieval-Tasks benötigen außerdem den Corpus, die Search-Konfiguration und die pro Turn verfügbaren Evidences. Übernehmen Sie diese Task-Formen für lokale Regression-Cases, statt einen Public-Leaderboard-Rang als Release-Kriterium zu verwenden.

Auch der Sandbox ist Teil des Tests. Anthropics Infrastructure-Studie vom Februar 2026 fand bei identischem Model, Harness und identischen Tasks einen Unterschied von sechs Prozentpunkten bei Terminal-Bench 2.0 zwischen strikten und unbegrenzten Resource-Setups. Mehr Headroom reduzierte sowohl Infrastructure Failures als auch die Einschränkungen für unterschiedliche Solution Strategies. Dokumentieren Sie CPU- und RAM-Garantien sowie -Limits, Timeouts, Concurrency, Network Access und den Umgang mit Infrastructure Errors. Berichten Sie diese Fehler separat, ohne sie stillschweigend aus dem Expected-Task-Denominator zu entfernen.

Component-Evals

Outcome- und Trajectory-Metriken zeigen, dass ein Run fehlgeschlagen ist, und ungefähr, wo dies geschah. Component-Evals bewerten einen Span: War der abgerufene Chunk relevant? Hat der Sub-Agent das von seinem Caller erwartete Schema zurückgegeben? Ließ sich die Response des Tools parsen? Verknüpfen Sie den Score mit dem Span und nicht mit dem Run. Dann wird „Welches Tool hat sich diese Woche verschlechtert?“ zu einer Query statt zu einem erneuten Run.

Drei Checks decken den größten Teil ab:

  • Per-Span-Scoring: Führen Sie die zum Span-Typ passende Metrik aus. Retrieval-Spans erhalten Recall und Precision gegen den annotierten Chunk, Sub-Agent-Spans Schema Validation plus ihren eigenen Tool-Correctness-Score, Tool-Spans Error Rate und Latency.
  • Tool-Result-Interpretation: Geben Sie dem Agent ein korrektes, aber ungewöhnliches Tool Output (eine leere Liste, einen Partial Match oder einen veralteten Timestamp) und prüfen Sie, was er als Nächstes tut. Ein Tool kann korrekt sein, während der Agent es falsch liest. Dieser Fehler wird oft erst zwei Schritte später sichtbar.
  • Failure Attribution: Der sichtbare Fehler liegt meist downstream des eigentlichen Fehlers. Ordnen Sie ihn dem frühesten Span zu, dessen Output bereits falsch war, nicht dem Schritt, der den Error ausgelöst hat.

Auch hier greift die Compounding-Mathematik aus der Einleitung. Wenn 20 Schritte isoliert betrachtet gut aussehen, kann der Run dennoch meistens fehlschlagen. Per-Span-Pass-Rates zeigen, welcher Schritt mit 95 % läuft und welcher mit 70 %.

Das Trace-to-Eval-Flywheel

Analysieren Sie zunächst Production Failures, bevor Sie zusätzliche Eval-Cases brainstormen.

Der Loop:

  1. Erfassen Sie genügend Trace-Evidence, um den Fehler zu rekonstruieren, und kontrollieren Sie dabei sensible Inhalte.
  2. Labeln Sie, was fehlgeschlagen ist.
  3. Gruppieren Sie ähnliche Fehler.
  4. Behalten Sie repräsentative Goldens einschließlich Varianten, die unterschiedliche Outcomes benötigen.
  5. Versionieren Sie das Dataset.
  6. Führen Sie es in CI aus.
  7. Scoren Sie weiterhin gesampelte Production-Traces online.

Das begleitende Repository trace2evals demonstriert diesen Workflow mit einem fehlerhaften Support-Agent. Es zeichnet Tool Calls und den Shop State in lokalem OpenTelemetry JSONL auf, erkennt Fehler mit deterministischen Regeln und erzeugt versionierte Review-Kandidaten. Ein Reviewer muss die Expected Outcomes definieren und freigeben, bevor diese als Release-Tests verwendet werden. Die enthaltene Reference-Suite liefert separate, explizite synthetische Task Contracts zur Evaluation neuer Runs.

Führen Sie uv sync --locked und make demo in diesem Repository für das Offline-Beispiel aus. Sein skriptbasiertes Backend reproduziert eingebaute Fehler ohne API-Key. Die optionalen OpenAI-Run-Anweisungen erfordern das Live-Extra, einen API-Key und die explizite Option --backend openai. Die Installation des Extras oder das Setzen eines Keys aktiviert die Live-Ausführung nicht.

Die Demo verwendet synthetische Cases, In-Memory-Tools und ein repository-spezifisches Trace-Schema. Ihr Adapter akzeptiert keine beliebigen OpenTelemetry-Exports. Ein erfolgreicher Suite-Run belegt das geprüfte Verhalten für diese Cases, nicht Production Reliability oder ein Production Authorization System.

Fehler mit Error Analysis analysieren

Hamels Field Guide zeigt den Workflow: Untersuchen Sie reale Conversations, machen Sie offene Notizen, kategorisieren Sie Fehler und erstellen Sie spezifische Tests.

  1. Traces untersuchen und offene Notizen darüber verfassen, was schiefgelaufen ist.
  2. Wiederkehrende Fehler gruppieren und benannte Kategorien bilden.
  3. Traces labeln und sie gegen diese Taxonomie bewerten.
  4. Spezifische Tests erstellen für die größten umsetzbaren Cluster.

Beginnen Sie nicht mit Labels wie reasoning_issue oder tool_problem. Sie sind zu vage, um sie zu testen. Verwenden Sie Labels wie missing_identity_verification, date_argument_mismatch, retried_same_tool_after_429 oder stopped_before_database_update. Ein derart spezifisches Label sagt Ihnen exakt, was der Regression-Test prüfen sollte.

Vor der Promotion deduplizieren

Der Trace-Mining-Loop hat eine Falle: jeden fehlerhaften Trace dauerhaft hinzuzufügen. Dadurch entsteht ein großes, teures und enges Dataset. Es besteht aus Near-Duplicates vom März, verpasst aber die neue Form desselben Bugs im Juni.

Gruppieren Sie zuerst. Beginnen Sie mit einem repräsentativen Golden pro Cluster und behalten Sie anschließend Varianten mit unterschiedlichen Permissions, Argumenten, Recovery States oder Expected Outcomes. Ähnliche Formulierungen machen zwei Policy-Cases nicht äquivalent. Speichern Sie verwandte Trace IDs in Access-Controlled Metadata, damit ein Reviewer die Evidence später untersuchen kann.

Wenn ein Failure Cluster nach einem Fix erneut auftritt, hat der Regression Case nicht generalisiert. Überarbeiten Sie den Cluster und ergänzen Sie die fehlenden Behavioral Variants, statt nahezu identische Transkripte zu sammeln.

Das Dataset versionieren

Versionieren Sie Datasets wie Prompts und Code. Wenn sich etwas Wesentliches ändert (Model, Prompt, Tool Schema, Judge Prompt oder App-Verhalten), möchten Sie dieselbe Dataset-Version davor und danach ausführen.

Der CI-Check sollte Folgendes pinnen:

  • Dataset-Version
  • App-Version
  • Prompt-Version
  • Judge Model
  • Judge Prompt
  • Evaluator-Code-Version
  • Tool Schemas, Policy, Harness- und Context-Management-Konfiguration
  • Model Revision, Reasoning- und Sampling-Settings
  • Initial Environment Fixture und erlaubte externe Effects

Wenn sich einer dieser Punkte ändert, wird der Vorher-Nachher-Vergleich unscharf. Eine goldens-v3.json-Datei in Git ist bei kleinem Maßstab ausreichend. Tool-native Snapshots in Langfuse, Phoenix, Braintrust oder LangSmith helfen, sobald das Dataset kollaborativ wird.

Halten Sie Development Regressions, Judge-Calibration-Examples, Held-out Validation und Monitoring Samples getrennt. Gruppieren Sie verwandte Sessions, User und Tasks vor dem Split, damit Near-Duplicates nicht zwischen Sets leaken. Sobald ein Case einen Prompt oder eine Rubric beeinflusst, behandeln Sie ihn als Development-Evidence. Eine aus Failure Mining entstandene Suite testet bekannte Regressions; ihr Durchschnitt schätzt nicht die Production Success Rate.

Setzen Sie Mutable State für jeden Trial zurück: Files, Database Rows, Caches und Tool Fixtures. Isolieren Sie Credentials und externe Effects und halten Sie die Budgets von Candidate und Baseline gleich. Berichten Sie die Anzahl der Tasks getrennt von den Trials sowie alle gestarteten Attempts, Timeouts, Crashes und nicht scorbaren Outcomes. Vergleichen Sie gepaarte Ergebnisse auf denselben Tasks. Diese Entscheidungen folgen dem in Anthropics Evaluation Guide beschriebenen Ansatz für Clean Trials und Outcome Grading.

Evals in CI ausführen

Ein Release Check muss den Build fehlschlagen lassen, wenn eine Metrik ihr vereinbartes Limit überschreitet. Andernfalls ist die Eval-Suite lediglich ein Dashboard.

Nach der Wiederherstellung des Case-Fixtures in einem isolierten Trial sollte der Test den aktuellen Agent gegen den Golden Input erneut ausführen. Er sollte nicht lediglich den alten fehlgeschlagenen Trace abspielen (Skizze; die ausführbare Version befindet sich im begleitenden Repository):

@pytest.mark.parametrize("golden", GOLDENS, ids=[item["id"] for item in GOLDENS])
def test_agent_regression(golden: dict) -> None:
    answer, fresh_trace = run_agent_and_capture_trace(golden["input"])

    refired = set(flag_failures(fresh_trace)) & set(golden["failure_modes"])
    assert not refired, f"failure mode regressed: {sorted(refired)}"

    assert tool_correctness(
        called=[call["name"] for call in fresh_trace["tool_calls"]],
        expected=golden["expected_tools"],
        mode=golden.get("tool_match", "in_order"),
    ) >= golden.get("tool_threshold", 1.0)

Diese Unterscheidung wird leicht übersehen. Die Aufgabe des Datasets besteht darin, die nächste Version des Agents zu stoppen, wenn sie einen alten Fehler wiederholt, und nicht darin, den Fehler selbst zu archivieren.

Den Judge kalibrieren, bevor Sie ihm vertrauen

LLM-as-Judge ist hilfreich. Man kann sich damit aber auch leicht selbst täuschen.

G-Eval evaluiert drei Meta-Evaluation-Benchmarks. Dies sind SummEval, basierend auf News-Summarization mit CNN/DailyMail; Topical-Chat, ein Knowledge-Grounded-Dialogue-Benchmark; und QAGS, das die Factual Consistency von CNN/DailyMail- und XSum-Summaries testet. Mit GPT-4 als Backbone erreichte G-Eval-4 auf SummEval eine Spearman-Korrelation von 0,514 mit Human Judgments. Die Scoring Function gewichtet Rating Levels anhand der Token Probability (score=∑ip(si) si\text{score} = \sum_i p(s_i)\,s_iscore=∑i​p(si​)si​).

Das Paper schätzte GPT-4s Token Probabilities durch 20-faches Sampling, weil das Model sie im Experiment nicht offenlegte. Ein Hosted Model kann keine nutzbaren Logprobs bereitstellen. Behalten Sie daher die Rubric bei, implizieren Sie aber nicht, dass Sie die Probability Weighting des Papers reproduziert haben. Diese Ergebnisse vergleichen das Protokoll des Papers mit seinen NLG-Baselines auf diesen Benchmarks. Sie sprechen dafür, einen Judge mit expliziter Rubric zu testen, nicht für einen allgemeinen Ersatz automatischer Metriken oder eines Production-Agent-Trajectory-Benchmarks.

MT-Bench zeigte, dass GPT-4 ungefähr so häufig mit menschlichen Präferenzen übereinstimmte, wie Menschen untereinander übereinstimmen. Dieses Ergebnis trug dazu bei, LLM Judging zum Mainstream zu machen. Spätere Arbeiten zeigten Biases durch Position, Length und Self-Preference. Judge Scores können sich außerdem ändern, wenn sich Prompt oder Model-Version ändern.

JudgeBench erstellte Response-Paare, bei denen eine Antwort in verifizierbarem Wissen, Reasoning, Math und Code objektiv falsch war. Mit einem einfachen Judge Prompt erreichte GPT-4o 50,9 %, also kaum mehr als einen Coin Flip. Der stärkere Arena-Hard-Prompt des Papers hob dasselbe Model nur auf 56,6 %. Der Wechsel des Models unter diesem stärkeren Prompt ist relevanter: Claude 3.5 Sonnet, der beste getestete General-Purpose-Judge, erreichte 64,3 %, während o3-mini bei hohem Reasoning Effort 80,9 % erzielte. Confident but Wrong Answers bleiben für einen Judge schwierig, der vor dem Grading nicht Reasoning betreibt.

Behandeln Sie den Judge wie ein Messinstrument: Kalibrieren Sie ihn gegen Human Labels, bevor er irgendetwas bewertet, und überprüfen Sie ihn erneut, sobald sich Judge Model oder Prompt ändern.

Wenn ein Judge erforderlich ist, machen Sie das Verdict strukturiert. Schema-Guided Reasoning (SGR) gibt dem Verdict ein Schema für Output Shape und Inspectability. Structured Outputs oder Constrained Decoding können Object Shape, Required Fields und Value Constraints für Felder wie evidence, passed_criteria, failed_criteria, failure_mode und score erzwingen.

Platzieren Sie Evidence Fields vor dem Score, wenn dadurch die Inspektion des Records einfacher wird. Die Field Order ist eine Präsentationsfrage und keine Garantie für Reasoning. Ein schema-valider Verdict kann weiterhin unsupported Evidence oder einen unzuverlässigen Score enthalten. Testen Sie die Reliability des Judges mit Calibration gegen Human Labels, deterministischen Validatoren und Transcript Review. CI kann ein stabiles JSON-Objekt diffen. Das prüft jedoch Inspectability und Shape, nicht den Nachweis, dass Rubric-Stages befolgt wurden.

Ein Structured Verdict kann außerdem die Cost Curve verändern. Behandeln Sie ein günstigeres Model als Kandidaten und nicht als automatischen Ersatz. Führen Sie es über denselben Human-Labeled-Calibration-Set aus. Vergleichen Sie Agreement, False-Pass-Rate und False-Fail-Rate mit dem größeren Judge. Verwenden Sie es für Routine-Cases nur, wenn es die von Ihrer Application gesetzten Thresholds erfüllt. Behalten Sie den größeren Judge für Disagreements, High-Risk-Cases oder Calibration Runs.

Checkliste für Judge Hygiene:

  1. Bevorzugen Sie nach Möglichkeit Binary Pass/Fail. Fünf-Punkte-Skalen laden zu Fake Precision ein.
  2. Labeln Sie Trajectories, die die tatsächlichen Failure Modes abdecken, bevor Sie die Rubric finalisieren. Wählen Sie die Sample Size anhand der Coverage und der Unsicherheit, die die Entscheidung tolerieren kann, und reservieren Sie separate Cases für Validation.
  3. Messen Sie die Judge-Human-Agreement mit Cohens Kappa, einer Confusion Matrix sowie Positive und Negative Recall. Kappa misst Agreement nach Berücksichtigung des zufallsbedingt erwarteten Agreements; höher ist besser. Ein Judge, der immer „Pass“ sagt, besitzt keine nützliche Discrimination. Kappa kann daher null oder undefiniert sein. Legen Sie fest, wie mit einem undefinierten Wert umzugehen ist, bevor Sie die Metrik zur Release-Freigabe verwenden.
  4. Zerlegen Sie grobe Kriterien. „Hat der Agent vor dem Refund Tool Call die Identität verifiziert?“ ist besser als „War die Trajectory gut?“
  5. Geben Sie das Verdict über ein SGR-Schema mit Evidence, Failed Criteria, Failure Mode und Score aus.
  6. Vergleichen Sie Same-Family- und Cross-Family-Judges mit Held-out Human Labels. Die Trennung der Families allein belegt keine Reliability.
  7. Messen Sie die Pairwise Order Sensitivity. Behalten Sie Randomization oder Swapped-Order-Aggregation nur bei, wenn dadurch Held-out Decisions verbessert werden; eine kontrollierte Studie von 2026 stellte fest, dass Swapping bei adversarial Cases schaden kann.
  8. Gewähren Sie keinen Credit für zusätzlichen Text, außer er fügt korrekten, relevanten und belegten Content hinzu. Eine längere Antwort ist nicht automatisch besser.
  9. Pinnen Sie Judge Model, Prompt, Dataset, Schema und App-Version.
  10. Kalibrieren Sie nach Änderungen an Model, Prompt, Tool, Policy oder Schema erneut.

Ein Panel ist ein weiterer Kandidat, den Sie testen können. PoLL berichtete über bessere Alignment mit Human Judgments, reduzierten Intra-Model-Bias und geringere Kosten als seine Single-GPT-4-Baseline über sechs Datasets hinweg. Diese Ergebnisse gelten für die verwendeten Models, Tasks und historischen Preise. Sie belegen nicht, dass ein Panel für Ihren Task sicherer ist. Vergleichen Sie False Passes, False Failures, Kosten und den Disagreement-Workload mit einem kalibrierten Judge anhand von Held-out Labels.

Es gibt keinen universellen Kappa-Threshold, der einen Judge für CI geeignet macht. Berichten Sie Confusion Matrix, Label Counts, False-Pass-Rate unter den Human Failures und False-Fail-Rate unter den Human Passes jeweils mit Unsicherheit. Wählen Sie Release Limits anhand der Konsequenzen dieser Fehler. Verwenden Sie Review Queues, wenn die Evidence für eine automatische Akzeptanz zu schwach ist, und behalten Sie Human Authorization für folgenreiche Actions bei, wenn der Workflow dies erfordert.

Guardrails blockieren inline, Online-Evals beobachten danach

Byte sagt

Ein asynchroner Injection-Check kann eine Verletzung erst erkennen, nachdem der Tool Call bereits ausgeführt wurde.

Diese Konzepte werden verwechselt, weil beide Scores erzeugen. Der Unterschied ist die Platzierung: inline im Request Path, vor dem Release oder nach der Response.

Guardrails laufen inline. Sie sind schnell und für den User sichtbar. Ein Guardrail kann einen Tool Call blockieren, PII redigieren, Prompt Injection ablehnen oder vor dem Verlassen Ihres Systems einen Retry erzwingen. Ein False Positive ist ein Production Bug. Ein False Negative ist leiser und schlimmer, weil im Request Path nichts darüber berichtet. Schema-, Range- und Policy-Checks sind deterministisch. Injection- und PII-Detection sind Classifiers. Behandeln Sie Misses daher als erwartbar und lassen Sie ein Async Eval beobachten, was diese durchlassen.

Offline-Evals laufen vor dem Release. Sie sind reproduzierbar und prüfen Prompts, Models, Tools, Retrievers und Policies gegen ein fixes Dataset.

Online-Evals laufen nach der Response, üblicherweise auf gesampeltem Traffic. Sie können langsamere LLM Judges verwenden, weil sie nicht im Latency Path liegen. Ihre Aufgabe ist es, Drift zu erkennen, neue Failure Clusters zu finden und das nächste Offline-Dataset zu speisen.

Eine falsche Platzierung schadet in beide Richtungen:

  • Ein Judge im Request Path erhöht die Latency und erzeugt eine neue Flakiness-Quelle.
  • Ein Guardrail, das auf Async Scoring verschoben wird, lässt Policy Violations bis zum User gelangen.

Unterscheiden Sie bei Security Tests zwischen Attack Detection, dem Versuch einer Prohibited Action und dem tatsächlichen erfolgreichen Harmful Effect. Berichten Sie Successful Harmful Effects pro Attack Trial inklusive Threat Model und Attempt Budget sowie Legitimate Task Success und False Blocks pro Benign Trial. Ein Detector Score allein kann nicht belegen, dass Daten privat geblieben oder Writes verhindert worden sind. Verwenden Sie isolierte Targets. Anthropics Cybersecurity-Evaluation-Incident-Report dokumentiert, warum Evaluation Effects eingegrenzt werden müssen.

Bei High-Volume-Systemen sollten Sie ein kleines Sample mit einem stärkeren Judge und ein größeres Sample mit günstigeren Classifiers scoren. Alarmieren Sie bei Clustern und Confidence Bounds und nicht bei einem einzelnen verrauschten Point Estimate.

Tooling-Auswahl

Kein einzelnes Tool beherrscht den gesamten Loop. Vergleichen Sie einen Trace-/Dataset-Store und einen CI-/Eval-Runner separat. Ein Product kann beides abdecken, Sie müssen jedoch nicht beides beim selben Vendor kaufen.

Die Trade-off-Hinweise beschreiben, wo Kosten entstehen, nicht wie hoch sie sind. Pricing Pages ändern sich, und Vendors zählen unterschiedliche Dinge: Traces, Observations, Spans, Scores, User, Retention oder verarbeitete Daten. Prüfen Sie Live Pricing erneut, bevor Sie sich festlegen.

Empfehlungen nach Constraint:

  • Wählen Sie Phoenix, wenn Self-Hosting, Privacy und OTel-kompatibles Tracing harte Requirements sind und Ihr Team das Deployment betreiben kann.
  • Wählen Sie Langfuse, wenn Sie zusätzlich Dataset-Versionierung und Experimente benötigen und den Storage Stack betreiben oder die erforderlichen Add-ons kaufen können.
  • Wählen Sie DeepEval, wenn Python-/pytest-CI-Pass-Fail der primäre Vertrag ist.
  • Wählen Sie Inspect AI, wenn die Hauptarbeit in Safety- oder Frontier-Agent-Evaluation in konfigurierbaren Sandboxes besteht.
  • Wählen Sie LangSmith, wenn die LangChain-/LangGraph-Integration zu Ihrem Workflow passt. Nutzen Sie Cloud oder berücksichtigen Sie die Enterprise-Anforderung für BYOC oder Self-Hosted Platform Hosting.
  • Wählen Sie Braintrust, wenn Managed Pull-Request-Feedback und Experiment-Vergleiche einen API-Key-basierten Service rechtfertigen.
  • Wählen Sie Promptfoo, wenn Prompt- oder Red-Team-Checks die zentrale Regression Surface sind und ein Trace Store außerhalb des Scopes liegt.

Die Tool-Auswahl ist nachrangig. Wenn Production Failures nicht zu Test Cases werden, bezahlen Sie im Wesentlichen für Trace Storage.

Praktische Rollout-Checkliste

Bauen Sie die Evidence Pipeline auf, bevor Sie den Metrik-Stack erweitern. Entscheiden Sie zunächst, woher die Examples kommen.

  1. Sammeln Sie zuerst historische Runs. Wenn der Agent bereits existiert, holen Sie Traces, Support Tickets, Bug Reports, Thumbs-Down-Sessions, manuelle QA-Transkripte und Dogfooding-Notizen zusammen, bevor Sie die Implementation ändern. Wenn der Agent noch nicht existiert, loggen Sie ab Tag eins jeden Prototype und jeden manuellen Test Run.

  2. Instrumentieren Sie die Trace Shape. Erfassen Sie Messages, Tool Calls, Arguments, Tool Outputs, Errors, Token Counts, Latency, Cost, User Feedback, App Version, Prompt Version, Model Version, Tool Schema Version und den finalen Environment State. Verwenden Sie OpenTelemetry GenAI Conventions oder OpenInference-Style-Spans, wenn Sie Portability benötigen, und pinnen Sie Convention-Version und Adapter. Erfassen Sie Content selektiv: Redigieren Sie Secrets und persönliche Daten, beschränken Sie den Zugriff und legen Sie Retention fest, bevor Sie Traces in Datasets übernehmen. Verwenden Sie Langfuse, LangSmith, Phoenix oder Braintrust, wenn Sie sofort eine Trace UI und einen Dataset-Workflow benötigen.

  3. Wandeln Sie reale Fehler in Seed Cases um. Lesen Sie die Traces, bevor Sie sie mit einem Model zusammenfassen. Speichern Sie für jeden nützlichen Fehler Input, Source Trace ID, Expected State, Expected Tool Invariants, Failure Mode, Severity und Reviewer Note. Langfuse kann Dataset Items mit Production Traces verknüpfen; LangSmith kann Datasets aus getraceten Runs erzeugen. Bewahren Sie den Source Link auf, damit der Case auditierbar bleibt.

  4. Wenn keine Historie vorhanden ist, generieren Sie Cold-Start-Cases. Bitten Sie ein LLM, Tasks aus Product Requirements, Policies, Tool Schemas, State Machines und Support Macros zu entwerfen. Decken Sie Happy Paths und Failures ab, etwa falsche Permissions, fehlende Identity Checks, veraltete Tool Results, mehrdeutige Datumsangaben, Retries nach Rate Limits und widersprüchliche Tool Outputs.

  5. Vertrauen Sie synthetischen Cases erst nach Human Review. Synthetische Examples sind für Coverage nützlich, nicht für Truth. Markieren Sie sie mit source: synthetic und verlangen Sie die Freigabe des Expected Outcomes durch einen Reviewer. Führen Sie nach Möglichkeit einen Known-Good-Reference-Path aus und validieren Sie generierte Expectations unabhängig. Die Verwendung einer anderen Model Family ersetzt diesen Check nicht.

  6. Bauen Sie ein kleines, ausgewogenes Dataset. Nehmen Sie Successes, Failures, Refusals, Boundary Cases, Long-Turn-Cases, Policy-Sensitive-Cases und gültige alternative Pfade auf. Machen Sie den Golden nicht zum „exakten alten Transkript“. Speichern Sie die oben beschriebenen Golden-Informationen sowie den Failure Mode, aufgrund dessen der Case in der Suite gelandet ist.

  7. Fügen Sie zuerst deterministische Checks hinzu. Required Tool Order, wenn die Reihenfolge Policy ist, Required Arguments, Schema Validation, Final-State-Diffs, Loop Limits, Token- und Latency-Ceilings sowie Task-spezifische Invarianten sollten vor jedem Judge laufen.

  8. Fügen Sie einen SGR-förmigen Judge hinzu. Verwenden Sie ihn nur für den Teil, der Interpretation erfordert. Kalibrieren Sie ihn gegen Human Labels und testen Sie die gewählte Rubric auf unberührten Validation Cases. Wenn er im Calibration Set gute und schlechte Examples nicht trennen kann, korrigieren Sie die Rubric, bevor Sie ihn in CI integrieren.

  9. Verdrahten Sie den Loop. Führen Sie die kleine Offline-Suite in CI aus, die größere Suite vor dem Release, scoren Sie gesampelten Production Traffic online und übernehmen Sie wiederkehrende Online-Failure-Cluster zurück in das Offline-Dataset.

Ihre erste Eval-Suite wird Cases übersehen. Führen Sie sie trotzdem aus und ergänzen Sie wiederkehrende Failures als Cases. Eine Suite, die täglich läuft, liefert Evidence für ihre Verbesserung.
