AI-Agent-Evaluation in Production: Von Traces zu Testsuites

Viacheslav Dubrov

2026-06-10 · Aktualisiert 2026-08-08 · 21 Min. · KI-Agenten

Automatische Übersetzung Dieser Artikel wurde automatisch aus der englischen Originalversion übersetzt.

Ein Chatbot liefert dir eine Antwort zur Bewertung. Ein Agent liefert dir einen ganzen Entscheidungsbaum: Pläne, Tool Calls, Retries und den Moment, in dem er entscheidet, dass er fertig ist.

Dieser Unterschied erfordert eine andere Evaluationsmethode. Eine finale Antwort kann korrekt aussehen, obwohl der Agent ein erforderliches Tool übersprungen, einen Call 17-mal wiederholt, ein Ergebnis falsch interpretiert oder einen durch die Production-Policy verbotenen Pfad gewählt hat. Eine reine Bewertung der Antwort verbirgt diese Fehler.

Dieser Guide richtet sich an Engineers, die Tool-using Agents in Production betreiben.

Am Ende kannst du Production-Traces in begrenzte Regression-Cases mit deterministischen Trajectory-Checks und kalibrierten Judges umwandeln.

Den kurzen Tool-Vergleich findest du unter Best AI Agent Evaluation Tools.

TL;DR

Agent-Evals benötigen drei Ebenen: Outcome-Metriken, Trajectory-Metriken und Component-Metriken. Baue den Prozess um diese Schleife herum auf: Trace -> Label -> Cluster -> Dedupe -> versioniertes Dataset -> CI-Gate -> Online-Monitoring. Verwende deterministische Checks für Tool-Reihenfolge, Argumente, Loops und Invarianten. Setze LLM Judges nur dort ein, wo die Prüfung Interpretation erfordert, strukturiere diese Judges mit Schema-Guided Reasoning (SGR) und kalibriere sie anhand menschlicher Labels, bevor du ihnen vertraust.

Warum sich Agent-Evals unterscheiden

Traditionelle LLM-Evals bewerten normalerweise ein Input-Output-Paar: Relevanz, Faithfulness, Correctness, Safety, eventuell Stil. Agents bringen Planning, Tool Calls, Retries und Termination-Checks hinzu, wobei jeder Schritt eine neue Fehlerquelle darstellt.

Nimm einen Refund-Agent. Das Transkript kann gut enden, während der Trace falsch ist:

lookup_order -> issue_refund -> final_answer

Die Output-Eval besteht. Eine Trajectory-Eval sollte jedoch fehlschlagen, weil verify_identity nie vor issue_refund ausgeführt wurde. Für Tool-using Agents sind reine Answer-Evals Smoke Tests: Sie erkennen einen vollständigen Ausfall und übersehen fast alles andere.

Es gibt ein zweites Problem: Fehler kumulieren. Wenn ein Workflow 20 erforderliche Schritte enthält, jeder Schritt unabhängig erfolgreich ist und jeder Schritt dieselbe Reliability von 95 % hat, liegt die End-to-End-Success-Rate bei etwa 36 %:

0.9520≈0.360.95^{20} \approx 0.360.9520≈0.36

Der Agent kann also in isolierten Checks solide wirken und trotzdem die meisten vollständigen Runs nicht bestehen. Der Bruch liegt normalerweise irgendwo in der Mitte. Ihn zu finden erfordert Visibility auf Component-Ebene, nicht einen weiteren Blick auf die Antwort.

Zwei Research-Teams haben dies quantifiziert.

tau-bench gibt einem Agent Aufgaben aus Airline- und Retail-Kundenservice. Der Agent spricht mit einem simulierten User, ruft APIs auf und muss die Domain-Policy einhalten. Nach der Conversation prüft der Grader, ob die Datenbank den annotierten Goal State erreicht hat. Ein plausibles Transkript mit den falschen Rows schlägt trotzdem fehl.

Unter diesem Grading löste GPT-4o nur 35,2 % der Airline-Aufgaben und knapp über 60 % der Retail-Aufgaben. Das Paper führte außerdem pass^k ein: Dieselbe Aufgabe wird k-mal ausgeführt, und ein Pass zählt nur, wenn der Agent in allen k Runs erfolgreich ist.

Retail, der einfachere Split, fiel bei k = 8 unter 25 %. Bei mehr als drei Vierteln dieser Aufgaben scheiterte derselbe Agent bei mindestens einem von acht Runs mit derselben Aufgabe. Eine Eval mit nur einem Run kann diese Inkonsistenz nicht sichtbar machen.

MAST untersucht, warum Agents scheitern. Die Autoren entwickelten aus 150 manuell annotierten Traces eine Taxonomie mit 14 Modi und wandten sie anschließend auf mehr als 1.600 Traces aus sieben populären Multi-Agent-Frameworks an. Die Taxonomie umfasst vage Role Definitions (System Design), einen Agent, der ignoriert, was ein anderer Agent berichtet hat (Inter-Agent Misalignment), sowie das Deklarieren eines Erfolgs ohne Prüfung des Ergebnisses (No Verification). Diese Fehler betreffen Prompts, Orchestration Logic und fehlende Checks im Harness. Ein stärkeres Base Model kann keinen Verification Step ausführen, der nie implementiert wurde. Das Evaluationsziel muss daher auch den Harness rund um das Model umfassen.

Die Adoption Gap

Die Umfrage State of Agent Engineering von LangChain (1.340 Befragte, durchgeführt Ende 2025) deutet darauf hin, dass viele Teams bereits die Rohdaten für bessere Evals besitzen. Demnach verfügten 89 % über eine Form von Observability, 52,4 % führten Offline-Evals aus und 37,3 % Online-Evals.

Die Umfrage berichtet außerdem, dass 57,3 % der Befragten bereits Agents in Production einsetzen. Auf die Frage, was Production-Einsätze blockiert, nannten 32 % Quality und 20 % Latency. Dies ist eine Vendor-Umfrage unter den eigenen Befragten und keine Vollerhebung aller Agent-Teams. Sie zeigt jedoch eine nützliche Lücke zwischen Trace-Erfassung und systematischer Evaluation.

Teams befinden sich dadurch oft in einem unangenehmen Zwischenzustand: Sie können einen fehlerhaften Run nachträglich untersuchen und anschließend trotzdem denselben Fehler erneut ausliefern.

Jeder diagnostizierte Production-Fehler sollte einen Trace, ein Label, eine Dataset-Zeile und einen Scorer hinterlassen. Ein reproduzierbarer Fehler gehört in die Regression-Suite.

Wähle Metriken nach Failure Mode

Die richtige Metrik hängt vom Failure Mode ab, nicht vom Framework. Die sinnvolle Aufteilung umfasst drei Ebenen:

  1. Outcome-Evals beantworten, ob die Aufgabe erfolgreich war.
  2. Trajectory-Evals beantworten, ob der Pfad valide, effizient und policy-konform war.
  3. Component-Evals beantworten, welches Tool, welcher Retriever, welcher Sub-Agent oder welcher Decision Step fehlerhaft war.

Jede Ebene kann offline auf festen, reproduzierbaren Cases vor dem Release oder online auf gesampelten Production-Traces nach der Response ausgeführt werden. Der Abschnitt zu Guardrails behandelt diese Aufteilung im Detail. Offline-Evals können Goldens erfordern: gespeicherte Cases, die einen Input mit dem Outcome, Tool-Invarianten und den Argumenten verbinden, die ein korrekter Run erzeugen muss. Online-Evals sollten Invarianten, Distributions und asynchrone Checks bevorzugen, die nicht im Request Path liegen.

Beginne mit deterministischen Metriken. Sie sind günstig, schnell und driften nicht.

Tool-Call-Correctness

Tool Correctness vergleicht die aufgerufenen Tools mit den erwarteten Tools. Wähle die Strenge bewusst:

  • Exact Match: Die Sequenz muss exakt übereinstimmen. Verwende dies, wenn die Reihenfolge Policy ist, zum Beispiel lookup_order -> verify_identity -> issue_refund.
  • In-Order-Match: Erforderliche Tools müssen in der richtigen relativen Reihenfolge erscheinen, zusätzliche harmlose Calls sind jedoch erlaubt.
  • Any-Order-Match: Erforderliche Tools müssen vorkommen, die Reihenfolge darf aber variieren.

Ein kleiner lokaler Scorer reicht für den Anfang:

from collections import Counter

def tool_correctness(called: list[str], expected: list[str], mode: str = "in_order") -> float:
    if not expected:
        return 1.0
    if mode == "exact":
        return float(called == expected)
    if mode == "any_order":
        matched = sum((Counter(called) & Counter(expected)).values())
        return matched / len(expected)

    rows = [[0] * (len(expected) + 1) for _ in range(len(called) + 1)]
    for i, tool in enumerate(called):
        for j, wanted in enumerate(expected):
            if tool == wanted:
                rows[i + 1][j + 1] = rows[i][j] + 1
            else:
                rows[i + 1][j + 1] = max(rows[i][j + 1], rows[i + 1][j])
    return rows[-1][-1] / len(expected)

called = ["lookup_order", "check_refund_policy", "issue_refund"]
expected = ["lookup_order", "verify_identity", "issue_refund"]

print(round(tool_correctness(called, expected, "exact"), 3))     # 0.0
print(round(tool_correctness(called, expected, "in_order"), 3))  # 0.667

Der in_order-Score ist der Recall der Longest Common Subsequence: Welcher Anteil der erforderlichen Sequenz in der richtigen Reihenfolge erhalten geblieben ist. Beachte, was er ignoriert. Junk Calls senken den Score nicht. Ein Agent kann hier also 1,0 erreichen und trotzdem doppelt so viele Calls ausführen wie nötig. Wenn zusätzliche Calls Kosten verursachen oder State mutieren, solltest du zusätzlich die Precision erfassen (gematchte Required Calls geteilt durch alle Calls) und beide Werte gemeinsam betrachten. Recall findet den fehlenden Schritt; Precision erkennt das Wandern.

DeepEvals Tool-Correctness-Metrik stellt dieselben Stellschrauben über should_consider_ordering und should_exact_match bereit.

Argument Correctness

Das richtige Tool mit falschen Argumenten aufzurufen ist oft schlimmer als das falsche Tool aufzurufen, weil der Trace normal aussieht.

Für einfache Fälle validierst du JSON Schema und exakte Werte. Für semantische Fälle speicherst du erwartete Argumente und bewertest die Deltas:

{
    "trace_id": "tr_2417",
    "input": "Reschedule order A-100 for next Friday.",
    "expected_tools": ["lookup_order", "reschedule_delivery"],
    "expected_arguments": {
        "reschedule_delivery": {
            "order_id": "A-100",
            "date": "2026-06-19"
        }
    }
}

Eine Tool-Name-Metrik kann 2026-06-17 nicht erkennen, wenn die Policy 2026-06-19 verlangt. Das Dataset muss daher auch Argumente speichern.

Die zu diesem Dataset passende Metrik ist Parameter Match: der Anteil der erwarteten (tool, key, value)-Tripel, die der Agent korrekt erzeugt hat.

def argument_correctness(called_args: dict, expected_args: dict) -> float:
    total = matched = 0
    for tool, params in expected_args.items():
        for key, want in params.items():
            total += 1
            if called_args.get(tool, {}).get(key) == want:
                matched += 1
    return matched / total if total else 1.0

Exakte Gleichheit ist für IDs, Enums und bereits auf ein Format normalisierte Datumswerte richtig. Für Freitext, Floats und Datumswerte in der vom Model erzeugten Form ist sie falsch, weil == eine korrekte Antwort als falsch markiert. Bewerte diese Felder entsprechend ihrer Semantik: mit einem normalisierten String-Match, einem Date Parse oder einer numerischen Toleranz. Die Metrik bleibt gleich; nur der Comparator pro Feld ändert sich.

Efficiency, Loops und Dead Ends

Ein Agent, der die Aufgabe nach fünf redundanten Tool Calls abschließt, weist weiterhin auf ein Planning-Problem hin und verursacht höhere Betriebskosten.

Mit diesen günstigen Signalen solltest du beginnen:

  • Redundant-Call-Rate: Identische Tool Calls mit identischen Argumenten, die mehr als zweimal wiederholt werden.
  • Trace-Shape-Anomalien: Plötzliche Anstiege bei Tiefe, Tool-Call-Anzahl, Token-Anzahl, Latency oder Kosten.
  • Path Convergence: Wie nahe der Run am kürzesten bekannten validen Pfad für die Aufgabe liegt.
  • Termination Correctness: Ob der Agent zu früh gestoppt, nach dem Erfolg weitergearbeitet oder Erfolg ohne die erforderliche State-Änderung deklariert hat.
  • Plan Adherence: Wenn der Agent vor dem Handeln einen Plan schreibt, prüfst du, ob der Trace ihm folgt. Ein ignorierter guter Plan und ein perfekt befolgter schlechter Plan schlagen beide fehl – aus entgegengesetzten Gründen. Die Differenz zwischen Plan und Trace zeigt dir, welcher Fall vorliegt.

Führe diese Checks nach Möglichkeit vor einem Judge aus. Ein Loop Detector umfasst nur wenige Zeilen über dem Trace. Er benötigt kein Model.

Task Completion und Outcome Grading

Beim Outcome Grading lautet die Frage: „Hat der User bekommen, worum er gebeten hat?“

Zwei Patterns funktionieren am besten:

  • Referenceless Task-Completion-Judging: Extrahiere das Ziel aus dem Input und bewerte, ob Trace plus finale Antwort es erreicht haben. Das funktioniert online, weil Production Traffic nur selten Golden Outputs enthält.
  • Environment-State-Grading: Vergleiche die finale Datenbankzeilen, Files, Tickets, Bookings oder Records mit einem annotierten Goal State. Das ist robuster als Transcript Matching, weil Agents valide Pfade finden können, die du nicht explizit vorgegeben hast.

Die zweite Option ist besser, wenn du sie bauen kannst. Der Final State ist der Contract. Das Transkript ist nur Evidence.

Zwei Einschränkungen halten diese Methode ehrlich. Ein 2025 Audit von agentischen Benchmarks stellte fest, dass tau-bench einige Aufgaben ausschließlich anhand des Database State bewertet. Bei manchen Aufgaben erfordert das annotierte Outcome weder eine State-Änderung noch einen bestimmten Text. Ein Agent, der nichts tut, kann dadurch einen Pass erhalten: 38 % im Airline-Split und 6,0 % im Retail-Split, bei jedem k. Anthropic berichtete von einem Opus-4.5-Run, der eine Booking-Aufgabe in tau2-bench, dem Nachfolge-Benchmark, „nicht bestand“. Der Agent hatte eine Policy-Lücke gefunden, die für den User tatsächlich das bessere Ergebnis darstellte. State Grading ist besser als Transcript Matching, aber der Goal State bleibt eine Annotation, und Annotationen können Fehler enthalten. Prüfe auch Cases, die zu leicht bestehen, nicht nur solche, die fehlschlagen.

Component Evals

Outcome- und Trajectory-Metriken zeigen dir, dass der Run fehlgeschlagen ist, und ungefähr wo. Component Evals bewerten einen einzelnen Span: War der Retrieved Chunk relevant? Hat der Sub-Agent das Schema zurückgegeben, das sein Caller erwartet hat? Ließ sich die Response des Tools parsen? Hänge den Score an den Span statt an den Run, damit „Welches Tool hat diese Woche nachgelassen?“ eine Query und kein erneuter Run ist.

Drei Checks decken den größten Teil ab:

  • Per-Span-Scoring: Führe die zum Span-Typ passende Metrik aus. Retrieval-Spans erhalten Recall und Precision gegenüber dem annotierten Chunk, Sub-Agent-Spans Schema Validation plus ihren eigenen Tool-Correctness-Score, Tool-Spans Error Rate und Latency.
  • Tool-Result-Interpretation: Gib dem Agent ein korrektes, aber ungewöhnliches Tool Output (eine leere Liste, einen Partial Match, einen veralteten Timestamp) und prüfe, was er als Nächstes tut. Ein Tool kann korrekt sein, während der Agent es falsch liest; dieser Fehler wird dann zwei Schritte später sichtbar.
  • Failure Attribution: Der sichtbare Fehler liegt meist hinter dem eigentlichen Fehler. Ordne ihn dem frühesten Span zu, dessen Output bereits falsch war, nicht dem Schritt, der den Error ausgelöst hat.

Hier zahlt sich auch die Compounding Math aus dem Einstieg aus. Wenn 20 Schritte isoliert betrachtet jeweils gut aussehen, kann der Run trotzdem meistens fehlschlagen. Per-Span-Pass-Raten zeigen, welcher Schritt mit 95 % läuft und welcher mit 70 %.

Das Trace-to-Eval-Flywheel

Untersuche zunächst Production-Fehler, bevor du zusätzliche Eval-Cases brainstormst.

Die Schleife:

  1. Erfasse den vollständigen Trace.
  2. Label, was fehlgeschlagen ist.
  3. Gruppiere ähnliche Fehler.
  4. Behalte ein repräsentatives Golden pro Cluster.
  5. Versioniere das Dataset.
  6. Führe es in CI aus.
  7. Scoring gesampelter Production-Traces bleibt online aktiv.

Das begleitende Repository trace2evals implementiert die vollständige Schleife für einen fehlerhaften Support-Agent. Es erfasst OpenTelemetry-GenAI-Spans, erkennt Fehler mit deterministischen Regeln, dedupliziert Cases in ein versioniertes Golden Dataset und führt jedes Golden in CI erneut aus. Das Default-Backend ersetzt das Model durch deterministische Regeln, die die Entscheidungen des fehlerhaften Agents nachstellen. Dadurch reproduziert make demo die gesamte Schleife offline und ohne API Key. Führe uv sync --extra live aus und setze einen API Key; dann steuern dieselben Commands stattdessen ein echtes Model.

Fehler mit Error Analysis untersuchen

Hamel Husain und Shreya Shankar beschreiben für genau diesen Schritt einen Error-Analysis-Workflow; Hamels Field Guide führt durch den Prozess. Die ersten beiden Schritte übernehmen ihre Bezeichnungen aus der qualitativen Forschung, die Methode ist jedoch geradlinig: Traces lesen, Notizen machen, Patterns benennen.

  1. Open Coding: Lies 30 bis 50 reale Traces und notiere frei, was schiefgelaufen ist.
  2. Axial Coding: Gruppiere diese Notizen in fünf oder sechs benannte Failure-Kategorien.
  3. Label alles anhand der Taxonomie.
  4. Baue Metriken für die größten Buckets.

Beginne nicht mit Labels wie reasoning_issue oder tool_problem. Sie sind zu vage zum Testen. Verwende Labels wie missing_identity_verification, date_argument_mismatch, retried_same_tool_after_429 oder stopped_before_database_update. Ein derart spezifisches Label sagt dir exakt, was der Regressionstest behaupten sollte.

Vor dem Promote deduplizieren

Das Trace-Mining-Flywheel hat eine Falle: jeden schlechten Trace dauerhaft hinzuzufügen. Dadurch entsteht ein großes, teures und enges Dataset. Es besteht aus Near-Duplicates vom März, verfehlt aber im Juni die neue Ausprägung desselben Bugs.

Gruppiere zuerst. Promote ein repräsentatives Golden pro Cluster. Speichere die zugehörigen Trace IDs in den Metadaten, damit ein Reviewer die Production-Evidence später untersuchen kann.

Wenn ein Failure Cluster nach einem Fix erneut auftritt, hat der Regression Case nicht generalisiert. Cluster ihn erneut und erweitere das Golden, statt 15 punktuelle Beispiele hinzuzufügen.

Das Dataset versionieren

Versioniere Datasets genauso wie Prompts und Code. Sobald sich etwas Wesentliches ändert (Model, Prompt, Tool Schema, Judge Prompt oder App-Verhalten), möchtest du dieselbe Dataset-Version vor und nach der Änderung ausführen.

Das CI-Gate sollte Folgendes pinnen:

  • Dataset-Version
  • App-Version
  • Prompt-Version
  • Judge Model
  • Judge Prompt
  • Version des Evaluator-Codes

Wenn sich einer dieser Werte ändert, wird dein Before-/After-Vergleich schwer interpretierbar. Eine goldens-v3.json-Datei in Git reicht bei kleinem Umfang aus. Tool-native Snapshots in Langfuse, Phoenix, Braintrust oder LangSmith helfen, sobald das Dataset kollaborativ bearbeitet wird.

CI-Gates einrichten

Eine fehlschlagende Metrik muss zu einem fehlschlagenden Build führen, sonst ist die Eval-Suite nur ein Dashboard, das niemand liest.

Der Test sollte den aktuellen Agent gegen den Golden Input erneut ausführen. Er sollte nicht lediglich den alten fehlgeschlagenen Trace abspielen (Skizze; die ausführbare Version befindet sich im begleitenden Repository):

@pytest.mark.parametrize("golden", GOLDENS, ids=[item["id"] for item in GOLDENS])
def test_agent_regression(golden: dict) -> None:
    answer, fresh_trace = run_agent_and_capture_trace(golden["input"])

    refired = set(flag_failures(fresh_trace)) & set(golden["failure_modes"])
    assert not refired, f"failure mode regressed: {sorted(refired)}"

    assert tool_correctness(
        called=[call["name"] for call in fresh_trace["tool_calls"]],
        expected=golden["expected_tools"],
        mode=golden.get("tool_match", "in_order"),
    ) >= golden.get("tool_threshold", 1.0)

Diese Unterscheidung wird leicht falsch umgesetzt. Die Aufgabe des Datasets besteht darin, die nächste Version des Agents dabei zu ertappen, wie sie einen alten Fehler wiederholt – nicht darin, den Fehler selbst zu archivieren.

Den Judge kalibrieren, bevor du ihm vertraust

LLM-as-Judge ist hilfreich. Gleichzeitig kann man sich damit leicht selbst täuschen.

G-Eval bewertet drei Meta-Evaluation-Benchmarks. Diese sind SummEval, das auf News Summarization mit CNN/DailyMail basiert, Topical-Chat, ein Knowledge-Grounded-Dialogue-Benchmark, sowie QAGS, das die faktische Konsistenz von Summaries aus CNN/DailyMail und XSum testet. Mit GPT-4 als Backbone erreichte G-Eval-4 auf SummEval eine Spearman-Korrelation von 0,514 mit menschlichen Bewertungen. Seine Scoring-Funktion gewichtet Rating Levels anhand der Token Probability (score=∑ip(si) si\text{score} = \sum_i p(s_i)\,s_iscore=∑i​p(si​)si​).

Das Paper schätzte GPT-4s Token Probabilities durch 20 Samples, weil das Model sie im Experiment nicht offenlegte. Ein Hosted Model stellt möglicherweise keine nutzbaren Logprobs bereit. Behalte daher das Rubric bei, suggeriere aber nicht, dass du die Probability Weighting des Papers reproduziert hast. Diese Ergebnisse vergleichen das Protokoll des Papers auf diesen Benchmarks mit dessen NLG-Baselines. Sie unterstützen die Erprobung eines Judges mit explizitem Rubric, nicht den generellen Ersatz automatischer Metriken oder eines Production-Agent-Trajectory-Benchmarks.

MT-Bench zeigte, dass GPT-4 ungefähr so häufig mit menschlichen Präferenzen übereinstimmt, wie Menschen untereinander übereinstimmen. Dieses Ergebnis trug dazu bei, LLM Judging zu etablieren. Spätere Arbeiten zeigten Biases bezüglich Position, Länge und Self-Preference. Judge-Scores können sich außerdem ändern, wenn sich Prompt oder Model-Version ändern.

JudgeBench erstellte Response-Paare, bei denen eine Antwort über überprüfbares Wissen, Reasoning, Mathematik und Code objektiv falsch ist. Mit einem einfachen Judge Prompt erreichte GPT-4o 50,9 % – kaum mehr als einen Münzwurf. Der stärkere Arena-Hard-Prompt des Papers hob dasselbe Model nur auf 56,6 %. Der Austausch des Models unter diesem stärkeren Prompt ist relevanter: Claude 3.5 Sonnet, der beste getestete General-Purpose-Judge, erreichte 64,3 %, und o3-mini mit hohem Reasoning-Aufwand 80,9 %. Selbstbewusste, aber falsche Antworten bleiben für einen Judge schwierig, der nicht vor der Bewertung Reasoning betreibt.

Behandle den Judge als Messinstrument: Kalibriere ihn anhand menschlicher Labels, bevor er irgendetwas bewertet, und überprüfe ihn erneut, sobald sich Judge Model oder Prompt ändern.

Wenn ein Judge erforderlich ist, sollte das Verdict strukturiert sein. Schema-Guided Reasoning (SGR) gibt dem Verdict ein Schema für Output Shape und Inspectability. Structured Outputs oder Constrained Decoding können Object Shape, Required Fields und Value Constraints für Felder wie evidence, passed_criteria, failed_criteria, failure_mode und score erzwingen.

Platziere Evidence Fields vor dem Score, wenn das Record dadurch leichter zu inspizieren ist. Die Feldreihenfolge ist Präsentation, keine Garantie für Reasoning. Ein schema-valider Verdict kann weiterhin nicht belegte Evidence oder einen unzuverlässigen Score enthalten. Verwende die Kalibrierung anhand menschlicher Labels, deterministische Validatoren und Transcript Review, um die Zuverlässigkeit des Judges zu prüfen. CI kann ein stabiles JSON-Objekt diffen, prüft damit aber Inspectability und Shape, nicht den Nachweis, dass die Rubric-Stufen befolgt wurden.

Ein strukturiertes Verdict kann auch die Kostenkurve verändern. Behandle ein günstigeres Model als Kandidaten, nicht als automatischen Ersatz. Führe es über dasselbe Human-Labeled-Calibration-Set aus. Vergleiche Agreement, False-Pass-Rate und False-Fail-Rate mit dem größeren Judge. Verwende es nur für Routine-Cases, wenn es die von deiner Anwendung festgelegten Schwellenwerte erreicht. Behalte den größeren Judge für Disagreements, High-Risk-Cases oder Calibration Runs.

Checkliste für die Judge-Hygiene:

  1. Bevorzuge nach Möglichkeit binäres Pass/Fail. Fünfstufige Skalen suggerieren eine künstliche Präzision.
  2. Label 30 bis 50 Trajectories manuell, bevor du das finale Rubric schreibst.
  3. Miss die Übereinstimmung zwischen Judge und Menschen mit Cohens Kappa, einer Confusion Matrix sowie Positive und Negative Recall. Ein Judge, der immer „Pass“ sagt, besitzt keine nützliche Discrimination; Kappa kann null oder undefiniert sein, wenn der Nenner der erwarteten Übereinstimmung null ist. Lege eine explizite Policy für undefiniertes Kappa fest, bevor du die Metrik als Deployment-Gate verwendest.
  4. Zerlege grobe Kriterien. „Hat der Agent vor dem Refund-Tool-Call die Identität verifiziert?“ ist besser als „War die Trajectory gut?“
  5. Gib das Verdict über ein SGR Schema mit Evidence, Failed Criteria, Failure Mode und Score aus.
  6. Verwende nach Möglichkeit einen Judge aus einer anderen Model-Family als der Generator.
  7. Randomisiere die Reihenfolge bei Pairwise-Vergleichen und mittlere beide Richtungen.
  8. Bestrafe nicht belegte Länge im Rubric. Eine längere Antwort ist keine bessere Antwort.
  9. Pinne Judge Model, Prompt, Dataset, Schema und App-Version.
  10. Kalibriere nach Änderungen an Model, Prompt, Tool, Policy oder Schema erneut.

Für High-Stakes-Scores solltest du statt eines einzelnen großen Judges eine kleine Jury einsetzen. PoLL testete ein Panel kleinerer Judges aus disjunkten Model-Families und aggregierte deren Verdicts. Über sechs Datasets folgte das Panel menschlichen Bewertungen besser als ein einzelner GPT-4 Judge. Es vermied außerdem den Self-Preference-Bias des einzelnen Judges und kostete mehr als siebenmal weniger. Behalte Human Review für Entscheidungen bei, die Geld, Zugriff, Safety oder Compliance betreffen.

Wenn ein Judge bei deiner Aufgabe ein Kappa von 0,55 mit Menschen erreicht, verwende ihn nicht, um Deployments zu blockieren. Nutze ihn zum Sortieren von Review Queues. Liegt er nahe bei 0,75 und sind die Fehlerkosten moderat, lässt sich ein CI-Gate deutlich leichter vertreten.

Guardrails blockieren inline, Online-Evals beobachten danach

Byte says

Ich machte die Injection-Prüfung asynchron, um p95 zu schützen. Die erzeugten Scores waren identisch. Sie kamen nur an, nachdem der Tool-Aufruf bereits ausgeführt worden war.

Diese Konzepte werden häufig verwechselt, weil beide Scores erzeugen. Der Unterschied ist die Platzierung: inline im Request Path, vor dem Release oder nach der Response.

Guardrails laufen inline. Sie sind schnell und für den User sichtbar. Ein Guardrail kann einen Tool Call blockieren, PII redigieren, Prompt Injection zurückweisen oder vor dem Verlassen deines Systems einen Retry erzwingen. Ein False Positive ist ein Production-Bug. Ein False Negative ist leiser und schlimmer, weil nichts im Request Path darüber berichtet. Schema-, Range- und Policy-Checks sind deterministisch. Injection- und PII-Detection sind Classifier. Behandle Misses daher als erwartbar und lasse ein asynchrones Eval überwachen, was diese Checks durchlassen.

Offline-Evals laufen vor dem Release. Sie sind reproduzierbar. Sie gaten Prompts, Models, Tools, Retriever und Policies gegen ein fixes Dataset.

Online-Evals laufen nach der Response, normalerweise auf gesampeltem Traffic. Sie können langsamere LLM Judges einsetzen, weil sie nicht im Latency Path liegen. Ihre Aufgabe ist es, Drift zu erkennen, neue Failure Cluster zu finden und das nächste Offline-Dataset zu speisen.

Eine falsche Platzierung schadet in beide Richtungen:

  • Ein Judge im Request Path erhöht die Latency und führt eine weitere Flakiness-Quelle ein.
  • Ein Guardrail, das auf asynchrones Scoring verschoben wird, lässt Policy-Verletzungen bis zum User durch.

Bei Systemen mit hohem Volumen solltest du eine kleine Stichprobe mit einem stärkeren Judge bewerten und eine größere Stichprobe mit günstigeren Classifiers. Alarme sollten auf Clustern und Confidence Bounds basieren, nicht auf einem einzelnen verrauschten Point Estimate.

Tooling-Auswahl

Kein einzelnes Tool besitzt die gesamte Schleife. Vergleiche einen Trace-/Dataset-Store und einen CI-/Eval-Runner getrennt. Ein Produkt kann beides abdecken, du musst aber nicht beides bei einem Vendor kaufen.

Dies ist ein Autoren-Snapshot, geprüft am 16.08.2026. Jeder Link verweist auf die aktuelle Dokumentation, die ich für die jeweilige Capability-Aussage verwendet habe. Pläne, Lizenzen, API Keys, Provider-Zugriff und Infrastructure Requirements gelten weiterhin.

Die Trade-off-Hinweise beschreiben, wo Kosten entstehen, nicht deren Höhe. Pricing-Seiten ändern sich, und Vendors zählen unterschiedliche Einheiten: Traces, Observations, Spans, Scores, Users, Retention oder verarbeitete Daten. Prüfe die aktuellen Preise erneut, bevor du dich festlegst.

Empfehlungen nach Constraint:

  • Wähle Phoenix, wenn Self-Hosting, Privacy und OTel-kompatibles Tracing zwingend erforderlich sind und dein Team das Deployment betreiben kann.
  • Wähle Langfuse, wenn du zusätzlich Dataset-Versionierung und Experimente benötigst und den Storage Stack selbst betreiben oder die erforderlichen Add-ons kaufen kannst.
  • Wähle DeepEval, wenn Python-/pytest-CI-Pass-Fail der primäre Contract ist.
  • Wähle Inspect AI, wenn der Schwerpunkt auf Safety oder Frontier-Agent-Evaluation in konfigurierbaren Sandboxes liegt.
  • Wähle LangSmith, wenn die LangChain-/LangGraph-Integration die Enterprise-Anforderung für Hybrid- oder Self-Hosted-Deployment aufwiegt.
  • Wähle Braintrust, wenn Managed Pull-Request-Feedback und Experiment-Vergleiche einen API-Key-basierten Service rechtfertigen.
  • Wähle Promptfoo, wenn Prompt- oder Red-Team-Checks die wichtigste Regression Surface sind und ein Trace Store außerhalb des Scopes liegt.

Die Tool-Auswahl ist zweitrangig. Wenn Production-Fehler nicht zu Test-Cases werden, bezahlst du hauptsächlich für Trace Storage.

Praktische Rollout-Checkliste

Baue zunächst die Evidence Pipeline auf, bevor du den Metrik-Stack erweiterst. Entscheide zuerst, woher die Beispiele stammen.

  1. Sammle zuerst historische Runs. Wenn der Agent bereits existiert, hole Traces, Support-Tickets, Bug Reports, Thumbs-Down-Sessions, manuelle QA-Transkripte und Dogfooding-Notizen, bevor du die Implementierung änderst. Wenn der Agent noch nicht existiert, logge ab Tag eins jeden Prototype- und Manual-Test-Run.

  2. Instrumentiere die Trace Shape. Erfasse Messages, Tool Calls, Argumente, Tool Outputs, Errors, Token Counts, Latency, Kosten, User Feedback, App-Version, Prompt-Version, Model-Version, Tool-Schema-Version und den finalen Environment State. Verwende OpenTelemetry-GenAI-Conventions oder OpenInference-artige Spans, wenn du Portabilität möchtest. Nutze Langfuse, LangSmith, Phoenix oder Braintrust, wenn du sofort eine Trace UI und einen Dataset-Workflow benötigst.

  3. Mache aus realen Fehlern Seed Cases. Lies die Traces, bevor du sie mit einem Model zusammenfassen lässt. Speichere für jeden nützlichen Fehler Input, Source Trace ID, Expected State, Expected Tool Invariants, Failure Mode, Severity und Reviewer Note. Langfuse kann Dataset Items mit Production-Traces verknüpfen; LangSmith kann Datasets aus getraceten Runs erstellen. Bewahre den Source Link auf, damit der Case auditierbar bleibt.

  4. Wenn keine Historie existiert, generiere Cold-Start-Cases. Bitte ein LLM, Tasks aus Product Requirements, Policies, Tool Schemas, State Machines und Support Macros zu entwerfen. Decke Happy Paths und Fehler ab, etwa falsche Berechtigungen, fehlende Identity Checks, veraltete Tool Results, mehrdeutige Datumsangaben, Retries nach Rate Limits und widersprüchliche Tool Outputs.

  5. Vertraue Synthetic Cases erst nach Human Review. Synthetische Beispiele sind für Coverage nützlich, nicht für Truth. Markiere sie mit source: synthetic und verlange, dass ein Reviewer das Expected Outcome freigibt. Führe nach Möglichkeit einen Known-Good-Reference-Path aus und verwende unterschiedliche Model Families zur Case-Generierung und zur Bewertung des Ergebnisses.

  6. Baue ein kleines, ausgewogenes Dataset. Nimm Successes, Failures, Refusals, Boundary Cases, Long-Turn-Cases, Policy-Sensitive-Cases und valide alternative Pfade auf. Mache das Golden nicht zu „dem exakt alten Transkript“. Speichere zusätzlich zu den oben genannten Golden-Inhalten den Failure Mode, aufgrund dessen der Case in die Suite aufgenommen wurde.

  7. Füge zuerst deterministische Checks hinzu. Required Tool Order, wenn die Reihenfolge Policy ist, Required Arguments, Schema Validation, Final-State-Diffs, Loop Limits sowie Token- und Latency-Ceilings und aufgabenspezifische Invarianten sollten vor jedem Judge ausgeführt werden.

  8. Füge einen SGR-geprägten Judge hinzu. Verwende ihn nur für den Teil, der Interpretation erfordert. Kalibriere ihn anhand menschlicher Labels. Wenn er im Calibration Set gute und schlechte Beispiele nicht trennen kann, korrigiere das Rubric, bevor du ihn in CI integrierst.

  9. Verdrahte die Schleife. Führe die kleine Offline-Suite in CI aus, die größere Suite vor dem Release, bewerte gesampelten Production Traffic online und überführe wiederkehrende Online-Failure-Cluster zurück in das Offline-Dataset.

Deine erste Eval-Suite wird auf langweilige Weise fehlerhaft sein. Shippe sie trotzdem. Eine Suite, die du täglich ausführst, lässt sich leichter verbessern als ein perfektes Design-Dokument, das nie einen schlechten PR blockiert.
