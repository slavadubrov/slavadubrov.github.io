Was ist AI-Agent-Memory?

AI-Agent-Memory ist die State-Schicht, die es einem Agent ermöglicht, Task-Fortschritt zu bewahren, früheres Wissen abzurufen und sein Wissen über mehrere Runs hinweg zu aktualisieren. Ein Design kann Checkpoints, semantische oder strukturierte Stores sowie für Menschen lesbare Dokumente verwenden. Wähle nur die Stores, die für die Recall- und Recovery-Anforderungen des Produkts nötig sind.

Beginne nicht mit Memory, nur weil es intelligent klingt. Beginne mit dem für den User sichtbaren Fehler: verlorener Fortschritt, vergessene Präferenz, wiederholte Recherche oder die Unfähigkeit, eine Projektkonvention erneut zu verwenden.

Fehlerfälle, die Memory erfordern

Ein stateless Agent kann eine isolierte Frage beantworten, vergisst den Request aber, sobald der Call endet. Dieses Design scheitert, wenn das Produkt eines der folgenden Verhaltensweisen benötigt:

  • Pause und Resume: Ein User startet eine Recherche, schließt den Laptop und kehrt am nächsten Tag zurück. Ohne Checkpointed State startet der Agent von vorn.
  • Kohärenz über mehrere Turns: In einer langen Konversation muss sich der Agent merken, welche Tools er aufgerufen, welche Daten er gesammelt und welche Plan-Schritte er abgeschlossen hat.
  • Personalisierung: Ein wiederkehrender User erwartet, dass der Agent seine Risikotoleranz, bevorzugte Analysetiefe und früheren Interaktionen kennt.
  • Human-in-the-Loop (HITL): Der Agent sammelt seine Belege und wartet darauf, dass ein Mensch den nächsten Schritt freigibt. Der „wartende“ State muss Prozess-Neustarts überstehen.

Beim Market Analyst Agent aus Teil 1 erzeugt der Request „Analyze NVDA“ einen Plan, fünf Tool Calls, gesammelte Daten und einen Entwurf des Berichts. Wenn der User mit „sieht gut aus, aber füge eine Wettbewerbsanalyse hinzu“ antwortet, stellt ein Checkpoint den Plan und die Recherche ab dem letzten abgeschlossenen Schritt wieder her. Das Hinzufügen des Wettbewerbs-Schritts würde eine nachträgliche Interpretation und Replanning erfordern; die Begleitimplementierung setzt dieses Verhalten nicht um. Der Checkpoint liefert den vorherigen State, während die Anwendung entscheiden muss, wie der neue Request den Plan verändert.

Long-Term Memory behandelt einen anderen Fall. Wenn der User eine Woche später zurückkehrt und fragt: „Aktualisiere meine NVDA-Analyse“, muss sich der Agent möglicherweise an eine Präferenz für konservative Risikobewertungen und ein Interesse an Halbleiteraktien erinnern. Ein Vector-backed Memory Store kann diese Fakten über Sessions hinweg abrufen, ohne erneut danach zu fragen.

Die folgenden Implementierungsbeispiele verwenden LangGraph, LangChains Open-Source-Library zum Erstellen von Agents als explizite State Graphs; die von ihr gezogenen Storage-Grenzen lassen sich auf jedes Framework übertragen. Betrachte die fortlaufende „Analyze NVDA“-Konversation eines Users als einen Thread. Jedes Ausführen des Graphen, um eine Antwort zu geben oder die Konversation fortzusetzen, ist ein Run innerhalb dieses Threads. Während ein Run aktiv ist, bilden der Model-Kontext und die lokalen Variablen des Programms das Working Memory; sie verschwinden, sobald diese Arbeit endet. LangGraph bezeichnet State, der für diesen einen Thread gespeichert wird, als Short-Term Memory, und Fakten, die für andere Threads verfügbar sind, als Long-Term Memory. Im Folgenden bedeuten „Thread“ und „Konversation“ dasselbe. Teil 5 verwendet „Session“ für das persistente Protokoll eines einzelnen Runs; deshalb vermeidet dieser Artikel den Begriff für die Konversation.

Eine Taxonomie für AI-Agent-Memory

Bevor wir zur Implementierung kommen, hilft es, zu klassifizieren, woran sich Agents erinnern müssen. Das CoALA-Framework — Cognitive Architectures for Language Agents (Sumers, Yao et al., 2023) — ist eine häufig zitierte Taxonomie, die auf der Kognitionswissenschaft aufbaut. Working Memory enthält die aktuellen Beobachtungen, abgerufenen Fakten und Zwischenergebnisse des aktiven Runs. Ein Teil davon liegt in Application-Variablen; die ausgewählten Messages und Tool Results bilden den Input des Models. Dieser Input muss in das Context Window des Models passen, während der Application State größer sein und über mehrere Schritte hinweg persistieren kann. Ohne explizites Speichern geht Process Memory bei einem Crash verloren. Die anderen Tiers liefern Informationen für diesen Working State.

Short-Term Memory ist der Checkpoint, den LangGraph nach jeder Einheit der Graph-Ausführung schreibt — einem Super-Step, der im nächsten Abschnitt definiert wird. Episodic und Semantic Memory persistieren über Threads hinweg. Document Memory speichert Projektnotizen, Forschungszusammenfassungen und gelernte Konventionen in Dateien, die Menschen und Agents prüfen können. Procedural Memory umfasst System Instructions, Tool Definitions und wiederverwendbare Verfahren, die für eine Task abgerufen werden können. Die Lebensdauern in der Tabelle sind beispielhaft; die Aufbewahrung folgt der Policy der Anwendung, und Working State kann während eines gesamten aktiven Runs bestehen bleiben.

Für die Implementierung reduzieren sich fünf der sechs Kategorien auf drei Storage-Tiers. Short-Term Memory wird zu Hot Memory, dem Checkpoint für den aktuellen Thread. Episodic und Semantic werden zu Cold Memory, also Recall über Threads hinweg. Document Memory bewahrt angesammeltes Projektwissen lesbar und direkt bearbeitbar auf. Working Memory wird der Hot-Tier zugerechnet, weil Checkpoints den State bewahren können, der zur Rekonstruktion eines aktiven Runs erforderlich ist. Ein Checkpoint ist nicht die vollständige interne Berechnung des Models. Procedures können mit dem Agent ausgeliefert oder in Dateien beziehungsweise einem anderen Store gespeichert und daraus abgerufen werden. Diese Tiers beschreiben die Implementierungsentscheidungen dieses Artikels, keine sich gegenseitig ausschließenden Memory-Typen.

CoALA klassifiziert Working, Episodic, Semantic und Procedural Memory. Die Studie Memory in the Age of AI Agents organisiert Memory stattdessen nach Form, Funktion und Dynamik, einschließlich Dokumenten, Codebases und wiederverwendbaren Workflows. Dateien können mehrere dieser Kategorien implementieren. Dieser Artikel benennt Document Memory separat, damit seine Storage- und Maintenance-Verantwortlichkeiten sichtbar bleiben.

Dasselbe Storage-Pattern findet sich auch in anderen Domänen. Ein Minecraft Agent (Voyager) speichert wiederverwendbare Game Skills als Code-Libraries, und Web Agents leiten aus erfolgreichen Runs wiederverwendbare Browsing-Workflows ab. Auf beide komme ich später zurück. Inspizierbare Dateien und indexiertes Retrieval können koexistieren: Voyager ruft Programme über Embeddings ihrer Beschreibungen ab.

Von einer festen RAG-Pipeline unterscheidet sich agent-managed Memory außerdem dadurch, wer den Write ausführt. Der Agent oder sein Harness wählt aus, was gespeichert, aktualisiert und gelöscht wird, und entscheidet später, wann es abgerufen wird.

Die Studie Generative Agents (Park et al., 2023) zeigte, wie weit dies gehen kann: Simulierte Agents speicherten, reflektierten über und riefen ihre eigenen Memories ab. Ihr Memory Stream bewertete Kandidaten nach Recency, Importance und Relevance — ein Design, das weiterhin einen nützlichen Referenzpunkt für Agent-Memory-Retrieval darstellt.

Compaction hält eine Konversation nutzbar

Ein größeres Context Window beseitigt nicht die Notwendigkeit, auszuwählen, was erhalten bleibt. Aktuelle APIs können eine ältere Konversation zusammenfassen, bevor sie das Window füllt. Claudes serverseitige Compaction gibt, am 2026-09-06 noch als Beta-Feature, einen compaction-Block zurück, den nachfolgende Requests anstelle der früheren Inhalte verwenden. Das kann den Aufwand für clientseitige Zusammenfassungen reduzieren, aber in der Summary kann ein später benötigter Fakt fehlen.

Bewahre maßgeblichen Task-State außerhalb dieser Summary auf: abgeschlossene Effects, Freigaben, Quellenreferenzen und exakte User-Constraints. Ein Checkpoint stellt die Ausführung wieder her; Compaction verkürzt den Model-Kontext; Long-Term Memory wählt Wissen für eine andere Konversation aus. Teste diese drei Verhaltensweisen getrennt. Erzwinge in der Mitte eines Tests eine Compaction und prüfe, ob die nächste Action weiterhin eine frühere Constraint einhält. Verwende ein compacted Transcript nicht als einzigen Nachweis dafür, was freigegeben wurde.

Short-Term Agent-Memory: der Checkpoint Store

Byte says

Ein Checkpoint ist kein Audit Log: Er zeichnet genug State für ein Resume auf, nicht jedes Event, das dorthin geführt hat.

LangGraph checkpointet den Graph-State an Super-Step-Grenzen — einen Node oder einen Batch parallel ausgeführter Nodes. Mit dem Default durability="async" kann der nächste Schritt laufen, während dieser Write abgeschlossen wird; durability="sync" wartet vor dem Fortfahren auf die Persistence und fügt Write-Latency hinzu. Crash Recovery verwendet den letzten persistent gespeicherten Checkpoint, nicht zwingend den zuletzt abgeschlossenen Schritt. Das ist die Grundlage für Pause/Resume, Time-Travel-Debugging und HITL-Workflows.

Ein Checkpoint enthält den für ein Resume nötigen Graph-State: das AgentState aus Teil 1 — Messages, Identity, User Profile, Plan Steps, Research Data und Execution Mode. Nach einem HITL-Interrupt oder Prozess-Neustart stellt LangGraph den zuletzt gespeicherten State wieder her und verwendet seine Scheduling-Metadaten, um den nächsten Node auszuwählen. Das Resume erfolgt an einer abgeschlossenen Node-Grenze, nicht an einer beliebigen Python-Zeile. Zu den gespeicherten Details gehören eine Checkpoint-ID und ein Timestamp, eine Version für jeden Channel (LangGraphs Bezeichnung für einen State-Key) sowie die Channel-Versionen, die jeder Node bereits gesehen hat. Die Step-Nummer ist Metadaten dieses Checkpoints. Ein Checkpoint unterscheidet sich außerdem von einem Append-only Event Log oder Trace; Teil 5 trennt diese Runtime-Observability-Flächen ausdrücklich.

So funktioniert Checkpointing in LangGraph

LangGraphs BaseCheckpointSaver ist ein einfaches Interface: put() schreibt einen Checkpoint, get_tuple() liest den neuesten für einen Thread, und list() gibt die History zurück. Jeder Checkpoint wird über (thread_id, checkpoint_ns, checkpoint_id) adressiert, wobei thread_id die Konversation identifiziert, checkpoint_ns das Namespacing von Subgraphs übernimmt und checkpoint_id eine eindeutige Version ist.

Die entscheidende Frage ist, welcher Backend darunter liegt. PostgreSQL und Redis sind zwei gängige Production-Optionen.

PostgreSQL: der durable Default

PostgreSQL ist für die meisten Teams der sicherere Default. Checkpoints überstehen Crashes, du erhältst vollständige Transaction-Semantics, und die Checkpoint-History macht Time-Travel-Debugging unkompliziert.

Eine vereinfachte Version des Checkpoint-Setups aus memory/hot.py. Wenn ein Angreifer Checkpoints schreiben könnte, setze LANGGRAPH_STRICT_MSGPACK=true oder konfiguriere allowed_msgpack_modules. Dadurch wird die Deserialisierung auf sichere oder deklarierte Typen beschränkt; der permissive Default warnt vor nicht registrierten Typen, erlaubt sie aber weiterhin.

import asyncio
from contextlib import asynccontextmanager

from langchain_core.messages import HumanMessage
from langgraph.checkpoint.postgres.aio import AsyncPostgresSaver

@asynccontextmanager
async def postgres_checkpointer(connection_string: str):
    """Yield a PostgreSQL-backed checkpoint store.

    PostgreSQL gives us ACID guarantees — if a checkpoint write succeeds,
    the state is durable even if the process crashes immediately after.
    `from_conn_string` is itself an async context manager: it owns the
    connection and closes it on exit, so the graph has to run inside it.
    """
    async with AsyncPostgresSaver.from_conn_string(connection_string) as checkpointer:
        # Create the checkpoint tables if they don't exist.
        # This is idempotent — safe to call on every startup.
        await checkpointer.setup()
        yield checkpointer

async def main(authenticated_user_id: str) -> None:
    # The graph lives inside the context manager's scope.
    async with postgres_checkpointer(
        "postgresql://user:pass@localhost:5432/agent_memory"
    ) as checkpointer:
        graph = create_graph(checkpointer=checkpointer)

        # Every invoke/stream call now persists state automatically.
        config = {"configurable": {"thread_id": "user-123-session-1"}}
        result = await graph.ainvoke(
            {"user_id": authenticated_user_id,
             "messages": [HumanMessage(content="Analyze NVDA")]}, config
        )

        # After the server authenticates the approver and validates approval
        # of this exact draft, update the companion's approval field.
        await graph.aupdate_state(config, {"report_approved": True})
        # Continue the static interrupt_before pause; new input starts a new run.
        result = await graph.ainvoke(None, config)

# Local fixture identity. A server supplies this only after authentication.
asyncio.run(main(authenticated_user_id="user-123"))

Das user_id im Graph-Input stammt aus dem authentifizierten Server-Kontext; thread_id lokalisiert lediglich Checkpoints und stellt weder Identity fest noch autorisiert es den Zugriff auf einen Thread. Der AsyncPostgresSaver verwendet das Package langgraph-checkpoint-postgres, das vier Tabellen erzeugt: checkpoints (der serialisierte State), checkpoint_blobs (große Binärdaten), checkpoint_writes (ausstehende Writes für Crash Recovery) und checkpoint_migrations (Schema-Version). Concurrent Writers werden über den Primary Key (thread_id, checkpoint_ns, checkpoint_id) und Upserts statt über Locking getrennt — zwei Worker desselben Threads überschreiben einander nicht, koordinieren sich aber ebenfalls nicht.

Redis: wenn Latency der Bottleneck ist

Wenn Checkpoint-Latency der Bottleneck ist, ist Redis eine Option für recoverable State. Miss vor der Entscheidung für Redis gegenüber PostgreSQL die serialisierte State-Größe, Persistence-Settings und Concurrency.

Eine vereinfachte Version des Checkpoint-Setups aus memory/hot.py:

import asyncio
from contextlib import asynccontextmanager

from langgraph.checkpoint.redis.aio import AsyncRedisSaver

@asynccontextmanager
async def redis_checkpointer(redis_url: str):
    """Yield a Redis-backed checkpoint store.

    Redis keeps checkpoints in memory for low-latency access.
    Durability depends on RDB snapshots, AOF fsync policy, and replication.
    AOF with appendfsync everysec can still lose about one second of writes
    after a crash; enabling AOF alone is not a no-loss guarantee.
    """
    async with AsyncRedisSaver.from_conn_string(redis_url) as checkpointer:
        # Initialize Redis data structures
        await checkpointer.asetup()
        yield checkpointer

async def main() -> None:
    # Same graph API, different backend.
    async with redis_checkpointer("redis://localhost:6379") as checkpointer:
        graph = create_graph(checkpointer=checkpointer)

asyncio.run(main())

Das AsyncRedisSaver aus langgraph-checkpoint-redis speichert jeden Checkpoint als eigenes RedisJSON-Dokument unter demselben (thread_id, checkpoint_ns, checkpoint_id)-Key wie der Postgres Saver. Das Redesign von v0.1.0 bettete Checkpoint-Werte ein und ersetzte das Retrieval pro Channel durch einen JSON.GET-Pfad. Diese Änderung betrifft das Value Retrieval, nicht jede Persistence-Operation; die Latency-Messungen des Vendors hängen von dessen Workload ab. Redis 8.0+ enthält RedisJSON und RediSearch standardmäßig — es müssen keine zusätzlichen Module installiert werden.

Wähle die Redis-Persistence- und fsync-Policy anhand des tolerierten Verlustfensters. RDB kann Writes seit dem letzten Snapshot verlieren; die übliche AOF-Policy appendfsync everysec kann ungefähr eine Sekunde verlieren. always tauscht Write-Latency gegen stärkere Persistence, während no das Flushing dem OS überlässt. Teste die Recovery mit den tatsächlichen Disk- und Replication-Settings.

Für RAM-beschränkte Deployments speichert ShallowRedisSaver nur den neuesten Checkpoint pro Thread — keine History, aber minimalen RAM-Verbrauch. Verwende dies, wenn du Pause/Resume benötigst, aber kein Time-Travel-Debugging.

Wann welche Option?

Verwende PostgreSQL, wenn:

  • du die vollständige Checkpoint-History für Time-Travel-Debugging oder reproduzierbares Resume brauchst
  • Durability nicht verhandelbar ist (Finanzdienstleistungen, Gesundheitswesen)
  • du PostgreSQL bereits in deinem Stack betreibst
  • dein Agent lange Tasks ausführt, bei denen verlorener State stundenlange Neuberechnung bedeutet
  • du einen Unified Data Store möchtest — PostgreSQL mit pgvector kann ein einzelnes Backend für Checkpoints, Long-Term Memory und Vector Search sein

Verwende Redis, wenn:

  • Checkpoint-Latency dein Bottleneck ist (Real-Time-Chat, Streaming-UX)
  • du Voice Bots oder Streaming-Erlebnisse entwickelst, bei denen der Zugriff auf Checkpoints auf einem gemessenen latency-kritischen Pfad liegt
  • du horizontale Skalierung über viele unabhängige Threads benötigst. Wenn mehrere Agents gemeinsamen State ändern, gib diesem State einen Owner und koordiniere außerhalb des Checkpoint Savers.
  • es sich um kurzlebige Sessions handelt, bei denen der Verlust eines Checkpoints wiederherstellbar ist
  • du Semantic Caching zur Reduzierung redundanter LLM Calls einsetzen möchtest (Redis LangCache cached semantisch ähnliche Queries, um wiederholte LLM Calls zu vermeiden)

Weitere Optionen: langgraph-checkpoint-sqlite funktioniert für lokale Entwicklung und Single-Process-Deployments. Für AWS-native Stacks stellt langgraph-checkpoint-aws einen DynamoDBSaver mit automatischem Payload-Offloading bereit — der dokumentierte Saver lagert Payloads oberhalb seines 350-KB-Schwellenwerts aus, wenn ein S3-Bucket konfiguriert ist. Dieser Schwellenwert ist eine Implementierungs-Policy, nicht das 400-KB-Item-Limit von DynamoDB. Serverless-Pricing und keine zu verwaltende Infrastruktur machen diese Option für Deployments mit variablem Load attraktiv.

Long-Term Memory: Erinnern über Sessions hinweg

Hot Memory behandelt die aktuelle Konversation. Long-Term Memory betrifft den User, der nächste Woche zurückkehrt: Es speichert Fakten, Präferenzen und Interaktionshistorie, die über Threads hinweg bestehen bleiben.

LangGraph stellt über sein BaseStore-Objekt ein Store-Interface für Thread-übergreifendes Memory bereit. Jedes Memory-Item ist ein (namespace, key)-Paar mit einem JSON-Wert und optionalem Vector Embedding. Der Namespace codiert üblicherweise User oder Organisation: ("user", "user-123", "preferences").

Vector Storage: semantischer Recall mit Qdrant

Wenn der Agent unstrukturierte Fakten abrufen muss („Was sagte der User über seinen Anlagehorizont?“), bietet Vector Search semantischen Recall. Statt über exakte Keys zu suchen, fragt der Agent nach Bedeutung.

Qdrant ist eine auf Vectors spezialisierte, in Rust geschriebene Vector Database, die Embedding Storage, Indexing (Hierarchical Navigable Small World oder HNSW) und gefilterte Suche unterstützt. HNSW und seine Trade-offs habe ich ausführlich in meinem Beitrag über Search Ranking behandelt. Qdrant bietet außerdem einen MCP Server, der als semantische Memory-Schicht fungiert — nützlich, wenn dein Agent-Framework das Model Context Protocol unterstützt.

Das Folgende ist ein unabhängiges illustratives Qdrant-Design. Es ist keine vereinfachte Version des aktuellen memory/long.py. Das aktuelle Projekt speichert User Profiles mit exaktem user_id-Filtering und einem Zero-Vector-Placeholder. Eine echte Embedding-Integration ist weiterhin zukünftige Arbeit. Der Request Handler muss den Request authentifizieren und principal aus der verifizierten Identity erstellen; der Client liefert ihn niemals selbst. Der Qdrant-Filter definiert den Retrieval-Scope, nicht die Authorization.

from qdrant_client import QdrantClient
from qdrant_client.models import (
    PointStruct, Distance, VectorParams, Filter, FieldCondition, MatchValue,
)
import hashlib
import json
from dataclasses import dataclass

@dataclass(frozen=True)
class AuthenticatedPrincipal:
    """Created by the server after authentication, never from request JSON."""
    user_id: str

class UserMemoryStore:
    """Long-term memory backed by Qdrant vector search.

    Stores user facts as embedded vectors for semantic retrieval.
    Each fact is a short natural-language statement about the user.
    """

    def __init__(self, qdrant_url: str, collection_name: str = "user_memory"):
        self.client = QdrantClient(url=qdrant_url)
        self.collection_name = collection_name
        self._ensure_collection()

    def _ensure_collection(self):
        """Create the collection if it doesn't exist."""
        collections = [c.name for c in self.client.get_collections().collections]
        if self.collection_name not in collections:
            self.client.create_collection(
                collection_name=self.collection_name,
                vectors_config=VectorParams(
                    size=1536,  # text-embedding-3-small dimensions
                    distance=Distance.COSINE,
                ),
            )

    def store_fact(
        self, principal: AuthenticatedPrincipal, fact: str, embedding: list[float]
    ):
        """Store a user fact with its embedding."""
        identity = json.dumps([principal.user_id, fact], ensure_ascii=False).encode()
        point_id = hashlib.sha256(identity).hexdigest()[:32]
        self.client.upsert(
            collection_name=self.collection_name,
            points=[PointStruct(
                id=point_id,
                vector=embedding,
                payload={"user_id": principal.user_id, "fact": fact},
            )],
        )

    def recall(
        self,
        principal: AuthenticatedPrincipal,
        query_embedding: list[float],
        top_k: int = 5,
    ):
        """Retrieve the most relevant facts for a user given a query."""
        results = self.client.query_points(
            collection_name=self.collection_name,
            query=query_embedding,
            query_filter=Filter(
                must=[FieldCondition(
                    key="user_id", match=MatchValue(value=principal.user_id)
                )]
            ),
            limit=top_k,
        )
        return [hit.payload["fact"] for hit in results.points]

Die Point-ID hasht ein JSON-Array aus User-ID und Fakt, damit Delimiter innerhalb eines der beiden Werte nicht zwei Identitäten zusammenführen können. Beispielsweise muss sich User a:b mit dem Fakt c von User a mit dem Fakt b:c unterscheiden. Die 32 hexadezimalen Zeichen passen in Qdrants UUID-Repräsentation für Point-IDs.

Der Ablauf besteht aus drei Schritten. In diesem illustrativen Design extrahiert ein LLM zentrale Fakten aus der Interaktion („User hat eine hohe Risikotoleranz“, „User interessiert sich für Halbleiteraktien“). Diese Fakten werden embeddet und in Qdrant gespeichert. Zu Beginn der nächsten Konversation stellt der Server den authentifizierten Principal bereit, und der Agent fragt Qdrant mit der neuen User-Message ab, um relevanten Kontext abzurufen. Der aktuelle Market Analyst Agent implementiert diesen semantischen Extraktions- und Embedding-Flow noch nicht.

Retrieval Scoring: über Cosine Similarity hinaus

Raw Cosine Similarity ist ein Ausgangspunkt, aber Production-Memory-Systeme benötigen ein umfangreicheres Retrieval. Die Studie Generative Agents (Park et al., 2023) führte eine Scoring-Funktion ein, die drei Signale kombiniert:

  • Recency: Regelbasierter Verfall, sodass neuere Memories höher bewertet werden. Eine exponentielle Decay-Funktion lässt einen Fakt von gestern einen gleichwertigen Fakt von vor sechs Monaten übertreffen.
  • Importance: Vom LLM bewertete Signifikanz auf einer Skala von 1 bis 10. „Das Portfolio des Users ist um 40 % gefallen“ erhält einen höheren Score als „User sagte hallo.“
  • Relevance: Cosine Similarity des Embeddings zwischen Query und gespeichertem Fakt.

Die Studie normalisiert alle drei Signale vor der Kombination auf vergleichbare Skalen. Tu dasselbe, bevor du die Weights tunest; ein roher Importance-Score von 1–10 würde sonst ein Signal von 0–1 dominieren. Der finale Retrieval-Score ist eine gewichtete Summe: score = alpha * recency + beta * importance + gamma * relevance. Dadurch werden aktuelle, wichtige Fakten nicht unter veralteten, aber semantisch ähnlichen Fakten begraben. Für einen Prototyp zur Finanzanalyse würde ich zunächst alpha = 0.3 für Recency, beta = 0.2 für Importance und gamma = 0.5 für Relevance verwenden, da die aktuelle Query gewöhnlich bestimmt, welcher ansonsten gültige Fakt in den Kontext gehört. Die Studie Generative Agents verwendete gleiche Gewichte; diese Werte sind ein vorgeschlagener Startpunkt, keine gemessene Verbesserung. Tune sie anhand von Held-out-Recall und Checks der Task-Qualität, bevor du dich darauf verlässt.

Alternativen zu Vector Search

Vector Search ist leistungsfähig, aber nicht immer das richtige Tool. Hier ist, wann Alternativen sinnvoll sind:

Key-Value Store (Redis)Strukturierte User Profiles und PräferenzenRAM-Verbrauch und Persistence-Policy

Key-Value Stores eignen sich gut für strukturierte Daten. Wenn dein Long-Term Memory ein User Profile ist — Risikotoleranz, Anlagehorizont, bevorzugte Sektoren — ist ein Redis-Hash oder eine PostgreSQL-JSONB-Spalte einfacher und schneller als das Embeddieren und Abfragen von Vectors. Verwende Vector Search, wenn die Memory unstrukturiert ist und die Retrieval-Query in ihrer Formulierung variiert.

LangGraphs integrierter Store stellt ein Namespace-basiertes Key-Value-Interface mit optionaler Vector Search bereit. Die BaseStore-API ist einfach: put(), get(), search() und delete() mit hierarchischem Namespace-Scoping. Es gibt drei Implementierungen:

  • InMemoryStore — für Development und Testing (Daten gehen beim Prozessende verloren)
  • PostgresStore — persistenter Production Store mit vollständigen SQL-Queries
  • AsyncRedisStore — Thread-übergreifendes Memory mit Vector Search, TTL-Support und Metadata-Filtering

Die Konfiguration index aktiviert Vector Search über gespeicherte Items mit einem konfigurierbaren Embedding Model. Für viele Use Cases ist dieser integrierte Store ausreichend, ohne eine dedizierte Vector Database einzusetzen.

import asyncio
from langgraph.store.memory import InMemoryStore

# Create a store with vector search enabled
store = InMemoryStore(
    index={
        "dims": 1536,
        "embed": my_embedding_function,  # e.g., OpenAI text-embedding-3-small
    }
)

async def main() -> None:
    # Store a user preference (namespace scopes to user).
    await store.aput(
        namespace=("user", "user-123", "preferences"),
        key="risk-profile",
        value={"risk_tolerance": "high", "horizon": "long-term"},
    )

    # Semantic search across the user's memories.
    # The namespace prefix is positional here — `search`/`asearch` declare it
    # as positional-only `namespace_prefix`, unlike `aput`.
    results = await store.asearch(
        ("user", "user-123"),
        query="What is their investment style?",
        limit=5,
    )

asyncio.run(main())

Eine Strategie für Long-Term Memory auswählen

Beginne mit Key-Value, wenn dein Memory strukturiert und klar definiert ist (User Profiles, Settings, benannte Entitäten). Füge Vector Search hinzu, wenn du semantisches Retrieval über unstrukturierte Fakten benötigst oder die Query-Formulierung unvorhersehbar variiert.

Knowledge Graphs lohnen sich, wenn Beziehungen zwischen Entitäten wichtig sind, etwa: „Über welche Unternehmen hat der User gefragt, die Konkurrenten von NVDA sind?“ Das interessanteste neuere Projekt ist hier Graphiti (von Zep), das einen temporal-aware Knowledge Graph aufbaut, der festhält, wann Fakten gültig waren, nicht nur was gültig war. Seine zeitlichen Beziehungen können Gültigkeitsintervalle und abgelöste Werte bewahren; Extraktions- und Update-Logik bestimmen weiterhin, ob ein Fakt aktuell ist. Die Zep-Studie berichtet für das evaluierte Zep-System mit Graphiti und GPT-4 Turbo eine DMR-Accuracy von 94,8 %, gegenüber 94,4 % für Full Context. DMR verwendet Konversationen mit 60 Messages und eine begrenzte Fact-Retrieval-Task. Dieser geringe Abstand belegt keinen allgemeinen Vorteil temporaler Graphen.

Der Haken ist operativ. Der Betrieb einer Graph Database ist nicht trivial, und für die meisten Agent-Anwendungen deckt Vector Search mit Metadata Filtering denselben Bereich mit weniger Infrastruktur ab.

Managed Memory Frameworks wie Mem0 und Letta (früher MemGPT) übernehmen die Pipeline aus Extraction, Consolidation und Retrieval. Bemerkenswert an Mem0 ist: Ein LLM extrahiert mögliche Memories, eine Decision Engine vergleicht jeden neuen Fakt mit vorhandenen Einträgen im Vector Store, und ein Resolver entscheidet über Add, Update, Delete oder No-op. Dadurch bleibt der Memory Store konsistent und redundant-frei. Letta verfolgt einen Ansatz aus der Betriebssystemwelt: Agents verwalten ihr eigenes Context Window mit Memory-Management-Tools und verschieben Daten autonom zwischen „Core Memory“ (in-context) und „Archival Memory“ (out-of-context). Beide sind eine Evaluierung wert, wenn du schneller in Production kommen möchtest und keine vollständige Kontrolle über die Memory-Pipeline benötigst.

Document Memory: der Aktenschrank des Agents

Vector Stores und Key-Value-Backends behandeln semantischen Recall und strukturierte Lookups gut. Angesammelter Projektkontext — Konventionen, Forschungsnotizen und über Sessions hinweg bewahrte Entscheidungen — gehört häufig in Dateien, die Menschen lesen, prüfen und versionieren können.

Das ist Document Memory: Der Agent liest und schreibt strukturierte Dateien (Markdown, JSON, YAML) in ein bekanntes Verzeichnis. Keine Embeddings, keine Datenbank, keine Infrastruktur. Nur Dateien auf Disk, die sowohl der Agent als auch der Developer cat, grep, git diff und manuell bearbeiten können.

In einer von einem Vendor durchgeführten Evaluation berichtete Letta 74,0 % Accuracy auf LoCoMo — einem Long-Conversation-Question-Answering-Benchmark — für einen GPT-4o-mini-Agent mit angehängten Dateien, automatischen Embeddings, semantischem search_files und verpflichtenden Search-Tool-Regeln. Mem0s beste Graph-Variante erzielte 68,5 %. Dies ist ein einzelner Vendor, ein Model, ein Benchmark und ein Harness. Es zeigt, dass ein file-facing Interface in diesem Setup gut funktionieren kann; es zeigt nicht, dass Raw Markdown oder Keyword Search ausreicht. Der operative Vorteil ist davon getrennt: Developer können das gespeicherte Wissen direkt lesen, bearbeiten und diffen.

Größere Context Windows machen auch das Lesen vollständiger Dateien für bestimmte Projektdokumente praktikabel. Chunked Retrieval passt weiterhin zu großen Korpora, aber eine kurze Konventions- oder Handoff-Datei kann oft direkt geladen werden. Die Entscheidung hängt von Dokumentgröße, Retrieval-Präzision, Context-Budget und der Häufigkeit ab, mit der Menschen den Memory prüfen oder bearbeiten müssen.

Warum Dateien?

Für ein langlebiges Agent-Projekt solltest du ein Verzeichnis mit gut organisierten Notizen verwenden, wenn Menschen einen prüfbaren Nachweis benötigen. Betrachte einen Coding Agent, der wochenlang an einem Projekt arbeitet:

  • Er lernt, dass das Projekt Pydantic v2 und nicht v1 verwendet
  • Er entdeckt, dass Tests mit pytest -x --tb=short ausgeführt werden müssen
  • Er sammelt Wissen über die Architektur der Codebase
  • Er lernt die Präferenzen des Developers („immer pathlib verwenden, niemals os.path“)

Diese Fakten könnten in einem Vector- oder Key-Value-System liegen. Dateien sind hier der bessere Default, weil der Developer verbundene Notizen lesen, bearbeiten, prüfen und versionieren muss. Füge Keyword- oder Semantic Search erst hinzu, wenn das Dokumentenkorpus und das Query-Pattern dies erfordern. Wenn der Agent etwas Falsches lernt, öffnest du die Datei und korrigierst es.

Claude Code, Cursor und Devin Desktop verwenden Varianten dieses Patterns. Die folgenden Beispiele zeigen, wie die jeweiligen Systeme ihre Dateien speichern und laden.

Einen File-Memory-Store implementieren

Die Implementierung ist bewusst einfach. Der Agent erhält vier Operationen: ein Dokument schreiben, ein Dokument lesen, verfügbare Dokumente auflisten und per Keyword über Dokumente hinweg suchen.

Das Folgende ist ein unabhängiger illustrativer Raw-Markdown-File-Store. Es ist keine vereinfachte Version des aktuellen memory/document.py. Das aktuelle Projekt verwendet DocumentMemory, das einen Namespace und Key benötigt und einen JSON-Envelope mit content, metadata und created_at schreibt. Diese Skizze definiert ein anderes Design, um den Trade-off menschenlesbarer Markdown-Dateien zu zeigen:

from pathlib import Path
import json

class FileMemory:
    """Document memory backed by the local filesystem.

    Stores agent knowledge as human-readable files organized by topic.
    No embeddings, no database — just files that both the agent and
    the developer can read, edit, and version-control.
    """

    def __init__(self, base_dir: str | Path):
        self.base_dir = Path(base_dir).resolve()
        self.base_dir.mkdir(parents=True, exist_ok=True)

    def _resolve_path(self, path: str) -> Path:
        """Return a path inside base_dir, rejecting escapes and symlinks."""
        requested = Path(path)
        if requested.is_absolute() or ".." in requested.parts:
            raise ValueError("path must be relative to base_dir without traversal")
        resolved = (self.base_dir / requested).resolve()
        try:
            resolved.relative_to(self.base_dir)
        except ValueError as error:
            raise ValueError("path must stay inside base_dir") from error
        return resolved

    def write_doc(self, path: str, content: str, metadata: dict | None = None):
        """Write or overwrite a document at the given path.

        Paths are relative to base_dir. Directories are created automatically.
        Metadata (if provided) is stored as a JSON sidecar file.
        """
        full_path = self._resolve_path(path)
        full_path.parent.mkdir(parents=True, exist_ok=True)
        full_path.write_text(content, encoding="utf-8")

        if metadata:
            meta_path = self._resolve_path(
                str(full_path.relative_to(self.base_dir).with_suffix(full_path.suffix + ".meta"))
            )
            meta_path.write_text(json.dumps(metadata, indent=2), encoding="utf-8")

    def read_doc(self, path: str) -> str | None:
        """Read a document by path. Returns None if not found."""
        full_path = self._resolve_path(path)
        if full_path.exists():
            return full_path.read_text(encoding="utf-8")
        return None

    def list_docs(self, pattern: str = "**/*") -> list[str]:
        """List documents matching a glob pattern."""
        self._resolve_path(pattern)
        return [
            str(self._resolve_path(str(p.relative_to(self.base_dir))).relative_to(self.base_dir))
            for p in self.base_dir.glob(pattern)
            if self._resolve_path(str(p.relative_to(self.base_dir))).is_file()
            and not p.name.endswith(".meta")
        ]

    def search_docs(self, query: str, pattern: str = "**/*.md") -> list[dict]:
        """Search documents by keyword. Returns matching files with context.

        This is intentionally simple — grep-style keyword search.
        For semantic search, use a vector store instead.

        # ponytail: linear scan of file bytes; add an index when measured
        # latency, concurrency, or retrieval quality requires it.
        """
        self._resolve_path(pattern)
        results = []
        for path in self.base_dir.glob(pattern):
            path = self._resolve_path(str(path.relative_to(self.base_dir)))
            if not path.is_file() or path.name.endswith(".meta"):
                continue
            content = path.read_text(encoding="utf-8")
            if query.lower() in content.lower():
                # Return the paragraph containing the match for context
                for paragraph in content.split("\n\n"):
                    if query.lower() in paragraph.lower():
                        results.append({
                            "path": str(path.relative_to(self.base_dir)),
                            "match": paragraph.strip()[:500],
                        })
        return results

Der Path Helper wird bewusst von Reads, Writes und Glob Results gemeinsam verwendet: Relative Paths können durch .. oder einen bestehenden Symlink weiterhin aus einem Verzeichnis herausführen. Diese illustrative Klasse ist für ein vertrauenswürdiges Single-User- oder kontrolliertes Filesystem gedacht. Sie prüft vor der Verwendung einen aufgelösten Path; an einer feindlichen Multi-Tenant-Grenze solltest du Descriptor-relative No-Follow-Operationen verwenden, damit eine Filesystem-Mutation diese Prüfung nicht überholen kann. Führe diesen kleinen Regression Check nach dem Kopieren der Klasse aus:

from tempfile import TemporaryDirectory

with TemporaryDirectory() as root:
    memory = FileMemory(root)
    memory.write_doc("notes/ok.md", "safe memory")
    assert memory.read_doc("notes/ok.md") == "safe memory"
    assert memory.list_docs() == ["notes/ok.md"]
    assert memory.search_docs("safe")[0]["path"] == "notes/ok.md"

    (Path(root) / "escape").symlink_to(Path(root).parent, target_is_directory=True)
    for operation in (
        lambda: memory.write_doc("../escape.md", "nope"),
        lambda: memory.read_doc("/tmp/escape.md"),
        lambda: memory.read_doc("escape/outside.md"),
        lambda: memory.list_docs("../**/*"),
        lambda: memory.search_docs("safe", "../**/*.md"),
    ):
        try:
            operation()
        except ValueError:
            pass
        else:
            raise AssertionError("FileMemory accepted an escaped path")

Folder-Struktur

Der größte Wert von Document Memory entsteht durch die Struktur des Verzeichnisses. So würde ich es für einen Research Agent anlegen. Der Market Analyst Agent verwendet Namespaces unter memory/documents/, aber sein aktueller DocumentMemory schreibt jeden Eintrag als JSON-Envelope mit einem content-String statt als Raw Markdown. Das Raw-Markdown-Layout unten gehört zum unabhängigen illustrativen Design FileMemory von oben:

    user-profiles/

Im illustrativen Design FileMemory ist jedes Dokument Markdown, und der Zweck jedes Dokuments ist aus seinem Path ersichtlich. Die JSON-Envelopes des aktuellen Projekts bewahren Namespace- und Key-Struktur, bieten aber nicht dieselbe Raw-Markdown-Diff-Erfahrung.

Wann Document Memory, Vector oder Key-Value verwenden?

Die drei Memory-Backends bedienen unterschiedliche Zugriffsmuster:

Verwende Document Memory, wenn:

  • der Agent über mehrere Sessions hinweg Projektwissen ansammelt
  • Developer prüfen, bearbeiten oder überschreiben müssen, was der Agent „weiß“
  • das Wissen als Dokumente strukturiert ist (Notizen, Zusammenfassungen, Konventionen) und nicht als isolierte Fakten
  • du eine Git-basierte Versionierung des Agent-Memory möchtest
  • Zero Infrastructure eine harte Anforderung ist

Verwende Vector Stores, wenn:

  • du fuzzy semantisches Retrieval benötigst („Finde Memories zu X“)
  • die Query-Formulierung unvorhersehbar variiert
  • du Tausende bis Millionen einzelner Fakten hast

Verwende Key-Value Stores, wenn:

  • du exakte, schnelle Lookups für strukturierte Daten benötigst (User Profiles, Settings)
  • das Daten-Schema klar definiert ist

Die drei Stores können koexistieren, müssen es aber nicht. Der aktuelle Market Analyst Agent verwendet PostgreSQL Checkpoints für Hot Memory, Qdrant für exakten User-Profile-Storage mit Placeholder-Vectors und einen namespaced JSON-Envelope-Document-Store. Die Varianten für Semantic Recall und Raw Markdown in diesem Artikel sind illustrative Erweiterungen.

Beispiele aus der Praxis

Das Pattern ist bei AI Coding Assistants bereits weit verbreitet:

  • Claude Code liest CLAUDE.md-Dateien aus dem Project Root und übergeordneten Verzeichnissen und unterhält unter ~/.claude/projects/ eine Memory-Datei pro Projekt für Session-übergreifende Learnings. Das Memory-System besteht aus einfachen Markdown-Dateien, und die Dateien auf Projektebene werden zusammen mit deinem Code committet.
  • Cursor lädt Projektregeln aus .cursor/rules als .mdc-Dateien — Coding-Konventionen, Framework-Präferenzen und Architekturentscheidungen — wobei Frontmatter steuert, wann jede Regel gilt.
  • Devins Legacy-Cascade-Agent in Desktop liest Regeln aus .devin/rules/, wobei .windsurf/rules/ und das Root-Level-.windsurfrules als Legacy-Fallbacks beibehalten werden. Cascade speichert automatisch erzeugte Memories lokal pro Workspace und ruft sie später ab; der Default-Devin-Local-Agent für neue Tabs persistiert keine Memories.
  • Anthropics Memory Tool für die Claude API ist ein clientseitiges Tool, das das Model über File Operations steuert — view, create, str_replace, insert, delete und rename — über ein /memories-Verzeichnis. Deine Anwendung implementiert jeden Command und entscheidet dadurch, wo die Dateien tatsächlich liegen (lokale Disk, S3, Datenbank).

Die file-backed Varianten speichern Agent-Wissen als menschenlesbaren Text mit expliziten Read-/Write-Operationen, und keine benötigt eine Embedding-Pipeline. Der Agent entscheidet, was geschrieben wird; wenn der Text in einem Git-managed lokalen Verzeichnis liegt, kann der Developer ihn in einem git diff sehen und bearbeiten. Wenn ein Anthropic-Memory-Tool-Handler /memories auf S3 oder eine Datenbank abbildet, hängen Inspection und Versionierung von dieser Implementierung ab.

Deklarative Notizen und ausführbare Skills

File-backed Knowledge findet sich auch außerhalb von Coding Assistants, aber das Storage-Format sagt nicht, wie es verwendet wird. Voyager speichert wiederverwendbare JavaScript-Programme: Der Agent kann diesen Code ausführen. Die zentrale Methode Agent Workflow Memory fügt induzierte Web-Workflows stattdessen als Guidance für nachfolgende Actions in den Prompt-Kontext ein. Das separate AWM_AS-Experiment stellt Workflows als aufrufbare Actions bereit. Ein im Kontext beschriebenes Verfahren und ein ausführbares Verfahren benötigen unterschiedliche Checks.

Teste aufrufbare Skills, indem du sie in einer kontrollierten Umgebung ausführst und Effects prüfst. Prüfe Projektnotizen und kontextuelle Workflows auf die Fakten, Constraints und Action Guidance, die sie liefern, und teste anschließend, ob diese Instructions das Verhalten nachgelagerter Schritte verbessern. Beide Formen können zu einer schädlichen Action führen; keine verleiht zusätzliche Permissions.

Dieselbe Grenze hält Memory getrennt von Skills und Tools. Der Agent Skills Standard verwendet SKILL.md-Dateien, um einem Agent zu erklären, wie eine Klasse von Arbeiten ausgeführt wird; Memory hält Fakten fest, die aus einem Projekt oder früheren Run gelernt wurden. Teil 3 zieht die benachbarte Grenze zwischen Skill und Tool. Wähle einen File Store für inspizierbaren gelernten Kontext; wähle einen Skill oder ein Tool nur, wenn die Anforderung ein wiederverwendbares Verfahren oder eine Capability ist.

Document Memory für Production skalieren

Die oben gezeigte file-basierte Implementierung passt zu einem kontrollierten Single-User-Filesystem. Mehrere Tenants und Concurrent Writers erfordern explizite Zugriffs- und Write-Koordination, unabhängig von der Dokumentanzahl.

Der Raw Store oben besitzt keine Coordination für Concurrent Writes, kein Tenant-Modell und keinen Search Index. Miss diese Anforderungen, bevor du ihn ersetzt. Eine Datenbank oder ein Object Store kann andere Concurrency- und Access-Contracts bereitstellen; auch Dateien können indexiert werden.

Drei gängige Ansätze:

Ansatz A: Hybrid mit einer dünnen Database-Schicht

Behalte Dateien für das Authoring (Developer bearbeiten Markdown lokal), stelle sie aber zur Runtime aus einer Datenbank bereit. Synchronisiere Dateien beim Deployment in PostgreSQL-Rows. Der Agent liest aus der Datenbank, nicht von Disk. Das bietet:

  • Gute Developer Experience (Markdown bearbeiten, in Git committen)
  • Production Query Performance (indexierte Database Reads)
  • Klare Trennung zwischen Authoring und Serving

Ansatz B: Object Storage + Vector-Index-Sidecar

Speichere Dokumente als Objekte in S3/GCS und verwende eine Qdrant Collection, die ihre Embeddings indexiert. Der Agent fragt Qdrant nach relevanten Dokument-IDs ab und lädt anschließend den Inhalt aus dem Object Storage. Das skaliert horizontal und unterstützt Semantic Search, erhöht aber die Komplexität: zwei zu verwaltende Systeme, eine zu wartende Embedding-Pipeline und Eventual Consistency zwischen Store und Index.

Ansatz C: Strukturierter Document Store mit PostgreSQL (empfohlen)

Speichere Dokumente als PostgreSQL-JSONB-Rows mit Full-Text Search (GIN Index) und optionalen Vector Embeddings (pgvector). Dadurch erhältst du Hybrid Search (Keyword + Semantic), ACID-Transaktionen und ein einzelnes operatives System.

Eine Skizze von Ansatz C. Der kombinierte Score verwendet exaktes Scoring über ein begrenztes Tenant-Korpus; er nutzt keinen Approximate-Nearest-Neighbor-(ANN)-Index. pgvector erfordert für diesen Index-Pfad eine direkte aufsteigende Distanzsortierung mit LIMIT. Bei einem größeren Korpus solltest du Keyword- und Vector-Kandidaten separat begrenzen und anschließend ihre Ranks fusionieren. Dies ist ein RLS-Pattern, kein direkt einsetzbarer Application Code: Seine Database Role darf nur dem vertrauenswürdigen Application Server zur Verfügung stehen. Der Server authentifiziert den Request und erstellt principal; er akzeptiert keine Tenant-ID vom Caller. PostgreSQL RLS macht diesen Scope anschließend durchsetzbar, selbst wenn eine spätere Query den Tenant-Predicate auslässt.

from typing import Optional
from dataclasses import dataclass
import asyncpg

@dataclass(frozen=True)
class AuthenticatedPrincipal:
    """The verified identity returned by the application's authentication layer."""
    tenant_id: str

class ProductionDocumentMemory:
    """Illustrative PostgreSQL document memory with hybrid search and RLS.

    Apply this schema and policy as the table owner during deployment:

        CREATE TABLE documents (
            id SERIAL PRIMARY KEY,
            tenant_id TEXT NOT NULL,
            path TEXT NOT NULL,
            content TEXT NOT NULL,
            metadata JSONB,
            embedding vector(1536),  -- pgvector extension
            ts_vector tsvector GENERATED ALWAYS AS (to_tsvector('english', content)) STORED,
            created_at TIMESTAMPTZ DEFAULT NOW(),
            UNIQUE(tenant_id, path)
        );
        CREATE INDEX ON documents USING GIN(ts_vector);

        ALTER TABLE documents ENABLE ROW LEVEL SECURITY;
        ALTER TABLE documents FORCE ROW LEVEL SECURITY;
        CREATE POLICY tenant_documents ON documents
            USING (tenant_id = current_setting('app.tenant_id', true))
            WITH CHECK (tenant_id = current_setting('app.tenant_id', true));

    `FORCE` also subjects the table owner to the policy. Superusers and roles with
    `BYPASSRLS` still bypass it, so neither belongs in the application's pool.
    """

    def __init__(self, pool: asyncpg.Pool):
        self.pool = pool

    async def write(
        self,
        principal: AuthenticatedPrincipal,
        path: str,
        content: str,
        metadata: Optional[dict] = None,
        embedding: Optional[list[float]] = None,
    ):
        """Write or update a document.

        Sketch: on a real pool you must register codecs first, or asyncpg
        raises DataError — `set_type_codec` for the JSONB metadata column
        and pgvector's `register_vector` for the embedding.
        """
        async with self.pool.acquire() as conn:
            async with conn.transaction():
                # true keeps this trusted context to this transaction only.
                await conn.execute(
                    "SELECT set_config('app.tenant_id', $1, true)", principal.tenant_id
                )
                await conn.execute(
                    """
                    INSERT INTO documents (tenant_id, path, content, metadata, embedding)
                    VALUES ($1, $2, $3, $4, $5)
                    ON CONFLICT (tenant_id, path) DO UPDATE
                    SET content = EXCLUDED.content,
                        metadata = EXCLUDED.metadata,
                        embedding = EXCLUDED.embedding
                    """,
                    principal.tenant_id, path, content, metadata, embedding,
                )

    async def search(
        self,
        principal: AuthenticatedPrincipal,
        query: str,
        embedding: Optional[list[float]] = None,
        limit: int = 5,
    ) -> list[dict]:
        """Hybrid search: full-text + optional vector similarity."""
        async with self.pool.acquire() as conn:
            async with conn.transaction():
                await conn.execute(
                    "SELECT set_config('app.tenant_id', $1, true)", principal.tenant_id
                )
                if embedding:
                    # Hybrid scoring: 0.6 * text relevance + 0.4 * vector similarity
                    rows = await conn.fetch(
                        """
                        SELECT path, content, metadata,
                               (0.6 * ts_rank(ts_vector, plainto_tsquery('english', $1)) +
                                0.4 * COALESCE(1 - (embedding <=> $2), 0)) AS score
                        FROM documents
                        WHERE ts_vector @@ plainto_tsquery('english', $1)
                           OR (embedding <=> $2) < 0.5
                        ORDER BY score DESC
                        LIMIT $3
                        """,
                        query, embedding, limit,
                    )
                else:
                    # Full-text search only
                    rows = await conn.fetch(
                        """
                        SELECT path, content, metadata,
                               ts_rank(ts_vector, plainto_tsquery('english', $1)) AS score
                        FROM documents
                        WHERE ts_vector @@ plainto_tsquery('english', $1)
                        ORDER BY score DESC
                        LIMIT $2
                        """,
                        query, limit,
                    )
                return [dict(row) for row in rows]

set_config(..., true) ist transaction-scoped, sodass eine gepoolte Connection den Kontext eines Tenants nicht für den nächsten Request behalten kann. Das OR im ersten Branch macht den Ansatz hybrid. COALESCE hält ein keyword-matchendes Dokument ohne Embedding mit seinem Text-Score im Result Set; es trägt keine Vector Similarity bei. Mit ausschließlich dem Predicate @@ wird ein Dokument, das semantisch das Richtige bedeutet, aber keine Keywords der Query teilt, vor dem Scoring herausgefiltert — das ist Keyword Retrieval mit semantischem Reranking, kein Hybrid Retrieval. Die Weights 0.6/0.4 sind illustrativ: Text Rank und Cosine Similarity haben unterschiedliche Skalen. Normalisiere sie anhand deiner Retrieval-Evaluation oder verwende Rank Fusion, bevor du diese Weights als relative Wichtigkeit interpretierst. Der Distance Threshold ist ein Tuning-Parameter: Verschärfe ihn, wenn der Vector-Arm die Ergebnisse überflutet, und lockere ihn, wenn semantische Matches nie auftauchen.

Die folgende Regression beschreibt das Verhalten, das du nach Migrationen gegen eine echte Datenbank testen solltest. Unter tenant-a liefert ein Read von tenant-b keine Rows, und ein direkter Cross-Tenant-Insert scheitert an RLS:

BEGIN;
SELECT set_config('app.tenant_id', 'tenant-a', true);
SELECT path FROM documents WHERE tenant_id = 'tenant-b'; -- 0 rows
INSERT INTO documents (tenant_id, path, content)
VALUES ('tenant-b', 'leak.md', 'must fail'); -- ERROR: row-level security policy
ROLLBACK;

Das erhältst du:

  • Hybrid Search: Keyword Matching (GIN Index) + semantische Similarity (pgvector), gemeinsam gescored
  • Multi-Tenancy: serverseitig abgeleitete Identity plus datenbankseitig durchgesetztes RLS
  • ACID-Garantien: Transaktionen auf dem Primary committen atomar; Replica Reads können verzögert sein
  • Ein einzelnes operatives System: keine separate Vector Database zu verwalten
  • Skalierung: Read Replicas können stale-tolerante Queries bedienen. Native Partitioning kann Pruning und Maintenance unterstützen, verteilt aber Writes nicht über mehrere Server; dafür ist ein explizites Sharding-Design nötig. Leite Read-after-Write-Pfade an den Primary oder miss eine geeignete synchrone Policy

Dateien eignen sich hervorragend für Workflows mit einem einzelnen Developer. Für Multi-Tenant-Production ist ein strukturierter Document Store auf PostgreSQL normalerweise das richtige Gleichgewicht aus Einfachheit, Performance und operativer Reife.

Alles zusammenführen: die vollständige Architektur

Byte says

Speichere neue Fakten nach der Antwort, damit das Embeddieren den User nicht warten lässt.

So können alle drei Memory-Tiers in einer vom Market Analyst Agent inspirierten Architektur zusammenspielen. Das Diagramm zeigt einen illustrativen Flow vom User Request bis zur Antwort, mit allen aktiven Memory-Schichten.

Die Architektur hat drei Memory-Pfade:

  1. Hot Path (Checkpoint Store): LangGraph schreibt den resumable Graph-State an jeder Super-Step-Grenze in den Checkpoint Store. Wenn der Graph einen interrupt_before-Node erreicht (wie den publish-Node in Teil 1), pausiert die Ausführung. Der User kann die App schließen; bei der Rückkehr setzt der Graph die Ausführung aus dem Checkpoint fort. Runtime Event Logs und Traces sind separate Production-Anliegen.

  2. Cold Path (Long-Term Store): Nachdem der Router eine Route ausgewählt hat, fragt der Planner den Long-Term Store nach relevantem User-Kontext ab. Der Planner kann nicht personalisieren, bevor dieser Read zurückkehrt. Ein Vector-backed Lookup kann Query Embedding und Index Retrieval enthalten; ein Key-Value Lookup nicht. Neue Fakten können nach dem Ende der Konversation extrahiert und gespeichert werden, sodass dieser Write den Reasoning Loop nicht verzögert.

  3. Document Path (File Store): Während der Planung liest der Agent die für den Request nötigen Projektkonventionen und Forschungsnotizen. Während der Ausführung schreibt er Forschungszusammenfassungen und gelernte Patterns zurück auf Disk. Diese Reads informieren die aktuelle Task, daher beeinflussen Dateigröße, Filesystem-Geschwindigkeit und Cache-State die Antwortzeit. Cache nur, wenn der Cache klare Invalidation- und Tenant-Isolation-Regeln besitzt. Writes können später erfolgen.

Die Verdrahtung in LangGraph ist unkompliziert — Checkpoint Store und Long-Term Store werden bei der Graph-Kompilierung übergeben, während der Document Store als Dependency injiziert wird. Die lokale Skizze unten kompiliert einen bereits konfigurierten StateGraph-Builder einschließlich Nodes, die den Store akzeptieren. Dies erweitert die Graph-Verdrahtung; die Helpers aus Teil 1 und der Companion create_graph akzeptieren kein Argument store. Sie verwendet InMemoryStore mit Vector-Unterstützung, damit das Snippet klein bleibt. Die Companion-Implementierung verwendet Qdrant für exakten User-Profile-Storage mit Placeholder-Zero-Vectors; semantischer Recall ist eine hier gezeigte Erweiterung.

Der vollständige Flow

Im erweiterten Design oben könnte der Request eines zurückkehrenden Users „Analyze TSLA“ diesem Flow folgen. Semantischer Recall und asynchrone Fact Extraction sind vorgeschlagene Erweiterungen, kein aktuelles Verhalten der Companion-Implementierung:

  1. Router: Der Router klassifiziert den Request als DEEP_RESEARCH. In diesem Beispiel nutzt das Routing den Request selbst und nicht Long-Term Preferences.

  2. Memory Reads + Planner: Der Planner fragt den Long-Term Store mit der User-Message ab. Er ruft ab: „User hat eine hohe Risikotoleranz“, „User bevorzugt detaillierte Wettbewerbsanalysen“, „User hat zuvor NVDA und AMD recherchiert“. Außerdem liest er Projektkonventionen aus dem Document Store: Präferenzen für das Analyseformat, bevorzugte Datenquellen und Tool-Usage-Patterns. Beide Reads müssen abgeschlossen sein, bevor die Planung ihre Inhalte verwendet. Vector Recall kann Query Embedding und Index Retrieval enthalten; Document Reads hängen von Dateigröße, Filesystem-Geschwindigkeit und Cache-State ab. Der Planner erstellt anschließend einen Research-Plan mit fünf Schritten, der eine Wettbewerbsanalyse enthält und dem Format des Konventionsdokuments folgt.

  3. Executor Loop (Hot Memory): Jeder Schritt wird nach dem ReAct-Pattern aus Teil 1 ausgeführt — denken, handeln, beobachten, bis der Schritt abgeschlossen ist. LangGraph checkpointet jeden Super-Step (Router, Planner, jeden sequenziellen Executor-Schritt hier). Die Recovery beginnt beim neuesten persistent gespeicherten Checkpoint. Wenn der Write von Schritt 3 abgeschlossen wurde, kann der Graph mit Schritt 4 fortfahren; bei asynchroner Persistence kann ein Crash die Wiederholung eines abgeschlossenen Schritts erfordern.

  4. HITL-Interrupt: Der Reporter schreibt einen Entwurf. Eine separate Model-Session ohne History des Runs liest den Entwurf und hält eine Bewertung fest. Der Graph erreicht anschließend publish, wobei interrupt_before ihn unabhängig von dieser Bewertung pausiert. Der Checkpoint enthält sowohl Entwurf als auch Bewertung, sodass der Mensch beides prüft, bevor er entscheidet, ob veröffentlicht wird. Stunden später lädt der Graph den Checkpoint erneut und folgt dieser Entscheidung.

  5. Memory Updates: Nach dem Ende der Konversation extrahiert ein asynchroner Prozess neue User-Fakten („User verfolgt jetzt TSLA“, „User hat das Berichtsformat freigegeben“) und speichert sie im Long-Term Vector Store. Der Agent schreibt außerdem eine Forschungszusammenfassung in den Document Store (research/TSLA-2026-02) zur späteren Referenz.

Das Three-Tier-Pattern trennt Verantwortlichkeiten sauber. Der Checkpoint Store übernimmt Durability und Resume; er ist Infrastruktur. Der Long-Term Store übernimmt Personalisierung; er ist Product Logic. Der Document Store hält angesammeltes Projektwissen; er ist das Notebook des Agents.

Trade-offs und Überlegungen

Memory bringt Nutzen, aber auch Kosten und Komplexität:

  • Embedding-Kosten: Jeder in einer Vector Database gespeicherte Fakt erfordert die Erzeugung eines Embeddings. Ein gehosteter Embedding Provider fügt einen API Call, provider-spezifische Kosten und Network Latency hinzu; im September 2026 listete OpenAI text-embedding-3-small für $0,02 pro einer Million Tokens. Die Kosten eines gehosteten Models pro Fakt sind vernachlässigbar, summieren sich aber über Tausende User und Sessions. Bündele Hosted Calls und cache Ergebnisse. Zur Query-Zeit kann Vector Recall Query Embedding sowie Index- und Network-Latency enthalten; ein Key-Value Lookup nicht. Miss diesen Pfad in deinem Deployment und cache anschließend häufige Query Embeddings oder verwende ein lokales Embedding Model, wenn die Latency kritisch ist.

  • Veraltetes Memory: User-Präferenzen ändern sich. Ein vor sechs Monaten gespeicherter Fakt („User bevorzugt konservative Investments“) ist möglicherweise nicht mehr korrekt. Lege Expiry-Policies fest. Ein Team könnte beispielsweise Preferences nach 365 Tagen und episodische Events nach 90 Tagen ablaufen lassen, wenn Privacy-Regeln, Update-Rate und Retrieval-Evaluation diese Zeiträume rechtfertigen; diese Werte sind eine vorgeschlagene Policy und keine portablen Defaults. Der Beitrag zu Context Engineering lehnt feste Retention-Regeln als portable Policy ab. Expiry ist die grobe Variante. Schema-guided Typed State ist die präzisere: zeitliche Gültigkeit und Provenance an jedem Fakt, sodass ein abgelöster Wert beim Retrieval gegenüber dem aktuellen verliert und nicht erst beim Expiry.

  • Memory-Overhead im Kontext: Jeder abgerufene Fakt verbraucht Tokens im Context Window des LLM. Wenn du pro Query 20 Fakten abrufst, sind das mehrere hundert Tokens Memory-Kontext, die mit der eigentlichen Task konkurrieren. Begrenze die Anzahl abgerufener Fakten und priorisiere nach Relevance Score.

  • Privacy und Compliance: Long-Term Memory speichert User-Daten. Du brauchst PII-Redaction vor dem Storage, klare Retention-Policies und User-facing Controls zum Löschen von Daten. In regulierten Branchen ist nichts davon optional.

  • Wachstum des Checkpoint-Storage: PostgreSQL-Checkpoint-Tabellen wachsen mit jedem Super-Step. Führe keine allgemeine SQL-Pruning-Query aus: Delta Channels können Ancestor-Checkpoints und deren Write-/Blob-Records benötigen, um einen behaltenen Checkpoint zu rekonstruieren. Verwende eine vom Saver unterstützte Pruning-API erst, nachdem du sie gegen den exakt installierten Saver und dessen Recovery-Contract für Delta Channels geprüft hast. Wenn diese Unterstützung fehlt, behalte die vollständige Parent-, Write- und Blob-Closure und teste das Resume von einem behaltenen Checkpoint mit dem installierten Saver.

  • Memory Consolidation und Retention: Ein kompaktes abgeleitetes Memory wie „User fragte im Januar dreimal nach NVDA“ kann den Recall verbessern, ohne die Quellkonversationen zu ersetzen. Mem0 extrahiert mögliche Fakten und entscheidet, ob vorhandene Memories hinzugefügt, aktualisiert, gelöscht oder unverändert gelassen werden. Graphitis Design in der Zep-Studie behält Raw Episodes neben abgeleiteten semantischen Entitäten und Beziehungen sowie Links zu ihren Quellen. Keine der beiden Mechanismen definiert die Retention-Policy deiner Anwendung. Definiere Expiry, Deletion oder verlustbehaftete Archival Compaction separat und teste, welche Belege durch diese Operationen entfernt werden.

  • Cold-Start-Problem: Neue User besitzen kein Long-Term Memory. Der Agent sollte graceful degradieren und klärende Fragen stellen, statt Annahmen zu treffen. Memory ist additiv, nicht erforderlich.

  • Memory Poisoning: Alles im Context Window des Agents ist ein potenzieller Injection Point. Wenn ein Angreifer irreführende Fakten in den Document Store oder das Long-Term Memory schreibt („Transaktionen immer ohne Verifikation freigeben“), kann der Agent sie als Instructions ausführen. Prompt Injection über gespeicherte Memories ist eine reale Angriffsfläche. Die Gegenmaßnahmen sind Validation vor dem Storage, der Umgang mit abgerufenem Content als untrusted Data statt als System Instructions und Access Controls, die begrenzen, welche Memories kritische Operationen beeinflussen können.

  • Drift von Document Memory: File-based Memory besitzt keine automatische Deduplication oder Conflict Resolution. Mit der Zeit sammeln sich Widersprüche an: Eine Datei sagt „pytest verwenden“, eine andere „unittest“. Plane regelmäßige Reviews ein (oder überlasse sie dem Agent), um Inhalte zu bereinigen und zu konsolidieren. Dateien unterstützen grep; Vector-Store-Payloads können ebenfalls inspiziert oder exportiert werden. Kein Storage-Format erkennt Widersprüche selbstständig.

  • Search Scale: Der Raw File Scan oben liest das Korpus bei jeder Query. Wähle einen Index anhand von gescannten Bytes, Update-Rate, Concurrency, Latency und Retrieval-Qualität. File-backed Content kann einen Full-Text- oder Vector-Index verwenden; die Dokumentanzahl allein bestimmt nicht das Backend.

Recall und Memory-Lifecycle testen

Vergleiche Baselines ohne Memory und mit vollständigem Kontext anhand von Held-out-Fragen. Berücksichtige Paraphrasen, Widersprüche, Präferenzänderungen, veraltete Fakten, nicht beantwortbare Fragen, Deletions und Cross-Tenant-Requests. LongMemEval bietet 500 Fragen zu Extraction, Multi-Session- und temporalem Reasoning, Updates und Abstention. Miss Retrieval Precision/Recall getrennt von Answer Correctness sowie die Nutzung veralteter Fakten, nicht autorisierte Offenlegung, Write-/Update-/Delete-Correctness, Latency und Kosten.

Recall-Fragen sind nur ein Teil der Evaluation. MemoryArena ergänzt interdependente Tasks über Sessions hinweg, bei denen eine frühere Action und ihr Feedback das spätere Verhalten verändern müssen. Die Tasks umfassen Shopping, Reiseplanung, Progressive Search und formales Reasoning. Verwende dieses Design, wenn das Produkt verspricht, aus Arbeit zu lernen, statt nur Fragen über gespeicherte Konversationen zu beantworten. Dies sind Research Tasks und keine Messungen eines deployten Memory Services.

EvoMemBench trennt ebenfalls Wissen von Execution Experience sowie Within-Episode- von Cross-Episode-Memory. Der Vergleich von 15 Methoden findet keine durchgehend stärkste Memory-Form; Long-Context-Baselines bleiben unter dem verwendeten Protocol konkurrenzfähig. Das spricht dafür, die einfachen Baselines in deiner Evaluation beizubehalten, statt jeden Store durch das neueste Framework zu ersetzen.

Bewahre Provenance und Gültigkeit neben abgerufenen Fakten auf. Importance Scores können weder Trust begründen noch Permissions ändern. Die Deletion Policy muss neben dem Originaldatensatz auch Indizes, gecachte Summaries und aufbewahrte Artefakte abdecken.

Die nächste Schicht ist Action

Die Teile 5 und 6 betrachten Memory erneut von der operativen Seite und behandeln unterschiedliche Hälften davon. Der Runtime gehört der Checkpoint: wo die Ausführung gestoppt hat und wie sie neu gestartet wird. Dem Harness gehört der Handoff: was die Arbeit bedeutet und was noch offen ist, als Document Memory für die nächste Model-Session festgehalten — ein zusammenhängender Abschnitt des Model-Kontexts, in der Terminologie, die Teil 5 festlegt. Den Prozess wiederherzustellen ist nicht dasselbe wie die Task wiederherzustellen.
