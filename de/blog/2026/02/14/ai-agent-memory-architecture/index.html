Ein Reasoning Loop überlebt nur einen Request, sofern sein State nicht außerhalb des Workers gespeichert wird. Ohne Agent Memory kann der Agent keinen pausierten Plan fortsetzen, sich nach einem Crash erholen oder sich an eine Präferenz aus einer früheren Session erinnern. Teil 1 behandelte den Control Flow. TL;DR

Trenne Memory nach Access Pattern. Hot Memory ist Checkpoint-State pro Conversation zum Pausieren und Fortsetzen. Cold Memory enthält Session-übergreifende Fakten in einem Key-Value- oder Vector Store. Document Memory hält Projektwissen in inspizierbaren Dateien. Beginne mit dem Fehler, den du beheben musst, und wähle danach den Store. Lege keine exakten Fakten in ein Fuzzy-Retrieval-System und behandle einen Checkpoint nicht als Audit Log.

Jeder unten beschriebene Store wird vom Harness gelesen, also von dem Code, der den Loop um das Model steuert. Der Harness entscheidet, welche Inhalte in das Context Window gelangen; die Stores selbst tun das nicht. Dieser Artikel behandelt, wo dieser State liegt, bevor der Harness darauf zugreift. Teil 3 und Teil 4 behandeln, was der Harness anschließend mit dem Prompt macht.

Was ist AI-Agent-Memory?

AI-Agent-Memory ist die State-Schicht, mit der ein Agent Task-Fortschritt bewahren, früheres Wissen abrufen und seinen Wissensstand über mehrere Runs hinweg aktualisieren kann. In Production ist das keine einzelne Vector Database. Es ist eine Kombination aus Hot Checkpoints, Cold Stores für semantische oder strukturierte Daten und menschenlesbarer Document Memory.

Beginne nicht mit Memory, nur weil es intelligent klingt. Beginne mit dem sichtbaren Fehler: verlorener Fortschritt, vergessene Präferenz, wiederholte Recherche oder eine nicht wiederverwendete Projektkonvention.

Die Fehler, die Memory erfordern

Ein Stateless Agent kann eine isolierte Frage beantworten, vergisst den Request aber, sobald der Call endet. Dieses Design scheitert, wenn das Produkt eines der folgenden Verhalten benötigt:

  • Pausieren und fortsetzen: Ein User startet eine Recherche, schließt den Laptop und kommt am nächsten Tag zurück. Ohne Checkpoint-State startet der Agent von vorn.
  • Kohärenz über mehrere Turns: In einer langen Conversation muss der Agent wissen, welche Tools er aufgerufen, welche Daten er gesammelt und welche Plan-Schritte er abgeschlossen hat.
  • Personalisierung: Ein wiederkehrender User erwartet, dass der Agent seine Risikotoleranz, die bevorzugte Analysetiefe und frühere Interaktionen kennt.
  • Human-in-the-Loop (HITL): Der Agent sammelt seine Belege und wartet, bis ein Mensch den nächsten Schritt freigibt. Dieser „wartende“ State muss Prozessneustarts überleben.

Im Market Analyst Agent aus Teil 1 erzeugt der Request „Analyze NVDA“ einen Plan, fünf Tool Calls, gesammelte Daten und einen Entwurf des Berichts. Wenn der User „looks good, but add competitor analysis“ antwortet, kann ein Checkpoint Store den State des letzten abgeschlossenen Schritts laden und den Competitor-Schritt ergänzen. Ohne Checkpoint-State kann der Agent nicht auflösen, worauf sich „looks good“ bezieht, und muss von vorn beginnen.

Long-Term Memory behandelt einen anderen Fall. Wenn der User eine Woche später zurückkommt und fragt: „Update my NVDA analysis“, muss sich der Agent möglicherweise an eine Präferenz für konservative Risikobewertungen und ein Interesse an Semiconductor Stocks erinnern. Ein Vector-basierter Memory Store kann diese Fakten Session-übergreifend abrufen, ohne sie erneut abzufragen.

Die Implementierungsbeispiele unten verwenden LangGraph, LangChains Open-Source-Library zum Aufbau von Agents als explizite State Graphs; die von ihr gezogenen Storage-Grenzen lassen sich auf jedes Framework übertragen. LangGraph trennt Memory nach Scope. Jede Graph-Ausführung läuft innerhalb eines Threads, also einer Conversation oder eines Tasks. Persistierter State innerhalb dieses Threads ist Short-Term Memory. State, der über Threads hinweg geteilt wird, ist Long-Term Memory. Im Folgenden sind „Thread“ und „Conversation“ austauschbar; ich vermeide für diese Spanne „Session“, weil Teil 5 den Begriff für das Durable Log eines einzelnen Runs reserviert, von denen sich mehrere auf einem Thread ansammeln können. Der aktuelle Context des Models und Variablen im Prozess bilden die Working-Memory-Schicht oberhalb beider Stores.

Eine Taxonomie von AI-Agent-Memory

Bevor wir zur Implementierung kommen, ist es hilfreich zu klassifizieren, woran sich Agents erinnern müssen. Das CoALA-Framework — Cognitive Architectures for Language Agents (Sumers, Yao et al., 2023) — ist eine häufig zitierte Taxonomie mit Bezug zur Kognitionswissenschaft. In meinem Context-Engineering-Beitrag habe ich Memory-Scoping eingeführt; hier erweitere ich es auf sechs Kategorien:

Working Memory ist das, womit das LLM gerade aktiv Reasoning betreibt: Python-Variablen in der aktuellen Funktion, der Inhalt des Context Window und Tool-Call-Argumente während der Ausführung. Das ist die schnellste und flüchtigste Schicht. Nichts davon bleibt über den aktuellen Schritt hinaus erhalten. Working Memory ist durch das Context Window des Models begrenzt, wodurch es zum Bottleneck wird. Alles, was der Agent zum Entscheidungszeitpunkt „weiß“, muss hier hineinpassen — unabhängig davon, ob es aus dem Checkpoint Store, einer Vector Query oder einem File Read stammt. Die anderen Tiers existieren, um die richtigen Informationen zum richtigen Zeitpunkt in Working Memory zu laden.

Short-Term Memory ist der Checkpoint, den LangGraph nach jeder Einheit der Graph-Ausführung schreibt — einem Super-Step, der im nächsten Abschnitt definiert wird. Episodic und Semantic Memory bleiben über Threads hinweg erhalten. Document Memory speichert Projektnotizen, Research-Zusammenfassungen und gelernte Konventionen in Dateien, die Menschen und Agents inspizieren können. Procedural Memory liegt in System Instructions und Tool Definitions und ändert sich nicht für jeden User.

Für die Implementierung fallen fünf dieser sechs Kategorien auf drei Storage-Tiers zusammen. Short-Term Memory wird zu Hot Memory, dem Checkpoint für den aktuellen Thread. Episodic und Semantic werden zu Cold Memory, also Recall über Threads hinweg. Document Memory hält angesammeltes Projektwissen lesbar und direkt editierbar. Working Memory ist in der obigen Taxonomie mit dem Hot Tier gruppiert, wird aber nie wirklich gespeichert: Es existiert nur für einen einzelnen Schritt im Prozess und ist das Context Window, in das die drei Storage-Tiers laden. Procedural Memory liegt außerhalb aller drei: Es lebt im System Prompt und in Tool Definitions und wird mit dem Agent ausgeliefert, statt gespeichert und abgerufen zu werden.

CoALA klassifiziert Working, Episodic, Semantic und Procedural Memory. Die Studie „Memory in the Age of AI Agents“ betont Vector Stores und Knowledge Graphs, während LangGraph Checkpoints und sein Store Interface dokumentiert. File-basiertes Projektwissen liegt außerhalb dieser Taxonomien, obwohl Claude Code, Cursor und Devin Desktop persistente Projektdateien laden.

Dasselbe Storage Pattern findet sich in anderen Domänen. Ein Minecraft Agent (Voyager) speichert wiederverwendbare Game Skills als Code Libraries, Teams in einem Enterprise-Document-QA-Wettbewerb iterieren über prozedurale Prompt-Dokumente, und Web Agents leiten aus erfolgreichen Runs wiederverwendbare Browsing Workflows ab. Auf alle drei komme ich später zurück; wichtig ist hier, dass Dateien dieses Wissen inspizierbar und versionierbar machen, ohne einen separaten Embedding Service.

Von einer festen RAG Pipeline unterscheidet sich Agent-managed Memory außerdem dadurch, wer den Write ausführt. Der Agent oder sein Harness wählt aus, was gespeichert, aktualisiert und gelöscht wird, und entscheidet später, wann es abgerufen wird.

Das Paper „Generative Agents“ (Park et al., 2023) zeigte, wie weit dies gehen kann: Simulierte Agents speicherten, reflektierten über und riefen ihre eigenen Memories ab. Sein Memory Stream bewertete Kandidaten nach Aktualität, Wichtigkeit und Relevanz — ein Design, das weiterhin einen nützlichen Referenzpunkt für Agent-Memory-Retrieval darstellt.

Short-Term Agent Memory: der Checkpoint Store

Immer wenn LangGraph einen Super-Step abschließt — einen Node oder einen parallel ausgeführten Batch von Nodes — serialisiert das Framework den vollständigen Graph-State und schreibt ihn in einen Checkpoint Store. Das ist die Grundlage für Pause/Resume, Time-Travel-Debugging und HITL Workflows.

Ein Checkpoint enthält den Graph-State, der zum Fortsetzen benötigt wird: das AgentState aus Teil 1 — Messages, Identity, User Profile, Plan-Schritte, Research-Daten und Execution Mode. Zusätzlich speichert LangGraph eigene Verwaltungsdaten: ID und Timestamp des Checkpoints, eine Version pro Channel (LangGraphs Bezeichnung für einen einzelnen State Key) sowie einen separaten Record darüber, welche Channel-Versionen jeder Node bereits gesehen hat. Die Step-Nummer liegt in den Metadaten des Checkpoints und nicht auf dem Checkpoint selbst. Der Vergleich dieser beiden Angaben bestimmt, was als Nächstes ausgeführt wird. Nach einem HITL Interrupt oder einem Prozessneustart lädt der Graph den Checkpoint, der an der letzten abgeschlossenen Grenze geschrieben wurde, und tritt wieder in den nächsten Node ein. Er setzt nicht an einer beliebigen Python-Zeile fort. Ein Checkpoint ist außerdem etwas anderes als ein Append-only Event Log oder Trace; Teil 5 trennt diese Runtime-Observability-Flächen ausdrücklich.

So funktioniert Checkpointing in LangGraph

LangGraphs BaseCheckpointSaver ist ein einfaches Interface: put() schreibt einen Checkpoint, get_tuple() liest den neuesten Checkpoint eines Threads, list() gibt die History zurück. Jeder Checkpoint wird über (thread_id, checkpoint_ns, checkpoint_id) adressiert, wobei thread_id die Conversation identifiziert, checkpoint_ns das Subgraph-Namespaceing übernimmt und checkpoint_id eine eindeutige Version darstellt.

Die entscheidende Frage ist, welcher Backend darunter liegt. PostgreSQL und Redis sind zwei verbreitete Production-Optionen.

PostgreSQL: der Durable Default

PostgreSQL ist für die meisten Teams der sicherere Default. Checkpoints überleben Crashes, du erhältst vollständige Transaktionssemantik, und die Checkpoint-History macht Time-Travel-Debugging unkompliziert.

Eine vereinfachte Version des Checkpoint-Setups in memory/hot.py:

from contextlib import asynccontextmanager

from langchain_core.messages import HumanMessage
from langgraph.checkpoint.postgres.aio import AsyncPostgresSaver

@asynccontextmanager
async def postgres_checkpointer(connection_string: str):
    """Yield a PostgreSQL-backed checkpoint store.

    PostgreSQL gives us ACID guarantees — if a checkpoint write succeeds,
    the state is durable even if the process crashes immediately after.
    `from_conn_string` is itself an async context manager: it owns the
    connection and closes it on exit, so the graph has to run inside it.
    """
    async with AsyncPostgresSaver.from_conn_string(connection_string) as checkpointer:
        # Create the checkpoint tables if they don't exist.
        # This is idempotent — safe to call on every startup.
        await checkpointer.setup()
        yield checkpointer

# Usage: the graph lives inside the context manager's scope
async with postgres_checkpointer(
    "postgresql://user:pass@localhost:5432/agent_memory"
) as checkpointer:
    graph = create_graph(checkpointer=checkpointer)

    # Every invoke/stream call now persists state automatically
    config = {"configurable": {"thread_id": "user-123-session-1"}}
    result = await graph.ainvoke({"messages": [HumanMessage(content="Analyze NVDA")]}, config)

    # Resume later on the same thread_id — loads the latest checkpoint
    result = await graph.ainvoke({"messages": [HumanMessage(content="approved")]}, config)

Der AsyncPostgresSaver verwendet das Package langgraph-checkpoint-postgres, das vier Tabellen anlegt: checkpoints (den serialisierten State), checkpoint_blobs (große Binärdaten), checkpoint_writes (ausstehende Writes für Crash-Recovery) und checkpoint_migrations (Schema-Version). Concurrent Writes werden durch den Primary Key (thread_id, checkpoint_ns, checkpoint_id) und Upserts voneinander getrennt, nicht durch Locking — zwei Worker auf demselben Thread beschädigen sich nicht gegenseitig, koordinieren sich aber auch nicht.

Redis: wenn Latency der Bottleneck ist

Wenn Sub-Millisecond-Checkpoint-Latency entscheidend ist (Real-Time-Conversational Agents, High-Frequency-Tool-Loops), ist Redis die bessere Wahl.

Eine vereinfachte Version des Checkpoint-Setups in memory/hot.py:

from contextlib import asynccontextmanager

from langgraph.checkpoint.redis.aio import AsyncRedisSaver

@asynccontextmanager
async def redis_checkpointer(redis_url: str):
    """Yield a Redis-backed checkpoint store.

    Redis stores checkpoints in memory for sub-millisecond access.
    Trade-off: less durable than PostgreSQL unless you enable AOF,
    Redis's append-only log — snapshots alone lose recent writes on a crash.
    """
    async with AsyncRedisSaver.from_conn_string(redis_url) as checkpointer:
        # Initialize Redis data structures
        await checkpointer.setup()
        yield checkpointer

# Usage: same graph API, different backend
async with redis_checkpointer("redis://localhost:6379") as checkpointer:
    graph = create_graph(checkpointer=checkpointer)

Der AsyncRedisSaver aus langgraph-checkpoint-redis speichert jeden Checkpoint als eigenes RedisJSON-Dokument unter demselben (thread_id, checkpoint_ns, checkpoint_id) Key wie der Postgres Saver. Das Redesign von v0.1.0 ersetzte mehrere Search-Operationen durch einen einzelnen JSON.GET Call und reduzierte die Latency deutlich. Redis 8.0+ enthält RedisJSON und RediSearch standardmäßig — zusätzliche Module müssen nicht installiert werden.

Für Deployments mit begrenztem Memory speichert ShallowRedisSaver nur den neuesten Checkpoint pro Thread — keine History, aber minimale RAM-Nutzung. Verwende dies, wenn du Pause/Resume benötigst, aber kein Time-Travel-Debugging.

Wann welche Option sinnvoll ist

Verwende PostgreSQL, wenn:

  • Du eine vollständige Checkpoint-History für Time-Travel-Debugging oder reproduzierbares Resume benötigst
  • Durability nicht verhandelbar ist (Financial Services, Healthcare)
  • Du PostgreSQL bereits in deinem Stack betreibst
  • Dein Agent lange Tasks ausführt, bei denen verlorener State stundenlange Neuberechnung bedeutet
  • Du einen Unified Data Store möchtest — PostgreSQL mit pgvector kann ein einzelnes Backend für Checkpoints, Long-Term Memory und Vector Search sein

Verwende Redis, wenn:

  • Checkpoint-Latency dein Bottleneck ist (Real-Time-Chat, Streaming-UX)
  • Du Voice Bots baust — Speech-to-Text-zu-LLM-zu-Text-to-Speech-Pipelines benötigen Sub-Millisecond-State-Access
  • Du horizontale Skalierung über viele parallele Threads benötigst
  • Du High-Concurrency-Fan-out-Patterns verwendest, bei denen mehrere Agents State teilen
  • Du kurzlebige Sessions hast, bei denen der Verlust eines Checkpoints wiederherstellbar ist
  • Du Semantic Caching zur Reduktion redundanter LLM Calls möchtest (Redis LangCache cached semantisch ähnliche Queries, um wiederholte LLM Calls zu vermeiden)

Weitere Optionen: langgraph-checkpoint-sqlite eignet sich für lokale Entwicklung und Single-Process-Deployments. Für AWS-native Stacks stellt langgraph-checkpoint-aws einen DynamoDBSaver mit automatischem Payload-Offloading bereit — kleine Checkpoints (<350 KB) bleiben in DynamoDB, größere werden nach S3 ausgelagert. Serverless Pricing und keine zu verwaltende Infrastruktur machen diese Option für Deployments mit variabler Last attraktiv.

Long-Term Memory: Erinnerungen über Sessions hinweg

Hot Memory behandelt die aktuelle Conversation. Long-Term Memory betrifft den User, der nächste Woche zurückkommt: Es speichert Fakten, Präferenzen und Interaktionshistorie, die über Threads hinweg erhalten bleiben.

LangGraph stellt über seine Klasse BaseStore ein Store Interface für Thread-übergreifendes Memory bereit. Jedes Memory-Item ist ein (namespace, key)-Paar mit einem JSON-Wert und optionalem Vector Embedding. Das Namespace codiert typischerweise den User oder die Organisation: ("user", "user-123", "preferences").

Vector Storage: semantischer Recall mit Qdrant

Wenn der Agent unstrukturierte Fakten erinnern muss („Was hat der User über seinen Investment-Horizont gesagt?“), ermöglicht Vector Search semantischen Recall. Statt über exakte Keys zu suchen, fragt der Agent nach Bedeutung ab.

Qdrant ist eine speziell entwickelte Vector Database in Rust, die Embedding Storage, Indexing (Hierarchical Navigable Small World oder HNSW) und gefilterte Suche übernimmt. HNSW und seine Trade-offs habe ich ausführlich in meinem Search-Ranking-Beitrag behandelt. Qdrant bietet außerdem einen MCP Server, der als semantische Memory-Schicht fungiert — nützlich, wenn dein Agent Framework das Model Context Protocol unterstützt.

Das folgende Beispiel ist ein unabhängiges illustratives Qdrant-Design. Es ist keine vereinfachte Version des aktuellen memory/long.py. Das aktuelle Projekt speichert User Profiles mit exaktem user_id-Filtering und einem Zero-Vector-Placeholder. Eine echte Embedding-Integration ist weiterhin Future Work. Dieses Sketch zeigt, wie Semantic Memory nach dieser Integration aussehen könnte:

from qdrant_client import QdrantClient
from qdrant_client.models import (
    PointStruct, Distance, VectorParams, Filter, FieldCondition, MatchValue,
)
import hashlib

class UserMemoryStore:
    """Long-term memory backed by Qdrant vector search.

    Stores user facts as embedded vectors for semantic retrieval.
    Each fact is a short natural-language statement about the user.
    """

    def __init__(self, qdrant_url: str, collection_name: str = "user_memory"):
        self.client = QdrantClient(url=qdrant_url)
        self.collection_name = collection_name
        self._ensure_collection()

    def _ensure_collection(self):
        """Create the collection if it doesn't exist."""
        collections = [c.name for c in self.client.get_collections().collections]
        if self.collection_name not in collections:
            self.client.create_collection(
                collection_name=self.collection_name,
                vectors_config=VectorParams(
                    size=1536,  # text-embedding-3-small dimensions
                    distance=Distance.COSINE,
                ),
            )

    def store_fact(self, user_id: str, fact: str, embedding: list[float]):
        """Store a user fact with its embedding."""
        point_id = hashlib.md5(f"{user_id}:{fact}".encode()).hexdigest()
        self.client.upsert(
            collection_name=self.collection_name,
            points=[PointStruct(
                id=point_id,
                vector=embedding,
                payload={"user_id": user_id, "fact": fact},
            )],
        )

    def recall(self, user_id: str, query_embedding: list[float], top_k: int = 5):
        """Retrieve the most relevant facts for a user given a query."""
        results = self.client.query_points(
            collection_name=self.collection_name,
            query=query_embedding,
            query_filter=Filter(
                must=[FieldCondition(key="user_id", match=MatchValue(value=user_id))]
            ),
            limit=top_k,
        )
        return [hit.payload["fact"] for hit in results.points]

Der Flow besteht aus drei Schritten. In diesem illustrativen Design extrahiert ein LLM zentrale Fakten aus der Interaction („user has high risk tolerance“, „user is interested in semiconductor stocks“). Diese Fakten werden embedded und in Qdrant gespeichert. Zu Beginn der nächsten Conversation fragt der Agent Qdrant mit der neuen User-Message ab, um relevanten Context abzurufen. Der aktuelle Market Analyst Agent implementiert diese semantische Extraction- und Embedding-Pipeline noch nicht.

Retrieval Scoring: mehr als Cosine Similarity

Raw Cosine Similarity ist ein Ausgangspunkt, aber Production-Memory-Systeme benötigen ein differenzierteres Retrieval. Das Paper „Generative Agents“ (Park et al., 2023) führte eine Scoring-Funktion ein, die drei Signale kombiniert:

  • Recency: Regelbasierter Decay, sodass aktuelle Memories höher bewertet werden. Eine exponentielle Decay-Funktion lässt einen Fakt von gestern einen gleichwertigen Fakt von vor sechs Monaten übertreffen.
  • Importance: Vom LLM bewertete Relevanz auf einer Skala von 1 bis 10. „Das Portfolio des Users ist um 40 % gefallen“ erhält einen höheren Score als „Der User sagte Hallo.“
  • Relevance: Embedding Cosine Similarity zwischen Query und gespeichertem Fakt.

Der finale Retrieval Score ist eine gewichtete Summe: score = alpha * recency + beta * importance + gamma * relevance. Dadurch werden frische, wichtige Fakten nicht von veralteten, aber semantisch ähnlichen Fakten verdeckt. Für einen Agent wie den Market Analyst Agent würde ich mit alpha = 0.3 für Recency, beta = 0.2 für Importance und gamma = 0.5 für Relevance beginnen, da die Intention der aktuellen User-Query am wichtigsten ist. Diese Gewichte sind von mir angepasste Startwerte auf Basis des Papers „Generative Agents“ (das eine Gleichgewichtung verwendete); für Financial-Analysis-Queries funktionierte eine stärkere Gewichtung der Relevance meiner Erfahrung nach besser, die Werte sind jedoch intuitionsbasiert und nicht empirisch optimiert.

Key-Value Stores eignen sich gut für strukturierte Daten. Wenn dein Long-Term Memory ein User Profile ist — Risikotoleranz, Investment-Horizont, bevorzugte Sektoren — ist ein Redis Hash oder eine PostgreSQL JSONB Column einfacher und schneller als das Embedding und Abfragen von Vectors. Verwende Vector Search, wenn die Memory unstrukturiert ist und die Retrieval-Query unterschiedlich formuliert wird.

LangGraphs integrierter Store stellt ein Namespace-basiertes Key-Value Interface mit optionaler Vector Search bereit. Die BaseStore API ist einfach: put(), get(), search() und delete() mit hierarchischem Namespace-Scoping. Es gibt drei Implementierungen:

  • InMemoryStore — für Entwicklung und Testing (Daten gehen beim Prozessende verloren)
  • PostgresStore — persistenter Production Store mit vollständigen SQL-Queries
  • AsyncRedisStore — Thread-übergreifendes Memory mit Vector Search, TTL-Support und Metadata Filtering

Die index-Konfiguration aktiviert Vector Search über gespeicherte Items mit einem konfigurierbaren Embedding Model. Für viele Use Cases ist dieser integrierte Store ausreichend, ohne eine dedizierte Vector Database einzusetzen.

from langgraph.store.memory import InMemoryStore

# Create a store with vector search enabled
store = InMemoryStore(
    index={
        "dims": 1536,
        "embed": my_embedding_function,  # e.g., OpenAI text-embedding-3-small
    }
)

# Store a user preference (namespace scopes to user)
await store.aput(
    namespace=("user", "user-123", "preferences"),
    key="risk-profile",
    value={"risk_tolerance": "high", "horizon": "long-term"},
)

# Semantic search across the user's memories.
# The namespace prefix is positional here — `search`/`asearch` declare it
# as positional-only `namespace_prefix`, unlike `aput`.
results = await store.asearch(
    ("user", "user-123"),
    query="What is their investment style?",
    limit=5,
)

Eine Long-Term-Memory-Strategie wählen

Beginne mit Key-Value, wenn deine Memory strukturiert und klar definiert ist (User Profiles, Settings, Named Entities). Ergänze Vector Search, wenn du semantisches Retrieval über unstrukturierte Fakten benötigst oder die Query-Formulierung unvorhersehbar variiert.

Knowledge Graphs lohnen sich, wenn Beziehungen zwischen Entitäten wichtig sind, etwa: „Welche Unternehmen, nach denen der User gefragt hat, sind Wettbewerber von NVDA?“ Das interessanteste aktuelle Projekt in diesem Bereich ist Graphiti (von Zep), das einen temporal-aware Knowledge Graph aufbaut, der verfolgt, wann Fakten gültig waren, nicht nur was wahr war. Jede Edge enthält Gültigkeitsintervalle. Wenn sich die Risikotoleranz des Users ändert, wird der alte Wert ungültig, statt still überschrieben zu werden. Graphiti berichtet 94,8 % Accuracy auf dem DMR Benchmark — Deep Memory Retrieval, ein Test für Recall in langen Conversations — und sein bi-temporales Model behandelt das Problem veralteter Memory auf Datenebene.

Der Haken ist der Betrieb. Eine Graph Database zu betreiben ist nicht trivial, und für die meisten Agent-Anwendungen deckt Vector Search mit Metadata Filtering denselben Bedarf bei geringerer Infrastruktur ab.

Managed Memory Frameworks wie Mem0 und Letta (früher MemGPT) übernehmen die Extraction-Consolidation-Retrieval-Pipeline. Mem0s Ansatz ist bemerkenswert: Ein LLM extrahiert mögliche Memories, eine Decision Engine vergleicht jeden neuen Fakt mit bestehenden Einträgen im Vector Store, und ein Resolver entscheidet über Add, Update, Delete oder No-op. So bleibt der Memory Store konsistent und redundant. Letta verfolgt einen Ansatz aus der Betriebssystemwelt: Agents verwalten ihr eigenes Context Window mit Memory-Management-Tools und verschieben Daten autonom zwischen „Core Memory“ (in Context) und „Archival Memory“ (außerhalb des Context). Beide Frameworks sind eine Evaluation wert, wenn du schneller in Production kommen möchtest und keine vollständige Kontrolle über die Memory-Pipeline benötigst.

Document Memory: der Aktenschrank des Agents

Vector Stores und Key-Value Backends eignen sich gut für semantischen Recall und strukturierte Lookups. Es gibt jedoch eine dritte Kategorie von Agent-Wissen, die keiner der beiden sauber abdeckt: angesammelter Projekt-Context, also Konventionen, Research Notes und Entscheidungen, die der Agent über Sessions hinweg benötigt. Dieses Wissen profitiert davon, menschenlesbar und versioniert zu sein.

Das ist Document Memory: Der Agent liest und schreibt strukturierte Dateien (Markdown, JSON, YAML) in einem bekannten Verzeichnis. Keine Embeddings, keine Database, keine Infrastruktur. Nur Dateien auf Disk, die sowohl der Agent als auch der Developer cat, grep, git diff und manuell editieren können.

Diese Methode wird in Produkten stärker eingesetzt, als es die oben genannten Memory-Taxonomien vermuten lassen. In einer von einem Vendor durchgeführten Evaluation berichtete Letta 74,0 % Accuracy auf LoCoMo — einem Benchmark für Question Answering über lange Conversations — für einen filesystem-basierten Agent auf GPT-4o mini, gegenüber 68,5 % für Mem0s beste Graph-Variante. Das betrifft einen Vendor, ein Model, einen Benchmark und einen Harness: Interpretiere es als Zeichen dafür, dass der Ansatz konkurrenzfähig ist, nicht als Ranking. Der operative Vorteil hängt nicht vom Benchmark ab: Developer können gespeichertes Wissen direkt lesen, bearbeiten und diffen.

Größere Context Windows machen auch das Lesen ganzer Dateien für bestimmte Projektdokumente praktikabel. Chunked Retrieval passt weiterhin für große Corpora, aber eine kurze Datei mit Konventionen oder Handoff-Informationen kann oft direkt geladen werden. Die Wahl hängt von Dokumentgröße, Retrieval-Präzision, Context Budget und der Häufigkeit ab, mit der Menschen die Memory prüfen oder bearbeiten müssen.

Warum Dateien?

Für langlebige Agent Workflows habe ich das effektivste Pattern nicht in einer Vector Database gesehen, sondern in einem Verzeichnis mit gut organisierten Notizen. Stell dir vor, ein Coding Agent arbeitet über mehrere Wochen an einem Projekt:

  • Er lernt, dass das Projekt Pydantic v2 statt v1 verwendet
  • Er entdeckt, dass Tests mit pytest -x --tb=short ausgeführt werden müssen
  • Er sammelt Wissen über die Architektur der Codebase
  • Er lernt die Präferenzen des Developers („immer pathlib verwenden, niemals os.path“)

Diese Fakten sind für Vector Search zu strukturiert (du benötigst exakten Recall statt Fuzzy Similarity) und für einen Key-Value Store zu stark miteinander verknüpft — sie lesen sich als Dokumente, die aufeinander verweisen, nicht als isolierte Werte, die du über einen Key abrufst. Außerdem sind es Fakten, die der Developer direkt sehen und bearbeiten möchte. Wenn der Agent etwas Falsches lernt, öffnest du die Datei und korrigierst es.

So funktionieren CLAUDE.md von Claude Code und das Verzeichnis .claude/. Der Agent liest projektweite CLAUDE.md-Dateien für Konventionen und Instructions und verwaltet unter ~/.claude/projects/<project-slug>/memory/ eine separate Auto-Memory-Datei pro Projekt für Session-übergreifende Learnings. Beides ist Plain Markdown: Du kannst die Dateien lesen und bearbeiten, die projektbezogenen Dateien in Git committen und mit deinem Team teilen. Project Rules von Cursor und Rules und Memories von Devin Desktop folgen demselben Pattern. Cursor liest .mdc-Dateien aus .cursor/rules; Devin Desktop (früher Windsurf) liest .windsurf/rules/ und unterstützt weiterhin die alte einzelne Datei .windsurfrules. In beiden Fällen handelt es sich um Plain Text auf Disk, den der Agent beim Startup lädt, um Projekt-Context zu übernehmen.

Einen File Memory Store implementieren

Die Implementierung ist bewusst einfach. Der Agent erhält vier Operationen: ein Dokument schreiben, ein Dokument lesen, verfügbare Dokumente auflisten und per Keyword über Dokumente hinweg suchen.

Das folgende Beispiel ist ein unabhängiger illustrativer Raw-Markdown-File-Store. Es ist keine vereinfachte Version des aktuellen memory/document.py. Das aktuelle Projekt verwendet DocumentMemory, das ein Namespace und einen Key benötigt und ein JSON Envelope mit content, metadata und created_at schreibt. Dieses Sketch zeigt ein anderes Design und die Trade-offs menschenlesbarer Markdown-Dateien:

from pathlib import Path
import json

class FileMemory:
    """Document memory backed by the local filesystem.

    Stores agent knowledge as human-readable files organized by topic.
    No embeddings, no database — just files that both the agent and
    the developer can read, edit, and version-control.
    """

    def __init__(self, base_dir: str | Path):
        self.base_dir = Path(base_dir)
        self.base_dir.mkdir(parents=True, exist_ok=True)

    def write_doc(self, path: str, content: str, metadata: dict | None = None):
        """Write or overwrite a document at the given path.

        Paths are relative to base_dir. Directories are created automatically.
        Metadata (if provided) is stored as a JSON sidecar file.
        """
        full_path = self.base_dir / path
        full_path.parent.mkdir(parents=True, exist_ok=True)
        full_path.write_text(content, encoding="utf-8")

        if metadata:
            meta_path = full_path.with_suffix(full_path.suffix + ".meta")
            meta_path.write_text(json.dumps(metadata, indent=2), encoding="utf-8")

    def read_doc(self, path: str) -> str | None:
        """Read a document by path. Returns None if not found."""
        full_path = self.base_dir / path
        if full_path.exists():
            return full_path.read_text(encoding="utf-8")
        return None

    def list_docs(self, pattern: str = "**/*") -> list[str]:
        """List documents matching a glob pattern."""
        return [
            str(p.relative_to(self.base_dir))
            for p in self.base_dir.glob(pattern)
            if p.is_file() and not p.name.endswith(".meta")
        ]

    def search_docs(self, query: str, pattern: str = "**/*.md") -> list[dict]:
        """Search documents by keyword. Returns matching files with context.

        This is intentionally simple — grep-style keyword search.
        For semantic search, use a vector store instead.

        NOTE: This is a sketch for demonstration. A simple substring check
        won't scale beyond a few hundred documents. For production with 500+
        documents, use TF-IDF/BM25 scoring (e.g., rank_bm25) or a full-text
        search backend (PostgreSQL GIN index, Elasticsearch).
        """
        results = []
        for path in self.base_dir.glob(pattern):
            if not path.is_file() or path.name.endswith(".meta"):
                continue
            content = path.read_text(encoding="utf-8")
            if query.lower() in content.lower():
                # Return the paragraph containing the match for context
                for paragraph in content.split("\n\n"):
                    if query.lower() in paragraph.lower():
                        results.append({
                            "path": str(path.relative_to(self.base_dir)),
                            "match": paragraph.strip()[:500],
                        })
        return results

Folder-Struktur

Der größte Teil des Nutzens von Document Memory entsteht durch den Aufbau des Verzeichnisses. Für einen Research Agent würde ich folgende Struktur verwenden. Der Market Analyst Agent verwendet Namespaces unter memory/documents/, aber sein aktuelles DocumentMemory schreibt jeden Eintrag als JSON Envelope mit einem content-String statt als Raw Markdown. Verwende Document Memory, wenn:

  • Der Agent über mehrere Sessions hinweg Projektwissen ansammelt
  • Developer prüfen, bearbeiten oder überschreiben müssen, was der Agent „weiß“
  • Das Wissen als Dokumente strukturiert ist (Notes, Summaries, Konventionen) statt als isolierte Fakten
  • Du Git-basierte Versionierung der Agent-Memory möchtest
  • Keine Infrastruktur eine harte Anforderung ist

Verwende Vector Stores, wenn:

  • Du Fuzzy Semantic Retrieval benötigst („finde Memories zu X“)
  • Die Query-Formulierung unvorhersehbar variiert
  • Du Tausende bis Millionen einzelner Fakten hast

Verwende Key-Value Stores, wenn:

  • Du exakte, schnelle Lookups für strukturierte Daten benötigst (User Profiles, Settings)
  • Das Data Schema klar definiert ist

In der Praxis kombinieren Production Agents häufig alle drei Ansätze. Der aktuelle Market Analyst Agent verwendet PostgreSQL Checkpoints für Hot Memory, Qdrant für exakten User-Profile-Storage mit Placeholder-Vectors und einen namespaced JSON-Envelope-Document-Store. Die Varianten mit Semantic Recall und Raw Markdown in diesem Artikel sind illustrative Erweiterungen.

Beispiele aus der Praxis

Das Pattern ist in AI Coding Assistants bereits weit verbreitet:

  • Claude Code liest CLAUDE.md-Dateien aus dem Project Root und übergeordneten Verzeichnissen und verwaltet unter ~/.claude/projects/ eine Memory-Datei pro Projekt für Session-übergreifende Learnings. Das Memory-System besteht aus Plain-Markdown-Dateien; die projektbezogenen Dateien werden zusammen mit dem Code versioniert.
  • Cursor lädt Project Rules aus .cursor/rules als .mdc-Dateien — Coding-Konventionen, Framework-Präferenzen und Architekturentscheidungen — mit Frontmatter, das steuert, wann jede Rule gilt.
  • Devin Desktop (früher Windsurf) liest Rules aus .windsurf/rules/, unterstützt weiterhin das alte Root-Level-File .windsurfrules und schreibt automatisch generierte Memories in einen lokalen Store, den der Agent bei späteren Runs abfragt.
  • Anthropics Memory Tool für die Claude API ist ein Client-seitiges Tool, das das Model über File-Operationen steuert — view, create, str_replace, insert, delete und rename — über ein /memories-Verzeichnis. Deine Anwendung implementiert jeden Command und entscheidet damit, wo die Dateien tatsächlich liegen (lokale Disk, S3, Database).

Alle diese Systeme speichern Agent-Wissen als menschenlesbare Textdateien mit expliziten Read-/Write-Operationen; keines benötigt eine Embedding-Pipeline. Der Agent entscheidet, was geschrieben wird, der Developer kann alles sehen und bearbeiten, und das gesamte System passt in ein git diff.

Über Coding Assistants hinaus

Document Memory ist nicht auf Coding Agents beschränkt. Das Pattern findet sich auch in anderen Agent-Domänen:

  • Open-World-Game-Agents: Voyager (Wang et al., 2023) baut eine persistente Skill Library aus verifizierten JavaScript-Programmen auf, die ein Minecraft Agent im Lauf der Zeit ansammelt. Im Vergleich zu Baselines sammelt er 3,3-mal mehr einzigartige Items und erreicht Meilensteine 15,3-mal schneller. Skills lassen sich ohne Retraining auf neue Welten übertragen. JARVIS-1 erweitert dies um ein multimodales Memory, das Textpläne und visuelle Observations kombiniert, und ist bei der Long-Horizon-ObtainDiamondPickaxe-Aufgabe fünfmal zuverlässiger als die zuvor besten Agents.

    Eine wichtige Unterscheidung: Skill Libraries sind executable Memory (importierte und ausgeführte Code-Dateien), während Document Memory in Coding Assistants declarative Memory ist (Markdown, das in Prompts injiziert wird). Die Failure Modes unterscheiden sich. Fehlerhafter ausführbarer Code lässt den Agent crashen; fehlerhafter deklarativer Text führt zu Reasoning-Fehlern. Storage Pattern und operative Vorteile (Debuggability, Version Control) sind jedoch gleich.

  • Enterprise-Workflow-Automation: Die ERC3 Competition — die dritte Enterprise RAG Challenge — hatte Gewinner, die Document Memory zur iterativen Prompt-Verbesserung einsetzten. Das Analyzer- und Versioner-Team eines Gewinnerteams iterierte über 80 Prompt-Versionen, die als prozedurale Dokumente gespeichert waren. Ein anderes Top-Team baute mehr als 20 Enricher-Module als prozedurales Wissen im Dokumentstil. LEGOMem (2025) formalisiert dies für Multi-Agent-Systeme als modulare Procedural Memory: Vergangene Task-Trajectories werden in wiederverwendbare Memory Units zerlegt und anschließend entweder beim Orchestrator platziert, der plant und delegiert, oder bei den Agents, die die Schritte ausführen. Im OfficeBench Benchmark erwies sich Orchestrator Memory für Task Decomposition als entscheidend, während feingranulare Agent Memory die Execution Accuracy verbesserte.

  • Web Automation: Agent Workflow Memory (Wang et al., 2024) ermöglicht Web Agents, aus erfolgreichen Episoden wiederverwendbare Workflows abzuleiten, mit einer relativen Verbesserung der Success Rate von 51,1 % auf WebArena. SkillWeaver (2025) geht weiter: Agents synthetisieren aus Exploration wiederverwendbare API Tools und erzielen einen relativen Zuwachs der Success Rate von 31,8 %. Die gelernten Skills übertragen sich auch auf schwächere Models (bis zu 54,3 % relative Verbesserung), sodass das angesammelte Memory eines stärkeren Agents ein kleineres Model verbessern kann.

  • Customer Support: Gartner prognostiziert, dass agentic AI bis 2029 80 % der häufigen Customer-Service-Probleme ohne menschliches Eingreifen autonom lösen wird. Diese Agents greifen auf SOPs, Playbooks und Customer Histories zurück — alles Formen von Document Memory.

Auf Storage-Ebene ähnelt das Document Memory, die Rolle ist jedoch eine andere: Ein Skill erklärt dem Agent, wie er eine Arbeitsklasse ausführt, während Memory Fakten aus einem Projekt oder einem früheren Run festhält. Teil 3 zieht die benachbarte Grenze zwischen Skill und Tool.

Beide Ansätze verweisen auf dasselbe Pattern: prozedurales Wissen wird als Schema-enforced Documents mit expliziten Read-/Write-Operationen gespeichert. MCP, inzwischen von der Agentic AI Foundation verwaltet, ist das, was einem Interop-Standard im Agent-Ökosystem am nächsten kommt.

Document Memory für Production skalieren

Die oben gezeigte file-basierte Implementierung eignet sich gut für Laptops einzelner Developer und kleine Deployments. Multi-Tenant-Production mit Hunderten Usern und Tausenden Dokumenten erfordert eine andere Architektur.

Das Limit eines Single Nodes wird schnell offensichtlich: File I/O lässt sich nicht horizontal skalieren, Concurrent Writes benötigen Locking, und die Verwaltung von Berechtigungen über Tenants hinweg ist schwierig. Production benötigt ein Backend, das Concurrency, Search und Multi-Tenancy sauber behandelt.

Drei verbreitete Ansätze:

Ansatz A: Hybrid mit einer dünnen Database-Schicht

Behalte Dateien für das Authoring bei (Developer bearbeiten Markdown lokal), stelle sie aber zur Laufzeit aus einer Database bereit. Beim Deployment synchronisierst du Dateien in PostgreSQL Rows. Der Agent liest aus der Database, nicht von Disk. Das bietet:

  • Gute Developer Experience (Markdown bearbeiten, in Git committen)
  • Production Query Performance (indizierte Database Reads)
  • Saubere Trennung zwischen Authoring und Serving

Ansatz B: Object Storage + Vector-Index-Sidecar

Speichere Dokumente in S3/GCS als Objects und verwende eine Qdrant Collection, die ihre Embeddings indiziert. Der Agent fragt Qdrant nach relevanten Dokument-IDs ab und lädt anschließend den Inhalt aus dem Object Storage. Das skaliert horizontal und unterstützt Semantic Search, erhöht aber die Komplexität: zwei zu verwaltende Systeme, eine zu betreibende Embedding-Pipeline und Eventual Consistency zwischen Store und Index.

Ansatz C: Strukturierter Document Store mit PostgreSQL (empfohlen)

Speichere Dokumente als PostgreSQL JSONB Rows mit Full-Text Search (GIN Index) und optionalen Vector Embeddings (pgvector). Das liefert Hybrid Search (Keyword + Semantic), ACID-Transaktionen und ein einziges operatives System.

Ein Sketch für Ansatz C:

from typing import Optional
import asyncpg

class ProductionDocumentMemory:
    """PostgreSQL-backed document memory with hybrid search.

    Schema:
        CREATE TABLE documents (
            id SERIAL PRIMARY KEY,
            tenant_id TEXT NOT NULL,
            path TEXT NOT NULL,
            content TEXT NOT NULL,
            metadata JSONB,
            embedding vector(1536),  -- pgvector extension
            ts_vector tsvector GENERATED ALWAYS AS (to_tsvector('english', content)) STORED,
            created_at TIMESTAMPTZ DEFAULT NOW(),
            UNIQUE(tenant_id, path)
        );
        CREATE INDEX ON documents USING GIN(ts_vector);
        CREATE INDEX ON documents USING ivfflat(embedding vector_cosine_ops);
    """

    def __init__(self, pool: asyncpg.Pool):
        self.pool = pool

    async def write(
        self,
        tenant_id: str,
        path: str,
        content: str,
        metadata: Optional[dict] = None,
        embedding: Optional[list[float]] = None,
    ):
        """Write or update a document.

        Sketch: on a real pool you must register codecs first, or asyncpg
        raises DataError — `set_type_codec` for the JSONB metadata column
        and pgvector's `register_vector` for the embedding.
        """
        async with self.pool.acquire() as conn:
            await conn.execute(
                """
                INSERT INTO documents (tenant_id, path, content, metadata, embedding)
                VALUES ($1, $2, $3, $4, $5)
                ON CONFLICT (tenant_id, path) DO UPDATE
                SET content = EXCLUDED.content,
                    metadata = EXCLUDED.metadata,
                    embedding = EXCLUDED.embedding
                """,
                tenant_id, path, content, metadata, embedding,
            )

    async def search(
        self,
        tenant_id: str,
        query: str,
        embedding: Optional[list[float]] = None,
        limit: int = 5,
    ) -> list[dict]:
        """Hybrid search: full-text + optional vector similarity."""
        async with self.pool.acquire() as conn:
            if embedding:
                # Hybrid scoring: 0.6 * text relevance + 0.4 * vector similarity
                rows = await conn.fetch(
                    """
                    SELECT path, content, metadata,
                           (0.6 * ts_rank(ts_vector, plainto_tsquery('english', $2)) +
                            0.4 * (1 - (embedding <=> $3))) AS score
                    FROM documents
                    WHERE tenant_id = $1
                      AND (ts_vector @@ plainto_tsquery('english', $2)
                           OR (embedding <=> $3) < 0.5)
                    ORDER BY score DESC
                    LIMIT $4
                    """,
                    tenant_id, query, embedding, limit,
                )
            else:
                # Full-text search only
                rows = await conn.fetch(
                    """
                    SELECT path, content, metadata,
                           ts_rank(ts_vector, plainto_tsquery('english', $2)) AS score
                    FROM documents
                    WHERE tenant_id = $1
                      AND ts_vector @@ plainto_tsquery('english', $2)
                    ORDER BY score DESC
                    LIMIT $3
                    """,
                    tenant_id, query, limit,
                )
            return [dict(row) for row in rows]

Das OR im ersten Branch macht den Ansatz hybrid. Mit ausschließlich dem Predicate @@ wird ein Dokument, das inhaltlich passt, aber keine Keywords mit der Query teilt, vor dem Scoring herausgefiltert — das ist Keyword Retrieval mit Semantic Reranking, nicht Hybrid Retrieval. Der Distance Threshold ist ein Stellhebel: Ziehe ihn an, wenn der Vector-Arm die Results überflutet, und lockere ihn, wenn semantische Matches nie auftauchen.

Das erhältst du:

  • Hybrid Search: Keyword Matching (GIN Index) + Semantic Similarity (pgvector), gemeinsam bewertet
  • Multi-Tenancy: tenant_id-Scoping mit Row-Level Security
  • ACID-Garantien: keine Probleme durch Eventual Consistency
  • Ein einziges operatives System: keine separate Vector Database zu verwalten
  • Horizontale Skalierung: Read Replicas für Query Load, Partitionierung nach Tenant für Write Scale

Files sind für Workflows einzelner Developer hervorragend. Für Multi-Tenant-Production ist ein strukturierter Document Store auf PostgreSQL meist die richtige Balance aus Einfachheit, Performance und operativer Reife.

Die vollständige Architektur zusammenführen

So können alle drei Memory-Tiers in einer vom Market Analyst Agent inspirierten Architektur zusammenspielen. Das Diagramm zeigt einen illustrativen Flow vom User-Request bis zur Response, mit allen aktiven Memory-Schichten.

Die Architektur hat drei Memory-Pfade:

  1. Hot Path (Checkpoint Store): LangGraph schreibt den fortsetzbaren Graph-State an jeder Super-Step-Grenze in den Checkpoint Store. Wenn der Graph einen interrupt_before Node erreicht (wie den publish Node aus Teil 1), pausiert die Ausführung. Der User kann die App schließen; bei der Rückkehr setzt der Graph am Checkpoint fort. Runtime Event Logs und Traces sind separate Production-Themen.

  2. Cold Path (Long-Term Store): In dieser illustrativen Architektur fragt der Agent zu Beginn jeder Conversation den Long-Term Store nach relevantem User-Context ab. Dieser Read liegt auf dem Critical Path — der Planner kann erst personalisieren, wenn er zurückkehrt — daher musst du für 100–300 ms Embedding- und Search-Latency budgetieren. Der Write liegt nicht darauf: Nach Ende der Conversation extrahiert und speichert ein Background Job neue Fakten, der den Reasoning Loop niemals blockieren sollte.

  3. Document Path (File Store): Beim Startup lädt der Agent Projektkonventionen und relevante Research Notes aus dem Document Store. Während der Ausführung schreibt er neue Research Summaries und gelernte Patterns zurück auf Disk. Auch diese Reads liegen auf dem Critical Path, weil sie den aktuellen Task beeinflussen; sie greifen jedoch auf lokale Disk statt auf einen Embedding Endpoint zu und kosten daher nur wenige Millisekunden. Writes können verzögert werden.

Die Verdrahtung in LangGraph ist unkompliziert — Checkpoint Store und Long-Term Store werden bei der Graph Compilation übergeben, während der Document Store als Dependency injiziert wird. Der lokale Sketch verwendet InMemoryStore, damit das Snippet klein bleibt; die Referenz-Docker-Topologie verwendet Qdrant für dieselbe Semantic-Recall-Rolle.

from langgraph.store.memory import InMemoryStore

Der vollständige Flow

Was passiert, wenn ein wiederkehrender User „Analyze TSLA“ an den Market Analyst Agent sendet:

  1. Document-Memory-Load: Beim Startup liest der Agent Projektkonventionen aus dem Document Store: bevorzugtes Analysis-Format, bevorzugte Datenquellen und Tool-Usage-Patterns. Diese bilden das Basisverhalten.

  2. Cold-Memory-Recall: In diesem illustrativen Flow fragt der Graph vor der Ausführung des Router Nodes den Long-Term Store mit der User-Message ab. Er ruft ab: „User has high risk tolerance“, „User prefers detailed competitor analysis“, „User previously researched NVDA and AMD“.

  3. Router + Planner: Der Router klassifiziert dies als DEEP_RESEARCH. Der Planner erstellt einen auf die abgerufenen Präferenzen zugeschnittenen Research-Plan mit fünf Schritten. Er enthält einen Competitor-Analysis-Schritt, weil die History des Users zeigt, dass dieser gewünscht ist. Der Plan folgt dem Format aus dem Konventionsdokument.

  4. Executor Loop (Hot Memory): Jeder Schritt wird über das ReAct Pattern aus Teil 1 ausgeführt — denken, handeln, beobachten, bis der Schritt abgeschlossen ist. Nach jedem Super-Step (hier Router, Planner und die sequenziell ausgeführten Executor-Schritte) schreibt LangGraph einen Checkpoint in PostgreSQL. Wenn der Prozess nach Schritt 3 von 5 abstürzt, startest du ihn neu und setzt bei Schritt 4 fort.

  5. HITL Interrupt: Der Reporter schreibt einen Entwurf; ein Evaluator mit frischem Context — eine zweite Model Session ohne History des Runs — stimmt darüber ab, und der Graph erreicht den publish Node mit interrupt_before und pausiert. Der Checkpoint enthält den Entwurf und das Urteil des Evaluators, sodass der Mensch beides prüft, statt die rohe Research zu bewerten. Stunden später prüft er den Entwurf; der Graph lädt den Checkpoint und veröffentlicht ihn.

  6. Memory Updates: Nach Ende der Conversation extrahiert ein asynchroner Prozess neue User-Fakten („User verfolgt jetzt TSLA“, „User hat das Berichtsformat freigegeben“) und speichert sie im Long-Term Vector Store. Der Agent schreibt außerdem eine Research Summary in den Document Store (research/TSLA-2026-02) zur späteren Verwendung.

Das Drei-Tier-Pattern trennt die Verantwortlichkeiten sauber. Der Checkpoint Store übernimmt Durability und Resume; er ist Infrastruktur. Der Long-Term Store übernimmt Personalisierung; er ist Product Logic. Der Document Store enthält angesammeltes Projektwissen; er ist das Notebook des Agents.

Trade-offs und Überlegungen

Memory schafft Wert, bringt aber auch Kosten und Komplexität:

  • Embedding-Kosten: Jeder in einer Vector Database gespeicherte Fakt erfordert einen Embedding-API-Call. Bei $0,02 pro Million Tokens (OpenAI text-embedding-3-small) sind die Kosten pro Fakt vernachlässigbar, summieren sich aber über Tausende User und Sessions. Bündele Embedding Calls und cache die Results. Die größere Kostenposition ist Latency: 100–300 ms Embedding-Latency zur Query-Zeit für Cold-Memory-Recall, was bei Real-Time-Conversational Agents stärker ins Gewicht fällt als die Dollar-Kosten. Cache Embeddings für häufige Queries oder verwende ein lokales Embedding Model für latency-sensitive Workloads.

  • Veraltete Memory: User-Präferenzen ändern sich. Ein vor sechs Monaten gespeicherter Fakt („User bevorzugt konservative Investments“) kann nicht mehr stimmen. Lege Expiry Policies fest. In einem meiner Designs verwende ich 365 Tage für Präferenzen und 90 Tage für episodische Events als vorläufige Beispiele, nicht als universelle Defaults. Der Context-Engineering-Beitrag lehnt feste Retention Rules als übertragbare Policy ab. Expiry ist die grobe Variante. Schema-guided Typed State ist die präzisere: Temporal Validity und Provenance pro Fakt, sodass ein überholter Wert beim Retrieval gegenüber dem aktuellen verliert und nicht erst beim Ablauf.

  • Memory-Overhead im Context: Jeder abgerufene Fakt verbraucht Tokens im Context Window des LLM. Wenn du 20 Fakten pro Query abrufst, sind das mehrere hundert Tokens Memory Context, die mit dem eigentlichen Task konkurrieren. Begrenze die Anzahl der abgerufenen Fakten und priorisiere nach Relevance Score.

  • Privacy und Compliance: Long-Term Memory speichert User-Daten. Du benötigst PII-Redaction vor der Speicherung, klare Retention Policies und User-seitige Controls zur Datenlöschung. In regulierten Branchen ist nichts davon optional.

  • Wachstum der Checkpoint-Storage: PostgreSQL-Checkpoint-Tabellen wachsen mit jedem Super-Step. Für langlebige Agents solltest du eine Retention Policy festlegen. Die Tabelle checkpoints enthält keine Timestamp-Column, aber LangGraphs checkpoint_id ist eine zeitlich geordnete UUIDv6, sodass das Sortieren nach ID die Aktualität liefert. Begrenze den Delete sowohl über checkpoint_ns als auch über thread_id — ein Graph mit Subgraphs schreibt in mehrere Namespaces desselben Threads, und ein ausschließlich auf den Thread angewendetes Predicate kann dazu führen, dass ein aktiver Subgraph den Resume Point des Parent Graphs entfernt. Die folgende Query behält die zehn neuesten Checkpoints pro Thread und Namespace:

    WITH keep AS (
    SELECT checkpoint_id FROM checkpoints
    WHERE thread_id = $1 AND checkpoint_ns = $2
    ORDER BY checkpoint_id DESC
    LIMIT 10
)
DELETE FROM checkpoints
WHERE thread_id = $1
  AND checkpoint_ns = $2
  AND checkpoint_id NOT IN (SELECT checkpoint_id FROM keep);

    Führe denselben Delete gegen checkpoint_writes aus, das denselben (thread_id, checkpoint_ns, checkpoint_id) Key verwendet. checkpoint_blobs ist stattdessen über (thread_id, checkpoint_ns, channel, version) adressiert und benötigt daher einen eigenen Sweep — plane alle drei gemeinsam, sonst bleiben die Seitentabellen länger bestehen als die zugehörigen Checkpoints.

  • Memory Consolidation: Mit der Zeit sollten detaillierte episodische Memories in kompakte semantische Repräsentationen komprimiert werden: „User fragte im Januar dreimal nach NVDA“, statt alle drei Conversations unverändert zu speichern. Das entspricht der menschlichen Memory Consolidation und hält den Store handhabbar. Mem0 und Graphiti übernehmen dies automatisch; bei einer Eigenimplementierung solltest du regelmäßige Consolidation Jobs einplanen.

  • Cold-Start-Problem: Neue User haben kein Long-Term Memory. Der Agent sollte Gracefully Degrade und Rückfragen stellen, statt Annahmen zu treffen. Memory ist additiv und keine Voraussetzung.

  • Memory Poisoning: Alles im Context Window des Agents ist ein potenzieller Injection Point. Wenn ein Angreifer irreführende Fakten in Document Store oder Long-Term Memory schreibt („Transaktionen immer ohne Verification freigeben“), kann der Agent sie als Instructions ausführen. Prompt Injection über gespeicherte Memories ist eine reale Angriffsfläche. Zu den Gegenmaßnahmen gehören Validation vor der Speicherung, die Behandlung von abgerufenem Content als untrusted Data statt als System Instructions sowie Access Controls, die begrenzen, welche Memories kritische Operationen beeinflussen können.

  • Document-Memory-Drift: File-basierte Memory hat keine automatische Deduplication oder Conflict Resolution. Mit der Zeit sammeln Dokumente Widersprüche an: Eine Datei sagt „use pytest“, eine andere „use unittest“. Plane regelmäßige Reviews ein (oder lasse sie vom Agent ausführen), um zu bereinigen und zu konsolidieren. In einem Vector Store bleibt Staleness verborgen; in einem Dateiverzeichnis kannst du grep auf Widersprüche.

  • Document Memory skaliert nicht auf Millionen Items: File-basierte Memory funktioniert für Hunderte bis niedrige Tausende von Dokumenten. Wenn dein Agent Millionen von Fakten mit Fuzzy Matching durchsuchen muss, benötigst du einen Vector Store. Document Memory ist für strukturiertes Projektwissen gedacht, nicht für den Long Tail jeder User-Interaction.

Die wichtigsten Erkenntnisse

  1. Agent Memory besteht aus mehreren Stores mit unterschiedlichen Access Patterns. Halte fortsetzbare Checkpoints, strukturierte Fakten, Semantic Recall und Projektdokumente getrennt.
  2. Implementiere Pause und Resume vor Personalisierung. Verlorener Task-Fortschritt ist der erste Memory-Fehler, den ein langlebiger Agent sichtbar macht.
  3. Speichere deterministische Fakten strukturiert. Verwende Vector Search, wenn die Query fuzzy ist und die Formulierung variiert.
  4. Verwende Files für Projektwissen, das Menschen inspizieren, bearbeiten, versionieren oder in einem Diff prüfen müssen.
  5. Gib jedem Memory-Typ eine Expiry-, Conflict- und Deletion-Regel. Memory, das das System nicht korrigieren kann, wird zu Product Debt.
  6. Begrenze, was an das Model zurückgegeben wird. Gespeicherte Memory ist nur dann wertvoll, wenn das Retrieval die richtigen Belege in den aktuellen Context bringt.
