Architektur der AI-Agent-Memory: Checkpoints und Vector Stores

Teil 2 der Serie „Engineering the Agentic Stack“

Ein Reasoning Loop überlebt nur eine Anfrage, sofern sein Zustand nicht außerhalb des Workers gespeichert wird. Ohne Agent Memory kann der Agent einen pausierten Plan weder fortsetzen noch sich nach einem Crash erholen oder sich an eine Präferenz aus einer früheren Session erinnern. Teil 1 behandelte den Control Flow. Dieser Beitrag zeigt, welchen Zustand jeder spätere Turn benötigt und wo dieser Zustand liegen sollte.

Ich erläutere die Memory-Architektur des Market Analyst Agent — eines kleinen LangGraph Agents, der Marktdaten abruft und einen Analystenbericht schreibt — und zeige, wie Hot Checkpoints, Cold Vector Stores und dateibasierte Dokument-Memory für langlebige Agents zusammenspielen. Anschließend geht es darum, wann PostgreSQL, Redis, Qdrant, Key-Value Stores und einfache Markdown-Dateien jeweils sinnvoll sind.

TL;DR: Trenne Memory nach Zugriffsmuster. Hot Memory ist Checkpoint-Zustand pro Konversation für Pause und Fortsetzung. Cold Memory enthält sitzungsübergreifende Fakten in einem Key-Value oder Vector Store. Document Memory hält Projektwissen in inspizierbaren Dateien. Beginne mit dem Fehler, den du beheben musst, und wähle anschließend den Store. Lege keine exakten Fakten in ein unscharfes Retrieval-System und behandle einen Checkpoint nicht als Audit-Log.

Jeder der folgenden Stores wird vom Harness gelesen, also von dem Code, der den Loop um das Model steuert. Das Harness entscheidet, welche Inhalte in das Context Window gelangen — nicht die Stores. Dieser Artikel behandelt, wo dieser Zustand liegt, bevor das Harness darauf zugreift. Teil 3 und Teil 4 behandeln, was das Harness anschließend mit dem Prompt macht.

Was ist AI-Agent-Memory?

AI-Agent-Memory ist die Zustandsschicht, die es einem Agent ermöglicht, den Task-Fortschritt zu bewahren, früheres Wissen abzurufen und sein Wissen über mehrere Runs hinweg zu aktualisieren. In Production ist sie keine einzelne Vector Database, sondern eine Kombination aus Hot Checkpoints, Cold Semantic oder Structured Stores und menschenlesbarer Document Memory.

Beginne nicht mit Memory, nur weil es intelligent klingt. Beginne mit dem für User sichtbaren Fehler: verlorener Fortschritt, vergessene Präferenz, wiederholte Recherche oder die fehlende Wiederverwendung einer Projektkonvention.

Fehlerbilder, die Memory erfordern

Ein Stateless Agent kann eine isolierte Frage beantworten, vergisst die Anfrage aber, sobald der Call endet. Dieses Design scheitert, sobald das Produkt eines der folgenden Verhaltensweisen benötigt:

  • Pause und Fortsetzung: Ein User startet eine Recherche, schließt seinen Laptop und kehrt am nächsten Tag zurück. Ohne Checkpoint-Zustand startet der Agent von vorn.
  • Kohärenz über mehrere Turns: In einer langen Konversation muss sich der Agent merken, welche Tools er aufgerufen, welche Daten er gesammelt und welche Planungsschritte er abgeschlossen hat.
  • Personalisierung: Ein wiederkehrender User erwartet, dass der Agent seine Risikotoleranz, die bevorzugte Analysetiefe und frühere Interaktionen kennt.
  • Human-in-the-Loop (HITL): Der Agent sammelt seine Belege und wartet auf die Freigabe eines Menschen für den nächsten Schritt. Der Zustand „wartet“ muss Prozessneustarts überleben.

Im Market Analyst Agent aus Teil 1 erzeugt die Anfrage „Analyze NVDA“ einen Plan, fünf Tool Calls, gesammelte Daten und einen Berichtsentwurf. Antwortet der User mit „sieht gut aus, aber füge eine Wettbewerbsanalyse hinzu“, kann ein Checkpoint Store den Zustand des letzten abgeschlossenen Schritts laden und den Wettbewerberschritt ergänzen. Ohne Checkpoint-Zustand kann der Agent nicht auflösen, worauf sich „sieht gut aus“ bezieht, und muss von vorn beginnen.

Long-Term Memory behandelt einen anderen Fall. Kehrt der User eine Woche später zurück und fragt „Update my NVDA analysis“, muss sich der Agent möglicherweise an eine Präferenz für konservative Risikobewertungen und ein Interesse an Halbleiteraktien erinnern. Ein Vector-backed Memory Store kann diese Fakten sitzungsübergreifend abrufen, ohne erneut danach zu fragen.

Die folgenden Implementierungsbeispiele verwenden LangGraph, LangChains Open-Source-Bibliothek zum Erstellen von Agents als explizite State Graphs; die von ihr gezogenen Storage-Grenzen lassen sich auf jedes Framework übertragen. LangGraph trennt Memory nach Scope. Jede Graph-Ausführung läuft innerhalb eines Threads, also einer Konversation oder eines Tasks. Persistierter Zustand innerhalb dieses Threads ist Short-Term Memory. Über Threads geteilter Zustand ist Long-Term Memory. Im Folgenden sind „Thread“ und „Konversation“ austauschbar; den Begriff „Session“ vermeide ich für diesen Scope, da Teil 5 ihn für das dauerhafte Log eines einzelnen Runs reserviert. Mehrere solcher Runs können sich auf einem Thread ansammeln. Der aktuelle Context des Models und Variablen im Prozess bilden die Working-Memory-Schicht oberhalb beider Stores.

Eine Taxonomie der AI-Agent-Memory

Vor der Implementierung hilft eine Klassifizierung dessen, woran sich Agents erinnern müssen. Das CoALA-Framework — Cognitive Architectures for Language Agents (Sumers, Yao et al., 2023) — ist eine häufig zitierte Taxonomie mit Anleihen aus der Kognitionswissenschaft. Working Memory umfasst das, womit das LLM gerade aktiv Reasoning betreibt: Python-Variablen in der aktuellen Funktion, den Inhalt des Context Window und Tool-Call-Argumente während der Ausführung. Es ist die schnellste und flüchtigste Schicht. Nichts bleibt über den aktuellen Schritt hinaus bestehen. Working Memory ist durch das Context Window des Models begrenzt und bildet damit den Bottleneck. Alles, was der Agent zum Entscheidungszeitpunkt „weiß“, muss hier hineinpassen — unabhängig davon, ob es aus dem Checkpoint Store, einer Vector Query oder einer gelesenen Datei stammt. Die anderen Tiers liefern die richtigen Informationen zum richtigen Zeitpunkt in das Working Memory.

Short-Term Memory ist der Checkpoint, den LangGraph nach jeder Einheit der Graph-Ausführung schreibt — einem Super-Step, der im nächsten Abschnitt definiert wird. Episodic und Semantic Memory bleiben über Threads hinweg bestehen. Document Memory speichert Projektnotizen, Recherche-Zusammenfassungen und gelernte Konventionen in Dateien, die Menschen und Agents inspizieren können. Procedural Memory lebt in System Instructions und Tool Definitions und ändert sich nicht für jeden User.

Für die Implementierung werden fünf der sechs Typen zu drei Storage-Tiers zusammengefasst. Short-Term Memory wird zu Hot Memory, dem Checkpoint für den aktuellen Thread. Episodic und Semantic werden zu Cold Memory, also dem Erinnern über Threads hinweg. Document Memory hält angesammeltes Projektwissen lesbar und direkt editierbar. Working Memory ist in der obigen Taxonomie dem Hot Tier zugeordnet, wird aber nie wirklich gespeichert: Es existiert nur für einen einzelnen Schritt im Prozess und ist das Context Window, in das die drei Storage-Tiers laden. Procedural Memory liegt außerhalb aller drei: Es lebt im System Prompt und in den Tool Definitions und wird mit dem Agent ausgeliefert, statt gespeichert und abgerufen zu werden.

CoALA klassifiziert Working, Episodic, Semantic und Procedural Memory. Die Studie „Memory in the Age of AI Agents“ betont Vector Stores und Knowledge Graphs, während LangGraph Checkpoints und sein Store Interface dokumentiert. Datei-basiertes Projektwissen liegt außerhalb dieser Taxonomien, obwohl Claude Code, Cursor und Devin Desktop allesamt persistente Projektdateien laden.

Dasselbe Storage-Pattern findet sich in anderen Domänen. Ein Minecraft Agent (Voyager) speichert wiederverwendbare Game Skills als Code Libraries, Teams in einem Enterprise-Document-QA-Wettbewerb iterieren über prozedurale Prompt-Dokumente, und Web Agents leiten aus erfolgreichen Runs wiederverwendbare Browsing-Workflows ab. Auf alle drei Beispiele komme ich später zurück; der Punkt ist hier, dass Dateien dieses Wissen ohne separaten Embedding Service inspizierbar und versionierbar machen.

Von einer festen RAG Pipeline unterscheidet sich vom Agent verwaltetes Memory außerdem dadurch, wer den Write ausführt. Der Agent oder sein Harness wählt aus, was gespeichert, aktualisiert und gelöscht wird, und entscheidet später, wann es abgerufen wird.

Das Paper „Generative Agents“ (Park et al., 2023) zeigte, wie weit dies gehen kann: Simulierte Agents speicherten, reflektierten über und riefen ihre eigenen Memories ab. Sein Memory Stream bewertete Kandidaten nach Aktualität, Wichtigkeit und Relevanz — ein Design, das weiterhin einen nützlichen Referenzpunkt für Agent-Memory-Retrieval bildet.

Short-Term Agent Memory: der Checkpoint Store

Immer wenn LangGraph einen Super-Step abschließt — einen einzelnen Node oder einen parallel ausgeführten Node-Batch — serialisiert das Framework den vollständigen Graph-Zustand und schreibt ihn in einen Checkpoint Store. Das ist die Grundlage für Pause/Fortsetzung, Time-Travel-Debugging und HITL-Workflows.

Ein Checkpoint enthält den für die Fortsetzung notwendigen Graph-Zustand: den AgentState aus Teil 1 — Messages, Identity, User Profile, Plan Steps, Research Data und Execution Mode. Zusätzlich speichert LangGraph eigene Verwaltungsdaten: ID und Timestamp des Checkpoints, eine Version pro Channel (LangGraphs Bezeichnung für einen einzelnen State Key) sowie einen separaten Datensatz darüber, welche Channel-Versionen jeder Node bereits gesehen hat. Die Step-Nummer liegt in den Metadaten des Checkpoints und nicht auf dem Checkpoint selbst. Durch den Vergleich dieser beiden Informationen ermittelt der Graph, was als Nächstes ausgeführt wird. Nach einem HITL Interrupt oder Prozessneustart lädt der Graph den Checkpoint an der letzten abgeschlossenen Grenze und steigt in den nächsten Node ein. Er setzt nicht an einer beliebigen Python-Zeile fort. Ein Checkpoint unterscheidet sich außerdem von einem Append-only Event Log oder Trace; Teil 5 trennt diese Runtime-Observability-Flächen ausdrücklich.

Funktionsweise des LangGraph-Checkpointing

LangGraphs BaseCheckpointSaver ist ein einfaches Interface: put() schreibt einen Checkpoint, get_tuple() liest den neuesten Checkpoint eines Threads, list() gibt die Historie zurück. Jeder Checkpoint wird über (thread_id, checkpoint_ns, checkpoint_id) adressiert, wobei thread_id die Konversation identifiziert, checkpoint_ns das Subgraph-Namespaceing übernimmt und checkpoint_id eine eindeutige Version ist.

Die relevante Entscheidung ist, welches Backend dahinterliegt. PostgreSQL und Redis sind zwei verbreitete Production-Optionen.

PostgreSQL: der dauerhafte Standard

PostgreSQL ist für die meisten Teams die sicherere Standardwahl. Checkpoints überleben Crashes, du erhältst vollständige Transaktionssemantik, und die Checkpoint-Historie macht Time-Travel-Debugging unkompliziert.

Eine vereinfachte Version des Checkpoint-Setups aus memory/hot.py:

from contextlib import asynccontextmanager

from langchain_core.messages import HumanMessage
from langgraph.checkpoint.postgres.aio import AsyncPostgresSaver

@asynccontextmanager
async def postgres_checkpointer(connection_string: str):
    """Yield a PostgreSQL-backed checkpoint store.

    PostgreSQL gives us ACID guarantees — if a checkpoint write succeeds,
    the state is durable even if the process crashes immediately after.
    `from_conn_string` is itself an async context manager: it owns the
    connection and closes it on exit, so the graph has to run inside it.
    """
    async with AsyncPostgresSaver.from_conn_string(connection_string) as checkpointer:
        # Create the checkpoint tables if they don't exist.
        # This is idempotent — safe to call on every startup.
        await checkpointer.setup()
        yield checkpointer

# Usage: the graph lives inside the context manager's scope
async with postgres_checkpointer(
    "postgresql://user:pass@localhost:5432/agent_memory"
) as checkpointer:
    graph = create_graph(checkpointer=checkpointer)

    # Every invoke/stream call now persists state automatically
    config = {"configurable": {"thread_id": "user-123-session-1"}}
    result = await graph.ainvoke({"messages": [HumanMessage(content="Analyze NVDA")]}, config)

    # Resume later on the same thread_id — loads the latest checkpoint
    result = await graph.ainvoke({"messages": [HumanMessage(content="approved")]}, config)

Das AsyncPostgresSaver verwendet das Package langgraph-checkpoint-postgres, das vier Tabellen anlegt: checkpoints (der serialisierte Zustand), checkpoint_blobs (große Binärdaten), checkpoint_writes (ausstehende Writes für Crash-Recovery) und checkpoint_migrations (Schema-Version). Concurrent Writers werden über den Primary Key (thread_id, checkpoint_ns, checkpoint_id) und Upserts voneinander getrennt, nicht über Locking. Zwei Worker auf demselben Thread beschädigen einander also nicht, koordinieren sich aber auch nicht.

Redis: wenn Latency der Bottleneck ist

Wenn Checkpoint-Latency im Sub-Millisekunden-Bereich entscheidend ist — etwa bei Echtzeit-Konversations-Agents oder High-Frequency-Tool-Loops — ist Redis die bessere Wahl.

Eine vereinfachte Version des Checkpoint-Setups aus memory/hot.py:

from contextlib import asynccontextmanager

from langgraph.checkpoint.redis.aio import AsyncRedisSaver

@asynccontextmanager
async def redis_checkpointer(redis_url: str):
    """Yield a Redis-backed checkpoint store.

    Redis stores checkpoints in memory for sub-millisecond access.
    Trade-off: less durable than PostgreSQL unless you enable AOF,
    Redis's append-only log — snapshots alone lose recent writes on a crash.
    """
    async with AsyncRedisSaver.from_conn_string(redis_url) as checkpointer:
        # Initialize Redis data structures
        await checkpointer.setup()
        yield checkpointer

# Usage: same graph API, different backend
async with redis_checkpointer("redis://localhost:6379") as checkpointer:
    graph = create_graph(checkpointer=checkpointer)

Der AsyncRedisSaver aus langgraph-checkpoint-redis speichert jeden Checkpoint als eigenes RedisJSON-Dokument unter demselben (thread_id, checkpoint_ns, checkpoint_id) Key wie der Postgres Saver. Das Redesign von v0.1.0 ersetzte mehrere Search-Operationen durch einen einzigen JSON.GET Call und reduzierte die Latency deutlich. Redis 8.0+ enthält RedisJSON und RediSearch standardmäßig — zusätzliche Module müssen nicht installiert werden.

Für Deployments mit knappem Memory speichert ShallowRedisSaver nur den neuesten Checkpoint pro Thread — keine Historie, aber minimaler RAM-Verbrauch. Nutze diese Variante, wenn du Pause/Fortsetzung benötigst, aber kein Time-Travel-Debugging.

Wann welche Option?

Verwende PostgreSQL, wenn:

  • du die vollständige Checkpoint-Historie für Time-Travel-Debugging oder reproduzierbare Fortsetzung benötigst
  • Dauerhaftigkeit nicht verhandelbar ist (Finanzdienstleistungen, Gesundheitswesen)
  • PostgreSQL bereits Teil deines Stacks ist
  • dein Agent lange Tasks ausführt, bei denen verlorener Zustand stundenlange Neuberechnung bedeutet
  • du einen Unified Data Store möchtest — PostgreSQL mit pgvector kann ein einziges Backend für Checkpoints, Long-Term Memory und Vector Search sein

Verwende Redis, wenn:

  • Checkpoint-Latency dein Bottleneck ist (Echtzeit-Chat, Streaming-UX)
  • du Voice Bots entwickelst — Speech-to-Text-zu-LLM-zu-Text-to-Speech-Pipelines benötigen State-Zugriff im Sub-Millisekunden-Bereich
  • du horizontale Skalierung über viele parallele Threads benötigst
  • du High-Concurrency-Fan-out-Patterns verwendest, bei denen mehrere Agents Zustand teilen
  • du kurzlebige Sessions hast, bei denen der Verlust eines Checkpoints wiederherstellbar ist
  • du Semantic Caching zur Reduktion redundanter LLM Calls möchtest (Redis LangCache cached semantisch ähnliche Queries, um wiederholte LLM Calls zu vermeiden)

Weitere Optionen: langgraph-checkpoint-sqlite eignet sich für lokale Entwicklung und Single-Process-Deployments. Für AWS-native Stacks stellt langgraph-checkpoint-aws einen DynamoDBSaver mit automatischem Payload-Offloading bereit — kleine Checkpoints (<350 KB) bleiben in DynamoDB, größere werden nach S3 ausgelagert. Serverless-Pricing und keine zu verwaltende Infrastruktur machen diese Option für Deployments mit variabler Last attraktiv.

Long-Term Memory: Erinnern über Sessions hinweg

Hot Memory behandelt die aktuelle Konversation. Long-Term Memory betrifft den User, der nächste Woche zurückkehrt: Es speichert Fakten, Präferenzen und Interaktionshistorie, die über Threads hinweg bestehen bleiben.

LangGraph stellt über seine Klasse BaseStore ein Store Interface für Thread-übergreifendes Memory bereit. Jedes Memory-Element ist ein (namespace, key)-Paar mit einem JSON-Wert und optionalem Vector Embedding. Das Namespace codiert typischerweise den User oder die Organisation: ("user", "user-123", "preferences").

Vector Storage: semantisches Erinnern mit Qdrant

Wenn der Agent sich an unstrukturierte Fakten erinnern muss („Was hat der User über seinen Investment-Zeithorizont gesagt?“), bietet Vector Search semantisches Erinnern. Statt über exakte Keys sucht der Agent nach Bedeutung.

Qdrant ist eine speziell entwickelte Vector Database in Rust, die Embedding Storage, Indexing (Hierarchical Navigable Small World, kurz HNSW) und gefilterte Suche unterstützt. HNSW und seine Trade-offs habe ich ausführlich in meinem Beitrag zum Search Ranking behandelt. Qdrant bietet außerdem einen MCP Server, der als semantische Memory-Schicht fungiert — nützlich, wenn dein Agent-Framework das Model Context Protocol unterstützt.

Eine vereinfachte Version des Vector Stores aus memory/long.py:

from qdrant_client import QdrantClient
from qdrant_client.models import (
    PointStruct, Distance, VectorParams, Filter, FieldCondition, MatchValue,
)
import hashlib

class UserMemoryStore:
    """Long-term memory backed by Qdrant vector search.

    Stores user facts as embedded vectors for semantic retrieval.
    Each fact is a short natural-language statement about the user.
    """

    def __init__(self, qdrant_url: str, collection_name: str = "user_memory"):
        self.client = QdrantClient(url=qdrant_url)
        self.collection_name = collection_name
        self._ensure_collection()

    def _ensure_collection(self):
        """Create the collection if it doesn't exist."""
        collections = [c.name for c in self.client.get_collections().collections]
        if self.collection_name not in collections:
            self.client.create_collection(
                collection_name=self.collection_name,
                vectors_config=VectorParams(
                    size=1536,  # text-embedding-3-small dimensions
                    distance=Distance.COSINE,
                ),
            )

    def store_fact(self, user_id: str, fact: str, embedding: list[float]):
        """Store a user fact with its embedding."""
        point_id = hashlib.md5(f"{user_id}:{fact}".encode()).hexdigest()
        self.client.upsert(
            collection_name=self.collection_name,
            points=[PointStruct(
                id=point_id,
                vector=embedding,
                payload={"user_id": user_id, "fact": fact},
            )],
        )

    def recall(self, user_id: str, query_embedding: list[float], top_k: int = 5):
        """Retrieve the most relevant facts for a user given a query."""
        results = self.client.query_points(
            collection_name=self.collection_name,
            query=query_embedding,
            query_filter=Filter(
                must=[FieldCondition(key="user_id", match=MatchValue(value=user_id))]
            ),
            limit=top_k,
        )
        return [hit.payload["fact"] for hit in results.points]

Der Ablauf besteht aus drei Schritten. Nach jeder Konversation extrahiert ein LLM Schlüsselfakten aus der Interaktion („User hat hohe Risikotoleranz“, „User interessiert sich für Halbleiteraktien“). Diese Fakten werden embedded und in Qdrant gespeichert. Zu Beginn der nächsten Konversation fragt der Agent Qdrant mit der neuen User-Nachricht ab, um relevanten Context abzurufen.

Retrieval Scoring: mehr als Cosine Similarity

Rohe Cosine Similarity ist ein Ausgangspunkt, aber Production-Memory-Systeme benötigen ein umfassenderes Retrieval. Das Paper „Generative Agents“ (Park et al., 2023) führte eine Scoring-Funktion ein, die drei Signale kombiniert:

  • Recency: Regelbasierter Verfall, sodass aktuelle Memories höher bewertet werden. Eine exponentielle Decay-Funktion lässt einen Fakt von gestern einen äquivalenten Fakt von vor sechs Monaten übertreffen.
  • Importance: Vom LLM bewertete Bedeutung auf einer Skala von 1 bis 10. „Das Portfolio des Users ist um 40 % gefallen“ erhält einen höheren Score als „User hat Hallo gesagt“.
  • Relevance: Embedding-Cosine-Similarity zwischen Query und gespeichertem Fakt.

Der finale Retrieval Score ist eine gewichtete Summe: score = alpha * recency + beta * importance + gamma * relevance. Dadurch werden aktuelle, wichtige Fakten nicht von veralteten, aber semantisch ähnlichen Fakten verdrängt. Für einen Agent wie den Market Analyst Agent würde ich mit alpha = 0.3 für Recency, beta = 0.2 für Importance und gamma = 0.5 für Relevance beginnen, da die aktuelle Query-Intention des Users am wichtigsten ist. Diese Gewichte sind von der Arbeit zu Generative Agents abgeleitete Startwerte (dort wurde gleich gewichtet); nach meiner Erfahrung funktioniert eine stärkere Gewichtung der Relevance bei Financial-Analysis-Queries besser. Die Werte sind jedoch intuitionsbasiert und nicht empirisch optimiert.

Key-Value Stores eignen sich gut für strukturierte Daten. Wenn dein Long-Term Memory ein User-Profil ist — Risikotoleranz, Investmenthorizont, bevorzugte Sektoren — ist ein Redis Hash oder eine PostgreSQL-JSONB-Spalte einfacher und schneller als das Embedding und Abfragen von Vectors. Verwende Vector Search, wenn das Memory unstrukturiert ist und die Retrieval-Query in ihrer Formulierung variiert.

LangGraphs integrierter Store stellt ein Namespace-basiertes Key-Value Interface mit optionaler Vector Search bereit. Die BaseStore API ist einfach: put(), get(), search() und delete() mit hierarchischem Namespace-Scope. Es stehen drei Implementierungen zur Verfügung:

  • InMemoryStore — für Entwicklung und Tests (Daten gehen beim Prozessende verloren)
  • PostgresStore — persistenter Production Store mit vollständigem SQL-Querying
  • AsyncRedisStore — Thread-übergreifendes Memory mit Vector Search, TTL-Support und Metadata Filtering

Die Konfiguration index aktiviert Vector Search über gespeicherte Items mit einem konfigurierbaren Embedding Model. Für viele Use Cases ist dieser integrierte Store ausreichend, ohne eine dedizierte Vector Database einzusetzen.

from langgraph.store.memory import InMemoryStore

        "dims": 1536,

# Store a user preference (namespace scopes to user)

Eine Strategie für Long-Term Memory auswählen

Beginne mit Key-Value, wenn dein Memory strukturiert und klar definiert ist (User-Profile, Settings, benannte Entitäten). Ergänze Vector Search, sobald du semantisches Retrieval über unstrukturierte Fakten benötigst oder die Formulierung der Query unvorhersehbar variiert.

Knowledge Graphs lohnen sich, wenn Beziehungen zwischen Entitäten wichtig sind, etwa: „Über welche Unternehmen hat der User gefragt, die Wettbewerber von NVDA sind?“ Das interessanteste neuere Projekt ist Graphiti von Zep. Es erstellt einen temporally-aware Knowledge Graph, der verfolgt, wann Fakten gültig waren, nicht nur, was gültig war. Jede Edge trägt Gültigkeitsintervalle. Eine Änderung der Risikotoleranz des Users macht den alten Wert dadurch ungültig, statt ihn stillschweigend zu überschreiben. Graphiti berichtet 94,8 % Genauigkeit auf dem DMR Benchmark — Deep Memory Retrieval, einem Recall-Test für lange Konversationen — und sein bi-temporales Model behandelt das Problem veralteter Memories auf Datenebene.

Der Haken ist der Betrieb. Eine Graph Database zu betreiben ist nicht trivial, und für die meisten Agent-Anwendungen deckt Vector Search mit Metadata Filtering denselben Bedarf mit weniger Infrastruktur ab.

Managed-Memory-Frameworks wie Mem0 und Letta (früher MemGPT) übernehmen die Pipeline aus Extraction, Consolidation und Retrieval. Der Ansatz von Mem0 ist bemerkenswert: Ein LLM extrahiert mögliche Memories, eine Decision Engine vergleicht jeden neuen Fakt mit bestehenden Einträgen im Vector Store, und ein Resolver entscheidet über Add, Update, Delete oder No-op. So bleibt der Memory Store konsistent und redundant. Letta verfolgt einen Ansatz aus der Betriebssystemwelt: Agents verwalten ihr eigenes Context Window mit Memory-Management-Tools und verschieben Daten autonom zwischen „Core Memory“ (im Context) und „Archival Memory“ (außerhalb des Contexts). Beide Frameworks sind eine Evaluation wert, wenn du schneller in Production kommen möchtest und keine vollständige Kontrolle über die Memory-Pipeline benötigst.

Document Memory: der Aktenschrank des Agents

Vector Stores und Key-Value Backends beherrschen semantisches Erinnern und strukturierte Lookups gut. Es gibt jedoch eine dritte Kategorie von Agent-Wissen, die keines von beiden sauber abdeckt: angesammelter Projekt-Context, also Konventionen, Recherche-Notizen und Entscheidungen, die der Agent über Sessions hinweg benötigt. Dieses Wissen profitiert davon, menschenlesbar und versioniert zu sein.

Das ist Document Memory: Der Agent liest und schreibt strukturierte Dateien (Markdown, JSON, YAML) in einem bekannten Verzeichnis. Keine Embeddings, keine Database, keine Infrastruktur. Nur Dateien auf der Festplatte, die sowohl der Agent als auch der Developer cat, grep, git diff und manuell editieren können.

In Produkten findet dieser Ansatz mehr Verbreitung, als die obigen Memory-Taxonomien vermuten lassen. In einer von einem Anbieter durchgeführten Evaluation berichtete Letta 74,0 % Genauigkeit auf LoCoMo — einem Benchmark für Frage-Antwort-Systeme über lange Konversationen — für einen filesystem-basierten Agent auf GPT-4o mini, gegenüber 68,5 % für Mem0s beste Graph-Variante. Das war ein Anbieter, ein Model, ein Benchmark und ein Harness: Das Ergebnis zeigt, dass der Ansatz konkurrenzfähig ist, stellt aber kein Ranking dar. Der operative Vorteil hängt nicht vom Benchmark ab: Developer können das gespeicherte Wissen direkt lesen, editieren und diffen.

Größere Context Windows machen das Lesen ganzer Dateien für manche Projektdokumente ebenfalls praktikabel. Chunked Retrieval passt weiterhin für große Korpora, aber eine kurze Datei mit Konventionen oder Handover-Informationen kann oft direkt geladen werden. Die Entscheidung hängt von Dokumentgröße, Retrieval-Präzision, Context-Budget und der Häufigkeit ab, mit der Menschen das Memory prüfen oder editieren müssen.

Warum Dateien?

Für langlebige Agent-Workflows ist das effektivste Pattern, das ich gesehen habe, keine Vector Database, sondern ein Verzeichnis mit gut organisierten Notizen. Stell dir vor, ein Coding Agent arbeitet über mehrere Wochen an einem Projekt:

  • Er lernt, dass das Projekt Pydantic v2 und nicht v1 verwendet.
  • Er entdeckt, dass Tests mit pytest -x --tb=short ausgeführt werden müssen.
  • Er sammelt Wissen über die Architektur der Codebase.
  • Er lernt die Präferenzen des Developers („immer pathlib verwenden, niemals os.path“).

Diese Fakten sind für Vector Search zu strukturiert (du benötigst exaktes Retrieval statt unscharfer Ähnlichkeit) und für einen Key-Value Store zu stark vernetzt. Sie lesen sich wie Dokumente, die aufeinander verweisen, nicht wie isolierte Werte, die du über einen Key abrufst. Außerdem sind es Fakten, die der Developer direkt sehen und editieren möchte. Lernt der Agent etwas Falsches, öffnest du die Datei und korrigierst es.

So funktionieren Claude Codes CLAUDE.md und das Verzeichnis .claude/. Der Agent liest projektweite CLAUDE.md-Dateien für Konventionen und Instructions und hält unter ~/.claude/projects/<project-slug>/memory/ eine separate Auto-Memory-Datei pro Projekt für sitzungsübergreifende Learnings. Beide sind einfaches Markdown: Du kannst sie lesen, editieren, die Projektdateien in Git committen und mit dem Team teilen. Cursors Project Rules sowie die Rules und Memories von Devin Desktop folgen demselben Pattern. Cursor liest .mdc-Dateien aus .cursor/rules; Devin Desktop (früher Windsurf) liest .windsurf/rules/ und unterstützt weiterhin die ältere einzelne Datei .windsurfrules. In beiden Fällen handelt es sich um Plaintext auf der Festplatte, den der Agent beim Start lädt, um Projekt-Context zu übernehmen.

Implementierung eines File Memory Stores

Die Implementierung ist bewusst einfach. Der Agent erhält vier Operationen: ein Dokument schreiben, ein Dokument lesen, verfügbare Dokumente auflisten und dokumentübergreifend per Keyword suchen.

Eine vereinfachte Version des Document Stores aus memory/document.py:

from pathlib import Path
import json

class FileMemory:
    """Document memory backed by the local filesystem.

    Stores agent knowledge as human-readable files organized by topic.
    No embeddings, no database — just files that both the agent and
    the developer can read, edit, and version-control.
    """

    def __init__(self, base_dir: str | Path):
        self.base_dir = Path(base_dir)
        self.base_dir.mkdir(parents=True, exist_ok=True)

    def write_doc(self, path: str, content: str, metadata: dict | None = None):
        """Write or overwrite a document at the given path.

        Paths are relative to base_dir. Directories are created automatically.
        Metadata (if provided) is stored as a JSON sidecar file.
        """
        full_path = self.base_dir / path
        full_path.parent.mkdir(parents=True, exist_ok=True)
        full_path.write_text(content, encoding="utf-8")

        if metadata:
            meta_path = full_path.with_suffix(full_path.suffix + ".meta")
            meta_path.write_text(json.dumps(metadata, indent=2), encoding="utf-8")

    def read_doc(self, path: str) -> str | None:
        """Read a document by path. Returns None if not found."""
        full_path = self.base_dir / path
        if full_path.exists():
            return full_path.read_text(encoding="utf-8")
        return None

    def list_docs(self, pattern: str = "**/*") -> list[str]:
        """List documents matching a glob pattern."""
        return [
            str(p.relative_to(self.base_dir))
            for p in self.base_dir.glob(pattern)
            if p.is_file() and not p.name.endswith(".meta")
        ]

    def search_docs(self, query: str, pattern: str = "**/*.md") -> list[dict]:
        """Search documents by keyword. Returns matching files with context.

        This is intentionally simple — grep-style keyword search.
        For semantic search, use a vector store instead.

        NOTE: This is a sketch for demonstration. A simple substring check
        won't scale beyond a few hundred documents. For production with 500+
        documents, use TF-IDF/BM25 scoring (e.g., rank_bm25) or a full-text
        search backend (PostgreSQL GIN index, Elasticsearch).
        """
        results = []
        for path in self.base_dir.glob(pattern):
            if not path.is_file() or path.name.endswith(".meta"):
                continue
            content = path.read_text(encoding="utf-8")
            if query.lower() in content.lower():
                # Return the paragraph containing the match for context
                for paragraph in content.split("\n\n"):
                    if query.lower() in paragraph.lower():
                        results.append({
                            "path": str(path.relative_to(self.base_dir)),
                            "match": paragraph.strip()[:500],
                        })
        return results

Verzeichnisstruktur

Der größte Teil des Nutzens von Document Memory ergibt sich aus der Struktur des Verzeichnisses. Für einen Research Agent würde ich folgende Form verwenden. Der Market Analyst Agent strukturiert seinen Store unter memory/documents/ auf dieselbe Weise, schreibt aber jeden Eintrag als JSON Envelope mit einem content-String statt als rohes Markdown — und verliert dadurch einen Großteil dessen, worum es im nächsten Absatz geht:

.agent-memory/

    PROGRESS.md                # Handoff for the next session: what is done, what is next
    user-profiles/
        user-123.md            # Preferences, history, risk profile
        user-456.md
    research/

Jede Datei ist Markdown, und der Zweck jeder Datei ist aus ihrem Pfad ersichtlich. Du kannst das gesamte Memory-Verzeichnis mit git diff einsehen, um zu sehen, was der Agent in einer Session gelernt hat, git revert ein fehlerhaftes Learning oder das Verzeichnis in ein anderes Projekt kopieren. Versuche das mit einer Qdrant Collection. Derselbe Tree als JSON Envelopes bewahrt zwar die Pfade, verliert aber die Diffs — ein schlechterer Trade-off, als es zunächst scheint.

Verwende Document Memory, wenn:

  • der Agent über mehrere Sessions hinweg Projektwissen ansammelt
  • Developer inspizieren, editieren oder überschreiben können müssen, was der Agent „weiß“
  • das Wissen als Dokumente strukturiert ist (Notizen, Zusammenfassungen, Konventionen) und nicht als isolierte Fakten
  • du Git-basierte Versionierung des Agent-Memory möchtest
  • keine Infrastruktur zwingend erforderlich sein darf

Verwende Vector Stores, wenn:

  • du unscharfes semantisches Retrieval benötigst („Finde Memories zu X“)
  • die Formulierung der Query unvorhersehbar variiert
  • du Tausende bis Millionen einzelner Fakten hast

Verwende Key-Value Stores, wenn:

  • du exakte, schnelle Lookups für strukturierte Daten benötigst (User-Profile, Settings)
  • das Daten-Schema klar definiert ist

In der Praxis kombinieren Production-Agents häufig alle drei Ansätze. Der Market Analyst Agent verwendet PostgreSQL Checkpoints für Hot Memory, Qdrant für semantisches Retrieval von User-Fakten und einen dateibasierten Document Store für Projektkonventionen und Recherche-Notizen.

Beispiele aus der Praxis

Das Pattern ist in AI-Coding-Assistenten bereits weit verbreitet:

  • Claude Code liest CLAUDE.md-Dateien aus dem Project Root und übergeordneten Verzeichnissen und verwaltet unter ~/.claude/projects/ eine projektbezogene Memory-Datei für sitzungsübergreifende Learnings. Das Memory-System besteht aus einfachen Markdown-Dateien, und die projektbezogenen Dateien werden zusammen mit dem Code committed.
  • Cursor lädt Project Rules aus .cursor/rules als .mdc-Dateien — Coding-Konventionen, Framework-Präferenzen und Architekturentscheidungen. Frontmatter steuert, wann jede Rule gilt.

Über Coding-Assistenten hinaus

Document Memory ist nicht auf Coding Agents beschränkt. Das Pattern findet sich auch in anderen Agent-Domänen:

  • Open-World-Game-Agents: Voyager (Wang et al., 2023) baut eine persistente Skill Library aus verifizierten JavaScript-Programmen auf, die ein Minecraft Agent im Laufe der Zeit ansammelt. Dadurch sammelt er 3,3-mal mehr einzigartige Items und erreicht Meilensteine 15,3-mal schneller als Baselines. Skills lassen sich ohne Retraining auf neue Welten übertragen. JARVIS-1 erweitert dies um ein multimodales Memory, das Textpläne und visuelle Beobachtungen kombiniert, und ist bei der langlaufenden ObtainDiamondPickaxe-Aufgabe fünfmal zuverlässiger als die zuvor besten Agents.

    Eine wichtige Unterscheidung: Skill Libraries sind ausführbares Memory (Code-Dateien, die importiert und ausgeführt werden), während Document Memory in Coding-Assistenten deklarativ ist (Markdown, das in Prompts injiziert wird). Die Failure Modes unterscheiden sich. Fehlerhafter ausführbarer Code lässt den Agent crashen; fehlerhafter deklarativer Text führt zu Reasoning-Fehlern. Das Storage-Pattern und die operativen Vorteile (Debuggability, Version Control) sind jedoch identisch.

  • Enterprise-Workflow-Automation: Die ERC3 Competition — die dritte Enterprise RAG Challenge — hatte Gewinner, die Document Memory für iterative Prompt-Verbesserung verwendeten. Ein Gewinnerteam iterierte mit Analyzer- und Versioner-Agents über 80 in prozeduralen Dokumenten gespeicherte Prompt-Versionen. Ein weiteres Top-Team baute mehr als 20 Enricher-Module als prozedurales Wissen im Dokumentstil. LEGOMem (2025) formalisiert dies für Multi-Agent-Systeme als modulares prozedurales Memory: Vergangene Task-Trajektorien werden in wiederverwendbare Memory-Einheiten zerlegt und anschließend entweder beim Orchestrator abgelegt, der plant und delegiert, oder bei den Agents, die die Schritte ausführen. Im OfficeBench Benchmark erwies sich Orchestrator-Memory als entscheidend für die Task-Decomposition, während feingranulares Agent-Memory die Ausführungsgenauigkeit verbesserte.

  • Web-Automation: Agent Workflow Memory (Wang et al., 2024) lässt Web Agents aus erfolgreichen Episoden wiederverwendbare Workflows ableiten und verbesserte die relative Erfolgsrate auf WebArena um 51,1 %. SkillWeaver (2025) geht weiter: Agents synthetisieren aus Exploration wiederverwendbare API-Tools und erzielen einen relativen Anstieg der Erfolgsrate um 31,8 %. Die gelernten Skills übertragen sich außerdem auf schwächere Models (bis zu 54,3 % relative Verbesserung). Das angesammelte Memory eines stärkeren Agents kann somit einen kleineren Agent aufwerten.

  • Customer Support: Gartner prognostiziert, dass agentic AI bis 2029 80 % der häufigen Customer-Service-Probleme ohne menschlichen Eingriff autonom lösen wird. Diese Agents greifen auf SOPs, Playbooks und Customer Histories zu — alles Formen von Document Memory.

Der MemAgents Workshop auf der ICLR 2026 ist ein Zeichen dafür, dass die Research-Community zu dem aufschließt, was Practitioners bereits gebaut haben.

Skills verwenden Dokumente, um prozedurale Instructions zu bündeln. Der Agent Skills Standard speichert diese Instructions in SKILL.md-Dateien mit YAML Frontmatter und einem Markdown Body. Das ähnelt Document Memory auf der Storage-Ebene, die Rolle ist jedoch eine andere: Ein Skill erklärt dem Agent, wie er eine Klasse von Aufgaben ausführt, während Memory Fakten aus einem Projekt oder früheren Run festhält. Teil 3 zieht die benachbarte Grenze zwischen Skill und Tool.

MCP (Model Context Protocol) geht in dieselbe Richtung: Tool Definitions sind JSON Schema-Dateien, die jeder Agent entdecken und aufrufen kann. Beide Ansätze weisen auf dasselbe Pattern hin: prozedurales Wissen wird als Schema-enforced Documents gespeichert, mit expliziten Read-/Write-Operationen. MCP, inzwischen von der Agentic AI Foundation verwaltet, ist das, was einem Interop-Standard im Agent-Ökosystem am nächsten kommt.

Document Memory für Production skalieren

Die oben gezeigte dateibasierte Implementierung funktioniert gut auf Laptops einzelner Developer und in kleinen Deployments. Multi-Tenant-Production mit Hunderten von Usern und Tausenden von Dokumenten benötigt eine andere Architektur.

Das Limit eines Single-Node-File-Systems wird schnell sichtbar: File I/O lässt sich nicht horizontal skalieren, Concurrent Writes benötigen Locking, und die Verwaltung von Berechtigungen über Tenants hinweg ist mühsam. Production benötigt einen Backing Store, der Concurrency, Search und Multi-Tenancy sauber unterstützt.

Drei verbreitete Ansätze:

Ansatz A: Hybrid mit dünner Database-Schicht

Behalte Dateien für das Authoring (Developer editieren Markdown lokal), liefere sie zur Laufzeit aber aus einer Database. Beim Deployment werden Dateien in PostgreSQL Rows synchronisiert. Der Agent liest aus der Database und nicht von der Festplatte. Das bietet:

  • gute Developer Experience (Markdown editieren, in Git committen)
  • Production-Query-Performance (indizierte Database Reads)
  • eine klare Trennung zwischen Authoring und Serving

Ansatz B: Object Storage + Vector-Index-Sidecar

Speichere Dokumente als Objects in S3/GCS und verwende eine Qdrant Collection, die ihre Embeddings indiziert. Der Agent fragt Qdrant nach relevanten Document IDs ab und ruft anschließend den Inhalt aus dem Object Storage ab. Das skaliert horizontal und unterstützt Semantic Search, erhöht aber die Komplexität: zwei zu verwaltende Systeme, eine zu betreibende Embedding-Pipeline und Eventual Consistency zwischen Store und Index.

Ansatz C: Strukturierter Document Store mit PostgreSQL (empfohlen)

Speichere Dokumente als PostgreSQL-JSONB-Rows mit Full-Text Search (GIN Index) und optionalen Vector Embeddings (pgvector). Damit erhältst du Hybrid Search (Keyword + Semantic), ACID-Transaktionen und ein einziges operatives System.

Eine Skizze von Ansatz C:

from typing import Optional
import asyncpg

class ProductionDocumentMemory:
    """PostgreSQL-backed document memory with hybrid search.

    Schema:
        CREATE TABLE documents (
            id SERIAL PRIMARY KEY,
            tenant_id TEXT NOT NULL,
            path TEXT NOT NULL,
            content TEXT NOT NULL,
            metadata JSONB,
            embedding vector(1536),  -- pgvector extension
            ts_vector tsvector GENERATED ALWAYS AS (to_tsvector('english', content)) STORED,
            created_at TIMESTAMPTZ DEFAULT NOW(),
            UNIQUE(tenant_id, path)
        );
        CREATE INDEX ON documents USING GIN(ts_vector);
        CREATE INDEX ON documents USING ivfflat(embedding vector_cosine_ops);
    """

    def __init__(self, pool: asyncpg.Pool):
        self.pool = pool

    async def write(
        self,
        tenant_id: str,
        path: str,
        content: str,
        metadata: Optional[dict] = None,
        embedding: Optional[list[float]] = None,
    ):
        """Write or update a document.

        Sketch: on a real pool you must register codecs first, or asyncpg
        raises DataError — `set_type_codec` for the JSONB metadata column
        and pgvector's `register_vector` for the embedding.
        """
        async with self.pool.acquire() as conn:
            await conn.execute(
                """
                INSERT INTO documents (tenant_id, path, content, metadata, embedding)
                VALUES ($1, $2, $3, $4, $5)
                ON CONFLICT (tenant_id, path) DO UPDATE
                SET content = EXCLUDED.content,
                    metadata = EXCLUDED.metadata,
                    embedding = EXCLUDED.embedding
                """,
                tenant_id, path, content, metadata, embedding,
            )

    async def search(
        self,
        tenant_id: str,
        query: str,
        embedding: Optional[list[float]] = None,
        limit: int = 5,
    ) -> list[dict]:
        """Hybrid search: full-text + optional vector similarity."""
        async with self.pool.acquire() as conn:
            if embedding:
                # Hybrid scoring: 0.6 * text relevance + 0.4 * vector similarity
                rows = await conn.fetch(
                    """
                    SELECT path, content, metadata,
                           (0.6 * ts_rank(ts_vector, plainto_tsquery('english', $2)) +
                            0.4 * (1 - (embedding <=> $3))) AS score
                    FROM documents
                    WHERE tenant_id = $1
                      AND (ts_vector @@ plainto_tsquery('english', $2)
                           OR (embedding <=> $3) < 0.5)
                    ORDER BY score DESC
                    LIMIT $4
                    """,
                    tenant_id, query, embedding, limit,
                )
            else:
                # Full-text search only
                rows = await conn.fetch(
                    """
                    SELECT path, content, metadata,
                           ts_rank(ts_vector, plainto_tsquery('english', $2)) AS score
                    FROM documents
                    WHERE tenant_id = $1
                      AND ts_vector @@ plainto_tsquery('english', $2)
                    ORDER BY score DESC
                    LIMIT $3
                    """,
                    tenant_id, query, limit,
                )
            return [dict(row) for row in rows]

Das OR im ersten Branch macht den Ansatz hybrid. Mit ausschließlich dem @@-Predicate wird ein Dokument, das zwar die richtige Bedeutung hat, aber keine Keywords mit der Query teilt, vor dem Scoring herausgefiltert — das ist Keyword Retrieval mit semantischem Reranking und kein Hybrid Retrieval. Der Distance Threshold ist ein Stellhebel: Ziehe ihn enger, wenn der Vector-Arm die Ergebnisse überflutet, und lockere ihn, wenn semantische Matches nie auftauchen.

Das erhältst du:

  • Hybrid Search: Keyword Matching (GIN Index) + semantische Ähnlichkeit (pgvector), gemeinsam bewertet
  • Multi-Tenancy: tenant_id-Scoping mit Row-Level Security
  • ACID-Garantien: keine Probleme durch Eventual Consistency
  • Ein operatives System: keine separate Vector Database zu verwalten
  • Horizontale Skalierung: Read Replicas für Query-Last und Partitionierung nach Tenant für Write-Scale

Dateien sind für Workflows einzelner Developer hervorragend geeignet. Für Multi-Tenant-Production ist ein strukturierter Document Store auf PostgreSQL meist die beste Balance aus Einfachheit, Performance und operativer Reife.

Zusammensetzen: die vollständige Architektur

So arbeiten die drei Memory-Tiers im Market Analyst Agent zusammen. Das Diagramm zeigt den vollständigen Ablauf von der User-Anfrage bis zur Antwort, mit allen aktiven Memory-Schichten.

Die Architektur hat drei Memory-Pfade:

  1. Hot Path (Checkpoint Store): LangGraph schreibt den fortsetzbaren Graph-Zustand an jeder Super-Step-Grenze in den Checkpoint Store. Erreicht der Graph einen interrupt_before Node — etwa den publish Node aus Teil 1 — pausiert die Ausführung. Der User kann die App schließen; bei der Rückkehr setzt der Graph am Checkpoint fort. Runtime Event Logs und Traces sind davon getrennte Production-Themen.

  2. Cold Path (Long-Term Store): Zu Beginn jeder Konversation fragt der Agent den Long-Term Store nach relevantem User-Context ab. Dieser Read liegt auf dem Critical Path — der Planner kann erst nach dessen Rückkehr personalisieren —, daher müssen 100–300 ms für Embedding und Search eingeplant werden. Der Write liegt nicht auf dem Critical Path: Nach Ende der Konversation extrahiert und speichert ein Background Job neue Fakten. Dieser Job darf den Reasoning Loop niemals blockieren.

  3. Document Path (File Store): Beim Start lädt der Agent Projektkonventionen und relevante Recherche-Notizen aus dem Document Store. Während der Ausführung schreibt er neue Recherche-Zusammenfassungen und gelernte Muster zurück auf die Festplatte. Auch diese Reads liegen auf dem Critical Path, weil sie den aktuellen Task beeinflussen; sie greifen jedoch auf die lokale Festplatte statt auf einen Embedding Endpoint zu und kosten daher nur wenige Millisekunden. Writes können verzögert werden.

Die Verdrahtung in LangGraph ist unkompliziert: Checkpoint Store und Long-Term Store werden bei der Graph Compilation übergeben, während der Document Store als Dependency injiziert wird. Die lokale Skizze verwendet InMemoryStore, damit das Snippet klein bleibt; die Referenz-Docker-Topologie verwendet Qdrant für dieselbe Rolle des semantischen Erinnerns.

from langgraph.store.memory import InMemoryStore

Der vollständige Ablauf

Was geschieht, wenn ein wiederkehrender User „Analyze TSLA“ an den Market Analyst Agent sendet:

  1. Document-Memory-Load: Beim Start liest der Agent Projektkonventionen aus dem Document Store: Präferenzen für das Analyseformat, bevorzugte Datenquellen und Tool-Usage-Patterns. Sie definieren das grundlegende Verhalten.

  2. Cold-Memory-Recall: Bevor der Router Node ausgeführt wird, fragt der Graph den Long-Term Store mit der User-Nachricht ab. Er ruft ab: „User hat hohe Risikotoleranz“, „User bevorzugt eine detaillierte Wettbewerbsanalyse“, „User hat zuvor NVDA und AMD recherchiert“.

  3. Router + Planner: Der Router klassifiziert die Anfrage als DEEP_RESEARCH. Der Planner erstellt einen auf die abgerufenen Präferenzen zugeschnittenen Fünf-Schritte-Research-Plan. Er enthält einen Wettbewerbsanalyse-Schritt, weil die Historie des Users zeigt, dass dieser eine solche Analyse wünscht. Der Plan folgt dem Format aus dem Konventionsdokument.

  4. Executor Loop (Hot Memory): Jeder Schritt wird nach dem ReAct Pattern aus Teil 1 ausgeführt — denken, handeln, beobachten, bis der Schritt abgeschlossen ist. Nach jedem Super-Step (hier Router, Planner und jeder sequenziell ausgeführte Executor-Schritt) schreibt LangGraph einen Checkpoint nach PostgreSQL. Crasht der Prozess nach Schritt 3 von 5, startest du ihn neu und setzt bei Schritt 4 fort.

  5. HITL Interrupt: Der Reporter schreibt einen Entwurf. Ein Evaluator mit frischem Context — eine zweite Model-Session ohne Historie dieses Runs — bewertet ihn. Der Graph erreicht den publish Node mit interrupt_before und pausiert. Der Checkpoint enthält den Entwurf und das Urteil des Evaluators, sodass der Mensch beides prüfen kann, statt die rohe Recherche selbst bewerten zu müssen. Stunden später prüft der Mensch den Entwurf; der Graph lädt den Checkpoint und veröffentlicht ihn.

  6. Memory Updates: Nach Ende der Konversation extrahiert ein asynchroner Prozess neue User-Fakten („User verfolgt jetzt TSLA“, „User hat das Berichtsformat freigegeben“) und speichert sie im Long-Term Vector Store. Außerdem schreibt der Agent eine Recherche-Zusammenfassung in den Document Store (research/TSLA-2026-02) zur späteren Verwendung.

Das Drei-Tier-Pattern trennt die Verantwortlichkeiten sauber. Der Checkpoint Store übernimmt Dauerhaftigkeit und Fortsetzung; er ist Infrastruktur. Der Long-Term Store übernimmt Personalisierung; er ist Produktlogik. Der Document Store enthält angesammeltes Projektwissen; er ist das Notizbuch des Agents.

Trade-offs und Überlegungen

Memory schafft Nutzen, bringt aber auch Kosten und Komplexität mit sich:

  • Embedding-Kosten: Jeder in einer Vector Database gespeicherte Fakt erfordert einen Embedding-API-Call. Bei $0,02 pro Million Tokens (OpenAI text-embedding-3-small) sind die Kosten pro Fakt vernachlässigbar, summieren sich aber über Tausende von Usern und Sessions. Batch Embedding Calls und cache Ergebnisse. Die größere Kostenposition ist die Latency: 100–300 ms Embedding-Latency beim Query-Time-Recall von Cold Memory. Für Echtzeit-Konversations-Agents ist das wichtiger als der Preis. Cache Embeddings für häufige Queries oder verwende für latenzkritische Workloads ein lokales Embedding Model.

  • Veraltetes Memory: User-Präferenzen ändern sich. Ein vor sechs Monaten gespeicherter Fakt („User bevorzugt konservative Investments“) kann inzwischen falsch sein. Lege Expiry-Policies fest. Ich verwende 365 Tage für Präferenzen und 90 Tage für episodische Events, wie in meinem Context-Engineering-Beitrag beschrieben. Expiry ist die grobe Lösung. Schema-guided Typed State ist die präzisere: Temporal Validity und Provenance für jeden Fakt, sodass ein überholter Wert beim Retrieval gegenüber dem aktuellen verliert und nicht erst beim Ablaufdatum.

  • Memory-Overhead im Context: Jeder abgerufene Fakt verbraucht Tokens im Context Window des LLM. Wenn du pro Query 20 Fakten abrufst, konkurrieren mehrere hundert Tokens Memory-Context mit dem eigentlichen Task. Begrenze die Zahl der abgerufenen Fakten und priorisiere sie nach dem Relevance Score.

  • Privacy und Compliance: Long-Term Memory speichert User-Daten. Vor dem Speichern benötigst du PII-Redaction, klare Retention-Policies und User-seitige Controls zum Löschen von Daten. In regulierten Branchen ist nichts davon optional.

  • Wachstum des Checkpoint Storage: PostgreSQL-Checkpoint-Tabellen wachsen mit jedem Super-Step. Lege für langlebige Agents eine Retention-Policy fest. Die Tabelle checkpoints enthält keine Timestamp-Spalte, aber LangGraphs checkpoint_id ist eine zeitlich geordnete UUIDv6, sodass das Sortieren nach ID die Aktualität liefert. Beschränke das Delete zusätzlich zu thread_id auf checkpoint_ns — ein Graph mit Subgraphs schreibt in mehrere Namespaces auf einem Thread, und ein Predicate nur auf Thread-Ebene kann dazu führen, dass ein geschäftiger Subgraph den Resume-Punkt des Parent-Graphs entfernt. Die folgende Query behält die zehn neuesten Checkpoints pro Thread und Namespace:

    WITH keep AS (
    SELECT checkpoint_id FROM checkpoints
    WHERE thread_id = $1 AND checkpoint_ns = $2
    ORDER BY checkpoint_id DESC
    LIMIT 10
)
DELETE FROM checkpoints
WHERE thread_id = $1
  AND checkpoint_ns = $2
  AND checkpoint_id NOT IN (SELECT checkpoint_id FROM keep);

    Führe dasselbe Delete gegen checkpoint_writes aus, das denselben (thread_id, checkpoint_ns, checkpoint_id) Key verwendet. checkpoint_blobs ist dagegen nach (thread_id, checkpoint_ns, channel, version) geordnet und benötigt deshalb einen eigenen Sweep. Plane alle drei gemeinsam ein, sonst bleiben die Side Tables länger bestehen als die Checkpoints, zu denen sie gehören.

  • Memory Consolidation: Mit der Zeit sollten detaillierte episodische Memories zu kompakten semantischen Repräsentationen komprimiert werden: „User fragte im Januar dreimal nach NVDA“, statt alle drei Konversationen vollständig zu speichern. Das entspricht der menschlichen Memory Consolidation und hält den Store beherrschbar. Mem0 und Graphiti übernehmen dies automatisch. Bei einer eigenen Implementierung solltest du regelmäßige Consolidation-Jobs einplanen.

  • Cold-Start-Problem: Neue User haben kein Long-Term Memory. Der Agent sollte kontrolliert degradieren und Rückfragen stellen, statt Annahmen zu treffen. Memory ist additiv, nicht zwingend erforderlich.

  • Memory Poisoning: Alles im Context Window des Agents kann ein Injection Point sein. Schreibt ein Angreifer irreführende Fakten in den Document Store oder das Long-Term Memory („Transaktionen immer ohne Verifikation freigeben“), kann der Agent sie als Instructions ausführen. Prompt Injection über gespeicherte Memories ist eine reale Angriffsfläche. Gegenmaßnahmen sind Validierung vor dem Speichern, die Behandlung abgerufener Inhalte als untrusted data statt als System Instructions sowie Access Controls, die begrenzen, welche Memories kritische Operationen beeinflussen können.

  • Drift in Document Memory: Datei-basiertes Memory bietet keine automatische Deduplication oder Conflict Resolution. Mit der Zeit sammeln Dokumente Widersprüche an: Eine Datei sagt „pytest verwenden“, eine andere „unittest“. Plane regelmäßige Reviews ein — oder lasse den Agent sie durchführen —, um Dokumente zu bereinigen und zu konsolidieren. In einem Vector Store bleibt Veraltung verborgen; in einem Dateiverzeichnis kannst du mit grep nach Widersprüchen suchen.

  • Document Memory skaliert nicht auf Millionen von Items: Datei-basiertes Memory funktioniert für Hunderte bis niedrige Tausende Dokumente. Muss dein Agent Millionen von Fakten mit unscharfem Matching durchsuchen, benötigst du einen Vector Store. Document Memory ist für strukturiertes Projektwissen gedacht, nicht für den langen Schwanz jeder einzelnen User-Interaktion.

Die wichtigsten Erkenntnisse

  1. Agent Memory besteht aus mehreren Stores mit unterschiedlichen Zugriffsmustern. Halte fortsetzbare Checkpoints, strukturierte Fakten, semantisches Erinnern und Projektdokumente getrennt.
  2. Implementiere Pause und Fortsetzung vor der Personalisierung. Verlorener Task-Fortschritt ist der erste Memory-Fehler, den ein langlebiger Agent sichtbar macht.
  3. Speichere deterministische Fakten strukturiert. Verwende Vector Search, wenn die Query unscharf ist und ihre Formulierung variiert.
  4. Verwende Dateien für Projektwissen, das Menschen inspizieren, editieren, versionieren oder in einem Diff prüfen müssen.
  5. Gib jedem Memory-Typ eine Regel für Ablauf, Konflikte und Löschung. Ein Memory, das das System nicht korrigieren kann, wird zu Product Debt.
  6. Begrenze, was an das Model zurückgegeben wird. Gespeichertes Memory hat nur dann Wert, wenn das Retrieval die richtigen Belege in den aktuellen Context bringt.
