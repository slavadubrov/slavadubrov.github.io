Datenverarbeitungs-Engines: Polars, DataFusion, Ray und Spark

Viacheslav Dubrov

2026-02-21 · Aktualisiert 2026-07-15 · 14 Min. · KI-Infrastruktur

Automatische Übersetzung Dieser Artikel wurde automatisch aus der englischen Originalversion übersetzt.

Jahrelang übernahm Pandas die Arbeit mit In-Memory-Tabellendaten, während Apache Spark für die verteilte Verarbeitung zuständig war. Diese Aufteilung funktionierte gut, solange die Daten strukturiert waren.

Moderne Pipelines verarbeiten auch Bilder, Audio und Video. Bei solchen Workloads kann CPU-Decoding die GPU-Inference ausbremsen, während die Garbage Collection der JVM und Pythons Global Interpreter Lock den Throughput begrenzen. Neue Engines nutzen Rust und Apache Arrow, um diese Kosten zu reduzieren.

Für den Vergleich der Optionen habe ich Pandas, Polars, DataFusion, Daft und natives Rust anhand von zwei realen Datasets gebenchmarkt. Spark und Ray werden in separaten verteilten Notebooks behandelt. NYC-Taxifahrten stehen für tabellarische Verarbeitung; Food-101-Bilder repräsentieren eine multimodale Pipeline.

Das engine-comparison-demo repository enthält den Code. Führen Sie ihn auf Ihrer eigenen Hardware aus, da die Performance einer Engine von Maschine, Dataset und Workload abhängt.

TL;DR

Beginnen Sie mit der Struktur des Workloads, nicht mit dem Gewinner eines Benchmarks. Polars ist ein starker Standard für lokale DataFrame-Pipelines; DataFusion eignet sich für Teams, die eine Query-Engine einbetten; Ray Data und Daft sind für gemischte CPU/GPU-Pipelines ausgelegt; und Spark bleibt eine ausgereifte Wahl für verteiltes SQL und ETL. Die in diesem Leitfaden beschriebenen Speedups beziehen sich auf spezifische Workloads und übertragen sich nicht automatisch auf Ihre. Führen Sie die begleitenden Benchmarks mit Ihren Daten und auf Ihrer Hardware erneut aus, bevor Sie sich entscheiden.

Arten von Workloads in der Datenverarbeitung

Engines sind auf bestimmte Aufgaben spezialisiert. Die erste Frage lautet daher, welche Art von Workload tatsächlich vorliegt. Die wichtigste Unterscheidung ist strukturiert versus multimodal.

Strukturierte oder tabellarische Daten umfassen Filtering, Aggregation und Joins. Die Verarbeitung ist in der Regel CPU-bound und passt häufig in den Arbeitsspeicher. Viele solcher Queries können auf einer modernen Maschine ausgeführt werden. Dennoch bestimmen Speicher, I/O, Concurrency, Recovery und die Struktur des Workloads, ob ein Cluster sinnvoll ist.

Multimodale AI verarbeitet Bilder, Audio oder Video. Die Inference kann auf einer GPU laufen, während CPU-Decoding, Remote Reads oder Batching die Pipeline begrenzen. Welche Stufe den Throughput begrenzt, hängt vom Instance-Typ und den Operators ab. Messen Sie daher die Auslastung über den gesamten Pfad, statt die GPU isoliert zu dimensionieren.

Die neueren Engines zielen auf unterschiedliche Bereiche dieses Spektrums. Native Execution kann den Python-Overhead reduzieren, Arrow-kompatible Interfaces können den Datenaustausch günstiger machen, und Streaming Execution kann den Speicherbedarf bei Datasets begrenzen, die größer als der Arbeitsspeicher sind. Keiner dieser Vorteile tritt jedoch automatisch bei jedem Operator oder jeder Konvertierung ein.

Teil 1: Verarbeitung auf einem einzelnen Node

Pandas setzt auf ein eager In-Memory-Programmiermodell. Viele gängige Operationen erzeugen Zwischenresultate, und die parallele Ausführung wird nicht über einen Query Optimizer koordiniert. Dieser Trade-off hält explorativen Code direkt verständlich, kann bei größeren analytischen Scans jedoch teuer werden. Im PDS-H-Benchmark von Polars benötigte Pandas bei einem Scale Factor von 10 für die Suite etwa 365 Sekunden, während die Streaming Engine von Polars 3,89 Sekunden benötigte. Das Ergebnis von ungefähr 94x beschreibt diesen Benchmark und diese Konfiguration; es ist kein allgemeiner Umrechnungsfaktor von Pandas zu Polars.

Polars für lokale tabellarische Pipelines

Polars ist eine praktische Standardwahl, wenn eine lokale DataFrame-Pipeline über die eager Ausführung in einem einzelnen Prozess hinausgewachsen ist. Seine Lazy API erstellt vor der Ausführung einen Query Plan und ermöglicht dadurch Optimierungen wie Predicate Pushdown und Projection Pruning. Die Engine kann Operatoren anschließend parallel und, sofern unterstützt, in Streaming-Batches ausführen.

Mit zunehmender Datenmenge wird der Abstand größer. Beim Scale Factor 100 (~100 GB) benötigte Polars’ Streaming Engine 23,94 Sekunden, verglichen mit 152,27 Sekunden für die eigene In-Memory Engine — also etwa 6-mal schneller, und das bei Daten, die größer als der Arbeitsspeicher sind.

Das Folgende ist eine beispielhafte API-Skizze und kein wörtlicher Auszug aus der aktuellen Version von engine_comparison_examples.ipynb oder tabular.py:

import polars as pl

# scan_parquet reads only the schema — no data loaded yet
q = (
    pl.scan_parquet("yellow_tripdata_2024-01.parquet")
    .filter(
        (pl.col("trip_distance") > 5.0)
        & (pl.col("total_amount") > 30.0)
    )
    .group_by("payment_type")
    .agg(
        pl.col("total_amount").mean().alias("avg_fare"),
        pl.col("trip_distance").mean().alias("avg_distance"),
        pl.len().alias("trip_count"),
    )
)

# The entire plan is optimized and executed here, in parallel
result = q.collect()

Der wesentliche Unterschied liegt im Execution Model. In der Lazy Query oben kann Polars den Filter und die Spaltenauswahl in den Parquet-Scan verschieben. Dadurch lassen sich möglicherweise Row Groups überspringen und nicht benötigte Spalten müssen nicht gelesen werden. Eine typische eager Pandas-Pipeline verfügt über keinen Query Plan für die gesamte Abfrage, den sie optimieren könnte. Durch den sorgfältigen Einsatz von Parquet-Filtern, ausgewählten Spalten und alternativen Backends lässt sich ein Teil des Abstands jedoch aufholen.

DataFusion für eingebettete Query Engines

Während Polars eine Library ist, die man direkt verwendet, ist DataFusion die Engine, auf der man andere Engines aufbaut. Sie treibt InfluxDB 3.0, GreptimeDB und Apples Comet Spark Accelerator an.

In einem im November 2024 vom DataFusion-Projekt veröffentlichten ClickBench-Lauf lag DataFusion bei den getesteten Single-Node-Parquet-Konfigurationen vorn. Das Embucket-Team veröffentlichte später eine Vendor Case Study für den TPC-H Scale Factor 1000 mit datafusion-cli auf r6gd.metal sowie 64 vCPUs, 512 GB RAM, lokalem NVMe und Timings aus einem warmen Cache. Q18 und Q21 schlugen im ursprünglichen Lauf fehl oder liefen übermäßig lange; für die abgeschlossenen Ergebnisse wurden sie anschließend strukturell umgeschrieben. Dies zeigt Scale-up auf einem einzelnen Node unter diesem Setup, nicht ein allgemeingültiges TPC-H-Ergebnis.

Das Folgende ist eine beispielhafte API-Skizze und kein wörtlicher Auszug aus der aktuellen Version von engine_comparison_examples.ipynb oder tabular.py:

from datafusion import SessionContext

ctx = SessionContext()
ctx.register_parquet("taxi", "yellow_tripdata_2024-01.parquet")

# SQL executed directly against Parquet — no intermediate copies
df = ctx.sql("""
    SELECT payment_type,
           COUNT(*)           AS trip_count,
           AVG(trip_distance) AS avg_distance,
           AVG(total_amount)  AS avg_fare
    FROM taxi
    WHERE trip_distance > 5.0 AND total_amount > 30.0
    GROUP BY payment_type
    ORDER BY trip_count DESC
""")
result = df.to_pandas()

Die Stärke von DataFusion ist seine Modularität. Die Extension APIs decken Custom Catalogs, Table Providers, Optimizer Rules und Execution Plans ab. Deshalb taucht DataFusion immer dann auf, wenn jemand eine Custom Data Platform entwickelt oder eine Query Engine in das eigene Produkt einbettet.

Daft für multimodale Daten

Daft integriert Bilder, Audio, Video und Embeddings in den DataFrame-Workflow. Es stellt native Expressions für Vorgänge wie das Decoding von Bildern und URL-Downloads bereit, sodass gängige Preprocessing-Pfade keine Python-Schleife auf Zeilenebene benötigen. Diese Integration ist der wichtigste Grund, Daft einer allgemeinen tabellarischen Engine vorzuziehen.

Das Folgende ist eine beispielhafte API-Skizze und kein wörtlicher Auszug aus der aktuellen Version von engine_comparison_examples.ipynb oder multimodal.py:

import daft

df = daft.read_parquet("yellow_tripdata_2024-01.parquet")

result = (
    df.where(
        (daft.col("trip_distance") > 5.0)
        & (daft.col("total_amount") > 30.0)
    )
    .groupby("payment_type")
    .agg(
        daft.col("total_amount").mean().alias("avg_fare"),
        daft.col("trip_distance").mean().alias("avg_distance"),
        daft.col("trip_distance").count().alias("trip_count"),
    )
    .collect()
)

Die API wird Ihnen vertraut vorkommen, wenn Sie Pandas kennen. Die Engine basiert jedoch auf demselben Rust- und Arrow-Stack wie Polars und DataFusion. Daft spielt seine Stärken aus, wenn die „Zeilen“ in Ihrem DataFrame aus Bildern, PDFs oder Tensors bestehen.

Spark und Ray kommen in den verteilten Beispielen zum Einsatz, nicht in diesem Single-Node-Benchmark. Die vollständigen Ergebnisse finden Sie im Demo-Repository:

Das Diagramm dient als Kontext für den begleitenden Benchmark, ist jedoch kein fairer Engine-Vergleich nach dem Prinzip „Äpfel mit Äpfeln“: Pandas lädt die Trip- und Zonendaten vor seiner gemessenen Funktion, während Polars, DataFusion, Daft und Rust innerhalb des gemessenen Abschnitts unterschiedliche Anteile des Dateilesens, der Registrierung oder des Query-Setups ausführen. Der Zustand des Filesystem-Caches, Warm-up, CPU und weitere Laufbedingungen können die Werte verändern. Richten Sie die Messgrenze aneinander aus und führen Sie den Benchmark unter kontrollierten Bedingungen erneut aus, bevor Sie die Reihenfolge als Performance-Ergebnis interpretieren.

Bei dieser Größe (etwa 660 MB Parquet) schließen die drei neueren Python-Engines schnell ab. Der oben gezeigte Wert von 94× zugunsten von Polars gegenüber Pandas stammt aus PDS-H; mein Taxi-Workload mit 41 Millionen Zeilen ergab einen kleineren Abstand. In diesem Lauf mit unterschiedlichen Messgrenzen lagen Polars, DataFusion, Daft und Polars-rs im selben groben Bereich, wobei DataFusion die niedrigste gemeldete Zeit erreichte. Diese Reihenfolge gilt für diese Query und Messgrenze, nicht allgemein für die Engines. Wenn Engines so dicht beieinanderliegen, sollten API-Fit und wiederholte Messungen mit repräsentativen Daten die Entscheidung bestimmen.

Teil 2: multimodale Daten

Tabellarische ETL verkleinert Daten normalerweise: filtern, aggregieren und weniger schreiben, als gelesen wird. Multimodale AI-Pipelines machen das Gegenteil. Aus einem einzelnen Dokumentpfad können Dutzende Text-Chunks und Embedding-Vektoren entstehen.

In einer konventionellen PySpark-Pipeline gelangen Bilder und Audio häufig als Binärdaten in die Pipeline und werden zur Decodierung oder Transformation an Python-Bibliotheken weitergegeben. Das Überschreiten der JVM/Python-Grenze und das Serialisieren der Ergebnisse können einen großen Teil der Wall-Clock-Zeit ausmachen. Spark unterstützt Arrow-basierte Pfade, vektorisierte UDFs und Accelerator-Integrationen. Diese Optionen erfordern jedoch ein explizites Design und entsprechende Messungen.

Pipelined Execution und GPU-Auslastung

Spark plant die Verarbeitung in Stages, die durch Shuffle-Grenzen voneinander getrennt sind. Eine direkte Implementierung kann Download, Decodierung und Inference in eine Sequenz bringen, in der entweder CPU- oder GPU-Kapazität wartet. Spark unterstützt GPU-Ressourcenplanung und Plugins, daher ist Leerlauf nicht unvermeidlich. Overlap und Backpressure sind jedoch keine automatischen Eigenschaften eines gewöhnlichen PySpark-DataFrame-Jobs.

Pipelined Execution ist die Alternative. Statt Stages nacheinander auszuführen, überlappt die Engine I/O, CPU-Arbeit und GPU-Inference. Wenn Stages und Buffer ausgewogen sind, kann dieser Overlap die Leerlaufzeit reduzieren und den Throughput steigern. Startup und Drain, Backpressure oder eine langsamere Stage können jedoch weiterhin dazu führen, dass Ressourcen warten.

Teil 3: verteilte Verarbeitung

Sobald eine einzelne Maschine nicht mehr ausreicht, müssen Sie entscheiden, wie Sie die Arbeit verteilen.

Apache Spark

Spark ist eine ausgereifte Option für umfangreiche tabellarische ETL-Prozesse, Joins mit hohem Shuffle-Anteil und Organisationen, die das zugehörige Ökosystem bereits betreiben. Die auf Lineage basierende Wiederherstellung und die breite Plattformunterstützung sind wichtig, wenn Zuverlässigkeit und operative Vertrautheit wichtiger sind als lokale Geschwindigkeit. Gemischte CPU/GPU-Pipelines erfordern eine sorgfältigere Ressourcen-Konfiguration und Pipeline-Gestaltung als der SQL-Pfad. Genau hier bieten Ray Data und Daft eine fokussiertere Abstraktion.

Das Folgende ist ein beispielhafter Spark-API-Entwurf und kein wörtlicher Auszug aus der aktuellen Version von distributed_spark.ipynb oder spark_etl.py:

from pyspark.sql import SparkSession
from pyspark.sql import functions as F

spark = SparkSession.builder \
    .appName("TaxiETL") \
    .config("spark.sql.adaptive.enabled", "true") \
    .getOrCreate()

orders = spark.read.parquet("s3a://lake/taxi/*.parquet")
zones = spark.read.csv("s3a://lake/taxi_zones.csv", header=True)

# Spark excels at this: joining massive tables with a shuffle
result = (
    orders
    .filter(F.col("trip_distance") > 5.0)
    .join(zones, orders.PULocationID == zones.LocationID, "inner")
    .groupBy("Borough")
    .agg(
        F.sum("total_amount").alias("total_revenue"),
        F.avg("total_amount").alias("avg_fare"),
    )
    .orderBy(F.desc("total_revenue"))
)

Ray Data für heterogene Compute-Workloads

Ray Data wurde für AI-Workloads entwickelt. Anstelle von Sparks Stage-Barrieren verwendet es ein Streaming-Modell, das die GPUs kontinuierlich auslastet. Das wichtigste Feature für AI-Pipelines ist das Scheduling gemischter Ressourcen: Sie können deklarieren, dass ein Actor „1 GPU, 4 CPUs“ benötigt und ein anderer nur CPUs, während Ray den Rest übernimmt.

Amazon berichtete von mehr als $120 Millionen jährlichen Einsparungen, nachdem ausgewählte interne Datenverarbeitungs-Workloads von Spark zu Ray migriert worden waren. Dem Bericht zufolge lag die Kosteneffizienz im Proof of Concept um 91 % und in Production pro GiB S3-Input um 82 % höher. Die Größenordnung ist bemerkenswert, doch es handelt sich um eine Migrations-Fallstudie für bestimmte Workloads und nicht um eine zu erwartende Einsparung bei einer typischen Ray-Einführung.

Das Folgende ist ein beispielhafter Ray-Data-API-Entwurf und kein wörtlicher Auszug aus der aktuellen Version von distributed_ray.ipynb oder ray_inference.py:

import ray

ray.init()

ds = ray.data.read_images("s3://my-bucket/food101/")

class ImageClassifier:
    def __init__(self):
        import torch
        from torchvision.models import resnet18, ResNet18_Weights
        self.model = resnet18(weights=ResNet18_Weights.DEFAULT).cuda()
        self.model.eval()
        self.preprocess = ResNet18_Weights.DEFAULT.transforms()

    def __call__(self, batch):
        import torch
        tensors = torch.stack([
            self.preprocess(img) for img in batch["image"]
        ]).cuda()
        with torch.no_grad():
            preds = self.model(tensors)
        return {
            "prediction": preds.argmax(dim=1).cpu().numpy(),
            "confidence": preds.max(dim=1).values.cpu().numpy(),
        }

# ActorPoolStrategy creates persistent GPU workers
predictions = ds.map_batches(
    ImageClassifier,
    compute=ray.data.ActorPoolStrategy(size=4),
    num_gpus=1,
    batch_size=64,
)
predictions.write_parquet("s3://output/predictions/")

Das Verhältnis von CPUs zu GPUs verdient hier besondere Aufmerksamkeit. In Anyscales Benchmarks skalierte Ray Data weiter, als die Anzahl der CPUs pro GPU stieg, während die anderen getesteten Engines ein Plateau erreichten. Die Quelle berichtet bei der Bild-Inference von bis zu 3-fachem Speedup, wenn die CPU-Auslastung nicht mehr der begrenzende Faktor ist, weil die CPU-Feeder mit der GPU Schritt halten können.

Verteiltes Daft

Daft skaliert über seine Flotilla Engine: ein Swordfish Worker pro Node, während Flotilla darüber das clusterweite Scheduling übernimmt. Swordfish führt lokalen Rust-Code aus und pipelined I/O und Compute über Streaming in kleinen Batches, sodass jeder Node ausgelastet bleibt, ohne auf die nächste Stufe zu warten.

In den von Daft veröffentlichten Benchmarks lief Flotilla bei vier multimodalen Workloads 4–18-mal schneller als die getesteten Spark-Implementierungen. Der größte Abstand zeigte sich bei einem Anwendungsfall zur Video-Objekterkennung. Betrachte dieses Ergebnis als Beleg dafür, dass das Execution Design für solche Pipelines relevant ist, und vergleiche es anschließend mit den untenstehenden Ergebnissen von Anyscale sowie mit einem lokalen Test.

Anyscale, das Unternehmen hinter Ray, veröffentlichte einen konkurrierenden Benchmark, in dem Ray Data den Abstand auf Instanzen mit vielen CPUs nach entsprechender Optimierung schloss oder umkehrte. Zusammengenommen sind die beiden Vendor-Studien ein Grund, repräsentative Operatoren und CPU-zu-GPU-Verhältnisse zu testen, statt daraus eine dauerhaft gültige Rangliste abzuleiten.

Das Folgende ist ein illustrativer Daft-API-Entwurf und kein wörtlicher Auszug aus der aktuellen distributed_daft.ipynb oder daft_pipeline.py:

import daft
import numpy as np
from daft import col

# Daft's Flotilla engine distributes work across the cluster
df = daft.read_parquet("s3://data-lake/pdf_metadata/*.parquet")

# Download PDFs — Daft parallelizes downloads in Rust
df = df.with_column("pdf_bytes", col("pdf_url").download())

# Define a GPU class UDF for batched embedding generation
@daft.cls
class TextEmbedder:
    def __init__(self):
        from sentence_transformers import SentenceTransformer
        self.model = SentenceTransformer("all-MiniLM-L6-v2", device="cuda")

    @daft.method.batch(
        return_dtype=daft.DataType.fixed_size_list(daft.DataType.float32(), 384)
    )
    def __call__(self, text_col):
        texts = text_col.to_pylist()
        embeddings = self.model.encode(texts, batch_size=32)
        return np.asarray(embeddings, dtype=np.float32)

# Daft schedules CPU downloads and GPU embeddings simultaneously
embedder = TextEmbedder()
df = df.with_column("embedding", embedder(col("text")))
df.write_parquet("s3://output/embeddings/")

Teil 4: die Rolle von Rust und Arrow

Unterhalb des Wettbewerbs ist die Konvergenz die interessantere Entwicklung. Polars, Daft und DataFusion verwenden Rust intensiv, während Ray neben seinen Python-APIs native Komponenten enthält. Alle können Daten über Teile des Apache-Arrow-Ökosystems austauschen.

Die Arrow PyCapsule Interface (__arrow_c_stream__-Protokoll) bietet kompatiblen Libraries eine standardisierte Möglichkeit, Arrow-Streams auszutauschen. Transfers können eine zeilenweise Serialisierung vermeiden und bei kompatiblen Schemas und Memory Layouts Buffer wiederverwenden. Materialisierung, Rechunking, Typkonvertierung oder Device-Transfer können dennoch Daten kopieren. Überprüfe die Übergabe daher mit Profiling, statt von kostenloser Übertragung auszugehen.

Die folgende API-Skizze ist kein eigenständiges Skript: Sie setzt voraus, dass events.parquet bereits existiert. Das zugehörige engine_comparison_examples.ipynb erstellt .data/events.parquet in seinen Setup-Zellen vor dem Arrow-Beispiel.

from datafusion import SessionContext
import polars as pl

# Compute in DataFusion (Rust-native execution)
ctx = SessionContext()
ctx.register_parquet("events", "events.parquet")
df = ctx.sql("""
    SELECT user_id, COUNT(*) as event_count
    FROM events WHERE event_type = 'purchase'
    GROUP BY user_id HAVING COUNT(*) > 5
""")

# Convert through Arrow; compatible buffers may be reused
arrow_table = df.to_arrow_table()
df_polars = pl.from_arrow(arrow_table)

# Continue analysis in Polars
result = df_polars.with_columns(
    pl.col("event_count").rank().alias("rank")
).sort("rank")

Warum verwenden diese neueren Engines Rust für die native Ausführung?

  1. Kein Tracing Garbage Collector im Rust-Code. Ownership gibt nativen Operatoren eine direktere Kontrolle über Allokation und Freigabe. Das kann die GC-bedingte Latency reduzieren, verhindert aber weder Memory Pressure noch Out-of-Memory-Fehler.

  2. Kompakte native Repräsentationen. Rust-Strukturen enthalten keine Java Object Headers. Der praktische Vorteil hängt vom Layout der Engine ab: Columnar-JVM-Systeme vermeiden ebenfalls, jeden Wert als einzelnes Objekt zu repräsentieren.

  3. Strengere Concurrency-Prüfungen. Safe Rust schließt viele Data Races bereits zur Compile-Zeit aus. Engine-Code kann weiterhin unsafe-Blöcke und logische Concurrency-Bugs enthalten, aber die Sprache begrenzt die Failure Surface.

Zusammen mit Arrows columnarem Memory Layout können diese Entscheidungen den Overhead für Allokation und Serialisierung reduzieren. An jeder Boundary verschwindet dieser Overhead jedoch nicht; Python-Objekte, Network Transport, inkompatible Schemas und Device Movement bleiben relevant.

Teil 5: Mehrere Engines einsetzen

Du musst nicht die gesamte Plattform durch eine einzige Engine zwingen. Composition ist sinnvoll, wenn die Übergabe zwischen Engines weniger kostet, als ein einzelnes System für jeden Workload anzupassen.

Eine mögliche Relay-Architektur verwendet Spark für etablierte Lakehouse-Joins, schreibt ein offenes Table- oder File-Format und übergibt das Ergebnis an Ray Data oder Daft für GPU-Inference oder multimodale Transforms. Polars oder DuckDB können lokale Analysen über dieselben Dateien ausführen. Ein kleineres Team benötigt möglicherweise nur eine dieser Engines; füge eine weitere hinzu, wenn ein gemessener Bottleneck die operative Boundary rechtfertigt.

Diese Composition wird durch Interoperabilität ermöglicht. Parquet ist in diesen Beispielen die gemeinsame File-Handoff-Option, während Arrow den In-Memory-Austausch ermöglichen kann. Die Unterstützung für Delta und Iceberg hängt von Engine und Connector ab; überprüfe daher jede Boundary. Eine File-Handoff verursacht außerdem I/O- und Conversion-Kosten und ist nicht automatisch kostenlos.

Diagonales Scaling

Lange Zeit bestand die Wahl darin, vertikal zu skalieren (eine größere Maschine) oder horizontal zu skalieren (mehr Maschinen). Polars Cloud verfolgt einen Ansatz dazwischen, den das Unternehmen diagonales Scaling nennt. Beim Lesen aus dem Cloud Storage wird horizontal skaliert, um die I/O maximal auszunutzen. Sobald Filter und Aggregationen die Datenmenge reduziert haben, wird auf einen einzelnen großen Node konsolidiert. Ein verteilter Shuffle findet nicht statt.

Die übergeordnete Erkenntnis ist, die Kosten pro erfolgreich abgeschlossenem Job zu vergleichen und nicht den Preis pro Stunde einer Instanz. Ein größerer Node kann günstiger sein, wenn die Verkürzung der Laufzeit seinen höheren Stundensatz überwiegt. Das Ergebnis hängt jedoch von I/O, Memory Pressure und dem Umfang der Arbeit ab, die vor einem Shuffle entfällt.

Vergleich reproduzieren

Das begleitende Demo-Repository enthält die für die Vergleiche verwendeten Skripte, Notebooks und die Umgebung. Der folgende kurze Befehl verwendet das standardmäßige vollständige Taxi-Dataset für 2024 aus dem Repository und entspricht damit dem zuvor gezeigten größeren Lauf.

# Install dependencies
uv sync

# Run the tabular benchmark (~41M NYC taxi trips from full-year 2024)
uv run python -m engine_comparison.benchmarks.tabular

# Run the multimodal benchmark (500 real food photos)
uv run python -m engine_comparison.benchmarks.multimodal

# Run native Rust benchmarks (Polars-rs + image crate)
cd rust_benchmark && cargo run --release && cd ..

Zentrale Erkenntnisse

  1. Belege, dass eine einzelne Maschine nicht ausreicht. Ergebnisse des Scale-up zeigen, dass manche großen analytischen Scans auf einem einzelnen Node ausgeführt werden können. Miss Memory, I/O, Spill und Recovery-Anforderungen, bevor du den Overhead eines Clusters akzeptierst.

  2. Execution Models sind wichtiger als vertraute Syntax. Lazy Planning, Pushdown, Streaming und parallele Operatoren erklären einen großen Teil des Abstands zwischen einem eager DataFrame-Skript und einer Analytical Engine.

  3. Miss die gesamte Accelerator Pipeline. Decode, Network I/O, Batching, Serialisierung und Backpressure bestimmen, ob eine GPU ausgelastet bleibt. Ray Data und Daft machen diese Überlappung zu einer zentralen Abstraktion; Spark kann sie mit zusätzlichem Design und Tooling unterstützen.

  4. Erstelle anhand des Workloads eine Shortlist und führe anschließend Benchmarks durch. Nutze die Eignung des Ecosystems, um das Feld einzugrenzen, und wähle anhand eines repräsentativen End-to-End-Jobs. Benchmark-Ergebnisse von Vendors sind Hypothesen, keine Garantien.

  5. Offene Formate halten die Wahl reversibel. Arrow-kompatible Interfaces, Parquet und offene Table Formats können Übergabekosten reduzieren. Prüfe, ob eine bestimmte Konvertierung Buffer wiederverwendet oder kopiert.

Wenn du einen Ausgangspunkt brauchst, probiere Polars für eine lokale tabellarische Pipeline und Daft oder Ray Data für eine gemischte CPU/GPU-Pipeline. Wähle Spark, wenn dessen verteilte Ausführung, Ecosystem oder bestehende operative Basis eine Anforderung erfüllt. Die Dataset-Größe allein ist kein überzeugender Grund.
