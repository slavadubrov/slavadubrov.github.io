Datenverarbeitungs-Engines: Polars, DataFusion, Ray und Spark

Beginnen Sie mit der Form des Workloads, nicht mit einem Benchmark-Sieger. Polars ist ein starker Default für lokale DataFrame-Pipelines; DataFusion eignet sich für Teams, die eine Query Engine einbetten; Ray Data und Daft sind für gemischte CPU/GPU-Pipelines ausgelegt; und Spark bleibt eine ausgereifte Wahl für verteiltes SQL und ETL. Die Speedups in diesem Leitfaden beziehen sich auf konkrete Workloads und übertragen sich nicht automatisch auf Ihre Workloads. Führen Sie die begleitenden Benchmarks mit Ihren Daten und auf Ihrer Hardware erneut aus, bevor Sie sich entscheiden.

Typen von Datenverarbeitungs-Workloads

Engines sind spezialisiert. Die erste Frage lautet daher, welche Art von Workload tatsächlich vorliegt. Die wichtigste Unterscheidung ist strukturiert vs. multimodal.

Strukturierte oder tabellarische Daten umfassen Filtering, Aggregation und Joins. Sie sind meist CPU-bound und passen häufig in den Arbeitsspeicher. Viele solcher Queries können auf einer modernen Maschine laufen. Ob ein Cluster sinnvoll ist, hängt jedoch weiterhin von Memory, I/O, Concurrency, Recovery und der Workload-Struktur ab.

Multimodales AI verarbeitet Bilder, Audio oder Video. Die Inference kann auf einer GPU laufen, während CPU-Decoding, Remote Reads oder Batching die Pipeline begrenzen. Welche Stage den Throughput begrenzt, hängt vom Instance-Typ und den Operators ab. Messen Sie daher die Auslastung über den gesamten Pfad, statt die GPU isoliert zu dimensionieren.

Die neueren Engines zielen auf unterschiedliche Bereiche dieses Spektrums. Native Execution kann Python-Overhead reduzieren, Arrow-kompatible Interfaces können den Datenaustausch verbilligen, und Streaming Execution kann den Memory-Bedarf bei Datasets begrenzen, die größer als der RAM sind. Keiner dieser Vorteile ist für jeden Operator oder jede Conversion automatisch gegeben.

Teil 1: Single-Node-Verarbeitung

Byte sagt

Ein veröffentlichter Speedup kommt zusammen mit einer Query und einer Maschine. Die Schlagzeile lässt sich deutlich leichter in ein Design-Dokument kopieren.

Pandas bevorzugt ein eager Programming Model: Jede Operation wird sofort ausgeführt, wobei die Daten üblicherweise im Memory gehalten werden. Ein lazy Model plant dagegen mehrere Operationen gemeinsam, bevor sie ausgeführt werden. In Pandas erzeugen viele gängige Operationen Intermediate Tables, und die parallele Ausführung wird nicht über einen Query Optimizer koordiniert. Dieser Trade-off hält explorativen Code direkt, kann bei größeren analytischen Scans jedoch teuer werden. In Polars’ PDS-H-Benchmark vom Mai 2025 bei Scale Factor 10 benötigte Pandas etwa 365 Sekunden für die Suite, während Polars’ Streaming Engine 3,89 Sekunden benötigte. Das Ergebnis von ungefähr 94x beschreibt diesen Benchmark und diese Konfiguration; es ist kein allgemeiner Umrechnungsfaktor von Pandas zu Polars.

Polars für lokale tabellarische Pipelines

Polars ist ein praktischer Default, wenn eine lokale DataFrame-Pipeline über eager, Single-Process Execution hinausgewachsen ist. Seine Lazy API erstellt vor der Ausführung einen Query Plan. Dadurch kann es Rows möglichst früh filtern (predicate pushdown) und nur die benötigten Columns lesen (projection pruning). Die Engine kann Operators anschließend parallel ausführen und – sofern unterstützt – in Streaming-Batches arbeiten.

Bei Scale Factor 100 (~100 GB CSV) schloss die Streaming Engine von Polars 1.30.0 in 23,94 Sekunden ab, verglichen mit 152,27 Sekunden für die In-Memory Engine: etwa 6,4x schneller. Beide Runs liefen auf einer c7a.24xlarge mit 192 GB RAM. Die Quelle führt diese Lücke hauptsächlich auf weniger CPU-Cache-Misses und eine bessere Core-Auslastung zurück; dies ist kein Beleg für Input-Daten, die größer als der RAM sind.

Die folgende Query liest Taxifahrten aus Parquet, wählt Fahrten mit mehr als fünf Meilen Länge und einem Gesamtbetrag über $30 aus und berechnet Counts und Averages nach Payment Type. Informationen zum Taxi-Setup finden Sie unter engine_comparison_examples.ipynb oder tabular.py:

import polars as pl

# Build a lazy scan; query execution happens at collect()
q = (
    pl.scan_parquet("yellow_tripdata_2024-01.parquet")
    .filter(
        (pl.col("trip_distance") > 5.0)
        & (pl.col("total_amount") > 30.0)
    )
    .group_by("payment_type")
    .agg(
        pl.col("total_amount").mean().alias("avg_fare"),
        pl.col("trip_distance").mean().alias("avg_distance"),
        pl.len().alias("trip_count"),
    )
)

# The entire plan is optimized and executed here, in parallel
result = q.collect(engine="streaming")

Der entscheidende Unterschied liegt im Execution Model. In der obigen Lazy Query kann Polars den Filter und die Column-Auswahl in den Parquet-Scan pushen. Dadurch können Row Groups übersprungen und nicht benötigte Columns nicht gelesen werden. Streaming ist hier explizit; collect materialisiert weiterhin das finale Ergebnis, und nicht unterstützte Operationen können auf In-Memory Execution zurückfallen. Eine typische eager Pandas-Pipeline besitzt keinen Whole-Query Plan zur Optimierung. Durch den sorgfältigen Einsatz von Parquet-Filtern, ausgewählten Columns und alternativen Backends lässt sich jedoch ein Teil der Lücke schließen.

DataFusion für eingebettete Query Engines

Während Polars eine Library ist, die Sie direkt verwenden, ist DataFusion die Engine, auf der Sie andere Engines aufbauen. Sie treibt InfluxDB 3.0, GreptimeDB und Apples Comet-Spark-Accelerator an.

In einem vom DataFusion-Projekt veröffentlichten ClickBench-Run vom November 2024 lag DataFusion bei den getesteten Single-Node-Parquet-Konfigurationen vorn. Das Embucket-Team veröffentlichte später eine Vendor Case Study für TPC-H Scale Factor 1000 mit datafusion-cli auf r6gd.metal, mit 64 vCPUs, 512 GB RAM, lokalem NVMe und Timings aus einem Hot Cache. Q18 und Q21 schlugen im ursprünglichen Run fehl oder liefen extrem lange und wurden anschließend strukturell für die abgeschlossenen Ergebnisse umgeschrieben. Dies zeigt Scale-up auf einem Node unter dieser Konfiguration, nicht ein allgemeines TPC-H-Ergebnis.

Hier ist dieselbe Taxi-Zusammenfassung in DataFusion SQL, wobei die Payment Types nach Trip Count sortiert werden. Die SQL-Variante finden Sie unter engine_comparison_examples.ipynb oder tabular.py:

from datafusion import SessionContext

ctx = SessionContext()
ctx.register_parquet("taxi", "yellow_tripdata_2024-01.parquet")

# Plan SQL against the registered Parquet source
df = ctx.sql("""
    SELECT payment_type,
           COUNT(*)           AS trip_count,
           AVG(trip_distance) AS avg_distance,
           AVG(total_amount)  AS avg_fare
    FROM taxi
    WHERE trip_distance > 5.0 AND total_amount > 30.0
    GROUP BY payment_type
    ORDER BY trip_count DESC
""")
result = df.to_pandas()

Die Stärke von DataFusion ist seine Modularität. Die Extension APIs decken Custom Catalogs, Table Providers, Optimizer Rules und Execution Plans ab. Deshalb taucht DataFusion überall dort auf, wo jemand eine eigene Data Platform entwickelt oder eine Query Engine in ein eigenes Produkt einbettet.

Daft für multimodale Daten

Daft macht Bilder, Audio, Video und Embeddings zu Bestandteilen des DataFrame-Workflows. Es bietet native Expressions für Operationen wie Image Decoding und URL Downloads, sodass gängige Preprocessing-Pfade keine Row-by-Row-Python-Schleife benötigen. Diese Integration ist der wichtigste Grund, Daft gegenüber einer allgemeinen tabellarischen Engine in Betracht zu ziehen.

Bevor wir zu Bildern kommen, zeigt dieses Beispiel dieselbe Taxi-Zusammenfassung über Dafts vertraute tabellarische API. Der begleitende API-Vergleich steht unter engine_comparison_examples.ipynb oder multimodal.py:

import daft

df = daft.read_parquet("yellow_tripdata_2024-01.parquet")

result = (
    df.where(
        (daft.col("trip_distance") > 5.0)
        & (daft.col("total_amount") > 30.0)
    )
    .groupby("payment_type")
    .agg(
        daft.col("total_amount").mean().alias("avg_fare"),
        daft.col("trip_distance").mean().alias("avg_distance"),
        daft.col("trip_distance").count().alias("trip_count"),
    )
    .collect()
)

Die API wird vertraut wirken, wenn Sie Pandas kennen. Die Engine ist jedoch derselbe Rust- und Arrow-Stack wie bei Polars und DataFusion. Daft spielt seine Stärken aus, wenn die „Rows“ in Ihrem DataFrame Bilder, PDFs oder Tensors sind.

Teil 2: multimodale Daten

Tabulares ETL verkleinert Daten typischerweise: filtern, aggregieren und weniger schreiben, als gelesen wurde. Multimodale AI-Pipelines machen das Gegenteil. Aus einem einzelnen Dokumentpfad können Dutzende Text-Chunks und Embedding-Vektoren entstehen.

In einer konventionellen PySpark-Pipeline gelangen Bilder und Audio häufig als Binärdaten hinein und werden für Decoding oder Transformation in Python-Libraries überführt. Das Überschreiten der JVM/Python-Grenze und das Serialisieren von Ergebnissen kann einen großen Teil der Wall-Clock-Zeit ausmachen. Spark kann Arrow-basierte Pfade, vektorisierte UDFs und Accelerator-Integrationen verwenden, doch diese Optionen erfordern explizites Design und Messungen.

Pipelined Execution und GPU-Auslastung

Spark plant Arbeit in Stages, die durch Shuffle-Grenzen getrennt sind. Eine geradlinige Implementierung kann Downloads, Decoding und Inference so anordnen, dass entweder CPU- oder GPU-Kapazität wartet. Spark unterstützt GPU-Resource-Scheduling und Plugins, Idle Time ist daher nicht unvermeidbar. Um Stages ausgelastet zu halten, ist außerdem Backpressure erforderlich: Frühere Stages müssen verlangsamt werden, wenn spätere Stages nicht Schritt halten. Weder diese Steuerung noch die Überlappung von CPU- und GPU-Arbeit geschieht automatisch in einem gewöhnlichen PySpark-DataFrame-Job.

Pipelined Execution ist die Alternative. Statt Stages nacheinander auszuführen, überlappt die Engine I/O, CPU-Arbeit und GPU-Inference. Wenn Stages und Buffers ausbalanciert sind, kann diese Überlappung Idle Time reduzieren und den Throughput verbessern. Startup und Drain, Backpressure oder eine langsamere Stage können jedoch weiterhin dazu führen, dass Ressourcen warten.

Benchmark für Image Processing

Ich habe Image Processing mit 500 echten Fotografien aus dem Food-101-Dataset gebenchmarkt. Ergebnisse aus dem Demo-Repository:

Polars und DataFusion fehlen, weil dieser Test auf Image-Operationen abzielt. Die aufgezeichneten Python-Ergebnisse und Rust-Ergebnisse zeigen ungefähr 1,01 Sekunden für Pandas + Pillow, 0,28 für Daft und 0,24 für Rust. Diese Timings messen unterschiedliche Arbeit.

Der Pandas-Pfad decodiert und resized mit Lanczos, konvertiert anschließend die Pixel zu float32 und normalisiert sie. Daft lädt herunter, decodiert und resized; Rust lädt und resized und verwirft Image-Open-Fehler stillschweigend. Keiner führt den Pandas-Normalisierungsschritt aus. Der Run prüfte nicht, ob jede Engine dieselben Bilder verarbeitete und äquivalente Ergebnisse erzeugte. Die Zeitverhältnisse isolieren daher weder Engine- noch Language-Overhead. Verwenden Sie vor dem Vergleich von Throughput dieselben Bilder und gleichen Sie Operationen, Resize-Verhalten, Outputs und Error Accounting an. 500 Bilder allein wären weiterhin zu wenig, um die Production Performance vorherzusagen.

Teil 3: verteilte Verarbeitung

Sobald eine einzelne Maschine nicht mehr ausreicht, müssen Sie entscheiden, wie Sie die Arbeit verteilen.

Apache Spark

Spark ist eine ausgereifte Option für großes tabulares ETL, Shuffle-intensive Joins und Organisationen, die bereits sein Ecosystem betreiben. Die lineage-basierte Recovery und die breite Plattformunterstützung sind wichtig, wenn Reliability und operative Vertrautheit mehr zählen als lokale Geschwindigkeit. Gemischte CPU/GPU-Pipelines erfordern ein bewussteres Resource-Configuration- und Pipeline-Design als der SQL-Pfad. Hier bieten Ray Data und Daft eine fokussiertere Abstraction.

Diese Spark-Query verbindet längere Taxifahrten mit Informationen zur Abholzone und fasst anschließend den Gesamtumsatz und die durchschnittlichen Fahrpreise nach Borough zusammen. Informationen zum Cluster-ETL-Setup finden Sie unter distributed_spark.ipynb oder spark_etl.py:

from pyspark.sql import SparkSession
from pyspark.sql import functions as F

spark = SparkSession.builder \
    .appName("TaxiETL") \
    .config("spark.sql.adaptive.enabled", "true") \
    .getOrCreate()

orders = spark.read.parquet("s3a://lake/taxi/*.parquet")
zones = spark.read.csv("s3a://lake/taxi_zones.csv", header=True)

# Spark excels at this: joining massive tables with a shuffle
result = (
    orders
    .filter(F.col("trip_distance") > 5.0)
    .join(zones, orders.PULocationID == zones.LocationID, "inner")
    .groupBy("Borough")
    .agg(
        F.sum("total_amount").alias("total_revenue"),
        F.avg("total_amount").alias("avg_fare"),
    )
    .orderBy(F.desc("total_revenue"))
)

Ray Data für heterogene Compute-Workloads

Ray Data wurde für AI-Workloads entwickelt. Anstelle der Stage Barriers von Spark verwendet es ein Streaming Model, das GPUs versorgt. Ein Ray-Actor ist ein persistenter Worker, der ein Model zwischen Batches geladen halten kann. Das wichtigste Feature für AI-Pipelines ist Mixed Resource Scheduling: Sie können deklarieren, dass ein Actor „1 GPU, 4 CPUs“ benötigt und ein anderer nur CPUs, worauf Ray den Rest übernimmt.

Amazon berichtete über Compute-Einsparungen, nachdem ausgewählte interne Data-Processing-Workloads von Spark zu Ray migriert worden waren. Zu EC2-On-Demand-R5-Raten entsprachen diese Einsparungen mehr als $120 Millionen jährlich. Der Bericht nennt im Proof of Concept eine um 91 % bessere Cost Efficiency und in Production 82 % pro GiB S3-Input. Die Größenordnung ist bemerkenswert. Es handelt sich jedoch um eine Migrations-Case-Study für konkrete Workloads und nicht um eine erwartbare Einsparung bei einer typischen Ray-Einführung.

Das folgende Beispiel liest Bilder, klassifiziert sie mit ResNet18 auf GPU-Workern und schreibt die Predictions nach Parquet. Informationen zum Image-Inference-Setup finden Sie unter distributed_ray.ipynb oder ray_inference.py:

import ray

ray.init()

ds = ray.data.read_images("s3://my-bucket/food101/", mode="RGB")

class ImageClassifier:
    def __init__(self):
        import torch
        from torchvision.models import resnet18, ResNet18_Weights
        self.model = resnet18(weights=ResNet18_Weights.DEFAULT).cuda()
        self.model.eval()
        self.preprocess = ResNet18_Weights.DEFAULT.transforms()

    def __call__(self, batch):
        import torch
        from PIL import Image
        tensors = torch.stack([
            self.preprocess(Image.fromarray(img)) for img in batch["image"]
        ]).cuda()
        with torch.no_grad():
            preds = self.model(tensors)
        return {
            "prediction": preds.argmax(dim=1).cpu().numpy(),
            "max_logit": preds.max(dim=1).values.cpu().numpy(),
        }

# ActorPoolStrategy creates persistent GPU workers
predictions = ds.map_batches(
    ImageClassifier,
    compute=ray.data.ActorPoolStrategy(size=4),
    num_gpus=1,
    batch_size=64,
)
predictions.write_parquet("s3://output/predictions/")

Diese Skizze reserviert vier One-GPU-Actors und setzt vier verfügbare CUDA-GPUs, Torchvision Weights und S3-Zugriff voraus. Ray liest Bilder als NumPy-Arrays; die Konvertierung von RGB-Arrays zu PIL liefert der ResNet18-Preprocessing-Transform einen akzeptierten Input. max_logit ist der größte rohe Model Score, keine Confidence Probability.

Das CPU/GPU-Verhältnis verdient hier besondere Aufmerksamkeit. In Anyscales Benchmarks skalierte Ray Data weiter, als die Zahl der CPUs pro GPU erhöht wurde, während die anderen getesteten Engines ein Plateau erreichten. Die Quelle berichtet bis zu 3x Speedup bei Image Inference, wenn CPU Starvation abnimmt, weil die CPU Feeder mit der GPU Schritt halten können.

Verteiltes Daft

Daft skaliert über seine Flotilla Engine: ein Swordfish-Worker pro Node, mit Flotilla als darüberliegender clusterweiter Scheduling-Schicht. Swordfish übernimmt die lokale Rust Execution und pipelined I/O mit Compute über Streaming in Small Batches, sodass jeder Node ausgelastet bleibt, ohne auf die nächste Stage zu warten.

In von Daft veröffentlichten Benchmarks war Flotilla bei vier multimodalen Workloads 4–18x schneller als die getesteten Spark-Implementierungen. Die größte Lücke trat bei einem Video-Object-Detection-Fall auf. Betrachten Sie dieses Ergebnis als Beleg dafür, dass das Execution Design bei solchen Pipelines wichtig ist. Vergleichen Sie es anschließend mit den konkurrierenden Anyscale-Ergebnissen unten und mit einem lokalen Test.

Anyscale, das Unternehmen hinter Ray, veröffentlichte einen konkurrierenden Benchmark, in dem Ray Data die Lücke auf CPU-intensiven Instanzen nach Tuning schloss oder umkehrte. Zusammen sind die beiden Vendor-Studien ein Grund, repräsentative Operators und CPU/GPU-Verhältnisse zu testen, statt eine dauerhafte Rangliste abzuleiten.

Das nächste Beispiel verwendet Dafts Ray Runner; es reproduziert nicht den obigen Flotilla-Benchmark. Es liest bereits aus Dokumenten extrahierten Text, erzeugt Embeddings auf GPU-Workern und schreibt sie nach Parquet. Informationen zum verteilten Embedding-Setup finden Sie unter distributed_daft.ipynb oder daft_pipeline.py:

import daft
import numpy as np
from daft import col

# Connect to an existing Ray cluster before building the query
daft.set_runner_ray(address="auto")

# PDF extraction happened upstream: each row has non-null string text
df = daft.read_parquet("s3://data-lake/extracted_text/*.parquet")

# Define a GPU class UDF for batched embedding generation
@daft.cls(gpus=1)
class TextEmbedder:
    def __init__(self):
        from sentence_transformers import SentenceTransformer
        self.model = SentenceTransformer("all-MiniLM-L6-v2", device="cuda")

    @daft.method.batch(
        return_dtype=daft.DataType.fixed_size_list(daft.DataType.float32(), 384)
    )
    def __call__(self, text_col):
        texts = text_col.to_pylist()
        embeddings = self.model.encode(texts, batch_size=32)
        return np.asarray(embeddings, dtype=np.float32)

# CPU file reads feed GPU embedding batches
embedder = TextEmbedder()
df = df.with_column("embedding", embedder(col("text")))
df.write_parquet("s3://output/embeddings/")

Dieses Beispiel startet mit vorab extrahiertem Text, nicht mit PDF-Bytes. Dafts Ray Runner verbindet sich mit einem bestehenden Cluster; der Default Native Runner verwendet die lokale Maschine. Installieren Sie Daft mit Ray-Support und stellen Sie GPU-Worker, Sentence Transformers, Model Weights und S3-Credentials auf diesem Cluster bereit. Die Class- und Batch-Method API hält das Model zwischen Batches vor; CPU Reads können GPU Inference überlappen, abhängig von Partitioning und Backpressure.

Teil 4: Die Rolle von Rust und Arrow

Byte sagt

Arrow bietet diesen Engines eine gemeinsame Beschreibung für Buffers. Ob ein Handoff diese Buffers wiederverwendet, muss weiterhin gemessen werden.

Unter der Oberfläche des Wettbewerbs ist die Konvergenz die interessantere Geschichte. Polars, Daft und DataFusion verwenden Rust intensiv, während Ray neben seinen Python APIs native Components enthält. Alle können Daten über Teile des Apache-Arrow-Ecosystems austauschen.

Das Arrow PyCapsule Interface-Protokoll (__arrow_c_stream__) bietet kompatiblen Libraries eine standardisierte Möglichkeit, Arrow-Streams auszutauschen. Transfers können Row-by-Row-Serialisierung vermeiden und Buffers wiederverwenden, wenn Schemas und Memory Layouts kompatibel sind. Materialization, Rechunking, Type Conversion oder Device Transfer können weiterhin Daten kopieren. Verifizieren Sie den Handoff daher mit Profiling, statt anzunehmen, dass er kostenlos ist.

Das nächste Beispiel demonstriert einen Arrow-Handoff: DataFusion zählt die Purchases von Users mit mehr als fünf Purchases, und Polars rankt diese Counts. Es setzt voraus, dass events.parquet bereits existiert. Das begleitende engine_comparison_examples.ipynb erstellt .data/events.parquet in seinen Setup Cells vor dem Arrow-Beispiel.

from datafusion import SessionContext
import polars as pl

# Compute in DataFusion (Rust-native execution)
ctx = SessionContext()
ctx.register_parquet("events", "events.parquet")
df = ctx.sql("""
    SELECT user_id, COUNT(*) as event_count
    FROM events WHERE event_type = 'purchase'
    GROUP BY user_id HAVING COUNT(*) > 5
""")

# Convert through Arrow; compatible buffers may be reused
arrow_table = df.to_arrow_table()
df_polars = pl.from_arrow(arrow_table)

# Continue analysis in Polars
result = df_polars.with_columns(
    pl.col("event_count").rank().alias("rank")
).sort("rank")

Warum verwenden diese neueren Engines Rust für Native Execution?

  1. Kein Tracing Garbage Collector im Rust-Code. Ownership gibt nativen Operators eine direktere Kontrolle über Allocation und Deallocation. Das kann GC-bedingte Latency reduzieren, verhindert jedoch weder Memory Pressure noch Out-of-Memory-Fehler.

  2. Kompakte native Repräsentationen. Rust-Strukturen enthalten keine Java-Object-Headers. Der praktische Vorteil hängt vom Layout der Engine ab: Auch spaltenbasierte JVM-Systeme vermeiden es, jeden Wert als einzelnes Object zu repräsentieren.

  3. Stärkere Concurrency Checks. Die Regeln von Safe Rust schließen viele Data Races zur Compile-Zeit aus. Engine-Code kann weiterhin Unsafe Blocks und logische Concurrency Bugs enthalten, aber die Sprache begrenzt die Failure Surface.

Zusammen mit Arrows columnarem Memory Layout können diese Entscheidungen Allocation- und Serialisierungs-Overhead reduzieren. Sie beseitigen ihn jedoch nicht an jeder Grenze; Python-Objekte, Network Transport, inkompatible Schemas und Device Movement bleiben relevant.

Teil 5: Mehrere Engines einsetzen

Sie müssen nicht die gesamte Plattform durch eine einzige Engine zwingen. Composition ist sinnvoll, wenn der Handoff zwischen Engines weniger kostet, als ein einzelnes System für jeden Workload zu verwenden.

Ein möglicher Relay verwendet Spark für etablierte Lakehouse-Joins, schreibt ein Open-Table- oder File-Format und übergibt das Ergebnis für GPU-Inference oder multimodale Transformations an Ray Data oder Daft. Polars oder DuckDB können lokale Analysen über dieselben Files ausführen. Ein kleineres Team benötigt möglicherweise nur eine dieser Engines; fügen Sie eine weitere hinzu, wenn ein gemessener Bottleneck die operative Grenze rechtfertigt.

Diese Composition wird durch Interoperability möglich. Parquet ist in diesen Beispielen der gemeinsame File-Handoff, während Arrow den In-Memory-Austausch ermöglichen kann. Die Unterstützung für Delta und Iceberg hängt von Engine und Connector ab; prüfen Sie daher jede Grenze. Ein File-Handoff verursacht außerdem I/O- und Conversion-Kosten und ist nicht automatisch kostenlos.

Diagonales Scaling

Lange Zeit bestand die Wahl zwischen Scale-up (eine größere Maschine) und Scale-out (mehr Maschinen). Polars Cloud beschreibt einen Query-abhängigen Ansatz namens diagonal scaling. Skalieren Sie horizontal, während Sie aus Cloud Storage lesen, um die I/O zu maximieren. Sobald Filter und Aggregationen die Daten verkleinert haben, wechseln Sie zu einem einzelnen großen Node. Frühe Reduktion kann den Datentransfer begrenzen und die verbleibende Arbeit auf einem Node abschließen lassen. Ob ein verteilter Shuffle stattfindet, hängt vom Physical Query Plan ab.

Die übergeordnete Lehre lautet, die Kosten pro erfolgreich abgeschlossenem Job zu vergleichen, nicht den stündlichen Instance-Preis. Ein größerer Node kann günstiger sein, wenn die Runtime-Reduktion seinen höheren Preis überwiegt. Das Ergebnis hängt jedoch von I/O, Memory Pressure und der Menge der Arbeit ab, die vor einem Shuffle entfällt.

Zentrale Erkenntnisse

  1. Belegen Sie, dass eine Maschine nicht ausreicht. Scale-up-Ergebnisse zeigen, dass einige große analytische Scans auf einem einzelnen Node Platz finden. Messen Sie Memory, I/O, Spill und Recovery-Anforderungen, bevor Sie Cluster-Overhead akzeptieren.

  2. Execution Models sind wichtiger als vertraute Syntax. Lazy Planning, Pushdown, Streaming und parallele Operators erklären einen großen Teil der Lücke zwischen einem eager DataFrame-Script und einer analytischen Engine.

  3. Messen Sie die gesamte Accelerator-Pipeline. Decoding, Network I/O, Batching, Serialisierung und Backpressure bestimmen, ob eine GPU ausgelastet bleibt. Ray Data und Daft machen diese Überlappung zu einer zentralen Abstraction; Spark kann sie mit zusätzlichem Design und Tooling unterstützen.

  4. Erstellen Sie anhand des Workloads eine Shortlist und benchmarken Sie anschließend. Verwenden Sie Ecosystem-Fit, um das Feld einzugrenzen, und einen repräsentativen End-to-End-Job für die Auswahl. Vendor-Benchmark-Ergebnisse sind Hypothesen, keine Garantien.

  5. Open Formats halten die Auswahl reversibel. Arrow-kompatible Interfaces, Parquet und Open-Table-Formate können Handoff-Kosten reduzieren. Prüfen Sie, ob eine konkrete Conversion Buffers wiederverwendet oder kopiert.
