Reasoning Loops für AI Agents: ReAct, ReWOO, Plan-and-Execute

Teil 1 der Serie „Engineering the Agentic Stack“

Ein Reasoning Loop für Agents steuert, wie ein System plant, Tools aufruft, Ergebnisse liest und entscheidet, wann es stoppt. Dieser Control Flow prägt Kosten, Latency und die Wiederherstellung, nachdem ein Tool etwas Unerwartetes zurückgegeben hat.

Dieser Beitrag vergleicht die drei AI-Agent-Loop-Patterns, die man 2026 kennen sollte: ReAct, ReWOO und Plan-and-Execute. Das durchgehende Beispiel ist ein Market Analyst Agent, den ich in LangGraph entwickelt habe; der vollständige Code ist auf GitHub verfügbar.

Dies ist die innerste Schicht der Serie. Alles, was die späteren Teile hinzufügen, ist Code, der um diesen Loop herumgelegt wird.

TL;DR: ReAct ist flexibel, aber teuer, ReWOO ist bei vorhersehbaren Workflows schnell, und Plan-and-Execute eignet sich für mehrstufige Analysen. Ein produktiver AI Agent kann je nach Request zwischen Reasoning Loops routen. Dabei nutzt er gemeinsamen State und checkpointed LangGraph-Runs, sodass jede Aufgabe den Loop erhält, der zu ihrer Struktur passt.

Der Reasoning Loop entscheidet, was als Nächstes passiert. Er kann nichts speichern, ausführen oder ablehnen. Diese Aufgaben gehören zwei außerhalb liegenden Schichten.

Der Harness ist das Control-Programm zwischen Model und Maschine. Er setzt den Prompt aus gespeichertem State zusammen (Teil 2) und definiert die Aktionen, die das Model benennen darf (Teil 3). Anschließend entscheidet er, ob jeder vorgeschlagene Call ausgeführt werden darf (Teil 4), und liest die Evidenz, anhand derer entschieden wird, ob die Aufgabe abgeschlossen ist (Teil 6). Diese vier Themen erhalten separate Beiträge, weil es sich um separate Probleme handelt. In einem laufenden System sind sie vier Phasen eines Turns.

Der Runtime (Teil 5) ist das Fundament des Harness: Session-Log, Sandbox, Checkpoint Store und Traces, die länger bestehen als ein einzelner Worker-Prozess.

Jeder Beitrag steht für sich. In der richtigen Reihenfolge führen sie vom innersten Loop nach außen.

Der Loop steuert Kosten, Latency und Recovery

Ein brauchbarer Agent braucht mehr als einen guten Prompt. Die drei folgenden Patterns unterscheiden sich in einem Punkt: Wie viel der Arbeit wird vor dem ersten Tool Call entschieden? Diese Entscheidung bestimmt, wie viele Model Calls eine Aufgabe kostet, wie früh ein fehlerhafter Plan sichtbar wird und ob der Agent den Kurs ändern kann, wenn ein Tool etwas Unerwartetes zurückgibt.

Drei Reasoning-Patterns für AI Agents

ReAct: denken, handeln, beobachten, wiederholen

ReAct (Yao et al., 2022), kurz für Reason + Act, ist das ursprüngliche Pattern für interaktive Agents. Es führt einen Loop aus:

  1. Thought: Der Agent erzeugt einen „Thought“, um das Ziel zu zerlegen und den nächsten Schritt zu planen.
  2. Action: Auf Grundlage des Thoughts ruft er ein Tool auf.
  3. Observation: Der Agent liest das Ergebnis, wodurch sich sein Verständnis für den nächsten Thought aktualisiert.

Vorteile:

  • Grounding anhand realer Observations reduziert erfundene Fakten.
  • Der Agent kann seine Strategie spontan an das gerade Gesehene anpassen.
  • Die Historie der Tool Calls und Observations liefert einen konkreten Execution Trace.

Nachteile:

  • Die Historie wächst und wird bei jedem Schritt erneut verarbeitet, daher steigen Latency und Kosten mit der Länge des Loops.
  • Ineffizient, wenn die Tool Calls im Voraus geplant werden könnten; genau hier setzt ReWOO an.
  • Ohne Stop Condition oder Step Limit kann der Loop unbegrenzt laufen.

Geeignet für: explorative Aufgaben, Debugging und Situationen, in denen nicht vorhersehbar ist, was als Nächstes passiert.

ReWOO: alles im Voraus planen

ReWOO (Reasoning WithOut Observation) ist ein effizienterer Verwandter von ReAct. Der entscheidende Ansatz ist die Entkopplung von Reasoning und Tool Execution: Statt nach jeder Action anzuhalten und zu beobachten, plant ReWOO die gesamte Sequenz von Tool Calls in einem Durchlauf.

  1. Plan: Ein LLM Call schreibt den vollständigen Plan der Tool Calls und verwendet dabei Variable Placeholders (#E1, #E2) für Outputs, die noch nicht existieren.
  2. Worker: Ein Non-LLM-Executor führt die geplanten Tools sequenziell oder parallel aus und füllt die Placeholders.
  3. Solver: Ein abschließender LLM Call nimmt die gesammelten Observations und schreibt die Antwort.

Vorteile:

  • Weniger wiederholte Model Calls als bei ReAct, wenn der ursprüngliche Plan gültig bleibt.
  • Geringere Latency. Die Historie muss nicht bei jedem Schritt erneut übermittelt werden.
  • Der Planner kann unabhängig und ohne Live-Umgebung fine-tuned werden.

Nachteile:

  • Fragil, wenn sich Tools nicht erwartungsgemäß verhalten. Der Plan geht davon aus, dass alles funktioniert.
  • Erfordert vorhersehbare Workflows.
  • Ohne explizite Fallback-Logik wird ein fehlerhafter Plan weiter ausgeführt.

Geeignet für: schnelle Snapshots, Statusprüfungen und Dashboards – überall dort, wo sich Tools vorhersehbar verhalten.

Plan-and-Execute: ein Hybrid

Plan-and-Solve Prompting, sobald Tools beteiligt sind meist Plan-and-Execute genannt, liegt zwischen den beiden anderen Patterns. Das Paper skizziert eine einfache Aufteilung, die viele moderne Agents verwenden:

  1. Planning-Phase: Der Agent erzeugt zunächst einen Plan, der die Aufgabe in kleinere Sub-Tasks zerlegt.
  2. Execution-Phase: Der Agent führt diese Sub-Tasks anschließend einzeln aus. Sobald Tools beteiligt sind, läuft jeder Sub-Task meist als eigener kleiner ReAct Loop. Dadurch kann der Executor weiterhin auf das reagieren, was ein Tool zurückgibt, obwohl der übergeordnete Plan feststeht.

Das ursprüngliche Paper konzentrierte sich auf Zero-Shot Prompting. Frameworks wie LangGraph haben daraus ein Orchestration-Pattern mit sequenzieller Ausführung und Model-Auswahl pro Schritt entwickelt. Du kannst ein starkes Reasoning Model für die Planung und ein günstigeres Model für die Ausführung verwenden.

Vorteile:

  • Hierarchisches Reasoning, das widerspiegelt, wie ein menschlicher Experte ein Projekt zerlegt.
  • Re-Planning ist möglich. Du kannst pausieren und neu bewerten, wenn das Ergebnis eines Schritts unerwartet war.
  • Model-Spezialisierung. Der Planner kann teuer, der Executor günstig sein.
  • Ein klarer Checkpoint nach jedem Schritt, sodass ein Fehler am letzten Checkpoint statt am Anfang fortgesetzt wird.

Nachteile:

  • Höhere Latency als bei ReWOO, weil die Schritte sequenziell ausgeführt werden.
  • Mehr State, der verwaltet werden muss.
  • Overkill für One-Shot-Queries.

Geeignet für: komplexe mehrstufige Analysen, Research-Aufgaben und alles, was am Ende eine Synthese benötigt.

Die Tabelle ist ein Ausgangspunkt, kein Benchmark-Ergebnis. Verwende ReAct, wenn jede Observation die nächste Action ändern kann. Verwende Plan-and-Execute, wenn sich die Gesamtaufgabe zerlegen lässt, einzelne Schritte aber weiterhin Feedback benötigen. Verwende ReWOO, wenn jede Abhängigkeit zwischen Tool Calls vor dem Start der Ausführung bekannt ist. Ein bekannter Dependency Graph ermöglicht Cancel-on-Failure: Du kannst die von einem fehlgeschlagenen Call abhängigen Schritte überspringen, statt ihnen dessen Fehler-String zu übergeben. Diese Prüfung musst du trotzdem selbst implementieren – der folgende Worker enthält sie nicht. Miss alle drei Patterns mit deiner eigenen Tool Latency, deinem Model, deinem Task Set und deiner Retry Policy, bevor du ausschließlich anhand der Kosten auswählst.

Ein durchgängiges Beispiel: der Market Analyst Agent

Um das konkret zu machen, habe ich einen Market Analyst Agent entwickelt, der alle drei Patterns in einer Codebase für eine Market-Research-Aufgabe verwendet.

Für die Orchestration nutzt er LangGraph. Zwei Konzepte decken alles Folgende ab: Ein Node ist eine einfache Python-Funktion, die das gemeinsame State-Objekt entgegennimmt und ein Dict mit den zu aktualisierenden Feldern zurückgibt. Eine Edge legt fest, welcher Node als Nächstes ausgeführt wird – bedingt, wenn du ihr eine Routing-Funktion übergibst. LangGraph führt jedes zurückgegebene Dict mit dem State zusammen und kann nach jedem Node einen Snapshot speichern. Dadurch wird ein Run resumable. Alle drei Patterns teilen sich ein State-Objekt, sodass der Router je nach Request den Pfad wechseln kann, ohne für jedes Pattern ein eigenes Schema zu benötigen:

State-Definition

Der gemeinsame State enthält alles, was der Agent über die verschiedenen Modi hinweg benötigt:

Pattern 1: Plan-and-Execute-Implementierung

Plan-and-Execute eignet sich für Aufgaben, die eine mehrstufige Synthese benötigen. Planning und Execution bleiben getrennt: Ein starkes Model schreibt den Plan, anschließend führt ein ReAct Loop jeden Schritt aus und reagiert auf die Tool Results.

Der folgende Code pinnt claude-sonnet-4-5-20250929. Damit habe ich diese Beispiele ausgeführt, als der Beitrag im Januar 2026 veröffentlicht wurde. Model-Generationen haben sich seitdem weiterentwickelt. Tausche es gegen ein aktuelles Model aus und überprüfe das Routing-Verhalten mit deinen eigenen Aufgaben – entscheidend ist das Pattern, nicht die Model-ID.

So entspricht es dem Pattern:

  1. Eine vorgelagerte Planning-Phase. Ein einzelner LLM Call erzeugt den vollständigen Plan als Liste von Schrittbeschreibungen.
  2. Schema-guided Output, der den Plan vor der Ausführung validiert.
  3. Noch keine Tool Execution. Der Planner entscheidet nur, was zu tun ist, nicht wie.
  4. Für Menschen lesbare Schritte. Jeder Schritt ist Text, den ein Executor interpretiert.
# System prompt guides the LLM to think like a research analyst
# creating a strategic plan, not immediate tool calls
PLANNER_SYSTEM_PROMPT = """You are a senior investment research analyst.
Break down stock analysis requests into 4-6 research steps covering:
1. Current price and basic metrics
2. Recent news and announcements
3. Competitor analysis (if relevant)
4. Financial health assessment
5. Risk factors
6. Investment thesis synthesis

Output as JSON with step_number, description, and tool_hint."""

# Schema-Guided Reasoning: Enforce structure with Pydantic
class PlanOutput(BaseModel):
    """Structured output for the planner."""

    steps: list[PlanStep] = Field(description="Research steps to execute")
    ticker: str = Field(description="The stock ticker being analyzed")

def planner_node(state: AgentState) -> dict:
    """Generate a research plan from the user's request.

    This is Phase 1 of Plan-and-Execute: creating the high-level strategy.
    """

    # Use a powerful model for strategic planning
    llm = ChatAnthropic(model="claude-sonnet-4-5-20250929", temperature=0)

    # Ask for a typed plan and validate it before execution.
    # The API can still fail, so production code also handles that exception.
    structured_llm = llm.with_structured_output(PlanOutput)

    # Pull the request out of the message history
    human = [m for m in state.messages if isinstance(m, HumanMessage)]
    last_user_message = human[-1].content if human else "Analyze the market"

    # Context from long-term memory personalizes the plan
    profile_context = f"""
User Profile:
- Risk Tolerance: {state.user_profile.risk_tolerance}
- Investment Horizon: {state.user_profile.investment_horizon}
"""

    # Single LLM call creates the complete plan
    result: PlanOutput = structured_llm.invoke([
        SystemMessage(content=PLANNER_SYSTEM_PROMPT + profile_context),
        HumanMessage(content=f"Create a research plan for: {last_user_message}"),
    ])

    # State update: Store the plan and initialize tracking
    return {
        "plan": result.steps,           # The sequential steps to execute
        "current_step_index": 0,        # Start at step 0
        "research_data": ResearchData(ticker=result.ticker),  # Initialize data container
    }

Die Zeile llm.with_structured_output(PlanOutput) steht für Schema-Guided Reasoning (SGR), das ich in einem früheren Beitrag behandelt habe. Das Schema erlaubt der Anwendung, einen fehlerhaften Plan zurückzuweisen, bevor LangGraph die validierten Felder zur Steuerung bedingter Edges verwendet.

Pattern 2: ReAct Execution

Sobald der Plan existiert, führt der Executor jeden Schritt als eigenen ReAct Loop aus. Das ist Phase 2: Jeder Schritt ist klein genug, dass ein Thought-Action-Observation-Zyklus fokussiert bleibt, und der Agent kann auf alles reagieren, was das Tool zurückgibt.

So entspricht der ReAct-Teil dem Pattern:

  1. Iterative Execution. Ein Schritt nach dem anderen, mit Observation-Feedback.
  2. Der Thought-Action-Observation-Loop läuft innerhalb von create_react_agent.
  3. Die Ergebnisse vorheriger Schritte werden als Context für das aktuelle Reasoning übergeben.
  4. Der Agent wählt Tools anhand der Schrittbeschreibung aus.
  5. Er kann seine Vorgehensweise innerhalb eines Schritts an das anpassen, was ein Tool zurückgibt.
# The five market-data tools the ReAct agent chooses from here. The repo's
# TOOLS list carries four more — a skill loader, two CLI wrappers, and a
# restricted in-process Python evaluator — covering three of the five tool
# modalities Part 3 compares. MCP is the fourth, and it lives in a sidecar
# rather than in this list.
TOOLS = [
    get_stock_snapshot,
    get_price_history,
    search_news,
    search_competitors,
    get_financials,
]

def executor_node(state: AgentState) -> dict:
    """Execute the current step using a ReAct agent.

    This is Phase 2 of Plan-and-Execute: adaptive execution of each planned step.
    Each step runs as a mini ReAct loop until completion.
    """

    # Get the current step from the plan
    current_step = state.plan[state.current_step_index]

    # Build context from what we've learned so far
    # This matters: each step builds on previous observations
    previous_context = ""
    for step in state.plan[:state.current_step_index]:
        if step.result:
            previous_context += f"\nStep {step.step_number}: {step.result}\n"

    # Create a ReAct agent for this step
    # LangGraph's create_react_agent implements the full Thought-Action-Observation loop:
    # 1. Agent generates a "thought" about what tool to call
    # 2. Agent calls the tool ("action")
    # 3. Tool returns result ("observation")
    # 4. Agent decides: call another tool or finish
    react_agent = create_react_agent(
        model=ChatAnthropic(model="claude-sonnet-4-5-20250929"),
        tools=TOOLS,
    )

    # Invoke the ReAct loop for this single step
    # The agent will loop internally until it completes the step
    result = react_agent.invoke({
        "messages": [
            SystemMessage(content=EXECUTOR_SYSTEM_PROMPT),
            HumanMessage(content=f"""Execute Step {current_step.step_number}:
{current_step.description}

Ticker: {state.research_data.ticker}
Previous findings: {previous_context}"""),
        ]
    })

    # Extract the final answer from the ReAct agent's message history
    # The last message contains the synthesis after all tool calls
    updated_plan = list(state.plan)
    updated_plan[state.current_step_index] = PlanStep(
        step_number=current_step.step_number,
        description=current_step.description,
        completed=True,
        result=result["messages"][-1].content,  # Final observation
    )

    # State update: Mark step complete and advance to next
    return {
        "plan": updated_plan,
        "current_step_index": state.current_step_index + 1,
    }

Pattern 3: ReWOO für schnelle Snapshots

Für kurze Briefings überspringt ReWOO das verschachtelte Reasoning und führt die Tools parallel aus. Der Planner erzeugt im Voraus ein kompiliertes Script aus Tool Calls, und der Worker führt es ohne weitere Beteiligung eines LLM aus.

Die Struktur:

  1. Drei Phasen (Planner → Worker → Solver), keine Loops.
  2. Tool Calls referenzieren #E1 und #E2 als Placeholders für Ergebnisse, die noch nicht existieren.
  3. Kein LLM während der Execution. Der Worker führt einfach die Tools aus.
  4. Unabhängige Tools werden parallel ausgeführt.
  5. Ein abschließender Synthese-Call über alle Daten auf einmal.

Phase 1: ReWOO Planner (erstellt den vollständigen Execution Graph im Voraus)

class ReWOOPlanStep(BaseModel):
    """A step in the ReWOO plan with variable placeholders.

    Key difference from Plan-and-Execute's PlanStep:
    - Contains actual tool_name and tool_args (not just description)
    - Uses variable references (#E1) for dependencies
    """
    step_id: str  # e.g., "#E1" - becomes a variable
    description: str
    tool_name: str     # Exact tool to call
    tool_args: dict    # May contain variable refs like {"price": "#E1"}
    depends_on: list[str] = []  # For dependency ordering
    result: str | None = None

class ReWOOPlanOutput(BaseModel):
    """Structured output for ReWOO planner."""
    steps: list[ReWOOPlanStep] = Field(description="Planned tool calls with variables")

def rewoo_planner_node(state: AgentState) -> dict:
    """Generate a complete plan of tool calls upfront.

    This is the key difference from Plan-and-Execute: instead of creating
    human-readable step descriptions, we create EXACT tool calls that
    the worker will execute blindly.
    """

    llm = ChatAnthropic(model="claude-sonnet-4-5-20250929", temperature=0)

    # Schema-Guided Reasoning ensures valid tool call specifications
    structured_llm = llm.with_structured_output(ReWOOPlanOutput)

    ticker = state.research_data.ticker if state.research_data else "UNKNOWN"
    human = [m for m in state.messages if isinstance(m, HumanMessage)]
    query = human[-1].content if human else f"Analyze {ticker}"

    # Single LLM call to plan ALL tool executions
    result: ReWOOPlanOutput = structured_llm.invoke([
        SystemMessage(content=REWOO_PLANNER_PROMPT),
        HumanMessage(content=f"""Create a ReWOO plan for: {query}

Ticker: {ticker}

Output tool calls with:
- step_id: Variable name (#E1, #E2, etc.)
- description: What this accomplishes
- tool_name: Exact tool from the list
- tool_args: Dictionary of arguments
- depends_on: List of step_ids this depends on"""),
    ])

    # State update: Store the complete execution plan
    # Worker will execute this without any LLM involvement
    return {"rewoo_plan": result.steps}

Phase 2: ReWOO Worker (führt Tools ohne LLM Reasoning aus)

def rewoo_worker_node(state: AgentState) -> dict:
    """Execute all planned tools in parallel (no LLM calls).

    This is the key efficiency: Worker is "dumb" - it just runs tools
    according to the plan. No LLM calls means no tokens spent here.
    """

    results = {}        # Results keyed by step_id (e.g., "#E1": "$150.23")
    updated_steps = []  # Plan steps with their result field filled in

    # Execute the independent steps in parallel using ThreadPoolExecutor.
    # This is where ReWOO gets its speed advantage.
    with ThreadPoolExecutor(max_workers=5) as executor:
        futures = {
            executor.submit(execute_tool, step, results): step
            for step in state.rewoo_plan
            if not step.depends_on  # Only independent tools for parallel batch
        }

        # Collect results as they complete
        for future in as_completed(futures):
            step = futures[future]
            results[step.step_id] = future.result()
            updated_steps.append(step.model_copy(update={"result": results[step.step_id]}))
            # No LLM reasoning here - just store the raw tool output

    # Dependent steps run afterwards, in plan order — which assumes the planner
    # listed each dependency before the step that uses it. execute_tool() swaps any
    # "#E1"-style argument for the matching entry in `results`, which is how
    # a placeholder written before execution turns into a real value.
    for step in state.rewoo_plan:
        if step.depends_on:
            results[step.step_id] = execute_tool(step, results)
            updated_steps.append(step.model_copy(update={"result": results[step.step_id]}))

    # State update: restore the planner's order (sorting on step_id would put
    # "#E10" before "#E2") and hand the filled-in plan to the Solver
    plan_order = {s.step_id: i for i, s in enumerate(state.rewoo_plan)}
    return {"rewoo_plan": sorted(updated_steps, key=lambda s: plan_order[s.step_id])}

Phase 3: ReWOO Solver (synthetisiert alle Ergebnisse in einem LLM Call)

def rewoo_solver_node(state: AgentState) -> dict:
    """Synthesize all tool results into a flash briefing.

    This is the second efficiency gain: Instead of interleaving
    LLM calls with tool execution (like ReAct), we make ONE
    final synthesis call with all gathered data.
    """

    # Build context from ALL tool results at once
    tool_results = []
    for step in state.rewoo_plan:
        if step.result:
            tool_results.append(f"### {step.description}\n{step.result}")

    context = "\n\n".join(tool_results)

    # Single LLM call to synthesize everything
    llm = ChatAnthropic(model="claude-sonnet-4-5-20250929", temperature=0)
    structured_llm = llm.with_structured_output(FlashBriefingOutput)
    result = structured_llm.invoke([
        SystemMessage(content=REWOO_SOLVER_PROMPT),
        HumanMessage(content=f"Create a flash briefing from this data:\n\n{context}"),
    ])

    # FlashBriefingOutput and DraftReport carry the same fields; the state
    # schema expects DraftReport, so convert before returning.
    return {"draft_report": DraftReport(**result.model_dump())}

ReWOO plant jeden Tool Call im Voraus und schreibt das noch unbekannte Ergebnis jedes Schritts als Placeholder wie #E1 oder #E2. Spätere Schritte referenzieren diese Placeholders, um eine Dependency auszudrücken. Der Worker führt unabhängige Calls parallel aus, ohne das Model zu fragen, was als Nächstes zu tun ist. Ein abschließender Model Call führt die Ergebnisse zusammen.

ReWOO1 für Planning + 0 während der Execution + 1 für die SyntheseParalleler Abschluss der Tool Executionrewoo_planner_node() → rewoo_worker_node() → rewoo_solver_node()

Der Unterschied besteht darin, was – wenn überhaupt – der Planner erzeugt. Dieser Output bestimmt, was der restliche Graph tun kann.

  1. Plan-and-Execute erzeugt für Menschen lesbare Schrittbeschreibungen:

    # Planner output (list of PlanStep objects)
plan = [
    PlanStep(
        step_number=1,
        description="Get current price and key financial metrics",
        tool_hint="get_stock_snapshot"
    ),
    PlanStep(
        step_number=2,
        description="Search for recent news and earnings",
        tool_hint="search_news"
    ),
    # ... more steps
]

    Der Executor liest jede Beschreibung und entscheidet, welche Tools aufgerufen werden. Das ist flexibel, aber jeder Schritt ist ein eigener ReAct Loop. Daher kostet ein Schritt mehrere Model Calls und nicht nur einen.

  2. ReAct hat keinen vorgelagerten Plan. Es verwendet iteratives Reasoning:

    # No planning phase - ReAct works step-by-step with accumulated messages
messages = [
    HumanMessage(content="Execute Step 1: Get current price"),
    AIMessage(content="I'll call get_stock_snapshot"),
    ToolMessage(tool_call_id="1", content="$132.45"),
    AIMessage(content="Now I need metrics..."),
    # ... agent continues until step complete
]

    Die Model Calls hinter diesen Messages passen sich an Observations an, und jeder einzelne liest eine Historie erneut, die während der gesamten Aufgabe wächst. Plan-and-Execute verwendet ebenfalls ReAct Loops, aber jeder startet mit der Beschreibung des jeweiligen Schritts plus einer Zusammenfassung früherer Ergebnisse, nicht mit der vollständigen Tool-Call-Historie.

  3. ReWOO erzeugt explizite, ausführbare Tool-Call-Spezifikationen:

    # Planner output (list of ReWOOPlanStep objects)
rewoo_plan = [
    ReWOOPlanStep(
        step_id="#E1",
        tool_name="get_stock_snapshot",
        tool_args={"ticker": "NVDA"}
    ),
    ReWOOPlanStep(
        step_id="#E2",
        tool_name="search_news",
        tool_args={"query": "NVDA earnings", "limit": 5}
    ),
    # ... all tool calls planned upfront
]

    Der Worker arbeitet blind und ohne Beteiligung eines LLM. Alle Model Calls finden im Planner und Solver statt, wodurch die Anzahl der Model Calls vorhersehbar wird.

Memory- und State-Flow:

  • Plan-and-Execute: Der State wandert durch plan → current_step_index → research_data.
  • ReAct: Der State akkumuliert sich im Array messages (der vollständigen Conversation History).
  • ReWOO: Der State wandert durch rewoo_plan; der Worker füllt dabei die Felder result aus.

Alles zusammenführen: den Graphen verdrahten

So koexistieren die drei Patterns in einem einzigen LangGraph-System. Sie teilen sich ein AgentState und befinden sich in einem Graphen. Ein Router wählt den Pfad pro Request aus. Es handelt sich also um einen Agent mit zwei routbaren Modi – Deep Research und Flash Briefing – und nicht um drei Agents im Trenchcoat. ReAct ist keine der Routen; es läuft innerhalb jedes Deep-Research-Schritts.

Eine Sache, die das Diagramm von Plan-and-Execute zeigt, dieser Graph aber nicht: einen Replanner. Plan-and-Execute erlaubt einen solchen Replanner, dieser Agent führt den Plan jedoch vollständig aus und ändert ihn während des Runs nicht. Seine Ergänzung erfordert eine weitere bedingte Edge von executor zurück zu planner sowie eine Regel dafür, wann ein überraschendes Schritt-Ergebnis die Kosten eines weiteren Planning Calls rechtfertigt. Betrachte das Diagramm als Darstellung des Patterns und den Code als eine konkrete Implementierung davon.

LangGraph hält die Verdrahtung deklarativ:

def create_graph(checkpointer=None):
    builder = StateGraph(AgentState)

    # Add nodes
    builder.add_node("router", router_node)
    builder.add_node("planner", planner_node)
    builder.add_node("executor", executor_node)
    builder.add_node("reporter", reporter_node)
    builder.add_node("rewoo_planner", rewoo_planner_node)
    builder.add_node("rewoo_worker", rewoo_worker_node)
    builder.add_node("rewoo_solver", rewoo_solver_node)
    builder.add_node("evaluator", evaluator_node)
    builder.add_node("publish", publish_node)

    # Define edges
    builder.add_edge(START, "router")
    builder.add_conditional_edges("router", route_after_router, {
        "planner": "planner",
        "rewoo_planner": "rewoo_planner",
    })

    # Deep Research path
    builder.add_edge("planner", "executor")
    builder.add_conditional_edges("executor", route_after_executor, {
        "executor": "executor",  # Loop back for more steps
        "reporter": "reporter",  # Done with plan
    })
    builder.add_edge("reporter", "evaluator")

    # Flash Briefing path (ReWOO)
    builder.add_edge("rewoo_planner", "rewoo_worker")
    builder.add_edge("rewoo_worker", "rewoo_solver")
    builder.add_edge("rewoo_solver", "evaluator")

    # Both paths converge on the same acceptance check
    builder.add_edge("evaluator", "publish")
    builder.add_edge("publish", END)

    return builder.compile(
        checkpointer=checkpointer,
        # Human-in-the-loop pause: the reporter (or the ReWOO solver) writes a
        # draft, a fresh-context evaluator — a second model session with no
        # history of the run — votes on it, and the graph stops before publish.
        # The human approves a report that already carries an evaluator's
        # verdict rather than adjudicating raw research. The verdict is
        # advisory here — the graph routes to the interrupt either way.
        # Part 6 takes up how an acceptance check decides that a run is done.
        interrupt_before=["publish"],
    )

Automatische Pattern-Auswahl mit einem Router

Um für jeden Request den passenden Loop auszuwählen, habe ich einen Router Classifier ergänzt. Er verwendet Schema-Guided Reasoning, um die Klassifizierung zuverlässig zu halten:

class ExecutionMode(str, Enum):
    """Execution mode for the agent."""

    DEEP_RESEARCH = "deep_research"  # Plan-and-Execute + ReAct (thorough)
    FLASH_BRIEFING = "flash_briefing"  # ReWOO (fast, token-efficient)

class RouterOutput(BaseModel):
    """Structured output for the router."""

    mode: ExecutionMode  # DEEP_RESEARCH or FLASH_BRIEFING
    ticker: str
    reasoning: str

ROUTER_SYSTEM_PROMPT = """Classify the user's request:

1. **deep_research**: Complex analysis requiring synthesis
   - Examples: "Analyze strategic risks", "investment thesis"

2. **flash_briefing**: Quick snapshots, simple data retrieval
   - Examples: "quick snapshot", "current price"

Default to deep_research if unclear."""

llm = ChatAnthropic(model="claude-sonnet-4-5-20250929", temperature=0)
structured_llm = llm.with_structured_output(RouterOutput)

Damit wählen die User keinen Modus selbst aus. „Aktueller Preis“ wird an ReWOO geroutet, „Investmentthese“ an Plan-and-Execute.

Zentrale Erkenntnisse

  1. ReAct bietet die häufigsten Feedback-Punkte, bezahlt dafür aber mit wiederholten Model Calls.
  2. ReWOO reduziert Model Round Trips, wenn die Tools zuverlässig und Dependencies vorhersehbar sind.
  3. Plan-and-Execute eignet sich für komplexe Analysen, die vor der Execution zerlegt werden können, aber pro Schritt weiterhin Feedback benötigen.
  4. Ein Router kann pro Request zwischen ihnen auswählen, sodass User dies nicht selbst tun müssen.
  5. Der Loop benötigt gespeicherten State, um einen Interrupt oder Neustart des Workers zu überleben. Das ist das Thema von Teil 2.

Die vollständige Implementierung einschließlich Router und gemeinsamem State befindet sich im Repository des Market Analyst Agent.
