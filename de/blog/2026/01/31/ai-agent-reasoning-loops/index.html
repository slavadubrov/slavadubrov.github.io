AI-Agent-Reasoning-Loops im Jahr 2026: ReAct gegen ReWOO gegen Plan-and-Execute

Teil 1 der Serie „Engineering the Agentic Stack“

Ein Agent-Reasoning-Loop steuert, wie ein System plant, Tools aufruft, Ergebnisse liest und entscheidet, wann es aufhören soll. Dieser Kontrollfluss beeinflusst Kosten, Latenz sowie die Fähigkeit, sich nach unerwarteten Tool-Ergebnissen zu erholen.

In diesem Beitrag werden die drei im Jahr 2026 relevanten Muster von AI-Agent-Reasoning-Loops verglichen: ReAct, ReWOO und Plan-and-Execute. Das laufende Beispiel ist ein Market-Analyst-Agent, den ich in LangGraph entwickelt habe; der vollständige Code befindet sich auf GitHub.

Dies ist die innere Schicht dieser Serie. In den folgenden Teilen werden der Zustand behandelt, aus dem der Loop wieder aufnimmt, die aufrufbaren Tools, die zugrunde liegende Strategie für diese Aufrufe, der Agent Runtime, der einen Lauf am Leben erhält, sowie die Guardrails, die festlegen, ob die Arbeit tatsächlich abgeschlossen ist.

Zusammenfassung: ReAct ist flexibel, aber kostspielig; ReWOO ist schnell, wenn der Workflow vorhersehbar ist; Plan-and-Execute eignet sich für mehrstufige Analysen. Ein produktiver AI-Agent kann je nach Anfrage zwischen den Reasoning-Loops wechseln, wobei gemeinsam genutzter Zustand sowie checkpointierte LangGraph-Knoten gewählt werden, damit jede Aufgabe den Loop erhält, der zu ihrer Struktur passt.

Der Loop bestimmt Kosten, Latenz und Erholungsfähigkeit

Ein nützlicher Agent benötigt mehr als nur einen guten System Prompt. Sein Kontrollgraph muss Reasoning, Tools und Agent Memory miteinander verbinden und gleichzeitig Fehlern begegnen.

Der Reasoning-Loop steuert, wann das Modell plant, ein Tool aufruft, das Ergebnis liest und stoppt. Eine schlechte Wahl führt zu unnötigen Modellaufrufen und erhöht die Latenz. Zudem kann dadurch verhindert werden, dass sich der Agent von unerwarteten Tool-Ergebnissen erholt.

Drei Muster des AI-Agent-Reasonings

ReAct: Denken, Handeln, Beobachten, Wiederholen

ReAct (Yao et al., 2022) ist das ursprüngliche Muster für interaktive Agenten. Es läuft einen Loop ab:

  1. Thought: Der Agent erzeugt einen „Thought“, um das Ziel zu zerlegen und den nächsten Schritt zu planen.
  2. Action: Basierend auf diesem Thought ruft er ein Tool auf.
  3. Observation: Der Agent liest das Ergebnis ein, das sein Verständnis für den nächsten Thought aktualisiert.

Vorteile:

  • Die Grundlage in echten Beobachtungen verringert erfundene Fakten.
  • Der Agent kann seine Strategie je nach neuem Erkenntnisstand sofort anpassen.
  • Die Historie der Tool-Aufrufe und Beobachtungen liefert eine konkrete Ausführungsverfolgung.

Nachteile:

  • Die Historie sammelt sich an und wird bei jedem Schritt erneut verarbeitet, wodurch Latenz und Kosten mit der Länge des Loops zunehmen.
  • Verschwendungsvoll, wenn die Tool-Aufrufe im Voraus geplant werden könnten – genau hier kommt ReWOO ins Spiel.
  • Ohne Stoppsbedingung oder Schrittlimit läuft der Loop unbegrenzt weiter.

Am besten geeignet für: explorative Aufgaben, Debugging sowie Situationen, in denen man den weiteren Verlauf nicht vorhersagen kann.

ReWOO: Alles im Voraus planen

ReWOO (Reasoning WithOut Observation) ist ein effizienterer Variant von ReAct. Der Trick besteht darin, Reasoning von der Tool-Ausführung zu trennen: Anstatt nach jeder Aktion anzuhalten, um zu beobachten, plant ReWOO die gesamte Abfolge der Tool-Aufrufe in einem einzigen Durchlauf.

  1. Planung: Ein einziger Aufruf des LLM erstellt den vollständigen Ablauf der Tool-Aufrufe und verwendet Variable als Platzhalter (#E1, #E2) für noch nicht vorhandene Ausgaben.
  2. Ausführung: Ein nicht-LLM-basierter Executor führt die geplanten Tools nacheinander oder parallel aus und ersetzt dabei die Platzhalter durch tatsächliche Werte.
  3. Lösungserstellung: Ein weiterer Aufruf des LLM nutzt die gesammelten Ergebnisse, um die endgültige Antwort zu formulieren.

Vorteile:

  • Weniger wiederholte Modellaufrufe im Vergleich zu ReAct, sofern der ursprüngliche Plan weiterhin gültig ist.
  • Geringere Latenz – es muss keine Historie bei jedem Schritt erneut übermittelt werden.
  • Der Planer kann unabhängig voneinander feinjustiert werden, ohne auf eine laufende Umgebung angewiesen zu sein.

Nachteile:

  • Anfälligkeit bei fehlerhaftem Verhalten der Tools, da der Plan davon ausgeht, dass alles ordnungsgemäß funktioniert.
  • Erfordert vorhersehbare Arbeitsabläufe.
  • Ohne explizite Fallback-Logik wird ein fehlerhafter Plan weiter ausgeführt.

Einsatzgebiete: Schnelle Überprüfungen, Statusabfragen, Dashboards – insbesondere dort, wo die Tools sich vorhersehbar verhalten.

Plan-and-Execute: Ein Hybridmodell

Plan-and-Execute verbindet beide Ansätze miteinander. Die entsprechende Studie beschreibt einen einfachen Aufbau, den die meisten modernen AI Agents verwenden:

  1. Planungsphase: Zunächst wird ein Plan erstellt, der die Aufgabe in kleinere Unteraufgaben aufteilt.
  2. Ausführungsphase: Anschließend werden diese Unteraufgaben ausgeführt.

Die ursprüngliche Arbeit konzentrierte sich auf zero-shot Prompting. Moderne Frameworks wie LangGraph haben dieses Konzept weiterentwickelt zu einem vollständigen Orchestrierungsmuster mit sequenzieller Ausführung sowie Auswahl eines geeigneten Modells pro Schritt (ein leistungsstarkes Reasoning-Modell für die Planung, ein günstigeres für die Ausführung).

Vorteile:

  • Hierarchisches Reasoning, das der Vorgehensweise menschlicher Experten entspricht.
  • Möglichkeit zur Neuplanung – man kann bei unerwarteten Ergebnissen pausieren und neu bewerten.
  • Spezialisierung der Modelle: Der Planer kann teuer sein, während der Executor kostengünstig arbeitet.
  • Begrenzte Komplexität, da nach jedem Schritt ein klar definiertes Checkpoint vorhanden ist.

Nachteile:

  • Höhere Latenz im Vergleich zu ReWOO, da die Schritte nacheinander ausgeführt werden.
  • Mehr Zustände müssen verwaltet werden.
  • Überdimensioniert für one-shot-Anfragen.

Einsatzgebiete: Komplexe mehrstufige Analysen, Forschungsaufgaben sowie alle Anwendungen, die eine Synthese am Ende erfordern.

Messen Sie alle drei Ansätze anhand Ihrer eigenen Tool-Latenz, Ihres Modells, Ihres Aufgabensatzes sowie Ihrer Wiederholungsstrategie, bevor Sie ausschließlich aufgrund der Kosten entscheiden.

Für die Orchestration kommt LangGraph zum Einsatz. Alle drei Ansätze teilen sich denselben Zustandsobjekt, sodass der Router pro Anfrage entscheiden kann, welcher Ansatz ausgeführt werden soll:

Muster 1: Implementierung von Plan-and-Execute

Plan-and-Execute eignet sich besonders gut für Aufgaben, die mehrstufige Synthese erfordern. Der Schlüssel liegt darin, Planung und Ausführung voneinander zu trennen: Ein leistungsstarkes Modell erstellt zunächst den Plan, anschließend wird ein ReAct-Loop genutzt, um jeden Schritt auszuführen und dabei auf die Ergebnisse der Tools reagieren zu können.

Übereinstimmung mit dem Muster:

  1. Eine einzige Planungsphase zu Beginn. Ein einziger LLM-Aufruf liefert den gesamten Plan als Liste von Schrittbeschreibungen.
  2. Schema-gestützte Ausgabe, die den Plan vor der Ausführung validiert.
  3. Noch keine Tool-Ausführung. Der Planner bestimmt lediglich, was getan werden soll, nicht wie.
  4. Menschlich lesbare Schritte. Jeder Schritt ist Text, den ein Executor interpretieren kann.
# System prompt guides the LLM to think like a research analyst
# creating a strategic plan, not immediate tool calls
PLANNER_SYSTEM_PROMPT = """You are a senior investment research analyst.
Break down stock analysis requests into 4-6 research steps covering:
1. Current price and basic metrics
2. Recent news and announcements
3. Competitor analysis (if relevant)
4. Financial health assessment
5. Risk factors
6. Investment thesis synthesis

Output as JSON with step_number, description, and tool_hint."""

# Schema-Guided Reasoning: Enforce structure with Pydantic
class PlanOutput(BaseModel):
    """Structured output for the planner."""

    steps: list[PlanStep] = Field(description="Research steps to execute")
    ticker: str = Field(description="The stock ticker being analyzed")

def planner_node(state: AgentState) -> dict:
    """Generate a research plan from the user's request.

    This is Phase 1 of Plan-and-Execute: creating the high-level strategy.
    """

    # Use a powerful model for strategic planning
    llm = ChatAnthropic(model="claude-sonnet-4-5-20250929", temperature=0)

    # Ask for a typed plan and validate it before execution.
    # The API can still fail, so production code also handles that exception.
    structured_llm = llm.with_structured_output(PlanOutput)

    # Context from long-term memory personalizes the plan
    profile_context = f"""
User Profile:
- Risk Tolerance: {state.user_profile.risk_tolerance}
- Investment Horizon: {state.user_profile.investment_horizon}
"""

    # Single LLM call creates the complete plan
    result: PlanOutput = structured_llm.invoke([
        SystemMessage(content=PLANNER_SYSTEM_PROMPT + profile_context),
        HumanMessage(content=f"Create a research plan for: {last_user_message}"),
    ])

    # State update: Store the plan and initialize tracking
    return {
        "plan": result.steps,           # The sequential steps to execute
        "current_step_index": 0,        # Start at step 0
        "research_data": ResearchData(ticker=result.ticker),  # Initialize data container
    }

Die Zeile llm.with_structured_output(PlanOutput) stellt Schema-Guided Reasoning (SGR) dar, das ich bereits in einem früheren Beitrag erläutert habe. Mithilfe des Schemas kann die Anwendung einen fehlerhaften Plan bereits vor dem Einsatz der validierten Felder durch LangGraph zur Erzeugung bedingter Kanten ablehnen.

Muster 2: ReAct-Ausführung

Sobald ein Plan vorhanden ist, führt der Executor jeden Schritt als eigenständigen ReAct Loop aus. Dies ist Phase 2: Jeder Schritt ist so klein, dass der Thought-Action-Observation-Zyklus fokussiert bleibt und der Agent auf die Rückmeldungen der Tools reagieren kann.

Zusammenspiel der ReAct-Komponenten:

  1. Iterative Ausführung – Schritt für Schritt unter Berücksichtigung von Beobachtungsfeedback.
  2. Der Thought-Action-Observation-Loop läuft innerhalb von create_react_agent ab.
  3. Die Ergebnisse des vorherigen Schritts werden als Kontext für die aktuelle Reasoning-Schleife verwendet.
  4. Der Agent wählt basierend auf der Beschreibung des Schritts geeignete Tools aus.
  5. Er kann mitten im Schritt seine Vorgehensweise anhand der Rückmeldungen eines Tools ändern.
# Tools available for the ReAct agent to choose from
TOOLS = [
    get_stock_snapshot,
    get_price_history,
    search_news,
    search_competitors,
    get_financials,
]

def executor_node(state: AgentState) -> dict:
    """Execute the current step using a ReAct agent.

    This is Phase 2 of Plan-and-Execute: adaptive execution of each planned step.
    Each step runs as a mini ReAct loop until completion.
    """

    # Get the current step from the plan
    current_step = state.plan[state.current_step_index]

    # Build context from what we've learned so far
    # This matters: each step builds on previous observations
    previous_context = ""
    for step in state.plan[:state.current_step_index]:
        if step.result:
            previous_context += f"\nStep {step.step_number}: {step.result}\n"

    # Create a ReAct agent for this step
    # LangGraph's create_react_agent implements the full Thought-Action-Observation loop:
    # 1. Agent generates a "thought" about what tool to call
    # 2. Agent calls the tool ("action")
    # 3. Tool returns result ("observation")
    # 4. Agent decides: call another tool or finish
    react_agent = create_react_agent(
        model=ChatAnthropic(model="claude-sonnet-4-5-20250929"),
        tools=TOOLS,
    )

    # Invoke the ReAct loop for this single step
    # The agent will loop internally until it completes the step
    result = react_agent.invoke({
        "messages": [
            SystemMessage(content=EXECUTOR_SYSTEM_PROMPT),
            HumanMessage(content=f"""Execute Step {current_step.step_number}:
{current_step.description}

Ticker: {state.research_data.ticker}
Previous findings: {previous_context}"""),
        ]
    })

    # Extract the final answer from the ReAct agent's message history
    # The last message contains the synthesis after all tool calls
    updated_plan = list(state.plan)
    updated_plan[state.current_step_index] = PlanStep(
        step_number=current_step.step_number,
        description=current_step.description,
        completed=True,
        result=result["messages"][-1].content,  # Final observation
    )

    # State update: Mark step complete and advance to next
    return {
        "plan": updated_plan,
        "current_step_index": state.current_step_index + 1,
    }

Das ist der Kern des Plan-and-Execute-Flusses: Ein leistungsstarkes Modell erstellt den Plan, anschließend führt ReAct jeden Schritt mit voller Anpassungsfähigkeit aus.

Muster 3: ReWOO für schnelle Snapshots

Für schnelle Informationsabrufe überspringt ReWOO die verschachtelte Reasoning-Logik und führt die Tools parallel aus. Der Planner generiert im Voraus einen kompilierten Skript mit Tool Calls, welches vom Worker ohne weitere Beteiligung des LLM ausgeführt wird.

Aufbau dieses Ansatzes:

  1. Drei Phasen (Planner → Worker → Solver), ohne Schleifen.
  2. Die Tool Calls beziehen sich auf die Platzhalter #E1 und #E2 für noch nicht vorhandene Ergebnisse.
  3. Während der Ausführung kommt kein LLM zum Einsatz – der Worker ruft lediglich die Tools auf.
  4. Unabhängige Tools laufen parallel.
  5. Am Ende erfolgt eine einzige Syntheseaufruf, bei dem alle Daten gleichzeitig verarbeitet werden.

Phase 1: ReWOO Planner (erstellt im Voraus das vollständige Ausführungsgraphen)

class ReWOOPlanStep(BaseModel):
    """A step in the ReWOO plan with variable placeholders.

    Key difference from Plan-and-Execute's PlanStep:
    - Contains actual tool_name and tool_args (not just description)
    - Uses variable references (#E1) for dependencies
    """
    step_id: str  # e.g., "#E1" - becomes a variable
    description: str
    tool_name: str     # Exact tool to call
    tool_args: dict    # May contain variable refs like {"price": "#E1"}
    depends_on: list[str] = []  # For dependency ordering
    result: str | None = None

class ReWOOPlanOutput(BaseModel):
    """Structured output for ReWOO planner."""
    steps: list[ReWOOPlanStep] = Field(description="Planned tool calls with variables")

def rewoo_planner_node(state: AgentState) -> dict:
    """Generate a complete plan of tool calls upfront.

    This is the key difference from Plan-and-Execute: instead of creating
    human-readable step descriptions, we create EXACT tool calls that
    the worker will execute blindly.
    """

    llm = ChatAnthropic(model="claude-sonnet-4-5-20250929", temperature=0)

    # Schema-Guided Reasoning ensures valid tool call specifications
    structured_llm = llm.with_structured_output(ReWOOPlanOutput)

    ticker = state.research_data.ticker if state.research_data else "UNKNOWN"

    # Single LLM call to plan ALL tool executions
    result: ReWOOPlanOutput = structured_llm.invoke([
        SystemMessage(content=REWOO_PLANNER_PROMPT),
        HumanMessage(content=f"""Create a ReWOO plan for: {query}

Ticker: {ticker}

Output tool calls with:
- step_id: Variable name (#E1, #E2, etc.)
- description: What this accomplishes
- tool_name: Exact tool from the list
- tool_args: Dictionary of arguments
- depends_on: List of step_ids this depends on"""),
    ])

    # State update: Store the complete execution plan
    # Worker will execute this without any LLM involvement
    return {"rewoo_plan": result.steps}

Phase 2: ReWOO Worker (führt die Tools ohne LLM-Reasoning aus)

def rewoo_worker_node(state: AgentState) -> dict:
    """Execute all planned tools in parallel (no LLM calls).

    This is the key efficiency: Worker is "dumb" - it just runs tools
    according to the plan. No LLM calls = massive token savings.
    """

    results = {}  # Store results keyed by step_id (e.g., "#E1": "$150.23")

    # Execute ALL independent steps in parallel using ThreadPoolExecutor
    # This is where ReWOO gets its speed advantage
    with ThreadPoolExecutor(max_workers=5) as executor:
        futures = {
            executor.submit(execute_tool, step): step
            for step in state.rewoo_plan
            if not step.depends_on  # Only independent tools for parallel batch
        }

        # Collect results as they complete
        for future in as_completed(futures):
            step = futures[future]
            results[step.step_id] = future.result()
            # No LLM reasoning here - just store the raw tool output

    # State update: Store results for the Solver phase
    return {"rewoo_plan": updated_steps}

Phase 3: ReWOO Solver (synthetisiert alle Ergebnisse in einem einzigen LLM-Aufruf)

def rewoo_solver_node(state: AgentState) -> dict:
    """Synthesize all tool results into a flash briefing.

    This is the second efficiency gain: Instead of interleaving
    LLM calls with tool execution (like ReAct), we make ONE
    final synthesis call with all gathered data.
    """

    # Build context from ALL tool results at once
    tool_results = []
    for step in state.rewoo_plan:
        if step.result:
            tool_results.append(f"### {step.description}\n{step.result}")

    context = "\n\n".join(tool_results)

    # Single LLM call to synthesize everything
    structured_llm = llm.with_structured_output(FlashBriefingOutput)
    result = structured_llm.invoke([
        SystemMessage(content=REWOO_SOLVER_PROMPT),
        HumanMessage(content=f"Create a flash briefing from this data:\n\n{context}"),
    ])

    return {"draft_report": result}

ReWOO plant im Voraus jeden Tool Call und speichert Abhängigkeiten in Platzhaltern wie #E1 und #E2. Der Executor kann unabhängige Aufrufe parallel ausführen, ohne das Modell nach weiteren Schritten fragen zu müssen. Ein letzter Modellaufruf kombiniert schließlich alle Ergebnisse, wodurch vorhersehbare Workflows kostengünstig realisierbar sind.

Wo jeder Ansatz das Modell aufruft

Die drei Muster unterscheiden sich hinsichtlich Zeitpunkt und Art des LLM-Aufrufs:

MusterLLM-Aufrufe während der AusführungZustandsaktualisierungenHauptcodemuster

Der Unterschied zwischen diesen Ansätzen ergibt sich aus dem, was der Planer erzeugt – dieser bestimmt schließlich alles in den nachfolgenden Schritten.

  1. Plan-and-Execute erstellt menschenlesbare Beschreibungen der einzelnen Schritte:

    # Planner output (list of PlanStep objects)
plan = [
    PlanStep(
        step_number=1,
        description="Get current price and key financial metrics",
        tool_hint="get_stock_price"
    ),
    PlanStep(
        step_number=2,
        description="Search for recent news and earnings",
        tool_hint="search_news"
    ),
    # ... more steps
]

    Der Executor liest jede dieser Beschreibungen und entscheidet, welche Tool Calls durchgeführt werden sollen. Dieser Ansatz ist flexibel, erfordert jedoch für jeden Schritt einen Aufruf des LLM.

  2. ReAct verfügt nicht über einen vorab erstellten Plan. Stattdessen wird ein iterativer Reasoning Loop genutzt:

    # No planning phase - ReAct works step-by-step with accumulated messages
messages = [
    HumanMessage(content="Execute Step 1: Get current price"),
    AIMessage(content="I'll call get_stock_price"),
    ToolMessage(tool_call_id="1", content="$132.45"),
    AIMessage(content="Now I need metrics..."),
    # ... agent continues until step complete
]

    Mehrere LLM-Aufrufe pro Schritt ermöglichen Anpassungen an neu gewonnene Beobachtungen, was in der Regel mehr Kosten verursacht als die beiden anderen Ansätze.

  3. ReWOO erzeugt explizite, ausführbare Spezifikationen für Tool Calls:

    # Planner output (list of ReWOOPlanStep objects)
rewoo_plan = [
    ReWOOPlanStep(
        step_id="#E1",
        tool_name="get_stock_price",
        tool_args={"ticker": "NVDA"}
    ),
    ReWOOPlanStep(
        step_id="#E2",
        tool_name="search_news",
        tool_args={"query": "NVDA earnings", "limit": 5}
    ),
    # ... all tool calls planned upfront
]

    Der Worker arbeitet dabei ohne Einmischung des LLM – alle Modellaufrufe finden im Planer sowie im Solver statt, wodurch die Anzahl der Modellaufrufe vorhersehbar bleibt.

Fluss von Speicher und Zustand:

  • Plan-and-Execute: Der Zustand wandert von plan über current_step_index bis zu research_data.
  • ReAct: Der Zustand wird im Array messages akkumuliert – hier befindet sich die gesamte Konversationshistorie.
  • ReWOO: Der Zustand bewegt sich über rewoo_plan, wobei die Felder von result vom Worker ausgefüllt werden.

Zusammenfassung: Verknüpfung der Komponenten

So koexistieren die drei Ansätze innerhalb eines einzigen LangGraph-Systems. Sie teilen sich denselben AgentState und befinden sich im selben Graphen. Ein Router wählt je nach Anfrage den passenden Pfad – es handelt sich somit um einen einzigen AI Agent mit drei Ausführungsmodi, nicht um drei separate Agenten.

LangGraph stellt die Verknüpfungen deklarativ bereit:

def create_graph(checkpointer=None):
    builder = StateGraph(AgentState)

    # Add nodes
    builder.add_node("router", router_node)
    builder.add_node("planner", planner_node)
    builder.add_node("executor", executor_node)
    builder.add_node("reporter", reporter_node)
    builder.add_node("rewoo_planner", rewoo_planner_node)
    builder.add_node("rewoo_worker", rewoo_worker_node)
    builder.add_node("rewoo_solver", rewoo_solver_node)

    # Define edges
    builder.add_edge(START, "router")
    builder.add_conditional_edges("router", route_after_router, {
        "planner": "planner",
        "rewoo_planner": "rewoo_planner",
    })

    # Deep Research path
    builder.add_edge("planner", "executor")
    builder.add_conditional_edges("executor", route_after_executor, {
        "executor": "executor",  # Loop back for more steps
        "reporter": "reporter",  # Done with plan
    })
    builder.add_edge("reporter", END)

    # Flash Briefing path (ReWOO)
    builder.add_edge("rewoo_planner", "rewoo_worker")
    builder.add_edge("rewoo_worker", "rewoo_solver")
    builder.add_edge("rewoo_solver", END)

    return builder.compile(
        checkpointer=checkpointer,
        interrupt_before=["reporter"],  # HITL pause for approval
    )

Automatische Auswahl des Ansatzes mittels Router

Um für jede Anfrage den geeigneten Reasoning Loop auszuwählen, habe ich einen Router-Klassifizierer hinzugefügt. Dieser nutzt Schema-Guided Reasoning, um eine zuverlässige Klassifizierung zu gewährleisten:

class ExecutionMode(str, Enum):
    """Execution mode for the agent."""

    DEEP_RESEARCH = "deep_research"  # Plan-and-Execute + ReAct (thorough)
    FLASH_BRIEFING = "flash_briefing"  # ReWOO (fast, token-efficient)

class RouterOutput(BaseModel):
    """Structured output for the router."""

    mode: ExecutionMode  # DEEP_RESEARCH or FLASH_BRIEFING
    ticker: str
    reasoning: str

ROUTER_SYSTEM_PROMPT = """Classify the user's request:

1. **deep_research**: Complex analysis requiring synthesis
   - Examples: "Analyze strategic risks", "investment thesis"

2. **flash_briefing**: Quick snapshots, simple data retrieval
   - Examples: "quick snapshot", "current price"

Default to deep_research if unclear."""

structured_llm = llm.with_structured_output(RouterOutput)

Dadurch müssen die Nutzer keinen Modus manuell auswählen – der Router leitet beispielsweise Anfragen zum „aktuellen Preis“ automatisch an ReWOO und solche zur „Investitionsthese“ an Plan-and-Execute weiter.

Wichtige Erkenntnisse

  1. ReAct bietet die häufigsten Rückmeldepunkte, kostet aber wiederholte Modellaufrufe.
  2. ReWOO reduziert die Anzahl der Modellaufrufe, wenn die Tools zuverlässig sind und Abhängigkeiten vorhersehbar sind.
  3. Plan-and-Execute eignet sich für komplexe Analysen, die vor der Ausführung aufgeteilt werden können, aber dennoch Schritt-für-Schritt-Rückmeldungen benötigen.
  4. Ein Router kann je nach Anfrage zwischen den Ansätzen wählen – somit müssen die Nutzer dies nicht selbst tun.
  5. Der Reasoning Loop benötigt gespeicherten Zustand, um bei Unterbrechungen oder Neustarts des Workers weiterhin funktionstüchtig zu bleiben. Dies ist Gegenstand von Teil 2.
