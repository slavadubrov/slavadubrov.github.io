Enterprise RAG Challenge 3: Erkenntnisse aus öffentlichen Einreichungen

Bei der Enterprise RAG Challenge 3 (ERC3) sollten Agents Geschäftaufgaben gegen eine simulierte Unternehmens-API erledigen. Die eingefrorene Prize-Rangliste ist besonders nützlich, weil viele Teilnehmende mehr als nur einen Score veröffentlicht haben: Architektur, Model-Mix, Kosten und Hinweise zu Fehlern.

Ich habe diese öffentlichen Beschreibungen ausgewertet, um eine engere Frage zu beantworten: Welche Designentscheidungen tauchten in starken Einreichungen wiederholt auf, und welche davon sind auch außerhalb dieses Benchmarks nützlich?

Am Ende solltest du diese Beobachtungen in Design-Hypothesen für deine eigenen Agent Traces übersetzen und anschließend gegen deinen Task-Mix und deine Fehlerkosten testen können.

TL;DR: Es gab keine einheitliche Gewinner-Topologie. Starke Einreichungen reichten von einem einfachen Tool-Calling Agent bis zu spezialisierten Pipelines und Plan-Execute-Systemen. Die wiederkehrenden Ideen waren konkreter: Aus fehlgeschlagenen Traces lernen, riskante Schritte nahe am Ausführungspunkt validieren, eine explizite Context-Policy definieren und API-Risiken wie Pagination hinter zuverlässigen Wrappern verbergen. Der Prize-Gewinner nutzte als Production Prompt die 80. automatisch generierte Version.

Was ist die Enterprise RAG Challenge?

Die Enterprise RAG Challenge 3 ist ein groß angelegtes, crowdsourced Research-Projekt, das testet, wie autonome AI Agents komplexe Geschäftsaufgaben bewältigen. Im Gegensatz zu statischen Benchmarks läuft ERC3 auf der Agentic Enterprise Simulation (AGES), einer Discrete-Event-Simulation, die eine realistische Enterprise-API bereitstellt.

Was der Benchmark testet

In AGES arbeiten Agents innerhalb eines simulierten Unternehmens mit:

  • Mitarbeiterprofilen mit spezifischen Fähigkeiten und Abteilungen
  • Projekten mit Teamzuordnungen und Kundenbeziehungen
  • Corporate Wiki mit Geschäftsregeln und Berechtigungshierarchien
  • Zeiterfassung und Finanzprozessen

Jeder Task startet eine isolierte Simulation. Das Corporate Wiki wird geteilt, die operativen Datensätze unterscheiden sich jedoch je nach Task. Ein Agent kann die Suite daher nicht lösen, indem er sich nur einen einzelnen Unternehmenszustand merkt.

Task-Typen

Die Tasks decken mehrere Kompetenzbereiche ab:

  • Multi-Hop Reasoning, etwa die Zuordnung von Mitarbeiterfähigkeiten zu Projektbesetzungen.
  • Permission Validation, etwa das Blockieren nicht autorisierter Gehaltsänderungen oder Datenzugriffe.
  • Ambiguous Queries, einschließlich mehrsprachiger und paraphrasierter Anfragen.
  • Strict Output Compliance, einschließlich verpflichtender Entity-Links in Antworten.

Was die Einreichungen tatsächlich nahelegen

Die öffentlichen Berichte stützen kein eindeutiges Urteil wie „Multi-Agent schlägt Single-Agent“. Der Prize-Eintrag auf Platz vier war ausdrücklich als einfaches Single-Agent-Design umgesetzt. Sie stützen jedoch vier engere Beobachtungen:

  1. Decomposition war nützlich, wenn sie eine bekannte Fehlergrenze isolierte. Teams trennten Permission Checks, Step Validation, Code Execution oder Response Formatting – nicht beliebige „Agent Roles“.
  2. Validierung rückte näher an irreversible Aktionen. Mehrere Systeme prüften Permissions vor der Execution, überprüften einzelne Schritte oder schützten die finale Response.
  3. Trace-driven Iteration war wichtig. Der Prize-Gewinner überführte fehlgeschlagene Runs über einen automatisierten Loop in Prompt-Revisionen; andere Teams dokumentierten ähnlich konkrete Tool- und Prompt-Fixes.
  4. Die Context-Policy war eine Architekturentscheidung. Teams testeten Distillation, Preloading, Retrieval und History Compression. Ihre eigenen Berichte widersprechen sich darin, ob Compression geholfen hat – eine universelle Vorgehensweise gibt es daher nicht.

Ich habe sie ausgewählt, weil ihre öffentlichen Beschreibungen fünf unterschiedliche Arten zeigen, ein System zu bauen: automatisierte Prompt-Revision, Specialist-Stages, Per-Step-Validation, Response Guards und Plan-Execute-Isolation. 1. Evolutionary Prompt Engineering (Team VZS9FL / @aostrikov)

Der Ansatz mit dem höchsten Score automatisierte Prompt Engineering über einen Self-Improvement Loop.

Statt den Production Prompt manuell zu optimieren, baute das Team einen Three-Agent Loop, der aus fehlgeschlagenen Traces mögliche Revisionen erzeugte.

Three-Agent-Pipeline:

AgentRolle
Main AgentFührt den Benchmark aus und protokolliert alle Aktionen und Fehler
Analyzer AgentPrüft fehlgeschlagene Tasks und formuliert Hypothesen zu Root Causes
Versioner AgentErzeugt eine neue Prompt-Version, die die Learnings aufnimmt

Der Production Prompt war die 80. automatisch generierte Version. Das Team beschreibt den Loop als Prozess, der fehlgeschlagene Tasks analysiert, Ursachen vorschlägt und entscheidet, welche Empfehlungen übernommen werden. Die Rangliste belegt den finalen Score und die Anzahl der Iterationen. Sie isoliert nicht, wie viel des Zugewinns auf die Automation und wie viel auf Models, Tools oder das kumulierte Benchmark-Feedback zurückzuführen ist.

Stack: claude-opus-4.5 mit Anthropic Python SDK und nativem Tool Use.

2. Multi-Agent Sequential Pipeline (Team Lcnxuy / @andrey_aiweapps)

Diese Einreichung baute einen sequentiellen Workflow, in dem spezialisierte Komponenten für Security Checks, Context Extraction, Execution und Entity-Link-Formatting zuständig waren.

Dokumentierte Komponenten:

  1. Security Gate Agent: Führt vor der Main Loop einen Pre-Execution Check durch und validiert Permissions anhand der Wiki-Regeln.
  2. Context Extraction Agent: Extrahiert die kritischen Regeln aus umfangreichen Prompts und lädt User-, Projekt- und Kundendaten vorab.
  3. Execution Agent: ReAct-basiertes Planning mit fünf internen Phasen (Identity → Threat Detection → Info Gathering → Access Validation → Execution).
  4. LinkGeneratorAgent: In das Response Tool eingebettet; analysiert den Context, um die erforderlichen Entity-Links einzufügen.

Der LinkGeneratorAgent ist der am leichtesten übertragbare Teil. Indem er innerhalb des Response Tools platziert wird, wird eine Benchmark-Anforderung (verpflichtende Entity-Links) zu einer Eigenschaft des Interfaces und nicht zu einer weiteren Anweisung, die das Execution Model vergessen kann.

Stack: atomic-agents- und instructor-Frameworks mit gpt-5.1-codex-max, gpt-4.1 und claude-sonnet-4.5.

3. Schema-Guided Reasoning mit Step Validation (Team NLN7Dw / Ilia Ris)

Dieses Team kombinierte SGR mit schneller Inference und einem Validator für jeden vorgeschlagenen Schritt. Das Design macht Revisionen günstig: Einen fehlerhaften Schritt ablehnen, bevor er zu einem Tool Call wird, und anschließend den Main Flow mit den Kommentaren des Validators zur Überarbeitung auffordern.

Zentrale Komponenten:

KomponenteFunktion
StepValidatorPrüft jeden vorgeschlagenen Schritt. Wenn etwas nicht stimmt, gibt er ihn mit Kommentaren zur Überarbeitung zurück.
Context ManagementVollständiger Plan aus dem vorherigen Turn sowie komprimierte History für ältere Turns
Dynamic EnrichmentLädt automatisch User Profile, Projekte und Kunden; das LLM filtert und injiziert nur für den Task relevante Daten
Auto-Pagination WrappersAlle List Endpoints liefern automatisch vollständige Ergebnisse

Das Team berichtete, gpt-oss-120b auf Cerebras mit bis zu ungefähr 3.000 Tokens pro Sekunde auszuführen. Die Kombination aus Validation und High-Throughput-Inference könnte deren Latenzkosten reduziert haben. Das öffentliche Ergebnis isoliert diesen Effekt nicht.

Stack: gpt-oss-120b auf Cerebras mit einer angepassten SGR-NextStep-Implementierung.

4. Enricher- und Guard-System (Team J8Gvbi / @mishka)

Diese Einreichung ergänzte eine SGR-Basis um nicht blockierende Hinweise und ein abgestuftes Guard-System. Sobald API Responses eintrafen, analysierten Enricher diese und fügten dem nachfolgenden Context operative Hinweise hinzu.

Mehr als 20 Enricher analysierten API Responses und injizierten kontextbezogene Hinweise:

RoleEnricher: "You are LEAD of this project, proceed with update."
PaginationHintEnricher: "next_offset=5 means MORE results! MUST paginate."

Three-Mode-Guard-System:

ModusVerhalten
Hard BlockUnmögliche Aktionen werden dauerhaft blockiert
Soft BlockRiskante Aktionen werden beim ersten Versuch blockiert und bei einem Retry zugelassen
Soft HintGibt Hinweise, ohne zu blockieren

Hybrid-RAG-Wiki: Drei Search Streams (Regex, Semantic und Keyword) deckten unterschiedliche Query-Formen im Corporate Wiki ab.

Stack: qwen/qwen3-235b-a22b-2507 auf dem LangChain SGR Framework.

5. Plan-Execute REPL (Team key_concept_parallel)

Diese Architektur trennte Planning und Execution durch eine harte Grenze und verwendete einen Code-generierenden Loop. Sie erschien auf der breiteren Ultimate-Rangliste, nicht unter den fünf besten Einträgen der eingefrorenen Prize-Rangliste. Ihre öffentliche Beschreibung ist dennoch nützlich, weil sie eine andere Form der Decomposition zeigt: Isolation nach Execution-Phase statt nach Business Role.

Unterschiedliche Models übernahmen unterschiedliche Aufgaben: eines plante, eines schrieb Python, und ein separates Decision Model entschied nach jedem Schritt über das weitere Vorgehen.

Multi-Model-Setup:

PhaseModel
Planningopenai/gpt-5.1
Code Generationdeepseek/deepseek-v3.2
Post-Step Decisionopenai/gpt-4.1
Final Responseopenai/gpt-4.1

Die Step-Completion-REPL:

  1. Der Planner erstellt einen High-Level-Schritt.
  2. Das Code-Gen-Model arbeitet in einem frischen Model Context und schreibt dafür ein Python-Script.
  3. Das Script wird in einer Task-scoped REPL ausgeführt, deren Variablen über die einzelnen Schritte hinweg erhalten bleiben.
  4. Das Decision Model betrachtet das Ergebnis und wählt zwischen Continue, Abort oder Replan.

Der Replan-Pfad ist die wiederverwendbare Idee. Wenn ein Schritt teilweise fehlschlägt, kann das Decision Model abgeschlossene Arbeit erhalten und nur den verbleibenden Plan neu schreiben.

Wiederkehrende Patterns in den Einreichungen

Die Implementierungen unterschieden sich, doch mehrere Engineering-Themen tauchten in den öffentlichen Beschreibungen wiederholt auf.

Context Management war explizit

Kein Team konnte dem Model jede Regel, jeden Datensatz und jeden vorherigen Schritt geben, ohne eine Policy-Entscheidung zu treffen. Der interessante Unterschied lag darin, wo die einzelnen Systeme Informationen filterten.

StrategieAnsatzAm besten geeignet für
Rule DistillationWiki-Regeln vorverarbeiten und in kompakte Instructions überführen, ohne Constraints zu verlierenSchlanke Prompts, schneller Startup
Aggressive PreloadingUser-, Projekt- und Kundendaten vor der Execution ladenMinimierung von Tool Calls
Hybrid RAGRegex-, Semantic- und Keyword-Search-StreamsKomplexe Retrieval-Anforderungen
History CompressionAktuelle Turns vollständig behalten und ältere History komprimierenLange Konversationen

Trade-off: NLN7Dw komprimierte ältere Turns, während f1Uixf berichtete, dass History Compression in seinen Experimenten geschadet habe und stattdessen die vollständige Konversation beibehielt. Behandle Compression als gemessene Entscheidung und nicht als Default.

Guardrails wurden an unterschiedlichen Fehlergrenzen platziert

Mehrere Teams platzierten Checks vor, während oder nach der Main Loop. Diese Mechanismen adressierten unterschiedliche Risiken und sollten nicht zu einem generischen „Critic Agent“ zusammengefasst werden.

Guardrail-TypZeitpunktBeispiel
Pre-Execution GatesVor dem Start der Main LoopSecurity Gate Agent validiert Permissions anhand der Wiki-Regeln
In-Loop ValidatorsWährend des ReasoningStepValidator prüft jede vorgeschlagene Aktion und löst bei Fehlern eine Überarbeitung aus
Post-Execution GuardsVor der finalen SubmissionThree-Mode Guard System prüft Response-Ergebnisse anhand von API-Evidenz und Policy

Tool Wrapper

Mehrere Teams bauten Abstraction Layers um die Raw API:

  • Auto-Pagination: Wrapper iterieren über jede Page und liefern den vollständigen Datensatz zurück.
  • Fuzzy Normalization: „Willingness to travel“ wird in das API-Feld will_travel übersetzt.
  • Specialized Reasoning Tools: think, plan und critic Tools für kontrollierte Deliberation.

Failure Modes und die von Teams berichteten strukturellen Fixes

Die Berichte erwähnen wiederholt Fehler an API- und Policy-Grenzen. Die am besten übertragbaren Fixes verlagerten die Anforderung in Code oder in einen dedizierten Validation Step:

Eine praktische Reihenfolge für die Einführung

ERC3 betrifft ein einzelnes simuliertes Unternehmen und ist keine allgemeine Agent-Ablation-Studie. Nutze die Ergebnisse als Quelle für Design-Hypothesen und teste diese anschließend gegen deine eigenen Traces. Eine sinnvolle Reihenfolge ist:

  1. Stelle zuerst die API-Korrektheit deterministisch sicher. Führe bei List Endpoints automatisch Pagination durch, normalisiere fuzzy Felder, validiere Schemas und erzeuge erforderliche Links innerhalb des Response Tools.
  2. Füge Checks an realen Risikogrenzen hinzu. Prüfe Identity und Permission vor Mutationen; validiere einen Schritt vor der Execution nur dann, wenn der zusätzliche Model Call Fehler abfängt, deren Wert seine Kosten rechtfertigt.
  3. Dokumentiere eine Context-Policy. Entscheide, was preloaded, retrieved, compressed oder unverändert beibehalten wird. Miss die Policy nach Task Slice und nicht nur anhand der Token-Anzahl.
  4. Mache fehlgeschlagene Traces zu Regression Cases. Klassifiziere den Fehler, ändere einen Mechanismus und führe den betroffenen Slice erneut aus. Automatisiere Prompt-Revisionen erst, wenn dieser Loop zuverlässig funktioniert.
  5. Führe Decomposition ein, wenn Zuständigkeiten klarer werden. Eine separate Komponente ist dann gerechtfertigt, wenn sie einen Constraint besitzen, ein anderes Model oder Tool verwenden oder unabhängig getestet werden kann – nicht bloß, weil „Multi-Agent“ leistungsfähiger klingt.

Über diese Berichte hinweg machten die zuverlässigen Einreichungen verborgene operative Anforderungen in Tools, Validators und Evaluation Loops sichtbar.
