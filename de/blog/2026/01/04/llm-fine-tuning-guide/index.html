LLM Fine-Tuning Guide: LoRA, QLoRA, Unsloth, Axolotl

Viacheslav Dubrov

2026-01-04 · Aktualisiert 2026-07-15 · 19 Min. · Modellentwicklung

Automatische Übersetzung Dieser Artikel wurde automatisch aus der englischen Originalversion übersetzt.

Die meisten Fine-Tuning-Fehlschläge sind Entscheidungsfehler. Ein Team trainiert, bevor es nachgewiesen hat, dass Prompting, Retrieval oder Constrained Decoding das Problem nicht lösen können. Ein anderes evaluiert auf der Trainingsverteilung oder stellt erst nach dem Training fest, dass sich das Artefakt nur schwer bereitstellen lässt.

Dieser Guide behandelt Adaptation als Experiment mit einem operativen Ziel. Er beginnt mit der Entscheidungsgrenze und folgt anschließend einem Pfad über Daten, LoRA oder QLoRA, aufgabenspezifische Evaluation, Export und Serving.

Für die kurze Entscheidungshilfe siehe Fine-Tuning vs RAG vs Prompting.

TL;DR

Fine-Tuning lohnt sich, wenn eine gemessene Baseline zeigt, dass eine Änderung des Model-Verhaltens ein Update der Weights rechtfertigt. Verwende Retrieval für veränderliche Fakten und Constrained Decoding für Syntax. Starte mit LoRA, wenn das Base Model bequem in den Speicher passt; verwende QLoRA, wenn der Speicherbedarf der eingefrorenen Weights der limitierende Faktor ist. Halte vor dem Training ein Eval-Set zurück, vergleiche mit der ungetunten Baseline und lege das Deployment-Artefakt fest, bevor du dich für eine Methode entscheidest.

Fine-Tuning vs RAG

Fine-Tuning kann verändern, wie ein Model Domänensprache verwendet. Als Update-Mechanismus für Fakten, die sich ändern oder zitiert werden müssen, ist es jedoch ungeeignet. Retrieval und Fine-Tuning lösen unterschiedliche Teile des Problems und gehören oft in dasselbe System.

Fine-Tuning vs Prompt Engineering

Moderne LLMs reagieren gut auf klare Prompts und Beispiele. Teste diese Optionen, bevor du in Fine-Tuning investierst.

[!TIP] Teste zuerst Prompting Starte mit einem Prompt und repräsentativen Beispielen. Wenn nur die Output-Syntax unzuverlässig ist, füge Constrained Decoding hinzu, bevor du die Weights veränderst.

Fine-Tuning vs Constrained Decoding

Bibliotheken wie xgrammar und outlines beschränken die Generierung auf ein JSON Schema, einen regulären Ausdruck oder eine Grammar. Abhängig von Constraint und Backend kompilieren sie einen Automaten oder eine Grammar und maskieren ungültige nächste Tokens. Ein Weight-Update ist nicht erforderlich.

Damit wird die Zugehörigkeit zur unterstützten Output-Sprache garantiert. Diese Garantie sagt jedoch nichts darüber aus, ob die Werte korrekt, vollständig oder semantisch passend sind. Ein syntaktisch gültiger Function Call kann dennoch die falsche Kunden-ID enthalten.

Eine praktische Reihenfolge:

  1. Starte für grundlegende Formatierung mit Prompting und Few-Shot-Beispielen.
  2. Füge Constrained Decoding (xgrammar oder outlines) hinzu, wenn die Syntax inkonsistent ist.
  3. Führe Fine-Tuning nur durch, wenn du Verhaltensänderungen benötigst, die ein Schema nicht erzwingen kann.

Mache den Business Case messbar

Fine-Tuning kann wiederkehrende Prompt-Tokens reduzieren oder ermöglichen, dass ein kleineres Model das Ziel erreicht. Keine dieser Einsparungen ist jedoch automatisch gegeben. Berechne den Break-even-Punkt mit deinem eigenen Traffic und Pricing:

[ \text{Break-even-Requests} = \frac{\text{Kosten für Training + Evaluation + Deployment}} {\text{Baseline-Kosten/Request} - \text{Kosten des getunten Models/Request}} ]

Wenn der Nenner klein oder negativ ist oder auf einer nicht nachgewiesenen Qualitätsannahme beruht, gibt es für das Projekt noch keinen wirtschaftlichen Case.

[!TIP] Das hybride Setup Eine verbreitete Architektur kombiniert ein kleineres, auf die Aufgabe adaptiertes Model mit Retrieval für veränderliche Fakten. Behandle das größere Prompted Model als Baseline und behalte das kleinere Model nur dann, wenn es dieselben aufgabenspezifischen Qualitäts- und Safety-Schwellenwerte erreicht.

Arten von Fine-Tuning

Fine-Tuning kann grundsätzlich drei Formen annehmen. Sie unterscheiden sich darin, welche Daten sie benötigen und was sie dem Model beibringen.

1. Continued Pre-Training (unsupervised)

Du trainierst das Base Model mit zusätzlichem Rohtext, ohne Labels. Es führt weiterhin Next-Token-Prediction durch – genau wie beim ursprünglichen Pretraining.

Wann du es einsetzen solltest:

  • Die Domäne enthält ein Vokabular, das das Base Model nie gesehen hat (medizinische oder juristische Texte, interne Codebases).
  • Du hast große Mengen an Domänentext, aber keine gelabelten (Input-, Output-)Paare.
  • Das Base Model hat Schwierigkeiten mit domänenspezifischer Terminologie.

Beispiel: Training auf Millionen klinischer Notizen, damit das Model medizinische Abkürzungen, Medikamentennamen und klinische Workflows erlernt.

2. Supervised Fine-Tuning (SFT)

SFT trainiert auf gelabelten (Input-, Output-)Paaren. Du zeigst dem Model für jeden Input exakt den gewünschten Output.

Wann du es einsetzen solltest:

  • Du hast eine konkrete Aufgabe mit sauberem Input-/Output-Format.
  • Du verfügst über hochwertige gelabelte Daten, auch in kleinen Mengen.
  • Du benötigst vorhersehbares Verhalten für eine bekannte Input-Struktur.

Beispiel: Training auf Paaren aus (Beschreibung einer SQL-Abfrage, SQL-Code) für Text-to-SQL.

{
    "input": "Get all users who signed up last month",
    "output": "SELECT * FROM users WHERE signup_date >= DATE_SUB(NOW(), INTERVAL 1 MONTH)"
}

3. Instruction Tuning

Instruction Tuning ist ein Sonderfall von SFT. Es wurde dafür entwickelt, Models dazu zu bringen, eine große Bandbreite natürlichsprachlicher Anweisungen zu befolgen. Die Trainingsdaten bestehen aus (Instruction-, Response-)Paaren für viele verschiedene Aufgaben.

Wann du es einsetzen solltest:

  • Du möchtest einen General-Purpose Assistant wie ChatGPT oder Claude.
  • Das Model muss vielfältige, offene Anfragen verarbeiten.
  • Du entwickelst eine Chat-Schnittstelle.

Beispiel: Training auf Tausenden unterschiedlichen Instructions wie „Fasse diesen Artikel zusammen“, „Schreibe ein Gedicht über X“ oder „Erkläre Y in einfachen Worten“.

[!NOTE] Was in der Praxis tatsächlich gemacht wird SFT und Instruction Tuning verwenden dasselbe Next-Token-Objective. Der Unterschied liegt in der Breite und Konstruktion des Datasets. Continued Pre-Training ist ein separates Experiment und sollte von Tests auf Domänengewinne und Regressionen bei allgemeinen Fähigkeiten gefolgt werden.

Die Fine-Tuning-Pipeline in 7 Phasen

Fine-Tuning ist eine Pipeline, kein einzelner Befehl. Jede Phase hat eigene Failure Modes. Wird eine Phase übersprungen, zeigt sich das meist später als schlechtes Model.

Jede Phase baut auf der vorherigen auf:

  1. Datenvorbereitung — Definiere die Evaluationseinheit, teile die Daten auf, bereinige und formatiere sie anschließend.
  2. Model-Auswahl — Wähle das passende Base Model und lade die Weights.
  3. Trainings-Setup — Konfiguriere Hardware, Hyperparameter und die Optimierungsstrategie.
  4. Fine-Tuning — Führe SFT-, DPO- oder ORPO-Training aus.
  5. Evaluation — Miss die Performance per Benchmark und validiere die Qualität.
  6. Deployment — Exportiere und serve dein Model.
  7. Monitoring — Verfolge die Performance, führe Wartung durch und iteriere.

[!WARNING] Daten sind das Fundament Training reproduziert systematische Fehler in den Beispielen. Prüfe Labels, Leakage, Abdeckung und Policy-Konformität, bevor du Zeit in Optimizer-Sweeps investierst.

Phase 1: Datenvorbereitung

Viele Fine-Tuning-Projekte scheitern hier, nicht im Training. Moderne Datenvorbereitung bedeutet mehr, als einen Regex über CSVs laufen zu lassen.

Die Datenpipeline in 5 Phasen

Tools wie DataTrove und Distilabel können bei großen Datenmengen helfen. Lass die Fehler-Taxonomie und den Data Contract das Pipeline-Design bestimmen; die Tool-Auswahl folgt daraus.

1. Ingestion und Filtering

  • Aktion: Verwirrende Antworten („Das kann ich nicht beantworten“), beschädigtes UTF-8 und nicht relevante Sprachen entfernen.
  • Tools: Trafilatura für Extraction, FastText für Language ID.

2. Policy für sensitive Daten

  • Aktion: Entscheide, was das Model lernen darf. Redigiere, tokenisiere oder schließe personenbezogene und vertrauliche Felder nach Bedarf aus.
  • Tools: Microsoft Presidio oder scrubadub.
  • Warum: Ein Detector ist nur eine einzelne Kontrolle. Anforderungen an Provenance, Einwilligung, Aufbewahrung, Zugriff und Löschung gelten weiterhin.

3. Deduplication (MinHash LSH)

  • Aktion: Beinahe-Duplikate entfernen, damit das Model sie nicht memoriert.
  • Tools: DataTrove eignet sich gut für Processing im Terabyte-Maßstab.

4. Synthetische Augmentation, falls erforderlich

  • Aktion: Ein stärkeres Teacher Model (GPT-4o, DeepSeek-V3) verwenden, um Rohdaten in saubere Instruction-/Response-Paare umzuschreiben.
  • Tools: Distilabel.
  • Validierung: Teacher-Outputs stichprobenartig prüfen, anhand derselben Rubrik wie menschliche Labels bewerten und synthetische sowie von Menschen erstellte Slices in der Evaluation getrennt halten.

5. Formatting

  • Aktion: In ein Standardformat konvertieren (Alpaca oder ShareGPT).

Beispiele für Datenformate

Alpaca-Format (Instruction-Following):

{
    "instruction": "Summarize the following text.",
    "input": "The text to be summarized...",
    "output": "This is the summary."
}

ShareGPT-/ChatML-Format (konversationell):

{
    "conversations": [
        { "from": "user", "value": "Hello, who are you?" },
        { "from": "assistant", "value": "I am a helpful AI assistant." }
    ]
}

Worauf es tatsächlich ankommt

  • Abdeckung vor Volumen. Füge Beispiele hinzu, die unterschiedliche Failure Modes repräsentieren, statt Wiederholungen des einfachen Mehrheitsfalls.
  • Sauberkeit. Entferne irrelevanten Text, normalisiere Whitespace und halte die Formatierung konsistent.
  • Balance. Bewahre wichtige seltene Fälle und berichte die Performance pro Slice.
  • Trennung. Teile nach Quelle, User, Dokument oder Zeit auf, wenn zufällige Row-Splits Near-Duplicates leaken würden.
  • Provenance. Erfasse für jede Dataset-Version Quelle, Lizenz oder Berechtigung, Transformationshistorie und Löschpfad.

Phase 2: Model-Auswahl und Hardware

Die Wahl des Base Models und das Verständnis des GPU-Minimums bestimmen, was du tatsächlich trainieren kannst.

Starte mit dem kleinsten Base Model, das die unverzichtbaren Baseline-Checks bereits besteht. Prüfe:

  • Lizenz und Bedingungen für die Weiterverteilung im vorgesehenen Produkt;
  • Language-, Domain-, Tool-Use- und Safety-Verhalten vor der Adaptation;
  • Kompatibilität von Tokenizer und Chat Template mit dem Dataset;
  • den für reale Beispiele erforderlichen maximalen Kontext und das Truncation-Verhalten;
  • Unterstützung sowohl im Trainings-Framework als auch in der Ziel-Serving-Engine.

Fine-Tuning ist ein Adaptationsschritt, kein Mittel zur Reparatur eines ungeeigneten Base Models. Wenn das Model bei Fähigkeiten versagt, die das Dataset nicht abdeckt, wähle vor weiteren Epochen ein anderes Base Model.

Plane den Run, nicht die Marketingklasse

Es gibt keine dauerhaft gültige Tabelle „Model-Größe → GPU“. Der Peak-Speicherbedarf verändert sich mit Weight-Precision, Optimizer, Anzahl trainierbarer Parameter, Sequence Length, Micro-Batch-Size, Activation Checkpointing, Attention-Implementierung und Framework-Overhead. Beginne mit einer Speicherschätzung und führe anschließend einen kurzen Smoke Test mit maximaler Länge auf dem exakten Stack aus.

Das ursprüngliche QLoRA-Paper passte ein 65B-LLaMA-Model in seinem spezifischen Setup auf eine einzelne 48-GB-GPU. Dieses Ergebnis ist ein hilfreicher Richtwert, aber keine Garantie dafür, dass jede aktuelle 70B-Architektur, Context Length, jeder Kernel oder Trainer auf dasselbe Gerät passt.

Speicherberechnung

Bei einem Model mit PPP Parametern benötigen allein die Weights ungefähr 2P2P2P Bytes in BF16/FP16 beziehungsweise 0.5P0.5P0.5P Bytes bei vier Bits – noch vor Quantization-Metadaten und Runtime-Buffern. Full Training im Adam-Stil benötigt zusätzlich Gradients, Optimizer States und häufig höherpräzise Master Weights. LoRA vermeidet den größten Teil des Speichers für trainierbare States; QLoRA reduziert zusätzlich den Speicherbedarf der eingefrorenen Base Weights. Activations können bei langen Sequence Lengths weiterhin dominieren.

Verwende diesen Ablauf:

  1. Wähle die längste Sequence und Micro-Batch-Size, die du unterstützen musst.
  2. Schätze Weights und trainierbare States und plane Headroom für Activations und Kernels ein.
  3. Führe einen Forward-/Backward-Step bei maximaler Länge aus.
  4. Erfasse den Peak von alloziertem und reserviertem Speicher.
  5. Skaliere erst danach Batch-Size, Rank, Sequence Length oder GPU-Anzahl.

Phase 3: Trainingsmethoden (PEFT und LoRA)

Full Fine-Tuning vs PEFT

Full Fine-Tuning (FFT) aktualisiert jedes Weight. Gradients und Optimizer States skalieren daher mit dem gesamten Model. Der Peak-Speicherbedarf lässt sich nicht allein aus der Parameteranzahl ableiten, liegt aber deutlich über dem Speicherbedarf zum Laden der Weights für Inference.

Parameter-efficient Fine-Tuning (PEFT) trainiert nur eine kleine Teilmenge der Parameter und friert den Rest ein. Die Mathematik wird dadurch deutlich angenehmer.

LoRA: der Ausgangspunkt

LoRA (Low-Rank Adaptation) friert eine vortrainierte Matrix ein und repräsentiert ihr gelerntes Update mit zwei kleineren Matrizen. Das Original-Paper begründet diesen Ansatz mit der Hypothese, dass nützliche Adaptations-Updates einen niedrigen intrinsischen Rank besitzen.

Für eine eingefrorene Matrix W0∈Rdout×dinW_0 \in \mathbb{R}^{d_{out} \times d_{in}}W0​∈Rdout​×din​ lernt LoRA:

  • A∈Rr×dinA \in \mathbb{R}^{r \times d_{in}}A∈Rr×din​
  • B∈Rdout×rB \in \mathbb{R}^{d_{out} \times r}B∈Rdout​×r

Die adaptierte Layer ist:

W′=W0+αrBAW' = W_0 + \frac{\alpha}{r}BAW′=W0​+rα​BA

Der Adapter hat r(din+dout)r(d_{in}+d_{out})r(din​+dout​) trainierbare Parameter statt dindoutd_{in}d_{out}din​dout​ für diese Matrix. Bei einer quadratischen Matrix mit einer Breite von 4.096 und Rank 16 entspricht das einer Reduktion um den Faktor 128 für diese Matrix – nicht um den Faktor 10.000 für ein beliebiges Model. Die 10.000×-Angabe im LoRA-Paper bezog sich auf eine spezifische GPT-3-175B-Konfiguration, bei der ausgewählte Matrizen adaptiert wurden.

Wann welche Methode?

  • LoRA: Starte hier. Schnell, speichereffizient und gut unterstützt.
  • QLoRA: Wenn dasselbe LoRA-Experiment wegen der eingefrorenen Base Weights nicht passt.
  • DoRA: Nachdem ein Apples-to-Apples-Vergleich mit LoRA einen nützlichen Gewinn gezeigt hat.
  • Full Fine-Tuning: Erst dann, wenn PEFT nachweislich ein Bottleneck ist und nicht nur angenommen wird.

DoRA: Weight-Decomposed LoRA

DoRA (Weight-Decomposed Low-Rank Adaptation) trennt die Magnitude jedes Weight-Vektors von seiner Richtung. Es wendet ein LoRA-Update auf die Richtungskomponente an und lernt die Magnitude separat.

So funktioniert es:

Statt Weights als eine Einheit zu behandeln, zerlegt DoRA vortrainierte Weights in zwei Komponenten:

  1. Magnitude — ein trainierbarer Wert pro Weight-Vektor.
  2. Richtung — ein normalisierter Vektor, der über Low-Rank-Matrizen aktualisiert wird.

In kompakter spaltenweiser Schreibweise:

W′=mV+BA∥V+BA∥cW' = m \frac{V + BA}{\lVert V + BA \rVert_c}W′=m∥V+BA∥c​V+BA​

wobei:

  • m = Magnitude (trainierbar)
  • VVV = die eingefrorene Richtungs-Matrix
  • BABABA = das gelernte Low-Rank-Richtungs-Update
  • ∥⋅∥c\lVert \cdot \rVert_c∥⋅∥c​ = spaltenweise Normalisierung

Das erhältst du für diese zusätzliche Struktur:

  • Mehr Freiheitsgrade als bei Standard-LoRA, da sich die Magnitude unabhängig ändern kann.
  • Bessere Ergebnisse als LoRA in mehreren vom Paper der Autoren berichteten Konfigurationen.
  • Zusätzliche Parameter und Berechnung; der Gewinn sollte daher auf deiner Aufgabe und deinem Serving-Pfad verifiziert werden.

Adapter-Merging für Multi-Task Learning

Separate Adapter ermöglichen es, dass ein eingefrorenes Base Model mehrere Tasks unterstützt. Du kannst Requests an einen Adapter routen, mehrere Adapter aus einer Engine serven, sofern dies unterstützt wird, oder offline einen zusammengeführten Kandidaten erzeugen. Merging kann Interferenzen verursachen. Evaluiere daher das zusammengeführte Artefakt, statt von einer sauberen Komposition der Quell-Adapter auszugehen.

Gängige Merging-Methoden:

  1. Concatenation — Adapter-Parameter kombinieren und den effektiven Rank erhöhen. Schnell und einfach.
  2. Linear Combination — gewichtete Summe der Adapter. Bietet Stellschrauben.
  3. SVD — Matrixzerlegung für das Merging. Flexibler, aber langsamer.

Beispiel: Ein Adapter für Summarization und ein weiterer für Translation werden zu einem einzelnen Multi-Task-Model zusammengeführt.

Phase 4: Fine-Tuning und Preference Alignment

SFT lernt Demonstrationen. Preference Optimization lernt dagegen aus Vergleichen wie „Chosen Response A ist besser als Rejected Response B“. Verwende sie nur, wenn Paarpräferenzen das richtige Label für den Fehler sind. Faktische Korrektheit und Policy-Konformität erfordern häufig stärkere Evaluators als eine globale Präferenz.

PPO-basiertes RLHF

Das ursprüngliche Rezept war eine Pipeline in drei Phasen:

  1. SFT — die Aufgabe lernen.
  2. Reward Model — auf menschlichen Präferenzen trainieren (Chosen vs. Rejected).
  3. PPO (Proximal Policy Optimization) — Reinforcement Learning zur Optimierung der Policy.

Die operativen Kosten entstehen durch die zahlreichen beweglichen Teile:

  • Komplex in Implementierung und Wartung.
  • Teuer – mehrere Models werden trainiert.
  • On-Policy-Sampling und Reward-Optimierung erfordern sorgfältige Stabilitäts- und Reward-Hacking-Prüfungen.

DPO

DPO (Direct Preference Optimization) entfernt das explizite Reward Model und den RL Loop. Es optimiert weiterhin das RLHF-Objective (Reward-Maximierung mit einer KL-Divergenz-Constraint), tut dies jedoch als reparametrisiertes Supervised-Learning-Problem statt mit Reinforcement Learning:

{
    "prompt": "Explain quantum computing",
    "chosen": "Quantum computing uses qubits...",   # Preferred response
    "rejected": "Well, it's complicated..."        # Non-preferred response
}

Operativ ändert sich Folgendes:

  • Einfacherer Code-Pfad (kein separates Reward Model, kein RL Loop).
  • Ein Offline-Objective über Präferenzpaare statt On-Policy-Reinforcement-Learning.
  • Eine Reference Policy oder äquivalente Reference Log Probabilities in der Standardformulierung.

DPO lässt sich leichter prototypen als eine vollständige PPO-Pipeline, ist aber kein automatisches Qualitäts-Upgrade. Die Ergebnisse hängen von der Starting Policy, der Qualität der Paare, den Loss-Einstellungen, Längeneffekten und dem Eval-Protokoll ab. Vergleiche DPO mit einem SFT-Checkpoint anhand derselben zurückgehaltenen Präferenz- und Task-Suites.

ORPO

ORPO (Odds-Ratio Preference Optimization) kombiniert den SFT Negative-Log-Likelihood-Loss mit einer Odds-Ratio-Penalty für Rejected Responses. Es entfernt das separate Reference Model und kann Task Learning sowie Preference Optimization in einem Run kombinieren.

So funktioniert es: ORPO verwendet einen kombinierten Loss, der zwei Dinge gleichzeitig tut:

  1. Maximiert die Likelihood der Chosen Response (lernt die Aufgabe).
  2. Bestraft die Rejected Response mit einem Odds-Ratio-Term (lernt Präferenzen).

Wichtige Hyperparameter:

from trl import ORPOConfig

config = ORPOConfig(
    learning_rate=8e-6,  # Very low, as recommended by the ORPO paper
    beta=0.1,            # Controls strength of preference penalty
    # ... other params
)
  • Learning Rate: Das Paper verwendete in seinen Experimenten niedrige Werte. Tune sie für dein Model, deinen Batch und deine Daten, statt einen einzelnen Wert als allgemeine Regel zu kopieren.
  • Beta: Steuert den Anteil des Preference-Terms relativ zum SFT-Term.

Der Trade-off:

  • Eine Trainingsphase statt zwei.
  • Kein Reward Model.
  • Kein Forward Pass des Reference Models.
  • Ein gekoppelter Run: Wenn Task Learning oder Preference-Verhalten regressiert, gibt es keinen zwischengeschalteten SFT-Checkpoint aus derselben Pipeline zur Inspektion.

Entscheide anhand von Daten- und Eval-Design:

  • Verwende DPO, wenn du bereits einen zufriedenstellenden SFT-Checkpoint hast und ein einfacheres Offline-Preference-Experiment möchtest.
  • Teste ORPO, wenn ein Reference-freies Objective in einer einzigen Phase zu deinen Daten und operativen Constraints passt.
  • Verwende PPO-basiertes RLHF, wenn Online-Sampling gegen einen explizit gelernten Reward Teil der Anforderungen ist und du Reward Exploitation überwachen kannst.

Keine dieser Methoden ist für alle Tasks ein Default. Behalte eine reine SFT-Baseline und berichte sowohl Task- als auch Preference-Metriken.

Fine-Tuning-Frameworks

Frameworks überschneiden sich und ändern sich schnell. Wähle nach dem Execution Path, den du unterstützen musst, pinne die Versionen und halte die Trainingskonfiguration portabel genug, um sie außerhalb eines Notebooks reproduzieren zu können.

Unsloth — Speed und Speichereffizienz

Unsloth integriert sich in Hugging Face trl und transformers und stellt optimierte Kernels, Checkpointing sowie quantisierte Fine-Tuning-Pfade für unterstützte Models bereit.

  • Eigene Triton-GPU-Kernels für Attention, RoPE und Cross-Entropy, die PyTorch-Overhead vermeiden.
  • Speichereffizientes Backprop, das Activations während des Backward Passes neu berechnet, statt sie im Speicher zu halten.
  • Gefusete Operationen, die mehrere Schritte (Layer Norm + Linear und ähnliche) zu einzelnen GPU-Calls zusammenfassen.
  • 4-Bit-Quantization direkt im QLoRA-Pfad mit optimierter Dequantization.

[!IMPORTANT] Die Import-Reihenfolge ist wichtig Folge für die von dir gepinnte Version der Import-Reihenfolge im Unsloth-Beispiel. Unsloth wendet beim Import Patches an. Daher sollte es vor trl und transformers importiert werden, um fehlende Optimierungen oder versionsspezifische Fehler zu vermeiden.

# Correct order
from unsloth import FastLanguageModel  # Must be first!
from trl import SFTTrainer
from transformers import TrainingArguments

# Avoid this order with Unsloth's patched path
from trl import SFTTrainer
from unsloth import FastLanguageModel

Am besten geeignet für: Training auf einer einzelnen GPU, Prototyping, Colab-Notebooks und alle, die ihre GPU-Kosten im Blick behalten.

Veröffentlichte Speed- und Memory-Werte variieren je nach Model, Sequence Length, Batch, Precision und Hardware. Messe Tokens pro Sekunde und Peak-Speicher in deinem eigenen Run, statt eine Headline-Ratio als Eigenschaft des Frameworks zu betrachten.

Kern des Trainingscodes

from unsloth import FastLanguageModel
from trl import SFTConfig, SFTTrainer

# Load model with 4-bit quantization
model, tokenizer = FastLanguageModel.from_pretrained(
    model_name="nvidia/Llama-3.1-Nemotron-Nano-4B-v1.1",
    max_seq_length=4096,
    load_in_4bit=True,
)

# Add LoRA adapters
model = FastLanguageModel.get_peft_model(
    model,
    r=16,
    lora_alpha=32,
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj",
                    "gate_proj", "up_proj", "down_proj"],
    use_gradient_checkpointing="unsloth",  # Lower activation memory; extra compute
)

# The preceding data step must create these versioned dataset objects.
# Each row has the chat messages and tool schemas expected by current TRL.

# Train with the current TRL configuration surface.
trainer = SFTTrainer(
    model=model,
    processing_class=tokenizer,
    train_dataset=train_dataset,
    eval_dataset=eval_dataset,
    args=SFTConfig(
        output_dir="outputs/nemotron-function-calling",
        max_length=4096,
        packing=True,
        per_device_train_batch_size=2,
        gradient_accumulation_steps=4,
        learning_rate=2e-4,
        num_train_epochs=3,
        bf16=True,
    ),
)
trainer.train()

Phase 5: Evaluation

Byte says

Ich teilte die Zeilen zufällig auf, und das getunte Modell schlug die Basis deutlich. Dann fand ich dasselbe Support-Ticket in beiden Hälften. Ich hatte Zeilen geteilt, obwohl das Ticket die richtige Einheit war.

Lege den Eval Contract vor dem ersten Run fest. Vergleiche mindestens den getunten Checkpoint mit exakt derselben ungetunten Base unter identischem Prompt, denselben Decoding-Einstellungen und derselben Tool-Umgebung. Berichte aggregierte Qualität erst, nachdem du die Failure Slices geprüft hast, die das Projekt verbessern sollte.

Verfolge vier Gruppen:

  1. Ziel-Task: Exact Match, Execution Success, menschliche Rubrik oder ein anderes Ergebnis, das an den Use Case gebunden ist.
  2. Regression: Allgemeine Fähigkeiten und zuvor unterstützte Task-Slices, die durch Adaptation beschädigt werden könnten.
  3. Safety und Policy: Refusals, Data Leakage, Prompt Injection oder domänenspezifische Constraints.
  4. Operations: Latency, Throughput, Speicher, Artefaktgröße und Kosten in der vorgesehenen Serving-Konfiguration.

Automatisierte Benchmarks

Verwende lm-evaluation-harness für relevante standardisierte Tasks, aber nicht als Ersatz für die Product Evaluation:

lm_eval --model hf \
    --model_args pretrained=./outputs/merged-model \
    --tasks hellaswag,arc_easy,mmlu \
    --batch_size 8

LLM-as-Judge

Bei subjektiver Qualität kann ein größeres Model beim Scoring helfen. Kalibriere es jedoch anhand menschlich geprüfter Beispiele und halte die Identität der Kandidaten verborgen:

judge_prompt = """
Rate this response from 1-5 on:
- Relevance
- Accuracy
- Formatting

Response: {model_output}
Expected: {ground_truth}
"""

Domänenspezifische Evaluation

Halte reale Beispiele nach Quelle, User, Dokument oder Zeit zurück, damit keine Near-Duplicates über den Split hinweg leaken können. Validiere bei Function Calling die vollständige Trajectory: Tool-Auswahl, Argumente, Execution Result, Recovery und finale Response. Berichte bei kleinen Samples Confidence Intervals oder gepaarte Win/Loss-Zählungen und prüfe jede Regression in einem kritischen Slice.

Phase 6: Deployment und Output-Formate

Wähle das Artefakt anhand von Serving-Engine und Rollback-Plan, nicht nur anhand der Dateigröße:

1. LoRA-Adapter

uv run finetune  # Saves ~100-500MB adapter
  • Größe: proportional zu Target Modules, Rank, Layern und Dtype; oft deutlich kleiner als die Base.
  • Am besten geeignet für: Entwicklung, versionierte Task-Adapter und Engines mit direkter LoRA-Unterstützung.
  • Vorteil: Adapter können ausgetauscht werden, ohne das Base Model erneut herunterzuladen.

2. Merged Model

uv run finetune --merge  # Creates a standalone full model
  • Größe: ungefähr die Größe des vollständigen Base Checkpoints in der gewählten Output-Precision.
  • Am besten geeignet für: Engines oder Distribution Paths, die den Adapter nicht separat unterstützen.
  • Trade-off: Größeres Artefakt und langsameres Rollout, dafür einfacheres Laden eines einzelnen Models.

3. GGUF-Format

uv run finetune --gguf q4_k_m  # Creates ~2-4GB quantized model
  • Größe: abhängig vom Model; bei Q4-Varianten ungefähr 4-Bit-Weights plus Metadaten.
  • Am besten geeignet für: CPU-Inference, Ollama, llama.cpp und Edge-Deployment.
  • Optionen: q4_k_m (kleiner), q5_k_m (höhere Weight-Treue), q8_0 (größer und höhere Treue). Messe die Auswirkungen auf die Task nach der Konvertierung.

Das ausgerollte Model überwachen

Der Lifecycle endet nicht bei einem gesunden Training Loss. Erfasse Base-Model-Revision, Tokenizer und Chat Template, Adapter-Hash, Dataset-Version, Trainingskonfiguration und Eval-Report als eine gemeinsame Release-Einheit. Überwache in Production Task Success, ungültige Outputs, Policy-Verstöße, Latency und Input Drift anhand derselben Slices wie offline. Halte das vorherige Artefakt ladbar und definiere vor dem Launch einen Rollback-Schwellenwert.

Zentrale Erkenntnisse

  1. Führe Fine-Tuning erst durch, wenn eine ungetunte Baseline und eine Failure Taxonomy zeigen, dass Weight Adaptation das Problem adressiert.
  2. Retrieval verwaltet veränderliche Evidenz; Constrained Decoding verwaltet Syntax. Beides wird durch SFT nicht ersetzt.
  3. LoRA reduziert den trainierbaren State. QLoRA komprimiert zusätzlich die eingefrorenen Base Weights. Ordne QLoRA-Speicherwerte nicht LoRA zu.
  4. Datenabdeckung, Split-Integrität, Provenance und Loss Masking sind wichtiger, als eine aktuelle Optimizer-Konfiguration zu kopieren.
  5. DPO, ORPO und PPO-basiertes RLHF sind unterschiedliche Experimentdesigns, keine Qualitätsleiter mit einem universellen Default.
  6. Evaluiere Zielverhalten, Regressionen, Safety und Operations anhand desselben Base Models.
  7. Wähle Adapter-, Merged- oder GGUF-Output anhand der Serving- und Rollback-Anforderungen, bevor du trainierst.
