Leitfaden zur Feinabstimmung von LLMs: LoRA, QLoRA, DoRA, Unsloth, Axolotl und Bereitstellung

Die meisten Misserfolge bei der Feinabstimmung resultieren aus Fehlentscheidungen. Ein Team trainiert, ohne zunächst nachzuweisen, dass Prompting, Retrieval oder Constrained Decoding das Problem lösen können, bewertet die Ergebnisse auf der Trainingsdatenbasis oder stellt nach dem Training fest, dass das resultierende Modell schwer zu bereitstellen ist.

Dieser Leitfaden betrachtet die Anpassung als Experiment mit einem definierten Ausstiegspunkt. Er beginnt mit der Entscheidungsgrenze und folgt anschließend einem Weg durch Datenverarbeitung, den Einsatz von LoRA oder QLoRA, spezifische Aufgabenevaluation, Export sowie Bereitstellung des Modells.

Zusammenfassung: Führen Sie eine Feinabstimmung durch, wenn eine gemessene Baseline zeigt, dass eine Änderung des Modellverhaltens eine Aktualisierung der Gewichte rechtfertigt. Verwenden Sie Retrieval zur Änderung von Fakten und Constrained Decoding für syntaktische Anpassungen. Beginnen Sie mit LoRA, wenn das Basismodell problemlos passt; nutzen Sie QLoRA, wenn die Einschränkung in der Nutzung von gefrorenen Gewichten besteht. Behalten Sie vor dem Training einen Evaluationsdatensatz zurück, vergleichen Sie ihn mit der unangepassten Baseline und wählen Sie das finale Bereitstellungsformat, bevor Sie sich für eine Methode entscheiden.

Sollte man überhaupt feinabstimmen?

Bevor Sie GPU-Zeit investieren, entscheiden Sie zunächst, ob die Feinabstimmung das geeignete Mittel für das vorliegende Problem darstellt.

Feinabstimmung versus RAG

Durch Feinabstimmung kann sich die Art und Weise ändern, wie ein Modell Fachsprache verwendet, doch sie eignet sich nur unzureichend zur Aktualisierung von Fakten, die sich ändern oder zitiert werden müssen. Retrieval und Feinabstimmung adressieren unterschiedliche Aspekte des Problems und gehören oft zum selben System.

Feinabstimmung versus Constrained Decoding

Bibliotheken wie xgrammar und outlines beschränken die Generierung auf ein JSON-Schema, eine reguläre Ausdrucksregel oder eine Grammatik. Je nach Konstraint und Backend werden dabei ein Automat oder eine Grammatik kompiliert, wodurch ungültige Folgetoken maskiert werden. Es ist keine Gewichtsanpassung erforderlich.

Dies garantiert lediglich, dass die Ausgabe im unterstützten Sprachrahmen liegt – nicht jedoch, dass die Werte wahr, vollständig oder semantisch angemessen sind. Eine syntaktisch korrekte Funktionsaufruf kann dennoch eine falsche Kunden-ID enthalten.

Eine praktische Vorgehensweise:

  1. Beginnen Sie mit Prompting sowie wenigen Beispielen zur Grundformatierung.
  2. Fügen Sie bei inkonsistenten Syntaxen eine Constrained Decoding (xgrammar oder outlines) hinzu.
  3. Wenden Sie Feinabstimmung nur dann an, wenn Verhaltensänderungen nötig sind, die durch ein Schema nicht erzwungen werden können.

Den wirtschaftlichen Nutzen messbar machen

Fine-Tuning kann die Anzahl wiederkehrender Prompt-Token reduzieren oder es ermöglichen, dass ein kleineres Modell die Zielvorgaben erfüllt, doch keiner dieser Vorteile tritt automatisch ein. Berechnen Sie den Break-Even-Punkt anhand Ihres eigenen Traffic und Ihrer Preisstruktur:

[ \text{Break-Even-Anfragen} = \frac{\text{Kosten für Training + Evaluation + Deployment}} {\text{Baseline-Kosten pro Anfrage} - \text{Kosten nach Fine-Tuning pro Anfrage}} ]

Ist der Nenner klein, negativ oder basiert auf einer ungesicherten Qualitätsannahme, dann gibt es noch keinen wirtschaftlichen Grund für das Projekt.

Betrachten Sie das größere, promptgesteuerte Modell als Baseline und behalten Sie das kleinere Modell nur bei, wenn es dieselben qualitativen und sicherheitstechnischen Schwellenwerte wie das Basismodell erfüllt.

Arten des Fine-Tunings

Es gibt drei Hauptformen des Fine-Tunings. Sie unterscheiden sich dadurch, welche Art von Daten benötigt wird und was dem Modell vermittelt wird.

1. Fortgesetztes Unsupervised Pretraining

Sie trainieren das Basismodell mit weiterem Rohtext ohne Labels. Es führt weiterhin Vorhersagen für den nächsten Token durch, genauso wie während des ursprünglichen Pretraining-Prozesses.

Wann verwenden?

  • Der Bereich weist ein Vokabular auf, das das Basismodell noch nie gesehen hat (Medizin, Recht, interne Codebasen).
  • Sie verfügen über große Mengen an Branchentexten, aber keine gelabelten (Eingang, Ausgang)-Paare.
  • Das Basismodell hat Schwierigkeiten mit branchenspezifischer Terminologie.

Beispiel: Training mit Millionen von klinischen Notizen, damit das Modell medizinische Abkürzungen, Medikamentennamen sowie klinische Arbeitsabläufe erkennt.

2. Supervised Fine-Tuning (SFT)

SFT wird mit gelabelten (Eingang, Ausgang)-Paaren trainiert. Sie zeigen dem Modell genau die Ausgabe, die Sie für jeden Eingang erwarten.

Wann verwenden?

  • Sie haben eine spezifische Aufgabe mit einem klaren Eingang/Ausgang-Format.
  • Sie verfügen über qualitativ hochwertige, gelabelte Daten – auch in geringer Menge.
  • Sie benötigen vorhersehbares Verhalten für einen bekannten Eingabestil.

Beispiel: Training mit Paaren aus (SQL-Abfragedescript, SQL-Code) für Text-zu-SQL-Umsetzungen.

{
    "input": "Get all users who signed up last month",
    "output": "SELECT * FROM users WHERE signup_date >= DATE_SUB(NOW(), INTERVAL 1 MONTH)"
}

3. Anpassung an Anweisungen

Die Anpassung an Anweisungen ist ein Spezialfall des SFT und dient dazu, Modelle dazu zu bringen, einer Vielzahl natürsprachlicher Anweisungen zu folgen. Die Trainingsdaten bestehen aus Paaren aus Anweisung und Antwort für viele verschiedene Aufgaben.

Wann wird sie eingesetzt?

  • Wenn man einen universellen Assistenten benötigt (wie ChatGPT oder Claude).
  • Wenn das Modell mit vielfältigen, offenen Anfragen umgehen muss.
  • Wenn eine Chat-Schnittstelle entwickelt wird.

Beispiel: Training mit Tausenden unterschiedlicher Anweisungen wie „Zusammenfassen Sie diesen Artikel“, „Schreiben Sie ein Gedicht über X“ oder „Erklären Sie Y in einfachen Worten“.

Das kontinuierliche Vortrainieren ist ein eigenständiges Experiment, dem Tests sowohl hinsichtlich fachlicher Verbesserungen als auch bezüglich möglicher Rückgänge der allgemeinen Fähigkeiten folgen sollten.

Der 7-stufige Fine-Tuning-Pipeline

Fine-Tuning ist ein Pipeline-Prozess, kein einzelner Befehl. Jede Stufe weist eigene Fehlermöglichkeiten auf, und das Überspringen einer Stufe führt in der Regel später zu einem schlechten Modell.

Jede Stufe baut auf der vorherigen auf:

  1. Datenvorbereitung – Definition der Bewertungseinheit, Aufteilung der Daten sowie Reinigung und Formatierung derselben.
  2. Modellwahl – Auswahl des geeigneten Basismodells sowie Laden der Gewichte.
  3. Trainingskonfiguration – Einrichtung der Hardware, Hyperparameter sowie der Optimierungsstrategie.
  4. Fine-Tuning – Durchführung von SFT-, DPO- oder ORPO-Trainingsprozessen.
  5. Bewertung – Messung der Leistung anhand von Benchmarks sowie Überprüfung der Qualität.
  6. Einsatz – Export und Bereitstellung des Modells.
  7. Überwachung – Erfassung der Leistung, Wartung sowie iterative Verbesserungen.

[!WARNING] Daten sind die Grundlage Das Training reproduziert systematische Mängel in den Beispielen. Prüfen Sie vor dem Einsatz von Optimierern Etiketten, Datenlecks, Deckung sowie die Einhaltung von Richtlinien.

Stufe 1: Datenvorbereitung

Die meisten Fine-Tuning-Projekte scheitern hier, nicht beim Training. Moderne Datenvorbereitung umfasst mehr als nur das Durchlaufen von Regulären Ausdrücken in CSV-Dateien.

Der 5-stufige Datenpipeline

Tools wie DataTrove und Distilabel können bei großen Skalen helfen, doch der Pipeline-Prozess sollte eher durch die Fehlerklassifikation und den Datenvertrag gesteuert werden als durch einen bevorzugten Tool.

1. Eingabe und Filterung

  • Maßnahme: Ablehnungen (“Ich kann darauf nicht antworten”), beschädigte UTF-8-Daten sowie Sprachen außerhalb des Zielspektrums entfernen.
  • Tools: Trafilatura zur Extraktion, FastText zur Bestimmung der Sprache.

2. Richtlinie für sensible Daten

  • Maßnahme: Bestimmen, welche Informationen das Modell lernen darf, und ggf. personenbezogene sowie vertrauliche Felder entfernen, tokenisieren oder ausschließen.
  • Werkzeuge: Microsoft Presidio oder Scrubadub.
  • Grund: Ein Detektor stellt lediglich eine Kontrollmaßnahme dar; weiterhin gelten Anforderungen hinsichtlich Herkunft, Einwilligung, Aufbewahrung, Zugriff und Löschung.

3. Duplikatentfernung (MinHash LSH)

  • Maßnahme: Nahezu identische Datensätze entfernen, damit das Modell sie nicht speichert.
  • Werkzeuge: DataTrove eignet sich hervorragend für die Verarbeitung von Terabytes an Daten.

4. Synthetische Erweiterung bei Bedarf

  • Maßnahme: Ein leistungsstärkeres Lehrmodell (z. B. GPT-4o, DeepSeek-V3) verwenden, um Rohdaten in saubere „Anweisung‑Antwort“-Paare umzuwandeln.
  • Werkzeuge: Distilabel.
  • Validierung: Auswahlpunkte aus den Lehrmodell-Ausgaben prüfen, diese gegen dieselben Kriterien wie menschliche Labels bewerten und synthetisch erzeugte sowie menschlich verfasste Beispiele bei der Bewertung getrennt halten.

5. Formatierung

  • Maßnahme: In ein Standardformat überführen (Alpaca oder ShareGPT).

Beispiele für Datensatzformate

Alpaca-Format (Anweisungsfolge):

{
    "instruction": "Summarize the following text.",
    "input": "The text to be summarized...",
    "output": "This is the summary."
}

ShareGPT/ChatML-Format (Konversation):

{
    "conversations": [
        { "from": "user", "value": "Hello, who are you?" },
        { "from": "assistant", "value": "I am a helpful AI assistant." }
    ]
}

Was tatsächlich entscheidend ist

  • Zuvor Abdeckung als Voraussetzung für Menge. Beispiele solcher Fälle hinzufügen, die unterschiedliche Fehlermuster darstellen, statt nur wiederholte einfache Fälle.
  • Sauberkeit: Unrelevante Texte entfernen, Leerzeichen normalisieren und die Formatierung konsequent beibehalten.
  • Ausgewogenheit: Wichtige, seltene Fälle erhalten bleiben, und die Leistung pro Datensatzsegment wird dokumentiert.
  • Trennung: Bei zufälliger Aufteilung von Datensätzen, die zu Duplikaten führen könnten, nach Quelle, Benutzer, Dokument oder Zeit trennen.
  • Herkunftsverfolgung: Für jede Version des Datensatzes Quelle, Lizenz oder Genehmigung, Transformationshistorie sowie Löschweg erfassen.

Phase 2: Auswahl des Modells und Hardware

Die Wahl des Basismodells sowie das Verständnis der technischen Grenzen der GPU bestimmen, was tatsächlich trainiert werden kann. Beginnen Sie mit dem kleinsten Basismodell, das bereits die unverzichtbaren Basisprüfungen besteht. Überprüfen Sie dabei:

  • Lizenz- und Weiterverbreitungsbedingungen für das geplante Produkt;
  • Sprache, Anwendungsbereich, Tool‑Use‑Fähigkeiten sowie Sicherheitsverhalten vor der Anpassung;
  • Kompatibilität des Tokenizers sowie der Chat‑Templates mit dem Datensatz;
  • maximale Kontextlänge sowie Trunkierungsverhalten, wie es in realen Beispielen erforderlich ist;
  • Unterstützung sowohl im Trainingssystem als auch im Ziel‑Serving‑Engine. Fine‑Tuning dient lediglich der Anpassung und nicht der Behebung eines ungeeigneten Basismodells. Falls das Modell Fähigkeiten vermissen lässt, die vom Datensatz nicht abgedeckt werden, wählen Sie vor dem Sammeln weiterer Trainingszyklen ein anderes Basismodell.

Größe der Trainingssitzung – nicht Marketingklasse

Es existiert keine stabile Tabelle „Modellgröße → GPU“. Die maximale Speichernutzung hängt von der Gewichtspräzision, dem Optimierer, der Anzahl der trainierbaren Parameter, der Sequenzlänge, der Größe der Mikrobatches, der Aktivierungs‑Checkpointing‑Strategie, der Implementierung von Attention‑Mechanismen sowie den Overhead‑Kosten des Frameworks ab. Beginnen Sie mit einer Schätzung des benötigten Speichers und führen anschließend einen kurzen Test mit maximaler Sequenzlänge unter Verwendung genau dieser Technologie‑Stacks durch.

Der ursprüngliche QLoRA‑Artikel führte ein 65 B großes LLaMA‑Modell in seiner spezifischen Konfiguration auf einer einzigen 48 GB‑GPU aus. Dieses Ergebnis stellt eine nützliche Obergrenze dar, nicht jedoch eine Garantie dafür, dass jede aktuelle 70 B‑Architektur, jede Kontextlänge, jedes Kernel‑Design oder jeder Trainer auf denselben Gerätetyp passt.

Speichermathematik

Für ein Modell mit (P) Parametern benötigen allein die Schwerwerte in BF16/FP16 etwa (2P) Bytes bzw. bei vier Bit etwa (0{,}5P) Bytes – noch bevor Metadaten zur Quantisierung sowie Laufzeitpuffer hinzukommen. Ein vollständiges Adam‑basiertes Training fügt zusätzlich Gradienten, Optimierer‑Zustände sowie oft Schwerwerte in höherer Präzision hinzu. LoRA vermeidet den Großteil des Speichers für trainierbare Zustände; QLoRA verringert darüber hinaus den Speicherbedarf der gefrorenen Basisschwerwerte. Bei langen Sequenzen können die Aktivierungen weiterhin einen großen Anteil am Gesamtspeicher ausmachen.

Verwenden Sie diesen Ablauf:

  1. Wählen Sie die längste Sequenz sowie den kleinsten Micro‑Batch, den Sie unterstützen müssen.
  2. Schätzen Sie den Bedarf an Schwerwerten und trainierbaren Zuständen ein und lassen Sie dabei Puffer für Aktivierungen und Kernels frei.
  3. Führen Sie einen Vorwärts-/Rückwärts‑Schritt bei maximaler Länge aus.
  4. Erfassen Sie den maximalen belegten sowie reservierten Speicher.
  5. Erst danach skalieren Sie Batch‑Größe, Modell‑Rank, Sequenzlänge oder Anzahl der GPUs.

Phase 3: Trainingsmethoden (PEFT und LoRA)

Vollständiges Feintuning gegenüber PEFT

Beim vollständigen Feintuning (FFT) werden alle Schwerwerte aktualisiert, wodurch Gradienten und Optimierer‑Zustände im Verhältnis zum gesamten Modell wachsen. Die maximale Speichernutzung lässt sich nicht allein aus der Anzahl der Parameter ableiten; sie liegt jedoch deutlich über dem Speicherbedarf, der lediglich zum Laden der Schwerwerte für die Inferenz erforderlich ist.

Beim parametereffizienten Feintuning (PEFT) werden nur ein kleiner Teil der Parameter trainiert, während der Rest gefroren bleibt. Dadurch wird die Berechnung erheblich einfacher.

LoRA: Der Ausgangspunkt

LoRA (Low‑Rank Adaptation) gefriert eine vortrainierte Matrix und repräsentiert deren gelernte Anpassung durch zwei kleinere Matrizen. Der ursprüngliche Artikel begründet dies damit, dass nützliche Anpassungsupdates einen niedrigen intrinsischen Rang aufweisen.

Für eine gefrorene Matrix (W_0 \in \mathbb{R}^{d_{out} \times d_{in}}) lernt LoRA:

  • (A \in \mathbb{R}^{r \times d_{in}})
  • (B \in \mathbb{R}^{d_{out} \times r})

Die angepasste Schicht lautet dann:

[ W’ = W_0 + \frac{\alpha}{r}BA ]

Der Adapter weist somit (r(d_{in}+d_{out})) trainierbare Parameter auf, anstatt die (d_{in}d_{out}) Parameter der ursprünglichen Matrix. Bei einer quadratischen Matrix mit 4.096 Elementen und Rang 16 ergibt sich eine Reduzierung um das 128‑Fache – und nicht das 10.000‑Fache wie in der ursprünglichen LoRA‑Darstellung für ein beliebiges Modell. Der in dem Paper genannte Faktor 10.000 bezog sich auf eine spezifische GPT‑3‑175 B‑Konfiguration, bei der ausgewählte Matrizen angepasst wurden.

Wann welche Methode gewählt werden sollte

  • LoRA: Hier beginnen. Schnell, memorieneffizient und gut unterstützt.
  • QLoRA: Wenn das gleiche LoRA-Experiment aufgrund gefrorener Basismodellgewichte nicht funktioniert.
  • DoRA: Nachdem ein direkter LoRA-Vergleich einen nützlichen Vorteil zeigt.
  • Vollständiges Feintuning: Nur dann, wenn PEFT als echter Engpass nachgewiesen wurde und nicht nur als Annahme gilt.

DoRA: Gewichtstrennende LoRA

DoRA (Weight-Decomposed Low-Rank Adaptation) trennt die Stärke jedes Gewichtsvektors von seiner Richtung. Es wird eine LoRA-Update-Anwendung auf den Richtungskomponenten vorgenommen, während die Stärke separat gelernt wird.

Funktionsweise:

Anstatt die Gewichte als einzige Einheit zu behandeln, teilt DoRA die vortrainierten Gewichte in zwei Komponenten auf:

  1. Stärke – ein trainierbarer Wert pro Gewichtsvektor.
  2. Richtung – ein normalisierter Vektor, der über niederrangige Matrizen aktualisiert wird.

In kompakter Spaltennotation:

[ W’ = m \frac{V + BA}{\lVert V + BA \rVert_c} ]

wobei:

  • m = Stärke (trainierbar)
  • (V) = die gefrorene Richtungsmatrix
  • (BA) = der erlernte niederrangige Richtungsupdate
  • (\lVert \cdot \rVert_c) = Spaltennormalisierung

Vorteile dieser zusätzlichen Struktur:

  • Mehr Freiheitsgrade im Vergleich zu herkömmlicher LoRA, da sich die Stärke unabhängig ändern kann.
  • Bessere Ergebnisse als bei LoRA in mehreren vom Verfasserpapier beschriebenen Konfigurationen.
  • Mehr Parameter und Rechenaufwand; daher muss der Nutzen für die eigene Aufgabe sowie den jeweiligen Bereitstellungsweg überprüft werden.

Adapter-Kombination für Multi-Task-Lernen

Getrennte Adapter ermöglichen es, ein einziges gefrorenes Basismodell für mehrere Aufgaben zu nutzen. Man kann Anfragen an einen Adapter leiten, mehrere Adapter über denselben Engine bereitstellen, falls möglich, oder einen offline kombinierten Kandidaten erstellen. Die Kombination kann zu Interferenzen führen; daher sollte das resultierende Modell bewertet werden, anstatt davon auszugehen, dass die Quelladapter sauber zusammenarbeiten.

Gängige Kombinationsmethoden:

  1. Kombination – Vereinigung der Adapterparameter und Erhöhung des effektiven Rangs. Schnell und einfach.
  2. Lineare Kombination – Gewichtete Summe der Adapter. Bietet Anpassungsmöglichkeiten.
  3. SVD – Matrixzerlegung zur Kombination. Flexibler, aber langsamer.

Beispiel: Ein Adapter für Zusammenfassung, ein weiterer für Übersetzung, die zu einem einzigen Multi-Task-Modell kombiniert werden.

Phase 4: Fine-Tuning und Abstimmung von Präferenzen

SFT lernt anhand von Demonstrationen. Die Präferenzoptimierung hingegen nutzt Vergleiche wie „die gewählte Antwort A ist besser als die abgelehnte Antwort B“. Sie sollte nur eingesetzt werden, wenn paarebasierte Präferenzen als geeigneter Fehlerindikator dienen; für faktenbasierte Korrektheit und Einhaltung von Richtlinien sind oft stärkere Bewertungsmethoden erforderlich als eine globale Präferenzangabe.

PPO-basierte RLHF

Die ursprüngliche Vorgehensweise bestand aus einem dreistufigen Pipeline:

  1. SFT – Lernen der Aufgabe.
  2. Belohnungsmodell – Training anhand menschlicher Präferenzen (gewählt vs. abgelehnt).
  3. PPO (Proximal Policy Optimization) – Verstärkungslernen zur Optimierung der Strategie.

Die operativen Herausforderungen liegen in den beweglichen Komponenten:

  • Schwierige Implementierung und Wartung.
  • Hohe Kosten – mehrere Modelle müssen trainiert werden.
  • Beim On-Policy-Sampling sowie bei der Belohnungsoptimierung sind sorgfältige Überprüfungen bezüglich Stabilität und möglicher Belohnungsbetrug erforderlich.

DPO

DPO (Direct Preference Optimization) verzichtet auf ein explizites Belohnungsmodell sowie den RL-Loop. Es optimiert weiterhin das RLHF-Ziel (Maximierung der Belohnung unter Berücksichtigung einer KL-Divergenz-Beschränkung), doch dies geschieht als umparameterisiertes überwachtes Lernproblem statt mittels Verstärkungslernen:

{
    "prompt": "Explain quantum computing",
    "chosen": "Quantum computing uses qubits...",   # Preferred response
    "rejected": "Well, it's complicated..."        # Non-preferred response
}

Operative Änderungen:

  • Einfacherer Codepfad (kein separates Belohnungsmodell, kein RL-Loop).
  • Offline-Ziel basierend auf Präferenzpaaren statt On-Policy-Verstärkungslernen.
  • In der Standardformulierung ein Referenzmodell oder äquivalente Referenzlogwahrscheinlichkeiten.

DPO lässt sich leichter prototypisieren als ein vollständiger PPO-Pipeline, stellt jedoch keine automatische Qualitätsverbesserung dar. Die Ergebnisse hängen von der Ausgangsstrategie, der Qualität der Paare, den Verlusteinstellungen, Längeneffekten sowie dem Bewertungsprotokoll ab. Vergleichen Sie es mit einem SFT-Checkpoint auf denselben getrennten Präferenz- und Aufgabensätzen.

ORPO

ORPO (Odds-Ratio Preference Optimization) kombiniert den negativen Log-Likelihood-Verlust von SFT mit einer Odds-Ratio-Bestrafung für abgelehnte Antworten. Dadurch entfällt ein separates Referenzmodell, und Aufgabenerlernen sowie Präferenzoptimierung können in einem einzigen Durchlauf erfolgen.

Funktionsweise: ORPO verwendet einen kombinierten Verlust, der gleichzeitig zwei Aufgaben erledigt:

  1. Maximierung der Wahrscheinlichkeit der gewählten Antwort (Lernen der Aufgabe).
  2. Bestrafung der abgelehnten Antwort mittels eines Odds-Ratio-Terms (Lernen von Präferenzen).

Wichtige Hyperparameter:

from trl import ORPOConfig

config = ORPOConfig(
    learning_rate=8e-6,  # Very low, as recommended by the ORPO paper
    beta=0.1,            # Controls strength of preference penalty
    # ... other params
)
  • Lernrate: In den Experimenten des Papers wurden niedrige Werte verwendet; justieren Sie sie anhand Ihres Modells, der Batch-Größe und der Daten, anstatt einfach einen Wert als Regel zu übernehmen.
  • Beta: Steuert den Anteil des Präferenzterms im Verhältnis zum SFT-Term.

Der Kompromiss:

  • Nur eine Trainingsphase statt zweier.
  • Kein Belohnungsmodell.
  • Keine Vorwärtsberechnung eines Referenzmodells.
  • Koppelter Durchlauf: Sollte das Aufgabenerlernen oder das Präferenzverhalten zurückgehen, gibt es keinen Zwischen-Checkpoint aus derselben Pipeline zur Überprüfung.

Entscheiden Sie anhand der Daten und des Bewertungsdesigns:

  • Wählen Sie DPO, wenn Sie bereits einen zufriedenstellenden SFT-Checkpoint haben und ein einfacheres Offline-Präferenzexperiment wünschen.
  • Testen Sie ORPO, wenn ein referenzfreies, einstufiges Ziel zu Ihren Daten und operativen Einschränkungen passt.
  • Verwenden Sie PPO-basierte RLHF, wenn Online-Sampling gegenüber einem explizit gelernten Belohnungssystem erforderlich ist und Sie die Ausnutzung der Belohnung überwachen können.

Keine Methode ist für alle Aufgaben standardmäßig geeignet. Behalten Sie einen reinen SFT-Baseline bei und berichten Sie sowohl über Aufgabemetriken als auch über Präferenzmetriken.

Frameworks für Fine-Tuning

Die verfügbaren Frameworks überschneiden sich stark und entwickeln sich rasant weiter. Wählen Sie eines entsprechend dem zu unterstützenden Ausführungspfad, fixieren Sie die Versionen und stellen Sie sicher, dass die Trainingskonfiguration ausreichend portabel ist, um auch außerhalb von Notebook-Umgebungen reproduziert werden zu können.

Unsloth – Geschwindigkeit und Speichereffizienz

Unsloth integriert sich mit Hugging Face trl sowie transformers und bietet optimierte Kernel, Checkpoint-Funktionen sowie quantisierte Fine-Tuning-Pfade für unterstützte Modelle.

  • Benutzerdefinierte Triton-GPU-Kernel für Attention, RoPE und Cross-Entropy, die den Overhead von PyTorch umgehen.
  • Speichereffizientes Backpropagation, das Aktivierungen während des Rückwärtspasses erneut berechnet, anstatt sie im Speicher zu halten.
  • Verschmolzene Operationen, die mehrere Schritte (z. B. Layer Norm + Linear) in einen einzigen GPU-Aufruf zusammenfassen.
  • 4-Bit-Quantisierung, die direkt in den QLoRA-Pfad integriert ist und eine optimierte Dekodierung bietet.

[!WICHTIG] Die Reihenfolge der Importe ist entscheidend Befolgen Sie die im Unsloth-Beispiel angegebene Reihenfolge der Importe für die festgelegte Version. Unsloth wendet während des Imports Patches an; daher vermeiden Sie durch Import vor trl und transformers fehlende Optimierungen oder versionsspezifische Fehler.

# ✅ Correct order
from unsloth import FastLanguageModel  # Must be first!
from trl import SFTTrainer
from transformers import TrainingArguments

# Avoid this order with Unsloth's patched path
from trl import SFTTrainer
from unsloth import FastLanguageModel

Am besten geeignet für: Training auf einem einzelnen GPU, Prototypenentwicklung, Colab-Notebooks sowie alle, die die GPU-Kosten im Auge behalten müssen. Die angegebenen Werte für Geschwindigkeit und Speicherverbrauch variieren je nach Modell, Sequenzlänge, Batch-Größe, Präzision und Hardware. Messen Sie selbst die Anzahl der Tokens pro Sekunde sowie den maximalen Speicherverbrauch in Ihren Tests, anstatt sich auf allgemeine Angaben zu verlassen.

Rank, Alpha, Lernrate sowie Zielmodule sollten erst nach Festlegung der Daten und des Basismodells überprüft werden.

Kern-Trainingscode

from unsloth import FastLanguageModel
from trl import SFTConfig, SFTTrainer

# Load model with 4-bit quantization
model, tokenizer = FastLanguageModel.from_pretrained(
    model_name="nvidia/Llama-3.1-Nemotron-Nano-4B-v1.1",
    max_seq_length=4096,
    load_in_4bit=True,
)

# Add LoRA adapters
model = FastLanguageModel.get_peft_model(
    model,
    r=16,
    lora_alpha=32,
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj",
                    "gate_proj", "up_proj", "down_proj"],
    use_gradient_checkpointing="unsloth",  # Lower activation memory; extra compute
)

# The data step creates versioned train_dataset and eval_dataset objects.
# Each row has the chat messages and tool schemas expected by current TRL.

# Train with the current TRL configuration surface.
trainer = SFTTrainer(
    model=model,
    processing_class=tokenizer,
    train_dataset=train_dataset,
    eval_dataset=eval_dataset,
    args=SFTConfig(
        output_dir="outputs/nemotron-function-calling",
        max_length=4096,
        packing=True,
        per_device_train_batch_size=2,
        gradient_accumulation_steps=4,
        learning_rate=2e-4,
        num_train_epochs=3,
        bf16=True,
    ),
)
trainer.train()

Phase 5: Bewertung

Erfrieren Sie den Bewertungsvertrag vor dem ersten Ausführungsvorgang. Vergleichen Sie mindestens den angepassten Checkpoint mit dem exakt unangepassten Basismodell unter denselben Prompt-Einstellungen, Dekodierungsparametern sowie Tool-Umgebung. Berichten Sie nur über die Gesamtbewertung, nachdem Sie geprüft haben, ob die Fehlerfälle tatsächlich verbessert wurden.

Folgende vier Gruppen sollten erfasst werden:

  1. Zielaufgabe: exakte Übereinstimmung, Erfolgsgrad der Ausführung, menschliche Bewertungskriterien oder weitere mit dem Anwendungsfall verbundene Ergebnisse.
  2. Regression: allgemeine Fähigkeiten sowie zuvor unterstützte Aufgabentypen, die durch Anpassungen beeinträchtigt werden könnten.
  3. Sicherheit und Richtlinien: Ablehnungen, Datenlecks, Prompt-Injection-Vorfälle oder domänenspezifische Einschränkungen.
  4. Betriebsaspekte: Latenz, Durchsatz, Speicherverbrauch, Größe der Erzeugnisse sowie Kosten bei der vorgesehenen Bereitstellungskonfiguration.

Automatisierte Benchmarks

Verwenden Sie lm-evaluation-harness für relevante standardisierte Aufgaben – jedoch nicht als Ersatz für die eigentliche Produktbewertung:

lm_eval --model hf \
    --model_args pretrained=./outputs/merged-model \
    --tasks hellaswag,arc_easy,mmlu \

LLM als Bewertungsinstanz

Für subjektive Qualität kann ein größeres Modell bei der Bewertung helfen, muss jedoch anhand von von Menschen überprüften Beispielen kalibriert werden, wobei die Identität des Kandidaten verdeckt bleiben sollte:

judge_prompt = """
Rate this response from 1-5 on:
- Relevance
- Accuracy
- Formatting

Response: {model_output}
Expected: {ground_truth}
"""

Domänenspezifische Bewertung

Halten Sie echte Beispiele nach Quelle, Benutzer, Dokument oder Zeit getrennt, damit nahezu identische Beispiele nicht zwischen den Gruppen austauschen können. Bei Function Calling müssen die gesamte Ablaufkette überprüft werden: Auswahl des Tools, Übermittlung der Argumente, Ausführungsergebnis, Wiederherstellung sowie endgültige Antwort. Bei kleinen Stichproben sollten Konfidenzintervalle oder Paarungen aus Gewinn/Niederlage berichtet werden, und jede Regression in kritischen Bereichen muss genauestens analysiert werden.

Phase 6: Bereitstellung und Ausgabeformate

Wählen Sie das passende Erzeugnis basierend auf dem Bereitstellungsmechanismus und dem Rollback-Plan – und nicht ausschließlich auf der Dateigröße:

1. LoRA-Adapter

uv run finetune  # Saves ~100-500MB adapter
  • Größe: proportional zu den Zielmodulen, Rank-Werten, Schichten sowie dem Datentyp; in der Regel deutlich kleiner als das Basismodell.
  • Am besten geeignet für: Entwicklung, versionierte Aufgabentransformer sowie Engines, die LoRA direkt unterstützen.
  • Vorteil: Adapter können ohne Neuherunterladen des Basismodells ausgetauscht werden.

2. Verschmolzenes Modell

uv run finetune --merge  # Creates a standalone full model
  • Größe: etwa gleich dem vollständigen Basismodell-Checkpoint bei der gewählten Ausgabengenauigkeit.
  • Am besten geeignet für: Engines oder Vertriebswege, die den Adapter nicht separat unterstützen.
  • Nachteil: größeres Erzeugnis und langsamere Einführung; einfacheres Laden eines einzigen Modells.

3. GGUF-Format

uv run finetune --gguf q4_k_m  # Creates ~2-4GB quantized model
  • Größe: abhängig vom jeweiligen Modell; in der Regel vier Bit pro Gewichtsknoten plus Metadaten für die Q4-Varianten.
  • Am besten geeignet für: Inferenz auf CPU, Nutzung von Ollama, llama.cpp sowie Edge-Deployment.
  • Optionen: q4_k_m (kleinerer Umfang), q5_k_m (höhere Gewichtstreue), q8_0 (größerer Umfang und höhere Treue). Der Einfluss dieser Optionen auf die Aufgabenergebnisse sollte nach der Konvertierung gemessen werden.

Überwachung des bereitgestellten Modells

Der Lebenszyklus endet nicht bereits bei einem akzeptablen Trainingsverlust. Als eine einzige Veröffentlichungseinheit sollten die Version des Basismodells, der Tokenizer sowie das Chat-Template, der Hash des Adapters, die Versionsnummer des Datensatzes, die Trainingskonfiguration und der Bewertungsbericht erfasst werden. In der Produktion müssen Task-Erfolge, ungültige Ausgaben, Richtlinienfehler, Latenzzeiten sowie Eingabeveränderungen mithilfe derselben Messkriterien wie im Offline-Betrieb überwacht werden. Zudem muss sichergestellt werden, dass ältere Versionen weiterhin ladenbar sind, und ein Rollback-Threshold vor dem Start festgelegt werden.

Wichtige Erkenntnisse

  1. Führen Sie nur dann Feintuning durch, wenn eine unangepasste Baseline sowie eine Fehlerklassifizierung zeigen, dass eine Anpassung der Gewichte das Problem löst.
  2. Die Retrieval-Methode kümmert sich um sich ändernde Belege, während Constrained Decoding die Syntax steuert – beides wird nicht durch SFT ersetzt.
  3. LoRA reduziert den zu trainierenden Zustand. QLoRA komprimiert zudem die gefrorenen Basismodellgewichte. Zu den Speicherkapazitäten von QLoRA dürfen keine Angaben aus LoRA herangezogen werden.
  4. Datenabdeckung, Integrität der Datensplits, Herkunft der Daten sowie das Maskieren von Verlusten sind wichtiger als das Kopieren einer modischen Optimiererkonfiguration.
  5. DPO, ORPO und PPO-basierte RLHF-Methoden stellen unterschiedliche experimentelle Ansätze dar und bilden keine hierarchische Qualitätsleiter mit einem universellen Standard.
  6. Bewerten Sie das Zielverhalten, Regressionen, Sicherheit sowie Betriebsaspekte stets am selben Basismodell.
  7. Wählen Sie vor dem Training entweder einen Adapter, eine verschmolzene Version oder eine GGUF-Ausgabe entsprechend den Anforderungen an Bereitstellung und Rollback aus.
