Dieser Guide richtet sich an Python Engineers, die entscheiden müssen, ob und wie sie ein Large Language Model fine-tunen. Sie erfahren, wann Fine-Tuning gegenüber Prompting oder Retrieval die bessere Wahl ist und wie Sie zwischen Methoden wie LoRA und QLoRA wählen. Außerdem zeigt der Guide, wie Sie Daten vorbereiten, das trainierte Model evaluieren und dessen Deployment planen.

Die Beispiele erläutern Konfigurationen und Prüfungen. Sie sind kein verifiziertes End-to-End-Trainingsrezept; im Praxisteil werden die Befehle aus dem Begleit-Repository von einer vorgeschlagenen Trainingskonfiguration getrennt.

Eine kürzere Gegenüberstellung dieser Optionen finden Sie unter Fine-Tuning vs RAG vs Prompting.

Sollten Sie überhaupt fine-tunen?

Bevor Sie GPU-Stunden investieren, entscheiden Sie, ob Fine-Tuning für das vorliegende Problem tatsächlich das richtige Werkzeug ist.

Byte sagt

Wenn nur valides JSON als Verhalten fehlt, testen Sie zuerst Constrained Decoding mit den ursprünglichen Weights. Ein Trainingslauf ist ein langer Weg, um eine fehlende geschweifte Klammer zu entdecken.

Fine-Tuning verändert das in den Weights kodierte Verhalten. Retrieval liefert Evidenz zur Inference-Zeit und ist daher der bessere Ausgangspunkt für Fakten, die sich ändern oder Zitate benötigen. Neue Dokumente werden erst nach Ingestion und Indexierung verfügbar; prüfen Sie diese Aktualität anhand Ihrer Anforderung.

Klare Prompts und Beispiele lassen sich günstiger iterieren als ein neuer Trainingslauf. Sie lösen möglicherweise bereits ein Problem bei Stil oder Instruction-Following. Fine-Tuning kann wiederholte Prompt-Tokens reduzieren, aber die Serving-Latency hängt vom Model, der Output-Länge, der Hardware und der Implementierung ab; ein Weight-Update ist nicht automatisch eine Beschleunigung.

Für Syntax können Bibliotheken wie xgrammar und outlines ungültige nächste Tokens unter einem unterstützten Schema oder einer Grammatik maskieren. Eine erfolgreich abgeschlossene Constrained Generation gehört zu dieser Sprache. Behandeln Sie Truncation und andere unvollständige Generations separat und validieren Sie das Ergebnis vor der Verwendung. Die Constraint kann eine Customer-ID nicht wahr machen und keine geeignete Tool-Auswahl erzwingen. Messen Sie die Latency auf Ihrem Backend, statt einen festen Overhead anzunehmen.

Den Business Case messbar machen

Fine-Tuning kann wiederkehrende Prompt-Tokens reduzieren oder ermöglichen, dass ein kleineres Model das Ziel erreicht; keine dieser Einsparungen ist jedoch automatisch gegeben. Berechnen Sie den Break-even-Punkt mit Ihrem eigenen Traffic und Pricing:

[ \text{break-even requests} = \frac{\text{training + evaluation + deployment cost}} {\text{baseline cost/request} - \text{tuned cost/request}} ]

Wenn der Nenner klein oder negativ ist oder auf einer unbewiesenen Qualitätsannahme beruht, gibt es für das Projekt noch keinen wirtschaftlichen Case.

[!TIP] Das hybride Setup Eine gängige Architektur kombiniert ein kleineres, auf die Aufgabe angepasstes Model mit Retrieval für veränderliche Fakten. Behandeln Sie das größere, per Prompt gesteuerte Model als Baseline und behalten Sie das kleinere Model nur, wenn es dieselben aufgabenspezifischen Qualitäts- und Safety-Schwellenwerte erfüllt.

Arten von Fine-Tuning

Fine-Tuning kann grundsätzlich drei Formen annehmen. Sie unterscheiden sich darin, welche Daten sie benötigen und was sie dem Model beibringen.

1. Continued Pre-Training (Self-Supervised)

Sie trainieren das Base Model mit zusätzlichem Rohtext und verwenden das nächste Token jeder Sequenz als Trainingsziel. Das ist Self-Supervised Learning: Der Text liefert seine eigenen Targets, genau wie im ursprünglichen Pretraining-Lauf.

Wann Sie es einsetzen sollten:

  • Die Domäne enthält ein Vokabular, das das Base Model nie gesehen hat (medizinische, juristische oder interne Codebases).
  • Sie verfügen über große Mengen an Domänentext, aber über keine gelabelten (Input, Output)-Paare.
  • Das Base Model hat Schwierigkeiten mit domänenspezifischer Terminologie.

Beispiel: Training mit Millionen klinischer Notizen, damit das Model medizinische Abkürzungen, Medikamentennamen und klinische Workflows erlernt.

2. Supervised Fine-Tuning (SFT)

SFT trainiert mit gelabelten (Input, Output)-Paaren. Sie zeigen dem Model für jeden Input exakt den gewünschten Output.

Wann Sie es einsetzen sollten:

  • Sie haben eine spezifische Aufgabe mit einem sauberen Input/Output-Format.
  • Sie verfügen über hochwertige gelabelte Daten, auch in kleinen Mengen.
  • Sie benötigen vorhersehbares Verhalten bei einer bekannten Input-Struktur.

Beispiel: Training mit (SQL-Query-Beschreibung, SQL-Code)-Paaren für Text-to-SQL. Dieses feste Kalenderintervall setzt voraus, dass signup_date in UTC gespeichert ist:

{
    "input": "Get users who signed up in August 2026 (UTC)",
    "output": "SELECT * FROM users WHERE signup_date >= '2026-08-01' AND signup_date < '2026-09-01'"
}

3. Instruction Tuning

Instruction Tuning ist ein spezieller Anwendungsfall von SFT, der Models darauf ausrichtet, einer großen Vielfalt natürlichsprachlicher Instructions zu folgen. Die Trainingsdaten bestehen aus (Instruction, Response)-Paaren über viele verschiedene Tasks hinweg.

Wann Sie es einsetzen sollten:

  • Sie möchten einen General-Purpose Assistant entwickeln (wie ChatGPT oder Claude).
  • Das Model muss vielfältige, offene Anfragen verarbeiten.
  • Sie entwickeln ein Chat-Interface.

Beispiel: Training mit Tausenden unterschiedlichen Instructions wie „Fasse diesen Artikel zusammen“, „Schreibe ein Gedicht über X“ oder „Erkläre Y in einfachen Worten“.

Die 7-stufige Fine-Tuning-Pipeline

Fine-Tuning ist eine Pipeline, kein einzelner Befehl. Jede Stufe hat eigene Failure Modes; das Überspringen einer Stufe zeigt sich meist erst später in einem schlechten Model.

Jede Stufe baut auf der vorherigen auf:

  1. Datenvorbereitung — Definieren Sie die Evaluationseinheit, teilen Sie die Daten auf und bereinigen und formatieren Sie sie anschließend.
  2. Model-Auswahl — Wählen Sie das passende Base Model und laden Sie die Weights.
  3. Trainings-Setup — Konfigurieren Sie Hardware, Hyperparameter und Optimierungsstrategie.
  4. Fine-Tuning — Führen Sie SFT-, DPO- oder ORPO-Training aus.
  5. Evaluation — Benchmarken Sie die Performance und validieren Sie die Qualität.
  6. Deployment — Exportieren und serven Sie Ihr Model.
  7. Monitoring — Verfolgen Sie die Performance, warten Sie das System und iterieren Sie.

[!WARNING] Daten sind die Grundlage Das Training reproduziert systematische Fehler in den Beispielen. Prüfen Sie Labels, Leakage, Abdeckung und Policy-Compliance, bevor Sie Zeit in Optimizer-Sweeps investieren.

Stufe 1: Datenvorbereitung

Viele Fine-Tuning-Projekte scheitern hier, nicht im Training. Moderne Datenvorbereitung ist mehr, als einen Regex über CSVs laufen zu lassen.

Fünf Transformationen nach dem Source-Split

Ordnen Sie Source-Gruppen dem Training oder der Evaluation zu, bevor Sie Rows transformieren. Ein Support-Ticket und jede Umschreibung dieses Tickets bleiben in derselben Partition. Clustern Sie bekannte Near-Duplicates vor der Zuordnung der Gruppen und prüfen Sie nach dem Cleaning erneut über alle Partitionen hinweg. Frieren Sie das Evaluation-Set ein; augmentieren Sie nur Trainingsdaten.

Listen Sie die Fehler auf, die Ihre Beispiele dem Model beibringen sollen, und definieren Sie anschließend die erforderlichen Felder und Labels jeder Row. Wählen Sie für diese Schritte geeignete Processing-Tools; DataTrove und Distilabel können bei größeren Datasets helfen.

1. Ingestion und Filtering

  • Aktion: Entfernen Sie fehlerhaftes UTF-8 und nicht aufgabenbezogene Inhalte. Kennzeichnen Sie Refusals nach Policy: Behalten Sie korrekte Refusals als Trainingsziele und Evaluationsfälle; schließen Sie nur ungültige oder nicht aufgabenbezogene Refusals aus.
  • Tools: Trafilatura für die Extraktion und fastTexts Language-Identification-Models für Language ID; die verteilten lid.176-Models erkennen 176 Sprachen.

2. Policy für sensible Daten

  • Aktion: Entscheiden Sie, was das Model lernen darf, und redigieren, tokenisieren oder schließen Sie personenbezogene und vertrauliche Felder entsprechend aus.
  • Tools: Microsoft Presidio oder scrubadub.
  • Warum: Ein Detector ist nur eine Control; Anforderungen an Provenance, Einwilligung, Aufbewahrung, Zugriff und Löschung gelten weiterhin.

3. Deduplication (MinHash LSH)

  • Aktion: Entfernen Sie Near-Duplicates, um Repetition und Leakage-Risiken zu reduzieren; dies verhindert Memorization nicht.
  • Tools: DataTrove eignet sich gut für Processing im Terabyte-Maßstab.

4. Synthetische Augmentation, falls erforderlich

  • Aktion: Verwenden Sie ein geeignetes Teacher Model, um Trainingsbeispiele in Instruction-Response-Paare umzuschreiben, und behalten Sie deren Source-IDs bei. Augmentieren Sie die zurückgehaltene Partition nicht.
  • Tools: Distilabel.
  • Validation: Sampeln Sie Teacher-Outputs, prüfen Sie sie anhand derselben Rubrik wie Human-Labels und berichten Sie die Ergebnisse separat für synthetische und von Menschen verfasste Beispiele. Eine solche Evaluations-Teilmenge wird Slice genannt; weitere nützliche Slices sind Sprache und Task-Typ.

5. Formatting

  • Aktion: Konvertieren Sie die Daten in ein Standardformat (Alpaca oder ShareGPT).

Beispiele für Datenformate

Alpaca-Format (Instruction-Following):

{
    "instruction": "Summarize the following text.",
    "input": "The text to be summarized...",
    "output": "This is the summary."
}

ShareGPT-ähnliche Speicherung (konversationell):

{
    "conversations": [
        { "from": "user", "value": "Hello, who are you?" },
        { "from": "assistant", "value": "I am a helpful AI assistant." }
    ]
}

Worauf es tatsächlich ankommt

  • Abdeckung vor Umfang. Fügen Sie Beispiele hinzu, die unterschiedliche Failure Modes repräsentieren, statt Wiederholungen des einfachen Mehrheitsfalls.
  • Sauberkeit. Entfernen Sie irrelevanten Text, normalisieren Sie Whitespace und halten Sie die Formatierung konsistent.
  • Balance. Bewahren Sie wichtige seltene Fälle und berichten Sie die Performance pro Slice.
  • Trennung. Teilen Sie nach Source, User, Dokument oder Zeit auf, wenn zufällige Row-Splits Near-Duplicates leaken würden.
  • Provenance. Erfassen Sie für jede Dataset-Version Source, Lizenz oder Berechtigung, Transformationshistorie und Löschpfad.

Stufe 2: Model-Auswahl und Hardware

Das Base Model und seine minimale GPU-Speicheranforderung bestimmen, was Sie trainieren können.

Beginnen Sie mit dem kleinsten Base Model, das die unverhandelbaren Baseline-Checks bereits besteht. Bestätigen Sie:

  • Lizenz- und Redistributionsbedingungen für das geplante Produkt;
  • Sprache, Domäne, Tool Use und Safety-Verhalten vor der Anpassung;
  • Kompatibilität von Tokenizer und Chat-Template mit dem Dataset;
  • maximalen Context und erforderliches Truncation-Verhalten anhand realer Beispiele;
  • Support sowohl im Training Framework als auch in der Ziel-Serving Engine.

Fine-Tuning ist ein Adaptation-Schritt, keine Reparatur für ein ungeeignetes Base Model. Wenn das Model bei Fähigkeiten versagt, die das Dataset nicht abdeckt, wählen Sie vor weiteren Epochs ein anderes Base Model.

Den Run dimensionieren, nicht die Marketingklasse

Eine dauerhaft gültige Tabelle „Model-Größe → GPU“ gibt es nicht. Der Peak-Speicher ändert sich mit Weight Precision, Optimizer, Anzahl trainierbarer Parameter, Sequence Length, Micro-Batch-Größe, Activation Checkpointing, Attention-Implementierung und Framework-Overhead. Beginnen Sie mit einer Speicherschätzung und führen Sie anschließend einen kurzen Smoke Test mit maximaler Sequence Length auf dem exakten Stack aus.

Das ursprüngliche QLoRA-Paper brachte ein 65B-LLaMA-Model in seinem spezifischen Setup auf einer einzelnen 48-GB-GPU unter. Dieses Ergebnis ist eine nützliche Grenze, aber keine Zusage, dass jede aktuelle 70B-Architektur, Context Length, jeder Kernel oder Trainer auf dasselbe Device passt.

Memory Math

Für ein Model mit PPP Parametern benötigen allein die Weights ungefähr 2P2P2P Bytes in BF16/FP16 oder 0.5P0.5P0.5P Bytes bei vier Bits — noch vor Quantization-Metadaten und Runtime-Buffern. Full Adam-Style-Training fügt Gradients, Optimizer States und häufig höherpräzise Master Weights hinzu. LoRA vermeidet den Großteil des Speichers für trainierbare States; QLoRA reduziert zusätzlich den Footprint der eingefrorenen Base Weights. Bei langen Sequence Lengths können Activations dennoch dominieren.

Verwenden Sie diesen Ablauf:

  1. Wählen Sie die längste Sequence und den Micro-Batch, die Sie unterstützen müssen.
  2. Schätzen Sie Weights und trainierbaren State und lassen Sie Headroom für Activations und Kernels.
  3. Führen Sie einen Forward/Backward-Step mit maximaler Länge aus.
  4. Erfassen Sie den Peak bei allokiertem und reserviertem Speicher.
  5. Skalieren Sie erst danach Batch-Größe, Rank, Sequence Length oder GPU-Anzahl.

Stufe 3: Trainings-Setup und Methoden

Von gespeicherten Rows zu Trainingszielen

ShareGPT bezeichnet eine Dataset-Struktur; ChatML ist eine Serialisierungskonvention. Konvertieren Sie from/value in die Rollen und Felder, die der Trainer akzeptiert, und verwenden Sie anschließend das Chat-Template des ausgewählten Models. Ersetzen Sie ChatML-Tokens nicht nur deshalb, weil die Daten konversationell sind.

Für die Greeting-Row oben lauten die normalisierten Messages:

messages = [
    {"role": "user", "content": "Hello, who are you?"},
    {"role": "assistant", "content": "I am a helpful AI assistant."},
]
# Inspection step after loading the selected model's tokenizer:
rendered = tokenizer.apply_chat_template(
    messages, tokenize=False, add_generation_prompt=False,
)
print(rendered)

Prüfen Sie die tatsächlich serialisierte Row vor dem Training: Role Delimiters, End-of-Turn-Tokens und Tool Schemas müssen zur Inference passen. Bewahren Sie bei einer Tool-Use-Row Tool-Definitionen, Assistant Tool Calls und Tool Results als getrennte Felder auf. Prüfen Sie, dass Truncation weder die supervised Response entfernt noch ein Tool-Argument halbiert.

Loss Masking legt fest, für welche Tokens das Model beim Predicting belohnt wird. Beim Full-Sequence-Training können User-, System-, Tool- und Assistant-Text beitragen. Beim Assistant-Only-Training bleiben diese Context-Tokens für Attention sichtbar, ihre Labels werden jedoch ignoriert (üblicherweise -100); nur Assistant-Spans tragen bei. Für diese Greeting sollte die Antwort ein Target sein, die Frage des Users dagegen nicht, wenn Assistant-Only-Verhalten beabsichtigt ist.

TRLs SFT-Dokumentation unterstützt assistant_only_loss=True für konversationelle Datasets, deren Templates Generation-Spans bereitstellen. Ein Template ohne diese Spans kann diese Mask nicht liefern. Prompt/Completion-Datasets haben eine separate Option completion_only_loss. Aktivieren Sie eine der beiden Optionen erst, nachdem Sie einen tokenisierten Batch inspiziert und die Tokens mit nicht ignorierten Labels dekodiert haben. Wiederholen Sie dies mit einer Tool-Konversation und einem Beispiel maximaler Länge. Die unten stehende illustrative Trainingskonfiguration verwendet bewusst Full-Sequence-Loss; Assistant-Only-Training erfordert diese zusätzliche Prüfung von Template und Mask.

Wählen Sie die Sequence Length anhand der Datenverteilung und führen Sie den Memory Check maximaler Länge aus Stufe 2 durch. Packing platziert mehrere kürzere Beispiele in einer Trainingssequenz. Beginnen Sie ohne Packing, damit Row-Grenzen leicht zu inspizieren sind. Benchmarken Sie Packing erst, nachdem die serialisierten Rows und Labels korrekt sind.

Full Fine-Tuning vs. PEFT

Full Fine-Tuning (FFT) aktualisiert jedes Weight, daher skalieren Gradients und Optimizer State mit dem gesamten Model. Der Peak lässt sich nicht allein aus der Parameteranzahl ableiten, liegt aber deutlich über dem Speicher, der zum Laden der Weights für Inference erforderlich ist.

Parameter-efficient Fine-Tuning (PEFT) trainiert nur eine kleine Teilmenge der Parameter und friert den Rest ein. Die Rechnung wird deutlich angenehmer.

LoRA: der Ausgangspunkt

LoRA (Low-Rank Adaptation) friert eine vortrainierte Matrix ein und repräsentiert ihr gelerntes Update durch zwei kleinere Matrizen. Das Original-Paper begründet dies mit der Hypothese, dass nützliche Adaptation-Updates einen niedrigen intrinsischen Rank besitzen.

Hier ist dind_{in}din​ die Input-Breite der Schicht und doutd_{out}dout​ ihre Output-Breite. Der Rank rrr ist die kleinere gemeinsame Dimension der beiden trainierbaren Matrizen: Ein kleinerer Rank verwendet weniger trainierbare Parameter. Die Einstellung α\alphaα steuert die Skalierung des Updates über das Verhältnis α/r\alpha/rα/r.

DoRA: Weight-Decomposed LoRA

DoRA (Weight-Decomposed Low-Rank Adaptation) trennt die Magnitude jedes Weight-Vektors von seiner Richtung. Das DoRA-Paper wendet ein LoRA-Update auf die Richtungskomponente an und lernt die Magnitude separat.

So funktioniert es:

Anstatt Weights als eine Einheit zu behandeln, zerlegt DoRA vortrainierte Weights in zwei Komponenten:

  1. Magnitude — ein trainierbarer Wert pro Weight-Vektor.
  2. Richtung — ein normalisierter Vektor, der über Low-Rank-Matrizen aktualisiert wird.

In kompakter spaltenweiser Notation:

W′=mV+BA∥V+BA∥cW' = m \frac{V + BA}{\lVert V + BA \rVert_c}W′=m∥V+BA∥c​V+BA​

Dabei gilt:

  • m = Magnitude (trainierbar)
  • V=W0V = W_0V=W0​ = die eingefrorene Initial-Matrix; nach dem Addieren von BABABA normalisieren
  • BABABA = das gelernte Low-Rank-Richtungsupdate
  • ∥⋅∥c\lVert \cdot \rVert_c∥⋅∥c​ = spaltenweise Normalisierung

Was Sie durch diese zusätzliche Struktur erhalten:

  • Mehr Freiheitsgrade als bei Standard-LoRA, da sich die Magnitude unabhängig ändern kann.
  • Bessere Ergebnisse als mit LoRA in mehreren vom Paper der Autoren berichteten Konfigurationen.
  • Zusätzliche Parameter und Berechnung; der Gewinn sollte daher für Ihren Task und Serving-Pfad verifiziert werden.

Adapter-Merging für Multi-Task Learning

Separate Adapter ermöglichen es einer eingefrorenen Base, mehrere Tasks zu unterstützen. Sie können Requests an einen Adapter routen, mehrere Adapter aus einer Engine serven, sofern unterstützt, oder offline einen gemergten Kandidaten erzeugen. Merging kann Interference verursachen; evaluieren Sie daher das gemergte Artefakt, statt eine saubere Komposition der Source-Adapter anzunehmen.

Gängige Merging-Methoden:

  1. Concatenation — Adapter-Parameter kombinieren und den effektiven Rank erhöhen. Schnell und einfach.
  2. Linear Combination — gewichtete Summe der Adapter. Bietet Stellschrauben.
  3. SVD — Matrix-Decomposition für Merging. Flexibler, aber langsamer.

Beispiel: ein Adapter für Summarization und ein weiterer für Translation, gemergt in ein einzelnes Multi-Task-Model.

Stufe 4: Fine-Tuning und Preference Alignment

SFT lernt Demonstrationen. Preference Optimization lernt dagegen aus Vergleichen wie „Chosen Response A ist besser als Rejected Response B“. Verwenden Sie sie nur, wenn Pairwise Preference das richtige Label für den Fehler ist; faktische Korrektheit und Policy-Compliance benötigen häufig stärkere Evaluators als eine globale Preference.

PPO-basiertes RLHF

RLHF bedeutet Reinforcement Learning from Human Feedback. Die Policy ist das Language Model, das Responses generiert; ein Reward Model bewertet diese Responses anhand von Preferences, die aus menschlichen Vergleichen gelernt wurden. Ein PPO-basiertes Rezept umfasst drei Stufen:

  1. SFT — den Task lernen.
  2. Reward Model — mit menschlichen Preferences trainieren (Chosen vs. Rejected).
  3. PPO (Proximal Policy Optimization) — Responses generieren und das Language Model so aktualisieren, dass deren Reward Scores steigen.

Die operativen Kosten entstehen durch die beweglichen Teile:

  • Kompliziert zu implementieren und zu warten.
  • Teuer — Sie trainieren mehrere Models.
  • Sampling aus dem trainierten Model erfordert Prüfungen auf instabile Updates sowie Responses, die das Reward Model ausnutzen, ohne den Task zu erfüllen.

DPO

DPO (Direct Preference Optimization) verzichtet auf ein separates Reward Model und den Reinforcement-Learning-Loop. Es bevorzugt Chosen Responses und hält zugleich große Änderungen gegenüber einem festen Start-Model zurück, dem Reference Model. Das DPO-Paper leitet dieses Objective her, indem es begrenzt, wie weit sich Response-Wahrscheinlichkeiten von dieser Referenz entfernen dürfen; die mathematische Begrenzung ist eine KL-Divergence-Constraint.

Ein Preference-Paar enthält denselben Prompt und zwei Kandidaten-Responses. Diese verkürzte Row zeigt die Felder; reale Labels benötigen vollständige Responses und einen Grund für die Präferenz:

{
    "prompt": "Explain quantum computing",
    "chosen": "Quantum computing uses qubits...",   # Preferred response
    "rejected": "Well, it's complicated..."        # Non-preferred response
}

Operativ ändert sich Folgendes:

  • Einfacherer Code Path (kein separates Reward Model, kein RL-Loop).
  • Training mit gespeicherten Preference-Paaren, statt bei jedem Update neue Responses für Reward Scoring zu generieren.
  • Ein fixes Reference Model oder in der Standardformulierung dessen gespeicherte Log-Probabilities für die Trainings-Responses.

DPO lässt sich leichter prototypen als eine vollständige PPO-Pipeline, ist aber kein automatisches Qualitätsupgrade. Die Ergebnisse hängen von der Start-Policy, der Qualität der Paare, den Loss-Einstellungen, Längeneffekten und dem Evaluationsprotokoll ab. Vergleichen Sie DPO mit einem SFT-Checkpoint auf denselben zurückgehaltenen Preference- und Task-Suites.

ORPO

ORPO (Odds-Ratio Preference Optimization) kombiniert den SFT Negative-Log-Likelihood-Loss mit einer Odds-Ratio-Penalty für Rejected Responses. Es entfernt das separate Reference Model und kann Task Learning und Preference Optimization in einem Lauf kombinieren.

So funktioniert es: ORPO verwendet einen kombinierten Loss, der gleichzeitig zwei Dinge tut:

  1. Maximiert die Likelihood der Chosen Response (lernt den Task).
  2. Bestraft die Rejected Response mit einem Odds-Ratio-Term (lernt Preferences).

Relevante Hyperparameter (TRL 1.12.0 API):

# API shown in TRL 1.12.0 documentation
from trl.experimental.orpo import ORPOConfig

config = ORPOConfig(
    learning_rate=8e-6,  # Very low, as recommended by the ORPO paper
    beta=0.1,            # Controls strength of preference penalty
    # ... other params
)
  • Learning Rate: Das Paper verwendete in seinen Experimenten niedrige Raten; tunen Sie anhand Ihres Models, Batches und Datas, statt einen Wert als allgemeine Regel zu kopieren.
  • Beta: Steuert den Preference-Term relativ zum SFT-Term.

Der Trade-off:

  • Eine Trainingsstufe statt zwei.
  • Kein Reward Model.
  • Kein Forward Pass des Reference Models.
  • Ein gekoppelter Run: Wenn Task Learning oder Preference-Verhalten regressiert, gibt es keinen Zwischen-SFT-Checkpoint aus derselben Pipeline zur Inspektion.

Wählen Sie anhand von Daten- und Evaluationsdesign:

  • Verwenden Sie DPO, wenn bereits ein zufriedenstellender SFT-Checkpoint existiert und Sie ein einfacheres Offline-Preference-Experiment möchten.
  • Testen Sie ORPO, wenn ein Reference-freies, einstufiges Objective zu Ihren Daten und operativen Constraints passt.
  • Verwenden Sie PPO-basiertes RLHF, wenn Online-Sampling gegen einen explizit gelernten Reward Teil der Anforderung ist und Sie Reward Exploitation überwachen können.

Keine dieser Methoden ist für alle Tasks ein Default. Behalten Sie eine SFT-only-Baseline und berichten Sie sowohl Task Metrics als auch Preference Metrics.

Fine-Tuning Frameworks

Frameworks überschneiden sich und ändern sich schnell. Wählen Sie anhand des Execution Paths, den Sie unterstützen müssen, pinnen Sie Versionen und halten Sie die Trainingskonfiguration portabel genug, um sie außerhalb eines Notebooks zu reproduzieren.

Unsloth — Geschwindigkeit und Memory Efficiency

Unsloth integriert sich in Hugging Face trl und transformers und stellt optimierte Kernels, Checkpointing sowie quantisierte Fine-Tuning-Pfade für unterstützte Models bereit.

  • Eigene Triton-GPU-Kernels für Attention, RoPE und Cross-Entropy, die PyTorch-Overhead überspringen.
  • Memory-efficient Backpropagation, die Activations während des Backward Pass neu berechnet, statt sie im Speicher zu halten.
  • Fused Operations, die mehrere Schritte (Layer Norm + Linear und ähnliche) zu einzelnen GPU-Calls zusammenfassen.
  • 4-Bit-Quantization direkt im QLoRA-Pfad mit optimierter Dequantization.

[!IMPORTANT] Die Import-Reihenfolge ist wichtig Folgen Sie für die von Ihnen gepinnte Version der Import-Reihenfolge im Unsloth-Beispiel. Unsloth wendet beim Import Patches an; der Import vor trl und transformers verhindert fehlende Optimierungen oder versionsabhängige Fehler.

# Correct order
from unsloth import FastLanguageModel  # Must be first!
from trl import SFTTrainer
from transformers import TrainingArguments

# Avoid this order with Unsloth's patched path
from trl import SFTTrainer
from unsloth import FastLanguageModel

Geeignet für: Single-GPU-Training, Prototyping, Colab-Notebooks und alle, die ihre GPU-Kosten im Blick behalten.

Veröffentlichte Speed- und Memory-Werte variieren je nach Model, Sequence Length, Batch, Precision und Hardware. Benchmarken Sie Tokens pro Sekunde und Peak-Speicher in Ihrem eigenen Run, statt eine Headline-Ratio als Framework-Eigenschaft zu betrachten.

Vorgeschlagene TRL-Trainingskonfiguration

Dies ist eine schematische Konfiguration und kein vom Companion ausgelieferter Code. Stellen Sie train_dataset und eval_dataset als Hugging Face Datasets mit messages sowie bei Tool-Beispielen mit tools-Spalten bereit. Erzeugen Sie sie aus einem versionierten Source-/Group-Split wie in Stufe 1 beschrieben. Pinnen Sie kompatible Revisionen von Unsloth, TRL, Transformers und dem Model; die API-Struktur folgt TRL 1.12.0.

Die folgenden Calls evaluieren den Holdout-Token-Loss einmal pro Epoch. Das ist ein Diagnostic, keine Accuracy-Messung für Tool Calls; Stufe 5 erfordert weiterhin eine separate Task-Evaluation.

from unsloth import FastLanguageModel
from trl import SFTConfig, SFTTrainer

# Load model with 4-bit quantization
model, tokenizer = FastLanguageModel.from_pretrained(
    model_name="nvidia/Llama-3.1-Nemotron-Nano-4B-v1.1",
    max_seq_length=4096,
    load_in_4bit=True,
)

# Add LoRA adapters
model = FastLanguageModel.get_peft_model(
    model,
    r=16,
    lora_alpha=32,
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj",
                    "gate_proj", "up_proj", "down_proj"],
    use_gradient_checkpointing="unsloth",  # Lower activation memory; extra compute
)

# Prerequisite: supply the prepared datasets described above.

# Train with the current TRL configuration surface.
trainer = SFTTrainer(
    model=model,
    processing_class=tokenizer,
    train_dataset=train_dataset,
    eval_dataset=eval_dataset,
    args=SFTConfig(
        output_dir="outputs/proposed-nemotron-run",
        max_length=4096,
        packing=False,
        assistant_only_loss=False,  # Full-sequence targets; inspect before changing
        eval_strategy="epoch",
        per_device_train_batch_size=2,
        gradient_accumulation_steps=4,
        learning_rate=2e-4,
        num_train_epochs=3,
        bf16=True,  # Requires BF16-capable hardware
    ),
)
trainer.train()
trainer.save_model("outputs/proposed-nemotron-adapter")
tokenizer.save_pretrained("outputs/proposed-nemotron-adapter")

Stufe 5: Evaluation

Byte sagt

Wenn dasselbe Support-Ticket in Training und Evaluation vorkommt, kann ein höherer Score das Wiedererkennen dieses Tickets belohnen. Teilen Sie vor dem Erzeugen von Rows oder Umschreibungen nach Ticket auf.

Legen Sie Testfälle, Scoring-Regeln und Passing Thresholds vor dem ersten Run fest. Vergleichen Sie mindestens den getunten Checkpoint mit der exakt ungetunten Base unter denselben Prompts, Decoding-Settings und derselben Tool-Umgebung. Berichten Sie aggregierte Qualität erst, nachdem Sie die Failure Slices geprüft haben, die das Projekt verbessern sollte.

Verfolgen Sie vier Gruppen:

  1. Ziel-Task: Exact Match, Execution Success, Human Rubric oder ein anderes Outcome, das an den Use Case gebunden ist.
  2. Regression: allgemeine Fähigkeiten und zuvor unterstützte Task-Slices, die durch die Anpassung beeinträchtigt werden könnten.
  3. Safety und Policy: Refusals, Data Leakage, Prompt Injection oder domänenspezifische Constraints.
  4. Operations: Latency, Throughput, Speicher, Artefaktgröße und Kosten in der vorgesehenen Serving-Konfiguration.

Automatisierte Benchmarks

Verwenden Sie lm-evaluation-harness, um relevante standardisierte Tasks neben Ihren Product Tests zu prüfen. Dieser Befehl benötigt einen gemergten Hugging Face Checkpoint. Sein Beispielpfad verweist auf den gemergten Output des Legacy-Companions aus Stufe 6; der mit der vorgeschlagenen Konfiguration oben gespeicherte Adapter wird nicht geladen. Ersetzen Sie ihn durch den gemergten Checkpoint, den Sie evaluieren möchten:

lm_eval --model hf \
    --model_args pretrained=./outputs/unsloth-nemotron-function-calling-merged \
    --tasks hellaswag,arc_easy,mmlu \
    --batch_size 8

LLM-as-Judge

Für subjektive Qualität kann ein größeres Model beim Scoring unterstützen. Kalibrieren Sie es jedoch anhand von durch Menschen geprüften Beispielen und halten Sie die Identität der Kandidaten verborgen:

judge_prompt = """
Rate this response from 1-5 on:
- Relevance
- Accuracy
- Formatting

Response: {model_output}
Expected: {ground_truth}
"""

Domänenspezifische Evaluation

Halten Sie reale Beispiele nach Source, User, Dokument oder Zeit zurück, damit Near-Duplicates nicht über den Split leaken können. Validieren Sie beim Function Calling die vollständige Trajectory: Tool Selection, Arguments, Execution Result, Recovery und Final Response. Berichten Sie bei kleinen Samples Confidence Intervals oder gepaarte Win/Loss Counts und inspizieren Sie jede Regression in einem kritischen Slice.

Stufe 6: Deployment und Output-Formate

Wählen Sie das Artefakt anhand von Serving Engine und Rollback-Plan, nicht nur anhand der Dateigröße. Diese CLI-Beispiele beziehen sich auf den Legacy-Companion, nicht auf den vorgeschlagenen TRL-Auszug. Sein Standard-Adapterverzeichnis ist outputs/unsloth-nemotron-function-calling; für Exports verwendet er die Verzeichnisse -merged und -gguf. Jeder CLI-Aufruf trainiert erneut; es handelt sich nicht um einen reinen Export-Befehl. Für einen echten Release exportieren Sie den ausgewählten evaluierten Checkpoint, statt Artefakte aus separaten Retraining-Runs zu vergleichen.

1. LoRA-Adapter

uv run finetune  # Default adapter directory shown below
  • Größe: proportional zu Target Modules, Rank, Layers und Dtype; oft deutlich kleiner als die Base.
  • Geeignet für: Development, versionierte Task-Adapter und Engines mit direktem LoRA-Support.
  • Vorteil: Sie können Adapter austauschen, ohne das Base Model erneut herunterzuladen.

2. Gemergtes Model

uv run finetune --merge  # Creates a standalone full model
  • Größe: ungefähr der vollständige Base-Checkpoint in der gewählten Output Precision.
  • Geeignet für: Engines oder Distributionspfade, die den Adapter nicht separat unterstützen.
  • Trade-off: größeres Artefakt und langsamerer Rollout, dafür einfacheres Laden eines einzelnen Models.

3. GGUF-Format

uv run finetune --gguf q4_k_m  # File size and name depend on the exporter
  • Größe: Model-abhängig; bei Q4-Varianten ungefähr 4-Bit-Weigths plus Metadaten.
  • Geeignet für: CPU-Inference, Ollama, llama.cpp und Edge Deployment.
  • Optionen: q4_k_m (kleiner), q5_k_m (höhere Weight Fidelity), q8_0 (größer und höhere Fidelity). Messen Sie den Task-Effekt nach der Konvertierung.

Stufe 7: Serving und Monitoring

Mit vLLM

Dieser Serving-Sketch setzt voraus, dass der vorgeschlagene Adapter die Task-Evaluation bestanden hat und mit einem Llama-3.1-kompatiblen Tool-Template trainiert wurde. Speichern Sie genau dieses geprüfte Template als serving-chat-template.jinja; der Companion erzeugt es nicht. Für das Legacy-ChatML-formatierte Adapter-Setup ist die Kompatibilität mit diesem Parser/Template-Paar nicht festgestellt. Verifizieren Sie eine vollständige Tool-Trajectory, bevor Sie den Endpoint veröffentlichen.

# Serve the base and expose a PEFT adapter as a model name. This parser and
# template pair is for a Llama 3.1-compatible function-calling adapter.
vllm serve nvidia/Llama-3.1-Nemotron-Nano-4B-v1.1 \
    --enable-lora \
    --lora-modules function-calling=./outputs/proposed-nemotron-adapter \
    --enable-auto-tool-choice \
    --tool-call-parser llama3_json \
    --chat-template ./serving-chat-template.jinja \
    --host 0.0.0.0 \
    --port 8000 \
    --max-model-len 4096

Dieses bewusst minimale Flight-Schema testet Argument Generation über die OpenAI-kompatible API. Es fordert einen vorgeschlagenen book_flight-Call mit einem Ziel an, führt aber keine Buchung aus. Inspizieren Sie response.choices[0].message.tool_calls auf Function Name und JSON Arguments. Für diesen Input lautet das erwartete Ergebnis book_flight mit {"destination": "Tokyo"}. Da die Tool-Auswahl automatisch erfolgt, prüfen Sie außerdem, ob das Model überhaupt einen Call zurückgegeben hat:

from openai import OpenAI

client = OpenAI(base_url="http://localhost:8000/v1", api_key="dummy")
response = client.chat.completions.create(
    model="function-calling",
    messages=[{"role": "user", "content": "Book a flight to Tokyo"}],
    tools=[
        {
            "type": "function",
            "function": {
                "name": "book_flight",
                "description": "Book a flight to a city.",
                "strict": True,
                "parameters": {
                    "type": "object",
                    "properties": {
                        "destination": {"type": "string"},
                    },
                    "required": ["destination"],
                    "additionalProperties": False,
                },
            },
        }
    ],
    tool_choice="auto",
)

vLLMs Tool-Calling-Guide erfordert automatische Tool-Auswahl und einen zum Model passenden Parser. Stellen Sie ein kompatibles Chat-Template bereit, wenn die Tokenizer-Konfiguration keines enthält. Bei Verwendung von tool_choice="auto" benötigen Constrained Arguments außerdem strict: true für mindestens eine Function sowie ein Strict-kompatibles parameters-Schema. Das Strict-Tool-Calling-Setting des Servers muss aktiviert sein (der dokumentierte Default). Ohne dieses Opt-in extrahiert vLLM Calls aus Raw Text; dadurch können Arguments fehlerhaft sein oder gegen das Schema verstoßen.

Das veröffentlichte Model überwachen

Der Lifecycle endet nicht bei einem gesunden Training Loss. Erfassen Sie Model-Revision, Tokenizer und Chat-Template, Adapter-Hash, Dataset-Version, Trainingskonfiguration und Evaluationsbericht als gemeinsame Release-Einheit. Überwachen Sie in Production Task Success, ungültige Outputs, Policy Failures, Latency und Input Drift anhand derselben Slices wie offline. Halten Sie das vorherige Artefakt ladbar und definieren Sie vor dem Launch eine Rollback-Schwelle.

Ihr nächster Test

Inspizieren Sie vor einem vollständigen Run eine serialisierte Konversation und ihre Loss Targets und führen Sie anschließend einen Forward/Backward-Step mit maximaler Länge durch. Speichern Sie diese Konfiguration zusammen mit Dataset-Split und Baseline-Report. Wenn ein Tool Schema fehlt, bewahren Sie es in der Trainings-Row auf. Wenn eine Antwort abgeschnitten wird, passen Sie Sequence Length und Formatting so an, dass die vollständige Antwort erhalten bleibt. Lösen Sie diese Probleme, bevor Sie weitere Epochs hinzufügen.
