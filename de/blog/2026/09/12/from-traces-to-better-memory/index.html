AI-Systeme per Meta-Engineering verbessern: von Traces zu besserer Memory

Dieser Artikel eröffnet Meta-Engineering AI Systems, einen sechsteiligen Leitfaden zu Closed-Loop AI Engineering: Agents einzusetzen, um Fehler zu untersuchen, Änderungen zu testen und die Ergebnisse zur Verbesserung von AI-Systemen zu nutzen.

Das Verhalten einer AI-Anwendung hängt von mehr als ihrem Model ab. Prompts, abgerufene Informationen, gespeicherte Memory, Tools und Anwendungscode beeinflussen das Ergebnis. Wenn eine Antwort falsch ist, können mehrere Änderungen plausibel erscheinen. Die Engineering-Aufgabe besteht darin zu entscheiden, welche Änderung hilft, welche Kosten sie verursacht und was sie außerdem beschädigt.

Mit Meta-Engineering bezeichne ich hier das Design des Verbesserungsprozesses selbst: Welche Evidenz der Agent sieht, was er ändern darf, wie wir seine Vorschläge testen und wer über ihre Übernahme entscheidet. Closed-Loop beschreibt, wie dieser Prozess aus seinen Experimenten lernt. Jedes Ergebnis beeinflusst, was wir als Nächstes ausprobieren oder verwenden – auch dann, wenn eine vorgeschlagene Änderung scheitert.

Wir können diese Arbeit schrittweise automatisieren. Eine Person kann die exakt zu testenden Änderungen vorgeben, eine Menge zulässiger Alternativen für einen Suchalgorithmus definieren oder den nächsten Vorschlag an einen LLM Agent delegieren. Der Runner testet jeden Kandidaten und bewahrt die Evidenz für die nächste Entscheidung auf. Diese Serie konzentriert sich darauf, Agents in diesen Prozess einzubinden und gleichzeitig Ausführung, Evaluierung und Übernahme explizit zu kontrollieren.

Die zentrale Frage aller sechs Teile lautet, wie viel dieser Arbeit wir an einen Agent delegieren können, ohne dass Evidenz und Übernahmeentscheidung ihre Vertrauenswürdigkeit verlieren. Wir beginnen mit einer Abbildung des Gesamtsystems und bauen anschließend eine kleine funktionierende Version rund um Agent Memory.

Was den Loop schließt

Es gilt, zwei unterschiedliche Loops im Blick zu behalten. Innerhalb einer Agent-Anwendung wählt der Runtime Loop eine Aktion, führt einen Tool Call aus, beobachtet das Ergebnis und setzt die aktuelle Aufgabe des Users fort. Der Improvement Loop arbeitet über verschiedene Versionen dieser Anwendung hinweg. Er untersucht das Verhalten abgeschlossener Runs und testet Änderungen, die spätere Runs verbessern sollen.

Der Improvement Loop beginnt mit Evidenz: einer falschen Antwort, einer unerwünschten Zustandsänderung, überhöhten Kosten oder einem anderen beobachtbaren Fehler. Ein Trace zeichnet die Schritte hinter diesem Ergebnis auf. Der Proposer wählt einen Kandidaten, also eine konkrete Version einer Änderung. Ein Runner führt den Kandidaten für definierte Aufgaben aus, und ein Evaluator prüft das resultierende Verhalten gegen die Anforderungen. Im Live-Experiment dieses Artikels ist ein LLM Agent der Proposer:

Die Evaluierung informiert eine Entscheidung; sie autorisiert sich nicht selbst. Jemand muss entscheiden, ob der gemessene Nutzen die Übernahme der Änderung rechtfertigt – einschließlich ihrer Auswirkungen auf Kosten, Berechtigungen und anderes erforderliches Verhalten. In dieser Serie beginnen wir mit einem Human Reviewer. Der Proposer kann eine Änderung vorschlagen, aber weder die Checks umschreiben noch sein eigenes Budget erhöhen oder sich selbst die Genehmigung erteilen.

Es gibt zwei Rückwege. Die Experimenthistorie fließt in spätere Vorschläge ein, auch wenn ein Kandidat abgelehnt wird. Wird ein Kandidat genehmigt und übernommen, liefert sein Verhalten neue Evidenz aus der Nutzung. Eine Änderung reversibel zu halten ist wichtig, wenn diese Evidenz dem ursprünglichen Experiment widerspricht. Einen Score aufzuzeichnen ist nur ein Schritt; der Loop schließt sich erst, wenn die Evidenz beeinflusst, was wir als Nächstes ausprobieren oder verwenden.

Das, was verbessert wird, ist das Target. Dabei kann es sich um eine Memory Policy, eine Retrieval Pipeline, Code zur Tool-Auswahl oder das Programm handeln, das den Context eines Models zusammenstellt. Model Training ist ein weiterer möglicher Eingriff. Der Loop kann mit festen Model Weights arbeiten: Der Agent kann das umgebende Programm verbessern, ohne ein Model zu trainieren. Diese erste Demo enthält bereits den äußeren LLM Agent. Spätere Teile verbessern den Evaluator und testen, ob agentic Search seine Kosten gegenüber einfacheren Methoden rechtfertigt.

Entscheiden, wie viel der Search delegiert wird

Angenommen, Sie wissen bereits, was Sie ausprobieren möchten: zwei Models in einem Extraction-Schritt vergleichen oder Memory-Schwellenwerte von 0.6, 0.7 und 0.8 testen. Sie können diese Entscheidungen selbst vorgeben und Ausführung, Scoring und Reporting automatisieren. Nach der Lektüre der Ergebnisse wählen Sie das nächste Experiment. Der Feedback Loop funktioniert auch dann, wenn das System die Kandidaten nicht selbst erfunden hat.

Ich verwende vier Arbeitsmodi, um diese Aufteilung sichtbar zu machen. Die Abbildung zeigt eine Möglichkeit, zunehmend mehr Experimentdesign zu delegieren: mit exakten Model-Auswahlen zu beginnen, das System nach Settings und genehmigten Components suchen zu lassen oder einen Agent zu bitten, Fehler zu untersuchen und das nächste Experiment auszuwählen. Der Mensch spezifiziert immer weniger von jedem Versuch, legt aber weiterhin die Regeln für die Search fest.

Die Namen der Modi beschreiben praktische Anordnungen für diese Serie und keine branchenweit standardisierte Autonomieskala. Was geändert werden darf und wer die Änderung auswählt, sind getrennte Entscheidungen. Optunas Beispiele für Search Spaces kombinieren Model-Auswahl mit Parameterbereichen. Scikit-learns Pipeline Search vergleicht alternative Components per gewöhnlicher Grid Search. Das Ersetzen einer Component macht den Prozess daher nicht automatisch agentic. Die Breiten der Abbildung veranschaulichen die Arbeitsaufteilung in diesen Beispielen; sie sind keine gemessenen Anteile von Kontrolle oder Aufwand.

Agent-led Investigation beschreibt, wie der nächste Versuch ausgewählt wird. Der Agent liest Fehler und frühere Ergebnisse, schlägt eine Änderung vor und passt sich nach dem Test an. Das entspricht der Unterscheidung in Anthropics Workflow- und Agent-Patterns: Ein vordefinierter Prozess kann die Ausführung automatisieren, während ein Agent seine nächsten Schritte anhand von Feedback steuert. Auch hybride Methoden sind möglich: DSPys MIPROv2 verwendet ein Model, um Instructions vorzuschlagen, und Bayesian Optimization, um deren Kombinationen zu durchsuchen. Ein fester Model-Vergleich benötigt keinen LLM Proposer; seine Ergebnisse fließen in den Feedback Loop ein, wenn sie das nächste Experiment oder die nächste Systemversion bestimmen.

Berechtigungen für Proposal, Ausführung und Übernahme bleiben getrennt. Ein Agent kann vor jedem Run eine Änderung zur Genehmigung vorlegen oder zulässige Änderungen unbeaufsichtigt testen, während ein Mensch die Übernahme prüft. Eine Liste genehmigter Components benötigt weiterhin kompatible Implementierungen; die Berechtigung zur Auswahl eines Adapters umfasst nicht die Berechtigung, einen solchen zu schreiben. In jedem Modus bleibt der Agent auf die erlaubten Änderungen, festen Checks und das Budget beschränkt und kann sich keine Deployment-Genehmigung erteilen. Mehr Delegation lässt außerdem Raum für Supervision: Anthropics Studie zu eingesetzten Agents beschreibt, wie User von der Genehmigung einzelner Aktionen zur Überwachung und Intervention übergehen.

Alle Modi können dasselbe Experiment Ledger: eine Aufzeichnung jedes versuchten Changes verwenden. Bewahren Sie den Kandidaten und seinen Parent, die exakte Änderung und ihre Quelle, die Versionen von Test und Environment, das Ergebnis, die Kosten sowie jeden Fehler oder jede Ablehnung auf. Diese Historie ermöglicht es einem Menschen, den nächsten Vorschlag an einen Agent zu übergeben – oder die Kontrolle zurückzunehmen –, ohne die Evidenz zu verlieren. Scores aus unterschiedlichen Testversionen müssen weiterhin unterscheidbar bleiben.

Diese Demo kombiniert Configuration Search mit Agent-led Investigation. Wir definieren fünf Settings, die Tests, das Budget und die Selection Rule. Der Agent wählt Werte und die nächste Hypothese anhand des Feedbacks; Python führt die Tests automatisch aus. Das Human Release Review bleibt davon getrennt. Das Repository akzeptiert außerdem ein von einer Person geliefertes Candidate JSON über lab evaluate. Model Sweeps, Component Adapters und von Agents geschriebener Code sind weitergehende Designoptionen für spätere Teile und keine implementierten Modi dieser Memory-Demo.

Warum das jetzt untersuchen?

Das Feedback-Prinzip ist aus dem Engineering vertraut. Die neuere Arbeit, die mich interessiert, setzt Coding Agents in den Untersuchungs- und Experimentprozess ein. Sie liefert konkrete Implementierungen, die wir analysieren können, statt vorauszusetzen, dass autonome Verbesserung funktionieren wird.

Karpathys autoresearch definiert ein kompaktes Experiment: ein Trainingsprogramm ändern, es unter einem festen Training-Time-Budget ausführen, das Validation-Ergebnis prüfen und aufzeichnen, ob der Versuch behalten, verworfen oder abgebrochen wurde. Die Instructions trennen die editierbare Trainingsdatei vom festen Evaluierungscode. Dadurch werden die vorgeschlagene Arbeit und ihr Erfolgskriterium überprüfbar.

Meta-Harness, ein Preprint vom März 2026, untersucht ein anderes Target: den Code, der steuert, welche Informationen eine LLM-Anwendung speichert, abruft und ihrem Model präsentiert. Sein Proposer kann den Source Code, Scores und Execution Traces früherer Kandidaten über ein Filesystem inspizieren. Die Experimenthistorie wird zum Arbeitsmaterial für die nächste Untersuchung.

Diese Projekte motivieren die Engineering-Frage der Serie: Was muss das umgebende System leisten, damit Experimente nützlich werden, sobald ein Agent Untersuchungen durchführen und Änderungen vorschlagen kann? Mehr Versuche allein belegen keine besseren Entscheidungen. Ein schwacher Evaluator kann eine schädliche Änderung belohnen, und ein Search-Prozess kann diese Schwäche wiederholt ausnutzen. Wir werden den Wert agentic Proposals gegen einfachere Alternativen testen, statt einen Vorteil vorauszusetzen.

Dem äußeren Agent ein kleines, überprüfbares Target geben

Stellen Sie sich einen Assistant vor, der sich Adas Account-Details merkt. Am 1. Januar lernt er, dass sie in Berlin lebt. Am 3. Januar erfährt er von einem Umzug nach Paris mit Wirkung zum 10. Januar. Auf die Frage nach ihrer Stadt am 5. Januar antwortet er Paris.

Die Memory enthält beide Fakten. Die Retrieval Rule bevorzugt den zuletzt empfangenen, ohne zu prüfen, wann er gültig wird. Das ist ein konkreter Fehler, den ein Improvement Agent untersuchen kann.

Das Target ist bewusst nur ein Memory Tool, kein vollständiger Assistant. Es empfängt vorbereitete Fakten, speichert oder verwirft sie und ruft einen Wert für eine Frage ab. Writer, Datumsverarbeitung, Retrieval und Answer Selection sind gewöhnliches Python. Conversation Extraction und die Generierung natürlicher Antworten lassen wir außerhalb dieses Experiments, damit wir identifizieren können, was eine Regeländerung tatsächlich bewirkt hat.

Das LLM befindet sich im äußeren Loop des Python-Experiments. Der Agent erhält Testergebnisse, entscheidet, welche Settings geändert werden, und bekommt das nächste Ergebnis zurück. Die aufgezeichneten Campaigns verwenden ein tatsächliches Model, um diese Änderungen auszuwählen.

Durch diese Aufteilung können wir den Engineering Loop testen, ohne eine zweite Quelle von Model-Verhalten in das Memory Tool einzuführen. In einer größeren Anwendung könnten beide Loops Models verwenden. Hier genügt ein LLM, um den Improvement Process agentic zu machen. Ein anderes LLM kann dieselbe Proposer-Rolle übernehmen; seine Proposals müssen demselben Schema folgen und dieselben Checks bestehen.

Einen Test verstehen, bevor der Score gelesen wird

Ein Scenario ist eine vollständige Testgeschichte. Ein Event ist eine an das Memory Tool gesendete Aktion: Schreiben, Abfragen oder Löschen. Das Scenario zum zukünftigen Umzug besteht aus vier Events:

  1. city = Berlin speichern, gültig ab 1. Januar.
  2. city = Paris speichern, empfangen am 3. Januar, aber gültig ab 10. Januar.
  3. Am 5. Januar nach der Stadt fragen. Berlin erwarten.
  4. Am 12. Januar nach der Stadt fragen. Paris erwarten.

Die Inputs sind bereits strukturiert. Der Paris-Fakt identifiziert beispielsweise den Owner (north Workspace, User ada), das Subject (account), die Property (city), den Value (Paris) und das Effective Date. Die Strings Berlin und Paris stammen aus den Testdaten und nicht aus einem Model, das Memories aus einer Conversation generiert.

Confidence ist ein vorgegebener Score, anhand dessen entschieden wird, ob ein vorgeschlagener Fakt gespeichert wird. Der Writer vergleicht ihn mit min_confidence. Ein delivery = courier-Proposal mit dem Score 0.4 wird beim Baseline Threshold von 0.7 verworfen, aber bei einem Threshold von 0.2 gespeichert. Der Testautor liefert den Score; er ist keine gemessene Wahrscheinlichkeit dafür, dass der Proposal korrekt ist. Wir evaluieren, wie die Storage Rule mit diesen Scores umgeht, nicht, ob ein Model sie zuverlässig schätzen kann.

Jedes Scenario beginnt mit einer leeren Python-Liste von Memory Records. Akzeptierte Updates schließen den Validity Period des vorherigen Werts und hängen einen neuen Record an. Nach den beiden City Writes beschreiben die Records Folgendes:

ValueReceivedValid fromValid until
Berlin1. Januar1. Januar10. Januar, ausgeschlossen
Paris3. Januar10. JanuarKein Enddatum

Die Answer Function gibt den ersten abgerufenen Record zurück, der zur angefragten Property passt. Der Evaluator vergleicht diesen Value mit der erwarteten Antwort. Ein vollständiges Scenario besteht nur dann, wenn jede Antwort korrekt ist und jeder anwendbare Data-Rule-Check besteht. Für Deletion, Owner Isolation und unzulässige Writes gibt es neben der Answer Quality explizite Checks.

Die Tests liefern Owner IDs direkt; diese Demo hat kein Authentication System. Ein realer Service muss diese IDs aus dem authentifizierten Request beziehen. Die explizite Ablehnung eines Inputs, der als Instruction gekennzeichnet ist, demonstriert außerdem nicht die Erkennung von Instructions, die in gewöhnlichem Text verborgen sind.

Byte sagt

Die neue Adresse ist ein gültiger Fakt über die nächste Woche. Wenn nach dem Datum der Frage gefiltert wird, erscheint sie nicht in der heutigen Antwort, wird aber nicht verworfen.

Auch Memory ein Schema geben

Auch die Fakten brauchen eigene Regeln. Ich verwende Schema-Guided Agent Memory (SGAM) für ein Pattern, bei dem Schemas den gespeicherten State und seinen Lifecycle steuern. Hier demonstrieren wir einen kleinen Teil davon: typisierte Fakten, Ownership, Source References, Validity Intervals und Deletion. Das spätere SGR-Schema steuert, was der äußere Agent vorschlagen darf; dieses Memory Schema steuert, was das Tool speichern darf.

Der Paris-Record nach dem zweiten Write enthält:

{
    "tenant": "north",
    "user": "ada",
    "entity": "account",
    "key": "city",
    "value": "Paris",
    "confidence": 0.95,
    "source": "user",
    "valid_from": "2026-01-10",
    "schema_version": 1,
    "memory_type": "fact",
    "id": "m002",
    "source_event_id": "future-move:event-2",
    "observed_at": "2026-01-03",
    "valid_to": null,
    "supersedes_memory_id": "m001"
}

source_event_id verweist auf das Event, das Paris geliefert hat. supersedes_memory_id verknüpft Paris mit dem Berlin-Record m001. schema_version: 1 identifiziert das Record-Format; es bedeutet nicht, dass das Programm alte Daten automatisch migrieren kann.

MemoryRecord und Memory.write() setzen dieses Format durch. Fehlende Source References, ungültige Datumsangaben und fehlerhafte Felder werden abgelehnt, bevor sich die gespeicherte Historie ändert. Ein geschlossenes Interval muss nach seinem Beginn enden. Berlin kann am 10. Januar enden, während Paris an diesem Tag beginnt; kein Record hat ein leeres Interval.

Angenommen, der nächste Write lautet Rome, ebenfalls gültig ab 10. Januar. Der Writer lehnt diesen Konflikt ab und lässt Paris unverändert. Ein zweiter Paris-Fakt für dasselbe Datum verwendet einfach den vorhandenen Record erneut. Ein Update mit einem früheren Effective Date wird ebenfalls abgelehnt: Dieser kleine Writer rekonstruiert keine verspätet eintreffende Historie. Das sind feste Policies, die der äußere Agent nicht ändern darf. Sein deduplicate Setting steuert wiederholte Bestätigungen mit einem späteren Effective Date.

Die Baseline ignoriert beim Lesen weiterhin bewusst Subject- und Date-Filter. Sie speichert gültige Records, kann aber den falschen auswählen. Das ist der Fehler, den wir dem Agent zur Reparatur geben. Owner Isolation gilt für jede Configuration, und Deletion entfernt alle Versionen der angeforderten Property innerhalb des Subjects dieses Owners.

Dies ist eine In-Memory-Demonstration dieser SGAM-Regeln. Es gibt keine persistente Database, keinen Retention Service und kein Migration System. Separate Writer Regression Tests prüfen abgelehnte Writes und Interval-Grenzen; sie sind keine zusätzlichen Scenarios im 20-Story Campaign Score.

Den Agent eine Änderung auswählen lassen

Eine Campaign ist ein Versuch, die ursprüngliche Configuration zu verbessern, beginnend mit einer frischen Agent-Historie. Eine Iteration ist ein Aufruf, in dem der Agent eine Änderung vorschlägt oder sich entscheidet zu stoppen. Die nächste Iteration erhält Feedback aus den vorherigen.

Die Campaign beginnt mit der Ausführung ausschließlich der Baseline. Sie besteht 13 von 20 Scenarios. Danach geben wir dem Agent:

  • die aktuellen Settings und ihre Bedeutung;
  • die Messwerte der Baseline;
  • Traces aus fehlgeschlagenen Scenarios, abgelehnten Writes und Duplicate Confirmations;
  • die Änderungen, die er vorschlagen darf;
  • frühere Proposals und ihre Ergebnisse, sofern vorhanden.

Der erste Request enthält keine fertigen verbesserten Configurations. Das Repository enthält außerdem vier vorbereitete Configurations zur Erklärung der Memory-Mechanik, aber der Live Agent beginnt nicht mit diesen Antworten.

Der Agent kann fünf Settings im bestehenden Tool ändern:

SettingWirkung der Änderung
min_confidenceÄndert den minimalen vorgegebenen Score, der zum Speichern eines Fakts erforderlich ist.
filter_entityBeschränkt Retrieval auf das angefragte Subject, etwa Home statt Work.
time_awareBeschränkt Retrieval auf Fakten, die am angefragten Datum gültig sind.
deduplicateVerwendet einen identischen aktiven Fakt erneut, statt eine weitere Confirmation zu speichern.
top_kLegt fest, wie viele Records ausgewählt werden, bevor der Answer Context gepackt wird.

Ein Proposal darf höchstens zwei Settings ändern. Numerische Werte haben Bounds: Confidence von 0 bis 1 und top_k von 1 bis 8. Der Contract zeichnet die zulässigen Configuration Changes des Tools auf; Agent-Schema und Validator ergänzen die Proposal-Regeln.

Der Agent hat in diesem Prozess keine Shell- oder Filesystem-Tools. Er kann weder Python, erwartete Antworten, Owner Isolation, Deletion-Verhalten, das Memory Schema, Conflict Handling, Scoring, Budgets noch Release Authority bearbeiten. Seine Ausgabe besteht aus Daten, die Python akzeptieren oder ablehnen kann. Dies ist ein kleines Configuration Experiment und keine Sandbox für beliebigen, von einem Agent geschriebenen Code.

Jedes Proposal als SGR Decision Record ausgeben

Ich verwende Schema-Guided Reasoning, um die Entscheidung überprüfbar zu machen. Jede Model Response enthält dieselben Felder:

FeldWas der Leser inspizieren können sollte
observationsWelches bereitgestellte Scenario und Event stützen die vorgeschlagene Änderung?
hypothesisWelche Rule scheint das Problem zu verursachen?
predicted_effectWas sollte sich verbessern, wenn wir die Änderung testen?
actionSchlägt der Agent eine Änderung vor oder stoppt er?
patchWelche zulässigen Settings sollen geändert werden?

Der OpenAI-Responses-Request verwendet ein striktes JSON Schema, das aus Pydantic Models generiert wird. Objects lehnen zusätzliche Felder ab, und jedes Patch-Feld ist erforderlich, darf aber null sein, also „dieses Setting unverändert lassen“. Structured Outputs beschränkt die Form der Response. Python prüft weiterhin, ob References existieren, Werte zulässig sind und die vorgeschlagene Configuration nicht bereits getestet wurde.

Das Schema beweist weder die Hypothese noch legt es das interne Reasoning des Models offen. Es handelt sich um knappe Decision Records, die wir gegen Evidenz prüfen können.

In der ersten aufgezeichneten Iteration identifizierte der Agent Retrieval über Subjects hinweg und Fakten, die außerhalb ihres Validity Intervals zurückgegeben wurden. Seine tatsächliche Response schlug diesen Patch vor:

{
    "min_confidence": null,
    "filter_entity": true,
    "time_aware": true,
    "deduplicate": null,
    "top_k": null
}

Diese beiden Settings wurden vom Model ausgewählt. Der Runner lieferte die Parent-ID und vergab die Candidate-ID; das Model konnte die Änderung weder auf einen beliebigen Parent noch auf eine beliebige Datei umleiten.

Die Änderung durch Python verfolgen

Sowohl die Baseline als auch die neue Configuration speichern dieselben Berlin- und Paris-Records. Die vorgeschlagene Änderung beeinflusst, welche Records Retrieval berücksichtigen darf.

In Memory.query() aktivieren diese Switches zwei Filter:

if self.config.filter_entity:
    eligible = [r for r in eligible if r["entity"] == event["entity"]]
if self.config.time_aware:
    eligible = [r for r in eligible if valid_at(r, event["as_of"])]

Der Validity Check schließt das Startdatum ein und das Enddatum aus:

def valid_at(item: dict, at: str) -> bool:
    return item["valid_from"] <= at and (
        item["valid_to"] is None or at < item["valid_to"]
    )

Die Daten verwenden YYYY-MM-DD, sodass ihre String-Reihenfolge der Kalenderreihenfolge entspricht. Bei der Frage vom 5. Januar wird Paris ausgeschlossen, weil es am 10. Januar gültig wird. Berlin bleibt verfügbar. Bei der Frage vom 12. Januar ist Paris gültig und Berlin historisch.

Python führt die vorgeschlagene Configuration für alle 20 Stories aus. Diese erste Änderung verbessert den Erfolg von 13/20 auf 19/20, wobei alle implementierten Hard Checks bestehen. Sie ändert zwei Filter gleichzeitig, daher misst der Suite-weite Gewinn ihren kombinierten Effekt. Der City Trace zeigt, was der Date Filter in diesem konkreten Fall bewirkt hat.

Der Runner wählt diese Configuration als Parent für das nächste Experiment aus. Diese Auswahl deployt sie nicht. Das Model erhält im nächsten Request das gemessene Ergebnis, die ausgewählten Settings und die verbleibende Evidenz zurück.

Die nächste Entscheidung muss das Ergebnis verwenden

Hier ist die vollständige erste Campaign. Jede Zeile ist eine echte Model Response und kein vorab geschriebener Schritt eines Demo-Scripts:

Durch Deduplication bleibt ein Record statt drei erhalten, während die Antwort unverändert bleibt. Über die Suite hinweg sank die durchschnittliche Zahl gespeicherter Records von 1,70 auf 1,60, bei weiterhin 19/20 erfolgreichen Scenarios.

Das dritte Proposal behandelte einen anderen Fehler. Eine nützliche Sprachpräferenz hatte eine vorgegebene Confidence von 0.6 und lag damit unter dem aktuellen 0.7 Threshold. Durch die Senkung des Thresholds auf 0.6 wurde sie zugelassen, während das unsichere Courier-Proposal mit einem Score von 0.4 weiterhin abgelehnt wurde. Der Erfolg erreichte 20/20; die durchschnittliche Zahl gespeicherter Records betrug 1,65, weil Memory nun den zusätzlichen nützlichen Fakt behielt.

Beim vierten Call entschied sich der Agent zu stoppen: Aus der bereitgestellten Evidenz hatte er keine weitere begründete Änderung vorzuschlagen. Das ist eine Model-Entscheidung und kein Beweis dafür, dass die Configuration global optimal ist.

Der nächste Request enthält die aktuellen Ergebnisse und früheren Entscheidungen. Nachdem der Agent gesehen hatte, dass sein Retrieval-Fix geholfen hatte, wandte er sich Storage und Write Admission zu. Der Runner lieferte diese nächsten Patches oder eine vorab geschriebene Schrittfolge nicht.

Die Selection Rule ist fest: Alle Hard Checks müssen bestehen; vollständiger Scenario-Erfolg wird bevorzugt, und bei gleichem Erfolg werden weniger gespeicherte Records bevorzugt. Ein schlechteres Ergebnis lässt den vorherigen Parent unverändert. Die Tests durchlaufen außerdem diesen Rejection Path mit einem vorgegebenen regressiven Proposal; es war kein gemessener Qualitätsrückgang in diesen drei Live Campaigns.

Ein separater Development Run enthält eine echte Validation Rejection: Der Agent verwies auf agent-01, eine Candidate-ID, als wäre sie ein Scenario. Die Response entsprach dem JSON Schema, aber ihre Reference identifizierte kein bereitgestelltes Event, weshalb Python sie vor der Evaluierung ablehnte. Der Controller gibt die abgelehnte Response und den konkreten Validation Error als Feedback zurück; Offline-Tests prüfen dieses Verhalten. Die drei unten berichteten Campaigns hatten keine Validation Failures.

Die Search Campaign wiederholen, nicht den deterministischen Test

Dieselbe Memory Configuration und dieselben Inputs erzeugen dieselben Antworten. Eine Wiederholung dieser Evaluierung fügt keine Evidenz zur Answer Quality hinzu. Der Runner prüft eine neue Configuration einmal und verwendet verifizierte Parent-Ergebnisse für Vergleiche erneut.

Der äußere Agent kann unterschiedliche Proposals auswählen, deshalb haben wir drei unabhängige Campaigns ausgeführt. Jede begann mit derselben Baseline von 13/20, erhielt eine frische History und hatte höchstens vier Model-Entscheidungen. Keine Campaign erhielt die Entdeckungen einer vorherigen Campaign.

Qualität und Kosten auf der richtigen Ebene betrachten

Das Experiment hat zwei unterschiedliche Kostenarten. Die Ausführung des Memory Tools verwendet lokale CPU-Zeit und erzeugt keine Model Calls. Die Ausführung des äußeren Proposers verwendet Input- und Output-Tokens. Ein Provider-Cost-Feld mit dem Wert null in einem Memory-Evaluierungsreport beschreibt nur das innere Tool; es ist nicht die Campaign-Kosten.

Für die aufgezeichnete Studie vom 11. September 2026 verwendeten wir GPT-5.6 Luna (gpt-5.6-luna), Reasoning Effort low, das gespeicherte SGR-Schema und die gespeicherten Instructions sowie maximal 4.096 Output-Tokens pro Call. Das Programm deaktivierte automatische SDK-Retries und setzte ein Request-Timeout von 60 Sekunden. Exakte Requests, zurückgegebene Model IDs, Usage und Call-Dauern bleiben erhalten.

Die tokenbasierte Kostenschätzung für die 12 Model Calls beträgt USD 0.039177 bei einem konfigurierten Budget von USD 0.50. Die Berechnung verwendet die veröffentlichten Model Rates, enthält den in Usage gemeldeten Cache-Write-Aufschlag und ignoriert Cache-Read-Rabatte. Es handelt sich um eine konservative Schätzung aus aufgezeichneter Usage, nicht um eine Rechnung. Hardware- und Entwicklungszeit sind in dieser Zahl nicht enthalten.

Vor jedem Call reserviert der Runner eine obere Schätzung auf Basis der begrenzten Input-Größe und der maximalen Output-Tokens. Wenn das verbleibende Budget diese Reservation nicht abdecken kann, stoppt er. Fehlgeschlagene oder unterbrochene Calls bleiben im Record; wenn Usage nicht verfügbar ist, wird der reservierte Betrag beibehalten und nicht als null behandelt.

Für Answer Quality bedeutet 20/20, dass jede Antwort und jeder anwendbare Hard Check für diese 20 vorbereiteten Stories bestanden wurde. Das bedeutet nicht, dass die Memory produktionsreif ist. Alle Stories sind öffentliche Development Cases; ausgewählte Traces und Suite-Feedback stehen dem Proposer zur Verfügung. Sie decken Updates, historische Fragen, Unsicherheit, Duplikate, Distractors, Owner Separation, Deletion und unzulässige Writes ab. Die Labels search, evaluation und adversarial strukturieren die ursprüngliche Suite; sie machen keinen dieser Fälle zu einem Hidden Test Set.

Diese kleine Suite greift Ideen aus LongMemEval, MemoryAgentBench, VehicleMemBench und GateMem auf. Inputs und Scoring stammen hier von uns; die Ergebnisse reproduzieren diese Benchmarks nicht.

Sie können außerdem vier vorbereitete Configurations im Repository vergleichen. Sie veranschaulichen, warum das Akzeptieren weiterer Fakten Antworten verschlechtern kann und wie Storage ohne höhere Answer Quality verbessert werden kann. Außerdem zeigen sie die menschlich spezifizierte Seite derselben Experiment-Infrastruktur: Der Autor liefert die Kandidaten, und Python evaluiert sie. Sie sind nützliche Lehrvergleiche, aber keine Evidenz dafür, dass agentic Search einen kompetenten Menschen oder eine andere Search-Methode schlägt.

Um den Agent neue Proposals auswählen zu lassen, klonen Sie das Companion und laden Sie die aufgezeichnete Evidenz herunter:

git clone --branch v0.2.2 --depth 1 https://github.com/slavadubrov/meta-engineering-ai-lab.git
cd meta-engineering-ai-lab
uv sync --frozen
uv run --frozen python scripts/fetch_evidence.py

Der Download prüft SHA-256 und stellt die vollständigen Aufzeichnungen unter artifacts/ wieder her. Er führt keine Model Calls aus. Wenn Sie die Evidenz bereits heruntergeladen haben, überspringen Sie diesen Schritt und führen Sie den Verification Command aus.

Speichern Sie ein OPENAI_API_KEY in einer lokalen Datei .env.local. Das Repository ignoriert diese Datei. Führen Sie anschließend Folgendes aus:

uv run --frozen --env-file .env.local python -m lab campaign \
  --live --campaigns 3 --iterations 4 --budget-usd 0.50 \
  --output artifacts/my-agent-study

--live aktiviert Provider Calls explizit. Ein Key in der Environment aktiviert weder die Offline-Memory-Commands noch den Browser als Live Agent. --campaigns 3 erstellt drei unabhängige Agent Histories; --iterations 4 begrenzt die Entscheidungen innerhalb jeder einzelnen. Verwenden Sie für jede Studie ein neues Output Directory: Vorhandene Evidenz wird niemals überschrieben.

Öffnen Sie artifacts/my-agent-study/report.md für die Campaign-Ergebnisse und Links zu jedem Request, jeder Response und jeder Python-Evaluierung. Vergleichen Sie die vorgeschlagenen Änderungen mit der oben aufgezeichneten Campaign: Der Agent kann sich anders entscheiden, obwohl die Memory-Tests deterministisch sind.

Die README ordnet Code und Commands zu. Der eingefrorene Campaign Report sowie Archive-Checksum und Example Index ermöglichen es dem Leser, die Evidenz dieses Artikels direkt zu inspizieren.

Experimenthistorie und User Memory getrennt halten

Das Memory Tool speichert Adas Stadt und Sprache. Die Experimenthistorie speichert, was der Agent gesehen hat, den vorgeschlagenen Patch, jede Ablehnung, die resultierenden Messwerte und welche Configuration zum nächsten Parent wurde. Diese Stores dienen unterschiedlichen Zwecken.

Jede Iteration bewahrt den exakten Request mit Instructions und Schema, die Provider Response, Usage und Timing, das Validation-Ergebnis und jede abgeschlossene Evaluierung auf. Fehlgeschlagene Proposals bleiben sichtbar. File Hashes binden die gespeicherte Evidenz an die für das Experiment verwendete Implementierung und die verwendeten Inputs.

Da es sich um synthetische Fakten handelt, kann das öffentliche Protokoll vollständige Zustände behalten. Reale Traces benötigen eine eigene Retention Policy: Das Löschen eines Fakts aus dem Memory Tool entfernt frühere Kopien aus Experiment Logs oder Backups nicht. Der Deletion Test der Demo prüft die Records des Tools und spätere Reads, nicht die Löschung aus jedem möglichen Store.

Was der nächste Artikel herausfordern muss

Wir haben nun einen Agent innerhalb des Improvement Loops. Er schlägt eine Änderung vor, erhält ein gemessenes Ergebnis, wählt die nächste Änderung und kann sich zum Stoppen entscheiden. Ungültige Proposals durchlaufen einen separaten Rejection Path und bleiben im Record. Seine Autorität ist auf Configuration beschränkt; Testing und Release Review bleiben getrennte Verantwortlichkeiten.

Das nächste Risiko ist der Evaluator selbst. Wenn Erfolg das Behalten jedes Fakts belohnt, kann der Agent lernen, Schätzungen zu speichern. Wenn eine Suite nur nach der aktuellen Stadt fragt, kann sie eine Änderung übersehen, die nützliche Historie zerstört. Ein leistungsfähigerer Proposer kann schwache Messungen effizienter ausnutzen.

Teil 2, Erst Scorable werden, dann Autonomous werden, fragt, wie diese Messungen getestet werden müssen, bevor der Proposer mehr Freiheit erhält. Die 20/20 der ersten Campaign sind der Ausgangspunkt für diese Untersuchung.
