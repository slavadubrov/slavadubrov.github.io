Dieser Artikel richtet sich an Engineers, die Agents bauen, die Fehler untersuchen, Änderungen testen und die Ergebnisse zur Verbesserung von AI-Systemen nutzen. Er eröffnet Meta-Engineering AI Systems, einen sechsteiligen Leitfaden zu Closed-Loop AI Engineering. In diesem ersten Teil bauen Sie einen LLM-gesteuerten Verbesserungsprozess rund um ein kleines Memory-Tool und untersuchen die Evidenz hinter jedem vorgeschlagenen Change.

Das Verhalten einer AI-Anwendung hängt von mehr als ihrem Model ab. Prompts, abgerufene Informationen, gespeicherte Memory, Tools und Application Code beeinflussen gleichermaßen, was geschieht. Wenn eine Antwort falsch ist, können mehrere Änderungen plausibel erscheinen. Die Engineering-Aufgabe besteht darin zu entscheiden, welche Änderung hilft, was sie kostet und was sie außerdem kaputt macht.

Ich verwende Meta-Engineering hier für das Design des Verbesserungsprozesses selbst: welche Evidenz der Agent sieht, was er ändern darf, wie wir seine Vorschläge testen und wer entscheidet, ob wir sie übernehmen. Closed-Loop beschreibt, wie dieser Prozess aus seinen Experimenten lernt. Jedes Ergebnis beeinflusst, was wir als Nächstes ausprobieren oder einsetzen – auch dann, wenn ein vorgeschlagener Change scheitert.

Die Frage, die sich durch alle sechs Teile zieht, lautet: Wie viel dieser Arbeit können wir an einen Agent delegieren, während Evidenz und Übernahmeentscheidung vertrauenswürdig bleiben? Um diesen Prozess zu entwerfen, müssen wir zunächst unterscheiden, was wir ändern können und wie wir entscheiden, ob eine Änderung geholfen hat.

Was Meta-Engineering optimiert

Prompt Engineering ändert die Instruktionen. Context Engineering ändert, welche Informationen das Model erhält. Loop Engineering ändert, wie ein Agent handelt, Ergebnisse beobachtet, erneut versucht und stoppt. Graph Engineering ändert, wie Schritte oder Agents verbunden werden und Arbeit routen. Das sind sich überschneidende Designentscheidungen innerhalb eines AI-Systems.

Meta-Engineering organisiert die Experimente, die alle vier Bereiche optimieren. Prompt-Formulierung, Context Assembly, Loop-Konfiguration und Graph-Struktur werden zu Parametern, die kontrollierte Experimente variieren und messen können. Wir beurteilen einen Change anhand der Ergebnisse des Gesamtsystems – einschließlich Qualität, Kosten und erforderlichem Verhalten. Graph-Struktur bleibt ein sinnvoller Optimierungsbereich; der Experimentprozess zeigt uns, ob ein bestimmter Graph-Change hilft. Diese Serie behandelt diesen Prozess für Agent-Systeme. Memory ist das erste durchgearbeitete Beispiel.

Was den Loop schließt

Der Experimentprozess im Diagramm ist der Improvement Loop. Er arbeitet über Versionen einer Anwendung hinweg, untersucht abgeschlossene Runs und testet Änderungen, die spätere Runs verbessern sollen. Innerhalb der Anwendung wählt der Runtime Loop eine Aktion, führt einen Tool Call aus, beobachtet das Ergebnis und setzt die aktuelle Aufgabe des Users fort. Loop Engineering ändert dieses Runtime-Verhalten; Meta-Engineering testet, ob der Change die Ergebnisse des Systems verbessert.

Der Improvement Loop beginnt mit Evidenz: einer falschen Antwort, einer unerwünschten Zustandsänderung, überhöhten Kosten oder einem anderen beobachtbaren Fehler. Ein Trace zeichnet die Schritte hinter diesem Ergebnis auf. Der Proposer wählt einen Candidate, also eine spezifische Version einer Änderung. Ein Runner führt den Candidate auf definierten Tasks aus, und ein Evaluator prüft das resultierende Verhalten gegen die Anforderungen. Im Live-Experiment dieses Artikels ist ein LLM Agent der Proposer:

Die Evaluierung informiert eine Entscheidung; sie autorisiert sich nicht selbst. Jemand muss entscheiden, ob der gemessene Nutzen die Übernahme des Changes rechtfertigt – einschließlich seiner Auswirkungen auf Kosten, Berechtigungen und anderes erforderliches Verhalten. In dieser Serie beginnen wir mit einem Human Reviewer. Der Proposer kann einen Change vorschlagen, aber weder die Checks umschreiben noch sein eigenes Budget erhöhen oder sich selbst eine Freigabe erteilen.

Es gibt zwei Rückwege. Die Experimenthistorie fließt in spätere Vorschläge ein, auch wenn ein Candidate abgelehnt wird. Wird ein Candidate freigegeben und übernommen, liefert sein Verhalten neue Evidenz aus der Nutzung. Ein Change muss reversibel bleiben, wenn diese Evidenz dem ursprünglichen Experiment widerspricht. Einen Score aufzuzeichnen ist nur ein Schritt; der Loop ist erst geschlossen, wenn die Evidenz beeinflusst, was wir als Nächstes ausprobieren oder einsetzen.

Das, was verbessert wird, ist das Target. Dabei kann es sich um eine Memory Policy, eine Retrieval Pipeline, Tool-Selection-Code oder das Programm handeln, das den Context eines Models zusammenstellt. Model Training ist eine weitere mögliche Intervention. Der Loop kann mit fixierten Model Weights arbeiten: Der Agent kann das umgebende Programm verbessern, ohne ein Model zu trainieren. Diese erste Demo enthält bereits den äußeren LLM Agent. Spätere Teile stärken den Evaluator und prüfen, ob sich agentic Search im Vergleich zu einfacheren Methoden lohnt.

Entscheiden, wie viel der Suche delegiert werden soll

Die Entscheidung, was geändert wird, ist von der Entscheidung getrennt, wer das Experiment entwirft. Jeder der vier oben genannten Designbereiche kann von Menschen spezifizierte Änderungen, automatisierte Suche oder agentengeleitete Untersuchung umfassen.

Angenommen, Sie wissen bereits, was Sie ausprobieren möchten: zwei Models in einem Extraction-Schritt vergleichen oder Memory-Schwellenwerte von 0.6, 0.7 und 0.8 testen. Sie können diese Auswahl selbst vorgeben und Ausführung, Scoring und Reporting automatisieren. Nach dem Lesen der Ergebnisse wählen Sie das nächste Experiment. Der Feedback Loop funktioniert, obwohl das System die Candidates nicht selbst erfunden hat.

Ich verwende vier Arbeitsmodi, um diese Aufteilung sichtbar zu machen. Die Abbildung zeigt eine Möglichkeit, schrittweise mehr Experimentdesign zu delegieren: mit exakten Model-Auswahlen beginnen, das System Settings und freigegebene Components durchsuchen lassen oder einen Agent bitten, Fehler zu untersuchen und das nächste Experiment auszuwählen. Der Mensch spezifiziert weniger von jedem Versuch und legt gleichzeitig weiterhin die Regeln für die Suche fest.

Die Namen der Modi beschreiben praktische Anordnungen für diese Serie und keine branchenweit standardisierte Autonomieskala. Optunas Beispiele für Search Spaces kombinieren Model-Auswahl mit Parameterbereichen. Scikit-learns Pipeline Search vergleicht alternative Components durch gewöhnliche Grid Search. Das Ersetzen einer Component macht den Prozess daher nicht automatisch agentic. Die Breiten der Abbildung veranschaulichen die Arbeitsaufteilung in diesen Beispielen; sie sind keine gemessenen Anteile von Kontrolle oder Aufwand.

Agentengeleitete Untersuchung beschreibt, wie der nächste Versuch ausgewählt wird. Der Agent liest Fehler und frühere Ergebnisse, schlägt einen Change vor und passt sich nach dem Test an. Das folgt der Unterscheidung in Anthropics Workflow- und Agent-Patterns: Ein vordefinierter Prozess kann die Ausführung automatisieren, während ein Agent seine nächsten Schritte anhand von Feedback steuert. Auch hybride Methoden sind möglich: DSPys MIPROv2 verwendet ein Model, um Instruktionen vorzuschlagen, und Bayesian Optimization, um ihre Kombinationen zu durchsuchen. Ein fixer Model-Vergleich benötigt keinen LLM Proposer; seine Ergebnisse fließen in den Feedback Loop ein, wenn sie das nächste Experiment oder die nächste Systemversion steuern.

Berechtigungen für Proposal, Ausführung und Übernahme bleiben getrennt. Ein Agent kann vor jedem Run einen Change zur Freigabe vorlegen oder erlaubte Changes unbeaufsichtigt testen, während ein Mensch die Übernahme prüft. Auch eine freigegebene Component-Liste benötigt kompatible Implementierungen; die Berechtigung, einen Adapter auszuwählen, schließt nicht die Berechtigung ein, einen zu schreiben. In jedem Modus bleibt der Agent innerhalb der erlaubten Changes, fixierten Checks und des Budgets und kann sich keine Deployment-Freigabe erteilen. Mehr Delegation lässt außerdem Raum für Supervision: Anthropics Studie zu eingesetzten Agents beschreibt, wie User von der Freigabe einzelner Aktionen zu Monitoring und Intervention wechseln.

Alle Modi können dasselbe Experiment Ledger verwenden: eine Aufzeichnung jedes versuchten Changes. Halten Sie Candidate und Parent, den exakten Change und dessen Quelle, die Versionen von Test und Environment, Ergebnis, Kosten sowie jeden Fehler oder jede Ablehnung fest. Diese Historie ermöglicht es einem Menschen, den nächsten Vorschlag an einen Agent zu übergeben – oder die Aufgabe wieder selbst zu übernehmen –, ohne die Evidenz zu verlieren. Scores aus unterschiedlichen Testversionen müssen weiterhin unterschieden werden.

Diese Demo kombiniert Konfigurationssuche mit agentengeleiteter Untersuchung. Wir definieren fünf Settings, die Tests, das Budget und die Selection Rule. Der Agent wählt Werte und die nächste Hypothese anhand von Feedback; Python führt die Tests automatisch aus. Das Human Release Review bleibt davon getrennt. Das Repository akzeptiert außerdem ein von einer Person geliefertes Candidate-JSON über lab evaluate. Model Sweeps, Component-Adapter und von Agents geschriebener Code sind breitere Designoptionen für spätere Teile und keine implementierten Modi dieser Memory-Demo.

Warum das jetzt untersuchen?

Das Feedback-Prinzip ist aus dem Engineering bekannt. Die neuere Arbeit, die mich interessiert, setzt Coding Agents in den Untersuchungs- und Experimentprozess ein. Sie liefert konkrete Implementierungen, die wir untersuchen können, statt uns darauf zu verlassen, dass autonome Verbesserung funktionieren wird.

Karpathys Autoresearch spezifiziert ein kompaktes Experiment: Ein Trainingsprogramm wird geändert, unter einem fixierten Trainingszeit-Budget ausgeführt, das Validation-Ergebnis untersucht und aufgezeichnet, ob der Versuch beibehalten, verworfen oder abgebrochen wurde. Die Instruktionen trennen die editierbare Trainingsdatei vom fixierten Evaluierungscode. Dadurch werden die vorgeschlagene Arbeit und ihr Erfolgskriterium nachvollziehbar.

Der Proposer kann den Source, Scores und Execution Traces früherer Candidates über ein Filesystem untersuchen. Die Experimenthistorie wird zum Arbeitsmaterial für die nächste Untersuchung.

Dem äußeren Agent ein kleines, nachvollziehbares Target geben

Stellen Sie sich einen Assistant vor, der Adas Kontaktdaten kennt. Am 1. Januar erfährt er, dass sie in Berlin lebt. Am 3. Januar erfährt er von einem Umzug nach Paris mit Wirkung zum 10. Januar. Auf die Frage nach ihrer Stadt am 5. Januar antwortet er Paris.

Die Memory enthält beide Fakten. Die Retrieval Rule bevorzugt den zuletzt empfangenen Fakt, ohne zu prüfen, ab wann er gültig wird. Das ist ein konkreter Fehler, den ein Improvement Agent untersuchen kann.

Das Target ist bewusst nur ein Memory-Tool und kein vollständiger Assistant. Es erhält vorbereitete Fakten, speichert oder verwirft sie und ruft einen Wert für eine Frage ab. Writer, Datumsbehandlung, Retrieval und Answer Selection sind gewöhnliches Python. Conversation Extraction und Natural-Language Answer Generation lassen wir außerhalb dieses Experiments, damit wir erkennen können, was eine Rule-Änderung tatsächlich bewirkt hat.

Das LLM befindet sich im äußeren Loop des Python-Experiments. Der Agent erhält Testergebnisse, entscheidet, welche Settings geändert werden, und bekommt das nächste Ergebnis zurück. In den aufgezeichneten Campaigns verwendet ein tatsächliches Model diese Changes.

Diese Aufteilung ermöglicht es uns, den Engineering Loop zu testen, ohne eine zweite Quelle von Model-Verhalten innerhalb des Memory-Tools einzuführen. In einer größeren Anwendung könnten beide Loops Models verwenden. Hier genügt ein LLM, um den Verbesserungsprozess agentic zu machen. Ein anderes LLM kann dieselbe Proposer-Rolle übernehmen; seine Proposals müssen dasselbe Schema befolgen und dieselben Checks bestehen.

Einen Test verstehen, bevor der Score gelesen wird

Ein Scenario ist eine vollständige Testgeschichte. Ein Event ist eine an das Memory-Tool gesendete Aktion: Write, Query oder Delete. Das Scenario zum zukünftigen Umzug umfasst vier Events:

  1. city = Berlin speichern, gültig ab dem 1. Januar.
  2. city = Paris speichern, empfangen am 3. Januar, aber gültig ab dem 10. Januar.
  3. Am 5. Januar nach der Stadt fragen. Berlin erwarten.
  4. Am 12. Januar nach der Stadt fragen. Paris erwarten.

Die Inputs sind bereits strukturiert. Der Paris-Fakt identifiziert beispielsweise den Owner (north Workspace, User ada), das Subject (account), die Property (city), den Value (Paris) und das Gültigkeitsdatum. Die Strings Berlin und Paris stammen aus den Testdaten und nicht aus einem Model, das Memory aus einer Conversation generiert.

Confidence ist ein mitgelieferter Score, anhand dessen entschieden wird, ob ein vorgeschlagener Fakt gespeichert wird. Der Writer vergleicht ihn mit min_confidence. Ein mit delivery = courier bewerteter Proposal mit 0.4 wird beim Baseline-Threshold von 0.7 verworfen, aber bei einem Threshold von 0.2 gespeichert. Der Testautor liefert den Score; er ist keine gemessene Wahrscheinlichkeit dafür, dass der Proposal korrekt ist. Wir evaluieren, wie die Storage Rule mit diesen Scores umgeht, nicht ob ein Model sie zuverlässig schätzen kann.

Jedes Scenario beginnt mit einer leeren Python-Liste von Memory Records. Akzeptierte Updates schließen den Gültigkeitszeitraum des vorherigen Werts und hängen einen neuen Record an. Nach den beiden City-Writes beschreiben die Records Folgendes:

WertEmpfangenGültig abGültig bis
Berlin1. Januar1. Januar10. Januar, ausgeschlossen
Paris3. Januar10. JanuarKein Enddatum

Die Answer Function gibt den ersten abgerufenen Record zurück, der zur angefragten Property passt. Der Evaluator vergleicht diesen Wert mit der erwarteten Antwort. Ein vollständiges Scenario besteht nur dann, wenn jede Antwort korrekt ist und jeder anwendbare Data-Rule-Check besteht. Delete, Owner Isolation und Prohibited Writes verfügen neben der Answer Quality über explizite Checks.

Die Tests liefern Owner IDs direkt; diese Demo besitzt kein Authentication-System. Ein echter Service muss diese IDs aus dem authentifizierten Request beziehen. Das explizite Zurückweisen eines Inputs, der als Instruktion gekennzeichnet ist, demonstriert außerdem nicht die Erkennung von Instruktionen, die in gewöhnlichem Text verborgen sind.

Die neue Adresse ist ein gültiger Fakt über die nächste Woche. Ein Filter anhand des Fragedatums hält sie aus der heutigen Antwort heraus, ohne sie zu verwerfen.

Auch Memory ein Schema geben

Auch Fakten benötigen eigene Regeln. Für das Muster, bei dem Schemas den gespeicherten Zustand und seinen Lifecycle steuern, verwende ich Schema-Guided Agent Memory (SGAM). Hier demonstrieren wir einen kleinen Teil davon: typisierte Fakten, Ownership, Source References, Gültigkeitsintervalle und Delete. Das spätere SGR-Schema steuert, was der äußere Agent vorschlagen darf; dieses Memory-Schema steuert, was das Tool speichern darf.

Der Paris-Record nach dem zweiten Write enthält:

{
    "tenant": "north",
    "user": "ada",
    "entity": "account",
    "key": "city",
    "value": "Paris",
    "confidence": 0.95,
    "source": "user",
    "valid_from": "2026-01-10",
    "schema_version": 1,
    "memory_type": "fact",
    "id": "m002",
    "source_event_id": "future-move:event-2",
    "observed_at": "2026-01-03",
    "valid_to": null,
    "supersedes_memory_id": "m001"
}

source_event_id verweist auf das Event, das Paris geliefert hat. supersedes_memory_id verknüpft Paris mit dem Berlin-Record, m001. schema_version: 1 identifiziert das Record-Format; daraus folgt nicht, dass das Programm alte Daten automatisch migrieren kann.

MemoryRecord und Memory.write() erzwingen dieses Format. Fehlende Source References, ungültige Daten und fehlerhafte Felder werden zurückgewiesen, bevor sich die gespeicherte Historie ändert. Ein geschlossenes Intervall muss nach seinem Start enden. Berlin kann am 10. Januar enden, während Paris an diesem Tag beginnt; kein Record hat ein leeres Intervall.

Angenommen, der nächste Write lautet Rome, ebenfalls gültig ab dem 10. Januar. Der Writer weist diesen Konflikt zurück und lässt Paris unverändert. Ein zweiter Paris-Fakt für dasselbe Datum verwendet einfach den bestehenden Record erneut. Ein Update mit einem früheren Gültigkeitsdatum wird ebenfalls zurückgewiesen: Dieser kleine Writer rekonstruiert keine verspätet eintreffende Historie. Das sind fixe Policies, die der äußere Agent nicht ändern kann. Sein deduplicate Setting steuert wiederholte Bestätigungen mit einem späteren Gültigkeitsdatum.

Die Baseline ignoriert beim Lesen weiterhin bewusst Subject- und Datumsfilter. Sie speichert gültige Records, kann aber den falschen auswählen. Das ist der Fehler, den wir dem Agent zur Reparatur geben. Owner Isolation gilt für jede Konfiguration, und Delete entfernt alle Versionen der angefragten Property innerhalb des Subjects dieses Owners.

Dies ist eine In-Memory-Demonstration dieser SGAM-Regeln. Es gibt weder eine durable Database noch einen Retention Service oder ein Migrationssystem. Separate Writer-Regressionstests prüfen zurückgewiesene Writes und Intervallgrenzen; sie sind keine zusätzlichen Scenarios im Score der 20-Story-Campaign.

Den Agent einen Change auswählen lassen

Eine Campaign ist ein Versuch, die ursprüngliche Konfiguration zu verbessern, und beginnt mit einer frischen Agent-Historie. Eine Iteration ist ein Call, in dem der Agent einen Change vorschlägt oder beschließt zu stoppen. Die nächste Iteration erhält Feedback aus den vorherigen.

Die Campaign beginnt mit der Ausführung nur der Baseline. Sie besteht 13 von 20 Scenarios. Anschließend geben wir dem Agent:

  • die aktuellen Settings und ihre Bedeutungen;
  • die Messwerte der Baseline;
  • Traces aus fehlschlagenden Scenarios, zurückgewiesenen Writes und doppelten Bestätigungen;
  • die Changes, die er vorschlagen darf;
  • frühere Proposals und ihre Ergebnisse, sofern vorhanden.

Der erste Request enthält keine fertigen verbesserten Konfigurationen. Das Repository enthält außerdem vier vorbereitete Konfigurationen zur Erklärung der Memory-Mechanik, aber der Live-Agent startet nicht mit diesen Antworten.

Der Agent kann fünf Settings des bestehenden Tools ändern:

SettingWirkung der Änderung
min_confidenceÄndert den minimal erforderlichen gelieferten Score, um einen Fakt zu speichern.
filter_entityBeschränkt Retrieval auf das angefragte Subject, etwa Home statt Work.
time_awareBeschränkt Retrieval auf Fakten, die am angefragten Datum gültig sind.
deduplicateVerwendet einen identischen aktiven Fakt erneut, statt eine weitere Bestätigung zu speichern.
top_kLegt fest, wie viele Records vor dem Packen des Answer Context ausgewählt werden.

Ein Proposal darf höchstens zwei Settings ändern. Numerische Werte haben Grenzen: Confidence von 0 bis 1 und top_k von 1 bis 8. Der Contract dokumentiert die erlaubten Konfigurationsänderungen des Tools; Agent-Schema und Validator ergänzen die Proposal-Regeln.

Der Agent besitzt in diesem Prozess weder Shell- noch Filesystem-Tools. Er kann Python, Expected Answers, Owner Isolation, Delete-Verhalten, Memory-Schema, Conflict Handling, Scoring, Budgets oder Release Authority nicht editieren. Sein Output sind Daten, die Python akzeptieren oder ablehnen kann. Dies ist ein kleines Konfigurationsexperiment und keine Sandbox für beliebigen von einem Agent geschriebenen Code.

Jeden Proposal zu einem SGR Decision Record machen

Ich verwende Schema-Guided Reasoning, um die Entscheidung nachvollziehbar zu machen. Jede Model Response besitzt dieselben Felder:

FeldWas der Leser untersuchen können sollte
observationsWelches bereitgestellte Scenario und Event stützen den vorgeschlagenen Change?
hypothesisWelche Rule scheint das Problem zu verursachen?
predicted_effectWas sollte sich beim Testen des Changes verbessern?
actionSchlägt der Agent einen Change vor oder stoppt er?
patchWelche erlaubten Settings sollten geändert werden?

Der OpenAI-Responses-Request verwendet ein striktes JSON Schema, das aus Pydantic-Modellen generiert wird. Objects weisen zusätzliche Felder zurück, und jedes Patch-Feld ist erforderlich, darf aber null sein, also „dieses Setting unverändert lassen“. Structured Outputs beschränkt die Form der Response. Python prüft weiterhin, ob References existieren, Werte erlaubt sind und die vorgeschlagene Konfiguration noch nicht getestet wurde.

Das Schema beweist weder die Hypothese noch legt es die interne Reasoning des Models offen. Es handelt sich um kurze Decision Records, die wir gegen die Evidenz prüfen können.

In der ersten aufgezeichneten Iteration identifizierte der Agent Retrieval über mehrere Subjects hinweg und Fakten, die außerhalb ihres Gültigkeitsintervalls zurückgegeben wurden. Seine tatsächliche Response schlug diesen Patch vor:

{
    "min_confidence": null,
    "filter_entity": true,
    "time_aware": true,
    "deduplicate": null,
    "top_k": null
}

Diese beiden Settings wurden vom Model ausgewählt. Der Runner lieferte die Parent-ID und vergab die Candidate-ID; das Model konnte den Change nicht auf einen beliebigen Parent oder ein beliebiges File umleiten.

Den Change durch Python verfolgen

Sowohl die Baseline als auch die neue Konfiguration speichern dieselben Berlin- und Paris-Records. Der vorgeschlagene Change beeinflusst, welche Records Retrieval berücksichtigen darf.

In Memory.query() aktivieren diese Switches zwei Filter:

if self.config.filter_entity:
    eligible = [r for r in eligible if r["entity"] == event["entity"]]
if self.config.time_aware:
    eligible = [r for r in eligible if valid_at(r, event["as_of"])]

Der Validity Check schließt das Startdatum ein und das Enddatum aus:

def valid_at(item: dict, at: str) -> bool:
    return item["valid_from"] <= at and (
        item["valid_to"] is None or at < item["valid_to"]
    )

Die Daten verwenden YYYY-MM-DD, sodass ihre String-Reihenfolge der Kalenderreihenfolge entspricht. Bei der Frage vom 5. Januar wird Paris ausgeschlossen, weil der Fakt erst am 10. Januar gültig wird. Berlin bleibt verfügbar. Bei der Frage vom 12. Januar ist Paris gültig und Berlin historisch.

Python führt die vorgeschlagene Konfiguration auf allen 20 Stories aus. Dieser erste Change verbessert den Erfolg von 13/20 auf 19/20, wobei alle implementierten Hard Checks bestehen. Er ändert zwei Filter gemeinsam, daher misst der Gewinn über die gesamte Suite ihren kombinierten Effekt. Der City-Trace zeigt, was der Date-Filter in diesem konkreten Fall bewirkt hat.

Der Runner wählt diese Konfiguration als Parent für das nächste Experiment aus. Diese Auswahl stellt keinen Deployment dar. Das Model erhält im nächsten Request das gemessene Ergebnis, die ausgewählten Settings und die verbleibende Evidenz.

Die nächste Entscheidung muss das Ergebnis verwenden

Hier ist die vollständige erste Campaign. Jede Zeile ist eine echte Model Response und kein vorab geschriebener Schritt eines Demo-Scripts:

Über die Suite hinweg sank die durchschnittliche Zahl gespeicherter Records von 1,70 auf 1,60, während der Erfolg bei 19/20 blieb.

Der dritte Proposal adressierte einen anderen Fehler. Eine nützliche Sprachpräferenz hatte einen gelieferten Confidence-Wert von 0.6, der unter dem aktuellen 0.7-Threshold lag. Durch das Senken des Thresholds auf 0.6 wurde sie zugelassen, während der unsichere Courier-Proposal mit dem Score 0.4 weiterhin abgewiesen wurde. Der Erfolg erreichte 20/20; die durchschnittliche Zahl gespeicherter Records betrug nun 1,65, weil Memory den zusätzlichen nützlichen Fakt behielt.

Beim vierten Call entschied sich der Agent zum Stoppen: Aus der bereitgestellten Evidenz hatte er keinen weiteren unterstützten Change vorzuschlagen. Das ist eine Model-Entscheidung und kein Beweis dafür, dass die Konfiguration global optimal ist.

Der nächste Request enthält die aktuellen Ergebnisse und die früheren Entscheidungen. Nachdem der Agent gesehen hatte, dass sein Retrieval-Fix geholfen hatte, wandte er sich Storage und Write Admission zu. Der Runner lieferte diese nächsten Patches oder eine vorab geschriebene Schrittfolge nicht.

Die Selection Rule ist fixiert: Alle Hard Checks müssen bestehen; danach wird besserer Complete-Scenario-Success bevorzugt und bei gleichem Erfolg die geringere Zahl gespeicherter Records. Ein schlechteres Ergebnis lässt den vorherigen Parent bestehen. Die Tests enthalten außerdem diesen Rejection Path mit einem vorgegebenen regressiven Proposal; er war in diesen drei Live-Campaigns keine gemessene Qualitätsregression.

Ein separater Development-Run enthält eine echte Validation Rejection: Der Agent verwies auf agent-01, eine Candidate-ID, als wäre sie ein Scenario. Die Response entsprach dem JSON Schema, aber ihre Reference identifizierte kein bereitgestelltes Event, weshalb Python sie vor der Evaluierung zurückwies. Der Controller gibt die zurückgewiesene Response und den konkreten Validation Error als Feedback zurück; Offline-Tests prüfen dieses Verhalten. Die drei unten berichteten Campaigns hatten keine Validation Failures.

Die Search-Campaign wiederholen, nicht den deterministischen Test

Dieselbe Memory-Konfiguration und dieselben Inputs erzeugen dieselben Antworten. Eine Wiederholung dieser Evaluierung liefert keine zusätzliche Evidenz zur Answer Quality. Der Runner prüft eine neue Konfiguration einmal und verwendet verifizierte Parent-Ergebnisse für Vergleiche erneut.

Der äußere Agent kann unterschiedliche Proposals auswählen, daher haben wir drei unabhängige Campaigns ausgeführt. Jede begann bei derselben Baseline von 13/20, erhielt eine frische Historie und hatte höchstens vier Model-Entscheidungen. Keine Campaign erhielt die Entdeckungen der vorherigen Campaign.

Es gab 12 Model Calls: neun Proposals, die Python evaluierte, gefolgt von drei Stop-Entscheidungen. Jede Campaign führte die Baseline plus drei neue Konfigurationen auf 20 Stories aus: 80 Memory-Tool-Ausführungen pro Campaign. Die 20 Stories blieben währenddessen unverändert.

Sie schätzt nicht, wie zuverlässig der Optimizer unbekannte Systeme verbessern wird. Ein stärkerer Vergleich gehört in einen späteren Teil der Serie: wiederholte Campaigns unter angeglichenen Budgets, konkurrierende Proposal-Methoden und Tests, die der Proposer nicht einsehen kann.

Qualität und Kosten auf der richtigen Ebene lesen

Das Experiment hat zwei unterschiedliche Kostenarten. Die Ausführung des Memory-Tools verwendet lokale CPU-Zeit und erzeugt keine Model Calls. Die Ausführung des äußeren Proposers verwendet Input- und Output-Tokens. Ein Provider-Cost-Feld mit null in einem Memory-Evaluierungsreport beschreibt nur das innere Tool; es ist nicht die Kostenangabe der Campaign.

Für die aufgezeichnete Studie vom 11. September 2026 verwendeten wir GPT-5.6 Luna (gpt-5.6-luna), Reasoning Effort low, das gespeicherte SGR-Schema und die entsprechenden Instruktionen sowie maximal 4.096 Output-Tokens pro Call. Das Programm deaktivierte automatische SDK-Retries und setzte ein Request-Timeout von 60 Sekunden. Exakte Requests, zurückgegebene Model IDs, Usage und Call-Dauern bleiben erhalten.

Die tokenbasierte Kostenschätzung für die 12 Model Calls beträgt USD 0.039177 gegenüber einem konfigurierten Budget von USD 0.50. Die Berechnung verwendet die veröffentlichten Model Rates, enthält den in Usage gemeldeten Cache-Write-Aufschlag und ignoriert Cache-Read-Rabatte. Es handelt sich um eine konservative Schätzung aus aufgezeichneter Usage, nicht um eine Rechnung. Hardware- und Entwicklungszeit sind darin nicht enthalten.

Vor jedem Call reserviert der Runner eine obere Schätzung auf Basis einer begrenzten Input-Größe und der maximalen Output-Tokens. Wenn das verbleibende Budget diese Reservierung nicht abdecken kann, stoppt er. Fehlgeschlagene oder unterbrochene Calls bleiben im Record; wenn Usage nicht verfügbar ist, wird der reservierte Betrag beibehalten und nicht als null behandelt.

Für die Answer Quality bedeutet 20/20, dass jede Antwort und jeder anwendbare Hard Check auf diesen 20 vorbereiteten Stories bestanden wurde. Das bedeutet nicht, dass die Memory produktionsbereit ist. Alle Stories sind öffentliche Development-Fälle; ausgewählte Traces und Suite-Feedback stehen dem Proposer zur Verfügung. Sie decken Updates, historische Fragen, Unsicherheit, Duplikate, Distractors, Owner Separation, Delete und unzulässige Writes ab. Die Labels search, evaluation und adversarial strukturieren die ursprüngliche Suite; sie machen keinen dieser Fälle zu einem Hidden-Testset.

Diese kleine Suite greift Ideen aus LongMemEval, MemoryAgentBench, VehicleMemBench und GateMem auf. Inputs und Scoring stammen von uns; die Ergebnisse reproduzieren diese Benchmarks nicht.

Sie können außerdem vier vorbereitete Konfigurationen im Repository vergleichen. Sie zeigen, warum das Akzeptieren weiterer Fakten Antworten verschlechtern kann und wie Storage ohne höhere Answer Quality verbessert werden kann. Außerdem zeigen sie die menschlich spezifizierte Seite derselben Experiment-Machinery: Der Autor liefert die Candidates, und Python evaluiert sie. Sie sind nützliche Lehrvergleiche, aber keine Evidenz dafür, dass agentic Search einen kompetenten Menschen oder eine andere Search-Methode übertrifft.

Öffnen Sie artifacts/my-agent-study/report.md für die Campaign-Ergebnisse und Links zu jedem Request, jeder Response und jeder Python-Evaluierung. Experimenthistorie von User Memory getrennt halten

Das Memory-Tool speichert Adas Stadt und Sprache. Die Experimenthistorie speichert, was der Agent gesehen hat, den vorgeschlagenen Patch, jede Rejection, die resultierenden Messwerte und welche Konfiguration zum nächsten Parent wurde. Diese Stores erfüllen unterschiedliche Zwecke.

Jede Iteration bewahrt den exakten Request mit Instruktionen und Schema, die Provider Response, Usage und Timing, das Validation-Ergebnis sowie jede abgeschlossene Evaluierung auf. Fehlgeschlagene Proposals bleiben sichtbar. File-Hashes binden die gespeicherte Evidenz an die für das Experiment verwendete Implementierung und die verwendeten Inputs.

Da es sich um synthetische Fakten handelt, kann der öffentliche Record vollständige Zustände enthalten. Reale Traces benötigen eine separate Retention Policy: Das Löschen eines Fakts aus dem Memory-Tool entfernt frühere Kopien aus Experimentlogs oder Backups nicht. Der Delete-Test der Demo prüft die Records des Tools und spätere Reads, nicht die Löschung aus jedem möglichen Store.

Was der nächste Artikel infrage stellen muss

Wir haben nun einen Agent im Improvement Loop. Er schlägt einen Change vor, erhält ein gemessenes Ergebnis, wählt den nächsten Change und kann entscheiden zu stoppen. Ungültige Proposals folgen einem separaten Rejection Path und bleiben im Record. Memory lieferte uns ein kleines Target für dieses erste Experiment. Die Trennung von Proposal, Evaluierung und Übernahme gilt auch, wenn wir andere Teile eines Agent-Systems ändern.

Das nächste Risiko ist der Evaluator selbst. Wenn Erfolg das Beibehalten jedes Fakts belohnt, kann der Agent lernen, Vermutungen zu behalten. Wenn eine Suite nur nach der aktuellen Stadt fragt, kann sie einen Change übersehen, der nützliche Historie zerstört. Ein leistungsfähigerer Proposer kann schwache Messungen effizienter ausnutzen.

Teil 2, Make It Scorable Before You Make It Autonomous, fragt, wie wir diese Messungen testen, bevor wir dem Proposer mehr Freiheit geben. Die 20/20 der ersten Campaign bilden den Ausgangspunkt für diese Untersuchung.
