Harness Engineering für AI Agents: den Loop um das Model entwerfen

Teil 6 der Serie Engineering the Agentic Stack

Der Reasoning Loop eines Agents wählt die nächste Aktion. Sein Harness liefert Kontext, validiert und autorisiert vorgeschlagene Tool Calls, dispatcht akzeptierte Calls an das Runtime, zeichnet die Ergebnisse auf und entscheidet, ob die Aufgabe abgeschlossen ist.

Models schlagen Edits vor und können Aufgaben als abgeschlossen deklarieren, während das Harness Berechtigungen durchsetzt und die Acceptance Checks interpretiert, die entscheiden, ob der Loop stoppen kann. Teil 5 behandelte das Runtime, das den Prozess am Leben hält. Dieser Artikel fokussiert sich auf den Control-Code innerhalb dieses Runtime: wie man misst, ob jede Ergänzung hilft, und wie man die daraus entstehenden Kontrollen auffindbar hält, wenn sich das Harness verändert.

Jeder zusätzliche Retry, Handoff oder Evaluator über den ersten expliziten Acceptance Check hinaus ist eine Hypothese über ein beobachtetes Versagen. Er verdient seinen Platz nur dann, wenn ein kontrollierter Vergleich zeigt, dass er hilft.

Um diesen Control-Pfad greifbar zu machen, verwende ich ein kleines fiktives Store-Repository. Die Coding-Aufgabe besteht darin, den Schwellenwert für einen automatischen Rabatt von 10 % von $100 auf $75 in src/checkout.py zu senken. Das Repository hat zwei erforderliche Checks:

  • pytest tests/test_checkout.py verifiziert die Rabattberechnung.
  • pnpm playwright test tests/checkout_discount.spec.ts fügt in einem lokalen Test-Store ein $80-Item hinzu und prüft, dass die Checkout-Seite einen Rabatt von $8 anzeigt.

Das Beispiel ist ein Lehr-Setup, keine reale Anwendung und kein Benchmark. Jeder Versuch startet vom selben Commit und mit denselben per Seed festgelegten Testdaten. Das Harness darf die Änderung nur akzeptieren, wenn beide Kommandos erfolgreich durchlaufen und der Trace diese Ergebnisse mit dem getesteten Commit verknüpft.

Spätere Abschnitte wechseln absichtlich zu zwei anderen Beispielen. Eine Staging-Order-API zeigt, warum zustandsverändernde Calls Replay-Schutz brauchen, während eine Migration eines Payment-Adapters zeigt, was eine neue Model-Session benötigt, um unvollendete Arbeit wiederaufzunehmen. Das begleitende Lab gegen Ende ist wieder separat: Es ist ausführbar, enthält aber generische simulierte Aufgaben statt dieses Store-Repositorys.

Kurzfassung: Starte mit einem Model, einigen wenigen schmalen Tools und einem expliziten Acceptance Check. Füge Retries hinzu, nachdem Traces transiente Call-Fehler gezeigt haben. Füge einen Progress Handoff hinzu, wenn wiederaufgenommene Sessions Arbeit wiederholen. Wenn du eine der beiden Änderungen testest, halte Model-Version, Aufgaben, Grader und Gesamtbudget konstant. Entferne die Komponente, wenn sie das gemessene Ergebnis nicht verbessert.

Was dem Harness gehört

OpenAIs Codex-Loop-Walkthrough beschreibt den grundlegenden Zyklus. Das Harness baut einen Prompt zusammen, fragt das Model nach der nächsten Aktion, sendet einen akzeptierten Tool Call an das Runtime, hängt das Ergebnis an und fragt erneut, bis das Harness das Ergebnis akzeptiert oder die Kontrolle an den User zurückgibt.

Implementierungen können mehrere Verantwortlichkeiten in einem Prozess zusammenfassen. Die Fehlergrenzen unterscheiden sich trotzdem:

Wenn ein Fehler auftritt, diagnostiziere die Grenze, die darauf reagieren sollte. Ein schlechter Plan braucht möglicherweise bessere Instruktionen oder besseres Model-Reasoning. Wenn edit_file auf einen Pfad außerhalb von src/ zielt, sollte das Harness ihn ablehnen, während ein Sandbox-Prozess, der stirbt, bevor der Edit ausgeführt wird, zum Runtime gehört, das den Worker neu starten oder den Crash melden muss.

OpenAIs eigene Harness-Engineering-Case-Study beschreibt eine bootbare Anwendungsinstanz für jedes Worktree. Das Team hat außerdem Browser-Automation in die Agent-Umgebung verdrahtet und Logs, Metrics und Traces verfügbar gemacht.

Eine Aufgabe wie „Kein Span in diesen vier kritischen User Journeys überschreitet zwei Sekunden“ wurde testbar, weil der Agent die Anwendung ausführen und dieselben Signale abfragen konnte, die auch ein Engineer inspizieren würde. Die Case Study ist produktspezifisch. Übertragbar ist die Bedingung hinter dem Ergebnis: Die Anwendung und ihre Performance-Signale mussten innerhalb der Agent-Umgebung verfügbar sein.

Lopopolo, der Autor dieser Case Study, pflegt einen Field Guide für Harness Engineering, der die zwei Hebel benennt, an denen dieser Artikel zieht: Model und Coding-Agent als Black Box fix halten und den Kontext sowie die Tools darum herum engineeren. Sein Framing erklärt auch, warum so viel vom Harness am Ende gewöhnlicher Code ist.

Die Qualitätslatte, Verfahren, Ausnahmengeschichte und Autoritätsbeziehungen einer Organisation liegen unterhalb der Wasserlinie dessen, was ein allgemeines Model wissen kann. Das Harness macht sie als Repository-Instruktionen, Berechtigungsregeln und Acceptance Checks sichtbar. Jeder akzeptierte Run kann seine Erkenntnisse in diese Artefakte zurückspeisen, statt sich darauf zu verlassen, dass die nächste Session sie erneut entdeckt.

Verfolge die Rabattänderung von der Proposal bis zur Acceptance

Für die oben definierte Rabattaufgabe schlägt das Model vor, calculate_discount in src/checkout.py zu ändern. Mehrere Dinge passieren, bevor dieser Edit als Fortschritt zählt:

  1. Der Context Builder liefert die Aufgabe, Repository-Instruktionen, relevante Dateien, frühere Tool Results und den aktuellen Plan.
  2. Das Model schlägt einen edit_file-Call mit Pfad und Ersetzungstext vor.
  3. Die Tool-Grenze (der Harness-Code zwischen Proposal und Ausführung) validiert die Argumente, prüft den Pfad gegen den erlaubten Scope und fragt nach Freigabe, falls die Operation sie benötigt.
  4. Das Runtime wendet den Edit in der Sandbox an und gibt ein Structured Output zurück.
  5. Das Harness führt pytest tests/test_checkout.py aus, gefolgt von pnpm playwright test tests/checkout_discount.spec.ts, und liest beide Exit Codes. Der Browser-Test prüft den sichtbaren Rabatt von $8 auf dem per Seed angelegten $80-Warenkorb.
  6. Das Harness entscheidet, was die Ergebnisse bedeuten. Ein fehlgeschlagener Check wird neuer Kontext für den nächsten Model-Turn, und ein erfolgreicher Run macht die Aufgabe zu einem Kandidaten für den Abschluss.
  7. Ein erfolgreiches Ergebnis wird erst dann zur Abschluss-Evidenz, wenn das Harness Kommando, Exit Code und getestete Artifact-Version im Trace aufzeichnet.

In Schritt 2 hat sich noch keine Datei geändert. Das Harness kann ../../secrets.env ablehnen, für ein destruktives Kommando Freigabe verlangen oder einen Run stoppen, dessen Budget erschöpft ist. Nachdem die Tests gelaufen sind, liest das Harness ihre Exit Codes selbst. Das Model kann seinen eigenen Edit nicht als erfolgreich markieren.

Der Trace sollte den vorgeschlagenen Pfad und Ersetzungstext, die Berechtigungsentscheidung, die geänderten Dateien, den getesteten Commit und beide Kommandoergebnisse zeigen. Eine abschließende done-Nachricht ohne diese Aufzeichnungen beweist nicht, dass diese Änderung ihre erforderlichen Checks bestanden hat.

Entscheide, wo jede Regel durchgesetzt wird

Lege tests/checkout_discount.spec.ts in normale Programmlogik. Das Harness dispatcht das Playwright-Kommando an das Runtime, liest seinen Exit Code und verweigert das Beenden des Runs, solange es fehlschlägt. Ein Prompt kann das Model daran erinnern, den Test auszuführen. Er kann das Model nicht daran hindern, ohne Evidenz Erfolg zu deklarieren.

Tool-Verträge trennen Proposal von Berechtigung

Die Rabattaufgabe braucht nur Dateiedits und Testkommandos. Eine zustandsverändernde API hat einen anderen Failure Mode, daher wechseln wir für diesen Abschnitt das Beispiel. Angenommen, der Agent kann create_test_order gegen einen Staging-Order-Service aufrufen, während er Testdaten vorbereitet. Dieses Tool gehört nicht zu den Acceptance Checks der Rabattaufgabe. Es ist hier nützlich, weil ein Timeout verbergen kann, ob der Service eine Order erstellt hat.

Die Tool-Grenze braucht mehr als eine natürlichsprachliche Beschreibung. Für create_test_order benötigt das Harness einen Vertrag mit:

  • validierten Argumenten, sodass fehlerhafte Eingaben vor der Ausführung abgelehnt werden
  • einem Structured Output wie { "order_id": "123", "created": true }, sodass spätere Checks keinen Freitext parsen müssen
  • einer Effect-Kategorie, die festhält, ob der Call nur Informationen abruft oder eine Datei, einen Datenbankeintrag oder einen externen Service verändert. Sie hält auch fest, ob das Wiederholen des Calls sicher ist. Dieses Label sagt dem Harness, ob ein automatischer Retry Arbeit duplizieren könnte: Es kann get_order_status erneut versuchen, wenn der Service diese Abfrage als read-only definiert, aber es darf create_test_order nicht blind erneut versuchen, weil der erste Call die Order möglicherweise bereits erstellt hat
  • einer Timeout- und Retry-Policy, damit eine verlorene Antwort keine unbegrenzte Folge von Calls auslöst
  • einer Berechtigungsregel, die festlegt, welche Freigabe erforderlich ist. Das Lesen des Order-Status kann automatisch laufen, während das Erstellen einer Order eine Bestätigung verlangen kann

Die natürlichsprachliche Beschreibung ist Text, der dem Model gezeigt wird. Sie könnte lauten: „Erstelle eine Test-Order zur Verifikation des Checkouts.“ Dieser Satz hilft dem Model zu entscheiden, wann es create_test_order vorschlagen soll. Er autorisiert den Call nicht. In diesem Beispiel validiert der MCP-Client des Harness die Argumente, wendet eigene Regeln an und prüft Server-Vertrauen, Freigabeanforderungen und Retry-Sicherheit, bevor irgendetwas dispatcht wird.

Ein MCP-Server veröffentlicht Tool-Beschreibungen und optionale Behavior-Anmerkungen an den Client. Ein fehlerhafter oder bösartiger Server könnte ein zustandsveränderndes Tool als harmlos beschreiben. Wenn der Client diese Behauptung automatisch akzeptierte, könnte er create_test_order ohne Freigabe ausführen oder erneut versuchen und ein Duplikat erzeugen, daher verlangt die MCP- Spezifikation, dass Clients Tool-Anmerkungen als nicht vertrauenswürdig behandeln, sofern der Server selbst nicht vertrauenswürdig ist.

Die Spezifikation schreibt keine universelle Trust-Einstellung vor. Der Client benötigt daher eine explizite Trust-Policy für sein Deployment; ein Server kann seine eigenen Anmerkungen nicht selbst vertrauenswürdig machen. Diese Policy entscheidet, welche Metadaten Berechtigungs- oder Retry-Entscheidungen beeinflussen dürfen und welche Annotations nur hinweisenden Charakter haben.

Ein Retry für einen zustandsverändernden Call braucht Replay-Schutz

Ein schwierigeres Retry-Problem tritt auf, wenn create_test_order die Order erstellt, seine HTTP-Antwort aber verloren geht. Das Harness sieht ein Timeout und kann nicht erkennen, ob der Server die Anfrage abgeschlossen hat. Das Wiederholen des Calls kann eine zweite Order erzeugen.

Eine Statusabfrage kann erneut versucht werden, wenn der Service sie als read-only definiert. Ein Creation-Call braucht Schutz, etwa einen Idempotency Key: Der Client hängt einen eindeutigen Request-Identifier an, und der Service gibt das erste Ergebnis zurück, statt eine weitere Order zu erstellen, wenn er denselben Identifier erneut sieht. Ohne diesen Schutz sollte das Harness prüfen, ob die Order existiert, oder vor einem weiteren Versuch eine menschliche Entscheidung einholen. AWS dokumentiert dieses Muster in seiner Guidance zu idempotent APIs.

Acceptance braucht unabhängige Evidenz

Eine erfolgreiche create_test_order-Antwort belegt nur, dass das Tool Daten zurückgegeben hat. Sie beweist nicht, dass eine Coding-Aufgabe ihre Tests bestanden hat. Wenn ein späterer Browser-Test von der vorbereiteten Order abhängt, muss das Harness das Response-Schema validieren und diesen Test trotzdem ausführen, bevor es die Codeänderung akzeptiert.

Einige Kriterien lassen sich nicht auf einen Exit Code reduzieren. Für eine separate Visual-Design- Aufgabe kann ein frischer Evaluator eine gerenderte Seite oder ein Diagramm mit einer schriftlichen Rubrik vergleichen. Teams sollten diesen Evaluator gegen Human Reviews prüfen, bevor sie ihn als Completion Gate verwenden.

Eine Payment-Adapter-Migration braucht einen Handoff

Wechseln wir die Aufgabe erneut, bleiben aber im fiktiven Store-Repository. Der Agent muss Checkout nun von Payment Adapter v1 auf v2 migrieren. Die Arbeit umfasst den Checkout-Handler, Payment-Client, Konfiguration und Tests und kann daher länger dauern als eine einzelne Model-Session.

Bevor die erste Session ihr Context Window erreicht, hat sie mehrere Dateien modifiziert, eine lokale Payment-Sandbox gestartet und tests/payment_migration.spec.ts in einem fehlgeschlagenen Zustand hinterlassen. Dieser Browser-Acceptance-Test schließt eine Payment über Adapter v2 ab und prüft die aufgezeichnete Provider-ID. Eine Conversation Summary kann die nächste Model-Session orientieren, aber sie kann die Sandbox weder neu starten noch beweisen, welche Dateien aktuell verändert sind.

Die nächste Session muss drei Dinge wiederherstellen:

Was wiederhergestellt werden mussWas es umfasstWie es fehlschlagen kann

Working EnvironmentDateien, Payment-Sandbox und Browser-Test-StatusDas Transkript sagt, ein Service laufe, obwohl er starb
Task ProgressPlan, abgeschlossene Checks, ausstehende Freigabe, nächste AktionDie nächste Session wiederholt bereits erledigte Arbeit

Compaction ersetzt ältere Nachrichten durch eine kürzere Zusammenfassung, damit die aktuelle Session fortfahren kann. Ein Progress Handoff zeichnet auf, was die nächste Session braucht: den aktuellen Branch, geänderte Dateien, das letzte Testkommando samt Output und den nächsten ungelösten Schritt. Wenn die alte Konversation veraltete Annahmen enthält, kann das Harness mit diesem Handoff und dem aktuellen Workspace eine frische Model-Session starten. Das Ersetzen eines abgestürzten Workers und das Wiederherstellen seiner Prozesse ist eine separate Runtime-Recovery-Aufgabe.

Ein kleiner Dokumentationsedit braucht möglicherweise keinen dieser Mechanismen. Die Payment- Migration braucht einen Handoff, sobald sich die Arbeit über mehrere Sessions erstreckt, weil die nächste Model- Session sowohl den Workspace als auch den Aufgabenstatus rekonstruieren muss.

Anthropics Experimente mit lang laufenden Coding-Agents nutzten Git-History und eine Progress-Datei zwischen Sessions, während der spätere Report zum Harness-Design Compaction von einem Fresh-Context-Handoff trennt und über die zusätzliche Orchestration, den Token-Verbrauch und die Wall Time berichtet, die Handoffs erfordern.

Ein Chat-Transkript zeichnet auf, was das Model gesehen hat. Es kann nicht beweisen, ob der Order- Service eine Anfrage committed hat, bevor die Antwort verschwand. Bevor du eine Komponente hinzufügst, benenne den wiederkehrenden Fehler, den sie reduzieren soll, und die Zahl, die du verfolgen wirst. Entferne die Komponente, wenn ein kontrollierter Vergleich diese Zahl nicht stark genug bewegt, um ihre Kosten zu rechtfertigen.

Miss immer nur eine Änderung auf einmal

Eine Ablation misst, ob eine Harness-Komponente den erwarteten Effekt verursacht, indem diese Komponente verändert oder entfernt wird, während der Rest des Experiments konstant bleibt. Zum Beispiel: Hilft Editor-Linting diesem Model auf dieser Task-Suite?

Nutze das folgende Protokoll:

  1. Friere Model-Version, Task-Instanzen, Umgebung, Grader und Prompts außerhalb der getesteten Komponente ein.
  2. Gib beiden Varianten dasselbe Gesamtbudget für Tokens, Zeit und Dollar.
  3. Lege die Zahl der Trials oder die Stop-Regel vor dem Vergleich fest.
  4. Führe dieselben Task-Instanzen in beiden Varianten aus. Weil die Model-Outputs variieren, wiederhole jede Task mehrere Male.
  5. Berichte den Mittelwert zusammen mit der Streuung oder dem Konfidenzintervall.
  6. Zähle jeden gestarteten Trial, einschließlich Timeouts, Policy-Stopps, Harness-Crashes und Evaluator-Fehlern.

Die Erfolgsrate allein kann eine teure Komponente verbergen. Miss mindestens fehlgeschlagene Tasks, die dennoch als abgeschlossen akzeptiert wurden, Kosten und Wall Time pro abgeschlossener Task, Tool-Fehler, duplizierte Orders, Review-Minuten und manuelle Permission Overrides. Wähle die Metrik, die die realen Kosten für das Produkt trägt. Ein Anstieg abgeschlossener Tasks um zwei Punkte ist ein schlechter Tausch, wenn er die Review-Queue verdoppelt.

Ein gepaartes Payment-Migrationsexperiment macht den Progress Handoff messbar. Jedes Control-/Treatment-Paar startet vom selben Repository-Commit und demselben per Seed gesetzten Checkpoint, mit demselben Model, derselben Task, demselben Grader und demselben Gesamtbudget. Der Handoff ist der einzige Schalter. Die primäre Metrik zählt doppelte Tool-Aktionen nach dem Resume: Eine Aktion ist doppelt, wenn ihre Operation und ihr Artefakt mit einem Schritt übereinstimmen, den die vorherige Session bereits abgeschlossen hatte.

Halte das Harness editierbar, nachdem es seinen Platz verdient hat

Ablation hält ein Harness klein, aber sein Code kann das Model, auf das er abgestimmt wurde, trotzdem überleben. Eine Anfrage wie „maskiere Secrets in jedem Capture-Pfad“ benennt ein Verhalten, keine Datei. In einem produktiven Harness kann sich dieses Verhalten über Ausführungsstufen und Shared State erstrecken. Ein Mensch oder Coding-Agent muss jede Implementierungsstelle finden, bevor er sie sicher ändern kann.

Ein Preprint von Wang et al. aus dem Jahr 2026, das Harness Handbook, nennt diesen Schritt Behavior Localization. Das Handbook baut aus der Harness- Codebasis eine verhaltensorientierte Karte. Statische Analyse extrahiert einen Programmgraphen ohne Model-Calls, dann organisiert ein LLM dessen Einheiten in Ausführungsstufen.

Der Maintainer oder Coding-Agent beginnt mit einem Systemüberblick, öffnet die relevante Ausführungsstufe und steigt zu source-grounded Einträgen für eine Funktion oder Datei hinab. Eine Register-Ansicht zeichnet auf, wo Shared State zwischen Stufen geschrieben und gelesen wird. Diese Hierarchie hält den Überblick klein und bewahrt zugleich einen Pfad bis zum Source Code.

Aktualität ist eine separate Regel. Jeder Locator muss gegen das Live- Repository auflösbar sein. Das Handbook schließt veraltete Einträge aus, statt zu raten, und jeder nicht leere Diff resynchronisiert die Einträge, die er betrifft.

Das Diagramm komprimiert den Modifikations-Loop: Eine rein verhaltensbezogene Anfrage steigt durch die Ebenen des Handbook hinab, jeder Kandidaten-Locator wird gegen das Live-Repository verifiziert, bevor der Plan geschrieben wird, und jeder angewendete Diff resynchronisiert die Karte.

Die Handbook-Evaluation folgt dem Protokoll, für das dieser Artikel argumentiert. Auf zwei Open-Source-Harnesses (Terminus-2, sechs Python- Dateien, und dem Codex-Monorepo, 2.267 Rust-Dateien) hat ein read-only-Planner auf Basis von DeepSeek-V4-Pro entweder das Repository direkt erkundet oder über das Handbook geroutet. Requests, Repository, Tool-Berechtigungen und Decoding waren in beiden Armen identisch. Drei Judges (GPT-5.5, Opus 4.8, DeepSeek-V4-Pro) bewerteten jeden Edit-Plan hinsichtlich Localization, Scope Control und Reasoning:

Der durch das Handbook unterstützte Planner gewann in beiden Repositories häufiger und nutzte weniger Planner-Tokens. Die Bedingungen bleiben an dieses Ergebnis gebunden: Drei LLM- Judges bewerteten Edit-Pläne, die von einem Planner-Model auf zwei Harnesses erzeugt wurden. Die Studie evaluierte Pläne, nicht ausgeführte Diffs oder Defektraten in Produktion.

Die vorherigen Abschnitte nutzen Traces, um zu beantworten, warum eine Komponente existiert. Diese Karte beantwortet die nächste Frage: Wo lebt diese Komponente, wenn sie geändert werden muss?

Probiere die Methode im begleitenden Lab aus

Das Projekt harness-demo auf Commit 517353f3 ist eine kleine, deterministische Übung mit 12 generischen synthetischen Tasks, die Codeänderungen wie fix-parser-edge-case, split-large-module und wire-browser-test abdecken. Es implementiert nicht das fiktive Store-Repository.

Jede Task-Fixture deklariert einen Schwierigkeitsgrad sowie vier boolesche Bedingungen: ein flaky Tool, verlorenen Fortschritt, eine übersehene Implementierungslücke und mehrdeutigen Abschluss. Der Simulator leitet für schwierige Tasks, die auch eine Progress-Datei brauchen, eine fünfte Bedingung ab: Ohne context_reset bewahrt Compaction veraltete Annahmen. Ein deterministischer Grader markiert eine Task nur dann als bestanden, wenn die gewählte Konfiguration jede anwendbare Bedingung verarbeitet. Es laufen weder Model noch externer Service.

Die Kommandos beantworten unterschiedliche Fragen:

  • make check führt Ruff und sieben Unit-Tests aus, darunter den Validator, der jedes Ablation-Paar zurückweist, das mehr als eine Komponente ändert.
  • make run gibt eine kumulative Lehrmatrix und danach fünf gültige Leave-one-component-out-Vergleiche aus.
  • make failures benennt für jede fehlgeschlagene Task die nicht behandelte Bedingung. Das vollständige Harness sollte mit all synthetic tasks pass enden.
make check
make run
make failures

Der kausale Abschnitt von make run sieht so aus:

component                 control  treatment  delta
retry_policy              8/12     12/12       +4
progress_handoff          7/12     12/12       +5
evaluator                 8/12     12/12       +4
fail_closed_acceptance    7/12     12/12       +5
context_reset            10/12     12/12       +2

Für jede Zeile ist die Control-Variante die vollständige Konfiguration mit einer entfernten Komponente; das Treatment stellt nur diese eine Komponente wieder her. Die frühere kumulative Matrix ist nützlich zur Orientierung, aber einige ihrer benachbarten Zeilen fügen mehrere Komponenten auf einmal hinzu und können daher keine Ursache identifizieren.

Das Lab validiert jedes deklarierte Paar, bevor es ausgeführt wird. Seine Regression-Tests enthalten auch ein absichtlich ungültiges Paar, das Retry-Policy und Evaluator gemeinsam ändert; der Validator weist es zurück.

Das Konfigurationsschema des Labs prüft alle fünf Komponentenfelder. Dieser ausführbare Auszug zeigt dieselbe Guard für ein gültiges Progress-Handoff-Paar:

from dataclasses import dataclass, fields


@dataclass(frozen=True)
class Config:
    progress_handoff: bool = False
    evaluator: bool = False
    retry_policy: bool = False
    fail_closed_acceptance: bool = False
    context_reset: bool = False


def changed_components(control: Config, treatment: Config) -> tuple[str, ...]:
    return tuple(
        field.name
        for field in fields(control)
        if getattr(control, field.name) != getattr(treatment, field.name)
    )


control = Config(progress_handoff=False, evaluator=True, retry_policy=True)
treatment = Config(progress_handoff=True, evaluator=True, retry_policy=True)
assert changed_components(control, treatment) == ("progress_handoff",)

Starte mit einem Loop und einem Acceptance Check

Ich würde ein Coding-Agent-Harness mit einem leistungsfähigen Model, Repository- Instruktionen, einigen wenigen schmalen Tools, einer Sandbox und einem expliziten Acceptance-Test starten. Ich würde Tool Calls, Ergebnisse, Kosten und diesen finalen Test in einem einzigen Trace aufzeichnen, damit die ersten nützlichen Fehler sichtbar werden, ohne sie aus Terminal-Logs und Chat-Transkripten rekonstruieren zu müssen. Das ist eine vorgeschlagene Baseline, keine Evidenz aus einem deployed System.

Von dort aus füge nur hinzu, was ein Trace rechtfertigt. Zeichne auf, wer jede Komponente pflegt, wie viele Tokens oder Sekunden sie hinzufügt und welcher Regression-Test ihre Entfernung nach einem Model-Upgrade rechtfertigen würde.

Sechs Monate später sollte jemand, der progress_handoff=True sieht, die fehlgeschlagenen Traces finden können, die es gerechtfertigt haben, und die Regression-Cases, die es noch immer dort halten. Die Traces erklären, warum die Komponente existiert; eine aktuelle Behavior-Map erklärt, wo man sie anfassen muss.
