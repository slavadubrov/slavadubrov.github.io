Harness Engineering für AI Agents: Control Loops entwerfen

Viacheslav Dubrov

2026-07-22 · Aktualisiert 2026-08-01 · 24 Min. · KI-Agenten

Automatische Übersetzung Dieser Artikel wurde automatisch aus der englischen Originalversion übersetzt.

Der Reasoning Loop eines Agents wählt die nächste Aktion. Sein Harness liefert Kontext, validiert vorgeschlagene Tool Calls, autorisiert sie, dispatcht die akzeptierten Calls, protokolliert die Ergebnisse und entscheidet, ob die Aufgabe abgeschlossen ist.

Für die ersten drei dieser Aufgaben gibt es bereits einen Artikel. Memory liefert den Kontext, Tool Use definiert, was vorgeschlagen werden kann, und Security entscheidet, was ausgeführt wird. Diese Themen erschienen als separate Beiträge, weil es sich um separate Engineering-Probleme handelt. Die Entscheidung zwischen Qdrant und pgvector hat nichts mit dem Schreiben einer PreToolUse-Deny-Regel zu tun.

Sie haben jedoch einen gemeinsamen Moment: die Lücke zwischen dem Benennen einer Aktion durch das Model und ihrer Ausführung durch die Maschine. Jede dieser Disziplinen beantwortet eine Frage zu dieser Lücke, und der Harness ist der Code, der sie lange genug offenhält, um alle drei Fragen zu stellen.

Dieser Artikel behandelt, was nach diesen drei Themen noch übrig bleibt: zu entscheiden, ob die fertige Arbeit tatsächlich fertig ist, und nachzuweisen, dass jeder Control in der Loop die Kosten rechtfertigt. Teil 5 behandelte den Runtime, der den Prozess im Hintergrund am Leben hält.

Dieser Artikel richtet sich an Engineers, die Coding-Agent-Harnesses entwickeln oder überprüfen müssen, die Tool Calls autorisieren, Fortschritt bewahren und den Abschluss nachweisen.

Am Ende solltest du jeden Control richtig einordnen können, Acceptance Evidence unabhängig vom vorschlagenden Model halten, Retries für Side Effects absichern und jeweils nur eine Komponente messen.

TL;DR

Beginne mit einem Model, einigen eng gefassten Tools und einem expliziten Acceptance Check. Füge Retries hinzu, nachdem Traces transiente Call-Fehler zeigen. Ergänze einen Progress Handoff, wenn resumte Sessions Arbeit wiederholen. Wenn du eines von beiden testest, halte Model-Version, Tasks, Grader und Gesamtbudget konstant. Entferne die Komponente, wenn sie das gemessene Ergebnis nicht verbessert.

Über den ersten expliziten Acceptance Check hinaus ist jeder zusätzliche Retry, Handoff oder Evaluator eine Hypothese über einen beobachteten Fehler. Er verdient seinen Platz nur dann, wenn ein kontrollierter Vergleich zeigt, dass er hilft.

Der einfachste Acceptance Check lässt sich für einen kleinen Research Agent leicht schreiben, wie ihn diese Serie entwickelt hat — einen LangGraph Agent, der Marktdaten abruft und einen Analystenbericht schreibt. Ein Hook außerhalb des Models validiert den Bericht gegen ein Schema und prüft, ob er tatsächlich Stock Tickers enthält; ein fehlerhafter Bericht hält den Run offen. Zwölf Zeilen gewöhnlicher Code genügen, und das Model darf seinen eigenen Output nicht als wohlgeformt deklarieren. Das eigene Gate des Repositories ist weicher: ein Evaluator in einem frischen Kontext gibt eine Bewertung ab, danach folgt ein Mensch. (Teil 4 skizziert die deterministische Variante.)

Was dieses Beispiel nicht zeigen kann, ist der interessante Teil: Was passiert, wenn die Evidence mehrdeutig ist, ein Retry jemanden doppelt belasten könnte oder die Arbeit die Session überdauert, in der sie gestartet wurde? Dafür braucht es eine Aufgabe mit einer schärferen Pass/Fail-Grenze als ein Research Report. Der Research Agent bleibt das Beispiel für den Acceptance Check; für die Fälle mit Retry und Handoff kommt ein kleines fiktives Store-Repository hinzu. Die Coding-Aufgabe besteht darin, den Schwellenwert für einen automatischen Rabatt von 10 % in src/checkout.py von $100 auf $75 zu senken. Das Repository hat zwei erforderliche Checks:

  • pytest tests/test_checkout.py verifiziert die Rabattberechnung.
  • pnpm playwright test tests/checkout_discount.spec.ts fügt einem lokalen Test-Store einen Artikel für $80 hinzu und prüft, ob die Checkout-Seite einen Rabatt von $8 anzeigt.

Das Beispiel ist ein Lehr-Fixture, keine reale Anwendung und kein Benchmark. Jeder Versuch startet beim selben Commit und mit denselben gesäten Testdaten. Der Harness darf die Änderung nur akzeptieren, wenn beide Commands erfolgreich sind und der Trace diese Ergebnisse mit dem getesteten Commit verknüpft.

Das Diagramm verfolgt die Rabattänderung vom Vorschlag bis zur Evidence. Der Harness liefert Task und Dateien, prüft die vorgeschlagenen edit_file-Argumente und Berechtigungen und dispatcht den akzeptierten Call. Nachdem der Runtime den Edit angewendet hat, führt der Harness die genannten Unit- und Browser-Acceptance-Tests aus. Ein fehlgeschlagener Command geht als Evidence für einen weiteren Turn an das Model zurück; zwei erfolgreiche Commands machen die Änderung für die Akzeptanz zugelassen.

Was der Harness besitzt

OpenAIs Codex-Loop-Walkthrough beschreibt den grundlegenden Zyklus. Der Harness stellt einen Prompt zusammen, fragt das Model nach der nächsten Aktion, sendet einen akzeptierten Tool Call an den Runtime und hängt das Ergebnis an. Danach fragt er erneut. Das wiederholt sich, bis der Harness das Ergebnis akzeptiert oder die Kontrolle an den User zurückgibt.

Implementierungen können mehrere Verantwortlichkeiten in einem Prozess zusammenfassen. Die Failure Boundaries bleiben trotzdem unterschiedlich:

BegriffAufgabeBeispiel für einen Coding Agent
ModelSchlägt Text, einen Tool Call oder eine finale Antwort vorSchlägt einen Edit an src/checkout.py vor
Reasoning LoopWählt aus dem verfügbaren Kontext den nächsten SchrittInspizieren, Editieren, Testen, erneut inspizieren
HarnessLiefert Kontext, validiert Vorschläge, autorisiert sie, dispatcht akzeptierte Calls, protokolliert Ergebnisse und prüft den AbschlussErlaubt Edits unter src/ und verlangt beide genannten Tests
RuntimeFührt akzeptierte Calls aus und hält den State außerhalb des Worker-Prozesses am LebenSession-Log, Sandbox, Checkpoint Store, Trace Backend

Die Runtime-Zeile umfasst vier Dinge: Session, Sandbox, Checkpoint und Trace. Alle vier speichern State oder begrenzen die Ausführung. Das Model schlägt die Aktion vor, und der Reasoning Loop wählt den nächsten Schritt. Der Harness entscheidet, ob ein vorgeschlagener Call ausgeführt werden darf und ob die Evidence für den Abschluss ausreicht — deshalb erhält er einen eigenen Artikel. Teil 5 zählt den Harness zusammen mit diesen vier als eines von fünf Primitives, die vor dem Shipping eingeordnet werden müssen; dieser Artikel löst ihn wieder heraus.

Wenn ein Fehler auftritt, diagnostiziere die Boundary, die reagieren sollte. Ein schlechter Plan kann bessere Instructions oder besseres Model Reasoning erfordern. Wenn edit_file auf einen Pfad außerhalb von src/ zielt, sollte der Harness ihn ablehnen. Ein Sandbox-Prozess, der stirbt, bevor der Edit ausgeführt wird, gehört zum Runtime; dieser muss den Worker neu starten oder den Crash melden.

Die Teile 3 und 4 teilen sich Schritt 3. Genau diese Überschneidung ist das zentrale Argument dafür, sie als ein Programm zu behandeln. Dieselbe Schicht des Harness-Codes, die ein fehlerhaftes Argument ablehnt, lehnt auch einen Call ab, der zwar erlaubt, aber noch nicht freigegeben ist. Werden diese beiden Ablehnungen auf zwei Services verteilt, driften sie auseinander, und ein Call, der an einer Stelle die Schema-Validierung passiert, wird an anderer Stelle autorisiert, ohne dass das Schema dort bekannt ist.

Für das Debugging bleibt die Trennung wichtig: Ein Edit an der falschen Datei ist eine Pfadregel aus Teil 4, kein Retrieval-Problem aus Teil 2. Ein Abschnitt gegen Ende dieses Artikels übersetzt das in eine Routing-Tabelle.

OpenAIs eigene Harness-Engineering-Fallstudie beschreibt eine bootfähige Anwendungsinstanz für jeden Worktree. Das Team integrierte außerdem Browser Automation in die Agent-Umgebung und machte Logs, Metrics und Traces verfügbar.

Eine Aufgabe wie „Kein Span in diesen vier kritischen User Journeys überschreitet zwei Sekunden“ wurde testbar, weil der Agent die Anwendung ausführen und dieselben Signals abfragen konnte, die auch ein Engineer untersuchen würde. Die Fallstudie ist produktspezifisch. Übertragbar ist die Bedingung hinter dem Ergebnis: Die Anwendung und ihre Performance-Signals mussten innerhalb der Agent-Umgebung verfügbar sein.

Lopopolo, der Autor dieser Fallstudie, pflegt einen Field Guide zu Harness Engineering. Er benennt die beiden Hebel, an denen dieser Artikel ansetzt: Model und Coding Agent als Black Box konstant halten und den Kontext sowie die Tools darum herum entwickeln. Sein Framing erklärt auch, warum so viel vom Harness aus gewöhnlichem Code besteht.

Der Qualitätsmaßstab einer Organisation, ihre Verfahren, die Historie von Ausnahmen und ihre Autoritätsbeziehungen liegen außerhalb dessen, was ein generalistisches Model wissen kann. Der Harness macht sie als Repository Instructions, Permission Rules und Acceptance Checks sichtbar. Jeder akzeptierte Run kann seine Lessons in diese Artefakte zurückführen, statt darauf zu vertrauen, dass die nächste Session sie erneut entdeckt.

Die Rabattänderung vom Vorschlag bis zur Akzeptanz verfolgen

Für die oben definierte Rabattaufgabe schlägt das Model vor, calculate_discount in src/checkout.py zu ändern. Bevor dieser Edit als Fortschritt zählt, geschehen mehrere Dinge:

  1. Der Context Builder liefert Task, Repository Instructions, relevante Dateien, frühere Tool Results und den aktuellen Plan.
  2. Das Model schlägt einen edit_file-Call mit einem Pfad und Replacement Text vor.
  3. Die Tool Boundary (der Harness-Code zwischen Vorschlag und Ausführung) validiert die Argumente, prüft den Pfad gegen den erlaubten Scope und fordert bei Bedarf eine Approval an.
  4. Der Runtime wendet den Edit in der Sandbox an und gibt ein strukturiertes Result zurück.
  5. Der Harness führt pytest tests/test_checkout.py und anschließend pnpm playwright test tests/checkout_discount.spec.ts aus und liest beide Exit Codes. Der Browser-Test prüft den sichtbaren Rabatt von $8 im gesäten Warenkorb mit einem Wert von $80.
  6. Der Harness entscheidet, was die Ergebnisse bedeuten. Ein fehlgeschlagener Check wird zum neuen Kontext für den nächsten Model-Turn, und ein erfolgreicher Run macht den Task zu einem Kandidaten für den Abschluss.
  7. Ein erfolgreiches Result wird erst dann zu Completion Evidence, wenn der Harness Command, Exit Code und die Version des getesteten Artefakts im Trace protokolliert hat.

Nach Schritt 2 wurde noch keine Datei geändert. Der Harness kann ../../secrets.env ablehnen, für einen destruktiven Command eine Approval verlangen oder einen Run stoppen, der sein Budget ausgeschöpft hat. Das ist der letzte günstige Zeitpunkt, den du bekommst. Nachdem die Tests gelaufen sind, liest der Harness ihre Exit Codes selbst. Das Model kann seinen eigenen Edit nicht als erfolgreich markieren.

Der Trace sollte den vorgeschlagenen Pfad und Replacement Text, die Permission-Entscheidung, die geänderten Dateien, den getesteten Commit und beide Command Results zeigen. Eine finale done-Nachricht ohne diese Records beweist nicht, dass diese Änderung ihre erforderlichen Checks bestanden hat.

Entscheiden, wo jede Regel durchgesetzt wird

Die Anforderung, dass tests/checkout_discount.spec.ts erfolgreich ist, gehört in deterministischen Code, nicht in den Prompt. Der Harness dispatcht den Playwright-Command an den Runtime, liest dessen Exit Code und weigert sich, den Run zu beenden, solange der Test fehlschlägt. Ein Prompt kann das Model daran erinnern, den Test auszuführen. Er kann das Model jedoch nicht daran hindern, ohne Evidence Erfolg zu deklarieren.

Andere Regeln gehören in andere Schichten:

Regel platzieren inGeeignet fürBeispiel
Prompt oder SkillSuchreihenfolge, Coding Conventions und PlanformatVor dem Editieren von Checkout-Code AGENTS.md lesen
Tool BoundaryArgumentvalidierung, erlaubte Pfade, Approvals und Tool AccessWrites nur unter src/ erlauben
Deterministischer CodeBudgets, Timeouts, Retries, Test-Exit-Codes und Release GatesDen Run offen halten, solange der Playwright-Test fehlschlägt
Evaluator in frischem KontextVisual Review oder Kriterien, die menschliches Urteil benötigenEin generiertes Diagramm mit einer schriftlichen Rubrik vergleichen

Tool Contracts trennen Vorschlag und Berechtigung

Die Rabattaufgabe benötigt nur File Edits und Test Commands. Eine State-Changing API hat einen anderen Failure Mode, daher wechseln wir für diesen Abschnitt das Beispiel. Angenommen, der Agent kann create_test_order gegen einen Staging Order Service aufrufen, während er Testdaten anlegt. Dieses Tool ist keiner der Acceptance Checks der Rabattaufgabe. Es ist hier nützlich, weil ein Timeout unklar lassen kann, ob der Service eine Order angelegt hat.

Die Tool Boundary braucht mehr als eine Beschreibung in natürlicher Sprache. Sie braucht einen expliziten Tool Contract. Teil 3 hat einen solchen Contract aus Sicht des Models gefordert: klare Aktionen, kompakte Rückmeldungen und recoverable Errors. Der Harness benötigt denselben Contract aus einem anderen Grund. Er muss ohne Rückfrage an das Model entscheiden, ob ein Call ausgeführt werden darf und ob ein fehlgeschlagener Call wiederholt werden darf. Für create_test_order bedeutet das einen Contract mit:

  • validierten Argumenten, damit fehlerhafte Eingaben vor der Ausführung abgelehnt werden
  • einem strukturierten Result wie { "order_id": "123", "created": true }, damit spätere Checks keinen Freitext parsen müssen
  • einer Effect Category, die festhält, ob der Call nur Informationen abruft oder eine Datei, einen Datenbankeintrag oder einen externen Service verändert. Sie hält außerdem fest, ob eine Wiederholung sicher ist. Dieses Label teilt dem Harness mit, ob ein automatischer Retry Arbeit duplizieren könnte. Der Harness kann get_order_status erneut ausführen, wenn der Service diesen Lookup als Read-only definiert. create_test_order darf er nicht blind wiederholen, weil der erste Call die Order möglicherweise bereits angelegt hat
  • einem Timeout und einer Retry Policy, damit eine verlorene Response keine unbegrenzte Folge von Calls auslöst
  • einer Permission Rule, die festlegt, welche Approval erforderlich ist. Das Lesen des Order-Status kann automatisch laufen, während das Anlegen einer Order eine Bestätigung erfordern kann

Die Beschreibung in natürlicher Sprache ist Text, der dem Model angezeigt wird. Sie könnte lauten: „Create a test order for checkout verification.“ Dieser Satz hilft dem Model zu entscheiden, wann es create_test_order vorschlagen sollte. Er autorisiert den Call nicht. In diesem Beispiel validiert der MCP-Client des Harness die Argumente, wendet eigene Regeln an und prüft Server Trust, Approval Requirements und Retry Safety, bevor er etwas dispatcht. Diese Prüfung entspricht der Ordered Deny/Ask/Hook/Allow Ladder aus Teil 4, ergänzt um eine Frage: Darf ein Call, der bereits fehlgeschlagen ist, erneut gesendet werden?

Ein MCP Server veröffentlicht Tool Descriptions und optionale Behavior Annotations für den Client. Ein fehlerhafter oder bösartiger Server könnte ein State-Changing Tool als harmlos beschreiben. Ein Client, der diese Angabe automatisch akzeptiert, könnte create_test_order ohne Approval ausführen oder wiederholen und eine Duplikat-Order anlegen. Die MCP-Spezifikation verlangt daher, dass Clients Tool Annotations als untrusted behandeln, sofern der Server selbst nicht vertrauenswürdig ist.

Die Spezifikation schreibt keine universelle Trust-Einstellung vor. Du brauchst daher eine explizite Trust Policy für dein Deployment; ein Server kann seine eigenen Annotations nicht vertrauenswürdig machen. Diese Policy entscheidet, welche Metadaten Permission- oder Retry-Entscheidungen beeinflussen dürfen und welche Annotations nur beratenden Charakter haben.

Das Wiederholen eines State-Changing Calls erfordert Replay Protection

Teil 5 versieht jeden Side-Effecting Tool Call mit einem Idempotency Key. Der Harness entscheidet, wann dieser Key seine eigentliche Funktion erfüllen muss. create_test_order legt die Order an, aber die HTTP-Response geht verloren. Der Harness sieht einen Timeout und kann nicht feststellen, ob der Server die Request abgeschlossen hat. Eine Wiederholung kann eine zweite Order anlegen.

Ein Status Lookup kann wiederholt werden, wenn der Service ihn als Read-only definiert. Ein Creation Call benötigt den Key: Der Client hängt eine eindeutige Request-ID an, und der Service gibt beim erneuten Auftreten dieser ID das erste Result zurück, statt eine weitere Order anzulegen. Ohne diesen Schutz sollte der Harness prüfen, ob die Order existiert, oder vor einem weiteren Versuch eine Human Decision einholen. AWS dokumentiert dieses Muster in seinen Guidelines für idempotente APIs.

Acceptance benötigt unabhängige Evidence

Eine erfolgreiche Response von create_test_order belegt nur, dass das Tool Daten zurückgegeben hat. Sie beweist nicht, dass eine Coding-Aufgabe ihre Tests bestanden hat. Wenn ein späterer Browser-Test von der angelegten Order abhängt, muss der Harness das Response Schema validieren und diesen Test trotzdem ausführen, bevor er die Codeänderung akzeptiert.

Einige Kriterien lassen sich nicht auf einen Exit Code reduzieren. Für eine separate Visual-Design-Aufgabe kann ein Evaluator in frischem Kontext eine gerenderte Seite oder ein Diagramm mit einer schriftlichen Rubrik vergleichen — „frischer Kontext“ bedeutet eine zweite Model-Session, die ohne History des Runs startet und die erzeugten Artefakte statt des Transcripts liest. Prüfe diesen Evaluator gegen menschliche Reviews, bevor du ihn als Gate für den Abschluss einsetzt.

Eine Payment-Adapter-Migration benötigt einen Handoff

Wechseln wir erneut die Aufgabe, bleiben aber im fiktiven Store-Repository. Der Agent muss den Checkout von Payment Adapter v1 auf v2 migrieren. Die Arbeit erstreckt sich über Checkout Handler, Payment Client, Configuration und Tests und kann daher eine Model-Session überdauern — einen zusammenhängenden Abschnitt von Model-Kontext, der durch einen Restart oder einen bewusst gestarteten neuen Kontext endet, statt fortgeführt zu werden.

Bevor die erste Session ihr Context Window erreicht, hat sie mehrere Dateien geändert, eine lokale Payment Sandbox gestartet und tests/payment_migration.spec.ts fehlschlagend zurückgelassen. Dieser Browser-Acceptance-Test führt eine Zahlung über Adapter v2 aus und verifiziert die aufgezeichnete Provider-ID. Eine Conversation Summary kann die nächste Model-Session orientieren, aber sie kann die Sandbox nicht neu starten und nicht beweisen, welche Dateien aktuell geändert sind.

Die nächste Session muss drei Dinge wiederherstellen:

Was wiederhergestellt werden mussWas es umfasstWie es fehlschlagen kann
Conversation HistoryMessages, Tool Calls und zurückgegebene ResultsAlte Details verdrängen den aktuellen Task
Working EnvironmentDateien, Payment Sandbox und Browser-Test-StateDas Transcript sagt, ein Service laufe, obwohl er beendet wurde
Task ProgressPlan, abgeschlossene Checks, ausstehende Approval, nächster SchrittDie nächste Session wiederholt abgeschlossene Arbeit

Compaction ersetzt ältere Messages durch eine kürzere Summary, damit die aktuelle Session fortgesetzt werden kann. Ein Progress Handoff hält fest, was die nächste Session benötigt: den aktuellen Branch, geänderte Dateien, den letzten Test-Command samt Output und den nächsten offenen Schritt.

Eine Handoff-Datei ist Document Memory, geschrieben für einen Leser — die nächste Model-Session — und ein anderes Artefakt als der Checkpoint, den der Runtime wiederherstellt. Der Checkpoint beantwortet, wo die Ausführung angehalten wurde. Der Handoff beantwortet, was die Arbeit bedeutet und was noch offen ist. Stellst du einen Checkpoint ohne Handoff wieder her, erhält die nächste Session einen resumable Prozess, aber keine Information darüber, welcher der vier Bereiche — Handler, Client, Configuration, Tests — bereits abgeschlossen ist. Das erzeugt Duplicate Work.

Wenn die alte Conversation veraltete Annahmen enthält, kann der Harness eine frische Model-Session mit diesem Handoff und dem aktuellen Workspace starten. Das Ersetzen eines gecrashten Workers und das Wiederherstellen seiner Prozesse ist eine separate Runtime-Recovery-Aufgabe.

Ein kleiner Documentation Edit benötigt möglicherweise keines dieser Mechanismen. Die Payment-Migration benötigt einen Handoff, sobald die Arbeit Sessions überschreitet, weil die nächste Model-Session sowohl Workspace als auch Task-Status rekonstruieren muss.

Anthropics Experimente mit Long-Running Coding Agents nutzten Git History und eine Progress-Datei zwischen Sessions. Anthropics späterer Bericht zum Harness Design trennt Compaction von einem Handoff in frischem Kontext und berichtet, dass Handoffs zusätzliche Orchestration, Token-Verbrauch und Wall Time verursachen, ohne Zahlen zu veröffentlichen, die einen dieser Overheads dem Handoff selbst zuordnen.

Traces nutzen, um drei Fehler zu unterscheiden

Die nächsten drei Zeilen sind illustrative Trace-Skizzen, keine gemessenen Runs und kein Output aus dem Companion Lab. Jede Zeile zeigt einen anderen Fehler und damit eine andere Harness-Reaktion.

Was der Trace protokolliertWas passiert istRichtige Reaktion
Der Read-only-Call get_order_status liefert 503; kein State-Changing Call ist aktivEin transienter Lookup ist fehlgeschlagenDen Lookup mit Limit und Backoff wiederholen
create_test_order läuft in einen Timeout, danach findet ein Status Lookup Order 123 unter dem Idempotency Key checkout-42Der Service hat die Order angelegt, aber die Response ging verlorenDie bestehende Order zurückgeben, keine weitere anlegen
Der Edit und der Unit-Test bestehen, aber der Trace enthält kein Result für tests/checkout_discount.spec.ts auf dem getesteten CommitErforderliche Acceptance Evidence fehltRun offen halten und den Browser-Acceptance-Test dispatchen

Ein transient wirkender Fehler macht nicht jeden Call sicher wiederholbar. Die erste Zeile betrifft einen Read-only Lookup. Die zweite Zeile betrifft eine State-Changing Request; daher entscheiden Idempotency Key und serverseitiger Status, ob ein weiterer Creation-Versuch zulässig ist. Die dritte Zeile ist überhaupt kein Tool-Fehler; der Harness hat die für die Akzeptanz der Rabattänderung erforderliche Evidence noch nicht gesammelt.

Ein Chat-Transcript protokolliert, was das Model gesehen hat. Es kann nicht beweisen, ob der Order Service eine Request committed hat, bevor die Response verschwunden ist. Das Transcript ist der Bericht des Agents über die Ereignisse; der Trace zeigt, was die Maschine tatsächlich getan hat. Wenn beide voneinander abweichen, vertraue dem Trace. Der Trace muss den Client Call, die Approval-Entscheidung, den Idempotency Key, das Server-Result oder den Status Lookup, den getesteten Commit und das Acceptance-Test-Result verknüpfen. Diese Felder zeigen dem Harness, auf welchem der drei Pfade er sich befindet.

Bevor du eine Komponente hinzufügst, benenne den wiederkehrenden Fehler, den sie reduzieren soll, sowie die Zahl, die du beobachten wirst. Entferne die Komponente, wenn ein kontrollierter Vergleich diese Zahl nicht ausreichend bewegt, um ihre Kosten zu rechtfertigen. Die meisten Harnesses, die ich gesehen habe, wachsen in die andere Richtung: Jemand erlebt einen schlechten Run, fügt einen Guard hinzu, und der Guard bleibt für immer, weil niemand beweisen kann, dass er sicher gelöscht werden kann. So entsteht eine Loop, die niemand anfassen möchte.

Diese wiederkehrenden Fehler in eine versionierte Regression Suite zu überführen, ist eine eigene Aufgabe. Ich habe sie separat in AI Agent Evaluation in Production beschrieben.

Jeweils nur eine Änderung messen

Eine Ablation misst, ob eine Harness-Komponente den erwarteten Effekt verursacht, indem diese Komponente geändert oder entfernt wird, während der Rest des Experiments konstant bleibt. Hilft beispielsweise Editor-Linting diesem Model auf dieser Task Suite?

Verwende das folgende Protokoll:

  1. Fixiere Model-Version, Task-Instanzen, Umgebung, Grader und Prompts außerhalb der getesteten Komponente.
  2. Gib beiden Varianten dasselbe Gesamtbudget für Tokens, Zeit und Geld.
  3. Lege die Anzahl der Trials oder eine Stopping Rule vor dem Vergleich fest.
  4. Führe in beiden Varianten dieselben Task-Instanzen aus. Da Model-Outputs variieren, wiederhole jeden Task mehrmals.
  5. Berichte den Mittelwert zusammen mit Streuung oder Confidence Interval.
  6. Zähle jeden gestarteten Trial, einschließlich Timeouts, Policy Stops, Harness Crashes und Evaluator Failures.

Die Success Rate allein kann eine teure Komponente verbergen. Tracke mindestens als abgeschlossen akzeptierte, aber fehlerhafte Tasks, Kosten und Wall Time pro abgeschlossenem Task, Tool Errors, Duplicate Orders, Review-Minuten und manuelle Permission Overrides. Wähle die Metrik, die die tatsächlichen Kosten für dein Produkt trägt. Ein Anstieg um zwei Prozentpunkte bei den abgeschlossenen Tasks ist ein schlechter Tausch, wenn sich dadurch die Review Queue verdoppelt.

Ein Paired Experiment zur Payment-Migration macht den Progress Handoff messbar. Jedes Control/Treatment-Paar startet beim selben Repository-Commit und mit demselben gesäten Checkpoint sowie demselben Model, Task, Grader und Gesamtbudget. Der Handoff ist der einzige Schalter. Die Primary Metric zählt Duplicate Tool Actions nach dem Resume: Eine Action ist doppelt, wenn ihre Operation und ihr Artefakt einem Schritt entsprechen, den die vorherige Session bereits abgeschlossen hatte.

Das SWE-agent-Paper fixiert GPT-4 Turbo auf dem 300-Task-SWE-bench-Lite-Split und berichtet mit seinem vollständigen Interface 18,0 % gelöste Tasks, verglichen mit 11,0 % für einen Shell-only Agent mit einer ausgearbeiteten Demonstration und 7,3 % für denselben Agent ohne Demonstration. Die im Paper hervorgehobene Differenz von 10,7 Prozentpunkten wird gegenüber der 7,3-%-Baseline gemessen; Teil 3 arbeitet dieselben drei Zahlen aus der Perspektive des Interface Designs auf. Das Paper veränderte außerdem einzelne Interface Features:

Interface-ÄnderungGelöst
Vollständiges SWE-agent-Interface (Referenz, unverändert)18,0 %
Editor ohne Linting15,0 %
Vollständige Datei statt eines Viewers mit 100 Zeilen12,7 %
Vollständige Observation History statt der letzten fünf15,0 %

Diese Zahlen gehören zu diesem Model, diesem Benchmark und dem Cap von $4 pro Task. Die drei Zeilen unterhalb der Referenz sind die nützlichen One-Feature-Tests: In jedem Fall wurde ein Interface Feature geändert, während Model und Evaluations-Setup konstant blieben.

LangChain veröffentlichte einen breiteren Fixed-Model-Vergleich für deepagents-cli. Darin wird ein Anstieg auf Terminal-Bench 2.0 von 52,8 % auf 66,5 % berichtet, wobei gpt-5.2-codex konstant blieb, während das Team System Prompt, Tools und Middleware änderte. Der Beitrag bündelt mehrere Änderungen und enthält weder ein Confidence Interval noch einen Vergleich mit fixiertem Gesamtbudget oder eine Ablation-Tabelle pro Änderung. Das Ergebnis kann daher nicht identifizieren, welche Änderung geholfen hat. Die Model-Namen in diesem Abschnitt sind jene, die die jeweilige Studie zum Zeitpunkt ihrer Durchführung fixiert hat; Übertragbar ist das Protokoll, nicht die Model-Liste.

Anthropics Bericht zu Long-Running Applications ist eine qualitative, produktspezifische Fallstudie und kein kontrollierter Benchmark. Die Anwendung heißt RetroForge, ein 2D-Retro-Game-Maker; in Sprint 3 prüfte der Harness Evaluator 27 Kriterien des Level Editors. Die Arbeit begann mit früheren Opus-Modellen. Als Opus 4.6 erschien, entfernte das Team Harness-Komponenten einzeln, um zu sehen, welche durch das neuere Model redundant geworden waren. Der Bericht zeigt, dass Evaluator Calls bei Aufgaben, die Opus 4.6 allein zuverlässig abschließen konnte, zum Overhead wurden, an der Grenze des Models aber weiterhin halfen. Das Beispiel ist ein Anlass, alte Scaffolding-Komponenten bei einem Model-Wechsel erneut zu validieren; es schätzt keine allgemeine Effect Size.

Den Harness editierbar halten, nachdem er sich bewährt hat

Ablation hält einen Harness klein, aber sein Code kann das Model überdauern, für das er optimiert wurde. Eine Anforderung wie „Secrets in jedem Capture Path maskieren“ benennt ein Verhalten, keine Datei. In einem Production Harness kann sich dieses Verhalten über mehrere Execution Stages und Shared State erstrecken. Bevor du es sicher ändern kannst, musst du jede Implementierungsstelle finden — und das gilt auch für den Coding Agent, den du damit beauftragst.

Ein Preprint von Wang et al. aus dem Jahr 2026, das Harness Handbook, nennt diese Suche Behavior Localization. Das Handbook erstellt eine verhaltensorientierte Map der Harness-Codebase. Statische Analyse, die keine Model Calls benötigt, extrahiert einen Program Graph; anschließend organisiert ein LLM dessen Units in Execution Stages.

Der Maintainer oder Coding Agent startet mit einem System Overview, öffnet die relevante Execution Stage und geht hinunter zu source-grounded Entries für eine Function oder Datei. Ein State Register hält fest, wo Shared State zwischen Stages geschrieben und gelesen wird. Diese Hierarchie hält die Übersicht klein und bewahrt zugleich einen Pfad zum Source Code.

Freshness ist eine separate Regel. Jeder Locator muss sich gegen das Live Repository auflösen lassen. Das Handbook friert veraltete Entries ein, statt zu raten, und jeder nichtleere Diff synchronisiert die betroffenen Entries erneut.

Das Diagramm komprimiert die Modification Loop: Eine verhaltensbezogene Request steigt durch die Ebenen des Handbooks ab, jeder potenzielle Locator wird vor dem Schreiben des Plans gegen das Live Repository verifiziert, und jeder angewendete Diff synchronisiert die Map erneut.

Die Handbook Evaluation folgt dem in diesem Artikel vorgeschlagenen Protokoll. Sie umfasst zwei Open-Source-Harnesses: Terminus-2 (sechs Python-Dateien) und das Codex-Monorepo (2.267 Rust-Dateien). In jedem Harness erkundete ein Read-only Planner, angetrieben von DeepSeek-V4-Pro, das Repository entweder direkt oder über das Handbook. Requests, Repository, Tool Permissions und Decoding waren in beiden Armen identisch. Drei Judges (GPT-5.5, Opus 4.8, DeepSeek-V4-Pro) bewerteten jeden Edit Plan nach Localization, Scope Control und Reasoning — wichtig: Einer der Judges ist dasselbe Model, das die Pläne erzeugt hat:

HarnessBaseline Win RateMit HandbookPlanner Tokens
Terminus-2 (6 Dateien)26,7 %45,6 %−8,6 %
Codex-Monorepo (2.267 Dateien)28,3 %38,3 %−12,7 %

Der Planner mit Handbook gewann in beiden Repositories häufiger und verwendete weniger Planner Tokens. Die Bedingungen gehören zu diesem Ergebnis: Drei LLM Judges bewerteten Edit Plans, die von einem Planner Model auf zwei Harnesses erzeugt wurden. Die Studie evaluierte Pläne, keine ausgeführten Diffs oder Production Defect Rates.

Die Methode im Companion Lab ausprobieren

Das Harness-Demo-Projekt bei Commit 517353f3 ist eine kleine, deterministische Übung mit 12 generischen synthetischen Tasks, die Codeänderungen wie fix-parser-edge-case, split-large-module und wire-browser-test abdecken. Es implementiert nicht das fiktive Store-Repository.

Jedes Task-Fixture definiert eine Schwierigkeit sowie vier boolesche Bedingungen: ein flaky Tool, verlorener Fortschritt, eine übersehene Implementierungslücke und ein mehrdeutiger Abschluss. Der Simulator leitet für schwierige Tasks, die zusätzlich eine Progress-Datei benötigen, eine fünfte Bedingung ab: Ohne context_reset bewahrt Compaction veraltete Annahmen. Ein deterministischer Grader markiert einen Task nur dann als bestanden, wenn die ausgewählte Configuration jede zutreffende Bedingung behandelt. Es läuft kein Model und kein externer Service.

Die Commands beantworten unterschiedliche Fragen:

  • make check führt Ruff und sieben Unit Tests aus, einschließlich des Validators, der jedes Ablation-Paar ablehnt, das mehr als eine Komponente verändert.
  • make run gibt zunächst eine kumulative Teaching Matrix und danach fünf gültige Leave-One-Component-Out-Vergleiche aus.
  • make failures nennt für jeden fehlgeschlagenen Task die nicht behandelte Bedingung. Der vollständige Harness sollte mit all synthetic tasks pass enden.
make check
make run
make failures

Der kausale Abschnitt von make run sieht so aus:

component                 control  treatment  delta
retry_policy              8/12     12/12       +4
progress_handoff          7/12     12/12       +5
evaluator                 8/12     12/12       +4
fail_closed_acceptance    7/12     12/12       +5
context_reset            10/12     12/12       +2

Für jede Zeile ist das Control die vollständige Configuration mit einer entfernten Komponente; das Treatment stellt genau diese Komponente wieder her. Die frühere kumulative Matrix ist für die Orientierung nützlich, aber einige benachbarte Zeilen fügen mehrere Komponenten gleichzeitig hinzu und können daher keine Ursache identifizieren.

Das Lab validiert jedes deklarierte Paar, bevor es ausgeführt wird. Seine Regressionstests enthalten außerdem absichtlich ein ungültiges Paar, das Retry Policy und Evaluator gleichzeitig ändert; der Validator lehnt es ab.

Das Lab vergleicht bei der Validierung eines Paars alle fünf Component Fields. Dieser ausführbare Ausschnitt zeigt denselben Guard an einem gültigen Progress-Handoff-Paar:

from dataclasses import dataclass, fields

@dataclass(frozen=True)
class Config:
    progress_handoff: bool = False
    evaluator: bool = False
    retry_policy: bool = False
    fail_closed_acceptance: bool = False
    context_reset: bool = False

def changed_components(control: Config, treatment: Config) -> tuple[str, ...]:
    return tuple(
        field.name
        for field in fields(control)
        if getattr(control, field.name) != getattr(treatment, field.name)
    )

control = Config(progress_handoff=False, evaluator=True, retry_policy=True)
treatment = Config(progress_handoff=True, evaluator=True, retry_policy=True)
assert changed_components(control, treatment) == ("progress_handoff",)

Welche Schicht du bei einem fehlerhaften Run öffnen solltest

Die Serie verlief von innen nach außen, und hier zahlt sich diese Reihenfolge aus. Ein fehlerhafter Agent Run hat normalerweise einen klaren Owner:

Was der Run getan hatWo der Fix hingehörtTeil
Mit den bereits verfügbaren Informationen einen schlechten nächsten Schritt gewähltReasoning Loop oder Model1
Arbeit wiederholt oder eine vor einer Stunde getroffene Entscheidung verlorenContext Assembly und Handoffs2
Die benötigte Aktion nicht ausdrücken konnte oder ein zurückgegebenes Result falsch interpretierteTool Contract3
Etwas getan hat, das er niemals hätte tun dürfenPermission Rules4
Alles verlor, als ein Worker während eines Calls starbSession, Checkpoint, Sandbox5
Erfolg für Arbeit deklarierte, die nicht erledigt warAcceptance Checks und Traces6

Vier dieser sechs Zeilen betreffen Harness-Code. Zeile 5 ist der darunterliegende Runtime, und Zeile 1 ist die einzige, die ein Prompt noch beeinflussen kann.

Mit einer Loop und einem Acceptance Check beginnen

Ich würde einen Coding-Agent-Harness mit einem leistungsfähigen Model, Repository Instructions, einigen eng gefassten Tools, einer Sandbox und einem expliziten Acceptance Test starten. Ich würde Tool Calls, Results, Kosten und diesen finalen Test in einem Trace protokollieren, damit die ersten nützlichen Fehler sichtbar sind, ohne sie aus Terminal-Logs und Chat-Transcripts rekonstruieren zu müssen. Das ist ein vorgeschlagener Ausgangspunkt, keine Evidence aus einem deployten System.

Füge von dort aus nur hinzu, was ein Trace rechtfertigt. Halte fest, wer jede Komponente wartet, wie viele Tokens oder Sekunden sie kostet und welcher Regressionstest ihre Entfernung nach einem Model-Upgrade rechtfertigen würde.

Sechs Monate später sollte jemand, der progress_handoff=True sieht, die fehlgeschlagenen Traces finden können, die diese Komponente gerechtfertigt haben, sowie die Regression Cases, die sie weiterhin erforderlich machen. Die Traces erklären, warum die Komponente existiert; eine aktuelle Behavior Map erklärt, wo sie geändert werden muss.

Wenn du über eine Suche hierher gelangt bist, haben die fünf vorherigen Artikel ein System rund um einen Reasoning Loop aufgebaut:

  1. Die Loop wählt den nächsten Schritt.
  2. Memory liefert Kontext, und ein echter Postgres Checkpoint Store bewahrt ihn.
  3. Tool Contracts definieren Aktionen und Result Shapes, die spätere Checks lesen können.
  4. Security ergänzt den Deny Hook und den Stop-Hook-Validator. Beide bleiben im Beispiel Skizzen, markieren aber die Control Points.
  5. Der Runtime hält den Prozess über Sessions und Fehler hinweg am Leben.

Die Serie hat außerdem einen MCP Sidecar ergänzt, um zu zeigen, wo Tokens von Data Providern hingehören, sowie einen Evaluator Node, der den Draft Report prüft, bevor ein Mensch ihn sieht. Das sind gewöhnliche Code-Komponenten rund um einen Model Call. Der Router ist aus demselben Grund Harness-Code: Er wählt das Reasoning Pattern, bevor der Reasoning Loop beginnt.

Dein nächster Schritt ist, eine kleine Loop zu instrumentieren. Protokolliere Tool Calls, Results, Kosten und einen expliziten Acceptance Test. Füge jeweils nur einen Control hinzu, nachdem ein Trace den Fehler gezeigt hat, den er adressiert. Vergleiche ihn mit einem fixierten Control und entferne ihn, sobald der gemessene Nutzen verschwindet.
