Dieser Leitfaden richtet sich an Engineers, die Tool-using AI Agents entwickeln oder deployen. Er erklärt, an welchen Stellen Tool-Berechtigungen, Sandbox-Einschränkungen, Credential-Limits und menschliche Freigaben durchgesetzt werden sollten, damit Sie entscheiden können, welcher Check eine unsichere Aktion stoppt, bevor sie Dateien, Netzwerke oder ein externes System erreicht.

Das Harness ist der Code, der jeden Prompt erstellt, entscheidet, welche vorgeschlagenen Tool Calls ausgeführt werden, und die Ergebnisse an das Model zurückgibt. Die meisten Checks gehören dorthin, weil dies die letzte kostengünstige Stelle ist, an der sich ein Command stoppen lässt. Nach der Ausführung eines Commands müssen die Sandbox, die empfangenen Credentials und jeder Recovery-Prozess den Schaden begrenzen. Einige der in diesem Artikel beschriebenen Incidents erreichen ein Model überhaupt nicht.

AI-Agent-Sicherheit geht über LLM-Safety hinaus. Frühe Guardrail-Produkte prüften Input und Output eines einzelnen Model Calls. Sie konnten toxischen Text filtern, personenbezogene Daten redigieren, Jailbreaks blockieren und themenfremde Antworten ablehnen. Diese Grenze war nützlich, solange das Model nur Text zurückgeben konnte.

Tool Loops fügten Filesysteme, Shells, Model Context Protocol (MCP)-Server und Credentials hinzu. Damit erweiterte sich das Threat Model von unsicherem Text auf unsichere Aktionen. Die sieben folgenden Incident-Gruppen umfassen Indirect Prompt Injection sowie Fehler in Konfiguration, Identität und Software Distribution. Text-Screening kann bei einigen bösartigen Inputs helfen; es kann die Controls an diesen Execution Boundaries nicht ersetzen.

Wenn ein Agent ein Repository lesen, ein Tool aufrufen oder Daten an einen Dritten senden kann, ordnen Sie jede vorgeschlagene Aktion dem Check zu, der sie stoppen kann. Die folgenden Abschnitte behandeln Berechtigungen, Hooks, Sandboxes, Credentials und Human Review.

TL;DR

Content Filters prüfen Text rund um einen Model Call. Agent-Sicherheit kontrolliert außerdem vorgeschlagene Tool Calls, Credentials, Dateien, Netzwerkzugriff und irreversible Side Effects. Mehrere Incidents umgingen das Model vollständig; andere nutzten bösartigen Text, um erlaubte Operationen zu steuern. Ein praktikabler Policy-Stack kombiniert Berechtigungen, Pre-Tool Hooks, OS-Sandboxes, menschliche Eskalation, Scoped Credentials und einen Audit Trace.

Content Filters fragen, ob das Model etwas Unsicheres gesagt hat. Agent-Sicherheit fragt zusätzlich, ob das System die nächste Aktion ausführen darf.

Die Harness-Zeilen entscheiden, ob eine Aktion ausgeführt werden darf. Die Runtime-Zeilen erzwingen vorab gesetzte Limits und protokollieren, was passiert ist. Behalten Sie die Sandbox auch dann bei, wenn die Berechtigungsregeln vollständig erscheinen: Sie kann einen Call stoppen, den das Harness nicht vorhergesehen hat. Sie kann jedoch nicht entscheiden, ob eine erlaubte Aktion die richtige Aktion war; das muss das Harness tun.

Die letzte Spalte beschreibt, wo ein Check ausgeführt wird, nicht, wer ihn betreibt. Ein Vendor kann einen Content Filter bereitstellen, aber das Harness ruft ihn auf.

Managed Content Filters decken die Textebene ab. Die übrigen Controls gehören in Application Policy, Identity und Infrastructure.

Warum sich AI-Agent-Sicherheit von LLM-Safety unterscheidet

Bharani Subramaniam und Martin Fowler legten den Rahmen Anfang 2025 in Emerging Patterns in Building GenAI Products fest. Ihre Beobachtung war eng gefasst und direkt:

„Bei traditionellen Systemen konnten wir die Korrektheit hauptsächlich durch Tests bewerten … Bei LLM-basierten Systemen treffen wir auf ein System, das sich nicht mehr deterministisch verhält.“

Output Evaluation fragt, ob eine Model Response ein Rubric erfüllt. Ein Agent Threat Model muss außerdem Tool Calls, Shell Commands, File Writes, Credentials und Network Requests abdecken. Ein Output Grader kann diese Aktionen nicht stoppen. Das Harness kann es: Es ist die Menge der Checks, die aus einem Model-Vorschlag eine erlaubte Aktion macht. Der Rest dieses Artikels behandelt diese Checks.

Simon Willison prägte die Form des agentspezifischen Risikos im Juni 2025 mit dem Begriff lethal trifecta:

„Die lethal trifecta von Fähigkeiten besteht aus: Zugriff auf Ihre privaten Daten; Kontakt mit nicht vertrauenswürdigem Content; und der Fähigkeit, extern zu kommunizieren, sodass diese Fähigkeit zum Diebstahl Ihrer Daten genutzt werden könnte. Wenn Ihr Agent diese drei Eigenschaften kombiniert, kann ein Angreifer ihn leicht dazu bringen, auf Ihre privaten Daten zuzugreifen und sie an den Angreifer zu senden.“

Viele nützliche Agents kombinieren diese Fähigkeiten: Zugriff auf ein Postfach, Web Retrieval und ein Messaging-Tool; oder Zugriff auf ein Repository, Lesen von Issues und Schreiben von Pull Requests. Ein Content Guardrail fragt, ob das Model unsicheren Text generiert hat. Die Trifecta fragt, ob nicht vertrauenswürdiger Input das System dazu steuern kann, Daten über eine erlaubte Aktion offenzulegen.

Die strukturelle Version desselben Arguments findet sich in Joel Fokous Parallax-Preprint (arXiv 2604.12986, eingereicht am 14. April 2026, nicht peer-reviewed). Die zentrale These:

„Das System, das Aktionen analysiert, muss strukturell nicht in der Lage sein, sie auszuführen, und das System, das Aktionen ausführt, muss strukturell nicht in der Lage sein, sie zu analysieren; dazwischen muss ein unabhängiger, unveränderlicher Validator liegen.“

Sie müssen die Evaluationszahlen des Papers nicht akzeptieren, um seine strukturelle Aussage zu prüfen. Mehrere aktuelle Harnesses setzen Teile derselben Trennung um:

  • Claude Codes PreToolUse Hooks
  • Der OS-sandboxed Executor der Codex CLI (unter Linux bubblewrap plus seccomp-System-Call-Filtering)
  • Anthropics Managed Agents, die Credentials in einem Vault aufbewahren, den der Agent nie sieht
  • MCPs RFC-8707-Audience-bound Tokens

Diese Systeme halten das Model von dem Code getrennt, der Commands ausführt. Ihre Controls unterscheiden sich, aber keines davon erlaubt es dem Command Runner, sich auf die Sicherheitsmeinung des Models zu verlassen.

Eine ergänzende Disziplin formulierte Alessandro Pignati im Januar 2026 besonders prägnant: das Principle of Least Agency. Least Privilege fragt: Auf was darf diese Identität zugreifen? Least Agency fragt: Was darf dieser Agent entscheiden? Privilege begrenzt die Credentials; Agency begrenzt die Reichweite eines Plans, selbst wenn die Credentials gültig sind. Excessive Agency ist ein eigener Eintrag in den Top 10 für LLM Applications, die von OWASP, dem Open Worldwide Application Security Project, veröffentlicht wurden. Die separate, später in diesem Artikel behandelte agentic Liste verteilt denselben Fehler auf Tool Misuse und Privilege Abuse. Least Agency ist die Design-Disziplin, die beides verhindert. Ein Agent, der Ihr Postfach zusammenfassen kann, benötigt wahrscheinlich keine Commit-Rechte auf Ihr Monorepo.

Was LLM Guardrails abdecken

Byte sagt

Geben Sie einem Agenten einen Content Filter und ein Write Tool. Der Filter kann seine Worte prüfen; die Tool Policy entscheidet, ob der File Write ausgeführt wird.

LLM Guardrails leisten rund um den Model Call wichtige Arbeit. Sie prüfen Input, Retrieved Text und Output und blockieren, redigieren, reparieren oder markieren Content, der eine konfigurierte Regel verletzt. Die folgenden Produkte unterscheiden sich bei Deployment und Coverage. Ein Content Check ist von einem Authorization Check an der Tool- oder MCP-Server-Grenze getrennt; manche Produkte bieten außerdem Runtime-Policy-Features, die separat konfiguriert und evaluiert werden müssen.

NVIDIA NeMo Guardrails

Das am stärksten opinionated Produkt: ein Orchestration Framework rund um fünf Rail-Typen (Input, Dialog, Retrieval, Execution, Output) mit eigener DSL — Colang, einer Python-ähnlichen Sprache für Dialog-Flows, User Intents und Bot Messages. Die Grundlagen können Sie über Python + YAML steuern, komplexere Dialoglogik wird jedoch in Colang geschrieben — daher „opinionated“. Die Dokumentation finden Sie unter docs.nvidia.com/nemo/guardrails.

Dies ist eine illustrative API-Struktur; sie benötigt das Package und ein konfiguriertes ./config-Verzeichnis.

from nemoguardrails import LLMRails, RailsConfig

config = RailsConfig.from_path("./config")
rails = LLMRails(config)
response = rails.generate(
    messages=[{"role": "user", "content": "Hello"}]
)

NeMos Repository beschreibt sein Threat Model ausdrücklich: „gängige LLM-Schwachstellen wie Jailbreaks und Prompt Injections“. Ebenso klar ist der Scope: „Die integrierten Guardrails können für einen bestimmten Production Use Case geeignet sein oder auch nicht … Entwickler sollten mit ihrem internen Application Team zusammenarbeiten, um sicherzustellen, dass die Guardrails die Anforderungen erfüllen.“ Der hier gezeigte Content-Screening-Pfad überwacht, was das Model sagt. NeMos aktuelle Dokumentation beschreibt außerdem Execution Rails, Custom Actions und Tool-Call-Inspections; dabei handelt es sich um konfigurierbare Runtime Controls, nicht um einen Beleg dafür, dass das eingesetzte Tool oder der MCP-Server den Call authentifiziert und autorisiert hat. Diese Grenze bleibt in der Verantwortung der Application.

Meta Llama Guard 4

Ein reiner 12B-Content-Classifier, der aus Llama-4-Scout pruned wurde und an der MLCommons-Hazards-Taxonomie ausgerichtet ist (13 Harm Categories plus Code-Interpreter-Abuse laut der Model Card). Meta benennt die Grenzen ungewöhnlich offen:

„Einige Hazard Categories benötigen möglicherweise aktuelles, faktisches Wissen, um vollständig evaluiert zu werden … Schließlich kann Llama Guard 4 als LLM für adversarial attacks oder prompt injection attacks anfällig sein, die den vorgesehenen Zweck umgehen oder verändern könnten: siehe Llama Prompt Guard 2 zur Erkennung von Prompt Attacks.“

Meta liefert ein separates Produkt, um seinen Content Classifier gegen Prompt Injection zu schützen. Wenn dieser Satz wie ein strukturelles Eingeständnis klingt, dann ist er das.

Guardrails AI

Eine Validator Registry. Sie kombinieren Hub Validators (PII über Presidio, JailbreakDetect, CompetitorCheck, Provenance Checks) mit on_fail-Actions exception | fix | fix_reask | filter | refrain | reask | noop oder einem Custom Callback (guardrailsai.com). Beachten Sie exception, nicht raise. Im aktuellen Source Code führt ein nicht erkanntes on_fail-String zur Custom-Callback-Behandlung und zu einem Fehler beim Validator-Setup, statt eine Warnung auszugeben und auf einen Fallback zurückzugreifen. Pinnen Sie die eingesetzte Version und testen Sie diesen Fehlerpfad. Es gibt kein einheitliches Threat Model; die Coverage entspricht der Vereinigungsmenge der installierten Validators. Sie erhalten Schutz für das, wofür Sie einen Validator haben, und keinen für alles andere.

Lakera Guard

Die etablierte SaaS API, trainiert auf zig Millionen Attack Samples aus Gandalf. Sie verspricht, Input und Output auf „prompt attacks … und data leakage“ zu prüfen. Lakeras separates Produkt AI Agent Security beschreibt außerdem Policy und Runtime Enforcement dafür, worauf Agents zugreifen, was sie aufrufen und was sie tun dürfen. Das ist eine andere Product Surface als der hier besprochene Content-Screening-Call. Prüfen Sie vor dem Deployment den aktuellen Produkt- und Pricing-Vertrag.

AWS Bedrock Guardrails

Die Enterprise-Default-Option, wenn Sie bereits Bedrock verwenden. ApplyGuardrail funktioniert mit jedem Model, unabhängig davon, ob es auf Bedrock läuft:

import boto3

brt = boto3.client("bedrock-runtime")

    guardrailIdentifier="gr-xxxxxxxxxxxx",
    guardrailVersion="2",
    source="INPUT",

Azure AI Content Safety

Liefert Prompt Shields als einheitlichen Endpoint, der „adversarial user input attacks … direkte und indirekte Bedrohungen“ erkennt und blockiert. Azure ist ebenfalls offen: „Sie können Azure AI Content Safety nicht verwenden, um illegale Bilder zur Ausbeutung von Kindern zu erkennen“, und die Qualität für mehrere Sprachen ist auf acht evaluierte Sprachen begrenzt.

Was Content Filters nicht entscheiden

Zwei Beobachtungen gelten für alle sieben Produkte.

Erstens sind veröffentlichte Zahlen zu Latency und Throughput rar. Bedrock, Azure und Lakera veröffentlichen Pricing, aber keine Garantien für Worst-Case-Latency. Meta veröffentlicht ebenfalls keine Garantie für einen gehosteten Endpoint von Llama Guard. NVIDIA liefert NeMo Guardrails als Software, die Sie selbst hosten; die Latency hängt daher von Ihrem Model und Ihrer Infrastruktur ab. Messen Sie jeden synchronen Check auf dem Critical Path, statt seine Kosten aus dem Produkt-Pricing abzuleiten.

Zweitens behandelt dieser Abschnitt die oben aufgeführten Content-orientierten Konfigurationen.

Ein Content Filter kann Model Input und Output prüfen. Er zeigt nicht, dass ein bestimmter Tool Call autorisiert ist, dass ein MCP-Server seinen Caller authentifiziert hat oder dass das System mehrstufige Data Exfiltration oder Code Execution vor einem Model Call stoppen kann. Authorization ist eine separate Entscheidung darüber, ob diese Identität diesen Call an diesen Server richten darf.

NeMo dokumentiert außerdem Execution Rails und Tool-Call-Inspection, und Lakera beschreibt Runtime Enforcement in seinem separaten AI-Agent-Security-Produkt. Das sind zusätzliche Controls, die konfiguriert und getestet werden müssen. Der Rest dieses Beitrags behandelt die Checks rund um Tool Execution.

Bedrohungen für AI-Agent-Sicherheit: sieben Incidents und die OWASP ASI Top 10

Die Lücke zwischen Text-Filtering und Execution Guarding war Mitte 2025 nicht mehr nur akademisch. Die folgenden sieben Incidents erreichten Retrieval, Konfiguration, Credentials, Package Installation oder CI Execution. Ein Content Classifier kann weiterhin einen verdächtigen String erkennen, aber die Controls, die diese Pfade direkt blockieren, liegen an den Grenzen von Tools, Identitäten, Sandboxes und der Supply Chain.

EchoLeak — CVE-2025-32711

Im Juni 2025 von Aim Labs, dem Research Arm von Aim Security, gegen Microsoft 365 Copilot veröffentlicht. Die technische Beschreibung befindet sich inzwischen bei Cato Networks, das dieses Team übernommen hat, unter dem Namen von Aim Labs’ ehemaligem Leiter Itay Ravia (Beschreibung). Eine präparierte E-Mail, formuliert als Anweisung an den menschlichen Empfänger, passierte XPIA (Microsofts integrierten Filter, der Copilot-Inputs auf Prompt-Injection-Attacks prüft). Von dort gelangte sie in Copilots Retrieval Layer, den Teil des Systems, der Ihre Dokumente durchsucht, um Kontext für Antworten zu finden. Die Forscher nennen diesen Trick RAG Spraying: Der Angreifer verwendet mehrere E-Mails oder eine lange, in Chunks aufgeteilte E-Mail, um die Retrieval-Exposure zu vergrößern. Das erhöht die Wahrscheinlichkeit eines Retrievals, garantiert es aber nicht. Sobald der Inhalt im System war, bettete Copilot die sensibelsten Daten der Session pflichtgemäß in einen Markdown-Link ein, der auf ein Bild auf einer vom Angreifer kontrollierten Domain zeigte. Die Teams Preview API, die auf einer Domain lief, der Microsofts eigene Browser Policies bereits vertrauten, rief diese Bild-URL automatisch ab und übergab dabei die Daten an den Angreifer. Keine Klicks. Aim Labs nannte diese Angriffsklasse „LLM Scope Violation“: Das Model überschreitet eine Grenze, die es niemals überschreiten sollte, und verwendet dabei nur Operationen, die jedes einzelne System als legitim betrachtete.

Jeder Schritt sah isoliert betrachtet legitim aus. Die E-Mail war an einen Menschen adressiert. Retrieval holte ein Dokument, das es holen sollte. Der Markdown-Link wurde so gerendert, wie Markdown-Links gerendert werden. Der Image Fetch traf eine allowlistete Domain. Die Forscher umgingen XPIAs Screening, und das Model folgte indirekten Anweisungen aus Retrieved Content. Der Fall kombiniert einen Prompt-Injection-Fehler mit Retrieval-, Rendering- und Egress-Verhalten; er zeigt nicht, dass Detectors nichts hätten markieren können.

Amazon Q Developer VS Code v1.84.0 — Juli 2025

AWS veröffentlichte einen kompromittierten Build, nachdem ein Angreifer über ein zu weitreichendes CodeBuild-GitHub-Token eine bösartige System-Prompt-Datei committet hatte (Advisory). Der Payload versuchte, die Instructions des Agents auf destruktive Aktionen auszurichten. Der bösartige Code wurde mit v1.84.0 verteilt, aber wegen eines Syntaxfehlers nicht ausgeführt. AWS widerrief die Credentials, entfernte den Code und veröffentlichte v1.85.0. Der Payload scheiterte wegen dieses Syntaxfehlers, nicht weil ein Security Control ihn blockierte.

Azure Web Apps MCP Service — CVE-2026-32211

Microsofts Vendor-CVE-Record betrifft fehlende Authentication im gehosteten Azure-Web-Apps-MCP-Service. Es handelt sich nicht um ein Advisory gegen jeden lokalen Azure MCP Server oder SDK. Ein Caller, der einen nicht authentifizierten Tool Service erreicht, kann das Model vollständig umgehen; der eingesetzte Service muss den Request authentifizieren und autorisieren.

Claude-Code-Project-Trust-Schwachstellen

Dies waren separate Schwachstellen und keine zwingenden Schritte eines einzigen Angriffs:

  1. Ein Bypass der Trust-Warnung wurde in 1.0.87 behoben.
  2. Pre-Trust Execution, CVE-2025-59536, wurde in 1.0.111 behoben. Die Repository-Konfiguration konnte Execution auslösen, bevor dem Projekt vertraut wurde.
  3. Exposure von Endpoint/API-Key, CVE-2026-21852, wurde in 2.0.65 behoben. Nicht vertrauenswürdige Konfiguration konnte API Traffic umleiten und Credentials offenlegen.

Project Trust, Hook Execution und Endpoint Configuration sind Host Controls. Ein Content Classifier kann keinen Code verhindern, der vor dem Model Call ausgeführt wird.

Axios 1.14.1 und 0.30.4 — 31. März 2026

Das Postmortem des Maintainers identifiziert zwei bösartige Releases, 1.14.1 und 0.30.4, die die Dependency plain-crypto-js@4.2.1 enthielten. Diese Dependency installierte einen Remote-Access-Trojaner: Malware, die einem Angreifer Remote Access auf die Maschine gibt. Die Exposure erforderte, dass die betroffenen Versionen aufgelöst und das relevante Installationsverhalten ausgeführt wurden; ein unabhängiges npm install rief sie nicht automatisch ab. Dies ist ein Supply-Chain-Execution-Fehler, unabhängig vom Verhalten eines Models.

Trivy-Actions-Tag-Hijacking — 19. März 2026

Das Aqua-Advisory beschreibt, dass 76 von 77 trivy-action-Versionstags und sieben setup-trivy-Tags auf bösartigen Content umgeleitet wurden. Der Entry Point der bösartigen Action sammelte den Speicher des Runner-Prozesses und Credential Files; schreiben Sie nicht den gesamten Collection-Pfad dem Scanner Binary zu. Das spätere Docker-Hub-Ereignis hatte ein separates Exposure Window.

Ein Workflow, der während der Kompromittierung ein betroffenes Tag auflöste, konnte den Payload ausführen. Tags sind bewegliche Referenzen. Pinnen Sie daher überprüfte Actions auf unveränderliche Commit-SHAs und verifizieren Sie Dependency Changes. Ein Coding Agent kann dieselbe unsichere Referenz in weitere Workflow Files übertragen.

OpenAI / Hugging Face — Evaluations im Juli 2026

OpenAIs Incident Report vom 26. August beschreibt interne Cybersecurity-Evaluation-Agents, die über gemeinsame Infrastruktur das Internet erreichten, über ein nicht autorisiertes Message Board kooperierten und Hugging-Face-Systeme kompromittierten. Das zentrale Model war nur intern verfügbar, und die Evaluations liefen mit reduzierten Safeguards. Dies ist Evidenz über diese Evaluationsumgebung, keine gemessene Failure Rate für öffentlich deployte Agents.

Die Engineering-Lektion lautet, dass ein erlaubter interner Service zu einem Outbound Path oder einem Cross-Session-Communication-Channel werden kann. Testen Sie, was ein Package Mirror, Proxy und Shared Store im Auftrag des Agents tun können, nicht nur, ob die Sandbox eine direkte Internetverbindung öffnen kann. METRs separate Untersuchung analysierte Agentenverhalten und Kollaboration; die Evaluation der Wirksamkeit von Safeguards und der Remediation lag außerhalb ihres Scopes.

Asynchrone Provider-Intervention

OpenAIs Misalignment Monitoring kann nach Output oder Actions intervenieren. Bei abgedeckten Models können Responses Requests mit persistiertem Reasoning, WebSockets oder OpenAI Compaction automatisch gestoppt werden. Andere Responses Requests können Alerts ohne automatisches Stoppen erzeugen; Chat Completions fällt nicht in dieses System. Ein Webhook aktiviert kein Blocking.

Ein blockierter Request meldet misalignment_policy_violation mit HTTP 403 vor dem Streaming; Errors können auch mitten im Stream eintreffen. Stoppen Sie weitere Actions, bewahren Sie Request- und Tool-Records auf und holen Sie eine Operator Review ein. Führen Sie keinen automatischen Retry durch. Frühere Effekte bleiben bestehen, und Alerts können falsch sein oder Probleme übersehen. Das ergänzt Detection, ersetzt aber keine lokale Authorization.

Die OWASP Agentic Security Initiative (ASI) ist eine Working Group, die sich speziell auf LLM-driven Agents konzentriert. Am 9. Dezember 2025 veröffentlichte sie die Agentic Security Initiative Top 10 für 2026: einen Katalog von zehn Risiko-Kategorien für Agent-Sicherheit.

Permission ist Infrastructure, nicht Prompt

Hier enden Guardrails als Produkt und werden zu einem Subsystem eines Harnesses. Drei aktuelle Systeme (OpenAI Agents SDK, Codex CLI und Claude Code) zeigen, wie eine Production Policy Surface tatsächlich aussieht. Alle drei setzen Permissions in Code durch. Keines verlässt sich darauf, dass das Model vorsichtig ist.

OpenAI Agents SDK

Das SDK trennt Harness und Compute. Hosted MCP Tools akzeptieren require_approval — entweder den reinen String "always" / "never" oder ein Filterobjekt, dessen Schlüssel diese beiden Policies sind und das die jeweils abgedeckten Tool-Namen enthält — sowie einen on_approval_request-Callback, der für jedes Tool unter "always" ausgelöst wird und mit optionalem Grund {"approve": bool} zurückgibt. Fine-Grained Tool Filtering (tool_filter) ist bei den Local-Server-Varianten (MCPServerStdio, MCPServerStreamableHttp, MCPServerSse) verfügbar, falls Sie es benötigen:

# No-run: illustrative Agents SDK shape; requires openai-agents, a configured hosted MCP server, and credentials.
from agents import Agent, HostedMCPTool

def approve(request):
    # Only tools under the "always" policy reach this callback.
    if request.data.name == "delete_repo":
        return {"approve": False, "reason": "escalate to a human reviewer"}
    return {"approve": True}

agent = Agent(
    name="Ops",
    tools=[HostedMCPTool(
        tool_config={
            "type": "mcp",
            "server_label": "github",
            "server_url": "https://mcp.example.com",
            "require_approval": {
                "always": {"tool_names": ["delete_repo"]},
                "never": {"tool_names": ["list_issues"]},
            },
        },
        on_approval_request=approve,
    )],
)

Der Approval Callback ist Code. Die Approval Policy pro Tool ist Code. Sie können diese Datei lesen, testen und diffen. Nichts davon gilt für einen System Prompt, der sagt: „Bitte gehen Sie vorsichtig mit Production um.“

Codex CLI und die Managed Policy Layer

OpenAIs Coding Harness unterstützt eine Managed-requirements.toml-Datei, die IT-Abteilungen über Device Management ausrollen können. Auf Unix-Systemen befindet sich die Systemdatei unter /etc/codex/requirements.toml. Sie wirkt als Hard-Constraint-Layer, sodass Projekt-Settings ihre Regeln nicht überschreiben können:

# /etc/codex/requirements.toml
[rules]
prefix_rules = [
    { pattern = [{ token = "rm" }, { any_of = ["-rf", "-fr"] }], decision = "forbidden", justification = "Recursive force-delete prohibited by IT policy" },
]

prefix_rules.decision akzeptiert nur "prompt" oder "forbidden", niemals "allow". Ein Projekt kann sich keine Permission geben, die der Managed Layer verbietet. MCP-Allowlists verwenden sowohl Name als auch Identität als Schlüssel, etwa einen Command String oder eine URL. Ein Projekt kann daher nicht behaupten, github-mcp zu sein, und auf den Server eines Angreifers zeigen. Die unterstützten Anforderungen unterscheiden sich je nach Client und Version. Die aktuelle Dokumentation verlangt für Managed Permission-Profile Keys ausdrücklich Codex 0.138.0 oder höher. Testen Sie daher jede Requirements Policy vor dem Rollout gegen alle Client-Versionen im Fleet.

Claudes Permission Ladder

Claude Code veröffentlicht keine feste Sequenz von sechs Checks für jeden Tool Call. Seine Permission Rules werden deny → ask → allow ausgewertet; die erste passende Regel bestimmt das Rule Outcome. Ein PreToolUse Hook läuft vor dem Permission Prompt. Ein PreToolUse-Entscheidung kann einen Call ohne Prompt erlauben, ihn ablehnen, den User fragen oder zur späteren Bearbeitung zurückstellen. Deny- und Ask-Rules gelten weiterhin; einige interaktive Actions behalten ebenfalls ihre Approval-Anforderungen. Der aktive Permission Mode verarbeitet Calls, die durch Rules und Hooks nicht aufgelöst wurden. Das Claude Agent SDK besitzt einen separaten canUseTool-Callback für ungelöste Requests. Dieser Callback ist ein SDK-Control und kein Claude-Code-CLI-Permission-Check.

Die Modes wechseln mit Shift+Tab zwischen default → acceptEdits → plan. auto, bypassPermissions und dontAsk werden unter bestimmten Entry Conditions aktiviert, die die Enterprise-Managed Policy Layer sperren kann. Das ist mehr als eine Config-Datei, die auf Korrektheit geprüft wird. Es ist eine State Machine mit Precedence Rules, die veröffentlicht ist, damit ein Security Team sie nachvollziehen kann.

Drei Blast Radii in einer Datei

So sieht die Struktur einer Permission Config im Codex-Stil mit einem Default und zwei benannten Profilen aus:

# ~/.codex/config.toml
approval_policy = "on-request"
sandbox_mode = "workspace-write"

[profiles.ci]
approval_policy = "never"
sandbox_mode = "read-only"

[profiles.release]
approval_policy = "untrusted"
sandbox_mode = "danger-full-access"

[mcp_servers.github]
command = "gh-mcp"
args = ["--readonly"]

Zwei Keys leisten die eigentliche Arbeit, und sie sind unabhängig voneinander. approval_policy entscheidet, wann ein Mensch gefragt wird. on-request erlaubt es dem Agenten, zu eskalieren, wenn er nicht weiterkommt. never fragt überhaupt nichts. untrusted stoppt bei jedem Command, der nicht auf der Trusted List steht. sandbox_mode entscheidet, worauf der Command zugreifen kann, wenn er ausgeführt wird.

CI unterbricht niemanden und kann nicht schreiben. Release kann die gesamte Maschine erreichen, muss aber fast alles zuerst mit einem Menschen klären. Das Release-Profil bezahlt für diese Reichweite: danger-full-access schaltet die Sandbox aus, sodass untrusted-Approval die einzige verbleibende Kontrolle ist. Alles außerhalb der Trusted List wird von einem Menschen freigegeben oder nicht ausgeführt. Diese Trusted List ist nun die gesamte Security Boundary.

Die Default- und CI-Profile behalten den Kernel unter sich: Seatbelt auf macOS, bubblewrap plus seccomp auf Linux und Restricted Tokens auf Windows. In jedem Fall spielt die Meinung des Models keine Rolle.

Sandbox Enforcement ist eine OS-Frage

Der Kernel erledigt hier die eigentliche Arbeit. Jedes OS stellt ein anderes Toolkit bereit, und die beiden CLIs greifen nicht immer auf dasselbe Element zurück:

PlattformClaude CodeCodex CLI
macOSSeatbelt über sandbox-exec mit einem SBPL-(Seatbelt Profile Language-)ProfilSeatbelt über sandbox-exec -p
Linuxbubblewrap + socat Network Proxybubblewrap + seccomp (Legacy-Landlock über use_legacy_landlock)
WindowsWSL2 erforderlichNative Restricted Tokens + Workspace ACLs + Capability SIDs

Sie stimmen dort überein, wo das OS eine Option bietet (Seatbelt, bubblewrap), und unterscheiden sich dort, wo dies nicht der Fall ist. Claude Codes Sandbox benötigt unter Windows WSL2; das ist eine Sandbox-Limitation und keine Aussage darüber, dass die CLI nicht nativ ausgeführt werden kann. Codex liefert eine native Windows Sandbox. In beiden Fällen erfolgt das Enforcement im Kernel, nicht im Model.

Codex stapelt auf dem Linux-Pfad drei Locks auf Kernel-Ebene um den Command. PR_SET_NO_NEW_PRIVS verhindert, dass der Prozess zusätzliche Privileges erlangt, selbst wenn er es versucht. Ein seccomp-Filter sorgt dafür, dass der Kernel ganze Klassen von System Calls ablehnt. Netzwerkrestriktionen hängen davon ab, ob Networking deaktiviert oder ein Proxy Mode konfiguriert ist; sie sind nicht universell auf Unix Sockets beschränkt. Siehe die Linux-Sandbox-Implementierung. Ein frischer isolierter /proc verbirgt den Rest der Maschine.

Codex härtet außerdem auf jeder Unix-Plattform sein eigenes Binary beim Start. Es setzt RLIMIT_CORE=0, um Crash Dumps zu unterdrücken, und verweigert das Debugger-Attach. Das ist eine andere Boundary als die Sandbox.

Die Windows-Sandbox hat zwei Modes. unelevated verwendet als User ein Restricted Token und bietet nicht das Network Enforcement des Elevated Modes. elevated verwendet dedizierte Sandbox Users, Firewall Rules und Filesystem ACLs.

Wenn Network Access deaktiviert ist, legt Codex Stub-.bat- und .cmd-Dateien für ssh und scp in einem Verzeichnis am Anfang von PATH ab. Diese Commands beenden sich mit einem Non-Zero-Status, statt die echten Binaries zu erreichen. Codex setzt außerdem HTTP_PROXY, HTTPS_PROXY, ALL_PROXY und die Git-Proxy-Variablen auf einen nicht erreichbaren lokalen Port. Diese Maßnahmen betreffen kooperative Tools; Proxy-Variablen und Command Stubs allein können beliebiges Networking nicht begrenzen.

Eine Sandbox benötigt außerdem einen definierten Failure Mode. In Claude Codes aktueller Konfiguration stoppt sandbox.failIfUnavailable: true die Execution, wenn die Sandbox nicht gestartet werden kann. allowUnsandboxedCommands: false deaktiviert den Unsandboxed-Retry-Escape-Hatch des Agents, aber excludedCommands umgeht ihn weiterhin. Testen Sie die effektive Konfiguration mit fehlenden Dependencies und einem verbotenen Ziel.

Credential Brokering ist inzwischen auch lokal verfügbar. Claudes sandbox.credentials kann benannte Dateien und Environment Variables ablehnen. Environment-Variable-Masking, seit v2.1.199 verfügbar, gibt sandboxed Commands einen Platzhalter und erlaubt dem Proxy, den echten Wert in Requests an konfigurierte Hosts einzusetzen. Setzen Sie enge injectHosts und konfigurieren Sie TLS Termination; Masking autorisiert die angeforderte Operation nicht. Diese Controls decken sandboxed Bash Commands ab. Hooks, MCP Processes und andere Execution Paths benötigen daher weiterhin ihre eigene Credential Policy.

Isolation-Optionen jenseits von Claude Code und Codex

Wenn Sie einen eigenen Agenten entwickeln, erweist sich „Sandbox“ als Oberbegriff. Die Open-Source-Optionen liegen auf einem Spektrum — von leichten Namespace-Wrappers auf der einen bis zu vollständigen MicroVMs auf der anderen Seite — und die Wahl hängt davon ab, wie sehr Sie dem darin ausgeführten Code vertrauen.

Leichte Isolation – gleicher Kernel, weniger Privileges:

  • bubblewrap — ein Low-Level-Namespace-Sandbox-Constructor, der von Flatpak und Claude Code unter Linux verwendet wird. Der Caller muss Filesystem, Netzwerk und optionale seccomp Policy selbst festlegen; bubblewrap selbst ist keine fertige Security Policy.
  • Standard-Docker-/OCI-Container — Namespace Isolation über einem gemeinsam genutzten Host-Kernel. Keine Sandbox für nicht vertrauenswürdigen Code; die eigenen Docs von gVisor machen dies ausdrücklich klar („containers are not a sandbox“). Als Ausgangspunkt in Kombination mit seccomp und AppArmor sinnvoll, aber nicht mehr.

Application-Kernel-Isolation – der Agent spricht mit einem Fake Kernel:

  • gVisor — Googles User-Space-Kernel. Ihr Container glaubt, unter Linux zu laufen, während eine in Go implementierte Kernel-Schicht System Calls abfängt. Das reduziert die direkte Exposure des Host-Kernels ohne Guest VM, bringt aber Kompatibilitäts- und Performance-Trade-offs mit sich.

Vollständige VM-Isolation – eigener Kernel pro Sandbox:

  • Firecracker — AWS’ MicroVM-Technologie. Jede VM verfügt unter KVM über einen eigenen Linux-Kernel; Container teilen sich den Host-Kernel. Ein Compromise in einer VM muss weiterhin VMM- oder Host-Controls überwinden, um den Host oder eine andere VM zu beeinflussen. Firecrackers Jailer und ein gepatchter Host bleiben daher Teil des Schutzes.
  • Kata Containers — Container UX mit VM-grade Isolation. Die Wahl für Kubernetes-Cluster, die nicht vertrauenswürdigen Code ausführen müssen.

Platforms – was Sie mieten würden, statt es selbst zu bauen:

  • E2B verpackt Firecracker in eine gehostete Sandbox API.
  • OpenSandbox trennt das SDK von der durch Administratoren konfigurierten Runtime Isolation. Standard-Docker-runc ist keine MicroVM; der Firecracker-Pfad verwendet Kata mit Firecracker über Kubernetes.
  • Microsofts Agent Governance Toolkit (MIT-lizenziert, April 2026) fügt darauf eine Runtime Policy Engine hinzu. Es ordnet Policy Controls der OWASP ASI Top 10 zu. Die angegebene Launch Latency betrifft eine einzelne Policy Engine, nicht die Gesamtkosten jedes Checks in einem deployten Agenten.

Wählen Sie das Isolation Level anhand von Trust Level des Codes, Tenant Boundary, Network Access, Host Data und Recovery Cost. Namespace- und seccomp-Controls können für vertrauenswürdige interne Tools ausreichen. LLM-generierter Code und nicht vertrauenswürdige Packages benötigen eine stärkere Boundary wie gVisor, Kata oder eine MicroVM, gefolgt von Tests gegen Escape- und Exfiltration-Pfade in Ihrem eigenen Threat Model.

Claude Code und Codex haben aus demselben Menü gewählt wie alle anderen. Sie haben es nur unterschiedlich verpackt.

PreToolUse Hooks als programmierbare Policy

Modes und Allowlists decken die einfachen Fälle ab: „Lass den Agenten Files editieren, aber kein Bash ausführen“, „Lehne alles ab, was wie rm -rf aussieht.“ Sie versagen, wenn Ihre Policy echte Logik benötigt. Sie wollen git push nur blockieren, wenn der Branch main ist. Sie wollen jedes Edit ablehnen, das eine Datei bearbeitet, die auf eine Secret Regex matcht. Sie wollen Shell Calls pro Session rate-limitieren oder jede Tool Invocation in Ihr zentrales Audit Log schreiben (das SIEM, also das Security Information and Event Management System, das Ihr Security Team bereits überwacht).

Nichts davon passt in eine statische Allowlist. Dafür gibt es Hooks — Shell Commands, die Claude Code an bestimmten Punkten im Tool-Call-Lifecycle ausführt, mit der Möglichkeit, den ausstehenden Call zu prüfen und ein strukturiertes Allow/Deny zurückzugeben. Claude Code stellt rund dreißig Lifecycle Events bereit (die vollständige Liste finden Sie in der Dokumentation), und eines davon ordnet alles andere neu: Ein PreToolUse Hook, der permissionDecision: "deny" zurückgibt, blockiert ein Tool unabhängig vom Mode.

So sieht die Settings-Struktur aus:

{
    "permissions": {
        "defaultMode": "acceptEdits",
        "deny": ["Bash(rm -rf:*)", "Bash(sudo:*)", "Read(.env*)"]
    },
    "hooks": {
        "PreToolUse": [
            {
                "matcher": "Bash",
                "hooks": [
                    {
                        "type": "command",
                        "command": ".claude/hooks/pre-bash-firewall.sh"
                    }
                ]
            },
            {
                "matcher": "Edit|Write",
                "hooks": [
                    {
                        "type": "command",
                        "command": ".claude/hooks/protect-paths.sh"
                    }
                ]
            }
        ]
    }
}

Die statischen deny-Rules und die dynamischen Hooks haben unterschiedliche Failure Modes. Ein PreToolUse-Result mit deny blockiert vor dem normalen Permission Flow. Ein Timeout bei einem command-, HTTP- oder MCP-Tool-Hook ist dagegen Non-Blocking: Claude Code setzt den Flow fort. In diesem Beispiel kann acceptEdits daher ein Edit oder Write genehmigen, wenn protect-paths.sh abläuft. Lassen Sie eine nicht verhandelbare Pfadbeschränkung nicht allein von einem Command Hook abhängen. Legen Sie statische Restrictions in Deny Rules oder der Sandbox ab. Für dynamische Policy wählen Sie ein Control, dessen Evaluator-Failure restriktiv bleibt, und testen Sie sowohl das Timeout-Verhalten als auch ein explizites Deny.

Ein Hook kann ein Shell Script mit fünf Zeilen oder eine vollständige Policy Engine sein. Entscheidend ist die Return-Struktur:

{
    "hookSpecificOutput": {
        "hookEventName": "PreToolUse",
        "permissionDecision": "deny",
        "permissionDecisionReason": "writes outside workspace prohibited"
    }
}

Das Model sieht ein strukturiertes Deny. Der Reasoning Loop aus Teil 1 verarbeitet es wie jede andere Tool Observation: Die Ablehnung wird zu Context, der Agent plant neu, und der Loop läuft weiter. Genau das ermöglicht „Permission ist Infrastructure“. Das Deny ist in denselben Mechanismus integriert, der auch einen 500er eines HTTP Tools verarbeitet. Es ist kein separater Security Workflow, der nachträglich angebaut werden muss.

Ein häufiges Anti-Pattern besteht darin, einen System Prompt mit der Anweisung „Lösche keine Dateien ohne explizite Bestätigung des Users“ zu schreiben, den Agenten auszuliefern und diese Anweisung als Control zu verwenden. Ein injizierter Prompt oder ein Tool Result, das ein Angreifer kontrolliert, kann diese Anweisung umgehen. Das Model ist keine Policy Engine. Es kann das von Ihnen geschriebene Pattern erkennen — oder eines, das ein Angreifer vorgibt.

Human Approval funktioniert nur als Eskalation

Byte sagt

Nach zwanzig Approval Prompts ist es leicht, auf „Approve“ zu klicken, ohne zu lesen. Heben Sie Prompts für Actions auf, die eine Entscheidung eines Menschen benötigen.

Content Filters prüfen, was das Model sagt. Permission Rules prüfen den Tool Call, bevor er ausgeführt wird. Human-in-the-Loop Review behandelt Actions, für die weiterhin ein Mensch benötigt wird. Wenn Menschen 93 % der Prompts genehmigen, prüfen Sie die Eskalationsregeln und die Qualität der Prompts.

LangGraph liefert das Pause/Resume-Primitiv. HumanLayer verpackt den Approval Channel, und Anthropics Nutzungsdaten zeigen, warum Anzahl und Qualität der Eskalationen gemessen werden müssen.

Das LangGraph-Primitiv

LangGraphs interrupt() + Command(resume=value) pausiert einen Graphen, persistiert seinen State über den konfigurierten Checkpointer und setzt ihn mit einem von Menschen gelieferten Wert fort. Ob dieses Resume sicher ist, hängt von einem Detail in der Dokumentation ab:

„Wenn die Execution fortgesetzt wird (nachdem Sie den angeforderten Input bereitgestellt haben), startet die Runtime den gesamten Node von Anfang an neu — sie setzt nicht exakt an der Zeile fort, in der interrupt aufgerufen wurde.“

Aus diesem Restart-Verhalten folgen drei Einschränkungen:

1. Side Effects vor interrupt() müssen idempotent sein. Wenn der Mensch antwortet, läuft der gesamte Node von oben erneut, nicht ab der Zeile interrupt(). Wenn Ihr Node also eine E-Mail sendet, auf Approval wartet und anschließend „sent“ zurückgibt, wird die E-Mail beim Resume ein zweites Mal gesendet. Lösung: Legen Sie Side Effects nach den Interrupt oder machen Sie sie wiederholbar (Dedupe Keys, Upsert statt Insert, Cache anhand der Message ID).

2. Interrupts werden anhand des Index, nicht des Namens, Resumes zugeordnet. Enthält ein einzelner Node zwei interrupt()-Calls, ordnet LangGraph sie den Command(resume=...)-Werten in der Reihenfolge ihres Auftretens zu. Jede Verzweigung, die die Anzahl ausgeführter Interrupts verändert (ein if, das beim Resume einen Interrupt überspringt, oder ein Loop mit einer anderen Iterationsanzahl), bringt die Indizes durcheinander. Ein Resume Value kann dadurch beim falschen Interrupt landen.

3. Halten Sie Payloads JSON-safe. LangGraphs Dokumentation verlangt JSON-serialisierbare Werte für interrupt() und Resume Payloads. Verwenden Sie Strings, Zahlen, Booleans, Arrays und Dictionaries, die solche Werte enthalten. Vermeiden Sie Functions, Class Instances und andere komplexe Objekte, da die Serialisierung vom konfigurierten Checkpointer abhängt. Konvertieren Sie Approval-Daten in Dictionaries und Primitives, bevor Sie sie an interrupt() übergeben oder über eine HTTP API bereitstellen.

Die drei kanonischen Patterns:

# No-run: illustrative LangGraph sketches; requires LangGraph, a tool decorator, interrupt, and smtp_send.
# (a) Approval check
@tool
def send_email(to, subject, body):
    resp = interrupt({"action": "send_email", "to": to,
                      "subject": subject, "body": body})
    if resp.get("action") == "approve":
        return smtp_send(to, subject, body)
    return "Email cancelled"

# (b) Edit-and-continue
def review_node(state):
    edited = interrupt({"content": state["generated_text"]})
    return {"generated_text": edited}

# (c) Mid-run state correction — conditional edge
class AgeState(TypedDict):
    age: int | None
    pending_question: str | None

def get_age_node(state: AgeState):
    question = state.get("pending_question") or "What is your age?"
    answer = interrupt(question)  # once per node invocation
    if isinstance(answer, int) and answer > 0:
        return {"age": answer, "pending_question": None}
    return {"pending_question": f"'{answer}' is not valid. Please enter a positive number."}

def route_age(state: AgeState):
    return END if state.get("age") is not None else "get_age"

builder = StateGraph(AgeState)
builder.add_node("get_age", get_age_node)
builder.add_edge(START, "get_age")
builder.add_conditional_edges("get_age", route_age)

Resume ist graph.invoke(Command(resume={"action": "approve"}), config=cfg). LangGraph 0.4+ unterstützt Dict-basierte Multi-Interrupt-Resumes für parallele Branches. Das ist relevant, sobald Ihr Agent fan-out betreibt.

HumanLayer: Approval als Produkt

HumanLayer ist die Managed-Version derselben Idee. Dekorieren Sie eine Function, und Approval Requests werden mit Rules für die zuständigen Personen an Slack, E-Mail oder Discord geroutet. Wenn der Agent versucht, multiply(2, 5) aufzurufen, sehen die Logs so aus:

last message led to 1 tool calls: [('multiply', '{"x":2,"y":5}')]
HumanLayer: waiting for approval for multiply

Der Approver klickt in Slack auf Approve oder Deny. Bei einem Deny formuliert es die HumanLayer-Dokumentation so: „HumanLayer gibt Ihr Feedback an den Agenten zurück, der anschließend seinen Ansatz anpassen kann.“ Dieses Feedback erlaubt dem Agenten, seinen Plan zu überarbeiten, statt eine Ablehnung als Sackgasse zu behandeln.

Approval Fatigue in den Daten

Anthropic veröffentlichte die tatsächlichen Daten im Februar 2026. Drei Ergebnisse sind wichtiger als der Rest.

„Wir stellten fest, dass 80 % der Tool Calls von Agents stammen, die offenbar mindestens eine Art von Safeguard besitzen (etwa Restricted Permissions oder Human-Approval-Anforderungen), dass 73 % offenbar in irgendeiner Form einen Human-in-the-Loop haben und dass nur 0,8 % der Actions offenbar irreversibel sind.“

Das sind die guten Nachrichten. Betrachten Sie 80 % als Obergrenze, denn Anthropics Fußnote 14 ergänzt: „Claude überschätzte die menschliche Beteiligung häufig, daher erwarten wir, dass 80 % eine Obergrenze darstellen.“

„Neuere User (<50 Sessions) verwenden Full Auto-Approve ungefähr in 20 % der Fälle; bei 750 Sessions steigt dieser Wert auf über 40 % der Sessions.“

Das ist der Drift. User beginnen vorsichtig und werden weniger vorsichtig, während sie Vertrauen in das Tool aufbauen. Das entspricht menschlichem Verhalten und ist kein Charakterfehler. Es ist ein Telemetry Signal, das Ihr System verfolgen sollte. (Ein kleiner Fact-Check-Hinweis: In der Sekundärberichterstattung wurde dies häufig als „20 % → über 50 %“ zitiert. Nach Anthropics Primärdaten lautet die verifizierte Zahl 20 % → über 40 %. Wenn Sie die 50-%-Zahl gesehen haben, stammt sie daher.)

Anthropics Engineering-Post vom März 2026 zum Auto Mode von Claude Code nennt die entscheidende Zahl:

„Claude-Code-User genehmigen 93 % der Permission Prompts. Wir haben Classifiers entwickelt, um einige Entscheidungen zu automatisieren, die Sicherheit zu erhöhen und gleichzeitig Approval Fatigue zu reduzieren … Wenn eine Session drei aufeinanderfolgende Denials oder insgesamt 20 Denials ansammelt, stoppen wir das Model und eskalieren an den Menschen.“

Eine hohe Approval Rate ist ein Anlass zu prüfen, ob Prompts den Menschen bei Entscheidungen helfen; sie beweist keinen universellen Failure Threshold. Anthropics zweistufiger Classifier reduziert Prompts und eskaliert gebündelte Denials. Die gemeldete False-Positive-Rate von 0,4 % wurde anhand von 10.000 Traffic Examples ermittelt. False-Negative-Raten lagen bei 17 % für 52 reale, übereifrige Actions und bei 5,7 % für 1.000 synthetische Exfiltration Cases. Das sind unterschiedliche Populationen, keine komplementären Prozentsätze und kein Beleg dafür, dass Classification Sandboxing ersetzt.

Qualität der Eskalation messen

Nehmen Sie routinemäßige, reversible Actions in die Allowlist auf und protokollieren Sie sie. Eskalieren Sie Actions, deren Side Effects eine Boundary überschreiten, die die Runtime nicht rückgängig machen kann, etwa eine externe Nachricht, einen Production Write, einen Force Push oder eine Zahlung. Anthropic beschreibt das Ziel so, dass ein Mensch eingreifen können muss, wenn eine Entscheidung echte Konsequenzen hat.

Verfolgen Sie den vollständigen Funnel, statt ein fremdes Approval-Rate-Ziel zu übernehmen: vorgeschlagene Actions, automatische Allows, Eskalationen, Approvals, Denials, Edits und Incidents nach einem Approval. Eine hohe Approval Rate kann bedeuten, dass die Prompts routinemäßiges Rauschen sind. Eine hohe Denial- oder Edit-Rate kann bedeuten, dass der Planner die falsche Action vorschlägt oder die für den Approver erforderlichen Informationen verbirgt. Der sinnvolle Threshold hängt von der Action-Klasse und den Kosten eines False Allow ab. Legen Sie ihn daher anhand Ihrer eigenen Incident- und Review-Daten fest.

MCP-Scoping und die Supply Chain

MCP verbindet Agents mit externen Tools wie Slack, GitHub und Datenbanken. Dadurch wird sein Authorization Model zu einem Teil der Security Boundary. Die Spec-Revisions von 2025 trennten die Rollen von Token Issuer und Resource Server und fügten Resource Indicators hinzu. Diese Historie erklärt, welche Audience- und Forwarding-Checks ein Server heute durchsetzen muss.

MCP Authorization in drei Revisionen

Authorization war in der Spec vom 26.03.2025 für MCP-Implementierungen optional. Für ein Production HTTP Deployment, das User-Daten oder Tools schützt, empfehle ich OAuth 2.1 mit PKCE (Proof Key for Code Exchange), das die Spec verlangt, sobald eine Implementierung OAuth Authorization unterstützt. Das frühe Design erlaubte einem MCP Server, zwei Rollen zu übernehmen. Der Authorization Server stellt Tokens aus; der Resource Server akzeptiert sie. Das sind getrennte Rollen, selbst wenn ein Service beide übernimmt. Wenn dieser Service einen Request an einen anderen Server weiterleitet, kann dasselbe Credential an einen Ort gelangen, für den es nie vorgesehen war. Das war die Lücke.

Die Revision vom 18.06.2025 machte die Rollen explizit. Ein geschützter MCP Server agiert als OAuth Resource Server, während ein Authorization Server das Token ausstellt. Der Authorization Server kann gemeinsam mit dem Resource Server gehostet oder separat betrieben werden. RFC 8707 Resource Indicators binden das Token an eine Target Resource, und RFC 9728 Protected Resource Metadata gibt dem Client einen expliziten Discovery Path. Die Spec verbietet einem MCP Server außerdem, das Token eines Clients Upstream weiterzuleiten.

Die Revision vom 25.11.2025 behielt diese Trennung bei und arbeitete an den Bereichen, die ein Client korrekt implementieren muss. Die Discovery des Authorization Servers erhielt OpenID Connect Discovery, sodass ein Client den richtigen Issuer finden kann, statt ihn zu erraten. Incremental Scope Consent wurde in den WWW-Authenticate-Header verschoben. Dadurch kann ein Server bei Bedarf einen weiteren Scope anfordern, statt von Anfang an alles zu verlangen. Die Client Registration erhielt OAuth Client ID Metadata Documents als empfohlenen Mechanismus und ersetzte damit Dynamic Registration für die meisten Deployments. Auch die Discovery von Protected Resource Metadata wurde an RFC 9728 angepasst, wodurch WWW-Authenticate mit einem .well-known-Fallback optional wurde.

Prüfen Sie vor der Implementierung die Versioning-Seite. Am 6. September 2026 ist die aktuelle Revision 2026-07-28. Sie verlangt, dass jeder Request die Protocol Version deklariert, und erlaubt dem Server, jeden Request unabhängig zu akzeptieren oder abzulehnen. Ein Client kann vorab server/discover aufrufen, um eine Version auszuwählen, aber Discovery ist optional. Die Deklaration und Negotiation pro Request bleiben erforderlich, auch wenn der Client einen Unsupported-Version-Error verarbeitet und mit einer gemeinsam unterstützten Version erneut versucht.

Audience Binding begrenzt Replay gegen den falschen MCP Server. Es neutralisiert nicht die oben beschriebenen separaten Claude-Code-Konfigurationsschwachstellen: Ein Host-seitiger Hook kann weiterhin vor dem Start des Models ausgeführt werden, und ein nicht vertrauenswürdiges Projekt kann weiterhin versuchen, die lokale Konfiguration zu verändern. Token Scope, Project Trust, Hook Policy und Sandboxing bleiben separate Controls.

Die MCP-Checkliste für 2026

Wenn Sie MCP in Production bereitstellen oder nutzen:

  1. Behandeln Sie Authentication als Production Requirement, nicht als Protocol Default. MCP lässt Authorization optional, aber ich empfehle OAuth 2.1 mit PKCE für ein geschütztes HTTP Deployment. Das Advisory zum gehosteten Azure-Web-Apps-MCP-Service betraf fehlende Authentication. Wenn Ihr Server Traffic akzeptiert, ohne die Credentials des Callers zu verifizieren, haben Sie ein Tool gebaut, das jeder aufrufen kann, der es erreicht.
  2. Tokens sind Audience-bound. Fordern Sie ein Token für die Target MCP Resource an und validieren Sie, dass das präsentierte Token Ihren Server als Audience nennt. Lehnen Sie Tokens ab, die für eine andere Resource ausgestellt wurden.
  3. Trennen Sie Read- und Write-Authority bewusst. MCP bindet ein Token an einen Resource Server, nicht an ein einzelnes Tool. Wenn ein Slack Server ein Credential mit chat:write akzeptiert und es sowohl an Read- als auch an Write-Handler routet, kann ein Read-orientiertes Tool über die Policy dieses Servers zu einem Message-Sending Path werden. Verwenden Sie separate Resource Server oder separate Credentials und Authorization Checks, wenn Read- und Write-Operationen unabhängige Blast Radii benötigen.
  4. Verwenden Sie frische, kurzlebige Tokens statt permanenter API Keys. Das Vault-Pattern von Claude Managed Agents (Anthropic Engineering) ist die Referenz: Der Agent selbst sieht die echten Credentials nie. Der Proxy ruft die zugehörigen gespeicherten Credentials aus dem Vault ab, ruft das Tool im Auftrag des Agents auf und gibt das Result zurück. Dass für jeden Call ein frisches Token ausgestellt wird, ist keine dokumentierte Garantie; kurzlebige Credentials sind eine Deployment-Empfehlung.

Supply-Chain-Controls gelten weiterhin

Die Axios- und Trivy-Incidents sind bekannte Package- und CI-Supply-Chain-Failures, angewendet auf Systeme, die Dependency Installation automatisieren. Automation erhöht Anzahl und Geschwindigkeit der Executions. Deshalb müssen Version-, Provenance- und Review-Controls ausgeführt werden, bevor der generierte Command CI oder eine Sandbox erreicht.

Die Abwehr ist unkompliziert:

  • Pinnen Sie Versionen im Lockfile. Agents dürfen niemals eine Floating Version auflösen — kein @latest, kein npm update, kein --upgrade.
  • Scannen Sie in CI mit Tools, die unabhängig von der geprüften Component sind.
  • Verwenden Sie GitHub Commit SHAs für Actions, nicht Tags.
  • Prüfen Sie Dependency Diffs in Agent-driven PRs vor dem Merge.

Das sind Standard-Supply-Chain-Controls. Agent Automation verändert ihre Häufigkeit, nicht ihren Mechanismus.

Ein Policy-Stack für den Market Analyst Agent

Der Market Analyst Agent aus Teil 1 ist ein kleiner LangGraph Agent, der Marktdaten abruft und einen Analystenbericht schreibt — aber nicht so klein, wie diese Beschreibung vermuten lässt. Zusätzlich zu den Market-Data-Tools führt er über subprocess eine allowlistete CLI aus, evaluiert vom Model geschriebenes Python In-Process und erstellt simulierte Trade Records. Er nutzt Tool Invocation, Code Execution und Approval Routing, platziert aber keine echten Orders. So sieht ein minimaler Policy-Stack dafür aus.

Layer 1: Ein PreToolUse Hook, der vor der Execution ablehnt

Selbst ein Agent, der „nur Aktiendaten liest“, kann Dinge anfordern, die er nicht sollte: ein curl an eine vom Angreifer kontrollierte URL, Writes außerhalb des Workspace oder git-Mutations im Host-Repository. Eine Deny Rule ist Infrastructure, kein Prompt. Der folgende Sketch gibt die eigene Decision Shape des Agents zurück, nicht das umschließende hookSpecificOutput-Envelope, das Claude Code erwartet.

# agent/permissions.py
from pathlib import Path

DENY_COMMANDS = frozenset({
    "rm -rf", "sudo", "chmod 777",
    "curl -X POST", "wget", "nc ",
})
WORKSPACE = Path("./workspace").resolve()

def _outside_workspace(path: str) -> bool:
    # Resolve first: "~/.ssh/id_rsa" and "workspace/../../etc" both
    # have to become real paths before the comparison means anything.
    return not Path(path).expanduser().resolve().is_relative_to(WORKSPACE)

def pre_tool_use(tool_name: str, args: dict) -> dict | None:
    if tool_name == "shell":
        cmd = args.get("command", "")
        if any(bad in cmd for bad in DENY_COMMANDS):
            return {"permissionDecision": "deny",
                    "reason": f"command pattern disallowed: {cmd!r}"}
    if tool_name == "write_file":
        path = args.get("path", "")
        if _outside_workspace(path):
            return {"permissionDecision": "deny",
                    "reason": f"path outside workspace: {path!r}"}
    return None  # fall through to mode / canUseTool

Der Sketch macht den Control Point sichtbar. Der Hook gibt ein strukturiertes Deny zurück, und der Reasoning Loop erhält diese Ablehnung als Tool Observation.

Die Path-Prüfung ist eine Allowlist: eine Workspace Root, alles andere wird abgelehnt. Eine Denylist verbotener Prefixes blockiert nur Pfade, die Sie bedacht haben. ~/.ssh/id_rsa wird niemals genau so geschrieben, wie Sie es dokumentiert haben. Die Command-Prüfung ist weiterhin eine Denylist. Substring Matching ist keine Production Shell Policy. Eine echte Implementierung sollte den Command parsen und sich bei der Execution auf die OS Sandbox verlassen. Der Sketch selbst ist keine Execution Boundary: Wenn ein externer Hook ihn ausführt, muss ein Timeout eine unabhängige Workspace Restriction aktiv lassen.

Layer 2: Ein Input Canary gegen Prompt Injection

Agent-Goal-Hijack (ASI01) kommt oft über eine abgerufene Webseite, eine User Message oder ein Research-Paper-PDF. Ein günstiger Regex Canary erkennt wörtliche Instruction Patterns und erzeugt ein nützliches Telemetry Event. Obfuskierte, mehrsprachige und kontextabhängige Injections wird er übersehen, daher kann er nicht als Decision Boundary dienen:

# agent/input_canary.py
import re

INJECTION_PATTERNS = [
    re.compile(r"ignore\s+(?:all\s+|any\s+|the\s+)?"
               r"(?:previous\s+|prior\s+|above\s+|earlier\s+)?"
               r"(?:instructions|rules|prompts?)",
               re.IGNORECASE),
    re.compile(r"you are now|act as|roleplay as", re.IGNORECASE),
    re.compile(r"system[ _:]*prompt", re.IGNORECASE),
    re.compile(r"<\|im_(start|end)\|>"),
]

def input_canary(text: str) -> dict | None:
    for pat in INJECTION_PATTERNS:
        m = pat.search(text)
        if m:
            return {"flag": "possible_injection", "match": m.group(0)}
    return None

Loggen Sie markierte Inputs; lehnen Sie sie nicht automatisch ab. False Positives sind für einen Research Assistant teuer. Das Log ermöglicht Ihnen jedoch zu erkennen, wenn die Anzahl der Flags bei einem User plötzlich ansteigt.

Layer 3: Ein Custom Completion Validator

Ein Custom Harness kann einen Report validieren, bevor es ihn als abgeschlossen akzeptiert. In diesem Sketch muss das Harness die zurückgegebene Decision verarbeiten: continue sendet das Feedback für einen begrenzten Retry an das Model; allow_stop akzeptiert den Report. Wenn die Retries aufgebraucht sind, muss das Harness einen Failure melden, statt den invaliden Output zu akzeptieren. Die Function allein erzwingt diesen Loop nicht.

Dies sind Custom Decision Names und nicht der Claude-Code-Stop-Contract, der decision: "block" mit einem reason verwendet, um ein Stoppen zu verhindern. Schema- und Ticker-Check unten veranschaulichen die Application-Level-Validation:

# No-run: illustrative policy sketch; requires Pydantic and the repo-local agent.schemas module.
# agent/completion_validator.py
from pydantic import ValidationError
from agent.schemas import MarketReport

def validate_completion(final_output: str) -> dict:
    try:
        report = MarketReport.model_validate_json(final_output)
    except ValidationError as e:
        return {"decision": "continue",
                "feedback": f"schema invalid: {e.errors()[:3]}"}
    if not report.tickers:
        return {"decision": "continue",
                "feedback": "no tickers in report — did you skip the snapshot step?"}
    return {"decision": "allow_stop"}

Diese Checks stellen fest, dass der Output dem Report Schema entspricht und mindestens einen Ticker nennt. Sie verifizieren nicht die Marktdaten oder die Analyse.

Layer 4: Approval vor Outbound Actions

Der execute_trade des Market Analysts ist ein simulärer, idempotenter State Transition. Er demonstriert daher Approval Routing statt eines irreversiblen Financial Side Effects. Bei einer echten Outbound Integration — E-Mail, Slack, ein Report an einen Kunden oder eine Brokerage Order — zeigen Sie dem Menschen die vorgeschlagene Action und warten Sie auf Approval oder Rejection, bevor das Tool ausgeführt wird. Verwenden Sie interrupt() für diese Pause:

# No-run: illustrative outbound-tool sketch; requires LangGraph, a tool decorator, and smtp_send.
# agent/tools/notify.py
from langgraph.types import interrupt

@tool
def send_report(to: str, body: str):
    resp = interrupt({
        "action": "send_report",
        "to": to,
        "body": body,  # Review the complete content that will execute.
    })
    if resp.get("action") == "approve":
        return smtp_send(to, body)
    return "send cancelled by human"

Outbound Actions vervollständigen die lethal trifecta. Verlangen Sie Approval für Outbound Actions, wenn die bestehende Authorization und Deployment Policy sie nicht abdecken. Binden Sie das Approval an vollständiges Ziel und vollständigen Content; geänderte Arguments erfordern eine neue Decision. Messages an Finance, Kunden oder andere externe Empfänger sollten dem Approver zeigen, was gesendet wird und wohin.

Was dieser Stack nicht leistet

Dies ist keine Abwehr gegen:

  • Eine kompromittierte Upstream Dependency (Axios-Klasse). Der Agent führt aus, was uv sync vorgibt.
  • Ein bösartiges .mcp.json in einem geklonten Repository (CVE-2025-59536-Klasse). Dort greift das Permission Model des Host-MCP-Clients, nicht der Code des Agents.
  • Eine Data-Theft-Chain aus legitimen Tools (EchoLeak-Klasse) — der Agent liest private Daten, ruft externe URLs ab und sendet Messages nach außen. Unterbrechen oder begrenzen Sie diesen Exfiltration Path mit Scoped Data Access, Trusted Routing, Egress Restrictions und erforderlichem Approval. Das Entfernen einer Capability blockiert diesen konkreten Path, nicht jeden möglichen Angriff.
  • Einen Escape aus execute_python_analysis, dem In-Process-Python-Evaluator des Agents. Er blockiert eine Liste von Statement Types, lehnt jeden Identifier ab, der mit einem Underscore beginnt, und erlaubt Imports nur aus json, math und statistics. Aber exec im Worker-Prozess ist keine Boundary: Ein Bypass läuft mit den File Handles und dem Netzwerk des Workers. Verschieben Sie ihn hinter Filesystem-, Netzwerk- und Credential Isolation sowie CPU-, Memory- und Time Limits, bevor Sie nicht vertrauenswürdigen Code evaluieren. Ein Subprocess allein übernimmt den Zugriff und ist keine Security Sandbox.

Diese vier Layer sind lokale Policy, und lokale Policy ist die innerste von Ihnen kontrollierte Layer, nicht die einzige. Jeder Punkt dieser Liste muss an anderer Stelle abgefangen werden — im Lockfile, im MCP Client, an der Process Boundary um generierten Code oder in Controls, die verhindern, dass nicht vertrauenswürdige Instructions private Daten mit einem Exfiltration Target verbinden.

Die wichtigsten Erkenntnisse

  1. Content Filters und Execution Policy schützen unterschiedliche Boundaries. Filters prüfen Model Input und Output. Tool Authorization, Credential Scope, Sandboxes und Supply-Chain-Controls wirken auf die Pfade, die in den sieben Incidents verwendet wurden.
  2. Die meisten OWASP-ASI-Kategorien benötigen Controls außerhalb des Model Outputs. Verwenden Sie die Liste, um jede Threat der Component zuzuordnen, die sie tatsächlich blockieren oder protokollieren kann.
  3. Permission ist Infrastructure, nicht Prompt. Claude Code dokumentiert die Precedence von Deny-, Ask- und Allow-Rules, während PreToolUse vor der Execution blockieren kann. Das Claude Agent SDK stellt einen separaten canUseTool-Pfad bereit. Andere Runtimes benötigen ein ebenso testbares Precedence Model.
  4. Behandeln Sie das strukturierte Deny eines PreToolUse Hooks wie jede andere Tool Observation. Der Reasoning Loop verarbeitet es bereits. Sie benötigen keinen separaten Security Workflow.
  5. Eine Approval Rate von 93 % ist ein Signal, Prompt Quality und Escalation Frequency zu prüfen. Tracken Sie Edits, Denials und Incidents nach Approvals, statt ein universelles Ziel zu übernehmen.
  6. Audience-bound Tokens und Per-Session-Vaults begrenzen Credential Replay und Exposure. Sie ersetzen Project Trust, Hook Policy oder Sandboxing nicht.
  7. Supply-Chain-Checks müssen mit der Geschwindigkeit der Automation laufen. Pinnen Sie Versionen und Action-SHAs, scannen Sie in CI und prüfen Sie Dependency Changes in von Agents verfassten Pull Requests.
  8. Bauen Sie die Policy Layer so, dass ein neuer Product Launch sie nicht entwertet. OpenAI Agents SDK, Codex CLI und Claude Code drücken dieselben Primitives unterschiedlich aus. Entscheidend sind die Primitives (Permission Ladders, Hooks, Sandboxes, Interrupts, Audience-bound Tokens).
