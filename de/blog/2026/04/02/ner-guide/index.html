NER-Leitfaden 2026: GLiNER, spaCy, Transformers und LLMs

Named Entity Recognition (NER) umfasst inzwischen kompakte Encoder, Open-Vocabulary-Modelle und LLM-basierte Extraktion. In der zitierten CrossNER-Evaluation übertrifft ein GLiNER-Modell mit 300M Parametern den berichteten Zero-Shot-F1-Wert von UniNER mit 13B Parametern. Ein neuerer Bi-Encoder berichtet bei 1.024 Entity Types und vorab berechneten Labels einen bis zu 130-fachen Throughput gegenüber dem vergleichbaren gliner_small-v2.5 Uni-Encoder. Das Paper hat dies auf einer einzelnen H100 mit Batch Size 1 für Inputs mit 64, 256 und 512 Tokens gemessen. Diese Ergebnisse sprechen für Experimente, nicht für ein allgemeingültiges Production-Ranking.

Für Workloads, die von expliziten Spans dominiert werden, sind kompakte Encoder in der Regel die schnellere und günstigere Option. LLMs bleiben nützlich, um Trainingsdaten zu erzeugen und Fälle zu bearbeiten, die Inferenz oder Normalisierung erfordern.

Was ist Named Entity Recognition?

Named Entity Recognition findet Spans in Texten und weist ihnen Types wie Person, Organisation, Datum, Produkt oder domänenspezifische Labels zu. NER identifiziert die Mention. Entity Linking ist der separate Schritt, der eine Mention einem kanonischen Datensatz oder einem Ontology-Konzept zuordnet.

Wo moderne Systeme NER einsetzen

NER findet weiterhin Textspans und weist ihnen Labels zu. Geändert hat sich seine Position im System. Heute liefert NER Filter für RAG, strukturierte Argumente für Agent-Tools und Felder für Document-Processing-Pipelines. Dadurch werden Latenz, Kosten und Schema-Flexibilität ebenso wichtig wie die Benchmark-Genauigkeit.

RAG: bessere Retrieval-Ergebnisse durch Entity Extraction

Similarity Search allein hat Schwierigkeiten, wenn eine Frage exakte Entities enthält. Bei „what did Anthropic say about model safety in Q4 2024?“ sollte das System „Anthropic“ und „Q4 2024“ als Metadata Filter extrahieren, statt sich ausschließlich auf Embeddings zu verlassen.

Beim Indexing extrahieren Sie Entities aus jedem Chunk und speichern sie als Metadata: {"organizations": ["Anthropic"], "dates": ["Q4 2024"], ...}. Damit können Sie vor der Vector Search nach Entities filtern. Knowledge Graph RAG (GraphRAG, LlamaIndex Property Graphs) geht weiter: NER plus Relation Extraction baut einen Graphen auf, der Multi-Hop-Fragen beantworten kann, an denen flache Embeddings scheitern.

Zur Query-Zeit steuern aus der Nutzerfrage extrahierte Entities das Routing. Eine Frage mit einem Unternehmensnamen geht an einen Finance Index; eine Frage mit Medikamentennamen an eine Clinical Knowledge Base. GLiNER ist nützlich, wenn sich das Schema oder die Entity Types zur Query-Zeit ändern. Unbekannte Unternehmens- oder Medikamentennamen allein erfordern keine Open-Vocabulary-Labels; ein Closed-Label-Model kann neue Mentions bekannter Types weiterhin erkennen.

AI Agents: Text in strukturierte Fakten umwandeln

Agents erhalten unstrukturierten Text wie Webseiten, API-Responses und User Messages. NER wandelt diesen Text in strukturierte Fakten um, über die der Agent Reasoning ausführen, die er speichern oder an Tools übergeben kann.

Für Tool Routing erfordert eine Anfrage wie „schedule a meeting with Sarah Chen from Accenture on Thursday at 2pm“ vor dem Aufruf der Calendar API PERSON: Sarah Chen, ORGANIZATION: Accenture und DATETIME: Thursday 2pm. Ein lokaler Encoder vermeidet den API-Roundtrip und ist häufig deutlich schneller. Die Latenz hängt jedoch von Model, Runtime, Hardware, Batch Size und Label Count ab. Messen Sie beide Pfade anhand des Calendar Workloads, statt von einer festen Differenz in Millisekunden auszugehen.

NER unterstützt außerdem Entity Tracking über mehrere Konversationen hinweg. Agent-Memory-Systeme müssen erkennen, dass „Sarah“ in Turn 3 und „Ms. Chen“ in Turn 12 dieselbe Person sind. NER identifiziert die Spans; Entity Linking ordnet sie derselben ID zu.

In beiden Fällen ist die Einschränkung die Latenz. Wenn jeder von zehn sequenziellen Schritten einen 200-ms-NER-Call ausführt, addieren sich diese NER-Calls zu zwei Sekunden wahrgenommener Verzögerung. Ein einzelner Call verursacht 200 ms. Encoder-Modelle eignen sich in der Regel besser für Entity-Work innerhalb von Agent Loops als LLM-basierte Extraktion.

Document Intelligence: von Bildern zu strukturierten Daten

OCR wandelt Bilder in Text um. NER wandelt diesen Text in strukturierte Felder um.

Eine Standard-Pipeline verwendet zunächst OCR, etwa Tesseract, Azure Document Intelligence oder AWS Textract, um Text und Bounding Boxes zu erzeugen. NER extrahiert anschließend Felder wie invoice_number, vendor_name, line_items, total und due_date. Dieselbe Abfolge gilt für Verträge, medizinische Datensätze und regulatorische Dokumente.

Moderne Document Pipelines können Layout Understanding, Entity Extraction und Relation Extraction kombinieren. OCR oder ein Layout-Aware Document Model liefert weiterhin Text, Lesereihenfolge, Tabellen und Bounding Boxes. GLiNER 2 kann anschließend Entity-, Relation-, Classification- und hierarchische Structured Extraction über diesen Text in einem Schema-Driven Pass kombinieren.

Bei den meisten dieser Pipelines entscheiden die Kosten. Kalkulieren Sie Ihre tatsächlichen monatlichen Dokumentvolumina einschließlich Retries und Review. Ein kompakter Encoder kann auf der CPU laufen, während ein API-basiertes LLM Kosten und Latenz pro Dokument verursacht. Ein praxisnaher Test besteht darin, einen repräsentativen Invoice-Satz von einem LLM labeln zu lassen. Fine-Tunen Sie GLiNER auf den geprüften Datensätzen und vergleichen Sie anschließend beide Pfade anhand von Field-Level-F1, Latenz und Gesamtkosten.

PII Detection und LLM Guardrails

Die Datenschutzgrundsätze und Sicherheitsanforderungen der DSGVO (Artikel 5, 25 und 32), die technologieneutrale Security Rule von HIPAA (HHS Guidance) sowie der kalifornische CCPA in der durch den CPRA geänderten Fassung schreiben unterschiedliche Rechte und risikobasierte Schutzmaßnahmen vor. Die zitierten Vorschriften verlangen weder NER noch eine bestimmte Pre-Model-Scanning-Architektur. Dies ist keine Rechtsberatung; lassen Sie die für Ihre Daten und Jurisdiktion geltenden Anforderungen von einer Rechtsberatung prüfen. NER kann Data Inventory, Minimierung oder De-Identification unterstützen, ist aber nur ein einzelner Control, dessen Recall für die relevante Datenbasis und Jurisdiktion validiert werden muss.

NER kann diese Aufgabe direkt übernehmen. De-Identification-Modelle finden Spans wie PERSON, SSN, PHONE, EMAIL und ADDRESS und schwärzen sie entweder oder ersetzen sie durch synthetische Äquivalente. Microsoft Presidio kombiniert Recognizer mit Anonymization Operators; seine Beispiele enthalten GLiNER als Recognizer. GLiNER2-PII mit 0,3B Parametern ist ein weiterer Kandidat: Das Paper behandelt 42 PII Types auf Character-Span-Auflösung. Keines der beiden Systeme ist ein Compliance-Nachweis. Validieren Sie den Recall nach Datenformat, Jurisdiktion, Sprache und PII-Klasse, bevor Sie einen Detector als Control einsetzen.

Im von John Snow Labs durchgeführten Vendor-Vergleich mit 48 von Experten annotierten Open-Source-Dokumenten aus sechs PHI-Klassen wurde in der Token-Level-Evaluation ein F1-Wert von 96 % berichtet. Für Azure wurden 91 %, für AWS 83 % und für GPT-4o 79 % berichtet. Die Studie ordnete Provider-Labels dem Ground-Truth-Schema zu und schloss nicht abbildbare Predictions aus. Betrachten Sie sie als engen Provider-Vergleich, nicht als Compliance-Nachweis. Ein separater Deployment-Bericht beschreibt, dass Providence täglich mehr als 100.000 klinische Notizen verarbeitet.

Für LLM Guardrails eignet sich NER als Pre-Screening Layer: Scannen Sie den User Input vor dem Senden an eine externe API auf PII und blockieren oder anonymisieren Sie ihn anschließend. Das kann schneller oder einfacher sein, als das LLM um Self-Moderation zu bitten. Behandeln Sie dies als Deployment-Hypothese: Messen Sie beide Pfade für Ihr Model, Ihre Hardware, Ihren Input-Mix und Ihr Recall-Ziel. False Negatives sind weiterhin möglich. Ergänzen Sie daher ein weiteres Control für die PII-Exposition, die Ihr System nicht akzeptieren kann. GLiNER ist hier besonders nützlich, weil PII-Kategorien je nach Jurisdiktion variieren. Sie können unter einer neuen Regulierung neue Entity Types wie „genetic information“ ergänzen, ohne das Model neu zu trainieren.

GLiNER: Span-to-Label Matching für Open-Vocabulary NER

GLiNER (NAACL 2024, Zaratiana et al.) machte Encoder-basiertes NER bei einem Bruchteil der Kosten gegenüber LLMs konkurrenzfähig. Statt NER als Sequence Labeling oder Text Generation zu behandeln, modelliert GLiNER es als Matching-Problem. Das Model bewertet jeden möglichen Textspan – jede zusammenhängende Wortfolge wie „Bill Gates“ oder „Microsoft“ – gegen jeden Entity-Type-Label und behält die Paare mit hohen Scores.

Das Model erhält Entity-Type-Labels und Input-Text als eine Sequenz: [ENT] person [ENT] organization [ENT] date [SEP] Bill Gates founded Microsoft.... Ein bidirektionaler Transformer (DeBERTa-v3) encodiert alles gemeinsam.

Aus dem Output bildet das Model zwei Repräsentationsmengen. Eine repräsentiert Entity Types aus den Token-Positionen [ENT]. Die andere repräsentiert Textspans, indem Start- und End-Token-Vektoren über ein kleines FFN kombiniert werden. Ein Dot Product zwischen einer Span-Repräsentation und einer Entity-Type-Repräsentation ergibt einen Score.

Wenden Sie Sigmoid an, erhalten Sie die Wahrscheinlichkeit, dass der Span von Token iii bis Token jjj zum Entity Type ttt gehört: ϕ(i,j,t)=σ(SijT⋅qt)\phi(i, j, t) = \sigma(S_{ij}^T \cdot q_t)ϕ(i,j,t)=σ(SijT​⋅qt​). Dabei ist SijS_{ij}Sij​ der vom FFN erzeugte Span-Vektor und qtq_tqt​ das Entity-Type-Embedding aus dem entsprechenden [ENT]-Token (Zaratiana et al., 2024, Gl. 1–2). Spans sind auf 12 Tokens begrenzt, um die Verarbeitung schnell zu halten.

GLiNER akzeptiert bei der Inference natürliche Label-Beschreibungen, ohne dass ein Retraining erforderlich ist. Die Extraction-Qualität hängt jedoch von der Formulierung des Labels und der Domain-Fit ab. Sie übergeben Entity Types wie „person“, „adverse drug reaction“ oder „financial instrument“, und das Model bewertet Spans gegen diese Types. Die folgenden Konfigurationen mit 50M, 90M und 300M sind die Original-Modelle des Papers. Die aktuelle Model Card für v2.1 listet dagegen englische Checkpoints mit 166M, 209M und 459M sowie einen multilingualen Checkpoint mit 209M Parametern – alle unter Apache 2.0. Vergleichen Sie Latenz oder Speicherbedarf dieser Generationen nicht so, als wären die Parameternamen identisch (GLiNER v2.1 Model Card).

Für einen echten Hard-Zero-Shot-Test müssen Sie sowohl Ziel-Types als auch Zielbeispiele zurückhalten. Eine Type Description wie „a medically confirmed adverse effect caused by a treatment“ liefert dem Model mehr Informationen als allein adverse event. Das garantiert keinen Transfer, aber Description-Driven ZeroNER übertraf Name-Only-Baselines in den Benchmarks mit zurückgehaltenen Types (Cocchieri et al., 2025).

Die Trainingsdaten des Originalmodells stammten aus dem Dataset Pile-NER: 44.889 Passagen mit 240K Entity Spans über 13K Entity Types, alle von ChatGPT gelabelt. Das Training von GLiNER-L dauerte auf einer einzelnen A100 etwa fünf Stunden (Zaratiana et al., 2024).

Wie GLiNER im Vergleich zu spaCy abschneidet

spaCy ist eine der etabliertesten NLP-Libraries in Production. Die Library arbeitet außerdem unter anderen architektonischen Bedingungen als GLiNER.

spaCy-Pipelines (en_core_web_sm, en_core_web_trf) führen Closed-Vocabulary-NER durch: eine feste Menge von Entity Types (PERSON, ORG, GPE, DATE usw.), die zur Trainingszeit definiert werden. Sie benötigen einen neuen Entity Type? Dann sammeln Sie gelabelte Daten und trainieren neu. Verwenden Sie das gepflegte 3.8-Model-Package, statt eine noch nicht veröffentlichte Major-Version als Production-Upgrade anzunehmen. Die Model Card von en_core_web_trf 3.8.0 berichtet 90,19 NER F1 auf OntoNotes 5.0 – allerdings nur für die 18 vordefinierten Types (spaCy Model Card).

GLiNER führt Open-Vocabulary-NER durch: Zur Inference funktioniert jedes Label, ohne dass Retraining erforderlich ist. Das macht GLiNER zur besseren Wahl, wenn Entity Types im Voraus unbekannt sind, sich häufig ändern oder domänenspezifisch sind („adverse drug reaction“, „financial instrument“, „threat indicator“).

Meine Empfehlung: Verwenden Sie spaCy für Standard-Entity-Types, für die Pretrained Pipelines gut validiert sind. Verwenden Sie GLiNER, wenn Sie flexible Zero-Shot-Types benötigen oder sich Ihre Pipeline ohne Retraining anpassen muss. Beide können eine Pipeline gemeinsam nutzen: spaCy übernimmt Tokenization und Sentence Splitting, GLiNER die Entity Extraction.

Eine supervised Transformer-Baseline

Bei stabilen Labels und repräsentativen annotierten Spans sollten Sie als supervised Baseline mit einem Fine-Tuned Token Classifier wie RoBERTa oder DeBERTa beginnen. Dieser tauscht Label-Flexibilität gegen task-spezifische Genauigkeit. Vergleichen Sie ihn mit spaCy und GLiNER anhand von Exact-Span-F1, Recall pro Label, Calibration, Latenz und Kosten auf demselben Domain Set.

UniNER und NuNER: Wie klein kann man werden?

UniNER (ICLR 2024, Zhou et al.) und NuNER (EMNLP 2024, Bogdanov et al.) destillieren beide LLM-Annotationen in kleinere NER-Modelle – unterscheiden sich aber darin, wie klein diese Modelle werden können.

UniNER: der maximalistische Ansatz

UniNER führt Fine-Tuning von LLaMA-7B/13B auf 45.889 Input-Output-Paaren durch, die von ChatGPT generiert wurden. Für jeden Entity Type beantwortet das Model die Frage „What describes [type] in the text?“ und gibt JSON-Listen aus. Ein wichtiger Trainingstrick: Frequency-Based Negative Sampling erhöht den F1-Wert von 31,5 % auf 53,4 % (Zhou et al., 2024).

UniNER-7B erreicht über 43 Datasets hinweg 41,7 % Zero-Shot-F1 und übertrifft damit ChatGPTs 34,9 % um sieben Punkte. Die 13B-Variante erreicht 43,4 %, also nur 1,7 Punkte mehr bei nahezu doppeltem Compute-Aufwand (Zhou et al., 2024).

Der Production Trade-off: Das im Paper höher bewertete UniNER-Setup fragt jeden Entity Type sequenziell ab. Die All-in-One-Variante verwendet eine Response, lag aber im Durchschnitt 3,3 % niedriger. Bei FP16 benötigt ein 7B-Checkpoint allein für die Weights ungefähr 14 GB; Quantization mit weniger Bits kann diesen Footprint reduzieren. Außerdem steht das Model unter einer restriktiven CC-BY-NC-4.0-Lizenz.

NuNER: der minimalistische Ansatz

NuNER startet mit RoBERTa-base (125M Parameter) und verwendet Contrastive Training mit 4,38 Millionen GPT-3.5-Annotationen über 200K Konzepte hinweg. Nach dem Training wird der Concept Encoder entfernt; der Text Encoder lässt sich als RoBERTa-Ersatz in jede Standard-NER-Pipeline einsetzen (Bogdanov et al., 2024).

NuNER übertrifft einfaches RoBERTa über alle Few-Shot-Größen hinweg um 6–15 F1-Punkte. Mit nur einem Dutzend Beispielen pro Entity Type erreicht NuNER trotz 56-mal weniger Parametern dasselbe Ergebnis wie UniNER-7B (Bogdanov et al., 2024).

Beide Papers unterstützen die Distillation von LLM-Annotationen in kleinere NER-Modelle. NuNER zeigt, dass ein Encoder mit 125M Parametern bei verfügbarem task-spezifischem Fine-Tuning-Dataset das berichtete UniNER-7B-Ergebnis erreichen kann – mit MIT-Lizenzierung und CPU-freundlicher Inference.

GLiNER 2: ein Model, vier Tasks

Im ursprünglichen GLiNER-Ökosystem waren NER, Relation Extraction, Classification und Document-Level Extraction auf separate Modelle verteilt. Das GLiNER2-Paper aus EMNLP 2025 vereinte NER, Classification und hierarchische Extraction in einem Model mit 205M Parametern; spätere aktuelle Releases ergänzten Relation Extraction über dasselbe Schema Interface.

Die Architektur behält das Cross-Encoder-Design bei, erweitert den Context auf 2.048 Tokens (das Vierfache des Originals) und ergänzt deklarative Schemas zur Definition von Extraction Tasks. Das Training verwendet 135.698 echte Dokumente, die mit GPT-4o annotiert wurden, sowie 118.636 synthetische Beispiele (Zaratiana et al., 2025).

Auf CrossNER im Zero-Shot-Setting erreicht GLiNER 2 0,590 F1 und liegt damit nahe an GPT-4o mit 0,599 im Mid-2025-Benchmark des Papers. Für Classification beträgt der Durchschnitt über sieben Benchmarks 0,72, verglichen mit 0,69 für DeBERTa-v3-large. Für die CPU berichtet das Paper bei den getesteten Label Counts eine Classification Latency von 130–208 ms. Die DeBERTa-Baseline steigt von 1.714 ms bei fünf Labels auf 16.897 ms bei 50 Labels (Zaratiana et al., 2025).

from gliner2 import GLiNER2
extractor = GLiNER2.from_pretrained("fastino/gliner2-base-v1")

# Multi-task composition in ONE forward pass
schema = (extractor.create_schema()
    .entities({"person": "Names of people", "company": "Organization names"})
    .classification("sentiment", ["positive", "negative", "neutral"])
    .relations(["works_for", "founded", "located_in"])
    .structure("product_info")
        .field("name", dtype="str")
        .field("price", dtype="str"))
text = "Acme launched a $19 widget in Berlin."
results = extractor.extract(text, schema)

Aktuelle GLiNER2-Releases stellen Entity Recognition, Classification, hierarchische Extraction und Relation Extraction über ein gemeinsames Schema bereit. Das EMNLP-Paper evaluiert NER und Classification; es berichtet keinen Benchmark zur hierarchischen Extraction und deckt die spätere Relation API nicht ab. Behandeln Sie den Vier-Task-Pfad als Deployment-Fähigkeit, die Sie benchmarken müssen, nicht als Beleg dafür, dass ein Model die Genauigkeit von vier spezialisierten Modellen bewahrt.

Der Bi-Encoder: NER mit Millionen von Labels skalieren

Das ursprüngliche GLiNER encodiert Labels und Text gemeinsam. Gemeinsames Encoding wird zunehmend teurer, wenn Label-Text den Context verbraucht und für jedes Dokument erneut encodiert werden muss. Der Crossover hängt von Checkpoint, Label-Beschreibungen und Hardware ab. Wenn dasselbe große Type Inventory für viele Dokumente wiederverwendet wird, sollte der GLiNER Bi-Encoder der Standardvergleich sein. Er teilt Text- und Label-Encoding auf zwei separate Transformer auf (Stepanov et al., 2026).

Der Text Encoder verwendet ModernBERT (Ettin-Familie), der Label Encoder Sentence Transformers (BGE oder MiniLM). Spans und Labels werden per Dot Product gescored. Dadurch können Entity-Type-Embeddings einmalig vorab berechnet und gecacht werden. Bei der Inference muss nur der Text encodiert werden; die Label-Seite wird zu einem Cache Read.

from gliner import GLiNER

LLMs als Teacher: eine Fallstudie zu $70 und eine deploybare Pipeline

Das LLM-as-Teacher-Muster trennt teure Annotation von günstigerer Inference. Zwei veröffentlichte Fallstudien zeigen, wie Teams es unter unterschiedlichen Bedingungen eingesetzt haben.

Die CFM-Fallstudie

In einer Hugging-Face-Fallstudie extrahierte Capital Fund Management Unternehmensnamen aus etwa 900.000 Financial-News-Headlines. GLiNER im Zero-Shot-Modus erreichte 87,0 % F1. Das Team verwendete Llama 3.1-70B, um das Dataset in etwa acht Stunden für rund $70 zu annotieren, und prüfte anschließend in weiteren acht Stunden 2.714 Samples über Argilla.

Das Fine-Tuning von GLiNER auf diesen Daten erreichte in der Fallstudie 93,4 % F1, verglichen mit 92,7 % beim Llama-70B-Teacher. Die Autoren berichten $0,10 pro Stunde auf der CPU für das Fine-Tuned Model und $8 pro Stunde für den Teacher (CFM-Fallstudie). Diese Werte beziehen sich auf eine Financial-News-Aufgabe und ein bestimmtes Infrastructure Setup.

Die Studie von Refuel AI

Der technische Report von Refuel AI benchmarkt LLM Labeling über acht NLP-Datasets, darunter CoNLL-2003. Er berichtet in seinem Setup eine Übereinstimmung von 88,4 % mit der Ground Truth für GPT-4 (März 2023) und 86,2 % für menschliche Annotatoren, außerdem ein 20-mal schnelleres und siebenmal günstigeres Labeling. Das Ensemble routet einfache Beispiele an günstigere Modelle und schwierige Beispiele an GPT-4 und erreicht in den berichteten Experimenten mehr als 95 % Übereinstimmung (Technischer Report von Refuel AI). Behandeln Sie diese Werte als Vendor-Reported Results unter dem Annotation Protocol dieser Studie.

Eine Production Pipeline

Ein praxisnaher Production Flow umfasst sechs Schritte:

  1. Annotation Guidelines in natürlicher Sprache verfassen
  2. Von Menschen gelabelte Validation- und Held-Out-Testsets erstellen, deren Größe sich aus Entity Prevalence, Anforderungen an Slices pro Label und der gewünschten Breite des Confidence Intervals ergibt. Ein Pilot mit 50–200 Dokumenten kann die Guidelines kalibrieren, ist aber keine standardmäßige Größe für Production Evaluation.
  3. Ein LLM mit versioniertem Prompt und explizitem Output Schema verwenden, um umfangreiche Trainingsdaten zu labeln; Model-Version, Prompt und Quelltext mit jedem Label speichern
  4. Eine Teilmenge über Argilla oder Label Studio prüfen
  5. Einen kompakten Encoder (GLiNER, SpanMarker, RoBERTa) per Fine-Tuning anpassen
  6. Nur deployen, wenn der Encoder den Quality Gate erfüllt und die gemessenen Gesamtkosten senkt. CFM berichtete in seinem Setup 16–80-fach niedrigere stündliche Infrastructure Costs; beziehen Sie Annotation, Review, Serving und Retraining in den Vergleich ein.

Das LLM kann das Volumen manueller Annotation reduzieren. Das Team bleibt jedoch für Validation Set, Annotation Guidelines, gezieltes Review und Error Analysis verantwortlich.

Wo GLiNER scheitert und LLMs weiterhin nützlich sind

Der Sease-Benchmark von Oktober 2025 verglich GLiNER mit GPT-4.1-mini auf 30 Query-Parsing-Tasks. GPT-4.1-mini erzielte 100 % vollständig korrekte Ergebnisse. GLiNER erzielte 53 % (16 von 30). GLiNER antwortete jedoch in 0,08 Sekunden statt in 1,21 Sekunden beim LLM – also 15-mal schneller.

In diesem Benchmark mit 30 Tasks scheiterte GLiNER in drei wiederkehrenden Mustern:

  1. Implizite Entities: „event“ aus „Elton John performed at Madison Square Garden“ extrahieren – im Text steht nicht wörtlich „event“, aber das LLM schließt auf „concert“
  2. Sensitivität gegenüber Label-Formulierungen: „2022“ erzielt gegen „date“ einen Score von 0,388, gegen „year“ dagegen 0,958 – kleine Label-Änderungen verursachen große Score-Schwankungen
  3. Value Mapping: GLiNER gibt den exakten Surface Text („family houses“) statt des kanonischen Werts („Single family house“) zurück. Ein LLM kann diese Normalisierung durchführen, wenn Prompt und Schema die Zielwerte definieren.

Verschachtelte und überlappende Entities

GLiNER verwendet standardmäßig Flat Decoding, das überlappende Spans unterdrückt. Die API unterstützt außerdem flat_ner=False, sodass verschachtelte Predictions möglich sind. Die Qualität hängt jedoch von Checkpoint, Labels und Domain-Daten ab. Benchmarken Sie beide Decoding-Modi auf einem verschachtelten Span-Level-Testset, bevor Sie ein spezialisiertes Model auswählen.

Verwenden Sie GLiNER für explizite Entity Extraction und routen Sie Fälle, die Inferenz, Reasoning oder Mapping auf vordefinierte Ontologien erfordern, an ein LLM. Der Routing-Schwellenwert sollte aus einem gelabelten Domain Set abgeleitet werden.

NER evaluieren: Metriken, Fallstricke und Testsets

Ein Model kann auf einem kuratierten Testset 95 % F1 erreichen und dennoch auf der nach dem Deployment auftretenden Dokumentverteilung scheitern. Erstellen Sie das Evaluation Set aus der Production Distribution und halten Sie Slices für seltene Formate und Entity Types vor, die der aggregierte F1-Wert verschleiern kann.

Die zentralen Metriken

  • Entity-Level-F1: Die Standardmetrik. Eine Prediction ist nur dann korrekt, wenn sowohl die Span-Grenzen als auch der Type exakt mit der Ground Truth übereinstimmen. Dies ist die Metrik, die die meisten Papers berichten.
  • Token-Level-F1: Bewertet jedes Token einzeln. Diese Metrik überschätzt Ergebnisse, weil das korrekte Erkennen eines großen Teils einer langen Entity Teil-Credit liefert. Bevorzugen Sie Entity-Level-F1.
  • Precision vs. Recall: Diese Größen haben häufig asymmetrische Kosten. Bei De-Identification ist Recall wichtiger – einen Namen zu übersehen ist schlimmer als zu viel zu schwärzen. Bei Database Extraction ist Precision wichtiger – falsche Einträge verfälschen nachgelagerte Analysen.

Häufige Evaluationsfehler

  1. Überschätzung durch Partial Matches: Wenn „Bill“ extrahiert wird, während das Gold-Label „Bill Gates“ lautet, zählen manche Scripts dies als Partial Match. Verwenden Sie Exact-Span-Matching, sofern es keinen Grund dagegen gibt.
  2. Type Confusion: Wenn „Microsoft“ korrekt als Span erkannt, aber als PERSON statt ORG gelabelt wird, sollte die Bewertung null ergeben. Prüfen Sie, ob Ihr Evaluation Code dies korrekt behandelt.
  3. Leakage im Testset: Wenn Test-Entities mit Trainings-Entities überlappen, werden Scores überschätzt. Zero-Shot-Benchmarks wie CrossNER und Few-NERD testen die Generalisierung.
  4. Unkontrollierte Label Prompts: Ein kurzer Type Name und eine getestete Type Description sind unterschiedliche Inputs. Versionieren Sie Label-Beschreibungen, Thresholds, Checkpoint-Revisionen und Decoding Mode gemeinsam mit dem Score.
  5. Zero-Shot-Claims für nur eine Sprache: Leiten Sie keine multilingualen Aussagen aus Englisch ab. OpenNER umfasst 36 Corpora und 52 Sprachen; die Baselines fanden kein einzelnes Model, das in jeder Sprache am besten ist (Palen-Michel et al., 2025). In FiNERweb-Experimenten veränderte der Wechsel von englischen zu zielsprachlichen Labels den F1-Wert je nach Setting um 0,02–0,09 (Golde et al., 2026). Testen Sie beide Label-Sprachen, wenn das Produkt lokale Terminologie verwendet.
  6. Ein Lauf ist kein Urteil: Berichten Sie, sofern relevant, die Variation über Random Seeds, Threshold Sweeps und wiederholte Production Samples. Kleine Slice Counts machen ein Model-Ranking instabil.

Ein Domain-Testset erstellen

Für Production Evaluation empfehle ich:

  1. Aus Production Data sampeln, nicht aus kuratierten Beispielen. Schließen Sie die unordentlichen Dokumente ein, die Ihr Model tatsächlich sehen wird.
  2. Das Testset auf die benötigte Schätzung auslegen. Wählen Sie die Anzahl anhand von Entity Prevalence, Slice-Größen pro Label und der gewünschten Breite des Confidence Intervals. Berichten Sie Bootstrap- oder analytische Confidence Intervals.
  3. Mindestens zwei Annotatoren auf einem Calibration Subset einsetzen. Schlichten Sie Uneinigkeiten und berichten Sie ein spanbezogenes Agreement-Maß. Agreement diagnostiziert Ambiguität und die Qualität der Guidelines; es stellt keine Obergrenze für Model Performance dar.
  4. Nach Schwierigkeit stratifizieren – einfache Fälle (sauberer Text, Standard-Types) und schwierige Fälle (mehrdeutige Entities, Fachjargon, verrauschter Text).
  5. Privacy- und Fairness-Slices beibehalten. Berichten Sie bei PII den Recall nach PII Type, Sprache, Locale, Dokumentformat und relevanten demografischen oder Name-Origin-Slices. Beschränken Sie den Zugriff der Evaluatoren auf sensible Rohtexte, setzen Sie Retention Limits und prüfen Sie False Negatives.

Continual NER benötigt ein unveränderliches Regression Set

Production-Taxonomien ändern sich. Fügen Sie neue Types hinzu, ohne unbemerkt die Bedeutung eines alten Types zu verändern. Bewahren Sie ein versioniertes, unveränderliches Regression Set für bestehende Types, ein separates Testset für den neuen Type und ein Changelog für Änderungen der Annotation Guidelines auf. Berichten Sie Scores für alte und neue Types getrennt, bevor Sie einen Checkpoint ersetzen. So erkennen Sie Forgetting und Taxonomy Drift am einfachsten.

Deployment-Optimierung: von Python zu Inference mit geringerer Latenz

Das begleitende Repo demonstriert den GLiNER-ONNX-Export und INT8-Packaging. Es erfasst Artifact-Größen, reproduziert aber nicht die von externen Projekten berichteten Latenz- oder F1-Werte.

Native GLiNER Serving

Bevor Sie zu einer neuen Runtime wechseln, testen Sie den Ray-Serve-Pfad des Projekts. gliner[serve] bietet Dynamic Batching, Memory-Aware Batch Sizing, Multi-Replica Scaling und einen HTTP-Client. Dadurch kann Queueing-Overhead für einen Multi-User-Service entfallen, während derselbe Model Code erhalten bleibt. Benchmarken Sie Queue Latency, Warm Latency, Throughput und Exact-Span-F1 unter Ihrem Request Mix, bevor Sie den Pfad mit ONNX oder Rust vergleichen.

ONNX-Export

GLiNER bietet native ONNX-Konvertierung; vorab konvertierte Modelle sind auf Hugging Face verfügbar (onnx-community/gliner_small-v2.1). Messen Sie die Latenz gegenüber demselben PyTorch-Checkpoint, derselben Batch Size, Hardware und demselben Warm-up-Protokoll.

INT8 Quantization

Dynamic Quantization kann Storage- und Memory-Anforderungen eines ONNX-Modells reduzieren. Der Effekt auf Latenz und F1 pro Label hängt von Checkpoint und CPU ab. Das Export-Script ist daher ein Packaging-Nachweis, kein Deployment-Benchmark.

Structured Extraction: native Schemas, Instructor und lokale Decoder

Wenn Sie mehr Flexibilität benötigen, als Encoder-Modelle bieten – etwa für implizite Entities, Reasoning oder Ontology Mapping –, beginnen Sie mit dem nativen Schema-Mechanismus des Providers. OpenAI unterstützt strikte json_schema Response Formats, Anthropic Structured Outputs unterstützt JSON Outputs und strikte Tool Inputs, und die Gemini API unterstützt eine Teilmenge von JSON Schema. Ein gemeinsames Pydantic- oder Zod-Model kann den Contract beschreiben; jeder Provider akzeptiert jedoch eine andere Schema-Teilmenge und zeigt anderes Verhalten bei Refusals und komplexen Schemas.

Schema Conformance macht Parsing zuverlässig. Sie beweist nicht, dass ein extrahierter Span im Quelltext existiert oder ein normalisierter Wert korrekt ist. Validieren Sie Feldwerte, bewahren Sie nach Möglichkeit Offsets oder Zitate auf und bewerten Sie die semantische Genauigkeit auf einem gelabelten Set.

Instructor kapselt Provider-Clients mit Pydantic Validation und optionalen Retries nach Validation Failures.

Adaptiert aus dem Instructor-Muster in scripts/05_structured_extraction.py:

import instructor
from pydantic import BaseModel
from typing import List, Literal
from openai import OpenAI

class Entity(BaseModel):
    name: str
    label: Literal["PERSON", "ORGANIZATION", "LOCATION"]

class ExtractEntities(BaseModel):
    entities: List[Entity]

client = instructor.from_openai(OpenAI())
result = client.chat.completions.create(
    model="gpt-5.4-mini", temperature=0.0,
    response_model=ExtractEntities,
    messages=[{"role": "user", "content": "BioNTech SE acquired InstaDeep in the U.K."}])
# entities=[Entity(name='BioNTech SE', label='ORGANIZATION'), ...]

Outlines von dottxt verfolgt einen anderen Ansatz: Constrained Token Generation über Finite-State Machines. Der Decoder maskiert Tokens, die die Zielgrammatik verletzen würden, statt auf einen Validation Failure zu warten und anschließend zu retrien. Eine AWS-Übersicht nennt 98 % Schema Adherence gegenüber 76 % bei Post-Generation Validation. Sie wiederholt separat die Behauptung von .txt Engineering, dass die Generation durch dessen Coalescence-Ansatz bis zu fünfmal schneller sei; die Seite veröffentlicht nicht genug Methodik, um beide Werte als einen kontrollierten Benchmark zu behandeln.

    AutoTokenizer.from_pretrained(model_id),

result = model(
    "Extract entities from: BioNTech SE acquired InstaDeep in the U.K.",
    ExtractEntities,

LangExtract ist nützlich, wenn ein generiertes Feld in der Quelle verankert sein muss: Es liefert Character Intervals und unterstützt gehostete oder lokale LLM Backends. Für Self-Hosted Document Extraction konvertiert NuExtract JSON Schemas in Templates und enthält multimodale Document Models. Behandeln Sie beide als Structured-Extraction-Systeme, nicht als automatische Ersatzlösungen für Span NER. Ihre Anforderungen an Felder, Offsets, Document Layout und Latenz benötigen eigene Tests.

Die Wahl hängt davon ab, wo Sie Ihre Modelle ausführen. Native Schemas sind der reibungsärmste Pfad für einen unterstützten Provider. Instructor ergänzt eine Provider-agnostische Pydantic-Validation- und Retry-Schicht. Outlines beschränkt lokale Generation auf ein Schema. LangExtract priorisiert Source Grounding, während NuExtract auf Self-Hosted Document Extraction zielt. Alle LLM-Pfade enthalten weiterhin autoregressive Generation. Benchmarken Sie jeden Pfad gegen einen Encoder mit identischer Batch Size, Hardware, Entity Schema und Rubrik für semantische Genauigkeit.

Die Drei-Tier-Production-Architektur

Ich würde Production NER anhand der Aufgabenform routen, nicht anhand eines einzigen Model-Rankings.

Tier 1: Encoder-Modelle für explizite Spans. Verwenden Sie einen GLiNER Cross-Encoder für ein kleines Type Inventory. Wenn ein großes Inventory wiederverwendet wird, vergleichen Sie den Bi-Encoder mit gecachten Type Embeddings. Führen Sie Fine-Tuning über die LLM-as-Teacher-Pipeline durch und deployen Sie anschließend mit Native Serving, ONNX, INT8 oder gline-rs – aber nur, wenn dieser Pfad den Domain-Benchmark besteht.

Tier 2: Multi-Task- oder Relation Extraction. Wenn eine Anfrage NER, Classification und hierarchische Felder benötigt, testen Sie GLiNER2s gemeinsames Model mit 205M Parametern. Wenn die zentrale Anforderung gemeinsame Spans plus Relations sind, testen Sie GLiNER-Relex. Das GLiNER2-Paper berichtet für Classification bei den getesteten Label Counts eine CPU-Latency von 130–208 ms; dies ist kein Nachweis für die spätere Relation API oder ein anderes Deployment.

Tier 3: LLMs für Reasoning-intensive Extraction. Routen Sie implizite Entities, kontextuelle Inferenz und Ontology Mapping bei Cloud APIs an eine native Schema API oder Instructor und bei lokalem Constrained Output an Outlines. Verwenden Sie LangExtract, wenn Source Intervals essenziell sind, und NuExtract, wenn das Dokument selbst der Input ist. Loggen Sie diese Fälle, weil sie Kandidaten für das nächste Tier-1-Trainingsset sind.

Die CFM-Fallstudie liefert einen Kostenreferenzwert für Tier 1: 93,4 % F1 bei berichteten $0,10 pro Stunde auf der CPU, verglichen mit 92,7 % F1 und $8 pro Stunde für den Llama-70B-Teacher. Berechnen Sie diesen Vergleich mit Ihrer Hardware, Ihrem Teacher-Model, Ihrem Labelset und Ihren Review-Kosten neu.

Trade-offs und Einschränkungen

Für jeden der folgenden Trade-offs sind zwei Fragen entscheidend: Wo tritt er auf, und können Sie ihn vor dem Deployment messen?

Fehler des LLM-as-Teacher propagieren sich. Wenn das LLM einen bestimmten Entity Type systematisch falsch erkennt, etwa Tochtergesellschaften mit Muttergesellschaften verwechselt, übernimmt der Fine-Tuned Encoder dieses Bias. Die Lösung ist gezieltes Human Review: Konzentrieren Sie den Aufwand auf Entity Types, bei denen die Confidence des LLM niedrig oder inkonsistent ist, statt zufällig zu sampeln.

Ein valides Schema kann falsche Fakten enthalten. Native Structured Output, Instructor und Constrained Decoder können eine Response parsebar machen. Sie können jedoch nicht sicherstellen, dass jedes Feld geerdet ist, dass eine Span-Grenze korrekt verläuft oder dass ein normalisierter Wert dem richtigen Datensatz zugeordnet wird. Bewahren Sie Source Evidence auf und validieren Sie die Semantik separat.

Quantization Losses hängen von Checkpoint und Daten ab. Das begleitende Repo erzeugt ein dynamisch quantisiertes INT8-Artifact, misst dessen F1 aber nicht. Die aktuelle GLiNER-Dokumentation empfiehlt Quantization-Aware Training, wenn die INT8-Genauigkeit erhalten bleiben muss. Vergleichen Sie quantisierte und originale Checkpoints vor dem Deployment anhand von Exact-Span-F1 und Recall pro Label.

Wann die Drei-Tier-Architektur Overkill ist. Eine einzelne Domain mit stabilen Entity Types und ausreichend gelabelten Beispielen benötigt möglicherweise nur eine Fine-Tuned-RoBERTa- oder spaCy-Pipeline. Das Drei-Tier-Muster passt zu mehreren Domains, sich entwickelnden Entity Types oder einem gemessenen Mix aus expliziter und Reasoning-intensiver Extraction. Eine schmale Invoice-Pipeline, die Namen und Daten extrahiert, kann bei Tier 1 bleiben.

Die Qualität des Bi-Encoders variiert je nach Dataset. Gemeinsames Encoding kann auf manchen Datasets helfen, während der Bi-Encoder den CrossNER-Vergleich des Papers gewinnt und der Uni-Encoder auf CoNLL-2003 knapp besser abschneidet. Benchmarken Sie beide auf dem Domain Set. Entscheiden Sie anhand gemessener Exact-Span-Qualität, Calibration, Label Count und Throughput, statt „High Stakes“ als Regel für eine Model-Familie zu verwenden.

PII- und Multilingual-Claims benötigen Slices. Ein hoher aggregierter Score kann gefährliche Recall-Verluste für eine Locale, Namensform, ein Dokumentlayout oder eine seltene PII-Klasse verbergen. Betrachten Sie ein Privacy-Model als eine Defense-in-Depth-Maßnahme, definieren Sie einen Prozess für False Negatives und evaluieren Sie erneut, wenn sich Taxonomy, Sprachenmix oder Datenquelle ändern.

Die wichtigsten Erkenntnisse

  1. Verwenden Sie einen kompakten Encoder für explizite Spans erst, nachdem er ein Domain Test Set mit Support pro Type und Confidence Intervals bestanden hat.
  2. Verwenden Sie GLiNER für wechselnde Label-Vocabularies. Vergleichen Sie zuerst den Bi-Encoder, wenn ein großes Type Inventory wiederverwendet wird; aktivieren Sie flat_ner=False erst nach einer Messung der Qualität verschachtelter Spans.
  3. Verwenden Sie für Hard-Zero-Shot-Claims getestete Type Descriptions und testen Sie bei multilingualen Produkten englische und lokalisierte Label-Formulierungen separat.
  4. Behandeln Sie OCR, NER, Relation Extraction und Entity Linking als getrennte Evaluationsstufen, selbst wenn ein Model mehrere Tasks über ein gemeinsames Interface anbietet.
  5. Betrachten Sie einen LLM-Teacher als System zur Erstellung von Annotation-Vorschlägen. Menschliche Guidelines, Adjudication, unveränderliche Regression Sets und ein Held-Out-Testset bleiben erforderlich.
  6. Verwenden Sie Native Schemas für unterstützte LLM-Provider, validieren Sie aber semantische Korrektheit und Source Grounding getrennt von der JSON-Validität.
  7. Benchmarken Sie Native Serving, ONNX, Quantization und Rust-Pfade separat und gemeinsam. Multiplizieren Sie niemals nicht gemessene Speedups.
