Was ist Named Entity Recognition?

Named Entity Recognition findet Spans in Texten und weist ihnen Types wie Person, Organisation, Datum, Produkt oder domänenspezifische Labels zu. NER identifiziert die Mention. Entity Linking ist der separate Schritt, der eine Mention einem kanonischen Datensatz oder einem Ontology-Konzept zuordnet.

Wo moderne Systeme NER einsetzen

NER findet weiterhin Textspans und weist ihnen Labels zu. Verändert hat sich seine Position im System. NER liefert inzwischen Filter für RAG, strukturierte Argumente für Agent Tools und Felder für Document-Processing-Pipelines. Dadurch werden Latency, Kosten und Schema-Flexibilität ebenso wichtig wie die Accuracy in Benchmarks.

RAG: besseres Retrieval durch Entity Extraction

Alleinige Similarity Search hat Schwierigkeiten, wenn eine Frage exakte Entities enthält. Bei „what did Anthropic say about model safety in Q4 2024?“ sollte das System „Anthropic“ und „Q4 2024“ als Metadata-Filter extrahieren, statt sich ausschließlich auf Embeddings zu verlassen.

Beim Indexing extrahierst du Entities aus jedem Chunk und speicherst sie als Metadata: {"organizations": ["Anthropic"], "dates": ["Q4 2024"], ...}. So kannst du vor der Vector Search nach Entities filtern. Knowledge-Graph-RAG (GraphRAG, LlamaIndex Property Graphs) geht noch weiter: NER plus Relation Extraction erstellt einen Graphen, der Multi-Hop-Fragen beantworten kann, bei denen flache Embeddings nicht ausreichen.

Zur Query-Zeit steuern aus der User-Frage extrahierte Entities das Routing. Eine Frage mit einem Unternehmensnamen geht an einen Finance Index, eine Frage mit Medikamentennamen an eine Clinical Knowledge Base. GLiNER ist nützlich, wenn sich das Schema oder die Entity Types zur Query-Zeit ändern. Unbekannte Unternehmens- oder Medikamentennamen allein erfordern keine Open-Vocabulary-Labels; ein Closed-Label-Model kann neue Mentions bekannter Types weiterhin erkennen.

AI Agents: Text in strukturierte Fakten umwandeln

Agents erhalten unstrukturierten Text wie Webseiten, API-Responses und User-Nachrichten. NER wandelt diesen Text in strukturierte Fakten um, über die der Agent Reasoning ausführen, die er speichern oder an Tools übergeben kann.

Für Tool Routing erfordert eine Anfrage wie „schedule a meeting with Sarah Chen from Accenture on Thursday at 2pm“ vor dem Aufruf der Calendar API PERSON: Sarah Chen, ORGANIZATION: Accenture und DATETIME: Thursday 2pm. Ein lokaler Encoder vermeidet den API Round Trip und ist häufig deutlich schneller. Die Latency hängt jedoch von Model, Runtime, Hardware, Batch Size und Label-Anzahl ab. Miss beide Wege mit dem Calendar Workload, statt von einer festen Differenz in Millisekunden auszugehen.

NER unterstützt außerdem Entity Tracking über mehrere Conversations hinweg. Agent-Memory-Systeme müssen erkennen, dass „Sarah“ in Turn 3 und „Ms. Chen“ in Turn 12 dieselbe Person sind. NER identifiziert die Spans; Entity Linking ordnet sie derselben ID zu.

In beiden Fällen ist die Einschränkung die Latency. Wenn jeder von zehn sequenziellen Schritten einen NER-Call mit 200 ms ausführt, addieren sich diese NER-Calls zu zwei Sekunden wahrgenommener Verzögerung. Ein einzelner Call fügt 200 ms hinzu. Encoder-Modelle passen meist besser in Agent Loops als LLM-basierte Extraktion.

Document Intelligence: von Bildern zu strukturierten Daten

OCR wandelt Bilder in Text um. NER wandelt diesen Text in strukturierte Felder um.

Eine Standard-Pipeline verwendet zunächst OCR, etwa Tesseract, Azure Document Intelligence oder AWS Textract, um Text und Bounding Boxes zu erzeugen. NER extrahiert anschließend Felder wie invoice_number, vendor_name, line_items, total und due_date. Dieselbe Sequenz gilt für Verträge, medizinische Unterlagen und regulatorische Einreichungen.

Moderne Document Pipelines können Layout Understanding, Entity Extraction und Relation Extraction kombinieren. OCR oder ein Layout-Aware-Document-Model liefert weiterhin Text, Reading Order, Tabellen und Bounding Boxes. GLiNER 2 kann anschließend Entity-, Relation-, Classification- und hierarchische Structured Extraction über diesen Text in einem schema-getriebenen Pass kombinieren.

Bei den meisten dieser Pipelines entscheidet der Preis. Kalkuliere deine Kosten anhand des tatsächlichen monatlichen Dokumentvolumens einschließlich Retries und Review. Ein kompakter Encoder kann auf der CPU laufen, während ein API-basiertes LLM pro Dokument zusätzliche Inference-Kosten und Latency verursacht. Ein praxisnaher Test besteht darin, einen repräsentativen Invoice-Datensatz mit einem LLM zu labeln. Fine-Tune GLiNER auf den geprüften Records und vergleiche anschließend beide Wege anhand von Field-Level-F1, Latency und Gesamtkosten.

PII Detection und LLM Guardrails

Die Datenschutzprinzipien und Sicherheitsanforderungen der DSGVO (Artikel 5, 25 und 32), die technologie-neutrale Security Rule von HIPAA (HHS Guidance) sowie der kalifornische CCPA, geändert durch CPRA, schreiben unterschiedliche Rechte und risikobasierte Schutzmaßnahmen vor. Die zitierten Bestimmungen verlangen weder NER noch eine bestimmte Pre-Model-Scanning-Architektur. Dies ist keine Rechtsberatung; lasse die für deine Daten und Jurisdiktion geltenden Anforderungen von einer Rechtsberatung prüfen. NER kann Data Inventory, Minimierung oder De-Identification unterstützen, ist aber nur ein einzelner Control, dessen Recall für die relevanten Daten und die jeweilige Jurisdiktion validiert werden muss.

NER erledigt dies direkt. De-Identification-Modelle finden die Spans PERSON, SSN, PHONE, EMAIL und ADDRESS und schwärzen sie entweder oder ersetzen sie durch synthetische Entsprechungen. In einem von John Snow Labs durchgeführten Vendor-Vergleich mit 48 von Experten annotierten Open-Source-Dokumenten, die sechs PHI-Klassen abdeckten, wurde in der Token-Level-Evaluation ein F1 von 96 % berichtet. Für Azure wurden 91 %, für AWS 83 % und für GPT-4o 79 % berichtet. Die Studie ordnete Provider-Labels dem Ground-Truth-Schema zu und schloss nicht abbildbare Predictions aus. Betrachte sie als engen Provider-Vergleich, nicht als Compliance-Nachweis. Ein separater Deployment-Report beschreibt, wie Providence täglich mehr als 100.000 klinische Notizen verarbeitet.

Für LLM Guardrails funktioniert NER als Pre-Screening-Layer: Scanne User-Input vor dem Senden an eine externe API auf PII und blockiere oder anonymisiere ihn anschließend. Das kann schneller oder einfacher sein, als das LLM zur Selbstmoderation aufzufordern. Behandle dies als Deployment-Hypothese: Miss beide Wege mit deinem Model, deiner Hardware, deinem Input-Mix und deinem Recall-Ziel. False Negatives sind weiterhin möglich. Ergänze daher einen weiteren Control für die PII-Exposure, die dein System nicht akzeptieren kann. GLiNER ist hier besonders nützlich, weil PII-Kategorien je nach Jurisdiktion variieren. Du kannst unter einer neuen Regulierung neue Entity Types wie „genetische Informationen“ hinzufügen, ohne neu zu trainieren.

GLiNER verändert die NER-Ökonomie mit einem Model mit 300M Parametern

GLiNER (NAACL 2024, Zaratiana et al.) machte Encoder-basierte NER im Vergleich zu LLMs bei einem Bruchteil der Kosten konkurrenzfähig. Statt NER als Sequence Labeling oder Text Generation zu behandeln, formuliert GLiNER den Task als Matching-Problem. Das Model bewertet jeden möglichen Textspan – also jede zusammenhängende Wortfolge wie „Bill Gates“ oder „Microsoft“ – gegen jeden Entity-Type-Label und behält die Paare mit hohen Scores.

Das Model erhält Entity-Type-Labels und Input-Text als eine Sequenz: [ENT] person [ENT] organization [ENT] date [SEP] Bill Gates founded Microsoft.... Ein bidirektionaler Transformer (DeBERTa-v3) encodiert alles gemeinsam.

Aus dem Output erstellt das Model zwei Mengen von Representations. Die eine repräsentiert Entity Types aus den Token-Positionen [ENT]. Die andere repräsentiert Textspans, indem Start- und End-Token-Vektoren über ein kleines FFN kombiniert werden. Ein Dot Product zwischen Span-Representation und Entity-Type-Representation liefert einen Score.

Wende Sigmoid an, und du erhältst die Wahrscheinlichkeit, dass der Span von Token iii bis Token jjj zum Entity Type ttt gehört: ϕ(i,j,t)=σ(SijT⋅qt)\phi(i, j, t) = \sigma(S_{ij}^T \cdot q_t)ϕ(i,j,t)=σ(SijT​⋅qt​). Dabei ist SijS_{ij}Sij​ der vom FFN erzeugte Span-Vektor und qtq_tqt​ das Entity-Type-Embedding aus dem entsprechenden [ENT]-Token (Zaratiana et al., 2024, Gleichungen 1–2). Spans sind auf 12 Tokens begrenzt, damit der Prozess schnell bleibt.

GLiNER akzeptiert zur Inference-Zeit natürlichsprachliche Label-Beschreibungen, ohne dass ein Retraining erforderlich ist. Die Extraktionsqualität hängt jedoch von der Formulierung der Labels und ihrer Eignung für die Domäne ab. Du übergibst Entity Types wie „person“, „adverse drug reaction“ oder „financial instrument“, und das Model bewertet Spans gegen diese Labels. Es gibt drei Größen: GLiNER-S (50M Parameter), GLiNER-M (90M) und GLiNER-L (300M). Die Trainingsdaten stammen aus dem Pile-NER-Dataset: 44.889 Passagen mit 240K Entity Spans über 13K Entity Types, sämtlich von ChatGPT gelabelt. Das Training von GLiNER-L dauert auf einer einzelnen A100 etwa fünf Stunden (Zaratiana et al., 2024).

Wie GLiNER im Vergleich zu spaCy abschneidet

spaCy ist eine der etabliertesten NLP Libraries im Production-Einsatz. Die Library arbeitet außerdem unter anderen architektonischen Randbedingungen als GLiNER.

spaCy-Pipelines (en_core_web_sm, en_core_web_trf) führen Closed-Vocabulary-NER durch: eine feste Menge von Entity Types (PERSON, ORG, GPE, DATE usw.), die zum Trainingszeitpunkt definiert wird. Du willst einen neuen Entity Type hinzufügen? Dann musst du gelabelte Daten sammeln und neu trainieren. Der Transformer-basierte en_core_web_trf erreicht 89,8 % F1 auf OntoNotes 5.0, allerdings nur für seine 18 vordefinierten Types.

GLiNER führt Open-Vocabulary-NER durch: Jeder Label funktioniert zur Inference-Zeit, ohne dass ein Retraining erforderlich ist. Das macht GLiNER zur besseren Wahl, wenn Entity Types im Voraus unbekannt sind, sich häufig ändern oder domänenspezifisch sind („adverse drug reaction“, „financial instrument“, „threat indicator“).

Meine Empfehlung: Verwende spaCy für Standard-Entity-Types, für die Pretrained Pipelines gut validiert sind. Verwende GLiNER, wenn du flexible Zero-Shot-Types benötigst oder sich deine Pipeline ohne Retraining anpassen muss. Beide können eine Pipeline gemeinsam nutzen: spaCy übernimmt Tokenization und Sentence Splitting, GLiNER die Entity Extraction.

Eine supervised Transformer-Baseline

Bei stabilen Labels und repräsentativen annotierten Spans solltest du als supervised Baseline mit einem Fine-Tuned Token Classifier wie RoBERTa oder DeBERTa beginnen. Dieser tauscht Labelflexibilität gegen Task-spezifische Accuracy. Vergleiche ihn mit spaCy und GLiNER anhand von Exact-Span-F1, Recall pro Label, Calibration, Latency und Kosten auf derselben Domänenmenge.

UniNER und NuNER: Wie klein kann man werden?

UniNER (ICLR 2024, Zhou et al.) und NuNER (EMNLP 2024, Bogdanov et al.) destillieren beide LLM-Annotationen in kleinere NER-Modelle – sie unterscheiden sich jedoch darin, wie klein diese Modelle werden können.

UniNER: der maximalistische Ansatz

UniNER führt Fine-Tuning von LLaMA-7B/13B auf 45.889 Input-Output-Paaren durch, die von ChatGPT generiert wurden. Für jeden Entity Type beantwortet das Model die Frage „What describes [type] in the text?“ und gibt JSON-Listen aus. Ein zentraler Trainingstrick: Frequency-Based Negative Sampling steigert den F1-Wert von 31,5 % auf 53,4 % (Zhou et al., 2024).

UniNER-7B erreicht 41,7 % Zero-Shot-F1 über 43 Datensätze und übertrifft damit ChatGPT mit 34,9 % um 7 Punkte. Die 13B-Variante erreicht 43,4 %, also nur 1,7 Punkte mehr bei nahezu doppeltem Compute-Aufwand (Zhou et al., 2024).

Der Production Trade-off: Das im Paper besser bewertete UniNER-Setup fragt jeden Entity Type sequenziell ab. Die All-in-One-Variante verwendet eine Response, liegt aber im Mittel 3,3 % niedriger. Bei FP16 benötigt ein 7B-Checkpoint allein für die Weights ungefähr 14 GB; Quantization mit weniger Bits kann diesen Footprint reduzieren. Das Model steht außerdem unter einer restriktiven CC-BY-NC-4.0-Lizenz.

NuNER: der minimalistische Ansatz

NuNER startet mit RoBERTa-base (125M Parameter) und verwendet Contrastive Training mit 4,38 Millionen GPT-3.5-Annotationen über 200K Konzepte. Nach dem Training wird der Concept Encoder verworfen; der Text Encoder kann in jede Standard-NER-Pipeline als RoBERTa-Ersatz eingesetzt werden (Bogdanov et al., 2024).

NuNER übertrifft einfaches RoBERTa über alle Few-Shot-Größen hinweg um 6–15 F1-Punkte. Mit nur einem Dutzend Beispielen pro Entity Type erreicht NuNER das Niveau von UniNER-7B trotz 56-mal weniger Parametern (Bogdanov et al., 2024).

Beide Papers zeigen, dass sich LLM-Annotationen in kleinere NER-Modelle destillieren lassen. NuNER zeigt, dass ein Encoder mit 125M Parametern das berichtete UniNER-7B-Ergebnis erreichen kann, wenn Task-spezifische Fine-Tuning-Daten verfügbar sind – bei MIT-Lizenz und CPU-freundlicher Inference.

GLiNER 2: ein Model, vier Tasks

Das ursprüngliche GLiNER-Ökosystem verteilte NER, Relation Extraction, Classification und Document-Level Extraction auf separate Modelle. Das GLiNER2-Paper von EMNLP 2025 vereinheitlichte NER, Classification und hierarchische Extraction in einem Model mit 205M Parametern; aktuelle Releases haben später Relation Extraction in dieselbe Schema-Schnittstelle aufgenommen.

Die Architektur behält das Cross-Encoder-Design bei, erweitert den Context auf 2.048 Tokens (das Vierfache des Originals) und ergänzt deklarative Schemas zur Definition von Extraction Tasks. Das Training verwendet 135.698 reale Dokumente, die mit GPT-4o annotiert wurden, sowie 118.636 synthetische Beispiele (Zaratiana et al., 2025).

Auf Zero-Shot-CrossNER erreicht GLiNER 2 0,590 F1, nahe an GPT-4o mit 0,599 im Mid-2025-Benchmark des Papers. Für Classification liegt der Durchschnitt über 7 Benchmarks bei 0,72, verglichen mit 0,69 für DeBERTa-v3-large. Auf der CPU berichtet das Paper eine Classification-Latency von 130–208 ms über die getesteten Label-Anzahlen. Die DeBERTa-Baseline steigt von 1.714 ms bei 5 Labels auf 16.897 ms bei 50 Labels (Zaratiana et al., 2025).

from gliner2 import GLiNER2
extractor = GLiNER2.from_pretrained("fastino/gliner2-base-v1")

# Multi-task composition in ONE forward pass
schema = (extractor.create_schema()
    .entities({"person": "Names of people", "company": "Organization names"})
    .classification("sentiment", ["positive", "negative", "neutral"])
    .relations(["works_for", "founded", "located_in"])
    .structure("product_info")
        .field("name", dtype="str")
        .field("price", dtype="str"))
text = "Acme launched a $19 widget in Berlin."
results = extractor.extract(text, schema)

Aktuelle GLiNER2-Releases stellen Entity Recognition, Classification, hierarchische Extraction und Relation Extraction über ein gemeinsames Schema bereit. Das EMNLP-Paper evaluiert NER und Classification; es berichtet keinen Benchmark für hierarchische Extraction und deckt die spätere Relation API nicht ab. Betrachte den Four-Task-Ansatz als Deployment-Fähigkeit, die du benchmarken musst, nicht als Beleg dafür, dass ein einzelnes Model die Accuracy von vier spezialisierten Modellen erhält.

Der Bi-Encoder: NER mit Millionen von Labels skalieren

Der ursprüngliche GLiNER encodiert Labels und Text gemeinsam. Joint Encoding wird zunehmend teurer, wenn Label-Text Context verbraucht und für jedes Dokument erneut encodiert werden muss. Der Crossover hängt von Checkpoint, Label-Beschreibungen und Hardware ab. Der GLiNER Bi-Encoder (Februar 2026, Stepanov et al.; arXiv 2602.18487) adressiert dies, indem Text und Label-Encoding auf zwei separate Transformer aufgeteilt werden.

Der Text Encoder verwendet ModernBERT (Ettin-Familie), der Label Encoder Sentence Transformers (BGE oder MiniLM). Spans und Labels werden per Dot Product gescort. Durch diese Aufteilung können Entity-Type-Embeddings einmalig vorab berechnet und gecacht werden. Bei der Inference muss nur der Text encodiert werden; die Label-Seite wird aus dem Cache gelesen.

Vier Model-Größen sind verfügbar, alle auf CrossNER evaluiert (Stepanov et al., 2026, Tabelle 1):

Bei 1.024 Entity Types verliert der vorab berechnete gliner-bi-edge-v2.0 Bi-Encoder gegenüber einem einzelnen Label nur 5,2 % Throughput (19,3 → 18,3 Ex/s). Der vergleichbare gliner_small-v2.5 Uni-Encoder verliert 98,7 % (10,7 → 0,14 Ex/s). In den Tests des Papers mit einer einzelnen H100, Batch Size 1 sowie Inputs mit 64, 256 und 512 Tokens erreicht der Bi-Encoder mit vorab berechneten Labels einen bis zu 130-fachen Throughput-Vorteil gegenüber gliner_small-v2.5. Mit 100 Entity Types verarbeitet der Bi-Encoder auf einer einzelnen H100 1,96 Millionen Predictions pro Tag, gegenüber 368K beim Cross-Encoder (Stepanov et al., 2026).

Auch die Accuracy bleibt erhalten. Bi-Encoder-Large erreicht 61,5 % CrossNER-F1 und liegt damit knapp vor dem Cross-Encoder mit 60,9 %. Die Autoren empfehlen bi-base-v2.0 (194M) als Sweet Spot: 98 % der Accuracy des Large-Modells bei 2,6-facher Geschwindigkeit (Stepanov et al., 2026).

from gliner import GLiNER

model = GLiNER.from_pretrained("knowledgator/gliner-bi-base-v2.0")

# Pre-compute embeddings for massive label sets — encode once, use forever
entity_types = ["person", "organization", "date"]  # Can be thousands or millions
entity_embeddings = model.encode_labels(entity_types, batch_size=8)

# Inference only encodes text — labels are a cached lookup
outputs = model.batch_predict_with_embeds(texts, entity_embeddings, entity_types)

LLMs als Teacher: eine $70-Fallstudie und eine deploybare Pipeline

Das LLM-as-Teacher-Muster trennt teure Annotation von günstigerer Inference. Zwei veröffentlichte Fallstudien zeigen, wie Teams dieses Muster unter unterschiedlichen Bedingungen eingesetzt haben.

Die CFM-Fallstudie

In einer Hugging-Face-Fallstudie extrahierte Capital Fund Management Unternehmensnamen aus rund 900.000 Financial-News-Headlines. GLiNER erreichte Zero-Shot einen F1 von 87,0 %. Das Team verwendete Llama 3.1-70B, um den Datensatz in rund 8 Stunden für etwa $70 zu annotieren, und prüfte anschließend in weiteren 8 Stunden 2.714 Samples über Argilla.

Fine-Tuning von GLiNER auf diesen Daten erreichte in der Fallstudie 93,4 % F1, verglichen mit 92,7 % beim Llama-70B-Teacher. Die Autoren berichten $0,10 pro Stunde auf der CPU für das Fine-Tuned Model und $8 pro Stunde für den Teacher (CFM-Fallstudie). Diese Zahlen beschreiben einen einzelnen Financial-News-Task und ein bestimmtes Infrastructure-Setup.

Die Refuel-AI-Studie

Der Technical Report von Refuel AI benchmarkt LLM-Labeling über 8 NLP-Datasets, darunter CoNLL-2003. Er berichtet in seinem Setup 88,4 % Übereinstimmung mit der Ground Truth für GPT-4 (März 2023) und 86,2 % für die menschlichen Annotatoren sowie ein 20-mal schnelleres und 7-mal günstigeres Labeling. Das Ensemble routet einfache Beispiele an günstigere Modelle und schwierige Beispiele an GPT-4 und erreicht in den berichteten Experimenten mehr als 95 % Übereinstimmung (Refuel-AI-Technical-Report). Betrachte diese Zahlen als Vendor-Reported-Results unter dem Annotation Protocol dieser Studie.

Eine Production-Pipeline

Ein praktikabler Production-Flow umfasst sechs Schritte:

  1. Verfasse Annotation Guidelines in natürlicher Sprache
  2. Erstelle von Menschen gelabelte Validation- und Held-Out-Test-Sets. Bestimme ihre Größe anhand der Entity-Prävalenz, der Slice-Anforderungen pro Label und der gewünschten Breite des Confidence Intervals. Ein Pilot mit 50–200 Dokumenten kann die Guidelines kalibrieren, ist aber keine Standardgröße für eine Production Evaluation.
  3. Verwende ein LLM (GPT-5.4 Mini, Llama 4 Maverick oder Qwen3.5), um umfangreiche Trainingsdaten zu labeln
  4. Prüfe eine Teilmenge über Argilla oder Label Studio
  5. Fine-Tune einen kompakten Encoder (GLiNER, SpanMarker, RoBERTa)
  6. Deploye nur dann, wenn der Encoder den Quality Gate erfüllt und die gemessenen Gesamtkosten senkt. CFM berichtete in seinem Setup 16–80-mal niedrigere stündliche Infrastructure-Kosten; berücksichtige in deinem Vergleich Annotation, Review, Serving und Retraining.

Das LLM kann den Umfang manueller Annotation reduzieren. Das Team bleibt jedoch für das Validation Set, die Annotation Guidelines, gezieltes Review und Error Analysis verantwortlich.

Wo GLiNER scheitert und LLMs weiterhin nützlich sind

Der Sease-Benchmark (Oktober 2025) testete GLiNER gegen GPT-4.1-mini auf 30 Query-Parsing-Tasks. GPT-4.1-mini erreichte 100 % vollständig korrekte Ergebnisse. GLiNER erreichte 53 % (16 von 30). GLiNER antwortete jedoch in 0,08 Sekunden statt 1,21 Sekunden beim LLM – also 15-mal schneller.

In diesem Benchmark mit 30 Tasks scheiterte GLiNER vor allem in drei wiederkehrenden Mustern:

  1. Implizite Entities: Extraktion von „event“ aus „Elton John performed at Madison Square Garden“ – im Text steht nicht wörtlich „event“, aber das LLM schließt auf „concert“
  2. Sensitivität gegenüber der Label-Formulierung: „2022“ erreicht gegen „date“ einen Score von 0,388, gegen „year“ aber 0,958 – kleine Änderungen am Label verursachen große Score-Schwankungen
  3. Value Mapping: GLiNER gibt den exakten Surface Text („family houses“) statt des kanonischen Werts („Single family house“) zurück. Ein LLM kann diese Normalisierung durchführen, wenn Prompt und Schema die Zielwerte definieren.

Verschachtelte und überlappende Entities

GLiNER verwendet standardmäßig Flat Decoding, wodurch überlappende Spans unterdrückt werden. Seine API unterstützt außerdem flat_ner=False, sodass verschachtelte Predictions möglich sind. Die Qualität hängt jedoch von Checkpoint, Labels und Domänendaten ab. Benchmark beide Decoding-Modi auf einem Span-Level-Testset mit verschachtelten Entities, bevor du ein spezialisiertes Model auswählst.

Verwende GLiNER für explizite Entity Extraction und route Fälle, die Inferenz, Reasoning oder Mapping auf vordefinierte Ontologien erfordern, an ein LLM. Der Routing-Schwellenwert sollte aus einem gelabelten Domänen-Set abgeleitet werden.

NER evaluieren: Metriken, Fallstricke und Testsets

Ein Model kann auf einem kuratierten Testset einen F1 von 95 % erreichen und dennoch bei der Dokumentverteilung scheitern, die es nach dem Deployment sieht. Erstelle das Evaluationsset aus der Production Distribution und behalte Slices für seltene Formate und Entity Types, die der aggregierte F1-Wert verbergen kann.

Die wichtigsten Metriken

  • Entity-Level-F1: Die Standardmetrik. Eine Prediction ist nur dann korrekt, wenn sowohl die Span-Grenzen als auch der Type exakt mit der Ground Truth übereinstimmen. Dies berichten die meisten Papers.
  • Token-Level-F1: Bewertet jeden Token einzeln. Die Ergebnisse werden aufgebläht, weil das korrekte Erkennen des größten Teils einer langen Entity Partial Credit erhält. Bevorzuge Entity-Level-F1.
  • Precision vs. Recall: Die Kosten sind häufig asymmetrisch. Bei De-Identification ist Recall wichtiger – einen Namen zu übersehen ist schlimmer als zu viel zu redigieren. Bei Database Extraction ist Precision wichtiger – False Entries verfälschen nachgelagerte Analysen.

Häufige Evaluationsfehler

  1. Inflation durch Partial Matches: „Bill“ wird extrahiert, obwohl das Gold-Label „Bill Gates“ lautet – manche Scripts zählen dies als Partial Match. Verwende Exact-Span-Matching, sofern kein guter Grund dagegen spricht.
  2. Type Confusion: „Microsoft“ wurde korrekt als Span erkannt, aber statt ORG als PERSON gelabelt; das sollte mit null gewertet werden. Prüfe, ob dein Evaluation Code dies berücksichtigt.
  3. Testset Leakage: Wenn Test-Entities mit Entities aus dem Training überlappen, werden die Scores künstlich erhöht. Zero-Shot-Benchmarks wie CrossNER und Few-NERD testen die Generalisierung.

Ein Domain-Testset erstellen

Für Production Evaluation empfehle ich:

  1. Aus Production Data sampeln, nicht aus kuratierten Beispielen. Nimm die unordentlichen Dokumente auf, die dein Model tatsächlich sehen wird.
  2. Die Größe des Testsets auf die benötigte Schätzung abstimmen. Bestimme die Anzahl anhand von Entity-Prävalenz, Slice-Größen pro Label und der gewünschten Breite des Confidence Intervals. Berichte Bootstrap- oder analytische Confidence Intervals.
  3. Mindestens zwei Annotatoren auf einem Calibration Subset einsetzen. Schlichte Meinungsverschiedenheiten und berichte ein span-basiertes Agreement-Maß. Agreement diagnostiziert Ambiguität und die Qualität der Guidelines; es ist keine Obergrenze für die Model-Performance.
  4. Nach Schwierigkeit stratifizieren – einfache Fälle (sauberer Text, Standard-Types) und schwierige Fälle (ambige Entities, Jargon, verrauschter Text).

Production-NER in vier Branchen

Dies sind ausgewählte Branchenbeispiele mit konkreten Zahlen unter den jeweils berichteten Bedingungen. Die Quellen kombinieren Vendor-Reported-Comparisons, von Unternehmen oder Projekten berichtete Case Studies sowie Peer-Reviewed Papers und Preprints. Betrachte sie als Praxisbeispiele, nicht als Maturity-Ranking.

Healthcare

John Snow Labs bietet Clinical-Entity-Modelle, die auf ICD-10, SNOMED CT, LOINC und RxNorm gemappt sind. In seinem Vendor-Reported-Vergleich mit 48 Dokumenten und sechs Klassen wurde in der Token-Level-Evaluation ein F1 von 96 % berichtet, gegenüber 91 % für Azure, 83 % für AWS und 79 % für GPT-4o. Der Vergleich bildete Labels neu ab und schloss nicht abbildbare Predictions aus. Eine separate, vom Provider berichtete Case Study beschreibt Providence St. Joseph Health mit 100.000–500.000 klinischen Notizen pro Tag.

In seinem 2025 vom Projekt berichteten Review nennt das Open-Source-OpenMed-Projekt mehr als 380 biomedizinische NER-Modelle, 29,7 Millionen Hugging-Face-Downloads und führende Ergebnisse auf 10 von 12 öffentlichen biomedizinischen Benchmarks.

Financial NER

Der wichtigste Use Case ist die Extraktion aus SEC Filings. John Snow Labs Finance NLP extrahiert mehr als 11 Entity Types aus 10-K/10-Q-Filings (Adressen, Ticker, Geschäftsjahre, Börsen). Peer-Reviewed-Varianten von FinBERT-MRC erreichen bei Financial-Entity-Tasks 0,87–0,93 F1. Die schwierigen Aspekte sind lange Dokumente und verschachtelte Entities in komplexen Financial Instruments.

E-Commerce

Peer-Reviewed-Papers berichten, dass WalMarts EAMT-System (KDD 2023) mit 965 Millionen Queries und etwa 60 Entity Labels trainiert wurde und in A/B-Tests einen GMV Lift von 0,51 % erzielte. Home Depots TripleLearn-Framework (AAAI 2021) steigerte NER-F1 durch iteratives Training von 69,5 auf 93,3.

Cybersecurity

Das Peer-Reviewed-iACE-System (CCS 2016) verarbeitete 71.000 Artikel aus 45 Security Blogs und extrahierte 900K OpenIOC-Items mit 95 % Precision und über 90 % Coverage. Ein Project Report zu modernen Systemen wie CyNER beschreibt die Kombination von DeBERTa (F1 >91 %) mit Regex-basierten IOC-Heuristiken. Der CyberNER-Preprint harmonisiert in seinem Unified Dataset von 2025 vier Datasets zu 21 an STIX 2.1 ausgerichteten Entity Types; RoBERTa erreicht dabei 0,736 F1.

Deployment-Optimierung: von Python zu Inference mit geringerer Latency

Das begleitende Repo demonstriert GLiNER-ONNX-Export und INT8-Packaging. Es dokumentiert Artifact-Größen, reproduziert jedoch weder die von externen Projekten berichteten Latency- noch die F1-Werte.

ONNX-Export

GLiNER bietet native ONNX-Konvertierung; vorab konvertierte Modelle existieren auf Hugging Face (onnx-community/gliner_small-v2.1). Miss die Latency gegen denselben PyTorch-Checkpoint, dieselbe Batch Size, Hardware und dasselbe Warm-up-Protokoll.

Aus scripts/02_onnx_export.py:

# Export with quantization
# python convert_to_onnx.py --model_path model/ --save_path onnx/ --quantize True

# Load the exported ONNX model
from gliner import GLiNER
model = GLiNER.from_pretrained("path/to/model", load_onnx_model=True)

entities = model.predict_entities(text, labels, threshold=0.5)

INT8-Quantization

Dynamic Quantization kann Storage- und Memory-Anforderungen eines ONNX-Modells reduzieren. Der Effekt auf Latency und F1 pro Label hängt von Checkpoint und CPU ab. Das Export-Script liefert daher Packaging-Evidence und keinen Deployment-Benchmark.

from onnxruntime.quantization import quantize_dynamic, QuantType

# Quantize weights dynamically, then evaluate the result
quantize_dynamic("gliner.onnx", "gliner_int8.onnx", weight_type=QuantType.QInt8)

gline-rs: Rust-Reimplementation

gline-rs (Apache 2.0) entfernt die Python Runtime aus dem Inference-Pfad. Sein Token-Mode-Benchmark v0.9.0 auf einem Intel i9 mit drei Labels berichtet 6,67 Sequenzen/s gegenüber 1,61 bei Python; das Ergebnis auf einer RTX 4080 beträgt 248,75 Sequenzen/s. Dies sind die eigenen Bedingungen des Projekts und keine vom begleitenden Repo reproduzierten Ergebnisse. Es unterstützt Span- und Token-Modelle, GPU/NPU über ONNX Runtime und wird als Crate auf crates.io ausgeliefert.

use gliner::{GLiNER, TokenMode, Parameters, RuntimeParameters, TextInput};

let model = GLiNER::<TokenMode>::new(
    Parameters::default(), RuntimeParameters::default(),
    "tokenizer.json", "model.onnx")?;

let input = TextInput::from_str(
    &["My name is James Bond."], &["person", "vehicle"])?;
let output = model.inference(input)?;
// => "James Bond" : "person" (99.7%)

Das Paket fast-gliner stellt Python Bindings über PyO3 bereit.

Structured Extraction: Instructor vs. Outlines

Wenn du mehr Flexibilität benötigst, als Encoder-Modelle bieten – etwa für implizite Entities, Reasoning oder Ontology Mapping –, übernehmen zwei Libraries Structured Extraction aus LLMs.

Instructor wrapped Provider Clients mit Pydantic Validation und optionalen Retries nach fehlgeschlagener Validation.

Angelehnt an das Instructor-Muster aus scripts/05_structured_extraction.py:

import instructor
from pydantic import BaseModel
from typing import List, Literal
from openai import OpenAI

class Entity(BaseModel):
    name: str
    label: Literal["PERSON", "ORGANIZATION", "LOCATION"]

class ExtractEntities(BaseModel):
    entities: List[Entity]

client = instructor.from_openai(OpenAI())
result = client.chat.completions.create(
    model="gpt-5.4-mini", temperature=0.0,
    response_model=ExtractEntities,
    messages=[{"role": "user", "content": "BioNTech SE acquired InstaDeep in the U.K."}])
# entities=[Entity(name='BioNTech SE', label='ORGANIZATION'), ...]

Outlines von dottxt verfolgt einen anderen Ansatz: Constrained Token Generation über Finite-State Machines. Der Decoder maskiert Tokens, die die Zielgrammatik verletzen würden, statt auf einen Validation-Fehler zu warten und zu retrien. Eine AWS-Übersicht nennt 98 % Schema Adherence gegenüber 76 % bei Post-Generation Validation. Sie wiederholt separat die Behauptung von .txt Engineering, dass der Coalescence-Ansatz die Generation um bis zu das Fünffache beschleunigt; die Seite veröffentlicht nicht genug Methodik, um beide Werte als einen kontrollierten Benchmark zu behandeln.

import outlines
from transformers import AutoModelForCausalLM, AutoTokenizer

model_id = "microsoft/Phi-3-mini-4k-instruct"
model = outlines.from_transformers(
    AutoModelForCausalLM.from_pretrained(model_id),
    AutoTokenizer.from_pretrained(model_id),
)
result = model(
    "Extract entities from: BioNTech SE acquired InstaDeep in the U.K.",
    ExtractEntities,
)

Die Wahl hängt davon ab, wo du deine Modelle ausführst. Instructor bietet Cloud-LLM-APIs einen vertrauten Pydantic-Validation- und Retry-Pfad. Outlines beschränkt lokale Generation anhand eines Schemas. Beide unterstützen NER-artige Extraktion, aber ihre Latency umfasst weiterhin autoregressive Generation. Benchmarke beide Wege gegen einen Encoder mit derselben Batch Size, Hardware und demselben Entity Schema.

Die dreistufige Production-Architektur

Ich würde Production-NER nach der Form des Tasks routen, nicht nach einem einzigen Model-Ranking.

Tier 1: Encoder-Modelle für explizite Spans. Verwende einen GLiNER Cross-Encoder für kleinere Label-Sets und teste den Bi-Encoder, sobald die Anzahl der Labels steigt. Führe Fine-Tuning über die LLM-as-Teacher-Pipeline durch und deploye anschließend mit ONNX, INT8 oder gline-rs, sofern diese Wege den Domänen-Benchmark bestehen.

Tier 2: GLiNER 2 für Multi-Task-Extraction. Wenn eine Anfrage NER, Classification, Relation Extraction und Structured Data benötigt, teste GLiNER 2 als gemeinsames Model mit 205M Parametern. Das Paper berichtet für Classification eine CPU-Latency von 130–208 ms über die getesteten Label-Anzahlen.

Tier 3: LLMs für reasoning-intensive Extraction. Route implizite Entities, kontextuelle Inferenz und Ontology Mapping über Instructor für Cloud APIs oder Outlines für lokale Modelle an ein LLM. Logge diese Fälle, weil sie Kandidaten für das nächste Tier-1-Trainingsset sind.

Die CFM-Fallstudie liefert eine Kostenreferenz für Tier 1: 93,4 % F1 bei berichteten $0,10 pro Stunde auf der CPU, verglichen mit 92,7 % F1 und $8 pro Stunde für ihren Llama-70B-Teacher. Berechne diesen Vergleich mit deiner Hardware, deinem Teacher-Model, deinem Label-Set und deinen Review-Kosten neu.

Trade-offs und Einschränkungen

Bei jedem der folgenden Trade-offs sind zwei Fragen entscheidend: Wo zeigt er sich, und kannst du ihn vor dem Deployment messen?

Fehler des LLM-as-Teacher propagieren sich. Wenn das LLM einen bestimmten Entity Type systematisch falsch erkennt (z. B. Tochtergesellschaften mit Muttergesellschaften verwechselt), übernimmt der Fine-Tuned Encoder dieses Bias. Die Lösung ist gezieltes Human Review: Konzentriere den Aufwand auf Entity Types, bei denen die Confidence des LLM niedrig oder inkonsistent ist, statt zufällig zu sampeln.

Quantization-Verluste hängen von Checkpoint und Daten ab. Das begleitende Repo erstellt ein dynamisch quantisiertes INT8-Artifact, misst aber dessen F1 nicht. Die aktuelle GLiNER-Guidance empfiehlt Quantization-Aware Training, wenn die Accuracy unter INT8 erhalten bleiben muss. Vergleiche quantisierte und originale Checkpoints vor dem Deployment anhand von Exact-Span-F1 und Recall pro Label.

Wann die dreistufige Architektur Overkill ist. Eine einzelne Domäne mit stabilen Entity Types und ausreichend gelabelten Beispielen benötigt möglicherweise nur eine Fine-Tuned-RoBERTa- oder spaCy-Pipeline. Das dreistufige Muster eignet sich für mehrere Domänen, sich entwickelnde Entity Types oder einen gemessenen Mix aus expliziter und reasoning-intensiver Extraction. Eine schmale Invoice-Pipeline, die Namen und Daten extrahiert, kann bei Tier 1 bleiben.

Die Qualität des Bi-Encoders variiert je nach Dataset. Joint Encoding kann bei manchen Datasets helfen, während der Bi-Encoder den CrossNER-Vergleich des Papers gewinnt und der Uni-Encoder bei CoNLL-2003 knapp vorne liegt. Benchmarke beide auf dem Domänen-Set. Entscheide anhand gemessener Exact-Span-Quality, Calibration, Label-Anzahl und Throughput, statt „High Stakes“ als Regel für eine Model-Familie zu verwenden.

Wichtigste Erkenntnisse

  1. Verwende einen kompakten Encoder für explizite Spans erst, nachdem er ein Domain-Testset mit Support pro Type und Confidence Intervals bestanden hat.
  2. Verwende GLiNER für wechselnde Label-Vokabulare und aktiviere flat_ner=False erst, nachdem du die Qualität verschachtelter Spans gemessen hast.
  3. Behandle OCR, NER, Relation Extraction und Entity Linking als getrennte Evaluationsstufen, auch wenn ein Model mehrere Tasks über eine gemeinsame Schnittstelle bereitstellt.
  4. Betrachte einen LLM-Teacher als System für Annotation Proposals. Menschliche Guidelines, Adjudication und ein Held-Out-Testset bleiben erforderlich.
  5. Benchmarke ONNX-, Quantization- und Rust-Pfade getrennt und gemeinsam. Multipliziere niemals nicht gemessene Speedups.
