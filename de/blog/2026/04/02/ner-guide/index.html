Was ist Named Entity Recognition?

Named Entity Recognition findet Spans in Text und weist ihnen Typen wie Person, Organisation, Datum, Produkt oder domänenspezifische Labels zu. Ein Span ist ein zusammenhängender Teil des Originaltexts. NER identifiziert die Mention; Entity Linking ist der separate Schritt, der sie zu einem kanonischen Record oder Ontology-Konzept auflöst.

Wo moderne Systeme NER einsetzen

NER findet weiterhin Textspans und weist ihnen Labels zu. Verändert hat sich seine Position im System. Heute liefert NER Filter für RAG, strukturierte Argumente für Agent Tools und Felder für Dokumentverarbeitungs-Pipelines. Dadurch werden Latenz, Kosten und Schema-Flexibilität ebenso wichtig wie die Benchmark-Genauigkeit.

RAG: besseres Retrieval durch Entity Extraction

Alleinige Similarity Search hat Schwierigkeiten, wenn eine Frage exakte Entities enthält. Für „what did Anthropic say about model safety in Q4 2024?“ kann Entity Extraction beispielsweise „Anthropic“ und „Q4 2024“ als Filter vorschlagen. Wenden Sie einen Hard Filter nur an, wenn die indizierten Metadaten und die Semantik des Datums dies unterstützen; andernfalls verwenden Sie ihn als Ranking-Signal oder behalten einen ungefilterten Retrieval-Pfad bei. Ein übersehener Alias oder ein falsch abgeleiteter Datumsbereich kann die Antwort ausschließen.

Beim Indexing extrahieren Sie Entities aus jedem Chunk und speichern sie als Metadaten: {"organizations": ["Anthropic"], "dates": ["Q4 2024"], ...}. Dadurch können Sie vor der Vector Search nach Entities filtern. Knowledge Graph RAG (GraphRAG, Property Graphs in LlamaIndex) ergänzt benannte Beziehungen, denen das Retrieval über mehrere Hops folgen kann. Vergleichen Sie diesen Ansatz mit wiederholten Vector Searches auf den Fragen und dem Corpus, die Sie unterstützen müssen.

Zur Query-Zeit steuern aus der Frage des Users extrahierte Entities das Routing. Eine Frage mit einem Firmennamen geht an einen Finance Index; eine Frage mit Medikamentennamen an eine klinische Knowledge Base. GLiNER ist nützlich, wenn sich das Schema oder die Entity-Typen zur Query-Zeit ändern. Unbekannte Firmen- oder Medikamentennamen allein erfordern keine Open-Vocabulary Labels; ein Closed-Label Model kann neue Mentions bekannter Typen weiterhin erkennen.

AI Agents: Text in strukturierte Fakten umwandeln

Agents erhalten unstrukturierten Text, etwa Webseiten, API-Antworten und User-Nachrichten. NER wandelt diesen Text in strukturierte Fakten um, über die der Agent Reasoning durchführen, die er speichern oder an Tools übergeben kann.

Für Tool Routing kann eine Anfrage wie „schedule a meeting with Sarah Chen from Accenture on Thursday at 2pm“ PERSON: Sarah Chen, ORGANIZATION: Accenture, DATE: Thursday und TIME: 2pm liefern. Ein Calendar Resolver kombiniert Datum und Uhrzeit anschließend zu dem von der API benötigten Timestamp. Ein lokaler Encoder vermeidet den API-Roundtrip und ist oft deutlich schneller; die Latenz hängt jedoch von Model, Runtime, Hardware, Batch Size und Label Count ab. Messen Sie beide Pfade auf dem Calendar-Workload, statt von einer festen Differenz in Millisekunden auszugehen.

NER unterstützt außerdem Entity Tracking über mehrere Konversationen hinweg. Agent-Memory-Systeme müssen erkennen, dass „Sarah“ in Turn 3 und „Ms. Chen“ in Turn 12 dieselbe Person sind. NER identifiziert die Spans; Coreference Resolution entscheidet, ob sich die Mentions im Kontext auf dieselbe Person beziehen. Entity Linking ordnet diese Person anschließend einem kanonischen Record zu, sofern einer existiert.

Die Einschränkung ist in beiden Fällen die Latenz. Wenn jeder von zehn sequenziellen Schritten einen 200-ms-NER-Call ausführt, addieren sich diese NER-Calls zu zwei Sekunden wahrgenommener Verzögerung. Ein Call fügt 200 ms hinzu. Encoder-Models integrieren Entity Work in der Regel besser in Agent Loops als LLM-basierte Extraction.

Document Intelligence: von Bildern zu strukturierten Daten

OCR wandelt Bilder in Text um. NER wandelt diesen Text in strukturierte Felder um.

Eine Standard-Pipeline verwendet zunächst OCR, etwa Tesseract, Azure Document Intelligence oder AWS Textract, um Text und Bounding Boxes zu erzeugen. NER findet anschließend Spans für Felder wie invoice_number, vendor_name, total und due_date. Ein Schema- oder Relation-Extraction-Schritt muss Beschreibungen, Mengen und Preise von Einzelpositionen zu line_items gruppieren. Dieselbe Sequenz gilt für Verträge, medizinische Records und regulatorische Einreichungen.

Moderne Dokument-Pipelines können Layout Understanding, Entity Extraction und Relation Extraction kombinieren. OCR oder ein layout-bewusstes Document Model liefert weiterhin Text, Lesereihenfolge, Tabellen und Bounding Boxes. Das aktuelle GLiNER2.5 stellt Entities, Relations, Classification und strukturierte Records über eine Schema-Schnittstelle bereit. Evaluieren Sie jede Ausgabe separat; das ältere GLiNER2-Paper benchmarkte nicht jeden Task, den die Library heute bereitstellt.

Die Kosten entscheiden über die meisten dieser Pipelines. Kalkulieren Sie Ihre Kosten anhand des tatsächlichen monatlichen Dokumentvolumens, einschließlich Retries und Review. Ein kompakter Encoder kann auf der CPU laufen, während ein API-basiertes LLM Kosten und Latenz pro Dokument verursacht. Ein praktischer Test besteht darin, einen repräsentativen Invoice-Datensatz mit einem LLM zu labeln. Fine-Tunen Sie GLiNER auf den geprüften Records und vergleichen Sie anschließend beide Pfade anhand von Field-Level F1, Latenz und Gesamtkosten.

PII Detection und LLM Guardrails

Die Datenschutzprinzipien und Sicherheitsanforderungen der DSGVO (Artikel 5, 25 und 32), die technologieneutrale Security Rule von HIPAA (HHS Guidance) und der kalifornische CCPA in der Fassung des CPRA schreiben unterschiedliche Rechte und risikobasierte Schutzmaßnahmen vor. Die zitierten Bestimmungen verlangen weder NER noch eine bestimmte Pre-Model-Scanning-Architektur. Dies ist keine Rechtsberatung; lassen Sie die für Ihre Daten und Jurisdiktion geltenden Anforderungen von Rechtsberatern prüfen. NER kann Data Inventory, Minimization oder De-Identification unterstützen, ist aber nur ein Control, dessen Recall für die relevanten Daten und die jeweilige Jurisdiktion validiert werden muss.

NER kann dies direkt übernehmen. De-Identification-Models finden Spans wie PERSON, SSN, PHONE, EMAIL und ADDRESS und redigieren sie entweder oder ersetzen sie durch synthetische Entsprechungen. Microsoft Presidio kombiniert Recognizer mit Anonymization Operators; die Beispiele enthalten GLiNER als Recognizer. Das GLiNER2-PII mit 0,3B Parametern ist ein weiterer Kandidat: Sein Paper behandelt 42 PII-Typen auf Character-Span-Auflösung. Keines der beiden Systeme ist ein Compliance-Nachweis. Validieren Sie den Recall nach Datenformat, Jurisdiktion, Sprache und PII-Klasse, bevor Sie einen Detector als Control einsetzen.

Im von John Snow Labs durchgeführten Vendor-Vergleich wurden 48 von Experten annotierte Dokumente mit sechs PHI-Klassen untersucht. Provider-Labels wurden umgemappt und nicht abbildbare Predictions ausgeschlossen, was die Interpretation über Provider hinweg einschränkt. Der Providence-Report beschreibt 281 geleakte PHI-Events bei der Prüfung von 1.000 Notizen mit 34.701 Sätzen. Events sind nicht identisch mit einzelnen betroffenen Sätzen: Erfassen Sie in einer Datenschutz-Evaluation sowohl geleakte Instanzen als auch betroffene Dokumente.

Für LLM Guardrails dient NER als Pre-Screening Layer: Scannen Sie User-Input nach PII, bevor Sie ihn an eine externe API senden, und blockieren oder anonymisieren Sie ihn anschließend. Das kann schneller oder einfacher sein, als das LLM zur Selbstmoderation aufzufordern. Behandeln Sie dies als Deployment-Hypothese: Messen Sie beide Pfade auf Ihrem Model, Ihrer Hardware, Ihrem Input-Mix und Ihrem Recall-Ziel. False Negatives sind weiterhin möglich; ergänzen Sie daher ein weiteres Control für die PII-Exposure, die Ihr System nicht akzeptieren kann. GLiNER ist hier besonders nützlich, weil PII-Kategorien je nach Jurisdiktion variieren. Eine API kann ein neues Label wie „genetic information“ ohne Retraining akzeptieren. Das bestätigt jedoch nicht den Recall für die neue Kategorie; validieren Sie diese anhand geprüfter Beispiele, bevor Sie sich darauf verlassen.

GLiNER: Span-to-Label Matching für Open-Vocabulary NER

GLiNER (NAACL 2024, Zaratiana et al.) machte Encoder-basierte NER zu einem Bruchteil der Kosten konkurrenzfähig mit LLMs. Statt NER als Sequence Labeling oder Text Generation zu behandeln, versteht GLiNER NER als Matching-Problem. Es bewertet jeden möglichen Textspan (jede zusammenhängende Wortsequenz wie „Bill Gates“ oder „Microsoft“) gegen jeden Entity-Type-Label und behält die Paare mit hohen Scores.

Das Model erhält Entity-Type-Labels und Input-Text als eine Sequenz: [ENT] person [ENT] organization [ENT] date [SEP] Bill Gates founded Microsoft.... Ein bidirektionaler Transformer (DeBERTa-v3) kodiert alles gemeinsam.

Aus der Ausgabe erzeugt das Model zwei Repräsentationsmengen. Die erste verfeinert jede Entity-Type-Repräsentation aus einer [ENT]-Tokenposition durch ein kleines Feed-Forward Network (FFN), das den Encoder-Vektor transformiert. Die zweite repräsentiert Textspans, indem sie Start- und End-Word-Vektoren über ein weiteres FFN kombiniert. Ein Dot Product zwischen Span-Repräsentation und Entity-Type-Repräsentation ergibt einen Score.

Wenden Sie Sigmoid an, erhalten Sie die Wahrscheinlichkeit, dass der Span von Wortposition iii bis Wortposition jjj zum Entity-Typ ttt gehört: ϕ(i,j,t)=σ(SijT⋅qt)\phi(i, j, t) = \sigma(S_{ij}^T \cdot q_t)ϕ(i,j,t)=σ(SijT​⋅qt​). Dabei ist SijS_{ij}Sij​ der vom FFN erzeugte Span-Vektor und qtq_tqt​ das vom FFN verfeinerte Entity-Type-Embedding des entsprechenden [ENT]-Tokens (Zaratiana et al., 2024, Gleichungen 1–2). Candidate Spans sind auf 12 Wörter begrenzt; der Tokenizer kann ein Wort in mehrere Subword-Tokens aufteilen.

GLiNER akzeptiert Natural-Language Label Descriptions zur Inference-Zeit ohne Retraining; die Extraction-Qualität hängt jedoch von der Formulierung der Labels und der Domain-Passung ab. Sie übergeben Entity Types wie „person“, „adverse drug reaction“ oder „financial instrument“, und das Model bewertet Spans anhand dieser Labels. Die folgenden 50M-, 90M- und 300M-Konfigurationen sind die Original-Models des Papers. Die Model Card von v2.1 listet dagegen 166M-, 209M- und 459M-englische Checkpoints sowie einen multilingualen 209M-Checkpoint, alle unter Apache 2.0. Vergleichen Sie Latenz oder Speicherbedarf dieser Generationen nicht so, als wären die Parameterbezeichnungen identisch (GLiNER-v2.1-Model-Card).

Für einen echten Hard-Zero-Shot-Test müssen sowohl Zieltypen als auch Zielbeispiele zurückgehalten werden: Das Model hat keine gelabelten Beispiele für den Ziel-Task. Eine Typbeschreibung wie „a medically confirmed adverse effect caused by a treatment“ liefert dem Model mehr Informationen als adverse event allein. Das garantiert keinen Transfer, aber beschreibungsbasiertes ZeroNER übertraf Name-only-Baselines auf seinen Benchmarks mit zurückgehaltenen Typen (Cocchieri et al., 2025).

Die Trainingsdaten des Original-Models stammten aus dem Pile-NER-Dataset: 44.889 Passagen mit 240K Entity Spans über 13K Entity Types, die alle von ChatGPT gelabelt wurden. Das Training von GLiNER-L dauerte auf einer einzelnen A100 etwa fünf Stunden (Zaratiana et al., 2024).

Wie GLiNER im Vergleich zu spaCy abschneidet

spaCy ist eine der etabliertesten NLP-Libraries im Production-Einsatz. Außerdem arbeitet spaCy unter anderen architektonischen Bedingungen als GLiNER.

Die spaCy-Pipelines (en_core_web_sm, en_core_web_trf) führen Closed-Vocabulary NER durch: ein festes Set von Entity Types (PERSON, ORG, GPE, DATE usw.), das zur Trainingszeit definiert wird. Das Erweitern der trainierten ner-Komponente erfordert gelabelte Beispiele und Training. Für IDs oder ein kontrolliertes Wörterbuch kann EntityRuler über Patterns benutzerdefinierte Labels ohne Retraining hinzufügen; testen Sie den Recall außerhalb dieser Patterns. Pinnen Sie das gepflegte 3.8-Model-Package, statt eine unveröffentlichte Major-Version als Production-Upgrade anzunehmen. Die en_core_web_trf-Model-Card 3.8.0 berichtet 90,19 NER F1 auf OntoNotes 5.0, allerdings nur für die 18 vordefinierten Typen (spaCy Model Card).

GLiNER führt Open-Vocabulary NER durch: Es akzeptiert neuen Label-Text zur Inference-Zeit ohne Retraining. Das garantiert keine nützliche Extraction für jedes Label; Formulierung und Domain-Passung bleiben wichtig. GLiNER ist ein starker Kandidat, wenn Entity Types im Voraus unbekannt sind, sich häufig ändern oder domänenspezifisch sind („adverse drug reaction“, „financial instrument“, „threat indicator“).

Meine Empfehlung: Verwenden Sie spaCy für Standard-Entity-Types, wenn die vortrainierten Pipelines gut validiert sind. Verwenden Sie GLiNER für flexible Zero-Shot-Typen oder wenn sich Ihre Pipeline ohne Retraining anpassen muss. Beide können sich eine Pipeline teilen: spaCy übernimmt Tokenization und Sentence Splitting, GLiNER die Entity Extraction.

Eine überwachte Transformer-Baseline

Beginnen Sie bei stabilen Labels mit repräsentativen annotierten Spans mit einem Fine-Tuned Token Classifier wie RoBERTa oder DeBERTa als Supervised Baseline. Dieser tauscht Label-Flexibilität gegen Task-spezifische Genauigkeit. Vergleichen Sie ihn mit spaCy und GLiNER anhand von Exact-Span-F1, Recall pro Label, Calibration, Latenz und Kosten auf demselben Domain-Set.

UniNER und NuNER: Wie klein kann man werden?

UniNER (ICLR 2024, Zhou et al.) und NuNER (EMNLP 2024, Bogdanov et al.) destillieren beide LLM-Annotationen in kleinere NER-Models – sie unterscheiden sich jedoch darin, wie klein diese Models werden können.

UniNER: der maximalistische Ansatz

UniNER fine-tunt LLaMA-7B/13B auf 45.889 Input-Output-Paaren, die von ChatGPT generiert wurden. Für jeden Entity Type beantwortet das Model die Frage „What describes [type] in the text?“ und gibt JSON-Listen aus. Ein wichtiger Trainingstrick: Frequency-Based Negative Sampling erhöht den F1-Score von 31,5 % auf 53,4 % (Zhou et al., 2024).

UniNER-7B erreicht 41,7 % Zero-Shot F1 über 43 Datasets und übertrifft damit ChatGPTs 34,9 % um 7 Punkte. Die 13B-Variante erreicht 43,4 %, also nur 1,7 Punkte mehr bei nahezu doppelt so vielen Parametern (Zhou et al., 2024).

Der Trade-off für Production: Das im Paper höher bewertete UniNER-Type-Setup fragt jeden Entity Type sequenziell ab. Die All-in-One-Variante verwendet eine Antwort, lag aber im Durchschnitt 3,3 % niedriger. Bei FP16 benötigt ein 7B-Checkpoint allein für die Weights ungefähr 14 GB; Quantization mit niedrigeren Bitbreiten kann diesen Footprint reduzieren. Der UniNER-7B-all-Checkpoint ist mit CC BY-NC 4.0 gekennzeichnet; prüfen Sie den exakten Checkpoint, statt dieses Label auf jede Variante zu übertragen.

NuNER: der minimalistische Ansatz

NuNER startet mit RoBERTa-base (125M Parameter) und verwendet Contrastive Training mit 4,38 Millionen GPT-3.5-Annotationen über 200K Konzepte. Nach dem Training wird der Concept Encoder entfernt; der Text Encoder kann in jeder Standard-NER-Pipeline als RoBERTa-Ersatz eingesetzt werden (Bogdanov et al., 2024).

Tabelle 3 von NuNER berichtet mit eingefrorenen Encodern und linearen Heads ungefähr 6,1–16,2 Punkte Vorsprung gegenüber RoBERTa beim Macro-Average Token-Classification-F1 über vier Datasets und verschiedene gesampelte Trainingsgrößen. Das Paper vergleicht außerdem Task-spezifisches Fine-Tuning mit UniNER-7B; die separate Diskussion von mehr als einem Dutzend Beispielen betrifft GPT-4 In-Context Learning, nicht einen Schwellenwert für das Erreichen von UniNER (Bogdanov et al., 2024).

Beide Papers sprechen dafür, aus LLM-Annotationen zu lernen. Sie zeigen nicht, dass ein kleineres Model in einer neuen Domain seinen Teacher übertrifft. Halten Sie ein separat geprüftes Test-Set zurück.

GLiNER2 und GLiNER2.5: Paper und Checkpoint getrennt betrachten

Das ursprüngliche GLiNER-Ökosystem verteilte NER, Relation Extraction, Classification und dokumentweite Extraction auf separate Models. Das GLiNER2-Paper von EMNLP 2025 vereinte NER, Classification und hierarchische Extraction in einem Model mit 205M Parametern; spätere aktuelle Releases ergänzten Relation Extraction über dieselbe Schema-Schnittstelle.

Diese Architektur von 2025 behält das Cross-Encoder-Design bei, erweitert den Context auf 2.048 Tokens (das Vierfache des Originals) und ergänzt deklarative Schemas zur Definition von Extraction Tasks. Das Training verwendet 135.698 reale Dokumente, die mit GPT-4o annotiert wurden, sowie 118.636 synthetische Beispiele (Zaratiana et al., 2025).

Auf dem Zero-Shot-CrossNER erreicht GLiNER 2 0,590 F1, nahe an GPT-4os 0,599 im Mid-2025-Benchmark des Papers. Der Bi-Encoder: NER mit Millionen von Labels skalieren

Byte sagt

Bei tausend Labels kodiert ein Cross-Encoder jedes Label für jedes Dokument erneut. Testen Sie einen Bi-Encoder mit gecachten Label-Embeddings, bevor Sie diese Kosten akzeptieren.

GLiNER kodiert Labels und Text gemeinsam. Diese gemeinsame Kodierung wird zunehmend teurer, wenn Label-Text Context verbraucht und für jedes Dokument erneut kodiert werden muss. Der Crossover hängt von Checkpoint, Label Descriptions und Hardware ab. Wenn dasselbe große Type Inventory für viele Dokumente wiederverwendet wird, sollte der GLiNER Bi-Encoder der Standardvergleich sein. Er teilt Text- und Label-Kodierung auf zwei separate Transformer auf (Stepanov et al., 2026).

Der Text Encoder verwendet ModernBERT (Ettin-Familie), der Label Encoder Sentence Transformers (BGE oder MiniLM). Spans und Labels werden per Dot Product gescort. Dadurch können Entity-Type-Embeddings einmalig vorab berechnet und gecacht werden. Zur Inference vermeiden gecachte Labels die wiederholte Label-Kodierung. Das Scoring von Candidate Spans gegen diese Labels benötigt weiterhin Compute und Speicher; eine Anwendung mit einer Million Labels benötigt außerdem begrenztes Candidate Retrieval oder Batching, wobei der Recall für vor dem Scoring ausgeschlossene Labels gemessen werden muss.

Vier Model-Größen sind verfügbar, alle auf CrossNER benchmarked (Stepanov et al., 2026, Tabelle 1):

LLMs als Teacher: eine $70-Fallstudie und eine deploybare Pipeline

Das LLM-as-Teacher-Muster trennt teure Annotation von günstigerer Inference. Zwei veröffentlichte Fallstudien zeigen, wie Teams diesen Ansatz unter unterschiedlichen Bedingungen eingesetzt haben.

Die CFM-Fallstudie

In einer Hugging-Face-Fallstudie extrahierte Capital Fund Management Firmennamen aus ungefähr 900.000 Financial-News-Headlines. Zero-Shot-GLiNER erzielte 87,0 % F1. Das Team verwendete Llama 3.1-70B, um den Datensatz in etwa 8 Stunden für ungefähr $70 zu annotieren, und prüfte anschließend in weiteren 8 Stunden 2.714 Samples über Argilla.

Fine-Tuning von GLiNER auf diesen Daten erreichte in der Fallstudie 93,4 % F1, verglichen mit 92,7 % beim Llama-70B-Teacher. Die Autoren berichten $0.10 pro Stunde auf der CPU für das Fine-Tuned Model und $8 pro Stunde für den Teacher (CFM-Fallstudie). Diese Werte beschreiben eine Financial-News-Aufgabe und ein bestimmtes Infrastruktur-Setup.

Die Refuel-AI-Studie

Der technische Report von Refuel AI benchmarkt LLM Labeling auf 8 NLP-Datasets, darunter CoNLL-2003. Er berichtet in seinem Setup 88,4 % Übereinstimmung mit Ground Truth für GPT-4 (März 2023) und 86,2 % für menschliche Annotatoren sowie 20-fach schnelleres und siebenfach günstigeres Labeling. Ein separates Ensemble-Experiment mit proprietären Daten übertraf 95 % Übereinstimmung, wobei das beste einzelne LLM 89 % erreichte. Confidence-basiertes Routing zu günstigeren oder stärkeren Models ist eine vorgeschlagene Nutzung, nicht der gemessene Mechanismus hinter dem Ergebnis über acht Datasets (Technischer Report von Refuel AI). Betrachten Sie diese Werte als vom Vendor berichtete Ergebnisse unter dem Annotationsprotokoll der Studie.

Eine Production-Pipeline

Ein praktischer Production Flow umfasst sechs Schritte:

  1. Schreiben Sie Annotation Guidelines in natürlicher Sprache.
  2. Erstellen Sie von Menschen gelabelte Validation- und Holdout-Test-Sets. Dimensionieren Sie sie anhand von Entity-Prävalenz, Anforderungen an Slices pro Label und der gewünschten Breite des Confidence Intervals. Ein Pilotprojekt mit 50–200 Dokumenten kann die Guidelines kalibrieren, ist aber keine standardmäßige Größe für eine Production Evaluation.
  3. Verwenden Sie ein LLM mit versioniertem Prompt und explizitem Output-Schema, um umfangreiche Trainingslabels vorzuschlagen. Bewahren Sie angefordertes und tatsächlich verwendetes Model, Prompt, Quelltext und Fallback-Status auf. Verwerfen Sie unbekannte Typen und Spans, die sich nicht auf die Quelle ausrichten lassen.
  4. Prüfen Sie eine Teilmenge über Argilla oder Label Studio.
  5. Fine-Tunen Sie einen kompakten Encoder (GLiNER, SpanMarker, RoBERTa).
  6. Deployen Sie erst, wenn der Encoder einen Holdout-Check auf Qualität und Gesamtkosten besteht. CFM berichtete in seinem Setup 16–80-fach niedrigere stündliche Infrastrukturkosten; beziehen Sie Annotation, Review, Serving und Retraining in den Vergleich ein.

Das LLM kann den Umfang manueller Annotation reduzieren, aber das Team bleibt für Validation Set, Annotation Guidelines, gezieltes Review und Error Analysis verantwortlich.

Der Teacher- und Training-Input-Workflow des Begleit-Repositories erfordert explizites --allow-paid für Provider-Calls. Er zeichnet angeforderte und tatsächliche Producer-/Model-Identitäten auf, validiert Source-Offsets und belässt Provider-Fehler als Fehler, ohne stillen Fallback. Annotationen starten ungeprüft. Nach dem Human Review prüft der Converter die Spans über GLiNERs tatsächliches SpanDataCollator und schreibt separate Train-, Development- und Test-Inputs. Die Konvertierung führt keine Optimizer Steps aus und erzeugt keinen Fine-Tuned Student.

Wo GLiNER scheitert und LLMs weiterhin nützlich sind

Der Sease-Benchmark (Oktober 2025) testete GLiNER gegen GPT-4.1-mini auf 30 Query-Parsing-Tasks. GPT-4.1-mini war in 100 % der Fälle vollständig korrekt. GLiNER erreichte 53 % (16 von 30). Dafür antwortete GLiNER in 0,08 Sekunden gegenüber 1,21 Sekunden beim LLM – also 15-mal schneller.

In diesem Benchmark mit 30 Tasks scheiterte GLiNER in drei wiederkehrenden Mustern:

  1. Implizite Entities: Extraktion von „event“ aus „Elton John performed at Madison Square Garden“ – im Text steht wörtlich kein „event“, aber das LLM leitet „concert“ ab.
  2. Sensitivität gegenüber der Label-Formulierung: „2022“ erreicht gegen „date“ einen Score von 0,388, gegen „year“ jedoch 0,958 – kleine Labeländerungen verursachen große Score-Schwankungen.
  3. Value Mapping: GLiNER gibt den exakten Surface Text („family houses“) statt des kanonischen Werts („Single family house“) zurück. Ein LLM kann diese Normalisierung durchführen, wenn Prompt und Schema die Zielwerte definieren.

Verschachtelte und überlappende Entities

GLiNER verwendet standardmäßig Flat Decoding, wodurch überlappende Spans unterdrückt werden. Seine API unterstützt auch flat_ner=False; verschachtelte Predictions sind daher möglich, wobei die Qualität von Checkpoint, Labels und Domain-Daten abhängt. Benchmarken Sie beide Decoding-Modi auf einem Span-Level-Test-Set mit verschachtelten Entities, bevor Sie ein spezialisiertes Model auswählen.

Verwenden Sie GLiNER für explizite Entity Extraction und routen Sie Fälle, die Inference, Reasoning oder Mapping auf vordefinierte Ontologies erfordern, an ein LLM. Der Routing-Schwellenwert sollte aus einem gelabelten Domain-Set abgeleitet werden.

Ein Model kann auf einem kuratierten Test-Set 95 % F1 erreichen und nach dem Deployment trotzdem auf dem tatsächlichen Dokument-Mix scheitern. Erstellen Sie das Evaluation Set aus der Production Distribution und behalten Sie Slices für seltene Formate und Entity Types, die der aggregierte F1 verbergen kann.

date und year sind bei Zero-Shot-NER unterschiedliche Model-Inputs. Versionieren Sie Label-Text gemeinsam mit Checkpoint, Threshold und Decoding Mode, die für jeden Score verwendet wurden.

Die zentralen Metriken

Identifizieren Sie jede Occurrence über Document ID, Half-Open Start-/End-Offsets und Type und prüfen Sie, ob text[start:end] die Mention wiederherstellt. Der Exact Evaluator des Begleit-Repositories implementiert Occurrence Matching und behält fehlende, fehlgeschlagene und übersprungene Dokumente im Gold Denominator; unvollständige Abdeckung senkt die Headline-Metriken. Zwei Occurrences von „John“ sind zwei Targets. Validieren Sie Dokumentanzahlen vor dem Matching: Fehlende Predictions müssen False Negatives erzeugen und dürfen nicht über zip() verschwinden. Zählen Sie falsche Typen oder Offsets als eine nicht gematchte Prediction und einen nicht gematchten Gold-Span. Berichten Sie Micro Precision, Recall und F1, Support und Recall pro Type sowie die Definition der Macro-Aggregation und der leeren Fälle.

  • Entity-Level F1: Die Standardmetrik. Eine Prediction ist nur dann korrekt, wenn sowohl die Span-Grenzen als auch der Type exakt mit der Ground Truth übereinstimmen. Dies berichten die meisten Papers.
  • Token-Level F1: Bewertet jedes Token einzeln. Dadurch kann eine teilweise korrekte Boundary besser aussehen als bei Exact-Span-Scoring. Berichten Sie Exact-Span-F1, wenn Boundary Correctness wichtig ist; verwenden Sie Token-Level-Metriken nur, wenn die Downstream-Entscheidung auf Token-Ebene erfolgt.
  • Precision vs. Recall: Die Kosten sind häufig asymmetrisch. Bei De-Identification ist Recall wichtiger – einen Namen zu übersehen ist schlimmer als eine Über-Redaction. Bei Database Extraction ist Precision wichtiger – falsche Einträge verfälschen die nachgelagerte Analyse.

Häufige Evaluationsfehler

  1. Inflation durch Partial Matches: Wenn „Bill“ extrahiert wird, obwohl das Gold-Label „Bill Gates“ lautet, zählen manche Scripts dies als Partial Match. Verwenden Sie Exact-Span-Matching, sofern es keinen Grund dagegen gibt.
  2. Type Confusion: „Microsoft“ wurde zwar korrekt als Span erkannt, aber mit PERSON statt ORG gelabelt und muss daher mit null bewertet werden. Prüfen Sie, ob Ihr Evaluation Code dies berücksichtigt.
  3. Test-Set Leakage: Halten Sie Duplikate und Near-Duplicate-Records, Dokumente und Annotationen aus dem Test-Set heraus. Für einen Hard-Zero-Shot-Anspruch müssen Sie außerdem Ziel-Entity-Types aus dem Training heraushalten; wiederholte Surface Strings allein sind kein Leakage.
  4. Unkontrollierte Label-Prompts: Ein kurzer Type Name und eine getestete Type Description sind unterschiedliche Inputs. Versionieren Sie Label Descriptions, Thresholds, Checkpoint-Revisions und Decoding Mode gemeinsam mit dem Score.
  5. Zero-Shot-Ansprüche auf Basis einer Sprache: Leiten Sie keine multilinguale Qualität aus Englisch ab. OpenNER umfasst 36 Corpora und 52 Sprachen; seine Baselines fanden kein einzelnes Model, das in jeder Sprache am besten war (Palen-Michel et al., 2025). In FiNERweb-Experimenten veränderte der Wechsel von englischen zu Labels in der Zielsprache den F1 je nach Setting um 0,02–0,09 (Golde et al., 2026). Testen Sie beide Label-Sprachen, wenn das Produkt lokale Terminologie verwendet.
  6. Ein Run ist kein Urteil: Berichten Sie, sofern zutreffend, die Variation über Random Seeds, Threshold Sweeps und wiederholte Production Samples. Kleine Slice Counts machen ein Model Ranking instabil.

Halten Sie Normalisierung, Entity Linking, Record Grouping und Relation Endpoints vom Extractive F1 getrennt. Berichten Sie für Privacy geleakte Instanzen, betroffene automatisch akzeptierte Dokumente, False Redactions und den Review-Anteil. Berichten Sie für Serving Completion Rate, p50-/p95-Dokumentlatenz, Cold und Warm Runs, Batch- und Labelgrößen, maximalen Speicherbedarf sowie Kosten pro akzeptiertem Dokument.

Ein Domain-Test-Set erstellen

Für Production Evaluation empfehle ich:

  1. Aus Production-Daten sampeln, nicht aus kuratierten Beispielen. Beziehen Sie die unordentlichen Dokumente ein, die das Model tatsächlich sehen wird.
  2. Das Test-Set für die benötigte Schätzgenauigkeit dimensionieren. Wählen Sie die Anzahl anhand von Entity-Prävalenz, Slice-Größen pro Label und gewünschter Breite des Confidence Intervals. Berichten Sie Bootstrap- oder analytische Confidence Intervals.
  3. Mindestens zwei Annotatoren auf einem Calibration Subset einsetzen. Schlichten Sie Uneinigkeiten und berichten Sie ein span-bewusstes Agreement-Maß. Agreement diagnostiziert Ambiguität und Qualität der Guidelines; es ist keine Obergrenze der Model-Performance.
  4. Nach Schwierigkeit stratifizieren – einfache Fälle (sauberer Text, Standardtypen) und schwierige Fälle (mehrdeutige Entities, Jargon, verrauschter Text).
  5. Privacy- und Fairness-Slices beibehalten. Berichten Sie bei PII den Recall nach PII-Typ, Sprache, Locale, Dokumentformat und relevanten demografischen oder Name-Origin-Slices. Minimieren Sie den Zugriff der Evaluatoren auf rohen sensiblen Text, setzen Sie Aufbewahrungsgrenzen und prüfen Sie False Negatives.

Continual NER benötigt ein unveränderliches Regression Set

Production-Taxonomies ändern sich. Fügen Sie neue Types hinzu, ohne stillschweigend die Bedeutung eines alten Types zu verändern. Bewahren Sie ein versioniertes, unveränderliches Regression Set für bestehende Types, ein separates Test Set für den neuen Type und ein Changelog für Änderungen an den Annotation Guidelines auf. Berichten Sie Scores für alte und neue Types getrennt, bevor Sie einen Checkpoint ersetzen. So erkennen Sie Forgetting und Taxonomy Drift am einfachsten.

Er lädt den gepinnten Checkpoint und die erforderlichen Backbone Files herunter und führt anschließend ein kurzes Extraction-Beispiel aus.

uv sync --locked --all-extras

uv run --all-extras python -m ner_demo.quickstart --download
uv run --all-extras python -m ner_demo.data --split test --limit 32

Verwenden Sie ein neues Output Directory oder --reuse, um bestehende Packages zu prüfen. Jede Span-Abweichung führt nach dem Speichern des Vergleichs zu einem Nonzero Exit Status.

INT8 Quantization

Dynamic Quantization kann den Speicherbedarf eines ONNX-Models reduzieren, aber kleinere Dateien belegen keine nützliche Extraction. Die README des Begleit-Repositories dokumentiert einen lokalen Check mit 32 Dokumenten, bei dem FP32 alle PyTorch-Spans erhielt, während INT8 keine Entities zurückgab und damit Recall 0 erzielte. Dieses berichtete INT8-Artefakt ist nicht für Deployment validiert.

from onnxruntime.quantization import quantize_dynamic, QuantType

# Quantize weights dynamically, then evaluate the result
quantize_dynamic("gliner.onnx", "gliner_int8.onnx", weight_type=QuantType.QInt8)

Das Snippet illustriert nur die Quantization-API. Ein nutzbares Package benötigt außerdem die Graph-, Loading- und Prediction-Checks des Begleit-Repositories. Vergleichen Sie Qualität und Latenz auf dem Ziel-Checkpoint und der Ziel-CPU, bevor Sie eine quantisierte Konfiguration akzeptieren.

gline-rs: Rust-Reimplementation

gline-rs (Apache 2.0) entfernt die Python-Runtime aus dem Inference-Pfad. Sein Token-Mode-Benchmark v0.9.0 auf einem Intel i9 mit drei Labels berichtet 6,67 Sequenzen/s gegenüber 1,61 bei Python auf 100 NuNER-Samples. Ein separates RTX-4080-Experiment v0.9.1 mit 1.000 Samples berichtet 248,75 Sequenzen/s, ohne gematchten Python-GPU-Vergleich. Dies sind die eigenen Bedingungen des Projekts und keine vom Begleit-Repository reproduzierten Ergebnisse. Es unterstützt Span- und Token-Models, GPU/NPU über ONNX Runtime und wird als Crate auf crates.io veröffentlicht.

use gliner::{GLiNER, TokenMode, Parameters, RuntimeParameters, TextInput};

let model = GLiNER::<TokenMode>::new(
    Parameters::default(), RuntimeParameters::default(),
    "tokenizer.json", "model.onnx")?;

let input = TextInput::from_str(
    &["My name is James Bond."], &["person", "vehicle"])?;

// => "James Bond" : "person" (99.7%)

Das fast-gliner-Package stellt Python Bindings über PyO3 bereit.

Structured Extraction: native Schemas, Instructor und lokale Decoders

Wenn Sie mehr Flexibilität benötigen, als Encoder-Models bieten – etwa für implizite Entities, Reasoning oder Ontology Mapping –, beginnen Sie mit dem nativen Schema-Mechanismus des Providers. OpenAI unterstützt strikte json_schema Response Formats, Anthropic Structured Outputs unterstützt JSON Outputs und strikte Tool Inputs, und die Gemini API unterstützt ein Subset von JSON Schema. Ein gemeinsames Pydantic- oder Zod-Model kann den Contract beschreiben, aber jeder Provider akzeptiert ein anderes Schema-Subset und weist ein anderes Verhalten bei Refusals und Komplexität auf.

Schema Conformance macht Parsing zuverlässig. Sie beweist jedoch nicht, dass ein extrahierter Span im Quelltext existiert oder dass ein normalisierter Wert korrekt ist. Validieren Sie Feldwerte, bewahren Sie nach Möglichkeit Offsets oder Zitate auf und bewerten Sie semantische Genauigkeit auf einem gelabelten Set.

Instructor umschließt Provider-Clients mit Pydantic-Validation und optionalen Retries nach Validierungsfehlern.

Dieses eigenständige Beispiel benötigt pip install instructor openai pydantic, ein OPENAI_API_KEY und einen kostenpflichtigen Provider-Request. Es ist vom Teacher-Modul des Begleit-Repositories getrennt. Das ausgewählte Model GPT-5.6 Terra unterstützt Chat Completions, Function Calling, Structured Outputs und none Reasoning Effort. Vergleichen Sie es mit einer günstigeren Baseline, bevor Sie einen High-Volume-Extractor umstellen; eine neue Generation belegt keine bessere NER-Genauigkeit.

import instructor
from pydantic import BaseModel
from typing import List, Literal
from openai import OpenAI

class Entity(BaseModel):
    name: str
    label: Literal["PERSON", "ORGANIZATION", "LOCATION"]

class ExtractEntities(BaseModel):
    entities: List[Entity]

client = instructor.from_openai(OpenAI())
result = client.chat.completions.create(
    model="gpt-5.6-terra", reasoning_effort="none",
    response_model=ExtractEntities,
    messages=[{"role": "user", "content": "BioNTech SE acquired InstaDeep in the U.K."}])
# entities=[Entity(name='BioNTech SE', label='ORGANIZATION'), ...]

Outlines von dottxt verfolgt einen anderen Ansatz: Constrained Token Generation über Finite-State Machines. Der Decoder maskiert Tokens, die die Zielgrammatik verletzen würden, statt auf einen Validierungsfehler zu warten und einen Retry auszuführen. Eine AWS-Übersicht zitiert 98 % Schema Adherence gegenüber 76 % bei Post-Generation-Validation. Separat wiederholt sie die Behauptung von .txt Engineering, dass der Generierungsansatz mit Coalescence bis zu fünfmal schneller sei; die Seite veröffentlicht nicht genügend Methodik, um beide Werte als einen kontrollierten Benchmark zu behandeln.

Das folgende kleine lokale Beispiel behält Phi-3 als historisches Beispiel für Decoder-Integration bei und ist keine Model-Empfehlung für 2026. Für einen neuen Self-Hosted-Extraction-Vergleich sollten Sie aktuelle Qwen3.8-27B- oder die kleineren Qwen3.5-Checkpoints einbeziehen. Verwenden Sie deren dokumentierten Model Loader, Chat Template und Serving Backend; allein das Ersetzen des folgenden Strings belegt keine Kompatibilität mit einer multimodalen Architektur oder deren Reasoning-Format.

import outlines
from transformers import AutoModelForCausalLM, AutoTokenizer
from pydantic import BaseModel
from typing import Literal

class Entity(BaseModel):
    name: str
    label: Literal["PERSON", "ORGANIZATION", "LOCATION"]

class ExtractEntities(BaseModel):
    entities: list[Entity]

model_id = "microsoft/Phi-3-mini-4k-instruct"
model = outlines.from_transformers(
    AutoModelForCausalLM.from_pretrained(model_id),
    AutoTokenizer.from_pretrained(model_id),
)
result = model(
    "Extract entities from: BioNTech SE acquired InstaDeep in the U.K.",
    ExtractEntities,
)

LangExtract ist nützlich, wenn ein generiertes Feld in der Quelle verankert sein muss: Es gibt Character Intervals zurück und unterstützt gehostete oder lokale LLM-Backends. Für Self-Hosted Document Extraction wandelt NuExtract JSON Schemas in Templates um und umfasst multimodale Document Models. Betrachten Sie beide als Structured-Extraction-Systeme, nicht als automatische Ersatzprodukte für Span NER. Ihre Ziele für Fields, Offsets, Dokumentlayout und Latenz benötigen eigene Tests.

Die Wahl hängt davon ab, wo Sie Ihre Models ausführen. Native Schemas sind der reibungsärmste Pfad für einen unterstützten Provider. Instructor ergänzt eine Provider-agnostische Pydantic-Validation- und Retry-Schicht. Outlines constrained lokale Generierung gegen ein Schema. LangExtract priorisiert Source Grounding, während NuExtract auf Self-Hosted Document Extraction zielt. Alle LLM-Pfade umfassen weiterhin autoregressive Generation. Benchmarken Sie jeden Pfad gegenüber einem Encoder bei identischer Batch Size, Hardware, Entity Schema und einem gemeinsamen Rubric für semantische Genauigkeit.

Die Drei-Tier-Production-Architektur

Ich würde Production NER anhand der Aufgabenform routen, nicht anhand eines einzigen Model Rankings.

Tier 1: Encoder-Models für explizite Spans. Verwenden Sie einen GLiNER Cross-Encoder für ein kleines Type Inventory. Wenn ein großes Inventory wiederverwendet wird, vergleichen Sie den Bi-Encoder mit gecachten Type-Embeddings. Fine-Tunen Sie über die LLM-as-Teacher-Pipeline und deployen Sie anschließend über Native Serving, ONNX, INT8 oder gline-rs nur dann, wenn dieser Pfad den Domain-Benchmark besteht.

Tier 2: Multi-Task- oder Relation Extraction. Wenn ein Request NER, Classification und hierarchische Felder benötigt, testen Sie den aktuellen 194M-Parameter-Checkpoint GLiNER2.5 gegen separate Baselines pro Task. Wenn die zentrale Anforderung gemeinsame Spans plus Relations sind, testen Sie GLiNER-Relex. Das GLiNER2-Paper berichtet 130–208 ms CPU Classification-Latenz über die getesteten Label Counts; dies ist kein Beleg für die spätere Relation API oder ein anderes Deployment.

Tier 3: LLMs für Reasoning-intensive Extraction. Routen Sie implizite Entities, kontextuelle Inference und Ontology Mapping für Cloud-APIs an eine native Schema-API oder Instructor und für lokale Constrained Outputs an Outlines. Verwenden Sie LangExtract, wenn Source Intervals essenziell sind, und NuExtract, wenn das Dokument selbst der Input ist. Protokollieren Sie diese Fälle zur Prüfung. Nur explizite, quellenausgerichtete Spans können zu gewöhnlichen Tier-1-Trainingszielen werden; abgeleitete Fakten und normalisierte Werte benötigen eigene Targets und Evaluation.

Die CFM-Fallstudie liefert eine Kostenreferenz für Tier 1: 93,4 % F1 bei berichteten $0.10 pro Stunde auf der CPU, verglichen mit 92,7 % F1 und $8 pro Stunde für ihren Llama-70B-Teacher. Stündliche Instanzpreise bestimmen ohne Throughput nicht die Kosten pro Dokument. Kalkulieren Sie neu mit Ihrer Hardware, Ihrem Teacher Model, Label Set, der Auslastung und Review-Kosten.

Trade-offs und Einschränkungen

Bei jedem der folgenden Trade-offs ist die entscheidende Frage, wo er auftritt und ob Sie ihn vor dem Deployment messen können.

Fehler des LLM-as-Teacher propagieren. Wenn das LLM einen bestimmten Entity Type systematisch falsch erkennt, etwa Tochtergesellschaften mit Muttergesellschaften verwechselt, übernimmt der Fine-Tuned Encoder diese Verzerrung. Prüfen Sie Low-Confidence- oder inkonsistente Types besonders intensiv und behalten Sie eine stratifizierte Zufallsstichprobe, um sichere systematische Fehler zu finden.

Ein gültiges Schema kann falsche Fakten enthalten. Native Structured Output, Instructor und Constrained Decoders können eine Antwort parsebar machen. Sie garantieren nicht, dass jedes Feld Grounded ist, dass eine Span Boundary korrekt ist oder dass ein normalisierter Wert dem richtigen Record zugeordnet wird. Bewahren Sie Quellbelege auf und validieren Sie die Semantik separat.

Quantization-Verluste hängen von Checkpoint und Daten ab. Der aufgezeichnete INT8-Check des Begleit-Repositories gab auf seiner 32-Dokumente-Stichprobe trotz eines ladbaren Packages keine Entities zurück. Die aktuelle GLiNER-Guidance empfiehlt Quantization-Aware Training, wenn die INT8-Genauigkeit erhalten bleiben muss. Vergleichen Sie quantisierte und originale Checkpoints vor dem Deployment anhand von Exact-Span-F1 und Recall pro Label.

Wann die Drei-Tier-Architektur überdimensioniert ist. Eine einzelne Domain mit stabilen Entity Types und genügend gelabelten Beispielen benötigt möglicherweise nur eine Fine-Tuned-RoBERTa- oder spaCy-Pipeline. Das Drei-Tier-Muster passt zu mehreren Domains, sich entwickelnden Entity Types oder einem gemessenen Mix aus expliziter und Reasoning-intensiver Extraction. Eine schmale Invoice-Pipeline, die Namen und Daten extrahiert, kann bei Tier 1 enden.

Die Qualität des Bi-Encoders variiert je nach Dataset. Joint Encoding kann auf manchen Datasets helfen, während der Bi-Encoder den CrossNER-Vergleich des Papers gewinnt und der Uni-Encoder auf CoNLL-2003 knapp besser abschneidet. Benchmarken Sie beide auf dem Domain-Set; wählen Sie anhand gemessener Exact-Span-Qualität, Calibration, Label Count und Throughput statt „High Stakes“ als Regel für eine Model-Familie zu verwenden.

PII- und multilinguale Ansprüche benötigen Slices. Ein hoher aggregierter Score kann einen gefährlichen Recall-Verlust für eine Locale, Namensform, ein Dokumentlayout oder eine seltene PII-Klasse verbergen. Betrachten Sie ein Privacy Model als eine Defense-in-Depth-Maßnahme, definieren Sie einen Prozess für False Negatives und evaluieren Sie erneut, wenn sich Taxonomy, Sprachenmix oder Datenquelle ändern.

Die wichtigsten Erkenntnisse

  1. Verwenden Sie einen kompakten Encoder für explizite Spans erst, nachdem er ein Domain-Test-Set mit Support pro Type und Confidence Intervals bestanden hat.
  2. Verwenden Sie GLiNER für wechselnde Label-Vocabularies. Vergleichen Sie zuerst den Bi-Encoder, wenn ein großes Type Inventory wiederverwendet wird; aktivieren Sie flat_ner=False erst, nachdem Sie die Qualität verschachtelter Spans gemessen haben.
  3. Verwenden Sie für Hard-Zero-Shot-Ansprüche getestete Type Descriptions und testen Sie englische und lokalisierte Label-Formulierungen bei multilingualen Produkten separat.
  4. Behalten Sie OCR, NER, Relation Extraction und Entity Linking als getrennte Evaluationsstufen bei, auch wenn ein Model mehrere Tasks bereitstellt.
  5. Betrachten Sie einen LLM-Teacher als System für Vorschläge zu Trainingsannotationen. Menschliche Guidelines, Adjudication, unveränderliche Regression Sets und ein Holdout-Test-Set bleiben erforderlich.
  6. Verwenden Sie native Schemas für unterstützte LLM-Provider, validieren Sie aber semantische Korrektheit und Source Grounding unabhängig von der JSON-Gültigkeit.
  7. Benchmarken Sie Native Serving, ONNX, Quantization und Rust-Pfade separat und gemeinsam. Multiplizieren Sie niemals nicht gemessene Speedups.
