AI Agent Tool Use: MCP, CLI, Skills und Code Execution

Dieser Artikel richtet sich an Engineers, die Agents mit Tool Use bauen. Er vergleicht JSON Tool Calling, MCP, CLI-Kommandos und Sandbox-Code, damit du den passenden Ausführungsmechanismus für deinen Workload auswählen und ihn mit Skills steuern kannst.

Skills liefern Anweisungen für die Auswahl und Verwendung von Tools. Der Harness ist das gewöhnliche Programm rund um das Model: Er erstellt Prompts, prüft einen vorgeschlagenen Call, führt einen freigegebenen Call aus und entscheidet, wann die Aufgabe abgeschlossen ist.

Dieser dritte Artikel der Serie ergänzt die Action Layer zu den Reasoning Loops aus Teil 1 und der Memory aus Teil 2. Teil 4 untersucht den Policy-Check vor der Ausführung, und Teil 6 den Harness, der sowohl den Call als auch diesen Check ausführt.

Die Tooling-Landschaft hat sich 2025–2026 verändert. MCP, das Model Context Protocol, gab Vendors eine gemeinsame Möglichkeit, externe Services bereitzustellen. Code-executing Agents zeigten, dass ein Model manchmal effizienter ein kleines Programm komponieren kann, als eine lange Sequenz von JSON Calls auszugeben. Anthropic berichtete für einen Google-Drive-to-Salesforce-Workflow eine Token-Reduktion von 98,7 %, und das CodeAct-Paper meldete im gesamten Benchmark-Setup Task-Success-Zuwächse von bis zu 20 Prozentpunkten. Diese Ergebnisse beziehen sich auf die jeweiligen Tasks und Harnesses, nicht auf einen universellen Vorteil von Code Execution.

Ein späterer Abschnitt wendet die Designprinzipien des Agent-Computer Interface (ACI) auf den Market Analyst Agent an, einen kleinen LangGraph Research Agent, den ich für Teil 1 gebaut habe und der Marktdaten abruft und einen Analystenbericht schreibt.

Eine kurze Entscheidungshilfe für Interfaces findest du unter AI Agent Tool Interfaces.

TL;DR

Verwende JSON Tool Calls für kleine typisierte Actions, MCP für gemeinsam genutzte Integrationen, CLI-Kommandos für etablierte lokale Workflows und Sandbox-Code für Multi-Step-Workloads. Skills liefern wiederverwendbare Anweisungen für jede dieser Optionen. Bevor ein Call ausgeführt wird, muss der Harness seine Argumente prüfen und seine Wirkung freigeben; ein Schema oder Transport übernimmt das nicht automatisch. Über alle Oberflächen hinweg sollte das Agent-Computer Interface (ACI) Actions eindeutig, Feedback kompakt und Fehler recoverable machen.

Ausführungsoberflächen und prozedurale Anleitung

Der Reasoning Loop schlägt einen Call vor. Der Harness prüft die Argumente und ob der Call zulässig ist, sendet ihn anschließend an ein Tool oder eine Sandbox und gibt das Ergebnis zurück. JSON Schemas, MCP-Transport, CLI-Wrapper und Code Runner können Eingaben beschränken, entscheiden aber nicht, ob die angeforderte Action zulässig ist. Skills liefern Anweisungen für diesen Ablauf. Diese Ausführungsoberflächen unterscheiden sich bei Token-Kosten, Flexibilität und Durchsetzung.

1. JSON Tool Calling: die Basis

Das ursprüngliche Muster: Du definierst Tool Schemas als JSON, das LLM gibt Structured Function Calls aus und dein Code führt sie aus. Dieses Vorgehen ist gut verstanden und funktioniert für kleine Toolsets problemlos.

# Schema cost depends on its text, structure, and the model tokenizer
tools = [
    {
        "name": "get_stock_price",
        "description": "Get the current stock price for a ticker symbol",
        "input_schema": {
            "type": "object",
            "properties": {
                "ticker": {"type": "string", "description": "Stock ticker (e.g., NVDA)"}
            },
            "required": ["ticker"]
        }
    }
]

Zähle die Tokens in deinen tatsächlichen Schemas. Die Kosten hängen von ihrer Länge und davon ab, wie viele Schemas der Host lädt; ein kompakter Price Lookup und ein tief verschachtelter API Contract sind keine gleich großen Einheiten. Deferred Discovery kann vermeiden, dass die gesamte Registry geladen wird.

2. MCP für gemeinsam genutzte Integrationen

MCP ist der Standard, auf den sich die meisten Vendors geeinigt haben. Ein MCP Server ist ein Prozess, der eine Liste von Tools über ein definiertes Wire Protocol bereitstellt – stdio für einen lokalen Prozess, HTTP für einen Remote-Prozess. Dein Agent führt einen MCP Client aus, verbindet sich, fragt den Server nach seinen Tools und leitet die Calls des Models an ihn weiter. Dadurch funktioniert derselbe Server mit jedem Client, der das Protokoll unterstützt. Anthropic übertrug das Protokoll im Dezember 2025 an die Linux Foundation, unter der Agentic AI Foundation, die das Unternehmen gemeinsam mit OpenAI und Block gegründet hat. Google, Microsoft und AWS unterstützen die Foundation als Platinum Members. OpenAI ergänzte MCP Support in seiner Responses API. Zum Zeitpunkt von Anthropics Ankündigung der Spende im Dezember 2025 zählte das Ökosystem über 10.000 aktive öffentliche MCP Server und über 97 Millionen monatliche SDK Downloads über die Python- und TypeScript-SDKs hinweg.

MCP eignet sich für SaaS-Integrationen über Vendor-Grenzen hinweg (Figma, Notion, Salesforce), für Services ohne CLI-Äquivalent und für Umgebungen, die OAuth Orchestration benötigen. Sein Wert liegt in einer gemeinsamen Discovery- und Transport-Layer. Die Governance hängt weiterhin von Authentication, Authorization, Logging und Deployment Controls des Servers ab.

Die Protocol-Version ist inzwischen eine praktische Migrationsentscheidung. Die Revision vom 28.07.2026 ändert Verhalten, von dem ältere Tutorials ausgehen:

ÄnderungWas du in einer Integration prüfen solltest

Dieselbe Revision stuft Roots, Sampling, Logging und OAuth Dynamic Client Registration als deprecated ein; eine Deprecation bedeutet nicht die sofortige Entfernung. Die aktuelle Client Registration bevorzugt Client ID Metadata Documents. Bestehende Integrationen verwenden möglicherweise weiterhin eine ältere Revision. Prüfe daher das installierte SDK und den Server Contract, bevor du ein neues Feature übernimmst.

Die Produktionsrealität ist komplizierter, als die Schlagzeilenzahlen vermuten lassen.

Das Vulnerable MCP Project sammelt Reports zu Prompt Injection, Input Validation, Authentication und Network Controls. Eine solche Sammlung hilft bei der Identifikation von Testfällen; ohne einen Exposure Denominator kann sie MCP nicht gegen Shell- oder direkte API Calls einordnen.

Tool Poisoning ist die Angriffsklasse, die mir am meisten Sorgen bereitet. Invariant Labs demonstrierte, dass vergiftete MCP Tools Daten exfiltrieren können, selbst wenn sie nie aufgerufen werden. Es genügt, dass das Model die Metadaten des Tools liest. Die MCPTox Benchmarks, die 20 LLM Agents gegen 45 reale MCP Server testeten, meldeten unter ihrem Tool-Poisoning-Setup eine durchschnittliche Attack Success von 72,8 % für o1-mini. Das ist das Benchmark-Ergebnis eines Models, keine Durchschnittsrate über die 20 Agents und keine Rate realer Sicherheitsvorfälle.

Der operative Problempunkt ist der Token Overhead. Ein Team, das MCP Server für GitHub, Slack und Sentry betrieb (insgesamt etwa 40 Tools), fand 55.000 Tokens an Schema-Definitionen, die geladen wurden, bevor ein User überhaupt etwas fragte. Ein anderer Bericht nannte 143.000 von 200.000 verfügbaren Tokens (72 %), die allein durch Tool-Definitionen verbraucht wurden.

Anthropics Bericht zum Tool Search Tool nannte ungefähre Context-Endpunkte von 77.000 Tokens vor Beginn der Arbeit und 8.700 Tokens nach Deferred Discovery; im traditionellen Setup waren etwa 72.000 Tokens für Tool-Definitionen erforderlich. Geladen werden nur die drei bis fünf Tools, die ein Request benötigt, dafür kommt vor dem Invocation ein Discovery-Schritt hinzu. Für kleine, kompakte Toolsets, deren Tools in jeder Session häufig verwendet werden, ist dieser Ansatz weniger nützlich.

3. Skills paketieren Expertise, nicht Execution

Agent Skills sind ein offenes Format zum Paketieren von Anweisungen und unterstützenden Dateien. Tools liefern Capabilities (was Agents tun können), Skills liefern Expertise (was Agents darüber wissen, wie komplexe Tasks erledigt werden).

Das SKILL.md-Format definiert einen Skill als Markdown-Datei mit YAML Frontmatter. Der offene Standard erfordert nur name und description; das folgende Beispiel verwendet außerdem zwei Claude-Code-Extensions, argument-hint und user-invocable, sowie den positional-argument placeholder $0:

---
name: deploy
description: Deploy the application to production
argument-hint: "[environment]"
user-invocable: true
---
Deploy the application to the $0 environment (default: staging).
Steps:
1. Run the test suite
2. Build the production bundle
3. Deploy using the deploy script
4. Verify the deployment health check

Skills verwenden Progressive Disclosure. Beim Startup erhält der Agent etwa 100 Tokens an name und description. Das vollständige SKILL.md wird erst geladen, wenn der Skill benötigt wird; referenzierte Scripts, Dokumente oder Assets werden anschließend bei Bedarf geladen. Diese Startup-Kosten sind deutlich geringer als die ungefähr 55.000 Tokens, die etwa 40 MCP Tools vor Beginn des Reasoning verbrauchen können. Ein aktiver Skill fügt seinem Context weiterhin Instructions und Resources hinzu.

Verwende Skills für Domain Knowledge, Multi-Step-Prozeduren und wiederkehrende Arbeiten wie Database Migrations oder Payment Integrations. Sie eignen sich für Tasks, bei denen der Agent Anweisungen dafür benötigt, wie eine bestehende Capability eingesetzt wird.

4. CLI- und Shell-Tools

CLI Interfaces können im Context deutlich günstiger sein, wenn das Model das Command bereits kennt. Scalekit berichtete über einen Token-Unterschied von 4–32x zwischen seinem CLI- und MCP-Pfad über 75 Runs hinweg. Diese Case Study misst die eigenen Tools und Tasks; sie ersetzt keinen Vergleich mit deinen eigenen Tool-Definitionen und Command-Outputs.

Weit verbreitete, gut dokumentierte Commands wie git, docker, kubectl, gh, curl und jq benötigen oft nur wenig einleitenden Schema-Text. Weniger verbreitete oder interne CLIs brauchen weiterhin discoverable Help, Examples und stabiles maschinenlesbares Output.

Ugo Enyiohas Leitfaden “Writing CLI Tools That AI Agents Actually Want to Use” formulierte acht Designregeln:

  1. Structured Output ist Pflicht – unterstütze --json
  2. Exit Codes sind Control Flow – verwende unterschiedliche Codes für unterschiedliche Fehlertypen
  3. Commands sollten idempotent sein
  4. Self-documenting --help mit realistischen Examples
  5. Für Composability designen – --quiet für reine Werte, stdin-Support
  6. --dry-run- und --yes-Flags bereitstellen
  7. Version Introspection unterstützen
  8. Auth über Environment Variables abwickeln

CLI verfügt über keine Protocol-Level Discovery. JSON Tool Calling kann typisierte Schemas übertragen, während MCP Tool Discovery und für HTTP-Transports ein Authorization Model standardisiert. Keine der beiden Optionen liefert Governance automatisch: Host, Server oder Harness müssen Policy durchsetzen und die für ein Audit erforderlichen Calls protokollieren. Ein praktikabler Default ist CLI für Development und lokale Operations sowie MCP für gemeinsam genutzte externe Services, wenn Cross-Client Discovery oder OAuth Orchestration den Server-Overhead rechtfertigt.

5. Code Execution für Multi-Step-Workloads

Das ist die folgenreichste Veränderung im Agent Tooling. Statt strukturiertes JSON auszugeben, um vordefinierte Functions einzeln aufzurufen, schreibt der Agent ein Python- oder Bash-Script. Das Script ruft mehrere Tools auf, verarbeitet Results mit Loops und Conditionals und gibt nur die abschließende Zusammenfassung an den Model Context zurück.

Anthropic führte Programmatic Tool Calling (PTC) als Beta ein. Der aktuelle API Guide verwendet die reguläre Messages API mit code_execution_20260120 oder höher; der ursprüngliche Beta-Launch ist historischer Kontext. Die akademische Grundlage ist das CodeAct-Paper (Wang et al., ICML 2024), das 17 LLMs testete und feststellte, dass Code Actions in den untersuchten Tasks bis zu 20 Prozentpunkte höhere Task Success und 30 % weniger Actions als JSON-Alternativen erreichten.

Drei First-Party Case Studies zeigen, wo das Muster helfen kann: Vercel und Cloudflare unten sowie anschließend Anthropics Expense-Analysis-Beispiel. Betrachte sie als Vendor-Evidence und führe den Vergleich mit deinen eigenen Tasks erneut durch.

  • Vercel baute d0, seinen Natural-Language-to-SQL Data Agent, neu. Das alte Code-Beispiel nennt 17 Tools, das neue Code-Beispiel stellt ExecuteCommand und ExecuteSQL bereit. Vercel beschreibt das Redesign als Entfernung von 80 % seiner Tools; diese Aussage ist Vercels Schlagzeile und keine Prozentzahl, die sich aus den genannten Tools der Beispiele ableiten lässt. Über fünf repräsentative Queries hinweg berichtet Vercel, dass der Task Success von 4/5 auf 5/5 stieg, die durchschnittliche Execution Time um den Faktor 3,5 sank (274,8 s auf 77,4 s) und der durchschnittliche Token-Verbrauch um 37 % zurückging (~102k auf ~61k). Ihre Formulierung lautet: „The best agents might be the ones with the fewest tools.“

  • Cloudflare entwickelte „Code Mode“, mit dem Agents TypeScript schreiben können, um ihre API aufzurufen, statt Tool Schemas zu definieren. Dadurch sinkt der Context Overhead. Die Begründung lautet: „LLMs have an enormous amount of real-world TypeScript in their training set, but only a small set of contrived examples of tool calls.“

Hier ist das Muster aus Anthropics PTC-Dokumentation. In Anthropics sequenzieller Expense-Analysis-Illustration erfordert traditionelles Tool Calling mehr als 20 separate Inference Passes, wobei Intermediate Data durch den Context fließt. Nach dem Team Lookup kann ein Host, der Parallel Tool Calls unterstützt, die unabhängigen Expense Requests batchen; die Zahl von mehr als 20 macht das nicht unmöglich. Anthropic berichtet, dass generierter Code, der dieselbe Frage beantwortet, den in den Context gelangenden Umfang von 200 KB roher Expense Rows – über 2.000 Line Items – auf 1 KB Results reduziert. Das folgende Script illustriert diesen Control Flow mit eigenen asynchronen Python-Adaptern: Sie akzeptieren positionale Argumente und geben decodierte Listen und Dictionaries zurück. Es handelt sich nicht um den nativen PTC Wrapper Contract.

# Custom decoded Python adapters, not native Claude PTC wrappers.
import asyncio
import json

async def main() -> None:
    team = await get_team_members("engineering")
    levels = list(set(member["level"] for member in team))
    budgets = dict(zip(
        levels,
        await asyncio.gather(*(get_budget_by_level(level) for level in levels)),
    ))
    expenses = await asyncio.gather(
        *(get_expenses(member["id"], "Q3") for member in team)
    )
    over_budget = []
    for member, employee_expenses in zip(team, expenses):
        total = sum(expense["amount"] for expense in employee_expenses)
        limit = budgets[member["level"]]["travel_limit"]
        if total > limit:
            over_budget.append(
                {"name": member["name"], "spent": total, "limit": limit}
            )
    # Only this final summary returns to the LLM context
    print(json.dumps(over_budget))

asyncio.run(main())

Für native Claude PTC Wrappers übergib jedem Tool ein Argument-Dictionary, decodiere den zurückgegebenen JSON-String und verwende im verwalteten Execution Environment das Top-Level-await, statt mit asyncio.run einen Event Loop zu starten. Das Beispiel mit eigenen Adaptern oben setzt eine gewöhnliche Python-Script-Runtime voraus; es ist auch kein direkt einsetzbares Beispiel für einen nativen MCP Connector. Die aktuellen PTC API Constraints schließen strict: true-Tools und native MCP Connector Tools vom Programmatic Calling aus und beschränken rekursive Schemas. Eine eigene Code-to-MCP-Bridge ist eine separate Integration. allowed_callers beschreibt, wie Claude ein Tool aufruft; es ist keine Authorization Boundary. Der Host muss jede zurückgegebene Invocation validieren, einschließlich eines unerwarteten Direct Calls.

Das LLM sieht nur die finale JSON-Zusammenfassung, nicht die tausenden im Sandbox verarbeiteten Expense Line Items. Die Einsparung ist nicht spezifisch für Expense Reports: Anthropics separater Bericht zu Code Execution nennt für einen Google-Drive-to-Salesforce-Workflow die prägnanteste Zahl: Der Umfang sank von etwa 150.000 Tokens auf etwa 2.000 – eine Reduktion von 98,7 %.

Der aktuelle PTC Guide nennt auch ein Gegenbeispiel: Bei den Airline-, Retail- und Telecom-Tasks von tau2-bench blieben die Scores durch PTC unverändert, während die Kosten um etwa 8 % stiegen. In einem separaten Project-Management-Benchmark mit 75 Tools senkte PTC die abgerechneten Input-Tokens um etwa 38 %, ohne die Accuracy zu verändern. Diese internen Evaluations nennen nur ein Production Claude Model, keine exakte ID. Kleine sequenzielle Workflows sparen möglicherweise nicht genug, um Container- und Code-Generation-Overhead auszugleichen.

Token Efficiency ist ein potenzieller Vorteil. Loops und Conditionals kosten praktisch nichts, und Code Execution kann Fehler mit expliziten Handlern behandeln, statt das Model über Failures in natürlicher Sprache Reasoning betreiben zu lassen. Ein Code-Execution-Pfad kann sensible Intermediate Data aus dem Model Context heraushalten; das ist jedoch keine Confidentiality-Garantie: Isolation, Egress Controls, Scoped Credentials und Logging müssen separat durchgesetzt werden.

Wann JSON Tool Calling weiterhin sinnvoll ist: bei einzelnen atomaren Operations, in Umgebungen ohne Sandbox-Infrastruktur, bei kleineren Models mit schwacher Code Generation oder bei Audit-Anforderungen, die jeden einzelnen Tool Invocation protokolliert sehen müssen.

JSON Tool Calling, MCP, CLI und Code Execution sind Ausführungsoberflächen. Skills sind Instructions, die eine dieser Oberflächen steuern; daher hängen Latenz, Context und Setup vom gewählten Mechanismus ab. „Meta-Tools“ bezeichnet die wenigen generischen Entry Points, die ein Code-executing Agent benötigt – beispielsweise Vercels ExecuteCommand und ExecuteSQL – statt eines Schemas für jede Operation. Die Zeilen zu Composability und Latenz beschreiben Calls, deren spätere Argumente von früheren Results abhängen. JSON Tool Calling und MCP können unabhängige Calls gemeinsam ausführen, abhängige Calls benötigen jedoch normalerweise einen weiteren Model Turn. PTC verlagert diesen abhängigen Control Flow und das Filtering in ein Script und gibt anschließend eine Zusammenfassung an das Model zurück. Die Token- und Task-Success-Zellen fassen zitierte Beispiele zusammen, keinen kontrollierten Benchmark über alle fünf Spalten hinweg.

Das Agent-Computer Interface (ACI) für AI-Agent-Tools

Der Begriff „Agent-Computer Interface“ (ACI) wurde von John Yang, Carlos E. Jimenez und Kollegen in Princeton in ihrem SWE-agent-Paper (NeurIPS 2024) geprägt. Die Qualität menschlicher Interfaces verfügt über eine eigene Disziplin – Human-Computer Interaction oder HCI. Das Paper argumentiert, dass Language-Model Agents dieselbe Aufmerksamkeit verdienen: Sie seien „a new category of end users with their own needs and abilities, and would benefit from specially-built interfaces.“

Ihre Ablation Results quantifizieren diesen Effekt. Mit demselben GPT-4-Turbo-Basismodel erreichte die SWE-bench-Lite-Ablation des Papers mit der vollständigen ACI von SWE-agent bei 300 Tasks 18,0 %, gegenüber 7,3 % für die Shell-only-Bedingung ohne Worked Demonstration und 11,0 % mit einer Demonstration. Der Vergleich zeigt, dass Interface- und Demonstrationsbedingungen die Performance in diesem Setup erheblich veränderten; er isoliert Interface Design nicht von allen anderen Unterschieden und zeigt nicht, dass das Model keine Arbeit geleistet hat. Innerhalb derselben Interface-Ablation erhöhte aktiviertes Linting die Edit-Bedingung von 15,0 % auf 18,0 %; über den vollständigen SWE-bench-Testdatensatz hinweg stieß 51,7 % der SWE-agent-Runs mindestens auf ein Edit, das der Linter ablehnte, bevor es weitergegeben werden konnte.

Das Diagramm zeigt die Result Validation, nachdem ein Tool Feedback zurückgegeben hat. Argument Validation ist eine separate Prüfung vor der Tool Execution; ein ungültiges Result wird zur Korrektur an den Agent zurückgegeben, bevor eine weitere Action es verwendet.

Anthropic übernahm ACI als grundlegendes Konzept in seinem “Building Effective Agents” Guide und führte es als eines von drei Kernprinzipien auf: „Carefully craft your agent-computer interface through thorough tool documentation and testing.“ Die praktische Empfehlung lautet: „One rule of thumb is to think about how much effort goes into human-computer interfaces, and plan to invest just as much effort in creating good agent-computer interfaces.“

Vier ACI-Prinzipien in der Praxis

1. Actions sollten einfach und leicht verständlich sein. Der häufigste Fehler besteht darin, API Endpoints eins zu eins zu wrappen. Implementiere statt list_users, list_events und create_event ein schedule_event, das Availability und Scheduling in einem Call ermittelt. Implementiere statt read_logs ein search_logs, das nur die relevanten Zeilen mit Context zurückgibt.

2. Actions sollten kompakt und effizient sein. Konsolidiere wichtige Operations in möglichst wenige Actions. Im Market Analyst Agent kombiniere ich Price Fetching und grundlegende Metrics in einem einzigen get_stock_snapshot-Tool, statt separate Calls für Price, Volume, Market Cap und PE Ratio zu verlangen.

3. Environment Feedback sollte informativ, aber prägnant sein. Vermeide die Rückgabe von rohem HTML oder vollständigen API Payloads. Löse kryptische IDs in semantische Namen auf. Anthropics Tests ergänzten ein response_format Enum, damit der Agent eine kompakte Response (~72 Tokens) oder eine detaillierte Response (~206 Tokens) anfordern kann – ungefähr ein Faktor 3 bei den Token-Kosten.

4. Validation sollte Error Propagation abmildern. Automatische Error Detection hilft Agents, Fehler schnell zu erkennen und zu korrigieren. In SWE-agent lehnt ein Custom File Editor mit integriertem Linting Syntax Errors automatisch ab – der Validation-Schritt hinter der oben genannten Zahl von 51,7 %. Das ist Validation der Inputs und Outputs eines Tools, nicht das Content Filtering rund um einen Model Call, das die Guardrail-Produkte in Teil 4 übernehmen; dasselbe Wort wird für beides verwendet. Im Market Analyst Agent wende ich dasselbe Prinzip an, indem ich Tool Arguments vor der Execution mit Pydantic Schemas validiere:

from pydantic import BaseModel, Field, field_validator

from market_analyst.utils import normalize_ticker

class StockQuery(BaseModel):
    """Validated input for stock queries.

    Pydantic catches malformed tickers before the API call,
    preventing error propagation through the reasoning loop.
    """
    ticker: str = Field(description="Stock ticker symbol (e.g., NVDA)")

    @field_validator("ticker")
    @classmethod
    def validate_ticker(cls, v: str) -> str:
        return normalize_ticker(v)

class StockHistoryQuery(StockQuery):
    """Validated input for price history queries."""

    period: str = Field(default="1mo", description="Time period: 1d, 5d, 1mo, 3mo, 6mo, 1y")

    @field_validator("period")
    @classmethod
    def validate_period(cls, v: str) -> str:
        valid = {"1d", "5d", "1mo", "3mo", "6mo", "1y"}
        if v not in valid:
            raise ValueError(f"Invalid period: {v}. Must be one of {valid}")
        return v

Der gemeinsame Normalizer entfernt Whitespace und wandelt den Wert in Großbuchstaben um. Anschließend akzeptiert er Ticker-Ziffern und punkt- oder hyphengetrennte Suffixe wie BRK.B und BF-B; StockHistoryQuery, nicht StockQuery, besitzt period.

Funktionierende AI-Agent-Tool-Design-Patterns

Anthropics “Writing effective tools for agents” Guide beschreibt Tools als „a new kind of software which reflects a contract between deterministic systems and non-deterministic agents.“

Behandle Tool Descriptions als Prompt Engineering

Descriptions sollten mindestens drei oder vier Sätze umfassen und erklären, wann das Tool zu verwenden ist, welche Parameter erforderlich oder optional sind, welches Output-Format gilt und welche Edge Cases existieren. Anthropic berichtet, dass die Wahl zwischen Prefix- und Suffix-basierter Namespacing-Struktur (asana_search gegenüber search_asana) in den eigenen Tool-Use-Evaluations „non-trivial effects“ hatte. Es wird nicht angegeben, welches Schema gewinnt. Teste daher beide Varianten mit deinem Toolset, statt Präfixe vorauszusetzen. Anthropic gab außerdem die Transcripts seiner Evaluation Agents an Claude Code zurück und ließ die Tools neu schreiben. Auf Held-out-Testsets erzielte dieser Loop weitere Verbesserungen „even beyond what we achieved with ‘expert’ tool implementations“ – unabhängig davon, ob die Tools manuell von den Researchern geschrieben oder von Claude erzeugt wurden.

# Bad: vague, no context for when to use
tools = [{
    "name": "search",
    "description": "Search for items",
}]

# Good: specific, with input examples and edge cases
tools = [{
    "name": "search_news",
    "description": (
        "Search for recent news articles about a specific stock or company. "
        "Use this tool when the user asks about recent events, earnings, "
        "announcements, or market-moving news for a specific ticker. "
        "Returns up to 10 articles sorted by relevance. "
        "For company competitors rather than news, use search_competitors instead."
    ),
    "input_schema": {
        "type": "object",
        "properties": {
            "query": {
                "type": "string",
                "description": "Search query. Examples: 'NVDA earnings Q3 2025', 'Tesla delivery numbers'"
            },
            "max_results": {
                "type": "integer",
                "description": "Max articles to return (1-10, default 5)",
                "default": 5
            }
        },
        "required": ["query"]
    }
}]

Anthropics interne Tests zeigten, dass ein zusätzliches input_examples-Feld die Accuracy bei komplexer Parameterverarbeitung von 72 % auf 90 % erhöhte.

Gib High-Signal-, maschinenlesbares Output zurück

Verwende im Default Response semantische Labels statt Low-Level-Identifier (uuid, mime_type). Behalte eine ID, wenn ein späteres Tool sie benötigt, oder biete eine detaillierte Response an, die sie enthält. Ein Search Result für Jane kann beispielsweise kompakt lesbar sein, während ein detailliertes Result die ID enthält, die send_message benötigt. Strukturiere die Response so, dass der Agent darüber Reasoning betreiben kann, ohne Boilerplate parsen zu müssen:

# Bad: raw API response dumped to agent
def get_stock_snapshot(ticker: str) -> dict:
    response = api.get(f"/v1/quotes/{ticker}")
    return response.json()  # 500+ tokens of nested JSON

# Good: high-signal summary the agent can immediately reason about
def get_stock_snapshot(ticker: str) -> dict:
    data = api.get(f"/v1/quotes/{ticker}").json()
    return {
        "ticker": ticker,
        "price": data["regularMarketPrice"],
        "change_pct": round(data["regularMarketChangePercent"], 2),
        "volume": data["regularMarketVolume"],
        "market_cap_b": round(data["marketCap"] / 1e9, 1),
        "pe_ratio": data.get("trailingPE"),
        "summary": f"{ticker} at ${data['regularMarketPrice']:.2f} "
                   f"({'up' if data['regularMarketChangePercent'] > 0 else 'down'} "
                   f"{abs(data['regularMarketChangePercent']):.1f}%)"
    }

Gib Errors zurück, mit denen der Loop arbeiten kann

Error Handling benötigt vier separate Mechanismen, weil sie unterschiedliche Failure Classes behandeln:

  1. Retry mit Exponential Backoff für transiente Fehler
  2. Model Fallback Chains bei Provider-Ausfällen
  3. Error-Classification Routing – transiente Fehler werden wiederholt, LLM-recoverable Errors mit Context an den Agent zurückgegeben, Human-required Errors eskaliert
  4. Checkpoint Recovery für das Überleben von Crashes

Anthropics “Writing effective tools for agents” Guide empfiehlt klare Tool Errors und Evaluation-driven Tool Design, nennt jedoch keine universelle Zahl dafür, wie viel diese vier Mechanismen wiederherstellen. Messe Recovery Rate, Retries und Escalation in deiner eigenen Task Suite.

import httpx
from tenacity import retry, retry_if_exception, stop_after_attempt, wait_exponential

def is_transient_error(error: BaseException) -> bool:
    if isinstance(error, (httpx.TimeoutException, httpx.NetworkError)):
        return True
    if isinstance(error, httpx.HTTPStatusError):
        return error.response.status_code == 429 or 500 <= error.response.status_code < 600
    return False

@retry(
    retry=retry_if_exception(is_transient_error),
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=1, min=2, max=10),
    reraise=True,
)
def call_stock_api(ticker: str) -> dict:
    """Fetch stock data with automatic retry on transient failures.

    Mechanism 1 of the four above: exponential backoff for rate limits
    and network blips.
    This only retries transient transport failures. If attempts are exhausted,
    Tenacity re-raises the original httpx exception.
    """
    response = httpx.get(
        f"https://api.example.com/v1/quotes/{ticker}",
        timeout=10.0,
    )
    response.raise_for_status()
    return response.json()

Der Caller oder Harness benötigt weiterhin den nächsten Schritt: Er muss diese Exception in ein stabiles Result umwandeln, das angibt, welche Operation fehlgeschlagen ist, ob ein Retry erfolgen soll und was als Nächstes zu tun ist. Ein nicht wiederholbarer 4xx überspringt diesen Decorator und benötigt dieselbe Behandlung. Das Wiederholen eines Requests klassifiziert seinen Fehler nicht und stellt keinen Checkpoint wieder her.

Anwendung der Patterns auf den Market Analyst Agent

Byte sagt

Ich stelle Price, Volume, Market Cap und P/E Ratio über ein einziges get_stock_snapshot-Tool bereit.

Tool Consolidation

Die ursprünglichen Tool-Module definierten get_stock_price, get_company_metrics, get_price_history, zwei Search Tools und execute_trade. Für eine grundlegende Analyse musste der Agent sowohl den Price- als auch den Metrics-Call auswählen; Market Cap und P/E waren Felder von get_company_metrics und keine eigenständigen Tools. Der Source vor der Konsolidierung zeigt diese frühere Oberfläche.

Ich habe die Market-Data-Oberfläche gemäß dem ACI-Prinzip kompakter, effizienter Actions in fünf High-Level-Tools umgeformt. Die ReAct-Tool-Liste des Repositories enthält daneben vier weitere Tools – einen Skill Loader, zwei CLI-Wrapper und einen eingeschränkten In-Process-Python-Evaluator (eine AST-Allowlist, keine Sandbox; Teil 4 behandelt dies) – und deckt damit drei der fünf oben genannten Modalitäten ab. MCP erscheint als Sidecar und nicht als Tool in dieser Liste:

Vorher (ursprüngliche Tools)Nachher (Market-Data-Tools)Warum
get_stock_price + get_company_metricsget_stock_snapshotEin Call liefert den grundlegenden Price- und Valuation-Snapshot
get_price_historyget_price_historyMit validierten Periods und Average-Volume-Summary beibehalten
search_newssearch_newsGibt strukturierte Items mit extrahierten Key Points zurück
search_competitorssearch_competitorsBehält die Competitor-focused Search Action bei
Kein Financial-Statement-Toolget_financialsWählt Income-, Balance-Sheet- oder Cash-Flow-Daten per Parameter

Dadurch werden Price und Valuation in einer Task-shaped Definition zusammengeführt und Financial Statements als explizite Action ergänzt. Ob dies die Tool Selection verbessert, muss anhand repräsentativer Requests und Traces getestet werden.

Structured Outputs für Tool Results

Die Stock- und News-Tools geben Pydantic-validierte Responses zurück. Die CLI- und Code-Execution-Wrapper geben str zurück. Daher beschreiben die folgenden Models die Structured Tool Results und nicht jeden Wrapper im Repository:

from pydantic import BaseModel

class StockSnapshot(BaseModel):
    """Structured tool response — the agent never sees raw API noise."""
    ticker: str
    price: float
    change_pct: float
    volume: int
    market_cap_b: float
    pe_ratio: float | None
    summary: str  # Human-readable one-liner for direct use in reports

class NewsItem(BaseModel):
    """One news item pre-processed for agent consumption."""
    headline: str
    source: str
    date: str
    relevance_score: float  # Pre-ranked so the agent doesn't waste tokens sorting
    key_points: list[str]  # Extracted by the tool, not the agent

class NewsSearchResult(BaseModel):
    query: str
    results: list[NewsItem]
    summary: str

Das Feld summary liefert dem Agent einen direkt verwendbaren String für einen Report. NewsItem.key_points bewahren das Model davor, Article Bodies zu parsen. Wenn eine spätere Action eine ID benötigt, behalte sie in der detaillierten Response oder biete concise und detailed Modes an; entferne sie nicht überall.

Trade-offs und Überlegungen

Neben den spezifischen Einschränkungen der oben beschriebenen Patterns prägen einige übergreifende Aspekte die Auswahl:

  • Die Operational Costs unterscheiden sich je nach Dimension. Code Execution kann Model-Context-Tokens sparen, indem Intermediate Results gefiltert werden; Code Generation und Container-Overhead können diese Einsparungen jedoch übersteigen und zusätzliche Latenz verursachen. MCP spart Development-Zeit bei SaaS-Integrationen, bringt aber Server-Deployment-Overhead mit sich. CLI ist zunächst kostenlos, lässt sich aber in großem Maßstab schwerer steuern. Optimiere für deinen tatsächlichen Bottleneck – Token-Kosten, Latenz oder operative Komplexität.

  • Team Skills sind relevant. Code Execution setzt voraus, dass deine Agents und die zugrunde liegenden Models zuverlässiges Python oder TypeScript generieren können. CLI setzt Vertrautheit mit Unix-Konventionen voraus. MCP erfordert Verständnis von Transport Protocols und OAuth Flows. Passe die Modalität an die Stärken deines Teams an.

  • Tool Consolidation kann zu weit gehen. Wenn ein Tool nicht zusammenhängende Modes und Arguments ansammelt, entsteht innerhalb des Schemas ein anderes Selection Problem. Verwende Tool-Selection- und Task-Success-Evaluations, um die passende Oberfläche für deinen Workload zu finden.

  • Skills sind promptbasiert und nicht enforced. Ein Skill enthält Instructions, die der Agent befolgen sollte, nicht Guardrails, die er befolgen muss. Ein Skill-Bundle kann beliebige Files und executable Scripts enthalten. Vertraue daher auf die Quelle, prüfe das Bundle und lasse den Host die Permissions für jede Resource durchsetzen, die der Agent lesen, ändern oder ausführen kann. Kombiniere Skills bei kritischen Workflows mit deterministischer Validation.

  • Audit Requirements beeinflussen die Auswahl. Strukturierte MCP- und JSON-Calls sind praktische Events für Logging, aber keines der beiden Protokolle erzeugt automatisch einen vollständigen Audit Trail. Host, Server oder Harness müssen Invocations und Results protokollieren und anschließend Authorization, Policy, Retention und Review durchsetzen. Code Execution benötigt dieselbe Instrumentierung rund um die Sandbox; Script und Output allein sind kein Compliance Record.

Drei Richtungen für AI-Agent-Tooling im großen Maßstab

Die erste ist Tool RAG zur Skalierung. Bevor das Model ein Tool auswählt, werden die wenigen Tool Descriptions abgerufen, die zum Request passen. Das Model wählt dann aus dieser Teilmenge statt aus der vollständigen Registry. In den Benchmark-Tasks und dem MCP Stress Test von RAG-MCP lag die Baseline-Accuracy bei der Tool Selection bei 13,62 %; durch Retrieval stieg sie auf 43,13 %, eine Verbesserung um den Faktor 3,2, während die Prompt Tokens von 2.133,84 auf 1.084 sanken (etwa 49,2 %). Im Abstract des Papers steht „over 50%“, und die Beschreibungen von Generator und Evaluator unterscheiden sich zwischen den Abschnitten; diese Inkonsistenzen begrenzen die Interpretation. Das Ergebnis ist Evidenz für dieses Evaluations-Setup, keine universelle Rate für naive Selection bei wachsenden Toolsets.

Die zweite Richtung sind Agents, die ihre eigenen Tools erzeugen. Das LATM-Framework („LLMs As Tool Makers“) etablierte ein Zwei-Phasen-Paradigma, in dem ein leistungsfähiges LLM wiederverwendbare Python Functions erstellt und ein leichtgewichtiges LLM sie verwendet. Im ToolMaker-Benchmark mit 15 Tasks zu Papers mit öffentlichen Code-Repositories, die als GitHub URLs und kurze Task Descriptions bereitgestellt wurden, implementierte es 12 von 15 Tasks korrekt; der Benchmark umfasst insgesamt mehr als 100 Tests. Dieser kleine Repository-Task-Benchmark belegt keine Production Reliability. Beide Ansätze weisen über Tool Use hinaus in Richtung Tool Creation und anschließend zum Management einer Library generierter Tools.

Die dritte Richtung ist der Dual-Protocol-Stack aus A2A + MCP. Google übertrug A2A im Juni 2025 an die Linux Foundation. Die A2A Protocol Documentation trennt die Zuständigkeiten: MCP verbindet einen Agent mit Tools und Resources, während A2A es unabhängigen Agents ermöglicht, einander zu entdecken, Interaktionen auszuhandeln, gemeinsame Tasks zu verwalten und Arbeit zu delegieren.

Vergleiche Interfaces anhand identischer Tasks und erlaubter Operations. Erfasse Discovery Tokens, gecachte und nicht gecachte Inputs, Execution Output, Retries, Latenz und Final-State Success. Teste neben Token-Einsparungen auch verfehlte Discovery; zähle bei generierten Programmen Syntax Errors, Runtime Errors und Partial Completion.

Wichtigste Erkenntnisse

  1. Wähle die Execution Surface anhand der Action: JSON Calls für kleine typisierte Operations, MCP für Shared Services, CLI für etablierte Commands und Sandbox-Code für lokale Composition. Verwende Skills, um zu dokumentieren, wie diese Oberfläche ausgewählt und genutzt wird.
  2. Ordne die Benchmark-Bedingungen dem Ergebnis zu. CodeAct, Anthropic, Vercel, Cloudflare, Apideck und Scalekit haben unterschiedliche Models, Tasks, Tools und Harnesses gemessen.
  3. ACI-Qualität bleibt auch bei Protocol Changes relevant. Klare Actions, kompaktes Feedback, Validation und hilfreiche Errors unterstützen jede Modalität.
  4. Konsolidiere überlappende Tools nur dann, wenn Evaluations zeigen, dass die kleinere Oberfläche Selection oder Task Success verbessert.
  5. Mit größerer Execution Power verschiebt sich auch die Security. Shell- und Code-Interfaces benötigen Sandboxing; MCP braucht Scoped Identity und Server Policy; Skills bleiben Instructions und sind keine Enforcement-Mechanismen.

Die nächste Layer ist Policy

Teil 4, AI Agent Security, behandelt den Harness-Check zwischen einem vorgeschlagenen Tool Call und der Execution. Teil 5 setzt Tool und Sandbox in einen recoverable Runtime. Teil 6 ergänzt einen Contract, den das Model nicht sieht: eine Effect Category, eine Retry Rule und ein Structured Result, das ein Acceptance Check ohne Parsing von Prose auswerten kann.
