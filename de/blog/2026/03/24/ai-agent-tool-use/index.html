Tool Use für AI Agents: MCP, CLI, Skills und Code Execution

Viacheslav Dubrov

2026-03-24 · Aktualisiert 2026-08-01 · 20 Min. · KI-Agenten

Automatische Übersetzung Dieser Artikel wurde automatisch aus der englischen Originalversion übersetzt.

Teil 1 behandelte Reasoning Loops, Teil 2 die Memory. Dieser Artikel ergänzt die Action Layer: wie ein Agent Tools bereitstellt, auswählt und ausführt. Die Memory entscheidet, was der Agent zu Beginn eines Turns weiß; diese Layer entscheidet, was er damit tun kann. Teil 4 behandelt die Prüfung, die entscheidet, ob ein benannter Call überhaupt ausgeführt wird, und Teil 6 behandelt das Harness, das sowohl den Call als auch die Prüfung ausführt. In diesem Artikel bezeichnet Harness das Control Program, das jeden Prompt zusammenstellt, die akzeptierten Tool Calls dispatcht und entscheidet, wann die Aufgabe abgeschlossen ist – also alles rund um das Model, was gewöhnlicher Code ist, den Sie schreiben.

Die Tooling-Landschaft hat sich 2025–2026 verändert. MCP, das Model Context Protocol, gab Anbietern eine gemeinsame Möglichkeit, externe Services bereitzustellen. Code-executing Agents zeigten, dass ein Model manchmal effizienter ein kleines Programm komponieren kann, als eine lange Sequenz von JSON Calls auszugeben. Anthropic berichtete für einen Google-Drive-to-Salesforce-Workflow eine Token-Reduktion von 98,7 %, und das CodeAct-Paper berichtete in seinem Benchmark-Setup von Verbesserungen um bis zu 20 %. Diese Ergebnisse beziehen sich auf die jeweiligen Tasks und Harnesses, nicht auf einen universellen Vorteil von Code Execution.

Ich vergleiche JSON Tool Calling, MCP, Skills, CLI Tools und Code Execution in dieser Reihenfolge. Ein späterer Abschnitt wendet Designprinzipien für Agent-Computer Interfaces (ACI) auf den Market Analyst Agent an, einen kleinen LangGraph Research Agent, den ich für Teil 1 entwickelt habe und der Marktdaten abruft und einen Analystenbericht schreibt.

Eine kurze Entscheidungshilfe für Interfaces finden Sie unter AI Agent Tool Interfaces.

TL;DR

Fünf nützliche Interface-Patterns decken den Großteil der Tool-Nutzung durch AI Agents ab. Skills transportieren Instructions, CLI Tools eignen sich für lokale Entwicklung, MCP verbindet gemeinsam genutzte Services, und Code Execution komponiert mehrstufige Arbeit innerhalb einer Sandbox. JSON Tool Calling bleibt die einfachste Wahl für kleine, atomare Actions. Unabhängig vom Protocol muss das Agent-Computer Interface (ACI) Actions eindeutig machen, Feedback kompakt halten und eine Recovery von Fehlern ermöglichen.

Fünf Möglichkeiten, wie AI Agents Tools verwenden

In Teil 1 wählte der Reasoning Loop den nächsten Schritt. Teil 2 speicherte den Zustand, der für die Fortsetzung benötigt wurde. Die Tool-Grenze liegt zwischen beiden: Sie validiert, was der Loop vorgeschlagen hat, leitet den Call anschließend zur Ausführung weiter und gibt das Ergebnis an den Loop zurück. Diese fünf Patterns treffen unterschiedliche Abwägungen bei Token-Kosten, Flexibilität und Durchsetzung.

1. JSON Tool Calling: die Baseline

Das ursprüngliche Pattern: Sie definieren Tool Schemas als JSON, das LLM gibt strukturierte Function Calls aus, und Ihr Code führt sie aus. Es ist gut verstanden und funktioniert für kleine Toolsets problemlos.

# Traditional tool definition — each tool consumes ~550-1,400 tokens (Apideck benchmark)
tools = [
    {
        "name": "get_stock_price",
        "description": "Get the current stock price for a ticker symbol",
        "input_schema": {
            "type": "object",
            "properties": {
                "ticker": {"type": "string", "description": "Stock ticker (e.g., NVDA)"}
            },
            "required": ["ticker"]
        }
    }
]

Bei 5–10 Tools ist der Overhead akzeptabel. Das Problem ist die Skalierung: Jede Tool-Definition kostet 550–1.400 Tokens. Bei 20 Tools geben Sie 11–28K Tokens aus, bevor der Agent überhaupt mit dem Reasoning beginnt.

2. MCP für gemeinsam genutzte Integrationen

MCP ist der Standard, auf den sich die meisten Anbieter geeinigt haben. Ein MCP-Server ist ein Prozess, der über ein definiertes Wire Protocol eine Liste von Tools bereitstellt — für einen lokalen Prozess über stdio, für einen entfernten über HTTP. Dein Agent führt einen MCP-Client aus, der eine Verbindung herstellt, den Server nach seinen verfügbaren Tools fragt und die Calls des Models an ihn weiterleitet. Dadurch funktioniert derselbe Server mit jedem Client, der das Protocol unterstützt. Anthropic hat das Protocol im Dezember 2025 unter der Agentic AI Foundation an die Linux Foundation übertragen. Diese Foundation wurde gemeinsam mit OpenAI und Block gegründet. Google, Microsoft und AWS unterstützen die Foundation als Platinum Members. OpenAI hat MCP-Unterstützung in seiner Responses API ergänzt. Zum Zeitpunkt der Ankündigung von Anthropic zur Übertragung im Dezember 2025 umfasste das Ökosystem mehr als 10.000 aktive öffentliche MCP-Server und mehr als 97 Millionen monatliche SDK-Downloads über die Python- und TypeScript-SDKs hinweg.

MCP eignet sich für SaaS-Integrationen über Anbietergrenzen hinweg (Figma, Notion, Salesforce), für Services ohne CLI-Äquivalente und für Umgebungen, die OAuth-Orchestration benötigen. Der Wert liegt in einer gemeinsamen Discovery- und Transport-Schicht. Die Governance hängt weiterhin von den Authentifizierungs-, Autorisierungs-, Logging- und Deployment-Kontrollen des jeweiligen Servers ab.

Die Realität im Production-Betrieb ist komplexer, als die Schlagzeilenzahlen vermuten lassen.

Die Security Surface ist das erste Problem. Das Vulnerable MCP Project erfasst 50 Schwachstellen in MCP-Servern, davon 13 mit dem Rating Critical, gemeldet von 32 Security Researchern. Die Angriffsklassen reichen von Prompt Injection über Fehler bei der Input-Validierung und Authentifizierungslücken bis hin zu Sicherheitslücken in Netzwerken. Der erste bösartige MCP-Server in freier Wildbahn tauchte im September 2025 auf: ein Paket namens postmark-mcp, das jede ausgehende E-Mail per BCC an die Adresse eines Angreifers weiterleitete. Vor seiner Entdeckung waren schätzungsweise 300–500 Organisationen betroffen.

Tool Poisoning ist die Angriffsklasse, die mir am meisten Sorgen bereitet. Invariant Labs zeigte, dass kompromittierte MCP-Tools Daten exfiltrieren können, selbst wenn sie nie aufgerufen werden. Es reicht aus, dass das Model die Metadaten des Tools liest, um den Angriff auszulösen. Die MCPTox-Benchmarks, in denen 20 LLM Agents gegen 45 MCP-Server aus der Praxis getestet wurden, ermittelten Attack Success Rates von bis zu 72,8 %.

Der Token-Overhead ist das operative Problem. Ein Team, das MCP-Server für GitHub, Slack und Sentry betrieb (insgesamt etwa 40 Tools), stellte fest, dass 55.000 Tokens an Tool-Schema-Definitionen injiziert wurden, bevor ein User überhaupt eine Anfrage stellte. Ein anderes Team berichtete, dass allein die Tool-Definitionen 143.000 von 200.000 verfügbaren Tokens (72 %) verbrauchten.

Anthropic berichtete von einer Reduktion der Tokens für Tool-Definitionen um 85 % durch sein Tool Search Tool — ungefähr 77.000 Tokens an Schemas wurden auf 8.700 reduziert — indem nur die drei bis fünf Tools geladen werden, die eine Anfrage tatsächlich benötigt. Selektives Laden erhält die Protocol Surface und entfernt zugleich die Schemas, die für die aktuelle Anfrage nicht erforderlich sind.

Byte says

Ich verband MCP-Server für drei Dienste und ließ jedes Tool geladen. Die Schemas fraßen den größten Teil des Kontextfensters, noch bevor der Nutzer etwas eingab. Der Agent verwendete vier dieser Tools.

3. Skills bündeln Expertise, nicht Execution

Ende 2025 wurden Agent Skills als offenes Format standardisiert (im Oktober 2025 eingeführt und im Dezember 2025 als offener Standard veröffentlicht). Tools stellen Capabilities bereit (was Agents tun können), während Skills Expertise liefern (was Agents darüber wissen, wie komplexe Aufgaben erledigt werden).

Das SKILL.md-Format definiert einen Skill als Markdown-Datei mit YAML-Frontmatter. Der offene Standard erfordert lediglich name und description; das folgende Beispiel verwendet außerdem zwei Claude-Code-Erweiterungen, argument-hint und user-invocable, sowie dessen Platzhalter für Positionsargumente $0:

---
name: deploy
description: Deploy the application to production
argument-hint: "[environment]"
user-invocable: true
---
Deploy the application to the $0 environment (default: staging).
Steps:
1. Run the test suite
2. Build the production bundle
3. Deploy using the deploy script
4. Verify the deployment health check

Skills verwenden Progressive Disclosure. Beim Startup werden etwa 100 Tokens an Metadaten geladen; die vollständigen Anweisungen werden erst geladen, wenn der Skill aktiv ist. Zum Vergleich: Rund 40 MCP-Tools können bereits vor Beginn des Reasoning ungefähr 55.000 Tokens verbrauchen.

Bis März 2026 hatten Claude Code, OpenAI Codex CLI, Cursor, GitHub Copilot, Gemini CLI, Goose, Devin Desktop (damals Windsurf) und Roo Code das Format übernommen. Skills stehen neben einer umfassenderen Entwicklung hin zu codegesteuerten Agent-Aktionen. Victor Dibia zeichnet diese Entwicklung von JSON Function Calls zu generiertem Code nach — dem Muster, das Abschnitt 5 behandelt.

Verwende Skills für Domänenwissen, mehrstufige Verfahren und wiederkehrende Aufgaben wie Datenbankmigrationen oder Payment-Integrationen. Sie eignen sich für Aufgaben, bei denen der Agent Anweisungen dazu benötigt, wie eine vorhandene Fähigkeit verwendet wird.

4. CLI- und Shell-Tools

CLI-Schnittstellen können beim Context-Verbrauch deutlich günstiger sein, wenn das Model den Befehl bereits kennt. Scalekit berichtete über einen 4- bis 32-fachen Token-Unterschied zwischen seinen CLI- und MCP-Pfaden in 75 Runs. Diese Fallstudie misst die eigenen Tools und Aufgaben; sie ersetzt keinen Vergleich mit den eigenen Tool-Definitionen und der eigenen Command-Ausgabe.

Weitgehend dokumentierte Befehle wie git, docker, kubectl, gh, curl und jq benötigen häufig nur wenig einleitenden Schema-Text. Weniger verbreitete oder interne CLIs brauchen weiterhin auffindbare Hilfe, Beispiele und eine stabile maschinenlesbare Ausgabe.

Ugo Enyiohas Leitfaden “Writing CLI Tools That AI Agents Actually Want to Use” fasst acht Designregeln zusammen:

  1. Structured Output ist obligatorisch — unterstütze --json
  2. Exit-Codes sind Control Flow — verwende unterschiedliche Codes für verschiedene Fehlertypen
  3. Befehle sollten idempotent sein
  4. Selbstdokumentierend --help mit realistischen Beispielen
  5. Auf Composability auslegen — --quiet für reine Werte und stdin-Unterstützung
  6. Unterstütze die Flags --dry-run und --yes
  7. Unterstütze Version-Introspection
  8. Behandle Authentifizierung über Umgebungsvariablen

CLI bietet nicht die Type Safety, integrierte OAuth-Orchestration, Tool Discovery und Audit-Trail-Funktionen von MCP. Das Muster, auf das sich die meisten Teams meiner Beobachtung nach einigen: CLI als Standard für Entwicklung und lokale Operationen, MCP für die Integration externer Services und Enterprise Governance.

5. Codeausführung für mehrstufige Aufgaben

Dies ist die folgenreichste Änderung bei Agent-Tools, die ich beobachte. Statt strukturiertes JSON auszugeben, um vordefinierte Funktionen einzeln aufzurufen, schreibt der Agent ein Python- oder Bash-Skript. Das Skript ruft mehrere Tools auf, verarbeitet Ergebnisse mit Loops und Conditionals und gibt nur die abschließende Zusammenfassung an den Model-Kontext zurück.

Anthropic hat dies mit Programmatic Tool Calling (PTC) formalisiert, das inzwischen allgemein über die Claude API verfügbar ist. Die wissenschaftliche Grundlage bildet das CodeAct-Paper (Wang et al., ICML 2024). Darin wurden 17 LLMs getestet. Code Actions erzielten dabei bis zu 20 % höhere Task-Success-Raten und benötigten 30 % weniger Schritte als JSON-Alternativen.

Drei First-Party-Fallstudien zeigen, wo dieses Pattern helfen kann: Vercel und Cloudflare weiter unten sowie anschließend Anthropics Beispiel zur Spesenanalyse. Betrachten Sie sie als Vendor-Evidenz und führen Sie den Vergleich mit Ihren eigenen Tasks erneut durch.

  • Vercel hat d0, seinen Natural-Language-to-SQL-Daten-Agent, neu aufgebaut und dabei die Anzahl der Tools von 15 auf 2 reduziert — ExecuteCommand und ExecuteSQL —, was laut ihrem Beitrag einer Reduktion um 80 % entspricht. Über fünf repräsentative Queries hinweg stieg der Task Success von 4/5 auf 5/5, die durchschnittliche Ausführungszeit sank um den Faktor 3,5 (von 274,8 s auf 77,4 s), und der durchschnittliche Token-Verbrauch ging um 37 % zurück (von etwa 102.000 auf etwa 61.000 Tokens). Ihre Formulierung: „Die besten Agents sind vielleicht diejenigen mit den wenigsten Tools.“

  • Cloudflare entwickelte „Code Mode“, mit dem Agents TypeScript schreiben können, um ihre API aufzurufen, anstatt Tool Schemas zu definieren. Dadurch sinkt der Context Overhead. Ihre Begründung: „LLMs haben eine enorme Menge an praxisnahem TypeScript in ihren Trainingsdaten, aber nur eine kleine Anzahl konstruierter Beispiele für Tool Calls.“

Hier ist das Pattern aus Anthropics PTC-Dokumentation. Herkömmliches Tool Calling für die Spesenanalyse erfordert mehr als 20 separate Inference-Pässe, jeweils einen pro Teammitglied, wobei sämtliche Zwischendaten durch den Context fließen. Anthropic berichtet, dass generierter Code, der dieselbe Frage beantwortet, die im Context ankommende Datenmenge von 200 KB roher Spesenzeilen — mehr als 2.000 Einzelpositionen — auf 1 KB an Ergebnissen reduziert. Mit Code Execution schreibt der Agent ein einzelnes Skript:

# Agent generates this code, executes in sandbox
import json
members = get_team_members("engineering")
over_budget = []
for m in members:
    expenses = get_expenses(m["id"], "Q3")
    total = sum(e["amount"] for e in expenses)
    if total > 5000:
        custom = get_custom_budget(m["id"])
        limit = custom["limit"] if custom else 5000
        if total > limit:
            over_budget.append({"name": m["name"], "spent": total, "limit": limit})
# Only this final summary returns to the LLM context
print(json.dumps(over_budget))

Das LLM sieht nur die finale JSON-Zusammenfassung, nicht die Tausenden von Spesenpositionen, die in der Sandbox verarbeitet wurden. Die Einsparung ist nicht spezifisch für Spesenberichte: Anthropics separater Beitrag zu Code Execution nennt den deutlichsten Wert für dieses Pattern: Ein Google-Drive-to-Salesforce-Workflow sank von etwa 150.000 Tokens auf etwa 2.000 — eine Reduktion um 98,7 %.

Token-Effizienz ist der offensichtlichste Vorteil. Loops und Conditionals sind praktisch kostenlos, Fehler laufen über try/except statt über Reasoning in natürlicher Sprache zu Fehlschlägen, und sensible Daten bleiben in der Sandbox.

Wann JSON Tool Calling weiterhin sinnvoll ist: bei einzelnen atomaren Operationen, in Umgebungen ohne Sandbox-Infrastruktur, bei kleineren Models mit schwacher Code-Generierung oder bei Audit-Anforderungen, die jeden einzelnen Tool-Aufruf protokolliert benötigen.

„Meta-Tools“ in der Zeile zum Token-Overhead bezeichnet die wenigen generischen Einstiegspunkte, die ein Code-ausführender Agent benötigt – beispielsweise Vercels ExecuteCommand und ExecuteSQL – statt eines Schemas pro zugrunde liegender Operation. Komponierbarkeit beschreibt hier, wie einfach sich mehrere Operationen zu einem größeren Workflow verketten lassen. Niedrig bedeutet, dass jeder Tool Call üblicherweise einen weiteren Model-Roundtrip erfordert; hoch bedeutet, dass die Schnittstelle Zwischenergebnisse über Pipes, Variablen oder prozedurale Schritte weitergeben kann. Die Token- und Task-Success-Zellen fassen die zitierten Beispiele zusammen und stellen keinen kontrollierten Benchmark über alle fünf Spalten hinweg dar.

Das Agent-Computer Interface (ACI) für AI-Agent-Tools

Der Begriff „Agent-Computer Interface“ (ACI) wurde von John Yang, Carlos E. Jimenez und Kollegen an der Princeton University in ihrem SWE-agent-Paper (NeurIPS 2024) geprägt. Der Qualität von Human Interfaces ist eine ganze Disziplin gewidmet – Human-Computer Interaction oder HCI. Das Paper argumentiert, dass Language-Model-Agents die gleiche Behandlung verdienen: Sie seien „eine neue Kategorie von Endnutzern mit eigenen Anforderungen und Fähigkeiten und würden von speziell entwickelten Schnittstellen profitieren“.

Ihre Ablationsergebnisse machen das messbar. Mit demselben GPT-4-Turbo-Basismodell erreichte die SWE-bench-Lite-Ablation des Papers auf 300 Tasks 18,0 % mit der vollständigen ACI von SWE-agent, gegenüber 7,3 % für die reine Shell-Bedingung ohne ausgearbeitete Demonstration und 11,0 % mit einer solchen. Der Vergleich zeigt, dass Interface- und Demonstrationsbedingungen die Performance in diesem Setup substanziell verändert haben; er isoliert das Interface-Design jedoch nicht von allen anderen Unterschieden und zeigt nicht, dass das Modell keine Arbeit geleistet hat. Innerhalb derselben Interface-Ablation erhöhte die Aktivierung von Linting die Edit-Bedingung von 15,0 % auf 18,0 %; über den vollständigen SWE-bench-Testsatz hinweg enthielten 51,7 % der SWE-agent-Runs mindestens einen Edit, den der Linter ablehnte, bevor er weitergegeben werden konnte.

Anthropic übernahm ACI als grundlegendes Konzept in ihrem Leitfaden “Building Effective Agents” und führt es als eines von drei Kernprinzipien auf: „Gestalten Sie Ihr Agent-Computer-Interface sorgfältig durch umfassende Tool-Dokumentation und Tests.“ Die praktische Empfehlung lautet: „Als Faustregel sollten Sie sich vor Augen führen, wie viel Aufwand in Human-Computer-Interfaces fließt, und planen, genauso viel Aufwand in die Entwicklung guter Agent-Computer-Interfaces zu investieren.“

Vier ACI-Prinzipien in der Praxis

1. Aktionen sollten einfach und leicht verständlich sein. Der häufigste Fehler besteht darin, API-Endpunkte eins zu eins zu kapseln. Anstatt list_users, list_events und create_event zu verwenden, implementieren Sie schedule_event, das Verfügbarkeiten findet und die Planung in einem Tool Call übernimmt. Anstatt read_logs implementieren Sie search_logs, das nur die relevanten Zeilen mit Kontext zurückgibt.

2. Aktionen sollten kompakt und effizient sein. Fassen Sie wichtige Operationen in möglichst wenigen Aktionen zusammen. Im Market Analyst Agent kombiniere ich das Abrufen von Kursen mit grundlegenden Metriken in einem einzigen get_stock_snapshot-Tool, statt separate Tool Calls für Kurs, Volumen, Market Cap und PE-Ratio zu verlangen.

3. Das Feedback der Umgebung sollte informativ, aber prägnant sein. Vermeiden Sie die Rückgabe von rohem HTML oder vollständigen API-Payloads. Lösen Sie kryptische IDs in semantische Namen auf. Anthropics Tests fügten ein response_format-Enum hinzu, sodass der Agent eine prägnante Antwort (~72 Tokens) oder eine detaillierte Antwort (~206 Tokens) anfordern kann — ein ungefähr dreifacher Unterschied bei den Token-Kosten.

4. Validierung sollte die Fehlerfortpflanzung begrenzen. Automatische Fehlererkennung hilft Agents, Fehler schnell zu erkennen und zu korrigieren. In SWE-agent weist ein benutzerdefinierter Datei-Editor mit integriertem Linting Syntaxfehler automatisch zurück — der Validierungsschritt hinter der oben genannten Zahl von 51,7 %. Dabei handelt es sich um die Validierung der Inputs und Outputs eines Tools, nicht um die Inhaltsfilterung rund um einen Model Call, die die Guardrail-Produkte in Teil 4 übernehmen; dasselbe Wort wird für beides verwendet. Im Market Analyst Agent wende ich dasselbe Prinzip an, indem ich Tool-Argumente vor der Ausführung mit Pydantic-Schemas validiere:

from pydantic import BaseModel, Field, field_validator

class StockQuery(BaseModel):
    """Validated input for stock queries.

    Pydantic catches malformed tickers before the API call,
    preventing error propagation through the reasoning loop.
    """
    ticker: str = Field(description="Stock ticker symbol (e.g., NVDA)")
    period: str = Field(default="1mo", description="Time period: 1d, 5d, 1mo, 3mo, 6mo, 1y")

    @field_validator("ticker")
    @classmethod
    def validate_ticker(cls, v: str) -> str:
        v = v.upper().strip()
        if not v.isalpha() or len(v) > 5:
            raise ValueError(f"Invalid ticker format: {v}")
        return v

    @field_validator("period")
    @classmethod
    def validate_period(cls, v: str) -> str:
        valid = {"1d", "5d", "1mo", "3mo", "6mo", "1y"}
        if v not in valid:
            raise ValueError(f"Invalid period: {v}. Must be one of {valid}")
        return v

Funktionierende Tool-Design-Patterns für AI Agents

Anthropics Leitfaden “Writing effective tools for agents” beschreibt Tools als „eine neue Art von Software, die einen Vertrag zwischen deterministischen Systemen und nichtdeterministischen Agents abbildet.“

Tool-Beschreibungen als Prompt Engineering behandeln

Beschreibungen sollten mindestens drei oder vier Sätze umfassen und abdecken, wann das Tool verwendet werden soll, welche Parameter erforderlich beziehungsweise optional sind, welches Ausgabeformat gilt und welche Edge Cases auftreten können. Anthropic berichtet, dass die Entscheidung zwischen prefix- und suffix-basierter Namespacing-Strategie (asana_search beziehungsweise search_asana) bei den eigenen Tool-Use-Evaluierungen „nicht triviale Auswirkungen“ hatte. Es wird nicht angegeben, welches Schema besser abschneidet. Teste daher beide Varianten mit deinem Toolset, statt Präfixe vorauszusetzen. Anthropic speiste außerdem die Transkripte seiner Evaluator Agents zurück in Claude Code und ließ die Tools umschreiben. Auf zurückgehaltenen Testsets erzielte dieser Loop weitere Verbesserungen, „die sogar über das hinausgingen, was wir mit ‚Expert‘-Tool-Implementierungen erreicht hatten“ — unabhängig davon, ob diese Tools von den Forschenden von Hand geschrieben oder von Claude generiert worden waren.

# Bad: vague, no context for when to use
tools = [{
    "name": "search",
    "description": "Search for items",
}]

# Good: specific, with input examples and edge cases
tools = [{
    "name": "search_news",
    "description": (
        "Search for recent news articles about a specific stock or company. "
        "Use this tool when the user asks about recent events, earnings, "
        "announcements, or market-moving news for a specific ticker. "
        "Returns up to 10 articles sorted by relevance. "
        "For company competitors rather than news, use search_competitors instead."
    ),
    "input_schema": {
        "type": "object",
        "properties": {
            "query": {
                "type": "string",
                "description": "Search query. Examples: 'NVDA earnings Q3 2025', 'Tesla delivery numbers'"
            },
            "max_results": {
                "type": "integer",
                "description": "Max articles to return (1-10, default 5)",
                "default": 5
            }
        },
        "required": ["query"]
    }
}]

Anthropics interne Tests zeigten, dass ein zusätzliches Feld input_examples die Accuracy bei der Verarbeitung komplexer Parameter von 72 % auf 90 % steigerte.

High-Signal-Ausgaben in maschinenlesbarem Format zurückgeben

Vermeide Low-Level-Identifier (uuid, mime_type). Löse kryptische IDs in semantische Namen auf. Strukturiere die Antwort so, dass der Agent darüber Reasoning betreiben kann, ohne Boilerplate parsen zu müssen:

# Bad: raw API response dumped to agent
def get_stock_snapshot(ticker: str) -> dict:
    response = api.get(f"/v1/quotes/{ticker}")
    return response.json()  # 500+ tokens of nested JSON

# Good: high-signal summary the agent can immediately reason about
def get_stock_snapshot(ticker: str) -> dict:
    data = api.get(f"/v1/quotes/{ticker}").json()
    return {
        "ticker": ticker,
        "price": data["regularMarketPrice"],
        "change_pct": round(data["regularMarketChangePercent"], 2),
        "volume": data["regularMarketVolume"],
        "market_cap_b": round(data["marketCap"] / 1e9, 1),
        "pe_ratio": data.get("trailingPE"),
        "summary": f"{ticker} at ${data['regularMarketPrice']:.2f} "
                   f"({'up' if data['regularMarketChangePercent'] > 0 else 'down'} "
                   f"{abs(data['regularMarketChangePercent']):.1f}%)"
    }

Fehler zurückgeben, mit denen der Loop arbeiten kann

Fehlerbehandlung benötigt vier separate Mechanismen, da sie unterschiedliche Fehlerklassen behandeln:

  1. Retries mit exponentiellem Backoff für transiente Fehler
  2. Model-Fallback-Chains bei Ausfällen von Providern
  3. Routing nach Fehlerklassifikation — transiente Fehler werden erneut versucht, durch das LLM behebbare Fehler werden mit Kontext an den Agent zurückgegeben, und Fehler, die einen Menschen erfordern, werden eskaliert
  4. Checkpoint-Recovery zur Überlebenssicherung bei Crashes

Anthropics “Writing effective tools for agents” plädiert für klare Tool-Fehler und Evaluations-getriebenes Tool-Design, nennt jedoch keine universelle Zahl dafür, wie viele Fehler diese vier Mechanismen beheben. Miss Recovery Rate, Retries und Eskalationen in deiner eigenen Task Suite.

import httpx
from tenacity import retry, stop_after_attempt, wait_exponential

@retry(
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=1, min=2, max=10),
)
def call_stock_api(ticker: str) -> dict:
    """Fetch stock data with automatic retry on transient failures.

    Mechanism 1 of the four above: exponential backoff for rate limits
    and network blips.
    If all retries fail, the error propagates to the agent with
    enough context to decide whether to try a different approach.
    """
    response = httpx.get(
        f"https://api.example.com/v1/quotes/{ticker}",
        timeout=10.0,
    )
    response.raise_for_status()
    return response.json()

Anwendung der Patterns auf den Market Analyst Agent

Der Market Analyst Agent aus Teil 1 macht den Effekt des Interface-Designs sichtbar.

Byte says

Ich gab jedem API-Endpunkt ein eigenes Tool und lieferte zehn davon aus. Der Agent verbrachte sein Reasoning-Budget damit, herauszufinden, welche vier er kombinieren sollte. Ich hatte ihm meine API-Dokumentation gegeben und das ein Toolset genannt.

Tool-Konsolidierung

Das ursprüngliche Design umfasste mehr als zehn Tools: get_stock_price, get_company_metrics, get_market_cap, get_pe_ratio, get_volume und weitere. Jedes davon war ein Thin Wrapper um einen einzelnen API-Endpunkt. Der Agent musste für jede Anfrage ableiten, welche Kombination aufgerufen werden sollte.

Ich habe die Market-Data-Oberfläche nach dem ACI-Prinzip kompakter, effizienter Actions in fünf High-Level-Tools konsolidiert. Die Tool-Liste des Repos enthält daneben vier weitere Tools — einen Skill Loader, zwei CLI-Wrapper und einen eingeschränkten In-Process-Python-Evaluator (eine AST-Allowlist, keine Sandbox; Teil 4 geht darauf ein) — und deckt damit drei der fünf oben genannten Modalitäten ab. MCP erscheint als Sidecar und nicht als Tool in dieser Liste:

Vorher (10+ Tools)Nachher (5 Tools)Warum
get_stock_price + get_company_metrics + get_pe_ratioget_stock_snapshotEin einzelner Call liefert alles, was für eine grundlegende Analyse benötigt wird
get_price_history + get_volume_historyget_price_historyKombiniert mit konfigurierbarem Zeitraum und Indikatoren
search_news + search_press_releasessearch_newsEinheitliche Suche mit Quellenfilterung
search_competitors + get_sector_datasearch_competitorsLiefert Wettbewerber mit relativen Kennzahlen
get_financials + get_balance_sheet + get_cash_flowget_financialsVereinheitlicht durch den Parameter statement_type

Dadurch wurde der Overhead durch die Tool Schemas reduziert. In meinen eigenen Tests wurde außerdem die Tool-Auswahl zuverlässiger, da weniger mehrdeutige Entscheidungen getroffen werden müssen.

Structured Outputs für Tool Results

Jedes Tool im Market Analyst Agent liefert eine durch Pydantic validierte Response. Damit wird das ACI-Validierungsprinzip auf den Output des Tools angewendet:

class StockSnapshot(BaseModel):
    """Structured tool response — the agent never sees raw API noise."""
    ticker: str
    price: float
    change_pct: float
    volume: int
    market_cap_b: float
    pe_ratio: float | None
    summary: str  # Human-readable one-liner for direct use in reports

class NewsResult(BaseModel):
    """Each news item is pre-processed for agent consumption."""
    headline: str
    source: str
    date: str
    relevance_score: float  # Pre-ranked so the agent doesn't waste tokens sorting
    key_points: list[str]  # Extracted by the tool, not the agent

Das Feld summary ist dabei am wichtigsten. Es liefert dem Agent eine direkt verwendbare Zeichenkette, die ohne zusätzliche Verarbeitung in einen Report übernommen werden kann. Die key_points in NewsResult werden vom Tool und nicht vom Agent extrahiert. Dadurch muss der Agent keine Inference-Tokens für das Parsen von Artikeltexten aufwenden.

Abwägungen und wichtige Überlegungen

Neben den spezifischen Einschränkungen der einzelnen oben beschriebenen Patterns beeinflussen einige übergreifende Aspekte die Auswahl:

  • Die operativen Kosten unterscheiden sich je nach Dimension. Code Execution spart Tokens, verursacht aber zusätzliche Cold-Start-Latenz im Sandbox. MCP spart Entwicklungszeit bei SaaS-Integrationen, bringt jedoch zusätzlichen Aufwand für das Deployment des Servers mit sich. CLI ist zunächst kostenlos, lässt sich aber bei großer Skalierung schwieriger steuern. Optimiere für deinen tatsächlichen Bottleneck – unabhängig davon, ob es Token-Kosten, Latenz oder operative Komplexität ist.

  • Die Fähigkeiten des Teams sind relevant. Code Execution setzt voraus, dass deine Agents (und die dahinterliegenden Models) zuverlässiges Python oder TypeScript generieren können. CLI setzt Vertrautheit mit Unix-Konventionen voraus. Für MCP sind Kenntnisse über Transportprotokolle und OAuth-Flows erforderlich. Wähle die Modalität passend zu den Stärken deines Teams.

  • Tool-Konsolidierung kann zu weit gehen. Wenn ein Tool voneinander unabhängige Modi und Argumente ansammelt, steht der Agent innerhalb des Schemas vor einem anderen Auswahlproblem. Verwende Evals zur Tool-Auswahl und zum Task-Erfolg, um die passende Oberfläche für deinen Workload zu ermitteln.

  • Skills basieren auf Prompts und werden nicht erzwungen. Ein Skill besteht aus Anweisungen, die der Agent befolgen sollte, nicht aus Guardrails, die er befolgen muss. Für kritische Workflows solltest du Skills mit deterministischer Validierung kombinieren.

  • Audit-Anforderungen beeinflussen die Auswahl. Wenn du ein vollständiges Log jedes Tool-Aufrufs und seines Results benötigst, liefern MCP und JSON Tool Calling standardmäßig strukturierte Audit-Trails. Code Execution erzeugt ein Script und dessen Output. Das ist nützlich, lässt sich für Compliance-Reporting jedoch schwieriger in einzelne Aktionen zerlegen.

Drei Richtungen für AI-Agent-Tooling im großen Maßstab

Die erste ist Tool RAG für Skalierung. Wenn Toolsets auf Hunderte oder Tausende anwachsen, sinkt die Genauigkeit der naiven Tool-Auswahl auf 13,62 %. Das RAG-MCP-Paper wendete Retrieval-Augmented Generation auf die Tool-Auswahl an: Die Tool-Beschreibungen werden in einer Vector Database indexiert, und pro Query werden nur die relevanten Tools abgerufen. Damit wurde eine Genauigkeit von 43,13 % erreicht – eine Verbesserung um den Faktor 3,2 –, während sich die Prompt-Tokens um etwa 50 % reduzierten.

Die zweite Richtung sind Agents, die ihre eigenen Tools erstellen. Das LATM Framework („LLMs As Tool Makers“) etablierte ein zweiphasiges Paradigma, bei dem ein leistungsfähiges LLM wiederverwendbare Python-Funktionen erstellt und ein leichtgewichtiges LLM diese nutzt. ToolMaker (ACL 2025) transformiert GitHub-Repositories autonom in LLM-kompatible Tools – mit einer Erfolgsquote von 80 %. Beide Ansätze weisen über Tool Use hinaus: zunächst hin zur Tool-Erstellung und anschließend zur Verwaltung einer Bibliothek generierter Tools.

Die dritte Richtung ist der duale A2A- und MCP-Protocol-Stack. Das von Google entwickelte und im Juni 2025 an die Linux Foundation übertragene Agent2Agent Protocol (A2A) adressiert, was MCP nicht abdeckt: die Kommunikation zwischen Agents. MCP übernimmt die Integration von Agent und Tool; A2A übernimmt Discovery, Verhandlung und Task Delegation zwischen Agents.

Zentrale Erkenntnisse

  1. Wählt das Interface anhand der Aktion: JSON Calling für kleine typisierte Operationen, MCP für Shared Services, Skills für Prozeduren, CLI für etablierte Commands und Sandbox-Code für lokale Komposition.
  2. Haltet die Benchmark-Bedingungen beim Ergebnis fest. CodeAct, Anthropic, Vercel, Cloudflare, Apideck und Scalekit haben unterschiedliche Models, Tasks, Tools und Harnesses gemessen.
  3. Die Qualität der ACI bleibt auch bei Protocol-Änderungen erhalten. Klare Aktionen, kompaktes Feedback, Validierung und hilfreiche Fehlermeldungen unterstützen jede Modalität.
  4. Konsolidiert überlappende Tools nur dann, wenn Evals zeigen, dass die kleinere Oberfläche die Auswahl oder den Task-Erfolg verbessert.
  5. Mit der Ausführungsleistung steigt auch die Bedeutung der Security. Shell- und Code-Interfaces benötigen Sandboxing; MCP benötigt eine eingeschränkte Identität und Server-Policies; Skills bleiben Anweisungen und sind keine Enforcement-Mechanismen.

Die nächste Ebene ist Policy

Teil 4, AI Agent Security, setzt eine Policy-Prüfung zwischen einen vorgeschlagenen Tool Call und dessen Ausführung. Es handelt sich um dieselbe oben beschriebene Tool-Grenze, diesmal aus der Perspektive der Instanz, die Nein sagt. Teil 5 platziert das Tool und seine Sandbox anschließend in einem recoverable Runtime, und Teil 6 ergänzt einen zweiten Contract, den das Model niemals sieht: eine Effect-Kategorie, eine Retry-Regel und ein strukturiertes Ergebnis, das ein Acceptance Check lesen kann, ohne Prosa parsen zu müssen.
