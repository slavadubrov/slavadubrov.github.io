AI Agent Tool Use in 2026: MCP, CLI, Skills und Code Execution

Teil 3 der Engineering the Agentic Stack series

Teil 1 behandelte reasoning loops, und Teil 2 behandelte memory. Dieser Artikel ergänzt die Action-Schicht: wie ein Agent Tools anbietet, auswählt und ausführt.

Die Tooling-Story hat sich in 2025–2026 verändert. MCP brachte Anbietern ein gemeinsames Protokoll für externe Services. Code-executing Agents zeigten, dass ein Modell manchmal effizienter ein kleines Programm zusammensetzt als eine lange Sequenz von JSON Calls auszugeben. Anthropic berichtete eine 98,7% token reduction für einen Expense-Analyse-Workflow, und das CodeAct Paper berichtete Gains von bis zu 20% über seine Benchmark-Setups. Diese Ergebnisse beschreiben ihre Aufgaben und Harnesses – kein universeller Vorteil für Code Execution.

Ich vergleiche JSON tool calling, MCP, Skills, CLI Tools und Code Execution in dieser Reihenfolge. Der letzte Abschnitt wendet Agent-Computer Interface (ACI)-Designprinzipien auf den Market Analyst Agent an.

TL;DR: Fünf nützliche Interface-Muster decken die meisten Anforderungen beim Tool Use von Agents ab. Skills transportieren Instruktionen, CLI-Tools passen zu lokalem Development, MCP verbindet gemeinsame Services, und Code Execution komponiert mehrstufige Arbeit innerhalb eines Sandboxes. JSON tool calling bleibt die einfachste Wahl für kleine atomare Aktionen. Unabhängig vom Protokoll muss das Agent-Computer Interface (ACI) Aktionen klar machen, Feedback kompakt halten und Fehler so behandeln, dass sich Recovery durchführen lässt.

Fünf Wege, wie AI Agents Tools verwenden

In Teil 1 hat die reasoning loop den nächsten Schritt gewählt. Teil 2 speicherte den State, der nötig ist, um wieder einzusteigen. Die Tool-Grenze macht diese Entscheidung zu einer Aktion und liefert eine Observation an die Loop zurück. Diese fünf Muster treffen unterschiedliche Trade-offs bei Tokenkosten, Flexibilität und Durchsetzung.

1. JSON tool calling: der Baseline-Ansatz

Das ursprüngliche Muster: Tool-Schemas definieren Sie als JSON, das LLM erzeugt strukturierte function calls, und Ihr Code führt sie aus. Das ist gut verstanden und funktioniert für kleine Toolsets zuverlässig.

# Traditional tool definition — each tool consumes ~550-1,400 tokens (Apideck benchmark)
tools = [
    {
        "name": "get_stock_price",
        "description": "Get the current stock price for a ticker symbol",
        "input_schema": {
            "type": "object",
            "properties": {
                "ticker": {"type": "string", "description": "Stock ticker (e.g., NVDA)"}
            },
            "required": ["ticker"]
        }
    }
]

Bei 5–10 Tools ist Overhead noch akzeptabel. Das Problem ist Skalierung: Jede Tool-Definition kostet 550–1.400 Tokens. Bei 20 Tools geben Sie 15–25K Tokens aus, bevor der Agent überhaupt mit dem Reasoning beginnt.

2. MCP für gemeinsame Integrationen

Der Model Context Protocol-Standard ist die Konvergenz, zu der die meisten Vendoren gegangen sind. Anthropic hat ihn im Dezember 2025 unter dem Agentic AI Foundation (AAIF) – das sie gemeinsam mit OpenAI und Block mitbegründet haben – an die Linux Foundation gespendet. Google, Microsoft und AWS unterstützen die Foundation als Platinum-Mitglieder. OpenAI hat MCP Support in seiner Responses API ergänzt. Es gibt mittlerweile 10.000+ aktive MCP-Server und 97M+ monatliche SDK-Downloads.

MCP passt zu plattformübergreifenden SaaS-Integrationen (Figma, Notion, Salesforce), zu Services ohne CLI-Äquivalente und zu Umgebungen, die OAuth-Orchestrierung benötigen. Der Mehrwert liegt in einer gemeinsamen Discovery- und Transport-Schicht. Governance hängt weiterhin von den serverseitigen Controls für Authentication, Authorization, Logging und Deployment ab.

Die Production-Story ist jedoch unaufgeräumter, als die Headline-Zahlen vermuten lassen.

Die erste Problemklasse ist die Security Surface. Das Vulnerable MCP Project erfasst 50 Vulnerabilities über MCP-Server hinweg, davon 13 mit Rating Critical – beigetragen von 32 Security Researchers. Die Attack-Klassen reichen von Prompt Injection, Input-Validation-Fehlern, Authentifizierungs-Lücken bis hin zu Netzwerksicherheitslücken. Der erste echte böswillige MCP-Server tauchte im September 2025 auf: ein Package namens postmark-mcp, das jede ausgehende E-Mail per BCC an die Adresse eines Angreifers weiterleitete und nach Schätzung 300–500 Organisationen traf, bevor es entdeckt wurde.

Tool Poisoning ist die Attack-Klasse, die mir am meisten Sorgen macht. Invariant Labs konnte zeigen, dass gepoisonte MCP-Tools Daten exfiltrieren können, selbst wenn sie nie aufgerufen werden. Das Lesen der Tool-Metadaten durch das Modell reicht, um den Angriff auszulösen. MCPTox Benchmarks testeten 20 LLM Agents gegen 45 reale MCP-Server und fanden Attack Success Rates von bis zu 72,8%.

Token Overhead ist das operative Hauptproblem. Ein Team, das MCP-Server für GitHub, Slack und Sentry betreibt (insgesamt ~40 Tools), fand 55.000 Tokens an Schema-Definitionen, die injiziert wurden, bevor ein User überhaupt etwas fragt. Ein anderes berichtet 143.000 von 200.000 verfügbaren Tokens (72%), die allein durch Tool-Definitionen verbraucht wurden.

Anthropic berichtete eine 85% Schema-Reduction durch sein Tool Search Tool und eine 96% Reduktion, wenn drei bis fünf relevante Tools für die evaluierten Aufgaben geladen wurden. Selektives Laden hält die Protokoll-Oberfläche, entfernt aber Schemas, die die aktuelle Anfrage nicht benötigt.

3. Skills: Package-Expertise, nicht Execution

Ende 2025 wurde die Standardisierung von agent skills als offenes Format vorangetrieben (gestartet im Oktober 2025, als Open Standard im Dezember 2025 veröffentlicht). Tools liefern Fähigkeiten (was Agents tun können), und Skills liefern Expertise (was Agents wissen, um komplexe Aufgaben zu erledigen).

Der SKILL.md Standard definiert eine Skill als eine Markdown-Datei mit YAML Frontmatter:

---
name: deploy
description: Deploy the application to production
argument-hint: "[environment]"
user-invocable: true
---
Deploy the application to the $0 environment (default: staging).
Steps:
1. Run the test suite
2. Build the production bundle
3. Deploy using the deploy script
4. Verify the deployment health check

Skills nutzen progressive disclosure. Etwa 100 Tokens Metadaten werden beim Startup geladen; die vollständigen Instruktionen werden erst geladen, wenn die Skill aktiv ist. Vergleichen Sie das mit den ca. 55.000 Tokens, die etwa 40 MCP Tools verbrauchen können, bevor das Reasoning beginnt.

Bis März 2026 hatten Claude Code, OpenAI Codex CLI, Cursor, GitHub Copilot, Gemini CLI, Goose, Windsurf und Roo Code das Format übernommen. Victor Dibia beschreibt diesen Shift hin zu code-getriebenen Agent-Aktionen.

Nutzen Sie Skills für Domain Knowledge, mehrstufige Prozeduren und wiederkehrende Arbeit wie Datenbank-Migrationen oder Payment-Integrationen. Sie passen zu Aufgaben, bei denen der Agent Anweisungen dafür braucht, wie er eine vorhandene Capability verwendet.

4. CLI und Shell-Tools

CLI-Interfaces können im Kontext deutlich günstiger sein, wenn das Modell den Command bereits kennt. Scalekit berichtete eine 4–32x token difference zwischen seinem CLI- und MCP-Path über 75 Runs. Dieses Case Study misst Tools und Tasks; es ersetzt keinen Vergleich in Ihren eigenen Manifests und Kommandoausgaben.

Weit dokumentierte Commands wie git, docker, kubectl, gh, curl und jq benötigen oft nur wenig einleitenden Schema-Text. Seltener verwendete oder interne CLIs brauchen dennoch auffindbare Hilfe, Beispiele und stabile maschinenlesbare Ausgaben.

Ugo Enyiohas Guide “Writing CLI Tools That AI Agents Actually Want to Use” hat acht Designregeln kodifiziert:

  1. Structured output ist Pflicht — unterstützen Sie --json
  2. Exit codes steuern den Control Flow — nutzen Sie unterschiedliche Codes für verschiedene Fehlerklassen
  3. Commands sollten idempotent sein
  4. Self-documenting --help mit realistischen Beispielen
  5. Design für Komponierbarkeit — --quiet für einzelne Werte, stdin Support
  6. Stellen Sie --dry-run und --yes Flags bereit
  7. Support für Version Introspection
  8. Auth über Environment Variables handhaben

CLI fehlt MCPs Typsicherheit, integrierte OAuth-Orchestrierung, Tool Discovery und Audit Trail. Das Muster, zu dem die meisten Teams konvergieren, lautet: CLI als Default für Development und lokale Operationen, MCP für externe Service-Integration und Enterprise-Governance.

5. Code Execution für mehrstufige Arbeit

Das ist die Tooling-Änderung, die ich als am folgenreichsten erachte. Statt strukturierte JSONs zu emittieren, um vordefinierte Funktionen einzeln aufzurufen, schreibt der Agent ein Python- oder bash-Skript. Das Skript ruft mehrere Tools auf, verarbeitet Ergebnisse mit Loops und Conditionals und liefert nur die finale Zusammenfassung in den Modell-Kontext zurück.

Anthropic hat dies mit Programmatic Tool Calling (PTC) formalisiert, das jetzt GA in der Claude API ist. Die akademische Grundlage ist das CodeAct Paper (Wang et al., ICML 2024), das über 17 LLMs getestet hat und fand, dass Code-Aktionen bis zu 20% höhere Task Success Rates und 30% weniger Steps als JSON-Alternativen erreichen.

Drei First-Party Case Studies zeigen, wo das Muster helfen kann: erst Vercel und Cloudflare, dann das Expense-Analyse-Beispiel von Anthropic. Behandeln Sie das als Vendor-Evidenz und führen Sie den Vergleich auf Ihre eigenen Tasks erneut durch.

  • Vercel hat ihren d0 text-to-SQL agent neu gebaut, indem sie 80% der Tools entfernt haben (von 15 auf 2: ExecuteCommand und ExecuteSQL). Der Task-Erfolg stieg von 80% auf 100%, die Ausführungszeit fiel um den Faktor 3,5, und der Tokenverbrauch sank um 40%. Formulierung: „Die besten Agents sind vielleicht die mit den wenigsten Tools.“

  • Cloudflare entwickelte „Code Mode,“ wodurch Agents TypeScript schreiben, um ihre API aufzurufen, statt Tool-Schemas zu definieren. Das reduziert den Context-Overhead. Ihre Reasoning-These: „LLMs haben in ihrem Trainingsset eine enorme Menge an realem TypeScript, aber nur eine kleine Anzahl kontrivierter Beispiele für Tool Calls.“

Hier ist das Muster aus Anthropics PTC-Dokumentation. Traditionelles Tool calling für Expense Analysis benötigt 20+ separate Inferenz-Passes, jeweils pro Teammitglied, wobei alle Zwischendaten durch den Kontext laufen. Ein Workflow, der ~150.000 Tokens mit direktem Tool calling verbraucht, wurde auf ~2.000 Tokens reimplementiert, eine 98,7% Reduktion. Mit Code Execution schreibt der Agent genau ein Skript:

# Agent generates this code, executes in sandbox
import json
members = get_team_members("engineering")
over_budget = []
for m in members:
    expenses = get_expenses(m["id"], "Q3")
    total = sum(e["amount"] for e in expenses)
    if total > 5000:
        custom = get_custom_budget(m["id"])
        limit = custom["limit"] if custom else 5000
        if total > limit:
            over_budget.append({"name": m["name"], "spent": total, "limit": limit})
# Only this final summary returns to the LLM context
print(json.dumps(over_budget))

Das LLM sieht nur die finale JSON-Zusammenfassung, nicht die tausenden Expense Line Items, die in der Sandbox verarbeitet wurden. Der offensichtlichste Gewinn ist Token-Effizienz. Loops und Conditionals fallen „kostenlos“ an, Fehler laufen über try/except statt über Natural-Language Reasoning über Failures, und sensible Daten bleiben in der Sandbox.

Wann JSON tool calling weiterhin sinnvoll ist: einzelne atomare Operationen, Umgebungen ohne Sandbox-Infrastruktur, kleinere Modelle mit schwacher Code-Generierung oder Audit-Anforderungen, die jede einzelne Tool-Invocation geloggt haben müssen.

Das Agent-Computer Interface (ACI) für AI Agent Tools

Der Begriff „Agent-Computer Interface“ (ACI) wurde von John Yang, Carlos E. Jimenez und Kolleginnen/Kollegen an Princeton in ihrem SWE-agent Paper geprägt (NeurIPS 2024). Wie Menschen von gut designten Interfaces profitieren (HCI), argumentiert das Paper, dass LM Agents „eine neue Kategorie von End-Usern mit eigenen Bedürfnissen und Fähigkeiten“ seien und deshalb „von speziell gebauten Interfaces“ profitieren würden.

Ihre Ablation-Results quantifizieren das. SWE-agent mit vollem ACI erreichte 18,0% auf SWE-bench Lite gegenüber 7,3% nur mit einer standardmäßigen Linux-Shell – eine 10,7 Prozentpunkte Verbesserung allein durch Interface-Design. Das Linting-Guardrail alleine trug 3 Prozentpunkte bei: 51,7% der Agent Edits enthielten mindestens einen Fehler, der der Linter erkannt und abgefangen hat, bevor er sich fortpflanzen konnte.

Anthropic übernahm ACI als grundlegendes Konzept in seinem Leitfaden “Building Effective Agents” und listet es als eines von drei Kernprinzipien: „Carefully craft your agent-computer interface through thorough tool documentation and testing.“ Praktische Guidance: „Eine Daumenregel ist, sich vor Augen zu führen, wie viel Aufwand in Human-Computer Interfaces fließt, und entsprechend genauso viel in die Erstellung guter agent-computer interfaces zu investieren.“

Vier ACI-Prinzipien in der Praxis

1. Aktionen sollen einfach und leicht verständlich sein. Der häufigste Fehler ist, API Endpoints 1:1 einzupacken. Statt list_users, list_events, create_event zu implementieren, implementieren Sie schedule_event, das Verfügbarkeit findet und in einem Call schedulet. Statt read_logs implementieren Sie search_logs, das nur die relevanten Zeilen inklusive Kontext zurückgibt.

2. Aktionen sollen kompakt und effizient sein. Konsolidieren Sie wichtige Operationen auf so wenige Aktionen wie möglich. Im Market Analyst Agent kombiniere ich Preisabruf mit Basismetriken in ein einziges get_stock_snapshot Tool, statt separate Calls für Preis, Volumen, Market Cap und PE Ratio zu verlangen.

3. Environment Feedback sollte informativ, aber kompakt sein. Vermeiden Sie das Zurückgeben von rohem HTML oder vollständigen API Payloads. Auflösen kryptischer IDs in semantische Namen. Anthropics Testing fügte ein response_format Enum hinzu, damit der Agent eine kompakte (~72 Tokens) oder detaillierte (~206 Tokens) Antwort anfragen kann – grob ein 3x Unterschied in den Tokenkosten. Sie berichteten verbessertes Real-World Performance.

4. Guardrails sollten die Fehlerfortpflanzung mitigieren. Automatische Fehlererkennung hilft Agents, Fehler schnell zu erkennen und zu korrigieren. Im SWE-agent gibt es einen custom File Editor mit integriertem Linting: Syntaxfehler werden automatisch verworfen, mindestens ein Fehler in 51,7% der Agent Edits wird abgefangen, bevor er sich verstärken kann. Ich wende dasselbe Prinzip im Market Analyst Agent an, indem ich Tool-Argumente mit Pydantic-Schemas validiere, bevor sie ausgeführt werden:

from pydantic import BaseModel, Field, field_validator

class StockQuery(BaseModel):
    """Validated input for stock queries.

    Pydantic catches malformed tickers before the API call,
    preventing error propagation through the reasoning loop.
    """
    ticker: str = Field(description="Stock ticker symbol (e.g., NVDA)")
    period: str = Field(default="1mo", description="Time period: 1d, 5d, 1mo, 3mo, 1y")

    @field_validator("ticker")
    @classmethod
    def validate_ticker(cls, v: str) -> str:
        v = v.upper().strip()
        if not v.isalpha() or len(v) > 5:
            raise ValueError(f"Invalid ticker format: {v}")
        return v

    @field_validator("period")
    @classmethod
    def validate_period(cls, v: str) -> str:
        valid = {"1d", "5d", "1mo", "3mo", "6mo", "1y", "5y"}
        if v not in valid:
            raise ValueError(f"Invalid period: {v}. Must be one of {valid}")
        return v

AI agent Tool-Designmuster, die funktionieren

Anthropics Leitfaden “Writing effective tools for agents” beschreibt Tools als „eine neue Art von Software, die einen Vertrag zwischen deterministischen Systemen und nicht-deterministischen Agents widerspiegelt.“

Behandeln Sie Tool-Descriptions als prompt engineering

Beschreibungen sollten mindestens 3–4+ Sätze umfassen: wann das Tool zu verwenden ist, benötigte versus optionale Parameter, Output-Format und Edge Cases. Namespacing mit Prefixes (asana_search, jira_search) hat „nicht-triviale Effekte“ auf die Tool-Auswahl-Accuracy. In Anthropics Experimenten schnitten Claude-optimierte Tool-Descriptions gegenüber Experten-Manual-Texten bei Evaluations-Benchmarks besser ab.

# Bad: vague, no context for when to use
tools = [{
    "name": "search",
    "description": "Search for items",
}]

# Good: specific, with input examples and edge cases
tools = [{
    "name": "stock_search_news",
    "description": (
        "Search for recent news articles about a specific stock or company. "
        "Use this tool when the user asks about recent events, earnings, "
        "announcements, or market-moving news for a specific ticker. "
        "Returns up to 10 articles sorted by relevance. "
        "For broad market news (not ticker-specific), use market_overview instead."
    ),
    "input_schema": {
        "type": "object",
        "properties": {
            "query": {
                "type": "string",
                "description": "Search query. Examples: 'NVDA earnings Q3 2025', 'Tesla delivery numbers'"
            },
            "max_results": {
                "type": "integer",
                "description": "Max articles to return (1-10, default 5)",
                "default": 5
            }
        },
        "required": ["query"]
    }
}]

Internes Testing zeigte, dass Input-Beispiele (input_examples Field) die Genauigkeit bei komplexer Parameterbehandlung deutlich verbessern.

Geben Sie High-Signal, maschinenlesbare Outputs zurück

Vermeiden Sie Low-Level-Identifier (uuid, mime_type). Auflösen kryptischer IDs in semantische Namen. Strukturieren Sie die Antwort so, dass der Agent darüber nachdenken kann, ohne Boilerplate zu parsen:

# Bad: raw API response dumped to agent
def get_stock_price(ticker: str) -> dict:
    response = api.get(f"/v1/quotes/{ticker}")
    return response.json()  # 500+ tokens of nested JSON

# Good: high-signal summary the agent can immediately reason about
def get_stock_price(ticker: str) -> dict:
    data = api.get(f"/v1/quotes/{ticker}").json()
    return {
        "ticker": ticker,
        "price": data["regularMarketPrice"],
        "change_pct": round(data["regularMarketChangePercent"], 2),
        "volume": data["regularMarketVolume"],
        "market_cap_b": round(data["marketCap"] / 1e9, 1),
        "pe_ratio": data.get("trailingPE"),
        "summary": f"{ticker} at ${data['regularMarketPrice']:.2f} "
                   f"({'up' if data['regularMarketChangePercent'] > 0 else 'down'} "
                   f"{abs(data['regularMarketChangePercent']):.1f}%)"
    }

Geben Sie Errors zurück, mit denen die Loop handeln kann

Nutzen Sie vier separate Mechanismen, weil sie unterschiedliche Fehlerklassen abdecken:

  1. Retry mit exponentiellem Backoff für transiente Fehler
  2. Model Fallback Chains für Provider-Outages
  3. Error-Classification Routing — transiente Fehler retryen, LLM-recoverable Fehler zurück an den Agent inkl. Kontext, human-required Fehler eskalieren
  4. Checkpoint-Recovery für Crash-Überleben

Der zitierte Anthropic-Guide unterstützt klare Tool-Errors und evaluation-getriebenes Tool-Design. Er belegt jedoch keine universelle Reduktion der Failure-Rate, daher messen Sie Recovery-Rate, Retries und Escalation auf Ihrer eigenen Task Suite.

from tenacity import retry, stop_after_attempt, wait_exponential

@retry(
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=1, min=2, max=10),
)
def call_stock_api(ticker: str) -> dict:
    """Fetch stock data with automatic retry on transient failures.

    Layer 1: Exponential backoff handles rate limits and network blips.
    If all retries fail, the error propagates to the agent with
    enough context to decide whether to try a different approach.
    """
    response = httpx.get(
        f"https://api.example.com/v1/quotes/{ticker}",
        timeout=10.0,
    )
    response.raise_for_status()
    return response.json()

Anwendung der Muster auf den Market Analyst Agent

Der Market Analyst Agent aus Teil 1 macht die Wirkung des Interfaces sichtbar.

Tool-Konsolidierung

Der Teil-1-Artikel zeigt die vereinfachte 5-Tool-Oberfläche nach diesem Refactor. Vor diesem Cleanup hatte das ursprüngliche Design 10+ Tools: get_stock_price, get_company_metrics, get_market_cap, get_pe_ratio, get_volume und so weiter. Jedes war ein dünner Wrapper um genau einen API Endpoint. Der Agent musste für jede Anfrage überlegen, welche Kombination an Calls nötig ist.

Ich konsolidierte das in 5 High-Level Tools und folgte dabei dem ACI-Prinzip kompakter, effizienter Aktionen:

Vorher (10+ Tools)Nachher (5 Tools)Warum
get_stock_price + get_company_metrics + get_pe_ratioget_stock_snapshotSingle Call liefert alles für die grundlegende Analyse
get_price_history + get_volume_historyget_price_historyKombiniert mit konfigurierbarer Periode und Indikatoren
search_news + search_press_releasessearch_newsUnified Search mit Source-Filtering

Dadurch sank der Tool-Schema-Overhead, und die Toolauswahl des Agents wurde zuverlässiger, weil es weniger mehrdeutige Entscheidungen gibt.

Strukturierte Outputs für Tool-Results

Jedes Tool im Market Analyst Agent liefert eine Pydantic-validierte Antwort. Das ist eine direkte Anwendung des ACI-Guardrails-Prinzips an der Tool-Grenze:

class StockSnapshot(BaseModel):
    """Structured tool response — the agent never sees raw API noise."""
    ticker: str
    price: float
    change_pct: float
    volume: int
    market_cap_b: float
    pe_ratio: float | None
    summary: str  # Human-readable one-liner for direct use in reports

class NewsResult(BaseModel):
    """Each news item is pre-processed for agent consumption."""
    headline: str
    source: str
    date: str
    relevance_score: float  # Pre-ranked so the agent doesn't waste tokens sorting
    key_points: list[str]  # Extracted by the tool, not the agent

Das summary Feld ist das, was am meisten zählt. Es gibt dem Agent einen direkt verwendbaren String, der ohne zusätzliche Verarbeitung in einen Report übernommen werden kann. Das key_points in NewsResult wird serverseitig extrahiert; dadurch spart der Agent Inferenz-Tokens beim Parsen der Artikeltexte.

Trade-offs und Überlegungen

Neben den modalitätspezifischen Caveats oben beeinflussen einige übergreifende Aspekte die Auswahl:

  • Die operativen Kosten variieren nach Dimension. Code Execution spart Tokens, addiert aber Sandbox-Cold-Start-Latenz. MCP spart Entwicklungszeit für SaaS-Integrationen, bringt aber Overhead beim Server-Deployment. CLI ist zum Start „free“, aber schwieriger im Scale zu gobern. Optimieren Sie für Ihren echten Bottleneck – Tokenkosten, Latenz oder operative Komplexität.

  • Team-Skills sind wichtig. Code execution setzt voraus, dass Ihre Agents (und die Modelle dahinter) in der Lage sind, zuverlässiges Python oder TypeScript zu generieren. CLI setzt Vertrautheit mit Unix-Konventionen voraus. MCP erfordert Verständnis für Transport-Protokolle und OAuth-Flows. Ordnen Sie die Modalität den Stärken Ihres Teams zu.

  • Tool-Konsolidierung kann zu weit gehen. Wenn ein Tool mehrere unzusammenhängende Modi und Argumente ansammelt, stößt der Agent auf ein anderes Selektionsproblem innerhalb des Schemas. Nutzen Sie Tool-Selection- und Task-Success-Evaluations, um die passende Oberfläche für Ihre Workloads zu finden.

  • Skills sind prompt-basiert, nicht erzwungen. Eine Skill sind Instruktionen, denen der Agent folgen sollte, nicht Guardrails, die er muss befolgen. Für kritische Workflows kombinieren Sie Skills mit deterministischer Validierung.

  • Audit-Anforderungen prägen die Auswahl. Wenn Sie einen vollständigen Log für jede Tool-Invocation und ihr Resultat benötigen, liefern MCP und JSON tool calling strukturierte Audit-Trails out of the box. Code execution erzeugt ein Skript und dessen Output: nützlich, aber schwerer in einzelne Aktionen zu zerlegen, wenn Sie Compliance-Reporting brauchen.

Tool-Auswahl im größeren Maßstab

Drei Richtungen lohnt es sich zu verfolgen.

Die erste ist tool RAG zum Skalieren. Wenn Toolsets auf hunderte oder tausende wachsen, sinkt naive Toolauswahl-Accuracy auf 13,62%. Das RAG-MCP paper hat retrieval-augmented generation für Tool Selection angewendet: Tool-Descriptions in einer Vector Database indexieren und pro Query nur die relevanten abrufen. Das erreichte 43,13% Accuracy – ein Faktor 3,2 – und senkte Prompt Tokens um ca. 50%.

Die zweite ist das Erstellen eigener Tools durch Agents. Das LATM framework („LLMs As Tool Makers“) etablierte ein Two-Phase-Paradigma: ein leistungsfähiges LLM erstellt wiederverwendbare Python-Funktionen, und ein leichtgewichtiges LLM nutzt sie. ToolMaker (ACL 2025) transformiert GitHub Repositories autonom in LLM-kompatible Tools mit einer 80%-Success-Rate. Beide zeigen, dass Tool Use weiter Richtung Tool Creation geht – und dann hin zur Verwaltung einer Bibliothek generierter Tools.

Die dritte ist der A2A + MCP Dual-Protocol Stack. Googles Agent2Agent Protocol (A2A) adressiert, was MCP nicht kann: Kommunikation Agent-zu-Agent. MCP übernimmt agent-to-tool Integration; A2A übernimmt agent-to-agent Discovery, Negotiation und Task Delegation.

Kernaussagen

  1. Wählen Sie das Interface aus der Aktion heraus: JSON calling für kleine typisierte Operationen, MCP für gemeinsame Services, Skills für Prozeduren, CLI für etablierte Commands und sandboxed code für lokale Komposition.
  2. Hängen Sie Benchmark-Bedingungen ans Ergebnis. CodeAct, Anthropic, Vercel, Cloudflare, Apideck und Scalekit maßen unterschiedliche Modelle, Tasks, Tools und Harnesses.
  3. ACI-Qualität überlebt Protokollwechsel. Klare Aktionen, kompakte Feedbacks, Validierung und brauchbare Errors helfen jeder Modalität.
  4. Konsolidieren Sie überlappende Tools nur dann, wenn Evaluations zeigen, dass die kleinere Oberfläche Selection oder Task Success verbessert.
  5. Security bewegt sich mit der Execution Power. Shell- und Code-Interfaces brauchen Sandboxing; MCP braucht scoped identity und Server-Policy; Skills bleiben Instruktionen statt Enforcement.
