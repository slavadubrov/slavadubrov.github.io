Tool Use für AI Agents: MCP, CLI, Skills und Code Execution

Teil 3 der Serie „Engineering the Agentic Stack“

Teil 1 behandelte Reasoning Loops, Teil 2 Agent Memory. Dieser Artikel ergänzt die Action Layer: wie ein Agent Tools bereitstellt, auswählt und ausführt. Memory bestimmt, was der Agent zu Beginn eines Turns weiß; diese Layer bestimmt, was er damit tun kann. Teil 4 behandelt den Check, der entscheidet, ob ein benannter Call überhaupt ausgeführt wird, und Teil 6 das Harness, das sowohl den Call als auch den Check ausführt. Im gesamten Artikel bezeichnet Harness das Steuerprogramm, das jeden Prompt zusammenstellt, akzeptierte Tool Calls dispatcht und entscheidet, wann die Aufgabe abgeschlossen ist – also alles rund um das Model, was aus gewöhnlichem Code besteht, den du selbst schreibst.

Die Tooling-Landschaft hat sich 2025–2026 verändert. MCP, das Model Context Protocol, gab Anbietern eine gemeinsame Möglichkeit, externe Services bereitzustellen. Code-executing Agents zeigten, dass ein Model manchmal effizienter ein kleines Programm zusammenstellen kann, als eine lange Folge von JSON Calls auszugeben. Anthropic berichtete für einen Google-Drive-to-Salesforce-Workflow von einer Token-Reduktion um 98,7 %, und das CodeAct-Paper meldete in seinem Benchmark-Setup Verbesserungen von bis zu 20 %. Diese Ergebnisse beziehen sich auf die jeweiligen Tasks und Harnesses, nicht auf einen universellen Vorteil von Code Execution.

Ich vergleiche JSON Tool Calling, MCP, Skills, CLI Tools und Code Execution in dieser Reihenfolge. Ein späterer Abschnitt wendet die Designprinzipien des Agent-Computer Interface (ACI) auf den Market Analyst Agent an, einen kleinen LangGraph Research Agent, den ich für Teil 1 entwickelt habe und der Marktdaten abruft und einen Analystenbericht schreibt.

TL;DR: Fünf nützliche Interface-Patterns decken den Großteil von Tool Use in Agents ab. Skills transportieren Instructions, CLI Tools eignen sich für lokale Entwicklung, MCP verbindet gemeinsam genutzte Services, und Code Execution setzt Multi-Step-Arbeit innerhalb einer Sandbox zusammen. JSON Tool Calling bleibt die einfachste Wahl für kleine atomare Aktionen. Unabhängig vom Protocol muss das Agent-Computer Interface (ACI) Aktionen klar machen, Feedback kompakt halten und Fehler recoverbar machen.

Fünf Möglichkeiten, wie AI Agents Tools verwenden

In Teil 1 wählte der Reasoning Loop den nächsten Schritt. Teil 2 speicherte den Zustand, der für die Wiederaufnahme erforderlich war. Die Tool-Grenze liegt zwischen beiden: Sie validiert, was der Loop vorgeschlagen hat, leitet den Call anschließend zur Ausführung weiter und gibt das Ergebnis an den Loop zurück. Diese fünf Patterns treffen unterschiedliche Trade-offs bei Token-Kosten, Flexibilität und Durchsetzung.

1. JSON Tool Calling: die Baseline

Das ursprüngliche Pattern: Du definierst Tool Schemas als JSON, das LLM gibt strukturierte Function Calls aus, und dein Code führt sie aus. Dieses Vorgehen ist gut verstanden und funktioniert für kleine Toolsets problemlos.

# Traditional tool definition — each tool consumes ~550-1,400 tokens (Apideck benchmark)
tools = [
    {
        "name": "get_stock_price",
        "description": "Get the current stock price for a ticker symbol",
        "input_schema": {
            "type": "object",
            "properties": {
                "ticker": {"type": "string", "description": "Stock ticker (e.g., NVDA)"}
            },
            "required": ["ticker"]
        }
    }
]

Bei 5–10 Tools ist der Overhead akzeptabel. Das Problem ist die Skalierung: Jede Tool-Definition kostet 550–1.400 Tokens. Bei 20 Tools werden 11–28K Tokens verbraucht, bevor der Agent überhaupt mit dem Reasoning beginnt.

2. MCP für gemeinsam genutzte Integrationen

MCP ist der Standard, auf den sich die meisten Anbieter verständigt haben. Ein MCP Server ist ein Prozess, der über ein definiertes Wire Protocol eine Liste von Tools bereitstellt – stdio für einen lokalen Prozess, HTTP für einen Remote-Prozess. Dein Agent führt einen MCP Client aus, der eine Verbindung herstellt, den Server nach seinen Tools fragt und die Calls des Models an ihn weiterleitet. Dadurch funktioniert derselbe Server mit jedem Client, der das Protocol unterstützt. Anthropic übergab das Protocol im Dezember 2025 an die Linux Foundation – unter der Agentic AI Foundation, die das Unternehmen gemeinsam mit OpenAI und Block gegründet hat. Google, Microsoft und AWS unterstützen die Foundation als Platinum Members. OpenAI ergänzte MCP Support in seiner Responses API. Laut Anthropics Ankündigung der Übergabe im Dezember 2025 umfasste das Ökosystem mehr als 10.000 aktive öffentliche MCP Server und mehr als 97 Millionen monatliche SDK Downloads über die Python- und TypeScript-SDKs.

MCP eignet sich für SaaS-Integrationen über Anbietergrenzen hinweg (Figma, Notion, Salesforce), für Services ohne CLI-Äquivalent sowie für Umgebungen, die OAuth Orchestration benötigen. Sein Wert liegt in einer gemeinsamen Discovery- und Transport-Layer. Governance hängt weiterhin von den Authentication-, Authorization-, Logging- und Deployment-Kontrollen des Servers ab.

Die Production-Realität ist komplizierter, als die Schlagzeilenzahlen vermuten lassen.

Die Security Surface ist das erste Problem. Das Vulnerable MCP Project dokumentiert 50 Schwachstellen in MCP Servern, davon 13 mit der Einstufung Critical, die von 32 Security Researchers gemeldet wurden. Die Angriffsklassen reichen von Prompt Injection und Fehlern bei der Input-Validierung bis zu Authentication-Lücken und Schwachstellen in der Network Security. Der erste bösartige MCP Server in der Praxis tauchte im September 2025 auf: ein Package namens postmark-mcp, das jede ausgehende E-Mail per BCC an die Adresse eines Angreifers weiterleitete. Vor seiner Entdeckung waren schätzungsweise 300–500 Organisationen betroffen.

Tool Poisoning ist die Angriffsklasse, die mir am meisten Sorgen bereitet. Invariant Labs zeigte, dass vergiftete MCP Tools Daten exfiltrieren können, selbst wenn sie nie aufgerufen werden. Es reicht aus, dass das Model die Metadaten des Tools liest, um den Angriff auszulösen. Die MCPTox Benchmarks, die 20 LLM Agents gegen 45 MCP Server aus der Praxis testeten, ermittelten Attack Success Rates von bis zu 72,8 %.

Der Token-Overhead ist das operative Problem. Ein Team, das MCP Server für GitHub, Slack und Sentry betrieb (insgesamt etwa 40 Tools), stellte fest, dass 55.000 Tokens an Schema-Definitionen injiziert wurden, bevor ein User überhaupt eine Frage stellte. Ein anderes Team meldete, dass allein Tool-Definitionen 143.000 von 200.000 verfügbaren Tokens (72 %) verbrauchten.

Anthropic berichtete, dass sein Tool Search Tool die Tokens für Tool-Definitionen um 85 % reduziert – ungefähr 77.000 Tokens für Schemas auf 8.700 –, indem nur die drei bis fünf Tools geladen werden, die ein Request tatsächlich benötigt. Selektives Laden erhält die Protocol-Surface und entfernt gleichzeitig Schemas, die der aktuelle Request nicht benötigt.

3. Skills bündeln Expertise, nicht Execution

Ende 2025 wurden Agent Skills als offenes Format standardisiert (im Oktober 2025 eingeführt und im Dezember 2025 als offener Standard veröffentlicht). Tools stellen Capabilities bereit (was Agents tun können), während Skills Expertise liefern (was Agents darüber wissen, wie sie komplexe Tasks erledigen).

Das SKILL.md-Format definiert einen Skill als Markdown-Datei mit YAML Frontmatter. Der offene Standard verlangt nur name und description; das folgende Beispiel verwendet außerdem zwei Claude-Code-Erweiterungen, argument-hint und user-invocable, sowie den Positionsargument-Platzhalter $0:

---
name: deploy
description: Deploy the application to production
argument-hint: "[environment]"
user-invocable: true
---
Deploy the application to the $0 environment (default: staging).
Steps:
1. Run the test suite
2. Build the production bundle
3. Deploy using the deploy script
4. Verify the deployment health check

Skills verwenden Progressive Disclosure. Beim Startup werden etwa 100 Tokens Metadaten geladen; die vollständigen Instructions werden erst geladen, wenn der Skill aktiv ist. Zum Vergleich: Rund 55.000 Tokens können etwa 40 MCP Tools verbrauchen, bevor das Reasoning beginnt.

Bis März 2026 hatten Claude Code, OpenAI Codex CLI, Cursor, GitHub Copilot, Gemini CLI, Goose, Devin Desktop (damals Windsurf) und Roo Code das Format übernommen. Skills stehen neben einer umfassenderen Bewegung hin zu codegesteuerten Agent-Actions. Victor Dibia beschreibt deren Entwicklung von JSON Function Calls zu generiertem Code – dem Pattern, das Abschnitt 5 behandelt.

Verwende Skills für Domain Knowledge, Multi-Step-Prozeduren und wiederkehrende Aufgaben wie Database Migrations oder Payment Integrations. Sie eignen sich für Tasks, bei denen der Agent Instructions benötigt, wie er eine bestehende Capability verwendet.

4. CLI- und Shell-Tools

CLI Interfaces können im Context deutlich günstiger sein, wenn das Model den Befehl bereits kennt. Scalekit berichtete über einen Token-Unterschied von 4–32x zwischen seinen CLI- und MCP-Pfaden über 75 Runs hinweg. Diese Case Study misst die eigenen Tools und Tasks; sie ersetzt keinen Vergleich mit deinen eigenen Tool-Definitionen und Command Outputs.

Weit verbreitete, gut dokumentierte Commands wie git, docker, kubectl, gh, curl und jq benötigen oft nur wenig einführenden Schema-Text. Weniger bekannte oder interne CLIs brauchen weiterhin auffindbare Hilfe, Beispiele und stabilen maschinenlesbaren Output.

Ugo Enyiohas Guide „Writing CLI Tools That AI Agents Actually Want to Use“ formulierte acht Designregeln:

  1. Structured Output ist obligatorisch – unterstütze --json
  2. Exit Codes sind Control Flow – verwende unterschiedliche Codes für verschiedene Fehlertypen
  3. Commands sollten idempotent sein
  4. Self-Documenting --help mit realistischen Beispielen
  5. Für Composability designen – --quiet für reine Werte sowie stdin-Support
  6. --dry-run- und --yes-Flags bereitstellen
  7. Version Introspection unterstützen
  8. Authentication über Environment Variables abwickeln

CLI fehlt die Type Safety von MCP, die integrierte OAuth Orchestration, Tool Discovery und ein Audit Trail. Das Pattern, auf das sich die meisten Teams einigen: CLI als Default für Development und lokale Operations, MCP für die Integration externer Services und Enterprise Governance.

5. Code Execution für Multi-Step-Arbeit

Dies ist die folgenreichste Veränderung im Agent Tooling. Statt strukturiertes JSON auszugeben, um vordefinierte Funktionen einzeln aufzurufen, schreibt der Agent ein Python- oder Bash-Script. Das Script ruft mehrere Tools auf, verarbeitet Ergebnisse mit Loops und Conditionals und gibt nur die abschließende Zusammenfassung an den Model Context zurück.

Anthropic hat dieses Vorgehen mit Programmatic Tool Calling (PTC) formalisiert, das inzwischen allgemein in der Claude API verfügbar ist. Die akademische Grundlage bildet das CodeAct-Paper (Wang et al., ICML 2024). Es testete 17 LLMs und stellte fest, dass Code Actions bis zu 20 % höhere Task-Success-Rates und 30 % weniger Schritte als JSON-Alternativen erzielten.

Drei First-Party Case Studies zeigen, wo dieses Pattern helfen kann: unten Vercel und Cloudflare sowie anschließend das Beispiel zur Expense Analysis von Anthropic. Betrachte sie als Evidence der jeweiligen Anbieter und wiederhole den Vergleich mit deinen eigenen Tasks.

  • Vercel hat d0, seinen Natural-Language-to-SQL Data Agent, neu entwickelt und ihn von 15 Tools auf 2 reduziert – ExecuteCommand und ExecuteSQL –, was laut dem eigenen Post einer Reduktion um 80 % entspricht. Über fünf repräsentative Queries stieg der Task Success von 4/5 auf 5/5, die durchschnittliche Execution Time sank um den Faktor 3,5 (274,8 s auf 77,4 s), und der durchschnittliche Token-Verbrauch fiel um 37 % (etwa 102K auf etwa 61K). Die Formulierung von Vercel: „Die besten Agents könnten diejenigen mit den wenigsten Tools sein.“

  • Cloudflare entwickelte „Code Mode“, mit dem Agents TypeScript schreiben können, um die API aufzurufen, anstatt Tool Schemas zu definieren. Dadurch sinkt der Context-Overhead. Die Begründung: „LLMs haben enorme Mengen an realem TypeScript in ihren Trainingsdaten, aber nur eine kleine Zahl konstruierter Beispiele für Tool Calls.“

Hier ist das Pattern aus Anthropics PTC-Dokumentation. Traditionelles Tool Calling für Expense Analysis erfordert mehr als 20 separate Inference Passes – einen pro Teammitglied –, wobei alle Zwischenresultate durch den Context fließen. Anthropic berichtet, dass generierter Code bei derselben Frage den Inhalt, der den Context erreicht, von 200 KB rohen Expense Rows – mehr als 2.000 Line Items – auf 1 KB Ergebnisse reduziert. Mit Code Execution schreibt der Agent ein einzelnes Script:

# Agent generates this code, executes in sandbox
import json
members = get_team_members("engineering")
over_budget = []
for m in members:
    expenses = get_expenses(m["id"], "Q3")
    total = sum(e["amount"] for e in expenses)
    if total > 5000:
        custom = get_custom_budget(m["id"])
        limit = custom["limit"] if custom else 5000
        if total > limit:
            over_budget.append({"name": m["name"], "spent": total, "limit": limit})
# Only this final summary returns to the LLM context
print(json.dumps(over_budget))

Das LLM sieht nur die abschließende JSON-Zusammenfassung, nicht die Tausenden von Expense Line Items, die in der Sandbox verarbeitet wurden. Die Einsparung ist nicht spezifisch für Expense Reports: Anthropics separate Beschreibung von Code Execution nennt als prägnanteste Zahl einen Google-Drive-to-Salesforce-Workflow, der von etwa 150.000 Tokens auf etwa 2.000 fiel – eine Reduktion um 98,7 %.

Token-Effizienz ist der offensichtliche Vorteil. Loops und Conditionals sind praktisch kostenlos, Fehler laufen über try/except statt über Natural-Language-Reasoning zu Fehlern, und sensible Daten bleiben in der Sandbox.

Wann JSON Tool Calling weiterhin sinnvoll ist: bei einzelnen atomaren Operations, in Umgebungen ohne Sandbox-Infrastruktur, bei kleineren Models mit schwacher Code-Generierung oder bei Audit-Anforderungen, die verlangen, dass jeder einzelne Tool-Aufruf protokolliert wird.

„Meta-Tools“ in der Zeile zum Token-Overhead bezeichnet die wenigen generischen Entry Points, die ein Code-executing Agent benötigt – beispielsweise Vercels ExecuteCommand und ExecuteSQL – anstelle eines Schemas pro zugrunde liegender Operation. Die Token- und Task-Success-Zellen fassen die zitierten Beispiele zusammen und stellen keinen kontrollierten Benchmark über alle fünf Spalten dar.

Das Agent-Computer Interface (ACI) für AI-Agent-Tools

Der Begriff „Agent-Computer Interface“ (ACI) wurde von John Yang, Carlos E. Jimenez und Kollegen an der Princeton University in ihrem SWE-agent-Paper (NeurIPS 2024) geprägt. Die Qualität menschlicher Interfaces hat mit Human-Computer Interaction (HCI) ein eigenes Fachgebiet. Das Paper argumentiert, dass Language-Model Agents dieselbe Behandlung verdienen: Sie seien „eine neue Kategorie von End Usern mit eigenen Anforderungen und Fähigkeiten und würden von speziell entwickelten Interfaces profitieren“.

Ihre Ablation Results quantifizieren diesen Effekt. SWE-agent mit vollständigem ACI erzielte 18,0 % auf SWE-bench Lite, einem Set aus 300 realen GitHub Issues, die ein Agent tatsächlich beheben muss. Ein Shell-only Agent ohne Worked Demonstration erreichte 7,3 % und mit einer Demonstration 11,0 %. Gegenüber der Baseline ohne Demonstration entspricht das einem Zugewinn von 10,7 Prozentpunkten allein durch Interface Design; gegenüber der Demonstrations-Baseline sind es 7,0 Punkte. In beiden Fällen leistet das Interface, nicht das Model, die entscheidende Arbeit. Der Linting Check allein machte 3 Prozentpunkte aus und hatte reichlich zu tun: Über den vollständigen SWE-bench-Testdatensatz hinweg enthielten 51,7 % der SWE-agent-Runs mindestens eine Änderung, die der Linter ablehnte, bevor sie sich weiter ausbreiten konnte.

Anthropic übernahm ACI als grundlegendes Konzept in seinem Guide „Building Effective Agents“ und führt es als eines von drei Kernprinzipien auf: „Entwickle dein Agent-Computer Interface sorgfältig durch umfassende Tool-Dokumentation und Tests.“ Die praktische Empfehlung lautet: „Eine Faustregel ist, darüber nachzudenken, wie viel Aufwand in Human-Computer Interfaces fließt, und genauso viel Aufwand für die Entwicklung guter Agent-Computer Interfaces einzuplanen.“

Vier ACI-Prinzipien in der Praxis

1. Actions sollten einfach und leicht verständlich sein. Der häufigste Fehler besteht darin, API Endpoints eins zu eins zu kapseln. Anstatt list_users, list_events und create_event zu verwenden, implementiere schedule_event, das Availability findet und in einem Call einen Termin plant. Anstatt read_logs zu verwenden, implementiere search_logs, das nur die relevanten Zeilen mit Context zurückgibt.

2. Actions sollten kompakt und effizient sein. Fasse wichtige Operations in so wenigen Actions wie möglich zusammen. Im Market Analyst Agent kombiniere ich das Abrufen von Preisen mit grundlegenden Metrics in einem einzigen get_stock_snapshot Tool, statt separate Calls für Preis, Volumen, Market Cap und PE Ratio zu verlangen.

3. Environment Feedback sollte informativ, aber prägnant sein. Vermeide die Rückgabe von rohem HTML oder vollständigen API Payloads. Löse kryptische IDs in semantische Namen auf. Anthropics Tests ergänzten ein response_format Enum, sodass der Agent eine kompakte (etwa 72 Tokens) oder detaillierte (etwa 206 Tokens) Antwort anfordern kann – ungefähr ein Unterschied von 3x bei den Token-Kosten.

4. Validation sollte Error Propagation eindämmen. Automatische Error Detection hilft Agents, Fehler schnell zu erkennen und zu korrigieren. In SWE-agent lehnt ein Custom File Editor mit integriertem Linting Syntaxfehler automatisch ab – der Validation Step hinter der oben genannten Zahl von 51,7 %. Hier geht es um die Validation der Inputs und Outputs eines Tools, nicht um das Content Filtering rund um einen Model Call, das die Guardrail-Produkte in Teil 4 übernehmen; dasselbe Wort wird für beides verwendet. Im Market Analyst Agent wende ich dasselbe Prinzip an, indem ich Tool Arguments vor der Ausführung mit Pydantic Schemas validiere:

from pydantic import BaseModel, Field, field_validator

class StockQuery(BaseModel):
    """Validated input for stock queries.

    Pydantic catches malformed tickers before the API call,
    preventing error propagation through the reasoning loop.
    """
    ticker: str = Field(description="Stock ticker symbol (e.g., NVDA)")
    period: str = Field(default="1mo", description="Time period: 1d, 5d, 1mo, 3mo, 6mo, 1y")

    @field_validator("ticker")
    @classmethod
    def validate_ticker(cls, v: str) -> str:
        v = v.upper().strip()
        if not v.isalpha() or len(v) > 5:
            raise ValueError(f"Invalid ticker format: {v}")
        return v

    @field_validator("period")
    @classmethod
    def validate_period(cls, v: str) -> str:
        valid = {"1d", "5d", "1mo", "3mo", "6mo", "1y"}
        if v not in valid:
            raise ValueError(f"Invalid period: {v}. Must be one of {valid}")
        return v

AI-Agent-Tool-Design-Patterns, die funktionieren

Anthropics Guide „Writing effective tools for agents“ beschreibt Tools als „eine neue Art von Software, die einen Vertrag zwischen deterministischen Systemen und nichtdeterministischen Agents abbildet“.

Behandle Tool Descriptions als Prompt Engineering

Descriptions sollten mindestens drei oder vier Sätze umfassen und erklären, wann das Tool verwendet werden sollte, welche Parameter erforderlich bzw. optional sind, welches Output-Format gilt und welche Edge Cases existieren. Anthropic berichtet, dass die Wahl zwischen Prefix- und Suffix-basiertem Namespacing (asana_search gegenüber search_asana) bei den eigenen Tool-Use-Evals „nichttriviale Effekte“ hatte. Es wird nicht angegeben, welches Schema gewinnt. Teste daher beide mit deinem Toolset, statt Prefixes vorauszusetzen. Anthropic gab außerdem die Transcripts seiner Eval Agents an Claude Code zurück und ließ die Tools umschreiben. Auf zurückgehaltenen Testsets fand dieser Loop weitere Verbesserungen, „die sogar über das hinausgingen, was wir mit von Experten implementierten Tools erreicht hatten“ – unabhängig davon, ob die Tools von den eigenen Researchern geschrieben oder von Claude generiert worden waren.

# Bad: vague, no context for when to use
tools = [{
    "name": "search",
    "description": "Search for items",
}]

# Good: specific, with input examples and edge cases
tools = [{
    "name": "search_news",
    "description": (
        "Search for recent news articles about a specific stock or company. "
        "Use this tool when the user asks about recent events, earnings, "
        "announcements, or market-moving news for a specific ticker. "
        "Returns up to 10 articles sorted by relevance. "
        "For company competitors rather than news, use search_competitors instead."
    ),
    "input_schema": {
        "type": "object",
        "properties": {
            "query": {
                "type": "string",
                "description": "Search query. Examples: 'NVDA earnings Q3 2025', 'Tesla delivery numbers'"
            },
            "max_results": {
                "type": "integer",
                "description": "Max articles to return (1-10, default 5)",
                "default": 5
            }
        },
        "required": ["query"]
    }
}]

Anthropics interne Tests zeigten, dass das Hinzufügen eines input_examples-Felds die Accuracy bei komplexem Parameter Handling von 72 % auf 90 % erhöhte.

Gib signalreichen, maschinenlesbaren Output zurück

Vermeide Low-Level-Identifier (uuid, mime_type). Löse kryptische IDs in semantische Namen auf. Strukturiere die Response so, dass der Agent darüber Reasoning betreiben kann, ohne Boilerplate parsen zu müssen:

# Bad: raw API response dumped to agent
def get_stock_snapshot(ticker: str) -> dict:
    response = api.get(f"/v1/quotes/{ticker}")
    return response.json()  # 500+ tokens of nested JSON

# Good: high-signal summary the agent can immediately reason about
def get_stock_snapshot(ticker: str) -> dict:
    data = api.get(f"/v1/quotes/{ticker}").json()
    return {
        "ticker": ticker,
        "price": data["regularMarketPrice"],
        "change_pct": round(data["regularMarketChangePercent"], 2),
        "volume": data["regularMarketVolume"],
        "market_cap_b": round(data["marketCap"] / 1e9, 1),
        "pe_ratio": data.get("trailingPE"),
        "summary": f"{ticker} at ${data['regularMarketPrice']:.2f} "
                   f"({'up' if data['regularMarketChangePercent'] > 0 else 'down'} "
                   f"{abs(data['regularMarketChangePercent']):.1f}%)"
    }

Gib Fehler zurück, mit denen der Loop arbeiten kann

Error Handling benötigt vier separate Mechanismen, da sie unterschiedliche Fehlerklassen behandeln:

  1. Retries mit Exponential Backoff für transiente Fehler
  2. Model-Fallback-Chains bei Ausfällen von Providern
  3. Error-Classification-Routing – transiente Fehler werden erneut versucht, durch LLMs recoverbare Fehler gehen mit Context an den Agent zurück, und Fehler, die einen Menschen erfordern, werden eskaliert
  4. Checkpoint Recovery zur Überlebensfähigkeit bei Crashes

Anthropics „Writing effective tools for agents“ empfiehlt klare Tool Errors und Eval-driven Tool Design, nennt aber keine universelle Zahl dafür, wie viele Fehler diese vier Mechanismen beheben. Miss Recovery Rate, Retries und Escalations auf deiner eigenen Task Suite.

import httpx
from tenacity import retry, stop_after_attempt, wait_exponential

@retry(
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=1, min=2, max=10),
)
def call_stock_api(ticker: str) -> dict:
    """Fetch stock data with automatic retry on transient failures.

    Mechanism 1 of the four above: exponential backoff for rate limits
    and network blips.
    If all retries fail, the error propagates to the agent with
    enough context to decide whether to try a different approach.
    """
    response = httpx.get(
        f"https://api.example.com/v1/quotes/{ticker}",
        timeout=10.0,
    )
    response.raise_for_status()
    return response.json()

Anwendung der Patterns auf den Market Analyst Agent

Der Market Analyst Agent aus Teil 1 macht den Effekt des Interfaces sichtbar.

Tool Consolidation

Das ursprüngliche Design hatte mehr als 10 Tools: get_stock_price, get_company_metrics, get_market_cap, get_pe_ratio, get_volume und weitere. Jedes war ein dünner Wrapper um einen einzelnen API Endpoint. Der Agent musste für jeden Request überlegen, welche Kombination aufgerufen werden sollte.

Ich habe die Market-Data-Surface gemäß dem ACI-Prinzip kompakter und effizienter Actions auf 5 High-Level-Tools konsolidiert. Die ReAct-Tool-Liste des Repositories enthält daneben vier weitere Tools – einen Skill Loader, zwei CLI Wrapper und einen eingeschränkten In-Process-Python-Evaluator (eine AST-Allowlist, keine Sandbox; Teil 4 behandelt das näher) – und deckt damit drei der fünf oben beschriebenen Modalities ab. MCP erscheint als Sidecar und nicht als Tool in dieser Liste:

Vorher (10+ Tools)Nachher (5 Tools)Warum
get_stock_price + get_company_metrics + get_pe_ratioget_stock_snapshotEin Call liefert alles, was für eine grundlegende Analyse benötigt wird
get_price_history + get_volume_historyget_price_historyMit konfigurierbarem Zeitraum und Indicators kombiniert
search_news + search_press_releasessearch_newsEinheitliche Suche mit Source Filtering
search_competitors + get_sector_datasearch_competitorsGibt Wettbewerber mit relativen Metrics zurück
get_financials + get_balance_sheet + get_cash_flowget_financialsMit dem Parameter statement_type vereinheitlicht

Dadurch sanken der Overhead der Tool Schemas und in meinen eigenen Tests auch die Zuverlässigkeit der Tool-Auswahl, da weniger mehrdeutige Optionen zur Verfügung standen.

Structured Outputs für Tool Results

Jedes Tool im Market Analyst Agent gibt eine Pydantic-validierte Response zurück. Damit wird das ACI-Validation-Prinzip auf den Output des Tools angewendet:

class StockSnapshot(BaseModel):
    """Structured tool response — the agent never sees raw API noise."""
    ticker: str
    price: float
    change_pct: float
    volume: int
    market_cap_b: float
    pe_ratio: float | None
    summary: str  # Human-readable one-liner for direct use in reports

class NewsResult(BaseModel):
    """Each news item is pre-processed for agent consumption."""
    headline: str
    source: str
    date: str
    relevance_score: float  # Pre-ranked so the agent doesn't waste tokens sorting
    key_points: list[str]  # Extracted by the tool, not the agent

Das Feld summary ist am wichtigsten. Es gibt dem Agent einen direkt verwendbaren String, der ohne weitere Verarbeitung in einen Report übernommen werden kann. Die key_points in NewsResult werden vom Tool und nicht vom Agent extrahiert. Dadurch muss der Agent keine Inference Tokens für das Parsen von Article Bodies aufwenden.

Trade-offs und Überlegungen

Neben den spezifischen Einschränkungen der einzelnen Patterns prägen einige übergreifende Aspekte die Auswahl:

  • Die operativen Kosten unterscheiden sich je nach Dimension. Code Execution spart Tokens, fügt aber Sandbox-Cold-Start-Latency hinzu. MCP spart Entwicklungszeit bei SaaS-Integrationen, erhöht jedoch den Aufwand für das Deployment von Servern. CLI ist schnell und kostenlos einsetzbar, aber bei einer Skalierung schwieriger zu governieren. Optimiere für deinen tatsächlichen Bottleneck – unabhängig davon, ob es Token-Kosten, Latency oder operative Komplexität sind.

  • Team Skills sind relevant. Code Execution setzt voraus, dass deine Agents (und die dahinterliegenden Models) zuverlässiges Python oder TypeScript generieren können. CLI setzt Vertrautheit mit Unix-Konventionen voraus. MCP erfordert Verständnis von Transport Protocols und OAuth Flows. Wähle die Modality passend zu den Stärken deines Teams.

  • Tool Consolidation kann zu weit gehen. Wenn ein Tool nicht zusammenhängende Modi und Arguments anhäuft, entsteht ein anderes Selection-Problem innerhalb des Schemas. Nutze Tool-Selection- und Task-Success-Evals, um die richtige Surface für deinen Workload zu finden.

  • Skills sind promptbasiert, nicht erzwungen. Ein Skill enthält Instructions, denen der Agent folgen sollte, keine Guardrails, denen er folgen muss. Für kritische Workflows solltest du Skills mit deterministischer Validation kombinieren.

  • Audit-Anforderungen beeinflussen die Auswahl. Wenn du ein vollständiges Log jedes Tool-Aufrufs und seines Results benötigst, liefern MCP und JSON Tool Calling strukturierte Audit Trails direkt mit. Code Execution erzeugt ein Script und dessen Output. Das ist nützlich, aber für Compliance Reports schwieriger in einzelne Actions zu zerlegen.

Drei Richtungen für AI-Agent-Tooling im großen Maßstab

Die erste ist Tool RAG für die Skalierung. Wenn Toolsets auf Hunderte oder Tausende anwachsen, sinkt die Accuracy naiver Tool Selection auf 13,62 %. Das RAG-MCP-Paper wandte Retrieval-Augmented Generation auf die Tool Selection an: Die Tool Descriptions werden in einer Vector Database indexiert und pro Query nur die relevanten Tools abgerufen. Dadurch wurde eine Accuracy von 43,13 % erreicht – eine Verbesserung um den Faktor 3,2 –, während die Prompt Tokens um etwa 50 % sanken.

Die zweite Richtung sind Agents, die ihre eigenen Tools erstellen. Das LATM-Framework („LLMs As Tool Makers“) etablierte ein Zwei-Phasen-Paradigma, bei dem ein leistungsfähiges LLM wiederverwendbare Python-Funktionen erstellt und ein kleineres LLM sie verwendet. ToolMaker (ACL 2025) transformiert GitHub-Repositories autonom in LLM-kompatible Tools und erreicht dabei eine Success Rate von 80 %. Beide Ansätze weisen über Tool Use hinaus in Richtung Tool Creation und anschließend in Richtung Management einer Bibliothek generierter Tools.

Die dritte Richtung ist der duale A2A- und MCP-Protocol-Stack. Das von Google entwickelte und im Juni 2025 an die Linux Foundation übergebene Agent2Agent Protocol (A2A) adressiert, was MCP nicht abdeckt: Agent-to-Agent Communication. MCP übernimmt die Integration von Agent und Tool; A2A übernimmt Agent-to-Agent Discovery, Negotiation und Task Delegation.

Zentrale Erkenntnisse

  1. Wähle das Interface passend zur Action: JSON Calling für kleine typisierte Operations, MCP für gemeinsam genutzte Services, Skills für Prozeduren, CLI für etablierte Commands und sandboxed Code für lokale Composition.
  2. Halte die Benchmark-Bedingungen beim Ergebnis fest. CodeAct, Anthropic, Vercel, Cloudflare, Apideck und Scalekit haben unterschiedliche Models, Tasks, Tools und Harnesses gemessen.
  3. ACI-Qualität bleibt auch bei Protocol-Änderungen erhalten. Klare Actions, kompaktes Feedback, Validation und hilfreiche Errors unterstützen jede Modality.
  4. Konsolidiere überlappende Tools nur dann, wenn Evals zeigen, dass die kleinere Surface die Selection oder den Task Success verbessert.
  5. Mehr Execution Power bedeutet mehr Security-Anforderungen. Shell- und Code-Interfaces benötigen Sandboxing; MCP braucht Scoped Identity und Server Policy; Skills bleiben Instructions und sind keine Enforcement-Mechanismen.

Die nächste Layer ist Policy

Teil 4, AI Agent Security, platziert einen Policy Check zwischen einem vorgeschlagenen Tool Call und dessen Execution. Es handelt sich um dieselbe oben beschriebene Tool-Grenze, diesmal aus der Perspektive, die „Nein“ sagt. Teil 5 platziert anschließend das Tool und seine Sandbox in einem recoverbaren Runtime; Teil 6 ergänzt einen zweiten Vertrag, den das Model nie sieht: eine Effect Category, eine Retry Rule und ein strukturiertes Result, das ein Acceptance Check lesen kann, ohne Prose parsen zu müssen.
