Teil I — Hardware-Grundlagen

Die Konzepte dieses Teils – Arithmetic Intensity, die GPU Memory Hierarchy und die Hardware-Begriffe – tauchen im gesamten restlichen Guide auf.

1. Memory-bound vs. Compute-bound und das Roofline Model

Der Ausgangspunkt für LLM-Performance ist Arithmetic Intensity: Wie viele nützliche Berechnungen führt die GPU für jedes Byte an Daten aus, das sie aus dem Memory lädt? Dieses Verhältnis entscheidet, ob eine Operation Compute-bound ist (Warten auf den Prozessor) oder Memory-bound (Warten auf das Laden der Daten).

Jede GPU hat einen Schwellenwert für die „Critical Intensity“, bei dem ihre Compute-Kapazität exakt ihre Memory Bandwidth ausgleicht. Für eine NVIDIA H100 SXM im Sparse-TF32-Modus (NVIDIA H100 specifications) gilt:

989 TFLOPS3.35 TB/s≈295 FLOPs/byte\frac{989 \text{ TFLOPS}}{3.35 \text{ TB/s}} \approx 295 \text{ FLOPs/byte}3.35 TB/s989 TFLOPS​≈295 FLOPs/byte

Batch-one Decode sowie langes oder ausreichend gebatchtes Prefill liegen typischerweise auf entgegengesetzten Seiten dieses Schwellenwerts:

  • Decode ist Memory-bound. Bei der Token-Generierung nacheinander wird die mehrere Gigabyte große Weight Matrix aus dem Memory geladen, um sie mit einem einzelnen neuen Token zu multiplizieren. In einer vereinfachten 16-Bit-Analyse mit Batch-one liegt die Operation bei etwa 1 FLOP/Byte, also fast 300-mal unterhalb des Roofline-Schwellenwerts der H100. Diese Lücke erklärt, warum Decode in diesem Regime den maximalen Compute-Throughput nicht annähernd erreicht.
  • Langes oder ausreichend gebatchtes Prefill ist oft Compute-bound. Bei der Verarbeitung vieler Prompt-Tokens werden Weights in großen Matrix-Multiplications wiederverwendet, wodurch die Arithmetic Intensity über den Roofline-Schwellenwert steigen kann. Kurze Prompts und kleine Batches können stattdessen durch Memory Traffic oder Kernel-Launch-Overhead begrenzt sein.

Um Decode zu beschleunigen, arbeiten Sie an der Memory Bandwidth: Verkleinern Sie die Weights mit Quantization, reduzieren Sie den KV-Memory-Overhead mit GQA und PagedAttention und erhöhen Sie die Intensity mit Batching. Für lange oder gut gebatchte Prefills können schnellere Matrix-Berechnungen und Compute mit niedrigerer Precision helfen; profilieren Sie Workloads mit kurzem Prefill separat.

2. GPU Memory Hierarchy

Eine GPU besitzt vier Memory Layers, die wie eine Pyramide angeordnet sind: Unten befindet sich ein großer, aber langsamer Main Memory (HBM), oben winzige, aber sehr schnelle Registers. Der Datentransfer durch diese Hierarchie ist eine wesentliche Performance-Constraint.

Von schnell nach langsam auf einer H100:

  1. Registers sind der schnellste Memory und direkt an Processing Threads angebunden. Bei Hoppers WGMMA kann Matrix A aus Registers oder Shared Memory kommen, während Matrix B aus dem Shared Memory kommt.
  2. SRAM (Shared Memory) ist schneller On-Chip-Working-Memory, der lokal für jeden SM verfügbar ist.
  3. L2 Cache ist eine gemeinsame 50-MB-Schicht. Er kann Daten bedienen, die über mehrere SMs hinweg wiederverwendet werden, ohne einen weiteren HBM-Fetch.
  4. HBM3 ist der 80 GB große Main Memory, der Model Weights und den KV cache enthält, mit ~3,35 TB/s Bandwidth.

FlashAttention und Kernel Fusion reduzieren den HBM Traffic, indem sie Zwischenresultate On-Chip behalten oder mehrere Operationen zusammenfassen. PagedAttention adressiert ein anderes Problem: Es mappt logische KV-Blöcke auf nicht zusammenhängende physische GPU-Memory-Blöcke, reduziert Fragmentation und ermöglicht Block-Sharing.

3. GPU-Hardware-Glossar

Die folgenden Begriffe tauchen im restlichen Guide immer wieder auf.

HBM (High Bandwidth Memory) stapelt DRAM-Dies, die über Through-Silicon Vias (TSVs) neben dem GPU-Die angebunden sind. Zu den Generationen gehören HBM2e (A100, 2 TB/s), HBM3 (H100, 3,35 TB/s) und HBM3e (H200/B200, 4,8–8 TB/s). Die HBM Bandwidth ist in Memory-bound-Decode-Regimes eine direkte Constraint für TPOT.

GDDR (Graphics DDR) ist traditioneller Graphics Memory, der in Consumer- und Workstation-GPUs wie RTX 4090 und L40S eingesetzt wird. Er hat eine geringere Bandwidth als HBM, kostet aber weniger pro GB. GDDR6X auf der RTX 4090 liefert ungefähr 1 TB/s gegenüber 3,35 TB/s HBM3-Bandwidth bei der H100.

Ein SM (Streaming Multiprocessor) ist der grundlegende Compute-Block in einer NVIDIA GPU. Jeder SM enthält CUDA Cores, Tensor Cores, Shared Memory und einen Warp Scheduler. Die H100 besitzt 132 SMs, die A100 108.

Tensor Cores sind spezialisierte Matrix-Multiply-Accumulate-Einheiten innerhalb jedes SM. Sie beschleunigen Mixed-Precision-MatMuls, die den Großteil der Transformer-Berechnungen ausmachen. Die Tensor Cores der H100 SXM liefern 494,5 dichte oder 989 Sparse-TF32-TFLOPS; beim Vergleich dieser Zahl müssen Precision und Sparsity-Modus immer angegeben werden.

CUDA Cores sind universelle Floating-Point- und Integer-Einheiten. Sie verarbeiten Element-wise-Operationen, Activation Functions und andere Nicht-Matrix-Arbeiten, während Tensor Cores unterstützte Matrix-Operationen ausführen.

Ein Warp ist eine Gruppe aus 32 Threads, die auf einem SM synchron ausgeführt werden, und damit die kleinste Scheduling-Einheit von NVIDIA. Warp Specialization weist verschiedene Warps Data Movement und Compute zu, sodass diese Aufgaben überlappen können.

NVLink ist NVIDIAs schneller GPU-to-GPU-Interconnect innerhalb eines Nodes. NVLink 4.0 auf der H100 liefert 900 GB/s bidirektionale Bandwidth; NVLink 5.0 auf der B200 erreicht 1,8 TB/s. Diese Bandwidth ist für Tensor Parallelism relevant, weil GPUs in jedem Transformer-Layer Teilergebnisse austauschen.

InfiniBand ist eine schnelle Network Fabric für die Inter-Node-Kommunikation. InfiniBand-Adapter der ConnectX-Klasse stellen die Inter-Node-Fabric für Pipeline-Parallel- oder Distributed-Training-Traffic bereit; die Bandwidth hängt von Adapter und Port-Konfiguration ab.

RDMA (Remote Direct Memory Access) ermöglicht einem Device, auf Memory eines anderen Rechners zuzugreifen, ohne den Datenpfad über eine CPU zu führen. GPUDirect RDMA unterstützt direkte GPU-to-GPU-Transfers über Nodes hinweg, einschließlich KV-cache-Transfers bei Disaggregated Serving.

NVMe (Non-Volatile Memory Express) ist die SSD-Schnittstelle für KV-cache-Offloading und ZeRO-Infinity-Parameter-Offloading, wenn GPU- und CPU-Memory nicht ausreichen. Die sequenzielle Bandwidth hängt von Drive und Workload ab und liegt weiterhin deutlich unter der HBM Bandwidth.

TFLOPS und PFLOPS sind Billionen beziehungsweise Billiarden Floating-Point-Operationen pro Sekunde. Ein TFLOPS entspricht 101210^{12}1012 FLOPS. Die H100 erreicht 989 Sparse-TF32-Tensor-TFLOPS, während FlashAttention-3 etwa 1,2 PFLOPS in FP8 meldet; diese Werte verwenden unterschiedliche Formate und sollten nicht als dieselbe Metrik verglichen werden.

Teil II — Inference-Grundlagen

Inference ist der Teil des Systems, den Nutzer tatsächlich spüren. Latency, der KV cache, das Zwei-Phasen-Ausführungsmodell, Attention und Quantization bestimmen gemeinsam, wie schnell, günstig und zuverlässig Sie serven können.

4. Latency: TTFT, TPOT und Percentiles

Time to First Token (TTFT) ist die End-to-End-Verzögerung vom Absenden eines Requests bis zum ersten Output-Token. Sie umfasst Queueing, Tokenization, Scheduling, Prompt-Prefill, den ersten Decode-Schritt und Network Delivery. Längere Prompts erhöhen normalerweise den Prefill-Anteil, aber jede dieser Phasen kann dominieren. Ziele sind produktspezifisch; MLPerf Inference v5.0 verwendet für sein interaktives Llama-2-70B-Szenario ein P99-TTFT-Limit von ≤\leq≤ 450 ms.

Time Per Output Token (TPOT) ist das durchschnittliche Intervall zwischen aufeinanderfolgenden Tokens nach dem ersten. Es entspricht der Decode-Phase. Decode mit Batch-one oder niedriger Intensity ist üblicherweise Memory-Bandwidth-bound, während ausreichend große Batches Compute-bound werden können:

TPOT=E2E Latency−TTFTOutput Tokens−1\text{TPOT} = \frac{\text{E2E Latency} - \text{TTFT}}{\text{Output Tokens} - 1}TPOT=Output Tokens−1E2E Latency−TTFT​

Diese Definition setzt mindestens zwei Output-Tokens voraus; für eine One-Token-Response ist TPOT nicht definiert.

Die durchschnittliche stille Lesegeschwindigkeit von Erwachsenen auf Englisch liegt bei ungefähr 238 Wörtern pro Minute für Sachtexte (Brysbaert, 2019). Streaming-Ziele sollten dennoch aus Product Testing abgeleitet werden; MLPerf verwendet für sein interaktives Szenario ein P99-TPOT-Limit von ≤\leq≤ 40 ms.

P50- vs. P99-Latency ist relevant, weil der Median den Tail verbirgt. Ein System mit gutem P50 und schlechtem P99 kann Probleme mit Batching, Preemption, Queueing oder Workload-Skew haben; um zwischen diesen Ursachen zu unterscheiden, sind Traces erforderlich.

5. Throughput: Tokens pro Sekunde und der Latency-Trade-off

Throughput wird als Output-Tokens pro Sekunde über concurrent Requests gemessen. Requests pro Sekunde sind allein eine schwächere Metrik, weil eine 10-Token-Response und eine 1.000-Token-Response sehr unterschiedliche Kosten verursachen. Vergleichen Sie vLLM, SGLang und TensorRT-LLM mit demselben Harness, statt ihre Headline-Ergebnisse zu kombinieren.

Der Trade-off: Bei niedriger Concurrency erhält jeder Request eine sehr gute Latency, aber die GPU ist unterausgelastet. Eine Erhöhung der Batch Size steigert den Throughput nahezu linear, bis der Compute saturiert; danach steigt die Latency stark an. Goodput, also die Rate von Requests pro Sekunde, die Ihre SLO-Ziele erfüllen, verbindet den rohen Throughput mit der tatsächlichen User Experience.

6. KV cache: der Bottleneck hinter den meisten anderen Bottlenecks

Bei autoregressiver Generation attendet jeder neue Token auf alle vorherigen Tokens. Der KV cache speichert die Key- und Value-Projections jedes Tokens in jedem Layer, um O(n2)O(n^2)O(n2) eine erneute Berechnung zu vermeiden. Ohne ihn müsste die Generierung von Token nnn das Model über alle n−1n-1n−1 vorherigen Tokens erneut ausführen.

Der KV cache kann bei langen Sequence Lengths oder hoher Concurrency zum dominierenden variablen Memory Pressure werden, weil er linear mit Sequence Length, Batch Size und Layer-Anzahl wächst:

KVcache=2×L×hkv×dh×s×B×bytesKVcache = 2 \times L \times h_{kv} \times d_h \times s \times B \times \text{bytes}KVcache=2×L×hkv​×dh​×s×B×bytes

wobei:

  • LLL = Anzahl der Layers
  • hkvh_{kv}hkv​ = Anzahl der KV-Heads
  • dhd_hdh​ = Head Dimension
  • sss = Sequence Length
  • BBB = Batch Size
  • bytes\text{bytes}bytes = Bytes pro gecachtem Element, festgelegt durch die KV-cache-Precision

Konkrete Beispiele mit FP16 und Batch Size 1: Llama 3.1 8B benötigt bei 8.192 Tokens etwa 1,0 GB KV cache, bei 128K Tokens 16 GB. Llama 3.1 70B benötigt bei 128K Tokens für eine einzelne Sequence ~40 GB, also die Hälfte des VRAM einer H100. Bei hoher Concurrency oder langem Context kann der KV cache den Memory-Bedarf der Model Weights übersteigen; das Ergebnis hängt von Sequence Length, aktiver Batch Size, KV-Precision und der Anzahl der KV-Heads ab. Naive Implementierungen verschwenden durch Fragmentation 60–80 % des allozierten KV-Memory – genau dieses Problem soll PagedAttention lösen.

Die wichtigsten Optimierungen sind GQA (weniger KV-Heads), KV-cache-Quantization (FP8/INT8), PagedAttention (Block-basierte Allocation mit <4 % Waste) sowie das Offloading des KV cache auf CPU oder NVMe.

7. Prefill vs. Decode: zwei Phasen, zwei Bottlenecks

Die Prefill-Phase verarbeitet den Input-Prompt parallel und befüllt den KV cache. Langes oder ausreichend gebatchtes Prefill wird oft Compute-bound, weil es große Matrix-Multiplications verwendet; kurzes Prefill kann weiterhin durch Memory Traffic oder Kernel-Launch-Overhead begrenzt sein. Prefill trägt neben Queueing, Tokenization, Scheduling, dem ersten Decode-Schritt und Network Delivery zu Time to First Token (TTFT) bei. Die Decode-Phase generiert jeweils einen Token. Jeder Schritt liest Model Weights und den KV cache aus HBM, wodurch Batch-one Decode Memory-Bandwidth-bound und zum Haupttreiber von Time Per Output Token (TPOT) wird.

Chunked Prefill teilt den Prompt in Blöcke fester Größe auf, statt ihn vollständig auf einmal zu verarbeiten. Ein Scheduler kann diese Chunks mit Decode-Arbeit verschachteln, sodass ein langer Prompt keine Iteration monopolisiert. Sarathi-Serve berichtet in den getesteten Workloads bessere Throughput-Latency-Trade-offs, aber der Gewinn hängt von Model, Hardware, Request-Length-Verteilung, Chunk Size und Vergleichs-Baseline ab. Zusätzliches Scheduling und kleinere Kernels können TTFT für den neuen Request erhöhen.

Disaggregated Serving platziert Prefill und Decode auf getrennten GPU-Pools, sodass jeder Pool auf einen anderen Bottleneck optimieren kann. Splitwise und DistServe beschreiben dieses Pattern. Die Pools übertragen KV-cache-Daten über einen schnellen Interconnect wie RDMA, wodurch Communication Cost Teil des Designs wird.

8. GQA und MQA: den KV cache verkleinern

Standard-Multi-Head Attention (MHA) gibt jedem Query-Head einen eigenen K- und V-Head. Multi-Query Attention (MQA) verwendet einen einzelnen KV-Head gemeinsam für alle Query-Heads und ist damit eine extreme Reduktion. Grouped-Query Attention (GQA) ist der praktische Mittelweg: Gruppen von Query-Heads teilen sich jeweils einen KV-Head.

Llama 3 70B verwendet 64 Query-Heads, aber nur 8 KV-Heads – eine 8-fache Reduktion des KV cache gegenüber derselben Architektur mit einem KV-Head pro Query-Head. Llama 3.1 405B verwendet 128 Query-Heads und 8 KV-Heads, also nach derselben Berechnung eine 16-fache Reduktion (Meta, 2024). Ainslie et al. berichten in ihren getesteten Models eine GQA-Qualität nahe an MHA bei gleichzeitig annähernder MQA-Geschwindigkeit. Ein kleinerer KV cache kann größere Batches ermöglichen; der tatsächlich erzielte Latency- und Throughput-Gewinn hängt jedoch weiterhin von Kernel und Workload ab.

9. Quantization: Bits gegen Geschwindigkeit und Memory tauschen

Quantization reduziert die Precision von Model Weights und/oder Activations. Die zentralen Trade-offs:

FormatBitsWeight Memory (7B Model)Quality-Hinweis

FP88~7 GBHardware-native auf Hopper; Model evaluieren

AWQ (Activation-Aware Weight Quantization) identifiziert anhand von Activation Magnitudes besonders wichtige Weight Channels und wendet Per-Channel-Scaling an, um diese zu schützen. Der Calibration-Bedarf hängt von Model und Configuration ab; in einem OPT-6.7B-INT3-g128-Vergleich verwendete AWQ 16 Calibration Sequences, GPTQ dagegen 192. Geben Sie in einem reproduzierbaren Setup sowohl die Anzahl der Sequences als auch ihre Länge an. GPTQ verwendet approximierte Informationen zweiter Ordnung für Layer-wise Quantization. bitsandbytes kann während des Model-Loadings ohne separaten Preprocessing-Pass quantisieren; sein NF4-Format ist die Grundlage für QLoRA Fine-Tuning. FP8 auf Hopper-Klasse-Hardware halbiert den Weight Memory gegenüber FP16/BF16, aber Quality und Speed hängen weiterhin von Model, Calibration und Kernel ab.

Der Serving Kernel kann ebenso wichtig sein wie der Quantization-Algorithmus. Abschnitt 10 liefert ein begrenztes Marlin-Ergebnis und erklärt, warum der Gewinn von der Serving Configuration abhängt.

Teil III — Inference-Optimierungen

Jede Software-Technik in diesem Teil adressiert einen bestimmten Bottleneck: FlashAttention nutzt die Lücke zwischen SRAM und HBM, PagedAttention entfernt KV-cache-Fragmentation und Continuous Batching hält die GPU beschäftigt.

10. CUDA Kernels und Kernel Fusion

Ein CUDA Kernel ist eine für die GPU geschriebene Function, die parallel über Tausende Threads ausgeführt wird. Wenn die CPU einen Kernel aufruft, verteilt die GPU die Arbeit auf ihre SMs: Jeder SM führt mehrere Warps mit jeweils 32 Threads aus, und jeder Thread verarbeitet einen Teil der Daten. Jede Operation in der LLM-Inference – von Matrix Multiplication bis Token Sampling – ist letztlich ein Kernel Launch. Ein einzelner Forward Pass durch ein 70B-Model löst Hunderte bis Tausende Kernel Launches aus; die Differenz zwischen einem naiven und einem optimierten Kernel kann darüber entscheiden, ob Ihr System sein Latency-SLO erfüllt.

Die wichtigsten Kernel-Kategorien im LLM Serving:

  • GEMM Kernels für Matrix Multiplication, die sowohl Prefill- als auch Decode-Compute dominieren.
  • Attention Kernels wie FlashAttention, die Berechnungen tilen, damit sie im SRAM bleiben, statt in HBM ausgelagert zu werden.
  • Fused Kernels, die mehrere Operationen – etwa Add + Layer Norm oder QKV Projection – in einem einzigen Launch kombinieren und dadurch die Zwischen-Round-Trips zu HBM überspringen.
  • Sampling Kernels, die Logits über Top-k, Top-p oder Temperature Sampling in Token IDs umwandeln.

Die Kernel-Qualität kann bestimmen, ob komprimierte Weights tatsächlich einen Speedup liefern. Das Marlin Paper berichtet für getestete Weight-only-INT4-vLLM-Konfigurationen bis zu 2,8-fachen End-to-End-Speedup gegenüber seiner FP16-Baseline. Dieses Ergebnis ist spezifisch für die Models, GPUs, Batch Sizes und Serving Configuration des Papers und daher kein allgemeiner INT4-Gewinn.

Triton senkt die Einstiegshürde für Custom Kernels, indem es GPU Programming über Python statt über reines CUDA C++ bereitstellt. Dadurch wird Kernel-Level-Optimization für ML Engineers und nicht nur für GPU-Spezialisten zugänglich. Die meisten später in diesem Teil beschriebenen Optimierungen (FlashAttention, Fused Kernels, PagedAttention) sind entweder bessere Kernels oder intelligentere Formen der Orchestration von Kernel Launches.

Kernel Fusion kombiniert sequenzielle Operationen in einem GPU Kernel und überspringt Zwischenwrites nach HBM. Übliche Fusions sind QKV Projection, Attention plus Softmax, Add plus RMSNorm (FlashNorm) und die SwiGLU Activation (DeepFusionKernel). Triton macht diese Kernels über Python zugänglich. Die genauen Verbesserungen bei Launch Count und Utilization hängen von Model Graph, Compiler, GPU und Serving Framework ab; profilieren Sie daher den deplo­yten Stack, statt sich auf einen universellen Prozentsatz zu verlassen.

11. FlashAttention: Attention durch Tiling im SRAM ausführen

Standard-Attention materialisiert die vollständige N×NN \times NN×N Attention Matrix in HBM. Das kostet O(N2)O(N^2)O(N2) Memory und erzeugt viel Memory Traffic. Die Idee hinter FlashAttention ist, diese Matrix überhaupt nicht zu materialisieren. Q-, K- und V-Matrices werden in Blöcke geteilt, die in SRAM passen; innerhalb jedes Tiles wird partielle Attention berechnet und die Ergebnisse werden über einen Online-Softmax zusammengeführt, der Maximum und Summe inkrementell über die Blöcke hinweg verfolgt. Der Memory-Bedarf sinkt von O(N2)O(N^2)O(N2) auf O(N)O(N)O(N), und die HBM Reads sinken um eine Größenordnung.

Jede Version adressiert den Bottleneck ihrer GPU-Generation:

  • FlashAttention v1 (A100, 2022) zeigte, dass die Kombination aus Tiling und Online-Softmax funktioniert. Das Paper meldete einen 2–4-fachen Speedup gegenüber Standard-Attention, aber nur 25–40 % GPU Utilization, weil das Kernel-Scheduling viele SMs ungenutzt ließ.
  • FlashAttention v2 (A100, 2023) überarbeitete den Parallelism, sodass über die Sequence Dimension statt über Batch und Heads gesplittet wurde. Auf der A100 wurden 50–73 % Utilization und ungefähr die doppelte Geschwindigkeit von v1 erreicht.
  • FlashAttention v3 (H100 Hopper, 2024) fügte Warp Specialization (separate Warps für Data Movement und Math) sowie GEMM-Softmax-Pipelining hinzu, um Memory Loads und Compute zu überlappen. Das Paper berichtet auf der H100 bis zu 740 TFLOPS/s in FP16 (75 % Utilization) und annähernd 1,2 PFLOPS/s in FP8. NeurIPS 2024 Spotlight.
  • FlashAttention v4 (B200 Blackwell, 2026) adressiert einen neuen Bottleneck: Auf Blackwell skaliert der Tensor-Core-Throughput so schnell, dass Nicht-Matmul-Operationen (Softmax-Exponentials, Rescaling) zum Limiter werden. FA4 emuliert die Exponentialfunktion per Polynomial Approximations auf FMA Units, verwendet Conditional Rescaling zur Reduktion des Overheads und speichert Zwischenwerte in Blackwells dediziertem Tensor Memory (TMEM) statt in Registers. Das Paper berichtet in seinen Tests etwa 1,6 PFLOPS auf der B200 in BF16, 1,3-mal schneller als cuDNN 9.13 und 2,7-mal schneller als Triton.

12. FlashDecoding: den Decode-Bottleneck parallelisieren

Standard FlashAttention hält die GPU beschäftigt, indem es die Arbeit über Batch Size und Query Length aufteilt. Beim Decode generiert das Model genau 1 Token auf einmal (Query Length = 1). Wenn Batch Size multipliziert mit der Anzahl der Attention Heads kleiner ist als die Gesamtzahl der SMs der GPU (108 auf einer A100), bleibt der Großteil der GPU ungenutzt, während wenige Einheiten die Token-History sequenziell verarbeiten.

FlashDecoding löst dieses Problem durch eine neue Parallelisierungsdimension: die KV Sequence Length selbst. Der KV cache wird in kleinere Chunks geteilt und über alle ansonsten ungenutzten GPU-Prozessoren verteilt, die ihn parallel auswerten. Anschließend werden die Teilergebnisse über eine Log-Sum-Exp-Reduction zusammengeführt.

Im Batch-one-CodeLlama-34B-Benchmark von Stanford erreichte FlashDecoding bei Sequence Lengths von 512 bis 64K Tokens bis zu 8-fachen End-to-End-Speedup gegenüber den getesteten Baselines und hielt die Attention-Latency bis 64K nahezu konstant. Das Ergebnis ist auf diese Hardware und diesen Benchmark begrenzt und keine allgemeine Decode-Garantie.

13. Continuous Batching vs. Static Batching

Static Batching wartet, bis jede Sequence eines Batches abgeschlossen ist, bevor der nächste Batch startet. Kurze Sequences verschwenden daher GPU Cycles, nachdem sie das Ende erreicht haben. Continuous Batching (eingeführt durch das Orca Paper, OSDI 2022) arbeitet auf Iterationsebene: In jedem Decode-Schritt werden abgeschlossene Sequences entfernt und neue aufgenommen.

Im OPT-13B-Benchmark von Anyscale erreichte optimiertes Static Batching das Vierfache seiner naiven Baseline, Continuous Batching das Achtfache und vLLM mit Continuous Batching plus PagedAttention das 23-Fache (Anyscale, 2023). Continuous Batching erhöht außerdem den Druck auf die KV Allocation und wird daher häufig mit paged Memory Management kombiniert.

14. PagedAttention: Virtual Memory für den KV cache

vLLMs PagedAttention überträgt das OS-Konzept der Virtual Memory auf das KV-cache-Management. Der KV cache wird in Blöcke fester Größe aufgeteilt (typischerweise 16 Tokens), Blöcke werden bei der Token-Generierung nach Bedarf alloziert und logische (sequenzielle) Positionen über Block Tables auf physische (verstreute) Memory Locations gemappt. Mehrere Requests mit gemeinsamem Prefix (System Prompts, Beam Search) können auf dieselben physischen Blöcke zeigen.

Frühere Systeme verschwendeten durch Fragmentation und Pre-Allocation 60–80 % des KV-cache-Memory. PagedAttention reduziert diesen Anteil auf <4 %, wodurch der Throughput bei gleicher Latency um das 2–4-Fache und gegenüber HuggingFace Transformers um bis zu 24x steigen kann (vLLM Blog, 2023).

15. Speculative Decoding: mehrere Tokens pro Forward Pass

Bei Speculative Decoding generiert ein kleines Draft Model KKK Kandidaten-Tokens; anschließend bewertet das große Target Model alle KKK Positionen in einem Forward Pass. Der Decoder akzeptiert Draft-Tokens von links nach rechts mit Wahrscheinlichkeiten, die aus den Target- und Draft-Distributionen abgeleitet werden. Nach der ersten Ablehnung sampelt er eine Korrektur aus der Residual-Target-Distribution und verwirft die übrigen Draft-Tokens. Dieser modifizierte Rejection-Sampling-Schritt erhält die Output-Distribution des Target Models innerhalb der Hardware-Numerik; reines Exact Token Matching tut dies nicht.

Der Gewinn ist am wahrscheinlichsten bei kleinen Serving-Batches und kurzen Draft Lengths, wenn die Bewertung des Drafts durch Weight-, KV-cache- oder Communication-Traffic dominiert wird und nicht durch die zusätzliche Token-Berechnung. Das ursprüngliche Speculative-Sampling-Paper meldete für sein getestetes 70B-Chinchilla-Setup einen 2–2,5-fachen Decode-Speedup; EAGLE-3 meldete in seinen Tests bis zu 6,5-fachen Speedup. Varianten umfassen Medusa (zusätzliche Prediction Heads, kein separates Model), Prompt Lookup Decoding (N-Gram-Matching gegen den Input ohne separaten Draft-Model-Forward-Pass) und EAGLE (Feature-Level-Extrapolation).

Bei hohen Batch Sizes kann zusätzliche Draft- und Verification-Arbeit den Gewinn aufzehren. Speculative Decoding ist besonders vielversprechend, wenn der Serving-Batch klein genug und die Draft-Akzeptanz hoch ist; benchmarken Sie den vollständigen Serving Loop und nicht nur den Verification Kernel.

16. Prefix Caching und KV-cache-Wiederverwendung

Statt den KV cache nach Abschluss eines Requests zu verwerfen, hält Prefix Caching ihn zur Wiederverwendung bei neuen Requests mit denselben Prefix-Tokens vor. Dadurch entfällt redundantes Prefill für System Prompts, Few-shot-Beispiele, RAG Context und Multi-turn Conversation History.

vLLMs Automatic Prefix Caching hasht KV-Blöcke und verwendet eine globale Hash Table zur Suche. SGLangs RadixAttention verwaltet einen Radix Tree gecachter KV-Tensors mit Token-Level-Granularität. Beide Ansätze hängen von wiederkehrenden, token-identischen Prefixes ab; berichten Sie daher die Hit Rate zusammen mit Latency oder Throughput.

17. Streaming in der Praxis

Streaming sendet Tokens an den Client, sobald sie generiert werden, statt auf die vollständige Response zu warten. Viele Serving Frameworks stellen dies über Server-Sent Events bereit: Der Client öffnet eine langlebige HTTP Connection, und der Server pusht jeden Token oder Token-Batch als data:-Event. TTFT bestimmt, wann der Nutzer erstmals Output sieht; TPOT beeinflusst, wie flüssig sich die Ausgabe anfühlt. Legen Sie das Ziel über Product Testing und das gewählte Interaktionsmodell fest.

Auf der Client-Seite erzwingt Streaming Entscheidungen zur Buffering-Strategie. Tokenweises Rendering kann zu visuellem Jitter führen, insbesondere bei Markdown oder Code Blocks, die für eine korrekte Formatierung mehrere Tokens Kontext benötigen. Übliche Patterns sind Word-Level Buffering (Tokens bis zu einer Whitespace-Grenze sammeln), Line-Level Buffering (bis zu einem Newline warten) und Adaptive Buffering (Prosa sofort rendern, Code Blocks puffern). In der OpenAI Chat Completions API fügt stream_options: {"include_usage": true} vor der data: [DONE]-Message einen abschließenden Usage Chunk hinzu. OpenAI-kompatible Server können sich unterscheiden; prüfen Sie daher die ausgewählte Implementierung.

Chunked Prefill ist eine Möglichkeit, zu verhindern, dass lange Prefills die Token-Auslieferung für concurrent User blockieren. Decode-Priority-Scheduling kann laufende Requests schützen, während Disaggregated Serving Prefill und Decode auf getrennten GPU-Pools isoliert.

18. Grundlagen der Transformer Architecture

Ein moderner Decoder-only Transformer (GPT, Llama) ist ein Stack identischer Layers, die jeweils aus zwei Sub-Blocks bestehen: Attention und Feed-Forward. Jeder Sub-Block ist von einer Residual Connection und Normalization umgeben. Die wichtigsten Komponenten:

Multi-Head Attention ermöglicht jedem Token, Informationen von Tokens zu gewichten, die unter der Attention Mask sichtbar sind. Der Input wird in drei Matrices projiziert: Queries (Wonach suche ich?), Keys (Was enthalte ich?) und Values (Welche Information trage ich?). Die Attention Scores werden anschließend so berechnet:

Das QKTQK^TQKT Dot Product misst die Ähnlichkeit zwischen jedem Token-Paar. Die Division durch dk\sqrt{d_k}dk​​ verhindert, dass die Dot Products zu groß werden und Softmax dadurch in Bereiche mit verschwindenden Gradients gedrückt wird. Softmax wandelt die Scores in Wahrscheinlichkeiten um; die Multiplikation mit VVV erzeugt eine gewichtete Kombination der Value Vectors. Wenn dies parallel über mehrere Heads ausgeführt wird, kann das Model gleichzeitig unterschiedliche Beziehungen betrachten (ein Head für Syntax, ein anderer für Coreference usw.).

Das Feed-Forward Network (FFN) transformiert jede Token-Repräsentation unabhängig, nachdem Attention Informationen über Tokens hinweg gemischt hat. Moderne LLMs verwenden häufig SwiGLU anstelle des ursprünglichen Zwei-Matrix-ReLU-FFN:

Das FFN macht typischerweise etwa zwei Drittel der gesamten Model Parameters aus, wobei der genaue Anteil von der Architecture abhängt.

Residual Connections addieren den Output jedes Sub-Blocks wieder zu dessen Input: Output=Input+Sublayer(Input)\text{Output} = \text{Input} + \text{Sublayer}(\text{Input})Output=Input+Sublayer(Input). Der Skip Path verbessert Signal- und Gradient-Propagation durch tiefe Stacks.

RMSNorm ist in modernen LLM Families verbreitet. LayerNorm zentriert neu, indem es den Mean subtrahiert, und skaliert anhand der Standard Deviation. RMSNorm überspringt die Mean-Subtraction und skaliert nur; das Paper berichtet über die getesteten Models hinweg 7–64 % Speedup, ohne in diesen Experimenten einen Performance-Verlust. Auch Pre-norm Placement, bei dem vor Attention oder FFN normalisiert wird, ist verbreitet, weil es die Gradient Stability verbessert.

19. Decoder-only Models für General-Purpose Generation

Der ursprüngliche Transformer (2017) besaß sowohl einen Encoder als auch einen Decoder. Seitdem hat sich das Feld in drei Architektur-Families aufgeteilt, von denen eine zum Standard für Generative AI wurde.

Encoder-only Models (BERT, RoBERTa) verwenden Bidirectional Attention: Jeder Token attendet auf jeden anderen Token in beide Richtungen. Das erzeugt reichhaltige Repräsentationen für Understanding Tasks (Classification, NER, Semantic Similarity), kann aber Text nicht autoregressiv generieren. Encoder-only Models sind weiterhin als Backbone für Embedding Models, Reranker und Lightweight Classifier verbreitet (beispielsweise die BERT-basierten Router in RouteLLM).

Encoder-decoder Models (T5, BART, der ursprüngliche Transformer) trennen Understanding und Generation. Der Encoder verarbeitet den vollständigen Input mit Bidirectional Attention; anschließend generiert der Decoder Output autoregressiv und attendet über Cross-Attention auf die Repräsentationen des Encoders. Das bot einen natürlichen Vorteil für Sequence-to-Sequence Tasks wie Translation, bei denen Input und Output unterschiedliche Sequences sind. Googles T5 zeigte, dass sich jede NLP-Aufgabe als Text-to-Text formulieren lässt; Encoder-decoder Models treiben weiterhin einige spezialisierte Systeme an (Whisper für Speech Recognition, FLAN-T5 für Instruction Following).

Decoder-only Models (GPT, Llama, Mistral, Gemini) verwenden Causal (Unidirectional) Attention: Jeder Token attendet nur auf vorherige Tokens. Sie sind für General-Purpose Text Generation verbreitet, weil ein Causal-Language-Model-Objective über Unpaired Text skaliert, während Inference Instructions, Few-shot Demonstrations und Query als Tokens in einem Prefix behandelt. Der wiederholte Decoder Block vermeidet außerdem einen separaten Encoder Stack und Cross-Attention Path. Encoder-decoder Models bleiben nützlich, wenn eine Aufgabe davon profitiert, den Input separat zu encoden und gegen diese Repräsentation zu generieren, etwa bei Translation und Speech Recognition.

20. Mixture of Experts

MoE ersetzt das Dense FFN in jedem Transformer-Layer durch mehrere kleinere Expert FFNs sowie einen leichtgewichtigen Gating Router. Der Router berechnet für jeden Expert einen Score (typischerweise einen Softmax über gelernte lineare Projections) und wählt die Top-kkk Experts pro Token aus. Nur die aktivierten Experts rechnen; dadurch kann ein Model eine enorme Gesamtkapazität besitzen und gleichzeitig geringe Kosten pro Token aufweisen. Dies ist Sparse Conditional Computation: Die Total Parameters bestimmen, was das Model repräsentieren kann; die Active Parameters bestimmen, was es kostet, auszuführen.

21. Tokenization: BPE, SentencePiece und tiktoken

LLMs sehen keinen Text. Sie sehen Sequenzen von Integer-Token-IDs. Ein Tokenizer zerlegt Raw Text in Tokens (Subword Pieces) und mappt jeden Token auf eine ID. Die Wahl des Tokenizers beeinflusst Model Quality, Inference Speed und Multilingual Fairness.

Byte Pair Encoding (BPE) ist der verbreitete Algorithmus. Er merged iterativ die häufigsten benachbarten Paare im Training Corpus. Ein vereinfachtes Beispiel:

  1. Start mit einem Character-Level Vocabulary: [l, o, w, e, r, _]
  2. Häufigstes Pair ist (l, o) → Merge zu lo → Vocabulary: [l, o, w, e, r, _, lo]
  3. Nächsthäufigstes Pair ist (lo, w) → Merge zu low → Vocabulary ergänzt low
  4. Fortfahren, bis das Vocabulary die Zielgröße erreicht (z. B. 128K Tokens)

Häufige Wörter wie „the“ werden zu einzelnen Tokens, während seltene Wörter wie „defenestration“ in Subword Pieces wie ["def", "en", "est", "ration"] zerlegt werden. Der Trade-off besteht zwischen Vocabulary Size und Sequence Length.

Drei Tokenizer-Implementierungen decken den Großteil des Production-Einsatzes ab:

  • SentencePiece wird direkt auf Raw Unicode Text ohne Language-specific Pre-tokenizer trainiert. Whitespace wird mit dem Meta-Symbol ▁ erhalten; optional kann auf UTF-8-Byte-Tokens zurückgefallen werden. SentencePiece unterstützt sowohl BPE- als auch Unigram-Models und wird von Llama 1/2, T5 und Mistral verwendet.
  • tiktoken ist OpenAIs Rust-basierter Tokenizer mit Byte-Level BPE. Im veröffentlichten GPT-2-Benchmark lief er 3–6-mal schneller als die getestete GPT2TokenizerFast-Konfiguration. Llama 3 wechselte von SentencePiece zu tiktokens Algorithmus.
  • Hugging Face Tokenizers ist eine weit verbreitete Rust-basierte Library mit Unterstützung für BPE, WordPiece und Unigram.

Fertility misst, wie viele Tokens ein Tokenizer pro Wort oder einer anderen gewählten Text-Einheit erzeugt. Sie variiert nach konkretem Tokenizer, Sprache, Script, Normalization, Domain und Sample. Messen Sie sie an repräsentativem Traffic, statt aus einem einzelnen Tokenizer oder einer einzelnen Sprache zu extrapolieren.

Unmasked Self-Attention ist permutation-equivariant: Werden die Input-Tokens neu angeordnet, werden die Outputs auf dieselbe Weise neu angeordnet. Die Causal Mask eines Decoders begrenzt jeden Token bereits auf sein Prefix; das Umkehren eines Satzes erzeugt daher keine identischen Hidden States. Positional Encodings fügen explizite Positions- und Relative-Distance-Information innerhalb dieses sichtbaren Prefixes hinzu.

Drei verbreitete Ansätze sind:

  • RoPE (Rotary Position Embeddings) rotiert Query- und Key-Vectors um positionsabhängige Winkel, sodass ihr Dot Product von der relativen Position abhängt. Der Token Content bestimmt weiterhin den Attention Score; RoPE fügt Positionsinformation ohne gelernte Absolute-Position-Embeddings hinzu. RoPE wird von Open-Model-Families wie Llama, Mistral und Qwen verwendet.

  • ALiBi (Attention with Linear Biases) überspringt Änderungen an Embeddings und fügt direkt zu den Attention Scores einen Penalty hinzu: Je weiter zwei Tokens auseinanderliegen, desto größer ist der negative Bias. Es gibt keine gelernten Positional Parameters. Im ursprünglichen Paper zeigte ein mit Sequences von 1.024 Tokens trainiertes 1,3B-Model bei 2.048 Tokens eine ähnliche Performance wie ein mit 2.048 Tokens trainiertes Model mit Sinusoidal Positions. Das Verhalten über die getesteten Models und Lengths des Papers hinaus ist Model-abhängig.

  • YaRN (Yet another RoPE extensioN) erweitert ein RoPE-Model über seinen Training Context hinaus. Frequency Dimensions werden in drei Kategorien gruppiert und jeweils unterschiedlich skaliert. Das Paper berichtet 10-mal weniger Fine-Tuning-Tokens und 2,5-mal weniger Training Steps als die Position-Interpolation-Baseline.

23. Pretraining, Fine-Tuning und Alignment

Pretraining ist Self-Supervised Next-Token Prediction auf einem großen Corpus. Der Compute-Bedarf erstreckt sich über viele Größenordnungen; Llama 3 405B verwendete beispielsweise 3.8×10253.8 \times 10^{25}3.8×1025 FLOPs. Supervised Fine-Tuning (SFT) passt das pretrained Model an aufgabenspezifische gelabelte Daten an. RLHF / RLAIF formt das Verhalten anhand von Preference Data: Eine konventionelle RLHF Pipeline sammelt Vergleiche, trainiert ein Reward Model und optimiert anschließend die Policy. RLAIF ersetzt einen Teil der menschlichen Bewertungen durch AI-generiertes Feedback.

Der Compute-Bedarf hängt von Model Size, Sequence Length, Data Volume, Optimizer und Methode ab. PPO führt außerdem mehr Model State mit als SFT, weil ein typisches Setup Policy, Reference, Reward und Critic Models umfasst. Das vollständige Decision Framework für Fine-Tuning habe ich im LLM Fine-Tuning Guide behandelt.

24. LoRA und QLoRA: Parameter-Efficient Fine-Tuning

LoRA friert die pretrained Weights ein und fügt trainierbare Low-Rank-Matrices AAA (r×kr \times kr×k) und BBB (d×rd \times rd×r) ein, sodass das aktualisierte Weight W0+BAW_0 + BAW0​+BA lautet. Das LoRA Paper reduzierte GPT-3 175B in seinem Setup auf etwa 18 Millionen trainierbare Parameters. Der Rank ist ein Tuning-Parameter und keine Regel für Task Complexity; wählen Sie ihn über einen Quality- und Memory-Sweep. LoRA Adapters können nach dem Training in die Base Weights gemerged werden, um bei Inference einen separaten Adapter Path zu vermeiden.

QLoRA lädt das Base Model in 4-Bit-NF4-Quantization, während LoRA Adapters in BF16 trainiert werden. NormalFloat4 platziert mehr Quantization Levels nahe null, wo die Weight Density am höchsten ist. Das Paper fine-tunte ein 65B-Model auf einer einzelnen 48-GB-GPU und berichtete Ergebnisse nahe an seinen 16-Bit-Baselines. Die Runtime- und Memory-Trade-offs sind spezifisch für den getesteten Stack.

25. Mixed-Precision Training

Jedes Floating-Point-Format verteilt seine Bits auf drei Felder: Sign (immer 1 Bit), Exponent (bestimmt den Dynamic Range) und Mantissa (bestimmt die Precision). Mehr Exponent-Bits bedeuten einen größeren Bereich darstellbarer Magnitudes; mehr Mantissa-Bits erlauben feinere Unterscheidungen zwischen benachbarten Werten. Integer-Formate besitzen überhaupt keinen Exponent und stellen innerhalb eines festen Ranges nur gleichmäßig verteilte Ganzzahlen dar.

BF16 hat denselben Range wie FP32, weil der Range durch das Exponent-Feld bestimmt wird und BF16 alle 8 Exponent-Bits von FP32 übernimmt. Dafür gibt BF16 Mantissa-Bits auf (7 statt 23) und tauscht Precision gegen eine 2-fache Memory-Reduktion, ohne viele Range-Probleme des FP16-Trainings zu übernehmen. FP16 hat nur 5 Exponent-Bits, wodurch sein endlicher Range bei etwa 65K endet. Viele Gradients sind für FP16 dagegen zu klein und underflowen gegen null. Loss Scaling multipliziert die Loss vor der Backpropagation, sodass diese Gradients darstellbar bleiben, und entfernt die Skalierung vor dem Optimizer Step wieder; Dynamic Scaling reduziert den Faktor, wenn ein Overflow auftritt. Der größere Exponent-Range von BF16 vermeidet diese Anforderung üblicherweise.

Integer-Formate sind für die zentrale Training Arithmetic unüblich, weil Backpropagation einen großen Dynamic Range benötigt. In der Inference werden sie dagegen häufig verwendet, da eingefrorene Weights auf kalibrierte Scales gemappt werden können. INT4 Weight Quantization reduziert ein 7B-Model von etwa 14 GB auf 3,5 GB, bevor Runtime Overhead hinzukommt; Quality muss für das ausgewählte Model und die gewählte Methode gemessen werden.

FP8 Training auf der H100 über Transformer Engine verwendet E4M3, wenn Precision wichtig ist, und E5M2, wenn ein größerer Range zählt. Das FP8-LM Paper berichtet, dass sein Mixed-Precision Framework GPT-175B im getesteten H100-Setup 75 % schneller als seine BF16-Megatron-LM-Baseline und 37 % schneller als NVIDIA Transformer Engine trainierte. DeepSeek-V3 verwendete Mixed Precision in FP8 und meldete für seinen finalen Training Run etwa $5,6 Millionen an mietenäquivalentem Compute, ohne R&D und Infrastructure.

26. Gradient Checkpointing

Jeder Layer des Forward Pass erzeugt einen Intermediate Output, der Activation genannt wird:

Input→[Layer 1]→activation1→[Layer 2]→activation2→[Layer 3]→output\text{Input} \rightarrow [\text{Layer 1}] \rightarrow \text{activation}_1 \rightarrow [\text{Layer 2}] \rightarrow \text{activation}_2 \rightarrow [\text{Layer 3}] \rightarrow \text{output}Input→[Layer 1]→activation1​→[Layer 2]→activation2​→[Layer 3]→output

Normalerweise müssen alle Activations im Memory bleiben, weil Backpropagation sie zur Berechnung der Gradients benötigt. Bei einem tiefen Transformer können die gespeicherten Activations mehr Memory beanspruchen als die Model Weights selbst.

Gradient Checkpointing tauscht Compute gegen Memory, indem die meisten Activations verworfen und während der Backpropagation bei Bedarf neu berechnet werden. Die Standardstrategie (Chen et al., 2016) teilt ein Network aus nnn Layers in n\sqrt{n}n​ gleichmäßig verteilte Segments und speichert nur die Boundary Activation jedes Segments. Diese gespeicherten Boundaries sind die „Checkpoints“. Alle Intermediate Activations innerhalb eines Segments werden sofort verworfen.

Wenn der Backward Pass einen Layer innerhalb eines Segments erreicht, werden dessen Activations vom nächsten Checkpoint aus neu berechnet. Bei der gleichmäßig segmentierten Strategie sinkt der gespeicherte Activation Memory von O(n)O(n)O(n) auf O(n)O(\sqrt{n})O(n​). Die tatsächliche Memory-Ersparnis und der Recompute-Overhead hängen von Model, Checkpoint Boundaries, Sequence Length, Framework und Implementation ab; messen Sie daher beides im Ziel-Training Run. FlashAttention verwendet dasselbe Prinzip innerhalb von Attention, indem die vollständige Attention Matrix nicht materialisiert wird. Aktivieren Sie es in HuggingFace mit gradient_checkpointing=True.

27. DeepSpeed-ZeRO-Stages

Bei Standard Data Parallelism hält jede GPU eine vollständige Kopie der Model Weights, Gradients und Optimizer States. Bei Adam entfallen auf jeden Parameter 2 Bytes für das FP16 Weight + 4 Bytes für das FP32 Master Weight + 4 Bytes für Momentum + 4 Bytes für Variance + 2 Bytes für den Gradient, also 16 Bytes pro Parameter. Ein Model mit 7,5B Parameters benötigt pro GPU ~120 GB, und jede GPU speichert dieselben Daten. Auf 64 GPUs sind das 64 identische 120-GB-Kopien. Viel Verschwendung.

DeepSpeed ZeRO (Zero Redundancy Optimizer) entfernt diese Duplikation, indem diese Komponenten über die GPUs geshardet statt repliziert werden:

  • Stage 1 – Optimizer States partitionieren. Jede GPU speichert nur 1/N der Optimizer States (FP32 Master Weights sowie Adams erste und zweite Moments, 12 Bytes/Parameter). Wenn eine GPU ein Weight aktualisieren muss, aktualisiert sie nur ihren Slice und broadcastet das Ergebnis. Unter den folgenden Annahmen sinkt der Memory-Bedarf von ~120 GB auf ~41,3 GB pro GPU.
  • Stage 2 – zusätzlich Gradients partitionieren. Gradients werden nicht mehr an jede GPU all-reduced (2 Bytes/Parameter). Jede GPU erhält über Reduce-Scatter nur den benötigten Gradient-Slice. Unter denselben Annahmen sinkt der Memory-Bedarf auf ~28,1 GB pro GPU.
  • Stage 3 – zusätzlich Model Weights partitionieren. Jede GPU hält nur 1/N der FP16 Weights. Vor dem Forward- oder Backward-Pass jedes Layers ruft die GPU All-Gather auf, um die vollständigen Layer Weights temporär aus den anderen GPUs zu rekonstruieren; sie berechnet und verwirft die gesammelten Weights anschließend. Unter denselben Annahmen sinkt der Memory-Bedarf auf ~15,0 GB pro GPU.

Der Trade-off ist Communication. Stage 1 fügt minimalen Overhead hinzu, Stage 2 ersetzt All-Reduce durch Reduce-Scatter zu ähnlichen Kosten. Stage 3 benötigt All-Gather-Aufrufe vor jedem Layer sowohl im Forward als auch im Backward Pass und hat gegenüber Standard Data Parallelism ungefähr 1,5-faches Communication Volume.

ZeRO-Infinity erweitert Stage 3, indem partitionierte States in CPU RAM und sogar NVMe SSDs offloaded werden. Dadurch kann das Training von Models mit Billionen von Parameters auf begrenzten GPU-Clustern möglich werden. Storage Offload fügt PCIe- und Storage-Transfer-Kosten hinzu; die gemessenen Auswirkungen hängen von Drive, PCIe Topology, Partitioning, Prefetching, Transfer Overlap und Workload ab. Verwenden Sie es, um Capacity Requirements zu erfüllen, statt von einem festen Slowdown auszugehen, und profilieren Sie die Zielkonfiguration.

28. FSDP: PyTorch-native Sharding

Fully Sharded Data Parallel (FSDP) ist PyTorchs integrierte Antwort auf DeepSpeed ZeRO-3. Es shardet Parameters, Gradients und Optimizer States über GPUs mit demselben Grundprinzip. Der Ablauf pro Layer ist eine einfache Schleife:

  1. All-Gather der vollständigen Parameters von allen GPUs (temporäre Rekonstruktion des kompletten Layers).
  2. Compute des Forward- oder Backward-Passes für diesen Layer.
  3. Freigeben der gesammelten Parameters sofort. Jede GPU behält nur ihren eigenen Shard.
  4. Reduce-Scatter der Gradients, sodass jede GPU nur ihren zugewiesenen Gradient-Slice erhält.

Da FSDP nativ in PyTorch integriert ist, lässt es sich direkt mit PyTorch-Debugging-Tools, Profilern und torch.compile verbinden. Die Performance gegenüber DeepSpeed ZeRO-3 hängt von Wrapping Policy, Communication Topology, Offload Settings und Model Size ab; vergleichen Sie beide auf demselben Cluster.

29. Scaling Laws und die Chinchilla-Falle

Wenn ein kleineres Model mit mehr Daten die erforderliche Quality erreicht, kann es über den gesamten High-Volume-Inference-Lifecycle günstiger sein.

30. RLHF, DPO, GRPO und die Alignment-Landschaft

Alignment steuert ein pretrained Model in Richtung gewünschter Instructions, Preferences und Safety Policies. Es garantiert für sich genommen weder Truthfulness noch sicheres Verhalten. Die folgenden Methoden tauschen Implementation Complexity, Data Requirements, Exploration und Training Stability gegeneinander ab.

Die klassische RLHF Pipeline: SFT → Human Preference Pairs sammeln → Reward Model auf diesen Pairs trainieren → Policy mit PPO fine-tunen (Proximal Policy Optimization). PPO hält gleichzeitig 4 Model Copies im Memory (Policy, Reference, Critic/Value Model, Reward Model) und reagiert empfindlich auf Hyperparameters. Außerdem ist es anfällig für Reward Hacking, bei dem das Model Eigenheiten des Reward Models ausnutzt, etwa ausführliche, selbstsicher klingende Antworten, statt die Quality wirklich zu verbessern.

DPO (Direct Preference Optimization) überspringt das gelernte Reward Model und den Online-RL-Loop, indem es eine Loss auf Preference Pairs direkt optimiert. Das vereinfacht die Training Pipeline. Standard-DPO ist Offline: Es trainiert auf einem festen Dataset und exploriert während des Update-Loops keine neuen Responses. Ob diese Einschränkung relevant ist, hängt von Task und Data Coverage ab.

GRPO (Group Relative Policy Optimization, DeepSeek) entfernt den gelernten Critic von PPO, indem mehrere Completions pro Prompt generiert und Group-relative Rewards als Baseline verwendet werden. Dadurch sinkt die Model-State-Last gegenüber einem typischen PPO-Setup. Anders als DPO ist GRPO On-Policy: Das Model generiert während des Trainings frische Responses. DeepSeek-R1 kombiniert GRPO mit RLVR (Reinforcement Learning from Verifiable Rewards) und verwendet Checks wie mathematische Antworten, Code Compilation und Unit Tests. Solche Rewards sind leichter zu auditieren als ein gelernter Preference Score, aber unvollständige Tests und Proxy Objectives können weiterhin ausgenutzt werden.

31. Distillation: Wissen zwischen Models komprimieren

Knowledge Distillation überträgt Capabilities von einem großen Teacher auf einen kleineren Student. Logit-based Distillation trainiert den Student so, dass er die Output Distribution des Teachers nachbildet. Data-based Distillation lässt den Teacher Examples generieren, auf denen der Student fine-getunt wird. Data-based Methods sind bei LLMs verbreitet, weil sie architekturübergreifend und mit API-only Teachers funktionieren können; ihr Wert ist jedoch durch Teacher Quality, Data Coverage, Filtering und Generation Cost begrenzt.

DeepSeek-R1 kuratierte eine Mischung aus ungefähr 800.000 Examples – etwa 600.000 Reasoning-bezogene Samples und 200.000 Non-Reasoning-Samples – und verwendete sie zur Distillation von Qwen2.5- und Llama-3-Models mit 1,5B bis 70B Parameters. In der Evaluation des Papers:

  • DeepSeek-R1-Distill-Qwen-32B erreicht 72,6 % auf AIME 2024 und 94,3 % auf MATH-500 und liegt damit über den im Paper berichteten Werten von OpenAI o1-mini.
  • DeepSeek-R1-Distill-Qwen-7B erreicht 55,5 % auf AIME 2024 und liegt damit über dem Ergebnis von QwQ-32B-Preview des Papers, obwohl es sich um ein kleineres Model handelt.

In den Small-Model-Experimenten von DeepSeek-R1 übertraf Distillation das direkte GRPO auf den getesteten Base Models. Das Ergebnis unterstützt Distillation für dieses Setup, etabliert aber kein universelles Ranking zwischen Distillation und RL.

32. Synthetic-Data-Generation

Von LLMs generierte Trainingsdaten werden in mehreren wiederkehrenden Patterns eingesetzt:

  • Self-Instruct startet mit einem kleinen Seed Set von menschengeschriebenen Instructions: Das LLM generiert neue Instructions, Inputs und Outputs, die gefiltert und wieder in den Pool aufgenommen werden. Das Alpaca-Projekt verwendete 52.000 Examples, die aus 175 Seeds generiert wurden. Stanford berichtete eine Data Generation unter 500andfine−tuningunder500 and fine-tuning under 500andfine−tuningunder100 und setzte die anfänglichen Reproduction Costs damit unter $600; der GPT-3.5-Vergleich war eine begrenzte Project Evaluation und keine breit angelegte Äquivalenz.
  • Evol-Instruct (WizardLM) nimmt bestehende Instructions und entwickelt sie entlang von Complexity Axes iterativ weiter (Constraints hinzufügen, Reasoning vertiefen, Problems konkreter machen), um sukzessive schwierigere Training Examples zu erzeugen.
  • Microsofts Phi-4 (14B) verwendete für einen großen Teil des Pretrainings Synthetic Data, darunter Generation, Critique, Self-Revision und Instruction Reversal. Der Technical Report vergleicht die resultierende STEM- und Coding-Performance auf den ausgewählten Benchmarks mit größeren Models.

Das relevante Risiko ist Model Collapse: Wenn Models rekursiv auf Synthetic Data aus früheren Generationen trainiert werden, verschwinden die Tails der ursprünglichen Distribution zunehmend. Das Model überschätzt häufige Patterns und verliert seltene, aber wichtige Variationen (Shumailov et al., 2024). Eine separate Ahrefs-Classifier-Studie samplte im April 2025 aus 900.000 Pages pro Domain jeweils eine neu erkannte englische Page und klassifizierte 74,2 % als Text mit einem gewissen AI-generated-Anteil. Diese Vendor-Studie ist keine Zählung des gesamten Webs. Die Mitigation beginnt mit der Mischung synthetischer und realer Daten, Filtering und Lineage Tracking, sodass rekursiv generiertes Material gemessen werden kann.

Teil VI — Scaling und Deployment

Die Skalierung von einer GPU auf einen Cluster bedeutet, Arbeit über Devices zu verteilen. Dieser Teil behandelt Parallelism-Strategien, Serving Frameworks, GPU-Auswahl und Routing.

33. Vier Formen von Parallelism

Tensor Parallelism (TP) teilt einzelne Weight Matrices über GPUs auf und kommuniziert üblicherweise nach jedem Layer. Schnelle Intra-Node-Links wie NVLink machen TP innerhalb eines Nodes besonders praktikabel. Mehr Shards reduzieren Memory und Compute pro Device, erhöhen aber die Communication; wählen Sie den Degree anhand eines Latency Benchmarks.

Pipeline Parallelism (PP) teilt Layers sequenziell über GPUs auf und übergibt Activations zwischen Stages. Das Communication Pattern kann über Nodes hinweg funktionieren, aber Pipeline Bubbles und ungleichmäßige Stage-Zeiten reduzieren die Utilization. Große Deployments kombinieren häufig TP innerhalb eines Nodes mit PP über Nodes hinweg.

Data Parallelism (DP) repliziert das Serving Model, sodass jedes Replica unabhängige Requests ohne Cross-Replica-Communication pro Request verarbeitet. Das ist effizient, wenn das Model passt und Traffic ausbalanciert werden kann. Im Training wird DP häufig mit ZeRO oder FSDP kombiniert, um State zu sharden.

Expert Parallelism (EP) verteilt MoE Experts über GPUs und verwendet All-to-All-Communication für Token Routing. Die Performance hängt von Token Balance, Expert Placement und Interconnect Topology ab; All-to-All-Traffic kann zum dominierenden Bottleneck werden.

Eine erste Parallelism-Heuristik:

  • Model passt auf eine GPU: Beginnen Sie mit unabhängigen Replicas und messen Sie DP Scaling.
  • Model passt in einen Node: Testen Sie TP innerhalb des Nodes und replizieren Sie die Gruppe anschließend, wenn der Traffic dies erfordert.
  • Model erstreckt sich über Nodes: Testen Sie eine Kombination aus TP und PP gegen Interconnect und Latency Target.
  • Mixture of Experts: Fügen Sie EP nur hinzu, wenn Expert Placement dies erfordert.

34. Serving Frameworks im Vergleich

vLLM bietet paged KV Allocation, Continuous Batching, eine OpenAI-kompatible API und mehrere Parallelism-Modi. Model- und Hardware-Support ändern sich häufig; prüfen Sie daher das Ziel-Model gegen die aktuelle Compatibility Matrix.

SGLang kombiniert RadixAttention für Prefix Reuse, einen Custom Scheduler und Structured Generation. Die veröffentlichten Throughput-Gewinne hängen von Workload und Configuration ab; vergleichen Sie SGLang mit vLLM und TensorRT-LLM anhand identischer Prompts, Outputs, Hardware und SLOs.

TensorRT-LLM zielt mit CUDA Graph Fusion und Kernel Optimization auf niedrige Single-Request-Latency und bietet native Unterstützung für FP8/FP4. Die veröffentlichten Zahlen sind hardware- und model-spezifisch. Der Trade-off ist eine steilere Learning Curve und eine NVIDIA-spezifische Deployment Surface.

TGI integriert sich in das Hugging-Face-Ecosystem und unterstützt mehrere Hardware-Backends. Prüfen Sie vor der Auswahl für ein neues Deployment den aktuellen Maintenance- und Feature-Status des Repositories.

Ollama legt den Schwerpunkt auf einen einfachen lokalen Model-Workflow. Verwenden Sie es für Development Convenience; benchmarken Sie bei hoher Concurrency oder expliziter SLO-Steuerung einen anderen Serving Stack.

llama.cpp ist ein portabler C/C++ Runtime mit ARM-, x86-, Metal-, CUDA-, ROCm- und Vulkan-Pfaden. GGUF unterstützt mehrere Quantization Levels. Die Performance variiert stark nach Model, Quantization, Context und Backend; verwenden Sie das lokale Benchmark Tool für die Zielmaschine.

36. Model Cascading und Routing

Model Routing wählt anhand der vorhergesagten Complexity oder Capability, welches LLM einen Query verarbeitet. RouteLLM (LMSYS/UC Berkeley, ICLR 2025) berichtet in seinem MT-Bench-Setup eine 85-prozentige Cost Reduction bei Beibehaltung von 95 % seiner GPT-4-Quality-Baseline. Ob sich Routing lohnt, hängt von den aktuellen Preisen, dem Traffic Mix, Router Errors und der Quality Floor ab.

Router reichen von Lightweight Classifiers bis zu LLM-basierten Judges. Cascading ist die sequenzielle Variante: Ein Query startet bei einem günstigeren Model und eskaliert, wenn eine Scoring Function die Antwort ablehnt. FrugalGPT berichtet in seinem evaluierten Model Pool bis zu 98 % geringere Kosten oder bis zu 4 % höhere Accuracy. Eine Production Cascade benötigt kalibrierte Escalation Criteria und Monitoring für Queries, die das günstigere Model fälschlich akzeptiert.

Teil VII — Applications

Patterns auf Application-Ebene, die rohe Model Capabilities in nützliche Systeme verwandeln. Embeddings treiben Retrieval an, RAG verankert Responses in externem Wissen, Agents orchestrieren Multi-Step-Workflows und Prompt Engineering verbindet alles.

37. Embedding Models vs. Generative Models

Embedding Models encoden Text in Vectors fester Dimension, die semantische Bedeutung erfassen. Anders als Generative Models, die Token Sequences erzeugen, geben sie einen einzelnen Dense Vector für den Input aus, typischerweise mit einigen hundert bis mehreren tausend Dimensions. Ihre Backbones umfassen bidirektionale Encoder-only-Transformer und aus Decodern abgeleitete Models, die für Representation Learning angepasst wurden. Eine Pooling Layer reduziert die Per-Token-Repräsentationen häufig über Mean Pooling, einen speziellen Classification Token oder eine Model-spezifische Last-Token-Methode auf einen Vector. Contrastive Fine-Tuning verschiebt semantisch ähnliche Texte näher zusammen und unähnliche Texte weiter auseinander.

Aktuelle Embedding-Systeme decken unterschiedliche Deployment Needs ab. Qwen3-Embedding-8B unterstützt konfigurierbare Output Dimensions und viele Sprachen. Gemini Embedding 2 akzeptiert Text, Images, Video, Audio und Documents. pplx-embed-v1-4B untersucht Dense Embeddings mit niedrigerer Precision. OpenAI text-embedding-3-large unterstützt verkürzte Embeddings über seinen Dimensions Parameter. Dies sind Beispiele und kein Ranking: Evaluieren Sie Language, Modality, Task, Dimension und Serving Cost auf einem gemeinsamen Retrieval Set.

Matryoshka Representation Learning (MRL, Kusupati et al., NeurIPS 2022) macht Embedding Dimensions flexibel. Benannt nach russischen Matrjoschka-Puppen strukturiert MRL ein Embedding so, dass seine ersten mmm Dimensions ebenso informativ sind wie ein unabhängig trainiertes mmm-dimensionales Model. Während des Trainings aggregiert MRL Losses über ein ausgewähltes O(log⁡d)O(\log d)O(logd) Set von Prefix Dimensions, normalerweise konsistente Halbierungen; das 2048-dimensionale Beispiel des Papers verwendet {8,16,…,1024,2048}\{8, 16, \ldots, 1024, 2048\}{8,16,…,1024,2048}. Die aggregierte Loss sorgt dafür, dass die führenden Dimensions grobe semantische Information tragen, während spätere Dimensions feinere Details ergänzen.

Nach dem Training kann ein MRL Embedding auf eine unterstützte Prefix Dimension gekürzt werden. OpenAI berichtet, dass text-embedding-3-large mit 256 Dimensions text-embedding-ada-002 mit 1.536 Dimensions im zitierten MTEB-Vergleich übertrifft. Das ergibt eine 6-fache Reduktion des Raw-Vector-Storage; Search Latency und Database Cost hängen außerdem von Index, Metadata, Filtering und Hardware ab.

Das Embedding Model ist eine wichtige Komponente einer RAG Pipeline, zusammen mit Parsing, Chunking, Search, Reranking und Generation. Wenn relevante Evidenz nicht retrieved wird, kann ein stärkerer Generator sie nicht zuverlässig wiederherstellen.

38. RAG Architecture in Production

Retrieval-Augmented Generation versorgt ein LLM zur Query-Zeit mit retrieved Documents. Dadurch können aktuelle oder private Evidences eingebracht werden, die in den Model Weights fehlen; Retrieval garantiert jedoch nicht, dass das Model diese Evidenz korrekt verwendet. Ein Production-RAG-System ist eine Multi-Stage-Pipeline, deren Stages separat evaluiert werden müssen.

Die Ingestion Pipeline läuft offline. Raw Documents (PDFs, HTML, Markdown, Databases) werden zunächst in sauberen Text geparst – schwieriger, als es klingt: Allein PDF Parsing kann Tables, Headers und Formatting verlieren. Der Text wird anschließend in Chunks geteilt, die unabhängig voneinander embedded und indexiert werden.

Chunking beeinflusst sowohl Retrieval Recall als auch den für den Generator verfügbaren Context. Sinnvolle Sizes hängen von Document Structure, Query Granularity, Embedder Limits und Reranker Limits ab. Übliche Ansätze sind Fixed-size mit Overlap, Recursive Splitting entlang von Document Boundaries und Semantic Chunking anhand von Embedding Similarity. Vergleichen Sie diese anhand von Relevance Labels auf Page- oder Section-Level, statt universell eine Token Range zu übernehmen.

Jeder Chunk wird anschließend mit einem Model wie denen aus Abschnitt 37 embedded und in einer Vector Database (Pinecone, Weaviate, Qdrant, pgvector usw.) gespeichert.

Die Retrieval Pipeline läuft zur Query-Zeit. Beginnen Sie mit einer messbaren Baseline und fügen Sie Stages hinzu, wenn Error Analysis zeigt, dass sie einen tatsächlichen Miss adressieren:

  • Hybrid Search kombiniert Dense Vector Retrieval mit Sparse Retrieval wie BM25, oft zusammengeführt über Reciprocal Rank Fusion (RRF). Dense Search verarbeitet semantische Paraphrases; Sparse Search findet exakte Identifiers, Error Codes und Acronyms. Vendor Benchmarks berichten Gains gegenüber Vector-only-Baselines, aber die Größenordnung hängt von Corpus und Relevance Labels ab.
  • Reranking lässt retrieved Candidates durch ein Model bewerten, das Query und Document gemeinsam scored. Das kann Fine-Grained Relevance verbessern, kostet aber einen weiteren Model Call. Candidate Count, Retained Count und Latency sollten gemeinsam getunt werden. Die vollständige Multi-Stage-Pipeline habe ich in Building a Modern Search Ranking Stack behandelt.
  • Query Transformation schreibt die User Query vor dem Retrieval um, um Recall zu verbessern. Bei HyDE (Hypothetical Document Embeddings) generiert das LLM eine hypothetische Antwort, die anschließend embedded und für Retrieval verwendet wird. Multi-query Expansion erzeugt mehrere Formulierungen derselben Frage. Step-back Prompting stellt zunächst eine allgemeinere Frage, um breiteren Context abzurufen.

Die häufigsten Failure Modes:

  • Retrieval Failure – das korrekte Document existiert, wird aber nicht retrieved. Testen Sie Chunking, Query Transformation, Hybrid Search und Metadata Filtering gegen den Miss.
  • Context Poisoning – irrelevante retrieved Chunks führen das LLM in die Irre. Testen Sie Reranking, Context Filters und kleinere Retained Sets.
  • Lost-in-the-middle – in den getesteten Multi-Document-Question-Answering- und Key-Value-Retrieval-Settings stellten Liu et al. fest, dass die Answer Performance im Allgemeinen am höchsten war, wenn relevante Information am Anfang oder Ende des Inputs erschien, und niedriger, wenn sie in der Mitte stand.

GraphRAG (Microsoft, 2024) erweitert Vector Retrieval um einen extrahierten Entity- und Relationship-Graph. Es zielt auf Corpus-Level- und Relationship-heavy-Questions, die Flat Chunk Retrieval möglicherweise verfehlt. Der Trade-off sind zusätzliche Extraction-, Indexing-, Storage- und Evaluation-Arbeiten.

Practitioner Guides veröffentlichen Latency Ranges für Embedding, Search, Reranking und Generation; diese Zahlen variieren jedoch nach Region, Corpus, Hardware und Model. Messen Sie jede Stage in Traces und evaluieren Sie die Quality-Änderung, bevor Sie die zusätzliche Latency akzeptieren.

39. Agent Architectures und Tool Calling

LLM Agents verwenden Models, um Tool Calls in einem sich entwickelnden State auszuwählen und zu sequenzieren. Drei nützliche Orchestration Patterns sind:

  • ReAct – verschachtelt Action Selection und Observations. Nach jedem Tool Result kann das System adaptieren, aber eine wachsende History erhöht Token- und Latency-Kosten.
  • ReWOO – plant Tool Calls mit Placeholders, führt unabhängige Arbeit parallel aus und synthetisiert anschließend. Das Paper berichtet Token Savings gegenüber ReAct; der feste Plan benötigt jedoch einen expliziten Recovery Path, falls ein Tool fehlschlägt.
  • Planner-executor – trennt Planning von Execution und kann nach einem Fehler eine Re-Planning Policy hinzufügen. Das erlaubt Model Specialization, fügt aber Orchestration State und eine weitere Decision Boundary hinzu.

Function Calling ist ein verbreiteter Mechanismus zur Tool Invocation. APIs legen Tool Definitions offen und geben strukturierte Arguments zurück, wodurch der Bedarf entfällt, Free-form Text zu parsen. Schema-valide Arguments können dennoch das falsche Tool auswählen oder ungültige Werte enthalten. Parallel Function Calling kann Round Trips reduzieren, wenn Operationen unabhängig sind.

Structured Output und Constrained Decoding erzwingen ein Schema, indem die verfügbaren Tokens bei jedem Generation Step eingeschränkt werden. Engines wie xgrammar, die in vLLM und SGLang verwendet werden, können in unterstützten Configurations viele Syntax- und Parsing-Failures mit geringem Overhead entfernen. Sie garantieren nicht, dass die extrahierten Values oder Decisions korrekt sind. Schema-Guided Reasoning (SGR) verwendet Field Order und Schema Structure, um den Intermediate State vor der finalen Decision inspizierbar zu machen. Seine drei Patterns sind Cascade (sequenzielle Steps), Routing (Union Types als semantische Switches) und Cycle (begrenzte Lists).

Tool-Selection Quality, End-to-End-Latency und Token Cost verschlechtern sich normalerweise, wenn Tool Set und Action Depth wachsen. Messen Sie diese Kurven mit den tatsächlichen Tool Descriptions und der Failure Distribution. Frameworks wie LangGraph können State und Recovery Paths explizit machen, beseitigen aber nicht den Evaluationsaufwand.

40. Prompt Engineering für Production

Production Prompting ist ein Evaluation Problem: Ändern Sie jeweils einen Teil des Prompts oder Contexts und messen Sie anschließend Task Quality und Failure Modes. Die folgenden Techniken sind verbreitete Ausgangspunkte, aber keine universelle Reihenfolge.

Few-shot Examples sind häufig effektiv, um das Output Format zu kontrollieren. Beginnen Sie mit 3–5 Examples, die leere Inputs, ambige Queries und mehrteilige Answers abdecken, und messen Sie das Ergebnis auf einem Held-out Set. Die Examples sollten die reale Input Distribution abdecken und nicht nur den Happy Path. Mehr Examples verbrauchen Context und garantieren keine weiteren Gains.

Chain-of-thought (CoT) Prompting fordert ein Model auf, vor der Antwort Intermediate Reasoning offenzulegen. Kojima et al. berichteten auf ihren getesteten Reasoning Tasks Gains durch das Suffix „Let’s think step by step“, aber der Effekt variiert nach Model; neuere Reasoning APIs legen möglicherweise keine Hidden Traces offen. Bevorzugen Sie in Production eine inspizierbare Task Decomposition oder eine knappe Rationale, wenn sie für den Evaluator nützlich ist. Self-consistency (Wang et al., 2023) sampelt mehrere Reasoning Paths und aggregiert die Answers; das tauscht zusätzliche Inference-Kosten gegen Robustheit bei geeigneten Tasks.

Structured Output mit expliziten JSON Schemas (Abschnitt 39) entfernt viele Parsing Failures. Constrained-Decoding-Engines wie xgrammar können die unterstützte Grammar während der Generation erzwingen; Factual Accuracy und Semantic Validity erfordern weiterhin Evaluation, und nicht unterstützte Schema Features müssen möglicherweise separat behandelt werden.

Prompt Chaining zerlegt einen Task in fokussierte Stages, beispielsweise Intent Classify → Context Retrieve → Response Generate → Output Validate. Dadurch lassen sich Failures lokalisieren, unterschiedliche Models pro Stage einsetzen und cachebare Intermediate States offenlegen. Gleichzeitig entstehen zusätzliche Interfaces und Latency; vergleichen Sie den Ansatz daher mit einer Single-Call-Baseline.

Temperature verändert die Sampling Distribution. Niedrige Werte sind ein sinnvoller Ausgangspunkt für Classification oder Extraction; höhere Werte können die Diversity bei Ideation erhöhen. Das genaue Verhalten unterscheidet sich zwischen Model APIs und interagiert mit top_p, top_k und Provider Defaults. Sweepen Sie deshalb die unterstützten Settings für den konkreten Task, statt einen Bereich zu kopieren.

Trennung von System- und User-Messages hält persistente Policy vom Request-spezifischen Content getrennt. Chat Templates und Instruction Tuning geben diesen Rollen unterschiedliche Priorität, machen eine System Message jedoch nicht zu einer Enforcement Boundary. Legen Sie stabiles Verhalten in der System Message ab, halten Sie untrusted Data in User- oder Tool Content und erzwingen Sie harte Constraints wie PII Removal zusätzlich außerhalb des Models.

Context Engineering erweitert Prompt-Arbeit auf die Zusammenstellung von retrieved Documents, Tool Results, Conversation History und Examples. Liu et al. fanden in den von ihnen getesteten Long-Context Models einen Lost-in-the-middle-Effekt; die Position sollte daher Teil der Evaluation sein und nicht als irrelevant vorausgesetzt werden. Den breiteren Workflow habe ich in Context Engineering for AI Agents behandelt.

Dieser Teil behandelt Rate Limiting, Failure Modes, Monitoring, Cost Optimization und Capacity Planning unter realem Traffic.

41. Rate Limiting für Requests mit variablen Kosten

Traditionelles Rate Limiting nach Requests pro Sekunde setzt ungefähr gleiche Kosten pro Request voraus. LLMs brechen diese Annahme. Ein 10-Token-Classification-Prompt und eine 100K-Token-Document-Analysis treffen denselben API Endpoint, unterscheiden sich aber bei den Kosten um vier Größenordnungen. Rate Limiting nach RPS lässt entweder teure Requests unkontrolliert durch oder benachteiligt günstige Requests unnötig.

Production-Systeme benötigen Token-based Rate Limiting über mehrere Dimensions hinweg. OpenAI dokumentiert Request- und Token-Limits nach Usage Tier. Anthropic trennt Input-Token- und Output-Token-Limits. Exakte Quotas und Algorithmen können sich ändern; behandeln Sie die Provider-Dokumentation als Source of Truth. Der architektonische Punkt ist, Requests und Tokens unabhängig zu budgetieren.

Das praktische Implementation Pattern ist eine multidimensionale Limit Hierarchy (User → Application → Organization → Global) mit Priority Tiers für Premium Access. Auf Request-Ebene ist Token Budget Reservation entscheidend: Schätzen Sie die Total Tokens (Input + max_tokens) bei der Admission, ziehen Sie sie vom Bucket ab und korrigieren Sie den Wert nach Abschluss des Requests anhand des tatsächlichen Usage. So verhindert das System, dass ein Burst langer Generation Requests die Capacity erschöpft, bevor überhaupt Output produziert wird.

Bei Self-hosted Deployments entspricht dem eine Provisioned Throughput: dedizierte GPU Capacity für bestimmte Token Rates reservieren. Bei vLLM Deployments bedeutet das, Admission Control anhand aktiver Decode Slots und KV-cache Pressure statt allein anhand der Request-Anzahl zu konfigurieren. Wie Abschnitt 5 erklärt, benötigen sowohl Throughput als auch Admission Token-aware Limits.

42. Failure Modes, gegen die Sie designen sollten

LLM Serving fügt Failure Modes hinzu, die an variable Sequence Length, KV Memory und lang laufende Decode-Arbeit gebunden sind. Entwerfen und load-testen Sie die Gegenmaßnahmen, bevor Production Traffic von ihnen abhängt.

Out-of-Memory (OOM) ist ein häufiges Failure. Ein 70B-FP16-Model benötigt allein für die Weights etwa 140 GB; der KV cache für eine einzelne 128K-Context-Sequence von Llama 3.1 70B kann unter den Annahmen aus Abschnitt 6 weitere etwa 40 GB hinzufügen. Die Lücke zwischen „passt in den Memory“ und „OOM unter Load“ ist kleiner, als sie wirkt, weil ein Batch langer Context Requests mehr KV Memory verbrauchen kann als erwartet. Prevention kombiniert einen gemessenen Memory Reserve mit Quantization und paged KV Allocation. Für Workloads mit hohem KV Pressure kann LMCache KV Data in CPU Memory oder auf Disk offloaden; verwenden Sie die veröffentlichten Ergebnisse als Ausgangspunkt und benchmarken Sie die lokale Memory Hierarchy.

Preemption tritt auf, wenn KV-cache Pressure den Scheduler zwingt, Arbeit zu evicten oder neu zu berechnen. Die genaue Strategy hängt von Serving Version und Configuration ab. Für den User zeigt sich das als höhere End-to-End-Latency ohne offensichtlichen Application Error. Beobachten Sie Preemption Counts und korrelieren Sie sie mit KV Usage, Queue Depth und Request Lengths.

Tail Latency kann stark ansteigen, wenn große Prefills Decode-Arbeit verzögern. Chunked Prefill (Abschnitt 7) und Length-aware Scheduling zielen auf diese Interferenz. Das Learning-to-Rank-Scheduler-Paper und CascadeInfer berichten in ihren evaluierten Workloads Verbesserungen gegenüber ihren Baselines; das genaue Ergebnis hängt jedoch von Request-Length-Distribution und Scheduler Configuration ab.

Cascading Failures können beginnen, wenn langsame Requests die Queue vergrößern, Upstream Clients timeouten und Retries zusätzliche Load erzeugen. Zu den Gegenmaßnahmen gehören Admission Control, Per-Tenant-Concurrency-Limits, Output Caps, Retry Budgets und Gateway Circuit Breakers. Disaggregated Prefill- und Decode-Pools können helfen, wenn Load Tests anhaltende Phaseninterferenz zeigen.

43. LLM-Systeme monitoren

LLM Monitoring unterscheidet sich in einigen grundlegenden Punkten von traditionellem API Monitoring. Jeder Request hat variable Kosten, zwei unterschiedliche Phasen mit unterschiedlichen Bottlenecks und einen Memory Footprint, der sowohl von Input Length als auch Generation Length abhängt. Standard Metrics wie Request Latency und Error Rate übersehen den Großteil des Relevanten.

Goodput ist die Anzahl der Requests pro Sekunde, die alle definierten SLO Thresholds erfüllen, etwa TTFT, TPOT und Total Latency. Es ist eine nützliche kombinierte Metrik, weil der rohe Throughput gesund aussehen kann, während Latency SLOs verfehlt werden: Ein System, das 100 Requests pro Sekunde verarbeitet, aber bei 40 % die Thresholds verfehlt, hat einen Goodput von 60 Requests pro Sekunde. Die Optimierung auf Goodput hält die Performance Distribution sichtbar, statt nur den Mean zu melden.

vLLM stellt einen Prometheus Endpoint unter /metrics bereit, mit laufenden und wartenden Requests, KV-cache Usage, Generation-Length-Distributions und Prefix-cache-Statistiken. Metric Names können sich zwischen Releases ändern; binden Sie Dashboards an die deplo­yte Version. Ein typischer Stack verwendet Prometheus für Metrics, Grafana für Visualization und OpenTelemetry-kompatible Traces über Application- und Serving-Komponenten hinweg.

Nützliche Alert Patterns sind unter anderem folgende. Leiten Sie die Thresholds aus Load Tests ab, statt diese Beispiele unverändert zu kopieren:

  • Preemption Count Spikes – die Runtime tauscht Arbeit aus oder berechnet sie neu, was Latency ohne Application Error erhöht.
  • KV-cache Utilization nähert sich der getesteten Preemption Region – fügen Sie Capacity hinzu oder reduzieren Sie Load, bevor Evictions eskalieren.
  • Queue Depth liegt dauerhaft über dem getesteten Batch Envelope – Admission Control sollte beginnen, Requests abzulehnen oder nachrangig zu behandeln.
  • TTFT steigt, während TPOT konstant bleibt – diese Divergenz deutet zunächst auf Queueing, Admission, Network oder Prefill Pressure statt auf Decode Throughput hin. Verwenden Sie Traces und Queue Metrics, um die Ursachen zu unterscheiden.

44. Cost Optimization: eine kumulative Strategie

Provider-Preise und Input-to-Output-Price-Ratios ändern sich. Rufen Sie vor einer Beschaffungsentscheidung aktuelle Rates ab; Model Tier und Output Length können die Rechnung schon vor Infrastructure Optimizations dominieren.

Mehrere Ansätze lassen sich kombinieren, aber erst nachdem gemessen wurde, welche für den Workload relevant sind:

  1. Quantization von FP16 auf INT4 reduziert den Weight Memory um 75 %. Ob dadurch die Rechnung sinkt, hängt von Kernel Speed, Batch Size und Hardware Utilization ab (Abschnitt 9).
  2. Model Routing sendet geeigneten Traffic an günstigere Models. Messen Sie False-Accept-Rate des Routers und End-to-End-Quality, bevor Sie den Anteil der günstigeren Models erhöhen (Abschnitt 36).
  3. Prompt Caching reduziert wiederholte Prefix-Arbeit. Provider Discounts und Rate-Limit-Behandlung ändern sich im Lauf der Zeit; kombinieren Sie daher gemessene Hit Rate mit aktuellen Terms (Abschnitt 16).
  4. Batch APIs können Non-Real-Time-Arbeit wie Evals, Synthetic-Data-Generation und Bulk Classification vergünstigen. Prüfen Sie aktuelle Preise und Completion Windows.
  5. Self-hosting kann bei dauerhafter Utilization gewinnen, aber es gibt keinen universellen Break-even für Token Volume. Berücksichtigen Sie neben der GPU-Miete auch Engineering, Orchestration, Observability, Capacity Slack und On-Call-Kosten.

Die Multiplikation der illustrativen Faktoren ergibt eine große theoretische Reduction, aber die Inputs sind nicht unabhängig: Quantization verändert den Throughput, Routing verändert den Quality Mix, und Caching sowie Batching gelten nur für geeigneten Traffic. Erstellen Sie die Schätzung aus gemessenen Traffic Shares und validieren Sie sie gegen die Rechnung.

45. Capacity Planning und Autoscaling

Capacity Planning für LLM Serving muss variable Request Costs, lang laufende Decode-Arbeit und sequenzabhängigen Memory berücksichtigen. Je nach Workload können KV Memory, Memory Bandwidth, Compute oder Interconnect die limitierende Resource sein.

Das theoretische Memory Ceiling für concurrent Requests ergibt sich aus dem KV-cache Budget:

max concurrent sequences=GPU memory−model weights−overheadper-sequence KV cache size\text{max concurrent sequences} = \frac{\text{GPU memory} - \text{model weights} - \text{overhead}}{\text{per-sequence KV cache size}}max concurrent sequences=per-sequence KV cache sizeGPU memory−model weights−overhead​

Nehmen wir für die Capacity-Arithmetic an, dass die Runtime ein KV Budget von 40 GiB für Llama 3.1 70B mit FP16 KV cache bereitstellt. Jede 4K-Sequence benötigt etwa 1,25 GiB, jede 128K-Sequence etwa 40 GiB. Das Budget reicht damit vor Allocator-, Runtime-, Workload-Variance- und SLO-Overhead für höchstens ungefähr 32 4K-Sequences oder eine 128K-Sequence. Deshalb treiben GPU-Auswahl und KV-cache-Optimierung den Capacity Plan direkt.

Die Capacity Formula für Fleet Sizing:

required GPUs=peak tokens/s×safety-factor multiplierper-GPU tokens/s at target SLO\text{required GPUs} = \frac{\text{peak tokens/s} \times \text{safety-factor multiplier}}{\text{per-GPU tokens/s at target SLO}}required GPUs=per-GPU tokens/s at target SLOpeak tokens/s×safety-factor multiplier​

Konvertieren Sie beide Rates vor der Division in dieselbe Zeiteinheit. Entscheidend ist der Zusatz „at target SLO“. Ein Safety-Factor-Multiplier wie 1,3 reserviert 30 % Headroom; wählen Sie ihn anhand von Burstiness, Failures und Recovery Time. Peak Token Throughput und SLO-compliant Throughput können bei steigender Concurrency stark auseinanderfallen. Benchmarken Sie mit der realen Prompt- und Output-Length-Distribution bei den erforderlichen TTFT- und TPOT-Thresholds, statt ein theoretisches Maximum zu verwenden.

GPU Utilization ist als einziges Autoscaling-Signal unzureichend, weil sie sowohl bei gesunder Verarbeitung als auch unter Overload hoch bleiben kann. Kombinieren Sie sie mit Queue Depth, KV-cache Utilization und Goodput Degradation. Tunen Sie Thresholds anhand von Load Tests; Werte wie 80 % KV Utilization sind Ausgangspunkte und keine universellen Limits. Diese Metrics werden in Abschnitt 43 eingeführt.

Scale-to-zero kann für Development- und Staging-Umgebungen mit langen Idle-Phasen geeignet sein. Serverless-Inference-Plattformen und Kubernetes-basierte Autoscaler wie KEDA können Idle Capacity entfernen, aber Savings und Cold-Start-Time hängen von Model Size, Image- und Weight-Caching sowie Infrastructure ab. Messen Sie Startup Time, bevor Sie dieselbe Policy für Latency-sensitive Production Traffic verwenden.

Das vernetzte System

Der KV-cache-Bedarf begrenzt die erreichbare Batch Size gemeinsam mit Weight Memory, Runtime Overhead und Request Lengths. Größere Batches können die Arithmetic Intensity erhöhen; die Workload Shape bestimmt jedoch weiterhin, ob Decode Memory-bound bleibt. Continuous Batching verbessert die Utilization und erhöht zugleich den Churn bei der KV Allocation; PagedAttention reduziert Fragmentation und Pre-Allocation-Waste durch Sequences variabler Length.

Auf der Training-Seite kann Lifecycle Cost dafür sprechen, ein kleineres Model mit mehr Tokens zu trainieren, wie Llama 3 8B zeigt. GRPO reduziert die Critic-State-Last von PPO. Im getesteten Small-Model-Setup von DeepSeek-R1 übertraf Distillation direktes RL. Dies sind Design Options, die evaluiert werden sollten, kein einzelnes Training Recipe.

Routing, Caching, Quantization und passend dimensionierte Hardware kumulieren nur dann, wenn jede Maßnahme gegen dasselbe Quality- und Latency Target gemessen wird.

Zentrale Prinzipien

  1. LLM Inference hat zwei klar getrennte Phasen. In üblichen Serving-Regimes tendiert Prefill zu Compute und Decode zu Memory Bandwidth; die Workload Shape kann die Grenze verschieben.
  2. Der KV cache ist oft eine zentrale Constraint. Seine Größe beeinflusst Batch Capacity und Memory Pressure. GQA, paged Allocation und KV Quantization adressieren unterschiedliche Teile dieser Constraint.
  3. Die GPU Memory Hierarchy erklärt viele Optimizations. FlashAttention und Kernel Fusion reduzieren kostspielige Data Movement, statt die Function des Models zu verändern.
  4. Continuous Batching und PagedAttention arbeiten zusammen. Ein veröffentlichter Vergleich berichtet 23x Throughput gegenüber seiner naiven Baseline; messen Sie den Gewinn in Ihrem Serving Stack.
  5. Chinchilla-optimal ist nicht Inference-optimal. Llama 3 8B wurde beispielsweise mit etwa 1.875 Tokens pro Parameter trainiert, um mehr Training Compute gegen günstigere Inference zu tauschen.
  6. GRPO und Distillation haben das Alignment Toolkit verändert. DeepSeek-R1 berichtete in seinen direkten RL-Experimenten stärkere Small-Model-Ergebnisse durch Distillation.
  7. Cost Optimization kumuliert nur über geeigneten Traffic. Model Quantization, Routing, Caching und Batch APIs benötigen separate Coverage- und Quality-Messungen, bevor ihre Savings multipliziert werden.
  8. Serving Hardware muss zum Bottleneck passen. Decode-heavy Workloads profitieren häufig von HBM Capacity und Bandwidth; Prefill-heavy Workloads gewichten Compute stärker.
