RAG-Evaluationsmetriken: Retrieval, Reranking, Generation

Ein RAG-System mit fehlerhaften Filtern kann monatelang laufen, ohne einen operativen Alarm auszulösen. Es liefert weiterhin Antworten und hält sein Latency-Ziel ein, aber diese Antworten basieren auf unvollständiger Evidenz. Recall@k gegenüber dem ursprünglichen Gold Set macht den Verlust sichtbar; Latency- und Availability-Dashboards tun das nicht.

Evaluation kann den Fehler nur erkennen, wenn jede Pipeline-Stufe eine eigene Metrik besitzt. Dieser Artikel ordnet gängige Failure Modes diesen Metriken zu – vom Document Parsing bis zum Production Monitoring.

Direkt zum Code?

Das ausführbare slavadubrov/rag-evals-demo-Repository wendet die Metriken auf SciFact an. make eval führt die Suite aus, und make benchmark vergleicht Chunking-, Embedding- und LLM-Konfigurationen. Die Notebooks 00–09 isolieren die einzelnen Metriken. Die Demo verwendet eingebettetes Qdrant und benötigt daher kein Docker.

TL;DR

  • Eine Pipeline-Stufe ohne Metrik ist eine Stufe, die unbemerkt ausfällt.
  • Ein nützlicher Evaluation Stack deckt Ingestion, Retrieval, Grounding der Generation, Ontology Conformance und Systemsignale ab. RAGAS, TruLens, DeepEval, Arize Phoenix und der TREC 2024 RAG Track liefern die Tools. Die Auswahl der Metriken übernehmen sie nicht.
  • Für metadata- und ontology-grounded RAG kann ein falsches Tag oder ein fragiler harter Predicate die Recall auf null reduzieren. Standard-Recall@k erkennt den Verlust, sofern das ursprüngliche Gold Set erhalten bleibt. Eine Metrik für False Exclusions durch Filter identifiziert die Ursache; Faithfulness kann trotzdem gut aussehen, weil das Model wahrheitsgemäß „Ich weiß es nicht“ gesagt hat.

Teil 1: Erfolg vor der Architektur definieren

Erstelle das Eval Set vor dem Architekturdiagramm. So erhält jede spätere Component-Entscheidung ein messbares Ziel.

Du kannst nicht zwischen BM25 und Dense Retrieval, Recursive und Semantic Chunking oder Cohere Rerank und BGE wählen, bevor klar ist, was optimiert werden soll. „Bessere Antworten“ ist keine Metrik. Ein beispielhafter Vertrag wäre: „Faithfulness ≥ 0,85 auf einem Golden Set mit 200 Queries, das unsere drei wichtigsten Intents abdeckt, bei p95 Latency < 1,5 s und einer False-Exclusion-Rate des Filters < 2 %.“ Die Zahlen sind Platzhalter; entscheidend ist, dass Quality, Coverage, Latency und Filtering explizite Gates besitzen.

Definiere das Harness, bevor du Retrieval-Code schreibst. Das erste Harness wird falsch sein und überarbeitet werden müssen. Eine Metrik zu ändern ist deutlich günstiger, als ein bereits ausgeliefertes System zu ändern.

Drei Pipeline-Layer und zwei Run Modes

Modernes RAG ist eine Pipeline – daher muss auch die Evaluation eine Pipeline sein. Keine einzelne Zahl erfasst jeden Failure Mode.

Production Evaluation besitzt drei Pipeline-Layer. Ingestion Evaluation fragt, ob Corpus und Index die Quelle erhalten. Query-Time Evaluation prüft, ob Rewriting, Filtering, Retrieval, Reranking und Context Assembly die richtige Evidenz gefunden haben. Answer and Production Evaluation untersucht, ob die Antwort diese Evidenz verwendet und ob die Quality unter Live-Traffic stabil bleibt. Werden die Layer zu einem Score zusammengefasst, kann ein Normalisierungsfehler in einem akzeptablen Answer Score verschwinden.

Die Layer beschreiben, wo ein Fehler auftritt. Offline und Online beschreiben, wann und gegen welche Daten geprüft wird. Offline Evaluation verwendet ein festes Dataset mit bekannter Ground Truth; sie ist reproduzierbar und gehört in Component Selection, A/B-Vergleiche und CI-Gates. Online Evaluation bewertet gesampelten Live-Traffic und erfasst Regeneration, Dwell Time, explizites Feedback und echten Query Drift. Sie ist verrauschter und schwieriger zu instrumentieren.

Jeder Pipeline-Layer kann Offline- und Online-Checks beitragen. Ein fixes Ingestion Corpus erkennt Parser-Regressionen vor dem Release, während Freshness- und Parse-Failure-Monitore Live-Updates abdecken. Ein fixes Query Set misst Retrieval vor dem Release, während gesampelte Live Traces Production Drift sichtbar machen. Nur Offline verpasst Änderungen im Live-Betrieb; nur Online macht Regressionen schwer reproduzierbar.

Component-Level vs. End-to-End

Es gibt zwei häufige Fehler. Eine reine End-to-End-Evaluation zeigt, dass das System defekt ist, aber nicht wo. Eine reine Component-Evaluation kann zeigen, dass jeder Teil besteht, während das Gesamtsystem weiterhin scheitert. Die Lösung sind einige zentrale End-to-End-Metriken für Go/No-Go-Entscheidungen sowie Component-Metriken für die Diagnose. Retrieval-Metriken erkennen Retriever-Regressionen, Generation-Metriken Generator-Regressionen und End-to-End Answer Correctness Integrationsfehler.

Teil 2: Evaluationspunkte auf die Pipeline abbilden

Ein Production-RAG-System ist größer als „Documents embedden, Chunks retrieven, ein LLM aufrufen“. Jede Stufe zwischen Document Acquisition und Answer Delivery kann ausfallen.

Jede Stufe im Diagramm hat mindestens eine Metrik. Eine Stufe ohne Metrik kann ausfallen, ohne dass es jemand bemerkt.

Die drei Lanes entsprechen den Stellen, an denen Evidenz verloren gehen kann. Die Ingestion Lane umfasst Parsing, Cleaning, Chunking, Embedding und Indexing. Die Query-Time Lane umfasst Rewriting, Filtering, Retrieval, Reranking und Context Assembly. Die Answer-and-Production-Lane umfasst Faithfulness, Citation Verification, User Signals, Drift, Latency und Kosten.

Fehler verstärken sich entlang der Kette: Schlechtes Parsing begrenzt Chunking, schlechtes Chunking begrenzt Retrieval, und schlechtes Retrieval begrenzt sowohl Reranking als auch Generation. Faithfulness misst nur die finale Antwort – niemals die vorgelagerte Ursache.

Teil 3: Ingestion Evaluation

Viele Production-RAG-Fehler beginnen bei der Ingestion. Das System funktioniert mit sauberen Testdokumenten und scheitert dann an realen PDFs, Scans, Tabellen und unstrukturierten Corpus-Seiten.

Document Acquisition und Parsing

Was zu messen ist:

  • Text Extraction Completeness: extracted_chars / expected_chars auf einem gelabelten Sample, berechnet pro Document Class. Es gibt kein kanonisches Package – schreibe ein kleines Harness, das Parser-Output mit einer manuell bereinigten Referenz vergleicht. Achte auf fehlende Fußnoten, Header und Captions.

  • OCR Accuracy: CER (Character Error Rate) und WER (Word Error Rate), die Standardmetriken für Speech und OCR:

    CER=S+D+IN,WER=Sw+Dw+IwNw\text{CER} = \frac{S + D + I}{N}, \qquad \text{WER} = \frac{S_w + D_w + I_w}{N_w}CER=NS+D+I​,WER=Nw​Sw​+Dw​+Iw​​

    Dabei sind SSS, DDD und III zeichenbasierte Substitutions, Deletions und Insertions, während NNN die Anzahl der Referenzzeichen bezeichnet (Subscript www für die Wortversion). Verwende nicht für jedes Corpus dieselbe CER-Grenze. Kalibriere sie nach Document Class und nachgelagertem Answer Loss; gedruckter Text, Handschrift und mehrsprachiges Material besitzen unterschiedliche Error Profiles. Berechne mit jiwer (jiwer.cer(refs, hyps), jiwer.wer(refs, hyps)) oder dem Hugging Face evaluate. Für Evaluation Corpora sind FUNSD und SROIE öffentliche Benchmarks.

print(f"WER = {wer(refs, hyps):.3f}")  # WER = 0.286

  • Table Extraction Fidelity: TEDS (Tree-Edit-Distance-based Similarity) misst, wie nahe ein vorhergesagter HTML-Table-Tree an der Referenz liegt, normalisiert anhand der Größe des größeren Trees. Siehe Zhong et al., 2020 (PubTabNet):

    TEDS(Ta,Tb)=1−EditDist(Ta,Tb)max⁡(∣Ta∣,∣Tb∣)\text{TEDS}(T_a, T_b) = 1 - \frac{\text{EditDist}(T_a, T_b)}{\max(|T_a|, |T_b|)}TEDS(Ta​,Tb​)=1−max(∣Ta​∣,∣Tb​∣)EditDist(Ta​,Tb​)​

    TEDS verwendet sowohl Structure (Rows, Columns, Spans) als auch Cell Content; TEDS-S entfernt den Content und bewertet nur die Structure. Referenzimplementierung: PubTabNets teds.py (verwendet intern apted). Für Evaluation Corpora siehe PubTabNet, FinTabNet und SciTSR. Naive Parser scheitern häufig an Tabellen; führe Benchmarks durch, bevor du ihnen vertraust.

  • Layout-/Structure Preservation: Heading-Reihenfolge, Listenintegrität und Reading Order in mehrspaltigen PDFs. Verwende DocLayNet als gelabelten Benchmark. Ein direkter Vergleich kann einen Element Parser wie unstructured, eine PDF Library wie pymupdf und einen VLM Parser wie docling umfassen.

Vergleiche verschiedene Parser-Familien, etwa eine Tesseract-Baseline, ein VLM-basiertes OCR Model und den Kandidaten deines Vendors. Verwende ein stratifiziertes Sample realer Document Classes bei fester DPI – einschließlich sauberer Scans, Fotos, Tabellen, mehrsprachigem Text, Mathematik und Handschrift. Berichte CER oder WER pro Klasse und TEDS für Tabellenseiten.

Cleaning und Normalization

  • Boilerplate Removal Accuracy: Precision/Recall gegenüber von Menschen gelabelten Boilerplate-Spans. Aggressives Entfernen löscht relevanten Content; zu zurückhaltendes Entfernen verschmutzt Embeddings. Zu vergleichende Tools: trafilatura, jusText, Resiliparse. Barbaresi (2021) vergleicht sie direkt.

  • Unicode Normalization: Der Prozentsatz der Documents mit identischem NFC- und NFKC-Output (berechnet mit dem Standardbibliotheks-unicodedata.normalize) ist ein nützliches Drift-Signal. Abweichungen führen dazu, dass Zero-Width-Joiner und ähnlich aussehende Zeichen die Retrieval Recall beschädigen.

  • Language Detection Accuracy: F1 auf einem gelabelten multilingualen Sample. Für multilinguale Indexe ist dies entscheidend. Nutze fasttext-langdetect (Facebooks lid.176), lingua-py oder cld3. FLORES-200 liefert Evaluationstext für 200 Sprachen; für den Test-Slice sollte jedoch dein Production Language Mix maßgeblich sein.

  • Deduplication Effectiveness (MinHash / LSH): Precision/Recall des Near-Duplicate Detectors gegenüber einem manuell gelabelten Set. Die Grundidee: Jaccard Similarity J(A,B)=∣A∩B∣∣A∪B∣J(A, B) = \frac{|A \cap B|}{|A \cup B|}J(A,B)=∣A∪B∣∣A∩B∣​ zwischen Document-Shingle-Sets mit kkk Zufalls-Permutations-Hashes schätzen (Broder, 1997) und Near-Duplicates durch LSH-Banding in Buckets gruppieren (Indyk & Motwani, 1998). Sweep über Hash Count und Jaccard Threshold auf deinem Corpus. Tracke False-Merge-Rate (beschädigt Antworten) getrennt von Missed-Merge-Rate (verschwendet Index-Space). datasketch liefert die unten verwendete Implementierung; die Parameter sind illustrativ:

    from datasketch import MinHash, MinHashLSH

def shingles(text: str, k: int = 5) -> set[str]:
    text = text.lower()
    return {text[i:i + k] for i in range(len(text) - k + 1)}

def to_minhash(text: str, num_perm: int = 128) -> MinHash:
    m = MinHash(num_perm=num_perm)
    for s in shingles(text):
        m.update(s.encode("utf-8"))
    return m

docs = {
    "d1": "Mars has two moons, Phobos and Deimos.",
    "d2": "Mars has two moons, Phobos and Deimos!",   # near-dup
    "d3": "Curiosity rover landed on Mars in 2012.",
}

lsh = MinHashLSH(threshold=0.8, num_perm=128)
for did, text in docs.items():
    lsh.insert(did, to_minhash(text))

print(sorted(lsh.query(to_minhash(docs["d1"]))))  # ['d1', 'd2']

  • PII Scrubbing: Precision und Recall, jeweils pro Entity Type (E-Mails, SSNs, Namen, Adressen). Recall Errors erzeugen Compliance-Risiken; Precision Errors verschlechtern die Answer Quality. Lege den Operating Point gemeinsam mit dem Legal Team fest. Kandidaten sind Microsoft Presidio, scrubadub oder ein Fine-Tuned-NER-Model auf einem gelabelten Set.

Chunking bestimmt die Retrieval-Quality

Chunking kann selbst bei unverändertem Embedding Model eine mehrfache Recall-Lücke erzeugen. Im NVIDIA Vendor Benchmark von 2025 erzielte Page-Level Chunking bei paginierten Documents die höchste Accuracy und niedrigste Varianz. Interpretiere dieses Ergebnis als Evidenz für das getestete Corpus, nicht als universellen Gewinner.

Semantic Chunking gruppiert benachbarte Sätze anhand ihrer Embedding Similarity und trennt an unähnlichen Grenzen. LangChains SemanticChunker und LlamaIndexs SemanticSplitterNodeParser implementieren diese Strategie. Sie kann gegenüber festen Windows die Recall verbessern, wenn thematische Grenzen entscheidend sind.

Recursive Character Splitting versucht zunächst Paragraph Breaks, dann Sentence Breaks und anschließend Word Breaks, bis jeder Chunk in die Zielgröße passt. LangChains RecursiveCharacterTextSplitter implementiert diese Sequenz. Wähle Kandidaten für Window und Overlap passend zur Document Structure und überlasse dem Golden Set die endgültige Auswahl.

Zu trackende Metriken:

  • Chunk Coherence: coherence=cos⁡(si,sj)‾within−cos⁡(si,sj)‾across boundary\text{coherence} = \overline{\cos(s_i, s_j)}_{\text{within}} - \overline{\cos(s_i, s_j)}_{\text{across boundary}}coherence=cos(si​,sj​)​within​−cos(si​,sj​)​across boundary​, wobei sis_isi​ Sentence Embeddings sind. Gesunde Chunks sind intern ähnlich und an den Grenzen unähnlich. Berechne dies mit sentence-transformers plus cosine_similarity von scikit-learn.
  • Boundary Quality: manuell gelabeltes „Ist dies eine sinnvolle Trennung?“ auf einem Sample sowie ein Structural Check, dass Chunks keine Tabellen, Listen oder nummerierten Sections aufteilen.
  • Optimal Chunk Size: Token Sizes (128, 256, 512, 1024) sweepen und Recall@k gegen die Size auf dem Golden Set plotten. Wähle den Knee Point – nicht den Wert aus irgendeinem Tutorial.
  • Overlap Effectiveness: Mehrere Overlap Fractions ablationieren und Recall@k messen. Erhöhe den Overlap nicht weiter, sobald die lokale Recall Curve abflacht oder die Duplication Cost den Gewinn überwiegt.
  • Chunk Attribution Fidelity: Anteil der Chunks mit verifizierbarem Source Pointer (Page Number, Section Anchor, Doc ID). Das ist Voraussetzung für Auditability.
  • Late vs. Early Chunking: Late Chunking (Günther et al., 2024) embed­det das vollständige Document und segmentiert es anschließend, wodurch globaler Context erhalten bleibt (Referenzimplementierung in jina-embeddings-v3). Contextual Retrieval (Anthropic, 2024) stellt jedem Chunk LLM-generierten Context voran. Beides verursacht zusätzliche Kosten. Benchmarke auf deinem Corpus, bevor du eine der Varianten übernimmst.

Meine Einschätzung: Structural Chunking – Trennung an Headings, Tabellen und Sections, implementiert etwa durch Parser wie unstructured.io oder durch Traversieren des bereits erzeugten AST – wird zu selten genutzt. Wenn deine Documents Structure besitzen, verwende sie vor zusätzlichen Similarity-Heuristiken. Recursive Character Splitting ist die Baseline; Semantic Chunking rechtfertigt den Overhead vor allem bei unstrukturierter Prosa.

Metadata Extraction und Enrichment

  • NER Precision/Recall/F1: pro Entity Type auf einem gelabelten Subset. Verwende den Standard im CoNLL-/MUC-Stil. Berechne mit seqeval (from seqeval.metrics import f1_score) für die BIO-/IOB-Tag-bewusste Variante oder mit scikit-learn für Span-Set-Vergleiche. CoNLL-2003 und OntoNotes 5.0 sind die kanonischen Referenz-Corpora.
  • Relation Extraction F1: für Ontology-Grounded Systems noch wichtiger. Label ein nach Relation Type und Document Class stratifiziertes Set manuell. TACRED und DocRED sind öffentliche Benchmarks; mögliche Implementierungen sind opennre und spaCy.
  • Title-/Heading-Extraction-Accuracy: Exact Match plus normalisierte Levenshtein Similarity (1−edit_dist(a,b)max⁡(∣a∣,∣b∣)1 - \frac{\text{edit\_dist}(a, b)}{\max(|a|, |b|)}1−max(∣a∣,∣b∣)edit_dist(a,b)​) gegenüber der Ground Truth – python-Levenshtein oder rapidfuzz liefern beides mit einem Aufruf.
  • Hierarchical Metadata Preservation: Anteil der Chunks, die Parent Section, Parent Document und Ancestry Path korrekt behalten. Diese Metrik entscheidet, ob dein RAG Fragen wie „Was sagt das Kind von Policy X?“ beantworten kann.

Embedding Generation

  • Model-Selection-Benchmarks: MTEB für allgemeine Fähigkeiten (nDCG@10 ist die zentrale Metrik; das MTEB Python Package reproduziert die Rangliste lokal), BEIR für Zero-Shot-Generalization und MIRACL für multilingual Retrieval. Die besten Retrieval Models liegen in einem engen nDCG@10-Bereich, aber englische MTEB-Scores sagen die Performance in Low-Resource-Sprachen nur schlecht voraus.
  • Domain-Specific Evaluation: Interpretiere den Rang in einem allgemeinen Benchmark nicht als Domain-Ergebnis. Erstelle anhand der Coverage Matrix und der tolerierbaren Unsicherheit ein Domain Golden Set. Reranke Kandidaten darauf mit ranx oder pytrec_eval. Ein Domain Set kann die Leaderboard-Reihenfolge umkehren; veröffentliche Dataset Slice, Retrieval Protocol und Confidence Interval mit dem Ergebnis.
  • Embedding Drift Detection: Tracke distributional KL oder Model-Based Drift zwischen einem festen Reference Window und Production Embeddings aus einem Rolling Window; miss zusätzlich die Nearest-Neighbor Stability auf einem festen Probe Set. evidently und alibi-detect implementieren model-basierte und statistische Detectors. Evidentlys Comparative Study ist eine Vendor-Evaluation; vergleiche Methoden mit bekannten Shifts in deinen eigenen Embeddings.
  • Multi-Vector vs. Single-Vector: Late Interaction erhält Token-Level Representations, anstatt jedes Document in einen Vector zu kollabieren. ColBERT ist das kanonische Design; Referenzimplementierungen gibt es in RAGatouille und PyLate. Die reichhaltigere Representation erhöht Index- und Retrieval-Kosten. Vergleiche Quality, Storage und Latency mit einer Single-Vector-Baseline auf demselben Domain Set.

Index Construction

  • Recall@k unter Approximation: Vergleiche den ANN-Index mit einer exakten Brute-Force-Baseline bei gleichem k – in FAISS ist das IndexHNSWFlat (oder IndexIVFFlat) gegenüber IndexFlatIP/IndexFlatL2. Lege den akzeptablen Recall Loss anhand deines Downstream-Quality-Budgets fest. Das ann-benchmarks-Projekt verfolgt Recall–QPS-Pareto-Kurven über mehrere Libraries.
  • HNSW Tuning: HNSW (Hierarchical Navigable Small World – ein mehrschichtiger Proximity Graph; siehe Malkov & Yashunin, 2018, implementiert in hnswlib, FAISSs IndexHNSWFlat und den meisten Vector DBs) besitzt drei Stellschrauben: M (Graph Fan-Out), efConstruction (Candidate Width beim Build) und efSearch (Candidate Width bei Queries). Starte mit den dokumentierten Library-Defaults und sweepe die Parameter, bis die Recall–Latency-Kurve die Anforderungen des Evaluation Sets erfüllt.
  • IVF Tuning: IVF (Inverted File Index – Vectors per K-Means in nlist Cells partitionieren und zur Query-Zeit die nprobe nächsten Cells durchsuchen; siehe FAISS IndexIVFFlat und IndexIVFPQ). Sweepe nlist und nprobe gegenüber Exact-Search-Recall und Latency. Benchmarke gefilterte Queries separat, da Indexfamilien und Vector Databases Filter Traversal unterschiedlich implementieren.
  • Update Freshness Lag: Zeit vom Document Commit bis zur Retrieval-Fähigkeit. Tracke p50 und p99. Für Systeme mit regulatorischen Anforderungen zusätzlich den Anteil der Queries, die gegen veraltete Indexe laufen.

Teil 4: Query-Time Evaluation

Die Query-Time Lane enthält die Metriken zur Diagnose des Retrieval Paths. Recall@k allein zeigt nicht, ob Rewriting, Filtering, Reranking oder Context Assembly den Fehler verursacht hat.

Query Understanding und Rewriting

  • Query Expansion Quality: Recall@k Uplift auf dem Golden Set, Expanded Query gegenüber Raw Query. Definiere Minimum Gain und Unsicherheit vor dem Test. Wenn die Expansion dieses lokale Gate nicht erreicht, rechtfertigt sie ihre Latency und Kosten nicht. Klassische PRF-Baselines wie RM3 und Bo1 bleiben nützliche Sanity Checks; LLM-basierte Expansion muss sie übertreffen.
  • HyDE Evaluation: HyDE (Gao et al., 2022) erzeugt mit dem LLM eine hypothetische Antwort, embed­det sie und führt darauf Retrieval aus. Das bringt zusätzliche Generation Latency und einen neuen Failure Surface. Miss Recall@10 getrennt für In-Domain-, Out-of-Domain- und Low-Confidence-Slices und entscheide dann, ob HyDE in den Default Path, einen Fallback oder in keinen der beiden gehört.
  • Multi-Query Generation: Recall@k der Union von N Rewrites gegenüber einer einzelnen Query. Sweep N und wähle einen Punkt auf der Recall–Latency-Frontier. Implementierungen: LangChains MultiQueryRetriever, LlamaIndexs QueryFusionRetriever.
  • Intent Classification Accuracy: Standard Precision/Recall/F1 pro Intent (berechne mit sklearn.metrics.classification_report); die operative Metrik ist jedoch Routing Correctness: Wird die richtige Downstream-Pipeline aufgerufen?
  • Adaptive Routing: Adaptive-RAG (Jeong et al., NAACL 2024) zeigt, dass nicht jede Query dieselbe Retrieval Strategy benötigt. Tracke Router Accuracy als Classification Problem gegenüber einem gelabelten Set aus „kein Retrieval / One-Shot / Iterative“.

    "q4": ["d1", "d2", "d3", "d6", "d8", "d9", "d10", "d12", "d13", "d14"],
}

def recall_at_k(ranked, gold_set, k):
    if not gold_set:
        return 0.0
    hit = sum(1 for d in ranked[:k] if d in gold_set)
    return hit / len(gold_set)

def reciprocal_rank(ranked, gold_set):
    # MRR contribution per query: 1/rank of the first relevant doc.
    for rank, d in enumerate(ranked, start=1):
        if d in gold_set:
            return 1.0 / rank
    return 0.0

def ndcg_at_k(ranked, gold_set, k):
    # binary relevance: rel ∈ {0, 1}
    gains = [1.0 if d in gold_set else 0.0 for d in ranked[:k]]
    dcg = sum(g / log2(i + 2) for i, g in enumerate(gains))
    # ideal DCG: all gold docs ranked first, capped by k
    n_gold_in_topk = min(k, len(gold_set))
    idcg = sum(1.0 / log2(i + 2) for i in range(n_gold_in_topk))
    return dcg / idcg if idcg else 0.0

K = 5
print(f"Recall@{K}: {mean(recall_at_k(runs[q], gold[q], K) for q in gold):.3f}")
print(f"MRR:       {mean(reciprocal_rank(runs[q], gold[q]) for q in gold):.3f}")
print(f"nDCG@{K}:  {mean(ndcg_at_k(runs[q], gold[q], K) for q in gold):.3f}")

Hybrid Retrieval und Reciprocal Rank Fusion

BM25 ist ein sparsener lexikalischer Scorer, der Exact-Term-Matching, Term Weighting und Length Normalization kombiniert. Er ist in rank_bm25, Elasticsearch, OpenSearch und den meisten Search Engines verfügbar.

Reciprocal Rank Fusion (Cormack, Clarke und Buettcher, SIGIR 2009) kombiniert BM25- und Dense-Rankings anhand ihrer Position. Die ursprüngliche k=60-Einstellung ist eine nützliche Baseline. RRF ist Score-agnostic und vermeidet damit die Cross-Lane-Normalisierung, die für lineare Interpolation nötig wäre. Mit einem ausreichend großen gelabelten Set kannst du zusätzlich eine Convex Combination testen und α tunen.

Hybrid Retrieval mit einem Cross-Encoder Reranker verbessert häufig technische, logartige und Code-Corpora. Auf stark semantischen Corpora kann der Gain klein sein. Vergleiche stets Dense-Only und Sparse-Only, da eine schlechte Fusion beide Eingangslanes unterbieten kann.

Die Implementierung passt in wenige Zeilen.

from collections import defaultdict

# two retrieval lanes: dense embeddings and BM25.
dense  = ["d3", "d7", "d1", "d4", "d2", "d9", "d10"]
sparse = ["d2", "d3", "d8", "d1", "d11", "d4", "d6"]

def rrf(rankings: list[list[str]], k: int = 60) -> list[tuple[str, float]]:
    """Reciprocal Rank Fusion (Cormack et al., SIGIR 2009).

    score(d) = sum over rankings of 1 / (k + rank(d))
    Score-agnostic: only rank position matters. k=60 is the canonical default.
    """
    scores: dict[str, float] = defaultdict(float)
    for ranking in rankings:
        for rank, doc in enumerate(ranking, start=1):
            scores[doc] += 1.0 / (k + rank)
    return sorted(scores.items(), key=lambda kv: kv[1], reverse=True)

fused = rrf([dense, sparse], k=60)
for doc, score in fused[:5]:
    print(f"{doc}  score={score:.5f}")
# d3  score=0.03252   <- rank 1 dense, rank 2 sparse
# d2  score=0.03178   <- rank 5 dense, rank 1 sparse
# d1  score=0.03150

Beachte, was RRF nicht tut: Es betrachtet niemals die Raw Similarity Scores. Ein Dense Retriever mit Cosine 0,98 und eine BM25-Lane mit Score 17,4 sind nicht direkt vergleichbar. Bei Normalisierung mit z-Scores oder Min-Max-Scaling kann die Lane mit der höchsten Varianz in diesem Batch bevorzugt werden.

RRF verwendet ausschließlich den Rang. Platziert ein Retriever ein Document an Position 2, ist diese Stimme 1 / (60 + 2) wert – unabhängig vom Raw Score.

Reranking

  • ΔnDCG / ΔMRR: Uplift gegenüber No-Rerank auf dem Golden Set und bei der Depth, die die Anwendung tatsächlich verwendet. Führe die Retrieval-Metriken mit und ohne Reranker auf identischen Candidate Sets aus.
  • Cross-Encoder vs. Bi-Encoder: Ein Bi-Encoder embed­det Query und Document unabhängig voneinander (ein Vector pro Seite) und bewertet per Dot Product. Ein Cross-Encoder konkateniert Query und Document und führt einen Forward Pass aus, der beide gemeinsam per Attention verarbeitet. Cross-Encoder tauschen einen Forward Pass pro Candidate gegen reichhaltigere Query–Document Interaction. Referenzimplementierung: sentence-transformers CrossEncoder. Benchmarke Relevance und Latency auf benannter Hardware, Batch Size und Candidate Depth; übertrage Ergebnisse eines Models oder Managed Services nicht auf eine andere Umgebung.
  • Listwise vs. Pointwise: Pointwise bewertet jedes (Query, Document)-Paar unabhängig; Listwise bewertet die gesamte Candidate List gemeinsam und kann Candidates vergleichen. Evaluiere beide auf denselben Candidate Sets. Kalibriere Score Thresholds pro Model und Corpus, statt ein veröffentlichtes Beispiel als portabel zu behandeln.
from sentence_transformers import CrossEncoder

    "To rotate prod DB creds, run the `rotate-secrets` GitHub Action.",

Vergleiche diesen Gain mit kleineren Retrieval-Änderungen, bevor du die nächste Optimierung auswählst.

Context Construction und Lost-in-the-Middle

Viele Fälle von „gutem Retrieval, schlechter Antwort“ beginnen bei der Context Construction.

  • Context Relevance: Relevance Score pro Chunk aus RAGAS ContextRelevance oder einem Cross-Encoder, aggregiert als Mittelwert und als Anteil der Chunks unter einem Threshold.
  • Context Utilization: Wie viele der in den Context gelegten Chunks wurden tatsächlich zitiert oder in der Antwort verwendet? Berechne ∣cited chunks∣∣retrieved chunks∣\frac{|\text{cited chunks}|}{|\text{retrieved chunks}|}∣retrieved chunks∣∣cited chunks∣​ auf einem gelabelten Sample. Lege den Threshold anhand von Answer Quality und Token Cost fest, nicht anhand eines universellen Prozentsatzes.
  • Lost-in-the-Middle Detection: Synthetische Eval, bei der der Gold Chunk an Position {first, middle, last} eines langen Contexts platziert und Answer Correctness gemessen wird. Die U-förmige Degradation ist real und in Liu et al. (TACL 2023) dokumentiert. Moderne Models sind besser als Models aus dem Jahr 2023, aber der Bias bleibt bestehen. Gegenmaßnahmen: Rerank und ordne Top-k neu, sodass der bestbewertete Chunk am Anfang oder Ende steht (LangChains LongContextReorder tut genau das), oder komprimiere mittlere Chunks aggressiv. Miss mit einer positionsstratifizierten Eval statt nur mit einem aggregierten Score. Eine ausführbare Beispiel-Eval befindet sich in Notebook 06 (Modul: evaluation/lost_in_middle.py).
  • Context Compression: Berichte Compression Ratio (Input Tokens / Output Tokens) zusammen mit Answer Correctness. Tools sind LangChains ContextualCompressionRetriever und LongLLMLingua. Definiere den maximal akzeptablen Correctness Loss anhand von Risiko und Token Budget der Anwendung und verwerfe Konfigurationen, die ihn überschreiten.

Teil 5: Filter False-Exclusion-Rate

Diese Metrik erhält einen eigenen Abschnitt, weil aggregierte Retrieval Scores einen Miss nicht dem Filter zuordnen können.

Ein harter Metadata-Filter wie tenant_id = X AND product = Y AND locale = en-US kann die effektive Recall auf null reduzieren. Korrekt implementierte Recall@k erkennt den Verlust, weil ihr Nenner das ursprüngliche Set relevanter Documents bleibt. Sie sagt jedoch nicht, ob Filter, Retriever oder Ranker den Miss verursacht hat. Faithfulness kann weiterhin gut aussehen, weil die Antwort nur gegen den unvollständigen Retrieved Context bewertet wird; das Model hat korrekt „Ich weiß es nicht“ gesagt.

Der hervorgehobene Branch ist der häufige Failure Mode: Das richtige Document existiert, aber der Filter entfernt es vor dem Retrieval. Recall@k registriert den Drop; nur die Exclusion Rate ordnet ihn dem Predicate zu.

Die Metrik

filter_false_exclusion_rate =
    (# queries where all gold docs were excluded by metadata filter) /
    (# queries with at least one gold doc)

Diese Definition auf Query-Level zählt katastrophale Exclusions: Kein relevantes Document überlebt. Bei Queries mit mehreren Gold Documents macht Standard-Recall@k weiterhin partielle Verluste sichtbar; ergänze eine Exclusion Rate pro Document, wenn diese Grenze relevant ist. Du benötigst (a) Ground-Truth-Doc-IDs für jede Eval Query und (b) Instrumentation, die die angewendeten Filter Predicates loggt, nicht nur die finalen Ergebnisse. Lege das Target anhand der Kosten einer ausgeschlossenen gültigen Antwort und des Confidence Intervals deines Production Samples fest.

Hier ist eine funktionierende Implementierung. Sie vergleicht korrekte Standard-Recall mit einem ungültigen Evaluator, der Relevance nach dem Filtering neu definiert.

# A small worked example where hard filters remove relevant documents.
docs = [
    {"id": "d1", "tenant": "acme",   "locale": "en-US"},
    {"id": "d2", "tenant": "acme",   "locale": "en-GB"},
    {"id": "d3", "tenant": "globex", "locale": "en-US"},
    {"id": "d4", "tenant": "acme",   "locale": "en-US"},
    {"id": "d5", "tenant": "acme",   "locale": "de-DE"},
]

queries = [
    # the gold doc lives in en-GB but the dynamic filter forced en-US
    {"qid": "q1", "gold": {"d2"}, "filter": lambda d: d["locale"] == "en-US"},
    # the gold doc is correctly within the tenant filter
    {"qid": "q2", "gold": {"d4"}, "filter": lambda d: d["tenant"] == "acme"},
    # the gold doc is in a different tenant and gets dropped
    {"qid": "q3", "gold": {"d3"}, "filter": lambda d: d["tenant"] == "acme"},
    # the gold doc passes the filter (de-DE locale match)
    {"qid": "q4", "gold": {"d5"}, "filter": lambda d: d["locale"] == "de-DE"},
]

def filter_false_exclusion_rate(queries, docs):
    n_with_gold, n_excluded = 0, 0
    for q in queries:
        if not q["gold"]:
            continue
        n_with_gold += 1
        survivors = {d["id"] for d in docs if q["filter"](d)}
        if not (q["gold"] & survivors):
            n_excluded += 1
    return n_excluded / n_with_gold if n_with_gold else 0.0

rate = filter_false_exclusion_rate(queries, docs)
print(f"filter_false_exclusion_rate = {rate:.2%}")
# filter_false_exclusion_rate = 50.00%

# Correct Recall@k keeps the original gold set as its denominator.
def standard_recall_at_k(queries, docs, k=10):
    recalls = []
    for q in queries:
        # demo only: the survivor set stands in for a ranked run.
        # A real harness ranks the survivors first, then slices to k.
        survivors = [d for d in docs if q["filter"](d)][:k]
        survivor_ids = {d["id"] for d in survivors}
        recalls.append(len(q["gold"] & survivor_ids) / len(q["gold"]))
    return sum(recalls) / len(recalls) if recalls else 0.0

print(f"standard recall@10 = {standard_recall_at_k(queries, docs):.2%}")
# standard recall@10 = 50.00%

# INVALID: rebuilding the gold set after filtering changes the question.
# It drops queries whose relevant documents did not survive, then scores 100%.
def invalid_recall_over_filtered_gold(queries, docs, k=10):
    recalls = []
    all_doc_ids = {d["id"] for d in docs}
    for q in queries:
        all_survivors = {d["id"] for d in docs if q["filter"](d)}
        filtered_gold = q["gold"] & all_doc_ids & all_survivors
        if not filtered_gold:
            continue
        top_k_ids = set(list(all_survivors)[:k])
        recalls.append(len(filtered_gold & top_k_ids) / len(filtered_gold))
    return sum(recalls) / len(recalls) if recalls else 0.0

invalid = invalid_recall_over_filtered_gold(queries, docs)
print(f"INVALID recall (filtered gold) = {invalid:.2%}")
# INVALID recall (filtered gold) = 100.00%

assert rate == 0.5
assert standard_recall_at_k(queries, docs) == 0.5
assert invalid == 1.0

Die Hälfte der Queries verliert ihr Gold Document durch den Filter, daher fällt korrekte Recall@10 auf 50 %. Dieser Score erkennt das Symptom, kann es aber nicht zuordnen. Die False-Exclusion-Rate zeigt, dass das Predicate zwei Antworten vor dem Retrieval entfernt hat. Der absichtlich ungültige Evaluator meldet 100 %, weil er diese Fehler aus dem Gold Set entfernt. Kein Model kann ein herausgefiltertes Document zurückholen.

Begleitmetrik: Predicate Precision und Recall

Wenn Filtering dynamisch erfolgt, etwa weil ein LLM Filter Predicates aus der Query extrahiert, behandle den Predicate Extractor als Classification Model und evaluiere ihn entsprechend. Miss Predicate Precision und Recall auf einem gelabelten Set von (query, correct predicate)-Paaren. Eine Predicate Error Rate entspricht nicht direkt demselben Point Loss bei Retrieval Recall; miss daher, wie häufig diese Fehler ein Gold Document ausschließen. Sobald ein harter Filter das Gold Document entfernt, hilft kein Reranking mehr.

Soft Boost vs. Hard Filter

Diese Metrik erzwingt eine Designentscheidung. Verwende Hard Filters, wenn Correctness binär ist: Legal Jurisdiction, ACL-Grenzen, Published vs. Draft. Verwende Soft Boosts, wenn Relevance abgestuft ist: Locale Preference, Recency, Version. Ohne Exclusion-Rate-Messung ist die falsche Wahl schwer erkennbar.

Die messbare Entscheidungsregel:

For each filter predicate F:
  hard_recall_F  = retrieval_recall@k with F as a hard filter
  soft_recall_F  = retrieval_recall@k with F as a +0.X rerank boost
  hard_precision = relevant_in_top_k / k under hard filter
  soft_precision = relevant_in_top_k / k under soft boost
  exclusion_rate = % of queries where the gold doc was filtered out (hard)

Use hard filter only if exclusion_rate < ε AND hard_precision >> soft_precision.
Otherwise prefer soft boost.

Wähle ε anhand des Schadens einer False Exclusion, des Nutzens zusätzlicher Precision und der Größe des Evaluation Samples. Ein eigener Beitrag zu diesem Trade-off ist geplant; siehe die am Ende genannten Follow-ups.

def extract_claims(answer: str) -> list[str]:
    # Production: an LLM call that decomposes the answer.
    # Demo: split on sentence-final punctuation.
    return [c.strip() for c in answer.replace("?", ".").replace("!", ".").split(".") if c.strip()]

def verify_claim(claim: str, context: str) -> bool:
    # Production: an NLI (natural-language inference) model or LLM judge.
    # Demo: a deterministic stand-in so the example runs offline.
    entailed_pairs = {
        "Mars has two moons": True,
        "Phobos and Deimos orbit Mars": True,
        "Mars has a thick atmosphere": False,  # unsupported by context
        "Curiosity landed in 2012": True,
    }
    for k, v in entailed_pairs.items():
        if k.lower() in claim.lower() or claim.lower() in k.lower():
            return v
    words = [w.lower() for w in claim.split() if len(w) > 3]
    return all(w in context.lower() for w in words) if words else False

context = (
    "Mars has two moons, Phobos and Deimos. NASA's Curiosity rover "
    "landed on Mars in 2012."
)
answer = (
    "Mars has two moons. Phobos and Deimos orbit Mars. "
    "Mars has a thick atmosphere. Curiosity landed in 2012."
)

claims = extract_claims(answer)
verdicts = [(c, verify_claim(c, context)) for c in claims]
faithfulness = sum(1 for _, ok in verdicts if ok) / len(verdicts)
for c, ok in verdicts:
    print(f"  [{'✓' if ok else '✗'}] {c}")
print(f"faithfulness = {faithfulness:.2f}")
# faithfulness = 0.75   (one unsupported claim about the atmosphere)

FActScore (Min et al., EMNLP 2023) zerlegt Long-Form-Generations in atomare Fakten, ruft Evidenz pro Fakt ab, labelt jeden als supported / not-supported und berichtet den Anteil unterstützter Fakten:

FActScore=∣supported atomic facts∣∣total atomic facts∣\text{FActScore} = \frac{|\text{supported atomic facts}|}{|\text{total atomic facts}|}FActScore=∣total atomic facts∣∣supported atomic facts∣​

Referenzimplementierung: shmsw25/FActScore. Das funktioniert gut für Biografien, Summaries und andere Long-Form-Outputs. Vorsicht: Wiederholte triviale Fakten können den Score aufblasen, und „MontageLie“-Angriffe – wahre Fakten in irreführender Reihenfolge – können die Metrik täuschen. VeriScore behandelt Claims mit notwendigen Modifiers; der Core-Filter hilft gegen Fact Padding.

Citation Accuracy

Tracke Citation Precision (zitierte Spans unterstützen den Claim tatsächlich) und Citation Recall (Claims, die zitiert werden sollten, sind zitiert):

cite_precision=∣cited spans that support a claim∣∣cited spans∣,cite_recall=∣claims with at least one supporting cited span∣∣claims that should be cited∣\text{cite\_precision} = \frac{|\text{cited spans that support a claim}|}{|\text{cited spans}|}, \quad \text{cite\_recall} = \frac{|\text{claims with at least one supporting cited span}|}{|\text{claims that should be cited}|}cite_precision=∣cited spans∣∣cited spans that support a claim∣​,cite_recall=∣claims that should be cited∣∣claims with at least one supporting cited span∣​

Der TREC 2024 RAG Track definiert ein reproduzierbares Support-Evaluation-Protokoll. Thakur et al. (SIGIR 2025) berichten, dass GPT-4o bei manueller Bewertung ohne Vorbearbeitung in 56 % der Fälle mit Human Judges übereinstimmte; nach Post-Editing der LLM Predictions stieg der Wert auf 72 %. Das ist unter diesen Bedingungen ein Force Multiplier, kein Ersatz für Human Assessment in High-Stakes-Kontexten. Als automatisierte Approximation implementiert ALCE (Gao et al., EMNLP 2023) Citation Precision/Recall mit NLI-basierter Verification.

Answer Correctness, Completeness und Refusal

  • Answer Correctness vs. Ground Truth: Wenn Ground Truth vorhanden ist, Exact Match oder Token-F1 für Short-Answer Tasks (evaluate.load("squad")), Semantic Similarity für Open-Ended Tasks (bert-score, Embedding Cosine via sentence-transformers oder RAGAS AnswerCorrectness).
  • Completeness via Nuggets: Ein „Nugget“ ist ein einzelnes atomares Informationselement, das jede korrekte Antwort enthalten muss. Bei „Wann wurde das Unternehmen gegründet?“ könnten die Nuggets beispielsweise {year: 1994, founder: Jane Doe} sein. TRECs AutoNuggetizer extrahiert die Gold Nuggets einer korrekten Antwort aus einer Referenz und bewertet, welchen Anteil das System abdeckt. Bei TREC 2024 korrelierte die Metrik stark mit manueller Evaluation über 21 Topics × 45 Runs.
  • Refusal Behavior: Queries ohne Antwort im Corpus sollten zu Abstention statt Hallucination führen. Tracke Abstention Precision (korrekte Refusals) und Abstention Recall (Out-of-Scope-Queries, die eine Refusal auslösen). NoMIRACL ist der öffentliche Benchmark; in deiner eigenen Domain labelst du einen Out-of-Scope-Slice und trackst Abstention Accuracy.

Post-Generation Verification

Die günstigsten Reliability Gains entstehen oft durch deterministische Post-Checks und nicht durch größere Models.

  • Entity Grounding Check: Jede Named Entity in der Antwort muss im Retrieved Context vorkommen oder daraus ableitbar sein. Ein einfacher Regex- und Exact-Match-Check (oder ents von spaCy gegen einen normalisierten Context String) erkennt überraschend viele Hallucinations.
  • Claim Verification: Claims extrahieren, NLI gegen den Context ausführen und alle Claims unterhalb des Thresholds ablehnen oder markieren. NLI-as-Faithfulness-Models: cross-encoder/nli-deberta-v3-large, MoritzLaurer/DeBERTa-v3-large-mnli-fever-anli-ling-wanli. Das erhöht die Latency, lohnt sich aber in High-Stakes-Domains.
  • Self-Consistency (Wang et al., ICLR 2023): Mehrere Generations bei Temperature > 0 samplen; Agreement Rate melden, etwa den Anteil der Generations mit der Modal Answer oder den paarweisen BERTScore. Wähle die Sample Count anhand der Stability–Cost-Curve und markiere Antworten mit geringer Übereinstimmung für Human Review.
  • Confidence Calibration: Verbalisierte Confidence („Wie sicher bist du, 0–1?“) sammeln und mit der tatsächlichen Correctness auf dem Eval Set vergleichen. Zeichne eine Calibration Curve und berichte Expected Calibration Error: ECE=∑m=1M∣Bm∣n∣acc(Bm)−conf(Bm)∣\text{ECE} = \sum_{m=1}^{M} \frac{|B_m|}{n} |\text{acc}(B_m) - \text{conf}(B_m)|ECE=∑m=1M​n∣Bm​∣​∣acc(Bm​)−conf(Bm​)∣, wobei BmB_mBm​ Confidence Bins sind. Implementierungen: netcal, torchmetrics.CalibrationError. Ein Model mit Confidence 0,9 sollte in vergleichbaren Fällen ungefähr zu 90 % korrekt sein; miss die Abweichung, statt Calibration anzunehmen.

Teil 7: Ontology-Grounded-RAG-Evaluation

Die Standardmetriken oben decken Open-Corpus-RAG ab. Wenn dein RAG gegen eine strukturierte Ontology, Taxonomy oder Knowledge Graph retrievt – etwa Products in einem Catalog, Conditions in SNOMED, Components in einer BOM oder Security Techniques in MITRE ATT&CK –, sind diese Metriken notwendig, aber nicht ausreichend. Zusätzlich muss die Ontology Layer gemessen werden.

Entity-Linking-Accuracy

Die erste Aufgabe ist, eine Mention in einer Query einer Ontology Entity zuzuordnen („Aspirin“ → wikidata:Q18216, „die 737“ → aircraft:Boeing_737).

  • Mention-Level Precision/Recall/F1: Standardmetriken gegenüber Gold Mention Spans (berechne mit seqeval oder einem Span-Set-Comparator).
  • Disambiguation Accuracy: Welcher Anteil der korrekt erkannten Mentions wird der richtigen Entity ID zugeordnet? Öffentliche Referenzen sind ReFinED, REL und GENRE; Benchmarks wie AIDA-CoNLL und BELB zeigen, dass Ergebnisse nach System und Domain variieren.
  • NIL Handling: Precision/Recall für „Entity nicht in der Ontology“. Miss Over-Linking zu ähnlichen, aber falschen Entities getrennt von korrekter Abstention.

Hierarchy-Aware Evaluation

Plain Accuracy behandelt „Sedan vorhergesagt, Wahrheit ist Hatchback“ genauso wie „Sedan vorhergesagt, Wahrheit ist Submarine“. Diese Fehler sind nicht gleichwertig.

  • Hierarchical Precision/Recall/F1 (Kosmopoulos et al., 2015): Berücksichtige Ancestors und Descendants im Ontology DAG. Mit P^q\hat{P}_qP^q​ dem vorhergesagten Node plus allen Ancestors und TqT_qTq​ dem True Node plus allen Ancestors:

    hP=∑q∣P^q∩Tq∣∑q∣P^q∣,hR=∑q∣P^q∩Tq∣∑q∣Tq∣,hF1=2⋅hP⋅hRhP+hRhP = \frac{\sum_q |\hat{P}_q \cap T_q|}{\sum_q |\hat{P}_q|}, \quad hR = \frac{\sum_q |\hat{P}_q \cap T_q|}{\sum_q |T_q|}, \quad hF1 = \frac{2 \cdot hP \cdot hR}{hP + hR}hP=∑q​∣P^q​∣∑q​∣P^q​∩Tq​∣​,hR=∑q​∣Tq​∣∑q​∣P^q​∩Tq​∣​,hF1=hP+hR2⋅hP⋅hR​

    Implementiere dies mit networkx auf dem Ontology Graph: Ergänze Prediction und Label um ihre Ancestors und berechne die Set Overlaps.

  • Wu-Palmer Similarity zwischen vorhergesagter und Gold Entity in der Taxonomy (Wu & Palmer, 1994):

    WuP(c1,c2)=2⋅depth(LCA(c1,c2))depth(c1)+depth(c2)\text{WuP}(c_1, c_2) = \frac{2 \cdot \text{depth}(\text{LCA}(c_1, c_2))}{\text{depth}(c_1) + \text{depth}(c_2)}WuP(c1​,c2​)=depth(c1​)+depth(c2​)2⋅depth(LCA(c1​,c2​))​

    LCA bezeichnet den Lowest Common Ancestor in der Taxonomy. Für WordNet ist dies in NLTK (from nltk.corpus import wordnet as wn; wn.synset("car.n.01").wup_similarity(wn.synset("truck.n.01"))) direkt verfügbar; bei Custom Taxonomies lässt sich die LCA mit networkx berechnen.

  • Sibling-/Parent-Confusion-Rate: Tracke Confusions zu Siblings, Parents und Children getrennt – count_sibling / total_errors, count_parent / total_errors, count_descendant / total_errors. Prüfe anhand Review-Beispielen, ob Sibling Errors aus ambigen Mentions und Parent Errors aus Over-Generalization entstehen.

Filter False-Exclusion-Rate – erneut, jetzt kritisch

In Ontology-Grounded Systems stammen Hard Filters häufig direkt aus der Ontology („Nur Documents mit Category X retrieven“). Die in Teil 5 definierte Exclusion Rate wird damit zu einem primären Correctness Signal. Eine falsche Category Prediction kann Recall auf null setzen; die Exclusion Rate ordnet diesen Verlust dem Filter zu.

Constrained-Generation-Conformance

Wenn der Output einer Ontology entsprechen muss – jeder Entity Name in der Antwort muss ein gültiges Ontology Member sein, jedes Predicate aus einem geschlossenen Vocabulary stammen –, miss:

  • Schema Validity Rate: Anteil der Outputs, die gegen das Ontology Schema parsen und validieren. Validiere mit jsonschema oder pydantic. JSONSchemaBench ist der öffentliche Benchmark für allgemeinen Structured Output; für Ontology-spezifische Schemas erstelle einen eigenen Validator.
  • Vocabulary Conformance: Anteil der Named Entities im Output, die gültige Ontology IDs sind – ein einfacher Set-Membership-Check gegen das geschlossene Vocabulary.
  • Semantic Conformance: Ein syntaktisch gültiger Output kann dennoch die falsche, aber gültige Entity auswählen. Kombiniere Conformance daher mit Downstream Answer Correctness.

Constrained-Decoding-Frameworks (Outlines, XGrammar, Guidance, OpenAI Structured Outputs) erzwingen Schema Validity. JSONSchemaBench vergleicht Efficiency, Coverage und Quality über Implementierungen hinweg. Führe passende Cases mit deinem Schema und Serving Backend erneut aus, da Coverage und Latency von beidem abhängen.

Auditability

Für Ontology-Grounded Systems, deren Antworten geprüft werden:

  • Citation Completeness: Anteil der faktischen Claims mit mindestens einem verifizierbaren Citation.
  • Provenance Depth: Anteil der Citations, die bis zu einem Source Document mit stabiler ID aufgelöst werden können – nicht nur zu einem Chunk Hash.
  • Reproducibility Rate: Eine erneute Ausführung derselben Query auf einem festen Snapshot liefert dieselbe Antwort. Pinnutze Model Version, Runtime, Decoding Configuration und Seed und lege die notwendige Repeat Rate anhand der Auditability-Anforderungen des Workflows fest. Temperature Zero allein garantiert keine Determinism. Ein Miss kann durch Generation, Serving Runtime oder jede vorgelagerte Stufe entstehen.

Teil 8: System-Level Evaluation

Holistic Answer Quality

  • LLM-as-Judge (Zheng et al., NeurIPS 2023): ein skalierbarer model-basierter Evaluation-Ansatz. G-Eval (Liu et al., EMNLP 2023 – ein LLM-Judge-Protokoll, bei dem das Model vor dem Scoring eine eigene Chain-of-Thought-Rubric erzeugt) leitet eine Rubric aus einem natürlichsprachlichen Kriterium ab und scored mit Log-Prob-gewichteten Outputs. Die Agreement Rate hängt von Judge, Task, Prompt und Calibration Set ab.
  • Pairwise Preference: Der Judge erhält Antwort A und Antwort B und gibt eine Preference ab. Das vermeidet Probleme bei der Kalibrierung absoluter Scores. MT-Bench berichtete unter seinen Benchmark-Bedingungen eine GPT-4-Judge-Agreement von über 80 % mit Human Preferences und Human–Human Agreement. Übertrage diesen Wert nicht ohne Calibration auf andere Domains.

LLM-as-Judge besitzt reale Biases:

  • Position Bias: Judges bevorzugen die erste oder zweite Antwort unabhängig von ihrer Quality. Gegenmaßnahme: Reihenfolge randomisieren oder beide Reihenfolgen ausführen und mitteln.
  • Verbosity Bias: Judges können Länge mit Quality verwechseln. Eine kontrollierte Studie von 2026 fand heterogenes Verhalten bei Expansion Pairs: Drei Judges bevorzugten längere Antworten, Claude bevorzugte knappe Antworten und GPT-4o war ungefähr neutral. Alle fünf schnitten bei Truncation Controls gut ab. Das Ergebnis ist an den Benchmark gebunden; definiere in der Rubric, wie Completeness und Filler behandelt werden sollen, und berichte Length-Controlled Performance auf deiner eigenen Rubric.
  • Self-Preference Bias: GPT-4 bevorzugt GPT-4-Outputs; der Bias korreliert mit Output Perplexity. Gegenmaßnahme: Verwende eine andere Judge-Familie als das evaluierte System. Lass ein Model sich nicht selbst bewerten.

Praktisches Vorgehen: Wähle einen Judge auf Human-Labeled Calibration Data, randomisiere die Answer Order, maskiere Model Identities und beschreibe die Length Policy in der Rubric. Wiederhole Cases nur, wenn zusätzliche Samples die Unsicherheit wesentlich reduzieren. Bei High-Stakes-Evaluationen vergleiche Judges aus unterschiedlichen Model-Familien und analysiere Abweichungen anhand von Human Labels.

Schema-Guided Reasoning für Judges

Free-Form Output ist eine Variationsquelle in Judge Runs. Zwei Runs auf derselben Antwort können die Rubric unterschiedlich strukturieren und verschiedene Scores erzeugen. Schema-Guided Reasoning (SGR) macht die Rubric explizit: Definiere Evaluation Stages als Pydantic Schema und verwende Constrained Output mit Outlines, XGrammar, vLLM Structured Outputs oder OpenAI response_format, sodass jeder Run dieselben Felder in derselben Reihenfolge zurückgibt.

Für RAG Eval zerlegt das Schema das Judgment in explizite, auditierbare Felder, statt das Model direkt zu einer Zahl springen zu lassen:

from pydantic import BaseModel, Field
from typing import Literal

class FaithfulnessJudgment(BaseModel):
    extracted_claims: list[str] = Field(
        description="Atomic factual claims in the answer, one per item."
    )
    supported_claims: list[str] = Field(
        description="Subset of extracted_claims that are entailed by the context."
    )
    unsupported_claims: list[str] = Field(
        description="Subset that is NOT entailed by the context."
    )
    failure_mode: Literal[
        "none", "fabrication", "overgeneralization", "wrong_entity", "stale_fact"
    ]
    score: float = Field(ge=0.0, le=1.0)
    rationale: str

Die Structured Fields machen den Score als len(supported) / len(extracted) rekonstruierbar und zeigen exakt, bei welchen Claims zwei Judges voneinander abweichen. Das Pydantic Model macht eine Rubric-Änderung als Code Diff sichtbar. Constrained Output garantiert die Form, kein unvoreingenommenes Urteil; Position Randomization, Cross-Family Judges und Human Calibration bleiben daher nötig.

Das funktioniert für jede Rubric-basierte Judge-Aufgabe, nicht nur für Faithfulness. Pairwise Preference, Citation Support und Refusal Correctness profitieren ebenfalls davon.

Ein G-Eval-/Pairwise-/Position-Bias-/Cross-Family-Judge-Harness befindet sich in Notebook 07; Modul: evaluation/llm_judge.py. Der Benchmark Sweep (make benchmark im Repository) verbindet drei Models (gpt-5-mini, claude-haiku-4-5, gemini-2.5-flash) mit einem rotierenden Judge für Pairwise A/B. Jedes Model bewertet die beiden anderen, sodass Self-Preference als Zahl sichtbar wird.

Latency und Kosten

  • p50, p95, p99 auf jeder Pipeline-Stufe. Wähle SLO-Percentile und Alert Threshold anhand der User Journey, des Traffic Volumes und des Error Budgets.
  • Time-to-First-Token gegenüber der gesamten Generation Time. Für Streaming UX ist TTFT entscheidend.
  • Stage Breakdown: Retrieval, Reranking, Generation und Post-Processing. Verwende den Trace, um den Tail zu lokalisieren, statt eine Stufe zu vermuten; erfasse bei Vergleichen Reranker Device und Batch Size.
  • Gesamt $/Query = Embedding + Retrieval + Rerank + Generation + Storage amortisiert. Tracke p50 und p99; im Long Tail liegt der größte Budgetverbrauch.
  • Cache Hit Rates auf Embedding-Cache-, Retrieval-Cache- und KV-Cache-Ebene. Lege getrennte Targets anhand von Repetition, Invalidation Policy und vermiedenen Kosten je Layer fest.

Per-Stage p50/p95/p99 mit Stage Breakdown sind in Notebook 08 und im Runner unter evaluation/latency.py implementiert; der Benchmark Report verbindet Latency und Faithfulness in einer Matrix, die du mit make benchmark erneut ausführen kannst.

A/B Testing

  • Unit of Randomization: Wähle die Unit aus Estimand, Carryover und Interference. Verwende User- oder Session-Level Assignment, wenn wiederholte Exposure Verhalten ändern oder eine inkonsistente UX erzeugen kann. Query-Level Assignment ist nur vertretbar, wenn diese Effekte vernachlässigbar sind und die Analyse wiederholte Beobachtungen modelliert.
  • Primary, Guardrail und Exploratory Metrics: Registriere sie vorab. Wähle die Primary Metric anhand des Product Outcomes; Satisfaction Proxies sind Thumbs, Regenerations und Dwell. Behandle Latency und Kosten als Guardrails, wenn sie die Experience begrenzen.
  • Sample Size: Führe vor dem Launch eine Power Analysis anhand des kleinsten relevanten Effekts, der Baseline-Varianz, der Assignment Unit und der Stopping Rule durch.

Teil 9: Test-Set-Konstruktion

Eine Metrik ist nur so gut wie das Test Set, auf dem sie läuft. Wenn dein Golden Set drei Intents abdeckt, der Production Traffic aber zwölf, misst Recall@10 nur diese drei Intents. Schlimmer noch: Ein Test Set, das sich auf einfache Fragen wie „Wie lautet die Rückgaberichtlinie des Unternehmens?“ spezialisiert, kann ein System freigeben, das an schwierigen Fragen scheitert, etwa: „Welche Voraussetzungen gelten für eine teilweise Stornierung nach dem EU Digital Services Act von 2023, wenn in EUR abgerechnet wird und die Bestellung aus Irland stammt?“ Der Aggregate Score steigt, obwohl das System einen wichtigen Teil des Production Traffic weiterhin nicht beherrscht.

Dasselbe Problem betrifft die Ground Truth. Wenn SMEs die offensichtlichen Documents labeln, aber relevante Long-Tail-Documents übersehen, bewertet Recall@k einen Retriever zu schlecht, obwohl er diese Documents gefunden hat. Du optimierst auf die Labels, nicht auf die Wahrheit.

Baue das Test Set zunächst anhand der realen Query Distribution und Difficulty. Wähle anschließend Metriken, die auf die Ziel-Failure-Modes reagieren, und tune das System gegen diese Metriken.

Synthetic Query Generation

Verwende ein LLM, um Fragen aus deinem Corpus zu generieren:

  • Pro Chunk: „Generiere drei Fragen, die ein User stellen könnte und die dieser Chunk beantwortet.“
  • Multi-Hop: Sample zwei Chunks und generiere eine Frage, die beide benötigt.
  • Adversarial: Generiere Questions mit Distractor Entities, Near-Duplicate Phrasing und ambigen Mentions.

RAGAS besitzt eine eingebaute Question-Type-Distribution (Reasoning, Conditional, Multi-Context). DataMorgana generiert konfigurierbare Synthetic Benchmarks über User- und Question-Kategorien. Synthetic Data ist für Cold Starts und Coverage Testing nützlich, kann Real User Queries aber nicht ersetzen.

Golden-Dataset-Konstruktion

Von Menschen kuratierte Daten verankern das Golden Set.

  1. Sample reale User Queries (oder vor dem Launch simulierte Queries), stratifiziert nach Intent.
  2. Lass SMEs jede Frage beantworten und die Documents identifizieren, die die Antwort enthalten.
  3. Dimensioniere das Set anhand der Coverage Matrix und des für Release-Entscheidungen erforderlichen Confidence Intervals; Coverage ist wichtiger als eine übernommene Query Count.
  4. Kuratiere neu, wenn Release Cadence, Drift Signals, Domain Risk und Annotation Capacity dies rechtfertigen.

Adversarial Test Sets

  • Counterfactuals: Tausche zentrale Entities in der Query aus. Retrievt das System für die veränderte Query die richtigen Chunks?
  • Distractors: Queries, bei denen das Corpus eine plausible, aber falsche Antwort enthält, die nicht retrievt werden sollte. Das ist der Fokus von RGB (Chen et al., AAAI 2024): Noise Robustness, Negative Rejection, Information Integration und Counterfactual Robustness.
  • Negation und Quantifiers: Queries mit „nicht“, „außer“ und „nur“. Dense Retriever haben damit häufig Schwierigkeiten.
  • Out-of-Scope: Queries ohne Antwort im Corpus. Das System sollte „Ich weiß es nicht“ sagen und nicht halluzinieren. NoMIRACL gehört in diese Kategorie. Evaluiere Abstention explizit für deine Production Query Types.

Coverage und Continuous Evaluation

  • Erstelle eine Coverage Matrix: Query Intent × Document Type × Ontology Branch. Ziel ist mindestens eine Query pro Cell. Leere Cells sind nicht überwachte Bereiche, in denen sich Regressionen verstecken.
  • Führe bei jedem PR ein begrenztes, schnelles Regression Subset und nach einem langsameren Zeitplan die vollständige Suite aus.
  • Plane die vollständige Golden-Set-Eval anhand von Release Cadence und Evaluation Cost; Release Candidates sind ein natürliches Gate.
  • Plane Drift Evaluation anhand von Traffic Volume, erwarteten Änderungen und Risiko. Verwende ein Rolling Production Sample und stratifiziere nach Feedback, statt die Target Distribution stillschweigend zu verändern.

Teil 10: Production Monitoring

Die ausgelieferte Eval Suite beschreibt das System beim Launch. Production Traffic verändert sich danach.

Implizites und explizites Feedback

  • Click-Through-/Open-Rate auf zitierten Sources, sofern die UI sie anzeigt.
  • Dwell Time auf der Antwort.
  • Regeneration Rate: Anteil der Antworten, die User erneut fragen oder neu erzeugen lassen. Behandle dies als ein Dissatisfaction Signal und kalibriere es gegen geprüfte Conversations.
  • Copy-/Share-/Export-Raten – starke positive Signale.
  • Follow-up Patterns: Fragen wie „Bist du sicher?“ oder „Aber was ist mit X?“ deuten auf Misstrauen hin.
  • Thumbs Up/Down mit optionalen Reason Categories (falsch, unvollständig, off-topic, schädlich, langsam). Inline Edits, sofern die UI sie erlaubt, tragen meist die meiste Information aller Feedback Signals.

Drift Detection

  • Query Drift: Vergleiche die Query-Embedding-Distribution mit einem Reference Window anhand von KL Divergence, MMD oder einem model-basierten Detector. Bei einem Shift alarmieren und anschließend segmentweise debuggen.
  • Embedding Drift: Fixiere ein Probe Set aus Documents, embedde es periodisch neu und miss die Cosine Similarity zu den ursprünglichen Embeddings. Selbst kleiner Drift zwischen Provider-Model-Versionen kann Retrieval stillschweigend beschädigen. Versionierter Embedding Storage mit unveränderlichen Snapshots pro Version ist die günstigste Gegenmaßnahme.
  • Performance Drift: Tracke Production-equivalente Metriken wie Regeneration Rate pro Intent über die Zeit. Plötzliche Sprünge bedeuten, dass etwas defekt ist; langsame Drifts, dass sich die Welt verändert hat.

Shadow Evaluation und Human-in-the-Loop

Betreibe das Kandidatensystem parallel zu Production, vergleiche die Outputs offline und liefere sie nicht an User aus. Das erkennt Regressionen vor dem Launch. Es verursacht zusätzliche Inference Cost, hat aber keinen Customer Impact.

Für Human-in-the-Loop (HITL) Review:

  • Sample Low-Confidence-Outputs in eine Review Queue.
  • Füge für Blind Reviews ein Random Sample des Production Traffic hinzu; bestimme die Rate anhand von Traffic Volume, Risiko und Reviewer Capacity.
  • Gewichte Thumbs-Down-Outputs stark.
  • Nutze geprüfte Outputs zur Erweiterung des Golden Sets.

Das minimale Guardrail Set

Alarmiere in dieser Reihenfolge:

  1. Faithfulness-/HHEM-Score unterhalb des Thresholds auf einem Rolling Production Sample.
  2. p95 Latency oberhalb des SLO.
  3. Filter False-Exclusion-Rate oberhalb des Thresholds (sample-basiert).
  4. Regeneration Rate außerhalb eines lokal kalibrierten Control Bands, das Window Size, Traffic, Seasonality und False-Alert Budget berücksichtigt.
  5. Cost/Query oberhalb des Budgets.

Wenn ein Alert ohne entsprechende Code- oder Model-Änderung auslöst, liegt vermutlich Drift vor. Löst er nach einer Änderung aus, handelt es sich wahrscheinlich um eine Regression. In beiden Fällen erhältst du ein Signal, bevor Support Tickets eintreffen.

Caveats

  • Targets sind lokal, nicht universell. Jede in diesem Guide als illustrativ bezeichnete Zahl ist ein Beispiel oder ein ausgearbeitetes Resultat, kein Release Threshold. Kalibriere Thresholds an Domain, Stakes, Unsicherheit des Evaluation Sets und User Expectations.
  • Der Framework-Markt bewegt sich schnell. HHEM-Versionen, RAGAS-Metric Names, Model Cards und Leaderboard-Reihenfolgen können sich nach der Veröffentlichung ändern. Prüfe die verlinkte Source und benchmarke erneut, bevor du dich festlegst.
  • LLM-as-Judge-Agreement-Zahlen haben Sternchen. Die 80-%-Zahl für GPT-4 gegenüber Menschen stammt aus MT-Bench-/Chatbot-Arena-Bedingungen. In Nischen-Domains und adversarial Cases sinkt die Agreement Rate stark. Verwende Judges als Force Multiplier, nicht als Ersatz für Stichprobenprüfungen.
  • Vendor-Benchmark-Uplifts sind häufig nicht unabhängig reproduzierbar. Reproduziere sie auf eigenen Daten, bevor du einer Zahl vertraust – insbesondere bei neueren Rerankern und OCR-Systemen.
  • Keine Metrik ersetzt die Sichtprüfung von Outputs. Plane Blind Reviews eines zufälligen Production Samples entsprechend Traffic, Risiko und Reviewer Capacity. Die Metriken skalieren diese Gewohnheit, ersetzen sie aber nicht.
