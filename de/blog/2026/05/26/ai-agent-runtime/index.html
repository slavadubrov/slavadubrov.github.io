Was ist ein AI Agent Runtime?

Ein AI Agent Runtime ist die Infrastruktur, die einen Tool-Using Agent nach dem Ende eines Model Calls weiterlaufen lässt. Er speichert Session State, führt Tools aus, speichert Checkpoints, verwaltet Secrets, schreibt Traces, setzt Cost Limits durch und definiert, wie der Service deployed wird. Das Model wählt die nächste Action. Der Runtime entscheidet, wo diese Action ausgeführt wird, zeichnet das Ergebnis auf und stellt den Run nach einem Failure wieder her. Der Harness entscheidet, ob eine Action zulässig ist. Er ist kein Store, wird aber in der Tabelle aufgeführt, weil der Runtime ihn irgendwo ausführen muss.

Lange Runs brechen Annahmen über stateless Processes

Byte says

Wenn das Run Log ausschließlich im Worker-Memory liegt, kann ein routinemäßiges Deployment den Worker mitten in der Aufgabe ersetzen und die Run-Historie löschen.

Ein stateless Chat Endpoint kann Request State in einem Prozess halten und ihn nach der Response verwerfen. Ein Long-Running Agent Run übersteht Worker-Restarts, Deployments, Context Resets und Approval Pauses. Der Worker-Prozess kann daher nicht länger die Source of Truth sein.

Das OpenAI-Codex-Team berichtet in seinem Harness-Engineering-Beitrag, wie lange diese Runs werden:

“We regularly see single Codex runs work on a single task for upwards of six hours (often while the humans are sleeping).”

Das Engineering-Team von Anthropic beschreibt das entsprechende State-Problem in Effective harnesses for long-running agents:

“The core challenge of long-running agents is that they must work in discrete sessions, and each new session begins with no memory of what came before.”

Beide Beobachtungen führen zum selben Runtime-Design: State außerhalb des Workers persistieren und Worker austauschbar machen.

Die Session muss außerhalb des Worker-Prozesses liegen. Ein dauerhafter Store zeichnet Model Calls, Tool Intents und Outcomes sowie Approvals auf, damit ein anderer Worker nach einem Crash am letzten sicheren Punkt fortsetzen kann. Ein ausstehender externer Effect muss vor diesem Resume reconciled werden, damit es als sicher gelten kann. Checkpoints ermöglichen dem Runtime außerdem, bei vollem Context Window eine neue Model Session zu starten, ohne die gesamte Historie erneut abzuspielen. In Anthropics Formulierung werden Harness-Instanzen disposable und restartable; der dauerhafte State liegt an anderer Stelle.

Fünf Primitives, die Sie vor dem Shipping platzieren sollten

Anthropics Scaling Managed Agents-Beitrag liefert eine nützliche Terminologie für fünf Runtime-Verantwortlichkeiten. Der Harness treibt den Agent voran, während die Session aufzeichnet, was er getan hat, und die Sandbox Commands ausführt. Der Checkpoint gibt dem nächsten Worker einen Resume Point; der Trace bewahrt Evidence für späteres Debugging. Eine Implementierung kann Komponenten zusammenlegen, aber Verantwortlichkeiten und Failure Boundaries benötigen weiterhin klare Namen.

Session. Ein separat geschriebenes Append-only Event Log mit Model Calls, angeforderten und abgeschlossenen Tool Calls, Errors und Approvals. Eine Checkpoint-Datenbank unterstützt die Recovery, aber die Graph-State-Historie ist kein Ersatz für dieses Log.

Der Begriff ist überladen; deshalb verwendet dieser Artikel eine Naming Convention auf Anwendungsebene für drei Spans. Ein Thread ist die Conversation eines Users über mehrere Tage hinweg. Er ist der langlebigste Span und kann viele Runs enthalten.

Eine Model Session ist die kürzeste Einheit: eine zusammenhängende Phase desselben Model Contexts. Compaction – der Schritt, der das Window zusammenfasst, damit die Arbeit fortgesetzt werden kann – verlängert eine Model Session, statt sie zu beenden. Ein Restart oder ein bewusst gestarteter Fresh Start beendet sie. Part 6 verwendet „Model Session“ in diesem Sinn.

In diesem Artikel bedeutet „Session“ das dauerhafte Log für einen Run. Mehrere Model Sessions können in dasselbe Log schreiben, und ein Conversation Thread kann mehrere Run Logs enthalten. Für die Recovery aktivieren Sie den Run, laden seine Session, reconciliieren einen ausstehenden Side Effect und setzen nach dem letzten Event fort: wake(sessionId) → getSession(id) → reconcile pending effects → resume from last event.

In LangGraph ist thread_id der Storage- und Retrieval-Key des Checkpointers für die Graph-State-Historie eines Threads (siehe LangGraph persistence); er definiert nicht die Conversation-, Model-Session- oder Event-Log-Grenzen dieses Artikels. Geben Sie dem Event Log eine eigene dauerhafte Run- oder Session-ID und legen Sie explizit fest, wie diese IDs auf LangGraph Threads abgebildet werden. Das OpenAI Agents SDK enthält zehn integrierte Session Backends, darunter SQLiteSession, RedisSession, SQLAlchemySession, MongoDBSession und EncryptedSession (siehe die Sessions docs). Sie halten mutable Conversation History einschließlich Removal, Clearing und Compaction; mappen Sie eine SDK Session ID bei Bedarf auf die Run-Event-ID, behandeln Sie den SDK-Verlauf jedoch nicht als Append-only Recovery- oder Audit-Log, sofern keine gleichwertige Immutability-Garantie besteht.

Harness. Die Orchestration Loop und das einzige Primitive in dieser Liste, das Entscheidungen trifft. Er stellt den Prompt aus Memory zusammen, ruft das Model auf, prüft den vorgeschlagenen Tool Call gegen seine Permission Rules, dispatcht erlaubte Calls, schreibt Results in die Session zurück, wendet Retry Rules an und entscheidet, ob die Aufgabe beendet ist. Planning-Hilfen und Context Management kodieren Annahmen über die Model-Fähigkeiten. Verbindliche Authorization und Isolation setzen außerdem Anforderungen um, die auch bei besseren Models bestehen bleiben. Anthropic weist direkt darauf hin – das Zitat steht weiter unten im Abschnitt zu Failure Modes, der sich überwiegend damit beschäftigt, was passiert, wenn solche Annahmen veralten.

Das Codex-Team von OpenAI nennt dies Harness Engineering: Software zu schreiben erfordert weiterhin Engineering-Aufwand, aber ein größerer Anteil fließt jetzt in das Scaffolding statt in den Code selbst. LangGraphs CompiledStateGraph, LangChains Deep Agents und sein create_deep_agent Entry Point sowie Claude Code selbst sind Harnesses in diesem Sinn.

Sandbox. Die isolierte Execution Environment, in der Commands tatsächlich ausgeführt werden. Die Seite zu Sandbox Concepts des OpenAI Agents SDK ordnet Approvals, Tracing, Handoffs und den für Resume erforderlichen State dem äußeren Runtime zu. Commands, File Changes und Environment Isolation ordnet sie der Sandbox Session zu.

„Outer Runtime“ bezeichnet dort den Harness zusammen mit seinen State Stores. In der Terminologie dieser Serie sind Approvals und Handoffs Harness-Entscheidungen (Part 4 und Part 6); Tracing und Resume Bookkeeping sind die Primitives Session und Checkpoint.

Sandboxes unterscheiden sich darin, wie lange sie leben und was sie zwischen Runs behalten. Die einfachste Form ist fresh ephemeral: Eine Sandbox wird für eine einzelne Aufgabe gestartet, nach deren Ende zerstört, und bei jedem Run fallen Cold-Start-Kosten an.

Persistent paused-Sandboxes behalten Filesystem und Memory Snapshot zwischen Runs. Der nächste Resume kann dadurch einen vollständigen Boot vermeiden. Snapshot or fork erstellt aus einem vorbereiteten Parent ein Copy-on-Write-Image, sodass viele Tasks installierte Dependencies und warme Caches teilen, ohne ihren Writable State zu teilen.

Per-Worktree-Workspaces geben Tasks separate Checkouts; Git worktrees teilen Repository-Infrastruktur und sind keine OS-Sandboxes. Schränken Sie Execution separat durch einen Container, eine VM oder eine Process Policy ein. Eine Per-Task-Anwendung kann außerdem über einen eigenen Observability Stack verfügen. Separate Logs, Metrics und Traces ermöglichen das Debugging eines Runs, ohne dass dessen State in andere Runs übergreift. Die Provider-Tabelle weiter unten vergleicht Isolation- und Persistence-Contracts.

Checkpoint. Der zum Resume erforderliche State: welcher Graph Node ausgeführt wurde, seine neuesten Values und was als Nächstes ausgeführt werden soll. Ein Event Log beantwortet die Frage, was passiert ist: die angeforderten Actions und ihre Outcomes. Ein Checkpoint kann Events nicht rekonstruieren, die der Harness nie geloggt hat.

LangGraphs PostgresSaver schreibt an jeder Super-Step-Grenze einen Checkpoint. Ein Super-Step ist eine Runde des Graphs, entweder ein einzelner Node oder ein parallel ausgeführter Batch. Per-Task-Writes gehen an checkpoint_writes, sodass erfolgreiche Node Outputs bei einem Fehler eines Geschwisters nicht erneut berechnet werden.

Ein Checkpoint ist ein einfaches Dict (v, id, ts, channel_values, channel_versions, versions_seen, updated_channels). LangGraph serialisiert es mit dem msgpack-basierten JsonPlusSerializer statt mit JSON. datetime, set, Decimal und Dataclasses lassen sich dabei round-trippen. Das Format ist auf der langgraph-checkpoint-postgres-PyPI-Seite und in der LangGraph Checkpoints Reference dokumentiert.

StateSnapshot ist die separate, reichhaltigere Ansicht, die graph.get_state() auf einem Checkpoint aufbaut. Ein Debug Bundle kann dessen .values als letzten bekannten Graph State exportieren; Event-Details, die der Harness nie geloggt hat, lassen sich damit nicht rekonstruieren.

Trace. Die Debug- und Audit-Oberfläche. Jeder Model Call, Tool Call und Sub-Agent Step sollte Timing, Status, Model und Provider, Correlation IDs, Token Counts und Kosten ausgeben. Prompts, Completions, Tool Arguments und Tool Results sind opt-in Content: OpenTelemetrys GenAI guidance verwendet standardmäßig Metadaten, weil diese Felder sensible Daten enthalten können. Erfassen Sie sie erst, nachdem Sie Redaction oder Filtering, Access Controls und Retention festgelegt haben. Wenn ein sechs Stunden langer Run fehlschlägt, lesen Sie den Trace, um herauszufinden, was schiefgelaufen ist. Er kann eine Untersuchung unterstützen, aber Event Log und Checkpoint State zusammen mit Idempotency Handling ermöglichen ein sicheres Resume oder Replay. Die Terminalausgabe des Runs ist zu diesem Zeitpunkt längst verschwunden. OpenTelemetrys GenAI semantic conventions standardisieren die Attributnamen (welches Model, welcher Provider, wie viele Tokens, welche Conversation, welcher Workflow). Für ein OTLP-kompatibles Ziel, das diese Conventions unterstützt, kann dieselbe Instrumentierung den Trace an Systeme wie Tempo, Jaeger, Honeycomb oder LangSmith exportieren, auch wenn möglicherweise Backend-Adapter oder zielsystemspezifische Konfiguration erforderlich sind.

Policy und Secrets verlaufen quer durch die Primitives

Zwei Grenzen verlaufen quer durch alle fünf Primitives. Sie sind die Runtime-Version des Security-Arguments aus Part 4. Die Permission Decision selbst gehört zum Harness; im Folgenden geht es darum, wo die sie durchsetzende und versorgende Mechanik physisch sitzt.

Permission Enforcement

Die Permission Ladder aus Part 4 benötigt einen Ausführungsort. Der Check erfolgt vor jedem Tool Call und entscheidet, ob dieser durchgelassen wird. In Production sind zwei Muster verbreitet. Deep Agents’ filesystem-permission middleware kann die integrierten Filesystem Tools auf deklarierte Pfade begrenzen. Sie steuert keine Sandbox Shell Commands, Custom Tools oder MCP Calls; setzen Sie diese in der Sandbox Policy oder hinter einem eigenen Tool Proxy durch. Anthropic Managed Agents leitet Custom MCP Tool Calls durch einen Proxy mit Credentials. Sandbox Command Execution und Git Authentication verwenden separate Pfade; der MCP Proxy ist kein universeller Interceptor für jede Action. Wenn ein sensibler Call eine Human Approval benötigt, pausieren LangGraphs interrupt() und der Approval Hook von Deep Agents den Graph, bis eine Person zustimmt.

Secret Broker

Das Model sollte keine langlebigen Secrets sehen, und normalerweise sollte dies auch für die Sandbox gelten. Das Managed-Agents-Muster ist das, was Sie übernehmen sollten:

“For Git, we use each repository’s access token to clone the repo during sandbox initialization and wire it into the local git remote. Git push and pull work from inside the sandbox without the agent ever handling the token itself. For custom tools, we support MCP and store OAuth tokens in a secure vault. Claude calls MCP tools via a dedicated proxy; this proxy takes in a token associated with the session. … The harness is never made aware of any credentials.”

Im market-analyst-agent-Referenz-Stack – einem kleinen LangGraph Agent, der Market Data abruft und einen Analyst Report schreibt und über diese Serie hinweg aufgebaut wird – ruft der Worker seine Market-Data-Tools lokal auf. Der optionale MCP Server stellt eine Tool Surface bereit; er ist kein implementierter Credential Broker zwischen diesem Worker und seinen Providern. Beide Container können das gemeinsame Development-.env lesen. Ein Production Broker müsste Provider Credentials in einen Store verschieben, den der Worker nicht lesen kann, und jeden relevanten Call über den Broker routen.

Platzierung einem Plausibilitätscheck unterziehen

Ein praktischer Plausibilitätscheck besteht darin, jede Komponente und das von ihr implementierte der fünf Primitives zu notieren. Postgres könnte Session und Checkpoint abdecken. Der Worker-Container ist der Harness. Ein Service wie Daytona, Modal oder E2B stellt die Sandbox bereit, während Tempo oder LangSmith den Trace speichert.

Untersuchen Sie anschließend gekoppelte Failures. Wenn zwei Primitives im selben Prozess liegen, reißt ein Crash beide mit. Wenn sie ein Credential teilen, überschreitet ein Leak beide Grenzen. Häufige Beispiele sind ein Worker, der zugleich die Trace-Durability besitzt, oder ein Sidecar-Token, das zugleich die Checkpoint-Datenbank entsperrt.

Failure Modes eines Production AI Agent Runtime

Der Runtime verwaltet Retries, stellt frühere Arbeit wieder her, isoliert Workspaces und setzt Budgets durch. Wenn sich Runs über Worker und Context Windows erstrecken, verschieben sich die Failures in Richtung State, duplicate Side Effects, Sandbox Drift und Budget Overruns.

Die Failures fallen in vier Gruppen:

  • Quality-of-Output Failures: Der Agent erklärt die Arbeit für abgeschlossen, obwohl sie noch nicht fertig ist, vergisst nach einem Context-Window-Reset, was er getan hat, oder vertraut seiner eigenen Self-Evaluation und liefert fehlerhaften Output aus.
  • Cost-Control Failures: Der Agent gerät in eine Retry Loop oder verbraucht ein Token- oder Tool-Call-Budget, ohne etwas Nützliches zu produzieren.
  • State- und Crash-Failures: Workspaces driften, weil ein Run Dateien verändert, die einem anderen Run gehören; Tool Calls werden durch Replay von Retries mehrfach ausgeführt; oder Arbeit geht verloren, wenn ein Worker zwischen Events stirbt.
  • Context-Window Failures: Das Model fasst zusammen und beendet sich frühzeitig, weil es glaubt, der verfügbare Platz gehe aus, obwohl das Window noch Kapazität hat.

Die Tabelle ordnet jedem Failure eine Mitigation, die Grundlage der Empfehlung und den Runtime Hook zu, der sie durchsetzt. Model-spezifisches Verhalten kann sich ändern; behandeln Sie Vendor-Beobachtungen daher als Anlass, die Annahme erneut zu testen, nicht als dauerhafte Regeln.

Das Harness-Team von OpenAI bringt es in einem Satz auf den Punkt: „Humans steer. Agents execute.“ Wenn etwas fehlschlägt, lautet die nützliche Frage, welche Capability fehlt und wie diese Capability für den Agent sowohl verständlich als auch durchsetzbar gemacht werden kann.

Der gesunde Run-Lifecycle

Ein gut funktionierender Run ist langweilig. Er besteht aus einer Kette kleiner, recoverbarer Steps, und jeder abgeschlossene Step schreibt dauerhaften State, bevor der nächste beginnt.

Wenn jedes Result vor dem Start des nächsten Steps geschrieben wird, bleibt der Crash-Schaden begrenzt. Ein In-Flight External Effect ist die Ausnahme: Ein Worker kann crashen, nachdem der Provider ihn committed hat, aber bevor der Harness sein Outcome aufzeichnet. Der nächste Worker muss diesen Pending Effect reconciliieren, bevor er vom letzten abgeschlossenen Step fortsetzt.

  1. Boot aus einer frischen oder resumed Session. Beim Resume mounten Sie den Workspace in seinem letzten bekannten State, lesen Progress-Dateien, die der vorherige Versuch hinterlassen hat (PROGRESS.md, feature-list.json), laden den letzten Checkpoint und prüfen das Event Log auf Pending Tool Intents. Reconciliieren Sie jeden Pending External Effect, bevor Sie einen weiteren Model- oder Tool Call ausführen.
  2. Planen Sie, bevor Tool Calls ausgelöst werden. Halten Sie fest, wie „done“ aussieht, wie viel der Run ausgeben darf, welche Tools der Agent aufrufen kann und wodurch der Run vorzeitig beendet werden soll. Diese Plan Values werden zu Runtime Checks; ohne sie hat die Execution nichts, was ihr Grenzen setzt.
  3. Serialisieren oder koordinieren Sie Side-Effecting Tool Calls explizit. Der Permission Check des Harness entscheidet, ob jeder einzelne zugelassen wird. Fügen Sie vor dem Dispatch einen pending Intent mit seinem Idempotency Key an; fügen Sie nach der Rückgabe des Providers das Outcome an. Unabhängige Read-Only- oder Idempotent Calls können parallel laufen, wenn jeder über einen eigenen dauerhaften Intent/Result Record verfügt und die Results deterministisch aggregiert werden. Wenn der Worker zwischen Side Effect und Outcome Write stirbt, setzen Sie fort, indem Sie den Provider mit demselben Key abfragen oder erneut versuchen und anschließend entweder das recovered Outcome oder needs_human anhängen. Stripe gibt beispielsweise bei einem wiederholten Idempotency Key das gespeicherte Result des ersten Requests zurück; ein anderer Provider benötigt einen gleichwertigen Lookup- oder Retry-Contract.
  4. Checkpoint an Super-Step-Grenzen oder, in einem einfacheren Harness, nach jedem Event. Persistieren Sie den Graph State, den Workspace Diff und References auf erzeugte Artefakte. Dieser Checkpoint wird in Step 1 beim nächsten Resume gelesen. Fehlt der Checkpoint oder ist er veraltet, muss die Recovery den State möglicherweise aus dem Event Log rekonstruieren, was wesentlich langsamer ist.
  5. Evaluieren Sie anhand der Artefakte, wenn der Agent glaubt, fertig zu sein: Tests, ein Fresh-Context Evaluator, Schema Validation, Browser Checks. Wenn der Check erfolgreich ist, wird der Run erfolgreich beendet. Schlägt er fehl, wird der Run vom letzten sauberen Checkpoint mit der in den Context aufgenommenen Failure Message fortgesetzt und erneut versucht.

Kein Step dieser Liste erfordert, dass der Agent sich zwischen Runs an etwas erinnert. Der State liegt in Session und Checkpoint und wird bei jedem Resume erneut gelesen.

Persistieren Sie vor dem Dispatch eine anwendungsseitig kontrollierte Operation ID und binden Sie sie an die genehmigten Arguments. Verwenden Sie sie für die Recovery derselben Business Intent, auch wenn Replanning eine neue Model Tool-Call-ID erzeugt. Zeichnen Sie diese Model IDs separat zur Korrelation auf. Natürlich idempotente Updates benötigen stattdessen möglicherweise eine Version Precondition. AWS’ Retry Guidance erklärt, warum Request Identity die Intent repräsentiert. Definieren Sie, wann eine Action wirklich neu ist und wie lange Deduplication gilt: Stripe erlaubt das Entfernen von Keys nach mindestens 24 Stunden. Reconciliieren Sie geänderte Payloads und abgelaufene Keys, bevor Sie einen weiteren Versuch starten.

Wählen Sie einen aktiven Writer oder eine Lease pro Thread. Für Input, der während eines Runs eintrifft, legen Sie explizit fest, ob Sie ihn ablehnen, enqueuen, unterbrechen oder zurückrollen; Deep Agents’ Runtime Account beschreibt diese Optionen. Cancellation muss neuen Dispatch stoppen, die Anfrage aufzeichnen und In-Flight Effects reconciliieren; das Beenden des Workers macht einen Provider Call nicht rückgängig.

Budget Enforcement gehört neben den Dispatch. Concurrent Calls dürfen nicht dieselbe verbleibende Allowance ausgeben. Prometheus ist ein Monitoring-System, kein autoritatives Per-Request-Spending-Ledger. Reservieren Sie konservativ und reconciliieren Sie den tatsächlichen Verbrauch; verzögertes Provider Accounting und Cancellation können weiterhin zu Overshoot führen.

Neue Model Controls helfen, den Run zu takten, besitzen aber nicht dessen Spending Limit. Anthropics Beta-Task Budgets geben unterstützten Messages-API-Models ein Advisory Budget über eine agentic Loop hinweg. Es kann überschritten werden; max_tokens begrenzt eine einzelne Response, nicht den gesamten Run. Der Support ist Modelspezifisch: Opus 5 unterstützt Task Budgets, Sonnet 5 nicht. Behalten Sie Dispatch Ledger und Cancellation Path auch dann bei, wenn das Model einen Budget Hint erhält.

Provider Safety Stops benötigen einen eigenen Terminal Path. Für OpenAIs misalignment_policy_violation stoppen Sie den Dispatch, behalten korrelierte Records und fordern Operator Review an, statt erneut zu versuchen. Behandeln Sie Stream Errors nach partieller Ausgabe und reconciliieren Sie vorherige Effects; Part 4 erklärt die Monitoring-Grenze.

Evaluation sollte Evidence außerhalb des Producing Contexts einschließen. Ein Fresh-Context Evaluator reduziert Shared-Context Bias, während Tests, Lints, Browser Checks und Schema Validation deterministische Evidence liefern. Der Check kann pass, fail oder needs_human zurückgeben. Bei Code Agents kann der Reviewer eine weitere Model Session mit Read-Only Tools sein. Bei Data- und Report Agents kombinieren Sie deterministische Validation mit einem Reviewer Model, wenn weiterhin Judgment erforderlich ist.

Mit „Shape“ meine ich eine Anordnung dieser Primitives: Wo der Harness liegt, wo State persistiert wird und welche Sandbox die Arbeit ausführt. Ein Shape ist eine Wiring-Entscheidung, keine Vendor-Auswahl. Die folgende Grafik zeigt, bei welcher Run Length jedes Shape seinen Sweet Spot hat. Das ist der Default, den ich den meisten Teams empfehle, das im Reference Repo verwendete Shape und das Grundgerüst, von dem die meisten anderen Shapes abweichen: Queue → Durable State, wobei Sandbox Source, Harness Owner oder State Engine ausgetauscht werden. 1. SDK in einem App Server (synchron, Request-scoped)

Das ursprüngliche Shape. Das Agent SDK läuft innerhalb eines Request Handlers. Gut für Tasks unter 30 Sekunden, Demos und interne Tools. Schlecht für alles, wovon sich ein HTTP Client trennen könnte. Cloud Runs HTTP Timeout liegt maximal bei 60 Minuten, und jeder Panic im Web Tier beendet den Run. Das SDK ist der Harness. Untrusted Tool Execution benötigt eine separate Sandbox, und State liegt normalerweise im Process Memory, sofern Sie ihn nicht explizit anderswo ablegen. Verwenden Sie dies nicht für mehrstündige Arbeit.

2. Queue + Worker + Checkpoint DB

Der Default, den ich den meisten Teams empfehle, sowie die Production-ähnliche Demo-Implementierung in market-analyst-agent: ein Python Worker mit PostgreSQL Checkpointer, Redis Streams (oder RabbitMQ) für die Inbound Queue und ein MCP Sidecar für Tools. Gut für Runs von zehn Minuten bis zu mehreren Stunden mit idempotenten Steps. Der Local Runner kann die Queue für synchrone Entwicklung umgehen, aber die Queue gehört zum Production Shape, sobald Sie asynchrone Submission und Backpressure benötigen.

Im Production Pattern nimmt die App einen Request an, erstellt eine Session Row, pusht einen Job und gibt eine Run ID zurück. Der Worker zieht den Job, führt den Harness aus, schreibt Session Events und Checkpoints, streamt Status und speichert Artefakte währenddessen. Postgres bleibt erhalten, Worker sind austauschbar, und die Queue Depth liefert Backpressure. Spot-/Preemptible-Compute funktioniert, solange die dauerhaften Event- und Checkpoint-Writes abgeschlossen sind, bevor der Worker Success meldet. Das verlinkte Repository veranschaulicht diese Topologie; dauerhafte Wiederherstellung hängt auch von Queue-Leases, der Rücknahme unterbrochener Jobs und der Bestätigung abgeschlossener Arbeit ab.

In diesem Shape ist der Worker der Harness. Sein Container und der Per-Thread-Workspace bilden eine Execution Boundary, aber untrusted Code benötigt weiterhin eine Hardened Sandbox oder VM. Der Event Store besitzt die Session History; PostgresSaver besitzt den Checkpoint State. Sie können eine Datenbank teilen, sofern der Harness beide Schemas explizit schreibt. Traces laufen über OpenTelemetry in den von Ihnen betriebenen Observability Stack.

3. Durable Workflow Engine (Temporal-Style)

Agent-Orchestration-Code läuft in einem Temporal Workflow; Model Calls und Tool Calls laufen als Activities. Workflow State liegt in einem durch Cassandra, MySQL oder Postgres gestützten Event-History-Log und kann daher über Failures hinweg replayed werden. Workflow-Code-Deployments, die sich mit einer laufenden Execution überschneiden, benötigen Replay-Safe Worker Versioning oder Patches; das Ersetzen von Code ohne diese Disziplin kann Replay brechen. Die Temporal × OpenAI Agents SDK Integration, allgemein verfügbar seit März 2026, liefert einen OpenAIAgentsPlugin- und einen activity_as_tool-Helper. Der Agentic-Sandboxes-Beitrag beschreibt, wie ein laufender Agent während einer Conversation auf einen anderen Sandbox Provider geforkt wird. Idle Workflows verbrauchen keine Compute-Ressourcen. Die Einschränkungen sind real: Realtime Agents werden nicht unterstützt, Streaming ist weiterhin als experimentell markiert, und LocalShellTool und ComputerTool sind deaktiviert, weil sie nicht zu einem verteilten Modell passen.

Verwenden Sie dieses Shape, wenn der Run echte Waiting Points hat: Human Approvals, externe Callbacks, lange Sleeps, Retries mit Business Rules oder Deployment Windows – und das Team Replay-Safe Workflow Versioning betreiben kann. Eine Human Approval wird zu einem dauerhaften Sleep ohne Compute-Verbrauch, nicht zu einer Polling Loop.

Der Workflow Code ist der Harness. Die Sandbox liegt normalerweise außerhalb von Temporal und wird aus Activities heraus aufgerufen. Session- und Checkpoint State verschmelzen im Temporal Event-History-Log; Trace Visibility entsteht durch die Temporal UI sowie OpenTelemetry Spans auf jeder Activity.

4. Sandbox Provider pro Session

Ein neueres Shape. Jeder Agent Run erhält eine eigene MicroVM oder einen eigenen Container von einem Sandbox-as-a-Service Provider. Der Harness liegt an einem dauerhaften Ort; die Sandbox ist die disposable Execution Environment.

5. Anthropic Managed Agents (Hosted Harness)

Anthropic hat Managed Agents am 8. April 2026 als Public Beta gestartet, hinter dem managed-agents-2026-04-01-Beta-Header. Der Service stellt eine Hosted Session, einen Harness, eine Sandbox und einen Vault-backed MCP Proxy bereit. wake(sessionId) kann den Harness auf einem neuen Worker initialisieren, ohne dauerhaften Session State zu verlieren.

Anthropic berechnet für Managed Agents die Standard-Token-Rates plus $0.08 pro Session-Stunde. Die Abrechnung erfolgt auf Millisekundenbasis und gilt nur, solange der Session Status „running“ ist; Idle Time ist kostenlos. Eine Runaway Retry Loop verursacht daher zusätzlich zu den Token-Kosten Session-Hour-Kosten.

Lesen Sie die Einschränkungen. Der Batch-API-Discount gilt nicht („Sessions are stateful and interactive. There is no batch mode.“). Managed Agents ist weder über AWS Bedrock noch über Google Vertex AI verfügbar. Innerhalb der Beta liegen MCP Tunnels und Agent „Dreaming“ hinter einer weiteren Research Preview, für die Sie Zugriff anfordern müssen; Multi-Agent Coordination und Rubric-Graded Self-Evaluation sind dokumentierte Teile der Beta. Lock-in ist hoch: Sie tauschen Harness-Freiheit dagegen, die Loop nicht selbst betreiben zu müssen.

Die Default-Cloud-Konfiguration platziert alle fünf Primitives bei Anthropic. Mit Self-Hosted Sandboxes betreiben Sie Execution, Filesystems und Network Egress, während Anthropic Orchestration und Model ausführt. Tool Inputs und Results erreichen weiterhin dessen Control Plane; angehängte Skills und Memory werden dort gespeichert und synchronisiert. Die Kontrolle über die Execution macht das Gesamtsystem nicht Self-Hosted.

Claude Platform on AWS unterstützt ebenfalls Managed Agents und Self-Hosted Sandboxes und ist von Bedrock getrennt. Dort benötigt eine autonome Session nach sechs Stunden ein User-Role-Event zur Reauthentication, und Self-Hosted Sessions können keine Memory Stores anhängen. First-Party Managed Agents hat diese beiden Einschränkungen nicht. Prüfen Sie vor der Übernahme eines Session Designs sowohl die Plattform als auch das Model.

6. LangChain Deep Agents Deploy (Managed Open Harness)

deepagents deploy verpackt einen deepagents.toml in eine LangSmith Deployment mit Durable Execution, Memory, Multi-Tenancy, Human-in-the-Loop, Observability, Sandboxed Code Execution und Scheduled Runs. Cloud-, Hybrid- und Self-Hosted-Deployment-Modi werden unterstützt. Sandbox Provider (LangSmith Sandboxes, Daytona, Modal, Runloop oder Custom) lassen sich über einen einzigen Config Value austauschen. Agent Files und Memory liegen in einem Virtual Filesystem mit pluggable Backends; Checkpoint Persistence ist separat, und Memory ist auf User, Assistant oder beide scoped. Der Lock-in ist geringer als bei Managed Agents: Der Harness ist MIT-licensed, Instructions verwenden den offenen AGENTS.md-Standard, und Agents werden über MCP, das A2A-(Agent2Agent-)Protokoll und Agent Protocol exponiert. Siehe LangChains runtime-behind-production-deep-agents-Beitrag.

Standardmäßig werden alle fünf Primitives gehostet, aber jedes kann per Configuration ausgetauscht werden. Die Sandbox liegt hinter einem einzelnen Config Value. Das Memory Filesystem ist von Thread- und Checkpoint Persistence getrennt. Der Trace geht an LangSmith.

7. Google Cloud Run Service oder Job

Cloud Run verfügt über zwei unterschiedliche Runtime-Modi; welcher passt, hängt davon ab, wie der Agent aufgerufen wird. Services sind HTTP-gebunden und skalieren zwischen Requests auf null; der Harness läuft als Request Handler und kehrt zurück, wenn der Run beendet ist. Jobs laufen ohne HTTP Entry Point bis zum Abschluss; der Harness läuft als One-Shot Worker und beendet sich nach Abschluss der Aufgabe. Beide können den Harness hosten, aber keiner hält State über Runs hinweg. Sessions und Checkpoints müssen in Postgres, Spanner oder einem ähnlichen externen Store liegen.

Die harten Limits unterscheiden sich stark. Cloud Run Service Request Timeout: standardmäßig 300 s, maximal 3.600 s (60 min). WebSockets erhalten denselben Timeout. Cloud Run Jobs: standardmäßig 10 min pro Task, maximal 168 h (7 Tage); bei Tasks mit GPUs maximal 1 Stunde. Instance-Based Billing (Always-Allocated CPU) erlaubt weiterhin Scale-to-Zero; Minimum Instances ist eine separate Einstellung; Jobs besitzen kein HTTP und autoskalieren nicht.

Verwenden Sie einen Service für synchrone Runs bis 60 Minuten. Verwenden Sie einen Job für längere One-Shot- oder asynchrone Arbeit. Cloud Run Jobs können einen Task tagelang am Leben halten, bieten aber kein Durable Replay über Deployments, Versionswechsel oder Worker-Replacement hinweg. Ein längerer Workflow kann sich über mehrere Executions erstrecken, wenn ein externer Orchestrator dauerhaften Progress besitzt.

Cloud Run hostet den Harness. Session- und Checkpoint State liegen in Postgres, Spanner oder einem anderen externen Store, und Traces können über Cloud Logging und OpenTelemetry fließen. Der Service Container ist eine Execution Environment; fügen Sie eine separate Sandbox hinzu, wenn der Agent untrusted Code ausführt.

8. AWS Lambda: begrenzte Invocations und Durable Workflows

Lambdas maximale Function Timeout beträgt unveränderlich 900 s (15 Minuten). Wenn API Gateway der Function vorgeschaltet ist, hängt das Integration Limit vom API-Typ ab. HTTP APIs erlauben 30 Sekunden; REST Integrations haben standardmäßig 29 Sekunden, während Regional und Private REST APIs einen längeren Timeout konfigurieren können. Lambda Durable Functions, im Dezember 2025 gestartet, fügen Managed Checkpoints, Steps und Waits über Executions mit einer Dauer von bis zu einem Jahr hinzu. Die aktive Invocation bleibt begrenzt, während der Durable Workflow sie überleben kann. Vergleichen Sie unterstützte Runtimes, Regionen, Replay Rules und Activity Idempotency mit Ihren Anforderungen.

Lambda kann einen begrenzten Harness innerhalb des 15-Minuten-Caps ausführen. Session- und Checkpoint State benötigen weiterhin explizite externe Speicherorte; fügen Sie für untrusted Code eine eigene Sandbox hinzu und exportieren Sie Traces an externe Telemetry. Ein Durable Lambda Workflow kann mehrstündige Arbeit über begrenzte Invocations hinweg orchestrieren.

9. AWS ECS / Fargate Task pro Run

Fargate dokumentiert kein hartes Task-Runtime-Limit, anders als eine gewöhnliche Lambda Invocation. Fargate unterstützt keine GPU Tasks; ECS GPU Workloads benötigen geeignete EC2 Instances oder einen externen GPU Service. Fargate bietet Virtualization-Based Task Isolation, aber Credentials und erlaubter Network Access benötigen weiterhin ein Threat Model. Fargate Throttling Quotas erlauben einen Launch Burst von 100 und Refilling mit 20 pro Sekunde, mit separaten On-Demand- und Spot-Budgets. ECS Service Quotas begrenzen Services mit AWS Cloud Map Discovery auf 1.000 Tasks pro Service und EC2-basierte Clusters auf 5.000 Container Instances.

Fargate benötigt den awsvpc-Modus, sodass jeder Task ein Network Interface und eine Private IP erhält. Dieses Shape eignet sich für VPC-interne Datenzugriffe. Fargate Spot erhöht das Interruption Risk, und Durability bleibt Ihre Verantwortung, da die Plattform kein Temporal-Style Replay bietet.

Fargate hostet den Harness und gibt jedem Run einen eigenen Task. Das trennt Workspaces und Task Credentials, ist aber für sich genommen keine vollständige Sandbox für hostile Code. Session, Checkpoint und Trace gehen an externe Services wie RDS oder DynamoDB sowie CloudWatch/X-Ray.

Vergleichen Sie außerdem Amazon Bedrock AgentCore Runtime, bevor Sie die AWS Session Layer selbst bauen. Er hostet Ihren Agent Code mit Managed Session Lifecycle und einer Auswahl an Compute. AWS dokumentiert bis zu 8 Stunden auf Serverless MicroVMs oder 14 Tage auf seinem Instances Compute Type, der auch GPU Workloads unterstützt. Instances verwenden von AWS verwaltete EC2-Ressourcen in Ihrem Account und haben ein anderes Security Model als die Serverless-Option. Wählen und testen Sie diesen Compute Contract explizit; eine langlebigere Instance garantiert weiterhin keine Exactly-Once-Execution eines External Side Effects.

10. Kubernetes Job oder Namespace pro Session

Gut geeignet, wenn Sie bereits Kubernetes betreiben und Sandbox-per-Session mit Cluster-weiten Controls wünschen. Schlecht geeignet, wenn Sie Sub-Second Startup benötigen, da das Ziehen des Container-Images und die Initialisierung des Pods bei Cold Start zu lange dauern. Das Pattern besteht aus einem Job pro Agent Run mit activeDeadlineSeconds, einem PersistentVolumeClaim für den Workspace und einem Sidecar für den MCP Server. Crash Recovery müssen Sie selbst bauen. Kubernetes allein für Agents einzuführen, ist aufgrund des Configuration Overheads und der operativen Last teuer. Es lohnt sich nur, wenn Sie K8s bereits aus anderen Gründen betreiben.

Kubernetes hostet den Harness und die Per-Run-Execution-Environment, normalerweise als einen Job und manchmal mit einem dedizierten Namespace. Starke Isolation hängt weiterhin von Runtime Class, Network Policy, Pod Security und der zugrunde liegenden Container- oder VM-Grenze ab. Session- und Checkpoint State liegen in einer externen Datenbank oder auf einem PersistentVolumeClaim.

11. Lokales Docker Compose (nur Development)

Die Referenz für den nächsten Abschnitt. Der Zweck dieses Shapes besteht darin, die Production Topology eins zu eins abzubilden (dieselben Primitives, dieselbe Network Shape), während alles auf einer einzelnen Maschine läuft. Was nicht gespiegelt wird, ist die Isolation: ein gemeinsamer Workspace Mount, ein Postgres, keine Hardened Sandbox und keine separaten Failure Domains zwischen Worker und State. Shippen Sie nichts, das so aufgebaut ist.

Compose spiegelt Shape #2 auf einem einzelnen Host. Im Reference Stack enthält Postgres den Checkpoint State und der Worker Container ist der Harness. Eine Production-ähnliche Session benötigt einen eigenen Append-only Event Store; PostgresSaver History allein stellt keinen solchen bereit. Der gemeinsame Workspace Mount ist für Development praktisch, isoliert aber keine untrusted Runs. Der optionale OpenTelemetry Stack zeichnet Traces auf.

password = quote(os.environ["POSTGRES_PASSWORD"], safe="")
DB_URI = f"postgresql://agent:{password}@postgres:5432/agent"
# `builder` is your StateGraph, already built
session_id = "session-123"
with PostgresSaver.from_conn_string(DB_URI) as checkpointer:
    checkpointer.setup()  # creates tables on first run
    graph = builder.compile(checkpointer=checkpointer)
    result = graph.invoke(

        {"configurable": {"thread_id": session_id}},

Observability, die den Run übersteht

Kurze Request Handlers lassen sich leicht debuggen: Wenn etwas fehlschlägt, lesen Sie die Response und das Live Log. Long-Running Agents haben diesen Luxus nicht. Wenn ein sechs Stunden langer Run fehlschlägt, liegt das interessante Event fünf Stunden zurück, die Live-Terminalausgabe ist verschwunden und der Worker, der sie erzeugt hat, wurde ersetzt. Niemand wird den Run aus dem Memory rekonstruieren. Sie debuggen daher anhand dauerhafter Artefakte, die geschrieben wurden, während der Run noch aktiv war.

Byte says

Wenn ein langer Run fehlschlägt, nachdem die interessante Terminalausgabe weggescrollt ist, bleiben zum Untersuchen das Durable Event Log und der Trace.

Production Stacks decken typischerweise vier Arten von Artefakten ab, aufgeteilt in zwei Gruppen. Zwei davon lesen Sie nach dem Ende des Runs für Postmortems und Replay: ein abfragbares Event Log jedes Steps und OpenTelemetry Traces darüber, wohin Zeit und Tokens flossen. Zwei davon lesen Sie während des Runs. Das eine ist ein Live Tail dessen, was der Agent im Workspace produziert. Das andere ist ein Per-Worktree-Observability-Stack, den der Agent selbst abfragen kann, während er arbeitet.

Strukturiertes Event Log (nach dem Run lesen)

Jeder Model Call, Tool Call, jedes Result, jeder Error und jede Approval wird mit Session ID und Timestamp als Key in Durable Storage geschrieben. Nach Ende des Runs fragen Sie es wie eine normale Datenbanktabelle ab. Addy Osmani setzt in Long-running Agents den Maßstab klar: „If you can’t reconstruct what the agent did in the last 24 hours from durable storage, what you have is a long-running shell script that happens to call an LLM, not a long-running agent.“

OpenTelemetry GenAI Traces (nach dem Run lesen)

Dieselben schrittweisen Daten werden als Spans mit den Standardattributen aus den gen_ai.*-Semantic Conventions ausgegeben: Model Name, Provider, Input- und Output-Token-Counts, Conversation ID und Workflow Name. Die Conventions befinden sich weiterhin im Development-Stabilitätsstatus.

2026 wurden sie aus dem zentralen OpenTelemetry-Semantic-Conventions-Repository in ein eigenes GenAI Semantic Conventions Repo verschoben. Die Attributnamen können zur Instrumentierung verwendet werden; pinnen Sie jedoch die von Ihnen validierte Revision statt einer Main-Repo-Versionsnummer. Provider-spezifische Felder liegen in Subnamespaces (anthropic.*, openai.*), die über gen_ai.provider.name referenziert werden. Der Grund für den Standard ist Portability: Auf OTLP-kompatiblen Destinations, die diese Conventions unterstützen, erfordert ein Backend-Wechsel möglicherweise keine erneute Instrumentierung; Backend-Adapter oder zielsystemspezifische Configuration können dennoch erforderlich sein.

Tool-Call-Timeline plus Workspace-Diffs (während des Runs lesen)

Workspace Changes geben einen schnellen Überblick darüber, was ein Agent während eines Runs tut. Anthropics Harness Primitives for Long-Running Claude Agents Quick Start verwendet Live Workspace Monitoring. Wo watch installiert ist, aktualisiert watch -n 5 'git log --oneline -8' alle fünf Sekunden die neuesten Commits. Für Screenshots öffnen Sie das Screenshot-Verzeichnis in einem File Browser, sortieren nach Modification Time mit den neuesten zuerst und prüfen die neuesten Bilder. Commits und Screenshots sind Hinweise auf Aktivität; vergleichen Sie sie mit Test Results und Run Status, bevor Sie entscheiden, dass der Agent Fortschritte macht.

Ephemeral Stack pro Worktree (vom Agent selbst während des Runs gelesen)

Nach OpenAIs Harness Post gilt: „Logs, metrics, and traces are exposed to Codex via a local observability stack that’s ephemeral for any given worktree.“ Jeder Agent Worktree erhält ein eigenes kurzlebiges Loki + Prometheus + Tempo, das ausschließlich auf diesen Run scoped ist. Der Agent fragt es während seiner Arbeit ab. Dadurch kann ein Prompt wie „Kein Span in diesen vier User Journeys überschreitet zwei Sekunden“ direkt vom Agent verifiziert werden, statt dass er raten muss.

(Der Fresh-Context Evaluator aus der Failure-Modes-Tabelle liest diese Artefakte, um „done“ zu entscheiden. Er gehört zur Evaluation, nicht zur Observability; siehe § gesunder Run-Lifecycle. Er hängt von jeder der oben genannten Oberflächen ab.)

Ein minimaler Self-Hosted Observability Stack

Für etwas wie market-analyst-agent:

  1. OpenTelemetry Collector mit dem GenAI Normalizer Processor (contrib, alpha) für unterstützte GenAI Attributes. Verwenden Sie die generischen Attributes- oder Transform-Prozessoren, um gen_ai.*-Felder zu filtern oder umzuschreiben.
  2. Tempo (oder Jaeger) für Traces, keyed by gen_ai.conversation.id / thread_id.
  3. Loki für strukturierte Event-Log-Einträge.
  4. Prometheus für gen_ai.client.token.usage, gen_ai.client.operation.duration und gen_ai.client.operation.time_to_first_chunk – die gen_ai.server.*-Metrics kommen vom Model Server und sind daher nur verfügbar, wenn Sie die Weights hosten (siehe die GenAI Metrics Conventions).
  5. Grafana Dashboards keyed on gen_ai.agent.name und gen_ai.request.model.

  • LangSmith: native LangGraph Integration; zugleich Deployment Target für Deep Agents Deploy.
  • Braintrust: stärkste Eignung, wenn Eval-First-Regression-Suites Priorität haben.
  • Arize Phoenix: OSS, nativ zu OTLP (dem OpenTelemetry Wire Protocol), mit OpenInference-Instrumentation.
  • OpenAIs Tracing Dashboard: automatisch bei Verwendung des OpenAI Agents SDK oder seiner Temporal Integration.

)

)

{ span.gen_ai.operation.name = "execute_tool" && duration > 30s }

Die LogQL Aggregation nimmt genau ein geloggtes Completion Event pro Model Call an. Deduplicieren Sie diese Events vor der Ingestion; rate würde Tokens pro Sekunde statt dieses einstündigen Totals melden. Validieren Sie das Field Mapping gegen Ihren deployed Loki Stream.

Das Debug-Bundle-Pattern

Wenn ein Run fehlschlägt, sollte der Worker /workspaces/${THREAD_ID}/_debug/ mit den Artefakten ablegen, nach denen Sie in einem Postmortem fragen würden:

  • events.jsonl: Export aus dem separat geschriebenen Append-only Event Store des Harness, einschließlich Tool Intents, Outcomes, Approvals und Errors.
  • checkpoints.jsonl: Graph-State-History aus checkpointer.list({"configurable": {"thread_id": ...}}), als Checkpoints statt als Event Log gekennzeichnet.
  • last_state.json: StateSnapshot.values aus dem letzten erfolgreichen Super-Step.
  • trace.json: OTLP-exportierte Spans für den Run; Metadaten sind die Baseline, erfasster Content folgt der Trace Policy.
  • tool_calls.csv: (ts, tool, input_hash, latency_ms, status, error).
  • workspace.tar.zst: Workspace-Verzeichnis plus git diff gegen den Initializer Commit.
  • screenshots/*.png: was der Agent gesehen hat.
  • PROGRESS.md, feature-list.json und andere vom Agent verfasste Progress Files.
  • env.txt: Image Tags, Model Version, Harness Commit SHA.

Zusammen können diese Artefakte einem Menschen oder Reviewer Agent genügend Evidence liefern, um den Failure zu rekonstruieren, sofern der Harness den Event Store geschrieben hat, während der Run aktiv war. „Der Agent ist stecken geblieben“ ist vage. Ein illustrativer Report ist konkret: Session s_123 verbrauchte 71 Prozent ihrer Tokens damit, drei Commands zu wiederholen, nachdem npm install fehlgeschlagen war.

Das richtige Shape auswählen: Ein Entscheidungsleitfaden

Der Großteil des obigen Vergleichs läuft auf eine Handvoll Entscheidungen hinaus.

Mit der Run Length beginnen

Verwenden Sie die Run Length als ersten Filter:

  • Unter 30 Sekunden, idempotent: Request-Lifecycle-SDK in einem App Server.
  • 30 s bis 60 min: Queue + Worker + Checkpoint DB.
  • 60 min bis 24 h: dieselbe Queue + Worker oder ein Cloud Run Job für One-Shot-Arbeit. Verwenden Sie eine Durable Workflow Engine, wenn Sie zusätzlich Versioning und Replay benötigen.
  • Mehr als 24 h, muss Deployments überstehen: Durable Workflow Engine (Temporal-Style). Cloud Run Jobs können lange Arbeit bis zu ihrem Task Limit halten, bieten aber keine Replay Semantics.
  • Multi-Day Reinforcement-Learning Training Loops: K8s Job + Volume + Temporal.

Prüfen Sie nach diesem groben Filter Side Effects, Recovery, Replay, Isolation, Data Location und das Team, das das System betreiben wird.

Platform Fit nach Use Case

Die Matrix ist dicht, und keine einzelne grüne Zelle entscheidet über die Architektur; die Conditional Cells, in denen eine Plattform etwas nur mit einer Einschränkung unterstützt, sind meist ausschlaggebend. Eine breite Workload Coverage ist nützlich, zeigt aber weder Data Residency noch Replay Semantics, Provider Dependence, Operational Maturity oder die Kosten einer späteren State-Migration.

Die Conditional Cells verwenden für jede Plattform dieselbe Regel. Deep Agents’ AWS-/VPC- und GPU-Optionen hängen von Hybrid Deployment oder einem Sandbox Provider ab; Managed Agents kann kundenseitig betriebene Execution verwenden und gleichzeitig Hosted Orchestration beibehalten. Die Zeile zur Sandbox Choice umfasst eine External-Provider-Integration, die Sie auf einem eigenen Runtime bauen oder in einem Managed Harness konfigurieren. Sie verspricht keinen Snapshot des laufenden States. Ein Kubernetes Job benötigt für einen interaktiven Request ebenfalls eine API- oder Queue-Layer; schnelles Abschließen macht ihn nicht zu einem HTTP Service. Vergleichen Sie vor der Auswahl den Network Access, die Hardware, die Recovery und den State-Export-Path des gewählten Deployments. Die Zeile zum Harness Code betrifft den Zugriff auf die Loop-Implementierung, nicht die Portability eines Managed Deployments oder seines States. Kubernetes GPU Execution benötigt außerdem GPU Nodes, Drivers und ein Device Plugin.

Managed Agents erfordert Claude und von Anthropic betriebene Orchestration. Seine optionale Self-Hosted Sandbox kann zu Private-Network-Execution passen; eine Anforderung, Inference oder Control Plane selbst zu hosten, schließt es jedoch weiterhin aus. Prüfen Sie, welche Tool Inputs, Results, Skills und Memory diese Grenze überschreiten können. Interne Coding-Arbeit kann passen, wenn diese Data Flows akzeptabel sind und das Team den Betrieb des Harness delegieren möchte.

Das Pricing sollten Sie vor der Entscheidung modellieren, nicht danach. Die Session-Hour-Zeile beträgt $0.08/hour zusätzlich zu den Standard-Token-Kosten. Wenn eine einzelne Session dauerhaft liefe, entspräche dies ungefähr $58/Monat pro Session. Bei 100 dauerhaft laufenden Sessions wären es ungefähr $5,800/Monat vor Tokens. Multiplizieren Sie $0.08 mit Ihren erwarteten Concurrent-Session-Hours, addieren Sie dies zu Ihrer Token-Rechnung und vergleichen Sie es mit den Kosten eines Queue-+Worker-Stacks auf Ihrer eigenen Infrastruktur. Die Migration weg von Managed Agents ist ein Re-Platforming-Projekt, keine Config-Änderung.

Hosted Harness vs. Owned Harness

Die Unterscheidung betrifft, wer den Harness betreibt, nicht wer seinen Code geschrieben hat. Hosted bedeutet, dass der Vendor die Harness Loop in seiner Infrastruktur betreibt und Sie eine API aufrufen. Owned bedeutet, dass Sie die Loop auf Ihrer eigenen Infrastruktur ausführen, selbst wenn der Harness Code von einem Vendor stammt.

LangChain erscheint auf beiden Seiten dieser Grenze, was leicht zu Verwirrung führt. Das Unternehmen liefert LangGraph, eine MIT-licensed Library, die Sie selbst hosten (owned), und Deep Agents Deploy, ein Managed Product, das im Default-Cloud-Modus einen Deep-Agents-Harness auf LangSmith Deployment ausführt (hosted). Dasselbe Unternehmen, zwei unterschiedliche Operating Models. Sie wählen, wer die Loop betreibt, nicht wessen Logo auf der Library steht. (Deep Agents Deploy besitzt außerdem einen Self-Hosted Mode für Teams, die Harness-Ergonomie ohne die Cloud-Komponente wünschen; dieser Modus fällt in die Owned-Kategorie.)

Wählen Sie einen Hosted Harness, wenn Model Support, Data Boundary, Recovery Behavior und Extension Points bereits passen. Wählen Sie einen Owned Harness, wenn diese Constraints Anforderungen sind, von denen Sie erwarten, dass sie sich ändern. Die Migration zwischen beiden verändert State, Observability und Execution Boundaries; testen Sie daher den Exit Path, bevor Production Data davon abhängt.

Hosted Sandbox vs. eigene Execution Environment

Wählen Sie eine Hosted Sandbox, wenn Isolation, Pause/Resume oder Fork Semantics des Providers zu Threat Model und Startup Budget passen. Docker oder Fargate können für vertrauenswürdige interne Workloads mit VPC Access oder strikter Data Residency geeignet sein; ein Standardcontainer ist jedoch keine ausreichende Boundary für hostile Code. Part 4 erläutert das Isolation Menu für diesen Fall.

State Stores: Git, DB und Object Storage nebeneinander

Long-Running Agents verwenden meist drei State Stores gleichzeitig, weil jeder Store ein anderes Artefakt besitzt.

Git speichert Workspace State: den Code, die Dokumente und die Progress Files, die der Agent verändert. Jeder Commit gibt dem Harness einen stabilen Recovery Point und der nächsten Session eine kompakte Historie.

Die Checkpoint-Datenbank speichert Graph State: was entschieden wurde, welche Nodes liefen, welche Results zurückkamen und was als Nächstes laufen soll. Der Artifact Store enthält große Final Outputs wie PDFs, Parquet-Dateien und Screenshots. Diese Artefakte gehören weder in Git noch in die Checkpoint-Datenbank.

Wann Git als State verwendet werden sollte

Verwenden Sie Git, wenn der Workload Code-förmig ist (Multi-File-Edits, Refactorings, App Generation) oder dokumentenförmig genug, dass File History relevant ist. Das Pattern ist einfach: Einen Run Branch erstellen, einen Initializer Commit anlegen und anschließend an sinnvollen Boundaries committen: nach Setup, nach jedem Feature, nach bestandenen Tests und nach dem finalen Cleanup. Speichern Sie die aktuelle Workspace Commit SHA neben der Checkpoint Row. Beim Resume checkt der nächste Worker den Branch aus, liest git log --oneline -8, untersucht git status und den neuesten Diff und liest anschließend PROGRESS.md oder die Handoff-Datei, die die vorherige Session geschrieben hat.

Damit wird Git zu einer Recovery Surface für das bearbeitete Artefakt, nicht zu einem Ersatz für die Checkpoint DB. Git kann zwei Fragen beantworten: Was hat sich geändert und welche Version hat die Tests bestanden? Es kann dem Harness nicht sagen, welcher Graph Node als Nächstes laufen soll, welcher Tool Call auf Approval wartet oder welcher Retry seinen Idempotency Key bereits verwendet hat. Anthropics Harness verwendet Initializer Commits und Per-Feature Commits als Source of Truth für Workspace Recovery; das Model liest git log --oneline -8, um State wiederherzustellen. Überspringen Sie Git, wenn das Arbeitsprodukt eine einzelne Conversation Response ist. Der Overhead lohnt sich dann nicht.

Wann DB Checkpointing verwendet werden sollte

Verwenden Sie PostgresSaver-artiges Checkpointing, wenn der Agent eine Graph Structure mit mehreren Nodes besitzt, deren Intermediate State relevant ist (Planner → Researcher → Writer → Verifier). Das Reference Repo verwendet es genau aus diesem Grund. Legen Sie Workspace-Artefakte im Terabyte-Maßstab nicht in den Checkpoint; sie gehören in Object Storage.

Wann ein Artifact Store verwendet werden sollte (S3 / GCS)

Verwenden Sie Object Storage, wenn:

  • der Output größer ist, als die Checkpoint-Datenbank tragen sollte;
  • Downstream Consumers ein URL-adressierbares Artefakt benötigen, ohne über den Agent zu gehen; oder
  • Deliverable und Run State unterschiedliche Retention Windows haben.

Sie könnten beispielsweise das Session Log nach 30 Tagen löschen, den finalen Report aber jahrelang behalten. Strukturieren Sie das Layout nach (thread_id, checkpoint_id, artifact_name), damit der erzeugende Run rekonstruierbar bleibt.

Wann Human-Approval-Gates erforderlich sind

Legen Sie Approval Requirements anhand von Action Risk, bereits erteilter Authority und Deployment Policy fest. Ein reversibler Draft Database Write unterscheidet sich von einer Kundenbelastung oder einer destruktiven Production-Änderung. Wenn eine Approval erforderlich ist, zeigen Sie die tatsächliche Action, Arguments und Destination an, persistieren Sie die Entscheidung und prüfen Sie sie erneut, wenn sich der vorgeschlagene Call ändert; führen Sie einen abgelehnten Call nicht aus. LangGraphs interrupt() und die Approval Middleware von Deep Agents können den Run für diese Entscheidung pausieren. Part 4 erklärt, warum es sich um eine Permission Decision und nicht um eine Prompt Instruction handelt.

Eine praktische Production-Checkliste

Bevor ein Long-Running Agent ausgeliefert wird, beantworten Sie diese Fragen in konkreten Infrastrukturbegriffen.

  1. Welcher Store besitzt Session Events und Checkpoints?
  2. Was passiert, wenn der Worker mitten in einem Tool Call stirbt?
  3. Kann ein Run den Workspace eines anderen Runs beschädigen?
  4. Welche Actions benötigen Approval?
  5. Können Model oder Sandbox Raw Credentials lesen?
  6. Welche Tool Calls lassen sich sicher retryen?
  7. Wo wird das Per-Run-Cost-Cap durchgesetzt?
  8. Welche deterministische Evidence entscheidet über Completion, und welche verbleibenden Kriterien benötigen einen Reviewer?
  9. Wo liegen Final Outputs, nachdem die Sandbox verschwunden ist?
  10. Können wir einen fehlgeschlagenen Run morgen erklären, ohne ihn erneut auszuführen?

Wenn die Antwort auf eine dieser Fragen lautet: „Der Prompt weist den Agent an, vorsichtig zu sein“, ist das System noch nicht deployed. Es ist weiterhin eine Demo.
