Das Model wählt weiterhin die nächste Aktion, aber der Runtime muss den Zustand bewahren, die Ausführung steuern und sich von einem Fehler inmitten eines Tool Calls erholen. TL;DR

Ein Long-Running Agent benötigt fünf explizit platzierte Dinge: ein dauerhaftes Session Log, das Harness, das den Loop steuert, eine Sandbox, einen Checkpoint Store und einen Trace. Queue plus Worker plus ein PostgreSQL Checkpointer ist für die meisten Teams der richtige Default. Wenn du nicht benennen kannst, welche Komponente jeweils für eines der fünf Dinge zuständig ist, handelt es sich beim Agent um einen Prototyp.

Was ist ein AI Agent Runtime?

Ein AI Agent Runtime ist die Infrastruktur-Schicht, die einen Tool-Using Agent nach dem Ende des Model Calls am Leben hält, isoliert, beobachtbar macht und fortsetzbar hält. Sie verwaltet Session State, Tool Execution, Checkpoints, Secrets, Traces, Cost Limits und die Deployment-Form. Das Model wählt die nächste Aktion; der Runtime bestimmt, wo diese Aktion ausgeführt wird, wie sie protokolliert wird und wie der Run nach einem Fehler fortgesetzt wird. Ob die Aktion zulässig ist, entscheidet das Harness. Das Harness ist keine Storage-Schicht, sondern das Programm, das auf diesen Komponenten aufsetzt; es erscheint in der folgenden Tabelle, weil auch sein Platz festgelegt werden muss.

Lange Läufe brechen Annahmen über zustandslose Prozesse

Ein zustandsloser Chat-Endpunkt kann den Request-Zustand in einem Prozess halten und ihn nach der Antwort verwerfen. Ein langer Agent-Lauf übersteht Worker-Neustarts, Deployments, Context-Resets und Pausen für Freigaben. Der Worker-Prozess kann daher nicht länger die Quelle der Wahrheit sein.

Das OpenAI-Codex-Team berichtet in seinem Harness-Engineering-Beitrag, wie lange diese Läufe dauern:

„Wir beobachten regelmäßig, dass einzelne Codex-Läufe über sechs Stunden an einer einzigen Aufgabe arbeiten (oft während die Menschen schlafen).“

Das Engineering-Team von Anthropic beschreibt das entsprechende Zustandsproblem in Effective harnesses for long-running agents:

„Die zentrale Herausforderung bei langen Agent-Läufen besteht darin, dass sie in diskreten Sessions arbeiten müssen und jede neue Session ohne Erinnerung an das beginnt, was zuvor geschehen ist.“

Beide Beobachtungen führen zum selben Runtime-Design: Zustand außerhalb des Workers persistieren und Worker austauschbar machen.

Die Session muss außerhalb des Worker-Prozesses liegen. Ein Durable Store zeichnet Model Calls, Tool Results und Freigaben auf, sodass ein anderer Worker nach einem Crash am letzten sicheren Punkt fortsetzen kann. Checkpoints ermöglichen es dem Runtime außerdem, eine frische Model Session zu starten, wenn das Context Window voll ist, ohne die vollständige Historie erneut abzuspielen. In Anthropics Formulierung werden Harness-Instanzen dadurch wegwerfbar und neu startbar; der Durable State liegt an anderer Stelle.

Fünf Primitives, die vor dem Deployment feststehen sollten

Der Beitrag Scaling Managed Agents von Anthropic bietet eine nützliche Begrifflichkeit für fünf Verantwortungsbereiche einer Runtime. Der Harness treibt den Agent voran, während die Session festhält, was er getan hat, und die Sandbox Commands ausführt. Der Checkpoint gibt dem nächsten Worker einen Resume Point; der Trace bewahrt Belege für das spätere Debugging. Eine Implementierung kann Komponenten zusammenlegen, doch die Verantwortungsbereiche und Failure Boundaries benötigen weiterhin eindeutige Bezeichnungen.

Session. Ein Append-only-Log aller Ereignisse: Model Calls, Tool Calls, Results, Fehler und Freigaben.

Der Begriff ist überladen; daher unterscheiden wir drei Spans, die als Session bezeichnet werden. Ein Thread ist die Konversation eines Users über mehrere Tage hinweg. Er ist der langlebigste der drei Begriffe, und LangGraph verfolgt ihn mit einem thread_id.

Eine Model Session ist die kürzeste: ein durchgehender Abschnitt desselben Model Context. Compaction – der Schritt, der das Window zusammenfasst, damit die Arbeit fortgesetzt werden kann – verlängert eine Model Session, statt sie zu beenden. Ein Neustart oder ein bewusst gesetzter neuer Start beendet sie. Teil 6 verwendet „Model Session“ in diesem Sinn.

In diesem Artikel bezeichnet „Session“ das Durable Log eines einzelnen Laufs. Sie liegt zwischen den beiden anderen Begriffen: Viele Model Sessions schreiben in ein Log, und ein Thread sammelt viele Logs. Recovery ist wake(sessionId) → getSession(id) → resume from last event.

In LangGraph verwendet die Wiederherstellung einen thread_id zusammen mit einem Postgres-Checkpointer (siehe LangGraph persistence). Das OpenAI Agents SDK enthält zehn integrierte Session-Backends, darunter SQLiteSession, RedisSession, SQLAlchemySession, MongoDBSession und EncryptedSession (siehe die Sessions-Dokumentation).

Harness. Der Orchestration Loop und hier die einzige Primitive, die Entscheidungen trifft. Er stellt den Prompt aus der Memory zusammen, ruft das Model auf, prüft den vorgeschlagenen Tool Call anhand seiner Berechtigungsregeln, führt erlaubte Aufrufe aus, schreibt die Ergebnisse zurück in die Session, wendet Retry-Regeln an und entscheidet, ob die Aufgabe abgeschlossen ist. Jeder dieser Schritte enthält eine Annahme darüber, was das Model nicht selbst erledigen kann. Anthropic formuliert diesen Punkt direkt — das entsprechende Zitat steht weiter unten im Abschnitt zu Failure Modes, der sich größtenteils damit befasst, was passiert, wenn diese Annahmen veralten.

Das Codex-Team von OpenAI nennt dies Harness Engineering: Software zu schreiben erfordert weiterhin Engineering-Aufwand, aber ein größerer Teil davon fließt inzwischen in das Scaffolding statt in den Code selbst. LangGraphs CompiledStateGraph, LangChains Deep Agents und sein create_deep_agent-Einstiegspunkt sowie Claude Code selbst sind Harnesses in diesem Sinne.

Sandbox. Die isolierte Ausführungsumgebung, in der Commands tatsächlich laufen. Die Seite zu Sandbox concepts im OpenAI Agents SDK zieht die Grenze klar:

„Die äußere Runtime ist weiterhin für Approvals, Tracing, Handoffs und die Resume-Verwaltung zuständig. Die Sandbox-Session ist für Commands, Dateiänderungen und die Isolation der Umgebung zuständig.“

Mit „äußerer Runtime“ ist dort das Harness zusammen mit seinen State Stores gemeint. In der Terminologie dieser Reihe sind Approvals und Handoffs Entscheidungen des Harness (Teil 4 und Teil 6); Tracing und Resume-Verwaltung sind Session- und Checkpoint-Primitives.

Sandboxes unterscheiden sich darin, wie lange sie bestehen und was sie zwischen Runs speichern. Die einfachste Variante ist fresh ephemeral: Eine Sandbox wird für eine einzelne Aufgabe gestartet, nach deren Ende zerstört, und bei jedem Run fallen die Cold-Start-Kosten an.

Persistent paused-Sandboxes behalten das Dateisystem und einen Memory-Snapshot zwischen Runs. Beim nächsten Resume kann ein vollständiger Boot vermieden werden. Snapshot or fork erstellt aus einem vorbereiteten Parent ein Copy-on-Write-Image, sodass viele Aufgaben installierte Dependencies und warme Caches gemeinsam nutzen können, ohne ihren beschreibbaren State zu teilen.

Per-worktree-Sandboxes geben jeder Aufgabe ihren eigenen Workspace und Observability-Stack. Separate Logs, Metriken und Traces ermöglichen das Debugging eines Runs, ohne dass dessen State in einen anderen Run überläuft. Die weiter unten in diesem Artikel enthaltene Provider-Tabelle vergleicht Cold-Start- und Persistenzverhalten.

Checkpoint. Resumable State.

LangGraphs PostgresSaver schreibt an jeder Grenze eines Super-Steps einen Checkpoint. Ein Super-Step ist eine Runde des Graphs — entweder ein einzelner Node oder ein parallel ausgeführter Batch. Task-spezifische Writes gehen an checkpoint_writes, sodass erfolgreiche Node-Outputs bei einem Fehler eines Geschwisters nicht erneut berechnet werden.

Ein Checkpoint ist ein einfaches Dict (v, id, ts, channel_values, channel_versions, versions_seen, updated_channels). LangGraph serialisiert es mit seinem auf msgpack basierenden JsonPlusSerializer statt mit JSON. datetime, set, Decimal und Dataclasses lassen sich ohne Informationsverlust serialisieren und deserialisieren. Das Format ist auf der PyPI-Seite von langgraph-checkpoint-postgres sowie in der LangGraph checkpoints reference dokumentiert.

StateSnapshot ist die separate, umfangreichere Ansicht, die graph.get_state() auf Basis eines Checkpoints erstellt. Dieses Objekt wird später über sein .values in das Debug-Bundle geschrieben.

Trace. Die Oberfläche für Replay und Debugging. Jeder Model-Aufruf, Tool Call und Schritt eines Subagents wird zu einem Span mit Timing, Inputs, Outputs, Token-Anzahlen und Kosten. Wenn ein sechs Stunden dauernder Lauf fehlschlägt, liest du den Trace, um herauszufinden, was schiefgelaufen ist. Die Terminalausgabe des Laufs ist zu diesem Zeitpunkt längst verschwunden. Die GenAI semantic conventions von OpenTelemetry standardisieren die Attributnamen (welches Model, welcher Provider, wie viele Tokens, welche Konversation, welcher Workflow). Für ein OTLP-kompatibles Zielsystem, das diese Konventionen unterstützt, kann dieselbe Instrumentierung den Trace an Systeme wie Tempo, Jaeger, Honeycomb oder LangSmith exportieren; möglicherweise sind jedoch weiterhin Backend-Adapter oder eine zielsystemspezifische Konfiguration erforderlich.

Richtlinien und Secrets durchziehen die Primitives

Zwei Grenzen durchziehen alle fünf Primitives. Sie sind die Runtime-Variante des Security-Arguments aus Teil 4. Die Berechtigungsentscheidung selbst gehört zum Harness; im Folgenden geht es darum, wo die sie durchsetzende und mit Daten versorgende Infrastruktur physisch sitzt.

Durchsetzung von Berechtigungen

Die Berechtigungsleiter aus Teil 4 benötigt einen Ausführungsort. Die Prüfung wird vor jedem Tool Call ausgelöst und entscheidet, ob dieser ausgeführt wird. In Production sind zwei Muster verbreitet. Deep Agents lässt jeden Subagent deklarieren, welche Dateipfade er lesen oder schreiben darf, und die Middleware blockiert alles außerhalb dieser Deklaration. Anthropic Managed Agents leitet jeden Tool Call über einen Model Context Protocol (MCP)-Proxy, sodass der Proxy die Berechtigungen anstelle des Agent-Codes durchsetzt. Wenn ein sensibler Call eine menschliche Freigabe erfordert, pausieren interrupt() von LangGraph und der Approval Hook von Deep Agents den Graph, bis eine Person zustimmt.

Secret Broker

Das Model sollte keine langlebigen Secrets sehen, und normalerweise sollte auch die Sandbox keinen Zugriff darauf haben. Das Managed-Agents-Muster ist dasjenige, das du übernehmen solltest:

„Für Git verwenden wir den Access Token des jeweiligen Repositorys, um das Repository während der Initialisierung der Sandbox zu clonen, und binden ihn in das lokale Git-Remote ein. Git push und pull funktionieren innerhalb der Sandbox, ohne dass der Agent den Token selbst verarbeitet. Für Custom Tools unterstützen wir MCP und speichern OAuth-Tokens in einem sicheren Vault. Claude ruft MCP Tools über einen dedizierten Proxy auf; dieser Proxy erhält einen mit der Session verknüpften Token. … Das Harness erhält zu keinem Zeitpunkt Kenntnis von Credentials.“

Im market-analyst-agent-Referenz-Stack — einem kleinen LangGraph Agent, der Marktdaten abruft und einen Analystenbericht verfasst und im Verlauf dieser Serie entwickelt wurde — hält der MCP-Sidecar die API-Keys des Datenanbieters und stellt dem LangGraph Worker ausschließlich die Tool-Oberfläche bereit. In der lokalen Compose-Datei lesen beide Container dieselbe .env. Das ist ein Development-Shortcut und nicht das empfohlene Muster. In der Produktion bezieht der Sidecar seine Umgebungsvariablen aus einem Secret Store — Docker Secrets oder HashiCorp Vault — auf den der Worker nicht zugreifen kann. Der Worker ruft das Tool dann auf, ohne das dahinterliegende Credential jemals selbst zu halten.

Platzierung auf Plausibilität prüfen

Eine praktische Plausibilitätsprüfung besteht darin, jede Komponente und die von ihr implementierten fünf Primitives zu dokumentieren. Postgres könnte Session und Checkpoint abdecken. Der Worker-Container ist das Harness. Ein Service wie Daytona, Modal oder E2B stellt die Sandbox bereit, während Tempo oder LangSmith den Trace speichert.

Untersuche anschließend gekoppelte Fehler. Wenn zwei Primitives im selben Prozess liegen, kann ein einziger Crash beide lahmlegen. Wenn sie ein Credential gemeinsam nutzen, kann ein Leak beide Grenzen überschreiten. Häufige Beispiele sind ein Worker, der zugleich für die dauerhafte Speicherung von Traces zuständig ist, oder ein Sidecar-Token, der zugleich die Checkpoint-Datenbank entsperrt.

Fehlerzustände in Production AI Agent Runtimes

Der Runtime verwaltet Retries, stellt frühere Arbeit wieder her, isoliert Workspaces und setzt Budgets durch. Wenn sich Runs über mehrere Worker und Context Windows erstrecken, verlagern sich die Fehlerursachen hin zu State-Problemen, doppelten Seiteneffekten, Sandbox-Drift und Budgetüberschreitungen.

Die Fehler lassen sich in vier Gruppen einteilen:

  • Fehler bei der Output-Qualität: Der Agent erklärt die Aufgabe für erledigt, obwohl die Arbeit tatsächlich noch nicht abgeschlossen ist, vergisst nach einem Reset des Context Windows, was er getan hat, oder vertraut seiner eigenen Self-Evaluation und liefert fehlerhaften Output aus.
  • Fehler bei der Kostenkontrolle: Der Agent gerät in eine Retry-Schleife oder verbraucht ein Token- oder Tool-Call-Budget, ohne etwas Nützliches zu produzieren.
  • State- und Crash-Fehler: Workspaces driften auseinander, weil ein Run Dateien verändert, die einem anderen Run gehören; Tool Calls werden aufgrund von Retries mehrfach ausgeführt; oder Arbeit geht verloren, wenn ein Worker zwischen zwei Events ausfällt.
  • Fehler des Context Windows: Das Model fasst zusammen und beendet den Lauf zu früh, weil es glaubt, der verfügbare Platz gehe aus, obwohl das Window noch über ausreichend Kapazität verfügt.

Die Tabelle ordnet jedem Fehler eine Mitigation, die Grundlage der Empfehlung und den Runtime-Hook zu, der sie durchsetzt. Model-spezifisches Verhalten kann sich ändern. Betrachte Beobachtungen zu einzelnen Anbietern daher als Anlass, die Annahme erneut zu testen, nicht als dauerhaft gültige Regeln.

Der gesunde Run-Lifecycle

Ein gut funktionierender Run ist langweilig. Er besteht aus einer Kette kleiner, wiederherstellbarer Schritte, und jeder Schritt schreibt sein Ergebnis in einen persistenten Speicher, bevor der nächste beginnt.

Das Schreiben jedes Ergebnisses vor dem Start des nächsten Schritts begrenzt den Schaden bei einem Crash. Ein Fehler verliert nur den gerade laufenden Schritt, und der nächste Worker setzt beim letzten abgeschlossenen Schritt fort, statt die gesamte Anfrage neu zu starten.

  1. Starten Sie entweder mit einer neuen oder mit einer fortgesetzten Session. Beim Fortsetzen mounten Sie den Workspace aus seinem zuletzt bekannten Zustand, lesen Sie alle Fortschrittsdateien ein, die der vorherige Versuch hinterlassen hat (PROGRESS.md, feature-list.json), und laden Sie den letzten Checkpoint aus der Datenbank. An dieser Stelle übergibt das Harness dem Agent alles, was der vorherige Worker vor seinem Abbruch im Speicher hatte.
  2. Planen Sie, bevor Tool Calls ausgelöst werden. Halten Sie fest, woran „fertig“ zu erkennen ist, wie viele Ressourcen der Run verwenden darf, welche Tools der Agent aufrufen kann und wodurch der Run vorzeitig beendet werden soll. Diese Planwerte werden zu Runtime-Prüfungen; ohne sie gibt es bei der Ausführung keine Begrenzung.
  3. Führen Sie jeweils nur einen Tool Call aus. Die Berechtigungsprüfung des Harness entscheidet, ob er zugelassen wird, dispatcht ihn, erfasst das Ergebnis und schreibt ein Event in das Session Log. Ein Schritt, ein Event. Ein Absturz zwischen zwei Events ist beherrschbar, weil das Log – nicht der Speicher des Workers – als Source of Truth dient.
  4. Erstellen Sie an den Grenzen von Super-Steps oder in einem einfacheren Harness nach jedem Event einen Checkpoint. Persistieren Sie den Graph-Zustand, den Workspace-Diff und Referenzen auf alle erzeugten Artefakte. Dieser Checkpoint wird beim nächsten Resume von Schritt 1 eingelesen. Fehlt der Checkpoint oder ist er veraltet, fällt die Recovery auf die vollständige Wiedergabe des Session Logs von Anfang an zurück, was deutlich langsamer ist.
  5. Bewerten Sie die Artefakte, sobald der Agent davon ausgeht, fertig zu sein: Tests, ein Evaluator mit frischem Kontext, Schema-Validierung, Browser-Checks. Besteht die Prüfung, wird der Run erfolgreich beendet. Schlägt sie fehl, wird der Run mit der Fehlermeldung im Context vom letzten sauberen Checkpoint aus fortgesetzt und erneut ausgeführt.

Kein Schritt in dieser Liste erfordert, dass der Agent sich zwischen Runs an etwas erinnert. Der Zustand liegt in der Session und im Checkpoint und wird bei jedem Resume erneut vom Agent eingelesen.

Jedes Tool mit Side Effects benötigt einen aus Session ID und Tool-Call-ID abgeleiteten Idempotency Key, der vor dem Auslösen des Side Effects gespeichert wird. send_email(session_id, tool_call_id, message_hash). create_pr(session_id, tool_call_id, branch_name). charge_customer(session_id, tool_call_id, invoice_id). At-least-once Execution ist in Queues und Workflow Engines der Standard, daher wird die Duplikation auftreten. Wenn ein Tool bei wiederholter Ausführung realen Schaden verursachen kann und Sie es nicht über einen Key deduplizieren können, ist das Tool noch nicht für Agents bereit.

Die Evaluation sollte auch Evidenz außerhalb des erzeugenden Contexts einbeziehen. Ein Evaluator mit frischem Context reduziert den Bias durch gemeinsam genutzten Context, während Tests, Lints, Browser-Checks und Schema-Validierung deterministische Evidenz liefern. Die Prüfung kann pass, fail oder needs_human zurückgeben. Bei Code Agents kann der Reviewer eine andere Model-Session mit Read-only-Tools sein. Bei Data- und Report-Agents sollten Sie deterministische Validierung mit einem Reviewer-Model kombinieren, wenn weiterhin menschliches oder modellbasiertes Urteil erforderlich ist.

Elf Deployment-Muster für AI Agents und was zwischen ihnen entscheidet

Sobald die fünf Primitives benannt sind, stellt sich die Frage, welche Deployment-Form sie ausführt. Mit „Form“ meine ich eine Anordnung dieser Primitives: wo das Harness liegt, wo der Zustand persistiert wird und welche Art von Sandbox die Arbeit ausführt. Eine Form ist eine Wiring-Entscheidung, keine Vendor-Auswahl. Das folgende Diagramm zeigt, bei welcher Run-Länge sich die jeweilige Form bewährt. Im anschließenden Text wird erläutert, was zwischen ihnen entscheidet.

Wenn Sie nur eines der elf lesen, lesen Sie Form 2: Queue + Worker + Checkpoint-DB. Das ist die Standardempfehlung für die meisten Teams, die im Referenz-Repository verwendete Form und das Grundgerüst, von dem die meisten anderen Formen abweichen: Queue → Worker → persistenter State, wobei Sandbox-Quelle, Harness-Verantwortlicher oder State Engine ausgetauscht werden. Wenn Sie zuerst Form 2 lesen, lässt sich der Rest schneller überfliegen.

Das Diagramm vergleicht die Formen nach Run-Länge. Die folgende Matrix vergleicht sie nach Ownership: Sie zeigt, wo jedes der fünf Primitives physisch angesiedelt ist. Grüne Zellen markieren, dass die Form das Primitive bereitstellt, graue Zellen, dass Sie es selbst anbinden müssen, und rote Zellen, dass die Form dieses Primitive überhaupt nicht hosten kann.

1. SDK in einem App Server (synchron, auf den Request begrenzt)

Die ursprüngliche Form. Das Agent SDK läuft innerhalb eines Request Handlers. Geeignet für Tasks unter 30 Sekunden, Demos und interne Tools. Ungeeignet für alles, bei dem sich ein HTTP-Client trennen könnte. Das HTTP-Timeout von Cloud Run ist auf maximal 60 Minuten begrenzt, und jede Panic im Web-Tier beendet den Run. Das SDK ist das Harness, der Web-Prozess fungiert zugleich als Sandbox, und der State liegt normalerweise im Prozessspeicher, sofern Sie ihn nicht explizit an anderer Stelle persistieren. Verwenden Sie diese Form nicht für mehrstündige Workloads.

2. Queue + Worker + Checkpoint-DB

Die Standardempfehlung für die meisten Teams und die in market-analyst-agent verwendete Production-Form: ein Python-Worker mit PostgreSQL Checkpointer, Redis Streams (oder RabbitMQ) für die eingehende Queue sowie ein MCP-Sidecar für Tools. Geeignet für Runs von 10 Minuten bis zu mehreren Stunden mit idempotenten Steps. Der lokale Runner kann die Queue in der synchronen Entwicklung umgehen; sobald Sie jedoch asynchrone Submission und Backpressure benötigen, gehört die Queue zur Production-Form.

Die App nimmt einen Request entgegen, erstellt eine Session-Zeile, stellt einen Job in die Queue und gibt eine Run-ID zurück. Der Worker holt den Job ab, führt das Harness aus, schreibt Checkpoints, streamt den Status und speichert die Artefakte während der Ausführung. Postgres bleibt erhalten, Worker sind austauschbar, und die Queue-Tiefe liefert Backpressure. Spot-/Preemptible-Compute funktioniert, solange der Checkpointer das Schreiben auf die Festplatte abschließt, bevor er Erfolg meldet.

In dieser Form ist der Worker das Harness. Sein Container und der Workspace pro Thread bilden eine Execution Boundary; nicht vertrauenswürdiger Code benötigt jedoch weiterhin eine gehärtete Sandbox oder VM. Postgres verwaltet Session- und Checkpoint-State. Traces laufen über OpenTelemetry in den von Ihnen betriebenen Observability-Stack.

3. Durables Workflow Engine (Temporal-Style)

Der Orchestration-Code des AI Agents läuft innerhalb eines Temporal Workflows; Model Calls und Tool Calls laufen als Activities. Der Workflow-Zustand liegt in einem von Cassandra, MySQL oder Postgres unterstützten Event-History-Log, sodass sich der Zustand über Deployments hinweg sauber re-playen lässt. Die Temporal × OpenAI Agents SDK Integration, die seit März 2026 allgemein verfügbar ist, liefert einen OpenAIAgentsPlugin und einen activity_as_tool Helper. Der Beitrag zu agentic sandboxes beschreibt außerdem, wie ein laufender Agent mitten in einer Konversation auf einen anderen Sandbox-Provider geforkt werden kann. Inaktive Workflows verbrauchen keinerlei Compute-Ressourcen. Die Einschränkungen sind real: Realtime Agents werden nicht unterstützt, und Streaming ist weiterhin als experimentell gekennzeichnet. Außerdem sind LocalShellTool und ComputerTool deaktiviert, weil sie nicht zu einem verteilten Modell passen.

Verwende dieses Muster, wenn der Run echte Wartepunkte enthält: menschliche Freigaben, externe Callbacks, lange Sleeps, Retries mit Business-Regeln oder Deployment-Fenster. Eine menschliche Freigabe wird zu einem dauerhaften Sleep, der keine Compute-Ressourcen verbraucht – nicht zu einer Polling-Schleife, die genau das tut.

Der Workflow-Code ist das Harness. Die Sandbox liegt normalerweise außerhalb von Temporal und wird aus Activities heraus aufgerufen. Session- und Checkpoint-Zustand gehen im Event-History-Log von Temporal auf, während die Trace-Sichtbarkeit über die Temporal UI sowie OpenTelemetry-Spans für jede Activity entsteht.

5. Anthropic Managed Agents (gehostetes Harness)

Anthropic hat Managed Agents am 8. April 2026 als öffentliche Beta hinter dem managed-agents-2026-04-01-Beta-Header gestartet. Der Service stellt eine gehostete Session, ein Harness, eine Sandbox und einen Vault-gestützten MCP-Proxy bereit. wake(sessionId) kann das Harness auf einem neuen Worker initialisieren, ohne den persistenten Session State zu verlieren.

Anthropic berechnet Managed Agents zu den Standard-Tokenpreisen zuzüglich $0.08 pro Session-Stunde. Die Abrechnung erfolgt auf Millisekundenbasis und gilt nur, solange der Session-Status „running“ lautet; Leerlaufzeit ist kostenlos. Eine außer Kontrolle geratene Retry-Schleife verursacht daher zusätzlich zu den Tokenkosten Session-Stundenkosten.

Beachte die Einschränkungen. Der Rabatt der Batch API gilt nicht („Sessions sind zustandsbehaftet und interaktiv. Es gibt keinen Batch-Modus.“). Managed Agents ist weder über AWS Bedrock noch über Google Vertex AI verfügbar. Innerhalb der Beta stehen MCP-Tunnel und das „Träumen“ von Agents hinter einer weiteren Research Preview, für die du Zugriff beantragen musst; Multi-Agent Coordination und rubric-basierte Self-Evaluation sind dokumentierte Bestandteile der Beta. Der Lock-in ist hoch: Du tauschst die Freiheit beim Harness dagegen ein, die Schleife nicht selbst betreiben zu müssen.

Anthropic hostet alle fünf Primitives: Session, Harness, Sandbox, Checkpoint und Trace. Du übergibst den Runtime und erhältst die Outputs.

6. LangChain Deep Agents Deploy (verwaltetes offenes Harness)

deepagents deploy verpackt einen deepagents.toml in ein LangSmith Deployment mit Durable Execution, Memory, Multi-Tenancy, Human-in-the-Loop, Observability, sandboxed Code Execution und geplanten Runs. Cloud-, hybride und selbst gehostete Deployment-Modi werden unterstützt. Sandbox-Provider (LangSmith Sandboxes, Daytona, Modal, Runloop oder eigene Provider) lassen sich über einen einzigen Config-Wert austauschen. Der State liegt in einem virtuellen Dateisystem mit austauschbaren Backends; die Memory ist auf User, Assistant oder beide begrenzt. Der Lock-in ist geringer als bei Managed Agents: Das Harness steht unter der MIT-Lizenz, die Instructions verwenden den offenen AGENTS.md-Standard, und Agents werden über MCP, das A2A-Protokoll (Agent2Agent) und das Agent Protocol bereitgestellt. Siehe LangChains runtime-behind-production-deep-agents-Beitrag.

Standardmäßig werden alle fünf Primitives gehostet, aber jedes davon lässt sich per Config austauschen. Die Sandbox wird über einen einzigen Config-Wert ausgewählt. Session und Checkpoint liegen in einem virtuellen Dateisystem mit austauschbaren Backends. Der Trace geht an LangSmith.

7. Google Cloud Run Service oder Job

Cloud Run bietet zwei unterschiedliche Runtime-Modi. Welcher davon passt, hängt davon ab, wie der Agent aufgerufen wird. Services sind an HTTP gebunden und skalieren zwischen Requests auf null herunter; das Harness läuft als Request Handler und gibt die Antwort zurück, sobald der Run beendet ist. Jobs laufen ohne HTTP-Entrypoint bis zum Abschluss; das Harness läuft als einmaliger Worker und beendet sich, sobald die Aufgabe abgeschlossen ist. Beide können das Harness hosten, aber keiner von beiden hält State über mehrere Runs hinweg. Sessions und Checkpoints müssen in Postgres, Spanner oder einem vergleichbaren externen Store liegen.

Die harten Limits unterscheiden sich deutlich. Das Timeout für Service-Requests bei Cloud Run beträgt standardmäßig 300 s, maximal jedoch 3.600 s (60 Min.). Für WebSockets gilt dasselbe Timeout. Bei Cloud Run Jobs beträgt es standardmäßig 10 Min. pro Task, maximal 168 Std. (7 Tage); für Tasks mit GPUs gilt ein Maximum von 1 Stunde. Services skalieren auf null, sofern Sie keine dauerhaft aktive CPU aktivieren; Jobs bieten kein HTTP und skalieren nicht automatisch.

Verwenden Sie einen Service für synchrone Ausführungen bis zu 60 Minuten. Verwenden Sie einen Job für längere einmalige oder asynchrone Workloads. Cloud Run Jobs können einen Task tagelang am Leben halten, bieten aber kein dauerhaftes Replay über Deployments, Versionsänderungen oder den Austausch von Workern hinweg. Für Laufzeiten von mehr als 7 Tagen sollten Sie Cloud Run nicht verwenden.

Cloud Run hostet das Harness. Session- und Checkpoint-Zustand liegen in Postgres, Spanner oder einem anderen externen Store; Traces können über Cloud Logging und OpenTelemetry laufen. Der Service-Container ist eine Ausführungsumgebung. Wenn der Agent nicht vertrauenswürdigen Code ausführt, sollten Sie zusätzlich einen separaten Sandbox einsetzen.

8. AWS Lambda (warum es das falsche Tool ist)

Das maximale Function-Timeout von Lambda beträgt strikt 900 s (15 Minuten). Wenn API Gateway der Function vorgeschaltet ist, hängt das Integrationslimit vom API-Typ ab. HTTP APIs erlauben 30 Sekunden; bei REST-Integrationen beträgt der Standardwert 29 Sekunden, während regionale und private REST APIs ein längeres Timeout konfigurieren können. Keine dieser Varianten macht Lambda zu einem Worker für mehrstündige Ausführungen. Ein langlebiges Harness benötigt weiterhin externen Zustand und erneute Invocations, wodurch wieder die Struktur aus Queue und Worker entsteht. Verwenden Sie Lambda für begrenzte Tool Calls, etwa zum Abrufen von Dateien oder für S3-Uploads, die von einer länger laufenden Orchestration aufgerufen werden. Platzieren Sie die Orchestration nicht dort.

Lambda kann höchstens einen Tool Call innerhalb seines 15-Minuten-Limits ausführen. Harness, Session, Checkpoint, Sandbox und Trace müssen an anderer Stelle liegen.

9. AWS ECS / Fargate: ein Task pro Run

Fargate dokumentiert im Gegensatz zu Lambda kein hartes Limit für die Laufzeit eines Tasks. Die Fargate-Throttling-Quotas erlauben einen Launch Burst von 100 und eine Auffüllrate von 20 pro Sekunde, mit separaten Budgets für On-Demand und Spot. Die ECS-Service-Quotas begrenzen Services mit AWS-Cloud-Map-Discovery auf 1.000 Tasks pro Service und EC2-basierte Cluster auf 5.000 Container-Instanzen.

Fargate erfordert den awsvpc-Modus, sodass jeder Task ein Network Interface und eine private IP erhält. Diese Struktur eignet sich für den Zugriff auf Daten innerhalb einer VPC. Fargate Spot erhöht das Unterbrechungsrisiko. Für die Dauerhaftigkeit sind weiterhin Sie verantwortlich, da die Plattform kein Replay im Stil von Temporal bietet.

Fargate hostet das Harness und weist jedem Run einen eigenen Task zu. Dadurch werden Workspaces und Task-Credentials voneinander getrennt; allein ist dies jedoch keine vollständige Sandbox für nicht vertrauenswürdigen Code. Session, Checkpoint und Trace werden an externe Services wie RDS oder DynamoDB sowie an CloudWatch/X-Ray gesendet.

10. Kubernetes-Job oder Namespace pro Session

Geeignet, wenn Sie bereits Kubernetes betreiben und pro Session eine Sandbox mit Cluster-weiten Controls benötigen. Ungeeignet, wenn Sie einen Start im Subsekundenbereich brauchen, da das Abrufen des Container-Images und die Initialisierung des Pods bei einem Cold Start zu lange dauern. Das Muster besteht aus einem Job pro Agent-Run, mit activeDeadlineSeconds, einer PersistentVolumeClaim für den Workspace und einem Sidecar für den MCP-Server. Die Crash-Recovery müssen Sie selbst implementieren. Kubernetes nur für das Hosten von Agents einzuführen, ist angesichts des Konfigurationsaufwands und der operativen Belastung teuer. Es lohnt sich nur, wenn Sie K8s bereits aus anderen Gründen betreiben.

Kubernetes hostet das Harness und die Ausführungsumgebung pro Run, üblicherweise als ein Job und manchmal mit einem dedizierten Namespace. Eine starke Isolation hängt weiterhin von Runtime Class, Network Policy, Pod Security sowie der zugrunde liegenden Container- oder VM-Grenze ab. Session- und Checkpoint-Status werden in einer externen Datenbank oder auf einer PersistentVolumeClaim gespeichert.

11. Lokales Docker Compose (nur für die Entwicklung)

Die Referenz für den nächsten Abschnitt. Der Zweck dieses Aufbaus besteht darin, die Production-Topologie eins zu eins abzubilden (dieselben Primitives, dieselbe Netzwerkstruktur), während alles auf einer einzigen Maschine läuft. Nicht abgebildet wird die Isolation: ein gemeinsam genutzter Workspace-Mount, ein Postgres, keine gehärtete Sandbox und keine getrennten Failure Domains zwischen Worker und dessen Status. Nichts, was so aufgebaut ist, sollte ausgeliefert werden.

Compose bildet Shape #2 auf einem einzelnen Host ab. Postgres speichert Session- und Checkpoint-Status, und der Worker-Container ist das Harness. Der gemeinsam genutzte Workspace-Mount ist für die Entwicklung praktisch, isoliert jedoch keine nicht vertrauenswürdigen Runs. Der optionale OpenTelemetry-Stack zeichnet Traces auf.

Referenz-Stack: Docker Compose

Die Referenz-Topologie, die in slavadubrov/market-analyst-agent verwendet wird, besteht aus einem LangGraph-Worker, einem Postgres-Checkpointer, Qdrant für Retrieval, einem MCP-Sidecar, einer Redis-Queue für asynchrone, produktionsähnliche Runs sowie einem optionalen Prometheus / Grafana / Loki / Tempo / OTel-Observability-Stack. In lokalem Compose ist Redis nur deshalb optional, weil der synchrone Runner den Worker direkt aufrufen kann. docker compose up startet die Kern-Topologie lokal; der MCP-Sidecar und der Observability-Stack sind Opt-in-Profile (--profile mcp, --profile observability).

Der einzige Teil, dessen Inline-Darstellung sich lohnt, ist die kanonische LangGraph-Verdrahtung. Es handelt sich um einen illustrativen Ausschnitt, nicht um ein in einem Repository ausführbares Beispiel. Für die Ausführung benötigen Sie langgraph, langgraph-checkpoint-postgres und psycopg[binary,pool], eine erreichbare PostgreSQL-Datenbank mit Berechtigung zum Erstellen der Checkpointer-Tabellen, POSTGRES_PASSWORD sowie ein zuvor erstelltes StateGraph in builder; siehe LangGraphs Einrichtung des Postgres-Checkpointers.

Observability, die den Run überdauert

Kurze Request-Handler sind leicht zu debuggen: Wenn etwas fehlschlägt, liest man die Response und das Live-Log. Lang laufende Agents haben diesen Luxus nicht. Wenn ein sechs Stunden dauernder Run fehlschlägt, liegt das relevante Ereignis fünf Stunden zurück, die Ausgabe im Live-Terminal ist verschwunden, und der Worker, der sie erzeugt hat, wurde ersetzt. Niemand wird den Run aus dem Gedächtnis rekonstruieren. Deshalb debuggt man anhand persistenter Artefakte, die geschrieben wurden, während der Run noch lief.

Production-Stacks decken typischerweise vier Arten von Artefakten ab, aufgeteilt in zwei Gruppen. Zwei davon liest man nach Ende des Runs – für Postmortems und Replay: ein abfragbares Event-Log jedes einzelnen Schritts und OpenTelemetry-Traces darüber, wohin Zeit und Tokens geflossen sind. Zwei liest man während des Runs. Das eine ist ein Live-Tail dessen, was der Agent im Workspace erzeugt. Das andere ist ein Observability-Stack pro Worktree, den der Agent selbst abfragen kann, während er noch arbeitet.

Strukturiertes Event-Log (nach dem Run lesen)

Jeder Model Call, Tool Call, jedes Ergebnis, jeder Fehler und jede Freigabe wird anhand von Session-ID und Zeitstempel in persistentem Storage gespeichert. Nach Ende des Runs fragt man die Daten wie eine normale Datenbanktabelle ab. Addy Osmani formuliert den Maßstab in Long-running Agents klar: „Wenn du nicht aus persistentem Storage rekonstruieren kannst, was der Agent in den letzten 24 Stunden getan hat, hast du kein Long-running Agent, sondern ein lang laufendes Shell-Script, das zufällig ein LLM aufruft.“

OpenTelemetry-GenAI-Traces (nach dem Run lesen)

Dieselbe Art schrittweiser Daten wird als Spans mit den Standardattributen aus den gen_ai.* Semantic Conventions ausgegeben: Model-Name, Provider, Anzahl der Input- und Output-Tokens, Conversation-ID und Workflow-Name. Die Conventions befinden sich weiterhin im Stability-Level Development.

Im Jahr 2026 wurden sie aus OpenTelemetrys zentralem Repository für Semantic Conventions in ein eigenes Repository für GenAI Semantic Conventions verschoben. Die Attributnamen können zur Instrumentierung verwendet werden. Statt einer Versionsnummer des Main-Repositories sollte jedoch die Revision festgeschrieben werden, gegen die validiert wurde. Provider-spezifische Felder liegen in Subnamespaces (anthropic.*, openai.*), die über gen_ai.provider.name ausgewählt werden. Der Grund für den Standard ist Portabilität: Bei OTLP-kompatiblen Zielen, die diese Conventions unterstützen, ist beim Wechsel des Backends möglicherweise keine erneute Instrumentierung des Codes erforderlich. Backend-Adapter oder zielspezifische Konfiguration können jedoch weiterhin nötig sein.

Tool-Call-Timeline plus Workspace-Diffs (während des Runs lesen)

Der schnellste Weg, zu erkennen, was ein Agent gerade tut, besteht darin, die von ihm im Workspace erzeugten Änderungen zu verfolgen, statt ein Session-Log zu durchsuchen. Anthropic liefert dafür im Quick Start von Harness Primitives for Long-Running Claude Agents eine Watch Loop mit zwei Ansichten: watch -n 5 'git log --oneline -8' zeigt die neuesten Commits des Agents, und watch -n 5 'find screenshots -name "*.png" | tail -5' zeigt die neuesten Screenshots, die er aufgenommen hat. Zwei Terminal-Ansichten, die sich alle fünf Sekunden aktualisieren, reichen aus, um zu erkennen, ob ein Run echten Fortschritt macht oder sich im Kreis dreht.

Ephemeraler Stack pro Worktree (vom Agent selbst während des Runs gelesen)

Laut OpenAIs Harness-Post gilt: „Logs, Metriken und Traces werden Codex über einen lokalen Observability-Stack bereitgestellt, der für ein bestimmtes Worktree ephemeral ist.“ Jedes Agent-Worktree erhält ein eigenes, kurzlebiges Loki + Prometheus + Tempo, das ausschließlich auf diesen Run begrenzt ist. Der Agent fragt diese Systeme während seiner Arbeit ab. Dadurch kann eine Anweisung wie „Kein Span in diesen vier User Journeys darf zwei Sekunden überschreiten“ direkt vom Agent überprüft werden, statt dass er dies schätzen muss.

(Der Evaluator mit frischem Context aus der Tabelle der Failure Modes liest diese Artefakte, um zu entscheiden, ob der Run „done“ ist. Er gehört zur Evaluation, nicht zur Observability; siehe § Lifecycle eines gesunden Runs. Er hängt von jeder der oben genannten Oberflächen ab.)

Ein minimaler selbst gehosteter Observability-Stack

Für etwas wie market-analyst-agent:

  1. OpenTelemetry Collector mit dem GenAI Normalizer Processor (contrib, alpha) für unterstützte GenAI-Attribute. Verwende die generischen Attributes- oder Transform-Prozessoren, um gen_ai.*-Felder zu filtern oder umzuschreiben.
  2. Tempo (oder Jaeger) für Traces, nach gen_ai.conversation.id / thread_id gruppiert.
  3. Loki für strukturierte Event-Log-Einträge.
  4. Prometheus für gen_ai.client.token.usage, gen_ai.client.operation.duration und gen_ai.client.operation.time_to_first_chunk — die gen_ai.server.*-Metriken stammen vom Model Server, daher erhältst du sie nur, wenn du die Weights selbst hostest (siehe die GenAI Metrics Conventions).
  5. Grafana-Dashboards, gruppiert nach gen_ai.agent.name und gen_ai.request.model.

Gehostete Alternativen (wähle eine, nicht drei):

  • LangSmith: native LangGraph-Integration; außerdem das Deployment-Ziel für Deep Agents Deploy.
  • Braintrust: die beste Wahl, wenn Eval-first-Regression-Suites Priorität haben.

Das Debug-Bundle-Muster

Wenn ein Run fehlschlägt, sollte der Worker /workspaces/${THREAD_ID}/_debug/ ablegen, das die Artefakte enthält, die du in einem Postmortem anfordern würdest:

  • session.jsonl: vollständiger Event-Log-Dump aus dem PostgresSaver (checkpointer.list({"configurable": {"thread_id": ...}})).
  • last_state.json: StateSnapshot.values aus dem letzten erfolgreichen Super-Step.
  • trace.json: für den Lauf exportierte OTLP-Spans.
  • tool_calls.csv: (ts, tool, input_hash, latency_ms, status, error).
  • workspace.tar.zst: das Workspace-Verzeichnis sowie git diff gegen den Initializer-Commit.
  • screenshots/*.png: was der Agent gesehen hat.
  • PROGRESS.md, feature-list.json und alle anderen vom Agent verfassten Progress-Dateien.
  • env.txt: Image-Tags, Model-Version, Harness-Commit-SHA.

Dieses Bundle liefert einem Menschen oder Reviewer-Agent genügend Belege, um den Fehler zu rekonstruieren. „Der Agent ist stecken geblieben“ ist vage. Ein beispielhafter Bericht ist konkret: Session s_123 verbrauchte 71 Prozent ihrer Tokens damit, drei Commands zu wiederholen, nachdem npm install fehlgeschlagen war.

Die passende Form auswählen: ein Entscheidungsleitfaden

Der Großteil des obigen Vergleichs lässt sich auf eine Handvoll Entscheidungen reduzieren.

Mit der Laufzeit beginnen

Verwenden Sie die Laufzeit als ersten Filter:

  • Unter 30 Sekunden, idempotent: SDK für den Request-Lifecycle in einem App-Server.
  • 30 Sekunden bis 60 Minuten: Queue + Worker + Checkpoint-DB.
  • 60 Minuten bis 24 Stunden: dieselbe Queue + Worker oder ein Cloud Run Job für einmalige Aufgaben. Verwenden Sie eine Durable Workflow Engine, wenn Sie zusätzlich Versionierung und Replay benötigen.
  • Mehr als 24 Stunden, Deployments müssen überstanden werden: Durable Workflow Engine (Temporal-ähnlich). Cloud Run Jobs können lange Aufgaben bis zum Task-Limit halten, bieten aber keine Replay-Semantik.
  • Multi-Day Reinforcement-Learning-Training-Loops: K8s Job + Volume + Temporal.

Prüfen Sie anschließend Side Effects, Recovery, Replay, Isolation, Datenstandort und das Team, das das System betreiben wird.

Plattform-Fit nach Anwendungsfall

Die Matrix ist umfangreich, und keine einzelne grüne Zelle entscheidet über die Architektur; ausschlaggebend sind meist die gelben Zellen, bei denen eine Plattform etwas nur mit Einschränkungen unterstützt. Eine breite Abdeckung von Workloads ist nützlich, zeigt aber weder Data Residency noch Replay-Semantik, Provider-Abhängigkeit, operative Reife oder die Kosten einer späteren Verlagerung des States.

Deep Agents Deploy ist die einzige Spalte der Matrix ohne rote oder gelbe Zelle: kurze synchrone Läufe, Batch-Verarbeitung über mehrere Stunden, Sandbox-Forking, GPU-Arbeit und der geringste Lock-in sind durchgehend grün. Das macht die Plattform zu einem Kandidaten, wenn eine Plattform alle Ihre Workloads bedienen muss. Diese Breite geht mit einer kürzeren Production-Historie als bei einem Queue- + Worker- + Postgres-Stack einher. Betrachten Sie die grünen Zellen als Capability Claims, die validiert werden müssen, und vergleichen Sie anschließend die operativen Einschränkungen, die die Matrix nicht abbilden kann.

Anthropic Managed Agents passt entweder vollständig zu Ihrem Workload oder überhaupt nicht. Das Produkt hat zwei harte Einschränkungen: Es ist ausschließlich Hosted und ausschließlich für Claude verfügbar. Wenn Ihr Workload beide Bedingungen erfüllt — Claude ist bereits das gewünschte Model, und Sie möchten ein Harness lieber nicht selbst betreiben —, ist Managed Agents sehr gut geeignet. Ein interner Coding-Agent, der in Bursts von zwei bis sechs Stunden läuft, entspricht am ehesten der passenden Form und nimmt Ihrem Team einen großen Teil der Plattformarbeit ab. Wenn eine der beiden Bedingungen nicht erfüllt ist, weil Sie ein Nicht-Claude-Model oder Self-Hosted-Compliance benötigen, passt Managed Agents nicht. Das lässt sich durch keine Konfigurationsänderung beheben.

Gehostetes Harness vs. eigenes Harness

Hier geht es darum, wer das Harness betreibt – nicht darum, wer den Code dafür geschrieben hat. Gehostet bedeutet, dass der Anbieter die Harness-Schleife in seiner Infrastruktur ausführt und Sie eine API aufrufen. Eigenbetrieben bedeutet, dass Sie die Schleife auf Ihrer eigenen Infrastruktur ausführen, selbst wenn der Harness-Code von einem Anbieter stammt.

LangChain ist auf beiden Seiten dieser Grenze vertreten, was häufig für Verwirrung sorgt. Das Unternehmen stellt LangGraph bereit, eine MIT-lizenzierte Library, die Sie selbst hosten (eigenbetrieben), und Deep Agents Deploy, ein Managed Product, das im standardmäßigen Cloud-Modus ein Deep-Agents-Harness auf LangSmith Deployment ausführt (gehostet). Dasselbe Unternehmen, zwei unterschiedliche Betriebsmodelle. Sie entscheiden, wer die Schleife ausführt – nicht, wessen Logo auf der Library steht. (Deep Agents Deploy verfügt außerdem über einen Self-Hosted-Modus für Teams, die die Ergonomie des Harness ohne die Cloud-Komponente nutzen möchten; dieser Modus fällt in die Kategorie „eigenbetrieben“.)

Wählen Sie ein gehostetes Harness, wenn dessen Model-Support, Data Boundary, Recovery-Verhalten und Extension Points bereits zu Ihren Anforderungen passen. Entscheiden Sie sich für ein eigenes Harness, wenn diese Einschränkungen Anforderungen betreffen, von denen Sie erwarten, dass sie sich ändern. Eine Migration zwischen beiden verändert State, Observability und Execution Boundaries. Testen Sie daher den Exit-Pfad, bevor Produktionsdaten davon abhängen.

Gehostete Sandbox vs. eigene Execution Environment

Wählen Sie eine gehostete Sandbox, wenn Isolation, Pause-/Resume- oder Fork-Semantik des Anbieters zu Ihrem Threat Model und Ihrem Startup-Budget passen. Docker oder Fargate kann für vertrauenswürdige interne Workloads geeignet sein, die VPC-Zugriff oder strikte Data Residency benötigen. Ein Standard-Container stellt jedoch keine ausreichende Boundary für nicht vertrauenswürdigen Code dar. Teil 4 beschreibt für diesen Fall die verfügbaren Isolationsoptionen.

State Stores: Git, DB und Object Storage im Vergleich

Long-Running Agents verwenden in der Regel drei State Stores gleichzeitig, weil jeder Store für ein anderes Artefakt zuständig ist.

Git speichert den Workspace State: den Code, die Dokumente und die Fortschrittsdateien, die der Agent verändert. Jeder Commit gibt dem Harness einen stabilen Recovery Point und der nächsten Session eine kompakte Historie.

Die Checkpoint-Datenbank speichert den Graph State: was entschieden wurde, welche Nodes ausgeführt wurden, welche Results zurückkamen und was als Nächstes ausgeführt werden soll. Der Artifact Store enthält große finale Outputs wie PDFs, Parquet-Dateien und Screenshots. Diese Artefakte gehören weder in Git noch in die Checkpoint-Datenbank.

Wann Sie Git als State verwenden sollten

Verwenden Sie Git, wenn der Workload codeförmig ist (Multi-File-Edits, Refactorings, App-Generierung) oder ausreichend dokumentförmig, sodass die Dateihistorie relevant ist. Das Muster ist einfach: Erstellen Sie einen Run-Branch, legen Sie einen Initializer-Commit an und committen Sie anschließend an sinnvollen Grenzen: nach dem Setup, nach jedem Feature, nach erfolgreichen Tests und nach dem finalen Cleanup. Speichern Sie die SHA des neuesten Workspace-Commits neben der Checkpoint-Zeile. Beim Resume checkt der nächste Worker den Branch aus, liest git log --oneline -8, untersucht git status und den neuesten Diff und liest anschließend PROGRESS.md oder die Handoff-Datei, die die vorherige Session geschrieben hat.

Damit wird Git zu einer Recovery-Oberfläche für das gerade bearbeitete Artefakt – nicht zu einem Ersatz für die Checkpoint-Datenbank. Git kann zwei Fragen beantworten: Was hat sich geändert, und welche Version hat die Tests bestanden? Git kann dem Harness jedoch nicht mitteilen, welcher Graph-Knoten als Nächstes ausgeführt werden soll, welcher Tool Call auf eine Genehmigung wartet oder welcher Retry seinen Idempotency Key bereits verwendet hat. Anthropic setzt in seinem Harness Initializer-Commits und Commits pro Feature als maßgebliche Quelle für die Workspace-Recovery ein; das Model liest git log --oneline -8, um den Zustand wiederherzustellen. Überspringe Git, wenn das Arbeitsergebnis aus einer einzelnen konversationellen Antwort besteht. Der zusätzliche Aufwand lohnt sich dann nicht.

Wann DB-Checkpointing verwendet werden sollte

Verwende Checkpointing im Stil von PostgresSaver, wenn der Agent eine Graph-Struktur mit mehreren Knoten besitzt, deren Zwischenzustand relevant ist (Planner → Researcher → Writer → Verifier). Das Referenz-Repository verwendet dies genau aus diesem Grund. Lege keine Workspace-Artefakte im Terabyte-Bereich in den Checkpoint; diese gehören in den Object Storage.

Wann ein Artifact Store (S3 / GCS) verwendet werden sollte

Verwende Object Storage, wenn:

  • die Ausgabe größer ist, als die Checkpoint-Datenbank sinnvoll speichern sollte;
  • nachgelagerte Consumer ein per URL adressierbares Artefakt benötigen, ohne den Agent zu durchlaufen; oder
  • für das Deliverable und den Run State unterschiedliche Aufbewahrungsfristen gelten.

Beispielsweise könntest du das Session Log nach 30 Tagen löschen, den finalen Report aber jahrelang aufbewahren. Strukturiere die Ablage anhand von (thread_id, checkpoint_id, artifact_name), damit der erzeugende Run rekonstruierbar bleibt.

Wann Human-Approval-Gates hinzugefügt werden sollten

Füge Gates hinzu, wenn der Tool Call destruktiv und irreversibel ist (DB-Schreibvorgänge, Geldtransfers, das Versenden externer Kommunikation), wenn der Tool Call den Blast Radius des Agents verlässt (Production-Deployments, Veröffentlichungen für Kunden) oder wenn Regulatoren eine Prüfung verlangen. Sowohl LangGraphs interrupt() als auch die Approval Middleware von Deep Agents unterstützen diese Gates direkt. Teil 4 hat erläutert, warum diese Gates eine Berechtigungsfrage und keine Prompt-Frage sind.

Eine praxisnahe Production-Checkliste

Bevor ein Long-Running Agent in die Produktion geht, beantworte diese Fragen in konkreten Infrastrukturbegriffen.

  1. Welcher Store verwaltet Session Events und Checkpoints?
  2. Was passiert, wenn der Worker während eines Tool Calls abstürzt?
  3. Kann ein Run den Workspace eines anderen Runs beschädigen?
  4. Welche Aktionen erfordern eine Genehmigung?
  5. Können das Model oder die Sandbox rohe Credentials lesen?
  6. Welche Tool Calls können sicher erneut ausgeführt werden?
  7. Wo wird das Cost Cap pro Run durchgesetzt?
  8. Welcher Evaluator mit frischem Context entscheidet, dass der Run „fertig“ ist?
  9. Wo liegen die finalen Ausgaben, nachdem die Sandbox gelöscht wurde?
  10. Können wir morgen einen fehlgeschlagenen Run erklären, ohne ihn erneut auszuführen?

Wenn die Antwort auf eine dieser Fragen lautet: „Der Prompt weist den Agent an, vorsichtig zu sein“, ist das System noch nicht deployed. Es ist weiterhin nur eine Demo.
