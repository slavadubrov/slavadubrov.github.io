Lang laufender AI Agent Runtime im Jahr 2026: Sessions, Sandboxes, Checkpoints und Harnesses

Teil 5 der Serie „Engineering the Agentic Stack“

Die vorherigen vier Beiträge behandelten das interne Design des Agents: Reasoning Loops, Memory, Tool Use und Security. Dieser Artikel behandelt den Runtime, der diese Komponenten über lange Sessions und Prozessausfälle hinweg funktionsfähig hält.

Ein Agent Run kann mehrere Stunden dauern, während sein Worker-Prozess jederzeit neu starten kann. Das Model wählt weiterhin die nächste Aktion, aber der Runtime muss den State erhalten, die Ausführung steuern und sich von einem Ausfall mitten in einem Tool Call erholen. Dieser Beitrag definiert die Runtime-Grenze. Teil 6 untersucht den Harness darin: die Feedback-, Retry-, Handoff- und Acceptance-Logik, die bestimmt, ob der Agent weiterarbeitet oder stoppt.

Was ist ein AI Agent Runtime?

Ein AI Agent Runtime ist die Infrastruktur-Schicht, die einen Tool-using Agent am Leben, isoliert, observierbar und nach Ende des Model Calls wiederaufnehmbar hält. Er verwaltet Session State, Tool-Ausführung, Checkpoints, Policy-Prüfungen, Secrets, Traces, Kostenlimits und die Deployment-Form. Das Model wählt die nächste Aktion; der Runtime entscheidet, wo diese Aktion ausgeführt wird, ob sie zulässig ist, wie sie aufgezeichnet wird und wie der Run nach einem Ausfall fortgesetzt wird.

Lange Runs brechen Annahmen über stateless Prozesse

Ein stateless Chat-Endpunkt kann den Request State in einem Prozess halten und ihn nach der Antwort verwerfen. Ein langer Agent Run erstreckt sich über Worker-Neustarts, Deployments, Context Resets und Approval-Pausen. Der Worker-Prozess kann daher nicht länger die einzige Quelle der Wahrheit sein.

Das OpenAI-Codex-Team berichtet in seinem Harness-Engineering-Beitrag über die Run-Dauer:

„Wir sehen regelmäßig einzelne Codex Runs, die mehr als sechs Stunden an einer einzigen Aufgabe arbeiten (oft, während die Menschen schlafen).“

Das Engineering-Team von Anthropic beschreibt das entsprechende State-Problem in Effective harnesses for long-running agents:

„Die zentrale Herausforderung lang laufender Agents besteht darin, dass sie in diskreten Sessions arbeiten müssen und jede neue Session ohne Erinnerung an das beginnt, was zuvor passiert ist.“

Beide Beobachtungen führen zum selben Runtime-Design: State außerhalb des Workers persistieren und Worker austauschbar machen.

Die Session muss außerhalb des Worker-Prozesses liegen. Ein Durable Store zeichnet Model Calls, Tool Results und Approvals auf, damit ein anderer Worker nach einem Crash am letzten sicheren Punkt fortsetzen kann. Checkpoints ermöglichen es dem Runtime außerdem, bei einem vollen Context Window eine neue Model Session zu starten, ohne die gesamte Historie erneut abzuspielen. In Anthropics Formulierung werden Harness-Instanzen damit wegwerfbar und neu startbar; der Durable State liegt an anderer Stelle.

Die fünf Runtime-Primitiven, die jeder lang laufende AI Agent benötigt

Anthropics Beitrag Scaling Managed Agents liefert eine nützliche Begrifflichkeit für fünf Runtime-Verantwortlichkeiten. Der Harness treibt den Agent voran, während die Session aufzeichnet, was er getan hat, und die Sandbox Commands ausführt. Der Checkpoint gibt dem nächsten Worker einen Resume-Punkt; der Trace bewahrt Belege für späteres Debugging. Eine Implementierung kann Komponenten zusammenlegen, aber Verantwortlichkeiten und Failure Boundaries müssen weiterhin benannt werden.

Session. Ein Append-only Log über alles, was passiert ist: Model Calls, Tool Calls, Results, Errors und Approvals. Recovery ist wake(sessionId) → getSession(id) → resume from last event. In LangGraph ist dies ein thread_id plus Postgres Checkpointer (siehe LangGraph Persistence). Das OpenAI Agents SDK enthält zehn integrierte Session-Backends, darunter SQLiteSession, RedisSession, SQLAlchemySession, MongoDBSession und EncryptedSession (siehe die Sessions-Dokumentation).

Harness. Der Orchestration Loop. Er ruft das Model auf, parst Tool Calls, führt sie aus, schreibt die Results zurück in die Session und wendet Retry-Regeln an. Anthropic formuliert es direkt:

„Jede Komponente in einem Harness kodiert eine Annahme darüber, was das Model nicht selbst leisten kann.“

Das Codex-Team von OpenAI bezeichnet dies als Harness Engineering: Software zu schreiben erfordert weiterhin Engineering-Aufwand, aber inzwischen fließt mehr davon in das Scaffolding als in den Code selbst. LangGraphs CompiledStateGraph, Deep Agents’ create_deep_agent und Claude Code selbst sind Harnesses in diesem Sinn.

Sandbox. Die isolierte Ausführungsumgebung, in der Commands tatsächlich laufen. Die Seite Sandbox concepts des OpenAI Agents SDK zieht die Grenze klar:

„Der äußere Runtime besitzt weiterhin Approvals, Tracing, Handoffs und Resume-Bookkeeping. Die Sandbox Session besitzt Commands, Dateiänderungen und Environment Isolation.“

Sandboxes unterscheiden sich darin, wie lange sie leben und was sie zwischen Runs speichern. Die einfachste Form ist fresh ephemeral: Für eine einzelne Aufgabe eine Sandbox starten, sie nach Abschluss zerstören und bei jedem Run die Cold-Start-Kosten zahlen.

Persistent paused-Sandboxes behalten das Filesystem und einen Memory Snapshot zwischen Runs. Beim nächsten Resume entfällt dadurch ein vollständiger Boot. Snapshot or fork erstellt aus einem vorbereiteten Parent ein Copy-on-Write-Image, sodass viele Aufgaben installierte Dependencies und warme Caches teilen können, ohne ihren beschreibbaren State zu teilen.

Per-Worktree-Sandboxes geben jeder Aufgabe ihren eigenen Workspace und Observability-Stack. Separate Logs, Metrics und Traces ermöglichen das Debugging eines Runs, ohne dass dessen State in einen anderen Run gelangt. Die Provider-Tabelle weiter unten vergleicht Cold-Start- und Persistence-Verhalten.

Checkpoint. Wiederaufnehmbarer State. LangGraphs PostgresSaver schreibt an jeder Super-Step-Grenze ein StateSnapshot, mit Per-Task-Writes nach checkpoint_writes, sodass erfolgreiche Node-Outputs bei einem Fehler eines Geschwisters nicht erneut berechnet werden. Der Snapshot ist ein JSON-serialisierbares Dict (v, ts, id, channel_values, channel_versions, versions_seen, pending_sends), dokumentiert auf der langgraph-checkpoint-postgres-PyPI-Seite und in der LangGraph-Checkpoints-Referenz.

Trace. Die Replay- und Debug-Oberfläche. Jeder Model Call, Tool Call und Sub-Agent-Schritt wird zu einem Span mit Timing, Inputs, Outputs, Token Counts und Kosten. Wenn ein sechsstündiger Run fehlschlägt, lesen Sie den Trace, um herauszufinden, was schiefgelaufen ist. Die Terminalausgabe des Runs ist zu diesem Zeitpunkt längst verschwunden. Die GenAI Semantic Conventions von OpenTelemetry standardisieren die Attributnamen (welches Model, welcher Provider, wie viele Tokens, welche Conversation, welcher Workflow), sodass derselbe Trace ohne erneute Instrumentierung sauber in Tempo, Jaeger, Honeycomb oder LangSmith dargestellt werden kann.

Policy und Secrets sind separate Runtime-Grenzen

Zwei Grenzen schneiden sich mit allen fünf Primitiven. Sie sind die Runtime-Version des Security-Arguments aus Teil 4.

Policy Engine

Vor jedem Tool Call läuft eine Permission-Prüfung, die entscheidet, ob er ausgeführt werden darf. In der Produktion sind zwei Muster verbreitet. Deep Agents lässt jeden Sub-Agent deklarieren, welche File Paths er lesen oder schreiben darf; die Middleware blockiert alles außerhalb dieser Deklaration. Anthropic Managed Agents leitet jeden Tool Call über einen MCP Proxy, sodass der Proxy die Permissions statt des Agent-Codes durchsetzt. Wenn ein sensibler Call menschliche Freigabe benötigt, pausieren LangGraphs interrupt() und der Approval Hook von Deep Agents den Graph, bis eine Person zustimmt.

Secret Broker

Das Model sollte keine langlebigen Secrets sehen, und in der Regel sollte dies auch für die Sandbox gelten. Das Managed-Agents-Muster ist das richtige Vorbild:

„Für Git verwenden wir das Access Token jedes Repositorys, um das Repository während der Sandbox-Initialisierung zu klonen und es in das lokale Git Remote einzubinden. Git push und pull funktionieren innerhalb der Sandbox, ohne dass der Agent das Token jemals selbst verarbeitet. Für Custom Tools unterstützen wir MCP und speichern OAuth-Tokens in einem sicheren Vault. Claude ruft MCP Tools über einen dedizierten Proxy auf; dieser Proxy erhält ein mit der Session verknüpftes Token. … Der Harness erhält niemals Kenntnis von Credentials.“

Im Referenz-Stack market-analyst-agent liest der MCP Sidecar OAuth-Tokens aus einem Docker Secret (in der Produktion HashiCorp Vault) und stellt dem LangGraph Worker nur die Tool-Oberfläche zur Verfügung. Der Worker sieht das Token nie. git push funktioniert. cat ~/.ssh/id_rsa nicht.

Ein praktischer Plausibilitätscheck besteht darin, jede Komponente und das von ihr implementierte der fünf Primitive aufzuschreiben. Postgres kann Session und Checkpoint abdecken. Der Worker-Container ist der Harness. Ein Service wie Daytona, Modal oder E2B stellt die Sandbox bereit, während Tempo oder LangSmith den Trace speichert.

Untersuchen Sie anschließend gekoppelte Ausfälle. Wenn zwei Primitive im selben Prozess leben, reißt ein Crash beide mit. Wenn sie ein Credential teilen, überschreitet ein Leak beide Grenzen. Häufige Beispiele sind ein Worker, der zugleich die Trace-Durability besitzt, oder ein Sidecar-Token, das zugleich die Checkpoint-Datenbank entsperrt.

Failure Modes von AI Agent Runtimes in der Produktion

Der Runtime verwaltet Retries, stellt frühere Arbeit wieder her, isoliert Workspaces und setzt Budgets durch. Wenn sich Runs über Worker und Context Windows erstrecken, verlagern sich die Fehler in Richtung State, duplizierter Side Effects, Sandbox Drift und Budget-Durchsetzung.

Die Fehler lassen sich in vier Gruppen einteilen:

  • Quality-of-Output-Fehler: Der Agent erklärt die Aufgabe für abgeschlossen, obwohl sie noch nicht erledigt ist, vergisst nach einem Context-Window-Reset, was er getan hat, oder vertraut seiner eigenen Self-Evaluation und liefert fehlerhaften Output aus.
  • Cost-Control-Fehler: Der Agent bleibt in einer Retry-Schleife hängen oder verbraucht ein Token- oder Tool-Call-Budget, ohne etwas Nützliches zu produzieren.
  • State- und Crash-Fehler: Workspaces driften auseinander, weil ein Run Dateien bearbeitet, die einem anderen Run gehören; Tool Calls werden durch Replays bei Retries mehrfach ausgeführt; oder Arbeit geht verloren, wenn ein Worker zwischen zwei Events stirbt.
  • Context-Window-Fehler: Das Model fasst zusammen und beendet den Run vorzeitig, weil es glaubt, der Platz werde knapp, obwohl das Window noch Kapazität hat.

Die Tabelle ordnet jedem Fehler eine Mitigation, den Runtime Hook, der sie durchsetzt, und die Grundlage der Empfehlung zu. Model-spezifisches Verhalten kann sich ändern. Behandeln Sie Vendor-Beobachtungen daher als Anlass, die Annahme erneut zu testen, nicht als dauerhafte Regeln.

Vercel über das verwandte Problem, dass zu viele Tools zu viele Annahmen kodieren, in We removed 80% of our agent’s tools:

„Wir haben den größten Teil gelöscht und den Agent auf ein einziges Tool reduziert: beliebige Bash-Commands ausführen. Wir nennen das einen File-System-Agent.“

Das von Vercel berichtete Ergebnis bei einer repräsentativen Query: Die Erfolgsrate stieg von 80 auf 100 Prozent, und der Worst Case sank von 724 s / 100 Steps / 145.463 Tokens (fehlgeschlagen) auf 141 s / 19 Steps / 67.483 Tokens (erfolgreich). Die Lehre lautet nicht „Löschen Sie Ihre Tools“. Sie lautet, dass jedes Primitiv in Ihrem Runtime, einschließlich der Tool-Oberfläche, eine begrenzte Lebensdauer hat. Testen Sie die Annahme erneut, wenn sich das Model ändert.

Die Lösung besteht darin, die 1M-Token-Beta zu aktivieren und die Nutzung auf 200k zu begrenzen, sodass das Model weiterhin glaubt, Headroom zu haben. Das Harness-Team von OpenAI fasst es in einem Satz zusammen: „Menschen steuern. Agents führen aus.“ Wenn etwas fehlschlägt, lautet die nützliche Frage, welche Capability fehlt und wie diese Capability für den Agent zugleich verständlich und durchsetzbar gemacht werden kann.

Der gesunde Run-Lifecycle

Ein gut funktionierender Run ist langweilig. Er besteht aus einer Kette kleiner, wiederherstellbarer Schritte, wobei jeder Schritt sein Ergebnis in Durable Storage schreibt, bevor der nächste beginnt.

Das Schreiben jedes Ergebnisses vor dem Start des nächsten Schritts begrenzt den Crash-Schaden. Ein Fehler verliert nur den gerade laufenden Schritt, und der nächste Worker setzt am letzten abgeschlossenen Schritt fort, statt den gesamten Request neu zu starten.

  1. Von einer neuen oder fortgesetzten Session booten. Beim Resume den Workspace aus seinem letzten bekannten State mounten, eventuell vom vorherigen Versuch hinterlassene Progress-Files lesen (PROGRESS.md, feature-list.json) und den letzten Checkpoint aus der Datenbank laden. Hier übergibt der Harness dem Agent alles, was der vorherige Worker vor seinem Ausfall im Memory hatte.
  2. Vor jedem Tool Call planen. Festhalten, wie „done“ aussieht, wie viel der Run ausgeben darf, welche Tools der Agent aufrufen kann und was den Run vorzeitig beenden soll. Diese Planwerte werden zu Runtime-Checks; ohne sie hat die Ausführung nichts, was sie begrenzen könnte.
  3. Jeweils einen Tool Call ausführen. Die Policy-Schicht entscheidet, ob der Call zulässig ist. Der Harness führt ihn aus, erfasst das Result und schreibt ein Event in das Session Log. Ein Schritt, ein Event. Ein Crash zwischen Events ist wiederherstellbar, weil das Log und nicht der Memory des Workers die Quelle der Wahrheit ist.
  4. An Super-Step-Grenzen oder in einem einfacheren Harness nach jedem Event einen Checkpoint schreiben. Den Graph State, den Workspace-Diff und Referenzen auf erzeugte Artefakte persistieren. Dieser Checkpoint wird beim nächsten Resume in Schritt 1 gelesen. Fehlt der Checkpoint oder ist er veraltet, verschlechtert sich die Recovery zum erneuten Abspielen des gesamten Session Logs, was erheblich langsamer ist.
  5. Wenn der Agent glaubt, fertig zu sein, anhand der Artefakte evaluieren: Tests, Fresh-Context-Reviewer, Schema-Validierung, Browser-Checks. Besteht die Prüfung, endet der Run erfolgreich. Schlägt sie fehl, wird der Run vom letzten sauberen Checkpoint mit der Fehlermeldung im Context fortgesetzt und erneut versucht.

Kein Schritt dieser Liste setzt voraus, dass sich der Agent zwischen Runs an etwas erinnert. Der State liegt in Session und Checkpoint, und der Agent liest ihn bei jedem Resume erneut ein.

Jedes Tool mit Side Effects benötigt einen aus Session-ID und Tool-Call-ID abgeleiteten Idempotency Key, der vor dem Side Effect gespeichert wird. send_email(session_id, tool_call_id, message_hash). create_pr(session_id, tool_call_id, branch_name). charge_customer(session_id, tool_call_id, invoice_id). At-least-once Execution ist der Standard in Queues und Workflow Engines. Wenn die Wiederholung eines Tool Calls realen Schaden verursachen kann, ist das Tool noch nicht für Agents bereit.

Evaluation sollte Evidence außerhalb des Producing Context enthalten. Ein Fresh Evaluator reduziert Shared-Context-Bias, während Tests, Lints, Browser-Checks und Schema-Validierung deterministische Evidence liefern. Die Prüfung kann pass, fail oder needs_human zurückgeben. Bei Code Agents kann der Reviewer eine andere Model Session mit Read-only Tools sein. Für Daten- und Report-Agents sollten deterministische Validierung und ein Reviewer Model kombiniert werden, wenn weiterhin ein Urteil erforderlich ist.

Elf AI-Agent-Deployment-Muster und die Entscheidungskriterien

Sobald die fünf Primitive benannt sind, stellt sich die Frage, welche Deployment-Form sie ausführt. Mit „Form“ ist eine Anordnung dieser Primitive gemeint: Wo lebt der Harness, wo wird State persistiert und welche Art von Sandbox führt die Arbeit aus? Eine Form ist eine Wiring-Entscheidung, keine Vendor-Auswahl. Das Diagramm unten zeigt, bei welchen Run-Längen sich die jeweiligen Formen bewähren. Der folgende Text erläutert, was zwischen ihnen entscheidet.

Wenn Sie nur eines der elf Muster lesen, lesen Sie Muster 2: Queue + Worker + Checkpoint DB. Dies ist die Standardempfehlung für die meisten Teams, die im Referenz-Repository verwendete Form und das Grundgerüst, von dem die meisten anderen Formen abweichen: Queue → Durable State, mit ausgetauschtem Sandbox-Source, Harness-Besitzer oder State Engine. Wenn Sie zuerst Muster 2 lesen, lassen sich die übrigen schneller überfliegen.

Das Diagramm vergleicht die Formen nach Run-Länge. Die folgende Matrix vergleicht sie nach Ownership: Wo befindet sich jedes der fünf Primitive physisch? Grüne Zellen zeigen, wo die Form das Primitiv bereitstellt; Grau bedeutet, dass Sie es selbst anbinden.

1. SDK in einem App Server (synchron, Request-scoped)

Die ursprüngliche Form. Das Agent SDK läuft in einem Request Handler. Gut für Aufgaben unter 30 Sekunden, Demos und interne Tools. Schlecht für alles, bei dem sich ein HTTP-Client trennen könnte. Das HTTP-Timeout von Cloud Run endet spätestens nach 60 Minuten, und jeder Panic im Web-Tier beendet den Run. Das SDK ist der Harness, der Web-Prozess fungiert zugleich als Sandbox, und State liegt meist im Process Memory, sofern Sie ihn nicht explizit anderswo speichern. Für mehrstündige Arbeit nicht verwenden.

2. Queue + Worker + Checkpoint DB

Die Standardempfehlung für die meisten Teams und die in market-analyst-agent verwendete Produktionsform: ein Python Worker mit PostgreSQL Checkpointer, Redis Streams (oder RabbitMQ) für die eingehende Queue und ein MCP Sidecar für Tools. Gut für Runs von zehn Minuten bis zu mehreren Stunden mit idempotenten Steps. Der lokale Runner kann die Queue für synchrone Entwicklung umgehen; sobald asynchrone Submission und Backpressure erforderlich sind, gehört die Queue zur Produktionsform.

Die App nimmt einen Request entgegen, erstellt eine Session Row, legt einen Job in die Queue und gibt eine Run-ID zurück. Der Worker holt den Job ab, führt den Harness aus, schreibt Checkpoints, streamt den Status und speichert währenddessen Artefakte. Postgres bleibt erhalten, Worker sind austauschbar, und die Queue-Tiefe liefert Backpressure. Spot-/Preemptible-Compute funktioniert, solange der Checkpointer vor der Erfolgsmeldung seinen Schreibvorgang auf den Datenträger abschließt.

In dieser Form ist der Worker der Harness. Sein Container und der Per-Thread-Workspace bilden eine Ausführungsgrenze, aber nicht vertrauenswürdiger Code benötigt weiterhin eine gehärtete Sandbox oder VM. Postgres besitzt Session- und Checkpoint-State. Traces laufen über OpenTelemetry in den von Ihnen betriebenen Observability-Stack.

3. Durable Workflow Engine (Temporal-Style)

Der Agent Orchestration Code läuft in einem Temporal Workflow; Model Calls und Tool Calls laufen als Activities. Der Workflow State liegt in einem von Cassandra, MySQL oder Postgres unterstützten Event-History-Log, sodass State über Deployments hinweg sauber replays ausgeführt werden kann. Die Public-Preview-Temporal × OpenAI Agents SDK Integration enthält einen OpenAIAgentsPlugin und einen activity_as_tool Helper. Der Beitrag Agentic Sandboxes beschreibt außerdem, wie ein laufender Agent mitten in einer Conversation auf einen anderen Sandbox-Provider geforkt wird. Idle Workflows verbrauchen keinen Compute. Die Einschränkungen sind real: Streaming- und Voice-Agents werden in der aktuellen Integration nicht unterstützt, und LocalShellTool sowie ComputerTool sind deaktiviert, weil sie nicht zum Distributed Model passen.

Verwenden Sie diese Form, wenn der Run echte Wartepunkte enthält: menschliche Approvals, externe Callbacks, lange Sleeps, Retries mit Business Rules oder Deployment-Fenster. Eine menschliche Approval wird zu einem Durable Sleep ohne Compute-Verbrauch und nicht zu einer Polling-Schleife.

Der Workflow-Code ist der Harness. Die Sandbox liegt meist außerhalb von Temporal und wird aus Activities aufgerufen. Session- und Checkpoint-State fallen in Temportal zu dessen Event-History-Log zusammen, während die Trace-Sichtbarkeit aus der Temporal UI und OpenTelemetry-Spans für jede Activity stammt.

4. Sandbox Provider pro Session

Eine neuere Form. Jeder Agent Run erhält eine eigene MicroVM oder einen eigenen Container von einem Sandbox-as-a-Service-Provider. Der Harness liegt an einem Durable Ort; die Sandbox ist die wegwerfbare Ausführungsumgebung.

5. Anthropic Managed Agents (gehosteter Harness)

Anthropic hat Managed Agents am 8. April 2026 als Public Beta hinter dem managed-agents-2026-04-01 Beta Header gestartet. Der Service stellt eine gehostete Session, einen Harness, eine Sandbox und einen Vault-basierten MCP Proxy bereit. wake(sessionId) kann den Harness auf einem neuen Worker initialisieren, ohne Durable Session State zu verlieren.

Claude berechnet für Managed Agents die Standard-Token-Raten plus $0.08 pro Session-Stunde. Die Abrechnung erfolgt millisekundengenau und gilt nur, solange der Session-Status „running“ lautet; Idle-Zeit ist kostenlos. Eine außer Kontrolle geratene Retry-Schleife verursacht daher zusätzlich zu den Token-Kosten Session-Hour-Kosten.

Beachten Sie die Einschränkungen. Der Batch-API-Rabatt gilt nicht („Sessions sind Stateful und interaktiv. Es gibt keinen Batch-Modus.“). Managed Agents ist nicht über AWS Bedrock oder Google Vertex AI verfügbar. Multi-Agent Coordination und Self-Evaluation befinden sich weiterhin in einer Research Preview. Die Bindung ist stark: Sie tauschen die Freiheit beim Harness gegen den Vorteil, den Loop nicht selbst betreiben zu müssen.

Anthropic hostet alle fünf Primitive: Session, Harness, Sandbox, Checkpoint und Trace. Sie übergeben den Runtime und erhalten die Outputs.

6. LangChain Deep Agents Deploy (Managed Open Harness)

deepagents deploy verpackt einen deepagents.toml in ein LangSmith Deployment mit Durable Execution, Memory, Multi-Tenancy, Human-in-the-Loop, Observability, Sandbox-Codeausführung und geplanten Runs. Cloud-, Hybrid- und Self-hosted-Deployment-Modi werden unterstützt. Sandbox-Provider (LangSmith Sandboxes, Daytona, Modal, Runloop oder Custom) lassen sich über einen einzelnen Config-Wert austauschen. State liegt in einem Virtual Filesystem mit austauschbaren Backends; Memory kann auf User, Assistant oder beide begrenzt werden. Die Bindung ist geringer als bei Managed Agents: Der Harness steht unter MIT-Lizenz, Instructions verwenden den offenen AGENTS.md-Standard, und Agents werden über MCP, A2A und Agent Protocol bereitgestellt. Siehe den Beitrag von LangChain runtime-behind-production-deep-agents.

Standardmäßig werden alle fünf Primitive gehostet, aber jedes lässt sich per Config austauschen. Die Sandbox sitzt hinter einem einzelnen Config-Wert. Session und Checkpoint liegen in einem Virtual Filesystem mit austauschbaren Backends. Der Trace geht an LangSmith.

7. Google Cloud Run Service oder Job

Cloud Run besitzt zwei unterschiedliche Runtime-Modi. Welcher passt, hängt davon ab, wie der Agent aufgerufen wird. Services sind HTTP-gebunden und skalieren zwischen Requests auf null; der Harness läuft als Request Handler und gibt zurück, wenn der Run abgeschlossen ist. Jobs laufen ohne HTTP-Einstieg bis zum Abschluss; der Harness läuft als One-Shot-Worker und beendet sich nach Ende der Aufgabe. Beide können den Harness hosten, aber keiner hält State über Runs hinweg. Sessions und Checkpoints müssen in Postgres, Spanner oder einem ähnlichen externen Store liegen.

Die harten Limits unterscheiden sich deutlich. Cloud Run Service Request Timeout: standardmäßig 300 s, maximal 3.600 s (60 min). WebSockets erhalten dasselbe Timeout. Cloud Run Jobs: standardmäßig 10 Minuten pro Task, maximal 168 h (7 Tage); für Tasks mit GPUs maximal 1 Stunde. Services skalieren auf null, sofern Sie Always-on-CPU nicht aktivieren; Jobs haben kein HTTP und autoskalieren nicht.

Verwenden Sie einen Service für synchrone Runs bis zu 60 Minuten. Verwenden Sie einen Job für längere One-Shot- oder asynchrone Arbeit. Cloud Run Jobs können einen Task tagelang am Leben halten, liefern aber kein Durable Replay über Deployments, Versionswechsel oder Worker-Ersatz hinweg. Oberhalb von 7 Tagen sollten Sie Cloud Run nicht verwenden.

Cloud Run hostet den Harness. Session- und Checkpoint-State liegen in Postgres, Spanner oder einem anderen externen Store; Traces können über Cloud Logging und OpenTelemetry laufen. Der Service-Container ist eine Ausführungsumgebung; fügen Sie eine separate Sandbox hinzu, wenn der Agent nicht vertrauenswürdigen Code ausführt.

8. AWS Lambda (warum es das falsche Tool ist)

Das maximale Function Timeout von Lambda beträgt unveränderlich 900 s (15 Minuten). Wenn API Gateway die Function davor schaltet, hängt das Integrationslimit vom API-Typ ab. HTTP APIs erlauben 30 Sekunden; REST-Integrationen verwenden standardmäßig 29 Sekunden, während regionale und private REST APIs ein längeres Timeout konfigurieren können. Keine dieser Varianten macht Lambda zu einem mehrstündigen Worker. Ein lang laufender Harness benötigt weiterhin externen State und erneute Invocations, wodurch das Queue-+-Worker-Muster wieder entsteht. Verwenden Sie Lambda für begrenzte Tool Calls, etwa File Fetches oder S3 Uploads, die von einem länger laufenden Orchestrator aufgerufen werden. Den Orchestrator sollten Sie dort nicht platzieren.

Lambda hält höchstens einen Tool Call innerhalb seines 15-Minuten-Limits. Harness, Session, Checkpoint, Sandbox und Trace müssen an anderer Stelle liegen.

9. AWS ECS / Fargate Task pro Run

Fargate dokumentiert im Gegensatz zu Lambda kein hartes Limit für die Task-Laufzeit. Fargate-Throttling-Quotas erlauben einen Launch Burst von 100 und ein Auffüllen mit 20 pro Sekunde, mit separaten Budgets für On-Demand und Spot. ECS Service Quotas begrenzen Services mit AWS Cloud Map Discovery auf 1.000 Tasks pro Service und EC2-basierte Cluster auf 5.000 Container Instances.

Fargate erfordert den awsvpc-Modus, sodass jeder Task ein Network Interface und eine private IP erhält. Diese Form eignet sich für VPC-internen Datenzugriff. Fargate Spot bringt ein Unterbrechungsrisiko mit sich, und die Durability bleibt Ihre Verantwortung, weil die Plattform kein Temporal-ähnliches Replay bietet.

Fargate hostet den Harness und gibt jedem Run einen eigenen Task. Dadurch werden Workspaces und Task-Credentials getrennt, aber Fargate ist allein noch keine vollständige Sandbox für feindseligen Code. Session, Checkpoint und Trace gehen an externe Services wie RDS oder DynamoDB sowie CloudWatch/X-Ray.

10. Kubernetes Job oder Namespace pro Session

Gut geeignet, wenn Sie Kubernetes bereits betreiben und Sandbox-per-Session mit clusterweiten Controls benötigen. Schlecht geeignet, wenn Sie einen Start in unter einer Sekunde benötigen, da das Abrufen des Container-Images und die Initialisierung des Pods beim Cold Start zu lange dauern. Das Muster verwendet einen Job pro Agent Run, mit activeDeadlineSeconds, einem PersistentVolumeClaim für den Workspace und einem Sidecar für den MCP Server. Die Crash Recovery müssen Sie selbst bauen. Kubernetes nur für Agents einzuführen, ist aufgrund von Konfigurationsaufwand und operativer Last teuer. Es lohnt sich nur, wenn Sie K8s bereits aus anderen Gründen betreiben.

Kubernetes hostet den Harness und die Ausführungsumgebung pro Run, üblicherweise als einzelner Job und gelegentlich mit einem dedizierten Namespace. Starke Isolation hängt weiterhin von Runtime Class, Network Policy, Pod Security und der zugrunde liegenden Container- oder VM-Grenze ab. Session- und Checkpoint-State liegen in einer externen Datenbank oder auf einem PersistentVolumeClaim.

11. Lokales Docker Compose (nur Entwicklung)

Die Referenz für den nächsten Abschnitt. Der Zweck dieser Form besteht darin, die Produktions-Topologie eins zu eins abzubilden (dieselben Primitive, dieselbe Netzwerkform), während alles auf einem einzelnen Rechner läuft. Lesen Sie die Liste „nicht produktionssicher“ am Ende des nächsten Abschnitts, bevor Sie etwas ausliefern, das so aussieht.

Compose spiegelt Form Nummer 2 auf einem einzelnen Host. Postgres hält Session- und Checkpoint-State, und der Worker-Container ist der Harness. Der gemeinsame Workspace-Mount ist für die Entwicklung praktisch, isoliert jedoch keine nicht vertrauenswürdigen Runs. Der optionale OpenTelemetry-Stack zeichnet Traces auf.

Referenz-Stack: Docker Compose

Die in slavadubrov/market-analyst-agent verwendete Referenz-Topologie besteht aus einem LangGraph Worker, einem Postgres Checkpointer, Qdrant für Retrieval, einem MCP Sidecar, einer Redis Queue für asynchrone produktionsähnliche Runs und einem optionalen Prometheus / Grafana / Loki / Tempo / OTel Observability-Stack. In Local Compose ist Redis nur deshalb optional, weil der synchrone Runner den Worker direkt aufrufen kann. docker compose up startet die gesamte Topologie lokal.

Der einzige Teil, der inline gezeigt werden sollte, ist die kanonische LangGraph-Verdrahtung. Sie ist das kleinste konkrete Beispiel für das Checkpoint-Primitiv:

Observability, die den Run überlebt

Kurze Request Handler lassen sich leicht debuggen: Wenn etwas fehlschlägt, lesen Sie die Response und das Live-Log. Lang laufende Agents haben diesen Luxus nicht. Wenn ein sechsstündiger Run fehlschlägt, liegt das interessante Event fünf Stunden zurück, die Live-Terminalausgabe ist verschwunden und der Worker, der sie erzeugt hat, wurde ersetzt. Niemand wird den Run aus dem Gedächtnis rekonstruieren. Sie debuggen daher anhand Durable Artifacts, die geschrieben wurden, während der Run noch lief.

Produktions-Stacks decken typischerweise vier Artefaktarten in zwei Gruppen ab. Zwei davon lesen Sie nach Abschluss des Runs für Postmortems und Replay: ein abfragbares Event Log jedes Schritts und OpenTelemetry Traces darüber, wohin Zeit und Tokens geflossen sind. Zwei davon lesen Sie während des Runs. Das eine ist ein Live-Tail dessen, was der Agent im Workspace produziert. Das andere ist ein Per-Worktree-Observability-Stack, den der Agent selbst abfragen kann, während er arbeitet.

Strukturiertes Event Log (nach dem Run lesen)

Jeder Model Call, Tool Call, jedes Result, jeder Error und jedes Approval wird mit Session-ID und Timestamp versehen in Durable Storage geschrieben. Nach dem Ende des Runs können Sie es wie eine normale Datenbanktabelle abfragen. Addy Osmani formuliert den Maßstab in Long-running Agents klar: „Wenn Sie nicht aus Durable Storage rekonstruieren können, was der Agent in den letzten 24 Stunden getan hat, haben Sie kein lang laufendes Agent-System, sondern ein lang laufendes Shell-Script, das zufällig ein LLM aufruft.“

OpenTelemetry GenAI Traces (nach dem Run lesen)

Dieselben schrittweisen Daten, aber als Spans mit den Standardattributen aus den gen_ai.* Semantic Conventions: Model-Name, Provider, Input- und Output-Token-Counts, Conversation-ID, Workflow-Name (Development Status seit v1.36.0). Provider-spezifische Felder liegen in Subnamespaces (anthropic.*, openai.*), die auf gen_ai.provider.name basieren. Der Grund für den Standard ist Portabilität: Ein Backend-Wechsel erfordert keine erneute Instrumentierung des Codes.

Tool-Call-Timeline plus Workspace-Diffs (während des Runs lesen)

Der schnellste Weg herauszufinden, was ein Agent gerade tut, ist, die von ihm im Workspace erzeugten Dateien zu tailen, statt ein Session Log zu durchsuchen. Der Quick-Start Harness Primitives for Long-Running Claude Agents von Anthropic liefert dafür zwei Hooks: watch -n 5 'git log --oneline -8' zeigt die neuesten Commits des Agents, und watch -n 5 'find screenshots -name "*.png" | tail -5' zeigt die neuesten Screenshots, die er aufgenommen hat. Zwei Terminal-Panes, die sich alle fünf Sekunden aktualisieren, reichen aus, um zu erkennen, ob ein Run echten Fortschritt macht oder sich im Kreis dreht.

Ephemerer Stack pro Worktree (vom Agent selbst während des Runs lesen)

Laut OpenAIs Harness-Beitrag werden „Logs, Metrics und Traces Codex über einen lokalen Observability-Stack zur Verfügung gestellt, der für jeden Worktree ephemer ist“. Jeder Agent Worktree erhält ein eigenes kurzlebiges Loki + Prometheus + Tempo, ausschließlich auf diesen Run begrenzt. Der Agent fragt den Stack während seiner Arbeit ab. So kann ein Prompt wie „Kein Span in diesen vier User Journeys überschreitet zwei Sekunden“ direkt vom Agent verifiziert werden, statt dass er raten muss.

(Der Fresh-Context-Evaluator aus der Failure-Modes-Tabelle liest diese Artefakte, um „done“ zu entscheiden. Er gehört zur Evaluation, nicht zur Observability; siehe § Der gesunde Run-Lifecycle. Er hängt von jeder oben genannten Oberfläche ab.)

Ein minimaler selbst gehosteter Observability-Stack

Für etwas wie market-analyst-agent:

  1. OpenTelemetry Collector mit GenAI Processor und einem Attribute Filter auf gen_ai.*.
  2. Tempo (oder Jaeger) für Traces, nach gen_ai.conversation.id / thread_id verschlüsselt.
  3. Loki für strukturierte Event-Log-Einträge.
  4. Prometheus für gen_ai.client.token.usage, gen_ai.client.operation.duration, gen_ai.server.time_to_first_token (siehe die GenAI Metrics Conventions).
  5. Grafana-Dashboards nach gen_ai.agent.name und gen_ai.request.model.

Gehostete Alternativen (eine auswählen, nicht drei):

  • LangSmith: native LangGraph-Integration; zugleich das Deployment-Ziel für Deep Agents Deploy.
  • Braintrust: beste Eignung, wenn Eval-first-Regression-Suites Priorität haben.
  • Arize Phoenix: OSS, OTLP-nativ, passend zu OpenInference-Instrumentation.
  • OpenAIs Tracing Dashboard: automatisch, wenn Sie das OpenAI Agents SDK oder dessen Temporal-Integration verwenden.
  • Anthropics Claude Tracing: für Sessions innerhalb von Managed Agents.

Das Debug-Bundle-Muster

Wenn ein Run fehlschlägt, sollte der Worker /workspaces/${THREAD_ID}/_debug/ mit den Artefakten ablegen, die Sie für ein Postmortem anfordern würden:

  • session.jsonl: vollständiger Event-Log-Dump aus dem PostgresSaver (checkpointer.list({"thread_id": ...})).
  • last_state.json: StateSnapshot.values aus dem letzten erfolgreichen Super-Step.
  • trace.json: OTLP-exportierte Spans für den Run.
  • tool_calls.csv: (ts, tool, input_hash, latency_ms, status, error).
  • workspace.tar.zst: Workspace-Verzeichnis plus git diff gegen den Initializer Commit.
  • screenshots/*.png: was der Agent gesehen hat.
  • PROGRESS.md, feature-list.json und alle anderen vom Agent verfassten Progress-Files.
  • env.txt: Image-Tags, Model-Version, Harness Commit SHA.

Dieses Bundle liefert einem Menschen oder Reviewer Agent genügend Evidence, um den Fehler zu rekonstruieren. „Der Agent ist stecken geblieben“ ist vage. Ein beispielhafter Report ist konkret: Session s_123 verbrauchte 71 Prozent ihrer Tokens damit, drei Commands zu wiederholen, nachdem npm install fehlgeschlagen war.

Die passende Form auswählen: Ein Entscheidungsleitfaden

Der größte Teil des Vergleichs lässt sich auf einige wenige Entscheidungen reduzieren.

Mit der Run-Länge beginnen

Verwenden Sie die Run-Länge als ersten Filter:

  • Unter 30 Sekunden, idempotent: Request-Lifecycle-SDK in einem App Server.
  • 30 s bis 60 min, keine Crash Recovery erforderlich: Queue + Worker + Checkpoint DB.
  • 60 min bis 24 h: Derselbe Queue-+-Worker-Stack oder ein Cloud Run Job für One-Shot-Arbeit. Eine Durable Workflow Engine verwenden, wenn zusätzlich Versionierung und Replay erforderlich sind.
  • Mehr als 24 h, muss Deployments überleben: Durable Workflow Engine (Temporal-Style). Cloud Run Jobs können lange Arbeit bis zu ihrem Task-Limit halten, bieten aber keine Replay-Semantik.
  • Multi-Day-RL-Training-Loops: K8s Job + Volume + Temporal.

Prüfen Sie nach diesem groben Filter Side Effects, Recovery, Replay, Isolation, Datenstandort und das Team, das das System betreiben wird.

Plattform-Eignung nach Use Case

Die Matrix ist dicht, weil keine einzelne grüne Zelle die Architektur entscheidet. Eine breite Workload-Abdeckung ist nützlich, zeigt aber weder Data Residency noch Replay-Semantik, Provider-Abhängigkeit, operative Reife oder die Kosten einer späteren State-Migration.

Deep Agents Deploy deckt jeden in der Matrix erfassten Workload-Typ ab. Damit ist es ein Kandidat, wenn eine Plattform kurze Runs, mehrstündige Arbeit, Code Agents, Research Agents und geplante Jobs bedienen muss. Diese Breite geht mit einer kürzeren Produktionshistorie einher als bei einem Queue-+Worker-+Postgres-Stack. Betrachten Sie die grünen Zellen als Capability Claims, die Sie validieren müssen, und vergleichen Sie anschließend die operativen Einschränkungen, die die Matrix nicht abbilden kann.

Anthropic Managed Agents passt entweder vollständig zu Ihrer Workload oder gar nicht. Das Produkt hat drei harte Einschränkungen: Es ist Hosted-only, Claude-only und auf weniger als 24 Stunden pro Session begrenzt. Wenn Ihre Workload alle drei Bedingungen erfüllt, etwa ein interner Coding Agent, der in Bursts von 2–6 Stunden läuft und bei dem Sie den Harness lieber nicht selbst betreiben möchten, ist Managed Agents gut geeignet. Ein großer Teil der Plattformarbeit entfällt für Ihr Team. Wenn eine Einschränkung verletzt wird, weil Sie ein Nicht-Claude-Model, Self-hosted Compliance oder 48-Stunden-Runs benötigen, passt Managed Agents nicht. Keine Konfigurationsänderung kann das ändern.

Gehosteter Harness vs. eigener Harness

Die Unterscheidung ist operativ und nicht davon abhängig, wer den Harness-Code geschrieben hat. Hosted bedeutet, dass der Vendor den Harness Loop in seiner Infrastruktur betreibt und Sie eine API aufrufen. Owned bedeutet, dass Sie den Loop auf Ihrer eigenen Infrastruktur betreiben, selbst wenn der Harness-Code von einem Vendor stammt.

LangChain erscheint auf beiden Seiten dieser Grenze, was häufig zu Verwirrung führt. Das Unternehmen liefert LangGraph, eine MIT-lizenzierte Library, die Sie selbst hosten (owned), und Deep Agents Deploy, ein Managed Product, das im Standard-Cloud-Modus einen Deep-Agents-Harness auf LangSmith Deployment betreibt (hosted). Dasselbe Unternehmen, zwei unterschiedliche operative Modelle. Sie wählen das Modell, nicht den Vendor. (Deep Agents Deploy verfügt auch über einen Self-hosted-Modus für Teams, die die Harness-Ergonomie ohne die Cloud-Komponente möchten; dieser Modus fällt in die Owned-Kategorie.)

Wählen Sie einen Hosted Harness, wenn dessen Model Support, Daten-Grenze, Recovery-Verhalten und Extension Points bereits passen. Wählen Sie einen Owned Harness, wenn diese Constraints Anforderungen sind, von denen Sie erwarten, dass sie sich ändern. Eine Migration zwischen beiden verändert State, Observability und Ausführungsgrenzen. Testen Sie den Exit Path, bevor Produktionsdaten davon abhängen.

Gehostete Sandbox vs. eigene Ausführungsumgebung

Wählen Sie eine Hosted Sandbox, wenn Isolation, Pause/Resume oder Fork-Semantik des Providers zu Ihrem Threat Model und Startup-Budget passen. Docker oder Fargate können für vertrauenswürdige interne Workloads mit VPC-Zugriff oder strikter Data Residency ausreichen, aber ein Standard-Container ist keine ausreichende Grenze für feindseligen Code. Fügen Sie gVisor, Kata, eine MicroVM oder einen anderen gehärteten Runtime hinzu, wenn der Agent nicht vertrauenswürdige Packages installiert oder generierte Programme ausführt.

State Stores: Git, DB und Object Storage nebeneinander

Lang laufende Agents verwenden meist drei State Stores gleichzeitig, weil jeder Store ein anderes Artefakt besitzt.

Git speichert Workspace State: Code, Dokumente und Progress-Files, die der Agent ändert. Jeder Commit liefert dem Harness einen stabilen Recovery-Punkt und der nächsten Session eine kompakte Historie.

Die Checkpoint-Datenbank speichert Graph State: Was entschieden wurde, welche Nodes liefen, welche Results zurückkamen und was als Nächstes laufen soll. Der Artifact Store hält große finale Outputs wie PDFs, Parquet-Dateien und Screenshots. Diese Artefakte gehören weder in Git noch in die Checkpoint-Datenbank.

Git als State verwenden

Verwenden Sie Git, wenn die Workload codeförmig ist (Multi-File-Edits, Refactorings, App-Generierung) oder dokumentförmig genug, dass File History relevant ist. Das Muster ist einfach: einen Run Branch erstellen, einen Initializer Commit anlegen und anschließend an sinnvollen Grenzen committen: nach dem Setup, nach jeder Feature-Implementierung, nach bestandenen Tests und nach dem finalen Cleanup. Die neueste Workspace Commit SHA neben der Checkpoint Row speichern. Beim Resume checkt der nächste Worker den Branch aus, liest git log --oneline -8, untersucht git status und den neuesten Diff und liest anschließend PROGRESS.md oder das Handoff-File, das die vorherige Session geschrieben hat.

Damit wird Git zu einer Recovery-Oberfläche für das bearbeitete Artefakt und nicht zu einem Ersatz für die Checkpoint DB. Git kann zwei Fragen beantworten: Was hat sich geändert, und welche Version hat die Tests bestanden? Git kann dem Harness nicht mitteilen, welcher Graph Node als Nächstes laufen soll, welcher Tool Call auf Approval wartet oder welcher Retry seinen Idempotency Key bereits verwendet hat. Anthropics Harness nutzt Initializer Commits plus Per-Feature-Commits als Quelle der Wahrheit für die Workspace Recovery; das Model liest git log --oneline -8, um den State wiederherzustellen. Überspringen Sie Git, wenn das Arbeitsergebnis aus einer einzelnen konversationellen Antwort besteht. Der Overhead lohnt sich dann nicht.

DB-Checkpointing verwenden

Verwenden Sie PostgresSaver-artiges Checkpointing, wenn der Agent eine Graph-Struktur mit mehreren Nodes besitzt, deren Zwischen-State relevant ist (Planner → Researcher → Writer → Verifier). Das Referenz-Repository verwendet es genau aus diesem Grund. Legen Sie Workspace-Artefakte im Terabyte-Maßstab nicht in den Checkpoint; diese gehören in Object Storage.

Einen Artifact Store verwenden (S3 / GCS)

Verwenden Sie Object Storage, wenn:

  • der Output größer ist, als die Checkpoint-Datenbank tragen sollte;
  • nachgelagerte Consumer ein per URL adressierbares Artefakt benötigen, ohne über den Agent zu gehen; oder
  • Deliverable und Run State unterschiedliche Retention Windows haben.

Sie könnten beispielsweise das Session Log nach 30 Tagen löschen, den finalen Report aber jahrelang aufbewahren. Strukturieren Sie das Layout nach (thread_id, checkpoint_id, artifact_name), damit der erzeugende Run rekonstruierbar bleibt.

Wann Human-Approval-Gates hinzugefügt werden sollten

Fügen Sie Gates hinzu, wenn der Tool Call destruktiv und irreversibel ist (DB Writes, Geldbewegungen, das Senden externer Kommunikation), wenn der Tool Call den Blast Radius des Agents verlässt (Production Deployments, kundenorientierte Veröffentlichungen) oder wenn Regulatoren eine Prüfung verlangen. LangGraphs interrupt() und die Approval Middleware von Deep Agents unterstützen diese Gates bereits. Teil 4 behandelte, warum diese Gates eine Permission-Frage und keine Prompt-Frage sind.

Eine praktische Production Checklist

Bevor ein lang laufender Agent ausgeliefert wird, beantworten Sie diese Fragen mit konkreten Infrastrukturangaben.

  1. Welcher Store besitzt Session Events und Checkpoints?
  2. Was passiert, wenn der Worker mitten in einem Tool Call stirbt?
  3. Kann ein Run den Workspace eines anderen Runs beschädigen?
  4. Welche Aktionen benötigen Approval?
  5. Können Model oder Sandbox Raw Credentials lesen?
  6. Welche Tool Calls können sicher wiederholt werden?
  7. Wo wird das Cost Cap pro Run durchgesetzt?
  8. Welche Fresh-Context-Prüfung entscheidet über „done“?
  9. Wo liegen finale Outputs, nachdem die Sandbox verschwunden ist?
  10. Können wir morgen einen fehlgeschlagenen Run erklären, ohne ihn erneut auszuführen?

Wenn die Antwort auf eine dieser Fragen lautet „Der Prompt weist den Agent an, vorsichtig zu sein“, ist das System noch nicht deployed. Es ist weiterhin eine Demo.

Die nächste Schicht ist der Harness Loop

Dieser Runtime kann einen Run am Leben und wiederherstellbar halten, aber Durability beweist nicht, dass die Arbeit korrekt ist. Teil 6, Harness Engineering für AI Agents, behandelt den Loop um das Model: wie ein Trace zu einem Test Case wird, wo Retry- und Stop-Regeln liegen, was ein Handoff bewahren muss und wie eine externe Acceptance-Prüfung entscheidet, dass ein Run abgeschlossen ist.
