Aufgaben von Node, npm, pnpm, TypeScript und tsx

Die ähnlichen Namen verbergen getrennte Aufgaben:

  • JavaScript ist die Sprache.
  • Node.js ist die Runtime, grob vergleichbar mit CPython für JavaScript. Installieren Sie für dieses Projekt Node 24.
  • Die npm-Registry ist der Package-Index, grob vergleichbar mit PyPI. Der Befehl npm wird mit Node installiert und kann Packages aus dieser Registry installieren.
  • pnpm ist der Package Manager, für den sich dieses Repository entschieden hat. Er installiert aus der npm-Registry, verwaltet den Monorepo-Workspace und führt die in package.json deklarierten Befehle aus.
  • package.json ist das Projektmanifest und entspricht am ehesten pyproject.toml. Sein Abschnitt scripts vergibt Namen wie demo, check und dev:api für längere Befehle.
  • TypeScript ist JavaScript mit statischen Typen. Sein Befehl tsc prüft diese Typen. Das Repository führt ihn über pnpm check oder pnpm typecheck aus.
  • tsx führt .ts-Dateien ohne separaten Build aus. Die Entwicklungs-Scripts verwenden seinen watch-Modus, um API oder Worker nach einer Änderung am Quellcode neu zu starten. In diesem Leitfaden rufen Sie ihn nicht direkt auf.

Führen Sie in diesem Repository die pnpm-Scripts aus. Node ist die Runtime innerhalb dieser Scripts; das bereitgestellte Dockerfile übernimmt die Produktion.

Eine kurze Übersetzung von Enums

Für Zustände mit String-Werten verwendet dieses Repository ein Object plus einen daraus abgeleiteten String-Union-Typ:

const Status = { Queued: "queued", Running: "running" } as const;
type Status = (typeof Status)[keyof typeof Status]; // "queued" | "running"

Das Object stellt zur Runtime Status.Queued bereit. Die Zeile type erlaubt beim Type-Checking nur "queued" oder "running". Zusammen erfüllen beide die zwei Rollen dieser Python-Deklaration:

from enum import Enum

class Status(str, Enum):
    QUEUED = "queued"
    RUNNING = "running"

Sie müssen nur das Muster erkennen. as const bewahrt die Werte des Objects als exakte Strings, statt sie auf einen beliebigen string zu erweitern.

Die sieben semantischen Unterschiede, die Zeit kosten

Byte says

Ich übertrug den Python-Standardwert mit or direkt auf ||. Eine konfigurierte Batchgröße von 0 wurde zu 10, und der Run sah völlig normal aus. ?? fängt nur null und undefined ab.

Die Syntax-Tabelle bringt Sie durch die Beispiele. Diese semantischen Unterschiede sind die Stellen, an denen Python-Gewohnheiten Bugs verursachen.

1. Leere Arrays und Objects sind truthy

Die Python-Gewohnheit „leerer Container ist falsy“ wird am schlechtesten übertragen. if (results) ist für ein leeres Array true. Schreiben Sie if (results.length).

2. null und undefined sind verschieden

null kennzeichnet normalerweise bewusstes Fehlen. undefined bedeutet normalerweise, dass ein Wert fehlt oder nicht zugewiesen wurde, obwohl Code es explizit zuweisen kann. Library-Code gibt ständig undefined zurück. Der Unterschied wird relevant, wenn Sie einen Default setzen. || ersetzt die rechte Seite, sobald die linke Seite falsy ist. Dazu gehören 0, "" und false. ?? ersetzt dagegen nur bei null und undefined. Daher ist 0 || 10 gleich 10, während 0 ?? 10 gleich 0 ist. So wird eine Batch-Größe von null unbemerkt zu zehn.

3. Ein Catch-Block erhält unknown

Es gibt kein except ValueError:. Ein catch-Block erhält alles. Da JavaScript das Werfen eines Strings, einer Zahl oder von null erlaubt, typisiert TypeScript den abgefangenen Wert als unknown – den Typ „könnte buchstäblich alles sein“ unter strict. Das Begleit-Repository aktiviert strict, und neue Projekte sollten dies im Allgemeinen ebenfalls tun. Grenzen Sie den Wert zuerst ein, bevor Sie den Fehler untersuchen:

try {
    await risky();
} catch (error) {
    // `error` is `unknown` until you prove otherwise. This line is the
    // TypeScript equivalent of `except ValueError as e:` and it is not
    // optional.
    const message = error instanceof Error ? error.message : String(error);
}

4. Promises starten sofort

Der Aufruf einer async-Funktion beginnt mit der Ausführung ihres Rumpfs und gibt ein Promise zurück. Ein Python-Coroutine-Objekt tut nichts, bis Sie es awaiten oder einplanen. Promise.all entspricht ungefähr asyncio.gather. Promise.allSettled entspricht ungefähr gather(..., return_exceptions=True), außer dass jedes Ergebnis als { status, value } oder { status, reason } verpackt wird.

Node übernimmt das Scheduling der Runtime. Der Prozess bleibt aktiv, solange noch aktive Handles oder Requests wie Timer und Sockets existieren. Ein gewöhnliches ausstehendes Promise allein hält Node nicht am Leben. Sie verpacken das Programm nicht in asyncio.run. In einem ES Module können Sie auf Top-Level await verwenden, wenn der Start auf eine asynchrone Operation warten muss.

5. JavaScript hat einen gewöhnlichen numerischen Typ

Der JavaScript-Typ number speichert Werte als 64-Bit-Gleitkommazahlen, ungefähr wie Pythons float. Der technische Standard für dieses Format heißt IEEE 754. Dezimalwerte sind Näherungen, daher ist 0.1 + 0.2 nicht exakt 0.3, und Ganzzahlen bleiben nur bis 2**53 - 1 bzw. 9,007,199,254,740,991 exakt.

Belassen Sie 64-Bit-IDs an Service-Grenzen als Strings. Die Konvertierung einer Postgres-bigint-Spalte in einen JavaScript-number kann Rundungsfehler verursachen. Für größere exakte Ganzzahlen stellt JavaScript den separaten Typ BigInt bereit, der sich nicht mit gewöhnlichen Zahlen kombinieren lässt.

6. Verwenden Sie Map für ein Python-ähnliches Dictionary

In JavaScript erzeugt {} ein Object. Objects stellen normalerweise Records mit benannten Feldern dar:

const request = { model: "gpt-5", seqLen: 4096 };
console.log(request.model);

Ein Object ist keine saubere Key-Value-Tabelle wie ein Python-dict. Es erbt einige Namen aus JavaScript selbst. Das kann zu einem überraschenden Ergebnis führen:

const tools: Record<string, unknown> = {};

tools["constructor"]; // a built-in function, not a missing value
Object.hasOwn(tools, "constructor"); // false

Wenn ein externer String ein Feld aus einem Object auswählt, rufen Sie vor dem Lesen Object.hasOwn auf. Wenn Sie ein allgemeines Dictionary benötigen, verwenden Sie Map. Map entspricht eher Pythons dict: Ein Key existiert nur, wenn Ihr Code ihn hinzufügt.

const tools = new Map<string, unknown>();
tools.get("constructor"); // undefined

7. Die Dateiendung in relativen Imports angeben

Eine JavaScript-Quelldatei, die Code mit anderen Dateien teilt, wird Module genannt. Dieses Projekt verwendet das moderne Module-Format ES modules, meist zu ESM verkürzt. ES steht für ECMAScript, den formalen Namen der JavaScript- Sprache. Praktisch ist ESM die im gesamten Projekt verwendete Syntax für import und export.

Bei einem relativen Import verlangt Node den exakten Dateinamen. Es errät nicht, ob ./env ./env.ts oder ./env.js bedeutet:

import { loadEnv } from "./env.ts";

Imports aus installierten oder Workspace-Packages verwenden weiterhin den Package- Namen – ohne Dateiendung:

import { z } from "zod";
import { runAgent } from "@agent/core";

Zod ist pydantic mit umgekehrter Richtung

In pydantic deklarieren Sie eine Klasse und erhalten einen Validator. In Zod deklarieren Sie einen Validator und leiten daraus den Typ ab. Dieselbe Single Source of Truth, aber in umgekehrter Richtung.

Aus packages/schemas/src/env.ts:

import { z } from "zod"; // `z` is Zod's whole API, the way `pd` is pandas

const EnvSchema = z.object({
    PORT: z.coerce.number().int().positive().default(8080),
    // See the note below: a bare z.url() would accept "localhost:8000".
    OPENAI_BASE_URL: z
        .url({ protocol: /^https?$/ })
        .default("https://api.openai.com/v1"),
    DATABASE_URL: z.string().optional(),
});

export type Env = z.infer<typeof EnvSchema>;

z.infer<typeof EnvSchema> liest einen statischen Typ aus dem Runtime-Schema. z.coerce.number() berücksichtigt, dass jeder definierte Wert in process.env (Node-os.environ) ein String ist. Es erfüllt dieselbe Aufgabe wie pydantics Coercion numerischer Settings, wobei sich die konkret akzeptierten Strings unterscheiden. Dies folgt dem pydantic-settings-Muster und wird einmal beim Start ausgeführt. Eine ungültige Umgebung führt dann zu einem verständlichen Startup-Fehler statt zu einem TypeError innerhalb eines Handlers.

Ein einfaches z.url() akzeptiert localhost:8000. Der URL-Standard behandelt alles vor dem ersten Doppelpunkt als Schema. Er liest daher localhost: als ein Protokoll namens „localhost“ und akzeptiert den String. Der Wert erreicht dann den HTTP-Client und schlägt dort mit weniger Kontext fehl. Schema-Validierung verschiebt Fehler nach vorn, erzwingt aber ein permissives Schema, wenn Sie genau dieses geschrieben haben.

Zod 4 enthält außerdem z.toJSONSchema. Dieses Projekt benötigt daher nicht die in älteren Tutorials verbreitete Dependency zod-to-json-schema. Das wird wichtig, sobald ein Schema drei Consumer versorgen muss – genau darum geht es im folgenden Abschnitt „Ein Tool, drei Consumer“.

Der Service

Der Demo-Service dimensioniert LLM-Deployments. Ein Tool schlägt Architekturkonstanten eines Models nach. Das andere schätzt dessen KV-cache-Footprint: den GPU-Speicher, der für Attention-Keys und -Values laufender Requests benötigt wird. Beide Tools führen absichtlich nur einfache Arithmetik aus. Sie benötigen kein Netzwerk und liefern jedes Mal dasselbe Ergebnis. Dadurch lässt sich der Service ohne API-Key testen. Der KV-cache-Estimator wird außerdem über das Model Context Protocol (MCP) veröffentlicht, sodass andere AI-Clients ihn aufrufen können.

typescript-agent-service/
├── apps/
│   ├── api/           @agent/api: Hono API, streams Server-Sent Events (below)
│   ├── worker/        polls Postgres for long-running jobs
│   └── mcp/           MCP server: exposes one tool to outside AI clients
├── packages/
│   ├── schemas/       package name @agent/schemas: env, API, and tool schemas

│   └── observability/ Pino logging, OpenTelemetry tracing

pnpm-workspace.yaml ist die Datei, die den Workspace deklariert. Interne Packages erhalten einen Scoped Name wie @agent/core, wobei das Präfix @agent/ eine Namenskonvention und kein Sprachfeature ist. Jedes Package deklariert seinen öffentlichen Einstiegspunkt in package.json. Diese Package-Grenze hängt nicht davon ab, welcher Befehl die Anwendung startet.

Dieser private Workspace verweist bei diesen Einstiegspunkten auf den .ts-Quellcode, weil jeder Consumer Teil desselben Repositorys ist. Öffentliche npm-Packages veröffentlichen normalerweise JavaScript plus .d.ts-Typdeklarationen, damit gewöhnliche Node-Consumer weder den TypeScript-Runner noch das Build-Setup des Package-Autors benötigen.

Den Tool Loop einmal von Hand schreiben

Tool-calling-Agent-Frameworks kapseln denselben grundlegenden Loop:

  1. Model mit Tool-Definitionen aufrufen.
  2. Die angeforderten Tools validieren und ausführen.
  3. Die Ergebnisse an die Messages anhängen.
  4. Das Model erneut aufrufen.

Schreiben Sie diesen Loop einmal selbst. Dann wird das Verhalten des Frameworks zu einer Engineering-Entscheidung, die Sie begründen können.

Der Loop ist ein async function*, also ein async Generator – exakt die Form von Pythons async def mit yield. Die HTTP-Route iteriert über diesen Generator, wandelt jedes Event in einen Server-Sent-Events-Frame um und akkumuliert den Text. Nach dem Ende des Streams ruft die Route storage.createRun einmal mit dem finalen Text auf. Tests rufen den Loop separat auf und sammeln seine Events in einem Array. Ein SSE-Frame ist ein Chunk einer langlebigen HTTP-Response. Der folgende Abschnitt erklärt das Format.

Der Loop hat zwei normale Enden. Eine Response ohne Tool Calls liefert done mit stopReason: "stop". Wenn das Model bis maxSteps weiter Tools anfordert, wird der Generator trotzdem abgeschlossen und liefert done mit stopReason: "max_steps". Behandeln Sie dieses Ergebnis als abgeschlossen, aber abgeschnitten: Der akkumulierte Text kann unvollständig sein.

Aus packages/agent-core/src/loop.ts:

let text = ""; // the assistant text produced during this model step
// Keyed by the `index` field, because a streamed response interleaves
// fragments of several parallel tool calls and only `index` is present
// on every fragment. `id` and `name` arrive once, `arguments` arrives
// in pieces. `a?.b` below reads `b` only if `a` exists, and gives back
// `undefined` instead of throwing if it doesn't.
const partial = new Map<number, PartialToolCall>();

for await (const chunk of stream) {
    const choice = chunk.choices[0];
    if (!choice) continue;

    if (choice.delta.content) {
        text += choice.delta.content;
        yield { type: "text", delta: choice.delta.content };
    }

    for (const fragment of choice.delta.tool_calls ?? []) {
        const slot = partial.get(fragment.index) ?? { id: "", name: "", args: "" };
        if (fragment.id) slot.id = fragment.id;
        if (fragment.function?.name) slot.name = fragment.function.name;
        if (fragment.function?.arguments) slot.args += fragment.function.arguments;
        partial.set(fragment.index, slot);
    }
}

Die lokale Variable text enthält einen Model-Schritt. Der Loop verwendet sie für die Assistant-Message des nächsten Schritts oder im finalen done-Event. Sie ist nicht der Accumulator auf Routenebene, der später persistiert wird.

Die Map partial ist der Teil, den Frameworks verbergen. Das SDK stellt String- Fragmente der Function Arguments bereit; sie können das serialisierte JSON an beliebigen Positionen teilen. Mehrere parallele Calls können sich außerdem verschachteln. Das Repository enthält einen Test, der {"model":"llama-3.1-8b",...} in vier Chunks aufteilt.

Der zweite Teil, den Sie selbst schreiben sollten, ist das Verhalten bei einer fehlgeschlagenen Validierung:

// `tool.parse` is this repo's wrapper, not Zod's. Zod's own `.parse` throws and
// `.safeParse` returns `{ success, data, error }`; this returns
// `{ ok: true, value }` on success and `{ ok: false, error }` on failure, so no
// caller has to catch.
const parsed = tool.parse(raw);
if (!parsed.ok) {
    return {
        ok: false,
        value: { error: `Invalid arguments: ${parsed.error}` },
        parsedArgs: raw,
    };
}

Vor der Ausführung kann die Tool-Suche fehlschlagen, JSON.parse die Argumente ablehnen oder Zod deren Struktur zurückweisen. Jeder Fehler wird zu einer Message, die das Model liest. Während der Ausführung wird auch ein erwarteter ToolError als Tool Result zurückgegeben, damit das Model seinen Call korrigieren kann. Eine unerwartete Exception läuft dagegen in den HTTP-Fehlerpfad und wird nicht als Domain-Fehler präsentiert. z.prettifyError wandelt Zods Issue-Tree in eine Message um, mit der das Model arbeiten kann, statt in einen Stacktrace.

strict: true in einer OpenAI-Function-Definition fordert den Provider auf, Constrained Decoding anhand des Schemas zu verwenden. Das hat keinen Zusammenhang mit dem TypeScript-tsconfig-Flag strict. Es ähnelt dem Guided Decoding von vLLM, wobei sich unterstützte Schemas und Details der Durchsetzung unterscheiden. Dadurch entfällt eine Fehlerquelle, aber ein Self-Hosted-Endpoint kann das Flag ignorieren. Die Argumente müssen außerdem JSON.parse überstehen.

Der Loop ruft /chat/completions auf, weil das Begleit-Repository OpenAI-kompatible Server adressiert. vLLM, SGLang und Ollama dokumentieren diesen Endpoint, daher kann OPENAI_BASE_URL denselben Client auf jeden dieser Server richten. Der Umfang der Responses-API-Unterstützung unterscheidet sich und ändert sich mit den Releases. Wenn Sie beide Seiten kontrollieren, prüfen Sie vor der Wahl zwischen den APIs die aktuelle Kompatibilitätsseite des Servers.

Anschließend zum AI SDK wechseln – und wissen, was Sie eintauschen

Für spätere Projekte würde ich das Vercel AI SDK verwenden. Das Begleit-Repository implementiert denselben Agent zweimal, damit der Trade-off sichtbar wird. Beide Versionen geben denselben AgentEvent-Stream aus, sodass die HTTP-Schicht keinen Unterschied erkennt.

Das Begleit-Repository pinnt AI SDK 7.0.42 in packages/agent-core/package.json. Die Framework-Implementierung befindet sich in packages/agent-core/src/loop-ai-sdk.ts:

const result = streamText({
    model: provider.chatModel(options.model),
    prompt: options.message,
    tools: aiSdkTools,          // Zod schemas passed straight through
    stopWhen: stepCountIs(options.maxSteps ?? 6),
});

for await (const part of result.fullStream) {
    switch (part.type) {
        case "text-delta": yield { type: "text", delta: part.text }; break;
        case "tool-call":  yield { type: "tool_call", callId: part.toolCallId, /* ... */ }; break;
        // ...
    }
}

Das SDK entfernt fünf Teile des Application-Codes:

  • den Fragment-Accumulator
  • JSON.parse und dessen Fehlerpfad
  • den Aufruf, der Zod über die geparsten Argumente laufen lässt
  • Provider-spezifisches Zusammensetzen der Messages
  • den Step-Counter

stopWhen akzeptiert mehrere Bedingungen, darunter ein Step-Limit oder einen bestimmten Tool Call. Der for await-Loop muss sich nicht ändern, wenn sich die Stop-Policy ändert.

Was Sie aufgeben, ist die direkte Kontrolle über Validierungsfehler. Der handgeschriebene Loop entscheidet, was das Model nach einem abgelehnten Call sieht. Das SDK stellt die experimentelle Option experimental_repairToolCall für einen eigenen Repair-Callback bereit. Das aktuelle Begleit-Repository setzt diese Option nicht und verlässt sich daher auf das Standardverhalten des SDK bei ungültigen Calls.

Der Trade-off funktioniert auch in die andere Richtung. In der SDK-Version ist ein Provider-Wechsel im Provider-Adapter gekapselt. Das passende Provider-Package, Credentials, Konfiguration und Integrationstests werden trotzdem benötigt. Im Raw Loop gehören Provider-spezifisches Request- und Stream-Handling zu Ihrem Code und müssen von Ihnen geändert werden.

Im ersten Projekt schreibe ich den Loop selbst und verwende in späteren Projekten das SDK. Diese Lektion bezahlen Sie nur einmal. Die Alternative ist, beim ersten Produktionsfehler die Internals eines Frameworks zu lesen.

Streaming über HTTP: Hono und SSE

Hono-Routen lesen sich wie FastAPI-Routen. Die eine Ergänzung ist zValidator, das die Aufgabe übernimmt, die FastAPI aus den Type-Annotations der Handler- Signatur kostenlos erhält. Das c im folgenden Handler ist Honos Request Context – das Object, das FastAPI auf Ihre Parameter verteilt. deps ist ein Dependency-Container, mit dem die App konstruiert wird, statt Dependencies direkt zu importieren. runAgent ist eine davon; der Testabschnitt zeigt, welchen Vorteil das bringt.

Aus apps/api/src/app.ts:

app.post("/v1/chat", zValidator("json", ChatRequestSchema), (c) => {
    const body = c.req.valid("json");
    const log = deps.logger.child({ route: "chat" });

    return streamSSE(c, async (stream) => {
        let text = "";
        try {
            await withSpan(
                "agent.run",
                { "agent.max_steps": body.maxSteps },
                async () => {
                    for await (const event of deps.runAgent({
                        message: body.message,
                        maxSteps: body.maxSteps,
                    })) {
                        if (event.type === "text") text += event.delta;

                        await stream.writeSSE({
                            event: event.type,
                            data: JSON.stringify(event),
                        });
                    }
                },
            );
        } catch (error) {
            log.error({ err: error }, "agent run failed");
            await stream.writeSSE({
                event: "error",
                data: JSON.stringify({
                    type: "error",
                    message: "Agent run failed",
                }),
            });
            return;
        }

        await deps.storage.createRun({
            kind: "chat",
            status: "succeeded",
            input: { message: body.message },
            output: { text },
        });
    });
});

Die Route behandelt derzeit jeden normal abgeschlossenen Generator gleich. Sie persistiert status: "succeeded" nach jedem Generator, der sein Ende erreicht, einschließlich eines Generators, dessen letztes Event stopReason: "max_steps" enthält. Damit wird das Ergebnis „completed but truncated“ bzw. „partial“ nicht als bereits persistierter Fehler behandelt. Produktionscode sollte das done- Event prüfen und eine explizite Policy anwenden. Beispielsweise könnte er einen eigenen Truncated-Status oder einen Review-/Retry-Pfad verwenden, bevor er Erfolg meldet.

zValidator validiert den Body und gibt c.req.valid("json") den vom Schema erzeugten Typ. Ohne diesen Schritt ist der Body als any typisiert, als TypeScripts Opt-out: Jeder Property-Zugriff kompiliert, und nichts wird geprüft. Damit wird der Type-Safety-Vorteil des Schemas deaktiviert.

Diese Route verwendet Server-Sent Events statt WebSockets. Der Server hält eine HTTP-Response offen, während er event: <name>- und data: <json>- Frames schreibt, und schließt sie nach dem finalen Event. Der Datenfluss geht vom Server zum Client, was zu diesem Agent Stream passt. Ein WebSocket würde bidirektionale Nachrichten und ein Protocol Upgrade hinzufügen, die diese Route nicht benötigt.

Ein Fehler mitten im Stream verändert die HTTP-Fehlerberichterstattung. Sobald der erste Frame mit Status 200 gesendet wurde, kann der Server diese Response nicht mehr durch eine 500-Response ersetzen. Der catch-Block loggt den abgefangenen Fehler, sendet dem Client ein konstantes Error-Event und kehrt zurück. Diese Rückkehr ist wichtig: Nur ein erfolgreich abgeschlossener Stream erreicht storage.createRun. Ein Generator, der done ausgibt, einschließlich max_steps, ist ein normal abgeschlossener Stream und erreicht diesen Write tatsächlich.

Ein Test deckt diesen Pfad ab. Ein Generator liefert zunächst ein Text-Delta und wirft anschließend einen Fehler. Die Response bleibt 200; ihr letzter Frame ist ein error-Event mit der konstanten Nachricht Agent run failed. Der Logger behält den abgefangenen Fehler zur serverseitigen Diagnose. Jeder Client, der nur den Statuscode prüft, meldet einen fehlgeschlagenen Run als erfolgreich.

Byte says

Mein Client prüfte den Statuscode und protokollierte den Run als Erfolg. Die 200 wurde mit dem ersten Frame gesendet, und der Stream starb direkt danach.

app.ts trifft zwei kleinere, aber erwähnenswerte Entscheidungen. Es behandelt /healthz als Liveness-Endpoint; diese Route greift daher absichtlich nicht auf Postgres zu. Ein Liveness-Fehler während eines Datenbankausfalls könnte jedes Replica neu starten, ohne die Dependency zu reparieren. Fügen Sie einen separaten Readiness-Check hinzu, wenn der Orchestrator den Traffic von einer Instanz abziehen muss, die Postgres nicht erreicht. Die Fehlerpfade loggen den abgefangenen Fehler, geben aber einen konstanten String zurück. error.message in den Response-Body zu spiegeln, ist der Weg, auf dem Connection Strings im Browser anderer Personen landen.

Der Celery-ähnliche Teil – ohne Celery

Lange Jobs gehören nicht in einen Request-Handler. Die API fügt eine Zeile ein und gibt 202 zurück. Ein Worker übernimmt die Zeile.

Hier gibt es weder Redis noch BullMQ. PostgreSQL dokumentiert SKIP LOCKED für mehrere Consumer einer Queue-ähnlichen Tabelle. Die Klausel gibt diesem kleinen Service eine At-Least-Once-Queue in einer einzigen Tabelle. Sie ist transaktional mit Ihren übrigen Writes und bedeutet einen Service weniger in docker-compose.yml.

Die Claim-Query in packages/agent-core/src/db/storage.ts lautet:

const [candidate] = await tx
    .select({ id: runs.id })
    .from(runs)
    // The real query also picks up rows whose lock went stale; trimmed here.
    .where(and(eq(runs.kind, kind), eq(runs.status, "queued")))
    .orderBy(runs.createdAt)
    .limit(1)
    // `.for()` exists but is undocumented; SKIP LOCKED rides in its second
    // argument.
    .for("update", { skipLocked: true });

Die Zeile wird für die Transaktion gesperrt; jeder parallele Worker, der dieselbe Query ausführt, überspringt sie, statt zu blockieren. Zwei gleichzeitige Claims erhalten daher nicht dieselbe nicht-veraltete Zeile. Ein Integrationstest startet über Promise.all zwei Claims gleichzeitig und prüft, dass sie unterschiedliche Zeilen zurückgeben. Die naive Variante, SELECT ... LIMIT 1 gefolgt von UPDATE, fällt in diesem Test durch: Beide Transaktionen lesen dieselbe Zeile, bevor eine von ihnen schreibt, und starten daher denselben Job.

Das ist At-Least-Once-Ausführung, nicht Exactly-Once-Ausführung. Die vollständige Query übernimmt außerdem eine running-Zeile erneut, wenn deren Lock älter als fünf Minuten ist; der Demo-Worker erneuert dieses Lease nicht. Ein laufender Job, der länger als fünf Minuten dauert, kann daher zweimal geclaimt werden. Machen Sie Jobs idempotent. Fügen Sie für lang laufende Arbeit einen Lease-Heartbeat hinzu oder setzen Sie den Schwellenwert für veraltete Locks über die maximale Laufzeit.

Fügen Sie BullMQ hinzu, wenn Sie verzögerte Jobs, wiederholbare Schedules, Prioritäten, Rate Limits oder ein Dashboard benötigen. In Python würde ich denselben Schritt von einer Datenbanktabelle zu Celery machen. Davor ist Redis ein weiterer Service, den Sie betreiben, überwachen und der jeweiligen Bereitschaft erklären müssen.

Der Worker validiert die aus jsonb gelesenen Daten erneut:

// The row was validated on the way in, but it has been through a database.
// A stored row can outlive the schema version that accepted it.
// The job is a batch-size sweep. Zod's own `.parse` throws; the poll loop
// catches that and marks the run failed.
const input = SweepRequestSchema.parse(run.input);

Die Testsuite gibt dem Worker außerdem eine Zeile, deren seqLen ein String ist. Der Worker schlägt den Run fehl und pollt weiter, statt abzustürzen und dieselbe Poison Row endlos erneut zu versuchen.

CPU-Arbeit legt eine weitere Node-Einschränkung offen. Ein synchroner Callback läuft im Event-Loop-Thread und wird nicht preempted. Eine for- Schleife, die zwei Sekunden lang Arithmetik ausführt, blockiert in diesem Prozess zwei Sekunden lang jeden Request, Timer und Liveness-Check. Eine enge Schleife in einem async def blockiert asyncio auf dieselbe Weise. Beide Runtimes verlangen, dass Sie CPU-Arbeit explizit auslagern.

await setTimeout(0) aus node:timers/promises (das Präfix node: steht für die Standardbibliothek; node:timers entspricht in Node also dem, was os in Python ist) ist await asyncio.sleep(0). Der Sweep gibt nach jeder Batch-Größe die Kontrolle zurück, damit der Worker-Prozess Timer und andere Callbacks bedienen kann. Yielding macht CPU-Arbeit nicht parallel. Node worker_threads kann JavaScript parallel ausführen. Für reine Python-CPU-Arbeit in einem üblichen GIL-aktivierten CPython-Build verwenden Sie statt eines Thread-Pools einen Process Pool. Dieser Service verwendet keines von beiden. Belassen Sie rechenintensive Numerik in Python, wo die passenden Libraries bereits vorhanden sind, und entfernen Sie sie vom API-Event-Loop.

Ein Tool, drei Consumer

EstimateKvCacheInput hat drei Consumer:

  • Der handgeschriebene Loop konvertiert es mit z.toJSONSchema.
  • Das AI SDK erhält es unverändert.
  • Der MCP-Server veröffentlicht seine Form.

Diese Wiederverwendung ist der Grund für packages/schemas.

Aus apps/mcp/src/index.ts:

server.registerTool(
    "estimate_kv_cache",
    {
        description: "Estimate KV-cache VRAM in GiB for a served model...",
        // A Zod object schema keeps the map of fields you passed in on
        // `.shape`. This SDK wants that map, not the schema wrapped around it.
        inputSchema: EstimateKvCacheInput.shape,
    },
    async ({ model, seqLen, batchSize }) => {
        /* ... */
    },
);

await server.connect(new StdioServerTransport());

Bevor Sie einen Client verbinden, sind zwei Details wichtig. Erstens: Ein auf diese Weise gestarteter Server verwendet stdin und stdout für die Kommunikation mit dem Client. Jede Zeile ist eine JSON-RPC-Message. Ein versehentliches console.log, das JavaScript-Äquivalent zu print, beschädigt anschließend eine Message. Der Client trennt die Verbindung mit einem Parse-Fehler, der keine Datei nennt. Senden Sie sämtliche Diagnoseausgaben an stderr.

Zweitens sollte ein Domain-Fehler isError: true mit einer Message zurückgeben. Das aufrufende Model kann den Call dann korrigieren, genauso wie nach ungültigen Tool-Argumenten im Agent Loop.

Sie können den Server einmal mit printf und einer Pipe ansteuern, bevor Sie einen echten Client darauf richten:

printf '%s\n' \
  '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"probe","version":"1"}}}' \
  '{"jsonrpc":"2.0","method":"notifications/initialized"}' \
  '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"estimate_kv_cache","arguments":{"model":"llama-3.1-70b","seqLen":8192,"batchSize":4}}}' \
  | pnpm -s mcp   # -s suppresses pnpm's own output so only JSON-RPC comes back

Die Probe entspricht der im README des Begleit-Repositories verwendeten Protocol-Version. Für einen echten Client verwenden Sie das SDK, statt JSON-RPC- Messages von Hand zu pflegen.

Einen Agent ohne API-Key testen

Vitest übernimmt die Rolle von pytest, aber die Struktur ist anders. describe gruppiert zusammengehörige Tests. it und test definieren jeweils einen Testfall. test.each entspricht ungefähr parametrize, beforeEach stellt Setup pro Test bereit, vi.fn() erzeugt eine Mock-Funktion und describe.skipIf überspringt eine Gruppe bedingt.

Agent-Tests hängen von einer Entscheidung ab: runAgent erhält einen OpenAI- Client als Parameter, statt selbst einen zu konstruieren. Der Fake ist ein Object mit einer chat.completions.create-Methode, die ein geskriptetes asynchrones Iterable zurückgibt:

function fakeClient(scripts: Chunk[][]): OpenAI {
    let call = 0;
    return {
        chat: {
            completions: {
                create: async () => {
                    const script = scripts[call++] ?? [];
                    // Defines an async generator and calls it on the same
                    // line, so `create` hands back something you can
                    // `for await` over, which is the shape a real streaming
                    // response has.
                    return (async function* () {
                        for (const chunk of script) yield chunk;
                    })();
                },
            },
        },
        // TypeScript refuses a direct cast between unrelated shapes, so you
        // launder it through `unknown` first. A lie to the compiler, confined
        // to one line in a test file, which is the only place it belongs.
    } as unknown as OpenAI;
}

Die Tests teilen einen JSON-Argument-String über mehrere Chunks auf und verarbeiten zwei Tool Calls in einer Response. Sie decken außerdem ungültige batchSize, fehlerhaftes JSON, unbekannte Tool-Namen und ein Model ab, das so lange Tools aufruft, bis maxSteps es stoppt. Die Testdatei läuft deutlich unter einer Sekunde – ohne Netzwerk und ohne Key.

Integrationstests gegen Postgres verwenden describe.skipIf(!process.env.DATABASE_URL). Dadurch funktioniert pnpm test in einem frischen Clone ohne laufendes Postgres, während CI die Tests durch Setzen der Variable aktiviert. Das Repository enthält 40 Tests. 36 davon laufen ohne Postgres und ohne API-Key.

Strukturierte Events mit Pino loggen

Pino erfüllt dieselbe Aufgabe wie structlog: ein JSON-Objekt pro Zeile, Child-Logger mit gebundenen Feldern und explizite Redaction. Das Begleit-Repository konfiguriert Pino in packages/observability/src/logger.ts:

const log = pino({
    redact: {
        paths: [
            "req.headers.authorization",
            "apiKey",
            "OPENAI_API_KEY",
            "*.apiKey",
        ],
        censor: "[redacted]",
    },
});

Ohne Redaction kann log.info({ req }, "...") einen Authorization-Header ins Log-Backend kopieren.

Application Work mit manuellen Spans tracen

Das Begleit-Repository verwendet OpenTelemetry für drei Spans auf Application-Ebene: agent.run, agent.tool und worker.sweep. Automatisches HTTP- oder Postgres-Instrumentation wird nicht installiert. startTracing() in packages/observability/src/tracing.ts erzeugt einen NodeSDK mit einem OTLP-Trace-Exporter. Wenn OTEL_EXPORTER_OTLP_ENDPOINT fehlt, bleibt Tracing deaktiviert.

Die eigentliche Arbeit wird von withSpan() aus derselben Datei umschlossen:

return tracer.startActiveSpan(name, { attributes }, async (span) => {
    try {
        return await fn(span);
    } finally {
        span.end();
    }
});

JavaScript besitzt keine Python-ähnliche Context-Manager-Syntax. Hier ist der Callback der Block, den ein Python-Context-Manager umschließen würde. Der vollständige Helper erfasst außerdem Exceptions und setzt den Span-Status, bevor er die Exception erneut wirft.

Automatische HTTP- und Datenbank-Spans sind ein separates Feature. Sie benötigen die passenden Instrumentation-Packages und eine Initialisierung, bevor die instrumentierten Module geladen werden. Fügen Sie das nur hinzu, wenn diese Spans nützlich sind, und folgen Sie für die exakt deployten Package-Versionen dem OpenTelemetry Node SDK Setup.

Das Monorepo in Docker ausliefern

Verwenden Sie das bereitgestellte Dockerfile. Der Container startet die API mit dem tsx-Loader. Beim Deployment müssen Sie keinen TypeScript- Runner auswählen oder aufrufen.

Der Build verwendet pnpm fetch, damit Dependency-Downloads bis zu einer Änderung der Lockfile gecacht bleiben. Anschließend verwendet er pnpm deploy, um die API und ihre Production-Dependencies in ein eigenständiges Verzeichnis zu kopieren. Die Runtime-Stage läuft als nicht privilegierter User node; die Exec-Form von CMD ermöglicht es der API, SIGTERM direkt für einen Graceful Shutdown zu empfangen.

Warum das Dockerfile tsx lädt

Node 24 kann ein begrenztes TypeScript-Subset ausführen, indem es Type-Annotations entfernt. Es prüft den Code nicht auf Typfehler und führt nicht die Transformationen aus, die ein vollständiger TypeScript-Runner unterstützt. Die Package-Scripts des Repositorys verbergen dieses Detail. pnpm check führt den separaten statischen Check aus.

Der Container legt eine weitere Einschränkung offen. pnpm deploy kopiert die Workspace-Packages nach node_modules, und Node verweigert dort absichtlich das Entfernen von TypeScript (Node-TypeScript-Dokumentation). Die erste Image-Version stürzte mit ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING ab. Es funktioniert. Ich war entmutigt.

Das Dockerfile behebt das Problem, indem es tsx lädt, das diese .ts-Dateien verarbeitet, bevor Node sie ausführt. Ein Team, das im Runtime-Image ausschließlich .js-Dateien möchte, kann stattdessen einen Compile-Schritt ergänzen. Das ist ein alternatives Production-Design, kein zusätzlicher Schritt, der zum Ausführen dieses Begleit-Repositories erforderlich ist.

Trade-offs

Numerik in Python belassen

Node eignet sich gut für Orchestration, HTTP-Serving und Streaming. Dauerhafte CPU-bound-Berechnungen blockieren den Main-Event-Loop-Thread. Belassen Sie vLLM und Training-Code in Python, sofern ein gemessener Workload keine Verlagerung rechtfertigt.

Jede Grenze zur Runtime validieren

Eine TypeScript-Annotation prüft weder einen HTTP-Body noch eine Environment Variable, ein vom Model generiertes Tool-Argument oder eine aus jsonb gelesene Zeile. Jede Grenze benötigt ein Runtime-Schema.

SDK-Änderungen kapseln

AI SDK 6 ersetzte Experimental_Agent durch ToolLoopAgent und benannte die Agent-Einstellung system in instructions um (AI-SDK-6-Migrationsleitfaden). Das Begleit-Repository ruft streamText direkt auf AI SDK 7 auf und stellt seinen eigenen AgentEvent-Stream bereit. Diese Grenze hält die HTTP-Route unverändert, wenn sich SDK-Code ändert.

Den handgeschriebenen Loop überspringen, wenn die Deadline wichtiger ist

Wenn Sie den Loop selbst schreiben, lernen Sie, welches Verhalten das SDK übernimmt. Wenn Sie zuerst ausliefern müssen und keinen Grund haben, Validierungsfehler anzupassen, beginnen Sie mit dem SDK.

Zentrale Erkenntnisse

  1. Installieren Sie Node 24 und pnpm. Verwenden Sie anschließend die Scripts des Repositorys: pnpm demo, pnpm dev:api, pnpm dev:worker und pnpm check. Die Scripts verbergen die niedriger angesiedelten Runtime- und Type-Checker-Befehle.
  2. Runtime-Validierung ist strukturell notwendig. Zod ist der gewählte Validator dieses Projekts. Statische Typen prüfen weder HTTP-Bodies noch Environment Variables, Model-Output oder Datenbankzeilen. Mit Zod deklarieren Sie ein Runtime-Schema und leiten den TypeScript-Typ mit z.infer ab.
  3. Der Stack lässt sich größtenteils sauber abbilden: pnpm für uv, Hono für FastAPI, Drizzle für SQLAlchemy, Vitest für pytest und Biome für Ruff. Drei Zeilen sind keine direkten Ersetzungen: Validierung, Type-Checking und Job-Queue.
  4. Schreiben Sie einen Agent Loop einmal selbst, wenn Sie die verborgenen Pfade verstehen oder anpassen müssen: Fragment-Akkumulation, Validierung und Tool-Error- Feedback.
  5. Machen Sie den Loop zu einem async Generator. Die HTTP-Route konsumiert seine AgentEvent-Werte, gibt SSE-Frames aus, akkumuliert den Text und persistiert ihn nach dem Stream. Tests konsumieren den Generator separat, ohne Netzwerk und ohne API-Key.
  6. Postgres kann eine At-Least-Once-Queue bereitstellen. Machen Sie Handler idempotent und erneuern Sie das Lease bzw. dimensionieren Sie es für lang laufende Jobs über deren maximale Laufzeit. Fügen Sie BullMQ hinzu, wenn Sie Delays, Prioritäten oder Schedules benötigen.
  7. Verwenden Sie das bereitgestellte Dockerfile für die Produktion. Es paketiert die ausgewählte App, lädt TypeScript mit tsx, läuft als nicht privilegierter User und leitet Shutdown-Signale an den API-Prozess weiter.
