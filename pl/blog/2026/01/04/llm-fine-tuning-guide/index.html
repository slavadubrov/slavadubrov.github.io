Przewodnik po fine-tuning LLM: LoRA, QLoRA, Unsloth, Axolotl

Viacheslav Dubrov

2026-01-04 · Zaktualizowano 2026-09-12 · 22 min · Inżynieria modeli

Tłumaczenie automatyczne

Ten artykuł został automatycznie przetłumaczony z angielskiego oryginału.

Ten przewodnik jest przeznaczony dla inżynierów Pythona, którzy decydują, czy i jak przeprowadzić fine-tuning dużego modelu językowego. Dowiesz się, kiedy wybrać fine-tuning zamiast promptingu lub wyszukiwania oraz jak wybierać między metodami takimi jak LoRA i QLoRA. Przewodnik wyjaśnia również, jak przygotować dane, ewaluować wytrenowany model i zaplanować jego deployment.

Przykłady objaśniają konfiguracje i mechanizmy kontrolne. Nie są zweryfikowaną receptą na trening end-to-end; sekcja praktyczna oddziela komendy z repozytorium towarzyszącego od proponowanej konfiguracji treningowej.

Krótkie porównanie tych opcji znajdziesz w artykule Fine-Tuning vs RAG vs Prompting.

Czy w ogóle warto przeprowadzać fine-tuning?

Zanim zaczniesz zużywać godziny GPU, zdecyduj, czy fine-tuning jest właściwym narzędziem do rozwiązania konkretnego problemu.

Byte mówi

Jeśli jedynym brakującym zachowaniem jest poprawny JSON, najpierw przetestuj constrained decoding na oryginalnych weights. Trening to długa droga, aby odkryć brakujący nawias klamrowy.

Fine-tuning zmienia zachowanie zapisane w weights. Retrieval dostarcza dowodów w czasie inferencji, dlatego jest lepszym punktem wyjścia dla faktów, które się zmieniają lub wymagają cytowania. Nowe dokumenty stają się dostępne dopiero po ingestion i indeksowaniu; sprawdź, czy ich aktualność odpowiada wymaganiom.

Jasne prompty i przykłady są tańsze w iterowaniu niż nowy run treningowy. Mogą już rozwiązać problem stylu lub podążania za instrukcjami. Fine-tuning może ograniczyć liczbę powtarzanych prompt tokens, ale latency serwowania zależy od modelu, długości wyjścia, hardware’u i implementacji; aktualizacja weights sama w sobie nie przyspiesza działania.

W przypadku składni biblioteki takie jak xgrammar i outlines maskują niepoprawne next tokens zgodnie ze wspieranym schematem lub grammar. Pomyślnie zakończona constrained generation należy do tego języka. Truncation i inne niekompletne generacje obsługuj osobno, a przed użyciem waliduj wynik. Constraint nie sprawi, że customer ID będzie prawdziwy ani że wybór narzędzia będzie właściwy. Zmierz latency na swoim backendzie, zamiast zakładać stały narzut.

Spraw, by uzasadnienie biznesowe było mierzalne

Fine-tuning może ograniczyć liczbę powtarzanych prompt tokens lub pozwolić mniejszemu modelowi osiągnąć wymagany poziom, ale żadna z tych oszczędności nie jest automatyczna. Oblicz punkt break-even na podstawie własnego ruchu i cen:

[ \text{break-even requests} = \frac{\text{training + evaluation + deployment cost}} {\text{baseline cost/request} - \text{tuned cost/request}} ]

Jeśli mianownik jest mały, ujemny albo opiera się na nieudowodnionym założeniu dotyczącym jakości, projekt nie ma jeszcze uzasadnienia ekonomicznego.

[!TIP] Konfiguracja hybrydowa Częstą architekturą jest mniejszy model dostosowany do zadania oraz retrieval dla zmieniających się faktów. Traktuj większy model z promptingiem jako baseline i zachowaj mniejszy model tylko wtedy, gdy spełnia te same, specyficzne dla zadania progi jakości i bezpieczeństwa.

Rodzaje fine-tuning

Fine-tuning może przyjmować trzy główne formy. Różnią się rodzajem danych, których wymagają, oraz tym, czego uczą model.

1. Continued pre-training (self-supervised)

Trenujesz model bazowy na dodatkowym raw text, używając następnego tokena w każdej sekwencji jako targetu treningowego. To self-supervised learning: tekst dostarcza własne targety, podobnie jak w oryginalnym pre-trainingu.

Kiedy używać:

  • Domena ma słownictwo, którego model bazowy nigdy nie widział (medycyna, prawo, wewnętrzne codebase’y).
  • Masz duże ilości tekstu domenowego, ale nie masz oznaczonych par (input, output).
  • Model bazowy myli terminologię specyficzną dla domeny.

Przykład: trening na milionach notatek klinicznych, aby model przyswoił skróty medyczne, nazwy leków i workflows kliniczne.

2. Supervised fine-tuning (SFT)

SFT trenuje się na oznaczonych parach (input, output). Pokazujesz modelowi dokładne wyjście, którego oczekujesz dla każdego inputu.

Kiedy używać:

  • Masz konkretne zadanie z ustalonym formatem input/output.
  • Masz wysokiej jakości dane oznaczone, nawet jeśli jest ich niewiele.
  • Potrzebujesz przewidywalnego zachowania dla znanego kształtu inputu.

Przykład: trening na parach (opis zapytania SQL, kod SQL) dla text-to-SQL. Ten stały przedział kalendarzowy zakłada, że signup_date jest zapisane w UTC:

{
    "input": "Get users who signed up in August 2026 (UTC)",
    "output": "SELECT * FROM users WHERE signup_date >= '2026-08-01' AND signup_date < '2026-09-01'"
}

3. Instruction tuning

Instruction tuning to szczególny przypadek SFT, którego celem jest nauczenie modeli wykonywania szerokiego zakresu instrukcji w języku naturalnym. Dane treningowe to pary (instruction, response) obejmujące wiele różnych zadań.

Kiedy używać:

  • Chcesz zbudować asystenta ogólnego przeznaczenia (takiego jak ChatGPT lub Claude).
  • Model musi obsługiwać zróżnicowane, otwarte prośby.
  • Budujesz interfejs chatowy.

Przykład: trening na tysiącach różnorodnych instrukcji, takich jak „Podsumuj ten artykuł”, „Napisz wiersz o X” czy „Wyjaśnij Y prostymi słowami”.

Pipeline fine-tuning w 7 etapach

Fine-tuning to pipeline, a nie pojedyncza komenda. Każdy etap ma własne failure modes, a pominięcie któregoś z nich zwykle ujawnia się później jako słaby model.

Każdy etap opiera się na poprzednim:

  1. Przygotowanie danych — Zdefiniuj jednostkę ewaluacji, podziel dane, a następnie je oczyść i sformatuj
  2. Wybór modelu — Wybierz właściwy model bazowy i załaduj weights
  3. Setup treningu — Skonfiguruj hardware, hyperparameters i strategię optymalizacji
  4. Fine-tuning — Uruchom trening SFT, DPO lub ORPO
  5. Ewaluacja — Zmierz wydajność benchmarkami i zweryfikuj jakość
  6. Deployment — Wyeksportuj i serwuj model
  7. Monitoring — Śledź wydajność, utrzymuj model i iteruj

[!WARNING] Dane są fundamentem Trening odtwarza systematyczne wady obecne w przykładach. Przed poświęceniem czasu na sweepy optymalizatora sprawdź labels, leakage, coverage i zgodność z politykami.

Etap 1: Przygotowanie danych

Wiele projektów fine-tuning kończy się niepowodzeniem właśnie tutaj, a nie podczas treningu. Nowoczesne przygotowanie danych to coś więcej niż uruchomienie regexu na CSV.

Pięć transformacji po podziale źródeł

Przypisz grupy źródłowe do training lub evaluation, zanim przekształcisz wiersze. Ticket supportowy i każda jego przeredagowana wersja muszą pozostać w tej samej partycji. Przed przypisaniem grup połącz znane near-duplicates w klastry, a po czyszczeniu ponownie sprawdź dane między partycjami. Zamroź evaluation set; augmentuj wyłącznie dane treningowe.

Wypisz błędy, które przykłady powinny nauczyć model korygować, a następnie zdefiniuj wymagane fields i labels każdego wiersza. Dobierz tools do tych kroków; DataTrove i Distilabel mogą pomóc przy większych datasetach.

1. Ingestion i filtering

  • Działanie: usuń uszkodzone UTF-8 i treści niezwiązane z zadaniem. Oznacz refusals zgodnie z polityką: zachowaj poprawne refusals jako training targets i przypadki ewaluacyjne; wykluczaj tylko refusals niepoprawne lub niezwiązane z zadaniem.
  • Tools: Trafilatura do ekstrakcji oraz modele fastText do identyfikacji języka do language ID; rozproszone modele lid.176 rozpoznają 176 języków.

2. Polityka danych wrażliwych

  • Działanie: zdecyduj, czego model może się nauczyć, a następnie zgodnie z wymaganiami redaguj, tokenizuj lub wykluczaj pola osobowe i poufne.
  • Tools: Microsoft Presidio lub scrubadub.
  • Dlaczego: detektor jest tylko jednym z mechanizmów kontroli; nadal obowiązują wymagania dotyczące provenance, zgody, retencji, dostępu i usuwania.

3. Deduplikacja (MinHash LSH)

  • Działanie: usuń near-duplicates, aby ograniczyć powtórzenia i ryzyko leakage; nie zapobiega to memorization.
  • Tools: DataTrove dobrze radzi sobie z przetwarzaniem w skali terabajtów.

4. Synthetic augmentation, jeśli potrzebne

  • Działanie: użyj odpowiedniego modelu nauczyciela do przepisania przykładów treningowych na pary instruction-response, zachowując ich source IDs. Nie augmentuj partycji held-out.
  • Tools: Distilabel.
  • Walidacja: próbkuj outputy modelu nauczyciela, sprawdzaj je według tej samej rubric co human labels i raportuj wyniki osobno dla przykładów syntetycznych i napisanych przez ludzi. Taki podzbiór ewaluacyjny nazywa się slice; inne przydatne slices obejmują język i typ zadania.

5. Formatting

  • Działanie: przekonwertuj dane do standardowego formatu (Alpaca lub ShareGPT).

Przykłady formatów danych

Format Alpaca (instruction-following):

{
    "instruction": "Summarize the following text.",
    "input": "The text to be summarized...",
    "output": "This is the summary."
}

Przechowywanie w stylu ShareGPT (konwersacyjne):

{
    "conversations": [
        { "from": "user", "value": "Hello, who are you?" },
        { "from": "assistant", "value": "I am a helpful AI assistant." }
    ]
}

Co faktycznie ma znaczenie

  • Coverage przed volume. Dodawaj przykłady reprezentujące różne failure modes, a nie powtórzenia łatwego majority case.
  • Cleanliness. Odrzucaj nieistotny tekst, normalizuj whitespace i zachowuj spójne formatowanie.
  • Balance. Zachowuj istotne rzadkie przypadki i raportuj wydajność dla każdego slice.
  • Separation. Dziel dane według source, user, document lub time, gdy losowy podział wierszy powodowałby wyciek near-duplicates.
  • Provenance. Dla każdej wersji datasetu zapisuj source, license lub permission, historię transformacji i ścieżkę usuwania.

Etap 2: Wybór modelu i hardware

Model bazowy i jego minimalne wymagania dotyczące pamięci GPU determinują, co możesz wytrenować.

Zacznij od najmniejszego modelu bazowego, który już przechodzi niepodlegające negocjacjom baseline checks. Potwierdź:

  • warunki licencji i redystrybucji dla planowanego produktu;
  • zachowanie językowe, domenowe, związane z tool use i bezpieczeństwem przed adaptacją;
  • zgodność tokenizera i chat template z datasetem;
  • wymagany przez realne przykłady maksymalny context i zachowanie truncation;
  • wsparcie zarówno w training frameworku, jak i docelowym serving engine.

Fine-tuning jest etapem adaptacji, a nie naprawą nieodpowiedniego base modelu. Jeśli model nie radzi sobie z capabilities, których dataset nie obejmuje, wybierz inny base, zanim uruchomisz kolejne epochs.

Szacuj konkretny run, nie tier marketingowy

Nie istnieje trwała tabela „rozmiar modelu → GPU”. Peak memory zmienia się wraz z precision weights, liczbą trainable parameters, sequence length, micro-batch size, activation checkpointing, implementacją attention i narzutem frameworka. Zacznij od oszacowania pamięci, a następnie wykonaj krótki smoke test dla maksymalnej długości na dokładnie tym stacku.

Oryginalna praca o QLoRA zmieściła model LLaMA 65B na jednej GPU 48 GB w swoim konkretnym setupie. To użyteczna granica, a nie obietnica, że każda współczesna architektura 70B, context length, kernel lub trainer zmieści się na tym samym urządzeniu.

Matematyka pamięci

Dla modelu z PPP parametrami same weights wymagają około 2P2P2P bajtów w BF16/FP16 lub 0.5P0.5P0.5P bajtów przy czterech bitach, przed uwzględnieniem metadanych kwantyzacji i runtime buffers. Trening w stylu Full Adam dodaje gradients, optimizer states i często master weights o wyższej precision. LoRA pozwala uniknąć większości pamięci na trainable state; QLoRA dodatkowo zmniejsza footprint zamrożonych base weights. Activations nadal mogą dominować przy długich sequence lengths.

Użyj następującego workflow:

  1. Wybierz najdłuższą sekwencję i micro-batch, które musisz obsłużyć.
  2. Oszacuj weights i trainable state, zostawiając zapas na activations i kernels.
  3. Wykonaj jeden forward/backward step przy maksymalnej długości.
  4. Zapisz peak allocated i reserved memory.
  5. Dopiero potem skaluj batch size, rank, sequence length lub liczbę GPUs.

Etap 3: Setup treningu i metody

Od zapisanych wierszy do training targets

ShareGPT to kształt datasetu; ChatML to jedna z konwencji serializacji. Przekształć from/value na roles i fields akceptowane przez trainer, a następnie użyj chat template wybranego modelu. Nie zastępuj tokenów ChatML tylko dlatego, że dane są konwersacyjne.

Dla pokazanego wyżej wiersza z greetingiem znormalizowane messages to:

messages = [
    {"role": "user", "content": "Hello, who are you?"},
    {"role": "assistant", "content": "I am a helpful AI assistant."},
]
# Inspection step after loading the selected model's tokenizer:
rendered = tokenizer.apply_chat_template(
    messages, tokenize=False, add_generation_prompt=False,
)
print(rendered)

Przed treningiem sprawdź rzeczywiście zserializowany wiersz: delimitery ról, end-of-turn tokens i tool schemas muszą być zgodne z inferencją. W przypadku wiersza z tool use zachowaj definicje narzędzi, tool calls asystenta i wyniki narzędzi jako osobne fields. Sprawdź, czy truncation nie usuwa supervised response ani nie ucina argumentu narzędzia w połowie.

Loss masking określa, za przewidywanie których tokens model otrzymuje nagrodę. W full-sequence training user, system, tool i assistant text mogą wszystkie wnosić wkład. W assistant-only training te context tokens pozostają widoczne dla attention, ale ich labels są ignorowane (często jako -100); uwzględniane są tylko assistant spans. W przypadku tego greetingu odpowiedź powinna być targetem, a pytanie użytkownika nie — jeśli celem jest zachowanie assistant-only.

Dokumentacja SFT w TRL wspiera assistant_only_loss=True dla conversational datasets, których templates ujawniają generation spans. Template bez tych spans nie może dostarczyć takiej maski. Dla prompt/completion datasets istnieje osobna opcja completion_only_loss. Przed włączeniem którejkolwiek z nich sprawdź jeden ztokenizowany batch i zdekoduj tokens z non-ignored labels. Następnie powtórz to z tool conversation i przykładem o maksymalnej długości. Poniższa przykładowa konfiguracja treningowa celowo używa full-sequence loss; assistant-only training wymaga dodatkowej kontroli template i maski.

Wybierz sequence length na podstawie rozkładu danych i wykonaj memory check dla maksymalnej długości z Etapu 2. Packing umieszcza kilka krótszych przykładów w jednej sekwencji treningowej. Zacznij bez niego, aby granice wierszy były łatwe do sprawdzenia. Packing benchmarkuj dopiero po potwierdzeniu, że zserializowane wiersze i labels są poprawne.

Full fine-tuning vs PEFT

Full fine-tuning (FFT) aktualizuje każdy weight, więc gradients i optimizer state skalują się z całym modelem. Peak memory nie można wywnioskować wyłącznie z liczby parametrów, ale jest znacznie większy niż pamięć potrzebna do załadowania weights do inferencji.

Parameter-efficient fine-tuning (PEFT) trenuje tylko mały podzbiór parametrów i zamraża resztę. Matematyka staje się znacznie przyjaźniejsza.

LoRA: punkt wyjścia

LoRA (Low-Rank Adaptation) zamraża pre-trained matrix i reprezentuje nauczoną aktualizację za pomocą dwóch mniejszych matrices. Oryginalna praca uzasadnia to hipotezą, że użyteczne aktualizacje adaptacyjne mają niski intrinsic rank.

Tutaj dind_{in}din​ to input width warstwy, a doutd_{out}dout​ to jej output width. Rank rrr jest mniejszym wspólnym wymiarem dwóch trainable matrices: mniejszy rank oznacza mniej trainable parameters. Ustawienie α\alphaα kontroluje skalę aktualizacji za pomocą ilorazu α/r\alpha/rα/r.

Dla zamrożonej matrix W0∈Rdout×dinW_0 \in \mathbb{R}^{d_{out} \times d_{in}}W0​∈Rdout​×din​ LoRA uczy się:

  • A∈Rr×dinA \in \mathbb{R}^{r \times d_{in}}A∈Rr×din​
  • B∈Rdout×rB \in \mathbb{R}^{d_{out} \times r}B∈Rdout​×r

Dostosowana warstwa ma postać:

W′=W0+αrBAW' = W_0 + \frac{\alpha}{r}BAW′=W0​+rα​BA

Adapter ma r(din+dout)r(d_{in}+d_{out})r(din​+dout​) trainable parameters zamiast dindoutd_{in}d_{out}din​dout​ dla tej matrix. Dla kwadratowej matrix o szerokości 4 096 i rank 16 oznacza to 128× redukcję trainable parameters dla tej matrix. Oszczędności dla całego modelu zależą od tego, które matrices otrzymują adapters.

DoRA: LoRA z dekompozycją weights

DoRA (Weight-Decomposed Low-Rank Adaptation) oddziela magnitude każdego weight vector od jego direction. Praca o DoRA stosuje aktualizację LoRA do komponentu kierunkowego, ucząc magnitude osobno.

Jak to działa:

Zamiast traktować weights jako pojedynczą całość, DoRA dzieli pre-trained weights na dwa components:

  1. Magnitude — trainable value dla każdego weight vector.
  2. Direction — znormalizowany vector aktualizowany przez low-rank matrices.

W zwartej notacji column-wise:

W′=mV+BA∥V+BA∥cW' = m \frac{V + BA}{\lVert V + BA \rVert_c}W′=m∥V+BA∥c​V+BA​

gdzie:

  • m = magnitude (trainable)
  • V=W0V = W_0V=W0​ = frozen initial matrix; normalizuj po dodaniu BABABA
  • BABABA = learned low-rank directional update
  • ∥⋅∥c\lVert \cdot \rVert_c∥⋅∥c​ = column-wise normalization

Co daje ta dodatkowa struktura:

  • Więcej degrees of freedom niż standardowe LoRA, ponieważ magnitude może zmieniać się niezależnie.
  • Lepsze wyniki niż LoRA w kilku konfiguracjach opisanych przez autorów pracy.
  • Dodatkowe parameters i computation, dlatego zysk należy zweryfikować dla własnego task i serving path.

Łączenie adapterów w multi-task learning

Oddzielne adapters pozwalają jednemu zamrożonemu base obsługiwać wiele zadań. Możesz kierować requests do adaptera, serwować wiele adapters z jednego engine’a, jeśli jest to wspierane, albo utworzyć offline merged candidate. Łączenie może powodować interference, dlatego ewaluuj merged artifact zamiast zakładać, że źródłowe adapters połączą się bez problemów.

Typowe metody merging:

  1. Concatenation — połącz adapter parameters i zwiększ effective rank. Szybko i prosto.
  2. Linear combination — weighted sum adapters. Zapewnia dodatkowe pokrętła konfiguracyjne.
  3. SVD — matrix decomposition do merging. Bardziej elastyczne, ale wolniejsze.

Przykład: jeden adapter do summarization, drugi do translation, połączone w jeden model multi-task.

Etap 4: Fine-tuning i preference alignment

SFT uczy się na demonstrations. Preference optimization uczy się natomiast na porównaniach, takich jak „chosen response A jest lepsza niż rejected response B”. Używaj go tylko wtedy, gdy preference pair jest właściwą etykietą dla danego błędu; factual correctness i policy compliance często wymagają silniejszych evaluatorów niż global preference.

RLHF oparte na PPO

RLHF oznacza reinforcement learning from human feedback. Policy to language model generujący responses; reward model ocenia te responses na podstawie preferences wyuczonych z porównań wykonanych przez ludzi. Recipe oparte na PPO ma trzy stages:

  1. SFT — nauka zadania.
  2. Reward model — trening na human preferences (chosen vs rejected).
  3. PPO (Proximal Policy Optimization) — generowanie responses i aktualizacja language model, aby zwiększyć ich reward scores.

Koszt operacyjny wynika z liczby elementów:

  • Skomplikowane w implementacji i utrzymaniu.
  • Drogie — trenujesz wiele models.
  • Sampling z modelu, który jest aktualnie trenowany, wymaga kontroli niestabilnych aktualizacji oraz responses wykorzystujących reward model bez realizacji zadania.

DPO

DPO (Direct Preference Optimization) usuwa osobny reward model i reinforcement-learning loop. Promuje chosen responses, jednocześnie zniechęcając do dużych zmian względem ustalonego modelu początkowego, nazywanego reference model. Praca o DPO wyprowadza ten objective przez ograniczenie tego, jak daleko probabilities responses mogą odejść od reference; matematycznym ograniczeniem jest KL-divergence constraint.

Preference pair zawiera ten sam prompt i dwie candidate responses. Ten skrócony wiersz pokazuje jego fields; rzeczywiste labels potrzebują kompletnych responses i powodu, dla którego jedna jest preferowana:

{
    "prompt": "Explain quantum computing",
    "chosen": "Quantum computing uses qubits...",   # Preferred response
    "rejected": "Well, it's complicated..."        # Non-preferred response
}

Zmiany operacyjne:

  • Prostsza ścieżka code (bez osobnego reward model i RL loop).
  • Training na zapisanych preference pairs zamiast generowania nowych responses do reward scoringu przy każdej aktualizacji.
  • Stały reference model albo jego zapisane log probabilities dla training responses w standardowej formulacji.

DPO łatwiej prototypować niż pełny pipeline PPO, ale nie jest automatycznym ulepszeniem jakości. Wyniki zależą od starting policy, jakości pairs, loss settings, efektów długości i protokołu ewaluacji. Porównaj je z SFT checkpoint na tych samych held-out preference i task suites.

ORPO

ORPO (Odds-Ratio Preference Optimization) łączy SFT negative-log-likelihood loss z odds-ratio penalty dla rejected responses. Usuwa osobny reference model i może połączyć task learning oraz preference optimization w jednym runie.

Jak to działa: ORPO używa combined loss, który wykonuje jednocześnie dwie rzeczy:

  1. Maksymalizuje likelihood chosen response (uczenie zadania).
  2. Nakłada karę na rejected response za pomocą odds-ratio term (uczenie preferences).

Warto znać następujące hyperparameters (TRL 1.12.0 API):

# API shown in TRL 1.12.0 documentation
from trl.experimental.orpo import ORPOConfig

config = ORPOConfig(
    learning_rate=8e-6,  # Very low, as recommended by the ORPO paper
    beta=0.1,            # Controls strength of preference penalty
    # ... other params
)
  • Learning rate: w pracy użyto niskich wartości w eksperymentach; dostosuj ją do modelu, batcha i danych, zamiast traktować jedną wartość jako uniwersalną regułę.
  • Beta: kontroluje udział preference term względem SFT term.

Kompromis:

  • Jeden training stage zamiast dwóch.
  • Brak reward model.
  • Brak reference-model forward pass.
  • Coupled run: jeśli task learning lub preference behavior ulegnie regresji, pipeline nie ma pośredniego SFT checkpoint do analizy.

Wybieraj na podstawie danych i projektu ewaluacji:

  • Użyj DPO, jeśli masz już satysfakcjonujący SFT checkpoint i chcesz przeprowadzić prostszy offline preference experiment.
  • Przetestuj ORPO, jeśli reference-free, single-stage objective pasuje do danych i ograniczeń operacyjnych.
  • Użyj PPO-based RLHF, jeśli online sampling względem jawnego learned reward jest wymaganiem i możesz monitorować reward exploitation.

Żadna z tych metod nie jest domyślnym wyborem dla wszystkich zadań. Zachowaj SFT-only baseline i raportuj zarówno task metrics, jak i preference metrics.

Frameworki fine-tuning

Frameworki częściowo się pokrywają i szybko się zmieniają. Wybierz je na podstawie execution path, który musisz obsłużyć, przypnij versions i zachowaj konfigurację treningową na tyle przenośną, aby można ją było odtworzyć poza notebookiem.

Unsloth — szybkość i efektywność pamięciowa

Unsloth integruje się z Hugging Face trl i transformers oraz udostępnia optimized kernels, checkpointing i quantized fine-tuning paths dla wspieranych models.

  • Custom Triton GPU kernels dla attention, RoPE i cross-entropy, które pomijają narzut PyTorch.
  • Memory-efficient backprop, które przelicza activations podczas backward pass zamiast przechowywać je w pamięci.
  • Fused operations, które łączą wiele kroków (layer norm + linear i podobne) w pojedyncze wywołania GPU.
  • 4-bit quantization zintegrowana bezpośrednio ze ścieżką QLoRA, z optimized dequantization.

[!IMPORTANT] Kolejność importów ma znaczenie Stosuj kolejność importów z przykładu Unsloth dla przypiętej wersji. Unsloth stosuje patches podczas importu, dlatego import przed trl i transformers pozwala uniknąć braku optymalizacji lub błędów zależnych od wersji.

# Correct order
from unsloth import FastLanguageModel  # Must be first!
from trl import SFTTrainer
from transformers import TrainingArguments

# Avoid this order with Unsloth's patched path
from trl import SFTTrainer
from unsloth import FastLanguageModel

Najlepsze zastosowania: trening na jednej GPU, prototyping, notebooki Colab i sytuacje, w których kontrolujesz rachunek za GPU.

Publikowane liczby dotyczące szybkości i pamięci różnią się w zależności od modelu, sequence length, batch, precision i hardware. Zmierz tokens per second i peak memory we własnym runie, zamiast traktować nagłaśniany współczynnik jako właściwość frameworka.

Etap 5: Ewaluacja

Byte mówi

Jeśli ten sam support ticket pojawia się w training i evaluation, wyższy score może nagradzać odtworzenie tego ticketu. Podziel dane według ticketu przed utworzeniem wierszy lub rewrite’ów.

Ustal test cases, scoring rules i passing thresholds przed pierwszym runem. Co najmniej porównaj tuned checkpoint z dokładnie tym samym untuned base przy identycznym prompt, decoding settings i tool environment. Raportuj aggregate quality dopiero po sprawdzeniu failure slices, które projekt miał poprawić.

Śledź cztery grupy:

  1. Target task: exact match, execution success, human rubric lub inny wynik powiązany z use case’em.
  2. Regression: ogólne abilities i wcześniej wspierane task slices, które adaptacja może pogorszyć.
  3. Safety and policy: refusals, data leakage, prompt injection lub constraints specyficzne dla domeny.
  4. Operations: latency, throughput, memory, artifact size i koszt przy docelowej konfiguracji serwowania.

Automated benchmarks

Użyj lm-evaluation-harness do sprawdzenia odpowiednich standardowych zadań obok testów produktu. Ta komenda wymaga merged Hugging Face checkpoint. Jej przykładowa ścieżka to merged output legacy companion z Etapu 6; nie ładuje adaptera zapisanego przez proponowaną konfigurację powyżej. Zastąp ją merged checkpoint, który zamierzasz ewaluować:

lm_eval --model hf \
    --model_args pretrained=./outputs/unsloth-nemotron-function-calling-merged \
    --tasks hellaswag,arc_easy,mmlu \
    --batch_size 8

LLM-as-judge

W przypadku jakości subiektywnej większy model może pomóc w scoringu, ale skalibruj go względem przykładów ocenionych przez ludzi i ukryj tożsamość kandydata:

judge_prompt = """
Rate this response from 1-5 on:
- Relevance
- Accuracy
- Formatting

Response: {model_output}
Expected: {ground_truth}
"""

Ewaluacja specyficzna dla domeny

Odłóż realne przykłady według source, user, document lub time, aby near-duplicates nie wyciekały między splitami. W przypadku function calling waliduj pełną trajectory: wybór narzędzia, arguments, execution result, recovery i final response. Przy małej próbie raportuj confidence intervals lub paired win/loss counts i sprawdź każdą regresję w critical slice.

Etap 6: Deployment i formaty wyjściowe
