Korzystanie z narzędzi przez agentów AI: MCP, CLI, Skills i wykonywanie kodu

Viacheslav Dubrov

2026-03-24 · Zaktualizowano 2026-09-12 · 23 min · Agenci AI

Tłumaczenie automatyczne

Ten artykuł został automatycznie przetłumaczony z angielskiego oryginału.

Ten artykuł jest przeznaczony dla inżynierów budujących agentów korzystających z narzędzi. Porównuje wywoływanie narzędzi przez JSON, MCP, polecenia CLI i kod wykonywany w sandboxie, aby ułatwić wybór mechanizmu wykonawczego odpowiedniego dla danego obciążenia oraz wykorzystanie Skills do sterowania tym procesem.

Skills dostarczają instrukcji dotyczących wyboru narzędzi i korzystania z nich. Harness to zwykły program otaczający model: buduje prompty, sprawdza proponowane wywołanie, wykonuje zatwierdzone wywołanie i decyduje, kiedy zadanie jest zakończone.

Ten trzeci artykuł z serii dodaje warstwę działania do pętli rozumowania z części 1 i pamięci z części 2. Część 4 analizuje kontrolę polityki przed wykonaniem, a część 6 — harness, który uruchamia zarówno wywołanie, jak i tę kontrolę.

Historia narzędzi zmieniła się w latach 2025–2026. MCP, Model Context Protocol, dał dostawcom jeden wspólny sposób udostępniania usług zewnętrznych. Agenci wykonujący kod pokazały, że model może czasem efektywniej komponować mały program niż wysyłać długą sekwencję wywołań JSON. Anthropic odnotował 98,7% redukcję liczby tokenów w jednym przepływie pracy Google Drive–Salesforce, a artykuł CodeAct wykazał wzrost skuteczności zadań nawet o 20 punktów procentowych w swoim środowisku benchmarkowym. Wyniki te dotyczą opisanych zadań i harnessów, a nie uniwersalnej przewagi wykonywania kodu.

W dalszej części zastosowano zasady projektowania Agent-Computer Interface (ACI) do Market Analyst Agent — małego agenta badawczego opartego na LangGraph, którego zbudowałem w części 1. Agent pobiera dane rynkowe i tworzy raport analityczny.

Krótki przewodnik po wyborze interfejsu znajduje się w artykule Interfejsy narzędzi agentów AI.

TL;DR

Używaj wywołań narzędzi przez JSON dla małych, typowanych operacji, MCP dla współdzielonych integracji, poleceń CLI dla ugruntowanych lokalnych operacji, a kodu wykonywanego w sandboxie dla pracy wieloetapowej. Skills dostarczają wielokrotnego użytku instrukcji dotyczących korzystania z każdego z tych mechanizmów. Zanim wywołanie zostanie wykonane, harness musi sprawdzić jego argumenty i zatwierdzić jego efekt; sam schemat ani transport tego nie zapewniają. Niezależnie od wybranej powierzchni Agent-Computer Interface (ACI) powinien jasno opisywać działania, zwracać zwięzłe informacje zwrotne i umożliwiać odzyskiwanie po błędach.

Powierzchnie wykonawcze i wskazówki proceduralne

Pętla rozumowania proponuje wywołanie. Harness sprawdza jego argumenty oraz to, czy wywołanie jest dozwolone, następnie przekazuje je do narzędzia lub sandboxa i zwraca wynik. Schematy JSON, transport MCP, wrappery CLI i runnery kodu mogą ograniczać dane wejściowe, ale żaden z nich samodzielnie nie decyduje, czy żądane działanie jest dozwolone. Skills dostarczają instrukcji dotyczących tej ścieżki. Poszczególne powierzchnie wykonawcze różnią się kosztami tokenów, elastycznością i możliwościami egzekwowania reguł.

1. Wywoływanie narzędzi przez JSON: punkt odniesienia

Oryginalny wzorzec: definiujesz schematy narzędzi jako JSON, LLM emituje ustrukturyzowane wywołania funkcji, a kod je wykonuje. To dobrze znane podejście, które sprawdza się w przypadku małych zestawów narzędzi.

# Schema cost depends on its text, structure, and the model tokenizer
tools = [
    {
        "name": "get_stock_price",
        "description": "Get the current stock price for a ticker symbol",
        "input_schema": {
            "type": "object",
            "properties": {
                "ticker": {"type": "string", "description": "Stock ticker (e.g., NVDA)"}
            },
            "required": ["ticker"]
        }
    }
]

Policz tokeny w rzeczywistych schematach. Koszt zależy od ich długości oraz od liczby schematów ładowanych przez hosta; zwięzły lookup ceny i głęboko zagnieżdżony kontrakt API nie są równoważnymi jednostkami. Odroczone wyszukiwanie może wyeliminować konieczność ładowania całego rejestru.

2. MCP dla współdzielonych integracji

MCP to standard, wokół którego zbieżność osiągnęło większość dostawców. Serwer MCP to proces, który reklamuje listę narzędzi za pośrednictwem zdefiniowanego protokołu przewodowego — stdio dla procesu lokalnego oraz HTTP dla zdalnego. Agent uruchamia klienta MCP, który nawiązuje połączenie, pyta serwer o dostępne narzędzia i przekazuje mu wywołania modelu, dzięki czemu ten sam serwer działa z każdym klientem obsługującym protokół. W grudniu 2025 roku Anthropic przekazał protokół Linux Foundation, w ramach Agentic AI Foundation współzałożonej z OpenAI i Block. Google, Microsoft i AWS wspierają fundację jako członkowie platynowi. OpenAI dodało obsługę MCP w Responses API. Według ogłoszenia Anthropic o przekazaniu protokołu z grudnia 2025 roku ekosystem obejmował ponad 10 000 aktywnych publicznych serwerów MCP i ponad 97 mln miesięcznych pobrań SDK dla SDK języków Python i TypeScript.

MCP dobrze sprawdza się w integracjach SaaS między dostawcami (Figma, Notion, Salesforce), w usługach bez odpowiedników CLI oraz w środowiskach wymagających orkiestracji OAuth. Jego wartość polega na współdzielonej warstwie wykrywania i transportu. Governance nadal zależy od mechanizmów uwierzytelniania, autoryzacji, logowania i wdrażania po stronie serwera.

Wersja protokołu jest dziś praktyczną decyzją migracyjną. Wersja z 28.07.2026 zmienia zachowanie zakładane w starszych tutorialach:

ZmianaCo sprawdzić w integracji
Żądania bezstanowe zastępują handshake inicjalizacyjny i sesje transportoweWysyłaj metadane protokołu przy każdym żądaniu; użyj server/discover, aby sprawdzić obsługę. Zweryfikuj wersje klienta i serwera.
Żądania Multi Round-Trip zwracają InputRequiredResultObsłuż żądania dodatkowych danych wejściowych, a następnie ponów pierwotną operację z odpowiedziami i stanem kontynuacji.
Zadania trafiają do oficjalnego rozszerzenia tasksSprawdź obsługę rozszerzenia, zamiast zakładać istnienie starszego eksperymentalnego API zadań w jądrze.
Usunięto możliwość wznawiania SSEPrzerwany strumień odpowiedzi wymaga nowego żądania. Niezależnie zapobiegaj duplikowaniu efektów biznesowych.

Ta sama wersja oznacza Roots, Sampling, Logging i OAuth Dynamic Client Registration jako przestarzałe; wycofanie nie oznacza natychmiastowego usunięcia. Obecnie rejestracja klienta preferuje Client ID Metadata Documents. Istniejące integracje mogą nadal korzystać ze starszej wersji, dlatego przed przyjęciem nowej funkcji sprawdź zainstalowany SDK i kontrakt serwera.

Rzeczywistość produkcyjna jest bardziej złożona, niż sugerują nagłówkowe liczby.

Projekt Vulnerable MCP Project zbiera zgłoszenia dotyczące prompt injection, walidacji danych wejściowych, uwierzytelniania i kontroli sieci. Taki zbiór pomaga identyfikować przypadki testowe; bez mianownika określającego ekspozycję nie można na jego podstawie porównywać MCP z shellem ani bezpośrednimi wywołaniami API.

Najbardziej niepokoi mnie klasa ataków polegająca na zatruwaniu narzędzi. Invariant Labs zademonstrowało, że zatrute narzędzia MCP mogą eksfiltrować dane, nawet jeśli nigdy nie zostaną wywołane. Do uruchomienia ataku wystarczy, że model odczyta metadane narzędzia. Benchmarki MCPTox, testujące 20 agentów LLM wobec 45 rzeczywistych serwerów MCP, wykazały średnią skuteczność ataku na poziomie 72,8% dla o1-mini w scenariuszu zatruwania narzędzi. To wynik benchmarku dla jednego modelu, a nie średnia dla 20 agentów ani wskaźnik incydentów w środowisku produkcyjnym.

Problemem operacyjnym jest narzut tokenów. Jeden zespół uruchamiający serwery MCP dla GitHub, Slacka i Sentry (łącznie około 40 narzędzi) stwierdził, że przed zadaniem przez użytkownika czegokolwiek wstrzykiwano 55 000 tokenów definicji schematów. Inny zespół zgłosił, że same definicje narzędzi zajmowały 143 000 z 200 000 dostępnych tokenów (72%).

Raport Anthropic dotyczący Tool Search Tool podaje przybliżone rozmiary kontekstu: 77 000 tokenów przed rozpoczęciem pracy oraz 8700 po odroczonym wyszukiwaniu, przy około 72 000 tokenów definicji narzędzi w tradycyjnej konfiguracji. Ładowane są tylko trzy do pięciu narzędzi potrzebnych dla danego żądania, ale przed wywołaniem pojawia się dodatkowy etap wyszukiwania; rozwiązanie jest mniej przydatne w przypadku małych, zwięzłych zestawów narzędzi, z których korzysta się często w każdej sesji.

Byte mówi

Ładuj tylko narzędzia potrzebne dla danego żądania. W ewaluacji Anthropic zmniejszyło to całkowity kontekst z około 77 000 do 8700 tokenów.

3. Skills pakują wiedzę ekspercką, a nie wykonanie

Agent skills to otwarty format służący do pakowania instrukcji i plików pomocniczych. Narzędzia zapewniają możliwości (co agenci mogą robić), a skills zapewniają wiedzę ekspercką (co agenci wiedzą o tym, jak wykonywać złożone zadania).

Format SKILL.md definiuje skill jako plik markdown z nagłówkiem YAML frontmatter. Otwarty standard wymaga wyłącznie name i description; poniższy przykład używa również dwóch rozszerzeń Claude Code, argument-hint i user-invocable, a także jego placeholdera argumentu pozycyjnego $0:

---
name: deploy
description: Deploy the application to production
argument-hint: "[environment]"
user-invocable: true
---
Deploy the application to the $0 environment (default: staging).
Steps:
1. Run the test suite
2. Build the production bundle
3. Deploy using the deploy script
4. Verify the deployment health check

Skills wykorzystują progressive disclosure. Przy uruchomieniu agent otrzymuje około 100 tokenów name i description. Pełny SKILL.md jest ładowany dopiero wtedy, gdy agent potrzebuje danego skilla, a następnie — w razie potrzeby — wskazane skrypty, dokumenty lub zasoby. Ten koszt początkowy jest znacznie niższy niż około 55 000 tokenów, które około 40 narzędzi MCP może zużyć, zanim rozpocznie się rozumowanie. Aktywny skill nadal dodaje swoje instrukcje i zasoby do kontekstu.

Używaj skills do wiedzy domenowej, procedur wieloetapowych oraz powtarzalnych zadań, takich jak migracje baz danych czy integracje płatności. Pasują do zadań, w których agent potrzebuje instrukcji, jak korzystać z istniejących możliwości.

4. Narzędzia CLI i shell

Interfejsy CLI mogą być znacznie tańsze pod względem kontekstu, gdy model zna już daną komendę. Scalekit odnotował różnicę od 4 do 32 razy w liczbie tokenów między ścieżkami CLI i MCP w 75 uruchomieniach. To studium przypadku mierzy konkretne narzędzia i zadania; nie zastępuje porównania opartego na własnych definicjach narzędzi i wynikach poleceń.

Szeroko udokumentowane polecenia, takie jak git, docker, kubectl, gh, curl i jq, często wymagają niewielkiej ilości wprowadzającego tekstu schematu. Mniej popularne lub wewnętrzne CLI nadal potrzebują odkrywalnej pomocy, przykładów i stabilnego, czytelnego maszynowo formatu wyjściowego.

Przewodnik Ugo Enyiohy “Writing CLI Tools That AI Agents Actually Want to Use” skodyfikował osiem zasad projektowych:

  1. Ustrukturyzowane dane wyjściowe są obowiązkowe — obsługuj --json
  2. Kody wyjścia sterują przepływem — używaj odrębnych kodów dla różnych typów błędów
  3. Polecenia powinny być idempotentne
  4. Samodokumentowanie --help z realistycznymi przykładami
  5. Projektuj z myślą o kompozycji — --quiet dla nieopakowanych wartości, obsługa stdin
  6. Udostępniaj flagi --dry-run i --yes
  7. Obsługuj introspekcję wersji
  8. Obsługuj uwierzytelnianie za pomocą zmiennych środowiskowych

CLI nie oferuje wykrywania na poziomie protokołu. Wywoływanie narzędzi przez JSON może przenosić typowane schematy, podczas gdy MCP standaryzuje wykrywanie narzędzi oraz — dla transportów HTTP — model autoryzacji. Żadne z tych rozwiązań samo w sobie nie zapewnia governance: host, serwer lub harness musi egzekwować politykę i rejestrować wywołania wymagane do audytu. Praktycznym ustawieniem domyślnym jest CLI dla programowania i lokalnych operacji oraz MCP dla współdzielonej integracji z usługami zewnętrznymi, gdy wykrywanie między klientami lub orkiestracja OAuth uzasadniają narzut serwera.

5. Wykonywanie kodu w pracy wieloetapowej

To zmiana w narzędziach agentów, którą uważam za najbardziej istotną. Zamiast emitować ustrukturyzowany JSON w celu wywoływania z góry zdefiniowanych funkcji pojedynczo, agent pisze skrypt w Pythonie lub bashu. Skrypt wywołuje wiele narzędzi, przetwarza wyniki za pomocą pętli i warunków, a do kontekstu modelu zwraca wyłącznie końcowe podsumowanie.

Anthropic wprowadził w becie Programmatic Tool Calling (PTC). Aktualny przewodnik API korzysta ze standardowego Messages API z code_execution_20260120 lub nowszym; pierwotne uruchomienie wersji beta jest kontekstem historycznym. Podstawą akademicką jest artykuł CodeAct (Wang i in., ICML 2024), w którym testowano 17 LLM i stwierdzono, że działania oparte na kodzie zapewniły do 20 punktów procentowych wyższą skuteczność zadań oraz o 30% mniej działań niż alternatywy oparte na JSON.

Trzy studia przypadków z pierwszej ręki pokazują, gdzie ten wzorzec może pomóc: poniżej Vercel i Cloudflare, a następnie przykład analizy wydatków Anthropic. Traktuj je jako dowody pochodzące od dostawców i ponownie wykonaj porównanie na własnych zadaniach.

  • Vercel przebudował d0, agenta danych przekształcającego język naturalny w SQL. Stary przykład kodu wymienia 17 narzędzi, a nowy udostępnia ExecuteCommand i ExecuteSQL. Vercel przedstawia tę przebudowę jako usunięcie 80% narzędzi, ale jest to nagłówkowe stwierdzenie Vercel, a nie odsetek wynikający z nazw narzędzi w przykładach. Dla pięciu reprezentatywnych zapytań Vercel raportuje wzrost skuteczności zadań z 4/5 do 5/5, skrócenie średniego czasu wykonania 3,5 raza (z 274,8 s do 77,4 s) oraz spadek średniego użycia tokenów o 37% (około 102 tys. do około 61 tys.). Ich sformułowanie brzmi: „Najlepsi agenci mogą być tymi, którzy mają najmniej narzędzi”.

  • Cloudflare opracował „Code Mode”, pozwalający agentom pisać TypeScript wywołujący ich API zamiast definiować schematy narzędzi, co zmniejsza narzut kontekstu. Ich argumentacja brzmi: „LLM mają w zbiorach treningowych ogromną ilość rzeczywistego TypeScriptu, ale tylko niewielki zestaw sztucznych przykładów wywołań narzędzi”.

Oto wzorzec z dokumentacji PTC Anthropic. W sekwencyjnym przykładzie analizy wydatków Anthropic tradycyjne wywoływanie narzędzi wymaga ponad 20 oddzielnych przebiegów inferencji, a dane pośrednie przepływają przez kontekst. Po wyszukaniu zespołu host obsługujący równoległe wywołania narzędzi może połączyć niezależne żądania dotyczące wydatków; liczba ponad 20 nie oznacza, że jest to niemożliwe. Anthropic informuje, że wygenerowany kod odpowiadający na to samo pytanie zmniejsza ilość danych trafiających do kontekstu z 200 KB surowych wierszy wydatków — ponad 2000 pozycji — do 1 KB wyników. Poniższy skrypt ilustruje ten przepływ sterowania za pomocą niestandardowych asynchronicznych adapterów Pythona: przyjmują argumenty pozycyjne i zwracają zdekodowane listy oraz słowniki. Nie jest to natywny kontrakt wrappera PTC.

# Custom decoded Python adapters, not native Claude PTC wrappers.
import asyncio
import json

async def main() -> None:
    team = await get_team_members("engineering")
    levels = list(set(member["level"] for member in team))
    budgets = dict(zip(
        levels,
        await asyncio.gather(*(get_budget_by_level(level) for level in levels)),
    ))
    expenses = await asyncio.gather(
        *(get_expenses(member["id"], "Q3") for member in team)
    )
    over_budget = []
    for member, employee_expenses in zip(team, expenses):
        total = sum(expense["amount"] for expense in employee_expenses)
        limit = budgets[member["level"]]["travel_limit"]
        if total > limit:
            over_budget.append(
                {"name": member["name"], "spent": total, "limit": limit}
            )
    # Only this final summary returns to the LLM context
    print(json.dumps(over_budget))

asyncio.run(main())

Aby używać natywnych wrapperów Claude PTC, przekazuj do każdego narzędzia jeden słownik argumentów, dekoduj zwrócony string JSON i używaj najwyższego poziomu await w zarządzanym środowisku wykonawczym zamiast uruchamiać pętlę zdarzeń za pomocą asyncio.run. Powyższy przykład z niestandardowymi adapterami zakłada zwykłe środowisko uruchomieniowe skryptu w Pythonie; nie jest też gotowym przykładem natywnego konektora MCP. Aktualne ograniczenia API PTC wykluczają narzędzia strict: true i natywne narzędzia konektora MCP z wywołań programistycznych oraz ograniczają rekurencyjne schematy. Niestandardowy most kod–MCP to osobna integracja. allowed_callers określa sposób, w jaki Claude wywołuje narzędzie; nie jest granicą autoryzacji. Host musi walidować każde zwrócone wywołanie, w tym nieoczekiwane wywołanie bezpośrednie.

LLM widzi tylko końcowe podsumowanie JSON, a nie tysiące pozycji wydatków przetworzonych w sandboxie. Oszczędność nie dotyczy wyłącznie raportów wydatków: osobny artykuł Anthropic o wykonywaniu kodu podaje najbardziej wyrazistą liczbę dla tego wzorca — przepływ Google Drive–Salesforce zmniejszył liczbę tokenów z około 150 000 do około 2000, czyli o 98,7%.

Aktualny przewodnik PTC opisuje także kontrprzykład: w zadaniach lotniczych, detalicznych i telekomunikacyjnych benchmarku tau2-bench PTC nie zmienił wyników, a koszt wzrósł o około 8%. W osobnym benchmarku zarządzania projektami z 75 narzędziami zmniejszył liczbę rozliczanych tokenów wejściowych o około 38%, bez zmiany dokładności. Te wewnętrzne ewaluacje wskazują wyłącznie produkcyjny model Claude, bez dokładnego identyfikatora. Małe sekwencyjne przepływy pracy mogą nie zapewniać oszczędności wystarczających do zrównoważenia narzutu kontenera i generowania kodu.

Wydajność tokenowa jest potencjalną korzyścią. Pętle i warunki są praktycznie darmowe, a wykonywanie kodu może obsługiwać błędy za pomocą jawnych handlerów, zamiast zmuszać model do rozumowania o awariach w języku naturalnym. Ścieżka wykonywania kodu może utrzymywać wrażliwe dane pośrednie poza kontekstem modelu, ale nie oznacza to poufności: izolacja, kontrola egressu, ograniczone dane uwierzytelniające i logowanie wymagają osobnego egzekwowania.

Kiedy wywoływanie narzędzi przez JSON nadal ma sens: w przypadku pojedynczych operacji atomowych, środowisk bez infrastruktury sandboxowej, mniejszych modeli o słabej generacji kodu lub wymagań audytowych, w których każde pojedyncze wywołanie narzędzia musi być rejestrowane.

Wywoływanie narzędzi przez JSON, MCP, CLI i wykonywanie kodu to powierzchnie wykonawcze. Komórki dotyczące tokenów i skuteczności zadań podsumowują cytowane przykłady, a nie jeden kontrolowany benchmark obejmujący wszystkie pięć kolumn.

Agent-Computer Interface (ACI) dla narzędzi agentów AI

Termin „Agent-Computer Interface” (ACI) został ukuty przez Johna Yanga, Carlosa E. Jimeneza i współpracowników z Princeton w ich artykule o SWE-agent (NeurIPS 2024). Jakość interfejsów dla ludzi ma całą poświęconą jej dziedzinę — interakcję człowiek–komputer, czyli HCI. Autorzy twierdzą, że agenci opartowi na modelach językowych zasługują na takie samo podejście: są „nową kategorią użytkowników końcowych o własnych potrzebach i możliwościach, którym przyniosłyby korzyść interfejsy projektowane specjalnie dla nich”.

Ich wyniki ablation pokazują to liczbowo. Przy użyciu tego samego bazowego modelu GPT-4 Turbo ablation SWE-bench Lite w artykule osiągnęło 18,0% z pełnym ACI SWE-agent na 300 zadaniach, wobec 7,3% w warunku wyłącznie shellowym bez przykładu demonstracyjnego oraz 11,0% z jednym przykładem. Porównanie pokazuje, że interfejs i warunki demonstracji istotnie zmieniły wydajność w tym środowisku; nie izoluje jednak projektowania interfejsu od każdej innej różnicy ani nie dowodzi, że model nie wykonał żadnej pracy. W ramach tej samej ablation interfejsu włączenie lintingu podniosło wynik warunku edycji z 15,0% do 18,0%; w całym zestawie testowym SWE-bench 51,7% uruchomień SWE-agent napotkało co najmniej jedną edycję odrzuconą przez linter, zanim mogła zostać zastosowana dalej.

Diagram pokazuje walidację wyniku po otrzymaniu informacji zwrotnej z narzędzia. Walidacja argumentów to osobna kontrola wykonywana przed uruchomieniem narzędzia; nieprawidłowy wynik wraca do agenta w celu korekty, zanim kolejne działanie go wykorzysta.

Anthropic przyjął ACI jako koncepcję fundamentalną w przewodniku “Building Effective Agents”, wymieniając ją jako jedną z trzech podstawowych zasad: „Starannie zaprojektuj interfejs agent–komputer poprzez dokładną dokumentację i testowanie narzędzi”. Praktyczna wskazówka brzmi: „Jedną z zasad orientacyjnych jest zastanowienie się, ile wysiłku wymaga tworzenie interfejsów człowiek–komputer, a następnie zaplanowanie równie dużego wysiłku przy tworzeniu dobrych interfejsów agent–komputer”.

Cztery zasady ACI w praktyce

1. Działania powinny być proste i łatwe do zrozumienia. Najczęstszym błędem jest odwzorowywanie endpointów API jeden do jednego. Zamiast list_users, list_events i create_event zaimplementuj schedule_event, które w jednym wywołaniu sprawdza dostępność i rezerwuje termin. Zamiast read_logs zaimplementuj search_logs, które zwraca tylko odpowiednie wiersze wraz z kontekstem.

2. Działania powinny być zwięzłe i efektywne. Konsoliduj ważne operacje w możliwie małej liczbie działań. W Market Analyst Agent łączę pobieranie cen z podstawowymi metrykami w jednym narzędziu get_stock_snapshot, zamiast wymagać osobnych wywołań dla ceny, wolumenu, kapitalizacji rynkowej i wskaźnika PE.

3. Informacje zwrotne ze środowiska powinny być przydatne, ale zwięzłe. Unikaj zwracania surowego HTML lub pełnych payloadów API. Zastępuj nieczytelne identyfikatory nazwami semantycznymi. Testy Anthropic dodały enum response_format, dzięki któremu agent może poprosić o zwięzłą (około 72 tokenów) lub szczegółową (około 206 tokenów) odpowiedź, co daje mniej więcej trzykrotną różnicę w koszcie tokenowym.

4. Walidacja powinna ograniczać propagację błędów. Automatyczne wykrywanie błędów pomaga agentom szybko je rozpoznawać i korygować. W SWE-agent niestandardowy edytor plików ze zintegrowanym lintingiem automatycznie odrzuca błędy składni — to etap walidacji stojący za podaną wyżej wartością 51,7%. Jest to walidacja danych wejściowych i wyjściowych narzędzia, a nie filtrowanie treści wokół wywołania modelu, za które odpowiadają produkty guardrails z części 4; tego samego słowa używa się w obu znaczeniach. W Market Analyst Agent stosuję tę samą zasadę, walidując argumenty narzędzi za pomocą schematów Pydantic przed wykonaniem:

from pydantic import BaseModel, Field, field_validator

from market_analyst.utils import normalize_ticker

class StockQuery(BaseModel):
    """Validated input for stock queries.

    Pydantic catches malformed tickers before the API call,
    preventing error propagation through the reasoning loop.
    """
    ticker: str = Field(description="Stock ticker symbol (e.g., NVDA)")

    @field_validator("ticker")
    @classmethod
    def validate_ticker(cls, v: str) -> str:
        return normalize_ticker(v)

class StockHistoryQuery(StockQuery):
    """Validated input for price history queries."""

    period: str = Field(default="1mo", description="Time period: 1d, 5d, 1mo, 3mo, 6mo, 1y")

    @field_validator("period")
    @classmethod
    def validate_period(cls, v: str) -> str:
        valid = {"1d", "5d", "1mo", "3mo", "6mo", "1y"}
        if v not in valid:
            raise ValueError(f"Invalid period: {v}. Must be one of {valid}")
        return v

Wspólny normalizer usuwa białe znaki i zamienia wartość na wielkie litery, a następnie akceptuje cyfry w tickerach oraz przyrostki zawierające kropki lub łączniki, takie jak BRK.B i BF-B; StockHistoryQuery, a nie StockQuery, zarządza period.

Wzorce projektowania narzędzi agentów AI, które działają

Przewodnik Anthropic “Writing effective tools for agents” opisuje narzędzia jako „nowy rodzaj oprogramowania odzwierciedlającego kontrakt między systemami deterministycznymi a agentami niedeterministycznymi”.

Traktuj opisy narzędzi jak prompt engineering

Opisy powinny mieć co najmniej trzy lub cztery zdania i obejmować sytuacje, w których należy użyć narzędzia, parametry wymagane i opcjonalne, format danych wyjściowych oraz przypadki brzegowe. Anthropic informuje, że wybór między namespacingiem opartym na prefiksie i sufiksie (asana_search kontra search_asana) miał „nietrywialny wpływ” na własne ewaluacje korzystania z narzędzi. Nie wskazuje jednak, który schemat wygrywa, dlatego przetestuj oba na swoim zestawie narzędzi, zamiast zakładać przewagę prefiksów. Anthropic przekazał również transkrypcje agentów ewaluacyjnych do Claude Code i pozwolił mu przepisać narzędzia. Na wstrzymanych zbiorach testowych ta pętla przyniosła dalsze usprawnienia „nawet wykraczające poza to, co osiągnęliśmy dzięki implementacjom narzędzi przygotowanym przez ekspertów” — niezależnie od tego, czy narzędzia zostały napisane ręcznie przez badaczy, czy wygenerowane przez Claude.

# Bad: vague, no context for when to use
tools = [{
    "name": "search",
    "description": "Search for items",
}]

# Good: specific, with input examples and edge cases
tools = [{
    "name": "search_news",
    "description": (
        "Search for recent news articles about a specific stock or company. "
        "Use this tool when the user asks about recent events, earnings, "
        "announcements, or market-moving news for a specific ticker. "
        "Returns up to 10 articles sorted by relevance. "
        "For company competitors rather than news, use search_competitors instead."
    ),
    "input_schema": {
        "type": "object",
        "properties": {
            "query": {
                "type": "string",
                "description": "Search query. Examples: 'NVDA earnings Q3 2025', 'Tesla delivery numbers'"
            },
            "max_results": {
                "type": "integer",
                "description": "Max articles to return (1-10, default 5)",
                "default": 5
            }
        },
        "required": ["query"]
    }
}]

Wewnętrzne testy Anthropic wykazały, że dodanie pola input_examples podniosło dokładność obsługi złożonych parametrów z 72% do 90%.

Zwracaj wysokosygnałowe, czytelne maszynowo dane wyjściowe

W domyślnej odpowiedzi używaj etykiet semantycznych zamiast niskopoziomowych identyfikatorów (uuid, mime_type). Zachowaj ID, jeśli późniejsze narzędzie go potrzebuje, albo zaoferuj szczegółową odpowiedź, która go zawiera. Na przykład wynik wyszukiwania Jane może być zwięzły i łatwy do odczytania, a szczegółowy wynik może zawierać ID potrzebne narzędziu send_message. Zorganizuj odpowiedź tak, aby agent mógł na jej podstawie rozumować bez parsowania szablonowego tekstu:

# Bad: raw API response dumped to agent
def get_stock_snapshot(ticker: str) -> dict:
    response = api.get(f"/v1/quotes/{ticker}")
    return response.json()  # 500+ tokens of nested JSON

# Good: high-signal summary the agent can immediately reason about
def get_stock_snapshot(ticker: str) -> dict:
    data = api.get(f"/v1/quotes/{ticker}").json()
    return {
        "ticker": ticker,
        "price": data["regularMarketPrice"],
        "change_pct": round(data["regularMarketChangePercent"], 2),
        "volume": data["regularMarketVolume"],
        "market_cap_b": round(data["marketCap"] / 1e9, 1),
        "pe_ratio": data.get("trailingPE"),
        "summary": f"{ticker} at ${data['regularMarketPrice']:.2f} "
                   f"({'up' if data['regularMarketChangePercent'] > 0 else 'down'} "
                   f"{abs(data['regularMarketChangePercent']):.1f}%)"
    }

Zwracaj błędy, na podstawie których pętla może działać

Obsługa błędów wymaga czterech odrębnych mechanizmów, ponieważ każdy z nich obsługuje inną klasę awarii:

  1. Ponawianie z exponential backoff dla błędów przejściowych
  2. Łańcuchy fallbacku modeli na wypadek awarii dostawcy
  3. Routing według klasy błędu — błędy przejściowe są ponawiane, błędy możliwe do naprawienia przez LLM wracają do agenta z kontekstem, a błędy wymagające człowieka są eskalowane
  4. Odzyskiwanie z checkpointów na wypadek awarii procesu

„Writing effective tools for agents” firmy Anthropic zaleca czytelne błędy narzędzi i projektowanie narzędzi oparte na ewaluacji, ale nie podaje uniwersalnej liczby określającej, ile awarii odzyskują te cztery mechanizmy. Mierz wskaźnik odzyskiwania, ponowienia i eskalacje na własnym zestawie zadań.

import httpx
from tenacity import retry, retry_if_exception, stop_after_attempt, wait_exponential

def is_transient_error(error: BaseException) -> bool:
    if isinstance(error, (httpx.TimeoutException, httpx.NetworkError)):
        return True
    if isinstance(error, httpx.HTTPStatusError):
        return error.response.status_code == 429 or 500 <= error.response.status_code < 600
    return False

@retry(
    retry=retry_if_exception(is_transient_error),
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=1, min=2, max=10),
    reraise=True,
)
def call_stock_api(ticker: str) -> dict:
    """Fetch stock data with automatic retry on transient failures.

    Mechanism 1 of the four above: exponential backoff for rate limits
    and network blips.
    This only retries transient transport failures. If attempts are exhausted,
    Tenacity re-raises the original httpx exception.
    """
    response = httpx.get(
        f"https://api.example.com/v1/quotes/{ticker}",
        timeout=10.0,
    )
    response.raise_for_status()
    return response.json()

Wywołujący lub harness nadal musi wykonać kolejny krok: przekształcić ten wyjątek w stabilny wynik informujący, która operacja się nie powiodła, czy należy ją ponowić i co zrobić dalej. Nieponawialny błąd 4xx pomija ten dekorator i wymaga takiej samej obsługi. Ponowienie żądania nie klasyfikuje błędu ani nie odzyskuje checkpointu.

Ustrukturyzowane dane wyjściowe wyników narzędzi

Narzędzia akcji i wiadomości zwracają odpowiedzi walidowane przez Pydantic. Wrappery CLI i wykonywania kodu zwracają str, dlatego poniższe modele opisują ustrukturyzowane wyniki narzędzi, a nie każdy wrapper w repozytorium:

from pydantic import BaseModel

class StockSnapshot(BaseModel):
    """Structured tool response — the agent never sees raw API noise."""
    ticker: str
    price: float
    change_pct: float
    volume: int
    market_cap_b: float
    pe_ratio: float | None
    summary: str  # Human-readable one-liner for direct use in reports

class NewsItem(BaseModel):
    """One news item pre-processed for agent consumption."""
    headline: str
    source: str
    date: str
    relevance_score: float  # Pre-ranked so the agent doesn't waste tokens sorting
    key_points: list[str]  # Extracted by the tool, not the agent

class NewsSearchResult(BaseModel):
    query: str
    results: list[NewsItem]
    summary: str

Pole summary dostarcza agentowi gotowy do użycia string na potrzeby raportu. NewsItem.key_points zwalniają model z konieczności parsowania treści artykułów. Jeśli późniejsze działanie potrzebuje ID, zachowaj je w szczegółowej odpowiedzi albo zaoferuj tryb zwięzły i szczegółowy; nie usuwaj go wszędzie.

Kompromisy i kwestie do rozważenia

Poza zastrzeżeniami charakterystycznymi dla opisanych wyżej wzorców na wybór wpływa kilka kwestii przekrojowych:

  • Koszt operacyjny różni się w zależności od wymiaru. Wykonywanie kodu może oszczędzać tokeny kontekstu modelu przez filtrowanie wyników pośrednich, ale narzut generowania kodu i kontenera może przewyższyć te oszczędności i zwiększyć opóźnienie. MCP oszczędza czas programistyczny przy integracjach SaaS, ale dodaje narzut wdrażania serwerów. CLI można uruchomić bezpłatnie, lecz trudniej zarządzać nim na dużą skalę. Optymalizuj rzeczywiste wąskie gardło — koszt tokenów, opóźnienie albo złożoność operacyjną.

  • Umiejętności zespołu mają znaczenie. Wykonywanie kodu zakłada, że agenci (i stojące za nimi modele) potrafią niezawodnie generować Python lub TypeScript. CLI zakłada znajomość konwencji Unix. MCP wymaga zrozumienia protokołów transportowych i przepływów OAuth. Dopasuj rodzaj narzędzi do mocnych stron zespołu.

  • Konsolidacja narzędzi może posunąć się za daleko. Jeśli jedno narzędzie zgromadzi niezwiązane ze sobą tryby i argumenty, agent napotka inny problem wyboru — tym razem wewnątrz schematu. Użyj ewaluacji wyboru narzędzi i skuteczności zadań, aby znaleźć odpowiednią powierzchnię dla danego obciążenia.

  • Skills są oparte na promptach, a nie egzekwowane. Skill zawiera instrukcje, których agent powinien przestrzegać, a nie guardrails, których musi przestrzegać. Pakiet skilla może zawierać dowolne pliki i wykonywalne skrypty, dlatego ufaj jego źródłu, przejrzyj pakiet i pozwól hostowi egzekwować uprawnienia dla każdego zasobu, który może odczytywać, modyfikować lub wykonywać. W krytycznych przepływach pracy łącz skills z deterministyczną walidacją.

  • Wymagania audytowe wpływają na wybór. Ustrukturyzowane wywołania MCP i JSON są wygodnymi zdarzeniami do logowania, ale żaden z tych protokołów nie tworzy od razu kompletnego śladu audytowego. Host, serwer lub harness musi rejestrować wywołania i wyniki, a następnie egzekwować autoryzację, politykę, retencję i przegląd. Wykonywanie kodu wymaga takiej samej instrumentacji wokół sandboxa; sam skrypt i jego wynik nie stanowią dokumentacji zgodności.

Trzy kierunki rozwoju narzędzi agentów AI na dużą skalę

Pierwszym jest tool RAG służący do skalowania. Zanim model wybierze narzędzie, pobierz kilka opisów narzędzi pasujących do żądania i pozwól mu wybierać z tego podzbioru zamiast z pełnego rejestru. W zadaniach benchmarku RAG-MCP i teście obciążeniowym MCP bazowa dokładność wyboru narzędzi wynosiła 13,62%; retrieval podniósł ją do 43,13%, czyli 3,2 raza, jednocześnie zmniejszając liczbę tokenów promptu z 2133,84 do 1084 (około 49,2%). Abstrakt artykułu mówi o „ponad 50%”, a opisy generatora i ewaluatora różnią się między sekcjami; te niespójności ograniczają interpretację. Wynik stanowi dowód dla tej konfiguracji ewaluacyjnej, a nie uniwersalny wskaźnik dla naiwnego wyboru wraz ze wzrostem zestawu narzędzi.

Drugim kierunkiem są agenci tworzący własne narzędzia. Framework LATM („LLMs As Tool Makers”) ustanowił dwuetapowy paradygmat, w którym potężny LLM tworzy wielokrotnego użytku funkcje Pythona, a lekki LLM z nich korzysta. W benchmarku ToolMaker obejmującym 15 zadań opartych na artykułach z publicznymi repozytoriami kodu, dostarczanych jako URL GitHub i krótkie opisy zadań, poprawnie zaimplementowano 12 z 15 zadań; benchmark zawiera łącznie ponad 100 testów. Ten niewielki benchmark zadań repozytoriów nie dowodzi niezawodności produkcyjnej. Oba kierunki wykraczają poza korzystanie z narzędzi w stronę ich tworzenia, a następnie zarządzania biblioteką wygenerowanych narzędzi.

Trzecim jest dwuprotokołowy stos A2A + MCP. Google przekazał A2A Linux Foundation w czerwcu 2025 roku. Dokumentacja protokołu A2A rozdziela ich odpowiedzialności: MCP łączy agenta z narzędziami i zasobami, podczas gdy A2A pozwala niezależnym agentom wykrywać się nawzajem, negocjować interakcje, zarządzać współdzielonymi zadaniami i delegować pracę.

Porównuj interfejsy na identycznych zadaniach i przy tych samych dozwolonych operacjach. Rejestruj tokeny wykrywania, dane wejściowe z cache i bez cache, wynik wykonania, ponowienia, opóźnienie oraz skuteczność stanu końcowego. Testuj zarówno pominięte wykrywanie, jak i oszczędności tokenów; w przypadku programów generowanych zliczaj błędy składni, błędy czasu wykonania i częściowe ukończenia.

Najważniejsze wnioski

  1. Wybierz powierzchnię wykonawczą na podstawie działania: wywołania JSON dla małych, typowanych operacji, MCP dla współdzielonych usług, CLI dla ugruntowanych poleceń oraz kod wykonywany w sandboxie dla lokalnej kompozycji. Używaj Skills do dokumentowania sposobu wyboru i korzystania z tej powierzchni.
  2. Zawsze wiąż wynik z warunkami benchmarku. CodeAct, Anthropic, Vercel, Cloudflare, Apideck i Scalekit mierzyli różne modele, zadania, narzędzia i harnessy.
  3. Jakość ACI pozostaje ważna niezależnie od zmian protokołu. Jasne działania, zwięzłe informacje zwrotne, walidacja i użyteczne błędy pomagają każdemu rodzajowi narzędzi.
  4. Konsoliduj nakładające się narzędzia tylko wtedy, gdy ewaluacje pokażą, że mniejsza powierzchnia poprawia wybór lub skuteczność zadań.
  5. Bezpieczeństwo podąża za możliwościami wykonawczymi. Interfejsy shell i kodu wymagają sandboxingu; MCP wymaga ograniczonej tożsamości i polityki serwera; Skills pozostają instrukcjami, a nie mechanizmem egzekwowania.
