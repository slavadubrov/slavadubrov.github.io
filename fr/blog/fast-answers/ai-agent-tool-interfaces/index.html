Interfaces d’outils pour les AI Agents : MCP, function calling, CLI, skills

Viacheslav Dubrov

2026-08-10 · 3 min · Agents IA · Outils de développement

Traduction automatique Cet article a été traduit automatiquement depuis la version originale en anglais.

Utilisez le function calling lorsqu’une application expose un petit ensemble d’outils typés à une seule API de modèle. Utilisez le Model Context Protocol (MCP) lorsque plusieurs clients compatibles doivent découvrir et appeler un serveur réutilisable. Utilisez une CLI lorsqu’une commande stable existe déjà et que le texte ou les fichiers constituent une boundary acceptable. Utilisez une skill lorsque des instructions, scripts et références réutilisables doivent apprendre à un agent à exécuter un workflow.

Ces interfaces peuvent être composées. Une skill peut indiquer à un agent quand appeler un outil MCP, un serveur MCP peut encapsuler une CLI, et un modèle peut sélectionner l’appel via le function calling. La boundary de sécurité relève toutefois du harness et du runtime, et non de la description de l’interface.

Dernière révision : 2026-08-10. La comparaison privilégie la clarté du schéma, la réutilisation entre clients, le coût du transport et du déploiement, le principe du moindre privilège, l’observabilité et la responsabilité de maintenance.

Function calling

Le function calling fournit au modèle des opérations nommées avec des arguments structurés. Il convient à un harness dont le produit contrôle les outils, les vérifications de policy, les credentials et l’exécution au sein d’une seule application. Gardez les schémas étroits, validez chaque argument et évaluez à la fois la sélection de l’outil et l’effet de bord qui en résulte.

MCP

MCP sépare les clients des serveurs réutilisables et standardise la découverte et l’invocation. Il est utile lorsqu’une même intégration doit fonctionner avec plusieurs agents ou applications compatibles. MCP ne décide pas si un tool call est autorisé. Authentifiez le serveur, limitez la portée des tokens, examinez les changements de définition des outils, isolez les serveurs non fiables et traitez les résultats comme des entrées non fiables.

Outils CLI

Une CLI est souvent le chemin le plus court vers des fonctionnalités matures telles que Git, les gestionnaires de packages, les outils cloud et les systèmes de build. Privilégiez une sortie structurée, des répertoires de travail explicites, des options non interactives, des timeouts bornés et des credentials aux permissions limitées. Évitez de construire des chaînes shell à partir de texte non fiable.

Skills

Une skill regroupe des instructions procédurales et peut inclure des scripts, des références ou des templates. Elle est utile lorsque la difficulté principale consiste à connaître le workflow plutôt qu’à créer un nouvel outil distant. Gardez la skill suffisamment petite pour être revue, figez les hypothèses externes et rendez explicites les actions destructrices ou externes.

Checklist de sélection

  • Qui est responsable du client, de l’interface et de l’implémentation ?
  • Plusieurs clients doivent-ils la réutiliser ?
  • Le schéma d’entrée est-il étroit et versionné ?
  • Où l’autorisation et l’approbation sont-elles appliquées ?
  • Du contenu non fiable peut-il atteindre les credentials ou la sortie réseau ?
  • Les appels, arguments, résultats et décisions de policy sont-ils traçables ?
  • Un appel de bibliothèque typé peut-il résoudre le problème avec une surface d’exposition moindre ?
