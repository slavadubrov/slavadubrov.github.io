Raisonnement guidé par schéma : vLLM, XGrammar et Pydantic

Viacheslav Dubrov

2025-12-28 · Mis à jour 2026-09-12 · 15 min · Agents IA · Ingénierie des modèles

Traduction automatique

Cet article a été traduit automatiquement depuis la version originale en anglais.

Cet article s’adresse aux ingénieurs Python qui ont besoin de sorties de modèle validables par le code en aval. Vous apprendrez à définir un schéma Pydantic, à demander une sortie structurée à vLLM et à ajouter des contrôles applicatifs portant sur le sens et les règles métier.

Pydantic décrit les champs de la réponse, vLLM sert le modèle et XGrammar restreint les tokens que le modèle peut générer. Cette restriction s’appelle le constrained decoding. Elle s’applique uniquement aux fonctionnalités du schéma prises en charge par le backend de décodage, ici XGrammar. Une limite de tokens peut tout de même laisser un préfixe JSON incomplet ; le code applicatif doit donc vérifier que la génération est terminée et valider le résultat.

Qu’est-ce que le raisonnement guidé par schéma ?

Le raisonnement guidé par schéma est une technique que Rinat Abdullin a décrite en juillet 2025. Au lieu de laisser le modèle compléter librement le texte — ce qui peut produire un résultat incohérent ou ambigu — vous lui fournissez un modèle strict qui définit :

  • les étapes que la réponse doit représenter
  • l’ordre prévu de ces étapes, afin qu’un reviewer puisse inspecter le cheminement des données vers la décision
  • les éléments auxquels le modèle doit accorder son attention

Considérez-le comme une checklist des sorties à inspecter, et non comme une preuve du raisonnement interne du modèle. Le décodeur vérifie la structure de la sortie ; le code applicatif contrôle le moment où chaque étape s’exécute et détermine si un résultat peut être utilisé.

Ce que contrôle le schéma

L’exemple présenté propose une remise pour retenir un client susceptible de partir. La probabilité de churn estime cette probabilité de départ ; la valeur du panier correspond au total avant remise. La marge est le bénéfice brut exprimé comme une fraction de ce total : un panier de $200 avec une marge de 0.20 génère $40 de bénéfice brut. Les remises utilisent des points de pourcentage : une proposition de 15 signifie donc 15 %.

Un modèle de pricing peut renvoyer un JSON valide tout en proposant une remise de 25 % alors que la marge n’est que de 20 %. Le schéma enregistre la proposition ; le code applicatif doit vérifier si la remise est autorisée.

Des champs tels que churn_analysis, margin_math et max_discount_percent rendent explicites les sorties intermédiaires attendues. Un schéma contraint la forme renvoyée. À lui seul, il ne rend pas un champ dépendant d’un autre et ne prouve pas que la décision est correcte.

Vous obtenez ainsi :

  • une structure de sortie comparable entre plusieurs exécutions
  • des sorties intermédiaires enregistrées et inspectables par les reviewers
  • des champs intermédiaires que vous pouvez évaluer sur un dataset de test
  • une hypothèse à tester avec des modèles plus petits : contraindre le format peut aider, mais la précision sur la tâche doit toujours être évaluée
  • Abdullin écrit qu’un gain de précision de 5 à 10 % n’est « pas inhabituel » dans les cas qu’il a observés ; il s’agit d’une observation de praticien, pas d’un résultat de benchmark. Mesurez donc ce gain sur votre propre charge de travail

Conseils de prompt et contraintes du décodeur

Les conseils de prompt et le constrained decoding peuvent être combinés. Cette comparaison montre à quel moment chacun vérifie le format demandé.

Prompt engineering : demander le format

Ce prompt demande au modèle de formater la proposition de remise en JSON :

Please analyze the customer data and output your response as valid JSON
with the following structure: {"discount": <number>, "reason": <string>}
Be careful with the formatting!

Vous espérez que la compréhension par le modèle de « output JSON » l’emporte sur sa tendance à converser. Une mise à jour du modèle, un changement de température ou un autre exemple few-shot peut suffire à casser votre parser.

Chain of Thought : une trace de raisonnement utile, mais le même problème de structure

Un prompt chain-of-thought (CoT) demande une analyse intermédiaire. La réponse peut ressembler à ceci :

Let's think step by step:
1. First, I'll analyze the customer's churn risk...
2. Then I'll calculate the margin...
3. Therefore, I recommend a 15% discount.

Le CoT peut améliorer la précision sur la tâche lorsque le prompt, le modèle, la tâche et l’évaluation s’y prêtent, mais il laisse le résultat sous forme de prose, difficile à parser de manière fiable. Vous pourriez finir par effectuer un second appel à un LLM uniquement pour extraire des données structurées.

SGR : chain-of-thought structurée

SGR peut rendre les champs intermédiaires disponibles pour inspection et évaluation. L’amélioration éventuelle de la précision sur la tâche dépend du modèle, du prompt, de la tâche et de l’utilisation de ces champs ; le schéma ne fait que formaliser leur structure :

class PricingLogic(BaseModel):
    # 1. Recorded analysis
    churn_analysis: str = Field(..., description="Analyze churn_probability")
    financial_analysis: str = Field(..., description="Analyze cart_value and margin")

    # 2. Proposed calculation, checked by application code
    margin_math: str = Field(..., description="Calculate: 'Cart $X * Y% = $Z'")

    # 3. Proposed decision, not bounded by the analysis fields
    max_discount_percent: float = Field(..., description="Max allowed discount")

    # 4. Final Output
    customer_message: str

Le schéma décrit ces champs dans cet ordre. Un schéma d’objet unique ne crée pas d’étape de validation distincte entre eux. Utilisez des appels séparés ou des contrôles applicatifs lorsque les décisions ultérieures doivent dépendre des résultats précédents.

Patterns SGR

Byte dit

Placer les champs d’analyse avant une décision rend la réponse plus facile à inspecter. Un champ appelé margin_math reste une chaîne de caractères, pas une calculatrice.

SGR repose sur trois patterns fondamentaux qui peuvent être composés en workflows plus importants.

1. Cascade : étapes de raisonnement séquentielles

Cascade représente un ordre de raisonnement dans une réponse structurée unique. Ici, un classifieur de documents enregistre un résumé, un score de correspondance thématique et une catégorie proposée. Il n’effectue pas de contrôle distinct entre ces champs.

from pydantic import BaseModel
from typing import Literal, Annotated
from annotated_types import Ge, Le

class DocumentEvaluation(BaseModel):
    """Record a document summary, score, and proposed category."""

    # Step 1: Record a summary
    brief_document_summary: str

    # Step 2: Rate (bounded integer)
    rate_topic_match: Annotated[int, Ge(1), Le(10)]

    # Step 3: Decide (constrained choices)
    final_recommendation: Literal["relevant", "irrelevant", "review"]

Exemples d’utilisation : classification de documents et triage de tickets de support.

Le modèle doit renvoyer brief_document_summary, rate_topic_match et final_recommendation dans cet ordre. Si cet ordre constitue une exigence de politique, imposez-le avec des appels séparés ou une logique applicative déterministe.

2. Routing : une instruction switch sémantique

Routing demande au modèle de sélectionner un chemin parmi un ensemble d’options, implémenté avec des types Union. Ce router choisit entre récupérer les données client pour une demande de pricing et renvoyer une réponse générale.

from pydantic import BaseModel
from typing import Literal, Union

class FeatureLookup(BaseModel):
    """Route to database lookup."""
    rationale: str
    tool_name: Literal["fetch_user_features"] = "fetch_user_features"
    user_id: str

class GeneralResponse(BaseModel):
    """Standard response for non-pricing queries."""
    tool_name: Literal["respond"] = "respond"
    content: str

class RouterSchema(BaseModel):
    """The model must pick exactly ONE branch."""
    action: Union[FeatureLookup, GeneralResponse]

Cas d’usage adaptés : classification d’intention, sélection d’outils, triage du support et dispatch multi-agent.

Les valeurs Literal propres à chaque branche aident la validation à distinguer les membres de l’union. Elles ne rendent pas le routing correct. Validez le résultat et effectuez le dispatch dans le code applicatif. Pour utiliser un discriminateur Pydantic explicite, configurez et testez une union discriminée.

3. Cycle : raisonnement répété avec des listes

Cycle décrit plusieurs éléments, avec des bornes sur leur nombre. Cet exemple d’évaluation des risques demande de deux à quatre facteurs, chacun accompagné d’une explication et d’un niveau de gravité.

from pydantic import BaseModel
from typing import List, Literal, Annotated
from annotated_types import MinLen, MaxLen

class RiskFactor(BaseModel):
    explanation: str
    severity: Literal["low", "medium", "high"]

class RiskAssessment(BaseModel):
    """Generate 2-4 risk factors."""
    factors: Annotated[List[RiskFactor], MinLen(2), MaxLen(4)]

Cas d’usage adaptés : évaluation des risques, extraction de problèmes, tool calls parallèles et planification en plusieurs étapes.

Les bornes de la liste décrivent un batch variable de 2 à 4 éléments. Un décodeur compatible peut contraindre cette longueur ; la validation applicative la vérifie une nouvelle fois. Combinée à Routing, la liste peut décrire des tool calls proposés. Le code applicatif doit les autoriser et les dispatcher.

Faire fonctionner SGR : constrained decoding

Les patterns ci-dessus ne sont que des schémas Pydantic. Le constrained decoding peut imposer les contraintes prises en charge et exportées dans leur JSON Schema. Les validateurs Python arbitraires ne deviennent pas des contraintes du décodeur ; ils continuent de s’exécuter dans Pydantic après la génération.

Le constrained decoding modifie l’étape de génération des tokens. Au lieu de laisser le modèle échantillonner librement dans son vocabulaire, le moteur applique un masque de grammaire qui bloque les tokens susceptibles de violer le schéma. Cette opération se déroule dans le moteur d’inférence, et non dans votre code applicatif.

[!TIP] SGR ne nécessite pas de « modèles de raisonnement » comme o1 ou DeepSeek-R1. Des modèles instruction-tuned peuvent également produire des réponses contraintes par schéma. Comparez la précision sur la tâche pour les modèles que vous prévoyez de servir.

Pourquoi utiliser vLLM et XGrammar ici ?

L’API de structured output de vLLM accepte un JSON Schema via un client compatible OpenAI. L’exemple peut ainsi conserver un plumbing de requête familier tout en configurant le backend de décodage sur le serveur. Les sous-ensembles de schémas, la gestion des erreurs et le comportement du modèle doivent néanmoins être testés lors d’un changement de provider.

XGrammar fournit le compilateur de grammaire et le mécanisme de masque de tokens. Son aperçu technique explique la répartition CPU/GPU ci-dessous ; ses résultats de benchmark s’appliquent aux charges de travail testées, et non à tous les déploiements.

Comment XGrammar impose les schémas

Où le masquage se produit

Les logits sont les scores non normalisés attribués par le modèle aux tokens suivants possibles. XGrammar modifie ces scores après le forward pass du modèle et avant l’échantillonnage. Il ne modifie pas le modèle lui-même. Il filtre les tokens qui peuvent être sélectionnés.

Une boucle d’inférence standard ressemble à ceci :

1. Input tokens → GPU Forward Pass → Logits (one unnormalized score per vocabulary token)
2. Logits → Sampling (temperature, top-p, etc.) → Next Token
3. Repeat until done

XGrammar s’intercale entre les étapes 1 et 2 :

1. Input tokens → GPU Forward Pass → Raw Logits
2. Raw Logits → XGrammar Logits Processor → Masked Logits
3. Masked Logits → Sampling → Next Token (continues the grammar-valid prefix)
4. Repeat until done

Le diagramme montre comment les scores du modèle et le masque de grammaire se combinent avant la sélection d’un token. Chaque token accepté met également à jour l’état de la grammaire pour l’étape suivante.

Le modèle calcule toujours sa distribution de probabilités complète sur le GPU. Le GrammarMatcher de XGrammar génère le bitmask sur le CPU, puis le moteur de serving transfère ce bitmask vers le device des logits et l’applique en place avant l’échantillonnage. Pour les logits situés sur le GPU, XGrammar utilise un kernel GPU pour cette application. Les tokens invalides voient leurs logits définis à -∞, ce qui rend leur probabilité exactement égale à 0 après le softmax.

Deux phases

XGrammar sépare le travail entre la compilation et le runtime. Cette conception réduit le travail répété lié à la grammaire.

Phase 1 : compilation de la grammaire, une fois par schéma

Cet extrait construit une grammaire pour le schéma en utilisant le tokenizer du modèle. Le résultat compilé peut être réutilisé lors de la génération de réponses avec ce schéma.

# This happens once per schema
tokenizer_info = xgr.TokenizerInfo.from_huggingface(tokenizer)
grammar_compiler = xgr.GrammarCompiler(tokenizer_info)
compiled_grammar = grammar_compiler.compile_json_schema(schema_json)

Lors de la compilation, XGrammar :

  1. Convertit le JSON Schema en grammaire hors contexte.
  2. Construit un Pushdown Automaton (PDA), c’est-à-dire une machine à états dotée d’une pile, capable de gérer des structures imbriquées telles que {"a": {"b": {"c": ...}}}.
  3. Pré-calcul les tokens valides à chaque position de la grammaire. Le résultat est l’« adaptive token mask cache ».
  4. Classe les tokens comme « indépendants du contexte » (mis en cache) ou « dépendants du contexte » (à vérifier au runtime en fonction de l’état de la pile).

[!NOTE] L’article de XGrammar indique qu’environ 99 % des tokens étaient indépendants du contexte dans ses mesures (article). Considérez ce chiffre comme spécifique au benchmark, et non comme un ratio universel.

Phase 2 : génération du masque au runtime, à chaque token

À chaque étape de génération :

  1. Le GrammarMatcher suit la position actuelle dans la grammaire.
  2. Il recherche le masque pré-calculé pour les tokens indépendants du contexte.
  3. Il exécute le PDA pour vérifier les tokens restants, dépendants du contexte.
  4. Il les combine en un bitmask final, le transfère vers le device des logits et l’y applique.

Pourquoi des automates à pile plutôt que des regex ?

À cause de l’imbrication. Une expression régulière — une machine à états finis — ne peut pas reconnaître de manière fiable des structures telles que :

{ "user": { "profile": { "settings": { "theme": "dark" } } } }

La difficulté réside dans les accolades fermantes }}} : vous devez mémoriser le nombre d’accolades ouvertes. Un Pushdown Automaton dispose d’une pile qui suit cette information et peut donc gérer une profondeur d’imbrication arbitraire. C’est également pourquoi XGrammar peut imposer des types Union, des objets imbriqués et des schémas récursifs, là où les approches basées sur des regex atteignent leurs limites.

Exemple concret : générer un champ float

Lorsque le modèle génère "max_discount_percent":, XGrammar sait grâce au schéma qu’un float doit suivre. L’ensemble des tokens valides dépend de l’état du parser et du tokenizer. Au début du nombre, le masque peut autoriser un chiffre ou un signe moins ; après un chiffre, il peut autoriser des continuations telles qu’un autre chiffre, un point décimal ou un marqueur d’exposant.

  • Une quote, {, [, true, false ou null ne peut pas commencer ce nombre ; le masque bloque donc leurs tokens dans cet état.
  • Le forward pass peut avoir attribué une probabilité élevée au token correspondant à "fifteen". Comme ce token ne peut pas prolonger ce champ numérique, le masque le supprime et le modèle doit choisir une continuation numérique valide.

Ce qui influence le surcoût

Trois raisons :

  1. Génération et transfert du masque. XGrammar génère les masques sur le CPU, puis le moteur de serving les transfère vers le device des logits pour une application en place. Le degré de recouvrement dépend de l’implémentation du serving et de la charge de travail.
  2. Mise en cache. La majeure partie du travail de validation est effectuée à la compilation. Le runtime consiste principalement en recherches dans le cache.
  3. Implémentation C++. Le chemin critique est en C++, et non en Python, et le masque est appliqué en place aux logits.

Les benchmarks cités indiquent un faible surcoût pour les grammaires, tokenizers, matériels et charges de travail testés. Ces résultats ne constituent pas une garantie générale de latence ou de débit.

Étape 1 : définir les schémas

RouterSchema autorise deux alternatives : demander les données client avec FeatureLookup, ou renvoyer du texte avec GeneralResponse. Après récupération des données, un appel séparé utilise PricingLogic pour enregistrer l’analyse et la remise proposée. Séparer ces réponses permet à l’application de récupérer les données avant de demander une proposition.

# sgr/models/schemas.py
from pydantic import BaseModel, Field
from typing import Literal, Union

# --- Phase 1: Routing (Union for branching) ---
class FeatureLookup(BaseModel):
    """Route to DB lookup if pricing context is needed."""
    rationale: str
    tool_name: Literal["fetch_user_features"] = "fetch_user_features"
    user_id: str

class GeneralResponse(BaseModel):
    """Standard response for non-pricing queries."""
    tool_name: Literal["respond"] = "respond"
    content: str

class RouterSchema(BaseModel):
    action: Union[FeatureLookup, GeneralResponse]

# --- Phase 2: Pricing Logic (Cascade for sequential reasoning) ---
class PricingLogic(BaseModel):
    """
    Structured response for dynamic pricing. The fields record an intended analysis→decision flow.
    """
    # 1. Data Analysis (Reflection)
    churn_analysis: str = Field(...,
        description="Analyze churn_probability (High > 0.7).")
    financial_analysis: str = Field(...,
        description="Analyze cart_value and profit_margin.")

    # 2. Recorded calculation; application code recomputes policy
    margin_math: str = Field(...,
        description="Calculate absolute profit: 'Cart $200 * 0.20 Margin = $40'.")

    # 3. Model-proposed decision; application code approves it.
    max_discount_percent: float = Field(...,
        description="Proposed discount percentage. Application code enforces policy.")

Étape 2 : demander et valider une réponse structurée

Le client exporte le modèle Pydantic sous forme de JSON Schema, l’ajoute à un message système existant pour fournir des indications au modèle, puis l’envoie comme contrainte de structured output. XGrammar est configuré sur le serveur ; le client fournit le schéma pour chaque requête.

completed_content rejette les réponses incomplètes, refusées ou vides avant que Pydantic ne valide le JSON et ses champs. Il rejette les arrêts dus à la limite de tokens, même si le texte renvoyé peut être parsé. Ces erreurs sont propagées à l’appelant, qui doit fournir une réponse d’erreur ou une politique de retry ; aucune offre n’est approuvée dans ces cas.

# sgr/utils/llm_client.py
import json
from typing import TypeVar

from openai import OpenAI
from pydantic import BaseModel

T = TypeVar("T", bound=BaseModel)

def completed_content(completion) -> str:
    """Reject incomplete, refused, or empty results before JSON validation."""
    if not completion.choices:
        raise ValueError("No completion returned")
    choice = completion.choices[0]
    if choice.finish_reason != "stop" or getattr(choice.message, "refusal", None):
        raise ValueError("Completion was not successful")
    content = choice.message.content
    if not isinstance(content, str) or not content.strip():
        raise ValueError("Completion has no content")
    return content

class LLMClient:
    """Wrapper for vLLM with XGrammar-enforced structured generation."""

    def __init__(self, base_url: str = "http://localhost:8000/v1"):
        # Local vLLM commonly has no authentication. EMPTY is not authentication.
        self.client = OpenAI(base_url=base_url, api_key="EMPTY")
        self.model = self._get_available_model()

    def _get_available_model(self) -> str:
        """Auto-detect the model running on vLLM server."""
        models = self.client.models.list()
        if not models.data:
            raise RuntimeError("vLLM reported no available models")
        return models.data[0].id

    def run_sgr(self, messages: list[dict], schema_class: type[T]) -> T:
        """Run inference with Schema-Guided Response constraints.

        Uses vLLM structured outputs to constrain the JSON shape at generation time.
        """
        schema_dict = schema_class.model_json_schema()

        # Enhance system message with schema for model guidance
        enhanced_messages = messages.copy()
        if enhanced_messages and enhanced_messages[0]["role"] == "system":
            schema_json = json.dumps(schema_dict, indent=2)
            enhanced_messages[0] = {
                "role": "system",
                "content": (
                    enhanced_messages[0]["content"]
                    + f"\n\nRespond with JSON matching this schema:\n{schema_json}"
                ),
            }

        # vLLM v0.12+ structured outputs. Configure the backend on the server.
        completion = self.client.chat.completions.create(
            model=self.model,
            messages=enhanced_messages,
            temperature=0.1,  # Reduces sampling variation; it is not deterministic.
            extra_body={"structured_outputs": {"json": schema_dict}},
        )

        return schema_class.model_validate_json(completed_content(completion))

[!NOTE] Dans la version actuelle de vLLM, structured_outputs: {"json": schema_dict} demande un JSON correspondant au schéma. Configurez si nécessaire le backend de structured output avec l’option --structured-outputs-config.backend du serveur. Il s’agit d’un contrôle logiciel assuré par le serveur d’inférence, et non d’un contrôle matériel.

Étape 3 : orchestrer l’agent

L’application route la requête, récupère les données pour l’appelant authentifié, demande une proposition, la vérifie et renvoie le résultat. Le feature store utilise le user_id authentifié, jamais l’ID proposé par le modèle. Le prompt reçoit également user_ltv, la valeur estimée du customer lifetime value ; cette estimation fournit un contexte au modèle, mais ne définit pas la limite de remise.

La règle de démonstration rejette les pourcentages proposés en dehors de 0–20, puis arrondit à la baisse au centième de point de pourcentage. Elle rejette une remise finale dont le coût dépasse le bénéfice brut du panier. approve_discount vérifie que les entrées sont finies, que la valeur du panier est positive et que la marge est une fraction comprise entre 0 et 1 avant d’effectuer le calcul.

# sgr/agent.py
from decimal import Decimal, ROUND_DOWN

from .models.schemas import PricingLogic, RouterSchema
from .prompts.routing import build_routing_prompt
from .prompts.pricing import build_pricing_context_prompt, ASSISTANT_FETCH_MESSAGE
from .store.hybrid_store import HybridFeatureStore
from .utils.llm_client import LLMClient

def approve_discount(offer: PricingLogic, context: dict) -> Decimal:
    """Enforce the pricing policy independently of the model's explanation."""
    cart_value = Decimal(str(context["current_cart_value"]))
    margin = Decimal(str(context["cart_profit_margin"]))
    proposed = Decimal(str(offer.max_discount_percent))

    if not all(value.is_finite() for value in (cart_value, margin, proposed)):
        raise ValueError("Pricing values must be finite")
    if cart_value <= 0 or not Decimal("0") <= margin <= Decimal("1"):
        raise ValueError("Invalid pricing context")

    if not Decimal("0") <= proposed <= Decimal("20"):
        raise ValueError("Proposed discount violates pricing policy")
    # Policy rounds down to hundredths of a percentage point before approval.
    approved = proposed.quantize(Decimal("0.01"), rounding=ROUND_DOWN)
    gross_profit = cart_value * margin
    discount_cost = cart_value * approved / Decimal("100")
    policy_cap = min(margin * Decimal("100"), Decimal("20"))
    if not Decimal("0") <= approved <= policy_cap or discount_cost > gross_profit:
        raise ValueError("Proposed discount violates pricing policy")

    return approved

def pricing_agent(user_query: str, user_id: str) -> str:
    """Integrate routing, context, and pricing; user_id is caller-authenticated."""

    llm = LLMClient()
    feature_store = HybridFeatureStore()

    # Build conversation history
    history = [
        {"role": "system", "content": build_routing_prompt(user_id)},
        {"role": "user", "content": user_query},
    ]

    # --- Phase 1: Routing (Uses RouterSchema) ---
    print(f"🤖 Processing: '{user_query}' for {user_id}")
    decision = llm.run_sgr(history, RouterSchema)
    print(f"📍 Routing decision: {decision.action.tool_name}")

    if decision.action.tool_name == "respond":
        return decision.action.content

    # --- Phase 2: Context Retrieval ---
    if decision.action.tool_name == "fetch_user_features":
        print(f"🔍 Fetching features for {user_id}...")
        context = feature_store.get_user_context(user_id)

        if not context:
            return "Error: User profile not found."

        print(f"   [Data] LTV: ${context.get('user_ltv')} | "
              f"Margin: {context.get('cart_profit_margin', 0) * 100}%")

        # Inject context into conversation
        history.append({"role": "assistant", "content": ASSISTANT_FETCH_MESSAGE})
        history.append({
            "role": "user",
            "content": build_pricing_context_prompt(
                churn_prob=context.get("churn_probability", 0.5),
                cart_val=context.get("current_cart_value", 100),
                margin=context.get("cart_profit_margin", 0.2),
                user_ltv=context.get("user_ltv", 0),
            ),
        })

        # --- Phase 3: model proposal, then deterministic policy enforcement ---
        print("🧠 Proposing Offer (Schema Enforced)...")
        offer = llm.run_sgr(history, PricingLogic)
        try:
            approved_discount = approve_discount(offer, context)
        except ValueError:
            return "No discount approved: the proposal failed the pricing policy."

        # Audit log: reasoning is inspectable; pricing is application-enforced.
        print(f"   [Audit] Math: {offer.margin_math}")
        print(f"   [Audit] Approved Discount: {approved_discount}%")

        return (
            f"Illustrative approved discount: {approved_discount}%. "
            "No coupon has been issued."
        )

    return "I'm sorry, I couldn't process your request."

if __name__ == "__main__":
    response = pricing_agent("I want a discount or I'm leaving!", "user_102")
    print(f"\n💬 Final Reply: {response}")

Commande du serveur pour une intégration

Configurez le processus de serving pour utiliser XGrammar avant de connecter le client :

# On a separately provisioned vLLM host
vllm serve Qwen/Qwen2.5-7B-Instruct \
    --port 8000 \
    --structured-outputs-config.backend xgrammar

L’argument positionnel du modèle et l’option du backend suivent la référence vLLM serve. Provisionnez un accélérateur/runtime pris en charge et suffisamment de mémoire pour le modèle et la longueur de contexte sélectionnés en suivant le guide d’installation. Cette commande est une référence d’intégration, et non une recette d’installation testée.

Une proposition de 15 % sur un panier de $200 avec une marge de 20 % renvoie 15.00 depuis la fonction de politique. L’application communique ce pourcentage sans prétendre émettre un coupon. Un test de limite utilise une marge de 0.12346, soit 12,346 %. Une proposition 12.346 est arrondie à la baisse à 12.34 avant le contrôle de la valeur finale. Arrondir à 12.35 après l’approbation dépasserait la marge.

Contrôles avant une intégration réelle

Byte dit

Une proposition peut contenir un JSON valide et une remise supérieure à la marge. La fonction de politique vérifie le nombre même si l’explication semble convaincante.

Conception du schéma

  1. Ordonnez les champs selon le flux de raisonnement attendu. Considérez cet ordre comme de la documentation, sauf si des appels séparés ou des contrôles applicatifs l’imposent.
  2. Rédigez des descriptions Field descriptives. Elles orientent l’attention du modèle autant que le nom du champ.
  3. Contraignez avec Literal et Annotated. Utilisez Literal["a", "b"] pour les enums et Annotated[int, Ge(1), Le(10)] pour les bornes.
  4. Gardez des schémas ciblés. Un schéma par phase de raisonnement, puis une composition au moyen de plusieurs appels.

Configuration de vLLM

  1. Utilisez une température basse (0.1–0.3) pour réduire la variation d’échantillonnage. Pour des tests reproductibles, fixez le modèle et la configuration de serving, utilisez le mode déterministe du serveur s’il en fournit un et vérifiez le résultat.
  2. Expliquez la tâche et les champs du schéma dans le prompt, comme le fait le client ci-dessus. Les indications du prompt et les contraintes du décodeur jouent des rôles complémentaires.
  3. Mesurez l’utilisation des tokens avec le même prompt, le même modèle, le même schéma et la même tâche. SGR peut émettre plus ou moins de tokens qu’une réponse CoT libre.

Considérations de production

  1. Versionnez vos schémas de la même manière que vos APIs.
  2. Même avec SGR, les erreurs réseau et serveur doivent faire l’objet d’une gestion robuste.
  3. Enregistrez séparément la proposition et la décision de politique pour faciliter le débogage, conformément à vos règles de conservation et de caviardage des données.
  4. Recalculez les prix, limites, permissions et autres règles sémantiques dans le code applicatif avant utilisation ; testez les valeurs limites que le schéma seul ne peut pas rejeter.

Le prochain test

Commencez par la limite de remise et une complétion incomplète. Le contrôle offline couvre ces deux cas, mais il ne peut pas vous dire si un modèle route correctement un véritable client ou explique précisément la marge. Pour une évaluation live, maintenez fixes le modèle, les prompts, le schéma et les paramètres de serving. Comptabilisez séparément les résultats incomplets, les échecs de schéma, les erreurs de routing et les rejets de politique avant de comparer le coût ou la précision sur la tâche.
