Raisonnement guidé par schéma sur vLLM : sorties structurées grâce à xgrammar et Pydantic

Tenter à nouveau une appel à un LLM ne garantit pas l’obtention de JSON valide. Le prochain échantillon peut échouer de la même manière, et les appels répétés augmentent à la fois le temps de réponse et les coûts.

Le Raisonnement guidé par schéma (SGR) impose un schéma au modèle à chaque génération de token. Vous définissez les champs requis à l’aide de Pydantic, et le moteur d’inférence bloque les tokens qui contreviendraient à cette structure. Ainsi, le résultat est syntaxiquement valide dès sa création, sans avoir recours à des tentatives répétées.

En résumé. Le SGR utilise une décodage contraint pour aligner la sortie d’un LLM sur un schéma Pydantic que vous contrôlez. En le combinant avec le backend xgrammar de vLLM, vous obtenez systématiquement du JSON valide, avec des pertes de performance négligeables.

Qu’est-ce que le Raisonnement guidé par schéma ?

Le Raisonnement guidé par schéma est une technique décrite en 2024 par Rinat Abdullin. Au lieu de laisser le modèle compléter librement le texte (ce qui peut entraîner des résultats incohérents ou ambigus), vous lui fournissez un modèle strict qui définit :

  • les étapes qu’il doit suivre, afin qu’il ne puisse pas omettre l’analyse ;
  • l’ordre de ces étapes, de sorte que le raisonnement progresse des données vers la décision ;
  • les points sur lesquels il doit concentrer son attention, pour que la profondeur de l’analyse soit adaptée aux besoins.

Pensez-y comme à une liste de contrôle cognitive que le modèle doit respecter.

Ce que contrôle le schéma

Des champs tels que churn_analysis, margin_math et max_discount_percent précisent les sorties intermédiaires attendues. Le modèle doit remplir cette structure obligatoire avant de pouvoir retourner la décision finale concernant la remise.

Cela vous permet d’obtenir :

  • un raisonnement reproductible lors de multiples exécutions ;
  • des sorties auditable, où chaque étape peut être examinée ;
  • des champs intermédiaires que vous pouvez évaluer à l’aide d’un ensemble de données de test ;
  • des modèles plus petits, car le schéma impose déjà ce que le modèle aurait sinon dû apprendre ;
  • une amélioration de l’exactitude de 5 à 10 % selon les charges de travail réelles des utilisateurs initiaux, amélioration que vous devriez valider sur vos propres données.

Ingénierie des prompts : persuasion sémantique

Please analyze the customer data and output your response as valid JSON
with the following structure: {"discount": <number>, "reason": <string>}
Be careful with the formatting!

On espère que la compréhension du modèle concernant l’exigence “générer du JSON” l’emportera sur sa tendance à adopter un style conversationnel. Une mise à jour du modèle, une modification de la température ou un exemple différent de type few-shot peut cependant compromettre le fonctionnement de votre parser.

Chaîne de réflexion : meilleur raisonnement, même problème de structure

Let's think step by step:
1. First, I'll analyze the customer's churn risk...
2. Then I'll calculate the margin...
3. Therefore, I recommend a 15% discount.

La chaîne de réflexion améliore la précision du raisonnement, mais aggrave le problème de structure. Le résultat est une prose imprévisible qu’il est presque impossible de parser de manière fiable. Il faut généralement effectuer une deuxième appel à l’LLM uniquement pour extraire les données structurées.

SGR : chaîne de réflexion structurée

Le SGR conserve l’intuition de la chaîne de réflexion selon laquelle un raisonnement intermédiaire améliore la précision. Il se contente de formaliser les étapes :

class PricingLogic(BaseModel):
    # 1. Data Analysis (must complete before decision)
    churn_analysis: str = Field(..., description="Analyze churn_probability")
    financial_analysis: str = Field(..., description="Analyze cart_value and margin")

    # 2. Math Enforcement (explicit calculation)
    margin_math: str = Field(..., description="Calculate: 'Cart $X * Y% = $Z'")

    # 3. Decision Constraint (bounded by prior analysis)
    max_discount_percent: float = Field(..., description="Max allowed discount")

    # 4. Final Output
    offer_code: str
    customer_message: str

Le modèle ne peut pas générer max_discount_percent avant que churn_analysis, financial_analysis et margin_math soient remplis. Le schéma impose l’ordre du raisonnement.

Modèles de SGR

Le SGR comporte trois modèles de base qui s’assemblent pour former des workflows plus complexes.

1. Cascade : étapes de raisonnement séquentielles

La cascade impose un ordre précis de raisonnement. Chaque champ doit être complété avant de passer au suivant.

from pydantic import BaseModel
from typing import Literal, Annotated
from annotated_types import Ge, Le

class CandidateEvaluation(BaseModel):
    """Evaluate a job candidate with enforced reasoning order."""

    # Step 1: Summarize (forces context awareness)
    brief_candidate_summary: str

    # Step 2: Rate (bounded integer)
    rate_skill_match: Annotated[int, Ge(1), Le(10)]

    # Step 3: Decide (constrained choices)
    final_recommendation: Literal["hire", "reject", "hold"]

Cas d’usage adaptés : évaluation de candidats, classification de documents, analyse de conformité, diagnostic médical.

Le modèle doit d’abord écrire brief_candidate_summary avant de pouvoir évaluer, puis évaluer avant de pouvoir recommander. Il n’existe aucun raccourci.

2. Routing : instruction de sélection sémantique

Le routing pousse le modèle à choisir une voie parmi plusieurs options, ce qui est réalisé à l’aide de types Union.

from pydantic import BaseModel
from typing import Literal, Union

class FeatureLookup(BaseModel):
    """Route to database lookup."""
    rationale: str
    tool_name: Literal["fetch_user_features"] = "fetch_user_features"
    user_id: str

class GeneralResponse(BaseModel):
    """Standard response for non-pricing queries."""
    tool_name: Literal["respond"] = "respond"
    content: str

class RouterSchema(BaseModel):
    """The model must pick exactly ONE branch."""
    action: Union[FeatureLookup, GeneralResponse]

Cas d’usage adaptés : classification des intentions, sélection d’outils, tri des demandes de support, déploiement multi-agents.

Le discriminant Literal (tool_name) pousse le modèle à sélectionner une seule branche et à remplir uniquement les champs requis par celle-ci.

3. Cycle : raisonnement itératif avec des listes

Le mécanisme Cycle oblige le modèle à générer plusieurs éléments, en imposant des limites quant au nombre maximal.

from pydantic import BaseModel
from typing import List, Literal, Annotated
from annotated_types import MinLen, MaxLen

class RiskFactor(BaseModel):
    explanation: str
    severity: Literal["low", "medium", "high"]

class RiskAssessment(BaseModel):
    """Generate 2-4 risk factors."""
    factors: Annotated[List[RiskFactor], MinLen(2), MaxLen(4)]

Cas d’usage adaptés : évaluation des risques, extraction d’incidents, appels simultanés à des outils, planification multi‑étapes.

Les contraintes définies par MinLen et MaxLen exigent au moins 2 et au plus 4 éléments. En combinaison avec le mécanisme de routage, cela permet d’envoyer des lots de taille fixe d’appels à des outils.

Faire fonctionner SGR : décodage contraint

Les schémas présentés ci‑dessus ne sont que des structures Pydantic. Ce qui les rend contraignants, c’est le décodage contraint (également appelé sortie structurée).

Le décodage contraint modifie l’étape de génération des tokens. Au lieu de laisser le modèle choisir librement dans son vocabulaire, le moteur applique un masque grammatical qui bloque les tokens susceptibles de violer le schéma. Ce processus s’effectue au niveau du moteur d’inférence, et non dans le code de l’application.

[!TIP] SGR n’a pas besoin de « modèles de raisonnement » tels que o1 ou DeepSeek‑R1. Il fonctionne parfaitement avec des modèles entraînés sur des instructions, et encore mieux avec des modèles distillés à partir de modèles de raisonnement.

Pourquoi cet article se concentre sur vLLM et xgrammar

Quelques raisons :

  • vLLM est le moteur d’inférence de LLM open source le plus largement déployé, ce qui permet une portabilité aisée des solutions développées ici.
  • xgrammar étant implémenté en C++, il génère une latence négligeable.
  • L’API de vLLM est compatible avec OpenAI, ce qui réduit les coûts de migration depuis les fournisseurs cloud.
  • xgrammar gère efficacement des schémas imbriqués complexes, des unions ainsi que des structures récursives.

La section suivante explique comment xgrammar applique effectivement les contraintes de schéma au niveau des tokens.

Comment xgrammar applique les schémas

Il est essentiel de bien comprendre cette partie, car elle influence la manière dont on débogue et affine les workflows SGR.

Où a lieu le masquage

xgrammar modifie les logits de sortie après le passage en avant du modèle et avant l’échantillonnage. Il ne modifie pas le modèle lui-même ; il filtre simplement les tokens pouvant être sélectionnés.

Un cycle d’inférence standard se présente comme suit :

1. Input tokens → GPU Forward Pass → Logits (probability scores for all ~128K tokens)
2. Logits → Sampling (temperature, top-p, etc.) → Next Token
3. Repeat until done

xgrammar s’insère entre les étapes 1 et 2 :

1. Input tokens → GPU Forward Pass → Raw Logits
2. Raw Logits → xgrammar Logits Processor → Masked Logits
3. Masked Logits → Sampling → Next Token (guaranteed valid)
4. Repeat until done

Le modèle calcule toujours sa distribution de probabilités complète sur la GPU. xgrammar s’exécute ensuite sur la CPU et applique un masque binaire à ces logits avant l’échantillonnage. Les tokens invalides voient leurs logits fixés à -∞, ce qui fait que leur probabilité devient exactement 0 après application de la fonction softmax.

Deux phases

xgrammar divise le travail en phase de compilation et phase de exécution, ce qui explique sa rapidité.

Phase 1 : compilation de la grammaire, une fois par schéma

# This happens once per schema
tokenizer_info = xgr.TokenizerInfo.from_huggingface(tokenizer)
grammar_compiler = xgr.GrammarCompiler(tokenizer_info)
compiled_grammar = grammar_compiler.compile_json_schema(schema_json)

Lors de la compilation, xgrammar :

  1. Convertit le JSON Schema en une grammaire libre de contexte.
  2. Construit un automate à pile (PDA), c’est‑à‑dire un automate à états doté d’une pile, afin de gérer des structures imbriquées telles que {"a": {"b": {"c": ...}}}.
  3. Pré‑calcule quels tokens sont valides à chaque position de la grammaire. Le résultat constitue le « cache de masque de token adaptatif ».
  4. Catégorise les tokens en « indépendants du contexte » (pouvant être mémorisés dans le cache) ou « dépendants du contexte » (doivent être vérifiés en temps réel par rapport à l’état de la pile).

[!NOTE] Environ 99 % des tokens se révèlent indépendants du contexte et sont donc stockés dans le cache (XGrammar paper). La plupart des vérifications de validité en temps réel ne sont en réalité que des recherches dans le cache, ce qui explique la vitesse d’exécution de xgrammar.

Phase 2 : génération du masque en temps réel, pour chaque token

À chaque étape de génération :

  1. Le GrammarMatcher suit la position actuelle dans la grammaire.
  2. Il récupère le masque précalculé destiné aux tokens indépendants du contexte.
  3. Il exécute un automate à pile pour vérifier les tokens dépendants du contexte restants.
  4. Il combine ces derniers en un masque binaire final et l’applique aux logits.

Pourquoi des automates à pile plutôt que des expressions régulières ?

En raison du chevauchement de structures. Une expression régulière (une machine à états finis) ne peut pas reconnaître de manière fiable des structures telles que :

{ "user": { "profile": { "settings": { "theme": "dark" } } } }

La partie difficile concerne les crochets de fermeture }}} : il faut se souvenir du nombre ouvert. Un automate à pile dispose d’une pile qui enregistre ce comptage, lui permettant ainsi de gérer n’importe quelle profondeur de chevauchement. C’est également la raison pour laquelle xgrammar peut imposer des types Union, des objets imbriqués et des schémas récursifs, là où les approches basées sur les expressions régulières échouent.

Exemple concret : génération d’un champ flottant

Lorsque le modèle génère "max_discount_percent":, xgrammar sait, grâce au schéma, qu’un float suivra. Le masque :

  • autorise (probabilité inchangée) : 0, 1, 2, …, 9, ., -
  • bloque (probabilité mise à 0) : ", {, [, true, false, null, ainsi que le reste du vocabulaire de plus de 128 K éléments

La passe avant pourrait avoir attribué une haute probabilité au mot "fifteen". Après application du masque de xgrammar, cette token a une probabilité nulle. Le modèle doit donc produire des chiffres.

Pourquoi un « overhead » quasi nul ?

Trois raisons :

  1. Exécution parallèle. Le calcul du masque sur le CPU coïncide avec la prochaine passe avant sur le GPU. Tandis que le GPU calcule les logits pour le token N+1, le CPU calcule le masque pour le token N.
  2. Mémorisation. La majeure partie du travail de validation s’effectue au moment de la compilation ; en temps de exécution, il s’agit principalement de lectures dans la mémoire cache.
  3. Implémentation en C++. Le chemin critique est écrit en C++, et non en Python, et le masque est appliqué aux logits directement sur place.

Dans les benchmarks, xgrammar présente un overhead négligeable, et la génération structurée peut parfois être plus rapide que la génération non contrainte, car le vocabulaire restreint rend l’échantillonnage moins coûteux.

Étape 1 : définir les schémas

# sgr/models/schemas.py
from pydantic import BaseModel, Field
from typing import Literal, Union


# --- Phase 1: Routing (Union for branching) ---
class FeatureLookup(BaseModel):
    """Route to DB lookup if pricing context is needed."""
    rationale: str
    tool_name: Literal["fetch_user_features"] = "fetch_user_features"
    user_id: str


class GeneralResponse(BaseModel):
    """Standard response for non-pricing queries."""
    tool_name: Literal["respond"] = "respond"
    content: str


class RouterSchema(BaseModel):
    action: Union[FeatureLookup, GeneralResponse]


# --- Phase 2: Pricing Logic (Cascade for sequential reasoning) ---
class PricingLogic(BaseModel):
    """
    Strict reasoning topology for dynamic pricing.
    Fields are ordered to enforce the analysis→decision flow.
    """
    # 1. Data Analysis (Reflection)
    churn_analysis: str = Field(...,
        description="Analyze churn_probability (High > 0.7).")
    financial_analysis: str = Field(...,
        description="Analyze cart_value and profit_margin.")

    # 2. Hard Math Enforcement
    margin_math: str = Field(...,
        description="Calculate absolute profit: 'Cart $200 * 0.20 Margin = $40'.")

    # 3. The Decision Constraint
    max_discount_percent: float = Field(...,
        description="Max allowed discount %. NEVER exceed margin.")

    # 4. Final Output
    offer_code: str = Field(..., description="Generated code (e.g. SAVE20).")
    customer_message: str = Field(..., description="The final polite offer text.")

Étape 2 : un client LLM qui active xgrammar

# sgr/utils/llm_client.py
from openai import OpenAI
from pydantic import BaseModel
from typing import TypeVar
import json

T = TypeVar("T", bound=BaseModel)


class LLMClient:
    """Wrapper for vLLM with xgrammar-enforced structured generation."""

    def __init__(self, base_url: str = "http://localhost:8000/v1"):
        self.client = OpenAI(base_url=base_url, api_key="EMPTY")
        self.model = self._get_available_model()

    def _get_available_model(self) -> str:
        """Auto-detect the model running on vLLM server."""
        try:
            models = self.client.models.list()
            if models.data:
                return models.data[0].id
        except Exception:
            pass
        return "Qwen/Qwen2.5-7B-Instruct"

    def run_sgr(self, messages: list[dict], schema_class: type[T]) -> T:
        """Run inference with Schema-Guided Response constraints.

        Uses vLLM's guided_json with xgrammar backend to enforce
        strict schema constraints at the token generation level.
        """
        schema_dict = schema_class.model_json_schema()

        # Enhance system message with schema for model guidance
        enhanced_messages = messages.copy()
        if enhanced_messages and enhanced_messages[0]["role"] == "system":
            schema_json = json.dumps(schema_dict, indent=2)
            enhanced_messages[0] = {
                "role": "system",
                "content": (
                    enhanced_messages[0]["content"]
                    + f"\n\nRespond with JSON matching this schema:\n{schema_json}"
                ),
            }

        # vLLM's guided_json with the xgrammar backend
        completion = self.client.chat.completions.create(
            model=self.model,
            messages=enhanced_messages,
            temperature=0.1,  # Low temp for deterministic reasoning
            extra_body={
                "guided_json": schema_dict,  # Pydantic schema as dict
                "guided_decoding_backend": "xgrammar",  # Hardware-enforced
            },
        )

        raw_response = completion.choices[0].message.content
        return schema_class.model_validate_json(raw_response)

[!NOTE] > guided_json accepte un dictionnaire JSON Schema. Grâce à guided_decoding_backend: "xgrammar", le LLM ne peut générer que des tokens correspondant à un JSON valide conforme à votre schéma.

Étape 3 : orchestrer l’agent

# sgr/agent.py
from .models.schemas import PricingLogic, RouterSchema
from .prompts.routing import build_routing_prompt
from .prompts.pricing import build_pricing_context_prompt, ASSISTANT_FETCH_MESSAGE
from .store.hybrid_store import HybridFeatureStore
from .utils.llm_client import LLMClient


def pricing_agent(user_query: str, user_id: str) -> str:
    """Process a pricing query with three-phase SGR workflow."""

    llm = LLMClient()
    feature_store = HybridFeatureStore()

    # Build conversation history
    history = [
        {"role": "system", "content": build_routing_prompt(user_id)},
        {"role": "user", "content": user_query},
    ]

    # --- Phase 1: Routing (Uses RouterSchema) ---
    print(f"🤖 Processing: '{user_query}' for {user_id}")
    decision = llm.run_sgr(history, RouterSchema)
    print(f"📍 Routing decision: {decision.action.tool_name}")

    if decision.action.tool_name == "respond":
        return decision.action.content

    # --- Phase 2: Context Retrieval ---
    if decision.action.tool_name == "fetch_user_features":
        print(f"🔍 Fetching features for {user_id}...")
        context = feature_store.get_user_context(user_id)

        if not context:
            return "Error: User profile not found."

        print(f"   [Data] LTV: ${context.get('user_ltv')} | "
              f"Margin: {context.get('cart_profit_margin', 0) * 100}%")

        # Inject context into conversation
        history.append({"role": "assistant", "content": ASSISTANT_FETCH_MESSAGE})
        history.append({
            "role": "user",
            "content": build_pricing_context_prompt(
                churn_prob=context.get("churn_probability", 0.5),
                cart_val=context.get("current_cart_value", 100),
                margin=context.get("cart_profit_margin", 0.2),
                user_ltv=context.get("user_ltv", 0),
            ),
        })

        # --- Phase 3: SGR Logic Execution (Uses PricingLogic) ---
        print("🧠 Calculating Offer (Schema Enforced)...")
        offer = llm.run_sgr(history, PricingLogic)

        # Audit log — the SGR benefit: explicit reasoning traces
        print(f"   [Audit] Math: {offer.margin_math}")
        print(f"   [Audit] Max Allowed: {offer.max_discount_percent}%")

        return offer.customer_message

    return "I'm sorry, I couldn't process your request."


if __name__ == "__main__":
    response = pricing_agent("I want a discount or I'm leaving!", "user_102")
    print(f"\n💬 Final Reply: {response}")

Bonnes pratiques

Conception des schémas

  1. Organisez les champs selon le flux de raisonnement : les champs d’analyse doivent précéder ceux de décision.
  2. Rédigez des descriptions Field explicites. Elles orientent l’attention du modèle tout autant que le nom du champ.
  3. Imposez des contraintes à l’aide de Literal et Annotated. Utilisez Literal["a", "b"] pour les énumérations et Annotated[int, Ge(1), Le(10)] pour les plages de valeurs.
  4. Gardez les schémas ciblés : un schéma par phase de raisonnement, puis combinez-les via plusieurs appels.

Configuration de vLLM

  1. Employez une température faible (0,1–0,3) pour assurer un raisonnement déterministe.
  2. Laissez xgrammar gérer la structure ; évitez d’introduire des instructions de formatage dans le prompt.
  3. Surveillez l’utilisation des tokens. Le SGR consomme généralement moins de tokens que le CoT, car il ne nécessite pas de prose verbose.

Considérations en environnement de production

  1. Versionnez vos schémas de la même manière que vous versionnez vos APIs.
  2. Même avec le SGR, les erreurs réseau ou serveur exigent toujours un traitement adapté.
  3. Enregistrez les sorties brutes du SGR aux fins de conformité et de débogage.
  4. Testez avec des cas limites afin de garantir la robustesse des schémas aux frontières.

Conclusion

Le SGR permet de passer d’un fonctionnement uniquement en environnement de démonstration à un fonctionnement fiable en production. Vous définez la topologie de raisonnement via Pydantic, laissez xgrammar la faire respecter au moment du décodage, ce qui donne comme résultats :

  • des sorties toujours valides, sans boucles de tentative ni erreurs de parsing,
  • une traçabilité au niveau des champs,
  • une compatibilité avec des modèles plus petits, puisqu’ils n’ont plus besoin de gérer eux-mêmes le format,
  • des coûts d’exécution réduits, grâce à une utilisation moindre de tokens, de tentatives et de modèles.

La démo sgr-discount-manager relie chaque exemple de code présenté dans cet article à un serveur vLLM réel. Cloniez-la et commencez à adapter les schémas à votre propre flux de travail.

Points clés

  1. Le Reasoning guidé par des schémas rend explicite la topologie de raisonnement, plutôt que de compter sur le fait que le modèle suive des instructions textuelles.
  2. Le décodage contraint empêche la génération de JSON invalide dès le départ, ce qui est plus efficace que de valider et de réessayer ultérieurement.
  3. Placez les champs d’analyse avant ceux de décision lorsque le schéma doit imposer un raisonnement préalable à l’affichage.
  4. Utilisez le SGR lorsque du code ultérieur dépend de la structure, et non lorsque le produit final doit être sous forme de prose libre.
