LLM locaux sur macOS : Ollama, LM Studio, llama.cpp, MLX et Apple Silicon

De nombreuses requêtes courantes n’ont pas besoin d’une API distante. Apple Silicon permet d’exécuter des modèles de langage utiles en local, car le CPU et la GPU partagent un pool mémoire unifié, bien que le fichier du modèle ne constitue qu’une partie du budget mémoire disponible.

Le critère principal dans ce guide est l’outil associé au modèle. Ollama, LM Studio, llama.cpp et MLX-LM présentent des similitudes, mais offrent différents niveaux de contrôle : un service local géré, une exploration depuis le poste de travail, une exécution directe des fichiers GGUF, ou encore l’utilisation de Python natif d’Apple. Choisissez d’abord le modèle en fonction de la qualité attendue, puis l’outil en fonction de l’interface et des artefacts nécessaires.

En résumé. Utilisez Ollama pour un service local géré, LM Studio pour l’exploration visuelle des modèles depuis le bureau ainsi que ses API locales, llama.cpp pour un contrôle direct de l’exécution des fichiers GGUF, et MLX-LM pour expérimenter avec Python natif d’Apple. Aucun outil n’est systématiquement le plus rapide. Effectuez des benchmarks avec le modèle précis, le niveau de quantification, la longueur du contexte et la charge de travail, en tenant compte de l’espace mémoire restant.

Commencer par définir le budget mémoire

La taille brute des poids quantifiés n’est que le premier facteur à prendre en compte :

peak memory ≈ model weights
            + KV cache
            + runtime workspace
            + multimodal components
            + application and OS memory

La longueur du contexte, le type de données du cache, le nombre de requêtes simultanées et l’architecture du modèle influencent également ce résultat. Un modèle de 7 G ou 8 G de paramètres quantifié en quatre bits peut encore poser problème sur un Mac équipé de 8 GB de mémoire, car le système d’exploitation ne peut pas attribuer toute la mémoire installée au processus en cours d’exécution.

Utilisez le Gestionnaire d’activités ou les métriques fournies par le runtime lors des tests. Prévoyez suffisamment d’espace mémoire pour éviter toute pression mémoire et tout recours au swap ; un modèle qui se charge mais force le système à utiliser constamment le swap n’est pas adapté à un usage interactif.

Il convient également de distinguer l’inférence locale de le fonctionnement hors ligne. Les requêtes peuvent rester sur la machine, tandis que l’application continue d’accéder au réseau afin de télécharger des modèles, des mises à jour ou des fonctionnalités optionnelles. Téléchargez d’abord les artefacts, déconnectez-vous du réseau, puis vérifiez le flux de travail si un fonctionnement hors ligne est requis.

Il s’agit d’un tableau des responsabilités, non d’un classement par vitesse. Plusieurs outils peuvent utiliser des noyaux ou des formats similaires, et les performances varient en fonction du support des modèles et des versions disponibles.

Ollama : service local géré

Ollama gère les téléchargements de modèles, les templates, le cycle de vie des processus ainsi qu’une API accessible en localhost. Il s’avère utile lorsque le code d’une application doit faire référence à un service local fiable plutôt qu’à des paramètres d’inférence personnalisés.

ollama pull <model>
ollama run <model>

curl http://localhost:11434/api/chat \
    -H 'Content-Type: application/json' \
    -d '{
      "model": "<model>",
      "messages": [{"role": "user", "content": "Explain unified memory."}],
      "stream": false
    }'

Il convient d’examiner le manifeste du modèle et la configuration du contexte, au lieu de supposer que le nom d’une bibliothèque court identifie automatiquement un checkpoint immuable. Il est nécessaire de fixer ou de consigner l’artefact exact pour effectuer des évaluations.

Ollama sacrifie une certaine visibilité au niveau bas pour simplifier la gestion du cycle de vie. Recourir à llama.cpp ou à un autre runtime est recommandé lorsque l’on souhaite contrôler directement un fichier GGUF, un template de conversation, une configuration de cache ou une nouvelle fonctionnalité backend.

LM Studio : exploration desktop et APIs locales

LM Studio est pratique lorsqu’il est nécessaire de découvrir des modèles, de configurer leur chargement, d’inspecter les conversations et d’évaluer manuellement en parallèle, tout cela au sein d’un même flux de travail desktop. Son serveur prend en charge des SDK natifs ainsi que des points d’entrée de compatibilité.

Voici à quoi ressemble l’utilisation actuelle du SDK Python :

import lmstudio as lms


with lms.Client() as client:
    model = client.llm.model("<downloaded-model-key>")
    response = model.respond("Write one sentence about local inference.")
    print(response)

Il est possible de démarrer l’API locale depuis l’onglet Développeur ou via :

lms server start

LM Studio peut fonctionner en localhost ou sur un réseau local et prend en charge les jetons API. Préférez le mode loopback sauf si un accès distant est explicitement requis ; en effet, lier le service au réseau transforme un modèle desktop privé en un service nécessitant une authentification, des règles de pare-feu et une configuration sécurisée des outils.

llama.cpp : exécution directe de fichiers GGUF

llama.cpp constitue la solution de référence lorsque l’artefact est au format GGUF et que l’on souhaite observer directement les limites du runtime. Ce dernier prend en charge Apple Metal en plus du CPU et d’autres backends matériels.

brew install llama.cpp

# Download through the Hugging Face integration and select a quantization.
llama-cli -hf <publisher>/<gguf-repository>:Q4_K_M

# Or start an OpenAI-compatible local server.
llama-server -hf <publisher>/<gguf-repository>:Q4_K_M

Le chemin -hf présent dans le répertoire permet de télécharger un projeteur multimodal correspondant, le cas échéant. La compatibilité avec les modèles, les templates et les paramètres CLI évolue rapidement ; il est donc conseillé de fixer une version connue et de conserver la commande de lancement accompagnée des données d’évaluation.

Préférez llama.cpp lorsque le contrôle direct est un objectif, et non parce que le niveau bas implique automatiquement des performances supérieures. Un outil géré peut proposer des valeurs par défaut optimales ; en revanche, l’utilisation de paramètres directs peut également entraîner une baisse des performances.

MLX-LM : travail en Python natif sur Apple

MLX-LM s’appuie sur le framework d’arrays MLX d’Apple. Il prend en charge la génération de texte, les conversations, la conversion de formats, la quantification ainsi que le fine-tuning efficace en termes de paramètres pour les modèles compatibles.

uv add mlx-lm
uv run mlx_lm.generate \
    --model mlx-community/<compatible-model> \
    --prompt "Explain Metal acceleration in one paragraph."

En Python, le modèle et le tokenizer sont exposés directement :

from mlx_lm import generate, load


model, tokenizer = load("mlx-community/<compatible-model>")
messages = [{"role": "user", "content": "Give one local-LLM benchmark rule."}]
prompt = tokenizer.apply_chat_template(
    messages,
    tokenize=False,
    add_generation_prompt=True,
)
print(generate(model, tokenizer, prompt=prompt, max_tokens=80))

Le serveur HTTP de MLX-LM est décrit comme un serveur de développement disposant de mécanismes de sécurité de base, et non comme un service destiné à un environnement de production. Utilisez-le pour des expérimentations locales ou placez devant lui une couche d’application ayant fait l’objet d’une validation rigoureuse.

Un benchmark fiable prend moins de temps qu’un téléchargement défaillant

Testez les mêmes familles de checkpoints ainsi que des niveaux de quantification comparables, dans la mesure où les formats le permettent. Utilisez un petit ensemble de prompts comprenant :

  • un prompt interactif court
  • un prompt long proche du contexte attendu
  • des sorties structurées ou des appels à des outils si nécessaire
  • une longueur de génération représentative
  • une demande répétée afin de distinguer un chargement initial d’une inférence après préchauffage

Il ne faut pas comparer un modèle à 4 bits d’un outil avec un modèle à précision complète d’un autre outil, ni attribuer cette différence au temps d’exécution.

Liste de contrôle sécurité et confidentialité

  1. Associez les API au réseau loopback sauf si un accès réseau est requis.
  2. Ajoutez une authentification avant toute exposition sur le LAN.
  3. Traitez les fichiers de modèle comme des artefacts tiers ; enregistrez l’origine, la version, la licence et son hash.
  4. Évitez d’exécuter du code de modèle personnalisé non examiné.
  5. Vérifiez si les fonctionnalités optionnelles (documents, outils, mises à jour ou analyses) effectuent des appels réseau.
  6. Ne supposez pas que la génération locale rend les documents récupérés, les journaux ou les effets secondaires de l’outil sûrs.

Conclusion

Le choix pertinent n’est pas « le meilleur logiciel LLM pour Mac ». Il s’agit plutôt du stack le plus minimal qui offre l’interface de contrôle nécessaire à votre flux de travail. Ollama gère le service, LM Studio gère le cycle d’exploration sur poste de travail, llama.cpp permet l’exécution de fichiers GGUF, et MLX-LM prend en charge le Python natif d’Apple.

Attribuez à chaque solution candidate la même tâche, le même contexte et les mêmes ressources mémoire. Les résultats obtenus seront plus fiables que les croyances populaires liées au matériel ou des tableaux statiques de notation — et faciles à reconsidérer en cas de changement d’outil.
