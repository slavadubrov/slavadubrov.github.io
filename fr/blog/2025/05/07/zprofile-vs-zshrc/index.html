Fichiers de démarrage de Zsh : ~/.zprofile contre ~/.zshrc sous macOS et Linux

Si votre terminal semble lent, ou si une variable d’environnement apparaît dans un terminal mais pas dans un autre, la cause est souvent le mode de démarrage de Zsh. Les deux fichiers auxquels les utilisateurs ont généralement recours sont ~/.zprofile et ~/.zshrc, mais aucun de ces noms de fichiers ne permet de déterminer à lui seul si une ligne doit y être placée.

Zsh sélectionne les fichiers de démarrage en fonction de deux critères indépendants : le fait que le shell soit un shell de connexion et qu’il soit interactive. Les applications de terminal sous macOS et Linux peuvent choisir différentes combinaisons, il convient donc d’examiner le shell en cours d’exécution plutôt que de supposer que c’est le système d’exploitation qui décide à sa place.

En résumé. Placez l’initialisation des sessions de connexion dans .zprofile et le comportement interactif dans .zshrc. Gardez .zshenv silencieux et minimal. Ne transférez pas les hooks de gestion de versions interactifs dans .zprofile, ni n’importez tout le profil depuis .zshrc ; examinez plutôt le code généré par l’outil et suivez ses instructions Zsh actuelles.

Zsh évalue deux indicateurs indépendants

Un shell peut être :

  • à la fois de connexion et interactif, comme c’est le cas lorsque Apple Terminal lance habituellement le shell de connexion par défaut de l’utilisateur
  • non de connexion mais interactif, comme lorsqu’un zsh imbriqué ou de nombreuses configurations de terminal Linux le lancent
  • de connexion mais non interactif, comme avec zsh -lc 'command'
  • ni de connexion ni interactif, comme avec zsh -c 'command'

Les applications de terminal, les IDE, les sessions distantes, les multiplexeurs ainsi que les indicateurs explicites du shell peuvent choisir différents modes. Le système d’exploitation seul ne détermine pas ce mode.

Demandez au shell en cours d’exécution plutôt que de deviner :

print -r -- "interactive=$options[interactive] login=$options[login]"

Ordre réel de démarrage

Zsh lit d’abord les fichiers globaux, puis le fichier correspondant pour l’utilisateur. Avec les paramètres par défaut RCS, l’ordre des fichiers utilisateur est le suivant :

  1. $ZDOTDIR/.zshenv à chaque invocation de Zsh
  2. $ZDOTDIR/.zprofile si le shell est un shell de connexion
  3. $ZDOTDIR/.zshrc si le shell est interactive
  4. $ZDOTDIR/.zlogin si le shell est un shell de connexion
  5. $ZDOTDIR/.zlogout lorsque un shell de connexion se termine normalement

Si ZDOTDIR n’est pas défini, Zsh utilise $HOME. Les emplacements des fichiers au niveau système dépendent de l’installation ; les valeurs par défaut courantes sont /etc/zshenv, /etc/zprofile, /etc/zshrc, /etc/zlogin et /etc/zlogout.

Cet ordre constitue un filtre, et non une garantie liée au cycle de vie du processus. .zprofile s’exécute une fois par processus de shell de connexion, et non une fois par connexion au système. Si chaque nouvelle fenêtre de terminal lance un shell de connexion, chaque fenêtre le lit alors.

Gardez .zshenv simple

Chaque zsh -c non interactif lit .zshenv. La présence d’un echo, d’une invocation de gestionnaire de paquets ou d’un sous-processus coûteux peut corrompre l’output des commandes et ralentir les scripts. La plupart des utilisateurs n’ont besoin que de très peu, voire rien, dans ce fichier.

Une variable exportée dans .zprofile est héritée par les enfants de cet interpréteur de connexion. Elle n’est pas injectée automatiquement dans des applications GUI, des services ou des interpréteurs indépendants dont le parent n’a jamais lu le fichier.

Utilisez .zprofile pour la configuration réservée aux connexions

Un petit profil peut définir des valeurs par défaut exportées ainsi qu’un chemin idempotent :

# ~/.zprofile
export EDITOR=nvim
export VISUAL=nvim

# Zsh ties the path array to the PATH scalar.
typeset -U path PATH
path=("$HOME/.local/bin" $path)
export PATH

typeset -U supprime les éléments dupliqués des tableaux. Cela rend la relecture répétée plus sûre, bien que les fichiers de démarrage doivent néanmoins éviter tout travail inutile.

Utilisez .zshrc pour l’état interactif

# ~/.zshrc
setopt auto_cd hist_ignore_all_dups share_history

autoload -Uz compinit
compinit

alias ll='ls -lah'
bindkey -e

Les alias, les widgets de complétion, les mappages de touches, les prompts et les hooks de changement de répertoire appartiennent à l’interpréteur interactif qui les utilise.

Les gestionnaires de versions franchissent les limites simples des fichiers

Le conseil selon lequel « on doit placer les gestionnaires de versions dans .zprofile car ils sont lents » est peu fiable. Un gestionnaire de versions peut générer plusieurs types de codes :

  • un chemin statique ou une variable racine
  • un chemin de shim de commande nécessaire aux processus enfants
  • des définitions de complétion
  • des fonctions d’interpréteur modifiant l’interpréteur courant
  • des hooks de changement de répertoire permettant un basculement automatique de version

Les parties interactives doivent exister dans chaque interpréteur interactif, y compris dans un zsh imbriqué lancé depuis un éditeur. La documentation actuelle de fnm place donc ce hook dans .zshrc :

eval "$(fnm env --use-on-cd --shell zsh)"

De même, la documentation actuelle de pyenv place toute l’initialisation interactive dans .zshrc :

export PYENV_ROOT="$HOME/.pyenv"
[[ -d $PYENV_ROOT/bin ]] && path=("$PYENV_ROOT/bin" $path)
eval "$(pyenv init - zsh)"

Pyenv décrit un mode pyenv init --path plus restreint pour la configuration des chemins shim, mais le mode complet pyenv init installe également des fonctionnalités de complétion ainsi que des fonctions de shell. Il convient d’examiner la documentation actuelle d’un outil ainsi que son output généré avant de le diviser en composants.

Si le démarrage est lent, il faut mesurer ce temps avant de transférer du code vers un mode qui rend ce processus impossible.

Ne charger pas l’intégralité du profil depuis .zshrc

Une solution courante fonctionnant sur tous les systèmes est :

# Avoid this blanket coupling.
source ~/.zprofile

Cette approche transforme les actions réservées au seul accès en ligne de commande en actions spécifiques à chaque shell interactif, ce qui peut entraîner une exécution répétée du démarrage de l’agent, d’accès au trousseau de clés, de génération d’output ou de modification de chemins.

Lorsque tant les shells interactifs en mode connexion qu’en mode hors connexion nécessitent un petit ensemble d’exports statiques, il faut extraire un fragment idempotent et le charger délibérément :

# ~/.config/zsh/environment.zsh
typeset -U path PATH
path=("$HOME/.local/bin" $path)
export PATH EDITOR=nvim VISUAL=nvim
# ~/.zprofile
source "$HOME/.config/zsh/environment.zsh"
# ~/.zshrc
if [[ ! -o login ]]; then
  source "$HOME/.config/zsh/environment.zsh"
fi

# Interactive-only configuration follows.

Ce schéma permet de séparer les données partagées des effets secondaires liés à la connexion. Une autre option valable consiste à configurer de manière cohérente le terminal ou le gestionnaire de sessions, plutôt que de prendre en charge les deux modes simultanément.

Diagnostiquer le shell qui présente des retards ou manque d’état

Il faut reproduire directement chaque mode :

zsh -lic 'print "login interactive"'
zsh -ic  'print "non-login interactive"'
zsh -lc  'print "login non-interactive"'
zsh -c   'print "non-login non-interactive"'

Mesurer le mode que les utilisateurs lancent réellement :

time zsh -lic exit
time zsh -ic exit

Suivre le fichier de traçage ainsi que l’exécution ligne par ligne lorsque la source est incertaine :

PS4='%N:%i> ' zsh -xlic exit

Exécuter le fichier de traçage dans un compte de test propre ou l’analyser avant de le partager : les commandes de démarrage peuvent modifier des tokens ainsi que d’autres valeurs sensibles.

En cas d’exécutable manquant, il faut examiner à la fois le mode concerné et le chemin associé :

print -r -- "interactive=$options[interactive] login=$options[login]"
print -l -- $path

Conclusion

La distinction pertinente n’est pas « environnement contre alias ». Elle concerne plutôt l’état réservé au seul accès en ligne de commande par rapport à l’état interactif, ainsi que la petite quantité d’éléments qui doivent réellement affecter chaque processus Zsh.

Il faut confirmer les flags du shell, garder les fichiers de démarrage discrets, et placer chaque crochet généré là où toutes ses fonctionnalités requises sont disponibles. Cela permet une configuration portable entre différentes applications de terminal, sans prétendre que macOS et Linux disposent chacun d’un mode de démarrage fixe.
