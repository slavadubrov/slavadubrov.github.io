Fichiers de démarrage Zsh : .zprofile ou .zshrc sur macOS et Linux

Viacheslav Dubrov

2025-05-07 · Mis à jour 2026-07-15 · 5 min · Outils de développement

Traduction automatique Cet article a été traduit automatiquement depuis la version originale en anglais.

Si votre terminal semble lent, ou si une variable d’environnement apparaît dans un terminal mais pas dans un autre, la cause vient souvent du mode de démarrage de Zsh. Les deux fichiers que la plupart des utilisateurs consultent sont ~/.zprofile et ~/.zshrc, mais aucun de ces noms ne suffit à déterminer si une ligne doit y figurer.

Zsh choisit ses fichiers de démarrage selon deux propriétés indépendantes : le shell est-il un login shell et est-il interactif ? Les applications de terminal sur macOS et Linux peuvent choisir des combinaisons différentes ; inspectez donc le shell en cours plutôt que de supposer que le système d’exploitation décide à votre place.

En bref. Placez l’initialisation de la session de connexion dans .zprofile et le comportement interactif dans .zshrc. Gardez .zshenv silencieux et minimal. Ne déplacez pas les hooks interactifs d’un gestionnaire de versions dans .zprofile et ne sourcez pas l’intégralité du profile depuis .zshrc ; consultez le code généré par l’outil et suivez ses instructions Zsh actuelles.

Zsh évalue deux indicateurs indépendants

Un shell peut être :

  • login et interactif, comme Apple Terminal le fait normalement lorsqu’il lance le login shell par défaut du compte
  • non-login et interactif, comme un zsh imbriqué ou de nombreuses configurations de terminaux Linux
  • login et non interactif, comme zsh -lc 'command'
  • non-login et non interactif, comme zsh -c 'command'

Les applications de terminal, les IDE, les sessions distantes, les multiplexeurs et les options explicites du shell peuvent sélectionner des modes différents. Le système d’exploitation seul ne détermine donc pas le résultat.

Demandez directement au shell en cours plutôt que de deviner :

print -r -- "interactive=$options[interactive] login=$options[login]"

L’ordre réel de démarrage

Zsh lit les fichiers globaux, puis le fichier utilisateur correspondant. Avec les options RCS par défaut, l’ordre des fichiers utilisateur est le suivant :

  1. $ZDOTDIR/.zshenv pour chaque invocation de Zsh
  2. $ZDOTDIR/.zprofile si le shell est un login shell
  3. $ZDOTDIR/.zshrc si le shell est interactif
  4. $ZDOTDIR/.zlogin si le shell est un login shell
  5. $ZDOTDIR/.zlogout lorsqu’un login shell se termine normalement

Si ZDOTDIR n’est pas défini, Zsh utilise $HOME. Les emplacements des fichiers propres au système dépendent de l’installation ; les valeurs par défaut courantes sont /etc/zshenv, /etc/zprofile, /etc/zshrc, /etc/zlogin et /etc/zlogout.

.zprofile est exécuté une fois par processus de login shell, et non une fois par connexion à l’ordinateur. Si chaque nouvel onglet de terminal démarre un login shell, chaque onglet le lit.

Gardez .zshenv ennuyeux

Tout zsh -c non interactif lit .zshenv. Un echo, un appel à un gestionnaire de paquets ou un sous-processus coûteux à cet endroit peut corrompre la sortie des commandes et ralentir les scripts. La plupart des utilisateurs n’ont besoin de presque rien dans ce fichier.

Une variable exportée dans .zprofile est héritée par les processus enfants de ce login shell. Elle n’est pas automatiquement injectée dans des applications GUI, des services ou des shells indépendants dont le parent n’a jamais lu le fichier.

Utilisez .zprofile pour la configuration réservée à la connexion

Un profile minimal peut définir des valeurs par défaut exportées et un PATH idempotent :

# ~/.zprofile
export EDITOR=nvim
export VISUAL=nvim

# Zsh ties the path array to the PATH scalar.
typeset -U path PATH
path=("$HOME/.local/bin" $path)
export PATH

typeset -U supprime les doublons dans les entrées du tableau. Cela rend les sources répétées plus sûres, même si les fichiers de démarrage doivent toujours éviter le travail inutile.

Utilisez .zshrc pour l’état interactif

# ~/.zshrc
setopt auto_cd hist_ignore_all_dups share_history

autoload -Uz compinit
compinit

alias ll='ls -lah'
bindkey -e

Les alias, widgets de complétion, raccourcis clavier, prompts et hooks de changement de répertoire appartiennent au shell interactif qui les utilise.

Les gestionnaires de versions dépassent la simple séparation entre fichiers

Byte says

J’ai déplacé pyenv vers .zprofile pour accélérer l’ouverture des nouveaux onglets. Les nouveaux onglets se sont ouverts plus vite. Le shell de mon éditeur a perdu toutes les fonctions et complétions de pyenv, car il ne lit jamais .zprofile.

« Placez les gestionnaires de versions dans .zprofile parce qu’ils sont lents » est un conseil peu fiable. Un gestionnaire de versions peut produire plusieurs types de code :

  • une variable statique de PATH ou de racine
  • un chemin vers un shim de commande requis par les processus enfants
  • des définitions de complétion
  • des fonctions shell qui modifient le shell courant
  • des hooks de changement de répertoire pour changer automatiquement de version

Les éléments interactifs doivent exister dans chaque shell interactif, y compris dans un zsh imbriqué lancé depuis un éditeur. La documentation actuelle de fnm place donc ce hook dans .zshrc :

eval "$(fnm env --use-on-cd --shell zsh)"

La documentation actuelle de pyenv place également l’initialisation interactive complète dans .zshrc :

export PYENV_ROOT="$HOME/.pyenv"
[[ -d $PYENV_ROOT/bin ]] && path=("$PYENV_ROOT/bin" $path)
eval "$(pyenv init - zsh)"

Pyenv documente un mode pyenv init --path plus limité pour configurer le chemin des shims, mais le mode pyenv init complet installe aussi la complétion et les fonctions shell. Consultez la documentation actuelle de l’outil et sa sortie générée avant de les répartir.

Si le démarrage est lent, mesurez-le avant de déplacer du code vers un mode dans lequel il ne fonctionnera plus.

Ne sourcez pas l’intégralité du profile depuis .zshrc

Une solution de contournement courante entre les plateformes consiste à faire ceci :

# Avoid this blanket coupling.
source ~/.zprofile

Cela transforme les actions réservées à la connexion en actions exécutées par chaque shell interactif et peut répéter le démarrage d’un agent, l’accès au trousseau, la sortie ou la modification du PATH.

Si les shells interactifs login et non-login ont tous deux besoin d’un petit ensemble d’exports statiques, extrayez un fragment idempotent et sourcez-le explicitement :

# ~/.config/zsh/environment.zsh
typeset -U path PATH
path=("$HOME/.local/bin" $path)
export PATH EDITOR=nvim VISUAL=nvim
# ~/.zprofile
source "$HOME/.config/zsh/environment.zsh"
# ~/.zshrc
if [[ ! -o login ]]; then
  source "$HOME/.config/zsh/environment.zsh"
fi

# Interactive-only configuration follows.

Ce pattern sépare les données partagées des effets de bord réservés à la connexion. Une autre option valide consiste à configurer le terminal ou le gestionnaire de session de manière cohérente, plutôt que de prendre en charge les deux modes.

Diagnostiquez le shell lent ou privé de son état

Reproduisez directement chaque mode :

zsh -lic 'print "login interactive"'
zsh -ic  'print "non-login interactive"'
zsh -lc  'print "login non-interactive"'
zsh -c   'print "non-login non-interactive"'

Mesurez le mode réellement lancé par les utilisateurs :

time zsh -lic exit
time zsh -ic exit

Tracez l’exécution des fichiers et des lignes lorsque la source du problème n’est pas claire :

PS4='%N:%i> ' zsh -xlic exit

Exécutez le trace dans un compte de test propre ou inspectez-le avant de le partager : les commandes de démarrage peuvent développer des tokens et d’autres valeurs sensibles.

Pour un exécutable introuvable, inspectez à la fois le mode et le PATH :

print -r -- "interactive=$options[interactive] login=$options[login]"
print -l -- $path

Conclusion

La distinction utile n’est pas « environnement contre alias ». Il s’agit de l’état réservé à la connexion par rapport à l’état interactif, ainsi que de la petite quantité de configuration qui doit réellement affecter chaque processus Zsh.

Confirmez les indicateurs du shell, gardez les fichiers de démarrage silencieux et placez chaque hook généré là où toutes ses fonctionnalités requises sont disponibles. La configuration devient ainsi portable entre les applications de terminal, sans prétendre que macOS et Linux possèdent chacun un mode de lancement unique et fixe.
