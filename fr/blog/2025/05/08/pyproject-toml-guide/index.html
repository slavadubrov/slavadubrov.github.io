pyproject.toml Guide : emballage Python, dépendances et configuration des outils

Les projets Python plus anciens répartissent souvent les configurations dans setup.py, setup.cfg, des fichiers de requirements, MANIFEST.in, ainsi que dans des fichiers distincts destinés aux outils de développement. pyproject.toml offre un espace centralisé pour gérer ces éléments, bien qu’il ne remplace pas tous les fichiers de projet ni ne fait de chaque section une partie d’un format standard unique.

Ce guide examine ce fichier, du point de vue de la configuration de compilation jusqu’aux métadonnées du projet et aux paramètres des outils. Pour en faciliter la compréhension, il est préférable de distinguer quatre responsables : celui qui compile le projet, celui qui publie les résultats, ceux dont les contributions nécessitent des ressources locales, et ceux qui configurent les outils individuels.

En résumé. Utilisez [build-system] pour le backend chargé de créer la distribution, [project] pour les métadonnées publiées ainsi que les dépendances en temps de exécution, [dependency-groups] pour les environnements de développement non publiés, et [tool.*] uniquement lorsque la documentation de l’outil l’exige. Une déclaration de dépendance n’est pas un fichier de verrouillage.

Un seul fichier, quatre responsables

Trois normes d’emballage ont défini la structure de base :

  • PEP 518 définit les exigences relatives au système de compilation.
  • PEP 621 définit les métadonnées du projet.
  • PEP 735 définit les groupes de dépendances non publiés.

Les auteurs d’outils peuvent également réserver un espace nommé sous [tool]. Cette zone est conventionnelle et non universelle : chaque outil définit ses propres clés et comportements.

Voici un petit exemple de bibliothèque emballée :

[build-system]
requires = ["hatchling>=1.26"]
build-backend = "hatchling.build"

[project]
name = "weather-client"
version = "0.1.0"
description = "A small weather API client"
readme = "README.md"
requires-python = ">=3.11"
dependencies = [
  "httpx>=0.27",
]

[project.optional-dependencies]
cli = ["rich>=13"]

[project.scripts]
weather = "weather_client.cli:main"

[dependency-groups]
test = ["pytest>=8", "pytest-cov>=5"]
lint = ["ruff>=0.12"]

[tool.pytest.ini_options]
testpaths = ["tests"]

[tool.ruff]
line-length = 100
target-version = "py311"

Chaque liste de dépendances répond à une question différente. C’est cette distinction qui constitue le cœur du fichier.

[build-system] : comment le code source devient une distribution

Un front-end de compilation tel que python -m build, pip ou uv invoque un back-end de compilation. Ce dernier décide de la manière dont l’arbre de source est transformé en sdist ou wheel, ainsiquels fichiers sont inclus dans ces artefacts.

[build-system]
requires = ["hatchling>=1.26"]
build-backend = "hatchling.build"

requires contient les dépendances nécessaires pour exécuter le back-end dans son environnement de compilation isolé. Il ne s’agit pas de la liste des dépendances en temps de exécution de votre paquet.

Déclarez un système de compilation lorsque le projet génère une distribution ou a besoin que son propre code soit installé en tant que paquet. Un projet qui n’est pas un paquet peut néanmoins utiliser pyproject.toml ; PEP 735 autorise même un fichier ne contenant que des groupes de dépendances. Les gestionnaires d’environnement diffèrent quant à la façon dont ils traitent les projets sans système de compilation, il convient donc de faire ce choix en connaissance de cause.

Choisissez le back-end en fonction des exigences de compilation :

  • besoins liés à une architecture pure-Python et à la sélection des fichiers,
  • extensions compilées ou systèmes de compilation externes,
  • exigences de version dynamique ou de fichiers générés,
  • comportement d’installation éditable,
  • maturité du back-end dans la chaîne de déploiement.

Copiez le tableau recommandé actuel du back-end depuis sa documentation. Ne rajoutez pas wheel aux exigences de compilation par habitude ; c’est le back-end lui-même qui indique ce dont il a besoin.

[project] : ce que reçoivent les consommateurs de métadonnées

Le tableau [project] décrit la distribution : son nom, sa version, sa compatibilité avec Python, ses dépendances en temps de exécution, ses points d’entrée, ainsi que d’autres métadonnées d’indexation.

[project]
name = "weather-client"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = ["httpx>=0.27"]

Les spécificateurs de dépendance constituent des contraintes destinées à un résolveur, et non une capture d’un environnement donné. Ils font partie des métadonnées générées par les fichiers wheel et sdist, permettant ainsi aux outils d’installation ultérieurs de les combiner avec les exigences provenant d’autres paquets.

Les extras représentent une interface d’installation publique

[project.optional-dependencies] définit les extras que les utilisateurs peuvent demander :

[project.optional-dependencies]
cli = ["rich>=13"]
postgres = ["psycopg[binary]>=3.2"]

Un utilisateur peut installer weather-client[cli]. Étant donné que les noms et les exigences associés aux extras sont publiés, il convient de les considérer comme des fonctionnalités du produit. Il ne faut pas utiliser un extra nommé dev uniquement pour héberger tous les outils utilisés par les contributeurs.

Les points d’entrée relient les commandes installées à Python

[project.scripts]
weather = "weather_client.cli:main"

Une fois la distribution installée, l’environnement expose weather, qui importe et exécute weather_client.cli:main. Il est nécessaire de tester la commande à partir d’un fichier wheel compilé, et non seulement depuis la racine du répertoire de dépôt ; c’est le fichier wheel que reçoivent les utilisateurs.

[dependency-groups] : environnements locaux non publiés

PEP 735 permet de décrire des groupes de dépendances correspondant à des environnements de développement ou non liés à des paquets, sans pour autant les publier en tant que métadonnées de paquet.

[dependency-groups]
test = ["pytest>=8", "pytest-cov>=5"]
lint = ["ruff>=0.12"]
dev = [
  { include-group = "test" },
  { include-group = "lint" },
]

Ce cadre constitue la limite appropriée pour les tests, les outils de vérification de syntaxe, les générateurs de documentation et autres outils similaires utilisés par les contributeurs. Il est également utile pour les applications ou les notebooks qui ne génèrent pas de distribution propre.

Les groupes de dépendances sont des données normalisées, mais les interfaces d’installation restent variables. Il convient de vérifier comment le gestionnaire d’environnement choisi les installe, les verrouille et les résout. PEP 735 ne définit pas d’interface en ligne de commande universelle.

[tool.*] : configuration gérée par un outil spécifique

Les tables relatives aux outils ne partagent pas le même schéma :

[tool.pytest.ini_options]
addopts = "-ra"
testpaths = ["tests"]

[tool.ruff]
line-length = 100

Il ne faut utiliser une table [tool.*] que si l’outil le prévoit explicitement. Certaines configurations doivent rester dans des fichiers distincts, soit parce qu’un autre écosystème les utilise, soit parce que le fichier nécessite un format différent, soit encore parce que la configuration y est plus clairement exprimée. pyproject.toml sert de point de coordination, et non d’obligation de centraliser tout le contenu.

Les déclarations, les fichiers de verrouillage et les fichiers de requisites résolvent des problèmes différents

La source la plus fréquente de confusion réside dans la tendance à considérer chaque artefact de dépendance comme une source de vérité concurrente.

ArtefactBut principalContenu typique
[project.dependencies]Contrat de runtime publiéExigences directes ainsi que plages de compatibilité
[project.optional-dependencies]Fonctionnalités optionnelles publiéesExtras destinés aux utilisateurs
[dependency-groups]Environnements locaux non publiésGroupes utilisés pour les tests, la vérification de syntaxe, la documentation ou les applications
Fichier de verrouillageReprésenter un environnement résoluVersions exactes, sources ainsi que métadonnées de résolution
requirements.txtDonnées d’installation compatibles avec pipExigences accompagnées d’options, de contraintes, d’URL ou d’hashes propres à pip

Une bibliothèque publie généralement des contraintes et des tests compatibles pour une plage donnée. Une application, quant à elle, enregistre habituellement le fichier de verrouillage généré par le gestionnaire d’environnement. Les valeurs de pin précises doivent figurer dans l’artefact de déploiement final, et non de manière arbitraire dans les métadonnées publiques de la bibliothèque.

Il convient de conserver un fichier de spécifications lorsque l’intégration exige le format ou certaines fonctionnalités propres à pip. Lorsqu’un projet géré par uv nécessite un tel fichier, il faut l’exporter à partir du fichier de verrouillage plutôt que de maintenir deux ensembles de dépendances indépendants :

uv export --format requirements.txt --output-file requirements.txt

Cet export représente une sortie de compatibilité dérivée. Le fichier de verrouillage reste la source fiable pour ce flux de travail.

Une migration conservant le comportement existant

Ne commencez pas par supprimer setup.py ou requirements.txt. Identifiez d’abord la fonction de chaque fichier existant.

  1. Faites l’inventaire de la logique de compilation, des métadonnées, des exigences en temps de exécution, des éléments supplémentaires, des environnements de développement, des paramètres d’outil, des données de paquet ainsi que des points d’entrée.
  2. Choisissez un backend capable de reproduire l’inclusion des fichiers actuelle, les artefacts compilés et les installations modifiables.
  3. Déplacez les métadonnées statiques publiées dans [project] ; conservez explicites uniquement les champs véritablement dynamiques.
  4. Transférez les exigences réservées aux contributeurs dans [dependency-groups], et non dans les éléments supplémentaires publics.
  5. Déplacez les paramètres d’outil uniquement là où l’outil prend en charge une sémantique équivalente.
  6. Compilez à la fois un sdist et un wheel, examinez leur contenu, puis installez le wheel dans un environnement propre.
  7. Exécutez les points d’entrée, les tests, les vérifications d’importation ainsi que le processus de déploiement réel.
  8. Ne supprimez les anciennes configurations qu’une fois que les artefacts et le comportement correspondent.

MANIFEST.in peut encore être nécessaire avec certaines structures de setuptools, et un petit setup.py peut rester valide pour un comportement de compilation programmatisé. La modernisation consiste en un changement de responsabilités, et non en une compétition de suppression de fichiers.

Un flux de travail actuel avec uv

uv distingue les applications des bibliothèques lors de la création d’un projet :

# Non-library application template
uv init weather-app

# Packaged library with a src layout and build system
uv init --lib weather-client

uv init crée les fichiers du projet. La première opération effectuée sur le projet, telle que uv run, uv sync ou uv lock, génère le fichier de verrouillage ainsi que le .venv persistant selon les besoins.

cd weather-client
uv add httpx
uv add --group test pytest pytest-cov
uv run pytest
uv build

Actuellement, uv place les exigences de développement local dans des groupes de dépendances normalisés. Son backend natif uv_build constitue une option pour les projets purement Python ; les extensions compilées nécessitent une alternative adaptée, comme maturin ou scikit-build-core.

Conclusion

pyproject.toml devient clair lorsque chaque tableau cible un public bien défini. L’isolement de la compilation relève de [build-system]. Le comportement publié appartient à [project]. Les environnements de contribution relèvent de [dependency-groups]. Les changements d’outil relèvent de l’outil lui-même qui les définit.

Une fois ces frontières stabilisées, il devient plus facile d’examiner les fichiers — et les migrations cessent de confondre les métadonnées des paquets avec l’environnement résolu d’une machine donnée.
