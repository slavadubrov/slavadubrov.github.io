Architecture de mémoire des AI Agents en 2026 : checkpoints, vector stores et mémoire basée sur des fichiers

Part 2 de la série Engineering the Agentic Stack

Une reasoning loop ne survit qu’à une seule requête si son état n’est pas stocké en dehors du worker. Sans agent memory, l’agent ne peut pas reprendre un plan en pause, récupérer après un crash, ou rappeler une préférence issue d’une session précédente. Part 1 couvrait le control flow. Ici, on identifie quel état chaque tour suivant doit charger et où cet état doit vivre.

Je vais parcourir l’architecture mémoire de l’Market Analyst Agent, en montrant comment des checkpoints “chauds”, des vector stores “froids” et une mémoire documentaire basée sur des fichiers collaborent pour des agents longue durée. Ensuite, je détaillerai quand PostgreSQL, Redis, Qdrant, des key-value stores, et de simples fichiers Markdown ont chacun du sens.

TL;DR : Séparez la mémoire selon les patterns d’accès. La hot memory correspond à l’état de checkpoint au niveau du thread pour pause/reprise. La cold memory conserve des faits trans-session via un key-value store ou un vector store. La document memory garde la connaissance du projet dans des fichiers lisibles. Commencez par l’échec à corriger, puis choisissez le store. Ne mettez pas des faits exacts dans un système de retrieval “flou”, et ne traitez pas un checkpoint comme un audit log.

Qu’est-ce que la mémoire d’un AI agent ?

AI agent memory est la couche d’état qui permet à un agent de préserver l’avancement d’une tâche, de retrouver une connaissance antérieure et de mettre à jour ce qu’il “sait” d’une exécution à l’autre. En production, ce n’est pas un seul vector database. C’est un mélange de checkpoints chauds, de stores sémantiques ou structurés “froids”, et d’une mémoire documentaire lisible par un humain.

Ne commencez pas par la mémoire parce que “ça sonne intelligent”. Commencez par l’échec observable côté utilisateur : perdre un progrès, oublier une préférence, répéter une recherche, ou ne pas réutiliser une convention de projet.

Les échecs qui nécessitent de la mémoire

Un agent stateless peut répondre à une question isolée, mais il oublie la requête dès que l’appel se termine. Ce design échoue lorsque le produit a besoin de l’un des comportements suivants :

  • Pause et reprise : un utilisateur démarre une tâche de recherche, ferme son laptop, puis revient demain. Sans état checkpointé, l’agent redémarre de zéro.
  • Cohérence multi-tours : sur une conversation longue, l’agent doit se souvenir des outils qu’il a appelés, des données qu’il a collectées, et des étapes du plan qu’il a terminées.
  • Personnalisation : un utilisateur de retour s’attend à ce que l’agent connaisse sa tolérance au risque, la profondeur d’analyse préférée, et l’historique des interactions passées.
  • Human-in-the-loop (HITL) : l’agent rédige un rapport et attend une approbation. L’état “en attente” doit survivre aux redémarrages de processus.

Dans l’Market Analyst Agent de Part 1, la requête “Analyze NVDA” produit un plan, cinq tool calls, des données collectées, puis un rapport draft. Quand l’utilisateur répond “looks good, but add competitor analysis”, un checkpoint store permet à l’agent de charger l’état depuis le dernier nœud et d’ajouter l’étape “competitor”. Sans checkpointed state, il ne peut pas déterminer à quoi renvoie “looks good” et doit repartir de zéro.

La mémoire long terme gère un autre cas. Si l’utilisateur revient une semaine plus tard et demande “Update my NVDA analysis”, l’agent devra peut-être rappeler une préférence pour des évaluations de risque prudentes et un intérêt pour les actions du secteur des semi-conducteurs. Un vector-backed memory store peut retrouver ces faits à travers les sessions sans reposer de questions.

LangGraph découpe cela par scope. Chaque exécution de graphe tourne dans un thread, c’est-à-dire une conversation ou une tâche. L’état persisté dans ce thread correspond à de la short-term memory. L’état partagé entre threads correspond à de la long-term memory. Le contexte courant du modèle et les variables en cours de traitement forment la couche de working memory au-dessus des deux stores.

Une taxonomie de la mémoire d’AI agent

Avant de rentrer dans l’implémentation, il est utile de classifier ce que les agents doivent mémoriser. Le CoALA framework (Sumers, Yao et al., 2023) est une taxonomie largement citée et s’appuie sur la science cognitive. J’ai introduit le memory scoping dans mon post de context engineering ; ici, je l’étends en six catégories :

Type de mémoireScopeDurée de vieExemplePattern de stockage
WorkingÉtape couranteMillisecondesArguments des tool calls, réponse LLM couranteIn-process (Python dict)
Short-termThread courantMinutes–heuresHistorique de conversation, progression de plan, données collectéesCheckpoint store
EpisodicCross-threadJours–mois“La semaine dernière, l’utilisateur a demandé à propos des earnings de NVDA”Vector store / KV store
SemanticCross-threadMois–permanent“L’utilisateur préfère des investissements prudents”Vector store / KV store

ProceduralSystème entierPermanent“Quand on analyse des actions, toujours vérifier les dépôts SEC”Config / system prompt

Working memory correspond à ce avec quoi le LLM raisonne activement maintenant : variables Python dans la fonction courante, contenu de la fenêtre de contexte, arguments des tool calls en plein exécution. C’est la couche la plus rapide et la plus éphémère. Rien ne persiste au-delà de l’étape courante. La working memory est bornée par la fenêtre de contexte du modèle, ce qui en fait le goulot d’étranglement. À l’instant où l’agent décide, tout ce qu’il “sait” doit pouvoir tenir ici, qu’il provienne du checkpoint store, d’une requête vectorielle, ou d’une lecture de fichier. Les autres niveaux existent pour injecter au bon moment la bonne information dans working memory.

Short-term memory est le checkpoint que LangGraph écrit après chaque nœud. Les mémoires episodic et semantic persistent à travers les threads. La document memory stocke les notes de projet, les résumés de recherche et les conventions apprises dans des fichiers que les humains (et les agents) peuvent inspecter. La procedural memory vit dans les instructions système et les définitions d’outils, plutôt que dans des éléments qui changent pour chaque utilisateur.

Pour l’implémentation, ces catégories se condensent en trois strates. La hot memory couvre la session courante. La cold memory permet le rappel entre sessions. La document memory conserve la connaissance accumulée du projet, lisible et directement éditable.

CoALA classe working, episodic, semantic et procedural memory. Le survey Memory in the Age of AI Agents met l’accent sur les vector stores et les knowledge graphs, tandis que LangGraph documente les checkpoints et son Store interface. La connaissance projet “backed by files” est en dehors de ces taxonomies, même si Claude Code, Cursor, Windsurf et Devin chargent tous des fichiers de projet persistants.

Le même pattern de stockage apparaît dans d’autres domaines. Voyager stocke des compétences réutilisables sous forme de bibliothèques de code, des équipes ERC3 ont itéré sur des documents de prompt procéduraux, et Agent Workflow Memory induit des workflows web réutilisables à partir d’épisodes réussis. Les fichiers rendent cette connaissance inspectable et versionnable sans service d’embeddings séparé.

La mémoire gérée par l’agent diffère aussi d’un pipeline RAG fixe sur le fait que c’est l’agent (ou son harness) qui effectue l’écriture. L’agent choisit quoi stocker, quoi mettre à jour et quoi supprimer, puis il choisit plus tard quand le relire.

Le Generative Agents paper (Park et al., 2023) a montré à quel point on peut aller loin : des agents simulés stockaient, réfléchissaient et retrouvaient leur propre mémoire. Son memory stream classe les candidats par récence, importance et pertinence ; une conception qui reste un point de référence utile pour le retrieval de memory d’agent.

Mémoire agent court terme : le checkpoint store

À chaque fois qu’un nœud LangGraph s’exécute, le framework sérialise l’état complet du graphe et l’écrit dans un checkpoint store. C’est la base pour pause/reprise, pour le debugging “time-travel”, et pour les workflows HITL.

Un checkpoint contient l’état du graphe nécessaire pour reprendre : le AgentState depuis Part 1 (messages, identity, user profile, plan steps, research data, execution mode), plus les métadonnées LangGraph comme le nœud qui l’a produit et son checkpoint ID. Après une interruption HITL ou un redémarrage de processus, le graphe charge la dernière frontière enregistrée et ré-entre dans le nœud suivant. Il ne continue pas à partir d’une ligne Python arbitraire. Un checkpoint est aussi différent d’un append-only event log ou d’une trace ; Part 5 sépare explicitement ces surfaces d’observabilité runtime.

Comment fonctionne le checkpointing dans LangGraph

L’BaseCheckpointSaver de LangGraph est une interface simple : put() écrit un checkpoint, get_tuple() lit le dernier pour un thread, list() renvoie l’historique. Chaque checkpoint est indexé par (thread_id, checkpoint_ns, checkpoint_id), où thread_id identifie la conversation, checkpoint_ns gère le namespacing du sous-graphe, et checkpoint_id est une version unique.

La décision importante est quel backend mettre derrière. PostgreSQL et Redis sont deux choix courants en production.

PostgreSQL vs Redis

Les benchmarks génériques de bases de données ne prédisent pas les performances de checkpoints. Mesurez la taille sérialisée de l’état, la fréquence d’écriture, les paramètres de persistance, et la concurrence de votre propre graphe.

PostgreSQL : le default durable

PostgreSQL est le choix le plus sûr pour la plupart des équipes. Les checkpoints survivent aux crashs, vous obtenez la sémantique complète des transactions, et l’historique rend le debugging time-travel trivial.

Depuis checkpointer_setup.py :

from langgraph.checkpoint.postgres.aio import AsyncPostgresSaver

async def create_postgres_checkpointer(connection_string: str) -> AsyncPostgresSaver:
    """Create a PostgreSQL-backed checkpoint store.

    PostgreSQL gives us ACID guarantees — if a checkpoint write succeeds,
    the state is durable even if the process crashes immediately after.
    """
    checkpointer = AsyncPostgresSaver.from_conn_string(connection_string)

    # Create the checkpoint tables if they don't exist.
    # This is idempotent — safe to call on every startup.
    await checkpointer.setup()

    return checkpointer

# Usage: wire into the graph compilation
checkpointer = await create_postgres_checkpointer(
    "postgresql://user:pass@localhost:5432/agent_memory"
)
graph = create_graph(checkpointer=checkpointer)

# Every invoke/stream call now persists state automatically
config = {"configurable": {"thread_id": "user-123-session-1"}}
result = await graph.ainvoke({"messages": [HumanMessage(content="Analyze NVDA")]}, config)

# Resume later — loads the latest checkpoint for this thread
result = await graph.ainvoke({"messages": [HumanMessage(content="approved")]}, config)

Le AsyncPostgresSaver utilise le package langgraph-checkpoint-postgres, qui crée trois tables : checkpoints (l’état sérialisé), checkpoint_blobs (de grosses données binaires), et checkpoint_writes (écritures en attente pour recovery après crash). Le schéma supporte l’accès concurrent et utilise des advisory locks pour prévenir les conflits d’écriture.

Redis : quand la latence est le goulot d’étranglement

Quand la latence de checkpoint en dessous de la microseconde (sub-millisecond) est critique (agents conversationnels temps réel, tool loops à haute fréquence), Redis est le meilleur choix.

Depuis checkpointer_setup.py :

from langgraph.checkpoint.redis.aio import AsyncRedisSaver

async def create_redis_checkpointer(redis_url: str) -> AsyncRedisSaver:
    """Create a Redis-backed checkpoint store.

    Redis stores checkpoints in memory for sub-millisecond access.
    Trade-off: less durable than PostgreSQL unless AOF is enabled.
    """
    checkpointer = AsyncRedisSaver.from_conn_string(redis_url)

    # Initialize Redis data structures
    await checkpointer.setup()

    return checkpointer

# Usage: same graph API, different backend
checkpointer = await create_redis_checkpointer("redis://localhost:6379")
graph = create_graph(checkpointer=checkpointer)

Le AsyncRedisSaver de langgraph-checkpoint-redis stocke les checkpoints comme des documents JSON indexés par thread ID. La v0.1.0 redesign a remplacé plusieurs opérations de recherche par un seul JSON.GET call, réduisant significativement la latence. Redis 8.0+ inclut RedisJSON et RediSearch par défaut — pas besoin d’installer de modules supplémentaires.

Pour des déploiements contraints en mémoire, ShallowRedisSaver stocke uniquement le dernier checkpoint par thread — pas d’historique, mais usage RAM minimal. À utiliser quand vous avez besoin de pause/reprise, sans besoin de debugging time-travel.

Quand utiliser quoi

Utilisez PostgreSQL quand :

  • Vous avez besoin de l’historique complet des checkpoints pour du time-travel debugging ou une reprise reproductible
  • La durabilité est non négociable (services financiers, santé)
  • Vous exécutez déjà PostgreSQL dans votre stack
  • Votre agent effectue des tâches longues où perdre un état signifie des heures de recomputation
  • Vous voulez un unified data store — PostgreSQL avec pgvector peut devenir un backend unique pour checkpoints, long-term memory, et vector search

Utilisez Redis quand :

  • La latence de checkpoint est votre goulot d’étranglement (chat temps réel, UX streaming)
  • Vous construisez des voice bots — STT-to-LLM-to-TTS pipelines ont besoin d’un sub-millisecond state access
  • Vous avez besoin d’un scaling horizontal sur beaucoup de threads concurrents
  • Des patterns de fan-out à forte concurrence où plusieurs agents partagent l’état
  • Des sessions de courte durée où perdre un checkpoint reste récupérable
  • Vous voulez un semantic caching pour réduire les appels LLM redondants (Redis LangCache met en cache des requêtes sémantiquement proches pour éviter des appels LLM répétitifs)

Autres options : langgraph-checkpoint-sqlite marche pour le développement local et les déploiements mono-process. Pour des stacks AWS-native, langgraph-checkpoint-aws fournit un DynamoDBSaver avec traitement intelligent des payloads — les petits checkpoints (<350 KB) restent dans DynamoDB, les gros sont offloadés automatiquement vers S3. La tarification serverless et l’absence d’infrastructure à gérer le rendent attractif pour des déploiements à charge variable.

Mémoire long terme : se souvenir au-delà des sessions

La hot memory gère la conversation en cours. La long-term memory couvre l’utilisateur qui revient la semaine suivante : elle stocke des faits, des préférences et l’historique d’interactions, qui persistent d’un thread à l’autre.

LangGraph fournit une interface Store pour la mémoire cross-thread via sa classe BaseStore. Chaque élément de mémoire est un (namespace, key) couplé à une valeur JSON et à un embedding vectoriel optionnel. Le namespace encode typiquement l’utilisateur ou l’organisation : ("user", "user-123", "preferences").

Stockage vectoriel : rappel sémantique avec Qdrant

Quand l’agent doit rappeler des faits non structurés (“Que l’utilisateur a-t-il dit à propos de son horizon d’investissement ?”), la recherche vectorielle permet un rappel sémantique. Au lieu de lookup par clé exacte, l’agent interroge par “signification”.

Qdrant est une base de données vectorielles conçue pour cet usage, écrite en Rust, qui gère le stockage d’embeddings, l’indexing (HNSW) et la recherche filtrée. J’ai couvert HNSW et ses compromis en détail dans mon post sur le search ranking. Qdrant propose aussi un MCP server qui agit comme une couche de semantic memory — utile si votre framework d’agent supporte le Model Context Protocol.

Depuis memory_store.py :

from qdrant_client import QdrantClient
from qdrant_client.models import PointStruct, Distance, VectorParams
from langchain_anthropic import ChatAnthropic
import hashlib
import json

class UserMemoryStore:
    """Long-term memory backed by Qdrant vector search.

    Stores user facts as embedded vectors for semantic retrieval.
    Each fact is a short natural-language statement about the user.
    """

    def __init__(self, qdrant_url: str, collection_name: str = "user_memory"):
        self.client = QdrantClient(url=qdrant_url)
        self.collection_name = collection_name
        self._ensure_collection()

    def _ensure_collection(self):
        """Create the collection if it doesn't exist."""
        collections = [c.name for c in self.client.get_collections().collections]
        if self.collection_name not in collections:
            self.client.create_collection(
                collection_name=self.collection_name,
                vectors_config=VectorParams(
                    size=1536,  # text-embedding-3-small dimensions
                    distance=Distance.COSINE,
                ),
            )

    def store_fact(self, user_id: str, fact: str, embedding: list[float]):
        """Store a user fact with its embedding."""
        point_id = hashlib.md5(f"{user_id}:{fact}".encode()).hexdigest()
        self.client.upsert(
            collection_name=self.collection_name,
            points=[PointStruct(
                id=point_id,
                vector=embedding,
                payload={"user_id": user_id, "fact": fact},
            )],
        )

    def recall(self, user_id: str, query_embedding: list[float], top_k: int = 5):
        """Retrieve the most relevant facts for a user given a query."""
        results = self.client.query_points(
            collection_name=self.collection_name,
            query=query_embedding,
            query_filter={"must": [{"key": "user_id", "match": {"value": user_id}}]},
            limit=top_k,
        )
        return [hit.payload["fact"] for hit in results.points]

Le flux comporte trois étapes. Après chaque conversation, un LLM extrait des faits clés de l’interaction (“l’utilisateur a une tolérance au risque élevée”, “l’utilisateur s’intéresse aux actions de semi-conducteurs”). Ces faits sont embarqués (embedded) et stockés dans Qdrant. Au début de la conversation suivante, l’agent interroge Qdrant avec le nouveau message de l’utilisateur pour rappeler le contexte pertinent.

Scoring de retrieval : au-delà de la similarité cosinus

La similarité cosinus brute est un point de départ, mais les systèmes de mémoire en production ont besoin d’un retrieval plus riche. Le Generative Agents paper (Park et al., 2023) introduit une fonction de scoring qui combine trois signaux :

  • Recency : décroissance (decay) basée sur des règles pour que les souvenirs récents aient un score plus élevé. Une fonction de décroissance exponentielle fait qu’un fait d’hier surclasse un fait équivalent vieux de six mois.
  • Importance : la significativité est évaluée par un LLM sur une échelle de 1 à 10. “Le portefeuille de l’utilisateur est en baisse de 40%” obtient un score plus élevé que “l’utilisateur a dit bonjour”.
  • Relevance : similarité cosinus entre l’embedding de la requête et l’embedding du fait stocké.

Le score final de retrieval est une somme pondérée : score = alpha * recency + beta * importance + gamma * relevance. Cela évite que des faits importants et récents soient enterrés sous des faits plus vieux mais sémantiquement proches. Pour l’Market Analyst Agent, je pèse la pertinence en premier (0.5), puis la récence (0.3) et l’importance (0.2), car l’intention de la requête courante de l’utilisateur est ce qui compte le plus. Ce sont des poids de départ adaptés depuis le Generative Agents paper (qui utilisait une pondération égale) ; j’ai constaté qu’insister sur la relevance marche mieux pour les requêtes d’analyse financière, mais ces valeurs sont basées sur l’intuition, pas optimisées empiriquement.

Alternatives au vector search

La recherche vectorielle est puissante, mais pas toujours le bon outil. Voici quand utiliser d’autres approches :

Les key-value stores conviennent bien aux données structurées. Si votre long-term memory est un profil utilisateur — tolérance au risque, horizon d’investissement, secteurs préférés — un Redis hash ou une colonne PostgreSQL JSONB est plus simple et plus rapide que d’embarquer et de requêter des vecteurs. Utilisez la vector search quand la mémoire est non structurée et que la forme de la requête varie en formulation.

Le LangGraph built-in Store fournit une interface key-value basée sur un namespace, avec une vector search optionnelle. L’BaseStore API est simple : put(), get(), search() et delete() avec scoping hiérarchique des namespaces. Trois implémentations sont disponibles :

  • InMemoryStore — pour le développement et les tests (perte des données à la sortie du process)
  • PostgresStore — store persistant production avec requêtes SQL complètes
  • AsyncRedisStore — mémoire cross-thread avec vector search, support TTL, et filtrage de métadonnées

La config index permet d’activer une vector search sur les items stockés avec un modèle d’embedding configurable. Pour beaucoup de cas d’usage, ce store intégré suffit sans aller chercher un vector database dédié.

from langgraph.store.memory import InMemoryStore

# Create a store with vector search enabled
store = InMemoryStore(
    index={
        "dims": 1536,
        "embed": my_embedding_function,  # e.g., OpenAI text-embedding-3-small
    }
)

# Store a user preference (namespace scopes to user)
await store.aput(
    namespace=("user", "user-123", "preferences"),
    key="risk-profile",
    value={"risk_tolerance": "high", "horizon": "long-term"},
)

# Semantic search across user's memories
results = await store.asearch(
    namespace=("user", "user-123"),
    query="What is their investment style?",
    limit=5,
)

Choisir une stratégie de long-term memory

Commencez par key-value si votre mémoire est structurée et bien définie (profils utilisateurs, settings, named entities). Ajoutez la vector search quand vous avez besoin d’un retrieval sémantique sur des faits non structurés, ou quand la formulation de la requête varie de façon imprévisible.

Les knowledge graphs valent le coût quand les relations entre entités comptent, par exemple “Quelles entreprises l’utilisateur a-t-il demandées qui sont des concurrentes de NVDA ?”. Le projet récent le plus intéressant ici est Graphiti (par Zep), qui construit un temporally-aware knowledge graph qui suit quand un fait est vrai, pas seulement ce qui est vrai. Chaque arête porte des intervalles de validité : si la tolérance au risque de l’utilisateur change, l’ancienne valeur devient invalide au lieu d’être écrasée silencieusement. Graphiti rapporte 94.8% accuracy sur le DMR benchmark, et son modèle bi-temporel gère le problème de mémoire périmée au niveau des données.

Le piège, c’est l’exploitation : exécuter une base de données graphe n’est pas trivial, et pour la majorité des applications d’agents, une vector search avec filtrage de métadonnées couvre le même besoin avec moins d’infrastructure.

Managed memory frameworks comme Mem0 et Letta (anciennement MemGPT) gèrent pour vous le pipeline extraction-consolidation-retrieval. La démarche de Mem0 est notable : un LLM extrait des mémoires candidates, un moteur de décision compare chaque nouveau fait aux entrées existantes dans le vector store, puis un resolver décide d’ajouter, mettre à jour ou supprimer. Cela garde le store cohérent et non redondant. Letta adopte un angle “gestion de système d’exploitation” : les agents gèrent leur propre context window via des outils de mémoire, en déplaçant de manière autonome les données entre “core memory” (in-context) et “archival memory” (out-of-context). Les deux méritent d’être évalués si vous voulez un time-to-production plus rapide et que vous n’avez pas besoin d’un contrôle complet sur le pipeline mémoire.

Document memory : le filing cabinet de l’agent

La mémoire basée sur des fichiers a plus d’adoption produit que ce que montrent les taxonomies ci-dessus. Dans une évaluation LoCoMo menée par un éditeur, Letta a rapporté 74.0% pour son approche filesystem. Conservez ce résultat dans son cadre : modèle, benchmark et conditions de harness. L’avantage opérationnel ne dépend pas du benchmark : les développeurs peuvent lire, éditer et diff l’information stockée directement.

Des context windows plus longs rendent aussi les lectures de fichiers entiers pratiques pour certains documents projet. Le retrieval par chunking convient encore aux corpus volumineux, mais pour une courte conventions ou un fichier handoff, on peut souvent le charger en entier. Le choix dépend de la taille du document, de la précision du retrieval, du budget de contexte, et de la fréquence à laquelle les gens doivent relire ou éditer la mémoire.

Les vector stores et les key-value backends gèrent bien le rappel sémantique et les lookups structurés. Mais il existe une troisième catégorie de connaissance d’agent qui ne se mappe ni proprement dans ces solutions : le contexte projet accumulé, les conventions, notes de recherche et décisions dont l’agent a besoin au fil des sessions. Cette connaissance profite d’être lisible par un humain et versionnée.

C’est la document memory : l’agent lit et écrit des fichiers structurés (Markdown, JSON, YAML) dans un répertoire connu. Pas d’embeddings, pas de base de données, pas d’infrastructure. Juste des fichiers sur disque que l’agent et le développeur peuvent cat, grep, git diff et éditer à la main.

Pourquoi les fichiers ?

Pour des workflows d’agents longue durée, le pattern le plus efficace que j’ai vu n’est pas une vector database. C’est un répertoire de notes bien organisées. Voyez ce qui se passe quand un agent de coding travaille sur un projet pendant des semaines :

  • Il apprend que le projet utilise Pydantic v2, pas v1
  • Il découvre que les tests doivent tourner avec pytest -x --tb=short
  • Il accumule de la connaissance sur l’architecture du codebase
  • Il apprend les préférences du développeur (“toujours utiliser pathlib, jamais os.path”)

Ces faits sont trop structurés pour la vector search (vous avez besoin d’un rappel exact, pas d’une similarité floue) et trop nombreux pour un key-value store (ce sont des documents interconnectés, pas des faits isolés). Ce sont aussi des faits que le développeur veut voir et éditer directement. Si l’agent apprend quelque chose de faux, vous ouvrez le fichier et vous le corrigez.

C’est exactement ce que permettent Claude Code’s CLAUDE.md et le répertoire .claude/. L’agent lit des fichiers CLAUDE.md au niveau du projet pour les conventions et instructions, et écrit dans ~/.claude/MEMORY.md pour les apprentissages cross-session. Les fichiers sont du Markdown : vous les lisez, les éditez, vous les comitiez dans git, vous les partagez avec votre équipe. Cursor’s .cursorrules et Windsurf’s .windsurfrules suivent le même pattern : des fichiers texte que l’agent charge au démarrage pour récupérer le contexte projet.

Implémenter un file memory store

L’implémentation est volontairement simple. L’agent reçoit quatre opérations : écrire un document, lire un document, lister les documents disponibles, et chercher à travers les documents par mot-clé.

Depuis file_memory.py :

from pathlib import Path
import json
import fnmatch

class FileMemory:
    """Document memory backed by the local filesystem.

    Stores agent knowledge as human-readable files organized by topic.
    No embeddings, no database — just files that both the agent and
    the developer can read, edit, and version-control.
    """

    def __init__(self, base_dir: str | Path):
        self.base_dir = Path(base_dir)
        self.base_dir.mkdir(parents=True, exist_ok=True)

    def write_doc(self, path: str, content: str, metadata: dict | None = None):
        """Write or overwrite a document at the given path.

        Paths are relative to base_dir. Directories are created automatically.
        Metadata (if provided) is stored as a JSON sidecar file.
        """
        full_path = self.base_dir / path
        full_path.parent.mkdir(parents=True, exist_ok=True)
        full_path.write_text(content, encoding="utf-8")

        if metadata:
            meta_path = full_path.with_suffix(full_path.suffix + ".meta")
            meta_path.write_text(json.dumps(metadata, indent=2), encoding="utf-8")

    def read_doc(self, path: str) -> str | None:
        """Read a document by path. Returns None if not found."""
        full_path = self.base_dir / path
        if full_path.exists():
            return full_path.read_text(encoding="utf-8")
        return None

    def list_docs(self, pattern: str = "**/*") -> list[str]:
        """List documents matching a glob pattern."""
        return [
            str(p.relative_to(self.base_dir))
            for p in self.base_dir.glob(pattern)
            if p.is_file() and not p.name.endswith(".meta")
        ]

    def search_docs(self, query: str, pattern: str = "**/*.md") -> list[dict]:
        """Search documents by keyword. Returns matching files with context.

        This is intentionally simple — grep-style keyword search.
        For semantic search, use a vector store instead.

        NOTE: This is a sketch for demonstration. A simple substring check
        won't scale beyond a few hundred documents. For production with 500+
        documents, use TF-IDF/BM25 scoring (e.g., rank_bm25) or a full-text
        search backend (PostgreSQL GIN index, Elasticsearch).
        """
        results = []
        for path in self.base_dir.glob(pattern):
            if not path.is_file() or path.name.endswith(".meta"):
                continue
            content = path.read_text(encoding="utf-8")
            if query.lower() in content.lower():
                # Return the paragraph containing the match for context
                for paragraph in content.split("\n\n"):
                    if query.lower() in paragraph.lower():
                        results.append({
                            "path": str(path.relative_to(self.base_dir)),
                            "match": paragraph.strip()[:500],
                        })
        return results

Structure de dossier

La majeure partie de la valeur de la document memory vient de la façon dont le répertoire est structuré. Voici la structure que j’utilise pour l’Market Analyst Agent :

.agent-memory/

    user-profiles/
        user-123.md            # Preferences, history, risk profile
        user-456.md
    research/

        TSLA-2026-01.md

Chaque fichier est du Markdown. Chaque fichier a un rôle évident à partir de son chemin. Vous pouvez git diff tout le répertoire de mémoire pour voir ce que l’agent a appris pendant une session, git revert une mauvaise leçon, ou copier le répertoire vers un autre projet. Essayez de faire ça avec une collection Qdrant.

Quand utiliser document memory vs vector vs key-value

Les trois backends de mémoire répondent à différents patterns d’accès :

Utilisez document memory quand :

  • L’agent accumule de la connaissance projet sur plusieurs sessions
  • Les développeurs doivent inspecter, éditer, ou surcharger ce que l’agent “sait”
  • La connaissance est structurée en documents (notes, résumés, conventions) plutôt qu’en faits isolés
  • Vous voulez versionner la mémoire d’agent via git
  • Zéro infrastructure est une contrainte forte

Utilisez vector stores quand :

  • Vous avez besoin d’un retrieval sémantique flou (“trouver des souvenirs liés à X”)
  • La formulation de la requête varie de façon imprévisible
  • Vous avez des milliers à des millions de faits individuels

Utilisez key-value stores quand :

  • Vous avez besoin de lookups exacts et rapides pour des données structurées (profils utilisateurs, settings)
  • Le schéma de données est bien défini

En pratique, les agents en production combinent souvent les trois. L’Market Analyst Agent utilise des checkpoints PostgreSQL pour la hot memory, Qdrant pour le rappel sémantique de faits utilisateur, et un document store basé sur des fichiers pour les conventions de projet et les notes de recherche.

Exemples concrets

Le pattern est déjà répandu dans les assistants de coding AI :

  • Claude Code lit CLAUDE.md depuis le répertoire racine du projet et les répertoires parents, et écrit dans ~/.claude/MEMORY.md pour les apprentissages cross-session. Le système de mémoire entier est constitué de fichiers Markdown simples, que vous comitiez avec votre code.
  • Cursor charge .cursorrules pour les instructions d’agent spécifiques au projet : conventions de code, préférences de frameworks, décisions d’architecture.
  • Windsurf utilise .windsurfrules avec un répertoire memories/ où l’agent stocke les patterns appris depuis votre codebase.
  • Anthropic’s memory tool pour Claude API fournit create_memory, read_memory, update_memory et delete_memory opérations implémentées côté client. Votre application décide où vivent les fichiers (disque local, S3, base de données).

Tous stockent la connaissance d’agent sous forme de fichiers texte lisibles par un humain avec des opérations de lecture/écriture explicites, et aucun ne nécessite un pipeline d’embeddings. L’agent décide quoi écrire, le développeur peut tout voir et éditer, et tout le système tient dans un git diff.

Au-delà des assistants de coding

La document memory ne se limite pas aux agents de coding. Le pattern apparaît aussi dans d’autres domaines :

  • Open-world game agents : Voyager (Wang et al., 2023) construit une bibliothèque persistante de compétences sous forme de programmes JavaScript vérifiés, accumulés au fil du temps par un agent Minecraft, collectant 3.3x plus d’items uniques et atteignant des milestones 15.3x plus vite que les baselines. Les compétences se transfèrent vers de nouveaux mondes sans retraining. JARVIS-1 étend cela avec une mémoire multimodale combinant plans textuels et observations visuelles, avec un taux de succès 5x sur les tâches les plus difficiles.

    Une distinction utile : les skill libraries sont une mémoire exécutable (des fichiers de code importés et exécutés), tandis que la document memory des assistants de coding est déclarative (Markdown injecté dans les prompts). Les modes d’échec diffèrent : un mauvais code exécutable fait crash l’agent ; un mauvais texte déclaratif mène à des erreurs de raisonnement. Mais le pattern de stockage et les bénéfices opérationnels (debuggability, version control) sont les mêmes.

  • Automatisation de workflow en entreprise : Les gagnants de la ERC3 competition ont utilisé une document memory pour l’affinage itératif de prompts. Les agents Analyzer et Versioner d’une équipe gagnante ont itéré à travers 80 versions de prompts stockées comme documents procéduraux. Une autre équipe a construit 20+ modules enricher comme connaissances procédurales document-style. LEGOMem (2025) formalise cela comme un framework modulaire de mémoire pour systèmes multi-agent, avec des types de mémoire spécialisés (sensory, short-term, long-term) que les agents composent comme des briques.

  • Web automation : Agent Workflow Memory (Wang et al., 2024) permet à des web agents d’induire des workflows réutilisables à partir d’épisodes réussis, avec une amélioration de 51% du taux de succès sur WebArena. SkillWeaver (2025) va plus loin : les agents synthétisent des API tools réutilisables à partir de l’exploration, avec un gain de 31.8% de taux de succès. Les compétences apprises se transfèrent aussi à des modèles plus faibles (54.3% d’amélioration), donc la mémoire accumulée d’un agent plus fort peut élever le niveau d’un plus petit.

  • Support client : Gartner prédit que des AI agents résoudront de manière autonome 80% des problèmes courants de service client d’ici 2029. Ces agents s’appuient sur des SOPs, playbooks et historiques clients, qui sont tous des formes de document memory.

Le MemAgents workshop at ICLR 2026 est un signe que la communauté de recherche rattrape ce que les praticiens ont déjà construit.

Les skills utilisent des documents pour emballer des instructions procédurales. La Agent Skills standard stocke ces instructions dans SKILL.md fichiers avec YAML frontmatter et un corps Markdown. Cela ressemble à de la document memory au niveau stockage, mais le rôle est différent : une skill explique à l’agent comment exécuter une classe de travail, tandis que la mémoire enregistre des faits appris depuis un projet ou une exécution précédente. Part 3 couvre cette distinction côté tool.

MCP (Model Context Protocol) va dans le même sens : les définitions d’outils sont des fichiers JSON Schema que n’importe quel agent peut découvrir et appeler. Le protocole a 97 million monthly SDK downloads et est supporté par OpenAI, Google, Microsoft et AWS. MCP n’est pas spécifique au coding. Les mêmes serveurs connectent des agents à des bases de données, des internal APIs et des systèmes enterprise.

Tout converge vers le même pattern : connaissance procédurale stockée sous forme de documents contraints par un schéma, avec des opérations de lecture/écriture explicites. MCP, maintenant gouverné par le Agentic AI Foundation, est la chose la plus proche d’un standard d’interop que l’écosystème agent possède.

Mettre à l’échelle document memory en production

L’implémentation ci-dessus basée sur des fichiers marche bien pour les laptops solo et des déploiements de petite taille. En production multi-tenant, avec des centaines d’utilisateurs et des milliers de documents, il faut une autre architecture.

La limite “single-node” des fichiers devient vite évidente : vous ne pouvez pas scaler l’I/O de fichiers horizontalement, les écritures concurrentes nécessitent des verrous, et gérer des permissions entre tenants est douloureux. En production, il faut un backing store qui gère correctement la concurrence, la recherche et le multi-tenancy.

Trois approches courantes :

Approche A : hybride avec une couche database fine

Conservez les fichiers pour l’édition (les développeurs éditent localement du Markdown), mais servez-les depuis une base de données au runtime. Au déploiement, synchronisez les fichiers vers des lignes PostgreSQL. L’agent lit depuis la base et pas depuis le disque. Vous obtenez :

  • Ergonomie développeur (éditer Markdown, commiter dans git)
  • Performance requête en production (lectures indexées en base)
  • Séparation propre entre authoring et serving

Approche B : object storage + vector index sidecar

Stockez les documents dans S3/GCS comme des objets, avec une collection Qdrant qui indexe leurs embeddings. L’agent interroge Qdrant pour obtenir les IDs de documents pertinents, puis récupère le contenu depuis l’object storage. Cela scale horizontalement et supporte la recherche sémantique, mais ajoute de la complexité : deux systèmes à gérer, un pipeline d’embeddings à maintenir, et une cohérence éventuelle entre le store et l’index.

Approche C : document store structuré avec PostgreSQL (recommandé)

Stockez les documents comme des lignes PostgreSQL JSONB avec full-text search (GIN index) et des embeddings vectoriels optionnels (pgvector). Vous obtenez une recherche hybride (keyword + sémantique), des transactions ACID, et un système opérationnel unique.

Un aperçu de l’Approche C :

from typing import Optional
import asyncpg

class ProductionDocumentMemory:
    """PostgreSQL-backed document memory with hybrid search.

    Schema:
        CREATE TABLE documents (
            id SERIAL PRIMARY KEY,
            tenant_id TEXT NOT NULL,
            path TEXT NOT NULL,
            content TEXT NOT NULL,
            metadata JSONB,
            embedding vector(1536),  -- pgvector extension
            ts_vector tsvector GENERATED ALWAYS AS (to_tsvector('english', content)) STORED,
            created_at TIMESTAMPTZ DEFAULT NOW(),
            UNIQUE(tenant_id, path)
        );
        CREATE INDEX ON documents USING GIN(ts_vector);
        CREATE INDEX ON documents USING ivfflat(embedding vector_cosine_ops);
    """

    def __init__(self, pool: asyncpg.Pool):
        self.pool = pool

    async def write(
        self,
        tenant_id: str,
        path: str,
        content: str,
        metadata: Optional[dict] = None,
        embedding: Optional[list[float]] = None,
    ):
        """Write or update a document."""
        async with self.pool.acquire() as conn:
            await conn.execute(
                """
                INSERT INTO documents (tenant_id, path, content, metadata, embedding)
                VALUES ($1, $2, $3, $4, $5)
                ON CONFLICT (tenant_id, path) DO UPDATE
                SET content = EXCLUDED.content,
                    metadata = EXCLUDED.metadata,
                    embedding = EXCLUDED.embedding
                """,
                tenant_id, path, content, metadata, embedding,
            )

    async def search(
        self,
        tenant_id: str,
        query: str,
        embedding: Optional[list[float]] = None,
        limit: int = 5,
    ) -> list[dict]:
        """Hybrid search: full-text + optional vector similarity."""
        async with self.pool.acquire() as conn:
            if embedding:
                # Hybrid scoring: 0.6 * text relevance + 0.4 * vector similarity
                rows = await conn.fetch(
                    """
                    SELECT path, content, metadata,
                           (0.6 * ts_rank(ts_vector, plainto_tsquery('english', $2)) +
                            0.4 * (1 - (embedding <=> $3))) AS score
                    FROM documents
                    WHERE tenant_id = $1
                      AND ts_vector @@ plainto_tsquery('english', $2)
                    ORDER BY score DESC
                    LIMIT $4
                    """,
                    tenant_id, query, embedding, limit,
                )
            else:
                # Full-text search only
                rows = await conn.fetch(
                    """
                    SELECT path, content, metadata,
                           ts_rank(ts_vector, plainto_tsquery('english', $2)) AS score
                    FROM documents
                    WHERE tenant_id = $1
                      AND ts_vector @@ plainto_tsquery('english', $2)
                    ORDER BY score DESC
                    LIMIT $3
                    """,
                    tenant_id, query, limit,
                )
            return [dict(row) for row in rows]

Ce que vous obtenez :

  • Hybrid search : matching keyword (GIN index) + similarité sémantique (pgvector) scorés ensemble
  • Multi-tenancy : tenant_id scoping via row-level security
  • Garanties ACID : pas de soucis de cohérence éventuelle
  • Système opérationnel unique : pas de vector database séparée à gérer
  • Scaling horizontal : read replicas pour la charge requêtes, partitionnement par tenant pour le write scale

Les fichiers sont très bien pour les workflows de dev solo. En multi-tenant production, un document store structuré sur PostgreSQL est généralement le bon compromis entre simplicité, performance et maturité opérationnelle.

Tout assembler : l’architecture complète

Voici comment les trois strates de mémoire fonctionnent ensemble dans l’Market Analyst Agent. Le schéma illustre le flux complet de la requête utilisateur à la réponse, avec toutes les couches mémoire actives.

L’architecture comporte trois chemins mémoire :

  1. Hot path (checkpoint store) : chaque nœud dans LangGraph écrit son état de graphe “rejouable” dans le checkpoint store. Quand le graphe atteint un nœud interrupt_before (comme le reporter dans Part 1), l’exécution se met en pause. L’utilisateur peut fermer l’app, et en revenant, le graphe reprend depuis le checkpoint. Les logs d’événements runtime et les traces sont des préoccupations de production séparées.

  2. Cold path (long-term store) : au début de chaque conversation, l’agent interroge le long-term store pour du contexte utilisateur pertinent. À la fin, il extrait et stocke de nouveaux faits. Cet aspect s’exécute de façon asynchrone — il ne doit jamais bloquer la reasoning loop principale.

  3. Document path (file store) : au démarrage, l’agent charge des conventions projet et des notes de recherche pertinentes depuis le document store. Pendant l’exécution, il écrit de nouveaux résumés de recherche et patterns appris sur disque. Contrairement au cold path, les lectures document sont synchrones (elles informent la tâche courante), tandis que les écritures peuvent être différées.

Le “wiring” dans LangGraph est direct : le checkpoint store et le long-term store sont passés à la compilation du graphe, tandis que le document store est injecté comme dépendance. Le schéma local ci-dessous utilise InMemoryStore pour garder l’extrait petit ; le topology Docker de référence utilise Qdrant pour la même fonction de semantic recall.

from langgraph.checkpoint.postgres.aio import AsyncPostgresSaver

Le flux complet

Que se passe-t-il quand un utilisateur revient et envoie “Analyze TSLA” à l’Market Analyst Agent :

  1. Chargement de document memory : au démarrage, l’agent lit les conventions du projet depuis le document store : préférences de format d’analyse, sources de données préférées, patterns d’usage des outils. Cela fixe le comportement de base.

  2. Rappel cold memory : avant l’exécution du nœud router, le graphe interroge le long-term store avec le message de l’utilisateur. Il récupère : “User has high risk tolerance”, “User prefers detailed competitor analysis”, “User previously researched NVDA and AMD”.

  3. Router + Planner : le router classe cela comme DEEP_RESEARCH. Le planner construit un plan de recherche en 5 étapes, personnalisé aux préférences rappelées. Il inclut une étape d’analyse des concurrents car l’historique montre que l’utilisateur en veut une. Le plan suit le format du document de conventions.

  4. Executor loop (hot memory) : chaque étape s’exécute via le pattern ReAct de Part 1. Après chaque nœud (router, planner, puis chaque étape executor), LangGraph écrit un checkpoint dans PostgreSQL. Si le processus crash après l’étape 3 de 5, vous redémarrez et continuez depuis l’étape 4.

  5. Interrupt HITL : le graphe atteint le nœud reporter avec interrupt_before. Le rapport draft se trouve dans le checkpoint. L’utilisateur le relit quelques heures plus tard, puis le graphe charge le checkpoint et continue.

  6. Mises à jour mémoire : à la fin de la conversation, un processus asynchrone extrait de nouveaux faits (“user is now tracking TSLA”, “user approved the report format”) et les stocke dans le long-term vector store. L’agent écrit aussi un résumé de recherche dans le document store (research/TSLA-2026-02.md) pour référence future.

Le pattern à trois niveaux sépare proprement les responsabilités. Le checkpoint store gère durabilité et reprise ; c’est de l’infrastructure. Le long-term store gère la personnalisation ; c’est la logique produit. La document store contient la connaissance projet accumulée ; c’est le “carnet” de l’agent.

Compromis et considérations

La mémoire ajoute de la valeur, mais aussi un coût et de la complexité :

  • Coût des embeddings : chaque fait stocké dans un vector database requiert un appel API d’embedding. À $0.02 par million de tokens (OpenAI text-embedding-3-small), le coût par fait est négligeable, mais ça s’accumule sur des milliers d’utilisateurs et sessions. Faites du batch embedding et mettez en cache les résultats. Le coût le plus important est la latence : 100-300ms de latence d’embedding au moment de la requête pour le cold memory recall, qui compte souvent plus que les dollars pour les agents conversationnels temps réel. Cachez les embeddings pour les requêtes fréquentes, ou utilisez un modèle d’embedding local pour des workloads sensibles à la latence.

  • Mémoire périmée (stale memory) : les préférences utilisateur changent. Un fait stocké il y a six mois (“user prefers conservative investments”) peut ne plus être exact. Fixez des politiques d’expiration. J’utilise 365 jours pour les préférences et 90 jours pour les événements episodic, comme décrit dans mon post de context engineering.

  • Surcharge mémoire dans le contexte : chaque fait rappelé consomme des tokens dans la context window du LLM. Si vous rappelez 20 faits par requête, vous consommez plusieurs centaines de tokens de mémoire de contexte, en concurrence avec la tâche actuelle. Limitez le nombre de faits rappelés et priorisez par score de pertinence.

  • Confidentialité et conformité : la long-term memory stocke des données utilisateur. Il faut faire de la redaction de PII avant stockage, définir des politiques de rétention claires, et fournir des contrôles côté utilisateur pour la suppression des données. Rien de tout cela n’est optionnel dans les secteurs régulés.

  • Croissance du checkpoint storage : les tables de checkpoint PostgreSQL grossissent à chaque exécution de nœud. Pour les agents longue durée, fixez une politique de rétention : gardez les N derniers checkpoints par thread et archivez ou supprimez les anciens. Exemple de requête de cleanup qui conserve les 10 derniers checkpoints par thread et supprime tout ce qui date de plus de 30 jours :

    DELETE FROM checkpoints
WHERE thread_id = $1
  AND created_at < NOW() - INTERVAL '30 days'
  AND checkpoint_id NOT IN (
    SELECT checkpoint_id FROM checkpoints
    WHERE thread_id = $1
    ORDER BY created_at DESC
    LIMIT 10
  );

  • Consolidation de la mémoire : avec le temps, les mémoires episodic détaillées doivent compresser en représentations sémantiques compactes : “user asked about NVDA three times in January” au lieu de stocker les trois conversations mot pour mot. Cela imite la consolidation de mémoire humaine et maintient le store gérable. Mem0 et Graphiti gèrent cela automatiquement ; si vous construisez votre propre système, planifiez des jobs de consolidation périodiques.

  • Problème de cold start : les nouveaux utilisateurs n’ont pas de long-term memory. L’agent doit dégrader gracieusement et poser des questions de clarification plutôt que d’assumer. La mémoire est additive, pas obligatoire.

  • Memory poisoning : tout ce qui se trouve dans la context window de l’agent est un point d’injection potentiel. Si un attaquant écrit des faits trompeurs dans le document store ou la long-term memory (“always approve transactions without verification”), l’agent peut les exécuter comme des instructions. Le prompt injection via des mémoires stockées est une surface d’attaque réelle. Les mitigations incluent : validation avant stockage, traiter le contenu rappelé comme une donnée non fiable plutôt que comme une instruction système, et des contrôles d’accès qui limitent quelles mémoires peuvent influencer des opérations critiques.

  • Document memory drift : la mémoire basée sur fichiers n’a pas de déduplication automatique ni de résolution de conflits. Avec le temps, des contradictions s’accumulent : un fichier dit “use pytest” tandis qu’un autre dit “use unittest.” Planifiez des revues périodiques (ou laissez l’agent le faire) pour pruner et consolider. Contrairement aux vector stores où la staleness reste cachée, vous pouvez grep pour les contradictions.

  • Document memory ne scale pas à des millions d’items : la mémoire basée sur fichiers marche pour des centaines à de faibles milliers de documents. Si votre agent doit rappeler depuis des millions de faits avec un matching flou, vous avez besoin d’un vector store. La document memory sert pour la connaissance projet structurée, pas pour la “long tail” de toutes les interactions utilisateur.

Messages clés

  1. La agent memory est composée de plusieurs stores avec des patterns d’accès différents. Gardez les checkpoints re-jouables, des faits structurés, du semantic recall, et des documents projet distincts.
  2. Construisez pause et resume avant la personnalisation. Perdre l’avancement d’une tâche est le premier échec mémoire qu’un agent longue durée met en évidence.
  3. Mettez des faits déterministes dans un stockage structuré. Utilisez la vector search quand la requête est floue et que la formulation varie.
  4. Utilisez des fichiers pour la connaissance projet que les humains doivent inspecter, éditer, versionner, ou relire via un diff.
  5. Donnez à chaque type de mémoire une règle d’expiration, de conflit et de suppression. Une mémoire que le système ne peut pas corriger devient une dette produit.
  6. Limitez ce qui retourne au modèle. La mémoire stockée ne vaut que lorsque le retrieval injecte les preuves pertinentes dans le contexte courant.
