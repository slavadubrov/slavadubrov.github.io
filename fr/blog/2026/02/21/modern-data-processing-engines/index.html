Comparaison des moteurs modernes de traitement de données : Polars, DataFusion, Daft, Ray Data et Spark

Pendant des années, Pandas a géré le traitement tabulaire en mémoire, tandis que Apache Spark gère le mode distribué. Cette séparation fonctionnait bien quand les données étaient structurées.

Les pipelines modernes traitent aussi des images, de l’audio et de la vidéo. Sur ces charges, le décodage CPU peut affamer l’inférence GPU, tandis que le garbage collection JVM et le Global Interpreter Lock de Python limitent le débit. Les nouveaux moteurs utilisent Rust et Apache Arrow pour réduire ces coûts.

Pour comparer les options, j’ai benchmarké Polars, DataFusion, Daft, Ray Data et Spark sur deux jeux de données réels. Les trajets de taxi à NYC représentent le travail tabulaire ; les images Food-101 représentent un pipeline multimodal.

Le répertoire engine-comparison-demo contient le code. Exécutez-le sur votre matériel, car les performances dépendent de la machine, du jeu de données et de la charge de travail.

TL;DR : commencez par la forme du travail, pas par le gagnant d’un benchmark. Polars est un bon défaut pour des pipelines locaux de DataFrame ; DataFusion convient aux équipes qui intègrent un moteur de requête ; Ray Data et Daft sont conçus pour des pipelines mixtes CPU/GPU ; et Spark reste un choix mature pour du SQL distribué et de l’ETL. Les gains de vitesse décrits dans ce guide correspondent à des charges spécifiques ; ils ne se répercutent pas automatiquement sur les vôtres. Relancez les benchmarks associés sur vos données et votre matériel avant de décider.

Types de charges de travail pour le traitement de données

Les moteurs se spécialisent : la première question à trancher est donc le type de charge réel que vous avez. La plus grande séparation oppose les données structurées aux données multimodales.

Données structurées ou tabulaires : filtrage, agrégation et jointures. Elles sont généralement limitées par le CPU et tiennent souvent en mémoire. D’après Polars, environ 90% des requêtes traitent moins de 1TB, donc beaucoup peuvent s’exécuter sur une seule machine moderne plutôt que sur un cluster.

AI multimodale : traite images, audio ou vidéo. L’inférence peut tourner sur un GPU alors que le décodage CPU, les lectures distantes ou le batching limitent le pipeline. La phase qui limite le débit varie avec le type d’instance et les opérateurs ; mesurez donc l’utilisation sur l’ensemble du chemin plutôt que de dimensionner le GPU isolément.

Les nouveaux moteurs ciblent différents segments de cet espace. L’exécution native peut réduire la surcouche Python, des interfaces compatibles Arrow peuvent rendre les échanges de données moins coûteux, et une exécution en streaming peut borner la mémoire sur des jeux de données plus grands que le RAM. Aucun de ces avantages n’est automatique pour chaque opérateur ou conversion.

Partie 1 : traitement sur nœud unique

Pandas privilégie un modèle de programmation eager, en mémoire. Beaucoup d’opérations courantes créent des intermédiaires, et l’exécution parallèle n’est pas coordonnée via un query optimizer. Cet arbitrage rend le code exploratoire plus direct, mais peut devenir coûteux sur des scans analytiques plus grands. Sur le benchmark PDS-H de Polars, au facteur d’échelle 10, Pandas a pris environ 365 secondes pour la suite, tandis que le moteur streaming de Polars prenait 3.89 secondes. Le résultat d’environ 94x décrit ce benchmark et cette configuration ; ce n’est pas un facteur de conversion général Pandas→Polars.

Polars pour des pipelines tabulaires locaux

Polars est un défaut pragmatique lorsque le pipeline local de DataFrame a dépassé l’exécution eager, en un seul processus. Son API lazy construit un plan de requête avant exécution, permettant des optimisations comme le predicate pushdown et la projection pruning. Le moteur peut ensuite exécuter les opérateurs en parallèle et, quand c’est supporté, en batches streaming.

L’écart se creuse avec la taille des données. Au scale factor 100 (~100 GB), le moteur streaming de Polars a terminé en 23.94 secondes contre 152.27 secondes pour son moteur in-memory — environ 6x plus rapide, sur un jeu de données plus grand que le RAM.

D’après engine_comparison_examples.ipynb :

import polars as pl

# scan_parquet reads only the schema — no data loaded yet
q = (
    pl.scan_parquet("yellow_tripdata_2024-01.parquet")
    .filter(
        (pl.col("trip_distance") > 5.0)
        & (pl.col("total_amount") > 30.0)
    )
    .group_by("payment_type")
    .agg(
        pl.col("total_amount").mean().alias("avg_fare"),
        pl.col("trip_distance").mean().alias("avg_distance"),
        pl.len().alias("trip_count"),
    )
)

# The entire plan is optimized and executed here, in parallel
result = q.collect()

La différence importante est le modèle d’exécution. Dans la requête lazy ci-dessus, Polars peut pousser le filtre et la sélection de colonnes dans le scan Parquet. Cela peut sauter des row groups et éviter de lire des colonnes inutilisées. Un pipeline eager Pandas typique n’a pas de plan global de requête pour optimiser, même si une utilisation soigneuse de filtres Parquet, des colonnes sélectionnées et des backends alternatifs peut récupérer une partie de l’écart.

DataFusion pour des moteurs de requête embarqués

Là où Polars est une bibliothèque utilisée directement, DataFusion est le moteur sur lequel on construit d’autres moteurs. Il alimente InfluxDB 3.0, GreptimeDB et l’accélérateur Comet Spark d’Apple.

Lors d’un ClickBench publié par le projet DataFusion en novembre 2024, DataFusion a mené les configurations Parquet testées sur un nœud unique. L’équipe Embucket a ensuite publié un run TPC-H scale-factor-1000 sur un nœud large. Ces résultats montrent ce que peut apporter une montée en charge sous conditions spécifiques ; ils ne prouvent pas que toute charge de 1 TB doive éviter un cluster.

D’après engine_comparison_examples.ipynb:

from datafusion import SessionContext

ctx = SessionContext()
ctx.register_parquet("taxi", "yellow_tripdata_2024-01.parquet")

# SQL executed directly against Parquet — no intermediate copies
df = ctx.sql("""
    SELECT payment_type,
           COUNT(*)           AS trip_count,
           AVG(trip_distance) AS avg_distance,
           AVG(total_amount)  AS avg_fare
    FROM taxi
    WHERE trip_distance > 5.0 AND total_amount > 30.0
    GROUP BY payment_type
    ORDER BY trip_count DESC
""")
result = df.to_pandas()

La force de DataFusion est sa modularité. Les APIs d’extension couvrent des catalogues personnalisés, des table providers, des règles d’optimizer et des plans d’exécution. C’est pour cela qu’on la retrouve dès que quelqu’un construit une plateforme de données sur mesure ou embarque un moteur de requête dans son propre produit.

Daft pour des données multimodales

Daft intègre images, audio, vidéo et embeddings dans le workflow de DataFrame. Il fournit des expressions natives pour des opérations comme le décodage d’image et les téléchargements d’URL, de sorte que les parcours de prétraitement courants n’exigent pas une boucle Python ligne-par-ligne. Cette intégration est la raison principale de le considérer plutôt qu’un moteur tabulaire généraliste.

D’après engine_comparison_examples.ipynb :

import daft

df = daft.read_parquet("yellow_tripdata_2024-01.parquet")

result = (
    df.where(
        (daft.col("trip_distance") > 5.0)
        & (daft.col("total_amount") > 30.0)
    )
    .groupby("payment_type")
    .agg(
        daft.col("total_amount").mean().alias("avg_fare"),
        daft.col("trip_distance").mean().alias("avg_distance"),
        daft.col("trip_distance").count().alias("trip_count"),
    )
    .collect()
)

L’API vous semblera familière si vous connaissez Pandas, mais le moteur est le même stack Rust + Arrow que celui qu’on trouve dans Polars et DataFusion. Là où Daft apporte un gain est lorsque les “lignes” de votre DataFrame sont des images, des PDFs ou des tenseurs.

Partie 2 : données multimodales

L’ETL tabulaire réduit généralement les données : filtre, agrège, puis écrit moins que ce qu’on lit. Les pipelines AI multimodaux font l’inverse. Un chemin “document” unique peut se déployer en dizaines de chunks de texte et en vecteurs d’embedding.

Dans un pipeline PySpark conventionnel, images et audio entrent souvent comme des données binaires et finissent dans des bibliothèques Python pour le décodage ou des transformations. Passer la frontière JVM/Python et sérialiser les résultats peut représenter une part importante du temps wall-clock. Spark peut utiliser des chemins basés sur Arrow, des UDF vectorisés et des intégrations avec accélérateurs, mais ces choix demandent une conception et une mesure explicites.

Exécution pipeline et utilisation GPU

Spark planifie le travail en étapes séparées par des frontières de shuffle. Une implémentation simple peut placer téléchargement, décodage et inférence dans une séquence qui laisse soit du CPU, soit du GPU en attente. Spark supporte le scheduling de ressources GPU et des plugins ; l’idle time n’est donc pas une fatalité. En revanche, le chevauchement et le backpressure ne sont pas des propriétés automatiques d’un job DataFrame PySpark “ordinaire”.

L’exécution pipeline est l’alternative. Au lieu d’exécuter les étapes l’une après l’autre, le moteur chevauche I/O, travail CPU et inférence GPU : ainsi, la composante lente est la seule chose qui attend à un instant donné.

Partie 3 : traitement distribué

Dès qu’une seule machine n’est plus suffisante, il faut choisir comment répartir le travail.

Apache Spark

Spark est une option mature pour l’ETL tabulaire à grande échelle, les jointures lourdes en shuffle, et les organisations qui opèrent déjà dans son écosystème. Sa récupération basée sur la lignée (lineage) et son support large de plateformes comptent lorsque la fiabilité et la familiarité opérationnelle l’emportent sur la vitesse locale. Les pipelines CPU/GPU mixtes demandent une configuration plus délibérée des ressources et une conception de pipeline, en particulier sur la voie SQL : c’est là où Ray Data et Daft offrent une abstraction plus ciblée.

D’après distributed_spark.ipynb:

from pyspark.sql import SparkSession
from pyspark.sql import functions as F

spark = SparkSession.builder \
    .appName("TaxiETL") \
    .config("spark.sql.adaptive.enabled", "true") \
    .getOrCreate()

orders = spark.read.parquet("s3a://lake/taxi/*.parquet")
zones = spark.read.csv("s3a://lake/taxi_zones.csv", header=True)

# Spark excels at this: joining massive tables with a shuffle
result = (
    orders
    .filter(F.col("trip_distance") > 5.0)
    .join(zones, orders.PULocationID == zones.LocationID, "inner")
    .groupBy("Borough")
    .agg(
        F.sum("total_amount").alias("total_revenue"),
        F.avg("total_amount").alias("avg_fare"),
    )
    .orderBy(F.desc("total_revenue"))
)

Ray Data pour du calcul hétérogène

Ray Data a été conçu autour des charges AI. Au lieu des barrières d’étapes de Spark, il s’appuie sur un modèle streaming qui maintient les GPUs alimentés. La fonctionnalité la plus importante pour les pipelines AI est le mixed resource scheduling : vous pouvez déclarer qu’un actor veut “1 GPU, 4 CPUs” et qu’un autre ne veut que des CPUs, et Ray gère le reste.

Amazon a rapporté plus de $120 millions de dollars d’économies annuelles après avoir migré certaines charges internes de traitement de données de Spark vers Ray. Le rapport cite 91% d’amélioration en efficacité des coûts dans la preuve de concept et 82% en production par GiB de données en entrée S3. L’échelle est notable, mais c’est une étude de cas de migration sur des charges spécifiques, pas une économie attendue pour une adoption Ray “typique”.

D’après distributed_ray.ipynb:

import ray

ray.init()

ds = ray.data.read_images("s3://my-bucket/food101/")

class ImageClassifier:
    def __init__(self):
        import torch
        from torchvision.models import resnet18, ResNet18_Weights
        self.model = resnet18(weights=ResNet18_Weights.DEFAULT).cuda()
        self.model.eval()
        self.preprocess = ResNet18_Weights.DEFAULT.transforms()

    def __call__(self, batch):
        import torch
        tensors = torch.stack([
            self.preprocess(img) for img in batch["image"]
        ]).cuda()
        with torch.no_grad():
            preds = self.model(tensors)
        return {
            "prediction": preds.argmax(dim=1).cpu().numpy(),
            "confidence": preds.max(dim=1).values.cpu().numpy(),
        }

# ActorPoolStrategy creates persistent GPU workers
predictions = ds.map_batches(
    ImageClassifier,
    compute=ray.data.ActorPoolStrategy(size=4),
    num_gpus=1,
    batch_size=64,
)
predictions.write_parquet("s3://output/predictions/")

Le ratio CPU→GPU mérite ici l’attention. Dans les benchmarks d’Anyscale, Ray Data a continué à monter en performance quand le nombre de CPUs par GPU augmentait, tandis que les autres moteurs testés plafonnaient. Passer d’un ratio 4:1 à 32:1 a apporté un speedup de 3x sur l’inférence d’images, parce que les feeders CPU finissaient enfin par suivre le GPU.

Daft distribué

Daft scale out via son moteur Flotilla : un worker Swordfish par nœud, avec Flotilla au-dessus qui fait le scheduling à l’échelle du cluster. Swordfish gère l’exécution Rust locale et fait transiter I/O et calcul via du streaming en small-batch, ce qui permet à chaque nœud de rester occupé sans attendre l’étape suivante.

Dans les benchmarks publiés par Daft, Flotilla a tourné 2–18x plus vite que les implémentations Spark testées sur quatre charges multimodales. Le plus grand écart concernait un cas de video-object-detection. Traitez ce résultat comme une preuve que la conception de l’exécution compte pour ces pipelines, puis comparez-le avec les résultats Anyscale ci-dessous et avec un test local.

Anyscale, la société à l’origine de Ray, a publié un benchmark concurrent où Ray Data réduit ou inverse l’écart sur des instances à forte charge CPU après tuning. Ensemble, les deux études des éditeurs sont une raison de tester des opérateurs représentatifs et des ratios CPU-to-GPU, plutôt que d’inférer un classement durable des “ligues” entre moteurs.

D’après distributed_daft.ipynb:

import daft
from daft import col

# Daft's Flotilla engine distributes work across the cluster
df = daft.read_parquet("s3://data-lake/pdf_metadata/*.parquet")

# Download PDFs — Daft parallelizes downloads in Rust
df = df.with_column("pdf_bytes", col("pdf_url").url.download())

# Define a GPU UDF for embedding generation
@daft.udf(return_dtype=daft.DataType.list(daft.DataType.float32()))
class TextEmbedder:
    def __init__(self):
        from sentence_transformers import SentenceTransformer
        self.model = SentenceTransformer("all-MiniLM-L6-v2", device="cuda")

    def __call__(self, text_col):
        texts = text_col.to_pylist()
        embeddings = self.model.encode(texts, batch_size=32)
        return [emb.tolist() for emb in embeddings]

# Daft schedules CPU downloads and GPU embeddings simultaneously
df = df.with_column("embedding", TextEmbedder(col("text")))
df.write_parquet("s3://output/embeddings/")

Partie 4 : le rôle de Rust et Arrow

Sous la concurrence, la convergence est l’histoire la plus intéressante. Polars, Daft et DataFusion utilisent massivement Rust, tandis que Ray inclut des composants natifs aux côtés de ses APIs Python. Tous peuvent échanger des données via des briques de l’écosystème Apache Arrow.

Le Arrow PyCapsule Interface (le protocole @@__arrow_c_stream__) donne aux bibliothèques compatibles un moyen standard d’échanger des streams Arrow. Les transferts peuvent éviter la sérialisation ligne-par-ligne et réutiliser des buffers quand les schémas et les layouts mémoire sont compatibles. La matérialisation, le rechunking, la conversion de type ou le transfert de périphérique peuvent toutefois copier des données ; vérifiez donc le handoff via du profiling, plutôt que d’assumer qu’il est gratuit.

from datafusion import SessionContext
import polars as pl

# Compute in DataFusion (Rust-native execution)
ctx = SessionContext()
ctx.register_parquet("events", "events.parquet")
df = ctx.sql("""
    SELECT user_id, COUNT(*) as event_count
    FROM events WHERE event_type = 'purchase'
    GROUP BY user_id HAVING COUNT(*) > 5
""")

# Convert through Arrow; compatible buffers may be reused
arrow_table = df.to_arrow_table()
df_polars = pl.from_arrow(arrow_table)

# Continue analysis in Polars
result = df_polars.with_columns(
    pl.col("event_count").rank().alias("rank")
).sort("rank")

Pourquoi ces nouveaux moteurs utilisent-ils Rust pour l’exécution native ?

  1. Absence de tracing garbage collector dans le code Rust. L’ownership donne aux opérateurs natifs un contrôle plus direct sur l’allocation et la libération. Cela peut réduire la latence liée au GC, mais n’empêche pas la pression mémoire ni les échecs out-of-memory.

  2. Représentations natives plus compactes. Les structures Rust ne transportent pas d’en-têtes d’objets Java. Le bénéfice pratique dépend du layout du moteur : des systèmes JVM columnaires évitent aussi souvent de représenter chaque valeur comme un objet individuel.

  3. Vérifications de concurrence plus strictes. Les règles de Rust safe empêchent de nombreuses data races à la compilation. Le code du moteur peut encore contenir des blocs unsafe et des bugs de concurrence logiques, mais le langage réduit la surface d’échec.

Combiné avec le layout mémoire columnar d’Arrow, ces choix peuvent réduire le surcoût d’allocation et de sérialisation. Ils ne l’éliminent pas à toutes les frontières : les objets Python, le transport réseau, les schémas incompatibles et les mouvements entre périphériques restent déterminants.

Partie 5 : adopter plusieurs moteurs

Vous n’avez pas besoin de forcer toute la plateforme à passer par un seul moteur. La composition est utile quand le coût de handoff entre moteurs est inférieur à la nécessité de faire gérer à un seul système toutes les charges.

Un schéma de relais possible utilise Spark pour des jointures lakehouse établies, pour écrire une table ouverte ou un format de fichier, puis confie le résultat à Ray Data ou Daft pour de l’inférence GPU ou des transformations multimodales. Polars ou DuckDB peuvent servir pour une analyse locale sur les mêmes fichiers. Une petite équipe peut n’avoir besoin que d’un seul de ces moteurs ; ajoutez-en un autre quand un goulot d’étranglement mesuré justifie la frontière opérationnelle.

Ce qui rend cette composition possible, ce sont les formats ouverts : Parquet, Delta, Iceberg, Arrow. Chaque moteur de la stack les lit et écrit nativement, de sorte que le handoff entre étapes se résume à un chemin de fichier.

Scaling diagonal

Pendant longtemps, le choix se résumait à scale up (une machine plus grosse) ou scale out (plus de machines). Polars Cloud fait quelque chose entre les deux, qu’ils appellent diagonal scaling. Vous scalez horizontalement en lisant depuis le stockage cloud pour saturer l’I/O, puis vous revenez à un gros nœud unique une fois que filtres et agrégations ont réduit les données. Le shuffle distribué ne se produit jamais.

Le message plus général : comparez le coût par job réussi, pas le prix horaire d’une instance. Un nœud plus grand peut être moins cher quand la réduction du runtime dépasse son taux plus élevé, mais le résultat dépend de l’I/O, de la pression mémoire et de la quantité de travail éliminée avant un shuffle.

Points clés

  1. Prouvez qu’une seule machine ne suffit pas. Les résultats de scale-up montrent que certains gros scans analytiques tiennent sur un nœud unique. Mesurez la mémoire, l’I/O, le spill et les exigences de recovery avant d’accepter le surcoût d’un cluster.

  2. Les modèles d’exécution comptent plus que la syntaxe familière. La planification lazy, le pushdown, le streaming et les opérateurs parallèles expliquent une grande partie de l’écart entre un script DataFrame eager et un moteur analytique.

  3. Mesurez tout le pipeline d’accélération. Décodage, I/O réseau, batching, sérialisation et backpressure déterminent si un GPU reste occupé. Ray Data et Daft rendent ce chevauchement une abstraction centrale ; Spark peut le supporter avec une conception et des outils additionnels.

  4. Constituez la shortlist par charge de travail, puis benchmarkez. Utilisez l’ajustement à l’écosystème pour réduire le champ et un job end-to-end représentatif pour choisir. Les résultats de benchmarks des éditeurs sont des hypothèses, pas des garanties.

  5. Les formats ouverts rendent le choix réversible. Les interfaces compatibles Arrow, Parquet et les formats de tables ouverts peuvent réduire les coûts de handoff. Confirmez si une conversion donnée réutilise des buffers ou les copie.

Si vous avez besoin d’un point de départ, commencez par Polars pour un pipeline tabulaire local et Daft ou Ray Data pour un pipeline CPU/GPU mixte. Choisissez Spark quand son exécution distribuée, son écosystème ou sa base opérationnelle existante résout une exigence. La taille du dataset seule est une raison faible.
