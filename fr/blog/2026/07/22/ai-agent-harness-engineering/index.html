Harness engineering pour les agents AI : concevoir la boucle autour du modèle

Partie 6 de la série Engineering the Agentic Stack

La reasoning loop d’un agent choisit l’action suivante. Son harness fournit le contexte, valide et autorise les tool calls proposés, transmet les appels acceptés au runtime, enregistre les résultats et décide si la tâche est terminée.

Les modèles proposent des modifications et peuvent déclarer une tâche terminée, tandis que le harness applique les permissions et interprète les checks d’acceptation qui déterminent si la boucle peut s’arrêter. La partie 5 traitait du runtime qui maintient le processus en vie. Cet article se concentre sur le code de contrôle à l’intérieur de ce runtime : comment mesurer si chaque ajout aide réellement, et comment garder ces contrôles faciles à localiser à mesure que le harness évolue.

Au-delà du premier check d’acceptation explicite, chaque retry, handoff ou évaluateur ajouté est une hypothèse sur une défaillance observée. Il ne mérite sa place que lorsqu’une comparaison contrôlée montre qu’il aide.

Pour rendre ce chemin de contrôle concret, j’utiliserai un petit dépôt fictif de boutique. La tâche de développement consiste à abaisser le seuil d’une remise automatique de 10 % de $100 à $75 dans src/checkout.py. Le dépôt comporte deux checks requis :

  • pytest tests/test_checkout.py vérifie le calcul de la remise.
  • pnpm playwright test tests/checkout_discount.spec.ts ajoute un article à $80 dans une boutique de test locale et vérifie que la page de paiement affiche une remise de $8.

L’exemple est un support pédagogique, pas une vraie application ni un benchmark. Chaque tentative démarre du même commit et des mêmes données de test initialisées. Le harness ne peut accepter la modification que lorsque les deux commandes passent et que la trace relie ces résultats au commit testé.

Les sections suivantes basculent volontairement vers deux autres exemples. Une API de commande en staging montre pourquoi les appels qui modifient l’état ont besoin d’une protection contre le replay, tandis qu’une migration d’adaptateur de paiement montre ce dont une nouvelle session modèle a besoin pour reprendre un travail inachevé. Le lab compagnon vers la fin est encore distinct : il est exécutable, mais il contient des tâches simulées génériques plutôt que ce dépôt de boutique.

En bref : commencez avec un seul modèle, quelques outils étroits et un check d’acceptation explicite. Ajoutez des retries après que les traces ont montré des échecs transitoires d’appel. Ajoutez un handoff de progression lorsque des sessions reprises refont le travail. Quand vous testez l’un ou l’autre changement, gardez fixes la version du modèle, les tâches, le grader et le budget total. Retirez le composant s’il n’améliore pas le résultat mesuré.

Le schéma suit la modification de remise depuis la proposition jusqu’à la preuve. Le harness fournit la tâche et les fichiers, vérifie les arguments et permissions proposés pour edit_file, puis transmet l’appel accepté. Après que le runtime a appliqué la modification, le harness exécute les tests d’acceptation unitaires et browser nommés. Une commande échouée revient au modèle comme preuve pour un nouveau tour ; deux commandes qui passent rendent la modification éligible à l’acceptation.

Ce que possède le harness

Le walkthrough de la boucle Codex d’OpenAI décrit le cycle de base. Le harness assemble un prompt, demande au modèle l’action suivante, envoie un tool call accepté au runtime, ajoute le résultat et redemande jusqu’à ce que le harness accepte le résultat ou rende le contrôle à l’utilisateur.

Les implémentations peuvent fusionner plusieurs responsabilités dans un seul processus. Les frontières de défaillance restent toutefois différentes :

TermeRôleExemple d’agent de développement
ModèlePropose du texte, un tool call ou une réponse finaleSuggère une modification de src/checkout.py
Reasoning loopChoisit le mouvement suivant à partir du contexte disponibleInspecter, modifier, tester, réinspecter
HarnessFournit le contexte, autorise et transmet les appels, enregistre les résultats et vérifie l’achèvementAutorise les modifications sous src/ et exige les deux tests nommés
RuntimeExécute les appels et maintient le processus en vie et isoléWorker, sandbox, magasin de sessions, file d’attente

Quand une défaillance apparaît, diagnostiquez la frontière qui doit répondre. Un mauvais plan peut nécessiter de meilleures instructions ou un meilleur raisonnement du modèle. Si edit_file cible un chemin en dehors de src/, le harness doit le rejeter, tandis qu’un processus sandbox qui meurt avant l’exécution de la modification relève du runtime, qui doit redémarrer le worker ou signaler le crash.

La propre étude de cas sur le harness engineering d’OpenAI décrit une instance applicative amorçable pour chaque worktree. L’équipe a aussi connecté l’automatisation browser à l’environnement de l’agent et exposé logs, métriques et traces.

Une tâche telle que « aucun span dans ces quatre parcours utilisateurs critiques ne dépasse deux secondes » est devenue testable parce que l’agent pouvait exécuter l’application et interroger les mêmes signaux qu’un ingénieur inspecterait. L’étude de cas est spécifique au produit. Ce qui se transfère, c’est la condition derrière le résultat : l’application et ses signaux de performance devaient être disponibles à l’intérieur de l’environnement de l’agent.

Lopopolo, auteur de cette étude de cas, maintient un guide de terrain du harness engineering qui nomme les deux leviers que cet article actionne : garder le modèle et l’agent de développement fixes comme une boîte noire, et concevoir le contexte et les outils autour d’eux. Son cadrage explique aussi pourquoi une si grande partie du harness finit sous forme de code ordinaire.

Le niveau de qualité d’une organisation, ses procédures, l’historique des exceptions et les relations d’autorité se situent sous la ligne de flottaison de ce qu’un modèle général peut connaître. Le harness les expose sous forme d’instructions de dépôt, de règles de permission et de checks d’acceptation. Chaque exécution acceptée peut réinjecter ses enseignements dans ces artefacts au lieu de compter sur la session suivante pour les redécouvrir.

Suivre la modification de remise de la proposition à l’acceptation

Pour la tâche de remise définie ci-dessus, le modèle propose de modifier calculate_discount dans src/checkout.py. Plusieurs choses se produisent avant que cette modification compte comme une progression :

  1. Le constructeur de contexte fournit la tâche, les instructions du dépôt, les fichiers pertinents, les résultats d’outils antérieurs et le plan courant.
  2. Le modèle propose un appel edit_file avec un chemin et un texte de remplacement.
  3. La frontière d’outil (le code du harness entre proposition et exécution) valide les arguments, vérifie le chemin par rapport au périmètre autorisé et demande une approbation si l’opération en a besoin.
  4. Le runtime applique la modification dans le sandbox et renvoie un résultat structuré.
  5. Le harness exécute pytest tests/test_checkout.py, puis pnpm playwright test tests/checkout_discount.spec.ts, et lit les deux codes de sortie. Le test browser vérifie la remise visible de $8 sur le panier initialisé à $80.
  6. Le harness décide de la signification des résultats. Un check échoué devient un nouveau contexte pour le tour de modèle suivant, et une exécution qui passe fait de la tâche une candidate à l’achèvement.
  7. Un résultat qui passe ne devient une preuve d’achèvement qu’après que le harness a enregistré la commande, le code de sortie et la version de l’artefact testé dans la trace.

À l’étape 2, aucun fichier n’a encore changé. Le harness peut rejeter ../../secrets.env, exiger une approbation pour une commande destructive ou arrêter une exécution qui a épuisé son budget. Après l’exécution des tests, le harness lit lui-même leurs codes de sortie. Le modèle ne peut pas marquer sa propre modification comme réussie.

La trace doit montrer le chemin proposé et le texte de remplacement, la décision de permission, les fichiers modifiés, le commit testé et les résultats des deux commandes. Un message final done sans ces enregistrements ne prouve pas que cette modification a passé les checks requis.

Décider où chaque règle est appliquée

Placez tests/checkout_discount.spec.ts dans la logique normale du programme. Le harness transmet la commande Playwright au runtime, lit son code de sortie et refuse de terminer l’exécution tant qu’elle échoue. Un prompt peut rappeler au modèle d’exécuter le test. Il ne peut pas empêcher le modèle de déclarer le succès sans preuve.

Les contrats d’outil séparent proposition et permission

La tâche de remise ne nécessite que des modifications de fichiers et des commandes de test. Une API qui modifie l’état a un mode de défaillance différent ; changeons donc d’exemple pour cette section. Supposons que l’agent puisse appeler create_test_order sur un service de commandes en staging pendant la préparation des données de test. Cet outil n’est pas l’un des checks d’acceptation de la tâche de remise. Il est utile ici parce qu’un timeout peut masquer si le service a créé une commande.

La frontière d’outil a besoin de plus qu’une description en langage naturel. Pour create_test_order, le harness a besoin d’un contrat avec :

  • des arguments validés, afin qu’une entrée mal formée soit rejetée avant exécution
  • un résultat structuré tel que { "order_id": "123", "created": true }, afin que les checks suivants n’aient pas à parser du texte libre
  • une catégorie d’effet qui enregistre si l’appel ne fait que récupérer de l’information ou modifie un fichier, un enregistrement de base de données ou un service externe. Elle enregistre aussi si répéter l’appel est sûr. Cette étiquette indique au harness si un retry automatique pourrait dupliquer le travail : il peut retry get_order_status quand le service définit cette recherche comme read-only, mais il ne doit pas retry aveuglément create_test_order parce que le premier appel a peut-être déjà créé la commande
  • une politique de timeout et de retry, afin qu’une réponse perdue ne déclenche pas une séquence illimitée d’appels
  • une règle de permission qui indique quelle approbation est requise. La lecture du statut d’une commande peut s’exécuter automatiquement, tandis que la création d’une commande peut nécessiter une confirmation

La description en langage naturel est le texte montré au modèle. Elle peut dire : « Créer une commande de test pour vérifier le checkout. » Cette phrase aide le modèle à décider quand proposer create_test_order. Elle n’autorise pas l’appel. Dans cet exemple, le client MCP du harness valide les arguments, applique ses propres règles et vérifie la confiance du serveur, les exigences d’approbation et la sécurité des retries avant de transmettre quoi que ce soit.

Un serveur MCP publie au client des descriptions d’outils et des annotations de comportement facultatives. Un serveur défaillant ou malveillant pourrait décrire un outil qui modifie l’état comme inoffensif. Si le client acceptait automatiquement cette affirmation, il pourrait exécuter ou retry create_test_order sans approbation et créer un doublon ; la spécification MCP exige donc que les clients traitent les annotations d’outil comme non fiables à moins que le serveur lui-même ne soit de confiance.

La spécification ne prescrit pas un réglage de confiance universel. Le client a donc besoin d’une politique de confiance explicite pour son déploiement ; un serveur ne peut pas rendre ses propres annotations dignes de confiance. Cette politique décide quelles métadonnées peuvent influencer les décisions de permission ou de retry, et quelles annotations restent seulement indicatives.

Retry d’un appel qui modifie l’état : il faut une protection contre le replay

Un problème de retry plus difficile apparaît lorsque create_test_order crée la commande mais que sa réponse HTTP est perdue. Le harness voit un timeout et ne peut pas dire si le serveur a terminé la requête. Répéter l’appel peut créer une deuxième commande.

Une recherche de statut peut être rejouée quand le service la définit comme read-only. Un appel de création a besoin d’une protection telle qu’une clé d’idempotence : le client attache un identifiant de requête unique, et le service renvoie le premier résultat au lieu de créer une autre commande lorsqu’il revoit cet identifiant. Sans cette protection, le harness doit vérifier si la commande existe ou demander une décision humaine avant une nouvelle tentative. AWS documente ce pattern dans ses recommandations sur les APIs idempotentes.

L’acceptation a besoin d’une preuve indépendante

Une réponse create_test_order réussie n’établit que le fait que l’outil a renvoyé des données. Elle ne prouve pas qu’une tâche de développement a passé ses tests. Si un test browser ultérieur dépend de la commande préparée, le harness doit valider le schéma de réponse et exécuter quand même ce test avant d’accepter la modification de code.

Certains critères ne peuvent pas être réduits à un code de sortie. Pour une tâche distincte de design visuel, un évaluateur fresh peut comparer une page ou un diagramme rendu à une grille écrite. Les équipes devraient calibrer cet évaluateur par rapport à des revues humaines avant de l’utiliser comme gate d’achèvement.

Une migration d’adaptateur de paiement a besoin d’un handoff

Changeons encore de tâche, tout en restant dans le dépôt fictif de boutique. L’agent doit maintenant migrer le checkout de l’adaptateur de paiement v1 vers v2. Le travail s’étend au gestionnaire de checkout, au client de paiement, à la configuration et aux tests ; il peut donc dépasser la durée d’une session modèle.

Avant que la première session n’atteigne sa limite de contexte, elle a modifié plusieurs fichiers, démarré un sandbox de paiement local et laissé tests/payment_migration.spec.ts en échec. Ce test browser d’acceptation termine un paiement via l’adaptateur v2 et vérifie l’ID fournisseur enregistré. Un résumé de conversation peut orienter la session modèle suivante, mais il ne peut pas redémarrer le sandbox ni prouver quels fichiers sont actuellement modifiés.

La session suivante doit récupérer trois choses :

Ce qui doit être récupéréCe que cela inclutComment cela peut échouer
Historique de conversationMessages, tool calls et résultats renvoyésD’anciens détails encombrent la tâche courante
Environnement de travailFichiers, sandbox de paiement et état du test browserLa transcription dit qu’un service tourne alors qu’il est mort
Progression de la tâchePlan, checks terminés, approbation en attente, action suivanteLa session suivante répète un travail déjà terminé

La compaction remplace les anciens messages par un résumé plus court afin que la session courante puisse continuer. Un handoff de progression enregistre ce dont la session suivante a besoin : la branche courante, les fichiers modifiés, la dernière commande de test et sa sortie, ainsi que la prochaine étape non résolue. Si l’ancienne conversation contient des hypothèses obsolètes, le harness peut démarrer une nouvelle session modèle avec ce handoff et le workspace courant. Remplacer un worker crashé et restaurer ses processus est une tâche de reprise distincte du runtime.

Une petite modification de documentation peut ne nécessiter aucun de ces mécanismes. La migration de paiement a besoin d’un handoff dès que le travail traverse plusieurs sessions, parce que la session modèle suivante doit reconstruire à la fois le workspace et l’état de la tâche.

Les expériences d’Anthropic sur les agents de développement de longue durée utilisaient l’historique git et un fichier de progression entre les sessions, tandis que son rapport ultérieur sur la conception des harnesses sépare la compaction d’un handoff à fresh context et décrit l’orchestration supplémentaire, l’usage de tokens et le temps mur requis par les handoffs.

Une transcription de chat enregistre ce que le modèle a vu. Elle ne peut pas prouver si le service de commande a validé une requête avant la disparition de la réponse. La trace doit relier l’appel client, la décision d’approbation, la clé d’idempotence, le résultat serveur ou la recherche de statut, le commit testé et le résultat du test d’acceptation. Avant d’ajouter un composant, nommez la défaillance répétée qu’il doit réduire et le nombre que vous allez suivre. Retirez le composant si une comparaison contrôlée ne fait pas assez bouger ce nombre pour rembourser son coût.

Mesurer un changement à la fois

Une ablation mesure si un composant du harness produit l’effet attendu en modifiant ou en retirant ce composant pendant que le reste de l’expérience reste fixe. Par exemple, l’analyse lint de l’éditeur aide-t-elle ce modèle sur cette suite de tâches ?

Utilisez le protocole suivant :

  1. Figez la version du modèle, les instances de tâche, l’environnement, le grader et les prompts en dehors du composant testé.
  2. Donnez aux deux variantes le même budget total en tokens, en temps et en dollars.
  3. Choisissez le nombre d’essais ou la règle d’arrêt avant d’exécuter la comparaison.
  4. Exécutez les mêmes instances de tâche dans les deux variantes. Comme les sorties de modèle varient, répétez chaque tâche plusieurs fois.
  5. Rapportez la moyenne avec la dispersion ou l’intervalle de confiance.
  6. Comptez chaque essai démarré, y compris les timeouts, les arrêts de policy, les crashes du harness et les échecs de l’évaluateur.

Le taux de réussite seul peut masquer un composant coûteux. Au minimum, suivez les tâches incorrectes acceptées comme terminées, le coût et le temps mur par tâche terminée, les erreurs d’outil, les commandes dupliquées, les minutes de revue et les dérogations manuelles de permission. Choisissez la métrique qui porte le coût réel pour le produit. Une hausse de deux points des tâches terminées est un mauvais échange si elle double la file de revue.

Une expérience appariée sur la migration de paiement rend le handoff de progression mesurable. Chaque paire contrôle/traitement démarre du même commit du dépôt et du même checkpoint initialisé, avec le même modèle, la même tâche, le même grader et le même budget total. Le handoff est le seul interrupteur. La métrique primaire compte les actions d’outil dupliquées après reprise : une action est dupliquée lorsque son opération et son artefact correspondent à une étape que la session précédente avait déjà terminée.

LangChain a publié une comparaison plus large à modèle fixe pour deepagents-cli. L’exemple montre qu’il faut revalider l’ancien échafaudage quand le modèle change ; il ne fournit pas une taille d’effet générale.

Garder le harness modifiable après qu’il a justifié sa place

L’ablation garde un harness compact, mais son code peut quand même survivre au modèle pour lequel il a été réglé. Une demande telle que « masquer les secrets dans chaque chemin de capture » désigne un comportement, pas un fichier. Dans un harness de production, ce comportement peut s’étendre à plusieurs étapes d’exécution et à de l’état partagé. Un humain ou un agent de développement doit trouver chaque site d’implémentation avant de le modifier en sécurité.

Une prépublication de 2026 de Wang et al., le Harness Handbook, appelle cette étape behavior localization. Le handbook construit une carte centrée sur les comportements à partir de la codebase du harness. Une analyse statique extrait un graphe de programme sans appels au modèle, puis un LLM organise ses unités en étapes d’exécution.

Le mainteneur ou l’agent de développement commence par une vue d’ensemble du système, ouvre l’étape d’exécution pertinente, puis descend jusqu’à des entrées ancrées dans le code source pour une fonction ou un fichier. Une vue registre enregistre où l’état partagé est écrit et lu entre les étapes. Cette hiérarchie garde la vue d’ensemble compacte tout en préservant un chemin vers le code source.

La fraîcheur est une règle distincte. Chaque localisateur doit se résoudre par rapport au dépôt vivant. Le handbook exclut les entrées obsolètes au lieu de deviner, et chaque diff non vide resynchronise les entrées qu’il affecte.

Le schéma compresse la boucle de modification : une requête portant uniquement sur un comportement descend les niveaux du handbook, chaque localisateur candidat est vérifié par rapport au dépôt vivant avant l’écriture du plan, et chaque diff appliqué resynchronise la carte.

L’évaluation du Handbook suit le protocole défendu par cet article. Sur deux harnesses open source (Terminus-2, six fichiers Python, et le monorepo Codex, 2 267 fichiers Rust), un planner read-only piloté par DeepSeek-V4-Pro explorait soit directement le dépôt, soit via le handbook. Les requêtes, le dépôt, les permissions d’outil et le decoding étaient identiques dans les deux bras. Trois juges (GPT-5.5, Opus 4.8, DeepSeek-V4-Pro) ont évalué chaque plan de modification sur la localization, le contrôle du périmètre et le raisonnement :

HarnessTaux de victoire baselineAvec assistance du HandbookTokens du planner
Terminus-2 (6 fichiers)26.7%45.6%−8.6%
Monorepo Codex (2 267 fichiers)28.3%38.3%−12.7%

Le planner assisté par le handbook gagnait plus souvent et utilisait moins de tokens de planning dans les deux dépôts. Les conditions restent attachées à ce résultat : trois juges LLM ont noté des plans de modification produits par un seul modèle de planner sur deux harnesses. L’étude évaluait des plans, pas des diffs exécutés ni des taux de défauts en production.

Les sections précédentes utilisent les traces pour répondre à la question de savoir pourquoi un composant existe. Cette carte répond à la question suivante : où vit ce composant lorsqu’il faut le modifier ?

Essayer la méthode dans le lab compagnon

Le projet harness-demo au commit 517353f3 est un petit exercice déterministe avec 12 tâches synthétiques génériques couvrant des changements de code comme fix-parser-edge-case, split-large-module et wire-browser-test. Il n’implémente pas le dépôt fictif de boutique.

Chaque fixture de tâche déclare une difficulté plus quatre conditions booléennes : un outil flaky, une progression perdue, un gap d’implémentation manqué et un achèvement ambigu. Le simulateur dérive une cinquième condition pour les tâches difficiles qui nécessitent aussi un fichier de progression : sans context_reset, la compaction préserve des hypothèses obsolètes. Un grader déterministe marque une tâche comme réussie uniquement lorsque la configuration sélectionnée gère toutes les conditions applicables. Aucun modèle ni service externe n’est exécuté.

Les commandes répondent à des questions différentes :

  • make check exécute Ruff et sept tests unitaires, y compris le validateur qui rejette toute paire d’ablation qui modifie plus d’un composant.
  • make run imprime une matrice pédagogique cumulative, puis cinq comparaisons valides leave-one-component-out.
  • make failures nomme la condition non gérée pour chaque tâche en échec. Le harness complet doit se terminer avec all synthetic tasks pass.
make check
make run
make failures

La section causale de make run ressemble à ceci :

component                 control  treatment  delta
retry_policy              8/12     12/12       +4
progress_handoff          7/12     12/12       +5
evaluator                 8/12     12/12       +4
fail_closed_acceptance    7/12     12/12       +5
context_reset            10/12     12/12       +2

Pour chaque ligne, le contrôle est la configuration complète avec un composant retiré ; le traitement ne rétablit que ce composant. La matrice cumulative précédente est utile pour s’orienter, mais certaines de ses lignes adjacentes ajoutent plusieurs composants à la fois et ne peuvent donc pas identifier une cause.

Le lab valide chaque paire déclarée avant de l’exécuter. Ses tests de régression incluent aussi une paire volontairement invalide qui modifie à la fois la politique de retry et l’évaluateur ; le validateur la rejette.

Le schéma de configuration du lab vérifie les cinq champs de composant. Cet extrait exécutable montre la même garde sur une paire valide de handoff de progression :

from dataclasses import dataclass, fields


@dataclass(frozen=True)
class Config:
    progress_handoff: bool = False
    evaluator: bool = False
    retry_policy: bool = False
    fail_closed_acceptance: bool = False
    context_reset: bool = False


def changed_components(control: Config, treatment: Config) -> tuple[str, ...]:
    return tuple(
        field.name
        for field in fields(control)
        if getattr(control, field.name) != getattr(treatment, field.name)
    )


control = Config(progress_handoff=False, evaluator=True, retry_policy=True)
treatment = Config(progress_handoff=True, evaluator=True, retry_policy=True)
assert changed_components(control, treatment) == ("progress_handoff",)

Commencer avec une seule boucle et un seul check d’acceptation

Je commencerais un harness d’agent de développement avec un seul modèle capable, des instructions de dépôt, quelques outils étroits, un sandbox et un seul test d’acceptation explicite. J’enregistrerais les tool calls, les résultats, les coûts et ce test final dans une seule trace afin que les premières défaillances utiles soient visibles sans avoir à les reconstituer à partir des logs terminal et des transcriptions de chat. Il s’agit d’une baseline proposée, pas d’une preuve issue d’un système déployé.

À partir de là, n’ajoutez que ce qu’une trace justifie. Enregistrez qui maintient chaque composant, combien de tokens ou de secondes il ajoute, et quel test de régression justifierait sa suppression après une montée de version du modèle.

Six mois plus tard, quelqu’un qui voit progress_handoff=True doit pouvoir trouver les traces d’échec qui l’ont justifié et les cas de régression qui le maintiennent encore en place. Les traces expliquent pourquoi le composant existe ; une carte de comportement à jour explique où le modifier.
