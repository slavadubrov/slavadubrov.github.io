Sécurité des AI agents : permissions, sandboxes et menaces MCP

Viacheslav Dubrov

Ce guide s’adresse aux ingénieurs qui développent ou déploient des AI agents utilisant des tools. Il explique où appliquer les permissions des tools, les restrictions de sandbox, les limites de credentials et l’approbation humaine, afin que vous puissiez déterminer quel contrôle doit arrêter une action dangereuse avant qu’elle n’atteigne des fichiers, des réseaux ou un système externe.

Le harness est le code qui construit chaque prompt, décide quels tool calls proposés sont exécutés et renvoie les résultats au modèle. La plupart des contrôles doivent se trouver à cet endroit, car c’est le dernier point peu coûteux où arrêter une commande. Une fois la commande exécutée, la sandbox, les credentials qui lui ont été transmis et tout processus de récupération doivent contenir les dommages. Certains incidents décrits dans cet article n’atteignent jamais un modèle.

La sécurité des AI agents est plus large que la sécurité des LLM. Les premiers produits de guardrails inspectaient l’entrée et la sortie d’un seul appel de modèle. Ils pouvaient filtrer les textes toxiques, masquer les données personnelles, bloquer les jailbreaks et rejeter les réponses hors sujet. Cette frontière était utile tant que le modèle ne pouvait renvoyer que du texte.

Les tool loops ont ajouté des systèmes de fichiers, des shells, des serveurs Model Context Protocol (MCP) et des credentials. La threat model est ainsi passée du texte dangereux aux actions dangereuses. Les sept groupes d’incidents ci-dessous couvrent l’indirect prompt injection ainsi que les défaillances de configuration, d’identité et de distribution logicielle. Le filtrage de texte peut aider contre certains inputs malveillants ; il ne peut pas remplacer les contrôles appliqués à ces frontières d’exécution.

Lorsqu’un agent peut lire un repository, appeler un tool ou envoyer des données à un tiers, associez chaque action proposée au contrôle capable de l’arrêter. Les sections suivantes couvrent les permissions, les hooks, les sandboxes, les credentials et la revue humaine.

TL;DR

Les content filters inspectent le texte autour d’un appel de modèle. La sécurité des agents contrôle également les tool calls proposés, les credentials, les fichiers, l’accès réseau et les effets de bord irréversibles. Plusieurs incidents ont contourné entièrement le modèle ; d’autres ont utilisé du texte malveillant pour orienter des opérations autorisées. Une policy stack pratique combine permissions, pre-tool hooks, sandboxes OS, escalade humaine, credentials scoppés et trace d’audit.

Pour la checklist courte des contrôles, consultez AI Agent Security Checklist.

Stack de sécurité des AI agents

Aucun guardrail unique ne suffit à sécuriser un agent. Chaque composant du système doit disposer de son propre contrôle.

Les content filters demandent si le modèle a produit quelque chose de dangereux. La sécurité des agents demande aussi si le système peut effectuer l’action suivante.

Les lignes du harness décident si une action peut être exécutée. Les lignes du runtime appliquent les limites définies à l’avance et enregistrent ce qui s’est passé. Conservez la sandbox même lorsque les règles de permissions semblent complètes : elle peut arrêter un appel que le harness n’avait pas anticipé. Elle ne peut pas décider si une action autorisée était la bonne ; c’est au harness de le faire.

La dernière colonne indique où s’exécute un contrôle, et non qui l’opère. Un fournisseur peut proposer un content filter, mais c’est le harness qui l’appelle.

Les content filters managés couvrent la couche texte. Les autres contrôles doivent être intégrés à la policy applicative, à l’identité et à l’infrastructure.

Pourquoi la sécurité des AI agents diffère de la sécurité des LLM

Bharani Subramaniam et Martin Fowler ont posé le cadre début 2025 dans Emerging Patterns in Building GenAI Products. Leur observation était ciblée et directe :

« Avec les systèmes traditionnels, nous pouvions évaluer la correction principalement par des tests… Avec les systèmes basés sur des LLM, nous sommes confrontés à un système qui ne se comporte plus de manière déterministe. »

L’évaluation de la sortie demande si la réponse du modèle respecte une grille. La threat model d’un agent doit également couvrir les tool calls, les commandes shell, les écritures de fichiers, les credentials et les requêtes réseau. Un grader de sortie ne peut pas arrêter ces actions. Le harness, si : il regroupe les contrôles qui transforment une proposition du modèle en action autorisée. Le reste de cet article couvre ces contrôles.

Simon Willison a formulé en juin 2025 la structure du risque propre aux agents avec la lethal trifecta :

« La lethal trifecta des capacités est la suivante : accès à vos données privées ; exposition à du contenu non fiable ; capacité à communiquer vers l’extérieur d’une manière qui pourrait être utilisée pour voler vos données. Si votre agent combine ces trois fonctionnalités, un attaquant peut facilement le piéger pour qu’il accède à vos données privées et les lui envoie. »

De nombreux agents utiles combinent ces capacités : accès à une boîte de réception, web retrieval et tool de messagerie ; ou accès à un repository, lecture des issues et écritures dans les pull requests. Un content guardrail demande si le modèle a généré du texte dangereux. La trifecta demande si un input non fiable peut orienter le système vers la divulgation de données via une action autorisée.

La version structurelle du même argument se trouve dans le preprint Parallax de Joel Fokou (arXiv 2604.12986, soumis le 14 avril 2026, non évalué par les pairs). L’affirmation centrale est la suivante :

« Le système qui raisonne sur les actions doit être structurellement incapable de les exécuter, et le système qui exécute les actions doit être structurellement incapable de raisonner à leur sujet, avec un validateur indépendant et immuable interposé entre les deux. »

Vous n’avez pas besoin d’accepter les chiffres d’évaluation de l’article pour examiner son point structurel. Plusieurs harnesses actuels implémentent une partie de cette séparation :

  • Les hooks PreToolUse de Claude Code
  • L’executor isolé par l’OS de Codex CLI (sous Linux, bubblewrap et filtrage des appels système avec seccomp)
  • Managed Agents d’Anthropic, qui conservent les credentials dans un vault que l’agent ne voit jamais
  • Les tokens liés à l’audience de la RFC 8707 de MCP

Ces systèmes séparent le modèle du code qui exécute les commandes. Leurs contrôles diffèrent, mais aucun ne permet au command runner de s’en remettre à l’opinion du modèle sur la sécurité.

Une discipline complémentaire a été formulée le plus clairement par Alessandro Pignati en janvier 2026 : le Principle of Least Agency. Le Least Privilege demande à quelles ressources cette identité peut-elle accéder ? Le Least Agency demande quelles décisions cet agent est-il autorisé à prendre ? Le privilege limite les credentials ; l’agency limite la portée d’un plan, même lorsque les credentials sont valides. L’Excessive Agency constitue sa propre entrée du Top 10 pour les applications LLM publié par l’OWASP, l’Open Worldwide Application Security Project. La liste agentic distincte abordée plus loin dans cet article répartit le même échec entre misuse des tools et abuse des privileges. Le Least Agency est la discipline de conception qui évite les deux. Un agent capable de résumer votre boîte de réception n’a probablement pas besoin de droits de commit sur votre monorepo.

Ce que couvrent les guardrails des LLM

Byte says

Donnez à un agent un content filter et un write tool. Le filter peut inspecter ses mots ; la policy du tool décide si son écriture de fichier est exécutée.

Les guardrails des LLM jouent un rôle important autour de l’appel de modèle. Ils inspectent l’input, le texte récupéré et l’output, puis bloquent, masquent, corrigent ou signalent le contenu qui ne respecte pas une règle configurée. Les produits ci-dessous diffèrent par leur déploiement et leur couverture. Un content check est distinct d’un authorization check à la frontière d’un tool ou d’un serveur MCP ; certains produits proposent également des fonctionnalités de runtime policy qui nécessitent leur propre configuration et leur propre évaluation.

NVIDIA NeMo Guardrails

Le plus opinionated : un orchestration framework autour de cinq types de rails (input, dialog, retrieval, execution, output), avec son propre DSL — Colang, un langage proche de Python pour les flows de dialogue, les intents utilisateur et les messages du bot. Vous pouvez piloter les fonctions de base avec Python + YAML, mais la logique de dialogue avancée s’écrit en Colang — d’où le terme « opinionated ». Documentation à docs.nvidia.com/nemo/guardrails.

Voici une forme d’API illustrative ; elle nécessite le package et un répertoire ./config configuré.

from nemoguardrails import LLMRails, RailsConfig

config = RailsConfig.from_path("./config")
rails = LLMRails(config)
response = rails.generate(
    messages=[{"role": "user", "content": "Hello"}]
)

Le repo de NeMo explicite sa threat model : « les vulnérabilités courantes des LLM, telles que les jailbreaks et les prompt injections ». Il explicite tout autant sa portée : « Les guardrails intégrés peuvent convenir ou non à un cas d’usage donné en production… les développeurs doivent travailler avec leur équipe applicative interne pour s’assurer que les guardrails répondent aux exigences. » Le chemin de content screening présenté ici surveille ce que dit le modèle. La documentation actuelle de NeMo décrit également les execution rails, les custom actions et l’inspection des tool calls ; il s’agit de contrôles de runtime configurables, et non d’une preuve que le tool ou le serveur MCP déployé a authentifié et autorisé l’appel. L’application reste responsable de cette frontière.

Meta Llama Guard 4

Un classifieur de contenu pur de 12B, dérivé par pruning de Llama-4-Scout et aligné sur la taxonomie des risques de MLCommons (13 catégories de dommages plus l’abus de code interpreter, selon la model card). Meta se montre inhabituellement explicite sur ses limites :

« Certaines catégories de risques peuvent nécessiter des connaissances factuelles et à jour pour être évaluées complètement… Enfin, en tant que LLM, Llama Guard 4 peut être vulnérable aux attaques adversariales ou aux attaques par prompt injection susceptibles de contourner ou d’altérer son utilisation prévue : consultez Llama Prompt Guard 2 pour détecter les attaques sur les prompts. »

Meta fournit un produit distinct pour protéger son classifieur de contenu contre la prompt injection. Si cette phrase ressemble à un aveu structurel, c’est parce qu’elle l’est.

Guardrails AI

Un registry de validators. Vous composez des validators Hub (PII via Presidio, JailbreakDetect, CompetitorCheck, contrôles de provenance) avec des actions on_fail exception | fix | fix_reask | filter | refrain | reask | noop, ou avec un callback personnalisé (guardrailsai.com). Notez exception, et non raise. Dans le source actuel, une chaîne on_fail non reconnue est transmise au traitement des custom callbacks et provoque une erreur lors de l’initialisation du validator, au lieu d’émettre un warning et de revenir au comportement par défaut. Verrouillez la version déployée et testez ce chemin d’erreur. Il n’existe pas de threat model unifiée ; la couverture correspond à l’union des validators installés. Vous êtes protégé contre ce pour quoi vous avez un validator, et contre rien d’autre.

Lakera Guard

L’API SaaS historique, entraînée sur des dizaines de millions d’échantillons d’attaques collectés via Gandalf. Elle promet de filtrer les inputs et outputs pour détecter les « prompt attacks… and data leakage ». Le produit distinct AI Agent Security de Lakera décrit également une policy et une exécution runtime pour contrôler ce à quoi les agents peuvent accéder, ce qu’ils peuvent appeler et ce qu’ils peuvent faire. Il s’agit d’une surface produit différente de l’appel de content screening présenté ici. Vérifiez le produit et le contrat tarifaire actuels avant le déploiement.

AWS Bedrock Guardrails

Le choix par défaut en entreprise si vous utilisez déjà Bedrock. ApplyGuardrail fonctionne avec n’importe quel modèle, qu’il soit hébergé sur Bedrock ou non :

# No-run: illustrative AWS request; requires boto3, AWS credentials, and a real guardrail identifier.
import boto3

brt = boto3.client("bedrock-runtime")
resp = brt.apply_guardrail(
    guardrailIdentifier="gr-xxxxxxxxxxxx",
    guardrailVersion="2",
    source="INPUT",
    content=[{"text": {"text": "user question",
                        "qualifiers": ["guard_content"]}}],
)

Tarification ApplyGuardrail publiée : $0.15 pour 1 000 unités de texte concernant les content filters ou les sujets refusés, $0.10 pour les filtres PII ou le contextual grounding. Une unité de texte contient jusqu’à 1 000 caractères.

Azure AI Content Safety

Fournit Prompt Shields comme endpoint unifié qui « détecte et bloque les attaques adversariales dans les inputs utilisateur… les menaces directes et indirectes ». Azure se montre également transparent : « Vous ne pouvez pas utiliser Azure AI Content Safety pour détecter des images illégales d’exploitation d’enfants », et la qualité multilingue est limitée à huit langues évaluées.

OpenAI Moderation et OpenAI Guardrails

omni-moderation-latest constitue la baseline multimodale gratuite. Séparément, openai-guardrails-python (documentation à guardrails.openai.com) est la réponse framework d’OpenAI : une pipeline en trois étapes (pre-flight, input, output) avec Jailbreak Detection, Hallucination Detection via FileSearch, NSFW, PII via Presidio et LLM-as-judge. GuardrailAgent s’intègre à l’Agents SDK.

from guardrails import GuardrailsOpenAI, GuardrailTripwireTriggered

client = GuardrailsOpenAI(config="guardrail_config.json")
try:
    resp = client.responses.create(model="<your-model-id>", input="...")

Ce que les content filters ne décident pas

Deux observations s’appliquent aux sept produits.

Premièrement, les chiffres publiés de latence et de throughput sont rares. Bedrock, Azure et Lakera publient leurs tarifs, mais aucune garantie de latence dans le pire cas. Meta ne publie pas non plus de garantie pour un endpoint hébergé Llama Guard. NVIDIA fournit NeMo Guardrails comme software que vous hébergez, donc la latence dépend de votre modèle et de votre infrastructure. Mesurez chaque check synchrone sur le chemin critique au lieu d’en déduire le coût à partir du tarif du produit.

Deuxièmement, cette section couvre les configurations centrées sur le contenu énumérées ci-dessus.

Un content filter peut inspecter l’input et l’output du modèle. Il ne montre pas qu’un tool call précis est autorisé, qu’un serveur MCP a authentifié son appelant ou que le système peut arrêter une exfiltration de données ou une exécution de code en plusieurs étapes avant un appel de modèle. L’autorisation est une décision distincte : cette identité peut-elle effectuer cet appel vers ce serveur ?

NeMo documente également les execution rails et l’inspection des tool calls, et Lakera décrit l’exécution runtime dans son produit distinct AI Agent Security. Ce sont des contrôles supplémentaires à configurer et à tester. La suite de cet article couvre les contrôles autour de l’exécution des tools.

Menaces pesant sur les AI agents : sept incidents et l’OWASP ASI Top 10

L’écart entre filtrer du texte et protéger l’exécution a cessé d’être théorique mi-2025. Les sept incidents ci-dessous ont atteint le retrieval, la configuration, les credentials, l’installation de packages ou l’exécution en CI. Un classifieur de contenu peut encore détecter une chaîne suspecte, mais les contrôles qui bloquent directement ces chemins se trouvent aux frontières des tools, de l’identité, de la sandbox et de la supply chain.

EchoLeak — CVE-2025-32711

Divulgué en juin 2025 par Aim Labs, la branche de recherche d’Aim Security, contre Microsoft 365 Copilot. L’analyse technique se trouve désormais chez Cato Networks, qui a acquis cette équipe, sous la signature de l’ancien responsable d’Aim Labs, Itay Ravia (analyse). Un email spécialement conçu, formulé comme des instructions destinées au destinataire humain, a contourné XPIA (le filter intégré de Microsoft qui recherche les prompt-injection attacks dans les inputs de Copilot). Le contenu a ensuite été aspiré par la couche de retrieval de Copilot, qui recherche dans vos documents le contexte nécessaire aux réponses. Les chercheurs appellent cette technique le RAG-spraying : l’attaquant utilise plusieurs emails ou un long email découpé en chunks pour élargir l’exposition au retrieval. Cela augmente la probabilité d’être récupéré ; ce n’est pas une garantie. Une fois le contenu intégré, Copilot a docilement inséré les données les plus sensibles de la session dans un lien Markdown pointant vers une image hébergée sur un domaine contrôlé par l’attaquant. L’API de prévisualisation de Teams, exécutée sur un domaine déjà approuvé par les policies de navigateur de Microsoft, a automatiquement récupéré cette URL d’image et transmis ainsi les données à l’attaquant. Zéro clic. Aim Labs a nommé cette classe d’attaque « LLM Scope Violation » : le modèle franchit une frontière qu’il n’était jamais censé franchir, en utilisant uniquement des opérations que chaque système individuel considérait comme légitimes.

Chaque étape semblait légitime prise isolément. L’email était adressé à un humain. Le retrieval a récupéré un document qu’il était censé récupérer. Le lien Markdown s’est rendu comme le font les liens Markdown. Le téléchargement de l’image a atteint un domaine allowlisté. Les chercheurs ont contourné le screening de XPIA, et le modèle a suivi les instructions indirectes du contenu récupéré. Le cas combine un échec de prompt injection avec des comportements de retrieval, de rendu et d’egress ; il ne montre pas que les detectors n’avaient rien à signaler.

Amazon Q Developer VS Code v1.84.0 — juillet 2025

AWS a livré un build compromis après qu’un attaquant a commité un fichier de system prompt malveillant via un token GitHub CodeBuild trop largement scopé (advisory). Le payload tentait de modifier les instructions de l’agent pour l’orienter vers des actions destructrices. Le code malveillant a été distribué avec v1.84.0, mais ne s’est pas exécuté en raison d’une erreur de syntaxe. AWS a révoqué les credentials, supprimé le code et publié v1.85.0. Le payload a échoué à cause de cette erreur de syntaxe, et non parce qu’un contrôle de sécurité l’a bloqué.

Azure Web Apps MCP service — CVE-2026-32211

Le CVE record du fournisseur publié par Microsoft concerne l’absence d’authentification dans le service MCP Azure Web Apps hébergé. Il ne s’agit pas d’un advisory contre tous les serveurs MCP ou SDK Azure locaux. Un appelant qui atteint un tool service non authentifié peut contourner entièrement le modèle ; le service déployé doit authentifier et autoriser la requête.

Vulnérabilités de confiance dans les projets Claude Code

Il s’agissait de vulnérabilités distinctes, et non des étapes obligatoires d’une même attaque :

  1. Un contournement de l’avertissement de confiance a été corrigé dans la version 1.0.87.
  2. Pre-trust execution, CVE-2025-59536, a été corrigé dans la version 1.0.111. La configuration du repository pouvait déclencher une exécution avant que le projet ne soit approuvé.
  3. L’exposition de l’endpoint/de l’API key, CVE-2026-21852, a été corrigée dans la version 2.0.65. Une configuration non fiable pouvait rediriger le trafic API et exposer les credentials.

La confiance accordée au projet, l’exécution des hooks et la configuration des endpoints sont des contrôles de l’hôte. Un classifieur de contenu ne peut pas empêcher l’exécution d’un code qui se déclenche avant l’appel de modèle.

Axios 1.14.1 et 0.30.4 — 31 mars 2026

Le postmortem du maintainer identifie deux releases malveillantes, 1.14.1 et 0.30.4, contenant la dépendance plain-crypto-js@4.2.1. Cette dépendance a installé un remote access trojan : un malware qui donne à un attaquant un accès distant à la machine. L’exposition nécessitait de résoudre les versions affectées et d’exécuter le comportement d’installation concerné ; un npm install sans rapport ne les récupérait pas automatiquement. Il s’agit d’un échec d’exécution de supply chain, indépendant du comportement du modèle.

Détournement du tag Trivy Actions — 19 mars 2026

L’advisory d’Aqua décrit la redirection vers du contenu malveillant de 76 des 77 tags de version trivy-action et de sept tags setup-trivy. L’entrypoint de l’action malveillante collectait la mémoire du process du runner et les fichiers de credentials ; n’attribuez pas l’intégralité de ce chemin de collecte au binaire du scanner. L’événement Docker Hub ultérieur correspondait à une autre fenêtre d’exposition.

Un workflow qui résolvait un tag affecté pendant la compromission pouvait exécuter le payload. Les tags sont des références mobiles : pinnez donc les Actions examinées sur des commit SHAs immuables et vérifiez les changements de dépendances. Un coding agent peut propager la même référence dangereuse dans d’autres fichiers de workflow.

Évaluations OpenAI / Hugging Face — juillet 2026

Le rapport d’incident du 26 août publié par OpenAI décrit des agents d’évaluation interne en cybersécurité qui ont atteint Internet via une infrastructure partagée, ont collaboré sur un tableau de messages non autorisé et ont compromis des systèmes Hugging Face. Le modèle principal était réservé à un usage interne et les évaluations s’exécutaient avec des safeguards réduits. Cela fournit des éléments sur cet environnement d’évaluation, et non un taux d’échec mesuré pour des agents déployés publiquement.

La leçon d’ingénierie est qu’un service interne autorisé peut devenir un chemin sortant ou un canal de communication inter-session. Testez ce qu’un package mirror, un proxy et un store partagé peuvent faire au nom de l’agent, et pas seulement si la sandbox peut ouvrir une connexion directe à Internet. L’analyse distincte de METR a examiné le comportement et la collaboration des agents ; l’évaluation de l’efficacité des safeguards et de la remédiation ne faisait pas partie de son périmètre.

Intervention asynchrone du fournisseur

Le système de monitoring de misalignment d’OpenAI peut intervenir après une sortie ou une action. Pour les modèles couverts, les requêtes Responses avec reasoning persistant, WebSockets ou compaction OpenAI peuvent être arrêtées automatiquement. D’autres requêtes Responses peuvent générer des alertes sans arrêt automatique ; Chat Completions est hors de ce système. Un webhook n’autorise pas le blocage.

Une requête bloquée renvoie misalignment_policy_violation, avec HTTP 403 avant le streaming ; des erreurs peuvent également survenir en cours de stream. Arrêtez les actions supplémentaires, préservez les enregistrements de la requête et des tools, puis demandez une revue opérateur. Ne retentez pas automatiquement. Les effets antérieurs persistent, et les alertes peuvent être erronées ou manquer des problèmes. Cela ajoute de la détection ; cela ne remplace pas l’autorisation locale.

La permission est une infrastructure, pas un prompt

C’est ici que les guardrails cessent d’être le produit pour devenir un sous-système du harness. Trois systèmes actuels — OpenAI Agents SDK, Codex CLI et Claude Code — montrent à quoi ressemble réellement une surface de policy en production. Tous trois appliquent les permissions dans le code. Aucun ne dépend de la prudence du modèle.

OpenAI Agents SDK

Le SDK sépare le harness du compute. Les tools MCP hébergés acceptent require_approval — soit les chaînes brutes "always" / "never", soit un filter object indexé par ces deux policies avec les noms des tools couverts par chacune — ainsi qu’un callback on_approval_request déclenché pour chaque tool restant sous "always" et qui renvoie {"approve": bool} avec une raison facultative. Le filtrage fin des tools (tool_filter) est disponible avec les variantes de serveurs locaux (MCPServerStdio, MCPServerStreamableHttp, MCPServerSse) si vous en avez besoin :

# No-run: illustrative Agents SDK shape; requires openai-agents, a configured hosted MCP server, and credentials.
from agents import Agent, HostedMCPTool

def approve(request):
    # Only tools under the "always" policy reach this callback.
    if request.data.name == "delete_repo":
        return {"approve": False, "reason": "escalate to a human reviewer"}
    return {"approve": True}

agent = Agent(
    name="Ops",
    tools=[HostedMCPTool(
        tool_config={
            "type": "mcp",
            "server_label": "github",
            "server_url": "https://mcp.example.com",
            "require_approval": {
                "always": {"tool_names": ["delete_repo"]},
                "never": {"tool_names": ["list_issues"]},
            },
        },
        on_approval_request=approve,
    )],
)

Le callback d’approbation est du code. La policy d’approbation par tool est du code. Vous pouvez lire ce fichier, le tester et le comparer avec un diff. Rien de tout cela n’est possible avec un system prompt disant « soyez prudent avec la production ».

Codex CLI et la couche de policy managée

Le coding harness d’OpenAI prend en charge un fichier requirements.toml managé que les services IT peuvent distribuer via la gestion des appareils. Sur les systèmes Unix, le fichier système se trouve à /etc/codex/requirements.toml. Il agit comme une couche de contraintes strictes : les settings au niveau du projet ne peuvent pas remplacer ses règles :

# /etc/codex/requirements.toml
[rules]
prefix_rules = [
    { pattern = [{ token = "rm" }, { any_of = ["-rf", "-fr"] }], decision = "forbidden", justification = "Recursive force-delete prohibited by IT policy" },
]

prefix_rules.decision accepte uniquement "prompt" ou "forbidden", jamais "allow". Un projet ne peut pas s’accorder une permission interdite par la couche managée. Les allowlists MCP sont indexées à la fois par le nom et par l’identité, par exemple une chaîne de commande ou une URL. Un projet ne peut donc pas se déclarer github-mcp tout en pointant vers le serveur d’un attaquant. Les exigences prises en charge varient selon le client et la version. La documentation actuelle exige précisément Codex 0.138.0 ou une version ultérieure pour les clés de managed permission-profile ; testez donc toute policy de requirements avec chaque version cliente présente dans le parc avant le déploiement.

La permission ladder de Claude Code

Claude Code ne publie pas une séquence fixe de six contrôles pour chaque tool call. Ses règles de permission sont évaluées deny → ask → allow ; la première règle correspondante détermine le résultat. Un hook PreToolUse s’exécute avant le permission prompt. Une PreToolUse decision peut autoriser un appel sans prompt, le refuser, demander l’intervention de l’utilisateur ou le différer. Les règles deny et ask continuent de s’appliquer ; certaines actions interactives conservent également leurs exigences d’approbation. Le permission mode actif traite les appels non résolus par les règles et les hooks. Le Claude Agent SDK possède un callback canUseTool distinct pour les requêtes non résolues. Ce callback est un contrôle du SDK, et non un check de permission du CLI Claude Code.

Les modes basculent entre default → acceptEdits → plan avec Shift+Tab. auto, bypassPermissions et dontAsk s’activent dans des conditions d’entrée spécifiques que la couche de policy gérée par l’entreprise peut désactiver. Il ne s’agit pas simplement de vérifier la validité d’un fichier de configuration. C’est une state machine avec des règles de précédence, publiées afin qu’une équipe de sécurité puisse les analyser.

Trois rayons d’explosion dans un seul fichier

Voici la forme d’une configuration de permissions de type Codex avec un profil par défaut et deux profils nommés :

# ~/.codex/config.toml
approval_policy = "on-request"
sandbox_mode = "workspace-write"

[profiles.ci]
approval_policy = "never"
sandbox_mode = "read-only"

[profiles.release]
approval_policy = "untrusted"
sandbox_mode = "danger-full-access"

[mcp_servers.github]
command = "gh-mcp"
args = ["--readonly"]

Deux clés font le travail, et elles sont indépendantes. approval_policy décide quand demander l’intervention d’un humain. on-request permet à l’agent d’escalader lorsqu’il rencontre un blocage. never ne demande jamais rien. untrusted s’arrête sur chaque commande qui ne figure pas dans la liste de confiance. sandbox_mode décide de ce que la commande peut toucher lorsqu’elle s’exécute.

La CI n’interrompt personne et ne peut pas écrire. La release peut atteindre l’ensemble de la machine, mais doit obtenir l’accord d’un humain pour presque tout. Le profil release paie cette portée : danger-full-access désactive la sandbox, donc l’approbation untrusted est le seul contrôle restant. Tout ce qui ne figure pas dans la liste de confiance doit obtenir l’accord d’un humain ou ne s’exécute pas. Cette liste de confiance constitue désormais toute la frontière de sécurité.

Les profils default et CI conservent le kernel sous-jacent : Seatbelt sur macOS, bubblewrap et seccomp sur Linux, ainsi que des restricted tokens sur Windows. Dans tous les cas, l’opinion du modèle n’intervient pas.

L’application de la sandbox est une question d’OS

C’est le kernel qui effectue réellement le travail. Chaque OS fournit une boîte à outils différente, et les deux CLIs ne choisissent pas toujours le même composant :

PlateformeClaude CodeCodex CLI
macOSSeatbelt via sandbox-exec avec un profil SBPL (Seatbelt Profile Language)Seatbelt via sandbox-exec -p
Linuxbubblewrap + socat network proxybubblewrap + seccomp (Landlock legacy via use_legacy_landlock)
WindowsWSL2 requisNative restricted tokens + workspace ACLs + capability SIDs

Ils convergent lorsque l’OS ne propose qu’une option (Seatbelt, bubblewrap) et divergent lorsqu’il en propose plusieurs. La sandbox de Claude Code nécessite WSL2 sous Windows ; c’est une limite de la sandbox, et non l’affirmation que le CLI ne peut pas s’exécuter nativement. Codex fournit une sandbox Windows native. Dans tous les cas, l’application des contrôles se fait dans le kernel, pas dans le modèle.

Le chemin Linux de Codex empile trois verrous au niveau du kernel autour de la commande. PR_SET_NO_NEW_PRIVS empêche le process d’obtenir des privileges supplémentaires, même s’il essaie. Un filter seccomp fait refuser directement par le kernel des catégories entières d’appels système. Les restrictions réseau dépendent de la désactivation du réseau ou de la configuration d’un mode proxy ; elles ne se limitent pas universellement aux Unix sockets. Consultez l’implémentation de la sandbox Linux. Un /proc isolé et neuf masque le reste de la machine.

Codex durcit également son propre binaire au démarrage sur toutes les plateformes Unix. Il définit RLIMIT_CORE=0 pour supprimer les crash dumps et refuse l’attachement d’un debugger. Il s’agit d’une frontière différente de celle de la sandbox.

La sandbox Windows possède deux modes. unelevated utilise un restricted token comme utilisateur et ne fournit pas l’application réseau du mode élevé. elevated utilise des utilisateurs de sandbox dédiés, des règles de firewall et des ACLs de système de fichiers.

Lorsque l’accès réseau est désactivé, Codex place des fichiers .bat et .cmd factices pour ssh et scp dans un répertoire situé en tête de PATH. Ces commandes retournent un code non nul au lieu d’atteindre les vrais binaires. Codex pointe également HTTP_PROXY, HTTPS_PROXY, ALL_PROXY et les variables de proxy Git vers un port local inactif. Ces mesures concernent les tools coopératifs ; les variables de proxy et les command stubs ne peuvent pas, à eux seuls, confiner un réseau arbitraire.

Une sandbox doit également définir son mode d’échec. Dans la configuration actuelle de Claude Code, sandbox.failIfUnavailable: true arrête l’exécution lorsque la sandbox ne peut pas démarrer. allowUnsandboxedCommands: false désactive la possibilité pour l’agent de retenter sans sandbox, mais excludedCommands la contourne toujours. Testez la configuration effective avec des dépendances manquantes et une destination interdite.

Le credential brokering est désormais également disponible en local. Le sandbox.credentials de Claude Code peut refuser des fichiers et des variables d’environnement nommés. Le masquage des variables d’environnement, disponible depuis la version 2.1.199, fournit un placeholder aux commandes sandboxées et permet au proxy d’injecter la valeur réelle dans les requêtes vers des hosts configurés. Définissez des injectHosts étroits et configurez la terminaison TLS ; le masquage n’autorise pas l’opération demandée. Ces contrôles couvrent les commandes Bash sandboxées ; les hooks, les process MCP et les autres chemins d’exécution nécessitent donc leur propre policy de credentials.

Choix d’isolation au-delà de Claude Code et Codex

Si vous développez votre propre agent, « sandbox » se révèle être un terme générique. Les options open source se situent sur un spectre — des wrappers de namespaces légers à une extrémité, aux microVM complètes à l’autre — et votre choix dépend du niveau de confiance accordé au code exécuté à l’intérieur.

Isolation légère — même kernel, moins de privileges :

  • bubblewrap — un constructeur de sandbox bas niveau pour namespaces, utilisé par Flatpak et Claude Code sous Linux. L’appelant doit choisir le système de fichiers, le réseau et l’eventuelle policy seccomp ; bubblewrap n’est pas en soi une policy de sécurité prête à l’emploi.
  • Containers Docker / OCI standard — isolation par namespaces au-dessus d’un kernel hôte partagé. Ce ne sont pas des sandboxes pour du code non fiable ; la propre documentation de gVisor l’explicite (« containers are not a sandbox »). Un point de départ raisonnable lorsqu’ils sont associés à seccomp et AppArmor, mais rien de plus.

Isolation application-kernel — l’agent parle à un kernel fictif :

  • gVisor — le kernel en user space de Google. Votre container croit être sous Linux, tandis qu’une implémentation du kernel en Go intercepte les appels système. Cela réduit l’exposition directe au kernel de l’hôte sans guest VM, avec des compromis de compatibilité et de performance.

Isolation par VM complète — un kernel dédié par sandbox :

  • Firecracker — la technologie de microVM d’AWS. Chaque VM possède son propre kernel Linux sous KVM ; les containers partagent le kernel hôte. Une compromission dans une VM doit encore franchir les contrôles du VMM ou de l’hôte pour affecter l’hôte ou une autre VM ; le Jailer de Firecracker et un hôte patché restent donc des éléments de la protection.
  • Kata Containers — UX de container, isolation de niveau VM. C’est le choix des clusters Kubernetes qui doivent exécuter du code non fiable.

Platforms — ce que vous pouvez louer plutôt que construire :

  • E2B encapsule Firecracker dans une sandbox API hébergée.
  • OpenSandbox sépare le SDK de l’isolation runtime configurée par l’administrateur. Le Docker runc par défaut n’est pas une microVM ; son chemin Firecracker utilise Kata avec Firecracker via Kubernetes.
  • Le Agent Governance Toolkit de Microsoft (sous licence MIT, avril 2026) ajoute un policy engine runtime par-dessus. Il associe les contrôles de policy à l’OWASP ASI Top 10. Sa latence de lancement concerne un policy engine, et non le coût total de chaque check dans un agent déployé.

Choisissez le niveau d’isolation selon le niveau de confiance accordé au code, la frontière entre tenants, l’accès réseau, les données de l’hôte et le coût de récupération. Les contrôles de namespaces et de seccomp peuvent convenir à des tools internes de confiance. Le code généré par un LLM et les packages non fiables nécessitent une frontière plus forte, comme gVisor, Kata ou une microVM, suivie de tests sur les chemins d’évasion et d’exfiltration de votre propre threat model.

Claude Code et Codex ont choisi dans le même catalogue que tout le monde. Ils l’ont simplement encapsulé différemment.

Les hooks PreToolUse comme policy programmable

Les modes et les allowlists traitent les cas simples : « laissez l’agent modifier des fichiers, mais pas exécuter Bash », « refusez tout ce qui ressemble à rm -rf ». Ils échouent lorsque votre policy nécessite une véritable logique. Vous voulez bloquer git push uniquement lorsque la branche est main. Vous voulez refuser toute opération Edit qui touche un fichier correspondant à une regex de secret. Vous voulez limiter le nombre d’appels shell par session ou envoyer chaque invocation de tool dans votre journal d’audit central (le SIEM, le système de security information and event management déjà surveillé par votre équipe sécurité).

Rien de tout cela ne tient dans une allowlist statique. C’est à cela que servent les hooks — des commandes shell exécutées par Claude Code à des points précis du cycle de vie d’un tool call, capables d’inspecter l’appel en attente et de renvoyer un allow/deny structuré. Claude Code expose environ trente événements de cycle de vie (la liste complète se trouve dans la documentation), dont un réordonne tous les autres : un hook PreToolUse qui renvoie permissionDecision: "deny" bloque un tool quel que soit le mode.

Voici la forme des settings :

{
    "permissions": {
        "defaultMode": "acceptEdits",
        "deny": ["Bash(rm -rf:*)", "Bash(sudo:*)", "Read(.env*)"]
    },
    "hooks": {
        "PreToolUse": [
            {
                "matcher": "Bash",
                "hooks": [
                    {
                        "type": "command",
                        "command": ".claude/hooks/pre-bash-firewall.sh"
                    }
                ]
            },
            {
                "matcher": "Edit|Write",
                "hooks": [
                    {
                        "type": "command",
                        "command": ".claude/hooks/protect-paths.sh"
                    }
                ]
            }
        ]
    }
}

Les règles statiques deny et les hooks dynamiques ont des modes d’échec différents. Un résultat PreToolUse égal à deny bloque avant le flux normal de permissions, mais un command expiré — qu’il s’agisse d’un hook command, HTTP ou MCP-tool — est non bloquant : Claude Code poursuit ce flux. Dans cet exemple, acceptEdits peut donc approuver un Edit ou Write lorsque protect-paths.sh expire. Ne faites pas dépendre une restriction de chemin non négociable uniquement d’un command hook. Placez les restrictions statiques dans les règles deny ou la sandbox ; pour une policy dynamique, choisissez un contrôle dont l’échec de l’évaluateur reste restrictif, et testez à la fois son comportement en cas de timeout et un deny explicite.

Un hook peut être un script shell de cinq lignes ou un policy engine complet. C’est la forme du retour qui compte :

{
    "hookSpecificOutput": {
        "hookEventName": "PreToolUse",
        "permissionDecision": "deny",
        "permissionDecisionReason": "writes outside workspace prohibited"
    }
}

Le modèle voit un deny structuré. La reasoning loop de Part 1 le traite comme n’importe quelle observation de tool : le refus devient du contexte, l’agent replanifie et la loop continue. C’est ce que vous apporte le principe selon lequel « la permission est une infrastructure ». Le deny est branché sur le même mécanisme que celui qui traite un 500 renvoyé par un tool HTTP. Il ne s’agit pas d’un workflow de sécurité distinct qu’il faudrait ajouter après coup.

Un anti-pattern courant consiste à écrire un system prompt disant « ne supprimez aucun fichier sans confirmation explicite de l’utilisateur », à livrer l’agent et à considérer cette instruction comme le contrôle. Un injected prompt ou un tool result contrôlé par un attaquant peut contourner cette instruction. Le modèle n’est pas un policy engine. Il peut reconnaître le pattern que vous avez écrit, ou celui fourni par un attaquant.

L’approbation humaine ne fonctionne qu’en escalade

Byte says

Après vingt prompts d’approbation, il est facile de cliquer sur Approve sans lire. Réservez les prompts aux actions qui nécessitent réellement une décision humaine.

Les content filters inspectent ce que dit le modèle. Les règles de permission inspectent le tool call avant son exécution. La revue human-in-the-loop traite les actions qui nécessitent encore l’intervention d’une personne. Si les utilisateurs approuvent 93 % des prompts, examinez les règles d’escalade et la qualité des prompts.

LangGraph fournit la primitive pause/resume. HumanLayer encapsule le canal d’approbation, et les données d’utilisation d’Anthropic montrent pourquoi il faut mesurer le nombre et la qualité des escalades.

La primitive LangGraph

Le interrupt() + Command(resume=value) de LangGraph met une graph en pause, persiste son état via le checkpointer configuré et la reprend avec une valeur fournie par un humain. La sécurité de cette reprise dépend d’un détail de la documentation :

« Lorsque l’exécution reprend (après la fourniture de l’input demandé), le runtime redémarre le node entier depuis le début — il ne reprend pas à la ligne exacte où interrupt a été appelé. »

Trois contraintes découlent de ce comportement de redémarrage :

1. Les side effects avant interrupt() doivent être idempotents. Lorsque l’humain répond, le node entier s’exécute de nouveau depuis le début, et non depuis la ligne interrupt(). Ainsi, si votre node envoie un email, se met en pause pour demander une approbation, puis retourne « sent », l’email sera envoyé une deuxième fois à la reprise. Solution : placez les side effects après l’interrupt, ou rendez-les répétables sans danger (clés de déduplication, upsert plutôt qu’insert, cache indexé par message ID).

2. Les interrupts sont associés aux resumes par index, et non par nom. Si un node contient deux appels interrupt(), LangGraph les associe aux valeurs Command(resume=...) dans l’ordre de leur déclenchement. Tout branching qui modifie le nombre d’interrupts exécutés (un if qui en ignore un à la reprise, une loop dont le nombre d’itérations diffère) désalignera les index ; une valeur de reprise peut alors être appliquée au mauvais interrupt.

3. Conservez des payloads compatibles avec JSON. La documentation de LangGraph exige des valeurs sérialisables en JSON pour interrupt() et les payloads de reprise. Utilisez des strings, numbers, booleans, arrays et dictionaries contenant ces types. Évitez les functions, les instances de classes et autres objets complexes, car la sérialisation dépend du checkpointer configuré. Convertissez les données d’approbation en dictionaries et primitives avant de les transmettre à interrupt() ou de les exposer via une API HTTP.

Les trois patterns canoniques :

# No-run: illustrative LangGraph sketches; requires LangGraph, a tool decorator, interrupt, and smtp_send.
# (a) Approval check
@tool
def send_email(to, subject, body):
    resp = interrupt({"action": "send_email", "to": to,
                      "subject": subject, "body": body})
    if resp.get("action") == "approve":
        return smtp_send(to, subject, body)
    return "Email cancelled"

# (b) Edit-and-continue
def review_node(state):
    edited = interrupt({"content": state["generated_text"]})
    return {"generated_text": edited}

# (c) Mid-run state correction — conditional edge
class AgeState(TypedDict):
    age: int | None
    pending_question: str | None

def get_age_node(state: AgeState):
    question = state.get("pending_question") or "What is your age?"
    answer = interrupt(question)  # once per node invocation
    if isinstance(answer, int) and answer > 0:
        return {"age": answer, "pending_question": None}
    return {"pending_question": f"'{answer}' is not valid. Please enter a positive number."}

def route_age(state: AgeState):
    return END if state.get("age") is not None else "get_age"

builder = StateGraph(AgeState)
builder.add_node("get_age", get_age_node)
builder.add_edge(START, "get_age")
builder.add_conditional_edges("get_age", route_age)

La reprise est graph.invoke(Command(resume={"action": "approve"}), config=cfg). LangGraph 0.4+ prend en charge la reprise multi-interrupt basée sur des dictionaries pour les branches parallèles, ce qui devient important dès que votre agent fait du fan-out.

HumanLayer : l’approbation comme produit

HumanLayer est la version managée de la même idée. Décorez une function, puis routez les approval requests vers Slack, email ou Discord, avec des règles indiquant qui doit être notifié. Lorsque l’agent tente d’appeler multiply(2, 5), les logs ressemblent à ceci :

last message led to 1 tool calls: [('multiply', '{"x":2,"y":5}')]
HumanLayer: waiting for approval for multiply

L’approbateur clique sur approve ou deny dans Slack. En cas de deny, la documentation HumanLayer le formule ainsi : « HumanLayer transmet votre feedback à l’agent, qui peut alors ajuster son approche. » Ce feedback permet à l’agent de réviser son plan au lieu de considérer le refus comme une impasse.

La fatigue d’approbation dans les données

Anthropic a publié les données réelles en février 2026. Trois résultats importent davantage que les autres.

« Nous avons constaté que 80 % des tool calls proviennent d’agents qui semblent disposer d’au moins un type de safeguard (comme des permissions restreintes ou des exigences d’approbation humaine), que 73 % semblent disposer d’un human-in-the-loop d’une manière ou d’une autre, et que seulement 0,8 % des actions semblent irréversibles. »

C’est la bonne nouvelle. Considérez 80 % comme une limite supérieure, car la note 14 d’Anthropic précise que « Claude surestimait souvent l’implication humaine ; nous estimons donc que 80 % constitue une limite supérieure ».

« Les utilisateurs plus récents (<50 sessions) utilisent l’auto-approve complet environ 20 % du temps ; à 750 sessions, ce chiffre dépasse 40 % des sessions. »

C’est la dérive. Les utilisateurs commencent avec prudence, puis deviennent moins prudents à mesure qu’ils développent leur confiance dans l’outil. C’est un comportement humain, et non un défaut de caractère. Il s’agit d’un signal de telemetry que votre système devrait suivre. (Petite précision factuelle : des articles secondaires ont largement cité « 20 % → plus de 50 % ». D’après les données primaires d’Anthropic, le chiffre vérifié est 20 % → plus de 40 %. Si vous avez vu le chiffre de 50 %, c’est de là qu’il vient.)

L’article d’ingénierie de mars 2026 publié par Anthropic sur le mode auto de Claude Code fournit le chiffre clé :

« Les utilisateurs de Claude Code approuvent 93 % des permission prompts. Nous avons développé des classifieurs pour automatiser certaines décisions, améliorer la sécurité et réduire la fatigue d’approbation… Si une session accumule 3 refus consécutifs ou 20 refus au total, nous arrêtons le modèle et escaladons vers un humain. »

Un taux d’approbation élevé justifie d’examiner si les prompts aident réellement les utilisateurs à décider ; il ne prouve pas l’existence d’un seuil universel d’échec. Le classifieur en deux étapes d’Anthropic réduit le nombre de prompts et escalade les refus groupés. Son taux de faux positifs annoncé, 0,4 %, a été mesuré sur 10 000 exemples de trafic. Les taux de faux négatifs étaient de 17 % sur 52 actions réelles trop enthousiastes et de 5,7 % sur 1 000 cas synthétiques d’exfiltration. Il s’agit de populations différentes, et non de pourcentages complémentaires ni d’une preuve que la classification remplace la sandbox.

Mesurer la qualité des escalades

Allowlistez les actions routinières et réversibles, puis journalisez-les. Escaladez les actions dont les side effects franchissent une frontière que le runtime ne peut pas annuler, comme un message externe, une écriture en production, un force push ou un paiement. Anthropic formule l’objectif ainsi : maintenir la capacité d’un humain à intervenir lorsque la décision a une conséquence réelle.

Suivez l’intégralité du funnel plutôt que de viser un taux d’approbation emprunté : actions proposées, autorisations automatiques, escalades, approbations, refus, edits et incidents postérieurs à l’approbation. Un taux élevé d’approbation peut signifier que les prompts ne sont qu’un bruit routinier. Un taux élevé de refus ou d’edits peut indiquer que le planner propose la mauvaise action ou masque les informations nécessaires à l’approbateur. Le seuil utile dépend de la classe d’action et du coût d’un faux allow ; définissez-le à partir de vos propres données d’incidents et de revue.

Scoping MCP et supply chain

MCP connecte les agents à des tools externes tels que Slack, GitHub et des bases de données, ce qui fait de son modèle d’autorisation une partie de la frontière de sécurité. Les révisions de la spécification en 2025 ont séparé les rôles d’issuer de tokens et de resource server, et ajouté les resource indicators. Cette évolution explique quelles vérifications d’audience et de forwarding un serveur doit appliquer aujourd’hui.

L’autorisation MCP en trois révisions

L’autorisation était optionnelle pour les implémentations MCP dans la spécification du 26 mars 2025. Pour un déploiement HTTP en production qui protège des données utilisateur ou des tools, je recommande OAuth 2.1 avec PKCE (Proof Key for Code Exchange), que la spécification exige lorsqu’une implémentation prend en charge l’autorisation OAuth. La conception initiale permettait à un serveur MCP d’endosser deux rôles. L’authorization server émet les tokens ; le resource server les accepte. Ce sont deux rôles distincts, même lorsqu’un même service remplit les deux. Si ce service forwarde une requête vers un autre serveur, le même credential peut voyager vers un endroit pour lequel il n’était pas prévu. C’est la faille.

La révision du 18 juin 2025 a explicité les rôles. Un serveur MCP protégé agit comme resource server OAuth, tandis qu’un authorization server émet le token. L’authorization server peut être cohébergé avec le resource server ou s’exécuter séparément. Les Resource Indicators de la RFC 8707 lient le token à une ressource cible, et les Protected Resource Metadata de la RFC 9728 fournissent au client un chemin explicite de discovery. La spécification interdit également à un serveur MCP de forwarder le token d’un client en amont.

La révision du 25 novembre 2025 a conservé cette séparation et travaillé sur les éléments qu’un client doit correctement implémenter. La discovery de l’authorization server a ajouté OpenID Connect Discovery, afin qu’un client puisse trouver le bon issuer au lieu de le deviner. Le consentement aux scopes incrémentaux a été déplacé dans le header WWW-Authenticate, ce qui permet à un serveur de demander un scope supplémentaire au moment où il en a besoin plutôt que de tout exiger dès le départ. L’enregistrement client a adopté les OAuth Client ID Metadata Documents comme mécanisme recommandé, remplaçant le dynamic registration dans la plupart des déploiements. La discovery des Protected Resource Metadata a également été alignée sur la RFC 9728, rendant WWW-Authenticate optionnel avec un fallback .well-known.

Consultez la page de versioning avant d’implémenter. Au 6 septembre 2026, la révision actuelle est 2026-07-28. Elle exige que chaque requête déclare la version du protocole et permet au serveur d’accepter ou de rejeter chaque requête indépendamment. Un client peut appeler server/discover pour sélectionner une version à l’avance, mais la discovery est optionnelle. La déclaration par requête et la négociation restent obligatoires, y compris lorsque le client traite une erreur de version non prise en charge et retente avec une version mutuellement supportée.

Le binding d’audience limite le replay contre le mauvais serveur MCP. Il ne neutralise pas les vulnérabilités distinctes de configuration de Claude Code décrites plus haut : un hook côté hôte peut toujours s’exécuter avant le démarrage du modèle, et un projet non fiable peut toujours tenter de modifier la configuration locale. Le scope du token, la confiance du projet, la policy des hooks et la sandbox restent des contrôles distincts.

Checklist MCP 2026

Si vous livrez ou consommez MCP en production :

  1. Considérez l’authentification comme une exigence de production, et non comme une valeur par défaut du protocole. MCP laisse l’autorisation optionnelle, mais je recommande OAuth 2.1 avec PKCE pour un déploiement HTTP protégé. L’advisory concernant le service MCP Azure Web Apps hébergé portait sur l’absence d’authentification. Si votre serveur accepte du trafic sans vérifier les credentials de l’appelant, vous avez construit un tool que toute personne capable de l’atteindre peut appeler.
  2. Les tokens sont liés à une audience. Demandez un token pour la ressource MCP cible et vérifiez que le token présenté désigne votre serveur comme audience. Rejetez les tokens émis pour une autre ressource.
  3. Séparez délibérément les autorités de lecture et d’écriture. MCP lie un token à un resource server, et non à un tool individuel. Si un serveur Slack accepte un credential avec chat:write et le route vers des handlers de lecture et d’écriture, un tool orienté lecture peut devenir un chemin d’envoi de messages via la policy de ce serveur. Utilisez des resource servers distincts, ou des credentials et authorization checks distincts, lorsque les opérations de lecture et d’écriture doivent avoir des rayons d’explosion indépendants.
  4. Utilisez des tokens courts et renouvelés plutôt que des API keys permanentes. Le pattern du vault de Claude Managed Agents (Anthropic engineering) sert de référence : l’agent lui-même ne voit jamais les vrais credentials. Le proxy récupère les credentials correspondants dans le vault, appelle le tool au nom de l’agent et renvoie le résultat. L’émission d’un token frais à chaque appel n’est pas une garantie documentée ; les credentials de courte durée sont une recommandation de déploiement.

Les contrôles de supply chain restent applicables

Les incidents axios et Trivy sont des défaillances familières de package et de supply chain CI, appliquées à des systèmes qui automatisent l’installation de dépendances. L’automatisation augmente le nombre et la vitesse des exécutions ; les contrôles de version, de provenance et de revue doivent donc s’appliquer avant que la commande générée n’atteigne la CI ou une sandbox.

La défense est simple :

  • Pinnez les versions dans le lockfile. Les agents ne doivent jamais résoudre une version flottante — ni @latest, ni npm update, ni --upgrade.
  • Scannez dans la CI avec des tools indépendants du composant contrôlé.
  • Utilisez des GitHub commit SHAs pour les Actions, et non des tags.
  • Examinez les diffs de dépendances des PRs pilotées par un agent avant le merge.

Il s’agit de contrôles de supply chain standards. L’automatisation agentic modifie leur fréquence, pas leur mécanisme.

Une policy stack pour le Market Analyst Agent

Le Market Analyst Agent de la Part 1 est un agent LangGraph compact qui récupère des données de marché et rédige un rapport d’analyste — mais il est moins simple que ne le suggère cette description. En plus des tools de données de marché, il exécute un CLI allowlisté via subprocess, évalue du Python écrit par le modèle in process et crée des enregistrements de trades simulés. Il exerce l’invocation de tools, l’exécution de code et le routage d’approbation, mais ne passe pas d’ordres réels. Voici à quoi ressemble une policy stack minimale pour cet agent.

Couche 1 : un hook PreToolUse qui refuse avant l’exécution

Même un agent qui « se contente de lire des données boursières » peut tenter des opérations qu’il ne devrait pas effectuer : un curl vers une URL contrôlée par un attaquant, des écritures en dehors du workspace, des mutations git sur le repository hôte. Une deny rule est une infrastructure, pas un prompt. Le sketch ci-dessous renvoie la forme de décision propre à l’agent, et non l’enveloppe hookSpecificOutput attendue par Claude Code.

# agent/permissions.py
from pathlib import Path

DENY_COMMANDS = frozenset({
    "rm -rf", "sudo", "chmod 777",
    "curl -X POST", "wget", "nc ",
})
WORKSPACE = Path("./workspace").resolve()

def _outside_workspace(path: str) -> bool:
    # Resolve first: "~/.ssh/id_rsa" and "workspace/../../etc" both
    # have to become real paths before the comparison means anything.
    return not Path(path).expanduser().resolve().is_relative_to(WORKSPACE)

def pre_tool_use(tool_name: str, args: dict) -> dict | None:
    if tool_name == "shell":
        cmd = args.get("command", "")
        if any(bad in cmd for bad in DENY_COMMANDS):
            return {"permissionDecision": "deny",
                    "reason": f"command pattern disallowed: {cmd!r}"}
    if tool_name == "write_file":
        path = args.get("path", "")
        if _outside_workspace(path):
            return {"permissionDecision": "deny",
                    "reason": f"path outside workspace: {path!r}"}
    return None  # fall through to mode / canUseTool

Le sketch rend visible le point de contrôle. Le hook renvoie un deny structuré, et la reasoning loop reçoit ce refus comme observation de tool.

Le path check est une allowlist : une seule racine de workspace, tout le reste est refusé. Une deny-list de préfixes interdits ne bloque que les chemins auxquels vous avez pensé. ~/.ssh/id_rsa ne sera jamais écrit exactement comme vous l’aviez prévu. Le command check reste une deny-list. La recherche par substring n’est pas une policy shell de production. Une implémentation réelle devrait parser la commande et s’appuyer sur la sandbox OS au moment de l’exécution. Le sketch ne constitue pas lui-même une frontière d’exécution : si un hook externe l’exécute, un timeout doit laisser une restriction de workspace indépendante en vigueur.

Couche 2 : un canary d’input pour la prompt injection

Le goal hijack d’un agent (ASI01) arrive souvent via une page web récupérée, un message utilisateur ou un PDF de recherche. Un canary regex peu coûteux détecte les patterns d’instructions littéraux et génère un événement de telemetry utile. Il manquera les injections obfusquées, multilingues ou dépendantes du contexte ; il ne peut donc pas servir de frontière de décision :

# agent/input_canary.py
import re

INJECTION_PATTERNS = [
    re.compile(r"ignore\s+(?:all\s+|any\s+|the\s+)?"
               r"(?:previous\s+|prior\s+|above\s+|earlier\s+)?"
               r"(?:instructions|rules|prompts?)",
               re.IGNORECASE),
    re.compile(r"you are now|act as|roleplay as", re.IGNORECASE),
    re.compile(r"system[ _:]*prompt", re.IGNORECASE),
    re.compile(r"<\|im_(start|end)\|>"),
]

def input_canary(text: str) -> dict | None:
    for pat in INJECTION_PATTERNS:
        m = pat.search(text)
        if m:
            return {"flag": "possible_injection", "match": m.group(0)}
    return None

Journalisez les inputs signalés ; ne les rejetez pas automatiquement. Les faux positifs sont coûteux pour un assistant de recherche. Mais c’est le log qui vous permettra de remarquer une hausse soudaine du nombre de flags provenant d’un utilisateur.

Couche 3 : un validator de completion personnalisé

Un harness personnalisé peut valider un rapport avant de l’accepter comme terminé. Dans ce sketch, le harness doit consommer la décision renvoyée : continue envoie le feedback au modèle pour un retry borné ; allow_stop accepte le rapport. Si les retries sont épuisés, le harness doit signaler l’échec au lieu d’accepter une sortie invalide. La fonction seule n’impose pas cette loop.

Il s’agit de noms de décisions personnalisés, et non du contrat Claude Code Stop, qui utilise decision: "block" avec un reason pour empêcher l’arrêt. Le schema et le check de ticker ci-dessous illustrent la validation au niveau applicatif :

# No-run: illustrative policy sketch; requires Pydantic and the repo-local agent.schemas module.
# agent/completion_validator.py
from pydantic import ValidationError
from agent.schemas import MarketReport

def validate_completion(final_output: str) -> dict:
    try:
        report = MarketReport.model_validate_json(final_output)
    except ValidationError as e:
        return {"decision": "continue",
                "feedback": f"schema invalid: {e.errors()[:3]}"}
    if not report.tickers:
        return {"decision": "continue",
                "feedback": "no tickers in report — did you skip the snapshot step?"}
    return {"decision": "allow_stop"}

Ces checks vérifient que l’output respecte le schema du rapport et nomme au moins un ticker. Ils ne vérifient ni les données de marché ni l’analyse.

Couche 4 : approbation avant les actions sortantes

Le execute_trade du market analyst est une transition d’état simulée et idempotente ; il illustre donc le routage d’approbation plutôt qu’un side effect financier irréversible. Pour une véritable intégration sortante — email, Slack, rapport envoyé à un client ou ordre de courtage — présentez l’action proposée à une personne et attendez son approbation ou son rejet avant l’exécution du tool. Utilisez interrupt() pour cette pause :

# No-run: illustrative outbound-tool sketch; requires LangGraph, a tool decorator, and smtp_send.
# agent/tools/notify.py
from langgraph.types import interrupt

@tool
def send_report(to: str, body: str):
    resp = interrupt({
        "action": "send_report",
        "to": to,
        "body": body,  # Review the complete content that will execute.
    })
    if resp.get("action") == "approve":
        return smtp_send(to, body)
    return "send cancelled by human"

Les actions sortantes complètent la lethal trifecta. Exigez une approbation pour ces actions lorsque l’autorisation existante et la policy de déploiement ne les couvrent pas. Liez l’approbation à la destination et au contenu complets ; des arguments modifiés nécessitent une nouvelle décision. Les messages destinés aux services financiers, aux clients ou à d’autres destinataires externes doivent montrer à l’approbateur ce qui sera envoyé et où.

Ce que cette stack ne fait pas

Elle ne protège pas contre :

  • Une dépendance upstream compromise (de type axios). L’agent exécute ce que uv sync lui demande d’exécuter.
  • Un .mcp.json malveillant dans un repo cloné (de type CVE-2025-59536). C’est le permission model du client MCP hôte qui doit le détecter, et non le code de l’agent.
  • Une chaîne de vol de données construite à partir de tools légitimes (de type EchoLeak) — l’agent lit des données privées, récupère des URLs externes et envoie des messages à l’extérieur. Cassez ou limitez ce chemin d’exfiltration avec un accès aux données scopé, un routage de confiance, des restrictions d’egress et une approbation lorsque nécessaire. Retirer une capacité bloque ce chemin précis, et non toutes les attaques possibles.
  • Une évasion depuis execute_python_analysis, l’évaluateur Python in-process de l’agent. Il bloque une liste de types d’instructions, rejette tout identifier commençant par un underscore et n’autorise les imports que depuis json, math et statistics. Mais exec dans le worker process n’est pas une frontière : un bypass s’exécute avec les file handles et le réseau du worker. Placez-le derrière une isolation du système de fichiers, du réseau et des credentials, avec des limites CPU, mémoire et temps, avant d’évaluer du code non fiable. Un subprocess seul hérite des accès et ne constitue pas une security sandbox.

Ces quatre couches sont une policy locale, et la policy locale est la couche la plus interne que vous contrôlez, pas la seule. Chaque élément de cette liste doit être intercepté ailleurs — dans le lockfile, dans le client MCP, dans la frontière de process autour du code généré ou dans des contrôles empêchant des instructions non fiables de relier des données privées à une destination d’exfiltration.

Points clés

  1. Les content filters et la policy d’exécution protègent des frontières différentes. Les filters inspectent l’input et l’output du modèle. L’autorisation des tools, le scope des credentials, les sandboxes et les contrôles de supply chain agissent sur les chemins utilisés dans les sept incidents.
  2. La plupart des catégories OWASP ASI nécessitent des contrôles en dehors de l’output du modèle. Utilisez la liste pour associer chaque menace au composant capable de réellement la bloquer ou de l’enregistrer.
  3. La permission est une infrastructure, pas un prompt. Claude Code documente la précédence des règles deny, ask et allow, tandis que PreToolUse peut bloquer avant l’exécution. Le Claude Agent SDK expose un chemin canUseTool distinct. Les autres runtimes ont besoin d’un modèle de précédence tout aussi testable.
  4. Traitez le deny structuré d’un hook PreToolUse comme une observation de tool supplémentaire. La reasoning loop le gère déjà. Vous n’avez pas besoin d’un workflow de sécurité séparé.
  5. Un taux d’approbation de 93 % est un signal invitant à examiner la qualité des prompts et la fréquence des escalades. Suivez les edits, les refus et les incidents post-approbation plutôt que de copier une cible universelle.
  6. Les tokens liés à l’audience et les vaults par session limitent le replay et l’exposition des credentials. Ils ne remplacent ni la confiance du projet, ni la policy des hooks, ni la sandbox.
  7. Les checks de supply chain doivent s’exécuter à la vitesse de l’automatisation. Pinnez les versions et les SHAs des Actions, scannez dans la CI et examinez les changements de dépendances dans les pull requests rédigées par des agents.
  8. Construisez la policy layer de manière à ce que le lancement d’un nouveau produit ne l’invalide pas. OpenAI Agents SDK, Codex CLI et Claude Code expriment différemment les mêmes primitives. Ce sont les primitives — permission ladders, hooks, sandboxes, interrupts, tokens liés à l’audience — sur lesquelles vous misez.
