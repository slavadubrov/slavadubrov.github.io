Ce guide s’adresse aux ingénieurs Python qui doivent décider s’il faut effectuer le fine-tuning d’un large language model et comment procéder. Vous apprendrez quand choisir le fine-tuning plutôt que le prompting ou la retrieval, et comment choisir entre des méthodes telles que LoRA et QLoRA. Le guide explique également comment préparer les données, évaluer le modèle entraîné et planifier son déploiement.

Les exemples expliquent des configurations et des vérifications. Ils ne constituent pas une recette d’entraînement de bout en bout vérifiée ; la section pratique distingue les commandes du repository compagnon d’une configuration d’entraînement proposée.

Pour une comparaison plus courte de ces options, consultez Fine-Tuning vs RAG vs Prompting.

Faut-il vraiment effectuer un fine-tuning ?

Avant de consommer des heures de GPU, déterminez si le fine-tuning est l’outil adapté au problème que vous devez résoudre.

Byte says

Si le seul comportement manquant est la production de JSON valide, testez d’abord le constrained decoding sur les poids d’origine. Un entraînement est un long détour pour découvrir une accolade manquante.

Le fine-tuning modifie le comportement encodé dans les poids. La retrieval fournit des éléments probants au moment de l’inférence ; c’est donc le meilleur point de départ pour les faits qui évoluent ou qui nécessitent des citations. Les nouveaux documents ne deviennent disponibles qu’après ingestion et indexation ; vérifiez que cette fraîcheur correspond à votre besoin.

Des prompts et des exemples clairs sont moins coûteux à itérer qu’un nouvel entraînement. Ils peuvent déjà résoudre un problème de style ou de suivi des instructions. Le fine-tuning peut réduire le nombre de tokens répétés dans les prompts, mais la latence de serving dépend du modèle, de la longueur de sortie, du matériel et de l’implémentation ; une mise à jour des poids n’accélère pas automatiquement l’exécution.

Pour la syntaxe, des bibliothèques telles que xgrammar et outlines masquent les tokens suivants invalides selon un schema ou une grammaire pris en charge. Une génération contrainte menée à son terme appartient à ce langage. Gérez séparément la troncature et les autres générations incomplètes, puis validez le résultat avant de l’utiliser. La contrainte ne peut pas rendre un identifiant client exact ni garantir qu’un choix d’outil est pertinent. Mesurez sa latence sur votre backend plutôt que de supposer une surcharge fixe.

Rendre le business case mesurable

Le fine-tuning peut réduire le nombre récurrent de tokens dans les prompts ou permettre à un modèle plus petit d’atteindre la cible, mais aucune de ces économies n’est automatique. Calculez le point mort avec votre trafic et votre tarification :

[ \text{requêtes au seuil de rentabilité} = \frac{\text{coût d’entraînement + d’évaluation + de déploiement}} {\text{coût de référence/requête} - \text{coût du modèle ajusté/requête}} ]

Si le dénominateur est faible, négatif ou fondé sur une hypothèse de qualité non démontrée, le projet ne présente pas encore de justification économique.

[!TIP] L’architecture hybride Une architecture courante associe un modèle plus petit adapté à la tâche à une retrieval pour les faits changeants. Prenez comme baseline le modèle plus grand avec prompting et ne conservez le modèle plus petit que s’il atteint les mêmes seuils de qualité et de sécurité propres à la tâche.

Types de fine-tuning

Le fine-tuning peut prendre trois formes principales. Elles diffèrent par le type de données nécessaire et par ce qu’elles apprennent au modèle.

1. Continued pre-training (self-supervised)

Vous entraînez le modèle de base sur davantage de texte brut, en utilisant le token suivant de chaque séquence comme cible d’entraînement. Il s’agit d’apprentissage self-supervised : le texte fournit lui-même ses cibles, comme lors de la pre-training initiale.

Cas d’utilisation :

  • Le domaine possède un vocabulaire que le modèle de base n’a jamais rencontré (médical, juridique, codebases internes).
  • Vous disposez de grandes quantités de textes du domaine, mais d’aucune paire (input, output) annotée.
  • Le modèle de base gère mal la terminologie propre au domaine.

Exemple : entraîner le modèle sur des millions de notes cliniques afin qu’il assimile les abréviations médicales, les noms de médicaments et les workflows cliniques.

2. Supervised fine-tuning (SFT)

Le SFT s’effectue sur des paires (input, output) annotées. Vous montrez au modèle la sortie exacte attendue pour chaque entrée.

Cas d’utilisation :

  • Vous avez une tâche spécifique avec un format input/output propre.
  • Vous disposez de données annotées de qualité, même en petite quantité.
  • Vous avez besoin d’un comportement prévisible sur une forme d’entrée connue.

Exemple : entraîner le modèle sur des paires (description de requête SQL, code SQL) pour du text-to-SQL. Cet intervalle calendaire fixe suppose que signup_date est stocké en UTC :

{
    "input": "Get users who signed up in August 2026 (UTC)",
    "output": "SELECT * FROM users WHERE signup_date >= '2026-08-01' AND signup_date < '2026-09-01'"
}

3. Instruction tuning

L’instruction tuning est un cas particulier de SFT conçu pour permettre aux modèles de suivre une grande variété d’instructions en langage naturel. Les données d’entraînement sont constituées de paires (instruction, réponse) couvrant de nombreuses tâches.

Cas d’utilisation :

  • Vous voulez un assistant généraliste (comme ChatGPT ou Claude).
  • Le modèle doit gérer des demandes variées et ouvertes.
  • Vous construisez une interface conversationnelle.

Exemple : entraîner le modèle sur des milliers d’instructions diverses telles que « Résumez cet article », « Écrivez un poème sur X » ou « Expliquez Y simplement ».

Le continued pre-training est une expérience distincte, qui doit être suivie de tests mesurant à la fois les gains dans le domaine et la régression des capacités générales.

Le pipeline de fine-tuning en 7 étapes

Le fine-tuning est un pipeline, pas une commande unique. Chaque étape possède ses propres modes d’échec, et en omettre une se traduit généralement plus tard par un mauvais modèle.

Chaque étape s’appuie sur la précédente :

  1. Préparation des données — Définir l’unité d’évaluation, séparer les données, puis les nettoyer et les formater
  2. Sélection du modèle — Choisir le modèle de base adapté et charger les poids
  3. Configuration de l’entraînement — Configurer le matériel, les hyperparamètres et la stratégie d’optimisation
  4. Fine-tuning — Exécuter un entraînement SFT, DPO ou ORPO
  5. Évaluation — Mesurer les performances avec un benchmark et valider la qualité
  6. Déploiement — Exporter et servir votre modèle
  7. Monitoring — Suivre les performances, maintenir le système et itérer

[!WARNING] Les données sont le socle L’entraînement reproduit les défauts systématiques présents dans les exemples. Inspectez les labels, les fuites, la couverture et la conformité aux politiques avant de consacrer du temps aux balayages d’optimiseurs.

Étape 1 : préparation des données

De nombreux projets de fine-tuning échouent ici, et non pendant l’entraînement. La préparation moderne des données ne consiste pas seulement à appliquer une regex sur des CSV.

Cinq transformations après la séparation des sources

Attribuez les groupes sources à l’entraînement ou à l’évaluation avant de transformer les lignes. Un ticket de support et toutes ses réécritures doivent rester dans la même partition. Regroupez les quasi-doublons connus avant d’attribuer les groupes, puis vérifiez à nouveau entre les partitions après le nettoyage. Figez le jeu d’évaluation ; augmentez uniquement les données d’entraînement.

Répertoriez les erreurs que vos exemples doivent apprendre au modèle à corriger, puis définissez les champs et labels requis pour chaque ligne. Choisissez les outils de traitement adaptés à ces étapes ; DataTrove et Distilabel peuvent aider avec les datasets volumineux.

1. Ingestion et filtrage

  • Action : supprimer les contenus UTF-8 corrompus et hors sujet. Étiqueter les refus selon la politique : conserver les refus corrects comme cibles d’entraînement et cas d’évaluation ; exclure uniquement les refus invalides ou hors sujet.
  • Outils : Trafilatura pour l’extraction et les modèles d’identification de langue de fastText pour l’identification de la langue ; les modèles distribués lid.176 reconnaissent 176 langues.

2. Politique relative aux données sensibles

  • Action : déterminer ce que le modèle est autorisé à apprendre, puis anonymiser, tokenizer ou exclure les champs personnels et confidentiels selon les besoins.
  • Outils : Microsoft Presidio ou scrubadub.
  • Pourquoi : un detector n’est qu’un contrôle parmi d’autres ; les exigences de provenance, consentement, conservation, accès et suppression restent applicables.

3. Déduplication (MinHash LSH)

  • Action : supprimer les quasi-doublons afin de réduire la répétition et le risque de fuite ; cela n’empêche pas la mémorisation.
  • Outils : DataTrove gère efficacement les traitements à l’échelle du téraoctet.

4. Augmentation synthétique, si nécessaire

  • Action : utiliser un teacher model adapté pour réécrire les exemples d’entraînement en paires instruction-réponse, en conservant leurs identifiants sources. N’augmentez pas la partition réservée à l’évaluation.
  • Outils : Distilabel.
  • Validation : échantillonner les sorties du teacher, les vérifier selon le même rubric que les labels humains et présenter séparément les résultats des exemples synthétiques et rédigés par des humains. Un tel sous-ensemble d’évaluation est appelé une slice ; d’autres slices utiles incluent la langue et le type de tâche.

5. Formatage

  • Action : convertir dans un format standard (Alpaca ou ShareGPT).

Exemples de formats de données

Format Alpaca (suivi d’instructions) :

{
    "instruction": "Summarize the following text.",
    "input": "The text to be summarized...",
    "output": "This is the summary."
}

Stockage de style ShareGPT (conversationnel) :

{
    "conversations": [
        { "from": "user", "value": "Hello, who are you?" },
        { "from": "assistant", "value": "I am a helpful AI assistant." }
    ]
}

Ce qui compte réellement

  • La couverture avant le volume. Ajoutez des exemples représentant des modes d’échec distincts, plutôt que de répéter le cas majoritaire facile.
  • La propreté. Supprimez le texte non pertinent, normalisez les espaces et gardez un formatage cohérent.
  • L’équilibre. Préservez les cas rares importants et présentez les performances par slice.
  • La séparation. Séparez par source, utilisateur, document ou période lorsque des splits aléatoires par ligne créeraient des quasi-doublons en fuite.
  • La provenance. Enregistrez la source, la licence ou l’autorisation, l’historique des transformations et le chemin de suppression pour chaque version du dataset.

Étape 2 : sélection du modèle et du matériel

Le modèle de base et sa mémoire GPU minimale déterminent ce que vous pouvez entraîner.

Commencez par le plus petit modèle de base qui franchit déjà les vérifications de baseline non négociables. Confirmez :

  • les conditions de licence et de redistribution applicables au produit visé ;
  • le comportement du modèle en matière de langue, de domaine, de tool use et de sécurité avant adaptation ;
  • la compatibilité du tokenizer et du chat template avec le dataset ;
  • la longueur de contexte maximale et le comportement de troncature nécessaires pour les exemples réels ;
  • la prise en charge par le framework d’entraînement et le moteur de serving cible.

Le fine-tuning est une étape d’adaptation, pas un remède à un modèle de base inadapté. Si le modèle échoue sur des capacités que le dataset ne couvre pas, choisissez un autre modèle de base avant de lancer davantage d’epochs.

Dimensionner l’exécution, pas le segment marketing

Il n’existe pas de tableau durable « taille du modèle → GPU ». La mémoire de pointe varie selon la précision des poids, l’optimiseur, le nombre de paramètres entraînables, la longueur des séquences, la micro-batch size, l’activation checkpointing, l’implémentation de l’attention et la surcharge du framework. Commencez par une estimation mémoire, puis exécutez un court smoke test à longueur maximale sur la stack exacte.

L’article original sur QLoRA a fait tenir un modèle LLaMA 65B sur un GPU de 48 Go dans sa configuration spécifique. Ce résultat constitue une borne utile, pas la garantie que toute architecture 70B actuelle, toute longueur de contexte, tout kernel ou tout trainer tiendra sur le même appareil.

Calcul de la mémoire

Pour un modèle comportant PPP paramètres, les poids seuls nécessitent approximativement 2P2P2P octets en BF16/FP16 ou 0.5P0.5P0.5P octets en quatre bits, avant les métadonnées de quantification et les buffers du runtime. Un entraînement complet de type Adam ajoute les gradients, les états de l’optimiseur et souvent des poids master en haute précision. LoRA évite l’essentiel de la mémoire des états entraînables ; QLoRA réduit en plus l’empreinte des poids gelés du modèle de base. Les activations peuvent néanmoins dominer avec de longues séquences.

Utilisez ce workflow :

  1. Choisissez la plus longue séquence et la micro-batch size que vous devez prendre en charge.
  2. Estimez les poids et les états entraînables, en gardant une marge pour les activations et les kernels.
  3. Exécutez une étape forward/backward à longueur maximale.
  4. Enregistrez la mémoire allouée et réservée maximale.
  5. Augmentez seulement ensuite la batch size, le rank, la longueur des séquences ou le nombre de GPUs.

Étape 3 : configuration de l’entraînement et méthodes

Des lignes stockées aux cibles d’entraînement

ShareGPT désigne une structure de dataset ; ChatML est une convention de sérialisation. Convertissez from/value en rôles et champs acceptés par le trainer, puis utilisez le chat template du modèle sélectionné. Ne remplacez pas les tokens ChatML simplement parce que les données sont conversationnelles.

Pour la ligne de salutation ci-dessus, les messages normalisés sont :

messages = [
    {"role": "user", "content": "Hello, who are you?"},
    {"role": "assistant", "content": "I am a helpful AI assistant."},
]
# Inspection step after loading the selected model's tokenizer:
rendered = tokenizer.apply_chat_template(
    messages, tokenize=False, add_generation_prompt=False,
)
print(rendered)

Inspectez la ligne réellement sérialisée avant l’entraînement : les délimiteurs de rôles, les tokens de fin de tour et les tool schemas doivent correspondre à l’inférence. Pour une ligne utilisant un outil, conservez les définitions des outils, les tool calls de l’assistant et les tool results comme champs distincts. Vérifiez que la troncature ne supprime pas la réponse supervisée et ne coupe pas un argument d’outil au milieu.

Le loss masking détermine les tokens dont la prédiction est récompensée. Dans l’entraînement sur séquence complète, le texte user, system, tool et assistant peut contribuer. Dans l’entraînement assistant-only, ces tokens de contexte restent visibles par l’attention, mais leurs labels sont ignorés (généralement -100) ; seuls les segments de l’assistant contribuent. Pour cette salutation, la réponse doit être une cible et la question de l’utilisateur ne doit pas l’être, si l’objectif est un comportement assistant-only.

La documentation SFT de TRL prend en charge assistant_only_loss=True pour les datasets conversationnels dont les templates exposent des segments de génération. Un template dépourvu de ces segments ne peut pas fournir ce masque. Les datasets prompt/completion disposent d’une option completion_only_loss distincte. Avant d’activer l’une ou l’autre, inspectez un batch tokenisé et décodez les tokens dont les labels ne sont pas ignorés. Répétez ensuite avec une conversation utilisant un outil et un exemple de longueur maximale. La configuration d’entraînement illustrative ci-dessous utilise volontairement un loss sur séquence complète ; l’entraînement assistant-only nécessite cette vérification supplémentaire du template et du masque.

Choisissez une longueur de séquence à partir de la distribution des données et exécutez la vérification mémoire à longueur maximale de l’étape 2. Le packing place plusieurs exemples courts dans une seule séquence d’entraînement. Commencez sans packing afin de pouvoir inspecter facilement les limites entre les lignes. Évaluez le packing uniquement après avoir vérifié les lignes sérialisées et les labels.

Fine-tuning complet vs PEFT

Le fine-tuning complet (FFT) met à jour chaque poids ; les gradients et l’état de l’optimiseur évoluent donc avec la taille totale du modèle. Le pic de mémoire ne peut pas être déduit du seul nombre de paramètres, mais il dépasse largement la mémoire nécessaire pour charger les poids en inférence.

Le parameter-efficient fine-tuning (PEFT) n’entraîne qu’un petit sous-ensemble de paramètres et gèle le reste. Les calculs deviennent beaucoup plus favorables.

LoRA : le point de départ

LoRA (Low-Rank Adaptation) gèle une matrice pré-entraînée et représente sa mise à jour apprise avec deux matrices plus petites. L’article original formule cette approche à partir de l’hypothèse que les mises à jour utiles pour l’adaptation ont un rang intrinsèque faible.

Ici, dind_{in}din​ correspond à la largeur d’entrée de la couche et doutd_{out}dout​ à sa largeur de sortie. Le rang rrr est la dimension partagée la plus petite des deux matrices entraînables : un rang plus faible utilise moins de paramètres entraînables. Le paramètre α\alphaα contrôle l’échelle de la mise à jour via le ratio α/r\alpha/rα/r.

Pour une matrice gelée W0∈Rdout×dinW_0 \in \mathbb{R}^{d_{out} \times d_{in}}W0​∈Rdout​×din​, LoRA apprend :

  • A∈Rr×dinA \in \mathbb{R}^{r \times d_{in}}A∈Rr×din​
  • B∈Rdout×rB \in \mathbb{R}^{d_{out} \times r}B∈Rdout​×r

La couche adaptée est :

W′=W0+αrBAW' = W_0 + \frac{\alpha}{r}BAW′=W0​+rα​BA

L’adapter possède r(din+dout)r(d_{in}+d_{out})r(din​+dout​) paramètres entraînables au lieu de dindoutd_{in}d_{out}din​dout​ pour cette matrice. Pour une matrice carrée de largeur 4 096 avec un rang de 16, cela représente une réduction de 128× des paramètres entraînables de cette matrice. Les économies à l’échelle du modèle dépendent des matrices auxquelles les adapters sont appliqués.

DoRA : LoRA décomposé par poids

DoRA (Weight-Decomposed Low-Rank Adaptation) sépare la magnitude de chaque vecteur de poids de sa direction. L’article sur DoRA applique une mise à jour LoRA à la composante directionnelle tout en apprenant séparément la magnitude.

Fonctionnement :

Au lieu de traiter les poids comme une entité unique, DoRA décompose les poids pré-entraînés en deux composantes :

  1. Magnitude — une valeur entraînable par vecteur de poids.
  2. Direction — un vecteur normalisé mis à jour au moyen de matrices low-rank.

En notation compacte par colonne :

W′=mV+BA∥V+BA∥cW' = m \frac{V + BA}{\lVert V + BA \rVert_c}W′=m∥V+BA∥c​V+BA​

où :

  • m = magnitude (entraînable)
  • V=W0V = W_0V=W0​ = matrice initiale gelée ; normaliser après l’ajout de BABABA
  • BABABA = mise à jour directionnelle low-rank apprise
  • ∥⋅∥c\lVert \cdot \rVert_c∥⋅∥c​ = normalisation par colonne

Ce que cette structure supplémentaire apporte :

  • Davantage de degrés de liberté que LoRA standard, car la magnitude peut évoluer indépendamment.
  • De meilleurs résultats que LoRA dans plusieurs configurations rapportées par l’article qui propose la méthode.
  • Des paramètres et calculs supplémentaires ; le gain doit donc être vérifié sur votre tâche et votre chemin de serving.

Fusion d’adapters pour l’apprentissage multitâche

Des adapters distincts permettent à une même base gelée de prendre en charge plusieurs tâches. Vous pouvez router les requêtes vers un adapter, servir plusieurs adapters depuis un même moteur lorsque cette possibilité est supportée, ou créer un candidat fusionné hors ligne. La fusion peut entraîner des interférences ; évaluez donc l’artifact fusionné au lieu de supposer que les adapters sources se combinent proprement.

Méthodes de fusion courantes :

  1. Concaténation — combine les paramètres des adapters et augmente le rang effectif. Rapide et simple.
  2. Combinaison linéaire — somme pondérée des adapters. Offre des paramètres de réglage.
  3. SVD — décomposition matricielle pour la fusion. Plus flexible, mais plus lente.

Exemple : un adapter pour le résumé, un autre pour la traduction, fusionnés en un modèle multitâche unique.

Étape 4 : fine-tuning et preference alignment

Le SFT apprend à partir de démonstrations. La preference optimization apprend au contraire à partir de comparaisons telles que « la réponse choisie A est meilleure que la réponse rejetée B ». Utilisez-la uniquement lorsque la préférence par paire constitue le bon label pour l’erreur ; l’exactitude factuelle et la conformité aux politiques nécessitent souvent des evaluators plus robustes qu’une préférence globale.

RLHF basé sur PPO

RLHF signifie reinforcement learning from human feedback. La policy est le modèle de langage qui génère les réponses ; un reward model évalue ces réponses à partir de préférences apprises sur des comparaisons humaines. Une recette basée sur PPO comporte trois étapes :

  1. SFT — apprendre la tâche.
  2. Reward model — l’entraîner sur les préférences humaines (chosen vs rejected).
  3. PPO (Proximal Policy Optimization) — générer des réponses et mettre à jour le modèle de langage afin d’augmenter leurs scores de reward.

Le coût opérationnel vient des différents composants :

  • Implémentation et maintenance complexes.
  • Coûteux — plusieurs modèles sont entraînés.
  • L’échantillonnage depuis le modèle en cours d’entraînement nécessite de détecter les mises à jour instables et les réponses qui exploitent le reward model sans satisfaire la tâche.

DPO

DPO (Direct Preference Optimization) supprime le reward model distinct et la boucle de reinforcement learning. Il favorise les réponses choisies tout en décourageant les écarts importants par rapport à un modèle de départ fixe, appelé modèle de référence. L’article sur DPO dérive cet objectif en limitant l’écart entre les probabilités des réponses et celles de cette référence ; cette limite mathématique est une contrainte de divergence KL.

Une paire de préférences contient le même prompt et deux réponses candidates. Cette ligne abrégée montre ses champs ; de vrais labels nécessitent des réponses complètes et une raison de préférer l’une d’elles :

{
    "prompt": "Explain quantum computing",
    "chosen": "Quantum computing uses qubits...",   # Preferred response
    "rejected": "Well, it's complicated..."        # Non-preferred response
}

Ce qui change sur le plan opérationnel :

  • Chemin de code plus simple (pas de reward model séparé ni de boucle RL).
  • Entraînement sur des paires de préférences enregistrées, plutôt que génération de nouvelles réponses pour évaluer le reward à chaque mise à jour.
  • Modèle de référence fixe, ou log probabilities enregistrées pour les réponses d’entraînement, dans la formulation standard.

Le DPO est plus facile à prototyper qu’un pipeline PPO complet, mais il n’améliore pas automatiquement la qualité. Les résultats dépendent de la policy de départ, de la qualité des paires, des paramètres de loss, des effets de longueur et du protocole d’évaluation. Comparez-le à un checkpoint SFT sur les mêmes suites de préférences et de tâches réservées à l’évaluation.

ORPO

ORPO (Odds-Ratio Preference Optimization) combine le loss de negative log-likelihood du SFT avec une pénalité d’odds ratio sur les réponses rejetées. Il supprime le modèle de référence distinct et peut combiner apprentissage de la tâche et preference optimization au cours d’une seule exécution.

Fonctionnement : ORPO utilise un loss combiné qui réalise simultanément deux opérations :

  1. Maximiser la vraisemblance de la réponse choisie (apprentissage de la tâche).
  2. Pénaliser la réponse rejetée avec un terme d’odds ratio (apprentissage des préférences).

Hyperparamètres à connaître (API TRL 1.12.0) :

# API shown in TRL 1.12.0 documentation
from trl.experimental.orpo import ORPOConfig

config = ORPOConfig(
    learning_rate=8e-6,  # Very low, as recommended by the ORPO paper
    beta=0.1,            # Controls strength of preference penalty
    # ... other params
)
  • Learning rate : l’article utilise de faibles valeurs dans ses expériences ; ajustez-le à votre modèle, votre batch et vos données plutôt que de copier une valeur comme une règle.
  • Beta : contrôle le terme de préférence par rapport au terme SFT.

Le compromis :

  • Une seule étape d’entraînement au lieu de deux.
  • Aucun reward model.
  • Aucun forward pass du modèle de référence.
  • Une exécution couplée : si l’apprentissage de la tâche ou le comportement de préférence régresse, aucun checkpoint SFT intermédiaire du même pipeline n’est disponible pour inspection.

Choisissez en fonction des données et du protocole d’évaluation :

  • Utilisez DPO si vous disposez déjà d’un checkpoint SFT satisfaisant et souhaitez mener une expérience de préférence offline plus simple.
  • Testez ORPO si un objectif en une seule étape, sans modèle de référence, correspond à vos données et contraintes opérationnelles.
  • Utilisez le RLHF basé sur PPO si l’échantillonnage online face à un reward appris explicite fait partie du besoin et si vous pouvez surveiller l’exploitation du reward.

Aucune de ces méthodes n’est un choix par défaut pour toutes les tâches. Conservez une baseline SFT-only et présentez à la fois les métriques de tâche et de préférence.

Frameworks de fine-tuning

Les frameworks se recouvrent et évoluent rapidement. Choisissez-le en fonction du chemin d’exécution à prendre en charge, verrouillez les versions et conservez une configuration d’entraînement suffisamment portable pour être reproduite en dehors d’un notebook.

Unsloth — vitesse et efficacité mémoire

Unsloth s’intègre à trl et transformers de Hugging Face et fournit des kernels optimisés, du checkpointing et des chemins de fine-tuning quantifié pour les modèles pris en charge.

  • Kernels GPU Triton personnalisés pour l’attention, RoPE et l’entropie croisée, qui évitent la surcharge de PyTorch.
  • Backpropagation économe en mémoire, qui recalcule les activations pendant le backward pass au lieu de les conserver en mémoire.
  • Opérations fusionnées qui regroupent plusieurs étapes (layer norm + linear, entre autres) en un seul appel GPU.
  • Quantification 4 bits intégrée directement au chemin QLoRA, avec une déquantification optimisée.

[!IMPORTANT] L’ordre des imports est important Suivez l’ordre des imports de l’exemple Unsloth correspondant à la version que vous avez verrouillée. Unsloth applique des patches lors de l’import ; l’importer avant trl et transformers évite les optimisations manquantes ou les erreurs propres à certaines versions.

# Correct order
from unsloth import FastLanguageModel  # Must be first!
from trl import SFTTrainer
from transformers import TrainingArguments

# Avoid this order with Unsloth's patched path
from trl import SFTTrainer
from unsloth import FastLanguageModel

Idéal pour : l’entraînement sur un seul GPU, le prototypage, les notebooks Colab et toute personne attentive à sa facture GPU.

Les chiffres publiés de vitesse et de mémoire varient selon le modèle, la longueur des séquences, le batch, la précision et le matériel. Mesurez les tokens par seconde et la mémoire de pointe sur votre propre exécution au lieu de considérer un ratio mis en avant comme une propriété du framework.

Configuration d’entraînement TRL proposée

Il s’agit d’une configuration schématique, et non de code fourni par le companion. Fournissez train_dataset et eval_dataset sous forme de datasets Hugging Face contenant les colonnes messages et, pour les exemples d’outils, tools. Produisez-les à partir d’un split versionné par source/groupe, comme décrit à l’étape 1. Verrouillez des révisions compatibles d’Unsloth, TRL, Transformers et du modèle ; la forme de l’API suit TRL 1.12.0.

Le diagramme présente cette expérience proposée, notamment le split source.

Les appels ci-dessous évaluent le loss des tokens une fois par epoch. Il s’agit d’un diagnostic, pas d’une mesure de l’exactitude de l’exécution des tool calls ; l’étape 5 nécessite encore une évaluation distincte de la tâche.

from unsloth import FastLanguageModel
from trl import SFTConfig, SFTTrainer

# Load model with 4-bit quantization
model, tokenizer = FastLanguageModel.from_pretrained(
    model_name="nvidia/Llama-3.1-Nemotron-Nano-4B-v1.1",
    max_seq_length=4096,
    load_in_4bit=True,
)

# Add LoRA adapters
model = FastLanguageModel.get_peft_model(
    model,
    r=16,
    lora_alpha=32,
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj",
                    "gate_proj", "up_proj", "down_proj"],
    use_gradient_checkpointing="unsloth",  # Lower activation memory; extra compute
)

# Prerequisite: supply the prepared datasets described above.

# Train with the current TRL configuration surface.
trainer = SFTTrainer(
    model=model,
    processing_class=tokenizer,
    train_dataset=train_dataset,
    eval_dataset=eval_dataset,
    args=SFTConfig(
        output_dir="outputs/proposed-nemotron-run",
        max_length=4096,
        packing=False,
        assistant_only_loss=False,  # Full-sequence targets; inspect before changing
        eval_strategy="epoch",
        per_device_train_batch_size=2,
        gradient_accumulation_steps=4,
        learning_rate=2e-4,
        num_train_epochs=3,
        bf16=True,  # Requires BF16-capable hardware
    ),
)
trainer.train()
trainer.save_model("outputs/proposed-nemotron-adapter")
tokenizer.save_pretrained("outputs/proposed-nemotron-adapter")

Étape 5 : évaluation

Byte says

Si le même ticket de support apparaît dans l’entraînement et l’évaluation, un score plus élevé peut simplement récompenser la mémorisation de ce ticket. Séparez les données par ticket avant de créer les lignes ou les réécritures.

Fixez les cas de test, les règles de scoring et les seuils de réussite avant le premier run. Au minimum, comparez le checkpoint ajusté avec le modèle de base exactement non ajusté, en utilisant le même prompt, les mêmes paramètres de décodage et le même environnement d’outils. Ne présentez une qualité agrégée qu’après avoir vérifié les failure slices que le projet devait améliorer.

Suivez quatre groupes :

  1. Tâche cible : exact match, succès d’exécution, rubric humain ou autre résultat lié au cas d’usage.
  2. Régression : capacités générales et slices de tâches précédemment supportées que l’adaptation pourrait détériorer.
  3. Sécurité et politiques : refus, fuite de données, prompt injection ou contraintes propres au domaine.
  4. Opérations : latence, débit, mémoire, taille de l’artifact et coût dans la configuration de serving visée.

Benchmarks automatisés

Utilisez lm-evaluation-harness pour vérifier les tâches standardisées pertinentes en complément de vos tests produit. Cette commande nécessite un checkpoint Hugging Face fusionné. Son chemin d’exemple correspond à la sortie fusionnée legacy du companion à l’étape 6 ; elle ne charge pas l’adapter enregistré par la configuration proposée ci-dessus. Remplacez-le par le checkpoint fusionné que vous souhaitez évaluer :

lm_eval --model hf \
    --model_args pretrained=./outputs/unsloth-nemotron-function-calling-merged \
    --tasks hellaswag,arc_easy,mmlu \
    --batch_size 8

LLM-as-judge

Pour la qualité subjective, un modèle plus grand peut contribuer au scoring, mais calibrez-le sur des exemples évalués par des humains et masquez l’identité du candidat :

judge_prompt = """
Rate this response from 1-5 on:
- Relevance
- Accuracy
- Formatting

Response: {model_output}
Expected: {ground_truth}
"""

Évaluation propre au domaine

Réservez des exemples réels par source, utilisateur, document ou période afin d’empêcher la fuite de quasi-doublons entre les splits. Pour le function calling, validez la trajectoire complète : sélection de l’outil, arguments, résultat d’exécution, récupération et réponse finale. Présentez des intervalles de confiance ou des comptes de victoires/défaites appariés lorsque l’échantillon est réduit, et inspectez chaque régression dans une slice critique.

Étape 6 : déploiement et formats de sortie

Choisissez l’artifact en fonction du moteur de serving et du plan de rollback, pas uniquement de la taille des fichiers. Ces exemples CLI font référence au companion legacy, et non à l’extrait TRL proposé. Son répertoire d’adapter par défaut est outputs/unsloth-nemotron-function-calling, avec les répertoires -merged et -gguf pour les exports. Chaque invocation CLI entraîne à nouveau le modèle ; ce n’est pas une commande d’export uniquement. Pour une release réelle, exportez le checkpoint évalué sélectionné au lieu de comparer des artifacts issus d’entraînements distincts.

1. Adapter LoRA

uv run finetune  # Default adapter directory shown below
  • Taille : proportionnelle aux modules ciblés, au rang, au nombre de couches et au dtype ; souvent bien inférieure à celle de la base.
  • Idéal pour : le développement, les adapters de tâche versionnés et les moteurs qui prennent directement LoRA en charge.
  • Avantage : vous pouvez remplacer les adapters sans retélécharger le modèle de base.

2. Modèle fusionné

uv run finetune --merge  # Creates a standalone full model
  • Taille : environ celle du checkpoint de base complet dans la précision de sortie choisie.
  • Idéal pour : les moteurs ou chemins de distribution qui ne prennent pas en charge l’adapter séparément.
  • Compromis : artifact plus volumineux et rollout plus lent, mais chargement d’un modèle unique plus simple.

3. Format GGUF

uv run finetune --gguf q4_k_m  # File size and name depend on the exporter
  • Taille : dépend du modèle ; environ des poids quatre bits plus les métadonnées pour les variantes Q4.
  • Idéal pour : l’inférence CPU, Ollama, llama.cpp et le déploiement edge.
  • Options : q4_k_m (plus petit), q5_k_m (meilleure fidélité des poids), q8_0 (plus grand et plus fidèle). Mesurez l’impact sur la tâche après conversion.

Étape 7 : serving et monitoring

Avec vLLM

Ce sketch de serving suppose que l’adapter proposé a passé l’évaluation de tâche et a été entraîné avec un template d’outils compatible avec Llama 3.1. Enregistrez ce template exact et vérifié sous serving-chat-template.jinja ; le companion ne le crée pas. La compatibilité de l’adapter au format ChatML legacy avec cette paire parser/template n’est pas établie. Vérifiez une trajectoire complète d’utilisation d’un outil avant d’exposer l’endpoint.

# Serve the base and expose a PEFT adapter as a model name. This parser and
# template pair is for a Llama 3.1-compatible function-calling adapter.
vllm serve nvidia/Llama-3.1-Nemotron-Nano-4B-v1.1 \
    --enable-lora \
    --lora-modules function-calling=./outputs/proposed-nemotron-adapter \
    --enable-auto-tool-choice \
    --tool-call-parser llama3_json \
    --chat-template ./serving-chat-template.jinja \
    --host 0.0.0.0 \
    --port 8000 \
    --max-model-len 4096

Ce schema de vol volontairement minimal teste la génération des arguments via l’API compatible OpenAI. Il demande un book_flight proposé avec une destination ; il n’exécute pas de réservation. Inspectez response.choices[0].message.tool_calls pour vérifier le nom de la fonction et les arguments JSON. Pour cette entrée, le résultat attendu est book_flight avec {"destination": "Tokyo"}. Comme le choix de l’outil est automatique, vérifiez également si le modèle a renvoyé un appel :

from openai import OpenAI

client = OpenAI(base_url="http://localhost:8000/v1", api_key="dummy")
response = client.chat.completions.create(
    model="function-calling",
    messages=[{"role": "user", "content": "Book a flight to Tokyo"}],
    tools=[
        {
            "type": "function",
            "function": {
                "name": "book_flight",
                "description": "Book a flight to a city.",
                "strict": True,
                "parameters": {
                    "type": "object",
                    "properties": {
                        "destination": {"type": "string"},
                    },
                    "required": ["destination"],
                    "additionalProperties": False,
                },
            },
        }
    ],
    tool_choice="auto",
)

Le guide du tool calling de vLLM exige le choix automatique de l’outil et un parser adapté au modèle. Fournissez un chat template compatible si la configuration du tokenizer n’en contient pas. Avec tool_choice="auto", les arguments contraints nécessitent également strict: true sur au moins une fonction et un schema parameters compatible avec le mode strict. Le paramètre strict-tool-calling du serveur doit être activé (c’est la valeur par défaut documentée). Sans cette activation explicite, vLLM extrait les appels du texte brut ; les arguments peuvent donc être mal formés ou violer le schema.

Inspectez le répertoire d’export -gguf réel et remplacez MODEL_FILE.gguf ci-dessous par le nom de fichier produit ; les versions d’Unsloth peuvent utiliser des noms différents. Un fichier GGUF seul ne garantit pas un formatage correct des conversations et des outils dans Ollama ou llama.cpp. Faites correspondre le template entraîné et testez l’artifact importé.

# Import to Ollama

Avec llama.cpp (CPU)

En utilisant le même export GGUF et en remplaçant le nom de fichier de la même manière, cette commande vérifie une réponse en texte brut. Elle ne teste pas un tool call complet :

./llama-cli -m ./outputs/unsloth-nemotron-function-calling-gguf/MODEL_FILE.gguf \

Monitorer le modèle publié

Le cycle de vie ne s’arrête pas lorsque le loss d’entraînement est satisfaisant. Enregistrez la révision du modèle de base, le tokenizer et le chat template, le hash de l’adapter, la version du dataset, la configuration d’entraînement et le rapport d’évaluation comme une seule unité de release. En production, surveillez le succès des tâches, les sorties invalides, les échecs de politique, la latence et la dérive des entrées selon les mêmes slices qu’en offline. Gardez l’artifact précédent chargeable et définissez un seuil de rollback avant le lancement.

Votre prochain test

Avant une exécution complète, inspectez une conversation sérialisée et ses cibles de loss, puis réalisez une étape forward/backward à longueur maximale. Enregistrez cette configuration avec le split du dataset et le rapport de baseline. Si un tool schema est manquant, préservez-le dans la ligne d’entraînement. Si une réponse est tronquée, ajustez la longueur de séquence et le formatage afin que la réponse complète soit conservée. Résolvez ces problèmes avant d’ajouter des epochs.
