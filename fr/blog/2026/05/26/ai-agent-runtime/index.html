Ce guide s’adresse aux ingénieurs qui déploient des AI agents utilisant des tools et devant survivre aux redémarrages des workers. Il explique où conserver les journaux de session, les checkpoints, l’exécution des tools et les traces, puis compare les modèles de déploiement afin de vous aider à choisir un runtime récupérable.

Une exécution d’agent peut durer plusieurs heures, mais son processus worker peut redémarrer à tout moment. TL;DR

pour mettre en pause et reprendre une exécution, utilisez un checkpoint store. Conservez un event log durable pour enregistrer ce qui s’est passé, une sandbox pour l’exécution des tools, une trace pour le debugging et un harness pour exécuter la boucle. Pour la plupart des équipes, commencez avec une queue, un worker et un checkpointer PostgreSQL. Si vous ne pouvez pas nommer le responsable de chaque job, l’agent est encore un prototype.

Qu’est-ce qu’un runtime d’AI agent ?

Un runtime d’AI agent est l’infrastructure qui maintient en fonctionnement un agent utilisant des tools après la fin d’un appel au modèle. Il stocke l’état de session, exécute les tools, enregistre les checkpoints, gère les secrets, écrit les traces, applique les limites de coût et définit le mode de déploiement du service. Le modèle choisit l’action suivante. Le runtime décide où cette action s’exécute, enregistre le résultat et restaure l’exécution après un échec. Le harness décide si une action est autorisée. Ce n’est pas un store, mais il figure dans le tableau parce que le runtime doit bien l’exécuter quelque part.

Les exécutions longues remettent en cause les hypothèses des processus stateless

Byte says

Si le journal d’exécution ne vit que dans la mémoire du worker, un déploiement ordinaire peut remplacer le worker en pleine tâche et effacer l’historique de l’exécution.

Un endpoint de chat stateless peut conserver l’état de la requête dans un seul processus puis le supprimer après la réponse. Une exécution longue d’agent traverse les redémarrages de workers, les déploiements, les réinitialisations de contexte et les pauses d’approbation. Le processus worker ne peut plus être la source de vérité.

L’équipe OpenAI Codex indique la durée que peuvent atteindre ces exécutions dans son article sur le harness engineering :

« Nous voyons régulièrement des exécutions Codex individuelles travailler sur une seule tâche pendant plus de six heures (souvent pendant que les humains dorment). »

L’équipe d’ingénierie d’Anthropic décrit le problème d’état correspondant dans Effective harnesses for long-running agents :

« Le principal défi des agents longue durée est qu’ils doivent travailler par sessions discrètes, et que chaque nouvelle session commence sans mémoire de ce qui s’est passé auparavant. »

Ces deux observations impliquent la même conception du runtime : persister l’état en dehors du worker et rendre les workers remplaçables.

La session doit vivre en dehors du processus worker. Un store durable enregistre les appels au modèle, les intentions et résultats des tools, ainsi que les approbations, afin qu’un autre worker puisse reprendre au dernier point sûr après un crash. Un effet externe en attente doit être réconcilié avant que cette reprise puisse être considérée comme sûre. Les checkpoints permettent également au runtime de démarrer une nouvelle session de modèle lorsque la context window est pleine, sans rejouer tout l’historique. Selon la formulation d’Anthropic, les instances du harness deviennent jetables et redémarrables ; l’état durable vit ailleurs.

Cinq primitives à positionner avant la mise en production

L’article d’Anthropic Scaling Managed Agents fournit un vocabulaire utile pour cinq responsabilités du runtime. Le harness fait progresser l’agent, tandis que la session enregistre ce qu’il a fait et que la sandbox exécute les commandes. Le checkpoint fournit au worker suivant un point de reprise ; la trace conserve les éléments nécessaires au debugging ultérieur. Une implémentation peut fusionner certains composants, mais les responsabilités et les frontières d’échec doivent tout de même être nommées.

Session. Un event log append-only écrit séparément, contenant les appels au modèle, les tool calls demandés et terminés, les erreurs et les approbations. Une base de données de checkpoints facilite la récupération, mais l’historique de l’état du graphe ne remplace pas ce log.

Le terme étant ambigu, cet article utilise une convention de nommage applicative pour trois spans. Un thread est la conversation d’un utilisateur sur plusieurs jours. C’est le span qui dure le plus longtemps et qui peut contenir plusieurs exécutions.

Une model session est la plus courte : une période continue de contexte modèle. La compaction — l’étape qui résume la fenêtre afin de permettre au travail de continuer — prolonge une model session au lieu d’y mettre fin. Un redémarrage ou un nouveau départ explicite y met fin. La partie 6 emploie « model session » dans ce sens.

Dans cet article, « session » désigne le log durable d’une exécution. Plusieurs model sessions peuvent écrire dans un même log, et un thread de conversation peut contenir plusieurs run logs. Pour récupérer une exécution, réveillez-la, chargez sa session, réconciliez tout side effect en attente, puis reprenez après le dernier événement : wake(sessionId) → getSession(id) → reconcile pending effects → resume from last event.

Dans LangGraph, thread_id est la clé de stockage et de récupération du checkpointer pour l’historique de l’état du graphe d’un thread (voir LangGraph persistence) ; elle ne définit pas les frontières de conversation, de model session ou d’event log utilisées dans cet article. Donnez à l’event log son propre identifiant durable d’exécution ou de session, puis choisissez explicitement la correspondance entre ces identifiants et les threads LangGraph. L’OpenAI Agents SDK fournit dix session backends intégrés, notamment SQLiteSession, RedisSession, SQLAlchemySession, MongoDBSession et EncryptedSession (voir la documentation Sessions). Ils contiennent l’historique mutable des conversations, avec notamment la suppression, l’effacement et la compaction ; associez un identifiant de session SDK à l’identifiant des événements d’exécution si cela est utile, mais ne considérez pas l’historique du SDK comme le log append-only de récupération ou d’audit sans garantie d’immutabilité équivalente.

Harness. La boucle d’orchestration, et la seule primitive présentée ici qui prend des décisions. Elle construit le prompt à partir de la mémoire, appelle le modèle, vérifie le tool call proposé par rapport à ses règles de permission, distribue ce qu’elle autorise, réinjecte les résultats dans la session, applique les règles de retry et décide si la tâche est terminée. Les aides à la planification et la gestion du contexte encodent des hypothèses sur les capacités du modèle. L’autorisation obligatoire et l’isolation implémentent également des exigences qui restent valables à mesure que les modèles progressent. Anthropic le souligne directement — la citation apparaît dans la section consacrée aux modes d’échec ci-dessous, qui traite principalement des conséquences du vieillissement de ces hypothèses.

L’équipe Codex d’OpenAI appelle cela le harness engineering : écrire du software demande toujours un effort d’ingénierie, mais une part croissante de cet effort est désormais consacrée au scaffolding plutôt qu’au code lui-même. Le CompiledStateGraph de LangGraph, les Deep Agents de LangChain et leur point d’entrée create_deep_agent, ainsi que Claude Code lui-même, sont tous des harnesses dans ce sens.

Sandbox. L’environnement d’exécution isolé dans lequel les commandes s’exécutent réellement. La page de l’OpenAI Agents SDK consacrée aux concepts de sandbox attribue les approbations, le tracing, les handoffs et l’état nécessaire à la reprise des exécutions au runtime externe. Elle attribue les commandes, les modifications de fichiers et l’isolation de l’environnement à la session de sandbox.

Le terme « runtime externe » désigne ici le harness avec ses stores d’état. Dans le vocabulaire de cette série, les approbations et les handoffs sont des décisions du harness (partie 4 et partie 6) ; le tracing et le suivi des reprises sont assurés par les primitives session et checkpoint.

Les sandboxes diffèrent par leur durée de vie et par ce qu’elles mémorisent entre les exécutions. Le modèle le plus simple est fresh ephemeral : en créer une pour une seule tâche, la détruire à la fin de la tâche et payer le coût de cold start à chaque exécution.

Les sandboxes persistent paused conservent le système de fichiers et un snapshot mémoire entre les exécutions. La reprise suivante peut ainsi éviter un démarrage complet. Snapshot or fork crée une branche copy-on-write à partir d’un parent préparé : de nombreuses tâches partagent les dépendances installées et les caches chauds sans partager leur état inscriptible.

Les workspaces per-worktree donnent aux tâches des checkouts séparés ; les worktrees Git partagent l’infrastructure du dépôt et ne sont pas des sandboxes OS. Restreignez séparément l’exécution avec une container, une VM ou une politique de processus. Une application par tâche peut aussi disposer de sa propre stack d’observabilité. Des logs, métriques et traces séparés vous permettent de déboguer une exécution sans que son état contamine celui d’une autre. Le tableau des fournisseurs plus loin dans cet article compare les contrats d’isolation et de persistance.

Checkpoint. L’état nécessaire à la reprise : quel nœud du graphe s’est exécuté, quelles sont ses dernières valeurs et ce qui doit s’exécuter ensuite. Un event log répond à la question « que s’est-il passé ? » : les actions demandées et leurs résultats. Un checkpoint ne peut pas reconstruire des événements que le harness n’a jamais enregistrés.

Le PostgresSaver de LangGraph écrit un Checkpoint à chaque frontière de super-step. Un super-step correspond à un tour du graphe, soit un nœud unique, soit un batch exécuté en parallèle. Les écritures par tâche vont dans checkpoint_writes, de sorte que les sorties de nœuds réussis ne soient pas recalculées lorsqu’un nœud frère échoue.

Un checkpoint est un dict Python ordinaire (v, id, ts, channel_values, channel_versions, versions_seen, updated_channels). LangGraph le sérialise avec son JsonPlusSerializer fondé sur msgpack plutôt qu’avec JSON. datetime, set, Decimal et les dataclasses sont tous restaurés à l’identique. Le format est documenté sur la langgraph-checkpoint-postgres sur PyPI et dans la référence LangGraph checkpoints.

StateSnapshot est la vue séparée et plus riche que graph.get_state() construit au-dessus d’un checkpoint. Un debug bundle peut exporter son .values comme dernier état connu du graphe ; il ne peut pas reconstruire les détails des événements que le harness n’a jamais enregistrés.

Trace. La surface de debugging et d’audit. Chaque appel au modèle, tool call et étape de sous-agent devrait émettre la durée, le statut, le modèle et le fournisseur, les identifiants de corrélation, le nombre de tokens et le coût. Les prompts, completions, arguments des tools et résultats des tools sont des contenus opt-in : les recommandations GenAI d’OpenTelemetry utilisent par défaut les métadonnées, car ces champs peuvent contenir des données sensibles. Ne les capturez qu’après avoir défini la stratégie de redaction ou de filtrage, les contrôles d’accès et la rétention applicables. Lorsqu’une exécution de six heures échoue, c’est la trace que vous consultez pour comprendre ce qui s’est passé. Elle peut faciliter une investigation, mais c’est l’event log et l’état des checkpoints, avec la gestion de l’idempotence, qui permettent une reprise ou un replay sûrs. La sortie du terminal de l’exécution a alors disparu depuis longtemps. Les conventions sémantiques GenAI d’OpenTelemetry standardisent les noms d’attributs : quel modèle, quel fournisseur, combien de tokens, quelle conversation, quel workflow. Pour une destination compatible OTLP prenant en charge ces conventions, la même instrumentation peut exporter la trace vers des systèmes tels que Tempo, Jaeger, Honeycomb ou LangSmith, même si des adapters backend ou une configuration propre à la destination peuvent rester nécessaires.

Les policies et les secrets traversent les cinq primitives

Deux frontières traversent les cinq primitives. Elles constituent la version runtime de l’argument de sécurité présenté dans la partie 4. La décision de permission elle-même appartient au harness ; ce qui suit décrit où se trouvent physiquement les mécanismes qui l’appliquent et l’alimentent.

Application des permissions

La permission ladder de la partie 4 doit bien s’exécuter quelque part. La vérification se déclenche avant chaque tool call et décide s’il peut passer. Deux modèles sont courants en production. Le middleware filesystem-permission de Deep Agents peut limiter les filesystem tools intégrés aux chemins déclarés. Il ne gouverne ni les commandes shell de la sandbox, ni les tools custom, ni les appels MCP ; appliquez ces contrôles dans la policy de la sandbox ou derrière leur propre proxy de tools. Anthropic Managed Agents achemine les appels de tools MCP custom à travers un proxy qui détient les credentials. L’exécution des commandes de sandbox et l’authentification Git suivent des chemins distincts ; le proxy MCP n’est pas un intercepteur universel de toutes les actions. Lorsqu’un appel sensible nécessite une approbation humaine, le interrupt() de LangGraph et le hook d’approbation de Deep Agents mettent le graphe en pause jusqu’à la réponse d’une personne.

Secret broker

Le modèle ne devrait pas voir de secrets longue durée, et la sandbox ne devrait généralement pas les voir non plus. Le modèle Managed Agents est celui à reproduire :

« Pour Git, nous utilisons le token d’accès de chaque dépôt pour cloner le dépôt lors de l’initialisation de la sandbox et l’intégrer au remote Git local. Git push et pull fonctionnent depuis l’intérieur de la sandbox sans que l’agent ne manipule jamais lui-même le token. Pour les tools custom, nous prenons en charge MCP et stockons les tokens OAuth dans un vault sécurisé. Claude appelle les tools MCP via un proxy dédié ; ce proxy reçoit un token associé à la session. … Le harness n’a jamais connaissance des credentials. »

Dans la stack de référence market-analyst-agent — un petit agent LangGraph qui récupère des données de marché et rédige un rapport d’analyste, construit au fil de cette série — le worker appelle localement ses tools de données de marché. Le serveur MCP optionnel expose une surface de tools ; il ne constitue pas un credential broker implémenté entre ce worker et ses fournisseurs. Les deux containers peuvent lire le .env de développement partagé. Un broker de production nécessiterait de déplacer les credentials des fournisseurs dans un store illisible par le worker et de router chaque appel concerné à travers le broker.

Vérifier le positionnement

Une vérification pratique consiste à noter chaque composant et la primitive parmi les cinq qu’il implémente. Postgres peut couvrir la session et le checkpoint. Le container worker est le harness. Un service tel que Daytona, Modal ou E2B fournit la sandbox, tandis que Tempo ou LangSmith stocke la trace.

Examinez ensuite les échecs couplés. Si deux primitives vivent dans le même processus, un seul crash les fait tomber toutes les deux. Si elles partagent un credential, une fuite franchit les deux frontières. Exemples courants : un worker qui possède aussi la durabilité des traces, ou un token de sidecar qui déverrouille également la base de données des checkpoints.

Modes d’échec d’un runtime d’AI agent en production

Le runtime gère les retries, restaure le travail déjà effectué, isole les workspaces et applique les budgets. À mesure que les exécutions s’étendent sur plusieurs workers et context windows, les échecs se déplacent vers l’état, les side effects dupliqués, la dérive des sandboxes et les dépassements de budget.

Les échecs se répartissent en quatre groupes :

  • Échecs de qualité de sortie : l’agent déclare la victoire avant que le travail soit réellement terminé, oublie ce qu’il a fait après une réinitialisation de context window, ou fait confiance à sa propre auto-évaluation et publie une sortie défectueuse.
  • Échecs de contrôle des coûts : l’agent reste bloqué dans une boucle de retry ou consomme un budget de tokens ou de tool calls sans rien produire d’utile.
  • Échecs d’état et de crash : les workspaces dérivent parce qu’une exécution modifie des fichiers appartenant à une autre, les tool calls sont déclenchés plusieurs fois parce que les retries les rejouent, ou le travail est perdu lorsqu’un worker meurt entre deux événements.
  • Échecs de context window : le modèle résume puis s’arrête trop tôt parce qu’il pense manquer de place, alors que la fenêtre dispose encore de marge.

Le tableau associe chaque échec à une mitigation, à la base de la recommandation et au hook du runtime qui l’applique. Le comportement spécifique à un modèle peut changer : considérez donc les observations des fournisseurs comme des invitations à retester l’hypothèse, et non comme des règles permanentes.

Deux idées sous-tendent la plupart de ces lignes. Anthropic, à propos de l’obsolescence des harnesses dans Harness design for long-running application development :

« Chaque composant d’un harness encode une hypothèse sur ce que le modèle ne peut pas faire seul, et ces hypothèses méritent d’être soumises à des tests de résistance, à la fois parce qu’elles peuvent être incorrectes et parce qu’elles peuvent rapidement devenir obsolètes à mesure que les modèles progressent. »

Vercel, à propos du problème connexe de tools trop nombreux encodant trop d’hypothèses, dans We removed 80% of our agent’s tools :

« Nous avons supprimé la majeure partie et réduit l’agent à un seul tool : exécuter des commandes bash arbitraires. Nous appelons cela un file system agent. »

La citation décrit le cœur bash ; l’agent livré par Vercel conservait deux tools, ExecuteCommand et ExecuteSQL, remplaçant un ancien exemple de code qui nommait dix-sept tools. La partie 3 couvre l’avant et l’après en détail. Leur résultat rapporté sur cinq requêtes représentatives : la réussite est passée de 4/5 à 5/5, et le pire cas est passé de 724 s / 100 étapes / 145 463 tokens (échec) à 141 s / 19 étapes / 67 483 tokens (réussite). Cette ligne du pire cas est la plus spectaculaire ; en moyenne sur les cinq requêtes, l’économie de tokens était de 37 %. La leçon n’est pas « supprimez vos tools ». Une assistance optionnelle peut devenir redondante lorsque le comportement du modèle évolue. Retestez l’hypothèse lorsque le modèle change.

Cognition a observé la même évolution sur la durée des sessions avec Sonnet 4.5. Dans Rebuilding Devin for Claude Sonnet 4.5, l’équipe décrit un modèle qui écrit proactivement SUMMARY.md / CHANGELOG.md lorsqu’il perçoit l’épuisement du contexte, mais sous-estime le nombre de tokens restants. Leur correctif consistait à activer le contexte de 1M tokens et à plafonner l’utilisation à 200k afin que le modèle pense disposer encore de marge. Il s’agissait d’un flag beta au moment de la rédaction.

La documentation sur les context windows d’Anthropic, vérifiée le 6 septembre 2026, indique que Sonnet 5 et Opus 5 disposent par défaut d’1M de tokens ; Sonnet 4.5 reste à 200k. Les modèles Sonnet actuels reçoivent automatiquement des mises à jour sur le contexte restant, et la compaction côté serveur est disponible en beta pour Claude 4.6 et les modèles ultérieurs. Avant de reproduire le plafond historique de Cognition, testez le modèle choisi avec les contrôles de contexte qu’il prend en charge. Une fenêtre ou un budget plus grand ne garantit pas une mémorisation fiable, et aucun des deux ne remplace une progression durable en dehors du modèle.

L’équipe du harness d’OpenAI en donne la version en une ligne : « Les humains orientent. Les agents exécutent. » Lorsqu’un échec survient, la question utile est de savoir quelle capacité manque et comment rendre cette capacité à la fois lisible et applicable pour l’agent.

Le cycle de vie d’une exécution saine

Une exécution bien conçue est ennuyeuse. C’est une chaîne de petites étapes récupérables, et chaque étape terminée écrit un état durable avant le démarrage de la suivante.

Écrire chaque résultat avant le démarrage de l’étape suivante limite les dégâts d’un crash. Un effet externe en cours constitue l’exception : un worker peut crasher après le commit du fournisseur et avant que le harness n’enregistre son résultat. Le worker suivant doit réconcilier cet effet en attente avant de reprendre à partir de la dernière étape terminée.

  1. Démarrez depuis une session nouvelle ou reprise. En reprise, montez le workspace dans son dernier état connu, lisez les fichiers de progression laissés par la tentative précédente (PROGRESS.md, feature-list.json), chargez le dernier checkpoint et inspectez l’event log à la recherche d’intentions de tools en attente. Réconciliez tout effet externe en attente avant d’effectuer un nouvel appel au modèle ou à un tool.
  2. Planifiez avant tout déclenchement de tool call. Notez ce que signifie « terminé », combien l’exécution est autorisée à dépenser, quels tools l’agent peut invoquer et ce qui doit arrêter prématurément l’exécution. Ces valeurs de plan deviennent des vérifications du runtime ; sans elles, l’exécution n’a rien pour lui résister.
  3. Sérialisez ou coordonnez explicitement les tool calls qui produisent des side effects. La vérification de permission du harness décide d’autoriser ou non chacun d’eux. Avant la distribution, ajoutez une intention pending avec sa clé d’idempotence ; au retour du fournisseur, ajoutez le résultat. Les appels indépendants en lecture seule ou idempotents peuvent s’exécuter en parallèle lorsque chacun dispose de son propre enregistrement durable d’intention/résultat et que leurs résultats sont agrégés de manière déterministe. Si le worker meurt entre un side effect et l’écriture de son résultat, reprenez en interrogeant ou en retentant le fournisseur avec la même clé, puis ajoutez soit le résultat récupéré, soit needs_human. Stripe, par exemple, renvoie le résultat enregistré de la première requête lorsqu’une clé d’idempotence est répétée ; un autre fournisseur nécessite un contrat équivalent de lookup ou de retry.
  4. Créez un checkpoint aux frontières des super-steps, ou après chaque événement dans un harness plus simple. Persistez l’état du graphe, le diff du workspace et les références vers les artefacts produits. C’est ce checkpoint que lit l’étape 1 lors de la reprise suivante. Si le checkpoint est absent ou obsolète, la récupération peut devoir reconstruire l’état à partir de l’event log, ce qui est beaucoup plus lent.
  5. Évaluez les artefacts lorsque l’agent pense avoir terminé : tests, evaluator en fresh context, validation du schema, vérifications dans le browser. Si la vérification réussit, l’exécution se termine avec succès. Si elle échoue, l’exécution reprend depuis le dernier checkpoint propre, avec le message d’échec ajouté au contexte, puis réessaie.

Aucune étape de cette liste n’exige que l’agent se souvienne de quoi que ce soit entre les exécutions. L’état vit dans la session et le checkpoint, et l’agent le relit à chaque reprise.

Persistez un identifiant d’opération détenu par l’application avant la distribution et liez-le aux arguments approuvés. Réutilisez-le pour récupérer la même intention métier, même si la replanning produit un nouvel identifiant de tool call du modèle. Enregistrez séparément ces identifiants du modèle pour la corrélation. Les mises à jour naturellement idempotentes peuvent à la place nécessiter une précondition de version. Les recommandations d’AWS sur les retries expliquent pourquoi l’identité de requête représente l’intention. Définissez quand une action est réellement nouvelle et combien de temps la déduplication dure : Stripe autorise la suppression des clés après au moins 24 heures. Réconciliez les payloads modifiés et les clés expirées avant toute nouvelle tentative.

Choisissez un writer actif unique ou un lease par thread. Pour les entrées arrivant pendant une exécution, rejetez, mettez en queue, interrompez ou annulez explicitement ; le retour d’expérience runtime de Deep Agents décrit ces choix. L’annulation doit arrêter toute nouvelle distribution, enregistrer la demande et réconcilier les effets en cours ; tuer le worker n’annule pas un appel au fournisseur.

L’application du budget doit se trouver à côté de la distribution. Des appels concurrents ne doivent pas dépenser deux fois la même allocation restante. Prometheus est un système de monitoring, pas un ledger faisant autorité pour les dépenses par requête. Réservez de manière prudente et réconciliez l’utilisation réelle ; la comptabilisation différée du fournisseur et les annulations peuvent encore provoquer un dépassement.

Les nouveaux contrôles du modèle aident à rythmer l’exécution, mais ne sont pas responsables de sa limite de dépenses. Les task budgets beta d’Anthropic fournissent aux modèles pris en charge par la Messages API un budget indicatif pour une boucle agentic. Ils peuvent être dépassés ; max_tokens limite une réponse, pas l’exécution entière. La prise en charge dépend du modèle : Opus 5 prend en charge les task budgets, contrairement à Sonnet 5. Conservez le ledger de distribution et le chemin d’annulation même lorsque le modèle reçoit une indication de budget.

Les arrêts de sécurité du fournisseur doivent disposer de leur propre chemin terminal. Pour le misalignment_policy_violation d’OpenAI, arrêtez la distribution, conservez les enregistrements corrélés et demandez une revue opérateur plutôt que de retenter. Gérez les erreurs de stream après une sortie partielle et réconciliez les effets précédents ; la partie 4 explique la frontière de monitoring.

L’évaluation doit inclure des éléments probants extérieurs au contexte producteur. Un evaluator en fresh context réduit le biais du contexte partagé, tandis que les tests, lints, vérifications browser et validations de schema fournissent des éléments déterministes. La vérification peut renvoyer pass, fail ou needs_human. Pour les agents de code, le reviewer peut être une autre model session avec des tools en lecture seule. Pour les agents de données et de rapports, combinez une validation déterministe avec un reviewer model lorsque le jugement reste nécessaire.

Onze modèles de déploiement d’AI agents et les critères de choix

Une fois les cinq primitives nommées, la question devient celle de la forme de déploiement qui les exécute. Par « forme », j’entends une disposition de ces primitives : où vit le harness, où l’état est persistant et quel type de sandbox exécute le travail. Une forme est une décision de câblage, pas un choix de fournisseur. Le graphique ci-dessous indique où chaque forme est à l’aise selon la longueur de l’exécution. Le texte qui suit détaille les critères de décision.

Si vous ne lisez qu’une seule des onze formes, lisez la forme 2 : queue + worker + checkpoint DB. C’est le modèle par défaut que je recommande à la plupart des équipes, celui utilisé par le dépôt de référence et le squelette dont dérivent la plupart des autres formes : queue → worker → état durable, avec permutation de la source de la sandbox, du propriétaire du harness ou du moteur d’état. Lire d’abord la forme 2 permet de parcourir le reste plus rapidement.

Le graphique compare les formes selon la durée d’exécution. La matrice ci-dessous les compare selon la responsabilité : chaque cellule encadrée nomme le composant qui fournit la primitive correspondante.

1. SDK dans un app server (synchrone, limité à la requête)

La forme originale. L’agent SDK s’exécute dans un request handler. Elle convient aux tâches de moins de 30 secondes, aux démos et aux tools internes. Elle est inadaptée à tout ce dont un client HTTP pourrait se déconnecter. Le timeout HTTP de Cloud Run est plafonné à 60 minutes, et toute panique du web tier tue l’exécution. Le SDK est le harness. L’exécution de tools non fiables nécessite une sandbox séparée, et l’état vit généralement en mémoire du processus sauf si vous le poussez explicitement ailleurs. N’utilisez pas cette forme pour un travail de plusieurs heures.

2. Queue + worker + checkpoint DB

C’est le modèle par défaut que je recommande à la plupart des équipes, ainsi que l’implémentation de démonstration adaptée à la production dans market-analyst-agent : un worker Python avec un checkpointer PostgreSQL, Redis Streams (ou RabbitMQ) pour la queue entrante et un sidecar MCP pour les tools. Ce modèle convient aux exécutions de 10 minutes à plusieurs heures avec des étapes idempotentes. Le runner local peut contourner la queue pour le développement synchrone, mais la queue fait partie de la forme de production dès que vous avez besoin de soumissions asynchrones et de backpressure.

Dans le modèle de production, l’application accepte une requête, crée une ligne de session, pousse un job et renvoie un ID d’exécution. Le worker récupère le job, exécute le harness, écrit les événements de session et les checkpoints, diffuse le statut et stocke les artefacts au fil de l’exécution. Postgres persiste, les workers sont remplaçables et la profondeur de la queue fournit la backpressure. Un compute Spot/Preemptible fonctionne à condition que les écritures durables de l’event log et du checkpoint soient terminées avant que le worker ne signale le succès. Le dépôt lié illustre cette topologie ; la reprise durable dépend aussi des leases de la file, de la récupération des jobs interrompus et de la confirmation du travail terminé.

Dans cette forme, le worker est le harness. Son container et le workspace par thread fournissent une frontière d’exécution, mais le code non fiable nécessite toujours une sandbox renforcée ou une VM. L’event store possède l’historique de session ; PostgresSaver possède l’état des checkpoints. Ils peuvent partager une base de données uniquement lorsque le harness écrit explicitement les deux schemas. Les traces passent par OpenTelemetry vers la stack d’observabilité que vous utilisez.

3. Moteur de workflow durable (style Temporal)

Le code d’orchestration de l’agent s’exécute dans un Temporal Workflow ; les appels au modèle et les tool calls s’exécutent comme des Activities. L’état du workflow vit dans un event-history log sauvegardé par Cassandra, MySQL ou Postgres, ce qui permet le replay après un échec. Les déploiements de code du workflow qui chevauchent une exécution nécessitent Worker Versioning ou des patches compatibles avec le replay ; remplacer le code sans cette discipline peut casser le replay. L’intégration Temporal × OpenAI Agents SDK, généralement disponible depuis mars 2026, fournit un OpenAIAgentsPlugin et un helper activity_as_tool, tandis que l’article sur les agentic sandboxes décrit le fork d’un agent en cours d’exécution vers un autre fournisseur de sandbox pendant la conversation. Les workflows inactifs consomment zéro compute. Les réserves sont réelles : les agents realtime ne sont pas pris en charge et le streaming est encore marqué comme expérimental ; LocalShellTool et ComputerTool sont désactivés parce qu’ils ne correspondent pas à un modèle distribué.

Utilisez cette forme lorsque l’exécution comporte de véritables points d’attente : approbations humaines, callbacks externes, longues périodes de sommeil, retries avec règles métier, fenêtres de déploiement — et que l’équipe sait opérer un versioning de workflow compatible avec le replay. Une approbation humaine devient un sleep durable qui ne consomme aucun compute, et non une boucle de polling.

Le code du Workflow est le harness. La sandbox vit généralement en dehors de Temporal et est appelée depuis les Activities. L’état de session et de checkpoint se fond dans l’event-history log de Temporal, tandis que la visibilité des traces provient de l’interface Temporal et des spans OpenTelemetry sur chaque Activity.

4. Un sandbox provider par session

Une forme plus récente. Chaque exécution d’agent reçoit sa propre microVM ou son propre container depuis un fournisseur de sandbox-as-a-service. Le harness vit quelque part de manière durable ; la sandbox est l’environnement d’exécution jetable.

Mesurez séparément le délai entre la requête API et la première commande réussie, ainsi que le délai jusqu’à ce que l’application soit prête, en incluant l’état de l’image/cache, la région, la concurrence et les p95/p99. Le fournisseur possède la sandbox, et rien d’autre. Le harness, la session, le checkpoint et la trace restent de votre côté, généralement câblés selon la forme queue + worker de la section 2.

5. Anthropic Managed Agents (harness hébergé)

Anthropic a lancé Managed Agents en beta publique le 8 avril 2026, derrière le header beta managed-agents-2026-04-01. Le service fournit une session hébergée, un harness, une sandbox et un proxy MCP adossé à un vault. wake(sessionId) peut initialiser le harness sur un nouveau worker sans perdre l’état durable de la session.

Anthropic facture Managed Agents aux tarifs standards des tokens, plus $0.08 par heure-session. La facturation est granulaire à la milliseconde et ne s’applique que lorsque le statut de la session est « running » ; le temps d’inactivité est gratuit. Une boucle de retry incontrôlée ajoute donc un coût d’heures-session en plus du coût des tokens.

Lisez les réserves. La remise de la Batch API ne s’applique pas (« Les Sessions sont stateful et interactives. Il n’existe pas de mode batch. »). Managed Agents n’est pas disponible via AWS Bedrock ni via Google Vertex AI. Dans la beta, les tunnels MCP et le « dreaming » des agents nécessitent un accès supplémentaire au titre d’une research preview ; la coordination multi-agent et l’auto-évaluation notée par une rubric font partie des fonctionnalités documentées de la beta. Le lock-in est élevé : vous échangez la liberté du harness contre le fait de ne pas gérer vous-même la boucle.

La configuration cloud par défaut place les cinq primitives chez Anthropic. Avec les sandboxes self-hosted, vous gérez l’exécution, les systèmes de fichiers et l’egress réseau, tandis qu’Anthropic exécute l’orchestration et le modèle. Les entrées et résultats des tools atteignent toujours son control plane ; les skills et la mémoire attachées y sont stockées et synchronisées. Posséder l’exécution ne rend pas tout le système self-hosted.

Claude Platform on AWS prend également en charge Managed Agents et les sandboxes self-hosted ; ce service est distinct de Bedrock. Dans ce cas, une session autonome nécessite un événement de rôle utilisateur pour se réauthentifier après six heures, et les sessions self-hosted ne peuvent pas attacher de memory stores. Managed Agents first-party n’a pas ces deux restrictions. Vérifiez la plateforme aussi bien que le modèle avant de reproduire une conception de session.

6. LangChain Deep Agents Deploy (harness open managé)

deepagents deploy empaquette un deepagents.toml dans un LangSmith Deployment avec exécution durable, mémoire, multi-tenancy, human-in-the-loop, observabilité, exécution de code sandboxée et exécutions planifiées. Les modes de déploiement cloud, hybride et self-hosted sont pris en charge. Les fournisseurs de sandbox (LangSmith Sandboxes, Daytona, Modal, Runloop ou custom) peuvent être changés via une seule valeur de configuration. Les fichiers et la mémoire de l’agent vivent dans un système de fichiers virtuel avec des backends interchangeables ; la persistance des checkpoints est séparée, et la mémoire est limitée à l’utilisateur, à l’assistant ou aux deux. Le lock-in est inférieur à celui de Managed Agents : le harness est sous licence MIT, les instructions utilisent le standard ouvert AGENTS.md et les agents sont exposés via MCP, le protocole A2A (Agent2Agent) et Agent Protocol. Voir l’article de LangChain runtime-behind-production-deep-agents.

Les cinq primitives sont hébergées par défaut, mais chacune peut être remplacée par configuration. La sandbox se trouve derrière une seule valeur de configuration. Le memory filesystem est distinct de la persistance des threads et des checkpoints. La trace est envoyée à LangSmith.

7. Service ou job Google Cloud Run

Cloud Run propose deux modes de runtime différents, et le choix dépend de la manière dont l’agent est invoqué. Les services sont liés à HTTP et scale to zero entre les requêtes ; le harness s’exécute comme un request handler qui retourne lorsque l’exécution est terminée. Les jobs s’exécutent jusqu’à completion sans point d’entrée HTTP ; le harness fonctionne comme un worker one-shot qui se termine lorsque la tâche finit. Les deux peuvent héberger le harness, mais aucun ne conserve l’état entre les exécutions. Les sessions et les checkpoints doivent vivre dans Postgres, Spanner ou un store externe équivalent.

Les limites strictes sont très différentes. Timeout des requêtes Cloud Run service : 300 s par défaut, maximum 3 600 s (60 min). Les WebSockets ont le même timeout. Cloud Run jobs : 10 min par tâche par défaut, maximum 168 h (7 jours) ; pour les tâches utilisant des GPUs, maximum 1 heure. La facturation basée sur les instances (CPU toujours alloué) permet malgré tout le scale-to-zero ; le nombre minimal d’instances est un réglage distinct ; les jobs n’ont pas de HTTP et ne s’autoscalent pas.

Utilisez un service pour les exécutions synchrones allant jusqu’à 60 minutes. Utilisez un job pour un travail one-shot ou asynchrone plus long. Cloud Run Jobs peut maintenir une tâche en vie pendant plusieurs jours, mais ne fournit pas de replay durable lors des déploiements, des changements de version ou du remplacement d’un worker. Un workflow plus long peut s’étendre sur plusieurs exécutions lorsqu’un orchestrateur externe possède la progression durable.

Cloud Run héberge le harness. L’état des sessions et des checkpoints vit dans Postgres, Spanner ou un autre store externe, et les traces peuvent passer par Cloud Logging et OpenTelemetry. Le container du service est un environnement d’exécution ; ajoutez une sandbox séparée lorsque l’agent exécute du code non fiable.

8. AWS Lambda : invocations bornées et workflows durables

Le timeout maximal d’une fonction Lambda est de 900 s (15 minutes), sans exception. Si API Gateway est placé devant la fonction, la limite d’intégration dépend du type d’API. Les HTTP APIs autorisent 30 secondes ; les intégrations REST ont par défaut une limite de 29 secondes, tandis que les API REST régionales et privées peuvent configurer un timeout plus long. Les durable functions de Lambda, lancées en décembre 2025, ajoutent des checkpoints, étapes et attentes managés entre des exécutions pouvant durer jusqu’à un an. L’invocation active reste bornée, tandis que le workflow durable peut lui survivre. Comparez les runtimes, régions, règles de replay et idempotence des activities pris en charge avec vos exigences.

Lambda peut héberger un harness borné par sa limite de 15 minutes. L’état des sessions et des checkpoints nécessite toujours des emplacements externes explicites ; ajoutez une sandbox distincte pour le code non fiable et exportez les traces vers une télémétrie externe. Un workflow Lambda durable peut orchestrer un travail de plusieurs heures au travers d’invocations bornées.

9. Une tâche AWS ECS / Fargate par exécution

Fargate ne documente pas de limite stricte à la durée d’une tâche, contrairement à une invocation Lambda ordinaire. Fargate ne prend pas en charge les tâches GPU ; les workloads GPU ECS nécessitent des instances EC2 adaptées ou un service GPU externe. Fargate fournit une isolation des tâches fondée sur la virtualisation, mais les credentials et l’accès réseau autorisé nécessitent toujours un threat model. Les quotas de throttling Fargate autorisent un burst de lancement de 100 et un réapprovisionnement de 20 par seconde, avec des budgets distincts pour l’on-demand et le Spot. Les quotas de service ECS plafonnent les services utilisant la découverte AWS Cloud Map à 1 000 tâches par service, et les clusters adossés à EC2 à 5 000 instances de containers.

Fargate nécessite le mode awsvpc, de sorte que chaque tâche reçoive une interface réseau et une IP privée. Cette forme convient à l’accès à des données internes au VPC. Fargate Spot ajoute un risque d’interruption, et la durabilité reste sous votre responsabilité car la plateforme ne fournit pas de replay de type Temporal.

Fargate héberge le harness et donne à chaque exécution sa propre tâche. Cela sépare les workspaces et les credentials de tâche, mais ne constitue pas à lui seul une sandbox complète pour du code hostile. La session, le checkpoint et la trace sont envoyés à des services externes tels que RDS ou DynamoDB, ainsi qu’à CloudWatch/X-Ray.

Comparez également Amazon Bedrock AgentCore Runtime avant de construire vous-même la couche de sessions AWS. Il héberge votre code d’agent avec un cycle de vie de session managé et un choix de compute. AWS documente jusqu’à 8 heures sur des microVMs serverless, ou 14 jours avec son type de compute Instances, qui prend également en charge les workloads GPU. Instances utilise des ressources EC2 gérées par AWS dans votre compte, avec un modèle de sécurité différent de celui de l’option serverless. Sélectionnez et testez explicitement ce contrat de compute ; une instance à durée de vie plus longue ne garantit toujours pas l’exécution exactly-once d’un side effect externe.

10. Kubernetes Job ou namespace par session

Convient lorsque vous opérez déjà Kubernetes et souhaitez une sandbox par session avec des contrôles à l’échelle du cluster. Convient moins lorsque vous avez besoin d’un démarrage inférieur à la seconde, car le pull de l’image du container et l’initialisation du pod sont trop longs lors d’un cold start. Le modèle consiste en un Job par exécution d’agent, avec activeDeadlineSeconds, un PersistentVolumeClaim pour le workspace et un sidecar pour le serveur MCP. La récupération après crash est à construire vous-même. Adopter Kubernetes uniquement pour héberger des agents coûte cher en configuration et en charge opérationnelle. Cela ne vaut le coup que si vous exploitez déjà K8s pour d’autres raisons.

Kubernetes héberge le harness et l’environnement d’exécution par exécution, généralement sous la forme d’un Job et parfois avec un namespace dédié. Une isolation forte dépend toujours de la runtime class, de la network policy, de la pod security et de la frontière container ou VM sous-jacente. La session et l’état des checkpoints vivent dans une base de données externe ou sur un PersistentVolumeClaim.

11. Docker Compose local (uniquement pour le développement)

La référence pour la section suivante. L’intérêt de cette forme est qu’elle reproduit la topologie de production un pour un (mêmes primitives, même forme réseau) tout en s’exécutant sur une seule machine. Ce qu’elle ne reproduit pas est l’isolation : un montage de workspace partagé, un Postgres unique, aucune sandbox renforcée et aucune failure domain distincte entre le worker et son état. Ne mettez rien en production sous une forme similaire.

Compose reproduit la forme n°2 sur un seul hôte. Dans la stack de référence, Postgres contient l’état des checkpoints et le container worker est le harness. Une session adaptée à la production nécessite son propre event store append-only ; l’historique PostgresSaver seul ne suffit pas. Le montage de workspace partagé est pratique pour le développement, mais n’isole pas les exécutions non fiables. La stack OpenTelemetry optionnelle enregistre les traces.

Stack de référence : Docker Compose

La topologie de référence, utilisée dans slavadubrov/market-analyst-agent, est composée d’un worker LangGraph, d’un checkpointer Postgres, de Qdrant pour la retrieval, d’un sidecar MCP, d’une queue Redis pour les exécutions asynchrones proches de la production et d’une stack d’observabilité optionnelle Prometheus / Grafana / Loki / Tempo / OTel. Dans le Compose local, Redis est optionnel uniquement parce que le runner synchrone peut appeler directement le worker. docker compose up démarre localement la topologie centrale ; le sidecar MCP et la stack d’observabilité sont des profiles opt-in (--profile mcp, --profile observability).

Le diagramme montre le PostgresSaver de la démo locale. Une session adaptée à la production ajoute un schema d’événements écrit séparément pour les intentions et résultats des tools ; PostgresSaver reste uniquement l’état du checkpoint.

Le seul élément qui mérite d’être montré inline est le câblage LangGraph canonique. Il s’agit d’un extrait illustratif, et non d’un exemple exécutable tel quel dans le dépôt. Son exécution nécessite langgraph, langgraph-checkpoint-postgres et psycopg[binary,pool], une base PostgreSQL accessible avec le droit de créer les tables du checkpointer, POSTGRES_PASSWORD et un StateGraph préalablement construit dans builder ; voir la configuration du checkpointer Postgres de LangGraph.

from urllib.parse import quote

from langgraph.checkpoint.postgres import PostgresSaver

password = quote(os.environ["POSTGRES_PASSWORD"], safe="")
DB_URI = f"postgresql://agent:{password}@postgres:5432/agent"
# `builder` is your StateGraph, already built
session_id = "session-123"
with PostgresSaver.from_conn_string(DB_URI) as checkpointer:
    checkpointer.setup()  # creates tables on first run
    graph = builder.compile(checkpointer=checkpointer)
    result = graph.invoke(
        {"messages": [{"role": "user", "content": "Continue the task"}]},
        {"configurable": {"thread_id": session_id}},
    )

Une observabilité qui survit à l’exécution

Les request handlers courts sont faciles à déboguer : lorsqu’un problème survient, on lit la réponse et le log live. Les agents longue durée n’ont pas ce luxe. Lorsqu’une exécution de six heures échoue, l’événement intéressant s’est produit cinq heures plus tôt, la sortie du terminal live a disparu et le worker qui l’a produite a été remplacé. Personne ne va reconstruire l’exécution de mémoire. Le debugging se fait donc à partir d’artefacts durables écrits pendant que l’exécution était encore active.

Byte says

Si une exécution longue échoue après que la sortie intéressante du terminal a défilé, l’event log durable et la trace sont les éléments restants à inspecter.

Les stacks de production couvrent généralement quatre types d’artefacts, répartis en deux groupes. Deux se lisent après la fin de l’exécution, pour les postmortems et le replay : un event log interrogeable de chaque étape et des traces OpenTelemetry indiquant où sont passés le temps et les tokens. Deux se lisent pendant l’exécution. Le premier est un live tail de ce que l’agent produit dans le workspace. L’autre est une stack d’observabilité par worktree que l’agent lui-même peut interroger pendant son travail.

Event log structuré (à lire après l’exécution)

Chaque appel au modèle, tool call, résultat, erreur et approbation est écrit dans un stockage durable, indexé par l’identifiant de session et l’horodatage. Une fois l’exécution terminée, vous l’interrogez comme une table de base de données normale. Addy Osmani fixe clairement le niveau d’exigence dans Long-running Agents : « Si vous ne pouvez pas reconstruire ce que l’agent a fait au cours des dernières 24 heures à partir d’un stockage durable, vous avez un long-running shell script qui se trouve à appeler un LLM, pas un agent longue durée. »

Traces OpenTelemetry GenAI (à lire après l’exécution)

Les mêmes données détaillées étape par étape sont émises sous forme de spans utilisant les attributs standards des gen_ai.* conventions sémantiques : nom du modèle, fournisseur, nombre de tokens en entrée et en sortie, identifiant de conversation et nom du workflow. Ces conventions sont encore au niveau de stabilité Development.

En 2026, elles ont quitté le dépôt principal des conventions sémantiques d’OpenTelemetry pour rejoindre leur propre dépôt de conventions sémantiques GenAI. Les noms d’attributs peuvent servir à instrumenter le code, mais verrouillez la révision que vous avez validée plutôt qu’un numéro de version du dépôt principal. Les champs propres aux fournisseurs vivent dans des sous-namespaces (anthropic.*, openai.*) indexés par gen_ai.provider.name. L’intérêt du standard est la portabilité : sur les destinations compatibles OTLP qui prennent en charge ces conventions, changer de backend peut ne pas nécessiter de réinstrumenter le code, même si des adapters backend ou une configuration propre à la destination peuvent rester nécessaires.

Timeline des tool calls et diffs du workspace (à lire pendant l’exécution)

Les modifications du workspace donnent une vue rapide de ce que fait un agent pendant une exécution. Le Harness Primitives for Long-Running Claude Agents quick-start d’Anthropic utilise le monitoring live du workspace. Lorsque watch est installé, watch -n 5 'git log --oneline -8' actualise les derniers commits toutes les cinq secondes. Pour les screenshots, ouvrez le répertoire des screenshots dans un file browser, triez par date de modification avec les plus récents en premier et inspectez les dernières images. Les commits et screenshots donnent des indices sur l’activité ; comparez-les aux résultats des tests et au statut de l’exécution avant de conclure que l’agent progresse.

Stack éphémère par worktree (lue par l’agent lui-même pendant l’exécution)

Selon l’article d’OpenAI sur le harness : « Les logs, métriques et traces sont exposés à Codex via une stack locale d’observabilité, éphémère pour un worktree donné. » Chaque worktree d’agent reçoit sa propre stack Loki + Prometheus + Tempo de courte durée, limitée à cette seule exécution. L’agent l’interroge pendant son travail. C’est ce qui permet à un prompt tel que « aucun span de ces quatre parcours utilisateur ne dépasse deux secondes » de devenir quelque chose que l’agent peut vérifier directement, plutôt que de devoir le deviner.

(L’evaluator en fresh context du tableau des modes d’échec lit ces artefacts pour décider si le travail est « terminé ». Il relève de l’évaluation, pas de l’observabilité ; voir § cycle de vie d’une exécution saine. Il dépend de toutes les surfaces ci-dessus.)

Une stack d’observabilité self-hosted minimale

Pour quelque chose comme market-analyst-agent :

  1. OpenTelemetry Collector avec le GenAI Normalizer Processor (contrib, alpha) pour les attributs GenAI pris en charge. Utilisez les processors génériques Attributes ou Transform pour filtrer ou réécrire les champs gen_ai.*.
  2. Tempo (ou Jaeger) pour les traces, indexées par gen_ai.conversation.id / thread_id.
  3. Loki pour les entrées de l’event log structuré.
  4. Prometheus pour gen_ai.client.token.usage, gen_ai.client.operation.duration et gen_ai.client.operation.time_to_first_chunk — les métriques gen_ai.server.* proviennent du model server, vous ne les obtenez donc que si vous hébergez les weights (voir les conventions de métriques GenAI).
  5. Des dashboards Grafana indexés par gen_ai.agent.name et gen_ai.request.model.

Alternatives hébergées (choisissez-en une, pas trois) :

  • LangSmith : intégration LangGraph native ; également cible de déploiement pour Deep Agents Deploy.
  • Braintrust : meilleur choix si la priorité est donnée aux suites de régression eval-first.
  • Arize Phoenix : OSS, natif OTLP (le protocole filaire OpenTelemetry), associé à l’instrumentation OpenInference.
  • Dashboard de tracing d’OpenAI : automatique si vous utilisez l’OpenAI Agents SDK ou son intégration Temporal.
  • Tracing Claude d’Anthropic : pour les sessions exécutées dans Managed Agents.

Il suppose que le nœud LangGraph possède déjà un span OpenTelemetry actif, le thread_id courant et un objet réponse fournisseur usage avec input_tokens et output_tokens ; la configuration du tracer, l’export et le mapping de l’usage propre au fournisseur sont hors du périmètre de l’extrait.

Modèle du debug bundle

Lorsqu’une exécution échoue, le worker devrait déposer /workspaces/${THREAD_ID}/_debug/ contenant les artefacts demandés dans un postmortem :

  • events.jsonl : export depuis l’event store append-only écrit séparément par le harness, incluant les intentions de tools, les résultats, les approbations et les erreurs.
  • checkpoints.jsonl : historique de l’état du graphe provenant de checkpointer.list({"configurable": {"thread_id": ...}}), étiqueté comme checkpoints plutôt que comme event log.
  • last_state.json : StateSnapshot.values depuis le dernier super-step réussi.
  • trace.json : spans exportés en OTLP pour l’exécution ; les métadonnées constituent la base, et tout contenu capturé suit la trace policy.
  • tool_calls.csv : (ts, tool, input_hash, latency_ms, status, error).
  • workspace.tar.zst : le répertoire du workspace ainsi que git diff par rapport au commit initializer.
  • screenshots/*.png : ce que l’agent a vu.
  • PROGRESS.md, feature-list.json et tout autre fichier de progression écrit par l’agent.
  • env.txt : tags d’image, version du modèle, commit SHA du harness.

Ensemble, ces artefacts peuvent fournir à un humain ou à un reviewer agent suffisamment d’éléments pour reconstruire l’échec, à condition que le harness ait écrit l’event store pendant que l’exécution était active. « L’agent s’est bloqué » est vague. Un rapport illustratif est concret : la session s_123 a consacré 71 % de ses tokens à répéter trois commandes après l’échec de npm install.

Choisir la bonne forme : guide de décision

La plupart de la comparaison précédente se résume à quelques décisions.

Commencer par la durée d’exécution

Utilisez la durée d’exécution comme premier filtre :

  • Moins de 30 secondes, idempotent : SDK limité au cycle de vie de la requête dans un app server.
  • De 30 s à 60 min : queue + worker + checkpoint DB.
  • De 60 min à 24 h : même queue + worker, ou Cloud Run Job pour un travail one-shot. Utilisez un moteur de workflow durable si vous avez également besoin de versioning et de replay.
  • Plus de 24 h, avec obligation de survivre aux déploiements : moteur de workflow durable (style Temporal). Cloud Run Jobs peut héberger un travail long jusqu’à sa limite de tâche, mais ne fournit pas de sémantique de replay.
  • Boucles de reinforcement learning sur plusieurs jours : K8s Job + volume + Temporal.

Après ce filtre grossier, vérifiez les side effects, la récupération, le replay, l’isolation, la localisation des données et l’équipe qui opérera le système.

Adéquation de la plateforme selon le cas d’usage

La matrice est dense, et aucune cellule verte ne suffit à décider de l’architecture ; ce sont généralement les cellules conditionnelles, dans lesquelles une plateforme ne prend en charge quelque chose qu’avec une réserve, qui déterminent le choix. Une couverture large des workloads est utile, mais elle ne montre ni la résidence des données, ni la sémantique de replay, ni la dépendance au fournisseur, ni la maturité opérationnelle, ni le coût du déplacement ultérieur de l’état.

Les cellules conditionnelles appliquent la même règle à toutes les plateformes. Les options AWS/VPC et GPU de Deep Agents dépendent d’un déploiement hybride ou d’un sandbox provider ; Managed Agents peut utiliser une exécution opérée par le client tout en conservant une orchestration hébergée. La ligne consacrée au choix de sandbox inclut une intégration avec un fournisseur externe que vous construisez sur un runtime possédé ou que vous configurez dans un harness managé. Elle ne promet pas un snapshot de l’état en cours d’exécution. Un Kubernetes Job nécessite également une couche API ou queue pour une requête interactive ; terminer rapidement n’en fait pas un service HTTP. Comparez l’accès réseau, le hardware, la récupération et le chemin d’export de l’état du déploiement choisi avant de trancher. La ligne relative au code du harness concerne l’accès à l’implémentation de la boucle, et non la portabilité d’un déploiement managé ou de son état. L’exécution GPU sur Kubernetes nécessite également des nœuds GPU, des drivers et un device plugin.

Managed Agents nécessite Claude et une orchestration opérée par Anthropic. Sa sandbox self-hosted optionnelle peut convenir à une exécution sur réseau privé, mais l’obligation de self-hoster l’inférence ou le control plane l’exclut. Examinez les entrées des tools, les résultats, les skills et la mémoire susceptibles de franchir cette frontière. Un travail de code interne peut convenir lorsque ces flux de données sont acceptables et que l’équipe souhaite déléguer l’exploitation du harness.

La tarification mérite d’être modélisée avant l’engagement, pas après. La ligne des heures-session est de $0.08/heure, en plus du coût standard des tokens. Si une seule session fonctionnait en continu, cela représenterait environ $58/mois par session. Avec 100 sessions fonctionnant en continu, cela représenterait environ $5 800/mois avant les tokens. Multipliez $0.08 par le nombre d’heures-session concurrentes attendu, ajoutez ce montant à votre facture de tokens et comparez-le au coût d’une stack queue + worker sur votre propre infrastructure. Quitter Managed Agents plus tard est un exercice de re-platforming, pas un changement de configuration.

Harness hébergé ou harness possédé

La distinction porte ici sur l’opérateur du harness, et non sur l’auteur de son code. Hébergé signifie que le fournisseur exécute la boucle du harness dans son infrastructure et que vous appelez une API. Possédé signifie que vous exécutez la boucle dans votre propre infrastructure, même si le code du harness provient d’un fournisseur.

LangChain apparaît des deux côtés de cette ligne, ce qui prête à confusion. La société fournit LangGraph, une bibliothèque sous licence MIT que vous self-hostez (possédée), et Deep Agents Deploy, un produit managé qui exécute un harness Deep Agents sur LangSmith Deployment dans son mode cloud par défaut (hébergé). Même entreprise, deux modèles opérationnels différents. Le choix porte sur l’opérateur de la boucle, et non sur le logo de la bibliothèque. (Deep Agents Deploy possède également un mode self-hosted pour les équipes qui souhaitent l’ergonomie du harness sans le composant cloud ; ce mode relève de la catégorie possédée.)

Choisissez un harness hébergé lorsque la prise en charge des modèles, la frontière de données, le comportement de récupération et les points d’extension correspondent déjà à vos besoins. Choisissez un harness possédé lorsque ces contraintes sont des exigences dont vous prévoyez l’évolution. La migration entre les deux modifie l’état, l’observabilité et les frontières d’exécution ; testez donc le chemin de sortie avant que les données de production n’en dépendent.

Sandbox hébergée ou environnement d’exécution possédé

Choisissez une sandbox hébergée lorsque les sémantiques d’isolation, de pause/reprise ou de fork du fournisseur correspondent au threat model et au budget de démarrage. Docker ou Fargate peuvent convenir à des workloads internes de confiance qui nécessitent un accès VPC ou une résidence stricte des données, mais un container standard ne constitue pas une frontière suffisante pour du code hostile. La partie 4 présente les options d’isolation dans ce cas.

Stores d’état : Git, DB et object storage côte à côte

Les agents longue durée utilisent généralement trois state stores à la fois, car chacun possède un artefact différent.

Git stocke l’état du workspace : le code, les documents et les fichiers de progression modifiés par l’agent. Chaque commit fournit au harness un point de récupération stable et à la session suivante un historique compact.

La base de données des checkpoints stocke l’état du graphe : ce qui a été décidé, les nœuds exécutés, les résultats renvoyés et ce qui doit s’exécuter ensuite. L’artefact store contient les sorties finales volumineuses telles que les PDF, les fichiers Parquet et les screenshots. Ces artefacts n’ont pas leur place dans Git ni dans la base de données des checkpoints.

Quand utiliser Git comme état

Utilisez Git lorsque le workload est de nature code (modifications multi-fichiers, refactoring, génération d’application) ou suffisamment proche d’un document pour que l’historique des fichiers soit important. Le modèle est simple : créez une branche d’exécution, faites un commit initializer, puis commitez aux frontières importantes : après la configuration, après chaque feature, après la réussite des tests et après le nettoyage final. Stockez le SHA du dernier commit du workspace à côté de la ligne du checkpoint. À la reprise, le worker suivant checkout la branche, lit git log --oneline -8, inspecte git status et le dernier diff, puis lit PROGRESS.md ou tout fichier de handoff écrit par la session précédente.

Git devient ainsi une surface de récupération pour l’artefact en cours de modification, et non un remplacement de la checkpoint DB. Git peut répondre à deux questions : qu’est-ce qui a changé et quelle version a passé les tests ? Il ne peut pas indiquer au harness quel nœud du graphe doit s’exécuter ensuite, quel tool call attend une approbation ou quel retry a déjà utilisé sa clé d’idempotence. Le harness d’Anthropic utilise des commits initializer et des commits par feature comme source de vérité pour la récupération du workspace ; le modèle lit git log --oneline -8 pour récupérer l’état. Ignorez Git lorsque le produit est une réponse conversationnelle unique. La surcharge ne se justifie pas.

Quand utiliser le checkpointing en DB

Utilisez un checkpointing de type PostgresSaver lorsque l’agent possède une structure de graphe avec plusieurs nœuds dont l’état intermédiaire est important (planner → researcher → writer → verifier). Le dépôt de référence l’utilise précisément pour cette raison. Ne placez pas d’artefacts de workspace à l’échelle du téraoctet dans le checkpoint ; utilisez l’object storage.

Quand utiliser un artifact store (S3 / GCS)

Utilisez l’object storage lorsque :

  • la sortie est plus volumineuse que ce que la base de données des checkpoints devrait transporter ;
  • les consommateurs en aval ont besoin d’un artefact adressable par URL sans passer par l’agent ; ou
  • le livrable et l’état de l’exécution ont des fenêtres de rétention différentes.

Vous pouvez par exemple supprimer le log de session après 30 jours tout en conservant le rapport final pendant des années. Structurez les clés par (thread_id, checkpoint_id, artifact_name) afin que l’exécution productrice reste reconstructible.

Quand demander une approbation humaine

Définissez les exigences d’approbation selon le risque de l’action, l’autorité déjà accordée et la policy de déploiement. Une écriture réversible dans une base de données de brouillons diffère d’un débit client ou d’une modification destructive en production. Lorsqu’une approbation est requise, affichez l’action réelle, ses arguments et sa destination, persistez la décision et revérifiez-la si l’appel proposé change ; n’exécutez pas un appel rejeté. Le interrupt() de LangGraph et le middleware d’approbation de Deep Agents peuvent mettre l’exécution en pause pour cette décision. La partie 4 explique pourquoi il s’agit d’une décision de permission, et non d’une instruction de prompt.

Checklist pratique de production

Avant de mettre en production un agent longue durée, répondez concrètement aux questions suivantes en termes d’infrastructure.

  1. Quel store possède les événements de session et les checkpoints ?
  2. Que se passe-t-il si le worker meurt au milieu d’un tool call ?
  3. Une exécution peut-elle corrompre le workspace d’une autre ?
  4. Quelles actions nécessitent une approbation ?
  5. Le modèle ou la sandbox peuvent-ils lire les credentials bruts ?
  6. Quels tool calls peuvent être retentés sans risque ?
  7. Où le plafond de coût par exécution est-il appliqué ?
  8. Quelle preuve déterministe décide de la fin, et quels critères restants nécessitent un reviewer ?
  9. Où les sorties finales vivent-elles une fois la sandbox supprimée ?
  10. Pourrons-nous expliquer demain une exécution échouée sans la relancer ?

Si la réponse à l’une de ces questions est « le prompt dit à l’agent de faire attention », le système n’est pas encore déployé. Ce n’est encore qu’une démo.
