Utilisation d’outils par les AI agents en 2026 : MCP, CLI, Skills et exécution de code

Part 3 de la série Engineering the Agentic Stack

Part 1 a couvert les reasoning loops, et Part 2 a couvert la mémoire. Cet article ajoute la couche d’action : comment un agent expose, sélectionne et exécute des outils.

L’histoire du tooling a changé en 2025–2026. MCP a donné aux fournisseurs un protocole commun pour les services externes. Les agents qui exécutent du code ont montré qu’un modèle peut parfois composer un petit programme plus efficacement que d’émettre une longue séquence d’appels JSON. Anthropic a rapporté une réduction de 98,7% de tokens pour un workflow d’analyse de dépenses, et l’article CodeAct rapporte des gains allant jusqu’à 20% sur sa configuration de benchmark. Ces résultats décrivent leurs tâches et leurs harnesses, pas un avantage universel de l’exécution de code.

Je compare l’appel d’outils en JSON, MCP, les Skills, les outils CLI, et l’exécution de code dans cet ordre. La dernière section applique les principes de design de l’Agent-Computer Interface (ACI) au Market Analyst Agent.

TL;DR : Cinq patterns d’interface utiles couvrent la plupart des usages d’outils par les agents. Les Skills portent des instructions, les outils CLI conviennent au développement local, MCP connecte des services partagés, et l’exécution de code compose un travail multi-étapes à l’intérieur d’un sandbox. L’appel d’outils en JSON reste le choix le plus simple pour des actions atomiques. Quel que soit le protocole, l’Agent-Computer Interface (ACI) doit rendre les actions explicites, garder le feedback compact, et permettre une récupération des erreurs.

Cinq façons pour les AI agents d’utiliser des outils

Dans Part 1, le reasoning loop choisissait l’étape suivante. Part 2 a stocké l’état nécessaire pour reprendre. La frontière de l’outil transforme cette décision en une action et renvoie une observation au loop. Ces cinq patterns font des compromis différents en coût de tokens, flexibilité et enforcement.

1. Appel d’outils en JSON : le baseline

Le pattern initial : vous définissez des tool schemas en JSON, le LLM émet des function calls structurées, votre code les exécute. C’est bien compris et ça marche très bien pour de petits ensembles d’outils.

# Traditional tool definition — each tool consumes ~550-1,400 tokens (Apideck benchmark)
tools = [
    {
        "name": "get_stock_price",
        "description": "Get the current stock price for a ticker symbol",
        "input_schema": {
            "type": "object",
            "properties": {
                "ticker": {"type": "string", "description": "Stock ticker (e.g., NVDA)"}
            },
            "required": ["ticker"]
        }
    }
]

À 5–10 outils, l’overhead est acceptable. Le problème, c’est l’échelle : chaque définition d’outil coûte 550-1,400 tokens. À 20 outils, vous dépensez 15–25K tokens avant même que l’agent commence à raisonner.

2. MCP pour des intégrations partagées

Model Context Protocol est le standard sur lequel la plupart des fournisseurs ont convergé. Anthropic l’a donné à la Linux Foundation en décembre 2025, au sein de l’Agentic AI Foundation (AAIF) qu’elle a cofondée avec OpenAI et Block. Google, Microsoft et AWS soutiennent la fondation en tant que membres platinum. OpenAI a ajouté le support MCP dans son Responses API. Il y a désormais 10,000+ serveurs MCP actifs et 97M+ téléchargements mensuels de SDK.

MCP s’adapte aux intégrations SaaS multi-fournisseurs (Figma, Notion, Salesforce), aux services qui n’ont pas d’équivalent CLI, et aux environnements nécessitant une orchestration OAuth. Sa valeur réside dans une couche partagée de discovery et de transport. La gouvernance dépend encore de l’authentification, l’autorisation, la journalisation (logging) et les contrôles de déploiement du serveur.

L’histoire en production est plus complexe que ne le suggèrent les chiffres du headline.

La surface de sécurité est le premier problème. Le Vulnerable MCP Project recense 50 vulnérabilités sur des serveurs MCP, dont 13 classées Critical, proposées par 32 chercheurs en sécurité. Les classes d’attaque couvrent l’injection de prompt, les échecs de validation d’entrée, les lacunes d’authentification, et des failles de sécurité réseau. Le premier serveur MCP malveillant observé en situation réelle a fait son apparition en septembre 2025 : un package appelé postmark-mcp qui BCC’d chaque email sortant vers l’adresse d’un attaquant, en impactant environ 300–500 organisations avant la découverte.

L’empoisonnement d’outils (tool poisoning) est la classe d’attaque qui m’inquiète le plus. Invariant Labs a démontré que des outils MCP empoisonnés peuvent exfiltrer des données même lorsqu’ils ne sont jamais invoqués. Le modèle n’a qu’à lire les métadonnées de l’outil pour déclencher l’attaque. MCPTox benchmarks testant 20 LLM agents contre 45 serveurs MCP réels a trouvé des taux de succès d’attaque allant jusqu’à 72.8%.

L’overhead de tokens est le problème opérationnel. Une équipe faisant tourner des serveurs MCP pour GitHub, Slack et Sentry (~40 outils au total) a trouvé 55,000 tokens de définitions de schema injectées avant que l’utilisateur ne demande quoi que ce soit. Une autre rapporte 143,000 tokens sur 200,000 disponibles (72%) consommés uniquement par les définitions d’outils.

Anthropic a rapporté une réduction de schema de 85% via son Tool Search Tool et une réduction de 96% lors du chargement de trois à cinq outils pertinents pour les tâches évaluées. Le chargement sélectif préserve la surface du protocole tout en retirant les schemas que la requête actuelle n’a pas besoin.

3. Skills : l’expertise, pas l’exécution

La fin 2025 a apporté la standardisation des agent skills comme un format open (lancé en octobre 2025, publié comme standard open en décembre 2025). Les outils fournissent des capacités (ce que les agents peuvent faire), et les skills fournissent l’expertise (ce que les agents savent sur la façon d’accomplir des tâches complexes).

Le standard SKILL.md définit une skill comme un fichier markdown avec YAML frontmatter :

---
name: deploy
description: Deploy the application to production
argument-hint: "[environment]"
user-invocable: true
---
Deploy the application to the $0 environment (default: staging).
Steps:
1. Run the test suite
2. Build the production bundle
3. Deploy using the deploy script
4. Verify the deployment health check

Les Skills utilisent progressive disclosure. Environ 100 tokens de métadonnées se chargent au démarrage ; les instructions complètes ne se chargent que quand la skill est active. Comparez avec le ~55,000 tokens que ~40 outils MCP peuvent consommer avant que le reasoning ne commence.

En mars 2026, Claude Code, OpenAI Codex CLI, Cursor, GitHub Copilot, Gemini CLI, Goose, Windsurf et Roo Code avaient adopté le format. Victor Dibia décrit cette transition vers des actions d’agents pilotées par le code.

Utilisez les skills pour la connaissance métier, les procédures multi-étapes, et le travail récurrent comme les migrations de base de données ou les intégrations de paiement. Elles correspondent aux tâches où l’agent a besoin d’instructions sur comment utiliser une capacité existante.

4. CLI et outils shell

Les interfaces CLI peuvent être beaucoup moins coûteuses en contexte lorsque le modèle connaît déjà la commande. Scalekit a rapporté un écart de 4-32x de tokens entre ses chemins CLI et MCP sur 75 exécutions. Cette étude de cas mesure ses outils et ses tâches ; elle ne remplace pas une comparaison sur vos propres manifests et sorties de commande.

Des commandes largement documentées telles que git, docker, kubectl, gh, curl et jq ont souvent besoin de peu de texte de schema introductif. Les CLIs moins courantes ou internes ont encore besoin d’une aide découvrable, d’exemples, et d’une sortie stable lisible par machine.

Le guide d’Ugo Enyioha “Writing CLI Tools That AI Agents Actually Want to Use” a formalisé huit règles de design :

  1. La sortie structurée est obligatoire — supportez --json
  2. Les exit codes pilotent le flux — utilisez des codes distincts pour différents types d’erreur
  3. Les commandes doivent être idempotentes
  4. Auto-documentées --help avec des exemples réalistes
  5. Design pour la composabilité — --quiet pour les valeurs nues, support stdin
  6. Fournissez des flags --dry-run et --yes
  7. Supportez l’inspection de version
  8. Gérez l’auth via des variables d’environnement

La CLI manque de la type safety de MCP, de l’orchestration OAuth intégrée, de la discovery d’outils, et de l’audit trail. Le pattern vers lequel je vois la plupart des équipes converger : CLI par défaut pour le développement et les opérations locales, MCP pour l’intégration de services externes et la gouvernance enterprise.

5. Exécution de code pour du travail multi-étapes

C’est le changement dans le tooling des agents que je trouve le plus déterminant. Au lieu d’émettre du JSON structuré pour invoquer des fonctions pré-définies une par une, l’agent écrit un script Python ou bash. Le script appelle plusieurs outils, traite les résultats avec des boucles et des conditionnels, et ne renvoie qu’un résumé final dans le contexte de l’agent.

Anthropic l’a formalisé avec Programmatic Tool Calling (PTC), désormais GA dans l’API Claude. Le socle académique est le CodeAct paper (Wang et al., ICML 2024), qui a testé sur 17 LLM et a trouvé que les actions de code atteignent jusqu’à 20% de taux de succès supérieurs et 30% d’étapes en moins par rapport aux alternatives en JSON.

Trois études de cas first-party montrent où le pattern peut aider : Vercel et Cloudflare en premier, puis l’exemple d’analyse de dépenses d’Anthropic. Traitez-les comme des preuves côté fournisseur et relancez la comparaison sur vos propres tâches.

  • Vercel a reconstruit leur agent d0 text-to-SQL en supprimant 80% de ses outils (de 15 à 2 : ExecuteCommand et ExecuteSQL). Le succès de la tâche a grimpé de 80% à 100%, le temps d’exécution a baissé de 3,5x, et l’usage de tokens a chuté de 40%. Leur formulation : “Les meilleurs agents sont peut-être ceux qui ont le moins d’outils.”

  • Cloudflare a développé “Code Mode,” permettant aux agents d’écrire du TypeScript pour appeler leur API plutôt que de définir des tool schemas, ce qui réduit l’overhead de contexte. Leur raisonnement : “Les LLM ont une quantité énorme de TypeScript du monde réel dans leurs jeux d’entraînement, mais seulement un petit ensemble d’exemples artificiels de tool calls.”

Voici le pattern depuis la documentation PTC d’Anthropic. Pour l’analyse de dépenses, l’appel d’outils traditionnel nécessite 20+ passes d’inférence séparées, une par membre de l’équipe, avec toutes les données intermédiaires qui transitent par le contexte. Un workflow consommant ~150,000 tokens avec des tool calls directs a été réimplémenté pour ~2,000 tokens, soit une réduction de 98,7%. Avec l’exécution de code, l’agent écrit un script unique :

# Agent generates this code, executes in sandbox
import json
members = get_team_members("engineering")
over_budget = []
for m in members:
    expenses = get_expenses(m["id"], "Q3")
    total = sum(e["amount"] for e in expenses)
    if total > 5000:
        custom = get_custom_budget(m["id"])
        limit = custom["limit"] if custom else 5000
        if total > limit:
            over_budget.append({"name": m["name"], "spent": total, "limit": limit})
# Only this final summary returns to the LLM context
print(json.dumps(over_budget))

Le LLM ne voit que le résumé JSON final, pas les milliers de lignes de dépenses traitées dans le sandbox. Le gain évident est l’efficacité en tokens. Les boucles et conditionnels coûtent “gratuitement”, les erreurs passent par try/except au lieu d’un reasoning en langage naturel sur des échecs, et les données sensibles restent dans le sandbox.

Quand l’appel d’outils en JSON reste pertinent : opérations atomiques uniques, environnements sans infrastructure de sandboxing, modèles plus petits avec une génération de code faible, ou exigences d’audit qui imposent de logger chaque invocation d’outil.

L’Agent-Computer Interface (ACI) pour les tool d’AI agents

Le terme “Agent-Computer Interface” (ACI) a été inventé par John Yang, Carlos E. Jimenez et leurs collègues à Princeton dans leur SWE-agent paper (NeurIPS 2024). Comme les humains bénéficient d’interfaces bien conçues (HCI), l’article soutient que les LM agents sont “une nouvelle catégorie de terminaux utilisateurs avec leurs propres besoins et capacités, et bénéficieraient d’interfaces spécialement construites.”

Leurs résultats d’ablation donnent un chiffre. SWE-agent avec sa ACI complète atteint 18,0% sur SWE-bench Lite contre 7,3% avec seulement un shell Linux standard : +10,7 points de pourcentage grâce au design d’interface seul. La barrière “linting” par elle-même explique 3 points : 51,7% des modifications de l’agent contenaient au moins une erreur détectée par le linter avant de pouvoir se propager.

Anthropic a adopté ACI comme concept fondamental dans leur guide “Building Effective Agents”, en le listant comme l’un des trois principes clés : “Craft carefully your agent-computer interface through thorough tool documentation and testing.” Leur conseil pratique : “Une règle de pouce consiste à penser à l’effort nécessaire pour les interfaces humain-machine, et à planifier d’investir autant d’effort pour créer de bonnes agent-computer interfaces.”

Quatre principes ACI en pratique

1. Les actions doivent être simples et faciles à comprendre. La faute la plus courante consiste à encapsuler des endpoints d’API un-à-un. Au lieu de list_users, list_events, create_event, implémentez schedule_event qui trouve la disponibilité et planifie en un seul appel. Au lieu de read_logs, implémentez search_logs qui renvoie uniquement les lignes pertinentes avec le contexte.

2. Les actions doivent être compactes et efficaces. Consolidez les opérations importantes en un minimum d’actions. Dans le Market Analyst Agent, je combine la récupération du prix avec des métriques de base dans un seul outil get_stock_snapshot, plutôt que d’exiger des appels séparés pour le prix, le volume, la market cap et le ratio PE.

3. Le feedback de l’environnement doit être informatif mais concis. Évitez de renvoyer du HTML brut ou des payloads d’API complets. Résolvez des IDs cryptiques vers des noms sémantiques. Les tests d’Anthropic ont ajouté un response_format enum pour que l’agent demande soit une réponse concise (~72 tokens), soit une réponse détaillée (~206 tokens), soit environ un facteur 3 sur le coût en tokens. Ils ont rapporté de meilleures performances en conditions réelles.

4. Les garde-fous doivent limiter la propagation des erreurs. La détection automatique d’erreurs aide les agents à reconnaître et corriger rapidement leurs erreurs. Dans SWE-agent, un éditeur de fichiers personnalisé avec linting intégré rejette automatiquement les erreurs de syntaxe, en détectant au moins une erreur dans 51,7% des modifications de l’agent avant qu’elles ne puissent s’aggraver. J’applique le même principe dans le Market Analyst Agent en validant les arguments des outils via des schemas Pydantic avant exécution :

from pydantic import BaseModel, Field, field_validator

class StockQuery(BaseModel):
    """Validated input for stock queries.

    Pydantic catches malformed tickers before the API call,
    preventing error propagation through the reasoning loop.
    """
    ticker: str = Field(description="Stock ticker symbol (e.g., NVDA)")
    period: str = Field(default="1mo", description="Time period: 1d, 5d, 1mo, 3mo, 1y")

    @field_validator("ticker")
    @classmethod
    def validate_ticker(cls, v: str) -> str:
        v = v.upper().strip()
        if not v.isalpha() or len(v) > 5:
            raise ValueError(f"Invalid ticker format: {v}")
        return v

    @field_validator("period")
    @classmethod
    def validate_period(cls, v: str) -> str:
        valid = {"1d", "5d", "1mo", "3mo", "6mo", "1y", "5y"}
        if v not in valid:
            raise ValueError(f"Invalid period: {v}. Must be one of {valid}")
        return v

Patterns de design d’outils pour AI agents qui fonctionnent

Le guide d’Anthropic “Writing effective tools for agents” présente les outils comme “un nouveau type de logiciel reflétant un contrat entre des systèmes déterministes et des agents non-déterministes.”

Considérez les descriptions d’outils comme du prompt engineering

Les descriptions devraient utiliser au moins 3–4+ phrases, en couvrant quand utiliser l’outil, les paramètres requis vs optionnels, le format de sortie, et les cas limites. Le namespacing via des préfixes (asana_search, jira_search) a “des effets non triviaux” sur la précision de sélection des outils. Dans les expériences d’Anthropic, des descriptions d’outils optimisées pour Claude ont surpassé des descriptions rédigées par des experts humains sur des benchmarks d’évaluation.

# Bad: vague, no context for when to use
tools = [{
    "name": "search",
    "description": "Search for items",
}]

# Good: specific, with input examples and edge cases
tools = [{
    "name": "stock_search_news",
    "description": (
        "Search for recent news articles about a specific stock or company. "
        "Use this tool when the user asks about recent events, earnings, "
        "announcements, or market-moving news for a specific ticker. "
        "Returns up to 10 articles sorted by relevance. "
        "For broad market news (not ticker-specific), use market_overview instead."
    ),
    "input_schema": {
        "type": "object",
        "properties": {
            "query": {
                "type": "string",
                "description": "Search query. Examples: 'NVDA earnings Q3 2025', 'Tesla delivery numbers'"
            },
            "max_results": {
                "type": "integer",
                "description": "Max articles to return (1-10, default 5)",
                "default": 5
            }
        },
        "required": ["query"]
    }
}]

Des tests internes ont montré que les exemples d’entrée (input_examples field) améliorent substantiellement la précision sur la gestion de paramètres complexes.

Renvoyer une sortie riche en signal et lisible par machine

Évitez les identifiants bas-niveau (uuid, mime_type). Résolvez des IDs cryptiques vers des noms sémantiques. Structurez la réponse pour que l’agent puisse raisonner dessus sans devoir parser du boilerplate :

# Bad: raw API response dumped to agent
def get_stock_price(ticker: str) -> dict:
    response = api.get(f"/v1/quotes/{ticker}")
    return response.json()  # 500+ tokens of nested JSON

# Good: high-signal summary the agent can immediately reason about
def get_stock_price(ticker: str) -> dict:
    data = api.get(f"/v1/quotes/{ticker}").json()
    return {
        "ticker": ticker,
        "price": data["regularMarketPrice"],
        "change_pct": round(data["regularMarketChangePercent"], 2),
        "volume": data["regularMarketVolume"],
        "market_cap_b": round(data["marketCap"] / 1e9, 1),
        "pe_ratio": data.get("trailingPE"),
        "summary": f"{ticker} at ${data['regularMarketPrice']:.2f} "
                   f"({'up' if data['regularMarketChangePercent'] > 0 else 'down'} "
                   f"{abs(data['regularMarketChangePercent']):.1f}%)"
    }

Renvoyer des erreurs sur lesquelles la boucle peut agir

Utilisez quatre mécanismes séparés, car ils gèrent différents types de pannes :

  1. Retry avec exponential backoff pour les erreurs transitoires
  2. Chaînes de fallback de modèle en cas d’outage du provider
  3. Routage par classification d’erreurs — erreurs transitoires : retry ; erreurs récupérables par le LLM : retour à l’agent avec du contexte ; erreurs nécessitant un humain : escalade
  4. Récupération via checkpoint en cas de crash

Le guide d’Anthropic cité soutient des erreurs d’outils claires et un design d’outils piloté par l’évaluation. Il n’établit pas une réduction universelle du taux d’échec ; mesurez donc le taux de recovery, les retries et l’escalade sur votre propre suite de tâches.

from tenacity import retry, stop_after_attempt, wait_exponential

@retry(
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=1, min=2, max=10),
)
def call_stock_api(ticker: str) -> dict:
    """Fetch stock data with automatic retry on transient failures.

    Layer 1: Exponential backoff handles rate limits and network blips.
    If all retries fail, the error propagates to the agent with
    enough context to decide whether to try a different approach.
    """
    response = httpx.get(
        f"https://api.example.com/v1/quotes/{ticker}",
        timeout=10.0,
    )
    response.raise_for_status()
    return response.json()

Appliquer les patterns au Market Analyst Agent

Le Market Analyst Agent de Part 1 rend l’effet de l’interface visible.

Consolidation des outils

L’article de Part 1 montre la surface simplifiée à 5 outils après ce refactor. Avant ce nettoyage, le design original avait 10+ outils : get_stock_price, get_company_metrics, get_market_cap, get_pe_ratio, get_volume, etc. Chacun était un wrapper fin autour d’un seul endpoint d’API. L’agent devait raisonner sur la combinaison à appeler pour chaque requête.

Je les ai consolidés en 5 outils de haut niveau, en suivant le principe ACI d’actions compactes et efficaces :

Cette coupe réduit l’overhead du tool schema et rend la sélection d’outils par l’agent plus fiable, car il y a moins de choix ambigus à faire.

Sorties structurées pour les résultats d’outils

Chaque outil du Market Analyst Agent renvoie une réponse validée par Pydantic. Cela applique le principe de guardrails ACI à la frontière de l’outil :

class StockSnapshot(BaseModel):
    """Structured tool response — the agent never sees raw API noise."""
    ticker: str
    price: float
    change_pct: float
    volume: int
    market_cap_b: float
    pe_ratio: float | None
    summary: str  # Human-readable one-liner for direct use in reports

class NewsResult(BaseModel):
    """Each news item is pre-processed for agent consumption."""
    headline: str
    source: str
    date: str
    relevance_score: float  # Pre-ranked so the agent doesn't waste tokens sorting
    key_points: list[str]  # Extracted by the tool, not the agent

Le champ summary est celui qui compte le plus. Il fournit à l’agent une string prête à l’emploi, directement intégrable dans un rapport sans traitement additionnel. Les key_points dans NewsResult sont extraits côté serveur, ce qui évite à l’agent de dépenser des tokens d’inférence pour parser le corps des articles.

Compromis et considérations

Au-delà des caveats propres à chaque modalité cités plus haut, quelques préoccupations transverses orientent le choix :

  • Le coût opérationnel varie selon la dimension. L’exécution de code économise des tokens, mais ajoute une latence de cold-start côté sandbox. MCP économise du temps de développement pour les intégrations SaaS, mais ajoute de la charge de déploiement serveur. CLI est gratuite pour démarrer, mais plus difficile à gouverner à grande échelle. Optimisez pour votre goulot réel : coût en tokens, latence, ou complexité opérationnelle.

  • Les compétences d’équipe comptent. L’exécution de code suppose que vos agents (et les modèles derrière eux) savent générer du Python ou du TypeScript de façon fiable. La CLI suppose une familiarité avec les conventions Unix. MCP requiert de comprendre les protocoles de transport et les flows OAuth. Faites correspondre la modalité aux forces de votre équipe.

  • La consolidation des outils peut aller trop loin. Si un seul outil accumule des modes et des arguments sans rapport, l’agent fait face à un problème de sélection différent dans le schema. Utilisez des évaluations de sélection d’outils et de task-success pour trouver la surface pertinente pour votre charge de travail.

  • Les Skills sont prompt-based, pas enforced. Une skill est une instruction que l’agent devrait suivre, pas un guardrail qu’il doit suivre. Pour les workflows critiques, combinez skills avec une validation déterministe.

  • Les exigences d’audit structurent le choix. Si vous avez besoin d’un log complet de chaque tool invocation et de son résultat, MCP et l’appel d’outils en JSON fournissent une traçabilité structurée out of the box. L’exécution de code produit un script et sa sortie : utile, mais plus difficile à décomposer en actions individuelles pour des rapports de conformité.

Sélection d’outils à plus grande échelle

Trois directions valent la peine d’être suivies.

La première est Tool RAG pour scaler la sélection. Quand les toolsets grossissent jusqu’à des centaines voire des milliers, la précision naïve de sélection d’outils chute à 13,62%. Le RAG-MCP paper a appliqué retrieval-augmented generation à la sélection d’outils : indexez les descriptions d’outils dans une base vectorielle et ne récupérez que les plus pertinentes par requête. On atteint 43,13% d’exactitude, soit une amélioration de 3,2x, tout en coupant les prompt tokens d’environ ~50%.

La seconde est la création d’outils par les agents eux-mêmes. Le LATM framework (“LLMs As Tool Makers”) a établi un paradigme en deux phases : un LLM puissant crée des fonctions Python réutilisables, et un LLM léger les utilise. ToolMaker (ACL 2025) transforme de façon autonome des dépôts GitHub en outils compatibles LLM avec un taux de succès de 80%. Les deux pointent au-delà de l’usage d’outils vers la création d’outils, puis vers la gestion d’une bibliothèque d’outils générés.

La troisième est la stack dual-protocol A2A + MCP. Le protocole Agent2Agent Protocol (A2A) de Google aborde ce que MCP ne fait pas : la communication entre agents. MCP gère l’intégration agent-to-tool ; A2A gère la découverte agent-to-agent, la négociation et la délégation de tâches.

Points clés

  1. Choisissez l’interface en fonction de l’action : appel JSON pour des opérations typées petites, MCP pour des services partagés, Skills pour des procédures, CLI pour des commandes établies, et du code “sandboxed” pour la composition locale.
  2. Attachez les conditions de benchmark au résultat. CodeAct, Anthropic, Vercel, Cloudflare, Apideck et Scalekit ont mesuré différents modèles, tâches, outils et harnesses.
  3. La qualité ACI survit aux changements de protocole. Des actions claires, un feedback compact, de la validation et des erreurs utiles aident toutes les modalités.
  4. Consolidez les outils qui se recouvrent seulement quand les évaluations montrent que la surface plus petite améliore la sélection ou le task success.
  5. La sécurité suit la puissance d’exécution. Les interfaces shell et code nécessitent du sandboxing ; MCP nécessite une identité scoped et une politique serveur ; Skills reste des instructions plutôt qu’un enforcement.
