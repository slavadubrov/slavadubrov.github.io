Utilisation des outils par les agents AI : MCP, CLI, Skills et exécution de code

La partie 1 traitait des boucles de raisonnement, et la partie 2 de la mémoire. Cet article ajoute la couche d’action : comment un agent expose, sélectionne et exécute des outils. La mémoire détermine ce que l’agent sait au début d’un tour ; cette couche détermine ce qu’il peut en faire. L’écosystème des outils a changé en 2025–2026. MCP, le Model Context Protocol, a fourni aux éditeurs un moyen commun d’exposer des services externes. Les agents capables d’exécuter du code ont montré qu’un modèle peut parfois composer un petit programme plus efficacement qu’émettre une longue séquence d’appels JSON. Anthropic a rapporté une réduction de 98,7 % du nombre de tokens pour un workflow Google Drive vers Salesforce, et l’article CodeAct a rapporté des gains allant jusqu’à 20 % dans son dispositif de benchmark. Ces résultats décrivent leurs tâches et leurs harnesses, et ne constituent pas un avantage universel de l’exécution de code.

Je compare successivement les tool calls JSON, MCP, Skills, les outils CLI et l’exécution de code. Une section ultérieure applique les principes de conception de l’Agent-Computer Interface (ACI) au Market Analyst Agent, un agent de recherche LangGraph que j’ai construit pour la partie 1 et qui récupère des données de marché avant de rédiger un rapport d’analyste.

Pour une décision rapide concernant les interfaces, consultez AI Agent Tool Interfaces.

En bref : cinq modèles d’interface couvrent la plupart des usages d’outils par les agents. Les Skills portent les instructions, les outils CLI conviennent au développement local, MCP connecte les services partagés et l’exécution de code compose des opérations multi-étapes dans un sandbox. Les tool calls JSON restent le choix le plus simple pour les petites actions atomiques. Quel que soit le protocole, l’Agent-Computer Interface (ACI) doit rendre les actions explicites, les retours compacts et les erreurs récupérables.

Cinq façons dont les agents AI utilisent les outils

Dans la partie 1, la boucle de raisonnement choisissait l’étape suivante. La partie 2 stockait l’état nécessaire pour reprendre son exécution. La frontière des outils se situe entre les deux : elle valide ce que la boucle a proposé, transmet ensuite l’appel pour exécution et renvoie le résultat à la boucle. Ces cinq modèles effectuent des compromis différents en matière de coût en tokens, de flexibilité et de contrôle.

1. Tool calls JSON : la référence

Le modèle d’origine : vous définissez les tool schemas en JSON, le LLM émet des function calls structurés et votre code les exécute. Le fonctionnement est bien compris et convient parfaitement aux petits ensembles d’outils.

# Traditional tool definition — each tool consumes ~550-1,400 tokens (Apideck benchmark)
tools = [
    {
        "name": "get_stock_price",
        "description": "Get the current stock price for a ticker symbol",
        "input_schema": {
            "type": "object",
            "properties": {
                "ticker": {"type": "string", "description": "Stock ticker (e.g., NVDA)"}
            },
            "required": ["ticker"]
        }
    }
]

Avec 5 à 10 outils, la surcharge reste acceptable. Le problème apparaît à l’échelle : chaque définition d’outil coûte 550 à 1 400 tokens. Avec 20 outils, vous dépensez 11 à 28 kTokens avant même que l’agent ne commence à raisonner.

2. MCP pour les intégrations partagées

MCP est le standard vers lequel la plupart des éditeurs ont convergé. Un serveur MCP est un processus qui publie une liste d’outils via un wire protocol défini — stdio pour un processus local, HTTP pour un processus distant. Votre agent exécute un client MCP qui se connecte au serveur, lui demande quels outils sont disponibles, puis lui transmet les appels du modèle ; le même serveur fonctionne donc avec tout client qui parle le protocole. Anthropic a fait don du protocole à la Linux Foundation en décembre 2025, dans le cadre de l’Agentic AI Foundation qu’elle a cofondée avec OpenAI et Block. Google, Microsoft et AWS soutiennent la fondation en tant que membres platinum. OpenAI a ajouté la prise en charge de MCP dans son Responses API. D’après l’annonce du don d’Anthropic en décembre 2025, l’écosystème comptait plus de 10 000 serveurs MCP publics actifs et plus de 97 millions de téléchargements mensuels des SDK, toutes versions Python et TypeScript confondues.

MCP convient aux intégrations SaaS multi-éditeurs (Figma, Notion, Salesforce), aux services dépourvus d’équivalent CLI et aux environnements nécessitant une orchestration OAuth. Sa valeur réside dans une couche commune de découverte et de transport. La gouvernance dépend toujours des contrôles d’authentification, d’autorisation, de journalisation et de déploiement du serveur.

La réalité de la production est plus complexe que ne le laissent entendre ces chiffres.

La surface d’attaque est le premier problème. Le Vulnerable MCP Project recense 50 vulnérabilités dans des serveurs MCP, dont 13 classées Critical, signalées par 32 chercheurs en sécurité. Les classes d’attaque couvrent la prompt injection, les défauts de validation des entrées, les failles d’authentification et les vulnérabilités de sécurité réseau. Le premier serveur MCP malveillant observé dans le monde réel est apparu en septembre 2025 : un package nommé postmark-mcp qui ajoutait l’adresse d’un attaquant en BCC à chaque e-mail sortant, affectant selon les estimations 300 à 500 organisations avant sa découverte.

Le tool poisoning est la classe d’attaque qui m’inquiète le plus. Invariant Labs a démontré que des outils MCP empoisonnés peuvent exfiltrer des données même lorsqu’ils ne sont jamais invoqués. Il suffit que le modèle lise les métadonnées de l’outil pour déclencher l’attaque. Les benchmarks MCPTox, qui ont testé 20 agents LLM contre 45 serveurs MCP réels, ont trouvé des taux de réussite des attaques allant jusqu’à 72,8 %.

La surcharge en tokens est le problème opérationnel. Une équipe exécutant des serveurs MCP pour GitHub, Slack et Sentry (environ 40 outils au total) a constaté que 55 000 tokens de tool schemas étaient injectés avant même qu’un utilisateur ne demande quoi que ce soit. Une autre équipe a signalé que 143 000 des 200 000 tokens disponibles (72 %) étaient consommés par les définitions d’outils seules.

Anthropic a rapporté une réduction de 85 % des tokens consacrés aux définitions d’outils grâce à son Tool Search Tool — environ 77 000 tokens de schemas ramenés à 8 700 — en ne chargeant que les trois à cinq outils réellement nécessaires à une requête. Le chargement sélectif conserve la surface du protocole tout en supprimant les schemas inutiles pour la requête en cours.

Byte says

J’ai connecté des serveurs MCP pour trois services et laissé tous les outils chargés. Les schémas ont mangé la majeure partie de la fenêtre avant même que l’utilisateur écrive. L’agent a utilisé quatre de ces outils.

3. Les Skills encapsulent l’expertise, pas l’exécution

La fin de l’année 2025 a vu la standardisation des agent skills sous la forme d’un format ouvert (lancé en octobre 2025 et publié comme standard ouvert en décembre 2025). Les outils fournissent des capacités — ce que les agents peuvent faire — tandis que les Skills fournissent l’expertise — ce que les agents savent de la manière d’accomplir des tâches complexes.

Le format SKILL.md définit une skill comme un fichier Markdown doté d’un frontmatter YAML. Le standard ouvert impose uniquement name et description ; l’exemple ci-dessous utilise également deux extensions de Claude Code, argument-hint et user-invocable, ainsi que son placeholder d’argument positionnel $0 :

---
name: deploy
description: Deploy the application to production
argument-hint: "[environment]"
user-invocable: true
---
Deploy the application to the $0 environment (default: staging).
Steps:
1. Run the test suite
2. Build the production bundle
3. Deploy using the deploy script
4. Verify the deployment health check

Les Skills utilisent la divulgation progressive. Environ 100 tokens de métadonnées sont chargés au démarrage ; les instructions complètes ne sont chargées que lorsque la skill est active. Comparez cela aux quelque 55 000 tokens que peuvent consommer environ 40 outils MCP avant le début du raisonnement.

En mars 2026, Claude Code, OpenAI Codex CLI, Cursor, GitHub Copilot, Gemini CLI, Goose, Devin Desktop (alors Windsurf) et Roo Code avaient adopté ce format. Les Skills s’inscrivent dans une évolution plus large vers des actions d’agents pilotées par le code, que Victor Dibia retrace depuis les appels de fonctions JSON jusqu’au code généré — le modèle traité dans la section 5.

Utilisez les Skills pour les connaissances métier, les procédures multi-étapes et les tâches récurrentes telles que les migrations de bases de données ou les intégrations de paiement. Elles conviennent aux tâches pour lesquelles l’agent a besoin d’instructions sur la manière d’utiliser une capacité existante.

4. Outils CLI et shell

Les interfaces CLI peuvent être beaucoup moins coûteuses en contexte lorsque le modèle connaît déjà la commande. Scalekit a rapporté une différence de 4 à 32 fois le nombre de tokens entre ses parcours CLI et MCP sur 75 exécutions. Cette étude de cas mesure ses propres outils et tâches ; elle ne remplace pas une comparaison réalisée avec vos propres tool schemas et sorties de commandes.

Les commandes largement documentées telles que git, docker, kubectl, gh, curl et jq nécessitent souvent peu de texte de schema introductif. Les CLI moins courantes ou internes ont toutefois besoin d’une aide découvrable, d’exemples et d’une sortie machine-readable stable.

Le guide d’Ugo Enyioha, “Writing CLI Tools That AI Agents Actually Want to Use”, a codifié huit règles de conception :

  1. La sortie structurée est obligatoire — prendre en charge --json
  2. Les codes de sortie constituent le control flow — utiliser des codes distincts pour les différents types d’erreurs
  3. Les commandes doivent être idempotentes
  4. Auto-documentation --help avec des exemples réalistes
  5. Concevoir pour la composabilité — --quiet pour les valeurs brutes, prise en charge de stdin
  6. Fournir les flags --dry-run et --yes
  7. Prendre en charge l’introspection de version
  8. Gérer l’authentification via des variables d’environnement

La CLI n’offre pas la sécurité de typage de MCP, son orchestration OAuth intégrée, la découverte des outils ni sa piste d’audit. Le modèle vers lequel la plupart des équipes convergent est le suivant : CLI par défaut pour le développement et les opérations locales, MCP pour l’intégration de services externes et la gouvernance d’entreprise.

5. Exécution de code pour les opérations multi-étapes

C’est le changement dans le tooling des agents que je trouve le plus important. Au lieu d’émettre du JSON structuré pour invoquer des fonctions prédéfinies une par une, l’agent écrit un script Python ou bash. Le script appelle plusieurs outils, traite les résultats avec des boucles et des conditions, puis ne renvoie au contexte du modèle que le résumé final.

Anthropic a formalisé ce modèle avec le Programmatic Tool Calling (PTC), désormais généralement disponible dans la Claude API. Le fondement académique est l’article CodeAct (Wang et al., ICML 2024), qui a testé 17 LLMs et constaté que les actions sous forme de code atteignaient des taux de réussite jusqu’à 20 % supérieurs et nécessitaient 30 % d’étapes en moins que les alternatives JSON.

Trois études de cas de première partie montrent où ce modèle peut être utile : Vercel et Cloudflare ci-dessous, puis l’exemple d’analyse de dépenses d’Anthropic. Considérez-les comme des éléments de preuve fournis par les éditeurs et reproduisez la comparaison sur vos propres tâches.

  • Vercel a reconstruit d0, son agent de données en langage naturel vers SQL, en le faisant passer de 15 outils à 2 — ExecuteCommand et ExecuteSQL — soit une réduction de 80 % selon leur article. Sur cinq requêtes représentatives, la réussite est passée de 4/5 à 5/5, le temps d’exécution moyen a été divisé par 3,5 (274,8 s à 77,4 s) et l’utilisation moyenne de tokens a baissé de 37 % (environ 102 k à environ 61 k). Leur formulation : « Les meilleurs agents sont peut-être ceux qui disposent du moins d’outils. »

  • Cloudflare a développé « Code Mode », qui permet aux agents d’écrire du TypeScript pour appeler son API plutôt que de définir des tool schemas, ce qui réduit la surcharge du contexte. Leur raisonnement : « Les LLMs disposent d’une quantité énorme de TypeScript réel dans leurs données d’entraînement, mais seulement d’un petit nombre d’exemples artificiels de tool calls. »

Voici le modèle présenté dans la documentation PTC d’Anthropic. L’appel traditionnel d’outils pour analyser des dépenses nécessite plus de 20 passes d’inférence distinctes, une par membre de l’équipe, toutes les données intermédiaires transitant par le contexte. Anthropic rapporte que le code généré répondant à la même question réduit ce qui atteint le contexte : de 200 Ko de lignes brutes de dépenses — plus de 2 000 lignes — à 1 Ko de résultats. Avec l’exécution de code, l’agent écrit un seul script :

# Agent generates this code, executes in sandbox
import json
members = get_team_members("engineering")
over_budget = []
for m in members:
    expenses = get_expenses(m["id"], "Q3")
    total = sum(e["amount"] for e in expenses)
    if total > 5000:
        custom = get_custom_budget(m["id"])
        limit = custom["limit"] if custom else 5000
        if total > limit:
            over_budget.append({"name": m["name"], "spent": total, "limit": limit})
# Only this final summary returns to the LLM context
print(json.dumps(over_budget))

Le LLM ne voit que le résumé JSON final, et non les milliers de lignes de dépenses traitées dans le sandbox. Le gain ne concerne pas uniquement les rapports de dépenses : le document distinct d’Anthropic sur l’exécution de code donne le chiffre le plus frappant, avec un workflow Google Drive vers Salesforce passant d’environ 150 000 tokens à environ 2 000, soit une réduction de 98,7 %.

L’efficacité en tokens est le gain évident. Les boucles et les conditions sont disponibles gratuitement, les erreurs passent par try/except au lieu de nécessiter un raisonnement en langage naturel sur les échecs, et les données sensibles restent dans le sandbox.

Quand les tool calls JSON restent pertinents : opérations atomiques uniques, environnements sans infrastructure de sandbox, modèles plus petits dont la génération de code est faible, ou exigences d’audit nécessitant la journalisation de chaque invocation d’outil.

L’Agent-Computer Interface (ACI) pour les outils des agents AI

Le terme « Agent-Computer Interface » (ACI) a été forgé par John Yang, Carlos E. Jimenez et leurs collègues de Princeton dans leur article sur SWE-agent (NeurIPS 2024). La qualité des interfaces humaines bénéficie d’une discipline entière — l’interaction humain-machine, ou HCI. L’article soutient que les agents fondés sur des modèles de langage méritent le même traitement : ce sont « une nouvelle catégorie d’utilisateurs finaux, avec leurs propres besoins et capacités, qui bénéficieraient d’interfaces conçues spécialement pour eux ».

Leurs résultats d’ablation donnent une mesure concrète. Avec le même modèle de base GPT-4 Turbo, l’ablation SWE-bench Lite de l’article a atteint 18,0 % avec l’ACI complète de SWE-agent sur 300 tâches, contre 7,3 % dans la condition shell-only sans démonstration détaillée et 11,0 % avec une démonstration. La comparaison montre que l’interface et les conditions de démonstration ont modifié sensiblement les performances dans ce dispositif ; elle n’isole pas la conception de l’interface de toutes les autres différences et ne montre pas que le modèle n’a effectué aucun travail. Dans la même ablation de l’interface, l’activation du linting a fait passer la condition d’édition de 15,0 % à 18,0 % ; sur l’ensemble du jeu de test SWE-bench, 51,7 % des exécutions de SWE-agent ont rencontré au moins une modification rejetée par le linter avant sa propagation.

Anthropic a adopté l’ACI comme concept fondateur dans son guide “Building Effective Agents”, où elle la présente comme l’un des trois principes fondamentaux : « Concevez soigneusement votre interface agent-ordinateur au moyen d’une documentation et de tests approfondis des outils. » Sa recommandation pratique : « Une règle empirique consiste à réfléchir à l’effort consacré aux interfaces humain-machine et à prévoir d’investir autant d’efforts dans la création de bonnes interfaces agent-ordinateur. »

Quatre principes ACI en pratique

1. Les actions doivent être simples et faciles à comprendre. L’erreur la plus fréquente consiste à encapsuler les endpoints d’une API un à un. Au lieu de list_users, list_events et create_event, implémentez schedule_event, qui recherche les disponibilités et planifie le rendez-vous en un seul appel. Au lieu de read_logs, implémentez search_logs, qui ne renvoie que les lignes pertinentes avec leur contexte.

2. Les actions doivent être compactes et efficaces. Regroupez les opérations importantes en un nombre d’actions aussi réduit que possible. Dans le Market Analyst Agent, je combine la récupération des prix et les métriques de base dans un seul outil get_stock_snapshot, plutôt que d’exiger des appels distincts pour le prix, le volume, la capitalisation boursière et le ratio PE.

3. Les retours de l’environnement doivent être informatifs, mais concis. Évitez de renvoyer du HTML brut ou l’intégralité des payloads d’API. Résolvez les identifiants cryptiques en noms sémantiques. Les tests d’Anthropic ont ajouté un enum response_format afin que l’agent puisse demander une réponse concise (environ 72 tokens) ou détaillée (environ 206 tokens), soit une différence d’environ trois fois le coût en tokens.

4. La validation doit limiter la propagation des erreurs. La détection automatique des erreurs aide les agents à reconnaître et corriger rapidement leurs erreurs. Dans SWE-agent, un éditeur de fichiers personnalisé avec linting intégré rejette automatiquement les erreurs de syntaxe — l’étape de validation à l’origine du chiffre de 51,7 % mentionné plus haut. Il s’agit de la validation des entrées et sorties d’un outil, et non du filtrage de contenu autour d’un appel de modèle assuré par les produits de guardrails de la partie 4 ; le même terme est utilisé dans les deux cas. J’applique le même principe au Market Analyst Agent en validant les arguments des outils avec des schemas Pydantic avant l’exécution :

from pydantic import BaseModel, Field, field_validator

class StockQuery(BaseModel):
    """Validated input for stock queries.

    Pydantic catches malformed tickers before the API call,
    preventing error propagation through the reasoning loop.
    """
    ticker: str = Field(description="Stock ticker symbol (e.g., NVDA)")
    period: str = Field(default="1mo", description="Time period: 1d, 5d, 1mo, 3mo, 6mo, 1y")

    @field_validator("ticker")
    @classmethod
    def validate_ticker(cls, v: str) -> str:
        v = v.upper().strip()
        if not v.isalpha() or len(v) > 5:
            raise ValueError(f"Invalid ticker format: {v}")
        return v

    @field_validator("period")
    @classmethod
    def validate_period(cls, v: str) -> str:
        valid = {"1d", "5d", "1mo", "3mo", "6mo", "1y"}
        if v not in valid:
            raise ValueError(f"Invalid period: {v}. Must be one of {valid}")
        return v

Des patterns de conception d’outils pour agents AI qui fonctionnent

Le guide d’Anthropic “Writing effective tools for agents” présente les outils comme « un nouveau type de logiciel qui formalise un contrat entre des systèmes déterministes et des agents non déterministes ».

Traitez les descriptions d’outils comme du prompt engineering

Les descriptions devraient comporter au moins trois ou quatre phrases, couvrant les situations dans lesquelles utiliser l’outil, les paramètres obligatoires et facultatifs, le format de sortie et les cas limites. Anthropic rapporte que le choix entre un namespacing fondé sur des préfixes ou des suffixes (asana_search contre search_asana) a eu des « effets non négligeables » dans ses propres évaluations d’utilisation d’outils. L’étude n’indique pas quel schéma est le meilleur ; testez donc les deux sur votre ensemble d’outils plutôt que de supposer que les préfixes sont supérieurs. Anthropic a également transmis les transcriptions de ses agents d’évaluation à Claude Code et l’a laissé réécrire les outils. Sur des jeux de test de validation, cette boucle a trouvé de nouvelles améliorations, « allant même au-delà de celles obtenues avec des implémentations d’outils réalisées par des experts » — qu’elles aient été écrites par ses chercheurs ou générées par Claude.

# Bad: vague, no context for when to use
tools = [{
    "name": "search",
    "description": "Search for items",
}]

# Good: specific, with input examples and edge cases
tools = [{
    "name": "search_news",
    "description": (
        "Search for recent news articles about a specific stock or company. "
        "Use this tool when the user asks about recent events, earnings, "
        "announcements, or market-moving news for a specific ticker. "
        "Returns up to 10 articles sorted by relevance. "
        "For company competitors rather than news, use search_competitors instead."
    ),
    "input_schema": {
        "type": "object",
        "properties": {
            "query": {
                "type": "string",
                "description": "Search query. Examples: 'NVDA earnings Q3 2025', 'Tesla delivery numbers'"
            },
            "max_results": {
                "type": "integer",
                "description": "Max articles to return (1-10, default 5)",
                "default": 5
            }
        },
        "required": ["query"]
    }
}]

Les tests internes d’Anthropic ont montré que l’ajout d’un champ input_examples faisait passer la précision de 72 % à 90 % pour la gestion de paramètres complexes.

Renvoyez une sortie à forte valeur informative et machine-readable

Évitez les identifiants de bas niveau (uuid, mime_type). Résolvez les ID cryptiques en noms sémantiques. Structurez la réponse afin que l’agent puisse raisonner dessus sans analyser de boilerplate :

# Bad: raw API response dumped to agent
def get_stock_snapshot(ticker: str) -> dict:
    response = api.get(f"/v1/quotes/{ticker}")
    return response.json()  # 500+ tokens of nested JSON

# Good: high-signal summary the agent can immediately reason about
def get_stock_snapshot(ticker: str) -> dict:
    data = api.get(f"/v1/quotes/{ticker}").json()
    return {
        "ticker": ticker,
        "price": data["regularMarketPrice"],
        "change_pct": round(data["regularMarketChangePercent"], 2),
        "volume": data["regularMarketVolume"],
        "market_cap_b": round(data["marketCap"] / 1e9, 1),
        "pe_ratio": data.get("trailingPE"),
        "summary": f"{ticker} at ${data['regularMarketPrice']:.2f} "
                   f"({'up' if data['regularMarketChangePercent'] > 0 else 'down'} "
                   f"{abs(data['regularMarketChangePercent']):.1f}%)"
    }

Renvoyez des erreurs dont la boucle peut tirer parti

La gestion des erreurs nécessite quatre mécanismes distincts, car chacun traite une classe d’échec différente :

  1. Retry avec backoff exponentiel pour les erreurs transitoires
  2. Chaînes de fallback de modèles en cas d’indisponibilité d’un fournisseur
  3. Routage par classification d’erreur — les erreurs transitoires sont réessayées, les erreurs récupérables par le LLM sont renvoyées à l’agent avec leur contexte, et les erreurs nécessitant une intervention humaine sont escaladées
  4. Récupération depuis un checkpoint pour survivre aux crashs

L’article d’Anthropic “Writing effective tools for agents” préconise des erreurs d’outils claires et une conception guidée par l’évaluation, mais ne fournit aucun chiffre universel sur le taux de récupération assuré par ces quatre mécanismes. Mesurez le taux de récupération, les retries et les escalades sur votre propre suite de tâches.

import httpx
from tenacity import retry, stop_after_attempt, wait_exponential

@retry(
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=1, min=2, max=10),
)
def call_stock_api(ticker: str) -> dict:
    """Fetch stock data with automatic retry on transient failures.

    Mechanism 1 of the four above: exponential backoff for rate limits
    and network blips.
    If all retries fail, the error propagates to the agent with
    enough context to decide whether to try a different approach.
    """
    response = httpx.get(
        f"https://api.example.com/v1/quotes/{ticker}",
        timeout=10.0,
    )
    response.raise_for_status()
    return response.json()

Application des patterns au Market Analyst Agent

Le Market Analyst Agent de la partie 1 permet de voir concrètement l’effet de l’interface.

Byte says

J’ai donné à chaque endpoint d’API son propre outil et j’en ai livré dix. L’agent a dépensé son budget de raisonnement à déterminer lesquels combiner. Je lui avais remis la documentation de mon API et appelé cela un ensemble d’outils.

Consolidation des outils

La conception initiale comportait plus de 10 outils : get_stock_price, get_company_metrics, get_market_cap, get_pe_ratio, get_volume, etc. Chacun était une fine couche d’encapsulation autour d’un endpoint d’API. Pour chaque requête, l’agent devait déterminer quelle combinaison appeler.

J’ai consolidé la surface des données de marché en 5 outils de haut niveau, conformément au principe ACI d’actions compactes et efficaces. La liste d’outils ReAct du dépôt en comprend quatre autres — un chargeur de skill, deux wrappers CLI et un évaluateur Python en processus restreint (une allowlist AST, pas un sandbox ; la partie 4 revient sur ce point) — couvrant trois des cinq modalités ci-dessus. MCP apparaît comme sidecar plutôt que comme outil de cette liste :

Avant (10+ outils)Après (5 outils)Pourquoi
get_stock_price + get_company_metrics + get_pe_ratioget_stock_snapshotUn seul appel renvoie tout le nécessaire à l’analyse de base
get_price_history + get_volume_historyget_price_historyCombiné à une période et des indicateurs configurables

Cette réduction a diminué la surcharge des tool schemas et, lors de mes propres tests, rendu la sélection d’outils plus fiable, car elle réduit le nombre de choix ambigus.

Sorties structurées pour les tool results

Chaque outil du Market Analyst Agent renvoie une réponse validée par Pydantic. Cela applique le principe ACI de validation à la sortie de l’outil :

class StockSnapshot(BaseModel):
    """Structured tool response — the agent never sees raw API noise."""
    ticker: str
    price: float
    change_pct: float
    volume: int
    market_cap_b: float
    pe_ratio: float | None
    summary: str  # Human-readable one-liner for direct use in reports

class NewsResult(BaseModel):
    """Each news item is pre-processed for agent consumption."""
    headline: str
    source: str
    date: str
    relevance_score: float  # Pre-ranked so the agent doesn't waste tokens sorting
    key_points: list[str]  # Extracted by the tool, not the agent

Le champ summary est le plus important. Il fournit à l’agent une chaîne directement exploitable, qui peut être insérée telle quelle dans un rapport sans traitement supplémentaire. Les key_points dans NewsResult sont extraits par l’outil plutôt que par l’agent, ce qui évite à celui-ci de consommer des tokens d’inférence pour analyser le corps des articles.

Compromis et points à prendre en compte

Au-delà des réserves propres à chaque modèle présentées plus haut, quelques considérations transversales influencent le choix :

  • Le coût opérationnel varie selon la dimension considérée. L’exécution de code économise des tokens, mais ajoute la latence de cold start du sandbox. MCP réduit le temps de développement des intégrations SaaS, mais ajoute la surcharge liée au déploiement des serveurs. La CLI est gratuite à mettre en place, mais plus difficile à gouverner à grande échelle. Optimisez en fonction de votre véritable goulot d’étranglement : coût en tokens, latence ou complexité opérationnelle.

  • Les compétences de l’équipe comptent. L’exécution de code suppose que vos agents, et les modèles qui les sous-tendent, puissent générer du Python ou du TypeScript fiable. La CLI suppose une bonne connaissance des conventions Unix. MCP nécessite de comprendre les protocoles de transport et les flux OAuth. Adaptez la modalité aux points forts de votre équipe.

  • La consolidation des outils peut aller trop loin. Si un outil accumule des modes et des arguments sans rapport, l’agent se retrouve confronté à un autre problème de sélection à l’intérieur du schema. Utilisez des évaluations de sélection d’outils et de réussite des tâches pour trouver la surface adaptée à votre charge de travail.

  • Les Skills reposent sur les prompts et ne sont pas imposées. Une skill contient des instructions que l’agent devrait suivre, et non des guardrails qu’il doit respecter. Pour les workflows critiques, combinez les Skills avec une validation déterministe.

  • Les exigences d’audit influencent le choix. Si vous avez besoin d’un journal complet de chaque invocation d’outil et de son résultat, MCP et les tool calls JSON fournissent des pistes d’audit structurées prêtes à l’emploi. L’exécution de code produit un script et sa sortie, ce qui est utile, mais rend plus difficile la décomposition en actions individuelles pour les rapports de conformité.

Trois directions pour le tooling des agents AI à grande échelle

La première est le tool RAG pour passer à l’échelle. Lorsque les ensembles d’outils atteignent des centaines ou des milliers d’entrées, la précision d’une sélection naïve des outils tombe à 13,62 %. L’article RAG-MCP a appliqué la génération augmentée par récupération à la sélection d’outils : indexer les descriptions d’outils dans une base vectorielle et ne récupérer que les outils pertinents pour chaque requête. La précision atteint alors 43,13 %, soit une amélioration de 3,2 fois, tout en réduisant d’environ 50 % le nombre de tokens du prompt.

La deuxième est la création de leurs propres outils par les agents. Le framework LATM (« LLMs As Tool Makers ») a établi un paradigme en deux phases dans lequel un LLM puissant crée des fonctions Python réutilisables et un LLM léger les utilise. ToolMaker (ACL 2025) transforme automatiquement des dépôts GitHub en outils compatibles avec les LLMs, avec un taux de réussite de 80 %. Ces deux travaux dépassent l’utilisation des outils pour aller vers leur création, puis vers la gestion d’une bibliothèque d’outils générés.

La troisième est le stack de protocoles dual A2A + MCP. L’Agent2Agent Protocol (A2A), créé par Google et donné à la Linux Foundation en juin 2025, traite ce que MCP ne peut pas traiter : la communication d’agent à agent. MCP gère l’intégration agent-outil ; A2A gère la découverte, la négociation et la délégation de tâches entre agents.

Points clés à retenir

  1. Choisissez l’interface en fonction de l’action : appels JSON pour les petites opérations typées, MCP pour les services partagés, Skills pour les procédures, CLI pour les commandes établies et code exécuté dans un sandbox pour la composition locale.
  2. Conservez les conditions du benchmark avec le résultat. CodeAct, Anthropic, Vercel, Cloudflare, Apideck et Scalekit ont mesuré des modèles, tâches, outils et harnesses différents.
  3. La qualité de l’ACI reste valable malgré les changements de protocole. Des actions claires, des retours compacts, une validation et des erreurs utiles améliorent toutes les modalités.
  4. Ne consolidez les outils qui se chevauchent que lorsque les évaluations montrent qu’une surface réduite améliore la sélection ou la réussite des tâches.
  5. Le niveau de sécurité évolue avec le pouvoir d’exécution. Les interfaces shell et code nécessitent un sandbox ; MCP nécessite une identité limitée et une politique serveur ; les Skills restent des instructions et non un mécanisme d’application.
