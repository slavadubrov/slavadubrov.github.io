¿Qué es un runtime para agentes AI?

Un runtime para agentes AI es la infraestructura que mantiene en ejecución un agente que usa herramientas después de que termina una llamada al modelo. Almacena el estado de la sesión, ejecuta herramientas, guarda checkpoints, gestiona secretos, escribe trazas, aplica límites de coste y define cómo se despliega el servicio. El modelo elige la siguiente acción. El runtime decide dónde se ejecuta esa acción, registra el resultado y restaura la ejecución tras un fallo. El harness decide si una acción está permitida. No es un almacén, pero la tabla lo incluye porque el runtime tiene que ejecutarlo en algún sitio.

Las ejecuciones largas rompen las suposiciones de los procesos stateless

Byte dice

Si el log de ejecución solo vive en la memoria del worker, un despliegue rutinario puede sustituirlo en mitad de una tarea y borrar el historial de la ejecución.

Un endpoint de chat stateless puede mantener el estado de la petición en un único proceso y descartarlo después de la respuesta. Una ejecución larga de un agente atraviesa reinicios de workers, despliegues, resets de contexto y pausas para aprobaciones. El proceso worker ya no puede ser la fuente de la verdad.

El equipo de OpenAI Codex explica cuánto pueden durar estas ejecuciones en su artículo sobre harness engineering:

“Habitualmente vemos ejecuciones individuales de Codex trabajando en una única tarea durante más de seis horas (a menudo mientras los humanos duermen).”

El equipo de ingeniería de Anthropic describe el problema de estado correspondiente en Harnesses eficaces para agentes de larga duración:

“El reto fundamental de los agentes de larga duración es que deben trabajar en sesiones discretas, y cada nueva sesión comienza sin memoria de lo ocurrido anteriormente.”

Ambas observaciones implican el mismo diseño de runtime: persistir el estado fuera del worker y hacer que los workers sean reemplazables.

La sesión debe vivir fuera del proceso worker. Un almacén durable registra las llamadas al modelo, las intenciones y resultados de las herramientas y las aprobaciones, de modo que otro worker pueda reanudar desde el último punto seguro después de un crash. Un efecto externo pendiente necesita reconciliarse antes de que esa reanudación pueda considerarse segura. Los checkpoints también permiten que el runtime inicie una sesión nueva del modelo cuando se llena la context window, sin reproducir todo el historial. En palabras de Anthropic, las instancias del harness se vuelven desechables y reiniciables; el estado durable vive en otro lugar.

Cinco primitivas que debes ubicar antes de lanzar

El artículo de Anthropic Scaling Managed Agents proporciona un vocabulario útil para cinco responsabilidades del runtime. El harness hace avanzar al agente, mientras que la sesión registra lo que ha hecho y el sandbox ejecuta los comandos. El checkpoint proporciona al siguiente worker un punto de reanudación; la traza conserva evidencias para depurar más adelante. Una implementación puede fusionar componentes, pero las responsabilidades y los límites de fallo siguen necesitando nombres.

Sesión. Un event log append-only escrito por separado, con las llamadas al modelo, los tool calls solicitados y completados, los errores y las aprobaciones. Una base de datos de checkpoints ayuda a recuperarse, pero el historial del estado del grafo no sustituye a este log.

La palabra está sobrecargada, así que este artículo usa una nomenclatura de aplicación para tres ámbitos. Un thread es la conversación de un usuario a lo largo de varios días. Es el ámbito más duradero y puede contener muchas ejecuciones.

Una sesión del modelo es el ámbito más corto: un periodo continuo del contexto del modelo. La compactación —el paso que resume la ventana para que el trabajo pueda continuar— amplía una sesión del modelo en lugar de terminarla. Un reinicio o un inicio nuevo deliberado la termina. La parte 6 usa «sesión del modelo» en este sentido.

En este artículo, «sesión» significa el log durable de una ejecución. Varias sesiones del modelo pueden escribir en un mismo log, y un thread de conversación puede contener varios logs de ejecución. Para recuperarse, despierta la ejecución, carga su sesión, reconcilia cualquier efecto secundario pendiente y reanuda después del último evento: wake(sessionId) → getSession(id) → reconcile pending effects → resume from last event.

En LangGraph, thread_id es la clave de almacenamiento y recuperación del checkpointer para el historial del estado del grafo de un thread (consulta Persistencia de LangGraph); no define los límites de conversación, sesión del modelo o event log de este artículo. Asigna al event log su propio ID durable de ejecución o sesión y decide explícitamente cómo se relacionan esos ID con los threads de LangGraph. OpenAI Agents SDK incluye diez backends de sesión integrados, entre ellos SQLiteSession, RedisSession, SQLAlchemySession, MongoDBSession y EncryptedSession (consulta la documentación de Sessions). Mantienen un historial de conversación mutable, incluida su eliminación, limpieza y compactación; asigna un ID de sesión del SDK al ID de eventos de la ejecución si resulta útil, pero no trates el historial del SDK como log de recuperación o auditoría append-only sin una garantía equivalente de inmutabilidad.

Harness. El loop de orquestación y la única primitiva de aquí que toma decisiones. Construye el prompt a partir de la memoria, llama al modelo, comprueba el tool call propuesto frente a sus reglas de permisos, despacha lo que permite, escribe los resultados en la sesión, aplica las reglas de reintento y decide si la tarea ha terminado. Las ayudas de planificación y la gestión del contexto codifican suposiciones sobre las capacidades del modelo. La autorización y el aislamiento obligatorios también implementan requisitos que siguen vigentes a medida que mejoran los modelos. Anthropic lo señala directamente —la cita aparece en la sección de modos de fallo—, que trata sobre lo que ocurre cuando esas suposiciones quedan obsoletas.

El equipo de Codex de OpenAI denomina a esto harness engineering: escribir software sigue requiriendo esfuerzo de ingeniería, pero ahora una mayor parte se dedica al andamiaje que al código en sí. El CompiledStateGraph de LangGraph, Deep Agents de LangChain y su punto de entrada create_deep_agent, y Claude Code son harnesses en este sentido.

Sandbox. El entorno de ejecución aislado donde se ejecutan realmente los comandos. La página de conceptos de sandbox de OpenAI Agents SDK asigna las aprobaciones, el tracing, los handoffs y el estado necesario para reanudar ejecuciones al runtime externo. Asigna los comandos, los cambios en archivos y el aislamiento del entorno a la sesión del sandbox.

Allí, «runtime externo» significa el harness junto con sus almacenes de estado. En el vocabulario de esta serie, las aprobaciones y los handoffs son decisiones del harness (parte 4 y parte 6); el tracing y la gestión de la reanudación son responsabilidades de las primitivas de sesión y checkpoint.

Los sandboxes se diferencian por cuánto tiempo viven y qué recuerdan entre ejecuciones. La forma más sencilla es fresh ephemeral: crear uno para una única tarea, destruirlo al terminar y asumir el coste de arranque en frío en cada ejecución.

Los sandboxes persistent paused conservan el sistema de archivos y una instantánea de memoria entre ejecuciones. La siguiente reanudación puede evitar un arranque completo. Snapshot o fork crea una rama con una imagen copy-on-write a partir de un padre preparado, de modo que muchas tareas compartan dependencias instaladas y caches calientes sin compartir su estado escribible.

Los workspaces per-worktree proporcionan checkouts independientes para las tareas; los worktrees de Git comparten la infraestructura del repositorio y no son sandboxes del sistema operativo. Restringe la ejecución por separado con un contenedor, una VM o una política de procesos. Una aplicación por tarea también puede tener su propia pila de observabilidad. Los logs, métricas y trazas separados permiten depurar una ejecución sin que su estado se mezcle con el de otra. La tabla de proveedores más adelante compara los contratos de aislamiento y persistencia.

Checkpoint. El estado necesario para reanudar: qué nodo del grafo se ejecutó, sus valores más recientes y qué debe ejecutarse a continuación. Un event log responde a qué ocurrió: las acciones solicitadas y sus resultados. Un checkpoint no puede reconstruir eventos que el harness nunca registró.

El PostgresSaver de LangGraph escribe un Checkpoint en cada límite de super-step. Un super-step es una ronda del grafo, ya sea un único nodo o un lote ejecutado en paralelo. Las escrituras por tarea se realizan en checkpoint_writes, por lo que las salidas de nodos completados no se recalculan cuando falla un nodo hermano.

Un checkpoint es un dict normal (v, id, ts, channel_values, channel_versions, versions_seen, updated_channels). LangGraph lo serializa con su JsonPlusSerializer basado en msgpack, no con JSON. datetime, set, Decimal y las dataclasses se pueden serializar y deserializar conservando sus valores. El formato está documentado en la página de PyPI langgraph-checkpoint-postgres y en la referencia de checkpoints de LangGraph.

StateSnapshot es la vista independiente y más rica que graph.get_state() construye sobre un checkpoint. Un debug bundle puede exportar su .values como último estado conocido del grafo; no puede reconstruir detalles de eventos que el harness nunca registró.

Traza. La superficie de depuración y auditoría. Cada llamada al modelo, tool call y paso de un subagente debería emitir duración, estado, modelo y proveedor, ID de correlación, recuento de tokens y coste. Los prompts, completions, argumentos de herramientas y resultados de herramientas son contenido opt-in: la guía de GenAI de OpenTelemetry usa metadatos por defecto porque esos campos pueden contener datos sensibles. Captúralos solo después de decidir qué redacción o filtrado, controles de acceso y retención se aplican. Cuando falla una ejecución de seis horas, la traza es lo que lees para averiguar qué salió mal. Puede respaldar una investigación, pero el event log y el estado del checkpoint, junto con la gestión de idempotencia, son los que permiten una reanudación o replay seguro. Para entonces, la salida del terminal de la ejecución ya ha desaparecido. Las convenciones semánticas GenAI de OpenTelemetry estandarizan los nombres de atributos (qué modelo, qué proveedor, cuántos tokens, qué conversación y qué workflow). En un destino compatible con OTLP que admita estas convenciones, la misma instrumentación puede exportar la traza a sistemas como Tempo, Jaeger, Honeycomb o LangSmith, aunque pueden seguir siendo necesarios adaptadores del backend o configuración específica del destino.

Las políticas y los secretos atraviesan las primitivas

Hay dos límites que atraviesan las cinco primitivas. Son la versión de runtime del argumento de seguridad de la parte 4. La decisión sobre permisos pertenece al harness; lo que sigue explica dónde se ubica físicamente la maquinaria que la aplica y la alimenta.

Aplicación de permisos

La escala de permisos de la parte 4 necesita un lugar donde ejecutarse. La comprobación se dispara antes de cada tool call y decide si este se permite. En producción son habituales dos patrones. El middleware de permisos del sistema de archivos de Deep Agents puede limitar las herramientas de sistema de archivos integradas a rutas declaradas. No controla los comandos shell del sandbox, las herramientas personalizadas ni las llamadas MCP; aplícalo en la política del sandbox o detrás de su propio proxy de herramientas. Anthropic Managed Agents dirige los tool calls MCP personalizados a través de un proxy que contiene las credenciales. La ejecución de comandos del sandbox y la autenticación de Git utilizan rutas independientes; el proxy MCP no es un interceptor universal para todas las acciones. Cuando una llamada sensible necesita aprobación humana, interrupt() de LangGraph y el hook de aprobación de Deep Agents pausan el grafo hasta que una persona da su aprobación.

Broker de secretos

El modelo no debería ver secretos de larga duración y, normalmente, el sandbox tampoco. El patrón de Managed Agents es el que conviene copiar:

“Para Git, usamos el token de acceso de cada repositorio para clonar el repositorio durante la inicialización del sandbox y lo conectamos al remote local de git. Git push y pull funcionan desde dentro del sandbox sin que el agente llegue a manejar el token. Para las herramientas personalizadas, admitimos MCP y almacenamos los tokens OAuth en un vault seguro. Claude llama a las herramientas MCP mediante un proxy dedicado; este proxy recibe un token asociado a la sesión. … El harness nunca llega a conocer ninguna credencial.”

En el stack de referencia market-analyst-agent —un pequeño agente LangGraph que obtiene datos de mercado y escribe un informe de analista, desarrollado a lo largo de esta serie—, el worker llama localmente a sus herramientas de datos de mercado. El servidor MCP opcional exporta una superficie de herramientas; no es un broker de credenciales implementado entre ese worker y sus proveedores. Ambos contenedores pueden leer el .env de desarrollo compartido. Un broker de producción requeriría mover las credenciales de los proveedores a un almacén que el worker no pudiera leer y enrutar mediante el broker todas las llamadas pertinentes.

Comprueba la ubicación

Una comprobación práctica consiste en anotar cada componente y cuál de las cinco primitivas implementa. Postgres podría cubrir sesión y checkpoint. El contenedor worker es el harness. Un servicio como Daytona, Modal o E2B proporciona el sandbox, mientras que Tempo o LangSmith almacena la traza.

Después, inspecciona los fallos acoplados. Si dos primitivas viven en el mismo proceso, un solo crash las derriba a ambas. Si comparten una credencial, una filtración atraviesa los dos límites. Ejemplos habituales son un worker que también posee la durabilidad de las trazas o un token de sidecar que también desbloquea la base de datos de checkpoints.

Modos de fallo de un runtime de agentes AI en producción

El runtime gestiona reintentos, restaura el trabajo anterior, aísla workspaces y aplica presupuestos. A medida que las ejecuciones atraviesan workers y context windows, los fallos se desplazan hacia el estado, los efectos secundarios duplicados, la deriva del sandbox y los excesos de presupuesto.

Los fallos se dividen en cuatro grupos:

  • Fallos de calidad de salida: el agente declara la victoria antes de que el trabajo haya terminado realmente, olvida lo que hizo tras un reset de la context window o confía en su autoevaluación y publica una salida defectuosa.
  • Fallos de control de costes: el agente queda atrapado en un loop de reintentos o consume el presupuesto de tokens o tool calls sin producir nada útil.
  • Fallos de estado y crashes: los workspaces divergen porque una ejecución modifica archivos propiedad de otra, los tool calls se ejecutan más de una vez porque los reintentos los reproducen o el trabajo se pierde cuando muere un worker entre dos eventos.
  • Fallos de context window: el modelo resume y abandona pronto porque cree que se está quedando sin espacio, aunque la ventana aún tenga margen.

La tabla relaciona cada fallo con una mitigación, la base de la recomendación y el hook del runtime que la aplica. El comportamiento específico de cada modelo puede cambiar, así que considera las observaciones de los proveedores como motivos para volver a probar la suposición, no como reglas permanentes.

Dos ideas sustentan la mayoría de esas filas. Anthropic, sobre la obsolescencia del harness, en Harness design for long-running application development:

“Cada componente de un harness codifica una suposición sobre lo que el modelo no puede hacer por sí solo, y conviene someter esas suposiciones a pruebas de estrés, tanto porque pueden ser incorrectas como porque pueden quedar obsoletas rápidamente a medida que mejoran los modelos.”

Vercel, sobre el problema relacionado de que demasiadas herramientas codifican demasiadas suposiciones, en We removed 80% of our agent’s tools:

“Borramos la mayor parte y redujimos el agente a una sola herramienta: ejecutar comandos bash arbitrarios. Lo llamamos agente de sistema de archivos.”

La cita describe el núcleo bash; el agente que Vercel lanzó conservaba dos herramientas, ExecuteCommand y ExecuteSQL, sustituyendo un ejemplo de código antiguo que nombraba diecisiete herramientas. La parte 3 cubre el antes y el después completo. Su resultado comunicado en cinco consultas representativas: el éxito pasó de 4/5 a 5/5 y el peor caso bajó de 724 s / 100 pasos / 145.463 tokens (fallido) a 141 s / 19 pasos / 67.483 tokens (correcto). Ese peor caso es el más llamativo; de media en las cinco consultas, el ahorro de tokens fue del 37 %. La lección no es «elimina tus herramientas». La asistencia opcional puede volverse redundante a medida que cambia el comportamiento del modelo. Vuelve a probar la suposición cuando cambie el modelo.

Cognition observó el mismo objetivo cambiante en la duración de las sesiones con Sonnet 4.5. En Rebuilding Devin for Claude Sonnet 4.5 describen un modelo que escribe proactivamente SUMMARY.md / CHANGELOG.md cuando percibe que el contexto se agota, pero subestima cuántos tokens le quedan. Su solución fue habilitar el contexto de 1M tokens y limitar el uso a 200k para que el modelo siguiera creyendo que tenía margen. Cuando lo escribieron, era un flag beta.

La documentación de context window de Anthropic, consultada el 6 de septiembre de 2026, enumera Sonnet 5 y Opus 5 con 1M tokens por defecto; Sonnet 4.5 sigue en 200k. Los modelos Sonnet actuales reciben automáticamente actualizaciones sobre el contexto restante, y la compactación server-side está disponible en beta para Claude 4.6 y modelos posteriores. Antes de copiar el límite histórico de Cognition, prueba el modelo seleccionado con sus controles de contexto compatibles. Una ventana mayor o un contador de presupuesto no garantizan una recuperación fiable, y ninguno sustituye al progreso durable fuera del modelo.

El equipo de harness de OpenAI tiene una versión de una sola línea: «Los humanos dirigen. Los agentes ejecutan». Cuando algo falla, la pregunta útil es qué capacidad falta y cómo hacer que esa capacidad sea legible y aplicable para el agente.

El ciclo de vida de una ejecución saludable

Una ejecución bien comportada es aburrida. Es una cadena de pequeños pasos recuperables y cada paso completado escribe el estado durable antes de que comience el siguiente.

Escribir cada resultado antes de iniciar el paso siguiente limita el daño de un crash. Un efecto externo en curso es la excepción: un worker puede fallar después de que el proveedor haga commit y antes de que el harness registre el resultado. El siguiente worker debe reconciliar ese efecto pendiente antes de reanudar desde el último paso completado.

  1. Arranca desde una sesión nueva o reanudada. Al reanudar, monta el workspace desde su último estado conocido, lee los archivos de progreso que dejó el intento anterior (PROGRESS.md, feature-list.json), carga el último checkpoint e inspecciona el event log en busca de intenciones de herramientas pendientes. Reconcilia cualquier efecto externo pendiente antes de hacer otra llamada al modelo o a una herramienta.
  2. Planifica antes de ejecutar cualquier tool call. Deja por escrito cómo es el estado «done», cuánto puede gastar la ejecución, qué herramientas puede invocar el agente y qué debería detenerla antes de tiempo. Estos valores del plan se convierten en comprobaciones del runtime; sin ellos, la ejecución no tiene nada que la frene.
  3. Serializa o coordina explícitamente los tool calls con efectos secundarios. La comprobación de permisos del harness decide si permite cada uno. Antes del dispatch, añade una intención pending con su clave de idempotencia; después de que responda el proveedor, añade el resultado. Las llamadas independientes de solo lectura o idempotentes pueden ejecutarse en paralelo cuando cada una tiene su propio registro durable de intención/resultado y sus resultados se agregan de forma determinista. Si el worker muere entre un efecto secundario y la escritura de su resultado, reanuda consultando o reintentando al proveedor con la misma clave y añade después el resultado recuperado o needs_human. Por ejemplo, Stripe devuelve el primer resultado guardado de la petición cuando se repite una clave de idempotencia; otro proveedor necesita un contrato equivalente de consulta o reintento.
  4. Crea un checkpoint en los límites de super-step, o después de cada evento en un harness más sencillo. Persiste el estado del grafo, el diff del workspace y las referencias a los artefactos producidos. Este checkpoint es lo que lee el paso 1 en la siguiente reanudación. Si falta el checkpoint o está obsoleto, la recuperación puede necesitar reconstruir el estado a partir del event log, lo que es mucho más lento.
  5. Evalúa los artefactos cuando el agente cree que ha terminado: tests, un evaluador con contexto nuevo, validación del schema y comprobaciones del navegador. Si la comprobación pasa, la ejecución termina correctamente. Si falla, la ejecución reanuda desde el último checkpoint limpio con el mensaje del fallo añadido al contexto y vuelve a intentarlo.

Ningún paso de esa lista requiere que el agente recuerde algo entre ejecuciones. El estado vive en la sesión y el checkpoint, y el agente lo lee en cada reanudación.

Persiste un ID de operación propiedad de la aplicación antes del dispatch y vincúlalo a los argumentos aprobados. Reutilízalo para recuperar la misma intención de negocio, aunque la replanning produzca un nuevo ID de tool call del modelo. Registra esos ID del modelo por separado para la correlación. Las actualizaciones naturalmente idempotentes pueden necesitar, en su lugar, una precondición de versión. La guía de reintentos de AWS explica por qué la identidad de la petición representa la intención. Define cuándo una acción es realmente nueva y cuánto dura la deduplicación: Stripe permite eliminar claves después de al menos 24 horas. Reconcilia los payloads modificados y las claves caducadas antes de volver a intentarlo.

Elige un único writer activo o un lease por thread. Si llega una entrada durante una ejecución, recházala, encolala, interrúmpela o haz rollback de forma explícita; el análisis del runtime de Deep Agents describe estas opciones. La cancelación debe detener nuevos dispatches, registrar la petición y reconciliar los efectos en curso; matar el worker no deshace una llamada al proveedor.

La aplicación del presupuesto debe estar junto al dispatch. Las llamadas concurrentes no deben gastar el mismo margen restante. Prometheus es un sistema de monitorización, no un ledger autoritativo del gasto por petición. Reserva de forma conservadora y reconcilia el uso real; la contabilidad retrasada del proveedor y la cancelación aún pueden producir excesos.

Los nuevos controles del modelo ayudan a regular el ritmo de la ejecución, pero no son propietarios de su límite de gasto. Los task budgets beta de Anthropic proporcionan a los modelos compatibles con Messages API un presupuesto orientativo a lo largo de un loop agentic. Se pueden superar; max_tokens limita una respuesta, no toda la ejecución. La compatibilidad depende del modelo: Opus 5 admite task budgets, mientras que Sonnet 5 no. Conserva el ledger de dispatch y la ruta de cancelación aunque el modelo reciba una indicación de presupuesto.

Las paradas de seguridad del proveedor necesitan su propia ruta terminal. Para el misalignment_policy_violation de OpenAI, detén el dispatch, conserva los registros correlacionados y solicita la revisión de un operador en lugar de reintentar. Gestiona los errores del stream después de una salida parcial y reconcilia los efectos anteriores; la parte 4 explica el límite de monitorización.

La evaluación debería incluir evidencias externas al contexto que produce la salida. Un evaluador con contexto nuevo reduce el sesgo del contexto compartido, mientras que los tests, linters, comprobaciones del navegador y la validación del schema aportan evidencias deterministas. La comprobación puede devolver pass, fail o needs_human. En agentes de código, el revisor puede ser otra sesión del modelo con herramientas de solo lectura. En agentes de datos e informes, combina validación determinista con un modelo revisor cuando siga siendo necesario el juicio.

Once patrones de despliegue de agentes AI y qué determina la elección

Una vez nombradas las cinco primitivas, la pregunta es qué forma de despliegue las ejecuta. Por «forma» entiendo una disposición de esas primitivas: dónde vive el harness, dónde persiste el estado y qué tipo de sandbox ejecuta el trabajo. Una forma es una decisión de cableado, no una elección de proveedor. El gráfico siguiente muestra dónde resulta cómoda cada forma en el eje de duración de la ejecución. El texto posterior explica qué factores deciden entre ellas.

Si solo vas a leer una de las once, lee la forma 2: cola + worker + base de datos de checkpoints. Es la opción predeterminada que recomiendo a la mayoría de equipos, la forma usada por el repositorio de referencia y el esqueleto del que varían la mayoría de las demás: cola → worker → estado durable, cambiando el origen del sandbox, el propietario del harness o el motor de estado. Leer primero la forma 2 hace que el resto se pueda revisar más rápido.

El gráfico compara las formas por duración. La matriz siguiente las compara por propiedad: cada celda delimitada nombra el componente que proporciona esa primitiva.

1. SDK dentro de un servidor de aplicaciones (síncrono, ligado a la petición)

La forma original. El SDK del agente se ejecuta dentro de un request handler. Es adecuada para tareas de menos de 30 segundos, demos y herramientas internas. Es mala para cualquier cosa de la que un cliente HTTP pueda desconectarse. El timeout HTTP de Cloud Run tiene un máximo de 60 minutos y cualquier panic de la capa web mata la ejecución. El SDK es el harness. La ejecución de herramientas no confiables necesita un sandbox separado y el estado suele vivir en la memoria del proceso, salvo que lo envíes explícitamente a otro sitio. No uses esta forma para trabajos de varias horas.

2. Cola + worker + base de datos de checkpoints

Es la opción predeterminada que recomiendo a la mayoría de equipos y la implementación de demo con forma de producción en market-analyst-agent: un worker Python con un checkpointer PostgreSQL, Redis Streams (o RabbitMQ) para la cola de entrada y un sidecar MCP para las herramientas. Es adecuada para ejecuciones de 10 minutos a varias horas con pasos idempotentes. El runner local puede saltarse la cola para el desarrollo síncrono, pero la cola forma parte del patrón de producción cuando necesitas envío asíncrono y backpressure.

En el patrón de producción, la aplicación acepta una petición, crea una fila de sesión, inserta un job en la cola y devuelve un ID de ejecución. El worker extrae el job, ejecuta el harness, escribe eventos de sesión y checkpoints, transmite el estado y almacena los artefactos a medida que avanza. Postgres sobrevive, los workers son reemplazables y la profundidad de la cola proporciona backpressure. La computación Spot/Preemptible funciona siempre que las escrituras durables del evento y el checkpoint terminen antes de que el worker comunique el éxito. El repositorio enlazado ilustra esta topología; la recuperación durable también depende de los leases de la cola, la recuperación de jobs interrumpidos y la confirmación del trabajo completado.

En esta forma, el worker es el harness. Su contenedor y el workspace por thread proporcionan un límite de ejecución, pero el código no confiable sigue necesitando un sandbox reforzado o una VM. El event store posee el historial de sesión; PostgresSaver posee el estado de los checkpoints. Pueden compartir una base de datos solo cuando el harness escribe explícitamente ambos esquemas. Las trazas pasan por OpenTelemetry hasta la pila de observabilidad que utilices.

3. Motor de workflows durables (estilo Temporal)

El código de orquestación del agente se ejecuta dentro de un Temporal Workflow; las llamadas al modelo y a las herramientas se ejecutan como Activities. El estado del Workflow vive en un event-history log respaldado por Cassandra, MySQL o Postgres, por lo que puede reproducirse entre fallos. Los despliegues de código del Workflow que se solapen con una ejecución necesitan Worker Versioning o patches seguros para replay; sustituir código sin esa disciplina puede romper el replay. La integración de Temporal con OpenAI Agents SDK, disponible de forma general desde marzo de 2026, incluye un helper OpenAIAgentsPlugin y otro activity_as_tool, y el artículo sobre agentic sandboxes describe cómo hacer fork de un agente en ejecución hacia otro proveedor de sandbox a mitad de la conversación. Los workflows inactivos consumen cero computación. Las salvedades son reales: los agentes realtime no son compatibles y el streaming sigue marcado como experimental, mientras que LocalShellTool y ComputerTool están deshabilitados porque no encajan en un modelo distribuido.

Usa esta forma cuando la ejecución tenga verdaderos puntos de espera: aprobaciones humanas, callbacks externos, sleeps largos, reintentos con reglas de negocio o ventanas de despliegue, y el equipo pueda operar versionado de workflows seguro para replay. Una aprobación humana se convierte en un sleep durable que no consume computación, no en un loop de polling.

El código del Workflow es el harness. El sandbox suele vivir fuera de Temporal y se invoca desde Activities. La sesión y el estado de checkpoints se integran en el event-history log de Temporal, mientras que la visibilidad de las trazas procede de Temporal UI más spans de OpenTelemetry en cada Activity.

Una forma más reciente. Cada ejecución del agente obtiene su propio microVM o contenedor de un proveedor de sandbox-as-a-service. El harness vive en algún lugar durable; el sandbox es el entorno de ejecución desechable.

El proveedor posee el sandbox y nada más. El harness, la sesión, el checkpoint y la traza permanecen de tu lado, normalmente conectados mediante la forma de cola + worker del punto 2.

5. Anthropic Managed Agents (harness alojado)

Anthropic lanzó Managed Agents en beta pública el 8 de abril de 2026, detrás de la cabecera beta managed-agents-2026-04-01. El servicio proporciona una sesión, un harness, un sandbox y un proxy MCP respaldado por un vault, todo alojado. wake(sessionId) puede inicializar el harness en un worker nuevo sin perder el estado durable de la sesión.

Anthropic factura Managed Agents con las tarifas estándar de tokens más $0.08 por hora de sesión. La facturación tiene granularidad de milisegundos y solo se aplica mientras el estado de la sesión es «running»; el tiempo idle es gratuito. Por tanto, un loop de reintentos descontrolado añade coste de horas de sesión al coste de tokens.

Lee las salvedades. El descuento de Batch API no se aplica («Las sesiones tienen estado y son interactivas. No existe modo batch»). Managed Agents no está disponible mediante AWS Bedrock ni Google Vertex AI. Dentro de la beta, los túneles MCP y el «dreaming» del agente requieren además solicitar acceso a una research preview; la coordinación multi-agent y la autoevaluación con rúbricas forman parte de la beta documentada. El lock-in es alto: renuncias a la libertad sobre el harness para no tener que ejecutar tú mismo el loop.

La configuración cloud predeterminada coloca las cinco primitivas en Anthropic. Con sandboxes self-hosted, operas la ejecución, los sistemas de archivos y la salida de red mientras Anthropic ejecuta la orquestación y el modelo. Las entradas y resultados de las herramientas siguen llegando a su control plane; las skills y la memoria adjuntas se almacenan allí y se sincronizan. Ser propietario de la ejecución no convierte todo el sistema en self-hosted.

Claude Platform en AWS también admite Managed Agents y sandboxes self-hosted; es independiente de Bedrock. Allí, una sesión autónoma necesita un evento de rol de usuario para volver a autenticarse después de seis horas, y las sesiones self-hosted no pueden adjuntar almacenes de memoria. Managed Agents first-party no tiene esas dos restricciones. Comprueba la plataforma además del modelo antes de copiar un diseño de sesión.

6. LangChain Deep Agents Deploy (harness abierto gestionado)

deepagents deploy empaqueta un deepagents.toml en un LangSmith Deployment con ejecución durable, memoria, multi-tenancy, human-in-the-loop, observabilidad, ejecución de código en sandbox y ejecuciones programadas. Admite modos de despliegue cloud, híbrido y self-hosted. Los proveedores de sandbox (LangSmith Sandboxes, Daytona, Modal, Runloop o uno personalizado) se pueden cambiar mediante un único valor de configuración. Los archivos y la memoria del agente viven en un sistema de archivos virtual con backends conectables; la persistencia de checkpoints es independiente y la memoria puede estar asociada al usuario, al asistente o a ambos. El lock-in es menor que en Managed Agents: el harness tiene licencia MIT, las instrucciones utilizan el estándar abierto AGENTS.md y los agentes se exponen mediante MCP, el protocolo A2A (Agent2Agent) y Agent Protocol. Consulta el artículo de LangChain runtime-behind-production-deep-agents.

Las cinco primitivas están alojadas por defecto, pero cada una se puede cambiar mediante configuración. El sandbox se configura con un único valor. El sistema de archivos de memoria es independiente de la persistencia de threads y checkpoints. La traza se envía a LangSmith.

7. Servicio o job de Google Cloud Run

Cloud Run tiene dos modos de runtime diferentes y cuál encaja depende de cómo se invoque el agente. Los Services están vinculados a HTTP y escalan a cero entre peticiones; el harness se ejecuta como request handler y devuelve la respuesta cuando termina la ejecución. Los Jobs se ejecutan hasta completarse sin un endpoint HTTP; el harness funciona como worker de una sola ejecución y termina cuando finaliza la tarea. Ambos pueden alojar el harness, pero ninguno conserva estado entre ejecuciones. Las sesiones y los checkpoints deben vivir en Postgres, Spanner o un almacén externo similar.

Los límites estrictos son muy diferentes. Timeout de peticiones de Cloud Run service: 300 s por defecto, máximo 3.600 s (60 min). Los WebSockets tienen el mismo timeout. Cloud Run jobs: 10 min por tarea por defecto, máximo 168 h (7 días); para tareas que usan GPUs, máximo 1 hora. La facturación basada en instancias (CPU siempre asignada) sigue permitiendo scale-to-zero; el número mínimo de instancias es un ajuste independiente; los jobs no tienen HTTP ni autoscaling.

Usa un servicio para ejecuciones síncronas de hasta 60 minutos. Usa un job para trabajo one-shot o asíncrono más largo. Cloud Run Jobs puede mantener una tarea activa durante días, pero no proporciona replay durable entre despliegues, cambios de versión o sustituciones de workers. Un workflow más largo puede abarcar varias ejecuciones cuando un orquestador externo posee el progreso durable.

Cloud Run aloja el harness. El estado de sesión y checkpoints vive en Postgres, Spanner u otro almacén externo, y las trazas pueden fluir mediante Cloud Logging y OpenTelemetry. El contenedor del servicio es un entorno de ejecución; añade un sandbox independiente cuando el agente ejecute código no confiable.

8. AWS Lambda: invocaciones acotadas y workflows durables

El timeout máximo de una función Lambda es de 900 s (15 minutos), sin excepciones. Si API Gateway está delante de la función, el límite de integración depende del tipo de API. Las HTTP APIs permiten 30 segundos; las integraciones REST tienen 29 segundos por defecto, mientras que las REST Regional y private pueden configurar un timeout mayor. Lambda durable functions, lanzadas en diciembre de 2025, añaden checkpoints, pasos y esperas gestionados entre ejecuciones de hasta un año. La invocación activa sigue estando limitada, mientras que el workflow durable puede sobrevivirla. Compara runtimes compatibles, regiones, reglas de replay e idempotencia de Activities con tus requisitos.

Lambda puede albergar un harness acotado a su límite de 15 minutos. El estado de sesión y checkpoints sigue necesitando ubicaciones externas explícitas; añade un sandbox independiente para código no confiable y exporta las trazas a telemetría externa. Un workflow durable de Lambda puede orquestar trabajo de varias horas mediante invocaciones acotadas.

9. Una tarea de AWS ECS/Fargate por ejecución

Fargate no documenta un límite estricto de duración de las tareas, a diferencia de una invocación normal de Lambda. Fargate no admite tareas con GPU; las cargas ECS con GPU necesitan instancias EC2 adecuadas o un servicio externo de GPU. Fargate proporciona aislamiento de tareas basado en virtualización, aunque las credenciales y el acceso de red permitido siguen necesitando un modelo de amenazas. Las cuotas de throttling de Fargate permiten un burst de lanzamiento de 100 y se reponen a 20 por segundo, con presupuestos independientes para on-demand y spot. Las cuotas de servicio de ECS limitan los servicios que usan AWS Cloud Map discovery a 1.000 tareas por servicio y los clústeres respaldados por EC2 a 5.000 instancias de contenedor.

Fargate requiere el modo awsvpc, por lo que cada tarea obtiene una interfaz de red y una IP privada. Esta forma encaja con el acceso a datos dentro de una VPC. Fargate Spot añade riesgo de interrupción y la durabilidad sigue siendo responsabilidad tuya, porque la plataforma no ofrece replay al estilo Temporal.

Fargate aloja el harness y proporciona una tarea propia para cada ejecución. Esto separa los workspaces y las credenciales de las tareas, pero por sí solo no es un sandbox completo para código hostil. La sesión, el checkpoint y la traza se envían a servicios externos como RDS o DynamoDB, además de CloudWatch/X-Ray.

Compara también Amazon Bedrock AgentCore Runtime antes de construir tú mismo la capa de sesiones en AWS. Aloja tu código de agente con ciclo de vida de sesión gestionado y varias opciones de computación. AWS documenta hasta 8 horas en microVMs serverless o 14 días en su tipo de computación Instances, que también admite cargas con GPU. Instances utiliza recursos EC2 gestionados por AWS en tu cuenta, con un modelo de seguridad diferente al de la opción serverless. Selecciona y prueba explícitamente ese contrato de computación; una instancia de mayor duración tampoco proporciona ejecución exactly-once de un efecto externo.

10. Kubernetes Job o namespace por sesión

Es una buena opción si ya operas Kubernetes y quieres un sandbox por sesión con controles para todo el clúster. Es mala si necesitas un arranque inferior a un segundo, porque descargar la imagen del contenedor e inicializar el pod tarda demasiado en un arranque en frío. El patrón consiste en un Job por ejecución del agente, con activeDeadlineSeconds, un PersistentVolumeClaim para el workspace y un sidecar para el servidor MCP. La recuperación ante crashes tienes que construirla tú. Adoptar Kubernetes solo para alojar agentes tiene un coste elevado en complejidad de configuración y carga operativa. Solo merece la pena si ya ejecutas K8s por otros motivos.

Kubernetes aloja el harness y el entorno de ejecución por ejecución, normalmente como un Job y en ocasiones con un namespace dedicado. Un aislamiento fuerte sigue dependiendo de la runtime class, la política de red, la seguridad de los pods y el límite subyacente del contenedor o la VM. El estado de sesión y checkpoints vive en una base de datos externa o en un PersistentVolumeClaim.

11. Docker Compose local (solo desarrollo)

Es la referencia para la siguiente sección. El objetivo de esta forma es reflejar uno a uno la topología de producción (las mismas primitivas y la misma forma de red) mientras se ejecuta en una sola máquina. Lo que no refleja es el aislamiento: un único montaje de workspace compartido, un Postgres, ningún sandbox reforzado y ningún dominio de fallo separado entre el worker y su estado. No lances nada con esta forma.

Compose refleja la forma n.º 2 en un único host. En el stack de referencia, Postgres contiene el estado de los checkpoints y el contenedor worker es el harness. Una sesión con forma de producción necesita su propio event store append-only; el historial de PostgresSaver por sí solo no lo proporciona. El montaje de workspace compartido es cómodo para desarrollo, pero no aísla las ejecuciones no confiables. La pila opcional de OpenTelemetry registra las trazas.

Stack de referencia: Docker Compose

La topología de referencia, utilizada en slavadubrov/market-analyst-agent, consta de un worker LangGraph, un checkpointer Postgres, Qdrant para retrieval, un sidecar MCP, una cola Redis para ejecuciones asíncronas similares a producción y una pila de observabilidad opcional con Prometheus / Grafana / Loki / Tempo / OTel. En el compose local, Redis es opcional solo porque el runner síncrono puede llamar directamente al worker. docker compose up levanta localmente la topología principal; el sidecar MCP y la pila de observabilidad son perfiles opt-in (--profile mcp, --profile observability).

    checkpointer.setup()  # creates tables on first run
    graph = builder.compile(checkpointer=checkpointer)
    result = graph.invoke(
        {"messages": [{"role": "user", "content": "Continue the task"}]},
        {"configurable": {"thread_id": session_id}},
    )

Observabilidad que sobrevive a la ejecución

Los request handlers cortos son fáciles de depurar: cuando algo falla, lees la respuesta y el log en directo. Los agentes de larga duración no tienen ese lujo. Cuando falla una ejecución de seis horas, el evento interesante ocurrió hace cinco horas, la salida del terminal en directo ha desaparecido y el worker que la produjo ha sido sustituido. Nadie va a reconstruir la ejecución de memoria. Por eso depuras a partir de artefactos durables escritos mientras la ejecución seguía viva.

Byte dice

Si una ejecución larga falla después de que la salida interesante del terminal haya desaparecido, el event log durable y la traza son lo que queda para inspeccionarla.

Las pilas de producción suelen cubrir cuatro tipos de artefactos, en dos grupos. Dos se leen después de terminar la ejecución, para postmortems y replay: un event log consultable de cada paso y trazas OpenTelemetry de dónde se consumieron el tiempo y los tokens. Los otros dos se leen durante la ejecución. Uno es un tail en directo de lo que el agente está produciendo en el workspace. El otro es una pila de observabilidad por worktree que el propio agente puede consultar mientras trabaja.

Event log estructurado (se lee después de la ejecución)

Cada llamada al modelo, tool call, resultado, error y aprobación se escribe en almacenamiento durable, indexado por ID de sesión y timestamp. Cuando termina la ejecución, lo consultas como una tabla de base de datos normal. Addy Osmani fija claramente el estándar en Long-running Agents: «Si no puedes reconstruir lo que hizo el agente en las últimas 24 horas a partir de almacenamiento durable, lo que tienes es un shell script de larga duración que casualmente llama a un LLM, no un agente de larga duración».

Trazas OpenTelemetry GenAI (se leen después de la ejecución)

El mismo tipo de datos paso a paso se emite como spans utilizando los atributos estándar de las gen_ai.*convenciones semánticas: nombre del modelo, proveedor, recuento de tokens de entrada y salida, ID de conversación y nombre del workflow. Las convenciones siguen en estabilidad Development.

En 2026 salieron del repositorio principal de convenciones semánticas de OpenTelemetry y pasaron a su propio repositorio de convenciones semánticas GenAI. Los nombres de atributos se pueden utilizar para instrumentar, pero fija la revisión que hayas validado en lugar de un número de versión del repositorio principal. Los campos específicos del proveedor viven en subnamespaces (anthropic.*, openai.*) derivados de gen_ai.provider.name. La razón para usar el estándar es la portabilidad: en destinos compatibles con OTLP que admitan estas convenciones, cambiar de backend puede no requerir reinstrumentar el código, aunque pueden seguir siendo necesarios adaptadores del backend o configuración específica del destino.

Timeline de tool calls más diffs del workspace (se leen durante la ejecución)

Los cambios en el workspace ofrecen una vista rápida de lo que hace un agente durante una ejecución. El quick-start de Anthropic Harness Primitives for Long-Running Claude Agents utiliza monitorización en directo del workspace. Cuando watch está instalado, watch -n 5 'git log --oneline -8' actualiza los últimos commits cada cinco segundos. Para las capturas de pantalla, abre el directorio de capturas en un explorador de archivos, ordénalo por fecha de modificación con las más recientes primero e inspecciona las últimas imágenes. Los commits y las capturas son indicios de actividad; compáralos con los resultados de los tests y el estado de la ejecución antes de decidir que el agente está progresando.

Pila efímera por worktree (la consulta el propio agente durante la ejecución)

Según el artículo sobre el harness de OpenAI: «Los logs, métricas y trazas se exponen a Codex mediante una pila de observabilidad local efímera para cada worktree». Cada worktree del agente obtiene su propio Loki + Prometheus + Tempo de corta duración, limitado exclusivamente a esa ejecución. El agente lo consulta mientras trabaja. Eso permite que un prompt como «ningún span de estos cuatro recorridos de usuario supera los dos segundos» se convierta en algo que el agente puede verificar directamente, en lugar de tener que adivinarlo.

(El evaluador con contexto nuevo de la tabla de modos de fallo lee estos artefactos para decidir «done». Pertenece a la evaluación, no a la observabilidad; consulta § ciclo de vida de una ejecución saludable. Depende de todas las superficies anteriores.)

Una pila de observabilidad self-hosted mínima

Para algo como market-analyst-agent:

  1. OpenTelemetry Collector con el GenAI Normalizer Processor (contrib, alpha) para los atributos GenAI compatibles. Usa los procesadores genéricos Attributes o Transform para filtrar o reescribir campos gen_ai.*.
  2. Tempo (o Jaeger) para las trazas, indexadas por gen_ai.conversation.id / thread_id.
  3. Loki para las entradas estructuradas del event log.
  4. Prometheus para gen_ai.client.token.usage, gen_ai.client.operation.duration y gen_ai.client.operation.time_to_first_chunk — las métricas gen_ai.server.* proceden del servidor del modelo, así que solo las obtienes si alojas los pesos (consulta las convenciones de métricas GenAI).
  5. Dashboards de Grafana indexados por gen_ai.agent.name y gen_ai.request.model.

Alternativas alojadas (elige una, no tres):

  • LangSmith: integración nativa con LangGraph; también es el destino de despliegue de Deep Agents Deploy.
  • Braintrust: encaja mejor si la prioridad son las suites de regresión eval-first.
  • Arize Phoenix: OSS, nativo de OTLP (el protocolo de wire de OpenTelemetry), combinado con instrumentación de OpenInference.
  • Dashboard de tracing de OpenAI: automático cuando utilizas OpenAI Agents SDK o su integración con Temporal.
  • Tracing de Claude de Anthropic: para sesiones que se ejecutan dentro de Managed Agents.

El patrón de debug bundle

Cuando falla una ejecución, el worker debería dejar un /workspaces/${THREAD_ID}/_debug/ que contenga los artefactos que pedirías en un postmortem:

  • events.jsonl: exportación del event store append-only escrito por separado por el harness, incluidos intents de herramientas, resultados, aprobaciones y errores.
  • checkpoints.jsonl: historial del estado del grafo procedente de checkpointer.list({"configurable": {"thread_id": ...}}), etiquetado como checkpoints, no como event log.
  • last_state.json: StateSnapshot.values del último super-step completado correctamente.
  • trace.json: spans exportados mediante OTLP para la ejecución; los metadatos son la base y cualquier contenido capturado sigue la política de trazas.
  • tool_calls.csv: (ts, tool, input_hash, latency_ms, status, error).
  • workspace.tar.zst: el directorio del workspace más git diff frente al commit del inicializador.
  • screenshots/*.png: lo que vio el agente.
  • PROGRESS.md, feature-list.json y cualquier otro archivo de progreso escrito por el agente.
  • env.txt: tags de imagen, versión del modelo y SHA del commit del harness.

En conjunto, estos artefactos pueden proporcionar a una persona o a un agente revisor evidencias suficientes para reconstruir el fallo, siempre que el harness escribiera el event store mientras la ejecución seguía viva. «El agente se quedó atascado» es impreciso. Un informe ilustrativo es concreto: la sesión s_123 gastó el 71 % de sus tokens repitiendo tres comandos después de que fallara npm install.

Elegir la forma adecuada: guía de decisión

La mayor parte de la comparación anterior se reduce a unas pocas decisiones.

Empieza por la duración de la ejecución

Usa la duración como primer filtro:

  • Menos de 30 segundos, idempotente: SDK ligado al ciclo de vida de la petición en un servidor de aplicaciones.
  • De 30 s a 60 min: cola + worker + base de datos de checkpoints.
  • De 60 min a 24 h: la misma cola + worker o un Cloud Run Job para trabajo one-shot. Usa un motor de workflows durables si también necesitas versionado y replay.
  • Más de 24 h y debe sobrevivir a despliegues: motor de workflows durables (estilo Temporal). Cloud Run Jobs puede mantener trabajos largos hasta su límite de tarea, pero no proporciona semántica de replay.
  • Loops de entrenamiento de reinforcement learning de varios días: K8s Job + volumen + Temporal.

Después de ese filtro general, comprueba los efectos secundarios, la recuperación, el replay, el aislamiento, la ubicación de los datos y el equipo que operará el sistema.

Adecuación de la plataforma por caso de uso

La matriz es densa y ninguna celda verde decide por sí sola la arquitectura; normalmente la decisión la toman las celdas condicionales, donde una plataforma admite algo solo con una salvedad. Una cobertura amplia de cargas es útil, pero no muestra la residencia de datos, la semántica de replay, la dependencia del proveedor, la madurez operativa ni el coste de mover el estado más adelante.

Las celdas condicionales aplican la misma regla a todas las plataformas. Las opciones AWS/VPC y GPU de Deep Agents dependen de un despliegue híbrido o de un proveedor de sandbox; Managed Agents puede usar ejecución operada por el cliente manteniendo una orquestación alojada. La fila de elección del sandbox incluye una integración con un proveedor externo que construyes sobre un runtime propio o configuras en un harness gestionado. No promete una snapshot del estado en ejecución. Un Kubernetes Job también necesita una capa de API o cola para una petición interactiva; completarse rápidamente no lo convierte en un servicio HTTP. Compara el acceso de red, el hardware, la recuperación y la ruta de exportación del estado del despliegue elegido antes de seleccionarlo. La fila sobre el código del harness trata del acceso a la implementación del loop, no de la portabilidad de un despliegue gestionado ni de su estado. La ejecución de GPU en Kubernetes también requiere nodos GPU, drivers y un device plugin.

Managed Agents requiere Claude y una orquestación operada por Anthropic. Su sandbox self-hosted opcional puede encajar con la ejecución en redes privadas, pero un requisito de alojar tú mismo la inferencia o el control plane lo descarta. Revisa qué entradas de herramientas, resultados, skills y memoria pueden atravesar ese límite. El trabajo interno de coding puede encajar cuando esos flujos de datos son aceptables y el equipo quiere delegar la operación del harness.

Conviene modelar los precios antes de comprometerte, no después. La línea de horas de sesión es de $0.08/hora, además de los costes estándar de tokens. Si una única sesión se ejecutara continuamente, serían aproximadamente $58/mes por sesión. Con 100 sesiones ejecutándose continuamente, serían unos $5.800/mes antes de los tokens. Multiplica $0.08 por las horas de sesiones concurrentes previstas, súmalo a tu factura de tokens y compáralo con el coste de un stack de cola + worker en tu propia infraestructura. Migrar más adelante desde Managed Agents es un ejercicio de replatforming, no un cambio de configuración.

Harness alojado frente a harness propio

La distinción trata de quién opera el harness, no de quién escribió su código. Alojado significa que el proveedor ejecuta el loop del harness en su infraestructura y tú llamas a una API. Propio significa que ejecutas el loop en tu propia infraestructura, aunque el código del harness proceda de un proveedor.

LangChain aparece en ambos lados de esta línea, lo que puede confundir. Ofrece LangGraph, una librería con licencia MIT que alojas tú (propio), y Deep Agents Deploy, un producto gestionado que ejecuta un harness Deep Agents en LangSmith Deployment en su modo cloud predeterminado (alojado). Misma empresa, dos modelos operativos diferentes. Lo que eliges es quién ejecuta el loop, no el logo de la librería. (Deep Agents Deploy también tiene un modo self-hosted para equipos que quieren la ergonomía del harness sin el componente cloud; ese modo pertenece a la categoría propia.)

Elige un harness alojado cuando su compatibilidad de modelos, límite de datos, comportamiento de recuperación y puntos de extensión ya encajen. Elige un harness propio cuando esas restricciones sean requisitos que esperes cambiar. La migración entre ambos cambia el estado, la observabilidad y los límites de ejecución, así que prueba la ruta de salida antes de que los datos de producción dependan de ella.

Sandbox alojado frente a entorno de ejecución propio

Elige un sandbox alojado cuando el aislamiento, la pausa/reanudación o la semántica de fork del proveedor encajen con el modelo de amenazas y el presupuesto de arranque. Docker o Fargate pueden servir para cargas internas confiables que necesiten acceso a VPC o una residencia de datos estricta, pero un contenedor estándar no es un límite suficiente para código hostil. La parte 4 repasa el menú de aislamiento para ese caso.

Almacenes de estado: Git, DB y object storage juntos

Los agentes de larga duración suelen utilizar tres almacenes de estado a la vez porque cada uno es propietario de un artefacto diferente.

Git almacena el estado del workspace: el código, los documentos y los archivos de progreso que modifica el agente. Cada commit proporciona al harness un punto de recuperación estable y a la siguiente sesión un historial compacto.

La base de datos de checkpoints almacena el estado del grafo: qué se decidió, qué nodos se ejecutaron, qué resultados devolvieron y qué debe ejecutarse a continuación. El almacén de artefactos contiene salidas finales grandes, como PDF, archivos Parquet y capturas de pantalla. Esos artefactos no pertenecen a Git ni a la base de datos de checkpoints.

Cuándo usar git como estado

Usa git cuando la carga de trabajo tenga forma de código (ediciones en varios archivos, refactors, generación de aplicaciones) o de documento con suficiente importancia del historial de archivos. El patrón es sencillo: crea una rama de ejecución, haz un commit inicializador y después crea commits en límites significativos: tras la configuración, después de cada funcionalidad, cuando pasen los tests y tras la limpieza final. Guarda el SHA del último commit del workspace junto a la fila del checkpoint. Al reanudar, el siguiente worker hace checkout de la rama, lee git log --oneline -8, inspecciona git status y el diff más reciente y después lee PROGRESS.md o el archivo de handoff que haya escrito la sesión anterior.

Esto convierte git en una superficie de recuperación para el artefacto que se está editando, no en un sustituto de la base de datos de checkpoints. Git puede responder a dos preguntas: qué ha cambiado y qué versión ha pasado los tests. No puede decirle al harness qué nodo del grafo debe ejecutarse a continuación, qué tool call está esperando aprobación ni qué reintento ya utilizó su clave de idempotencia. El harness de Anthropic utiliza commits inicializadores y commits por funcionalidad como fuente de verdad para recuperar el workspace; el modelo lee git log --oneline -8 para recuperar el estado. Omite git cuando el producto de trabajo es una única respuesta conversacional. El overhead no compensa.

Cuándo usar checkpoints en una DB

Usa checkpoints de estilo PostgresSaver cuando el agente tenga una estructura de grafo con varios nodos cuyo estado intermedio importe (planner → researcher → writer → verifier). El repositorio de referencia lo utiliza precisamente por ese motivo. No introduzcas artefactos de workspace de escala terabyte en el checkpoint; deben ir a object storage.

Cuándo usar un almacén de artefactos (S3/GCS)

Usa object storage cuando:

  • la salida sea mayor de lo que debería transportar la base de datos de checkpoints;
  • los consumidores posteriores necesiten un artefacto direccionable mediante URL sin pasar por el agente; o
  • el entregable y el estado de la ejecución tengan ventanas de retención diferentes.

Por ejemplo, puedes eliminar el log de sesión después de 30 días, pero conservar el informe final durante años. Organiza el layout por (thread_id, checkpoint_id, artifact_name) para que la ejecución que lo produjo siga siendo reconstruible.

Cuándo solicitar aprobación humana

Define los requisitos de aprobación a partir del riesgo de la acción, la autoridad ya concedida y la política de despliegue. Una escritura reversible de borrador en una base de datos es distinta de un cargo a un cliente o un cambio destructivo en producción. Cuando se requiera aprobación, muestra la acción real, los argumentos y el destino, persiste esa decisión y vuelve a comprobarla si cambia la llamada propuesta; no ejecutes una llamada rechazada. interrupt() de LangGraph y el middleware de aprobación de Deep Agents pueden pausar la ejecución para tomar esa decisión. La parte 4 explica por qué esto es una decisión de permisos, no una instrucción del prompt.

Checklist práctico de producción

Antes de lanzar un agente de larga duración, responde a estas preguntas en términos concretos de infraestructura.

  1. ¿Qué almacén es propietario de los eventos de sesión y los checkpoints?
  2. ¿Qué ocurre si el worker muere a mitad de un tool call?
  3. ¿Puede una ejecución corromper el workspace de otra?
  4. ¿Qué acciones requieren aprobación?
  5. ¿Puede el modelo o el sandbox leer credenciales sin procesar?
  6. ¿Qué tool calls se pueden reintentar de forma segura?
  7. ¿Dónde se aplica el límite de coste por ejecución?
  8. ¿Qué evidencias deterministas deciden que la ejecución ha terminado y qué criterios restantes necesitan un revisor?
  9. ¿Dónde viven las salidas finales cuando desaparece el sandbox?
  10. ¿Podemos explicar mañana una ejecución fallida sin volver a ejecutarla?

Si la respuesta a alguna de estas preguntas es «el prompt le dice al agente que tenga cuidado», el sistema todavía no está desplegado. Sigue siendo una demo.
