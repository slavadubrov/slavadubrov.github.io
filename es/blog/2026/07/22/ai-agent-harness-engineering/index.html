Harness engineering para agentes de AI: diseñar el loop alrededor del modelo

Parte 6 de la serie Engineering the Agentic Stack

El reasoning loop de un agente elige la siguiente acción. Su harness aporta contexto, valida y autoriza las tool calls propuestas, envía las llamadas aceptadas al runtime, registra los resultados y decide si la tarea está completa.

Los modelos proponen ediciones y pueden declarar tareas como completadas, mientras que el harness aplica los permisos e interpreta las comprobaciones de aceptación que deciden si el loop puede detenerse. La Parte 5 cubría el runtime que mantiene vivo el proceso. Este artículo se centra en el código de control dentro de ese runtime: cómo medir si cada añadido ayuda y cómo mantener los controles resultantes localizables a medida que cambia el harness.

Más allá de la primera comprobación de aceptación explícita, cada retry, handoff o evaluador añadido es una hipótesis sobre un fallo observado. Solo se gana un sitio cuando una comparación controlada demuestra que ayuda.

Para concretar esa ruta de control, usaré un pequeño repositorio ficticio de una tienda. La tarea de código consiste en bajar el umbral para un descuento automático del 10% de $100 a $75 en src/checkout.py. El repositorio tiene dos comprobaciones obligatorias:

  • pytest tests/test_checkout.py verifica el cálculo del descuento.
  • pnpm playwright test tests/checkout_discount.spec.ts añade un artículo de $80 en una tienda local de pruebas y comprueba que la página de checkout muestra un descuento de $8.

El ejemplo es un fixture didáctico, no una aplicación real ni un benchmark. Cada intento empieza desde el mismo commit y los mismos datos de prueba sembrados. El harness solo puede aceptar el cambio cuando ambos comandos pasan y el trace vincula esos resultados al commit probado.

Las secciones posteriores cambian deliberadamente a otros dos ejemplos. Una API de pedidos en staging muestra por qué las llamadas que cambian estado necesitan protección frente a replay, mientras que una migración de un adaptador de pagos muestra qué necesita una nueva sesión de modelo para reanudar trabajo sin terminar. El laboratorio complementario cerca del final vuelve a ser distinto: se puede ejecutar, pero contiene tareas simuladas genéricas en lugar de este repositorio de tienda.

TL;DR: Empieza con un modelo, unas pocas tools limitadas y una comprobación de aceptación explícita. Añade retries cuando los traces muestren fallos transitorios en llamadas. Añade un progress handoff cuando las sesiones reanudadas repitan trabajo. Cuando pruebes cualquiera de los dos cambios, mantén fijos la versión del modelo, las tareas, el grader y el presupuesto total. Elimina el componente cuando no mejore el resultado medido.

El diagrama sigue el cambio del descuento desde la propuesta hasta la evidencia. El harness aporta la tarea y los archivos, comprueba los argumentos y permisos propuestos para edit_file y envía la llamada aceptada. Después de que el runtime aplique la edición, el harness ejecuta las pruebas de aceptación unitarias y de navegador indicadas. Un comando fallido vuelve al modelo como evidencia para otro turno; dos comandos que pasan hacen que el cambio pueda aceptarse.

Qué controla el harness

El recorrido del loop de Codex de OpenAI describe el ciclo básico. El harness monta un prompt, pide al modelo la siguiente acción, envía una tool call aceptada al runtime, añade el resultado y vuelve a preguntar hasta que el harness acepta el resultado o devuelve el control al usuario.

Las implementaciones pueden fusionar varias responsabilidades en un solo proceso. Los límites de fallo siguen siendo distintos:

TérminoFunciónEjemplo de agente de código
ModeloPropone texto, una tool call o una respuesta finalSugiere una edición en src/checkout.py
Reasoning loopElige el siguiente movimiento a partir del contexto disponibleInspeccionar, editar, probar, volver a inspeccionar
HarnessAporta contexto, autoriza y envía llamadas, registra resultados y comprueba la finalizaciónPermite ediciones bajo src/ y exige ambas pruebas nombradas
RuntimeEjecuta llamadas y mantiene el proceso vivo y aisladoWorker, sandbox, almacén de sesiones, cola

Cuando aparezca un fallo, diagnostica el límite que debería responder. Un mal plan puede necesitar mejores instrucciones o mejor razonamiento del modelo. Si edit_file apunta a una ruta fuera de src/, el harness debería rechazarlo, mientras que un proceso sandbox que muere antes de ejecutar la edición pertenece al runtime, que debe reiniciar el worker o informar del crash.

El propio caso de estudio sobre harness engineering de OpenAI describe una instancia arrancable de la aplicación para cada worktree. El equipo también conectó automatización de navegador al entorno del agente y expuso logs, métricas y traces.

Una tarea como “ningún span en estos cuatro recorridos críticos de usuario supera los dos segundos” pasó a ser verificable porque el agente podía ejecutar la aplicación y consultar las mismas señales que inspeccionaría un ingeniero. El caso de estudio es específico del producto. Lo transferible es la condición detrás del resultado: la aplicación y sus señales de rendimiento tenían que estar disponibles dentro del entorno del agente.

Lopopolo, autor de ese caso de estudio, mantiene una guía de campo sobre harness engineering que nombra las dos palancas que mueve este artículo: mantener fijos el modelo y el agente de código como una caja negra, e hacer ingeniería del contexto y las tools a su alrededor. Su planteamiento también explica por qué gran parte del harness acaba siendo código corriente.

El listón de calidad, los procedimientos, el historial de excepciones y las relaciones de autoridad de una organización quedan por debajo de la línea de flotación de lo que un modelo general puede conocer. El harness los expone como instrucciones del repositorio, reglas de permisos y comprobaciones de aceptación. Cada ejecución aceptada puede retroalimentar sus lecciones en esos artefactos en lugar de depender de que la siguiente sesión las redescubra.

Sigue el cambio de descuento desde la propuesta hasta la aceptación

Para la tarea de descuento definida arriba, el modelo propone cambiar calculate_discount en src/checkout.py. Ocurren varias cosas antes de que esa edición cuente como progreso:

  1. El constructor de contexto aporta la tarea, las instrucciones del repositorio, los archivos relevantes, los resultados previos de tools y el plan actual.
  2. El modelo propone una llamada a edit_file con una ruta y el texto de reemplazo.
  3. El límite de la tool (el código del harness entre la propuesta y la ejecución) valida los argumentos, comprueba la ruta frente al alcance permitido y pide aprobación si la operación la necesita.
  4. El runtime aplica la edición en el sandbox y devuelve un resultado estructurado.
  5. El harness ejecuta pytest tests/test_checkout.py y, a continuación, pnpm playwright test tests/checkout_discount.spec.ts, y lee ambos códigos de salida. La prueba de navegador comprueba el descuento visible de $8 en el carrito sembrado de $80.
  6. El harness decide qué significan los resultados. Una comprobación fallida se convierte en nuevo contexto para el siguiente turno del modelo, y una ejecución que pasa hace que la tarea sea candidata a completarse.
  7. Un resultado satisfactorio solo se convierte en evidencia de finalización después de que el harness registre el comando, el código de salida y la versión del artefacto probado en el trace.

En el paso 2, todavía no ha cambiado ningún archivo. El harness puede rechazar ../../secrets.env, exigir aprobación para un comando destructivo o detener una ejecución que ya haya agotado su presupuesto. Después de que se ejecuten las pruebas, el harness lee por sí mismo sus códigos de salida. El modelo no puede marcar su propia edición como correcta.

El trace debería mostrar la ruta propuesta y el texto de reemplazo, la decisión de permisos, los archivos que cambiaron, el commit probado y los resultados de ambos comandos. Un mensaje final done sin esos registros no demuestra que este cambio haya pasado sus comprobaciones obligatorias.

Decide dónde se aplica cada regla

Pon tests/checkout_discount.spec.ts en lógica normal del programa. El harness envía el comando de Playwright al runtime, lee su código de salida y se niega a terminar la ejecución mientras falle. Un prompt puede recordar al modelo que ejecute la prueba. No puede impedir que el modelo declare éxito sin evidencia.

Otras reglas encajan mejor en capas distintas:

Los contratos de las tools separan propuesta y permiso

La tarea del descuento solo necesita ediciones de archivos y comandos de prueba. Una API que cambia estado tiene un modo de fallo distinto, así que para esta sección cambiamos de ejemplo. Supongamos que el agente puede llamar a create_test_order contra un servicio de pedidos en staging mientras prepara datos de prueba. Esta tool no forma parte de las comprobaciones de aceptación de la tarea del descuento. Es útil aquí porque un timeout puede ocultar si el servicio ha creado un pedido.

El límite de la tool necesita algo más que una descripción en lenguaje natural. Para create_test_order, el harness necesita un contrato con:

  • argumentos validados, para que la entrada malformada se rechace antes de la ejecución
  • un resultado estructurado como { "order_id": "123", "created": true }, para que comprobaciones posteriores no tengan que parsear texto libre
  • una categoría de efecto que registre si la llamada solo obtiene información o cambia un archivo, un registro de base de datos o un servicio externo. También registra si repetir la llamada es seguro. Esta etiqueta le dice al harness si un retry automático podría duplicar trabajo: puede reintentar get_order_status cuando el servicio defina esa consulta como de solo lectura, pero no debe reintentar a ciegas create_test_order porque la primera llamada puede haber creado ya el pedido
  • una política de timeout y retry, para que una respuesta perdida no dispare una secuencia ilimitada de llamadas
  • una regla de permisos que indique qué aprobación se requiere. Leer el estado de un pedido puede ejecutarse automáticamente, mientras que crear un pedido puede requerir confirmación

La descripción en lenguaje natural es texto mostrado al modelo. Podría decir, “Crear un pedido de prueba para verificar el checkout”. Esa frase ayuda al modelo a decidir cuándo proponer create_test_order. No autoriza la llamada. En este ejemplo, el cliente MCP del harness valida los argumentos, aplica sus propias reglas y comprueba la confianza en el servidor, los requisitos de aprobación y la seguridad de retry antes de enviar nada.

Un servidor MCP publica descripciones de tools y anotaciones opcionales de comportamiento para el cliente. Un servidor defectuoso o malicioso podría describir una tool que cambia estado como inofensiva. Si el cliente aceptara automáticamente esa afirmación, podría ejecutar o reintentar create_test_order sin aprobación y crear un duplicado, así que la especificación de MCP exige que los clientes traten las anotaciones de tools como no fiables a menos que el propio servidor sea de confianza.

La especificación no prescribe un ajuste universal de confianza. Por tanto, el cliente necesita una política de confianza explícita para su despliegue; un servidor no puede hacer que sus propias anotaciones sean fiables. Esa política decide qué metadatos pueden influir en decisiones de permisos o retry y qué anotaciones siguen siendo solo orientativas.

Reintentar una llamada que cambia estado necesita protección frente a replay

Aparece un problema de retry más difícil cuando create_test_order crea el pedido pero se pierde su respuesta HTTP. El harness ve un timeout y no puede saber si el servidor completó la solicitud. Repetir la llamada puede crear un segundo pedido.

Una consulta de estado puede reintentarse cuando el servicio la define como de solo lectura. Una llamada de creación necesita protección, como una clave de idempotencia: el cliente adjunta un identificador de solicitud único, y el servicio devuelve el primer resultado en lugar de crear otro pedido cuando vuelve a ver ese identificador. Sin esta protección, el harness debería comprobar si el pedido existe o pedir una decisión humana antes de otro intento. AWS documenta este patrón en su guía sobre APIs idempotentes.

La aceptación necesita evidencia independiente

Una respuesta satisfactoria de create_test_order solo establece que la tool devolvió datos. No demuestra que una tarea de código haya pasado sus pruebas. Si una prueba posterior de navegador depende del pedido preparado en staging, el harness debe validar el schema de la respuesta y aun así ejecutar esa prueba antes de aceptar el cambio de código.

Algunos criterios no pueden reducirse a un código de salida. Para una tarea aparte de diseño visual, un evaluador nuevo puede comparar una página o diagrama renderizado con una rúbrica escrita. Los equipos deberían contrastar ese evaluador con revisiones humanas antes de usarlo como gate de finalización.

Una migración de adaptador de pagos necesita un handoff

Cambiemos otra vez de tarea, pero sigamos en el repositorio ficticio de la tienda. Ahora el agente tiene que migrar el checkout del adaptador de pagos v1 a v2. El trabajo abarca el handler de checkout, el cliente de pagos, la configuración y las pruebas, así que puede durar más que una sesión de modelo.

Antes de que la primera sesión alcance su límite de contexto, ha modificado varios archivos, ha arrancado un sandbox local de pagos y ha dejado tests/payment_migration.spec.ts fallando. Esa prueba de aceptación de navegador completa un pago a través del adaptador v2 y verifica el ID de proveedor registrado. Un resumen de la conversación puede orientar la siguiente sesión de modelo, pero no puede reiniciar el sandbox ni demostrar qué archivos están modificados en ese momento.

La siguiente sesión tiene que recuperar tres cosas:

Qué debe recuperarseQué incluyeCómo puede fallar
Historial de conversaciónMensajes, tool calls y resultados devueltosLos detalles antiguos desplazan a la tarea actual
Entorno de trabajoArchivos, sandbox de pagos y estado de las pruebas de navegadorLa transcripción dice que un servicio está ejecutándose cuando ya ha muerto
Progreso de la tareaPlan, comprobaciones completadas, aprobación pendiente, siguiente acciónLa siguiente sesión repite trabajo terminado

La compactación sustituye mensajes antiguos por un resumen más corto para que la sesión actual pueda continuar. Un progress handoff registra lo que necesita la siguiente sesión: la rama actual, los archivos cambiados, el último comando de prueba y su salida, y el siguiente paso sin resolver. Si la conversación antigua contiene supuestos obsoletos, el harness puede iniciar una sesión nueva de modelo con ese handoff y el workspace actual. Sustituir un worker caído y restaurar sus procesos es una tarea de recuperación distinta del runtime.

Una pequeña edición de documentación puede no necesitar ninguno de estos mecanismos. La migración de pagos necesita un handoff una vez que el trabajo cruza varias sesiones porque la siguiente sesión de modelo debe reconstruir tanto el workspace como el estado de la tarea.

Los experimentos de Anthropic con agentes de código de larga duración usaron historial de git y un archivo de progreso entre sesiones, mientras que su informe posterior sobre diseño de harnesses separa la compactación de un handoff con contexto nuevo e informa de la orquestación adicional, el uso de tokens y el tiempo total requeridos por los handoffs.

Usa traces para distinguir tres fallos

Las tres filas siguientes son bocetos ilustrativos de traces, no ejecuciones medidas ni salida del laboratorio complementario. Cada fila muestra un fallo distinto y, por tanto, una respuesta distinta del harness.

Lo que registra el traceQué ocurrióRespuesta correcta
La llamada de solo lectura get_order_status devuelve 503; no hay ninguna llamada que cambie estado en vueloFalló una consulta transitoriaReintentar la consulta con un límite y backoff
create_test_order agota el timeout y luego una consulta de estado encuentra el pedido 123 bajo la clave de idempotencia checkout-42El servicio creó el pedido, pero se perdió la respuestaDevolver el pedido existente; no crear otro
La edición y la prueba unitaria pasan, pero el trace no tiene resultado para tests/checkout_discount.spec.ts en el commit probadoFalta la evidencia de aceptación obligatoriaMantener la ejecución abierta y lanzar la prueba de aceptación en navegador

Esta distinción importa porque un 503 no hace que todas las llamadas sean seguras de reintentar. La primera fila es una consulta de solo lectura. La segunda es una solicitud que cambia estado, así que la clave de idempotencia y el estado en el servidor deciden si se permite otro intento de creación. La tercera ni siquiera es un fallo de tool; el harness todavía no ha recogido la evidencia necesaria para aceptar el cambio del descuento.

Una transcripción de chat registra lo que vio el modelo. No puede demostrar si el servicio de pedidos confirmó una solicitud antes de que desapareciera la respuesta. El trace debe unir la llamada del cliente, la decisión de aprobación, la clave de idempotencia, el resultado del servidor o la consulta de estado, el commit probado y el resultado de la prueba de aceptación. Esos campos le dicen al harness en cuál de los tres caminos está.

Síntoma repetidoPequeño cambio a probarQué medir
Las consultas de solo lectura fallan de forma transitoriaRetry acotado con backoffTasa de recuperación, llamadas extra, tiempo total
Las sesiones reanudadas repiten trabajo completadoProgress handoff estructuradoAcciones de tool duplicadas tras reanudar
Faltan pruebas obligatorias al completarGate de aceptación fail-closedTareas aceptadas sin todas las comprobaciones obligatorias
Los defectos visuales sobreviven a comprobaciones deterministasEvaluador nuevo con una rúbrica escritaDefectos detectados, falsos rechazos, tiempo de revisión

Antes de añadir un componente, nombra el fallo repetido que debería reducir y el número que vas a seguir. Elimina el componente si una comparación controlada no mueve ese número lo suficiente como para compensar su coste.

Mide un cambio cada vez

Una ablación mide si un componente del harness causa el efecto esperado cambiando o eliminando ese componente mientras el resto del experimento se mantiene fijo. Por ejemplo, ¿el linting del editor ayuda a este modelo en este conjunto de tareas?

Usa el siguiente protocolo:

  1. Congela la versión del modelo, las instancias de tarea, el entorno, el grader y los prompts fuera del componente bajo prueba.
  2. Da a ambas variantes el mismo presupuesto total de tokens, tiempo y dinero.
  3. Elige el número de pruebas o la regla de parada antes de ejecutar la comparación.
  4. Ejecuta las mismas instancias de tarea en ambas variantes. Como las salidas del modelo varían, repite cada tarea varias veces.
  5. Informa de la media junto con la dispersión o el intervalo de confianza.
  6. Cuenta cada prueba iniciada, incluidos timeouts, paradas por política, crashes del harness y fallos del evaluador.

La tasa de éxito por sí sola puede ocultar un componente caro. Como mínimo, sigue las tareas rotas aceptadas como completadas, el coste y el tiempo total por tarea completada, los errores de tool, los pedidos duplicados, los minutos de revisión y los overrides manuales de permisos. Elige la métrica que arrastre el coste real para el producto. Una subida de dos puntos en tareas completadas es un mal intercambio si duplica la cola de revisión.

Un experimento emparejado de migración de pagos hace medible el progress handoff. Cada par control/tratamiento arranca desde el mismo commit del repositorio y el mismo checkpoint sembrado, con el mismo modelo, tarea, grader y presupuesto total. El handoff es el único interruptor. La métrica principal cuenta acciones de tool duplicadas tras reanudar: una acción es duplicada cuando su operación y artefacto coinciden con un paso que la sesión anterior ya había completado.

El artículo de SWE-agent fija GPT-4 Turbo sobre la partición SWE-bench Lite de 300 tareas y reporta un 18.0% de tareas resueltas con su interfaz completa, frente al 11.0% del agente solo con shell. El artículo también cambió características individuales de la interfaz:

Cambio de interfazResueltas
Interfaz completa de SWE-agent18.0%
Editor sin linting15.0%
Archivo completo en lugar de un visor de 100 líneas12.7%
Historial completo de observaciones en lugar de las cinco últimas15.0%

Estos números pertenecen a ese modelo, benchmark y tope de $4 por tarea. Las filas without linting, full file y full history son las pruebas útiles de una sola característica: cada una cambió una característica de la interfaz mientras el modelo y la configuración de evaluación permanecían fijos.

LangChain publicó una comparación más amplia con modelo fijo para deepagents-cli. Informa de una subida en Terminal-Bench 2.0 del 52.8% al 66.5% con gpt-5.2-codex fijo mientras su equipo cambiaba el system prompt, las tools y el middleware. La entrada agrupa varios cambios y omite un intervalo de confianza, una comparación con presupuesto total fijo y una tabla de ablación por cambio. Ese resultado no puede identificar cuál fue el cambio útil.

El informe de Anthropic sobre aplicaciones de larga duración es un caso de estudio cualitativo y específico de producto, no un benchmark controlado. Su evaluador comprobó 27 criterios del editor de niveles en Sprint 3. El equipo informa de que las llamadas al evaluador pasaron a ser overhead en tareas que Opus 4.6 podía completar de forma fiable por sí solo, pero seguían ayudando cerca del límite del modelo, así que eliminó componentes del harness uno a uno tras la actualización del modelo. El ejemplo sirve para revalidar scaffolding antiguo cuando cambia el modelo; no estima un tamaño de efecto general.

Mantén el harness editable después de que se gane su sitio

La ablación mantiene pequeño un harness, pero su código puede sobrevivir al modelo para el que fue ajustado. Una petición como “enmascara secretos en todas las rutas de captura” nombra un comportamiento, no un archivo. En un harness de producción, ese comportamiento puede abarcar etapas de ejecución y estado compartido. Una persona o un agente de código debe encontrar cada punto de implementación antes de cambiarlo con seguridad.

Un preprint de 2026 de Wang et al., el Harness Handbook, llama a este paso behavior localization. El handbook construye un mapa centrado en comportamientos a partir del código del harness. El análisis estático extrae un grafo del programa sin llamadas al modelo, y luego un LLM organiza sus unidades en etapas de ejecución.

La persona mantenedora o el agente de código empieza con una visión general del sistema, abre la etapa de ejecución relevante y desciende hasta entradas ancladas al código fuente para una función o archivo. Una vista de registro anota dónde se escribe y se lee el estado compartido entre etapas. Esta jerarquía mantiene pequeña la vista general mientras preserva una ruta hasta el código fuente.

La frescura es una regla aparte. Cada localizador debe resolverse contra el repositorio vivo. El handbook excluye entradas obsoletas en lugar de adivinar, y cada diff no vacío resincroniza las entradas a las que afecta.

El diagrama comprime el loop de modificación: una petición basada solo en comportamiento desciende por los niveles del handbook, cada localizador candidato se verifica contra el repositorio vivo antes de escribir el plan, y cada diff aplicado resincroniza el mapa.

La evaluación del Handbook sigue el protocolo que defiende este artículo. En dos harnesses open source (Terminus-2, seis archivos Python, y el monorepo de Codex, 2.267 archivos Rust), un planner de solo lectura impulsado por DeepSeek-V4-Pro o bien exploró directamente el repositorio o bien pasó por el handbook. Las peticiones, el repositorio, los permisos de tools y la decodificación fueron idénticos en ambos brazos. Tres jueces (GPT-5.5, Opus 4.8, DeepSeek-V4-Pro) puntuaron cada plan de edición en localización, control de alcance y razonamiento:

HarnessTasa de victoria baselineAsistido por HandbookTokens del planner
Terminus-2 (6 archivos)26.7%45.6%−8.6%
Monorepo de Codex (2.267 archivos)28.3%38.3%−12.7%

El planner asistido por el handbook ganó más veces y usó menos tokens de planner en ambos repositorios. Las condiciones siguen ligadas a ese resultado: tres jueces LLM puntuaron planes de edición producidos por un modelo planner sobre dos harnesses. El estudio evaluó planes, no diffs ejecutados ni tasas de defectos en producción.

Las secciones anteriores usan traces para responder por qué existe un componente. Este mapa responde a la siguiente pregunta: ¿dónde vive ese componente cuando tiene que cambiar?

Prueba el método en el laboratorio complementario

El proyecto harness-demo en el commit 517353f3 es un ejercicio pequeño y determinista con 12 tareas sintéticas genéricas que cubren cambios de código como fix-parser-edge-case, split-large-module y wire-browser-test. No implementa el repositorio ficticio de la tienda.

Cada fixture de tarea declara una dificultad más cuatro condiciones booleanas: una tool inestable, pérdida de progreso, un hueco de implementación no detectado y una finalización ambigua. El simulador deriva una quinta condición para las tareas difíciles que también necesitan un archivo de progreso: sin context_reset, la compactación preserva supuestos obsoletos. Un grader determinista marca una tarea como superada solo cuando la configuración seleccionada maneja todas las condiciones aplicables. No se ejecuta ningún modelo ni servicio externo.

Los comandos responden a preguntas distintas:

  • make check ejecuta Ruff y siete pruebas unitarias, incluida la validación que rechaza cualquier par de ablación que cambie más de un componente.
  • make run imprime una matriz didáctica acumulativa y luego cinco comparaciones válidas de dejar fuera un componente cada vez.
  • make failures nombra la condición no gestionada para cada tarea fallida. El harness completo debería terminar con all synthetic tasks pass.

make run
make failures

La sección causal de make run tiene este aspecto:

component                 control  treatment  delta
retry_policy              8/12     12/12       +4
progress_handoff          7/12     12/12       +5
evaluator                 8/12     12/12       +4
fail_closed_acceptance    7/12     12/12       +5
context_reset            10/12     12/12       +2

Para cada fila, el control es la configuración completa con un componente eliminado; el tratamiento restaura únicamente ese componente. La matriz acumulativa anterior es útil para orientarse, pero algunas de sus filas adyacentes añaden varios componentes a la vez y por tanto no pueden identificar una causa.

El laboratorio valida cada par declarado antes de ejecutarlo. Sus pruebas de regresión también incluyen un par intencionadamente no válido que cambia a la vez la política de retry y el evaluador; el validador lo rechaza.

El schema de configuración del laboratorio comprueba los cinco campos de componente. Este fragmento ejecutable muestra la misma protección sobre un par válido de progress handoff:

from dataclasses import dataclass, fields


@dataclass(frozen=True)
class Config:
    progress_handoff: bool = False
    evaluator: bool = False
    retry_policy: bool = False
    fail_closed_acceptance: bool = False
    context_reset: bool = False


def changed_components(control: Config, treatment: Config) -> tuple[str, ...]:
    return tuple(
        field.name
        for field in fields(control)
        if getattr(control, field.name) != getattr(treatment, field.name)
    )


control = Config(progress_handoff=False, evaluator=True, retry_policy=True)
treatment = Config(progress_handoff=True, evaluator=True, retry_policy=True)
assert changed_components(control, treatment) == ("progress_handoff",)

Empieza con un loop y una comprobación de aceptación

Yo empezaría un harness de agente de código con un modelo capaz, instrucciones del repositorio, unas pocas tools limitadas, un sandbox y una prueba de aceptación explícita. Registraría tool calls, resultados, costes y esa prueba final en un único trace para que los primeros fallos útiles sean visibles sin reconstruirlos a partir de logs de terminal y transcripciones de chat. Esta es una baseline propuesta, no evidencia de un sistema desplegado.

A partir de ahí, añade solo lo que justifique un trace. Registra quién mantiene cada componente, cuántos tokens o segundos añade y qué prueba de regresión justificaría eliminarlo tras una actualización del modelo.

Seis meses después, alguien que vea progress_handoff=True debería poder encontrar los traces fallidos que lo justificaron y los casos de regresión que todavía hacen que siga ahí. Los traces explican por qué existe el componente; un mapa de comportamiento actualizado explica dónde tocarlo.
