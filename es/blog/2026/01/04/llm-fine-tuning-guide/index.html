Guía de fine-tuning de LLM: LoRA, QLoRA, Unsloth y Axolotl

Viacheslav Dubrov

2026-01-04 · Actualizado 2026-09-12 · 28 min · Ingeniería de modelos

Traducción automática

Esta guía está dirigida a ingenieros de Python que deben decidir si hacer fine-tuning de un large language model y cómo llevarlo a cabo. Aprenderás cuándo elegir fine-tuning frente a prompting o retrieval, y cómo escoger entre métodos como LoRA y QLoRA. La guía también explica cómo preparar los datos, evaluar el modelo entrenado y planificar su despliegue.

Los ejemplos explican configuraciones y comprobaciones. No constituyen una receta de entrenamiento end-to-end verificada; la sección práctica separa los comandos del repositorio complementario de una configuración de entrenamiento propuesta.

Para una comparación más breve de estas opciones, consulta Fine-Tuning vs RAG vs Prompting.

¿Deberías hacer fine-tuning?

Antes de gastar horas de GPU, decide si el fine-tuning es la herramienta adecuada para el problema que tienes delante.

Byte dice

Si el único comportamiento que falta es generar JSON válido, prueba primero el constrained decoding con los pesos originales. Una ejecución de entrenamiento es un rodeo muy largo para descubrir que faltaba una llave.

El fine-tuning modifica el comportamiento codificado en los pesos. El retrieval aporta evidencia en tiempo de inferencia, por lo que es un mejor punto de partida para hechos que cambian o necesitan citas. Los documentos nuevos solo están disponibles después de ingerirlos e indexarlos; comprueba que esa frescura cumple tus requisitos.

Los prompts claros y los ejemplos son más baratos de iterar que una nueva ejecución de entrenamiento. Puede que ya resuelvan un problema de estilo o de seguimiento de instrucciones. El fine-tuning puede reducir los tokens repetidos de los prompts, pero la latencia de serving depende del modelo, la longitud de salida, el hardware y la implementación; una actualización de pesos no acelera el sistema por sí sola.

Para la sintaxis, librerías como xgrammar y outlines enmascaran los siguientes tokens no válidos según un schema o una gramática compatibles. Una generación restringida completada correctamente pertenece a ese lenguaje. Gestiona por separado las truncaciones y otras generaciones incompletas, y valida el resultado antes de utilizarlo. La restricción no puede hacer que un ID de cliente sea correcto ni que una elección de herramienta sea adecuada. Mide su latencia en tu backend en lugar de asumir un overhead fijo.

Haz que el caso de negocio sea medible

El fine-tuning puede reducir los tokens recurrentes de los prompts o permitir que un modelo más pequeño alcance el objetivo, pero ninguno de estos ahorros es automático. Calcula el punto de equilibrio con tu tráfico y tus precios:

[ \text{peticiones de equilibrio} = \frac{\text{coste de entrenamiento + evaluación + despliegue}} {\text{coste base por petición} - \text{coste ajustado por petición}} ]

Si el denominador es pequeño, negativo o se basa en una suposición de calidad no demostrada, el proyecto todavía no tiene justificación económica.

[!TIP] La configuración híbrida Una arquitectura habitual combina un modelo más pequeño adaptado a la tarea con retrieval para los hechos cambiantes. Usa el modelo más grande con prompting como baseline y conserva el modelo pequeño solo si alcanza los mismos umbrales de calidad y seguridad específicos de la tarea.

Tipos de fine-tuning

El fine-tuning puede adoptar tres formas principales. Se diferencian en el tipo de datos que necesitan y en lo que enseñan al modelo.

1. Continued pre-training (self-supervised)

Entrenas el modelo base con más texto sin procesar, usando el siguiente token de cada secuencia como objetivo de entrenamiento. Es self-supervised learning: el propio texto proporciona sus objetivos, igual que en la ejecución original de pre-training.

Cuándo usarlo:

  • El dominio tiene vocabulario que el modelo base nunca ha visto (medicina, derecho, codebases internos).
  • Tienes grandes cantidades de texto del dominio, pero no pares etiquetados de (entrada, salida).
  • El modelo base falla con la terminología específica del dominio.

Ejemplo: entrenar con millones de notas clínicas para que el modelo aprenda abreviaturas médicas, nombres de fármacos y flujos de trabajo clínicos.

2. Supervised fine-tuning (SFT)

SFT se entrena con pares etiquetados de (entrada, salida). Muestras al modelo exactamente qué salida quieres para cada entrada.

Cuándo usarlo:

  • Tienes una tarea específica con un formato limpio de entrada/salida.
  • Dispones de datos etiquetados de calidad, aunque sean pocos.
  • Necesitas un comportamiento predecible para una forma de entrada conocida.

Ejemplo: entrenar con pares de (descripción de consulta SQL, código SQL) para text-to-SQL. Este intervalo fijo del calendario supone que signup_date se almacena en UTC:

{
    "input": "Get users who signed up in August 2026 (UTC)",
    "output": "SELECT * FROM users WHERE signup_date >= '2026-08-01' AND signup_date < '2026-09-01'"
}

3. Instruction tuning

Instruction tuning es un caso especial de SFT diseñado para que los modelos sigan una amplia variedad de instrucciones en lenguaje natural. Los datos de entrenamiento son pares de (instrucción, respuesta) procedentes de muchas tareas distintas.

Cuándo usarlo:

  • Quieres un asistente de propósito general (como ChatGPT o Claude).
  • El modelo debe gestionar peticiones variadas y abiertas.
  • Estás construyendo una interfaz de chat.

Ejemplo: entrenar con miles de instrucciones diversas como «Resume este artículo», «Escribe un poema sobre X» o «Explica Y con palabras sencillas».

El pipeline de fine-tuning en 7 etapas

El fine-tuning es un pipeline, no un único comando. Cada etapa tiene sus propios modos de fallo, y saltarse una suele manifestarse más adelante en forma de un modelo deficiente.

Cada etapa se apoya en la anterior:

  1. Preparación de datos — Define la unidad de evaluación, divide los datos y después límpialos y dales formato
  2. Selección del modelo — Elige el modelo base adecuado y carga los pesos
  3. Configuración del entrenamiento — Configura el hardware, los hiperparámetros y la estrategia de optimización
  4. Fine-tuning — Ejecuta entrenamiento SFT, DPO u ORPO
  5. Evaluación — Mide el rendimiento y valida la calidad
  6. Despliegue — Exporta y sirve el modelo
  7. Monitorización — Sigue el rendimiento, realiza el mantenimiento e itera

[!WARNING] Los datos son la base El entrenamiento reproduce los fallos sistemáticos de los ejemplos. Inspecciona las etiquetas, las fugas, la cobertura y el cumplimiento de políticas antes de dedicar tiempo a barridos del optimizador.

Etapa 1: Preparación de datos

Muchos proyectos de fine-tuning fallan aquí, no durante el entrenamiento. La preparación moderna de datos es algo más que ejecutar una regex sobre CSVs.

Cinco transformaciones después de dividir el origen

Asigna los grupos de origen a train o evaluación antes de transformar las filas. Un ticket de soporte y todas sus reescrituras deben permanecer en la misma partición. Agrupa los duplicados aproximados conocidos antes de asignar los grupos y vuelve a comprobarlos entre particiones después de la limpieza. Congela el conjunto de evaluación; aumenta únicamente los datos de training.

Haz una lista de los errores que tus ejemplos deben enseñar al modelo a corregir y define después los campos y etiquetas obligatorios de cada fila. Elige herramientas de procesamiento para esos pasos; DataTrove y Distilabel pueden ayudar con datasets grandes.

1. Ingesta y filtrado

  • Acción: elimina UTF-8 corrupto y contenido fuera de tarea. Etiqueta las denegaciones según la política: conserva las denegaciones correctas como objetivos de training y casos de evaluación; excluye únicamente las denegaciones inválidas o fuera de tarea.
  • Herramientas: Trafilatura para la extracción y los modelos de identificación de idioma de fastText para el language ID; los modelos distribuidos de lid.176 reconocen 176 idiomas.

2. Política de datos sensibles

  • Acción: decide qué puede aprender el modelo y, según corresponda, redacta, tokeniza o excluye los campos personales y confidenciales.
  • Herramientas: Microsoft Presidio o scrubadub.
  • Motivo: un detector es solo un control; los requisitos de procedencia, consentimiento, conservación, acceso y borrado siguen siendo aplicables.

3. Deduplicación (MinHash LSH)

  • Acción: elimina duplicados aproximados para reducir la repetición y el riesgo de fugas; esto no evita la memorización.
  • Herramientas: DataTrove gestiona bien el procesamiento a escala de terabytes.

4. Aumento sintético, si es necesario

  • Acción: utiliza un modelo teacher adecuado para reescribir ejemplos de training en pares instrucción-respuesta, conservando sus IDs de origen. No aumentes la partición reservada para evaluación.
  • Herramientas: Distilabel.
  • Validación: muestrea las salidas del teacher, compruébalas con la misma rúbrica que las etiquetas humanas e informa por separado de los resultados de los ejemplos sintéticos y los escritos por personas. Este subconjunto de evaluación se denomina slice; otros slices útiles incluyen el idioma y el tipo de tarea.

5. Formato

  • Acción: convierte los datos a un formato estándar (Alpaca o ShareGPT).

Ejemplos de formatos de datos

Formato Alpaca (seguimiento de instrucciones):

{
    "instruction": "Summarize the following text.",
    "input": "The text to be summarized...",
    "output": "This is the summary."
}

Almacenamiento con estilo ShareGPT (conversacional):

{
    "conversations": [
        { "from": "user", "value": "Hello, who are you?" },
        { "from": "assistant", "value": "I am a helpful AI assistant." }
    ]
}

Lo que importa realmente

  • Cobertura antes que volumen. Añade ejemplos que representen modos de fallo distintos, no repeticiones del caso mayoritario fácil.
  • Limpieza. Elimina texto irrelevante, normaliza los espacios y mantén un formato coherente.
  • Equilibrio. Conserva los casos raros importantes e informa del rendimiento por slice.
  • Separación. Divide por origen, usuario, documento o tiempo cuando dividir filas aleatoriamente pueda filtrar duplicados aproximados.
  • Procedencia. Registra el origen, la licencia o permiso, el historial de transformaciones y la vía de borrado de cada versión del dataset.

Etapa 2: Selección del modelo y hardware

El modelo base y sus requisitos mínimos de memoria de GPU determinan qué puedes entrenar.

Empieza por el modelo base más pequeño que ya supere las comprobaciones baseline no negociables. Confirma:

  • los términos de licencia y redistribución del producto previsto;
  • el comportamiento en idioma, dominio, uso de herramientas y seguridad antes de la adaptación;
  • la compatibilidad del tokenizer y la chat template con el dataset;
  • el contexto máximo y el comportamiento de truncation que necesitan los ejemplos reales;
  • la compatibilidad tanto con el framework de entrenamiento como con el motor de serving objetivo.

El fine-tuning es un paso de adaptación, no una reparación para un modelo base inadecuado. Si el modelo falla en capacidades que el dataset no cubre, elige otro modelo base antes de ejecutar más epochs.

Dimensiona la ejecución, no la categoría comercial

No existe una tabla duradera de «tamaño del modelo → GPU». La memoria máxima cambia según la precisión de los pesos, el optimizador, el número de parámetros entrenables, la longitud de secuencia, el micro-batch, el activation checkpointing, la implementación de attention y el overhead del framework. Empieza con una estimación de memoria y después ejecuta un smoke test corto con la longitud máxima sobre el stack exacto.

El paper original de QLoRA consiguió ajustar un modelo LLaMA de 65B en una GPU de 48 GB con su configuración específica. Ese resultado es un límite orientativo, no una promesa de que cualquier arquitectura actual de 70B, longitud de contexto, kernel o trainer vaya a caber en el mismo dispositivo.

Cálculo de memoria

Para un modelo con PPP parámetros, los pesos por sí solos requieren aproximadamente 2P2P2P bytes en BF16/FP16 o 0.5P0.5P0.5P bytes a cuatro bits, antes de contar los metadatos de quantization y los buffers de runtime. El entrenamiento completo con Adam añade gradientes, estados del optimizador y, a menudo, pesos maestros de mayor precisión. LoRA evita la mayor parte de la memoria de los estados entrenables; QLoRA reduce además la huella de los pesos base congelados. Las activations pueden seguir dominando con longitudes de secuencia grandes.

Usa este flujo de trabajo:

  1. Elige la secuencia más larga y el micro-batch que debas admitir.
  2. Estima los pesos y el estado entrenable, dejando margen para activations y kernels.
  3. Ejecuta un paso de forward/backward con la longitud máxima.
  4. Registra la memoria máxima allocated y reserved.
  5. Solo después escala el tamaño del batch, el rank, la longitud de secuencia o el número de GPUs.

Etapa 3: Configuración y métodos de entrenamiento

De las filas almacenadas a los objetivos de entrenamiento

ShareGPT es una estructura de dataset; ChatML es una convención de serialización. Convierte from/value en los roles y campos que acepte el trainer y utiliza después la chat template del modelo seleccionado. No sustituyas los tokens por los de ChatML solo porque los datos sean conversacionales.

Para la fila de saludo anterior, los mensajes normalizados son:

messages = [
    {"role": "user", "content": "Hello, who are you?"},
    {"role": "assistant", "content": "I am a helpful AI assistant."},
]
# Inspection step after loading the selected model's tokenizer:
rendered = tokenizer.apply_chat_template(
    messages, tokenize=False, add_generation_prompt=False,
)
print(rendered)

Inspecciona la fila serializada real antes del entrenamiento: los delimitadores de rol, los tokens de fin de turno y los tool schemas deben coincidir con la inferencia. En una fila de uso de herramientas, conserva las definiciones de herramientas, los tool calls del assistant y los tool results como campos distintos. Comprueba que la truncation no elimine la respuesta supervisada ni corte un argumento de herramienta por la mitad.

El loss masking determina qué tokens se recompensan cuando el modelo predice. En el entrenamiento de secuencia completa, el texto de usuario, system, herramienta y assistant puede contribuir. En el entrenamiento solo del assistant, esos tokens de contexto siguen visibles para attention, pero sus labels se ignoran (habitualmente -100); solo contribuyen los spans del assistant. Para este saludo, la respuesta debe ser un objetivo y la pregunta del usuario no, si la intención es entrenar solo el comportamiento del assistant.

La documentación de SFT de TRL admite assistant_only_loss=True para datasets conversacionales cuyas templates exponen spans de generación. Una template sin esos spans no puede proporcionar esa máscara. Los datasets de prompt/completion tienen una opción completion_only_loss independiente. Antes de activar cualquiera de las dos, inspecciona un batch tokenizado y decodifica los tokens cuyos labels no se ignoran. Repite después la comprobación con una conversación con herramientas y un ejemplo de longitud máxima. La configuración de entrenamiento ilustrativa siguiente utiliza deliberadamente loss sobre la secuencia completa; el entrenamiento solo sobre el assistant requiere esta comprobación adicional de la template y la máscara.

Elige la longitud de secuencia a partir de la distribución de los datos y ejecuta la comprobación de memoria con la longitud máxima de la Etapa 2. El packing coloca varios ejemplos cortos en una única secuencia de entrenamiento. Empieza sin packing para poder inspeccionar fácilmente los límites entre filas. Haz benchmark del packing solo después de confirmar que las filas serializadas y los labels son correctos.

Fine-tuning completo frente a PEFT

El fine-tuning completo (FFT) actualiza todos los pesos, por lo que los gradientes y el estado del optimizador escalan con todo el modelo. El pico de memoria no se puede inferir solo a partir del número de parámetros, pero queda muy por encima de la memoria necesaria para cargar los pesos durante la inferencia.

El fine-tuning eficiente en parámetros (PEFT) entrena solo un subconjunto pequeño de parámetros y congela el resto. Las cuentas resultan mucho más manejables.

LoRA: el punto de partida

LoRA (Low-Rank Adaptation) congela una matriz preentrenada y representa su actualización aprendida mediante dos matrices más pequeñas. El paper original lo motiva con la hipótesis de que las actualizaciones útiles de adaptación tienen un rank intrínseco bajo.

Aquí, dind_{in}din​ es el ancho de entrada de la capa y doutd_{out}dout​ su ancho de salida. El rank rrr es la dimensión compartida menor de las dos matrices entrenables: un rank más pequeño utiliza menos parámetros entrenables. El ajuste α\alphaα controla la escala de la actualización mediante la relación α/r\alpha/rα/r.

Para una matriz congelada W0∈Rdout×dinW_0 \in \mathbb{R}^{d_{out} \times d_{in}}W0​∈Rdout​×din​, LoRA aprende:

  • A∈Rr×dinA \in \mathbb{R}^{r \times d_{in}}A∈Rr×din​
  • B∈Rdout×rB \in \mathbb{R}^{d_{out} \times r}B∈Rdout​×r

La capa adaptada es:

W′=W0+αrBAW' = W_0 + \frac{\alpha}{r}BAW′=W0​+rα​BA

El adapter tiene r(din+dout)r(d_{in}+d_{out})r(din​+dout​) parámetros entrenables en lugar de dindoutd_{in}d_{out}din​dout​ para esa matriz. Para una matriz cuadrada de ancho 4.096 con rank 16, eso supone una reducción de 128× en los parámetros entrenables de esta matriz. El ahorro en el modelo completo depende de las matrices que reciban adapters.

DoRA: LoRA con descomposición de pesos

DoRA (Weight-Decomposed Low-Rank Adaptation) separa la magnitud de cada vector de pesos de su dirección. El paper de DoRA aplica una actualización LoRA al componente direccional y aprende la magnitud por separado.

Cómo funciona:

En lugar de tratar los pesos como una única entidad, DoRA descompone los pesos preentrenados en dos componentes:

  1. Magnitud — un valor entrenable por vector de pesos.
  2. Dirección — un vector normalizado actualizado mediante matrices de bajo rank.

En notación compacta por columnas:

W′=mV+BA∥V+BA∥cW' = m \frac{V + BA}{\lVert V + BA \rVert_c}W′=m∥V+BA∥c​V+BA​

donde:

  • m = magnitud (entrenable)
  • V=W0V = W_0V=W0​ = la matriz inicial congelada; normaliza después de añadir BABABA
  • BABABA = la actualización direccional de bajo rank aprendida
  • ∥⋅∥c\lVert \cdot \rVert_c∥⋅∥c​ = normalización por columnas

Qué aporta esta estructura adicional:

  • Más grados de libertad que LoRA estándar, porque la magnitud puede cambiar de forma independiente.
  • Mejores resultados que LoRA en varias configuraciones descritas por el paper que lo propone.
  • Más parámetros y computación, por lo que la mejora debe verificarse en tu tarea y en tu ruta de serving.

Fusión de adapters para aprendizaje multitarea

Los adapters separados permiten que una única base congelada admita varias tareas. Puedes enrutar las peticiones a un adapter, servir varios adapters desde un motor cuando sea compatible o crear un candidato fusionado offline. La fusión puede introducir interferencias, así que evalúa el artefacto fusionado en lugar de asumir que los adapters de origen se componen correctamente.

Métodos habituales de fusión:

  1. Concatenación — combina los parámetros de los adapters y aumenta el rank efectivo. Rápida y sencilla.
  2. Combinación lineal — suma ponderada de adapters. Proporciona parámetros de control.
  3. SVD — descomposición de matrices para fusionar. Más flexible, pero más lenta.

Ejemplo: un adapter para summarization y otro para traducción, fusionados en un único modelo multitarea.

Etapa 4: Fine-tuning y preference alignment

SFT aprende demostraciones. Preference optimization aprende, en cambio, de comparaciones como «la respuesta elegida A es mejor que la respuesta rechazada B». Úsalo solo cuando una preferencia por pares sea la etiqueta adecuada para el error; la corrección factual y el cumplimiento de políticas suelen necesitar evaluadores más sólidos que una preferencia global.

RLHF basado en PPO

RLHF significa reinforcement learning from human feedback. La policy es el modelo de lenguaje que genera respuestas; un reward model puntúa esas respuestas utilizando preferencias aprendidas de comparaciones humanas. Una receta basada en PPO tiene tres etapas:

  1. SFT — aprende la tarea.
  2. Reward model — se entrena con preferencias humanas (elegida frente a rechazada).
  3. PPO (Proximal Policy Optimization) — genera respuestas y actualiza el modelo de lenguaje para aumentar sus puntuaciones de reward.

El coste operativo procede de sus distintos componentes:

  • Es complicado de implementar y mantener.
  • Es caro: entrenas varios modelos.
  • El sampling del modelo que se está entrenando requiere comprobaciones para detectar actualizaciones inestables y respuestas que exploten el reward model sin satisfacer la tarea.

DPO

DPO (Direct Preference Optimization) elimina el reward model independiente y el loop de reinforcement learning. Favorece las respuestas elegidas y desincentiva cambios grandes respecto a un modelo inicial fijo, denominado reference model. El paper de DPO deriva este objetivo limitando cuánto pueden alejarse las probabilidades de respuesta de las de esa referencia; el límite matemático es una restricción de divergencia KL.

Un par de preferencias contiene el mismo prompt y dos respuestas candidatas. Esta fila abreviada muestra sus campos; las etiquetas reales necesitan respuestas completas y un motivo para preferir una:

{
    "prompt": "Explain quantum computing",
    "chosen": "Quantum computing uses qubits...",   # Preferred response
    "rejected": "Well, it's complicated..."        # Non-preferred response
}

Qué cambia desde el punto de vista operativo:

  • Ruta de código más sencilla (sin reward model separado ni RL loop).
  • Entrenamiento con pares de preferencias guardados en lugar de generar nuevas respuestas para puntuarlas con un reward durante cada actualización.
  • Un reference model fijo o sus log probabilities guardadas para las respuestas de training, en la formulación estándar.

DPO es más fácil de prototipar que un pipeline PPO completo, pero no mejora automáticamente la calidad. Los resultados dependen de la policy inicial, la calidad de los pares, los ajustes del loss, los efectos de la longitud y el protocolo de evaluación. Compáralo con un checkpoint SFT usando las mismas suites de preferencias reservadas y de tareas.

ORPO

ORPO (Odds-Ratio Preference Optimization) combina el loss de negative log-likelihood de SFT con una penalización de odds ratio sobre las respuestas rechazadas. Elimina el reference model separado y puede combinar el aprendizaje de la tarea y la preference optimization en una sola ejecución.

Cómo funciona: ORPO utiliza un loss combinado que hace dos cosas a la vez:

  1. Maximiza la likelihood de la respuesta elegida (aprende la tarea).
  2. Penaliza la respuesta rechazada mediante un término de odds ratio (aprende las preferencias).

Hiperparámetros que conviene conocer (API de TRL 1.12.0):

# API shown in TRL 1.12.0 documentation
from trl.experimental.orpo import ORPOConfig

config = ORPOConfig(
    learning_rate=8e-6,  # Very low, as recommended by the ORPO paper
    beta=0.1,            # Controls strength of preference penalty
    # ... other params
)
  • Learning rate: el paper utilizó valores bajos en sus experimentos; ajústalo para tu modelo, batch y datos en lugar de copiar un valor como regla.
  • Beta: controla el término de preferencias respecto al término de SFT.

La contrapartida:

  • Una etapa de entrenamiento en lugar de dos.
  • No hay reward model.
  • No hay forward pass del reference model.
  • Una ejecución acoplada: si el aprendizaje de la tarea o el comportamiento de preferencias empeoran, no hay un checkpoint SFT intermedio de la misma pipeline que inspeccionar.

Elige según el diseño de los datos y de la evaluación:

  • Usa DPO cuando ya tengas un checkpoint SFT satisfactorio y quieras un experimento de preferencias offline más sencillo.
  • Prueba ORPO cuando un objetivo sin referencia y de una sola etapa encaje con tus datos y restricciones operativas.
  • Usa RLHF basado en PPO cuando el sampling online frente a un reward aprendido explícito forme parte del requisito y puedas monitorizar la explotación del reward.

Ninguno es la opción predeterminada para todas las tareas. Conserva un baseline solo con SFT e informa tanto de métricas de la tarea como de métricas de preferencias.

Frameworks de fine-tuning

Los frameworks se solapan y cambian rápidamente. Elige según la ruta de ejecución que debas admitir, fija las versiones y mantén la configuración de entrenamiento suficientemente portable para reproducirla fuera de un notebook.

Unsloth: velocidad y eficiencia de memoria

Unsloth se integra con trl y transformers de Hugging Face y proporciona kernels optimizados, checkpointing y rutas de fine-tuning cuantizado para los modelos compatibles.

  • Kernels personalizados de Triton para attention, RoPE y cross-entropy que evitan el overhead de PyTorch.
  • Backpropagation eficiente en memoria que recalcula las activations durante el backward pass en lugar de mantenerlas en memoria.
  • Operaciones fusionadas que agrupan varios pasos (layer norm + linear y similares) en una única llamada a la GPU.
  • Quantization de 4 bits integrada directamente en la ruta QLoRA con dequantization optimizada.

[!IMPORTANT] El orden de importación importa Sigue el orden de importación del ejemplo de Unsloth para la versión que hayas fijado. Unsloth aplica parches durante la importación, por lo que importarlo antes que trl y transformers evita perder optimizaciones o encontrar errores específicos de una versión.

# Correct order
from unsloth import FastLanguageModel  # Must be first!
from trl import SFTTrainer
from transformers import TrainingArguments

# Avoid this order with Unsloth's patched path
from trl import SFTTrainer
from unsloth import FastLanguageModel

Más adecuado para: entrenamiento en una sola GPU, prototipado, notebooks de Colab y cualquiera que vigile la factura de GPU.

Las cifras publicadas de velocidad y memoria varían según el modelo, la longitud de secuencia, el batch, la precisión y el hardware. Haz benchmark de tokens por segundo y memoria máxima en tu propia ejecución en lugar de tratar una proporción destacada como una propiedad del framework.

Genéralos a partir de una división versionada por origen/grupo, tal como se describe en la Etapa 1. from unsloth import FastLanguageModel
from trl import SFTConfig, SFTTrainer

# Load model with 4-bit quantization
model, tokenizer = FastLanguageModel.from_pretrained(
    model_name="nvidia/Llama-3.1-Nemotron-Nano-4B-v1.1",
    max_seq_length=4096,
    load_in_4bit=True,
)

# Add LoRA adapters
model = FastLanguageModel.get_peft_model(
    model,
    r=16,
    lora_alpha=32,
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj",
                    "gate_proj", "up_proj", "down_proj"],
    use_gradient_checkpointing="unsloth",  # Lower activation memory; extra compute
)

# Prerequisite: supply the prepared datasets described above.

# Train with the current TRL configuration surface.
trainer = SFTTrainer(
    model=model,
    processing_class=tokenizer,
    train_dataset=train_dataset,
    eval_dataset=eval_dataset,
    args=SFTConfig(
        output_dir="outputs/proposed-nemotron-run",
        max_length=4096,
        packing=False,
        assistant_only_loss=False,  # Full-sequence targets; inspect before changing
        eval_strategy="epoch",
        per_device_train_batch_size=2,
        gradient_accumulation_steps=4,
        learning_rate=2e-4,
        num_train_epochs=3,
        bf16=True,  # Requires BF16-capable hardware
    ),
)
trainer.train()
trainer.save_model("outputs/proposed-nemotron-adapter")
tokenizer.save_pretrained("outputs/proposed-nemotron-adapter")

Etapa 5: Evaluación

Byte dice

Si el mismo ticket de soporte aparece en training y en evaluación, una puntuación más alta puede premiar que se recuerde ese ticket. Divide por ticket antes de crear las filas o reescrituras.

Fija los casos de prueba, las reglas de puntuación y los umbrales de aprobación antes de la primera ejecución. Como mínimo, compara el checkpoint ajustado con el modelo base exacto sin ajustar usando el mismo prompt, los mismos ajustes de decoding y el mismo entorno de herramientas. Informa de la calidad agregada solo después de comprobar los failure slices que el proyecto pretendía mejorar.

Sigue cuatro grupos:

  1. Tarea objetivo: exact match, éxito de ejecución, rúbrica humana u otro resultado vinculado al caso de uso.
  2. Regresión: capacidades generales y slices de tareas previamente compatibles que la adaptación podría perjudicar.
  3. Seguridad y políticas: denegaciones, fugas de datos, prompt injection o restricciones específicas del dominio.
  4. Operaciones: latencia, throughput, memoria, tamaño del artefacto y coste con la configuración de serving prevista.

Benchmarks automatizados

Usa lm-evaluation-harness para comprobar tareas estandarizadas relevantes junto con tus pruebas de producto. Este comando requiere un checkpoint fusionado de Hugging Face. La ruta del ejemplo corresponde a la salida fusionada del companion legacy de la Etapa 6; no carga el adapter guardado por la configuración propuesta anterior. Sustitúyela por el checkpoint fusionado que quieras evaluar:

lm_eval --model hf \
    --model_args pretrained=./outputs/unsloth-nemotron-function-calling-merged \
    --tasks hellaswag,arc_easy,mmlu \
    --batch_size 8

LLM-as-judge

Para la calidad subjetiva, un modelo más grande puede ayudar con la puntuación, pero calibra sus resultados con ejemplos revisados por personas y mantén oculta la identidad del candidato:

judge_prompt = """
Rate this response from 1-5 on:
- Relevance
- Accuracy
- Formatting

Response: {model_output}
Expected: {ground_truth}
"""

Evaluación específica del dominio

Reserva ejemplos reales por origen, usuario, documento o tiempo para impedir que duplicados aproximados se filtren entre las particiones. En function calling, valida la trayectoria completa: selección de herramienta, argumentos, resultado de ejecución, recuperación y respuesta final. Informa de intervalos de confianza o recuentos emparejados de victorias/derrotas cuando la muestra sea pequeña e inspecciona cada regresión en un slice crítico.

Etapa 6: Despliegue y formatos de salida

Elige el artefacto según el motor de serving y el plan de rollback, no solo por el tamaño de archivo. Estos ejemplos de CLI hacen referencia al companion legacy, no al fragmento TRL propuesto. Su directorio de adapters predeterminado es outputs/unsloth-nemotron-function-calling, con los directorios -merged y -gguf para las exportaciones. Cada invocación de la CLI vuelve a entrenar; no es un comando exclusivamente de exportación. En una release real, exporta el checkpoint evaluado seleccionado en lugar de comparar artefactos procedentes de ejecuciones de reentrenamiento distintas.

1. Adapter LoRA

uv run finetune  # Default adapter directory shown below
  • Tamaño: proporcional a los módulos objetivo, el rank, las capas y el dtype; a menudo mucho menor que la base.
  • Más adecuado para: desarrollo, adapters de tarea versionados y motores compatibles directamente con LoRA.
  • Ventaja adicional: puedes intercambiar adapters sin volver a descargar el modelo base.

2. Modelo fusionado

uv run finetune --merge  # Creates a standalone full model
  • Tamaño: aproximadamente el del checkpoint base completo con la precisión de salida elegida.
  • Más adecuado para: motores o rutas de distribución que no admiten el adapter por separado.
  • Contrapartida: artefacto más grande y rollout más lento; carga de un único modelo más sencilla.

3. Formato GGUF

uv run finetune --gguf q4_k_m  # File size and name depend on the exporter
  • Tamaño: depende del modelo; aproximadamente pesos de cuatro bits más metadatos para las variantes Q4.
  • Más adecuado para: inferencia en CPU, Ollama, llama.cpp y despliegues edge.
  • Opciones: q4_k_m (más pequeño), q5_k_m (mayor fidelidad de los pesos), q8_0 (más grande y con mayor fidelidad). Mide el impacto en la tarea después de la conversión.

Etapa 7: Serving y monitorización

Con vLLM

Este ejemplo de serving supone que el adapter propuesto ha superado la evaluación de la tarea y se ha entrenado con una template de herramientas compatible con Llama 3.1. Guarda esa template exacta revisada como serving-chat-template.jinja; el companion no la crea. No se ha establecido que el adapter con formato ChatML legacy sea compatible con este par de parser/template. Verifica una trayectoria completa de herramientas antes de exponer el endpoint.

# Serve the base and expose a PEFT adapter as a model name. This parser and
# template pair is for a Llama 3.1-compatible function-calling adapter.
vllm serve nvidia/Llama-3.1-Nemotron-Nano-4B-v1.1 \
    --enable-lora \
    --lora-modules function-calling=./outputs/proposed-nemotron-adapter \
    --enable-auto-tool-choice \
    --tool-call-parser llama3_json \
    --chat-template ./serving-chat-template.jinja \
    --host 0.0.0.0 \
    --port 8000 \
    --max-model-len 4096

Este schema de vuelo deliberadamente mínimo prueba la generación de argumentos a través de la API compatible con OpenAI. Solicita una llamada book_flight propuesta con un destino; no ejecuta ninguna reserva. Inspecciona response.choices[0].message.tool_calls para comprobar el nombre de la función y los argumentos JSON. Para esta entrada, el resultado previsto es book_flight con {"destination": "Tokyo"}. Como la elección de herramienta es automática, comprueba también si el modelo ha devuelto una llamada:

from openai import OpenAI

client = OpenAI(base_url="http://localhost:8000/v1", api_key="dummy")
response = client.chat.completions.create(
    model="function-calling",
    messages=[{"role": "user", "content": "Book a flight to Tokyo"}],
    tools=[
        {
            "type": "function",
            "function": {
                "name": "book_flight",
                "description": "Book a flight to a city.",
                "strict": True,
                "parameters": {
                    "type": "object",
                    "properties": {
                        "destination": {"type": "string"},
                    },
                    "required": ["destination"],
                    "additionalProperties": False,
                },
            },
        }
    ],
    tool_choice="auto",
)

La guía de tool calling de vLLM requiere auto tool choice y un parser adaptado al modelo. Proporciona una chat template compatible si la configuración del tokenizer no incluye ninguna. Con tool_choice="auto", los argumentos restringidos también requieren strict: true en al menos una función y un schema parameters compatible con strict. Debe estar activado el ajuste de strict tool calling del servidor (el valor predeterminado documentado). Sin ese opt-in, vLLM extrae las llamadas del texto sin procesar, por lo que los argumentos pueden estar mal formados o incumplir el schema.

Con Ollama (local)

Inspecciona el directorio real de exportación -gguf y sustituye el nombre de archivo generado por MODEL_FILE.gguf en el ejemplo siguiente; las versiones de Unsloth pueden asignar nombres distintos a los archivos. Un archivo GGUF por sí solo no garantiza un formato correcto de chat/herramientas en Ollama o llama.cpp. Haz coincidir la template utilizada en el entrenamiento y prueba el artefacto importado.

# Create Modelfile
echo 'FROM ./outputs/unsloth-nemotron-function-calling-gguf/MODEL_FILE.gguf' > Modelfile

# Import to Ollama
ollama create my-function-model -f Modelfile

# Run
ollama run my-function-model

Con llama.cpp (CPU)

Usando la misma exportación GGUF y sustituyendo el nombre de archivo, este comando comprueba una respuesta de texto plano. No prueba un tool call completo:

./llama-cli -m ./outputs/unsloth-nemotron-function-calling-gguf/MODEL_FILE.gguf \
    -p "What's the weather in Tokyo?" \
    --ctx-size 4096

Monitoriza el modelo publicado

El ciclo de vida no termina cuando el training loss es correcto. Registra la revisión del modelo base, el tokenizer y la chat template, el hash del adapter, la versión del dataset, la configuración de entrenamiento y el informe de evaluación como una única unidad de release. En producción, monitoriza el éxito de la tarea, las salidas no válidas, los fallos de política, la latencia y el drift de entrada usando los mismos slices que offline. Mantén cargable el artefacto anterior y define un umbral de rollback antes del lanzamiento.

Tu próxima prueba
