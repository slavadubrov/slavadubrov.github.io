Guía de ajuste fino de LLM: LoRA, QLoRA, DoRA, Unsloth, Axolotl y despliegue

La mayoría de los fallos en el ajuste fino se deben a decisiones erróneas. Un equipo entrena antes de demostrar que la utilización de prompts, la recuperación de información o el decodificación restringida no pueden resolver el problema; evalúa sobre la distribución de datos utilizada para entrenar; o descubre tras el entrenamiento que el modelo resultante es difícil de utilizar en producción.

Esta guía trata la adaptación como un experimento con un punto de salida operativo definido. Comienza por delimitar el umbral de decisión y luego sigue un camino que incluye el análisis de datos, el uso de técnicas como LoRA o QLoRA, la evaluación específica para la tarea, la exportación del modelo y su puesta en servicio.

TL;DR: Realice ajustes finos cuando una línea de base medible indique que modificar el comportamiento del modelo justifica una actualización de pesos. Utilice la recuperación de información para cambiar hechos y el decodificación restringida para gestionar aspectos sintácticos. Empiece con LoRA cuando el modelo base cabe cómodamente en los recursos disponibles; opte por QLoRA cuando el límite sea la memoria limitada para almacenar pesos congelados. Reserve un conjunto de evaluación antes de entrenar, compárelo con la línea de base sin ajustes y elija el formato final antes de decidirse por un método concreto.

¿Debería realizar ajustes finos en absoluto?

Antes de invertir horas en GPUs, decida si el ajuste fino es la herramienta adecuada para el problema que tiene entre manos.

Ajuste fino vs RAG

El ajuste fino puede modificar la forma en que un modelo utiliza el lenguaje propio de un dominio, pero es un mecanismo deficiente para actualizar hechos que cambian o que deben citarse. La recuperación de información y el ajuste fino abordan partes diferentes del problema y, con frecuencia, deben integrarse en el mismo sistema.

Los LLM modernos responden bien a prompts y ejemplos claros. Pruebe estas opciones antes de invertir tiempo en ajustes finos.

[!TIP] Pruebe primero con prompts Empiece con un prompt y ejemplos representativos. Si solo es la sintaxis de salida la que resulta poco fiable, añada decodificación restringida antes de modificar los pesos.

Afinamiento vs. decodificación restringida

Bibliotecas como xgrammar y outlines limitan la generación a un esquema JSON, una expresión regular o una gramática. Según la restricción y el backend utilizado, compilan un autómata o una gramática y ocultan los tokens siguientes inválidos. No es necesario actualizar pesos.

Esto garantiza que la salida pertenezca al lenguaje soportado, pero no que los valores sean verdaderos, completos ni semanticamente adecuados. Una llamada a función sintácticamente válida puede seguir conteniendo un ID de cliente incorrecto.

Secuencia práctica:

  1. Comience con prompts y ejemplos de pocos casos para lograr un formato básico.
  2. Añada decodificación restringida (xgrammar o outlines) cuando la sintaxis sea inconsistente.
  3. Realice afinamiento únicamente cuando necesite cambios de comportamiento que un esquema no pueda imponer.

Hacer medible el caso empresarial

El ajuste fino puede reducir la cantidad de tokens de prompt recurrentes o permitir que un modelo más pequeño cumpla con los objetivos, pero ninguna de estas economías es automática. Calcule el punto de equilibrio con su propio tráfico y precios:

[ \text{peticiones de equilibrio} = \frac{\text{coste de entrenamiento + evaluación + despliegue}} {\text{coste base/petición} - \text{coste ajustado/petición}} ]

Si el denominador es pequeño, negativo o se basa en una suposición de calidad no comprobada, el proyecto aún no tiene viabilidad económica.

[!TIP] La configuración híbrida Una arquitectura común consiste en un modelo más pequeño adaptado a la tarea, complementado por sistemas de recuperación de información para actualizar datos. Considere al modelo más grande con prompts como referencia y mantenga solo al modelo más pequeño si cumple con los mismos umbrales de calidad y seguridad específicos de la tarea.

Tipos de ajuste fino

Existen tres formas principales en las que puede realizarse el ajuste fino. Diferen en los tipos de datos que necesitan y en lo que enseñan al modelo.

1. Entrenamiento previo continuo (no supervisado)

Entrena el modelo base con más texto sin etiquetas. Continúa realizando predicciones del siguiente token, tal como ocurre durante el entrenamiento previo original.

Cuándo usarlo:

  • El dominio cuenta con vocabulario que el modelo base nunca ha visto (médico, legal, bases de código internas).
  • Dispone de grandes cantidades de texto del dominio, pero sin pares de entrada/salida etiquetados.
  • El modelo base tiene dificultades con terminología específica del dominio.

Ejemplo: entrenar con millones de notas clínicas para que el modelo reconozca abreviaturas médicas, nombres de fármacos y flujos de trabajo clínicos.

2. Ajuste fino supervisado (SFT)

El SFT se entrena con pares de entrada/salida etiquetados. Le muestra al modelo la salida exacta que desea obtener para cada entrada.

Cuándo usarlo:

  • Tiene una tarea específica con un formato claro de entrada/salida.
  • Dispone de datos etiquetados de calidad, aunque en pequeñas cantidades.
  • Necesita un comportamiento predecible con entradas de estructura conocida.

Ejemplo: entrenar con pares de (descripción de consulta SQL, código SQL) para tareas de texto a SQL.

{
    "input": "Get all users who signed up last month",
    "output": "SELECT * FROM users WHERE signup_date >= DATE_SUB(NOW(), INTERVAL 1 MONTH)"
}

3. Ajuste por instrucciones

El ajuste por instrucciones es un caso especial del SFT cuyo objetivo es hacer que los modelos sigan una gran variedad de instrucciones en lenguaje natural. Los datos de entrenamiento consisten en pares (instrucción, respuesta) provenientes de múltiples tareas distintas.

Cuándo utilizarlo:

  • Si se desea un asistente de uso general (como ChatGPT o Claude).
  • Cuando el modelo debe gestionar solicitudes variadas y abiertas.
  • Al desarrollar una interfaz de chat.

Ejemplo: entrenamiento con miles de instrucciones diversas como “Resuma este artículo”, “Escriba un poema sobre X” o “Explique Y de forma sencilla”.

[!NOTA] Qué hacen realmente los equipos El SFT y el ajuste por instrucciones emplean el mismo objetivo de predicción del siguiente token; la diferencia radica en la amplitud y estructura del conjunto de datos. El entrenamiento previo continuo es un experimento independiente que debe ir seguido de pruebas tanto para evaluar ganancias en el dominio específico como para detectar posibles regresiones en las capacidades generales.

El pipeline de afinación en 7 etapas

La afinación es un proceso en fases, no una única acción. Cada etapa presenta sus propios puntos de fallo, y omitir alguna suele traducirse posteriormente en un modelo de calidad deficiente.

Cada etapa se basa en la anterior:

  1. Preparación de datos — Definir la unidad de evaluación, dividir los datos y luego limpiarlos y formatearlos.
  2. Selección del modelo — Elegir el modelo base adecuado e cargar sus pesos.
  3. Configuración del entrenamiento — Definir el hardware, los hiperparámetros y la estrategia de optimización.
  4. Afinación — Ejecutar entrenamientos con SFT, DPO u ORPO.
  5. Evaluación — Medir el rendimiento y validar la calidad.
  6. Despliegue — Exportar y poner en servicio el modelo.
  7. Monitoreo — Seguir el rendimiento, mantener el sistema y realizar iteraciones.

[!ADVERTENCIA] Los datos son la base El entrenamiento reproduce defectos sistemáticos presentes en los ejemplos utilizados. Antes de dedicar tiempo a ajustes en los optimizadores, es necesario revisar las etiquetas, detectar fugas de información, verificar la cobertura y asegurar el cumplimiento de las políticas establecidas.

Etapa 1: Preparación de datos

La mayoría de los proyectos de afinación fracasan aquí, y no durante el entrenamiento en sí. La preparación moderna de datos va más allá de simplemente aplicar expresiones regulares a archivos CSV.

El pipeline de datos en 5 etapas

Herramientas como DataTrove y Distilabel pueden ser útiles a gran escala, pero el diseño del pipeline debe guiarse por la taxonomía de fallos y los requisitos definidos para los datos, y no por la preferencia por una herramienta en particular.

1. Ingestión y filtrado

  • Acción: descartar respuestas de rechazo (“No puedo responder a eso”), datos con codificación UTF-8 corrupta y textos en idiomas no deseados.
  • Herramientas: Trafilatura para la extracción de información y FastText para identificar el idioma.

2. Política de datos sensibles

  • Acción: determinar qué información puede aprender el modelo y, en su caso, eliminar, tokenizar o excluir los campos personales y confidenciales.
  • Herramientas: Microsoft Presidio o scrubadub.
  • Razón: un detector solo constituye un mecanismo de control; siguen siendo aplicables los requisitos relacionados con el origen de los datos, el consentimiento, el período de conservación, el acceso y la eliminación.

3. Duplicación (MinHash LSH)

  • Acción: descartar los datos casi idénticos para evitar que el modelo los memorice.
  • Herramientas: DataTrove es adecuado para procesar volúmenes de datos de varios terabytes.

4. Aumentación sintética, si es necesario

  • Acción: utilizar un modelo maestro más potente (GPT-4o, DeepSeek-V3) para reescribir los datos brutos como pares de instrucción-respuesta estructurados.
  • Herramientas: Distilabel.
  • Validación: seleccionar muestras de las salidas del modelo maestro, compararlas según los mismos criterios que las etiquetas generadas por humanos, y mantener separados en la evaluación los datos sintéticos de los escritos por personas.

5. Formato

  • Acción: convertir los datos al formato estándar (Alpaca o ShareGPT).

Ejemplos de formato de datos

Formato Alpaca (basado en instrucciones):

{
    "instruction": "Summarize the following text.",
    "input": "The text to be summarized...",
    "output": "This is the summary."
}

Formato ShareGPT/ChatML (de tipo conversacional):

{
    "conversations": [
        { "from": "user", "value": "Hello, who are you?" },
        { "from": "assistant", "value": "I am a helpful AI assistant." }
    ]
}

Factores realmente relevantes

  • La cobertura antes que el volumen. Incluir ejemplos que representen modos de fallo distintos, y no simplemente repeticiones de los casos más comunes y fáciles de manejar.
  • Limpieza. Eliminar texto irrelevante, normalizar los espacios en blanco y mantener una consistencia en el formato.
  • Equilibrio. Conservar los casos raros pero importantes y reportar el rendimiento por cada grupo de datos.
  • Separación. Dividir los datos por fuente, usuario, documento o momento, cuando la división aleatoria de filas pudiera generar duplicados cercanos.
  • Origen. Registrar la fuente, la licencia o permisos, el historial de transformaciones y el proceso de eliminación para cada versión del conjunto de datos.

Etapa 2: Selección del modelo y hardware

Elegir el modelo base y conocer las limitaciones del hardware determinan qué se puede entrenar realmente.

Comience con el modelo base más pequeño que ya cumpla con las verificaciones básicas indispensables. Verifique:

  • los términos de licencia y redistribución para el producto previsto;
  • el idioma, el dominio, el uso de herramientas y el comportamiento de seguridad antes de realizar adaptaciones;
  • la compatibilidad del tokenizador y las plantillas de chat con el conjunto de datos;
  • el contexto máximo y el comportamiento de truncación necesarios para los ejemplos reales;
  • la compatibilidad tanto con el marco de entrenamiento como con el motor de servicio objetivo.

El ajuste fino es un paso de adaptación, no una solución para un modelo base inadecuado. Si el modelo no cubre capacidades que el conjunto de datos no abarca, seleccione otro modelo base antes de seguir entrenando más épocas.

Definir el tamaño del entrenamiento, no el nivel de marketing

No existe una tabla fija que relacione el “tamaño del modelo” con el hardware necesario. La memoria máxima varía en función de la precisión de los pesos, el optimizador, la cantidad de parámetros entrenables, la longitud de las secuencias, el tamaño de los lotes micro, el uso de puntos de control de activación, la implementación de atención y la sobrecarga del marco de trabajo. Empiece con una estimación de la memoria requerida y, a continuación, realice una prueba breve de longitud máxima con el conjunto completo de componentes.

El artículo original de QLoRA adaptó un modelo LLaMA de 65 mil millones de parámetros a una GPU de 48 GB en su configuración específica. Ese resultado constituye un límite útil, pero no garantiza que cualquier arquitectura actual de 70 mil millones de parámetros, longitud de contexto, kernel o herramienta de entrenamiento pueda adaptarse al mismo dispositivo.

Cálculo de la memoria

Para un modelo con (P) parámetros, solo los pesos requieren aproximadamente (2P) bytes en formato BF16/FP16 o (0.5P) bytes en formato de cuatro bits, sin contar aún los metadatos de cuantización ni los buffers en tiempo de ejecución. El entrenamiento completo al estilo Adam añade los gradientes, los estados del optimizador y, a menudo, pesos maestros con mayor precisión. LoRA reduce significativamente la memoria necesaria para almacenar los estados entrenables; QLoRA además disminuye el espacio ocupado por los pesos base congelados. Las activaciones pueden seguir siendo la parte más consumidora de memoria en secuencias largas.

Sigue este flujo de trabajo:

  1. Elige la longitud máxima de secuencia y el tamaño mínimo de lote que debas soportar.
  2. Estima la memoria necesaria para los pesos y los estados entrenables, dejando margen adicional para las activaciones y los kernels.
  3. Ejecuta un paso hacia adelante/hacia atrás con la longitud máxima permitida.
  4. Registra el consumo máximo de memoria asignada y reservada.
  5. Solo entonces ajusta el tamaño del lote, el número de hilos, la longitud de la secuencia o la cantidad de GPUs.

Etapa 3: Métodos de entrenamiento (PEFT y LoRA)

Ajuste fino completo vs PEFT

El ajuste fino completo (FFT) actualiza todos los pesos, por lo que los gradientes y los estados del optimizador crecen proporcionalmente al tamaño total del modelo. No es posible estimar el consumo máximo solo a partir del número de parámetros, pero este suele ser mucho mayor que la memoria necesaria para cargar los pesos con fines de inferencia.

El ajuste fino eficiente en parámetros (PEFT) entrena solo un subconjunto reducido de parámetros y congela el resto. De este modo, los cálculos relacionados con el uso de memoria se vuelven mucho más sencillos.

LoRA: punto de partida

LoRA (Adaptación de rango bajo) congela una matriz preentrenada y representa su actualización aprendida mediante dos matrices más pequeñas. El artículo original justifica este enfoque partiendo de la hipótesis de que las actualizaciones útiles presentan un rango intrínseco bajo.

Para una matriz congelada (W0 \in \mathbb{R}^{d{out} \times d_{in}}), LoRA aprende:

  • (A \in \mathbb{R}^{r \times d_{in}})
  • (B \in \mathbb{R}^{d_{out} \times r})

La capa adaptada queda definida como:

[ W’ = W_0 + \frac{\alpha}{r}BA ]

El adaptador cuenta con (r(d*{in}+d*{out})) parámetros entrenables, en lugar de (d*{in}d*{out}) para dicha matriz. En el caso de una matriz cuadrada de 4,096 elementos con rango 16, esto supone una reducción de 128 veces en el tamaño de la matriz; no de 10,000 veces como se indicó erróneamente en el artículo original, que se refería a una configuración específica de GPT-3 de 175 mil millones de parámetros donde se adaptaron matrices seleccionadas.

Comparación de métodos PEFT

MétodoQué cambiaCuándo elegirlo

Cuándo elegir cada método

  • LoRA: empieza aquí. Es rápido, eficiente en memoria y cuenta con amplio soporte.
  • QLoRA: cuando el mismo experimento con LoRA no es viable debido a los pesos del modelo base congelados.
  • DoRA: tras una comparación directa con LoRA que demuestre una mejora significativa.
  • Ajuste fino completo: solo después de comprobar que PEFT representa un cuello de botella real y no una suposición.

DoRA: LoRA con magnitud descompuesta

DoRA (Adaptación de Rango Bajo con Magnitud Descompuesta) separa la magnitud de cada vector de peso de su dirección. Aplica una actualización de LoRA a la componente direccional mientras aprende la magnitud de forma independiente.

Funcionamiento:

En lugar de tratar los pesos como una entidad única, DoRA divide los pesos preentrenados en dos componentes:

  1. Magnitud: un valor entrenable para cada vector de peso.
  2. Dirección: un vector normalizado actualizado mediante matrices de rango bajo.

En notación compacta por columnas:

[ W’ = m \frac{V + BA}{\lVert V + BA \rVert_c} ]

donde:

  • m = magnitud (entrenable)
  • (V) = la matriz direccional congelada
  • (BA) = la actualización direccional de rango bajo aprendida
  • (\lVert \cdot \rVert_c) = normalización por columnas

Ventajas de esta estructura adicional:

  • Más grados de libertad que LoRA estándar, ya que la magnitud puede variar de forma independiente.
  • Mejores resultados que LoRA en varias configuraciones según el artículo original.
  • Mayor número de parámetros y consumo computacional; por ello, las mejoras deben validarse en la tarea concreta y en el flujo de servicio.

Fusión de adaptadores para aprendizaje multi-tarea

Los adaptadores independientes permiten que un modelo base congelado soporte varias tareas. Se pueden redirigir las solicitudes a un adaptador específico, servir varios adaptadores desde un mismo motor cuando sea posible, o crear una versión fusionada fuera de línea. La fusión puede generar interferencias, por lo que es necesario evaluar el resultado fusionado en lugar de asumir que los adaptadores originales funcionan sin problemas.

Métodos comunes de fusión:

  1. Concatenación: combina los parámetros de los adaptadores y aumenta el rango efectivo. Es rápido y sencillo.
  2. Combinación lineal: suma ponderada de los adaptadores. Permite ajustar los pesos según necesidades.
  3. SVD: descomposición matricial para la fusión. Es más flexible, pero más lento.

Ejemplo: un adaptador para resúmenes y otro para traducción, fusionados en un único modelo multi-tarea.

Etapa 4: Afinación y alineación de preferencias

El SFT aprende a partir de demostraciones. En cambio, la optimización de preferencias se basa en comparaciones como “la respuesta elegida A es mejor que la respuesta rechazada B”. Úsala únicamente cuando la etiqueta adecuada para el error sea una preferencia entre pares; la corrección factual y el cumplimiento de políticas suelen requerir evaluadores más robustos que una preferencia global.

RLHF basado en PPO

La solución original consistía en un pipeline de tres etapas:

  1. SFT: aprendizaje de la tarea.
  2. Modelo de recompensas: entrenamiento con preferencias humanas (elegidas frente a rechazadas).
  3. PPO (Proximal Policy Optimization): aprendizaje por refuerzo para optimizar la política.

Los costes operativos provienen de los componentes dinámicos:

  • Es complicado de implementar y mantener.
  • Costoso: se deben entrenar múltiples modelos.
  • El muestreo on-policy y la optimización de recompensas exigen controles estrictos de estabilidad y detección de manipulación de recompensas.

DPO

El DPO (Direct Preference Optimization) elimina el modelo de recompensas explícito y el bucle de aprendizaje por refuerzo. Sigue optimizando el objetivo del RLHF (maximización de recompensas con restricción de divergencia KL), pero lo hace como un problema de aprendizaje supervisado reparametrizado en lugar de mediante aprendizaje por refuerzo:

{
    "prompt": "Explain quantum computing",
    "chosen": "Quantum computing uses qubits...",   # Preferred response
    "rejected": "Well, it's complicated..."        # Non-preferred response
}

Cambios operativos:

  • Ruta de código más sencilla (sin modelo de recompensas separado ni bucle de RL).
  • Objetivo offline basado en pares de preferencias, en lugar de aprendizaje por refuerzo on-policy.
  • Existe una política de referencia o probabilidades de registro de referencia equivalentes en la formulación estándar.

El DPO es más fácil de prototipar que un pipeline completo de PPO, pero no supone automáticamente una mejora en la calidad. Los resultados dependen de la política inicial, la calidad de los pares, los parámetros de pérdida, los efectos de longitud y el protocolo de evaluación. Compáralo con un punto de control de SFT utilizando los mismos conjuntos de datos y tareas de preferencias reservados.

ORPO

El ORPO (Odds-Ratio Preference Optimization) combina la pérdida de verosimilitud negativa logarítmica del SFT con una penalización basada en la razón de probabilidades para las respuestas rechazadas. Elimina el modelo de referencia independiente y permite combinar el aprendizaje de tareas con la optimización de preferencias en una sola ejecución.

Funcionamiento: ORPO utiliza una pérdida combinada que realiza dos acciones simultáneamente:

  1. Maximiza la verosimilitud de la respuesta elegida (aprendizaje de la tarea).
  2. Penaliza la respuesta rechazada mediante un término basado en la razón de probabilidades (aprendizaje de preferencias).

Parámetros clave:

from trl import ORPOConfig

config = ORPOConfig(
    learning_rate=8e-6,  # Very low, as recommended by the ORPO paper
    beta=0.1,            # Controls strength of preference penalty
    # ... other params
)
  • Tasa de aprendizaje: en los experimentos del artículo se utilizaron tasas bajas; ajusta este valor según tu modelo, lotes y datos, en lugar de copiar directamente un valor como regla general.
  • Beta: controla la influencia del término de preferencias respecto al término del SFT.

Compromisos:

  • Una sola etapa de entrenamiento en lugar de dos.
  • No existe modelo de recompensas.
  • No se realiza paso forward con el modelo de referencia.
  • Ejecución acoplada: si el aprendizaje de tareas o el comportamiento de preferencias empeora, no hay un punto de control de SFT intermedio del mismo pipeline del que poder extraer información.

Elige según los datos y el diseño de evaluación:

  • Utiliza DPO cuando ya dispongas de un punto de control de SFT satisfactorio y desees un experimento de preferencias offline más sencillo.
  • Prueba ORPO cuando un objetivo de una sola etapa sin modelo de referencia se adapte a tus datos y limitaciones operativas.
  • Usa RLHF basado en PPO cuando el muestreo online contra una recompensa aprendida explícitamente forme parte de los requisitos y puedas monitorear la explotación de recompensas.

Ninguno de estos métodos es el predeterminado para todas las tareas. Mantén un punto de referencia basado únicamente en SFT e informa tanto sobre métricas de tarea como sobre métricas de preferencias.

Marcos de ajuste fino

Los marcos de trabajo son complementarios y evolucionan con rapidez. Elige según la ruta de ejecución que debas soportar, fija las versiones y asegúrate de que la configuración de entrenamiento sea lo suficientemente portátil como para reproducirse fuera de un cuaderno de notas.

Unsloth: velocidad y eficiencia de memoria

Unsloth se integra con Hugging Face trl y transformers, y ofrece núcleos optimizados, mecanismos de guardado de checkpoints y rutas de ajuste fino cuantizado para los modelos compatibles.

  • Núcleos GPU personalizados de Triton para operaciones de atención, RoPE y entropía cruzada que eliminan la sobrecarga de PyTorch.
  • Retropropagación eficiente en memoria que vuelve a calcular las activaciones durante el paso hacia atrás en lugar de almacenarlas en memoria.
  • Operaciones fusionadas que combinan varios pasos (normalización de capa + lineal, entre otros) en una sola llamada a la GPU.
  • Cuantización de 4 bits integrada directamente en la ruta QLoRA, con descuantización optimizada.

[!IMPORTANTE] El orden de importación es crucial Sigue el orden de importación del ejemplo de Unsloth correspondiente a la versión que hayas fijado. Unsloth aplica parches durante la importación; por lo tanto, importarlo antes de trl y transformers evita que falten optimizaciones o surjan errores específicos de la versión.

# ✅ Correct order
from unsloth import FastLanguageModel  # Must be first!
from trl import SFTTrainer
from transformers import TrainingArguments

# Avoid this order with Unsloth's patched path
from trl import SFTTrainer
from unsloth import FastLanguageModel

Ideal para: entrenamiento en una sola GPU, prototipado, cuadernos de notas de Colab y todo aquel que quiera controlar el consumo de GPU.

Las cifras publicadas sobre velocidad y memoria varían en función del modelo, longitud de secuencia, tamaño del lote, precisión y hardware. Mide tú mismo los tokens por segundo y el uso máximo de memoria en tus pruebas, en lugar de considerar una relación indicada como propiedad inherente al marco.

Etapa 5: Evaluación

Congelar el contrato de evaluación antes del primer ejecución. Como mínimo, comparar el checkpoint afinado con la versión base sin ajustes bajo las mismas instrucciones, parámetros de decodificación y entorno de herramienta. Informar únicamente sobre la calidad global tras verificar si se han reducido los fallos que el proyecto debía corregir.

Seguir cuatro categorías:

  1. Tarea objetivo: coincidencia exacta, éxito en ejecución, criterio humano o cualquier otro resultado relacionado con el caso de uso.
  2. Regresión: capacidades generales y subconjuntos de tareas anteriormente soportados que podrían verse afectados por la adaptación.
  3. Seguridad y políticas: rechazos, fugas de datos, inyección de instrucciones o restricciones específicas del dominio.
  4. Operaciones: latencia, ancho de banda, consumo de memoria, tamaño del artefacto y coste en la configuración de servicio prevista.

Pruebas automatizadas

Utilizar lm-evaluation-harness para tareas estandarizadas relevantes, pero no como sustituto de la evaluación del producto:

lm_eval --model hf \
    --model_args pretrained=./outputs/merged-model \
    --tasks hellaswag,arc_easy,mmlu \
    --batch_size 8

LLM como juez

Para evaluar la calidad subjetiva, un modelo más grande puede ayudar a puntuar, pero es necesario calibrarlo con ejemplos revisados por humanos y ocultar la identidad del candidato:

judge_prompt = """
Rate this response from 1-5 on:
- Relevance
- Accuracy
- Formatting

Response: {model_output}
Expected: {ground_truth}
"""

Evaluación específica del dominio

Reservar ejemplos reales por fuente, usuario, documento o fecha, de modo que los casi duplicados no se mezclen entre los grupos de prueba. En el caso de llamadas a funciones, validar toda la secuencia: selección de herramienta, argumentos, resultado de ejecución, recuperación y respuesta final. Cuando la muestra sea pequeña, informar sobre intervalos de confianza o conteos de éxitos/fracasos por pareja, e inspeccionar cada caso de regresión en los segmentos críticos.

Etapa 6: Despliegue y formatos de salida

Elegir el formato del artefacto en función del motor de servicio y del plan de reversión, no solo del tamaño del archivo:

1. Adaptador LoRA

uv run finetune  # Saves ~100-500MB adapter
  • Tamaño: proporcional a los módulos objetivo, rango, capas y tipo de dato; suele ser mucho menor que el modelo base.
  • Útil para: desarrollo, adaptadores de tareas versionados y motores que admitan LoRA directamente.
  • Ventaja adicional: se pueden intercambiar adaptadores sin volver a descargar el modelo base.

2. Modelo fusionado

uv run finetune --merge  # Creates a standalone full model
  • Tamaño: aproximadamente igual al tamaño total del checkpoint base en la precisión de salida elegida.
  • Adecuado para: motores o vías de distribución que no permiten usar el adaptador por separado.
  • Desventaja: mayor tamaño del artefacto y proceso de despliegue más lento; carga más sencilla de un único modelo.

3. Formato GGUF

uv run finetune --gguf q4_k_m  # Creates ~2-4GB quantized model
  • Tamaño: depende del modelo; aproximadamente pesos de cuatro bits más metadatos para las variantes Q4.
  • Útil para: inferencia en CPU, Ollama, llama.cpp, despliegue en entornos periféricos.
  • Opciones: q4_k_m (más pequeño), q5_k_m (mayor fidelidad en los pesos), q8_0 (más grande y con mayor fidelidad). Es necesario medir el impacto en la tarea tras realizar la conversión.

Monitoreo del modelo desplegado

El ciclo de vida no finaliza cuando la pérdida durante el entrenamiento se mantiene dentro de rangos aceptables. Se debe registrar como una única unidad de lanzamiento la versión del modelo base, el tokenizador y las plantillas de chat, el hash del adaptador, la versión del conjunto de datos, la configuración de entrenamiento y el informe de evaluación. En producción, se debe monitorear el éxito de las tareas, las salidas inválidas, los fallos en la política de comportamiento, la latencia y la deriva de las entradas utilizando los mismos indicadores que en modo offline. Asimismo, es necesario mantener accesible la versión anterior del modelo y definir un umbral de retroceso antes de iniciar el despliegue.

Conclusiones clave

  1. Realizar el ajuste fino solo después de haber comprobado que un modelo base sin ajustar y una taxonomía de fallos indican que la adaptación de pesos resuelve el problema.
  2. La recuperación de información gestiona la variabilidad de los datos de entrada; la decodificación restringida gestiona la sintaxis; ninguna de estas técnicas es sustituida por el entrenamiento basado en preferencias (SFT).
  3. LoRA reduce el número de parámetros entrenables. QLoRA, además, comprime los pesos base congelados. No se deben atribuir los valores de memoria de QLoRA a LoRA.
  4. La cobertura de datos, la integridad de las divisiones, el origen de los datos y el enmascaramiento de pérdidas son más importantes que copiar una configuración de optimizador de moda.
  5. Los métodos DPO, ORPO y PPO basados en RLHF son diseños experimentales distintos, y no constituyen una escala de calidad con un valor por defecto universal.
  6. Se debe evaluar el comportamiento deseado, las regresiones, la seguridad y las operaciones utilizando siempre el mismo modelo base.
  7. Antes de comenzar el entrenamiento, se debe elegir entre el formato de salida adaptador, fusionado o GGUF según los requisitos de servicio y posibles retrocesos.
