AI Agent Tool Use in 2026: MCP, CLI, Skills, and code execution

Parte 3 de la serie Engineering the Agentic Stack

Part 1 cubrió reasoning loops, y Part 2 cubrió memoria. Este artículo añade la capa de acción: cómo un agent expone, selecciona y ejecuta tools.

La historia del tooling cambió en 2025–2026. MCP dio a los vendors un protocolo compartido para servicios externos. Los agentes que ejecutan código mostraron que, a veces, un modelo puede componer un programa pequeño de forma más eficiente que emitir una larga secuencia de llamadas JSON. Anthropic reportó una reducción del 98,7% de tokens para un workflow de análisis de gastos, y el paper CodeAct reportó mejoras de hasta un 20% en su configuración de benchmark. Estos resultados describen sus tareas y harnesses, no una ventaja universal para la ejecución de código.

Comparo JSON tool calling, MCP, Skills, herramientas CLI y ejecución de código en ese orden. La sección final aplica los principios de diseño Agent-Computer Interface (ACI) al Market Analyst Agent.

TL;DR: Cinco patrones de interfaz útiles cubren la mayor parte del uso de herramientas por agents. Skills llevan instrucciones, las herramientas CLI encajan en desarrollo local, MCP conecta servicios compartidos y la ejecución de código compone trabajo multi-step dentro de un sandbox. JSON tool calling sigue siendo la opción más simple para acciones pequeñas y atómicas. Sea cual sea el protocolo, Agent-Computer Interface (ACI) debe hacer las acciones claras, el feedback compacto y los errores recuperables.

Five ways AI agents use tools

En Part 1, el reasoning loop eligió el siguiente paso. Part 2 almacenó el estado necesario para reanudarlo. El boundary de la tool convierte esa decisión en una acción y devuelve una observación al loop. Estos cinco patrones hacen trade-offs diferentes en coste de tokens, flexibilidad y enforcement.

1. JSON tool calling: la línea base

El patrón original: defines tool schemas en JSON, el LLM emite function calls estructuradas, tu código las ejecuta. Está bien entendido y funciona bien para conjuntos pequeños de tools.

# Traditional tool definition — each tool consumes ~550-1,400 tokens (Apideck benchmark)
tools = [
    {
        "name": "get_stock_price",
        "description": "Get the current stock price for a ticker symbol",
        "input_schema": {
            "type": "object",
            "properties": {
                "ticker": {"type": "string", "description": "Stock ticker (e.g., NVDA)"}
            },
            "required": ["ticker"]
        }
    }
]

Con 5-10 tools, el overhead es aceptable. El problema es la escala: cada definición de tool cuesta 550-1,400 tokens. Con 20 tools, estás gastando 15-25K tokens antes de que el agent incluso empiece a razonar.

2. MCP para integraciones compartidas

El Model Context Protocol es el estándar en el que la mayoría de vendors convergieron. Anthropic lo donó a la Linux Foundation en diciembre de 2025, bajo la Agentic AI Foundation (AAIF) que cofundó con OpenAI y Block. Google, Microsoft y AWS respaldan la fundación como miembros platinum. OpenAI añadió soporte MCP en su Responses API. Ahora hay 10.000+ MCP servers activos y 97M+ descargas mensuales de SDK.

MCP encaja en integraciones SaaS cross-vendor (Figma, Notion, Salesforce), servicios que no tienen equivalentes CLI y entornos que necesitan orquestación OAuth. Su valor está en una capa compartida de discovery y transporte. La gobernanza sigue dependiendo de los controles de autenticación, autorización, logging y despliegue del servidor.

La historia de producción es más enrevesada que lo que sugieren las cifras del titular.

La superficie de seguridad es el primer problema. El Vulnerable MCP Project rastrea 50 vulnerabilidades en MCP servers, 13 calificadas como Critical, aportadas por 32 investigadores de seguridad. Las clases de ataque incluyen prompt injection, fallos de validación de entrada, huecos de autenticación y agujeros de seguridad de red. El primer MCP server malicioso en la vida real apareció en septiembre de 2025: un paquete llamado postmark-mcp que BCC’d cada email saliente a la dirección de un atacante, afectando a unas 300–500 organizaciones antes del descubrimiento.

Tool poisoning es la clase de ataque por la que más me preocupa. Invariant Labs demostró que tools MCP envenenadas pueden exfiltrar datos incluso cuando nunca se invocan. Basta con que el modelo lea la metadata de la tool para disparar el ataque. MCPTox benchmarks probó 20 LLM agents contra 45 MCP servers reales y encontró tasas de éxito del ataque de hasta 72,8%.

El problema operativo es el overhead de tokens. Un equipo que ejecuta MCP servers para GitHub, Slack y Sentry (~40 tools en total) encontró 55.000 tokens de definiciones de schema inyectadas antes de que el usuario pida algo. Otro reportó 143.000 de 200.000 tokens disponibles (72%) consumidos solo por definiciones de tools.

Anthropic reportó una reducción del 85% de schema con su Tool Search Tool y una reducción del 96% al cargar tres a cinco tools relevantes para las tareas evaluadas. El loading selectivo mantiene la superficie del protocolo mientras elimina schemas que la petición actual no necesita.

3. Skills: experiencia empaquetada, no ejecución

A finales de 2025 llegó la estandarización de agent skills como un formato abierto (lanzado en octubre de 2025, publicado como estándar abierto en diciembre de 2025). Las tools proporcionan capacidades (lo que los agents pueden hacer), y skills aportan experiencia (lo que saben sobre cómo completar tareas complejas).

El estándar SKILL.md define una skill como un fichero markdown con YAML frontmatter:

---
name: deploy
description: Deploy the application to production
argument-hint: "[environment]"
user-invocable: true
---
Deploy the application to the $0 environment (default: staging).
Steps:
1. Run the test suite
2. Build the production bundle
3. Deploy using the deploy script
4. Verify the deployment health check

Las Skills usan progressive disclosure. Aproximadamente 100 tokens de metadata se cargan al inicio; las instrucciones completas solo se cargan cuando la skill está activa. Compáralo con los aprox. 55.000 tokens que unas 40 tools MCP pueden consumir antes de que empiece el razonamiento.

Para marzo de 2026, Claude Code, OpenAI Codex CLI, Cursor, GitHub Copilot, Gemini CLI, Goose, Windsurf y Roo Code habían adoptado el formato. Victor Dibia describe este cambio hacia acciones de agentes impulsadas por código.

Usa skills para conocimiento de dominio, procedimientos multi-step y trabajo recurrente como migraciones de bases de datos o integraciones de pagos. Encajan en tareas en las que el agent necesita instrucciones para cómo usar una capacidad existente.

4. CLI y herramientas de shell

Las interfaces CLI pueden ser mucho más baratas en contexto cuando el modelo ya conoce el comando. Scalekit reportó una diferencia de 4-32x tokens entre su ruta CLI y su ruta MCP en 75 ejecuciones. Ese estudio de caso mide sus tools y tareas; no sustituye una comparación en tus propios manifiestos y en la salida del comando.

Comandos documentados ampliamente como git, docker, kubectl, gh, curl y jq suelen necesitar poco texto de schema introductorio. Las CLIs menos comunes o internas todavía necesitan ayuda descubrible, ejemplos y una salida estable legible por máquina.

La guía de Ugo Enyioha “Writing CLI Tools That AI Agents Actually Want to Use” codificó ocho reglas de diseño:

  1. La salida estructurada es obligatoria — soportar --json
  2. Los exit codes son control flow — usar códigos distintos para diferentes tipos de error
  3. Los comandos deben ser idempotentes
  4. Self-documenting --help con ejemplos realistas
  5. Diseñar para composabilidad — --quiet para valores “pelados”, soporte de stdin
  6. Proporcionar flags --dry-run y --yes
  7. Soportar introspección de versión
  8. Gestionar auth con variables de entorno

CLI carece de type safety de MCP, orquestación OAuth integrada, tool discovery y audit trail. El patrón hacia el que veo converger a la mayoría de equipos es: CLI como opción por defecto para desarrollo y operaciones locales, MCP para integración de servicios externos y gobernanza enterprise.

5. Ejecución de código para trabajo multi-step

Este es el cambio en el tooling de agentes que considero más trascendental. En lugar de emitir JSON estructurado para invocar funciones predefinidas una a una, el agent escribe un script de Python o bash. El script llama a múltiples tools, procesa resultados con loops y conditionals, y devuelve solo el resumen final al contexto del modelo.

Anthropic lo formalizó con Programmatic Tool Calling (PTC), ahora GA en la Claude API. La base académica es el CodeAct paper (Wang et al., ICML 2024), que probó sobre 17 LLMs y encontró que las acciones de código logran hasta un 20% más de tasa de éxito y 30% menos steps que alternativas JSON.

Tres estudios de caso de primera parte muestran en qué puede ayudar el patrón: Vercel y Cloudflare por debajo, y luego el ejemplo de análisis de gastos de Anthropic. Trátalos como evidencia del vendor y repite la comparación en tus propias tareas.

  • Vercel reconstruyó su agent d0 text-to-SQL eliminando 80% de sus tools (de 15 a 2: ExecuteCommand y ExecuteSQL). El success pasó de 80% a 100%, el tiempo de ejecución bajó 3,5x y el uso de tokens cayó 40%. Su formulación: “Los mejores agents pueden ser los que tienen el menor número de tools.”

  • Cloudflare desarrolló “Code Mode,” permitiendo que los agents escriban TypeScript para llamar a su API en vez de definir tool schemas, lo que reduce overhead de contexto. Su razonamiento: “Los LLMs tienen una cantidad enorme de TypeScript real en su conjunto de entrenamiento, pero solo un pequeño conjunto de ejemplos artificiales de tool calls.”

Aquí está el patrón desde la documentación de PTC de Anthropic. La llamada tradicional a tools para análisis de gastos requiere 20+ pases de inferencia separados, uno por miembro del equipo, con todos los datos intermedios fluyendo por el contexto. Un workflow que consumía ~150.000 tokens con tool calling directo se reimplementó para ~2.000 tokens, un 98,7% de reducción. Con ejecución de código, el agent escribe un único script:

# Agent generates this code, executes in sandbox
import json
members = get_team_members("engineering")
over_budget = []
for m in members:
    expenses = get_expenses(m["id"], "Q3")
    total = sum(e["amount"] for e in expenses)
    if total > 5000:
        custom = get_custom_budget(m["id"])
        limit = custom["limit"] if custom else 5000
        if total > limit:
            over_budget.append({"name": m["name"], "spent": total, "limit": limit})
# Only this final summary returns to the LLM context
print(json.dumps(over_budget))

El LLM solo ve el resumen JSON final, no los miles de items de líneas de gasto procesados en el sandbox. La ganancia obvia es eficiencia de tokens. Los loops y conditionals salen “gratis”, los errores van por try/except en lugar de razonamiento en lenguaje natural sobre fallos, y los datos sensibles permanecen en el sandbox.

Cuándo todavía tiene sentido JSON tool calling: operaciones individuales atómicas, entornos sin infraestructura de sandboxing, modelos más pequeños con generación de código débil, o requisitos de auditoría que necesiten que cada invocación de tool quede logueada.

The Agent-Computer Interface (ACI) for AI agent tools

El término “Agent-Computer Interface” (ACI) fue acuñado por John Yang, Carlos E. Jimenez y colegas en Princeton en su SWE-agent paper (NeurIPS 2024). Igual que a los humanos les benefician interfaces bien diseñadas (HCI), el paper argumenta que los LM agents son “una nueva categoría de end users con sus propias necesidades y capacidades, y se beneficiarían de interfaces especialmente construidas”.

Sus resultados de ablation pusieron números a esa idea. SWE-agent con su ACI completa consiguió 18,0% en SWE-bench Lite frente a 7,3% usando solo un Linux shell estándar: una mejora de 10,7 puntos porcentuales atribuible solo al diseño de la interfaz. El guardrail de linting por sí solo explicó 3 puntos porcentuales: 51,7% de las ediciones del agent tenían al menos un error capturado por el linter antes de poder propagarse.

Anthropic adoptó ACI como concepto fundacional en su guía “Building Effective Agents”, listándolo como uno de tres principios core: “Carefully craft your agent-computer interface through thorough tool documentation and testing.” Su guía práctica: “Una regla general es pensar en cuánto esfuerzo se invierte en interfaces humano-computadora y planificar invertir el mismo esfuerzo para crear buenas agent-computer interfaces.”

Cuatro principios de ACI en práctica

1. Las acciones deben ser simples y fáciles de entender. El error más común es envolver endpoints de API 1:1. En lugar de list_users, list_events, create_event, implementa schedule_event que encuentra disponibilidad y programa en una sola llamada. En lugar de read_logs, implementa search_logs que devuelve solo las líneas relevantes con contexto.

2. Las acciones deben ser compactas y eficientes. Consolidar operaciones importantes en el menor número posible de acciones. En el Market Analyst Agent, combino la obtención de precios con métricas básicas en una única get_stock_snapshot tool en vez de requerir llamadas separadas para precio, volumen, market cap y PE ratio.

3. El feedback del entorno debe ser informativo pero conciso. Evita devolver HTML crudo o payloads completos de API. Resuelve IDs crípticos a nombres semánticos. Las pruebas de Anthropic añadieron un enum response_format para que el agent pueda pedir una respuesta concisa (~72 tokens) o detallada (~206 tokens), con una diferencia aproximada de 3x en coste de tokens. Reportaron mejor rendimiento en el mundo real.

4. Los guardrails deben mitigar la propagación de errores. La detección automática de errores ayuda a los agents a reconocer y corregir fallos rápidamente. En SWE-agent, un editor de ficheros custom con linting integrado rechaza automáticamente errores de sintaxis, capturando al menos un error en 51,7% de las ediciones del agent antes de que pudiera complicarse. Aplico el mismo principio en el Market Analyst Agent validando argumentos de tool con schemas Pydantic antes de la ejecución:

from pydantic import BaseModel, Field, field_validator

class StockQuery(BaseModel):
    """Validated input for stock queries.

    Pydantic catches malformed tickers before the API call,
    preventing error propagation through the reasoning loop.
    """
    ticker: str = Field(description="Stock ticker symbol (e.g., NVDA)")
    period: str = Field(default="1mo", description="Time period: 1d, 5d, 1mo, 3mo, 1y")

    @field_validator("ticker")
    @classmethod
    def validate_ticker(cls, v: str) -> str:
        v = v.upper().strip()
        if not v.isalpha() or len(v) > 5:
            raise ValueError(f"Invalid ticker format: {v}")
        return v

    @field_validator("period")
    @classmethod
    def validate_period(cls, v: str) -> str:
        valid = {"1d", "5d", "1mo", "3mo", "6mo", "1y", "5y"}
        if v not in valid:
            raise ValueError(f"Invalid period: {v}. Must be one of {valid}")
        return v

AI agent tool design patterns that work

La guía de Anthropic “Writing effective tools for agents” enmarca las tools como “un nuevo tipo de software que refleja un contrato entre sistemas deterministas y agents no deterministas”.

Tratar descripciones de tools como prompt engineering

Las descripciones deberían ejecutarse 3-4+ sentencias mínimo, cubriendo cuándo usar la tool, parámetros requeridos vs opcionales, formato de salida y casos límite. El “namespacing” con prefijos (asana_search, jira_search) tiene “efectos no triviales” en la precisión de selección de tools. En experimentos de Anthropic, descripciones de tools optimizadas para Claude superaron a las escritas por expertos humanos en benchmarks de evaluación.

# Bad: vague, no context for when to use
tools = [{
    "name": "search",
    "description": "Search for items",
}]

# Good: specific, with input examples and edge cases
tools = [{
    "name": "stock_search_news",
    "description": (
        "Search for recent news articles about a specific stock or company. "
        "Use this tool when the user asks about recent events, earnings, "
        "announcements, or market-moving news for a specific ticker. "
        "Returns up to 10 articles sorted by relevance. "
        "For broad market news (not ticker-specific), use market_overview instead."
    ),
    "input_schema": {
        "type": "object",
        "properties": {
            "query": {
                "type": "string",
                "description": "Search query. Examples: 'NVDA earnings Q3 2025', 'Tesla delivery numbers'"
            },
            "max_results": {
                "type": "integer",
                "description": "Max articles to return (1-10, default 5)",
                "default": 5
            }
        },
        "required": ["query"]
    }
}]

Testing interno mostró que los ejemplos de entrada (input_examples field) mejoran sustancialmente la precisión en el manejo de parámetros complejos.

Devolver output de alto valor y legible por máquina

Evita identificadores de bajo nivel (uuid, mime_type). Resuelve IDs crípticos a nombres semánticos. Estructura la respuesta para que el agent pueda razonar sin tener que parsear boilerplate:

# Bad: raw API response dumped to agent
def get_stock_price(ticker: str) -> dict:
    response = api.get(f"/v1/quotes/{ticker}")
    return response.json()  # 500+ tokens of nested JSON

# Good: high-signal summary the agent can immediately reason about
def get_stock_price(ticker: str) -> dict:
    data = api.get(f"/v1/quotes/{ticker}").json()
    return {
        "ticker": ticker,
        "price": data["regularMarketPrice"],
        "change_pct": round(data["regularMarketChangePercent"], 2),
        "volume": data["regularMarketVolume"],
        "market_cap_b": round(data["marketCap"] / 1e9, 1),
        "pe_ratio": data.get("trailingPE"),
        "summary": f"{ticker} at ${data['regularMarketPrice']:.2f} "
                   f"({'up' if data['regularMarketChangePercent'] > 0 else 'down'} "
                   f"{abs(data['regularMarketChangePercent']):.1f}%)"
    }

Devolver errores que el loop pueda ejecutar

Usa cuatro mecanismos separados porque manejan clases de fallo distintas:

  1. Reintento con exponential backoff para errores transitorios
  2. Model fallback chains para caídas del provider
  3. Error classification routing — errores transitorios se reintentan, errores recuperables por LLM devuelven contexto al agent, errores que requieren intervención humana escalan
  4. Recuperación desde checkpoint para sobrevivir a crash

La guía de Anthropic citada respalda errores claros de tool y diseño orientado a evaluación. No establece una reducción universal de tasa de fallo, así que mide tu tasa de recuperación, reintentos y escalado en tu suite de tareas.

from tenacity import retry, stop_after_attempt, wait_exponential

@retry(
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=1, min=2, max=10),
)
def call_stock_api(ticker: str) -> dict:
    """Fetch stock data with automatic retry on transient failures.

    Layer 1: Exponential backoff handles rate limits and network blips.
    If all retries fail, the error propagates to the agent with
    enough context to decide whether to try a different approach.
    """
    response = httpx.get(
        f"https://api.example.com/v1/quotes/{ticker}",
        timeout=10.0,
    )
    response.raise_for_status()
    return response.json()

Cada una era un wrapper fino alrededor de un endpoint de API. El agent tenía que razonar qué combinación llamar para cada request.

Salidas estructuradas para resultados de tools

Cada tool del Market Analyst Agent devuelve una respuesta validada con Pydantic. Esto aplica el principio de guardrails de ACI en el boundary de la tool:

class StockSnapshot(BaseModel):
    """Structured tool response — the agent never sees raw API noise."""
    ticker: str
    price: float
    change_pct: float
    volume: int
    market_cap_b: float
    pe_ratio: float | None
    summary: str  # Human-readable one-liner for direct use in reports

class NewsResult(BaseModel):
    """Each news item is pre-processed for agent consumption."""
    headline: str
    source: str
    date: str
    relevance_score: float  # Pre-ranked so the agent doesn't waste tokens sorting
    key_points: list[str]  # Extracted by the tool, not the agent

El campo summary es el que más importa. Proporciona al agent una string lista para usar que puede insertarse directamente en un informe sin procesamiento adicional. El key_points en NewsResult se extrae en el servidor, ahorrando al agent gastar tokens de inferencia parseando cuerpos de artículos.

Trade-offs y consideraciones

Más allá de las cautelas específicas por modalidad descritas arriba, hay algunas preocupaciones transversales que condicionan la elección:

  • El coste operativo varía por dimensión. La ejecución de código ahorra tokens pero añade latencia por cold-start de sandbox. MCP ahorra tiempo de desarrollo para integraciones SaaS pero añade overhead por despliegue de server. CLI puede arrancar sin coste pero es más difícil de gobernar a gran escala. Optimiza para tu cuello de botella real: coste de tokens, latencia o complejidad operativa.

  • Las habilidades del equipo importan. La ejecución de código asume que tus agents (y los modelos detrás de ellos) pueden generar Python o TypeScript fiable. CLI asume familiaridad con convenciones Unix. MCP requiere entender protocolos de transporte y flujos OAuth. Ajusta la modalidad a las fortalezas de tu equipo.

  • La consolidación de tools puede ir demasiado lejos. Si una tool acumula modos y argumentos no relacionados, el agent se enfrenta a un problema de selección distinto dentro del schema. Usa evaluaciones de selección de tool y de success de tareas para encontrar la superficie adecuada para tu carga de trabajo.

  • Skills son prompt-based, no enforced. Una skill son instrucciones que el agent debería seguir, no guardrails que tenga que seguir. Para workflows críticos, combina skills con validación determinista.

  • Los requisitos de auditoría condicionan la elección. Si necesitas un log completo de cada invocación de tool y su resultado, MCP y JSON tool calling proporcionan audit trails estructurados “out of the box”. La ejecución de código produce un script y su salida: útil, pero más difícil de descomponer en acciones individuales para reporting de compliance.

Tool selection at larger scale

Tres direcciones merece la pena seguir.

La primera es tool RAG para escalar. A medida que los toolsets crecen hasta cientos o miles, la precisión naive de selección de tools cae al 13,62%. El RAG-MCP paper aplicó retrieval-augmented generation a la selección de tools: indexar las descripciones de tools en una base de datos vectorial y recuperar solo las relevantes por query. Esto alcanzó 43,13% de accuracy, una mejora de 3,2x, mientras se cortaban ~50% los tokens del prompt.

La segunda es que los agents creen sus propias tools. El LATM framework (“LLMs As Tool Makers”) estableció un paradigma en dos fases donde un LLM potente crea funciones Python reutilizables y un LLM ligero las usa. ToolMaker (ACL 2025) transforma de forma autónoma repositorios de GitHub en tools compatibles con LLM con una tasa de éxito del 80%. Ambos apuntan más allá del uso de tools hacia la creación de tools, y luego hacia la gestión de una librería de tools generadas.

La tercera es el stack dual-protocol A2A + MCP. El Google Agent2Agent Protocol (A2A) aborda lo que MCP no puede: comunicación entre agents. MCP gestiona la integración agent-to-tool; A2A gestiona discovery, negociación y delegación de tareas entre agents.

Key takeaways

  1. Elige la interfaz desde la acción: JSON calling para operaciones tipadas pequeñas, MCP para servicios compartidos, Skills para procedimientos, CLI para comandos establecidos y código en sandbox para composición local.
  2. Mantén las condiciones del benchmark pegadas al resultado. CodeAct, Anthropic, Vercel, Cloudflare, Apideck y Scalekit midieron modelos, tareas, tools y harnesses distintos.
  3. La calidad ACI sobrevive a cambios de protocolo. Acciones claras, feedback compacto, validación y errores útiles ayudan a cualquier modalidad.
  4. Consolida tools solapadas solo cuando las evaluaciones demuestren que una superficie más pequeña mejora la selección o el success de tareas.
  5. La seguridad se mueve con el poder de ejecución. Interfaces de shell y código necesitan sandboxing; MCP necesita identidad con alcance y política del server; Skills siguen siendo instrucciones, no enforcement.

The next layer is policy

La Parte 4, AI Agent Security in 2026, pone una comprobación de policy entre una tool call propuesta y su ejecución. La Parte 5 coloca la tool y su sandbox en un runtime recuperable. La Parte 6 vuelve a la interfaz desde el lado del harness: cómo traces, evaluators, reglas de retry y checks de aceptación convierten el feedback de tools en un loop de mejora medido.
