Uso de herramientas en agentes de IA: MCP, CLI, Skills y ejecución de código

Parte 3 de la serie Engineering the Agentic Stack

La Parte 1 trataba los ciclos de razonamiento y la Parte 2, la memoria. Este artículo añade la capa de acción: cómo un agente expone, selecciona y ejecuta herramientas. La memoria determina qué sabe el agente al iniciar un turno; esta capa determina qué puede hacer con ello. La Parte 4 trata la comprobación que decide si una llamada con nombre llega siquiera a ejecutarse, y la Parte 6 trata el harness que ejecuta tanto la llamada como la comprobación. En todo este artículo, harness significa el programa de control que ensambla cada prompt, distribuye las llamadas a herramientas que acepta y decide cuándo ha terminado la tarea: todo lo que rodea al modelo y que implementas como código convencional.

La historia de las herramientas cambió en 2025–2026. MCP, el Model Context Protocol, proporcionó a los proveedores una forma compartida de exponer servicios externos. Los agentes capaces de ejecutar código demostraron que, en ocasiones, un modelo puede componer un programa pequeño de forma más eficiente que emitir una larga secuencia de llamadas JSON. Anthropic informó de una reducción del 98,7 % en tokens para un flujo de trabajo de Google Drive a Salesforce, y el artículo de CodeAct informó de mejoras de hasta el 20 % en su configuración de benchmarks. Estos resultados describen sus tareas y harnesses, no una ventaja universal de la ejecución de código.

Comparo las llamadas a herramientas mediante JSON, MCP, Skills, las herramientas CLI y la ejecución de código, en ese orden. Una sección posterior aplica principios de diseño de Agent-Computer Interface (ACI) al Market Analyst Agent, un pequeño agente de investigación basado en LangGraph que desarrollé para la Parte 1 y que obtiene datos de mercado y redacta un informe de análisis.

Para consultar una decisión breve sobre interfaces, véase AI Agent Tool Interfaces.

TL;DR: Cinco patrones de interfaz útiles cubren la mayoría de los casos de uso de herramientas en agentes. Las Skills contienen instrucciones, las herramientas CLI encajan en el desarrollo local, MCP conecta servicios compartidos y la ejecución de código compone trabajos de varios pasos dentro de un sandbox. Las llamadas a herramientas mediante JSON siguen siendo la opción más sencilla para acciones pequeñas y atómicas. Sea cual sea el protocolo, la Agent-Computer Interface (ACI) debe hacer que las acciones sean claras, el feedback sea compacto y los errores se puedan recuperar.

Cinco formas de usar herramientas en agentes de IA

En la Parte 1, el ciclo de razonamiento elegía el siguiente paso. La Parte 2 almacenaba el estado necesario para reanudarlo. El límite de herramientas se sitúa entre ambos: valida lo que ha propuesto el ciclo, envía la llamada para su ejecución y devuelve el resultado al ciclo. Estos cinco patrones implican distintas decisiones de compromiso en cuanto al coste en tokens, la flexibilidad y el control de la ejecución.

1. Llamadas a herramientas mediante JSON: el punto de partida

El patrón original: defines los esquemas de las herramientas como JSON, el LLM emite llamadas estructuradas a funciones y tu código las ejecuta. Es un enfoque conocido y funciona bien con conjuntos pequeños de herramientas.

# Traditional tool definition — each tool consumes ~550-1,400 tokens (Apideck benchmark)
tools = [
    {
        "name": "get_stock_price",
        "description": "Get the current stock price for a ticker symbol",
        "input_schema": {
            "type": "object",
            "properties": {
                "ticker": {"type": "string", "description": "Stock ticker (e.g., NVDA)"}
            },
            "required": ["ticker"]
        }
    }
]

Con entre 5 y 10 herramientas, la sobrecarga es aceptable. El problema aparece al escalar: cada definición de herramienta cuesta entre 550 y 1.400 tokens. Con 20 herramientas, gastas entre 11.000 y 28.000 tokens antes siquiera de que el agente empiece a razonar.

2. MCP para integraciones compartidas

MCP es el estándar en el que han convergido la mayoría de los proveedores. Un servidor MCP es un proceso que anuncia una lista de herramientas mediante un protocolo de comunicación definido: stdio para un proceso local y HTTP para uno remoto. Tu agente ejecuta un cliente MCP que se conecta, pregunta al servidor qué herramientas tiene y reenvía las llamadas del modelo, de modo que el mismo servidor funciona con cualquier cliente que implemente el protocolo. Anthropic donó el protocolo a la Linux Foundation en diciembre de 2025, dentro de la Agentic AI Foundation, que cofundó con OpenAI y Block. Google, Microsoft y AWS respaldan la fundación como miembros platinum. OpenAI añadió compatibilidad con MCP en su Responses API. Según el anuncio de donación de Anthropic de diciembre de 2025, el ecosistema contaba con más de 10.000 servidores MCP públicos activos y más de 97 millones de descargas mensuales de los SDK de Python y TypeScript.

MCP encaja en integraciones SaaS entre proveedores (Figma, Notion, Salesforce), servicios sin equivalentes de CLI y entornos que necesitan orquestación de OAuth. Su valor reside en ofrecer una capa compartida de descubrimiento y transporte. La gobernanza sigue dependiendo de los controles de autenticación, autorización, logging y despliegue del servidor.

La realidad en producción es más compleja de lo que sugieren las cifras principales.

La superficie de seguridad es el primer problema. El proyecto Vulnerable MCP registra 50 vulnerabilidades en servidores MCP, 13 de ellas con una valoración Critical, aportadas por 32 investigadores de seguridad. Las clases de ataque abarcan prompt injection, fallos de validación de entradas, carencias de autenticación y vulnerabilidades de seguridad de red. El primer servidor MCP malicioso del mundo real apareció en septiembre de 2025: un paquete llamado postmark-mcp que enviaba en BCC todos los correos salientes a la dirección de un atacante y que afectó, según las estimaciones, a entre 300 y 500 organizaciones antes de ser descubierto.

El tool poisoning es la clase de ataque que más me preocupa. Invariant Labs demostró que las herramientas MCP envenenadas pueden exfiltrar datos aunque nunca se invoquen. Basta con que el modelo lea los metadatos de la herramienta para activar el ataque. Los benchmarks MCPTox, que probaron 20 agentes LLM contra 45 servidores MCP reales, detectaron tasas de éxito de los ataques de hasta el 72,8 %.

El overhead de tokens es el problema operativo. Un equipo que ejecutaba servidores MCP para GitHub, Slack y Sentry (unas 40 herramientas en total) descubrió que se inyectaban 55.000 tokens de definiciones de esquemas antes de que el usuario preguntara nada. Otro equipo informó de que las definiciones de herramientas por sí solas consumían 143.000 de los 200.000 tokens disponibles (72 %).

Anthropic informó de una reducción del 85 % en los tokens de definiciones de herramientas mediante su Tool Search Tool: aproximadamente 77.000 tokens de esquemas se redujeron a 8.700 al cargar únicamente las tres a cinco herramientas que realmente necesita una solicitud. La carga selectiva mantiene la superficie del protocolo y elimina los esquemas que la solicitud actual no necesita.

3. Las skills empaquetan expertise, no ejecución

A finales de 2025 se estandarizaron las agent skills como un formato abierto (lanzado en octubre de 2025 y publicado como estándar abierto en diciembre de 2025). Las herramientas proporcionan capacidades (lo que pueden hacer los agentes), mientras que las skills aportan expertise (lo que los agentes saben sobre cómo realizar tareas complejas).

El formato SKILL.md define una skill como un archivo Markdown con frontmatter YAML. El estándar abierto solo requiere name y description; el ejemplo siguiente también utiliza dos extensiones de Claude Code, argument-hint y user-invocable, además de su placeholder de argumento posicional $0:

---
name: deploy
description: Deploy the application to production
argument-hint: "[environment]"
user-invocable: true
---
Deploy the application to the $0 environment (default: staging).
Steps:
1. Run the test suite
2. Build the production bundle
3. Deploy using the deploy script
4. Verify the deployment health check

Las skills utilizan divulgación progresiva. Al iniciarse, se cargan unos 100 tokens de metadatos; las instrucciones completas solo se cargan cuando la skill está activa. Compárese con los aproximadamente 55.000 tokens que unas 40 herramientas MCP pueden consumir antes de que comience el razonamiento.

En marzo de 2026, Claude Code, OpenAI Codex CLI, Cursor, GitHub Copilot, Gemini CLI, Goose, Devin Desktop (entonces Windsurf) y Roo Code habían adoptado el formato. Las skills forman parte de un cambio más amplio hacia acciones de agentes basadas en código, que Victor Dibia rastrea desde las llamadas a funciones JSON hasta el código generado: el patrón que cubre la sección 5.

Utiliza skills para conocimiento de dominio, procedimientos de varios pasos y tareas recurrentes, como migraciones de bases de datos o integraciones de pagos. Encajan en tareas en las que el agente necesita instrucciones sobre cómo utilizar una capacidad existente.

4. Herramientas CLI y de shell

Las interfaces CLI pueden consumir mucho menos contexto cuando el modelo ya conoce el comando. Scalekit informó de una diferencia de 4-32x tokens entre sus rutas CLI y MCP en 75 ejecuciones. Ese estudio de caso mide sus herramientas y tareas; no sustituye una comparación con tus propias definiciones de herramientas y la salida de tus comandos.

Los comandos ampliamente documentados, como git, docker, kubectl, gh, curl y jq, a menudo necesitan muy poco texto introductorio de esquema. Las CLI menos habituales o internas siguen necesitando ayuda descubrible, ejemplos y una salida estable y legible por máquinas.

La guía de Ugo Enyioha “Writing CLI Tools That AI Agents Actually Want to Use” estableció ocho reglas de diseño:

  1. La salida estructurada es obligatoria — admite --json
  2. Los códigos de salida son control de flujo — utiliza códigos distintos para cada tipo de error
  3. Los comandos deben ser idempotentes
  4. Documentación integrada --help con ejemplos realistas
  5. Diseña para la composabilidad — --quiet para valores sin formato y compatibilidad con stdin
  6. Proporciona los flags --dry-run y --yes
  7. Admite la introspección de versiones
  8. Gestiona la autenticación mediante variables de entorno

La CLI carece de la seguridad de tipos, la orquestación OAuth integrada, el descubrimiento de herramientas y la trazabilidad de auditoría de MCP. El patrón hacia el que veo converger a la mayoría de los equipos es: CLI como opción predeterminada para el desarrollo y las operaciones locales, y MCP para la integración con servicios externos y la gobernanza empresarial.

5. Ejecución de código para trabajo de varios pasos

Este es el cambio en las herramientas de agentes que considero más importante. En lugar de emitir JSON estructurado para invocar funciones predefinidas una a una, el agente escribe un script de Python o bash. El script llama a varias herramientas, procesa los resultados con bucles y condicionales, y devuelve al contexto del modelo únicamente el resumen final.

Anthropic formalizó este enfoque con Programmatic Tool Calling (PTC), ya disponible de forma general en la API de Claude. La base académica es el artículo de CodeAct (Wang et al., ICML 2024), que evaluó 17 LLM y descubrió que las acciones mediante código lograban hasta un 20 % más de tasa de éxito en las tareas y requerían un 30 % menos de pasos que las alternativas basadas en JSON.

Tres casos prácticos propios muestran dónde puede ayudar este patrón: Vercel y Cloudflare, a continuación, y después el ejemplo de Anthropic sobre análisis de gastos. Considéralos pruebas aportadas por los proveedores y vuelve a ejecutar la comparación con tus propias tareas.

  • Vercel reconstruyó d0, su agente de datos de lenguaje natural a SQL, reduciéndolo de 15 herramientas a 2 — ExecuteCommand y ExecuteSQL —; en su publicación, redondean la reducción al 80 %. En cinco consultas representativas, el éxito de las tareas pasó de 4/5 a 5/5, el tiempo medio de ejecución se redujo 3,5 veces (de 274,8 s a 77,4 s) y el uso medio de tokens cayó un 37 % (de ~102k a ~61k). En sus palabras: «Los mejores agentes podrían ser los que tienen menos herramientas».

  • Cloudflare desarrolló «Code Mode», que permite a los agentes escribir TypeScript para llamar a su API en lugar de definir esquemas de herramientas, lo que reduce la sobrecarga de contexto. Su razonamiento: «Los LLM tienen una cantidad enorme de TypeScript del mundo real en sus datos de entrenamiento, pero solo un pequeño conjunto de ejemplos artificiales de llamadas a herramientas».

Este es el patrón que aparece en la documentación de PTC de Anthropic. El tool calling tradicional para analizar gastos requiere más de 20 pasadas de inferencia independientes, una por cada miembro del equipo, y todos los datos intermedios pasan por el contexto. Anthropic informa de que el código generado que responde a la misma pregunta reduce lo que llega al contexto desde 200 KB de filas de gastos sin procesar —más de 2.000 partidas— hasta 1 KB de resultados. Con la ejecución de código, el agente escribe un único script:

# Agent generates this code, executes in sandbox
import json
members = get_team_members("engineering")
over_budget = []
for m in members:
    expenses = get_expenses(m["id"], "Q3")
    total = sum(e["amount"] for e in expenses)
    if total > 5000:
        custom = get_custom_budget(m["id"])
        limit = custom["limit"] if custom else 5000
        if total > limit:
            over_budget.append({"name": m["name"], "spent": total, "limit": limit})
# Only this final summary returns to the LLM context
print(json.dumps(over_budget))

El LLM solo ve el resumen JSON final, no las miles de partidas de gastos procesadas en el sandbox. El ahorro no es exclusivo de los informes de gastos: el artículo independiente de Anthropic sobre ejecución de código ofrece la cifra más contundente para este patrón, en un flujo de trabajo de Google Drive a Salesforce que pasó de ~150.000 tokens a ~2.000, una reducción del 98,7 %.

La eficiencia en tokens es la ventaja más evidente. Los bucles y las condicionales salen gratis, los errores se gestionan mediante try/except en lugar de razonamiento en lenguaje natural sobre los fallos, y los datos sensibles permanecen en el sandbox.

Cuándo sigue teniendo sentido el tool calling con JSON: operaciones atómicas individuales, entornos sin infraestructura de sandboxing, modelos pequeños con una capacidad limitada para generar código o requisitos de auditoría que necesiten registrar cada invocación individual de una herramienta.

La interfaz agente-ordenador (ACI) para herramientas de agentes de IA

El término «Agent-Computer Interface» (ACI) fue acuñado por John Yang, Carlos E. Jimenez y sus colaboradores de Princeton en su artículo sobre SWE-agent (NeurIPS 2024). La calidad de las interfaces para personas cuenta con toda una disciplina dedicada a ella —la interacción persona-ordenador, o HCI—. El artículo sostiene que los agentes basados en modelos de lenguaje merecen el mismo tratamiento: son «una nueva categoría de usuarios finales, con sus propias necesidades y capacidades, que se beneficiarían de interfaces diseñadas específicamente para ellos».

Sus resultados de ablación ponen cifras a esta cuestión. Con el mismo modelo base GPT-4 Turbo, la ablación del artículo en SWE-bench Lite alcanzó el 18,0 % con el ACI completo de SWE-agent en 300 tareas, frente al 7,3 % de la condición basada únicamente en shell, sin una demostración resuelta, y al 11,0 % con una. La comparación muestra que la interfaz y las condiciones de demostración cambiaron sustancialmente el rendimiento en esta configuración; no aísla el diseño de la interfaz de cualquier otra diferencia ni demuestra que el modelo no realizara trabajo alguno. Dentro de la misma ablación de interfaz, activar el linting elevó la condición de edición del 15,0 % al 18,0 %; en el conjunto completo de pruebas de SWE-bench, el 51,7 % de las ejecuciones de SWE-agent intentaron al menos una edición que el linter rechazó antes de que pudiera propagarse.

Anthropic adoptó ACI como concepto fundamental en su guía “Building Effective Agents”, donde lo presenta como uno de los tres principios básicos: «Diseña cuidadosamente la interfaz entre el agente y el ordenador mediante una documentación y unas pruebas exhaustivas de las herramientas». Su recomendación práctica es: «Una regla general es pensar en cuánto esfuerzo se dedica a las interfaces persona-ordenador y planificar invertir el mismo esfuerzo en crear buenas interfaces agente-ordenador».

Cuatro principios de ACI en la práctica

1. Las acciones deben ser sencillas y fáciles de entender. El error más habitual es encapsular los endpoints de la API uno a uno. En lugar de list_users, list_events, create_event, implementa schedule_event, que busca disponibilidad y programa la cita en una sola llamada. En lugar de read_logs, implementa search_logs, que devuelve únicamente las líneas relevantes con contexto.

2. Las acciones deben ser compactas y eficientes. Consolida las operaciones importantes en el menor número posible de acciones. En Market Analyst Agent, combino la obtención de precios con métricas básicas en una única herramienta get_stock_snapshot, en lugar de exigir llamadas independientes para el precio, el volumen, la capitalización bursátil y el PER.

3. La información del entorno debe ser útil, pero concisa. Evita devolver HTML sin procesar o payloads completos de la API. Resuelve los identificadores crípticos con nombres semánticos. Las pruebas de Anthropic añadieron un enum response_format para que el agente pueda solicitar una respuesta concisa (unos 72 tokens) o detallada (unos 206 tokens), lo que supone aproximadamente una diferencia de 3x en el coste en tokens.

4. La validación debe mitigar la propagación de errores. La detección automática de errores ayuda a los agentes a reconocer y corregir rápidamente sus fallos. En SWE-agent, un editor de archivos personalizado con linting integrado rechaza automáticamente los errores de sintaxis: es el paso de validación que explica la cifra del 51,7 % anterior. Esta validación se aplica a las entradas y salidas de una herramienta, no al filtrado de contenido que rodea una llamada al modelo y que realizan los productos de guardrails de la Parte 4; se utiliza la misma palabra para ambas cosas. Aplico el mismo principio en Market Analyst Agent validando los argumentos de las herramientas con esquemas de Pydantic antes de la ejecución:

from pydantic import BaseModel, Field, field_validator

class StockQuery(BaseModel):
    """Validated input for stock queries.

    Pydantic catches malformed tickers before the API call,
    preventing error propagation through the reasoning loop.
    """
    ticker: str = Field(description="Stock ticker symbol (e.g., NVDA)")
    period: str = Field(default="1mo", description="Time period: 1d, 5d, 1mo, 3mo, 6mo, 1y")

    @field_validator("ticker")
    @classmethod
    def validate_ticker(cls, v: str) -> str:
        v = v.upper().strip()
        if not v.isalpha() or len(v) > 5:
            raise ValueError(f"Invalid ticker format: {v}")
        return v

    @field_validator("period")
    @classmethod
    def validate_period(cls, v: str) -> str:
        valid = {"1d", "5d", "1mo", "3mo", "6mo", "1y"}
        if v not in valid:
            raise ValueError(f"Invalid period: {v}. Must be one of {valid}")
        return v

Patrones de diseño de herramientas para agentes de IA que funcionan

La guía de Anthropic “Writing effective tools for agents” presenta las herramientas como «un nuevo tipo de software que refleja un contrato entre sistemas deterministas y agentes no deterministas».

Tratar las descripciones de las herramientas como prompt engineering

Las descripciones deberían tener al menos tres o cuatro frases que indiquen cuándo usar la herramienta, qué parámetros son obligatorios y cuáles opcionales, el formato de salida y los casos límite. Anthropic informa de que la elección entre los nombres con namespace basado en el prefijo y en el sufijo (asana_search frente a search_asana) tuvo «efectos no triviales» en sus propias evaluaciones de uso de herramientas. No indica qué esquema funciona mejor, así que prueba ambos con tu conjunto de herramientas en lugar de dar por hecho que los prefijos son superiores. Anthropic también introdujo las transcripciones de sus agentes de evaluación en Claude Code y le permitió reescribir las herramientas. En conjuntos de prueba reservados, ese bucle obtuvo mejoras adicionales «incluso más allá de lo que logramos con implementaciones de herramientas “expertas”», tanto si las habían escrito manualmente sus investigadores como si las había generado Claude.

# Bad: vague, no context for when to use
tools = [{
    "name": "search",
    "description": "Search for items",
}]

# Good: specific, with input examples and edge cases
tools = [{
    "name": "search_news",
    "description": (
        "Search for recent news articles about a specific stock or company. "
        "Use this tool when the user asks about recent events, earnings, "
        "announcements, or market-moving news for a specific ticker. "
        "Returns up to 10 articles sorted by relevance. "
        "For company competitors rather than news, use search_competitors instead."
    ),
    "input_schema": {
        "type": "object",
        "properties": {
            "query": {
                "type": "string",
                "description": "Search query. Examples: 'NVDA earnings Q3 2025', 'Tesla delivery numbers'"
            },
            "max_results": {
                "type": "integer",
                "description": "Max articles to return (1-10, default 5)",
                "default": 5
            }
        },
        "required": ["query"]
    }
}]

Las pruebas internas de Anthropic mostraron que añadir un campo input_examples elevó la precisión en el manejo de parámetros complejos del 72 % al 90 %.

Devolver una salida de alta señal y legible por máquinas

Evita los identificadores de bajo nivel (uuid, mime_type). Resuelve los ID crípticos en nombres semánticos. Estructura la respuesta para que el agente pueda razonar sobre ella sin tener que analizar boilerplate:

# Bad: raw API response dumped to agent
def get_stock_snapshot(ticker: str) -> dict:
    response = api.get(f"/v1/quotes/{ticker}")
    return response.json()  # 500+ tokens of nested JSON

# Good: high-signal summary the agent can immediately reason about
def get_stock_snapshot(ticker: str) -> dict:
    data = api.get(f"/v1/quotes/{ticker}").json()
    return {
        "ticker": ticker,
        "price": data["regularMarketPrice"],
        "change_pct": round(data["regularMarketChangePercent"], 2),
        "volume": data["regularMarketVolume"],
        "market_cap_b": round(data["marketCap"] / 1e9, 1),
        "pe_ratio": data.get("trailingPE"),
        "summary": f"{ticker} at ${data['regularMarketPrice']:.2f} "
                   f"({'up' if data['regularMarketChangePercent'] > 0 else 'down'} "
                   f"{abs(data['regularMarketChangePercent']):.1f}%)"
    }

Devolver errores sobre los que el bucle pueda actuar

El manejo de errores necesita cuatro mecanismos independientes, porque cada uno gestiona una clase de fallos distinta:

  1. Reintentos con backoff exponencial para errores transitorios
  2. Cadenas de fallback de modelos ante caídas del proveedor
  3. Enrutamiento por clasificación de errores: los errores transitorios se reintentan, los errores recuperables por el LLM se devuelven al agente con contexto y los errores que requieren intervención humana se escalan
  4. Recuperación mediante checkpoints para sobrevivir a crashes

El artículo de Anthropic “Writing effective tools for agents” defiende unos errores de herramienta claros y un diseño guiado por evaluaciones, pero no establece una cifra universal sobre cuánto recuperan estos cuatro mecanismos. Mide la tasa de recuperación, los reintentos y las escalaciones en tu propia suite de tareas.

import httpx
from tenacity import retry, stop_after_attempt, wait_exponential

@retry(
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=1, min=2, max=10),
)
def call_stock_api(ticker: str) -> dict:
    """Fetch stock data with automatic retry on transient failures.

    Mechanism 1 of the four above: exponential backoff for rate limits
    and network blips.
    If all retries fail, the error propagates to the agent with
    enough context to decide whether to try a different approach.
    """
    response = httpx.get(
        f"https://api.example.com/v1/quotes/{ticker}",
        timeout=10.0,
    )
    response.raise_for_status()
    return response.json()

Aplicación de los patrones al Market Analyst Agent

El Market Analyst Agent de la Parte 1 hace visible el efecto de la interfaz.

Consolidación de herramientas

El diseño original tenía más de 10 herramientas: get_stock_price, get_company_metrics, get_market_cap, get_pe_ratio, get_volume, entre otras. Cada una era un wrapper fino sobre un endpoint de API. El agente tenía que razonar sobre qué combinación debía invocar para cada solicitud.

Consolidé la superficie de datos de mercado en 5 herramientas de alto nivel, siguiendo el principio ACI de acciones compactas y eficientes. La lista de herramientas ReAct del repo incluye otras cuatro: un cargador de skills, dos wrappers de CLI y un evaluador de Python restringido en el mismo proceso (una allowlist de AST, no un sandbox; la Parte 4 lo aborda), que cubren tres de las cinco modalidades anteriores. MCP aparece como sidecar, no como una herramienta de esta lista:

Esto redujo la sobrecarga del esquema de herramientas y, en mis propias pruebas, hizo que la selección de herramientas fuera más fiable, porque hay menos opciones ambiguas entre las que elegir.

Salidas estructuradas para los resultados de las herramientas

Todas las herramientas del Market Analyst Agent devuelven una respuesta validada mediante Pydantic. Esto aplica el principio de validación ACI a la salida de la herramienta:

class StockSnapshot(BaseModel):
    """Structured tool response — the agent never sees raw API noise."""
    ticker: str
    price: float
    change_pct: float
    volume: int
    market_cap_b: float
    pe_ratio: float | None
    summary: str  # Human-readable one-liner for direct use in reports

class NewsResult(BaseModel):
    """Each news item is pre-processed for agent consumption."""
    headline: str
    source: str
    date: str
    relevance_score: float  # Pre-ranked so the agent doesn't waste tokens sorting
    key_points: list[str]  # Extracted by the tool, not the agent

El campo summary es el más importante. Proporciona al agente una cadena lista para usar que puede incorporarse directamente a un informe sin procesamiento adicional. Los key_points de NewsResult los extrae la herramienta en lugar del agente, lo que evita que este tenga que dedicar tokens de inferencia a analizar los cuerpos de los artículos.

Compensaciones y consideraciones

Además de las salvedades específicas de cada patrón anterior, varios aspectos transversales influyen en la elección:

  • El coste operativo varía según la dimensión. La ejecución de código ahorra tokens, pero añade latencia de arranque en frío del sandbox. MCP ahorra tiempo de desarrollo en integraciones SaaS, pero añade sobrecarga de despliegue del servidor. La CLI es gratuita para empezar, pero resulta más difícil de gobernar a escala. Optimiza según tu cuello de botella real, ya sea el coste de tokens, la latencia o la complejidad operativa.

  • Las capacidades del equipo importan. La ejecución de código presupone que tus agentes (y los modelos en los que se basan) pueden generar Python o TypeScript fiable. La CLI presupone familiaridad con las convenciones de Unix. MCP requiere comprender los protocolos de transporte y los flujos de OAuth. Adapta la modalidad a los puntos fuertes de tu equipo.

  • La consolidación de herramientas puede llevarse demasiado lejos. Si una herramienta acumula modos y argumentos no relacionados, el agente se enfrenta a un problema de selección diferente dentro del esquema. Utiliza evaluaciones de selección de herramientas y de éxito de las tareas para encontrar la superficie adecuada para tu carga de trabajo.

  • Las skills se basan en prompts, no están impuestas. Una skill contiene instrucciones que el agente debería seguir, no guardrails que deba seguir. En flujos de trabajo críticos, combina las skills con validación determinista.

  • Los requisitos de auditoría condicionan la elección. Si necesitas un registro completo de cada invocación de herramienta y su resultado, MCP y las llamadas de herramientas mediante JSON proporcionan trazas de auditoría estructuradas de forma nativa. La ejecución de código produce un script y su salida, lo que resulta útil, pero dificulta descomponer las acciones individuales para los informes de cumplimiento.

Tres direcciones para las herramientas de agentes de IA a escala

La primera es el tool RAG para escalar. A medida que los conjuntos de herramientas crecen hasta cientos o miles, la precisión de la selección ingenua de herramientas cae hasta el 13,62 %. El artículo sobre RAG-MCP aplicó retrieval-augmented generation a la selección de herramientas: indexar las descripciones de las herramientas en una base de datos vectorial y recuperar solo las relevantes para cada consulta. Con ello se alcanzó una precisión del 43,13 %, una mejora de 3,2 veces, al tiempo que se redujeron los tokens del prompt aproximadamente un 50 %.

La segunda es que los agentes creen sus propias herramientas. El framework LATM («LLMs As Tool Makers») estableció un paradigma en dos fases en el que un LLM potente crea funciones Python reutilizables y un LLM ligero las utiliza. ToolMaker (ACL 2025) transforma de forma autónoma repositorios de GitHub en herramientas compatibles con LLM, con una tasa de éxito del 80 %. Ambos trabajos apuntan más allá del uso de herramientas: primero hacia la creación de herramientas y, después, hacia la gestión de una biblioteca de herramientas generadas.

La tercera es el stack de doble protocolo A2A + MCP. El Agent2Agent Protocol (A2A), creado por Google y donado a la Linux Foundation en junio de 2025, aborda lo que MCP no puede: la comunicación entre agentes. MCP gestiona la integración entre agentes y herramientas; A2A gestiona el descubrimiento, la negociación y la delegación de tareas entre agentes.

Conclusiones clave

  1. Elige la interfaz en función de la acción: llamadas JSON para operaciones tipadas pequeñas, MCP para servicios compartidos, Skills para procedimientos, CLI para comandos consolidados y código en un sandbox para composición local.
  2. Mantén las condiciones del benchmark asociadas al resultado. CodeAct, Anthropic, Vercel, Cloudflare, Apideck y Scalekit midieron modelos, tareas, herramientas y harnesses diferentes.
  3. La calidad de la ACI se mantiene aunque cambie el protocolo. Acciones claras, feedback compacto, validación y errores útiles ayudan a todas las modalidades.
  4. Consolida herramientas solapadas solo cuando las evaluaciones demuestren que una superficie más pequeña mejora la selección o el éxito de las tareas.
  5. La seguridad debe avanzar al mismo ritmo que la capacidad de ejecución. Las interfaces de shell y código necesitan sandboxing; MCP necesita una identidad con permisos acotados y una política de servidor; las Skills siguen siendo instrucciones, no mecanismos de enforcement.

La siguiente capa es la política

La Parte 4, Seguridad de los agentes de IA, introduce una comprobación de políticas entre la llamada a una herramienta propuesta y su ejecución. Es el mismo límite de la herramienta descrito anteriormente, visto desde el lado que dice que no. La Parte 5 sitúa después la herramienta y su sandbox dentro de un runtime recuperable, y la Parte 6 añade un segundo contrato que el modelo nunca ve: una categoría de efectos, una regla de reintento y un resultado estructurado que una comprobación de aceptación puede leer sin analizar prosa.
