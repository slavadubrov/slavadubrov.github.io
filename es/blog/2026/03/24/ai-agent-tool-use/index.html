Uso de herramientas en AI Agents: MCP, CLI, Skills y ejecución de código

Este artículo está dirigido a ingenieros que desarrollan agentes que utilizan herramientas. Compara JSON tool calling, MCP, comandos CLI y código en sandbox para ayudarte a elegir un mecanismo de ejecución para tu carga de trabajo y utilizar Skills para guiarlo.

Las Skills proporcionan instrucciones para elegir y utilizar herramientas. El harness es el programa convencional que rodea al modelo: construye prompts, comprueba una llamada propuesta, ejecuta una llamada aprobada y decide cuándo ha terminado la tarea.

Este tercer artículo de la serie añade la capa de acciones a los bucles de razonamiento de la Parte 1 y la memoria de la Parte 2. La Parte 4 examina la comprobación de políticas previa a la ejecución, y la Parte 6 analiza el harness que ejecuta tanto la llamada como dicha comprobación.

El panorama de las herramientas cambió en 2025–2026. MCP, el Model Context Protocol, proporcionó a los proveedores una forma común de exponer servicios externos. Los agentes capaces de ejecutar código demostraron que, en ocasiones, un modelo puede componer un pequeño programa de forma más eficiente que emitir una larga secuencia de llamadas JSON. Anthropic informó de una reducción del 98,7 % de tokens en un workflow de Google Drive a Salesforce, y el artículo de CodeAct informó de mejoras de hasta 20 puntos porcentuales en el éxito de las tareas en su configuración de benchmark. Estos resultados describen sus tareas y harnesses, no una ventaja universal de la ejecución de código.

Una sección posterior aplica los principios de diseño de Agent-Computer Interface (ACI) al Market Analyst Agent, un pequeño agente de investigación basado en LangGraph que desarrollé para la Parte 1 y que obtiene datos de mercado y redacta un informe de análisis.

Para una decisión rápida sobre la interfaz, consulta AI Agent Tool Interfaces.

En resumen: utiliza JSON tool calls para acciones pequeñas y tipadas, MCP para integraciones compartidas, comandos CLI para operaciones locales ya establecidas y código en sandbox para trabajo de varios pasos. Las Skills proporcionan instrucciones reutilizables para utilizar cualquiera de ellos. Antes de ejecutar una llamada, el harness debe comprobar sus argumentos y aprobar su efecto; un schema o un transporte no hacen esto por sí solos. En todas las superficies, la Agent-Computer Interface (ACI) debe hacer que las acciones sean claras, el feedback compacto y los errores recuperables.

Superficies de ejecución y guía procedimental

El bucle de razonamiento propone una llamada. El harness comprueba sus argumentos y si la llamada está permitida; después la envía a una herramienta o sandbox y devuelve el resultado. Los JSON schemas, el transporte MCP, los wrappers CLI y los code runners pueden restringir las entradas, pero ninguno decide si la acción solicitada está permitida. Las Skills proporcionan instrucciones para ese proceso. Estas superficies de ejecución intercambian de forma distinta coste en tokens, flexibilidad y enforcement.

1. JSON tool calling: el punto de partida

El patrón original: defines los tool schemas como JSON, el LLM emite function calls estructuradas y tu código las ejecuta. Es un enfoque conocido y funciona bien con conjuntos pequeños de herramientas.

# Schema cost depends on its text, structure, and the model tokenizer
tools = [
    {
        "name": "get_stock_price",
        "description": "Get the current stock price for a ticker symbol",
        "input_schema": {
            "type": "object",
            "properties": {
                "ticker": {"type": "string", "description": "Stock ticker (e.g., NVDA)"}
            },
            "required": ["ticker"]
        }
    }
]

Cuenta los tokens de tus schemas reales. El coste depende de su longitud y de cuántos cargue el host; una consulta compacta de precios y un contrato de API profundamente anidado no son unidades equivalentes. El descubrimiento diferido puede evitar cargar todo el registro.

2. MCP para integraciones compartidas

MCP es el estándar en el que han convergido la mayoría de los proveedores. Un servidor MCP es un proceso que anuncia una lista de herramientas mediante un protocolo de wire definido —stdio para un proceso local y HTTP para uno remoto—. Tu agente ejecuta un cliente MCP que se conecta, pregunta al servidor qué herramientas tiene y reenvía las llamadas del modelo, de modo que el mismo servidor funciona con cualquier cliente compatible con el protocolo. Anthropic donó el protocolo a la Linux Foundation en diciembre de 2025, dentro de la Agentic AI Foundation que cofundó con OpenAI y Block. Google, Microsoft y AWS respaldan la fundación como miembros platinum. OpenAI añadió compatibilidad con MCP en su Responses API. Según el anuncio de donación de Anthropic de diciembre de 2025, el ecosistema contaba con más de 10.000 servidores MCP públicos activos y más de 97 millones de descargas mensuales de los SDKs de Python y TypeScript.

MCP encaja con integraciones SaaS entre proveedores —Figma, Notion, Salesforce—, servicios sin equivalentes CLI y entornos que necesitan orquestación de OAuth. Su valor reside en ofrecer una capa compartida de descubrimiento y transporte. La gobernanza sigue dependiendo de los controles de autenticación, autorización, logging y despliegue del servidor.

La versión del protocolo es ahora una decisión práctica de migración. La revisión de 2026-07-28 cambia comportamientos que dan por supuestos los tutoriales antiguos:

La realidad de producción es más compleja de lo que sugieren las cifras de los titulares.

El Vulnerable MCP Project recopila informes relacionados con prompt injection, validación de entradas, autenticación y controles de red. Esta recopilación ayuda a identificar casos de prueba; sin un denominador de exposición, no puede clasificar MCP frente a shell o llamadas directas a una API.

El tool poisoning es la clase de ataque que más me preocupa. Invariant Labs demostró que unas herramientas MCP envenenadas pueden exfiltrar datos aunque nunca se invoquen. Basta con que el modelo lea los metadatos de la herramienta para activar el ataque. Los benchmarks de MCPTox, que probaron 20 agentes LLM contra 45 servidores MCP del mundo real, informaron de un 72,8 % de éxito medio de los ataques para o1-mini en su configuración de tool poisoning. Es el resultado del benchmark de un modelo, no una media de los 20 agentes ni una tasa de incidentes del mundo real.

El coste en tokens es el problema operativo. Un equipo que ejecutaba servidores MCP para GitHub, Slack y Sentry —unos 40 tools en total— encontró 55.000 tokens de definiciones de schemas inyectados antes de que el usuario solicitara nada. Otro informó de que las definiciones de herramientas por sí solas consumían 143.000 de los 200.000 tokens disponibles (72 %).

El informe de Anthropic sobre Tool Search Tool indicó unos endpoints de contexto aproximados de 77.000 tokens antes de comenzar el trabajo y de 8.700 después del descubrimiento diferido, frente a unos 72.000 tokens de definiciones de herramientas en la configuración tradicional. Solo carga las tres a cinco herramientas que necesita una petición, pero añade un paso de descubrimiento antes de la invocación; resulta menos útil para conjuntos pequeños y compactos de herramientas que se utilizan con frecuencia en todas las sesiones.

3. Las Skills empaquetan expertise, no ejecución

Las agent skills son un formato abierto para empaquetar instrucciones y archivos de soporte. Las herramientas proporcionan capacidades —lo que pueden hacer los agentes— y las skills proporcionan expertise —lo que saben los agentes sobre cómo realizar tareas complejas—.

El formato SKILL.md define una skill como un archivo Markdown con YAML frontmatter. El estándar abierto solo requiere name y description; el ejemplo siguiente también utiliza dos extensiones de Claude Code, argument-hint y user-invocable, además de su placeholder de argumento posicional $0:

---
name: deploy
description: Deploy the application to production
argument-hint: "[environment]"
user-invocable: true
---
Deploy the application to the $0 environment (default: staging).
Steps:
1. Run the test suite
2. Build the production bundle
3. Deploy using the deploy script
4. Verify the deployment health check

Las Skills utilizan progressive disclosure. Al arrancar, el agente recibe unos 100 tokens de name y description. Solo carga el SKILL.md completo cuando necesita la skill y, después, carga los scripts, documentos o assets referenciados según sea necesario. Ese coste inicial es mucho menor que los aproximadamente 55.000 tokens que unos 40 tools MCP pueden consumir antes de que comience el razonamiento. Una skill activa sigue añadiendo sus instrucciones y recursos al contexto.

Utiliza skills para conocimiento de dominio, procedimientos de varios pasos y trabajo recurrente, como migraciones de bases de datos o integraciones de pagos. Encajan en tareas en las que el agente necesita instrucciones sobre cómo usar una capacidad existente.

4. Herramientas CLI y shell

Las interfaces CLI pueden ser mucho más baratas en contexto cuando el modelo ya conoce el comando. Scalekit informó de una diferencia de entre 4 y 32 veces en tokens entre sus rutas CLI y MCP a lo largo de 75 ejecuciones. Este case study mide sus herramientas y tareas; no sustituye una comparación con tus propias definiciones de herramientas y salidas de comandos.

Los comandos ampliamente documentados, como git, docker, kubectl, gh, curl y jq, suelen necesitar poco texto introductorio de schema. Las CLI menos habituales o internas siguen necesitando ayuda descubrible, ejemplos y una salida estable legible por máquinas.

La guía de Ugo Enyioha, “Writing CLI Tools That AI Agents Actually Want to Use”, codificó ocho reglas de diseño:

  1. La salida estructurada es obligatoria — admite --json
  2. Los códigos de salida son control de flujo — utiliza códigos distintos para tipos de error diferentes
  3. Los comandos deben ser idempotentes
  4. Autodocumentación --help con ejemplos realistas
  5. Diseña pensando en la composabilidad — --quiet para valores simples y compatibilidad con stdin
  6. Proporciona flags --dry-run y --yes
  7. Admite introspección de versiones
  8. Gestiona la autenticación mediante variables de entorno

CLI no ofrece descubrimiento a nivel de protocolo. JSON tool calling puede transportar schemas tipados, mientras que MCP estandariza el descubrimiento de herramientas y, para transportes HTTP, un modelo de autorización. Ninguno proporciona gobernanza por sí mismo: el host, el servidor o el harness debe aplicar la política y registrar las llamadas necesarias para auditar. Un valor predeterminado práctico es CLI para desarrollo y operaciones locales, y MCP para integraciones compartidas con servicios externos cuando el descubrimiento entre clientes o la orquestación de OAuth justifican la sobrecarga del servidor.

5. Ejecución de código para trabajo de varios pasos

Este es el cambio en tooling de agentes que considero más importante. En lugar de emitir JSON estructurado para invocar funciones predefinidas de una en una, el agente escribe un script de Python o bash. El script llama a varias herramientas, procesa los resultados mediante bucles y condicionales, y devuelve al contexto del modelo solo el resumen final.

Anthropic presentó Programmatic Tool Calling (PTC) en beta. La guía actual de la API utiliza la Messages API habitual con code_execution_20260120 o posterior; el lanzamiento beta original pertenece al contexto histórico. La base académica es el artículo de CodeAct (Wang et al., ICML 2024), que probó 17 LLMs y descubrió que las acciones basadas en código lograban hasta 20 puntos porcentuales más de éxito en las tareas y un 30 % menos de acciones que las alternativas basadas en JSON.

Tres case studies de primera parte muestran dónde puede ayudar este patrón: Vercel y Cloudflare a continuación, y después el ejemplo de análisis de gastos de Anthropic. Trátalos como evidencia de proveedores y vuelve a ejecutar la comparación con tus propias tareas.

  • Vercel reconstruyó d0, su agente de datos de lenguaje natural a SQL. Su antiguo ejemplo de código nombra 17 herramientas; el nuevo expone ExecuteCommand y ExecuteSQL. Vercel presenta el rediseño como una eliminación del 80 % de sus herramientas, pero esa afirmación es el titular de Vercel, no un porcentaje que se deduzca de las herramientas nombradas en los ejemplos. En cinco consultas representativas, Vercel informa de que el éxito de las tareas pasó de 4/5 a 5/5, el tiempo medio de ejecución se redujo 3,5 veces —de 274,8 s a 77,4 s— y el uso medio de tokens cayó un 37 % —de unos 102.000 a unos 61.000—. En sus palabras: «Los mejores agentes quizá sean los que tienen menos herramientas».

  • Cloudflare desarrolló «Code Mode», que permite a los agentes escribir TypeScript para llamar a su API en lugar de definir tool schemas, reduciendo así la sobrecarga de contexto. Su razonamiento es el siguiente: «Los LLMs tienen una cantidad enorme de TypeScript del mundo real en su dataset de entrenamiento, pero solo un pequeño conjunto de ejemplos artificiales de tool calls».

Este es el patrón de la documentación de PTC de Anthropic. En la ilustración secuencial de análisis de gastos de Anthropic, el tool calling tradicional requiere más de 20 pasadas de inferencia separadas, con datos intermedios fluyendo por el contexto. Después de consultar al equipo, un host compatible con parallel tool calls puede agrupar las peticiones de gastos independientes; la cifra de más de 20 no lo impide. Anthropic informa de que el código generado que responde a la misma pregunta reduce lo que llega al contexto desde 200 KB de líneas de gastos sin procesar —más de 2.000 partidas— hasta 1 KB de resultados. El script siguiente ilustra ese flujo de control mediante adaptadores Python async personalizados: aceptan argumentos posicionales y devuelven listas y diccionarios decodificados. No es el contrato nativo del wrapper de PTC.

# Custom decoded Python adapters, not native Claude PTC wrappers.
import asyncio
import json

async def main() -> None:
    team = await get_team_members("engineering")
    levels = list(set(member["level"] for member in team))
    budgets = dict(zip(
        levels,
        await asyncio.gather(*(get_budget_by_level(level) for level in levels)),
    ))
    expenses = await asyncio.gather(
        *(get_expenses(member["id"], "Q3") for member in team)
    )
    over_budget = []
    for member, employee_expenses in zip(team, expenses):
        total = sum(expense["amount"] for expense in employee_expenses)
        limit = budgets[member["level"]]["travel_limit"]
        if total > limit:
            over_budget.append(
                {"name": member["name"], "spent": total, "limit": limit}
            )
    # Only this final summary returns to the LLM context
    print(json.dumps(over_budget))

asyncio.run(main())

Para utilizar los wrappers nativos de Claude PTC, pasa a cada herramienta un diccionario de argumentos, decodifica la cadena JSON que devuelve y utiliza await en el entorno de ejecución gestionado, en lugar de iniciar un event loop con asyncio.run. El ejemplo de adaptador personalizado anterior asume un runtime de script Python convencional; tampoco es un ejemplo de conector MCP nativo listo para usar. Las restricciones actuales de la API de PTC excluyen las herramientas strict: true y las herramientas de conectores MCP nativos del calling programático, y restringen los schemas recursivos. Un puente personalizado de código a MCP es una integración independiente. allowed_callers guía cómo Claude llama a una herramienta; no es un límite de autorización. El host debe validar cada invocación devuelta, incluida cualquier llamada directa inesperada.

El LLM solo ve el resumen JSON final, no las miles de líneas de gastos procesadas en el sandbox. El ahorro no es específico de los informes de gastos: el artículo independiente de Anthropic sobre code execution proporciona la cifra más llamativa del patrón, un workflow de Google Drive a Salesforce que pasó de unos 150.000 tokens a unos 2.000, una reducción del 98,7 %.

La guía actual de PTC también informa de un contraejemplo: en las tareas de aerolíneas, retail y telecomunicaciones de tau2-bench, PTC no cambió las puntuaciones y costó aproximadamente un 8 % más. En un benchmark independiente de gestión de proyectos con 75 herramientas, redujo los input tokens facturados aproximadamente un 38 % sin cambiar la precisión. Estas evaluaciones internas solo identifican un modelo Claude de producción, no un ID exacto. Los workflows secuenciales pequeños quizá no ahorren lo suficiente para compensar la sobrecarga del contenedor y la generación de código.

La eficiencia en tokens es una ganancia potencial. Los bucles y condicionales salen gratis, y la ejecución de código puede gestionar errores mediante handlers explícitos en lugar de obligar al modelo a razonar sobre los fallos en lenguaje natural. Una ruta de ejecución de código puede mantener datos intermedios sensibles fuera del contexto del modelo, pero eso no equivale a confidencialidad: el aislamiento, los controles de egress, las credenciales con scope y el logging necesitan enforcement independiente.

Cuándo sigue teniendo sentido JSON tool calling: operaciones atómicas individuales, entornos sin infraestructura de sandbox, modelos pequeños con una generación de código débil o requisitos de auditoría que necesiten registrar cada invocación individual de una herramienta.

JSON tool calling, MCP, CLI y la ejecución de código son superficies de ejecución. Las Skills son instrucciones que guían una de esas superficies, por lo que su latencia, contexto y configuración dependen del mecanismo seleccionado. «Meta-tools» significa los pocos entry points genéricos que necesita un agente que ejecuta código —por ejemplo, ExecuteCommand y ExecuteSQL de Vercel— en lugar de un schema para cada operación. Las filas de composabilidad y latencia describen llamadas cuyos argumentos posteriores dependen de resultados anteriores. JSON tool calling y MCP pueden emitir llamadas independientes conjuntamente, pero las llamadas dependientes suelen necesitar otro turno del modelo. PTC traslada ese flujo de control y filtrado dependientes a un script, que después devuelve un resumen al modelo. Las celdas de tokens y éxito de las tareas resumen ejemplos citados, no un benchmark controlado único entre las cinco columnas.

La Agent-Computer Interface (ACI) para herramientas de AI agents

El término «Agent-Computer Interface» (ACI) fue acuñado por John Yang, Carlos E. Jimenez y sus colaboradores de Princeton en su artículo sobre SWE-agent (NeurIPS 2024). La calidad de las interfaces humanas cuenta con toda una disciplina dedicada a ella —human-computer interaction, o HCI—. El artículo sostiene que los agentes basados en language models merecen el mismo tratamiento: son «una nueva categoría de usuarios finales con sus propias necesidades y capacidades, y se beneficiarían de interfaces creadas específicamente para ellos».

Sus resultados de ablación cuantificaron ese efecto. Utilizando el mismo modelo base GPT-4 Turbo, la ablación de SWE-bench Lite del artículo alcanzó el 18,0 % con la ACI completa de SWE-agent en 300 tareas, frente al 7,3 % de la condición solo shell sin una demostración guiada y al 11,0 % con una. La comparación muestra que la interfaz y las condiciones de demostración cambiaron materialmente el rendimiento en esta configuración; no aísla el diseño de la interfaz de cualquier otra diferencia ni demuestra que el modelo no realizara trabajo. Dentro de la misma ablación de interfaz, activar el linting elevó la condición de edición del 15,0 % al 18,0 %; en el conjunto completo de pruebas de SWE-bench, el 51,7 % de las ejecuciones de SWE-agent encontró al menos una edición que el linter rechazó antes de que pudiera propagarse.

El diagrama muestra la validación del resultado después de que una herramienta devuelva feedback. La validación de argumentos es una comprobación independiente previa a la ejecución de la herramienta; un resultado no válido vuelve al agente para que lo corrija antes de que otra acción lo utilice.

Anthropic adoptó ACI como concepto fundamental en su guía “Building Effective Agents”, donde lo enumera como uno de los tres principios básicos: «Diseña cuidadosamente tu interfaz agente-ordenador mediante una documentación y unas pruebas exhaustivas de las herramientas». Su recomendación práctica es: «Una regla general es pensar en cuánto esfuerzo se dedica a las interfaces persona-ordenador y planificar invertir el mismo esfuerzo en crear buenas interfaces agente-ordenador».

Cuatro principios de ACI en la práctica

1. Las acciones deben ser simples y fáciles de entender. El error más común consiste en envolver endpoints de API uno a uno. En lugar de list_users, list_events y create_event, implementa schedule_event, que encuentre la disponibilidad y programe la cita en una sola llamada. En lugar de read_logs, implementa search_logs, que devuelva solo las líneas relevantes con contexto.

2. Las acciones deben ser compactas y eficientes. Consolida las operaciones importantes en el menor número posible de acciones. En el Market Analyst Agent, combino la obtención de precios con métricas básicas en una única herramienta get_stock_snapshot, en lugar de exigir llamadas separadas para el precio, el volumen, la capitalización de mercado y el ratio PE.

3. El feedback del entorno debe ser informativo, pero conciso. Evita devolver HTML sin procesar o payloads completos de la API. Resuelve los IDs crípticos en nombres semánticos. Las pruebas de Anthropic añadieron un enum response_format para que el agente pueda solicitar una respuesta concisa —unos 72 tokens— o detallada —unos 206 tokens—, aproximadamente una diferencia de 3x en el coste de tokens.

4. La validación debe mitigar la propagación de errores. La detección automática de errores ayuda a los agentes a reconocer y corregir los fallos rápidamente. En SWE-agent, un editor de archivos personalizado con linting integrado rechaza automáticamente los errores de sintaxis: es el paso de validación que subyace a la cifra del 51,7 % anterior. Esta es la validación de las entradas y salidas de una herramienta, no el filtrado de contenido alrededor de una llamada al modelo que realizan los productos de guardrails de la Parte 4; la misma palabra se utiliza para ambas cosas. Aplico el mismo principio en el Market Analyst Agent validando los argumentos de las herramientas con schemas de Pydantic antes de la ejecución:

from pydantic import BaseModel, Field, field_validator

from market_analyst.utils import normalize_ticker

class StockQuery(BaseModel):
    """Validated input for stock queries.

    Pydantic catches malformed tickers before the API call,
    preventing error propagation through the reasoning loop.
    """
    ticker: str = Field(description="Stock ticker symbol (e.g., NVDA)")

    @field_validator("ticker")
    @classmethod
    def validate_ticker(cls, v: str) -> str:
        return normalize_ticker(v)

class StockHistoryQuery(StockQuery):
    """Validated input for price history queries."""

    period: str = Field(default="1mo", description="Time period: 1d, 5d, 1mo, 3mo, 6mo, 1y")

    @field_validator("period")
    @classmethod
    def validate_period(cls, v: str) -> str:
        valid = {"1d", "5d", "1mo", "3mo", "6mo", "1y"}
        if v not in valid:
            raise ValueError(f"Invalid period: {v}. Must be one of {valid}")
        return v

El normalizador compartido elimina espacios y convierte el valor a mayúsculas; después acepta dígitos de ticker y sufijos con puntos o guiones, como BRK.B y BF-B; StockHistoryQuery, no StockQuery, es quien posee period.

Patrones de diseño de herramientas para AI agents que funcionan

La guía de Anthropic “Writing effective tools for agents” define las herramientas como «un nuevo tipo de software que refleja un contrato entre sistemas deterministas y agentes no deterministas».

Trata las descripciones de las herramientas como prompt engineering

Las descripciones deberían tener al menos tres o cuatro frases y cubrir cuándo utilizar la herramienta, los parámetros obligatorios frente a los opcionales, el formato de salida y los casos límite. Anthropic informa de que la elección entre nombres con namespacing basado en prefijos o sufijos (asana_search frente a search_asana) tuvo «efectos no triviales» en sus propias evaluaciones de tool use. No indica qué esquema gana, así que prueba ambos con tu conjunto de herramientas en lugar de asumir que los prefijos son mejores. Anthropic también introdujo en Claude Code las transcripciones de sus agentes de evaluación y permitió que reescribiera las herramientas. En conjuntos de pruebas reservados, ese bucle encontró mejoras adicionales «incluso por encima de lo que conseguimos con implementaciones de herramientas “expertas”», tanto si dichas herramientas habían sido escritas manualmente por sus investigadores como si las había generado Claude.

# Bad: vague, no context for when to use
tools = [{
    "name": "search",
    "description": "Search for items",
}]

# Good: specific, with input examples and edge cases
tools = [{
    "name": "search_news",
    "description": (
        "Search for recent news articles about a specific stock or company. "
        "Use this tool when the user asks about recent events, earnings, "
        "announcements, or market-moving news for a specific ticker. "
        "Returns up to 10 articles sorted by relevance. "
        "For company competitors rather than news, use search_competitors instead."
    ),
    "input_schema": {
        "type": "object",
        "properties": {
            "query": {
                "type": "string",
                "description": "Search query. Examples: 'NVDA earnings Q3 2025', 'Tesla delivery numbers'"
            },
            "max_results": {
                "type": "integer",
                "description": "Max articles to return (1-10, default 5)",
                "default": 5
            }
        },
        "required": ["query"]
    }
}]

Las pruebas internas de Anthropic mostraron que añadir un campo input_examples elevó la precisión en la gestión de parámetros complejos del 72 % al 90 %.

Devuelve una salida de alta señal y legible por máquinas

Utiliza etiquetas semánticas en lugar de identificadores de bajo nivel (uuid, mime_type) en la respuesta predeterminada. Conserva un ID cuando otra herramienta lo necesite más adelante u ofrece una respuesta detallada que lo incluya. Por ejemplo, un resultado de búsqueda para Jane puede ser conciso de leer, mientras que un resultado detallado incluye el ID que necesita send_message. Estructura la respuesta para que el agente pueda razonar sobre ella sin analizar boilerplate:

# Bad: raw API response dumped to agent
def get_stock_snapshot(ticker: str) -> dict:
    response = api.get(f"/v1/quotes/{ticker}")
    return response.json()  # 500+ tokens of nested JSON

# Good: high-signal summary the agent can immediately reason about
def get_stock_snapshot(ticker: str) -> dict:
    data = api.get(f"/v1/quotes/{ticker}").json()
    return {
        "ticker": ticker,
        "price": data["regularMarketPrice"],
        "change_pct": round(data["regularMarketChangePercent"], 2),
        "volume": data["regularMarketVolume"],
        "market_cap_b": round(data["marketCap"] / 1e9, 1),
        "pe_ratio": data.get("trailingPE"),
        "summary": f"{ticker} at ${data['regularMarketPrice']:.2f} "
                   f"({'up' if data['regularMarketChangePercent'] > 0 else 'down'} "
                   f"{abs(data['regularMarketChangePercent']):.1f}%)"
    }

Devuelve errores que el bucle pueda gestionar

La gestión de errores necesita cuatro mecanismos independientes, porque cada uno aborda una clase de fallos distinta:

  1. Reintentos con exponential backoff para errores transitorios
  2. Cadenas de fallback de modelos para caídas del proveedor
  3. Enrutamiento por clasificación de errores: los errores transitorios se reintentan, los errores recuperables por el LLM se devuelven al agente con contexto y los errores que requieren intervención humana se escalan
  4. Recuperación desde checkpoint para sobrevivir a crashes

La guía de Anthropic “Writing effective tools for agents” defiende errores de herramientas claros y un diseño de herramientas guiado por evaluaciones, pero no proporciona una cifra universal sobre lo que recuperan estos cuatro mecanismos. Mide la tasa de recuperación, los reintentos y las escalaciones en tu propia suite de tareas.

import httpx
from tenacity import retry, retry_if_exception, stop_after_attempt, wait_exponential

def is_transient_error(error: BaseException) -> bool:
    if isinstance(error, (httpx.TimeoutException, httpx.NetworkError)):
        return True
    if isinstance(error, httpx.HTTPStatusError):
        return error.response.status_code == 429 or 500 <= error.response.status_code < 600
    return False

@retry(
    retry=retry_if_exception(is_transient_error),
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=1, min=2, max=10),
    reraise=True,
)
def call_stock_api(ticker: str) -> dict:
    """Fetch stock data with automatic retry on transient failures.

    Mechanism 1 of the four above: exponential backoff for rate limits
    and network blips.
    This only retries transient transport failures. If attempts are exhausted,
    Tenacity re-raises the original httpx exception.
    """
    response = httpx.get(
        f"https://api.example.com/v1/quotes/{ticker}",
        timeout=10.0,
    )
    response.raise_for_status()
    return response.json()

El caller o harness sigue necesitando el paso siguiente: convertir esa excepción en un resultado estable que indique qué operación ha fallado, si debe reintentarse y qué hacer después. Un 4xx que no sea reintentable se salta este decorador y necesita el mismo tratamiento. Reintentar una petición no clasifica su error ni recupera un checkpoint.

Consolidación de herramientas

Los módulos de herramientas originales definían get_stock_price, get_company_metrics, get_price_history, dos herramientas de búsqueda y execute_trade. Para un análisis básico, el agente tenía que elegir tanto la llamada de precio como la de métricas; la capitalización de mercado y el P/E eran campos de get_company_metrics, no herramientas independientes. La lista de herramientas ReAct del repositorio incluye otras cuatro: un cargador de skills, dos wrappers CLI y un evaluador Python restringido en proceso —una allowlist de AST, no un sandbox; la Parte 4 lo aborda—, que cubren tres de las cinco modalidades anteriores. Salidas estructuradas para resultados de herramientas

Las herramientas de acciones y noticias devuelven respuestas validadas por Pydantic. Los wrappers de CLI y de ejecución de código devuelven str, por lo que los modelos siguientes describen los resultados estructurados de las herramientas, no todos los wrappers del repositorio:

from pydantic import BaseModel

class StockSnapshot(BaseModel):
    """Structured tool response — the agent never sees raw API noise."""
    ticker: str
    price: float
    change_pct: float
    volume: int
    market_cap_b: float
    pe_ratio: float | None
    summary: str  # Human-readable one-liner for direct use in reports

class NewsItem(BaseModel):
    """One news item pre-processed for agent consumption."""
    headline: str
    source: str
    date: str
    relevance_score: float  # Pre-ranked so the agent doesn't waste tokens sorting
    key_points: list[str]  # Extracted by the tool, not the agent

class NewsSearchResult(BaseModel):
    query: str
    results: list[NewsItem]
    summary: str

El campo summary proporciona al agente una cadena lista para utilizar en un informe. NewsItem.key_points evita que el modelo tenga que analizar los cuerpos de los artículos. Si una acción posterior necesita un ID, consérvalo en la respuesta detallada u ofrece modos conciso y detallado; no lo elimines en todas partes.

Trade-offs y consideraciones

Más allá de las salvedades específicas de cada patrón anterior, varias consideraciones transversales condicionan la elección:

  • El coste operativo varía según la dimensión. La ejecución de código puede ahorrar tokens de contexto del modelo al filtrar resultados intermedios, pero la generación de código y la sobrecarga del contenedor pueden superar esos ahorros y añadir latencia. MCP ahorra tiempo de desarrollo en integraciones SaaS, pero añade sobrecarga de despliegue del servidor. CLI es gratis para empezar, pero más difícil de gobernar a escala. Optimiza para tu cuello de botella real, ya sea el coste de tokens, la latencia o la complejidad operativa.

  • Las capacidades del equipo importan. La ejecución de código presupone que tus agentes —y los modelos que los respaldan— pueden generar Python o TypeScript fiable. CLI presupone familiaridad con las convenciones de Unix. MCP requiere comprender los protocolos de transporte y los flujos OAuth. Adapta la modalidad a los puntos fuertes de tu equipo.

  • La consolidación de herramientas puede llevarse demasiado lejos. Si una herramienta acumula modos y argumentos sin relación, el agente se enfrenta a un problema de selección diferente dentro del schema. Utiliza evaluaciones de selección de herramientas y éxito de tareas para encontrar la superficie adecuada para tu carga de trabajo.

  • Las Skills se basan en prompts, no están enforced. Una skill contiene instrucciones que el agente debería seguir, no guardrails que deba seguir. Un bundle de skills puede incluir archivos arbitrarios y scripts ejecutables, así que confía en su origen, revisa el bundle y haz que el host aplique los permisos sobre cada recurso que pueda leer, modificar o ejecutar. En workflows críticos, combina skills con validación determinista.

  • Los requisitos de auditoría condicionan la elección. Las llamadas MCP y JSON estructuradas son eventos cómodos de registrar, pero ninguno de los dos protocolos crea de serie un audit trail completo. El host, el servidor o el harness debe registrar invocaciones y resultados, y después aplicar autorización, política, retención y revisión. La ejecución de código necesita la misma instrumentación alrededor del sandbox; su script y su salida por sí solos no constituyen un registro de compliance.

Tres direcciones para el tooling de AI agents a escala

La primera es el tool RAG para escalar. Antes de que el modelo elija una herramienta, recupera las pocas descripciones que coincidan con la petición y deja que elija dentro de ese subconjunto en lugar de hacerlo sobre todo el registro. En las tareas de benchmark y el stress test de MCP de RAG-MCP, la precisión baseline de selección de herramientas fue del 13,62 %; la recuperación la elevó al 43,13 %, una mejora de 3,2x, y redujo los tokens del prompt de 2.133,84 a 1.084 —aproximadamente un 49,2 %—. El abstract del artículo dice «más del 50 %», y las descripciones del generador y del evaluador difieren entre secciones; estas inconsistencias limitan la interpretación. El resultado es evidencia para esa configuración de evaluación, no una tasa universal de selección ingenua a medida que crecen los toolsets.

La segunda son los agentes que crean sus propias herramientas. El framework LATM («LLMs As Tool Makers») estableció un paradigma en dos fases en el que un LLM potente crea funciones Python reutilizables y un LLM ligero las utiliza. En el benchmark de 15 tareas de ToolMaker, compuesto por artículos con repositorios de código públicos proporcionados como URLs de GitHub y descripciones breves de las tareas, implementó correctamente 12 de 15 tareas; el benchmark contiene más de 100 tests en total. Ese pequeño benchmark de tareas sobre repositorios no establece una fiabilidad de producción. Ambos enfoques apuntan más allá del uso de herramientas, hacia la creación de herramientas y, después, hacia la gestión de una librería de herramientas generadas.

La tercera es el stack de dos protocolos A2A + MCP. Google transfirió A2A a la Linux Foundation en junio de 2025. La documentación del protocolo A2A separa sus responsabilidades: MCP conecta un agente con herramientas y recursos, mientras que A2A permite que agentes independientes se descubran entre sí, negocien interacciones, gestionen tareas compartidas y deleguen trabajo.

Compara las interfaces con tareas idénticas y operaciones permitidas idénticas. Registra los tokens de descubrimiento, la entrada con y sin caché, la salida de ejecución, los reintentos, la latencia y el éxito del estado final. Prueba tanto los fallos de descubrimiento como el ahorro de tokens; en programas generados, contabiliza los errores de sintaxis, los errores de runtime y la finalización parcial.

Conclusiones clave

  1. Elige la superficie de ejecución a partir de la acción: llamadas JSON para operaciones pequeñas y tipadas, MCP para servicios compartidos, CLI para comandos establecidos y código en sandbox para composición local. Utiliza Skills para documentar cómo elegir y usar esa superficie.
  2. Mantén las condiciones del benchmark asociadas al resultado. CodeAct, Anthropic, Vercel, Cloudflare, Apideck y Scalekit midieron modelos, tareas, herramientas y harnesses distintos.
  3. La calidad de la ACI sigue siendo importante aunque cambie el protocolo. Las acciones claras, el feedback compacto, la validación y los errores útiles ayudan a todas las modalidades.
  4. Consolida herramientas que se solapen solo cuando las evaluaciones demuestren que una superficie más pequeña mejora la selección o el éxito de las tareas.
  5. La seguridad se desplaza con la potencia de ejecución. Las interfaces de shell y código necesitan sandboxing; MCP necesita una identidad con scope y una política de servidor; las Skills siguen siendo instrucciones, no enforcement.
