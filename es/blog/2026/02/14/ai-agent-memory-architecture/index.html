Arquitectura de memoria para AI Agent en 2026: checkpoints, vector stores y memoria basada en ficheros

Parte 2 de la serie Engineering the Agentic Stack

Un reasoning loop solo sobrevive a una única request si no se guarda su estado fuera del worker. Sin agent memory, el agente no puede reanudar un plan pausado, recuperarse tras un crash, ni recordar una preferencia de una sesión anterior. Part 1 cubrió el flujo de control. Este post identifica qué estado necesita cada turno posterior y dónde debe vivir.

Voy a recorrer la arquitectura de memoria del Market Analyst Agent, mostrando cómo los checkpoints “hot”, los vector stores “cold” y la memoria documental basada en ficheros trabajan juntos para agents de larga duración. Después cubriré cuándo tiene sentido PostgreSQL, Redis, Qdrant, los key-value stores y ficheros Markdown “puros”.

TL;DR: Separa la memoria por patrón de acceso. Hot memory es el estado de checkpoint a nivel de hilo para pause y resume. Cold memory guarda hechos entre sesiones en un key-value o en un vector store. Document memory mantiene el conocimiento del proyecto en ficheros inspeccionables. Empieza por el fallo que necesitas corregir y luego elige el store. No pongas hechos exactos en un sistema de recuperación “fuzzy” ni trates un checkpoint como si fuera un audit log.

¿Qué es la AI agent memory?

La AI agent memory es la capa de estado que permite a un agente conservar el progreso de la tarea, recuperar conocimiento previo y actualizar lo que “sabe” a través de ejecuciones. En producción no es una sola base de datos vectorial. Es una mezcla de checkpoints hot, stores semánticos o estructurados cold y memoria documental legible para humanos.

No empieces por memoria porque suena “inteligente”. Empieza por el fallo visible para el usuario: perder progreso, olvidar una preferencia, repetir investigación o no reutilizar una convención del proyecto.

Los fallos que requieren memoria

Un agent stateless puede responder una pregunta aislada, pero olvida la request en cuanto termina la llamada. Ese diseño falla cuando el producto necesita cualquiera de los siguientes comportamientos:

  • Pausar y reanudar: un usuario inicia una tarea de investigación, cierra su portátil y vuelve mañana. Sin estado con checkpoint, el agente reinicia desde cero.
  • Coherencia multi-turn: en una conversación larga, el agente tiene que recordar qué herramientas llamó, qué datos recopiló y qué pasos del plan completó.
  • Personalización: un usuario recurrente espera que el agente conozca su tolerancia al riesgo, la profundidad de análisis preferida y sus interacciones pasadas.
  • Human-in-the-loop (HITL): el agente redacta un informe y espera aprobación. El estado de “esperar” tiene que sobrevivir a reinicios del proceso.

En el Market Analyst Agent de Part 1, la request “Analyze NVDA” produce un plan, cinco tool calls, datos recopilados y un borrador de informe. Cuando el usuario responde “looks good, but add competitor analysis”, un checkpoint store permite al agente cargar el estado desde el último nodo y añadir el paso del competidor. Sin estado con checkpoint, no puede resolver a qué se refiere “looks good” y tiene que empezar de nuevo.

La memoria a largo plazo gestiona un caso distinto. Si el usuario vuelve una semana más tarde y pregunta “Update my NVDA analysis”, el agente puede necesitar recordar una preferencia para evaluaciones de riesgo conservadoras y un interés en acciones del sector de semiconductores. Un vector-backed memory store puede recuperar esos hechos entre sesiones sin pedirlos otra vez.

LangGraph lo separa por alcance. Cada ejecución del grafo corre dentro de un thread, es decir, una conversación o tarea. El estado persistido dentro de ese thread es short-term memory. El estado compartido entre threads es long-term memory. El contexto actual del modelo y las variables en proceso forman la capa de working memory por encima de ambos stores.

Taxonomía de la AI agent memory

Antes de entrar en implementación, ayuda clasificar qué necesita recordar el agente. El framework CoALA (Sumers, Yao et al., 2023) es una taxonomía citada ampliamente y se apoya en ciencia cognitiva. Presenté el scoping de memoria en mi post sobre context engineering; aquí lo amplío a seis categorías:

Working memory es con lo que el LLM está razonando activamente ahora mismo: variables Python en la función actual, contenidos de la ventana de contexto, argumentos de tool calls a mitad de ejecución. Es la capa más rápida y efímera. Nada persiste más allá del paso actual. La working memory está acotada por la context window del modelo, lo que la convierte en el cuello de botella. Todo lo que el agente “sabe” en el momento de la decisión tiene que encajar aquí, ya venga del checkpoint store, de una consulta vectorial o de una lectura de fichero. Las otras capas existen para alimentar en el momento adecuado la información correcta a la working memory.

Short-term memory es el checkpoint que LangGraph escribe después de cada nodo. Episodic y semantic persisten entre threads. Document memory guarda notas del proyecto, resúmenes de investigación y convenciones aprendidas en ficheros que humanos y agentes pueden inspeccionar. Procedural memory vive en instrucciones del system y definiciones de tools, en lugar de cambiar para cada usuario.

Para implementación, estas categorías se reducen a tres tiers. Hot memory guarda la sesión actual. Cold memory soporta el recall entre sesiones. Document memory mantiene el conocimiento acumulado del proyecto de forma legible y editable directamente.

CoALA clasifica working, episodic, semantic y procedural memory. El Memory in the Age of AI Agents survey enfatiza vector stores y knowledge graphs, mientras que LangGraph documenta checkpoints y su interfaz Store. El conocimiento de proyecto respaldado por ficheros queda fuera de esas taxonomías, aunque Claude Code, Cursor, Windsurf y Devin cargan ficheros de proyecto persistentes.

El mismo patrón de almacenamiento aparece en otros dominios. Voyager guarda habilidades reutilizables de juego como librerías de código, equipos ERC3 iteraron con documentos de prompt procedurales y Agent Workflow Memory induce workflows web reutilizables a partir de episodios exitosos. Los ficheros hacen que ese conocimiento sea inspeccionable y versionable sin un servicio de embedding separado.

La memoria gestionada por el agente también difiere de un pipeline RAG fijo en quién realiza la escritura. El agente (o su harness) selecciona qué almacenar, qué actualizar y qué borrar; después, más tarde, decide cuándo recuperarlo.

El Generative Agents paper (Park et al., 2023) mostró hasta dónde puede llegar: agentes simulados guardaban, reflexionaban y recuperaban sus propias memorias. Su memory stream rankeaba candidatos por recencia, importancia y relevancia; una idea que aún sirve como punto de referencia útil para recuperación de agent-memory.

Short-term agent memory: el checkpoint store

Cada vez que se ejecuta un nodo de LangGraph, el framework serializa el estado completo del grafo y lo escribe en un checkpoint store. Esa es la base para pause/resume, debugging con time-travel y flujos HITL.

Un checkpoint contiene el estado del grafo necesario para reanudar: el AgentState de Part 1 (messages, identity, user profile, plan steps, research data, execution mode), además de metadatos de LangGraph como el nodo que lo produjo y su checkpoint ID. Tras una interrupción HITL o un restart del proceso, el grafo carga el último “boundary” registrado y entra en el siguiente nodo. No continúa desde una línea arbitraria de Python. Un checkpoint también es distinto de un append-only event log o trace; Part 5 separa explícitamente esas superficies de observabilidad del runtime.

Cómo funciona el checkpointing en LangGraph

El BaseCheckpointSaver de LangGraph es una interfaz simple: put() escribe un checkpoint, get_tuple() lee el último para un thread, list() devuelve el historial. Cada checkpoint está indexado por (thread_id, checkpoint_ns, checkpoint_id), donde thread_id identifica la conversación, checkpoint_ns maneja el namespacing de subgráfos y checkpoint_id es una versión única.

La decisión relevante es qué backend poner detrás. PostgreSQL y Redis son dos opciones habituales en producción.

Los benchmarks genéricos de bases de datos no predicen el rendimiento de checkpoints. Mide el tamaño serializado del estado, la frecuencia de escritura, los parámetros de persistencia y la concurrencia de tu propio grafo.

PostgreSQL: el default durable

PostgreSQL es el default más seguro para la mayoría de equipos. Los checkpoints sobreviven a crashes, obtienes semántica transaccional completa y el historial del checkpoint hace el debugging con time-travel más directo.

Desde checkpointer_setup.py:

from langgraph.checkpoint.postgres.aio import AsyncPostgresSaver

async def create_postgres_checkpointer(connection_string: str) -> AsyncPostgresSaver:
    """Create a PostgreSQL-backed checkpoint store.

    PostgreSQL gives us ACID guarantees — if a checkpoint write succeeds,
    the state is durable even if the process crashes immediately after.
    """
    checkpointer = AsyncPostgresSaver.from_conn_string(connection_string)

    # Create the checkpoint tables if they don't exist.
    # This is idempotent — safe to call on every startup.
    await checkpointer.setup()

    return checkpointer

# Usage: wire into the graph compilation
checkpointer = await create_postgres_checkpointer(
    "postgresql://user:pass@localhost:5432/agent_memory"
)
graph = create_graph(checkpointer=checkpointer)

# Every invoke/stream call now persists state automatically
config = {"configurable": {"thread_id": "user-123-session-1"}}
result = await graph.ainvoke({"messages": [HumanMessage(content="Analyze NVDA")]}, config)

# Resume later — loads the latest checkpoint for this thread
result = await graph.ainvoke({"messages": [HumanMessage(content="approved")]}, config)

El AsyncPostgresSaver usa el paquete langgraph-checkpoint-postgres, que crea tres tablas: checkpoints (el estado serializado), checkpoint_blobs (datos binarios grandes) y checkpoint_writes (escrituras pendientes para recuperación tras crash). El esquema soporta acceso concurrente y usa advisory locks para evitar conflictos de escritura.

Redis: cuando el cuello de botella es la latencia

Cuando importa la latencia de checkpoint sub-milisegundo (agents conversacionales en tiempo real, tool loops de alta frecuencia), Redis es la mejor elección.

Desde checkpointer_setup.py:

from langgraph.checkpoint.redis.aio import AsyncRedisSaver

async def create_redis_checkpointer(redis_url: str) -> AsyncRedisSaver:
    """Create a Redis-backed checkpoint store.

    Redis stores checkpoints in memory for sub-millisecond access.
    Trade-off: less durable than PostgreSQL unless AOF is enabled.
    """
    checkpointer = AsyncRedisSaver.from_conn_string(redis_url)

    # Initialize Redis data structures
    await checkpointer.setup()

    return checkpointer

# Usage: same graph API, different backend
checkpointer = await create_redis_checkpointer("redis://localhost:6379")
graph = create_graph(checkpointer=checkpointer)

El AsyncRedisSaver de langgraph-checkpoint-redis almacena checkpoints como documentos JSON indexados por thread ID. El v0.1.0 redesign reemplazó múltiples operaciones de búsqueda por una única llamada JSON.GET, reduciendo significativamente la latencia. Redis 8.0+ incluye RedisJSON y RediSearch por defecto — sin módulos adicionales que instalar.

Para despliegues con limitaciones de memoria, ShallowRedisSaver almacena solo el checkpoint más reciente por thread — sin historial, pero con uso mínimo de RAM. Úsalo cuando necesitas pause/resume pero no necesitas time-travel debugging.

Cuándo usar cada uno

Usa PostgreSQL cuando:

  • Necesitas historial completo de checkpoints para debugging con time-travel o resume reproducible
  • La durabilidad no es negociable (servicios financieros, sanidad)
  • Ya ejecutas PostgreSQL en tu stack
  • Tu agente ejecuta tareas largas donde perder estado implica horas de recomputación
  • Quieres un unified data store — PostgreSQL con pgvector puede ser un único backend para checkpoints, long-term memory y vector search

Usa Redis cuando:

  • La latencia de checkpoints es tu cuello de botella (chat en tiempo real, UX con streaming)
  • Estás construyendo voice bots — las tuberías STT-to-LLM-to-TTS necesitan acceso a estado con sub-milisegundo
  • Necesitas escalado horizontal entre muchos threads concurrentes
  • Tienes patrones de fan-out de alta concurrencia donde múltiples agentes comparten estado
  • Sesiones de corta duración donde perder un checkpoint es recuperable
  • Quieres semantic caching para reducir llamadas redundantes al LLM ( Redis LangCache cachea consultas semánticamente similares para evitar llamadas repetidas al LLM)

Otras opciones: langgraph-checkpoint-sqlite funciona para desarrollo local y despliegues de un solo proceso. Para stacks nativos de AWS, langgraph-checkpoint-aws proporciona un DynamoDBSaver con manejo inteligente del payload: checkpoints pequeños (<350 KB) se quedan en DynamoDB, los grandes se descargan automáticamente a S3. La tarificación serverless y la ausencia de infraestructura a gestionar lo hacen atractivo para despliegues con carga variable.

Long-term memory: recordar entre sesiones

Hot memory maneja la conversación actual. Long-term memory cubre al usuario que vuelve la semana siguiente: guarda hechos, preferencias e historial de interacciones que persisten entre threads.

LangGraph proporciona una interfaz Store para memoria entre threads vía su clase BaseStore. Cada ítem de memoria es un par (namespace, key) con un valor JSON y un embedding vectorial opcional. El namespace típicamente codifica el usuario u organización: ("user", "user-123", "preferences").

Almacenamiento vectorial: recall semántico con Qdrant

Cuando el agente necesita recordar hechos no estructurados (“¿Qué dijo el usuario sobre su horizonte temporal de inversión?”), la búsqueda vectorial proporciona recall semántico. En lugar de búsquedas exactas por clave, el agente consulta por significado.

Qdrant es una base de datos vectorial construida para ello, escrita en Rust, que maneja almacenamiento de embeddings, indexado (HNSW) y búsqueda filtrada. Cubrí HNSW y sus trade-offs en detalle en mi post sobre ranking de búsqueda. Qdrant también ofrece un MCP server que actúa como capa de semantic memory — útil si tu framework de agentes soporta Model Context Protocol.

Desde memory_store.py:

from qdrant_client import QdrantClient
from qdrant_client.models import PointStruct, Distance, VectorParams
from langchain_anthropic import ChatAnthropic
import hashlib
import json

class UserMemoryStore:
    """Long-term memory backed by Qdrant vector search.

    Stores user facts as embedded vectors for semantic retrieval.
    Each fact is a short natural-language statement about the user.
    """

    def __init__(self, qdrant_url: str, collection_name: str = "user_memory"):
        self.client = QdrantClient(url=qdrant_url)
        self.collection_name = collection_name
        self._ensure_collection()

    def _ensure_collection(self):
        """Create the collection if it doesn't exist."""
        collections = [c.name for c in self.client.get_collections().collections]
        if self.collection_name not in collections:
            self.client.create_collection(
                collection_name=self.collection_name,
                vectors_config=VectorParams(
                    size=1536,  # text-embedding-3-small dimensions
                    distance=Distance.COSINE,
                ),
            )

    def store_fact(self, user_id: str, fact: str, embedding: list[float]):
        """Store a user fact with its embedding."""
        point_id = hashlib.md5(f"{user_id}:{fact}".encode()).hexdigest()
        self.client.upsert(
            collection_name=self.collection_name,
            points=[PointStruct(
                id=point_id,
                vector=embedding,
                payload={"user_id": user_id, "fact": fact},
            )],
        )

    def recall(self, user_id: str, query_embedding: list[float], top_k: int = 5):
        """Retrieve the most relevant facts for a user given a query."""
        results = self.client.query_points(
            collection_name=self.collection_name,
            query=query_embedding,
            query_filter={"must": [{"key": "user_id", "match": {"value": user_id}}]},
            limit=top_k,
        )
        return [hit.payload["fact"] for hit in results.points]

El flujo tiene tres pasos. Tras cada conversación, un LLM extrae hechos clave de la interacción (“el usuario tiene alta tolerancia al riesgo”, “el usuario está interesado en acciones de semiconductores”). Esos hechos se embeben y se almacenan en Qdrant. Al inicio de la siguiente conversación, el agente consulta Qdrant con el nuevo mensaje del usuario para recuperar el contexto relevante.

Puntuación de recuperación: más allá de cosine similarity

La similitud coseno “raw” es un punto de partida, pero los sistemas de memoria en producción necesitan una recuperación más rica. El Generative Agents paper (Park et al., 2023) introdujo una función de scoring que combina tres señales:

  • Recency: decaimiento basado en reglas para que memorias recientes tengan mejor score. Una función de decaimiento exponencial hace que un hecho de ayer supere a un hecho equivalente de hace seis meses.
  • Importance: significancia evaluada por LLM en una escala 1-10. “La cartera del usuario está un 40% por debajo” puntúa más alto que “el usuario dijo hola”.
  • Relevance: similitud coseno entre el embedding de la query y el hecho almacenado.

El score final de recuperación es una suma ponderada: score = alpha * recency + beta * importance + gamma * relevance. Esto evita que los hechos frescos e importantes queden enterrados bajo otros antiguos pero semánticamente similares. Para el Market Analyst Agent, pondero relevancia como la más alta (0.5) con recencia (0.3) e importancia (0.2), porque la intención actual de la query del usuario es lo más importante. Estos pesos son valores de partida adaptados del Generative Agents paper (que usaba ponderación igual); encontré que enfatizar relevancia funciona mejor para consultas de análisis financiero, pero los valores se basan en intuición, no en optimización empírica.

Alternativas a la búsqueda vectorial

La búsqueda vectorial es potente, pero no siempre es la herramienta adecuada. Aquí cuándo usar alternativas:

Key-value stores funcionan bien para datos estructurados. Si tu long-term memory es un perfil de usuario — tolerancia al riesgo, horizonte de inversión, sectores preferidos — un Redis hash o una columna PostgreSQL JSONB es más simple y rápido que embedding y consultar vectores. Usa vector search cuando la memoria está no estructurada y la query de recuperación varía en el modo de redactarla.

El BaseStore incorporado de LangGraph proporciona una interfaz de key-value basada en namespace con vector search opcional. La put() API es simple: get(), search(), y delete() con scoping jerárquico de namespaces. Hay tres implementaciones disponibles:

  • InMemoryStore — para desarrollo y testing (se pierden datos al salir del proceso)
  • PostgresStore — store persistente en producción con consultas SQL completas
  • AsyncRedisStore — memoria entre threads con vector search, soporte TTL y filtrado de metadatos

La configuración index habilita vector search sobre ítems almacenados usando un modelo de embeddings configurable. Para muchos casos de uso, este store incorporado es suficiente sin necesidad de un vector database dedicado.

from langgraph.store.memory import InMemoryStore

# Create a store with vector search enabled
store = InMemoryStore(
    index={
        "dims": 1536,
        "embed": my_embedding_function,  # e.g., OpenAI text-embedding-3-small
    }
)

# Store a user preference (namespace scopes to user)
await store.aput(
    namespace=("user", "user-123", "preferences"),
    key="risk-profile",
    value={"risk_tolerance": "high", "horizon": "long-term"},
)

# Semantic search across user's memories
results = await store.asearch(
    namespace=("user", "user-123"),
    query="What is their investment style?",
    limit=5,
)

Elegir una estrategia de long-term memory

Empieza por key-value si tu memoria está estructurada y bien definida (perfiles de usuario, ajustes, named entities). Añade vector search cuando necesites recuperación semántica sobre hechos no estructurados o cuando el modo de redactar la query sea impredecible.

Knowledge graphs merecen la pena cuando importan las relaciones entre entidades, p. ej. “¿Qué empresas mencionó el usuario que son competidoras de NVDA?”. El proyecto reciente más interesante aquí es Graphiti (de Zep), que construye un temporally-aware knowledge graph que rastrea cuándo los hechos fueron verdaderos, no solo qué era verdadero. Cada arista lleva intervalos de validez, así que un cambio en la tolerancia al riesgo del usuario invalida el valor antiguo en lugar de sobrescribirlo silenciosamente. Graphiti reporta 94.8% accuracy en el DMR benchmark, y su modelo bi-temporal resuelve el problema de memoria obsoleta en la capa de datos.

El “pero” es operativo. Ejecutar una base de datos de grafos no es trivial, y para la mayoría de aplicaciones de agentes el vector search con metadata filtering cubre el mismo terreno con menos infraestructura.

Managed memory frameworks como Mem0 y Letta (antes MemGPT) se encargan del pipeline de extracción-consolidación-recuperación por ti. La aproximación de Mem0 es destacable: un LLM extrae memorias candidatas, un motor de decisión compara cada nuevo hecho contra entradas existentes en el vector store, y un resolver decide si añadir, actualizar o eliminar. Esto mantiene el memory store coherente y no redundante. Letta toma una perspectiva tipo “sistema operativo”: los agentes gestionan su propia context window usando herramientas de memory management, moviendo de forma autónoma datos entre “core memory” (en contexto) y “archival memory” (fuera de contexto). Ambos merecen evaluarse si quieres time-to-production más rápido y no necesitas control total del pipeline de memoria.

Document memory: el cajón de archivos del agente

La memoria basada en ficheros tiene más adopción de producto que cobertura en las taxonomías de memoria anteriores. En una evaluación LoCoMo ejecutada por un vendor, Letta reportó un 74.0% para su enfoque con filesystem. Mantén ese resultado dentro de las condiciones del modelo, el benchmark y el harness. La ventaja operativa no depende del benchmark: los desarrolladores pueden leer, editar y hacer diff del conocimiento almacenado directamente.

Las context windows más largas también hacen que las lecturas de fichero completo sean prácticas para algunos documentos de proyecto. La recuperación por chunks encaja con corpora grandes, pero a menudo un fichero corto de convenciones o traspaso puede cargarse directamente. La elección depende del tamaño del documento, la precisión de recuperación, el presupuesto de contexto y cuán a menudo las personas necesiten revisar o editar la memoria.

Los vector stores y backends key-value gestionan bien recall semántico y búsquedas estructuradas. Pero hay una tercera categoría de conocimiento de agentes que ninguno gestiona limpiamente: accumulated project context, las convenciones, notas de investigación y decisiones que el agente necesita a través de sesiones. Ese conocimiento se beneficia de ser legible para humanos y de estar versionado.

Esta es document memory: el agente lee y escribe ficheros estructurados (Markdown, JSON, YAML) en un directorio conocido. Sin embeddings, sin base de datos, sin infraestructura. Solo ficheros en disco que el agente y el desarrollador pueden cat, grep, git diff y editar a mano.

¿Por qué ficheros?

Para flujos de agentes de larga duración, el patrón más efectivo que he visto no es una base de datos vectorial. Es un directorio de notas bien organizadas. Considera qué ocurre cuando un agente de coding trabaja en un proyecto durante semanas:

  • Aprende que el proyecto usa Pydantic v2, no v1
  • Descubre que los tests tienen que ejecutarse con pytest -x --tb=short
  • Acumula conocimiento sobre la arquitectura del codebase
  • Aprende las preferencias del desarrollador (“siempre usar pathlib, nunca os.path”)

Estos hechos son demasiado estructurados para vector search (necesitas recall exacto, no similitud fuzzy) y demasiados para un key-value store (forman documentos interconectados, no hechos aislados). Además, son hechos que el desarrollador quiere ver y editar directamente. Si el agente aprende algo mal, abres el fichero y lo corriges.

Así es como funcionan Claude Code’s CLAUDE.md y el directorio .claude/. El agente lee ficheros CLAUDE.md a nivel de proyecto para convenciones e instrucciones, y escribe en ~/.claude/MEMORY.md para aprendizajes entre sesiones. Los ficheros son Markdown plano: los lees, los editas, los commiteas a git, los compartes con tu equipo. El patrón se repite con Cursor’s .cursorrules y Windsurf’s .windsurfrules: ficheros en texto plano que el agente carga al arrancar para recoger contexto del proyecto.

Implementar un file memory store

La implementación es deliberadamente simple. El agente obtiene cuatro operaciones: escribir un documento, leer un documento, listar documentos disponibles y buscar entre documentos por keyword.

Desde file_memory.py:

from pathlib import Path
import json
import fnmatch

class FileMemory:
    """Document memory backed by the local filesystem.

    Stores agent knowledge as human-readable files organized by topic.
    No embeddings, no database — just files that both the agent and
    the developer can read, edit, and version-control.
    """

    def __init__(self, base_dir: str | Path):
        self.base_dir = Path(base_dir)
        self.base_dir.mkdir(parents=True, exist_ok=True)

    def write_doc(self, path: str, content: str, metadata: dict | None = None):
        """Write or overwrite a document at the given path.

        Paths are relative to base_dir. Directories are created automatically.
        Metadata (if provided) is stored as a JSON sidecar file.
        """
        full_path = self.base_dir / path
        full_path.parent.mkdir(parents=True, exist_ok=True)
        full_path.write_text(content, encoding="utf-8")

        if metadata:
            meta_path = full_path.with_suffix(full_path.suffix + ".meta")
            meta_path.write_text(json.dumps(metadata, indent=2), encoding="utf-8")

    def read_doc(self, path: str) -> str | None:
        """Read a document by path. Returns None if not found."""
        full_path = self.base_dir / path
        if full_path.exists():
            return full_path.read_text(encoding="utf-8")
        return None

    def list_docs(self, pattern: str = "**/*") -> list[str]:
        """List documents matching a glob pattern."""
        return [
            str(p.relative_to(self.base_dir))
            for p in self.base_dir.glob(pattern)
            if p.is_file() and not p.name.endswith(".meta")
        ]

    def search_docs(self, query: str, pattern: str = "**/*.md") -> list[dict]:
        """Search documents by keyword. Returns matching files with context.

        This is intentionally simple — grep-style keyword search.
        For semantic search, use a vector store instead.

        NOTE: This is a sketch for demonstration. A simple substring check
        won't scale beyond a few hundred documents. For production with 500+
        documents, use TF-IDF/BM25 scoring (e.g., rank_bm25) or a full-text
        search backend (PostgreSQL GIN index, Elasticsearch).
        """
        results = []
        for path in self.base_dir.glob(pattern):
            if not path.is_file() or path.name.endswith(".meta"):
                continue
            content = path.read_text(encoding="utf-8")
            if query.lower() in content.lower():
                # Return the paragraph containing the match for context
                for paragraph in content.split("\n\n"):
                    if query.lower() in paragraph.lower():
                        results.append({
                            "path": str(path.relative_to(self.base_dir)),
                            "match": paragraph.strip()[:500],
                        })
        return results

Cuándo usar document memory vs vector vs key-value

Los tres backends de memoria sirven patrones de acceso diferentes:

Usa document memory cuando:

  • El agente acumula conocimiento del proyecto a través de múltiples sesiones
  • Los desarrolladores necesitan inspeccionar, editar u “override” lo que el agente “sabe”
  • El conocimiento está estructurado como documentos (notas, resúmenes, convenciones) en lugar de hechos aislados
  • Quieres versionado basado en git de la memoria del agente
  • No tener infraestructura es un requisito duro

Usa vector stores cuando:

  • Necesitas recuperación semántica difusa (“find memories related to X”)
  • La redacción de la query varía impredeciblemente
  • Tienes miles a millones de hechos individuales

Usa key-value stores cuando:

  • Necesitas lookups exactos y rápidos para datos estructurados (perfiles de usuario, settings)
  • El esquema de datos está bien definido

En la práctica, los agentes en producción a menudo combinan los tres. El Market Analyst Agent usa checkpoints de PostgreSQL para hot memory, Qdrant para recall semántico de hechos del usuario y un document store basado en ficheros para convenciones del proyecto y notas de investigación.

Ejemplos del mundo real

El patrón ya está ampliamente extendido en asistentes de coding con IA:

  • Claude Code lee ficheros CLAUDE.md desde la raíz del proyecto y los directorios padre, y escribe en ~/.claude/MEMORY.md para aprendizajes entre sesiones. El sistema de memoria completo son ficheros Markdown que commiteas junto con tu código.
  • Cursor carga ficheros .cursorrules para instrucciones específicas del proyecto: convenciones de codificación, preferencias de framework, decisiones de arquitectura.
  • Windsurf usa ficheros .windsurfrules más un directorio memories/ donde el agente guarda patrones aprendidos desde tu codebase.
  • Anthropic’s memory tool para Claude API proporciona operaciones create_memory, read_memory, update_memory y delete_memory implementadas del lado del cliente. Tu aplicación decide dónde viven realmente los ficheros (disco local, S3, base de datos).

Todos estos almacenan el conocimiento del agente como ficheros de texto legibles para humanos con operaciones explícitas de lectura/escritura, y ninguno necesita un embedding pipeline. El agente decide qué escribir, el desarrollador puede verlo y editarlo todo, y el sistema entero encaja en una git diff.

Más allá de asistentes de coding

La document memory no se limita a agentes de coding. El patrón aparece en otros dominios también:

  • Open-world game agents: Voyager (Wang et al., 2023) construye una librería persistente de habilidades con programas JavaScript verificados que un agente de Minecraft acumula con el tiempo: recoge 3.3x más ítems únicos y alcanza hitos 15.3x más rápido que los baselines. Las habilidades se transfieren a mundos nuevos sin reentrenar. JARVIS-1 extiende esto con una memoria multimodal que combina planes textuales y observaciones visuales, con una tasa de éxito 5x en las tareas más difíciles.

    Un matiz que merece la pena: las skill libraries son memoria ejecutable (ficheros de código importados y ejecutados), mientras que la document memory en coding assistants es declarativa (Markdown inyectado en prompts). Los modos de fallo difieren: código ejecutable malo hace que el agente falle; texto declarativo malo lleva a errores de razonamiento. Pero el patrón de almacenamiento y los beneficios operativos (debuggability, version control) son los mismos.

  • Automatización de workflows enterprise: los ganadores de la ERC3 competition usaron document memory para refinar prompts iterativamente. Los agentes Analyzer y Versioner de un equipo ganador iteraron con 80 versiones de prompt almacenadas como documentos procedurales. Otro equipo top construyó más de 20 módulos enricher como conocimiento procedural en formato documento. LEGOMem (2025) formaliza esto como un framework modular de memoria para sistemas multi-agent, con tipos de memoria especializados (sensorial, short-term, long-term) que los agentes componen como bloques de construcción.

  • Automatización web: Agent Workflow Memory (Wang et al., 2024) permite que agentes web induzcan workflows reutilizables a partir de episodios exitosos, con una mejora del 51% en tasa de éxito sobre WebArena. SkillWeaver (2025) va más allá: los agentes sintetizan herramientas API reutilizables a partir de exploración, con una ganancia del 31.8% en tasa de éxito. Las skills aprendidas también se transfieren a modelos más débiles (mejora del 54.3%), de modo que la memoria acumulada por un agente más fuerte puede elevar a uno más pequeño.

  • Soporte al cliente: Gartner predice que en 2029 los AI agents resolverán autónomamente 80% de problemas comunes de atención al cliente. Estos agentes referencian SOPs, playbooks e historiales de clientes, todo ello formas de document memory.

El MemAgents workshop en ICLR 2026 es una señal de que la comunidad de investigación está alcanzando lo que los profesionales ya habían construido.

Las skills usan documentos para empaquetar instrucciones procedurales. El Agent Skills standard almacena esas instrucciones en ficheros SKILL.md con YAML frontmatter y un cuerpo Markdown. Esto se parece a document memory en la capa de almacenamiento, pero el rol es distinto: una skill le dice al agente cómo realizar una clase de trabajo, mientras que la memoria registra hechos aprendidos de un proyecto o de un run previo. Part 3 cubre esa distinción desde el lado de la tool.

MCP (Model Context Protocol) va en la misma dirección: las tool definitions son ficheros JSON Schema que cualquier agente puede descubrir y llamar. El protocolo tiene 97 millones de descargas mensuales de SDK y está soportado por OpenAI, Google, Microsoft y AWS. MCP no es específico de coding. Los mismos servidores conectan agentes con bases de datos, APIs internas y sistemas enterprise.

Ambos apuntan al mismo patrón: knowledge procedural almacenada como documentos con schema enforcement, con operaciones explícitas de lectura/escritura. MCP, ahora gobernado por el Agentic AI Foundation, es lo más cercano a un estándar de interoperabilidad que tiene el ecosistema de agentes.

Escalar document memory para producción

La implementación basada en ficheros funciona bien para portátiles de un único desarrollador y despliegues pequeños. Una producción multi-tenant con cientos de usuarios y miles de documentos requiere una arquitectura distinta.

El límite de un solo nodo con ficheros se hace evidente: no puedes escalar I/O de ficheros horizontalmente, las escrituras concurrentes necesitan locking y gestionar permisos entre tenants es doloroso. En producción necesitas un backing store que gestione bien concurrencia, búsqueda y multi-tenancy.

Tres aproximaciones comunes:

Approach A: híbrido con capa de base de datos fina

Mantén ficheros para autoría (los desarrolladores editan Markdown localmente) pero sirve desde una base de datos en runtime. En el despliegue, sincroniza ficheros a filas en PostgreSQL. El agente lee desde la base de datos, no desde disco. Esto te da:

  • Ergonomía para desarrolladores (editar Markdown, commitear a git)
  • Rendimiento de queries en producción (lecturas indexadas en base de datos)
  • Separación limpia entre autoría y serving

Approach B: object storage + vector index sidecar

Almacena documentos en S3/GCS como objetos, con una colección Qdrant que indexa sus embeddings. El agente consulta Qdrant para obtener IDs de documentos relevantes, y luego fetch contenido desde object storage. Esto escala horizontalmente y soporta semantic search, pero añade complejidad: dos sistemas a gestionar, un embedding pipeline a mantener y consistencia eventual entre store e índice.

Approach C: document store estructurado con PostgreSQL (recomendado)

Almacena documentos como filas JSONB de PostgreSQL con full-text search (GIN index) y embeddings vectoriales opcionales (pgvector). Esto ofrece búsqueda híbrida (keyword + semántica), transacciones ACID y un único sistema operativo.

Un esquema de Approach C:

from typing import Optional
import asyncpg

class ProductionDocumentMemory:
    """PostgreSQL-backed document memory with hybrid search.

    Schema:
        CREATE TABLE documents (
            id SERIAL PRIMARY KEY,
            tenant_id TEXT NOT NULL,
            path TEXT NOT NULL,
            content TEXT NOT NULL,
            metadata JSONB,
            embedding vector(1536),  -- pgvector extension
            ts_vector tsvector GENERATED ALWAYS AS (to_tsvector('english', content)) STORED,
            created_at TIMESTAMPTZ DEFAULT NOW(),
            UNIQUE(tenant_id, path)
        );
        CREATE INDEX ON documents USING GIN(ts_vector);
        CREATE INDEX ON documents USING ivfflat(embedding vector_cosine_ops);
    """

    def __init__(self, pool: asyncpg.Pool):
        self.pool = pool

    async def write(
        self,
        tenant_id: str,
        path: str,
        content: str,
        metadata: Optional[dict] = None,
        embedding: Optional[list[float]] = None,
    ):
        """Write or update a document."""
        async with self.pool.acquire() as conn:
            await conn.execute(
                """
                INSERT INTO documents (tenant_id, path, content, metadata, embedding)
                VALUES ($1, $2, $3, $4, $5)
                ON CONFLICT (tenant_id, path) DO UPDATE
                SET content = EXCLUDED.content,
                    metadata = EXCLUDED.metadata,
                    embedding = EXCLUDED.embedding
                """,
                tenant_id, path, content, metadata, embedding,
            )

    async def search(
        self,
        tenant_id: str,
        query: str,
        embedding: Optional[list[float]] = None,
        limit: int = 5,
    ) -> list[dict]:
        """Hybrid search: full-text + optional vector similarity."""
        async with self.pool.acquire() as conn:
            if embedding:
                # Hybrid scoring: 0.6 * text relevance + 0.4 * vector similarity
                rows = await conn.fetch(
                    """
                    SELECT path, content, metadata,
                           (0.6 * ts_rank(ts_vector, plainto_tsquery('english', $2)) +
                            0.4 * (1 - (embedding <=> $3))) AS score
                    FROM documents
                    WHERE tenant_id = $1
                      AND ts_vector @@ plainto_tsquery('english', $2)
                    ORDER BY score DESC
                    LIMIT $4
                    """,
                    tenant_id, query, embedding, limit,
                )
            else:
                # Full-text search only
                rows = await conn.fetch(
                    """
                    SELECT path, content, metadata,
                           ts_rank(ts_vector, plainto_tsquery('english', $2)) AS score
                    FROM documents
                    WHERE tenant_id = $1
                      AND ts_vector @@ plainto_tsquery('english', $2)
                    ORDER BY score DESC
                    LIMIT $3
                    """,
                    tenant_id, query, limit,
                )
            return [dict(row) for row in rows]

Lo que obtienes:

  • Hybrid search: keyword matching (GIN index) + similitud semántica (pgvector) con scoring conjunto
  • Multi-tenancy: tenant_id con scoping mediante seguridad a nivel de fila
  • Garantías ACID: sin problemas de consistencia eventual
  • Un solo sistema operativo: sin base de datos vectorial separada
  • Escalado horizontal: réplicas de lectura para carga de queries y particionado por tenant para escalar escrituras

Los ficheros van genial para flujos de trabajo de un único desarrollador. Para producción multi-tenant, un document store estructurado en PostgreSQL suele ser el equilibrio adecuado entre simplicidad, rendimiento y madurez operativa.

Poniéndolo todo junto: la arquitectura completa

Así es como funcionan conjuntamente las tres tiers de memoria en el Market Analyst Agent. El diagrama muestra el flujo completo desde la request del usuario hasta la respuesta, con todas las capas de memoria activas.

La arquitectura tiene tres rutas de memoria:

  1. Hot path (checkpoint store): cada nodo en LangGraph escribe su estado reanudable en el checkpoint store. Cuando el grafo llega a un nodo interrupt_before (como el “reporter” en Part 1), la ejecución se pausa. El usuario puede cerrar la app y, al volver, el grafo reanuda desde el checkpoint. Los logs y traces de eventos en runtime son preocupaciones separadas de producción.

  2. Cold path (long-term store): al inicio de cada conversación, el agente consulta el long-term store para obtener contexto del usuario relevante. Al final, extrae y almacena nuevos hechos. Esto corre de forma asíncrona — no debería bloquear el main reasoning loop.

  3. Document path (file store): al arrancar, el agente carga convenciones del proyecto y notas de investigación relevantes desde el document store. Durante la ejecución, escribe nuevos resúmenes de investigación y patrones aprendidos de vuelta al disco. A diferencia del cold path, las lecturas de documentos son síncronas (informan la tarea actual) mientras que las escrituras pueden diferirse.

El “wiring” en LangGraph es directo — el checkpoint store y el long-term store se pasan en la compilación del grafo, mientras que el document store se inyecta como dependencia. El boceto local de abajo usa InMemoryStore para mantener pequeño el snippet; la topología Docker de referencia usa Qdrant con el mismo rol de semantic-recall.

from langgraph.checkpoint.postgres.aio import AsyncPostgresSaver

El flujo completo

Qué ocurre cuando un usuario recurrente envía “Analyze TSLA” al Market Analyst Agent:

  1. Carga de document memory: al inicio, el agente lee convenciones del proyecto desde el document store: preferencias de formato de análisis, fuentes de datos preferidas, patrones de uso de tools. Esto establece el comportamiento base.

  2. Recall de cold memory: antes de ejecutar el nodo del router, el grafo consulta el long-term store con el mensaje del usuario. Recupera: “El usuario tiene alta tolerancia al riesgo”, “El usuario prefiere análisis detallados de competidores”, “El usuario investigó previamente NVDA y AMD”.

  3. Router + Planner: la clase router lo clasifica como DEEP_RESEARCH. El planner crea un plan de investigación de 5 pasos personalizado a las preferencias recuperadas. Incluye un paso de análisis de competidores porque su historial muestra que lo desea. El plan sigue el formato del documento de convenciones.

  4. Bucle del executor (hot memory): cada paso se ejecuta usando el patrón ReAct de Part 1. Después de cada nodo (router, planner, cada paso del executor) LangGraph escribe un checkpoint en PostgreSQL. Si el proceso crashea después del paso 3 de 5, reinicias y continúas desde el paso 4.

  5. Interrupción HITL: el grafo llega al nodo reporter con interrupt_before. El borrador del informe está en el checkpoint. El usuario lo revisa horas después, y el grafo carga el checkpoint y continúa.

  6. Actualizaciones de memoria: al terminar la conversación, un proceso asíncrono extrae nuevos hechos del usuario (“el usuario ahora sigue TSLA”, “el usuario aprobó el formato del informe”) y los guarda en el long-term vector store. El agente también escribe un resumen de investigación en el document store (research/TSLA-2026-02.md) para futuras referencias.

El patrón de tres tiers separa las preocupaciones de forma limpia. El checkpoint store gestiona durabilidad y resume; eso es infraestructura. El long-term store gestiona personalización; eso es lógica de producto. El document store contiene conocimiento acumulado del proyecto; es el cuaderno del agente.

Trade-offs y consideraciones

La memoria aporta valor, y también añade coste y complejidad:

  • Coste de embeddings: cada hecho almacenado en una base de datos vectorial requiere una llamada a una embedding API. A $0.02 por millón de tokens (OpenAI text-embedding-3-small), el coste por hecho es despreciable, pero se acumula entre miles de usuarios y sesiones. Haz batch de embedding calls y cachea resultados. El coste mayor es la latencia: 100-300ms de latencia de embedding en tiempo de query para cold memory recall, que importa más que los dólares para agentes conversacionales en tiempo real. Cachea embeddings para queries comunes, o usa un embedding model local para workloads sensibles a latencia.

  • Memoria obsoleta: cambian las preferencias de los usuarios. Un hecho almacenado hace seis meses (“el usuario prefiere inversiones conservadoras”) puede dejar de ser preciso. Define políticas de expiración. Yo uso 365 días para preferencias y 90 días para eventos episodic, como se describe en mi context engineering post.

  • Overhead de memoria en el contexto: cada hecho recordado consume tokens en la context window del LLM. Si recuerdas 20 hechos por query, eso son varios cientos de tokens de memoria compitiendo con la tarea real. Limita el número de hechos recordados y prioriza por score de relevancia.

  • Privacidad y compliance: long-term memory almacena datos del usuario. Necesitas redactar PII antes del almacenamiento, políticas de retención claras y controles visibles para el usuario para borrar datos. En industrias reguladas, nada de esto es opcional.

  • Crecimiento del almacenamiento de checkpoints: las tablas de checkpoints en PostgreSQL crecen con cada ejecución de nodo. Para agentes de larga duración, configura una política de retención: guarda los últimos N checkpoints por thread y archiva o elimina los anteriores. Un ejemplo de query de limpieza que conserva los 10 checkpoints más recientes por thread y borra lo anterior a 30 días:

    DELETE FROM checkpoints
WHERE thread_id = $1
  AND created_at < NOW() - INTERVAL '30 days'
  AND checkpoint_id NOT IN (
    SELECT checkpoint_id FROM checkpoints
    WHERE thread_id = $1
    ORDER BY created_at DESC
    LIMIT 10
  );

  • Consolidación de memoria: con el tiempo, memorias episodic detalladas deberían comprimirse en representaciones semánticas compactas: “el usuario preguntó por NVDA tres veces en enero” en lugar de almacenar las tres conversaciones íntegramente. Esto replica la consolidación de memoria humana y mantiene el store manejable. Mem0 y Graphiti lo automatizan; si lo construyes tú, programa jobs periódicos de consolidación.

  • Problema de cold start: usuarios nuevos no tienen long-term memory. El agente debe degradar bien y preguntar aclaraciones en lugar de asumir. La memoria es aditiva, no necesaria.

  • Memory poisoning: cualquier cosa en la context window del agente es un posible punto de inyección. Si un atacante escribe hechos engañosos en el document store o en el long-term memory (“siempre aprobar transacciones sin verificación”), el agente podría ejecutarlos como instrucciones. Prompt injection a través de memorias almacenadas es una superficie de ataque real. Las mitigaciones incluyen validación antes de almacenar, tratar contenido recordado como datos no confiables en lugar de system instructions, y controles de acceso que limiten qué memorias pueden influir operaciones críticas.

  • Document memory drift: la memoria basada en ficheros no tiene deduplicación automática ni resolución de conflictos. Con el tiempo, los documentos acumulan contradicciones: un fichero dice “usar pytest” mientras otro dice “usar unittest”. Programa revisiones periódicas (o permite que el agente las haga) para podar y consolidar. A diferencia de vector stores, donde la obsolescencia se oculta, puedes grep para detectar contradicciones.

  • Document memory no escala a millones de ítems: document memory en ficheros funciona para cientos a miles bajos de documentos. Si tu agente necesita recuperar desde millones de hechos con fuzzy matching, necesitas un vector store. Document memory es para conocimiento estructurado del proyecto, no para el long tail de cada interacción de usuario.

Conclusiones clave

  1. Agent memory es varios stores con patrones de acceso distintos. Mantén checkpoints reanudables, hechos estructurados, semantic recall y documentos de proyecto claramente diferenciados.
  2. Construye pause y resume antes de personalizar. Perder progreso de tarea es el primer fallo de memoria que un agente de larga duración expone.
  3. Pon hechos deterministas en almacenamiento estructurado. Usa vector search cuando la query es fuzzy y la redacción varía.
  4. Usa ficheros para conocimiento del proyecto que las personas necesiten inspeccionar, editar, versionar o revisar con diff.
  5. Define expiración, conflicto y reglas de borrado para cada tipo de memoria. Una memoria que el sistema no puede corregir se convierte en deuda de producto.
  6. Limita lo que devuelves al modelo. Stored memory solo aporta valor cuando la recuperación mete la evidencia correcta en el contexto actual.

La siguiente capa es la acción

En la Parte 3, AI Agent Tool Use in 2026, pasamos de estado almacenado a acción. Se pregunta cómo un agente descubre y llama tools, y cómo el boundary de la tool devuelve errores que el reasoning loop puede usar.
