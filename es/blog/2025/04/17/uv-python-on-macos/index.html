uv en macOS: Gestión de versiones de Python, proyectos y herramientas

He pasado mi flujo de trabajo con Python a uv, ya que reemplaza la compleja gestión de herramientas que antes realizaba entre pip, entornos virtuales, pip-tools, pipx y gestores de proyecto. Ahora un único ejecutable cubre la mayor parte de esas tareas.

No obstante, los flujos de trabajo siguen siendo distintos. Un proyecto, un script de metadatos incrustados, una CLI de uso único y una CLI instalada tienen cada uno su propio entorno y ciclo de vida. Esta guía muestra los comandos que utilizo y los límites que definen cada uno de ellos.

Inicio rápido

# Install uv with Homebrew
brew install uv

# Start a project
uv init example-app
cd example-app
uv add httpx
uv run python main.py

# Run an isolated CLI without installing it permanently
uvx ruff check .

# Run a script that declares PEP 723 dependencies
uv run fetch.py

TL;DR. En los proyectos uso uv add, uv lock, uv sync y uv run; para los scripts autónomos, metadatos según PEP 723; uvx para herramientas de uso único; y uv tool install para comandos que deben permanecer en PATH. En entornos CI, --locked verifica que los metadatos del proyecto coincidan con uv.lock, mientras que --frozen confía en el archivo lock existente sin comprobar su actualidad.

Instalar uv con un único responsable

Homebrew es una vía práctica de instalación en macOS:

brew install uv
uv --version

Si Homebrew ya ha instalado uv, debe actualizárselo:

brew upgrade uv

uv self update se utiliza para el método de instalación independiente de uv y está desactivado en instalaciones mediante gestores de paquetes. No permita que dos instaladores compitan por el mismo ejecutable.

Comandos útiles para identificar elementos:

command -v uv
uv python dir
uv tool dir
uv cache dir

Las instalaciones gestionadas de Python, las herramientas persistentes y los elementos de caché temporales cuentan con directorios separados. El caché puede eliminarse y reconstruirse; no constituye una fuente fiable de información.

Proyectos: declaraciones, resolución y entorno

Un proyecto uv suele contener tres tipos de archivos diferentes:

  • pyproject.toml declara los metadatos del proyecto y los requisitos directos.
  • uv.lock almacena la resolución multiplataforma gestionada por uv.
  • .venv representa el entorno instalado localmente y debe ser temporal.

Cree una aplicación e incluya los requisitos necesarios para su ejecución y pruebas:

uv init forecast-app
cd forecast-app

uv add httpx
uv add --group test pytest
uv run python main.py
uv run --group test pytest

Los plantillas actuales de aplicaciones uv generan main.py, pyproject.toml, README.md y .python-version. Por defecto, no definen ningún sistema de compilación. Utilice uv init --lib para una biblioteca empaquetada con una estructura src y un backend de compilación específico.

uv run examina el proyecto, actualiza el archivo lock cuando es necesario, sincroniza las dependencias requeridas y ejecuta el comando correspondiente. La primera operación sobre el proyecto crea .venv y uv.lock según sea preciso; uv init, por su parte, solo genera los archivos del proyecto.

Commit las entradas, no el entorno

Guarde pyproject.toml, uv.lock, el código fuente y un .python-version intencionado. Ignore .venv y los cachés generados por uv.

El archivo lock registra la resolución obtenida en los diferentes marcadores y plataformas soportadas; no garantiza que los archivos binarios resultantes sean idénticos en macOS, Linux, Intel y Apple Silicon. Pruebe siempre en cada plataforma de despliegue.

Bloqueo de actualidad: --locked no es --frozen

Por defecto, los comandos del proyecto pueden actualizar uv.lock cuando cambian las declaraciones.

Se debe utilizar --locked para exigir que el bloqueo esté al día con la metadatos del proyecto:

uv lock --check
uv sync --locked
uv run --locked pytest

Si pyproject.toml y uv.lock difieren, estos comandos fallan en lugar de generar un nuevo bloqueo. Este comportamiento suele ser útil como filtro en los procesos CI.

Solo se debe emplear --frozen cuando se quiera explícitamente que uv utilice el bloqueo existente sin verificar si está actualizado:

uv sync --frozen

Esto puede resultar útil en fases de compilación controladas donde el bloqueo ya ha sido validado, pero no constituye un detector de bloqueos obsoletos. uv sync funciona de forma estricta por defecto y elimina paquetes no necesarios; uv run emplea una sincronización no estricta por defecto, a menos que se solicite lo contrario mediante --exact.

Python gestionado: una solicitud de versión, no un binario universal

uv permite descargar y gestionar distribuciones de Python:

uv python install 3.12 3.13
uv python list --only-installed
uv python pin 3.12

Las compilaciones de CPython gestionadas por uv provienen del proyecto python-build-standalone. Además, uv también puede detectar interpretadores del sistema, Homebrew, pyenv, Conda y otros.

.python-version representa una solicitud de versión identificada por uv y otras herramientas compatibles. requires-python en pyproject.toml define el contrato de compatibilidad del proyecto. Ambos elementos deben mantenerse intencionalmente:

[project]
requires-python = ">=3.12,<3.14"

Fijar 3.12 no garantiza que siempre se utilice la misma versión con parches ni que se obtenga el mismo artefacto en todos los sistemas operativos. Solo se debe solicitar una versión exacta cuando sea realmente necesario, y se debe indicar explícitamente en los procesos CI qué interpretador se utilizará.

Se debe emplear otro gestor de Python cuando un proyecto requiera una distribución o configuración de compilación que uv no ofrece. No obstante, uv sigue pudiendo utilizar dicho interpretador a través de --python o mediante el proceso normal de detección.

Elección entre uv run, uvx y herramientas instaladas

Herramientas vinculadas al proyecto: uv run

Si pytest, mypy, un generador de código u otra herramienta necesita importar el proyecto o utilizar sus plugins bloqueados, se debe declarar dentro de un grupo de dependencias:

uv add --group lint ruff
uv run --group lint ruff check .

Ejecutar dicha herramienta a través de uvx la aislaría del proyecto y podría ocultar los paquetes o plugins instalados que necesita.

Herramientas ad hoc: uvx

uvx es un alias de uv tool run. Crea un entorno aislado almacenado en la caché temporal de uv:

uvx ruff@0.12.0 check .
uvx --from jupyterlab jupyter lab
uvx --with mkdocs-material mkdocs --help

Se debe fijar la versión de la herramienta en los procesos CI o en la documentación. La primera ejecución sin especificar versión seleccionará la versión más reciente, mientras que las ejecuciones posteriores podrían reutilizar el estado de la caché.

Ejecutables persistentes: uv tool install

Se debe instalar una herramienta cuando scripts fuera del control del desarrollador necesiten su comando en PATH, o cuando el manifiesto de la máquina indique explícitamente que dicha herramienta pertenece a ella:

uv tool install 'ruff==0.12.0'
uv tool list
uv tool upgrade ruff
uv tool uninstall ruff

Las herramientas persistentes siguen utilizando entornos aislados. No se debe modificar manualmente dichos entornos con pip.

Scripts: hacer de un archivo la unidad de lanzamiento

PEP 723 define metadatos de script integrados. Un ejecutor compatible puede leer el bloque de comentarios y crear un entorno aislado.

# /// script
# requires-python = ">=3.12"
# dependencies = [
#   "httpx>=0.27,<1",
# ]
# ///
import httpx


response = httpx.get("https://example.com", timeout=10)
response.raise_for_status()
print(response.status_code)

Ejecutar y editar metadatos con uv:

uv run fetch.py
uv add --script fetch.py rich
uv remove --script fetch.py rich

El formato simple python fetch.py ignora los metadatos de comentario. Por lo tanto, el script depende de un ejecutor compatible, aun cuando la sintaxis de Python siga siendo válida.

Para un script que deba reproducir posteriormente una resolución específica, se debe crear un archivo de bloqueo adyacente:

uv lock --script fetch.py
uv run --script fetch.py

Esto escribe fetch.py.lock. Una marca de tiempo exclude-newer puede restringir las fechas posibles de distribución, pero es menos fiable que una resolución bloqueada con precisión y no garantiza que el artefacto permanezca disponible.

Se prefiere utilizar un proyecto cuando varios archivos comparten dependencias, el código es importable como paquete, las pruebas necesitan el estado del proyecto o varios scripts deben moverse conjuntamente.

Archivos de requisitos: compatibilidad, no fallos

Un archivo requirements.txt puede contener entradas flexibles, valores fijos, hashes, restricciones, índices, URLs o un entorno compilado. Su reproducibilidad depende de cómo se haya generado y consumido; el nombre del archivo por sí solo no indica nada.

Se puede utilizar la interfaz compatible con pip de uv sin realizar migraciones:

uv venv
uv pip sync requirements.txt
uv run python app.py

uv pip sync hace que el entorno coincida con el archivo, mientras que uv pip install -r tiene un efecto aditivo.

En el caso de una aplicación propia, una migración por etapas puede resultar útil:

uv init --bare
uv add -r requirements.in
uv add --group test -r requirements-test.in
uv lock
uv sync --locked

Ejecutar todo el proceso de pruebas e implementación antes de eliminar los archivos antiguos. Si un sistema posterior sigue esperando el formato de pip, se puede obtener dicho formato a partir del archivo de bloqueo validado de uv:

uv export --format requirements.txt \
  --output-file requirements.txt

No se debe mantener uv.lock junto con una exportación editada a mano como dos resoluciones concurrentes.

Caché, índices y límites en la cadena de suministro

El caché de uv mejora las instalaciones repetidas, pero sigue siendo temporal:

uv cache prune
uv cache clean

Se recomienda utilizar prune para tareas de limpieza habituales. clean elimina todas las entradas del caché e impide nuevas descargas y compilaciones hasta entonces.

Un archivo de bloqueo mejora la reproductibilidad, pero no hace que las dependencias sean fiables. Es necesario revisar las fuentes de los paquetes, la configuración de los índices, las revisiones de Git, los motores de compilación, las licencias y las credenciales. La configuración del índice autenticado debe permanecer fuera de los archivos comprometidos, a menos que el repositorio almacene únicamente referencias no sensibles a un mecanismo de credenciales aprobado.

En el caso de paquetes nativos, se debe registrar la arquitectura de despliegue y comprobar la disponibilidad de las versiones de prueba. De lo contrario, el resolvedor podría recurrir a una compilación desde la fuente, que requiere compiladores y bibliotecas del sistema que pueden faltar en entornos de CI o producción.

Lista de verificación operativa concisa

Para cada proyecto:

  1. Definir requires-python y las dependencias directas en pyproject.toml.
  2. Separar los recursos publicados de los grupos de dependencias locales.
  3. Cometer uv.lock; ignorar .venv y el estado del caché.
  4. Ejecutar las herramientas vinculadas al proyecto dentro del entorno correspondiente.
  5. Utilizar uv lock --check o --locked en los procesos de CI.
  6. Probar en cada sistema operativo y arquitectura representados por el archivo de bloqueo.
  7. Exportar formatos de compatibilidad únicamente para los consumidores designados.
  8. Revisar la política de fuentes y credenciales de forma independiente de la resolución elegida.

uv resulta más útil cuando estos límites de responsabilidad permanecen claros. Un único binario puede gestionar todo ello sin convertirlo en un único entorno. Esta combinación —menos herramientas y sin pretender que todos los flujos de trabajo sean idénticos— es la razón por la cual sigo utilizando uv como mi herramienta predeterminada para proyectos en Python en macOS.
