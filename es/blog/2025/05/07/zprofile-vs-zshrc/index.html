Archivos de inicio de Zsh: ~/.zprofile frente a ~/.zshrc en macOS y Linux

Si tu terminal funciona de forma lenta, o una variable de entorno aparece en un terminal pero no en otro, la causa suele ser el modo de inicio de Zsh. Los dos archivos que la mayoría de los usuarios consultan son ~/.zprofile y ~/.zshrc, pero ninguno de estos nombres por sí solo indica si una línea pertenece realmente allí.

Zsh selecciona los archivos de inicio en función de dos propiedades independientes: si el shell es un shell de inicio de sesión y si es interactivo. Las aplicaciones de terminal en macOS y Linux pueden elegir diferentes combinaciones, por lo que es necesario inspeccionar el shell en ejecución en lugar de suponer que el sistema operativo lo decide por uno.

En resumen. Coloca la inicialización de sesiones de inicio de sesión en .zprofile y el comportamiento interactivo en .zshrc. Mantén .zshenv sin cambios y con un contenido mínimo. No muevas los ganchos del gestor de versiones para modo interactivo a .zprofile ni cargues todo el perfil desde .zshrc; inspecciona el código generado por la herramienta y sigue las instrucciones actuales de Zsh.

Zsh evalúa dos indicadores independientes

Un shell puede ser:

  • de inicio de sesión e interactivo, ya que Apple Terminal suele iniciar el shell de inicio de sesión predeterminado de la cuenta;
  • sin inicio de sesión e interactivo, como ocurre cuando se utiliza un zsh anidado o muchas configuraciones de terminal de Linux;
  • de inicio de sesión y no interactivo, como en zsh -lc 'command';
  • sin inicio de sesión y no interactivo, como en zsh -c 'command'.

Las aplicaciones de terminal, los IDE, las sesiones remotas, los multiplexores y los indicadores explícitos del shell pueden elegir diferentes modos. El sistema operativo por sí solo no determina este resultado.

Pregunta al shell en ejecución en lugar de adivinar:

print -r -- "interactive=$options[interactive] login=$options[login]"

El orden real de inicio

Zsh lee primero los archivos globales y luego los archivos correspondientes del usuario. Con las opciones predeterminadas de RCS, el orden de lectura de los archivos del usuario es el siguiente:

  1. $ZDOTDIR/.zshenv en cada llamada a Zsh;
  2. $ZDOTDIR/.zprofile si el shell es un shell de inicio de sesión;
  3. $ZDOTDIR/.zshrc si el shell es interactivo;
  4. $ZDOTDIR/.zlogin si el shell es un shell de inicio de sesión;
  5. $ZDOTDIR/.zlogout cuando un shell de inicio de sesión finaliza de forma normal.

Si ZDOTDIR no está definido, Zsh utiliza $HOME. Las ubicaciones de los archivos a nivel de sistema dependen de la instalación; los valores predeterminados comunes son /etc/zshenv, /etc/zprofile, /etc/zshrc, /etc/zlogin y /etc/zlogout.

Este orden funciona como un filtro, no como una garantía de ciclo de vida. .zprofile se ejecuta una vez por proceso de shell de inicio de sesión, no una vez por cada inicio de sesión en el ordenador. Si cada pestaña de terminal nueva inicia un shell de inicio de sesión, todas las pestañas lo leerán.

Mantén .zshenv sin complejidad

Cada zsh -c no interactivo lee .zshenv. La presencia de un echo, una llamada al gestor de paquetes o un subproceso costoso puede dañar el output de los comandos y ralentizar los scripts. La mayoría de los usuarios solo necesitan poco o nada en este archivo.

Una variable exportada en .zprofile es heredada por los hijos de dicho shell de inicio de sesión. No se introduce automáticamente en aplicaciones GUI, servicios o shells no relacionados cuyo padre nunca haya leído el archivo.

Utiliza .zprofile para configuraciones exclusivas de inicio de sesión

Un perfil reducido puede establecer valores predeterminados exportados y una ruta idempotente:

# ~/.zprofile
export EDITOR=nvim
export VISUAL=nvim

# Zsh ties the path array to the PATH scalar.
typeset -U path PATH
path=("$HOME/.local/bin" $path)
export PATH

typeset -U elimina entradas duplicadas en arrays. Esto hace que la carga repetida sea más segura, aunque los archivos de inicio aún deben evitar tareas innecesarias.

Usa .zshrc para el estado interactivo

# ~/.zshrc
setopt auto_cd hist_ignore_all_dups share_history

autoload -Uz compinit
compinit

alias ll='ls -lah'
bindkey -e

Alias, widgets de completación, mapeos de teclas, prompts y ganchos de cambio de directorio pertenecen al shell interactivo que los utiliza.

Los gestores de versión trascienden los límites simples de los archivos

El consejo de “colocar los gestores de versión en .zprofile porque son lentos” no es fiable. Un gestor de versión puede generar varios tipos de código:

  • una ruta estática o variable raíz
  • una ruta de shim de comando necesaria para procesos hijos
  • definiciones de completaciones
  • funciones del shell que modifican el shell actual
  • ganchos de cambio de directorio para cambiar automáticamente de versión

Las partes interactivas deben existir en todo shell interactivo, incluido uno anidado zsh iniciado desde un editor. Por ello, la documentación actual de fnm coloca este gancho en .zshrc:

eval "$(fnm env --use-on-cd --shell zsh)"

De forma similar, la documentación actual de pyenv incluye toda la inicialización interactiva en .zshrc:

export PYENV_ROOT="$HOME/.pyenv"
[[ -d $PYENV_ROOT/bin ]] && path=("$PYENV_ROOT/bin" $path)
eval "$(pyenv init - zsh)"

Pyenv documenta un modo más restringido pyenv init --path para la configuración de shim-path, pero el modo completo pyenv init también instala funciones de completado y de shell. Antes de dividir una herramienta, se debe examinar su documentación actual y los resultados generados.

Si el tiempo de inicio es lento, hay que medirlo antes de pasar el código a un modo en el que ya no funcione.

No cargar todo el perfil desde .zshrc

Una solución común multiplataforma es:

# Avoid this blanket coupling.
source ~/.zprofile

Esto convierte las acciones exclusivas para el inicio de sesión en acciones específicas para cada shell interactivo, lo que puede provocar la repetición del inicio del agente, el acceso al keychain, la generación de salida o modificaciones en rutas.

Si tanto los shells interactivos de inicio de sesión como los que no lo son necesitan un conjunto reducido de exportaciones estáticas, se debe extraer un fragmento idempotente y cargarlo de forma intencionada:

# ~/.config/zsh/environment.zsh
typeset -U path PATH
path=("$HOME/.local/bin" $path)
export PATH EDITOR=nvim VISUAL=nvim
# ~/.zprofile
source "$HOME/.config/zsh/environment.zsh"
# ~/.zshrc
if [[ ! -o login ]]; then
  source "$HOME/.config/zsh/environment.zsh"
fi

# Interactive-only configuration follows.

Este patrón mantiene los datos compartidos separados de los efectos secundarios relacionados con el inicio de sesión. Otra opción válida es configurar de manera consistente el terminal o el gestor de sesiones, en lugar de soportar ambos modos.

Diagnosticar el shell que es lento o carece de estado

Se debe reproducir cada modo directamente:

zsh -lic 'print "login interactive"'
zsh -ic  'print "non-login interactive"'
zsh -lc  'print "login non-interactive"'
zsh -c   'print "non-login non-interactive"'

Es necesario medir el modo que realmente utilizan los usuarios:

time zsh -lic exit
time zsh -ic exit

Cuando la fuente sea incierta, se debe rastrear la ejecución de archivos y líneas:

PS4='%N:%i> ' zsh -xlic exit

El rastreo debe ejecutarse en una cuenta de prueba limpia o inspeccionarse antes de compartirlo: los comandos de inicio pueden expandir tokens y otros valores sensibles.

En caso de que falte un ejecutable, se deben examinar tanto el modo como la ruta correspondiente:

print -r -- "interactive=$options[interactive] login=$options[login]"
print -l -- $path
whence -va python node uv

Conclusión

La distinción relevante no es “entorno versus alias”, sino estado exclusivo para el inicio de sesión versus estado interactivo, sumado a esa pequeña cantidad de elementos que realmente deben afectar a todos los procesos de Zsh.

Es preciso confirmar las opciones del shell, mantener los archivos de inicio en silencio y colocar cada gancho generado donde estén presentes todas sus características requeridas. De este modo, la configuración resulta portable entre aplicaciones de terminal, sin pretender que macOS y Linux tengan un único modo de inicio fijo.
