LLMs locales en macOS: Ollama, LM Studio, llama.cpp, MLX y Apple Silicon

Muchos prompts cotidianos no requieren una API remota. Apple Silicon permite ejecutar modelos de lenguaje útiles de forma local, ya que el CPU y la GPU comparten un único pool de memoria, aunque el archivo del modelo solo representa una parte del presupuesto de memoria disponible.

La elección principal en esta guía depende de la herramienta que rodea al modelo. Ollama, LM Studio, llama.cpp y MLX-LM tienen funcionalidades similares, pero ofrecen distintos niveles de control: un servicio local gestionado, exploración desde escritorio, ejecución directa de archivos GGUF o uso de Python nativo para Apple. Primero elija el modelo según la calidad del resultado deseado, y luego seleccione la herramienta según la interfaz y los recursos que necesite.

En resumen: utilice Ollama para un servicio local gestionado, LM Studio para explorar modelos desde escritorio y acceder a sus APIs locales, llama.cpp para controlar directamente la ejecución de archivos GGUF, y MLX-LM para experimentar con Python nativo para Apple. Ninguna opción es necesariamente la más rápida. Realice pruebas de rendimiento con el modelo específico, el nivel de cuantización, la longitud del contexto y la carga de trabajo, teniendo en cuenta el espacio de memoria restante.

Comience definiendo el límite de memoria

El tamaño bruto de los pesos cuantizados es solo el primer factor a considerar:

peak memory ≈ model weights
            + KV cache
            + runtime workspace
            + multimodal components
            + application and OS memory

La longitud del contexto, el tipo de datos del caché, las solicitudes paralelas y la arquitectura del modelo también influyen en el consumo de memoria. Un modelo de 7 u 8 mil millones de parámetros cuantizado a cuatro bits puede seguir resultando insuficiente en una Mac de 8 GB, ya que el sistema operativo no puede asignar toda la memoria instalada al proceso en ejecución.

Durante las pruebas, utilice Activity Monitor o las métricas proporcionadas por la propia aplicación. Deje suficiente margen para evitar sobrecargas de memoria y uso del swap; un modelo que se cargue pero obligue al sistema a recurrir constantemente al swap no es adecuado para uso interactivo.

También sea preciso distinguir entre inferencia local y operación sin conexión. Los prompts pueden permanecer en la máquina mientras la aplicación accede a la red para descargar modelos, actualizaciones o funciones adicionales. Descargue primero los archivos necesarios, desconecte la red y verifique el flujo de trabajo si se requiere operar sin conexión.

Se trata de una tabla de responsabilidades, no de una clasificación por velocidad. Varias herramientas pueden utilizar kernels o formatos relacionados, y el rendimiento puede variar según el soporte de modelos y las versiones disponibles.

Ollama: servicio local gestionado

Ollama se encarga de descargar modelos, gestionar plantillas, controlar el ciclo de vida de los procesos y ofrecer una API en localhost. Resulta útil cuando el código de la aplicación debe apuntar a un servicio local estable en lugar de depender de parámetros de inferencia propios.

ollama pull <model>
ollama run <model>

curl http://localhost:11434/api/chat \
    -H 'Content-Type: application/json' \
    -d '{
      "model": "<model>",
      "messages": [{"role": "user", "content": "Explain unified memory."}],
      "stream": false
    }'

Se recomienda inspeccionar el manifiesto del modelo y la configuración de contexto en lugar de asumir que un nombre breve de biblioteca corresponde a un checkpoint inmutable. Es necesario fijar o registrar el artefacto exacto para realizar evaluaciones.

Ollama sacrifica cierta visibilidad a nivel bajo en beneficio de la comodidad en el manejo del ciclo de vida. Cuando sea necesario controlar directamente un archivo GGUF, una plantilla de chat, una configuración de caché o una nueva funcionalidad del backend, conviene recurrir a llama.cpp u otro entorno de ejecución.

LM Studio: exploración en escritorio e APIs locales

LM Studio es adecuado cuando la exploración de modelos, la carga de configuraciones, la inspección de chats y las evaluaciones realizadas por humanos de forma simultánea deben integrarse en un mismo flujo de trabajo en escritorio. Su servidor admite SDK nativos y puntos de conexión compatibles.

El uso actual del SDK en Python se presenta de la siguiente manera:

import lmstudio as lms


with lms.Client() as client:
    model = client.llm.model("<downloaded-model-key>")
    response = model.respond("Write one sentence about local inference.")
    print(response)

Se puede iniciar la API local desde la pestaña de Desarrollador o mediante:

lms server start

LM Studio puede funcionar en localhost o en una red local y soporta tokens de API. Es preferible mantenerlo en modo loopback a menos que se requiera acceso remoto; al vincularse a la red, un modelo destinado únicamente al uso local se convierte en un servicio que necesita autenticación, políticas de firewall y una configuración segura de herramientas.

llama.cpp: ejecución directa de archivos GGUF

llama.cpp constituye la opción de referencia cuando el formato del modelo es GGUF y se desea observar directamente los límites del entorno de ejecución. Este proyecto admite Apple Metal, además de CPU y otros backends de hardware.

brew install llama.cpp

# Download through the Hugging Face integration and select a quantization.
llama-cli -hf <publisher>/<gguf-repository>:Q4_K_M

# Or start an OpenAI-compatible local server.
llama-server -hf <publisher>/<gguf-repository>:Q4_K_M

La ruta -hf disponible en el repositorio permite descargar un proyector multimodal correspondiente si está disponible. La compatibilidad con modelos, las plantillas y los parámetros de la CLI cambian con frecuencia, por lo que es recomendable fijar una versión conocida y conservar la orden de ejecución junto con el registro de la evaluación realizada.

Elija llama.cpp cuando el objetivo sea un control directo, no porque un enfoque “a nivel más bajo” implique automáticamente mayor velocidad. Las herramientas gestionadas suelen ofrecer valores predeterminados adecuados; sin embargo, utilizar parámetros directos también puede reducir el rendimiento.

MLX-LM: desarrollo en Python nativo para Apple

MLX-LM se basa en el marco de arrays MLX de Apple. Permite tareas como generación de texto, interacción por chat, conversión de formatos, cuantización y ajuste fino de parámetros para modelos compatibles.

uv add mlx-lm
uv run mlx_lm.generate \
    --model mlx-community/<compatible-model> \
    --prompt "Explain Metal acceleration in one paragraph."

Python expone directamente el modelo y el tokenizador:

from mlx_lm import generate, load


model, tokenizer = load("mlx-community/<compatible-model>")
messages = [{"role": "user", "content": "Give one local-LLM benchmark rule."}]
prompt = tokenizer.apply_chat_template(
    messages,
    tokenize=False,
    add_generation_prompt=True,
)
print(generate(model, tokenizer, prompt=prompt, max_tokens=80))

El servidor HTTP de MLX-LM está documentado como un servidor de desarrollo con controles de seguridad básicos, y no como un servicio para producción. Úselo para pruebas locales o colóquelo delante de una capa de aplicación con validaciones adecuadas.

Un benchmark preciso tarda menos tiempo que una descarga defectuosa

Pruebe la misma familia de checkpoints y niveles de cuantización comparables siempre que los formatos lo permitan. Utilice un conjunto pequeño de prompts que incluya:

  • un prompt interactivo breve
  • un prompt largo similar al contexto esperado
  • salida estructurada o llamadas a herramientas si la aplicación las requiere
  • una longitud representativa de la generación
  • una solicitud repetida para diferenciar entre carga inicial y inferencia posterior

No se debe comparar un modelo de 4 bits de una herramienta con uno de precisión completa de otra, atribuyendo la diferencia al tiempo de ejecución.

Lista de verificación de seguridad y privacidad

  1. Vincular las APIs a loopback a menos que sea necesario acceder a la red.
  2. Incluir autenticación antes de exponerla a la red local.
  3. Tratar los archivos de modelos como artefactos de terceros; registrar fuente, versión, licencia y hash.
  4. Evitar ejecutar código de modelo personalizado sin revisión previa.
  5. Verificar si las funciones opcionales de documentos, herramientas, actualizaciones o análisis realizan llamadas a la red.
  6. No dar por sentado que la generación local hace seguros los documentos recuperados, los registros o los efectos secundarios de la herramienta.

Conclusión

La opción adecuada no es “la mejor app de LLM para Mac”. Se trata del conjunto más reducido que ofrece la interfaz de control necesaria para tu flujo de trabajo. Ollama gestiona un servicio, LM Studio gestiona un bucle de exploración en escritorio, llama.cpp permite ejecutar modelos en formato GGUF, y MLX-LM ofrece Python nativo para Apple.

Se debe asignar a cada candidato la misma tarea, contexto y límite de memoria. El resultado será más fiable que los mitos relacionados con el hardware o una tabla estática de calificaciones, y además será fácil de reevaluar cuando cambien las herramientas.
