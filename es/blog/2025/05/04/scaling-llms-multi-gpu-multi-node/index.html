Escalar LLMs con paralelismo multi-GPU y multinodo

Viacheslav Dubrov

2025-05-04 · Actualizado 2026-07-15 · 11 min · Ingeniería de modelos · Infraestructura de IA

Traducción automática Este artículo se tradujo automáticamente a partir de la versión original en inglés.

Las cargas de trabajo con modelos grandes superan los límites de una sola GPU por distintos motivos. Un trabajo de entrenamiento puede quedarse sin memoria por el estado del optimizador. Otro puede hacerlo por las activaciones de secuencias largas. Aunque un modelo quepa, quizá no alcance el objetivo de throughput. Cada problema requiere una partición y un patrón de comunicación diferentes.

Este es un recorrido práctico por las principales estrategias de paralelismo y las restricciones que las condicionan, basado en la Ultra-Scale Playbook de Hugging Face. El objetivo es mostrar qué aporta cada partición, qué comunica y cuándo resulta necesario combinarlas.

TL;DR. El paralelismo de datos replicado aporta throughput de entrenamiento cuando una réplica cabe en una GPU. El fully sharded data parallelism particiona el estado del modelo, pero añade all-gathers de parámetros y reduce-scatters de gradientes. El tensor, pipeline, contexto y expert parallelism dividen, respectivamente, las operaciones de las capas, la profundidad, la secuencia y las capas mixture-of-experts (MoE). Combínalos solo después de identificar la restricción dominante de memoria o comunicación.

Esta guía presupone que tienes soltura con la retropropagación, las capas Transformer y un bucle de entrenamiento estándar en PyTorch.

Empieza con dos presupuestos de memoria

El entrenamiento y la inferencia no tienen la misma huella de memoria.

training peak ≈ parameters
              + gradients
              + optimizer state
              + saved activations
              + temporary buffers
              + communication buffers
              + allocator headroom

inference peak ≈ resident weights
               + key/value (KV) cache
               + runtime workspace
               + communication buffers
               + allocator headroom

Un modelo de 70.000 millones de parámetros tiene un límite inferior decimal de 140 GB solo para los pesos en BF16. Esta cifra dice poco sobre el entrenamiento, donde pueden dominar los gradientes, el estado del optimizador, los pesos maestros y las activaciones. Tampoco dimensiona el serving, donde importan la política de caché, la longitud de secuencia, la concurrencia del batch y la cuantización.

Perfila la arquitectura exacta, la precisión, la longitud de secuencia, el micro-batch, el optimizador, la política de checkpointing y el runtime. Registra la memoria máxima asignada y reservada, los tokens por segundo, el tiempo en kernels y el tiempo expuesto en collectives.

El alivio de memoria no es un multiplicador fijo. Depende del grado de sharding, de qué elementos sigan replicados, del estado transitorio sin shard, de la política de activaciones, del padding, del desequilibrio y de los buffers.

Paralelismo de datos replicado: throughput sin aumentar la capacidad

El paralelismo de datos replicado, normalmente llamado distributed data parallel, mantiene una réplica completa del entrenamiento en cada rank. La documentación de DistributedDataParallel de PyTorch describe este modelo de réplica y sincronización de gradientes. Cada rank procesa un micro-batch diferente y los gradientes se sincronizan antes del paso del optimizador.

Úsalo cuando todo el estado del entrenamiento quepa con margen suficiente y el batch global pueda crecer o el gradient accumulation pueda ajustarse. Sus principales ventajas son una semántica sencilla y una implementación madura que solapa el cálculo de backward con la reducción de gradientes agrupados en buckets.

Añadir ranks puede perjudicar el rendimiento cuando el batch local se vuelve demasiado pequeño. También puede hacerlo cuando la red no consigue ocultar el all-reduce o se producen bloqueos en la entrega de datos. El batch de optimización deseado quizá no escale.

Fully sharded data parallelism: memoria de estado a cambio de collectives

El fully sharded data parallelism almacena shards de parámetros, gradientes y optimizador distribuidos entre un grupo. El artículo de ZeRO describe este patrón de sharding del estado, y la API FSDP2 de PyTorch lo implementa. Los parámetros de una capa se reúnen mediante all-gather para el cálculo y pueden volver a distribuirse después. Los gradientes se devuelven a sus propietarios mediante reduce-scatter.

La documentación actual de PyTorch distingue la API fully_shard en fully sharded data parallelism versión 2 (FSDP2) del wrapper FullyShardedDataParallel más antiguo. FSDP2 agrupa la comunicación por los módulos a los que se aplica fully_shard y recomienda aplicarlo de abajo arriba para que los grupos de capas puedan solapar comunicación y cálculo.

from torch.distributed.fsdp import fully_shard

# Apply bottom-up: each block becomes a communication group.
for block in model.transformer.blocks:
    fully_shard(block)

# Shard remaining root parameters such as embeddings and output projection.
fully_shard(model)

# Construct the optimizer after parameters have become sharded distributed tensors (DTensors).
optimizer = AdamW(model.parameters(), lr=learning_rate)

Este es un esquema estructural, no un launcher completo. Los device meshes, la mixed precision, el checkpointing, la inicialización, el estado del optimizador y los distributed checkpoints deben encajar con el stack de entrenamiento.

El sharding resulta atractivo cuando el estado del modelo es la restricción dominante y el cálculo de las capas puede ocultar suficiente tráfico de collectives. Puede ser un mal intercambio para modelos pequeños, enlaces lentos, capas diminutas o layouts cuyo grupo de shards atraviese el límite de topología equivocado.

Tensor parallelism: particionar las operaciones de las capas

El tensor parallelism particiona el álgebra lineal dentro de una capa. Algunos ejemplos son las proyecciones column-parallel y row-parallel. La guía de paralelismo de NVIDIA documenta esta división a nivel de capa. Los resultados parciales requieren collectives dentro de los bloques Transformer, por lo que la latencia y el ancho de banda importan repetidamente durante los pases forward y backward.

Úsalo cuando una capa o sus activaciones no quepan, o cuando las matmuls sean lo bastante grandes como para que los kernels particionados superen a un único rank. Asigna el grupo de tensor parallelism al dominio de comunicación más rápido disponible y mide después. Un grado elevado de tensor parallelism puede reducir cada matriz local hasta que disminuya la eficiencia de los kernels mientras crece el coste de los collectives.

El sequence parallelism suele combinarse con tensor parallelism para evitar replicar parte del trabajo sobre las activaciones. Es distinto del context parallelism, que opera sobre la secuencia de entrada completa del modelo.

Pipeline parallelism: particionar la profundidad y el tiempo de planificación

El pipeline parallelism coloca distintos grupos de capas en diferentes etapas y envía activaciones entre ellas. Los micro-batches mantienen las etapas ocupadas de forma concurrente. El artículo de GPipe utiliza esta planificación para redes neuronales gigantes.

Alivia el estado del modelo por etapa y puede reducir el volumen de comunicación que atraviesa un límite más lento frente a los collectives de tensor parallelism por capa. Sus costes son las burbujas, las transferencias de activaciones, el desequilibrio entre etapas, una planificación más compleja y una recuperación y un checkpointing más difíciles.

Para una planificación sencilla al estilo de GPipe con p etapas y m micro-batches, la fracción idealizada de burbuja del forward es aproximadamente:

(p - 1) / (m + p - 1)

Las planificaciones reales pueden usar variantes one-forward/one-backward, interleaving o zero-bubble, y el coste desigual de las capas puede dominar la fórmula. Elige los límites entre etapas a partir del tiempo y la memoria medidos, no de un número igual de capas.

Context parallelism: particionar las activaciones de secuencias largas

El context parallelism distribuye la dimensión de secuencia. La documentación de context parallelism de NVIDIA describe la división de la secuencia y el intercambio de key/value necesario para la atención. Cada rank posee un shard de la secuencia, mientras que la atención intercambia la información necesaria para conservar la semántica de contexto completo. Las implementaciones pueden usar anillos punto a punto, all-gather, all-to-all o combinaciones jerárquicas.

Reduce la memoria de activaciones en el entrenamiento con contexto largo, pero replica los pesos dentro del grupo de contexto e introduce comunicación de atención. El beneficio depende del tipo de atención, la máscara causal, la longitud de secuencia, la recomputación y la forma en que los grupos de contexto se combinan con los grupos de tensor y data parallelism.

No lo selecciones a partir de un umbral universal de 8K, 32K o 100K. Perfila la memoria de activaciones y la comunicación de atención en la arquitectura real.

Expert parallelism: solo para una arquitectura MoE

El expert parallelism distribuye los expertos en las capas mixture-of-experts. La guía de paralelismo de NVIDIA documenta esta colocación de expertos y su combinación con otras dimensiones de paralelismo. El router envía las representaciones de los tokens a los expertos seleccionados y combina sus resultados. Solo los expertos seleccionados calculan para cada token, pero el conjunto total de pesos de los expertos sigue requiriendo almacenamiento y una estrategia de placement para serving.

El expert parallelism no es un interruptor de optimización para un modelo dense. Forma parte de una arquitectura MoE. Entre sus aspectos críticos están el balanceo de carga, los límites de capacidad, el all-to-all de tokens, los tokens descartados o rellenados con padding, las pérdidas auxiliares y el desequilibrio entre fallos. Monitoriza los tokens por experto, la entropía del routing, el desbordamiento de capacidad, el tiempo de comunicación y la calidad por ruta.

Compón el layout a partir de la topología

Los sistemas de entrenamiento grandes combinan dimensiones. El world size total suele seguir el producto de los tamaños de los grupos de data parallelism (DP), tensor parallelism (TP), pipeline parallelism (PP) y context parallelism (CP). La guía de paralelismo de NVIDIA muestra este producto:

world size = DP × TP × PP × CP

El expert parallelism puede compartir dimensiones o integrarse en ellas de forma distinta, así que verifica el mesh compatible con el framework en lugar de multiplicar a ciegas.

Construye el layout en este orden:

  1. Dibuja los dominios de comunicación: enlaces GPU a GPU, switches, límites de non-uniform memory access (NUMA), fabric entre nodos, oversubscription y ruta de almacenamiento.
  2. Coloca los collectives frecuentes y sensibles a la latencia, normalmente TP, en el dominio adecuado más rápido.
  3. Elige grupos de FSDP o de DP replicado a partir de la capacidad y el ancho de banda restantes.
  4. Añade PP cuando la colocación por profundidad o el tráfico entre dominios lo justifique, equilibrando el tiempo y la memoria medidos de cada etapa.
  5. Añade CP solo por la restricción de secuencia, y expert parallelism (EP) solo por la topología de expertos del modelo.
  6. Confirma la divisibilidad de cabezas, dimensiones ocultas, capas, expertos, batch y secuencia para el mesh candidato.
  7. Evalúa varios meshes válidos. Las heurísticas conscientes de la topología eligen candidatos, no ganadores.

Dos clústeres con el mismo número de GPUs pueden preferir layouts distintos porque difieren el ancho de banda de los enlaces, la jerarquía de switches, la conexión de las CPUs y la congestión de red.

El entrenamiento y el serving requieren decisiones distintas

La inferencia normalmente no utiliza gradientes ni el estado del optimizador, por lo que los layouts de entrenamiento basados en FSDP no se trasladan automáticamente.

Para serving, pregunta:

  • ¿Cabe una réplica con los pesos, el KV cache, el workspace y la concurrencia objetivo?
  • ¿El throughput mejora más con varias réplicas independientes o haciendo sharding de una sola réplica?
  • ¿El TP reduce suficientemente la presión sobre los pesos y la caché por rank como para compensar la comunicación por capa?
  • ¿El PP está implementado de forma eficiente para el modelo y el scheduler de peticiones?
  • ¿Cómo afectan el prefill y el decode al cálculo, al ancho de banda de memoria y al interconnect de forma diferente?
  • ¿Qué ocurre con la latencia de cola cuando las peticiones tienen longitudes distintas de prompt y de salida?

Evalúa el servidor completo con el scheduler, la cuantización, la distribución del contexto, la política de batching y la forma del tráfico. Los tokens por segundo del entrenamiento no permiten predecir el tiempo hasta el primer token ni la latencia entre tokens del serving.

Mide un layout de escalado de forma rigurosa

Para cada candidato, registra:

  • identidad del modelo, el código, el runtime, los kernels y la topología
  • batch global y local, distribución de secuencias y número de tokens
  • memoria máxima por categoría, cuando esté disponible
  • tokens útiles por segundo y utilización de operaciones de coma flotante del modelo (FLOP), cuando se calculen de forma coherente
  • tiempo expuesto en operaciones all-reduce, all-gather, reduce-scatter, all-to-all y punto a punto
  • bloqueos de entrada, tiempo de checkpoint, comportamiento tras reinicios y distribución de stragglers
  • paridad de la loss de entrenamiento o de las salidas del serving respecto a la baseline

Compara de forma deliberada el escalado fuerte y el débil. El strong scaling mantiene constante el trabajo total mientras aumenta el número de ranks. El weak scaling mantiene constante el trabajo por rank, por lo que el trabajo total crece con el número de ranks. Un porcentaje etiquetado como «eficiencia de escalado» no tiene sentido sin conocer ese denominador y la baseline.

Conclusión

El paralelismo es un mapeo entre un cuello de botella medido, una dimensión del tensor y un patrón de comunicación. La replicación, el sharding, la partición de capas, el staging, la partición de secuencias y el routing de expertos alivian restricciones diferentes y crean modos de fallo distintos.

Haz inventario de la carga de trabajo, dibuja la topología, genera meshes válidos y perfílalos. El layout ganador es el que cabe con margen suficiente y minimiza la comunicación expuesta para el trabajo que realmente ejecutas.
