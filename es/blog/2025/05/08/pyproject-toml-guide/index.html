pyproject.toml Guía: Empaquetado en Python, dependencias y configuración de herramientas

Los proyectos antiguos en Python suelen distribuir la configuración en setup.py, setup.cfg, archivos de requisitos, MANIFEST.in, además de archivos separados para las herramientas de desarrollo. pyproject.toml proporciona un lugar único para todo esto, aunque no reemplaza todos los archivos del proyecto ni convierte cada sección en parte de un estándar único.

Esta guía explora el archivo desde la configuración de compilación hasta los metadatos del proyecto y los parámetros de las herramientas. La forma más sencilla de mantenerlo comprensible es dividirlo en cuatro responsables: lo que compila el proyecto, lo que publica el proyecto, lo que necesitan los colaboradores localmente y lo que configuran las herramientas individuales.

En resumen: Utiliza [build-system] para el backend que genera la distribución, [project] para los metadatos publicados y los requisitos en tiempo de ejecución, [dependency-groups] para los entornos de desarrollo no publicados, y [tool.*] únicamente cuando la documentación de esa herramienta así lo indique. Una declaración de dependencia no equivale a un archivo de bloqueo.

Un archivo, cuatro responsables

Tres estándares de empaquetado han definido la estructura básica:

  • PEP 518 establece los requisitos del sistema de compilación.
  • PEP 621 define los metadatos del proyecto.
  • PEP 735 define los grupos de dependencias no publicados.

Los autores de herramientas también pueden reservar un espacio de nombres bajo [tool]. Esa zona es convencional, no universal: cada herramienta define sus propias claves y comportamientos.

A continuación, se muestra una pequeña biblioteca empaquetada:

[build-system]
requires = ["hatchling>=1.26"]
build-backend = "hatchling.build"

[project]
name = "weather-client"
version = "0.1.0"
description = "A small weather API client"
readme = "README.md"
requires-python = ">=3.11"
dependencies = [
  "httpx>=0.27",
]

[project.optional-dependencies]
cli = ["rich>=13"]

[project.scripts]
weather = "weather_client.cli:main"

[dependency-groups]
test = ["pytest>=8", "pytest-cov>=5"]
lint = ["ruff>=0.12"]

[tool.pytest.ini_options]
testpaths = ["tests"]

[tool.ruff]
line-length = 100
target-version = "py311"

Cada lista de dependencias responde a una pregunta distinta. Esa distinción constituye el eje central del archivo.

[build-system]: cómo el código fuente se convierte en una distribución

Un frontend de compilación como python -m build, pip o uv invoca a un backend de compilación. Este último decide cómo el árbol de código fuente se transforma en un sdist o wheel y qué archivos forman parte de dichos artefactos.

[build-system]
requires = ["hatchling>=1.26"]
build-backend = "hatchling.build"

requires contiene las dependencias necesarias para ejecutar el backend en su entorno de compilación aislado. No corresponde a la lista de dependencias en tiempo de ejecución del paquete.

Debes declarar un sistema de compilación cuando el proyecto genere una distribución o necesite instalar su propio código como paquete. Un proyecto que no sea un paquete puede seguir utilizando pyproject.toml; de hecho, PEP 735 permite incluso un archivo que contenga únicamente grupos de dependencias. Los gestores de entorno difieren en cómo tratan a los proyectos sin sistema de compilación, por lo que hay que tomar esa decisión de forma deliberada.

Elige el backend según los requisitos de compilación:

  • Necesidades de estructura pura en Python y selección de archivos.
  • Extensiones compiladas o sistemas de compilación externos.
  • Requisitos de versión dinámica o archivos generados.
  • Comportamiento de instalación editable.
  • Madurez del backend en el pipeline de lanzamientos.

Copia la tabla recomendada actual del backend de su documentación. No añadas wheel a los requisitos de compilación por costumbre; el backend indica él mismo qué necesita.

[project]: información que reciben los consumidores de metadatos

La tabla [project] describe la distribución: su nombre, versión, compatibilidad con Python, dependencias en tiempo de ejecución, puntos de entrada y otros metadatos de índice.

[project]
name = "weather-client"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = ["httpx>=0.27"]

Los especificadores de dependencias son restricciones para un resolutor, no una captura de un entorno concreto. Forman parte de los metadatos de los archivos wheel y sdist, de modo que los instaladores posteriores pueden combinarlos con los requisitos de otros paquetes.

Los extras constituyen una interfaz pública de instalación

[project.optional-dependencies] define los extras que los usuarios pueden solicitar:

[project.optional-dependencies]
cli = ["rich>=13"]
postgres = ["psycopg[binary]>=3.2"]

Un usuario puede instalar weather-client[cli]. Dado que los nombres y requisitos de los extras se publican, deben considerarse como capacidades del producto. No se debe utilizar un extra denominado dev únicamente para albergar las herramientas de todos los colaboradores.

Los puntos de entrada vinculan los comandos instalados con Python

[project.scripts]
weather = "weather_client.cli:main"

Tras instalar la distribución, el entorno expone weather, el cual importa y llama a weather_client.cli:main. Se deben probar los comandos desde un archivo wheel compilado, y no solo desde la raíz del repositorio; es el wheel lo que reciben los usuarios.

[dependency-groups]: entornos locales no publicados

PEP 735 permite describir grupos de dependencias para entornos de desarrollo o no relacionados con paquetes, sin publicarlos como metadatos de paquete.

[dependency-groups]
test = ["pytest>=8", "pytest-cov>=5"]
lint = ["ruff>=0.12"]
dev = [
  { include-group = "test" },
  { include-group = "lint" },
]

Este es el límite adecuado para pruebas, herramientas de linting, generadores de documentación y otras herramientas similares de colaboradores. También resulta útil para aplicaciones o cuadernos de notas que no generan una distribución.

Los grupos de dependencias son datos estandarizados, pero las interfaces de instalación siguen variando. Es necesario verificar cómo el gestor de entornos seleccionado los instala, bloquea y resuelve. PEP 735 no define una interfaz de línea de comandos universal.

[tool.*]: configuración propiedad de una herramienta

Las tablas de herramientas no comparten un esquema uniforme:

[tool.pytest.ini_options]
addopts = "-ra"
testpaths = ["tests"]

[tool.ruff]
line-length = 100

Solo se debe utilizar una tabla [tool.*] si la propia herramienta lo documenta. Algunas configuraciones siguen correspondiendo a archivos independientes porque otro ecosistema las consume, porque el archivo requiere un formato distinto, o porque su estructura resulta más clara por separado. pyproject.toml sirve como punto de coordinación, no como obligación de centralizar todo.

Las declaraciones, archivos de bloqueo y archivos de requisitos resuelven problemas diferentes

La causa más frecuente de confusión radica en tratar cada artefacto de dependencia como una fuente de verdad competidora.

ArtefactoPropósito principalContenido típico
[project.dependencies]Contrato de ejecución publicadoRequisitos directos y rangos compatibles
[project.optional-dependencies]Capacidades opcionales publicadasExtras dirigidos a los usuarios
[dependency-groups]Entornos locales no publicadosGrupos para pruebas, linting, documentación o aplicaciones
Archivo de bloqueoReproducir un entorno ya resueltoVersiones exactas, fuentes y metadatos de resolución
requirements.txtEntrada de instalación compatible con pipRequisitos además de opciones, restricciones, URLs o hashes específicos de pip

Una biblioteca suele publicar restricciones y pruebas compatibles para un rango determinado. Una aplicación, por su parte, normalmente guarda el archivo de bloqueo del gestor de entornos. Las versiones exactas deben incluirse en el artefacto de despliegue resultante, y no de forma arbitraria en la metadatos públicos de la biblioteca.

Se debe mantener un archivo de requisitos cuando una integración requiera el formato o funcionalidades específicas de pip. Si un proyecto gestionado con uv necesita uno, es preferible exportarlo a partir del archivo de bloqueo en lugar de mantener dos conjuntos independientes de dependencias:

uv export --format requirements.txt --output-file requirements.txt

La exportación corresponde a un resultado de compatibilidad derivado. El archivo de bloqueo sigue siendo la fuente oficial para ese flujo de trabajo.

Una migración que preserva el comportamiento

No se debe comenzar eliminando setup.py o requirements.txt. Primero, es necesario clasificar la función de cada archivo existente.

  1. Inventario de la lógica de compilación, metadatos, requisitos en tiempo de ejecución, elementos adicionales, entornos de desarrollo, configuraciones de herramientas, datos de paquetes y puntos de entrada.
  2. Elegir un backend capaz de reproducir la inclusión de archivos, los artefactos compilados y las instalaciones editables actuales.
  3. Mover los metadatos estáticos publicados a [project]; los campos verdaderamente dinámicos deben quedar explícitos.
  4. Transferir los requisitos exclusivos para colaboradores a [dependency-groups], y no a los elementos adicionales públicos.
  5. Mover las configuraciones de herramientas únicamente allí donde dicha herramienta soporte semánticas equivalentes.
  6. Generar tanto un sdist como un wheel, inspeccionar su contenido e instalar el wheel en un entorno limpio.
  7. Ejecutar los puntos de entrada, las pruebas, las comprobaciones de importación y el proceso real de despliegue.
  8. Eliminar la configuración antigua solo una vez que los artefactos y el comportamiento coincidan.

MANIFEST.in puede seguir siendo necesario en algunos diseños de setuptools, y un pequeño setup.py puede seguir siendo válido para comportamientos de compilación programáticos. La modernización consiste en un cambio de responsabilidad, no en una competencia por eliminar archivos.

Un flujo de trabajo actual con uv

uv distingue entre aplicaciones y bibliotecas al crear un proyecto:

# Non-library application template
uv init weather-app

# Packaged library with a src layout and build system
uv init --lib weather-client

uv init genera los archivos del proyecto. La primera operación realizada en el proyecto, como uv run, uv sync o uv lock, crea el archivo de bloqueo y el .venv persistente según sea necesario.

cd weather-client
uv add httpx
uv add --group test pytest pytest-cov
uv run pytest
uv build

Actualmente, uv coloca los requisitos para el desarrollo local en grupos de dependencias estandarizados. Su backend nativo uv_build es una opción para proyectos puramente en Python; las extensiones compiladas requieren alternativas adecuadas como maturin o scikit-build-core.

Conclusión

pyproject.toml resulta claro cuando cada tabla está dirigida a un público específico. El aislamiento de compilación pertenece a [build-system]. El comportamiento publicado pertenece a [project]. Los entornos de colaboradores pertenecen a [dependency-groups]. Los cambios de herramienta corresponden a la herramienta que los define.

Una vez que estos límites están definidos de forma estable, los archivos son más fáciles de revisar, y las migraciones dejan de confundir los metadatos de paquetes con el entorno resuelto de una máquina concreta.
