Razonamiento guiado por esquema en vLLM: Salidas estructuradas con xgrammar y Pydantic

Volver a ejecutar una llamada al LLM no garantiza que el resultado sea JSON válido. El siguiente intento también puede fallar de la misma manera, y las llamadas repetidas incrementan la latencia y los costes.

El Razonamiento Guiado por Esquema (SGR) impone un esquema mientras el modelo genera cada token. Se definen los campos obligatorios mediante Pydantic, y el motor de inferencia bloquea aquellos tokens que violen dicha estructura. Como resultado, las salidas son sintácticamente válidas desde su creación, y no solo tras intentos repetidos.

En resumen. SGR emplea decodificación restringida para ajustar la salida del LLM a un esquema de Pydantic que se controla manualmente. Al combinarlo con el backend xgrammar de vLLM, se obtiene JSON válido en todo momento, con una sobrecarga de latencia prácticamente nula.

¿Qué es el Razonamiento Guiado por Esquema?

El Razonamiento Guiado por Esquema es una técnica descrita por Rinat Abdullin en 2024. En lugar de permitir que el modelo complete el texto libremente (lo cual puede generar inconsistencias o ambigüedades), se le proporciona una plantilla estricta que define:

  • los pasos que debe seguir, de modo que no pueda omitir el análisis;
  • el orden de dichos pasos, para que el razonamiento avance desde los datos hasta la decisión;
  • dónde debe centrar su atención, de forma que la profundidad del análisis sea adecuada en los puntos críticos.

Puede considerarse como una lista de verificación cognitiva que el modelo debe seguir.

Qué controla el esquema

Campos como churn_analysis, margin_math y max_discount_percent especifican claramente las salidas intermedias esperadas. El modelo debe completar la estructura requerida antes de poder devolver la decisión final sobre el descuento.

Esto permite obtener:

  • un razonamiento reproducible en ejecuciones repetidas;
  • salidas auditables, ya que cada paso es inspeccionable;
  • campos intermedios que se pueden evaluar contra un conjunto de datos de prueba;
  • modelos más pequeños que siguen siendo útiles, ya que el esquema impone lo que de otro modo el modelo tendría que aprender por sí mismo;
  • una mejora reportada del 5–10% en la precisión en los cargas de trabajo reales del autor original, aunque esto debe verificarse con los propios datos.

Ingeniería de prompts: persuasión semántica

Please analyze the customer data and output your response as valid JSON
with the following structure: {"discount": <number>, "reason": <string>}
Be careful with the formatting!

Se espera que la comprensión del modelo sobre “generar JSON” supere su tendencia a adoptar un estilo conversacional. Sin embargo, una actualización del modelo, un cambio en la temperatura o un ejemplo diferente pueden invalidar el analizador utilizado.

Cadena de razonamiento: mejor razonamiento, mismo problema de estructura

Let's think step by step:
1. First, I'll analyze the customer's churn risk...
2. Then I'll calculate the margin...
3. Therefore, I recommend a 15% discount.

La cadena de razonamiento mejora la precisión del razonamiento, pero empeora la estructura de la salida. El resultado es prosa impredecible que resulta casi imposible de analizar de forma fiable. Por lo general, es necesario realizar una segunda llamada al modelo para extraer los datos estructurados.

Razonamiento guiado por esquema: cadena de razonamiento estructurada

El Razonamiento guiado por esquema mantiene la idea de la cadena de razonamiento de que el razonamiento intermedio mejora la precisión. Solo formaliza los pasos a seguir:

class PricingLogic(BaseModel):
    # 1. Data Analysis (must complete before decision)
    churn_analysis: str = Field(..., description="Analyze churn_probability")
    financial_analysis: str = Field(..., description="Analyze cart_value and margin")

    # 2. Math Enforcement (explicit calculation)
    margin_math: str = Field(..., description="Calculate: 'Cart $X * Y% = $Z'")

    # 3. Decision Constraint (bounded by prior analysis)
    max_discount_percent: float = Field(..., description="Max allowed discount")

    # 4. Final Output
    offer_code: str
    customer_message: str

El modelo no puede generar max_discount_percent hasta que se hayan completado churn_analysis, financial_analysis y margin_math. El esquema impone el orden de razonamiento.

Patrones de Razonamiento guiado por esquema

El Razonamiento guiado por esquema cuenta con tres patrones básicos que se combinan para crear flujos de trabajo más complejos.

1. En cascada: pasos de razonamiento secuenciales

La en cascada impone un orden específico para el razonamiento. Cada campo debe completarse antes de pasar al siguiente.

from pydantic import BaseModel
from typing import Literal, Annotated
from annotated_types import Ge, Le

class CandidateEvaluation(BaseModel):
    """Evaluate a job candidate with enforced reasoning order."""

    # Step 1: Summarize (forces context awareness)
    brief_candidate_summary: str

    # Step 2: Rate (bounded integer)
    rate_skill_match: Annotated[int, Ge(1), Le(10)]

    # Step 3: Decide (constrained choices)
    final_recommendation: Literal["hire", "reject", "hold"]

Casos adecuados: evaluación de candidatos, clasificación de documentos, análisis de cumplimiento, diagnóstico médico.

El modelo debe escribir brief_candidate_summary antes de poder evaluar, y evaluar antes de poder recomendar. No existe atajo posible.

2. Enrutamiento: una instrucción condicional semántica

El enrutamiento hace que el modelo elija un camino específico entre varias opciones, implementándose mediante tipos Union.

from pydantic import BaseModel
from typing import Literal, Union

class FeatureLookup(BaseModel):
    """Route to database lookup."""
    rationale: str
    tool_name: Literal["fetch_user_features"] = "fetch_user_features"
    user_id: str

class GeneralResponse(BaseModel):
    """Standard response for non-pricing queries."""
    tool_name: Literal["respond"] = "respond"
    content: str

class RouterSchema(BaseModel):
    """The model must pick exactly ONE branch."""
    action: Union[FeatureLookup, GeneralResponse]

Casos adecuados: clasificación de intenciones, selección de herramientas, triaje de soporte técnico, despacho entre múltiples agentes.

El discriminador Literal (tool_name) hace que el modelo elija una única rama y rellene únicamente los campos necesarios para dicha rama.

3. Ciclo: razonamiento repetido con listas

El ciclo obliga al modelo a generar varios elementos, estableciendo límites sobre su cantidad.

from pydantic import BaseModel
from typing import List, Literal, Annotated
from annotated_types import MinLen, MaxLen

class RiskFactor(BaseModel):
    explanation: str
    severity: Literal["low", "medium", "high"]

class RiskAssessment(BaseModel):
    """Generate 2-4 risk factors."""
    factors: Annotated[List[RiskFactor], MinLen(2), MaxLen(4)]

Casos de uso adecuados: evaluación de riesgos, extracción de problemas, llamadas paralelas a herramientas, planificación multietapa.

Los límites definidos por MinLen y MaxLen exigen al menos 2 y como máximo 4 elementos. En combinación con el mecanismo de enrutamiento, esto permite enviar lotes fijos de llamadas a herramientas.

Hacer que SGR funcione: decodificación restringida

Los patrones mencionados anteriormente son simplemente esquemas Pydantic. Lo que los vuelve vinculantes es la decodificación restringida (también conocida como salida estructurada).

La decodificación restringida modifica la fase de generación de tokens. En lugar de permitir que el modelo elija libremente entre sus vocabularios, el motor aplica una máscara gramatical que bloquea aquellos tokens que violarían el esquema. Este proceso tiene lugar en el motor de inferencia, no en el código de la aplicación.

[!TIP] SGR no requiere “modelos de razonamiento” como o1 o DeepSeek-R1. Funciona perfectamente con modelos ajustados mediante instrucciones, y especialmente bien con modelos derivados de aquellos orientados al razonamiento.

Por qué este artículo se centra en vLLM y xgrammar

Algunas razones:

  • vLLM es el motor de inferencia de LLM de código abierto más ampliamente implementado, por lo que lo que se desarrolle aquí se puede adaptar con facilidad.
  • xgrammar está implementado en C++ y añade una latencia prácticamente nula.
  • La API de vLLM es compatible con OpenAI, lo que reduce los costes de migración desde proveedores cloud.
  • xgrammar gestiona esquemas anidados complejos, uniones y estructuras recursivas.

La siguiente sección explica cómo xgrammar aplica efectivamente las restricciones del esquema a nivel de token.

Cómo xgrammar aplica las restricciones de los esquemas

Esta parte merece ser comprendida con precisión, ya que influye en la forma en que se depuran y ajustan los flujos de trabajo SGR.

Dónde tiene lugar el enmascaramiento

xgrammar modifica los logits de salida después del paso forward del modelo y antes de la muestreo. No modifica al modelo en sí; simplemente filtra qué tokens pueden seleccionarse.

Un bucle de inferencia estándar se presenta así:

1. Input tokens → GPU Forward Pass → Logits (probability scores for all ~128K tokens)
2. Logits → Sampling (temperature, top-p, etc.) → Next Token
3. Repeat until done

xgrammar se inserta entre los pasos 1 y 2:

1. Input tokens → GPU Forward Pass → Raw Logits
2. Raw Logits → xgrammar Logits Processor → Masked Logits
3. Masked Logits → Sampling → Next Token (guaranteed valid)
4. Repeat until done

El modelo sigue calculando su distribución de probabilidades completa en la GPU. A continuación, xgrammar se ejecuta en la CPU y aplica una máscara de bits a dichos logits antes del muestreo. Los tokens inválidos tienen sus logits establecidos en -∞, lo que hace que su probabilidad sea exactamente 0 tras aplicar softmax.

Dos fases

xgrammar divide el proceso en tiempo de compilación y tiempo de ejecución, lo que es lo que le confiere rapidez.

Fase 1: compilación de la gramática, una vez por esquema

# This happens once per schema
tokenizer_info = xgr.TokenizerInfo.from_huggingface(tokenizer)
grammar_compiler = xgr.GrammarCompiler(tokenizer_info)
compiled_grammar = grammar_compiler.compile_json_schema(schema_json)

Durante la compilación, xgrammar:

  1. Convierte el JSON Schema en una gramática libre de contexto.
  2. Construye un autómata de empuje hacia abajo (PDA), que es un autómata de estados con pila capaz de manejar estructuras anidadas como {"a": {"b": {"c": ...}}}.
  3. Calcula previamente qué tokens son válidos en cada posición de la gramática. El resultado es el “cache de máscaras de tokens adaptativas”.
  4. Clasifica los tokens como “independientes del contexto” (que pueden almacenarse en caché) o “dependientes del contexto” (que deben verificarse en tiempo de ejecución según el estado de la pila).

[!NOTA] Aproximadamente el 99 % de los tokens resultan ser independientes del contexto y terminan almacenados en caché (artículo de XGrammar). La mayoría de las verificaciones de validez en tiempo de ejecución son simplemente búsquedas en el caché, lo que explica la rapidez de xgrammar.

Fase 2: generación de la máscara en tiempo de ejecución, para cada token

En cada paso de generación:

  1. El GrammarMatcher sigue la posición actual dentro de la gramática.
  2. Consulta la máscara precalculada para los tokens independientes del contexto.
  3. Ejecuta el PDA para analizar los tokens dependientes del contexto restantes.
  4. Combina todos ellos en una máscara binaria final y la aplica a los logits.

¿Por qué autómatas de desplazamiento hacia abajo y no expresiones regulares?

Debido al anidamiento. Una expresión regular (una máquina de estados finitos) no puede coincidir de forma fiable con estructuras como:

{ "user": { "profile": { "settings": { "theme": "dark" } } } }

La parte más complicada son los corchetes de cierre }}}: es necesario recordar cuántos se han abierto. Un autómata de desplazamiento hacia abajo dispone de una pila que registra esto, lo que le permite manejar profundidades de anidamiento arbitrarias. Por eso xgrammar puede aplicar tipos Union, objetos anidados y esquemas recursivos, algo imposible con enfoques basados en expresiones regulares.

Ejemplo concreto: generación de un campo de tipo float

Cuando el modelo genera "max_discount_percent":, xgrammar sabe, gracias al esquema, que a continuación vendrá un float. La máscara:

  • permite (con probabilidad sin cambios): 0, 1, 2, …, 9, ., -
  • bloquea (con probabilidad igual a 0): ", {, [, true, false, null, y el resto del vocabulario de más de 128K elementos.

En el paso forward pass podría asignarse una alta probabilidad a la palabra "fifteen". Tras aplicar la máscara de xgrammar, esa token tiene probabilidad 0. En ese caso, el modelo debe generar dígitos.

¿Por qué “sobrecarga casi nula”?

Tres razones:

  1. Ejecución paralela. El cálculo de la máscara en el CPU se superpone al siguiente paso forward pass en el GPU. Mientras el GPU calcula los logits del token N+1, el CPU calcula la máscara para el token N.
  2. Caché. La mayor parte del trabajo de validación se realiza en tiempo de compilación; en tiempo de ejecución solo hay búsquedas en caché.
  3. Implementación en C++. El camino crítico está escrito en C++, no en Python, y la máscara se aplica directamente a los logits sin pasar por copias adicionales.

En pruebas de rendimiento, xgrammar muestra una sobrecarga prácticamente nula. Además, la generación estructurada puede ser incluso más rápida que la generación sin restricciones, ya que el vocabulario limitado reduce costos de muestreo.

Paso 1: definir los esquemas

# sgr/models/schemas.py
from pydantic import BaseModel, Field
from typing import Literal, Union


# --- Phase 1: Routing (Union for branching) ---
class FeatureLookup(BaseModel):
    """Route to DB lookup if pricing context is needed."""
    rationale: str
    tool_name: Literal["fetch_user_features"] = "fetch_user_features"
    user_id: str


class GeneralResponse(BaseModel):
    """Standard response for non-pricing queries."""
    tool_name: Literal["respond"] = "respond"
    content: str


class RouterSchema(BaseModel):
    action: Union[FeatureLookup, GeneralResponse]


# --- Phase 2: Pricing Logic (Cascade for sequential reasoning) ---
class PricingLogic(BaseModel):
    """
    Strict reasoning topology for dynamic pricing.
    Fields are ordered to enforce the analysis→decision flow.
    """
    # 1. Data Analysis (Reflection)
    churn_analysis: str = Field(...,
        description="Analyze churn_probability (High > 0.7).")
    financial_analysis: str = Field(...,
        description="Analyze cart_value and profit_margin.")

    # 2. Hard Math Enforcement
    margin_math: str = Field(...,
        description="Calculate absolute profit: 'Cart $200 * 0.20 Margin = $40'.")

    # 3. The Decision Constraint
    max_discount_percent: float = Field(...,
        description="Max allowed discount %. NEVER exceed margin.")

    # 4. Final Output
    offer_code: str = Field(..., description="Generated code (e.g. SAVE20).")
    customer_message: str = Field(..., description="The final polite offer text.")

Paso 2: cliente LLM que activa xgrammar

# sgr/utils/llm_client.py
from openai import OpenAI
from pydantic import BaseModel
from typing import TypeVar
import json

T = TypeVar("T", bound=BaseModel)


class LLMClient:
    """Wrapper for vLLM with xgrammar-enforced structured generation."""

    def __init__(self, base_url: str = "http://localhost:8000/v1"):
        self.client = OpenAI(base_url=base_url, api_key="EMPTY")
        self.model = self._get_available_model()

    def _get_available_model(self) -> str:
        """Auto-detect the model running on vLLM server."""
        try:
            models = self.client.models.list()
            if models.data:
                return models.data[0].id
        except Exception:
            pass
        return "Qwen/Qwen2.5-7B-Instruct"

    def run_sgr(self, messages: list[dict], schema_class: type[T]) -> T:
        """Run inference with Schema-Guided Response constraints.

        Uses vLLM's guided_json with xgrammar backend to enforce
        strict schema constraints at the token generation level.
        """
        schema_dict = schema_class.model_json_schema()

        # Enhance system message with schema for model guidance
        enhanced_messages = messages.copy()
        if enhanced_messages and enhanced_messages[0]["role"] == "system":
            schema_json = json.dumps(schema_dict, indent=2)
            enhanced_messages[0] = {
                "role": "system",
                "content": (
                    enhanced_messages[0]["content"]
                    + f"\n\nRespond with JSON matching this schema:\n{schema_json}"
                ),
            }

        # vLLM's guided_json with the xgrammar backend
        completion = self.client.chat.completions.create(
            model=self.model,
            messages=enhanced_messages,
            temperature=0.1,  # Low temp for deterministic reasoning
            extra_body={
                "guided_json": schema_dict,  # Pydantic schema as dict
                "guided_decoding_backend": "xgrammar",  # Hardware-enforced
            },
        )

        raw_response = completion.choices[0].message.content
        return schema_class.model_validate_json(raw_response)

[!NOTA] > guided_json acepta un diccionario basado en JSON Schema. Gracias a guided_decoding_backend: "xgrammar", el LLM solo puede generar tokens que conformen JSON válido según el esquema especificado.

Paso 3: orquestar al agente

# sgr/agent.py
from .models.schemas import PricingLogic, RouterSchema
from .prompts.routing import build_routing_prompt
from .prompts.pricing import build_pricing_context_prompt, ASSISTANT_FETCH_MESSAGE
from .store.hybrid_store import HybridFeatureStore
from .utils.llm_client import LLMClient


def pricing_agent(user_query: str, user_id: str) -> str:
    """Process a pricing query with three-phase SGR workflow."""

    llm = LLMClient()
    feature_store = HybridFeatureStore()

    # Build conversation history
    history = [
        {"role": "system", "content": build_routing_prompt(user_id)},
        {"role": "user", "content": user_query},
    ]

    # --- Phase 1: Routing (Uses RouterSchema) ---
    print(f"🤖 Processing: '{user_query}' for {user_id}")
    decision = llm.run_sgr(history, RouterSchema)
    print(f"📍 Routing decision: {decision.action.tool_name}")

    if decision.action.tool_name == "respond":
        return decision.action.content

    # --- Phase 2: Context Retrieval ---
    if decision.action.tool_name == "fetch_user_features":
        print(f"🔍 Fetching features for {user_id}...")
        context = feature_store.get_user_context(user_id)

        if not context:
            return "Error: User profile not found."

        print(f"   [Data] LTV: ${context.get('user_ltv')} | "
              f"Margin: {context.get('cart_profit_margin', 0) * 100}%")

        # Inject context into conversation
        history.append({"role": "assistant", "content": ASSISTANT_FETCH_MESSAGE})
        history.append({
            "role": "user",
            "content": build_pricing_context_prompt(
                churn_prob=context.get("churn_probability", 0.5),
                cart_val=context.get("current_cart_value", 100),
                margin=context.get("cart_profit_margin", 0.2),
                user_ltv=context.get("user_ltv", 0),
            ),
        })

        # --- Phase 3: SGR Logic Execution (Uses PricingLogic) ---
        print("🧠 Calculating Offer (Schema Enforced)...")
        offer = llm.run_sgr(history, PricingLogic)

        # Audit log — the SGR benefit: explicit reasoning traces
        print(f"   [Audit] Math: {offer.margin_math}")
        print(f"   [Audit] Max Allowed: {offer.max_discount_percent}%")

        return offer.customer_message

    return "I'm sorry, I couldn't process your request."


if __name__ == "__main__":
    response = pricing_agent("I want a discount or I'm leaving!", "user_102")
    print(f"\n💬 Final Reply: {response}")

Mejores prácticas

Diseño de esquemas

  1. Ordenar los campos según el flujo de razonamiento: los campos de análisis deben ir antes que los de decisión.
  2. Escribir descripciones descriptivas Field. Estas guían la atención del modelo tanto como el nombre del campo.
  3. Imponer restricciones mediante Literal y Annotated. Utilizar Literal["a", "b"] para enumeraciones y Annotated[int, Ge(1), Le(10)] para límites.
  4. Mantener los esquemas enfocados: un esquema por fase de razonamiento, y luego combinarlos mediante múltiples llamadas.

Configuración de vLLM

  1. Aplicar una temperatura baja (0,1-0,3) para lograr un razonamiento determinista.
  2. Dejar que xgrammar se encargue de la estructura; no intentar imponer instrucciones de formato en el prompt.
  3. Controlar el uso de tokens. SGR suele requerir menos tokens que CoT, ya que no incluye prosa extensa.

Consideraciones en producción

  1. Versionar los esquemas de la misma forma que se hace con las APIs.
  2. Incluso con SGR, los errores de red y servidor siguen necesitando un manejo adecuado.
  3. Registrar las salidas brutas de SGR con fines de cumplimiento normativo y depuración.
  4. Probar con casos límite para asegurar que el esquema funcione en los extremos.

Conclusión

SGR es lo que permite pasar de un sistema que “funciona en una demostración” a uno que “funciona en producción”. Se define la topología de razonamiento en Pydantic, xgrammar la aplica en el momento de la decodificación, y el resultado es:

  • siempre válido, sin bucles de reintentos ni fallos de parseo
  • auditable a nivel de campos
  • compatible con modelos más pequeños, ya que estos no tienen que ajustar el formato por sí mismos
  • más económico en términos de recursos, gracias a menos tokens, menos reintentos y modelos más reducidos

La demo sgr-discount-manager conecta cada ejemplo de código de este artículo a un servidor vLLM real. Clónela y comienza a adaptar los esquemas a tu propio flujo de trabajo.

Puntos clave

  1. El razonamiento guiado por esquemas hace explícita la topología de razonamiento, en lugar de confiar en que el modelo siga instrucciones escritas.
  2. La decodificación restringida evita la generación de JSON inválido en tiempo real, lo cual es más eficiente que validar y volver a intentarlo posteriormente.
  3. Colocar los campos de análisis antes que los de decisión cuando el esquema debe obligar al razonamiento antes de la salida.
  4. Utilizar SGR cuando el código posterior depende de la estructura, no cuando lo que se necesita es prosa libre.
