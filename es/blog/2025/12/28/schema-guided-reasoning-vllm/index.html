Razonamiento guiado por esquemas: vLLM, XGrammar y Pydantic

Viacheslav Dubrov

2025-12-28 · Actualizado 2026-09-12 · 15 min · Agentes de IA · Ingeniería de modelos

Traducción automática

Este artículo se tradujo automáticamente a partir de la versión original en inglés.

Este artículo está dirigido a ingenieros de Python que necesitan salidas del modelo que el código posterior pueda validar. Aprenderás a definir un esquema de Pydantic, solicitar structured output a vLLM y añadir comprobaciones de aplicación para el significado y las políticas.

Pydantic describe los campos de la respuesta, vLLM sirve el modelo y XGrammar restringe los tokens que el modelo puede generar. Esta restricción se denomina constrained decoding. Solo se aplican las características del esquema compatibles con el backend de decoding; en este caso, XGrammar. Un límite de tokens todavía puede dejar un prefijo JSON incompleto, por lo que el código de la aplicación debe comprobar que la generación ha terminado y validar el resultado.

¿Qué es el razonamiento guiado por esquemas?

El razonamiento guiado por esquemas es una técnica que Rinat Abdullin describió en julio de 2025. En lugar de dejar que el modelo complete texto libremente —lo que puede resultar incoherente o ambiguo—, se le proporciona una plantilla estricta que define:

  • qué pasos debe representar la respuesta
  • el orden previsto de esos pasos, para que un revisor pueda inspeccionar el recorrido desde los datos hasta la decisión
  • dónde debe centrar la atención

Piensa en ello como una lista de comprobación de salidas que hay que inspeccionar, no como una prueba del razonamiento interno del modelo. El decoder comprueba la estructura de la salida; el código de la aplicación controla cuándo se ejecuta cada etapa y si se permite utilizar un resultado.

Qué controla el esquema

El ejemplo de referencia propone un descuento para retener a un cliente que podría marcharse. La probabilidad de churn estima esa posibilidad de abandono; el valor del carrito es el total antes del descuento. El margen es el beneficio bruto como fracción de ese total: un carrito de $200 con un margen de 0.20 genera $40 de beneficio bruto. Los descuentos utilizan puntos porcentuales, por lo que una propuesta de 15 equivale al 15 %.

Un modelo de pricing puede devolver JSON válido y aun así proponer un descuento del 25 % cuando el margen solo es del 20 %. El esquema registra la propuesta; el código de la aplicación debe comprobar si el descuento está permitido.

Campos como churn_analysis, margin_math y max_discount_percent hacen explícitas las salidas intermedias previstas. Un esquema restringe la forma de la respuesta. Por sí solo, no hace que un campo dependa de otro ni demuestra que la decisión sea correcta.

Esto proporciona:

  • una estructura de salida comparable entre ejecuciones repetidas
  • salidas intermedias registradas que los revisores pueden inspeccionar
  • campos intermedios que se pueden evaluar frente a un dataset de prueba
  • una hipótesis que probar con modelos más pequeños: restringir el formato puede ayudar, pero la precisión de la tarea aún debe evaluarse
  • Abdullin escribe que una mejora de precisión del 5–10 % «no es infrecuente» en los casos que ha observado; se trata de una observación de un profesional, no de un resultado de benchmark, así que debes medirla en tu propia carga de trabajo

Orientación del prompt y restricciones del decoder

La orientación del prompt y el constrained decoding se pueden combinar. Esta comparación muestra dónde comprueba cada uno el formato solicitado.

Prompt engineering: solicitar el formato

Este prompt pide al modelo que formatee la propuesta de descuento como JSON:

Please analyze the customer data and output your response as valid JSON
with the following structure: {"discount": <number>, "reason": <string>}
Be careful with the formatting!

Esperas que la comprensión que tiene el modelo de «output JSON» prevalezca sobre su tendencia a conversar. Una actualización del modelo, un cambio de temperatura o un ejemplo few-shot diferente pueden romper tu parser.

Chain of Thought: una traza de razonamiento útil con el mismo problema de estructura

Un prompt de chain-of-thought (CoT) solicita un análisis intermedio. La respuesta podría tener este aspecto:

Let's think step by step:
1. First, I'll analyze the customer's churn risk...
2. Then I'll calculate the margin...
3. Therefore, I recommend a 15% discount.

CoT puede mejorar la precisión de la tarea cuando el prompt, el modelo, la tarea y la evaluación lo permiten, pero deja el resultado en forma de prosa, difícil de parsear de manera fiable. Puede que acabes haciendo una segunda llamada al LLM solo para extraer datos estructurados.

SGR: chain of thought estructurado

SGR puede hacer que los campos intermedios estén disponibles para su inspección y evaluación. Que eso mejore la precisión de la tarea depende del modelo, el prompt, la tarea y el uso de esos campos; el esquema solo formaliza su forma:

class PricingLogic(BaseModel):
    # 1. Recorded analysis
    churn_analysis: str = Field(..., description="Analyze churn_probability")
    financial_analysis: str = Field(..., description="Analyze cart_value and margin")

    # 2. Proposed calculation, checked by application code
    margin_math: str = Field(..., description="Calculate: 'Cart $X * Y% = $Z'")

    # 3. Proposed decision, not bounded by the analysis fields
    max_discount_percent: float = Field(..., description="Max allowed discount")

    # 4. Final Output
    customer_message: str

El esquema describe estos campos en ese orden. Un esquema de objeto único no crea un paso de validación separado entre ellos. Utiliza llamadas independientes o comprobaciones de la aplicación cuando las decisiones posteriores deban depender de resultados anteriores.

Patrones de SGR

Byte says

Colocar los campos de análisis antes de una decisión facilita la inspección de la respuesta. Un campo llamado margin_math sigue siendo un string, no una calculadora.

SGR tiene tres patrones básicos que se pueden combinar para formar workflows más grandes.

1. Cascade: pasos de razonamiento secuenciales

Cascade representa un orden de razonamiento en una única respuesta estructurada. Aquí, un clasificador de documentos registra un resumen, una puntuación de coincidencia temática y una categoría propuesta. No ejecuta una comprobación independiente entre esos campos.

from pydantic import BaseModel
from typing import Literal, Annotated
from annotated_types import Ge, Le

class DocumentEvaluation(BaseModel):
    """Record a document summary, score, and proposed category."""

    # Step 1: Record a summary
    brief_document_summary: str

    # Step 2: Rate (bounded integer)
    rate_topic_match: Annotated[int, Ge(1), Le(10)]

    # Step 3: Decide (constrained choices)
    final_recommendation: Literal["relevant", "irrelevant", "review"]

Usos ilustrativos: clasificación de documentos y triaje de tickets de soporte.

Se pide al modelo que devuelva brief_document_summary, rate_topic_match y final_recommendation en ese orden. Si el orden es un requisito de la política, impónlo mediante llamadas separadas o lógica determinista de la aplicación.

2. Routing: una sentencia switch semántica

Routing pide al modelo que seleccione una ruta de entre un conjunto de opciones, implementadas mediante tipos Union. Este router elige entre obtener los datos del cliente para una solicitud de pricing y devolver una respuesta general.

from pydantic import BaseModel
from typing import Literal, Union

class FeatureLookup(BaseModel):
    """Route to database lookup."""
    rationale: str
    tool_name: Literal["fetch_user_features"] = "fetch_user_features"
    user_id: str

class GeneralResponse(BaseModel):
    """Standard response for non-pricing queries."""
    tool_name: Literal["respond"] = "respond"
    content: str

class RouterSchema(BaseModel):
    """The model must pick exactly ONE branch."""
    action: Union[FeatureLookup, GeneralResponse]

Buenos casos de uso: clasificación de intenciones, selección de tools, triaje de soporte y dispatch multi-agent.

Los valores Literal específicos de cada rama ayudan a la validación a distinguir los miembros de la unión. No hacen que el routing sea correcto. Valida el resultado y haz el dispatch desde el código de la aplicación. Para utilizar un discriminador explícito de Pydantic, configura y prueba una unión discriminada.

3. Cycle: razonamiento repetido con listas

Cycle describe varios elementos, con límites sobre su cantidad. Este ejemplo de evaluación de riesgos solicita entre dos y cuatro factores, cada uno con una explicación y una severidad.

from pydantic import BaseModel
from typing import List, Literal, Annotated
from annotated_types import MinLen, MaxLen

class RiskFactor(BaseModel):
    explanation: str
    severity: Literal["low", "medium", "high"]

class RiskAssessment(BaseModel):
    """Generate 2-4 risk factors."""
    factors: Annotated[List[RiskFactor], MinLen(2), MaxLen(4)]

Buenos casos de uso: evaluación de riesgos, extracción de incidencias, tool calls en paralelo y planificación en varios pasos.

Los límites de la lista describen un batch variable de 2–4 elementos. Un decoder compatible puede restringir esa longitud; la validación de la aplicación vuelve a comprobarla. Combinada con Routing, la lista puede describir tool calls propuestas. El código de la aplicación debe autorizarlas y hacer el dispatch.

Cómo hacer funcionar SGR: constrained decoding

Los patrones anteriores no son más que esquemas de Pydantic. El constrained decoding puede imponer las restricciones compatibles exportadas en su JSON Schema. Los validadores arbitrarios de Python no se convierten en restricciones del decoder; siguen ejecutándose en Pydantic después de la generación.

El constrained decoding modifica el paso de generación de tokens. En lugar de permitir que el modelo muestree libremente de su vocabulario, el engine aplica una grammar mask que bloquea los tokens que infringirían el esquema. Esto ocurre en el inference engine, no en el código de tu aplicación.

[!TIP] SGR no requiere «reasoning models» como o1 o DeepSeek-R1. Los modelos instruction-tuned también pueden producir respuestas restringidas por esquema. Compara la precisión de la tarea para los modelos concretos que pretendas servir.

¿Por qué utilizar vLLM y XGrammar aquí?

La API de structured output de vLLM acepta JSON Schema mediante un cliente compatible con OpenAI. Esto permite que el ejemplo conserve un plumbing de requests familiar mientras configura el backend de decoding en el servidor. Al cambiar de proveedor, sigue siendo necesario probar los subconjuntos de esquemas, la gestión de errores y el comportamiento del modelo.

XGrammar proporciona el compilador de gramáticas y la maquinaria de token masks. Su descripción técnica explica la división entre CPU y GPU que se muestra a continuación; sus resultados de benchmark se aplican a las cargas de trabajo probadas, no a todas las deployments.

Cómo impone XGrammar los esquemas

Dónde se aplica la máscara

Los logits son las puntuaciones no normalizadas del modelo para los posibles tokens siguientes. XGrammar modifica esas puntuaciones después del forward pass del modelo y antes del muestreo. No modifica el modelo en sí. Filtra los tokens que se pueden seleccionar.

Un inference loop estándar tiene este aspecto:

1. Input tokens → GPU Forward Pass → Logits (one unnormalized score per vocabulary token)
2. Logits → Sampling (temperature, top-p, etc.) → Next Token
3. Repeat until done

XGrammar se intercala entre los pasos 1 y 2:

1. Input tokens → GPU Forward Pass → Raw Logits
2. Raw Logits → XGrammar Logits Processor → Masked Logits
3. Masked Logits → Sampling → Next Token (continues the grammar-valid prefix)
4. Repeat until done

El diagrama muestra cómo las puntuaciones del modelo y la grammar mask se combinan antes de seleccionar un token. Cada token aceptado también actualiza el estado de la gramática para el paso siguiente.

El modelo sigue calculando en la GPU su distribución de probabilidad completa. El GrammarMatcher de XGrammar genera el bitmask en la CPU; después, el serving engine mueve ese bitmask al device de los logits y lo aplica in place antes del muestreo. Para logits en la GPU, XGrammar utiliza un kernel de GPU para aplicar la máscara. Los tokens no válidos reciben logits con valor -∞, lo que hace que su probabilidad sea exactamente 0 después del softmax.

Dos fases

XGrammar divide el trabajo entre compilación y runtime. Este diseño reduce el trabajo repetido de la gramática.

Fase 1: compilación de la gramática, una vez por esquema

Este fragmento construye una gramática para el esquema utilizando el tokenizer del modelo. El resultado compilado se puede reutilizar al generar respuestas con ese esquema.

# This happens once per schema
tokenizer_info = xgr.TokenizerInfo.from_huggingface(tokenizer)
grammar_compiler = xgr.GrammarCompiler(tokenizer_info)
compiled_grammar = grammar_compiler.compile_json_schema(schema_json)

Durante la compilación, XGrammar:

  1. Convierte el JSON Schema en una Context-Free Grammar.
  2. Construye un Pushdown Automaton (PDA), una máquina de estados con una pila que puede gestionar estructuras anidadas como {"a": {"b": {"c": ...}}}.
  3. Precalcula qué tokens son válidos en cada posición de la gramática. El resultado es la «adaptive token mask cache».
  4. Clasifica los tokens como «context-independent» (se pueden guardar en caché) o «context-dependent» (se deben comprobar en runtime frente al estado de la pila).

[!NOTE] El artículo de XGrammar informa de que aproximadamente el 99 % de los tokens eran context-independent en sus mediciones (artículo). Considera esa cifra específica del benchmark, no una proporción universal.

Fase 2: generación de la máscara en runtime, en cada token

En cada paso de generación:

  1. El GrammarMatcher sigue la posición actual en la gramática.
  2. Consulta la máscara precalculada para los tokens context-independent.
  3. Ejecuta el PDA para comprobar los tokens context-dependent restantes.
  4. Los combina en un bitmask final, lo mueve al device de los logits y lo aplica allí.

¿Por qué autómatas de pila y no regex?

Por el anidamiento. Una expresión regular —una máquina de estados finitos— no puede hacer match de forma fiable con estructuras como:

{ "user": { "profile": { "settings": { "theme": "dark" } } } }

La parte difícil son las llaves de cierre }}}: hay que recordar cuántas llaves de apertura se han visto. Un Pushdown Automaton tiene una pila que realiza ese seguimiento, por lo que puede gestionar una profundidad de anidamiento arbitraria. Por eso XGrammar también puede imponer Union types, objetos anidados y esquemas recursivos, ámbitos en los que los enfoques basados en regex se quedan cortos.

Un ejemplo concreto: generar un campo float

Cuando el modelo está generando "max_discount_percent":, XGrammar sabe por el esquema que a continuación viene un float. El conjunto de tokens válidos depende del estado del parser y del tokenizer. Al principio del número, la máscara puede admitir un dígito o un signo menos; después de un dígito, puede admitir continuaciones como otro dígito, un punto decimal o un marcador de exponente.

  • Una comilla, {, [, true, false o null no puede iniciar este número, por lo que la máscara bloquea sus tokens en ese estado.
  • El forward pass podría haber asignado una probabilidad alta al token correspondiente a "fifteen". Como ese token no puede continuar este campo numérico, la máscara lo elimina y el modelo debe elegir una continuación numérica válida.

Qué afecta al overhead

Tres motivos:

  1. Generación y transferencia de la máscara. XGrammar genera las máscaras en la CPU, y el serving engine las transfiere al device de los logits para aplicarlas in place. El grado de solapamiento depende de la implementación del serving y de la carga de trabajo.
  2. Caching. La mayor parte del trabajo de validación se realiza en tiempo de compilación. En runtime, el trabajo consiste sobre todo en consultar la caché.
  3. Implementación en C++. El hot path está escrito en C++, no en Python, y la máscara se aplica a los logits in place.

Los benchmarks citados indican un overhead bajo para sus gramáticas, tokenizers, hardware y cargas de trabajo probados. Esos resultados no establecen una garantía general de latencia o throughput.

Los fragmentos no se han probado contra un servidor vLLM activo. Utilizan Pydantic 2 y la API del cliente Python de OpenAI, sin un entorno de dependencias fijado. Para integrarlos, proporciona los builders de prompts y el feature store que muestran los imports, configura un contexto de usuario autenticado y prueba la combinación de servidor y modelo que hayas elegido.

Una solicitud general puede devolver una respuesta inmediatamente. Una solicitud de pricing necesita los datos del cliente y una propuesta del modelo, seguidos de una comprobación de la política de la aplicación antes de poder comunicar el descuento.

Paso 1: definir los esquemas

RouterSchema permite dos alternativas: solicitar datos del cliente con FeatureLookup o devolver texto con GeneralResponse. Después de recuperar los datos, una llamada independiente utiliza PricingLogic para registrar el análisis y el descuento propuesto. Mantener estas respuestas separadas permite que la aplicación obtenga los datos antes de solicitar una propuesta.

# sgr/models/schemas.py
from pydantic import BaseModel, Field
from typing import Literal, Union

# --- Phase 1: Routing (Union for branching) ---
class FeatureLookup(BaseModel):
    """Route to DB lookup if pricing context is needed."""
    rationale: str
    tool_name: Literal["fetch_user_features"] = "fetch_user_features"
    user_id: str

class GeneralResponse(BaseModel):
    """Standard response for non-pricing queries."""
    tool_name: Literal["respond"] = "respond"
    content: str

class RouterSchema(BaseModel):
    action: Union[FeatureLookup, GeneralResponse]

# --- Phase 2: Pricing Logic (Cascade for sequential reasoning) ---
class PricingLogic(BaseModel):
    """
    Structured response for dynamic pricing. The fields record an intended analysis→decision flow.
    """
    # 1. Data Analysis (Reflection)
    churn_analysis: str = Field(...,
        description="Analyze churn_probability (High > 0.7).")
    financial_analysis: str = Field(...,
        description="Analyze cart_value and profit_margin.")

    # 2. Recorded calculation; application code recomputes policy
    margin_math: str = Field(...,
        description="Calculate absolute profit: 'Cart $200 * 0.20 Margin = $40'.")

    # 3. Model-proposed decision; application code approves it.
    max_discount_percent: float = Field(...,
        description="Proposed discount percentage. Application code enforces policy.")

Paso 2: solicitar y validar una respuesta estructurada

El cliente exporta el modelo de Pydantic como JSON Schema, lo añade a un mensaje de sistema existente para orientar el prompt y lo envía como restricción de structured output. XGrammar se configura en el servidor; el cliente proporciona el esquema en cada request.

completed_content rechaza respuestas incompletas, rechazadas o vacías antes de que Pydantic valide el JSON y sus campos. También rechaza las paradas por límite de tokens aunque el texto devuelto se pueda parsear. Estos errores se propagan al caller, que debe proporcionar una respuesta de error o una política de retry; no se aprueba ninguna oferta por esas rutas.

# sgr/utils/llm_client.py
import json
from typing import TypeVar

from openai import OpenAI
from pydantic import BaseModel

T = TypeVar("T", bound=BaseModel)

def completed_content(completion) -> str:
    """Reject incomplete, refused, or empty results before JSON validation."""
    if not completion.choices:
        raise ValueError("No completion returned")
    choice = completion.choices[0]
    if choice.finish_reason != "stop" or getattr(choice.message, "refusal", None):
        raise ValueError("Completion was not successful")
    content = choice.message.content
    if not isinstance(content, str) or not content.strip():
        raise ValueError("Completion has no content")
    return content

class LLMClient:
    """Wrapper for vLLM with XGrammar-enforced structured generation."""

    def __init__(self, base_url: str = "http://localhost:8000/v1"):
        # Local vLLM commonly has no authentication. EMPTY is not authentication.
        self.client = OpenAI(base_url=base_url, api_key="EMPTY")
        self.model = self._get_available_model()

    def _get_available_model(self) -> str:
        """Auto-detect the model running on vLLM server."""
        models = self.client.models.list()
        if not models.data:
            raise RuntimeError("vLLM reported no available models")
        return models.data[0].id

    def run_sgr(self, messages: list[dict], schema_class: type[T]) -> T:
        """Run inference with Schema-Guided Response constraints.

        Uses vLLM structured outputs to constrain the JSON shape at generation time.
        """
        schema_dict = schema_class.model_json_schema()

        # Enhance system message with schema for model guidance
        enhanced_messages = messages.copy()
        if enhanced_messages and enhanced_messages[0]["role"] == "system":
            schema_json = json.dumps(schema_dict, indent=2)
            enhanced_messages[0] = {
                "role": "system",
                "content": (
                    enhanced_messages[0]["content"]
                    + f"\n\nRespond with JSON matching this schema:\n{schema_json}"
                ),
            }

        # vLLM v0.12+ structured outputs. Configure the backend on the server.
        completion = self.client.chat.completions.create(
            model=self.model,
            messages=enhanced_messages,
            temperature=0.1,  # Reduces sampling variation; it is not deterministic.
            extra_body={"structured_outputs": {"json": schema_dict}},
        )

        return schema_class.model_validate_json(completed_content(completion))

[!NOTE] En la versión actual de vLLM, structured_outputs: {"json": schema_dict} solicita un JSON que coincida con el esquema. Cuando sea necesario, configura el structured-output backend con la opción --structured-outputs-config.backend del servidor. Se trata de una imposición mediante software en el inference server, no de una imposición por hardware.

Paso 3: orquestar el agente

La aplicación enruta la solicitud, obtiene los datos del caller autenticado, solicita una propuesta, la comprueba y devuelve el resultado. El feature store utiliza el user_id autenticado, nunca el ID propuesto por el modelo. El prompt también recibe user_ltv, el valor estimado del ciclo de vida del cliente; esta estimación proporciona contexto al modelo, pero no establece el límite del descuento.

La política de demostración rechaza porcentajes propuestos fuera del intervalo 0–20 y después redondea hacia abajo a centésimas de punto porcentual. Rechaza un descuento final cuyo coste sea superior al beneficio bruto del carrito. approve_discount comprueba que las entradas sean finitas, que el valor del carrito sea positivo y que el margen sea una fracción entre 0 y 1 antes de realizar el cálculo.

# sgr/agent.py
from decimal import Decimal, ROUND_DOWN

from .models.schemas import PricingLogic, RouterSchema
from .prompts.routing import build_routing_prompt
from .prompts.pricing import build_pricing_context_prompt, ASSISTANT_FETCH_MESSAGE
from .store.hybrid_store import HybridFeatureStore
from .utils.llm_client import LLMClient

def approve_discount(offer: PricingLogic, context: dict) -> Decimal:
    """Enforce the pricing policy independently of the model's explanation."""
    cart_value = Decimal(str(context["current_cart_value"]))
    margin = Decimal(str(context["cart_profit_margin"]))
    proposed = Decimal(str(offer.max_discount_percent))

    if not all(value.is_finite() for value in (cart_value, margin, proposed)):
        raise ValueError("Pricing values must be finite")
    if cart_value <= 0 or not Decimal("0") <= margin <= Decimal("1"):
        raise ValueError("Invalid pricing context")

    if not Decimal("0") <= proposed <= Decimal("20"):
        raise ValueError("Proposed discount violates pricing policy")
    # Policy rounds down to hundredths of a percentage point before approval.
    approved = proposed.quantize(Decimal("0.01"), rounding=ROUND_DOWN)
    gross_profit = cart_value * margin
    discount_cost = cart_value * approved / Decimal("100")
    policy_cap = min(margin * Decimal("100"), Decimal("20"))
    if not Decimal("0") <= approved <= policy_cap or discount_cost > gross_profit:
        raise ValueError("Proposed discount violates pricing policy")

    return approved

def pricing_agent(user_query: str, user_id: str) -> str:
    """Integrate routing, context, and pricing; user_id is caller-authenticated."""

    llm = LLMClient()
    feature_store = HybridFeatureStore()

    # Build conversation history
    history = [
        {"role": "system", "content": build_routing_prompt(user_id)},
        {"role": "user", "content": user_query},
    ]

    # --- Phase 1: Routing (Uses RouterSchema) ---
    print(f"🤖 Processing: '{user_query}' for {user_id}")
    decision = llm.run_sgr(history, RouterSchema)
    print(f"📍 Routing decision: {decision.action.tool_name}")

    if decision.action.tool_name == "respond":
        return decision.action.content

    # --- Phase 2: Context Retrieval ---
    if decision.action.tool_name == "fetch_user_features":
        print(f"🔍 Fetching features for {user_id}...")
        context = feature_store.get_user_context(user_id)

        if not context:
            return "Error: User profile not found."

        print(f"   [Data] LTV: ${context.get('user_ltv')} | "
              f"Margin: {context.get('cart_profit_margin', 0) * 100}%")

        # Inject context into conversation
        history.append({"role": "assistant", "content": ASSISTANT_FETCH_MESSAGE})
        history.append({
            "role": "user",
            "content": build_pricing_context_prompt(
                churn_prob=context.get("churn_probability", 0.5),
                cart_val=context.get("current_cart_value", 100),
                margin=context.get("cart_profit_margin", 0.2),
                user_ltv=context.get("user_ltv", 0),
            ),
        })

        # --- Phase 3: model proposal, then deterministic policy enforcement ---
        print("🧠 Proposing Offer (Schema Enforced)...")
        offer = llm.run_sgr(history, PricingLogic)
        try:
            approved_discount = approve_discount(offer, context)
        except ValueError:
            return "No discount approved: the proposal failed the pricing policy."

        # Audit log: reasoning is inspectable; pricing is application-enforced.
        print(f"   [Audit] Math: {offer.margin_math}")
        print(f"   [Audit] Approved Discount: {approved_discount}%")

        return (
            f"Illustrative approved discount: {approved_discount}%. "
            "No coupon has been issued."
        )

    return "I'm sorry, I couldn't process your request."

if __name__ == "__main__":
    response = pricing_agent("I want a discount or I'm leaving!", "user_102")
    print(f"\n💬 Final Reply: {response}")

Comando del servidor para una integración

Configura el serving process para utilizar XGrammar antes de conectar el cliente:

# On a separately provisioned vLLM host
vllm serve Qwen/Qwen2.5-7B-Instruct \
    --port 8000 \
    --structured-outputs-config.backend xgrammar

El argumento posicional del modelo y la opción del backend siguen la referencia de vLLM serve. Proporciona un accelerator/runtime compatible y memoria suficiente para el modelo y la longitud de contexto seleccionados siguiendo la guía de instalación. Este comando es una referencia de integración, no una receta de instalación probada.

Una propuesta del 15 % sobre un carrito de $200 con un margen del 20 % devuelve 15.00 desde la función de políticas. La aplicación comunica ese porcentaje sin fingir que ha emitido un cupón. Una prueba de límite utiliza un margen de 0.12346, es decir, del 12,346 %. Una propuesta de 12.346 se redondea hacia abajo a 12.34 antes de comprobar el valor final. Redondear a 12.35 después de la aprobación superaría el margen.

Comprobaciones antes de una integración real

Byte says

Una propuesta puede contener JSON válido y un descuento superior al margen. La función de políticas comprueba el número aunque la explicación resulte convincente.

Diseño del esquema

  1. Ordena los campos según el flujo de razonamiento previsto. Trata ese orden como documentación, salvo que las llamadas independientes o las comprobaciones de la aplicación lo hagan cumplir.
  2. Escribe descripciones Field descriptivas. Guían la atención del modelo tanto como el nombre del campo.
  3. Restringe con Literal y Annotated. Utiliza Literal["a", "b"] para enums y Annotated[int, Ge(1), Le(10)] para los límites.
  4. Mantén los esquemas centrados. Un esquema por fase de razonamiento y, después, composición mediante varias llamadas.

Configuración de vLLM

  1. Utiliza una temperatura baja (0,1–0,3) para reducir la variación del muestreo. Para realizar pruebas repetibles, fija el modelo y la configuración de serving, utiliza el modo determinista del servidor si ofrece uno y verifica el resultado.
  2. Explica la tarea y los campos del esquema en el prompt, como hace el cliente anterior. La orientación del prompt y las restricciones del decoder cumplen funciones complementarias.
  3. Mide el uso de tokens con el mismo prompt, modelo, esquema y tarea. SGR puede emitir más o menos tokens que una respuesta CoT de forma libre.

Consideraciones para producción

  1. Versiona los esquemas del mismo modo que versionas las APIs.
  2. Incluso con SGR, los errores de red y del servidor siguen necesitando una gestión adecuada.
  3. Registra por separado la propuesta y la decisión de políticas para facilitar la depuración, de acuerdo con tus reglas de retención y redacción de datos.
  4. Recalcula en el código de la aplicación los precios, límites, permisos y demás reglas semánticas antes de utilizarlos; prueba valores límite que el esquema por sí solo no pueda rechazar.

La siguiente prueba

Empieza con el límite de descuento y una completion incompleta. La comprobación offline cubre ambos casos, pero no puede decirte si un modelo enruta correctamente a un cliente real o explica con precisión el margen. Para una evaluación en producción, mantén fijos el modelo, los prompts, el esquema y la configuración de serving. Cuenta por separado los resultados incompletos, los fallos del esquema, los errores de routing y los rechazos de políticas antes de comparar el coste o la precisión de la tarea.
