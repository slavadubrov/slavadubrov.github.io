Использование инструментов ИИ-агентами в 2026: MCP, CLI, Skills и выполнение кода

Часть 3 из серии Engineering the Agentic Stack

Часть 1 покрывала cycle ризонинга, а Часть 2 — архитектуру памяти. В этой статье добавляется слой действий: как агент раскрывает, выбирает и запускает инструменты.

История инструментов заметно изменилась в 2025–2026. MCP дал вендорам общий протокол для внешних сервисов. Агенты, исполняющие код, показали, что модель иногда может композиционировать небольшой программный фрагмент эффективнее, чем выпускать длинную цепочку JSON-вызовов. Anthropic сообщила о сокращении токенов на 98.7% для одного expense-analysis workflow, а в CodeAct paper зафиксированы улучшения до 20% на бенчмарках их настройки. Эти результаты описывают именно их задачи и harnesses — это не универсальное преимущество исполнения кода.

Я сравниваю JSON tool calling, MCP, Skills, CLI-инструменты и выполнение кода в этом порядке. Финальный раздел применяет принципы дизайна Agent-Computer Interface (ACI) к Market Analyst Agent.

TL;DR: Пять полезных паттернов интерфейса покрывают большую часть случаев использования инструментов агентами. Skills несут инструкции, CLI-инструменты подходят для локальной разработки, MCP связывает разделяемые сервисы, а выполнение кода композирует многошаговую работу внутри сэндбокса. JSON tool calling остаётся самым простым выбором для небольших атомарных действий. Какой бы протокол ни был выбран, Agent-Computer Interface (ACI) должен делать действия ясными, обратную связь компактной, а ошибки — восстанавливаемыми.

Пять способов, которыми ИИ-агенты используют инструменты

В Части 1 cycle ризонинга выбирал следующий шаг. Часть 2 хранила состояние, нужное для продолжения. Граница инструмента превращает это решение в действие и возвращает наблюдение в цикл. Эти пять паттернов по-разному балансируют токеновую стоимость, гибкость и степень enforcement.

1. JSON tool calling: базовый вариант

Исходный паттерн: вы определяете tool schemas как JSON, LLM эмитит структурированные function calls, ваш код исполняет их. Это хорошо изучено и работает отлично для небольших toolset.

# Traditional tool definition — each tool consumes ~550-1,400 tokens (Apideck benchmark)
tools = [
    {
        "name": "get_stock_price",
        "description": "Get the current stock price for a ticker symbol",
        "input_schema": {
            "type": "object",
            "properties": {
                "ticker": {"type": "string", "description": "Stock ticker (e.g., NVDA)"}
            },
            "required": ["ticker"]
        }
    }
]

При 5–10 инструментах оверхед приемлем. Проблема — масштаб: каждое определение инструмента стоит 550-1,400 tokens. При 20 инструментах вы тратите 15–25K токенов ещё до того, как агент начнёт reasoning.

2. MCP для shared integrations

Model Context Protocol — стандарт, к которому сошлись большинство вендоров. Anthropic пожертвовала его Linux Foundation в декабре 2025 года, в рамках Agentic AI Foundation (AAIF), которое она соосновала вместе с OpenAI и Block. Google, Microsoft и AWS поддерживают foundation как платиновые члены. OpenAI добавила поддержку MCP в свой Responses API. Теперь существует 10,000+ активных MCP servers и 97M+ ежемесячных SDK downloads.

MCP хорошо подходит для интеграций SaaS между вендорами (Figma, Notion, Salesforce), для сервисов, у которых нет CLI-эквивалентов, и для сред, где нужна OAuth-оркестрация. Ценность MCP — в едином discovery и transport-слое. При этом governance по-прежнему завязано на аутентификацию, авторизацию, логирование и деплой, которые контролируются на стороне сервера.

Продакшн-история оказывается более «грязной», чем это звучит в headline цифрах.

Проблема номер один — поверхность атаки. Vulnerable MCP Project отслеживает 50 уязвимостей на MCP servers, 13 из них оценены как Critical, вклад сделан 32 security researchers. Классы атак включают prompt injection, провалы в валидации входных данных, дырки в аутентификации и сетевые security holes. Первый real-world злонамеренный MCP server появился в сентябре 2025: пакет postmark-mcp, который BCC’нул каждый исходящий email на адрес атакующего, затронув около 300–500 организаций до обнаружения.

Tool poisoning — атака, о которой я больше всего переживаю. Invariant Labs продемонстрировала, что poisoned MCP tools способны эксфильтрировать данные даже тогда, когда их никогда не вызывают. Достаточно, чтобы модель прочитала metadata инструмента: этого уже хватает для запуска атаки. MCPTox benchmarks тестировали 20 LLM agents на 45 реальных MCP servers и нашли успех атаки вплоть до 72.8%.

Токеновый оверхед — операционная проблема. Одна команда, запускающая MCP servers для GitHub, Slack и Sentry (~40 инструментов целиком), обнаружила 55,000 tokens схем, инжектированных до того, как пользователь вообще спросит что-либо. Другая команда сообщила 143,000 из 200,000 доступных токенов (72%), которые уходили только на tool definitions.

Anthropic заявила 85% reduction схем через свой Tool Search Tool и 96% reduction при загрузке трёх-пяти релевантных инструментов для оцениваемых задач. Селективная загрузка сохраняет «поверхность» протокола, но убирает схемы, которые текущий запрос не требует.

3. Skills: экспертиза, а не исполнение

В конце 2025 произошла стандартизация agent skills в открытом формате (запуск в октябре 2025, публикация как open standard в декабре 2025). Tools дают capabilities (что агент может делать), а skills дают expertise (что агент знает о том, как выполнять сложные задачи).

SKILL.md стандарт определяет skill как markdown-файл с YAML frontmatter:

---
name: deploy
description: Deploy the application to production
argument-hint: "[environment]"
user-invocable: true
---
Deploy the application to the $0 environment (default: staging).
Steps:
1. Run the test suite
2. Build the production bundle
3. Deploy using the deploy script
4. Verify the deployment health check

Skills используют progressive disclosure. Около 100 токенов metadata загружается при старте; полные инструкции загружаются только когда skill активна. Для сравнения: примерно 55,000 tokens, которые примерно 40 MCP tools могут потребить до начала reasoning.

К марту 2026 Claude Code, OpenAI Codex CLI, Cursor, GitHub Copilot, Gemini CLI, Goose, Windsurf и Roo Code приняли этот формат. Victor Dibia описывает этот сдвиг в сторону code-driven agent actions.

Используйте skills для доменной экспертизы, многошаговых процедур и повторяющейся работы вроде database migrations или payment integrations. Они подходят под задачи, где агенту нужны инструкции про как пользоваться уже существующей capability.

4. CLI и shell tools

CLI-интерфейсы могут быть существенно дешевле по контексту, когда модель уже знает команду. Scalekit сообщила о разнице в 4-32x токена между её CLI и MCP путями на 75 запусках. Этот case study измеряет собственные инструменты и задачи; он не заменяет сравнение на ваших манифестах и выводе команд.

Широко задокументированные команды вроде git, docker, kubectl, gh, curl и jq часто требуют почти никакого вводного tool schema текста. Редкие или внутренние CLI всё ещё нуждаются в обнаруживаемой справке, примерах и стабильном machine-readable output.

Гайд Ugo Enyioha “Writing CLI Tools That AI Agents Actually Want to Use” формализовал восемь правил дизайна:

  1. Structured output — обязательно — support --json
  2. Exit codes — это управление потоком — используйте разные коды для разных типов ошибок
  3. Команды должны быть идемпотентными
  4. Самодокументируемость --help с реалистичными примерами
  5. Дизайн для композируемости — --quiet для «чистых» значений, поддержка stdin
  6. Предоставляйте флаги --dry-run и --yes
  7. Поддерживайте introspection версий
  8. Обрабатывайте auth через environment variables

CLI лишён type safety MCP, встроенной OAuth-оркестрации, tool discovery и audit trail. Паттерн, к которому большинство команд сходится: CLI как default для разработки и локальных операций, MCP — для интеграции с внешними сервисами и enterprise governance.

5. Выполнение кода для многошаговой работы

Это изменение в tooling ИИ-агентов я считаю самым значимым. Вместо того чтобы выпускать структурированный JSON для поочерёдного вызова заранее определённых функций, агент пишет Python- или bash-скрипт. Скрипт вызывает несколько инструментов, обрабатывает результаты с помощью loops и conditionals и возвращает только финальную сводку в контекст модели.

Anthropic формализовала это с Programmatic Tool Calling (PTC), теперь это GA в Claude API. Академическая основа — CodeAct paper (Wang et al., ICML 2024), который тестировали на 17 LLM и нашли, что code actions дают до 20% более высокие task success rates и на 30% меньше шагов по сравнению с JSON-альтернативами.

Три first-party case study показывают, где паттерн может помочь: Vercel и Cloudflare ниже, затем пример от Anthropic про expense-analysis. Рассматривайте их как свидетельства вендора и перепроверьте сравнение на ваших задачах.

  • Vercel переработали свой d0 text-to-SQL agent, убрав 80% инструментов (с 15 до 2: ExecuteCommand и ExecuteSQL). Task success вырос с 80% до 100%, время исполнения упало в 3.5 раза, а токен-использование снизилось на 40%. Их формулировка: “The best agents might be the ones with the fewest tools.”

  • Cloudflare разработала “Code Mode,” который позволяет агентам писать TypeScript для вызова их API вместо определения tool schemas, что уменьшает context overhead. Их рассуждение: “LLMs have an enormous amount of real-world TypeScript in their training set, but only a small set of contrived examples of tool calls.”

Вот паттерн из PTC документации Anthropic. Традиционный tool calling для expense analysis требует 20+ отдельных inference passes — по одному на каждого участника команды — и все промежуточные данные идут через context. Workflow, потреблявший ~150,000 токенов при прямом tool calling, переиспользовали под ~2,000 токенов, сократив на 98.7%. При code execution агент пишет один скрипт:

# Agent generates this code, executes in sandbox
import json
members = get_team_members("engineering")
over_budget = []
for m in members:
    expenses = get_expenses(m["id"], "Q3")
    total = sum(e["amount"] for e in expenses)
    if total > 5000:
        custom = get_custom_budget(m["id"])
        limit = custom["limit"] if custom else 5000
        if total > limit:
            over_budget.append({"name": m["name"], "spent": total, "limit": limit})
# Only this final summary returns to the LLM context
print(json.dumps(over_budget))

LLM видит только финальное JSON summary, а не тысячи expense line items, обработанные в сэндбоксе. Очевидный плюс — token efficiency. Loops и conditionals «достаются бесплатно», ошибки проходят через try/except вместо reasoning на естественном языке про сбои, а sensitive data остаётся внутри сэндбокса.

Когда JSON tool calling всё ещё имеет смысл: одиночные атомарные операции, среды без инфраструктуры сэндбоксинга, более маленькие модели со слабым code generation, или audit requirements, где нужно логировать каждый индивидуальный tool invocation.

Agent-Computer Interface (ACI) для инструментов ИИ-агентов

Термин “Agent-Computer Interface” (ACI) придумали John Yang, Carlos E. Jimenez и коллеги в Princeton в их SWE-agent paper (NeurIPS 2024). Как людям помогают хорошо спроектированные интерфейсы (HCI), так paper утверждает, что LM agents — это “a new category of end users with their own needs and abilities, and would benefit from specially-built interfaces.”

Их ablation results дают цифры. SWE-agent с полным ACI достиг 18.0% на SWE-bench Lite против 7.3% при использовании только стандартного Linux shell — улучшение на 10.7 процентных пункта только за счёт дизайна интерфейса. Линтинг-гардрейл сам по себе дал 3 процентных пункта: 51.7% правок агента содержали хотя бы одну ошибку, пойманную линтером до того, как она могла распространиться.

Anthropic использовала ACI как базовую концепцию в своём гайде “Building Effective Agents”, указав его как один из трёх core principles: “Carefully craft your agent-computer interface through thorough tool documentation and testing.” Практическое руководство: “One rule of thumb is to think about how much effort goes into human-computer interfaces, and plan to invest just as much effort in creating good agent-computer interfaces.”

Четыре ACI-принципа на практике

1. Actions должны быть простыми и понятными. Самая частая ошибка — оборачивать API endpoints 1-в-1. Вместо list_users, list_events, create_event, реализуйте schedule_event, который за один вызов находит доступность и планирует. Вместо read_logs реализуйте search_logs, который возвращает только релевантные строки с контекстом.

2. Actions должны быть компактными и эффективными. Консолидируйте важные операции в как можно меньшее число действий. В Market Analyst Agent я объединяю получение цены с базовыми метриками в один get_stock_snapshot tool, вместо отдельных вызовов для price, volume, market cap и PE ratio.

3. Feedback среды должен быть информативным, но кратким. Не возвращайте сырое HTML или full API payloads. Разрешайте криптичные ID в семантические имена. Тестирование Anthropic добавило response_format enum, чтобы агент мог запросить компактный (~72 токена) или детальный (~206 токенов) ответ — примерно 3x разницу в токеновой стоимости. Они сообщили об улучшении real-world performance.

4. Guardrails должны снижать propagation ошибок. Автоматическое обнаружение ошибок помогает агентам быстрее распознавать и исправлять промахи. В SWE-agent кастомный файловый редактор со встроенным linting автоматически отвергает syntax errors: он ловит как минимум одну ошибку в 51.7% правок агента до того, как она сможет «накрутиться». Я применяю тот же принцип в Market Analyst Agent, валидируя аргументы tool через Pydantic schemas до исполнения:

from pydantic import BaseModel, Field, field_validator

class StockQuery(BaseModel):
    """Validated input for stock queries.

    Pydantic catches malformed tickers before the API call,
    preventing error propagation through the reasoning loop.
    """
    ticker: str = Field(description="Stock ticker symbol (e.g., NVDA)")
    period: str = Field(default="1mo", description="Time period: 1d, 5d, 1mo, 3mo, 1y")

    @field_validator("ticker")
    @classmethod
    def validate_ticker(cls, v: str) -> str:
        v = v.upper().strip()
        if not v.isalpha() or len(v) > 5:
            raise ValueError(f"Invalid ticker format: {v}")
        return v

    @field_validator("period")
    @classmethod
    def validate_period(cls, v: str) -> str:
        valid = {"1d", "5d", "1mo", "3mo", "6mo", "1y", "5y"}
        if v not in valid:
            raise ValueError(f"Invalid period: {v}. Must be one of {valid}")
        return v

Паттерны дизайна tool’ов, которые работают

Гайд Anthropic “Writing effective tools for agents” рассматривает инструменты как “a new kind of software reflecting a contract between deterministic systems and non-deterministic agents.”

Относитесь к descriptions tool’ов как к prompt engineering

Описания должны идти минимум 3-4+ предложения: когда использовать tool, какие параметры обязательны/необязательны, формат output и edge cases. Именование с namespace и префиксами (asana_search, jira_search) имеет “non-trivial effects” на точность выбора инструмента. В экспериментах Anthropic tool descriptions, оптимизированные под Claude, обгоняли описания, написанные экспертами-людьми, на evaluation benchmarks.

# Bad: vague, no context for when to use
tools = [{
    "name": "search",
    "description": "Search for items",
}]

# Good: specific, with input examples and edge cases
tools = [{
    "name": "stock_search_news",
    "description": (
        "Search for recent news articles about a specific stock or company. "
        "Use this tool when the user asks about recent events, earnings, "
        "announcements, or market-moving news for a specific ticker. "
        "Returns up to 10 articles sorted by relevance. "
        "For broad market news (not ticker-specific), use market_overview instead."
    ),
    "input_schema": {
        "type": "object",
        "properties": {
            "query": {
                "type": "string",
                "description": "Search query. Examples: 'NVDA earnings Q3 2025', 'Tesla delivery numbers'"
            },
            "max_results": {
                "type": "integer",
                "description": "Max articles to return (1-10, default 5)",
                "default": 5
            }
        },
        "required": ["query"]
    }
}]

Internal testing показало, что input examples (input_examples field) существенно повышают точность при работе со сложной обработкой параметров.

Возвращайте output с высоким «сигналом» и машинно-читаемый

Избегайте низкоуровневых идентификаторов (uuid, mime_type). Разрешайте криптичные ID в семантические имена. Структурируйте ответ так, чтобы агент мог reasoning по нему без парсинга boilerplate:

# Bad: raw API response dumped to agent
def get_stock_price(ticker: str) -> dict:
    response = api.get(f"/v1/quotes/{ticker}")
    return response.json()  # 500+ tokens of nested JSON

# Good: high-signal summary the agent can immediately reason about
def get_stock_price(ticker: str) -> dict:
    data = api.get(f"/v1/quotes/{ticker}").json()
    return {
        "ticker": ticker,
        "price": data["regularMarketPrice"],
        "change_pct": round(data["regularMarketChangePercent"], 2),
        "volume": data["regularMarketVolume"],
        "market_cap_b": round(data["marketCap"] / 1e9, 1),
        "pe_ratio": data.get("trailingPE"),
        "summary": f"{ticker} at ${data['regularMarketPrice']:.2f} "
                   f"({'up' if data['regularMarketChangePercent'] > 0 else 'down'} "
                   f"{abs(data['regularMarketChangePercent']):.1f}%)"
    }

Возвращайте ошибки, с которыми цикл может действовать

Используйте четыре отдельных механизма, потому что они закрывают разные классы отказов:

  1. Retry с exponential backoff для transient ошибок
  2. Цепочки fallback для ситуаций с outage у провайдера
  3. Error classification routing — transient ошибки retry, ошибки, которые может восстановить сам LLM, возвращаются агенту вместе с контекстом, ошибки требующие человека — эскалируются
  4. Checkpoint recovery для выживания при падениях

Процитированный гайд Anthropic поддерживает понятные tool errors и evaluation-driven tool design. Он не устанавливает универсальное снижение failure-rate, поэтому измеряйте recovery rate, retries и эскалацию на вашем own task suite.

from tenacity import retry, stop_after_attempt, wait_exponential

@retry(
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=1, min=2, max=10),
)
def call_stock_api(ticker: str) -> dict:
    """Fetch stock data with automatic retry on transient failures.

    Layer 1: Exponential backoff handles rate limits and network blips.
    If all retries fail, the error propagates to the agent with
    enough context to decide whether to try a different approach.
    """
    response = httpx.get(
        f"https://api.example.com/v1/quotes/{ticker}",
        timeout=10.0,
    )
    response.raise_for_status()
    return response.json()

Структурированные output’ы для результатов tool’ов

Каждый tool в Market Analyst Agent возвращает Pydantic-validated response. Это применяет ACI guardrails принцип на границе инструмента:

class StockSnapshot(BaseModel):
    """Structured tool response — the agent never sees raw API noise."""
    ticker: str
    price: float
    change_pct: float
    volume: int
    market_cap_b: float
    pe_ratio: float | None
    summary: str  # Human-readable one-liner for direct use in reports

class NewsResult(BaseModel):
    """Each news item is pre-processed for agent consumption."""
    headline: str
    source: str
    date: str
    relevance_score: float  # Pre-ranked so the agent doesn't waste tokens sorting
    key_points: list[str]  # Extracted by the tool, not the agent

Поле summary — то, что важнее всего. Оно даёт агенту готовую к использованию строку, которую можно прямо вставлять в отчёт без дополнительной обработки. key_points в NewsResult извлекаются на стороне сервера, поэтому агент не тратит inference tokens на парсинг содержимого статьи.

Компромиссы и соображения

Помимо modality-specific оговорок выше, выбор формируют несколько сквозных concerns:

  • Операционная стоимость зависит от измерения. Выполнение кода экономит токены, но добавляет latency «холодного старта» сэндбокса. MCP экономит время разработки для SaaS-интеграций, но добавляет оверхед на деплой сервера. CLI можно стартовать бесплатно, но сложнее управлять им в масштабе. Оптимизируйте под ваш реальный боттлнек: токеновую стоимость, latency или операционную сложность.

  • Скиллы команды имеют значение. Выполнение кода предполагает, что ваши агенты (и модели за ними) умеют генерировать надёжный Python или TypeScript. CLI предполагает знакомство с Unix-конвенциями. MCP требует понимания transport-протоколов и OAuth flows. Подбирайте modality под сильные стороны команды.

  • Консолидация tool’ов может зайти слишком далеко. Если один tool начинает аккумулировать несвязанные режимы и аргументы, агент получает другую задачу выбора внутри schema. Используйте оценки tool-selection и task-success, чтобы найти подходящую «поверхность» под ваш workload.

  • Skills — это prompt-based, а не enforced. Skill — это инструкции, которым агент должен следовать, а не guardrails, которые он обязан соблюдать. Для критических workflow используйте skills в паре с deterministic validation.

  • Audit requirements влияют на выбор. Если вам нужен полный лог каждого tool invocation и его результата, MCP и JSON tool calling дают структурированные audit trail «из коробки». Выполнение кода производит скрипт и его output — это полезно, но сложнее разложить на отдельные действия для compliance-отчётности.

Выбор tool’ов в большем масштабе

Есть три направления, за которыми стоит следить.

Первое — tool RAG для масштабирования. Когда toolset растут до сотен или тысяч, наивная точность tool selection падает до 13.62%. RAG-MCP paper применил retrieval-augmented generation к tool selection: индексирует tool descriptions в vector database и по запросу возвращает только релевантные. Это дало точность 43.13% — улучшение в 3.2 раза, при этом prompt tokens сократились примерно на 50%.

Второе — агенты, создающие свои собственные tools. LATM framework (“LLMs As Tool Makers”) заложил двухфазную парадигму: мощный LLM создаёт переиспользуемые Python-функции, а лёгкий LLM использует их. ToolMaker (ACL 2025) автономно превращает GitHub repositories в LLM-compatible tools с 80% success rate. Оба направления уводят нас от использования tool’ов к созданию tool’ов, а затем — к управлению библиотекой сгенерированных tool’ов.

Третье — стек A2A + MCP dual-protocol. Agent2Agent Protocol (A2A) от Google закрывает то, чего MCP не умеет: коммуникацию агент → агент. MCP отвечает за agent-to-tool integration; A2A — за agent-to-agent discovery, negotiation и task delegation.

Ключевые выводы

  1. Выбирайте интерфейс по action: JSON calling для небольших typed операций, MCP для shared services, Skills для процедур, CLI для устоявшихся команд, а sandboxed code — для локальной композиции.
  2. Привязывайте условия бенчмарка к результату. CodeAct, Anthropic, Vercel, Cloudflare, Apideck и Scalekit меряли разные модели, задачи, tools и harnesses.
  3. Качество ACI переживает изменения протокола. Понятные действия, компактный feedback, валидация и полезные ошибки помогают любой modality.
  4. Консолидируйте пересекающиеся tool’ы только когда эвалюации показывают, что меньшая поверхность улучшает выбор или task success.
  5. Безопасность идёт вместе с мощностью исполнения. Shell и code-интерфейсы требуют сэндбоксинга; MCP требует scoped identity и server policy; Skills остаются инструкциями, а не enforcement.
