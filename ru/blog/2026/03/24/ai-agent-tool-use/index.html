Использование инструментов ИИ-агентами: MCP, CLI, Skills и исполнение кода

Viacheslav Dubrov

2026-03-24 · Обновлено 2026-08-01 · 18 мин · ИИ-агенты

Автоматический перевод Эта статья была автоматически переведена с оригинальной английской версии.

В части 1 разбирались циклы ризонинга, а в части 2 — память. Эта статья добавляет слой действий: как агент предоставляет, выбирает и запускает инструменты. Память определяет, что агент знает перед очередным шагом; этот слой определяет, что он может с этим сделать. В части 4 рассматривается проверка, которая решает, будет ли именованный вызов вообще выполнен, а в части 6 — харнесс, запускающий и вызов, и проверку. В этой статье харнессом называется управляющая программа, которая собирает каждый промпт, отправляет принятые ею вызовы инструментов и определяет момент завершения задачи — весь обычный код, который вы пишете вокруг модели.

История инструментов изменилась в 2025–2026 годах. MCP, Model Context Protocol, предоставил вендорам единый способ предоставлять внешние сервисы. Агенты с выполнением кода показали, что модель иногда может эффективнее собрать небольшую программу, чем выполнить длинную последовательность JSON-вызовов. Anthropic сообщила о сокращении числа токенов на 98,7% в одном сценарии переноса данных из Google Drive в Salesforce, а статья CodeAct сообщила об улучшении результатов до 20% в своей конфигурации бенчмарка. Эти результаты относятся к их задачам и харнессам, а не доказывают универсальное преимущество выполнения кода.

Я сравниваю JSON-вызовы инструментов, MCP, Skills, CLI-инструменты и выполнение кода именно в таком порядке. В следующем разделе я применяю принципы дизайна Agent-Computer Interface (ACI) к Market Analyst Agent — небольшому исследовательскому агенту на LangGraph, которого я создал для части 1: он получает рыночные данные и пишет аналитический отчёт.

Краткое решение по выбору интерфейса см. в статье Интерфейсы инструментов ИИ-агентов.

Кратко

пять полезных шаблонов интерфейсов покрывают большую часть сценариев использования инструментов агентами. Skills передают инструкции, CLI-инструменты подходят для локальной разработки, MCP подключает общие сервисы, а выполнение кода позволяет компоновать многошаговые операции внутри сэндбокса. JSON-вызовы инструментов остаются самым простым выбором для небольших атомарных действий. Независимо от протокола, Agent-Computer Interface (ACI) должен делать действия понятными, обратную связь — компактной, а ошибки — исправимыми.

Пять способов использования инструментов ИИ-агентами

В части 1 цикл ризонинга выбирал следующий шаг. В части 2 сохранялось состояние, необходимое для его продолжения. Граница инструментов находится между ними: она проверяет предложенный циклом шаг, передаёт вызов на выполнение и возвращает результат обратно в цикл. Эти пять шаблонов по-разному балансируют стоимость в токенах, гибкость и контроль исполнения.

1. JSON-вызовы инструментов: базовый вариант

Исходный шаблон: вы определяете схемы инструментов в JSON, LLM выдаёт структурированные вызовы функций, а ваш код их выполняет. Этот подход хорошо изучен и нормально работает с небольшими наборами инструментов.

# Traditional tool definition — each tool consumes ~550-1,400 tokens (Apideck benchmark)
tools = [
    {
        "name": "get_stock_price",
        "description": "Get the current stock price for a ticker symbol",
        "input_schema": {
            "type": "object",
            "properties": {
                "ticker": {"type": "string", "description": "Stock ticker (e.g., NVDA)"}
            },
            "required": ["ticker"]
        }
    }
]

При 5–10 инструментах накладные расходы приемлемы. Проблема возникает при масштабировании: каждое описание инструмента стоит 550–1 400 токенов. При 20 инструментах вы тратите 11–28 тыс. токенов ещё до того, как агент начинает ризонинг.

2. MCP для общих интеграций

MCP — стандарт, к которому в итоге пришло большинство вендоров. MCP-сервер — это процесс, который публикует список инструментов по определённому wire-протоколу: stdio для локального процесса и HTTP для удалённого. Ваш ИИ-агент запускает MCP-клиент, подключается к серверу, запрашивает список его инструментов и перенаправляет ему вызовы модели — поэтому один и тот же сервер работает с любым клиентом, поддерживающим этот протокол. В декабре 2025 года Anthropic передала протокол Linux Foundation в рамках Agentic AI Foundation, которую она основала совместно с OpenAI и Block. Google, Microsoft и AWS поддерживают фонд в качестве платиновых участников. OpenAI добавила поддержку MCP в Responses API. Согласно анонсу Anthropic о передаче протокола в декабре 2025 года, экосистема насчитывала более 10 000 активных публичных MCP-серверов и более 97 млн ежемесячных загрузок SDK для Python и TypeScript.

MCP подходит для SaaS-интеграций между вендорами (Figma, Notion, Salesforce), сервисов без CLI-эквивалентов и окружений, которым нужна оркестрация OAuth. Его ценность — общий слой обнаружения и транспорта. При этом управление всё ещё зависит от механизмов аутентификации, авторизации, логирования и деплоя конкретного сервера.

История с продакшеном сложнее, чем можно предположить по этим заголовочным цифрам.

Первая проблема — поверхность атаки. Проект Vulnerable MCP Project отслеживает 50 уязвимостей в MCP-серверах, 13 из которых имеют критический уровень; о них сообщили 32 исследователя безопасности. Классы атак включают промпт-инъекции, ошибки валидации входных данных, уязвимости аутентификации и проблемы сетевой безопасности. Первый реальный вредоносный MCP-сервер появился в сентябре 2025 года: пакет под названием postmark-mcp, который отправлял скрытую копию каждого исходящего письма на адрес атакующего. До обнаружения он затронул, по оценкам, 300–500 организаций.

Больше всего меня беспокоит класс атак с отравлением инструментов. Invariant Labs продемонстрировала, что отравленные MCP-инструменты могут эксфильтрировать данные, даже если их никогда не вызывают. Для запуска атаки модели достаточно просто прочитать метаданные инструмента. В бенчмарках MCPTox, где 20 LLM-агентов тестировались на 45 реальных MCP-серверах, доля успешных атак достигала 72,8%.

Операционная проблема — расход токенов. Одна команда, использовавшая MCP-серверы для GitHub, Slack и Sentry (около 40 инструментов), обнаружила, что до первого запроса пользователя внедряется 55 000 токенов определений схем. Другая команда сообщила, что одни только определения инструментов занимали 143 000 из 200 000 доступных токенов (72%).

Anthropic сообщила о сокращении числа токенов в определениях инструментов на 85% благодаря Tool Search Tool: примерно с 77 000 токенов схем до 8 700 — за счёт загрузки только тех трёх–пяти инструментов, которые действительно нужны запросу. Селективная загрузка сохраняет поверхность протокола, но убирает схемы, не нужные текущему запросу.

3. Skills упаковывают экспертизу, а не исполнение

Конец 2025 года принёс стандартизацию agent skills как открытого формата (запущенного в октябре 2025 года и опубликованного как открытый стандарт в декабре 2025 года). Инструменты предоставляют возможности (что могут делать агенты), а skills предоставляют экспертизу (что агенты знают о выполнении сложных задач).

Формат SKILL.md определяет skill как Markdown-файл с YAML frontmatter. Открытый стандарт требует только name и description; в примере ниже также используются два расширения Claude Code — argument-hint и user-invocable, а также его positional-argument placeholder $0:

---
name: deploy
description: Deploy the application to production
argument-hint: "[environment]"
user-invocable: true
---
Deploy the application to the $0 environment (default: staging).
Steps:
1. Run the test suite
2. Build the production bundle
3. Deploy using the deploy script
4. Verify the deployment health check

Skills используют progressive disclosure. При старте загружается около 100 токенов метаданных, а полные инструкции — только после активации skill. Для сравнения: примерно 55 000 токенов могут потребить около 40 MCP-инструментов ещё до начала ризонинга.

К марту 2026 года этот формат поддерживали Claude Code, OpenAI Codex CLI, Cursor, GitHub Copilot, Gemini CLI, Goose, Devin Desktop (ранее Windsurf) и Roo Code. Skills — часть более широкого перехода к действиям ИИ-агентов на основе кода; Victor Dibia прослеживает этот путь от JSON-вызовов функций до генерируемого кода — именно этот паттерн рассматривается в разделе 5.

Используйте skills для доменных знаний, многошаговых процедур и регулярно выполняемых задач, например миграций баз данных или интеграций с платёжными системами. Они подходят для задач, в которых агенту нужны инструкции о том, как использовать уже существующую возможность.

4. CLI- и shell-инструменты

CLI-интерфейсы могут требовать значительно меньше контекста, если модель уже знает нужную команду. Scalekit зафиксировала разницу в 4–32 раза по числу токенов между CLI- и MCP-путями в 75 запусках. Этот кейс измеряет собственные инструменты и задачи Scalekit; он не заменяет сравнение с вашими определениями инструментов и выводом команд.

Для широко задокументированных команд, таких как git, docker, kubectl, gh, curl и jq, часто достаточно небольшого вводного описания схемы. Для менее распространённых или внутренних CLI всё ещё нужны доступная через help документация, примеры и стабильный машиночитаемый вывод.

В руководстве Ugo Enyioha “Writing CLI Tools That AI Agents Actually Want to Use” сформулированы восемь правил дизайна:

  1. Структурированный вывод обязателен — поддерживайте --json
  2. Коды завершения — это управление потоком — используйте разные коды для разных типов ошибок
  3. Команды должны быть идемпотентными
  4. Самодокументируемость --help с реалистичными примерами
  5. Проектируйте с расчётом на композицию — --quiet для простых значений, поддержка stdin
  6. Предоставляйте флаги --dry-run и --yes
  7. Поддерживайте интроспекцию версии
  8. Обрабатывайте аутентификацию через переменные окружения

CLI уступает MCP в типобезопасности, встроенной оркестрации OAuth, обнаружении инструментов и audit trail. По моим наблюдениям, большинство команд сходится на следующем паттерне: CLI — по умолчанию для разработки и локальных операций, MCP — для интеграции с внешними сервисами и корпоративного управления.

5. Выполнение кода для многошаговых задач

Это наиболее существенное, на мой взгляд, изменение в инструментах для агентов. Вместо того чтобы по очереди выдавать структурированный JSON для вызова заранее определённых функций, агент пишет скрипт на Python или bash. Скрипт вызывает несколько инструментов, обрабатывает результаты с помощью циклов и условных конструкций, а в контекст модели возвращает только итоговое резюме.

< EOC_TEXT >Anthropic формализовала этот подход в Programmatic Tool Calling (PTC), который теперь доступен всем пользователям Claude API. Академическая основа подхода — статья CodeAct (Wang et al., ICML 2024). В исследовании проверили 17 LLM и обнаружили, что действия в виде кода обеспечивают до 20% более высокую успешность выполнения задач и требуют на 30% меньше шагов, чем альтернативы на основе JSON.

Три кейса от вендоров показывают, где этот паттерн может быть полезен: ниже — Vercel и Cloudflare, затем пример Anthropic с анализом расходов. Считайте их свидетельствами со стороны вендоров и повторите сравнение на собственных задачах.

  • Vercel переработала d0 — data agent, преобразующий естественный язык в SQL, сократив количество инструментов с 15 до 2 — ExecuteCommand и ExecuteSQL — то есть на 80%, если использовать округление из их поста. На пяти репрезентативных запросах успешность выросла с 4/5 до 5/5, среднее время выполнения сократилось в 3,5 раза (с 274,8 до 77,4 с), а среднее количество токенов уменьшилось на 37% (примерно со 102 тыс. до 61 тыс.). Их формулировка: «Лучшими могут оказаться агенты с наименьшим количеством инструментов».

  • Cloudflare разработала «Code Mode», позволяющий агентам писать TypeScript для вызова API вместо определения схем инструментов, что уменьшает нагрузку на контекст. Логика команды такова: «В обучающей выборке LLM огромное количество реального TypeScript, но лишь небольшой набор искусственных примеров вызова инструментов».

Ниже приведён паттерн из документации Anthropic по PTC. Традиционный вызов инструментов для анализа расходов требует более 20 отдельных инференс-проходов — по одному на каждого участника команды, — при этом все промежуточные данные проходят через контекст. Anthropic сообщает, что код, сгенерированный для ответа на тот же вопрос, сокращает объём данных, попадающих в контекст, с 200 КБ исходных строк расходов — более 2 000 позиций — до 1 КБ результатов. При выполнении кода агент пишет один скрипт:

# Agent generates this code, executes in sandbox
import json
members = get_team_members("engineering")
over_budget = []
for m in members:
    expenses = get_expenses(m["id"], "Q3")
    total = sum(e["amount"] for e in expenses)
    if total > 5000:
        custom = get_custom_budget(m["id"])
        limit = custom["limit"] if custom else 5000
        if total > limit:
            over_budget.append({"name": m["name"], "spent": total, "limit": limit})
# Only this final summary returns to the LLM context
print(json.dumps(over_budget))

LLM видит только итоговую JSON-сводку, а не тысячи строк расходов, обработанных в сэндбоксе. Экономия не специфична для отчётов о расходах: в отдельном материале Anthropic о выполнении кода приведён наиболее наглядный показатель для этого паттерна — пайплайн из Google Drive в Salesforce, где объём данных сократился примерно со 150 000 до 2 000 токенов, то есть на 98,7%.

Очевидное преимущество — эффективность по токенам. Циклы и условные конструкции не требуют дополнительных затрат, ошибки передаются через try/except вместо ризонинга на естественном языке о сбоях, а чувствительные данные остаются в сэндбоксе.

Когда вызов инструментов через JSON всё ещё оправдан: для одиночных атомарных операций, в окружениях без инфраструктуры сэндбоксинга, при использовании небольших моделей со слабой генерацией кода или при наличии требований к аудиту, согласно которым нужно логировать каждый отдельный вызов инструмента.

«Мета-инструменты» в строке об оверхеде по токенам — это несколько обобщённых точек входа, которые нужны агенту, исполняющему код, — например, ExecuteCommand и ExecuteSQL Vercel, — вместо отдельной схемы для каждой базовой операции. Здесь композируемость означает, насколько легко объединить несколько операций в более крупный воркфлоу. Низкая композируемость означает, что после каждого вызова инструмента обычно требуется ещё один round trip к модели; высокая — что интерфейс может передавать промежуточные результаты через пайпы, переменные или процедурные шаги. Ячейки с токенами и успешностью задач суммируют приведённые примеры, а не результаты одного контролируемого бенчмарка по всем пяти столбцам.

Agent-Computer Interface (ACI) для инструментов ИИ-агентов

Термин «Agent-Computer Interface» (ACI) ввели John Yang, Carlos E. Jimenez и их коллеги из Принстона в своей статье о SWE-agent (NeurIPS 2024). Качеству интерфейсов для людей посвящена целая дисциплина — взаимодействие человека и компьютера, или HCI. В статье утверждается, что к агентам на базе языковых моделей стоит применять такой же подход: это «новая категория конечных пользователей со своими потребностями и возможностями, которым пошли бы на пользу специально созданные интерфейсы».

Их результаты абляции позволяют количественно оценить этот эффект. При использовании той же базовой модели GPT-4 Turbo абляция на SWE-bench Lite в статье показала результат 18,0% с полным ACI SWE-agent на 300 задачах против 7,3% в условии только с shell без рабочего демо и 11,0% — с одним демо. Сравнение показывает, что интерфейс и наличие демо существенно изменили производительность в этой конфигурации; оно не позволяет отделить дизайн интерфейса от всех остальных различий и не доказывает, что модель не выполняла никакой работы. В рамках той же абляции интерфейса включение линтинга повысило результат в условии с редактором с 15,0% до 18,0%; на полном тестовом наборе SWE-bench в 51,7% запусков SWE-agent была выполнена хотя бы одна правка, которую линтер отклонил до её применения.

Anthropic сделали ACI фундаментальной концепцией в своём руководстве “Building Effective Agents”, где назвали его одним из трёх ключевых принципов: «Тщательно проектируйте интерфейс агента с компьютером, уделяя большое внимание документации и тестированию инструментов». Их практическая рекомендация такова: «Полезно помнить, сколько усилий обычно вкладывают в интерфейсы взаимодействия человека с компьютером, и планировать такие же инвестиции в создание качественных интерфейсов взаимодействия агента с компьютером».

Четыре принципа ACI на практике

1. Действия должны быть простыми и понятными. Самая распространённая ошибка — оборачивать API-эндпоинты один к одному. Вместо list_users, list_events, create_event реализуйте schedule_event, который за один вызов находит доступные варианты и создаёт расписание. Вместо read_logs реализуйте search_logs, возвращающий только релевантные строки с контекстом.

2. Действия должны быть компактными и эффективными. Объединяйте важные операции в минимально возможное число действий. В Market Analyst Agent я объединяю получение цен и базовых метрик в один инструмент get_stock_snapshot, вместо того чтобы требовать отдельные вызовы для цены, объёма, капитализации и коэффициента PE.

3. Обратная связь от окружения должна быть информативной, но краткой. Не возвращайте сырой HTML или полный payload API. Преобразуйте непонятные ID в семантические имена. В тестировании Anthropic добавили enum response_format, чтобы агент мог запросить краткий ответ (примерно 72 токена) или подробный (примерно 206 токенов), то есть разница в стоимости составляла примерно 3 раза.

4. Валидация должна сдерживать распространение ошибок. Автоматическое обнаружение ошибок помогает агентам быстро распознавать и исправлять ошибки. В SWE-agent пользовательский файловый редактор со встроенным линтингом автоматически отклоняет синтаксические ошибки — именно этот шаг валидации лежит в основе приведённого выше показателя 51,7%. Здесь валидируются входы и выходы инструмента, а не выполняется фильтрация контента вокруг вызова модели, которую обеспечивают продукты-гардрейлы из части 4; для обоих случаев используется одно и то же слово. В Market Analyst Agent я применяю тот же принцип, валидируя аргументы инструментов с помощью схем Pydantic перед выполнением:

from pydantic import BaseModel, Field, field_validator

class StockQuery(BaseModel):
    """Validated input for stock queries.

    Pydantic catches malformed tickers before the API call,
    preventing error propagation through the reasoning loop.
    """
    ticker: str = Field(description="Stock ticker symbol (e.g., NVDA)")
    period: str = Field(default="1mo", description="Time period: 1d, 5d, 1mo, 3mo, 6mo, 1y")

    @field_validator("ticker")
    @classmethod
    def validate_ticker(cls, v: str) -> str:
        v = v.upper().strip()
        if not v.isalpha() or len(v) > 5:
            raise ValueError(f"Invalid ticker format: {v}")
        return v

    @field_validator("period")
    @classmethod
    def validate_period(cls, v: str) -> str:
        valid = {"1d", "5d", "1mo", "3mo", "6mo", "1y"}
        if v not in valid:
            raise ValueError(f"Invalid period: {v}. Must be one of {valid}")
        return v

Рабочие паттерны дизайна инструментов для ИИ-агентов

В руководстве Anthropic “Writing effective tools for agents” инструменты описываются как «новый вид ПО, отражающий контракт между детерминированными системами и недетерминированными агентами».

Рассматривайте описания инструментов как промпт-инжиниринг

Описания должны состоять как минимум из трёх-четырёх предложений и охватывать случаи использования инструмента, обязательные и опциональные параметры, формат вывода и пограничные случаи. Anthropic сообщает, что выбор между неймспейсингом на основе префикса и суффикса (asana_search и search_asana) оказал «нетривиальное влияние» на собственные эвалуации использования инструментов. При этом не уточняется, какая схема лучше, поэтому протестируйте обе на своём наборе инструментов, а не делайте безосновательную ставку на префиксы. Anthropic также передавала транскрипты своих эвалуационных ИИ-агентов обратно в Claude Code и позволяла ему переписывать инструменты. На отложенных тестовых датасетах этот цикл выявил дополнительные улучшения, «превзошедшие даже результаты, которых мы достигли с помощью реализаций инструментов, созданных экспертами», — независимо от того, были ли эти инструменты написаны исследователями вручную или сгенерированы Claude.

# Bad: vague, no context for when to use
tools = [{
    "name": "search",
    "description": "Search for items",
}]

# Good: specific, with input examples and edge cases
tools = [{
    "name": "search_news",
    "description": (
        "Search for recent news articles about a specific stock or company. "
        "Use this tool when the user asks about recent events, earnings, "
        "announcements, or market-moving news for a specific ticker. "
        "Returns up to 10 articles sorted by relevance. "
        "For company competitors rather than news, use search_competitors instead."
    ),
    "input_schema": {
        "type": "object",
        "properties": {
            "query": {
                "type": "string",
                "description": "Search query. Examples: 'NVDA earnings Q3 2025', 'Tesla delivery numbers'"
            },
            "max_results": {
                "type": "integer",
                "description": "Max articles to return (1-10, default 5)",
                "default": 5
            }
        },
        "required": ["query"]
    }
}]

Внутреннее тестирование Anthropic показало, что добавление поля input_examples повысило точность обработки сложных параметров с 72% до 90%.

Возвращайте информативный машиночитаемый вывод

Избегайте низкоуровневых идентификаторов (uuid, mime_type). Преобразуйте неясные ID в семантические имена. Структурируйте ответ так, чтобы агент мог рассуждать по нему без парсинга шаблонного шума:

# Bad: raw API response dumped to agent
def get_stock_snapshot(ticker: str) -> dict:
    response = api.get(f"/v1/quotes/{ticker}")
    return response.json()  # 500+ tokens of nested JSON

# Good: high-signal summary the agent can immediately reason about
def get_stock_snapshot(ticker: str) -> dict:
    data = api.get(f"/v1/quotes/{ticker}").json()
    return {
        "ticker": ticker,
        "price": data["regularMarketPrice"],
        "change_pct": round(data["regularMarketChangePercent"], 2),
        "volume": data["regularMarketVolume"],
        "market_cap_b": round(data["marketCap"] / 1e9, 1),
        "pe_ratio": data.get("trailingPE"),
        "summary": f"{ticker} at ${data['regularMarketPrice']:.2f} "
                   f"({'up' if data['regularMarketChangePercent'] > 0 else 'down'} "
                   f"{abs(data['regularMarketChangePercent']):.1f}%)"
    }

Возвращайте ошибки, с которыми агентный цикл может работать

Обработка ошибок требует четырёх отдельных механизмов, поскольку они работают с разными классами сбоев:

  1. Повторные попытки с экспоненциальной задержкой для временных ошибок
  2. Цепочки fallback моделей при сбоях у провайдера
  3. Роутинг по классификации ошибок: временные ошибки отправляются на повторную попытку, ошибки, которые может исправить LLM, возвращаются агенту с контекстом, а ошибки, требующие участия человека, эскалируются
  4. Восстановление из чекпоинта для переживания падений

В материале Anthropic “Writing effective tools for agents” подчёркиваются понятные ошибки инструментов и дизайн инструментов на основе эвалуаций, но универсальные значения для того, сколько сбоев восстанавливают эти четыре механизма, не приводятся. Измеряйте долю восстановлений, количество повторных попыток и эскалаций на собственном наборе задач.

import httpx
from tenacity import retry, stop_after_attempt, wait_exponential

@retry(
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=1, min=2, max=10),
)
def call_stock_api(ticker: str) -> dict:
    """Fetch stock data with automatic retry on transient failures.

    Mechanism 1 of the four above: exponential backoff for rate limits
    and network blips.
    If all retries fail, the error propagates to the agent with
    enough context to decide whether to try a different approach.
    """
    response = httpx.get(
        f"https://api.example.com/v1/quotes/{ticker}",
        timeout=10.0,
    )
    response.raise_for_status()
    return response.json()

Применение паттернов к Market Analyst Agent

Market Analyst Agent из части 1 наглядно показывает влияние интерфейса.

Консолидация инструментов

В исходном дизайне было более 10 инструментов: get_stock_price, get_company_metrics, get_market_cap, get_pe_ratio, get_volume и так далее. Каждый представлял собой тонкую обёртку над одним API-эндпоинтом. Агенту приходилось для каждого запроса рассуждать о том, какую комбинацию инструментов вызвать.

Я объединил поверхность работы с рыночными данными в 5 высокоуровневых инструментов, следуя принципу ACI о компактных и эффективных действиях. В списке инструментов ReAct-репозитория рядом с ними находятся ещё четыре — загрузчик навыков, две CLI-обёртки и ограниченный встроенный Python-эвалуатор (список разрешённых AST-операций, а не сэндбокс; это рассматривается в части 4), — вместе они покрывают три из пяти описанных выше модальностей. Структурированные результаты инструментов

Каждый инструмент Market Analyst Agent возвращает ответ, прошедший валидацию Pydantic. Это реализует принцип ACI для выходных данных инструмента:

class StockSnapshot(BaseModel):
    """Structured tool response — the agent never sees raw API noise."""
    ticker: str
    price: float
    change_pct: float
    volume: int
    market_cap_b: float
    pe_ratio: float | None
    summary: str  # Human-readable one-liner for direct use in reports

class NewsResult(BaseModel):
    """Each news item is pre-processed for agent consumption."""
    headline: str
    source: str
    date: str
    relevance_score: float  # Pre-ranked so the agent doesn't waste tokens sorting
    key_points: list[str]  # Extracted by the tool, not the agent

Наиболее важным является поле summary. Оно предоставляет агенту готовую строку, которую можно напрямую включить в отчёт без дополнительной обработки. Значения key_points в NewsResult извлекает сам инструмент, а не агент, поэтому агенту не нужно тратить инференс-токены на парсинг текстов статей.

Компромиссы и соображения

Помимо ограничений, специфичных для каждого рассмотренного паттерна, на выбор влияют несколько общих факторов:

  • Операционные затраты различаются по направлениям. Выполнение кода экономит токены, но добавляет латентность холодного старта сэндбокса. MCP экономит время разработки SaaS-интеграций, но увеличивает накладные расходы на деплой сервера. CLI бесплатен на старте, но его сложнее контролировать при масштабировании. Оптимизируйте решение под фактический боттлнек — будь то стоимость токенов, латентность или операционная сложность.

  • Навыки команды имеют значение. Выполнение кода предполагает, что ваши агенты и лежащие в их основе модели умеют надёжно генерировать Python или TypeScript. CLI требует знакомства с соглашениями Unix. MCP требует понимания транспортных протоколов и OAuth-флоу. Выбирайте модальность с учётом сильных сторон команды.

  • Консолидация инструментов может зайти слишком далеко. Если один инструмент накапливает несвязанные режимы и аргументы, агент сталкивается с другой задачей выбора уже внутри схемы. Используйте эвалы выбора инструментов и успешности выполнения задач, чтобы определить подходящую поверхность для вашего workload.

  • Skills основаны на промптах и не обеспечивают enforcement. Skill содержит инструкции, которым агент должен следовать, а не гардрейлы, которым он обязан следовать. Для критичных workflow комбинируйте skills с детерминированной валидацией.

  • Требования к аудиту влияют на выбор. Если нужен полный лог каждого вызова инструмента и его результата, MCP и JSON tool calling изначально предоставляют структурированные audit trail. Выполнение кода создаёт скрипт и его вывод — это полезно, но такие данные сложнее разложить на отдельные действия для отчётности по требованиям compliance.

Три направления развития инструментов для ИИ-агентов в масштабе

Первое — tool RAG для масштабирования. По мере роста toolset’ов до сотен и тысяч инструментов точность наивного выбора инструментов снижается до 13,62%. В статье о RAG-MCP retrieval-augmented generation применили к выбору инструментов: описания инструментов индексируются в векторной базе данных, а для каждого запроса извлекаются только релевантные. Это повысило точность до 43,13% — в 3,2 раза, — и одновременно сократило число токенов в промпте примерно на 50%.

Второе — агенты, создающие собственные инструменты. Фреймворк LATM («LLMs As Tool Makers») заложил двухфазную парадигму: мощная LLM создаёт переиспользуемые Python-функции, а лёгкая LLM ими пользуется. ToolMaker (ACL 2025) автономно преобразует GitHub-репозитории в инструменты, совместимые с LLM, с вероятностью успеха 80%. Оба подхода выходят за рамки использования инструментов — к их созданию, а затем и к управлению библиотекой сгенерированных инструментов.

Третье — двухпротокольный стек A2A + MCP. Agent2Agent Protocol (A2A), созданный Google и переданный Linux Foundation в июне 2025 года, решает задачу, которую MCP не покрывает: коммуникацию между агентами. MCP отвечает за интеграцию агента с инструментом, а A2A — за обнаружение агентов, переговоры между ними и делегирование задач.

Ключевые выводы

  1. Выбирайте интерфейс исходя из действия: JSON-вызовы — для небольших типизированных операций, MCP — для общих сервисов, Skills — для процедур, CLI — для устоявшихся команд, а код в сэндбоксе — для локальной композиции.
  2. Всегда указывайте условия бенчмарка рядом с результатом. CodeAct, Anthropic, Vercel, Cloudflare, Apideck и Scalekit измеряли разные модели, задачи, инструменты и харнессы.
  3. Качество ACI сохраняется при смене протокола. Понятные действия, компактная обратная связь, валидация и полезные сообщения об ошибках помогают независимо от модальности.
  4. Объединяйте пересекающиеся инструменты только после того, как эвалы покажут: меньшая поверхность улучшает выбор инструментов или успешность выполнения задач.
  5. Безопасность должна соответствовать мощности исполнения. Интерфейсам shell и кода нужна изоляция в сэндбоксе; MCP нужны ограниченная область действия идентичности и политика сервера; Skills остаются инструкциями, а не механизмом принудительного контроля.

Следующий слой — политика

В части 4, Безопасность ИИ-агентов, проверка политики помещается между предложенным вызовом инструмента и его выполнением. Это та же граница инструмента, описанная выше, но с точки зрения стороны, которая может сказать «нет». Затем часть 5 помещает инструмент и его сэндбокс внутрь восстанавливаемого рантайма, а часть 6 добавляет второй контракт, которого модель никогда не видит: категорию эффекта, правило повторной попытки и структурированный результат, который проверка приемки может прочитать без парсинга прозы.
