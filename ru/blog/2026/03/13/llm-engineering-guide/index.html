Part I — Основы железа

Эти концепции — arithmetic intensity, иерархия памяти GPU и термины железа — встречаются дальше по всему гайду.

1. Memory-bound vs compute-bound и roofline model

Точка старта для производительности LLM — это arithmetic intensity: на каждый байт данных, которые GPU загружает из памяти, сколько полезных вычислений он делает? От этого зависит, является ли операция compute-bound (упирается в процессор) или memory-bound (упирается в данные, которые нужно загрузить).

У каждого GPU есть порог «critical intensity», где вычислительная способность ровно балансирует пропускную способность памяти. Для NVIDIA H100 (Datasheet, 2023):

989 TFLOPS3.35 TB/s≈295 FLOPs/byte\frac{989 \text{ TFLOPS}}{3.35 \text{ TB/s}} \approx 295 \text{ FLOPs/byte}3.35 TB/s989 TFLOPS​≈295 FLOPs/byte

Две фазы инференса LLM лежат по разные стороны этого порога:

  • Decode — memory-bound. Генерация токенов по одному означает, что нужно загрузить из памяти матрицу весов размером в много гигабайт, чтобы умножить её на один новый токен. В упрощённом анализе 16-bit, batch-one у операции примерно 1 FLOP/byte, то есть почти в 300 раз ниже порога roofline для H100. Этот разрыв объясняет, почему decode в этом режиме не приближается к пиковому вычислительному throughput.
  • Prefill — compute-bound. Обработка входного prompt загружает веса один раз, но умножает их на сотни или тысячи токенов одновременно. Интенсивность уверенно растёт выше 295 и «упирается» в compute units.

Чтобы ускорить decode, работайте над пропускной способностью памяти: сжимайте веса с quantization, уменьшайте overhead KV-памяти с GQA и PagedAttention, а интенсивность повышайте с batching. Чтобы ускорить prefill, работайте над сырой вычислительной мощностью: более быстрые GPU, FP8 compute.

2. Иерархия памяти GPU

У GPU четыре уровня памяти, расположенные как пирамида: снизу — большая, но медленная основная память (HBM), сверху — крошечные, но очень быстрые регистры. Движение данных вверх и вниз по этой пирамиде — главный «пробочный» участок. Самый сложный боттлнек находится между HBM и SRAM, где SRAM примерно в 10 раз быстрее.

От самого быстрого к самому медленному на H100:

  1. Registers — самая быстрая память, напрямую привязана к потокам выполнения. Здесь реально идут вычисления; данные должны быть загружены сюда, чтобы Tensor Cores могли их использовать.
  2. SRAM (Shared Memory) — рабочая память примерно 33 TB/s.
  3. L2 Cache — промежуточный уровень (50 MB) примерно на 12 TB/s. Он играет роль буфера: когда нескольким SM нужны одни и те же веса, им не приходится каждый раз ходить за ними в HBM.
  4. HBM3 — основная память 80 GB, где лежат веса модели и KV cache, на ~3.35 TB/s.

FlashAttention, kernel fusion и PagedAttention уменьшают трафик между этими уровнями. Они дольше держат данные в быстрых SRAM и избегают повторных трансферов в HBM.

3. Glossary по железным терминам GPU

Эти термины будут встречаться по всему остальному гайду.

HBM (High Bandwidth Memory) — стопка чипов DRAM, соединённых через-silicon vias (TSV), монтируется в одном package рядом с GPU die. Поколения: HBM2e (A100, 2 TB/s), HBM3 (H100, 3.35 TB/s), HBM3e (H200/B200, 4.8–8 TB/s). Почему это важно для LLM: decode — memory-bandwidth-bound, значит пропускная способность HBM напрямую определяет TPOT.

GDDR (Graphics DDR) — традиционная графическая память (GDDR6, GDDR6X) в consumer GPU (RTX 4090, L40S). Пропускная способность ниже, чем у HBM, но стоимость за GB меньше. GDDR6X на RTX 4090 даёт ~1 TB/s против 3.35 TB/s у HBM3 на H100.

SM (Streaming Multiprocessor) — базовый compute-блок NVIDIA GPU. Каждый SM содержит CUDA cores, Tensor Cores, shared memory (SRAM) и warp scheduler. У H100 132 SMs; у A100 — 108.

Tensor Cores — специализированные блоки внутри каждого SM для матричных операций multiply-accumulate. Они ускоряют mixed-precision matmuls (FP16, BF16, FP8, INT8), которые доминируют в вычислениях трансформера. Tensor Cores на H100 дают 989 TFLOPS в TF32 против ~67 TFLOPS только от CUDA cores.

CUDA Cores — универсальные блоки для операций с плавающей точкой и целых чисел. Они делают element-wise операции, activation functions и всё, что не matmul. Tensor Cores берут тяжёлую работу LLM; CUDA cores — остальное.

Warp — группа из 32 потоков, выполняющихся синхронно на SM. Это минимальная единица планирования на NVIDIA GPU. Warp specialization разносит разные warps по разным задачам (загрузка данных vs вычисления), обеспечивая конвейеризацию.

NVLink — высокоскоростная интерконнект-связь GPU-to-GPU внутри узла. NVLink 4.0 (H100) даёт 900 GB/s двунаправленно; NVLink 5.0 (B200) достигает 1.8 TB/s. Это критично для tensor parallelism, где GPU должны обмениваться активациями каждый слой.

InfiniBand — высокоскоростная сетевая fabric для коммуникаций между GPU в разных узлах. NVIDIA ConnectX-7 даёт 400 Gb/s на порт. Используется для pipeline parallelism и распределённого обучения между узлами.

RDMA (Remote Direct Memory Access) — позволяет одному GPU читать/писать память другой машины без участия CPU, минимизируя latency. GPUDirect RDMA включает прямые GPU-to-GPU трансферы между узлами. Используется в disaggregated serving для передачи KV cache.

NVMe (Non-Volatile Memory Express) — высокоскоростной SSD-интерфейс для offloading KV cache и ZeRO-Infinity offloading параметров, когда памяти GPU/CPU не хватает. Последовательное чтение 5–7 GB/s на диск (PCIe Gen 4); новые Gen 5 накопители достигают 10–14 GB/s.

TFLOPS / PFLOPS — тера/пета операций с плавающей точкой в секунду. 1 TFLOPS = 10¹² FLOPS. Это стандартная единица измерения вычислительного throughput GPU. H100 выдаёт 989 TFLOPS (TF32); FlashAttention-3 достигает ~1.2 PFLOPS в FP8.

Part II — Основы инференса

Инференс — это та часть системы, которую пользователи реально «чувствуют». Latency, KV cache, двухфазная модель исполнения, attention и quantization между ними задают, насколько быстро, дёшево и надёжно вы можете сервить модель.

4. Latency: TTFT, TPOT и перцентили

Time to First Token (TTFT) — задержка от подачи запроса до первого выходного токена. Определяется prefill-фазой: модели нужно обработать весь prompt, прежде чем она начнёт генерировать, поэтому более длинные промпты обычно повышают TTFT. Цели специфичны для продукта; MLPerf Inference v5.0 использует лимит P99 TTFT ≤\leq≤ 450 ms для интерактивного сценария Llama 2 70B.

Time Per Output Token (TPOT) — средний интервал между последовательными токенами после первого. Он отображает decode-фазу, где каждый шаг memory-bandwidth-bound:

TPOT=E2E Latency−TTFTOutput Tokens−1\text{TPOT} = \frac{\text{E2E Latency} - \text{TTFT}}{\text{Output Tokens} - 1}TPOT=Output Tokens−1E2E Latency−TTFT​

Средняя скорость чтения про себя у взрослого в английском — около 238 слов в минуту для non-fiction (Brysbaert, 2019). Streaming-цели всё равно нужно брать из продуктового тестирования; MLPerf использует лимит P99 TPOT ≤\leq≤ 40 ms для своего интерактивного сценария.

P50 vs P99 latency важен, потому что медиана скрывает хвост. Система с хорошим P50 и плохим P99 может страдать от batching, preemption, queueing или перекоса по нагрузке; нужны трейсы, чтобы это различить.

5. Throughput: токены в секунду и tradeoff с latency

Throughput измеряется в output tokens per second для одновременных запросов. Запросы в секунду (requests per second) сами по себе хуже, потому что 10-токенный ответ и 1,000-токенный ответ имеют очень разные стоимости. Опубликованные бенчмарк-цифры зависят от модели, precision, железа, длин prompt и output, concurrency и SLO. Сравнивайте vLLM, SGLang и TensorRT-LLM на одном harness’е, а не суммируя их «главные» результаты.

Tradeoff такой: при низком concurrency каждый запрос получает отличную latency, но GPU недоиспользуется. Увеличение batch size повышает throughput почти линейно, пока compute не насыщается, после чего latency резко растёт. Goodput — доля запросов, которые выполняют ваши целевые SLO, связывает «сырой» throughput с тем, что действительно испытывают пользователи.

6. KV cache: боттлнек за большинством других боттлнеков

В autoregressive generation каждый новый токен attends ко всем предыдущим токенам. KV cache хранит Key и Value проекции каждого токена на каждом слое, чтобы избежать O(n2)O(n^2)O(n2) пересчёта. Без этого генерация токена nnn требовала бы повторного прогона модели по всем n−1n-1n−1 предыдущим токенам.

KV cache обычно главный источник давления по памяти: он растёт линейно с длиной последовательности, batch size и количеством слоёв:

KVcache=2×L×hkv×dh×s×B×bytesKVcache = 2 \times L \times h_{kv} \times d_h \times s \times B \times \text{bytes}KVcache=2×L×hkv​×dh​×s×B×bytes

где:

  • LLL = число слоёв
  • hkvh_{kv}hkv​ = число KV heads
  • dhd_hdh​ = размерность head
  • sss = длина последовательности
  • BBB = batch size

Конкретные примеры для FP16 и batch size 1: Llama 3 8B при 8,192 токенах использует ~1.0 GB KV cache; при 128K токенах — 16 GB. Llama 3 70B при 128K токенах требует ~40 GB для одной последовательности, половину VRAM H100. При production batch size KV cache легко превышает память под веса. Наивные реализации теряют 60–80% выделенной KV-памяти из‑за фрагментации — ровно проблему, которую решает PagedAttention.

Ключевые оптимизации: GQA (меньше KV heads), квантизация KV cache (FP8/INT8), PagedAttention (block-based allocation с <4% waste) и offloading KV cache на CPU или NVMe.

7. Prefill vs decode: две фазы, два боттлнека

Prefill phase обрабатывает входной prompt параллельно и заполняет KV cache. Её большие матричные умножения делают её compute-bound, поэтому prefill в большой степени определяет время до первого токена (TTFT). Decode phase генерирует по одному токену за раз. На каждом шаге читаются веса модели и KV cache из HBM, значит decode memory-bandwidth-bound и является главным драйвером TPOT.

Chunked prefill разбивает prompt на чанки фиксированного размера (например, 512 токенов), а не обрабатывает всё сразу. Длинный prefill больше не блокирует текущие decode-запросы: compute-bound и memory-bound работа ко-расписываются на одном GPU. Бенчмарки vLLM показывают +50% throughput (Agrawal et al., 2024). Цена — чуть более высокий TTFT для нового запроса.

Disaggregated serving размещает prefill и decode на отдельных пулах GPU: так каждый пул может оптимизировать под свой боттлнек. Splitwise и DistServe описывают этот паттерн. Пулы передают данные KV-cache по быстрому интерконнекту вроде RDMA, поэтому стоимость коммуникаций становится частью дизайна.

8. GQA и MQA: сжатие KV cache

Стандартное Multi-Head Attention (MHA) даёт каждому query head собственные K и V head. Multi-Query Attention (MQA) делит один KV head между всеми query heads — это экстремальное сокращение. Grouped-Query Attention (GQA) — практический компромисс: группы query heads делят один KV head.

Llama 3 70B использует 64 query heads, но только 8 KV heads, то есть 8x уменьшение KV cache относительно той же архитектуры с одним KV head на каждый query head. Llama 3.1 405B использует 128 query heads и 8 KV heads, то же самое расчёт даёт 16x reduction (Meta, 2024). Ainslie et al. сообщают, что качество GQA близко к MHA в протестированных моделях, при этом скорость приближается к MQA. Меньший KV cache может позволить большие batch’и, но реальная выгода по latency и throughput всё равно зависит от kernel’а и workload’а.

9. Quantization: обмен битов на скорость и память

Quantization уменьшает точность весов модели и/или активаций. Основные tradeoffs:

AWQ (Activation-Aware Weight Quantization) находит <1% наиболее значимых весов, анализируя magnitude активаций, и применяет per-channel scaling, чтобы их защитить. Нужны всего 128–1,024 calibration tokens, и метод выиграл MLSys 2024 Best Paper Award. GPTQ использует информацию о втором порядке (Hessian) для layer-wise квантизации и требует больше calibration data. bitsandbytes (библиотека Тима Деттмерса) квантизирует во время загрузки модели без отдельного шага pre-processing; формат NF4 используется для QLoRA fine-tuning. FP8 на Hopper-подобном железе уменьшает память под веса вдвое относительно FP16/BF16, но качество и скорость всё ещё зависят от модели, калибровки и kernel’а.

Serving kernel может быть так же важен, как и сам алгоритм квантизации. В сравнении, обсуждаемом в Section 10, те же квантизированные веса показывали 2.6x разницу по throughput между kernel’ами.

Part III — Оптимизации инференса

Каждая софт-техника здесь таргетит конкретный боттлнек: FlashAttention использует разрыв SRAM-HBM, PagedAttention убирает фрагментацию KV cache, continuous batching удерживает GPU занятым.

10. CUDA kernels и kernel fusion

CUDA kernel — это функция, написанная для GPU, которая исполняется параллельно на тысячах потоков. Когда CPU вызывает kernel, GPU распределяет работу по своим SMs: каждый SM запускает несколько warps по 32 потоков, и каждый поток обрабатывает часть данных. Любая операция в инференсе LLM — от матмулов до token sampling — в итоге сводится к запуску kernel. Один forward pass через модель на 70B вызывает сотни или тысячи kernel launches, а разрыв между наивным и оптимизированным kernel’ом может определить, выполнит ли система свой latency SLO.

Основные категории kernel’ов в LLM serving:

  • GEMM kernels для матричного умножения, которые доминируют и в prefill, и в decode compute.
  • Attention kernels вроде FlashAttention, которые «тайлят» вычисления так, чтобы оставаться в SRAM, а не проливать в HBM.
  • Fused kernels, объединяющие несколько операций (например, add + layer norm или QKV projection) в один launch, чтобы пропустить промежуточные круги по HBM.
  • Sampling kernels, которые превращают logits в token IDs через top-k, top-p или temperature sampling.

Качество kernel’ов часто важнее, чем алгоритм квантизации. Те же INT4-веса, поданные через Marlin (оптимизированный FP16xINT4 kernel), дают 712 tokens/s против 276 tokens/s у vanilla GPTQ, то есть 2.6x разницу throughput исключительно из‑за лучшего использования GPU. Marlin достигает этого через asynchronous memory fetching и очереди shared memory, которые держат Tensor Cores занятыми вместо ожидания HBM.

Triton снижает порог для написания custom kernel’ов: он даёт GPU-программирование через Python вместо «сырого» CUDA C++, поэтому оптимизация на уровне kernel’ов становится доступной ML-инженерам, а не только специалистам по GPU. Большинство оптимизаций далее в этой части (FlashAttention, fused kernels, PagedAttention) — это либо лучшие kernel’ы, либо более умная оркестрация kernel launch’ей.

Kernel fusion объединяет последовательные операции в один GPU kernel и пропускает промежуточные записи в HBM. Типичные фьюзы: QKV projection, attention + softmax, add + RMSNorm (FlashNorm) и активация SwiGLU (DeepFusionKernel). Triton делает эти kernel’ы доступными через Python. Точные выигрыши по числу launch’ей и utilization зависят от графа модели, компилятора, GPU и serving framework’а, поэтому профилируйте развернутый стек, а не полагайтесь на универсальный процент.

11. FlashAttention: тайлинг attention, чтобы жить в SRAM

Обычная attention материализует полную N×NN \times NN×N матрицу attention в HBM, что стоит O(N2)O(N^2)O(N2) памяти и порождает много memory traffic. Идея FlashAttention — вообще не материализовать эту матрицу. Она делит Q, K, V на блоки, которые помещаются в SRAM, внутри каждого блока считает partial attention, а затем объединяет результаты с онлайн softmax (инкрементально отслеживая running max и sum по блокам). Память падает с O(N2)O(N^2)O(N2) до O(N)O(N)O(N), а чтения из HBM уменьшаются на порядок.

Каждая версия таргетит боттлнек своего поколения GPU:

  • FlashAttention v1 (A100, 2022) показала, что идея тайлинга плюс онлайн-softmax работает. 2–4x speedup над стандартной attention, но utilization всего 25–40%, потому что scheduling kernel’а оставлял многие SM простаивающими.
  • FlashAttention v2 (A100, 2023) переработала параллелизм: она делит вычисления не по batch и heads, а по dimension sequence. На A100 достигалось 50–73% utilization, примерно в 2 раза быстрее v1.
  • FlashAttention v3 (H100 Hopper, 2024) добавила warp specialization (отдельные warps для data movement и математики) и GEMM-softmax pipelining, чтобы оверлапить загрузки памяти с вычислениями. 75–85% utilization на H100 и до ~1.2 PFLOPS в FP8. Spotlight на NeurIPS 2024.
  • FlashAttention v4 (B200 Blackwell, 2026) отвечает на новый боттлнек: на Blackwell throughput tensor core растёт настолько быстро, что ограничением становятся non-matmul операции (softmax exponentials, rescaling). FA4 софт-эмулирует exponential через полиномиальные приближения на FMA unit’ах, использует conditional rescaling для снижения overhead и хранит промежуточные значения в выделенной tensor memory (TMEM) Blackwell вместо registers. Итог: 1,605 TFLOPS/s на B200 в BF16, в 1.3 раза быстрее cuDNN 9.13 и в 2.7 раза быстрее Triton.

12. FlashDecoding: параллелизация decode-боттлнека

Стандартная FlashAttention удерживает GPU занятым, разбивая работу по batch size и query length. Во время decode модель генерирует ровно 1 токен за шаг (query length = 1). Если произведение batch size и числа attention heads меньше общего числа SM (108 на A100), большинство GPU простаивает, а несколько unit’ов последовательно «перемалывают» историю токенов.

FlashDecoding решает это, добавляя новое измерение параллелизма: KV sequence length сама по себе. Он режет KV cache на меньшие чанки и распределяет их по всем GPU-процессорам, которые иначе простаивали бы, чтобы оценивать параллельно; затем объединяет partial вычисления через log-sum-exp reduction.

Результат — до 8x end-to-end ускорения decode на длинных последовательностях (контекст 64K) и примерно константное время decode на токен. Генерация токена 60,000 остаётся почти такой же быстрой, как генерация токена 100.

13. Continuous batching vs static batching

Static batching ждёт завершения всех последовательностей в батче перед стартом следующего. Поэтому короткие последовательности «съедают» GPU cycles простоями после достижения end-of-sequence. Continuous batching (введён в Orca paper, OSDI 2022) работает на уровне итераций: на каждом шаге decode завершённые последовательности удаляются, а новые добавляются.

В бенчмарке OPT-13B от Anyscale оптимизированный static batching дал 4x к наивной базе, continuous batching — 8x, а vLLM с continuous batching плюс PagedAttention достиг 23x (Anyscale, 2023). Continuous batching также увеличивает давление на KV allocation, поэтому обычно его комбинируют с paged memory management.

14. PagedAttention: виртуальная память для KV cache

PagedAttention в vLLM применяет идею OS virtual memory к управлению KV cache. KV cache делится на blocks фиксированного размера (обычно 16 токенов), blocks выделяются по требованию при генерации, а логические (последовательные) позиции мапятся на физические (разбросанные) места в памяти через block tables. Несколько запросов, разделяющих префикс (system prompts, beam search), могут ссылаться на одни и те же физические blocks.

Ранние системы тратили 60–80% памяти KV cache из‑за фрагментации и pre-allocation. PagedAttention снижает это до <4%, что позволяет поднимать throughput в 2–4x при той же latency и до 24x относительно HuggingFace Transformers (vLLM Blog, 2023).

15. Speculative decoding: несколько токенов за один forward pass

Маленькая draft model генерирует KKK кандидатов, затем большая target model проверяет все KKK токены за один forward pass. Правильные токены принимаются; первый неверный отвергается. Качество выхода математически идентично target model в одиночку, так что это lossless speedup.

Работает потому, что decode LLM memory-bandwidth-bound: проверка KKK токенов стоит примерно столько же, сколько генерация 1 токена, потому что и там и там все веса загружаются один раз. Типичные ускорения — между 1.5x и 3x, а методы вроде EAGLE-3 достигают до 6.5x. Варианты включают Medusa (дополнительные prediction heads, отдельной модели не нужно), prompt lookup decoding (n-gram matching по входу, free) и EAGLE (feature-level extrapolation).

На больших batch sizes лишние draft- и verification-работы могут «съесть» выигрыш: в одной цитируемой оценке при таком режиме отмечен 1.4–1.8x slowdown. Speculative decoding особенно перспективен, когда serving batch достаточно мал, а acceptance draft’а достаточно высока.

16. Prefix caching и повторное использование KV cache

Вместо того чтобы выбрасывать KV cache после завершения запроса, prefix caching сохраняет его для reuse на новых запросах, которые делят те же префиксные токены. Это сокращает лишний prefill для system prompts, few-shot примеров, RAG контекста и истории multi-turn диалога.

vLLM’s Automatic Prefix Caching хеширует KV blocks и использует глобальную hash table для lookup. SGLang’s RadixAttention хранит radix tree из закэшированных KV tensors с гранулярностью по токенам. Оба зависят от повторяющихся токено-идентичных префиксов, поэтому важно сообщать hit rate вместе с latency/throughput.

17. Streaming на практике

Streaming отправляет токены клиенту по мере генерации, не дожидаясь полного ответа. Многие serving framework’ы реализуют это через Server-Sent Events: клиент открывает долгоживущую HTTP-сессию, а сервер пушит каждый токен или батч токенов как data: event. TTFT определяет момент, когда пользователь впервые видит output; TPOT помогает понять, насколько «гладко» это ощущается. Цель задавайте через продуктовые тесты и выбранную модель взаимодействия.

На стороне клиента streaming заставляет принимать решения о buffering. Отрисовка токен-в-токен может приводить к визуальному jitter, особенно с markdown или code blocks, которым нужен контекст в несколько токенов, чтобы корректно форматироваться. Частые паттерны: word-level buffering (копите токены до границы пробельного разделителя), line-level buffering (ждите newline перед рендером) и adaptive buffering (сразу рендерите прозу, буферизуйте code blocks). Параметр stream_options: {"include_usage": true} в OpenAI-compatible APIs возвращает количество токенов в финальном SSE event, что позволяет корректно отслеживать стоимость для streamed responses.

Chunked prefill — именно то, что позволяет streaming держаться под нагрузкой. Без него один длинный prefill может «столбом» блокировать delivery токенов для всех остальных конкурентных пользователей.

18. Основы transformer architecture

Современный decoder-only transformer (GPT, Llama) — это стек одинаковых слоёв, в каждом из которых два sub-block: attention и feed-forward. Каждый sub-block обёрнут в residual connection и normalization. Ключевые компоненты:

Multi-Head Attention — механизм, который позволяет каждому токену посмотреть на все остальные токены и решить, что релевантно. Вход проецируется в три матрицы: Queries (что я ищу?), Keys (что у меня есть?), и Values (какую информацию я несу?). Затем scores attention вычисляются как:

Attention(Q,K,V)=softmax(QKTdk)V\text{Attention}(Q, K, V) = \text{softmax}\left(\frac{QK^T}{\sqrt{d_k}}\right)VAttention(Q,K,V)=softmax(dk​​QKT​)V

QKTQK^TQKT dot product измеряет сходство для каждой пары токенов. Деление на dk\sqrt{d_k}dk​​ не даёт dot products разрастись слишком сильно (что могло бы загнать softmax в область исчезающих градиентов). softmax превращает scores в вероятности, а умножение на VVV даёт взвешенную комбинацию value vectors. Прогон этого параллельно по нескольким heads позволяет модели одновременно «attend’ить» к разным отношениям (один head — синтаксис, другой — coreference и т.д.).

Feed-Forward Network (FFN) — после того как attention решила какие токены релевантны, FFN решает что делать с этой информацией. Современные LLM используют SwiGLU вместо исходного FFN с двумя матрицами и ReLU:

SwiGLU(x)=Swish(xW1)⊗xW2\text{SwiGLU}(x) = \text{Swish}(xW_1) \otimes xW_2SwiGLU(x)=Swish(xW1​)⊗xW2​

SwiGLU использует три weight matrices вместо двух и сглаженную активацию Swish вместо ReLU. Она применяется в семействах моделей, включая Llama, Mistral, Qwen и Gemma. FFN обычно занимает около двух третей всех параметров модели, хотя точная доля зависит от архитектуры.

Residual Connections — каждый sub-block добавляет выход обратно во вход: Output=Input+Sublayer(Input)\text{Output} = \text{Input} + \text{Sublayer}(\text{Input})Output=Input+Sublayer(Input). Без этой skip connection градиенты исчезли бы при backpropagation через 80–128 слоёв. Residual создаёт путь, по которому информация и градиенты могут идти напрямую из ранних слоёв в поздние.

RMSNorm — распространено во многих современных LLM-семействах. LayerNorm нормализует, пере-центрируя (вычитая mean) и re-scaling (деля на стандартное отклонение). RMSNorm пропускает вычитание mean и делает только re-scaling; в статье заявлены 7–64% speedups по протестированным моделям без падения качества в этих экспериментах. Также часто встречается pre-norm (нормализация до attention или FFN), потому что это улучшает стабильность градиентов.

19. Почему decoder-only доминируют

Изначальный Transformer (2017) имел и encoder, и decoder. Затем поле разделилось на три семейства архитектур, и одно стало дефолтом для генеративного AI.

Encoder-only модели (BERT, RoBERTa) используют bidirectional attention: каждый токен attends ко всем остальным токенам в обе стороны. Это даёт богатые представления для задач понимания (классификация, NER, semantic similarity), но не позволяет генерировать текст autoregressively. Encoder-only модели всё ещё часто используются как backbone для embedding models, rerankers и лёгких классификаторов (например, BERT-based routers в RouteLLM).

Encoder-decoder модели (T5, BART, исходный Transformer) разделяют понимание и генерацию. Encoder обрабатывает полный input bidirectional attention, а decoder генерирует output autoregressively, attend’я к представлениям encoder через cross-attention. Это естественно выгодно для задач sequence-to-sequence вроде перевода, где input и output — разные последовательности. Google T5 показал, что любую NLP-задачу можно представить как text-to-text, а encoder-decoder модели остаются основой некоторых специализированных систем (Whisper для распознавания речи, FLAN-T5 для instruction following).

Decoder-only модели (GPT, Llama, Mistral, Gemini) используют causal (unidirectional) attention: каждый токен attend’ит только к предыдущим токенам. Всё сводится к next-token prediction: «input» — это начало последовательности, «output» — её продолжение. Вот четыре причины, почему эта архитектура победила:

  1. Эффективность KV cache. KV cache от предыдущих токенов остаётся валидным при генерации новых токенов, поэтому вам не нужно дискардить или пересчитывать его. Encoder-decoder модели должны держать два разных attention cache (self-attention плюс cross-attention поверх output’ов encoder), что добавляет memory overhead и усложняет архитектуру.

  2. Простота обучения. Objective — простое next-token prediction по raw text. Нет необходимости в парных input-output данных (как для translation-моделей) или masked-token reconstruction (как для BERT). Можно обучать практически на любом тексте из интернета, книг и кода без специального препроцессинга — это огромный плюс при масштабировании данных до триллионов токенов.

  3. Архитектурная простота. Один модуль отвечает за всё: тот же transformer block, повторённый LLL раз. Нет encoder-decoder cross-attention слоёв, нет отдельного encoder stack. Это делает стратегии параллелизма более прямолинейными (Section 33) и сокращает поверхность для инженерных оптимизаций. FlashAttention, quantization и speculative decoding должны таргетить только один паттерн attention.

  4. In-context learning. Decoder-only модели естественно сильны в few-shot learning: примеры, инструкции и запрос — это просто токены в одной и той же последовательности. Модель не разделяет «input» и «output»; она предсказывает следующий токен, учитывая всё, что было до него. GPT-3 впервые показал это в масштабе, и decoder-only модели хорошо подошли под роль универсального assistant’а.

20. Mixture of experts

MoE заменяет dense FFN в каждом transformer-слое на набор нескольких маленьких expert FFNs плюс лёгкий gating router. Router вычисляет score для каждого expert (обычно softmax по learnable linear projection’ам) и выбирает top-kkk expert’ов на токен. Вычисляются только активированные эксперты, поэтому модель может иметь огромную суммарную capacity при низкой стоимости на токен. Это sparse conditional computation: total parameters задают то, что модель может представить, а active parameters задают то, во сколько это обходится при прогоне.

shared expert в DeepSeek-V3 активируется для каждого токена. Он даёт базовое представление, на которое routed experts могут «специализироваться» сверху.

У обучения MoE есть три повторяющиеся проблемы: load imbalance, expert collapse и overhead коммуникаций для expert parallelism. Традиционные MoE модели добавляют auxiliary loss, чтобы штрафовать несбалансированный routing, но этот loss может конкурировать с основной целью. DeepSeek-V3 делает иначе: добавляет bias terms вне backpropagation — система снижает score перегруженных expert’ов и повышает score недоиспользуемых. В статье заявлено лучшее балансирование routing без tradeoff с auxiliary-loss в их настройке.

21. Tokenization: BPE, SentencePiece и tiktoken

LLM не «видят» текст. Они видят последовательности integer token IDs. tokenizer разбивает raw text на токены (subword pieces) и мапит каждый на ID. Выбор tokenizer влияет на качество модели, скорость инференса и языковую «честность» (multilingual fairness).

Byte Pair Encoding (BPE) — самый распространённый алгоритм. Он итеративно сливает (merge) самые частые соседние пары в обучающем корпусе. Упрощённый пример:

  1. Стартуем с vocabulary на уровне символов: [l, o, w, e, r, _]
  2. Самая частая пара — (l, o) → merge в lo → vocabulary: [l, o, w, e, r, _, lo]
  3. Следующая по частоте пара — (lo, w) → merge в low → vocabulary добавляет low
  4. Продолжаем, пока vocabulary не достигнет целевого размера (например, 128K токенов)

Частые слова типа “the” становятся single tokens, а редкие слова вроде “defenestration” разбиваются на subword pieces вроде ["def", "en", "est", "ration"]. Tradeoff — размер словаря vs длина последовательности.

Большинство production-использований покрываются тремя реализациями tokenizer:

  • SentencePiece трактует input как сырой byte stream без языково-специфичной предобработки (нет pre-tokenization пробелами или пунктуацией), поэтому он language-agnostic и особенно важен для не-Latin скриптов. Поддерживает и BPE, и unigram. Используется Llama 1/2, T5 и Mistral.
  • tiktoken — Rust-based tokenizer от OpenAI, использующий byte-level BPE. Его скомпилированное Rust ядро в 3–6 раз быстрее, чем Python-based альтернативы. Llama 3 перешла с SentencePiece на алгоритм tiktoken.
  • Hugging Face Tokenizers — широко используемая Rust-библиотека с поддержкой BPE, WordPiece и Unigram.

context window — максимум токенов, которые модель может обработать в одном forward pass. Он сильно вырос:

Здесь есть базовая проблема: механизм attention воспринимает input как set, а не как последовательность. В нём нет встроенного понятия порядка слов. Без positional information выражения “the cat sat on the mat” и “the mat sat on the cat” дали бы идентичные представления. Positional encodings «вкалывают» порядок так, чтобы модель понимала, где находится каждый токен.

Есть три распространённых подхода:

  • RoPE (Rotary Position Embeddings) кодирует позицию токена через вращение его query и key vectors на угол, пропорциональный позиции. Близкие токены получают близкие вращения, поэтому их dot product (attention score) остаётся высоким. Далёкие токены получают очень разные вращения, что кодирует относительные расстояния. RoPE — стандарт для почти всех современных open LLM (Llama, Mistral, Qwen), потому что она хорошо работает с относительными позициями и вычислительно дешёвая.

  • ALiBi (Attention with Linear Biases) не меняет embeddings, а добавляет штраф напрямую в attention scores: чем дальше два токена друг от друга, тем больше отрицательный bias. Никаких learnable параметров, никаких дополнительных вычислений. Позволяет некоторую экстраполяцию за пределы training length, но заметно деградирует на контексте 2x+ от training.

  • YaRN (Yet another RoPE extensioN) расширяет RoPE-модель за пределы её training context. Она группирует frequency dimensions в три категории и масштабирует каждую по-разному. В статье указано в 10 раз меньше fine-tuning tokens и в 2.5 раза меньше training steps, чем в базовом подходе position-interpolation.

Part V — Обучение и выравнивание

Обучение — там, где появляются способности. В этой части: pretraining, efficient fine-tuning (LoRA, mixed precision), scaling laws и методы alignment.

23. Pretraining, fine-tuning и alignment

Pretraining — self-supervised next-token prediction на большом корпусе. Вычисления растянуты на много порядков; Llama 3 405B использовала 3.8×10253.8 \times 10^{25}3.8×1025 FLOPs, например. Supervised fine-tuning (SFT) адаптирует pretrained модель под task-specific размеченные данные. RLHF / RLAIF использует preference data для формирования поведения: классический pipeline RLHF собирает сравнения, тренирует reward model, затем оптимизирует policy. RLAIF заменяет часть human judgments на feedback, сгенерированный AI.

Compute зависит от размера модели, длины sequence, объёма данных, оптимизатора и метода. PPO держит больше состояния модели, чем SFT, потому что типичная настройка включает policy, reference, reward и critic/value модели. Я подробно описывал полный фреймворк принятия решений для fine-tuning в LLM Fine-Tuning Guide.

24. LoRA и QLoRA: parameter-efficient fine-tuning

LoRA замораживает pretrained weights и вставляет trainable low-rank matrices AAA (r×kr \times kr×k) и BBB (d×rd \times rd×r), так что обновлённый weight становится W0+BAW_0 + BAW0​+BA. Статья LoRA сократила GPT-3 175B до примерно 18 млн trainable parameters в их настройке. Rank — тюнинговый параметр, а не правило сложности задач; выбирайте его через sweep качества и памяти. Адаптеры LoRA после обучения можно слить в base weights, чтобы избежать отдельного adapter path на инференсе.

QLoRA загружает базовую модель в 4-bit NF4 quantization, а во время обучения обучает LoRA adapters в BF16. NormalFloat4 размещает больше квантованных уровней около нуля, где плотность весов максимальна. В статье модель на 65B файн-тюнили на одной GPU с 48 GB и получили результаты, близкие к 16-bit baseline. Его runtime и memory trade-offs зависят от конкретного тестового стека.

25. Обучение в mixed precision

Любой floating-point формат распределяет свои биты по трём полям: sign (всегда 1 бит), exponent (задаёт динамический диапазон) и mantissa (задаёт precision). Больше exponent бит означает больший диапазон представимых величин; больше mantissa бит — более тонкие различия между близкими значениями. Integer форматы не имеют exponent и представляют только равномерно распределённые целые числа в фиксированном диапазоне.

BF16 имеет тот же диапазон, что и FP32: range задаётся exponent field, и BF16 сохраняет все 8 exponent bits из FP32. При этом «отдают» mantissa bits вместо (7 вместо 23), меняя precision на двукратное уменьшение памяти, но избегая overflow/underflow проблем, которые преследуют обучение в FP16. FP16 имеет всего 5 exponent bits, поэтому её диапазон ограничен ~65K. Градиенты регулярно выходят за это, поэтому обучение FP16 требует loss scaling: умножать loss на большую константу перед backpropagation, а затем делить градиенты. BF16 делает loss scaling не обязательным.

Integer форматы необычны для «главной» вычислительной арифметики обучения, потому что backpropagation требует широкий динамический диапазон. Их широко применяют для инференса, где замороженные веса можно мапить на откалиброванные масштабы. Квантизация весов INT4 сокращает 7B модель примерно с 14 GB до 3.5 GB до runtime overhead; качество нужно измерять для выбранной модели и метода.

FP8 training на H100 через Transformer Engine использует E4M3 там, где важна точность, и E5M2 там, где нужен более широкий диапазон. NVIDIA заявляет до 75% более быстрый wall-clock time в тестовой конфигурации 175B. DeepSeek-V3 использовала FP8 mixed precision и сообщила около $5.6 million в rental-equivalent compute для финального training run, исключая R&D и инфраструктуру.

26. Gradient checkpointing

Каждый слой forward pass производит промежуточный output — activation:

Input→[Layer 1]→activation1→[Layer 2]→activation2→[Layer 3]→output\text{Input} \rightarrow [\text{Layer 1}] \rightarrow \text{activation}_1 \rightarrow [\text{Layer 2}] \rightarrow \text{activation}_2 \rightarrow [\text{Layer 3}] \rightarrow \text{output}Input→[Layer 1]→activation1​→[Layer 2]→activation2​→[Layer 3]→output

Обычно все активации должны оставаться в памяти, потому что backpropagation использует их для вычисления градиентов. Для глубокого трансформера хранящиеся активации могут занять больше памяти, чем сами веса модели.

Gradient checkpointing меняет compute на память: он выбрасывает большую часть активаций и пересчитывает их «на лету» во время backprop. Стандартная стратегия (Chen et al., 2016) делит сеть из nnn слоёв на n\sqrt{n}n​ равномерно распределённых сегментов и сохраняет только boundary activation каждого сегмента. Эти сохранённые boundary — «checkpoints». Все промежуточные активации внутри сегмента удаляются сразу.

Когда backward pass доходит до слоя внутри сегмента, его активации пересчитываются от ближайшего checkpoint. Это снижает память под активации с O(n)O(n)O(n) до O(n)O(\sqrt{n})O(n​), что на практике даёт 60–70% reduction, но с ценой примерно одного дополнительного forward pass (~20–33% больше compute). FlashAttention применяет ту же идею внутри attention: не материализует полную attention matrix. В HuggingFace это можно включить через gradient_checkpointing=True.

27. DeepSpeed ZeRO stages

При стандартном data parallelism каждый GPU хранит полную копию весов модели, градиентов и optimizer states. Для Adam каждый параметр занимает 2 байта для FP16 weight + 4 байта для FP32 master weight + 4 байта для momentum + 4 байта для variance + 2 байта для градиента, то есть 16 байт на параметр. Модель на 7.5B параметров требует ~120 GB на GPU, и каждый GPU хранит то же самое. На 64 GPU это 64 одинаковые копии по 120 GB — много потерь.

DeepSpeed ZeRO убирает это дублирование: он шардит эти компоненты по GPU вместо репликации:

  • Stage 1 — partition optimizer states. Каждый GPU хранит только 1/N optimizer states (momentum и variance у Adam, 8 bytes/param). Когда GPU нужно обновить weight, он обновляет только свой slice и broadcast’ит результат. Память падает с ~120 GB до ~31 GB на GPU.
  • Stage 2 — также partition gradients. Градиенты (2 bytes/param) больше не all-reduce’ятся на каждый GPU. Каждый GPU получает только нужный slice через reduce-scatter. Память падает до ~16 GB на GPU.
  • Stage 3 — также partition model weights. Каждый GPU хранит только 1/N FP16 весов. Перед каждым forward или backward проходом слоя GPU делает all-gather, чтобы временно восстановить полные веса слоя из остальных GPU, затем считает и выбрасывает собранные веса. Память падает до ~1.9 GB на GPU.

Tradeoff — коммуникации. Stage 1 даёт минимальный overhead, и Stage 2 заменяет all-reduce на reduce-scatter с сопоставимой стоимостью. Stage 3 требует all-gather вызовов перед каждым слоем и в forward, и в backward проходах — примерно 1.5x volume коммуникаций против стандартного data parallelism.

ZeRO-Infinity расширяет Stage 3 за счёт offload partitioned states в CPU RAM и даже NVMe SSD. Это делает возможным training моделей с триллионами параметров на ограниченных GPU-кластерах. Цена — сильное падение скорости (NVMe примерно ~500x медленнее HBM), поэтому ZeRO-Infinity используют, когда модель действительно не помещается в GPU + CPU память.

28. FSDP: sharding, нативный для PyTorch

Fully Sharded Data Parallel (FSDP) — встроенный в PyTorch ответ DeepSpeed ZeRO-3. Он шардит параметры, градиенты и optimizer states по GPU, используя ту же базовую идею. Механика для каждого слоя — это простой цикл:

  1. All-gather: собрать полные параметры из всех GPU (временно восстановить полный layer).
  2. Compute: выполнить forward или backward проход этого слоя.
  3. Free: освободить собранные параметры сразу; каждый GPU хранит только свой shard.
  4. Reduce-scatter: распространить градиенты так, чтобы каждый GPU получил только назначенный slice.

Так как FSDP нативен в PyTorch, он интегрируется прямо с PyTorch debugging tools, профайлерами и torch.compile. Производительность относительно DeepSpeed ZeRO-3 зависит от политики обёртки, коммуникационной топологии, offload настроек и размера модели, поэтому сравнивайте их на одном и том же кластере.

29. Scaling laws и Chinchilla trap

Chinchilla scaling (DeepMind, 2022) нашло compute-optimal allocation около 20 training tokens на параметр при сделанных допущениях. Эта objective не включает cost downstream serving. Если меньшая модель, обученная на большем объёме данных, достигает нужного качества, она может оказаться дешевле в high-volume inference lifecycle.

Исправление — перетренировать меньшие модели на намного больших данных:

30. RLHF, DPO, GRPO и landscape выравнивания

Alignment направляет pretrained модель к желаемым инструкциям, предпочтениям и политикам безопасности. Сам по себе он не гарантирует ни истинность, ни безопасное поведение. Методы ниже балансируют сложность реализации, требования к данным, exploration и стабильность обучения.

Классический RLHF pipeline: SFT → сбор human preference pairs → обучение reward model на этих парах → fine-tuning policy через PPO (Proximal Policy Optimization). PPO держит 4 копии модели в памяти одновременно (policy, reference, critic/value model, reward model) и сильно чувствителен к гиперпараметрам. Также PPO подвержен reward hacking: модель начинает «эксплуатировать» особенности reward model, например выдавать длинные ответы с уверенным тоном, вместо реального улучшения качества.

DPO (Direct Preference Optimization) пропускает learned reward model и online RL loop: он оптимизирует loss прямо на preference pairs. Это упрощает training pipeline. Стандартный DPO offline: он обучается на фиксированном датасете и не исследует новые ответы в update loop. Насколько это ограничение важно — зависит от задачи и coverage данных.

GRPO (Group Relative Policy Optimization, DeepSeek) убирает learned critic PPO: он генерирует несколько completions на один prompt и использует group-relative rewards как baseline. Это снижает burden по состоянию модели относительно типичного PPO. В отличие от DPO, GRPO on-policy: модель генерирует свежие ответы во время обучения. DeepSeek-R1 комбинирует GRPO с RLVR (reinforcement learning from verifiable rewards), используя проверки вроде математических ответов, компиляции кода и unit tests. Такие rewards легче аудитить, чем learned preference score, но неполные тесты и proxy objectives всё равно можно «обмануть».

31. Distillation: перенос знаний между моделями

Distillation знаний переносит способности от большой teacher-модели к меньшей student-модели. Logit-based distillation обучает student совпадать с output distribution teacher’а. Data-based distillation заставляет teacher генерировать примеры, на которых student затем файн-тюнятся. Data-based методы популярны для LLM, потому что они работают между архитектурами и с teacher’ами только через API, но ценность ограничена качеством teacher’а, coverage данных, фильтрацией и стоимостью генерации.

DeepSeek-R1 сгенерировала 800,000 reasoning examples и использовала их для дистилляции моделей Qwen2.5 и Llama 3: от 1.5B до 70B параметров. В оценке из статьи:

  • DeepSeek-R1-Distill-Qwen-32B набирает 72.6% на AIME 2024 и 94.3% на MATH-500, выше заявленных в статье OpenAI o1-mini.
  • DeepSeek-R1-Distill-Qwen-7B набирает 55.5% на AIME 2024, выше результата QwQ-32B-Preview для меньшей модели.

В маленьких-модельных экспериментах DeepSeek-R1 дистилляция обошла direct GRPO на протестированных base моделях. Этот результат поддерживает дистилляцию для этой настройки; он не доказывает универсальный ранг между distillation и RL.

32. Генерация synthetic-data

LLM-генерированный training data используется в нескольких повторяющихся паттернах:

  • Self-Instruct стартует с небольшого seed-набора human-written instructions: LLM генерирует новые инструкции, inputs и outputs, затем они фильтруются и добавляются обратно в пул. Проект Alpaca использовал 52,000 примеров из 175 seeds и сообщил примерно $600 стоимость генерации; сравнение с GPT-3.5 было ограниченной оценкой проекта, а не широкой эквивалентностью.
  • Evol-Instruct (WizardLM) берёт существующие инструкции и итеративно «эволюционирует» их по осям сложности (добавляет ограничения, углубляет reasoning, делает задачи более конкретными), чтобы получить постепенно более сложные training примеры.
  • Microsoft’s Phi-4 (14B) использовала synthetic data для большой доли pretraining, включая генерацию, critique, self-revision и instruction reversal. Технический отчёт сравнивает получившиеся STEM и coding результаты с крупными моделями на выбранных бенчмарках.

Здесь ключевой риск — model collapse: когда модели рекурсивно дообучаются на synthetic data из предыдущих поколений, хвосты исходного распределения постепенно исчезают. Модель переоценивает частые паттерны и теряет редкие, но важные вариации (Shumailov et al., 2024). Отдельное исследование Ahrefs классифицировало 74.2% newly created webpages в их выборке из 900,000 страниц как содержащие AI-generated text; это vendor-classifier результат, а не перепись всего веба. Митигация начинается с blending synthetic и real данных, фильтрации и tracking lineage, чтобы рекурсивно сгенерированный материал можно было измерять.

Part VI — Масштабирование и деплой

Масштабирование с одного GPU до кластера означает разбиение работы по устройствам. Эта часть покрывает стратегии параллелизма, serving framework’ы, выбор GPU и routing.

33. Четыре формы параллелизма

Tensor Parallelism (TP) шардит отдельные матрицы весов по GPU и обычно коммуницирует после каждого слоя. Быстрые intra-node связи вроде NVLink делают это наиболее практичным внутри узла. Больше шардов снижают память и compute на устройство, но увеличивают коммуникации, поэтому степень шардирования выбирайте через latency benchmark.

Pipeline Parallelism (PP) шардит слои последовательно по GPU, передавая активации между стадиями. Шаблон коммуникаций работает и между узлами, но pipeline bubbles и несбалансированное время стадий уменьшают utilization. Большие деплои часто комбинируют TP внутри узла и PP между узлами.

Data Parallelism (DP) реплицирует модель обслуживания, так что каждая реплика обслуживает независимые запросы без межрепликовой коммуникации на каждый запрос. Это эффективно, когда модель помещается, и трафик можно балансировать. В training DP часто комбинируют с ZeRO или FSDP для шардирования состояния.

Expert Parallelism (EP) распределяет MoE expert’ы по GPU, используя all-to-all коммуникации для token routing. Производительность зависит от баланса токенов, размещения expert’ов и topology интерконнекта; all-to-all traffic может стать доминирующим боттлнеком.

Стартовый heuristic по параллелизму:

  • Модель помещается на один GPU: начинайте с независимых реплик и измеряйте DP scaling.
  • Модель помещается в один узел: тестируйте TP внутри узла, затем реплицируйте группу, если трафик требует.
  • Модель охватывает узлы: тестируйте комбинацию TP и PP по интерконнекту и целевой latency.
  • Mixture of experts: добавляйте EP только если размещение expert’ов этого требует.

34. Сравнение serving framework’ов

vLLM предоставляет paged KV allocation, continuous batching, OpenAI-compatible API и несколько режимов параллелизма. Поддержка моделей и железа у него меняется часто, поэтому проверьте целевую модель по текущей compatibility matrix.

SGLang комбинирует RadixAttention для prefix reuse, кастомный scheduler и structured generation. Заявленные выигрыши по throughput зависят от workload’а и конфигурации; сравнивайте его с vLLM и TensorRT-LLM на одинаковых prompts, outputs, hardware и SLO.

TensorRT-LLM ориентирован на низкую latency одиночного запроса через CUDA graph fusion и kernel optimization, с нативной поддержкой FP8/FP4. Опубликованные числа специфичны для железа и модели. Tradeoff — более крутая кривая обучения и deployment поверхность NVIDIA-specific.

TGI интегрируется с экосистемой Hugging Face и поддерживает несколько hardware backends. Проверьте текущие maintenance и статус фич в репозитории перед выбором для нового деплоя.

Ollama делает упор на простой локальный workflow запуска моделей. Используйте для удобства разработки; если важны высокая конкуренция или явный контроль SLO — бенчмарчите другой serving stack.

llama.cpp — портируемый C/C++ рантайм с ARM, x86, Metal, CUDA, ROCm и Vulkan path’ами. GGUF поддерживает несколько уровней квантизации. Производительность сильно варьируется по модели, квантизации, context и backend’у, поэтому используйте его локальный benchmark tool для целевой машины.

36. Cascading моделей и routing

Model routing выбирает, какая LLM обслужит каждый query, на основе предсказанной сложности или capability. RouteLLM (LMSYS/UC Berkeley, ICLR 2025) сообщает 85% снижение стоимости на конфигурации MT-Bench при сохранении 95% baseline-качества GPT-4. Стоит ли routing “отбиваться” — зависит от текущих цен, микса трафика, ошибок router’а и нижней границы качества (quality floor).

Router’ы варьируются от лёгких классификаторов до judge-моделей на базе LLM. Cascading — последовательный вариант: запрос начинается с более дешёвой модели и эскалируется, когда scoring function отвергает ответ. FrugalGPT сообщает до 98% более низкую стоимость или до 4% более высокую точность в протестированном пуле моделей. Production cascade требует откалиброванных критериев эскалации и мониторинга на запросах, которые дешёвая модель обработала неверно.

Part VII — Приложения

Паттерны уровня application, которые превращают «сырые» возможности модели в полезные системы. Embeddings поддерживают retrieval, RAG привязывает ответы к внешним знаниям, agents оркестрируют многошаговые workflow, а prompt engineering связывает всё воедино.

37. Embedding models vs generative models

Embedding models кодируют текст в векторы фиксированной размерности, которые отражают семантический смысл. В отличие от generative decoder моделей, которые генерируют последовательности токенов, embeddings — это один плотный вектор (768–4,096 измерений) на весь input. Большинство embedding моделей используют encoder-only transformers (bidirectional attention), а не decoders. Encoder обрабатывает все input-токены сразу и выдаёт контекстуализированное представление для каждого токена. Затем pooling слой схлопывает per-token представления в один вектор, обычно mean pooling (усреднение всех token embeddings) или CLS pooling (использование output специального classification токена). После этого модель дообучают контрастивным learning: семантически похожие тексты «сдвигаются» ближе друг к другу в векторном пространстве, а несхожие — дальше.

Matryoshka Representation Learning (MRL, Kusupati et al., NeurIPS 2022) делает размер embedding гибким. По аналогии с матрёшками MRL структурирует embedding так, что первые mmm dimensions столь же информативны, как если бы существовала независимо обученная mmm-dimensional модель. Во время обучения вместо вычисления одного loss для полного embedding MRL считает несколько losses параллельно в логарифмически распределённых размерностях (64, 128, 256, 512, 1024, 2048, 3072). Aggregated loss подталкивает ведущие dimensions нести coarse semantic информацию, а последующие добавляют всё более детальные компоненты.

После обучения MRL embedding можно обрезать до поддерживаемого prefix-dimension. OpenAI сообщает, что text-embedding-3-large на 256 dimensions обходит text-embedding-ada-002 на 1,536 dimensions в их cited MTEB сравнении. Это даёт 6x снижение raw vector storage; latency поиска и стоимость базы данных тоже зависят от индекса, метаданных, фильтрации и hardware.

Embedding model — один важный компонент в RAG pipeline, наряду с парсингом, чанкингом, поиском, reranking и генерацией. Если релевантные доказательства не retrieval’ятся, даже более сильный генератор не сможет надёжно восстановить их.

38. Архитектура RAG в production

Retrieval-Augmented Generation подаёт LLM документы, retrieved во время обработки query. Это может дать актуальные или приватные доказательства, которых нет в весах модели, но retrieval не гарантирует, что ответ использует эти доказательства корректно. Production RAG — multi-stage pipeline, и каждую стадию нужно отдельно оценивать.

Ingestion pipeline запускается offline. Raw документы (PDF, HTML, Markdown, базы данных) сначала парсятся в очищенный текст — и это сложнее, чем кажется: парсинг PDF может потерять таблицы, заголовки и форматирование. Затем текст разбивается на chunks, которые отдельно эмбеддятся и индексируются.

Chunking влияет и на recall retrieval, и на то, сколько контекста будет доступно генератору. Полезные размеры зависят от структуры документа, гранулярности query, лимитов embedder’а и лимитов reranker’а. Частые подходы: fixed-size с overlap, recursive splitting по границам документа, и semantic chunking по похожести embeddings. Сравнивайте их по page- или section-level relevance labels, а не берите один общий token range «на все случаи».

Далее каждый chunk эмбеддится моделью вроде тех, что в Section 37, и сохраняется в vector database (Pinecone, Weaviate, Qdrant, pgvector и т.д.).

Retrieval pipeline работает во время обработки query. Начните с измеримого baseline, а затем добавляйте стадии только после error analysis, которая показывает реальный miss:

  • Hybrid search объединяет dense vector retrieval и sparse retrieval вроде BM25, обычно через Reciprocal Rank Fusion (RRF). Dense search ловит semantic paraphrases; sparse search помогает находить точные идентификаторы, error codes и акронимы. Vendor benchmarks часто показывают прирост относительно vector-only baseline, но величина зависит от корпуса и relevance labels.
  • Reranking прогоняет кандидатов через модель, которая оценивает вместе query и документ. Это может улучшить fine-grained relevance, но требует ещё один model call. Количество кандидатов, сколько оставить и итоговую latency нужно настраивать вместе. Полный multi-stage pipeline я разобрал в Building a Modern Search Ranking Stack.
  • Query transformation переписывает пользовательский запрос до retrieval, чтобы улучшить recall. HyDE (Hypothetical Document Embeddings) просит LLM сгенерировать гипотетический ответ, который затем эмбеддится и используется для retrieval. Multi-query expansion генерирует несколько перефразов той же самой вопросительной части. Step-back prompting сначала задаёт более общий вопрос, чтобы вытянуть шире контекст.

Типовые режимы отказа:

  • Retrieval failure — правильный документ существует, но не retrieval’ится. Тестируйте chunking, query transformation, hybrid search и metadata filtering против этого miss.
  • Context poisoning — неподходящие retrieved чанки вводят LLM в заблуждение. Тестируйте reranking, context filters и меньшие retained sets.
  • Lost-in-the-middle — LLM игнорирует релевантный контекст, помещённый в середину длинного prompt’а (Liu et al., 2024 показали, что модели обычно сильнее attend’ят к началу и концу context window).

GraphRAG (Microsoft, 2024) дополняет vector retrieval извлечённым entity and relationship graph. Он нацелен на вопросы на уровне всего корпуса и на вопросы, нагруженные связями, которые плоский chunk retrieval может пропустить. Tradeoff — дополнительная стоимость извлечения, индексации, хранения и evaluation.

Гайды для практиков публикуют диапазоны latency для embedding, search, reranking и generation, но эти цифры зависят от региона, корпуса, железа и модели. Меряйте каждую стадию по трейсам и оценивайте изменение качества до принятия решения о добавлении латентности.

39. Архитектуры agent’ов и tool calling

LLM agents используют модели, чтобы выбирать и упорядочивать tool calls вокруг развивающегося state. Есть три полезных паттерна оркестрации:

  • ReAct — чередует выбор action и observations. Может адаптироваться после каждого результата tool, но растущая история увеличивает cost по токенам и latency.
  • ReWOO — планирует tool calls с плейсхолдерами, исполняет независимую работу параллельно, затем синтезирует результат. В статье указаны экономии токенов относительно ReAct, но фиксированный план нуждается в явном recovery path при сбое tool.
  • Planner-executor — разделяет planning и execution и может добавлять policy перепланирования после failure. Это позволяет специализировать модель, но добавляет orchestration state и новую границу принятия решения.

Function calling — распространённый механизм вызова tool. API раскрывают определения tool и возвращают structured arguments, снижая необходимость парсить свободный текст. Structured output и constrained decoding принуждают следовать схеме, ограничивая доступные токены на каждом шаге генерации. Движки вроде xgrammar, используемые в vLLM и SGLang, могут убрать много ошибок синтаксиса и парсинга с низким overhead’ом в поддерживаемых конфигурациях. Но они не гарантируют, что извлечённые значения или решения корректны. Schema-Guided Reasoning (SGR) использует порядок полей и структуру схемы, чтобы промежуточное состояние было инспектируемым до финального решения. Его три паттерна: Cascade (последовательные шаги), Routing (union types как semantic switches) и Cycle (ограниченные списки).

Качество tool-selection, end-to-end latency и cost по токенам обычно ухудшаются по мере роста размера tool set’а и глубины action. Измеряйте эти кривые на реальных описаниях tool и распределении failure. Framework’ы вроде LangGraph могут сделать state и recovery paths явными, но они не снимают нагрузку на evaluation.

40. Prompt engineering для production

Production prompting — это задача evaluation: меняете одну часть prompt’а или контекста, затем измеряете качество задачи и режимы отказа. Техники ниже — хорошие стартовые точки, но не универсальный порядок.

Few-shot examples часто эффективны для контроля формата output. Начните с 3–5 примеров, которые покрывают пустые input’ы, неоднозначные запросы и multi-part ответы, затем измерьте результат на held-out set. Примеры должны соответствовать реальному распределению входов, а не только «happy path». Больше примеров — больше расход контекста, и они не гарантируют дальнейших приростов.

Chain-of-thought (CoT) prompting просит модель раскрывать промежуточное reasoning до ответа. Kojima et al. сообщили о приростах от суффикса “Let’s think step by step” на их тестовых reasoning tasks, но эффект отличается между моделями, и новые reasoning APIs могут не раскрывать скрытые трейсы. Для production предпочтительнее инспектируемая декомпозиция задачи или краткая рационализация, если это полезно эвалюатору. Self-consistency (Wang et al., 2023) семплит несколько reasoning путей и агрегирует ответы, увеличивая cost инференса, но повышая robustness на подходящих задачах.

Structured output с явными JSON schemas (Section 39) убирает много проблем парсинга. Engines с constrained decoding вроде xgrammar могут применять поддерживаемую грамматику во время генерации; factual accuracy и semantic validity всё равно нужно проверять через evaluation, а unsupported schema-фичи могут требовать дополнительной обработки.

Prompt chaining разбивает задачу на сфокусированные стадии: например classify intent → retrieve context → generate response → validate output. Это локализует failure’ы, позволяет использовать разные модели на разных стадиях и делает промежуточное состояние потенциально кешируемым. Но оно добавляет интерфейсы и latency, поэтому сравнивайте с baseline одного вызова.

Temperature меняет distribution sampling. Низкие значения — разумная отправная точка для классификации или извлечения; более высокие — могут увеличить разнообразие для ideation. Точное поведение отличается между model APIs и взаимодействует с top_p, top_k и дефолтами провайдера, поэтому делайте sweep поддерживаемых настроек под задачу, а не копируйте один диапазон.

Разделение system vs user message отделяет постоянную политику от контентa per-request. Chat templates и instruction tuning дают этим ролям разный приоритет, но это не превращает system message в «жёсткую boundary принуждения». Стабильное поведение — в system message, непроверенные данные — в user или tool content, а жёсткие ограничения (например, удаление PII) enforce’те не только на уровне модели, но и вне неё.

Context engineering расширяет работу с prompt’ом до сборки retrieved документов, tool results, истории диалога и примеров. Liu et al. нашли lost-in-the-middle effect в long-context моделях, которые они тестировали, поэтому позиция должна входить в evaluation, а не приниматься за неважную. Более широкий workflow описан в Context Engineering for AI Agents.

Part VIII — Производственная эксплуатация

Эта часть про rate limiting, режимы отказа, мониторинг, оптимизацию стоимости и планирование capacity при реальном трафике.

41. Rate limiting для запросов с переменной стоимостью

Классический rate limiting по requests-per-second предполагает примерно одинаковую стоимость на запрос. LLM ломают это допущение: 10-токенный classification prompt и анализ документа на 100K токенов попадают в один и тот же API endpoint, но отличаются по стоимости на четыре порядка. Ограничение по RPS либо пропустит дорогие запросы без контроля, либо будет неоправданно голодать дешёвые.

Production-системы нуждаются в token-based rate limiting сразу по нескольким измерениям. OpenAI документирует request и token limits по тарифам. Anthropic разделяет input-token и output-token лимиты. Точные квоты и алгоритмы могут меняться, поэтому считайте провайдерскую документацию источником правды; смысл архитектуры — бюджетировать запросы и токены независимо.

Практический паттерн реализации — multi-dimensional limit hierarchy (user → application → organization → global) с priority tiers для premium доступа. На уровне запроса важна техника token budget reservation: оцените total tokens (input + max_tokens) на момент admission, вычтите из bucket, а затем корректируйте, когда запрос завершится, используя реальное потребление. Это предотвращает ситуацию, когда burst длинных generation-запросов исчерпывает capacity до того, как они начнут реально выдавать output.

Для self-hosted деплоев эквивалент — provisioned throughput: резервировать выделенную GPU capacity под целевые токен-рейты. Для vLLM это означает настраивать admission control вокруг активных decode slots и давления на KV cache, а не только вокруг числа запросов. Как объясняет Section 5, throughput и admission тоже должны быть token-aware.

42. Режимы отказа, от которых нужно защититься

Serving LLM добавляет failure modes, связанные с переменной длиной последовательностей, KV памятью и долгой decode-работой. Заложите защиты и load-test’ите их до того, как появится production traffic.

Out-of-Memory (OOM) — частый тип отказа. FP16 модель на 70B требует ~140 GB только на веса, а KV cache для одного sequence с контекстом 128K при допущениях из Section 6 может добавить около 40 GB. Разрыв между «помещается в память» и «OOM при нагрузке» меньше, чем кажется: batch из длинноконтекстных запросов может потреблять больше KV памяти, чем ожидалось. Профилактика — это измеренный memory reserve плюс quantization и paged KV allocation. Для workload’ов с высоким KV pressure LMCache может offload’ить KV данные в CPU память или диск; используйте опубликованные результаты как отправную точку и обязательно бенчмарчите локальную memory hierarchy.

Preemption происходит, когда давление на KV cache заставляет scheduler evict’ить или пересчитывать работу. Точная стратегия зависит от версии serving и конфигурации. Со стороны пользователя симптом — рост end-to-end latency без очевидной ошибки в приложении. Следите за счётчиками preemption и коррелируйте с KV use, глубиной очереди и длинами запросов.

Tail latency может резко возрастать, когда большие prefill задерживают работу decode. Chunked prefill (Section 7) и length-aware scheduling нацелены именно на это вмешательство. Learning-to-Rank scheduler и CascadeInfer papers сообщают существенные выигрыши относительно baseline, но конкретный результат зависит от распределения длины запросов и конфигурации scheduler’а.

Cascading failures могут стартовать, когда медленные запросы раздувают очередь, upstream клиенты истекают по timeout, а ретраи добавляют ещё больше нагрузки. Защиты включают admission control, лимиты concurrency на tenant, output caps, retry budgets и gateway circuit breakers. Disaggregated prefill и decode пула могут помочь, если load tests показывают устойчивое interference по фазам.

43. Мониторинг систем на LLM

LLM monitoring отличается от традиционного API monitoring в нескольких базовых аспектах. У каждого запроса переменная стоимость, есть две разные фазы с разными боттлнеками и footprint памяти, зависящий и от input length, и от длины генерации. Стандартные метрики вроде request latency и error rate пропускают большую часть важного.

Goodput — количество запросов в секунду, которые одновременно выполняют все заданные SLO thresholds, включая TTFT, TPOT и суммарную latency. Это полезная комбинированная метрика: raw throughput может выглядеть здорово, но SLO по latency могут падать — система обрабатывает 100 запросов/с, но не проходит пороги на 40% из них, значит goodput будет 60. Оптимизация под goodput удерживает видимость распределения производительности, вместо публикации только среднего.

vLLM предоставляет Prometheus endpoint по /metrics с текущими и ожидающими запросами, использованием KV cache, distribution’ами generation-length и статистикой prefix-cache. Имена метрик могут меняться между релизами, поэтому привязывайте дашборды к deployed версии. Типичный стек: Prometheus для метрик, Grafana для визуализации и OpenTelemetry-compatible traces по application и serving компонентам.

Полезные алерт-паттерны:

  • Всплески preemption count — запросы evict’ятся и перезапускаются; пользователи видят «тихое» двукратное увеличение latency.
  • Utilization KV cache приближается к тестовой области preemption — добавляйте capacity или сбрасывайте нагрузку до того, как начнётся каскад evictions.
  • Queue depth постоянно выше тестового batch envelope — admission control должен начать reject’ить или понижать приоритет.
  • TTFT растёт, при этом TPOT остаётся плоским — это первое указание на queuing, admission, network или prefill pressure, а не на decode throughput. Используйте трейсы и метрики очередей, чтобы различить.

44. Оптимизация стоимости: стратегия с накопительным эффектом

В качестве снапшота на март 2026 API-цены различались на порядки между модельными tier’ами. Точные цены быстро меняются, поэтому используйте текущий калькулятор провайдера при решении о покупке. Долгоживущая идея: выбор модели и длина output могут доминировать в счёте ещё до того, как вы оптимизируете инфраструктуру.

В снапшоте марта 2026, который используется в этом разделе, output tokens стоят в несколько раз дороже, чем input tokens для упомянутых модельных tier’ов. Это асимметрия отражает последовательную decode-работу из Section 7. Для таких прайсингов сокращение ненужного output обычно даёт больше рычага, чем «сбривание» того же числа input tokens.

Несколько подходов можно сложить, но только после измерения, какие из них применимы к вашему workload’у:

  1. Quantization от FP16 к INT4 снижает weight memory на 75%. Уменьшит ли это итоговый bill — зависит от скорости kernel’ов, batch size и utilization железа (Section 9).
  2. Model routing отправляет подходящий трафик на более дешёвые модели. Maxim AI vendor case study сообщал снижение monthly bill с 42,000to42,000 to 42,000to29,000; воспроизведите quality gate перед тем, как брать долю routing (Section 36).
  3. Prompt caching уменьшает работу для repeated-prefix. Скидки провайдеров и отношение к rate-limit могут меняться со временем, поэтому комбинируйте измеренный hit rate с текущими условиями (Section 16).
  4. Batch APIs могут давать скидки для не-real-time задач: evaluations, генерация synthetic-data и bulk classification. Проверьте актуальные цены и completion windows.
  5. Self-hosting может победить при устойчивом utilization, но универсального token-volume break-even нет. Помимо GPU аренды учитывайте engineering, оркестрацию, observability, capacity slack и on-call стоимость.

Перемножение иллюстративных факторов даёт большую теоретическую редукцию, но входные параметры не независимы: quantization меняет throughput, routing меняет микс качества, а caching и batching применимы только к подходящему трафику. Стройте оценку по измеренным долям трафика и валидируйте по счету (invoice).

Отчёт вендора за 2024 год из TrueFoundry относит большую часть deployment cost в своей выборке к ML engineering, а не к compute. Рассматривайте эту цифру как prompt включить труд и operations в модель, а не как универсальное отношение.

45. Планирование capacity и autoscaling

Capacity planning для LLM serving должен учитывать переменную стоимость запросов, долгую decode-работу и memory, зависящую от sequence length. В зависимости от workload, лимитирующим ресурсом может быть KV memory, memory bandwidth, compute или интерконнект.

Жёсткий потолок по числу одновременно исполняемых запросов — это budget KV cache, а не FLOPS:

max concurrent sequences=GPU memory−model weights−overheadper-sequence KV cache size\text{max concurrent sequences} = \frac{\text{GPU memory} - \text{model weights} - \text{overhead}}{\text{per-sequence KV cache size}}max concurrent sequences=per-sequence KV cache sizeGPU memory−model weights−overhead​

В упрощённом примере Llama 3 70B INT4 на H100 (80 GB) ~35 GB весов на 80 GB оставляет примерно ~40 GB после резерва под дополнительный overhead. При context 4K, при допущении 160 MB на последовательность теоретический ceiling — около 250 последовательностей; при context 128K та же арифметика падает примерно до пяти. Реальная capacity ниже, когда учитываются поведение аллокатора, runtime buffers, variance длины запросов и latency SLO. Поэтому выбор GPU и оптимизация KV cache напрямую определяют план capacity.

Формула capacity для sizing флота:

required GPUs=peak tokens/min×measured safety marginper-GPU throughput at target SLO\text{required GPUs} = \frac{\text{peak tokens/min} \times \text{measured safety margin}}{\text{per-GPU throughput at target SLO}}required GPUs=per-GPU throughput at target SLOpeak tokens/min×measured safety margin​

Деталь, которая действительно важна: «при target SLO». Peak token throughput и throughput, удовлетворяющий SLO, могут резко отличаться по мере роста concurrency. Бенчмарчите с реальным распределением prompt’ов и длин output на нужных порогах TTFT и TPOT, а не используйте теоретический максимум.

Utilization GPU — недостаточный сигнал autoscaling, потому что он может оставаться высоким и при здоровой работе, и при перегрузе. Комбинируйте её с queue depth, utilization KV cache и degradation goodput. Подбирайте пороги по load tests; значения вроде 80% KV utilization — это starting points, а не универсальные лимиты. Эти метрики описаны в Section 43.

Scale-to-zero помогает fit’нуться в dev и staging окружения с долгими простоями. Serverless inference платформы и kubernetes autoscaler’ы вроде KEDA могут убрать idle capacity, но экономия и время cold-start зависят от размера модели, кэширования image/weight и инфраструктуры. Измерьте startup time прежде, чем использовать тот же policy для latency-sensitive production traffic.

Взаимосвязанная система

Размер KV cache определяет batch size, batch size управляет arithmetic intensity, arithmetic intensity определяет, является ли decode memory-bound, это двигает TPOT, а TPOT — throughput. GQA уменьшает KV cache, что позволяет делать большие batch’и, повышает arithmetic intensity и улучшает utilization GPU. FlashAttention использует разрыв SRAM-HBM. Continuous batching решает compute utilization, но создаёт memory fragmentation — ровно то, что исправляет PagedAttention. Chunked prefill одновременно планирует compute-bound и memory-bound работу; roofline model объясняет, почему эта комплементарность работает.

С side обучения, стоимость lifecycle может выигрывать от обучения меньшей модели на большем числе токенов — как показывает Llama 3 8B. GRPO уменьшает бремя critic-state по сравнению с PPO. В small-model setup DeepSeek-R1 дистилляция обошла прямой RL. Это не единый рецепт обучения, а варианты дизайна для evaluation.

Routing, caching, quantization и правильно подобранное железо «умножают» эффект только тогда, когда вы измеряете их относительно одной и той же цели по качеству и latency.

Ключевые принципы

  1. LLM inference состоит из двух разных фаз. В типичных режимах serving prefill тяготеет к compute, а decode — к memory bandwidth; форма workload может сдвигать границу.
  2. KV cache часто — центральное ограничение. Его размер влияет на batch capacity и давление по памяти. GQA, paged allocation и KV quantization нацелены на разные части этого ограничения.
  3. Иерархия памяти GPU объясняет многие оптимизации. FlashAttention и kernel fusion уменьшают дорогие перемещения данных, а не меняют функцию модели.
  4. Continuous batching и PagedAttention работают вместе. Одна опубликованная сравнивалка сообщает 23x throughput относительно наивного baseline; измерьте прирост в вашем serving stack.
  5. Chinchilla-optimal не равен inference-optimal. Например, Llama 3 8B обучали примерно на 1,875 tokens per parameter, чтобы обменять больше training compute на более дешёвый инференс.
  6. GRPO и distillation поменяли toolkit alignment. DeepSeek-R1 сообщила о более сильных small-model результатах от distillation, чем от собственных прямых RL экспериментов.
  7. Оптимизация стоимости «накапливается» только на eligible traffic. Model quantization, routing, caching и batch APIs требуют отдельного покрытия и измерений качества, прежде чем их экономию можно будет «умножать».
  8. Serving hardware должен соответствовать боттлнеку. Decode-heavy workload’ы часто выигрывают от capacity и bandwidth HBM; prefill-heavy workload’ы больше упираются в compute.
