Сравнение современных движков обработки данных: Polars, DataFusion, Daft, Ray Data и Spark

В течение многих лет Pandas справлялся с табличными вычислениями в памяти, а Apache Spark — с распределёнными. Такой раздел хорошо работал, когда данные были строго структурированными.

Современные пайплайны также обрабатывают изображения, аудио и видео. В этих задачах декодирование на CPU может «съедать» время, отведённое под GPU-инференс; JVM GC и Global Interpreter Lock в Python ограничивают throughput. Новые движки используют Rust и Apache Arrow, чтобы снизить эти издержки.

Чтобы сравнить варианты, я провёл бенчмарки Polars, DataFusion, Daft, Ray Data и Spark на двух реальных датасетах. NYC taxi trips — это табличная работа; Food-101 изображения — мультимодальный пайплайн.

Репозиторий engine-comparison-demo repository содержит код. Запустите его на своей инфраструктуре, потому что производительность движка зависит от машины, датасета и характера нагрузки.

TL;DR: Начинайте с формы работы, а не с победителя бенчмарка. Polars — сильный дефолт для локальных DataFrame-пайплайнов; DataFusion подходит командам, которые встраивают query engine; Ray Data и Daft ориентированы на смешанные CPU/GPU пайплайны; а Spark остаётся зрелым выбором для распределённого SQL и ETL. Прирост скорости в этом гайде описывает конкретные нагрузки — он не переносится автоматически на ваши. Перезапустите companion-бенчмарки на своих данных и железе, прежде чем выбирать.

Типы нагрузок на обработку данных

Движки специализируются, поэтому первый вопрос — какая именно нагрузка у вас. Главное разделение — structured vs. multimodal.

Structured или табличные данные включают фильтрацию, агрегацию и join’ы. Как правило, это CPU-bound, и часто помещается в память. По данным Polars, примерно 90% запросов обрабатывают меньше 1TB, поэтому многие задачи можно запускать на одной современной машине, а не на кластере.

Мультимодальный AI обрабатывает изображения, аудио или видео. Инференс может выполняться на GPU, но декодирование на CPU, удалённые чтения или батчинг ограничивают пайплайн. Какие именно стадии ограничивают throughput, зависит от типа инстанса и операторов, поэтому измеряйте утилизацию по всей цепочке, а не «размеряйте» GPU в изоляции.

Новые движки нацелены на разные части этого пространства. Нативное выполнение снижает overhead в Python, интерфейсы, совместимые с Arrow, удешевляют обмен данными, а streaming execution ограничивает память на датасетах больше RAM. Ни одно из этих преимуществ не гарантировано для каждого оператора или конверсии.

Часть 1: обработка на одной ноде

Pandas предпочитает eager, in-memory модель программирования. Многие распространённые операции создают промежуточные результаты, а параллельное выполнение не координируется через query optimizer. Компромисс помогает держать exploratory-код прямым, но на больших аналитических сканах это может стать дорогим. В PDS-H benchmark у Polars на scale factor 10 Pandas показал около 365 секунд на набор тестов, тогда как streaming-движок Polars — 3.89 секунды. Около 94x — это результат именно этого бенчмарка и конфигурации; это не универсальный коэффициент конверсии «Pandas → Polars».

Polars для локальных табличных пайплайнов

Polars — практичный дефолт, когда локальный DataFrame-пайплайн вырос из-за eager, single-process исполнения. Lazy API строит query plan до выполнения, что позволяет оптимизировать предикаты и вырезать ненужные колонки (predicate pushdown и projection pruning). Затем движок запускает операторы параллельно и, если поддерживается, выполняет streaming batches.

Зазор увеличивается по мере роста данных. На scale factor 100 (~100 GB) streaming engine Polars завершил работу за 23.94 секунды против 152.27 секунд для его in-memory engine — примерно в 6 раз быстрее на данных, которые больше RAM.

Из engine_comparison_examples.ipynb:

import polars as pl

# scan_parquet reads only the schema — no data loaded yet
q = (
    pl.scan_parquet("yellow_tripdata_2024-01.parquet")
    .filter(
        (pl.col("trip_distance") > 5.0)
        & (pl.col("total_amount") > 30.0)
    )
    .group_by("payment_type")
    .agg(
        pl.col("total_amount").mean().alias("avg_fare"),
        pl.col("trip_distance").mean().alias("avg_distance"),
        pl.len().alias("trip_count"),
    )
)

# The entire plan is optimized and executed here, in parallel
result = q.collect()

Ключевое отличие — модель выполнения. В lazy query выше Polars может «вдавить» фильтр и выбор колонок прямо в Parquet scan. Это позволяет пропустить row groups и не читать ненужные колонки. Типичный eager пайплайн Pandas не имеет плана на весь запрос для оптимизации, хотя аккуратное применение Parquet filters, selected columns и альтернативных backends может вернуть часть разрыва.

DataFusion для встраиваемых query engines

Если Polars — это библиотека, которую вы используете напрямую, то DataFusion — движок, поверх которого вы строите другие движки. Он питает InfluxDB 3.0, GreptimeDB и Apple’s Comet Spark accelerator.

В ноябрьском 2024 ClickBench run, опубликованном проектом DataFusion, DataFusion лидировал среди протестированных single-node конфигураций Parquet. Команда Embucket позже опубликовала TPC-H scale-factor-1000 run на одной большой ноде. Эти результаты показывают, что может дать «масштабирование вверх» при конкретных условиях; они не доказывают, что каждый workload на 1 TB должен избегать кластера.

Из engine_comparison_examples.ipynb:

from datafusion import SessionContext

ctx = SessionContext()
ctx.register_parquet("taxi", "yellow_tripdata_2024-01.parquet")

# SQL executed directly against Parquet — no intermediate copies
df = ctx.sql("""
    SELECT payment_type,
           COUNT(*)           AS trip_count,
           AVG(trip_distance) AS avg_distance,
           AVG(total_amount)  AS avg_fare
    FROM taxi
    WHERE trip_distance > 5.0 AND total_amount > 30.0
    GROUP BY payment_type
    ORDER BY trip_count DESC
""")
result = df.to_pandas()

Сила DataFusion — его modularity. Extension APIs покрывают кастомные каталоги, table providers, правила оптимизатора и execution plans. Поэтому он появляется всякий раз, когда кто-то строит кастомную data platform или встраивает query engine в свой продукт.

Daft для мультимодальных данных

Daft делает изображения, аудио, видео и embeddings частью DataFrame workflow. Он предоставляет нативные выражения для операций вроде image decoding и URL downloads, так что типовые preprocessing-пути не требуют row-by-row Python loop. Именно это — главная причина рассматривать Daft вместо общего табличного движка.

Из engine_comparison_examples.ipynb:

import daft

df = daft.read_parquet("yellow_tripdata_2024-01.parquet")

result = (
    df.where(
        (daft.col("trip_distance") > 5.0)
        & (daft.col("total_amount") > 30.0)
    )
    .groupby("payment_type")
    .agg(
        daft.col("total_amount").mean().alias("avg_fare"),
        daft.col("trip_distance").mean().alias("avg_distance"),
        daft.col("trip_distance").count().alias("trip_count"),
    )
    .collect()
)

API будет ощущаться знакомым, если вы работали с Pandas, но движок тот же Rust + Arrow stack, который вы находите в Polars и DataFusion. Где Daft особенно полезен — когда «ряды» в вашем DataFrame — это изображения, PDF’ы или tensors.

Часть 2: мультимодальные данные

Табличный ETL обычно уменьшает объём данных: фильтр, агрегация и запись занимают меньше, чем чтение. Мультимодальные AI пайплайны делают наоборот: один документ может разветвиться на десятки текстовых чанков и embedding-векторов.

В типичном PySpark пайплайне изображения и аудио часто входят как бинарные данные и уходят в Python-библиотеки для декодирования или трансформаций. Переход через границу JVM/Python и сериализация результатов могут занять большую часть wall-clock времени. Spark умеет работать через Arrow-based пути, vectorized UDF и интеграции с акселераторами, но такие решения требуют явного дизайна и измерений.

Пайплайновое выполнение и утилизация GPU

Spark планирует работу стадиями, разделёнными границами shuffle. Прямолинейная реализация может разместить download, decode и inference в последовательность, из-за которой либо CPU, либо GPU простаивают. Spark поддерживает планирование GPU-ресурсов и плагины, поэтому «бездействие» не неизбежно. Но overlap и backpressure не являются автоматическими свойствами обычного PySpark DataFrame job.

Pipelined execution — это альтернатива. Вместо того чтобы выполнять стадии одна за другой, движок перекрывает I/O, CPU-работу и GPU-inference, так что ожиданием становится только самая медленная компонента в каждый момент времени.

Часть 3: распределённая обработка

Когда одной машине недостаточно, нужно решить, как разнести работу.

Apache Spark

Spark — зрелый вариант для крупного табличного ETL, shuffle-heavy join’ов и организаций, уже работающих в его экосистеме. Наследуемое из lineage recovery и широкая поддержка платформы важны, когда надёжность и операционная привычность важнее локальной скорости. Смешанные CPU/GPU пайплайны требуют более продуманной настройки ресурсов и дизайна пайплайна, чем SQL-путь; именно здесь Ray Data и Daft дают более сфокусированную абстракцию.

Из distributed_spark.ipynb:

from pyspark.sql import SparkSession
from pyspark.sql import functions as F

spark = SparkSession.builder \
    .appName("TaxiETL") \
    .config("spark.sql.adaptive.enabled", "true") \
    .getOrCreate()

orders = spark.read.parquet("s3a://lake/taxi/*.parquet")
zones = spark.read.csv("s3a://lake/taxi_zones.csv", header=True)

# Spark excels at this: joining massive tables with a shuffle
result = (
    orders
    .filter(F.col("trip_distance") > 5.0)
    .join(zones, orders.PULocationID == zones.LocationID, "inner")
    .groupBy("Borough")
    .agg(
        F.sum("total_amount").alias("total_revenue"),
        F.avg("total_amount").alias("avg_fare"),
    )
    .orderBy(F.desc("total_revenue"))
)

Ray Data для гетерогенных вычислений

Ray Data был разработан вокруг AI workloads. Вместо stage barriers у Spark используется streaming model, которая держит GPU загруженными. Самая важная фича для AI-пайплайнов — mixed resource scheduling: можно объявить, что один actor хочет «1 GPU, 4 CPUs», а другой — только CPU, и Ray разберётся с остальным.

Amazon сообщила о более чем $120 млн годовых экономии после переноса выбранных внутренних задач обработки данных с Spark на Ray. В отчёте указано 91% более хорошая cost efficiency в proof of concept и 82% в production на каждый GiB S3 input. Масштаб впечатляет, но это кейс по миграции под конкретные workloads, а не ожидаемая экономия для типичного Ray adoption.

Из distributed_ray.ipynb:

import ray

ray.init()

ds = ray.data.read_images("s3://my-bucket/food101/")

class ImageClassifier:
    def __init__(self):
        import torch
        from torchvision.models import resnet18, ResNet18_Weights
        self.model = resnet18(weights=ResNet18_Weights.DEFAULT).cuda()
        self.model.eval()
        self.preprocess = ResNet18_Weights.DEFAULT.transforms()

    def __call__(self, batch):
        import torch
        tensors = torch.stack([
            self.preprocess(img) for img in batch["image"]
        ]).cuda()
        with torch.no_grad():
            preds = self.model(tensors)
        return {
            "prediction": preds.argmax(dim=1).cpu().numpy(),
            "confidence": preds.max(dim=1).values.cpu().numpy(),
        }

# ActorPoolStrategy creates persistent GPU workers
predictions = ds.map_batches(
    ImageClassifier,
    compute=ray.data.ActorPoolStrategy(size=4),
    num_gpus=1,
    batch_size=64,
)
predictions.write_parquet("s3://output/predictions/")

Обратите внимание на CPU-to-GPU ratio. В benchmarks Anyscale Ray Data продолжал масштабироваться при росте CPU на GPU, тогда как другие протестированные движки упирались в потолок (plateau). Переход от 4:1 к 32:1 дал 3x ускорение на image inference, потому что CPU feeders наконец стали успевать за GPU.

Distributed Daft

Daft масштабируется через свой Flotilla engine: на каждой ноде — один Swordfish воркер, а сверху Flotilla делает cluster-wide scheduling. Swordfish обрабатывает локальное Rust execution и пайплайнирует I/O с compute через small-batch streaming, поэтому каждая нода держит занятость без ожидания следующей стадии.

В benchmarks, опубликованных Daft, Flotilla работал в 2–18x быстрее, чем протестированные реализации Spark, на четырёх мультимодальных workload’ах. Самый большой разрыв — в кейсе video-object-detection. Рассматривайте результат как свидетельство того, что дизайн исполнения важен для таких пайплайнов, а затем сравните с конкурирующими результатами Anyscale ниже и с локальным тестом.

Anyscale, компания за Ray, опубликовала конкурирующий benchmark, где Ray Data закрывал или разворачивал разрыв на high-CPU инстансах после тюнинга. Вместе два vendor-исследования — это причина прогонять репрезентативные операторы и CPU-to-GPU ratios, а не выводить «стойкую» лигу победителей.

Из distributed_daft.ipynb:

import daft
from daft import col

# Daft's Flotilla engine distributes work across the cluster
df = daft.read_parquet("s3://data-lake/pdf_metadata/*.parquet")

# Download PDFs — Daft parallelizes downloads in Rust
df = df.with_column("pdf_bytes", col("pdf_url").url.download())

# Define a GPU UDF for embedding generation
@daft.udf(return_dtype=daft.DataType.list(daft.DataType.float32()))
class TextEmbedder:
    def __init__(self):
        from sentence_transformers import SentenceTransformer
        self.model = SentenceTransformer("all-MiniLM-L6-v2", device="cuda")

    def __call__(self, text_col):
        texts = text_col.to_pylist()
        embeddings = self.model.encode(texts, batch_size=32)
        return [emb.tolist() for emb in embeddings]

# Daft schedules CPU downloads and GPU embeddings simultaneously
df = df.with_column("embedding", TextEmbedder(col("text")))
df.write_parquet("s3://output/embeddings/")

Часть 4: роль Rust и Arrow

Под конкуренцией есть более интересная история — конвергенция подходов. Polars, Daft и DataFusion активно используют Rust, тогда как Ray включает нативные компоненты наряду с Python API. Все они могут обмениваться данными через части Apache Arrow ecosystem.

Arrow PyCapsule Interface (протокол __arrow_c_stream__) даёт совместимым библиотекам стандартный способ обмена Arrow streams. Трансферы могут избежать row-wise сериализации и иногда переиспользовать буферы, когда схемы и memory layouts совместимы. Но materialization, rechunking, type conversion или device transfer всё ещё могут копировать данные, поэтому проверяйте «передачу» через profiling, а не исходите из того, что это бесплатно.

from datafusion import SessionContext
import polars as pl

# Compute in DataFusion (Rust-native execution)
ctx = SessionContext()
ctx.register_parquet("events", "events.parquet")
df = ctx.sql("""
    SELECT user_id, COUNT(*) as event_count
    FROM events WHERE event_type = 'purchase'
    GROUP BY user_id HAVING COUNT(*) > 5
""")

# Convert through Arrow; compatible buffers may be reused
arrow_table = df.to_arrow_table()
df_polars = pl.from_arrow(arrow_table)

# Continue analysis in Polars
result = df_polars.with_columns(
    pl.col("event_count").rank().alias("rank")
).sort("rank")

Почему эти новые движки используют Rust для нативного выполнения?

  1. В Rust-коде нет tracing garbage collector. Ownership даёт нативным операторам более прямой контроль над аллокацией и деаллокацией. Это может снизить задержки, связанные с GC, но не убирает memory pressure и не предотвращает out-of-memory.

  2. Компактные нативные представления. Rust-структуры не несут Java object headers. Практическая выгода зависит от того, как движок раскладывает данные: колоночные JVM-системы тоже избегают представления каждого значения как отдельного объекта.

  3. Более сильные проверки конкурентности. Safe Rust исключает множество data races на этапе компиляции. Но движковый код всё равно может содержать unsafe blocks и логические concurrency bugs — просто язык сужает поверхность отказов.

В сочетании с Arrow’s columnar memory layout эти решения могут снизить накладные расходы на аллокации и сериализацию. Они не убирают их на каждой границе; Python-объекты, сетевой транспорт, несовместимые схемы и перенос между устройствами всё ещё имеют значение.

Часть 5: внедрение нескольких движков

Вам не нужно проталкивать всю платформу через один движок. Композиция полезна, когда стоимость handoff между движками меньше, чем цена за то, что один система будет обрабатывать абсолютно все workload’ы.

Один из возможных relay-подходов: Spark для established lakehouse joins, запись открытого table или file format и передача результата в Ray Data или Daft для GPU inference или мультимодальных трансформаций. Polars или DuckDB могут обслуживать локальный анализ над теми же файлами. Маленькой команде может хватить одного из этих движков; второй добавляют, когда измеренный bottleneck оправдывает операционную границу.

То, что такая композиция возможна, обеспечивают open formats: Parquet, Delta, Iceberg, Arrow. Каждый движок в стеке читает и пишет их нативно, поэтому handoff между стадиями — это просто file path.

Диагональное масштабирование

Долгое время выбор был между scale up (более мощная машина) и scale out (больше машин). Polars Cloud делает нечто среднее — то, что они называют diagonal scaling. Масштабируйтесь горизонтально, читая из cloud storage, чтобы упереться в I/O, а потом «сворачивайте» в одну большую ноду, когда фильтры и агрегации уже сократили объём данных. Распределённый shuffle не происходит.

Общий вывод: сравнивайте cost per successful job, а не hourly instance price. Большая нода может быть дешевле, если сокращение времени работы перевешивает более высокий rate, но итог зависит от I/O, memory pressure и количества работы, которая была устранена до shuffle.

Воспроизвести сравнение

В companion demo repository есть скрипты, notebooks и окружение, использованные для сравнений. Быстрая команда ниже использует данные за один месяц; следуйте инструкциям по датасету в репозитории, чтобы воссоздать более полный прогон за год, показанный выше.

# Install dependencies
uv sync

# Run the tabular benchmark (~2.9M NYC taxi trips)
uv run python -m engine_comparison.benchmarks.tabular

# Run the multimodal benchmark (500 real food photos)
uv run python -m engine_comparison.benchmarks.multimodal

# Run native Rust benchmarks (Polars-rs + image crate)
cd rust_benchmark && cargo run --release && cd ..

В репозитории также есть notebooks для side-by-side сравнений API и Docker Compose конфигурации для локальных distributed-запусков Spark, Ray и Daft.

Основные выводы

  1. Докажите, что одной машины недостаточно. Результаты scale-up показывают, что некоторые большие аналитические сканы помещаются на одной ноде. Прежде чем принимать overhead кластера, измерьте потребление памяти, I/O, spill и требования к recovery.

  2. Модели выполнения важнее знакомого синтаксиса. Lazy planning, pushdown, streaming и параллельные операторы объясняют значительную часть разрыва между eager DataFrame-скриптом и аналитическим движком.

  3. Измеряйте весь accelerator pipeline. Decode, сетевой I/O, батчинг, сериализация и backpressure определяют, будет ли GPU реально загружен. Ray Data и Daft делают overlap центральной абстракцией; Spark тоже может поддерживать это, но потребуются дополнительный дизайн и tooling.

  4. Сначала shortlist по нагрузке, затем бенчмарк. Используйте fit с экосистемой, чтобы сузить поле, и берите representative end-to-end job для выбора. Vendor benchmark’и — это гипотезы, а не гарантия.

  5. Open formats делают выбор обратимым. Arrow-compatible интерфейсы, Parquet и открытые table formats могут снизить стоимость handoff. Проверьте, переиспользуются ли буферы при конкретной конверсии или происходит копирование.

Если вам нужен стартовый ориентир: попробуйте Polars для локального табличного пайплайна, а Daft или Ray Data — для смешанного CPU/GPU пайплайна. Выбирайте Spark, если его distributed execution, экосистема или существующая операционная база закрывают вашу requirement. Размер датасета сам по себе — слабое основание для выбора.
