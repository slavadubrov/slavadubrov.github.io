Харнесс-инжиниринг для ИИ-агентов: как спроектировать цикл вокруг модели

Часть 6 из серии Engineering the Agentic Stack

Цикл ризонинга агента выбирает следующее действие. Его харнесс подаёт контекст, валидирует и авторизует предложенные tool calls, отправляет принятые вызовы в рантайм, записывает результаты и решает, завершена ли задача.

Модели предлагают правки и могут объявлять задачи завершёнными, а харнесс применяет permissions и интерпретирует acceptance checks, которые определяют, можно ли остановить цикл. В части 5 разбирался рантайм, который поддерживает процесс живым. Эта статья фокусируется на управляющем коде внутри этого рантайма: как измерять, помогает ли каждое добавление, и как сделать так, чтобы получившиеся контролы оставались находимыми по мере изменения харнесса.

За пределами первой явной acceptance check каждая добавленная retry, handoff или evaluator — это гипотеза о наблюдаемом сбое. Она заслуживает места только тогда, когда контролируемое сравнение показывает, что она помогает.

Чтобы сделать этот control path конкретным, я буду использовать небольшой вымышленный репозиторий магазина. Задача по коду — снизить порог для автоматической скидки 10% с $100 до $75 в src/checkout.py. В репозитории есть две обязательные проверки:

  • pytest tests/test_checkout.py проверяет расчёт скидки.
  • pnpm playwright test tests/checkout_discount.spec.ts добавляет товар на $80 в локальный тестовый магазин и проверяет, что страница checkout показывает скидку $8.

Этот пример — учебный fixture, а не реальное приложение или benchmark. Каждая попытка стартует с одного и того же commit и seed-данных тестов. Харнесс может принять изменение только тогда, когда обе команды проходят, а trace связывает эти результаты с проверенным commit.

В следующих разделах я намеренно переключусь ещё на два примера. API staging-заказов покажет, почему вызовам, меняющим состояние, нужна replay protection, а миграция payment adapter покажет, что новой model session нужно для возобновления незавершённой работы. Companion lab ближе к концу снова отдельный: он запускаемый, но содержит generic simulated tasks, а не этот репозиторий магазина.

TL;DR: Начинайте с одной модели, нескольких узких инструментов и явной acceptance check. Добавляйте retries после того, как traces покажут transient сбои вызовов. Добавляйте progress handoff, когда возобновлённые sessions начинают повторять работу. Когда тестируете любое из этих изменений, держите версию модели, задачи, grader и общий budget фиксированными. Удаляйте компонент, если он не улучшает измеряемый результат.

Диаграмма ниже показывает путь изменения скидки от предложения до evidence. Харнесс подаёт задачу и файлы, проверяет предложенные аргументы edit_file и permissions, а затем отправляет принятый вызов. После того как рантайм применяет правку, харнесс запускает указанные unit- и browser-based acceptance tests. Команда, завершившаяся с ошибкой, возвращается модели как evidence для следующего хода; две успешные команды делают изменение кандидатом на принятие.

Чем владеет харнесс

В разборе цикла Codex от OpenAI описан базовый цикл. Харнесс собирает промпт, запрашивает у модели следующее действие, отправляет принятый tool call в рантайм, добавляет результат и спрашивает снова, пока харнесс не примет результат или не вернёт управление пользователю.

В реализациях несколько обязанностей могут быть слиты в один процесс. Но границы отказов всё равно разные:

TermJobПример для coding agent
ModelПредлагает текст, tool call или финальный ответПредлагает правку в src/checkout.py
Reasoning loopВыбирает следующий ход на основе доступного контекстаПроверить, отредактировать, протестировать, снова проверить
HarnessПодаёт контекст, авторизует и отправляет вызовы, записывает результаты и проверяет завершениеРазрешает правки только в src/ и требует оба указанных теста
RuntimeВыполняет вызовы и поддерживает процесс живым и изолированнымWorker, sandbox, session store, queue

Когда возникает сбой, диагностируйте ту границу, которая должна на него реагировать. Плохому плану могут понадобиться более качественные инструкции или лучший ризонинг модели. Если edit_file нацелен на путь за пределами src/, харнесс должен это отклонить, а вот процесс в sandbox, который умер до применения правки, — это зона рантайма: он должен перезапустить worker или сообщить о падении.

В собственном case study по harness engineering от OpenAI описывается bootable instance приложения для каждого worktree. Команда также подключила browser automation в агентную среду и вывела логи, метрики и traces.

Задача вроде «ни один span в этих четырёх критичных пользовательских сценариях не превышает двух секунд» стала тестируемой, потому что агент мог запускать приложение и опрашивать те же сигналы, которые проверял бы инженер. Этот case study специфичен для продукта. Переносится из него одно условие: само приложение и его performance-сигналы должны были быть доступны внутри среды агента.

Lopopolo, автор этого case study, ведёт field guide по harness engineering, где названы два рычага, которые использует эта статья: держать модель и coding agent фиксированными как чёрный ящик и проектировать контекст и инструменты вокруг них. Его framing также объясняет, почему так большая часть харнесса в итоге оказывается обычным кодом.

Планка качества в организации, процедуры, история исключений и отношения полномочий находятся ниже ватерлинии того, что может знать general-purpose модель. Харнесс поднимает их на поверхность в виде инструкций репозитория, permission rules и acceptance checks. Каждый принятый run может возвращать извлечённые уроки обратно в эти артефакты, вместо того чтобы надеяться, что следующая session переоткроет их заново.

Проследим изменение скидки от предложения до принятия

Для определённой выше задачи со скидкой модель предлагает изменить calculate_discount в src/checkout.py. Прежде чем эта правка будет считаться прогрессом, происходит несколько вещей:

  1. Context builder подаёт задачу, инструкции репозитория, релевантные файлы, результаты предыдущих инструментов и текущий план.
  2. Модель предлагает вызов edit_file с путём и текстом замены.
  3. Tool boundary (код харнесса между предложением и исполнением) валидирует аргументы, проверяет путь на соответствие разрешённой области и запрашивает approval, если операция его требует.
  4. Рантайм применяет правку в sandbox и возвращает structured result.
  5. Харнесс запускает pytest tests/test_checkout.py, затем pnpm playwright test tests/checkout_discount.spec.ts и считывает exit code обеих команд. Browser test проверяет видимую скидку $8 на seed-корзине с товаром на $80.
  6. Харнесс решает, что означают эти результаты. Упавшая проверка становится новым контекстом для следующего хода модели, а успешный run делает задачу кандидатом на завершение.
  7. Успешный результат становится evidence завершения только после того, как харнесс записывает команду, exit code и версию проверенного артефакта в trace.

На шаге 2 ни один файл ещё не изменился. Харнесс может отклонить ../../secrets.env, потребовать approval для destructive-команды или остановить run, исчерпавший свой budget. После запуска тестов харнесс сам читает их exit codes. Модель не может сама объявить, что её правка прошла проверку.

В trace должны быть видны предложенный путь и текст замены, решение по permissions, изменившиеся файлы, протестированный commit и результаты обеих команд. Финальное сообщение done без этих записей не доказывает, что это изменение прошло обязательные проверки.

Решите, где должна применяться каждая rule

Помещайте tests/checkout_discount.spec.ts в обычную program logic. Харнесс отправляет Playwright-команду в рантайм, считывает её exit code и отказывается завершать run, пока она не проходит. Промпт может напомнить модели запустить тест. Но он не может помешать модели объявить успех без evidence.

Другие правила лучше ложатся на другие слои:

Куда поместить правилоКогда подходитПример
Prompt или skillПорядок поиска, coding conventions и формат планаЧитать AGENTS.md перед редактированием checkout-кода
Tool boundaryВалидация аргументов, разрешённые пути, approvals и доступ к инструментамРазрешать запись только в src/
Deterministic codeBudgets, timeouts, retries, test exit codes и release gatesДержать run открытым, пока падает Playwright-тест

Tool contracts отделяют предложение от разрешения

Задаче со скидкой нужны только правки файлов и тестовые команды. У API, меняющего состояние, другой failure mode, поэтому для этого раздела переключимся на другой пример. Предположим, агент может вызывать create_test_order к staging-сервису заказов при подготовке тестовых данных. Этот инструмент не входит в acceptance checks задачи со скидкой. Здесь он полезен, потому что timeout может скрыть, создал ли сервис заказ.

Tool boundary здесь нужно нечто большее, чем описание на естественном языке. Для create_test_order харнессу нужен contract, содержащий:

  • валидируемые аргументы, чтобы malformed input отклонялся до исполнения
  • structured result вроде { "order_id": "123", "created": true }, чтобы последующие проверки не парсили free-form текст
  • category эффекта, которая фиксирует, только ли вызов читает информацию или меняет файл, запись в базе или внешний сервис. Она также отмечает, безопасно ли повторять вызов. Этот label сообщает харнессу, может ли автоматический retry продублировать работу: он может повторить get_order_status, если сервис определяет этот lookup как read-only, но не должен слепо повторять create_test_order, потому что первый вызов уже мог создать заказ
  • policy таймаута и retry, чтобы потерянный ответ не запускал неограниченную последовательность вызовов
  • permission rule, которая говорит, какое approval требуется. Чтение статуса заказа может выполняться автоматически, а создание заказа может требовать подтверждения

Описание на естественном языке — это текст, показываемый модели. Там может быть сказано: «Создай тестовый заказ для проверки checkout». Это предложение помогает модели понять, когда предлагать create_test_order. Но оно не авторизует сам вызов. В этом примере MCP client харнесса валидирует аргументы, применяет свои собственные rules и проверяет доверие к серверу, требования по approval и безопасность retry перед любым dispatch.

MCP server публикует описания инструментов и optional behavior annotations для клиента. Ошибочный или malicious server может описать инструмент, меняющий состояние, как безвредный. Если клиент автоматически принял бы это утверждение, он мог бы запустить или повторить create_test_order без approval и создать дубликат, поэтому спецификация MCP требует от клиентов считать tool annotations недоверенными, если сам server не является доверенным.

Спецификация не предписывает одну универсальную trust setting. Поэтому клиенту нужна явная trust policy для своего деплоя; сервер не может сделать свои собственные annotations доверенными. Именно эта policy решает, какие metadata могут влиять на permission- или retry-решения, а какие annotations остаются лишь advisory.

Retry вызова, меняющего состояние, требует replay protection

Более сложная проблема retry появляется, когда create_test_order создаёт заказ, но теряется его HTTP response. Харнесс видит timeout и не может понять, завершил ли сервер запрос. Повтор вызова может создать второй заказ.

Lookup статуса можно повторять, если сервис определяет его как read-only. Вызову создания нужна защита вроде idempotency key: клиент прикрепляет уникальный идентификатор запроса, а сервис возвращает первый результат вместо создания нового заказа, когда снова видит тот же идентификатор. Без этой защиты харнесс должен проверить, существует ли заказ, или запросить решение человека перед новой попыткой. AWS документирует этот паттерн в своём руководстве по idempotent API.

Для принятия нужно независимое evidence

Успешный ответ create_test_order доказывает только то, что инструмент вернул данные. Это не доказывает, что coding task прошла свои тесты. Если последующий browser test зависит от staging-заказа, харнесс обязан валидировать schema ответа и всё равно запустить этот тест, прежде чем принять изменение кода.

Некоторые критерии нельзя свести к exit code. Для отдельной задачи по visual design свежий evaluator может сравнить отрендеренную страницу или диаграмму с письменной rubric. Командам стоит сначала проверить такого evaluator-а относительно human review, прежде чем использовать его как completion gate.

Для миграции payment adapter нужен handoff

Снова переключим задачу, но останемся в вымышленном репозитории магазина. Теперь агент должен мигрировать checkout с payment adapter v1 на v2. Работа охватывает checkout handler, payment client, configuration и tests, поэтому может пережить одну model session.

До того как первая session достигнет лимита контекста, она уже изменила несколько файлов, запустила локальный payment sandbox и оставила tests/payment_migration.spec.ts в падающем состоянии. Этот browser acceptance test завершает один платёж через adapter v2 и проверяет записанный provider ID. Summary разговора может сориентировать следующую model session, но не может перезапустить sandbox или доказать, какие файлы сейчас изменены.

Следующая session должна восстановить три вещи:

Что нужно восстановитьЧто в это входитКак это может сломаться
История разговораСообщения, tool calls и возвращённые результатыСтарые детали вытесняют текущую задачу
Рабочее окружениеФайлы, payment sandbox и состояние browser testТранскрипт говорит, что сервис работает, хотя он уже умер
Прогресс задачиПлан, завершённые проверки, pending approval, следующее действиеСледующая session повторяет уже завершённую работу

Compaction заменяет старые сообщения более коротким summary, чтобы текущая session могла продолжить работу. Progress handoff записывает то, что нужно следующей session: текущую ветку, изменённые файлы, последнюю тестовую команду и её вывод, а также следующий нерешённый шаг. Если в старом разговоре есть устаревшие предположения, харнесс может запустить новую model session с этим handoff и текущим workspace. Замена упавшего worker и восстановление его процессов — это отдельная задача recovery уровня рантайма.

Небольшой documentation edit может не требовать ни одного из этих механизмов. Но миграции платежей нужен handoff, как только работа пересекает границы sessions, потому что следующая model session должна реконструировать и workspace, и статус задачи.

В экспериментах Anthropic с long-running coding agents между sessions использовались git history и progress file, а в более позднем отчёте о design харнесса compaction отделяется от handoff со свежим контекстом, и там же сообщается о дополнительной оркестрации, расходе токенов и wall time, которые handoffs требуют.

Используйте traces, чтобы различать три сбоя

Следующие три строки — это иллюстративные sketches trace, а не измеренные runs и не output из companion lab. Каждая строка показывает разный сбой и, следовательно, разную реакцию харнесса.

Что записано в traceЧто произошлоПравильная реакция
Read-only вызов get_order_status возвращает 503; ни один вызов, меняющий состояние, не выполняетсяПроизошёл transient-сбой lookupПовторить lookup с ограничением и backoff
create_test_order уходит в timeout, затем lookup статуса находит заказ 123 по idempotency key checkout-42Сервис создал заказ, но response был потерянВернуть существующий заказ; не создавать ещё один
Правка и unit test проходят, но в trace нет результата для tests/checkout_discount.spec.ts на протестированном commitОтсутствует обязательное acceptance evidenceДержать run открытым и отправить browser acceptance test

Это различие важно, потому что 503 не делает каждый вызов безопасным для retry. Первая строка — это read-only lookup. Вторая строка — запрос, меняющий состояние, поэтому idempotency key и server-side status определяют, разрешена ли ещё одна попытка создания. Третья строка вообще не является сбоем инструмента; харнесс просто ещё не собрал evidence, необходимое для принятия изменения скидки.

Chat transcript фиксирует то, что видела модель. Но он не может доказать, закоммитил ли сервис заказа запрос до исчезновения response. Trace должен связывать клиентский вызов, approval decision, idempotency key, результат сервера или status lookup, протестированный commit и результат acceptance test. Именно эти поля говорят харнессу, по какому из трёх путей он сейчас идёт.

Повторяющийся симптомНебольшое изменение, которое стоит попробоватьЧто измерять
Read-only lookup-и transiently падаютОграниченный retry с backoffДоля восстановления, лишние вызовы, wall time
Возобновлённые sessions повторяют завершённую работуStructured progress handoffДублирующиеся действия инструментов после resume
При завершении отсутствуют обязательные тестыFail-closed acceptance gateЗадачи, принятые без всех обязательных проверок
Visual defects переживают deterministic checksFresh evaluator с письменной rubricНайденные дефекты, false rejection, review time
Агент редактирует вне своей областиБолее узкие permissions у инструментаЗаблокированные вызовы и manual overrides

Перед добавлением компонента назовите повторяющийся сбой, который он должен снизить, и число, которое вы будете отслеживать. Удаляйте компонент, если контролируемое сравнение не двигает это число достаточно, чтобы окупить его стоимость.

Измеряйте по одному изменению за раз

Ablation измеряет, вызывает ли компонент харнесса ожидаемый эффект, изменяя или убирая этот компонент при неизменности остальной части эксперимента. Например, помогает ли editor linting этой модели на этом наборе задач?

Используйте следующий протокол:

  1. Зафиксируйте версию модели, экземпляры задач, окружение, grader и промпты вне тестируемого компонента.
  2. Дайте обоим вариантам одинаковый общий budget по токенам, времени и деньгам.
  3. Выберите число trials или stopping rule до запуска сравнения.
  4. Прогоните одни и те же экземпляры задач в обоих вариантах. Поскольку output моделей варьируется, повторите каждую задачу несколько раз.
  5. Сообщайте mean вместе с разбросом или confidence interval.
  6. Считайте каждый начатый trial, включая timeouts, policy stops, падения харнесса и failures evaluator-а.

Одна только success rate может скрыть дорогой компонент. Как минимум, отслеживайте сломанные задачи, ошибочно принятые как завершённые, cost и wall time на завершённую задачу, tool errors, duplicate orders, минуты review и manual permission overrides. Выбирайте метрику, которая несёт реальную стоимость для продукта. Рост завершённых задач на два пункта — плохой trade-off, если он удваивает очередь на review.

Парный эксперимент по миграции платежей делает progress handoff измеримым. Каждая control/treatment-пара стартует с одного и того же commit репозитория и seed-чекпоинта, с той же моделью, задачей, grader и общим budget. Единственный переключатель — handoff. Основная метрика считает duplicate tool actions после resume: действие считается дубликатом, когда его операция и артефакт совпадают с шагом, который предыдущая session уже завершила.

В статье SWE-agent фиксируется GPT-4 Turbo на разбиении SWE-bench Lite из 300 задач и сообщается о 18.0% resolved для полного интерфейса против 11.0% у shell-only агента. В статье также отдельно менялись отдельные features интерфейса:

Изменение интерфейсаResolved
Полный интерфейс SWE-agent18.0%
Editor без linting15.0%
Полный файл вместо viewer на 100 строк12.7%
Полная история observation вместо последних пяти15.0%

Эти числа относятся именно к той модели, тому benchmark и лимиту $4 на задачу. Строки without linting, full file и full history полезны именно как one-feature tests: в каждой менялась одна feature интерфейса при фиксированных модели и setup оценки.

LangChain опубликовал более широкое сравнение с фиксированной моделью для deepagents-cli. Там сообщается о росте Terminal-Bench 2.0 с 52.8% до 66.5% при фиксированном gpt-5.2-codex, пока команда меняла системный промпт, инструменты и middleware. Этот пост объединяет несколько изменений и не даёт confidence interval, сравнения с фиксированным общим budget и таблицы ablation по отдельным изменениям. По такому результату нельзя понять, какое именно изменение было полезным.

Отчёт Anthropic о long-running applications — это qualitative и product-specific case study, а не контролируемый benchmark. Их evaluator проверял 27 критериев level editor в Sprint 3. Команда сообщает, что вызовы evaluator-а стали overhead на задачах, которые Opus 4.6 уже могла надёжно завершать самостоятельно, но всё ещё помогали на границе возможностей модели, поэтому после апгрейда модели они удаляли компоненты харнесса по одному. Этот пример — аргумент за повторную валидацию старых scaffolding-компонентов при смене модели; он не оценивает общий размер эффекта.

Сохраняйте редактируемость харнесса после того, как он доказал свою полезность

Ablation помогает держать харнесс компактным, но его код всё равно может пережить модель, под которую его тюнили. Запрос вроде «замаскировать секреты во всех путях захвата» задаёт поведение, а не файл. В production-харнессе это поведение может быть размазано по execution stages и shared state. Человек или coding agent должны найти каждое место реализации, прежде чем безопасно его менять.

В препринте 2026 года Wang et al., Harness Handbook, этот шаг называется behavior localization. Handbook строит behavior-centric map на основе codebase харнесса. Static analysis извлекает graph программы без model calls, а затем LLM организует его unit-ы по execution stages.

Maintainer или coding agent начинает с system overview, открывает релевантный execution stage и спускается к source-grounded entries для функции или файла. Представление register фиксирует, где shared state записывается и читается между stages. Эта иерархия сохраняет overview компактным, не теряя пути к исходникам.

Freshness — отдельное правило. Каждый locator должен разрешаться относительно live-репозитория. Handbook исключает устаревшие entries вместо угадывания, а каждый непустой diff пересинхронизирует те entries, которых он касается.

Диаграмма сжимает цикл модификации: запрос только на уровне поведения спускается по уровням handbook, каждый candidate locator проверяется относительно live-репозитория до записи плана, а каждый применённый diff пересинхронизирует карту.

Оценка Handbook следует тому самому протоколу, за который выступает эта статья. На двух open-source харнессах (Terminus-2, шесть Python-файлов, и monorepo Codex, 2,267 Rust-файлов) read-only planner на базе DeepSeek-V4-Pro либо исследовал репозиторий напрямую, либо работал через handbook. Requests, репозиторий, tool permissions и decoding были идентичны в обеих ветках. Три judges (GPT-5.5, Opus 4.8, DeepSeek-V4-Pro) оценивали каждый план правки по localization, scope control и reasoning:

HarnessBaseline win rateС handbookТокены планировщика
Terminus-2 (6 files)26.7%45.6%−8.6%
Codex monorepo (2,267 files)28.3%38.3%−12.7%

Planner с handbook выигрывал чаще и использовал меньше токенов планировщика в обоих репозиториях. Но условия этого результата сохраняются: три LLM judge-а оценивали планы правок, созданные одной моделью planner-а на двух харнессах. Исследование оценивало планы, а не исполненные diffs или production defect rate.

В предыдущих разделах traces отвечали на вопрос, зачем существует компонент. Эта карта отвечает на следующий вопрос: где живёт этот компонент, когда его нужно изменить?

Попробуйте метод в companion lab

Проект harness-demo на commit 517353f3 — это небольшое детерминированное упражнение с 12 generic synthetic tasks, охватывающими изменения кода вроде fix-parser-edge-case, split-large-module и wire-browser-test. Он не реализует вымышленный репозиторий магазина.

Каждый task fixture задаёт сложность и четыре булевых условия: flaky tool, потерянный прогресс, пропущенный implementation gap и неоднозначное завершение. Симулятор выводит пятое условие для сложных задач, которым ещё нужен progress file: без context_reset compaction сохраняет устаревшие предположения. Deterministic grader помечает задачу как passed только тогда, когда выбранная конфигурация обрабатывает все применимые условия. Ни модель, ни внешний сервис не запускаются.

Команды отвечают на разные вопросы:

  • make check запускает Ruff и семь unit tests, включая validator, который отклоняет любую пару для ablation, если в ней изменён более чем один компонент.
  • make run печатает cumulative teaching matrix, а затем пять валидных сравнений leave-one-component-out.
  • make failures называет необработанное условие для каждой проваленной задачи. Полный харнесс должен завершиться с all synthetic tasks pass.
make check
make run
make failures

Каузальная секция make run выглядит так:

component                 control  treatment  delta
retry_policy              8/12     12/12       +4
progress_handoff          7/12     12/12       +5
evaluator                 8/12     12/12       +4
fail_closed_acceptance    7/12     12/12       +5
context_reset            10/12     12/12       +2

Для каждой строки control — это полная конфигурация с одним удалённым компонентом; treatment возвращает только этот компонент. Более ранняя cumulative matrix полезна для ориентирования, но некоторые соседние строки в ней добавляют сразу несколько компонентов и поэтому не могут идентифицировать причину.

Lab валидирует каждую объявленную пару перед запуском. Его regression tests также включают намеренно невалидную пару, которая одновременно меняет retry policy и evaluator; validator её отклоняет.

Schema конфигурации lab проверяет все пять полей компонентов. Этот runnable excerpt показывает тот же guard на одной валидной паре progress-handoff:

from dataclasses import dataclass, fields


@dataclass(frozen=True)
class Config:
    progress_handoff: bool = False
    evaluator: bool = False
    retry_policy: bool = False
    fail_closed_acceptance: bool = False
    context_reset: bool = False


def changed_components(control: Config, treatment: Config) -> tuple[str, ...]:
    return tuple(
        field.name
        for field in fields(control)
        if getattr(control, field.name) != getattr(treatment, field.name)
    )


control = Config(progress_handoff=False, evaluator=True, retry_policy=True)
treatment = Config(progress_handoff=True, evaluator=True, retry_policy=True)
assert changed_components(control, treatment) == ("progress_handoff",)

Начните с одного цикла и одной acceptance check

Я бы начинал харнесс coding agent-а с одной достаточно мощной модели, инструкций репозитория, нескольких узких инструментов, sandbox и одного явного acceptance test. Я бы записывал tool calls, результаты, cost и этот финальный тест в один trace, чтобы первые полезные сбои были видны без реконструкции по terminal logs и chat transcripts. Это предлагаемый baseline, а не evidence из задеплоенной системы.

Дальше добавляйте только то, что оправдывает trace. Записывайте, кто поддерживает каждый компонент, сколько токенов или секунд он добавляет и какой regression test оправдает его удаление после апгрейда модели.

Через шесть месяцев тот, кто увидит progress_handoff=True, должен суметь найти failed traces, которые это оправдали, и regression cases, которые всё ещё держат его на месте. Traces объясняют, зачем компонент существует; актуальная behavior map объясняет, где его нужно трогать.
