Агентные циклы ризонинга ИИ-агентов в 2026 году: ReAct против ReWOO против «Планирование и выполнение»

Часть 1 серии «Инжиниринг агентного стека»

Агентный цикл ризонинга определяет способ, которым система планирует действия, вызывает инструменты, обрабатывает результаты и принимает решение о завершении работы. Именно этот поток управления влияет на затраты, латентность и возможности восстановления после получения неожиданных данных от инструментов.

В данной статье сравниваются три основных паттерна агентных циклов ризонинга, имеющих значение в 2026 году: ReAct, ReWOO и «Планирование и выполнение». Для демонстрации используется агент-аналитик рынка, созданный мной в LangGraph; полный код доступен на GitHub.

Это внутренний уровень рассмотрения серии. В последующих частях будут рассмотрены параметры, от которых зависит возобновление цикла, список доступных инструментов, правила их использования, среда рантайма, обеспечивающая продолжение работы, а также механизмы харнесс-инжиниринга, определяющие фактическое завершение задачи.

Кратко: ReAct обеспечивает гибкость, но сопряжён с высокими затратами; ReWOO работает быстро при предсказуемом порядке действий; подход «Планирование и выполнение» подходит для многоэтапного анализа. Промышленный ИИ-агент может переключаться между различными агентными циклами в зависимости от запроса, используя общее состояние и сохранённые узлы LangGraph, чтобы каждая задача выполнялась с учётом своих особенностей.

Цикл влияет на затраты, латентность и возможности восстановления

Полезный агент нуждается не только в качественном промпте. Его контрольная схема должна объединять процессы ризонинга, вызова инструментов и работы с памятью, одновременно обеспечивая обработку сбоев.

Агентный цикл ризонинга контролирует моменты, когда модель планирует действия, вызывает инструмент, получает результат и прекращает работу. Неправильный выбор такого цикла приводит к избыточным вызовам модели и увеличению латентности. Кроме того, это может помешать агенту восстановиться после получения неожиданных данных от инструмента.

Три паттерна ризонинга для ИИ-агентов

ReAct: мыслим, действуем, наблюдаем, повторяем

ReAct (Yao et al., 2022) — это первоначальный паттерн для интерактивных агентов. Он работает по следующему циклу:

  1. Мысль: агент формирует «мысль», чтобы разложить цель на части и спланировать следующий шаг.
  2. Действие: на основе этой мысли агент вызывает инструмент.
  3. Наблюдение: агент получает результат, что позволяет обновить его понимание перед следующей мыслью.

Преимущества:

  • Работа на основе реальных наблюдений снижает количество вымышленных фактов.
  • Агент может в реальном времени менять стратегию в зависимости от только что увиденного.
  • История вызовов инструментов и результатов наблюдений позволяет получить чёткий трейс выполнения.

Недостатки:

  • История данных накапливается и перерабатывается на каждом шаге, из-за чего латентность и затраты растут с увеличением длины цикла.
  • Является неэффективным, когда вызовы инструментов можно было запланировать заранее — именно в таких случаях проявляет преимущества ReWOO.
  • Отсутствие условия остановки или лимита шагов приводит к бесконечной работе цикла.

Идеально подходит для исследовательских задач, отладки и ситуаций, когда невозможно предсказать дальнейший ход событий.

ReWOO: всё планируем заранее

ReWOO (Reasoning WithOut Observation) — более эффективная версия ReAct. Секрет её эффективности заключается в разделении процессов ризонинга и выполнения инструментов: вместо остановки для наблюдения за каждым действием ReWOO планирует весь порядок вызовов инструментов за один проход.

  1. Планирование: один вызов большой языковой модели формирует полный план вызовов инструментов, используя местоимения-заменители (#E1, #E2) для обозначения результатов, которые ещё не генерированы.
  2. Выполнение: экзекьютор, не являющийся большой языковой моделью, выполняет запланированные инструменты последовательно или параллельно, заменяя указанные заменители на реальные значения.
  3. Решение: последний вызов большой языковой модели обрабатывает собранные данные и формирует окончательный ответ.

Преимущества:

  • Меньше повторных вызовов модели по сравнению с подходом ReAct, если первоначальный план остаётся корректным.
  • Более низкая латентность — не требуется повторная отправка истории на каждом шаге.
  • Планировщик можно отдельно подвергнуть файн-тюнингу без использования живой среды.

Недостатки:

  • Чувствителен к ошибкам инструментов, так как план предполагает их корректную работу.
  • Требует предсказуемых рабочих процессов.
  • Отсутствие явной логики возврата к альтернативному варианту приводит к продолжению выполнения некорректного плана.

Идеально для: быстрых снимков состояния, проверки статуса, дашбордов — любых задач, где поведение инструментов предсказуемо.

Планирование и выполнение: гибридный подход

Планирование и выполнение сочетает элементы двух предыдущих подходов. В описанной статье представлен простой разделитель, принятый большинством современных ИИ-агентов:

  1. Этап планирования: агент сначала генерирует план, разделяющий задачу на более мелкие подзадачи.
  2. Этап выполнения: затем агент выполняет эти подзадачи.

Изначально статья сосредотачивалась на промптинге без предоставления примеров. Современные фреймворки, такие как LangGraph, развили эту концепцию до полноценного шаблона оркестрации с последовательным выполнением и выбором модели для каждого шага (мощная модель ризонинга для планирования, более дешёвая — для выполнения).

Преимущества:

  • Иерархический ризонинг, напоминающий способ, которым человеческий эксперт разбивает проект на этапы.
  • Возможность перепланирования: можно приостановить работу и переоценить ситуацию, если результат шага оказался неожиданным.
  • Возможность специализации моделей: планировщик может быть ресурсоёмким, а экзекьютор — дешёвым.
  • Ограниченная сложность благодаря наличию чётких чекпоинтов после каждого шага.

Недостатки:

  • Более высокая латентность по сравнению с ReWOO из-за последовательного выполнения шагов.
  • Больше данных состояния, которые необходимо управлять.
  • Чрезмерная сложность для однократных запросов.

Идеально для: сложного многоэтапного анализа, исследовательских задач, любых случаев, требующих синтеза результатов в конце.

Данная таблица служит лишь отправной точкой, а не результатом бенчмарка. Используйте ReAct, когда каждое наблюдение может изменить следующее действие. Используйте Plan-and-Execute, когда общая задача может быть разложена на части, но отдельные шаги всё ещё требуют обратной связи. Используйте ReWOO, когда зависимости известны до выполнения, а сбой входных данных может прервать последующие вызовы. Прежде чем выбирать подход исключительно на основе затрат, измерьте производительность всех трёх методов с учётом латентности вашего инструмента, модели, набора задач и политики повторных попыток.

Пример реализации: агент-аналитик рынка

Чтобы проиллюстрировать это на практике, я создал агент-аналитик рынка, который использует все три подхода в одном кодовом базисе для выполнения задач по исследованию рынка.

Для оркестрации в нём применяется LangGraph. Все три подхода делит один и тот же объект состояния, поэтому роутер может выбирать, какой из них запустить для каждого запроса:

Определение состояния

Общее состояние хранит всю информацию, необходимую агенту во всех режимах работы:

class PlanStep(BaseModel):
    """A single step in the research plan."""
    step_number: int
    description: str
    tool_hint: str | None = None
    completed: bool = False
    result: str | None = None

class UserProfile(BaseModel):
    """Structured user context loaded from long-term memory."""
    risk_tolerance: str | None = None
    investment_horizon: str | None = None

class AgentState(BaseModel):
    """Main state for the Market Analyst Agent graph."""

    # Identity and profile context for memory-backed personalization
    user_id: str
    user_profile: UserProfile = Field(default_factory=UserProfile)

    # Message history with LangGraph's add_messages reducer
    messages: Annotated[list, add_messages] = Field(default_factory=list)

    # Execution mode (set by router)
    execution_mode: ExecutionMode | None = None

    # Plan-and-Execute state
    plan: list[PlanStep] = Field(default_factory=list)
    current_step_index: int = 0

    # ReWOO state
    rewoo_plan: list[ReWOOPlanStep] = Field(default_factory=list)

    # Research results
    research_data: ResearchData | None = None

    # HITL output
    draft_report: DraftReport | None = None
    report_approved: bool = False

Подход 1: реализация Plan-and-Execute

Plan-and-Execute — оптимальный выбор для задач, требующих многоэтапной синтезации. Ключевой момент заключается в разделении планирования и выполнения: сначала используется мощная модель для формирования плана, а затем применяется цикл ReAct для выполнения каждого шага с возможностью реагирования на результаты работы инструментов.

Как это соответствует описанному подходу:

  1. Один этап планирования в начале. Один вызов LLM генерирует полный план в виде списка описаний шагов.
  2. Вывод с использованием схемы, что позволяет проверить план перед его выполнением.
  3. Пока нет выполнения инструментов. Планировщик определяет только то, что нужно сделать, но не как.
  4. Шаги в читаемом формате. Каждый шаг представлен текстом, который будет интерпретироваться экзекьютором.
# System prompt guides the LLM to think like a research analyst
# creating a strategic plan, not immediate tool calls
PLANNER_SYSTEM_PROMPT = """You are a senior investment research analyst.
Break down stock analysis requests into 4-6 research steps covering:
1. Current price and basic metrics
2. Recent news and announcements
3. Competitor analysis (if relevant)
4. Financial health assessment
5. Risk factors
6. Investment thesis synthesis

Output as JSON with step_number, description, and tool_hint."""

# Schema-Guided Reasoning: Enforce structure with Pydantic
class PlanOutput(BaseModel):
    """Structured output for the planner."""

    steps: list[PlanStep] = Field(description="Research steps to execute")
    ticker: str = Field(description="The stock ticker being analyzed")

def planner_node(state: AgentState) -> dict:
    """Generate a research plan from the user's request.

    This is Phase 1 of Plan-and-Execute: creating the high-level strategy.
    """

    # Use a powerful model for strategic planning
    llm = ChatAnthropic(model="claude-sonnet-4-5-20250929", temperature=0)

    # Ask for a typed plan and validate it before execution.
    # The API can still fail, so production code also handles that exception.
    structured_llm = llm.with_structured_output(PlanOutput)

    # Context from long-term memory personalizes the plan
    profile_context = f"""
User Profile:
- Risk Tolerance: {state.user_profile.risk_tolerance}
- Investment Horizon: {state.user_profile.investment_horizon}
"""

    # Single LLM call creates the complete plan
    result: PlanOutput = structured_llm.invoke([
        SystemMessage(content=PLANNER_SYSTEM_PROMPT + profile_context),
        HumanMessage(content=f"Create a research plan for: {last_user_message}"),
    ])

    # State update: Store the plan and initialize tracking
    return {
        "plan": result.steps,           # The sequential steps to execute
        "current_step_index": 0,        # Start at step 0
        "research_data": ResearchData(ticker=result.ticker),  # Initialize data container
    }

Эта строка llm.with_structured_output(PlanOutput) представляет собой Schema-Guided Reasoning (SGR), который я уже рассматривал в предыдущей публикации. Благодаря этой схеме приложение может отклонить некорректный план ещё до того, как LangGraph начнёт использовать проверенные поля для формирования условных связей.

Шаблон 2: выполнение по схеме ReAct

Как только план готов, экзекьютор выполняет каждый шаг как отдельный агентный цикл ReAct. Это соответствует второму этапу: каждый шаг достаточно мал, чтобы цикл «мысль‑действие‑наблюдение» оставался сфокусированным, и ИИ-агент может оперативно реагировать на результаты, возвращаемые инструментами.

Как работает компонент ReAct:

  1. Итеративное выполнение — по одному шагу за раз с обратной связью от наблюдений.
  2. Цикл «мысль‑действие‑наблюдение» проходит внутри create_react_agent.
  3. Результаты предыдущего шага подаются в качестве контекста для текущего ризонинга.
  4. ИИ-агент выбирает инструменты на основе описания текущего шага.
  5. Он может изменить подход в ходе шага в зависимости от данных, полученных от инструмента.
# Tools available for the ReAct agent to choose from
TOOLS = [
    get_stock_snapshot,
    get_price_history,
    search_news,
    search_competitors,
    get_financials,
]

def executor_node(state: AgentState) -> dict:
    """Execute the current step using a ReAct agent.

    This is Phase 2 of Plan-and-Execute: adaptive execution of each planned step.
    Each step runs as a mini ReAct loop until completion.
    """

    # Get the current step from the plan
    current_step = state.plan[state.current_step_index]

    # Build context from what we've learned so far
    # This matters: each step builds on previous observations
    previous_context = ""
    for step in state.plan[:state.current_step_index]:
        if step.result:
            previous_context += f"\nStep {step.step_number}: {step.result}\n"

    # Create a ReAct agent for this step
    # LangGraph's create_react_agent implements the full Thought-Action-Observation loop:
    # 1. Agent generates a "thought" about what tool to call
    # 2. Agent calls the tool ("action")
    # 3. Tool returns result ("observation")
    # 4. Agent decides: call another tool or finish
    react_agent = create_react_agent(
        model=ChatAnthropic(model="claude-sonnet-4-5-20250929"),
        tools=TOOLS,
    )

    # Invoke the ReAct loop for this single step
    # The agent will loop internally until it completes the step
    result = react_agent.invoke({
        "messages": [
            SystemMessage(content=EXECUTOR_SYSTEM_PROMPT),
            HumanMessage(content=f"""Execute Step {current_step.step_number}:
{current_step.description}

Ticker: {state.research_data.ticker}
Previous findings: {previous_context}"""),
        ]
    })

    # Extract the final answer from the ReAct agent's message history
    # The last message contains the synthesis after all tool calls
    updated_plan = list(state.plan)
    updated_plan[state.current_step_index] = PlanStep(
        step_number=current_step.step_number,
        description=current_step.description,
        completed=True,
        result=result["messages"][-1].content,  # Final observation
    )

    # State update: Mark step complete and advance to next
    return {
        "plan": updated_plan,
        "current_step_index": state.current_step_index + 1,
    }

Таков основной поток работы «планирование‑исполнение»: мощная модель формирует план, после чего механизм ReAct выполняет каждый шаг с полной адаптивностью.

Шаблон 3: ReWOO для быстрого создания снапшотов

Для быстрых запросов ReWOO пропускает последовательный ризонинг и запускает инструменты параллельно. Планировщик заранее генерирует скомпилированный скрипт вызовов инструментов, после чего рабочий процесс выполняет его без участия LLM.

Структура этого подхода:

  1. Три фазы (Планировщик → Рабочий процесс → Решатель), без циклов.
  2. Вызовы инструментов содержат места замены #E1 и #E2 для данных, которых ещё нет.
  3. Во время выполнения LLM не задействуется — рабочий процесс просто запускает инструменты.
  4. Независимые инструменты работают параллельно.
  5. В конце происходит один вызов для синтеза всех результатов одновременно.

Фаза 1: планировщик ReWOO (заранее создаёт полную структуру выполнения)

class ReWOOPlanStep(BaseModel):
    """A step in the ReWOO plan with variable placeholders.

    Key difference from Plan-and-Execute's PlanStep:
    - Contains actual tool_name and tool_args (not just description)
    - Uses variable references (#E1) for dependencies
    """
    step_id: str  # e.g., "#E1" - becomes a variable
    description: str
    tool_name: str     # Exact tool to call
    tool_args: dict    # May contain variable refs like {"price": "#E1"}
    depends_on: list[str] = []  # For dependency ordering
    result: str | None = None

class ReWOOPlanOutput(BaseModel):
    """Structured output for ReWOO planner."""
    steps: list[ReWOOPlanStep] = Field(description="Planned tool calls with variables")

def rewoo_planner_node(state: AgentState) -> dict:
    """Generate a complete plan of tool calls upfront.

    This is the key difference from Plan-and-Execute: instead of creating
    human-readable step descriptions, we create EXACT tool calls that
    the worker will execute blindly.
    """

    llm = ChatAnthropic(model="claude-sonnet-4-5-20250929", temperature=0)

    # Schema-Guided Reasoning ensures valid tool call specifications
    structured_llm = llm.with_structured_output(ReWOOPlanOutput)

    ticker = state.research_data.ticker if state.research_data else "UNKNOWN"

    # Single LLM call to plan ALL tool executions
    result: ReWOOPlanOutput = structured_llm.invoke([
        SystemMessage(content=REWOO_PLANNER_PROMPT),

Ticker: {ticker}

Output tool calls with:
- step_id: Variable name (#E1, #E2, etc.)
- description: What this accomplishes
- tool_name: Exact tool from the list
- tool_args: Dictionary of arguments
- depends_on: List of step_ids this depends on"""),
    ])

    # State update: Store the complete execution plan
    # Worker will execute this without any LLM involvement
    return {"rewoo_plan": result.steps}

Фаза 2: рабочий процесс ReWOO (выполняет инструменты без участия LLM в ризонинге)

def rewoo_worker_node(state: AgentState) -> dict:
    """Execute all planned tools in parallel (no LLM calls).

    This is the key efficiency: Worker is "dumb" - it just runs tools
    according to the plan. No LLM calls = massive token savings.
    """

    results = {}  # Store results keyed by step_id (e.g., "#E1": "$150.23")

    # Execute ALL independent steps in parallel using ThreadPoolExecutor
    # This is where ReWOO gets its speed advantage
    with ThreadPoolExecutor(max_workers=5) as executor:
        futures = {
            executor.submit(execute_tool, step): step
            for step in state.rewoo_plan
            if not step.depends_on  # Only independent tools for parallel batch
        }

        # Collect results as they complete
        for future in as_completed(futures):
            step = futures[future]
            results[step.step_id] = future.result()
            # No LLM reasoning here - just store the raw tool output

    # State update: Store results for the Solver phase
    return {"rewoo_plan": updated_steps}

Фаза 3: решатель ReWOO (синтезирует все результаты в одном вызове LLM)

def rewoo_solver_node(state: AgentState) -> dict:
    """Synthesize all tool results into a flash briefing.

    This is the second efficiency gain: Instead of interleaving
    LLM calls with tool execution (like ReAct), we make ONE
    final synthesis call with all gathered data.
    """

    # Build context from ALL tool results at once
    tool_results = []
    for step in state.rewoo_plan:
        if step.result:
            tool_results.append(f"### {step.description}\n{step.result}")

    context = "\n\n".join(tool_results)

    # Single LLM call to synthesize everything
    structured_llm = llm.with_structured_output(FlashBriefingOutput)
    result = structured_llm.invoke([
        SystemMessage(content=REWOO_SOLVER_PROMPT),
        HumanMessage(content=f"Create a flash briefing from this data:\n\n{context}"),
    ])

    return {"draft_report": result}

ReWOO заранее планирует каждый вызов инструмента и сохраняет зависимости в местах замены вроде #E1 и #E2. Экзекьютор может выполнять независимые вызовы параллельно, не запрашивая модель о дальнейших действиях. Окончательный вызов модели объединяет все результаты, что позволяет сохранять предсказуемость и снижать затраты.

Где каждый шаблон вызывает модель

Эти три шаблона отличаются по времени и способу вызова LLM:

ШаблонКоличество вызовов LLM во время выполненияОбновление состоянияОсновной шаблон кода
Plan-and-Execute1 для планирования + 1 на каждый шагПоследовательное завершение шаговplanner_node() → цикл: executor_node() → reporter_node()
ReAct (внутри каждого шага)Множество вызовов на шаг (циклы «мысль‑действие»)Накопление истории сообщенийcreate_react_agent() выполняет внутренние циклы до завершения шага
ReWOO1 для планирования + 0 во время выполнения + 1 для синтезаПараллельное завершение инструментовrewoo_planner_node() → rewoo_worker_node() → rewoo_solver_node()

Различие между этими подходами заключается в том, что генерирует планировщик — именно он определяет всё, что происходит дальше.

  1. Подход «Планирование + выполнение» создаёт описания шагов, доступные для чтения человеком:

    # Planner output (list of PlanStep objects)
plan = [
    PlanStep(
        step_number=1,
        description="Get current price and key financial metrics",
        tool_hint="get_stock_price"
    ),
    PlanStep(
        step_number=2,
        description="Search for recent news and earnings",
        tool_hint="search_news"
    ),
    # ... more steps
]

    Экзекьютор считывает каждое описание и принимает решение о том, какие инструменты вызвать. Такой способ гибок, однако каждый шаг требует отдельного вызова LLM.

  2. Подход ReAct не предусматривает заранее составленного плана; он основан на итеративном ризонинге:

    # No planning phase - ReAct works step-by-step with accumulated messages
messages = [
    HumanMessage(content="Execute Step 1: Get current price"),
    AIMessage(content="I'll call get_stock_price"),
    ToolMessage(tool_call_id="1", content="$132.45"),
    AIMessage(content="Now I need metrics..."),
    # ... agent continues until step complete
]

    На каждом шаге происходит несколько вызовов LLM, что позволяет адаптироваться к получаемым данным, но обычно такой подход стоит дороже, чем два предыдущих варианта.

  3. Подход ReWOO формирует чёткие, готовые к выполнению спецификации вызовов инструментов:

    # Planner output (list of ReWOOPlanStep objects)
rewoo_plan = [
    ReWOOPlanStep(
        step_id="#E1",
        tool_name="get_stock_price",
        tool_args={"ticker": "NVDA"}
    ),
    ReWOOPlanStep(
        step_id="#E2",
        tool_name="search_news",
        tool_args={"query": "NVDA earnings", "limit": 5}
    ),
    # ... all tool calls planned upfront
]

    Рабочий процесс работает автономно, без участия LLM. Все вызовы модели происходят в планировщике и решателе, благодаря чему количество таких вызовов остаётся предсказуемым.

Течение памяти и состояния:

  • Подход «Планирование + выполнение»: состояние перемещается по plan → current_step_index → research_data.
  • Подход ReAct: состояние накапливается в массиве messages (весь исторический разговор).
  • Подход ReWOO: состояние перемещается по rewoo_plan, причём поля result заполняются самим рабочим процессом.

Сводная картина: связывание компонентов

Вот как эти три подхода сосуществуют в одной системе LangGraph. Они используют один и тот же AgentState и находятся в одном графе. Роутер выбирает оптимальный путь для каждого запроса, поэтому это один ИИ-агент с тремя режимами выполнения, а не три отдельных агента.

LangGraph позволяет описывать структуру связей декларативно:

def create_graph(checkpointer=None):
    builder = StateGraph(AgentState)

    # Add nodes
    builder.add_node("router", router_node)
    builder.add_node("planner", planner_node)
    builder.add_node("executor", executor_node)
    builder.add_node("reporter", reporter_node)
    builder.add_node("rewoo_planner", rewoo_planner_node)
    builder.add_node("rewoo_worker", rewoo_worker_node)
    builder.add_node("rewoo_solver", rewoo_solver_node)

    # Define edges
    builder.add_edge(START, "router")
    builder.add_conditional_edges("router", route_after_router, {
        "planner": "planner",
        "rewoo_planner": "rewoo_planner",
    })

    # Deep Research path
    builder.add_edge("planner", "executor")
    builder.add_conditional_edges("executor", route_after_executor, {
        "executor": "executor",  # Loop back for more steps
        "reporter": "reporter",  # Done with plan
    })
    builder.add_edge("reporter", END)

    # Flash Briefing path (ReWOO)
    builder.add_edge("rewoo_planner", "rewoo_worker")
    builder.add_edge("rewoo_worker", "rewoo_solver")
    builder.add_edge("rewoo_solver", END)

    return builder.compile(
        checkpointer=checkpointer,
        interrupt_before=["reporter"],  # HITL pause for approval
    )

Автоматический выбор подхода с помощью роутера

Для выбора подходящего цикла для каждого запроса был добавлен классификатор-роутер. Он использует метод Schema-Guided Reasoning для обеспечения надёжности классификации:

class ExecutionMode(str, Enum):
    """Execution mode for the agent."""

    DEEP_RESEARCH = "deep_research"  # Plan-and-Execute + ReAct (thorough)
    FLASH_BRIEFING = "flash_briefing"  # ReWOO (fast, token-efficient)

class RouterOutput(BaseModel):
    """Structured output for the router."""

    mode: ExecutionMode  # DEEP_RESEARCH or FLASH_BRIEFING
    ticker: str
    reasoning: str

ROUTER_SYSTEM_PROMPT = """Classify the user's request:

1. **deep_research**: Complex analysis requiring synthesis
   - Examples: "Analyze strategic risks", "investment thesis"

2. **flash_briefing**: Quick snapshots, simple data retrieval
   - Examples: "quick snapshot", "current price"

Default to deep_research if unclear."""

structured_llm = llm.with_structured_output(RouterOutput)

Благодаря этому пользователи не должны выбирать режим работы — роутер сам направляет запросы: «текущая цена» — в ReWOO, а «инвестиционная тезис» — в подход «Планирование + выполнение».

Основные выводы

  1. Подход ReAct обеспечивает наибольшее количество точек обратной связи, но за счёт многократных вызовов модели.
  2. Подход ReWOO сокращает количество вызовов модели, когда инструменты надёжны и зависимости предсказуемы.
  3. Подход «Планирование + выполнение» подходит для сложного анализа, который можно разложить перед выполнением, но при этом требуется обратная связь на каждом шаге.
  4. Роутер может сам выбирать подход для каждого запроса, избавляя пользователя от необходимости принимать решения.
  5. Для корректной работы цикла необходимо сохранять состояние на случай перерыва или перезапуска рабочего процесса. Об этом будет рассказано в части 2.
