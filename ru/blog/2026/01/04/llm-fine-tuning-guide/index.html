Руководство по файн-тюнингу LLM: LoRA, QLoRA, Unsloth, Axolotl

Viacheslav Dubrov

2026-01-04 · Обновлено 2026-09-12 · 21 мин · Инженерия моделей

Автоматический перевод

Эта статья была автоматически переведена с оригинальной английской версии.

Это руководство предназначено для Python-инженеров, которые решают, нужно ли и как выполнять файн-тюнинг большой языковой модели. Вы узнаете, когда файн-тюнинг предпочтительнее промптинга или retrieval и как выбирать между такими методами, как LoRA и QLoRA. Также в руководстве объясняется, как подготовить данные, оценить обученную модель и спланировать её деплой.

Примеры объясняют конфигурации и проверки. Это не проверенный сквозной рецепт обучения: в практической части отдельно приведены команды из companion-репозитория и предлагаемая конфигурация обучения.

Краткое сравнение этих вариантов см. в материале Fine-Tuning vs RAG vs Prompting.

Нужно ли вообще выполнять файн-тюнинг?

Прежде чем тратить часы GPU, решите, действительно ли файн-тюнинг — подходящий инструмент для вашей задачи.

Byte говорит

Если единственное недостающее поведение — валидный JSON, сначала проверьте constrained decoding на исходных весах. Обучение — слишком долгий способ обнаружить пропущенную фигурную скобку.

Файн-тюнинг изменяет поведение, закодированное в весах. Retrieval предоставляет свидетельства во время инференса, поэтому это лучшая отправная точка для фактов, которые меняются или требуют цитирования. Новые документы становятся доступны только после ingestion и индексации; сопоставьте эту свежесть со своими требованиями.

Понятные промпты и примеры дешевле итерировать, чем запускать новое обучение. Возможно, они уже решают проблему стиля или следования инструкциям. Файн-тюнинг может уменьшить количество повторяющихся промпт-токенов, но латентность сервинга зависит от модели, длины ответа, оборудования и реализации; обновление весов само по себе не ускоряет модель.

Для синтаксических ограничений библиотеки вроде xgrammar и outlines маскируют недопустимые следующие токены в рамках поддерживаемой схемы или грамматики. Успешно завершённая constrained generation принадлежит этому языку. Усечение и другие незавершённые генерации обрабатывайте отдельно и валидируйте результат перед использованием. Ограничение не может сделать ID клиента истинным или гарантировать уместность выбора инструмента. Измеряйте его латентность на своём бэкенде, а не предполагайте фиксированный overhead.

Сделайте бизнес-кейс измеримым

Файн-тюнинг может уменьшить регулярное число промпт-токенов или позволить меньшей модели достичь целевого качества, но ни одна из этих выгод не гарантирована. Рассчитайте точку безубыточности на собственном трафике и тарифах:

[ \text{запросы до безубыточности} = \frac{\text{стоимость обучения + оценки + деплоя}} {\text{стоимость базового запроса} - \text{стоимость запроса с tuned-моделью}} ]

Если знаменатель мал, отрицателен или основан на непроверенном предположении о качестве, экономического обоснования у проекта пока нет.

[!TIP] Гибридная схема Распространённая архитектура — адаптированная под задачу небольшая модель плюс retrieval для изменяющихся фактов. Используйте большую модель с промптингом как baseline и оставляйте меньшую модель только если она достигает тех же порогов качества и безопасности для конкретной задачи.

Типы файн-тюнинга

Файн-тюнинг обычно принимает одну из трёх основных форм. Они различаются необходимым типом данных и тем, чему обучают модель.

1. Continued pre-training (self-supervised)

Вы обучаете базовую модель на дополнительном сыром тексте, используя следующий токен в каждой последовательности как целевой. Это self-supervised learning: текст содержит собственные target-значения, как и в исходном претрейнинге.

Когда использовать:

  • В домене есть словарь, которого базовая модель никогда не видела (медицина, право, внутренние кодовые базы).
  • У вас много доменного текста, но нет размеченных пар (input, output).
  • Базовая модель плохо справляется с доменной терминологией.

Пример: обучение на миллионах клинических записей, чтобы модель освоила медицинские сокращения, названия препаратов и клинические процессы.

2. Supervised fine-tuning (SFT)

SFT обучается на размеченных парах (input, output). Вы показываете модели точный ответ, который хотите получать для каждого входа.

Когда использовать:

  • У вас есть конкретная задача с чистым форматом input/output.
  • У вас есть качественные размеченные данные, даже если их немного.
  • Вам нужно предсказуемое поведение на известной форме входных данных.

Пример: обучение на парах (описание SQL-запроса, SQL-код) для text-to-SQL. Этот фиксированный календарный интервал предполагает, что signup_date хранится в UTC:

{
    "input": "Get users who signed up in August 2026 (UTC)",
    "output": "SELECT * FROM users WHERE signup_date >= '2026-08-01' AND signup_date < '2026-09-01'"
}

3. Instruction tuning

Instruction tuning — частный случай SFT, предназначенный для обучения моделей следовать широкому набору инструкций на естественном языке. Датасет состоит из пар (instruction, response) для множества разных задач.

Когда использовать:

  • Вы создаёте ассистента общего назначения (например, ChatGPT или Claude).
  • Модель должна обрабатывать разнообразные открытые запросы.
  • Вы создаёте чат-интерфейс.

Пример: обучение на тысячах разнообразных инструкций вроде «Суммаризируй эту статью», «Напиши стихотворение о X», «Объясни Y простыми словами».

7 этапов пайплайна файн-тюнинга

Файн-тюнинг — это пайплайн, а не одна команда. На каждом этапе есть собственные failure mode, и пропуск одного из них обычно проявляется позже в виде плохой модели.

Каждый этап опирается на предыдущий:

  1. Подготовка данных — определите единицу оценки, разделите данные, затем очистите и отформатируйте их
  2. Выбор модели — выберите подходящую базовую модель и загрузите веса
  3. Настройка обучения — сконфигурируйте оборудование, гиперпараметры и стратегию оптимизации
  4. Файн-тюнинг — запустите обучение SFT, DPO или ORPO
  5. Оценка — проведите бенчмарк и проверьте качество
  6. Деплой — экспортируйте и запустите сервинг модели
  7. Мониторинг — отслеживайте качество, обслуживайте систему и итерируйте

[!WARNING] Данные — фундамент Обучение воспроизводит систематические дефекты в примерах. Проверьте разметку, утечки, покрытие и соответствие политикам до того, как тратить время на перебор параметров оптимизатора.

Этап 1: Подготовка данных

Многие проекты файн-тюнинга проваливаются именно здесь, а не на этапе обучения. Современная подготовка данных — это не просто запуск regex по CSV.

Пять преобразований после разделения источников

Назначьте исходные группы в train или evaluation до преобразования строк. Тикет поддержки и все его переписывания должны оставаться в одном разделе. Кластеризуйте известные near-duplicates до назначения групп, затем ещё раз проверьте разделы после очистки. Зафиксируйте evaluation set; аугментируйте только training data.

Составьте список ошибок, которым примеры должны научить модель, затем определите обязательные поля и метки каждой строки. Выберите инструменты обработки для этих шагов; DataTrove и Distilabel могут помочь с крупными датасетами.

1. Ingestion и фильтрация

  • Действие: удалите повреждённый UTF-8 и нерелевантный контент. Размечайте отказы по политике: корректные отказы оставляйте как training targets и evaluation cases; исключайте только невалидные или нерелевантные отказы.
  • Инструменты: Trafilatura для извлечения и модели fastText для определения языка; распределённые модели lid.176 распознают 176 языков.

2. Политика работы с чувствительными данными

  • Действие: решите, чему модели разрешено обучаться, затем при необходимости редактируйте, токенизируйте или исключайте персональные и конфиденциальные поля.
  • Инструменты: Microsoft Presidio или scrubadub.
  • Почему: детектор — лишь один из контролей; требования к происхождению данных, согласию, хранению, доступу и удалению всё равно действуют.

3. Удаление дубликатов (MinHash LSH)

  • Действие: удалите near-duplicates, чтобы уменьшить повторения и риск утечек; это не предотвращает запоминание.
  • Инструменты: DataTrove хорошо подходит для обработки в терабайтном масштабе.

4. Синтетическая аугментация, если нужна

  • Действие: используйте подходящую teacher-модель, чтобы преобразовать обучающие примеры в пары instruction-response, сохранив их source ID. Не выполняйте аугментацию для отложенного раздела.
  • Инструменты: Distilabel.
  • Валидация: выбирайте примеры ответов teacher-модели, проверяйте их по той же рубрике, что и человеческую разметку, и отдельно отчитывайтесь о результатах для синтетических и написанных людьми примеров. Такой evaluation subset называется slice; другие полезные slices включают язык и тип задачи.

5. Форматирование

  • Действие: преобразуйте данные в стандартный формат (Alpaca или ShareGPT).

Примеры форматов данных

Формат Alpaca (следование инструкциям):

{
    "instruction": "Summarize the following text.",
    "input": "The text to be summarized...",
    "output": "This is the summary."
}

Хранение в стиле ShareGPT (диалоговое):

{
    "conversations": [
        { "from": "user", "value": "Hello, who are you?" },
        { "from": "assistant", "value": "I am a helpful AI assistant." }
    ]
}

Что действительно важно

  • Покрытие важнее объёма. Добавляйте примеры, представляющие разные failure mode, а не повторы простого большинства.
  • Чистота. Удаляйте нерелевантный текст, нормализуйте пробелы, поддерживайте единообразное форматирование.
  • Баланс. Сохраняйте важные редкие случаи и отчитывайтесь о качестве по каждому slice.
  • Разделение. Разделяйте по источнику, пользователю, документу или времени, если случайное разделение строк создаёт утечки near-duplicates.
  • Происхождение. Для каждой версии датасета фиксируйте источник, лицензию или разрешение, историю преобразований и путь удаления данных.

Этап 2: Выбор модели и оборудования

Базовая модель и минимальный объём GPU-памяти определяют, что именно вы сможете обучать.

Начинайте с самой маленькой базовой модели, которая уже проходит обязательные baseline-проверки. Убедитесь в следующем:

  • условия лицензии и распространения для предполагаемого продукта;
  • поведение в отношении языка, домена, tool use и безопасности до адаптации;
  • совместимость токенизатора и chat template с датасетом;
  • максимальный контекст и поведение при усечении, необходимые для реальных примеров;
  • поддержка в training framework и целевом serving engine.

Файн-тюнинг — этап адаптации, а не способ исправить неподходящую базовую модель. Если модель не справляется со способностями, которые датасет не покрывает, выберите другую базу, прежде чем запускать дополнительные эпохи.

Оценивайте конкретный запуск, а не маркетинговый класс

Универсальной таблицы «размер модели → GPU» не существует. Пиковое потребление памяти меняется в зависимости от precision весов, оптимизатора, количества обучаемых параметров, длины последовательности, micro-batch, activation checkpointing, реализации attention и overhead фреймворка. Начните с оценки памяти, затем выполните короткий smoke test на максимальной длине в точном целевом стеке.

В исходной статье о QLoRA модель LLaMA 65B поместилась на одной GPU объёмом 48 GB в конкретной конфигурации авторов. Это полезная граница, но не обещание, что любая современная архитектура 70B, длина контекста, kernel или trainer поместятся на том же устройстве.

Математика памяти

Для модели с PPP параметрами одни только веса требуют примерно 2P2P2P байт в BF16/FP16 или 0.5P0.5P0.5P байт при четырёх битах — до учёта метаданных квантизации и runtime-буферов. Полное обучение в стиле Adam добавляет градиенты, состояния оптимизатора и часто master-веса повышенной точности. LoRA устраняет большую часть памяти под обучаемые состояния; QLoRA дополнительно уменьшает объём памяти под замороженные базовые веса. Однако при большой длине последовательности доминировать могут активации.

Используйте следующий процесс:

  1. Выберите максимальные длину последовательности и micro-batch, которые необходимо поддерживать.
  2. Оцените веса и обучаемые состояния, оставив запас под активации и kernels.
  3. Выполните один шаг forward/backward на максимальной длине.
  4. Зафиксируйте пиковый объём выделенной и зарезервированной памяти.
  5. Только после этого масштабируйте batch size, rank, длину последовательности или число GPU.

Этап 3: Настройка обучения и методы

От сохранённых строк к training targets

ShareGPT — это форма датасета, а ChatML — один из вариантов сериализации. Преобразуйте from/value в роли и поля, которые принимает trainer, затем используйте chat template выбранной модели. Не подставляйте ChatML-токены только потому, что данные являются диалоговыми.

Для приведённой выше строки с приветствием нормализованные сообщения выглядят так:

messages = [
    {"role": "user", "content": "Hello, who are you?"},
    {"role": "assistant", "content": "I am a helpful AI assistant."},
]
# Inspection step after loading the selected model's tokenizer:
rendered = tokenizer.apply_chat_template(
    messages, tokenize=False, add_generation_prompt=False,
)
print(rendered)

Проверьте фактически сериализованную строку до обучения: разделители ролей, end-of-turn-токены и схемы инструментов должны совпадать с инференсом. Для строки с tool use сохраняйте определения инструментов, tool calls ассистента и результаты инструментов как отдельные поля. Убедитесь, что усечение не удаляет supervised response и не обрезает аргумент инструмента посередине.

Loss masking определяет, за предсказание каких токенов модель получает вознаграждение. При обучении по всей последовательности могут учитываться текст пользователя, системы, инструмента и ассистента. При assistant-only training эти контекстные токены остаются видимыми для attention, но их labels игнорируются (обычно -100); учитываются только assistant spans. Для этого приветствия ответ должен быть target, а вопрос пользователя — нет, если целевым поведением является assistant-only.

Документация TRL по SFT поддерживает assistant_only_loss=True для conversational datasets, чьи templates предоставляют generation spans. Template без таких spans не может сформировать эту mask. Для prompt/completion datasets есть отдельная опция completion_only_loss. До включения любой из них проверьте один токенизированный batch и декодируйте токены с non-ignored labels. Затем повторите проверку для tool conversation и примера максимальной длины. Приведённая ниже иллюстративная конфигурация обучения намеренно использует full-sequence loss; assistant-only training требует дополнительной проверки template и mask.

Выберите длину последовательности по распределению данных и выполните проверку памяти на максимальной длине из Этапа 2. Packing помещает несколько коротких примеров в одну обучающую последовательность. Начните без него, чтобы границы строк было легко проверять. Исследуйте packing только после того, как сериализованные строки и labels будут корректны.

Полный файн-тюнинг против PEFT

При полном файн-тюнинге (FFT) обновляется каждый вес, поэтому объём градиентов и состояния оптимизатора масштабируется со всей моделью. Пиковое потребление нельзя вывести только из числа параметров, но оно намного выше памяти, необходимой для загрузки весов на инференс.

Parameter-efficient fine-tuning (PEFT) обучает только небольшую часть параметров, замораживая остальные. Математика становится гораздо проще.

LoRA: отправная точка

LoRA (Low-Rank Adaptation) замораживает предобученную матрицу и представляет выученное обновление двумя меньшими матрицами. Исходная статья объясняет это гипотезой о том, что полезные обновления при адаптации имеют низкий intrinsic rank.

Здесь dind_{in}din​ — ширина входа слоя, а doutd_{out}dout​ — его ширина выхода. Rank rrr — меньшая общая размерность двух обучаемых матриц: меньший rank означает меньше обучаемых параметров. Параметр α\alphaα управляет масштабом обновления через отношение α/r\alpha/rα/r.

Для замороженной матрицы W0∈Rdout×dinW_0 \in \mathbb{R}^{d_{out} \times d_{in}}W0​∈Rdout​×din​ LoRA обучает:

  • A∈Rr×dinA \in \mathbb{R}^{r \times d_{in}}A∈Rr×din​
  • B∈Rdout×rB \in \mathbb{R}^{d_{out} \times r}B∈Rdout​×r

Адаптированный слой:

W′=W0+αrBAW' = W_0 + \frac{\alpha}{r}BAW′=W0​+rα​BA

Для этой матрицы адаптер имеет r(din+dout)r(d_{in}+d_{out})r(din​+dout​) обучаемых параметров вместо dindoutd_{in}d_{out}din​dout​. Для квадратной матрицы шириной 4,096 и rank 16 это 128-кратное сокращение числа обучаемых параметров для данной матрицы. Экономия для всей модели зависит от того, на какие матрицы устанавливаются адаптеры.

DoRA: LoRA с декомпозицией весов

DoRA (Weight-Decomposed Low-Rank Adaptation) разделяет magnitude каждого вектора весов и его направление. В статье о DoRA обновление LoRA применяется к направляющей компоненте, а magnitude обучается отдельно.

Как это работает:

Вместо того чтобы рассматривать веса как единое целое, DoRA разделяет предобученные веса на две компоненты:

  1. Magnitude — обучаемое значение для каждого вектора весов.
  2. Направление — нормализованный вектор, обновляемый низкоранговыми матрицами.

В компактной column-wise нотации:

W′=mV+BA∥V+BA∥cW' = m \frac{V + BA}{\lVert V + BA \rVert_c}W′=m∥V+BA∥c​V+BA​

где:

  • m = magnitude (обучаемая)
  • V=W0V = W_0V=W0​ = исходная замороженная матрица; нормализуйте после добавления BABABA
  • BABABA = выученное низкоранговое обновление направления
  • ∥⋅∥c\lVert \cdot \rVert_c∥⋅∥c​ = нормализация по столбцам

Что даёт эта дополнительная структура:

  • Больше степеней свободы, чем у стандартной LoRA, поскольку magnitude может изменяться независимо.
  • Более высокие результаты, чем у LoRA, в нескольких конфигурациях, описанных авторами метода.
  • Дополнительные параметры и вычисления, поэтому выигрыш нужно проверять на своей задаче и serving path.

Слияние адаптеров для multi-task learning

Отдельные адаптеры позволяют одной замороженной базе поддерживать несколько задач. Можно направлять запросы к адаптеру, обслуживать несколько адаптеров одним engine, если это поддерживается, или создать offline merged candidate. Слияние может привести к interference, поэтому оценивайте объединённый артефакт, а не предполагайте, что исходные адаптеры корректно компонуются.

Распространённые методы слияния:

  1. Concatenation — объединение параметров адаптеров с увеличением эффективного rank. Быстро и просто.
  2. Linear combination — взвешенная сумма адаптеров. Даёт дополнительные knobs.
  3. SVD — matrix decomposition для слияния. Гибче, но медленнее.

Пример: один адаптер для суммаризации, другой для перевода, объединённые в одну multi-task-модель.

Этап 4: Файн-тюнинг и preference alignment

SFT обучается на демонстрациях. Preference optimization вместо этого обучается на сравнениях вроде «chosen response A лучше rejected response B». Используйте его только когда попарное предпочтение действительно является правильной разметкой ошибки; для фактической корректности и соответствия политикам часто нужны более сильные эвалуаторы, чем глобальное предпочтение.

RLHF на основе PPO

RLHF означает reinforcement learning from human feedback. Policy — это языковая модель, генерирующая ответы; reward model оценивает эти ответы по предпочтениям, выученным на человеческих сравнениях. Рецепт на основе PPO состоит из трёх этапов:

  1. SFT — обучение задаче.
  2. Reward model — обучение на человеческих предпочтениях (chosen против rejected).
  3. PPO (Proximal Policy Optimization) — генерация ответов и обновление языковой модели для увеличения их reward scores.

Операционная стоимость возникает из-за множества компонентов:

  • Сложность реализации и сопровождения.
  • Высокая стоимость — вы обучаете несколько моделей.
  • Sampling из обучаемой модели требует проверок на нестабильные обновления и ответы, которые эксплуатируют reward model, но не решают задачу.

DPO

DPO (Direct Preference Optimization) отбрасывает отдельную reward model и reinforcement-learning loop. Он усиливает chosen responses и препятствует большим изменениям относительно фиксированной исходной модели, называемой reference model. Статья о DPO выводит эту objective-функцию, ограничивая отклонение вероятностей ответов от reference; математическим ограничением является KL-divergence.

Preference pair содержит один и тот же prompt и два candidate responses. В этой сокращённой строке показаны её поля; реальные labels должны содержать полные responses и причину предпочтения одного ответа:

{
    "prompt": "Explain quantum computing",
    "chosen": "Quantum computing uses qubits...",   # Preferred response
    "rejected": "Well, it's complicated..."        # Non-preferred response
}

Что меняется с операционной точки зрения:

  • Более простой code path (нет отдельной reward model и RL loop).
  • Обучение на сохранённых preference pairs вместо генерации новых ответов для reward scoring на каждом update.
  • Фиксированная reference model или сохранённые log probabilities для training responses в стандартной формулировке.

DPO проще прототипировать, чем полный PPO pipeline, но это не автоматическое улучшение качества. Результаты зависят от исходной policy, качества пар, настроек loss, эффектов длины и протокола оценки. Сравнивайте DPO с SFT-чекпоинтом на тех же held-out preference и task suites.

ORPO

ORPO (Odds-Ratio Preference Optimization) объединяет SFT negative-log-likelihood loss со штрафом odds ratio для rejected responses. Он устраняет отдельную reference model и может объединить обучение задаче и preference optimization в одном запуске.

Как это работает: ORPO использует combined loss, который одновременно делает две вещи:

  1. Максимизирует likelihood chosen response (обучение задаче).
  2. Штрафует rejected response с помощью odds-ratio term (обучение предпочтениям).

Гиперпараметры, которые стоит знать (TRL 1.12.0 API):

# API shown in TRL 1.12.0 documentation
from trl.experimental.orpo import ORPOConfig

config = ORPOConfig(
    learning_rate=8e-6,  # Very low, as recommended by the ORPO paper
    beta=0.1,            # Controls strength of preference penalty
    # ... other params
)
  • Learning rate: в статье использовались низкие значения; настраивайте его под свою модель, batch и данные, а не копируйте одно значение как правило.
  • Beta: управляет вкладом preference term относительно SFT term.

Компромиссы:

  • Один training stage вместо двух.
  • Нет reward model.
  • Нет forward pass reference model.
  • Связанный запуск: если обучение задаче или preference behavior деградирует, в том же pipeline нет промежуточного SFT-чекпоинта для проверки.

Выбирайте по данным и дизайну оценки:

  • Используйте DPO, если у вас уже есть удовлетворительный SFT-чекпоинт и нужен более простой offline preference experiment.
  • Тестируйте ORPO, если reference-free, single-stage objective соответствует вашим данным и операционным ограничениям.
  • Используйте PPO-based RLHF, если online sampling с явной выученной reward является частью требований и вы можете отслеживать reward exploitation.

Ни один метод не является default для всех задач. Сохраняйте SFT-only baseline и отчитывайтесь как о task metrics, так и о preference metrics.

Фреймворки для файн-тюнинга

Фреймворки пересекаются по возможностям и быстро меняются. Выбирайте по execution path, который необходимо поддерживать, фиксируйте версии и сохраняйте конфигурацию обучения достаточно переносимой для воспроизведения вне notebook.

Unsloth — скорость и эффективность памяти

Unsloth интегрируется с Hugging Face trl и transformers и предоставляет оптимизированные kernels, checkpointing и пути квантизированного файн-тюнинга для поддерживаемых моделей.

  • Пользовательские Triton GPU kernels для attention, RoPE и cross-entropy, которые обходят overhead PyTorch.
  • Эффективный по памяти backprop: активации пересчитываются на backward pass вместо хранения в памяти.
  • Fused operations, объединяющие несколько шагов (layer norm + linear и аналогичные) в единичные GPU-вызовы.
  • 4-bit quantization, напрямую интегрированная в QLoRA path, с оптимизированной деквантизацией.

[!IMPORTANT] Порядок импортов важен Следуйте порядку импортов из примера Unsloth для зафиксированной вами версии. Unsloth применяет patches во время импорта, поэтому импорт до trl и transformers помогает избежать пропущенных оптимизаций или version-specific ошибок.

# Correct order
from unsloth import FastLanguageModel  # Must be first!
from trl import SFTTrainer
from transformers import TrainingArguments

# Avoid this order with Unsloth's patched path
from trl import SFTTrainer
from unsloth import FastLanguageModel

Лучше всего подходит для: обучения на одной GPU, прототипирования, Colab notebooks и тех, кто следит за счётом за GPU.

Опубликованные показатели скорости и памяти меняются в зависимости от модели, длины последовательности, batch, precision и оборудования. Измеряйте tokens per second и пиковую память на собственном запуске, а не воспринимайте рекламное соотношение как свойство фреймворка.

Предлагаемая конфигурация обучения TRL

Это схематичная конфигурация, а не код, поставляемый companion. Передайте train_dataset и eval_dataset как Hugging Face datasets с колонками messages и, для tool examples, tools. Этап 5: Оценка

Byte говорит

Если один и тот же тикет поддержки попал в training и evaluation, более высокий score может быть наградой за запоминание этого тикета. Разделяйте данные по тикетам до создания строк или переписываний.

Зафиксируйте test cases, правила подсчёта и проходные thresholds до первого запуска. Как минимум сравнивайте tuned checkpoint с точной untuned base при одинаковых prompt, decoding settings и tool environment. Публикуйте aggregate quality только после проверки failure slices, которые должен был улучшить проект.

Отслеживайте четыре группы:

  1. Целевая задача: exact match, execution success, human rubric или другой outcome, связанный с use case.
  2. Регрессия: общие способности и ранее поддерживаемые task slices, которым адаптация может навредить.
  3. Безопасность и политики: отказы, утечки данных, prompt injection или доменные ограничения.
  4. Эксплуатация: латентность, throughput, память, размер артефакта и стоимость в целевой serving-конфигурации.

Автоматизированные бенчмарки

Используйте lm-evaluation-harness для проверки релевантных стандартизированных задач вместе с продуктовыми тестами. Для этой команды нужен merged Hugging Face checkpoint. В её примере используется legacy merged output companion из Этапа 6; команда не загружает адаптер, сохранённый предлагаемой выше конфигурацией. Подставьте merged checkpoint, который собираетесь оценивать:

lm_eval --model hf \
    --model_args pretrained=./outputs/unsloth-nemotron-function-calling-merged \
    --tasks hellaswag,arc_easy,mmlu \
    --batch_size 8

LLM-as-judge

Для субъективного качества большая модель может помогать с оценкой, но откалибруйте её на примерах, проверенных людьми, и скройте identity кандидата:

judge_prompt = """
Rate this response from 1-5 on:
- Relevance
- Accuracy
- Formatting

Response: {model_output}
Expected: {ground_truth}
"""

Доменно-специфичная оценка

Откладывайте реальные примеры по источнику, пользователю, документу или времени, чтобы near-duplicates не утекали между разделами. Для function calling проверяйте всю траекторию: выбор инструмента, аргументы, результат выполнения, recovery и финальный ответ. При небольшом размере выборки сообщайте confidence intervals или paired win/loss counts и проверяйте каждую регрессию в критическом slice.

Этап 6: Деплой и форматы выходных данных

Выбирайте артефакт с учётом serving engine и плана rollback, а не только размера файла. Эти CLI-примеры относятся к legacy companion, а не к предлагаемому фрагменту TRL. Его каталог адаптера по умолчанию — outputs/unsloth-nemotron-function-calling, а каталоги -merged и -gguf предназначены для экспортов. Каждый CLI-вызов снова запускает обучение; это не команда только для экспорта. Для реального релиза экспортируйте выбранный оценённый checkpoint, а не сравнивайте артефакты от отдельных повторных запусков обучения.

1. LoRA-адаптер

uv run finetune  # Default adapter directory shown below
  • Размер: пропорционален целевым модулям, rank, слоям и dtype; часто намного меньше базы.
  • Лучше всего подходит для: разработки, версионируемых task adapters и engines с прямой поддержкой LoRA.
  • Дополнительный плюс: можно менять адаптеры без повторной загрузки базовой модели.

2. Merged model

uv run finetune --merge  # Creates a standalone full model
  • Размер: примерно равен полному base checkpoint в выбранной output precision.
  • Лучше всего подходит для: engines или путей дистрибуции, которые не поддерживают отдельный адаптер.
  • Компромисс: более крупный артефакт и более медленный rollout; зато проще загрузка одной модели.

3. Формат GGUF

uv run finetune --gguf q4_k_m  # File size and name depend on the exporter
  • Размер: зависит от модели; для Q4 variants примерно соответствует четырёхбитным весам плюс метаданные.
  • Лучше всего подходит для: CPU-инференса, Ollama, llama.cpp и edge-деплоя.
  • Варианты: q4_k_m (меньше), q5_k_m (выше fidelity весов), q8_0 (больше и выше fidelity). После конвертации измерьте влияние на задачу.

Этап 7: Сервинг и мониторинг

С vLLM

Этот serving sketch предполагает, что предлагаемый адаптер прошёл task evaluation и обучался с tool template, совместимым с Llama 3.1. Сохраните точно проверенный template как serving-chat-template.jinja. Совместимость адаптера в legacy ChatML-формате с этой парой parser/template не установлена. До публикации endpoint проверьте одну полную tool trajectory.

# Serve the base and expose a PEFT adapter as a model name. This parser and
# template pair is for a Llama 3.1-compatible function-calling adapter.
vllm serve nvidia/Llama-3.1-Nemotron-Nano-4B-v1.1 \
    --enable-lora \
    --lora-modules function-calling=./outputs/proposed-nemotron-adapter \
    --enable-auto-tool-choice \
    --tool-call-parser llama3_json \
    --chat-template ./serving-chat-template.jinja \
    --host 0.0.0.0 \
    --port 8000 \
    --max-model-len 4096

Эта намеренно минимальная flight schema проверяет генерацию аргументов через OpenAI-compatible API. Она запрашивает предлагаемый вызов book_flight с пунктом назначения; бронирование не выполняется. Проверьте response.choices[0].message.tool_calls на имя функции и JSON arguments. Для этого ввода ожидаемый результат — book_flight с {"destination": "Tokyo"}. Поскольку выбор инструмента автоматический, также проверьте, вернула ли модель вызов вообще:

from openai import OpenAI

client = OpenAI(base_url="http://localhost:8000/v1", api_key="dummy")
response = client.chat.completions.create(
    model="function-calling",
    messages=[{"role": "user", "content": "Book a flight to Tokyo"}],
    tools=[
        {
            "type": "function",
            "function": {
                "name": "book_flight",
                "description": "Book a flight to a city.",
                "strict": True,
                "parameters": {
                    "type": "object",
                    "properties": {
                        "destination": {"type": "string"},
                    },
                    "required": ["destination"],
                    "additionalProperties": False,
                },
            },
        }
    ],
    tool_choice="auto",
)

Руководство vLLM по tool calling требует auto tool choice и parser, соответствующий модели. Если в конфигурации токенизатора отсутствует chat template, передайте совместимый. При tool_choice="auto" constrained arguments также требуют strict: true хотя бы для одной функции и strict-compatible parameters schema. Необходимо включить server setting для strict tool calling (это задокументированное значение по умолчанию). Без этого opt-in vLLM извлекает calls из raw text, поэтому arguments могут быть malformed или нарушать schema.

С Ollama (локально)

Проверьте фактический каталог экспорта -gguf и подставьте имя созданного файла вместо MODEL_FILE.gguf ниже; версии Unsloth могут называть файлы по-разному. Один GGUF-файл не гарантирует корректное chat/tool formatting в Ollama или llama.cpp. Сопоставьте обученный template и проверьте импортированный артефакт.

# Create Modelfile
echo 'FROM ./outputs/unsloth-nemotron-function-calling-gguf/MODEL_FILE.gguf' > Modelfile

# Import to Ollama
ollama create my-function-model -f Modelfile

# Run
ollama run my-function-model

С llama.cpp (CPU)

С той же GGUF-экспортированной моделью и заменой имени файла эта команда проверяет ответ в plain text. Она не тестирует полный tool call:

./llama-cli -m ./outputs/unsloth-nemotron-function-calling-gguf/MODEL_FILE.gguf \
    -p "What's the weather in Tokyo?" \
    --ctx-size 4096

Мониторинг выпущенной модели

Жизненный цикл не заканчивается на хорошем training loss. Фиксируйте revision базовой модели, токенизатор и chat template, hash адаптера, версию датасета, конфигурацию обучения и evaluation report как единый release unit. В продакшене отслеживайте task success, невалидные ответы, policy failures, латентность и input drift по тем же slices, что использовались offline. Сохраняйте предыдущий артефакт загружаемым и определите rollback threshold до запуска.

Следующая проверка

До полного запуска проверьте один сериализованный диалог и его loss targets, затем выполните шаг forward/backward на максимальной длине. Сохраните эту конфигурацию вместе с разбиением датасета и baseline report. Если схема инструмента потеряна, сохраните её в training row. Если ответ усечён, скорректируйте длину последовательности и форматирование, чтобы полный ответ сохранялся. Решите эти проблемы до добавления эпох.
