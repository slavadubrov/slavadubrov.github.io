Метрики оценки RAG: retrieval, реранкинг, генерация

Viacheslav Dubrov

2026-05-10 · Обновлено 2026-09-12 · 38 мин · Поисковые и языковые системы

Автоматический перевод

Эта статья была автоматически переведена с оригинальной английской версии.

Для инженеров, которые эксплуатируют или оценивают системы retrieval-augmented generation (RAG), этот справочник сопоставляет сбои при парсинге документов, фильтрации, retrieval, реранкинге и генерации с метрикой, которая помогает выявить каждый из них. Здесь также показано, какие проверки выполняются до релиза, а какие мониторят live-трафик.

RAG-система со сломанными фильтрами релевантности может работать месяцами, не вызывая operational alert. Она по-прежнему возвращает ответы и укладывается в целевую latency, но ответы опираются на неполные свидетельства. Recall@k относительно исходного eligible gold set выявляет эту потерю. Дашборды latency и availability — нет.

Хотите сразу перейти к коду?

В runnable slavadubrov/rag-evals-demo репозитории выбранные метрики применяются к SciFact. make eval запускает suite, а make benchmark сравнивает конфигурации чанкинга, эмбеддингов и LLM. Ноутбуки 00–09 охватывают retrieval, фильтрацию, генерацию и примеры систем; они не реализуют каждую проверку из этого справочника. В демо используется embedded Qdrant, поэтому Docker не требуется.

TL;DR

  • Полезный evaluation stack охватывает ingestion, retrieval, grounding генерации, соответствие онтологии и system signals. RAGAS, TruLens, DeepEval, Arize Phoenix и TREC 2024 RAG Track предлагают библиотеки или публичные evaluation protocols. Но они не выбирают метрики за вас.
  • Для RAG, основанного на metadata и онтологии, неправильный тег или хрупкий hard predicate могут обнулить recall. Стандартный Recall@k фиксирует потерю, если сохраняет исходный eligible gold set. Метрика filter false-exclusion выявляет причину. Faithfulness всё ещё может оценивать claims относительно неполного контекста, но не способна диагностировать причину на уровне фильтра или retrieval. Пустой refusal может не содержать statements и дать NaN — в зависимости от реализации.

Часть 1: Определите критерии успеха до архитектуры

Составьте eval set до архитектурной схемы. Он задаст измеримую цель для каждого последующего выбора компонента.

Нельзя выбрать между BM25 и dense retrieval, recursive и semantic chunking или Cohere Rerank и BGE, пока не ясно, что именно вы оптимизируете. «Лучшие ответы» — не метрика. Пример требования к релизу: «faithfulness ≥ 0.85 на golden set из 200 запросов, покрывающем три главных интента, при p95 latency < 1.5 с и filter false-exclusion rate < 2%». Числа здесь условны; важно, чтобы у качества, покрытия, latency и фильтрации были явные thresholds.

Определите харнесс до написания retrieval-кода. Первый харнесс будет неправильным, и его придётся пересматривать. Исправить метрику гораздо дешевле, чем пересмотреть уже отправленную в production систему.

Три слоя пайплайна и два режима запуска

Production evaluation состоит из трёх слоёв пайплайна. Ingestion evaluation проверяет, сохраняют ли corpus и index исходный материал. Query-time evaluation проверяет, нашли ли query rewriting, фильтрация, retrieval, реранкинг и сборка контекста правильные свидетельства. Answer and production evaluation проверяет, использовал ли ответ эти свидетельства и сохраняется ли качество на live-трафике. Если свести слои к одному score, баг нормализации может затеряться внутри приемлемого answer score.

Эти слои описывают место возникновения сбоя. Offline и online описывают, когда и относительно каких данных выполняется проверка. Offline evaluation использует фиксированный датасет с известной ground truth; она воспроизводима и подходит для выбора компонентов, A/B-сравнений и CI-проверок, способных блокировать изменения. Online evaluation оценивает выборочный live-трафик и фиксирует regeneration, dwell time, явный feedback и реальный query drift. Она шумнее и сложнее для инструментирования.

Используйте оба режима там, где это полезно: фиксированные корпуса и query sets делают регрессии воспроизводимыми, а sampled live traces выявляют проблемы свежести и drift.

На уровне компонентов и end-to-end

Есть две распространённые ошибки. Evaluation только end-to-end показывает, что система сломана, но не где именно. Evaluation только компонентов может показать, что каждый компонент проходит проверку, хотя вся система всё равно не работает. Исправление — несколько headline end-to-end metrics для go/no-go решений плюс component metrics для диагностики. Retrieval metrics ловят регрессии retriever. Generation metrics ловят регрессии generator. End-to-end answer correctness выявляет integration failures.

Эти benchmarks расширяют покрытие, но не заменяют versioned query set приложения с eligible queries.

Часть 2: Карта точек evaluation

Используйте диаграмму, чтобы сопоставить симптом с первой diagnostic metric. Потери на upstream-этапах ограничивают downstream quality: плохой парсинг ограничивает retrieval, а плохой retrieval — реранкинг и генерацию. Faithfulness оценивает ответ, но никогда не указывает upstream-причину.

Часть 3: Ingestion evaluation

Многие production-сбои RAG начинаются на ingestion. Система работает на чистых тестовых документах, а затем ломается на реальных PDF, сканах, таблицах и неаккуратных страницах корпуса.

Byte говорит

Проверяйте страницы с таблицами отдельно. Парсер может выдать чистую прозу, одновременно превратив таблицу в одну длинную строку чисел.

Получение и парсинг документов

Что измерять:

  • Sanity check длины извлечения: extracted_chars / expected_chars для каждого класса документов выявляет подозрительные изменения длины, но дублированный или неправильный текст всё ещё может получить score 1.0. Сравнивайте выровненный текст с вручную очищенным reference, чтобы обнаружить пропуски и замены, а затем отдельно проверяйте footnotes, captions, содержимое таблиц и порядок чтения.

  • OCR accuracy: CER (Character Error Rate) и WER (Word Error Rate) — стандартные метрики для speech/OCR:

    CER=S+D+IN,WER=Sw+Dw+IwNw\text{CER} = \frac{S + D + I}{N}, \qquad \text{WER} = \frac{S_w + D_w + I_w}{N_w}CER=NS+D+I​,WER=Nw​Sw​+Dw​+Iw​​

    где SSS, DDD, III — замены, удаления и вставки на уровне символов, а NNN — количество символов в reference (для word-версии используется subscript www). Не применяйте один CER boundary ко всему корпусу. Калибруйте его по классу документов и downstream answer loss. Для печатного текста, рукописей и multilingual material характерны разные error profiles. Считайте метрики с помощью jiwer (jiwer.cer(refs, hyps), jiwer.wer(refs, hyps)) или HuggingFace evaluate. Для evaluation corpora доступны публичные benchmarks FUNSD и SROIE.

    from jiwer import cer, wer

refs = ["Mars has two moons, Phobos and Deimos."]
hyps = ["Mars has two m00ns, Phobos and Deirnos."]

print(f"CER = {cer(refs, hyps):.3f}")  # CER = 0.105
print(f"WER = {wer(refs, hyps):.3f}")  # WER = 0.286

  • Fidelity извлечения таблиц: TEDS (Tree-Edit-Distance-based Similarity) измеряет, насколько предсказанное дерево HTML-таблицы близко к reference, с нормализацией по размеру большего дерева. Из Zhong et al., 2020 (PubTabNet):

    TEDS(Ta,Tb)=1−EditDist(Ta,Tb)max⁡(∣Ta∣,∣Tb∣)\text{TEDS}(T_a, T_b) = 1 - \frac{\text{EditDist}(T_a, T_b)}{\max(|T_a|, |T_b|)}TEDS(Ta​,Tb​)=1−max(∣Ta​∣,∣Tb​∣)EditDist(Ta​,Tb​)​

    TEDS учитывает и структуру (строки, столбцы, spans), и содержимое ячеек. TEDS-S удаляет содержимое и оценивает только структуру. Reference implementation: teds.py PubTabNet (под капотом используется apted). Для evaluation corpora см. PubTabNet, FinTabNet и SciTSR. Наивные парсеры часто плохо работают с таблицами. Проведите benchmark до того, как начнёте им доверять.

  • Сохранение layout и структуры: порядок headings, целостность списков, порядок чтения в многостолбцовых PDF. Для labeled benchmark используйте DocLayNet. Сравнение «из коробки» может включать element parser, например unstructured, PDF-библиотеку вроде pymupdf и выбранный Docling pipeline. Docling предлагает standard и VLM paths; зафиксируйте, какой именно вы тестируете.

Сравнивайте разные семейства парсеров, например baseline на Tesseract, VLM-based OCR model и vendor candidate. Используйте stratified sample реальных классов документов при фиксированном DPI, включая чистые сканы, фотографии, таблицы, multilingual text, math и handwriting. Отчитывайтесь о CER или WER для каждого класса и TEDS для страниц с таблицами.

Очистка и нормализация

  • Точность удаления boilerplate: precision/recall относительно размеченных людьми boilerplate spans. Агрессивное удаление теряет релевантное содержимое, а недостаточное загрязняет эмбеддинги. Инструменты для сравнения: trafilatura, jusText, Resiliparse. Barbaresi (2021) сравнивает Trafilatura с baselines, включая jusText; Resiliparse — отдельный candidate, а не система, evaluated в той статье.

  • Unicode normalization: доля документов, дающих идентичный NFC и NFKC output (вычисляется стандартной библиотекой unicodedata.normalize), — полезный сигнал drift в compatibility form. Но он не обнаруживает невидимые/default-ignorable code points или похожие символы из разных scripts: первые нужно искать явно, а для вторых применять policy или detector для Unicode confusables, если это входит в scope.

  • Точность language detection: F1 на labeled multilingual sample. Это критично для multilingual indexes. Используйте fasttext-langdetect (Facebook’s lid.176), lingua-py или cld3. FLORES-200 содержит evaluation text на 200 языках, но test slice должен определяться языковым составом production.

  • Эффективность deduplication (MinHash / LSH): precision/recall near-duplicate detector относительно вручную размеченного набора. Идея состоит в том, чтобы оценивать Jaccard similarity J(A,B)=∣A∩B∣∣A∪B∣J(A, B) = \frac{|A \cap B|}{|A \cup B|}J(A,B)=∣A∪B∣∣A∩B∣​ между наборами document shingles с помощью kkk hash-функций случайных перестановок (Broder, 1997) и группировать near-duplicates с помощью LSH banding (Indyk & Motwani, 1998). Переберите количество hashes и Jaccard threshold на своём корпусе. Отдельно отслеживайте false-merge rate (портит ответы) и missed-merge rate (зря расходует место в index). datasketch содержит реализацию, использованную ниже; её параметры иллюстративны:

    from datasketch import MinHash, MinHashLSH

def shingles(text: str, k: int = 5) -> set[str]:
    text = text.lower()
    return {text[i:i + k] for i in range(len(text) - k + 1)}

def to_minhash(text: str, num_perm: int = 128) -> MinHash:
    m = MinHash(num_perm=num_perm)
    for s in shingles(text):
        m.update(s.encode("utf-8"))
    return m

docs = {
    "d1": "Mars has two moons, Phobos and Deimos.",
    "d2": "Mars has two moons, Phobos and Deimos!",   # near-dup
    "d3": "Curiosity rover landed on Mars in 2012.",
}

lsh = MinHashLSH(threshold=0.8, num_perm=128)
for did, text in docs.items():
    lsh.insert(did, to_minhash(text))

print(sorted(lsh.query(to_minhash(docs["d1"]))))  # ['d1', 'd2']

  • PII scrubbing: precision и recall, вычисленные отдельно для каждого типа сущностей (email, SSN, names, addresses). Ошибки recall создают compliance risk, а ошибки precision ухудшают качество ответов. Operating point согласуйте с legal team. Возможные инструменты: Microsoft Presidio, scrubadub или fine-tuned NER model на labeled set.

Чанкинг определяет качество retrieval

Чанкинг определяет, какие свидетельства дойдут до ответа. В vendor benchmark NVIDIA за 2025 год page-level chunking показал наивысшую среднюю end-to-end answer accuracy в протестированной конфигурации, где таблицы и графики сохранялись целыми блоками. Это измеряет answer accuracy, а не retrieval recall. Считайте такой результат свидетельством для протестированного корпуса, а не универсальным победителем.

Semantic chunking группирует соседние предложения по embedding similarity и разрезает текст на границах несходства. LangChain’s SemanticChunker и LlamaIndex’s SemanticSplitterNodeParser реализуют эту стратегию. Она может улучшить recall по сравнению с фиксированными окнами, когда важны тематические границы.

LangChain’s RecursiveCharacterTextSplitter по умолчанию пробует двойные переводы строк, одиночные переводы строк, пробелы, а затем отдельные символы: ["\n\n", "\n", " ", ""]. Она не определяет границы предложений, если не настроить подходящие separators или не использовать sentence-aware splitter. Выбирайте window и overlap под структуру документов, затем сравнивайте варианты на golden set.

Метрики для отслеживания:

  • Coherence чанка: coherence=cos⁡(si,sj)‾within−cos⁡(si,sj)‾across boundary\text{coherence} = \overline{\cos(s_i, s_j)}_{\text{within}} - \overline{\cos(s_i, s_j)}_{\text{across boundary}}coherence=cos(si​,sj​)​within​−cos(si​,sj​)​across boundary​, где sis_isi​ — sentence embeddings.   • Качество границ: human-labeled оценка «разумно ли здесь разрезать?» на sample плюс structural check, что чанки не разрывают таблицы, списки или numbered sections.
  • Оптимальный размер чанка: переберите token sizes (128, 256, 512, 1024) и постройте график Recall@k в зависимости от размера на golden set. Выберите knee. Не берите размер из tutorial.
  • Эффективность overlap: проведите ablation для нескольких overlap fractions и измерьте Recall@k. Прекратите увеличивать overlap, когда локальная recall curve выровняется или стоимость дублирования превысит прирост.
  • Fidelity атрибуции чанка: доля чанков, сохраняющих проверяемый source pointer (номер страницы, section anchor, doc ID). Без этого невозможен auditability.
  • Late vs. early chunking: late chunking (Günther et al., 2024) сначала эмбеддит весь документ, а затем сегментирует его, сохраняя global context (reference implementation в jina-embeddings-v3). Contextual Retrieval (Anthropic, 2024) добавляет к каждому чанку context, сгенерированный LLM. Оба подхода повышают cost. Перед внедрением benchmark их на своём корпусе.

Моё мнение: structural chunking (разделение по headings, tables и sections — реализуется парсерами вроде unstructured.io или обходом AST, который уже создал ваш парсер) используется недостаточно. Если документы имеют структуру, задействуйте её до добавления similarity heuristics. Recursive character splitting — baseline; semantic chunking в основном оправдывает overhead на неструктурированной прозе.

Генерация эмбеддингов

  • Benchmarks для выбора модели: используйте результаты retrieval tasks из MTEB, BEIR для zero-shot generalization и MIRACL для multilingual retrieval в качестве comparison points. Для retrieval MTEB обычно сообщает nDCG@10; другие task families используют иные metrics. MTEB Python package позволяет запускать benchmarks локально. Перенос результатов с English MTEB на язык с меньшими ресурсами рассматривайте как гипотезу, которую нужно проверить на labeled set этого языка.
  • Domain-specific evaluation: не трактуйте rank general benchmark как результат для домена. Размер domain golden set определяйте по coverage matrix и уровню uncertainty, который допустим для решения. Затем переранжируйте candidate models на нём с помощью ranx или pytrec_eval. Domain set может изменить порядок в leaderboard, поэтому публикуйте вместе с результатом dataset slice, retrieval protocol и confidence interval.
  • Обнаружение embedding drift: сравнивайте две коллекции эмбеддингов: фиксированный reference sample и rolling current sample. Maximum mean discrepancy (MMD) проверяет, различаются ли их distributions. Другой вариант — validated classifier, обученный различать reference и current samples. Kullback–Leibler (KL) divergence сравнивает probability distributions, поэтому требует явного estimator, например выбранных histograms; raw embedding coordinates не являются probabilities. Также измеряйте nearest-neighbor stability для fixed probe set. evidently и alibi-detect реализуют model-based и statistical detectors. Comparative study Evidently — один vendor evaluation; сравните методы на известных shifts собственных эмбеддингов.
  • Multi-vector vs. single-vector: late interaction сохраняет token-level representations вместо схлопывания каждого документа в один vector; ColBERT — canonical design, reference implementations доступны в RAGatouille и PyLate. Более богатое представление увеличивает стоимость index и retrieval. До внедрения сравните quality, storage и latency с single-vector baseline на том же domain set.

Построение index

  • Recall@k при approximation: сравнивайте approximate-nearest-neighbour (ANN) index с exact brute-force baseline при том же k — в FAISS это IndexHNSWFlat (или IndexIVFFlat) против IndexFlatIP/IndexFlatL2. Приемлемую recall loss задавайте из downstream quality budget. Проект ann-benchmarks отслеживает Pareto curves recall–QPS для разных библиотек.
  • HNSW tuning: HNSW (Hierarchical Navigable Small World) — layered proximity graph; см. Malkov & Yashunin, 2018. Он реализован в hnswlib, IndexHNSWFlat из FAISS и большинстве vector DB. В HNSW есть три параметра: M (graph fan-out), efConstruction (candidate width на этапе build) и efSearch (candidate width на этапе query). Начните с documented defaults библиотеки, затем переберите параметры, пока recall–latency curve не будет соответствовать требованиям evaluation set.
  • IVF tuning: IVF (Inverted File index — partition vectors с помощью k-means на nlist cells, а во время query сканирует nprobe ближайших cells; см. IndexIVFFlat и IndexIVFPQ из FAISS). Переберите nlist и nprobe относительно exact-search recall и latency. Filtered queries benchmark отдельно, потому что разные index families и vector databases по-разному реализуют filter traversal.
  • Update freshness lag: время от commit документа до его доступности для retrieval. Отслеживайте p50 и p99. Для систем с regulatory requirements дополнительно фиксируйте долю queries, обслуженных stale indexes.

Часть 4: Query-time evaluation

Query-time lane содержит метрики, диагностирующие retrieval path. Одного Recall@k недостаточно, чтобы понять, вызвал ли сбой rewriting, фильтр, retrieval, реранкинг или сборка контекста.

Понимание и rewriting query

  • Качество query expansion: Recall@k uplift на golden set, expanded query против raw query. До тестирования задайте minimum useful gain и его uncertainty. Если expansion не достигает этого требования, она не оправдывает свою latency и cost. Classical PRF (pseudo-relevance feedback) baselines вроде RM3 и Bo1 по-прежнему полезны для sanity check; LLM-based expansion должна их превосходить.
  • HyDE evaluation: HyDE (Gao et al., 2022) генерирует hypothetical answer с помощью LLM, эмбеддит его и выполняет retrieval относительно этого представления. Подход добавляет generation latency и новую surface area для сбоев. Отдельно измеряйте Recall@10 на in-domain, out-of-domain и low-confidence slices, затем решайте, должна ли технология быть default path, fallback или не использоваться вовсе.
  • Multi-query generation: union Recall@k для N rewrites против single query. Переберите N и выберите точку на recall–latency frontier. Реализации: MultiQueryRetriever из LangChain и QueryFusionRetriever из LlamaIndex.
  • Точность intent classification: стандартные precision/recall/F1 для каждого intent (вычисляются с помощью sklearn.metrics.classification_report), но operative metric — routing correctness: вызывается ли правильный downstream pipeline?
  • Adaptive routing: Adaptive-RAG (Jeong et al., NAACL 2024) показывает, что не каждому query нужна одна и та же retrieval strategy. Отслеживайте router accuracy как classification problem на labeled set из случаев «retrieval не нужен / one-shot / iterative».

Для iterative search нужен budgeted end-to-end test

Агент может выполнить search, изучить результат и искать снова вместо retrieval одного фиксированного top-k списка. Текущий tau3 knowledge domain предоставляет configurable RAG и agentic shell-based search, превращая это в конкретный evaluation path, а не только архитектурный sketch. Для локального сравнения дайте one-shot и iterative retrieval один и тот же eligible corpus и явные limits по времени, model tokens и tool calls. Записывайте каждый query и увиденные evidence на каждом turn; оценивайте final evidence coverage, answer correctness, citation support и budget-exhaustion failures. Дополнительные search calls полезны только тогда, когда добавленные evidence улучшают answer в рамках заданных limits.

def recall_at_k(ranked, gold_set, k):
    if k <= 0 or len(ranked) != len(set(ranked)):
        raise ValueError("require positive k and unique document IDs")
    if not gold_set:
        return 0.0
    hit = sum(1 for d in ranked[:k] if d in gold_set)
    return hit / len(gold_set)

def reciprocal_rank(ranked, gold_set):
    if len(ranked) != len(set(ranked)):
        raise ValueError("require unique document IDs")
    # MRR contribution per query: 1/rank of the first relevant doc.
    for rank, d in enumerate(ranked, start=1):
        if d in gold_set:
            return 1.0 / rank
    return 0.0

def ndcg_at_k(ranked, gold_set, k):
    if k <= 0 or len(ranked) != len(set(ranked)):
        raise ValueError("require positive k and unique document IDs")
    # binary relevance: rel ∈ {0, 1}
    gains = [1.0 if d in gold_set else 0.0 for d in ranked[:k]]
    dcg = sum(g / log2(i + 2) for i, g in enumerate(gains))
    # ideal DCG: all gold docs ranked first, capped by k
    n_gold_in_topk = min(k, len(gold_set))
    idcg = sum(1.0 / log2(i + 2) for i in range(n_gold_in_topk))
    return dcg / idcg if idcg else 0.0

Hybrid retrieval и reciprocal rank fusion

BM25 — sparse lexical scorer, объединяющий exact-term matching, term weighting и length normalization. Он доступен в rank_bm25, Elasticsearch, OpenSearch и большинстве search engines.

Reciprocal Rank Fusion (Cormack, Clarke и Buettcher, SIGIR 2009) объединяет BM25 и dense rankings по position. Исходная настройка k=60 — полезный baseline. RRF не зависит от scores, поэтому не требует cross-lane normalization, необходимой для linear interpolation. Имея labeled set, достаточно большой для оценки стабильного delta, протестируйте также convex combination и настройте α.

Моя гипотеза: hybrid retrieval вместе с cross-encoder reranker может помочь на technical, log-style и code corpora. На сильно semantic corpora gain может быть небольшим. Сравнивайте результат с dense-only и sparse-only lanes, поскольку плохая конфигурация fusion может уступить любому из входов. Companion SciFact notebook — один ограниченный тест, а не общий результат.

Реализация занимает несколько строк.

from collections import defaultdict

# two retrieval lanes: dense embeddings and BM25.
dense  = ["d3", "d7", "d1", "d4", "d2", "d9", "d10"]
sparse = ["d2", "d3", "d8", "d1", "d11", "d4", "d6"]

def rrf(rankings: list[list[str]], k: int = 60) -> list[tuple[str, float]]:
    """Reciprocal Rank Fusion (Cormack et al., SIGIR 2009).

    score(d) = sum over rankings of 1 / (k + rank(d))
    Score-agnostic: only rank position matters. k=60 is the canonical default.
    """
    scores: dict[str, float] = defaultdict(float)
    if k <= 0:
        raise ValueError("k must be positive")
    for ranking in rankings:
        if len(ranking) != len(set(ranking)):
            raise ValueError("each ranking must contain unique document IDs")
        for rank, doc in enumerate(ranking, start=1):
            scores[doc] += 1.0 / (k + rank)
    return sorted(scores.items(), key=lambda kv: kv[1], reverse=True)

fused = rrf([dense, sparse], k=60)
for doc, score in fused[:5]:
    print(f"{doc}  score={score:.5f}")
# d3  score=0.03252   <- rank 1 dense, rank 2 sparse
# d2  score=0.03178   <- rank 5 dense, rank 1 sparse
# d1  score=0.03150
assert [doc for doc, _ in fused[:3]] == ["d3", "d2", "d1"]
try:
    rrf([["d1", "d1"]])
except ValueError:
    pass
else:
    raise AssertionError("one lane must not vote twice for a document")

Важно понимать, чего RRF не делает: он никогда не смотрит на raw similarity scores. Dense retriever с cosine 0.98 и BM25 lane со score 17.4 напрямую несопоставимы. Z-score и min-max normalization устраняют affine scale differences, но не калибруют score как relevance. На normalized values и, следовательно, на результат fusion по-прежнему влияют outliers, shape distribution и candidate set. Любую score-based combination проверяйте на labeled queries.

RRF использует только rank. Если retriever ставит документ на position 2, его vote равен 1 / (60 + 2) независимо от raw score, который привёл к этой позиции.

Реранкинг

  • ΔnDCG / ΔMRR: uplift относительно no-rerank на golden set и на той глубине, которую реально использует приложение. Вычисляйте retrieval metrics с reranker и без него на идентичных candidate sets.
  • Cross-encoder vs. bi-encoder: bi-encoder независимо эмбеддит query и doc (по одному vector на сторону) и считает score через dot product; cross-encoder объединяет query+doc и выполняет один forward pass с совместным attention по обоим. Cross-encoders обменивают forward pass для каждого candidate на более богатое query–document interaction. Reference implementation: sentence-transformers CrossEncoder. Benchmark relevance и latency на конкретных hardware, batch size и candidate depth; не переносите результат одной model или managed service в другую среду.
  • Listwise vs. pointwise: pointwise оценивает каждую пару (query, doc) независимо; listwise совместно оценивает весь candidate list, чтобы модель могла сравнивать candidates. Оценивайте оба подхода на одних и тех же candidate sets. Score threshold калибруйте для каждой model и corpus, а не переносите published example как универсальный.

Сборка контекста и lost-in-the-middle

Многие случаи «хороший retrieval, плохой answer» начинаются на этапе сборки контекста.

  • Context relevance: Ragas ContextRelevance оценивает supplied context list с помощью двух prompts и normalized ratings; это не score для каждого чанка. Для диагностики чанков явно оценивайте каждую query–chunk pair, например cross-encoder, и публикуйте distribution относительно локально calibrated threshold.
  • Supplied-context citation coverage: число distinct supplied chunks с citations, делённое на число distinct chunks supplied. Empty-context cases отчитывайте отдельно. Этот observable proxy показывает, какие chunks получили citations, но не какие chunks модель использовала внутренне и поддерживают ли citations claims. Отдельно проверяйте citation support и сопоставляйте coverage с answer quality и token cost.
  • Обнаружение lost-in-the-middle: synthetic eval, в котором gold chunk размещается на позициях {first, middle, last} длинного context, после чего измеряется answer correctness. В цитируемом исследовании Liu et al. (TACL 2024) сообщается U-shaped degradation в условиях long context. Аналогичную картину для текущей модели рассматривайте как гипотезу для проверки. Mitigations: сначала rerank, затем переставить top-k так, чтобы chunk с highest score оказался first или last (LangChain’s LongContextReorder делает именно это), либо агрессивно сжать middle chunks. Измеряйте это position-stratified eval, а не только aggregate score. Рабочий runnable position-stratified eval находится в notebook 06 (module: evaluation/lost_in_middle.py).
  • Context compression: вместе с answer correctness публикуйте compression ratio (input tokens / output tokens). Инструменты включают LangChain’s ContextualCompressionRetriever и LongLLMLingua. Заранее задайте максимальную допустимую correctness loss с учётом risk и token budget приложения, а затем отклоняйте configurations, которые её превышают.

Часть 5: Filter false-exclusion rate

Этой метрике посвящён отдельный раздел, потому что aggregate retrieval scores не могут связать miss с relevance filter. Eligibility filters оценивайте отдельно относительно caller entitlements; документ вне этого множества должен оставаться исключённым.

Жёсткий relevance predicate вроде product = Y AND locale = en-US может обнулить effective recall среди документов, доступных caller. Корректно реализованный Recall@k фиксирует потерю, поскольку его denominator остаётся исходным eligible relevant-document set. Но он не показывает, вызвал ли miss filter, retriever или ranker. Faithfulness оценивает claims относительно retrieved context. Она может по-прежнему дать высокий score claims, поддержанным этим неполным контекстом, но не диагностирует причину на уровне filter или retrieval. Empty refusal может не содержать statements и дать NaN — в зависимости от реализации; не считайте это доказательством, что faithfulness одобрил refusal.

Выделенная ветка начинается после enforcement entitlement eligibility: разрешённый релевантный документ существует, но relevance filter удаляет его до retrieval. Recall@k регистрирует падение; только exclusion rate связывает его с predicate.

Метрика

filter_false_exclusion_rate =
    (# queries where all gold docs were excluded by metadata filter) /
    (# queries with at least one entitlement-eligible gold doc)

Это query-level definition, считающее catastrophic exclusions: ни один eligible relevant document не выжил. Перед scoring пересекайте gold set каждого query с entitlement set caller; неeligible document не является false exclusion. Для multi-gold queries стандартный Recall@k всё равно показывает partial loss; если важна эта граница, добавьте per-document exclusion rate. Для вычисления любой из rates нужны (a) ground-truth doc IDs для каждого eval query и (b) instrumentation, логирующий applied filter predicates, а не только final results. Target задавайте исходя из стоимости исключения valid answer и confidence interval production sample.

Ниже — рабочая реализация. Она сравнивает корректный standard recall с invalid evaluator, который переопределяет relevance после фильтрации.

# A small worked example where relevance predicates remove eligible documents.
docs = [
    {"id": "d1", "tenant": "acme",   "locale": "en-US"},
    {"id": "d2", "tenant": "acme",   "locale": "en-GB"},
    {"id": "d3", "tenant": "globex", "locale": "en-US"},
    {"id": "d4", "tenant": "acme",   "locale": "en-US"},
    {"id": "d5", "tenant": "acme",   "locale": "de-DE"},
    {"id": "d6", "tenant": "acme",   "locale": "fr-FR"},
]

# Tenant isolation is an eligibility invariant, not a relevance experiment.
# Verify it independently before evaluating relevance preferences.
eligible_docs = [d for d in docs if d["tenant"] == "acme"]
assert {d["id"] for d in eligible_docs} == {"d1", "d2", "d4", "d5", "d6"}

queries = [
    # the gold doc lives in en-GB but the dynamic filter forced en-US
    {"qid": "q1", "gold": {"d2"}, "filter": lambda d: d["locale"] == "en-US"},
    # the gold doc is correctly within the tenant filter
    {"qid": "q2", "gold": {"d4"}, "filter": lambda d: d["tenant"] == "acme"},
    # the gold doc lives in fr-FR but the dynamic filter forced en-US
    {"qid": "q3", "gold": {"d6"}, "filter": lambda d: d["locale"] == "en-US"},
    # the gold doc passes the filter (de-DE locale match)
    {"qid": "q4", "gold": {"d5"}, "filter": lambda d: d["locale"] == "de-DE"},
]

def filter_false_exclusion_rate(queries, eligible_docs):
    n_with_gold, n_excluded = 0, 0
    eligible_ids = {d["id"] for d in eligible_docs}
    for q in queries:
        eligible_gold = q["gold"] & eligible_ids
        if not eligible_gold:
            continue
        n_with_gold += 1
        survivors = {d["id"] for d in eligible_docs if q["filter"](d)}
        if not (eligible_gold & survivors):
            n_excluded += 1
    if not n_with_gold:
        raise ValueError("false-exclusion rate needs queries with eligible gold")
    return n_excluded / n_with_gold, n_with_gold

rate, eligible_query_count = filter_false_exclusion_rate(queries, eligible_docs)
print(f"filter_false_exclusion_rate = {rate:.2%}")
# filter_false_exclusion_rate = 50.00%
print(f"eligible queries = {eligible_query_count} / {len(queries)}")
# eligible queries = 4 / 4

# Correct Recall@k keeps the original eligible gold set as its denominator.
def standard_recall_at_k(queries, eligible_docs, k=10):
    recalls = []
    eligible_ids = {d["id"] for d in eligible_docs}
    for q in queries:
        eligible_gold = q["gold"] & eligible_ids
        if not eligible_gold:
            continue
        # demo only: the survivor set stands in for a ranked run.
        # A real harness ranks the survivors first, then slices to k.
        survivors = [d for d in eligible_docs if q["filter"](d)][:k]
        survivor_ids = {d["id"] for d in survivors}
        recalls.append(len(eligible_gold & survivor_ids) / len(eligible_gold))
    return sum(recalls) / len(recalls) if recalls else 0.0

print(f"standard recall@10 = {standard_recall_at_k(queries, eligible_docs):.2%}")
# standard recall@10 = 50.00%

# INVALID: rebuilding the gold set after filtering changes the question.
# It drops queries whose relevant documents did not survive, then scores 100%.
def invalid_recall_over_filtered_gold(queries, eligible_docs, k=10):
    recalls = []
    all_doc_ids = {d["id"] for d in eligible_docs}
    for q in queries:
        all_survivors = {d["id"] for d in eligible_docs if q["filter"](d)}
        filtered_gold = q["gold"] & all_doc_ids & all_survivors
        if not filtered_gold:
            continue
        top_k_ids = set(list(all_survivors)[:k])
        recalls.append(len(filtered_gold & top_k_ids) / len(filtered_gold))
    return sum(recalls) / len(recalls) if recalls else 0.0

invalid = invalid_recall_over_filtered_gold(queries, eligible_docs)
print(f"INVALID recall (filtered gold) = {invalid:.2%}")
# INVALID recall (filtered gold) = 100.00%

assert rate == 0.5
assert standard_recall_at_k(queries, eligible_docs) == 0.5
assert invalid == 1.0

# An unauthorized-only gold document belongs in an entitlement test, not this metric.
unauthorized_only = [
    {"qid": "q5", "gold": {"d3"}, "filter": lambda d: d["locale"] == "en-US"},
]
assert eligible_query_count == 4
assert filter_false_exclusion_rate(queries + unauthorized_only, eligible_docs) == (rate, 4)
for unscorable in ([], unauthorized_only):
    try:
        filter_false_exclusion_rate(unscorable, eligible_docs)
    except ValueError:
        pass
    else:
        raise AssertionError("an unmeasured exclusion rate must not pass as zero")

Функция возвращает rate и число queries с eligible gold. Если denominator пуст, она выбрасывает exception, а не сообщает успокаивающий zero; обязательная release check должна трактовать это как missing evidence. Queries, у которых весь gold unauthorized, остаются в отдельных entitlement tests.

Половина queries теряет gold doc из-за filter, поэтому корректный Recall@10 падает до 50%. Этот score фиксирует symptom, но не может атрибутировать его. False-exclusion rate показывает, что predicate удалил два ответа ещё до запуска retriever. Намеренно invalid evaluator сообщает 100% только потому, что выбрасывает эти failures из gold set. Ни одна model не может восстановить документ, отфильтрованный заранее.

Rate 50% выше воспроизводится unit test в companion repo: tests/test_filter_exclusion.py::test_50_percent_exclusion_rate. Notebook 04 запускает этот сценарий на SciFact с synthetic metadata, чтобы можно было увидеть, как реальный filter обнуляет recall; runtime metric (с companion metrics для predicate-precision/recall) находится в evaluation/filter_exclusion.py.

Companion metric: predicate precision и recall

Если фильтрация динамическая (например, LLM извлекает filter predicates из query), рассматривайте predicate extractor как classification model и оценивайте его соответственно. Измеряйте predicate precision и recall относительно labeled set из (query, correct predicate) pairs. Predicate error rate не переводится напрямую в такую же point loss retrieval recall; измеряйте, как часто эти ошибки исключают gold document. После того как hard filter удалил gold document, никакой реранкинг не поможет.

Eligibility filters vs. relevance preferences

Authorization, tenant isolation, legal jurisdiction и publication state определяют, может ли документ попасть в candidate set. Оставляйте их hard filters и проверяйте независимо; Recall@k, false-exclusion rate и relevance precision не разрешают их ослаблять.

Для relevance preference вроде locale, recency или version сравните hard predicate и soft boost на одном held-out наборе eligible queries:

For each relevance preference F:
  hard_recall_F  = retrieval_recall@k with F as a hard filter
  soft_recall_F  = retrieval_recall@k with F as a +0.X rerank boost
  hard_precision = relevant_in_top_k / k under hard filter
  soft_precision = relevant_in_top_k / k under soft boost
  precision_gain = hard_precision - soft_precision
  precision_gain_CI = paired-query uncertainty interval for precision_gain
  exclusion_rate = % of queries where the gold doc was filtered out (hard)

Pre-register Δ_min, ε, and recall_loss_max for this workflow.
Use a hard predicate only if:
  lower_bound(precision_gain_CI) >= Δ_min
  AND exclusion_rate <= ε
  AND hard_recall - soft_recall >= -recall_loss_max.
Otherwise prefer a soft boost.

Minimum useful precision gain, uncertainty interval, ε и recall-loss bound выбирайте исходя из вреда от исключения иным образом eligible answer, пользы дополнительной precision и размера held-out sample. Это локальные release criteria, а не универсальные thresholds. Отдельный пост об этом trade-off запланирован; см. follow-ups в конце.

Часть 6: Generation evaluation

Retrieval metrics показывают, что система могла бы ответить правильно. Но не показывают, что она ответила правильно. Generation metrics закрывают этот пробел.

Faithfulness и groundedness

RAGAS faithfulness разбирает answer на atomic claims (короткие самодостаточные factual statements), а затем проверяет каждый claim относительно retrieved context с помощью LLM judge:

faithfulness=∣claims supported by context∣∣total claims∣\text{faithfulness} = \frac{|\text{claims supported by context}|}{|\text{total claims}|}faithfulness=∣total claims∣∣claims supported by context∣​

Faithfulness проверяет support в supplied evidence; она не устанавливает, что evidence корректны или достаточны для ответа на вопрос. Ответы без claims записывайте отдельно и публикуйте их количество, а не присваивайте пустому answer perfect faithfulness.

def extract_claims(answer: str) -> list[str]:
    # Production: an LLM call that decomposes the answer.
    # Demo: split on sentence-final punctuation.
    return [c.strip() for c in answer.replace("?", ".").replace("!", ".").split(".") if c.strip()]

def verify_claim(claim: str, context: str) -> bool:
    # Production: an NLI (natural-language inference) model or LLM judge.
    # Demo: a deterministic stand-in so the example runs offline.
    entailed_pairs = {
        "Mars has two moons": True,
        "Phobos and Deimos orbit Mars": True,
        "Mars has a thick atmosphere": False,  # unsupported by context
        "Curiosity landed in 2012": True,
    }
    for k, v in entailed_pairs.items():
        if k.lower() in claim.lower() or claim.lower() in k.lower():
            return v
    words = [w.lower() for w in claim.split() if len(w) > 3]
    return all(w in context.lower() for w in words) if words else False

context = (
    "Mars has two moons, Phobos and Deimos. NASA's Curiosity rover "
    "landed on Mars in 2012."
)
answer = (
    "Mars has two moons. Phobos and Deimos orbit Mars. "
    "Mars has a thick atmosphere. Curiosity landed in 2012."
)

claims = extract_claims(answer)
verdicts = [(c, verify_claim(c, context)) for c in claims]
faithfulness = sum(1 for _, ok in verdicts if ok) / len(verdicts) if verdicts else None
for c, ok in verdicts:
    print(f"  [{'✓' if ok else '✗'}] {c}")
print(f"faithfulness = {faithfulness:.2f}" if faithfulness is not None else "no_claims")
# faithfulness = 0.75   (one unsupported claim about the atmosphere)
assert faithfulness == 0.75
assert extract_claims("") == []

Evaluation atomic facts

FActScore (Min et al., EMNLP 2023) разбирает long-form generations на atomic facts, извлекает evidence для каждого fact, помечает каждый как supported / not-supported и сообщает supported fraction:

FActScore=∣supported atomic facts∣∣total atomic facts∣\text{FActScore} = \frac{|\text{supported atomic facts}|}{|\text{total atomic facts}|}FActScore=∣total atomic facts∣∣supported atomic facts∣​

Reference implementation: shmsw25/FActScore. Подход хорошо работает для biographies, summaries и других long-form outputs. Но будьте внимательны: повторяющиеся тривиальные facts могут завысить score, а по отдельности истинные statements могут сформировать вводящий в заблуждение answer. MontageLie (EMNLP 2025) проверяет эту слабость через deceptive relationships и ordering между true statements. VeriScore работает с claims, для которых важны необходимые modifiers; фильтр Core помогает предотвращать fact-padding.

Answer correctness, completeness, refusal

  • Answer correctness относительно reference: exact match или token-F1 могут подходить для коротких answers. Для длинных answers проверяйте factual relations, entities, quantities, negation и required information относительно reviewed references. BERTScore и embedding cosine измеряют similarity; неправильное число или negation могут сохранить высокий score. Ragas AnswerCorrectness сочетает factual comparison с similarity, а не приравнивает одно к другому.
  • Completeness через nuggets: nugget — relevant information unit, где vital nuggets отличаются от optional useful. В вопросе о founding date год может быть обязательным, а имя founder — не обязательно. AutoNuggetizer строит и уточняет nuggets из judged document pools, а затем проверяет их наличие в generated answers. В initial TREC 2024 report были охвачены 21 topic и 45 runs. TREC 2025 overview, опубликованный в марте 2026 года, расширяет protocol на narrative queries и оценивает retrieval relevance, answer completeness и attribution. Это публичные evaluation protocols, а не свидетельство того, что каждому production RAG нужна такая же nugget rubric.
  • Refusal behavior: разметьте, позволяет ли supplied evidence дать answer, затем измеряйте correct refusals среди всех refusals и долю refusals среди случаев, где система должна abstain. NoMIRACL (Findings of EMNLP 2024) проверяет robustness относительно relevant и non-relevant supplied passages; это не доказывает, что во всём corpus нет ответа. В собственной suite разделяйте retrieval misses и действительно out-of-scope queries.

Post-generation verification

Самые дешёвые reliability gains часто дают deterministic post-checks, а не более крупные models.

  • Unseen-entity flag: записывайте named-entity strings в answer, отсутствующие в normalized context string (например, spaCy’s ents плюс exact matching). Это дешёвый domain-specific flag для unseen entity strings, а не grounding check: он не устанавливает identity, relation, negation, time или provenance. Измерьте его precision и recall на local labels до того, как использовать flag для approval release, и сохраняйте claim-level entailment или human review для verification.

  • Self-consistency (Wang et al., ICLR 2023): сэмплируйте несколько generations при temperature > 0; публикуйте agreement rate (например, долю generations, совпадающих с modal answer, или pairwise BERTScore); число samples выбирайте по stability–cost curve, а low-agreement answers отправляйте на human review.

  • Confidence calibration: собирайте verbalized confidence («How confident are you, 0–1?») и сравнивайте с фактической correctness на eval set. Стройте calibration curve и сообщайте Expected Calibration Error: ECE=∑m=1M∣Bm∣n∣acc(Bm)−conf(Bm)∣\text{ECE} = \sum_{m=1}^{M} \frac{|B_m|}{n} |\text{acc}(B_m) - \text{conf}(B_m)|ECE=∑m=1M​n∣Bm​∣​∣acc(Bm​)−conf(Bm​)∣, где BmB_mBm​ — confidence bins. Реализации: netcal, torchmetrics.CalibrationError. Model, сообщающая confidence 0.9, должна быть correct примерно в 90% сопоставимых случаев; измеряйте gap, а не предполагайте calibration.

Часть 7: Evaluation ontology-grounded RAG

Стандартные метрики выше покрывают open-corpus RAG. Если ваш RAG выполняет retrieval относительно structured ontology, taxonomy или knowledge graph, эти метрики необходимы, но недостаточны. Примеры: products в catalog, conditions в SNOMED, components в BOM и security techniques в MITRE ATT&CK. Нужно также измерять ontology layer.

Точность entity linking

Первая задача — сопоставить mention из query с ontology entity («Aspirin» → wikidata:Q18216, «the 737» → aircraft:Boeing_737).

  • Mention-level precision/recall/F1: стандартная оценка относительно gold mention spans (вычисляется с помощью seqeval или span-set comparator).
  • Disambiguation accuracy: какая доля correctly-detected mentions сопоставлена правильному entity ID? Публичные references включают ReFinED, REL и GENRE; benchmarks вроде AIDA-CoNLL и BELB показывают, что результаты зависят от системы и домена.
  • NIL handling: precision/recall для случаев «entity отсутствует в ontology». Отдельно измеряйте over-linking к близким, но неправильным entities и корректный abstention.

Hierarchy-aware evaluation

Plain accuracy считает «предсказан Sedan, а truth — Hatchback» такой же ошибкой, как «предсказан Sedan, а truth — Submarine». Эти ошибки неравноценны.

  • Hierarchical precision/recall/F1 (Kosmopoulos et al., 2015): учитывайте shared ancestors в ontology DAG. Пусть P^q\hat{P}_qP^q​ — predicted node плюс все его ancestors, а TqT_qTq​ — true node плюс все его ancestors:

    hP=∑q∣P^q∩Tq∣∑q∣P^q∣,hR=∑q∣P^q∩Tq∣∑q∣Tq∣,hF1=2⋅hP⋅hRhP+hRhP = \frac{\sum_q |\hat{P}_q \cap T_q|}{\sum_q |\hat{P}_q|}, \quad hR = \frac{\sum_q |\hat{P}_q \cap T_q|}{\sum_q |T_q|}, \quad hF1 = \frac{2 \cdot hP \cdot hR}{hP + hR}hP=∑q​∣P^q​∣∑q​∣P^q​∩Tq​∣​,hR=∑q​∣Tq​∣∑q​∣P^q​∩Tq​∣​,hF1=hP+hR2⋅hP⋅hR​

    Реализуйте через networkx на ontology graph: дополните каждую prediction и label её ancestors, затем вычислите set overlaps выше.

  • Wu-Palmer similarity между predicted и gold entity в taxonomy (Wu & Palmer, 1994):

    WuP(c1,c2)=2⋅depth(LCA(c1,c2))depth(c1)+depth(c2)\text{WuP}(c_1, c_2) = \frac{2 \cdot \text{depth}(\text{LCA}(c_1, c_2))}{\text{depth}(c_1) + \text{depth}(c_2)}WuP(c1​,c2​)=depth(c1​)+depth(c2​)2⋅depth(LCA(c1​,c2​))​

    где LCA — lowest common ancestor в taxonomy. Для WordNet доступна из коробки в NLTK (from nltk.corpus import wordnet as wn; wn.synset("car.n.01").wup_similarity(wn.synset("truck.n.01"))); для custom taxonomies вычисляйте LCA с помощью networkx.

  • Sibling/parent confusion rate: отдельно отслеживайте confusions с siblings, parents и children — count_sibling / total_errors, count_parent / total_errors, count_descendant / total_errors. Используйте reviewed examples, чтобы проверить, вызваны ли sibling errors неоднозначными mentions, а parent errors — over-generalization.

Filter false-exclusion rate: повтор, но теперь это критично

В ontology-grounded systems hard filters часто исходят из самой ontology («retrieval только docs с tag category X»). Метрика exclusion rate, определённая в Part 5, становится основным correctness signal. Ошибка category prediction может обнулить recall; exclusion rate атрибутирует эту потерю filter.

Conformance constrained generation

Когда output должен соответствовать ontology (каждое entity name в answer должно быть valid ontology member; каждый predicate — из closed vocabulary), измеряйте:

  • Schema validity rate: доля outputs, которые парсятся и проходят validation относительно ontology schema. Валидируйте с помощью jsonschema или pydantic. JSONSchemaBench — public benchmark для general structured output; для ontology-specific schemas создайте собственный validator.
  • Vocabulary conformance: доля named entities в output, являющихся valid ontology IDs — обычная set-membership check относительно closed vocabulary.
  • Semantic conformance: syntactically valid output всё ещё может выбрать неправильную, но valid entity. Сопоставляйте conformance с downstream answer correctness.

Constrained decoding frameworks (Outlines, XGrammar, Guidance, OpenAI Structured Outputs) предназначены для enforcement schema validity. JSONSchemaBench сравнивает efficiency, coverage и quality разных implementations. Перезапустите его cases, соответствующие вашим schemas и serving backend, поскольку coverage и latency зависят от обоих факторов.

Auditability

Для ontology-grounded systems, чьи answers проходят review:

  • Citation completeness: доля factual claims, имеющих хотя бы одну verifiable citation.
  • Provenance depth: доля citations, разрешающихся до source document со stable ID, а не только до chunk hash.
  • Reproducibility rate: повторный запуск того же query на фиксированном snapshot возвращает тот же answer. Зафиксируйте model version, runtime, decoding configuration и seed, затем задайте required repeat rate согласно auditability needs workflow. Одного temperature zero недостаточно для determinism. Miss может исходить из generation, serving runtime или любого upstream stage.

Часть 8: System-level evaluation

Holistic answer quality

  • LLM-as-judge (Zheng et al., NeurIPS 2023): масштабируемый model-based evaluation approach. G-Eval (Liu et al., EMNLP 2023) генерирует evaluation steps из task и criteria, а затем взвешивает rating levels по token probabilities: score=∑ip(si) si\text{score} = \sum_i p(s_i)\,s_iscore=∑i​p(si​)si​. Это probabilities, а не log probabilities. Agreement зависит от judge, task, prompt и calibration set.
  • Pairwise preference: предъявляйте judge answer A и answer B и записывайте preference. Это заменяет absolute rating сравнительным решением, но всё равно требует calibration относительно human preferences. MT-Bench сообщал об agreement GPT-4 judge выше 80% с human preferences и human–human agreement в условиях своего benchmark; не переносите эту rate в другой domain без calibration.

LLM-as-judge имеет реальные biases:

  • Position bias: измеряйте order sensitivity на human-labeled cases для выбранных judge и task. Randomization или aggregation после swap order могут помочь некоторым model/task pairs, но сохраняйте этот приём только если он улучшает local human agreement; controlled study 2026 года обнаружил, что position swapping вредил на его adversarial cases.
  • Verbosity bias: judges могут путать length с quality. Цитируемое controlled study 2026 года, version 2 выявило неоднородное поведение на expansion pairs: три judges предпочитали более длинные answers, Claude — concise answers, а GPT-4o был примерно neutral. Все пять хорошо работали на truncation controls. Эти результаты привязаны к benchmark, поэтому явно укажите judge, как трактовать completeness и filler, и публикуйте length-controlled performance по собственной rubric.
  • Self-preference risk: Zheng et al. наблюдали на 10% более высокий GPT-4 self-win rate и на 25% более высокий Claude-v1 self-win rate в своих data, но заключили, что ограниченный объём данных и небольшие различия не позволяют установить self-enhancement bias. Сравнивайте same- и cross-family judges с local human labels; выбирайте лучше calibrated judge, не считая заранее безопасной ни одну из конфигураций.

Практический рецепт: выбирайте judge на human-labeled calibration data, скрывайте model identities, измеряйте order sensitivity и указывайте length policy в rubric. Повторяйте cases только тогда, когда дополнительные samples существенно уменьшают uncertainty. Для high-stakes evaluations сравнивайте same- и cross-family judges и анализируйте расхождения относительно human labels.

Schema-Guided Reasoning для judges

Free-form output — один из источников variation в judge runs. Два запуска для одного answer могут по-разному организовать rubric и выдать разные scores. Schema-Guided Reasoning (SGR) делает rubric явной: определите evaluation stages как Pydantic schema, затем используйте constrained output через Outlines, XGrammar, vLLM structured outputs или OpenAI response_format, чтобы enforce поддерживаемые schema constraints. Порядок полей может помочь reviewer изучать record, но не доказывает, что model выполняла reasoning stages именно в этом порядке.

Для RAG eval schema раскладывает judgment на явные, audit-friendly fields вместо того, чтобы позволять model сразу переходить к числу:

from pydantic import BaseModel, Field, ValidationError, model_validator
from typing import Literal

class FaithfulnessJudgment(BaseModel):
    extracted_claims: list[str] = Field(
        description="Atomic factual claims in the answer, one per item."
    )
    supported_claims: list[str] = Field(
        description="Subset of extracted_claims that are entailed by the context."
    )
    unsupported_claims: list[str] = Field(
        description="Subset that is NOT entailed by the context."
    )
    outcome: Literal["scored", "no_claims"]
    failure_mode: Literal[
        "none", "fabrication", "overgeneralization", "wrong_entity", "stale_fact"
    ]
    rationale: str

    @model_validator(mode="after")
    def require_claim_partition(self):
        for claims in (self.extracted_claims, self.supported_claims, self.unsupported_claims):
            if any(not claim.strip() for claim in claims):
                raise ValueError("claims must contain non-whitespace text")
        extracted = set(self.extracted_claims)
        supported = set(self.supported_claims)
        unsupported = set(self.unsupported_claims)
        if not extracted:
            if supported or unsupported or self.outcome != "no_claims":
                raise ValueError("an empty extraction must be a no_claims outcome")
            return self
        if (
            len(extracted) != len(self.extracted_claims)
            or len(supported) != len(self.supported_claims)
            or len(unsupported) != len(self.unsupported_claims)
            or supported & unsupported
            or supported | unsupported != extracted
            or self.outcome != "scored"
        ):
            raise ValueError("verdict lists must be a complete, disjoint claim partition")
        return self

    @property
    def score(self) -> float | None:
        if not self.extracted_claims:
            return None
        return len(self.supported_claims) / len(self.extracted_claims)

valid = FaithfulnessJudgment(
    extracted_claims=["Mars has two moons", "Mars has a thick atmosphere"],
    supported_claims=["Mars has two moons"],
    unsupported_claims=["Mars has a thick atmosphere"],
    outcome="scored",
    failure_mode="fabrication",
    rationale="The atmosphere claim lacks support.",
)
assert valid.score == 0.5
empty = FaithfulnessJudgment(
    extracted_claims=[],
    supported_claims=[],
    unsupported_claims=[],
    outcome="no_claims",
    failure_mode="none",
    rationale="Score refusal correctness separately.",
)
assert empty.score is None
try:
    FaithfulnessJudgment(
        extracted_claims=["Mars has two moons"],
        supported_claims=["Mars has two moons"],
        unsupported_claims=["Mars has two moons"],
        outcome="scored",
        failure_mode="none",
        rationale="Contradictory verdict.",
    )
except ValidationError:
    pass
else:
    raise AssertionError("overlapping verdicts must fail validation")

for blank in ("", " ", "\t\n"):
    for verdict_field in ("supported_claims", "unsupported_claims"):
        fields = {"extracted_claims": [blank], "supported_claims": [], "unsupported_claims": []}
        fields[verdict_field] = [blank]
        try:
            FaithfulnessJudgment(
                **fields, outcome="scored", failure_mode="none", rationale="Blank claim."
            )
        except ValidationError:
            pass
        else:
            raise AssertionError("blank claims must fail validation")

Этот illustrative contract вычисляет score только после того, как verdict lists образуют полное и непересекающееся partition extracted claims. No-claim outcome не имеет faithfulness score и должен исключаться из faithfulness aggregate; сообщайте его count и отдельно оценивайте refusal correctness, чтобы abstentions не могли незаметно улучшить average. Сохраняйте эти semantic checks в production; constrained output гарантирует shape, но не unbiased verdict. Pydantic model также делает изменение rubric видимым как code diff, а human calibration проверяет сам judgment.

Подход работает для любой rubric-based judge, не только для faithfulness. Pairwise preference, citation support и refusal correctness также выигрывают от такой обработки.

Упрощённый rubric judge, а также pairwise, position-bias и cross-family examples находятся в notebook 07; module: evaluation/llm_judge.py. В проверенной revision функция g_eval запрашивает один integer rating; она не генерирует evaluation steps и не вычисляет probability-weighted scores, поэтому не воспроизводит G-Eval protocol. Benchmark sweep (make benchmark в repo) подключает три models (gpt-5-mini, claude-haiku-4-5, gemini-2.5-flash) к rotating-judge pairwise A/B: каждый judge оценивает answers двух других model families. Такая topology поддерживает cross-family pairwise results; для измерения self-preference нужны также same-family и cross-family conditions, сравнённые с local human labels.

Latency и cost

  • p50, p95, p99 для каждого pipeline stage. SLO percentile и alert threshold выбирайте исходя из user journey, traffic volume и error budget.
  • Time-to-first-token против total generation time. Для streaming UX пользователям важен TTFT.
  • Stage breakdown: retrieval, реранкинг, generation, post-processing. Используйте trace, чтобы найти tail, а не предполагайте, какой stage его вызвал; при сравнении runs фиксируйте reranker device и batch size.
  • Total $/query = embedding + retrieval + rerank + generation + storage amortized. Отслеживайте p50 и p99; именно long tail съедает budget.
  • Cache hit rates на уровнях embedding cache, retrieval cache и KV-cache. Отдельные targets задавайте по observed repetition, invalidation policy и avoided cost каждого слоя.

Per-stage p50/p95/p99 со stage breakdown встроены в notebook 08 и runner в evaluation/latency.py; benchmark report объединяет latency с faithfulness в одной matrix, которую можно повторно запустить с помощью make benchmark.

A/B testing

  • Unit of randomization: сначала определите outcome, который хотите оценить. Затем выясните, могут ли предыдущие answers изменить последующее поведение и может ли assigned version одного пользователя повлиять на experience другого. Используйте per-user или per-session assignment, если repeated exposure может менять поведение или создавать inconsistent UX. Per-query assignment оправдан только при пренебрежимо малых эффектах и анализе, моделирующем repeated observations.
  • Primary, guardrails, exploratory metrics: preregister их. Primary measure выбирайте по product outcome; satisfaction proxies включают thumbs, regenerations и dwell. Latency и cost считайте guardrails, если они ограничивают experience.
  • Sample size: до запуска проведите power analysis на основе minimum effect worth detecting, baseline variance, assignment unit и stopping rule.

Часть 9: Построение test set

Byte говорит

Стройте golden set из реальных query types, включая сложные. Recall@10 легко растёт, если оценивать retriever только на простом трафике.

Качество метрики не выше качества test set, на котором она запускается. Если golden set покрывает три intents, а production traffic включает двенадцать, Recall@10 измеряет только эти три intents. Ещё хуже, если test set переобучен на простые вопросы («Какова политика возврата компании?»): он может одобрить систему, которая проваливается на сложных вопросах («Каковы условия возврата при частичной отмене по EU Digital Services Act 2023, если billing в EUR, а источник — Ireland?»). Aggregate score растёт, пока система по-прежнему не справляется с важной частью production traffic.

Неполные relevance labels могут искажать recall в обе стороны. Если истинный relevant set — {a, b}, а labels содержат только {a}, retrieval {a} получает 1.0 вместо 0.5; retrieval {b} получает zero вместо 0.5. Версионируйте judgments и проверяйте newly retrieved, unjudged evidence до интерпретации delta.

Сначала стройте test set вокруг реального query distribution и difficulty. Затем выбирайте metrics, реагирующие на target failure modes, и настраивайте систему по ним.

Synthetic query generation

Используйте LLM для генерации вопросов из корпуса:

  • Per-chunk: «Generate 3 questions a user might ask that this chunk answers».
  • Multi-hop: выберите два chunks и сгенерируйте вопрос, требующий обоих.
  • Adversarial: генерируйте queries с distractor entities, near-duplicate phrasing и ambiguous mentions.

Ragas test generation использует graph-based scenarios с single-hop и multi-hop queries и конкретными или абстрактными information needs. DataMorgana генерирует configurable synthetic benchmarks по категориям users и questions. Synthetic data полезны для cold starts и coverage testing. Они не могут заменить real user queries.

Построение golden dataset

Human-curated data служит anchor для golden set.

  1. Сэмплируйте real user queries (или simulated queries до launch), стратифицированные по intent.
  2. Попросите SMEs ответить на каждый вопрос и указать documents, содержащие answer.
  3. Размер set определяйте по coverage matrix и confidence interval, нужному для release decisions; coverage важнее заимствованного query count.
  4. Re-curate set, когда это оправдано release cadence, drift signals, domain risk и annotation capacity.

Разделяйте development queries, judge calibration, held-out release measurement и monitoring samples. Перед split группируйте shared source documents и sessions. После того как query или label использован для tuning, это development data. Для валидации выбранной configuration и judge оставляйте untouched cases.

Записывайте версии corpus, query, relevance-label и policy, unit of k, supplied-context budget, scorer и judge revisions, а также aggregation rules. Сравнивайте paired per-query deltas на одной population с uncertainty и slice counts. Включайте каждый expected query: timeout, missing result или unscorable judge response должны оставаться видимыми в completion/error accounting. Не позволяйте release score улучшаться за счёт незаметного удаления failures. ARES предлагает research approach с automated judges, human validation и prediction-powered inference для system estimates при дефиците annotation; reviewed local suite может начать с более простой схемы.

Adversarial test sets

  • Counterfactuals: заменяйте ключевые entities в query. Извлекает ли система правильные chunks для изменённого query?
  • Distractors: queries, в которых corpus содержит правдоподобный, но неправильный answer, который не следует извлекать. Именно это stress-тестирует RGB (Chen et al., AAAI 2024): noise robustness, negative rejection, information integration и counterfactual robustness.
  • Negation и quantifiers: queries с «not», «except» и «only». Dense retrievers часто испытывают с ними трудности.
  • Out-of-scope: queries без answer в corpus. Система должна сказать «I don’t know», а не hallucinate. NoMIRACL предоставляет passage-level relevance/answerability tests; добавьте отдельные corpus-level out-of-scope labels. Явно оценивайте abstention на production query types.

Coverage и continuous evaluation

  • Стройте coverage matrix: query intent × document type × ontology branch. Один query на cell — это starting coverage inventory, но недостаточная statistical power для release decision. Empty cells показывают пробелы coverage; размер populated slices задавайте по допустимой uncertainty.
  • Запускайте bounded fast regression subset на каждом PR, а full suite — по более медленному расписанию.
  • Планируйте full golden-set eval согласно release cadence и evaluation cost; запускайте его на release candidates.
  • Планируйте drift evaluation по traffic volume, ожидаемым изменениям и risk. Используйте rolling production sample и stratify по feedback, не меняя target distribution незаметно.

Часть 10: Production monitoring

Eval suite, которую вы отгружаете, описывает систему на launch. После этого production traffic меняется.

Implicit и explicit feedback

  • Считайте implicit events candidate signals, а не positive или negative quality KPIs, пока они не будут сопоставлены с blinded review или explicit feedback на local sample.
  • Click-through / open rate для cited sources (если UI их показывает).
  • Dwell time на answer.
  • Regeneration rate: доля answers, которые пользователь переспрашивает или просит переделать. Считайте её одним из dissatisfaction signals и калибруйте относительно reviewed conversations.
  • Copy / share / export rates: candidate implicit signals, которые могут означать usefulness, verification, handoff или dissatisfaction. До назначения направления измерьте association и confidence interval.
  • Follow-up patterns: используйте «Are you sure?» или «But what about X?» как review strata, затем разметьте их association с distrust или unresolved need.
  • Thumbs up/down с optional reason categories (wrong, incomplete, off-topic, harmful, slow). Inline edits могут сохранять больше diagnostic context; оцените эту ценность на reviewed samples.

Обнаружение drift

  • Query drift: сравнивайте query embeddings с reference window через MMD или validated reference-versus-current classifier. KL требует defined probability estimator, например выбранных histograms; raw embedding coordinates не являются probabilities. Калибруйте alarms на known shifts, затем изучайте затронутые slices.
  • Embedding drift: зафиксируйте representation и probe set, затем измеряйте neighbor stability и retrieval quality. Разные model versions не обязаны иметь одинаковые dimensions или coordinate basis, поэтому cross-version cosine может быть бессмысленным. Мигрируйте query и document encoders вместе, оценивайте новый index и сохраняйте versioned snapshots для rollback.
  • Performance drift: отслеживайте production-equivalent metrics (regeneration rate по intent) во времени. Резкие и постепенные shifts предполагают разные hypotheses, но их форма не устанавливает причину; проверяйте data, traffic, provider, policy и deployment changes.

Shadow evaluation и human-in-the-loop

Запускайте candidate system параллельно с production, сравнивайте outputs offline и не показывайте их users. Это помогает выявлять regressions до launch. Shadow inference всё равно потребляет capacity и может вызывать tools: изолируйте resources, подавляйте writes и убедитесь, что comparison не ухудшает production latency.

Для human-in-the-loop (HITL) review:

  • Отправляйте low-confidence outputs в review queue.
  • Добавляйте random sample production traffic для blind review; rate задавайте по traffic volume, risk и reviewer capacity.
  • Oversample thumbs-down outputs для review вместе с random sample.
  • Используйте reviewed outputs для расширения golden set.

Минимальный набор guardrails

Alert priorities и thresholds выбирайте по user harm, SLOs и validated detector performance. Candidate signals:

  1. Faithfulness/HHEM score ниже threshold на rolling production sample.
  2. p95 latency выше SLO.
  3. Filter false-exclusion rate выше threshold (sample-based).
  4. Regeneration rate вне locally calibrated control band с учётом window size, traffic, seasonality и false-alert budget.
  5. Cost/query выше budget.

Используйте release timing для формирования diagnosis, затем проверяйте её по traces и affected slices. Deployment может совпасть с traffic drift, а provider или data change — произойти без application release. Alerts — это evidence для investigation; lead time относительно user reports нужно измерять.

Caveats

  • Targets локальны, а не универсальны. Любое число, названное в guide illustrative, — пример configuration или worked result, а не release threshold. Калибруйте thresholds под domain, stakes, evaluation-set uncertainty и user expectations.
  • Пространство фреймворков быстро меняется. Версии HHEM, названия RAGAS metrics, model cards и порядок leaderboard могут измениться после публикации. Повторно проверяйте linked source и проводите re-benchmark до фиксации решения.
  • Agreement numbers для LLM-as-judge требуют оговорок. Значение 80% для GPT-4-vs-human получено в условиях MT-Bench / Chatbot Arena. Оно не устанавливает agreement для niche domain или adversarial slice. Используйте judges как force multiplier, а не замену spot-checking.
  • Vendor benchmark uplifts часто нельзя независимо воспроизвести. Повторяйте benchmark на собственных data, прежде чем доверять числу, особенно для новых rerankers и OCR systems.
  • Ни одна метрика не заменяет просмотр outputs. Планируйте blind review случайной production sample с учётом traffic, risk и reviewer capacity. Метрики масштабируют эту практику, но не заменяют её.
