Файлы запуска Zsh: .zprofile и .zshrc в macOS и Linux

Viacheslav Dubrov

2025-05-07 · Обновлено 2026-07-15 · 4 мин · Инструменты разработчика

Автоматический перевод Эта статья была автоматически переведена с оригинальной английской версии.

Если терминал работает медленно или переменная окружения появляется в одном терминале, но отсутствует в другом, причина часто связана с режимом запуска Zsh. Два файла, к которым чаще всего обращаются, — ~/.zprofile и ~/.zshrc, но по одному имени файла нельзя понять, подходит ли он для конкретной строки.

Zsh выбирает файлы запуска по двум независимым свойствам: является ли оболочка login shell и является ли она interactive. Терминальные приложения в macOS и Linux могут выбирать разные комбинации, поэтому проверяйте режим запущенной оболочки, а не предполагайте, что его определяет операционная система.

Коротко. Помещайте инициализацию login-сессии в .zprofile, а интерактивное поведение — в .zshrc. Файл .zshenv должен оставаться тихим и минимальным. Не переносите интерактивные хуки менеджеров версий в .zprofile и не подключайте весь профиль из .zshrc; изучите сгенерированный инструментом код и следуйте его актуальным инструкциям для Zsh.

Zsh оценивает два независимых флага

Оболочка может быть:

  • login и interactive — так обычно Apple Terminal запускает login shell учетной записи по умолчанию
  • не login и interactive — так запускаются вложенный zsh и многие конфигурации терминалов в Linux
  • login и не interactive — так запускается zsh -lc 'command'
  • не login и не interactive — так запускается zsh -c 'command'

Терминальные приложения, IDE, удаленные сессии, мультиплексоры и явные флаги оболочки могут выбирать разные режимы, поэтому по одной операционной системе нельзя определить результат.

Вместо предположений запросите режим у запущенной оболочки:

print -r -- "interactive=$options[interactive] login=$options[login]"

Фактический порядок запуска

Zsh читает глобальные файлы, а затем соответствующий пользовательский файл. При стандартных опциях RCS порядок пользовательских файлов такой:

  1. $ZDOTDIR/.zshenv — при каждом запуске Zsh
  2. $ZDOTDIR/.zprofile — если оболочка является login shell
  3. $ZDOTDIR/.zshrc — если оболочка является interactive
  4. $ZDOTDIR/.zlogin — если оболочка является login shell
  5. $ZDOTDIR/.zlogout — при нормальном завершении login shell

Если ZDOTDIR не задана, Zsh использует $HOME. Расположение системных файлов зависит от установки; часто используются следующие пути по умолчанию: /etc/zshenv, /etc/zprofile, /etc/zshrc, /etc/zlogin и /etc/zlogout.

.zprofile выполняется один раз для каждого процесса login shell, а не один раз при входе пользователя в систему. Если каждая новая вкладка терминала запускает login shell, каждая вкладка прочитает этот файл.

Пусть .zshenv остается скучным

Каждый неинтерактивный zsh -c читает .zshenv. Команда echo, вызов пакетного менеджера или ресурсоемкий subprocess в этом файле могут испортить вывод команд и замедлить скрипты. Большинству пользователей в этом файле почти ничего не нужно.

Экспортируемая переменная в .zprofile наследуется дочерними процессами этого login shell. Она не внедряется автоматически в независимые GUI-приложения, сервисы или оболочки, родительский процесс которых не читал этот файл.

Используйте .zprofile для настройки только login shell

Небольшой профиль может задать экспортируемые значения по умолчанию и идемпотентный path:

# ~/.zprofile
export EDITOR=nvim
export VISUAL=nvim

# Zsh ties the path array to the PATH scalar.
typeset -U path PATH
path=("$HOME/.local/bin" $path)
export PATH

typeset -U удаляет дубликаты элементов массива. Это делает повторное подключение файла безопаснее, хотя в файлах запуска все равно следует избегать лишней работы.

Используйте .zshrc для интерактивного состояния

# ~/.zshrc
setopt auto_cd hist_ignore_all_dups share_history

autoload -Uz compinit
compinit

alias ll='ls -lah'
bindkey -e

Алиасы, completion widgets, key maps, промпты и хуки смены каталога должны находиться в интерактивной оболочке, которая ими пользуется.

Менеджеры версий выходят за границы простой схемы файлов

Byte says

Я перенёс pyenv в .zprofile, чтобы новые вкладки открывались быстрее. Новые вкладки действительно стали открываться быстрее. Shell внутри редактора потерял все функции и автодополнение pyenv, потому что никогда не читает .zprofile.

Совет «поместите менеджеры версий в .zprofile, потому что они медленные» ненадежен. Менеджер версий может генерировать несколько видов кода:

  • статический path или переменную root
  • path к command shim, необходимый дочерним процессам
  • определения completion
  • shell functions, изменяющие текущую оболочку
  • хуки смены каталога для автоматического переключения версий

Интерактивные части должны присутствовать в каждой интерактивной оболочке, включая вложенный zsh, запущенный из редактора. Поэтому актуальная документация fnm помещает этот хук в .zshrc:

eval "$(fnm env --use-on-cd --shell zsh)"

Актуальная документация pyenv также помещает полную интерактивную инициализацию в .zshrc:

export PYENV_ROOT="$HOME/.pyenv"
[[ -d $PYENV_ROOT/bin ]] && path=("$PYENV_ROOT/bin" $path)
eval "$(pyenv init - zsh)"

В документации pyenv описан более узкий режим pyenv init --path для настройки shim-path, но полная команда pyenv init также устанавливает completion и shell functions. Перед разделением кода изучите актуальную документацию инструмента и сгенерированный им вывод.

Если запуск медленный, сначала измерьте его, а уже потом переносите код в режим, где он перестанет работать.

Не подключайте весь профиль из .zshrc

Распространенный кроссплатформенный workaround выглядит так:

# Avoid this blanket coupling.
source ~/.zprofile

В результате действия, предназначенные только для login shell, выполняются для каждой интерактивной оболочки. Это может повторно запускать агента, обращаться к keychain, выводить данные или изменять path.

Если и login-, и non-login interactive shell должны получать небольшой набор статических экспортируемых переменных, вынесите идемпотентный фрагмент в отдельный файл и подключайте его явно:

# ~/.config/zsh/environment.zsh
typeset -U path PATH
path=("$HOME/.local/bin" $path)
export PATH EDITOR=nvim VISUAL=nvim
# ~/.zprofile
source "$HOME/.config/zsh/environment.zsh"
# ~/.zshrc
if [[ ! -o login ]]; then
  source "$HOME/.config/zsh/environment.zsh"
fi

# Interactive-only configuration follows.

Такой шаблон отделяет общие данные от побочных эффектов login shell. Другой корректный вариант — единообразно настроить терминал или менеджер сессий вместо поддержки обоих режимов.

Диагностируйте именно медленную оболочку или оболочку с отсутствующим состоянием

Воспроизведите каждый режим напрямую:

zsh -lic 'print "login interactive"'
zsh -ic  'print "non-login interactive"'
zsh -lc  'print "login non-interactive"'
zsh -c   'print "non-login non-interactive"'

Измерьте режим, который фактически запускают пользователи:

time zsh -lic exit
time zsh -ic exit

Если источник проблемы неясен, включите трейсинг выполнения файлов и строк:

PS4='%N:%i> ' zsh -xlic exit

Запускайте трейс в отдельной тестовой учетной записи или проверьте его перед передачей другим: команды запуска могут раскрывать токены и другие чувствительные значения.

Если исполняемый файл не найден, проверьте и режим, и path:

print -r -- "interactive=$options[interactive] login=$options[login]"
print -l -- $path
whence -va python node uv

Заключение

Полезное различие состоит не в «окружении и алиасах». Важно отделять состояние, нужное только login shell, от интерактивного состояния, а также учитывать небольшой объем настроек, который действительно должен влиять на каждый процесс Zsh.

Проверьте флаги оболочки, не допускайте вывода из файлов запуска и размещайте каждый сгенерированный хук там, где доступны все необходимые ему возможности. Так конфигурация будет переносимой между терминальными приложениями, без предположения, что в macOS и Linux существует только один фиксированный режим запуска.
