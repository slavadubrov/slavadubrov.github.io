Руководство по pyproject.toml: упаковка, зависимости и инструменты

Viacheslav Dubrov

2025-05-08 · Обновлено 2026-07-15 · 5 мин · Инструменты разработчика

Автоматический перевод Эта статья была автоматически переведена с оригинальной английской версии.

В старых Python-проектах конфигурация часто была распределена между setup.py, setup.cfg, файлами requirements, MANIFEST.in и отдельными файлами для инструментов разработки. pyproject.toml объединяет эти задачи в одном месте, хотя не заменяет все файлы проекта и не делает каждый раздел частью единого стандарта.

В этом руководстве файл рассматривается начиная с конфигурации сборки и заканчивая метаданными проекта и настройками инструментов. За разделами стоят четыре разных владельца: то, что собирает проект; то, что проект публикует; то, что локально нужно контрибьюторам; и то, что настраивают отдельные инструменты.

Кратко. Используйте [build-system] для бэкенда, который собирает дистрибутив, [project] — для публикуемых метаданных и runtime-зависимостей, [dependency-groups] — для непубликуемых окружений разработки, а [tool.*] — только если это предусмотрено документацией конкретного инструмента. Декларация зависимостей — не lockfile.

Один файл, четыре владельца

Основную структуру определяют три стандарта упаковки:

  • PEP 518 описывает требования build-системы.
  • PEP 621 описывает метаданные проекта.
  • PEP 735 описывает непубликуемые группы зависимостей.

Авторы инструментов также могут занимать пространство имён внутри [tool]. Стандарт не определяет, что должно находиться в этом разделе: каждый инструмент задаёт собственные ключи и поведение.

Вот небольшой упаковываемый пакет-библиотека:

[build-system]
requires = ["hatchling>=1.26"]
build-backend = "hatchling.build"

[project]
name = "weather-client"
version = "0.1.0"
description = "A small weather API client"
readme = "README.md"
requires-python = ">=3.11"
dependencies = [
  "httpx>=0.27",
]

[project.optional-dependencies]
cli = ["rich>=13"]

[project.scripts]
weather = "weather_client.cli:main"

[dependency-groups]
test = ["pytest>=8", "pytest-cov>=5"]
lint = ["ruff>=0.12"]

[tool.pytest.ini_options]
testpaths = ["tests"]

[tool.ruff]
line-length = 100
target-version = "py311"

Каждый список зависимостей отвечает на свой вопрос.

[build-system]: как исходный код превращается в дистрибутив

Build frontend, например python -m build, pip или uv, вызывает build backend. Бэкенд определяет, как исходное дерево превращается в sdist или wheel и какие файлы попадают в эти артефакты.

[build-system]
requires = ["hatchling>=1.26"]
build-backend = "hatchling.build"

requires содержит зависимости, необходимые для запуска бэкенда в его изолированном build-окружении. Это не список runtime-зависимостей вашего пакета.

Объявляйте build-систему, если проект создаёт дистрибутив или требует установки собственного кода как пакета. Проект без пакета всё равно может использовать pyproject.toml; PEP 735 даже допускает файл, содержащий только группы зависимостей. Менеджеры окружений по-разному работают с проектами без build-системы, поэтому принимайте это решение осознанно.

Выбирайте бэкенд с учётом требований к сборке:

  • layout чистого Python и потребности в выборе файлов
  • скомпилированные расширения или внешние build-системы
  • динамическая версия или требования к генерируемым файлам
  • поведение editable install
  • зрелость бэкенда в release pipeline

Скопируйте актуальную рекомендуемую таблицу бэкенда из его документации. Не добавляйте wheel в build-зависимости по привычке: бэкенд сам объявляет, что ему нужно.

[project]: какие метаданные получают потребители

Таблица [project] описывает дистрибутив: его имя, версию, совместимость с Python, runtime-зависимости, entry points и другие метаданные для индексов пакетов.

[project]
name = "weather-client"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = ["httpx>=0.27"]

Спецификаторы зависимостей задают ограничения для резолвера, а не снапшот конкретного окружения. Они становятся частью метаданных wheel и sdist, поэтому downstream-инсталляторы могут объединять их с требованиями других пакетов.

Extras — это публичный интерфейс установки

[project.optional-dependencies] определяет extras, которые могут запросить потребители:

[project.optional-dependencies]
cli = ["rich>=13"]
postgres = ["psycopg[binary]>=3.2"]

Потребитель может установить weather-client[cli]. Поскольку имена extras и требования к ним публикуются, рассматривайте их как продуктовые возможности. Не используйте extra с именем dev только для хранения всех инструментов контрибьютора.

Entry points связывают установленные команды с Python

[project.scripts]
weather = "weather_client.cli:main"

После установки дистрибутива окружение предоставляет команду weather, которая импортирует и вызывает weather_client.cli:main. Проверяйте команду на собранном wheel, а не только из корня репозитория: именно wheel получают пользователи.

[dependency-groups]: локальные непубликуемые окружения

Группы зависимостей PEP 735 описывают окружения для разработки или другие непакетные окружения, не публикуя их как метаданные пакета.

[dependency-groups]
test = ["pytest>=8", "pytest-cov>=5"]
lint = ["ruff>=0.12"]
dev = [
  { include-group = "test" },
  { include-group = "lint" },
]

Это правильная граница для тестов, линтеров, сборщиков документации и других инструментов контрибьютора. Группы также удобны для приложений или ноутбуков, которые не создают дистрибутив.

Группы зависимостей — стандартизированные данные, но интерфейсы инсталляторов по-прежнему различаются. Проверьте, как выбранный менеджер окружений устанавливает, лочит и резолвит их. PEP 735 не определяет универсальный CLI-интерфейс.

[tool.*]: конфигурация, которой владеет один инструмент

Таблицы инструментов не используют общую схему:

[tool.pytest.ini_options]
addopts = "-ra"
testpaths = ["tests"]

[tool.ruff]
line-length = 100

Используйте таблицу [tool.*] только в том случае, если инструмент документирует её поддержку. Некоторые настройки по-прежнему должны находиться в отдельных файлах: их потребляет другая экосистема, файл требует другого формата или отдельная конфигурация понятнее. pyproject.toml — это точка координации. Он не требует централизовать все настройки.

Декларации, lock-файлы и файлы requirements решают разные задачи

Распространённый источник путаницы — считать каждый артефакт зависимостей конкурирующим источником истины.

АртефактОсновное назначениеТипичное содержимое
[project.dependencies]Публикуемый runtime-контрактПрямые требования и совместимые диапазоны
[project.optional-dependencies]Публикуемые возможности по запросуExtras для потребителей
[dependency-groups]Непубликуемые локальные окруженияГруппы для тестов, линтинга, документации или приложения
LockfileВоспроизведение разрешённого окруженияТочные версии, источники и метаданные разрешения
requirements.txtВходные данные для pip-compatible установкиRequirements и специфичные для pip опции, constraints, URL или хэши

Библиотека обычно публикует совместимые ограничения и тестируется на диапазоне версий. Приложение обычно коммитит lockfile менеджера окружений. Точные pins должны находиться в разрешённом артефакте деплоя, а не бездумно попадать в публичные метаданные библиотеки.

Сохраняйте файл requirements, если интеграции требуется формат или возможности pip. Если он нужен проекту под управлением uv, экспортируйте его из lock-файла, а не поддерживайте два независимых набора зависимостей:

uv export --format requirements.txt --output-file requirements.txt

Экспорт — это производный compatibility output. Источником разрешённых зависимостей в этом workflow остаётся lock-файл.

Миграция с сохранением поведения

Не начинайте с удаления setup.py или requirements.txt. Сначала классифицируйте назначение каждого существующего файла.

  1. Проведите инвентаризацию build-логики, метаданных, runtime-зависимостей, extras, окружений разработчика, настроек инструментов, package data и entry points.
  2. Выберите бэкенд, способный воспроизвести текущее включение файлов, скомпилированные артефакты и editable installs.
  3. Перенесите статические публикуемые метаданные в [project]; действительно динамические поля оставьте явно динамическими.
  4. Перенесите требования только для контрибьюторов в [dependency-groups], а не в публичные extras.
  5. Переносите настройки инструментов только в тех случаях, когда инструмент поддерживает эквивалентную семантику.
  6. Соберите sdist и wheel, проверьте их содержимое и установите wheel в чистом окружении.
  7. Запустите entry points, тесты, проверки импортов и фактический путь деплоя.
  8. Удаляйте старую конфигурацию только после того, как артефакты и поведение совпадут.

MANIFEST.in всё ещё может требоваться в некоторых layout setuptools, а небольшой setup.py может оставаться допустимым для программного поведения сборки. Модернизация переносит зоны ответственности между файлами. Удаление файлов — не цель.

Актуальный workflow с uv

При создании проекта uv различает приложения и библиотеки:

# Non-library application template
uv init weather-app

# Packaged library with a src layout and build system
uv init --lib weather-client

Команда uv init создаёт файлы проекта. Первая операция с проектом, например uv run, uv sync или uv lock, при необходимости создаёт lock-файл и сохраняемый .venv.

cd weather-client
uv add httpx
uv add --group test pytest pytest-cov
uv run pytest
uv build

Сейчас uv помещает локальные зависимости разработки в стандартизированные группы зависимостей. Его нативный бэкенд uv_build — один из вариантов для проектов на чистом Python; для скомпилированных расширений нужен подходящий альтернативный бэкенд, например maturin или scikit-build-core. Актуальные настройки бэкенда см. в документации uv по конфигурации проекта.

Заключение

pyproject.toml остаётся понятным, когда у каждой таблицы есть одна аудитория. Изоляция сборки относится к [build-system], а публикуемое поведение — к [project]. Окружения контрибьюторов относятся к [dependency-groups]. Переключатели инструментов должны находиться у инструмента, который их определяет.

Когда эти границы зафиксированы, файл проще ревьюить, а миграции перестают смешивать метаданные пакета с разрешённым окружением одной машины.
