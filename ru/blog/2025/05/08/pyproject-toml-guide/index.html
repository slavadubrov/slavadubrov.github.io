pyproject.toml Руководство: пакетизация на Python, зависимости и настройка инструментов

В старых проектах на Python конфигурационные данные часто размещаются в setup.py, setup.cfg, файлах requirements, MANIFEST.in, а также в отдельных файлах для инструментов разработки. pyproject.toml предоставляет единое место для хранения всех этих данных, хотя он не заменяет все проектные файлы и не делает каждый раздел обязательным согласно стандарту.

В этом руководстве рассматривается структура файла от параметров настройки сборки до метаданных проекта и настроек инструментов. Чтобы сделать его понятным, рекомендуется выделить четыре категории ответственности: то, что собирает проект, то, что публикуется проектом, то, что необходимо участникам для локальной работы, и то, что настраивают отдельные инструменты.

Кратко. Используйте [build-system] для бэкенда, отвечающего за сборку дистрибутива, [project] — для публикуемых метаданных и зависимостей, необходимых во время выполнения, [dependency-groups] — для непубликуемых сред разработки, а [tool.*] — только тогда, когда это указано в документации соответствующего инструмента. Заявление о зависимости — это не файл блокировки версий.

Один файл, четыре категории ответственности

Основную структуру определяют три стандарта пакетизации:

  • PEP 518 определяет требования к системе сборки.
  • PEP 621 определяет метаданные проекта.
  • PEP 735 определяет группы зависимостей, которые не публикуются.

Авторы инструментов также могут зарезервировать собственное пространство имен под [tool]. Это пространство является конвенциональным, а не универсальным: каждый инструмент задаёт собственные ключи и правила работы.

Вот пример небольшой упакованной библиотеки:

[build-system]
requires = ["hatchling>=1.26"]
build-backend = "hatchling.build"

[project]
name = "weather-client"
version = "0.1.0"
description = "A small weather API client"
readme = "README.md"
requires-python = ">=3.11"
dependencies = [
  "httpx>=0.27",
]

[project.optional-dependencies]
cli = ["rich>=13"]

[project.scripts]
weather = "weather_client.cli:main"

[dependency-groups]
test = ["pytest>=8", "pytest-cov>=5"]
lint = ["ruff>=0.12"]

[tool.pytest.ini_options]
testpaths = ["tests"]

[tool.ruff]
line-length = 100
target-version = "py311"

Каждый список зависимостей отвечает на свой вопрос. Именно это различие лежит в основе структуры файла.

[build-system]: как исходный код превращается в дистрибутив

Фронтенд сборки, такой как python -m build, pip или uv, вызывает бэкенд сборки. Бэкенд определяет, как исходный код превращается в формат sdist или wheel, а также какие файлы входят в эти артефакты.

[build-system]
requires = ["hatchling>=1.26"]
build-backend = "hatchling.build"

requires содержит зависимости, необходимые для запуска бэкенда в его изолированной среде сборки. Это не список зависимостей, требуемых при выполнении вашего пакета.

Необходимо объявить систему сборки, если проект создаёт дистрибутив или требует установки собственного кода в виде пакета. Проекты, не являющиеся пакетами, всё равно могут использовать pyproject.toml; PEP 735 даже разрешает наличие файла, содержащего только группы зависимостей. Менеджеры сред различаются в том, как обрабатывать проекты без системы сборки, поэтому выбор следует делать осознанно.

Бэкенд выбирается в зависимости от требований сборки:

  • потребности в структуре на чистом Python и выборе файлов;
  • наличие скомпилированных расширений или внешних систем сборки;
  • требования к динамической версии или генерируемым файлам;
  • необходимость режима editable-install;
  • уровень зрелости бэкенда в пайплайне выпуска.

Скопируйте текущую рекомендуемую таблицу бэкенда из его документации. Не добавляйте wheel в список требований сборки по привычке — бэкенд сам указывает, что ему нужно.

[project]: данные, получаемые потребителями метаданных

Таблица [project] описывает дистрибутив: его имя, версию, совместимость с Python, зависимости, необходимые при выполнении, точки входа и другие метаданные для поиска.

[project]
name = "weather-client"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = ["httpx>=0.27"]

Спецификаторы зависимостей представляют собой ограничения, задаваемые резолвером, а не копию состояния конкретной среды. Они включаются в метаданные форматов wheel и sdist, что позволяет инсталляторам нижнего уровня объединять их с требованиями из других пакетов.

Дополнительные компоненты образуют публичный интерфейс установки

[project.optional-dependencies] определяет дополнительные компоненты, которые могут запрашиваться потребителями:

[project.optional-dependencies]
cli = ["rich>=13"]
postgres = ["psycopg[binary]>=3.2"]

Потребитель может установить weather-client[cli]. Поскольку названия дополнений и связанные с ними требования публикуются, их следует рассматривать как функциональные возможности продукта. Не следует использовать дополнение с именем dev исключительно для хранения инструментов разработчиков.

Точки входа связывают установленные команды с Python

[project.scripts]
weather = "weather_client.cli:main"

После установки дистрибутива среда предоставляет weather, который импортирует и вызывает weather_client.cli:main. Тестируйте команды, используя готовый wheel, а не только файлы из корневой директории репозитория — именно wheel и передаётся пользователям.

[dependency-groups]: локальные, непубликуемые среды

Группы зависимостей по PEP 735 описывают среды разработки или не являющиеся пакетами среды без их публикации в качестве метаданных пакета.

[dependency-groups]
test = ["pytest>=8", "pytest-cov>=5"]
lint = ["ruff>=0.12"]
dev = [
  { include-group = "test" },
  { include-group = "lint" },
]

Это подходящая граница для тестов, инструментов проверки кода, генераторов документации и других инструментов разработчиков. Она также полезна для приложений или ноутбуков, которые не создают дистрибутивы.

Группы зависимостей представляют собой стандартизированные данные, однако интерфейсы инсталляторов всё ещё различаются. Необходимо изучить, как конкретный менеджер сред устанавливает, блокирует и решает эти зависимости. PEP 735 не определяет универсального интерфейса командной строки.

[tool.*]: конфигурация, принадлежащая отдельному инструменту

Таблицы инструментов не имеют общей схемы:

[tool.pytest.ini_options]
addopts = "-ra"
testpaths = ["tests"]

[tool.ruff]
line-length = 100

Используйте таблицу [tool.*] только в том случае, если это указано в документации инструмента. Некоторые настройки всё равно лучше хранить в отдельных файлах: из-за использования их другими экосистемами, потребности в другом формате или для большей ясности самой конфигурации. pyproject.toml служит точкой координации, а не обязательством централизовать всё.

Файлы объявлений, блокировок и требований решают разные задачи

Наиболее частой причиной путаницы является рассмотрение каждого артефакта зависимости как потенциального источника истины.

АртефактОсновная цельТипичное содержимое
[project.dependencies]Опубликованный контракт рантаймаПрямые требования и совместимые диапазоны
[project.optional-dependencies]Опубликованные дополнительные возможностиДополнения, предназначенные для потребителей
[dependency-groups]Непубликуемые локальные средыГруппы для тестов, проверки кода, генерации документации или приложений
Файл блокировокВоспроизведение решённой средыТочные версии, источники и метаданные резолюции
requirements.txtВходные данные для установки через pipТребования плюс опции, ограничения, URL-адреса или хэши, специфичные для pip

Библиотеки обычно публикуют совместимые ограничения и тесты для определённого диапазона версий. Приложения же, как правило, сохраняют файл блокировки менеджера среды. Точные версии компонентов должны указываться в готовом результате деплойа, а не просто в публичных метаданных библиотеки.

Необходимо сохранять файл с требованиями, если интеграция требует формата или функций, предусмотренных инструментом pip. Если проект, управляемый uv, нуждается в таком файле, его следует экспортировать из файла блокировки, вместо того чтобы поддерживать два независимых набора зависимостей:

uv export --format requirements.txt --output-file requirements.txt

Результат экспорта представляет собой вывод о совместимости. Файл блокировки остаётся основным источником информации для данного процесса.

Миграция, сохраняющая текущее поведение

Не начинайте процесс с удаления setup.py или requirements.txt. Сначала определите функции каждого существующего файла.

  1. Составьте список логики сборки, метаданных, требований к рантайму, дополнительных компонентов, сред разработки, настроек инструментов, данных пакета и точек входа.
  2. Выберите бэкенд, способный воспроизводить текущую структуру включения файлов, результаты компиляции и возможность редактирования установленных версий.
  3. Переместите статические метаданные в [project]; явно оставьте только те поля, которые действительно динамичны.
  4. Переместите требования, предназначенные только для разработчиков, в [dependency-groups], а не в публичные дополнения.
  5. Указывайте настройки инструментов только там, где данный инструмент поддерживает соответствующую семантику.
  6. Соберите как версию в формате sdist, так и wheel, проверьте их содержимое и установите wheel в чистую среду.
  7. Запустите точки входа, тесты, проверки импорта и полный процесс деплойа.
  8. Удаляйте старую конфигурацию только после того, как результаты сборки и поведение приложения совпадут.

MANIFEST.in может потребоваться в некоторых конфигурациях setuptools, а небольшой setup.py может оставаться актуальным для программной сборки. Модернизация — это изменение ответственности за проект, а не соревнование по количеству удалённых файлов.

Текущий рабочий процесс с uv

uv различает приложения и библиотеки при создании проекта:

# Non-library application template
uv init weather-app

# Packaged library with a src layout and build system
uv init --lib weather-client

uv init создаёт файлы проекта. Первые операции в проекте, такие как uv run, uv sync или uv lock, при необходимости формируют файл блокировки и постоянный .venv.

cd weather-client
uv add httpx
uv add --group test pytest pytest-cov
uv run pytest
uv build

В настоящее время uv помещает требования локальной разработки в стандартизированные группы зависимостей. Его встроенный бэкенд uv_build подходит для проектов на чистом Python; для проектов с компилируемыми расширениями требуется альтернатива, такая как maturin или scikit-build-core.

Заключение

pyproject.toml становится понятным, когда у каждой таблицы есть чёткая аудитория. Изоляция сборки относится к [build-system]. Опубликованное поведение — к [project]. Среды разработчиков — к [dependency-groups]. Изменения инструментов определяются самим инструментом.

Как только эти границы становятся стабильными, файлы становятся проще для анализа, а миграции перестают путать метаданные пакетов с конфигурацией конкретной машины.
