Масштабирование LLM с помощью параллелизма на нескольких GPU и узлах

Viacheslav Dubrov

2025-05-04 · Обновлено 2026-07-15 · 8 мин · Инженерия моделей · ИИ-инфраструктура

Автоматический перевод Эта статья была автоматически переведена с оригинальной английской версии.

Вычисления с большими моделями выходят за пределы одного GPU по разным причинам. В одной задаче обучения может закончиться память под состояние оптимизатора. В другой — память под активации длинных последовательностей. Даже если модель помещается, она может не достигать целевого throughput. Для каждой проблемы нужны свои схема разбиения и паттерн коммуникации.

Это практический разбор основных стратегий параллелизма и связанных с ними ограничений, подготовленный с опорой на Ultra-Scale Playbook от Hugging Face. Цель — показать, что дает каждое разбиение, какими данными оно обменивается и когда становятся необходимы комбинации стратегий.

Кратко. Реплицированный параллелизм по данным повышает throughput обучения, если одна реплика помещается на одном устройстве. Полностью шардированный параллелизм по данным разбивает состояние модели, но добавляет all-gather параметров и reduce-scatter градиентов. Тензорный, конвейерный, контекстный и экспертный параллелизм разбивают соответственно математику слоев, глубину модели, последовательность и слои mixture-of-experts (MoE). Комбинируйте их только после определения узкого места — ограничения по памяти или по коммуникации.

Предполагается, что вы знакомы с backpropagation, слоями Transformer и стандартным тренировочным циклом в PyTorch.

Начните с двух бюджетов памяти

У обучения и инференса разный memory footprint.

training peak ≈ parameters
              + gradients
              + optimizer state
              + saved activations
              + temporary buffers
              + communication buffers
              + allocator headroom

inference peak ≈ resident weights
               + key/value (KV) cache
               + runtime workspace
               + communication buffers
               + allocator headroom

У модели со 70 миллиардами параметров нижняя граница для одних только весов в BF16 составляет 140 ГБ в десятичном исчислении. Для обучения это число мало что говорит: доминировать могут градиенты, состояние оптимизатора, master weights и активации. Оно также не позволяет оценить сервинг, где важны политика работы с кэшем, длина последовательности, конкуренция батчей и квантизация.

Профилируйте точную архитектуру, precision, длину последовательности, micro-batch, оптимизатор, политику чекпоинтинга и рантайм. Фиксируйте пиковую выделенную и зарезервированную память, токены в секунду, время в ядрах и время, видимое в collective-операциях.

Каждое измерение параллелизма требует компромисса

Для каждой стратегии выясняйте, какое измерение тензора разбивается, какое состояние реплицируется и какая collective-операция попадает в критический путь.

Экономия памяти не является фиксированным множителем. Она зависит от степени шардинга, того, что остается реплицированным, временно неразшардированного состояния, политики работы с активациями, padding, дисбаланса и буферов.

Реплицированный параллелизм по данным: throughput без увеличения емкости

Реплицированный параллелизм по данным, обычно называемый distributed data parallel, хранит полную тренировочную реплику на каждом rank. Документация PyTorch по DistributedDataParallel описывает эту модель с репликами и синхронизацией градиентов. Каждый rank обрабатывает свой micro-batch, а градиенты синхронизируются перед шагом оптимизатора.

Используйте эту стратегию, если полное состояние обучения помещается с достаточным запасом, а глобальный батч можно увеличить или скорректировать gradient accumulation. Главные преимущества — простая семантика и зрелая реализация, которая перекрывает вычисления backward с редукцией градиентов по бакетам.

Добавление rank может ухудшить ситуацию, если локальный батч становится слишком маленьким. Проблемы также возникают, когда сеть не успевает скрыть all-reduce или появляются задержки доставки входных данных. Нужный для оптимизации батч может не масштабироваться.

Полностью шардированный параллелизм по данным: память состояния в обмен на collective-операции

Полностью шардированный параллелизм по данным хранит шарды параметров, градиентов и состояния оптимизатора в группе. В статье про ZeRO описан этот паттерн шардинга состояния, а API FSDP2 в PyTorch его реализует. Параметры слоя собираются через all-gather перед вычислением, а затем могут быть повторно зашардированы. Градиенты через reduce-scatter возвращаются владельцам.

В актуальной документации PyTorch API fully_shard в полностью шардированном параллелизме по данным версии 2 (FSDP2) отделен от старой обертки FullyShardedDataParallel. FSDP2 группирует коммуникацию по модулям, к которым применяется fully_shard, и рекомендует применять его снизу вверх, чтобы группы слоев могли перекрывать коммуникацию и вычисления.

from torch.distributed.fsdp import fully_shard

# Apply bottom-up: each block becomes a communication group.
for block in model.transformer.blocks:
    fully_shard(block)

# Shard remaining root parameters such as embeddings and output projection.
fully_shard(model)

# Construct the optimizer after parameters have become sharded distributed tensors (DTensors).
optimizer = AdamW(model.parameters(), lr=learning_rate)

Это структурный эскиз, а не полноценный launcher. Device mesh, mixed precision, чекпоинтинг, инициализация, состояние оптимизатора и распределенные чекпоинты должны соответствовать вашему тренировочному стеку.

Шардинг особенно полезен, когда узкое место — состояние модели, а вычисления слоев могут скрыть достаточную часть трафика collective-операций. Для небольших моделей, медленных соединений, маленьких слоев или схем, где группа шардинга пересекает неподходящую границу топологии, это может быть невыгодным компромиссом.

Тензорный параллелизм: разбиение математики слоев

Тензорный параллелизм разбивает линейную алгебру внутри слоя. Примеры — column-parallel и row-parallel проекции. В руководстве NVIDIA по параллелизму описано это разбиение на уровне слоя. Для частичных результатов нужны collective-операции внутри блоков Transformer, поэтому латентность и пропускная способность многократно влияют на forward и backward.

Используйте его, если слой или его активации не помещаются либо если матмулы достаточно велики, чтобы partitioned kernels обгоняли один rank. Размещайте группу tensor parallel в самом быстром доступном домене коммуникации, а затем измеряйте. При большой степени tensor parallel каждая локальная матрица может стать настолько маленькой, что эффективность ядер снизится, а накладные расходы collective-операций вырастут.

Sequence parallelism часто комбинируют с tensor parallelism, чтобы не реплицировать часть вычислений над активациями. Это не то же самое, что context parallelism, который работает с полной входной последовательностью модели.

Конвейерный параллелизм: разбиение глубины и времени планирования

Конвейерный параллелизм размещает разные группы слоев на разных стадиях и передает между ними активации. Micro-batch позволяют стадиям работать одновременно. В статье про GPipe этот schedule используется для гигантских нейросетей.

Он уменьшает состояние модели на каждой стадии и может снизить объем коммуникации через медленную границу по сравнению с поуровневыми tensor collective-операциями. Цена — пузыри, передача активаций, дисбаланс стадий, более сложное планирование, а также усложнение восстановления и чекпоинтинга.

Для простого сбалансированного schedule в стиле GPipe с p стадиями и m micro-batch идеализированная доля пузыря в forward примерно равна:

(p - 1) / (m + p - 1)

В реальных schedule могут использоваться варианты one-forward/one-backward, interleaving или zero-bubble, а неравномерная стоимость слоев способна полностью изменить формулу. Границы стадий выбирайте по измеренным времени и памяти, а не по одинаковому числу слоев.

Контекстный параллелизм: разбиение активаций длинных последовательностей

Контекстный параллелизм распределяет измерение последовательности. В документации NVIDIA по контекстному параллелизму описаны разбиение последовательности и обмен key/value, необходимый для attention. Каждый rank владеет шардом последовательности, а attention обменивается данными, нужными для сохранения семантики полного контекста. В реализациях могут использоваться point-to-point-кольца, all-gather, all-to-all или иерархические комбинации.

Это снижает потребление памяти активациями при обучении на длинном контексте, но реплицирует веса внутри context group и добавляет коммуникацию для attention. Эффект зависит от типа attention, causal masking, длины последовательности, recomputation и от того, как context groups сочетаются с tensor- и data-parallel-группами.

Не выбирайте эту стратегию по универсальному порогу в 8K, 32K или 100K. Профилируйте память под активации и коммуникацию attention для конкретной архитектуры.

Экспертный параллелизм: только для архитектуры MoE

Экспертный параллелизм распределяет экспертов в слоях mixture-of-experts. В руководстве NVIDIA по параллелизму описано размещение экспертов и его сочетание с другими измерениями параллелизма. Роутер отправляет представления токенов выбранным экспертам и объединяет результаты. Для каждого токена вычисляются только выбранные эксперты, но все веса экспертов по-прежнему нужно хранить и размещать для сервинга.

Экспертный параллелизм — не переключатель оптимизации для dense-модели. Это часть архитектуры MoE. Среди ключевых проблем — балансировка нагрузки, ограничения емкости, all-to-all токенов, отброшенные или дополненные padding токены, auxiliary losses и дисбаланс при сбоях. Отслеживайте число токенов на эксперта, энтропию маршрутизации, переполнение емкости, время коммуникации и качество в зависимости от маршрута.

Собирайте схему с учетом топологии

В больших системах обучения комбинируются разные измерения. Общий world size обычно определяется произведением размеров групп параллелизма по данным (DP), tensor parallel (TP), pipeline parallel (PP) и context parallel (CP). В руководстве NVIDIA по параллелизму показано это произведение:

world size = DP × TP × PP × CP

Expert parallelism может разделять или по-другому включать эти измерения, поэтому проверяйте поддерживаемую фреймворком mesh, а не перемножайте размеры вслепую.

Собирайте схему в следующем порядке:

  1. Нарисуйте домены коммуникации: соединения GPU-GPU, свитчи, границы non-uniform memory access (NUMA), фабрику узлов, oversubscription и путь к хранилищу.
  2. Разместите частые чувствительные к латентности collective-операции, обычно TP, в самом быстром подходящем домене.
  3. Выберите группы FSDP или реплицированного DP с учетом оставшейся емкости и пропускной способности.
  4. Добавьте PP, если размещение по глубине или трафик между доменами дают преимущество; сбалансируйте измеренные время и память стадий.
  5. Добавляйте CP только при наличии ограничения по последовательности, а экспертный параллелизм (EP) — только при наличии соответствующей экспертной топологии модели.
  6. Проверьте делимость числа attention heads, hidden dimensions, слоев, экспертов, размера батча и последовательности для выбранной mesh.
  7. Сравните несколько допустимых mesh на бенчмарках. Эвристики с учетом топологии выбирают кандидатов, но не победителей.

Два кластера с одинаковым числом GPU могут предпочитать разные схемы из-за различий в пропускной способности соединений, иерархии свитчей, подключении CPU и конкуренции за сеть.

Для обучения и сервинга нужны разные решения

При инференсе обычно нет градиентов и состояния оптимизатора, поэтому схемы обучения в стиле FSDP не переносятся автоматически.

Для сервинга задайте следующие вопросы:

  • Помещается ли одна реплика вместе с весами, KV cache, workspace и целевой конкуренцией?
  • Что дает больший throughput: больше независимых реплик или шардинг одной реплики?
  • Снижает ли TP нагрузку на веса и кэш каждого rank настолько, чтобы окупить коммуникацию на уровне слоев?
  • Эффективно ли PP поддерживается для модели и планировщика запросов?
  • Как prefill и decode по-разному нагружают вычисления, пропускную способность памяти и interconnect?
  • Что происходит с tail latency, когда у запросов различаются длины промптов и ответов?

Проводите бенчмарк полного сервера вместе с планировщиком, квантизацией, распределением контекста, политикой батчинга и формой трафика. Число токенов в секунду при обучении не позволяет предсказать time to first token или inter-token latency при сервинге.

Честно измеряйте масштабирование схемы

Для каждого кандидата фиксируйте:

  • идентификаторы модели, кода, рантайма, ядер и топологии
  • глобальный и локальный батч, распределение длин последовательностей и число токенов
  • пиковую память по категориям, если это доступно
  • полезные токены в секунду и утилизацию model floating-point operation (FLOP), если она рассчитывается согласованно
  • видимое время в операциях all-reduce, all-gather, reduce-scatter, all-to-all и point-to-point
  • простои на входных данных, время чекпоинтинга, поведение при перезапуске и распределение straggler
  • loss обучения или паритет выходов сервинга относительно baseline

Осознанно сравнивайте strong и weak scaling. Strong scaling сохраняет общий объем работы постоянным при увеличении числа rank. При weak scaling объем работы на rank остается постоянным, поэтому общий объем растет вместе с числом rank. Процент с меткой «эффективность масштабирования» бессмысленен без указания знаменателя и baseline.

Заключение

Параллелизм — это отображение измеренного боттлнека на измерение тензора и паттерн коммуникации. Репликация, шардинг, разбиение слоев, разбиение на стадии, разбиение последовательности и маршрутизация экспертов снимают разные ограничения и создают разные режимы отказа.

Проведите инвентаризацию нагрузки, нарисуйте топологию, сгенерируйте допустимые mesh и профилируйте их. Побеждает схема, которая помещается с запасом и минимизирует видимую коммуникацию для задачи, которую вы действительно запускаете.
