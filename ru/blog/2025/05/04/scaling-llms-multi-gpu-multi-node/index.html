Масштабирование Large Language Models: стратегии для multi-GPU и multi-node, которые работают на практике

Нагрузки на large-model выходят за пределы одной GPU по разным причинам. Обучающий job может упереться в OOM по памяти на optimizer state, другой — на активации длинных последовательностей, а модель, которая помещается, всё равно может не достигать целевого throughput. Каждая проблема требует своего разбиения и паттерна обмена.

Это практический разбор основных стратегий параллелизма и ограничений, которые за ними стоят, с опорой на Hugging Face Ultra-Scale Playbook. Цель — показать, что именно даёт каждое разбиение, что оно коммуницирует, и когда комбинации становятся необходимыми.

TL;DR. Реплицированный data parallelism даёт throughput обучения, когда одна реплика целиком помещается. Fully sharded data parallelism партиционирует состояние модели, но добавляет parameter all-gathers и gradient reduce-scatters. Tensor, pipeline, context и expert parallelism раскладывают по частям математику по слоям, глубину, последовательность и экспертов MoE. Комбинируйте их только после того, как определите, какое именно ограничение — по памяти или по коммуникациям — является связывающим.

Данный гайд предполагает, что вы уверенно чувствуете backpropagation, Transformer layers и стандартный тренировочный цикл на PyTorch.

Начните с двух бюджетов памяти

Обучение и инференс не имеют одинакового footprint.

training peak ≈ parameters
              + gradients
              + optimizer state
              + saved activations
              + temporary buffers
              + communication buffers
              + allocator headroom

inference peak ≈ resident weights
               + KV cache
               + runtime workspace
               + communication buffers
               + allocator headroom

Модель на 70 миллиардов параметров имеет 140 GB нижней границы только на BF16-веса в десятичном представлении. Эта цифра мало что говорит про обучение: там часто доминируют градиенты, optimizer state, master weights и активации. Также она ничего не говорит про сервинг, где критичны политика кеширования, длина последовательности, конкурентность батчей и квантизация.

Профилируйте точную архитектуру, precision, длину последовательности, micro-batch, оптимизатор, политику checkpointing и runtime. Зафиксируйте peak allocated и reserved память, tokens per second, время в kernels и время, “видимое” в collectives.

Любое измерение параллелизма — это компромисс

Для каждой стратегии задайте вопрос: какая тензорная размерность разбивается, какое состояние реплицируется и какой collective попадает в критический путь.

Ослабление по памяти — не фиксированный мультипликатор. Оно зависит от степени шардирования, того, что остаётся реплицированным, транзиентного несекционированного состояния, политики активаций, паддинга, дисбаланса и буферов.

Replicated data parallelism: throughput без дефицита capacity

Replicated data parallelism, обычно называемый distributed data parallel, хранит полную training-реплику на каждом rank. Каждый rank обрабатывает свой micro-batch, а градиенты синхронизируются перед шагом оптимизатора.

Используйте его, когда полное состояние обучения помещается с безопасным запасом (headroom), а глобальный batch можно наращивать или градиентное накопление — подстраивать. Основные преимущества — простая семантика и зрелая реализация, которая накладывает backward вычисления на редукцию bucketed gradient’ов.

Добавление rank’ов может ухудшить ситуацию, если локальный batch становится слишком маленьким, сеть не может “спрятать” all-reduce, доставка input’ов начинает простаивать, или желаемый optimization batch не масштабируется.

Fully sharded data parallelism: память состояния ради collectives

Fully sharded data parallelism хранит шардированные фрагменты parameter, gradient и optimizer state по группе. Параметры слоя все-гатятся (all-gather) для вычислений и после этого могут быть перешардированы; градиенты reduce-scattered возвращаются владельцам.

Текущая документация PyTorch различает fully_shard API FSDP2 и более старый FullyShardedDataParallel wrapper. FSDP2 группирует коммуникации по модулям, к которым fully_shard применяется, и рекомендует bottom-up применение, чтобы группы слоёв могли перекрывать коммуникации и вычисления.

from torch.distributed.fsdp import fully_shard


# Apply bottom-up: each block becomes a communication group.
for block in model.transformer.blocks:
    fully_shard(block)

# Shard remaining root parameters such as embeddings and output projection.
fully_shard(model)

# Construct the optimizer after parameters have become sharded DTensors.
optimizer = AdamW(model.parameters(), lr=learning_rate)

Это структурный набросок, а не полноценный launcher. Device meshes, mixed precision, checkpointing, инициализация, optimizer state и distributed checkpoints должны соответствовать вашему стеку обучения.

Шардирование особенно привлекательно, когда модельное состояние — связывающее ограничение, а вычисления слоя способны скрывать достаточно коллективного трафика. Для small models, медленных линков, tiny layers или layout’ов, у которых shard group “пересекает” неправильную границу topology, это может оказаться плохой сделкой.

Tensor parallelism: партиционирование математики слоя

Tensor parallelism партиционирует линейную алгебру внутри слоя — например, column-parallel и row-parallel проекции. Частичные результаты требуют collectives внутри transformer blocks, поэтому latency и bandwidth важны снова и снова на каждом forward и backward проходах.

Используйте его, когда слой (или его активации) не помещается, либо когда матмулы достаточно велики, чтобы партиционированные kernels выигрывали у варианта с одним rank. Привяжите tensor-parallel group к самому быстрому доступному домену коммуникаций и затем померьте. Высокая степень tensor parallelism может уменьшить размер каждой локальной матрицы до момента, когда эффективность kernel’ов падает, а оверхед collectives растёт.

Sequence parallelism часто комбинируют с tensor parallelism, чтобы не реплицировать часть работы с активациями; при этом она отличается от context parallelism по полной input sequence модели.

Pipeline parallelism: партиционирование глубины и времени по расписанию

Pipeline parallelism размещает разные группы слоёв на разных стадиях и пересылает между ними активации. Micro-batches позволяют держать стадии занятыми параллельно.

Он снижает модельное состояние на каждую стадию и может уменьшить объём коммуникаций, пересекающих более медленную границу, по сравнению с per-layer tensor collectives. Цена — пузырьки (bubbles), пересылка активаций, дисбаланс стадий, более сложное планирование и более сложное восстановление и checkpointing.

Для простого сбалансированного GPipe-style расписания с p стадиями и m micro-batches доля “forward bubble” в идеализированном случае приблизительно равна:

(p - 1) / (m + p - 1)

В реальных расписаниях могут использоваться варианты one-forward/one-backward, interleaving или zero-bubble, а неравномерная стоимость слоёв способна доминировать формулу. Выбирайте границы стадий на основании измеренного времени и памяти, а не равных количеств слоёв.

Context parallelism: партиционирование активаций длинных последовательностей

Context parallelism распределяет размерность sequence. Каждый rank владеет шардом sequence, а обмен attention должен сохранить информацию, необходимую для семантики полного контекста. Реализации могут использовать point-to-point rings, all-gather, all-to-all или иерархические комбинации.

Context parallelism снижает память на активации при обучении на long-context, но реплицирует веса по context group и добавляет коммуникации attention. Выгода зависит от типа attention, causal masking, длины последовательности, recomputation и того, как context groups сочетаются с tensor и data parallel группами.

Не выбирайте его из универсального порога 8K, 32K или 100K. Профилируйте память на активации и коммуникации attention именно для вашей архитектуры.

Expert parallelism: только для MoE-архитектуры

Expert parallelism распределяет экспертов в mixture-of-experts слоях. Router отправляет представления токенов выбранным экспертам и комбинирует их результаты. Для каждого токена вычисляет только выбранные эксперты, но суммарные веса экспертов всё равно нужно хранить и размещать для сервинга.

Expert parallelism — не “переключатель оптимизации” для dense модели. Он является частью MoE-архитектуры со своими проблемами: load balance, capacity limits, token all-to-all, dropped или padded tokens, auxiliary losses и failure skew. Отслеживайте токены на эксперта, routing entropy, переполнение capacity, время коммуникаций и качество по route.

Соберите layout из topology

Крупные обучающие системы комбинируют несколько измерений. Общий world size часто следует произведению вида:

world size = DP × TP × PP × CP

Expert parallelism может делиться или “сворачиваться” с другими измерениями иначе, поэтому проверьте, какие meshes поддерживает ваш фреймворк, а не умножайте вслепую.

Собирайте layout в таком порядке:

  1. Нарисуйте communication domains: GPU-to-GPU ссылки, switches, границы NUMA, node fabric, oversubscription и storage path.
  2. Разместите частые latency-sensitive collectives, обычно TP, в самом быстром подходящем домене.
  3. Выберите FSDP или replicated DP группы, исходя из оставшейся capacity и bandwidth.
  4. Добавьте PP, если размещение по глубине или cross-domain трафик выгодно; балансируйте измеренное время стадий и память.
  5. Добавьте CP только при constraint по последовательности, и EP только для экспертной topology модели.
  6. Проверьте делимость (divisibility) heads, hidden dimensions, layers, experts, batch и sequence для кандидата mesh.
  7. Пробенчмарьте несколько валидных meshes; topology-aware эвристики выбирают кандидатов, а не победителя.

Два кластера с одинаковым числом GPU могут предпочесть разные layout’ы, потому что различаются bandwidth линков, иерархия switch’ов, присоединение CPU и уровень сетевых конкуренций.

Обучение и сервинг требуют разных решений

Инференс обычно не переносит градиенты или optimizer state, поэтому training-layout’ы в стиле FSDP не переносятся автоматически.

Для сервинга задайте вопросы:

  • Помещаются ли веса, KV cache, workspace и целевая конкурентность в одной реплике?
  • Лучше ли обеспечивать throughput большим числом независимых реплик или шардировать одну реплику?
  • Достаточно ли TP снижает давление на веса и cache на каждом rank, чтобы окупить коммуникации на уровне каждого слоя?
  • Поддерживается ли PP эффективно для модели и request scheduler?
  • Как по-разному prefill и decode нагружают compute, память bandwidth и interconnect?
  • Что происходит с tail latency, когда запросы имеют разные длины prompt и output?

Пробенчмарьте полностью сервер с scheduler’ом, квантизацией, распределением контекста, политикой batching и формой трафика. Training tokens per second не может предсказать время до первого токена или inter-token latency при сервинге.

Измеряйте scaling layout честно

Для каждого кандидата зафиксируйте:

  • model, code, runtime, kernels и identity topology
  • global и local batch, распределение sequence и число токенов
  • peak memory по категориям, если доступно
  • полезные tokens per second и модельную FLOP-утилизацию, если считать последовательно
  • видимое время в all-reduce, all-gather, reduce-scatter, all-to-all и point-to-point операциях
  • input stalls, время checkpoint, поведение при рестарте и распределение straggler’ов
  • training loss или соответствие serving-output базовой версии

Сравнивайте weak и strong scaling осознанно. Weak scaling увеличивает общий объём работ при росте числа rank’ов; strong scaling удерживает общий объём работ постоянным. Показатель в процентах, названный “scaling efficiency”, бессмысленен без этого делителя и baseline.

Заключение

Параллелизм — это отображение измеренного bottleneck на тензорную размерность и паттерн коммуникаций. Репликация, шардирование, партиционирование по слоям, staging, партиционирование по sequence и экспертный роутинг снимают разные ограничения и создают разные режимы отказов (failure mode).

Составьте инвентарь workload’а, набросайте topology, сгенерируйте валидные meshes и профилируйте их. Победивший layout — тот, который помещается с headroom и минимизирует “выставленные” коммуникации для того job’а, который вы реально запускаете.
