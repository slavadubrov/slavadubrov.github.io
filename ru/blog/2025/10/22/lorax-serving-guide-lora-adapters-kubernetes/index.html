Руководство по сервисированию LoRAX: работа с множеством адаптеров LoRA на Kubernetes

Одна базовая модель в сочетании с большим количеством адаптеров LoRA создаёт особую проблему при сервисировании. Веса базовой модели являются общими, но каждый запрос может требовать другого набора весов адаптера. Традиционный подход, предполагающий отдельную разработку для каждой версии, приводит к расточительству памяти GPU, поскольку большинство версий остаются неиспользуемыми.

LoRAX решает эту проблему, связанную с «длинным хвостом» запросов. Он загружает адаптеры по мере необходимости, объединяет запросы к разным адаптерам в группы и перемещает их веса между памятью GPU и CPU. Привлекательным результатом является возможность запуска «тысяч отфинтюнингованных моделей на одном GPU». Однако технический вопрос звучит более узко: помогает ли расписание обмена активными адаптерами, характер потока запросов и целевые показатели латентности оправдать использование дополнительного рантайма?

Данное руководство отвечает на этот вопрос, проверяет API локально, а затем преобразует стартовую Helm-диаграмму из репозитория в конкретный план внедрения в производство.

Кратко. Используйте LoRAX, когда множество совместимых адаптеров LoRA используют одну базовую модель, а трафик имеет редкий или «длиннохвостовый» характер. Пропускная способность зависит от активного набора моделей, а не от общего количества доступных адаптеров. Укажите конкретный рантайм, настройте аутентификацию и список разрешённых ID адаптеров, добавьте механизмы кэширования результатов и проверки работоспособности, оптимизируйте маршрутизацию с учётом локальности кэша и отдельно проводите тестирование холодных и тёплых сценариев.

Проблема сервисирования связана с активным набором моделей

Метод LoRA заключается в замораживании базовой модели и обучении низкоранговых обновлений для выбранных матриц весов. Результатом становится адаптер, размер которого обычно значительно меньше размера полного чекпоинта, но он всё равно зависит от ранга, целевых модулей, количества слоёв и типа данных. Такие утверждения вроде «каждый адаптер занимает 100 МБ» не являются точными показателями пропускной способности.

Для целей сервисирования необходимо различать три показателя:

  • Размер каталога: количество адаптеров, доступных системе из хранилища;
  • Активный набор моделей: адаптеры, получающие запросы в течение времени хранения в кэше;
  • Конкурентный набор: адаптеры, обрабатываемые одновременно в виде групп.

Каталог может содержать тысячи адаптеров, но в VRAM может поместиться лишь ограниченное их количество. Важным фактором является частота изменения активного набора, размер самого набора и возможность совместного использования групп для запросов к разным адаптерам.

LoRAX объединяет четыре механизма для решения этой проблемы:

  1. Базовая модель остаётся в памяти для всех совместимых адаптеров;
  2. Запрос указывает конкретный адаптер, который можно загрузить из Hugging Face, Predibase или файловой системы;
  3. Расписание обмена адаптерами позволяет заранее загружать необходимые веса и переносить их между памятью GPU и CPU;
  4. Гетерогенное непрерывное батчинг объединяет запросы к разным адаптерам в группы.

Согласно тестам проекта, гетерогенное батчинг обеспечивает почти постоянную пропускную способность и уровень латентности при увеличении количества одновременно обрабатываемых адаптеров. Можно рассматривать это как гипотезу для вашей рабочей нагрузки. Длина промпта, длина вывода, ранг, целевые модули, уровень загрузки батча, частота обновления кэша и производительность GPU могут влиять на результаты.

Когда LoRAX является подходящим решением

LoRAX имеет смысл использовать в следующих случаях:

  • адаптеры были обучены на одной и той же базовой модели и согласно одному и тому же стандарту токенизации;
  • трафик включает множество адаптеров с заметным «длиннохвостовым» характером;
  • загрузка адаптера по мере необходимости предпочтительнее, чем выделение отдельной инфраструктуры для него;
  • на уровне приложения уже существует механизм маршрутизации тенантов или задач;
  • команда способна управлять специализированным рантаймом и его поведением кэша.

Типичными примерами являются ассистенты, настроенные под конкретных арендаторов, множество вариантов моделей для разных областей, а также онлайн-эксперименты, использующие общий базовый чекпоинт.

Этот подход менее эффективен в ситуациях, когда небольшое количество адаптеров контролирует всё трафик, модели не имеют общей базы, строгие задания по латентности не позволяют работать с «холодными» загрузками, или платформа не может гарантированно контролировать, какие артефакты будет загружать сервер. В таких случаях проще использовать стандартную реализацию vLLM или TGI с фиксированным набором адаптеров.

Не стоит использовать Kubernetes только из-за большого количества компонентов — сначала необходимо проверить совместимость рантайма и адаптеров на одной видеокарте.

Проверка одной базовой модели и двух адаптеров локально

В документации LoRAX рекомендуется использовать готовый контейнер. В реальной среде следует применять изображение с неизменяемым дайджестом; main приведён здесь лишь потому, что это официальный тег быстрого запуска, указанный в репозитории.

mkdir -p data

docker run --rm --gpus all --shm-size 1g \
    -p 8080:80 \
    -v "$PWD/data:/data" \
    ghcr.io/predibase/lorax:main \
    --model-id mistralai/Mistral-7B-Instruct-v0.1

Минимальные требования, указанные в документации: операционная система Linux, инструмент Docker, видеокарта NVIDIA серии Ampere или новее, а также драйверы, совместимые с CUDA 11.8. Лицензии моделей и защищённые репозитории могут также требовать токена Hugging Face.

Начните с базовой модели:

curl http://127.0.0.1:8080/generate \
    -H 'Content-Type: application/json' \
    -d '{
      "inputs": "[INST] Give one reason to measure cold-adapter latency. [/INST]",
      "parameters": {"max_new_tokens": 64}
    }'

Затем отправьте совместимый адаптер:

curl http://127.0.0.1:8080/generate \
    -H 'Content-Type: application/json' \
    -d '{
      "inputs": "[INST] Solve: Natalia sold 48 clips in April and half as many in May. What is the total? [/INST]",
      "parameters": {
        "max_new_tokens": 64,
        "adapter_id": "vineetsharma/qlora-adapter-Mistral-7B-Instruct-v0.1-gsm8k"
      }
    }'

Первый запрос может потребовать загрузки и обработки адаптера; последующие запросы могут использовать уже сохранённые артефакты и веса модели. Записывайте оба варианта работы. Один запрос с уже загруженными данными мало что говорит о поведении системы при обработке редких запросов.

Использование текущего клиента OpenAI

LoRAX предоставляет конечную точку чата, совместимую с OpenAI. Поле model используется для идентификации адаптера:

from openai import OpenAI


client = OpenAI(
    api_key="EMPTY",
    base_url="http://127.0.0.1:8080/v1",
)

response = client.chat.completions.create(
    model="alignment-handbook/zephyr-7b-dpo-lora",
    messages=[
        {"role": "user", "content": "Explain cache locality in two sentences."},
    ],
    max_tokens=100,
)

print(response.choices[0].message.content)

По умолчанию сервер не требует API-ключа, что удобно для локальной работы, но создаёт риски при использовании в сети. Аутентификацию, авторизацию арендаторов, квоты и список разрешённых адаптеров следует реализовать перед использованием этой функции.

Определение критериев совместимости

Перед добавлением адаптера в каталог необходимо проверить, по крайней мере:

  • указанную базовую модель и её версию;
  • совместимость токенизатора и шаблона чата;
  • уровень LoRA и поддерживаемые рантаймом модули;
  • формат артефакта и формы тензоров;
  • лицензию, информацию о происхождении и хэш целостности;
  • набор простых тестов на поведение и отсутствие регрессий.

Несовместимые артефакты следует отклонять на этапе регистрации, а не при первом запросе пользователя.

Понимание способа размещения данных перед деплойом

Базовая модель занимает основную часть памяти видеокарты. Веса адаптеров, кэш KV, рабочее пространство пакетов и ядра рантайма конкурируют за оставшуюся память. CPU-RAM может хранить адаптеры, перенесённые с видеокарты, в то время как /data используется для хранения загруженных артефактов.

Эти уровни хранения не являются взаимозаменяемыми: артефакт, сохранённый на диске или в Hub, должен быть сначала прочитан и преобразован в формат, доступный для CPU или GPU, прежде чем стать адаптером, работающим в данном режиме. Необходимо отдельно измерять время перехода между форматами:

ПутьЧто включаетПоказатель для записи
GPU hitАдаптер уже находится в памяти GPUвремя ожидания в очереди и время до получения первого токена
CPU hitПередача или повторная загрузка в GPUзадержка загрузки адаптера и общая латентность
Artifact hitЧтение из локального кэша /dataвремя чтения/загрузки и объём использованного кэша
Remote missЗагрузка, проверка и обработка артефактавремя загрузки, количество ошибок и полная латентность при «холодном» старте

Планирование пропускной способности должно учитывать реальное распределение популярности адаптеров. Использование одинаковых случайных идентификаторов адаптеров приводит к иным проблемам с кэшированием по сравнению с рабочей нагрузкой, характерной для моделей типа Zipf.

Аккуратно развертывайте диаграмму репозитория

В репозитории содержится charts/lorax, поэтому воспроизводимой отправной точкой служат зафиксированная версия репозитория и локальная диаграмма:

git clone https://github.com/predibase/lorax.git
cd lorax
git checkout <reviewed-commit-or-release>

helm dependency update charts/lorax
helm template lorax charts/lorax -f values.production.yaml
helm upgrade --install lorax charts/lorax \
    --namespace inference \
    --create-namespace \
    -f values.production.yaml

Как было отмечено 15 июля 2026 года, параметры по умолчанию диаграммы требуют внимания:

  • тег изображения равен latest;
  • /data представляет собой emptyDir, в связи с чем замена подов приводит к удалению загруженных артефактов;
  • проверки жизнеспособности и готовности отсутствуют;
  • токен Hugging Face рассматривается как обычное значение среды;
  • по умолчанию запрашивается одна GPU.

Это делает диаграмму полезной основой, но не политикой для производственной среды.

Исходите из реальной структуры значений диаграммы

Диаграмма включает конфигурацию рантайма внутрь deployment, а аргументы запуска представляют собой список пар «имя/значение». Минимальная структура выглядит следующим образом:

deployment:
    replicas: 1

    image:
        repository: ghcr.io/predibase/lorax
        tag: "<tested-tag>" # Prefer an immutable digest in rendered manifests.

    args:
        - name: "--model-id"
          value: "mistralai/Mistral-7B-Instruct-v0.1"
        - name: "--max-input-length"
          value: "2048"
        - name: "--max-total-tokens"
          value: "3072"
        - name: "--max-batch-total-tokens"
          value: "8192"
        - name: "--max-batch-prefill-tokens"
          value: "4096"

    resources:
        requests:
            nvidia.com/gpu: "1"
        limits:
            nvidia.com/gpu: "1"

    readinessProbe:
        httpGet:
            path: /health
            port: http
        periodSeconds: 5
        failureThreshold: 600

service:
    serviceType: ClusterIP
    port: 80

Указанные выше лимиты на токены являются примерами начальных значений, а не рекомендациями по их размеру. Они определяются на основе типичных промптов, ожидаемой конкурентности, объёма памяти GPU и тестов нагрузки.

Явно устраняйте имеющиеся пробелы

Текущий шаблон диаграммы содержит жёстко заданные объёмы emptyDir и простые значения среды. Поэтому для надёжного развертывания требуется пересмотренная копия диаграммы, патч после генерации или использование более высокого уровня манифеста для добавления:

  • PersistentVolumeClaim или локального кэша артефактов, монтируемого в /data;
  • ссылки на Secret с учётными данными Hub;
  • проверки запуска перед более интенсивными проверками жизнеспособности;
  • политики прерывания подов и распределения по топологии для нескольких реплик;
  • NetworkPolicy, ограничений для счётов служб и авторизованного шлюза;
  • фиксации хэша изображения и проверок целостности артефактов.

Не размещайте токен Hub напрямую в файле с коммитированными значениями. Не предполагайте, что две реплики обеспечат достаточную доступность, пока обе не смогут загрузить базовую модель, а роутер не сможет избежать отправки всех «холодных» адаптеров в оба пода.

Обеспечивайте локальность кэширования при маршрутизации

Метод равномерного распределения может превратить каждую реплику в «холодный» кэш. Эффективный роутер генерирует хеш или иным образом связывает допустимый идентификатор адаптера с конкретной репликой, сохраняя при этом путь для переключения при её недоступности.

Ключ маршрутизации должен формироваться на основе авторизованного состояния приложения, а не произвольного параметра публичного URL. В противном случае вызывающий код может принудительно выполнять удалённые загрузки, заполнять кэш или запрашивать имена приватных адаптеров.

LoRAX или vLLM?

Современная версия vLLM способна обслуживать модули LoRA, указанные при запуске, а также загружать их динамически через конечные точки или плагины-резолверы. В её собственной документации указано, что обновление адаптеров в рантайме сопряжено с рисками для безопасности и не должно использоваться в производстве за пределами изолированной, надёжной среды.

Полезное сравнение касается операционных аспектов, а не числовых показателей:

ВопросLoRAXvLLM
Как находятся адаптеры для длинного хвоста?По запросу идентификатор адаптера может обращаться к ресурсам Hugging Face, Predibase или файловой системеСтатические модули, конечные точки динамического управления или плагины-резолверы
Как управляется размещением компонентов?Явное планирование обмена адаптерами между GPU и CPUНастройки лимитов активных и CPU-адаптеров LoRA, а также поведение резолвера
Каков интерфейс запроса?Структура в стиле TGI /generate, клиент на Python и чат, совместимый с OpenAIСервисирование, совместимое с OpenAI, и нативные Python-API
Что должно определять выбор?Уровень латентности при холодном/тёплом запуске, частота обновления кэша, пропускная способность неоднородных пакетов и соответствие операционным требованиямТе же критерии повторной обработки нагрузки и операционные параметры

Избегайте утверждений вроде «LoRAX поддерживает 1000 адаптеров, а vLLM — 10». Размер каталога сам по себе не определяет производительность. Сравнивайте их, используя одинаковую базовую модель, адаптеры, промпты, порядок ранжирования, трассировку запросов и аппаратное обеспечение.

Тест приёмки в продакшене

Перед расширением каталога выполните повторную обработку запросов, включающую:

  1. Фиксированный набор «горячих» адаптеров для определения уровня пропускной способности и латентности в тёплом режиме.
  2. Дистрибуцию данных из длинного хвоста для оценки количества успешных обращений к CPU и кэшу артефактов.
  3. Всплеск запросов к ранее не виденным, но включённым в список адаптерам.
  4. Замену контейнеров для оценки восстановления работы базовой модели и адаптеров.
  5. Один недоступный или повреждённый адаптер для проверки механизмов изоляции и перехода на альтернативу.
  6. Одновременную работу нескольких пользователей для проверки механизмов аутентификации, квот и меток метрик.

Отслеживайте скорость поступления запросов, время ожидания в очереди, время получения первого токена, латентность между токенами, общую латентность, время загрузки адаптера, тип успешного обращения к кэшу, объём памяти GPU и CPU, количество загруженных байтов и причины сбоев. Избегайте использования идентификаторов адаптеров в неограниченных метриках; отображайте их через контролируемые размерности или выборочные трассы.

Заранее определите пороговые значения для приёмки. Примеры включают максимальную долю ошибок при холодном запуске, целевое значение P99 для тёплого режима, целевой показатель успешных обращений к кэшу для заданной дистрибуции популярности и целевое время восстановления после потери контейнера.

Заключение

LoRAX преобразует множество совместимых вариантов финальной настройки модели из набора копий базовой модели в задачу размещения адаптеров. Это эффективный подход для обработки запросов из длинного хвоста, однако он не гарантирует постоянства затрат и латентности. Результат всё равно определяется активным набором компонентов, путём их обмена, составом пакетов и уровнем хранения.

Сначала проверьте эти механизмы на одном GPU. Если LoRAX показывает лучшие результаты, чем текущая конфигурация vLLM при одинаковых условиях тестирования, решение о деплойе будет обоснованным.
