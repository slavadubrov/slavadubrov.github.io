Разумование под управлением схемы в vLLM: структурированные выходные с использованием xgrammar и Pydantic

Повторные вызовы LLM не гарантируют получения корректного JSON. Следующий пример может сработать так же плохо, а многократные вызовы увеличивают латентность и затраты.

Техника разумования под управлением схемы (Schema-Guided Reasoning, SGR) обеспечивает соблюдение определённой схемы в процессе генерации каждого токена моделью. Необходимые поля задаются с помощью Pydantic, а движок инференса блокирует токены, нарушающие эту структуру. Благодаря этому результат автоматически оказывается синтаксически корректным, без необходимости повторных попыток.

Кратко. SGR использует ограниченную декодировку для привязки вывода LLM к схеме Pydantic, которую вы контролируете. В сочетании с бэкендом xgrammar от vLLM это обеспечивает получение корректного JSON в каждый раз при минимальных потерях в латентности.

Что такое разумование под управлением схемы?

Разумование под управлением схемы — это техника, описанная Rinat Abdullin в 2024 году. Вместо того чтобы позволять модели свободно завершать текст (что может привести к несогласованности или неоднозначности), ей предоставляется строгая шаблонная структура, определяющая:

  • последовательность шагов, которые модель должна выполнить, чтобы не пропустить анализ;
  • порядок этих шагов, что обеспечивает переход от данных к решению;
  • области, на которые следует сосредоточить внимание, чтобы глубина анализа была направлена туда, где это важно.

Можно представить это как когнитивный чек-лист, который модель обязана соблюдать.

Что контролирует схема

Поля вроде churn_analysis, margin_math и max_discount_percent чётко определяют ожидаемые промежуточные результаты. Модель должна заполнить всю необходимую структуру перед тем, как сможет вернуть окончательное решение о скидке.

Это даёт возможность:

  • получать воспроизводимые результаты при многократных запусках;
  • иметь проверяемые выходные, где каждый шаг можно просмотреть;
  • использовать промежуточные поля для оценки на основе тестовых датасетов;
  • использовать более мелкие модели, поскольку схема задаёт то, что модель иначе должна была бы сама изучать;
  • достигать улучшения точности на 5–10% в рабочих нагрузках исходных разработчиков, однако это требует проверки на собственных данных.

Промпт-инжиниринг: семантическое воздействие

Please analyze the customer data and output your response as valid JSON
with the following structure: {"discount": <number>, "reason": <string>}
Be careful with the formatting!

Здесь предполагается, что понимание моделью фразы “вывести JSON” преобладает над её склонностью к разговорному стилю. Однако обновление модели, изменение параметра temperature или использование другого примера в формате few-shot могут нарушить работу вашего парсера.

Последовательное мышление: лучший ризонинг, та же проблема структуры

Let's think step by step:
1. First, I'll analyze the customer's churn risk...
2. Then I'll calculate the margin...
3. Therefore, I recommend a 15% discount.

Метод CoT повышает точность ризонинга, но ухудшает структуру вывода. Результатом становится непредсказуемая проза, которую практически невозможно надёжно парсить. Обычно приходится выполнять второй вызов LLM только для извлечения структурированных данных.

SGR: структурированное последовательное мышление

SGR сохраняет идею CoT о том, что промежуточный ризонинг улучшает точность, но формализует процесс выполнения шагов:

class PricingLogic(BaseModel):
    # 1. Data Analysis (must complete before decision)
    churn_analysis: str = Field(..., description="Analyze churn_probability")
    financial_analysis: str = Field(..., description="Analyze cart_value and margin")

    # 2. Math Enforcement (explicit calculation)
    margin_math: str = Field(..., description="Calculate: 'Cart $X * Y% = $Z'")

    # 3. Decision Constraint (bounded by prior analysis)
    max_discount_percent: float = Field(..., description="Max allowed discount")

    # 4. Final Output
    offer_code: str
    customer_message: str

Модель не может вывести max_discount_percent до тех пор, пока не будут заполнены churn_analysis, financial_analysis и margin_math. Схема обеспечивает соблюдение порядка ризонинга.

Шаблоны SGR

SGR включает три основных шаблона, которые комбинируются для создания более сложных рабочих процессов.

1. Каскад: последовательные шаги ризонинга

Каскад обеспечивает соблюдение определённого порядка выполнения шагов ризонинга. Каждое поле должно быть заполнено перед переходом к следующему.

from pydantic import BaseModel
from typing import Literal, Annotated
from annotated_types import Ge, Le

class CandidateEvaluation(BaseModel):
    """Evaluate a job candidate with enforced reasoning order."""

    # Step 1: Summarize (forces context awareness)
    brief_candidate_summary: str

    # Step 2: Rate (bounded integer)
    rate_skill_match: Annotated[int, Ge(1), Le(10)]

    # Step 3: Decide (constrained choices)
    final_recommendation: Literal["hire", "reject", "hold"]

Хорошие примеры применения: оценка кандидатов, классификация документов, анализ соответствия нормам, медицинская диагностика. Модель должна сначала написать brief_candidate_summary, затем провести оценку, а уже после этого — сделать рекомендацию. Обходных путей нет.

2. Маршрутизация: семантическое операторы выбора

Маршрутизация заставляет модель выбрать один из возможных путей из набора вариантов с помощью типов Union.

from pydantic import BaseModel
from typing import Literal, Union

class FeatureLookup(BaseModel):
    """Route to database lookup."""
    rationale: str
    tool_name: Literal["fetch_user_features"] = "fetch_user_features"
    user_id: str

class GeneralResponse(BaseModel):
    """Standard response for non-pricing queries."""
    tool_name: Literal["respond"] = "respond"
    content: str

class RouterSchema(BaseModel):
    """The model must pick exactly ONE branch."""
    action: Union[FeatureLookup, GeneralResponse]

Хорошие примеры применения: классификация намерений, выбор инструментов, триаж поддержки, диспетчеризация мультиагентных систем.

Дискриминатор Literal (tool_name) заставляет модель выбрать один конкретный путь выполнения и заполнить лишь те поля, которые необходимы для этого пути.

3. Цикл: повторный ризонинг с использованием списков

Механизм цикла обязывает модель генерировать несколько элементов, при этом устанавливаются ограничения на их количество.

from pydantic import BaseModel
from typing import List, Literal, Annotated
from annotated_types import MinLen, MaxLen

class RiskFactor(BaseModel):
    explanation: str
    severity: Literal["low", "medium", "high"]

class RiskAssessment(BaseModel):
    """Generate 2-4 risk factors."""
    factors: Annotated[List[RiskFactor], MinLen(2), MaxLen(4)]

Хорошие примеры применения: оценка рисков, извлечение проблем, параллельные вызовы инструментов, многоэтапное планирование.

Ограничения, заданные через MinLen и MaxLen, требуют наличия от минимум 2 до максимум 4 элементов. В сочетании с механизмом роутинга это позволяет формировать пакеты вызовов инструментов фиксированной длины.

Реализация работы SGR: ограниченная декодировка

Приведённые выше шаблоны представляют собой просто схемы Pydantic. Однако именно ограниченная декодировка (также называемая структурированным выводом) делает их обязательными к соблюдению.

Ограниченная декодировка модифицирует процесс генерации токенов. Вместо того чтобы модель свободно выбирала элементы из своего словаря, движок применяет грамматическую маску, блокирующую те токены, которые могут нарушить структуру схемы. Этот процесс происходит в самом движке инференса, а не в коде приложения.

[!TIP] Для работы SGR не требуются «модели ризонинга» вроде o1 или DeepSeek-R1. Она эффективно работает с моделями, отрегулированными под выполнение инструкций, особенно хорошо — с моделями, полученными путём дистилляции из моделей ризонинга.

Почему в данной статье основное внимание уделяется vLLM и xgrammar

Несколько причин:

  • vLLM — наиболее широко используемый движок инференса для открытых ЯЗЫКОВ больших моделей, поэтому разработанные на его основе решения легко мигрируют на другие платформы.
  • xgrammar реализован на C++ и не добавляет значимой задержки при работе.
  • API vLLM совместим с технологиями OpenAI, что снижает затраты на миграцию из облачных сервисов.
  • xgrammar способен обрабатывать сложные вложенные схемы, объединения и рекурсивные структуры.

В следующем разделе рассматривается, как именно xgrammar обеспечивает соблюдение схемы на уровне токенов.

Как xgrammar обеспечивает соблюдение схемы

Эту часть важно понимать до мелочей, так как она влияет на процесс отладки и настройки рабочих процессов SGR.

Где происходит маскировка

xgrammar изменяет логиты вывода после выполнения модели и перед процедурой выбора токенов. Он не модифицирует саму модель, а лишь фильтрует токены, которые могут быть выбраны.

Стандартный агентный цикл выглядит следующим образом:

1. Input tokens → GPU Forward Pass → Logits (probability scores for all ~128K tokens)
2. Logits → Sampling (temperature, top-p, etc.) → Next Token
3. Repeat until done

xgrammar вставляется между шагами 1 и 2:

1. Input tokens → GPU Forward Pass → Raw Logits
2. Raw Logits → xgrammar Logits Processor → Masked Logits
3. Masked Logits → Sampling → Next Token (guaranteed valid)
4. Repeat until done

Модель продолжает вычислять полную распределение вероятностей на GPU. Затем xgrammar работает на CPU и применяет маску к этим логитам перед выбором токенов. Недопустимым токенам присваиваются логиты в значение -∞, в результате чего их вероятность после операции softmax становится равной 0.

Две фазы

xgrammar делит работу на этапы компиляции и рантайма, что обеспечивает высокую скорость работы.

Фаза 1: компиляция грамматики, один раз на схему

# This happens once per schema
tokenizer_info = xgr.TokenizerInfo.from_huggingface(tokenizer)
grammar_compiler = xgr.GrammarCompiler(tokenizer_info)
compiled_grammar = grammar_compiler.compile_json_schema(schema_json)

Во время компиляции xgrammar:

  1. Преобразует JSON Schema в грамматику с свободными конструкциями.
  2. Создаёт автомат с накоплением (PDA) — машину состояний с стеком, позволяющую обрабатывать вложенные структуры, подобные {"a": {"b": {"c": ...}}}.
  3. Заранее определяет, какие токены допустимы в каждой позиции грамматики. Результатом является «кэш адаптивных масок токенов».
  4. Классифицирует токены как «независимые от контекста» (можно кэшировать) или «зависимые от контекста» (необходимо проверять в рантайме на основе состояния стека).

[!NOTE] Примерно 99% токенов оказываются независимыми от контекста и сохраняются в кэше (XGrammar paper). Большинство проверок допустимости в рантайме представляют собой простые запросы к кэшу, что и обеспечивает высокую скорость работы xgrammar.

Фаза 2: генерация маски в рантайме, для каждого токена

На каждом шаге генерации:

  1. GrammarMatcher отслеживает текущее положение в грамматике.
  2. Он запрашивает заранее вычисленную маску для токенов, не зависящих от контекста.
  3. Затем он запускает автомат ПДА для проверки оставшихся токенов, зависящих от контекста.
  4. В итоге все они объединяются в финальную маску битов, которая применяется к логитам.

Почему именно автоматы с загрузкой данных, а не регулярные выражения?

Из‑за возможности вложенности. Регулярное выражение (машина конечных состояний) не может надёжно сопоставлять структуры вида:

{ "user": { "profile": { "settings": { "theme": "dark" } } } }

Самой сложной частью являются закрывающие скобки }}}: необходимо помнить, сколько из них было открыто. У автомата с загрузкой данных имеется стек, который отслеживает это количество, что позволяет обрабатывать любую глубину вложенности. Именно поэтому xgrammar может поддерживать типы «Union», вложенные объекты и рекурсивные схемы, тогда как подходы на основе регулярных выражений оказываются недостаточными.

Конкретный пример: генерация числа с плавающей точкой

Когда модель генерирует "max_discount_percent":, xgrammar на основе схемы знает, что далее должен появиться float. Маска:

  • разрешает (вероятность остаётся прежней): 0, 1, 2, …, 9, ., -;
  • блокирует (вероятность устанавливается в 0): ", {, [, true, false, null, а также все остальные элементы словаря объёмом более 128 K.

Во время прямого прохождения модель могла присвоить высокую вероятность слову "fifteen". После применения маски xgrammar вероятность этого токена становится равной 0, и модель вынуждена выводить цифры.

Почему накладные расходы практически равны нулю?

Три причины:

  1. Параллельная обработка. Вычисление маски на CPU происходит одновременно с следующим прямым прохождением на GPU. Пока GPU вычисляет логиты для токена N+1, CPU уже готовит маску для токена N.
  2. Кэширование. Большая часть работы по проверке корректности выполняется на этапе компиляции; во время выполнения основные операции — это запросы к кэшу.
  3. Реализация на C++. Основной поток выполнения написан на C++, а не на Python, и маска применяется к логитам непосредственно в памяти.

В бенчмарках xgrammar показывает практически незначительные накладные расходы, а структурированная генерация иногда бывает быстрее, чем генерация без ограничений, поскольку ограниченный словарь снижает стоимость выбора токенов.

Шаг 1: определение схем

# sgr/models/schemas.py
from pydantic import BaseModel, Field
from typing import Literal, Union


# --- Phase 1: Routing (Union for branching) ---
class FeatureLookup(BaseModel):
    """Route to DB lookup if pricing context is needed."""
    rationale: str
    tool_name: Literal["fetch_user_features"] = "fetch_user_features"
    user_id: str


class GeneralResponse(BaseModel):
    """Standard response for non-pricing queries."""
    tool_name: Literal["respond"] = "respond"
    content: str


class RouterSchema(BaseModel):
    action: Union[FeatureLookup, GeneralResponse]


# --- Phase 2: Pricing Logic (Cascade for sequential reasoning) ---
class PricingLogic(BaseModel):
    """
    Strict reasoning topology for dynamic pricing.
    Fields are ordered to enforce the analysis→decision flow.
    """
    # 1. Data Analysis (Reflection)
    churn_analysis: str = Field(...,
        description="Analyze churn_probability (High > 0.7).")
    financial_analysis: str = Field(...,
        description="Analyze cart_value and profit_margin.")

    # 2. Hard Math Enforcement
    margin_math: str = Field(...,
        description="Calculate absolute profit: 'Cart $200 * 0.20 Margin = $40'.")

    # 3. The Decision Constraint
    max_discount_percent: float = Field(...,
        description="Max allowed discount %. NEVER exceed margin.")

    # 4. Final Output
    offer_code: str = Field(..., description="Generated code (e.g. SAVE20).")
    customer_message: str = Field(..., description="The final polite offer text.")

Шаг 2: клиент LLM, включающий xgrammar

# sgr/utils/llm_client.py
from openai import OpenAI
from pydantic import BaseModel
from typing import TypeVar
import json

T = TypeVar("T", bound=BaseModel)


class LLMClient:
    """Wrapper for vLLM with xgrammar-enforced structured generation."""

    def __init__(self, base_url: str = "http://localhost:8000/v1"):
        self.client = OpenAI(base_url=base_url, api_key="EMPTY")
        self.model = self._get_available_model()

    def _get_available_model(self) -> str:
        """Auto-detect the model running on vLLM server."""
        try:
            models = self.client.models.list()
            if models.data:
                return models.data[0].id
        except Exception:
            pass
        return "Qwen/Qwen2.5-7B-Instruct"

    def run_sgr(self, messages: list[dict], schema_class: type[T]) -> T:
        """Run inference with Schema-Guided Response constraints.

        Uses vLLM's guided_json with xgrammar backend to enforce
        strict schema constraints at the token generation level.
        """
        schema_dict = schema_class.model_json_schema()

        # Enhance system message with schema for model guidance
        enhanced_messages = messages.copy()
        if enhanced_messages and enhanced_messages[0]["role"] == "system":
            schema_json = json.dumps(schema_dict, indent=2)
            enhanced_messages[0] = {
                "role": "system",
                "content": (
                    enhanced_messages[0]["content"]
                    + f"\n\nRespond with JSON matching this schema:\n{schema_json}"
                ),
            }

        # vLLM's guided_json with the xgrammar backend
        completion = self.client.chat.completions.create(
            model=self.model,
            messages=enhanced_messages,
            temperature=0.1,  # Low temp for deterministic reasoning
            extra_body={
                "guided_json": schema_dict,  # Pydantic schema as dict
                "guided_decoding_backend": "xgrammar",  # Hardware-enforced
            },
        )

        raw_response = completion.choices[0].message.content
        return schema_class.model_validate_json(raw_response)

[!NOTE] > guided_json принимает словарь JSON Schema. Благодаря guided_decoding_backend: "xgrammar" LLM может генерировать только те токены, которые формируют корректный JSON, соответствующий вашей схеме.

Шаг 3: оркестрация работы ИИ-агента

# sgr/agent.py
from .models.schemas import PricingLogic, RouterSchema
from .prompts.routing import build_routing_prompt
from .prompts.pricing import build_pricing_context_prompt, ASSISTANT_FETCH_MESSAGE
from .store.hybrid_store import HybridFeatureStore
from .utils.llm_client import LLMClient


def pricing_agent(user_query: str, user_id: str) -> str:
    """Process a pricing query with three-phase SGR workflow."""

    llm = LLMClient()
    feature_store = HybridFeatureStore()

    # Build conversation history
    history = [
        {"role": "system", "content": build_routing_prompt(user_id)},
        {"role": "user", "content": user_query},
    ]

    # --- Phase 1: Routing (Uses RouterSchema) ---
    print(f"🤖 Processing: '{user_query}' for {user_id}")
    decision = llm.run_sgr(history, RouterSchema)
    print(f"📍 Routing decision: {decision.action.tool_name}")

    if decision.action.tool_name == "respond":
        return decision.action.content

    # --- Phase 2: Context Retrieval ---
    if decision.action.tool_name == "fetch_user_features":
        print(f"🔍 Fetching features for {user_id}...")
        context = feature_store.get_user_context(user_id)

        if not context:
            return "Error: User profile not found."

        print(f"   [Data] LTV: ${context.get('user_ltv')} | "
              f"Margin: {context.get('cart_profit_margin', 0) * 100}%")

        # Inject context into conversation
        history.append({"role": "assistant", "content": ASSISTANT_FETCH_MESSAGE})
        history.append({
            "role": "user",
            "content": build_pricing_context_prompt(
                churn_prob=context.get("churn_probability", 0.5),
                cart_val=context.get("current_cart_value", 100),
                margin=context.get("cart_profit_margin", 0.2),
                user_ltv=context.get("user_ltv", 0),
            ),
        })

        # --- Phase 3: SGR Logic Execution (Uses PricingLogic) ---
        print("🧠 Calculating Offer (Schema Enforced)...")
        offer = llm.run_sgr(history, PricingLogic)

        # Audit log — the SGR benefit: explicit reasoning traces
        print(f"   [Audit] Math: {offer.margin_math}")
        print(f"   [Audit] Max Allowed: {offer.max_discount_percent}%")

        return offer.customer_message

    return "I'm sorry, I couldn't process your request."


if __name__ == "__main__":
    response = pricing_agent("I want a discount or I'm leaving!", "user_102")
    print(f"\n💬 Final Reply: {response}")

Лучшие практики

Проектирование схем

  1. Располагайте поля в соответствии с потоком ризонинга: поля анализа должны идти перед полями принятия решений.
  2. Пишите описательные Field. Они направляют внимание модели не менее эффективно, чем названия полей.
  3. Вводите ограничения с помощью Literal и Annotated. Для перечислений используйте Literal["a", "b"], а для заданий диапазонов — Annotated[int, Ge(1), Le(10)].
  4. Сохраняйте схемы лаконичными. Одна схема на этап ризонинга, затем их комбинируют с помощью нескольких вызовов.

Настройка vLLM

  1. Используйте низкую температуру (0,1–0,3) для обеспечения детерминистичного ризонинга.
  2. Позвольте xgrammar самостоятельно обрабатывать структуру. Не пытайтесь противостоять ему указаниями по форматированию в системном промпте.
  3. Контролируйте количество токенов. SGR обычно использует меньше токенов, чем CoT, поскольку не требует длинных описательных текстов.

Аспекты производственной эксплуатации

  1. Версионируйте схемы так же, как и API.
  2. Даже при использовании SGR сетевые и серверные ошибки всё равно требуют корректной обработки.
  3. Фиксируйте необработанные выходные данные SGR для целей соответствия стандартам и отладки.
  4. Тестируйте на крайних случаях, чтобы схема корректно работала на границах допустимых значений.

Заключение

SGR позволяет перейти от ситуации «работает в демо» к ситуации «работает в продакшене». Вы определяете топологию ризонинга с помощью Pydantic, позволяете xgrammar её реализовывать во время декодирования, в результате чего получается:

  • результат, всегда корректный, без необходимости в циклах повторных попыток или сбоев парсинга;
  • возможность аудита на уровне отдельных полей;
  • использование более мелких моделей, поскольку им больше не нужно самостоятельно соблюдать формат;
  • снижение затрат на выполнение, благодаря меньшему количеству токенов, попыток и размеру моделей.

Демо-проект sgr-discount-manager связывает все примеры кода из этой статьи с реальным сервером vLLM. Клонируйте его и начните адаптировать схемы под собственный рабочий процесс.

Основные выводы

  1. Метод Schema-Guided Reasoning делает топологию ризонинга явной, вместо того чтобы полагаться на следование моделью описательным текстам.
  2. Ограничения при декодировании предотвращают появление некорректного JSON на этапе генерации, что проще, чем последующая валидация и повторные попытки.
  3. Размещайте поля анализа перед полями принятия решений, если схема должна обязать модель сначала проанализировать данные, а уже затем выдавать результат.
  4. Используйте SGR тогда, когда последующий код зависит от строгой структуры, а не когда требуется свободный формат текста.
