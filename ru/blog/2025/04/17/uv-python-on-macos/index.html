uv на macOS: управление версиями Python, проектами и инструментами

Viacheslav Dubrov

2025-04-17 · Обновлено 2026-07-17 · 6 мин · Инструменты разработчика

Автоматический перевод Эта статья была автоматически переведена с оригинальной английской версии.

Я перевёл свой Python-воркфлоу на uv. Он заменил переключение между pip, виртуальными окружениями, pip-tools, pipx и менеджерами проектов. Теперь большую часть этой работы покрывает один исполняемый файл.

При этом сами воркфлоу остаются разными. У проекта, скрипта с inline-метаданными, CLI для разовой задачи и установленного CLI — собственные окружение и жизненный цикл. В этом руководстве показаны используемые мной команды и границы между этими сценариями.

Это руководство предназначено для Python-разработчиков на macOS, которые заменяют воркфлоу на базе pip, виртуальных окружений, pip-tools или pipx на uv. После его прочтения вы сможете выбрать подходящее окружение uv для проекта, автономного скрипта, разового инструмента или команды, которая должна оставаться на PATH.

Быстрый старт

# Install uv with Homebrew
brew install uv

# Start a project
uv init example-app
cd example-app
uv add httpx
uv run python main.py

# Run an isolated CLI without installing it permanently
uvx ruff check .

Кратко. В проектах я использую uv add, uv lock, uv sync и uv run. Для автономных скриптов я использую метаданные PEP 723, для разовых инструментов — uvx, а для команд, которые должны оставаться на uv tool install, — PATH. В CI команда --locked проверяет, что метаданные проекта соответствуют uv.lock. Команда --frozen доверяет существующему lock-файлу и не проверяет его актуальность.

Устанавливайте uv, назначив одного владельца

Homebrew — удобный способ установить uv на macOS. Поддерживаемые методы описаны в руководстве по установке uv:

brew install uv
uv --version

Если uv установил Homebrew, обновлять его также должен Homebrew:

brew upgrade uv

uv self update относится к автономному способу установки uv и отключена для установок через менеджеры пакетов. Не допускайте, чтобы два установщика конкурировали за один и тот же исполняемый файл.

Полезные команды для проверки установки:

command -v uv
uv python dir
uv tool dir
uv cache dir

У управляемых установок Python, постоянных инструментов и одноразовых записей в кэше разные директории. Кэш можно удалить и пересоздать. Он не является источником истины.

Проекты: декларации, разрешение зависимостей и окружение

Обычно у проекта uv есть три артефакта:

  • pyproject.toml содержит метаданные проекта и прямые зависимости.
  • uv.lock хранит кроссплатформенное разрешение зависимостей uv.
  • .venv — локальное установленное окружение, которое должно быть одноразовым.

Создайте приложение и добавьте зависимости для рантайма и тестов:

uv init forecast-app
cd forecast-app

uv add httpx
uv add --group test pytest
uv run python main.py
uv run --group test pytest

Текущие шаблоны приложений uv создают main.py, pyproject.toml, README.md и .python-version. По умолчанию они не задают build-систему. Используйте uv init --lib для упаковываемой библиотеки со структурой src и бэкендом сборки.

uv run проверяет проект, при необходимости обновляет lock-файл, синхронизирует нужные зависимости и запускает команду. Подробнее об этом жизненном цикле см. в документации uv по структуре проекта и синхронизации. Первая операция над проектом при необходимости создаёт .venv и uv.lock. Сама команда uv init создаёт только файлы проекта.

Коммитьте входные данные, а не окружение

Коммитьте pyproject.toml, uv.lock, исходный код и осознанно выбранный .python-version. Добавьте .venv и кэши uv в ignore.

Lock-файл фиксирует разрешение зависимостей для поддерживаемых маркеров и платформ. Он не делает нативные wheel-пакеты одинаковыми на macOS, Linux, Intel и Apple Silicon. Тестируйте каждую платформу деплоя.

Актуальность lock-файла: --locked — это не --frozen

Byte says

Я использовал --frozen в CI, чтобы пропустить разрешение зависимостей. Вместе с ним пропустилась и проверка расхождений. Lockfile месяц отставал от pyproject.toml, и ничего не стало красным.

По умолчанию команды проекта могут обновлять uv.lock при изменении деклараций. О настройках проверки актуальности и точности см. в документации uv по блокировке и синхронизации.

Используйте --locked, чтобы требовать актуальности lock-файла относительно метаданных проекта:

uv lock --check
uv sync --locked
uv run --locked pytest

Если pyproject.toml и uv.lock расходятся, эти команды завершаются с ошибкой вместо создания нового lock-файла. Обычно именно такую проверку и следует использовать как CI-гейт.

Используйте --frozen только когда намеренно хотите, чтобы uv использовал существующий lock-файл без проверки его актуальности:

uv sync --frozen

Это может быть полезно на контролируемом этапе сборки, где lock-файл уже прошёл проверку, но такая команда не обнаруживает устаревшие lock-файлы.

Точность — отдельная настройка, не связанная с актуальностью. uv sync по умолчанию выполняет точную синхронизацию и удаляет лишние пакеты. uv run по умолчанию выполняет неточную синхронизацию, если не передан --exact.

Управляемый Python: запрос версии, а не универсальный бинарник

uv умеет скачивать дистрибутивы Python и управлять ими:

uv python install 3.12 3.13
uv python list --only-installed
uv python pin 3.12

Управляемые сборки CPython в uv поставляются проектом python-build-standalone. Кроме того, uv умеет находить системные интерпретаторы, интерпретаторы из Homebrew, pyenv, Conda и других источников. Поддерживаемые источники и поведение при поиске описаны в документации uv по версиям Python.

.python-version — это запрос версии, который распознают uv и другие совместимые инструменты. requires-python в pyproject.toml — контракт совместимости проекта. Оба параметра должны быть выбраны осознанно:

[project]
requires-python = ">=3.12,<3.14"

Фиксация 3.12 не гарантирует одну и ту же patch-сборку навсегда или один и тот же артефакт на всех операционных системах. Если нужна конкретная patch-версия, запросите её явно, а в CI выбирайте интерпретатор и явно выводите информацию о нём.

Используйте другой менеджер Python, если проекту нужен дистрибутив или конфигурация сборки, которых uv не предоставляет. При этом uv всё равно может использовать этот интерпретатор через --python или обычный механизм поиска.

Выбор между uv run, uvx и установленными инструментами

Инструменты, связанные с проектом: uv run

Если pytest, mypy, генератор кода или другой инструмент должен импортировать проект либо использовать его зафиксированные плагины, объявите его в группе зависимостей:

uv add --group lint ruff
uv run --group lint ruff check .

Запуск такого инструмента через uvx изолирует его от проекта и может скрыть установленный пакет или нужные ему плагины.

Инструменты для разовых задач: uvx

uvx — это алиас для uv tool run. Команда создаёт изолированное окружение в одноразовом кэше uv. В документации uv по инструментам описаны этот кэш и жизненный цикл постоянных инструментов:

uvx ruff@0.12.0 check .
uvx --from jupyterlab jupyter lab
uvx --with mkdocs-material mkdocs --help

Фиксируйте версию инструмента в CI или документации. Первый запуск без указанной версии выбирает текущий релиз, а последующие запуски могут повторно использовать состояние кэша.

Постоянные исполняемые файлы: uv tool install

Установите инструмент, если скриптам, которые находятся вне вашего контроля, нужна его команда на PATH, или если манифест конфигурации машины должен управлять этой установкой:

uv tool install ruff
uv tool list
uv tool upgrade ruff
uv tool uninstall ruff

Постоянные инструменты по-прежнему используют изолированные окружения. Не изменяйте эти окружения вручную через pip.

Скрипты: сделайте один файл единицей поставки

PEP 723 определяет inline-метаданные скрипта. Совместимый раннер может прочитать блок комментариев и создать изолированное окружение. Формат метаданных и поведение раннера описаны в руководстве uv по скриптам и PEP 723.

# /// script
# requires-python = ">=3.12"
# dependencies = [
#   "httpx>=0.27,<1",
# ]
# ///
import httpx

response = httpx.get("https://example.com", timeout=10)
response.raise_for_status()
print(response.status_code)

Запускайте скрипт и редактируйте метаданные с помощью uv:

uv run fetch.py
uv add --script fetch.py rich
uv remove --script fetch.py rich

Обычный python fetch.py игнорирует метаданные в комментариях. Поэтому скрипт зависит от совместимого раннера, хотя синтаксис Python остаётся валидным.

Если скрипт должен позднее воспроизводить то же разрешение зависимостей, создайте рядом с ним lock-файл:

uv lock --script fetch.py
uv run --script fetch.py

Это создаёт fetch.py.lock. Метка времени exclude-newer может ограничить даты дистрибутивов-кандидатов, но это слабее, чем точное зафиксированное разрешение, и не гарантирует, что артефакт останется доступным.

Используйте проект, если несколько файлов используют общие зависимости, код импортируется как пакет, тестам нужно состояние проекта или несколько скриптов должны перемещаться вместе.

Файлы requirements: совместимость, а не гарантия отказоустойчивости

Файл requirements.txt может содержать неточные входные данные, точные версии, хэши, ограничения, индексы, URL или экспорт requirements, созданный резолвером. Его воспроизводимость зависит от способа создания и использования. Одно имя файла ничего не говорит о его свойствах.

Используйте совместимый с pip интерфейс uv без миграции:

uv venv
uv pip sync requirements.txt
uv run python app.py

uv pip sync приводит окружение в соответствие с файлом. uv pip install -r только добавляет зависимости.

Для приложения, которым вы управляете, может быть полезна поэтапная миграция:

uv init --bare
uv add -r requirements.in
uv add --group test -r requirements-test.in
uv lock
uv sync --locked

Прежде чем удалять старые файлы, прогоните полный путь тестирования и деплоя. Если downstream-система по-прежнему ожидает формат pip, создайте его из проверенного lock-файла uv с помощью команды экспорта uv:

uv export --format requirements.txt \
  --output-file requirements.txt

Не поддерживайте uv.lock и экспорт, отредактированный вручную, как два конкурирующих разрешения зависимостей.

Кэш, индексы и границы цепочки поставки

Кэш uv ускоряет повторные установки, но остаётся одноразовым:

uv cache prune
uv cache clean

Для обычной очистки предпочтительнее prune. clean удаляет все записи кэша, после чего последующие скачивания и сборки выполняются заново.

Lock-файл повышает воспроизводимость. Он не делает зависимости надёжными. Проверяйте источники пакетов, настройки индексов, Git-ревизии, бэкенды сборки, лицензии и учётные данные. Не храните конфигурацию аутентифицированных индексов в закоммиченных файлах. Исключение — несекретная ссылка на одобренный механизм получения учётных данных.

Для нативных пакетов фиксируйте архитектуру деплоя и проверяйте доступность wheel-пакетов. В противном случае резолвер может перейти к сборке из исходников, для которой нужны компиляторы и системные библиотеки, отсутствующие в CI или продакшене.

Краткий операционный чек-лист

Для каждого проекта:

  1. Определите requires-python и прямые зависимости в pyproject.toml.
  2. Разделяйте публикуемые extras и локальные группы зависимостей.
  3. Коммитьте uv.lock. Добавьте .venv и состояние кэша в ignore.
  4. Запускайте связанные с проектом инструменты через окружение проекта.
  5. Используйте uv lock --check или --locked в CI.
  6. Тестируйте каждую целевую ОС и архитектуру, представленную в lock-файле.
  7. Экспортируйте совместимые форматы только для явно указанных downstream-потребителей.
  8. Проверяйте политику источников и учётных данных независимо от разрешения зависимостей.

uv наиболее полезен, когда эти границы владения остаются видимыми. Один бинарник может управлять всеми сценариями, не превращая их в одно окружение. Инструментов становится меньше, а четыре воркфлоу остаются раздельными. Поэтому на macOS uv по-прежнему остаётся моим инструментом по умолчанию для Python-проектов.
