uv на macOS: управление версиями Python, проектами и инструментами

Я перешёл на рабочий процесс с использованием uv, так как он заменил необходимость постоянной смены инструментов — раньше я работал с pip, виртуальными средами, pip-tools, pipx и менеджерами проектов. Теперь один исполняемый файл покрывает большую часть этих задач.

Однако схемы работы остаются разными. У проекта, скрипта с встроенной метаинформацией, одноразового CLI-инструмента и установленного CLI-инструмента существуют свои собственные среды и жизненные циклы. В данном руководстве показаны команды, которые я использую, а также границы, разделяющие эти компоненты.

Быстрое начало

# Install uv with Homebrew
brew install uv

# Start a project
uv init example-app
cd example-app
uv add httpx
uv run python main.py

# Run an isolated CLI without installing it permanently
uvx ruff check .

# Run a script that declares PEP 723 dependencies
uv run fetch.py

Кратко. Внутри проектов я использую uv add, uv lock, uv sync и uv run; для самостоятельных скриптов применяется метаинформация по PEP 723; uvx предназначен для одноразовых инструментов; а uv tool install — для команд, которые должны оставаться на PATH. В средах CI --locked проверяет соответствие метаинформации проекта данным из uv.lock; --frozen доверяет существующему файлу lock без проверки его актуальности.

Установка uv с единственным источником

Для установки на macOS удобно использовать Homebrew:

brew install uv
uv --version

Если Homebrew уже установил uv, его следует обновить:

brew upgrade uv

uv self update предназначен для автономной установки uv и отключён при использовании менеджеров пакетов. Не допускайте конкуренции двух установщиков за один и тот же исполняемый файл.

Полезные команды для определения идентичности:

command -v uv
uv python dir
uv tool dir
uv cache dir

Управляемые установки Python, постоянные инструменты и временные элементы кэша хранятся в отдельных каталогах. Кэш можно удалять и восстанавливать заново; он не является источником истинных данных.

Проекты: объявление, разрешение зависимостей и среда

Обычно проект в uv содержит три разных типа файлов:

  • pyproject.toml содержит метаинформацию проекта и прямые требования к пакетам.
  • uv.lock хранит информацию о разрешении зависимостей в универсальном формате.
  • .venv представляет собой локальную установленную среду, которая должна быть временной.

Чтобы создать приложение, необходимо добавить требования к рантайму и тестам:

uv init forecast-app
cd forecast-app

uv add httpx
uv add --group test pytest
uv run python main.py
uv run --group test pytest

Текущие шаблоны приложений uv генерируют main.py, pyproject.toml, README.md и .python-version. По умолчанию они не определяют систему сборки. Для создания упакованной библиотеки с расположением по src и заданным движком сборки используйте uv init --lib.

uv run выполняет проверку проекта, при необходимости обновляет файл lock, синхронизирует требуемые зависимости и запускает указанную команду. При первой операции над проектом создаются .venv и uv.lock при необходимости; сам uv init создаёт только файлы проекта.

Фиксируйте входные данные, а не среду

Зафиксируйте в коммите pyproject.toml, uv.lock, исходный код и намеренно добавленный .python-version. Игнорируйте .venv и кэш uv.

Файл lock записывает информацию о разрешении зависимостей для всех поддерживаемых платформ и форматов; он не делает нативные версии пакетов идентичными на macOS, Linux, Intel и Apple Silicon. Обязательно тестируйте работу на каждой платформе развертывания.

Защита свежести блокировки: --locked не совпадает с --frozen

По умолчанию команды проекта могут обновлять uv.lock при изменении его настроек.

Чтобы обязать использование актуальной блокировки, согласованной с метаданными проекта, используйте --locked:

uv lock --check
uv sync --locked
uv run --locked pytest

Если pyproject.toml и uv.lock дают разные результаты, такие команды завершаются с ошибкой, вместо того чтобы создавать новую блокировку. Обычно это является полезным механизмом проверки в CI.

Используйте --frozen только тогда, когда вы намеренно хотите, чтобы uv использовал существующую блокировку без проверки её актуальности:

uv sync --frozen

Это может быть полезно на этапе контролируемой сборки, где блокировка уже была проверена, однако это не является инструментом обнаружения устаревших блокировок. uv sync по умолчанию работает в режиме точного сопоставления и удаляет лишние пакеты; uv run использует неточное синхронизированное поведение, если только не указано иное с помощью --exact.

Управляемый Python: запрос версии, а не универсальный бинарник

uv позволяет загружать и управлять дистрибутивами Python:

uv python install 3.12 3.13
uv python list --only-installed
uv python pin 3.12

Сборки CPython, управляемые uv, поставляются из проекта python-build-standalone. Кроме того, uv может обнаруживать системные интерпретаторы, а также те, что установлены через Homebrew, pyenv, Conda и другие инструменты.

.python-version представляет собой запрос на конкретную версию, обнаруженный uv и другими совместимыми инструментами. requires-python в pyproject.toml — это спецификация совместимости проекта. Оба этих элемента следует сохранять намеренно:

[project]
requires-python = ">=3.12,<3.14"

Фиксация 3.12 не гарантирует использование одной и той же версии патча навсегда или одного и того же артефакта на всех операционных системах. Запрашивайте точный патч только тогда, когда это действительно необходимо, и просите CI явно выбирать и указывать интерпретатор.

Используйте другой менеджер Python, если проекту требуется дистрибутив или конфигурация сборки, которые не предоставляетсь uv. В таких случаях uv всё равно может использовать данный интерпретатор через --python или обычный механизм обнаружения.

Выбор между uv run, uvx и установленными инструментами

Инструменты, связанные с проектом: uv run

Если pytest, mypy, генератор кода или другой инструмент должен импортировать файлы проекта или использовать его заблокированные плагины, необходимо указать его в группе зависимостей:

uv add --group lint ruff
uv run --group lint ruff check .

Запуск такого инструмента через uvx изолирует его от проекта, что может привести к скрытию необходимых установленных пакетов или плагинов.

Эпизодические инструменты: uvx

uvx является сокращением для uv tool run. Он создаёт изолированную среду, хранящуюся в временном кэше uv:

uvx ruff@0.12.0 check .
uvx --from jupyterlab jupyter lab
uvx --with mkdocs-material mkdocs --help

Укажите версию инструмента в CI или в документации. При первом запуске без указания версии выбирается текущая релизная версия, а последующие запуски могут использовать состояние кэша.

Постоянные исполняемые файлы: uv tool install

Устанавливайте инструмент тогда, когда скрипты, находящиеся вне вашего контроля, нуждаются в его командах для работы на PATH, или когда манифест машины явно указывает на его использование:

uv tool install 'ruff==0.12.0'
uv tool list
uv tool upgrade ruff
uv tool uninstall ruff

Даже при использовании постоянных инструментов создаются изолированные среды. Не вносите изменения в эти среды вручную с помощью pip.

Скрипты: делаем один файл единицей релиза

PEP 723 определяет структуру метаданных встроенных скриптов. Совместимый исполнитель может считывать блоки комментариев и создавать изолированную среду.

# /// script
# requires-python = ">=3.12"
# dependencies = [
#   "httpx>=0.27,<1",
# ]
# ///
import httpx


response = httpx.get("https://example.com", timeout=10)
response.raise_for_status()
print(response.status_code)

Для запуска и изменения метаданных используется утилита uv:

uv run fetch.py
uv add --script fetch.py rich
uv remove --script fetch.py rich

Обычный python fetch.py игнорирует метаданные в виде комментариев. Поэтому скрипт требует совместимого интерпретатора, даже если синтаксис Python остаётся корректным.

Если необходимо позже восстановить определённое решение, следует создать сопутствующий блокировочный файл:

uv lock --script fetch.py
uv run --script fetch.py

Это операция записывает fetch.py.lock. Временная метка exclude-newer может ограничивать диапазон возможных дат распространения, но она менее надёжна, чем точно зафиксированное решение, и не гарантирует доступности результатов работы.

Вместо этого следует использовать проектную структуру, когда несколько файлов имеют общие зависимости, код можно импортировать как пакет, тестам требуется состояние проекта, или несколько скриптов должны работать совместно.

Файлы с требованиями: совместимость, а не сбои

Файл requirements.txt может содержать разрешённые варианты входных данных, точные значения параметров, хэши, ограничения, индексы, URL-адреса или информацию о скомпилированной среде. Его воспроизводимость зависит от способа его создания и использования; одного только имени файла недостаточно для понимания характеристик.

Рекомендуется использовать интерфейс uv, совместимый с pip, без необходимости миграции:

uv venv
uv pip sync requirements.txt
uv run python app.py

uv pip sync приводит среду в соответствие с содержимым файла, тогда как uv pip install -r выполняет функцию дополнения настроек.

Для собственных приложений может оказаться полезной поэтапная миграция:

uv init --bare
uv add -r requirements.in
uv add --group test -r requirements-test.in
uv lock
uv sync --locked

Перед удалением старых файлов необходимо выполнить полный цикл тестирования и развертывания. Если последующая система всё ещё ожидает формат, характерный для pip, его можно получить на основе проверенного блокировочного файла uv:

uv export --format requirements.txt \
  --output-file requirements.txt

Не следует поддерживать одновременно uv.lock и вручную отредактированный вариант экспорта как два конкурирующих решения.

Кэш, индексы и границы цепочки поставок

Кэш uv ускоряет повторные установки, но он является временным решением:

uv cache prune
uv cache clean

Для регулярной очистки предпочтительнее использовать prune. Утилита clean удаляет все записи из кэша, что принудительно запускает последующие загрузки и сборки.

Файл блокировки повышает воспроизводимость, но не делает зависимости абсолютно надёжными. Необходимо тщательно проверять источники пакетов, настройки индексов, версии Git, среды сборки, лицензии и учётные данные. Не следует сохранять информацию об авторизованных настройках индекса в коммитируемых файлах, если в репозитории хранятся только несекретные ссылки на одобренные механизмы аутентификации.

Для нативных пакетов важно задокументировать архитектуру развертывания и проверить наличие тестовых версий в формате wheel. В противном случае инструмент разрешения зависимостей может обратиться к сборке из исходного кода, которая требует компиляторов и системных библиотек, отсутствующих в средах CI или продакшена.

Компактный чек-лист для работы

Для каждого проекта:

  1. Определите requires-python и прямые зависимости в pyproject.toml.
  2. Разделите публикуемые дополнения от локальных групп зависимостей.
  3. Закоммитируйте uv.lock; игнорируйте .venv и состояние кэша.
  4. Запустите инструменты, связанные с проектом, внутри его среды.
  5. В средах CI используйте uv lock --check или --locked.
  6. Протестируйте работу на всех целевых ОС и архитектурах, указанных в файле блокировки.
  7. Экспортируйте форматы с информацией о совместимости только для определённых потребителей.
  8. Проверяйте источники кода и правила обработки учётных данных независимо от выбранного решения.

uv наиболее эффективен, когда эти границы ответственности остаются чётко видимыми. Один бинарный файл может управлять всеми аспектами без необходимости объединения всего в одну среду. Именно такое сочетание — минимум инструментов без принуждения всех рабочих процессов к единым стандартам — делает его моим предпочтительным инструментом для работы с Python-проектами на macOS.
