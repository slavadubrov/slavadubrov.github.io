Melhores padrões de segurança para agentes de AI: permissões e sandboxes

Viacheslav Dubrov

2026-06-08 · 3 min · Agentes de IA

Tradução automática Este artigo foi traduzido automaticamente a partir da versão original em inglês.

A segurança dos agentes consiste em controlar as ações. Um chatbot pode dar uma resposta errada. Um agente pode usar credenciais reais, chamar uma ferramenta e alterar dados de produção.

A regra predefinida é simples: não dê a um agente capacidades de que não necessita. Comece por ferramentas restritas, verificações de políticas antes de cada tool call, sandboxes isoladas, credenciais limitadas, pontos de aprovação humana e rastreios de auditoria. Adicione também guardrails e filtros de saída, mas não os trate como o principal limite de segurança.

O que implementar primeiro

Comece por remover capacidades. Se o agente não precisa de escrever no GitHub, não lhe dê um token de escrita. Se só precisa de consultar a disponibilidade no calendário, não lhe conceda acesso integral à caixa de correio. Uma permissão restrita é mais segura do que um prompt severo.

Em seguida, verifique a política antes de cada tool call. Inspecione o nome da ferramenta, os argumentos, o recurso de destino, o utilizador, o ambiente e o efeito secundário. Um pedido aparentemente inofensivo pode, ainda assim, produzir um comando shell perigoso.

Adicione sandboxes para execução de código, automação de browser, acesso a ficheiros e processamento de documentos não fiáveis. Uma sandbox não torna a ação correta, mas reduz os danos resultantes de um resultado de ferramenta comprometido ou de um modelo confuso.

Utilize aprovação humana para ações irreversíveis. Não aprove cada passo. Aprove limites: deploys em produção, eliminação de dados, envios de emails, movimentação de dinheiro, alterações de permissões e decisões regulamentadas.

Riscos específicos do MCP

O MCP é útil porque normaliza o acesso a ferramentas. É arriscado porque as descrições das ferramentas, os esquemas, as identidades dos servidores, os âmbitos OAuth e os resultados das ferramentas passam todos a fazer parte do contexto de decisão do modelo.

Para o MCP, manteria estas regras no processo de revisão de código:

  • reveja as descrições e os esquemas das ferramentas antes da aprovação
  • prefira credenciais restritas por servidor
  • isole os servidores MCP não fiáveis das ferramentas sensíveis
  • esteja atento a alterações nas definições das ferramentas após a instalação
  • trate os resultados das ferramentas como entradas não fiáveis
  • registe todos os servidores, ferramentas, argumentos e resultados

Os guardrails não são suficientes

Os guardrails podem validar a entrada e a saída. Não resolvem o privilégio mínimo, o âmbito das credenciais, o sandboxing, o tool poisoning nem a política de aprovação. Mantenha-os, mas coloque-os depois da definição das capacidades e antes da saída visível para o utilizador.
