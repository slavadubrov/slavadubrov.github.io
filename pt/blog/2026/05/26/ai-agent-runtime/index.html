Este guia destina-se a engenheiros que fazem deployment de AI agents com tool use e que precisam de sobreviver a reinícios dos workers. Uma execução de um agent pode durar horas, mas o seu processo worker pode reiniciar a qualquer momento. O runtime mantém o estado da execução, executa as ferramentas e recupera se um tool call parar a meio. O modelo continua a escolher a ação seguinte. Para a maioria das equipas, comece com uma queue, um worker e um PostgreSQL checkpointer. Se não conseguir indicar quem é o responsável por cada job, o agent ainda é um protótipo.

O que é um AI agent runtime?

Um AI agent runtime é a infraestrutura que mantém um agent com tool use a funcionar depois de terminar uma chamada ao modelo. Armazena o estado da sessão, executa ferramentas, guarda checkpoints, gere secrets, escreve traces, aplica limites de custo e define como o serviço é deployed. O modelo escolhe a ação seguinte. O runtime decide onde essa ação é executada, regista o resultado e restaura a execução após uma falha. O harness decide se uma ação é permitida. Não é um store, mas a tabela inclui-o porque o runtime tem de o executar em algum lugar.

Execuções longas quebram as premissas de processos stateless

O Byte diz

Se o log da execução viver apenas na memória do worker, um deployment normal pode substituir o worker a meio da tarefa e apagar o histórico da execução.

Um endpoint de chat stateless pode manter o estado do request num único processo e descartá-lo depois da resposta. Uma execução longa de um agent atravessa reinícios de workers, deploys, resets de contexto e pausas para aprovação. O processo worker deixa de poder ser a fonte de verdade.

A equipa do OpenAI Codex relata a duração que estas execuções podem atingir no seu texto sobre harness engineering:

“Vemos regularmente execuções individuais do Codex a trabalhar numa única tarefa durante mais de seis horas (muitas vezes enquanto os humanos estão a dormir).”

A equipa de engenharia da Anthropic descreve o problema de estado correspondente em Effective harnesses for long-running agents:

“O desafio central dos agents de longa duração é terem de trabalhar em sessões discretas, começando cada nova sessão sem memória do que aconteceu anteriormente.”

Ambas as observações implicam o mesmo design de runtime: persistir o estado fora do worker e tornar os workers substituíveis.

A sessão tem de viver fora do processo worker. Um store durável regista chamadas ao modelo, intenções e resultados de ferramentas e aprovações, para que outro worker possa retomar no último ponto seguro após uma falha. Um efeito externo pendente precisa de reconciliação antes de essa retoma poder ser considerada segura. Os checkpoints também permitem ao runtime iniciar uma nova sessão de modelo quando a context window fica cheia, sem repetir todo o histórico. Nas palavras da Anthropic, as instâncias do harness tornam-se descartáveis e reiniciáveis; o estado durável vive noutro lugar.

Cinco primitivas a colocar antes de fazer deployment

O texto da Anthropic sobre Scaling Managed Agents fornece um vocabulário útil para cinco responsabilidades do runtime. O harness faz o agent avançar, enquanto a sessão regista o que ele fez e o sandbox executa os comandos. O checkpoint fornece ao worker seguinte um ponto de retoma; o trace preserva evidência para debugging posterior. Uma implementação pode combinar componentes, mas as responsabilidades e os limites de falha continuam a precisar de nomes.

Sessão. Um append-only event log escrito separadamente, com chamadas ao modelo, tool calls solicitados e concluídos, erros e aprovações. Uma checkpoint database ajuda na recuperação, mas o histórico do graph state não substitui este log.

A palavra é ambígua, por isso este artigo usa um esquema de nomes ao nível da aplicação para três spans. Um thread é a conversação de um utilizador ao longo de vários dias. É o span com maior duração e pode conter muitas execuções.

Uma sessão do modelo é a mais curta: um período contínuo de contexto do modelo. A compaction — o passo que resume a window para que o trabalho possa continuar — prolonga uma sessão do modelo em vez de a terminar. Um reinício ou um novo início deliberado terminam-na. A Parte 6 usa “sessão do modelo” nesse sentido.

Neste artigo, “sessão” significa o log durável de uma execução. Várias sessões do modelo podem escrever no mesmo log, e uma thread de conversação pode conter vários logs de execução. Para recuperar, acorde a execução, carregue a sua sessão, reconcilie qualquer efeito secundário pendente e retome depois do último evento: wake(sessionId) → getSession(id) → reconcile pending effects → resume from last event.

No LangGraph, thread_id é a chave de armazenamento e recuperação do checkpointer para o histórico de graph state de uma thread (consulte LangGraph persistence); não define os limites de conversação, sessão do modelo ou event log deste artigo. Dê ao event log o seu próprio ID durável de execução ou sessão e escolha explicitamente como esses IDs são mapeados para threads do LangGraph. O OpenAI Agents SDK inclui dez session backends integrados, incluindo SQLiteSession, RedisSession, SQLAlchemySession, MongoDBSession e EncryptedSession (consulte a documentação de Sessions). Estes mantêm um histórico mutável da conversação, incluindo remoção, limpeza e compaction; mapeie um SDK session ID para o run-event ID se for útil, mas não trate o histórico do SDK como log de recuperação ou auditoria append-only sem uma garantia equivalente de imutabilidade.

Harness. O loop de orchestration e a única primitiva aqui que toma decisões. Monta o prompt a partir da memória, chama o modelo, verifica o tool call proposto contra as suas regras de permissão, despacha o que permite, escreve os resultados de volta na sessão, aplica regras de retry e decide se a tarefa terminou. Os auxiliares de planeamento e a gestão de contexto codificam pressupostos sobre a capacidade do modelo. A autorização e o isolamento obrigatórios também implementam requisitos que continuam em vigor à medida que os modelos melhoram. A Anthropic salienta diretamente esse ponto — é citado na secção sobre modos de falha abaixo, que trata sobretudo do que acontece quando esses pressupostos ficam desatualizados.

A equipa do OpenAI Codex chama a isto harness engineering: escrever software continua a exigir esforço de engenharia, mas agora uma parte maior desse esforço é aplicada ao scaffolding e não ao código em si. O CompiledStateGraph do LangGraph, o Deep Agents da LangChain e o seu ponto de entrada create_deep_agent, bem como o próprio Claude Code, são todos harnesses neste sentido.

Sandbox. O ambiente de execução isolado onde os comandos são realmente executados. A página de sandbox concepts do OpenAI Agents SDK atribui as aprovações, tracing, handoffs e o estado necessário para retomar execuções ao runtime exterior. Atribui os comandos, alterações a ficheiros e isolamento do ambiente à sessão do sandbox.

“Runtime exterior” significa aí o harness juntamente com os seus state stores. No vocabulário desta série, as aprovações e os handoffs são decisões do harness (Parte 4 e Parte 6); o tracing e o controlo da retoma são as primitivas de sessão e checkpoint.

Os sandboxes diferem no tempo que permanecem ativos e no que recordam entre execuções. A forma mais simples é fresh ephemeral: criar um para uma única tarefa, destruí-lo quando a tarefa termina e suportar o custo de cold start em cada execução.

Os sandboxes persistent paused mantêm o sistema de ficheiros e um snapshot de memória entre execuções. A retoma seguinte pode evitar um arranque completo. Snapshot ou fork cria uma imagem copy-on-write a partir de um parent preparado, permitindo que muitas tarefas partilhem dependências instaladas e caches quentes sem partilharem o seu estado gravável.

Os workspaces per-worktree dão às tarefas checkouts separados; Git worktrees partilham a infraestrutura do repositório e não são OS sandboxes. Restrinja a execução separadamente com um container, VM ou política de processos. Uma aplicação por tarefa também pode ter a sua própria stack de observability. Logs, métricas e traces separados permitem fazer debugging de uma execução sem que o seu estado contamine outra. A tabela de providers mais à frente neste artigo compara os contratos de isolamento e persistência.

Checkpoint. O estado necessário para retomar: que nó do graph foi executado, os seus valores mais recentes e o que deve ser executado a seguir. Um event log responde ao que aconteceu: as ações solicitadas e os seus resultados. Um checkpoint não pode reconstruir eventos que o harness nunca registou.

O PostgresSaver do LangGraph escreve um Checkpoint em cada fronteira de super-step. Um super-step é uma ronda do graph, composta por um único nó ou por um batch executado em paralelo. As escritas por tarefa vão para checkpoint_writes, pelo que os outputs de nós concluídos não são recalculados quando um nó irmão falha.

Um checkpoint é um dict simples (v, id, ts, channel_values, channel_versions, versions_seen, updated_channels). O LangGraph serializa-o com o seu JsonPlusSerializer baseado em msgpack, e não com JSON. datetime, set, Decimal e dataclasses fazem round-trip. O formato está documentado na página langgraph-checkpoint-postgres do PyPI e na referência de checkpoints do LangGraph.

StateSnapshot é a vista separada e mais rica que graph.get_state() constrói sobre um checkpoint. Um debug bundle pode exportar o seu .values como o último graph state conhecido; não pode reconstruir detalhes de eventos que o harness nunca registou.

Trace. A superfície de debugging e auditoria. Cada chamada ao modelo, tool call e passo de sub-agent deve emitir timing, estado, modelo e provider, IDs de correlação, contagens de tokens e custo. Prompts, completions, argumentos de ferramentas e resultados de ferramentas são conteúdo opt-in: as orientações GenAI do OpenTelemetry usam metadata por omissão porque esses campos podem conter dados sensíveis. Capture-os apenas depois de decidir a redação ou filtragem, os controlos de acesso e a retenção aplicáveis. Quando uma execução de seis horas falha, o trace é o que lê para perceber o que correu mal. Pode apoiar uma investigação, mas o event log e o estado do checkpoint, juntamente com o tratamento de idempotency, são o que permite uma retoma ou replay seguro. Nessa altura, o output do terminal da execução já desapareceu há muito. As GenAI semantic conventions do OpenTelemetry normalizam os nomes dos atributos (qual foi o modelo, qual foi o provider, quantos tokens, qual a conversação, qual o workflow). Para um destino compatível com OTLP que suporte estas convenções, a mesma instrumentação pode exportar o trace para sistemas como Tempo, Jaeger, Honeycomb ou LangSmith, embora possam continuar a ser necessários adapters do backend ou configuração específica do destino.

Política e secrets atravessam as primitivas

Duas fronteiras atravessam as cinco primitivas. São a versão de runtime do argumento de segurança da Parte 4. A decisão de permissão pertence ao harness; o que se segue indica onde se encontra fisicamente a maquinaria que a aplica e alimenta.

Aplicação de permissões

A permission ladder da Parte 4 precisa de um lugar onde ser executada. A verificação ocorre antes de cada tool call e decide se este avança. Dois padrões são comuns em produção. O filesystem-permission middleware do Deep Agents pode limitar os filesystem tools integrados a caminhos declarados. Não controla comandos shell do sandbox, ferramentas customizadas ou chamadas MCP; aplique essas regras na política do sandbox ou atrás do seu próprio tool proxy. O Anthropic Managed Agents encaminha chamadas para ferramentas MCP customizadas através de um proxy que detém as credenciais. A execução de comandos do sandbox e a autenticação Git usam caminhos separados; o proxy MCP não é um interceptor universal para todas as ações. Quando uma chamada sensível requer aprovação humana, o interrupt() do LangGraph e o approval hook do Deep Agents pausam o graph até uma pessoa dizer que sim.

Secret broker

O modelo não deve ver secrets de longa duração e, normalmente, o sandbox também não deve vê-los. O padrão Managed Agents é o que deve copiar:

“Para Git, usamos o access token de cada repositório para clonar o repositório durante a inicialização do sandbox e ligamo-lo ao remote Git local. O Git push e pull funcionam a partir do sandbox sem que o agent alguma vez manipule o token. Para ferramentas customizadas, suportamos MCP e armazenamos OAuth tokens num secure vault. O Claude chama ferramentas MCP através de um proxy dedicado; este proxy recebe um token associado à sessão. … O harness nunca toma conhecimento de quaisquer credenciais.”

Na stack de referência market-analyst-agent — um pequeno LangGraph agent que obtém dados de mercado e escreve um relatório de analista, desenvolvido ao longo desta série — o worker chama localmente as suas ferramentas de dados de mercado. O servidor MCP opcional exporta uma superfície de ferramentas; não é um credential broker implementado entre esse worker e os seus providers. Ambos os containers podem ler o .env de desenvolvimento partilhado. Um broker de produção exigiria mover as credenciais dos providers para um store que o worker não pudesse ler e encaminhar todas as chamadas relevantes através do broker.

Verificação da colocação

Uma verificação prática consiste em anotar todos os componentes e qual das cinco primitivas cada um implementa. Postgres pode abranger sessão e checkpoint. O worker container é o harness. Um serviço como Daytona, Modal ou E2B fornece o sandbox, enquanto Tempo ou LangSmith armazena o trace.

Depois, inspecione as falhas acopladas. Se duas primitivas viverem no mesmo processo, uma única falha derruba ambas. Se partilharem uma credencial, uma fuga atravessa as duas fronteiras. Exemplos comuns incluem um worker que também detém a durabilidade do trace ou um token de sidecar que também desbloqueia a checkpoint database.

Modos de falha de um AI agent runtime em produção

O runtime gere retries, restaura trabalho anterior, isola workspaces e aplica budgets. À medida que as execuções se prolongam por vários workers e context windows, as falhas passam a concentrar-se no estado, efeitos secundários duplicados, drift do sandbox e ultrapassagens de budget.

As falhas dividem-se em quatro grupos:

  • Falhas de qualidade do output: o agent declara vitória antes de o trabalho estar realmente concluído, esquece o que fez após um reset da context window ou confia na sua própria autoavaliação e publica output com erros.
  • Falhas de controlo de custos: o agent fica preso num retry loop ou consome um token ou tool-call budget sem produzir algo útil.
  • Falhas de estado e crashes: os workspaces sofrem drift porque uma execução altera ficheiros pertencentes a outra, os tool calls são executados mais do que uma vez porque os retries os repetem ou o trabalho perde-se quando um worker morre entre eventos.
  • Falhas da context window: o modelo faz um resumo e termina cedo porque pensa que está a ficar sem espaço, mesmo quando a window ainda tem margem.

A tabela associa cada falha a uma mitigação, à base da recomendação e ao runtime hook que a aplica. O comportamento específico do modelo pode mudar, por isso trate as observações dos vendors como motivos para voltar a testar a premissa e não como regras permanentes.

Duas ideias estão por trás da maioria destas linhas. A Anthropic, sobre a obsolescência do harness em Harness design for long-running application development:

“Cada componente de um harness codifica um pressuposto sobre aquilo que o modelo não consegue fazer sozinho, e vale a pena testar esses pressupostos sob stress, tanto porque podem estar errados como porque podem ficar rapidamente desatualizados à medida que os modelos melhoram.”

A Vercel, sobre o problema relacionado de demasiadas ferramentas codificarem demasiados pressupostos, em We removed 80% of our agent’s tools:

“Eliminámo-las na sua maioria e reduzimos o agent a uma única ferramenta: executar comandos bash arbitrários. Chamamos-lhe um file system agent.”

A citação descreve o núcleo bash; o agent que a Vercel publicou manteve duas ferramentas, ExecuteCommand e ExecuteSQL, substituindo um exemplo de código antigo que nomeava dezassete ferramentas. A Parte 3 cobre o antes e depois completo. O resultado reportado nas cinco queries representativas foi: o sucesso passou de 4/5 para 5/5 e o pior caso desceu de 724 s / 100 passos / 145,463 tokens (falhou) para 141 s / 19 passos / 67,483 tokens (teve sucesso). Essa linha do pior caso é a mais dramática; na média das cinco queries, a poupança de tokens foi de 37%. A lição não é “elimine as suas ferramentas”. A assistência opcional pode tornar-se redundante à medida que o comportamento do modelo muda. Volte a testar o pressuposto quando o modelo mudar.

A Cognition observou o mesmo alvo móvel na duração da sessão com o Sonnet 4.5. Em Rebuilding Devin for Claude Sonnet 4.5 descreve um modelo que escreve proativamente SUMMARY.md / CHANGELOG.md quando deteta que o contexto está a esgotar-se, mas subestima quantos tokens ainda lhe restam. A solução foi ativar o contexto de 1M tokens e limitar a utilização a 200k para que o modelo continuasse a acreditar que tinha margem. Quando foi escrita, essa opção estava em beta.

A documentação de context window da Anthropic, verificada em 6 de setembro de 2026, lista o Sonnet 5 e o Opus 5 com 1M tokens por omissão; o Sonnet 4.5 permanece nos 200k. Os modelos Sonnet atuais recebem automaticamente atualizações sobre o contexto restante, e a compaction no lado do servidor está disponível em beta para os modelos Claude 4.6 e posteriores. Antes de copiar o limite histórico da Cognition, teste o modelo selecionado com os controlos de contexto suportados. Uma window ou budget counter maior não garante uma recuperação fiável, e nenhum dos dois substitui progresso durável fora do modelo.

A equipa de harness da OpenAI tem a versão numa linha: “Os humanos orientam. Os agents executam.” Quando algo falha, a pergunta útil é qual a capacidade que falta e como tornar essa capacidade simultaneamente legível e aplicável pelo agent.

O lifecycle saudável de uma execução

Uma execução bem comportada é aborrecida. É uma cadeia de pequenos passos recuperáveis, e cada passo concluído escreve estado durável antes de o seguinte começar.

Escrever cada resultado antes de iniciar o passo seguinte limita os danos de um crash. Um efeito externo em curso é a exceção: um worker pode falhar depois de o provider fazer commit e antes de o harness registar o resultado. O worker seguinte tem de reconciliar esse efeito pendente antes de retomar a partir do último passo concluído.

  1. Arranque a partir de uma sessão nova ou retomada. Ao retomar, monte o workspace a partir do seu último estado conhecido, leia quaisquer ficheiros de progresso deixados pela tentativa anterior (PROGRESS.md, feature-list.json), carregue o último checkpoint e inspecione o event log à procura de tool intents pendentes. Reconcilie qualquer efeito externo pendente antes de fazer outra chamada ao modelo ou ferramenta.
  2. Planeie antes de executar qualquer tool call. Registe qual é o aspeto de “done”, quanto a execução pode gastar, que ferramentas o agent pode invocar e o que deve terminar a execução prematuramente. Estes valores do plano tornam-se runtime checks; sem eles, a execução não tem nada que a limite.
  3. Serialize ou coordene explicitamente os tool calls com efeitos secundários. A verificação de permissões do harness decide se cada um é permitido. Antes do dispatch, acrescente uma intenção pending com a respetiva idempotency key; depois de o provider retornar, acrescente o resultado. Chamadas independentes, read-only ou idempotentes podem ser executadas em paralelo quando cada uma tem o seu próprio registo durável de intent/result e os resultados são agregados de forma determinística. Se o worker morrer entre um efeito secundário e a escrita do resultado, retome consultando ou repetindo a chamada ao provider com a mesma key e acrescente o resultado recuperado ou needs_human. Por exemplo, o Stripe devolve o primeiro resultado guardado de um request para uma idempotency key repetida; outro provider precisa de um contrato equivalente de consulta ou retry.
  4. Faça checkpoint nas fronteiras de super-step ou, num harness mais simples, depois de cada evento. Persista o graph state, o workspace diff e referências para quaisquer artifacts produzidos. Este checkpoint é o que o passo 1 lê na retoma seguinte. Se o checkpoint estiver em falta ou desatualizado, a recuperação poderá ter de reconstruir o estado a partir do event log, o que é muito mais lento.
  5. Avalie os artifacts quando o agent considerar que terminou: testes, um evaluator com contexto novo, validação de schema e verificações no browser. Se a verificação passar, a execução termina com sucesso. Se falhar, a execução retoma a partir do último checkpoint limpo, com a mensagem de falha adicionada ao contexto, e tenta novamente.

Nenhum passo desta lista exige que o agent se lembre de alguma coisa entre execuções. O estado vive na sessão e no checkpoint, e o agent volta a lê-lo em cada retoma.

Persista um operation ID pertencente à aplicação antes do dispatch e associe-o aos argumentos aprovados. Reutilize-o para recuperar a mesma intenção de negócio, mesmo que o replanning produza um novo model tool-call ID. Registe esses IDs do modelo separadamente para correlação. As atualizações naturalmente idempotentes podem, em alternativa, precisar de uma precondition de versão. As orientações da AWS sobre retries explicam por que razão a identidade do request representa a intenção. Defina quando uma ação é genuinamente nova e durante quanto tempo a deduplicação dura: o Stripe permite eliminar keys após pelo menos 24 horas. Reconcilie payloads alterados e keys expiradas antes de tentar novamente.

Escolha um writer ativo ou um lease por thread. Para input que chegue durante uma execução, rejeite, coloque em queue, interrompa ou faça rollback explicitamente; o relato sobre o runtime do Deep Agents descreve estas opções. A cancellation tem de parar novos dispatches, registar o pedido e reconciliar efeitos em curso; matar o worker não desfaz uma chamada ao provider.

A aplicação do budget pertence ao lado do dispatch. Chamadas concorrentes não podem gastar a mesma allowance restante. Prometheus é um sistema de monitorização, não um ledger autoritativo de gastos por request. Reserve de forma conservadora e reconcilie a utilização real; o accounting atrasado do provider e a cancellation podem ainda causar overshoot.

Novos controlos do modelo ajudam a controlar o ritmo da execução, mas não são responsáveis pelo seu limite de gastos. O beta task budgets da Anthropic fornece aos modelos suportados da Messages API um budget consultivo ao longo de um loop agentic. Pode ser ultrapassado; max_tokens limita uma resposta, não toda a execução. O suporte depende do modelo: o Opus 5 suporta task budgets, enquanto o Sonnet 5 não. Mantenha o dispatch ledger e o caminho de cancellation mesmo quando o modelo recebe uma indicação de budget.

Os safety stops do provider precisam do seu próprio caminho terminal. Para o misalignment_policy_violation da OpenAI, pare o dispatch, retenha os registos correlacionados e peça revisão de um operador em vez de repetir. Trate erros de stream depois de output parcial e reconcilie efeitos anteriores; a Parte 4 explica o limite de monitorização.

A avaliação deve incluir evidência fora do contexto que produz o output. Um evaluator com contexto novo reduz o shared-context bias, enquanto testes, linters, verificações no browser e validação de schema fornecem evidência determinística. A verificação pode devolver pass, fail ou needs_human. Para code agents, o reviewer pode ser outra sessão do modelo com ferramentas read-only. Para agents de dados e relatórios, combine validação determinística com um reviewer model quando ainda for necessário julgamento.

Onze padrões de deployment de AI agents e o que determina a escolha

Depois de nomear as cinco primitivas, a questão é qual o deployment shape que as executa. Por “shape” entendo uma disposição dessas primitivas: onde vive o harness, onde persiste o estado e que tipo de sandbox executa o trabalho. Um shape é uma decisão de wiring, não uma escolha de vendor. O gráfico abaixo mostra em que pontos do eixo de duração cada shape é mais adequado. O texto seguinte explica o que determina a escolha.

Se só ler um dos onze, leia o shape 2: queue + worker + checkpoint DB. É o default que recomendo à maioria das equipas, o shape usado pelo repositório de referência e o esqueleto de que os restantes shapes variam: queue → worker → durable state, trocando a origem do sandbox, o owner do harness ou o state engine. Ler primeiro o shape 2 torna os restantes mais rápidos de consultar.

O gráfico compara os shapes pela duração das execuções. A matriz abaixo compara-os pela ownership: cada célula contornada identifica o componente que fornece essa primitiva.

1. SDK dentro de um app server (síncrono, com scope do request)

O shape original. O agent SDK corre dentro de um request handler. É adequado para tarefas inferiores a 30 segundos, demos e ferramentas internas. É inadequado para tudo aquilo de que um cliente HTTP se possa desligar. O HTTP timeout do Cloud Run chega no máximo aos 60 minutos e qualquer panic da web tier mata a execução. O SDK é o harness. A execução de ferramentas não confiáveis precisa de um sandbox separado e o estado costuma viver na memória do processo, a menos que seja explicitamente enviado para outro lugar. Não use este padrão para trabalho de várias horas.

2. Queue + worker + checkpoint DB

O default que recomendo à maioria das equipas e a implementação de demonstração com shape de produção em market-analyst-agent: um worker Python com um PostgreSQL checkpointer, Redis Streams (ou RabbitMQ) para a queue de entrada e um MCP sidecar para ferramentas. É adequado para execuções de 10 minutos a várias horas com passos idempotentes. O local runner pode ignorar a queue para desenvolvimento síncrono, mas a queue faz parte do shape de produção assim que forem necessários submissão assíncrona e backpressure.

No padrão de produção, a aplicação aceita um request, cria uma session row, coloca um job na queue e devolve um run ID. O worker obtém o job, executa o harness, escreve eventos de sessão e checkpoints, transmite o estado e armazena artifacts à medida que avança. O Postgres sobrevive, os workers são substituíveis e a profundidade da queue fornece backpressure. Compute Spot/Preemptible funciona desde que as escritas duráveis de eventos e checkpoints terminem antes de o worker reportar sucesso. O repositório associado ilustra esta topologia; a recuperação durável também depende dos leases da fila, da recuperação de jobs interrompidos e da confirmação do trabalho concluído.

Neste shape, o worker é o harness. O seu container e workspace por thread fornecem um limite de execução, mas o código não confiável continua a precisar de um sandbox hardened ou de uma VM. O event store é responsável pelo histórico da sessão; PostgresSaver é responsável pelo estado do checkpoint. Podem partilhar uma database apenas quando o harness escreve explicitamente ambos os schemas. Os traces passam pelo OpenTelemetry para a stack de observability que executar.

3. Durable workflow engine (ao estilo Temporal)

O código de orchestration do agent corre dentro de um Temporal Workflow; as chamadas ao modelo e às ferramentas correm como Activities. O estado do workflow vive num event-history log suportado por Cassandra, MySQL ou Postgres, permitindo replay através de falhas. Os deployments do workflow code que se sobrepõem a uma execução precisam de Worker Versioning ou patches seguros para replay; substituir código sem essa disciplina pode quebrar o replay. A integração Temporal × OpenAI Agents SDK, geralmente disponível desde março de 2026, inclui um OpenAIAgentsPlugin e um helper activity_as_tool, e o texto sobre agentic sandboxes descreve como fazer fork de um agent em execução para outro sandbox provider a meio de uma conversação. Workflows inativos consomem zero compute. As limitações são reais: agents realtime não são suportados, o streaming continua marcado como experimental e LocalShellTool e ComputerTool estão desativados porque não se adequam a um modelo distribuído.

Use este shape quando a execução tiver pontos reais de espera: aprovações humanas, callbacks externos, sleeps longos, retries com regras de negócio e janelas de deployment — e a equipa conseguir operar versioning de workflows seguro para replay. Uma aprovação humana torna-se um sleep durável que não consome compute, e não um polling loop.

O código do Workflow é o harness. O sandbox normalmente vive fora do Temporal e é chamado a partir de Activities. O estado da sessão e do checkpoint colapsa no event-history log do Temporal, enquanto a visibilidade do trace vem da Temporal UI mais spans OpenTelemetry em cada Activity.

4. Sandbox provider por sessão

Um shape mais recente. Cada execução do agent recebe a sua própria microVM ou container de um sandbox-as-a-service provider. O harness vive num local durável; o sandbox é o ambiente de execução descartável.

Escolha este shape quando o agent executar código não confiável, automação de browser, testes ou instalações de packages. O trade-off é um custo e um acoplamento ao provider superiores aos de executar workers partilhados.

O provider é responsável pelo sandbox e por mais nada. O harness, a sessão, o checkpoint e o trace permanecem do seu lado, normalmente ligados como o shape queue + worker do #2.

5. Anthropic Managed Agents (harness hosted)

A Anthropic lançou Managed Agents em public beta a 8 de abril de 2026, atrás do header beta managed-agents-2026-04-01. O serviço fornece uma sessão hosted, harness, sandbox e MCP proxy suportado por vault. wake(sessionId) pode inicializar o harness num novo worker sem perder o estado durável da sessão.

A Anthropic cobra os Managed Agents às tarifas normais de tokens mais $0.08 por hora de sessão. O billing tem granularidade de milissegundos e aplica-se apenas enquanto o estado da sessão for “running”; o tempo idle é gratuito. Um retry loop descontrolado acrescenta, portanto, custo de horas de sessão ao custo dos tokens.

Leia as limitações. O desconto da Batch API não se aplica (“As Sessions são stateful e interativas. Não existe modo batch.”). Managed Agents não está disponível através de AWS Bedrock ou Google Vertex AI. No beta, os túneis MCP e o “dreaming” do agent estão ainda atrás de uma research preview adicional cujo acesso tem de ser solicitado; a coordenação multi-agent e a autoavaliação com rubrics fazem parte da documentação do beta. O lock-in é elevado: troca liberdade no harness por não executar o loop por si próprio.

A configuração cloud por omissão coloca as cinco primitivas na Anthropic. Com self-hosted sandboxes, opera a execução, os filesystems e o network egress, enquanto a Anthropic executa a orchestration e o modelo. Os inputs e resultados das ferramentas continuam a chegar ao seu control plane; as skills e a memória associadas são armazenadas e sincronizadas aí. Ser responsável pela execução não torna todo o sistema self-hosted.

Claude Platform on AWS também suporta Managed Agents e self-hosted sandboxes; é separado do Bedrock. Nesse ambiente, uma sessão autónoma precisa de um user-role event para se reautenticar após seis horas e as sessões self-hosted não podem anexar memory stores. Os Managed Agents first-party não têm essas duas restrições. Verifique a plataforma e o modelo antes de copiar um design de sessão.

6. LangChain Deep Agents Deploy (harness aberto gerido)

deepagents deploy empacota um deepagents.toml num LangSmith Deployment com execução durável, memória, multi-tenancy, human-in-the-loop, observability, execução de código em sandbox e execuções agendadas. São suportados modos de deployment cloud, híbrido e self-hosted. Os sandbox providers (LangSmith Sandboxes, Daytona, Modal, Runloop ou custom) podem ser trocados através de um único valor de configuração. Os ficheiros e a memória do agent vivem num virtual filesystem com backends configuráveis; a persistência dos checkpoints é separada e a memória tem scope de user, assistant ou ambos. O lock-in é inferior ao dos Managed Agents: o harness é MIT-licensed, as instruções usam o standard aberto AGENTS.md e os agents são expostos através de MCP, do protocolo A2A (Agent2Agent) e do Agent Protocol. Consulte o texto da LangChain sobre runtime-behind-production-deep-agents.

Por omissão, as cinco primitivas são hosted, mas cada uma pode ser trocada por configuração. O sandbox fica atrás de um único valor de configuração. O memory filesystem é separado da persistência de threads e checkpoints. O trace vai para o LangSmith.

7. Serviço ou job no Google Cloud Run

O Cloud Run tem dois modos de runtime diferentes e o mais adequado depende da forma como o agent é invocado. Services estão ligados a HTTP e escalam para zero entre requests; o harness corre como request handler e retorna quando a execução termina. Jobs correm até à conclusão sem um HTTP entrypoint; o harness corre como um worker one-shot que termina quando a tarefa acaba. Ambos podem alojar o harness, mas nenhum mantém estado entre execuções. As sessões e os checkpoints têm de viver em Postgres, Spanner ou num store externo semelhante.

Os limites rígidos são muito diferentes. Cloud Run service request timeout: 300 s por omissão, máximo de 3.600 s (60 min). WebSockets têm o mesmo timeout. Cloud Run jobs: 10 min por tarefa por omissão, máximo de 168 h (7 dias); para tarefas que usam GPUs, máximo de 1 hora. O billing baseado em instâncias (CPU sempre alocada) continua a permitir scale-to-zero; o número mínimo de instâncias é uma definição separada; os jobs não têm HTTP e não fazem autoscale.

Use um service para execuções síncronas até 60 minutos. Use um job para trabalho one-shot ou assíncrono mais longo. Os Cloud Run Jobs podem manter uma tarefa ativa durante dias, mas não fornecem replay durável através de deploys, alterações de versão ou substituição de workers. Um workflow mais longo pode abranger várias execuções quando um orchestrator externo é responsável pelo progresso durável.

O Cloud Run aloja o harness. O estado da sessão e do checkpoint vive em Postgres, Spanner ou noutro store externo, e os traces podem passar pelo Cloud Logging e OpenTelemetry. O service container é um ambiente de execução; acrescente um sandbox separado quando o agent executar código não confiável.

8. AWS Lambda: invocações limitadas e workflows duráveis

O timeout máximo de uma função Lambda é 900 s (15 minutos), sem exceção. Se o API Gateway estiver à frente da função, o limite da integração depende do tipo de API. HTTP APIs permitem 30 segundos; as integrações REST têm por omissão 29 segundos, enquanto Regional e private REST APIs podem configurar um timeout mais longo. Lambda durable functions, lançadas em dezembro de 2025, acrescentam checkpoints, passos e waits geridos entre execuções com duração até um ano. A invocação ativa continua limitada, enquanto o workflow durável pode sobreviver-lhe. Compare runtimes suportados, regiões, regras de replay e idempotency das activities com os seus requisitos.

O Lambda pode alojar um harness limitado dentro do limite de 15 minutos. O estado da sessão e do checkpoint continua a precisar de locais externos explícitos; acrescente um sandbox distinto para código não confiável e exporte traces para telemetria externa. Um workflow Lambda durável pode orquestrar trabalho de várias horas através de invocações limitadas.

9. AWS ECS / tarefa Fargate por execução

O Fargate não documenta um limite rígido para a duração de uma tarefa, ao contrário de uma invocação Lambda normal. O Fargate não suporta tarefas com GPU; workloads ECS com GPU precisam de instâncias EC2 adequadas ou de um GPU service externo. O Fargate fornece isolamento de tarefas baseado em virtualização, embora as credenciais e o acesso de rede permitido continuem a precisar de um threat model. As quotas de throttling do Fargate permitem um burst de lançamento de 100 e reposição a 20 por segundo, com budgets separados para on-demand e spot. As quotas de serviços ECS limitam os serviços que usam AWS Cloud Map discovery a 1.000 tasks por service e os clusters suportados por EC2 a 5.000 container instances.

O Fargate requer o modo awsvpc, pelo que cada task recebe uma interface de rede e um IP privado. Este shape adequa-se ao acesso a dados dentro da VPC. O Fargate Spot acrescenta risco de interrupção e a durabilidade continua a ser da sua responsabilidade, porque a plataforma não tem replay ao estilo Temporal.

O Fargate aloja o harness e fornece a cada execução a sua própria task. Isso separa workspaces e credenciais por task, mas não constitui por si só um sandbox completo para código hostil. Sessão, checkpoint e trace vão para serviços externos como RDS ou DynamoDB, além de CloudWatch/X-Ray.

Compare também o Amazon Bedrock AgentCore Runtime antes de criar a sua própria camada de sessão na AWS. Aloja o seu código de agent com lifecycle de sessão gerido e uma escolha de compute. A AWS documenta até 8 horas em serverless microVMs ou 14 dias no seu tipo de compute Instances, que também suporta workloads com GPU. Instances usam recursos EC2 geridos pela AWS na sua conta, com um modelo de segurança diferente da opção serverless. Selecione e teste explicitamente esse contrato de compute; uma instância de maior duração não garante, ainda assim, execução exactly-once de um efeito secundário externo.

10. Kubernetes Job ou namespace por sessão

É uma boa opção quando já opera Kubernetes e quer um sandbox por sessão com controlos à escala do cluster. É uma má opção quando precisa de startup inferior a um segundo, porque descarregar a imagem do container e inicializar o pod demora demasiado num cold start. O padrão consiste num Job por execução do agent, com activeDeadlineSeconds, um PersistentVolumeClaim para o workspace e um sidecar para o servidor MCP. A recuperação após crash é da sua responsabilidade. Adotar Kubernetes apenas para alojar agents é dispendioso em overhead de configuração e carga operacional. Só vale a pena se já executar K8s por outros motivos.

O Kubernetes aloja o harness e o ambiente de execução por execução, normalmente como um Job e, por vezes, com um namespace dedicado. Um isolamento forte continua a depender da runtime class, network policy, pod security e do limite subjacente do container ou VM. O estado da sessão e do checkpoint vive numa database externa ou num PersistentVolumeClaim.

11. Local Docker Compose (apenas dev)

A referência para a secção seguinte. O objetivo deste shape é espelhar a topologia de produção um para um (as mesmas primitivas, a mesma forma de rede), enquanto corre numa única máquina. O que não espelha é o isolamento: um mount de workspace partilhado, um Postgres, nenhum sandbox hardened e nenhum failure domain separado entre o worker e o seu estado. Não faça deployment de nada com esta forma.

O Compose replica o shape #2 num único host. Na stack de referência, o Postgres contém o estado dos checkpoints e o worker container é o harness. Uma sessão com shape de produção precisa do seu próprio event store append-only; apenas o histórico de PostgresSaver não o fornece. O mount de workspace partilhado é conveniente para desenvolvimento, mas não isola execuções não confiáveis. A stack OpenTelemetry opcional regista traces.

Stack de referência: Docker Compose

A topologia de referência, usada em slavadubrov/market-analyst-agent, é composta por um worker LangGraph, um Postgres checkpointer, Qdrant para retrieval, um MCP sidecar, uma queue Redis para execuções assíncronas semelhantes às de produção e uma stack opcional de observability com Prometheus / Grafana / Loki / Tempo / OTel. No compose local, o Redis é opcional apenas porque o runner síncrono pode chamar diretamente o worker. docker compose up levanta localmente a topologia principal; o MCP sidecar e a stack de observability são opt-in através dos profiles (--profile mcp, --profile observability).

Observability que sobrevive à execução

É fácil fazer debugging de request handlers curtos: quando algo falha, lê a resposta e o log em tempo real. Os agents de longa duração não têm esse luxo. Quando uma execução de seis horas falha, o evento relevante aconteceu há cinco horas, o output do terminal desapareceu e o worker que o produziu foi substituído. Ninguém vai reconstruir a execução a partir da memória. Por isso, o debugging é feito a partir de artifacts duráveis escritos enquanto a execução ainda estava ativa.

O Byte diz

Se uma execução longa falhar depois de o output interessante do terminal ter desaparecido, o event log durável e o trace são o que resta para inspecionar.

As stacks de produção tendem a cobrir quatro tipos de artifact, em dois grupos. Dois são lidos depois de a execução terminar, para postmortems e replay: um event log consultável de cada passo e traces OpenTelemetry sobre onde foram gastos tempo e tokens. Os outros dois são lidos durante a execução. Um é um live tail do que o agent está a produzir no workspace. O outro é uma stack de observability por worktree que o próprio agent pode consultar enquanto trabalha.

Event log estruturado (lido depois da execução)

Cada chamada ao modelo, tool call, resultado, erro e aprovação é escrito em armazenamento durável, indexado pelo session ID e timestamp. Quando a execução termina, pode consultá-lo como uma tabela de database normal. Addy Osmani define claramente o padrão em Long-running Agents: “Se não conseguir reconstruir o que o agent fez nas últimas 24 horas a partir de armazenamento durável, o que tem é um long-running shell script que por acaso chama um LLM, e não um long-running agent.”

Traces OpenTelemetry GenAI (lidos depois da execução)

O mesmo tipo de dados passo a passo é emitido como spans usando os atributos standard das gen_ai.* semantic conventions: nome do modelo, provider, contagens de tokens de input e output, conversation ID e workflow name. As convenções continuam com estabilidade Development.

Em 2026, saíram do repositório principal de semantic conventions do OpenTelemetry para o seu próprio repositório de GenAI semantic conventions. Os nomes dos atributos podem ser usados para instrumentação, mas fixe a revisão que validou em vez de um número de versão do repositório principal. Os campos específicos do provider vivem em subnamespaces (anthropic.*, openai.*) indexados por gen_ai.provider.name. A razão para usar o standard é a portabilidade: em destinos compatíveis com OTLP que suportem estas convenções, trocar de backend pode não exigir reinstrumentar o código, embora possam continuar a ser necessários adapters do backend ou configuração específica do destino.

Timeline de tool calls e workspace diffs (lidos durante a execução)

As alterações ao workspace fornecem uma visão rápida do que um agent está a fazer durante uma execução. O Harness Primitives for Long-Running Claude Agents quick-start da Anthropic usa monitorização do workspace em tempo real. Quando watch está instalado, watch -n 5 'git log --oneline -8' atualiza os commits mais recentes a cada cinco segundos. Para screenshots, abra o diretório de screenshots num file browser, ordene pela data de modificação com os mais recentes primeiro e inspecione as imagens mais recentes. Commits e screenshots são indícios de atividade; compare-os com resultados de testes e estado da execução antes de decidir que o agent está a progredir.

Stack efémera por worktree (lida pelo próprio agent durante a execução)

Segundo o post sobre o harness da OpenAI: “Logs, métricas e traces são expostos ao Codex através de uma stack de observability local e efémera para cada worktree.” Cada worktree do agent recebe um Loki + Prometheus + Tempo de curta duração, limitado exclusivamente a essa execução. O agent consulta-o enquanto trabalha. É isso que permite que um prompt como “nenhum span nestas quatro user journeys excede dois segundos” se torne algo que o agent pode verificar diretamente, em vez de ter de adivinhar.

(O evaluator com contexto novo da tabela de modos de falha lê estes artifacts para decidir “done”. Pertence à avaliação, não à observability; consulte § lifecycle saudável da execução. Depende de todas as superfícies acima.)

Uma stack de observability self-hosted mínima

Para algo semelhante a market-analyst-agent:

  1. OpenTelemetry Collector com o GenAI Normalizer Processor (contrib, alpha) para atributos GenAI suportados. Use os processors genéricos Attributes ou Transform para filtrar ou reescrever campos gen_ai.*.
  2. Tempo (ou Jaeger) para traces, indexados por gen_ai.conversation.id / thread_id.
  3. Loki para entradas estruturadas do event log.
  4. Prometheus para gen_ai.client.token.usage, gen_ai.client.operation.duration e gen_ai.client.operation.time_to_first_chunk — as métricas gen_ai.server.* vêm do model server, pelo que só as obtém se alojar os weights (consulte as GenAI metrics conventions).
  5. Grafana dashboards indexados por gen_ai.agent.name e gen_ai.request.model.

Alternativas hosted (escolha uma, não três):

  • LangSmith: integração nativa com LangGraph; também é o deployment target do Deep Agents Deploy.
  • Braintrust: melhor opção quando a prioridade são regression suites eval-first.
  • Arize Phoenix: OSS, nativo para OTLP (o wire protocol do OpenTelemetry), emparelhado com instrumentação OpenInference.
  • Dashboard de tracing da OpenAI: automático quando usa o OpenAI Agents SDK ou a sua integração com Temporal.
  • Claude tracing da Anthropic: para sessões que correm dentro de Managed Agents.

Três queries que vale a pena ter num dashboard

# Loki: output tokens per agent in the last hour (one completion event per call)
sum by (gen_ai_agent_name) (
    sum_over_time({service_name="market-analyst-agent"} | json | event = "model_call_completed" | unwrap gen_ai_usage_output_tokens | __error__="" [1h])
)
# PromQL: p95 model latency per model
histogram_quantile(0.95,
    sum by (le, gen_ai_request_model) (
        rate(gen_ai_client_operation_duration_bucket[5m])
    )
)

{ span.gen_ai.operation.name = "execute_tool" && duration > 30s }

A agregação LogQL assume exatamente um evento de conclusão registado por chamada ao modelo. Deduplicate esses eventos antes da ingestão; rate reportaria tokens por segundo em vez deste total de uma hora. Valide o mapping dos campos contra o stream Loki deployed.

O padrão do debug bundle

Quando uma execução falha, o worker deve criar /workspaces/${THREAD_ID}/_debug/ contendo os artifacts que seriam pedidos num postmortem:

  • events.jsonl: export do event store append-only escrito separadamente pelo harness, incluindo tool intents, outcomes, aprovações e erros.
  • checkpoints.jsonl: histórico do graph state de checkpointer.list({"configurable": {"thread_id": ...}}), identificado como checkpoints e não como event log.
  • last_state.json: StateSnapshot.values do último super-step concluído com sucesso.
  • trace.json: spans exportados por OTLP para a execução; metadata é a baseline e qualquer conteúdo capturado segue a trace policy.
  • tool_calls.csv: (ts, tool, input_hash, latency_ms, status, error).
  • workspace.tar.zst: o diretório do workspace mais git diff contra o initializer commit.
  • screenshots/*.png: o que o agent viu.
  • PROGRESS.md, feature-list.json e quaisquer outros ficheiros de progresso escritos pelo agent.
  • env.txt: image tags, versão do modelo, harness commit SHA.

Em conjunto, estes artifacts podem fornecer a um humano ou reviewer agent evidência suficiente para reconstruir a falha, desde que o harness tenha escrito o event store enquanto a execução estava ativa. “O agent ficou bloqueado” é vago. Um relatório ilustrativo é concreto: a sessão s_123 gastou 71 por cento dos seus tokens a repetir três comandos depois de npm install ter falhado.

Escolher o shape certo: um guia de decisão

A maior parte da comparação anterior resume-se a um conjunto reduzido de decisões.

Comece pela duração da execução

Use a duração da execução como primeiro filtro:

  • Menos de 30 segundos, idempotente: SDK com lifecycle de request num app server.
  • 30 s a 60 min: queue + worker + checkpoint DB.
  • 60 min a 24 h: a mesma queue + worker ou um Cloud Run Job para trabalho one-shot. Use um durable workflow engine se também precisar de versioning e replay.
  • Mais de 24 h, tem de sobreviver a deploys: durable workflow engine (ao estilo Temporal). Os Cloud Run Jobs podem manter trabalho longo até ao limite da task, mas não fornecem semântica de replay.
  • Loops de treino de reinforcement learning com duração de vários dias: K8s Job + volume + Temporal.

Depois desse filtro geral, verifique side effects, recovery, replay, isolamento, localização dos dados e a equipa que irá operar o sistema.

Adequação da plataforma por caso de uso

A matriz é densa e nenhuma célula verde decide sozinha a arquitetura; as células condicionais, onde uma plataforma suporta algo apenas com uma ressalva, são normalmente as que decidem. Uma cobertura ampla de workloads é útil, mas não mostra data residency, semântica de replay, dependência do provider, maturidade operacional ou o custo de mover o estado mais tarde.

As células condicionais usam a mesma regra para todas as plataformas. As opções AWS/VPC e GPU do Deep Agents dependem de deployment híbrido ou de um sandbox provider; Managed Agents pode usar execução operada pelo cliente mantendo orchestration hosted. A linha de escolha de sandbox inclui uma integração com um provider externo que se constrói num runtime próprio ou se configura num harness gerido. Não promete um snapshot do estado em execução. Um Kubernetes Job também precisa de uma camada de API ou queue para um request interativo; concluir rapidamente não o transforma num HTTP service. Compare o acesso de rede, hardware, recuperação e caminho de export do estado do deployment escolhido antes de o selecionar. A linha sobre o código do harness diz respeito ao acesso à implementação do loop, não à portabilidade de um deployment gerido ou do seu estado. A execução GPU no Kubernetes também requer GPU nodes, drivers e um device plugin.

Managed Agents requer Claude e orchestration operada pela Anthropic. O seu sandbox self-hosted opcional pode adequar-se a execução numa rede privada, mas uma exigência de self-hosting da inferência ou do control plane continua a excluí-lo. Reveja quais os inputs de ferramentas, resultados, skills e memória que podem atravessar essa fronteira. O trabalho interno de coding pode adequar-se quando esses fluxos de dados forem aceitáveis e a equipa quiser delegar a operação do harness.

Vale a pena modelar os custos antes de se comprometer, não depois. A linha de horas de sessão é $0.08/hora, além dos custos normais de tokens. Se uma única sessão funcionasse continuamente, seriam cerca de $58/mês por sessão. Com 100 sessões a funcionar continuamente, seriam cerca de $5.800/mês antes dos tokens. Multiplique $0.08 pelo número esperado de horas de sessões concorrentes, acrescente-o à fatura de tokens e compare com o custo de uma stack queue + worker na sua própria infraestrutura. Migrar posteriormente para fora do Managed Agents é um exercício de re-platforming, não uma alteração de configuração.

Harness hosted versus harness próprio

A distinção diz respeito a quem opera o harness, não a quem escreveu o seu código. Hosted significa que o vendor executa o loop do harness na sua infraestrutura e o utilizador chama uma API. Owned significa que o utilizador executa o loop na sua própria infraestrutura, mesmo que o código do harness tenha vindo de um vendor.

A LangChain aparece dos dois lados desta linha, o que causa confusão. Disponibiliza o LangGraph, uma library MIT-licensed que o utilizador aloja (owned), e o Deep Agents Deploy, um produto gerido que executa um harness Deep Agents no LangSmith Deployment no seu modo cloud por omissão (hosted). A mesma empresa, dois modelos operacionais diferentes. O que está a escolher é quem executa o loop, não cujo logo aparece na library. (O Deep Agents Deploy também tem um modo self-hosted para equipas que querem a ergonomia do harness sem o componente cloud; esse modo pertence à categoria owned.)

Escolha um harness hosted quando o suporte de modelos, limite de dados, comportamento de recovery e pontos de extensão já se adequarem. Escolha um harness owned quando essas restrições forem requisitos que espera que mudem. A migração entre os dois altera o estado, a observability e os limites de execução; teste o caminho de saída antes de os dados de produção dependerem dele.

Sandbox hosted versus ambiente de execução próprio

Escolha um sandbox hosted quando o isolamento, pause/resume ou semântica de fork do provider corresponderem ao threat model e ao budget de startup. Docker ou Fargate podem adequar-se a workloads internos confiáveis que precisem de acesso à VPC ou de data residency estrita, mas um container standard não é um limite suficiente para código hostil. A Parte 4 apresenta o menu de isolamento para esse caso.

State stores: Git, DB e object storage lado a lado

Os agents de longa duração usam normalmente três state stores ao mesmo tempo, porque cada store é responsável por um artifact diferente.

O Git armazena o estado do workspace: o código, documentos e ficheiros de progresso que o agent altera. Cada commit fornece ao harness um ponto de recuperação estável e à sessão seguinte um histórico compacto.

A checkpoint database armazena o graph state: o que foi decidido, que nós foram executados, que resultados retornaram e o que deve ser executado a seguir. O artifact store contém grandes outputs finais, como PDFs, ficheiros Parquet e screenshots. Esses artifacts não pertencem ao Git nem à checkpoint database.

Quando usar git como estado

Use git quando o workload tiver forma de código (edições em vários ficheiros, refactors, geração de aplicações) ou forma de documento suficiente para o histórico de ficheiros ser importante. O padrão é simples: crie uma run branch, faça um initializer commit e depois faça commit em fronteiras relevantes: após o setup, após cada feature, após os testes passarem e após a limpeza final. Armazene o último workspace commit SHA junto da checkpoint row. Ao retomar, o worker seguinte faz checkout da branch, lê git log --oneline -8, inspeciona git status e o diff mais recente e depois lê PROGRESS.md ou qualquer ficheiro de handoff escrito pela sessão anterior.

Assim, o git torna-se uma superfície de recovery para o artifact em edição, e não um substituto da checkpoint DB. O Git consegue responder a duas perguntas: o que mudou e que versão passou os testes. Não consegue dizer ao harness que nó do graph deve ser executado a seguir, que tool call está à espera de aprovação ou que retry já usou a sua idempotency key. O harness da Anthropic usa initializer commits e commits por feature como source of truth para a recuperação do workspace; o modelo lê git log --oneline -8 para recuperar o estado. Ignore o git quando o produto do trabalho for uma única resposta conversacional. O overhead não compensa.

Quando usar DB checkpointing

Use checkpointing ao estilo PostgresSaver quando o agent tiver uma estrutura de graph com vários nós cujo estado intermédio seja importante (planner → researcher → writer → verifier). O repositório de referência usa-o precisamente por essa razão. Não coloque artifacts de workspace à escala de terabytes no checkpoint; esses devem ir para object storage.

Quando usar um artifact store (S3 / GCS)

Use object storage quando:

  • o output for maior do que aquilo que a checkpoint database deve transportar;
  • os consumidores downstream precisarem de um artifact endereçável por URL sem passar pelo agent; ou
  • o deliverable e o estado da execução tiverem janelas de retenção diferentes.

Por exemplo, pode eliminar o session log após 30 dias, mas manter o relatório final durante anos. Estruture o layout por (thread_id, checkpoint_id, artifact_name) para que a execução produtora continue a ser reconstruível.

Quando pedir aprovação humana

Defina os requisitos de aprovação com base no risco da ação, na autoridade já concedida e na política de deployment. Uma escrita reversível de um draft numa database é diferente de uma cobrança a um cliente ou de uma alteração destrutiva em produção. Quando for necessária aprovação, mostre a ação real, os argumentos e o destino, persista a decisão e volte a verificá-la se a chamada proposta mudar; não execute uma chamada rejeitada. O interrupt() do LangGraph e o approval middleware do Deep Agents podem pausar a execução para essa decisão. A Parte 4 explica por que razão isto é uma decisão de permissão e não uma instrução de prompt.

Checklist prático de produção

Antes de fazer deployment de um agent de longa duração, responda a estas perguntas em termos concretos de infraestrutura.

  1. Que store é responsável pelos eventos da sessão e pelos checkpoints?
  2. O que acontece se o worker morrer a meio de um tool call?
  3. Uma execução pode corromper o workspace de outra?
  4. Que ações requerem aprovação?
  5. O modelo ou o sandbox podem ler credenciais em bruto?
  6. Que tool calls podem ser repetidos com segurança?
  7. Onde é aplicado o limite de custo por execução?
  8. Que evidência determinística decide a conclusão e que critérios restantes precisam de um reviewer?
  9. Onde vivem os outputs finais depois de o sandbox desaparecer?
  10. Podemos explicar uma execução falhada amanhã sem a executar novamente?

Se a resposta a alguma destas perguntas for “o prompt diz ao agent para ter cuidado”, o sistema ainda não está deployed. Continua a ser uma demo.
