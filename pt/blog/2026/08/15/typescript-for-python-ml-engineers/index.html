TypeScript para engenheiros de ML em Python: criar um agent service

Este é um guia rápido de integração para engenheiros Python experientes que precisam de colocar AI services em produção com TypeScript e Node. Destina-se a engenheiros de ML, cientistas de dados e developers de backend que não precisam de um curso introdutório de JavaScript.

Fiz essa integração por mim próprio nos últimos meses, depois de trabalhar com Python e Java. A maioria dos guias que encontrei começava pela programação básica ou pelo trabalho com o DOM no frontend. Este artigo parte dos conceitos de services em Python. No final, conseguirá mapear uma stack de services Python para TypeScript e reconhecer os hábitos de Python que causam bugs em JavaScript. O exemplo acompanha um agent service com streaming, desde o schema até ao deployment.

O que fazem Node, npm, pnpm, TypeScript e tsx

Os nomes semelhantes escondem tarefas distintas:

  • JavaScript é a linguagem.
  • Node.js é o runtime, aproximadamente o CPython para JavaScript. Instale Node 24 para este projeto.
  • O npm registry é o índice de packages, aproximadamente o PyPI. O comando npm vem com Node e pode instalar packages desse registry.
  • pnpm é o package manager escolhido por este repositório. Instala a partir do npm registry, gere o monorepo workspace e executa os comandos declarados em package.json.
  • package.json é o manifest do projeto, o equivalente mais próximo de pyproject.toml. A sua secção scripts atribui nomes como demo, check e dev:api a comandos mais longos.
  • TypeScript é JavaScript com tipos estáticos. O seu comando tsc verifica esses tipos. O repositório executa-o através de pnpm check ou pnpm typecheck.
  • tsx executa ficheiros .ts sem um build separado. Os scripts de desenvolvimento usam o seu modo watch para reiniciar a API ou o worker depois de uma alteração no código-fonte. Não o invocará diretamente neste guia.

Neste repositório, execute os scripts pnpm. Node é o runtime dentro desses scripts e o Dockerfile fornecido trata da produção.

Uma tradução curta de enum

Para estados com valores string, este repositório usa um objecto e um tipo string-union inferido:

const Status = { Queued: "queued", Running: "running" } as const;
type Status = (typeof Status)[keyof typeof Status]; // "queued" | "running"

O objecto fornece Status.Queued durante a execução do programa. A linha type permite apenas "queued" ou "running" durante a verificação de tipos. Em conjunto, preenchem os dois papéis desta declaração Python:

from enum import Enum

class Status(str, Enum):
    QUEUED = "queued"
    RUNNING = "running"

Só precisa de reconhecer o padrão. as const mantém os valores do objecto como strings exactas, em vez de os alargar para qualquer string.

As sete diferenças semânticas que consomem tempo

A tabela de sintaxe permite-lhe acompanhar os exemplos. É nestas diferenças semânticas que os hábitos de Python causam bugs.

1. Arrays e objectos vazios são truthy

O hábito de Python de que “um container vazio é falsy” é o que pior se transfere. if (results) é true para um array vazio. Escreva if (results.length).

2. null e undefined são diferentes

null normalmente assinala uma ausência deliberada. undefined normalmente significa que um valor está em falta ou não foi atribuído, embora o código possa atribuí-lo explicitamente. O código de libraries devolve undefined constantemente. A diferença é importante quando escreve um valor predefinido. || substitui o lado direito sempre que o lado esquerdo é falsy. Isso inclui 0, "" e false. ?? substitui apenas null e undefined. Assim, 0 || 10 é 10, enquanto 0 ?? 10 é 0. É assim que um batch size zero se transforma silenciosamente em dez.

3. Um bloco catch recebe unknown

Não existe except ValueError:. Um único bloco catch recebe tudo. Como JavaScript permite lançar uma string, um número ou null, TypeScript tipa o valor capturado como unknown, o seu tipo “pode ser literalmente qualquer coisa” sob strict. O repositório complementar ativa strict, e os novos projetos deveriam fazê-lo em geral. Para inspecionar o erro, restrinja primeiro o valor:

try {
    await risky();
} catch (error) {
    // `error` is `unknown` until you prove otherwise. This line is the
    // TypeScript equivalent of `except ValueError as e:` and it is not
    // optional.
    const message = error instanceof Error ? error.message : String(error);
}

4. Promises começam imediatamente

Chamar uma função async começa a executar o seu corpo e devolve uma promise. Um objecto coroutine de Python não faz nada até ser aguardado ou agendado. Promise.all é semelhante a asyncio.gather. Promise.allSettled é semelhante a gather(..., return_exceptions=True), exceto que cada resultado é encapsulado como { status, value } ou { status, reason }.

Node controla o agendamento do runtime. Mantém o processo vivo enquanto existirem handles activos ou requests, como timers e sockets. Uma promise pendente, por si só, não mantém Node vivo. Não envolva o programa em asyncio.run. Num ES module, pode usar await no top level quando o arranque tiver de aguardar uma operação assíncrona.

5. JavaScript tem um único tipo numérico normal

O tipo number de JavaScript armazena valores como números de vírgula flutuante de 64 bits, aproximadamente como o float de Python. A norma técnica deste formato chama-se IEEE 754. Os valores decimais são aproximados, por isso 0.1 + 0.2 não é exactamente 0.3, e os inteiros só permanecem exactos até 2**53 - 1, ou 9,007,199,254,740,991.

Mantenha IDs de 64 bits como strings nos limites do service. Converter um bigint de Postgres para um number JavaScript pode arredondá-lo. Para inteiros exactos maiores, JavaScript fornece o tipo separado BigInt, que não se combina com números normais.

6. Use Map quando precisar de um dicionário ao estilo de Python

Em JavaScript, {} cria um objecto. Os objectos normalmente representam registos com campos nomeados:

const request = { model: "gpt-5", seqLen: 4096 };
console.log(request.model);

Um objecto não é uma tabela limpa de chave-valor como um dict de Python. Herda alguns nomes do próprio JavaScript. Isto pode produzir um resultado surpreendente:

const tools: Record<string, unknown> = {};

tools["constructor"]; // a built-in function, not a missing value
Object.hasOwn(tools, "constructor"); // false

Se uma string externa seleccionar um campo de um objecto, chame Object.hasOwn antes de o ler. Se precisar de um dicionário de uso geral, use Map. Map é mais próximo de dict de Python: uma chave só existe quando o seu código a adiciona.

const tools = new Map<string, unknown>();
tools.get("constructor"); // undefined

7. Inclua a extensão nos imports relativos

Um ficheiro de código-fonte JavaScript que partilha código com outros ficheiros chama-se module. Este projeto usa o formato moderno de módulos, ES modules, normalmente abreviado como ESM. ES significa ECMAScript, o nome formal da linguagem JavaScript. Na prática, ESM é a sintaxe import e export usada em todo este projeto.

Num import relativo, Node requer o nome exacto do ficheiro. Não adivinhará se ./env significa ./env.ts ou ./env.js:

import { loadEnv } from "./env.ts";

Os imports de packages instalados ou de workspace continuam a usar o nome do package, sem extensão de ficheiro:

import { z } from "zod";
import { runAgent } from "@agent/core";

Zod é pydantic com a seta invertida

Em pydantic declara uma classe e obtém um validator. Em Zod declara um validator e deriva o tipo a partir dele. A mesma single source of truth, mas na direcção oposta.

De packages/schemas/src/env.ts:

import { z } from "zod"; // `z` is Zod's whole API, the way `pd` is pandas

const EnvSchema = z.object({
    PORT: z.coerce.number().int().positive().default(8080),
    // See the note below: a bare z.url() would accept "localhost:8000".
    OPENAI_BASE_URL: z
        .url({ protocol: /^https?$/ })
        .default("https://api.openai.com/v1"),
    DATABASE_URL: z.string().optional(),
});

export type Env = z.infer<typeof EnvSchema>;

z.infer<typeof EnvSchema> lê um tipo estático a partir do schema de runtime. z.coerce.number() trata do facto de cada valor definido em process.env (o os.environ do Node) ser uma string. Desempenha o mesmo papel da coerção de configurações numéricas do pydantic, embora as strings exactas aceites sejam diferentes. Isto segue o padrão pydantic-settings e é executado uma vez no arranque. Um ambiente inválido produz então um erro de arranque legível, em vez de um TypeError dentro de um handler.

Um z.url() simples aceita localhost:8000. O standard dos URLs trata tudo antes dos dois pontos como o scheme. Por isso lê localhost: como um protocolo chamado “localhost” e aceita a string. O valor chega depois ao HTTP client e falha com menos contexto. A validação do schema antecipa as falhas, mas aplicará um schema permissivo se foi isso que escreveu.

Zod 4 também inclui z.toJSONSchema, por isso este projeto não precisa da dependência zod-to-json-schema comum em tutoriais antigos. Isto é importante quando um schema tem de alimentar três consumers, que é o tema da secção “Uma ferramenta, três consumers” abaixo.

O service

O service de demonstração dimensiona deployments de LLM. Uma tool consulta constantes da arquitectura de um modelo. A outra estima o seu consumo de KV cache: a memória da GPU usada para guardar keys e values de attention de requests em execução. Ambas as tools fazem aritmética deliberadamente simples. Não precisam de rede e dão sempre a mesma resposta. Isso torna o service testável sem API key. O estimador de KV cache também é publicado através do Model Context Protocol (MCP), para que outros AI clients o possam chamar.

pnpm-workspace.yaml é o ficheiro que declara o workspace. Os packages internos recebem um nome com scope, como @agent/core, em que o prefixo @agent/ é uma convenção de nomenclatura, não uma funcionalidade da linguagem. Escreva o tool loop à mão, uma vez

Os frameworks de agents com tool calling envolvem o mesmo loop básico:

  1. Chamar o modelo com definições de tools.
  2. Validar e executar as tools pedidas.
  3. Acrescentar os resultados às mensagens.
  4. Chamar novamente o modelo.

Escreva este loop uma vez. O comportamento do framework passa então a ser uma escolha de engenharia que consegue justificar.

O loop é um async function*, um async generator, a forma exacta do async def de Python com yield. A rota HTTP itera esse generator, transforma cada evento numa frame de Server-Sent Events e acumula o texto. Depois de o stream terminar, a rota chama storage.createRun uma vez com o texto final. Os testes invocam o loop separadamente e recolhem os seus eventos num array. Uma frame SSE é um chunk de uma resposta HTTP de longa duração. A secção seguinte explica o formato.

O loop tem duas saídas normais. Uma resposta sem tool calls produz done com stopReason: "stop". Se o modelo continuar a pedir tools até maxSteps, o generator também termina e produz done com stopReason: "max_steps". Trate esse resultado como concluído mas truncado: o texto acumulado pode estar incompleto.

De packages/agent-core/src/loop.ts:

let text = ""; // the assistant text produced during this model step
// Keyed by the `index` field, because a streamed response interleaves
// fragments of several parallel tool calls and only `index` is present
// on every fragment. `id` and `name` arrive once, `arguments` arrives
// in pieces. `a?.b` below reads `b` only if `a` exists, and gives back
// `undefined` instead of throwing if it doesn't.
const partial = new Map<number, PartialToolCall>();

for await (const chunk of stream) {
    const choice = chunk.choices[0];
    if (!choice) continue;

    if (choice.delta.content) {
        text += choice.delta.content;
        yield { type: "text", delta: choice.delta.content };
    }

    for (const fragment of choice.delta.tool_calls ?? []) {
        const slot = partial.get(fragment.index) ?? { id: "", name: "", args: "" };
        if (fragment.id) slot.id = fragment.id;
        if (fragment.function?.name) slot.name = fragment.function.name;
        if (fragment.function?.arguments) slot.args += fragment.function.arguments;
        partial.set(fragment.index, slot);
    }
}

A variável local text contém um passo do modelo. O loop usa-a na mensagem do assistant para o passo seguinte ou no evento done final. Não é o acumulador ao nível da rota que será persistido posteriormente.

O map partial é a parte que os frameworks escondem. O SDK expõe fragmentos string dos argumentos da função, que podem dividir o JSON serializado em posições arbitrárias. Várias calls paralelas também podem ficar intercaladas. O repositório inclui um teste que divide {"model":"llama-3.1-8b",...} em quatro chunks.

A segunda coisa que vale a pena escrever por si próprio é o que acontece quando a validação falha:

// `tool.parse` is this repo's wrapper, not Zod's. Zod's own `.parse` throws and
// `.safeParse` returns `{ success, data, error }`; this returns
// `{ ok: true, value }` on success and `{ ok: false, error }` on failure, so no
// caller has to catch.
const parsed = tool.parse(raw);
if (!parsed.ok) {
    return {
        ok: false,
        value: { error: `Invalid arguments: ${parsed.error}` },
        parsedArgs: raw,
    };
}

Antes da execução, a procura pode não encontrar a tool, JSON.parse pode rejeitar os argumentos ou o Zod pode rejeitar a sua forma. Cada falha transforma-se numa mensagem que o modelo lê. Durante a execução, um ToolError esperado também se torna um tool result, para que o modelo possa corrigir a call. Uma excepção inesperada propaga-se para o HTTP error path, em vez de ser apresentada como uma falha de domínio. z.prettifyError transforma a árvore de issues do Zod numa mensagem que o modelo pode usar, em vez de num stack trace.

strict: true numa definição de função OpenAI pede ao provider que restrinja o decoding ao schema. Não tem qualquer relação com a flag strict do tsconfig do TypeScript. Isto é semelhante ao guided decoding do vLLM, embora os schemas suportados e os detalhes de enforcement sejam diferentes. Remove um modo de falha, mas um endpoint self-hosted pode ignorar a flag. Os argumentos também têm de sobreviver a JSON.parse.

O loop chama /chat/completions porque o repositório complementar aponta para servers compatíveis com OpenAI. vLLM, SGLang e Ollama documentam esse endpoint, pelo que OPENAI_BASE_URL pode apontar o mesmo client para qualquer um deles. A cobertura da Responses API varia e muda entre releases. Se controlar ambos os lados, consulte a página de compatibilidade actual do server antes de escolher entre as duas APIs.

Mude depois para o AI SDK e saiba o que está a trocar

Para projetos posteriores, usaria o Vercel AI SDK. O repositório complementar implementa o mesmo agent duas vezes, para tornar visível o compromisso. Ambas as versões emitem o mesmo stream AgentEvent, pelo que a camada HTTP não consegue distingui-las.

O repositório complementar fixa o AI SDK 7.0.42 em packages/agent-core/package.json. A implementação do framework está em packages/agent-core/src/loop-ai-sdk.ts:

const result = streamText({
    model: provider.chatModel(options.model),
    prompt: options.message,
    tools: aiSdkTools,          // Zod schemas passed straight through
    stopWhen: stepCountIs(options.maxSteps ?? 6),
});

for await (const part of result.fullStream) {
    switch (part.type) {
        case "text-delta": yield { type: "text", delta: part.text }; break;
        case "tool-call":  yield { type: "tool_call", callId: part.toolCallId, /* ... */ }; break;
        // ...
    }
}

O SDK remove cinco partes de código da aplicação:

  • o fragment accumulator
  • JSON.parse e o seu error path
  • a call que executa o Zod sobre os argumentos analisados
  • a montagem de mensagens específica do provider
  • o contador de passos

stopWhen aceita várias condições, incluindo um limite de passos ou uma tool call específica. O loop for await não muda quando a política de paragem muda.

O que perde é o controlo directo sobre falhas de validação. O loop escrito à mão decide o que o modelo vê depois de uma call rejeitada. O SDK expõe a opção experimental experimental_repairToolCall para um callback de reparação personalizado. O repositório complementar actual não define essa opção, pelo que depende do tratamento predefinido de calls inválidas do SDK. A troca também funciona no sentido inverso. Na versão com SDK, uma alteração de provider fica localizada no provider adapter. Continua a exigir o package do provider correspondente, credenciais, configuração e testes de integração. No loop raw, o tratamento específico do provider para requests e streams é código seu e terá de ser alterado por si.

Escrevo o loop à mão no primeiro projeto e uso o SDK nos seguintes. Paga essa aprendizagem uma vez. A alternativa é ler pela primeira vez os internals de um framework enquanto este falha em produção.

Streaming sobre HTTP: Hono e SSE

As rotas Hono parecem-se com rotas FastAPI. A única adição é zValidator, que faz o trabalho que o FastAPI obtém gratuitamente das type annotations na assinatura de um handler. O c no handler abaixo é o request context do Hono, o objecto que o FastAPI distribui pelos seus parâmetros. deps é um conjunto de dependências com que a app é construída, em vez de as importar directamente. runAgent é uma delas, e a secção de testes mostra o que isso permite.

De apps/api/src/app.ts:

app.post("/v1/chat", zValidator("json", ChatRequestSchema), (c) => {
    const body = c.req.valid("json");
    const log = deps.logger.child({ route: "chat" });

    return streamSSE(c, async (stream) => {
        let text = "";
        try {
            await withSpan(
                "agent.run",
                { "agent.max_steps": body.maxSteps },
                async () => {
                    for await (const event of deps.runAgent({
                        message: body.message,
                        maxSteps: body.maxSteps,
                    })) {
                        if (event.type === "text") text += event.delta;

                        await stream.writeSSE({
                            event: event.type,
                            data: JSON.stringify(event),
                        });
                    }
                },
            );
        } catch (error) {
            log.error({ err: error }, "agent run failed");
            await stream.writeSSE({
                event: "error",
                data: JSON.stringify({
                    type: "error",
                    message: "Agent run failed",
                }),
            });
            return;
        }

        await deps.storage.createRun({
            kind: "chat",
            status: "succeeded",
            input: { message: body.message },
            output: { text },
        });
    });
});

A rota trata actualmente todos os generators concluídos normalmente da mesma forma. Persiste status: "succeeded" depois de qualquer generator que chegue ao fim, incluindo um cujo evento final tenha stopReason: "max_steps". Isso faz com que o resultado de atingir o limite seja concluído mas truncado ou parcial, e não uma falha já persistida. O código de produção deve inspeccionar o evento done e aplicar uma política explícita. Por exemplo, poderia usar um status distinto de truncado ou um percurso de revisão/retry antes de reportar sucesso.

zValidator valida o body e dá a c.req.valid("json") o tipo produzido pelo schema. Se o omitir, o body fica tipado como any, o opt-out do TypeScript, em que cada acesso a uma propriedade compila e nada é verificado. Isso desactiva o benefício de type-safety do schema.

Esta rota usa Server-Sent Events em vez de WebSockets. O server mantém uma resposta HTTP aberta enquanto escreve frames event: <name> e data: <json>, fechando-a depois do evento final. O tráfego flui do server para o client, o que corresponde a este agent stream. Um WebSocket acrescentaria mensagens bidireccionais e um protocol upgrade de que esta rota não precisa.

Uma falha a meio do stream altera o reporting de erros HTTP. Depois de a primeira frame ser enviada com status 200, o server não pode substituir essa resposta por um 500. O bloco catch regista o erro capturado, envia um evento de erro constante para o client e retorna. Esse return é importante: apenas um stream concluído com sucesso chega a storage.createRun. Um generator que emita done, incluindo max_steps, é um stream concluído normalmente e chega a essa escrita.

Um teste cobre este caminho. Um generator produz um text delta e depois lança uma excepção. A resposta mantém o status 200 e a sua última frame é um evento error com a mensagem constante Agent run failed. O logger conserva o erro capturado para diagnóstico no server. Qualquer client que verifique apenas o status code reportará sucesso numa execução falhada.

app.ts toma duas decisões mais pequenas que vale a pena explicar. Trata /healthz como um endpoint de liveness, pelo que essa rota deliberadamente não toca no Postgres. Uma falha de liveness durante uma indisponibilidade da database poderia reiniciar todas as réplicas sem reparar a dependência. Adicione uma verificação de readiness separada quando o orchestrator tiver de deixar de encaminhar tráfego para uma instância que não consegue chegar ao Postgres. Os error paths registam o erro capturado, mas devolvem uma string constante. Reenviar error.message no response body é a forma de as connection strings acabarem no browser de outra pessoa.

A parte semelhante ao Celery, sem Celery

Jobs longos não pertencem a um request handler. A API insere uma row e devolve 202. Um worker reclama a row.

Aqui não há Redis nem BullMQ. O PostgreSQL documenta SKIP LOCKED para múltiplos consumers de uma tabela semelhante a uma fila. A cláusula dá a este pequeno service uma fila at-least-once numa única tabela. É transaccional com o resto das suas escritas e representa mais um service a menos no docker-compose.yml.

A claim query em packages/agent-core/src/db/storage.ts é:

const [candidate] = await tx
    .select({ id: runs.id })
    .from(runs)
    // The real query also picks up rows whose lock went stale; trimmed here.
    .where(and(eq(runs.kind, kind), eq(runs.status, "queued")))
    .orderBy(runs.createdAt)
    .limit(1)
    // `.for()` exists but is undocumented; SKIP LOCKED rides in its second
    // argument.
    .for("update", { skipLocked: true });

A row fica bloqueada para a transacção e qualquer worker concorrente que execute a mesma query salta-a em vez de ficar bloqueado. Assim, duas claims simultâneas não recebem a mesma row não obsoleta. Um teste de integração dispara duas claims ao mesmo tempo através de Promise.all e garante que devolvem rows diferentes. A versão ingénua, SELECT ... LIMIT 1 seguida de UPDATE, falha esse teste: ambas as transacções leem a mesma row antes de qualquer uma escrever, pelo que ambas iniciam o mesmo job.

Isto é execução at-least-once, não exactly-once. A query completa também reclama uma row running quando o seu lock tem mais de cinco minutos, e o worker da demo não renova essa lease. Um job activo que demore mais de cinco minutos pode, portanto, ser reclamado duas vezes. Torne os jobs idempotent. Para trabalho de longa duração, adicione um lease heartbeat ou defina o limiar de obsolescência acima do runtime máximo.

Adicione BullMQ quando precisar de jobs atrasados, schedules repetíveis, prioridades, rate limits ou um dashboard. Faria a mesma mudança de uma tabela de database para Celery em Python. Antes disso, Redis é mais um service para executar, monitorizar e explicar à pessoa de on-call.

O worker volta a validar o que lê de jsonb:

// The row was validated on the way in, but it has been through a database.
// A stored row can outlive the schema version that accepted it.
// The job is a batch-size sweep. Zod's own `.parse` throws; the poll loop
// catches that and marks the run failed.
const input = SweepRequestSchema.parse(run.input);

A suite de testes também fornece ao worker uma row cujo seqLen é uma string. O worker falha a execução e continua a fazer polling, em vez de crashar e repetir a mesma poison row indefinidamente.

O trabalho em CPU expõe outra limitação de Node. Um callback síncrono executa-se na thread do event loop e não é preemptado. Um loop for que faça cálculos durante dois segundos bloqueia todos os requests, timers e verificações de liveness desse processo durante dois segundos. Um loop apertado dentro de um async def bloqueia asyncio da mesma forma. Ambos os runtimes exigem que faça offload explícito do trabalho de CPU.

await setTimeout(0) de node:timers/promises (o prefixo node: significa standard library, pelo que node:timers está para Node como os está para Python) é await asyncio.sleep(0). O sweep cede o controlo depois de cada batch size para que o processo do worker possa tratar timers e outros callbacks. Ceder o controlo não torna o trabalho de CPU paralelo. Node worker_threads consegue executar JavaScript em paralelo. Para trabalho CPU puro em Python sob a build habitual de CPython com GIL activo, use um process pool em vez de um thread pool. Este service não usa nenhum dos dois. Mantenha os cálculos numéricos pesados em Python, onde já vivem as libraries de suporte, e retire-os do event loop da API.

Uma tool, três consumers

EstimateKvCacheInput tem três consumers:

  • O loop escrito à mão converte-o com z.toJSONSchema.
  • O AI SDK recebe-o sem alterações.
  • O MCP server publica a sua forma.

É por isso que existe packages/schemas.

De apps/mcp/src/index.ts:

server.registerTool(
    "estimate_kv_cache",
    {
        description: "Estimate KV-cache VRAM in GiB for a served model...",
        // A Zod object schema keeps the map of fields you passed in on
        // `.shape`. This SDK wants that map, not the schema wrapped around it.
        inputSchema: EstimateKvCacheInput.shape,
    },
    async ({ model, seqLen, batchSize }) => {
        /* ... */
    },
);

await server.connect(new StdioServerTransport());

Dois detalhes são importantes antes de ligar um client. Primeiro, um server iniciado desta forma usa o seu próprio stdin e stdout para comunicar com o client. Cada linha é uma mensagem JSON-RPC. Um console.log extraviado, o equivalente JavaScript de print, corrompe então uma mensagem. O client desliga-se com um erro de parsing que não indica nenhum ficheiro. Envie todos os diagnósticos para stderr.

Segundo, uma falha de domínio deve devolver isError: true com uma mensagem. O modelo que chama pode então corrigir a call, tal como depois de argumentos de tool inválidos no agent loop.

Pode conduzir o server com printf e um pipe, o que vale a pena fazer uma vez antes de apontar para ele um client real:

printf '%s\n' \
  '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"probe","version":"1"}}}' \
  '{"jsonrpc":"2.0","method":"notifications/initialized"}' \
  '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"estimate_kv_cache","arguments":{"model":"llama-3.1-70b","seqLen":8192,"batchSize":4}}}' \
  | pnpm -s mcp   # -s suppresses pnpm's own output so only JSON-RPC comes back

A probe corresponde à versão do protocolo usada no README do repositório complementar. Para um client real, use o SDK em vez de manter mensagens JSON-RPC manualmente.

Testar um agent sem API key

Vitest desempenha o papel de pytest, mas a estrutura é diferente. describe agrupa testes relacionados. it e test definem cada um um caso de teste. test.each é próximo de parametrize, beforeEach fornece setup por teste, vi.fn() cria uma função mock e describe.skipIf salta condicionalmente um grupo.

Os testes do agent dependem de uma decisão: runAgent recebe um OpenAI client como parâmetro, em vez de construir um. O fake é um objecto com um método chat.completions.create que devolve um async iterable scripted:

function fakeClient(scripts: Chunk[][]): OpenAI {
    let call = 0;
    return {
        chat: {
            completions: {
                create: async () => {
                    const script = scripts[call++] ?? [];
                    // Defines an async generator and calls it on the same
                    // line, so `create` hands back something you can
                    // `for await` over, which is the shape a real streaming
                    // response has.
                    return (async function* () {
                        for (const chunk of script) yield chunk;
                    })();
                },
            },
        },
        // TypeScript refuses a direct cast between unrelated shapes, so you
        // launder it through `unknown` first. A lie to the compiler, confined
        // to one line in a test file, which is the only place it belongs.
    } as unknown as OpenAI;
}

Os testes dividem uma string de argumento JSON entre chunks e tratam duas tool calls numa única resposta. Também cobrem batchSize inválido, JSON malformado, nomes de tools desconhecidos e um modelo que continua a chamar tools até maxSteps o parar. O ficheiro de testes executa em bem menos de um segundo, sem rede nem key.

Os testes de integração contra Postgres usam describe.skipIf(!process.env.DATABASE_URL), pelo que pnpm test funciona num clone novo sem Postgres em execução, e o CI activa-os fornecendo a variável. O repositório tem 40 testes. Trinta e seis executam sem Postgres nem API key.

Registar eventos estruturados com Pino

Pino desempenha o mesmo papel que structlog: um objecto JSON por linha, loggers filhos com campos associados e redacção explícita. O repositório complementar configura-o em packages/observability/src/logger.ts:

const log = pino({
    redact: {
        paths: [
            "req.headers.authorization",
            "apiKey",
            "OPENAI_API_KEY",
            "*.apiKey",
        ],
        censor: "[redacted]",
    },
});

Sem redacção, log.info({ req }, "...") pode copiar um header Authorization para o backend de logs.

Fazer tracing do trabalho da aplicação com spans manuais

O repositório complementar usa OpenTelemetry para três spans ao nível da aplicação: agent.run, agent.tool e worker.sweep. Não instala instrumentação automática de HTTP ou Postgres. startTracing() em packages/observability/src/tracing.ts cria um NodeSDK com um OTLP trace exporter. Se OTEL_EXPORTER_OTLP_ENDPOINT estiver ausente, deixa o tracing desligado.

O trabalho propriamente dito é envolvido por withSpan() do mesmo ficheiro:

return tracer.startActiveSpan(name, { attributes }, async (span) => {
    try {
        return await fn(span);
    } finally {
        span.end();
    }
});

JavaScript não tem sintaxe de context manager ao estilo de Python. Aqui, o callback é o bloco que um context manager Python envolveria. O helper completo também regista excepções e define o status do span antes de voltar a lançá-las.

Os spans automáticos de HTTP e database são uma funcionalidade separada. Requerem os packages de instrumentação correspondentes e inicialização antes de os módulos instrumentados serem carregados. Adicione-os apenas quando esses spans forem úteis e siga a configuração do OpenTelemetry Node SDK para as versões exactas dos packages que vai colocar em produção.

Colocar o monorepo em produção com Docker

Use o Dockerfile fornecido. O container inicia a API com o loader tsx. Não precisa de escolher nem invocar um TypeScript runner quando fizer deployment.

O build usa pnpm fetch para manter as descargas de dependências em cache até o lockfile mudar. Depois usa pnpm deploy para copiar a API e as suas dependências de produção para um directório autocontido. O runtime stage executa como o user não-root node, e o CMD em formato exec permite à API receber SIGTERM directamente para um shutdown gracioso.

Porque é que o Dockerfile carrega o tsx

Node 24 consegue executar um subconjunto limitado de TypeScript removendo type annotations. Não verifica os tipos nem executa as transformações que um TypeScript runner completo suporta. Os package scripts do repositório escondem esse detalhe. pnpm check faz a verificação estática separadamente.

O container expõe outra limitação. pnpm deploy copia os packages do workspace para node_modules e Node recusa deliberadamente remover TypeScript nesse local (documentação de TypeScript do Node). A primeira versão da imagem crashava com ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING. Funciona. Fiquei desanimado.

O Dockerfile corrige o problema carregando tsx, que trata esses ficheiros .ts antes de Node os executar. Uma equipa que queira apenas ficheiros .js na imagem de runtime pode adicionar um passo de compilação. Esse é um design alternativo de produção, não um passo adicional necessário para executar este repositório complementar.

Engenheiros Python experientes podem saltar o material que ensina variáveis e loops. Esta sequência centra-se nas partes que diferem de Python. A coluna de implementação mostra o objectivo de cada linha. A leitura dá-lhe o suporte.

Compromissos

Mantenha os cálculos numéricos em Python

Node funciona bem para orquestração, serving HTTP e streaming. Cálculos CPU-bound prolongados bloqueiam a sua thread principal do event loop. Mantenha vLLM e o código de training em Python, salvo se uma carga de trabalho medida justificar a migração.

Valide cada fronteira em runtime

Uma anotação TypeScript não verifica um HTTP body, uma environment variable, um argumento de tool gerado pelo modelo ou uma row lida de jsonb. Cada fronteira precisa de um runtime schema.

Isole a churn do SDK

AI SDK 6 substituiu Experimental_Agent por ToolLoopAgent e mudou o nome da definição de agent system para instructions (guia de migração do AI SDK 6). O repositório complementar chama directamente streamText no AI SDK 7 e expõe o seu próprio stream AgentEvent. Essa fronteira mantém a rota HTTP inalterada quando o código do SDK muda.

Ignore o loop escrito à mão quando o prazo for mais importante

Escrever o loop uma vez ensina-lhe que comportamento pertence ao SDK. Se precisar de colocar algo em produção primeiro e não tiver motivo para personalizar falhas de validação, comece pelo SDK.

Principais conclusões

  1. Instale Node 24 e pnpm. Depois use os scripts do repositório: pnpm demo, pnpm dev:api, pnpm dev:worker e pnpm check. Os scripts escondem os comandos de runtime e de verificação de tipos de baixo nível.
  2. A validação em runtime é estruturalmente necessária. Zod é o validator escolhido neste projeto. Os tipos estáticos não inspeccionam HTTP bodies, environment variables, output do modelo ou rows da database. Com Zod, declare um runtime schema e derive o tipo TypeScript com z.infer.
  3. A stack mapeia-se na sua maioria sem problemas: pnpm para uv, Hono para FastAPI, Drizzle para SQLAlchemy, Vitest para pytest e Biome para Ruff. Três linhas não são substituições: validação, verificação de tipos e job queue.
  4. Escreva um agent loop à mão se precisar de aprender ou personalizar os caminhos ocultos: acumulação de fragmentos, validação e feedback de erros das tools.
  5. Transforme o loop num async generator. A rota HTTP consome os seus valores AgentEvent, emite frames SSE, acumula o texto e persiste-o depois do stream. Os testes consomem o generator separadamente, sem rede nem API key.
  6. O Postgres pode fornecer uma fila at-least-once. Torne os handlers idempotent e renove a lease ou dimensione-a acima do runtime máximo para jobs longos. Adicione BullMQ quando precisar de atrasos, prioridades ou schedules.
  7. Use o Dockerfile fornecido em produção. Este empacota a app seleccionada, carrega TypeScript com tsx, executa como user não-root e encaminha os sinais de shutdown para o processo da API.
