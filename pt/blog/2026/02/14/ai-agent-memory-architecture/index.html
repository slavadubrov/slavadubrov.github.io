Arquitetura de memória de AI Agent: Checkpoints e Vector Stores

Viacheslav Dubrov

2026-02-14 · Atualizado 2026-08-01 · 38 min · Agentes de IA

Tradução automática Este artigo foi traduzido automaticamente a partir da versão original em inglês.

Um reasoning loop só sobrevive a um pedido, a menos que o seu estado seja armazenado fora do worker. Sem memória do agent, o agent não consegue retomar um plano pausado, recuperar após uma falha ou recordar uma preferência de uma sessão anterior. A Parte 1 abordou o fluxo de controlo. Este artigo identifica o estado de que cada turno posterior precisa e onde esse estado deve residir.

Vou usar o Market Analyst Agent — um pequeno agent LangGraph que obtém dados de mercado e escreve um relatório de analista — como referência para a discussão sobre hot checkpoints. As secções independentes sobre cold vectors e raw Markdown apresentam designs ilustrativos que mostram extensões ainda não implementadas no projeto atual. Depois, abordarei quando faz sentido usar PostgreSQL, Redis, Qdrant, key-value stores e ficheiros Markdown simples.

TL;DR

Separe a memória por padrão de acesso. A hot memory é o estado de checkpoint por conversa, usado para pausar e retomar. A cold memory contém factos entre sessões, num key-value store ou vector store. A document memory mantém o conhecimento do projeto em ficheiros inspecionáveis. Comece pela falha que precisa de corrigir e escolha depois o store. Não coloque factos exatos num sistema de retrieval difuso nem trate um checkpoint como um audit log.

Todos os stores abaixo são lidos pelo harness, o código que conduz o loop em redor do modelo. O harness decide que conteúdos chegam à context window; os stores não. Este artigo aborda onde esse estado reside antes de o harness o ir buscar. A Parte 3 e a Parte 4 explicam o que o harness faz depois com o prompt.

O que é a memória de um AI agent?

A memória de um AI agent é a camada de estado que permite a um agent preservar o progresso de uma tarefa, obter conhecimento anterior e atualizar o que sabe entre execuções. Em produção, não é uma única vector database. É uma combinação de hot checkpoints, stores semânticos ou estruturados para cold memory e document memory legível por humanos.

NecessidadePredefinição recomendadaMotivo
Pausar e retomar uma execuçãoPostgreSQL checkpoint storeDurável, consultável e fácil de operar com os dados da aplicação
Estado transitório com baixa latênciaRedis checkpoint storeRetoma rápida e estado de curta duração, com compromissos de persistência
Recuperação semântica entre threadsQdrant ou pgvectorObtém memórias pelo significado, não apenas por chaves exatas
Factos estruturados do utilizadorPostgreSQL ou key-value storeAtualizações determinísticas são melhores do que retrieval difuso para preferências e IDs
Convenções e procedimentos aprendidosFicheiros Markdown ou JSONLegíveis por humanos, comparáveis em diff e fáceis de atualizar por agents
Memória de relações entre várias entidadesKnowledge graphÚtil quando as relações importam mais do que os factos individuais

Não comece pela memória só porque parece inteligente. Comece pela falha visível para o utilizador: perder progresso, esquecer uma preferência, repetir investigação ou não reutilizar uma convenção do projeto.

As falhas que exigem memória

Um agent sem estado consegue responder a uma pergunta isolada, mas esquece o pedido assim que a chamada termina. Esse design falha quando o produto precisa de qualquer um dos seguintes comportamentos:

  • Pausar e retomar: um utilizador inicia uma tarefa de investigação, fecha o portátil e regressa no dia seguinte. Sem estado em checkpoint, o agent recomeça do zero.
  • Coerência multi-turno: numa conversa longa, o agent tem de se lembrar das tools que chamou, dos dados que recolheu e dos passos do plano que concluiu.
  • Personalização: um utilizador que regressa espera que o agent conheça a sua tolerância ao risco, a profundidade de análise preferida e as interações anteriores.
  • Human-in-the-loop (HITL): o agent recolhe evidências e aguarda que uma pessoa aprove o passo seguinte. O estado de espera tem de sobreviver a reinícios do processo.

No Market Analyst Agent da Parte 1, o pedido “Analyze NVDA” produz um plano, cinco tool calls, dados recolhidos e um relatório preliminar. Quando o utilizador responde “parece bem, mas acrescenta uma análise da concorrência”, um checkpoint store permite ao agent carregar o estado do último passo concluído e adicionar o passo de análise da concorrência. Sem estado em checkpoint, não consegue determinar a que se refere “parece bem” e tem de recomeçar.

A memória de longo prazo trata de um caso diferente. Se o utilizador regressar uma semana depois e perguntar “Atualiza a minha análise da NVDA”, o agent poderá ter de recordar uma preferência por avaliações de risco conservadoras e um interesse em ações de semicondutores. Um memory store suportado por vectors pode recuperar esses factos entre sessões sem voltar a perguntar por eles.

Os exemplos de implementação abaixo usam LangGraph, a biblioteca open-source da LangChain para criar agents como state graphs explícitos; as fronteiras de armazenamento que define são generalizáveis a qualquer framework. O LangGraph separa a memória por âmbito. Cada execução do graph ocorre dentro de uma thread, ou seja, uma conversa ou tarefa. O estado persistido nessa thread é a short-term memory. O estado partilhado entre threads é a long-term memory. Abaixo, “thread” e “conversa” são equivalentes; evito “sessão” para esse âmbito, porque a Parte 5 reserva esse termo para o log durável de uma execução, podendo várias execuções acumular-se numa thread. O contexto atual do modelo e as variáveis em processo formam a camada de working memory acima de ambos os stores.

Uma taxonomia da memória de AI agents

Antes de abordar a implementação, é útil classificar aquilo de que os agents precisam de se lembrar. O framework CoALA — Cognitive Architectures for Language Agents (Sumers, Yao et al., 2023) — é uma taxonomia amplamente citada, baseada em ciência cognitiva. Introduzi o scope da memória no meu artigo sobre context engineering; aqui desenvolvo-o em seis categorias:

Tipo de memóriaÂmbitoDuraçãoExemploPadrão de armazenamento
WorkingPasso atualMilissegundosArgumentos de tool call, resposta atual do LLMEm processo (Python dict)
Short-termThread atualMinutos–horasHistórico da conversa, progresso do plano, dados recolhidosCheckpoint store
EpisodicEntre threadsDias–meses“Na semana passada, o utilizador perguntou pelos resultados da NVDA”Vector store / KV store
SemanticEntre threadsMeses–permanente“O utilizador prefere investimentos conservadores”Vector store / KV store
DocumentEntre threadsDias–permanenteNotas do projeto, resumos de investigação, padrões aprendidosFile store (Markdown/JSON)
ProceduralTodo o sistemaPermanente“Ao analisar ações, verificar sempre os filings da SEC”Config / system prompt

A working memory é aquilo com que o LLM está a raciocinar ativamente neste momento: variáveis Python na função atual, conteúdos da context window e argumentos de tool calls durante a execução. É a camada mais rápida e mais efémera. Nada persiste além do passo atual. A working memory é limitada pela context window do modelo, o que a torna no bottleneck. Tudo o que o agent “sabe” no momento de tomar uma decisão tem de caber aqui, quer venha do checkpoint store, de uma vector query ou da leitura de um ficheiro. Os outros níveis existem para alimentar a working memory com a informação certa no momento certo.

A short-term memory é o checkpoint que o LangGraph escreve depois de cada unidade de execução do graph — um super-step, definido na secção seguinte. As memórias episodic e semantic persistem entre threads. A document memory armazena notas do projeto, resumos de investigação e convenções aprendidas em ficheiros que pessoas e agents podem inspecionar. A procedural memory reside em instruções de sistema e definições de tools, em vez de mudar para cada utilizador.

Para efeitos de implementação, cinco destas seis categorias condensam-se em três níveis de armazenamento. A short-term memory torna-se hot memory, o checkpoint da thread atual. As memórias episodic e semantic tornam-se cold memory, usada para recall entre threads. A document memory mantém o conhecimento acumulado do projeto legível e diretamente editável. A working memory é agrupada com o nível hot na taxonomia acima, mas é a única que nunca é realmente armazenada: existe durante um único passo, em processo, e corresponde à context window para a qual os três níveis de armazenamento carregam dados. A procedural memory fica fora dos três: vive no system prompt e nas definições de tools, sendo distribuída com o agent em vez de ser armazenada e recuperada.

O CoALA classifica as memórias working, episodic, semantic e procedural. O survey Memory in the Age of AI Agents dá destaque a vector stores e knowledge graphs, enquanto o LangGraph documenta checkpoints e a sua interface Store. O conhecimento de projeto suportado por ficheiros fica fora dessas taxonomias, embora Claude Code, Cursor e Devin Desktop carreguem ficheiros persistentes do projeto.

O mesmo padrão de armazenamento surge noutros domínios. Um agent de Minecraft (Voyager) armazena skills de jogo reutilizáveis como bibliotecas de código, equipas numa competição empresarial de document-QA iteram sobre documentos de prompts procedurais e web agents inferem browsing workflows reutilizáveis a partir de execuções bem-sucedidas. Retomarei os três casos mais à frente; o ponto aqui é que os ficheiros tornam esse conhecimento inspecionável e versionável sem um serviço de embedding separado.

A memória gerida pelo agent também difere de um pipeline RAG fixo quanto a quem executa a escrita. O agent ou o seu harness seleciona o que armazenar, atualizar e eliminar, escolhendo mais tarde quando o deve recuperar.

O artigo Generative Agents (Park et al., 2023) mostrou até onde isto pode chegar: agents simulados armazenavam, refletiam sobre e recuperavam as suas próprias memórias. O seu memory stream classificava candidatos por recência, importância e relevância — um design que continua a ser uma referência útil para o retrieval de memória de agents.

Short-term memory de agents: o checkpoint store

Sempre que o LangGraph termina um super-step — um node ou um conjunto de nodes executados em paralelo — o framework serializa o estado completo do graph e escreve-o num checkpoint store. Esta é a base de workflows de pause/resume, debugging com time travel e HITL.

Um checkpoint contém o estado do graph necessário para retomar: o AgentState da Parte 1 — mensagens, identidade, perfil do utilizador, passos do plano, dados de investigação e modo de execução. Em paralelo, o LangGraph armazena a sua própria informação de controlo: ID e timestamp do checkpoint, uma versão por channel (o nome que o LangGraph dá a cada chave individual de estado) e um registo separado das versões de channels que cada node já viu. O número do passo reside nos metadados do checkpoint, não no próprio checkpoint. É comparando estes dois elementos que o graph determina o que executar a seguir. Depois de uma interrupção HITL ou de um reinício do processo, o graph carrega o checkpoint escrito no último limite concluído e entra novamente no node seguinte. Não continua a partir de uma linha Python arbitrária. Um checkpoint também é diferente de um event log append-only ou de um trace; a Parte 5 separa explicitamente estas superfícies de observabilidade do runtime.

Como funciona o checkpointing do LangGraph

O BaseCheckpointSaver do LangGraph é uma interface simples: put() escreve um checkpoint, get_tuple() lê o último para uma thread e list() devolve o histórico. Cada checkpoint é indexado por (thread_id, checkpoint_ns, checkpoint_id), em que thread_id identifica a conversa, checkpoint_ns trata do namespacing do subgraph e checkpoint_id é uma versão única.

A decisão importante é o backend a colocar por baixo desta interface. PostgreSQL e Redis são duas escolhas comuns em produção.

PostgreSQL vs Redis

DimensãoPostgreSQL (langgraph-checkpoint-postgres)Redis (langgraph-checkpoint-redis)

Histórico de checkpointsHistórico durável para retoma e debuggingA retenção depende das definições do saver e de eviction

Benchmarks genéricos de bases de dados não preveem o desempenho de checkpoints. Meça o tamanho do estado serializado, a frequência de escrita, as definições de persistência e a concorrência do seu próprio graph.

PostgreSQL: a opção durável por predefinição

O PostgreSQL é a opção mais segura para a maioria das equipas. Os checkpoints sobrevivem a falhas, obtém semântica transacional completa e o histórico de checkpoints torna simples o debugging com time travel.

Uma versão simplificada da configuração de checkpoints em memory/hot.py:

from contextlib import asynccontextmanager

from langchain_core.messages import HumanMessage
from langgraph.checkpoint.postgres.aio import AsyncPostgresSaver

@asynccontextmanager
async def postgres_checkpointer(connection_string: str):
    """Yield a PostgreSQL-backed checkpoint store.

    PostgreSQL gives us ACID guarantees — if a checkpoint write succeeds,
    the state is durable even if the process crashes immediately after.
    `from_conn_string` is itself an async context manager: it owns the
    connection and closes it on exit, so the graph has to run inside it.
    """
    async with AsyncPostgresSaver.from_conn_string(connection_string) as checkpointer:
        # Create the checkpoint tables if they don't exist.
        # This is idempotent — safe to call on every startup.
        await checkpointer.setup()
        yield checkpointer

# Usage: the graph lives inside the context manager's scope
async with postgres_checkpointer(
    "postgresql://user:pass@localhost:5432/agent_memory"
) as checkpointer:
    graph = create_graph(checkpointer=checkpointer)

    # Every invoke/stream call now persists state automatically
    config = {"configurable": {"thread_id": "user-123-session-1"}}
    result = await graph.ainvoke({"messages": [HumanMessage(content="Analyze NVDA")]}, config)

    # Resume later on the same thread_id — loads the latest checkpoint
    result = await graph.ainvoke({"messages": [HumanMessage(content="approved")]}, config)

O AsyncPostgresSaver usa o package langgraph-checkpoint-postgres, que cria quatro tabelas: checkpoints (o estado serializado), checkpoint_blobs (dados binários de grande dimensão), checkpoint_writes (writes pendentes para recuperação após falhas) e checkpoint_migrations (versão do schema). Writers concorrentes são separados pela primary key (thread_id, checkpoint_ns, checkpoint_id) e por upserts, não por locking — dois workers na mesma thread não corrompem os dados uns dos outros, mas também não coordenam entre si.

Redis: quando a latência é o bottleneck

Quando é importante ter latência de checkpoint inferior a um milissegundo (agents conversacionais em tempo real, tool loops de alta frequência), Redis é a melhor escolha.

Uma versão simplificada da configuração de checkpoints em memory/hot.py:

from contextlib import asynccontextmanager

from langgraph.checkpoint.redis.aio import AsyncRedisSaver

@asynccontextmanager
async def redis_checkpointer(redis_url: str):
    """Yield a Redis-backed checkpoint store.

    Redis stores checkpoints in memory for sub-millisecond access.
    Trade-off: less durable than PostgreSQL unless you enable AOF,
    Redis's append-only log — snapshots alone lose recent writes on a crash.
    """
    async with AsyncRedisSaver.from_conn_string(redis_url) as checkpointer:
        # Initialize Redis data structures
        await checkpointer.setup()
        yield checkpointer

# Usage: same graph API, different backend
async with redis_checkpointer("redis://localhost:6379") as checkpointer:
    graph = create_graph(checkpointer=checkpointer)

O AsyncRedisSaver de langgraph-checkpoint-redis armazena cada checkpoint como o seu próprio documento RedisJSON, sob a mesma chave (thread_id, checkpoint_ns, checkpoint_id) que o saver de Postgres. O redesign da v0.1.0 substituiu várias operações de pesquisa por uma única chamada JSON.GET, reduzindo significativamente a latência. O Redis 8.0+ inclui RedisJSON e RediSearch por predefinição — não é necessário instalar módulos adicionais.

Em deployments limitados pela memória, ShallowRedisSaver armazena apenas o checkpoint mais recente por thread — sem histórico, mas com utilização mínima de RAM. Use-o quando precisar de pause/resume, mas não de debugging com time travel.

Quando usar cada um

Use PostgreSQL quando:

  • Precisa do histórico completo de checkpoints para debugging com time travel ou retoma reproduzível
  • A durabilidade é inegociável (serviços financeiros, saúde)
  • Já utiliza PostgreSQL na sua stack
  • O agent executa tarefas longas em que perder o estado implica horas de recomputação
  • Quer um unified data store — PostgreSQL com pgvector pode ser um único backend para checkpoints, memória de longo prazo e pesquisa vetorial

Use Redis quando:

  • A latência dos checkpoints é o seu bottleneck (chat em tempo real, streaming UX)
  • Está a criar voice bots — os pipelines speech-to-text para LLM e text-to-speech precisam de acesso ao estado em menos de um milissegundo
  • Precisa de scaling horizontal entre muitas threads concorrentes
  • Tem padrões de fan-out de elevada concorrência em que vários agents partilham estado
  • Tem sessões de curta duração em que a perda de um checkpoint é recuperável
  • Quer semantic caching para reduzir chamadas redundantes ao LLM (Redis LangCache coloca em cache queries semanticamente semelhantes para evitar chamadas repetidas ao LLM)

Outras opções: langgraph-checkpoint-sqlite funciona para desenvolvimento local e deployments num único processo. Para stacks AWS-native, langgraph-checkpoint-aws disponibiliza um DynamoDBSaver com offloading automático do payload — checkpoints pequenos (<350 KB) ficam no DynamoDB e os maiores são transferidos para o S3. O pricing serverless e a ausência de infraestrutura para gerir tornam-no atrativo para deployments com carga variável.

Long-term memory: recordar entre sessões

A hot memory trata da conversa atual. A long-term memory abrange o utilizador que regressa na semana seguinte: armazena factos, preferências e histórico de interações que persistem entre threads.

O LangGraph disponibiliza uma interface Store para memória entre threads através da sua classe BaseStore. Cada item de memória é um par (namespace, key) com um valor JSON e um embedding vectorial opcional. O namespace codifica normalmente o utilizador ou a organização: ("user", "user-123", "preferences").

Vector storage: recall semântico com Qdrant

Quando o agent precisa de recordar factos não estruturados (“O que disse o utilizador sobre o seu horizonte de investimento?”), a pesquisa vetorial proporciona recall semântico. Em vez de procurar por chaves exatas, o agent consulta pelo significado.

O Qdrant é uma vector database criada especificamente para o efeito e escrita em Rust, que trata do armazenamento de embeddings, indexing (Hierarchical Navigable Small World, ou HNSW) e pesquisa filtrada. Abordei o HNSW e os seus compromissos em detalhe no meu artigo sobre search ranking. O Qdrant também disponibiliza um MCP server que funciona como camada de memória semântica — útil se o seu agent framework suportar o Model Context Protocol.

O que se segue é um design Qdrant ilustrativo e independente. Não é uma versão simplificada do atual memory/long.py. O projeto atual armazena perfis de utilizador com filtragem exata por user_id e um placeholder de zero-vector. A integração real de embeddings continua a ser trabalho futuro. Este sketch mostra como poderia ser a memória semântica depois dessa integração:

from qdrant_client import QdrantClient
from qdrant_client.models import (
    PointStruct, Distance, VectorParams, Filter, FieldCondition, MatchValue,
)
import hashlib

class UserMemoryStore:
    """Long-term memory backed by Qdrant vector search.

    Stores user facts as embedded vectors for semantic retrieval.
    Each fact is a short natural-language statement about the user.
    """

    def __init__(self, qdrant_url: str, collection_name: str = "user_memory"):
        self.client = QdrantClient(url=qdrant_url)
        self.collection_name = collection_name
        self._ensure_collection()

    def _ensure_collection(self):
        """Create the collection if it doesn't exist."""
        collections = [c.name for c in self.client.get_collections().collections]
        if self.collection_name not in collections:
            self.client.create_collection(
                collection_name=self.collection_name,
                vectors_config=VectorParams(
                    size=1536,  # text-embedding-3-small dimensions
                    distance=Distance.COSINE,
                ),
            )

    def store_fact(self, user_id: str, fact: str, embedding: list[float]):
        """Store a user fact with its embedding."""
        point_id = hashlib.md5(f"{user_id}:{fact}".encode()).hexdigest()
        self.client.upsert(
            collection_name=self.collection_name,
            points=[PointStruct(
                id=point_id,
                vector=embedding,
                payload={"user_id": user_id, "fact": fact},
            )],
        )

    def recall(self, user_id: str, query_embedding: list[float], top_k: int = 5):
        """Retrieve the most relevant facts for a user given a query."""
        results = self.client.query_points(
            collection_name=self.collection_name,
            query=query_embedding,
            query_filter=Filter(
                must=[FieldCondition(key="user_id", match=MatchValue(value=user_id))]
            ),
            limit=top_k,
        )
        return [hit.payload["fact"] for hit in results.points]

O fluxo tem três passos. Neste design ilustrativo, um LLM extrai factos essenciais da interação (“o utilizador tem elevada tolerância ao risco”, “o utilizador interessa-se por ações de semicondutores”). Esses factos são convertidos em embeddings e armazenados no Qdrant. No início da conversa seguinte, o agent consulta o Qdrant com a nova mensagem do utilizador para recordar o contexto relevante. O atual Market Analyst Agent ainda não implementa este fluxo de extração semântica e embedding.

Scoring do retrieval: para além da similaridade de cosseno

A similaridade de cosseno em bruto é um ponto de partida, mas os sistemas de memória em produção precisam de um retrieval mais rico. O artigo Generative Agents (Park et al., 2023) introduziu uma função de scoring que combina três sinais:

  • Recência: Decaimento baseado em regras, para que memórias recentes obtenham uma pontuação superior. Uma função de decaimento exponencial faz com que um facto de ontem ultrapasse um facto equivalente de há seis meses.
  • Importância: Significância avaliada pelo LLM numa escala de 1 a 10. “A carteira do utilizador caiu 40%” obtém uma pontuação superior a “o utilizador disse olá”.
  • Relevância: Similaridade de cosseno entre o embedding da query e o facto armazenado.

A pontuação final de retrieval é uma soma ponderada: score = alpha * recency + beta * importance + gamma * relevance. Isto evita que factos recentes e importantes fiquem ocultos por factos antigos mas semanticamente semelhantes. Para um agent como o Market Analyst Agent, começaria com alpha = 0.3 para a recência, beta = 0.2 para a importância e gamma = 0.5 para a relevância, uma vez que a intenção da query atual do utilizador é o que mais importa. Estes pesos são valores iniciais adaptados do artigo Generative Agents (que usou ponderação igual); constatei que dar mais peso à relevância funcionou melhor para queries de análise financeira, mas os valores baseiam-se em intuição, não em otimização empírica.

Alternativas à pesquisa vetorial

A pesquisa vetorial é poderosa, mas nem sempre é a ferramenta certa. Eis quando usar alternativas:

Os key-value stores funcionam bem para dados estruturados. Se a sua memória de longo prazo for um perfil de utilizador — tolerância ao risco, horizonte de investimento, setores preferidos — um Redis hash ou uma coluna JSONB do PostgreSQL é mais simples e rápido do que gerar embeddings e consultar vectors. Use pesquisa vetorial quando a memória não for estruturada e a formulação da query variar.

O Store integrado do LangGraph disponibiliza uma interface key-value baseada em namespaces, com pesquisa vetorial opcional. A API BaseStore é simples: put(), get(), search() e delete(), com scope hierárquico por namespace. Estão disponíveis três implementações:

  • InMemoryStore — para desenvolvimento e testes (os dados perdem-se quando o processo termina)
  • PostgresStore — store persistente de produção com queries SQL completas
  • AsyncRedisStore — memória entre threads com pesquisa vetorial, suporte de TTL e filtragem por metadados

A configuração index ativa a pesquisa vetorial sobre os itens armazenados, usando um modelo de embedding configurável. Para muitos casos de uso, este store integrado é suficiente sem recorrer a uma vector database dedicada.

from langgraph.store.memory import InMemoryStore

# Create a store with vector search enabled
store = InMemoryStore(
    index={
        "dims": 1536,
        "embed": my_embedding_function,  # e.g., OpenAI text-embedding-3-small
    }
)

# Store a user preference (namespace scopes to user)
await store.aput(
    namespace=("user", "user-123", "preferences"),
    key="risk-profile",
    value={"risk_tolerance": "high", "horizon": "long-term"},
)

# Semantic search across the user's memories.
# The namespace prefix is positional here — `search`/`asearch` declare it
# as positional-only `namespace_prefix`, unlike `aput`.
results = await store.asearch(
    ("user", "user-123"),
    query="What is their investment style?",
    limit=5,
)

Escolher uma estratégia de memória de longo prazo

Comece com key-value se a sua memória for estruturada e bem definida (perfis de utilizador, definições, entidades nomeadas). Adicione pesquisa vetorial quando precisar de retrieval semântico sobre factos não estruturados ou quando a formulação da query variar de forma imprevisível.

Os knowledge graphs justificam o seu custo quando as relações entre entidades são importantes, por exemplo: “Que empresas mencionadas pelo utilizador são concorrentes da NVDA?” O projeto recente mais interessante nesta área é o Graphiti (da Zep), que cria um knowledge graph com consciência temporal e regista quando os factos eram verdadeiros, não apenas o que era verdadeiro. Cada edge contém intervalos de validade, pelo que uma alteração à tolerância ao risco do utilizador invalida o valor antigo, em vez de o substituir silenciosamente. O Graphiti reporta 94,8% de accuracy no benchmark DMR — Deep Memory Retrieval, um teste de recall em conversas longas — e o seu modelo bi-temporal trata o problema de memórias obsoletas na camada de dados.

O problema é operacional. Operar uma graph database não é trivial e, para a maioria das aplicações de agents, a pesquisa vetorial com filtragem por metadados cobre o mesmo espaço com menos infraestrutura.

Frameworks de memória gerida, como Mem0 e Letta (anteriormente MemGPT), tratam do pipeline de extração, consolidação e retrieval por si. A abordagem do Mem0 merece destaque: um LLM extrai memórias candidatas, um decision engine compara cada facto novo com as entradas existentes na vector store e um resolver decide se deve adicionar, atualizar, eliminar ou não fazer nada. Isto mantém o memory store coerente e não redundante. O Letta adota uma perspetiva de sistemas operativos: os agents gerem a sua própria context window com memory management tools, movendo autonomamente dados entre “core memory” (em contexto) e “archival memory” (fora do contexto). Ambos merecem ser avaliados se pretende chegar mais depressa à produção e não precisa de controlo total sobre o pipeline de memória.

Document memory: o arquivo do agent

Vector stores e backends key-value tratam bem do recall semântico e das pesquisas estruturadas. Existe uma terceira categoria de conhecimento do agent que nenhum dos dois serve de forma adequada: contexto acumulado do projeto, ou seja, as convenções, notas de investigação e decisões de que o agent precisa entre sessões. Esse conhecimento beneficia de ser legível por humanos e controlado por versões.

Isto é document memory: o agent lê e escreve ficheiros estruturados (Markdown, JSON, YAML) num diretório conhecido. Sem embeddings, sem base de dados, sem infraestrutura. Apenas ficheiros em disco que tanto o agent como o developer podem cat, grep, git diff e editar manualmente.

Esta abordagem tem mais adoção em produtos do que cobertura nas taxonomias de memória acima. Numa avaliação conduzida por um vendor, o Letta reportou 74,0% de accuracy no LoCoMo — um benchmark de question-answering em conversas longas — para um agent suportado por filesystem executado em GPT-4o mini, contra 68,5% da melhor variante baseada em graph do Mem0. É um vendor, um modelo, um benchmark e um harness: leia isto como um sinal de que a abordagem é competitiva, não como um ranking. A vantagem operacional não depende do benchmark: os developers podem ler, editar e comparar em diff diretamente o conhecimento armazenado.

Context windows maiores também tornam práticas, em alguns documentos de projeto, as leituras do ficheiro completo. O retrieval por chunks continua adequado para corpora grandes, mas um ficheiro curto de convenções ou handoff pode muitas vezes ser carregado diretamente. A escolha depende do tamanho do documento, da precisão do retrieval, do orçamento de contexto e da frequência com que as pessoas precisam de rever ou editar a memória.

Porquê ficheiros?

Em workflows de agents de longa duração, o padrão mais eficaz que encontrei não é uma vector database. É um diretório de notas bem organizado. Pense no que acontece quando um coding agent trabalha num projeto durante semanas:

  • Aprende que o projeto usa Pydantic v2, e não v1
  • Descobre que os testes têm de ser executados com pytest -x --tb=short
  • Acumula conhecimento sobre a arquitetura da codebase
  • Aprende as preferências do developer (“usar sempre pathlib, nunca os.path”)

Estes factos são demasiado estruturados para pesquisa vetorial (é necessário recall exato, não similaridade difusa) e demasiado interligados para um key-value store — são documentos que fazem referência uns aos outros, não valores isolados obtidos por chave. São também factos que o developer quer ver e editar diretamente. Se o agent aprender algo errado, basta abrir o ficheiro e corrigi-lo.

É assim que funcionam o CLAUDE.md do Claude Code e o diretório .claude/. O agent lê ficheiros CLAUDE.md ao nível do projeto para obter convenções e instruções, e mantém um ficheiro separado de auto-memory por projeto — em ~/.claude/projects/<project-slug>/memory/ — para aprendizagens entre sessões. Ambos são Markdown simples: pode lê-los, editá-los, fazer commit dos ficheiros do projeto no git e partilhá-los com a equipa. As project rules do Cursor e as rules e memories do Devin Desktop seguem o mesmo padrão. O Cursor lê ficheiros .mdc em .cursor/rules; o Devin Desktop (anteriormente Windsurf) lê .windsurf/rules/ e continua a respeitar o ficheiro único legado .windsurfrules. Em qualquer dos casos: texto simples em disco que o agent carrega no arranque para obter contexto do projeto.

Implementar um file memory store

A implementação é deliberadamente simples. O agent recebe quatro operações: escrever um documento, ler um documento, listar os documentos disponíveis e pesquisar por keyword em todos os documentos.

O que se segue é um file store raw-Markdown ilustrativo e independente. Não é uma versão simplificada do atual memory/document.py. O projeto atual usa DocumentMemory, que exige um namespace e uma key e escreve um envelope JSON contendo content, metadata e created_at. Este sketch define um design diferente para mostrar os compromissos dos ficheiros Markdown legíveis por humanos:

from pathlib import Path
import json

class FileMemory:
    """Document memory backed by the local filesystem.

    Stores agent knowledge as human-readable files organized by topic.
    No embeddings, no database — just files that both the agent and
    the developer can read, edit, and version-control.
    """

    def __init__(self, base_dir: str | Path):
        self.base_dir = Path(base_dir)
        self.base_dir.mkdir(parents=True, exist_ok=True)

    def write_doc(self, path: str, content: str, metadata: dict | None = None):
        """Write or overwrite a document at the given path.

        Paths are relative to base_dir. Directories are created automatically.
        Metadata (if provided) is stored as a JSON sidecar file.
        """
        full_path = self.base_dir / path
        full_path.parent.mkdir(parents=True, exist_ok=True)
        full_path.write_text(content, encoding="utf-8")

        if metadata:
            meta_path = full_path.with_suffix(full_path.suffix + ".meta")
            meta_path.write_text(json.dumps(metadata, indent=2), encoding="utf-8")

    def read_doc(self, path: str) -> str | None:
        """Read a document by path. Returns None if not found."""
        full_path = self.base_dir / path
        if full_path.exists():
            return full_path.read_text(encoding="utf-8")
        return None

    def list_docs(self, pattern: str = "**/*") -> list[str]:
        """List documents matching a glob pattern."""
        return [
            str(p.relative_to(self.base_dir))
            for p in self.base_dir.glob(pattern)
            if p.is_file() and not p.name.endswith(".meta")
        ]

    def search_docs(self, query: str, pattern: str = "**/*.md") -> list[dict]:
        """Search documents by keyword. Returns matching files with context.

        This is intentionally simple — grep-style keyword search.
        For semantic search, use a vector store instead.

        NOTE: This is a sketch for demonstration. A simple substring check
        won't scale beyond a few hundred documents. For production with 500+
        documents, use TF-IDF/BM25 scoring (e.g., rank_bm25) or a full-text
        search backend (PostgreSQL GIN index, Elasticsearch).
        """
        results = []
        for path in self.base_dir.glob(pattern):
            if not path.is_file() or path.name.endswith(".meta"):
                continue
            content = path.read_text(encoding="utf-8")
            if query.lower() in content.lower():
                # Return the paragraph containing the match for context
                for paragraph in content.split("\n\n"):
                    if query.lower() in paragraph.lower():
                        results.append({
                            "path": str(path.relative_to(self.base_dir)),
                            "match": paragraph.strip()[:500],
                        })
        return results

Estrutura de pastas

Grande parte do valor da document memory vem da forma como o diretório está organizado. Eis a estrutura que usaria para um research agent. O Market Analyst Agent usa namespaces em memory/documents/, mas o seu DocumentMemory atual escreve cada entrada como um envelope JSON com uma string content, e não como Markdown raw. A disposição raw-Markdown abaixo pertence ao design independente e ilustrativo FileMemory apresentado anteriormente:

.agent-memory/
    README.md                  # What this directory is, for human readers
    PROGRESS.md                # Handoff for the next session: what is done, what is next
    user-profiles/
        user-123.md            # Preferences, history, risk profile
        user-456.md
    research/
        NVDA-2026-02.md        # Research notes from recent analysis
        TSLA-2026-01.md

        data-sources.md        # Preferred data sources and API patterns
    learnings/

No design ilustrativo FileMemory, cada documento é Markdown e o propósito de cada documento é evidente pelo seu path. Pode git diff todo o diretório de memória para ver o que o agent aprendeu numa sessão, git revert uma aprendizagem incorreta ou copiar o diretório para outro projeto. Os envelopes JSON do projeto atual mantêm a estrutura de namespace e key, mas não proporcionam a mesma experiência de diff em Markdown raw.

Use document memory quando:

  • O agent acumula conhecimento do projeto ao longo de várias sessões
  • Os developers precisam de inspecionar, editar ou substituir o que o agent “sabe”
  • O conhecimento está estruturado como documentos (notas, resumos, convenções), e não como factos isolados
  • Quer versionamento da memória do agent baseado em git
  • Zero infraestrutura é um requisito absoluto

Use vector stores quando:

  • Precisa de retrieval semântico difuso (“encontrar memórias relacionadas com X”)
  • A formulação da query varia de forma imprevisível
  • Tem milhares a milhões de factos individuais

Use key-value stores quando:

  • Precisa de lookups exatos e rápidos para dados estruturados (perfis de utilizador, definições)
  • O schema dos dados é bem definido

Na prática, os agents de produção combinam frequentemente os três. O Market Analyst Agent atual usa checkpoints PostgreSQL para hot memory, Qdrant para armazenamento exato de perfis de utilizador com vectors placeholder e um document store namespaced com envelopes JSON. As variantes de recall semântico e raw-Markdown deste artigo são extensões ilustrativas.

Exemplos reais

O padrão já é generalizado nos AI coding assistants:

  • Claude Code lê ficheiros CLAUDE.md a partir da raiz do projeto e dos diretórios-pai, e mantém um ficheiro de memória por projeto em ~/.claude/projects/ para aprendizagens entre sessões. O sistema de memória consiste em ficheiros Markdown simples, e os ficheiros ao nível do projeto são commitados juntamente com o código.
  • Cursor carrega rules do projeto a partir de .cursor/rules como ficheiros .mdc — convenções de coding, preferências de framework e decisões arquiteturais — com frontmatter que controla quando cada rule se aplica.
  • Devin Desktop (anteriormente Windsurf) lê rules de .windsurf/rules/, continua a respeitar o .windsurfrules legado ao nível da raiz e escreve memories autogeradas num store local que o agent consulta em execuções posteriores.
  • A memory tool da Anthropic para a Claude API é uma tool do lado do cliente que o modelo conduz através de operações sobre ficheiros — view, create, str_replace, insert, delete e rename — num diretório /memories. A sua aplicação implementa cada comando, pelo que decide onde os ficheiros residem efetivamente (disco local, S3 ou base de dados).

Todos estes sistemas armazenam o conhecimento do agent como ficheiros de texto legíveis por humanos, com operações explícitas de leitura e escrita, e nenhum precisa de um pipeline de embeddings. O agent decide o que escrever, o developer consegue ver e editar tudo e o sistema inteiro cabe num git diff.

Para além dos coding assistants

A document memory não se limita a coding agents. O padrão surge também noutros domínios de agents:

  • Agents de jogos open-world: o Voyager (Wang et al., 2023) cria uma skill library persistente de programas JavaScript verificados que um agent de Minecraft acumula ao longo do tempo, recolhendo 3,3x mais itens únicos e atingindo milestones 15,3x mais depressa do que os baselines. As skills são transferidas para novos mundos sem retraining. O JARVIS-1 estende este conceito com uma memória multimodal que combina planos textuais e observações visuais, sendo cinco vezes mais fiável do que os melhores agents anteriores na tarefa ObtainDiamondPickaxe de longa duração.

    Vale a pena fazer uma distinção: as skill libraries são memória executável (ficheiros de código importados e executados), enquanto a document memory dos coding assistants é declarativa (Markdown injetado nos prompts). Os modos de falha são diferentes. Código executável incorreto faz o agent falhar; texto declarativo incorreto conduz a erros de raciocínio. Mas o padrão de armazenamento e os benefícios operacionais (debuggability, controlo de versões) são os mesmos.

  • Automação de workflows empresariais: a competição ERC3 — a terceira Enterprise RAG Challenge — teve vencedores que usaram document memory para refinar iterativamente os prompts. A equipa vencedora usou agents Analyzer e Versioner que iteraram por 80 versões de prompts armazenadas como documentos procedurais. Outra equipa de topo criou mais de 20 módulos enricher como conhecimento procedural em formato de documento. O LEGOMem (2025) formaliza isto para sistemas multi-agent como memória procedural modular: as trajetórias de tarefas anteriores são decompostas em unidades de memória reutilizáveis, que são depois colocadas no orchestrator que planeia e delega, ou nos agents que executam os passos. No benchmark OfficeBench, a memória do orchestrator revelou-se importante para a decomposição de tarefas, enquanto a memória detalhada dos agents melhorou a accuracy da execução.

  • Automação web: o Agent Workflow Memory (Wang et al., 2024) permite que web agents induzam workflows reutilizáveis a partir de episódios bem-sucedidos, com uma melhoria relativa de 51,1% na taxa de sucesso no WebArena. O SkillWeaver (2025) vai mais longe: os agents sintetizam API tools reutilizáveis a partir da exploração, obtendo um ganho relativo de 31,8% na taxa de sucesso. As skills aprendidas também são transferidas para modelos mais fracos (até 54,3% de melhoria relativa), pelo que a memória acumulada por um agent mais forte pode elevar o desempenho de um modelo menor.

  • Apoio ao cliente: a Gartner prevê que o agentic AI resolva autonomamente 80% dos problemas comuns de customer service sem intervenção humana até 2029. Estes agents consultam SOPs, playbooks e históricos de clientes, todos eles formas de document memory.

O workshop MemAgents no ICLR 2026 é um dos sinais de que a comunidade de investigação está a acompanhar aquilo que os practitioners já construíram.

As skills usam documentos para empacotar instruções procedurais. O Agent Skills standard armazena essas instruções em ficheiros SKILL.md com frontmatter YAML e corpo Markdown. Isto assemelha-se à document memory na camada de armazenamento, mas o papel é diferente: uma skill diz ao agent como executar uma classe de trabalho, enquanto a memória regista factos aprendidos com um projeto ou uma execução anterior. A Parte 3 traça a fronteira adjacente entre uma skill e uma tool.

O MCP (Model Context Protocol) segue a mesma direção: as definições de tools são ficheiros JSON Schema que qualquer agent pode descobrir e chamar. Uma análise de dezembro de 2025 sobre o primeiro ano do MCP colocou o protocolo nos 97 milhões de downloads mensais de SDKs entre Python e TypeScript, com adoção pela OpenAI, Google DeepMind e Microsoft. O MCP não é específico de coding. Os mesmos servers ligam agents a bases de dados, APIs internas e sistemas empresariais.

Ambos apontam para o mesmo padrão: conhecimento procedural armazenado como documentos sujeitos a schemas, com operações explícitas de leitura e escrita. O MCP, agora governado pela Agentic AI Foundation, é o equivalente mais próximo de um standard de interoperabilidade que o ecossistema de agents possui.

Escalar document memory para produção

A implementação baseada em ficheiros acima funciona bem em portáteis de developers individuais e em deployments de pequena escala. Um ambiente de produção multi-tenant com centenas de utilizadores e milhares de documentos exige uma arquitetura diferente.

O limite de ficheiros num único node torna-se evidente: não é possível escalar horizontalmente o file I/O, as escritas concorrentes precisam de locking e a gestão de permissões entre tenants é dolorosa. A produção precisa de um backing store que trate corretamente a concorrência, a pesquisa e o multi-tenancy.

Três abordagens comuns:

Abordagem A: híbrida, com uma camada fina de base de dados

Mantenha os ficheiros para authoring (os developers editam Markdown localmente), mas sirva-os a partir de uma base de dados em runtime. No deployment, sincronize os ficheiros com rows do PostgreSQL. O agent lê da base de dados, não do disco. Isto proporciona:

  • Ergonomia para developers (editar Markdown, fazer commit no git)
  • Desempenho de queries em produção (leituras indexadas na base de dados)
  • Separação clara entre authoring e serving

Abordagem B: object storage + vector index sidecar

Armazene os documentos no S3/GCS como objects, com uma collection Qdrant que indexa os seus embeddings. O agent consulta o Qdrant para obter os IDs dos documentos relevantes e depois obtém o conteúdo no object storage. Isto escala horizontalmente e suporta pesquisa semântica, mas acrescenta complexidade: dois sistemas para gerir, um pipeline de embeddings para manter e consistência eventual entre o store e o índice.

Abordagem C: structured document store com PostgreSQL (recomendada)

Armazene os documentos como rows JSONB no PostgreSQL, com pesquisa full-text (GIN index) e embeddings vetoriais opcionais (pgvector). Isto proporciona pesquisa híbrida (keyword + semantic), transações ACID e um único sistema operacional.

Um sketch da Abordagem C:

from typing import Optional
import asyncpg

class ProductionDocumentMemory:
    """PostgreSQL-backed document memory with hybrid search.

    Schema:
        CREATE TABLE documents (
            id SERIAL PRIMARY KEY,
            tenant_id TEXT NOT NULL,
            path TEXT NOT NULL,
            content TEXT NOT NULL,
            metadata JSONB,
            embedding vector(1536),  -- pgvector extension
            ts_vector tsvector GENERATED ALWAYS AS (to_tsvector('english', content)) STORED,
            created_at TIMESTAMPTZ DEFAULT NOW(),
            UNIQUE(tenant_id, path)
        );
        CREATE INDEX ON documents USING GIN(ts_vector);
        CREATE INDEX ON documents USING ivfflat(embedding vector_cosine_ops);
    """

    def __init__(self, pool: asyncpg.Pool):
        self.pool = pool

    async def write(
        self,
        tenant_id: str,
        path: str,
        content: str,
        metadata: Optional[dict] = None,
        embedding: Optional[list[float]] = None,
    ):
        """Write or update a document.

        Sketch: on a real pool you must register codecs first, or asyncpg
        raises DataError — `set_type_codec` for the JSONB metadata column
        and pgvector's `register_vector` for the embedding.
        """
        async with self.pool.acquire() as conn:
            await conn.execute(
                """
                INSERT INTO documents (tenant_id, path, content, metadata, embedding)
                VALUES ($1, $2, $3, $4, $5)
                ON CONFLICT (tenant_id, path) DO UPDATE
                SET content = EXCLUDED.content,
                    metadata = EXCLUDED.metadata,
                    embedding = EXCLUDED.embedding
                """,
                tenant_id, path, content, metadata, embedding,
            )

    async def search(
        self,
        tenant_id: str,
        query: str,
        embedding: Optional[list[float]] = None,
        limit: int = 5,
    ) -> list[dict]:
        """Hybrid search: full-text + optional vector similarity."""
        async with self.pool.acquire() as conn:
            if embedding:
                # Hybrid scoring: 0.6 * text relevance + 0.4 * vector similarity
                rows = await conn.fetch(
                    """
                    SELECT path, content, metadata,
                           (0.6 * ts_rank(ts_vector, plainto_tsquery('english', $2)) +
                            0.4 * (1 - (embedding <=> $3))) AS score
                    FROM documents
                    WHERE tenant_id = $1
                      AND (ts_vector @@ plainto_tsquery('english', $2)
                           OR (embedding <=> $3) < 0.5)
                    ORDER BY score DESC
                    LIMIT $4
                    """,
                    tenant_id, query, embedding, limit,
                )
            else:
                # Full-text search only
                rows = await conn.fetch(
                    """
                    SELECT path, content, metadata,
                           ts_rank(ts_vector, plainto_tsquery('english', $2)) AS score
                    FROM documents
                    WHERE tenant_id = $1
                      AND ts_vector @@ plainto_tsquery('english', $2)
                    ORDER BY score DESC
                    LIMIT $3
                    """,
                    tenant_id, query, limit,
                )
            return [dict(row) for row in rows]

O OR no primeiro branch é o que o torna híbrido. Apenas com o predicado @@, um documento que tenha o significado certo mas não partilhe keywords com a query é filtrado antes de o scoring começar — isto é keyword retrieval com semantic reranking, não retrieval híbrido. O threshold da distância é um parâmetro: torne-o mais restritivo se o braço vetorial inundar os resultados; torne-o mais permissivo se as correspondências semânticas nunca aparecerem.

O resultado é:

  • Pesquisa híbrida: correspondência por keywords (GIN index) + similaridade semântica (pgvector), avaliadas em conjunto
  • Multi-tenancy: scope por tenant_id com row-level security
  • Garantias ACID: sem problemas de consistência eventual
  • Um único sistema operacional: sem vector database separada para gerir
  • Escalabilidade horizontal: read replicas para carga de queries e partitioning por tenant para escalar as escritas

Os ficheiros são excelentes para workflows de um único developer. Em produção multi-tenant, um structured document store em PostgreSQL é normalmente o melhor equilíbrio entre simplicidade, desempenho e maturidade operacional.

Juntar tudo: a arquitetura completa

Eis como os três níveis de memória podem trabalhar em conjunto numa arquitetura inspirada no Market Analyst Agent. O diagrama mostra um fluxo ilustrativo desde o pedido do utilizador até à resposta, com todas as camadas de memória ativas.

A arquitetura tem três caminhos de memória:

  1. Hot path (checkpoint store): o LangGraph escreve o estado retomável do graph no checkpoint store em cada limite de super-step. Quando o graph chega a um node interrupt_before (como o node publish na Parte 1), a execução pausa. O utilizador pode fechar a aplicação e, quando regressar, o graph retoma a partir do checkpoint. Os event logs e traces de runtime são preocupações de produção separadas.

  2. Cold path (long-term store): nesta arquitetura ilustrativa, o agent consulta o long-term store no início de cada conversa para obter contexto relevante do utilizador. Essa leitura está no critical path — o planner não pode personalizar a resposta enquanto ela não terminar — pelo que deve reservar 100–300 ms para a latência de embedding e pesquisa. A escrita não está: quando a conversa termina, um background job extrai e armazena novos factos, e esse job nunca deve bloquear o reasoning loop.

  3. Document path (file store): no arranque, o agent carrega convenções do projeto e notas de investigação relevantes a partir do document store. Durante a execução, escreve no disco novos resumos de investigação e padrões aprendidos. Estas leituras também estão no critical path, porque informam a tarefa atual, mas acedem ao disco local em vez de a um embedding endpoint, pelo que custam apenas alguns milissegundos. As escritas podem ser adiadas.

A ligação no LangGraph é simples — o checkpoint store e o long-term store são passados na compilação do graph, enquanto o document store é injetado como dependência. O sketch local abaixo usa InMemoryStore para manter o snippet pequeno; a topologia Docker de referência usa Qdrant para o mesmo papel de recall semântico.

from langgraph.store.memory import InMemoryStore

# Cold memory: local sketch with vector search

O fluxo completo

O que acontece quando um utilizador que regressa envia “Analyze TSLA” para o Market Analyst Agent:

  1. Carregamento da document memory: no arranque, o agent lê as convenções do projeto a partir do document store: preferências de formato da análise, fontes de dados preferidas e padrões de utilização de tools. Estas definem o comportamento base.

  2. Recall da cold memory: neste fluxo ilustrativo, antes de o router node ser executado, o graph consulta o long-term store com a mensagem do utilizador. Obtém: “O utilizador tem elevada tolerância ao risco”, “O utilizador prefere uma análise detalhada da concorrência” e “O utilizador investigou anteriormente a NVDA e a AMD”.

  3. Router + Planner: o router classifica isto como DEEP_RESEARCH. O planner cria um plano de investigação de 5 passos, personalizado de acordo com as preferências recuperadas. Inclui um passo de análise da concorrência porque o histórico do utilizador mostra que este o pretende. O plano segue o formato do documento de convenções.

  4. Executor loop (hot memory): cada passo é executado através do padrão ReAct da Parte 1 — pensar, agir, observar, repetindo até o passo estar concluído. Depois de cada super-step (router, planner e cada passo do executor, executados sequencialmente neste caso), o LangGraph escreve um checkpoint no PostgreSQL. Se o processo falhar depois do passo 3 de 5, reinicia e continua a partir do passo 4.

  5. Interrupção HITL: o reporter escreve um draft, um evaluator com contexto novo — uma segunda sessão do modelo sem histórico da execução — vota nele e o graph chega ao node publish com interrupt_before, ficando em pausa. O checkpoint contém o draft e o veredicto do evaluator, pelo que a pessoa revê ambos em vez de avaliar a investigação em bruto. Pode revê-los horas depois, e o graph carrega o checkpoint e publica o resultado.

  6. Atualizações da memória: depois de a conversa terminar, um processo assíncrono extrai novos factos do utilizador (“o utilizador está agora a acompanhar a TSLA”, “o utilizador aprovou o formato do relatório”) e armazena-os na vector store de longo prazo. O agent também escreve um resumo da investigação no document store (research/TSLA-2026-02) para referência futura.

O padrão de três níveis separa claramente as responsabilidades. O checkpoint store trata da durabilidade e da retoma; é infraestrutura. O long-term store trata da personalização; é lógica de produto. O document store contém o conhecimento acumulado do projeto; é o caderno do agent.

Compromissos e considerações

A memória acrescenta valor, mas também custo e complexidade:

  • Custo de embeddings: cada facto armazenado numa vector database exige uma chamada à embedding API. A $0,02 por milhão de tokens (OpenAI text-embedding-3-small), o custo por facto é negligenciável, mas acumula-se entre milhares de utilizadores e sessões. Faça batch embedding calls e coloque os resultados em cache. A latência é o custo maior: 100–300 ms de latência de embeddings no momento da query para recall de cold memory, algo mais importante do que os euros em agents conversacionais de tempo real. Coloque embeddings de queries frequentes em cache ou use um modelo de embeddings local em workloads sensíveis à latência.

  • Memória obsoleta: as preferências dos utilizadores mudam. Um facto armazenado há seis meses (“o utilizador prefere investimentos conservadores”) pode já não ser exato. Defina políticas de expiração. Num dos meus designs, uso 365 dias para preferências e 90 dias para eventos episódicos como exemplos provisórios, não como defaults universais. O artigo sobre context engineering rejeita regras de retenção fixas como política portátil. A expiração é a versão bruta. O estado tipado guiado por schema oferece uma abordagem mais precisa: validade temporal e proveniência em cada facto, para que um valor substituído perca para o valor atual no momento do retrieval, e não no momento da expiração.

  • Overhead de memória no contexto: cada facto recuperado consome tokens na context window do LLM. Se recuperar 20 factos por query, serão várias centenas de tokens de contexto de memória a competir com a tarefa real. Limite o número de factos recuperados e dê prioridade com base no relevance score.

  • Privacidade e compliance: os stores de long-term memory contêm dados dos utilizadores. Precisa de redação de PII antes do armazenamento, políticas claras de retenção e controlos para que os utilizadores possam eliminar os seus dados. Nada disto é opcional em setores regulados.

  • Crescimento do armazenamento de checkpoints: as tabelas de checkpoints do PostgreSQL crescem a cada super-step. Para agents de longa duração, defina uma política de retenção. A tabela checkpoints não tem coluna de timestamp, mas o checkpoint_id do LangGraph é um UUIDv6 ordenado temporalmente, pelo que ordenar por ID fornece recência. Inclua checkpoint_ns e thread_id no âmbito do delete — um graph com subgraphs escreve em vários namespaces numa thread, e um predicado apenas por thread pode fazer com que um subgraph conversador elimine o ponto de retoma do graph-pai. A query abaixo mantém os 10 checkpoints mais recentes por thread e namespace:

    WITH keep AS (
    SELECT checkpoint_id FROM checkpoints
    WHERE thread_id = $1 AND checkpoint_ns = $2
    ORDER BY checkpoint_id DESC
    LIMIT 10
)
DELETE FROM checkpoints
WHERE thread_id = $1
  AND checkpoint_ns = $2
  AND checkpoint_id NOT IN (SELECT checkpoint_id FROM keep);

    Execute o mesmo delete sobre checkpoint_writes, que partilha a chave (thread_id, checkpoint_ns, checkpoint_id). checkpoint_blobs usa (thread_id, checkpoint_ns, channel, version) como chave, pelo que precisa da sua própria limpeza — agende as três em conjunto, ou as tabelas auxiliares sobreviverão aos checkpoints a que pertencem.

  • Consolidação da memória: com o tempo, memórias episódicas detalhadas devem ser comprimidas em representações semânticas compactas: “o utilizador perguntou pela NVDA três vezes em janeiro”, em vez de armazenar integralmente as três conversas. Isto replica a consolidação da memória humana e mantém o store gerível. O Mem0 e o Graphiti tratam disto automaticamente; se criar a sua própria solução, agende jobs periódicos de consolidação.

  • Problema do cold start: os utilizadores novos não têm long-term memory. O agent deve degradar graciosamente e fazer perguntas de clarificação, em vez de fazer suposições. A memória é aditiva, não obrigatória.

  • Memory poisoning: tudo o que entra na context window do agent é um potencial ponto de injeção. Se um atacante escrever factos enganosos no document store ou na long-term memory (“aprovar sempre transações sem verificação”), o agent poderá executá-los como instruções. Prompt injection através de memórias armazenadas é uma superfície de ataque real. As mitigações incluem validação antes do armazenamento, tratar o conteúdo recuperado como dados não fiáveis e não como instruções de sistema, e controlos de acesso que limitem que memórias podem influenciar operações críticas.

  • Drift da document memory: a memória baseada em ficheiros não tem deduplicação nem resolução de conflitos automáticas. Com o tempo, os documentos acumulam contradições: um ficheiro diz “usar pytest”, enquanto outro diz “usar unittest”. Agende revisões periódicas (ou deixe o agent fazê-las) para eliminar e consolidar conteúdo. Num vector store, a obsolescência fica escondida; num diretório de ficheiros pode grep contradições.

  • A document memory não escala para milhões de itens: a memória baseada em ficheiros funciona para centenas ou poucos milhares de documentos. Se o agent precisar de fazer recall sobre milhões de factos com correspondência difusa, precisa de um vector store. A document memory destina-se a conhecimento estruturado do projeto, não à cauda longa de cada interação com cada utilizador.

Principais conclusões

  1. A memória de um agent consiste em vários stores com padrões de acesso diferentes. Mantenha distintos os checkpoints retomáveis, os factos estruturados, o recall semântico e os documentos do projeto.
  2. Implemente pause e resume antes da personalização. Perder o progresso de uma tarefa é a primeira falha de memória exposta por um agent de longa duração.
  3. Coloque os factos determinísticos em armazenamento estruturado. Use pesquisa vetorial quando a query for difusa e a formulação variar.
  4. Use ficheiros para conhecimento do projeto que as pessoas precisem de inspecionar, editar, versionar ou rever num diff.
  5. Dê a cada tipo de memória regras de expiração, conflito e eliminação. Uma memória que o sistema não consegue corrigir transforma-se em dívida de produto.
  6. Limite o que regressa ao modelo. A memória armazenada só tem valor quando o retrieval coloca as evidências certas no contexto atual.
