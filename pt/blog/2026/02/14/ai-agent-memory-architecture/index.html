Arquitetura de memória de AI Agents: Checkpoints e Vector Stores

Parte 2 da série Engineering the Agentic Stack

Um reasoning loop só sobrevive a um pedido se o seu estado for armazenado fora do worker. Sem agent memory, o agent não consegue retomar um plano pausado, recuperar depois de uma falha ou recordar uma preferência de uma sessão anterior. A Parte 1 abordou o fluxo de controlo. Este artigo identifica de que estado cada turno subsequente precisa e onde esse estado deve residir.

Vou explicar a arquitetura de memória do Market Analyst Agent — um pequeno agent LangGraph que obtém dados de mercado e escreve um relatório de analista — mostrando como hot checkpoints, cold vector stores e memória documental baseada em ficheiros trabalham em conjunto para agents de longa duração. Depois, abordarei quando faz sentido usar PostgreSQL, Redis, Qdrant, key-value stores e ficheiros Markdown simples.

Em resumo: Separe a memória por padrão de acesso. A hot memory é o estado de checkpoint por conversa, utilizado para pausar e retomar. A cold memory contém factos entre sessões num key-value store ou vector store. A document memory mantém o conhecimento do projeto em ficheiros inspecionáveis. Comece pela falha que precisa de corrigir e escolha depois o store. Não coloque factos exatos num sistema de fuzzy retrieval nem trate um checkpoint como um audit log.

Todos os stores abaixo são lidos pelo harness, o código que conduz o loop em torno do modelo. O harness decide que partes do seu conteúdo chegam à context window; os stores não. Este artigo aborda onde esse estado reside antes de o harness o consultar. A Parte 3 e a Parte 4 explicam o que o harness faz depois com o prompt.

O que é a memória de um AI agent?

A AI agent memory é a camada de estado que permite a um agent preservar o progresso de uma tarefa, recuperar conhecimento anterior e atualizar aquilo que sabe entre execuções. Em produção, não é uma única vector database. É uma combinação de hot checkpoints, stores semânticos ou estruturados cold e document memory legível por humanos.

Não comece pela memória só porque parece inteligente. Comece pela falha visível para o utilizador: perder progresso, esquecer uma preferência, repetir investigação ou não reutilizar uma convenção do projeto.

As falhas que exigem memória

Um agent sem estado consegue responder a uma pergunta isolada, mas esquece o pedido assim que a chamada termina. Esse desenho falha quando o produto precisa de algum dos seguintes comportamentos:

  • Pausar e retomar: um utilizador inicia uma tarefa de investigação, fecha o portátil e regressa no dia seguinte. Sem estado em checkpoint, o agent recomeça do zero.
  • Coerência multi-turno: ao longo de uma conversa extensa, o agent tem de recordar que tools chamou, que dados recolheu e que passos do plano concluiu.
  • Personalização: um utilizador que regressa espera que o agent conheça a sua tolerância ao risco, a profundidade de análise preferida e as interações anteriores.
  • Human-in-the-loop (HITL): o agent recolhe as evidências e espera que um humano aprove o passo seguinte. O estado de espera tem de sobreviver a reinícios do processo.

No Market Analyst Agent da Parte 1, o pedido “Analyze NVDA” produz um plano, cinco tool calls, dados recolhidos e um relatório preliminar. Quando o utilizador responde “parece bem, mas acrescenta uma análise da concorrência”, um checkpoint store permite ao agent carregar o estado do último passo concluído e acrescentar o passo da concorrência. Sem estado em checkpoint, não consegue perceber a que se refere “parece bem” e tem de recomeçar.

A memória de longo prazo trata de um caso diferente. Se o utilizador regressar uma semana depois e perguntar “Atualiza a minha análise da NVDA”, o agent poderá ter de recordar uma preferência por avaliações de risco conservadoras e um interesse em ações de semicondutores. Um vector-backed memory store consegue recuperar esses factos entre sessões sem voltar a perguntar por eles.

Os exemplos de implementação abaixo usam LangGraph, a biblioteca open-source do LangChain para criar agents como grafos de estado explícitos; as fronteiras de armazenamento que define generalizam-se a qualquer framework. O LangGraph separa a memória por âmbito. Cada execução do grafo ocorre dentro de uma thread, ou seja, uma conversa ou tarefa. O estado persistido nessa thread é short-term memory. O estado partilhado entre threads é long-term memory. Abaixo, “thread” e “conversation” são intercambiáveis; evito “session” para esse intervalo, porque a Parte 5 reserva o termo para o log durável de uma execução, podendo várias execuções acumular-se numa thread. O contexto atual do modelo e as variáveis em processo formam a camada de working memory acima de ambos os stores.

Uma taxonomia da memória de AI Agents

Antes de abordar a implementação, é útil classificar aquilo que os agents precisam de recordar. O framework CoALA — Cognitive Architectures for Language Agents (Sumers, Yao et al., 2023) — é uma taxonomia amplamente citada, baseada na ciência cognitiva. Introduzi o scoping da memória no meu artigo sobre context engineering; aqui amplio-o para seis categorias:

Tipo de memóriaÂmbitoDuraçãoExemploPadrão de armazenamento
WorkingPasso atualMilissegundosArgumentos de tool call, resposta atual do LLMEm processo (Python dict)
Short-termThread atualMinutos–horasHistórico da conversa, progresso do plano, dados recolhidosCheckpoint store

A working memory é aquilo com que o LLM está a raciocinar neste momento: variáveis Python na função atual, o conteúdo da context window e argumentos de tool call durante a execução. É a camada mais rápida e efémera. Nada persiste para além do passo atual. A working memory é limitada pela context window do modelo, o que a torna o bottleneck. Tudo aquilo que o agent “sabe” no momento de decidir tem de caber aqui, quer venha do checkpoint store, de uma consulta vetorial ou da leitura de um ficheiro. Os outros níveis existem para alimentar a working memory com a informação certa no momento certo.

A short-term memory é o checkpoint que o LangGraph escreve após cada unidade de execução do grafo — um super-step, definido na secção seguinte. As memórias episodic e semantic persistem entre threads. A document memory armazena notas de projeto, resumos de investigação e convenções aprendidas em ficheiros que pessoas e agents podem inspecionar. A procedural memory reside nas instruções do sistema e nas definições das tools, em vez de mudar para cada utilizador.

Para efeitos de implementação, cinco das seis categorias agrupam-se em três níveis de armazenamento. A short-term memory torna-se hot memory, o checkpoint da thread atual. A memória episódica e a semântica tornam-se cold memory, para recuperação entre threads. A document memory mantém o conhecimento acumulado do projeto legível e diretamente editável. A working memory aparece agrupada com o nível hot na taxonomia acima, mas é a única que nunca é realmente armazenada: existe durante um único passo, em processo, e corresponde à context window para a qual os três níveis de armazenamento carregam informação. A procedural memory fica fora dos três: reside no system prompt e nas definições das tools, sendo distribuída com o agent em vez de ser armazenada e recuperada.

A CoALA classifica as memórias working, episodic, semantic e procedural. O inquérito Memory in the Age of AI Agents dá ênfase a vector stores e knowledge graphs, enquanto o LangGraph documenta checkpoints e a sua interface Store. O conhecimento de projeto suportado por ficheiros fica fora dessas taxonomias, embora Claude Code, Cursor e Devin Desktop carreguem todos ficheiros persistentes do projeto.

O mesmo padrão de armazenamento surge noutros domínios. Um agent de Minecraft (Voyager) armazena skills de jogo reutilizáveis como bibliotecas de código; equipas numa competição empresarial de document-QA iteram sobre documentos procedurais de prompts; e web agents inferem workflows de browsing reutilizáveis a partir de execuções bem-sucedidas. Retomarei os três casos mais à frente; o ponto aqui é que os ficheiros tornam esse conhecimento inspecionável e versionável sem um serviço de embedding separado.

A memória gerida pelo agent também difere de um pipeline RAG fixo devido a quem efetua a escrita. O agent ou o seu harness seleciona o que armazenar, atualizar e apagar, escolhendo mais tarde quando o recuperar.

O artigo Generative Agents (Park et al., 2023) mostrou até onde isto pode chegar: agents simulados armazenaram, refletiram sobre e recuperaram as suas próprias memórias. O seu memory stream classificava candidatos por recência, importância e relevância, um desenho que continua a ser uma referência útil para a recuperação em agent memory.

Memória de curto prazo de AI Agents: o checkpoint store

Sempre que o LangGraph termina um super-step — um nó ou um conjunto de nós executados em paralelo — o framework serializa o estado completo do grafo e escreve-o num checkpoint store. Esta é a base para workflows de pausa/retoma, debugging com time travel e HITL.

Um checkpoint contém o estado do grafo necessário para retomar: o AgentState da Parte 1 — mensagens, identidade, perfil do utilizador, passos do plano, dados de investigação e modo de execução. Paralelamente, o LangGraph armazena o seu próprio bookkeeping: o ID e timestamp do checkpoint, uma versão por canal (o nome do LangGraph para uma chave de estado individual) e um registo separado das versões de canal que cada nó já viu. O número do passo reside nos metadados do checkpoint, não no checkpoint em si. É através da comparação entre estes elementos que o grafo determina o que deve ser executado a seguir. Depois de uma interrupção HITL ou de um reinício do processo, o grafo carrega o checkpoint escrito no último limite concluído e reentra no nó seguinte. Não continua a partir de uma linha Python arbitrária. Um checkpoint também é diferente de um event log append-only ou de um trace; a Parte 5 separa explicitamente essas superfícies de observabilidade do runtime.

Como funciona o checkpointing do LangGraph

O BaseCheckpointSaver do LangGraph é uma interface simples: put() escreve um checkpoint, get_tuple() lê o mais recente para uma thread e list() devolve o histórico. Cada checkpoint é identificado por (thread_id, checkpoint_ns, checkpoint_id), em que thread_id identifica a conversa, checkpoint_ns trata do namespacing de subgrafos e checkpoint_id é uma versão única.

A decisão importante é escolher o backend que ficará por trás da interface. PostgreSQL e Redis são duas opções comuns em produção.

PostgreSQL vs Redis

Benchmarks genéricos de bases de dados não preveem o desempenho do checkpointing. Meça o tamanho do estado serializado, a frequência de escrita, as definições de persistência e a concorrência do seu próprio grafo.

PostgreSQL: a predefinição durável

O PostgreSQL é a predefinição mais segura para a maioria das equipas. Os checkpoints sobrevivem a falhas, obtém semântica transacional completa e o histórico de checkpoints torna simples o debugging com time travel.

Uma versão simplificada da configuração de checkpoints em memory/hot.py:

from contextlib import asynccontextmanager

from langchain_core.messages import HumanMessage
from langgraph.checkpoint.postgres.aio import AsyncPostgresSaver

@asynccontextmanager
async def postgres_checkpointer(connection_string: str):
    """Yield a PostgreSQL-backed checkpoint store.

    PostgreSQL gives us ACID guarantees — if a checkpoint write succeeds,
    the state is durable even if the process crashes immediately after.
    `from_conn_string` is itself an async context manager: it owns the
    connection and closes it on exit, so the graph has to run inside it.
    """
    async with AsyncPostgresSaver.from_conn_string(connection_string) as checkpointer:
        # Create the checkpoint tables if they don't exist.
        # This is idempotent — safe to call on every startup.
        await checkpointer.setup()
        yield checkpointer

# Usage: the graph lives inside the context manager's scope
async with postgres_checkpointer(
    "postgresql://user:pass@localhost:5432/agent_memory"
) as checkpointer:
    graph = create_graph(checkpointer=checkpointer)

    # Every invoke/stream call now persists state automatically
    config = {"configurable": {"thread_id": "user-123-session-1"}}
    result = await graph.ainvoke({"messages": [HumanMessage(content="Analyze NVDA")]}, config)

    # Resume later on the same thread_id — loads the latest checkpoint
    result = await graph.ainvoke({"messages": [HumanMessage(content="approved")]}, config)

O AsyncPostgresSaver usa o pacote langgraph-checkpoint-postgres, que cria quatro tabelas: checkpoints (o estado serializado), checkpoint_blobs (dados binários de grandes dimensões), checkpoint_writes (escritas pendentes para recuperação após falhas) e checkpoint_migrations (versão do schema). Os writers concorrentes são separados pela primary key (thread_id, checkpoint_ns, checkpoint_id) e por upserts, não por locking — dois workers na mesma thread não corrompem os dados um do outro, mas também não coordenam entre si.

Redis: quando a latência é o bottleneck

Quando é importante obter latência de checkpoint inferior a um milissegundo (agents conversacionais em tempo real, tool loops de alta frequência), o Redis é a melhor opção.

Uma versão simplificada da configuração de checkpoints em memory/hot.py:

from contextlib import asynccontextmanager

from langgraph.checkpoint.redis.aio import AsyncRedisSaver

@asynccontextmanager
async def redis_checkpointer(redis_url: str):
    """Yield a Redis-backed checkpoint store.

    Redis stores checkpoints in memory for sub-millisecond access.
    Trade-off: less durable than PostgreSQL unless you enable AOF,
    Redis's append-only log — snapshots alone lose recent writes on a crash.
    """
    async with AsyncRedisSaver.from_conn_string(redis_url) as checkpointer:
        # Initialize Redis data structures
        await checkpointer.setup()
        yield checkpointer

# Usage: same graph API, different backend
async with redis_checkpointer("redis://localhost:6379") as checkpointer:
    graph = create_graph(checkpointer=checkpointer)

O AsyncRedisSaver de langgraph-checkpoint-redis armazena cada checkpoint como um documento RedisJSON independente, usando a mesma chave (thread_id, checkpoint_ns, checkpoint_id) que o saver de Postgres. O redesign da v0.1.0 substituiu várias operações de pesquisa por uma única chamada JSON.GET, reduzindo significativamente a latência. O Redis 8.0+ inclui RedisJSON e RediSearch por predefinição — não é necessário instalar módulos adicionais.

Para deployments limitados pela memória, ShallowRedisSaver armazena apenas o checkpoint mais recente por thread — sem histórico, mas com utilização mínima de RAM. Use-o quando precisar de pausa/retoma, mas não de debugging com time travel.

Quando usar cada opção

Use PostgreSQL quando:

  • Precisa do histórico completo de checkpoints para debugging com time travel ou retoma reproduzível
  • A durabilidade é inegociável (serviços financeiros, saúde)
  • Já utiliza PostgreSQL na sua stack
  • O agent executa tarefas longas em que perder o estado significa horas de recomputação
  • Quer um unified data store — PostgreSQL com pgvector pode servir como backend único para checkpoints, memória de longo prazo e vector search

Use Redis quando:

  • A latência dos checkpoints é o seu bottleneck (chat em tempo real, UX de streaming)
  • Está a criar voice bots — pipelines de speech-to-text para LLM e de text-to-speech precisam de acesso ao estado inferior a um milissegundo
  • Precisa de scaling horizontal entre muitas threads concorrentes
  • Tem padrões de fan-out de elevada concorrência em que vários agents partilham estado
  • Tem sessões de curta duração em que a perda de um checkpoint é recuperável
  • Quer semantic caching para reduzir chamadas redundantes ao LLM (Redis LangCache armazena em cache queries semanticamente semelhantes para evitar chamadas repetidas ao LLM)

Outras opções: langgraph-checkpoint-sqlite funciona para desenvolvimento local e deployments de um único processo. Para stacks AWS-native, langgraph-checkpoint-aws disponibiliza um DynamoDBSaver com offloading automático do payload — checkpoints pequenos (<350 KB) permanecem no DynamoDB, enquanto os maiores são transferidos para S3. O preço serverless e a ausência de infraestrutura para gerir tornam-no atrativo para deployments com carga variável.

Memória de longo prazo: recordar entre sessões

A hot memory trata da conversa atual. A memória de longo prazo abrange o utilizador que regressa na semana seguinte: armazena factos, preferências e histórico de interações que persistem entre threads.

O LangGraph disponibiliza uma interface Store para memória entre threads através da sua classe BaseStore. Cada item de memória é um par (namespace, key) com um valor JSON e um vector embedding opcional. O namespace normalmente codifica o utilizador ou a organização: ("user", "user-123", "preferences").

Vector storage: recuperação semântica com Qdrant

Quando o agent precisa de recuperar factos não estruturados (“O que disse o utilizador sobre o seu horizonte de investimento?”), a pesquisa vetorial fornece recuperação semântica. Em vez de pesquisas por chave exata, o agent consulta pelo significado.

O Qdrant é uma vector database especializada, escrita em Rust, que trata do armazenamento de embeddings, indexação (Hierarchical Navigable Small World, ou HNSW) e pesquisa filtrada. Abordei detalhadamente o HNSW e os seus compromissos no meu artigo sobre search ranking. O Qdrant também disponibiliza um MCP server que funciona como uma camada de memória semântica — útil se o seu agent framework suportar o Model Context Protocol.

Uma versão simplificada do vector store em memory/long.py:

from qdrant_client import QdrantClient
from qdrant_client.models import (
    PointStruct, Distance, VectorParams, Filter, FieldCondition, MatchValue,
)
import hashlib

class UserMemoryStore:
    """Long-term memory backed by Qdrant vector search.

    Stores user facts as embedded vectors for semantic retrieval.
    Each fact is a short natural-language statement about the user.
    """

    def __init__(self, qdrant_url: str, collection_name: str = "user_memory"):
        self.client = QdrantClient(url=qdrant_url)
        self.collection_name = collection_name
        self._ensure_collection()

    def _ensure_collection(self):
        """Create the collection if it doesn't exist."""
        collections = [c.name for c in self.client.get_collections().collections]
        if self.collection_name not in collections:
            self.client.create_collection(
                collection_name=self.collection_name,
                vectors_config=VectorParams(
                    size=1536,  # text-embedding-3-small dimensions
                    distance=Distance.COSINE,
                ),
            )

    def store_fact(self, user_id: str, fact: str, embedding: list[float]):
        """Store a user fact with its embedding."""
        point_id = hashlib.md5(f"{user_id}:{fact}".encode()).hexdigest()
        self.client.upsert(
            collection_name=self.collection_name,
            points=[PointStruct(
                id=point_id,
                vector=embedding,
                payload={"user_id": user_id, "fact": fact},
            )],
        )

    def recall(self, user_id: str, query_embedding: list[float], top_k: int = 5):
        """Retrieve the most relevant facts for a user given a query."""
        results = self.client.query_points(
            collection_name=self.collection_name,
            query=query_embedding,
            query_filter=Filter(
                must=[FieldCondition(key="user_id", match=MatchValue(value=user_id))]
            ),
            limit=top_k,
        )
        return [hit.payload["fact"] for hit in results.points]

O fluxo tem três passos. Depois de cada conversa, um LLM extrai factos importantes da interação (“o utilizador tem elevada tolerância ao risco”, “o utilizador está interessado em ações de semicondutores”). Esses factos são transformados em embeddings e armazenados no Qdrant. No início da conversa seguinte, o agent consulta o Qdrant com a nova mensagem do utilizador para recuperar o contexto relevante.

Retrieval scoring: além da similaridade do cosseno

A similaridade bruta do cosseno é um ponto de partida, mas os sistemas de memória em produção precisam de uma recuperação mais rica. O artigo Generative Agents (Park et al., 2023) introduziu uma função de pontuação que combina três sinais:

  • Recência: Decaimento baseado em regras para que memórias recentes obtenham pontuações superiores. Uma função de decaimento exponencial faz com que um facto de ontem ultrapasse um facto equivalente de há seis meses.
  • Importância: Significância avaliada pelo LLM numa escala de 1 a 10. “A carteira do utilizador perdeu 40%” obtém uma pontuação superior a “o utilizador disse olá”.
  • Relevância: Similaridade do cosseno entre o embedding da query e o facto armazenado.

A pontuação final de recuperação é uma soma ponderada: score = alpha * recency + beta * importance + gamma * relevance. Assim, os factos recentes e importantes não ficam ocultos sob factos antigos mas semanticamente semelhantes. Para um agent como o Market Analyst Agent, começaria com alpha = 0.3 para a recência, beta = 0.2 para a importância e gamma = 0.5 para a relevância, uma vez que a intenção da query atual do utilizador é o fator mais importante. Estes são pesos iniciais adaptados do artigo Generative Agents (que usou pesos iguais); constatei que dar mais peso à relevância funcionava melhor para queries de análise financeira, mas os valores baseiam-se na intuição, não em otimização empírica.

Alternativas à pesquisa vetorial

A pesquisa vetorial é poderosa, mas nem sempre é a ferramenta certa. Eis quando usar alternativas:

AbordagemMelhor paraPrincipal custo operacional
Pesquisa vetorial (Qdrant)Recuperação semântica de factos não estruturadosCiclo de vida de embeddings e índices
Key-value store (Redis)Perfis e preferências estruturados do utilizadorUtilização de memória e política de persistência
Document store (ficheiros)Conhecimento de projeto e notas geridas pelo agentConcorrência, permissões e pesquisa
Full-text search (PostgreSQL GIN index)Recuperação por palavras-chave no históricoCrescimento do índice e afinação das queries
Knowledge graph (Neo4j)Relações entre entidades e queries multi-hopModelação do grafo e outro sistema de dados
Híbrida (vetorial + keywords)Recuperação quando a intenção da query variaDois percursos de pontuação para afinar e avaliar

Os key-value stores funcionam bem para dados estruturados. Se a sua memória de longo prazo for um perfil de utilizador — tolerância ao risco, horizonte de investimento, setores preferidos — um hash Redis ou uma coluna JSONB do PostgreSQL é mais simples e rápido do que criar embeddings e consultar vetores. Use pesquisa vetorial quando a memória não for estruturada e a query de recuperação variar na formulação.

O Store integrado do LangGraph disponibiliza uma interface key-value baseada em namespaces, com pesquisa vetorial opcional. A API BaseStore é simples: put(), get(), search() e delete(), com scoping hierárquico de namespaces. Estão disponíveis três implementações:

  • InMemoryStore — para desenvolvimento e testes (os dados perdem-se quando o processo termina)
  • PostgresStore — store persistente de produção com queries SQL completas
  • AsyncRedisStore — memória entre threads com pesquisa vetorial, suporte de TTL e filtragem por metadados

A configuração index ativa a pesquisa vetorial nos itens armazenados utilizando um modelo de embedding configurável. Para muitos casos de uso, este store integrado é suficiente sem recorrer a uma vector database dedicada.

from langgraph.store.memory import InMemoryStore

# Create a store with vector search enabled
store = InMemoryStore(
    index={
        "dims": 1536,
        "embed": my_embedding_function,  # e.g., OpenAI text-embedding-3-small
    }
)

# Store a user preference (namespace scopes to user)
await store.aput(
    namespace=("user", "user-123", "preferences"),
    key="risk-profile",
    value={"risk_tolerance": "high", "horizon": "long-term"},
)

# Semantic search across the user's memories.
# The namespace prefix is positional here — `search`/`asearch` declare it
# as positional-only `namespace_prefix`, unlike `aput`.
results = await store.asearch(
    ("user", "user-123"),
    query="What is their investment style?",
    limit=5,
)

Escolher uma estratégia de memória de longo prazo

Comece com key-value se a sua memória for estruturada e bem definida (perfis de utilizador, definições, entidades nomeadas). Acrescente pesquisa vetorial quando precisar de recuperação semântica sobre factos não estruturados ou quando a formulação da query variar de forma imprevisível.

Os knowledge graphs justificam o seu custo quando as relações entre entidades são importantes, por exemplo: “De que empresas falou o utilizador que são concorrentes da NVDA?” O projeto recente mais interessante neste domínio é o Graphiti (da Zep), que cria um knowledge graph com consciência temporal e acompanha quando os factos eram verdadeiros, não apenas o que era verdadeiro. Cada aresta contém intervalos de validade, pelo que uma alteração à tolerância ao risco do utilizador invalida o valor antigo em vez de o substituir silenciosamente. O Graphiti reporta 94,8% de accuracy no benchmark DMR — Deep Memory Retrieval, um teste de recuperação em conversas longas — e o seu modelo bitemporal trata o problema das memórias obsoletas na camada de dados.

O problema é operacional. Operar uma graph database não é trivial e, para a maioria das aplicações com agents, a pesquisa vetorial com filtragem por metadados cobre o mesmo terreno com menos infraestrutura.

Frameworks de memória gerida, como Mem0 e Letta (anteriormente MemGPT), tratam por si do pipeline de extração, consolidação e recuperação. A abordagem do Mem0 é particularmente interessante: um LLM extrai memórias candidatas, um motor de decisão compara cada facto novo com as entradas existentes no vector store e um resolver decide se deve adicionar, atualizar, apagar ou não fazer nada. Isto mantém o memory store coerente e sem redundâncias. O Letta adota uma perspetiva de sistemas operativos: os agents gerem a sua própria context window utilizando ferramentas de gestão de memória, movendo autonomamente dados entre “core memory” (em contexto) e “archival memory” (fora do contexto). Vale a pena avaliar ambos se quiser reduzir o time-to-production e não precisar de controlo total sobre o pipeline de memória.

Document memory: o arquivo do agent

Os vector stores e os backends key-value tratam bem da recuperação semântica e das pesquisas estruturadas. Existe uma terceira categoria de conhecimento de agents que nenhum dos dois serve adequadamente: contexto acumulado do projeto, incluindo convenções, notas de investigação e decisões de que o agent precisa entre sessões. Esse conhecimento beneficia de ser legível por humanos e controlado por versões.

Isto é document memory: o agent lê e escreve ficheiros estruturados (Markdown, JSON, YAML) num diretório conhecido. Sem embeddings, sem base de dados, sem infraestrutura. Apenas ficheiros em disco que tanto o agent como o developer podem cat, grep, git diff e editar manualmente.

Este padrão tem maior adoção em produtos do que cobertura nas taxonomias de memória acima. Numa avaliação realizada por um fornecedor, a Letta reportou 74,0% de accuracy no LoCoMo — um benchmark de question answering em conversas longas — para um agent suportado por filesystem a correr em GPT-4o mini, contra 68,5% da melhor variante baseada em grafos do Mem0. Trata-se de um fornecedor, um modelo, um benchmark e um harness: interprete o resultado como sinal de que a abordagem é competitiva, não como um ranking. A vantagem operacional não depende do benchmark: os developers podem ler, editar e comparar diretamente o conhecimento armazenado.

As context windows maiores também tornam práticos os carregamentos de ficheiros completos para alguns documentos de projeto. O retrieval por chunks continua adequado para corpora grandes, mas um ficheiro curto de convenções ou handoff pode muitas vezes ser carregado diretamente. A escolha depende do tamanho do documento, da precisão de recuperação, do orçamento de contexto e da frequência com que as pessoas precisam de rever ou editar a memória.

Porquê ficheiros?

Em workflows de agents de longa duração, o padrão mais eficaz que encontrei não é uma vector database. É um diretório de notas bem organizado. Considere o que acontece quando um coding agent trabalha num projeto durante semanas:

  • Aprende que o projeto usa Pydantic v2, não v1
  • Descobre que os testes têm de ser executados com pytest -x --tb=short
  • Acumula conhecimento sobre a arquitetura da codebase
  • Aprende as preferências do developer (“usar sempre pathlib, nunca os.path”)

Estes factos são demasiado estruturados para pesquisa vetorial (é necessária recuperação exata, não similaridade aproximada) e demasiado interligados para um key-value store — são documentos que fazem referência uns aos outros, não valores isolados que se obtêm por chave. São também factos que o developer quer ver e editar diretamente. Se o agent aprender algo errado, basta abrir o ficheiro e corrigi-lo.

É assim que funcionam o CLAUDE.md do Claude Code e o diretório .claude/. O agent lê ficheiros CLAUDE.md ao nível do projeto para obter convenções e instruções, e mantém um ficheiro de auto-memory separado por projeto — em ~/.claude/projects/<project-slug>/memory/ — para aprendizagens entre sessões. Ambos são Markdown simples: pode lê-los, editá-los, fazer commit dos ficheiros do projeto no git e partilhá-los com a equipa. As project rules do Cursor e as rules and memories do Devin Desktop seguem o mesmo padrão. O Cursor lê ficheiros .mdc a partir de .cursor/rules; o Devin Desktop (anteriormente Windsurf) lê .windsurf/rules/ e continua a respeitar o antigo ficheiro único .windsurfrules. Em qualquer dos casos: texto simples em disco que o agent carrega no arranque para obter o contexto do projeto.

Implementar um file memory store

A implementação é deliberadamente simples. O agent recebe quatro operações: escrever um documento, ler um documento, listar os documentos disponíveis e pesquisar em todos os documentos por palavra-chave.

Uma versão simplificada do document store em memory/document.py:

from pathlib import Path
import json

class FileMemory:
    """Document memory backed by the local filesystem.

    Stores agent knowledge as human-readable files organized by topic.
    No embeddings, no database — just files that both the agent and
    the developer can read, edit, and version-control.
    """

    def __init__(self, base_dir: str | Path):
        self.base_dir = Path(base_dir)
        self.base_dir.mkdir(parents=True, exist_ok=True)

    def write_doc(self, path: str, content: str, metadata: dict | None = None):
        """Write or overwrite a document at the given path.

        Paths are relative to base_dir. Directories are created automatically.
        Metadata (if provided) is stored as a JSON sidecar file.
        """
        full_path = self.base_dir / path
        full_path.parent.mkdir(parents=True, exist_ok=True)
        full_path.write_text(content, encoding="utf-8")

        if metadata:
            meta_path = full_path.with_suffix(full_path.suffix + ".meta")
            meta_path.write_text(json.dumps(metadata, indent=2), encoding="utf-8")

    def read_doc(self, path: str) -> str | None:
        """Read a document by path. Returns None if not found."""
        full_path = self.base_dir / path
        if full_path.exists():
            return full_path.read_text(encoding="utf-8")
        return None

    def list_docs(self, pattern: str = "**/*") -> list[str]:
        """List documents matching a glob pattern."""
        return [
            str(p.relative_to(self.base_dir))
            for p in self.base_dir.glob(pattern)
            if p.is_file() and not p.name.endswith(".meta")
        ]

    def search_docs(self, query: str, pattern: str = "**/*.md") -> list[dict]:
        """Search documents by keyword. Returns matching files with context.

        This is intentionally simple — grep-style keyword search.
        For semantic search, use a vector store instead.

        NOTE: This is a sketch for demonstration. A simple substring check
        won't scale beyond a few hundred documents. For production with 500+
        documents, use TF-IDF/BM25 scoring (e.g., rank_bm25) or a full-text
        search backend (PostgreSQL GIN index, Elasticsearch).
        """
        results = []
        for path in self.base_dir.glob(pattern):
            if not path.is_file() or path.name.endswith(".meta"):
                continue
            content = path.read_text(encoding="utf-8")
            if query.lower() in content.lower():
                # Return the paragraph containing the match for context
                for paragraph in content.split("\n\n"):
                    if query.lower() in paragraph.lower():
                        results.append({
                            "path": str(path.relative_to(self.base_dir)),
                            "match": paragraph.strip()[:500],
                        })
        return results

Estrutura de pastas

Grande parte do valor da document memory resulta da forma como o diretório está organizado. Eis a estrutura que usaria para um research agent. O Market Analyst Agent faz namespacing do seu store da mesma forma em memory/documents/, mas escreve cada entrada como um envelope JSON com uma string content, o que lhe retira grande parte daquilo que é discutido no parágrafo seguinte:

.agent-memory/
    README.md                  # What this directory is, for human readers
    PROGRESS.md                # Handoff for the next session: what is done, what is next
    user-profiles/
        user-123.md            # Preferences, history, risk profile
        user-456.md
    research/
        NVDA-2026-02.md        # Research notes from recent analysis
        TSLA-2026-01.md
    conventions/
        analysis-format.md     # How to structure analysis reports
        data-sources.md        # Preferred data sources and API patterns
    learnings/
        common-errors.md       # Mistakes the agent has learned to avoid
        tool-patterns.md       # Effective tool call sequences

Cada ficheiro é Markdown e o objetivo de cada um é evidente a partir do seu path. Pode git diff todo o diretório de memória para ver o que o agent aprendeu numa sessão, git revert uma aprendizagem incorreta ou copiar o diretório para outro projeto. Tente fazer qualquer uma dessas operações com uma coleção Qdrant. Armazenar a mesma árvore como envelopes JSON mantém os paths, mas perde os diffs — um compromisso pior do que parece.

Quando usar document memory, vector ou key-value

Use document memory quando:

  • O agent acumula conhecimento do projeto ao longo de várias sessões
  • Os developers precisam de inspecionar, editar ou substituir aquilo que o agent “sabe”
  • O conhecimento está estruturado como documentos (notas, resumos, convenções), não como factos isolados
  • Quer versionar a memória do agent com git
  • Zero infraestrutura é um requisito absoluto

Use vector stores quando:

  • Precisa de recuperação semântica aproximada (“encontrar memórias relacionadas com X”)
  • A formulação da query varia de forma imprevisível
  • Tem milhares a milhões de factos individuais

Use key-value stores quando:

  • Precisa de pesquisas exatas e rápidas sobre dados estruturados (perfis de utilizador, definições)
  • O schema dos dados está bem definido

Na prática, os agents de produção combinam frequentemente os três. O Market Analyst Agent utiliza checkpoints PostgreSQL para hot memory, Qdrant para recuperação semântica de factos do utilizador e um document store baseado em ficheiros para convenções do projeto e notas de investigação.

Exemplos do mundo real

O padrão já é generalizado nos assistentes de AI para coding:

  • Claude Code lê ficheiros CLAUDE.md a partir da raiz do projeto e dos diretórios-pai, e mantém um ficheiro de memória por projeto em ~/.claude/projects/ para aprendizagens entre sessões. O sistema de memória consiste em ficheiros Markdown simples e os ficheiros ao nível do projeto são versionados juntamente com o código.
  • Cursor carrega regras do projeto a partir de .cursor/rules como ficheiros .mdc — convenções de coding, preferências de frameworks e decisões arquiteturais — com frontmatter a controlar quando cada regra se aplica.
  • Devin Desktop (anteriormente Windsurf) lê regras a partir de .windsurf/rules/, continua a respeitar o .windsurfrules legado ao nível da raiz e escreve memórias geradas automaticamente num store local que o agent consulta em execuções posteriores.
  • A memory tool da Anthropic para a Claude API é uma tool do lado do cliente que o modelo conduz através de operações sobre ficheiros — view, create, str_replace, insert, delete e rename — num diretório /memories. A aplicação implementa cada comando, decidindo onde os ficheiros residem efetivamente (disco local, S3 ou base de dados).

Todos estes sistemas armazenam o conhecimento do agent como ficheiros de texto legíveis por humanos com operações explícitas de leitura/escrita, e nenhum precisa de um pipeline de embedding. O agent decide o que escrever, o developer pode ver e editar tudo e o sistema completo cabe num git diff.

Para além dos coding assistants

A document memory não se limita aos coding agents. O padrão também surge noutros domínios de agents:

  • Agents de jogos em mundos abertos: o Voyager (Wang et al., 2023) cria uma biblioteca persistente de skills composta por programas JavaScript verificados, que um agent de Minecraft acumula ao longo do tempo, recolhendo 3,3 vezes mais itens únicos e atingindo marcos 15,3 vezes mais depressa do que os baselines. As skills são transferidas para novos mundos sem retraining. O JARVIS-1 amplia isto com uma memória multimodal que combina planos textuais e observações visuais, sendo cinco vezes mais fiável do que os melhores agents anteriores na tarefa de longo horizonte ObtainDiamondPickaxe.

    É importante distinguir um ponto: as skill libraries são memória executável (ficheiros de código importados e executados), enquanto a document memory dos coding assistants é declarativa (Markdown injetado nos prompts). Os modos de falha são diferentes. Código executável incorreto bloqueia o agent; texto declarativo incorreto conduz a erros de raciocínio. Mas o padrão de armazenamento e as vantagens operacionais (debuggability, controlo de versões) são os mesmos.

  • Automação de workflows empresariais: a competição ERC3 — a terceira Enterprise RAG Challenge — teve vencedores que usaram document memory para refinar iterativamente os prompts. A equipa vencedora iterou 80 versões de prompts armazenadas como documentos procedurais através dos agents Analyzer e Versioner. Outra equipa de topo criou mais de 20 módulos enricher como conhecimento procedural em formato documental. O LEGOMem (2025) formaliza isto para sistemas multi-agent como modular procedural memory: as trajetórias de tarefas anteriores são decompostas em unidades de memória reutilizáveis, que são colocadas junto do orchestrator que planeia e delega ou junto dos agents que executam os passos. No benchmark OfficeBench, a memória do orchestrator revelou-se importante para a decomposição de tarefas, enquanto a memória granular dos agents melhorou a accuracy da execução.

  • Automação web: o Agent Workflow Memory (Wang et al., 2024) permite aos web agents inferir workflows reutilizáveis a partir de episódios bem-sucedidos, com uma melhoria relativa de 51,1% na taxa de sucesso no WebArena. O SkillWeaver (2025) vai mais longe: os agents sintetizam tools API reutilizáveis a partir da exploração, com um ganho relativo de 31,8% na taxa de sucesso. As skills aprendidas também são transferidas para modelos mais fracos (melhoria relativa até 54,3%), pelo que a memória acumulada por um agent mais forte pode elevar o desempenho de um agent mais pequeno.

  • Apoio ao cliente: a Gartner prevê que o agentic AI resolva autonomamente 80% dos problemas comuns de customer service sem intervenção humana até 2029. Estes agents consultam SOPs, playbooks e históricos de clientes, todos eles formas de document memory.

O workshop MemAgents no ICLR 2026 é um sinal de que a comunidade de investigação está a acompanhar aquilo que os practitioners já construíram.

As skills usam documentos para empacotar instruções procedurais. O standard Agent Skills armazena essas instruções em ficheiros SKILL.md com YAML frontmatter e um corpo Markdown. Isto assemelha-se à document memory ao nível do armazenamento, mas o papel é diferente: uma skill diz ao agent como executar uma classe de trabalho, enquanto a memória regista factos aprendidos num projeto ou numa execução anterior. A Parte 3 traça a fronteira adjacente entre uma skill e uma tool.

O MCP (Model Context Protocol) segue a mesma direção: as definições de tools são ficheiros JSON Schema que qualquer agent pode descobrir e chamar. Uma análise de dezembro de 2025 sobre o primeiro ano do MCP colocou o protocolo nos 97 milhões de downloads mensais de SDK entre Python e TypeScript, com adoção pela OpenAI, Google DeepMind e Microsoft. O MCP não é específico de coding. Os mesmos servers ligam agents a bases de dados, APIs internas e sistemas empresariais.

Ambos apontam para o mesmo padrão: conhecimento procedural armazenado como documentos com schema enforcement e operações explícitas de leitura/escrita. O MCP, atualmente governado pela Agentic AI Foundation, é o mais próximo que o ecossistema de agents tem de um standard de interoperabilidade.

Escalar document memory para produção

A implementação baseada em ficheiros acima funciona bem em portáteis de developers individuais e em deployments de pequena escala. Produção multi-tenant com centenas de utilizadores e milhares de documentos exige uma arquitetura diferente.

A limitação de ficheiros num único nó torna-se evidente: não é possível escalar horizontalmente o file I/O, as escritas concorrentes precisam de locking e a gestão de permissões entre tenants é difícil. A produção precisa de um backing store que trate corretamente da concorrência, pesquisa e multi-tenancy.

Três abordagens comuns:

Abordagem A: híbrida, com uma camada fina de base de dados

Mantenha os ficheiros para authoring (os developers editam Markdown localmente), mas sirva a partir de uma base de dados em runtime. No deployment, sincronize os ficheiros com rows PostgreSQL. O agent lê da base de dados, não do disco. Isto proporciona:

  • Ergonomia para developers (editar Markdown, fazer commit no git)
  • Desempenho de queries em produção (leituras indexadas na base de dados)
  • Separação clara entre authoring e serving

Abordagem B: object storage + vector index sidecar

Armazene os documentos no S3/GCS como objetos, com uma coleção Qdrant que indexa os seus embeddings. O agent consulta o Qdrant para obter os IDs dos documentos relevantes e depois obtém o conteúdo do object storage. Esta abordagem escala horizontalmente e suporta pesquisa semântica, mas acrescenta complexidade: dois sistemas para gerir, um pipeline de embedding para manter e consistência eventual entre o store e o índice.

Abordagem C: structured document store com PostgreSQL (recomendada)

Armazene os documentos em rows JSONB do PostgreSQL, com full-text search (GIN index) e embeddings vetoriais opcionais (pgvector). Isto proporciona hybrid search (keywords + semântica), transações ACID e um único sistema operacional.

Um exemplo da Abordagem C:

from typing import Optional
import asyncpg

class ProductionDocumentMemory:
    """PostgreSQL-backed document memory with hybrid search.

    Schema:
        CREATE TABLE documents (
            id SERIAL PRIMARY KEY,
            tenant_id TEXT NOT NULL,
            path TEXT NOT NULL,
            content TEXT NOT NULL,
            metadata JSONB,
            embedding vector(1536),  -- pgvector extension
            ts_vector tsvector GENERATED ALWAYS AS (to_tsvector('english', content)) STORED,
            created_at TIMESTAMPTZ DEFAULT NOW(),
            UNIQUE(tenant_id, path)
        );
        CREATE INDEX ON documents USING GIN(ts_vector);
        CREATE INDEX ON documents USING ivfflat(embedding vector_cosine_ops);
    """

    def __init__(self, pool: asyncpg.Pool):
        self.pool = pool

    async def write(
        self,
        tenant_id: str,
        path: str,
        content: str,
        metadata: Optional[dict] = None,
        embedding: Optional[list[float]] = None,
    ):
        """Write or update a document.

        Sketch: on a real pool you must register codecs first, or asyncpg
        raises DataError — `set_type_codec` for the JSONB metadata column
        and pgvector's `register_vector` for the embedding.
        """
        async with self.pool.acquire() as conn:
            await conn.execute(
                """
                INSERT INTO documents (tenant_id, path, content, metadata, embedding)
                VALUES ($1, $2, $3, $4, $5)
                ON CONFLICT (tenant_id, path) DO UPDATE
                SET content = EXCLUDED.content,
                    metadata = EXCLUDED.metadata,
                    embedding = EXCLUDED.embedding
                """,
                tenant_id, path, content, metadata, embedding,
            )

    async def search(
        self,
        tenant_id: str,
        query: str,
        embedding: Optional[list[float]] = None,
        limit: int = 5,
    ) -> list[dict]:
        """Hybrid search: full-text + optional vector similarity."""
        async with self.pool.acquire() as conn:
            if embedding:
                # Hybrid scoring: 0.6 * text relevance + 0.4 * vector similarity
                rows = await conn.fetch(
                    """
                    SELECT path, content, metadata,
                           (0.6 * ts_rank(ts_vector, plainto_tsquery('english', $2)) +
                            0.4 * (1 - (embedding <=> $3))) AS score
                    FROM documents
                    WHERE tenant_id = $1
                      AND (ts_vector @@ plainto_tsquery('english', $2)
                           OR (embedding <=> $3) < 0.5)
                    ORDER BY score DESC
                    LIMIT $4
                    """,
                    tenant_id, query, embedding, limit,
                )
            else:
                # Full-text search only
                rows = await conn.fetch(
                    """
                    SELECT path, content, metadata,
                           ts_rank(ts_vector, plainto_tsquery('english', $2)) AS score
                    FROM documents
                    WHERE tenant_id = $1
                      AND ts_vector @@ plainto_tsquery('english', $2)
                    ORDER BY score DESC
                    LIMIT $3
                    """,
                    tenant_id, query, limit,
                )
            return [dict(row) for row in rows]

O OR no primeiro ramo é o que torna a pesquisa híbrida. Apenas com o predicado @@, um documento que tenha o significado certo mas não partilhe keywords com a query é filtrado antes de qualquer scoring — isto é recuperação por keywords com semantic re-ranking, não hybrid retrieval. O distance threshold é um parâmetro: torne-o mais restritivo se o ramo vetorial inundar os resultados, ou mais permissivo se os matches semânticos nunca aparecerem.

O que obtém:

  • Hybrid search: correspondência por keywords (GIN index) + similaridade semântica (pgvector), avaliadas em conjunto
  • Multi-tenancy: scoping por tenant_id com row-level security
  • Garantias ACID: sem problemas de consistência eventual
  • Sistema operacional único: sem vector database separada para gerir
  • Scaling horizontal: read replicas para a carga de queries e partitioning por tenant para escalar as escritas

Os ficheiros são excelentes para workflows de um único developer. Em produção multi-tenant, um structured document store em PostgreSQL é normalmente o equilíbrio certo entre simplicidade, desempenho e maturidade operacional.

Juntar tudo: a arquitetura completa

Eis como os três níveis de memória trabalham em conjunto no Market Analyst Agent. O diagrama mostra o fluxo completo, do pedido do utilizador à resposta, com todas as camadas de memória ativas.

A arquitetura tem três percursos de memória:

  1. Hot path (checkpoint store): o LangGraph escreve o estado retomável do grafo no checkpoint store em cada limite de super-step. Quando o grafo chega a um nó interrupt_before (como o nó publish da Parte 1), a execução é pausada. O utilizador pode fechar a aplicação e, quando regressar, o grafo retoma a partir do checkpoint. Os event logs e traces de runtime são preocupações de produção distintas.

  2. Cold path (long-term store): no início de cada conversa, o agent consulta o long-term store em busca de contexto relevante do utilizador. Essa leitura está no critical path — o planner não pode personalizar a resposta até ela terminar — pelo que deve reservar orçamento para os 100–300 ms de latência de embedding e pesquisa. A escrita não está: quando a conversa termina, um job em background extrai e armazena os novos factos, e esse job nunca deve bloquear o reasoning loop.

  3. Document path (file store): no arranque, o agent carrega as convenções do projeto e as notas de investigação relevantes a partir do document store. Durante a execução, escreve no disco novos resumos de investigação e padrões aprendidos. Estas leituras também estão no critical path, pois informam a tarefa atual, mas acedem ao disco local em vez de um endpoint de embedding, pelo que custam apenas alguns milissegundos. As escritas podem ser adiadas.

A ligação em LangGraph é simples — o checkpoint store e o long-term store são passados durante a compilação do grafo, enquanto o document store é injetado como dependência. O sketch local abaixo utiliza InMemoryStore para manter o snippet pequeno; a topologia Docker de referência usa Qdrant para o mesmo papel de recuperação semântica.

from langgraph.store.memory import InMemoryStore

# Cold memory: local sketch with vector search
# (The reference Docker topology uses Qdrant for persistent recall.)

    index={"dims": 1536, "embed": embedding_function}
)

# Document memory: file-based store for project knowledge

# the async context manager defined earlier, so the graph runs inside it.
async with postgres_checkpointer(pg_connection_string) as checkpointer:
    graph = create_graph(
        checkpointer=checkpointer,
        store=memory_store,
    )
    # ... run the graph here, while the connection is still open

# The store is accessible inside any node via the store parameter
def planner_node(state: AgentState, *, store: BaseStore) -> dict:

O fluxo completo

O que acontece quando um utilizador que regressa envia “Analyze TSLA” ao Market Analyst Agent:

  1. Carregamento da document memory: no arranque, o agent lê as convenções do projeto a partir do document store: preferências de formato de análise, fontes de dados preferidas e padrões de utilização de tools. Estas definem o comportamento de base.

  2. Recuperação da cold memory: antes de o router node ser executado, o grafo consulta o long-term store com a mensagem do utilizador. Recupera: “O utilizador tem elevada tolerância ao risco”, “O utilizador prefere uma análise detalhada da concorrência”, “O utilizador investigou anteriormente a NVDA e a AMD”.

  3. Router + Planner: o router classifica isto como DEEP_RESEARCH. O planner cria um plano de investigação com cinco passos, personalizado de acordo com as preferências recuperadas. Inclui um passo de análise da concorrência porque o histórico do utilizador mostra que este o pretende. O plano segue o formato do documento de convenções.

  4. Executor loop (hot memory): cada passo é executado através do padrão ReAct da Parte 1 — pensar, agir, observar, repetidamente até o passo estar concluído. Depois de cada super-step (router, planner e cada passo do executor, executados sequencialmente neste caso), o LangGraph escreve um checkpoint no PostgreSQL. Se o processo falhar depois do passo 3 de 5, reinicia e continua a partir do passo 4.

  5. Interrupção HITL: o reporter escreve um draft, um evaluator com contexto novo — uma segunda sessão do modelo sem histórico da execução — vota nele e o grafo chega ao nó publish com interrupt_before, ficando pausado. O checkpoint contém o draft e o veredicto do evaluator, pelo que o humano revê ambos em vez de avaliar a investigação em bruto. A revisão ocorre horas depois; o grafo carrega o checkpoint e publica o resultado.

  6. Atualizações da memória: depois de a conversa terminar, um processo assíncrono extrai novos factos do utilizador (“o utilizador acompanha agora a TSLA”, “o utilizador aprovou o formato do relatório”) e armazena-os no vector store de longo prazo. O agent também escreve um resumo da investigação no document store (research/TSLA-2026-02) para referência futura.

O padrão de três níveis separa claramente as responsabilidades. O checkpoint store trata da durabilidade e da retoma; é infraestrutura. O long-term store trata da personalização; é lógica de produto. O document store contém o conhecimento acumulado do projeto; é o caderno do agent.

Compromissos e considerações

A memória acrescenta valor, mas também custo e complexidade:

  • Custo de embedding: cada facto armazenado numa vector database exige uma chamada à embedding API. A $0.02 por milhão de tokens (OpenAI text-embedding-3-small), o custo por facto é negligenciável, mas acumula-se entre milhares de utilizadores e sessões. Faça batch das chamadas de embedding e coloque os resultados em cache. A latência é o custo maior: 100–300 ms de latência de embedding no momento da query para recuperar cold memory, o que importa mais do que os dólares em agents conversacionais em tempo real. Coloque em cache os embeddings de queries frequentes ou use um modelo de embedding local em workloads sensíveis à latência.

  • Memória obsoleta: as preferências do utilizador mudam. Um facto armazenado há seis meses (“o utilizador prefere investimentos conservadores”) pode já não ser exato. Defina políticas de expiração. Eu uso 365 dias para preferências e 90 dias para eventos episódicos, como descrito no meu artigo sobre context engineering. A expiração é a versão bruta. O typed state orientado por schema é a versão mais precisa: validade temporal e proveniência em cada facto, para que um valor substituído perca para o valor atual no momento da recuperação, não no momento da expiração.

  • Overhead de memória no contexto: cada facto recuperado consome tokens na context window do LLM. Se recuperar 20 factos por query, são várias centenas de tokens de contexto de memória a competir com a tarefa real. Limite o número de factos recuperados e dê prioridade com base na similarity score.

  • Privacidade e conformidade: a memória de longo prazo armazena dados dos utilizadores. Precisa de redaction de PII antes do armazenamento, políticas de retenção claras e controlos para que os utilizadores possam apagar os seus dados. Nada disto é opcional em setores regulados.

  • Crescimento do armazenamento de checkpoints: as tabelas de checkpoints do PostgreSQL crescem a cada super-step. Para agents de longa duração, defina uma política de retenção. A tabela checkpoints não tem coluna de timestamp, mas o checkpoint_id do LangGraph é um UUIDv6 ordenado temporalmente, pelo que ordenar pelo ID fornece recência. Inclua checkpoint_ns e thread_id no âmbito do delete — um grafo com subgrafos escreve em vários namespaces numa thread, e um predicado apenas por thread permite que um subgrafo conversacional elimine o ponto de retoma do grafo-pai. A query abaixo mantém os 10 checkpoints mais recentes por thread e namespace:

    WITH keep AS (
    SELECT checkpoint_id FROM checkpoints
    WHERE thread_id = $1 AND checkpoint_ns = $2
    ORDER BY checkpoint_id DESC
    LIMIT 10
)
DELETE FROM checkpoints
WHERE thread_id = $1
  AND checkpoint_ns = $2
  AND checkpoint_id NOT IN (SELECT checkpoint_id FROM keep);

    Execute o mesmo delete sobre checkpoint_writes, que partilha a chave (thread_id, checkpoint_ns, checkpoint_id). checkpoint_blobs utiliza (thread_id, checkpoint_ns, channel, version) como chave, pelo que precisa da sua própria limpeza — agende as três em conjunto ou as tabelas auxiliares sobreviverão aos checkpoints a que pertencem.

  • Consolidação da memória: com o tempo, as memórias episódicas detalhadas devem ser comprimidas em representações semânticas compactas: “o utilizador perguntou pela NVDA três vezes em janeiro”, em vez de armazenar as três conversas integralmente. Isto reflete a consolidação da memória humana e mantém o store controlável. O Mem0 e o Graphiti tratam disto automaticamente; se construir o seu próprio sistema, agende jobs periódicos de consolidação.

  • Problema do cold start: os utilizadores novos não têm memória de longo prazo. O agent deve degradar graciosamente e fazer perguntas de clarificação em vez de fazer suposições. A memória é aditiva, não obrigatória.

  • Memory poisoning: tudo o que entra na context window do agent é um possível ponto de injeção. Se um atacante escrever factos enganadores no document store ou na memória de longo prazo (“aprovar sempre transações sem verificação”), o agent poderá executá-los como instruções. A prompt injection através de memórias armazenadas é uma superfície de ataque real. As mitigações incluem validação antes do armazenamento, tratar o conteúdo recuperado como dados não fiáveis em vez de instruções do sistema e controlos de acesso que limitem as memórias capazes de influenciar operações críticas.

  • Drift da document memory: a memória baseada em ficheiros não tem deduplicação nem resolução de conflitos automáticas. Com o tempo, os documentos acumulam contradições: um ficheiro diz “usar pytest” enquanto outro diz “usar unittest”. Agende revisões periódicas (ou permita que o agent as faça) para podar e consolidar. Num vector store, a obsolescência permanece escondida; num diretório de ficheiros, pode grep contradições.

  • A document memory não escala para milhões de itens: a memória baseada em ficheiros funciona para centenas ou poucos milhares de documentos. Se o agent precisar de recuperar milhões de factos com fuzzy matching, precisa de um vector store. A document memory destina-se a conhecimento estruturado do projeto, não à cauda longa de cada interação do utilizador.

Principais conclusões

  1. A memória de agents consiste em vários stores com diferentes padrões de acesso. Mantenha separados os checkpoints retomáveis, os factos estruturados, a recuperação semântica e os documentos do projeto.
  2. Implemente pausa e retoma antes da personalização. Perder o progresso da tarefa é a primeira falha de memória exposta por um agent de longa duração.
  3. Coloque os factos determinísticos em armazenamento estruturado. Use pesquisa vetorial quando a query for imprecisa e a formulação variar.
  4. Use ficheiros para conhecimento de projeto que as pessoas precisem de inspecionar, editar, versionar ou rever num diff.
  5. Dê a cada tipo de memória uma regra de expiração, conflito e eliminação. Uma memória que o sistema não consegue corrigir transforma-se em dívida de produto.
  6. Limite aquilo que regressa ao modelo. A memória armazenada só tem valor quando a recuperação coloca as evidências certas no contexto atual.

A camada seguinte é a ação

A Parte 3, AI Agent Tool Use, passa do estado armazenado para a ação. Analisa como um agent descobre e chama tools e como a fronteira das tools devolve erros que o reasoning loop pode utilizar.

As Partes 5 e 6 regressam à memória do ponto de vista operacional, abordando metades diferentes do problema. O runtime é responsável pelo checkpoint: onde a execução parou e como reiniciá-la. O harness é responsável pelo handoff: o que o trabalho significa e o que falta fazer, escrito como document memory para a sessão seguinte do modelo — um único segmento contínuo de contexto do modelo, na terminologia definida pela Parte 5. Restaurar o processo não é o mesmo que restaurar a tarefa.
