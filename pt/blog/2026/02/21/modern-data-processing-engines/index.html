Motores de processamento de dados: Polars, DataFusion, Ray e Spark

Viacheslav Dubrov

2026-02-21 · Atualizado 2026-07-15 · 18 min · Infraestrutura de IA

Tradução automática Este artigo foi traduzido automaticamente a partir da versão original em inglês.

Durante anos, o Pandas tratou os dados tabulares em memória e o Apache Spark tratou a vertente distribuída. Esta separação funcionava bem quando os dados eram estruturados.

Os pipelines modernos também processam imagens, áudio e vídeo. Nestes workloads, a descodificação no CPU pode deixar a inferência no GPU sem dados, enquanto a recolha de lixo da JVM e o Global Interpreter Lock do Python limitam o throughput. Os novos motores usam Rust e Apache Arrow para reduzir esses custos.

Para comparar as opções, fiz um benchmark do Pandas, Polars, DataFusion, Daft e Rust nativo em dois datasets reais. O Spark e o Ray são abordados em notebooks distribuídos separados. As viagens de táxi de Nova Iorque representam o processamento tabular; as imagens Food-101 representam um pipeline multimodal.

O repositório engine-comparison-demo contém o código. Execute-o no seu próprio hardware, porque o desempenho do motor depende da máquina, do dataset e do workload.

Em resumo: comece pelo formato do workload, não pelo vencedor de um benchmark. O Polars é uma opção predefinida sólida para pipelines locais com DataFrames; o DataFusion é adequado para equipas que incorporam um motor de queries; o Ray Data e o Daft foram concebidos para pipelines mistos de CPU/GPU; e o Spark continua a ser uma opção madura para SQL distribuído e ETL. Os ganhos de velocidade descritos neste guia referem-se a workloads específicos; não se aplicam automaticamente ao seu caso. Volte a executar os benchmarks complementares com os seus dados e hardware antes de escolher.

Tipos de workloads de processamento de dados

Os motores especializam-se, por isso a primeira pergunta a responder é que tipo de workload tem realmente. A principal distinção é entre dados estruturados e multimodais.

Os dados estruturados ou tabulares envolvem filtragem, agregação e joins. Normalmente, são limitados pelo CPU e cabem frequentemente na memória. Muitas destas queries podem ser executadas numa única máquina moderna, mas a memória, o I/O, a concorrência, a recuperação e o formato do workload continuam a determinar se é apropriado usar um cluster.

A IA multimodal processa imagens, áudio ou vídeo. A inferência pode ser executada no GPU, enquanto a descodificação no CPU, as leituras remotas ou o batching limitam o pipeline. O estágio que limita o throughput varia consoante o tipo de instância e os operadores; por isso, meça a utilização ao longo de todo o percurso, em vez de dimensionar o GPU isoladamente.

Os motores mais recentes visam diferentes partes deste espaço. A execução nativa pode reduzir o overhead do Python, as interfaces compatíveis com Arrow podem tornar a troca de dados mais barata e a execução em streaming pode limitar o uso de memória em datasets maiores do que a RAM. Nenhuma destas vantagens é automática para todos os operadores ou conversões.

Parte 1: processamento num único nó

Byte says

Certa vez coloquei a manchete de um benchmark publicado do Polars em um documento de design como o ganho de velocidade esperado. Ninguém perguntou qual consulta o tinha produzido, nem eu.

O Pandas privilegia um modelo de programação eager e em memória. Muitas operações comuns criam resultados intermédios, e a execução paralela não é coordenada através de um otimizador de queries. Esta escolha mantém o código exploratório direto, mas pode tornar-se dispendiosa em scans analíticos maiores. No benchmark PDS-H do Polars, com um factor de escala 10, o Pandas demorou cerca de 365 segundos a executar a suite, enquanto o motor de streaming do Polars demorou 3,89 segundos. O resultado de aproximadamente 94x descreve esse benchmark e essa configuração; não é um factor geral de conversão de Pandas para Polars.

Polars para pipelines tabulares locais

Polars é uma opção predefinida prática quando um pipeline local de DataFrame já ultrapassou a execução eager num único processo. A sua API lazy constrói um plano de consulta antes da execução, permitindo otimizações como o predicate pushdown e a eliminação de projeções. O motor pode então executar operadores em paralelo e, quando suportado, em batches de streaming.

A diferença aumenta à medida que os dados crescem. No fator de escala 100 (~100 GB), o motor de streaming do Polars terminou em 23,94 segundos, contra 152,27 segundos do seu próprio motor em memória — cerca de 6x mais rápido, com dados maiores do que a RAM.

O exemplo seguinte é uma ilustração da API, não um excerto literal da versão atual de engine_comparison_examples.ipynb ou tabular.py:

import polars as pl

# scan_parquet reads only the schema — no data loaded yet
q = (
    pl.scan_parquet("yellow_tripdata_2024-01.parquet")
    .filter(
        (pl.col("trip_distance") > 5.0)
        & (pl.col("total_amount") > 30.0)
    )
    .group_by("payment_type")
    .agg(
        pl.col("total_amount").mean().alias("avg_fare"),
        pl.col("trip_distance").mean().alias("avg_distance"),
        pl.len().alias("trip_count"),
    )
)

# The entire plan is optimized and executed here, in parallel
result = q.collect()

A diferença importante está no modelo de execução. Na consulta lazy acima, o Polars pode aplicar o filtro e a seleção de colunas diretamente à leitura do Parquet. Isso pode permitir ignorar row groups e evitar a leitura de colunas não utilizadas. Um pipeline Pandas eager típico não dispõe de um plano para otimizar a consulta completa, embora a utilização criteriosa de filtros Parquet, colunas selecionadas e backends alternativos possa recuperar parte da diferença.

DataFusion para motores de consulta embebidos

Enquanto o Polars é uma biblioteca que utiliza diretamente, o DataFusion é o motor sobre o qual se constroem outros motores. É utilizado pelo InfluxDB 3.0, pelo GreptimeDB e pelo Comet Spark accelerator da Apple.

Numa execução do ClickBench publicada pelo projeto DataFusion em novembro de 2024, o DataFusion liderou as configurações Parquet testadas num único nó. Mais tarde, a equipa do Embucket publicou um estudo de caso do fornecedor para o fator de escala 1000 do TPC-H, utilizando datafusion-cli em r6gd.metal, com 64 vCPUs, 512 GB de RAM, NVMe local e medições com a cache quente. As consultas Q18 e Q21 falharam ou demoraram excessivamente na execução original, tendo sido depois reescritas estruturalmente para obter os resultados completos. Isto demonstra scale-up num único nó nessa configuração, não um resultado geral do TPC-H.

O exemplo seguinte é uma ilustração da API, não um excerto literal da versão atual de engine_comparison_examples.ipynb ou tabular.py:

from datafusion import SessionContext

ctx = SessionContext()
ctx.register_parquet("taxi", "yellow_tripdata_2024-01.parquet")

# SQL executed directly against Parquet — no intermediate copies
df = ctx.sql("""
    SELECT payment_type,
           COUNT(*)           AS trip_count,
           AVG(trip_distance) AS avg_distance,
           AVG(total_amount)  AS avg_fare
    FROM taxi
    WHERE trip_distance > 5.0 AND total_amount > 30.0
    GROUP BY payment_type
    ORDER BY trip_count DESC
""")
result = df.to_pandas()

A principal vantagem do DataFusion é a sua modularidade. As APIs de extensão abrangem catálogos personalizados, table providers, regras do otimizador e planos de execução. É por isso que surge sempre que alguém está a criar uma plataforma de dados personalizada ou a incorporar um motor de consulta no seu próprio produto.

Daft para dados multimodais

O Daft integra imagens, áudio, vídeo e embeddings no workflow de DataFrame. Disponibiliza expressões nativas para operações como descodificação de imagens e downloads a partir de URLs, evitando que os pipelines de pré-processamento comuns necessitem de um ciclo Python linha a linha. Essa integração é o principal motivo para o considerar em vez de um motor tabular generalista.

O exemplo seguinte é uma ilustração da API, não um excerto literal da versão atual de engine_comparison_examples.ipynb ou multimodal.py:

import daft

df = daft.read_parquet("yellow_tripdata_2024-01.parquet")

result = (
    df.where(
        (daft.col("trip_distance") > 5.0)
        & (daft.col("total_amount") > 30.0)
    )
    .groupby("payment_type")
    .agg(
        daft.col("total_amount").mean().alias("avg_fare"),
        daft.col("trip_distance").mean().alias("avg_distance"),
        daft.col("trip_distance").count().alias("trip_count"),
    )
    .collect()
)

Se conhece o Pandas, a API ser-lhe-á familiar, mas o motor utiliza a mesma stack Rust + Arrow que encontra no Polars e no DataFusion. A vantagem do Daft manifesta-se quando as “linhas” do seu DataFrame são imagens, PDFs ou tensores.

Quando os motores apresentam resultados tão próximos, a decisão deve basear-se na adequação da API e em medições repetidas sobre dados representativos.

Parte 2: dados multimodais

Os pipelines ETL tabulares costumam reduzir os dados: filtram, agregam e escrevem menos do que leem. Os pipelines de IA multimodal fazem o oposto. Um único caminho para um documento pode dar origem a dezenas de fragmentos de texto e vetores de embeddings.

Num pipeline PySpark convencional, as imagens e o áudio entram frequentemente como dados binários e passam para bibliotecas Python para descodificação ou transformação. A passagem entre a JVM e o Python, bem como a serialização dos resultados, pode representar uma parte significativa do tempo total. O Spark suporta caminhos baseados em Arrow, UDFs vetorizadas e integrações com aceleradores, mas essas opções exigem desenho e medição explícitos.

Execução em pipeline e utilização da GPU

O Spark agenda o trabalho em etapas separadas por limites de shuffle. Uma implementação direta pode colocar a transferência, a descodificação e a inferência numa sequência que deixa a capacidade do CPU ou da GPU à espera. O Spark suporta agendamento de recursos de GPU e plugins, pelo que o tempo ocioso não é inevitável. No entanto, a sobreposição e o controlo de backpressure não são propriedades automáticas de um job comum de DataFrame em PySpark.

A execução em pipeline é a alternativa. Em vez de executar as etapas consecutivamente, o motor sobrepõe operações de I/O, trabalho no CPU e inferência na GPU. Quando as etapas e os buffers estão equilibrados, essa sobreposição pode reduzir o tempo ocioso e aumentar o throughput; o arranque e o escoamento, o backpressure ou uma etapa mais lenta podem ainda deixar recursos à espera.

Parte 3: processamento distribuído

Quando uma única máquina deixa de ser suficiente, é preciso decidir como distribuir o trabalho.

Apache Spark

O Spark é uma opção madura para ETL tabular de grande escala, joins com muito shuffle e organizações que já operam o respetivo ecossistema. A recuperação baseada em lineage e o amplo suporte de plataformas são importantes quando a fiabilidade e a familiaridade operacional pesam mais do que a velocidade local. Os pipelines mistos de CPU/GPU exigem uma configuração de recursos e um desenho do pipeline mais cuidadosos do que o percurso SQL, área em que o Ray Data e o Daft oferecem uma abstração mais focada.

O exemplo seguinte é um esboço ilustrativo da API do Spark, não uma transcrição literal da versão atual de distributed_spark.ipynb ou spark_etl.py:

from pyspark.sql import SparkSession
from pyspark.sql import functions as F

spark = SparkSession.builder \
    .appName("TaxiETL") \
    .config("spark.sql.adaptive.enabled", "true") \
    .getOrCreate()

orders = spark.read.parquet("s3a://lake/taxi/*.parquet")
zones = spark.read.csv("s3a://lake/taxi_zones.csv", header=True)

# Spark excels at this: joining massive tables with a shuffle
result = (
    orders
    .filter(F.col("trip_distance") > 5.0)
    .join(zones, orders.PULocationID == zones.LocationID, "inner")
    .groupBy("Borough")
    .agg(
        F.sum("total_amount").alias("total_revenue"),
        F.avg("total_amount").alias("avg_fare"),
    )
    .orderBy(F.desc("total_revenue"))
)

Ray Data para computação heterogénea

O Ray Data foi concebido para workloads de IA. Em vez das barreiras entre fases do Spark, utiliza um modelo de streaming que mantém as GPUs alimentadas. A funcionalidade mais importante para pipelines de IA é o agendamento de recursos mistos: pode declarar que um actor pretende “1 GPU, 4 CPUs” e que outro pretende apenas CPUs, deixando o Ray tratar do resto.

A Amazon reportou mais de $120 milhões de poupanças anuais depois de migrar workloads internos selecionados de processamento de dados do Spark para o Ray. O relatório indica uma melhoria de 91% na eficiência de custos durante a prova de conceito e de 82% em produção, por GiB de entrada do S3. A escala é relevante, mas este é um estudo de caso de migração para workloads específicos, e não uma poupança esperada numa adoção típica do Ray.

O exemplo seguinte é um esboço ilustrativo da API do Ray Data, não uma transcrição literal da versão atual de distributed_ray.ipynb ou ray_inference.py:

import ray

ray.init()

ds = ray.data.read_images("s3://my-bucket/food101/")

class ImageClassifier:
    def __init__(self):
        import torch
        from torchvision.models import resnet18, ResNet18_Weights
        self.model = resnet18(weights=ResNet18_Weights.DEFAULT).cuda()
        self.model.eval()
        self.preprocess = ResNet18_Weights.DEFAULT.transforms()

    def __call__(self, batch):
        import torch
        tensors = torch.stack([
            self.preprocess(img) for img in batch["image"]
        ]).cuda()
        with torch.no_grad():
            preds = self.model(tensors)
        return {
            "prediction": preds.argmax(dim=1).cpu().numpy(),
            "confidence": preds.max(dim=1).values.cpu().numpy(),
        }

# ActorPoolStrategy creates persistent GPU workers
predictions = ds.map_batches(
    ImageClassifier,
    compute=ray.data.ActorPoolStrategy(size=4),
    num_gpus=1,
    batch_size=64,
)
predictions.write_parquet("s3://output/predictions/")

A proporção entre CPU e GPU merece atenção. Nos benchmarks da Anyscale, o Ray Data continuou a escalar à medida que aumentava o número de CPUs por GPU, enquanto os outros engines testados atingiram um plateau. A fonte reporta até 3x de speedup na inferência de imagens à medida que diminui a subalimentação da CPU, porque os processos que alimentam as GPUs conseguem acompanhar o ritmo.

Daft distribuído

O Daft escala horizontalmente através do seu motor Flotilla: um worker Swordfish por nó, com o Flotilla a tratar do agendamento em todo o cluster. O Swordfish executa localmente em Rust e cria pipelines de I/O com o processamento através de streaming em pequenos lotes, mantendo cada nó ocupado sem esperar pela fase seguinte.

Nos benchmarks publicados pelo Daft, o Flotilla foi 4–18 vezes mais rápido do que as implementações de Spark testadas em quatro workloads multimodais. A maior diferença ocorreu num caso de deteção de objetos em vídeo. Considere este resultado como evidência de que o desenho da execução é importante nestes pipelines; em seguida, compare-o com os resultados concorrentes da Anyscale abaixo e com um teste local.

A Anyscale, a empresa responsável pelo Ray, publicou um benchmark concorrente no qual o Ray Data eliminou ou inverteu a diferença em instâncias com muitos recursos de CPU, após afinação. Em conjunto, os dois estudos dos fornecedores são um motivo para testar operadores representativos e rácios CPU/GPU, e não para inferir uma classificação estável.

Segue-se um exemplo ilustrativo da API do Daft, não uma transcrição literal da versão atual de distributed_daft.ipynb nem de daft_pipeline.py:

import daft
import numpy as np
from daft import col

# Daft's Flotilla engine distributes work across the cluster
df = daft.read_parquet("s3://data-lake/pdf_metadata/*.parquet")

# Download PDFs — Daft parallelizes downloads in Rust
df = df.with_column("pdf_bytes", col("pdf_url").download())

# Define a GPU class UDF for batched embedding generation
@daft.cls
class TextEmbedder:
    def __init__(self):
        from sentence_transformers import SentenceTransformer
        self.model = SentenceTransformer("all-MiniLM-L6-v2", device="cuda")

    @daft.method.batch(
        return_dtype=daft.DataType.fixed_size_list(daft.DataType.float32(), 384)
    )
    def __call__(self, text_col):
        texts = text_col.to_pylist()
        embeddings = self.model.encode(texts, batch_size=32)
        return np.asarray(embeddings, dtype=np.float32)

# Daft schedules CPU downloads and GPU embeddings simultaneously
embedder = TextEmbedder()
df = df.with_column("embedding", embedder(col("text")))
df.write_parquet("s3://output/embeddings/")

Parte 4: o papel do Rust e do Arrow

Byte says

Mudei uma etapa entre dois engines supondo que o Arrow tornava a transferência gratuita. Os buffers foram copiados mesmo assim. Zero-copy é uma propriedade de caminhos específicos, e o meu não era um deles.

Por baixo desta competição, a história mais interessante é a convergência. O Polars, o Daft e o DataFusion utilizam extensivamente Rust, enquanto o Ray inclui componentes nativos a par das suas APIs Python. Todos podem trocar dados através de partes do ecossistema do Apache Arrow.

A Arrow PyCapsule Interface (protocolo __arrow_c_stream__) disponibiliza às bibliotecas compatíveis uma forma normalizada de trocar streams Arrow. As transferências podem evitar a serialização linha a linha e reutilizar buffers quando os schemas e os layouts de memória são compatíveis. A materialização, o rechunking, a conversão de tipos ou a transferência entre dispositivos podem ainda copiar dados; por isso, valide a passagem com profiling, em vez de assumir que é gratuita.

O seguinte é um esboço ilustrativo de uma API, não um script autónomo: pressupõe que events.parquet já existe. O engine_comparison_examples.ipynb associado cria .data/events.parquet nas células de configuração antes do exemplo com Arrow.

from datafusion import SessionContext
import polars as pl

# Compute in DataFusion (Rust-native execution)
ctx = SessionContext()
ctx.register_parquet("events", "events.parquet")
df = ctx.sql("""
    SELECT user_id, COUNT(*) as event_count
    FROM events WHERE event_type = 'purchase'
    GROUP BY user_id HAVING COUNT(*) > 5
""")

# Convert through Arrow; compatible buffers may be reused
arrow_table = df.to_arrow_table()
df_polars = pl.from_arrow(arrow_table)

# Continue analysis in Polars
result = df_polars.with_columns(
    pl.col("event_count").rank().alias("rank")
).sort("rank")

Porque é que estes motores mais recentes usam Rust para execução nativa?

  1. Ausência de um garbage collector de tracing no código Rust. A propriedade dá aos operadores nativos um controlo mais direto sobre a alocação e a desalocação. Isso pode reduzir a latência associada ao GC, mas não evita a pressão de memória nem as falhas por falta de memória.

  2. Representações nativas compactas. As estruturas Rust não incluem cabeçalhos de objetos Java. O benefício prático depende do layout do motor: os sistemas JVM colunares também evitam representar cada valor como um objeto individual.

  3. Verificações de concorrência mais fortes. As regras de Rust seguro eliminam muitas data races em tempo de compilação. O código do motor pode ainda conter blocos unsafe e bugs lógicos de concorrência, mas a linguagem reduz a superfície de falhas.

Com o layout de memória colunar do Arrow, estas escolhas podem reduzir os custos de alocação e serialização. No entanto, não os eliminam em todas as fronteiras; os objetos Python, o transporte pela rede, os schemas incompatíveis e a transferência entre dispositivos continuam a ser relevantes.

Parte 5: adoção de vários motores

Não é necessário obrigar toda a plataforma a usar um único motor. A composição é útil quando a transferência entre motores custa menos do que fazer com que um único sistema trate de todas as cargas de trabalho.

Uma possível cadeia usa o Spark para joins estabelecidos no lakehouse, grava uma tabela ou um formato de ficheiro aberto e entrega o resultado ao Ray Data ou ao Daft para inferência em GPU ou transformações multimodais. O Polars ou o DuckDB podem servir para análise local sobre os mesmos ficheiros. Uma equipa mais pequena pode precisar apenas de um destes motores; adicione outro quando um bottleneck medido justificar essa fronteira operacional.

O que torna esta composição possível é a interoperabilidade. O Parquet é o formato comum de transferência de ficheiros nestes exemplos, enquanto o Arrow pode fornecer intercâmbio em memória. O suporte para Delta e Iceberg depende do motor e do conector, pelo que deve validar cada fronteira. A transferência através de ficheiros também tem custos de I/O e conversão; não é automaticamente gratuita.

Escalonamento diagonal

Durante muito tempo, a escolha era fazer scale-up (uma máquina maior) ou scale-out (mais máquinas). A Polars Cloud faz algo intermédio, a que chama escalonamento diagonal. Faça o escalonamento horizontal durante a leitura a partir do armazenamento cloud para maximizar o I/O e, depois de os filtros e as agregações reduzirem os dados, consolide o processamento num único nó de grandes dimensões. O shuffle distribuído nunca chega a acontecer.

A lição mais abrangente é comparar o custo por job concluído com sucesso, e não o preço horário da instância. Um nó maior pode ficar mais barato quando a redução do tempo de execução compensa a tarifa mais elevada, mas o resultado depende do I/O, da pressão sobre a memória e da quantidade de trabalho eliminada antes de um shuffle.

Reproduzir a comparação

O repositório de demonstração complementar contém os scripts, notebooks e o ambiente utilizados nas comparações. O comando rápido abaixo usa o dataset de táxis de 2024 completo, predefinido no repositório, correspondendo à execução maior apresentada anteriormente.

# Install dependencies
uv sync

# Run the tabular benchmark (~41M NYC taxi trips from full-year 2024)
uv run python -m engine_comparison.benchmarks.tabular

# Run the multimodal benchmark (500 real food photos)
uv run python -m engine_comparison.benchmarks.multimodal

# Run native Rust benchmarks (Polars-rs + image crate)
cd rust_benchmark && cargo run --release && cd ..

O repositório também inclui notebooks para comparações lado a lado das APIs e configurações de Docker Compose para execuções distribuídas locais de Spark, Ray e Daft.

Principais conclusões

  1. Demonstre que uma única máquina é insuficiente. Os resultados de scale-up mostram que algumas análises de grandes volumes cabem num único nó. Meça os requisitos de memória, I/O, spill e recuperação antes de aceitar o overhead de um cluster.

  2. Os modelos de execução são mais importantes do que uma sintaxe familiar. Planeamento lazy, pushdown, processamento em streaming e operadores paralelos explicam grande parte da diferença entre um script DataFrame eager e um motor analítico.

  3. Meça todo o pipeline de aceleração. Decoding, I/O de rede, batching, serialização e backpressure determinam se uma GPU se mantém ocupada. Ray Data e Daft fazem desta sobreposição uma abstração central; Spark pode suportá-la com design e tooling adicionais.

  4. Faça uma shortlist com base no workload e, depois, use benchmarks. Use a adequação ao ecossistema para reduzir as opções e um job representativo, de ponta a ponta, para escolher. Os resultados de benchmarks dos vendors são hipóteses, não garantias.

  5. Os formatos abertos mantêm a escolha reversível. Interfaces compatíveis com Arrow, Parquet e formatos de tabelas abertos podem reduzir os custos de passagem de dados. Confirme se uma determinada conversão reutiliza os buffers ou se os copia.

Se precisar de um ponto de partida, experimente Polars para um pipeline tabular local e Daft ou Ray Data para um pipeline misto de CPU/GPU. Escolha Spark quando a sua execução distribuída, o ecossistema ou a base operacional existente resolverem um requisito. O tamanho do dataset, por si só, é uma justificação fraca.
