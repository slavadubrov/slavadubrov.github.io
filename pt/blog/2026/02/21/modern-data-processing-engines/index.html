Motores de processamento de dados: Polars, DataFusion, Ray e Spark

Viacheslav Dubrov

Este guia ajuda engenheiros de Python e de dados a escolher um motor de processamento para dados tabulares e pipelines de imagens, áudio ou texto. Explica como Polars, DataFusion, Daft, Ray Data e Spark executam trabalho, que workloads lhes são adequados e como compará-los com os seus próprios dados.

Os pipelines modernos também processam imagens, áudio e vídeo. Nestes workloads, a descodificação no CPU pode deixar a inferência no GPU sem dados. Operadores nativos, troca de dados em formato colunar e sobreposição de trabalho no CPU/GPU endereçam custos diferentes; escolher um motor significa identificar qual deles limita o seu pipeline.

Em resumo: comece pela forma do trabalho, não por um vencedor de benchmark. Tipos de workloads de processamento de dados

Os motores são especializados, por isso a primeira pergunta é que tipo de workload tem realmente. A divisão principal é entre dados estruturados e multimodais.

Dados estruturados ou tabulares envolvem filtragem, agregação e joins. Normalmente são limitados pelo CPU e cabem frequentemente na memória. Muitas destas queries podem ser executadas numa única máquina moderna, mas a memória, o I/O, a concorrência, a recuperação e o formato do workload continuam a determinar se um cluster é adequado.

A AI multimodal processa imagens, áudio ou vídeo. A inferência pode correr num GPU enquanto a descodificação no CPU, as leituras remotas ou o batching limitam o pipeline. A fase que limita o throughput muda consoante o tipo de instância e os operadores; por isso, meça a utilização ao longo de todo o percurso em vez de dimensionar o GPU isoladamente.

Os motores mais recentes visam partes diferentes deste espaço. A execução nativa pode reduzir o overhead do Python, as interfaces compatíveis com Arrow podem tornar a troca de dados mais barata e a execução em streaming pode limitar a memória em datasets maiores do que a RAM. Nenhum destes benefícios é automático para todos os operadores ou conversões.

Parte 1: processamento num único nó

Byte diz

Um ganho de velocidade publicado vem acompanhado de uma query e de uma máquina. O título é bastante mais fácil de copiar para um documento de arquitetura.

Pandas privilegia um modelo de programação eager: executa cada operação imediatamente, mantendo normalmente os dados na memória. Um modelo lazy, pelo contrário, planeia várias operações em conjunto antes de as executar. No Pandas, muitas operações comuns criam tabelas intermédias, e a execução paralela não é coordenada por um otimizador de queries. Este compromisso mantém o código exploratório direto, mas pode tornar-se dispendioso em scans analíticos maiores. No benchmark PDS-H de maio de 2025 do Polars, com scale factor 10, o Pandas demorou cerca de 365 segundos para a suite, enquanto o motor de streaming do Polars demorou 3,89 segundos. O resultado de aproximadamente 94x descreve esse benchmark e essa configuração; não é um fator geral de conversão de Pandas para Polars.

Polars para pipelines tabulares locais

Polars é uma opção predefinida prática quando um pipeline local com DataFrame ultrapassou a execução eager num único processo. A sua API lazy cria um plano de queries antes da execução. Isto permite filtrar as linhas o mais cedo possível (predicate pushdown) e ler apenas as colunas necessárias (projection pruning). O motor pode então executar operadores em paralelo e, quando suportado, em batches de streaming.

Com scale factor 100 (~100 GB de CSV), o motor de streaming do Polars 1.30.0 terminou em 23,94 segundos, contra 152,27 segundos para o motor em memória: cerca de 6,4x mais rápido. Ambos foram executados numa c7a.24xlarge com 192 GB de RAM. A fonte atribui esta diferença principalmente a menos cache misses no CPU e a uma melhor utilização dos cores; isto não constitui evidência de uma entrada maior do que a RAM.

A query abaixo lê viagens de táxi a partir de Parquet, seleciona viagens superiores a cinco milhas com um montante total acima de $30 e calcula contagens e médias por tipo de pagamento. Para a configuração do táxi, consulte engine_comparison_examples.ipynb ou tabular.py:

import polars as pl

# Build a lazy scan; query execution happens at collect()
q = (
    pl.scan_parquet("yellow_tripdata_2024-01.parquet")
    .filter(
        (pl.col("trip_distance") > 5.0)
        & (pl.col("total_amount") > 30.0)
    )
    .group_by("payment_type")
    .agg(
        pl.col("total_amount").mean().alias("avg_fare"),
        pl.col("trip_distance").mean().alias("avg_distance"),
        pl.len().alias("trip_count"),
    )
)

# The entire plan is optimized and executed here, in parallel
result = q.collect(engine="streaming")

A diferença importante está no modelo de execução. Na query lazy acima, o Polars pode aplicar o filtro e a seleção de colunas no scan de Parquet. Isto pode permitir ignorar row groups e evitar a leitura de colunas não utilizadas. O streaming é explícito neste caso; collect materializa na mesma o resultado final, e operações não suportadas podem recuar para a execução em memória. Um pipeline eager típico de Pandas não tem um plano de query global para otimizar, embora a utilização cuidadosa de filtros Parquet, colunas selecionadas e backends alternativos possa recuperar parte da diferença.

DataFusion para motores de queries incorporados

Enquanto Polars é uma biblioteca que se utiliza diretamente, DataFusion é o motor sobre o qual se constroem outros motores. É utilizado pelo InfluxDB 3.0, pelo GreptimeDB e pelo Comet Spark accelerator da Apple.

Num ClickBench de novembro de 2024 publicado pelo projeto DataFusion, o DataFusion liderou as configurações Parquet testadas num único nó. Mais tarde, a equipa do Embucket publicou um estudo de caso do fornecedor para TPC-H scale factor 1000, utilizando datafusion-cli em r6gd.metal, com 64 vCPUs, 512 GB de RAM, NVMe local e tempos com cache quente. Q18 e Q21 falharam ou demoraram excessivamente na execução original, tendo sido posteriormente reescritas estruturalmente para obter os resultados concluídos. Isto demonstra scale-up num único nó nessa configuração, não um resultado geral de TPC-H.

Eis o mesmo resumo dos táxis em SQL do DataFusion, com os tipos de pagamento ordenados pela contagem de viagens. A variante SQL está em engine_comparison_examples.ipynb ou tabular.py:

from datafusion import SessionContext

ctx = SessionContext()
ctx.register_parquet("taxi", "yellow_tripdata_2024-01.parquet")

# Plan SQL against the registered Parquet source
df = ctx.sql("""
    SELECT payment_type,
           COUNT(*)           AS trip_count,
           AVG(trip_distance) AS avg_distance,
           AVG(total_amount)  AS avg_fare
    FROM taxi
    WHERE trip_distance > 5.0 AND total_amount > 30.0
    GROUP BY payment_type
    ORDER BY trip_count DESC
""")
result = df.to_pandas()

A principal força do DataFusion é a sua modularidade. As APIs de extensão abrangem catálogos personalizados, table providers, regras de otimização e planos de execução. É por isso que surge sempre que alguém está a construir uma plataforma de dados personalizada ou a incorporar um motor de queries no seu próprio produto.

Daft para dados multimodais

Daft integra imagens, áudio, vídeo e embeddings no workflow de DataFrame. Disponibiliza expressões nativas para operações como descodificação de imagens e downloads de URLs, pelo que os percursos comuns de pré-processamento não requerem um loop Python linha a linha. Essa integração é a principal razão para o considerar em vez de um motor tabular generalista.

Antes de passar às imagens, este exemplo mostra o mesmo resumo dos táxis através da API tabular familiar do Daft. A comparação das APIs está em engine_comparison_examples.ipynb ou multimodal.py:

import daft

df = daft.read_parquet("yellow_tripdata_2024-01.parquet")

result = (
    df.where(
        (daft.col("trip_distance") > 5.0)
        & (daft.col("total_amount") > 30.0)
    )
    .groupby("payment_type")
    .agg(
        daft.col("total_amount").mean().alias("avg_fare"),
        daft.col("trip_distance").mean().alias("avg_distance"),
        daft.col("trip_distance").count().alias("trip_count"),
    )
    .collect()
)

A API parecerá familiar se conhecer Pandas, mas o motor é a mesma stack Rust + Arrow presente no Polars e no DataFusion. O Daft revela o seu valor quando as “linhas” do DataFrame são imagens, PDFs ou tensores.

Parte 2: dados multimodais

O ETL tabular normalmente reduz os dados: filtra, agrega e escreve menos do que lê. Os pipelines de AI multimodal fazem o oposto. Um único percurso documental pode expandir-se para dezenas de segmentos de texto e vetores de embedding.

Num pipeline PySpark convencional, as imagens e o áudio entram frequentemente como dados binários e passam para bibliotecas Python para descodificação ou transformação. A travessia do limite JVM/Python e a serialização dos resultados podem representar uma parte significativa do tempo de relógio. Spark pode utilizar percursos baseados em Arrow, UDFs vetorizadas e integrações com aceleradores, mas essas opções exigem conceção e medição explícitas.

Execução em pipeline e utilização do GPU

Spark agenda o trabalho em fases separadas por limites de shuffle. Uma implementação direta pode colocar o download, a descodificação e a inferência numa sequência que deixa a capacidade do CPU ou do GPU à espera. Spark suporta agendamento de recursos GPU e plugins, pelo que o tempo ocioso não é inevitável. Manter as fases ocupadas também requer backpressure: abrandar as fases anteriores quando as posteriores não conseguem acompanhar. Nem esse controlo nem a sobreposição do trabalho no CPU e no GPU acontecem automaticamente num job normal de DataFrame em PySpark.

A execução em pipeline é a alternativa. Em vez de executar as fases consecutivamente, o motor sobrepõe I/O, trabalho no CPU e inferência no GPU. Quando as fases e os buffers estão equilibrados, essa sobreposição pode reduzir o tempo ocioso e melhorar o throughput; o arranque e o escoamento, o backpressure ou uma fase mais lenta podem ainda deixar recursos à espera.

Benchmark de processamento de imagens

Fiz um benchmark de processamento de imagens sobre 500 fotografias reais do dataset Food-101. Resultados do repositório de demonstração:

Polars e DataFusion estão ausentes porque este teste visa operações de imagem. Os resultados Python e os resultados Rust registados mostram aproximadamente 1,01 segundos para Pandas + Pillow, 0,28 para Daft e 0,24 para Rust. Estes tempos medem trabalho diferente.

O percurso com Pandas descodifica e redimensiona com Lanczos, converte os píxeis para float32 e normaliza-os. Daft descarrega, descodifica e redimensiona; Rust carrega e redimensiona, descartando silenciosamente falhas ao abrir imagens. Nenhum executa o passo de normalização do Pandas. A execução não verificou se todos os motores processaram as mesmas imagens e produziram resultados equivalentes. Por isso, os rácios de tempo não isolam o overhead do motor ou da linguagem. Utilize as mesmas imagens e alinhe as operações, o comportamento de resize, os outputs e o tratamento de erros antes de comparar o throughput; só 500 imagens continuariam a ser insuficientes para prever o desempenho em produção.

Parte 3: processamento distribuído

Quando uma única máquina deixa de ser suficiente, é necessário escolher como distribuir o trabalho.

Apache Spark

Spark é uma opção madura para ETL tabular de grande escala, joins intensivos em shuffle e organizações que já operam o seu ecossistema. A recuperação baseada em lineage e o amplo suporte de plataforma são importantes quando a fiabilidade e a familiaridade operacional pesam mais do que a velocidade local. Os pipelines mistos de CPU/GPU exigem uma configuração de recursos e um desenho do pipeline mais deliberados do que o percurso SQL, área em que Ray Data e Daft oferecem uma abstração mais focada.

Esta query Spark faz join entre viagens de táxi mais longas e informação sobre as zonas de recolha, resumindo depois a receita total e as tarifas médias por município. Para a configuração de ETL em cluster, consulte distributed_spark.ipynb ou spark_etl.py:

from pyspark.sql import SparkSession
from pyspark.sql import functions as F

spark = SparkSession.builder \
    .appName("TaxiETL") \
    .config("spark.sql.adaptive.enabled", "true") \
    .getOrCreate()

orders = spark.read.parquet("s3a://lake/taxi/*.parquet")
zones = spark.read.csv("s3a://lake/taxi_zones.csv", header=True)

# Spark excels at this: joining massive tables with a shuffle
result = (
    orders
    .filter(F.col("trip_distance") > 5.0)
    .join(zones, orders.PULocationID == zones.LocationID, "inner")
    .groupBy("Borough")
    .agg(
        F.sum("total_amount").alias("total_revenue"),
        F.avg("total_amount").alias("avg_fare"),
    )
    .orderBy(F.desc("total_revenue"))
)

Ray Data para computação heterogénea

Ray Data foi concebido para workloads de AI. Em vez das barreiras entre fases do Spark, utiliza um modelo de streaming que mantém os GPUs alimentados. Um actor do Ray é um worker persistente que pode manter um modelo carregado entre batches. A funcionalidade mais importante para pipelines de AI é o agendamento de recursos mistos: pode declarar que um actor pretende “1 GPU, 4 CPUs” e que outro precisa apenas de CPUs, deixando o Ray tratar do resto.

A Amazon comunicou poupanças computacionais depois de transferir workloads internos selecionados de processamento de dados do Spark para o Ray. Com as tarifas on-demand R5 do EC2, essas poupanças foram equivalentes a mais de $120 milhões por ano. O relatório cita uma eficiência de custos 91% superior na prova de conceito e 82% em produção por GiB de entrada do S3. A escala é significativa, mas trata-se de um estudo de caso de migração para workloads específicos, não de uma poupança esperada numa adoção típica do Ray.

O exemplo abaixo lê imagens, classifica-as com ResNet18 em workers GPU e escreve as previsões em Parquet. Para a configuração de inferência de imagens, consulte distributed_ray.ipynb ou ray_inference.py:

import ray

ray.init()

ds = ray.data.read_images("s3://my-bucket/food101/", mode="RGB")

class ImageClassifier:
    def __init__(self):
        import torch
        from torchvision.models import resnet18, ResNet18_Weights
        self.model = resnet18(weights=ResNet18_Weights.DEFAULT).cuda()
        self.model.eval()
        self.preprocess = ResNet18_Weights.DEFAULT.transforms()

    def __call__(self, batch):
        import torch
        from PIL import Image
        tensors = torch.stack([
            self.preprocess(Image.fromarray(img)) for img in batch["image"]
        ]).cuda()
        with torch.no_grad():
            preds = self.model(tensors)
        return {
            "prediction": preds.argmax(dim=1).cpu().numpy(),
            "max_logit": preds.max(dim=1).values.cpu().numpy(),
        }

# ActorPoolStrategy creates persistent GPU workers
predictions = ds.map_batches(
    ImageClassifier,
    compute=ray.data.ActorPoolStrategy(size=4),
    num_gpus=1,
    batch_size=64,
)
predictions.write_parquet("s3://output/predictions/")

Este esboço reserva quatro actors, cada um com um GPU, e requer quatro GPUs CUDA disponíveis, pesos do Torchvision e acesso ao S3. O Ray lê as imagens como arrays NumPy; converter arrays RGB para PIL fornece à transformação de pré-processamento do ResNet18 uma entrada aceite. max_logit é o maior score bruto do modelo, não uma probabilidade de confiança.

A proporção CPU-GPU merece atenção neste caso. Nos benchmarks da Anyscale, o Ray Data continuou a escalar à medida que aumentava o número de CPUs por GPU, enquanto os outros motores testados estabilizaram. A fonte relata até 3x de speedup na inferência de imagens à medida que diminui a falta de dados no CPU, porque os feeders no CPU conseguem acompanhar o GPU.

Daft distribuído

O Daft escala através do seu motor Flotilla: um worker Swordfish por nó, com o Flotilla por cima a realizar o agendamento em todo o cluster. O Swordfish trata da execução local em Rust e coloca o I/O em pipeline com a computação através de streaming em batches pequenos, mantendo cada nó ocupado sem esperar pela fase seguinte.

Nos benchmarks publicados pelo Daft, o Flotilla foi 4–18x mais rápido do que as implementações Spark testadas em quatro workloads multimodais. A maior diferença ocorreu num caso de deteção de objetos em vídeo. Interprete o resultado como evidência de que o desenho da execução é importante para estes pipelines e compare-o com os resultados concorrentes da Anyscale abaixo e com um teste local.

A Anyscale, a empresa por detrás do Ray, publicou um benchmark concorrente no qual o Ray Data reduziu ou inverteu a diferença em instâncias com muitos CPUs após tuning. Em conjunto, os dois estudos de fornecedores são uma razão para testar operadores representativos e proporções CPU-GPU, não para inferir uma tabela classificativa duradoura.

O exemplo seguinte utiliza o Ray runner do Daft; não reproduz o benchmark Flotilla acima. Lê texto já extraído de documentos, gera embeddings em workers GPU e escreve-os em Parquet. Para a configuração de embeddings distribuídos, consulte distributed_daft.ipynb ou daft_pipeline.py:

import daft
import numpy as np
from daft import col

# Connect to an existing Ray cluster before building the query
daft.set_runner_ray(address="auto")

# PDF extraction happened upstream: each row has non-null string text
df = daft.read_parquet("s3://data-lake/extracted_text/*.parquet")

# Define a GPU class UDF for batched embedding generation
@daft.cls(gpus=1)
class TextEmbedder:
    def __init__(self):
        from sentence_transformers import SentenceTransformer
        self.model = SentenceTransformer("all-MiniLM-L6-v2", device="cuda")

    @daft.method.batch(
        return_dtype=daft.DataType.fixed_size_list(daft.DataType.float32(), 384)
    )
    def __call__(self, text_col):
        texts = text_col.to_pylist()
        embeddings = self.model.encode(texts, batch_size=32)
        return np.asarray(embeddings, dtype=np.float32)

# CPU file reads feed GPU embedding batches
embedder = TextEmbedder()
df = df.with_column("embedding", embedder(col("text")))
df.write_parquet("s3://output/embeddings/")

Este exemplo começa com texto pré-extraído, não com bytes PDF. O Ray runner do Daft liga-se a um cluster existente; o runner nativo predefinido utiliza a máquina local. Instale o Daft com suporte para Ray e disponibilize workers GPU, Sentence Transformers, pesos do modelo e credenciais S3 nesse cluster. A API de classes e métodos de batch mantém o modelo entre batches; as leituras no CPU podem sobrepor-se à inferência no GPU, dependendo do particionamento e do backpressure.

Parte 4: o papel do Rust e do Arrow

Byte diz

Arrow fornece a estes motores uma forma comum de descrever buffers. É ainda necessário medir se uma transferência reutiliza esses buffers.

Por baixo da competição, a convergência é a história mais interessante. Polars, Daft e DataFusion utilizam Rust extensivamente, enquanto Ray inclui componentes nativos juntamente com as suas APIs Python. Todos podem trocar dados através de partes do ecossistema Apache Arrow.

A Arrow PyCapsule Interface (protocolo __arrow_c_stream__) fornece às bibliotecas compatíveis uma forma padrão de trocar streams Arrow. As transferências podem evitar a serialização linha a linha e reutilizar buffers quando os schemas e os layouts de memória são compatíveis. Materialização, rechunking, conversão de tipos ou transferência entre dispositivos podem ainda copiar dados; por isso, valide a transferência com profiling em vez de assumir que é gratuita.

O exemplo seguinte demonstra uma transferência Arrow: o DataFusion conta compras de utilizadores com mais de cinco compras e o Polars ordena essas contagens. Assume que events.parquet já existe. O engine_comparison_examples.ipynb complementar cria .data/events.parquet nas suas células de configuração antes do exemplo Arrow.

from datafusion import SessionContext
import polars as pl

# Compute in DataFusion (Rust-native execution)
ctx = SessionContext()
ctx.register_parquet("events", "events.parquet")
df = ctx.sql("""
    SELECT user_id, COUNT(*) as event_count
    FROM events WHERE event_type = 'purchase'
    GROUP BY user_id HAVING COUNT(*) > 5
""")

# Convert through Arrow; compatible buffers may be reused
arrow_table = df.to_arrow_table()
df_polars = pl.from_arrow(arrow_table)

# Continue analysis in Polars
result = df_polars.with_columns(
    pl.col("event_count").rank().alias("rank")
).sort("rank")

Por que razão estes motores mais recentes utilizam Rust para execução nativa?

  1. Ausência de um garbage collector de tracing no código Rust. A ownership dá aos operadores nativos um controlo mais direto sobre a alocação e desalocação. Isto pode reduzir a latência relacionada com o GC, mas não impede pressão de memória nem falhas por falta de memória.

  2. Representações nativas compactas. As estruturas Rust não transportam cabeçalhos de objetos Java. O benefício prático depende do layout do motor: os sistemas JVM colunares também evitam representar cada valor como um objeto individual.

  3. Verificações de concorrência mais fortes. As regras de Rust seguro excluem muitos data races em tempo de compilação. O código do motor pode ainda conter blocos unsafe e bugs lógicos de concorrência, mas a linguagem reduz a superfície de falha.

Combinadas com o layout de memória colunar do Arrow, estas escolhas podem reduzir o overhead de alocação e serialização. Não o eliminam em todas as fronteiras; objetos Python, transporte de rede, schemas incompatíveis e movimentação entre dispositivos continuam a ser relevantes.

Parte 5: adotar vários motores

Não tem de forçar toda a plataforma a utilizar um único motor. A composição é útil quando o custo da transferência entre motores é inferior ao custo de fazer um sistema tratar de todos os workloads.

Uma possível cadeia utiliza Spark para joins de lakehouse já estabelecidos, escreve num formato de tabela ou ficheiro aberto e entrega o resultado ao Ray Data ou ao Daft para inferência no GPU ou transformações multimodais. Polars ou DuckDB podem servir para análise local sobre os mesmos ficheiros. Uma equipa pequena pode precisar apenas de um destes motores; adicione outro quando um bottleneck medido justificar a fronteira operacional.

O que torna esta composição possível é a interoperabilidade. Parquet é o formato comum de transferência de ficheiros nestes exemplos, enquanto Arrow pode fornecer intercâmbio em memória. O suporte para Delta e Iceberg depende do motor e do connector, pelo que deve validar cada fronteira. Uma transferência por ficheiro também tem custos de I/O e conversão; não é automaticamente gratuita.

Escala diagonal

Durante muito tempo, a escolha era fazer scale up (uma máquina maior) ou scale out (mais máquinas). Polars Cloud descreve uma abordagem dependente da query chamada escala diagonal. Faça scale horizontal enquanto lê do armazenamento cloud para maximizar o I/O; depois, reduza para um único nó grande quando os filtros e as agregações tiverem reduzido os dados. A redução precoce pode limitar a transferência de dados e permitir que o trabalho restante termine num único nó. A ocorrência de um shuffle distribuído depende do plano físico da query.

A lição mais geral é comparar o custo por job concluído com sucesso, não o preço horário da instância. Um nó maior pode ser mais barato quando a redução do tempo de execução compensa a tarifa superior, mas o resultado depende do I/O, da pressão de memória e da quantidade de trabalho eliminada antes de um shuffle.

Reproduzir a comparação

O repositório de demonstração complementar contém os scripts, notebooks e o ambiente utilizados nas comparações. Estes comandos voltam a executar as implementações existentes, incluindo as limitações de medição descritas acima; não as corrigem. O comando tabular utiliza o dataset predefinido do repositório com dados de táxis de todo o ano de 2024, correspondendo à execução maior apresentada anteriormente.

# Install dependencies

# Run the tabular benchmark (~41M NYC taxi trips from full-year 2024)
uv run python -m engine_comparison.benchmarks.tabular

# Run the multimodal benchmark (500 real food photos)
uv run python -m engine_comparison.benchmarks.multimodal

# Run native Rust benchmarks (Polars-rs + image crate)

Principais conclusões

  1. Demonstre que uma máquina não é suficiente. Os resultados de scale-up mostram que alguns scans analíticos grandes cabem num único nó. Meça os requisitos de memória, I/O, spill e recuperação antes de aceitar o overhead de um cluster.

  2. Os modelos de execução são mais importantes do que a sintaxe familiar. Planeamento lazy, pushdown, streaming e operadores paralelos explicam grande parte da diferença entre um script eager com DataFrame e um motor analítico.

  3. Meça todo o pipeline do acelerador. Descodificação, I/O de rede, batching, serialização e backpressure determinam se um GPU permanece ocupado. Ray Data e Daft tornam esta sobreposição uma abstração central; Spark pode suportá-la com desenho e tooling adicionais.

  4. Faça a shortlist por workload e depois execute benchmarks. Utilize o ajuste ao ecossistema para restringir as opções e um job representativo end-to-end para escolher. Os resultados de benchmarks de fornecedores são hipóteses, não garantias.

  5. Os formatos abertos mantêm a escolha reversível. Interfaces compatíveis com Arrow, Parquet e formatos de tabela abertos podem reduzir os custos de transferência. Confirme se uma determinada conversão reutiliza buffers ou os copia.
