Guia de Fine-Tuning de LLM: LoRA, QLoRA, Unsloth, Axolotl

Viacheslav Dubrov

2026-01-04 · Atualizado 2026-07-15 · 22 min · Engenharia de modelos

Tradução automática Este artigo foi traduzido automaticamente a partir da versão original em inglês.

A maioria das falhas de fine-tuning são falhas de decisão. Uma equipa treina antes de demonstrar que prompting, retrieval ou constrained decoding não conseguem resolver o problema. Outra avalia na distribuição de treino ou descobre, depois do treino, que o artifact é difícil de servir.

Este guia trata a adaptação como uma experiência com um ponto de saída operacional. Começa pelo limite de decisão e segue um percurso através dos dados, de LoRA ou QLoRA, da avaliação específica da tarefa, da exportação e do serving.

Para uma decisão rápida sobre a intervenção, consulte Fine-Tuning vs RAG vs Prompting.

TL;DR

Faça fine-tuning quando um baseline medido demonstrar que alterar o comportamento do modelo justifica uma atualização dos pesos. Use retrieval para factos que mudam e constrained decoding para a sintaxe. Comece com LoRA quando o modelo base couber confortavelmente; use QLoRA quando a memória dos pesos congelados for a limitação. Separe um conjunto de avaliação antes do treino, compare com o baseline sem fine-tuning e escolha o artifact de deployment antes de se comprometer com um método.

Antes de gastar horas de GPU, decida se o fine-tuning é a ferramenta adequada para o problema que tem pela frente.

Fine-tuning vs RAG

O fine-tuning pode alterar a forma como um modelo utiliza a linguagem do domínio, mas é um mecanismo fraco para atualizar factos que mudam ou que têm de ser citados. Retrieval e fine-tuning resolvem partes diferentes do problema e pertencem frequentemente ao mesmo sistema.

Fine-tuning vs prompt engineering

Os LLMs modernos respondem bem a prompts claros e exemplos. Teste essas opções antes de investir em fine-tuning.

[!TIP] Experimente prompting primeiro Comece com um prompt e exemplos representativos. Se apenas a sintaxe do output for pouco fiável, adicione constrained decoding antes de alterar os pesos.

Fine-tuning vs constrained decoding

Bibliotecas como xgrammar e outlines restringem a geração a um JSON Schema, expressão regular ou grammar. Dependendo da restrição e do backend, compilam um autómato ou grammar e mascaram os tokens seguintes inválidos. Não é necessária qualquer atualização dos pesos.

Isto garante que o output pertence à linguagem suportada. A garantia nada diz sobre se os valores são verdadeiros, completos ou semanticamente adequados. Um function call sintaticamente válido pode, ainda assim, conter o ID de cliente errado.

AspetoConstrained DecodingFine-Tuning
SetupImediato — definir schema e fazer deployExige curadoria de dados, computação de GPU e iteração
GarantiaSintaxe válida para a restrição suportadaComportamento aprendido; a conformidade com o schema pode variar
FlexibilidadeAlterar o schema a qualquer momento sem novo treinoFica fixo após o treino
LatênciaPequeno overhead (o modelo pode “lutar” contra o schema)Mais baixa (o modelo produz naturalmente o formato)
Mais adequado paraJSON, opções, grammars, sintaxe de tool callComportamento repetido de uma tarefa que o modelo base não domina

Uma ordem prática:

  1. Comece com prompting e exemplos few-shot para formatação básica.
  2. Adicione constrained decoding (xgrammar ou outlines) quando a sintaxe for inconsistente.
  3. Faça fine-tuning apenas quando precisar de alterações comportamentais que um schema não consegue impor.

Torne o caso de negócio mensurável

O fine-tuning pode reduzir tokens de prompt recorrentes ou permitir que um modelo mais pequeno atinja o objetivo, mas nenhuma destas poupanças é automática. Calcule o ponto de equilíbrio com o seu tráfego e preços:

[ \text{pedidos de break-even} = \frac{\text{custo de treino + avaliação + deployment}} {\text{custo baseline/pedido} - \text{custo tuned/pedido}} ]

Se o denominador for pequeno, negativo ou baseado numa suposição de qualidade ainda não demonstrada, o projeto ainda não tem um caso económico.

[!TIP] A configuração híbrida Uma arquitetura comum combina um modelo mais pequeno adaptado à tarefa com retrieval para factos que mudam. Trate o modelo maior com prompting como baseline e mantenha o modelo mais pequeno apenas se atingir os mesmos thresholds de qualidade e segurança específicos da tarefa.

Tipos de fine-tuning

Existem três formas principais de fazer fine-tuning. Diferem no tipo de dados de que necessitam e no que ensinam ao modelo.

1. Continued pre-training (não supervisionado)

Treina o modelo base com mais texto bruto, sem labels. Continua a fazer previsão do token seguinte, tal como no treino de pre-training original.

Quando usar:

  • O domínio tem vocabulário que o modelo base nunca viu (medicina, direito, codebases internas).
  • Tem grandes volumes de texto do domínio, mas não tem pares (input, output) anotados.
  • O modelo base lida mal com terminologia específica do domínio.

Exemplo: treinar com milhões de notas clínicas para que o modelo aprenda abreviaturas médicas, nomes de fármacos e workflows clínicos.

2. Supervised fine-tuning (SFT)

O SFT treina com pares anotados de (input, output). Mostra ao modelo o output exato que pretende para cada input.

Quando usar:

  • Tem uma tarefa específica com um formato de input/output bem definido.
  • Tem dados anotados de qualidade, mesmo em pequenas quantidades.
  • Precisa de comportamento previsível para um formato de input conhecido.

Exemplo: treinar com pares (descrição de query SQL, código SQL) para text-to-SQL.

{
    "input": "Get all users who signed up last month",
    "output": "SELECT * FROM users WHERE signup_date >= DATE_SUB(NOW(), INTERVAL 1 MONTH)"
}

3. Instruction tuning

Instruction tuning é um caso especial de SFT, concebido para fazer os modelos seguir uma grande variedade de instruções em linguagem natural. Os dados de treino são pares (instrução, resposta) abrangendo muitas tarefas diferentes.

Quando usar:

  • Quer um assistant de uso geral (como ChatGPT ou Claude).
  • O modelo tem de lidar com pedidos variados e abertos.
  • Está a criar uma interface de chat.

Exemplo: treinar com milhares de instruções diversificadas, como “Resuma este artigo”, “Escreva um poema sobre X” ou “Explique Y em termos simples”.

Continued pre-training é uma experiência separada e deve ser seguida de testes tanto para ganhos no domínio como para regressões nas capacidades gerais.

O pipeline de fine-tuning em 7 etapas

Fine-tuning é um pipeline, não um único comando. Cada etapa tem os seus próprios modos de falha, e saltar uma delas costuma manifestar-se mais tarde num modelo de má qualidade.

Cada etapa assenta na anterior:

  1. Preparação dos dados — Definir a unidade de avaliação, dividir os dados e limpá-los e formatá-los
  2. Seleção do modelo — Escolher o modelo base adequado e carregar os pesos
  3. Configuração do treino — Configurar o hardware, os hyperparameters e a estratégia de otimização
  4. Fine-tuning — Executar treino SFT, DPO ou ORPO
  5. Avaliação — Fazer benchmark de desempenho e validar a qualidade
  6. Deployment — Exportar e servir o modelo
  7. Monitorização — Acompanhar o desempenho, manter e iterar

[!WARNING] Os dados são a base O treino reproduz falhas sistemáticas presentes nos exemplos. Inspecione labels, leakage, cobertura e conformidade com políticas antes de gastar tempo em sweeps do optimizer.

Etapa 1: Preparação dos dados

Muitos projetos de fine-tuning falham aqui, não no treino. A preparação moderna de dados é mais do que executar uma regex sobre CSVs.

O pipeline de dados em 5 etapas

Ferramentas como DataTrove e Distilabel podem ajudar à escala. Deixe que a taxonomia de falhas e o contrato de dados orientem o desenho do pipeline; a escolha da ferramenta vem depois.

1. Ingestão e filtragem

  • Ação: eliminar recusas (“I cannot answer that”), UTF-8 inválido e idiomas que não são o alvo.
  • Ferramentas: Trafilatura para extração, FastText para identificação de idioma.

2. Política de dados sensíveis

  • Ação: decidir o que o modelo está autorizado a aprender e, conforme necessário, ocultar, tokenizar ou excluir campos pessoais e confidenciais.
  • Ferramentas: Microsoft Presidio ou scrubadub.
  • Motivo: um detector é apenas um controlo; os requisitos de proveniência, consentimento, retenção, acesso e eliminação continuam a aplicar-se.

3. Deduplicação (MinHash LSH)

  • Ação: eliminar near-duplicates para que o modelo não os memorize.
  • Ferramentas: DataTrove lida bem com processamento à escala de terabytes.

4. Augmentation sintética, se necessário

  • Ação: usar um modelo teacher mais forte (GPT-4o, DeepSeek-V3) para reescrever dados brutos como pares limpos de instrução-resposta.
  • Ferramentas: Distilabel.
  • Validação: amostrar outputs do teacher, verificá-los com a mesma rubrica usada para labels humanos e manter separadas na avaliação as slices sintéticas e escritas por humanos.

5. Formatação

  • Ação: converter para um formato standard (Alpaca ou ShareGPT).

Exemplos de formatos de dados

Formato Alpaca (instruction-following):

{
    "instruction": "Summarize the following text.",
    "input": "The text to be summarized...",
    "output": "This is the summary."
}

Formato ShareGPT/ChatML (conversacional):

{
    "conversations": [
        { "from": "user", "value": "Hello, who are you?" },
        { "from": "assistant", "value": "I am a helpful AI assistant." }
    ]
}

O que realmente importa

  • Cobertura antes do volume. Adicione exemplos que representem modos de falha distintos, não repetições do caso maioritário e fácil.
  • Limpeza. Elimine texto irrelevante, normalize espaços e mantenha a formatação consistente.
  • Equilíbrio. Preserve casos raros importantes e reporte o desempenho por slice.
  • Separação. Divida por fonte, utilizador, documento ou tempo quando divisões aleatórias por linha permitiriam leakage de near-duplicates.
  • Proveniência. Registe a fonte, licença ou autorização, histórico de transformações e caminho de eliminação para cada versão do dataset.

Etapa 2: Seleção do modelo e hardware

A escolha do modelo base e a compreensão do GPU floor determinam aquilo que pode realmente treinar.

Comece pelo modelo base mais pequeno que já passe as verificações baseline não negociáveis. Confirme:

  • os termos de licença e redistribuição para o produto previsto;
  • o comportamento de linguagem, domínio, tool use e segurança antes da adaptação;
  • a compatibilidade do tokenizer e do chat template com o dataset;
  • o contexto máximo e o comportamento de truncation necessários para exemplos reais;
  • o suporte tanto no framework de treino como no serving engine de destino.

Fine-tuning é uma etapa de adaptação, não uma reparação para um modelo base inadequado. Se o modelo falhar capacidades que o dataset não abrange, escolha outro modelo base antes de executar mais epochs.

Dimensione o run, não o tier de marketing

Não existe uma tabela duradoura “tamanho do modelo → GPU”. A memória de pico varia com a precisão dos pesos, o optimizer, o número de parâmetros treináveis, o comprimento da sequência, o tamanho do micro-batch, activation checkpointing, a implementação de attention e o overhead do framework. Comece por uma estimativa de memória e execute depois um smoke test curto no comprimento máximo, usando exatamente a stack pretendida.

Componente de memóriaFine-tuning completoLoRAQLoRA
Pesos basePrecisão de treinoCongelados, normalmente BF16/FP16Congelados, normalmente NF4 de 4 bits
GradientsTodos os pesos treináveisPesos do adapterPesos do adapter
Estados do optimizerTodos os pesos treináveisPesos do adapterPesos do adapter
ActivationsDepende do batch e do comprimento da sequência em qualquer métodoMesma dependênciaMesma dependência

O artigo original sobre QLoRA conseguiu ajustar um modelo LLaMA 65B numa única GPU de 48 GB, na sua configuração específica. Esse resultado é um limite útil, não uma promessa de que todas as arquiteturas atuais de 70B, comprimentos de contexto, kernels ou trainers caberão no mesmo dispositivo.

Matemática da memória

Para um modelo com PPP parâmetros, só os pesos exigem aproximadamente 2P2P2P bytes em BF16/FP16 ou 0.5P0.5P0.5P bytes a quatro bits, antes dos metadados de quantization e dos buffers do runtime. O treino completo ao estilo Adam acrescenta gradients, estados do optimizer e, frequentemente, master weights de maior precisão. LoRA evita a maior parte da memória dos estados treináveis; QLoRA reduz adicionalmente a ocupação dos pesos base congelados. As activations podem, ainda assim, dominar com comprimentos de sequência elevados.

Use este workflow:

  1. Escolha a sequência mais longa e o micro-batch que tem de suportar.
  2. Estime os pesos e o estado treinável, deixando margem para activations e kernels.
  3. Execute um passo de forward/backward no comprimento máximo.
  4. Registe a memória de pico allocated e reserved.
  5. Só depois aumente o batch size, o rank, o comprimento da sequência ou o número de GPUs.

Etapa 3: Métodos de treino (PEFT e LoRA)

Fine-tuning completo vs PEFT

O fine-tuning completo (FFT) atualiza todos os pesos, pelo que os gradients e o estado do optimizer escalam com o modelo inteiro. O pico não pode ser inferido apenas a partir do número de parâmetros, mas é muito superior à memória necessária para carregar os pesos para inferência.

O parameter-efficient fine-tuning (PEFT) treina apenas um pequeno subconjunto de parâmetros e congela os restantes. A matemática torna-se bastante mais simples.

LoRA: o ponto de partida

LoRA (Low-Rank Adaptation) congela uma matriz pré-treinada e representa a sua atualização aprendida com duas matrizes mais pequenas. O artigo original motiva esta abordagem com a hipótese de que atualizações úteis de adaptação têm baixo rank intrínseco.

Para uma matriz congelada W0∈Rdout×dinW_0 \in \mathbb{R}^{d_{out} \times d_{in}}W0​∈Rdout​×din​, LoRA aprende:

  • A∈Rr×dinA \in \mathbb{R}^{r \times d_{in}}A∈Rr×din​
  • B∈Rdout×rB \in \mathbb{R}^{d_{out} \times r}B∈Rdout​×r

A layer adaptada é:

W′=W0+αrBAW' = W_0 + \frac{\alpha}{r}BAW′=W0​+rα​BA

O adapter tem r(din+dout)r(d_{in}+d_{out})r(din​+dout​) parâmetros treináveis, em vez de dindoutd_{in}d_{out}din​dout​ para essa matriz. Para uma matriz quadrada com largura 4.096 e rank 16, isso representa uma redução de 128× para a matriz, não de 10.000× para um modelo arbitrário. O valor de 10.000× destacado no artigo de LoRA correspondia a uma configuração específica do GPT-3 175B que adaptava matrizes selecionadas.

Quando escolher cada um

  • LoRA: comece aqui. Rápido, eficiente em memória e bem suportado.
  • QLoRA: quando a mesma experiência LoRA não couber devido aos pesos base congelados.
  • DoRA: depois de uma comparação LoRA apples-to-apples demonstrar um ganho útil.
  • Fine-tuning completo: apenas depois de PEFT ser um bottleneck avaliado, e não uma suposição.

DoRA: LoRA com decomposição dos pesos

DoRA (Weight-Decomposed Low-Rank Adaptation) separa a magnitude de cada vetor de pesos da sua direção. Aplica uma atualização LoRA ao componente direcional, enquanto aprende a magnitude separadamente.

Como funciona:

Em vez de tratar os pesos como uma entidade única, DoRA divide os pesos pré-treinados em dois componentes:

  1. Magnitude — um valor treinável por vetor de pesos.
  2. Direção — um vetor normalizado atualizado através de matrizes de baixo rank.

Em notação compacta por coluna:

W′=mV+BA∥V+BA∥cW' = m \frac{V + BA}{\lVert V + BA \rVert_c}W′=m∥V+BA∥c​V+BA​

onde:

  • m = magnitude (treinável)
  • VVV = matriz direcional congelada
  • BABABA = atualização direcional aprendida de baixo rank
  • ∥⋅∥c\lVert \cdot \rVert_c∥⋅∥c​ = normalização por coluna

O que obtém com esta estrutura adicional:

  • Mais graus de liberdade do que o LoRA standard, porque a magnitude pode mudar independentemente.
  • Melhores resultados do que LoRA em várias configurações reportadas pelo artigo que propôs o método.
  • Mais parâmetros e computação; o ganho deve, por isso, ser verificado na sua tarefa e no seu serving path.

Merging de adapters para aprendizagem multi-task

Adapters separados permitem que uma única base congelada suporte várias tarefas. Pode encaminhar pedidos para um adapter, servir vários adapters a partir de um único engine quando suportado ou criar um candidato merged offline. O merging pode introduzir interferência; avalie o artifact merged em vez de assumir que os adapters de origem se compõem sem problemas.

Métodos comuns de merging:

  1. Concatenação — combinar parâmetros dos adapters e aumentar o rank efetivo. Rápido e simples.
  2. Combinação linear — soma ponderada de adapters. Permite ajustar parâmetros.
  3. SVD — decomposição matricial para merging. Mais flexível, mas mais lenta.

Exemplo: um adapter para sumarização e outro para tradução, merged num único modelo multi-task.

Etapa 4: Fine-tuning e alinhamento de preferências

SFT aprende demonstrações. Preference optimization aprende, em vez disso, com comparações como “a resposta A escolhida é melhor do que a resposta B rejeitada”. Use-a apenas quando a preferência par a par for o label correto para o erro; a correção factual e a conformidade com políticas exigem frequentemente evaluators mais fortes do que uma preferência global.

RLHF baseado em PPO

A receita original era um pipeline em três etapas:

  1. SFT — aprender a tarefa.
  2. Reward model — treinar com preferências humanas (chosen vs rejected).
  3. PPO (Proximal Policy Optimization) — reinforcement learning para otimizar a policy.

O custo operacional vem dos vários componentes:

  • É complicado de implementar e manter.
  • É caro — treina vários modelos.
  • On-policy sampling e a otimização da reward exigem verificações cuidadosas de estabilidade e reward hacking.

DPO

DPO (Direct Preference Optimization) elimina o reward model explícito e o RL loop. Continua a otimizar o objetivo de RLHF (maximização da reward com uma restrição de divergência KL), mas fá-lo como um problema de supervised learning reparametrizado, em vez de reinforcement learning:

{
    "prompt": "Explain quantum computing",
    "chosen": "Quantum computing uses qubits...",   # Preferred response
    "rejected": "Well, it's complicated..."        # Non-preferred response
}

Alterações operacionais:

  • Caminho de código mais simples (sem reward model separado e sem RL loop).
  • Um objetivo offline sobre pares de preferências, em vez de reinforcement learning on-policy.
  • Uma policy de referência ou log probabilities de referência equivalentes na formulação standard.

DPO é mais fácil de prototipar do que um pipeline PPO completo, mas não é uma melhoria automática da qualidade. Os resultados dependem da policy inicial, da qualidade dos pares, das definições da loss, dos efeitos do comprimento e do protocolo de avaliação. Compare-o com um checkpoint SFT nas mesmas suites de preferências e tarefas held-out.

ORPO

ORPO (Odds-Ratio Preference Optimization) combina a loss de negative log-likelihood do SFT com uma penalização baseada em odds ratio para respostas rejeitadas. Remove o modelo de referência separado e pode combinar aprendizagem da tarefa e preference optimization num único run.

Como funciona: ORPO usa uma loss combinada que faz duas coisas ao mesmo tempo:

  1. Maximiza a likelihood da resposta escolhida (aprende a tarefa).
  2. Penaliza a resposta rejeitada com um termo de odds ratio (aprende preferências).

Hyperparameters importantes:

from trl import ORPOConfig

config = ORPOConfig(
    learning_rate=8e-6,  # Very low, as recommended by the ORPO paper
    beta=0.1,            # Controls strength of preference penalty
    # ... other params
)
  • Learning rate: o artigo usou valores baixos nas suas experiências; faça tuning tendo em conta o modelo, o batch e os dados, em vez de copiar um valor como regra.
  • Beta: controla o termo de preferência relativamente ao termo SFT.

O trade-off:

  • Uma etapa de treino em vez de duas.
  • Sem reward model.
  • Sem forward pass do modelo de referência.
  • Um run acoplado: se a aprendizagem da tarefa ou o comportamento de preferência regredir, não existe um checkpoint SFT intermédio do mesmo pipeline para inspecionar.

Escolha com base no desenho dos dados e da avaliação:

  • Use DPO quando já tiver um checkpoint SFT satisfatório e quiser uma experiência de preferência offline mais simples.
  • Teste ORPO quando um objetivo sem modelo de referência e de uma só etapa se adequar aos seus dados e restrições operacionais.
  • Use RLHF baseado em PPO quando o sampling online face a uma reward aprendida explícita fizer parte dos requisitos e puder monitorizar a exploração da reward.

Nenhum deles é default para todas as tarefas. Mantenha um baseline apenas com SFT e reporte métricas da tarefa e métricas de preferência.

Frameworks de fine-tuning

Os frameworks sobrepõem-se e mudam rapidamente. Escolha com base no execution path que precisa de suportar, fixe as versões e mantenha a configuração de treino suficientemente portátil para ser reproduzida fora de um notebook.

Unsloth — velocidade e eficiência de memória

Unsloth integra-se com Hugging Face trl e transformers e fornece kernels otimizados, checkpointing e execution paths de fine-tuning quantizado para modelos suportados.

  • Kernels GPU Triton personalizados para attention, RoPE e cross-entropy que evitam o overhead do PyTorch.
  • Backpropagation eficiente em memória que recalcula as activations durante o backward pass em vez de as manter em memória.
  • Operações fused que agregam vários passos (layer norm + linear e semelhantes) em chamadas únicas à GPU.
  • Quantization de 4 bits integrada diretamente no path QLoRA, com dequantization otimizada.

[!IMPORTANT] A ordem dos imports é importante Siga a ordem dos imports no exemplo do Unsloth para a versão que fixar. O Unsloth aplica patches durante o import; por isso, importá-lo antes de trl e transformers evita otimizações em falta ou erros específicos da versão.

# Correct order
from unsloth import FastLanguageModel  # Must be first!
from trl import SFTTrainer
from transformers import TrainingArguments

# Avoid this order with Unsloth's patched path
from trl import SFTTrainer
from unsloth import FastLanguageModel

Mais adequado para: treino numa única GPU, prototipagem, notebooks Colab e qualquer pessoa que esteja atenta à fatura de GPU.

Os valores publicados de velocidade e memória variam consoante o modelo, comprimento da sequência, batch, precisão e hardware. Faça benchmark de tokens por segundo e memória de pico no seu próprio run, em vez de tratar uma proporção de marketing como propriedade do framework.

# config.yaml - no code required
base_model: meta-llama/Meta-Llama-3-8B

Execute com: accelerate launch -m axolotl.cli.train config.yaml

Mais adequado para: runs declarativos e reproduzíveis e opções integradas de launcher para treino distribuído. A configuração pode ser revista, versionada e reutilizada em runs locais e distribuídos.

Código principal de treino

from unsloth import FastLanguageModel
from trl import SFTConfig, SFTTrainer

# Load model with 4-bit quantization
model, tokenizer = FastLanguageModel.from_pretrained(
    model_name="nvidia/Llama-3.1-Nemotron-Nano-4B-v1.1",
    max_seq_length=4096,
    load_in_4bit=True,
)

# Add LoRA adapters
model = FastLanguageModel.get_peft_model(
    model,
    r=16,
    lora_alpha=32,
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj",
                    "gate_proj", "up_proj", "down_proj"],
    use_gradient_checkpointing="unsloth",  # Lower activation memory; extra compute
)

# The preceding data step must create these versioned dataset objects.
# Each row has the chat messages and tool schemas expected by current TRL.

# Train with the current TRL configuration surface.
trainer = SFTTrainer(
    model=model,
    processing_class=tokenizer,
    train_dataset=train_dataset,
    eval_dataset=eval_dataset,
    args=SFTConfig(
        output_dir="outputs/nemotron-function-calling",
        max_length=4096,
        packing=True,
        per_device_train_batch_size=2,
        gradient_accumulation_steps=4,
        learning_rate=2e-4,
        num_train_epochs=3,
        bf16=True,
    ),
)
trainer.train()

Etapa 5: Avaliação

Byte says

Dividi as linhas aleatoriamente e o modelo ajustado esmagou o modelo base. Depois encontrei o mesmo chamado de suporte nas duas metades. Eu tinha dividido linhas quando a unidade era o chamado.

Congele o contrato de avaliação antes do primeiro run. No mínimo, compare o checkpoint tuned com a base exata sem fine-tuning, usando o mesmo prompt, as mesmas definições de decoding e o mesmo ambiente de ferramentas. Só reporte a qualidade agregada depois de verificar as failure slices que o projeto pretendia melhorar.

Acompanhe quatro grupos:

  1. Tarefa-alvo: exact match, sucesso de execução, rubrica humana ou outro resultado associado ao caso de uso.
  2. Regressão: capacidades gerais e slices de tarefas anteriormente suportadas que a adaptação possa prejudicar.
  3. Segurança e políticas: recusas, fuga de dados, prompt injection ou restrições específicas do domínio.
  4. Operações: latência, throughput, memória, tamanho do artifact e custo na configuração de serving prevista.

Etapa 6: Deployment e formatos de output

Escolha o artifact com base no serving engine e no plano de rollback, não apenas no tamanho do ficheiro:

1. Adapter LoRA

uv run finetune  # Saves ~100-500MB adapter
  • Tamanho: proporcional aos módulos-alvo, rank, layers e dtype; frequentemente muito inferior ao da base.
  • Mais adequado para: desenvolvimento, adapters de tarefa versionados e engines que suportem LoRA diretamente.
  • Vantagem adicional: pode trocar adapters sem voltar a descarregar o modelo base.

2. Modelo merged

uv run finetune --merge  # Creates a standalone full model
  • Tamanho: aproximadamente o checkpoint base completo na precisão de output escolhida.
  • Mais adequado para: engines ou paths de distribuição que não suportem o adapter separadamente.
  • Trade-off: artifact maior e rollout mais lento; carregamento de um único modelo mais simples.

3. Formato GGUF

uv run finetune --gguf q4_k_m  # Creates ~2-4GB quantized model
  • Tamanho: depende do modelo; aproximadamente pesos de quatro bits mais metadados para variantes Q4.
  • Mais adequado para: inferência em CPU, Ollama, llama.cpp e deployment edge.
  • Opções: q4_k_m (mais pequeno), q5_k_m (maior fidelidade dos pesos), q8_0 (maior e com mais fidelidade). Meça o impacto na tarefa depois da conversão.

Monitorizar o modelo lançado

O ciclo de vida não termina quando a training loss está saudável. Registe a revisão do modelo base, o tokenizer e o chat template, o hash do adapter, a versão do dataset, a configuração de treino e o relatório de avaliação como uma única unidade de release. Em produção, monitorize o sucesso da tarefa, outputs inválidos, falhas de políticas, latência e drift dos inputs usando as mesmas slices da avaliação offline. Mantenha o artifact anterior carregável e defina um threshold de rollback antes do lançamento.

Principais conclusões

  1. Faça fine-tuning apenas depois de um baseline sem fine-tuning e de uma taxonomia de falhas demonstrarem que a adaptação dos pesos resolve o problema.
  2. Retrieval gere evidência mutável; constrained decoding gere sintaxe; nenhum dos dois é substituído por SFT.
  3. LoRA reduz o estado treinável. QLoRA comprime adicionalmente os pesos base congelados. Não atribua ao LoRA os valores de memória do QLoRA.
  4. A cobertura dos dados, a integridade da divisão, a proveniência e o masking da loss importam mais do que copiar uma configuração de optimizer da moda.
  5. DPO, ORPO e RLHF baseado em PPO são desenhos experimentais diferentes, não uma escada de qualidade com um default universal.
  6. Avalie o comportamento-alvo, as regressões, a segurança e as operações contra o mesmo modelo base.
  7. Escolha o output adapter, merged ou GGUF com base nos requisitos de serving e rollback antes do treino.
