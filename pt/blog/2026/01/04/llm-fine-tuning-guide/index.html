Guia de Fine-Tuning de LLMs: LoRA, QLoRA, Unsloth, Axolotl

Viacheslav Dubrov

2026-01-04 · Atualizado 2026-09-12 · 26 min · Engenharia de modelos

Tradução automática

Este artigo foi traduzido automaticamente a partir da versão original em inglês.

Este guia destina-se a engenheiros de Python que precisam de decidir se devem fazer fine-tuning de um large language model e como fazê-lo. Ficará a saber quando escolher fine-tuning em vez de prompting ou retrieval e como escolher entre métodos como LoRA e QLoRA. O guia explica também como preparar dados, avaliar o modelo treinado e planear o deployment.

Os exemplos explicam configurações e verificações. Não constituem uma receita de treino end-to-end verificada; a secção prática separa os comandos do repositório complementar de uma configuração de treino proposta.

Para uma comparação mais curta dessas opções, consulte Fine-Tuning vs RAG vs Prompting.

Deve fazer fine-tuning?

Antes de gastar horas de GPU, decida se o fine-tuning é a ferramenta certa para o problema que tem à sua frente.

O Byte diz

Se o único comportamento em falta for JSON válido, teste primeiro constrained decoding nos pesos originais. Um treino é uma forma longa de descobrir que faltava uma chaveta.

O fine-tuning altera o comportamento codificado nos pesos. O retrieval fornece evidência em tempo de inferência, pelo que é o melhor ponto de partida para factos que mudam ou que precisam de citações. Os documentos novos só ficam disponíveis depois da ingestão e indexação; compare essa frescura com o seu requisito.

Prompts e exemplos claros são mais baratos de iterar do que um novo treino. Podem já resolver um problema de estilo ou de seguimento de instruções. O fine-tuning pode reduzir tokens repetidos de prompt, mas a latência de serving depende do modelo, do comprimento da saída, do hardware e da implementação; uma atualização dos pesos não é, por si só, uma aceleração.

Para sintaxe, bibliotecas como xgrammar e outlines mascaram os tokens seguintes inválidos sob um schema ou gramática suportados. Uma geração constrained concluída com sucesso pertence a essa linguagem. Trate a truncagem e outras gerações incompletas separadamente e valide o resultado antes de o utilizar. A constraint não pode tornar verdadeiro um ID de cliente nem tornar adequada uma escolha de ferramenta. Meça a latência no seu backend em vez de assumir um overhead fixo.

Tornar o caso de negócio mensurável

O fine-tuning pode reduzir tokens recorrentes de prompt ou permitir que um modelo mais pequeno atinja o objetivo, mas nenhuma dessas poupanças é automática. Calcule o ponto de equilíbrio com o seu tráfego e preços:

[ \text{pedidos de break-even} = \frac{\text{custo de treino + avaliação + deployment}} {\text{custo por pedido da baseline} - \text{custo por pedido do modelo ajustado}} ]

Se o denominador for pequeno, negativo ou baseado numa suposição de qualidade ainda não comprovada, o projeto ainda não tem um caso económico.

[!TIP] A configuração híbrida Uma arquitetura comum combina um modelo mais pequeno adaptado à tarefa com retrieval para factos que mudam. Trate o modelo maior com prompting como baseline e mantenha o modelo mais pequeno apenas se atingir os mesmos limiares de qualidade e segurança específicos da tarefa.

Tipos de fine-tuning

O fine-tuning pode assumir três formas principais. Diferem no tipo de dados de que precisam e no que ensinam ao modelo.

1. Continued pre-training (self-supervised)

Treina o modelo base com mais texto em bruto, usando o token seguinte em cada sequência como objetivo de treino. Isto é self-supervised learning: o texto fornece os seus próprios objetivos, tal como no treino original.

Quando utilizar:

  • O domínio tem vocabulário que o modelo base nunca viu (medicina, direito, bases de código internas).
  • Tem grandes volumes de texto do domínio, mas não tem pares anotados (entrada, saída).
  • O modelo base tem dificuldade com terminologia específica do domínio.

Exemplo: treinar com milhões de notas clínicas para que o modelo aprenda abreviaturas médicas, nomes de medicamentos e fluxos de trabalho clínicos.

2. Supervised fine-tuning (SFT)

O SFT treina com pares anotados (entrada, saída). Mostra ao modelo exatamente a saída pretendida para cada entrada.

Quando utilizar:

  • Tem uma tarefa específica com um formato de entrada/saída limpo.
  • Tem dados anotados de qualidade, mesmo que em pequena quantidade.
  • Precisa de comportamento previsível para um formato de entrada conhecido.

Exemplo: treinar com pares (descrição de query SQL, código SQL) para text-to-SQL. Este intervalo de calendário fixo assume que signup_date está armazenado em UTC:

{
    "input": "Get users who signed up in August 2026 (UTC)",
    "output": "SELECT * FROM users WHERE signup_date >= '2026-08-01' AND signup_date < '2026-09-01'"
}

3. Instruction tuning

Instruction tuning é um caso especial de SFT concebido para fazer com que os modelos sigam uma grande variedade de instruções em linguagem natural. Os dados de treino são pares (instrução, resposta) de muitas tarefas diferentes.

Quando utilizar:

  • Quer um assistente de uso geral (como ChatGPT ou Claude).
  • O modelo precisa de lidar com pedidos variados e abertos.
  • Está a criar uma interface de chat.

Exemplo: treinar com milhares de instruções diversificadas, como «Resuma este artigo», «Escreva um poema sobre X» ou «Explique Y em termos simples».

Continued pre-training é uma experiência distinta e deve ser seguida de testes tanto dos ganhos no domínio como de regressões nas capacidades gerais.

O pipeline de fine-tuning em 7 fases

O fine-tuning é um pipeline, não um único comando. Cada fase tem os seus próprios modos de falha e saltar uma delas costuma revelar-se mais tarde num modelo fraco.

Cada fase assenta na anterior:

  1. Preparação dos dados — Definir a unidade de avaliação, dividir os dados e depois limpá-los e formatá-los
  2. Seleção do modelo — Escolher o modelo base adequado e carregar os pesos
  3. Configuração do treino — Configurar hardware, hiperparâmetros e estratégia de otimização
  4. Fine-tuning — Executar treino SFT, DPO ou ORPO
  5. Avaliação — Fazer benchmark do desempenho e validar a qualidade
  6. Deployment — Exportar e servir o modelo
  7. Monitorização — Acompanhar o desempenho, manter e iterar

[!WARNING] Os dados são a base O treino reproduz falhas sistemáticas presentes nos exemplos. Inspecione labels, leakage, cobertura e conformidade com políticas antes de gastar tempo em sweeps do optimizer.

Fase 1: Preparação dos dados

Muitos projetos de fine-tuning falham aqui, não durante o treino. A preparação moderna de dados é mais do que executar uma regex sobre CSVs.

Cinco transformações depois da divisão por origem

Atribua os grupos de origem ao treino ou à avaliação antes de transformar as linhas. Um ticket de suporte e todas as suas reescritas devem permanecer na mesma partição. Faça clusterização dos near-duplicates conhecidos antes de atribuir os grupos e volte a verificar entre partições depois da limpeza. Congele o conjunto de avaliação; faça augmentation apenas nos dados de treino.

Enumere os erros que os seus exemplos devem ensinar o modelo a corrigir e, depois, defina os campos e labels obrigatórios de cada linha. Escolha ferramentas de processamento para esses passos; DataTrove e Distilabel podem ajudar com datasets maiores.

1. Ingestão e filtragem

  • Ação: remova UTF-8 inválido e conteúdo fora da tarefa. Classifique recusas segundo a política: mantenha recusas corretas como objetivos de treino e casos de avaliação; exclua apenas recusas inválidas ou fora da tarefa.
  • Ferramentas: Trafilatura para extração e modelos de identificação de idioma do fastText para language ID; os modelos distribuídos lid.176 reconhecem 176 idiomas.

2. Política de dados sensíveis

  • Ação: decida o que o modelo pode aprender e, depois, faça redaction, tokenização ou exclusão de campos pessoais e confidenciais conforme necessário.
  • Ferramentas: Microsoft Presidio ou scrubadub.
  • Porquê: um detector é apenas um controlo; continuam a aplicar-se requisitos de proveniência, consentimento, retenção, acesso e eliminação.

3. Deduplication (MinHash LSH)

  • Ação: remova near-duplicates para reduzir repetição e risco de leakage; isto não impede memorization.
  • Ferramentas: DataTrove lida bem com processamento à escala de terabytes.

4. Synthetic augmentation, se necessário

  • Ação: utilize um teacher model adequado para reescrever exemplos de treino em pares instrução-resposta, mantendo os respetivos IDs de origem. Não faça augmentation da partição reservada para avaliação.
  • Ferramentas: Distilabel.
  • Validação: recolha uma amostra das saídas do teacher, verifique-as com a mesma rubrica usada nos labels humanos e reporte separadamente os resultados dos exemplos sintéticos e dos exemplos escritos por humanos. Um subconjunto de avaliação deste tipo chama-se slice; outras slices úteis incluem idioma e tipo de tarefa.

5. Formatação

  • Ação: converta para um formato standard (Alpaca ou ShareGPT).

Exemplos de formatos de dados

Formato Alpaca (instruction-following):

{
    "instruction": "Summarize the following text.",
    "input": "The text to be summarized...",
    "output": "This is the summary."
}

Armazenamento ao estilo ShareGPT (conversacional):

{
    "conversations": [
        { "from": "user", "value": "Hello, who are you?" },
        { "from": "assistant", "value": "I am a helpful AI assistant." }
    ]
}

O que realmente importa

  • Cobertura antes do volume. Adicione exemplos que representem modos de falha distintos, não repetições do caso maioritário fácil.
  • Limpeza. Elimine texto irrelevante, normalize espaços e mantenha a formatação consistente.
  • Equilíbrio. Preserve casos raros importantes e reporte o desempenho por slice.
  • Separação. Divida por origem, utilizador, documento ou tempo quando divisões aleatórias por linha causariam leakage de near-duplicates.
  • Proveniência. Registe a origem, licença ou permissão, histórico de transformações e caminho de eliminação para cada versão do dataset.

Fase 2: Seleção do modelo e hardware

O modelo base e o requisito mínimo de memória de GPU determinam o que pode treinar.

Comece pelo modelo base mais pequeno que já ultrapassa as verificações de baseline não negociáveis. Confirme:

  • os termos de licença e redistribuição para o produto pretendido;
  • o comportamento em idioma, domínio, tool use e segurança antes da adaptação;
  • a compatibilidade do tokenizer e do chat template com o dataset;
  • o contexto máximo e o comportamento de truncagem necessários para exemplos reais;
  • o suporte tanto no framework de treino como no serving engine de destino.

O fine-tuning é uma etapa de adaptação, não uma correção para um modelo base inadequado. Se o modelo falhar em capacidades que o dataset não cobre, escolha outro modelo base antes de executar mais epochs.

Dimensione o run, não o nível de marketing

Não existe uma tabela duradoura «tamanho do modelo → GPU». A memória de pico muda com a precisão dos pesos, o optimizer, o número de parâmetros treináveis, o comprimento da sequência, o micro-batch size, o activation checkpointing, a implementação de attention e o overhead do framework. Comece por uma estimativa de memória e execute depois um smoke test curto no stack exato, com comprimento máximo.

O artigo original sobre QLoRA conseguiu ajustar um modelo LLaMA 65B numa única GPU de 48 GB na sua configuração específica. Esse resultado é um limite útil, não uma promessa de que qualquer arquitetura 70B atual, comprimento de contexto, kernel ou trainer caberá no mesmo dispositivo.

Matemática da memória

Para um modelo com PPP parâmetros, só os pesos exigem aproximadamente 2P2P2P bytes em BF16/FP16 ou 0.5P0.5P0.5P bytes a quatro bits, antes dos metadados de quantização e dos buffers do runtime. O treino completo ao estilo Adam adiciona gradientes, estados do optimizer e, frequentemente, master weights de maior precisão. LoRA evita a maior parte da memória do estado treinável; QLoRA reduz adicionalmente a pegada dos pesos base congelados. As ativações podem ainda dominar com comprimentos de sequência elevados.

Utilize este fluxo de trabalho:

  1. Escolha o comprimento de sequência e o micro-batch mais longos que tem de suportar.
  2. Estime os pesos e o estado treinável, deixando margem para ativações e kernels.
  3. Execute um passo forward/backward com o comprimento máximo.
  4. Registe a memória de pico alocada e reservada.
  5. Só depois aumente o batch size, o rank, o comprimento da sequência ou o número de GPUs.

Fase 3: Configuração e métodos de treino

De linhas armazenadas a objetivos de treino

ShareGPT é uma estrutura de dataset; ChatML é uma convenção de serialização. Converta from/value nos roles e campos aceites pelo trainer e, depois, utilize o chat template do modelo selecionado. Não substitua por tokens ChatML apenas porque os dados são conversacionais.

Para a linha de saudação acima, as mensagens normalizadas são:

messages = [
    {"role": "user", "content": "Hello, who are you?"},
    {"role": "assistant", "content": "I am a helpful AI assistant."},
]
# Inspection step after loading the selected model's tokenizer:
rendered = tokenizer.apply_chat_template(
    messages, tokenize=False, add_generation_prompt=False,
)
print(rendered)

Inspecione a linha efetivamente serializada antes do treino: delimitadores de roles, tokens de fim de turno e tool schemas têm de corresponder à inferência. Numa linha com tool use, preserve as definições das ferramentas, os tool calls do assistant e os tool results como campos distintos. Verifique que a truncagem não remove a resposta supervisionada nem corta um argumento de ferramenta a meio.

Loss masking determina quais os tokens pelos quais o modelo é recompensado ao fazer previsões. No treino da sequência completa, o texto do user, system, tool e assistant pode contribuir. No treino apenas do assistant, esses tokens de contexto continuam visíveis para a attention, mas os seus labels são ignorados (normalmente -100); apenas os spans do assistant contribuem. Para esta saudação, a resposta deve ser um objetivo e a pergunta do utilizador não deve ser, se essa for a intenção do comportamento assistant-only.

A documentação de SFT do TRL suporta assistant_only_loss=True para datasets conversacionais cujos templates expõem spans de geração. Um template sem esses spans não pode fornecer essa mask. Datasets prompt/completion têm uma opção completion_only_loss separada. Antes de ativar qualquer uma delas, inspecione um batch tokenizado e faça decode dos tokens com labels não ignorados. Repita depois com uma conversa com ferramentas e um exemplo de comprimento máximo. A configuração de treino ilustrativa abaixo utiliza deliberadamente loss na sequência completa; o treino assistant-only exige esta verificação adicional do template e da mask.

Escolha um comprimento de sequência com base na distribuição dos dados e execute a verificação de memória para o comprimento máximo da Fase 2. Packing coloca vários exemplos mais curtos numa única sequência de treino. Comece sem packing, para que os limites das linhas sejam fáceis de inspecionar. Faça benchmark do packing apenas depois de confirmar que as linhas serializadas e os labels estão corretos.

Fine-tuning completo vs PEFT

O fine-tuning completo (FFT) atualiza todos os pesos, pelo que os gradientes e o estado do optimizer escalam com o modelo inteiro. O pico não pode ser inferido apenas a partir do número de parâmetros, mas é muito superior à memória necessária para carregar os pesos para inferência.

Parameter-efficient fine-tuning (PEFT) treina apenas um subconjunto pequeno de parâmetros e congela o restante. A matemática torna-se muito mais favorável.

LoRA: o ponto de partida

LoRA (Low-Rank Adaptation) congela uma matriz pré-treinada e representa a sua atualização aprendida com duas matrizes mais pequenas. O artigo original fundamenta esta abordagem na hipótese de que as atualizações úteis de adaptação têm baixo rank intrínseco.

Aqui, dind_{in}din​ é a largura de entrada da camada e doutd_{out}dout​ é a sua largura de saída. O rank rrr é a dimensão partilhada mais pequena das duas matrizes treináveis: um rank menor utiliza menos parâmetros treináveis. A definição α\alphaα controla a escala da atualização através do rácio α/r\alpha/rα/r.

Para uma matriz congelada W0∈Rdout×dinW_0 \in \mathbb{R}^{d_{out} \times d_{in}}W0​∈Rdout​×din​, LoRA aprende:

  • A∈Rr×dinA \in \mathbb{R}^{r \times d_{in}}A∈Rr×din​
  • B∈Rdout×rB \in \mathbb{R}^{d_{out} \times r}B∈Rdout​×r

A camada adaptada é:

W′=W0+αrBAW' = W_0 + \frac{\alpha}{r}BAW′=W0​+rα​BA

Para uma matriz quadrada com largura 4.096 e rank 16, isso representa uma redução de 128× nos parâmetros treináveis dessa matriz. As poupanças no modelo completo dependem das matrizes que recebem adapters.

DoRA: LoRA com decomposição dos pesos

DoRA (Weight-Decomposed Low-Rank Adaptation) separa a magnitude de cada vetor de pesos da sua direção. O artigo sobre DoRA aplica uma atualização LoRA à componente direcional enquanto aprende a magnitude separadamente.

Como funciona:

Em vez de tratar os pesos como uma entidade única, DoRA divide os pesos pré-treinados em duas componentes:

  1. Magnitude — um valor treinável por vetor de pesos.
  2. Direção — um vetor normalizado atualizado através de matrizes de baixo rank.

Em notação compacta por coluna:

W′=mV+BA∥V+BA∥cW' = m \frac{V + BA}{\lVert V + BA \rVert_c}W′=m∥V+BA∥c​V+BA​

onde:

  • m = magnitude (treinável)
  • V=W0V = W_0V=W0​ = a matriz inicial congelada; normalizar depois de adicionar BABABA
  • BABABA = a atualização direcional de baixo rank aprendida
  • ∥⋅∥c\lVert \cdot \rVert_c∥⋅∥c​ = normalização por coluna

O que se obtém com esta estrutura adicional:

  • Mais graus de liberdade do que com LoRA standard, porque a magnitude pode mudar de forma independente.
  • Melhores resultados do que LoRA em várias configurações reportadas pelo artigo que propôs o método.
  • Parâmetros e computação adicionais, pelo que o ganho deve ser verificado na sua tarefa e no seu serving path.

Merging de adapters para aprendizagem multi-tarefa

Adapters separados permitem que uma única base congelada suporte várias tarefas. Pode encaminhar pedidos para um adapter, servir vários adapters a partir de um engine quando suportado ou criar um candidato merged offline. O merging pode introduzir interferência; por isso, avalie o artefacto merged em vez de assumir que os adapters de origem se compõem corretamente.

Métodos comuns de merging:

  1. Concatenação — combina parâmetros de adapters e aumenta o rank efetivo. Rápido e simples.
  2. Combinação linear — soma ponderada de adapters. Dá-lhe parâmetros de controlo.
  3. SVD — decomposição matricial para merging. Mais flexível, mas mais lenta.

Exemplo: um adapter para sumarização e outro para tradução, merged num único modelo multi-tarefa.

Fase 4: Fine-tuning e alinhamento de preferências

SFT aprende demonstrações. Preference optimization aprende, em vez disso, com comparações como «a resposta A escolhida é melhor do que a resposta B rejeitada». Utilize-a apenas quando a preferência pairwise for o label adequado para o erro; correção factual e conformidade com políticas precisam frequentemente de avaliadores mais fortes do que uma preferência global.

RLHF baseado em PPO

RLHF significa reinforcement learning from human feedback. A policy é o language model que gera respostas; um reward model atribui uma pontuação a essas respostas utilizando preferências aprendidas a partir de comparações humanas. Uma receita baseada em PPO tem três fases:

  1. SFT — aprender a tarefa.
  2. Reward model — treinar com preferências humanas (escolhida vs rejeitada).
  3. PPO (Proximal Policy Optimization) — gerar respostas e atualizar o language model para aumentar as respetivas pontuações de reward.

O custo operacional vem das várias componentes:

  • É complicado de implementar e manter.
  • É caro — treina vários modelos.
  • Fazer sampling do modelo que está a ser treinado exige verificações de atualizações instáveis e de respostas que exploram o reward model sem satisfazer a tarefa.

DPO

DPO (Direct Preference Optimization) elimina o reward model separado e o loop de reinforcement learning. Favorece respostas escolhidas e desencoraja alterações grandes relativamente a um modelo inicial fixo, chamado reference model. O artigo sobre DPO deriva este objetivo limitando o quanto as probabilidades das respostas podem afastar-se dessa referência; o limite matemático é uma restrição de divergência KL.

Um par de preferências contém o mesmo prompt e duas respostas candidatas. Esta linha abreviada mostra os seus campos; os labels reais precisam de respostas completas e de uma razão para preferir uma delas:

{
    "prompt": "Explain quantum computing",
    "chosen": "Quantum computing uses qubits...",   # Preferred response
    "rejected": "Well, it's complicated..."        # Non-preferred response
}

O que muda operacionalmente:

  • Caminho de código mais simples (sem reward model separado e sem RL loop).
  • Treino com pares de preferências guardados, em vez de gerar novas respostas para scoring do reward durante cada atualização.
  • Um reference model fixo ou as suas probabilidades log guardadas para as respostas de treino, na formulação standard.

DPO é mais fácil de prototipar do que um pipeline PPO completo, mas não é uma melhoria automática de qualidade. Os resultados dependem da policy inicial, da qualidade dos pares, das definições da loss, dos efeitos do comprimento e do protocolo de avaliação. Compare-o com um checkpoint SFT nos mesmos conjuntos de preferências e tarefas reservados.

ORPO

ORPO (Odds-Ratio Preference Optimization) combina a loss de negative log-likelihood do SFT com uma penalização de odds ratio nas respostas rejeitadas. Elimina o reference model separado e pode combinar aprendizagem da tarefa e preference optimization numa única execução.

Como funciona: ORPO utiliza uma loss combinada que faz duas coisas ao mesmo tempo:

  1. Maximiza a likelihood da resposta escolhida (aprende a tarefa).
  2. Penaliza a resposta rejeitada com um termo de odds ratio (aprende preferências).

Hiperparâmetros importantes (API do TRL 1.12.0):

# API shown in TRL 1.12.0 documentation
from trl.experimental.orpo import ORPOConfig

config = ORPOConfig(
    learning_rate=8e-6,  # Very low, as recommended by the ORPO paper
    beta=0.1,            # Controls strength of preference penalty
    # ... other params
)
  • Learning rate: o artigo utilizou valores baixos nas suas experiências; faça tuning com base no seu modelo, batch e dados, em vez de copiar um valor como regra.
  • Beta: controla o termo de preferência relativamente ao termo SFT.

O compromisso:

  • Uma fase de treino em vez de duas.
  • Sem reward model.
  • Sem forward pass do reference model.
  • Uma execução acoplada: se a aprendizagem da tarefa ou o comportamento de preferência sofrer uma regressão, não existe um checkpoint SFT intermédio do mesmo pipeline para inspecionar.

Escolha com base no desenho dos dados e da avaliação:

  • Use DPO quando já tem um checkpoint SFT satisfatório e quer uma experiência de preferências offline mais simples.
  • Teste ORPO quando um objetivo sem referência e de fase única se adequa aos seus dados e restrições operacionais.
  • Use RLHF baseado em PPO quando o sampling online face a um reward aprendido explícito fizer parte do requisito e puder monitorizar reward exploitation.

Nenhum deles é uma opção default para todas as tarefas. Mantenha uma baseline apenas com SFT e reporte métricas da tarefa e de preferências.

Frameworks de fine-tuning

Os frameworks sobrepõem-se e mudam rapidamente. Escolha com base no execution path que tem de suportar, fixe versões e mantenha a configuração de treino suficientemente portátil para ser reproduzida fora de um notebook.

Unsloth — velocidade e eficiência de memória

Unsloth integra-se com trl e transformers do Hugging Face e fornece kernels otimizados, checkpointing e paths de fine-tuning quantizado para modelos suportados.

  • Custom Triton GPU kernels para attention, RoPE e cross-entropy que evitam o overhead do PyTorch.
  • Backpropagation eficiente em memória que recalcula ativações durante o backward pass em vez de as manter em memória.
  • Operações fused que combinam vários passos (layer norm + linear, e semelhantes) numa única chamada à GPU.
  • Quantização de 4 bits integrada diretamente no path QLoRA, com dequantization otimizada.

[!IMPORTANT] A ordem dos imports é importante Siga a ordem dos imports no exemplo do Unsloth correspondente à versão que fixou. O Unsloth aplica patches durante o import, pelo que importá-lo antes de trl e transformers evita otimizações em falta ou erros específicos da versão.

# Correct order
from unsloth import FastLanguageModel  # Must be first!
from trl import SFTTrainer
from transformers import TrainingArguments

# Avoid this order with Unsloth's patched path
from trl import SFTTrainer
from unsloth import FastLanguageModel

Mais adequado para: treino numa única GPU, prototipagem, notebooks Colab e para quem controla a fatura de GPU.

Os números publicados de velocidade e memória variam consoante o modelo, comprimento da sequência, batch, precisão e hardware. Faça benchmark dos tokens por segundo e da memória de pico na sua própria execução, em vez de tratar um rácio de destaque como uma propriedade do framework.

Para configurações config-first e setups distribuídos, Axolotl torna o workflow reproduzível:

Configuração do companion

O config.py do companion seleciona o modelo, o dataset e as definições LoRA:

# Model & Dataset
MODEL_NAME = "nvidia/Llama-3.1-Nemotron-Nano-4B-v1.1"  # 4B params, 128K context
DATASET_NAME = "glaiveai/glaive-function-calling-v2"   # 113K examples

# LoRA Configuration

LORA_ALPHA = 32    # Update scaling; alpha/r is the classic LoRA scale

# Candidate modules for this Llama-family model

    "gate_proj", "up_proj", "down_proj",

[!NOTE] O rácio alpha-rank alpha/r escala a atualização LoRA clássica. alpha = 2r é uma heurística inicial comum em alguma documentação de ferramentas, não uma garantia de estabilidade. Faça sweep do rank, alpha, learning rate e target modules apenas depois de fixar os dados e a baseline.

Configuração de treino TRL proposta

Esta é uma configuração esquemática, não código distribuído pelo companion. Forneça train_dataset e eval_dataset como datasets Hugging Face com colunas messages e, para exemplos com ferramentas, tools. Produza-os a partir de uma divisão versionada por origem/grupo, conforme descrito na Fase 1. Fixe versões compatíveis de Unsloth, TRL, Transformers e do modelo; o formato da API segue o TRL 1.12.0.

O diagrama mostra esta experiência proposta, incluindo a divisão por origem.

As chamadas abaixo avaliam a loss de tokens held-out uma vez por epoch. Isto é um diagnóstico, não uma medida de exatidão da execução de tool calls; a Fase 5 continua a exigir uma avaliação separada da tarefa.

from unsloth import FastLanguageModel
from trl import SFTConfig, SFTTrainer

# Load model with 4-bit quantization
model, tokenizer = FastLanguageModel.from_pretrained(
    model_name="nvidia/Llama-3.1-Nemotron-Nano-4B-v1.1",
    max_seq_length=4096,
    load_in_4bit=True,
)

# Add LoRA adapters
model = FastLanguageModel.get_peft_model(
    model,
    r=16,
    lora_alpha=32,
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj",
                    "gate_proj", "up_proj", "down_proj"],
    use_gradient_checkpointing="unsloth",  # Lower activation memory; extra compute
)

# Prerequisite: supply the prepared datasets described above.

# Train with the current TRL configuration surface.
trainer = SFTTrainer(
    model=model,
    processing_class=tokenizer,
    train_dataset=train_dataset,
    eval_dataset=eval_dataset,
    args=SFTConfig(
        output_dir="outputs/proposed-nemotron-run",
        max_length=4096,
        packing=False,
        assistant_only_loss=False,  # Full-sequence targets; inspect before changing
        eval_strategy="epoch",
        per_device_train_batch_size=2,
        gradient_accumulation_steps=4,
        learning_rate=2e-4,
        num_train_epochs=3,
        bf16=True,  # Requires BF16-capable hardware
    ),
)
trainer.train()
trainer.save_model("outputs/proposed-nemotron-adapter")
tokenizer.save_pretrained("outputs/proposed-nemotron-adapter")

Fase 5: Avaliação

O Byte diz

Se o mesmo ticket de suporte aparecer no treino e na avaliação, uma pontuação mais alta pode recompensar a recuperação desse ticket. Divida por ticket antes de criar linhas ou reescritas.

Fixe os casos de teste, as regras de scoring e os limiares de aprovação antes da primeira execução. No mínimo, compare o checkpoint ajustado com a base exata sem ajuste, usando o mesmo prompt, as mesmas definições de decoding e o mesmo ambiente de ferramentas. Reporte qualidade agregada apenas depois de verificar as failure slices que o projeto pretendia melhorar.

Acompanhe quatro grupos:

  1. Tarefa-alvo: exact match, sucesso de execução, rubrica humana ou outro resultado ligado ao caso de uso.
  2. Regressão: capacidades gerais e slices de tarefas anteriormente suportadas que a adaptação possa prejudicar.
  3. Segurança e políticas: recusas, data leakage, prompt injection ou constraints específicas do domínio.
  4. Operações: latência, throughput, memória, tamanho do artefacto e custo na configuração de serving pretendida.

Benchmarks automatizados

Utilize lm-evaluation-harness para verificar tarefas standard relevantes juntamente com os seus testes de produto. Este comando requer um checkpoint Hugging Face merged. O path de exemplo é o output merged do companion legacy da Fase 6; não carrega o adapter guardado pela configuração proposta acima. Substitua pelo checkpoint merged que pretende avaliar:

lm_eval --model hf \
    --model_args pretrained=./outputs/unsloth-nemotron-function-calling-merged \
    --tasks hellaswag,arc_easy,mmlu \
    --batch_size 8

LLM-as-judge

Para qualidade subjetiva, um modelo maior pode ajudar no scoring, mas calibre-o com exemplos revistos por humanos e mantenha a identidade do candidato oculta:

judge_prompt = """
Rate this response from 1-5 on:
- Relevance
- Accuracy
- Formatting

Response: {model_output}
Expected: {ground_truth}
"""

Avaliação específica do domínio

Reserve exemplos reais por origem, utilizador, documento ou tempo, para que near-duplicates não atravessem a divisão. Para function calling, valide a trajetória completa: seleção da ferramenta, argumentos, resultado da execução, recuperação e resposta final. Reporte intervalos de confiança ou contagens paired de vitórias/derrotas quando a amostra for pequena e inspecione todas as regressões numa slice crítica.

Fase 6: Deployment e formatos de saída

Escolha o artefacto com base no serving engine e no plano de rollback, não apenas no tamanho do ficheiro. Estes exemplos CLI referem-se ao companion legacy, não ao excerto TRL proposto. O diretório default do adapter é outputs/unsloth-nemotron-function-calling, com os diretórios -merged e -gguf para exports. Cada invocação CLI treina novamente; não é um comando apenas de export. Numa release real, exporte o checkpoint avaliado selecionado, em vez de comparar artefactos provenientes de execuções de treino separadas.

1. LoRA adapter

uv run finetune  # Default adapter directory shown below
  • Tamanho: proporcional aos módulos-alvo, rank, camadas e dtype; frequentemente muito menor do que a base.
  • Melhor para: desenvolvimento, task adapters versionados e engines que suportem LoRA diretamente.
  • Bónus: pode trocar adapters sem voltar a descarregar o modelo base.

2. Modelo merged

uv run finetune --merge  # Creates a standalone full model
  • Tamanho: aproximadamente o checkpoint base completo na precisão de output escolhida.
  • Melhor para: engines ou paths de distribuição que não suportem o adapter separadamente.
  • Compromisso: artefacto maior e rollout mais lento; carregamento de um único modelo mais simples.

3. Formato GGUF

uv run finetune --gguf q4_k_m  # File size and name depend on the exporter
  • Tamanho: depende do modelo; aproximadamente pesos de quatro bits mais metadados para variantes Q4.
  • Melhor para: inferência em CPU, Ollama, llama.cpp e deployment edge.
  • Opções: q4_k_m (mais pequena), q5_k_m (maior fidelidade dos pesos), q8_0 (maior e com maior fidelidade). Meça o impacto na tarefa depois da conversão.

Fase 7: Serving e monitorização

Com vLLM

Este exemplo de serving assume que o adapter proposto passou a avaliação da tarefa e foi treinado com um tool template compatível com Llama 3.1. Guarde esse template revisto exato como serving-chat-template.jinja. Não está estabelecida a compatibilidade do adapter formatado em ChatML legacy com este par de parser/template. Verifique uma trajetória completa de tool use antes de expor o endpoint.

# Serve the base and expose a PEFT adapter as a model name. This parser and
# template pair is for a Llama 3.1-compatible function-calling adapter.
vllm serve nvidia/Llama-3.1-Nemotron-Nano-4B-v1.1 \
    --enable-lora \
    --lora-modules function-calling=./outputs/proposed-nemotron-adapter \
    --enable-auto-tool-choice \
    --tool-call-parser llama3_json \
    --chat-template ./serving-chat-template.jinja \
    --host 0.0.0.0 \
    --port 8000 \
    --max-model-len 4096

Este schema de voo deliberadamente mínimo testa a geração de argumentos através da API compatível com OpenAI. Pede uma book_flight proposta com um destino; não executa uma reserva. Inspecione response.choices[0].message.tool_calls para obter o nome da função e os argumentos JSON. Para esta entrada, o resultado pretendido é book_flight com {"destination": "Tokyo"}. Como a escolha da ferramenta é automática, verifique também se o modelo devolveu sequer um call:

from openai import OpenAI

client = OpenAI(base_url="http://localhost:8000/v1", api_key="dummy")
response = client.chat.completions.create(
    model="function-calling",
    messages=[{"role": "user", "content": "Book a flight to Tokyo"}],
    tools=[
        {
            "type": "function",
            "function": {
                "name": "book_flight",
                "description": "Book a flight to a city.",
                "strict": True,
                "parameters": {
                    "type": "object",
                    "properties": {
                        "destination": {"type": "string"},
                    },
                    "required": ["destination"],
                    "additionalProperties": False,
                },
            },
        }
    ],
    tool_choice="auto",
)

O guia de tool calling do vLLM requer escolha automática da ferramenta e um parser correspondente ao modelo. Forneça um chat template compatível se a configuração do tokenizer não tiver um. Com tool_choice="auto", os argumentos constrained também requerem strict: true em pelo menos uma função e um schema parameters compatível com strict. A definição strict-tool-calling do servidor tem de estar ativada (o default documentado). Sem essa ativação explícita, o vLLM extrai calls de texto em bruto, pelo que os argumentos podem estar malformados ou violar o schema.

Com Ollama (local)

Inspecione o diretório de export -gguf efetivo e substitua o filename emitido por MODEL_FILE.gguf abaixo; as versões do Unsloth podem atribuir nomes diferentes aos ficheiros. Um ficheiro GGUF, por si só, não garante formatação correta de chat/tool no Ollama ou no llama.cpp. Faça corresponder o template treinado e teste o artefacto importado.

# Create Modelfile
echo 'FROM ./outputs/unsloth-nemotron-function-calling-gguf/MODEL_FILE.gguf' > Modelfile

# Import to Ollama
ollama create my-function-model -f Modelfile

# Run
ollama run my-function-model

Com llama.cpp (CPU)

Usando o mesmo export GGUF e a substituição do filename, este comando verifica uma resposta em texto simples. Não testa um tool call completo:

./llama-cli -m ./outputs/unsloth-nemotron-function-calling-gguf/MODEL_FILE.gguf \
    -p "What's the weather in Tokyo?" \
    --ctx-size 4096

Monitorizar o modelo lançado

O ciclo de vida não termina com uma loss de treino saudável. Registe a revisão do modelo base, o tokenizer e o chat template, o hash do adapter, a versão do dataset, a configuração de treino e o relatório de avaliação como uma única unidade de release. Em produção, monitorize o sucesso da tarefa, outputs inválidos, falhas de políticas, latência e drift de inputs pelas mesmas slices utilizadas offline. Mantenha o artefacto anterior carregável e defina um limiar de rollback antes do lançamento.

O seu próximo teste

Antes de uma execução completa, inspecione uma conversa serializada e os seus objetivos de loss e, depois, complete um passo forward/backward com comprimento máximo. Guarde essa configuração juntamente com a divisão do dataset e o relatório da baseline. Se faltar um tool schema, preserve-o na linha de treino. Se uma resposta for truncada, ajuste o comprimento da sequência e a formatação para que a resposta completa sobreviva. Resolva esses problemas antes de adicionar epochs.
