Guia de Ajuste Fino de LLMs: LoRA, QLoRA, DoRA, Unsloth, Axolotl e Implementação

A maioria dos fracassos no ajuste fino deve‑se a decisões erradas. Uma equipa treina antes de comprovar que o uso de prompts, recuperação de informação ou decodificação condicionada não consegue resolver o problema; avalia os resultados na distribuição de dados utilizada para o treino; ou descobre, após o treino, que o modelo resultante é difícil de utilizar em produção.

Este guia trata a adaptação como um experimento com um ponto de saída operacional definido. Começa pela delimitação da decisão a ser tomada e, em seguida, segue um percurso que inclui a análise de dados, a aplicação de técnicas como LoRA ou QLoRA, avaliação específica para a tarefa, exportação do modelo e sua disponibilização.

TL;DR: Realize ajuste fino quando uma linha de base medida indicar que uma atualização de pesos é necessária para alterar o comportamento do modelo. Utilize a recuperação de informação para atualizar factos e a decodificação condicionada para lidar com questões sintáticas. Comece com LoRA quando o modelo base couber confortavelmente nos recursos disponíveis; opte por QLoRA quando a memória limitada de pesos congelados seja o fator restritivo. Mantenha um conjunto de avaliação separado antes do treino, compare os resultados com a linha de base não ajustada e escolha a versão final a ser implementada antes de decidir por um método específico.

Deve mesmo realizar ajuste fino?

Antes de gastar horas em GPUs, decida se o ajuste fino é realmente a ferramenta adequada para o problema que tem em mãos.

Ajuste Fino vs RAG

O ajuste fino pode modificar a forma como um modelo utiliza a linguagem de um domínio específico, mas é um mecanismo insuficiente para atualizar factos que mudam ou que precisam ser citados. A recuperação de informação e o ajuste fino abordam partes diferentes do problema e, frequentemente, devem coexistir no mesmo sistema.

Ajuste Fino vs. Decodificação Restrita

Bibliotecas como xgrammar e outlines restringem a geração a um esquema JSON, expressão regular ou gramática. Dependendo da restrição e do backend, elas compilam um autômato ou gramática e mascaram tokens seguintes inválidos. Não é necessário atualizar pesos.

Isto garante que a saída esteja dentro do idioma suportado — mas não que os valores sejam verdadeiros, completos ou semanticamente adequados. Uma chamada de função sintaticamente válida ainda pode conter um ID de cliente incorreto.

Uma ordem prática:

  1. Comece com prompts e exemplos de few-shot para formatação básica.
  2. Adicione decodificação restrita (xgrammar ou outlines) quando a sintaxe for inconsistente.
  3. Realize ajuste fino apenas quando precisar de alterações de comportamento que um esquema não consiga impor.

Tornar o caso de negócio mensurável

O ajuste fino pode reduzir o número de tokens de prompts recorrentes ou permitir que um modelo menor atinja os objetivos, mas nenhuma dessas economias é automática. Calcule o ponto de equilíbrio com base no seu próprio tráfego e preços:

[ \text{pedidos de equilíbrio} = \frac{\text{custo de treino + avaliação + implementação}} {\text{custo base/pedido} - \text{custo ajustado/pedido}} ]

Se o denominador for pequeno, negativo ou baseado numa suposição de qualidade não comprovada, o projeto ainda não possui viabilidade económica.

[!DICA] A configuração híbrida Uma arquitetura comum consiste num modelo menor adaptado à tarefa, aliado a mecanismos de recuperação para atualizar factos. Trate o modelo maior alimentado por prompts como referência e mantenha o modelo menor apenas se ele cumprir os mesmos critérios de qualidade e segurança específicos da tarefa.

Tipos de ajuste fino

Existem três formas principais de realizar ajuste fino. Elas diferem em termos dos dados necessários e no que são ensinados ao modelo.

1. Treino prévio contínuo (não supervisionado)

Treina-se o modelo base com mais texto bruto, sem rótulos. Ele continua a fazer previsões do próximo token, tal como durante o treino prévio inicial.

Quando utilizá-lo:

  • O domínio possui vocabulário que o modelo base nunca viu (médico, jurídico, bases de código internas).
  • Há grandes volumes de texto do domínio, mas sem pares de entrada/saída rotulados.
  • O modelo base apresenta dificuldades com terminologia específica do domínio.

Exemplo: treinar com milhões de notas clínicas para que o modelo aprenda abreviações médicas, nomes de medicamentos e fluxos de trabalho clínicos.

2. Ajuste fino supervisionado (SFT)

O SFT é realizado com pares de entrada/saída rotulados. Mostra-se ao modelo exatamente qual saída se deseja obter para cada entrada.

Quando utilizá-lo:

  • Existe uma tarefa específica com formato claro de entrada/saída.
  • Há dados rotulados de qualidade, mesmo que em pequenas quantidades.
  • É necessário um comportamento previsível para um formato conhecido de entrada.

Exemplo: treinar com pares de (descrição da consulta SQL, código SQL) para conversão de texto em SQL.

{
    "input": "Get all users who signed up last month",
    "output": "SELECT * FROM users WHERE signup_date >= DATE_SUB(NOW(), INTERVAL 1 MONTH)"
}

3. Ajuste por instruções

O ajuste por instruções é um caso especial do SFT, concebido para fazer com que os modelos sigam uma grande variedade de instruções em linguagem natural. Os dados de treino consistem em pares (instrução, resposta) provenientes de diversas tarefas.

Quando utilizá-lo:

  • Se pretender um assistente multiúso (como o ChatGPT ou o Claude).
  • Quando o modelo precisa lidar com solicitações variadas e abertas.
  • Ao desenvolver uma interface de chat.

Exemplo: treino com milhares de instruções distintas, como “Resuma este artigo”, “Escreva um poema sobre X” ou “Explique Y de forma simples”.

O pré-treino contínuo é um experimento separado e deve ser seguido de testes tanto para avaliar ganhos em determinados domínios como para detetar regressões nas capacidades gerais.

O pipeline de retreino em 7 fases

O retreino é um processo em várias fases, e não uma única instrução. Cada fase apresenta os seus próprios riscos de falha, e ignorar alguma delas costuma resultar num modelo de baixa qualidade posteriormente.

Cada fase constrói-se sobre a anterior:

  1. Preparação de dados — Definir a unidade de avaliação, dividir os dados e, em seguida, limpá-los e formatá-los.
  2. Seleção do modelo — Escolher o modelo base adequado e carregar os seus pesos.
  3. Configuração do treino — Definir o hardware, os hiperparâmetros e a estratégia de otimização.
  4. Retreino — Executar treinos com SFT, DPO ou ORPO.
  5. Avaliação — Medir o desempenho e validar a qualidade.
  6. Implantação — Exportar e disponibilizar o modelo.
  7. Monitorização — Acompanhar o desempenho, realizar manutenção e iterar.

[!AVISO] Os dados são a base O treino reproduz falhas sistemáticas presentes nos exemplos utilizados. Verifique os rótulos, eventuais vazamentos de informação, a cobertura dos dados e o cumprimento das políticas antes de dedicar tempo a ajustes nos otimizadores.

Fase 1: Preparação de dados

A maioria dos projetos de retreino falha nesta fase, e não durante o treino em si. A preparação moderna de dados vai além de simples aplicações de expressões regulares a ficheiros CSV.

O pipeline de dados em 5 fases

Ferramentas como a DataTrove e a Distilabel podem ser úteis em larga escala, mas o pipeline deve ser orientado pela taxonomia de falhas e pelo contrato de dados, e não apenas por uma ferramenta preferida.

1. Ingestão e filtragem

  • Ação: remover respostas de recusa (“Não consigo responder a isso”), dados com codificação UTF-8 incorreta e idiomas não alvo.
  • Ferramentas: Trafilatura para extração de informações, FastText para identificação de idioma.

2. Política de dados sensíveis

  • Ação: determinar quais informações o modelo pode aprender e, em seguida, remover, tokenizar ou excluir campos pessoais e confidenciais conforme necessário.
  • Ferramentas: Microsoft Presidio ou scrubadub.
  • Porquê: um detetor é apenas uma forma de controle; continuam a ser aplicáveis os requisitos relacionados à proveniência, consentimento, retenção, acesso e eliminação de dados.

3. Deduplicação (MinHash LSH)

  • Ação: eliminar duplicatas próximas para que o modelo não as memorize.
  • Ferramentas: O DataTrove é eficaz para processamento em escala de terabytes.

4. Aumentação sintética, se necessário

  • Ação: utilizar um modelo‑professor mais potente (GPT-4o, DeepSeek-V3) para reescrever os dados brutos em pares instrução‑resposta padronizados.
  • Ferramentas: Distilabel.
  • Validação: amostrar as saídas do modelo‑professor, compará‑las com as etiquetas geradas por humanos segundo a mesma rubrica, e manter separados, na avaliação, os dados sintéticos dos escritos por humanos.

5. Formatação

  • Ação: converter os dados para um formato padrão (Alpaca ou ShareGPT).

Exemplos de formato de dados

Formato Alpaca (com seguimento de instruções):

{
    "instruction": "Summarize the following text.",
    "input": "The text to be summarized...",
    "output": "This is the summary."
}

Formato ShareGPT/ChatML (conversacional):

{
    "conversations": [
        { "from": "user", "value": "Hello, who are you?" },
        { "from": "assistant", "value": "I am a helpful AI assistant." }
    ]
}

O que realmente importa

  • Cobertura antes de volume. Incluir exemplos que representem modos de falha distintos, e não repetições dos casos mais fáceis.
  • Limpeza. Remover texto irrelevante, normalizar espaços em branco e manter a formatação consistente.
  • Equilíbrio. Preservar casos raros importantes e reportar o desempenho por cada grupo de dados.
  • Separação. Dividir os dados por fonte, utilizador, documento ou período, caso a divisão aleatória de linhas possa levar à mistura de duplicatas próximas.
  • Proveniência. Registar a fonte, licença ou autorização, histórico de transformações e caminho de eliminação para cada versão do conjunto de dados.

Fase 2: Seleção do modelo e hardware

A escolha do modelo base e o conhecimento das capacidades mínimas da GPU determinam o que realmente pode ser treinado.

Comece com o modelo base mais pequeno que já passe nos testes de baseline indispensáveis. Verifique:

  • as condições de licença e redistribuição para o produto pretendido;
  • o idioma, domínio, tipo de ferramenta e comportamento de segurança antes da adaptação;
  • a compatibilidade do tokenizador e dos modelos de conversação com o conjunto de dados;
  • o contexto máximo e o comportamento de truncamento exigidos pelos exemplos reais;
  • a disponibilidade tanto na estrutura de treino como no motor de serviço alvo.

O ajuste fino é um passo de adaptação, e não uma solução para um modelo base inadequado. Se o modelo não conseguir lidar com funcionalidades que o conjunto de dados não cobre, escolha outro modelo base antes de continuar a treinar por mais épocas.

Defina o tamanho da execução, não o nível de marketing

Não existe uma tabela fixa que relacione “tamanho do modelo → GPU”. A memória máxima varia em função da precisão dos pesos, do otimizador, do número de parâmetros treináveis, do comprimento da sequência, do tamanho dos micro‑lotes, do uso de checkpoints de ativação, da implementação de atenção e dos custos operacionais da estrutura de programação. Comece com uma estimativa de memória e, em seguida, execute um teste rápido de longo comprimento usando exatamente essa configuração.

Pesos basePrecisão no treinoCongelados, geralmente em BF16/FP16Congelados, tipicamente em 4 bits NF4
GradientesTodos os pesos treináveisPesos do adaptadorPesos do adaptador
Estados do otimizadorTodos os pesos treináveisPesos do adaptadorPesos do adaptador

O artigo original sobre QLoRA adaptou um modelo LLaMA de 65B a uma GPU de 48 GB na sua configuração específica. Esse resultado serve como um limite útil, mas não garante que qualquer arquitetura atual de 70B, comprimento de contexto, kernel ou ferramenta de treino se encaixe nesse mesmo dispositivo.

Cálculos de memória

Para um modelo com (P) parâmetros, apenas os pesos exigem aproximadamente (2P) bytes em formato BF16/FP16 ou (0,5P) bytes em quatro bits, antes de considerar metadados de quantização e buffers em tempo de execução. O treino no estilo Adam acrescenta ainda os gradientes, os estados do otimizador e, frequentemente, pesos mestres com maior precisão. A abordagem LoRA evita a maior parte da memória ocupada pelos estados treináveis; o QLoRA reduz adicionalmente o espaço ocupado pelos pesos base congelados. As ativações ainda podem dominar o consumo de memória em sequências longas.

Siga este fluxo de trabalho:

  1. Escolha o maior comprimento de sequência e o tamanho mínimo de lote que precisa suportar.
  2. Estime os pesos e os estados treináveis, reservando espaço para as ativações e os kernels.
  3. Execute um passo de avanço/regresso com o comprimento máximo.
  4. Registre a memória máxima alocada e reservada.
  5. Só então ajuste o tamanho do lote, o número de GPUs, o comprimento da sequência ou o número de níveis de paralelismo.

Fase 3: Métodos de treino (PEFT e LoRA)

Ajuste fino completo vs PEFT

O ajuste fino completo (FFT) atualiza todos os pesos, fazendo com que os gradientes e os estados do otimizador cresçam proporcionalmente ao tamanho total do modelo. O consumo máximo de memória não pode ser estimado apenas a partir do número de parâmetros, mas é significativamente superior à memória necessária para carregar os pesos durante a inferência.

O ajuste fino eficiente em termos de parâmetros (PEFT) treina apenas um subconjunto pequeno de parâmetros, congelando o resto. Isso torna os cálculos muito mais simples.

LoRA: ponto de partida

A LoRA (Adaptação de Baixo Rank) congela uma matriz pré-treinada e representa suas atualizações aprendidas por meio de duas matrizes menores. O artigo original justifica isso com a hipótese de que as atualizações úteis possuem um rank intrínseco baixo.

Para uma matriz congelada (W0 \in \mathbb{R}^{d{out} \times d_{in}}), a LoRA aprende:

  • (A \in \mathbb{R}^{r \times d_{in}})
  • (B \in \mathbb{R}^{d_{out} \times r})

A camada adaptada fica assim:

[ W’ = W_0 + \frac{\alpha}{r}BA ]

O adaptador possui (r(d*{in}+d*{out})) parâmetros treináveis, em vez de (d*{in}d*{out}) para essa matriz. Para uma matriz quadrada com 4.096 elementos e rank 16, isso representa uma redução de 128 vezes — e não 10.000 vezes, como mencionado em alguns artigos para modelos genéricos. A afirmação de 10.000 vezes referia-se especificamente a uma configuração do GPT-3 de 175B, onde apenas algumas matrizes foram adaptadas.

MétodoO que é alteradoQuando escolhê-lo

Quando escolher cada método

  • LoRA: comece por aqui. Rápido, eficiente em termos de memória e amplamente suportado.
  • QLoRA: quando o mesmo experimento com LoRA não é viável devido aos pesos do modelo base estarem congelados.
  • DoRA: após uma comparação direta entre versões LoRA mostrar um ganho significativo.
  • Ajuste fino completo: apenas quando o PEFT for identificado como um gargalo real, e não apenas como uma suposição.

DoRA: LoRA com decomposição de pesos

A DoRA (Weight-Decomposed Low-Rank Adaptation) separa a magnitude de cada vetor de peso da sua direção. Ela aplica uma atualização LoRA à componente direcional, enquanto aprende a magnitude de forma independente.

Como funciona:

Em vez de tratar os pesos como uma única entidade, a DoRA divide os pesos pré-treinados em duas componentes:

  1. Magnitude — um valor treinável para cada vetor de peso.
  2. Direção — um vetor normalizado atualizado por meio de matrizes de baixo rank.

Na notação compacta por colunas:

[ W’ = m \frac{V + BA}{\lVert V + BA \rVert_c} ]

onde:

  • m = magnitude (treinável)
  • (V) = a matriz direcional congelada
  • (BA) = a atualização direcional de baixo rank aprendida
  • (\lVert \cdot \rVert_c) = normalização por colunas

Vantagens dessa estrutura adicional:

  • Mais graus de liberdade em comparação com a LoRA padrão, pois a magnitude pode ser alterada independentemente.
  • Resultados superiores à LoRA em várias configurações, conforme relatado no artigo original.
  • Mais parâmetros e custo computacional; portanto, o ganho deve ser verificado na sua tarefa específica e no fluxo de processamento.

Fusão de adaptadores para aprendizagem multitarefa

Adaptadores separados permitem que um modelo base congelado suporte várias tarefas. É possível direcionar solicitações a um adaptador específico, utilizar vários adaptadores a partir de um único motor quando isso for suportado, ou criar uma versão combinada offline. A fusão pode causar interferências, por isso é necessário avaliar o resultado combinado, em vez de assumir que os adaptadores originais funcionam de forma isolada sem problemas.

Métodos comuns de fusão:

  1. Concatenação — combina os parâmetros dos adaptadores, aumentando o rank efetivo. Rápido e simples.
  2. Combinação linear — soma ponderada dos adaptadores. Permite ajustes personalizados.
  3. SVD — decomposição matricial para fusão. Mais flexível, mas mais lenta.

Exemplo: um adaptador para resumo e outro para tradução, fundidos num único modelo multitarefa.

Fase 4: Ajuste fino e alinhamento de preferências

O SFT aprende a partir de demonstrações. Já a otimização de preferências baseia‑se em comparações do tipo “a resposta escolhida A é superior à resposta rejeitada B”. Utilize‑se apenas quando a preferência entre pares for o rótulo adequado para o erro; na maioria dos casos, a correção factual e o cumprimento das políticas exigem avaliadores mais robustos do que uma preferência global.

RLHF baseado em PPO

A abordagem original consistia num pipeline em três fases:

  1. SFT — aprendizagem da tarefa.
  2. Modelo de recompensa — treino com base nas preferências humanas (escolhidas vs. rejeitadas).
  3. PPO (Proximal Policy Optimization) — aprendizagem por reforço para otimizar a política.

Os custos operacionais derivam das componentes dinâmicas:

  • Implementação e manutenção complexas.
  • Custo elevado — são necessários vários modelos para treino.
  • O amostragem on‑policy e a otimização de recompensas exigem verificações rigorosas de estabilidade e prevenção de manipulação de recompensas.

DPO

O DPO (Direct Preference Optimization) elimina o modelo de recompensa explícito e o ciclo de RL. Continua a otimizar o objetivo do RLHF (maximização de recompensas com restrição de divergência KL), mas faz‑o como um problema de aprendizagem supervisionada reparametrizada, em vez de mediante aprendizagem por reforço:

{
    "prompt": "Explain quantum computing",
    "chosen": "Quantum computing uses qubits...",   # Preferred response
    "rejected": "Well, it's complicated..."        # Non-preferred response
}

As alterações operacionais incluem:

  • Caminho de código mais simples (sem modelo de recompensa separado, sem ciclo de RL).
  • Objetivo offline baseado em pares de preferências, em vez de aprendizagem por reforço on‑policy.
  • Uma política de referência ou probabilidades de registro de referência equivalentes na formulação padrão.

O DPO é mais fácil de prototipar do que um pipeline completo de PPO, mas não garante automaticamente uma melhoria de qualidade. Os resultados dependem da política inicial, da qualidade dos pares, das configurações de perda, dos efeitos de comprimento e do protocolo de avaliação. Compare‑o com um ponto de verificação SFT nas mesmas bases de dados de preferências e tarefas reservadas.

ORPO

O ORPO (Odds-Ratio Preference Optimization) combina a perda de verossimilhança negativa‑logarítmica do SFT com uma penalização de razão de probabilidades nas respostas rejeitadas. Elimina o modelo de referência separado e permite unir a aprendizagem da tarefa e a otimização de preferências numa única execução.

Funcionamento: o ORPO utiliza uma perda combinada que realiza duas funções simultaneamente:

  1. Maximiza a verossimilhança da resposta escolhida (aprendizagem da tarefa).
  2. Penaliza a resposta rejeitada através de um termo de razão de probabilidades (aprendizagem de preferências).

Hiperparâmetros importantes:

from trl import ORPOConfig

config = ORPOConfig(
    learning_rate=8e-6,  # Very low, as recommended by the ORPO paper
    beta=0.1,            # Controls strength of preference penalty
    # ... other params
)
  • Taxa de aprendizagem: o artigo utilizou taxas baixas nos seus experimentos; ajuste‑a de acordo com o seu modelo, lote e dados, em vez de seguir um valor fixo como regra.
  • Beta: controla a influência do termo de preferências em relação ao termo do SFT.

O compromisso envolve:

  • Uma única fase de treino em vez de duas.
  • Ausência de modelo de recompensa.
  • Não há passagem de dados pelo modelo de referência.
  • Execução acoplada: se a aprendizagem da tarefa ou o comportamento de preferências regredirem, não existe um ponto de verificação SFT intermédio do mesmo pipeline para análise.

Escolha conforme os dados e o design de avaliação:

  • Utilize DPO quando já dispõe de um ponto de verificação SFT satisfatório e deseja um experimento de preferências offline mais simples.
  • Teste ORPO quando um objetivo de fase única, sem modelo de referência, se adequa aos seus dados e restrições operacionais.
  • Utilize RLHF baseado em PPO quando o amostragem online com base numa recompensa aprendida explicitamente faz parte dos requisitos e for possível monitorizar a exploração de recompensas.

Nenhum desses métodos é o padrão para todas as tarefas. Mantenha uma linha de base apenas com SFT e reporte tanto métricas de tarefa como métricas de preferências.

Frameworks de ajuste fino

Os frameworks existentes sobrepor-se e evoluem com rapidez. Escolha o mais adequado ao fluxo de execução que precisa de suportar, fixe as versões e garanta que a configuração de treino seja suficientemente portátil para ser reproduzida fora de um notebook.

Unsloth — velocidade e eficiência de memória

O Unsloth integra-se com o Hugging Face trl e transformers, oferecendo kernels otimizados, funcionalidades de checkpointing e caminhos de ajuste fino quantizado para os modelos suportados.

  • Kernels GPU personalizados do Triton para operações de atenção, RoPE e entropia cruzada, que eliminam o overhead do PyTorch.
  • Backpropagation eficiente em termos de memória, que recalcula as ativações durante a passagem reversa em vez de as armazenar na memória.
  • Operações fundidas que combinam vários passos (como layer norm + linear) em uma única chamada à GPU.
  • Quantização de 4 bits integrada diretamente no caminho QLoRA, com desquantização otimizada.

[!IMPORTANTE] A ordem das importações é crucial Siga a ordem de importação apresentada no exemplo do Unsloth para a versão que tiver fixada. O Unsloth aplica patches durante as importações; portanto, importá-lo antes de trl e transformers evita a perda de otimizações ou erros específicos da versão.

# ✅ Correct order
from unsloth import FastLanguageModel  # Must be first!
from trl import SFTTrainer
from transformers import TrainingArguments

# Avoid this order with Unsloth's patched path
from trl import SFTTrainer
from unsloth import FastLanguageModel

Ideal para: treino em única GPU, prototipagem, notebooks do Colab e quem quer controlar o consumo de GPU.

Os valores divulgados de velocidade e uso de memória variam conforme o modelo, comprimento da sequência, tamanho do lote, precisão e hardware. Faça testes próprios medindo tokens por segundo e uso máximo de memória, em vez de considerar números publicados como características intrínsecas do framework.

Ajuste o rank, o valor alfa, a taxa de aprendizagem e os módulos-alvo apenas após terem sido definidos os dados e a versão de referência.

Código principal de treino

from unsloth import FastLanguageModel

# Load model with 4-bit quantization

# Add LoRA adapters
model = FastLanguageModel.get_peft_model(
    model,
    r=16,
    lora_alpha=32,
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj",
                    "gate_proj", "up_proj", "down_proj"],

)

# The data step creates versioned train_dataset and eval_dataset objects.
# Each row has the chat messages and tool schemas expected by current TRL.

# Train with the current TRL configuration surface.
trainer = SFTTrainer(
    model=model,
    processing_class=tokenizer,
    train_dataset=train_dataset,
    eval_dataset=eval_dataset,
    args=SFTConfig(
        output_dir="outputs/nemotron-function-calling",
        max_length=4096,
        packing=True,
        per_device_train_batch_size=2,
        gradient_accumulation_steps=4,

Etapa 5: Avaliação

Congele o contrato de avaliação antes da primeira execução. No mínimo, compare o checkpoint ajustado com a versão de base não ajustada, utilizando o mesmo prompt, definições de decodificação e ambiente da ferramenta. Relate apenas a qualidade global após verificar quais áreas do projeto foram efetivamente melhoradas.

Acompanhe quatro categorias:

  1. Tarefa-alvo: correspondência exata, sucesso na execução, avaliação humana ou outro resultado relacionado com o caso de uso.
  2. Regressão: capacidades gerais e partes das tarefas anteriormente suportadas que possam ser afetadas pela adaptação.
  3. Segurança e políticas: recusas, vazamento de dados, injeção de prompts ou restrições específicas do domínio.
  4. Operações: latência, taxa de processamento, consumo de memória, tamanho dos artefatos e custos na configuração de serviço pretendida.

Avaliação específica do domínio

Reserve exemplos reais por origem, utilizador, documento ou período de tempo, de modo a evitar que duplicatas próximas se misturem entre os conjuntos de teste. No caso de chamadas de função, valide toda a trajetória: seleção da ferramenta, argumentos, resultado da execução, recuperação e resposta final. Relate intervalos de confiança ou contagens de vitórias/derrotas quando a amostra for pequena, e analise cuidadosamente qualquer regressão em áreas críticas.

Etapa 6: Implementação e formatos de saída

Escolha o formato do artefato com base no motor de serviço e no plano de rollback, e não apenas no tamanho do ficheiro:

1. Adaptador LoRA

uv run finetune  # Saves ~100-500MB adapter
  • Tamanho: proporcional aos módulos-alvo, ao rank, às camadas e ao tipo de dado; geralmente muito menor que o modelo base.
  • Melhor para: desenvolvimento, adaptadores de tarefas versionados e motores que suportam diretamente LoRA.
  • Vantagem adicional: é possível trocar adaptadores sem precisar baixar novamente o modelo base.

2. Modelo fundido

uv run finetune --merge  # Creates a standalone full model
  • Tamanho: aproximadamente igual ao tamanho total do checkpoint base, na precisão de saída escolhida.
  • Melhor para: motores ou caminhos de distribuição que não suportam o adaptador separadamente.
  • Desvantagem: artefato maior e implementação mais lenta; carregamento de um único modelo mais simples.

3. Formato GGUF

uv run finetune --gguf q4_k_m  # Creates ~2-4GB quantized model
  • Tamanho: depende do modelo; aproximadamente pesos de quatro bits mais metadados para as variantes Q4.
  • Melhor para: inferência em CPU, Ollama, llama.cpp e implementação em dispositivos periféricos.
  • Opções: q4_k_m (menor), q5_k_m (maior fidelidade dos pesos), q8_0 (maior tamanho e maior fidelidade). É necessário avaliar o impacto da conversão na tarefa.

Monitorizar o modelo lançado

O ciclo de vida não termina com uma taxa de perda de treino aceitável. Deve‑se registar a versão do modelo base, o tokenizador e o modelo de chat, o hash do adaptador, a versão do conjunto de dados, as configurações de treino e o relatório de avaliação como uma única unidade de lançamento. Em produção, monitoriza‑se o sucesso das tarefas, saídas inválidas, falhas de política, latência e deriva de entrada utilizando os mesmos critérios utilizados offline. Mantenha a versão anterior acessível e defina um limiar de rollback antes do lançamento.

Principais conclusões

  1. Faça ajustes finos apenas após confirmar que uma versão inicial não ajustada e uma taxonomia de falhas indicam que a adaptação dos pesos resolve o problema.
  2. A recuperação de informação gere evidências em constante mudança; a decodificação condicionada gere a sintaxe; nenhum desses métodos é substituído pelo SFT.
  3. O LoRA reduz o número de parâmetros treináveis. O QLoRA adiciona ainda a compressão dos pesos base congelados. Não atribua os valores de memória do QLoRA ao LoRA.
  4. A cobertura de dados, a integridade das divisões, a proveniência e o mascaramento de perdas são mais importantes do que simplesmente copiar uma configuração de otimizador na moda.
  5. O DPO, o ORPO e o PPO‑based RLHF são designs experimentais distintos, e não representam uma escala de qualidade com um padrão universal.
  6. Avalie o comportamento alvo, regressões, segurança e operações com base no mesmo modelo base.
  7. Escolha entre adaptador, formato fundido ou saída GGUF de acordo com as exigências de serviço e rollback antes de iniciar o treino.
