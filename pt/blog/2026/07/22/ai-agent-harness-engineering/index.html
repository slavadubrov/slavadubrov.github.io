Harness Engineering para AI Agents: Conceber Loops de Controlo

Harness engineering é a conceção do código de controlo em torno do reasoning loop de um agent. Para engenheiros que constroem ou reveem coding agents, este artigo explica como verificar a conclusão, repetir operações em segurança, preservar o progresso entre sessões e comparar controlos opcionais com uma baseline fixa.

Um agent pode terminar o seu turno enquanto o trabalho continua incompleto. Para um coding agent, a evidência útil é o artefacto alterado e os resultados dos testes exigidos. Uma mensagem final a dizer «concluído» não comprova nenhum dos dois.

O harness fornece contexto, valida e autoriza tool calls, regista resultados e decide se a evidência é suficiente para aceitar o trabalho. O runtime mantém a execução e o estado ativos por baixo dele. Os exemplos de store abaixo são fictícios; o companion lab é uma simulação determinística, não uma medição de um agent em execução.

Em resumo: Não aceite uma coding task porque o model diz que está concluída. Exija o artefacto alterado e os resultados dos testes exigidos. Adicione um retry, handoff ou evaluator apenas quando uma comparação controlada demonstrar que melhora o resultado.

A verificação de aceitação mais simples é fácil de escrever para um pequeno research agent como o que esta série tem vindo a construir — um agent LangGraph que obtém dados de mercado e escreve um relatório de analista. Um hook fora do model valida o relatório contra um schema e verifica se este contém efetivamente stock tickers; um relatório malformado mantém a execução aberta. São doze linhas de código normal, e o model não pode declarar que o seu próprio output está bem formado. O repo utiliza uma verificação mais flexível: um evaluator em fresh context vota e, depois, um humano revê o resultado. A Part 4 esboça a versão determinística.

O que esse exemplo não consegue mostrar é a parte interessante: o que acontece quando a evidência é ambígua, quando um retry pode cobrar duas vezes a alguém ou quando o trabalho ultrapassa a sessão que o iniciou. Estes casos exigem uma task com uma fronteira de sucesso/insucesso mais nítida do que a de um relatório de investigação. O research agent mantém-se como exemplo de acceptance check; um pequeno store repository fictício junta-se-lhe nos casos de retry e handoff. A coding task consiste em baixar de $100 para $75 o limiar para um desconto automático de 10% em src/checkout.py. O repository tem duas verificações obrigatórias:

  • pytest tests/test_checkout.py verifica o cálculo do desconto.
  • pnpm playwright test tests/checkout_discount.spec.ts adiciona um item de $80 numa test store local e verifica que a página de checkout apresenta um desconto de $8.

O exemplo é um fixture pedagógico, não uma aplicação ou benchmark real. Todas as tentativas começam no mesmo commit e com os mesmos test data seeded. O harness só pode aceitar a alteração quando ambos os comandos passam e um acceptance record durável associa ambos os resultados a um candidato committed limpo ou a um digest do snapshot completo testado, incluindo os ficheiros untracked relevantes.

O diagrama acompanha a alteração do desconto, desde a proposta até à evidência. O harness fornece a task e os ficheiros, verifica os argumentos e as permissões propostos para edit_file e envia a call aceite. Depois de o runtime aplicar a edição, o harness executa os unit tests e browser acceptance tests indicados. Um comando que falhe regressa ao model como evidência para outro turno; dois comandos com sucesso tornam a alteração elegível para aceitação.

O que pertence ao harness

O Codex loop walkthrough da OpenAI descreve o ciclo básico. O harness reúne um prompt, pede ao model a ação seguinte, envia uma tool call aceite para o runtime e acrescenta o resultado. Depois pergunta novamente. Isto repete-se até o harness aceitar o resultado ou devolver o controlo ao utilizador.

As implementações podem combinar várias responsabilidades num único processo. Ainda assim, as fronteiras de falha são diferentes:

TermoFunçãoExemplo num coding agent
ModelPropõe texto, uma tool call ou uma resposta finalSugere uma edição a src/checkout.py
Reasoning loopEscolhe o passo seguinte a partir do contexto disponívelInspecionar, editar, testar, voltar a inspecionar
HarnessFornece contexto, valida propostas, autoriza-as, envia calls aceites, regista resultados e verifica a conclusãoPermite edições em src/ e exige ambos os testes indicados
RuntimeExecuta calls aceites e mantém o estado ativo fora do processo workerSession log, sandbox, checkpoint store, trace backend

A linha do runtime abrange quatro elementos: session, sandbox, checkpoint e trace. Os quatro armazenam estado ou confinam a execução. O model propõe a ação e o reasoning loop escolhe o passo seguinte. O harness decide se uma call proposta pode ser executada e se a evidência é suficiente para terminar, razão pela qual merece um artigo próprio. A Part 5 conta o harness, juntamente com esses quatro elementos, como um dos cinco primitives que é necessário posicionar antes do deployment; este artigo volta a separá-lo.

Quando surge uma falha, diagnostique a fronteira que deve responder. Um plano fraco pode exigir melhores instruções ou melhor reasoning do model. Se edit_file visar um path fora de src/, o harness deve rejeitá-lo. Um processo sandbox que morra antes de a edição ser executada pertence ao runtime, que deve reiniciar o worker ou reportar o crash.

O diagrama mapeia as responsabilidades ao longo da série. As suas linhas agrupam o model, o harness e o runtime; não mostram a ordem de execução. O contexto e as tools informam a proposta, as verificações de permissões precedem a execução e as verificações de conclusão utilizam a evidência resultante.

As Parts 3 e 4 partilham o passo 3, e essa sobreposição é precisamente o argumento para as tratar como um único programa. A mesma camada de código do harness que rejeita um argumento malformado rejeita também uma call que é permitida, mas ainda não foi aprovada. Se a validação e a autorização forem executadas em serviços separados, preserve os argumentos validados através dessa fronteira, para que a decisão de autorização se aplique à call que será executada.

A separação continua a ser importante para debugging: uma edição no ficheiro errado é uma regra de path da Part 4, não um problema de retrieval da Part 2. Uma secção perto do final deste artigo transforma isto numa routing table.

O próprio harness-engineering case study da OpenAI descreve uma instância de aplicação bootable para cada worktree. A equipa também ligou browser automation ao ambiente do agent e expôs logs, métricas e traces.

Uma task como «nenhum span nestas quatro jornadas críticas do utilizador pode exceder dois segundos» tornou-se testável porque o agent conseguia executar a aplicação e consultar os mesmos sinais que um engenheiro inspecionaria. O case study é específico do produto. O que é transferível é a condição por trás do resultado: a aplicação e os seus sinais de performance tinham de estar disponíveis dentro do ambiente do agent.

Lopopolo, o autor desse case study, mantém um field guide for harness engineering. Este identifica as duas alavancas usadas neste artigo: manter o model e o coding agent fixos como uma black box e conceber o contexto e as tools em torno deles. O seu enquadramento também explica por que razão grande parte do harness acaba por ser código normal.

A fasquia de qualidade, os procedimentos, o histórico de exceções e as relações de autoridade de uma organização estão fora do que um model geral pode conhecer. O harness expõe-nos como instruções do repository, regras de permissões e acceptance checks. Cada execução aceite pode devolver as suas lições a esses artefactos, em vez de depender da sessão seguinte para as redescobrir.

Acompanhar a alteração do desconto desde a proposta até à aceitação

Byte diz

Continuo a precisar dos dois resultados dos testes para esta alteração de desconto, mesmo que o model diga que está concluída.

Para a discount task definida acima, o model propõe alterar calculate_discount em src/checkout.py. Há várias coisas que acontecem antes de essa edição contar como progresso:

  1. O context builder fornece a task, as instruções do repository, os ficheiros relevantes, os resultados anteriores de tools e o plano atual.
  2. O model propõe uma call edit_file com um path e texto de substituição.
  3. A tool boundary (o código do harness entre a proposta e a execução) valida os argumentos, verifica o path contra o âmbito permitido e pede aprovação se a operação dela necessitar.
  4. O runtime aplica a edição no sandbox e devolve um resultado estruturado.
  5. O harness executa pytest tests/test_checkout.py, seguido de pnpm playwright test tests/checkout_discount.spec.ts, e lê ambos os exit codes. O browser test verifica o desconto visível de $8 no carrinho seeded de $80.
  6. O harness decide o significado dos resultados. Uma verificação falhada torna-se novo contexto para o turno seguinte do model e uma execução bem-sucedida torna a task candidata a conclusão.
  7. Um resultado bem-sucedido só se torna evidência de conclusão depois de o harness registar de forma durável o comando, o exit code, o snapshot testado, o grader e as versões do ambiente; um trace pode ligar-se a esse registo.

Depois do passo 2, nenhum ficheiro foi alterado. O harness pode rejeitar ../../secrets.env, exigir aprovação para um comando destrutivo ou parar uma execução que tenha esgotado o seu budget. Esse é o último momento barato que terá. Depois de os testes serem executados, o harness lê os seus exit codes autonomamente. O model não pode marcar a sua própria edição como bem-sucedida.

O acceptance record deve identificar o snapshot testado, ambos os comandos e resultados, bem como as versões do grader e do ambiente; os traces podem ligar-se a esse registo. Mantenha os testes obrigatórios fora do âmbito de escrita do agent ou aprove independentemente as alterações antes da avaliação. Qualquer edição posterior de um ficheiro invalida o resultado. Estas verificações implementam os princípios de ambiente estável e grader resistente a bypass presentes na guidance de avaliação da Anthropic. Uma mensagem final done sem esses registos não prova que esta alteração passou as verificações exigidas.

Decidir onde cada regra é aplicada

O requisito de que tests/checkout_discount.spec.ts passe pertence a código determinístico, não ao prompt. O harness envia o comando Playwright para o runtime, lê o seu exit code e recusa terminar a execução enquanto este falhar. Um prompt pode lembrar o model de executar o teste. Não pode impedir o model de declarar sucesso sem evidência.

Outras regras encaixam noutras camadas:

Os tool contracts separam a proposta da permissão

A discount task só precisa de edições de ficheiros e comandos de testes. Uma API com alteração de estado tem um failure mode diferente, por isso mudamos os exemplos nesta secção. Suponha que o agent pode chamar create_test_order contra um order service de staging ao preparar test data. Esta tool não é uma das acceptance checks da discount task. É útil aqui porque um timeout pode ocultar se o serviço criou uma order.

A tool boundary precisa de mais do que uma descrição em linguagem natural. Precisa de um tool contract explícito. A Part 3 defendeu um do lado do model: ações claras, feedback compacto e erros recuperáveis. O harness precisa do mesmo contract por uma razão diferente. Tem de decidir, sem perguntar ao model, se uma call pode ser executada e se uma call falhada pode ser repetida. Para create_test_order, isso significa um contract com:

  • argumentos validados, para que input malformado seja rejeitado antes da execução
  • um resultado estruturado, como { "order_id": "123", "created": true }, para que as verificações posteriores não tenham de analisar texto livre
  • uma categoria de efeito que regista se a call apenas obtém informação ou altera um ficheiro, um registo de base de dados ou um serviço externo. Regista também se é seguro repetir a call. Esta etiqueta indica ao harness se um retry automático pode duplicar trabalho. O harness pode repetir get_order_status quando o serviço define essa lookup como read-only. Não deve repetir cegamente create_test_order, porque a primeira call pode já ter criado a order
  • uma política de timeout e retry, para que uma resposta perdida não desencadeie uma sequência ilimitada de calls
  • uma regra de permissões que indique que aprovação é necessária. A leitura do estado da order pode ser executada automaticamente, enquanto a criação de uma order pode exigir confirmação

A descrição em linguagem natural é o texto apresentado ao model. Poderia dizer: «Create a test order for checkout verification.» Essa frase ajuda o model a decidir quando propor create_test_order. Não autoriza a call. Neste exemplo, o cliente Model Context Protocol (MCP) do harness valida os argumentos, aplica as suas próprias regras e verifica a confiança no server, os requisitos de aprovação e a segurança do retry antes de enviar qualquer coisa. Isto combina as regras de permissões e as verificações pre-tool discutidas na Part 4 com uma pergunta adicional: se uma call que já falhou pode ser enviada novamente.

Um MCP server publica descrições de tools e anotações comportamentais opcionais para o cliente. Um server defeituoso ou malicioso poderia descrever uma tool com alteração de estado como inofensiva. Um cliente que aceitasse automaticamente essa afirmação poderia executar ou repetir create_test_order sem aprovação e criar uma duplicada. A especificação MCP exige, por isso, que os clientes tratem as tool annotations como não fidedignas, salvo se o próprio server for trusted.

A especificação não prescreve uma única configuração universal de trust, pelo que é necessária uma política de trust explícita para o deployment; um server não pode tornar fidedignas as suas próprias annotations. Essa política decide que metadata pode influenciar decisões de permissões ou retry e que annotations permanecem apenas consultivas.

Repetir uma call com alteração de estado exige proteção contra replay

Part 5 exige uma identidade de operação durável para side effects que podem ser duplicados num retry. O harness é que decide quando essa key tem de suportar esse peso. create_test_order cria a order, mas a resposta HTTP perde-se. O harness vê um timeout e não consegue saber se o server concluiu o pedido. Repetir a call pode criar uma segunda order.

Persista um operation ID pertencente à aplicação antes do dispatch e associe-o aos argumentos aprovados. Reutilize-o ao recuperar a mesma order pretendida, mesmo que o model gere um novo tool-call ID; mantenha os IDs do model separadamente para correlation. Reconcilie payloads alterados ou janelas de deduplicação do provider expiradas, em vez de reenviar cegamente. O contract da Stripe, por exemplo, permite eliminar keys depois de pelo menos 24 horas.

Uma lookup de estado pode ser repetida quando o serviço a define como read-only. Uma call de criação precisa da key: o cliente anexa um identificador de pedido único e o serviço devolve o primeiro resultado, em vez de criar outra order quando volta a ver esse identificador. Sem esta proteção, o harness deve verificar se a order existe ou pedir uma decisão humana antes de outra tentativa. A AWS documenta este padrão na sua guidance sobre APIs idempotentes.

A aceitação precisa de evidência independente

Uma resposta bem-sucedida de create_test_order estabelece apenas que a tool devolveu dados. Não prova que uma coding task passou os seus testes. Se um browser test posterior depender da order staged, o harness tem de validar o schema da resposta e executar ainda esse teste antes de aceitar a alteração de código.

Alguns critérios não podem ser reduzidos a um exit code. Numa tarefa de visual design separada, um evaluator em fresh context pode comparar uma página renderizada ou um diagrama com uma rubric escrita — «fresh-context» significa uma segunda sessão do model que começa sem histórico da execução e lê os artefactos produzidos, em vez do transcript. Compare esse evaluator com revisões humanas antes de permitir que o seu resultado decida se a task está concluída.

Uma migração de payment adapter precisa de um handoff

Mudemos novamente de task, mas mantenhamo-nos no store repository fictício. O agent tem agora de migrar o checkout do payment adapter v1 para o v2. O trabalho abrange o checkout handler, o payment client, a configuração e os testes, pelo que pode ultrapassar uma sessão de model — um período contínuo de contexto do model, terminado por um restart ou por um fresh start deliberado, em vez de ser transportado para a frente.

Antes de a primeira sessão atingir o seu limite de contexto, modificou vários ficheiros, iniciou um payment sandbox local e deixou tests/payment_migration.spec.ts a falhar. Esse browser acceptance test conclui um pagamento através do adapter v2 e verifica o provider ID registado. Um resumo da conversa pode orientar a sessão seguinte do model, mas não pode reiniciar o sandbox nem provar que ficheiros estão atualmente modificados.

A sessão seguinte tem de recuperar três coisas:

O que tem de ser recuperadoO que incluiComo pode falhar
Histórico da conversaMensagens, tool calls e resultados devolvidosDetalhes antigos ocupam o espaço da task atual
Ambiente de trabalhoFicheiros, payment sandbox e estado do browser testO transcript diz que um serviço está ativo depois de este ter terminado
Progresso da taskPlano, verificações concluídas, aprovação pendente, próximo passoA sessão seguinte repete trabalho concluído

A compaction substitui mensagens antigas por um resumo mais curto, para que a sessão atual possa continuar. Um progress handoff regista aquilo de que a sessão seguinte precisa: a branch atual, os ficheiros alterados, o último comando de teste e o respetivo output, bem como o próximo passo por resolver.

Um ficheiro de handoff é document memory para a sessão seguinte do model. Um checkpoint pode já preservar o plano, os passos concluídos, os resultados e o trabalho restante. Adicione um handoff quando esses detalhes estiverem ausentes ou inutilizáveis no contexto seguinte e verifique os ficheiros e os serviços em execução contra o ambiente live.

Se a conversa antiga contiver pressupostos desatualizados, o harness pode iniciar uma sessão nova do model com esse handoff e o workspace atual. Substituir um worker que crashou e restaurar os seus processos é um trabalho separado de runtime recovery.

Uma pequena edição de documentação pode não precisar de nenhum destes mecanismos. A payment migration precisa de um handoff se o estado guardado não transportar progresso de task utilizável, porque a sessão seguinte do model tem de reconstruir tanto o workspace como o estado da task.

As experiências da Anthropic com long-running coding agents utilizaram o histórico do git e um progress file entre sessões. O relatório posterior da Anthropic sobre harness design separa a compaction de um fresh-context handoff e indica que os handoffs acrescentam orchestration, utilização de tokens e wall time, sem publicar valores que atribuam qualquer parte desse overhead ao handoff em si.

Usar traces para distinguir três falhas

As três linhas seguintes são trace sketches ilustrativos, não execuções medidas nem output do companion lab. Cada linha mostra uma falha diferente e, por isso, uma resposta diferente do harness.

Uma falha com aparência transitória não torna todas as calls seguras para retry. A primeira linha é uma lookup read-only. A segunda é um pedido com alteração de estado, pelo que a idempotency key e o estado no server determinam se é permitida outra tentativa de criação. A terceira nem sequer é uma falha de tool; o harness ainda não recolheu a evidência necessária para aceitar a alteração do desconto.

Um chat transcript regista o que o model viu. Não consegue provar se o order service fez commit de um pedido antes de a resposta desaparecer. Um trace só pode fornecer essa evidência se incluir o resultado relevante do server ou uma lookup de estado; um timeout apenas do lado do cliente deixa o resultado por resolver. Os operation records e acceptance records duráveis têm de associar a call do cliente, a decisão de aprovação, a identidade da operação, o resultado do server ou a lookup de estado, o snapshot testado e o resultado do acceptance test. Os traces podem expor essas ligações para debugging sem se tornarem o recovery ledger. Esses campos indicam ao harness em qual dos três caminhos se encontra.

Para assistência opcional, como auxiliares de planeamento, resumos e evaluators adicionais, identifique a falha e meça se o componente compensa o seu custo. Os requisitos de autorização, isolamento, privacidade e acceptance checks obrigatórios mantêm-se em vigor mesmo quando as tasks normais passam sem eles. Teste essas restrições com casos adversariais e invariants explícitos; um pequeno benchmark de sucesso não pode justificar a sua remoção.

Transformar essas falhas repetidas numa regression suite versionada é um trabalho próprio. Escrevi sobre isso separadamente em AI Agent Evaluation in Production.

Medir uma alteração de cada vez

Uma ablation mede se um componente do harness provoca o efeito esperado, alterando ou removendo esse componente enquanto o resto da experiência permanece fixo. Por exemplo: o editor linting ajuda este model neste task suite?

Utilize o protocolo seguinte:

  1. Fixe a versão do model, as task instances, o ambiente, o grader e os prompts que estejam fora do componente em teste.
  2. Dê às duas variantes o mesmo budget total de tokens, tempo e dinheiro.
  3. Escolha o número de trials ou a stopping rule antes de executar a comparação.
  4. Execute as mesmas task instances nas duas variantes. Como os outputs do model variam, repita cada task várias vezes.
  5. Reporte a média juntamente com a dispersão ou o intervalo de confiança.
  6. Conte todos os trials iniciados, incluindo timeouts, policy stops, crashes do harness e falhas do evaluator.

A success rate, por si só, pode ocultar um componente dispendioso. No mínimo, acompanhe tasks quebradas aceites como concluídas, custo e wall time por task concluída, tool errors, orders duplicadas, minutos de revisão e overrides manuais de permissões. Escolha a métrica que representa o custo real do seu produto. Um aumento de dois pontos nas tasks concluídas é uma má troca se duplicar a sua fila de revisão.

Para a fictional payment migration, uma paired experiment tornaria mensurável o progress handoff opcional. Cada par control/treatment começa no mesmo commit do repository e com o mesmo checkpoint seeded, utilizando o mesmo model, task, grader e budget total. O handoff é o único switch. A métrica principal conta as tool actions duplicadas depois do resume: uma action é duplicada quando a sua operação e o seu artefacto correspondem a um passo que a sessão anterior já tinha concluído.

O artigo SWE-agent fixa o GPT-4 Turbo no split de 300 tasks do SWE-bench Lite e reporta 18,0% de resolução com a sua interface completa, em comparação com 11,0% para um agent apenas com shell ao qual foi dada uma demonstração trabalhada e 7,3% para o mesmo agent sem essa demonstração. A diferença principal de 10,7 pontos do artigo é medida face à baseline de 7,3%; a Part 3 trabalha os mesmos três números do ponto de vista do design da interface. Interface SWE-agent completa (referência, inalterada)18,0%
Editor sem linting15,0%
Ficheiro completo em vez de um viewer de 100 linhas12,7%
Histórico de observação completo em vez dos últimos cinco15,0%

Estes números pertencem a esse model, benchmark e limite de $4 por task. As três linhas abaixo da referência são os testes úteis de uma feature: cada uma alterou uma feature da interface, mantendo fixos o model e a configuração de avaliação.

A LangChain publicou uma comparação com model fixo mais abrangente para deepagents-cli. Reporta um aumento no Terminal-Bench 2.0 de 52,8% para 66,5% com gpt-5.2-codex fixo, enquanto a equipa alterou o system prompt, as tools e o middleware. O post combina várias alterações e omite um intervalo de confiança, uma comparação com budget total fixo e uma tabela de ablation por alteração. Esse resultado não consegue identificar qual das alterações ajudou. Os nomes dos models nesta secção são os que cada estudo fixou no momento da sua execução; o que é transferível é o protocolo, não a lista de models.

Uma comparação mais recente mostra por que razão a configuração da API pertence à baseline congelada. No seu relatório de 29 de julho de 2026 sobre ARC-AGI-3, a OpenAI reporta que o score público do GPT-5.6 Sol subiu de 13,3% para 38,3% quando o seu harness reteve o reasoning e utilizou compaction, em vez de descartar o reasoning e truncar o histórico. A métrica é Relative Human Action Efficiency, não a fração de tasks resolvidas. Trata-se de uma comparação agrupada, reportada pelo vendor; não isola as duas configurações nem estabelece um effect size de produção. Numa upgrade, registe a API, a retenção de reasoning, a política de compaction e os budgets juntamente com o model ID. Caso contrário, uma aparente regressão do model pode ser uma capability em falta no adapter.

Inclua a intervenção do provider na failure suite. Um misalignment_policy_violation tem de chegar a um caminho de stop-and-review mesmo depois de streamed output; não é um caso de retry transitório. A Part 4 aborda o seu âmbito dependente da API. Teste se o harness interrompe o dispatch e regista os efeitos já concluídos.

O relatório da Anthropic sobre long-running applications é um case study qualitativo e específico do produto, não um benchmark controlado. A aplicação é a RetroForge, um criador de jogos retro 2D; no Sprint 3, o evaluator do harness verificou 27 critérios relativos ao seu level editor. O trabalho começou em models Opus anteriores e, quando o Opus 4.6 foi lançado, a equipa removeu componentes do harness um de cada vez para ver quais tinham sido tornados redundantes pelo model mais recente. O relatório indica que as calls do evaluator se tornaram overhead em tasks que o Opus 4.6 conseguia concluir de forma fiável sozinho, mas continuavam a ajudar perto do limite do model. O exemplo é uma razão para revalidar scaffolding antigo quando o model muda; não estima um effect size geral.

Manter o harness editável depois de este justificar o seu lugar

Ablation mantém o harness pequeno, mas o seu código pode continuar a existir depois de o model para o qual foi afinado ter mudado. Um pedido como «mascarar secrets em todos os caminhos de captura» especifica um comportamento, não um ficheiro. Num harness de produção, esse comportamento pode atravessar fases de execução e estado partilhado. Antes de o poder alterar em segurança, tem de encontrar todos os pontos de implementação — e o coding agent a quem delega a tarefa também.

Um preprint de 2026 de Wang et al. introduz o Harness Handbook, uma abordagem em fase de investigação para encontrar esse código. O artigo chama a esta pesquisa behavior localization. O handbook constrói um mapa centrado no comportamento a partir da codebase do harness. A análise estática, que não precisa de calls ao model, extrai um grafo do programa e, depois, um LLM organiza as suas unidades em fases de execução.

O maintainer ou coding agent começa com uma visão geral do sistema, abre a fase de execução relevante e desce até entradas fundamentadas no source para uma função ou ficheiro. Um state register regista onde o estado partilhado é escrito e lido entre fases. Esta hierarquia mantém a visão geral pequena, preservando simultaneamente um caminho até ao source.

A freshness é uma regra separada. O mapa é um auxílio de navegação; o source live estabelece o comportamento. Cada locator tem de ser resolvido contra o repository live. O handbook congela entradas stale em vez de adivinhar e cada diff não vazio ressincroniza as entradas afetadas.

O diagrama comprime o modification loop: um pedido centrado apenas no comportamento desce pelos níveis do handbook, cada locator candidato é verificado contra o repository live antes de o plano ser escrito e cada diff aplicado ressincroniza o mapa.

A avaliação do Handbook compara arms emparelhados em 30 pedidos por repository. Não estabelece budgets totais iguais, trials estocásticos repetidos ou estimativas de incerteza e as comparações reportadas excluem outputs em falta e erros do planner. Ilustra, portanto, apenas parte do protocolo acima, não a sua totalidade. Abrange dois harnesses open source: Terminus-2 (seis ficheiros Python) e o Codex monorepo (2.267 ficheiros Rust). Em cada um, um planner read-only alimentado pelo DeepSeek-V4-Pro explorou diretamente o repository ou foi encaminhado através do handbook. Os pedidos, o repository, as permissões das tools e o decoding eram idênticos nos dois arms. Três judges (GPT-5.5, Opus 4.8, DeepSeek-V4-Pro) atribuíram uma pontuação a cada plano de edição em localization, scope control e reasoning — note-se que um dos judges é o mesmo model que produziu os planos. Uma vitória significa que o quality score de um arm, numa escala de 0 a 100, excedeu o do outro em pelo menos três pontos; caso contrário, a comparação judge–request foi um empate. A taxa reportada é o número de vitórias dividido pelo número de comparações judge–request válidas:

HarnessTaxa de vitórias da baselineTaxa de vitórias com handbookTokens do planner
Terminus-2 (6 ficheiros)26,7%45,6%−8,6%
Codex monorepo (2.267 ficheiros)28,3%38,3%−12,7%

O planner assistido pelo handbook venceu mais vezes e utilizou menos tokens do planner em ambos os repositories. As condições mantêm-se associadas ao resultado: três LLM judges atribuíram pontuações a planos de edição produzidos por um único planner model em dois harnesses. O estudo avaliou planos, não diffs executados nem taxas de defeitos em produção.

Experimentar o método no companion lab

O projeto harness-demo no commit 517353f3 é um pequeno exercício determinístico com 12 tasks sintéticas genéricas que abrangem alterações de código como fix-parser-edge-case, split-large-module e wire-browser-test. Não implementa o fictional store repository.

Cada task fixture declara uma dificuldade e quatro condições booleanas: uma tool flaky, progresso perdido, uma lacuna de implementação não detetada e conclusão ambígua. O simulator deriva uma quinta condição para tasks difíceis que também precisam de um progress file: sem context_reset, a compaction preserva pressupostos stale. Um grader determinístico marca uma task como passed apenas quando a configuração selecionada trata todas as condições aplicáveis. Não é executado nenhum model nem serviço externo.

Os comandos respondem a perguntas diferentes:

  • make check executa Ruff e sete unit tests, incluindo o validator que rejeita qualquer par de ablation que altere mais do que um componente.
  • make run imprime uma teaching matrix cumulativa e, depois, cinco comparações válidas leave-one-component-out.
  • make failures indica a condição não tratada para cada task falhada. O harness completo deve terminar com all synthetic tasks pass.

Instale primeiro Git, make e uv. Clone o lab e selecione a revisão pinned; depois execute os seus comandos a partir da raiz do repository:

git clone https://github.com/slavadubrov/harness-demo.git
cd harness-demo
git checkout 517353f3a47541d66099983170fe90812b6ef23b
make check
make run
make failures

A secção causal de make run tem o seguinte aspeto:

component                 control  treatment  delta
retry_policy              8/12     12/12       +4
progress_handoff          7/12     12/12       +5
evaluator                 8/12     12/12       +4
fail_closed_acceptance    7/12     12/12       +5
context_reset            10/12     12/12       +2

Para cada linha, o control é a configuração completa com um componente removido; o treatment restaura apenas esse componente. A matriz cumulativa anterior é útil para orientação, mas algumas das suas linhas adjacentes adicionam vários componentes ao mesmo tempo e, por isso, não conseguem identificar uma causa.

O lab valida cada par declarado antes de o executar. Os seus regression tests incluem também um par intencionalmente inválido que altera simultaneamente a política de retry e o evaluator; o validator rejeita-o.

O lab compara os cinco campos de componentes quando valida um par. Este excerto executável mostra a mesma proteção num par válido de progress handoff:

from dataclasses import dataclass, fields

@dataclass(frozen=True)
class Config:
    progress_handoff: bool = False
    evaluator: bool = False
    retry_policy: bool = False
    fail_closed_acceptance: bool = False
    context_reset: bool = False

def changed_components(control: Config, treatment: Config) -> tuple[str, ...]:
    return tuple(
        field.name
        for field in fields(control)
        if getattr(control, field.name) != getattr(treatment, field.name)
    )

control = Config(progress_handoff=False, evaluator=True, retry_policy=True)
treatment = Config(progress_handoff=True, evaluator=True, retry_policy=True)
assert changed_components(control, treatment) == ("progress_handoff",)

Que camada abrir quando uma execução corre mal

A série avançou do reasoning loop para o exterior. Comece pela primeira falha que observar e, depois, investigue o componente responsável por esse trabalho. Uma execução pode envolver mais do que um componente:

O que a execução fezOnde vive a correçãoParte
Escolheu um passo seguinte fraco, apesar de ter a informação certa à frenteReasoning loop ou model1
Repetiu trabalho ou perdeu uma decisão tomada uma hora antesContext assembly e handoffs2
Não conseguiu expressar a ação necessária ou interpretou mal um resultado devolvidoTool contract3
Fez algo que nunca deveria ter podido fazerPermission rules4
Perdeu tudo quando um worker morreu a meio de uma callSession, checkpoint, sandbox5
Declarou sucesso num trabalho que não estava concluídoAcceptance checks e traces6

Quatro linhas apontam para código do harness, enquanto a linha 5 aponta para o runtime. As instruções podem influenciar o comportamento, mas não substituem uma verificação de permissões, um checkpoint durável ou um acceptance test.

Começar com um loop e uma acceptance check

Eu começaria um coding-agent harness com um model capaz, instruções do repository, algumas tools restritas, um sandbox e um acceptance test explícito. Registaria tool calls, resultados, custos e esse teste final num único trace, para que as primeiras falhas úteis fossem visíveis sem ter de as reconstruir a partir de logs do terminal e chat transcripts. Esta é uma baseline proposta, não evidência de um sistema deployed.

A partir daí, adicionaria apenas aquilo que um trace justificasse. Registaria quem mantém cada componente, quantos tokens ou segundos acrescenta e que regression test justificaria removê-lo depois de uma model upgrade.

Seis meses mais tarde, alguém que veja progress_handoff=True deverá conseguir encontrar os traces falhados que o justificaram e os regression cases que ainda o mantêm. Os traces explicam por que razão o componente existe; um behavior map atual explica onde atuar.

Se chegou aqui através de uma pesquisa, os cinco artigos anteriores construíram um sistema em torno de um reasoning loop:

  1. O loop escolhe o passo seguinte.
  2. A memory fornece contexto e um checkpoint store real em Postgres preserva-o.
  3. Os tool contracts definem as ações e os formatos dos resultados que as verificações posteriores conseguem ler.
  4. A security acrescenta o deny hook e o stop-hook validator. Ambos continuam a ser sketches no exemplo, mas assinalam os pontos de controlo.
  5. O runtime mantém o processo ativo entre sessões e falhas.

A série também adicionou uma superfície de server MCP opcional e um evaluator node que verifica o draft report antes de este chegar a um humano. Encaminhar o worker através de um proxy que detenha as credenciais continua a ser uma extensão proposta. Estas são peças normais de código em torno de uma call ao model. O router é código do harness pela mesma razão: escolhe o padrão de reasoning antes de o reasoning loop começar.

Para o próximo componente opcional de assistência, mantenha em conjunto o trace falhado, a regra de aceitação e a comparação com esse componente desativado. Deixe-o de fora se não conseguir identificar o seu benefício. As restrições de segurança e aceitação obrigatórias não dependem dessa comparação.
