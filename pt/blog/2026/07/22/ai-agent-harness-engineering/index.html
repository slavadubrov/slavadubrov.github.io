Harness engineering para agentes de AI: desenhar o loop à volta do modelo

Parte 6 da série Engineering the Agentic Stack

O reasoning loop de um agente escolhe a ação seguinte. O seu harness fornece contexto, valida e autoriza as tool calls propostas, envia as calls aceites para o runtime, regista os resultados e decide se a tarefa está concluída.

Os modelos propõem edições e podem declarar tarefas como concluídas, enquanto o harness impõe permissões e interpreta as verificações de aceitação que decidem se o loop pode parar. A Parte 5 abordou o runtime que mantém o processo vivo. Este artigo centra-se no código de controlo dentro desse runtime: como medir se cada adição ajuda e como manter os controlos resultantes localizáveis à medida que o harness muda.

Para lá da primeira verificação de aceitação explícita, cada retry, handoff ou evaluator adicional é uma hipótese sobre uma falha observada. Só ganha lugar quando uma comparação controlada mostra que ajuda.

Para tornar esse percurso de controlo concreto, vou usar um pequeno repositório ficcional de uma loja. A tarefa de programação é baixar o limiar para um desconto automático de 10% de $100 para $75 em src/checkout.py. O repositório tem duas verificações obrigatórias:

  • pytest tests/test_checkout.py verifica o cálculo do desconto.
  • pnpm playwright test tests/checkout_discount.spec.ts adiciona um artigo de $80 numa loja de teste local e verifica se a página de checkout mostra um desconto de $8.

O exemplo é um artefacto didático, não uma aplicação real nem um benchmark. Cada tentativa começa a partir do mesmo commit e dos mesmos dados de teste com seed. O harness só pode aceitar a alteração quando ambos os comandos passam e a trace liga esses resultados ao commit testado.

As secções posteriores mudam deliberadamente para outros dois exemplos. Uma API de pedidos em staging mostra porque é que as calls que alteram estado precisam de proteção contra replay, enquanto uma migração de adaptador de pagamentos mostra do que uma nova sessão de modelo precisa para retomar trabalho inacabado. O laboratório complementar perto do fim volta a ser separado: é executável, mas contém tarefas simuladas genéricas em vez deste repositório da loja.

TL;DR: Comece com um modelo, algumas tools limitadas e uma verificação de aceitação explícita. Adicione retries depois de as traces mostrarem falhas transitórias nas calls. Adicione um progress handoff quando sessões retomadas repetem trabalho. Quando testar qualquer uma destas alterações, mantenha fixos a versão do modelo, as tarefas, o grader e o orçamento total. Remova o componente quando ele não melhorar o resultado medido.

O diagrama segue a alteração do desconto desde a proposta até à evidência. O harness fornece a tarefa e os ficheiros, verifica os argumentos e permissões de edit_file propostos, e envia a call aceite. Depois de o runtime aplicar a edição, o harness executa os testes de aceitação unitários e de browser indicados. Um comando falhado volta ao modelo como evidência para mais um turno; dois comandos bem-sucedidos tornam a alteração elegível para aceitação.

O que pertence ao harness

O walkthrough do loop do Codex da OpenAI descreve o ciclo básico. O harness monta um prompt, pede ao modelo a ação seguinte, envia uma tool call aceite para o runtime, acrescenta o resultado e pergunta novamente até o harness aceitar o resultado ou devolver o controlo ao utilizador.

As implementações podem juntar várias responsabilidades num só processo. Os limites de falha continuam, no entanto, a ser diferentes:

TermoFunçãoExemplo num coding agent
ModelPropõe texto, uma tool call ou uma resposta finalSugere uma edição a src/checkout.py
Reasoning loopEscolhe o passo seguinte a partir do contexto disponívelInspecionar, editar, testar, voltar a inspecionar
HarnessFornece contexto, autoriza e envia calls, regista resultados e verifica a conclusãoPermite edições em src/ e exige ambos os testes indicados
RuntimeExecuta calls e mantém o processo vivo e isoladoWorker, sandbox, session store, queue

Quando surge uma falha, diagnostique o limite que deve responder. Um plano fraco pode precisar de melhores instruções ou de melhor reasoning do modelo. Se edit_file apontar para um caminho fora de src/, o harness deve rejeitá-lo, ao passo que um processo de sandbox que morre antes de a edição ser executada pertence ao runtime, que tem de reiniciar o worker ou comunicar o crash.

O estudo de caso sobre harness engineering da própria OpenAI descreve uma instância da aplicação arrancável para cada worktree. A equipa também integrou automação de browser no ambiente do agente e expôs logs, métricas e traces.

Uma tarefa como “nenhum span nestes quatro percursos críticos do utilizador ultrapassa dois segundos” tornou-se testável porque o agente conseguia executar a aplicação e consultar os mesmos sinais que um engenheiro inspecionaria. O estudo de caso é específico do produto. O que é transferível é a condição por trás do resultado: a aplicação e os seus sinais de desempenho tinham de estar disponíveis dentro do ambiente do agente.

Lopopolo, o autor desse estudo de caso, mantém um guia de campo para harness engineering que nomeia as duas alavancas que este artigo usa: manter o modelo e o coding agent fixos como uma caixa negra, e fazer engenharia do contexto e das tools à sua volta. O seu enquadramento também explica porque é que tanto do harness acaba por ser código normal.

A fasquia de qualidade de uma organização, os seus procedimentos, o histórico de exceções e as relações de autoridade ficam abaixo da linha de água daquilo que um modelo geral pode conhecer. O harness traz isso à superfície sob a forma de instruções do repositório, regras de permissão e verificações de aceitação. Cada execução aceite pode devolver as lições aprendidas a esses artefactos, em vez de depender de a sessão seguinte as redescobrir.

Seguir a alteração do desconto da proposta até à aceitação

Para a tarefa do desconto definida acima, o modelo propõe alterar calculate_discount em src/checkout.py. Acontecem várias coisas antes de essa edição contar como progresso:

  1. O construtor de contexto fornece a tarefa, as instruções do repositório, os ficheiros relevantes, os resultados anteriores de tools e o plano atual.
  2. O modelo propõe uma call de edit_file com um caminho e texto de substituição.
  3. O limite da tool (o código do harness entre a proposta e a execução) valida os argumentos, verifica o caminho face ao âmbito permitido e pede aprovação se a operação precisar dela.
  4. O runtime aplica a edição na sandbox e devolve um resultado estruturado.
  5. O harness executa pytest tests/test_checkout.py, seguido de pnpm playwright test tests/checkout_discount.spec.ts, e lê ambos os exit codes. O teste de browser verifica o desconto visível de $8 no carrinho com seed de $80.
  6. O harness decide o que os resultados significam. Uma verificação falhada torna-se novo contexto para o turno seguinte do modelo, e uma execução bem-sucedida torna a tarefa candidata à conclusão.
  7. Um resultado bem-sucedido só se torna evidência de conclusão depois de o harness registar na trace o comando, o exit code e a versão do artefacto testado.

No passo 2, ainda não mudou nenhum ficheiro. O harness pode rejeitar ../../secrets.env, exigir aprovação para um comando destrutivo, ou parar uma execução que tenha esgotado o seu orçamento. Depois de os testes correrem, o harness lê ele próprio os seus exit codes. O modelo não pode marcar a sua própria edição como aprovada.

A trace deve mostrar o caminho proposto e o texto de substituição, a decisão de permissão, os ficheiros que mudaram, o commit testado e os resultados de ambos os comandos. Uma mensagem final de done sem esses registos não prova que esta alteração passou nas verificações obrigatórias.

Decidir onde cada regra é imposta

Coloque tests/checkout_discount.spec.ts na lógica normal do programa. O harness envia o comando Playwright para o runtime, lê o seu exit code e recusa terminar a execução enquanto ele falhar. Um prompt pode lembrar o modelo de correr o teste. Não consegue impedir o modelo de declarar sucesso sem evidência.

Outras regras encaixam melhor em camadas diferentes:

Os contratos de tool separam proposta de permissão

A tarefa do desconto só precisa de edições de ficheiros e comandos de teste. Uma API que altera estado tem um modo de falha diferente, por isso mudemos de exemplo nesta secção. Suponha que o agente pode chamar create_test_order contra um serviço de pedidos em staging enquanto prepara dados de teste. Esta tool não é uma das verificações de aceitação da tarefa do desconto. É útil aqui porque um timeout pode esconder se o serviço criou um pedido.

O limite da tool precisa de mais do que uma descrição em linguagem natural. Para create_test_order, o harness precisa de um contrato com:

  • argumentos validados, para que input malformado seja rejeitado antes da execução
  • um resultado estruturado como { "order_id": "123", "created": true }, para que verificações posteriores não tenham de analisar texto livre
  • uma categoria de efeito que registe se a call apenas obtém informação ou se altera um ficheiro, um registo de base de dados ou um serviço externo. Também regista se repetir a call é seguro. Esta etiqueta diz ao harness se um retry automático pode duplicar trabalho: pode repetir get_order_status quando o serviço define essa consulta como read-only, mas não pode repetir cegamente create_test_order porque a primeira call pode já ter criado o pedido
  • uma política de timeout e retry, para que uma resposta perdida não desencadeie uma sequência ilimitada de calls
  • uma regra de permissão que diga que aprovação é necessária. Ler o estado de um pedido pode correr automaticamente, enquanto criar um pedido pode exigir confirmação

A descrição em linguagem natural é texto mostrado ao modelo. Pode dizer: “Criar um pedido de teste para verificar o checkout.” Essa frase ajuda o modelo a decidir quando propor create_test_order. Não autoriza a call. Neste exemplo, o cliente MCP do harness valida os argumentos, aplica as suas próprias regras e verifica a confiança no servidor, os requisitos de aprovação e a segurança de retry antes de enviar o que quer que seja.

Um servidor MCP publica descrições de tools e anotações opcionais de comportamento para o cliente. Um servidor defeituoso ou malicioso pode descrever uma tool que altera estado como inofensiva. Se o cliente aceitasse essa afirmação automaticamente, poderia executar ou repetir create_test_order sem aprovação e criar um duplicado, pelo que a especificação MCP exige que os clientes tratem as anotações de tool como não confiáveis a menos que o próprio servidor seja confiável.

A especificação não prescreve uma única definição universal de confiança. Por isso, o cliente precisa de uma política de confiança explícita para o seu deployment; um servidor não pode tornar as suas próprias anotações fiáveis. É essa política que decide que metadados podem influenciar decisões de permissão ou retry e que anotações permanecem apenas consultivas.

Repetir uma call que altera estado exige proteção contra replay

Um problema de retry mais difícil aparece quando create_test_order cria o pedido mas a sua resposta HTTP se perde. O harness vê um timeout e não consegue dizer se o servidor concluiu o pedido. Repetir a call pode criar um segundo pedido.

Uma consulta de estado pode ser repetida quando o serviço a define como read-only. Uma call de criação precisa de proteção como uma idempotency key: o cliente anexa um identificador único do pedido, e o serviço devolve o primeiro resultado em vez de criar outro pedido quando volta a ver esse identificador. Sem esta proteção, o harness deve verificar se o pedido existe ou pedir uma decisão humana antes de outra tentativa. A AWS documenta este padrão na sua orientação sobre APIs idempotentes.

A aceitação precisa de evidência independente

Uma resposta bem-sucedida de create_test_order estabelece apenas que a tool devolveu dados. Não prova que uma tarefa de programação passou os seus testes. Se um teste de browser posterior depender do pedido colocado em staging, o harness tem de validar o schema da resposta e ainda assim correr esse teste antes de aceitar a alteração ao código.

Alguns critérios não se conseguem reduzir a um exit code. Numa tarefa separada de design visual, um evaluator novo pode comparar uma página ou diagrama renderizado com uma rubrica escrita. As equipas devem verificar esse evaluator face a revisões humanas antes de o usar como gate de conclusão.

Uma migração de adaptador de pagamentos precisa de um handoff

Mudemos novamente de tarefa, mas mantendo-nos no repositório ficcional da loja. O agente tem agora de migrar o checkout do adaptador de pagamentos v1 para v2. O trabalho abrange o handler de checkout, o cliente de pagamentos, a configuração e os testes, por isso pode durar mais do que uma sessão do modelo.

Antes de a primeira sessão atingir o seu limite de contexto, já modificou vários ficheiros, arrancou uma sandbox de pagamentos local e deixou tests/payment_migration.spec.ts a falhar. Esse teste de aceitação de browser conclui um pagamento através do adaptador v2 e verifica o provider ID registado. Um resumo da conversa pode orientar a sessão seguinte do modelo, mas não consegue reiniciar a sandbox nem provar que ficheiros estão atualmente modificados.

A sessão seguinte tem de recuperar três coisas:

O que tem de ser recuperadoO que incluiComo pode falhar
Histórico da conversaMensagens, tool calls e resultados devolvidosDetalhes antigos ocupam o espaço da tarefa atual
Ambiente de trabalhoFicheiros, sandbox de pagamentos e estado do teste de browserA transcrição diz que um serviço está a correr depois de ele ter morrido
Progresso da tarefaPlano, verificações concluídas, aprovação pendente, ação seguinteA sessão seguinte repete trabalho já concluído

A compaction substitui mensagens antigas por um resumo mais curto para que a sessão atual possa continuar. Um progress handoff regista aquilo de que a sessão seguinte precisa: a branch atual, os ficheiros alterados, o último comando de teste e respetivo output, e o passo seguinte ainda por resolver. Se a conversa antiga contiver pressupostos desatualizados, o harness pode iniciar uma nova sessão de modelo com esse handoff e o workspace atual. Substituir um worker que crashou e restaurar os seus processos é uma tarefa separada de recuperação do runtime.

Uma pequena edição de documentação pode não precisar de nenhum destes mecanismos. A migração de pagamentos precisa de um handoff quando o trabalho se estende por várias sessões, porque a sessão seguinte do modelo tem de reconstruir tanto o workspace como o estado da tarefa.

As experiências da Anthropic com coding agents de longa duração usaram histórico git e um ficheiro de progresso entre sessões, enquanto o seu harness-design report posterior separa compaction de um handoff com contexto novo e relata a orquestração adicional, o consumo de tokens e o tempo de relógio exigidos pelos handoffs.

Usar traces para distinguir três falhas

As três linhas seguintes são esboços ilustrativos de trace, não execuções medidas nem output do laboratório complementar. Cada linha mostra uma falha diferente e, por isso, uma resposta diferente do harness.

O que a trace registaO que aconteceuResposta correta
A call read-only get_order_status devolve 503; não há nenhuma call que altere estado em vooFalhou uma consulta transitóriaRepetir a consulta com limite e backoff
create_test_order entra em timeout, depois uma consulta de estado encontra o pedido 123 sob a idempotency key checkout-42O serviço criou o pedido, mas a resposta perdeu-seDevolver o pedido existente; não criar outro
A edição e o teste unitário passam, mas a trace não tem resultado para tests/checkout_discount.spec.ts no commit testadoFalta a evidência de aceitação obrigatóriaManter a execução aberta e enviar o teste de aceitação de browser

Esta distinção importa porque um 503 não torna automaticamente todas as calls seguras para retry. A primeira linha é uma consulta read-only. A segunda linha é um pedido que altera estado, por isso a idempotency key e o estado do lado do servidor decidem se é permitido mais uma tentativa de criação. A terceira linha nem é uma falha de tool; o harness ainda não recolheu a evidência necessária para aceitar a alteração do desconto.

Uma transcrição de chat regista o que o modelo viu. Não consegue provar se o serviço de pedidos confirmou um pedido antes de a resposta desaparecer. A trace tem de juntar a call do cliente, a decisão de aprovação, a idempotency key, o resultado do servidor ou a consulta de estado, o commit testado e o resultado do teste de aceitação. São esses campos que dizem ao harness em qual dos três percursos está.

Sintoma repetidoPequena alteração a experimentarO que medir
Consultas read-only falham transitoriamenteRetry limitado com backoffTaxa de recuperação, calls extra, wall time
Sessões retomadas repetem trabalho concluídoProgress handoff estruturadoAções de tools duplicadas após retoma
Faltam testes obrigatórios na conclusãoGate de aceitação fail-closedTarefas aceites sem todas as verificações obrigatórias

Antes de adicionar um componente, nomeie a falha repetida que ele deve reduzir e o número que vai acompanhar. Remova o componente se uma comparação controlada não fizer esse número mexer o suficiente para pagar o seu custo.

Medir uma alteração de cada vez

Uma ablation mede se um componente do harness causa o efeito esperado alterando ou removendo esse componente enquanto o resto da experiência se mantém fixo. Por exemplo, será que o linting do editor ajuda este modelo neste conjunto de tarefas?

Use o seguinte protocolo:

  1. Congele a versão do modelo, as instâncias de tarefa, o ambiente, o grader e os prompts fora do componente em teste.
  2. Dê a ambas as variantes o mesmo orçamento total de tokens, tempo e dinheiro.
  3. Escolha o número de ensaios ou a regra de paragem antes de correr a comparação.
  4. Corra as mesmas instâncias de tarefa em ambas as variantes. Como os outputs do modelo variam, repita cada tarefa várias vezes.
  5. Reporte a média juntamente com a dispersão ou intervalo de confiança.
  6. Conte todos os ensaios iniciados, incluindo timeouts, paragens por policy, crashes do harness e falhas do evaluator.

A taxa de sucesso, por si só, pode esconder um componente caro. No mínimo, acompanhe tarefas erradas aceites como concluídas, custo e wall time por tarefa concluída, erros de tools, pedidos duplicados, minutos de revisão e overrides manuais de permissões. Escolha a métrica que carrega o custo real para o produto. Uma subida de dois pontos nas tarefas concluídas é uma má troca se duplicar a fila de revisão.

Uma experiência emparelhada de migração de pagamentos torna o progress handoff mensurável. Cada par controlo/tratamento começa a partir do mesmo commit do repositório e do mesmo checkpoint com seed, com o mesmo modelo, tarefa, grader e orçamento total. O handoff é o único interruptor. A métrica principal conta ações de tools duplicadas após retoma: uma ação é duplicada quando a sua operação e o seu artefacto correspondem a um passo que a sessão anterior já tinha concluído.

O artigo do SWE-agent fixa GPT-4 Turbo na divisão de 300 tarefas SWE-bench Lite e reporta 18,0% resolvidas com a sua interface completa, comparado com 11,0% para o agente apenas com shell. O artigo também alterou features individuais da interface:

A LangChain publicou uma comparação mais ampla com modelo fixo para deepagents-cli. Reporta um aumento no Terminal-Bench 2.0 de 52,8% para 66,5% com gpt-5.2-codex fixo enquanto a equipa mudou o system prompt, tools e middleware. O artigo agrupa várias alterações e omite um intervalo de confiança, uma comparação com orçamento total fixo e uma tabela de ablation por alteração. Esse resultado não consegue identificar qual foi a alteração útil.

O relatório sobre aplicações de longa duração da Anthropic é um estudo de caso qualitativo e específico do produto, e não um benchmark controlado. O seu evaluator verificou 27 critérios do level editor no Sprint 3. A equipa relata que as calls do evaluator se tornaram overhead em tarefas que o Opus 4.6 conseguia concluir de forma fiável sozinho, mas ainda assim ajudavam perto do limite do modelo, pelo que removeu componentes do harness um a um após o upgrade do modelo. O exemplo é uma razão para voltar a validar scaffolding antigo quando o modelo muda; não estima uma magnitude de efeito geral.

Manter o harness editável depois de ganhar o seu lugar

A ablation mantém um harness pequeno, mas o seu código pode ainda sobreviver ao modelo para o qual foi afinado. Um pedido como “mascarar segredos em todos os percursos de captura” nomeia um comportamento, não um ficheiro. Num harness de produção, esse comportamento pode abranger etapas de execução e estado partilhado. Um humano ou coding agent tem de encontrar todos os pontos de implementação antes de o alterar em segurança.

Uma preprint de 2026 de Wang et al., o Harness Handbook, chama a este passo behavior localization. O handbook constrói um mapa centrado no comportamento a partir do codebase do harness. A análise estática extrai um grafo do programa sem calls ao modelo, e depois um LLM organiza as suas unidades em etapas de execução.

O maintainer ou coding agent começa com uma visão geral do sistema, abre a etapa de execução relevante e desce até entradas ancoradas no código-fonte para uma função ou ficheiro. Uma vista de registo anota onde o estado partilhado é escrito e lido entre etapas. Esta hierarquia mantém a visão geral pequena, preservando ao mesmo tempo um caminho até ao código-fonte.

Atualidade é uma regra separada. Cada localizador tem de resolver contra o repositório vivo. O handbook exclui entradas desatualizadas em vez de adivinhar, e cada diff não vazio resincroniza as entradas que afeta.

O diagrama comprime o loop de modificação: um pedido apenas de comportamento desce pelos níveis do handbook, cada localizador candidato é verificado contra o repositório vivo antes de o plano ser escrito, e cada diff aplicado resincroniza o mapa.

A avaliação do Handbook segue o protocolo que este artigo defende. Em dois harnesses open-source (Terminus-2, seis ficheiros Python, e o monorepo do Codex, com 2.267 ficheiros Rust), um planner read-only com DeepSeek-V4-Pro explorou diretamente o repositório ou passou pelo handbook. Os pedidos, o repositório, as permissões de tools e o decoding eram idênticos em ambos os ramos. Três juízes (GPT-5.5, Opus 4.8, DeepSeek-V4-Pro) avaliaram cada plano de edição em localization, controlo de âmbito e reasoning:

HarnessTaxa de vitória baselineAssistido pelo HandbookTokens do planner
Terminus-2 (6 ficheiros)26.7%45.6%−8.6%
Monorepo do Codex (2.267 ficheiros)28.3%38.3%−12.7%

O planner assistido pelo handbook ganhou mais vezes e usou menos tokens do planner em ambos os repositórios. As condições mantêm-se ligadas a esse resultado: três juízes LLM avaliaram planos de edição produzidos por um único modelo planner em dois harnesses. O estudo avaliou planos, não diffs executados nem taxas de defeitos em produção.

As secções anteriores usam traces para responder à pergunta de porque existe um componente. Este mapa responde à pergunta seguinte: onde vive esse componente quando tiver de mudar?

Experimente o método no laboratório complementar

O projeto harness-demo no commit 517353f3 é um pequeno exercício determinístico com 12 tarefas sintéticas genéricas que cobrem alterações de código como fix-parser-edge-case, split-large-module e wire-browser-test. Não implementa o repositório ficcional da loja.

Cada fixture de tarefa declara uma dificuldade e quatro condições booleanas: uma tool instável, progresso perdido, uma lacuna de implementação não detetada e conclusão ambígua. O simulador deriva uma quinta condição para tarefas difíceis que também precisam de um ficheiro de progresso: sem context_reset, a compaction preserva pressupostos desatualizados. Um grader determinístico marca uma tarefa como aprovada apenas quando a configuração selecionada trata todas as condições aplicáveis. Não corre nenhum modelo nem serviço externo.

Os comandos respondem a perguntas diferentes:

  • make check executa Ruff e sete testes unitários, incluindo o validador que rejeita qualquer par de ablation que altere mais do que um componente.
  • make run imprime uma matriz de ensino cumulativa, depois cinco comparações válidas de remoção de um único componente.
  • make failures indica a condição não tratada para cada tarefa falhada. O harness completo deve terminar com all synthetic tasks pass.

A secção causal de make run é assim:

component                 control  treatment  delta
retry_policy              8/12     12/12       +4
progress_handoff          7/12     12/12       +5
evaluator                 8/12     12/12       +4
fail_closed_acceptance    7/12     12/12       +5
context_reset            10/12     12/12       +2

Para cada linha, o controlo é a configuração completa com um componente removido; o tratamento repõe apenas esse componente. A matriz cumulativa anterior é útil para orientação, mas algumas das suas linhas adjacentes adicionam vários componentes de uma só vez e, por isso, não conseguem identificar uma causa.

O laboratório valida cada par declarado antes de o executar. Os seus testes de regressão incluem também um par intencionalmente inválido que altera em conjunto a policy de retry e o evaluator; o validador rejeita-o.

O schema de configuração do laboratório verifica todos os cinco campos de componentes. Este excerto executável mostra a mesma salvaguarda num par válido de progress handoff:

from dataclasses import dataclass, fields


@dataclass(frozen=True)
class Config:
    progress_handoff: bool = False
    evaluator: bool = False
    retry_policy: bool = False
    fail_closed_acceptance: bool = False
    context_reset: bool = False


def changed_components(control: Config, treatment: Config) -> tuple[str, ...]:
    return tuple(
        field.name
        for field in fields(control)
        if getattr(control, field.name) != getattr(treatment, field.name)
    )


control = Config(progress_handoff=False, evaluator=True, retry_policy=True)
treatment = Config(progress_handoff=True, evaluator=True, retry_policy=True)
assert changed_components(control, treatment) == ("progress_handoff",)

Começar com um loop e uma verificação de aceitação

Eu começaria um harness para coding agent com um modelo capaz, instruções do repositório, algumas tools limitadas, uma sandbox e um teste de aceitação explícito. Registaria tool calls, resultados, custos e esse teste final numa só trace, para que as primeiras falhas úteis fiquem visíveis sem ser preciso reconstruí-las a partir de logs de terminal e transcrições de chat. Esta é uma baseline proposta, não evidência de um sistema em produção.

A partir daí, adicione apenas o que uma trace justificar. Registe quem mantém cada componente, quantos tokens ou segundos ele acrescenta, e que teste de regressão justificaria removê-lo após um upgrade do modelo.

Daqui a seis meses, alguém que veja progress_handoff=True deve conseguir encontrar as traces falhadas que o justificaram e os casos de regressão que ainda o mantêm lá. As traces explicam porque existe o componente; um mapa de comportamento atual explica onde tocar nele.
