Harness Engineering para AI Agents: conceber loops de controlo

Viacheslav Dubrov

2026-07-22 · Atualizado 2026-08-01 · 27 min · Agentes de IA

Tradução automática Este artigo foi traduzido automaticamente a partir da versão original em inglês.

O reasoning loop de um agent escolhe a ação seguinte. O seu harness fornece contexto, valida os tool calls propostos, autoriza-os, despacha os que aceita, regista os resultados e decide se a tarefa está concluída.

As três primeiras responsabilidades já têm um artigo. A memória fornece o contexto, o tool use define o que pode ser proposto e a segurança decide o que é executado. Foram publicados como artigos separados porque são problemas de engenharia distintos. Escolher entre Qdrant e pgvector não tem qualquer relação com escrever uma regra de negação PreToolUse.

Também partilham um momento: o intervalo entre o modelo nomear uma ação e a máquina a executar. Cada um responde a uma pergunta sobre esse intervalo, e o harness é o código que o mantém aberto tempo suficiente para colocar as três perguntas.

Este artigo aborda o que fica depois dessas três áreas: decidir se o trabalho concluído está realmente concluído e demonstrar que cada controlo no loop justifica o seu custo. A Parte 5 abordou o runtime que mantém o processo ativo por baixo.

Destina-se a engenheiros que estão a construir ou a rever harnesses para coding agents que têm de autorizar tool calls, preservar o progresso e provar a conclusão.

No final, deverá conseguir posicionar cada controlo, manter a evidência de aceitação independente do modelo que propõe as ações, proteger os retries de side effects e medir um componente de cada vez.

TL;DR

Comece com um modelo, algumas tools restritas e uma verificação explícita de aceitação. Adicione retries depois de os traces mostrarem falhas transitórias nos calls. Adicione um progress handoff quando as sessões retomadas repetirem trabalho. Ao testar qualquer um dos dois, mantenha fixa a versão do modelo, as tarefas, o grader e o orçamento total. Remova o componente quando não melhorar o resultado medido.

Para além da primeira verificação explícita de aceitação, cada retry, handoff ou evaluator adicional é uma hipótese sobre uma falha observada. Só ganha lugar quando uma comparação controlada demonstra que ajuda.

A verificação de aceitação mais simples é fácil de escrever para um pequeno research agent como o que a série tem vindo a construir — um agent LangGraph que obtém dados de mercado e escreve um relatório de analista. Um hook externo valida o relatório contra um schema e verifica se este contém efetivamente stock tickers; um relatório malformado mantém o run aberto. São doze linhas de código normal, e o modelo não pode declarar que o seu próprio output está bem formado. O gate do próprio repositório é mais flexível: um evaluator em fresh context que vota, seguido por uma pessoa. (A Parte 4 apresenta a versão determinística.)

O que esse exemplo não consegue mostrar é a parte interessante: o que acontece quando a evidência é ambígua, quando um retry pode cobrar duas vezes a alguém ou quando o trabalho ultrapassa a sessão que o iniciou. Esses casos precisam de uma tarefa com um limite de aprovação/reprovação mais claro do que um relatório de investigação. O research agent mantém-se como exemplo de verificação de aceitação; um pequeno repositório de uma loja fictícia junta-se aos casos de retry e handoff. A tarefa de coding consiste em baixar o limiar para aplicar automaticamente um desconto de 10% de $100 para $75 em src/checkout.py. O repositório tem duas verificações obrigatórias:

  • pytest tests/test_checkout.py verifica o cálculo do desconto.
  • pnpm playwright test tests/checkout_discount.spec.ts adiciona um artigo de $80 a uma loja de testes local e verifica que a página de checkout apresenta um desconto de $8.

O exemplo é um fixture pedagógico, não uma aplicação real nem um benchmark. Cada tentativa começa no mesmo commit e com os mesmos dados de teste semeados. O harness só pode aceitar a alteração quando ambos os comandos passam e o trace associa esses resultados ao commit testado.

O diagrama acompanha a alteração do desconto, desde a proposta até à evidência. O harness fornece a tarefa e os ficheiros, verifica os argumentos e as permissões do edit_file proposto e despacha o call aceite. Depois de o runtime aplicar a edição, o harness executa os testes de aceitação unitários e no browser indicados. Um comando que falha regressa ao modelo como evidência para outro turno; dois comandos aprovados tornam a alteração elegível para aceitação.

O que pertence ao harness

O percurso do Codex loop da OpenAI descreve o ciclo básico. O harness compõe um prompt, pede ao modelo a ação seguinte, envia um tool call aceite para o runtime e acrescenta o resultado. Depois pergunta novamente. O processo repete-se até o harness aceitar o resultado ou devolver o controlo ao utilizador.

As implementações podem combinar várias responsabilidades num só processo. Os limites das falhas continuam a ser diferentes:

TermoFunçãoExemplo num coding agent
ModeloPropõe texto, um tool call ou uma resposta finalSugere uma edição a src/checkout.py
Reasoning loopEscolhe o próximo passo a partir do contexto disponívelInspecionar, editar, testar, voltar a inspecionar
HarnessFornece contexto, valida propostas, autoriza-as, despacha calls aceites, regista resultados e verifica a conclusãoPermite edições em src/ e exige ambos os testes indicados
RuntimeExecuta calls aceites e mantém o estado ativo fora do processo workerLog da sessão, sandbox, checkpoint store, trace backend

A linha do runtime abrange quatro elementos: sessão, sandbox, checkpoint e trace. Os quatro armazenam estado ou confinam a execução. O modelo propõe a ação e o reasoning loop escolhe o passo seguinte. O harness decide se um call proposto pode ser executado e se a evidência é suficiente para terminar, razão pela qual tem um artigo próprio. A Parte 5 contabiliza o harness, juntamente com estes quatro elementos, como um dos cinco primitivos que é necessário posicionar antes de fazer shipping; este artigo separa-o novamente.

Quando surge uma falha, diagnostique o limite que deve responder. Um plano fraco pode precisar de melhores instruções ou de melhor reasoning do modelo. Se edit_file apontar para um caminho fora de src/, o harness deve rejeitá-lo. Um processo sandbox que morre antes de a edição ser executada pertence ao runtime, que deve reiniciar o worker ou reportar o crash.

Onde se enquadram as partes anteriores

A linha do harness acima faz a maior parte do trabalho nessa tabela e é onde acabam as Partes 2, 3 e 4. Cada uma decide uma coisa sobre um turno individual:

Parte anteriorO que decide para este turnoOnde atua no walkthrough da secção seguinte
Parte 2 — memóriaQue estado anterior entra no promptPasso 1, o context builder
Parte 3 — tool useQue ações existem e qual é o aspeto de um resultado validadoValidação dos argumentos no passo 3 e formato do resultado no passo 4
Parte 4 — segurançaSe este call específico pode ser executado agoraPasso 3, verificação do caminho e decisão de aprovação
Parte 6 — este artigoSe a evidência resultante termina o runPassos 5 a 7, verificações de aceitação e trace

As Partes 3 e 4 partilham o passo 3, e essa sobreposição é precisamente o argumento para as tratar como um só programa. A mesma camada de código do harness que rejeita um argumento malformado rejeita também um call permitido, mas ainda não aprovado. Quando estão divididas por dois serviços, essas duas rejeições divergem, e um call que passa a validação do schema num local é autorizado noutro que nunca viu o schema.

A separação continua a ser importante para debugging: uma edição no ficheiro errado é uma regra de caminho da Parte 4, não um problema de retrieval da Parte 2. Uma secção perto do final deste artigo transforma isso numa tabela de encaminhamento.

O próprio case study de harness engineering da OpenAI descreve uma instância da aplicação arrancável para cada worktree. A equipa também ligou a browser automation ao ambiente do agent e expôs logs, métricas e traces.

Uma tarefa como “nenhum span nestas quatro jornadas críticas do utilizador excede dois segundos” tornou-se testável porque o agent podia executar a aplicação e consultar os mesmos sinais que um engenheiro inspecionaria. O case study é específico do produto. O que é transferível é a condição subjacente ao resultado: a aplicação e os seus sinais de desempenho tinham de estar disponíveis dentro do ambiente do agent.

Lopopolo, autor desse case study, mantém um field guide para harness engineering. Identifica as duas alavancas usadas neste artigo: manter o modelo e o coding agent fixos como uma black box e fazer engineering do contexto e das tools à sua volta. O seu enquadramento também explica por que razão grande parte do harness acaba por ser código normal.

O nível de qualidade, os procedimentos, o histórico de exceções e as relações de autoridade de uma organização estão fora do que um modelo geral pode conhecer. O harness expõe-nos como instruções do repositório, regras de permissões e verificações de aceitação. Cada run aceite pode devolver as suas aprendizagens a esses artefactos, em vez de depender da sessão seguinte para as redescobrir.

Acompanhe a alteração do desconto desde a proposta até à aceitação

Byte says

Deixei o modelo avaliar seu próprio relatório por uma semana. Ele passou todas as vezes. O avaliador precisa ficar fora do loop.

Para a tarefa de desconto definida acima, o modelo propõe alterar calculate_discount em src/checkout.py. Várias coisas acontecem antes de essa edição contar como progresso:

  1. O context builder fornece a tarefa, as instruções do repositório, os ficheiros relevantes, os resultados anteriores de tool calls e o plano atual.
  2. O modelo propõe um call edit_file com um caminho e texto de substituição.
  3. O tool boundary (o código do harness entre a proposta e a execução) valida os argumentos, verifica o caminho contra o âmbito permitido e pede aprovação se a operação o exigir.
  4. O runtime aplica a edição na sandbox e devolve um resultado estruturado.
  5. O harness executa pytest tests/test_checkout.py, seguido de pnpm playwright test tests/checkout_discount.spec.ts, e lê ambos os exit codes. O teste no browser verifica o desconto visível de $8 no carrinho semeado de $80.
  6. O harness decide o significado dos resultados. Uma verificação falhada torna-se novo contexto para o turno seguinte do modelo, e um run aprovado torna a tarefa candidata a conclusão.
  7. Um resultado aprovado só se torna evidência de conclusão depois de o harness registar no trace o comando, o exit code e a versão do artefacto testado.

Depois do passo 2, nenhum ficheiro foi alterado. O harness pode rejeitar ../../secrets.env, exigir aprovação para um comando destrutivo ou parar um run que tenha esgotado o orçamento. Esse é o último momento barato de que dispõe. Depois de os testes serem executados, o harness lê ele próprio os seus exit codes. O modelo não pode marcar a sua própria edição como aprovada.

O trace deve mostrar o caminho e o texto de substituição propostos, a decisão de permissões, os ficheiros alterados, o commit testado e os resultados de ambos os comandos. Uma mensagem final done sem esses registos não prova que esta alteração passou as verificações obrigatórias.

Decida onde cada regra é aplicada

A exigência de que tests/checkout_discount.spec.ts passe pertence ao código determinístico, não ao prompt. O harness despacha o comando Playwright para o runtime, lê o seu exit code e recusa terminar o run enquanto este falhar. Um prompt pode lembrar o modelo de executar o teste. Não pode impedir o modelo de declarar sucesso sem evidência.

Outras regras encaixam noutras camadas:

Coloque a regra emAdequado paraExemplo
Prompt ou skillOrdem de pesquisa, convenções de coding e formato do planoLer AGENTS.md antes de editar código de checkout
Tool boundaryValidação de argumentos, caminhos permitidos, aprovações e acesso às toolsPermitir escritas apenas em src/
Código determinísticoOrçamentos, timeouts, retries, exit codes dos testes e gates de releaseManter o run aberto enquanto o teste Playwright falhar
Evaluator em fresh contextRevisão visual ou critérios que exigem julgamento semelhante ao humanoComparar um diagrama gerado com uma rubric escrita

Os tool contracts separam proposta e permissão

A tarefa do desconto só precisa de edições de ficheiros e comandos de teste. Uma API com alteração de estado tem um modo de falha diferente, por isso mudemos os exemplos desta secção. Suponha que o agent pode chamar create_test_order contra um serviço de encomendas de staging enquanto configura dados de teste. Esta tool não é uma das verificações de aceitação da tarefa de desconto. É útil aqui porque um timeout pode ocultar se o serviço criou uma encomenda.

O tool boundary precisa de mais do que uma descrição em linguagem natural. Precisa de um tool contract explícito. A Parte 3 defendeu um do lado do modelo: ações claras, feedback compacto e erros recuperáveis. O harness precisa do mesmo contrato por uma razão diferente. Tem de decidir, sem perguntar ao modelo, se um call pode ser executado e se um call falhado pode ser repetido. Para create_test_order, isso significa um contrato com:

  • argumentos validados, para que input malformado seja rejeitado antes da execução
  • um resultado estruturado como { "order_id": "123", "created": true }, para que as verificações posteriores não tenham de analisar texto livre
  • uma categoria de efeito que regista se o call apenas obtém informação ou altera um ficheiro, um registo de base de dados ou um serviço externo. Regista também se repetir o call é seguro. Esta etiqueta informa o harness se um retry automático pode duplicar trabalho. O harness pode repetir get_order_status quando o serviço define essa pesquisa como read-only. Não deve repetir cegamente create_test_order, porque o primeiro call pode já ter criado a encomenda
  • um timeout e uma política de retries, para que uma resposta perdida não desencadeie uma sequência ilimitada de calls
  • uma regra de permissões que indique que aprovação é necessária. A leitura do estado da encomenda pode ser executada automaticamente, enquanto a criação de uma encomenda pode exigir confirmação

A descrição em linguagem natural é o texto mostrado ao modelo. Poderá dizer: “Create a test order for checkout verification.” Essa frase ajuda o modelo a decidir quando propor create_test_order. Não autoriza o call. Neste exemplo, o cliente Model Context Protocol (MCP) do harness valida os argumentos, aplica as suas próprias regras e verifica a confiança no servidor, os requisitos de aprovação e a segurança dos retries antes de despachar qualquer coisa. Essa verificação é a ladder ordenada deny/ask/hook/allow da Parte 4, com uma pergunta adicional: se um call que já falhou pode ser enviado novamente.

Um servidor MCP publica descrições de tools e anotações opcionais de comportamento para o cliente. Um servidor defeituoso ou malicioso pode descrever uma tool que altera estado como inofensiva. Um cliente que aceitasse automaticamente essa afirmação poderia executar ou repetir create_test_order sem aprovação e criar uma duplicada. A especificação MCP exige, por isso, que os clientes tratem as anotações das tools como não confiáveis, salvo se o próprio servidor for confiável.

A especificação não prescreve uma única configuração universal de confiança, pelo que precisa de uma política de confiança explícita para a sua implementação; um servidor não pode tornar as suas próprias anotações confiáveis. Essa política decide que metadados podem influenciar decisões de permissões ou retries e que anotações permanecem apenas consultivas.

Repetir um call que altera estado exige proteção contra replay

A Parte 5 coloca uma idempotency key em cada tool call com side effects. O harness é que decide quando essa chave tem de suportar essa responsabilidade. create_test_order cria a encomenda, mas a resposta HTTP perde-se. O harness vê um timeout e não consegue saber se o servidor concluiu o pedido. Repetir o call pode criar uma segunda encomenda.

Uma pesquisa de estado pode ser repetida quando o serviço a define como read-only. Um call de criação precisa da chave: o cliente associa um identificador de pedido único e o serviço devolve o primeiro resultado, em vez de criar outra encomenda, quando volta a ver esse identificador. Sem esta proteção, o harness deve verificar se a encomenda existe ou pedir uma decisão humana antes de tentar novamente. A AWS documenta este padrão na sua orientação sobre APIs idempotentes.

A aceitação precisa de evidência independente

Uma resposta bem-sucedida de create_test_order apenas estabelece que a tool devolveu dados. Não prova que uma tarefa de coding passou os testes. Se um teste posterior no browser depender da encomenda em staging, o harness tem de validar o schema da resposta e executar ainda esse teste antes de aceitar a alteração de código.

Alguns critérios não podem ser reduzidos a um exit code. Numa tarefa separada de design visual, um evaluator em fresh context pode comparar uma página ou um diagrama renderizado com uma rubric escrita — “fresh context” significa uma segunda sessão do modelo que começa sem histórico do run e lê os artefactos produzidos, em vez do transcript. Valide esse evaluator contra revisões humanas antes de o deixar controlar a conclusão.

Uma migração de um payment adapter precisa de um handoff

Mudemos novamente de tarefa, mas mantenhamo-nos no repositório da loja fictícia. Agora o agent tem de migrar o checkout do payment adapter v1 para o v2. O trabalho abrange o checkout handler, o payment client, a configuração e os testes, pelo que pode ultrapassar uma sessão de modelo — um período contínuo de contexto do modelo, terminado por um restart ou por um início deliberadamente fresh, em vez de ser mantido.

Antes de a primeira sessão atingir o limite de contexto, modificou vários ficheiros, iniciou uma payment sandbox local e deixou tests/payment_migration.spec.ts a falhar. Esse teste de aceitação no browser conclui um pagamento através do adapter v2 e verifica o provider ID registado. Um resumo da conversa pode orientar a sessão seguinte do modelo, mas não pode reiniciar a sandbox nem provar que ficheiros estão atualmente modificados.

A sessão seguinte tem de recuperar três coisas:

O que tem de ser recuperadoO que incluiComo pode falhar
Histórico da conversaMensagens, tool calls e resultados devolvidosOs detalhes antigos ocupam o espaço da tarefa atual
Ambiente de trabalhoFicheiros, payment sandbox e estado do teste no browserO transcript diz que um serviço está a correr depois de este ter morrido
Progresso da tarefaPlano, verificações concluídas, aprovação pendente, próxima açãoA sessão seguinte repete trabalho concluído

A compactação substitui mensagens antigas por um resumo mais curto, para que a sessão atual possa continuar. Um progress handoff regista o que a sessão seguinte precisa: o branch atual, os ficheiros alterados, o último comando de teste e o respetivo output, e o próximo passo por resolver.

Um ficheiro de handoff é document memory escrito para um leitor específico, a sessão seguinte do modelo, e é um artefacto diferente do checkpoint que o runtime restaura. O checkpoint responde a onde a execução parou. O handoff responde ao significado do trabalho e ao que falta. Restaure um checkpoint sem handoff e a sessão seguinte obtém um processo retomável, mas não sabe qual das quatro áreas tocadas — handler, client, configuração, testes — já concluiu. É isso que produz trabalho duplicado.

Se a conversa antiga contiver pressupostos obsoletos, o harness pode iniciar uma sessão fresh do modelo com esse handoff e o workspace atual. Substituir um worker que sofreu crash e restaurar os seus processos é uma tarefa separada de recuperação do runtime.

Uma pequena edição de documentação pode não precisar de nenhum destes mecanismos. A migração do pagamento precisa de um handoff assim que atravessa sessões, porque a sessão seguinte tem de reconstruir tanto o workspace como o estado da tarefa.

As experiências da Anthropic com coding agents de longa duração usaram histórico Git e um ficheiro de progresso entre sessões. O posterior relatório de harness design da Anthropic separa a compactação de um handoff em fresh context e relata que os handoffs acrescentam orchestration, utilização de tokens e wall time, sem publicar valores que atribuam qualquer parte desse overhead ao handoff em si.

Use traces para distinguir três falhas

As três linhas seguintes são exemplos ilustrativos de traces, não execuções medidas nem output do companion lab. Cada linha mostra uma falha diferente e, por isso, uma resposta diferente do harness.

O que o trace registaO que aconteceuResposta correta
O call read-only get_order_status devolve 503; não está em curso nenhum call que altere estadoUma pesquisa transitória falhouRepetir a pesquisa com limites e backoff
create_test_order sofre timeout e, depois, uma pesquisa de estado encontra a encomenda 123 sob a idempotency key checkout-42O serviço criou a encomenda, mas a resposta perdeu-seDevolver a encomenda existente; não criar outra
A edição e o teste unitário passam, mas o trace não tem resultado para tests/checkout_discount.spec.ts no commit testadoFalta evidência de aceitação obrigatóriaManter o run aberto e despachar o teste de aceitação no browser

Uma falha com aspeto transitório não torna todos os calls seguros para repetir. A primeira linha é uma pesquisa read-only. A segunda é um pedido que altera estado, pelo que a idempotency key e o estado do lado do servidor determinam se é permitida outra tentativa de criação. A terceira nem sequer é uma falha de tool; o harness ainda não recolheu a evidência necessária para aceitar a alteração do desconto.

Um transcript de chat regista o que o modelo viu. Não consegue provar se o serviço de encomendas confirmou um pedido antes de a resposta desaparecer. O transcript é o relato dos eventos pelo agent; o trace é aquilo que a máquina executou realmente. Quando os dois discordam, confie no trace. O trace tem de associar o call do cliente, a decisão de aprovação, a idempotency key, o resultado do servidor ou a pesquisa de estado, o commit testado e o resultado do teste de aceitação. Esses campos indicam ao harness em que um dos três caminhos se encontra.

Sintoma repetidoPequena alteração a experimentarO que medir
As pesquisas read-only falham de forma transitóriaRetry limitado com backoffTaxa de recuperação, calls adicionais, wall time
As sessões retomadas repetem trabalho concluídoProgress handoff estruturadoTool actions duplicados após o resume
Faltam testes obrigatórios no momento da conclusãoGate de aceitação fail-closedTarefas aceites sem todas as verificações obrigatórias
Os defeitos visuais sobrevivem às verificações determinísticasEvaluator em fresh context com uma rubricDefeitos encontrados, rejeições falsas, tempo de revisão
O agent edita fora do seu âmbitoPermissões mais restritas nas toolsCalls bloqueados e overrides manuais
A memória recuperada ocupa o lugar da tarefa atualLimitar os factos recuperados; fazer ranking antes de os injetarTokens gastos na recuperação, tarefas concluídas, custo por tarefa

Antes de adicionar um componente, identifique a falha recorrente que este deve reduzir e o número que irá acompanhar. Remova o componente se uma comparação controlada não mover esse número o suficiente para compensar o seu custo. A maioria dos harnesses que vi cresce no sentido oposto: alguém encontra um run problemático, adiciona uma proteção e a proteção fica para sempre porque ninguém consegue provar que é seguro apagá-la. É assim que se acaba com um loop que ninguém quer alterar.

Transformar essas falhas recorrentes numa regression suite versionada é uma tarefa própria. Escrevi sobre isso separadamente em AI Agent Evaluation in Production.

Meça uma alteração de cada vez

Uma ablation mede se um componente do harness produz o efeito esperado, alterando ou removendo esse componente enquanto o resto da experiência permanece fixo. Por exemplo: o editor linting ajuda este modelo neste conjunto de tarefas?

Use o protocolo seguinte:

  1. Congele a versão do modelo, as instâncias das tarefas, o ambiente, o grader e os prompts que estão fora do componente em teste.
  2. Dê às duas variantes o mesmo orçamento total de tokens, tempo e dinheiro.
  3. Escolha o número de ensaios ou a regra de paragem antes de executar a comparação.
  4. Execute as mesmas instâncias de tarefas nas duas variantes. Como os outputs do modelo variam, repita cada tarefa várias vezes.
  5. Apresente a média juntamente com a dispersão ou o intervalo de confiança.
  6. Conte todos os ensaios iniciados, incluindo timeouts, paragens por política, crashes do harness e falhas do evaluator.

A taxa de sucesso, por si só, pode ocultar um componente dispendioso. No mínimo, acompanhe tarefas partidas aceites como concluídas, custo e wall time por tarefa concluída, erros de tools, encomendas duplicadas, minutos de revisão e overrides manuais de permissões. Escolha a métrica que representa o custo real do seu produto. Um aumento de dois pontos nas tarefas concluídas é uma má troca se duplicar a sua fila de revisão.

Uma experiência emparelhada de migração de pagamento torna mensurável o progress handoff. Cada par de controlo/tratamento começa no mesmo commit do repositório e no mesmo checkpoint semeado, com o mesmo modelo, tarefa, grader e orçamento total. O handoff é a única diferença. A métrica principal conta os tool actions duplicados depois do resume: uma ação é duplicada quando a sua operação e o seu artefacto correspondem a um passo que a sessão anterior já tinha concluído.

O artigo sobre o SWE-agent fixa o GPT-4 Turbo no split de 300 tarefas do SWE-bench Lite e reporta 18,0% resolvidas com a sua interface completa, em comparação com 11,0% para um agent apenas com shell a quem foi dada uma demonstração completa e 7,3% para o mesmo agent sem essa demonstração. A diferença de 10,7 pontos apresentada no artigo é medida contra o baseline de 7,3%; a Parte 3 trabalha os mesmos três números do ponto de vista do design da interface. O artigo também alterou funcionalidades individuais da interface:

Alteração da interfaceResolvidas
Interface completa do SWE-agent (referência, inalterada)18,0%
Editor sem linting15,0%
Ficheiro completo em vez de um viewer de 100 linhas12,7%
Histórico de observações completo em vez das últimas cinco15,0%

Estes números pertencem àquele modelo, benchmark e limite de $4 por tarefa. As três linhas abaixo da referência são os testes úteis de uma só funcionalidade: cada uma alterou uma funcionalidade da interface, mantendo fixos o modelo e a configuração de avaliação.

A LangChain publicou uma comparação com modelo fixo mais abrangente para deepagents-cli. Reporta um aumento no Terminal-Bench 2.0 de 52,8% para 66,5%, com gpt-5.2-codex fixo, enquanto a sua equipa alterou o system prompt, as tools e o middleware. O post combina várias alterações e omite um intervalo de confiança, uma comparação com orçamento total fixo e uma tabela de ablation por alteração. Esse resultado não consegue identificar que alteração ajudou. Os nomes dos modelos nesta secção são os que cada estudo manteve fixos no momento da execução; o que é transferível é o protocolo, não a lista de modelos.

O relatório de uma aplicação de longa duração da Anthropic é um case study qualitativo e específico do produto, não um benchmark controlado. A aplicação é a RetroForge, uma ferramenta para criar jogos retro 2D; no Sprint 3, o evaluator do harness verificou 27 critérios relacionados com o seu editor de níveis. O trabalho começou com modelos Opus anteriores e, quando o Opus 4.6 foi lançado, a equipa removeu componentes do harness, um de cada vez, para verificar quais tinham ficado redundantes com o modelo mais recente. O relatório indica que os calls do evaluator passaram a ser overhead em tarefas que o Opus 4.6 conseguia concluir de forma fiável sozinho, mas que continuavam a ajudar perto do limite do modelo. O exemplo é uma razão para revalidar scaffolding antigo quando o modelo muda; não estima um effect size geral.

Mantenha o harness editável depois de este justificar o seu lugar

A ablation mantém o harness pequeno, mas o seu código pode sobreviver ao modelo para o qual foi afinado. Um pedido como “ocultar secrets em todos os caminhos de captura” nomeia um comportamento, não um ficheiro. Num harness de produção, esse comportamento pode abranger fases de execução e estado partilhado. Antes de o poder alterar em segurança, tem de encontrar todos os locais de implementação — tal como o coding agent a quem delegar essa tarefa.

Um preprint de 2026 de Wang et al., o Harness Handbook, chama a esta pesquisa behavior localization. O handbook constrói um mapa centrado no comportamento a partir da codebase do harness. A análise estática, que não precisa de calls ao modelo, extrai um grafo do programa, e um LLM organiza depois as suas unidades em fases de execução.

O maintainer ou coding agent começa com uma visão geral do sistema, abre a fase de execução relevante e desce até entradas fundamentadas no código-fonte para uma função ou ficheiro. Um registo de estado documenta onde o estado partilhado é escrito e lido entre fases. Esta hierarquia mantém a visão geral pequena, preservando simultaneamente um caminho até ao código-fonte.

A freshness é uma regra separada. Cada locator tem de ser resolvido contra o repositório ativo. O handbook congela entradas obsoletas em vez de adivinhar, e cada diff não vazio ressincroniza as entradas que afeta.

O diagrama comprime o loop de modificação: um pedido apenas sobre o comportamento desce pelos níveis do handbook, cada locator candidato é verificado contra o repositório ativo antes de o plano ser escrito e cada diff aplicado ressincroniza o mapa.

A avaliação do Handbook segue o protocolo defendido neste artigo. Abrange dois harnesses open source: Terminus-2 (seis ficheiros Python) e o monorepo do Codex (2 267 ficheiros Rust). Em cada um, um planner read-only alimentado pelo DeepSeek-V4-Pro explorou diretamente o repositório ou foi encaminhado através do handbook. Os pedidos, o repositório, as permissões das tools e a decoding foram idênticos nos dois braços. Três judges (GPT-5.5, Opus 4.8, DeepSeek-V4-Pro) pontuaram cada plano de edição quanto a localization, controlo do âmbito e reasoning — note que um dos judges é o mesmo modelo que produziu os planos:

HarnessTaxa de vitórias do baselineAssistido pelo handbookTokens do planner
Terminus-2 (6 ficheiros)26,7%45,6%−8,6%
Codex monorepo (2 267 ficheiros)28,3%38,3%−12,7%

O planner assistido pelo handbook ganhou mais vezes e usou menos tokens de planner nos dois repositórios. As condições mantêm-se associadas a esse resultado: três judges LLM pontuaram planos de edição produzidos por um único modelo planner em dois harnesses. O estudo avaliou planos, não diffs executados nem taxas de defeitos em produção.

Experimente o método no companion lab

O projeto harness-demo no commit 517353f3 é um pequeno exercício determinístico com 12 tarefas sintéticas genéricas que abrangem alterações de código como fix-parser-edge-case, split-large-module e wire-browser-test. Não implementa o repositório da loja fictícia.

Cada fixture de tarefa declara uma dificuldade e quatro condições booleanas: uma tool flaky, progresso perdido, uma lacuna de implementação não detetada e conclusão ambígua. O simulador deriva uma quinta condição para tarefas difíceis que também precisam de um ficheiro de progresso: sem context_reset, a compactação preserva pressupostos obsoletos. Um grader determinístico marca uma tarefa como aprovada apenas quando a configuração selecionada trata todas as condições aplicáveis. Não é executado qualquer modelo ou serviço externo.

Os comandos respondem a perguntas diferentes:

  • make check executa Ruff e sete testes unitários, incluindo o validator que rejeita qualquer par de ablation que altere mais do que um componente.
  • make run imprime uma matriz pedagógica cumulativa e, depois, cinco comparações válidas leave-one-component-out.
  • make failures identifica a condição não tratada para cada tarefa falhada. O harness completo deve terminar com all synthetic tasks pass.

Em cada linha, o controlo é a configuração completa com um componente removido; o tratamento repõe apenas esse componente. A matriz cumulativa anterior é útil para orientação, mas algumas das suas linhas adjacentes adicionam vários componentes ao mesmo tempo e, por isso, não conseguem identificar uma causa.

O lab valida cada par declarado antes de o executar. Os seus regression tests também incluem um par intencionalmente inválido que altera simultaneamente a retry policy e o evaluator; o validator rejeita-o.

O lab compara os cinco campos de componentes ao validar um par. Este excerto executável mostra a mesma proteção num par válido de progress handoff:

from dataclasses import dataclass, fields

@dataclass(frozen=True)
class Config:
    progress_handoff: bool = False
    evaluator: bool = False
    retry_policy: bool = False
    fail_closed_acceptance: bool = False
    context_reset: bool = False

def changed_components(control: Config, treatment: Config) -> tuple[str, ...]:
    return tuple(
        field.name
        for field in fields(control)
        if getattr(control, field.name) != getattr(treatment, field.name)
    )

control = Config(progress_handoff=False, evaluator=True, retry_policy=True)
treatment = Config(progress_handoff=True, evaluator=True, retry_policy=True)
assert changed_components(control, treatment) == ("progress_handoff",)

Que camada abrir quando um run corre mal

A série avançou do interior para o exterior, e é aqui que essa ordem compensa. Um run de agent que falha costuma ter um responsável:

O que o run fezOnde vive a correçãoParte
Escolheu um passo seguinte fraco, embora tivesse a informação certa à sua frenteReasoning loop ou modelo1
Repetiu trabalho ou perdeu uma decisão tomada uma hora antesMontagem de contexto e handoffs2
Não conseguiu expressar a ação necessária ou interpretou mal um resultado devolvidoTool contract3
Fez algo que nunca deveria ter podido fazerRegras de permissões4
Perdeu tudo quando um worker morreu a meio de um callSessão, checkpoint, sandbox5
Declarou sucesso num trabalho que não estava concluídoVerificações de aceitação e traces6

Quatro dessas seis linhas são código do harness. A linha 5 é o runtime subjacente, e a linha 1 é a única que um prompt ainda consegue alterar.

Comece com um loop e uma verificação de aceitação

Eu começaria um harness para coding agents com um modelo competente, instruções do repositório, algumas tools restritas, uma sandbox e um teste de aceitação explícito. Registaria os tool calls, os resultados, os custos e esse teste final num único trace, para que as primeiras falhas úteis fossem visíveis sem ter de as reconstruir a partir de logs do terminal e transcripts de chat. Esta é uma baseline proposta, não evidência de um sistema implementado.

A partir daí, adicione apenas aquilo que um trace justificar. Registe quem mantém cada componente, quantos tokens ou segundos acrescenta e que regression test justificaria removê-lo depois de uma atualização do modelo.

Seis meses mais tarde, alguém que veja progress_handoff=True deve conseguir encontrar os traces falhados que justificaram a sua existência e os casos de regressão que ainda o mantêm. Os traces explicam por que razão o componente existe; um mapa de comportamento atual explica onde lhe mexer.

Se chegou aqui através de uma pesquisa, os cinco artigos anteriores construíram um sistema em torno de um reasoning loop:

  1. O loop escolhe o passo seguinte.
  2. A memória fornece contexto e um checkpoint store Postgres real preserva-o.
  3. Os tool contracts definem as ações e os formatos dos resultados que as verificações posteriores podem ler.
  4. A segurança acrescenta o deny hook e o validator de stop-hook. Ambos continuam a ser apenas sketches no exemplo, mas assinalam os pontos de controlo.
  5. O runtime mantém o processo ativo entre sessões e falhas.

A série também acrescentou um sidecar MCP para mostrar onde pertencem os tokens dos data providers e um evaluator node que verifica o draft do relatório antes de este chegar a uma pessoa. São componentes normais de código em torno de um call ao modelo. O router é código do harness pela mesma razão: escolhe o padrão de reasoning antes de o reasoning loop começar.

O próximo passo é instrumentar um pequeno loop. Registe tool calls, resultados, custos e um teste de aceitação explícito. Adicione um único controlo apenas depois de um trace mostrar a falha que este aborda. Compare-o com um controlo fixo e remova-o quando o benefício medido desaparecer.
