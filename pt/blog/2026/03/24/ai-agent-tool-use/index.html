Utilização de Ferramentas por AI Agents em 2026: MCP, CLI, Skills e Execução de Código

Parte 3 da série Engineering the Agentic Stack

Part 1 cobriu reasoning loops, e Part 2 cobriu memória. Este artigo adiciona a camada de ação: como um agent expõe, seleciona e executa tools.

A história das ferramentas mudou em 2025–2026. MCP deu aos vendors um protocolo partilhado para serviços externos. Agents que executam código mostraram que, por vezes, um LLM consegue compor um pequeno programa com mais eficiência do que emitir uma longa sequência de chamadas JSON. A Anthropic reportou uma redução de 98,7% de tokens para um workflow de análise de despesas, e o paper CodeAct reportou ganhos de até 20% na configuração do seu benchmark. Esses resultados descrevem as suas tarefas e harnesses, não uma vantagem universal da execução de código.

Eu comparo JSON tool calling, MCP, Skills, tools de CLI e execução de código por essa ordem. A secção final aplica princípios de Agent-Computer Interface (ACI) ao Market Analyst Agent.

TL;DR: Cinco padrões de interface úteis cobrem a maior parte da utilização de tools por agents. Skills carregam instruções, tools de CLI encaixam no desenvolvimento local, MCP liga serviços partilhados, e a execução de código compõe trabalho multi-etapa dentro de um sandbox. JSON tool calling continua a ser a escolha mais simples para ações atómicas pequenas. Independentemente do protocolo, a Agent-Computer Interface (ACI) tem de tornar as ações claras, feedback compacto e erros recuperáveis.

Cinco formas de AI agents usarem tools

Em Part 1, o reasoning loop escolheu o próximo passo. Part 2 guardou o estado necessário para o retomar. O limite da tool transforma essa decisão numa ação e devolve uma observação ao loop. Estes cinco padrões fazem trade-offs diferentes em custo de tokens, flexibilidade e enforcement.

1. JSON tool calling: o baseline

O padrão original: defines tool schemas em JSON, o LLM emite function calls estruturadas, e o teu código executa-as. É amplamente compreendido e funciona bem para pequenos conjuntos de tools.

# Traditional tool definition — each tool consumes ~550-1,400 tokens (Apideck benchmark)
tools = [
    {
        "name": "get_stock_price",
        "description": "Get the current stock price for a ticker symbol",
        "input_schema": {
            "type": "object",
            "properties": {
                "ticker": {"type": "string", "description": "Stock ticker (e.g., NVDA)"}
            },
            "required": ["ticker"]
        }
    }
]

Com 5-10 tools o overhead é aceitável. O problema é à escala: cada definição de tool custa 550-1,400 tokens. Com 20 tools estás a gastar 15-25K tokens antes de o agent sequer começar a raciocinar.

2. MCP para integrações partilhadas

O Model Context Protocol é o standard em que a maioria dos vendors convergiu. A Anthropic disponibilizou-o à Linux Foundation em Dezembro de 2025, no âmbito da Agentic AI Foundation (AAIF) que co-fundou com OpenAI e Block. Google, Microsoft e AWS apoiam a fundação como membros platinum. A OpenAI adicionou suporte a MCP no seu Responses API. Existem agora 10,000+ servidores MCP ativos e 97M+ downloads mensais de SDK.

O MCP encaixa em integrações SaaS entre vendors (Figma, Notion, Salesforce), serviços sem equivalentes de CLI, e ambientes que precisam de orquestração OAuth. O seu valor é uma camada partilhada de descoberta e transporte. A governação continua a depender dos controlos de autenticação, autorização, logging e deployment do servidor.

A história em produção é mais caótica do que sugerem os números do headline.

A superfície de segurança é o primeiro problema. O Vulnerable MCP Project mapeia 50 vulnerabilidades entre servidores MCP, 13 classificadas como Critical, contribuídas por 32 investigadores de segurança. As classes de ataque abrangem prompt injection, falhas de validação de input, lacunas de autenticação e buracos de segurança de rede. O primeiro servidor MCP malicioso em contexto real surgiu em Setembro de 2025: um pacote chamado postmark-mcp que BCC’d todos os e-mails enviados para o endereço de um atacante, afectando cerca de 300–500 organizações antes da descoberta.

Tool poisoning é a classe de ataque que mais me preocupa. Invariant Labs demonstrou que tools MCP envenenadas podem exfiltrar dados mesmo quando nunca são invocadas. Basta o modelo ler a metadata da tool para despoletar o ataque. MCPTox benchmarks testaram 20 agents LLM contra 45 servidores MCP reais e encontraram taxas de sucesso de ataque até 72.8%.

O overhead de tokens é o problema operacional. Uma equipa a correr servidores MCP para GitHub, Slack e Sentry (~40 tools no total) encontrou 55,000 tokens de definições de schema injectadas antes de um utilizador pedir qualquer coisa. Outra reportou 143,000 de 200,000 tokens disponíveis (72%) consumidos apenas pelas definições das tools.

A Anthropic reportou uma redução de 85% de schemas com a sua Tool Search Tool e uma redução de 96% ao carregar três a cinco tools relevantes para as tarefas avaliadas. O carregamento selectivo mantém a superfície do protocolo enquanto remove schemas que o pedido atual não precisa.

3. Skills: especialização, não execução

O final de 2025 trouxe a estandardização de agent skills como um formato open (lançado em Outubro de 2025, publicado como open standard em Dezembro de 2025). As tools fornecem capacidades (o que os agents conseguem fazer), e as skills fornecem especialização (o que os agents sabem sobre como concretizar tarefas complexas).

O SKILL.md define uma skill como um ficheiro markdown com YAML frontmatter:

---
name: deploy
description: Deploy the application to production
argument-hint: "[environment]"
user-invocable: true
---
Deploy the application to the $0 environment (default: staging).
Steps:
1. Run the test suite
2. Build the production bundle
3. Deploy using the deploy script
4. Verify the deployment health check

Skills usam progressive disclosure. Cerca de 100 tokens de metadata são carregados no arranque; instruções completas só são carregadas quando a skill está activa. Compara isso com os ~55,000 tokens que cerca de 40 tools MCP conseguem consumir antes de iniciar o reasoning.

Em Março de 2026, Claude Code, OpenAI Codex CLI, Cursor, GitHub Copilot, Gemini CLI, Goose, Windsurf e Roo Code tinham adoptado o formato. Victor Dibia descreve essa mudança para ações de agents orientadas por código.

Usa skills para conhecimento de domínio, procedimentos multi-etapa e trabalho recorrente como migrações de bases de dados ou integrações de pagamentos. Funcionam melhor em tarefas em que o agent precisa de instruções de como usar uma capacidade existente.

4. CLI e tools de shell

Interfaces de CLI podem ser muito mais baratas em contexto quando o modelo já conhece o comando. Scalekit reportou uma diferença de 4-32x tokens entre o seu caminho CLI e o caminho MCP ao longo de 75 execuções. Este estudo de caso mede as suas tools e tarefas; não substitui uma comparação nos teus próprios manifests e na saída do comando.

Comandos amplamente documentados como git, docker, kubectl, gh, curl e jq normalmente precisam de pouca introdução em forma de schema. CLIs menos comuns ou internas ainda precisam de ajuda descoberta, exemplos e output estável legível por máquina.

O guia de Ugo Enyioha “Writing CLI Tools That AI Agents Actually Want to Use” codificou oito regras de desenho:

  1. Structured output é obrigatório — suportar --json
  2. Exit codes são controlo de fluxo — usar códigos distintos para diferentes tipos de erro
  3. Commands devem ser idempotentes
  4. Auto-documentação --help com exemplos realistas
  5. Desenhar para composabilidade — --quiet para valores “soltos”, suporte a stdin
  6. Fornecer flags --dry-run e --yes
  7. Suportar introspeção de versões
  8. Tratar auth via variáveis de ambiente

CLI não tem a type safety do MCP, a orquestração OAuth embutida, a descoberta de tools e o audit trail. O padrão para que vejo a maioria das equipas convergir é: CLI como default para desenvolvimento e operações locais, MCP para integrações de serviços externos e governação enterprise.

5. Execução de código para trabalho multi-etapa

Esta é a mudança em tooling de agents que considero mais consequente. Em vez de emitir JSON estruturado para invocar funções predefinidas uma a uma, o agent escreve um script Python ou bash. O script chama múltiplas tools, processa resultados com loops e condicionais, e devolve apenas o resumo final ao contexto do modelo.

A Anthropic formalizou isto com Programmatic Tool Calling (PTC), agora GA na Claude API. A fundação académica é o CodeAct paper (Wang et al., ICML 2024), que testou em 17 LLMs e encontrou que ações de código atingem até 20% taxas de sucesso mais altas e 30% menos passos do que alternativas em JSON.

Três estudos de caso “first-party” mostram onde o padrão pode ajudar: Vercel e Cloudflare abaixo, e depois o exemplo de análise de despesas da Anthropic. Trata-os como evidência de vendor e reexecuta a comparação nas tuas tarefas.

  • Vercel reimplementou o seu d0 text-to-SQL agent removendo 80% das suas tools (de 15 para 2: ExecuteCommand e ExecuteSQL). O sucesso da tarefa subiu de 80% para 100%, o tempo de execução caiu 3,5x, e o uso de tokens baixou 40%. A sua formulação: “Os melhores agents podem ser os que têm o menor número de tools.”

  • Cloudflare desenvolveu “Code Mode,” permitindo que os agents escrevam TypeScript para chamar a sua API em vez de definirem tool schemas, o que reduz overhead de contexto. A sua linha de raciocínio: “LLMs têm uma quantidade enorme de TypeScript real no seu conjunto de treino, mas apenas um conjunto pequeno de exemplos contrived de tool calls.”

Aqui está o padrão da documentação do PTC da Anthropic. Tool calling tradicional para análise de despesas requer 20+ passes de inferência separados, um por membro da equipa, com todos os dados intermédios a fluir pelo contexto. Um workflow que consome ~150,000 tokens com tool calling directo foi reimplementado para ~2,000 tokens, uma redução de 98,7%. Com execução de código, o agent escreve um único script:

# Agent generates this code, executes in sandbox
import json
members = get_team_members("engineering")
over_budget = []
for m in members:
    expenses = get_expenses(m["id"], "Q3")
    total = sum(e["amount"] for e in expenses)
    if total > 5000:
        custom = get_custom_budget(m["id"])
        limit = custom["limit"] if custom else 5000
        if total > limit:
            over_budget.append({"name": m["name"], "spent": total, "limit": limit})
# Only this final summary returns to the LLM context
print(json.dumps(over_budget))

O LLM vê apenas o resumo JSON final, e não as milhares de linhas de despesas processadas no sandbox. O ganho óbvio é a eficiência de tokens. Loops e condicionais “custam” zero em termos de turning passes adicionais, erros passam por try/except em vez de reasoning em linguagem natural sobre falhas, e dados sensíveis ficam no sandbox.

Quando JSON tool calling ainda faz sentido: operações únicas atómicas, ambientes sem infraestrutura de sandboxing, modelos mais pequenos com fraca geração de código, ou requisitos de audit que precisam de cada invocação individual de tool registada.

A Agent-Computer Interface (ACI) para tools de AI agents

O termo “Agent-Computer Interface” (ACI) foi cunhado por John Yang, Carlos E. Jimenez, e colegas na Princeton, no seu SWE-agent paper (NeurIPS 2024). Tal como humanos beneficiam de interfaces bem desenhadas (HCI), o paper argumenta que agents de LM são “uma nova categoria de utilizadores finais com necessidades e capacidades próprias, que beneficiariam de interfaces especialmente construídas.”

Os seus resultados de ablation colocam números nisso. SWE-agent com a sua ACI completa atingiu 18,0% no SWE-bench Lite versus 7,3% apenas com uma Linux shell standard, uma melhoria de 10,7 pontos percentuais que vem apenas do desenho de interface. O guardrail de linting sozinho contribuiu com 3 pontos percentuais: 51,7% das edições do agent continham pelo menos um erro apanhado pelo linter antes de se propagar.

A Anthropic adoptou a ACI como conceito fundacional no seu guia “Building Effective Agents”, listando-a como um dos três princípios centrais: “Carefully craft your agent-computer interface through thorough tool documentation and testing.” A orientação prática: “Uma regra de bolso é pensar no esforço envolvido em interfaces humano-computador, e planear investir o mesmo esforço em criar boas agent-computer interfaces.”

Quatro princípios ACI na prática

1. As ações devem ser simples e fáceis de entender. O erro mais comum é embrulhar endpoints de API um-para-um. Em vez de list_users, list_events, create_event, implementa schedule_event que encontra disponibilidade e agenda em uma chamada. Em vez de read_logs, implementa search_logs que devolve apenas as linhas relevantes com contexto.

2. As ações devem ser compactas e eficientes. Consolida operações importantes no menor número possível de ações. No Market Analyst Agent, combino a recolha de preço com métricas básicas numa única tool get_stock_snapshot em vez de exigir chamadas separadas para preço, volume, market cap e PE ratio.

3. O feedback do ambiente deve ser informativo mas conciso. Evita devolver HTML bruto ou payloads completos de API. Resolve IDs crípticos para nomes semânticos. Testes da Anthropic adicionaram um response_format enum para o agent poder pedir uma resposta concisa (~72 tokens) ou detalhada (~206 tokens), cerca de 3x de diferença de custo de tokens. Reportaram melhor performance em contexto real.

4. Guardrails devem mitigar propagação de erros. Detecção automática de erros ajuda os agents a reconhecer e corrigir erros rapidamente. No SWE-agent, um editor de ficheiros custom com linting integrado rejeita automaticamente erros de sintaxe, apanhando pelo menos um erro em 51,7% das edições do agent antes de poder acumular. Aplico o mesmo princípio no Market Analyst Agent validando argumentos das tools com Pydantic schemas antes de executar:

from pydantic import BaseModel, Field, field_validator

class StockQuery(BaseModel):
    """Validated input for stock queries.

    Pydantic catches malformed tickers before the API call,
    preventing error propagation through the reasoning loop.
    """
    ticker: str = Field(description="Stock ticker symbol (e.g., NVDA)")
    period: str = Field(default="1mo", description="Time period: 1d, 5d, 1mo, 3mo, 1y")

    @field_validator("ticker")
    @classmethod
    def validate_ticker(cls, v: str) -> str:
        v = v.upper().strip()
        if not v.isalpha() or len(v) > 5:
            raise ValueError(f"Invalid ticker format: {v}")
        return v

    @field_validator("period")
    @classmethod
    def validate_period(cls, v: str) -> str:
        valid = {"1d", "5d", "1mo", "3mo", "6mo", "1y", "5y"}
        if v not in valid:
            raise ValueError(f"Invalid period: {v}. Must be one of {valid}")
        return v

Padrões de desenho de tools de AI agents que funcionam

O guia da Anthropic “Writing effective tools for agents” enquadra tools como “um novo tipo de software que reflete um contrato entre sistemas determinísticos e agents não-determinísticos.”

Tratar descrições de tools como prompt engineering

As descrições devem correr 3-4+ sentenças no mínimo, cobrindo quando usar a tool, parâmetros obrigatórios versus opcionais, formato de output e casos de canto. Atribuir nomes com prefixes (asana_search, jira_search) tem “efeitos não-triviais” na precisão da seleção de tools. Nos experimentos da Anthropic, descrições de tools optimizadas para Claude superaram descrições escritas por especialistas humanos em benchmarks de avaliação.

# Bad: vague, no context for when to use
tools = [{
    "name": "search",
    "description": "Search for items",
}]

# Good: specific, with input examples and edge cases
tools = [{
    "name": "stock_search_news",
    "description": (
        "Search for recent news articles about a specific stock or company. "
        "Use this tool when the user asks about recent events, earnings, "
        "announcements, or market-moving news for a specific ticker. "
        "Returns up to 10 articles sorted by relevance. "
        "For broad market news (not ticker-specific), use market_overview instead."
    ),
    "input_schema": {
        "type": "object",
        "properties": {
            "query": {
                "type": "string",
                "description": "Search query. Examples: 'NVDA earnings Q3 2025', 'Tesla delivery numbers'"
            },
            "max_results": {
                "type": "integer",
                "description": "Max articles to return (1-10, default 5)",
                "default": 5
            }
        },
        "required": ["query"]
    }
}]

Testing interno mostrou que exemplos de input (input_examples field) melhoram substancialmente a precisão no tratamento de parâmetros complexos.

Devolver output de alto sinal e legível por máquina

Evita identificadores de baixo nível (uuid, mime_type). Resolve IDs crípticos para nomes semânticos. Estrutura a resposta para que o agent consiga raciocinar sobre ela sem ter de fazer parsing de boilerplate:

# Bad: raw API response dumped to agent
def get_stock_price(ticker: str) -> dict:
    response = api.get(f"/v1/quotes/{ticker}")
    return response.json()  # 500+ tokens of nested JSON

# Good: high-signal summary the agent can immediately reason about
def get_stock_price(ticker: str) -> dict:
    data = api.get(f"/v1/quotes/{ticker}").json()
    return {
        "ticker": ticker,
        "price": data["regularMarketPrice"],
        "change_pct": round(data["regularMarketChangePercent"], 2),
        "volume": data["regularMarketVolume"],
        "market_cap_b": round(data["marketCap"] / 1e9, 1),
        "pe_ratio": data.get("trailingPE"),
        "summary": f"{ticker} at ${data['regularMarketPrice']:.2f} "
                   f"({'up' if data['regularMarketChangePercent'] > 0 else 'down'} "
                   f"{abs(data['regularMarketChangePercent']):.1f}%)"
    }

Devolver erros que o loop consiga tratar

Usa quatro mecanismos separados porque tratam classes diferentes de falha:

  1. Retry com exponential backoff para erros transitórios
  2. Model fallback chains para outages do provider
  3. Error classification routing — erros transitórios fazem retry; erros que o LLM consegue recuperar devolvem ao agent com contexto; erros que exigem intervenção humana escalam
  4. Recuperação por checkpoint para sobreviver a crash

O guia da Anthropic citado suporta erros claros das tools e um desenho orientado por avaliação. Não estabelece uma redução universal da taxa de falhas, por isso mede taxa de recuperação, retries e escalonamento nas tuas próprias tarefas.

from tenacity import retry, stop_after_attempt, wait_exponential

@retry(
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=1, min=2, max=10),
)
def call_stock_api(ticker: str) -> dict:
    """Fetch stock data with automatic retry on transient failures.

    Layer 1: Exponential backoff handles rate limits and network blips.
    If all retries fail, the error propagates to the agent with
    enough context to decide whether to try a different approach.
    """
    response = httpx.get(
        f"https://api.example.com/v1/quotes/{ticker}",
        timeout=10.0,
    )
    response.raise_for_status()
    return response.json()

O Market Analyst Agent de Part 1 torna o efeito da interface visível.

Cada uma era um wrapper fino em torno de um único endpoint de API. O agent tinha de raciocinar qual combinação chamar em cada pedido.

Outputs estruturados para resultados de tools

Cada tool no Market Analyst Agent devolve uma resposta validada por Pydantic. Isto aplica o princípio de guardrails ACI no limite da tool:

class StockSnapshot(BaseModel):
    """Structured tool response — the agent never sees raw API noise."""
    ticker: str
    price: float
    change_pct: float
    volume: int
    market_cap_b: float
    pe_ratio: float | None
    summary: str  # Human-readable one-liner for direct use in reports

class NewsResult(BaseModel):
    """Each news item is pre-processed for agent consumption."""
    headline: str
    source: str
    date: str
    relevance_score: float  # Pre-ranked so the agent doesn't waste tokens sorting
    key_points: list[str]  # Extracted by the tool, not the agent

O campo summary é o mais importante. Fornece ao agent uma string pronta a usar que pode ir diretamente para um relatório sem processamento adicional. O key_points em NewsResult é extraído no lado do servidor, poupando o agent de gastar tokens de inferência a fazer parsing de corpos de artigos.

Compensações e considerações

Para além das limitações específicas da modalidade acima, há algumas preocupações transversais que moldam a escolha:

  • O custo operacional varia por dimensão. Execução de código poupa tokens, mas adiciona latência de cold-start do sandbox. MCP poupa tempo de desenvolvimento para integrações SaaS, mas adiciona overhead de deployment de server. CLI é “grátis” para arrancar, mas é mais difícil de governar à escala. Optimiza para o teu bottleneck real, seja custo de tokens, latência ou complexidade operacional.

  • As skills da equipa importam. Execução de código assume que os teus agents (e os modelos por trás) conseguem gerar Python ou TypeScript de forma fiável. CLI assume familiaridade com convenções Unix. MCP requer compreender protocolos de transporte e flows OAuth. Faz match da modalidade com as forças da tua equipa.

  • Consolidação de tools pode ir longe demais. Se uma tool acumular modos e argumentos não relacionados, o agent enfrenta um problema de seleção diferente dentro do schema. Usa tool-selection e task-success evaluations para encontrar a superfície certa para a tua carga de trabalho.

  • Skills são prompt-based, não enforcement. Uma skill é instruções que o agent deveria seguir, não guardrails que o agent tem de seguir. Para workflows críticos, combina skills com validação determinística.

  • Requisitos de audit moldam a escolha. Se precisas de um log completo de cada invocação de tool e do seu resultado, MCP e JSON tool calling fornecem audit trails estruturados “out of the box”. Execução de código gera um script e a sua saída, o que é útil, mas é mais difícil de decompor em ações individuais para reporting de compliance.

Tool selection em escala maior

Há três direções que vale a pena acompanhar.

A primeira é tool RAG para escalar. À medida que os toolsets crescem para centenas ou milhares, a precisão de tool selection ingênua degrada para 13,62%. O RAG-MCP paper aplicou retrieval-augmented generation à tool selection: indexa as descrições das tools numa base de dados vectorial e recupera apenas as relevantes por query. Chegou a 43,13% de acurácia, uma melhoria de 3,2x, ao mesmo tempo que cortou ~50% dos prompt tokens.

A segunda é agents a criarem as suas próprias tools. O LATM framework (“LLMs As Tool Makers”) estabeleceu um paradigma em duas fases: um LLM poderoso cria funções Python reutilizáveis e um LLM leve usa-as. ToolMaker (ACL 2025) transforma autonomamente repositórios GitHub em tools compatíveis com LLM, com 80% de sucesso. Ambos apontam para além do uso de tools, rumo à criação de tools — e depois para gerir uma biblioteca de tools geradas.

A terceira é o stack dual-protocol A2A + MCP. Google’s Agent2Agent Protocol (A2A) endereça aquilo que o MCP não consegue: comunicação de agent para agent. MCP lida com agent-to-tool integration; A2A lida com agent-to-agent discovery, negociação e delegação de tarefas.

Principais conclusões

  1. Escolhe a interface pela ação: JSON calling para operações pequenas tipadas, MCP para serviços partilhados, Skills para procedimentos, CLI para comandos estabelecidos, e código em sandbox para composição local.
  2. Mantém as condições do benchmark associadas ao resultado. CodeAct, Anthropic, Vercel, Cloudflare, Apideck e Scalekit mediram modelos, tarefas, tools e harnesses diferentes.
  3. A qualidade ACI sobrevive a mudanças de protocolo. Ações claras, feedback compacto, validação e erros úteis ajudam qualquer modalidade.
  4. Consolida tools sobrepostas apenas quando avaliações mostram que a superfície menor melhora seleção ou sucesso da tarefa.
  5. A segurança anda com o poder de execução. Interfaces de shell e código precisam de sandboxing; MCP precisa de identidade com scope e política do server; Skills continuam a ser instruções em vez de enforcement.
