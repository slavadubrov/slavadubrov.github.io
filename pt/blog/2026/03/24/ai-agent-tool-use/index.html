Utilização de ferramentas por agentes de IA: MCP, CLI, Skills e execução de código

Parte 3 da série Engineering the Agentic Stack

A Parte 1 abordou os ciclos de raciocínio, e a Parte 2 abordou a memória. Este artigo acrescenta a camada de ação: como um agente expõe, seleciona e executa ferramentas. A memória determina o que o agente sabe ao iniciar um turno; esta camada determina o que pode fazer com esse conhecimento. A Parte 4 aborda a verificação que determina se uma chamada nomeada chega sequer a ser executada, e a Parte 6 aborda o harness que executa tanto a chamada como a verificação. Ao longo deste artigo, harness significa o programa de controlo que compõe cada prompt, despacha as chamadas de ferramentas que aceita e decide quando a tarefa está concluída — tudo o que envolve o modelo e que corresponde a código convencional escrito por si.

A abordagem às ferramentas mudou em 2025–2026. O MCP, Model Context Protocol, proporcionou aos fornecedores uma forma partilhada de expor serviços externos. Os agentes com execução de código demonstraram que, por vezes, um modelo consegue compor um pequeno programa de forma mais eficiente do que emitir uma longa sequência de chamadas JSON. A Anthropic reportou uma redução de 98,7% nos tokens num workflow do Google Drive para o Salesforce, e o artigo CodeAct reportou melhorias de até 20% na configuração do seu benchmark. Estes resultados descrevem as respetivas tarefas e harnesses, não uma vantagem universal da execução de código.

Comparo, por esta ordem, chamadas de ferramentas JSON, MCP, Skills, ferramentas CLI e execução de código. Uma secção posterior aplica princípios de design da Agent-Computer Interface (ACI) ao Market Analyst Agent, um pequeno agente de investigação construído com LangGraph que desenvolvi para a Parte 1 e que obtém dados de mercado e redige um relatório de analista.

Para uma decisão rápida sobre interfaces, consulte AI Agent Tool Interfaces.

Em resumo: Cinco padrões de interface úteis abrangem a maioria dos casos de utilização de ferramentas por agentes. As Skills transportam instruções, as ferramentas CLI adequam-se ao desenvolvimento local, o MCP liga serviços partilhados e a execução de código compõe trabalho em várias etapas dentro de uma sandbox. As chamadas de ferramentas JSON continuam a ser a opção mais simples para ações atómicas de pequena dimensão. Seja qual for o protocolo, a Agent-Computer Interface (ACI) deve tornar as ações claras, manter o feedback compacto e permitir a recuperação de erros.

Cinco formas de os agentes de IA utilizarem ferramentas

Na Parte 1, o ciclo de raciocínio escolhia o passo seguinte. A Parte 2 armazenava o estado necessário para o retomar. A fronteira das ferramentas situa-se entre ambos: valida o que o ciclo propôs, encaminha a chamada para execução e devolve o resultado ao ciclo. Estes cinco padrões fazem compromissos diferentes em termos de custo de tokens, flexibilidade e controlo.

1. Chamadas de ferramentas JSON: a referência

O padrão original: define esquemas de ferramentas em JSON, o LLM emite chamadas de funções estruturadas e o seu código executa-as. É uma abordagem bem conhecida e funciona bem para conjuntos pequenos de ferramentas.

# Traditional tool definition — each tool consumes ~550-1,400 tokens (Apideck benchmark)
tools = [
    {
        "name": "get_stock_price",
        "description": "Get the current stock price for a ticker symbol",
        "input_schema": {
            "type": "object",
            "properties": {
                "ticker": {"type": "string", "description": "Stock ticker (e.g., NVDA)"}
            },
            "required": ["ticker"]
        }
    }
]

Com 5–10 ferramentas, a sobrecarga é aceitável. O problema surge à escala: cada definição de ferramenta custa 550–1 400 tokens. Com 20 ferramentas, está a gastar 11–28 mil tokens antes de o agente sequer começar a raciocinar.

2. MCP para integrações partilhadas

O MCP é o padrão para o qual convergiram a maioria dos fornecedores. Um servidor MCP é um processo que anuncia uma lista de ferramentas através de um protocolo de comunicação definido — stdio para um processo local, HTTP para um remoto. O seu agente executa um cliente MCP que estabelece ligação, pergunta ao servidor que ferramentas disponibiliza e encaminha para este as chamadas do modelo, pelo que o mesmo servidor funciona com qualquer cliente compatível com o protocolo. Em dezembro de 2025, a Anthropic doou o protocolo à Linux Foundation, no âmbito da Agentic AI Foundation, que cofundou com a OpenAI e a Block. A Google, a Microsoft e a AWS apoiam a fundação como membros platinum. A OpenAI adicionou suporte para MCP à sua Responses API. À data do anúncio da doação da Anthropic em dezembro de 2025, o ecossistema contabilizava mais de 10 000 servidores MCP públicos ativos e mais de 97 milhões de downloads mensais dos SDKs de Python e TypeScript.

O MCP é adequado para integrações SaaS entre fornecedores (Figma, Notion, Salesforce), serviços sem equivalentes em CLI e ambientes que necessitam de orquestração OAuth. O seu valor está numa camada partilhada de descoberta e transporte. A governação continua a depender dos controlos de autenticação, autorização, logging e deployment do servidor.

A realidade em produção é mais complexa do que os números de destaque sugerem.

A superfície de segurança é o primeiro problema. O Vulnerable MCP Project acompanha 50 vulnerabilidades em servidores MCP, 13 classificadas como Critical, identificadas por 32 investigadores de segurança. As classes de ataque incluem prompt injection, falhas de validação de input, lacunas de autenticação e vulnerabilidades de segurança de rede. O primeiro servidor MCP malicioso no mundo real surgiu em setembro de 2025: um package chamado postmark-mcp que enviava em BCC todos os emails enviados para o endereço do atacante, afetando cerca de 300–500 organizações antes de ser descoberto.

Tool poisoning é a classe de ataque que mais me preocupa. A Invariant Labs demonstrou que ferramentas MCP envenenadas podem exfiltrar dados mesmo quando nunca são invocadas. Basta o modelo ler os metadados da ferramenta para desencadear o ataque. Os benchmarks MCPTox, que testaram 20 agentes LLM contra 45 servidores MCP reais, encontraram taxas de sucesso dos ataques de até 72,8%.

O overhead de tokens é o problema operacional. Uma equipa que executava servidores MCP para GitHub, Slack e Sentry (cerca de 40 ferramentas no total) descobriu que 55 000 tokens de definições de schemas eram injetados antes de o utilizador fazer qualquer pergunta. Outra equipa reportou que 143 000 dos 200 000 tokens disponíveis (72%) eram consumidos apenas pelas definições das ferramentas.

A Anthropic reportou uma redução de 85% nos tokens das definições de ferramentas com o seu Tool Search Tool — aproximadamente 77 000 tokens de schemas passaram para 8 700 — ao carregar apenas as três a cinco ferramentas de que um pedido realmente necessita. O carregamento seletivo mantém a superfície do protocolo, eliminando os schemas de que o pedido atual não precisa.

3. As skills empacotam conhecimento especializado, não execução

O final de 2025 trouxe a normalização das agent skills como um formato aberto (lançado em outubro de 2025 e publicado como padrão aberto em dezembro de 2025). As ferramentas fornecem capacidades (o que os agentes podem fazer) e as skills fornecem conhecimento especializado (o que os agentes sabem sobre como realizar tarefas complexas).

O formato SKILL.md define uma skill como um ficheiro Markdown com YAML frontmatter. O standard aberto exige apenas name e description; o exemplo abaixo utiliza também duas extensões do Claude Code, argument-hint e user-invocable, além do seu placeholder de argumento posicional $0:

---
name: deploy
description: Deploy the application to production
argument-hint: "[environment]"
user-invocable: true
---
Deploy the application to the $0 environment (default: staging).
Steps:
1. Run the test suite
2. Build the production bundle
3. Deploy using the deploy script
4. Verify the deployment health check

As skills utilizam divulgação progressiva. Cerca de 100 tokens de metadados são carregados no arranque; as instruções completas só são carregadas quando a skill está ativa. Compare-se com os aproximadamente 55 000 tokens que cerca de 40 ferramentas MCP podem consumir antes de o raciocínio começar.

Em março de 2026, Claude Code, OpenAI Codex CLI, Cursor, GitHub Copilot, Gemini CLI, Goose, Devin Desktop (então Windsurf) e Roo Code tinham adotado o formato. As skills integram uma mudança mais ampla para ações de agentes orientadas por código, que Victor Dibia traça desde chamadas de funções JSON até código gerado — o padrão abordado na secção 5.

Utilize skills para conhecimento de domínio, procedimentos com várias etapas e tarefas recorrentes, como migrações de bases de dados ou integrações de pagamentos. São adequadas para tarefas em que o agente precisa de instruções sobre como utilizar uma capacidade existente.

4. Ferramentas CLI e shell

As interfaces CLI podem consumir muito menos contexto quando o modelo já conhece o comando. A Scalekit reportou uma diferença de 4 a 32 vezes no número de tokens entre os seus percursos CLI e MCP, em 75 execuções. Esse estudo de caso mede as respetivas ferramentas e tarefas; não substitui uma comparação com as suas próprias definições de ferramentas e resultados dos comandos.

Comandos amplamente documentados, como git, docker, kubectl, gh, curl e jq, geralmente precisam de pouco texto de schema introdutório. As CLI menos comuns ou internas continuam a precisar de ajuda pesquisável, exemplos e resultados estáveis e legíveis por máquina.

O guia de Ugo Enyioha, “Writing CLI Tools That AI Agents Actually Want to Use”, formalizou oito regras de design:

  1. O output estruturado é obrigatório — suporte para --json
  2. Os códigos de saída são controlo de fluxo — utilize códigos distintos para diferentes tipos de erro
  3. Os comandos devem ser idempotentes
  4. Documentação autónoma --help com exemplos realistas
  5. Conceba para a composabilidade — --quiet para valores simples e suporte para stdin
  6. Disponibilize as flags --dry-run e --yes
  7. Suporte introspeção da versão
  8. Faça a autenticação através de variáveis de ambiente

A CLI não dispõe da segurança de tipos, da orquestração OAuth integrada, da descoberta de ferramentas e do registo de auditoria do MCP. O padrão para o qual vejo a maioria das equipas convergir é: CLI como opção predefinida para desenvolvimento e operações locais; MCP para integração com serviços externos e governação empresarial.

5. Execução de código para tarefas com várias etapas

Esta é a mudança nas ferramentas de agentes que considero mais significativa. Em vez de emitir JSON estruturado para invocar funções predefinidas uma de cada vez, o agente escreve um script Python ou bash. O script chama várias ferramentas, processa os resultados com ciclos e condicionais e devolve ao contexto do modelo apenas o resumo final.

A Anthropic formalizou isto com o Programmatic Tool Calling (PTC), agora geralmente disponível na API do Claude. A base académica é o artigo CodeAct (Wang et al., ICML 2024), que avaliou 17 LLMs e concluiu que as ações em código alcançaram taxas de sucesso até 20% superiores e exigiram 30% menos passos do que as alternativas baseadas em JSON.

Três estudos de caso de primeira mão mostram onde este padrão pode ser útil: os da Vercel e da Cloudflare abaixo, seguidos do exemplo de análise de despesas da Anthropic. Considere-os evidência dos fornecedores e repita a comparação nas suas próprias tarefas.

  • A Vercel reconstruiu o d0, o seu agente de dados de linguagem natural para SQL, reduzindo-o de 15 ferramentas para 2 — ExecuteCommand e ExecuteSQL —, uma redução que a publicação arredonda para 80%. Em cinco consultas representativas, o sucesso das tarefas passou de 4/5 para 5/5, o tempo médio de execução diminuiu 3,5 vezes (de 274,8 s para 77,4 s) e o consumo médio de tokens baixou 37% (de ~102 mil para ~61 mil). Nas palavras da própria Vercel: «Os melhores agentes podem ser os que têm menos ferramentas.»

  • A Cloudflare desenvolveu o «Code Mode», permitindo que os agentes escrevam TypeScript para chamar a sua API, em vez de definirem esquemas de ferramentas, o que reduz o overhead de contexto. O raciocínio apresentado é: «Os LLMs têm uma quantidade enorme de TypeScript do mundo real no seu conjunto de treino, mas apenas um pequeno conjunto de exemplos artificiais de chamadas a ferramentas.»

Eis o padrão descrito na documentação de PTC da Anthropic. A chamada tradicional de ferramentas para análise de despesas exige mais de 20 passagens de inferência separadas, uma por membro da equipa, com todos os dados intermédios a passarem pelo contexto. A Anthropic relata que o código gerado para responder à mesma pergunta reduz o que chega ao contexto de 200 KB de linhas de despesas em bruto — mais de 2 000 itens — para 1 KB de resultados. Com execução de código, o agente escreve um único script:

# Agent generates this code, executes in sandbox
import json
members = get_team_members("engineering")
over_budget = []
for m in members:
    expenses = get_expenses(m["id"], "Q3")
    total = sum(e["amount"] for e in expenses)
    if total > 5000:
        custom = get_custom_budget(m["id"])
        limit = custom["limit"] if custom else 5000
        if total > limit:
            over_budget.append({"name": m["name"], "spent": total, "limit": limit})
# Only this final summary returns to the LLM context
print(json.dumps(over_budget))

O LLM vê apenas o resumo JSON final, não os milhares de itens de despesas processados na sandbox. A poupança não é específica de relatórios de despesas: a análise separada da Anthropic sobre execução de código apresenta o número mais expressivo para este padrão: um fluxo de trabalho do Google Drive para o Salesforce que passou de ~150 000 tokens para ~2 000, uma redução de 98,7%.

A eficiência em tokens é o ganho mais evidente. Os ciclos e as condicionais não têm custo adicional, os erros passam por try/except em vez de exigirem raciocínio em linguagem natural sobre falhas, e os dados sensíveis permanecem na sandbox.

Quando a chamada de ferramentas em JSON continua a fazer sentido: operações atómicas únicas, ambientes sem infraestrutura de sandboxing, modelos mais pequenos com fraca capacidade de geração de código ou requisitos de auditoria que exijam o registo de cada invocação individual de ferramentas.

“Meta-tools”, na linha relativa ao overhead de tokens, refere-se às poucas entry points genéricas de que um agente com execução de código necessita — ExecuteCommand e ExecuteSQL da Vercel, por exemplo — em vez de um schema por cada operação subjacente. Aqui, composabilidade significa a facilidade com que várias operações podem ser encadeadas num workflow maior. Baixa significa que cada chamada de ferramenta normalmente requer outra round trip ao modelo; elevada significa que a interface consegue transmitir resultados intermédios através de pipes, variáveis ou passos procedurais. As células relativas aos tokens e ao sucesso das tarefas resumem os exemplos citados, não um benchmark controlado único que abranja as cinco colunas.

A Agent-Computer Interface (ACI) para ferramentas de agentes de IA

O termo “Agent-Computer Interface” (ACI) foi cunhado por John Yang, Carlos E. Jimenez e colegas de Princeton no seu artigo sobre o SWE-agent (NeurIPS 2024). A qualidade das interfaces destinadas a humanos tem toda uma área dedicada — a interação humano-computador, ou HCI. O artigo defende que os agentes baseados em modelos de linguagem merecem o mesmo tratamento: são “uma nova categoria de utilizadores finais, com necessidades e capacidades próprias, e beneficiariam de interfaces concebidas especificamente para eles.”

Os seus resultados de ablação quantificam essa diferença. Usando o mesmo modelo base GPT-4 Turbo, a ablação do artigo no SWE-bench Lite atingiu 18,0% com o ACI completo do SWE-agent em 300 tarefas, contra 7,3% na condição apenas com shell, sem uma demonstração trabalhada, e 11,0% com uma. A comparação mostra que a interface e as condições da demonstração alteraram materialmente o desempenho nesta configuração; não isola o design da interface de todas as outras diferenças, nem demonstra que o modelo não realizou trabalho. Na mesma ablação da interface, ativar o linting aumentou a condição de edição de 15,0% para 18,0%; em todo o conjunto de teste do SWE-bench, 51,7% das execuções do SWE-agent incluíram pelo menos uma edição que o linter rejeitou antes de esta poder propagar-se.

A Anthropic adotou o ACI como conceito fundamental no seu guia “Building Effective Agents”, apresentando-o como um dos três princípios essenciais: «Crie cuidadosamente a interface entre o agente e o computador, através de documentação e testes exaustivos das ferramentas.» A sua orientação prática é: «Uma regra prática consiste em pensar no esforço dedicado às interfaces homem-computador e planear investir o mesmo esforço na criação de boas interfaces entre agentes e computadores.»

Quatro princípios de ACI na prática

1. As ações devem ser simples e fáceis de compreender. O erro mais comum consiste em encapsular endpoints de API numa correspondência um-para-um. Em vez de list_users, list_events, create_event, implemente schedule_event, que encontra a disponibilidade e agenda tudo numa única chamada. Em vez de read_logs, implemente search_logs, que devolve apenas as linhas relevantes, com contexto.

2. As ações devem ser compactas e eficientes. Consolide as operações importantes no menor número possível de ações. No Market Analyst Agent, combino a obtenção de preços com métricas básicas numa única ferramenta get_stock_snapshot, em vez de exigir chamadas separadas para o preço, o volume, a capitalização bolsista e o rácio PE.

3. O feedback do ambiente deve ser informativo, mas conciso. Evite devolver HTML bruto ou payloads completos da API. Resolva IDs crípticos para nomes semânticos. Os testes da Anthropic adicionaram um enum response_format, para que o agente possa solicitar uma resposta concisa (~72 tokens) ou detalhada (~206 tokens), uma diferença de aproximadamente 3x no custo em tokens.

4. A validação deve reduzir a propagação de erros. A deteção automática de erros ajuda os agentes a reconhecer e corrigir rapidamente os seus enganos. No SWE-agent, um editor de ficheiros personalizado com linting integrado rejeita automaticamente erros de sintaxe — o passo de validação por detrás do valor de 51,7% acima. Trata-se da validação das entradas e saídas de uma ferramenta, não da filtragem de conteúdo em torno de uma chamada ao modelo realizada pelos produtos de guardrails da Parte 4; a mesma palavra é utilizada para ambos os casos. Aplico o mesmo princípio no Market Analyst Agent, validando os argumentos das ferramentas com schemas Pydantic antes da execução:

from pydantic import BaseModel, Field, field_validator

class StockQuery(BaseModel):
    """Validated input for stock queries.

    Pydantic catches malformed tickers before the API call,
    preventing error propagation through the reasoning loop.
    """
    ticker: str = Field(description="Stock ticker symbol (e.g., NVDA)")
    period: str = Field(default="1mo", description="Time period: 1d, 5d, 1mo, 3mo, 6mo, 1y")

    @field_validator("ticker")
    @classmethod
    def validate_ticker(cls, v: str) -> str:
        v = v.upper().strip()
        if not v.isalpha() or len(v) > 5:
            raise ValueError(f"Invalid ticker format: {v}")
        return v

    @field_validator("period")
    @classmethod
    def validate_period(cls, v: str) -> str:
        valid = {"1d", "5d", "1mo", "3mo", "6mo", "1y"}
        if v not in valid:
            raise ValueError(f"Invalid period: {v}. Must be one of {valid}")
        return v

Padrões de design de ferramentas para agentes de IA que funcionam

O guia da Anthropic “Writing effective tools for agents” descreve as ferramentas como «um novo tipo de software que reflete um contrato entre sistemas determinísticos e agentes não determinísticos.»

Tratar as descrições das ferramentas como engenharia de prompts

As descrições devem ter pelo menos três ou quatro frases, abrangendo quando utilizar a ferramenta, os parâmetros obrigatórios e opcionais, o formato do resultado e os casos-limite. A Anthropic relata que a escolha entre namespacing baseado em prefixos e em sufixos (asana_search versus search_asana) teve “efeitos não triviais” nas suas próprias avaliações de utilização de ferramentas. Não indica qual dos esquemas é superior; por isso, teste ambos no seu conjunto de ferramentas em vez de assumir que os prefixos são melhores. A Anthropic também introduziu as transcrições dos seus agentes de avaliação no Claude Code e permitiu que este reescrevesse as ferramentas. Nos conjuntos de testes reservados, esse ciclo encontrou melhorias adicionais “mesmo para além do que conseguimos com implementações de ferramentas ‘especializadas’” — quer essas ferramentas tivessem sido escritas manualmente pelos seus investigadores, quer geradas pelo Claude.

# Bad: vague, no context for when to use
tools = [{
    "name": "search",
    "description": "Search for items",
}]

# Good: specific, with input examples and edge cases
tools = [{
    "name": "search_news",
    "description": (
        "Search for recent news articles about a specific stock or company. "
        "Use this tool when the user asks about recent events, earnings, "
        "announcements, or market-moving news for a specific ticker. "
        "Returns up to 10 articles sorted by relevance. "
        "For company competitors rather than news, use search_competitors instead."
    ),
    "input_schema": {
        "type": "object",
        "properties": {
            "query": {
                "type": "string",
                "description": "Search query. Examples: 'NVDA earnings Q3 2025', 'Tesla delivery numbers'"
            },
            "max_results": {
                "type": "integer",
                "description": "Max articles to return (1-10, default 5)",
                "default": 5
            }
        },
        "required": ["query"]
    }
}]

Os testes internos da Anthropic mostraram que adicionar um campo input_examples aumentou a precisão no tratamento de parâmetros complexos de 72% para 90%.

Devolver resultados de alto sinal e legíveis por máquinas

Evite identificadores de baixo nível (uuid, mime_type). Resolva IDs crípticos para nomes semânticos. Estruture a resposta de modo a que o agente consiga raciocinar sobre ela sem analisar boilerplate:

# Bad: raw API response dumped to agent
def get_stock_snapshot(ticker: str) -> dict:
    response = api.get(f"/v1/quotes/{ticker}")
    return response.json()  # 500+ tokens of nested JSON

# Good: high-signal summary the agent can immediately reason about
def get_stock_snapshot(ticker: str) -> dict:
    data = api.get(f"/v1/quotes/{ticker}").json()
    return {
        "ticker": ticker,
        "price": data["regularMarketPrice"],
        "change_pct": round(data["regularMarketChangePercent"], 2),
        "volume": data["regularMarketVolume"],
        "market_cap_b": round(data["marketCap"] / 1e9, 1),
        "pe_ratio": data.get("trailingPE"),
        "summary": f"{ticker} at ${data['regularMarketPrice']:.2f} "
                   f"({'up' if data['regularMarketChangePercent'] > 0 else 'down'} "
                   f"{abs(data['regularMarketChangePercent']):.1f}%)"
    }

Devolver erros sobre os quais o ciclo possa agir

O tratamento de erros requer quatro mecanismos distintos, porque cada um lida com diferentes classes de falhas:

  1. Repetição com backoff exponencial para erros transitórios
  2. Cadeias de fallback de modelos para indisponibilidade de fornecedores
  3. Encaminhamento por classificação de erros — os erros transitórios são repetidos, os erros recuperáveis pelo LLM regressam ao agente com contexto e os erros que exigem intervenção humana são escalados
  4. Recuperação a partir de checkpoints para sobreviver a falhas

O artigo da Anthropic “Writing effective tools for agents” defende erros de ferramentas claros e um design de ferramentas orientado por avaliação, mas não atribui um valor universal à recuperação proporcionada por estes quatro mecanismos. Meça a taxa de recuperação, as repetições e os escalamentos no seu próprio conjunto de tarefas.

import httpx
from tenacity import retry, stop_after_attempt, wait_exponential

@retry(
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=1, min=2, max=10),
)
def call_stock_api(ticker: str) -> dict:
    """Fetch stock data with automatic retry on transient failures.

    Mechanism 1 of the four above: exponential backoff for rate limits
    and network blips.
    If all retries fail, the error propagates to the agent with
    enough context to decide whether to try a different approach.
    """
    response = httpx.get(
        f"https://api.example.com/v1/quotes/{ticker}",
        timeout=10.0,
    )
    response.raise_for_status()
    return response.json()

Aplicar os padrões ao Market Analyst Agent

O Market Analyst Agent da Parte 1 torna visível o efeito da interface.

Consolidação de ferramentas

O design original tinha mais de 10 ferramentas: get_stock_price, get_company_metrics, get_market_cap, get_pe_ratio, get_volume, entre outras. Cada uma era um wrapper fino em torno de um endpoint de API. O agente tinha de raciocinar sobre a combinação a chamar para cada pedido.

Consolidei a superfície de dados de mercado em 5 ferramentas de alto nível, seguindo o princípio ACI de ações compactas e eficientes. A lista de ferramentas ReAct do repositório inclui mais quatro — um carregador de skills, dois wrappers de CLI e um avaliador Python restrito no processo (uma allowlist de AST, não um sandbox; a Parte 4 aborda este tema) — cobrindo três das cinco modalidades acima. O MCP surge como sidecar, e não como uma ferramenta desta lista:

Isto reduziu o overhead do schema das ferramentas e, nos meus próprios testes, tornou a seleção de ferramentas mais fiável, porque há menos escolhas ambíguas a fazer.

Outputs estruturados para os resultados das ferramentas

Todas as ferramentas do Market Analyst Agent devolvem uma resposta validada pelo Pydantic. Isto aplica o princípio de validação ACI ao output da ferramenta:

class StockSnapshot(BaseModel):
    """Structured tool response — the agent never sees raw API noise."""
    ticker: str
    price: float
    change_pct: float
    volume: int
    market_cap_b: float
    pe_ratio: float | None
    summary: str  # Human-readable one-liner for direct use in reports

class NewsResult(BaseModel):
    """Each news item is pre-processed for agent consumption."""
    headline: str
    source: str
    date: str
    relevance_score: float  # Pre-ranked so the agent doesn't waste tokens sorting
    key_points: list[str]  # Extracted by the tool, not the agent

O campo summary é o mais importante. Fornece ao agente uma string pronta a utilizar, que pode ser incluída diretamente num relatório sem processamento adicional. Os key_points em NewsResult são extraídos pela ferramenta, e não pelo agente, evitando que este gaste tokens de inferência a analisar o conteúdo dos artigos.

Compromissos e considerações

Além das ressalvas específicas de cada padrão acima, há algumas preocupações transversais que influenciam a escolha:

  • O custo operacional varia consoante a dimensão. A execução de código poupa tokens, mas acrescenta latência de cold start da sandbox. O MCP poupa tempo de desenvolvimento em integrações SaaS, mas acrescenta overhead de deployment do servidor. A CLI é gratuita para começar, mas é mais difícil de governar à escala. Otimize em função do seu verdadeiro bottleneck, seja este o custo de tokens, a latência ou a complexidade operacional.

  • As competências da equipa são importantes. A execução de código pressupõe que os seus agentes (e os modelos que lhes estão subjacentes) conseguem gerar Python ou TypeScript fiável. A CLI pressupõe familiaridade com as convenções Unix. O MCP exige conhecimentos de protocolos de transporte e fluxos OAuth. Adapte a modalidade aos pontos fortes da sua equipa.

  • A consolidação de ferramentas pode ir longe demais. Se uma ferramenta acumular modos e argumentos não relacionados, o agente defronta-se com um problema de seleção diferente dentro do schema. Utilize avaliações de seleção de ferramentas e de sucesso das tarefas para encontrar a superfície adequada à sua carga de trabalho.

  • As skills baseiam-se em prompts, não são impostas. Uma skill contém instruções que o agente deve seguir, não guardrails que tem obrigatoriamente de seguir. Em workflows críticos, combine skills com validação determinística.

  • Os requisitos de auditoria influenciam a escolha. Se precisar de um registo completo de cada invocação de ferramenta e do respetivo resultado, o MCP e as chamadas de ferramentas JSON fornecem, de raiz, trilhos de auditoria estruturados. A execução de código produz um script e o respetivo output, o que é útil, mas dificulta a decomposição em ações individuais para efeitos de relatórios de conformidade.

Três direções para as ferramentas de agentes de IA à escala

A primeira é o tool RAG para escalar. À medida que os toolsets crescem para centenas ou milhares de ferramentas, a precisão de uma seleção de ferramentas ingénua degrada-se para 13,62%. O artigo sobre RAG-MCP aplicou geração aumentada por recuperação à seleção de ferramentas: indexar as descrições das ferramentas numa base de dados vetorial e recuperar apenas as relevantes para cada consulta. Isto atingiu 43,13% de precisão — uma melhoria de 3,2x — reduzindo simultaneamente os tokens do prompt em ~50%.

A segunda é a criação das próprias ferramentas pelos agentes. O framework LATM (“LLMs As Tool Makers”) estabeleceu um paradigma em duas fases, no qual um LLM poderoso cria funções Python reutilizáveis e um LLM leve utiliza-as. O ToolMaker (ACL 2025) transforma autonomamente repositórios GitHub em ferramentas compatíveis com LLM, com uma taxa de sucesso de 80%. Ambos apontam para além do uso de ferramentas, em direção à criação de ferramentas e, posteriormente, à gestão de uma biblioteca de ferramentas geradas.

A terceira é a stack de protocolos duplos A2A + MCP. O Agent2Agent Protocol (A2A), criado pela Google e doado à Linux Foundation em junho de 2025, resolve aquilo que o MCP não resolve: a comunicação entre agentes. O MCP trata da integração entre agentes e ferramentas; o A2A trata da descoberta, negociação e delegação de tarefas entre agentes.

Principais conclusões

  1. Escolha a interface com base na ação: chamadas JSON para operações pequenas e tipadas, MCP para serviços partilhados, Skills para procedimentos, CLI para comandos estabelecidos e código em sandbox para composição local.
  2. Mantenha as condições do benchmark associadas ao resultado. CodeAct, Anthropic, Vercel, Cloudflare, Apideck e Scalekit mediram modelos, tarefas, ferramentas e harnesses diferentes.
  3. A qualidade da ACI mantém-se apesar das mudanças de protocolo. Ações claras, feedback compacto, validação e erros úteis ajudam todas as modalidades.
  4. Consolide ferramentas sobrepostas apenas quando as avaliações demonstrarem que uma superfície mais pequena melhora a seleção ou o sucesso da tarefa.
  5. A segurança acompanha o poder de execução. As interfaces de shell e código precisam de sandboxing; o MCP precisa de identidade com âmbito definido e de políticas para servidores; as Skills continuam a ser instruções, não mecanismos de enforcement.

A camada seguinte é a política

A Parte 4, Segurança de agentes de IA, coloca uma verificação de política entre uma chamada de ferramenta proposta e a sua execução. É o mesmo limite de ferramenta descrito acima, visto do lado que diz não. A Parte 5 coloca então a ferramenta e a respetiva sandbox dentro de um runtime recuperável, e a Parte 6 acrescenta um segundo contrato que o modelo nunca vê: uma categoria de efeito, uma regra de retry e um resultado estruturado que uma verificação de aceitação pode ler sem analisar prosa.
