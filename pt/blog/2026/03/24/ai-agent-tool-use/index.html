Utilização de ferramentas por AI agents: MCP, CLI, Skills e execução de código

Viacheslav Dubrov

Este artigo destina-se a engenheiros que estão a criar agents que utilizam ferramentas. Compara JSON tool calling, MCP, comandos CLI e código executado numa sandbox, para que possa escolher o mecanismo de execução adequado à sua carga de trabalho e utilizar Skills para o orientar.

As Skills fornecem instruções para escolher e utilizar ferramentas. O harness é o programa convencional que envolve o modelo: cria prompts, verifica uma chamada proposta, executa uma chamada aprovada e decide quando a tarefa está concluída.

Este terceiro artigo da série acrescenta a camada de ação aos ciclos de raciocínio da Parte 1 e à memória da Parte 2. A Parte 4 analisa a verificação de política antes da execução, e a Parte 6 analisa o harness que executa tanto a chamada como essa verificação.

A realidade das ferramentas mudou em 2025–2026. O MCP, o Model Context Protocol, deu aos fornecedores uma forma partilhada de expor serviços externos. Agents que executam código mostraram que, por vezes, um modelo consegue compor um pequeno programa de forma mais eficiente do que emitir uma longa sequência de chamadas JSON. A Anthropic reportou uma redução de 98,7% nos tokens num workflow do Google Drive para o Salesforce, e o artigo CodeAct reportou ganhos de sucesso nas tarefas de até 20 pontos percentuais na sua configuração de benchmark. Estes resultados descrevem as respetivas tarefas e harnesses, não uma vantagem universal da execução de código.

Uma secção posterior aplica princípios de design da Agent-Computer Interface (ACI) ao Market Analyst Agent, um pequeno research agent em LangGraph que criei para a Parte 1, que obtém dados de mercado e escreve um relatório de analista.

Para uma decisão rápida sobre interfaces, consulte AI Agent Tool Interfaces.

TL;DR

Utilize JSON tool calls para ações pequenas e tipadas, MCP para integrações partilhadas, comandos CLI para trabalho local já estabelecido e código executado numa sandbox para trabalho com múltiplos passos. As Skills fornecem instruções reutilizáveis para utilizar qualquer uma destas opções. Antes de uma chamada ser executada, o harness tem de verificar os seus argumentos e aprovar o respetivo efeito; um schema ou transporte não fazem isso por si próprios. Em todas as superfícies, a Agent-Computer Interface (ACI) deve tornar as ações claras, o feedback compacto e os erros recuperáveis.

Superfícies de execução e orientação processual

O reasoning loop propõe uma chamada. O harness verifica os seus argumentos e se a chamada é permitida, envia-a depois para uma ferramenta ou sandbox e devolve o resultado. JSON schemas, o transporte MCP, wrappers CLI e runners de código podem restringir entradas, mas nenhum deles decide se a ação solicitada é permitida. As Skills fornecem instruções para esse percurso. Estas superfícies de execução trocam custo em tokens, flexibilidade e enforcement de formas diferentes.

1. JSON tool calling: a base

O padrão original: define tool schemas em JSON, o LLM emite function calls estruturadas e o seu código executa-as. É um padrão bem compreendido e funciona bem para conjuntos pequenos de ferramentas.

# Schema cost depends on its text, structure, and the model tokenizer
tools = [
    {
        "name": "get_stock_price",
        "description": "Get the current stock price for a ticker symbol",
        "input_schema": {
            "type": "object",
            "properties": {
                "ticker": {"type": "string", "description": "Stock ticker (e.g., NVDA)"}
            },
            "required": ["ticker"]
        }
    }
]

Conte os tokens dos seus schemas reais. O custo depende do seu comprimento e do número de schemas carregados pelo host; uma pesquisa compacta de preços e um contrato de API profundamente aninhado não são unidades equivalentes. A descoberta adiada pode evitar o carregamento de todo o registry.

2. MCP para integrações partilhadas

O MCP é o padrão em que a maioria dos fornecedores convergiu. Um servidor MCP é um processo que anuncia uma lista de ferramentas através de um protocolo wire definido — stdio para um processo local, HTTP para um remoto. O seu agent executa um cliente MCP que estabelece ligação, pergunta ao servidor que ferramentas este disponibiliza e encaminha para ele as chamadas do modelo, permitindo que o mesmo servidor funcione com qualquer cliente que fale o protocolo. A Anthropic doou o protocolo à Linux Foundation em dezembro de 2025, no âmbito da Agentic AI Foundation, que cofundou com a OpenAI e a Block. Google, Microsoft e AWS apoiam a foundation como membros platinum. A OpenAI acrescentou suporte para MCP na sua Responses API. À data do anúncio da doação da Anthropic em dezembro de 2025, o ecossistema contabilizava mais de 10 000 servidores MCP públicos ativos e mais de 97 milhões de downloads mensais dos SDKs Python e TypeScript.

O MCP adequa-se a integrações SaaS entre fornecedores (Figma, Notion, Salesforce), serviços sem equivalentes CLI e ambientes que necessitam de orquestração OAuth. O seu valor está numa camada partilhada de descoberta e transporte. A governance continua a depender dos controlos de autenticação, autorização, logging e deployment do servidor.

A versão do protocolo é agora uma decisão prática de migração. A revisão de 2026-07-28 altera comportamentos assumidos por tutoriais mais antigos:

AlteraçãoO que deve verificar numa integração
Os pedidos stateless substituem o handshake de inicialização e as sessões de transporteEnvie metadados do protocolo por pedido; utilize server/discover para verificar o suporte. Confirme as versões do cliente e do servidor.
Multi Round-Trip Requests devolve InputRequiredResultTrate pedidos de dados adicionais e, em seguida, repita a operação original com as respostas e o estado de continuação.
As Tasks passam para a extensão oficial de tasksVerifique o suporte da extensão em vez de assumir a antiga API experimental de tasks do core.

A mesma revisão torna Roots, Sampling, Logging e OAuth Dynamic Client Registration obsoletos; a obsolescência não significa remoção imediata. O registo de clientes atual privilegia Client ID Metadata Documents. As integrações existentes podem continuar a utilizar uma revisão anterior, por isso inspecione o SDK instalado e o contrato do servidor antes de adotar uma funcionalidade nova.

A realidade em produção é mais complexa do que os números dos títulos sugerem.

O Vulnerable MCP Project reúne relatórios relacionados com prompt injection, validação de inputs, autenticação e controlos de rede. Esta coleção ajuda a identificar casos de teste; sem um denominador de exposição, não pode comparar o MCP com shell ou chamadas diretas à API.

Tool poisoning é a classe de ataque que mais me preocupa. A Invariant Labs demonstrou que ferramentas MCP envenenadas podem exfiltrar dados mesmo quando nunca são invocadas. Basta o modelo ler os metadados da ferramenta para desencadear o ataque. Os benchmarks MCPTox, que testaram 20 LLM agents contra 45 servidores MCP reais, reportaram 72,8% de sucesso médio dos ataques para o o1-mini na sua configuração de tool poisoning. Este é o resultado de um benchmark de um modelo, não uma média dos 20 agents nem uma taxa de incidentes no mundo real.

O overhead de tokens é o problema operacional. Uma equipa que executava servidores MCP para GitHub, Slack e Sentry (~40 ferramentas no total) encontrou 55 000 tokens de definições de schemas injetados antes de o utilizador perguntar fosse o que fosse. Outro caso reportou que 143 000 dos 200 000 tokens disponíveis (72%) eram consumidos apenas pelas definições das ferramentas.

O relatório da Anthropic sobre Tool Search Tool reportou endpoints de contexto aproximados de 77 000 tokens antes de o trabalho começar e 8 700 após a descoberta adiada, com cerca de 72 000 tokens de definições de ferramentas na configuração tradicional. Carrega apenas as três a cinco ferramentas de que um pedido necessita, mas acrescenta um passo de descoberta antes da invocação; é menos útil para conjuntos pequenos e compactos de ferramentas utilizadas frequentemente em todas as sessões.

3. As Skills empacotam expertise, não execução

As agent skills são um formato aberto para empacotar instruções e ficheiros de suporte. As ferramentas fornecem capacidades (o que os agents conseguem fazer) e as skills fornecem expertise (o que os agents sabem sobre como executar tarefas complexas).

O formato SKILL.md define uma skill como um ficheiro Markdown com YAML frontmatter. O standard aberto exige apenas name e description; o exemplo abaixo utiliza também duas extensões do Claude Code, argument-hint e user-invocable, além do seu placeholder posicional de argumentos $0:

---
name: deploy
description: Deploy the application to production
argument-hint: "[environment]"
user-invocable: true
---
Deploy the application to the $0 environment (default: staging).
Steps:
1. Run the test suite
2. Build the production bundle
3. Deploy using the deploy script
4. Verify the deployment health check

As Skills utilizam progressive disclosure. No arranque, o agent recebe cerca de 100 tokens de name e description. Carrega o SKILL.md completo apenas quando necessita da skill e, em seguida, carrega scripts, documentos ou assets referenciados conforme necessário. Esse custo de arranque é muito inferior aos aproximadamente 55 000 tokens que cerca de 40 ferramentas MCP podem consumir antes de o raciocínio começar. Uma skill ativa continua a acrescentar as suas instruções e recursos ao contexto.

Utilize skills para conhecimento de domínio, procedimentos com múltiplos passos e trabalho recorrente, como migrações de bases de dados ou integrações de pagamentos. Adequam-se a tarefas em que o agent necessita de instruções sobre como utilizar uma capacidade existente.

4. Ferramentas CLI e shell

As interfaces CLI podem ser muito mais económicas em contexto quando o modelo já conhece o comando. A Scalekit reportou uma diferença de 4–32x em tokens entre os seus percursos CLI e MCP em 75 execuções. Este case study mede as suas ferramentas e tarefas; não substitui uma comparação com as suas próprias definições de ferramentas e output dos comandos.

Comandos amplamente documentados, como git, docker, kubectl, gh, curl e jq, frequentemente precisam de pouco texto introdutório de schema. CLIs menos comuns ou internos continuam a precisar de help descobrível, exemplos e output estável, legível por máquina.

O guia de Ugo Enyioha, “Writing CLI Tools That AI Agents Actually Want to Use”, codificou oito regras de design:

  1. Structured output é obrigatório — suporte --json
  2. Os exit codes são controlo de fluxo — utilize códigos distintos para diferentes tipos de erro
  3. Os comandos devem ser idempotentes
  4. Self-documenting --help com exemplos realistas
  5. Design para composability — --quiet para valores simples, suporte de stdin
  6. Forneça flags --dry-run e --yes
  7. Suporte introspeção da versão
  8. Trate a autenticação através de variáveis de ambiente

A CLI não tem discovery ao nível do protocolo. O JSON tool calling pode transportar schemas tipados, enquanto o MCP normaliza a descoberta de ferramentas e, para transportes HTTP, um modelo de autorização. Nenhum dos dois fornece governance por si próprio: o host, servidor ou harness tem de impor a policy e registar as chamadas que necessitam de auditoria. Um default prático é utilizar CLI para development e operações locais, e MCP para integração com serviços externos partilhados quando a descoberta entre clientes ou a orquestração OAuth justificam o overhead do servidor.

5. Execução de código para trabalho com múltiplos passos

Esta é a alteração nas ferramentas de agents que considero mais relevante. Em vez de emitir JSON estruturado para invocar funções predefinidas uma de cada vez, o agent escreve um script Python ou bash. O script chama várias ferramentas, processa resultados com loops e condicionais e devolve apenas o resumo final ao contexto do modelo.

A Anthropic introduziu o Programmatic Tool Calling (PTC) em beta. O guia atual da API utiliza a Messages API normal com code_execution_20260120 ou posterior; o lançamento beta original é contexto histórico. A base académica é o artigo CodeAct (Wang et al., ICML 2024), que testou 17 LLMs e concluiu que as ações em código alcançaram até mais 20 pontos percentuais de sucesso nas tarefas e 30% menos ações do que as alternativas JSON.

Três case studies first-party mostram onde o padrão pode ajudar: Vercel e Cloudflare abaixo, seguidos do exemplo de análise de despesas da Anthropic. Considere-os evidência dos fornecedores e volte a executar a comparação nas suas próprias tarefas.

  • A Vercel reconstruiu o d0, o seu data agent de linguagem natural para SQL. O exemplo antigo de código nomeia 17 ferramentas; o novo expõe ExecuteCommand e ExecuteSQL. A Vercel apresenta o redesign como uma remoção de 80% das ferramentas, mas essa afirmação é o headline da Vercel, não uma percentagem que resulte das ferramentas nomeadas nos exemplos. Em cinco queries representativas, a Vercel reporta que o sucesso das tarefas passou de 4/5 para 5/5, o tempo médio de execução diminuiu 3,5x (274,8 s para 77,4 s) e a utilização média de tokens caiu 37% (~102k para ~61k). Nas suas palavras: “Os melhores agents podem ser aqueles com menos ferramentas.”

  • A Cloudflare desenvolveu o “Code Mode”, que permite aos agents escrever TypeScript para chamar a sua API em vez de definir tool schemas, reduzindo o overhead de contexto. O seu raciocínio é: “Os LLMs têm uma enorme quantidade de TypeScript do mundo real nos dados de treino, mas apenas um pequeno conjunto de exemplos artificiais de tool calls.”

Eis o padrão da documentação PTC da Anthropic. Na ilustração sequencial de análise de despesas da Anthropic, o tool calling tradicional requer mais de 20 passes de inferência separados, com dados intermédios a circular pelo contexto. Após a pesquisa da equipa, um host que suporte chamadas paralelas de ferramentas pode agrupar os pedidos de despesas independentes; o valor de mais de 20 não torna isso impossível. A Anthropic reporta que o código gerado para responder à mesma pergunta reduz o que chega ao contexto de 200 KB de linhas de despesas em bruto — mais de 2 000 itens — para 1 KB de resultados. O script abaixo ilustra esse fluxo de controlo com adapters Python async personalizados: aceitam argumentos posicionais e devolvem listas e dicionários descodificados. Não é o contrato wrapper nativo do PTC.

# Custom decoded Python adapters, not native Claude PTC wrappers.
import asyncio
import json

async def main() -> None:
    team = await get_team_members("engineering")
    levels = list(set(member["level"] for member in team))
    budgets = dict(zip(
        levels,
        await asyncio.gather(*(get_budget_by_level(level) for level in levels)),
    ))
    expenses = await asyncio.gather(
        *(get_expenses(member["id"], "Q3") for member in team)
    )
    over_budget = []
    for member, employee_expenses in zip(team, expenses):
        total = sum(expense["amount"] for expense in employee_expenses)
        limit = budgets[member["level"]]["travel_limit"]
        if total > limit:
            over_budget.append(
                {"name": member["name"], "spent": total, "limit": limit}
            )
    # Only this final summary returns to the LLM context
    print(json.dumps(over_budget))

asyncio.run(main())

Para utilizar os wrappers PTC nativos do Claude, passe a cada ferramenta um dicionário de argumentos, descodifique a string JSON devolvida e utilize await de topo no ambiente de execução gerido, em vez de iniciar um event loop com asyncio.run. O exemplo de adapter personalizado acima assume um runtime de script Python normal; também não é um exemplo drop-in de um conector MCP nativo. As restrições atuais da API PTC excluem ferramentas strict: true e ferramentas de conectores MCP nativos do programmatic calling, além de restringirem schemas recursivos. Uma bridge personalizada entre código e MCP é uma integração separada. allowed_callers orienta a forma como Claude chama uma ferramenta; não é uma fronteira de autorização. O host tem de validar todas as invocações devolvidas, incluindo uma chamada direta inesperada.

O LLM vê apenas o resumo JSON final, não as milhares de linhas de despesas processadas na sandbox. A poupança não é específica de relatórios de despesas: o artigo separado da Anthropic sobre execução de código apresenta o número mais expressivo para este padrão: um workflow do Google Drive para o Salesforce que passou de ~150 000 tokens para ~2 000, uma redução de 98,7%.

O guia PTC atual também apresenta um contraexemplo: nas tarefas de aviação, retalho e telecomunicações do tau2-bench, o PTC não alterou os scores e custou aproximadamente mais 8%. Num benchmark separado de gestão de projetos com 75 ferramentas, reduziu os input tokens faturados em cerca de 38%, sem alterar a accuracy. Estas avaliações internas identificam apenas um modelo Claude de produção, não um ID exato. Workflows sequenciais pequenos podem não poupar o suficiente para compensar o overhead de container e de geração de código.

A eficiência de tokens é um ganho potencial. Loops e condicionais não têm custo adicional, e a execução de código pode tratar erros com handlers explícitos, em vez de obrigar o modelo a raciocinar sobre falhas em linguagem natural. Um percurso de execução de código pode manter dados intermédios sensíveis fora do contexto do modelo, mas isso não é confidentiality: isolamento, controlos de egress, credenciais com scope e logging precisam de enforcement separado.

Quando o JSON tool calling continua a fazer sentido: operações atómicas individuais, ambientes sem infraestrutura de sandbox, modelos mais pequenos com fraca geração de código ou requisitos de auditoria que necessitem de registar cada invocação individual de ferramentas.

JSON tool calling, MCP, CLI e execução de código são superfícies de execução. As Skills são instruções que orientam uma dessas superfícies, pelo que a sua latência, contexto e setup dependem do mecanismo selecionado. “Meta-tools” significa os poucos entry points genéricos de que um agent que executa código necessita — por exemplo, ExecuteCommand e ExecuteSQL da Vercel — em vez de um schema para cada operação. As linhas de composability e latência descrevem chamadas cujos argumentos posteriores dependem de resultados anteriores. JSON tool calling e MCP podem emitir chamadas independentes em conjunto, mas chamadas dependentes normalmente precisam de outro model turn. O PTC move esse fluxo de controlo e filtering dependente para um script e devolve depois um resumo ao modelo. As células relativas a tokens e sucesso nas tarefas resumem os exemplos citados, não um benchmark controlado único entre as cinco colunas.

A Agent-Computer Interface (ACI) para ferramentas de AI agents

O termo “Agent-Computer Interface” (ACI) foi cunhado por John Yang, Carlos E. Jimenez e colegas de Princeton no seu artigo sobre o SWE-agent (NeurIPS 2024). A qualidade das interfaces humanas tem toda uma disciplina dedicada — human-computer interaction, ou HCI. O artigo defende que os agents baseados em language models merecem o mesmo tratamento: são “uma nova categoria de utilizadores finais, com necessidades e capacidades próprias, que beneficiariam de interfaces construídas especificamente para eles”.

Os seus resultados de ablation quantificam essa ideia. Utilizando o mesmo modelo base GPT-4 Turbo, a ablation do SWE-bench Lite do artigo alcançou 18,0% com a ACI completa do SWE-agent em 300 tarefas, contra 7,3% na condição apenas com shell, sem uma demonstração trabalhada, e 11,0% com uma. A comparação mostra que as condições da interface e da demonstração alteraram materialmente o desempenho nesta configuração; não isola o design da interface de todas as outras diferenças nem demonstra que o modelo não tenha realizado trabalho. Na mesma ablation da interface, ativar linting elevou a condição de edição de 15,0% para 18,0%; em todo o conjunto de testes SWE-bench, 51,7% das execuções do SWE-agent encontraram pelo menos uma edição rejeitada pelo linter antes de esta poder propagar-se.

O diagrama mostra a validação dos resultados depois de uma ferramenta devolver feedback. A validação dos argumentos é uma verificação separada, anterior à execução da ferramenta; um resultado inválido regressa ao agent para correção antes de outra ação o utilizar.

A Anthropic adotou a ACI como conceito fundamental no seu guia “Building Effective Agents”, apresentando-a como um dos três princípios centrais: “Construa cuidadosamente a sua interface agent-computer através de documentação e testes exaustivos das ferramentas.” A sua orientação prática é: “Uma regra prática é pensar no esforço dedicado às interfaces human-computer e planear investir exatamente o mesmo esforço na criação de boas interfaces agent-computer.”

Quatro princípios ACI na prática

1. As ações devem ser simples e fáceis de compreender. O erro mais comum é encapsular endpoints de API numa relação um-para-um. Em vez de list_users, list_events, create_event, implemente schedule_event, que encontra disponibilidade e agenda numa única chamada. Em vez de read_logs, implemente search_logs, que devolve apenas as linhas relevantes com contexto.

2. As ações devem ser compactas e eficientes. Consolide operações importantes no menor número possível de ações. No Market Analyst Agent, combino a obtenção de preços com métricas básicas numa única ferramenta get_stock_snapshot, em vez de exigir chamadas separadas para preço, volume, market cap e PE ratio.

3. O feedback do ambiente deve ser informativo, mas conciso. Evite devolver HTML em bruto ou payloads completos da API. Resolva IDs crípticos para nomes semânticos. Os testes da Anthropic acrescentaram um enum response_format, permitindo ao agent pedir uma resposta concisa (~72 tokens) ou detalhada (~206 tokens), uma diferença de aproximadamente 3x no custo em tokens.

4. A validação deve mitigar a propagação de erros. A deteção automática de erros ajuda os agents a reconhecer e corrigir rapidamente os seus erros. No SWE-agent, um editor de ficheiros personalizado com linting integrado rejeita automaticamente erros de sintaxe — o passo de validação por trás do valor de 51,7% acima. Esta é a validação dos inputs e outputs de uma ferramenta, não o content filtering em torno de uma chamada ao modelo feito pelos produtos de guardrails da Parte 4; a mesma palavra é utilizada para ambos. Aplico o mesmo princípio no Market Analyst Agent, validando os argumentos das ferramentas com schemas Pydantic antes da execução:

from pydantic import BaseModel, Field, field_validator

from market_analyst.utils import normalize_ticker

class StockQuery(BaseModel):
    """Validated input for stock queries.

    Pydantic catches malformed tickers before the API call,
    preventing error propagation through the reasoning loop.
    """
    ticker: str = Field(description="Stock ticker symbol (e.g., NVDA)")

    @field_validator("ticker")
    @classmethod
    def validate_ticker(cls, v: str) -> str:
        return normalize_ticker(v)

class StockHistoryQuery(StockQuery):
    """Validated input for price history queries."""

    period: str = Field(default="1mo", description="Time period: 1d, 5d, 1mo, 3mo, 6mo, 1y")

    @field_validator("period")
    @classmethod
    def validate_period(cls, v: str) -> str:
        valid = {"1d", "5d", "1mo", "3mo", "6mo", "1y"}
        if v not in valid:
            raise ValueError(f"Invalid period: {v}. Must be one of {valid}")
        return v

O normalizer partilhado remove espaços e converte o valor para maiúsculas; depois aceita dígitos no ticker e suffixes separados por pontos ou hífenes, como BRK.B e BF-B; StockHistoryQuery, e não StockQuery, é responsável por period.

Padrões de design de ferramentas para AI agents que funcionam

O guia da Anthropic “Writing effective tools for agents” descreve as ferramentas como “um novo tipo de software que reflete um contrato entre sistemas determinísticos e agents não determinísticos”.

Trate as descrições das ferramentas como prompt engineering

As descrições devem ter pelo menos três ou quatro frases, cobrindo quando utilizar a ferramenta, parâmetros obrigatórios versus opcionais, formato do output e edge cases. A Anthropic reporta que a escolha entre namespacing baseado em prefixos ou suffixes (asana_search versus search_asana) teve “efeitos não triviais” nas suas próprias avaliações de tool use. Não indica qual o esquema vencedor, por isso teste ambos no seu toolset em vez de assumir prefixos. A Anthropic também alimentou o Claude Code com os transcripts dos seus agents de avaliação e permitiu-lhe reescrever as ferramentas. Em test sets reservados, esse loop encontrou melhorias adicionais “mesmo para além do que alcançámos com implementações de ferramentas feitas por ‘especialistas’” — quer essas ferramentas tivessem sido escritas pelos seus investigadores, quer geradas pelo Claude.

# Bad: vague, no context for when to use
tools = [{
    "name": "search",
    "description": "Search for items",
}]

# Good: specific, with input examples and edge cases
tools = [{
    "name": "search_news",
    "description": (
        "Search for recent news articles about a specific stock or company. "
        "Use this tool when the user asks about recent events, earnings, "
        "announcements, or market-moving news for a specific ticker. "
        "Returns up to 10 articles sorted by relevance. "
        "For company competitors rather than news, use search_competitors instead."
    ),
    "input_schema": {
        "type": "object",
        "properties": {
            "query": {
                "type": "string",
                "description": "Search query. Examples: 'NVDA earnings Q3 2025', 'Tesla delivery numbers'"
            },
            "max_results": {
                "type": "integer",
                "description": "Max articles to return (1-10, default 5)",
                "default": 5
            }
        },
        "required": ["query"]
    }
}]

Os testes internos da Anthropic mostraram que acrescentar um campo input_examples elevou a accuracy no tratamento de parâmetros complexos de 72% para 90%.

Devolva output de alto sinal e legível por máquina

Utilize labels semânticos em vez de identificadores de baixo nível (uuid, mime_type) na resposta por default. Mantenha um ID quando uma ferramenta posterior dele necessitar ou disponibilize uma resposta detalhada que o inclua. Por exemplo, um resultado de pesquisa de Jane pode ser conciso de ler, enquanto um resultado detalhado inclui o ID de que send_message necessita. Estruture a resposta para que o agent consiga raciocinar sobre ela sem fazer parsing de boilerplate:

# Bad: raw API response dumped to agent
def get_stock_snapshot(ticker: str) -> dict:
    response = api.get(f"/v1/quotes/{ticker}")
    return response.json()  # 500+ tokens of nested JSON

# Good: high-signal summary the agent can immediately reason about
def get_stock_snapshot(ticker: str) -> dict:
    data = api.get(f"/v1/quotes/{ticker}").json()
    return {
        "ticker": ticker,
        "price": data["regularMarketPrice"],
        "change_pct": round(data["regularMarketChangePercent"], 2),
        "volume": data["regularMarketVolume"],
        "market_cap_b": round(data["marketCap"] / 1e9, 1),
        "pe_ratio": data.get("trailingPE"),
        "summary": f"{ticker} at ${data['regularMarketPrice']:.2f} "
                   f"({'up' if data['regularMarketChangePercent'] > 0 else 'down'} "
                   f"{abs(data['regularMarketChangePercent']):.1f}%)"
    }

Devolva erros sobre os quais o loop possa atuar

O tratamento de erros precisa de quatro mecanismos separados, porque cada um trata uma classe de falhas diferente:

  1. Retry com exponential backoff para erros transitórios
  2. Model fallback chains para indisponibilidade do provider
  3. Error classification routing — erros transitórios fazem retry, erros recuperáveis pelo LLM regressam ao agent com contexto e erros que exigem intervenção humana são escalados
  4. Checkpoint recovery para sobrevivência a crashes

O guia da Anthropic “Writing effective tools for agents” defende erros claros nas ferramentas e design de ferramentas orientado por avaliações, mas não atribui um número universal ao que estes quatro mecanismos recuperam. Meça a recovery rate, os retries e as escalations no seu próprio conjunto de tarefas.

import httpx
from tenacity import retry, retry_if_exception, stop_after_attempt, wait_exponential

def is_transient_error(error: BaseException) -> bool:
    if isinstance(error, (httpx.TimeoutException, httpx.NetworkError)):
        return True
    if isinstance(error, httpx.HTTPStatusError):
        return error.response.status_code == 429 or 500 <= error.response.status_code < 600
    return False

@retry(
    retry=retry_if_exception(is_transient_error),
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=1, min=2, max=10),
    reraise=True,
)
def call_stock_api(ticker: str) -> dict:
    """Fetch stock data with automatic retry on transient failures.

    Mechanism 1 of the four above: exponential backoff for rate limits
    and network blips.
    This only retries transient transport failures. If attempts are exhausted,
    Tenacity re-raises the original httpx exception.
    """
    response = httpx.get(
        f"https://api.example.com/v1/quotes/{ticker}",
        timeout=10.0,
    )
    response.raise_for_status()
    return response.json()

O caller ou harness continua a precisar do passo seguinte: transformar essa exception num resultado estável que indique qual a operação que falhou, se deve ser repetida e o que fazer a seguir. Um 4xx não repetível ignora este decorator e precisa do mesmo tratamento. Repetir um pedido não classifica o seu erro nem recupera um checkpoint.

Consolidação de ferramentas

Os módulos de ferramentas originais definiam get_stock_price, get_company_metrics, get_price_history, duas ferramentas de pesquisa e execute_trade. Para uma análise básica, o agent tinha de escolher tanto a chamada de preço como a de métricas; market cap e P/E eram campos de get_company_metrics, não ferramentas autónomas. O código-fonte anterior à consolidação mostra essa superfície anterior.

Reestruturei a superfície de market data em 5 ferramentas de alto nível, seguindo o princípio ACI de ações compactas e eficientes. A lista de ferramentas ReAct do repo inclui mais quatro — um loader de skills, dois wrappers CLI e um evaluator Python restrito in-process (uma AST allowlist, não uma sandbox; a Parte 4 aborda este tema) — cobrindo três das cinco modalidades acima. Outputs estruturados para resultados de ferramentas

As ferramentas de ações e notícias devolvem respostas validadas por Pydantic. Os wrappers de CLI e de execução de código devolvem str, pelo que os modelos abaixo descrevem os resultados estruturados das ferramentas, e não todos os wrappers do repository:

from pydantic import BaseModel

class StockSnapshot(BaseModel):
    """Structured tool response — the agent never sees raw API noise."""
    ticker: str
    price: float
    change_pct: float
    volume: int
    market_cap_b: float
    pe_ratio: float | None
    summary: str  # Human-readable one-liner for direct use in reports

class NewsItem(BaseModel):
    """One news item pre-processed for agent consumption."""
    headline: str
    source: str
    date: str
    relevance_score: float  # Pre-ranked so the agent doesn't waste tokens sorting
    key_points: list[str]  # Extracted by the tool, not the agent

class NewsSearchResult(BaseModel):
    query: str
    results: list[NewsItem]
    summary: str

O campo summary fornece ao agent uma string pronta a utilizar num relatório. NewsItem.key_points evita que o modelo tenha de fazer parsing dos corpos dos artigos. Se uma ação posterior precisar de um ID, mantenha-o na resposta detalhada ou disponibilize modos conciso e detalhado; não o remova em todo o lado.

Trade-offs e considerações

Para além das ressalvas específicas de cada padrão acima, algumas preocupações transversais influenciam a escolha:

  • O custo operacional varia consoante a dimensão. A execução de código pode poupar tokens do contexto do modelo ao filtrar resultados intermédios, mas a geração de código e o overhead do container podem anular essas poupanças e acrescentar latência. O MCP poupa tempo de development em integrações SaaS, mas acrescenta overhead de deployment do servidor. A CLI é gratuita para começar, mas é mais difícil de governar à escala. Otimize para o seu bottleneck real, seja custo de tokens, latência ou complexidade operacional.

  • As competências da equipa são importantes. A execução de código pressupõe que os seus agents (e os modelos em que assentam) conseguem gerar Python ou TypeScript fiável. A CLI pressupõe familiaridade com convenções Unix. O MCP exige compreensão de protocolos de transporte e flows OAuth. Adeque a modalidade aos pontos fortes da equipa.

  • A consolidação de ferramentas pode ir longe demais. Se uma ferramenta acumular modes e argumentos sem relação entre si, o agent depara-se com um problema de seleção diferente dentro do schema. Utilize avaliações de tool selection e sucesso nas tarefas para encontrar a superfície certa para a sua carga de trabalho.

  • As Skills baseiam-se em prompts e não são impostas. Uma skill contém instruções que o agent deve seguir, não guardrails que tenha de seguir. Um bundle de skills pode incluir ficheiros arbitrários e scripts executáveis, por isso confie na sua origem, reveja o bundle e faça com que o host imponha as permissões para cada recurso que possa ler, alterar ou executar. Em workflows críticos, combine skills com validação determinística.

  • Os requisitos de auditoria influenciam a escolha. As chamadas estruturadas MCP e JSON são eventos convenientes para registar, mas nenhum dos protocolos cria, de raiz, um audit trail completo. O host, servidor ou harness tem de registar invocações e resultados e, em seguida, impor autorização, policy, retenção e revisão. A execução de código precisa da mesma instrumentação em torno da sandbox; o seu script e output, por si só, não constituem um registo de compliance.

Três direções para ferramentas de AI agents à escala

A primeira é tool RAG para scaling. Antes de o modelo escolher uma ferramenta, obtenha as poucas tool descriptions que correspondem ao pedido e permita-lhe escolher desse subconjunto, em vez do registry completo. Nas tarefas de benchmark e no stress test MCP do RAG-MCP, a accuracy baseline de seleção de ferramentas foi de 13,62%; a retrieval elevou-a para 43,13%, uma melhoria de 3,2x, reduzindo simultaneamente os prompt tokens de 2 133,84 para 1 084 (cerca de 49,2%). O abstract do artigo diz “mais de 50%”, e as descrições do generator/evaluator diferem entre secções; estas inconsistências limitam a interpretação. O resultado é evidência para essa configuração de avaliação, não uma taxa universal para seleção ingénua à medida que os toolsets crescem.

A segunda é agents que criam as suas próprias ferramentas. O framework LATM (“LLMs As Tool Makers”) estabeleceu um paradigma em duas fases no qual um LLM poderoso cria funções Python reutilizáveis e um LLM leve as utiliza. No benchmark de 15 tarefas do ToolMaker, constituído por artigos com repositories públicos de código e fornecido como URLs GitHub e descrições curtas de tarefas, implementou corretamente 12 de 15 tarefas; o benchmark contém mais de 100 testes no total. Este pequeno benchmark de tarefas sobre repositories não estabelece fiabilidade em produção. Ambos apontam para além do tool use, em direção à criação de ferramentas e, depois, à gestão de uma library de ferramentas geradas.

A terceira é a stack de duplo protocolo A2A + MCP. A Google transferiu o A2A para a Linux Foundation em junho de 2025. A documentação do protocolo A2A separa as respetivas responsabilidades: o MCP liga um agent a ferramentas e recursos, enquanto o A2A permite que agents independentes se descubram, negoceiem interações, giram tarefas partilhadas e deleguem trabalho.

Compare interfaces em tarefas e operações permitidas idênticas. Registe tokens de descoberta, input com e sem cache, output de execução, retries, latência e sucesso do estado final. Teste tanto a falha da descoberta como as poupanças de tokens; para programas gerados, conte erros de sintaxe, erros de runtime e conclusão parcial.

Principais conclusões

  1. Escolha a superfície de execução a partir da ação: chamadas JSON para operações pequenas e tipadas, MCP para serviços partilhados, CLI para comandos estabelecidos e código em sandbox para composição local. Utilize Skills para documentar como escolher e utilizar essa superfície.
  2. Mantenha as condições do benchmark associadas ao resultado. CodeAct, Anthropic, Vercel, Cloudflare, Apideck e Scalekit mediram modelos, tarefas, ferramentas e harnesses diferentes.
  3. A qualidade ACI mantém-se apesar das alterações de protocolo. Ações claras, feedback compacto, validação e erros úteis ajudam todas as modalidades.
  4. Consolide ferramentas sobrepostas apenas quando as avaliações mostrarem que uma superfície menor melhora a seleção ou o sucesso nas tarefas.
  5. A segurança acompanha o poder de execução. Interfaces shell e de código precisam de sandboxing; o MCP precisa de uma identidade com scope e policy do servidor; as Skills continuam a ser instruções, e não enforcement.
