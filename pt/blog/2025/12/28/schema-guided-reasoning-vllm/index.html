Raciocínio orientado por schema: vLLM, XGrammar e Pydantic

Viacheslav Dubrov

2025-12-28 · Atualizado 2026-09-12 · 15 min · Agentes de IA · Engenharia de modelos

Tradução automática

Este artigo foi traduzido automaticamente a partir da versão original em inglês.

Este artigo destina-se a engenheiros Python que precisam de outputs do modelo que o código a jusante consiga validar. Aprenderá a definir um schema Pydantic, a solicitar structured output a partir do vLLM e a adicionar verificações na aplicação para significado e políticas.

O Pydantic descreve os campos da resposta, o vLLM disponibiliza o modelo e o XGrammar restringe os tokens que o modelo pode gerar. Esta restrição chama-se constrained decoding. Aplica-se apenas às funcionalidades de schema suportadas pelo backend de decoding — neste caso, o XGrammar. Um limite de tokens pode ainda deixar um prefixo JSON incompleto, pelo que o código da aplicação tem de verificar a conclusão e validar o resultado.

O que é o Raciocínio orientado por schema?

O Raciocínio orientado por schema é uma técnica que Rinat Abdullin descreveu em julho de 2025. Em vez de deixar o modelo concluir texto livremente — o que pode ser inconsistente ou ambíguo — fornece-se-lhe um template rigoroso que define:

  • que passos a resposta deve representar
  • a ordem pretendida desses passos, para que um revisor possa inspecionar o percurso entre os dados e a decisão
  • onde deve concentrar a atenção

Pense nisto como uma checklist de outputs a inspecionar, e não como uma prova do raciocínio interno do modelo. O decoder verifica a estrutura do output; o código da aplicação controla quando cada fase é executada e se um resultado pode ser utilizado.

O que o schema controla

O exemplo em execução propõe um desconto para reter um cliente que poderá abandonar o serviço. A probabilidade de churn estima essa possibilidade; o valor do carrinho é o total antes do desconto. A margem é o lucro bruto como fração desse total: um carrinho de $200 com uma margem de 0.20 tem $40 de lucro bruto. Os descontos utilizam pontos percentuais, pelo que uma proposta de 15 significa 15%.

Um modelo de pricing pode devolver JSON válido e, ainda assim, propor um desconto de 25% quando a margem é de apenas 20%. O schema regista a proposta; o código da aplicação tem de verificar se o desconto é permitido.

Campos como churn_analysis, margin_math e max_discount_percent tornam explícitos os outputs intermédios pretendidos. Um schema restringe a forma devolvida. Por si só, não faz um campo depender de outro nem prova que a decisão está correta.

Isto proporciona:

  • uma estrutura de output comparável entre execuções repetidas
  • outputs intermédios registados que os revisores podem inspecionar
  • campos intermédios que podem ser avaliados face a um dataset de teste
  • uma hipótese a testar com modelos mais pequenos: restringir o formato pode ajudar, mas a accuracy da tarefa continua a exigir avaliação
  • Abdullin escreve que um aumento de accuracy de 5–10% não é “incomum” nos casos que observou; trata-se de uma observação de practitioner, não de um resultado de benchmark, pelo que deve medi-lo na sua própria workload

Orientação do prompt e restrições do decoder

A orientação do prompt e o constrained decoding podem ser combinados. Esta comparação mostra onde cada um verifica o formato solicitado.

Prompt engineering: solicitar o formato

Este prompt pede ao modelo que formate a proposta de desconto como JSON:

Please analyze the customer data and output your response as valid JSON
with the following structure: {"discount": <number>, "reason": <string>}
Be careful with the formatting!

Espera-se que a compreensão que o modelo tem de “output JSON” se sobreponha à sua tendência para ser conversacional. Uma atualização do modelo, uma alteração da temperature ou um exemplo few-shot diferente podem quebrar o parser.

Chain of Thought: trace de raciocínio útil, o mesmo problema de estrutura

Um prompt de chain-of-thought (CoT) pede uma análise intermédia. A resposta poderá ter este aspeto:

Let's think step by step:
1. First, I'll analyze the customer's churn risk...
2. Then I'll calculate the margin...
3. Therefore, I recommend a 15% discount.

O CoT pode melhorar a accuracy da tarefa quando o prompt, o modelo, a tarefa e a avaliação o suportam, mas deixa o resultado como prosa difícil de analisar de forma fiável. Poderá acabar por fazer uma segunda chamada ao LLM apenas para extrair dados estruturados.

SGR: chain of thought estruturado

O SGR pode disponibilizar campos intermédios para inspeção e avaliação. O facto de isso melhorar a accuracy da tarefa depende do modelo, do prompt, da tarefa e da forma como esses campos são utilizados; o schema apenas formaliza a sua forma:

class PricingLogic(BaseModel):
    # 1. Recorded analysis
    churn_analysis: str = Field(..., description="Analyze churn_probability")
    financial_analysis: str = Field(..., description="Analyze cart_value and margin")

    # 2. Proposed calculation, checked by application code
    margin_math: str = Field(..., description="Calculate: 'Cart $X * Y% = $Z'")

    # 3. Proposed decision, not bounded by the analysis fields
    max_discount_percent: float = Field(..., description="Max allowed discount")

    # 4. Final Output
    customer_message: str

O schema descreve estes campos pela ordem apresentada. Um único schema de objeto não cria uma etapa de validação separada entre eles. Utilize chamadas separadas ou verificações na aplicação quando decisões posteriores tiverem de depender de resultados anteriores.

Padrões de SGR

Byte says

Colocar os campos de análise antes de uma decisão torna a resposta mais fácil de inspecionar. Um campo chamado margin_math continua a ser uma string, não uma calculadora.

O SGR tem três padrões fundamentais que podem ser compostos em workflows maiores.

1. Cascade: passos de raciocínio sequenciais

Cascade representa uma ordem de raciocínio numa única resposta estruturada. Aqui, um classificador de documentos regista um resumo, uma pontuação de correspondência temática e uma categoria proposta. Não executa uma verificação separada entre esses campos.

from pydantic import BaseModel
from typing import Literal, Annotated
from annotated_types import Ge, Le

class DocumentEvaluation(BaseModel):
    """Record a document summary, score, and proposed category."""

    # Step 1: Record a summary
    brief_document_summary: str

    # Step 2: Rate (bounded integer)
    rate_topic_match: Annotated[int, Ge(1), Le(10)]

    # Step 3: Decide (constrained choices)
    final_recommendation: Literal["relevant", "irrelevant", "review"]

Utilizações ilustrativas: classificação de documentos e triagem de tickets de suporte.

É pedido ao modelo que devolva brief_document_summary, rate_topic_match e final_recommendation por essa ordem. Se a ordem for um requisito de política, imponha-a com chamadas separadas ou lógica determinística na aplicação.

2. Routing: uma instrução switch semântica

Routing pede ao modelo que selecione um caminho de um conjunto de opções, implementado com tipos Union. Este router escolhe entre obter dados do cliente para um pedido de pricing e devolver uma resposta geral.

from pydantic import BaseModel
from typing import Literal, Union

class FeatureLookup(BaseModel):
    """Route to database lookup."""
    rationale: str
    tool_name: Literal["fetch_user_features"] = "fetch_user_features"
    user_id: str

class GeneralResponse(BaseModel):
    """Standard response for non-pricing queries."""
    tool_name: Literal["respond"] = "respond"
    content: str

class RouterSchema(BaseModel):
    """The model must pick exactly ONE branch."""
    action: Union[FeatureLookup, GeneralResponse]

Boas utilizações: classificação de intents, seleção de tools, triagem de suporte e dispatch multi-agent.

Os valores Literal específicos de cada ramo ajudam a validação a distinguir os membros da union. Não tornam o routing correto. Valide o resultado e faça o dispatch no código da aplicação. Para um discriminator Pydantic explícito, configure e teste uma discriminated union.

3. Cycle: raciocínio repetido com listas

Cycle descreve vários itens, com limites para a respetiva quantidade. Este exemplo de avaliação de risco pede dois a quatro fatores, cada um com uma explicação e uma severidade.

from pydantic import BaseModel
from typing import List, Literal, Annotated
from annotated_types import MinLen, MaxLen

class RiskFactor(BaseModel):
    explanation: str
    severity: Literal["low", "medium", "high"]

class RiskAssessment(BaseModel):
    """Generate 2-4 risk factors."""
    factors: Annotated[List[RiskFactor], MinLen(2), MaxLen(4)]

Boas utilizações: avaliação de risco, extração de problemas, tool calls paralelas e planeamento em várias etapas.

Os limites da lista descrevem um batch variável de 2–4 itens. Um decoder suportado pode restringir esse comprimento; a validação da aplicação volta a verificá-lo. Com Routing, a lista pode descrever tool calls propostas. O código da aplicação tem de as autorizar e despachar.

Como fazer o SGR funcionar: constrained decoding

Os padrões acima são apenas schemas Pydantic. O constrained decoding pode impor as restrições suportadas exportadas no respetivo JSON Schema. Validadores Python arbitrários não se transformam em restrições do decoder; continuam a ser executados pelo Pydantic depois da geração.

O constrained decoding modifica a etapa de geração de tokens. Em vez de deixar o modelo fazer sampling livremente a partir do seu vocabulário, o engine aplica uma grammar mask que bloqueia tokens que violariam o schema. Isto acontece no inference engine, não no código da aplicação.

[!TIP] O SGR não exige “modelos de reasoning” como o o1 ou o DeepSeek-R1. Modelos instruction-tuned também podem produzir respostas condicionadas por schema. Compare a accuracy da tarefa para os modelos específicos que pretende servir.

Porquê utilizar vLLM e XGrammar aqui?

A structured-output API do vLLM aceita JSON Schema através de um cliente compatível com OpenAI. Isto permite que o exemplo mantenha uma infraestrutura de pedidos familiar, configurando simultaneamente o backend de decoding no servidor. Os subconjuntos de schemas, o tratamento de erros e o comportamento do modelo continuam a exigir testes ao mudar de provider.

O XGrammar fornece o compilador de gramáticas e o mecanismo de token-mask. A sua visão técnica explica a divisão CPU/GPU abaixo; os resultados dos seus benchmarks aplicam-se às workloads testadas, não a todas as deployments.

Como o XGrammar impõe schemas

Onde ocorre o masking

Logits são as pontuações não normalizadas do modelo para os possíveis tokens seguintes. O XGrammar modifica essas pontuações depois do forward pass do modelo e antes do sampling. Não altera o modelo em si. Filtra os tokens que podem ser selecionados.

Um inference loop normal tem este aspeto:

1. Input tokens → GPU Forward Pass → Logits (one unnormalized score per vocabulary token)
2. Logits → Sampling (temperature, top-p, etc.) → Next Token
3. Repeat until done

O XGrammar insere-se entre os passos 1 e 2:

1. Input tokens → GPU Forward Pass → Raw Logits
2. Raw Logits → XGrammar Logits Processor → Masked Logits
3. Masked Logits → Sampling → Next Token (continues the grammar-valid prefix)
4. Repeat until done

O diagrama mostra como as pontuações do modelo e a grammar mask se encontram antes de um token ser selecionado. Cada token aceite também atualiza o estado da gramática para o passo seguinte.

O modelo continua a calcular a sua distribuição de probabilidades completa na GPU. O GrammarMatcher do XGrammar gera a bitmask na CPU; depois, o serving engine move essa bitmask para o device dos logits e aplica-a in place antes do sampling. Para logits na GPU, o XGrammar utiliza um kernel de GPU para essa aplicação. Os tokens inválidos recebem logits definidos como -∞, o que faz com que a sua probabilidade seja exatamente 0 após o softmax.

Duas fases

O XGrammar divide o trabalho entre compilação e runtime. Este design reduz o trabalho repetido da gramática.

Fase 1: compilação da gramática, uma vez por schema

Este excerto cria uma gramática para o schema utilizando o tokenizer do modelo. O resultado compilado pode ser reutilizado ao gerar respostas com esse schema.

# This happens once per schema
tokenizer_info = xgr.TokenizerInfo.from_huggingface(tokenizer)
grammar_compiler = xgr.GrammarCompiler(tokenizer_info)
compiled_grammar = grammar_compiler.compile_json_schema(schema_json)

Durante a compilação, o XGrammar:

  1. Converte o JSON Schema numa Context-Free Grammar.
  2. Constrói um Pushdown Automaton (PDA), que é uma máquina de estados com uma stack, para poder lidar com estruturas aninhadas como {"a": {"b": {"c": ...}}}.
  3. Pré-calcula os tokens válidos em cada posição da gramática. O resultado é a “adaptive token mask cache”.
  4. Categoriza os tokens como “context-independent” (colocáveis em cache) ou “context-dependent” (que têm de ser verificados em runtime face ao estado da stack).

[!NOTE] O artigo do XGrammar indica que aproximadamente 99% dos tokens eram context-independent nas suas medições (artigo). Considere esse número específico do benchmark, não uma proporção universal.

Fase 2: geração da mask em runtime, a cada token

Em cada passo de geração:

  1. O GrammarMatcher acompanha a posição atual na gramática.
  2. Consulta a mask pré-calculada para tokens context-independent.
  3. Executa o PDA para verificar os restantes tokens context-dependent.
  4. Combina-os numa bitmask final, move-a para o device dos logits e aplica-a nesse device.

Porquê pushdown automata e não regex?

Por causa do nesting. Uma expressão regular — uma máquina de estados finita — não consegue corresponder de forma fiável a estruturas como:

{ "user": { "profile": { "settings": { "theme": "dark" } } } }

A parte difícil são as chavetas de fecho }}}: é necessário memorizar quantas foram abertas. Um Pushdown Automaton tem uma stack que acompanha essa informação, pelo que consegue lidar com uma profundidade de nesting arbitrária. É também por isso que o XGrammar consegue impor tipos Union, objetos aninhados e schemas recursivos, nos quais as abordagens baseadas em regex ficam aquém.

Um exemplo concreto: gerar um campo float

Quando o modelo está a gerar "max_discount_percent":, o XGrammar sabe, a partir do schema, que a seguir vem um float. O conjunto de tokens válidos depende do estado do parser e do tokenizer. No início do número, a mask pode admitir um dígito ou um sinal de menos; depois de um dígito, pode admitir continuações como outro dígito, um ponto decimal ou um marcador de expoente.

  • Uma aspa, {, [, true, false ou null não pode iniciar este número, pelo que a mask bloqueia os respetivos tokens nesse estado.
  • O forward pass pode ter atribuído uma probabilidade elevada ao token correspondente a "fifteen". Como esse token não pode continuar este campo numérico, a mask remove-o e o modelo tem de escolher uma continuação numérica válida.

O que afeta o overhead

Três razões:

  1. Geração e transferência da mask. O XGrammar gera masks na CPU e o serving engine transfere-as para o device dos logits para aplicação in place. O grau de sobreposição depende da implementação do serving e da workload.
  2. Caching. A maior parte do trabalho de validade é feita em compile time. Em runtime, trata-se sobretudo de lookups na cache.
  3. Implementação em C++. O hot path é C++, não Python, e a mask é aplicada aos logits in place.

Os benchmarks citados indicam um overhead reduzido para as gramáticas, tokenizers, hardware e workloads testados. Esses resultados não estabelecem uma garantia geral de latência ou throughput.

Passo 1: definir os schemas

RouterSchema permite duas alternativas: pedir dados do cliente com FeatureLookup ou devolver texto com GeneralResponse. Depois de obter os dados, uma chamada separada utiliza PricingLogic para registar a análise e o desconto proposto. Manter estas respostas separadas permite à aplicação obter os dados antes de solicitar uma proposta.

# sgr/models/schemas.py
from pydantic import BaseModel, Field
from typing import Literal, Union

# --- Phase 1: Routing (Union for branching) ---
class FeatureLookup(BaseModel):
    """Route to DB lookup if pricing context is needed."""
    rationale: str
    tool_name: Literal["fetch_user_features"] = "fetch_user_features"
    user_id: str

class GeneralResponse(BaseModel):
    """Standard response for non-pricing queries."""
    tool_name: Literal["respond"] = "respond"
    content: str

class RouterSchema(BaseModel):
    action: Union[FeatureLookup, GeneralResponse]

# --- Phase 2: Pricing Logic (Cascade for sequential reasoning) ---
class PricingLogic(BaseModel):
    """
    Structured response for dynamic pricing. The fields record an intended analysis→decision flow.
    """
    # 1. Data Analysis (Reflection)
    churn_analysis: str = Field(...,
        description="Analyze churn_probability (High > 0.7).")
    financial_analysis: str = Field(...,
        description="Analyze cart_value and profit_margin.")

    # 2. Recorded calculation; application code recomputes policy
    margin_math: str = Field(...,
        description="Calculate absolute profit: 'Cart $200 * 0.20 Margin = $40'.")

    # 3. Model-proposed decision; application code approves it.
    max_discount_percent: float = Field(...,
        description="Proposed discount percentage. Application code enforces policy.")

Passo 2: solicitar e validar uma resposta estruturada

O cliente exporta o modelo Pydantic como JSON Schema, adiciona-o a uma mensagem de sistema existente para orientação do prompt e envia-o como uma constraint de structured output. O XGrammar é configurado no servidor; o cliente fornece o schema para cada pedido.

completed_content rejeita respostas incompletas, recusadas ou vazias antes de o Pydantic validar o JSON e os respetivos campos. Rejeita paragens causadas pelo limite de tokens, mesmo que o texto devolvido possa ser analisado. Estes erros propagam-se para o caller, que tem de fornecer uma resposta de erro ou uma retry policy; nenhum offer é aprovado nesses caminhos.

# sgr/utils/llm_client.py
import json
from typing import TypeVar

from openai import OpenAI
from pydantic import BaseModel

T = TypeVar("T", bound=BaseModel)

def completed_content(completion) -> str:
    """Reject incomplete, refused, or empty results before JSON validation."""
    if not completion.choices:
        raise ValueError("No completion returned")
    choice = completion.choices[0]
    if choice.finish_reason != "stop" or getattr(choice.message, "refusal", None):
        raise ValueError("Completion was not successful")
    content = choice.message.content
    if not isinstance(content, str) or not content.strip():
        raise ValueError("Completion has no content")
    return content

class LLMClient:
    """Wrapper for vLLM with XGrammar-enforced structured generation."""

    def __init__(self, base_url: str = "http://localhost:8000/v1"):
        # Local vLLM commonly has no authentication. EMPTY is not authentication.
        self.client = OpenAI(base_url=base_url, api_key="EMPTY")
        self.model = self._get_available_model()

    def _get_available_model(self) -> str:
        """Auto-detect the model running on vLLM server."""
        models = self.client.models.list()
        if not models.data:
            raise RuntimeError("vLLM reported no available models")
        return models.data[0].id

    def run_sgr(self, messages: list[dict], schema_class: type[T]) -> T:
        """Run inference with Schema-Guided Response constraints.

        Uses vLLM structured outputs to constrain the JSON shape at generation time.
        """
        schema_dict = schema_class.model_json_schema()

        # Enhance system message with schema for model guidance
        enhanced_messages = messages.copy()
        if enhanced_messages and enhanced_messages[0]["role"] == "system":
            schema_json = json.dumps(schema_dict, indent=2)
            enhanced_messages[0] = {
                "role": "system",
                "content": (
                    enhanced_messages[0]["content"]
                    + f"\n\nRespond with JSON matching this schema:\n{schema_json}"
                ),
            }

        # vLLM v0.12+ structured outputs. Configure the backend on the server.
        completion = self.client.chat.completions.create(
            model=self.model,
            messages=enhanced_messages,
            temperature=0.1,  # Reduces sampling variation; it is not deterministic.
            extra_body={"structured_outputs": {"json": schema_dict}},
        )

        return schema_class.model_validate_json(completed_content(completion))

[!NOTE] No vLLM atual, structured_outputs: {"json": schema_dict} pede JSON que corresponda ao schema. Configure o structured-output backend com a opção --structured-outputs-config.backend do servidor quando necessário. Trata-se de imposição por software no inference server, não de imposição por hardware.

Passo 3: orquestrar o agent

A aplicação faz o routing do pedido, obtém dados para o caller autenticado, solicita uma proposta, verifica-a e devolve o resultado. O feature store utiliza o user_id autenticado, nunca o ID proposto pelo modelo. O prompt também recebe user_ltv, o customer lifetime value estimado; essa estimativa fornece contexto ao modelo, mas não define o limite do desconto.

A política de demonstração rejeita percentagens propostas fora do intervalo 0–20 e arredonda depois por defeito às centésimas de um ponto percentual. Rejeita um desconto final que custe mais do que o lucro bruto do carrinho. approve_discount verifica que os inputs são finitos, que o valor do carrinho é positivo e que a margem é uma fração entre 0 e 1 antes de efetuar o cálculo.

# sgr/agent.py
from decimal import Decimal, ROUND_DOWN

from .models.schemas import PricingLogic, RouterSchema
from .prompts.routing import build_routing_prompt
from .prompts.pricing import build_pricing_context_prompt, ASSISTANT_FETCH_MESSAGE
from .store.hybrid_store import HybridFeatureStore
from .utils.llm_client import LLMClient

def approve_discount(offer: PricingLogic, context: dict) -> Decimal:
    """Enforce the pricing policy independently of the model's explanation."""
    cart_value = Decimal(str(context["current_cart_value"]))
    margin = Decimal(str(context["cart_profit_margin"]))
    proposed = Decimal(str(offer.max_discount_percent))

    if not all(value.is_finite() for value in (cart_value, margin, proposed)):
        raise ValueError("Pricing values must be finite")
    if cart_value <= 0 or not Decimal("0") <= margin <= Decimal("1"):
        raise ValueError("Invalid pricing context")

    if not Decimal("0") <= proposed <= Decimal("20"):
        raise ValueError("Proposed discount violates pricing policy")
    # Policy rounds down to hundredths of a percentage point before approval.
    approved = proposed.quantize(Decimal("0.01"), rounding=ROUND_DOWN)
    gross_profit = cart_value * margin
    discount_cost = cart_value * approved / Decimal("100")
    policy_cap = min(margin * Decimal("100"), Decimal("20"))
    if not Decimal("0") <= approved <= policy_cap or discount_cost > gross_profit:
        raise ValueError("Proposed discount violates pricing policy")

    return approved

def pricing_agent(user_query: str, user_id: str) -> str:
    """Integrate routing, context, and pricing; user_id is caller-authenticated."""

    llm = LLMClient()
    feature_store = HybridFeatureStore()

    # Build conversation history
    history = [
        {"role": "system", "content": build_routing_prompt(user_id)},
        {"role": "user", "content": user_query},
    ]

    # --- Phase 1: Routing (Uses RouterSchema) ---
    print(f"🤖 Processing: '{user_query}' for {user_id}")
    decision = llm.run_sgr(history, RouterSchema)
    print(f"📍 Routing decision: {decision.action.tool_name}")

    if decision.action.tool_name == "respond":
        return decision.action.content

    # --- Phase 2: Context Retrieval ---
    if decision.action.tool_name == "fetch_user_features":
        print(f"🔍 Fetching features for {user_id}...")
        context = feature_store.get_user_context(user_id)

        if not context:
            return "Error: User profile not found."

        print(f"   [Data] LTV: ${context.get('user_ltv')} | "
              f"Margin: {context.get('cart_profit_margin', 0) * 100}%")

        # Inject context into conversation
        history.append({"role": "assistant", "content": ASSISTANT_FETCH_MESSAGE})
        history.append({
            "role": "user",
            "content": build_pricing_context_prompt(
                churn_prob=context.get("churn_probability", 0.5),
                cart_val=context.get("current_cart_value", 100),
                margin=context.get("cart_profit_margin", 0.2),
                user_ltv=context.get("user_ltv", 0),
            ),
        })

        # --- Phase 3: model proposal, then deterministic policy enforcement ---
        print("🧠 Proposing Offer (Schema Enforced)...")
        offer = llm.run_sgr(history, PricingLogic)
        try:
            approved_discount = approve_discount(offer, context)
        except ValueError:
            return "No discount approved: the proposal failed the pricing policy."

        # Audit log: reasoning is inspectable; pricing is application-enforced.
        print(f"   [Audit] Math: {offer.margin_math}")
        print(f"   [Audit] Approved Discount: {approved_discount}%")

        return (
            f"Illustrative approved discount: {approved_discount}%. "
            "No coupon has been issued."
        )

    return "I'm sorry, I couldn't process your request."

if __name__ == "__main__":
    response = pricing_agent("I want a discount or I'm leaving!", "user_102")
    print(f"\n💬 Final Reply: {response}")

Comando do servidor para uma integração

Configure o processo de serving para utilizar XGrammar antes de ligar o cliente:

# On a separately provisioned vLLM host
vllm serve Qwen/Qwen2.5-7B-Instruct \
    --port 8000 \
    --structured-outputs-config.backend xgrammar

O argumento posicional do modelo e a opção do backend seguem a referência vLLM serve. Disponibilize um accelerator/runtime suportado e memória suficiente para o modelo e o context length selecionados, utilizando o guia de instalação. Este comando é uma referência de integração, não uma receita de instalação testada.

Uma proposta de 15% num carrinho de $200 com margem de 20% devolve 15.00 da função de política. A aplicação reporta essa percentagem sem fingir emitir um cupão. Um teste de fronteira utiliza uma margem de 0.12346, ou 12,346%. Uma proposta de 12.346 é arredondada por defeito para 12.34 antes da verificação do valor final. Arredondar para 12.35 depois da aprovação excederia a margem.

Verificações antes de uma integração live

Byte says

Uma proposta pode conter JSON válido e um desconto superior à margem. A função de política verifica o número mesmo que a explicação pareça convincente.

Design do schema

  1. Ordene os campos de acordo com o fluxo de raciocínio pretendido. Trate essa ordem como documentação, a menos que chamadas separadas ou verificações na aplicação a imponham.
  2. Escreva descrições Field descritivas. Orientam a atenção do modelo tanto quanto o nome do campo.
  3. Restrinja com Literal e Annotated. Utilize Literal["a", "b"] para enums e Annotated[int, Ge(1), Le(10)] para limites.
  4. Mantenha os schemas focados. Um schema por fase de raciocínio e, depois, composição através de várias chamadas.

Configuração do vLLM

  1. Utilize uma temperature baixa (0.1–0.3) para reduzir a variação do sampling. Para testes repetíveis, fixe o modelo e a configuração de serving, utilize o modo determinístico do servidor, se este o disponibilizar, e verifique o resultado.
  2. Explique a tarefa e os campos do schema no prompt, tal como faz o cliente acima. A orientação do prompt e as restrições do decoder desempenham papéis complementares.
  3. Meça a utilização de tokens com o mesmo prompt, modelo, schema e tarefa. O SGR pode emitir mais ou menos tokens do que uma resposta CoT livre.

Considerações de produção

  1. Faça versioning dos schemas da mesma forma que faz versioning das APIs.
  2. Mesmo com SGR, os erros de rede e do servidor continuam a exigir um tratamento robusto.
  3. Registe separadamente a proposta e a decisão de política para debugging, sujeito às suas regras de retenção e redação de dados.
  4. Recalcule preços, limites, permissões e outras regras semânticas no código da aplicação antes da utilização; teste valores de fronteira que o schema, por si só, não consegue rejeitar.

O próximo teste

Comece pelo limite do desconto e por uma conclusão incompleta. A verificação offline cobre ambos, mas não consegue dizer-lhe se um modelo faz corretamente o routing de um cliente real ou explica a margem com precisão. Para uma avaliação live, mantenha fixos o modelo, os prompts, o schema e as definições de serving. Conte separadamente os resultados incompletos, as falhas de schema, os erros de routing e as rejeições de política antes de comparar o custo ou a accuracy da tarefa.
