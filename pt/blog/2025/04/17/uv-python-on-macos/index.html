uv no macOS: gerir versões de Python, projetos e ferramentas

Viacheslav Dubrov

2025-04-17 · Atualizado 2026-07-17 · 7 min · Ferramentas de desenvolvimento

Tradução automática Este artigo foi traduzido automaticamente a partir da versão original em inglês.

Mudei o meu workflow de Python para uv. Este substituiu a alternância que fazia entre pip, ambientes virtuais, pip-tools, pipx e gestores de projetos. Agora, um único executável cobre a maior parte desse trabalho.

Os workflows continuam a ser diferentes. Um projeto, um script com metadados inline, uma CLI pontual e uma CLI instalada têm, cada um, o seu próprio ambiente e ciclo de vida. Este guia mostra os comandos que utilizo e a fronteira subjacente a cada um.

Este guia destina-se a programadores Python no macOS que estão a substituir workflows baseados em pip, ambientes virtuais, pip-tools ou pipx por uv. No final, saberá escolher o ambiente uv adequado para um projeto, um script autónomo, uma ferramenta pontual ou um comando que tem de permanecer em PATH.

Início rápido

# Install uv with Homebrew
brew install uv

# Start a project
uv init example-app
cd example-app
uv add httpx
uv run python main.py

# Run an isolated CLI without installing it permanently
uvx ruff check .

Em resumo. Utilizo uv add, uv lock, uv sync e uv run dentro dos projetos. Utilizo metadados PEP 723 para scripts autónomos, uvx para ferramentas pontuais e uv tool install para comandos que têm de permanecer em PATH. Em CI, --locked verifica se os metadados do projeto estão de acordo com uv.lock. --frozen confia no lock existente sem verificar se está atualizado.

Instalar uv com um único responsável

O Homebrew é uma forma conveniente de instalar no macOS. Consulte o guia de instalação do uv para conhecer os métodos suportados:

brew install uv
uv --version

Se o Homebrew instalou o uv, deve ser o Homebrew a atualizá-lo:

brew upgrade uv

uv self update destina-se ao método de instalação autónoma do uv e está desativado para instalações efetuadas por gestores de pacotes. Não permita que dois instaladores disputem o mesmo executável.

Comandos úteis para confirmar a identidade:

command -v uv
uv python dir
uv tool dir
uv cache dir

As instalações de Python geridas, as ferramentas persistentes e as entradas descartáveis da cache utilizam diretórios separados. A cache pode ser eliminada e reconstruída. Não é uma fonte de verdade.

Projetos: declarações, resolução e ambiente

Um projeto uv tem normalmente três artefactos:

  • pyproject.toml declara os metadados do projeto e os requisitos diretos.
  • uv.lock armazena a resolução multiplataforma do uv.
  • .venv é o ambiente instalado localmente e deve ser descartável.

Crie uma aplicação e adicione os requisitos de runtime e de teste:

uv init forecast-app
cd forecast-app

uv add httpx
uv add --group test pytest
uv run python main.py
uv run --group test pytest

Os templates atuais de aplicações uv criam main.py, pyproject.toml, README.md e .python-version. Por predefinição, não definem um sistema de build. Utilize uv init --lib para uma biblioteca distribuída com um layout src e um build backend.

uv run verifica o projeto, atualiza o lock quando necessário, sincroniza as dependências necessárias e executa o comando. Consulte a documentação do uv sobre layout e sincronização de projetos para conhecer este ciclo de vida. A primeira operação sobre o projeto cria .venv e uv.lock, quando necessário. uv init limita-se a criar os ficheiros do projeto.

Faça commit das entradas, não do ambiente

Faça commit de pyproject.toml, uv.lock, do código-fonte e de um .python-version intencional. Ignore .venv e as caches do uv.

O lock regista uma resolução para os markers e plataformas suportados. Não torna os wheels nativos idênticos entre macOS, Linux, Intel e Apple Silicon. Teste todas as plataformas de deployment.

Atualização do lock: --locked não é --frozen

Byte says

Usei --frozen na CI para ignorar a resolução. Isso também ignorou a verificação de divergência. O lockfile ficou um mês atrás de pyproject.toml e nada ficou vermelho.

Por predefinição, os comandos do projeto podem atualizar uv.lock quando as declarações são alteradas. Consulte a documentação do uv sobre locking e sincronização para conhecer as opções de freshness e exactness.

Utilize --locked para exigir que o lock esteja atualizado relativamente aos metadados do projeto:

uv lock --check
uv sync --locked
uv run --locked pytest

Se pyproject.toml e uv.lock não coincidirem, estes comandos falham em vez de resolverem um novo lock. Normalmente, esta falha é precisamente a barreira de CI pretendida.

Utilize --frozen apenas quando quiser deliberadamente que o uv use o lock existente sem verificar se está atualizado:

uv sync --frozen

Isto pode ser útil numa fase controlada de build em que o lock já foi validado, mas não deteta locks desatualizados.

A exactness é uma definição independente da freshness. uv sync é exacto por predefinição e remove pacotes supérfluos. uv run utiliza uma sincronização inexata por predefinição, exceto quando é pedido --exact.

Python gerido: um pedido de versão, não um binário universal

O uv pode descarregar e gerir distribuições de Python:

uv python install 3.12 3.13
uv python list --only-installed
uv python pin 3.12

As builds de CPython geridas pelo uv provêm do projeto python-build-standalone. O uv também pode descobrir interpretadores do sistema, do Homebrew, pyenv, Conda e outras origens. Consulte a documentação do uv sobre versões de Python para conhecer as origens suportadas e o comportamento de discovery.

.python-version é um pedido de versão descoberto pelo uv e por outras ferramentas compatíveis. requires-python em pyproject.toml é o contrato de compatibilidade do projeto. Mantenha ambos intencionais:

[project]
requires-python = ">=3.12,<3.14"

Fixar 3.12 não garante para sempre a mesma build de patch nem o mesmo artefacto em todos os sistemas operativos. Peça um patch exato quando precisar de um e faça com que a CI selecione e comunique explicitamente o interpretador.

Utilize outro gestor de Python quando um projeto precisar de uma distribuição ou configuração de build que o uv não disponibilize. O uv pode continuar a utilizar esse interpretador através de --python ou da discovery normal.

Escolher entre uv run, uvx e ferramentas instaladas

Ferramentas associadas ao projeto: uv run

Se pytest, mypy, um gerador de código ou outra ferramenta tiver de importar o projeto ou utilizar os respetivos plugins bloqueados, declare-a num grupo de dependências:

uv add --group lint ruff
uv run --group lint ruff check .

Executar essa ferramenta através de uvx isolá-la-ia do projeto e poderia ocultar o pacote instalado ou os plugins de que necessita.

Ferramentas ad hoc: uvx

uvx é um alias de uv tool run. Cria um ambiente isolado armazenado na cache descartável do uv. A documentação do uv sobre tools descreve esta cache e o ciclo de vida das ferramentas persistentes:

uvx ruff@0.12.0 check .
uvx --from jupyterlab jupyter lab
uvx --with mkdocs-material mkdocs --help

Fixe a versão da ferramenta na CI ou na documentação. Uma primeira invocação sem versão seleciona uma release atual e as invocações posteriores podem reutilizar o estado da cache.

Executáveis persistentes: uv tool install

Instale uma ferramenta quando scripts fora do seu controlo precisarem do respetivo comando em PATH ou quando o manifesto de configuração da máquina tiver de ser o responsável por essa ferramenta:

uv tool install ruff
uv tool list
uv tool upgrade ruff
uv tool uninstall ruff

As ferramentas persistentes continuam a utilizar ambientes isolados. Não altere manualmente esses ambientes com pip.

Scripts: faça de um único ficheiro a unidade de release

A PEP 723 define metadados inline para scripts. Um runner compatível pode ler o bloco de comentários e criar um ambiente isolado. Consulte o guia de scripts do uv e a PEP 723 para conhecer o formato dos metadados e o comportamento do runner.

# /// script
# requires-python = ">=3.12"
# dependencies = [
#   "httpx>=0.27,<1",
# ]
# ///
import httpx

response = httpx.get("https://example.com", timeout=10)
response.raise_for_status()
print(response.status_code)

Execute o script e edite os metadados com uv:

uv run fetch.py
uv add --script fetch.py rich
uv remove --script fetch.py rich

Um python fetch.py simples ignora os metadados nos comentários. Por isso, o script depende de um runner compatível, embora a sintaxe Python continue válida.

Para um script que tenha de reproduzir uma resolução posteriormente, crie um lock adjacente:

uv lock --script fetch.py
uv run --script fetch.py

Isto escreve fetch.py.lock. Um timestamp exclude-newer pode restringir as datas dos artefactos candidatos, mas é mais fraco do que uma resolução bloqueada exata e não garante que um artefacto continue disponível.

Utilize um projeto quando vários ficheiros partilharem dependências, o código for importável como pacote, os testes precisarem do estado do projeto ou vários scripts tiverem de evoluir em conjunto.

Ficheiros de requirements: compatibilidade, não garantia de falha

Um ficheiro requirements.txt pode conter entradas flexíveis, pins exatos, hashes, constraints, indexes, URLs ou uma exportação de requirements gerada por um resolver. A sua reprodutibilidade depende da forma como foi produzido e consumido. O nome do ficheiro, por si só, não informa sobre isso.

Utilize a interface compatível com pip do uv sem migrar:

uv venv
uv pip sync requirements.txt
uv run python app.py

uv pip sync faz com que o ambiente corresponda ao ficheiro. uv pip install -r é aditivo.

Numa aplicação sob a sua responsabilidade, uma migração faseada pode ser útil:

uv init --bare
uv add -r requirements.in
uv add --group test -r requirements-test.in
uv lock
uv sync --locked

Execute todo o percurso de testes e deployment antes de eliminar os ficheiros antigos. Se um sistema downstream ainda esperar o formato do pip, derive-o do lock uv validado com o comando de export do uv:

uv export --format requirements.txt \
  --output-file requirements.txt

Não mantenha uv.lock e uma exportação editada manualmente como duas resoluções concorrentes.

Cache, indexes e fronteiras da supply chain

A cache do uv melhora as instalações repetidas, mas continua a ser descartável:

uv cache prune
uv cache clean

Prefira prune para a limpeza habitual. clean remove todas as entradas da cache e força novos downloads e builds posteriores.

Um lockfile melhora a repetibilidade. Não torna as dependências fiáveis. Reveja as origens dos pacotes, a configuração dos indexes, as revisões Git, os build backends, as licenças e as credenciais. Mantenha a configuração de indexes autenticados fora dos ficheiros versionados. A exceção é uma referência não secreta a um mecanismo de credenciais aprovado.

Para pacotes nativos, registe a arquitetura de deployment e teste a disponibilidade dos wheels. Caso contrário, um resolver pode recorrer a uma build a partir do código-fonte que necessite de compiladores e bibliotecas de sistema ausentes na CI ou em produção.

Checklist operacional compacto

Para cada projeto:

  1. Defina requires-python e as dependências diretas em pyproject.toml.
  2. Separe os extras publicados dos grupos de dependências locais.
  3. Faça commit de uv.lock. Ignore .venv e o estado da cache.
  4. Execute as ferramentas associadas ao projeto através do ambiente do projeto.
  5. Utilize uv lock --check ou --locked na CI.
  6. Teste todos os sistemas operativos e arquiteturas de destino representados pelo lock.
  7. Exporte formatos de compatibilidade apenas para consumidores downstream identificados.
  8. Reveja a política de origens e credenciais independentemente da resolução.

O uv é mais útil quando estas fronteiras de responsabilidade permanecem visíveis. Um único binário pode geri-las a todas sem as transformar num único ambiente. Menos ferramentas, mantendo separados os quatro workflows. É por isso que continuo a utilizá-lo como ferramenta Python predefinida para projetos no macOS.
