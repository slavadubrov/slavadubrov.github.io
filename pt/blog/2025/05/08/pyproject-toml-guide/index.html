pyproject.toml Guia: Empacotamento em Python, Dependências e Configuração de Ferramentas

Projetos mais antigos em Python costumam dispersar a configuração por setup.py, setup.cfg, ficheiros de requisitos, MANIFEST.in, bem como ficheiros separados para as ferramentas de desenvolvimento. pyproject.toml oferece um local unificado para esses elementos, embora não substitua todos os ficheiros do projeto nem torne todas as seções parte de um padrão único.

Este guia explora o ficheiro, desde a configuração de compilação até à metadados do projeto e às definições das ferramentas. A forma mais simples de mantê-lo compreensível é dividir as responsabilidades em quatro áreas distintas: o que compila o projeto, o que o projeto publica, o que os colaboradores necessitam localmente e o que as ferramentas individuais configuram.

TL;DR. Utilize [build-system] para o backend responsável pela criação da distribuição, [project] para os metadados publicados e os requisitos em tempo de execução, [dependency-groups] para ambientes de desenvolvimento não publicados, e [tool.*] apenas quando a documentação da ferramenta o indicar. Uma declaração de dependência não é um ficheiro de bloqueio.

Um ficheiro, quatro responsáveis

Três padrões de empacotamento definiram a estrutura básica:

  • PEP 518 define os requisitos do sistema de compilação.
  • PEP 621 define os metadados do projeto.
  • PEP 735 define grupos de dependências não publicados.

Os criadores de ferramentas também podem reivindicar um espaço de nomes abaixo de [tool]. Essa área é convencional, mas não universal: cada ferramenta define as suas próprias chaves e comportamentos.

Aqui está uma pequena biblioteca empacotada:

[build-system]
requires = ["hatchling>=1.26"]
build-backend = "hatchling.build"

[project]
name = "weather-client"
version = "0.1.0"
description = "A small weather API client"
readme = "README.md"
requires-python = ">=3.11"
dependencies = [
  "httpx>=0.27",
]

[project.optional-dependencies]
cli = ["rich>=13"]

[project.scripts]
weather = "weather_client.cli:main"

[dependency-groups]
test = ["pytest>=8", "pytest-cov>=5"]
lint = ["ruff>=0.12"]

[tool.pytest.ini_options]
testpaths = ["tests"]

[tool.ruff]
line-length = 100
target-version = "py311"

Cada lista de dependências responde a uma pergunta diferente. Essa distinção é o ponto central do ficheiro.

[build-system]: como o código-fonte se torna uma distribuição

Um frontend de compilação, como python -m build, pip ou uv, invoca um backend de compilação. O backend decide como a árvore de código-fonte se transforma num sdist ou wheel e quais ficheiros fazem parte desses artefatos.

[build-system]
requires = ["hatchling>=1.26"]
build-backend = "hatchling.build"

requires contém as dependências necessárias para executar o backend no seu ambiente de compilação isolado. Não se trata da lista de dependências em tempo de execução do seu pacote.

Deve declarar-se um sistema de compilação sempre que o projeto gere uma distribuição ou precise que o seu próprio código seja instalado como pacote. Um projeto que não seja um pacote ainda pode utilizar pyproject.toml; o PEP 735 permite inclusive ficheiros que contenham apenas grupos de dependências. Os gestores de ambiente diferem na forma como tratam projetos sem sistema de compilação, portanto deve fazer essa escolha de forma deliberada.

Escolha o backend com base nos requisitos de compilação:

  • necessidades de layout puramente em Python e seleção de ficheiros
  • extensões compiladas ou sistemas de compilação externos
  • requisitos de versão dinâmica ou ficheiros gerados
  • comportamento de instalação editável
  • maturidade do backend no pipeline de lançamento

Copie a tabela atualmente recomendada pelo backend a partir da sua documentação. Não adicione wheel aos requisitos de compilação por hábito; é o backend que declara o que precisa.

[project]: informações recebidas pelos consumidores de metadados

A tabela [project] descreve a distribuição: o seu nome, versão, compatibilidade com Python, dependências em tempo de execução, pontos de entrada e outros metadados de indexação.

[project]
name = "weather-client"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = ["httpx>=0.27"]

Os especificadores de dependência são restrições para um resolvedor, e não uma representação instantânea de um ambiente. Eles passam a fazer parte dos metadados dos arquivos wheel e sdist, permitindo que os instaladores subsequentes os combinem com as exigências de outros pacotes.

Os extras constituem uma interface pública de instalação

[project.optional-dependencies] define os extras que os utilizadores podem solicitar:

[project.optional-dependencies]
cli = ["rich>=13"]
postgres = ["psycopg[binary]>=3.2"]

Um utilizador pode instalar weather-client[cli]. Como os nomes e requisitos dos extras são publicados, deve‑se tratá‑los como funcionalidades do produto. Não utilize um extra denominado dev apenas para armazenar todas as ferramentas de contribuidores.

Os pontos de entrada ligam os comandos instalados ao Python

[project.scripts]
weather = "weather_client.cli:main"

Após a instalação da distribuição, o ambiente expõe weather, que importa e executa weather_client.cli:main. Teste o comando a partir de um wheel compilado, e não apenas a partir da raiz do repositório; é o wheel que os utilizadores recebem.

[dependency-groups]: ambientes locais e não publicados

O PEP 735 descreve grupos de dependência para ambientes de desenvolvimento ou que não são pacotes, sem publicá‑los como metadados de pacote.

[dependency-groups]
test = ["pytest>=8", "pytest-cov>=5"]
lint = ["ruff>=0.12"]
dev = [
  { include-group = "test" },
  { include-group = "lint" },
]

Este é o limite adequado para testes, linters, geradores de documentação e ferramentas semelhantes de contribuidores. É também útil para aplicações ou notebooks que não criam uma distribuição.

Os grupos de dependência são dados padronizados, mas as interfaces de instalação ainda variam. Verifique como o gestor de ambiente selecionado os instala, bloqueia e resolve. O PEP 735 não define uma interface de linha de comando universal.

[tool.*]: configuração pertencente a uma única ferramenta

As tabelas de ferramentas não partilham um esquema comum:

[tool.pytest.ini_options]
addopts = "-ra"
testpaths = ["tests"]

[tool.ruff]
line-length = 100

Utilize uma tabela [tool.*] apenas se a própria ferramenta o documentar. Algumas definições continuam a ser mantidas em ficheiros próprios porque outro ecossistema as consome, o ficheiro requer um formato diferente ou a configuração fica mais clara isoladamente. pyproject.toml serve apenas como ponto de coordenação, e não como obrigação de centralizar tudo.

Declarações, ficheiros de bloqueio e ficheiros de requisitos resolvem problemas diferentes

A fonte mais comum de confusão consiste em tratar cada artefato de dependência como uma fonte de verdade concorrente.

ArtefatoFinalidade principalConteúdo típico
[project.dependencies]Contrato de execução publicadoRequisitos diretos e intervalos compatíveis
[project.optional-dependencies]Funcionalidades opcionais publicadasExtras destinados aos utilizadores
[dependency-groups]Ambientes locais não publicadosGrupos para testes, linters, documentação ou aplicações
Ficheiro de bloqueioReproduzir um ambiente resolvidoVersões exatas, fontes e metadados de resolução
requirements.txtEntrada de instalação compatível com pipRequisitos acrescidos de opções, restrições, URLs ou hashes específicos do pip

Uma biblioteca costuma publicar restrições e testes compatíveis para um determinado intervalo. Uma aplicação, por sua vez, geralmente guarda o ficheiro de bloqueio gerado pelo gestor de ambientes. As versões exatas devem constar no artefato de deploy resultante, e não de forma arbitrária nos metadados públicos da biblioteca.

É recomendável manter um ficheiro de requisitos sempre que uma integração exigir o formato ou funcionalidades específicas do pip. Se um projeto gerido por uv precisar desse ficheiro, deve ser exportado a partir do lockfile, em vez de se manterem dois conjuntos de dependências independentes:

uv export --format requirements.txt --output-file requirements.txt

A exportação resulta de uma análise de compatibilidade. O lockfile continua a ser a fonte oficial para esse fluxo de trabalho.

Uma migração que preserva o comportamento

Não comece eliminando setup.py ou requirements.txt. Primeiro, identifique a função de cada ficheiro existente.

  1. Inventarie a lógica de compilação, os metadados, os requisitos em tempo de execução, os recursos adicionais, os ambientes de desenvolvimento, as definições de ferramentas, os dados dos pacotes e os pontos de entrada.
  2. Escolha um backend capaz de reproduzir a inclusão de ficheiros atual, os artefatos compilados e as instalações editáveis.
  3. Mova os metadados estáticos publicados para [project]; mantenha explícitos apenas os campos verdadeiramente dinâmicos.
  4. Transfira os requisitos destinados apenas aos colaboradores para [dependency-groups], e não como recursos públicos.
  5. Mova as definições de ferramentas apenas quando a ferramenta suportar semânticas equivalentes.
  6. Crie tanto um sdist como um wheel, analise o seu conteúdo e instale o wheel num ambiente limpo.
  7. Execute os pontos de entrada, os testes, as verificações de importação e o processo real de deploy.
  8. Elimine as configurações antigas somente após os artefatos e o comportamento corresponderem.

MANIFEST.in pode ainda ser necessário em algumas estruturas do setuptools, e um pequeno setup.py pode permanecer válido para comportamentos de compilação programática. A modernização consiste numa mudança de responsabilidade, e não numa competição para eliminar ficheiros.

Um fluxo de trabalho atual com uv

O uv distingue aplicações de bibliotecas ao criar um projeto:

# Non-library application template
uv init weather-app

# Packaged library with a src layout and build system
uv init --lib weather-client

uv init cria os ficheiros do projeto. A primeira operação realizada no projeto, como uv run, uv sync ou uv lock, gera o ficheiro de bloqueio e o .venv persistente, conforme necessário.

cd weather-client
uv add httpx
uv add --group test pytest pytest-cov
uv run pytest
uv build

Atualmente, o uv coloca os requisitos de desenvolvimento local em grupos de dependências padronizados. O seu backend nativo uv_build é uma opção para projetos puramente em Python; extensões compiladas exigem alternativas adequadas, como maturin ou scikit-build-core.

Conclusão

pyproject.toml fica mais claro quando cada tabela tem um público definido. A isolação de compilação pertence a [build-system]. O comportamento publicado pertence a [project]. Os ambientes dos colaboradores pertencem a [dependency-groups]. As alterações de ferramenta pertencem à ferramenta que as define.

Assim que essas fronteiras estiverem estabilizadas, os ficheiros tornam-se mais fáceis de rever — e as migrações deixam de confundir os metadados dos pacotes com o ambiente resolvido de um determinado equipamento.
