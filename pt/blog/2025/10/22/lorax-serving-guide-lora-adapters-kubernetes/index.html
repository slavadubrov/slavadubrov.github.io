Guia de Serviço LoRAX: Operar Múltiplos Adaptadores LoRA em Kubernetes

Um modelo base e vários adaptadores LoRA criam um problema de servir incomum. Os pesos do modelo base são partilhados, mas cada pedido pode exigir um conjunto diferente de pesos do adaptador. Um design convencional de uma implantação por variante desperdiça memória GPU quando a maioria das variantes permanece inativa.

LoRAX resolve esse problema relacionado com a “cauda longa”. Ele carrega os adaptadores sob demanda, agrupa pedidos destinados a adaptadores diferentes e transfere os pesos dos adaptadores entre a memória GPU e a CPU. O título atrativo é “milhares de modelos retocados num único GPU”. A questão técnica é mais específica: o conjunto atual de adaptadores ativos, o padrão de chegada dos pedidos e o objetivo de latência beneficiam-se suficientemente do agendamento de troca para justificar a utilização de outro ambiente de execução?

Este guia responde a essa pergunta, verifica a API localmente e, em seguida, transforma o diagrama Helm de inicialização do repositório num plano de produção detalhado.

TL;DR. Escolha o LoRAX quando vários adaptadores LoRA compatíveis partilham um mesmo modelo base e o tráfego é escasso ou apresenta uma cauda longa. A capacidade depende do conjunto de adaptadores ativos em uso, e não do tamanho do catálogo. Defina o ambiente de execução, autentique e inclua na lista de permissões os IDs dos adaptadores, adicione armazenamento em cache duradouro e ferramentas de monitorização, direcione os pedidos para garantir localidade de cache e faça testes de desempenho separadamente para cenários de cache vazio e cheio.

O problema de servir resume‑se ao conjunto de trabalho

O LoRA congela um modelo base e aprende atualizações de baixo rank para matrizes de pesos selecionadas. O adaptador resultante costuma ser muito menor do que um checkpoint completo, mas o seu tamanho ainda depende do rank, dos módulos alvo, do número de camadas e do tipo de dado. Afirmações fixas como “cada adaptador ocupa 100 MB” não fornecem informações precisas sobre a capacidade.

Para fins de servir, distingam‑se três grandezas:

  • Tamanho do catálogo: todos os adaptadores que uma plataforma consegue recuperar a partir do armazenamento
  • Conjunto de trabalho ativo: adaptadores que recebem pedidos dentro do período de retenção no cache
  • Conjunto concorrente: adaptadores representados em lotes ao mesmo tempo

Um catálogo pode conter milhares de adaptadores sem ocupar milhares de MB de VRAM. O que realmente importa é a frequência com que o conjunto ativo muda, o tamanho desses adaptadores e se os pedidos para adaptadores diferentes podem partilhar lotes úteis.

O LoRAX combina quatro mecanismos:

  1. O modelo base permanece em memória para todos os adaptadores compatíveis.
  2. Um pedido especifica um adaptador, que pode ser recuperado a partir da Hugging Face, da Predibase ou de um sistema de ficheiros.
  3. O agendamento de troca de adaptadores faz pré‑carregamento e transfere pesos entre a memória GPU e a CPU.
  4. O agrupamento contínuo heterogéneo organiza pedidos destinados a adaptadores diferentes em lotes.

O projeto indica que o agrupamento heterogéneo mantém a taxa de transferência e a latência praticamente constantes à medida que o número de adaptadores concorrentes aumenta nos seus testes de desempenho. Trate isso como uma hipótese para o seu workload. O comprimento do prompt, o comprimento da saída, o rank, os módulos alvo, a ocupação do lote, a renovação do cache e a geração pela GPU podem alterar os resultados.

Quando o LoRAX é uma opção viável

O LoRAX merece ser avaliado em benchmarks quando se verificam todas as seguintes condições:

  • Os adaptadores foram treinados com base no mesmo modelo base e contrato de tokenizador suportados
  • O tráfego abrange vários adaptadores, com uma cauda longa significativa
  • Carregar um adaptador frio sob demanda é preferível a reservar uma implantação exclusiva para ele
  • Já existe um sistema de roteamento de tenants ou tarefas na camada da aplicação
  • A equipa consegue operar um ambiente de inferência especializado e compreender o seu comportamento de cache

Exemplos típicos incluem assistentes específicos por utilizador, múltiplas variantes de domínio e experimentos online que partilham um ponto de verificação base.

A abordagem é menos adequada quando poucos adaptadores dominam o tráfego, os modelos não partilham uma base comum, objetivos de latência elevados não permitem cargas iniciais lentas, ou a plataforma não consegue controlar de forma segura quais artefatos o servidor deve carregar. Nesses casos, uma implementação padrão de vLLM ou TGI com um conjunto fixo de adaptadores pode ser mais simples.

Não utilize Kubernetes apenas porque o catálogo é grande. Primeiro, prove a compatibilidade entre o ambiente de execução e os adaptadores numa única GPU.

Verifique localmente uma base e dois adaptadores

O README do LoRAX recomenda o seu contêiner pré-construído. Em um ambiente real, utilize um digest de imagem imutável; main é exibido aqui apenas porque corresponde à tag de inicialização rápida documentada pelo repositório.

mkdir -p data

docker run --rm --gpus all --shm-size 1g \
    -p 8080:80 \
    -v "$PWD/data:/data" \
    ghcr.io/predibase/lorax:main \
    --model-id mistralai/Mistral-7B-Instruct-v0.1

Os requisitos mínimos documentados são Linux, Docker, uma GPU NVIDIA da série Ampere ou superior, e drivers compatíveis com CUDA 11.8. Licenças de modelo e repositórios protegidos também podem exigir um token da Hugging Face.

Comece com o modelo base:

curl http://127.0.0.1:8080/generate \
    -H 'Content-Type: application/json' \
    -d '{
      "inputs": "[INST] Give one reason to measure cold-adapter latency. [/INST]",
      "parameters": {"max_new_tokens": 64}
    }'

Em seguida, envie um adaptador compatível:

curl http://127.0.0.1:8080/generate \
    -H 'Content-Type: application/json' \
    -d '{
      "inputs": "[INST] Solve: Natalia sold 48 clips in April and half as many in May. What is the total? [/INST]",
      "parameters": {
        "max_new_tokens": 64,
        "adapter_id": "vineetsharma/qlora-adapter-Mistral-7B-Instruct-v0.1-gsm8k"
      }
    }'

A primeira requisição pode precisar baixar e carregar o adaptador; requisições posteriores podem utilizar artefatos em cache e pesos residentes. Registe ambos os caminhos. Uma única requisição rápida não fornece informações significativas sobre o comportamento em cenários menos comuns.

Utilize o cliente OpenAI atual

O LoRAX expõe um endpoint de chat compatível com o OpenAI. O campo model identifica o adaptador:

from openai import OpenAI


client = OpenAI(
    api_key="EMPTY",
    base_url="http://127.0.0.1:8080/v1",
)

response = client.chat.completions.create(
    model="alignment-handbook/zephyr-7b-dpo-lora",
    messages=[
        {"role": "user", "content": "Explain cache locality in two sentences."},
    ],
    max_tokens=100,
)

print(response.choices[0].message.content)

Por predefinição, o servidor não requer chave API. Isso é conveniente para uso em localhost, mas inseguro como configuração para acesso via Internet. Implemente autenticação, autorização por utilizador, cotas e lista de permissões de adaptadores antes de utilizá-lo.

Defina um filtro de compatibilidade

Antes de um adaptador ser incluído no catálogo, verifique, no mínimo:

  • modelo base e revisão declarados
  • compatibilidade entre tokenizer e template de chat
  • classe LoRA e módulos alvo suportados pelo ambiente de execução
  • formato dos artefatos e formas dos tensores
  • licença, origem e digest de integridade
  • um pequeno conjunto de testes de comportamento e regressão

Rejeite artefatos incompatíveis durante o registo, e não na primeira requisição de um utilizador.

Entenda a residência antes de implementar

O modelo base consome a maior parte fixa da memória da GPU. Os pesos dos adaptadores, o cache KV, o espaço de trabalho em lote e os kernels em tempo de execução competem pelo restante. A RAM da CPU pode armazenar adaptadores offloadados, enquanto /data guarda os artefatos baixados.

Esses níveis não são intercambiáveis. Um artefato armazenado em disco ou no Hub precisa ser lido e materializado antes de se tornar um adaptador residente na CPU ou na GPU. Meça as transições separadamente:

CaminhoO que incluiMétrica a registrar
Acesso GPUAdaptador já residentetempo de fila e tempo até o primeiro token
Acesso CPUTransferência ou rematerialização para GPUatraso no carregamento do adaptador e latência total
Acesso a artefatoLeitura do cache local /dataatraso na leitura/carregamento e tamanho em bytes do cache
Falha remotaBaixar, validar e carregartempo de download, falhas e latência total em carga inicial

O planeamento de capacidade deve replicar a distribuição real de popularidade dos adaptadores. IDs de adaptador aleatórios e uniformes geram um problema de cache diferente em comparação com um cenário de carga de trabalho semelhante ao modelo Zipf.

Implante o diagrama do repositório com cuidado

O repositório contém charts/lorax, pelo que o ponto de partida reprodutível é uma revisão do repositório fixada e um diagrama local:

git clone https://github.com/predibase/lorax.git
cd lorax
git checkout <reviewed-commit-or-release>

helm dependency update charts/lorax
helm template lorax charts/lorax -f values.production.yaml
helm upgrade --install lorax charts/lorax \
    --namespace inference \
    --create-namespace \
    -f values.production.yaml

Conforme analisado a 15 de julho de 2026, os valores padrão do diagrama merecem atenção:

  • a etiqueta da imagem é latest
  • /data é um emptyDir, pelo que a substituição de pods elimina os artefatos descarregados
  • as sondas de atividade e prontidão estão vazias
  • o token do Hugging Face é tratado como um valor de ambiente literal
  • é solicitada uma GPU por predefinição

Isso torna o diagrama um suporte útil, mas não uma política para produção.

Parta da estrutura real de valores do diagrama

O diagrama agrupa a configuração em tempo de execução sob deployment, e os argumentos do lançador são uma lista de pares nome/valor. Uma sobreposição mínima tem a seguinte aparência:

deployment:
    replicas: 1

    image:
        repository: ghcr.io/predibase/lorax
        tag: "<tested-tag>" # Prefer an immutable digest in rendered manifests.

    args:
        - name: "--model-id"
          value: "mistralai/Mistral-7B-Instruct-v0.1"
        - name: "--max-input-length"
          value: "2048"
        - name: "--max-total-tokens"
          value: "3072"
        - name: "--max-batch-total-tokens"
          value: "8192"
        - name: "--max-batch-prefill-tokens"
          value: "4096"

    resources:
        requests:
            nvidia.com/gpu: "1"
        limits:
            nvidia.com/gpu: "1"

    readinessProbe:
        httpGet:
            path: /health
            port: http
        periodSeconds: 5
        failureThreshold: 600

service:
    serviceType: ClusterIP
    port: 80

Os limites de tokens mencionados acima são valores iniciais exemplares, e não recomendações de dimensionamento. Eles devem ser determinados com base em prompts representativos, concorrência esperada, memória da GPU e testes de carga.

Corrija as lacunas de forma explícita

O modelo atual do diagrama define de forma rígida volumes de emptyDir e valores de ambiente simples. Por isso, uma implementação robusta requer uma versão modificada do diagrama, uma correção pós-geração ou uma camada de manifesto de nível superior para adicionar:

  • um PersistentVolumeClaim ou cache de artefatos local no nó montado em /data
  • uma referência a Secret para credenciais do Hub
  • uma sonda de inicialização antes de uma sonda de atividade mais agressiva
  • política de interrupção de pods e distribuição por topologia para múltiplas réplicas
  • NetworkPolicy, restrições de conta de serviço e um gateway autenticado
  • fixação de digests de imagem e verificações de integridade de artefatos

Não coloque um token do Hub diretamente num ficheiro de valores com commits. Não presuma que duas réplicas garantam alta disponibilidade útil até que ambas consigam carregar o modelo base e o router consiga evitar enviar todos os adaptadores “frios” para ambos os pods.

Roteie para localidade de cache

O balanceamento round-robin pode transformar cada réplica num cache “frio”. Um router eficaz hasha ou associa de outra forma um ID de adaptador permitido a uma réplica, mantendo ao mesmo tempo um caminho de failover quando essa réplica estiver indisponível.

A chave de roteamento deve provir do estado autenticado da aplicação, e não de um parâmetro de URL público arbitrário. Caso contrário, um utilizador externo pode forçar downloads remotos, esvaziar caches ou sondar nomes de adaptadores privados.

LoRAX ou vLLM?

O vLLM atual consegue servir módulos LoRA declarados na inicialização e também carregá-los dinamicamente através de endpoints ou plugins de resolução. A sua própria documentação alerta que a atualização de adaptadores em tempo de execução apresenta riscos de segurança e não deve ser utilizado em produção fora de um ambiente isolado e confiável.

A comparação relevante é de natureza operacional, e não numérica:

PerguntaLoRAXvLLM
Como são descobertos os adaptadores de cauda longa?O ID do adaptador permite aceder a recursos da Hugging Face, Predibase ou a ficheiros no sistema de ficheiros mediante pedidoMódulos estáticos, endpoints de gestão dinâmica ou plugins de resolução
Como é gerida a residência?Agendamento explícito da troca de adaptadores entre GPU e CPULimites configurados para LoRA ativa e em CPU, além do comportamento do resolvedor
Qual é a interface de pedido?Estilo TGI /generate, cliente em Python e chat compatível com OpenAIServiço compatível com OpenAI e APIs nativas em Python
O que deve determinar isso?Latência em condições de carga baixa/alta, taxa de atualização do cache, throughput de lotes heterogéneos e adequação operacionalOs mesmos critérios de reprodução de carga de trabalho e operacionais

Evite afirmações como “LoRAX para 1.000 adaptadores, vLLM para dez”. O tamanho do catálogo por si só não determina o desempenho. Faça benchmarks com a mesma base, adaptadores, prompts, classificações, sequências de chegada e hardware.

Um teste de aceitação em produção

Antes de expandir o catálogo, execute uma reprodução que inclua:

  1. Um conjunto fixo de adaptadores “quentes” para estabelecer o throughput e a latência em condições normais.
  2. Uma distribuição de cauda longa para medir as consultas ao cache e ao processador relacionadas com esses adaptadores.
  3. Um aumento súbito de adaptadores anteriormente desconhecidos, mas incluídos na lista permitida.
  4. Substituição de pods para avaliar a recuperação da base e dos adaptadores.
  5. Um adaptador indisponível ou corrompido para verificar o isolamento e mecanismos de fallback.
  6. Utilizadores concorrentes para validar autenticação, cotas e etiquetas de métricas.

Registe a taxa de pedidos, tempo de espera na fila, tempo até ao primeiro token, latência entre tokens, latência total, tempo de carregamento dos adaptadores, categoria de acerto no cache, memória GPU e CPU, bytes transferidos e falhas por motivo. Mantenha os IDs dos adaptadores fora de etiquetas de métricas ilimitadas; associe-os a dimensões controladas ou a rastreios amostrados.

Defina limiares de aceitação antes do teste. Exemplos incluem uma taxa máxima de erros em caminhos de carga baixa, um alvo P99 para condições normais, um alvo de acerto no cache para a distribuição de popularidade observada e um objetivo de tempo de recuperação após perda de pod.

Conclusão

O LoRAX transforma muitos ajustes finos compatíveis, que antes eram considerados cópias de modelos base, num problema de alocação de adaptadores. Isso pode ser uma abordagem eficaz para cargas de trabalho de cauda longa, mas não garante necessariamente custos ou latências constantes. O conjunto de adaptadores ativamente utilizados, o caminho de troca, a composição dos lotes e a camada de armazenamento continuam a influenciar o resultado final.

Teste primeiro esses mecanismos numa única GPU. Depois, trate o Kubernetes com seriedade: fixe os artefatos, preserve o cache, proteja as credenciais, autorize os adaptadores, direcione os pedidos de acordo com a localização geográfica e meça cada caminho de residência. Se o LoRAX superar uma configuração atual do vLLM nas mesmas condições de teste, a decisão de implementação terá fundamentos sólidos.
